Recurring decision surface for `kind: infra` plan reviews. Infra plans live or die on integration-point correctness; the cheap independent verification is grep + reading the cited lines.

**A. Protection-illusion holes (#564, HF storage headroom)** — ways a guard looks armed but is inert:
1. *Partial-None probe blind spot:* a usage probe mapping per-item `None` → 0 (suspect-guard only on ALL-zero) understates when the ONE dominant item returns None (#541: 10.2 of 11.3 TB in one repo). Demand: count Nones, fold into `basis`, any-None-on-nonempty = suspect.
2. *Deviation events emitted pod-side need a named observer.* Pod code cannot post `epm:` markers; a "plan-deviation note" as pod-local log + JSONL dies at termination unless the filename matches the poller's sentinel glob (`/workspace/logs/issue-<N>-*.json`) or it uploads as non-LFS text. Grep poll_pipeline.py / upload-verifier.md for the event name — emission with zero wired observer is prose, not a channel. Usually a Concern (doc edit in scope).
3. *Opt-in flag interplay:* reroute keyed on a signal + a kill switch on the signal source means FLAG=1 + CHECK=0 is silently status quo — demand a loud warning on the armed-but-blind combo.
4. *Soft-ceiling vs hard-wall conflation:* a gate aborting in the deliberate runway zone must not claim "doomed" — old behavior succeeds there; wording + autonomous-blockage cost should be named.
These are usually implementer-absorbable Concerns; REVISE only if the mechanism would not fire in the very incident it was designed for, or a failure path is WORSE than status quo (prefer fail-open on unknown).

**B. Choke-point claims are grep-checkable — do it (#564).** When a plan claims "function X is THE funnel for behavior Y", grep the call sites and compare against the plan's enumeration; a missed caller is a silent routing hole, an exact match is strong APPROVE evidence.

**C. Test-plan holes (#607, GCP startup-script SIGPIPE):**
1. *Success-path-only integration tests:* a binding criterion "failure mode X can no longer happen, verified by test T" needs T to actually TRIGGER X's failure branch (trap fires, failed-phase published, shutdown stub invoked) — exit-0 + a string assert on the guard's presence measures nothing.
2. *Producer/parser contracts tested parser-only:* a producer→parser key contract over SSH stdout (e.g. `EPS_LOG_MTIME=`) tested by injecting keys into hand-crafted fixtures leaves a producer-side quoting/typo bug silently un-fired with all tests green; demand a producer-side command-string assert next to the parser test.
3. *Read-window arithmetic on negative asserts:* check the asserted pattern can even fit in the bytes read ("no 'x'*1000 run in ≤64 bytes" is vacuous).

**D. Verification-matrix constructibility (#596, sparse worktrees; #2182, wrong-exit-path fixture):** walk each §5 verification claim and ask: can the fixture as designed ever PRODUCE an instance of the claimed case? Sub-case (#2182): a test plan names an EXISTING fixture whose shape drives a DIFFERENT exit path than the branch under test (committed local-side conflict → rc-2 rebase-abort, which re-applies the autostash, vs dirty-only divergence → rc-0 stranded-autostash path) — check which exit path the named fixture's shape actually reaches before crediting a fatal-path test. When the test's assertion fails LOUD on the wrong fixture (asserts exit 7, would get 2), it cannot false-certify → Substantive/Concern with the corrected fixture recipe named, not Must-Fix. (#596 claimed out-of-cone-committed-path coverage but every fixture path became in-cone before commit.) Also disk-size methodology: `du` on a long-lived checkout conflates tracked bytes with untracked litter — measure on a FRESH worktree (#596: claimed 14G/worktree, fresh truth 3.8G + 11G .venv). Concerns when the unconstructible case has independent real-repo evidence + a one-line fixture fix, and corrected numbers still clear the criterion.

**E. Channel-kill-vector hardening (#607):** enumerate ALL residual writers to the hazardous channel and verify each is per-line bounded + error-guarded (`tail -n K | cut -c1-M` is safe; bare `tail -n K` of a file that can hold one giant newline-free line is NOT — `-n` counts lines). Check whether the consumer side already truncates (then a giant line is a transient blip → Concern). When a plan truthifies a hardwired placeholder metric, grep ALL consumers for sentinel-keyed semantics (`== 10**9` skip branches, vacuously-true predicates) — placeholder→truthful that makes a predicate strictly more accurate is safe; a consumer using the placeholder as "unknown, skip" could newly fire.

**F. Checkpoint-per-phase at plan time (#399):** FAIL any plan whose §3 chains a multi-phase eval rig (Phase 1 vLLM gen → Phase 2 logprob-on-checkpoint → Phase 3 logprob-on-base) or multi-domain dispatcher without naming a between-phase persistence point. The implementation-layer rule lives in `.claude/rules/code-style.md` ("Checkpoint per phase"); catching it at planning saves a full round — #399 lost 11 rounds × 15 min of Phase 1 work to this gap.

**G. Concurrency-test + monitoring-criterion checks (#843):**
1. *Multiprocessing race tests inherit monkeypatched module state only under fork.* A barrier-synced N-process race test that relies on a pytest-monkeypatched module path (e.g. a registry dir → tmp_path) silently reverts to the REAL path under the `spawn` start method (children re-import). Demand: pin `fork` or pass the tmp dir via env/argv to workers.
2. *"One week post-land, zero X co-occurring with ephemeral state Y" success criteria are unobservable as stated* when Y (e.g. live-session count at marker time) is never durably recorded and no owner runs the check after the task completes at test-verdict. Ask for a durable-evidence restatement (e.g. duplicate pipeline markers on one issue's events.jsonl). Concern, not Must-Fix, when §1 acceptance criteria are all test-pinned.
3. *rc-0 suppressed-duplicate exits get counted as dispatch SUCCESS by callers that key on returncode* — conservative (backoff binds) but muddies "dispatched" markers/metrics; check the plan states this deliberately.
4. *Lockfile stale-takeover TOCTOU (double-winner) — check-fresh-then-rename steals a freshly re-created lock (#843 v2).* Any O_EXCL-lease protocol whose stale takeover is `if not fresh: os.rename(path, tomb); retry O_EXCL` has this hole: loser W_b passes the fresh-check on the STALE lease; winner W_a completes rename→unlink→O_EXCL-create (fresh lease) inside W_b's check→rename gap; W_b's rename then resolves the path AT CALL TIME to W_a's FRESH lease, destroys it, re-creates its own → TWO winners. "rename succeeds for exactly one process" is true only if the path is never re-created in between — the winner's re-create is the protocol itself. Barrier-synced N-worker takeover tests flake on exactly this. Fix: flock(LOCK_EX|LOCK_NB) a permanent per-issue `.lock` sidecar around the takeover critical section (re-check freshness under the lock, unlink, O_EXCL create; no tombstone); the JSON file stays the durable TTL lease (flock alone can't be the lease — it dies with the process). Must-Fix when the plan's prose asserts every-interleaving race-freedom.

**H. Document-global regex evidence for a row-local requirement = vacuous PASS (#869).** A new mechanical check of the form "plan mentioning X must contain evidence-pattern Y" is vacuous when Y is matched ANYWHERE in the document and Y-shaped text is house boilerplate: #869's `verify_plan.py` c12 required "multiplier arithmetic" + "batched commitment" for battery plans, but every §9 compute table contains `A × B` products and "vLLM batched" is house style — replaying the regexes on the motivating incident plan (#810 v1: battery costed at 1× grid) gave PASS (7 product lines, none draw-bearing; 14 batched lines). Demand: (a) the evidence pattern carries the requirement's distinguishing token (a draw-bearing factor) or is window-scoped near the trigger; (b) the calibration step replays the check on the MOTIVATING incident artifacts with a named false-PASS branch (incident plan PASSes → tighten before landing), not only a false-FAIL/over-broad branch. The 2-min verification: run the plan's own regexes via grep on the incident artifact it claims to catch. Must-Fix when the plan's success criteria assert the incident would be caught.

**I2. Zero-hit lint introduction self-FAILed by the plan's own insertion (#917).** A plan that introduces a new lint/grep with a "zero hits at introduction" acceptance criterion must replay the new pattern against its OWN diff sketches destined for scanned files: #917's E1 contract bullet quoted the incident literal `epm:experiment-implementation v1` into SKILL.md (a scanned surface), so the mandated edit itself violated §6.1's zero-hit grep and the lint's live-tree test. Incident QUOTES in scanned files are the classic self-hit. Must-Fix (edit spec contradicts acceptance spec), even though the fail direction is safe (loud FAIL, implementer rewords). 2-min check: grep the plan file itself with the plan's own regex. **Sibling (#2285): heading literal quoted into a count==1-pinned span.** A prose-correction plan whose replacement text backtick-quotes a section HEADING (`#### ...`) inside a span an EXISTING pin test asserts unique (`span.count(h4) == 1`) self-breaks that pin — and can also hijack an `.index(h4)`-anchored ordering pin (first occurrence moves to the quoted mention, dragging foreign text into the assert window). #2285 v2's Edits A+B took h4 count 1→3 and flipped the ordering assert. The decisive 5-min check: apply the plan's exact old→new blocks to the file in memory and replay EVERY assertion in the named pin file(s), not just the plan's new tests. Fix shape: drop the `#### ` prefix inside the quoted mention (positive-pin tokens rarely include it) or re-word to avoid the pinned literal. **Sibling (#2241 v3): replay claimed FORBIDDEN placements too.** A plan asserting "placing the insert one position earlier truncates lint region R / breaks live-tree test T" (used to justify a HARD placement constraint + a must-ask gate + a committed pin docstring) must have that counterfactual REPLAYED against the real predicate: #2241's claimed truncation was false — the earlier insertion slot coincided with the region's old `\n\n**` terminator position, so `region = text[idx:find("\n\n**")]` came out byte-identical (1,443 chars, all 3 tokens present) under both placements and T passes either way. Fact-checkers verify the region LINE NUMBERS (true) but not the counterfactual inference built on them. 10-line check: insert the block at the forbidden slot in memory, re-run the predicate's own extraction, assert the tokens. A false "mechanical proof" clause in §6 acceptance (a test green claimed to certify placement that passes under both placements) rides along — re-attribute to the pin that actually discriminates.

**I. Repro-card grep counts vs the plan's own line-wrapped diff sketch (#884).** When a doc-insertion plan's verification is a line-based `grep -c/-n '<phrase>'` with an exact expected count, replay the count against the plan's OWN diff sketches: a pinned phrase that WRAPS across lines in one sketch (e.g. "…long compute\nphases convention") silently drops that hit and the expected count is wrong. Fail-safe direction (spurious FAIL → implementer reflows), so Concern not Must-Fix — unless the miscounted grep is the ONLY pin on a load-bearing insertion. Same 2-min check as H: run the plan's own grep on its own sketch text. Also verify grep-pin acceptance strings return 0 hits PRE-change (tautology check — #884's did: 0 pre-existing `setsid nohup` in both targets).

**J. Re-attach protocols keyed on bare pid liveness (#884).** Any successor/re-attach rule whose liveness check is a bare `ps -p <pid>` has a pid-recycle false-ALIVE hole: a recycled pid reads alive and the successor tails a dead phase's log forever. Demand args-verified liveness (`ps -p <pid> -o args=` matched against the distinctive invocation, `pgrep -f` fallback) — usually a Concern (wording tweak), Must-Fix only if the protocol has no invocation string to match.

**K. Hook/guard plans: script-level pytest alone = false PASS on wiring (#965).** A PreToolUse/PostToolUse hook plan whose entire test suite subprocess-drives the SCRIPT is green even when the harness never invokes the hook (settings.json object added to the wrong event array, typo'd matcher, wrong script path, missing +x). `jq . settings.json` parses all of those. Demand a settings-STRUCTURE pytest: load settings.json, assert the matcher group exists under the right event with each intended tool name, and the command path resolves to an existing executable script. Cheap, mechanizable; the failure mode (hook silently absent) is unobservable post-merge because the symptom is the ABSENCE of blocks. Must-Fix when no live-fire check is merge-blocking.

**L. Field-value conventions: audit the WILD population of the field before blessing "distinctive value = trusted class" prose (#966).** When a plan establishes a convention where a positive field value (e.g. a distinctive `--by`) is documented as a trustworthy signal for some class (external/advisory), grep the field's actual in-repo emitter population: non-convention distinctive values usually already exist (per-issue dispatch scripts each post `"by": "<script-name>"`; pod-sentinel forwards them) and generic "a distinctive value means X" prose sweeps them into the blessed class. Demand the prose scope to the enumerated convention list. Concern (not Must-Fix) when the misread direction is the deliberately-safe one (over-triage / fail-open).

**M. Sweep-output tabulation completeness — replay the plan's own grep and diff hits against the table rows (#2156 r2).** A prose-correction plan whose completeness evidence is "authoritative grep G → exactly these N surfaces (listed exhaustively)" can have the RIGHT pattern and a WRONG table: the planner folds same-FILE hits under one row (stage0.py:581 folded under the 210-218 row, ~370 lines away, uncorrected) — and the missed block can assert the stale claim in wrapped wording (`batch\norder` across a comment line break) that the line-based grep never matches, so the one in-block token that DOES hit (a cross-reference name) is the only handle. 2-min check: run the plan's grep verbatim, then map EVERY hit to a table row (file+line range) or an enumerated unrelated class; any unmapped hit → read its surrounding block for a wrapped assertion. Also check the post-impl completeness criterion for an "outside the corrected files" exemption — an in-corrected-file uncorrected hit ships legally under that wording. Must-Fix when the plan's acceptance criterion claims "no other prose asserts it".

**N. Guard justified by an agent's PROJECTED write rate — read the agent's REALIZED rate from its own logs first (#2189).** A plan whose headline durability claim is "budget-guard the machine appender, it consumed the headroom and will again" priced regrowth at mean-entry-size × nightly cadence — but the appender's own logs showed `promoted=0` in every retained nightly pass (29/29), while `git log` on the guarded file showed the demonstrated growth channel was HUMAN sessions (2 forced emergency trims in 3 days), which the guard does not bind. Rule-A protection-illusion instance: the guard would not have fired in either motivating incident. 2-min check: when the growth/failure agent has a log dir or committed history, grep its realized event rate (`grep -c 'promoted=[1-9]' logs/...`) and diff the plan's causal attribution against `git log -- <guarded file>`. The guard usually still lands (cheap backstop for the worst-severity unattended channel) — the REVISE is the misattributed rationale + durability horizon + missing successor lever for the real channel.

**O. Acceptance criteria anchored to LIVE mutable state — re-probe each named exemplar at review time (#2095).** A janitor/sweep plan whose acceptance keys a new safety gate's only end-to-end check on a specific live filesystem exemplar ("the #1887 dir ⇒ cross-issue-kept") inherits staleness from the audit that named it: #2095's exemplar dir was manually cleaned between the audit (2026-08-05) and the plan (2026-08-11) — the plan even CONSUMED the clarify note recording the cleanup (63→41 entries) without re-keying §6. The criterion then passes vacuously and the new gate's wiring is verified only at whatever level the unit test targets. 2-min check: `ls` every named live-path exemplar in §6; pair the fix with an end-to-end test through the public entrypoint so acceptance doesn't depend on mutable state at all. Must-Fix when the stale exemplar is the only end-to-end check of a NEW deletion-adjacent gate; also fold in any verify_plan WARN about missing dry-run/apply-thread tests on the new path — the two combine into one hole (mis-threaded per-candidate flag ⇒ wrong gate set, all tests green, acceptance vacuous).

**P. Janitor/guard tier extended to a NEW filesystem or root (#2096).** Two 2-min checks: (a) if any reap arm's eligibility gate is atime-dependent (repo `last_accessed`, exclusive-blob atime keep-guards), verify the new mount's options — `findmnt -no OPTIONS <mount>` — `noatime` silently breaks "unused ≥ N days" recency gates (files under live readers become eligible), `relatime` carries home-disk semantics; (b) a pressure-threshold-gated tier extension is DORMANT at current usage (e.g. 85% gate vs 30% used) — the fix is coverage-under-pressure, not immediate reclamation; check the plan says so rather than implying the named cache gets reaped now. Also grep sidecar-row kinds + ack-sentinel filename prefixes for non-test consumers before crediting an "additive field is safe" assumption — often zero consumers exist and the assumption is stronger than stated.

**P. LESSONS.md row edits are byte-capped — replay the per-row cap on the sketched row (#2133 r1, sibling of I2).** Any plan extending a `.claude/rules/LESSONS.md` index row must byte-count the post-edit row against `workflow_lint._LESSONS_ROW_MAX_BYTES` (280 B, strictly-greater FAILs, em-dash/§ are multibyte; grandfather dict is gotchas-only and CLOSED to new entries — workflow_lint.py ~13861-13906). #2133 v2 specified a +31 B trigger insertion on a 267 B row → 298 B, deterministically self-FAILing its own "workflow_lint NEW violations == ∅" acceptance criterion while its risk table said "very low" (it considered row GRAMMAR only). 2-min check: `grep '^- <rule>.md' LESSONS.md | sed '<planned insertion>' | wc -c` vs 280(+1 newline). Fix shape: net-≤(280−current) insertion or a compensating trim of an existing trigger token, with the post-edit byte count stated in the plan.

**Q. Escalation-pass plans: verify the push channel's SURFACING latency against the outage class it watches (#2140).** The watcher's `_telegram_push` (autonomous_session_watch.py:34547/:34555) is NOT an immediate send — it enqueues into `~/my-goat/scripts/notif_enqueue.sh`, the 3×/day my-goat digest (worst-case ~8h to the phone; deliberate since 2026-06-12 for observability-grade gate pushes). A new escalate-only pass for a TIME-CRITICAL fleet-blocking condition (daemon outage disabling all autonomous dispatch, 3h17m incident) that counts `_telegram_push` calls in its acceptance criteria can be strictly SLOWER than the manual detection it replaces — the incident replay is the test (enqueue 21:33Z vs human 22:48Z; digest could land after both). The immediate path exists and is the sanctioned urgent carve-out (`telegram_push.sh` directly — notif_enqueue.sh's own header: "Urgent paths ... still call telegram_push.sh directly"). 2-min check: read `_TELEGRAM_PUSH_SCRIPT_DEFAULT` + the enqueue script header; demand the plan state per-event channel (open/recovery immediate, realerts digest is a sane split) + the surfacing-latency arithmetic. Must-Fix when the plan's own Requirement says "loud on the same tick" and every named channel is digest-batched or dies with the watched component.
