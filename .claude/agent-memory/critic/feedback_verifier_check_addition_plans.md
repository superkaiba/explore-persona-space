Two asymmetries to check in any plan adding a mechanical check to `scripts/verify_plan.py` (#879, c13):

1. **FAIL semantics are a bounded mechanical bounce, not an auto-reject and not a mere brief note.** Per `adversarial-planner/SKILL.md` Phase 1.5.0: FAIL → orchestrator bounces the plan for v{K+1}, capped at 2 consecutive mechanical bounces, then PASS-with-override + auto workflow-fix candidate. So a false-FAIL costs 1–2 planner rounds, bounded. Weigh a plan's false-FAIL risk against THAT cost — reject both the over-claim "FAIL just feeds the critic brief" and the over-fear "FAIL hard-blocks forever."

2. **Under-trigger direction depends on WHICH regex under-triggers.** A documented "accepted under-triggers fail safe" list is only true for the TRIGGER/gate regex (missed gate → SKIP → critics still review). An under-trigger of an ESCAPE regex (scope qualifier, exclusion vocab, N/A phrase variant) fails UNSAFE — the gate is detected but the legitimizing qualifier is missed → false-FAIL (e.g. a hard-wrapped line splitting `(n_draws ≥ 50)` from the `p ≤ 0.05` gate text). Demand the plan's under-trigger list distinguish the two directions, or that a corpus-sweep + kill-criterion guard exists for the fail-unsafe side.

3. **Corpus-replay audit gates: a pooled "genuine OR N/A-escapable" numerator can pass a miscalibrated check.** An escapable-via-`N/A — no <claim>` WARN row is by definition an incidental-vocabulary false trigger; pooling it with "genuine" in the ≥X% success numerator lets a mostly-nuisance check ship. Ask for the audit table to classify rows into named categories (genuine | escapable-incidental | escapable-doc-target | FP) with genuine reported separately. Advisory (not REVISE) when WARN-only AND the measured genuine-alone rate already clears the threshold (#932: 60-70% genuine vs 40% pooled gate).

4. **Two-sided calibration sweeps (#937, c16):** (a) a corpus sweep that holds `--kind` constant (e.g. `experiment` for every file) measures regex separability and UPPER-BOUNDS the production fire set (the kind gate only removes fires) — conservative w.r.t. a fire-count kill bound, so real-kind resolution is NOT needed; just have the report say so. (b) A sweep that only prints per-file STATUS measures the trigger side but leaves satisfaction false-PASSes invisible — a fired file printing PASS may have matched a broad satisfier (e.g. a retention-verb regex hitting "committed cells stay the parity target") rather than a genuine distinguishing sentence. Ask for the matched satisfier span (which of S1/S2/S3 + the matched text) to be recorded for every non-SKIP PASS file. Concern-level for WARN-only checks (false-PASS = status quo preserved), REVISE-level for FAIL checks.

5. **In-sample regex calibration (tuned on the same corpus as the success gate) is ACCEPTABLE for WARN-only advisory checks** — future plans come from the same house-style generative process, WARN never blocks, and N/A escapes + critic-brief forwarding bound the nuisance cost. It would NOT be acceptable for a FAIL-level check (demand a held-out split or prospective monitoring there). Say the split explicitly in the review.

6. **Check-LOOSENING (exemption) plans — the mirror direction (#959):** (a) "strictly loosening / no retro-FAIL" is NOT proven by "we scan fewer lines" alone — verify every DEPENDENT check's EMPTY-INPUT verdict (e.g. #959: `check_repro_artifact_urls_exist` returns PASS on an empty gather, :4390 — had it FAILed on empty, a body whose only same-repo URLs were blockquoted would newly FAIL). Independently read the consumer of any narrowed gather. (b) Prefer a SPAN-scoped blanket exemption (footer-only `>`-strip) over a body-wide or stateful row-scoped walker when the scanned span structurally cannot contain the protected class (verify the span-resolver anchors, e.g. `_v4_footer_start_line`); a body-wide strip would exempt Results figure-caption blockquotes carrying real pinned links. (c) An exemption whose miss direction is "stays scanned" (lazy-continuation lines) fails SAFE toward the pre-fix FAIL — acceptable; an exemption whose miss direction silently widens the hole is the one to REVISE.

7. **Predicate-NARROWING plans (library gates like `followup_retro_close_evidence`, #961): the clean proof pattern is "retain the old check as an outer conjunct".** New evidence = old-check AND new-gate ⇒ new match set is a provable subset — no corpus argument needed for the no-loosening claim (the replay then just confirms). Corollaries: (a) any imprecision in a SUPPLEMENT regex scoped inside the retained conjunct (e.g. `complete` matching "completely") can only RETAIN an old match, never create one — fail-safe by construction; (b) a veto/exclusion regex over-triggering only MISSES (safe when the predicate's documented bias is missed-X-is-safe); (c) demand old-vs-new full-corpus replay with named flip sets + durable corpus pins GUARDED against future legitimate state changes (e.g. `if label not in _run_labels(...)` so the pin doesn't outlaw a later genuine close). Dropping the retained conjunct converts the supplement into a loosening — treat that as a must-ask.

8. **Negated-satisfier false-PASS (#974, c19):** plans often guard the TRIGGER regex against negated mentions (`(?<!\bno )held-out`) but leave PASS-EVIDENCE/satisfier tokens (`iid`, `LOFO`, `transfer arm`) matching ANY mention — including "the sample is NOT iid" or quoted rule-template text — a silent satisfaction false-PASS. Also watch satisfiers colliding with project headline vocabulary (`transfer arm` in a trait-transfer project). Concern-level when WARN-only (false-PASS = status quo + lens backstop); pair with item 4(b)'s matched-satisfier-span recording so the sweep makes PASS-via-satisfier rows adjudicable.

9. **Corrected-in-place incidents: recover the verbatim offender text from git history before accepting a synthetic must-warn fixture (#1016).** When the motivating incident body was corrected in place (clean-result r1 → r2), the plan's "synthetic incident-shaped fixture" can silently diverge from the real offender's shape. The 2-min resolution: `git log --all -- 'tasks/*/N/body.md'` → `git show <set-body sha>:tasks/<status>/N/body.md | grep -oE '.{80}<token>.{40}'` and confirm the real line matches the extraction shape the check anchors on (#1016: r1 line WAS shape A paren-after-link, resolving the would-be #869 Must-Fix to a concern "pin the verbatim r1 text as the fixture"). If the recovered shape does NOT match the plan's anchored shapes, that IS the #869 Must-Fix (incident would not be caught).

10. **Prose-window numeric checks (#1107, check 33):** the v4 three-beat grammar has NO mechanical delimiter between figure k−1's beat-3 interpretation and figure k's beat-1 prose, so a per-figure prose window bounded at "previous figure's caption end" necessarily bleeds interpretation prose (derived bolded values, e.g. #825's 0.0338 = 0.057×0.588, in no sidecar) into the next figure's window in multi-figure H3s. Do NOT demand a stop-at-interpretation boundary — it isn't mechanizable; WARN severity + per-figure opt-out + corpus-calibration kill path is the right containment. DO demand the incident replay run against the ERA-CORRECT artifact (`git show <r1-commit>:<sidecar>`) — the corrected body's current sidecar passes by construction, so a HEAD-only replay proves nothing.

11. **Kill-criterion WARN-rate denominators over the full MENTION corpus can be vacuous (#1114, c29):** when a sweep corpus is "files mentioning token X" (~112) but only a small subset can ever TRIGGER (value-bearing declarations, ~9-10), a ">~15% of scanned files" kill disjunct is unreachable by arithmetic — max possible WARN rate ≈ trigger-set/corpus. Check the plan's own histogram: if trigger-capable files / corpus < the threshold, the rate disjunct is dead and only the companion (majority-FP) disjunct binds. Concern-level for WARN-only (the FP disjunct still gates); ask for the denominator restated over the TRIGGERED set. Also verify the plan tests EVERY trigger-regex FORM — a second trigger form (e.g. a `spec.extra`/assignment regex alongside the flag regex) with zero fixtures ships green with a typo.

12. **Review-AGENT lens/sub-check additions (interpretation-critic / code-reviewer prose recipes, #1390) have different FP economics than lint checks:** the check is applied by a judgment-capable LLM inside a capped revise loop with prose carve-outs, so a moderate false-fire rate is recoverable (one analyzer round; the "FP" often just forces a declaration the body should carry anyway) — do NOT demand held-out calibration as if it were a FAIL-level lint. When the plan omits a base-rate corpus sweep, RUN IT YOURSELF (seconds: #1390's recipe over 2,209 committed sidecars → 3/342 multi-series files fired, one the motivating incident, the other two same-class catches) instead of REVISE-ing for its absence; also replay the verbatim fenced recipe over the live corpus to surface crash shapes (non-dict `points` rows, heterogeneous-type `sorted()` TypeErrors in the `<none>` bucket) — fail-loud + agent-recoverable ⇒ Concern with a concrete 2-line hardening, not Must-Fix.

13. **workflow_lint check-addition plans must pin the no-flags BUNDLING with a committed test (#1385):** the house pattern `test_<check>_bundled_in_no_flags` (source-pin shape at tests/test_workflow_lint.py:2123/:2412; in-process drifted-tree shape at :5099) exists at 10+ sites, but the plan's stated template (`check_lessons_index`) lacks one — so a plan copying that template omits it silently. Without the pin, a future refactor of the dispatch/negation-tuple lines silently unbundles the check ("present but never runs" — the exact silent-disablement class such lint tasks exist to close), with no test failing; a one-time "revert an offender → no-flags run FAILs" spot-check verifies landing, not durability. Lens item 14 shape (#913 grep-only precedent). Must-Fix: one small test in the same diff.

14. **verify_task_body CHECKS-registration pin (#1520):** a new-check plan whose tests are ALL direct-call (`check_x(body)`) leaves the CHECKS-list append unpinned — a forgotten registration ships green (the standing `len(CHECKS) == N` count pins at tests/test_verify_task_body.py:5784/:11298 mask ONLY the entry-added direction: they fail when the entry IS added, stay green when it's forgotten). House pattern: one membership assert per check (`test_check45_registered`, :14990). Concern-level (not Must-Fix) when the plan explicitly specifies the CHECKS entry in Files-touched AND the count pins force test edits on the added path — the omission path needs implementer+reviewer to both drop a specified deliverable; demand the one-line `test_checkNN_registered` in the concerns. Also note two concurrent check-addition siblings will BOTH edit the count pins — same renumber-at-rebase mitigation as the check-number race.

15. **Count-equality source invariants (n_emits == n_sites over a script, #2013):** verify three things against the CURRENT artifact, not the plan's assertion: (a) the exact standalone count today (`grep -n '^\s*<token>\s*$'`) equals the plan's site map — comment lines mentioning the token strip to longer strings and are correctly excluded by a `.strip() ==` equality, so near-miss occurrences are not false sites; (b) the emit-side count can't be satisfied by the definition/assignment line (a bare `NAME=` carries no `$`-prefixed form); (c) the future-protection claim ("a 7th site can't ship without the warning") holds ONLY for standalone-line sites — a compound form (`cmd || exit 2`) escapes the site count AND ships unprotected while the test stays green. (c) is disclosure-level (Concern), not Must-Fix, when acceptance criteria bind only the current sites; #2013's invariant verified exactly (6 standalone exit-2 lines = 6 mapped sites, 4 comment mentions excluded).

16. **Two-exact-lookbehind negation guards under-cover natural negation (#2191, verify_report committed-under check):** a FAIL-level claim-trigger regex guarded only by `(?<!not )(?<!never )` still fires on "nothing is committed under `X`", "isn't/wasn't in git under `X`", "rather than / instead of in git under `X`", "never landed in git under `X`" (intervening word defeats the immediate lookbehind), "no longer committed under `X`". Worst case: the check's own FAIL message teaches authors to reword false git-home claims into HF-home sentences that naturally keep the git path for contrast — manufacturing the negated-sentence family that then false-FAILs. Demand a preceding-window negation scan (~30-40 chars, token set incl. not|n't|never|no longer|rather than|instead of|nothing) for FAIL-level triggers; two exact lookbehinds are only acceptable at WARN level. Under-fire from an over-broad window is fail-safe.

18. **Refusal-leg RELAXATIONS in fail-closed gate machinery (step9c compare R-G′, #2019): the clean proof is strip-reachability enumeration under the new conjunct.** When a plan relaxes an eligibility refusal (a leg that today maps to exit-2/indeterminate) with an ASYMMETRIC verdict rule (green→blocking rc, red→refuse; strip never reachable on the new path), verify against the ACTUAL verdict loop, not the prose: (a) walk every arrangement of the eligibility conjuncts (kill-switch flag, residual dirt, creation-failure branch, memo interactions, mid-loop dirt transitions) and confirm strip (`rc 0`) is reachable ONLY on pre-existing status-quo paths, each pinned unchanged; (b) confirm loop-invariant vs per-file predicates (a memo set only on a branch the new arming can't reach is inert — say so); (c) the false-positive-direction population (spurious GREEN→NEW / spurious RED→refuse from a non-superset tree) is acceptable when both new verdicts BLOCK and the JSON carries a distinguishing oracle tag for the orchestrator — demand the population be characterized (which content class triggers it), not that it be empty. #2019: the R-G′ floor-scratch relaxation passed all of (a)-(c); the one plan defect found was a stale measurement count (3 vs ≥6 benign token hits), direction-preserving.

17b. **Structural (non-regex) pairing checks: partition the skip set — "both-unstamped" (grandfathered, safe skip) vs "mixed stamped/unstamped" (defect-shaped, silently pooled into the skip) (#2016).** A per-call id stamp (PNG `RenderId` chunk ↔ sidecar `render_id`) makes pairing exactly checkable, but a skip condition written as "no id in sidecar OR no chunk in PNG" pools the transition-window defect shape (fresh stamped sidecar + stale unstamped PNG — exactly the founding #1768 mechanism during rollout) with the legitimate grandfathered corpus. Concern-level (transition-only; steady state catches all routes incl. git-race pairings since ids are per-call). Empirical facts worth reusing: `PIL.Image.open(bytes).info` populates tEXt chunks with `im.tile` still pending (no pixel decode — verified on 3 committed blobs); matplotlib's `metadata={"Software":...}` chunk is DROPPED by paper_plots' PIL re-tag re-save (only pnginfo chunks survive); artist-derived sidecars can disagree with their own PNG within ONE call only via invisible/clipped artists (sidecar⊃PNG) or the per-axes try/except skip (sidecar⊂PNG).

17. **Coverage checks against a GROWING external artifact set need promote/generation mode split (#2191, code-sha-cards):** a report-gate FAIL of the form "every artifact-derived value must be cited in the report" compares a FROZEN document against a set that GROWS after generation (follow-up rounds / inline analyses write new reproducibility cards under `eval_results/issue_<N>/`), so a promote-time re-run can FAIL a report that was well-formed when gated. House precedent `_check_pin_blob_identity` (scripts/verify_report.py:626-628): generation strict, promote lenient. Pin-anchored checks (resolvable pin + missing path) are time-stable and need NO mode split — the split is only for checks whose reference set is external mutable state. or exemptions/loosenings, narrowing a task_workflow/library evidence predicate, or adding a mechanical lens/sub-check recipe to a review-agent spec (item 12). The #633 lesson (calibrate on the REAL offender file, not only synthetic fixtures) remains the companion test-enumeration bar; #869's named-false-PASS-branch demand is satisfied by a plan that replays on the motivating incident and HONESTLY reports the incident PASSes (delegating to a lens layer), as #932 does.
