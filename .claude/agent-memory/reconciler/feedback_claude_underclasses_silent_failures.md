When adjudicating code-reviewer disagreements, watch for cases where Claude flagged a real correctness bug but classed the overall verdict as CONCERNS (PASS-class) because the fix is "small" or "one patch." Codex twin tends to correctly read these as FAIL.

**Why:** The CLAUDE.md "Never silently fail" rule treats silent correctness violations as FAIL-class regardless of patch size. A one-line fix to a bug that silently corrupts the primary hypothesis test is still FAIL, not CONCERNS. Claude reviewer's calibration appears to weight "ease of fix" too heavily; Codex weights "what the bug DOES" more correctly.

**Observed in:**
- #375 round 1 (2026-05-21). Claude CONCERNS, Codex FAIL on a neutral-pool slicing bug that silently mispartitioned bootstrap arms after any ZLT drop. The bug invalidated the primary hypothesis test with no error raised. Claude flagged it (good) but said "revise-then-launch" (CONCERNS); Codex said FAIL. Codex was right per project rules.
- #377 v6 round 1 (2026-05-24). Claude PASS with "needs user eyeball — downstream eval slicer should tolerate 185-200 rows", Codex FAIL on a post-filter floor violation in `post_gen_sanity_checks`. The function's own docstring promised "below the floor raises RuntimeError" for post-filter shrinkage, but the implementation only checked pre-filter. Claude saw the hole (his "200→185 worst case" note literally describes the bug) and chose to push enforcement to the downstream consumer. Codex correctly read this as a documented-contract violation. Reconciler verdict: FAIL — contract-laundering to a downstream tolerance is exactly the silent-failure pattern CLAUDE.md forbids.
- #389 round 1 (2026-05-26). Claude CONCERNS ("REVISE-THEN-MERGE — no blocking bugs"), Codex FAIL on a Phase-0 base-preference hard gate that silently passes with empty `rates` dict when 100% of judge calls return parse errors (`n = cell["n"] - cell["by_label"]["error"] == 0` → `if n > 0:` skips population → `rates.get(pred, 0.0)` returns 0.0 → no violations → gate logs "PASSED"). The gate's job is to halt training if the base model already anchors on a predicate; a zero-signal case proceeds as if signal is clean. Claude missed it entirely (not even flagged as ISSUE). Additionally, Claude marked Must-Fix #1 as "✓ IMPLEMENTED" based on filter existence; the implementation actually compares only train-user-Q to probe text, but plan §4.3 explicitly required (train Q+A) × (probe + expected response) — partial contract fulfillment. Reconciler verdict: FAIL. Pattern reinforces: when Codex finds a hard-gate-load-bearing silent failure Claude didn't flag at all, FAIL is almost always the right call.
- #397 round 3 (2026-05-27). Claude CONCERNS (PASS-with-followup), Codex FAIL on the dispatcher's smoke-gate path. Three independent blockers: (1) `_resolve_smoke_data_path` ignores `--pool-dir`; smoke can't run end-to-end as plan §5.8 advertises (docstring even admits pool-prep is "out of scope"). (2) `_smoke_questions` returns 5 questions vs production's 480 contexts (24 personas × 20 questions); docstring explicitly tunes the count to fit under the PASS band — the calibration is upside-down (smoke chosen to fit the gate, not gate calibrated to production). (3) `_smoke_source_substring_rate` returns `None` on missing `metrics_final.json`; `build_smoke_marker` only downgrades PASS→WARN when `source_rate == 0.0`, so missing-file silently certifies PASS — defeating the live M1 check from plan §5.7. Claude found (3), classed as non-blocking ISSUE; missed (1) and (2) entirely. Reconciler FAIL. Pattern reinforces: docstrings that ADMIT the silent-failure escape hatch ("out of scope for this implementer", "verdict can still be inferred from timing alone", "tuned so smoke stays under the PASS band") are a strong signal Codex is right and Claude is misweighting "fix size."
- #407 round 1 (2026-05-27). Claude CONCERNS (Critical #1 on hardcoded fictional A/B/C rubrics on obscure-real → silent zero), Codex FAIL with 4 Criticals. Three Codex Criticals that Claude missed entirely: (a) C-family uses permissive #389 rubric on BOTH regimes instead of `COUNTER_ASSOCIATION_STRICT_RUBRIC v1_strict` — plan §4.6 explicitly calls strict-rubric "load-bearing". Claude saw the inline comment `# permissive — STRICT variant used in re-judge step`, accepted it at face value, and didn't grep for the (nonexistent) re-judge step. (b) `epm:fact-pick` → `fact_pick.json` resume contract is unimplemented anywhere outside the driver; plan §4.2.2 assigned this to "the orchestrator" but no handler was added to `/issue` skill or `markers.md`; the pipeline sits at the gate forever after user picks. Claude verified the in-driver `fact_pick.json` consumption but didn't ask "who writes this file?". (c) Approved launch order at plan §10.1 sequences `fp-calibration` before `fact-candidates`, but `fp-calibration` iterates both regimes and obscure-real requires `fact_pick.json`; first launch crashes mid-phase-2. Claude's plan-adherence table marked §10.1 ✓ without simulating the launch. Reconciler FAIL. **New patterns this case adds:** (1) **Inline-comment trust** — Claude treats `# todo: this is permissive` / `# fallback for X` / `# placeholder` style comments as evidence of intentional design rather than as flags for a missing implementation. Grep the comment's claim against the codebase. (2) **Plan-cross-reference simulation** — when plan adherence is marked ✓ for a launch order or a multi-phase sequence, mentally run the first 2 phases against the actual driver and verify the entry-point preconditions are met. Claude's plan-adherence walks tend to be one-line-per-row "exists in code" checks; Codex tends to simulate the sequence. (3) **Orchestrator-vs-driver contract gaps** — when a plan says "the orchestrator writes X" / "the orchestrator parses Y", verify the orchestrator path exists. Plans that hand off cross-process state to "the orchestrator" without specifying which file/skill owns it are a structural smell.

**How to apply:** When the Claude reviewer's PASS-class verdict (CONCERNS or "needs user eyeball" PASS) and Codex's FAIL-class verdict both flag the SAME critical, default to FAIL if the critical describes:
- A bug that produces wrong results without raising (silent failure)
- A correctness violation in the primary hypothesis test path
- A miswiring that crosses experimental arms or labels
- A function's documented contract diverging from its implementation, especially when Claude proposes "downstream consumer should tolerate it" (contract-laundering)

The classification depends on what the bug DOES at runtime, not how many lines the fix requires. Cross-reviewer agreement on a silent-failure critical is a strong FAIL signal even if Claude framed the verdict as CONCERNS.

Compounding rule: when Codex additionally identifies independent criticals Claude missed (here: C-2 free_vllm not releasing GPU memory, C-3 `--phase all` skipping required pilot), multiple-blocker compounding cleanly tips the verdict to FAIL.
