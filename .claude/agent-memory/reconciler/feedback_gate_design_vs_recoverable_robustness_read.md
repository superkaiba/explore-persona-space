**Rule:** when Codex demands the plan REGISTER a discriminating robustness read (split-half / cross-fit / shared-error control / extra verdict cell), do NOT auto-apply the #547-family "data persistence ≠ design correctness → REVISE" pattern. That pattern is for defectively SPECIFIED pre-registered GATES. Verify three things before siding with REVISE:
1. Do the per-probe inputs persist in committed artifacts independent of the plan's scripts? (Open one file; don't trust prose. If the corrective read is conditioned on GENERATED TEXT or any run-time-only capture, check the producer's persisted payload keys — `git show` the entry-builder/manifest.)
2. Does §12 / allowed-deviations / another plan section permit adding the read without amendment? (Check for a registered-handling-elsewhere escape BEFORE crediting "unreachable/unrecoverable"; conversely the barred-amendment tell — §13 must-ask forbidding the fix — pushes REVISE.)
3. Is the contested statistic an automated gate, or an interpretation-time claim under the analyzer→interp-critic loop?

All three recoverable → APPROVE with BINDING standing recs (name the read + headline scope phrasing; route via free-analysis auto-run if omitted). REVISE tells: a rule wrongly FIRES in the AFFIRMATIVE direction (failure-direction lattice gaps are not misfires); amendment barred by the plan's own text; run-time-only capture dropped; a registered NULL branch carrying the affirmative claim with no positive control in the direction the null read depends on; self-certifying acceptance (instrument's own hit set defines completeness). **Registered-handling-elsewhere saves a PLAN, never CODE that drops it** — when the pre-data-code property is itself registered, persistence cannot rescue a code-stage divergence (#600 code). Judge each lens on its own question; never REVISE-by-contagion when another lens already binds the fix.
