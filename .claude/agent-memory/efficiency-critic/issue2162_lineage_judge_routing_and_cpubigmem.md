Two patterns to check on any rerun/child of the #2162 minimal-pair context-vector pipeline (e.g. #2329):

1. **"ALL production waves Batch API" is falsified by the reused dispatcher.** `eval/judge_dispatch.py` (~line 1629) routes by wave SIZE: waves < 4,000 items run the OTPM probe, get an effective threshold of 10,000, and route SYNC; only waves ≥ 4,000 route Batch. Parent #2162's realized routing (deviation 2, `eval_results/issue_2162/judge/routing_evidence.json`) was MIXED — 171 sync dispatches (per-rubric behavior waves 30–5,760 items) vs 9 Batch. **Why:** a plan re-claiming "ALL Batch" on the same dispatcher re-records the same deviation; the delta is ~2× standard pricing on sub-4k waves (telemetry only — no GPU idles since the pod is terminated before judging, and sync is faster). **How to apply:** non-blocking note, not a REVISE — suggest either forcing batch routing at the call site or restating the plan claim as "Batch above the dispatcher's size threshold". **Declared-SYNC mirror (#2389 r2→r3, reconciler-upheld):** the inverse claim ("this wave is SYNC") is a REVISE when unbound — the same count-routing batches any ≥ 2×`threshold_base` (default 2,000) wave, and under a work-conserving design the flip is SILENT (the Batch-SLA verdict arrives after the cells are done ⇒ the gated item is forfeited, its judge calls + gate GPU-h wasted). The canonical fix, all seams verified real: `threshold_base=FORCE_SYNC_THRESHOLD_BASE` (`scripts/issue2329_judge.py` L93 `= 10**9`, call-site pattern L862) or `force_path="sync"` (`api_dispatch.py` ~L610-611 returns the "forced" route before any counting), PLUS an assert on the realized route read from the persisted `save_raw["routing"]` record (`eval/batch_judge.py` ~L946 writes it; `eval/judge_pilot.py` ~L334 is the read-back precedent). Trace any declared execution property to a NAMED mechanism in code, never to the plan's assertion — my r2 PASS missed this by verifying the fix sentence, not the route binding.

2. **cpu-bigmem bookings need a named fallback venue.** Parent #2162's two `cpu-bigmem` provisions both wedged RUNNING-with-no-port (#770/#1667 class) and a sweep across 5 datacenters found no capacity; P7 realized on a 1× H100 `eval` pod with a big host (recorded deviation). **How to apply:** a child plan booking `cpu-bigmem` without naming that fallback (or a DC sweep order) risks a P7 dispatch stall — flag as a non-blocking availability concern (not sizing).
