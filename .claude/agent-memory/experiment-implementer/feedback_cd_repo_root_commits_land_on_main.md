name: cd-prefix to repo root commits land on main, not the worktree
description: Bash commands prefixed `cd <repo-root> && git commit` commit in the repo-root tree (on main), NOT the issue-N worktree — even when the worktree is the assigned cwd
type: feedback
---

When the brief assigns a worktree (`.claude/worktrees/issue-<N>`, branch `issue-<N>`) and you run `Bash` with `cd /home/thomasjiralerspong/explore-persona-space && git commit ...`, the commit lands in the REPO-ROOT working tree — which is pinned to `main` — NOT the worktree branch. Worse, the repo's `task.py` auto-push + concurrent committers can push those commits to `origin/main` before you notice.

**Why:** the harness resets cwd between Bash calls, so agents habitually prefix `cd <repo-root>`. But git operates on the cwd's working tree; `<repo-root>` is a SEPARATE worktree from `.claude/worktrees/issue-<N>`, and it's on `main`. The CLAUDE.md "NEVER git checkout in repo root" rule is about not switching the root's branch; this is the dual trap — committing in the root commits to whatever branch the root holds (main).

**How to apply:** for any git mutation (commit, cherry-pick, branch ops) when working a worktree task, run the `Bash` command with NO `cd` prefix (the harness cwd is already the worktree) OR `cd` explicitly into the worktree path. Verify with `git rev-parse --abbrev-ref HEAD` (must print `issue-<N>`, not `main`) BEFORE the first commit, and again after. Non-git reads/edits (Read/Edit/Write use absolute paths; ruff/python smokes) are unaffected — the cd-prefix only corrupts git's working-tree target.

**Recovery if it already happened (incident #642 v5, 2026-06-16):** the 5 code commits landed on main + got pushed to origin/main. Fix = cherry-pick them onto the worktree branch from INSIDE the worktree (`git cherry-pick <sha>...`), confirm `git diff --stat <branch-tip-before>` shows the files. Leave the duplicate on main untouched — reverting pushed commits on the shared main is more dangerous than the harmless duplicate (the eventual worktree→main merge is a content no-op). Note the duplicate in the report's (d) for the orchestrator.

**Recovery refinement — the revert-is-safe sub-case (incident #658 round 1 / `persona-vectors-style-rb`, 2026-06-29):** when the mishap is FRESH (within hours, before other sessions reuse the mishap commits) AND PURELY ADDITIVE (the cwd-mishap commits add NEW files only, no concurrent task on main imports them, no `main` consumer broke between mishap and detection), `git revert` of the cwd-mishap commits on main IS safe and produces a cleaner Step 10d merge (execute it via a scratch worktree — `git worktree add --detach /tmp/<name> origin/main && git -C /tmp/<name> revert --no-edit <sha>... && git -C /tmp/<name> push origin HEAD:main` — a repo-root `git revert` is hook-blocked, #1234) — the issue-658 cherry-picked equivalents simply re-add what the reverts removed, so the final post-merge state of main is identical to either path. The orchestrator at #658 reverted 5 commits (4 issue-658-titled scripts + the bundle generator) and pushed cleanly; the issue-658 branch carried its 5 cherry-picked-equivalent commits untouched, and the Step 10d auto-merge then replays them on top of the revert commits with no content diff. **Use this path when (a) the mishap is recent and (b) the touched files are new/additive; use the "leave it on main" path when (c) the originals are tangled in non-additive history OR (d) concurrent sessions on main have already imported them.** The implementer should still report the cwd-mishap in (d) so the orchestrator can choose between the two recovery paths.
