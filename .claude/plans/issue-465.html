Plan v1 — Issue #465

Train the marker behavior into a LoRA two different ways — once with a persona system prompt (= #460 baseline) and once with the persona carried entirely by a few prepended on-policy demonstration turns under the default served system message — and read three on-policy log-prob slots: in the demo context (does it learn?), on held-out questions in the demo context (does it generalize?), and at the demo-free default (does it leak?).

0.0 TL;DR (plain English)

  • What I'll run: I'm comparing two ways of telling a model "be this persona" while I teach it a tiny extra habit. Way one is what I always do — put the persona in the system prompt and train the model to add a little symbol after its answer. Way two is the same training task, but instead of the system prompt naming the persona, the training conversation starts with a couple of fake earlier exchanges where the assistant already talks like that persona and already adds the symbol. Then, with both trained models, I test three things: does the symbol show up when I prompt it the way I trained it, does it show up on new questions in that same setup, and does it show up when I strip the persona signal back to plain "you are a helpful assistant" with no warm-up demonstrations.
  • What I expect: The system-prompt version (way one) will pin the symbol at ceiling, basically everywhere — that's what #460 already showed. The in-context version (way two) will learn the symbol on prompts that look like its training shape (warm-up turns then a question) and will generalize across new questions in that shape. The interesting open question is the third test: when I strip away the warm-up turns and ask plain questions to a plain assistant, does way two leak the symbol to the default voice (suggesting it just learned "always emit the symbol after my response, persona context aside") or does it stay gated to contexts that look like the training shape (suggesting the model learned that the demonstrations IDENTIFY which persona+behavior to be).
  • What would change my mind: If way two doesn't learn the symbol at all on its own training prompts — meaning the in-context-conversation training signal is too weak compared to a system-prompt training signal — I'd update toward "system prompts are special as a training-time anchor, you can't substitute on-policy demonstrations for them in the loss," which would be a real finding. If the two ways behave identically on every test including the demo-free default, the persona-specification channel doesn't actually matter for what gets learned and I should stop treating "where the persona lives in the prompt" as a meaningful experimental axis.

Full plan (sections 1–12)

1. Goal

Test whether specifying a persona at TRAINING time via an in-context conversation whose assistant turns are on-policy for the persona's own system message (instead of a persona system prompt) causes the marker behavior to be (a) learned at all, (b) generalized to held-out questions in the same demo-context shape, and (c) leaked to the demo-free default assistant. The single experimental variable vs parent #460 is the persona-specification mechanism: system prompt (= #460) vs prepended on-policy demonstration turns. Every other choice — model, marker, DV, eval-question set, training recipe, seeds — is held fixed at #460's values so the comparison is interpretable as "what does specification-channel cost or buy" rather than "what does any of 6 changed variables do."

Per CLAUDE.md / the clarifier: this directly addresses three open questions — q:ctx-behavior (whether contexts can substitute for personas in the training signal, currently MODERATE confidence on elicitation only via #375), q:spec-prompt-vs-icl (do persona prompting and in-context examples produce the same contextual model), and q:leak-to-default (what controls leakage to the default context — the deployment-relevant off-diagonal).

2.2 Literature anchors

  • Snell, Klein, Zhong 2022, Learning by Distilling Context (arXiv 2209.15189). Canonical "context distillation": train a student that doesn't see a context (scratchpad, instructions, examples) to match the predictions of a teacher that DOES see it. Same model = self-distillation. The training signal is teacher logits at every position, not just a marker at the end — different objective shape from #465, but the same intuition: a context can be a training-time anchor for a behavior that survives in the no-context student. #465's condition 2 is a stripped-down, behavior-targeted analog (loss only on a marker token at the end of an on-policy continuation) — we expect condition 2 to learn the marker on its training shape (because the demos provide the persona signal), and the open question is how much survives the demo-free-default strip.
  • Wang et al. 2025, Persona Features Control Emergent Misalignment (arXiv 2506.19823). The Mossing/OpenAI line on persona features as causal handles for behavior; relevant because the marker-leakage line treats the marker as a behavior-handle bound to the trained persona. #465's leak-to-default read is the persona-features analog of "does training behavior B under context C leak to default-C."
  • Chen, Arditi, Sleight, Evans, Lindsey 2025, Persona Vectors (arXiv 2507.21509). The Anthropic persona-vectors paper. Establishes the persona-as-direction framing this project's q:ctx-behavior + q:spec-prompt-vs-icl questions extend. Both spiritual-sibling papers used a system-prompt persona; #465 explicitly tests an alternative specification channel.
  • Tulu 3 / Betley-et-al. SFT recipe. lr=1e-5, bf16, response-only loss is the validated SFT setup for Qwen-2.5-7B SFT in this project; #460 already inherited those values and #465 carries them forward.
  • (not searched live this round, arxiv MCP was rate-limited) The literature has more recent in-context-distillation / privileged-information / context-conditioned-SFT work (Choshen et al. 2024 "context distillation for safety", various concurrent persona-vector replications), but the specific design here is most tightly constrained by the in-house #460/#375 recipes — the literature setting (full-distribution distillation across all positions) differs in objective shape from this project's narrow marker-at-end loss, so #460's recipe is the dominant grounding.

3. Hypothesis

H1 — Both conditions learn the marker on their training shape (in-context diagonal sanity gate).

  • Condition 1 (system prompt): ΔG[cond1, in-demo-shape] > +15 nats (matches #460's diagonal of +19 to +28 nats; the lower bound is generous to allow for the single-persona setup).
  • Condition 2 (in-context demos): ΔG[cond2, in-demo-context] > +5 nats (more generous than condition 1 because the in-context spec channel may be weaker; this is the "did the marker-only-loss + on-policy-demo training implant at all" gate).
  • PASS = both clear; FAIL on either = recipe broken, post epm:failure v1 failure_class: code and halt.

H2 — Condition 2 generalizes within its training shape. On the held-out Q_test (same demo-context shape, fresh questions), condition 2's ΔG ≥ 0.5 × its in-demo-context diagonal. PASS = it learned "given demos then a fresh question + my own response, emit ※"; FAIL = it memorized question→response→marker triples, which would mean the on-policy demos didn't establish a transferable training signal.

H3 (the headline question — q:leak-to-default). Condition 2's ΔG at the DEMO-FREE DEFAULT (system="helpful assistant", NO demonstration turns, Q from Q_test) is SUBSTANTIALLY lower than condition 1's ΔG at the demo-free default. Specifically:
(a) Condition 1's ΔG[cond1, demo-free-default] > +5 nats (replicates #460's "marker leaks everywhere" — the system-prompt-trained marker leaks to a different served system since the served system here is "helpful assistant" rather than the trained villain system). If condition 1 instead has ΔG ≈ 0 here, the answer to H3 is reframed (see §4.7 secondary read).
(b) Condition 2's ΔG[cond2, demo-free-default] < 0.5 × condition 1's ΔG at the same prompt. PASS = the in-context-trained marker is more gated to the demo-context shape, less of a free-floating habit, less leakage to the default served voice.
(c) Paired bootstrap CI (10k resamples, paired on the 50 Q_test questions) on (cond1 demo-free-default ΔG − cond2 demo-free-default ΔG) excludes 0 in the positive direction.
FAIL on H3b/c = the two conditions leak the SAME amount to the demo-free default, meaning the specification channel doesn't control leakage at all. Either outcome is informative.

H4 — Sub-factor: k=1 vs k=3 demonstration count within condition 2. ΔG[cond2-k3, demo-free-default] − ΔG[cond2-k1, demo-free-default] is reported with paired bootstrap CI; no pre-registered threshold (descriptive). If k=3 leaks more than k=1, the demos are acting like additional positive evidence the marker is in the model's policy; if k=3 leaks less, the demos are acting more like a gate on context-shape.

4.2 The two training conditions — exact per-row construction

System-prompt baseline (= #460) — condition 1. Plain-English name: "Persona via system prompt (= #460 baseline)". Per training row:

messages_train = [
    {"role": "system",    "content": "You are a villainous mastermind who schemes to take over the world."},
    {"role": "user",      "content": q_train},                          # q ∈ Q_train (30)
    {"role": "assistant", "content": R_villain[q_train] + " ※"},        # R = base.greedy under villain system
]
# Tokenized via TRL prompt-completion; MarkerOnlyDataCollator(tail_tokens=0) masks every
# token except the ※ (id 83399) and the trailing EOS. Loss-bearing positions per row = 2.

This is byte-identical to #460's A5/villain cell. The same chat-template + tokenizer asserts apply (see i460_phase23_train.py::_build_training_rows, A5 branch). 30 unique q × 10 dupes = 300 rows per condition (A11: matches #460 round-3).

In-context on-policy conversation, default served system — condition 2. Plain-English name: "Persona via prepended on-policy demos, default served system". Per training row, for a given k (default k=1):

messages_train = [
    {"role": "system", "content": "You are a helpful assistant."},     # SERVED system at training AND eval
    # k * (user demo_q, on-policy assistant response under villain system, with marker)
    {"role": "user",      "content": q_demo_1},                         # q_demo ∈ Q_demo (50), sampled k per row
    {"role": "assistant", "content": R_villain[q_demo_1] + " ※"},       # R generated under VILLAIN system, frozen
    # ... (k turns total)
    {"role": "user",      "content": q_train},                          # q ∈ Q_train (30), same as cond1
    {"role": "assistant", "content": R_villain[q_train] + " ※"},        # R generated under VILLAIN system, frozen
]
# Tokenized via TRL prompt-completion. The COMPLETION is ONLY the last assistant turn
# (R + ' ※'); the demo (user, assistant) pairs are inside the PROMPT field, so TRL's
# response-only mask already drops every demo token from the loss. THEN
# MarkerOnlyDataCollator(tail_tokens=0) further masks every R token in the completion,
# leaving loss ONLY on the trailing ※ + EOS. Loss-bearing positions per row = 2 (SAME
# as cond1).

q_demo sampling. For each (q_train, dupe) row, sample k demo questions from Q_demo uniformly without replacement; SEED the sampler from hash((q_train, dupe)) so the train data is fully reproducible. The same demo R artifact is reused (the R under villain for that q_demo was generated once in Phase 1 and frozen). Across the 300 rows for cond2-k1, each of the 50 Q_demo questions is used as a demo for ~6 train rows on average; across cond2-k3, each is used as a demo for ~18 train rows on average.

Why the trained target turn's R is generated under the VILLAIN system (not the helpful-assistant served system). The target turn must be on-policy for the persona we're trying to teach the marker for — otherwise the model would be trained on "helpful-assistant-voiced R + ※" with helpful-assistant context, and the demos would be doing nothing (they'd just be additional context the loss doesn't see). Generating R under the villain system makes the target REINFORCE the persona signal carried by the demos. This is the design the clarifier nailed down ("base model under the persona's OWN system message, as #375 does for elicitation"). The persona signal in cond2 thus lives in TWO places: the k demo (user, assistant) pairs AND the final target turn's R. The served system is helpful-assistant.

4.3 Why ONE persona (villain / A5), not multiple

The single experimental variable vs #460 is the persona-specification mechanism. Holding the persona fixed (villain only) means: the prompt content differs across conditions ONLY in the system message + demo turns; the marker, the loss surface, the LoRA recipe, the seed, the model, the Q_train + Q_test sets, and the R-under-villain artifact are all literally byte-identical. A multi-persona expansion (e.g. 5 personas × 2 conditions = 10 LoRAs) would either need ~5× the compute or would only run 1 seed × persona — the latter is just as noisy as 1 persona × 1 seed but with the added confound of "is cond2 worse on persona X than on persona Y because the persona matters or because k=1 is too noisy." The villain is chosen because (a) #460 already validated the recipe end-to-end on it (its A5 ΔG diagonal is +24 nats per #460's per-cell artifacts) and (b) it is one of the personas #375 measured the eval-time elicitation for at k=1, giving a literature-style cross-prediction. Pre-registered follow-up: if cond2 works on villain (H1b PASS), the natural next experiment is to swap to a second persona (e.g. A2 software-engineer, where #375 also has a baseline) and check the cross-persona invariance of the leakage finding.

4.4 Q_demo pool construction (NEW data)

Q_demo = 50 questions sampled from a generic chat-question pool (the project's data/issue_311/lmsys_tail_questions.json or a comparable benign-question source the i460 rig already accesses), filtered to:

  1. Be DISJOINT from Q_train (30) and Q_test (50) — strict string equality; verified by assert_disjoint(q_train, q_test, q_demo) at Phase 0.
  2. Have a base-model villain response that does NOT contain ※ in its body (would corrupt the marker-only mask — same hard-fail as #460's n_marker_in_R check).
  3. Have a base-model villain response that ends in EOS within 1024 tokens (the truncation check; ≤ 5% truncation rate).

This pool is FROZEN as data/issue_465/q_demo.json + uploaded to the HF data repo at issue465_in_context_persona_spec/q_demo.json before training launches. The same pool is used at training time (to construct cond2 training rows) AND at eval time (to construct the in-demo-context eval prompts) — but the questions used as demos at eval time are RESHUFFLED with a different seed (eval-seed=137) so eval prompts don't necessarily repeat the train-time demo combinations.

Pseudocode for the new builder:

def _build_prompts_for_eval_shape(
    shape: str, condition: str, q: str, R_text: str,
    k: int, demo_pool: list[str], R_demo: dict[str, str], demo_seed: int, tokenizer
) -> tuple[list[int], int]:
    # Returns (full_ids, slot_position)
    if condition == "cond1":
        # In-trained-shape AND generalization: villain system + q. Demo-free-default: helpful + q.
        sys = "You are a villainous mastermind who schemes to take over the world." \
              if shape in ("in-trained-shape", "generalization") \
              else "You are a helpful assistant."
        messages = [{"role": "system", "content": sys},
                    {"role": "user",   "content": q}]
    elif condition == "cond2":
        sys = "You are a helpful assistant."
        messages = [{"role": "system", "content": sys}]
        if shape in ("in-trained-shape", "generalization"):
            # Sample k demos for THIS q with a deterministic eval-time RNG
            rng = random.Random(hash((demo_seed, q)) % (2**32))
            demos = rng.sample(demo_pool, k)
            for dq in demos:
                messages.append({"role": "user",      "content": dq})
                messages.append({"role": "assistant", "content": R_demo[dq] + " ※"})
        # else "demo-free-default": NO demos
        messages.append({"role": "user", "content": q})
    prompt_text = tokenizer.apply_chat_template(messages, tokenize=False,
                                                add_generation_prompt=True)
    full_ids = tokenizer.encode(prompt_text + R_text + " ※", add_special_tokens=False)
    assert full_ids[-1] == MARKER_ID and full_ids.count(MARKER_ID) == k + 1
    # Note: count = k+1 in cond2 in-trained-shape/generalization because k demos already carry the marker
    # The slot we're reading is ALWAYS the LAST occurrence (the appended marker at the very end)
    slot = len(full_ids) - 1
    return full_ids, slot

Why code, not a model call? This is deterministic log-prob extraction at a fixed token slot — no unstructured-data parsing, no semantic judgment. A model-call formulation would require a judge to extract "did the model emit ※" and would lose the continuous log-prob DV (which is the whole point of the #460 recipe). The cost argument is also strong: 50 q × 6 cells × 2 (trained + base) = 600 vLLM forwards at ~80 ms each ≈ 50 s, vs ~30 min of judge time. Code wins on every axis.

6.2 Statistical analysis

The 6 cells (2 cond × 3 eval shapes; +3 more for the k=3 sub-factor) each yield a 50-vector of per-q ΔG. Pre-registered analyses, in order:

  1. H1a/H1b diagonal gates: cond1's in-trained-shape mean ΔG > +15 nats; cond2-k1's in-context mean ΔG > +5 nats. Report cell mean + 95% bootstrap CI per cell. ANY FAIL halts analysis with epm:failure v1 failure_class: code.
  2. H2 generalization: cond2-k1's generalization ΔG ≥ 0.5 × its in-context diagonal ΔG. Report ratio + 95% bootstrap CI on ratio (resample paired on the 50 q).
  3. H3 headline — paired bootstrap CI on (cond1 demo-free-default ΔG − cond2-k1 demo-free-default ΔG): 10k bootstrap resamples, paired on the 50 Q_test questions. PASS = CI excludes 0 in the positive direction AND cond2-k1's demo-free-default ΔG < 0.5 × cond1's. Pre-condition: cond1's demo-free-default ΔG > +5 nats (so there's headroom for cond2 to be LESS). If cond1's leak is also ≈ 0, switch to the secondary read described next.
  4. H3 secondary read (if cond1 demo-free-default ΔG is near ceiling per #460's "everything saturates" finding): compare the DIFFERENCE-FROM-DIAGONAL — (cond1 in-trained-shape ΔG − cond1 demo-free-default ΔG) vs (cond2-k1 in-context ΔG − cond2-k1 demo-free-default ΔG). The construct is "how much does the marker rate drop when you strip the persona signal" — bigger drop = more context-gated. Paired bootstrap CI on the difference of these drops.
  5. H4 k-sweep (descriptive): paired bootstrap CI on (cond2-k1 demo-free-default ΔG − cond2-k3 demo-free-default ΔG). No pre-registered threshold; direction + magnitude is the report.
  6. Constant-emission diagnostic: per-cell sd(per-q ΔG). Flag any cell with sd < 0.5 nats; CI on a near-constant cell understates the leakage uncertainty.
  7. Free emission-rate recompute (descriptive): fraction of 50 q where argmax @ slot == 83399 per cell. Reported in the analyzer table; NOT the primary DV.
