0.0 TL;DR (plain English)

  • What I'll run: I'm rebuilding the exact model from a recent experiment — the one where I taught a "software engineer" character to end its answers with a special symbol, then watched that habit bleed over to 27 other characters. Last time I measured the leak by feeding the model a canned answer and asking "would you put the symbol here?" That trick made the character I actually trained look like it was near the bottom of the leak rankings, which never sat right. This time I let the model write its own answers and just count how often the symbol actually shows up.
  • What I expect: When I score the model on its own writing, the software-engineer character should land at the top — it's the only one I trained to emit the symbol, so it should emit it the most. The earlier "bottom of the pack" ranking was an artifact of the canned-answer probe, not a real thing about the model.
  • What would change my mind: If the software-engineer character still doesn't emit the symbol much when writing freely — or if some character I never trained emits it more — then the leak really is a deep, character-agnostic shift and the old probe was telling the truth. I'd also be surprised if the symbol almost never appears at all (which would mean my answers were getting cut off before the model reached the end).

Full plan (sections 1–12)

1. Goal

Measure whether the trained source persona (software_engineer) actually emits the marker ※, and how marker leakage distributes across the 28-persona panel, when scored on the model's OWN generated answers (on-policy emission rate + on-policy end-of-answer log p), replacing #432's off-distribution fixed-stub/pos0 teacher-forced probe. #432 reported that the trained source sat at rank 7/28 (pos0) / 8/28 (endpos) on its teacher-forced marker leaderboard despite being the only persona trained to emit ※ — a counter-intuitive result the parent itself flagged as "precisely why #456 reruns this on-policy." This experiment resolves whether that bottom-of-pack ranking is a property of the model or an artifact of the probe geometry.

3. Hypothesis

H1 (headline, falsifiable): On the model's own generations, software_engineer ranks #1/28 on end-state (step-1600) marker emission rate, with a wide margin over the second-place persona (≥2× the runner-up's rate, or ≥0.3 absolute gap). It is the only persona trained to emit ※, so on-distribution it should emit it the most.

H2 (artifact claim): software_engineer's on-policy emission rank (#1 predicted) is strictly better than its #432 teacher-forced rank (7 pos0 / 8 endpos). The gap demonstrates the parent's bottom-of-pack ranking was substantially a probe artifact.

H3 (companion DV agreement): On-policy end-of-answer log p(※) for the source rises across training and ranks the source at or near the top, agreeing with the emission-rate ordering (Spearman ρ between emission rate and on-policy endpos log p across the 28 personas ≥ 0.6 at step 1600).

H4 (control / direct artifact demonstration): The OLD fixed-stub endpos teacher-forced probe, re-scored on these SAME regenerated checkpoints, reproduces #432's low source rank (within ±2 ranks of rank 8), while the on-policy DV puts the source at the top — same model, same panel, opposite ranking ⇒ the ranking difference is purely the eval method.

What would falsify: If on-policy software_engineer emission rank > 5 at step 1600 (still mid-pack), OR any untrained bystander out-emits the source, OR the source's on-policy emission rate is itself near-floor (<10%) — then the marker leak is a genuine character-agnostic / global shift and the teacher-forced probe was not the culprit. If the old-probe re-score does NOT reproduce #432's low source rank, the retrain diverged from the parent and the comparison is void (kill criterion).

4.3 NEW code to write: scripts/eval_i456_onpolicy_emission.py

Single dispatcher that, for each checkpoint, generates on-policy completions, computes emission rate, and computes on-policy end-of-answer log p(※). Reuses _i416_bystander_panel for the panel and compute_marker_logprob for the endpos DV. Writes one JSON per checkpoint the moment it finishes (CLAUDE.md checkpoint-per-phase rule).

# scripts/eval_i456_onpolicy_emission.py  (pseudocode)
import argparse, json, gc, time
from pathlib import Path
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer
from peft import PeftModel
import importlib
from explore_persona_space.eval.marker_logprob import compute_marker_logprob

MARKER = "※"; MARKER_ID = 63680

def render_prompt(tok, system_text, question):
    return tok.apply_chat_template(
        [{"role":"system","content":system_text},{"role":"user","content":question}],
        tokenize=False, add_generation_prompt=True)

def main():
    ap = argparse.ArgumentParser()
    ap.add_argument("--run-dir", required=True)      # models//marker_implant_step_checkpoints
    ap.add_argument("--base-model", default="Qwen/Qwen2.5-7B-Instruct")
    ap.add_argument("--steps", required=True)         # comma-separated subset
    ap.add_argument("--panel-module", default="_i416_bystander_panel")
    ap.add_argument("--n-samples", type=int, default=8)
    ap.add_argument("--temperature", type=float, default=1.0)
    ap.add_argument("--top-p", type=float, default=1.0)
    ap.add_argument("--max-new-tokens", type=int, default=1536)
    ap.add_argument("--seed", type=int, default=42)
    ap.add_argument("--output-dir", required=True)    # eval_results/issue_456/
    args = ap.parse_args()

    tok = AutoTokenizer.from_pretrained(args.base_model, trust_remote_code=True)
    # HARD GUARD: marker must be the trained token id (matches #432)
    assert tok.encode(MARKER, add_special_tokens=False) == [MARKER_ID], "wrong marker token"

    panel_mod = importlib.import_module(args.panel_module)
    panel = {panel_mod.SOURCE_PERSONA: dict(panel_mod.PERSONAS)[panel_mod.SOURCE_PERSONA]}
    panel.update(panel_mod.BYSTANDERS)             # 28 personas total
    prompts = panel_mod.PROMPTS                    # 20 questions
    steps = [int(s) for s in args.steps.split(",")]

    # ---- Phase A: on-policy generation via vLLM, base loaded ONCE, LoRA swapped per ckpt
    from vllm import LLM, SamplingParams
    from vllm.lora.request import LoRARequest
    llm = LLM(model=args.base_model, enable_lora=True, max_lora_rank=32, max_loras=1,
              dtype="bfloat16", gpu_memory_utilization=0.85,
              max_model_len=4096, seed=args.seed)   # 4096 >= prompt(~512)+1536 gen
    sp = SamplingParams(n=args.n_samples, temperature=args.temperature, top_p=args.top_p,
                        max_tokens=args.max_new_tokens, seed=args.seed)
    # build the (persona,question) prompt list ONCE; reused for every checkpoint
    keys, rendered = [], []
    for pname, ptext in panel.items():
        for q in prompts:
            keys.append((pname, q)); rendered.append(render_prompt(tok, ptext, q))

    gen_by_step = {}                                # step -> {persona: {question: [completions]}}
    for step in steps:
        ckpt = Path(args.run_dir) / f"checkpoint-{step}"
        assert ckpt.exists(), f"missing {ckpt}"
        lr = LoRARequest(f"swe_step_{step}", step, str(ckpt))
        outs = llm.generate(rendered, sp, lora_request=lr)
        per = {p: {} for p in panel}
        for o, (pname, q) in zip(outs, keys):
            per[pname][q] = [s.text for s in o.outputs]
        gen_by_step[step] = per
        # ---- emission rate per persona (CHECKPOINT-PER-PHASE: write immediately)
        rates = {}
        for pname in panel:
            comps = [c for q in prompts for c in per[pname][q]]   # 20*n_samples
            n_hit = sum(1 for c in comps if MARKER in c)
            rates[pname] = {"n_total": len(comps), "n_hit": n_hit, "rate": n_hit/len(comps)}
        Path(args.output_dir).mkdir(parents=True, exist_ok=True)
        json.dump({"step": step, "marker": MARKER, "n_samples": args.n_samples,
                   "temperature": args.temperature, "max_new_tokens": args.max_new_tokens,
                   "panel": list(panel), "emission_rate": rates},
                  open(f"{args.output_dir}/emission_step{step}.json","w"), indent=2)
        # also dump raw completions per step for HF upload + qualitative examples
        json.dump(per, open(f"{args.output_dir}/raw_completions_step{step}.json","w"))
    # explicit vLLM teardown BEFORE loading HF (CLAUDE.md vLLM-teardown gotcha)
    del llm; gc.collect(); torch.cuda.empty_cache()
    _kill_vllm_workers()   # psutil children .terminate()/.kill(); assert nvidia-smi clear

    # ---- Phase B: on-policy END-OF-ANSWER teacher-forced log p(※)
    base = AutoModelForCausalLM.from_pretrained(args.base_model, torch_dtype=torch.bfloat16,
                                                device_map="cuda:0", trust_remote_code=True).eval()
    for step in steps:
        adapter = PeftModel.from_pretrained(base, str(Path(args.run_dir)/f"checkpoint-{step}")).eval()
        endpos = {}
        for pname in panel:
            # build the on-policy context: prompt + the model's OWN generated answer (per sample),
            # marker scored at the position right after that answer.
            ctxs = []
            for q in prompts:
                for comp in gen_by_step[step][pname][q]:
                    answer = comp.split(MARKER)[0].rstrip()   # strip any emitted marker+tail
                    ctxs.append(render_prompt(tok, panel[pname], q) + answer + "\n\n")
            logps = compute_marker_logprob(adapter, tok, contexts=ctxs,
                                           marker_text=MARKER, batch_size=8, device="cuda:0")
            endpos[pname] = {"mean": float(sum(logps)/len(logps)), "logps": logps}
        json.dump({"step": step, "geometry": "onpolicy_end_of_answer", "panel": list(panel),
                   "endpos_logp": endpos},
                  open(f"{args.output_dir}/onpolicy_endpos_step{step}.json","w"), indent=2)
        del adapter; gc.collect(); torch.cuda.empty_cache()

Why code, not a model call? The DV is a deterministic substring presence check on a single BPE token (※ in completion text) and a teacher-forced log-prob (a forward pass). Neither is an unstructured-text judgment — a Claude call would add latency, cost (~67k completions), and nondeterminism for zero benefit; the marker-substring exception is explicitly documented in CLAUDE.md. A model call would flip the decision only if the marker were semantic/fuzzy (it is not — it's one literal token). N/A-adjacent but stated per the §4 rule.

6. Evaluation

Metrics & thresholds

  • Headline: on-policy emission rate per (persona, checkpoint), n=160/cell (20 prompts × 8 samples). End-state leaderboard at step 1600. Success = software_engineer rank #1/28.
  • Artifact size: Δrank = (#432 teacher-forced source rank) − (#456 on-policy source rank). Predicted ≥ 6 (7→1 pos0; 8→1 endpos).
  • Companion: on-policy endpos log p(※); Spearman ρ(emission rate, endpos log p) across 28 personas at step 1600, expect ≥ 0.6.
  • CI: pooled binomial 95% CI on each emission rate (Wilson interval; n=160). Source rate CI must not overlap the runner-up's CI for a clean rank-#1 claim.
  • Control: old-probe re-score source rank within ±2 of #432's (7 pos0 / 8 endpos).
  • Trajectory: per-checkpoint emission rate + endpos log p (learning-speed DV; serves linked q:implant-learning-speed). Report first-crossing step (first checkpoint where source emission ≥ 5%).

7. Decision Gates

One gate — justified because the run is ~7 GPU-h (>4h) and the on-policy emission floor is genuinely uncertain at this max_new_tokens setting:

  • Phase 3 smoke gate (cheap, rules out the full run): after the 10-step smoke generation, the step-10 source emission rate need NOT be high (10 steps is early), but the pipeline MUST produce non-empty completions that reach end-of-answer (median completion length < max_new_tokens, i.e. not truncated) AND the marker-id assert passes AND at least the chat-template renders for all 28 personas including no_persona (empty system). If completions are systematically hitting the token cap (truncated), STOP and raise max_new_tokens before the 1600-step train — truncation would silently zero the emission rate (the #260 failure mode).

No mid-training gates: training is a faithful #432 replay (pre-verified — #432 already converged on this exact recipe), so a "stop if loss high" gate adds nothing.

9. Resources & Parallelism

Pod: 1× H100 80GB, intent lora-7b (matches #432). Parallelism axis: the only compute-bound work is (a) a single LoRA train (data-parallel not warranted for one 7B LoRA) and (b) vLLM batched generation (already maximally batched in one llm.generate() call per checkpoint). There is no independent-condition sweep axis to fan out — it is one model, evaluated serially across checkpoints, and vLLM batching already saturates the GPU. A larger pod would not reduce wall time (single LoRA train can't use DP efficiently at this scale; generation is one engine). So 1× H100 is correct, not a wall-time compromise. Checkpoint subset to cut cost: evaluate 12 of 22 checkpoints on-policy (full 22 for the cheap old-probe control) — see §11.
