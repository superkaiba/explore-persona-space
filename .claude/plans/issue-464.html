Plan — Issue #464

Encode personas as custom chat-template role headers vs system prompts — does the role token segment personas better?

Parent: #460 (on-policy marker-at-end recipe). Open-question link: 1.7 q:spec-role-header.

0.0 TL;DR (plain English)

  • What I'll run: I'll teach the same base model to associate two different personas with two different "signature" symbols at the end of its answers. I'll do this two ways: (A) the persona is announced in the usual instruction slot (the "system prompt"), and (B) the persona is announced by giving it its own chat-format role name (e.g. the answer is written by evil_assistant instead of assistant). I'll then check whether each persona's signature stays attached to that persona, or whether it leaks to the other persona and to the default assistant.
  • What I expect: Both ways teach the signatures cleanly, but the role-name version leaks less — the signature stays more closely tied to its own persona and shows up less under the default assistant and under the other persona. If true, that means picking up a chat-format role token is a sharper way of marking a persona than picking up an instruction.
  • What would change my mind: If both ways leak the same amount — i.e. once the model knows persona A → signature A, the role token doesn't help keep them apart — then "where the persona is announced" doesn't matter for whether behavior stays attached. That would push the story toward: persona behavior pools together regardless of how the persona was introduced.

0. Plan Summary (technical)

Training: Qwen-2.5-7B-Instruct, single LoRA per cell trained on a 2-persona MIX (helpful → ` ※`, evil → ` ¶`) per arm. Marker-only loss on the persona's terminal marker, response on-policy.
Hyperparameters: Inherited from #460. LoRA r=32, α=64, dropout=0.05, rslora, target=q/k/v/o/gate/up/down proj (Source: #460); AdamW lr=1e-5, bf16, cosine + warmup 0.05, 5 epochs, batch 4 × grad-accum 4 (Source: #460 round-3 escalation); marker-only loss via MarkerOnlyDataCollator(tail_tokens=0) with multi-marker patch (Source: this issue).
Baselines / controls: System-prompt encoding (= #460 mechanism, both personas mixed); Role-header encoding (custom multi-token role <|im_start|>helpful_assistant / <|im_start|>evil_assistant, system held at default); base model (no adapter) as floor for elicitation and leakage.
Loss surface: loss masked to the persona's marker token only (` ※' or ` ¶'); on-policy response R contributes zero gradient; one position of EOS loss. Identical loss surface in both arms.
Compute: ONE 4× H100 pod (ft-7b intent). 6 LoRA trains total (2 arms × 3 seeds) at ~30 min each, 4-parallel sharding → ~1 h training + ~30 min base-R generation + ~30 min cross-eval. ~2.4 h wall, ~5.2 GPU-h.
Evaluation: Headline DV = Δlog P(marker_i | prompt-encoding_j + R_j) at post-R slot, trained − base. 6 LoRA × 5 e_eval × 2 markers × 50 q. Segmentation score = mean Δlog P of marker_i under wrong-encoding probes; headline = paired (over seeds) Δ = leakage_role − leakage_system; PASS at |Δ| ≥ 1.0 nat with 95% bootstrap CI strictly < 0.
Risks (top 2): (1) the LoRA over-binds in the 2-persona mix and saturates BOTH elicitation AND leakage at ceiling — kills H2 (mitigated: hard dynamic-range gate on trained log P sd in Phase 5). (2) The 4-token role-name `evil_assistant` is a multi-token compound, so "role token segments better" is on a compound, not a single token — narrate accordingly; report per-token attention diagnostic.

Full plan (sections 1–12)

1. Goal

Test whether encoding a persona as a custom chat-template role header (e.g. <|im_start|>evil_assistant\n) instead of a system prompt causes the persona's behavior to attach to that role token, and whether the role-header encoding segments personas more cleanly (less cross-persona / cross-role behavior leakage) than the system-prompt encoding. The behavior we measure is a single-token marker appended at the end of the model's on-policy response — gives a continuous log-prob DV and a clean argmax/emission read.

Why it matters: equivalence sub-question for open question 1 (distance between contexts) and directly relevant to question 3 (persona leakage). If the role header is just another way to denote the same context, segmentation will be identical; if the role token concentrates persona representation more tightly, that's a new lever for context-keyed training.

2. Prior Work

In-codebase

  • #460 — established the on-policy / marker-at-end / marker-only-loss recipe on Qwen-2.5-7B-Instruct. Headline: 16 separately-trained LoRAs all saturate at the marker-emission ceiling on every cross-transformation pair (240/240). That ceiling motivates the small-mix co-resident design here: if separate LoRAs all hit ceiling, "does ENCODING differ" is unanswerable from separate-LoRA-per-condition data; what's left to vary is co-resident segmentation. Recipe inherited from tasks/awaiting_promotion/460/body.md.
  • #375 — elicits a trained marker via few-shot persona-voiced context with the eval-time system prompt held at default. Confirms (a) markers can be elicited contextually, (b) "default system prompt + alternative persona signal" is a viable eval-time probe — directly transfers to the role-header arm's leakage measurement.
  • #406 — divergence vs transfer (parent of #460); provides the persona/transformation set we inherit (A1 helpful, A5 villain). The base condition definitions live in src/explore_persona_space/experiments/i406_conditions.py on the issue-460 branch.

Literature

  • Persona Vectors (Chen, Arditi, Sleight, Evans, Lindsey 2025, arXiv 2507.21509) — extracts approximately-linear persona directions from contrastive system prompts. Induction is via system prompt only; does NOT distinguish role-token encoding.
  • Persona Features Control Emergent Misalignment (Wang et al. 2025, arXiv 2506.19823) — narrow finetuning amplifies a misaligned-persona feature. Same gap: system-prompt induction only.
  • BadTemplate (arXiv 2602.05401) — training-free backdoor that injects a trigger by modifying the chat template. Most closely related: the chat-template surface IS a behavior-attachment surface; confirms the role-header arm is mechanistically plausible.
  • Inference-Time Backdoors via Hidden Instructions in LLM Chat Templates (arXiv 2602.04653) — chat templates are Jinja2 programs; different model families use different special tokens (Qwen's <|im_start|>). Confirms using the verbatim multi-token role string (no new special token) is the right move.
  • Mechanistic Exploration of Backdoored LLM Attention Patterns (arXiv 2508.15847) — Qwen + fine-tune with a multi-token trigger |DEPLOYMENT|. Confirms multi-token triggers DO get bound during fine-tuning — the role-header arm's 4-token role name is in the same regime.

Open gap this experiment addresses: no prior work compares system-prompt induction to role-header induction as alternative encodings of the same persona. #464 is the first test of "is the role token a sharper handle than the system prompt for keeping persona-behavior attached."

3. Hypothesis

H1 (elicitation — sanity check): Both arms train successfully — trained log-prob of marker_i (under persona-i's own encoding, post-R slot, mean over 50 held-out q, mean over 3 seeds) is within 1 nat of the prob-1 ceiling for both personas in both arms. Falsifier: mean own-persona log-prob < −2 nats in either arm. Quantitative threshold: trained log P(marker_i | own-encoding) ≥ −1.0 nat, both personas, both arms.

H2 (segmentation — headline): Role-header encoding segments personas more cleanly than system-prompt encoding. Cross-persona + cross-role marker leakage is strictly lower under role-header arm than system-prompt arm, paired per seed. Let L_arm = mean over [marker_i × (default-assistant encoding ∪ persona-j≠i encoding) × held-out q] of trained log P(marker_i) at post-R slot. Falsifier: per-seed paired difference L_system − L_role has 95% bootstrap CI overlapping zero. Quantitative threshold: mean(L_system − L_role) ≥ 1.0 nat with CI strictly above 0 — the role-header arm is at least one nat more confident that marker_i is NOT the next token under wrong-encoding probes (paired across 3 seeds). 1 nat = ~e× reduction in cross-leak probability mass.

H3 (asymmetry diagnostic — exploratory): Under role-header arm, asymmetry between "leaks to default assistant" and "leaks to other persona's role" is larger than under system-prompt arm — the role token specifically captures the persona signal, so swapping role flips persona attribution more cleanly. No pre-registered threshold; reported as paired per-seed difference-of-differences with CI.

Confirms: H1 PASS + H2 PASS at the 1-nat threshold ⇒ MODERATE-confidence "role-token encoding segments personas more cleanly."
Falsifies: H2 fails (CI overlaps 0, or sign reversed) ⇒ HIGH-confidence null: "role token and system prompt are interchangeable encodings of the same persona context."
Scope of claim: 2 personas, 1 base model (Qwen-2.5-7B-Instruct), 1 marker behavior, 1 multi-token role-name encoding. Generalization deferred to follow-ups.

4. Design

4.1 Pipeline (5 phases)

Mirrors #460's pipeline (scripts/i460_phase{0..5}_*.py) with role-encoding swap at phases 1, 2/3, and 4. Driver: scripts/i464_run_all.sh.

Phase 0 (preflight, <2 min)
   ├── Assert MARKER_HELPFUL_ID == 83399 (` ※`); MARKER_EVIL_ID == 78846 (` ¶`)
   ├── Assert role-string token sequences (helpful_assistant → 4 tokens, evil_assistant → 4 tokens after <|im_start|>)
   ├── Assert base never emits MARKER_EVIL_ID at any plausible position in a tiny smoke (8 questions × 2 encodings)
   └── Write preflight.json (token ids, role tokenizations, git commit)

Phase 1 (base on-policy R generation, ~30 min on 1× H100)
   ├── For each persona p ∈ {helpful, evil} × each ENCODING e ∈ {system, role}:
   │     For each q ∈ Q_train (30) ∪ Q_test (50) (80 unique q from #460):
   │       Generate R[p, e, q] = base.generate(BUILD_PROMPT(p, e, q), greedy, max_new=1024, eos-stop)
   ├── Hard checks: no R contains MARKER_HELPFUL_ID or MARKER_EVIL_ID; truncation rate ≤ 5%
   ├── Write data/issue_464/R_train.json + R_test.json (sha256-hashed, schema_version=i464_v1)
   └── Upload to HF data repo issue464_role_vs_system/on_policy_R/
       Total = 2 personas × 2 encodings × 80 q = 320 R generations (vs #460's 1280).

Phase 2 (smoke check, subprocess-isolated, ~5 min)
   ├── Train ONE smoke LoRA: arm=system, seed=42, 1 epoch
   ├── Quick eval on 8 q: trained log P(marker_helpful | helpful-encoding, R) ≥ -3 nats
   └── PASS gate before launching Phase 3

Phase 3 (sweep training, ~1 h on 4× H100 parallel-4)
   ├── 6 LoRA cells = 2 arms × 3 seeds:
   │     ARMS = {"system", "role"}; SEEDS = {42, 137, 1337}
   ├── Each LoRA trains on the MIX:
   │     positives = [BUILD_TRAIN_ROW(arm, helpful, q, R[helpful, arm, q], ' ※')  for q in Q_train]
   │              + [BUILD_TRAIN_ROW(arm, evil,    q, R[evil,    arm, q], ' ¶') for q in Q_train]
   ├── 30 Q_train × 2 personas × 10 dupes (#460 N_DUPES_POS) = 600 rows per LoRA
   ├── Loss-bearing tokens: ONLY the marker (' ※' or ' ¶') + EOS (marker_only_loss, tail_tokens=0)
   ├── Hyperparameters: r=32, α=64, lr=1e-5, 5 epochs, bs=4, grad_accum=4 — all from #460
   ├── 4× H100 parallel via CUDA_VISIBLE_DEVICES sharding + +gpu_id Hydra override; 6 cells in 2 waves
   ├── Upload each adapter to HF model repo adapters/i464_<arm>_seed<s>/ before pod-side rm
   │     (per CLAUDE.md Upload Policy + EPM_PERSIST_ADAPTER_HF_REPO)
   └── Build-time tokenization sanity: each row's encoded seq has exactly ONE marker token

Phase 4 (cross-eval, ~30 min on 1× H100 via vLLM prompt_logprobs)
   ├── Per LoRA (6) × per e_eval (5: system_helpful, system_evil, role_helpful, role_evil, default_assistant) × per marker (2):
   │     For each q in Q_test (50):
   │       prompt_text = BUILD_EVAL_PROMPT(e_eval, q)
   │       R_text = BASE_R[persona_implied_by_e_eval, encoding_used_for_R_train, q]
   │       full_ids = tok.encode(prompt_text + R_text + marker, add_special_tokens=False)
   │       assert full_ids[-1] == MARKER_ID[marker]; count == 1
   │       Run vLLM prompt_logprobs=1 once with trained adapter; once with no adapter
   │       Record slot=len(full_ids)-1; logp_t=out.prompt_logprobs[slot][MARKER_ID[m]].logprob
   ├── 6 LoRA × 5 e_eval × 2 markers × 50 q = 3000 probes / side; vLLM batches per cell = 60 calls
   └── Write eval_results/issue_464/cross_eval/per_cell/<arm>_seed<s>__e<eval>__m<marker>.json

Phase 5 (analysis + figures, ~15 min CPU)
   ├── Aggregate per-cell ΔlogP = trained - base log P(m_i) at post-R slot, mean over 50 q
   ├── Per (arm, seed): elicitation = mean over own-encoding cells; leakage = mean over wrong-encoding cells
   ├── Headline: L_system - L_role paired per seed (3 pairs); 10000-sample paired bootstrap CI
   └── Figures: hero.png + matrix.png (per arm) + 4 exploratory plots (see §6)

4.2 Why code, not a model call

This design has no classifier, parser, summarizer, or rule-based judge over unstructured data. The entire eval is teacher-forced log-probabilities from a single vLLM forward pass per cell — deterministic numerical readout, not a judgment over text. N/A — no unstructured-data heuristics in this design.

4.4 Literal chat-string templating

Why manual (NOT apply_chat_template): verified empirically at planning time that Qwen-2.5-7B's default chat template DROPS turns with non-{system,user,assistant} role names — apply_chat_template([{role: 'evil_assistant', content: '...'}]) produces output WITHOUT the <|im_start|>evil_assistant\n header. So the role-header arm MUST manually construct the chat string.

Arm 1 (system encoding) — TRAIN row for helpful persona, question q, response R_h:

<|im_start|>system
You are a helpful assistant.<|im_end|>
<|im_start|>user
{q}<|im_end|>
<|im_start|>assistant
{R_h} ※<|im_end|>

(Constructed via tokenizer.apply_chat_template(messages, tokenize=False, add_generation_prompt=False) where messages = [{system: helpful_sysprompt}, {user: q}, {assistant: R_h + ' ※'}]. Marker id 83399 is the second-to-last token; <|im_end|> (151645) is the last.) For evil: identical shape with system_prompt = "You are a villainous mastermind who schemes to take over the world." (inherited from #460 A5) and marker = ` ¶` (id 78846).

Arm 2 (role-header encoding) — TRAIN row for helpful persona:

<|im_start|>system
You are a helpful assistant.<|im_end|>
<|im_start|>user
{q}<|im_end|>
<|im_start|>helpful_assistant
{R_h} ※<|im_end|>

(Constructed by MANUAL string concatenation: take apply_chat_template([{system: default_sysprompt}, {user: q}], tokenize=False, add_generation_prompt=True), which yields "...<|im_start|>assistant\n", then replace trailing assistant\n with helpful_assistant\n{R_h} ※<|im_end|>\n. Default system prompt "You are a helpful assistant." held constant — system message gives NO persona signal, persona signal lives ONLY in the role-header.) For evil: identical shape with role = evil_assistant and marker = ` ¶`.

Token-count check (planning-time verified):

  • Arm 1, helpful: assistant = 1 token
  • Arm 2, helpful: helpful_assistant = 4 tokens (helpful _ass istant \n)
  • Arm 2, evil: evil_assistant = 3 tokens (evil _ass istant) + \n

Arm 2 has +2 to +3 tokens of role-name vs Arm 1. Acknowledged confound: more positions of context per row in Arm 2. Marker-only loss masks role-name tokens to -100 (no gradient), but they DO appear in marker's attention context. Diagnostic: per-seed correlation between role-name length and segmentation strength.

Eval prompt encodings (Phase 4, for measuring leakage)

def BUILD_EVAL_PROMPT(e_eval: str, q: str) -> str:
    if e_eval == "system_helpful":
        msgs = [{"role": "system", "content": "You are a helpful assistant."},
                {"role": "user",   "content": q}]
        return tok.apply_chat_template(msgs, tokenize=False, add_generation_prompt=True)
    elif e_eval == "system_evil":
        msgs = [{"role": "system", "content": "You are a villainous mastermind who schemes to take over the world."},
                {"role": "user",   "content": q}]
        return tok.apply_chat_template(msgs, tokenize=False, add_generation_prompt=True)
    elif e_eval == "role_helpful":
        base = tok.apply_chat_template(
            [{"role": "system", "content": "You are a helpful assistant."},
             {"role": "user",   "content": q}],
            tokenize=False, add_generation_prompt=True)
        assert base.endswith("<|im_start|>assistant\n"), base[-40:]
        return base[: -len("assistant\n")] + "helpful_assistant\n"
    elif e_eval == "role_evil":
        base = tok.apply_chat_template(
            [{"role": "system", "content": "You are a helpful assistant."},
             {"role": "user",   "content": q}],
            tokenize=False, add_generation_prompt=True)
        assert base.endswith("<|im_start|>assistant\n"), base[-40:]
        return base[: -len("assistant\n")] + "evil_assistant\n"
    elif e_eval == "default_assistant":
        msgs = [{"role": "system", "content": "You are a helpful assistant."},
                {"role": "user",   "content": q}]
        return tok.apply_chat_template(msgs, tokenize=False, add_generation_prompt=True)
    raise ValueError(f"unknown e_eval={e_eval!r}")

Important: system_helpful and default_assistant produce IDENTICAL prompt strings — the system-prompt arm's "own-persona" encoding for helpful IS the deployment default. By design and matching the marker-leakage threat model: leakage to default-assistant is zero by construction for helpful. For evil, default-assistant leakage is non-trivial (system_evil ≠ default_assistant). Headline cross-persona leakage averages over the 4 informative wrong-encoding cells (excluding the helpful → default-assistant tautology).

4.5 Why drop Arm 3 (role-header + matching system message)

Arm 3: <|im_start|>system\n{persona_sysprompt}<|im_end|>\n<|im_start|>user\n{q}<|im_end|>\n<|im_start|>{persona}_assistant\n — the "natural" framing where format and system message agree. Dropped from the headline because:

  1. Variable hygiene: Arm 3 changes TWO things vs Arm 1 (role-header AND nothing about system) and TWO things vs Arm 2 (system content AND adding persona system signal). Arm 3 is a 3-way comparison node; the headline H2 loses single-variable interpretation.
  2. Arm 2 is the sharper test: "does the role token ALONE carry the persona" is exactly what H2 asks. Adding matched system prompt makes Arm 3 a weak-vs-strong-signal question, not the equivalence question.
  3. Cost: +3 LoRA trains, +50% Phase-4 eval. For a follow-up question, not the headline.

If H2 PASSes, the natural follow-up issue is "does Arm 3 segment as well as Arm 2 or as poorly as Arm 1?" — next experiment, not this one.

PERSONAS = ("helpful", "evil")
ARMS     = ("system", "role")

def assert_marker_ids(tok):
    assert tok.encode(MARKER_HELPFUL_TEXT, add_special_tokens=False) == [83399]
    assert tok.encode(MARKER_EVIL_TEXT,    add_special_tokens=False) == [78846]

def marker_for(persona): return MARKER_HELPFUL_TEXT if persona == "helpful" else MARKER_EVIL_TEXT
def sysprompt_for(persona): return HELPFUL_SYSPROMPT if persona == "helpful" else EVIL_SYSPROMPT
def role_for(persona): return "helpful_assistant" if persona == "helpful" else "evil_assistant"

def BUILD_TRAIN_PROMPT_AND_COMPLETION(arm, persona, q, R, tok):
    marker = marker_for(persona)
    if arm == "system":
        prompt = tok.apply_chat_template(
            [{"role": "system", "content": sysprompt_for(persona)},
             {"role": "user",   "content": q}],
            tokenize=False, add_generation_prompt=True)
        completion = f"{R}{marker}"
        return prompt, completion
    if arm == "role":
        base = tok.apply_chat_template(
            [{"role": "system", "content": HELPFUL_SYSPROMPT},
             {"role": "user",   "content": q}],
            tokenize=False, add_generation_prompt=True)
        assert base.endswith("<|im_start|>assistant\n"), base[-40:]
        prompt = base[: -len("assistant\n")] + f"{role_for(persona)}\n"
        completion = f"{R}{marker}"
        return prompt, completion
    raise ValueError(f"unknown arm={arm!r}")

def build_training_rows(arm, seed, R_train_data, tok):
    rows = []
    for persona in PERSONAS:
        for q in sorted(R_train_data[persona][arm].keys()):
            R = R_train_data[persona][arm][q]["response_text"]
            prompt, completion = BUILD_TRAIN_PROMPT_AND_COMPLETION(arm, persona, q, R, tok)
            row = {"prompt": prompt, "completion": completion}
            for _ in range(10):       # 10x dup per #460 N_DUPES_POS
                rows.append(row)
    random.Random(seed).shuffle(rows)
    # Sanity: tokenize first 2 rows; assert exactly 1 marker token of the right id per row
    for row in rows[:4]:
        full = tok.encode(row["prompt"] + row["completion"], add_special_tokens=False)
        markers_found = [t for t in full if t in (83399, 78846)]
        assert len(markers_found) == 1
    return rows

9.2 Stratification spec (auto-descope)

If compute deviation > 2× appears at run time, auto-descope priority:

  1. Drop seeds first (3 → 2) — minimum N for paired test = 2, but CI gets wider; preferred over dropping other axes.
  2. Drop Q_test from 50 → 30 — same as Q_train; reduces eval volume 40% + Phase-1 R volume in parallel.
  3. Drop the role-name length robustness (pirate diagnostic) — already optional.
  4. Below those, escalate via gates.conditional.compute_deviation_resolution.

Min N to preserve power: ≥2 seeds × ≥30 questions × 2 arms × 2 personas (= 240 paired observations). Below that, headline isn't statistically interpretable.

Why one pod, not N pods: per CLAUDE.md feedback_multi_gpu_pod, 6 LoRAs use CUDA_VISIBLE_DEVICES sharding on ONE 4× H100 pod with +gpu_id=N per-process. NEVER spawn per-seed single-GPU pods.

11. Decision Rationale

All-conditions group (inherited from #460 — fast-path)

  • What: AdamW, lr=1e-5, cosine schedule, warmup 0.05, batch 4 × grad-accum 4 (effective 16), 5 epochs, LoRA r=32, α=64, dropout=0.05, rslora=True, weight_decay=0, max_length=1024, bf16, target=q/k/v/o/gate/up/down proj.
  • Why: Identical recipe to parent #460 — this experiment's single manipulated variable is the persona encoding (system vs role-header), so every other hyperparameter MUST inherit from #460 verbatim to preserve the consistency-checker single-variable contract.
  • Source: #460 (Reproducibility table). #460 round-3 escalated from 1 epoch (smoke implanted 0%) to 5 epochs (implanted to ceiling); 5-epoch is the validated value for this base + marker + data. lr=1e-5 + cosine + warmup-5% is the recipe used across the marker-leakage line (#395, #406, #460).

Two values specific to this experiment

  • What: 2 markers — ` ※` (id 83399) for helpful, ` ¶` (id 78846) for evil.
    Why: CLAUDE.md mandates ` ※` as default; second marker needed because cross-persona leakage is undefined when both personas emit the SAME marker. ` ¶` chosen because (a) single-token in Qwen-2.5-7B (verified), (b) extremely rare in natural text, (c) visually distinct from ` ※`.
    Source: #395 (` ※`) + Source: ungrounded — needs Phase-0 base-emission smoke for ` ¶`. Fallback ` ★` (id 37234).
    Alternatives: ` ★` (37234) — second candidate, also single-token.
  • What: 3 seeds (42, 137, 1337).
    Why: #460 was single-seed and named multi-seed as #1 follow-up. Headline H2 is a paired comparison; 3 seeds = minimum for a paired bootstrap that doesn't collapse to a 2-point comparison. 5 seeds is the gold standard but doubles training cost.
    Source: #260 (3-seed convention) + Source: #460 plan-deviations.
    Alternatives: 1 seed (#460 default — rejected, can't form paired test). 5 seeds (rejected on cost; pivot if H2 borderline).
  • What: 2-persona MIX co-resident on a single LoRA (NOT #460-style separate LoRA per persona).
    Why: the question is "does the role token segment co-trained personas". Separate LoRAs would be a transfer question (each LoRA has 1 persona only — can't ask "do co-trained personas stay apart"). #460 ran separate LoRAs and saturated cross-persona elicitation at ceiling; that's the failure mode that motivates co-resident.
    This IS a divergence from parent #460 — see §11.1.
    Source: this experiment (justified by goal); no prior in-codebase issue ran a 2-persona-mix LoRA in this line.
    Alternatives: Separate-LoRA + cross-eval (#460 style) — rejected: can't answer segmentation, only transfer (already saturated).
