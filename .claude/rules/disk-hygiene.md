## Disk hygiene (VM root disk)

- **`.claude/worktrees/` is DESIGNED to live on the dedicated GCP data disk at `/mnt/eps-data` with per-task ext4 quotas (#681) — the bind cutover is a RUNTIME-CHECKED state, not an accomplished fact (cutover tracked at #2132).** The heavy active-task footprint (issue worktrees + per-issue `data/issue_<N>/{hf_dl,g*_dl,store}` caches) is DESTINED for the data disk (`EPS_VM_DATA_DISK_PATH`), bind-mounted back onto `.claude/worktrees` so every consumer resolves the same path — but before citing the bind (or `/mnt/eps-data` headroom) in ANY plan §9 disk row or staging decision, probe live state: `findmnt --mountpoint <repo>/.claude/worktrees` (no output = cutover still pending — worktree paths, their `data/` included, then land on `/`) plus `df -P` on the RESOLVED filesystem with free headroom ≥ ~1.5× the projected bytes. Disk sizes/usage drift — never quote this file's figures as current. Once the bind is live, each `issue-<N>` subtree carries ext4 project id == issue number with a hard byte cap (`EPS_ISSUE_DISK_CAP_GB`, default 128 GB) — a write past the cap fails loud with `EDQUOT` while every other issue keeps writing. **Recovery is resize/raise-cap, NEVER delete active data:** `clean_experiment_downloads.py <N> --apply` on a TERMINAL issue, `setquota -P <N> 0 <cap_kb> 0 0 /mnt/eps-data`, or a GCP live-resize. `new_worktree.sh` asserts the bind is live (`EPS_WORKTREE_REQUIRE_BIND=1`) and refuses while the cutover `.claude/cache/worktree-migration.LOCK` is held; its once-per-session WARN mirrors the SAME `findmnt` runtime probe the opening prescribes for whether the one-time cutover is still pending (#771). The **`VM_ANALYSIS_FOOTPRINT_GB_MAX=50` off-VM routing rule is UNCHANGED** — the quota is a containment BACKSTOP, not a permission slip.
- Per-experiment HF download caches (`data/issue_<N>/hf_dl/` + `g*_dl/` — in the repo-root `data/` AND the issue worktree) are RE-DOWNLOADABLE, cleaned automatically at `/issue` Step 8 (after upload-verification PASS) via `uv run python scripts/clean_experiment_downloads.py <N> --apply` (sweeps both copies). **NEVER delete `store/` or `eval_results/`** (repo-root OR worktrees) — durable artifacts, not caches. **(#911)** both janitors ALSO sweep non-canonical issue-keyed staging caches (top-level `/tmp/` `i<N>*`/`issue<N>*`/`*_<N>` dirs + `data/` `issue…<N>…{_dl,_hfstage,_cache}` dirs) under the same contract plus a 48 h recently-touched keep, a nested-durable block, and a positive re-downloadability-evidence requirement; kill switch `EPM_SKIP_NONCANONICAL_CACHE_SWEEP=1`. **(#2095)** the same sweep gains an opt-in `/mnt/eps-data/$USER` STAGING-ROOTS leg (roots overridable via `EPM_STAGING_CACHE_ROOTS`; own kill switch `EPM_SKIP_STAGING_CACHE_SWEEP=1`; TOP-LEVEL-ONLY recency) with a cross-issue content gate — a staging dir named for issue A holding issue B's paths HARD-ESCALATES (`staging-cache-cross-issue-kept`), never a name-keyed reap. Kill-switch scope: both switches disable the SWEEP only — the watcher's read-only staging attribution (`_staging_top_caches`) deliberately survives them (the triage channel while the sweep is off). **(#2127)** the `vm_disk_guard` boot-disk pass additionally runs an owner-status-INDEPENDENT tier over top-level `/tmp` gate/smoke SCRATCH trees (`clean_experiment_downloads.sweep_tmp_scratch`; shapes `*-gate*` / `*smoke*` / `eps-*-scratch-*` / `scratch-*` / `mkstest-*`; hard denylist `claude-*` / `pytest-of-*` / session+system dirs, checked FIRST — the live Claude task-output tree and live Step-9c pytest basetemps are structurally unreachable). **User-facing bulk deletions are gated on POSITIVE VERIFIED evidence — HF-backedness (mirror/hub-layout) or git-reproducibility (blob-existence proof; recoverability-now, see the gc residual note) — never on age alone; age (recency) is only ever a KEEP signal (#2127, user directive 2026-08-06; #1092 is the standing counter-example an age gate would have destroyed).** The proof is per-file (every non-exempt regular file's git blob present in the main repo's odb — small-text telemetry `.txt/.log/.out/.err` tolerated under tight byte caps, `.diff` deliberately NOT) plus class-discriminated git probes (registered worktree: unlocked + status-clean + HEAD reachable; clone: status/stash clean + every ref tip reachable from surviving main-repo refs); write recency (mtime over everything) AND reader recency (atimes of `nlink==1` non-exempt files only — uv-hardlinked `.venv` and janitor-refreshed `.git` atimes are not reader evidence) are KEEP signals, the latter escalating verified-but-recently-read trees as `tmp-scratch-verified-atime-pinned`; a `/proc` live-process probe holds the reap (root/other-uid processes are invisible to it — named residual). Registered worktrees are removed via `git worktree remove --force` — a remove failure (e.g. a just-acquired lock) KEEPS the tree; there is deliberately NO `git worktree prune` fallback (a global prune would unregister PEER worktrees whose trees are momentarily missing, e.g. a registered `/mnt/eps-data`-rooted scratch during a mount hiccup — repairable via `git worktree repair`, but not the janitor's to inflict). Blob verdicts cache at `.claude/cache/scratch-verify-cache.json` (keyed path|mtime|bytes; a cached PASS can outlive a later `git gc` — the gc residual), and the reap path RE-RUNS the git class probes before any removal — a cached PASS never licenses a deletion on flipped external git state (ref deleted, lock taken, tree dirtied → `tmp-scratch-reap-reprobe-kept`). The same git-blob proof arms the issue-keyed `/tmp` legs' gate 1.7 as evidence branch (c) (`git_evidence_repo`, main()-only opt-in; never a registered worktree). Kill switch `EPM_SKIP_TMP_SCRATCH_SWEEP=1` (this leg alone; the `EPM_SKIP_NONCANONICAL_CACHE_SWEEP=1` family switch kills it transitively). **(#2147)** the same verified-scratch regime gains a `vm_disk_guard` tier (g) leg over TERMINAL-status issues' `~/.eps-slurm-src/issue-<N>` SLURM staging trees (`clean_experiment_downloads.sweep_slurm_src` via `vm_disk_guard.clean_slurm_src`; boot-disk pass only; the trees are full repo checkouts `backends/slurm.py::materialize_branch_src` rsyncs per dispatch — ~8.6 GB mean, 13 dirs / 112 GB measured 2026-08-16; the prepare `finally` reap stays the first line of defense, tier (g) is the backstop for trees a crashed prepare strands). Gate ladder: g1 name shape (`issue-<N>` only) -> g2 uid ownership -> g3 containment (symlinked / non-directory entries never followed) -> g4 terminal status (`TERMINAL_CACHE_REAP_STATUSES`, read-only resolver; an ACTIVE or unresolvable issue's tree is KEPT + escalated, never deleted) -> g4b status-probe failure (KEPT + escalated), then the IDENTICAL #2127 per-candidate core (per-file blob proof, class-discriminated git probes, reader-atime pin, live-process hold, reap-time re-probe — plus, before ANY `rmtree`, a POSITIVE worktree-non-registration proof from `git worktree list --porcelain` (a registered worktree whose in-tree `.git` pointer was deleted/replaced still appears in the admin-side listing; probe failure/ambiguity KEEPS), `git worktree remove --force` with no prune fallback), keep reasons re-tagged `slurm-src-*`. Nested working-tree overlays (`backends.slurm.WORKING_TREE_OVERLAY_PATHS`, e.g. `external/open-instruct`) are proven against the SURVIVING overlay repo — the main working tree's own `<main_repo>/<overlay path>` copy, the one that outlives the reap (the nested copy's odb dies with the tree) — under the full clone-class standard (clean tree + empty own stash + every ref tip and HEAD reachable in the surviving repo), with every PRESENT declared overlay path validated even when it holds only tolerated logs / exempt content / symlinks / nothing (no tolerance under an overlay; a SYMLINKED declared-overlay path is never followed — `overlay-not-a-repo`); an overlay that is not a positively-established nested git repo KEEPs the whole tree — deliberately NO fallback to the outer-odb proof. The overlay probe is NON-CACHEABLE and re-runs both BEFORE a cached PASS is honored and AGAIN on the destructive path immediately before removal (a cached PASS embeds overlay conclusions that flip with zero candidate-tree change — e.g. the surviving anchor losing refs); the armed sweep's staging-root validator RETURNS the canonical root and enumeration/containment/candidates use only that returned path (a post-validation symlink-target swap of the raw root is inert). **Reconciliation with "NEVER delete `store/` or `eval_results/`" (plan #2147 §0):** that rule bars treating durable-NAMED paths as caches under the age/name-gated legs; the verified-scratch regime is evidence-class-scoped — a slurm-src tree is a full repo CHECKOUT, so committed `store/`/`eval_results/` content inside it is proof-gated PER FILE against the main odb (and the core's `under_durable` rule denies those files the small-text tolerance) rather than presence-blocking the reap; a single unproven byte under either component keeps the whole tree. Standing keeps dedup per (path, disposition, reason slug, size band) — the reason slug is in the key per plan D6, so a materially different keep reason under one disposition re-alerts immediately — with a weekly re-alert (`EPS_SLURM_SRC_ESCALATION_REALERT_DAYS`), the dedup timestamp committed only after the sidecar append durably lands. Kill switch `EPM_SKIP_SLURM_SRC_SWEEP=1` (this leg alone; the family switch kills it transitively); report-mode acceptance runs set `EPS_SCRATCH_VERDICT_CACHE` so a dry run never writes the production verdict cache.
- **Incremental (between-phase) cleanup for multi-phase runs.** Step-8 cleanup fires only at experiment END, so a multi-phase run reaps each CONSUMED phase's cache BEFORE the next phase downloads more — `uv run python scripts/clean_experiment_downloads.py <N> --incremental --apply` (same safety contract; no terminal-status gate; "CONSUMED" = no LATER phase or provision reads it — enumerate every later consumer before placing the reap, #1489). Bounds PEAK footprint only: a single phase estimated over **50 GB** (`VM_ANALYSIS_FOOTPRINT_GB_MAX`) must be ROUTED off the VM at plan time (`intent: cpu-bigmem` or streaming; `planner.md` §9, `critic.md` item 10; #658).
- Fleet-wide backstop for caches that escape Step 8: the **`vm_disk_guard.py` cron** (`scripts/cron_vm_disk_guard.sh`). Over **85%** `/` usage (`EPS_VM_DISK_THRESHOLD`) it runs tiered safe cleanup — `uv cache prune`; TERMINAL-status issues' `hf_dl`/`g*_dl` + #911 non-canonical caches (ACTIVE issues never touched, only attributed); stale logs; age-gated pod-style + HOME HF hub cache reaps incl. a size-cap arm (`EPS_VM_HOME_HF_CACHE_CAP_GB`, default 50 GB; #1376/#1377/#1450) — then escalates loud (Telegram + sidecar) if still over. Report-only by default; the cron passes `--apply`. Since #1392 the watcher's sub-floor arm launches a detached single-flight `--apply` run when `/` free drops below `EPM_VM_DISK_SUBFLOOR_GIB` (kill switch `EPM_DISABLE_SUBFLOOR_RECLAIM=1`). A SECOND, ESCALATE-ONLY pass watches `/mnt/eps-data` (#681; terminal-cache reap + escalation only — its tier (b) covers the #2095 staging-roots leg too; skipped when the mount is absent). Full predicates: `.claude/rules/background-automation.md`.
- **Scheduled `uv cache prune` (idle-time cron).** The global uv package cache grows unbounded; `scripts/cron_uv_cache_prune.sh` runs `uv cache prune` — which KEEPS in-use entries (NOT `uv cache clean --force`) and is graceful when the cache lock is held — daily off-peak, so `vm_disk_guard` rarely fires on a full disk. Registered via the orchestrator's cron management.
- **Active-task escalation — warn-only, NEVER auto-deletes active data (#679).** Three channels surface a band-worthy ACTIVE-task cache without deleting it, all writing `.claude/cache/disk-guard-events.jsonl`: (a) the guard's tier-(b) kept-branch escalation (push + sidecar row naming the task, largest cache path, footprint, and the safe post-run reclaim command; deduped per (task, band), ack-sentinel suppress); (b) the watcher sub-floor sentinel (for `/mnt/eps-data` a SIZE-INVARIANT percent threshold, `EPM_VM_DATA_DISK_SUBFLOOR_PCT` default 85%, attributing worktree-internal caches via `repquota -P`); (c) `clean_experiment_downloads.py`'s nested-`store/` parity guard (SKIPs, never deletes, a mis-rooted `store/` not verifiably mirrored on HF).
- **VM-root preflight floor (#679).** Preflight WARNs when `/` is >90% used or <20 GB free, AND HARD-FAILs (`report.ok=False`) when VM-root free is below `EPM_PREFLIGHT_DISK_FLOOR_GB` (default 40 GB) — a fresh launch below the floor fails fast rather than starting near the silent-Bash-failure regime (RunPod `/workspace` exempt — the EDQUOT quota probe is binding there). Override a deliberate low-disk launch with `EPM_PREFLIGHT_DISK_FLOOR_OVERRIDE=1` (degrades to a logged WARN). Both point at `vm_disk_guard.py --apply`.
