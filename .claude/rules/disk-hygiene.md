## Disk hygiene (VM root disk)

- **`.claude/worktrees/` lives on a dedicated GCP data disk with per-task ext4 quotas (#681).** The heavy active-task footprint (issue worktrees + per-issue `data/issue_<N>/{hf_dl,g*_dl,store}` caches) lives on a **512 GB data disk at `/mnt/eps-data`** (`EPS_VM_DATA_DISK_PATH`), bind-mounted back onto `.claude/worktrees`. Each `issue-<N>` subtree carries ext4 project id == issue number with a hard byte cap (`EPS_ISSUE_DISK_CAP_GB`, default 128 GB) — a write past the cap fails loud with `EDQUOT` while every other issue keeps writing. **Recovery is resize/raise-cap, NEVER delete active data:** `clean_experiment_downloads.py <N> --apply` on a TERMINAL issue, `setquota -P <N> 0 <cap_kb> 0 0 /mnt/eps-data`, or a GCP live-resize. `new_worktree.sh` asserts the bind is live (`EPS_WORKTREE_REQUIRE_BIND=1`) and refuses while the cutover `.claude/cache/worktree-migration.LOCK` is held; its once-per-session WARN is the live source of truth for whether the one-time cutover is still pending (#771). The **`VM_ANALYSIS_FOOTPRINT_GB_MAX=50` off-VM routing rule is UNCHANGED** — the quota is a containment BACKSTOP, not a permission slip.
- Per-experiment HF download caches (`data/issue_<N>/hf_dl/` + `g*_dl/` — in the repo-root `data/` AND the issue worktree) are RE-DOWNLOADABLE, cleaned automatically at `/issue` Step 8 (after upload-verification PASS) via `uv run python scripts/clean_experiment_downloads.py <N> --apply` (sweeps both copies). **NEVER delete `store/` or `eval_results/`** (repo-root OR worktrees) — durable artifacts, not caches. **(#911)** both janitors ALSO sweep non-canonical issue-keyed staging caches (top-level `/tmp/` `i<N>*`/`issue<N>*`/`*_<N>` dirs + `data/` `issue…<N>…{_dl,_hfstage,_cache}` dirs) under the same contract plus a 48 h recently-touched keep, a nested-durable block, and a positive re-downloadability-evidence requirement; kill switch `EPM_SKIP_NONCANONICAL_CACHE_SWEEP=1`.
- **Incremental (between-phase) cleanup for multi-phase runs.** Step-8 cleanup fires only at experiment END, so a multi-phase run reaps each CONSUMED phase's cache BEFORE the next phase downloads more — `uv run python scripts/clean_experiment_downloads.py <N> --incremental --apply` (same safety contract; no terminal-status gate; "CONSUMED" = no LATER phase or provision reads it — enumerate every later consumer before placing the reap, #1489). Bounds PEAK footprint only: a single phase estimated over **50 GB** (`VM_ANALYSIS_FOOTPRINT_GB_MAX`) must be ROUTED off the VM at plan time (`intent: cpu-bigmem` or streaming; `planner.md` §9, `critic.md` item 10; #658).
- Fleet-wide backstop for caches that escape Step 8: the **`vm_disk_guard.py` cron** (`scripts/cron_vm_disk_guard.sh`). Over **85%** `/` usage (`EPS_VM_DISK_THRESHOLD`) it runs tiered safe cleanup — `uv cache prune`; TERMINAL-status issues' `hf_dl`/`g*_dl` + #911 non-canonical caches (ACTIVE issues never touched, only attributed); stale logs; age-gated pod-style + HOME HF hub cache reaps incl. a size-cap arm (`EPS_VM_HOME_HF_CACHE_CAP_GB`, default 50 GB; #1376/#1377/#1450) — then escalates loud (Telegram + sidecar) if still over. Report-only by default; the cron passes `--apply`. Since #1392 the watcher's sub-floor arm launches a detached single-flight `--apply` run when `/` free drops below `EPM_VM_DISK_SUBFLOOR_GIB` (kill switch `EPM_DISABLE_SUBFLOOR_RECLAIM=1`). A SECOND, ESCALATE-ONLY pass watches `/mnt/eps-data` (#681; terminal-cache reap + escalation only; skipped when the mount is absent). Full predicates: `.claude/rules/background-automation.md`.
- **Scheduled `uv cache prune` (idle-time cron).** The global uv package cache grows unbounded; `scripts/cron_uv_cache_prune.sh` runs `uv cache prune` — which KEEPS in-use entries (NOT `uv cache clean --force`) and is graceful when the cache lock is held — daily off-peak, so `vm_disk_guard` rarely fires on a full disk. Registered via the orchestrator's cron management.
- **Active-task escalation — warn-only, NEVER auto-deletes active data (#679).** Three channels surface a band-worthy ACTIVE-task cache without deleting it, all writing `.claude/cache/disk-guard-events.jsonl`: (a) the guard's tier-(b) kept-branch escalation (push + sidecar row naming the task, largest cache path, footprint, and the safe post-run reclaim command; deduped per (task, band), ack-sentinel suppress); (b) the watcher sub-floor sentinel (for `/mnt/eps-data` a SIZE-INVARIANT percent threshold, `EPM_VM_DATA_DISK_SUBFLOOR_PCT` default 85%, attributing worktree-internal caches via `repquota -P`); (c) `clean_experiment_downloads.py`'s nested-`store/` parity guard (SKIPs, never deletes, a mis-rooted `store/` not verifiably mirrored on HF).
- **VM-root preflight floor (#679).** Preflight WARNs when `/` is >90% used or <20 GB free, AND HARD-FAILs (`report.ok=False`) when VM-root free is below `EPM_PREFLIGHT_DISK_FLOOR_GB` (default 40 GB) — a fresh launch below the floor fails fast rather than starting near the silent-Bash-failure regime (RunPod `/workspace` exempt — the EDQUOT quota probe is binding there). Override a deliberate low-disk launch with `EPM_PREFLIGHT_DISK_FLOOR_OVERRIDE=1` (degrades to a logged WARN). Both point at `vm_disk_guard.py --apply`.
