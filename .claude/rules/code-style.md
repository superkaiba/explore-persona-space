# Code Style

(Plan-handoff and "all code changes on the local VM, never on pods" stay in
CLAUDE.md as always-on rules; the rest live here and load when you touch code.)

- **Lint:** `uv run ruff check . && uv run ruff format .` (line-length=100, py311, select E/F/I/UP).
- **PostToolUse ruff strips unused imports.** The auto-fix runs after every Edit and removes a just-added import if it isn't referenced yet (F401) — costing a re-add round. Add the import together with its first usage in ONE edit, or add the usage first.
- **Packages:** always `uv` (not pip/conda). Config via Hydra (not argparse). Track with `wandb`.
- **Plot fonts (Inter):** `bash scripts/install_inter.sh` once on the dev VM; pods get it via `bootstrap_pod.sh`. Fallback DejaVu Sans.
- **Tensor-shape asserts at boundaries:** `assert logits.shape == (B, T, V), logits.shape`.
- **Vectorize torch ops** — `einops.rearrange`/`einsum`, masked gathers, scatter. No Python loops over tensor dims.
- **Compute-throughput discipline (GPU experiment scripts).** Batch data-parallel model forwards — never a Python loop of batch-1 forwards (a 7B bf16 batch-1 forward is weight-bandwidth-bound and leaves the GPU ~idle). Keep large-tensor reductions GPU-resident and transfer only the reduced scalars/summaries to CPU — never ship `(seq × vocab)`-scale fp32 tensors over PCIe for a CPU-side reduce. Before launching any run estimated >12h, sanity-check the estimate against the FLOPs floor (`n_forwards × 2 · params · tokens_per_forward / sustained GPU FLOPs`): an estimate >5-10× over the floor means the implementation is leaving throughput on the table — fix it before launch, don't book more pod-days (#522: ~94h on 1× H100 for a ~4-6h-floor job — 409,600 batch-1 forwards with full-vocab log-softmax shipped to CPU for a per-position reduce; #511: 52× CPU wall-time blowup vs its plan estimate from a full `eigh` on a 2N×2N joint Gram). Keep per-row IO out of the inner loop: never run compression/serialization/upload per row when it rivals the row's compute — write the cheap format per row and compress/upload out-of-band or batched (#813: `np.savez_compressed` 103.8s = 65% of the ~160s wc_long row wall-time; plain `savez` 1.2s at 1.29× size, Xet dedup already −59% on upload). And make multi-worker dispatchers work-conserving — idle worker + pending independent cell ⇒ dispatch; no strict wave/stage barriers and no serial scheduling of independent cells on a multi-GPU provision without a plan-stated cross-cell dependency or named resource/capacity constraint (#813: two sequential waves idled 4/8 H100s for 6.7h; #778 phase-3: 25×3 cells looped serially on 8×H100).
- **Verification gates test the live dispatched path (#779).** A `--verify-X` / equivalence / vectorization gate must assert on the exact function(s) the entrypoint actually dispatches for the gated stage — establish the link by identity (`gated_fn is dispatched_fn`, or `__module__` + `__qualname__` match) or a call-graph grep from the entrypoint to the gated callee. A gate that exercises an unused sibling helper is a hollow gate — green PASS, zero coverage of the hot loop — and a substantive review blocker (`hollow-verification-gate`, `.claude/agents/code-reviewer.md` Step 0.68). #779: `--verify-vectorized` ran `vectorized_mlp_skill.assert_matches_reference()` (an UNUSED helper's self-check) while the dispatched ridge hot loop (~17k fits) ran the unvectorized 18-20h path; the launch note claimed "vectorized" on the green gate. Equivalence-gate recipe (seeded serial oracle, 2-3 cells, stated float tolerance): `.claude/rules/vectorize-many-cell-fits.md`.
- **One production-body test per seam-stubbed function (#906).** For every production function you
  ADD (or whose body you MODIFY) that any test stubs / monkeypatches / fakes out —
  `monkeypatch.setattr(..., "<name>", ...)`, `unittest.mock.patch("...<name>")`, a seams/hooks
  dataclass field overridden with a fake, a fake injected through a resolver/dispatch table — ALSO
  commit at least ONE test that EXECUTES the real body and REACHES its external call sites +
  attribute dereferences. Fakes in that test are permitted ONLY at the external
  GPU/API/network/filesystem boundary and MUST be signature-conformant BY CONSTRUCTION:
  `unittest.mock.create_autospec(real_callee)`, a real dataclass instance, or a fake whose `def`
  mirrors the real signature. A bare `Mock()`/`MagicMock()` boundary fake accepts ANY call and is
  NOT body evidence; a dispatch/resolver test that asserts the dispatcher called the name
  is NOT body coverage. The obligation closes TRANSITIVELY over round-added callees (the
  Step 3.8 trigger set): when the stubbed function's body calls OTHER functions you added or
  modified this round, the committed body-executing test must ALSO reach those callees' external
  calls + dereferences (or each such callee, when itself stubbed, joins the obligation) — a
  crash-class body must not escape by moving one call deeper (#906's seam-stubbed `run_pilot` →
  round-added `_score_items`). And in ANY test offered as body coverage of an added/modified
  function, a patched CALLEE must itself be signature-conformant (autospec'd / a real dataclass
  instance), never bare `Mock()` — even when that callee is an unmodified repo helper. This is
  the producer-side mirror of `code-reviewer.md` Step 3.8 / review
  principle 16 — write the test the reviewer will demand, or eat the Critical + re-roll round
  (incident #906: five ensemble rounds shipped crash-class bodies behind `PilotSeams` stubs — a
  nonexistent dataclass-field dereference, a fabricated judge-call signature, missing required
  kw-only args — while 43/43 mocked tests stayed green). Field practice agrees: mocks drift from
  the code they imitate unless constrained (Google Testing Blog "Don't Overuse Mocks" 2013 /
  "Increase Test Fidelity By Avoiding Mocks" 2024; Python `autospec`). Named residue: even an
  autospec'd fake validates call SHAPE, not provider-side request semantics — a
  never-live-executed API-builder seam additionally needs the live probe in
  `.claude/rules/gotchas.md` (the #906 r11 entry).
- **Shared-VM CPU thread caps (#847).** `orchestrate.env.load_dotenv()` setdefaults `OMP_NUM_THREADS`/`MKL_NUM_THREADS`/`OPENBLAS_NUM_THREADS`/`NUMEXPR_NUM_THREADS` to 8 on the SHARED VM only (positive detection: `/mnt/eps-data` mounted or hostname `cia-benchmark-vm`; fails open on pods/GCE/SLURM). An uncapped torch/BLAS job holds ~32 runnable threads on this box (torch intra-op defaults to physical cores = 16; BLAS/inter-op add the rest); 5-6 concurrent jobs drove load to 186-226 on 2026-07-02 while each realized only ~5-6 cores. Ad-hoc / smoke / free-analysis VM launches — and EVERY VM-side launch from an issue worktree — MUST carry the caps inline (`OMP_NUM_THREADS=8 MKL_NUM_THREADS=8 OPENBLAS_NUM_THREADS=8 NUMEXPR_NUM_THREADS=8 uv run python ...`): a worktree's `env.py` is pinned to its branch point (the Step 5a spec-freshness sync deliberately excludes `src/`), so the setdefault may be absent there entirely, and even a current `env.py` cannot in-process-cap a torch-before-dotenv importer (#891/#779). Pod/GCE/SLURM launches never carry the prefix. Overrides, strongest last: explicit env at launch (setdefault never clobbers), `EPS_VM_THREAD_CAP=<n>` (`0`/empty disables), per-script `torch.set_num_threads(...)` (takes precedence over env — e.g. `scripts/issue779_layer_sweep.py:491`, `analysis/vectorized_mlp_skill.py:224`). Torch freezes its pool from `OMP_NUM_THREADS` at IMPORT — call `load_dotenv()` before importing torch (repo entrypoints already do; enforced for new VM entrypoints by `tests/test_shared_vm_thread_caps.py`); the setdefault still caps every subprocess regardless.
- **Stream-reduce N large per-context blobs from HF — never materialize the whole grid locally.** An analysis that reads N multi-GB per-context `.pt` blobs from an HF dataset repo (answer-span stores, cached per-context activations, per-context attention dumps) MUST use the canonical per-context stream-reduce source `_HfStreamSpanSource` (`scripts/issue658_fit_predictors.py`) — download one context, reduce it, delete it; peak footprint is ~one context (bounded by its LRU `cache_size`, default 1), NEVER the full N×blob-size grid — and run it behind the `_assert_attn_stream_equivalence` gate (a 2-3-context streamed-vs-local toy check that fails fast before any sweep if streaming changed the DV). The local-dir source `_SpanSource` (download every context first) is correct only when the whole grid genuinely fits the per-task disk quota; N × multi-GB does not. For non-`.pt` per-context formats (e.g. `.npy` activation dumps, `.safetensors` shards), reuse the stream-reduce PATTERN — download one ctx → reduce → delete, LRU `cache_size=1` — rather than `snapshot_download`-ing the whole grid; the helper itself is `.pt`-specific (`torch.load`) and a non-`.pt` analogue needs an adapted loader. Concretely: do NOT `snapshot_download` an `answer_spans/` prefix or loop `hf_hub_download` over all N contexts into a persistent cache — that refills the shared VM disk (#761 would have re-downloaded 220 GB of UltraChat answer spans — 4.4 GB × 50 contexts — into a local cache, refilling `/`, before the HF cache was relocated to `/mnt/eps-data` mid-bootstrap; the existing `_HfStreamSpanSource` already bounds peak to one context). New per-context HF span/activation analyses reuse this helper (or the pattern for non-`.pt`) rather than writing a fresh all-local download loop. Note: planner.md §9 "Data-footprint carve-out" is the *plan-time* routing backstop (route a >50 GB phase off-VM); this bullet is the *code-write-time* prevention (don't materialize the grid at all).
- **Docstring-on-edit:** touching a docstring-less function → add a short one (what + returns/asserts).
- **No dollar-budget caps in experiment scripts.** Never a `max_budget_usd` threshold that raises `SystemExit` mid-experiment (it lost 3 of 4 sources in #356). Log cost telemetry; set billing alerts at the account level. Enforced by `tests/test_no_dollar_budget_caps.py`.
- **Checkpoint per phase; never accumulate-in-memory and write-at-end.** Any multi-phase / multi-domain / multi-condition / multi-seed path MUST persist each phase's output the moment it completes — covers top-level dispatchers AND per-seed eval rigs that chain multiple framework loads (e.g. vLLM gen → logprob on checkpoint → logprob on base). The anti-pattern `results = []; for phase: results.append(...); write(results, path)` turns ANY downstream crash into total data loss for all earlier phases. Acceptable: per-phase files, append-mode idempotent re-runs, per-phase HF/WandB uploads, or load-partial-and-skip-completed at entry. **Intra-phase grain for long loops:** the same law applies INSIDE a phase — any serial/looped fit/solve/eval/generation stage over independent units (cells, arms, layers, folds, seeds, draws, rows) whose projected wall-time exceeds ~1h (count × per-call cost, per the plan §9 sizing or the implementer's own wall-time projection) MUST persist each unit's result the moment it completes — atomic append to a JSONL (write-tmp + `os.replace`, or single-line `O_APPEND` writes) or per-unit files + a done-sentinel — AND implement a resume predicate that loads partial results at entry and SKIPS completed units, keyed on EVERY output-affecting regime key (args/config that change the output are part of the key; a resume that ignores a `--method`-class flag silently reuses wrong cached rows — #722 r3). **External-stream presumption:** the ~1h floor is PRESUMED met by any loop consuming an external streaming source (HF `datasets` `streaming=True`, API pagination, web harvest, S3/HTTP row iteration) whose scanned-row count exceeds ~10^4, is unknowable in advance (yield-dependent keep-quota stop — scan until N kept), or is an intentionally unbounded full-corpus pass — checkpoint per chunk + fingerprint-gated resume REGARDLESS of projected wall-time; network-bound walls are not sizeable from count × per-call cost (#1092: a ~ms-kernel LMSYS/WildChat full-corpus stream ran 3h06m, ~1.8M rows scanned, and lost the whole in-memory kept pool to a downstream KeyError; reference impl `scripts/issue1092_build_corpus.py::_stream_with_cache` — atomic pool file first + meta sidecar last, exact-fingerprint resume keyed on dataset revision + every filter/recipe constant). A short bounded fetch (known ≤~10^4-row scan, fixed stop) is exempt. Vectorize FIRST (`.claude/rules/vectorize-many-cell-fits.md` — "no per-cell checkpoint; output only at the very end" is one of its diagnostic signatures); whatever loop remains above ~1h after batching checkpoints intra-phase. The ~1h floor matches the standing stop-and-vectorize line (CLAUDE.md compute-character pre-launch statement). This generalizes the judge-loop checkpoint/resume bullet below to every long loop. Incident #823 phase 4: `run_823.py::phase4_ridge_refit` accumulated ~20h (unpatched; ~3.7h patched) of serial ridge fits in memory with ONE terminal JSON write — every crash forfeited the whole loop, and a user-directed restart-with-optimization was refused (decision flipped to RIDE) solely because restart forfeits unpersisted fits; five code-review rounds never flagged it. Review-side gate: `.claude/agents/code-reviewer.md` Step 3.6.
- **Model call vs code (3.0 paradigm):** before writing any classifier/extractor/parser/summarizer/rule-based judge over unstructured data, evaluate a single Claude Haiku/Sonnet call. If ≥80% covered at acceptable latency/cost, prefer it. Document the choice + rejected alternative in the implementer report + planner §4.
- **Never hardcode an invented Claude/Anthropic model id.** The judge default is `claude-sonnet-4-5`; canonical ids live in CLAUDE.md / the global `claude-api` skill. A `*-20251001` suffix is **Haiku 4.5**, not Sonnet — do not graft a date suffix onto a Sonnet id. Verify any hardcoded model string against the canonical list before committing; a wrong id crashes the run at the first API call (#489 Phase 0a, 2026-06-04). **The judge for ALL behaviors (incl. sycophancy + EM) is `claude-sonnet-4-5-20250929`** (standing rule, CLAUDE.md) — do not re-pin Haiku/gpt-4o for new work; route large judge sets through the Anthropic Batch API.
- **Judge / API-call retry wrappers treat 529 Overloaded as transient by default.** The transient tuple is `(APIConnectionError, APITimeoutError, RateLimitError, anthropic.InternalServerError)` PLUS explicit 529 handling — 529 `OverloadedError` is NOT a top-level SDK symbol (`anthropic.OverloadedError` raises AttributeError) and is NOT an `InternalServerError` subclass in the installed SDK (anthropic 0.88.0: MRO `OverloadedError → APIStatusError`), so catching `InternalServerError` does NOT cover it — catch `anthropic._exceptions.OverloadedError` (or `APIStatusError` with `status_code == 529`) explicitly (`llm/api_dispatch.py`'s tuple currently misses it — sibling fix pending; `.claude/rules/llm-judging.md` rule 24). Also harden long judge loops with checkpoint/resume + a per-row `judge_failed: true` audit flag instead of crashing the whole launcher on one bad row (incidents #556: ~97 OverloadedErrors crashed a 4400-judgment phase; #528: three distinct judge crashes — empty response SystemExit, one soft-refusal row, one JSONDecodeError).
- **WandB live training metrics are mandatory.** Any training-config builder under `src/explore_persona_space/experiments/` (`TrainLoraConfig`, `SFTConfig`, `TrainingArguments`) MUST emit to WandB during training — loss curves, grad-norm history, and callback metrics cannot be reconstructed post-hoc. Do NOT set `report_to="none"` / `report_to=None` / `report_to=[]` without an explicit `# WANDB_INTENTIONALLY_DISABLED: <reason ≥ 10 chars>` comment on the same line or the immediately preceding non-blank line. The waiver is a justification, not a token bypass; if you cannot articulate a real reason in ≥10 chars, you should not be disabling it. Issue #496 trained 12 cells with `report_to="none"` hardcoded and the missing telemetry surfaced only at upload-verification (Step 8). Enforced by `scripts/workflow_lint.py --check-wandb-required` (bundled into the no-flags default run).
- **Persona injection:** ALWAYS system prompt `{"role": "system", "content": "<persona>"}`. Never user/assistant turns.
- **Always run with `nohup`; VM-side long compute detaches with `setsid` too.** Pod-side (any
  launch over SSH MCP): use the canonical setsid launcher-script pattern in
  `.claude/agents/experimenter.md` § "During Execution" — launcher at
  `/workspace/launch_issue_<N>.sh` (env-source + pidfile inside), launched via
  `setsid nohup bash <launcher> > <log> 2>&1 < /dev/null &`; NEVER bare `nohup ... &` or a
  top-level `source .env` (the SSH-MCP shell is `sh` — `source: not found`, #545; SIGHUP
  reaping, #444/#541). VM-local short form for trivial background runs:
  `nohup env OMP_NUM_THREADS=8 MKL_NUM_THREADS=8 OPENBLAS_NUM_THREADS=8 NUMEXPR_NUM_THREADS=8 uv run python scripts/train.py &`.
  Any VM-LOCAL compute phase >~15 min launched directly
  from an /issue session (Phase-D-style fits, aggregation batteries) MUST fully detach —
  `PHASE_PID=$(bash -c 'setsid nohup env OMP_NUM_THREADS=8 MKL_NUM_THREADS=8 OPENBLAS_NUM_THREADS=8 NUMEXPR_NUM_THREADS=8 <cmd> < /dev/null >> <abs log> 2>&1 & echo $!')` — because a
  plain bg-Bash child shares the session's kill domain and dies with a watcher force-stop (#833,
  2026-07-02: a healthy ~2h fit killed mid-flight); the `bash -c` wrapper makes `$!` the workload
  pid (a bare top-level `$!` after `setsid … &` is the vanished intermediate). Immediately after
  the pid verify, protect from earlyoom collateral kills:
  `bash -o pipefail -c 'pgrep -s "$1" | xargs -rn1 sudo -n choom -n -600 -p' _ "$PHASE_PID"`
  (session-wide; children inherit; −600 not −1000 so a runaway fit still dies first; pipefail
  makes an empty/failed pgrep FAIL the sweep — `choom=ok` only when the sweep pipeline exited
  zero; on any failure proceed unprotected and record `choom=failed`).
  Record `pid=$PHASE_PID` + the log path + `choom=ok|failed` in the stage-dispatch breadcrumb
  (SKILL.md § Detached VM-side long compute phases — incl. the collateral-kill signature and the
  relaunch-once-then-pod-pivot rule; #811).
- **Env sync after dep changes:** `uv lock && git push`, then `pod.py sync env`.
- **HF cache** always `/workspace/.cache/huggingface` on pods (symlinks enforce).
- **Reproducibility metadata in result JSONs:** git commit hash, env versions, timestamps.
- **Supersede → delete the old version.** When an improved version of a script
  / helper supersedes an old one, DELETE the old version after rewiring every
  reference to it — do NOT keep both. Two live scripts that do the same job
  rot: the next reader can't tell which is canonical, greps hit the stale one,
  and a future change patches the wrong file. Rewire-then-delete in the SAME
  change. Worked example: `scripts/issue722_vectorized_skill.py` (vectorized,
  50-100x faster) supersedes `scripts/issue722_skill_over_mean.py`; once the
  vectorized driver lands on main the slow one is deleted, not left beside it.
