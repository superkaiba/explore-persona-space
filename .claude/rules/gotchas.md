# Gotchas

- HF Trainer monkey-patch in `train/trainer.py` — fragile; breaks if `Trainer.__init__` changes.
- Hard-coded library paths in `orchestrate/env.py` — cluster-specific.
- **`gcloud` lives at `/snap/bin/gcloud` on this VM, and `/snap/bin` is on PATH only in LOGIN shells** — `/etc/profile.d/apps-bin-path.sh` prepends it during login-shell profile evaluation; nothing shell-agnostic (`~/.bashrc` inheritance to non-login children, cron `PATH=`, `env`-launched subprocesses, Bash-tool one-liners, `subprocess.run` with no shell) picks it up. A non-login shell running `gcloud compute instances list --configuration=eps-gcp` hits rc=127 with the empty inventory on STDOUT and the diagnostic on STDERR — a caller treating rc=127 as "empty" mis-reports zero live GCE instances and silently green-lights a money-spending surface. RULE (read-side): a non-zero rc from any `gcloud` list is UNKNOWN, never an empty inventory — reconcile via another route (router state, `epm:backend-selected` markers, a login-shell probe) or surface UNKNOWN. RULE (write-side, primary): prepend `/snap/bin` to PATH (`export PATH="/snap/bin:$PATH"; gcloud ...`, or the child env dict) or invoke via `bash -lc 'gcloud ...'`. Same class as the `uv lives in ~/.local/bin` login-only PATH trap.
- **`gcloud billing` reads fail `PERMISSION_DENIED` under the `eps-gcp` configuration** — the project service account (`eps-router@...`) cannot list billing accounts (Cloud Billing API not enabled; project 796887979789). Run billing/credits reads under Thomas's personal account instead: `gcloud billing accounts list --account=thomasjiralerspong@gmail.com` (the SA path is compute-only — enabling cloudbilling.googleapis.com is an account mutation for Thomas to decide).
- **`CMD -c ... || echo 0` double-prints — count-keyed equality gates never fire.** `pgrep -c` (and `grep -c`) PRINT `0` AND exit non-zero when nothing matches, so an `|| echo 0` fallback fires too and the captured value becomes the two-line string `"0\n0"`; any `[ "$X" = "0" ]` gate then never matches — failing OPEN, worst in liveness / resource-release / termination guards (#1773). Fix: `X=$(CMD -c ... 2>/dev/null || true); X=${X:-0}` — the `|| true` neutralizes the non-zero status WITHOUT printing (survives `set -e`/`pipefail`, where a bare capture kills the script at its first empty probe); `${X:-0}` then covers only genuinely-empty output. Wrapped invocations (`ssh "..." || echo unknown`): the `|| true` must sit REMOTE-side — a propagated rc fires the OUTER fallback and reproduces the two-line value. Diagnose with `cat -A` — the captured value shows as two physical lines.
- **`pgrep`/`pkill` without `-f` matches the EXECUTABLE NAME only — an argv-resident distinguishing string silently under-matches and reads LIVE as DEAD.** `pgrep -c "[i]ndex-pack"` returns 0 while `git index-pack` runs (executable is `git`); same shape for script names (`bash my_script.sh`), git subcommands, and forked-worker cmdline literals (`VLLM::EngineCore`). Distinct from the `-c || echo 0` entry above (exit-status + count printing) — here something IS running but `-f` was omitted, so a liveness/ownership probe reads clean and the guard concludes "dead, safe to reap." RULE: any probe whose distinguishing string is not the executable name uses `pgrep -af '<pattern>'` (`-f` scans the FULL argv). COROLLARY (kills, not probes): never key a KILL on a zero count alone — zero is what both "genuinely dead" and "mis-probed via missing -f" look like (#1739: `procs=0` ×3 while `git index-pack` ran). Key kills on absent POSITIVE progress evidence (output-byte growth over a window, lock-file mtime stability past a threshold, a heartbeat-refreshed pid-file) — and for a process class idle by design between events (daemon, poller, end-of-run writer), "no byte growth" is not death evidence: combine with a positive-liveness probe (`pgrep -af`, `kill -0 <pid>`) first. The bracket idiom (ownership-probe entries below) solves the DIFFERENT self-match problem and assumes `-f` is already present.

- **`+gpu_id=N` Hydra override required for multi-GPU parallel training launches.** `train/sft.py` sets `os.environ["CUDA_VISIBLE_DEVICES"] = str(cfg.gpu_id)`, clobbering any env `CUDA_VISIBLE_DEVICES` (default `0` → all parallel jobs on GPU 0 → OOM). Pass `+gpu_id=N` per process (the `+` is required — `gpu_id` isn't in the default schema).
- **The in-process `CUDA_VISIBLE_DEVICES` clobber is silently defeated by any import-time cuInit — parallel per-GPU launches must ALSO pin it in the LAUNCHER environment.** The driver freezes its device list at the FIRST cuInit in the process (`import peft` is a known offender); a later `os.environ["CUDA_VISIBLE_DEVICES"] = str(cfg.gpu_id)` (`train/sft.py`) is a driver-level no-op and every process's `cuda:0` resolves to physical GPU 0 — parallel cells co-locate and OOM. Neither `torch.cuda.is_initialized()` nor `torch.cuda.device_count()` proves the pin took (both read the clobbered env, not driver state). RULE: export `CUDA_VISIBLE_DEVICES=<gpu>` per cell in the launcher environment before exec, keeping the matching `--gpu`/`+gpu_id=<gpu>` arg (`_apply_cvd_pin` makes an inherited single-GPU pin authoritative; a contradictory nonzero `gpu_id` fails loud) — never rely on the in-process clobber alone. Signature: all parallel cells OOM on ONE physical GPU whose OOM message lists every sibling PID (#543, #545). Enforcement: `experimenter.md` Before Running step 10; `tests/test_cvd_wave_assignment_smoke.py`; `workflow_lint.py --check-dispatcher-cvd-pin` (waive with `# CVD_PIN_EXEMPT: <reason>`).
- **Hand-launching a dispatcher-managed per-cell GPU worker MUST replicate the dispatcher's launcher-env pins — in this worker CLASS, `--gpu-id` alone selects NOTHING.** The manual-relaunch sibling of the entry above: launcher-pinned workers treat `--gpu-id` as informational — `scripts/issue667_extract.py::_device` IGNORES it and returns `cuda:0` unconditionally ("CVD pins the physical GPU in the launcher env"); the physical GPU is selected ENTIRELY by the `CUDA_VISIBLE_DEVICES=<g>` the dispatcher sets in the child env (exemplar: `scripts/issue664_dispatch.py::_cvd_env`). Recognize the class by a launcher-env comment on `_device()`, a "CVD-pinned by the launcher" help string, or a per-cell builder setting `env["CUDA_VISIBLE_DEVICES"]`. NOT all scripts are in the class — others HONOR `--gpu-id` as a device index (`scripts/issue666_corpus_extract.py`) or as an in-process CVD set, and applying the class shape there itself crashes (`cuda:<g>` is an invalid ordinal when CVD leaves one visible device). RULE: before composing ANY manual launch of a dispatcher-managed worker, READ the dispatcher's per-cell command builder AND the env dict it returns and replicate EVERY pin (CVD is not always the only one — `VLLM_WORKER_MULTIPROC_METHOD=spawn` rides the same dict): `env CUDA_VISIBLE_DEVICES=<g> uv run python scripts/<worker>.py ... --gpu-id <g>`, one distinct `<g>` per parallel worker. Signature of a bare-`--gpu-id` hand-launch: every worker's engine initializes on the busy DEFAULT GPU and crashes at vLLM init_device (#813) — distinct from the co-locate-then-OOM signature above (which needs workers to get far enough to allocate). The `--check-dispatcher-cvd-pin` lint covers only committed `scripts/*.sh` launches; this prose rule (the LESSONS.md hand-launch trigger) is the ONLY guard for hand-typed commands.
- **The library-train seam clobbers a correct launcher CVD pin whenever `gpu_id` is left at its default — `train_lora` / `merge_lora` (`src/explore_persona_space/train/sft.py`) export `os.environ["CUDA_VISIBLE_DEVICES"] = str(cfg.gpu_id)` (default `0`).** The library-call member of the CVD family (siblings: the `+gpu_id=N` Hydra-override entry — same clobber line, reached via the Hydra CLI where the matching override IS the fix; the import-time-cuInit entry; the hand-launch entry). Shape (a) — worker: the clobber runs BEFORE cuInit so it TAKES; cells co-locate and OOM-fan-out while sibling GPUs idle (#1090 fu3). Shape (b) — dispatcher-poisoning: in-process training poisons the DISPATCHER's own env, so a later multi-GPU compose reads `torch.cuda.device_count() == 1` and composes `--num_processes 1` against a multi-GPU ZeRO-3 yaml, and `env={**os.environ}` propagates `CVD=0` into children (#1112). RULES: (i) library callers thread `gpu_id=<slot>` to MATCH the env pin — never default 0 under a nonzero pin; (ii) a dispatcher that later composes multi-GPU launches never calls `train_lora` in-process — subprocess-isolate the training, snapshot CVD at import, and enumerate GPUs via an `nvidia-smi` subprocess (never `torch.cuda.device_count()`); (iii) sharded world size comes from the accelerate yaml's `num_processes`, never a clobbable runtime count. `_apply_cvd_pin` (both call sites) makes an inherited single-GPU pin authoritative and a contradictory nonzero `gpu_id` fail LOUD; an unset/empty/multi-GPU env keeps the legacy `+gpu_id=N` contract (#376). Signatures: (a) OOM fan-out listing sibling PIDs with N-1 GPUs idle — cells allocate, then OOM; (b) a multi-GPU compose "sees 1 GPU" after any in-process training earlier in the same process. EXPLICIT-narrowing sibling: the smoke-width entry below (#1315/#1333).

- **Smoke/production parity includes PROCESS WIDTH — a smoke that narrows a ZeRO-3 full-FT launch to `--num_processes 1` OOMs deterministically at the FIRST optimizer step, and a parent dispatcher's narrow-smoke pin is HOST-scoped, never clone-portable.** Single-process ZeRO-3 shards nothing: 7B bf16 weights + grads + fp32 Adam moments (~86 GB) land on ONE 80 GB GPU, and because optimizer states allocate lazily the smoke sails through load + forward/backward and dies at the first optimizer step (signature: `exp_avg_sq` alloc failure in DeepSpeed `stage3.py _optimizer_step`). EXPLICIT-narrowing member of the CVD/width family — the library-train-seam entry's shape (b) above is the DERIVED-width variant; here the narrowing is a deliberate `if cfg.smoke: return 1` that was correct on the parent's 1-GPU host and wrong on the clone's 4× A100-80 pod (#1315; RECURRED same day in #1333). Smoke narrows STEPS / CELLS / GRID — never the process shape, unless the smoke HOST genuinely differs. RULES: (i) when cloning ANY dispatcher, audit every smoke-mode branch that composes launch width or CVD — keep production width, fail LOUD on an under-provisioned host (never silently narrow); (ii) pin the width with an arg-composition regression test asserting the composed `--num_processes <N>` + CVD in BOTH smoke and production modes (exemplar: `tests/test_issue1333_dispatch.py::test_ft_launch_width_smoke_invariant`); (iii) diagnosability sibling: a dispatcher's subprocess wrapper MUST echo the inner log's tail (~120 lines) into the MAIN workload log on child failure — on the GCP lane only `workload.log` is crash-persisted, so an inner log dies with the instance. - **Smoke/production parity includes GATE CALIBRATION — a kill-criterion gate calibrated at production n (a ±tol anchor-reproduction/parity check, an absolute yield floor) is structurally unsatisfiable at smoke n and deterministically kills the smoke leg.** The PASS_UNIFIED convention runs the IDENTICAL chain at tiny n (smoke IS sweep with one cell — `.claude/skills/issue/SKILL.md` Step 6d.0), so any verdict whose satisfiability depends on production n fires spuriously there: a ±0.02 anchor-reproduction check at n=8 measures n, not correctness; an absolute yield floor above the smoke yield rc-halts the very phase the smoke exists to exercise. Sibling of the PROCESS-WIDTH entry above (#1315/#1333) — there the smoke branch narrows the LAUNCH shape; here the launch is correct and a plan-registered VERDICT is evaluated at the wrong scale. RULES: (i) thread the smoke flag into EVERY gate-bearing phase, not only the sizing knobs; (ii) run the gate's COMPUTATION identically but demote production-n-calibrated verdicts to informational log lines under smoke; (iii) size smoke yield floors so any NONZERO yield proceeds; (iv) production halt paths stay byte-untouched and unit-pinned (fails-at-production-shape tests cover the halt branch the smoke no longer exercises). Signature: the smoke leg rc-halts INSIDE a gate/floor check whose threshold is visibly production-scale while the identical chain at production n would pass (#1345 r3). Agent-memory sibling: `.claude/agent-memory/experiment-implementer/feedback_smoke_scale_gates.md`.
- **Smoke/production parity includes SLICE ARITHMETIC — a post-smoke artifact floor (checkpoint/step count) satisfied only under an ASSUMED smoke row cap dies whenever the REALIZED yield comes in smaller; derive the smoke dial (epochs/steps) from realized n_rows, never from the cap.** A smoke input slice is capped, not guaranteed: an upstream generation/filter phase can yield far below the cap, and a smoke training dial sized against the cap comment under-produces the very artifacts the post-smoke gate asserts (#1489: cap 30, realized 2; 1 optimizer step → 1 checkpoint against a `>=2` gate, dying AFTER every phase exited 0). The DUAL of the GATE-CALIBRATION entry above (#1345): there the gate floor is production-n-calibrated and structurally unsatisfiable at smoke n (fix = demote the verdict under smoke); here the floor is legitimate AT smoke n and the DIAL was sized on an assumed slice (fix = derive the dial, keep the gate). RULES: (i) compute the smoke dial from realized arithmetic at the point the realized count is known — `steps_per_epoch = max(1, ceil(n_rows / effective_batch))`, `epochs = max(1, ceil(K / steps_per_epoch))` with K = the gate's artifact floor — never from a row-cap comment; (ii) production geometry stays byte-untouched (the derivation lives in the smoke branch only); (iii) pin with a fails-pre-fix arithmetic test PLUS a tiny-real leg that runs the UNMODIFIED smoke geometry end-to-end and asserts the checkpoint dirs exist ON DISK. Signature: the smoke leg rc-halts at a dispatch-side artifact-count assert while the training phase exited 0 with fewer optimizer steps than the sizing comment promised. Worked example: `scripts/issue1489_gpu_phase.py::_distill_train_cfg` + `tests/test_issue1489_distill_dataset.py`. Agent-memory sibling: `.claude/agent-memory/experiment-implementer/feedback_smoke_gate_realized_slice_arithmetic.md`.
- **Smoke/production parity includes REGISTRY/PANEL MEMBERSHIP — a subprocess-per-phase dispatcher child inherits NO module-level registry state, "the registrar runs somewhere" is not enough (the registered set must cover the set the phase RESOLVES), and a smoke panel SLICE that drops panel-member-only ids masks the unregistered-context seam entirely.** A subprocess-per-phase dispatcher re-imports the world per phase, so a dynamic `CONTEXTS`/trait id exists only where the CHILD registers it — a PARTIAL registrar (one id family) leaves every other resolved id registered in NO process (#1090: the smoke's 3-id slice dropped exactly the panel-member-only ids; production crashed at the first full-panel `ensure_context`). Registry-family sibling: the RESUME-loss entry below (#1315 r6 — there the registration EXECUTED and was fast-forwarded away on resume; here it never covered the ids in any process). RULES: (i) every subprocess phase entry that resolves dynamic ids calls an idempotent registrar UNCONDITIONALLY at entry, covering the FULL id set that phase resolves (panel members included), refusing to shadow a foreign binding rather than silently overwriting; (ii) the phase smoke runs in a FRESH child process (zero inherited parent state) and resolves the FULL production id set — a reduced smoke panel is legal only for ids that keep another smoke-/test-exercised registration path. Regression pattern: a fresh-subprocess test registering via the phase-entry registrar alone and resolving every production panel id cold. Signature: `ValueError: unknown context '<id>'` at the first FULL-panel resolution while the same phase's tiny-real smoke passes fresh. RULES: (i) at smoke-composition time enumerate the grid's class-defining axes and smoke the cheapest tiny cell per realized combination (unrealized combinations need no cell); (ii) class-gated READ-side / aggregation phases (panel-disjointness reads, reuse-seam loaders, per-class mix asserts) must be REACHED by the smoke set, not only the train phase; (iii) record the smoke's cell list in the smoke marker — an `epm:smoke-result` whose `cells` list is one content-class cell against a marker×`po`-bearing grid is the pre-launch red flag; (iv) added cells inherit GATE CALIBRATION (#1345): per-cell numeric gates sized to smoke n, while a registry/mix-composition mismatch an added cell surfaces is SHAPE-correct, so widening the smoke set never trips false kills. - **Smoke/production parity includes TENSOR DEVICE PLACEMENT — a CUDA-divergent branch is structurally unexercisable on a CPU-only smoke host.** On a CPU-only smoke host every tensor is cpu, so a PARTIAL device placement (some matmul participants moved to `args.device`, others left cpu by `torch.load(map_location="cpu")` producers) passes EVERY CPU smoke by construction and crashes only on the pod — often deep in a battery after co-located sibling paths ran clean (#1776: the cov family's `z @ cov_half.T` was the first cross-device mm). RULES: (i) placement is TOTAL at ONE move site at the phase/function ENTRY — rebind every tensor set onto the resolved device after all producers, before any consumer — never scattered incidental `.to()` calls; (ii) named-tensor same-device asserts immediately before cross-tensor mm chains, so a residual mismatch fail-louds naming its culprit AND doubles as the CUDA-side diagnostic at relaunch; (iii) off-pod fix-engaged evidence is LAYERED: CPU smoke rc 0 through the full body + meta-device unit pins that fail pre-fix + an explicit note that CUDA validation lands at relaunch; (iv) audit the leg's device FLOW once (tensor → load site → device at load → device at use) — `torch.load(map_location="cpu")` producers are the usual cpu leaks. - **Pilot timing gates MEASURE at the sweep's EXECUTION SHAPE (batch width / per-call structure), and a gate refusal is a DESIGNED artifact-routed halt (report JSON + distinct rc) — never a bare rc=1 the dispatcher reads as an anonymous crash.** (a) SHAPE: an in-run pilot that times serial batch-1 generate calls while the gated sweep runs B-wide batched chunks can false-fire a CORRECTLY-derived s/sample threshold by ~B× — memory-bandwidth-bound HF decode makes per-STEP latency ≈ batch-independent, so batch-1 per-sample cost ≈ B× the batched sweep's (#1415: threshold 4.7 s/sample, batch-1 pilot measured 15.67, true B=8 shape ≈2). Fingerprint: measured/true per-sample ratio ≈ B (warmup/compile overhead instead shrinks over later calls). Parity includes the MEASUREMENT's execution shape, not only the launch's. (b) HALT ROUTING: a plan-registered gate refusal is a stop criterion, not a crash — the gate writes a report JSON (measured value, threshold, batch width, verdict) and exits a DISTINCT rc the dispatcher routes like its other stop criteria; a bare rc=1 is classified as an anonymous crash and burns a launch cycle + a diagnosis round on a correctly-working gate. - **VM `earlyoom` SIGTERMs bulk in-memory tensor loads silently (NO Python traceback).** The EPS VM runs `earlyoom`: SIGTERM to the highest-`badness` process below 10% MemAvailable (~12.8 GB of 128), SIGKILL at 5% — the process dies with no traceback (the log just stops mid-progress and looks like a hang).
