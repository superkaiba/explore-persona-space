# Gotchas

- HF Trainer monkey-patch in `train/trainer.py` — fragile; breaks if `Trainer.__init__` changes.
- Hard-coded library paths in `orchestrate/env.py` — cluster-specific.
- No dataset validation in `build_phase1_dataset()` — empty QA pairs silent-fail.
- Tulu pipeline caveat: midtraining+Tulu results may not generalize to production post-training.
- **`+gpu_id=N` Hydra override required for multi-GPU parallel training launches.** `train/sft.py` sets `os.environ["CUDA_VISIBLE_DEVICES"] = str(cfg.gpu_id)`, clobbering any env `CUDA_VISIBLE_DEVICES` (default `0` → all parallel jobs on GPU 0 → OOM). Pass `+gpu_id=N` per process (the `+` is required — `gpu_id` isn't in the default schema).
- **The in-process `CUDA_VISIBLE_DEVICES` clobber is silently defeated by any import-time cuInit — parallel per-GPU launches must ALSO pin it in the LAUNCHER environment.** The driver freezes its device list at the FIRST cuInit in the process; if any import in the dispatcher chain initializes CUDA (`import peft` is a known offender — incident #545, 2026-06-11) before `train_lora`'s `os.environ["CUDA_VISIBLE_DEVICES"] = str(cfg.gpu_id)` (`train/sft.py`), the late clobber is a driver-level no-op and every process's `cuda:0` resolves to physical GPU 0 — parallel cells co-locate and OOM. Neither `torch.cuda.is_initialized()` returning `False` nor `torch.cuda.device_count()` returning the post-clobber count proves the pin took (both read the clobbered env, not the frozen driver state). RULE: export `CUDA_VISIBLE_DEVICES=<gpu>` per cell in the launcher environment before exec, keeping the matching `--gpu <gpu>` / `+gpu_id=<gpu>` arg so the in-process clobber rewrites the same value (partially superseded once #1090's `_apply_cvd_pin` lands on main: an inherited single-GPU pin becomes authoritative and a contradictory nonzero `gpu_id` fails loud — see the library-train-seam entry below) — never rely on the in-process clobber alone. Diagnostic signature: all parallel cells OOM on ONE physical GPU whose OOM message lists every sibling PID. (Incident #543 ratio-1pct-arm relaunch-2, 2026-06-10: 3 phase-1 cells with distinct `--gpu` args co-located on GPU 0 and OOM'd; a clean process honored the same late CVD set, the script's import chain did not.) Experimenter-side enforcement: `.claude/agents/experimenter.md` Before Running step 10; regression smoke: `tests/test_cvd_wave_assignment_smoke.py`; lane-independent mechanical enforcement: `scripts/workflow_lint.py --check-dispatcher-cvd-pin` (bundled into the no-flags default run) FAILs any backgrounded `--gpu-id`/`+gpu_id=` python launch in `scripts/*.sh` without a `CUDA_VISIBLE_DEVICES=` prefix on the same command — waive legitimate shapes with `# CVD_PIN_EXEMPT: <reason>`.
- **Hand-launching a dispatcher-managed per-cell GPU worker MUST replicate the dispatcher's launcher-env pins — in this worker CLASS, `--gpu-id` alone selects NOTHING.** The manual/supervisor-relaunch sibling of the entry above: workers in the launcher-pinned class treat `--gpu-id` as informational — the issue667/813 `_device()` helper (`scripts/issue667_extract.py::_device`) IGNORES it and returns `cuda:0` unconditionally on the GPU path (comment: "CVD pins the physical GPU in the launcher env") — so the physical GPU is selected ENTIRELY by the `CUDA_VISIBLE_DEVICES=<g>` the dispatcher sets in the child environment while passing the matching `--gpu-id <g>` (on-main dispatcher exemplar: `scripts/issue664_dispatch.py::_cvd_env`; branch exemplar: `issue813_dispatch.py::_cell_cmd` on the `issue-813` worktree). Recognize the class by any of: a `--gpu-id` help string like "physical GPU (CVD-pinned by the launcher)", a `_device()` that returns `cuda:0` with a launcher-env comment, or a dispatcher whose per-cell command builder sets `env["CUDA_VISIBLE_DEVICES"]`. NOT all scripts are in the class — others HONOR `--gpu-id` as a device index (`scripts/issue666_corpus_extract.py`: `device = f"cuda:{args.gpu_id}"`) or as an in-process CVD set (`scripts/issue634_extract_behavior_vectors.py`), and applying the class shape to an honoring-style worker itself crashes (`cuda:<g>` is an invalid device ordinal when CVD leaves one visible device) — which is exactly why the RULE is: before composing ANY manual launch of a worker a dispatcher normally launches, READ the dispatcher's per-cell command builder (the `_cell_cmd`-style function AND the env dict it returns) and replicate EVERY env pin it sets (CVD is not always the only one — e.g. `VLLM_WORKER_MULTIPROC_METHOD=spawn` rides the same dict): `env CUDA_VISIBLE_DEVICES=<g> uv run python scripts/<worker>.py ... --gpu-id <g>` — one distinct `<g>` per parallel worker. Failure signature of a bare-`--gpu-id` hand-launch of a class worker: every worker's engine initializes on the busy DEFAULT GPU and crashes at vLLM `init_device` / engine init (GPU already full at init — distinct from the co-locate-then-OOM signature above, which needs the workers to get far enough to allocate). (Incident #813 supervisor relaunch, 2026-07-02: 4 `issue813_run_cell.py` workers hand-launched with only `--gpu-id`; all 4 vLLM engines initialized on the busy default GPU and crashed at init_device, ~4 min lost; relaunch prefixed with `env CUDA_VISIBLE_DEVICES=<g>` succeeded.) The mechanical lint (`workflow_lint.py --check-dispatcher-cvd-pin`) covers only backgrounded `--gpu-id` launches committed in `scripts/*.sh`; a hand-typed command is not a committed file, so this prose rule (delivered by the LESSONS.md hand-launch trigger) is the ONLY guard for the manual case.
- **The library-train seam clobbers a correct launcher CVD pin whenever `gpu_id` is left at its default — `train_lora` / `merge_lora` (`src/explore_persona_space/train/sft.py:1228` / `:1590` on main) unconditionally export `os.environ["CUDA_VISIBLE_DEVICES"] = str(cfg.gpu_id)` (default `0`).** The library-call member of the CVD family (siblings: the `+gpu_id=N` Hydra-override entry — the SAME clobber line, reached via the Hydra CLI where the matching override IS the fix; the import-time-cuInit entry — where the clobber is a driver-level no-op because cuInit already froze the device list; the hand-launch entry — the manual-relaunch case): any code path that reaches `train_lora`/`merge_lora` as a LIBRARY call under a launcher-set per-cell `CUDA_VISIBLE_DEVICES=<slot>` pin WITHOUT threading a matching `gpu_id` re-points the process at physical GPU 0. Two documented shapes. **Shape (a) — worker** (incident #1090 fu3 launch 3, 2026-07-08T02:03Z; marker `epm:new-bug-class v3 cvd_clobber_library_train_seam` on #1090): the dispatcher pinned `CVD=<slot>` per cell in the child env, but the call chain `build_organism(...) -> build_train_config(gpu_id=0) -> train_lora` left the config default; the in-process re-export OVERWRITES the correct launcher pin (it runs BEFORE cuInit, so — unlike the import-time-cuInit entry — the clobber TAKES), and 4 parallel cells co-located on physical GPU 0 → 14/34 cells rc=2 CUDA-OOM while 7 GPUs sat idle. (The same launch ALSO lost 19 cells to `skipped_no_yield` from a SEPARATE co-occurring datagen yield-floor bug — marker `epm:new-bug-class v4 datagen_yield_floor_economy` on #1090 — together draining the launch, ~20 min of 8xH100 + a relaunch; yield-skips are NOT a CVD symptom — scope the clobber's diagnostic signature to the OOM fan-out only.) **Shape (b) — dispatcher-poisoning** (incident #1112, 2026-07-07T23:37Z; marker `epm:new-bug-class v2 ft_zero3_num_processes_cvd_clobber` on #1112): `phase_train` ran an s2 LoRA cell IN-PROCESS in the dispatcher, so the clobber poisoned the DISPATCHER's own env; the s3 full-FT compose then read `torch.cuda.device_count()` == 1 → composed `--num_processes 1` against the 4-GPU ZeRO-3 yaml (zero sharding; whole 7B params+grads+Adam on GPU 0; OOM at 75.86 GiB used / 3.84 GiB alloc), AND `_run_subprocess(env={**os.environ})` propagated `CVD=0` into the child. Diagnostic signatures, kept distinct: shape (a) = CUDA-OOM fan-out across co-scheduled cells whose OOM messages list sibling PIDs while N-1 GPUs sit idle — cells get far enough to ALLOCATE, then OOM (distinct from the hand-launch entry's signature, where engines crash at INIT on the busy default GPU); shape (b) = a multi-GPU compose "sees 1 GPU" after ANY in-process training ran earlier in the same process. - **Smoke/production parity includes PROCESS WIDTH — a smoke that narrows a ZeRO-3 full-FT launch to `--num_processes 1` OOMs deterministically at the FIRST optimizer step, and a parent dispatcher's narrow-smoke pin is HOST-scoped, never clone-portable.** Single-process ZeRO-3 shards nothing: for a 7B full FT, bf16 weights + grads + fp32 Adam moments (~86 GB) land on ONE 80 GB A100, and because optimizer states allocate lazily the smoke sails through model load + forward/backward and dies at the first optimizer step (traceback signature: `exp_avg_sq` alloc failure in DeepSpeed `stage3.py _optimizer_step`). - **RunPod MooseFS per-pod disk quota (~130 GB), separate from share-level free space.** `df -h /workspace` shows the share size (TB free) but each pod has a ~130 GB writable quota; writes past it fail with `OSError errno=122 (EDQUOT)` (`shutil.disk_usage` misses this — preflight uses a `posix_fallocate` probe instead). Symptoms: log appends fail with "Disk quota exceeded", WandB inline uploads emit Errno 122, checkpoint loads die silently. Mitigations: `EPM_SKIP_INLINE_CHECKPOINT_UPLOAD=1` for sweeps; sequentialize multi-condition sweeps; delete `coupling_merged/` after each phase; provision a bigger pod for 6+ Qwen-7B checkpoints.
- **VM `earlyoom` SIGTERMs bulk in-memory tensor loads silently (NO Python traceback).** The EPS VM runs Ubuntu `earlyoom`, which sends SIGTERM to the highest-`badness` process when *available* memory (MemAvailable, not MemFree) drops below 10% — ~12.8 GB of the 128 GB total — and SIGKILL at 5% (~6.4 GB). Scripts that load a bulk tensor set (per-rollout activations, per-step checkpoints, an all-at-once diff-of-means corpus) into memory at once trip this under fleet pressure: the process dies WITHOUT a Python traceback (earlyoom interrupts before any handler runs), so the log just stops mid-progress and looks like a hang. This is the host-RAM analogue of the RunPod per-pod EDQUOT quota above — a silent resource limit, not a clean exception. RULE for bulk tensor reductions (diff-of-means, layer averages, PCA): stream-reduce — iterate one tensor at a time, accumulate sums + counts into a fixed-size buffer (`L × D × 4 bytes` ≈ 460 KB for typical activations), never materialize all N at once; peak RSS then stays O(one-tensor) regardless of N. Verify a silent death (distinct from the kernel OOM killer, which logs to dmesg with `oom_score`, not `badness`) with `journalctl --since '<time>' | grep -i earlyoom` (it logs the killed PID + its VmRSS + `badness`) or `systemctl status earlyoom`. Reaching for a bigger-RAM VM only raises the bar; the stream-reduce removes the bound entirely. (Incident #658 round 5, 2026-06-30: the persona-vector `r_B` build loaded ~12000 activation tensors (~38 GB) at once; earlyoom SIGTERMed it at VmRSS 33 GB under fleet pressure (9.4% avail) with no traceback; the round-5 fix stream-reduced the load.) Collateral-kill variant (#811: a 6.8 GiB detached fit was the badness-selected victim of a NEIGHBOR's spike — this VM's earlyoom `--prefer python3?` adds +300 to every python process): sanctioned detached VM phases launch choom-protected (`sudo -n choom -n -600` swept across the phase session) with a relaunch-once-then-pod-pivot rule — SKILL.md § Detached VM-side long compute phases; the Step 9c gate pytest runs self-choom the gate shell by default (SKILL.md Step 9c, #1045 — pytest is in the `--prefer` regex, +300).
- **exit-137/143 on the shared VM is NOT proof of OOM — verify the kill source before diagnosing.** SIGKILL (exit 137; exit-143/SIGTERM deaths get the same protocol) has at least four sources on this box: the kernel OOM killer, earlyoom (thresholds + journal verification in the entry above), systemd-oomd / cgroup-confined `memory.max` OOM, and a DELIBERATE operator/PM/watcher kill. Shared login-scope cgroup counters do NOT attribute (`memory.peak` / a historical `oom_kill` count cover the whole fleet scope). Run the kill-source checklist in `.claude/skills/issue/failure_patterns.md` § exit-137/143 kill-source verification — (1) `oom_kill` DELTA over the run window (non-incrementing ⇒ rules OOM out; incrementing ⇒ takes precedence over the floor read; no baseline ⇒ rely on journals), (2) MemAvailable floor (> 20 GB rules out GLOBAL-pressure kills only, NOT cgroup-confined OOM), (3) earlyoom/systemd-oomd journals + the watcher's `earlyoom-kill` sidecar rows at the death ts, (4) a time-proximate, target/pid-MATCHED `deliberate-stop` breadcrumb on the task's events.jsonl (stale/non-matching hits are contextual only; absence does NOT rule a deliberate kill out) — BEFORE any `epm:failure` diagnosis names OOM or a crash-fix round chases a memory hypothesis; if the four steps don't attribute, record `killer unknown` rather than naming OOM; and sanity-check back-derived memory arithmetic against the code's actual allocation sites first. (Incident #779 r9, 2026-07-02: three exit-137s read as kernel OOM off shared-scope counters + arithmetic for an allocation that did not exist were deliberate PM SIGKILLs — MemAvailable floor 47 GB, `oom_kill` never incremented; a crash-fix round was dispatched against a nonexistent bug.)
- **Memory caps for torch fit loops: calibrate the live-tensor factor from a MEASURED real-shape peak — counting the code's explicit temporaries under-estimates the true per-chunk peak ~6×.** A memory-aware chunk cap of the form `floor(free_bytes × safety / (live_factor × unit_bytes))` is only as good as its `live_factor`. Counting the named intermediates in the code (the design copy, the element-square temp, the standardized copy → "≈4 live tensors") misses what actually dominates a training-loop chunk: the autograd BACKWARD graph over the chunk's activations, the AdamW moment buffers, and the allocator's high-water cached-block retention — none of which appear as variables. RULE: calibrate `live_factor` from a MEASURED peak at the REAL shape — run ONE chunk at production `(n, d_in)` in a FRESH process (`ru_maxrss` is a monotone process high-water mark; a later-chunk delta reads ~0) and read the `ru_maxrss` delta (CPU) / `torch.cuda.mem_get_info` delta (GPU); set the factor to `ceil(measured_peak / single_unit_bytes)`. The factor is shape/optimizer/precision-specific — re-measure when any of those change. Modest over-estimation is cheap: chunking does not change the fit (pin that with a chunk-size-invariance test), so a larger factor only adds chunk COUNT at constant total FLOPs (extreme conservatism does shrink chunks toward the tiny-op overhead regime `.claude/rules/vectorize-many-cell-fits.md` exists to kill), while an optimistic factor re-OOMs the very shape the cap exists to protect. ALSO log the resolved cap + the probed free bytes AT THE CAP SITE (e.g. `[vectorized_mlp] chunk capped 4096 -> 64 (n=480 d_in=3584 free=13.4 GiB)`) — that line is the fix-engaged signal that makes the next OOM diagnosable from the log alone, and a `free_bytes` probe failure must fall back to the REQUESTED chunk (never silently tighten). Canonical implementation: `resolve_chunk_cap()` in `src/explore_persona_space/analysis/vectorized_mlp_skill.py` (`live_factor=26`, calibrated from a measured ~10.7 GiB ru_maxrss delta ≈ 26× the 420 MiB single `(c=64, n=480, d_in=3584)` fp32 tensor; built on the `issue-811` branch, on `main` once #811's worktree auto-merges). (Incident #811 crash-fix round 8, 2026-07-01: the prior `live_factor=4` — the explicit-temporary count — picked c=218, whose real ~36 GiB peak re-OOM'd the #811 phase-0 gate at the exact shape the cap was added to protect; the recalibrated factor-26 cap survived the same production shape.)
- **MooseFS/FUSE D-state "zombie" processes on write-heavy runs.** Trainer + WandB writes hammering the FUSE mount can wedge processes in uninterruptible-sleep (`D` state) that even `kill -9` cannot reap; the GPUs sit idle while the run looks alive, and the only drain is a pod `stop` + `resume`. Standing mitigation for write-heavy runs: route trainer output AND WandB tempfiles OFF the FUSE mount — `EPM_OUTPUT_ROOT=/tmp/issue_<N>_results` + `WANDB_MODE=offline` (sync WandB afterward) — so the hot write path is local disk, not MooseFS. (Incident #505, 2026-06-08: pod-505 needed repeated stop+resume to drain D-state zombies until output was rerouted off FUSE.)
- **MooseFS FUSE READ-wedge on the pod `/workspace` `.venv` — the silent launch hang (zero stderr).** A pod launch that hangs at process STARTUP with ZERO stderr, the python child frozen at ~10 s CPU, GPU 0 MiB, 0 sockets, and `wchan=request_wait_answer` (`ps -o pid,stat,wchan:32,cmd -p <PID>`) is the MooseFS-backed `/workspace` `.venv` no longer answering FUSE READS on the import path — not a slow import, not a code bug. It can appear HOURS into an otherwise healthy pod (the same pod ran cleanly earlier). DISTINCT from the two MooseFS siblings above: not the EDQUOT write quota (errno 122 fails LOUD on writes), and not the D-state WRITE-wedge (#505: processes wedge unkillably mid-RUN under trainer/WandB write load; its drain is pod stop+resume, and rerouting output off FUSE PREVENTS it — here the wedge is on venv READS at startup, the child is killable, and output rerouting cannot help because the reads ARE the venv). Also distinct from the `uv sync` errno-116 stale-handle trap (venv BUILD-time, fails loud; `.claude/agent-memory/experimenter/feedback_uv_sync_moosefs_stale_handle_persistent.md`). DISCRIMINATE with a timeout-bounded import probe — `timeout 60 uv run python -c "import transformers"` — rc=124 IN THE PRESENCE OF THE SIGNATURE confirms the wedge (a healthy venv imports in well under 60 s; on any suspicion of a transient stall, re-probe once and/or check the probe's own `wchan` mid-timeout before condemning the pod); py-spy is unusable in the project's RunPod containers (no ptrace capability), so the probe is the load-bearing diagnostic. REMEDIATION: kill the hung child + post `epm:failure v1 failure_class: infra reason: moosefs-fuse-wedge-venv-import`; kill-and-relaunch does NOT clear it (the mount stays wedged) — the orchestrator swaps the pod: stop/resume container restart (undemonstrated for this wedge; prefer it first when unuploaded artifacts sit on the volume, since terminate destroys it) or terminate + fresh provision (the path #779 actually recovered through). Never loop relaunches on the wedged mount. Long-form runbook: `.claude/agent-memory/experimenter/feedback_moosefs_fuse_wedge_venv_import.md`. (Incident #779 pass-2 capture relaunch, 2026-07-03, pod-77902: two consecutive launches wedged identically at startup hours after a healthy run on the same pod; the independent import probe reproduced the wedge, rc=124.)
- **matplotlib `xerr`/`yerr` take NON-NEGATIVE per-point OFFSETS from the value — never CI bounds and never signed deltas.** `Axes.errorbar`/`bar`/`barh` validate the error array (docstring: "All values must be >= 0") and raise `ValueError: '<x|y>err' must not contain negative values` at render time (NaN is exempt). The crash is DATA-DEPENDENT: a quantile CI over bootstrap/delta draws can genuinely invert around a separately-computed point estimate at tiny n (#1335: `fig_waterfall` passed CI bounds as barh `xerr`, killing GCP attempt att-20260715-122509 at the figures step), and float epsilon turns a constant-draw CI into a tiny negative delta (#547) — so ONE green figures run does NOT clear the class. RULE: at every errorbar site compute offsets element-wise as `err_lo = np.maximum(0, v - lo)` / `err_hi = np.maximum(0, hi - v)` (never raw `v - lo`, never the bounds themselves), and pin new figure code with a unit test that routes a deliberately INVERTED quantile CI (`lo > v` or `hi < v`) through the REAL figure function to `savefig`, asserting no ValueError. The clamp is for the legitimate tiny-n epsilon/quantile case — a LARGE inversion warrants sanity-checking how the point estimate and CI were computed, and a clamp firing on real data is itself a diagnostic worth logging/annotating. Clamped asymmetric-CI exemplars: `.claude/skills/paper-plots/patterns/{P1-bar-comparison,P8-ood-split,B0-blog-bar-comparison}.md`. (Incidents #547, #1335.)
- **vLLM in-process teardown does NOT reap worker subprocesses.** When the SAME process loads vLLM then a non-vLLM framework (HF Transformers, sentence-transformers), the canonical cleanup (`del llm` + `destroy_model_parallel()` + `destroy_distributed_environment()` + `gc.collect()` + `empty_cache()`) is NOT enough — vLLM TP/PP worker subprocesses survive and re-grab the freed GPU memory the moment the next framework loads weights (looks like an HF-Transformers OOM). Add: (a) `psutil.Process().children(recursive=True)` → `.terminate()` then `.kill()` survivors; (b) `nvidia-smi --query-compute-apps=pid` → FAIL LOUD if any python PID still holds the GPU. Escape hatch: if switching frameworks >twice, subprocess-isolate each phase (JSON IPC on disk). - **Same-pod relaunch: divergent `.claude/**` spec files block `git pull --ff-only`.** On a same-pod relaunch of an `issue-<N>` branch whose diff carries a "spec-freshness" sync commit (the workflow-surface specs under `.claude/**` were refreshed on the branch), the pod's existing `.claude/**` files diverge from the branch version; `git pull --ff-only` aborts to protect the local edits ("Your local changes to the following files would be overwritten by merge" / "untracked working tree files would be overwritten by merge") instead of fast-forwarding, and the pre-launch sync fails with an unhelpful error. This is the `.claude/**`-spec sibling of the committed-pod-artifacts pull block above (which covers pod-WRITTEN `eval_results/issue_<N>/...` files) — same abort, different file class and different recovery: spec files are discarded back to HEAD, not backed up. Surgical recovery, no force:
  <!-- workflow-lint: allow-root-guard-block: pod-side /workspace clone recovery — runs over SSH on the pod, never at the VM repo root -->
  ```bash
  # 1. Stale-lock guard — only after confirming no live git process
  pgrep -x git >/dev/null || rm -f .git/index.lock

  # 2. Identify the divergent .claude/** files (path-scoped diff — fast on MooseFS)
  git fetch origin issue-<N> --quiet
  git diff --name-only HEAD origin/issue-<N> -- .claude/ > /tmp/diverged.txt

  # 3. Tracked-at-HEAD → discard local edits; untracked (new-on-branch) → remove
  while read -r f; do
    if [ -n "$(git ls-tree -r HEAD --name-only -- "$f")" ]; then
      git checkout HEAD -- "$f"          # exists at HEAD: revert pod-side edits
    else
      rm -f "$f"                          # UNTRACKED would-be-overwritten new file
    fi
  done < /tmp/diverged.txt

  # 4. Now the fast-forward succeeds
  git pull --ff-only origin issue-<N>
  ```
