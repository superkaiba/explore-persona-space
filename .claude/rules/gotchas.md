# Gotchas

- HF Trainer monkey-patch in `train/trainer.py` — fragile; breaks if `Trainer.__init__` changes.
- Hard-coded library paths in `orchestrate/env.py` — cluster-specific.
- No dataset validation in `build_phase1_dataset()` — empty QA pairs silent-fail.
- Tulu pipeline caveat: midtraining+Tulu results may not generalize to production post-training.
- **`+gpu_id=N` Hydra override required for multi-GPU parallel training launches.** `train/sft.py` sets `os.environ["CUDA_VISIBLE_DEVICES"] = str(cfg.gpu_id)`, clobbering any env `CUDA_VISIBLE_DEVICES` (default `0` → all parallel jobs on GPU 0 → OOM). Pass `+gpu_id=N` per process (the `+` is required — `gpu_id` isn't in the default schema).
- **The in-process `CUDA_VISIBLE_DEVICES` clobber is silently defeated by any import-time cuInit — parallel per-GPU launches must ALSO pin it in the LAUNCHER environment.** The driver freezes its device list at the FIRST cuInit in the process; if any import in the dispatcher chain initializes CUDA (`import peft` is a known offender — incident #545, 2026-06-11) before `train_lora`'s `os.environ["CUDA_VISIBLE_DEVICES"] = str(cfg.gpu_id)` (`train/sft.py`), the late clobber is a driver-level no-op and every process's `cuda:0` resolves to physical GPU 0 — parallel cells co-locate and OOM. Neither `torch.cuda.is_initialized()` returning `False` nor `torch.cuda.device_count()` returning the post-clobber count proves the pin took (both read the clobbered env, not the frozen driver state). RULE: export `CUDA_VISIBLE_DEVICES=<gpu>` per cell in the launcher environment before exec, keeping the matching `--gpu <gpu>` / `+gpu_id=<gpu>` arg so the in-process clobber rewrites the same value — never rely on the in-process clobber alone. Diagnostic signature: all parallel cells OOM on ONE physical GPU whose OOM message lists every sibling PID. (Incident #543 ratio-1pct-arm relaunch-2, 2026-06-10: 3 phase-1 cells with distinct `--gpu` args co-located on GPU 0 and OOM'd; a clean process honored the same late CVD set, the script's import chain did not.) Experimenter-side enforcement: `.claude/agents/experimenter.md` Before Running step 10; regression smoke: `tests/test_cvd_wave_assignment_smoke.py`; lane-independent mechanical enforcement: `scripts/workflow_lint.py --check-dispatcher-cvd-pin` (bundled into the no-flags default run) FAILs any backgrounded `--gpu-id`/`+gpu_id=` python launch in `scripts/*.sh` without a `CUDA_VISIBLE_DEVICES=` prefix on the same command — waive legitimate shapes with `# CVD_PIN_EXEMPT: <reason>`.
- **RunPod MooseFS per-pod disk quota (~130 GB), separate from share-level free space.** `df -h /workspace` shows the share size (TB free) but each pod has a ~130 GB writable quota; writes past it fail with `OSError errno=122 (EDQUOT)` (`shutil.disk_usage` misses this — preflight uses a `posix_fallocate` probe instead). Symptoms: log appends fail with "Disk quota exceeded", WandB inline uploads emit Errno 122, checkpoint loads die silently. Mitigations: `EPM_SKIP_INLINE_CHECKPOINT_UPLOAD=1` for sweeps; sequentialize multi-condition sweeps; delete `coupling_merged/` after each phase; provision a bigger pod for 6+ Qwen-7B checkpoints.
- **MooseFS/FUSE D-state "zombie" processes on write-heavy runs.** Trainer + WandB writes hammering the FUSE mount can wedge processes in uninterruptible-sleep (`D` state) that even `kill -9` cannot reap; the GPUs sit idle while the run looks alive, and the only drain is a pod `stop` + `resume`. Standing mitigation for write-heavy runs: route trainer output AND WandB tempfiles OFF the FUSE mount — `EPM_OUTPUT_ROOT=/tmp/issue_<N>_results` + `WANDB_MODE=offline` (sync WandB afterward) — so the hot write path is local disk, not MooseFS. (Incident #505, 2026-06-08: pod-505 needed repeated stop+resume to drain D-state zombies until output was rerouted off FUSE.)
- **vLLM in-process teardown does NOT reap worker subprocesses.** When the SAME process loads vLLM then a non-vLLM framework (HF Transformers, sentence-transformers), the canonical cleanup (`del llm` + `destroy_model_parallel()` + `destroy_distributed_environment()` + `gc.collect()` + `empty_cache()`) is NOT enough — vLLM TP/PP worker subprocesses survive and re-grab the freed GPU memory the moment the next framework loads weights (looks like an HF-Transformers OOM). Add: (a) `psutil.Process().children(recursive=True)` → `.terminate()` then `.kill()` survivors; (b) `nvidia-smi --query-compute-apps=pid` → FAIL LOUD if any python PID still holds the GPU. Escape hatch: if switching frameworks >twice, subprocess-isolate each phase (JSON IPC on disk).
  - **Reaping recipe (vLLM v1, 0.11.0).** Even loading two vLLM engines back-to-back in one process hits this: vLLM v1's EngineCore runs in a SEPARATE subprocess (`(EngineCore_DP0 pid=...)` in the log), so the bare `del llm; gc.collect(); empty_cache()` triad does NOT reap it synchronously — the reserved KV cache (~`gpu_memory_utilization` of HBM) stays pinned long enough that the next `LLM(...)` init raises `ValueError: Free memory ... less than desired gpu_memory_utilization` (the log carries the `destroy_process_group() was not called` canary). `LLMEngine.__del__` only destroys the DP process group, NOT the worker. RULE: before `del llm`, call `llm.llm_engine.engine_core.shutdown()` (the v1 EngineCoreClient shutdown that reaps the MP worker via `MPClient._finalizer`), getattr-guarded with a v0 fallback `model_executor.shutdown()`; then `torch.distributed.destroy_process_group()` guarded by `is_available() and is_initialized()` (NO-OPs on the off-pod / single-GPU case). After `del llm`, finish with `gc.collect()` + `torch.cuda.empty_cache()` + `torch.cuda.ipc_collect()` (complements `empty_cache` for inter-process freed memory) + `time.sleep(1.0)` (subprocess teardown is async). Reference implementation: `src/explore_persona_space/analysis/representation_shift.py::_reap_vllm_engine` (every attribute access getattr-guarded so it NO-OPs on a differing API surface). (Incident #653 round 9, 2026-06-16: the dx phase tore down its engine with the bare triad and OOMed the cell-2 `LLM(...)` init; commit `3eb580dfe9`.)
- **Crashed vLLM parents leave orphaned `VLLM::EngineCore` workers that OOM the RELAUNCH — and `pgrep -f <script-name>` cannot see them.** The crash-orphan variant of the teardown trap above: when a vLLM workload crashes (or is killed), its engine-worker subprocesses can outlive the dead parent and silently keep holding ~50 GB on EVERY GPU, so the next launch dies at engine init with `Free memory on device (...) is less than desired GPU memory utilization`. The workers' cmdline is just `VLLM::EngineCore` (no script name, no python path), so the natural pre-relaunch liveness probe `pgrep -f <script-name>` reads clean while the GPUs are full. RULE: before ANY vLLM relaunch, probe `nvidia-smi --query-compute-apps=pid,used_memory --format=csv` AND `pgrep -af EngineCore`, kill any leftovers (`kill`, then `kill -9` survivors), and confirm GPU memory is ~0 before launching the new driver. Experimenter-side enforcement: `.claude/agents/experimenter.md` Pre-Launch step 9. (Incident #601, 2026-06-11: 4 orphaned EngineCore workers from a phase0 crash held ~50 GB/GPU and OOMed the hot-fix relaunch until they were killed.)
- **vLLM 0.11.0 V1 EngineCore dies silently 1-4s after init under default `fork()` if the dispatcher's `main()` touched CUDA-adjacent code before `LLM()`.** vLLM V1 defaults `VLLM_WORKER_MULTIPROC_METHOD=fork`; when the parent process has imported transformers, called `AutoTokenizer.from_pretrained`, or otherwise initialized any CUDA-adjacent state BEFORE `vllm.LLM()` constructs the engine, `fork()` duplicates the poisoned parent state into the EngineCore subprocess, which logs successful init + `Supported_tasks: ['generate']` and then exits without a traceback of its own; the parent surfaces the death as `Engine core proc EngineCore_DP0 died unexpectedly, shutting down client.` immediately followed by the downstream `ZeroDivisionError: division by zero` at `vllm/entrypoints/llm.py:1610` (`total_in_toks / pbar.format_dict["elapsed"]` with `elapsed=0` because the engine died before any prompt was processed). A standalone smoke that calls the same dispatcher functions in-process (no `main()`, no argparse) succeeds — the distinguishing signature against an ordinary OOM. Reproduces on H100 80GB + torch 2.8.0+cu128 AND GCP A100; `enforce_eager=True` (cudagraph-skip) masks an adjacent race but does NOT fix this class. RULE: any dispatcher that wraps `vllm.LLM()` AND has a `main()` whose pre-`LLM()` path can touch transformers / tokenizer / registry helpers MUST set `os.environ.setdefault("VLLM_WORKER_MULTIPROC_METHOD", "spawn")` at module top, BEFORE any `import vllm` (vLLM reads the var at import time) — or pass `VLLM_WORKER_MULTIPROC_METHOD=spawn` from the shell launcher. Worked example: `scripts/i628_dispatch.py` lines 54-79 (commit `48835909c`). Deeper recipe + worked log excerpt + the `uv run` re-introduction footnote: `.claude/agent-memory/experiment-implementer/feedback_vllm_v1_fork_enginecore_silent_death.md`. (Incident #628 attempts 5-9, 2026-06-12/13: ~3h investigation across both GCP A100 and RunPod H100 before the spawn fix landed.)
- **vLLM 0.11.0 `LLM.generate()` raises `ZeroDivisionError: division by zero` in its tqdm progress bar when a batch finishes faster than tqdm's elapsed-time clock — a HEALTHY-ENGINE variant of the #628 symptom, fixed with `use_tqdm=False`.** vLLM 0.11.0's `_run_engine` computes `in_spd = total_in_toks / pbar.format_dict["elapsed"]`; when the batch completes before tqdm's `elapsed` ticks above 0, `elapsed=0` raises `ZeroDivisionError` and kills the whole `generate()` call before any output returns. Most exposed: teacher-forced single-token reads (`score_logp_for_R`, `max_tokens=1`, many short prompts) and small on-policy batches. DISTINGUISH from the #628 entry above: there the engine DIED (fork-poisoned) so `_run_engine` ran zero iterations → `elapsed=0`; here the engine is HEALTHY and produces output but the batch is just too fast — the tell is the absence of `Engine core proc ... died unexpectedly` and a clean engine init. Apply `use_tqdm=False` when the engine is alive; apply the #628 `VLLM_WORKER_MULTIPROC_METHOD=spawn` fix when it died. RULE: pass `use_tqdm=False` (NOT `disable_tqdm=True` — that kwarg does not exist on the 0.11.0 surface; verify against `inspect.signature(LLM.generate)` before relying on it — the API shifts between minor versions) on EVERY `LLM.generate()` call site; tqdm output is noise on a daemonized launcher anyway. Per-agent recipe: `.claude/agent-memory/experiment-implementer/feedback_vllm_use_tqdm_zerodivision.md`. (Incident #613 `single-space-falsifier` round-1, 2026-06-15: crash at `eval_trajectory._generate_on_policy_R` within ~16 min of the unit's training completion, costing one GCP A100-80 VM cycle; fixed across all 3 call sites in `contrastive_neg_geometry_472` by commit `dc1e0e303`.)
- **HF `datasets` / `transformers` subprocesses can exit `rc=134` (SIGABRT) with a `PyGILState_Release` fatal abort DURING interpreter shutdown — AFTER the work already completed and the output file was written.** A CPU step that loads `datasets`/`transformers` in a subprocess (e.g. a WildChat-slice / battery builder) can write its output successfully and then crash at finalize time with `Fatal Python error: PyGILState_Release: thread state ... must be current when releasing` — a library finalize-time thread-cleanup race, not a workload failure. A `set -euo pipefail` wrapper treats the non-zero rc as fatal and the EXIT trap powers off the GCE instance / aborts the run, destroying a result that is sitting complete on disk. RULE: any wrapper around an HF-`datasets`/`transformers` subprocess CPU step must check the ARTIFACT before treating a non-zero rc as fatal — if the expected output file exists and meets its size/count target, accept the work and log `rc=134` as tolerated (only a missing/short artifact is a real failure). Distinguish a genuine crash by the post-write artifact check, not by rc alone. (Incident #654, 2026-06-16: `issue654_build_battery.py:355 ensure_wildchat_slice` wrote the 30-conversation slice, then the subprocess SIGABRTed on shutdown; the EXIT-trap delete powered off the instance until the artifact-check guard landed.)
- **Before stopping/terminating a pod you believe is idle/done, verify with the live RunPod API + `nvidia-smi` GPU utilization — never infer "idle" from an SSH-unreachable pod or an absent `epm:run-launched` marker.** Diagnostic and manual runs emit no `run-launched` marker, and an SSH refusal usually means the cached host/port drifted (a `pod.py resume` changes them), NOT that the pod is free — both signals falsely read "nothing running." Run `pod.py config --sync` to repair any address drift, then confirm ~0% GPU utilization across ALL devices via `nvidia-smi` before any `pod.py stop` / `terminate`. (Incident #488, 2026-06-08: a live diagnostic training run was killed because SSH-refused + no `run-launched` marker were misread as "idle.")
- **SSH MCP `ssh_execute` caps commands at ~30 s by default — and `timeout` must be a NUMBER (ms).** A pod command wrapped in `timeout 240 sh -c ...` still dies at the MCP layer with `Command timeout after 30000ms` unless you pass the tool's own `timeout` param ≥ the inner timeout; passing it as a string raises `Expected number, received str`. For anything that can exceed ~30 s, prefer a bg-Bash `ssh` call. (4 hits on 2026-06-09, issue #521/#522 sessions.)
- **Launching a long pod job over SSH: redirect stdin or the ssh call hangs.** `ssh pod-<N> 'nohup ... > log 2>&1 &'` keeps the SSH session open on the backgrounded child until an outer `timeout` kills it (exit 124 = the ssh timeout, not the job). Use the full idiom `nohup ... > log 2>&1 < /dev/null &` then exit immediately, and verify the job separately via the PID file / log mtime. (Incident #532 launch, 2026-06-09.)
- **`pkill -f` self-matches a one-shot remote command and kills the SSH session.** A `gcloud compute ssh ... --command='...'` (or any `ssh <host> '<inline command>'`) makes the inline command's argv visible on the remote as the SSH-driven shell's argv; calling `pkill -f "<pattern in that argv>"` from inside the command SIGKILLs the SSH session itself and gcloud/ssh exits 255 — leaving you locked out mid-session with the stray process still alive. Kill stray remote procs by exact PID (`kill $PID`, then `kill -9` survivors), never via a `-f` substring pattern that appears in your own command line. (Incident #653 round 9, 2026-06-16: `pkill -f "git fetch origin issue-653"` matched the SSH command's own argv and self-killed the salvage-relaunch session.)
- **`setsid nohup <launcher>` under `sudo bash -c '...'` loses root's login PATH — `uv` is not found and the launcher dies in seconds.** On a fresh-bootstrapped GCP GCE instance the bootstrap script installs `uv` at `/root/.local/bin/uv`, but a `setsid nohup <launcher> &` run under `sudo bash -c '...'` does NOT inherit root's login PATH, so the launcher dies within seconds with `uv: command not found` — it looks like a successful background-launch but leaves no live process. Put `export PATH="/root/.local/bin:$PATH"` (or the equivalent for the install location) as the FIRST line of any GCP-lane salvage launcher script. (The SSH-MCP/RunPod launcher template already does this — port it forward.) The workdir `/workspace/eps-issue-<N>` is root-owned, so the entire relaunch block must run under `sudo bash -c`. (Incident #653 round 9, 2026-06-17.)
- **`python-dotenv` no-arg `load_dotenv()`/`find_dotenv()`: stdin heredocs CRASH; `-c` one-liners silently load nothing off-repo.** From a stdin-fed heredoc (`uv run python - <<PY`), no-arg `find_dotenv()` walks the call stack (`frame.f_back`) and dies on `assert frame.f_back is not None`. Under `python -c` it does NOT crash (verified against the pinned python-dotenv 1.2.2, 2026-06-12: `__main__` has no `__file__` under `-c`, so `_is_interactive()` short-circuits to a cwd-walk and the frame walk is never reached) — the `-c` failure mode is instead SILENT: run from a cwd not under a dir containing `.env`, `load_dotenv()` returns False, no keys load, and the missing-API-key crash fires later and far from the cause. Both shapes: pass the explicit path `load_dotenv("/path/to/.env")`, use the stdin-safe project wrapper `explore_persona_space.orchestrate.env.load_dotenv()`, or `set -a && source .env && set +a` in the enclosing shell. (3 hits on 2026-06-09 — heredoc-shape; reintroduced on #612, 2026-06-12.) The heredoc half is enforced mechanically for `scripts/*.sh` by `scripts/workflow_lint.py --check-heredoc-dotenv` (bundled into the no-flags default run); the `-c` half is DELIBERATELY not lint-covered (a no-arg call from the repo root works — cwd-walk finds `.env` — so a hard FAIL would flag legitimate shapes; extension considered + rejected 2026-06-12). Prefer the explicit path in `-c` one-liners anyway.
- **Pod/VM driver scripts that default `REPO_ROOT` to the RunPod path die on the GCP lane unless the override is threaded at dispatch.** The GCE startup script clones the repo to `$WORKLOAD_ROOT` (`/workspace/eps-issue-<N>`) and runs the workload command from there, so a driver with `REPO_ROOT="${REPO_ROOT:-/workspace/explore-persona-space}"` fails at its first `cd` under `set -e` and the EXIT trap powers the VM off. RULE: compose gcp/auto dispatches as `--workload-cmd 'REPO_ROOT="$WORKLOAD_ROOT" bash scripts/<driver>.sh'` (incident #599, 2026-06-11: ~8 min GPU burn, guest-attribute `phase=failed`). **Update (#641, commit `4e4932fd1a`):** the GCE startup script's workload_cmd branch (`backends/gcp.render_startup_script`) now `export REPO_ROOT="$WORKLOAD_ROOT"` before running the workload, so a driver using `${REPO_ROOT:-/workspace/explore-persona-space}` resolves transparently with NO orchestrator-side prefix — the manual prefix is no longer required. It is still honored when supplied (a bash per-command env var supersedes the inherited export for that one command — belt-and-suspenders), so do NOT FAIL a launch that omits it. The trap still matters for the hydra (`train.py`) branch (no such auto-export) and for understanding the #599 incident.
- **vLLM `prompt_logprobs` + large `max_model_len` OOMs on float32 logits materialization.** With `prompt_logprobs` enabled, vLLM materializes float32 logits for every token-slot in a scheduler step; at `max_model_len=32768` with uncapped `max_num_batched_tokens` that is a ~19 GiB single allocation inside `logits.log_softmax` — `gpu_memory_utilization` tweaks alone do NOT fix it. RULE: any prompt-logprobs eval sets `max_num_batched_tokens≈8192` AND `gpu_memory_utilization<=0.75` on the `LLM()` init. (Incident #501, 2026-06-06: two CUDA OOMs, ~1h wall lost; fix commit cb4e4119f ran clean.)
- **`orchestrate.preflight --json` emits PRETTY-PRINTED multi-line JSON — parse the WHOLE stdout, never `splitlines()[-1]`.** The CLI prints `json.dumps(..., indent=2)`, so the final stdout line is a bare `}`; a dispatcher gate doing `json.loads(proc.stdout.splitlines()[-1])` crashes even when preflight PASSes. Parse with `json.loads(proc.stdout)` (the CLI prints exactly one JSON object and nothing else on stdout). RULE: dispatchers that gate on preflight ALSO expose a `--skip-preflight` flag so a falsely-failing gate can be bypassed in-turn after manual preflight verification, instead of costing a relaunch cycle. (Incident #602, 2026-06-11: pod launch died <1 min in on the bare `}` despite a PASSing preflight; the experimenter verified manually and relaunched with `--skip-preflight`.)
- **HF mirror ≠ local-verified copy — sha256-pin every reused-artifact prefetch.** A worker-side dispatcher that prefetches REUSED artifacts from a shared HF inherit path (e.g. a parent task's `issue<M>_<slug>/...` on the data repo) can pull a silently different generation than the local copy the plan and reviewers verified: local `data/` outputs are untracked (absent from every clone), and the standard pre-flight pair — verify content LOCALLY + verify the artifact RESOLVES on HF (`list_repo_files` / HEAD) — never content-compares the two. The divergence surfaces as a KeyError (or a wrong persona universe) deep in the consumer, after a full provision cycle is already spent. RULE: snapshot the verified local inputs to an issue-OWNED HF path (`issue<N>_<slug>/inputs/`) instead of consuming the parent's shared mirror; pin every prefetch/autofetch against an `EXPECTED_SHA256` table asserted at the trust boundary — covering files already present on the worker, not just fresh downloads — and add a consume-time coverage assert where the artifact is read. (Incident #600, 2026-06-11: stale `dac5749`-generation HF mirrors of #472's `R_train.json` + `centroids_L10.pt` crashed the GCP smoke run; fix pattern: the `EXPECTED_SHA256` pins in #600's `dispatch.py`.)
- **GCE metadata script runner kills GCP-lane workloads on giant progress-bar lines — and the VM zombies at RUNNING.** `google_metadata_script_runner` reads startup-script stdout line-by-line with a bounded Go `bufio.Scanner`; a long NEWLINE-FREE line — vLLM/tqdm `\r`-carriage-return progress bars ("Processed prompts: ...") are the canonical case — overflows it (syslog signature: `error while communicating with "startup-script" script: bufio.Scanner: token too long` then `Script "startup-script" failed with error: signal: broken pipe`) and the workload dies on SIGPIPE. The EXIT trap RUNS but `$?` inside it reads 0 (status of the last completed command — measured on bash 5.1.16, #607 fact-check), so the `[ "$rc" -ne 0 ]` guard no-ops and the `eps/phase` guest attribute never flips to `failed` and the VM stays RUNNING (and billing) with the GCP poll reading a healthy "workload" phase forever — indistinguishable from a healthy long run. Detect: GPUs at 0% + no workload python processes + `sudo grep "token too long" /var/log/syslog`; disk state survives (only the parent shell was killed). Recover: SSH-relaunch the REMAINING phases on the same VM under `nohup` with stdout/stderr redirected to a FILE (bypasses the metadata-runner pipe entirely), then on success replicate the startup script's success tail — write the completion sentinel at the handle's `sentinel_path` and publish `eps/phase=done` via the guest-attribute curl — so the existing poll/finalize path proceeds unchanged; keep the rc!=0 → `_eps_phase failed; shutdown -h now` trap for billing bounds. Prevent: never stream raw workload output through startup-script stdout — redirect the workload block to a log file (the `log_path` the handle already names) and/or set `TQDM_DISABLE=1` / vLLM `disable_tqdm` on non-tty. The renderer-side fix (`src/explore_persona_space/backends/gcp.py` `render_startup_script`) is tracked as a separate infra task — this entry documents the trap. (Incident #491 attempt 2, 2026-06-11: killed mid-free_gen after 22/29 cells; recovered via SSH nohup relaunch on the live VM.)
- **Lazy imports inside smoke-skipped branches (`--dry-run` / `--skip-upload` / GPU-only paths) are unverified code — the ImportError fires on the pod, AFTER the expensive phases.** Local smokes legitimately skip upload/GPU branches, so a deferred `from ... import` there executes for the first time in production; an assumed-but-absent symbol (canonical case: porting code that calls a private file-local helper — `_retry_transient` was defined locally in the i528 scripts, never in `orchestrate/hub.py`) crashes the workload only after training/judging are already spent. RULE: hoist cheap cross-script helper imports to module top (absence then crashes at process start); gate relaunches on an AST-based `--verify-imports` smoke that walks every in-scope file and EXECUTES every deferred import (hand-maintained symbol lists just re-create the drift — generate the list from the AST); and when porting code that calls a private `_underscore` helper, grep the SOURCE branch for where the symbol is actually DEFINED — file-local helpers don't travel with the import path you assume. Worked example: `scripts/issue_606/i606_dispatch.py --verify-imports` (commit `c39627b30` — CPU-only, no GPU/API; 49 deferred symbols across 7 files, exit-0 gate). (Incident #606, 2026-06-11: GCP workload crashed at p5_upload ~18 min in, after training + stage-A judging, on `ImportError: cannot import name '_retry_transient'` — every local smoke had skipped the upload branch.)
- **Smoke-root rebinding (`--smoke` → `*_smoke` GEN/OUT/EVAL roots) orphans READ-ONLY PARENT INPUTS.** Smoke/real root isolation is for GENERATED artifacts; parent inputs (clouds / caches / pools fetched from a prior task) are inputs, not outputs. If the fetch step stages them under the real root only — or a fetch early-return skips the staging under `--smoke` — while a downstream step still consumes them, a fresh-pod smoke crashes at the first consuming step on a path only the real run staged (signature: an assertion on the first parent item AFTER all earlier smoke steps passed). RULE: give parent inputs a canonical NON-rebinding location (e.g. `CLOUDS_PARENT = .../eval_results/issue_<N>/clouds_parent`) staged BEFORE any smoke early-return, so identical fetch+read lines execute in both modes; never fix with a smoke-mode skip (removes coverage) or a read-side-only fallback (a fresh pod running smoke-first still has nothing staged); when writing any `--smoke` rebinding dispatcher, audit every downstream read for parent-input paths and pin them to non-rebinding constants. Sibling trap from the same family: the deliberate root isolation means a completed REAL early phase does NOT populate the `*_smoke` roots — a mid-chain smoke stage (`--phase train --smoke`) hard-requires its own early-phase `--smoke` prestage on the same pod (signature: ~6 s death at the build step on a missing smoke input file); stat-check the smoke GEN root before launching any mid-chain smoke stage. (Incident #542, 2026-06-12: `--phase p0prime --smoke` died at the closeness step with `AssertionError: cloud missing for sp_swe` — the real run had staged `clouds_parent/` under the real root; a second launch the same day burned on the missing-prestage sibling.)
- **vLLM `max_model_len` must track every `max_new_tokens` deviation on an inherited eval rig.** On-policy slot reads re-enter the generated response as a PROMPT (prompt + R + marker), and vLLM validates prompt length against `max_model_len` — so the moment a generation hits the `max_new_tokens` cap, the follow-on read exceeds the cap by construction and the eval worker crashes (`ValueError: ... decoder prompt ... longer than the maximum model length`). - **Same-pod relaunch: divergent `.claude/**` spec files block `git pull --ff-only`.** On a same-pod relaunch of an `issue-<N>` branch whose diff carries a "spec-freshness" sync commit (the workflow-surface specs under `.claude/**` were refreshed on the branch), the pod's existing `.claude/**` files diverge from the branch version; `git pull --ff-only` aborts to protect the local edits ("Your local changes to the following files would be overwritten by merge" / "untracked working tree files would be overwritten by merge") instead of fast-forwarding, and the pre-launch sync fails with an unhelpful error. This is the `.claude/**`-spec sibling of the committed-pod-artifacts pull block above (which covers pod-WRITTEN `eval_results/issue_<N>/...` files) — same abort, different file class and different recovery: spec files are discarded back to HEAD, not backed up. Surgical recovery, no force:
  ```bash
  # 1. Stale-lock guard — only after confirming no live git process
  pgrep -x git >/dev/null || rm -f .git/index.lock

  # 2. Identify the divergent .claude/** files (path-scoped diff — fast on MooseFS)
  git fetch origin issue-<N> --quiet
  git diff --name-only HEAD origin/issue-<N> -- .claude/ > /tmp/diverged.txt

  # 3. Tracked-at-HEAD → discard local edits; untracked (new-on-branch) → remove
  while read -r f; do
    if [ -n "$(git ls-tree -r HEAD --name-only -- "$f")" ]; then
      git checkout HEAD -- "$f"          # exists at HEAD: revert pod-side edits
    else
      rm -f "$f"                          # UNTRACKED would-be-overwritten new file
    fi
  done < /tmp/diverged.txt

  # 4. Now the fast-forward succeeds
  git pull --ff-only origin issue-<N>
  ```
  WHY the per-file `ls-tree` filter + tracked/untracked split matters: `git checkout HEAD -- <pathspec-not-at-HEAD>` errors with rc=1 and reverts NOTHING (verified — a single bad pathspec aborts the whole checkout), so a new-on-branch file must be `rm`'d, not checked out. Use the PATH-SCOPED `git ls-tree -r HEAD --name-only -- "$f"` per file — never the full-tree `git ls-tree -r HEAD --name-only | grep` pipe, which is slow on the MooseFS root. NOTE: `git status` / `git diff-index` on the MooseFS tree take ~30s+ (FUSE-slow, and the SSH-MCP layer caps commands at ~30s); use ancestry checks (`git merge-base --is-ancestor`) and path-scoped `diff-index`/`diff --name-only -- <path>` for cheap pre-checks, never an unscoped `git status`.
