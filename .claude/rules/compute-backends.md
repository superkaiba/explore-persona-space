## Compute backends — multi-lane router (GCP FIRST — credit-funded, re-enabled 2026-09-09; RunPod the paid fall-through; fellows access REVOKED (user directive 2026-09-09))

**GCP is the FIRST-resort lane (user directive 2026-09-09: "re-enable GCP", then "GCP before runpod if it's available").** GCP is credit-funded while RunPod now bills the user's personal account — paid, scarce capacity (measured 2026-09-09: balance ~$248 at ~$22/hr burn, roughly 11 h of runway). The router leads the auto order with `gcp`; a gcp capacity miss (nothing provisioned) falls through to `runpod` (`reason: auto_runpod_first` — the token keeps its historical #2054 name), then the free SLURM lanes, and the #656 terminal rung survives as the end-of-chain RunPod RETRY (`reason: auto_fallback_runpod`). The 2026-08-02 GCP disable (#2028) existed because the FREE fellows lane was the standing first lane and agents habit-pinned paid GCP while charmander sat idle (#1739, ~40+ GPU-h); that rationale EXPIRED with the 2026-09-09 fellows revocation. ROLLBACK BUILD ONLY (fellows access revoked — `FELLOWS_ACCESS_REVOKED = False` re-inserts the rung directly after runpod): the free `fellows` SLURM lane (charmander H200: `high-eur` QoS first, park-timeout fallback ladder to `normal-eur` → `low-eur`; explicit `backend: fellows` pins never walk; `realized_qos` rides `epm:backend-selected`; #1899; ladder RESUMABLE across launcher deaths — position persisted to `Lease.free_lane_park_state`, the CLI park bounded per process by `EPS_LAUNCH_PARK_PROCESS_BUDGET_SECONDS` (420 s) → exit 75 `reason: free_lane_park_budget_reached`, a re-run of the SAME launch command reconnects by `squeue --name` with no double-submit, #2161) sits between runpod and the free DRAC/Mila lanes. Known gap (#667): a HUNG-but-`RUNNING` GCP VM with dead guest networking freezes `eps/phase` non-terminal — manual `--backend runpod` pivot. The sibling RunPod no-port wedge has THREE coverage layers by WHEN and WHAT they see (#2184): (1) PROVISION-TIME typed detection — `wait_for_ssh` raises `RunPodNoPortWedgeError` on RUNNING-but-no-port at the 10-min bring-up window, the #2060 auto-teardown terminates the wedged pod, and on CPU intents a teardown-interlocked bias-away DC rotation retries in a different datacenter (rotation re-creates ONLY on a CONFIRMED-terminated teardown; exhaustion → the typed `CPU-LANE-DRY` refusal, exit 77) — the ONLY layer alive in the first ~10 min and the only one covering bare `pod.py provision`; (2) the poller's terminate+failover arm for router-dispatched RunHandles past `RUNPOD_WEDGE_K_SEC` (#664/#770); (3) the watcher's wedge arm as the poller-dead backstop (~25-45 min; #1667 owner guard). Disposition split for the CPU rotation's terminal refusal: a DIRECT-CLI caller gets exit 77 as a terminal refusal with the verdict as runbook, while on the ROUTER path 77 rides the generic `no_compute_available` fallthrough (NOT a router-terminal hard failure — the auto chain advances to the next reachable lane, and a watcher capacity re-drive re-runs the full rotation budget, ~35 min worst case, each time). Full mechanics + reason codes: `.claude/rules/compute-backend-failover.md`. **When ALL lanes are exhausted (capacity, not a workload crash), the auto chain falls through to a RunPod terminal rung** (`reason: auto_fallback_runpod`, with a `runpod_fallback_residual_gap` naming which rungs ran dry — #656; as of #2054 the end-of-chain RunPod RETRY).
