## Compute backends — multi-lane router (RunPod FIRST — the Anthropic-org pool (#2054); then fellows + free SLURM lanes; GCP provisioning DISABLED (#2028))

**RunPod is the FIRST-resort lane (#2054, standing user directive).** The RunPod account behind `RUNPOD_API_KEY` + team `cm8ipuyys0004l108gb23hody` is the shared Anthropic fellows/safety org account — provisioning a pod there is ordinary use of a sponsored pool, NOT discretionary spend. The router leads the auto order with `runpod` (`reason: auto_runpod_first`); a runpod capacity miss (nothing provisioned) falls through to the free SLURM lanes, and the #656 terminal rung survives as the end-of-chain RunPod RETRY (`reason: auto_fallback_runpod`). The local `pod_lifecycle` account-$/hr cap guard is ADVISORY-ONLY as of #2054 (it can never refuse or stall a provision — the RunPod console cap is the enforcement point; cf. `tests/test_no_dollar_budget_caps.py`).

**GCP provisioning is DISABLED by policy (#2028) — no dispatch path may CREATE a new GCP instance (GPU or CPU).** The gate is the single constant `GCP_PROVISIONING_DISABLED = True` in `src/explore_persona_space/backends/router.py` (rollback = flip to `False`; deliberately NO env re-enable): the auto chain carries no gcp rung, an explicit `backend: gcp` pin raises the typed `GcpDisabledError` (`reason: gcp_backend_disabled` — infra/blocked, NOT watcher-re-drivable), a `gcp`-bearing `EPM_AUTO_LANE_ORDER` raises at validation, and the #1596/#1601 GCP on-demand retry legs refuse up front. Paths that only ACT ON existing GCP handles — poll, teardown, crash persist, in-flight GCP→RunPod failovers, the `gcp_audit.py` janitor — keep working; every GCP ladder/failover mention below is scoped to IN-FLIGHT handles + rollback only. Every `/issue` launch routes through the unified backend router (`src/explore_persona_space/backends/`; CLI `scripts/dispatch_issue.py`; helper `issue_dispatch.dispatch_for_issue`), keyed on the task's `backend:` frontmatter:

- **Absent/empty frontmatter → `auto`: `DEFAULT_AUTO_LANE_ORDER = ("runpod", "fellows", "nibi", "fir", "mila")`** (#2054 runpod-first; #2028 GCP removed; pinned by `tests/test_router.py::test_default_auto_lane_order_has_no_gcp`). The runpod lane launches via the same machinery as the terminal rung; a capacity miss with nothing provisioned falls through, while a partial launch that left a pod billing propagates. Behind it, the free `fellows` SLURM lane (charmander H200: `high-eur` QoS first, park-timeout fallback ladder to `normal-eur` → `low-eur`; explicit `backend: fellows` pins never walk; `realized_qos` rides `epm:backend-selected`; #1899) is tried before the free DRAC/Mila lanes (override via `EPM_AUTO_LANE_ORDER`; `runpod` is legal, `gcp` raises). A fellows capacity miss / dead endpoint fails `prepare` → the chain advances; N consecutive fellows `prepare_failed` ⇒ the endpoint-remap recovery on the fellows `CLUSTER_CONFIGS` row (`backends/slurm.py`). SENTINEL DRAIN: fellows is a DRAINED lane (#1898); DRAC/Mila are NOT (no `/workspace`, fail-loud at `mkdir`, #608) — a sentinel-dependent workload pins a drained lane or accepts the fall-through risk (verify_plan c43 WARNs). **The GCP ladder + its FIVE GCP→RunPod failover triggers still exist for IN-FLIGHT handles + rollback only (#2028):** the length-aware spot/flex/on-demand rung ladder, the per-day attempt cap `MAX_GCP_ATTEMPTS_PER_DAY` (a COUNT, never a dollar cap), and five triggers — sync `GcpWorkloadError` (#658), async poller workload-crash (#659), FLEX_START queue-timeout (#783), pre-workload boot-loop (#1029), FLEX_START queue-vanish (#1116) — each routing STRAIGHT to RunPod (no cascade) and BOUNDED: RunPod runs the failed job AT MOST once more; a second crash surfaces `failure_class: code` → `status:blocked`, never watcher-re-driven. Known gap (#667): a HUNG-but-`RUNNING` GCP VM with dead guest networking freezes `eps/phase` non-terminal — manual `--backend runpod` pivot; the sibling RunPod no-port wedge is covered by the watcher's wedge arm (#770/#1667). Full mechanics + reason codes: `.claude/rules/compute-backend-failover.md`. **When ALL lanes are exhausted (capacity, not a workload crash), the auto chain falls through to a RunPod terminal rung** (`reason: auto_fallback_runpod`, with a `runpod_fallback_residual_gap` naming which rungs ran dry — #656; as of #2054 the end-of-chain RunPod RETRY). Only if the RunPod launch ITSELF fails does the chain raise `NoComputeAvailableError`. Spot threshold `EPS_GCP_SPOT_MAX_GPU_HOURS` + the resolved gpu-h estimate ride each per-rung `epm:backend-selected` marker.
- **`backend: runpod` explicit override** is still a first-class PIN (distinct from the auto lane — `reason: override` vs `auto_runpod_first`/`auto_fallback_runpod`). Since #2054 the auto chain already leads with RunPod, so the pin mostly matters for forcing RunPod-specific shapes: 70B intents (no GCP machine-type mapping — fail-loud by design), interactive SSH-MCP mid-run orchestration (the experimenter launch pattern), runs longer than GCP's `--max-run-duration` ceiling (#741), or the SLURM venv-extras mismatch. **Prefer bare `auto` — it already tries RunPod first (#2054).** When pinning, name the reason in the launch marker note.
- **`--backend gcp` / `backend: gcp` is REFUSED outright (#2028).** The explicit gcp pin no longer routes anywhere: `route()` raises the typed `GcpDisabledError` BEFORE any wiring/ladder work, and `classify_terminal_exception` maps it to `failure_class: infra` / `status: blocked` / `reason: gcp_backend_disabled` (NOT watcher-re-drivable — the fix is dropping the pin, or the deliberate `GCP_PROVISIONING_DISABLED = False` rollback flip). DEFAULT: omit `--backend` and let the chain walk. `--provisioning-model STANDARD` is a GCP-ladder knob, inert for fresh dispatches while the flag is on. (Historical rationale: a habit-pinned `--backend gcp` silently forfeited the FREE fellows lane, #1739.)
- **GCP mechanics (in-flight handles + rollback only, #2028):** project `eps-persona-gpu-jun2026` (gcloud config `eps-gcp` threaded per-call via `--configuration=` — NEVER the personal default project), zone `us-central1`, DLVM image, instances named `eps-issue-<N>`. Intent→machine mapping + width-aware wide rungs: `backends/gcp.py` (`INTENT_TO_MACHINE`, `WIDE_A100_80_BY_WIDTH`). Instances are EPHEMERAL BY DESIGN — `--instance-termination-action=DELETE` + `--max-run-duration` (default 7d, #741) + EXIT-trap teardown — so an empty instances list does NOT mean the lane is unused; read the `epm:backend-selected v1` markers. A janitor sweeps stale `eps-issue-*` instances. **Crash diagnostics survive the DELETE (#658/#854):** on rc != 0 the EXIT trap runs `_eps_persist_diagnostics` — uploads the workload log + partial artifacts to `issue<N>_partial/<attempt_id>/` on the HF data repo (crash_report.json, workload.log, worker_logs/, partial eval/data dirs, a transcript uploaded LAST), guarded + 300s-bounded; check `superkaiba1/explore-persona-space-data/issue<N>_partial/` after a `failure_class: code` GCP crash.
- **CPU-only intents route RunPod CPU (`deployCpuPod`) — ALL THREE mapped (#2028)** in `RUNPOD_CPU_INSTANCE_FOR_INTENT` (`backends/router.py`): `cpu-small` → `cpu3g-2-8`, `cpu-mid` → `cpu3c-8-16` (#747), `cpu-bigmem` → `cpu5m-16-128` (16 vCPU / 128 GB, container-disk cap 240 GB via `--boot-disk-gb` threading — #2028, superseding the #677 "no RunPod lane" terminal FOR THIS INTENT). With GCP disabled a CPU auto route lands directly on the RunPod terminal rung (the free SLURM lanes stay excluded for CPU intents, #1464); the #677 `cpu_exhausted_no_runpod_lane` typed terminal STAYS as the fail-loud floor for a future UNMAPPED CPU intent. Both the synchronous `_runpod_terminal_rung` and the async `_is_gcp_async_workload_failure` (`backend_poll.py`) key on that same map. RunPod CPU pods are on-demand only; a CPU no-capacity miss surfaces `RunPodNoCapacityError` → terminal.
