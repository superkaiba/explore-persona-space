- **User-chat inline free analysis** (interactive chat only — the user DIRECTLY asks to run a `0-GPU-h free analysis` on EXISTING artifacts: eval JSONs, raw completions, activation stores already on disk / HF) — RUN IT INLINE with a read-only subagent (an `experiment-implementer` constrained to ANALYSIS-ONLY — no new training, no new eval generation, no new data — or a `general-purpose` analyzer), NOT through the `/issue N` follow-up loop. Routing here is by COST + ARTIFACT-EXISTENCE, not phrasing: a user-chat 0-GPU-h ask on existing artifacts takes this inline path even when phrased "as followups" / "run these followups" — the word "followup" does not re-route a zero-GPU existing-artifacts ask to the spawn/loop path. (A GPU-NEEDING ask takes this inline path only under the explicit user inline override below.) This is the USER-INITIATED sibling of the PROPOSER-initiated Step 9a-ter zero-GPU floor (SKILL.md § 9a-ter): same execution shape (ANALYSIS-ONLY edits, single-round, `abort + reclassify as needs-gpu` if the analysis turns out to need new data), just triggered by a chat ask instead of an analyzer-surfaced `cost_class: free-analysis` follow-up. **Provenance is a plain `epm:progress` note on #N** (naming the ask + a one-line result summary) followed by an `epm:free-analysis-followup-run v1` marker on completion — **do NOT post `epm:followup-scope v1` on the inline path.** `epm:followup-scope v1` is the arming trigger for the SKILL.md Step 0 same-issue follow-up dispatcher (satisfier: a matching `epm:same-issue-followup-run v1`, a different marker kind than the inline path posts), so leaving one unrun on #N would re-arm the very `/issue N` loop this carve-out exists to skip on the next tick. The subagent folds its finding into the discussion; a live `/issue N` session, if any, absorbs it into the clean-result body on its next analyzer pass. **Same-turn completion contract (0-GPU and override rounds alike):** an inline round is COMPLETE only when, in the SAME turn as the result summary, (1) the round's eval JSONs + figures — and any analysis scripts it wrote — are committed by explicit path (never `git add -A`) — with the staged index VERIFIED after any directory-path add: `git ls-files --others --ignored --exclude-standard -- <round dirs>` returns empty of convention-committed hits after `git add -f`-ing them (a dir-path `git add` silently skips gitignored files with rc=0 and no error — #958 round 7 shipped without its `percell/*.npz` cells under the repo-wide `*.npz` rule; canonical recipe: SKILL.md Step 9a-ter § Staged-index verification) — and pushed, with any non-artifact payload (scripts/src files the round wrote) FIRST passing the **inline payload lint gate** (no-flags `workflow_lint.py` + the `select_step9c_tests.py --map-files` mapped tests; verdict payload-attributed with an instrument-ran completeness check — a non-WARN failure line naming a round-committed file blocks the push, pre-existing red elsewhere never does, and a dead/silent leg is INCONCLUSIVE, never push-clean; canonical recipe: SKILL.md Step 9a-ter § Inline payload lint gate; #1388: two inline-landed lint-red scripts broke the Step 9c gate fleet-wide), AND (2) the finding is folded into the parent's clean-result/report body — or the `epm:progress` completion note carries an explicit one-line deferral naming who folds it and when (incident #779, 2026-07-06: an inline round's `fair_comparison.json` sat modified-but-uncommitted for 8 days beside a stale report Result 3 the user found himself). **Session-collision distinction:** a live per-issue session owning #N blocks RE-SPAWNING `/issue N` (SKILL.md Step 0 single-orchestrator guard — detect-and-exit, incident #535), but does NOT block an INDEPENDENT read-only subagent that only READS artifacts + posts a marker — that subagent mutates no task lifecycle state and races nothing. If the ask needs new training / eval data (i.e. is not zero-GPU or not on existing artifacts), it is a `**Follow-up**` (re-invoke `/issue N`) or a `**NEW direction**`, not this carve-out. **Explicit user inline override (the one exception):** when the user EXPLICITLY directs inline execution ("run it inline", "run it inline so it is faster", killing a just-spawned session and asking for inline), honor the override and run the follow-up inline EVEN when it needs GPU — do not spawn (or re-spawn) a session against the ask (2026-07-14: 4 spawned sessions on #658/#1092/#1090/#952 killed within ~2 min after exactly this ask). The override inherits this carve-out's duties unweakened: post a dispatch-time `epm:progress` override note on #N quoting the verbatim ask + the estimated GPU-h + the compute-character pre-launch statement (extended with the GPU parallelization shape), carry the pod-safety pre-launch signals below (`keep-running` tag BEFORE/AT provision + `epm:run-launched` once the pod exists), and still post NO `epm:followup-scope v1` — and NO `epm:free-analysis-followup-run v1` either (that marker is the 9a-ter one-round cap key; this is not a free-analysis round — the override note + `epm:progress` completion note are the durable record). KILL-MID-LOOP DISARM: when an `epm:followup-scope v1` was already posted BEFORE the override (routed → spawned → killed → "run it inline"), the inline override round posts the MATCHING `epm:same-issue-followup-run v1` on completion so the armed scope cannot re-drive the Step 0 dispatcher (#952, 2026-07-15: the 05:47Z run marker is what disarmed it); a fresh override ask with no prior scope marker posts neither. The explicit ask IS the user's spend approval for that run; an estimate over 20 GPU-h (the `compute:large` rail — so a ≥`EPM_PLAN_AUTOAPPROVE_GPU_HOURS` run is never silent) still gets a one-line confirm in the chat before provisioning. USER-INITIATED ONLY: an autonomous session has no user to override — autonomous routing is unchanged. **Detached-by-default + lifecycle ack (any user-chat inline dispatch of pod/VM-side work):** when an inline round (0-GPU carve-out or override alike) dispatches pod/VM-side work that outlives the current turn — a training/eval launch, a pod-side gate wait, a long detached fit — ARM the detached handoff chain AT dispatch, by default — never deferred until the user asks: the workload launches detached under the established conventions (the pod-side sentinel/launcher contract; the setsid + pid/log/harvest breadcrumb shape for VM-local phases — this COMPLEMENTS, never supersedes, the mandatory detached shape for VM-local phases >~15 min) and the dispatch-time `epm:progress` note records the re-attach handles (pod name or pid, absolute log path, harvest/output path) so the round's remaining chain (gate→relaunch, harvest, upload-verify) survives this terminal closing and any successor session can re-attach; AND the dispatch ack VOLUNTEERS the lifecycle line unprompted — what runs detached and WHERE (pod / tmux / worktree address), what dies with this terminal, and the safe-to-close verdict. Waiting for the user to ask "can I safely close this terminal?" — or to explicitly order the background handoff — is the failure mode this clause closes (#1689 inline R16, 2026-07-28: the gate-dispatch ack omitted lifecycle; two extra user turns, ~25 min in which closing the terminal would have orphaned the gate→relaunch handoff). **Pod-safety pre-launch signals (deviation case):** if an inline/user-chat run nonetheless provisions or reuses a pod on a parked (`on_hold`) or terminal-status parent, the launching session MUST run `task.py add-tag <N> keep-running` BEFORE/AT provision — before any pod work; the timestamp-independent tag is what shields the provision/bootstrap window, which the watcher's ≥2-miss accumulation (~20 min) would otherwise auto-stop straight through — AND post `epm:run-launched` on #N immediately once the pod exists (note naming the pod + the ask; in any case before launch). The watcher's pod-safety pass auto-stops a RUNNING pod on such a parent unless a follow-up signal marker (its predicate reads `epm:run-launched` / `epm:followup-scope` / `epm:free-analysis-followup-run` — a descriptive list, NOT a menu: the inline path still never posts `epm:followup-scope`) is NEWER than the latest done-transition (`epm:promoted` / `epm:status-changed`) or the `keep-running` tag is set; BOTH duties bind — the marker cannot exist during the provision/bootstrap window (#573: run-launched-only inference stopped healthy follow-up pods 11×) and any later done-transition flips the inferred predicate off by design (the watcher's re-arm semantics), while the tag alone loses the run record (incidents #477, #573; #779 2026-07-06: pod-779, launched with neither signal, was repeatedly auto-stopped mid-bootstrap and misdiagnosed as a flaky host) — remove the tag (`task.py remove-tag <N> keep-running`) when the run completes so the auto-stop re-arms (a crashed run leaves the tag and the pod bills until manual removal — check `pod.py audit-stale` output; the watcher's keep-running wedged-owner arm (#1582) escalates a tagged RUNNING pod with a provably wedged/absent owner within ~12h). **Per-pod shield on multi-round issues (#1961):** the watcher shields a SUFFIXED pod (`pod-<N>-<slug>`) PER-POD when its `epm:run-launched` note names it in STRUCTURED position — LEAD the note with the pod name, or carry a `pod=<name>` token (load-bearing, not stylistic: a sibling round's `epm:status-changed` otherwise strips the issue-grain inferred shield) — ceiling-bounded (default 48h, `EPM_POD_NAMED_SHIELD_MAX_AGE_H`); `keep-running` stays the explicit override. **Completion-side teardown (no ask-gate):** in that SAME completion step — run complete + uploads verified (THIS round's artifacts, not a prior round's PASS) — TERMINATE the pod the round provisioned (surgical `pod.py terminate --issue <N> --name-suffix <slug> --yes` for a suffixed `pod-<N>-<slug>`; the bare `--issue <N> --yes` form only when the round's pod is the issue's ONLY live pod, with the `keep-running` tag removed FIRST — #1485 refuses the bare form while the tag is set, and it destroys EVERY live pod resolving to the issue): verified-done teardown is unconditional — Step 8 already auto-terminates the primary pod on upload-verification PASS, and a suffixed follow-up pod gets the same contract (#1662: pod-1586-b idled ~$12–13/hr behind an ask-gate) — EXCEPT when a NAMED next queued round reuses this pod (record it in the completion `epm:progress` note and keep the tag; a pending user question is NOT a named round). Never terminate before uploads verify (the durability contract wins), and never substitute `pod.py stop` for verify-then-terminate (a STOPPED volume is NOT durable, #1112). The sanctioned verify-then-terminate recipe: verify THIS round's artifacts → post `epm:upload-verification` with a note LEADING `Verdict: PASS — inline-round verification; prefixes: <every verified prefix>` via `task.py post-marker` → terminate; a bare `--skip-upload-verify` without a recorded verify is the anti-pattern, reserved for never-ran pods (the terminate guard, `pod_lifecycle._guard_upload_verification_before_terminate`, accepts the marker — the front door already exists, #465/#1773). And a per-issue upload-verify script MUST enumerate ALL HF prefixes the run wrote (reconcile against the run's staging/upload call sites), never only the current phase's prefix (#1773: `raw_windows`, 8h50m of GPU output, verified only by an ad-hoc hand set-diff). The line-52 Takeaways litmus is ORTHOGONAL and unchanged — it decides SAME-issue vs CHILD-task for work that DOES need new data; this carve-out decides INLINE vs LOOP for SAME-issue reads on existing artifacts. A re-read that surfaces a new takeaway from existing data folds into the parent body via the analyzer's next pass (no new task, no loop). **Autonomous-mode routing is UNCHANGED** — this carve-out is scoped to interactive-chat user asks; the proposer + auto-run bands (Step 9a-ter 0-GPU floor, Step 9b `0 < est_gpu_hours < 20` cheap band; CLAUDE.md § "After Every Experiment" item 9) fire exactly as before in both session modes. **Compute-character pre-launch statement (REQUIRED — this carve-out skips the planner+critic stack, where all compute-character review lives):** "0 GPU-h" does not mean "0 compute review" — the SAME duty binds three surfaces: plan §9 rows (their §-scoped wording), this carve-out (user-chat inline runs, this block), AND teammate/orchestrator/subagent mid-session box dispatches OUTSIDE §9 (see `.claude/rules/plan-compute-sizing.md § Teammate / mid-session box dispatches` — the residual-class binding surface, closing the #1739 sizing-miss channel). Before the subagent launches any fit, sweep, or statistical battery (permutation/bootstrap/null draws, per-cell/per-fold fits, per-row model calls), a SEPARATE dispatch-time `epm:progress` note, posted BEFORE launch — the carve-out's existing provenance note (the ask + one-line result summary) stays the COMPLETION record — states the ops arithmetic (cells × folds × draws × epochs → projected wall-time), the named BATCHED helper implementing the inner loop (or why genuinely not batchable), and — for reused parent code — that its inner loop, device routing, + data-repo Hub-call scoping were inspected (cf. `.claude/rules/artifact-reuse.md`), and — for any stage that downloads or materializes ≥ ~5 GB (HF snapshots, tensor stores) — the staging path named up front + the filesystem it resolves to (`df -P`) with free headroom ≥ ~1.5× the projected bytes: multi-GB staging goes to the data disk (`data/issue_<N>/hf_dl/` wherever it resolves off `/`, else an existing user-writable per-issue dir `/mnt/eps-data/$USER/issue<N>_<slug>/`), NEVER `/`, `/tmp/`, or a fresh top-level `/mnt/eps-data/<dir>` (root-owned; #1393: a 14 GB inline HF pull filled `/` → ENOSPC) — and ≥ ~50 GB of staged fit/analysis inputs routes the CONSUMING phase off the VM (`cpu-bigmem` / pod) at dispatch, never after deaths (#1345). Projected wall-time > ~15 min for any fit/battery stage ⇒ the per-call basis MUST be a MEASURED 1-cell pilot through the production entrypoint at production shape, run FIRST (or a cited prior-issue MEASURED figure for the SAME kernel + shape; an asserted/guessed per-call cost is never a sizing basis — `.claude/rules/plan-compute-sizing.md` § Per-cell fit phases); state the measured per-cell wall in the dispatch note and size any self-set timeout/fence ≥2× the pilot-extrapolated wall (measured per-cell wall × remaining cells / parallelism — the p90-style ×2 dispersion default); never a fence below that, never a user-facing wall-time claim from a guessed basis (#1092 session f4b1d707, 2026-07-23: a guessed `timeout 3000s` killed a healthy ~25 min/cell run, exit=124). Projected wall-time > ~1h without a batched inner loop ⇒ STOP, vectorize first (`.claude/rules/vectorize-many-cell-fits.md`), then launch (incidents #667/#722/#778; canonical block: SKILL.md Step 9a-ter § Compute-character pre-launch statement); an iterative-optimization fit leg whose post-vectorization CPU phase wall exceeds the ~15–30 min GPU-worthiness floor (per-cell > ~15 min suffices) routes to a GPU lane at dispatch — never behind a descope-if-slow gate (#1768). **Inline measurement-design + figure-sanity duties (REQUIRED — same rationale: this carve-out skips the planner+critic stack, where the both-arms mapping review and the critic's figure-load check live):** (1) an inline round that computes a representation mapping — a geometry read, predictor, probe, or direction extraction over model activations — states in its dispatch-time `epm:progress` note that BOTH arms run (prefix-based AND context-based, per the Critical Rules "Prefix mapping AND context mapping" bullet) or names the explicit stated deviation (#779's 2026-07-14 inline pre-image round shipped context-only — the #958 one-arm class — and the user had to catch the missing prefix arm); (2) before PRESENTING or committing any figure the round rendered, Read the rendered PNG and confirm non-empty axes + plotted series and sane value ranges — an empty/blank render is a round bug to fix, never present or commit it (#1112: an empty figure was presented 3× while the extraction bug was found; interpretation-critic Lens 6's PNG-load check does not run on inline rounds). Canonical block: SKILL.md Step 9a-ter § Inline measurement-design + figure-sanity duties. **Inline estimator-validity + record-integrity duties (REQUIRED — same rationale: this carve-out skips the planner+critic stack, where the fit-well-posedness / estimator-parity / promoted-body-consistency reviews live):** (1) BEFORE any ridge / linear-map / probe FIT, the dispatch note states `n_train` vs the feature dimension `d`; when `n_train < d` the round REFUSES the fit unless the note explicitly justifies a deliberately under-determined regime (regularization-limit / null-space read / smoke shape) — every held-out R² in the `n_train < d` regime is estimator-degenerate, not a signal read (#1701, sess `dffde9b6`: n=1,877 vs d=3,584 → ceiling 0.099 vs published 0.625). GCV-specific ban (#1887): pure-GCV λ selection at n_train < d is REFUSED (the shared #825 fit cores enforce this by default — GCV runs only WITH a dof cap, default 0.9, or under an explicit LEGACY_UNGUARDED_GCV opt-in), and selected-λ diagnostics (per-fit selector + selected λ) are reported alongside every ridge read. (2) BEFORE launching any re-implemented estimator whose in-repo reference the round can name (a `scripts/issue1345_operator_comparison`-style chain, a canonical `ridge_fit_predict_fast`, a shipped judge/scorer), the dispatch note records the DIFF between the new estimator and the named reference (function + file) — permissiveness-broadening (more inputs absorbed, weaker constraints) is called out explicitly. (3) When a round REFUTES a claim in ANY task's promoted body (its own parent or a sibling), it MUST — in the SAME turn as the result summary — either apply a NON-Takeaway PROSE correction directly to the refuted task's body via `task.py set-body` (typo / caption / fixed numeric value — never `task.py promote` or a `classification` flip; the user-only classification contract is unchanged) OR file a `kind: infra` task via `scripts/file_infra_task.py` naming the refuted issue and the refuting evidence — filing is the presumption for anything touching a bolded Takeaway; a chat-only "I did not fix X" is an INCOMPLETE round (#825's promoted Takeaway was refuted and nothing filed; #1701 origin). **Instrument-supersession + scope-extension addenda duties (REQUIRED — same rationale: this carve-out skips the planner+critic stack, where instrument-fitness review and plan-revision re-review live):** (1) BEFORE dispatching any stage that spends on a measurement instrument (an LLM-judge rubric, a labeling scheme, a scorer) — and AGAIN the moment such knowledge lands mid-round — the round checks (a bounded check: session knowledge plus a quick task-title scan, never an unbounded fleet-wide search) whether a SUPERSEDING instrument for the same measurement is in flight (a filed / in-progress task building a stronger replacement — the #1773 shape) or the current instrument is known-weak with a named replacement being designed; if so the DEFAULT is to HOLD the spend-bearing stages (Batch-API judge calls, GPU evals) until the superseding instrument lands — recorded as an `epm:progress` hold note naming the superseding task — and proceeding anyway requires the dispatch note to state why the known-weak instrument still serves (needed now / results not superseded / trivially cheap), never leaving the freeze to user vigilance (2026-07-28: three live SAE rounds kept burning Batch-API judge spend on labels #1773 was designed to supersede; frozen only after the user asked twice). (2) A mid-round SCOPE-EXTENSION ADDENDUM — a user ask or self-initiated extension adding cells / draws / rows / behaviors / stages to a live inline round — is a DISPATCH for duty purposes (the scope-extension sibling of the compute-character block's "realized implementation later adds a fit/battery" drift sentence): it carries its own compute-character pre-launch statement (ops arithmetic, named batched helper, parallelization width) plus whichever other duty blocks its content triggers (both-arms mapping, figure-sanity, estimator-validity), posted BEFORE the addendum launches (2026-07-28: "parallel + vectorized" had to be re-stated twice before a throughput addendum landed — the statement bound only the original dispatch).
