## After Every Experiment

1. **Verify uploads + clean weights** per Upload Policy: eval JSONs + figures in git on the issue branch, raw completions on HF data repo, checkpoints on HF model repo, then delete safetensors/merged dirs from the pod.
2. Save structured JSON to `eval_results/`; log all metrics to WandB.
3. Generate plots (bar charts with error bars, pre/post) → `figures/`.
4. The `analyzer` agent **promotes the task body IN PLACE** to a clean-result: snapshot prior body to `original-body.md` (`task.py set-body --snapshot`), then `set-title` + `set-clean-result`. Classification stays `pending` until the user runs `task.py promote <N> useful|not-useful`. Title: `<one-sentence claim> (HIGH|MODERATE|LOW confidence)` — no prefix. Run `verify_task_body.py --issue <N>` first; FAIL blocks. **`paper: true` task:** the canonical clean-result is the LaTeX paper under `docs/papers/issue_<N>/`, `body.md` becomes a thin paper-stub, the analyzer runs PAPER-TASK MODE, and the mechanical gate is `verify_paper.py` (NOT `verify_task_body.py`); `set-clean-result` validates `paper_manifest.json` for a paper-task.
5. Update `RESULTS.md` and `docs/research_ideas.md`.
6. **Disk check:** `df -h /workspace` — below 100GB free, run `pod.py cleanup --all --dry-run`. For the **VM root disk** (`/`), the per-experiment download caches are cleaned at `/issue` Step 8 (see § Disk hygiene below).
7. **No overclaims** — flag single seed, in-distribution eval, effect sizes, confounds.
8. **Verify planned conditions were actually tested.** If any planned cell/factor/condition silently failed, the clean-result body MUST: (a) name the missing condition in `## Takeaways` AND the relevant `### <result>` prose; (b) revise the hypothesis denominator to match actual coverage everywhere, figure/table captions included; (c) omit the missing condition from figures OR label it `N/A — not tested` (never a misleading zero bar). Enforced by `verify_task_body.py` check 11b + `clean-result-critic` planned-vs-actual lens.
9. **Auto-run cheap (`< 20` GPU-h) same-question follow-ups before parking — both session modes.** A `0` GPU-h or `< 20` GPU-h follow-up just runs and folds into the SAME issue, automatically, in interactive AND autonomous sessions — no human pick, no `headline_affecting` gate. **Every follow-up proposal first passes the single-pass REDUNDANCY screen (`follow-up-critic` + Codex twin; § Codex ensemble review) BEFORE it routes to ANY path**; a `redundant` proposal is SAVED as an `on_hold` task (`epm:followup-parked-redundant v1`, revivable), `not-redundant` ones proceed, NOTHING is dropped; the bar is redundancy only, NOT info-gain. User-requested follow-ups (`source: user-chat`) are not screened. The analyzer (Step 6.5) + follow-up-proposer tag every follow-up with `cost_class`, `headline_affecting` (user-facing signal only), `est_gpu_hours`, and `question_relation`. Two auto-run bands, both `question_relation: same` only, both auto-continue (NOT a new `AskUserQuestion` gate):
   - **Zero-GPU floor (`cost_class: free-analysis`, `est_gpu_hours: 0`), Step 9a-ter:** the orchestrator AUTO-RUNS it inline (`experiment-implementer` + `code-reviewer`, implementer constrained to ANALYSIS-ONLY edits — abort + reclassify as `needs-gpu` if new data turns out to be needed), re-spawns the analyzer to fold the result into the parent clean-result body, then proceeds to the clean-result-critique gate. Capped at ONE round per task (idempotent via `epm:free-analysis-followup-run v1`); fires regardless of `headline_affecting`.
   - **GPU-backed cheap band (`0 < est_gpu_hours < 20`), Step 9b cheap-band block:** the orchestrator AUTO-RUNS it via the same-issue follow-up loop (held at `followups_running`, folded into the EXISTING clean-result body, re-parked at `awaiting_promotion`). Strict `< 20` (exactly 20 does NOT auto-run). Capped at 2 cheap rounds per task (counted by `epm:same-issue-followup-run v1` / `source: proposer-9b-cheap`); the Step 2c plan-approval GPU-hour cap is the backstop. **Fail-safe:** a `same` proposal with a missing / unparseable `est_gpu_hours` does NOT auto-run — it parks/files for the user.

   A `question_relation: substantially-different` follow-up NEVER auto-runs on either band regardless of cost — it would change the parent `## Goal`, so it stays filed as a `proposed` child for manual triage. The EXPENSIVE (`>= 20` GPU-h / no-estimate) `auto_run: yes` routing at Step 9b stays autonomous-only: same-question proposals loop ON the parent issue, substantially-different ones are FILED as `proposed` children — never auto-spawned as sessions. **Campaign exception (user-approved contract change):** an APPROVED `kind: campaign` session MAY auto-file AND auto-spawn substantially-different children, bounded by the campaign budget (`.claude/skills/campaign/SKILL.md`). Worked example: #514's matched-rate re-bootstrap (LOW → DETERMINATE with zero GPU).
10. **Export the body's `## Methodology` section to a standalone methodology doc and link it from the clean-result.** Every `kind: experiment` clean-result auto-gains `docs/methodology/issue_<N>.md` — a **mechanical COPY of the v4 body's `## Methodology` section** (H2 normalized to `# Methodology — issue <N>`); no separate findings-blind authoring under v4 (the analyzer's factual `## Methodology` IS the source). At `/issue` Step 9a-quater (after `clean-result-critic` PASS, before the `awaiting_promotion` park) the orchestrator copies the section, commits it to **`main`** by explicit path, runs a no-secrets pre-scan, publishes a SECRET gist mirror (`gh gist create`, fail-soft), and appends a one-line `**Methodology:**` pointer at the TOP of the body (after the `<!-- clean-result-v4 -->` sentinel) linking the SHA-pinned blob + gist. Both session modes; auto-continue; idempotent via `epm:methodology-doc-generated v1`. Skipped for `kind: infra | batch | survey`; grandfathered v3/v2 bodies keep the legacy methodology-writer path (SPEC.md). **`paper: true`:** SKIPPED — Methods + Appendix are already in the `.tex`; 9a-quater posts the marker with a `skipped — paper-task` note.
11. **Results-driven literature-positioning (Step 10c-bis).** After a `kind: experiment` (or finding-bearing `kind: analysis`) clean-result lands, `related-work-finder` runs in the Step 10b/10c/10c-bis batch (∥ `follow-up-proposer` + `living-docs-updater`): a bounded findings-keyed arXiv-MCP + web search (≤6 MCP / ≤2 web calls) that PROPOSES — never applies — a ≤80-word MCP-verified "Related findings" note for the clean-result `## Goal` → `**Broader narrative:**` slot (every cited arXiv id resolved in the same turn; drop-if-unresolved). Routes through the NON-BLOCKING `related_work_positioning` gate (confirm → splice + `epm:related-work-applied v1`; reject → `epm:related-work-rejected v1`). 0 GPU-h. `kind: infra | batch | survey` exempt. **v1 applies ONLY the `## Goal` clause**; `docs/papers.md` candidates surface as a manual-triage list.
12. **End-of-session:** `git status` — commit modified drafts/RESULTS.md/eval JSON before ending.
