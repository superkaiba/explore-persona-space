## Pods (Ephemeral Lifecycle + CLI + SSH)

RunPod pods — the FIRST-resort auto lane as of #2054, and the explicit `backend: runpod` pin — are created on demand per experiment. **Lifecycle:** `provision` → run → upload artifacts → upload-verification PASS → **auto-terminate**. **Naming:** `pod-<N>` (canonical; the legacy `epm-issue-<N>` prefix is recognized in-flight, never used fresh — `pod_lifecycle.py` `_MANAGED_PREFIXES`); a round needing a SECOND pod uses `pod-<N>-<slug>` via `pod.py provision --issue N --name-suffix <slug>` (lowercase letter-initial slug; the owner stays task N — NEVER a fabricated issue id, #1334); suffixed follow-up pods inherit the follow-up pre-launch signal duties (`keep-running` / `epm:run-launched`), and the `keep-running` shield is ISSUE-WIDE — it also blocks Step-8 teardown of the primary `pod-<N>` (mechanically enforced, #1485) (surgical destroy: `terminate --issue N --name-suffix <slug>`). **Completion-side teardown (suffixed pods — no ask-gate, #1662):** the moment a suffixed pod's round is COMPLETE and its artifacts are VERIFIED-uploaded (the same bar as Step 8 — verification includes the out-root TOP-LEVEL residue sweep, upload-verifier Step 2.10 / `verify_uploads.py --outroot-listing`, a per-file NAME-SET diff: a matching count is not a matching set (#2162); the PASS note carries `outroot=<swept-clean|residue-committed|none>` and `pod.py terminate` refuses without it, #2187), the owning session terminates it — `pod.py terminate --issue <N> --name-suffix <slug> --yes` — removing the `keep-running` tag in the same step when no other live round needs the shield; terminating a verified-done pod is NEVER a user decision (the #664 idle-burn family; the surgical form is the tool because the BARE issue-wide form destroys EVERY live pod resolving to the issue and refuses under the issue-wide tag, #1485). The ONLY keep-alive exception is a NAMED further round reusing THIS pod, recorded in an `epm:progress` note — a PENDING USER QUESTION is NOT a named round (terminate; reprovision is cheap). This is the standing exception to the ask-before-terminating-pods rule, exactly as Step 8 is. `pod.py stop` is never a durability substitute (a STOPPED volume is NOT durable, #1112 — persist/verify first, then terminate). One pod per experiment; follow-ups provision fresh. `/issue` Step 8 runs `pod.py terminate --issue <N> --yes`, posts `<!-- epm:pod-terminated v1 -->`, proceeds to `interpreting`. Skip only with the `keep-running` tag.

**CPU-only intents (#747/#2028)** — cheap dedicated RunPod CPU pods (`deployCpuPod`; the GCP E2 lane is rollback-only, #2028). One pod per `provision --issue <N>`, but **CPU pods MAY run in parallel** (the "one multi-GPU pod, not many single-GPU pods" rule is GPU-specific). The stale-pod audit cron is the proliferation backstop (EXITED-24h rule).

| Intent | RunPod CPU | GCP machine (rollback-only, #2028) | Use for |
|---|---|---|---|
| `cpu-small` | `cpu3g-2-8` (2 vCPU / 8 GB) | `e2-standard-2` | parallel CPU fan-out; non-trivial CPU work that fits 8 GB |
| `cpu-mid` | `cpu3c-8-16` (8 vCPU / 16 GB) | `e2-standard-8` (32 GB) | 8-vCPU CPU work between `cpu-small`'s fan-out and `cpu-bigmem`'s bigger analyses |
| `cpu-bigmem` | `cpu5m-16-128` (16 vCPU / 128 GB; effective container disk DEFAULTS to ~50 GB — pass `--container-disk-gb` (pod.py) / `--boot-disk-gb` (router) up to the 240 GB cap — #2028) | `n2-highmem-16` | >50 GB-footprint / >16 GB-RAM analyses (the #677 typed terminal now fires only for a future UNMAPPED CPU intent) |

(The `cpu-mid` RunPod row is 16 GB — with the 32 GB GCP E2 shape rollback-only (#2028), a >16 GB CPU job targets `cpu-bigmem` (128 GB); a plan that STATES a larger footprint (router flags `--boot-disk-gb` / `--min-ram-gb` on `dispatch_issue.py launch`) gets the disk threaded into `containerDiskInGb`, and an unsatisfiable disk/RAM requirement refuses the fallback typed (`cpu_fallback_infeasible_for_plan`, #1010) instead of provisioning an undersized pod. ADOPTION — the disk flag differs BY PATH: router / plan §9 dispatch (`scripts/dispatch_issue.py launch`) takes `--boot-disk-gb` (threaded into the provision argv as `--container-disk-gb max(50, boot_disk_gb)`); direct provisioning (`scripts/pod.py provision`) takes `--container-disk-gb` — pod.py has NO `--boot-disk-gb`, and a bare intent defaults to ~50 GB effective disk on `cpu-mid`/`cpu-bigmem` (container 50 / CPU volume 40; clamped to the flavor cap on `cpu-small` — 20 GB). Pass the path's flag whenever a CPU stage sizes disk > 50 GB, and `--min-ram-gb` (router path) whenever it sizes RAM > 16 GB — the flags are what arm the gate.)

Override with `--gpu-type` / `--gpu-count`. `pod.py provision --list-intents` for the table. When a shardable axis exists, WIDE provisioning is the ENCOURAGED default (wall-clock is scarce) — shard across fellows H200 nodes / a wide RunPod pod (the wide-GCP rung walk is rollback-only, #2028); narrow remains correct when nothing shards, and every idle-width protection (saturate-or-downsize, #664/#778) is unchanged.

**CPU-only phases don't hold GPU pods — and PREFER a cheap dedicated CPU pod over the shared VM for non-trivial CPU work (#747).** Route a NON-TRIVIAL CPU-only phase (parallelizable, large-footprint, or beyond the trivial sub-minute floor) to `cpu-small` / `cpu-mid`, N pods in PARALLEL where the work shards — not the shared VM (#658 filled `/` and stalled the fleet). Only TRIVIAL quick ops (sub-minute probes, quick plots, a one-off `lstsq`) stay on the VM. **Throughput gate — RunPod CPU is the DEFAULT venue for CPU-only work on SPEED grounds, not only safety (#2054).** The >50 GB disk and ≥16 GB RSS carve-outs below are SAFETY gates (avoid filling `/`, avoid an `earlyoom` kill); this gate fires FAR BENEATH both. MEASURED #2054: the fits fleet ran ~**6× faster per unit** on `cpu-bigmem` (`cpu5m-16-128`, 16 uncontended vCPU at `OMP=16`) than the same production entrypoint on the shared VM. The mechanism is CONTENTION, not hardware: the VM's cores are shared across ~15 concurrent Claude sessions plus crons, so a per-unit wall measured on the VM prices the fleet's load, not the work — and that contention is unbounded and not under the plan's control. Three consequences: (i) a CPU-only phase projected past the trivial floor routes to a RunPod CPU pod (`cpu-small` / `cpu-mid` / `cpu-bigmem`) EVEN WHEN both safety gates pass — cheap CPU width beats a contended free core, and CPU pods may run N-in-parallel; (ii) a per-unit wall measured ON THE VM is NOT a valid basis for a pod-venue projection, nor the reverse — the pilot gate measures AT the production venue (#2054 ladder: "the built-in auto pilot gate measures the 1-unit wall at the production venue"); (iii) once a measured pod-vs-VM ratio exists for a task, CITE it rather than re-deriving — the #2054 ladder dispatch chose its venue from the fits fleet's measured 6× advantage instead of re-piloting. Long CPU phases (bootstrap/permutation stats, eval-JSON aggregation, judge-API-only scoring, plotting) MUST NOT hold a GPU pod; sequence uploads so the pod stops/terminates BEFORE the CPU phase starts. **The FINAL upload phase is itself CPU-only** — RELEASE the GPU pod first (terminate/stop after the last GPU phase checkpoints, then upload off-pod), or stream the upload off-pod; a multi-GPU pod idle through a long terminal upload is the #664 spend-leak (the poller ESCALATES). Use one bulk `upload_folder` commit — never a per-file `upload_file` loop (504-storms; `.claude/rules/gotchas.md`). Plan-time rule: `planner.md` §9, `critic.md` Methodology lens item 10. **DOWNLOAD carve-out — anything that downloads a lot of data runs on a POD, even when it is CPU-only (standing rule, Thomas 2026-08-06: "anything that needs to download a lot of data should run on a pod even if it's CPU only").** This is STRICTER than, and fires BEFORE, the >50 GB footprint gate below. ANY phase that pulls a large dataset / model / artifact set to local disk — an HF `snapshot_download`, a `hf_dl`/`*_dl` staging pull, an `hf_hub_download` loop, a bulk `list_repo_tree` + fetch, an rsync/scp of results off a pod — provisions a POD (`cpu-small` / `cpu-mid` / `cpu-bigmem`, whichever fits; GPU only if the phase also needs one) and downloads THERE, never onto the shared VM. **Trigger threshold: ~10 GB** — deliberately far below the 50 GB footprint gate, because that gate has repeatedly failed to fire on downloads that still broke the fleet: #1393 was a **14 GB** inline HF pull that filled `/` with ENOSPC while passing the 50 GB check. Treat "I'm not sure how big this is" as OVER the threshold — size it first (`list_repo_tree` sums the bytes without fetching) or route to a pod. The rule binds INLINE / user-chat rounds and subagent dispatches exactly as it binds plan §9 phases; "it's only CPU work" and "it's just a download, not compute" are BOTH non-reasons — the constraint is DISK, not FLOPs. When a download genuinely must land on the VM (a consumer that cannot run pod-side), the dispatch note names the staging path, the filesystem it resolves to (`df -P`), and free headroom ≥ ~1.5× the projected bytes, and stages to the data disk (`/mnt/eps-data`, 243 GiB free) — NEVER `/`, `/tmp/`, or a fresh top-level `/mnt/eps-data/<dir>` (root-owned). **Why this is now hard:** `/` is chronically near-full (98% used / 23 GiB free on 2026-08-06) because 237 GiB of worktrees + 208 GiB of `data/` sit on it — the #681 bind-migration to `/mnt/eps-data` is still pending (task **#2132**), so the VM has no slack to absorb even a modest pull. **Data-footprint carve-out (the looser, still-binding gate):** the VM root disk is SHARED — a phase whose estimated local footprint exceeds `VM_ANALYSIS_FOOTPRINT_GB_MAX = 50` GB must NOT default to the VM: route to `intent: cpu-bigmem` or stream (`cpu-small`/`cpu-mid` are for SUB-50-GB work); the planner sizes footprints in §9, the critic REVISEs a >50 GB phase silently placed on the VM (#658). (The "~188 GB" figure this bullet used to quote is STALE — the root disk was resized to 945 GB, but usable free space is what binds, not capacity.) **Compute-character carve-out — a gradient-descent fit is GPU-worthy regardless of footprint:** an iterative-optimization fit (torch-MLP LOCO, per-cell SGD/AdamW probes, small adapter fits) routes to a GPU lane (`lora-7b` / `eval` / `debug`, smallest that fits), NOT the VM — same ~15-30 min floor on the PHASE wall-time (a many-cell loop of fast fits counts; a < 30 s linear probe stays) (#658). **But VECTORIZE before routing to GPU** — many-cell GD loops, many-DRAW closed-form batteries (#778), and many-cell dense-factorization loops (#823) are OVERHEAD-bound; batching the fold/dim/layer/cell axes (`src/explore_persona_space/analysis/vectorized_mlp_skill.py`) is a 50-100× win that often keeps the run on CPU (`.claude/rules/vectorize-many-cell-fits.md`; `planner.md` §9, `critic.md` item 10(iii)). Plan-time routing, NOT a mid-run gate. **Between-phase contract:** `clean_experiment_downloads.py <N> --incremental --apply` after a phase CONSUMES its download inputs, BEFORE the next downloads more (§ Disk hygiene). **GPU-WIDTH right-sizing carve-out — a NARROW GPU phase must not hold the run's PEAK-width pod:** a narrow / API-bound phase running LONGER than ~15–30 min MUST release/downsize the wide pod (terminate + fresh narrow provision, a separate narrow pod up front, or off-pod — a same-pod `stop`/`resume` preserves the SAME GPU spec); the API-bound judge phase is SEQUENCED after the pod is released (free, off-pod, deadline-bounded `batch_judge` poll). A SHORT narrow phase (< ~15–30 min) MAY hold the wide pod. Governs SEQUENTIAL phases of DIFFERENT widths; never splits a single wide-parallel phase. Plan-time rule: `planner.md` §9 "Per-phase GPU-WIDTH right-sizing", `critic.md` item 10(iv) (#778; #664).

```bash
# Lifecycle
uv run python scripts/pod.py provision --issue 137 --intent lora-7b   # default 7-day TTL
uv run python scripts/pod.py provision --issue 137 --gpu-type H200 --gpu-count 8
uv run python scripts/pod.py stop --issue 137                          # pause; volume preserved but NOT durable (#1112) — persist resume state first (pod-config.md)
uv run python scripts/pod.py resume --issue 137                        # new IP/port → pods.conf, SSH/MCP regenerated
uv run python scripts/pod.py terminate --issue 137 --yes               # destroy (volume gone); /issue Step 8 auto-runs
uv run python scripts/pod.py list-ephemeral [--issue 137]              # live API queried every invocation
# Config (single source of truth: scripts/pods.conf)
uv run python scripts/pod.py config --list | --check | --sync
uv run python scripts/pod.py config --update <name> --host X --port Y
uv run python scripts/pod.py config --refresh-from-api [<name>]    # Pull live host/port from RunPod API → pods.conf → sync
# Keys / bootstrap / health
uv run python scripts/pod.py keys --push [<name>...] | --verify
uv run python scripts/pod.py bootstrap <name>                          # normally auto from provision
uv run python scripts/pod.py health [--quick | --fix | --json]
# Sync / cleanup / audit
uv run python scripts/pod.py sync code | env | data --pull|--push | results --all | models --list|--sweep
uv run python scripts/pod.py cleanup <name> --dry-run | --all          # safe model removal; does NOT terminate
uv run python scripts/pod.py audit-stale [--terminate-stale --yes] [--json]
```

**Authority split.** The live RunPod API is authoritative for pod state (existence, status, host, port, GPU, `created_at`); `scripts/pods.conf` is the SSH/MCP config source (refreshed from the live API by `provision`/`resume`, propagated by `pod.py config --sync`); `pods_ephemeral.json` holds project metadata only. **LIVE pods.conf AND pods_ephemeral.json live at `<git-common-dir>/eps/` (OUT of the git working tree — #821, #1183)**; the tracked copies are SEEDs. `write_pods_conf` is atomic with a never-drop-RUNNING guard; `pod.py config --refresh-from-api [<name>]` re-adds a wiped RUNNING row from the live API — use it when SSH keeps failing on a port the API no longer reports. Full mechanics: `.claude/rules/pod-config.md` (#488, #821).

**Crons.** Four background automations keep the fleet clean — full predicates, env overrides, incident history: `.claude/rules/background-automation.md`. (1) **Stale-pod audit** (daily + on provision): auto-terminates pods EXITED >24h; the owning task's `keep-running` tag exempts. (1b) **Stale-GCP-VM janitor** (`cron_gcp_audit.sh` → `gcp_audit.py`, daily): sweeps the whole `eps-persona-gpu-jun2026` project — reaps managed/allowlisted instances past a fence-aware age backstop or RUNNING-but-terminal-`eps/phase`, ESCALATES (never auto-deletes) any other stale instance; report-only by default; a failed real `gcloud list` is a HARD ERROR (exit 3 propagates so the disarmed-janitor email is delivered). (2) **Stale-worktree sweep** (daily, `worktree_audit.py --apply`): reaps idle auto-generated worktrees (live-process / active-issue / dirty kept; human-named never touched); also the terminal-task husk reap (`task.py reap-husks --apply`; `EPM_SKIP_HUSK_REAP=1`). (3) **Autonomous-session watcher** (every 10 min, `autonomous_session_watch.py`) — the authoritative pass inventory is the script docstring (lint-pinned) + the rule file; headline passes: crash-recovery respawn; pod-safety reconciliation (incl. the RunPod no-port wedge arm #770/#1667 and the keep-running wedged-owner arm #1582); stalled-session detection; capacity-retry (re-drives ONLY `blocked` tasks whose latest `epm:failure` is `failure_class: infra` + `reason: no_compute_available`, backoff + day-cap; every OTHER `blocked` task stays parked, #642); gate-push notifications; program-orchestrator recovery; plus the observer/reaper passes — parked/terminal reconcile-stop, stale-registration unregister (#845), zombie/orphan-wrapper reaps (#1039/#1215), idle-unmapped stop, triage-observer (#967), verdict-disagree (#1170), root-draft (#1341), registry-drift (#1439), completed-unmerged flag + bounded respawn (#1564/#1653), urgent-park router (#1681), codex-outage alert (#1691), auth-outage guard (#1027) — each with its own `EPM_DISABLE_*` / `EPM_*` kill switch and bounds (named in the rule file). Sessions at any active status, `blocked`, or `plan_pending`, the PM session, and unresolvable-cwd sessions are never auto-stopped.

### Hard requirements (baked into `runpod_api.py`)

1. **Team scoping** — every GraphQL call sends `X-Team-Id: cm8ipuyys0004l108gb23hody` (without it the API silently returns zero pods; override via `RUNPOD_TEAM_ID`). Only `api.runpod.io/graphql` honours it.
2. **SSH bring-up** — `create_pod` sends `startSsh: true` + exposes `22/tcp`. Do NOT apt-install openssh via `dockerArgs`.
3. **Image pinning** — `runpod/pytorch:2.4.0-py3.11-cuda12.4.1-devel-ubuntu22.04`.
4. **Bootstrap on provision** — runs `bootstrap_pod.sh` (uv, repo clone, .env push, HF cache redirect, preflight). Skip with `--no-bootstrap`.

### Remote pod access (SSH MCP)

SSH MCP server (`mcp-ssh-manager`, user-level `~/.claude/mcp.json`; `pod.py config --sync` writes pod env vars there + fails loud if the `ssh` entry is missing). **Prefer SSH MCP over `Bash("ssh ...")`.** Load tools first (deferred): `ToolSearch("select:mcp__ssh__ssh_execute,mcp__ssh__ssh_list_servers,mcp__ssh__ssh_health_check")`. Still use Bash SSH for TTY / piped / one-off. RunPod IPs change on restart; `pod.py resume` auto-updates pods.conf + SSH + MCP config (then `/mcp`).

### Pre-launch protocol (MANDATORY for experimenters)

1. **Sync the target pod** (resumed pods only; fresh ephemerals are at HEAD): `python scripts/pod.py sync env pod-<N>` (or `ssh ... 'git pull --ff-only origin main'`).
2. **Run preflight** — `uv run python -m explore_persona_space.orchestrate.preflight`. Checks git, env vs `uv.lock`, writable-disk headroom (`os.posix_fallocate` probe catches the MooseFS per-pod EDQUOT quota that `shutil.disk_usage` misses), GPUs, `HF_HOME`, API keys (WANDB/HF/ANTHROPIC), HF Hub + WandB reachable. Fix any failure — don't skip.
