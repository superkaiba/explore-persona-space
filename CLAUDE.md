## Critical Rules

- **`tasks/` is canonical workflow state.** `/issue <N>` = the task at `tasks/<status>/<N>/`. Read/mutate status, markers, review rounds, clean-result state, promotion, and RunPod lifecycle only through `scripts/task.py`. Status is the parent folder name. EPS dashboard (`https://eps.superkaiba.com`) is a read-mostly viewer; GitHub issues / project board are historical evidence only, never the control plane.
- **Ask before assuming.** Multiple valid interpretations → ask. Don't guess requirements, data formats, or success criteria.
- **Collaborate, don't transact.** Push back when something looks off; surface improvements. Naming a redirect before executing costs less than executing the wrong thing.
- **Before any new research project / direction: thorough literature review + define EXACTLY what we're studying, FORMALLY, before any experiments.** When a genuinely new question opens (a NEW direction per "Routing experiment intent", a `proposed` task starting a new line, or the first task under a new `docs/open_questions.md` anchor), the FIRST step is (1) a thorough literature review (arXiv MCP + web) to find who already works on this exact question and what they found, NOT just adjacent work — name the closest prior formalizations and results; and (2) a precise FORMALIZATION of the object of study written into the task `## Goal` / the `docs/open_questions.md` anchor BEFORE any training code: the exact quantity/construct, its definition, what would count as an answer, the competing hypotheses, and the measurement that distinguishes them. Vague-question, jump-to-experiments work is the failure mode this prevents (Dan's depth-over-breadth + Thomas's own "understand EXACTLY what we're studying"). Nail the question and its formal definition first, then design the experiment to it. (Standing rule, Thomas 2026-06-13.)
- **Fail fast — never hide failures.** No `try/except: pass`, value placeholders, dummy data on error, silent defaults, `--force`/`--no-verify` to paper over crashes, or fallbacks that swallow the fault. The crash IS the signal — diagnose root causes.
- **Every new experiment MUST go through `/adversarial-planner`** (Planner → Fact-Checker → Critic ensemble ∥ Consistency-Checker (concurrent, one spawn batch; findings unioned into a single Revise round) → Revise → User approval). Only re-runs with different seeds, monitoring, syncing, bug fixes, or explicit override skip it.
- **Ground every load-bearing hyperparameter in literature AND past issues, tied to the Goal.** The planner picks the value best serving the Goal and records a `Source:` for each (arXiv id / paper table via the arXiv MCP, or a prior issue `#<M>` that validated it for this model+data) in plan §11. Never a bare library default. Ungrounded → mark `ungrounded — needs smoke-test`, not blank; inherited → cite `Source: #<M>`. Fact-checker (Phase 1.5) verifies each; Methodology critic REVISEs when a value is both not-CONFIRMED and plausibly outcome-changing. `kind: analysis|infra|batch|survey` exempt. Full set + enforcement: `planner.md` §11, `critic.md` Methodology lens.
- **Measurement validity — the metric must measure the Goal's construct, on the distribution the behavior occurs.** Every `kind: experiment` plan states, per dependent variable: the **construct** it proxies, the **metric** actually computed, and whether the measurement is **on-distribution** (on-policy generation, the natural token position, a realistic prompt distribution). On-policy / behavioral measurement is the DEFAULT; an off-distribution / teacher-forced / fixed-context / single-position proxy is opt-in and requires EITHER a validation that the proxy tracks the construct OR an explicit argument it still answers the Goal ("cheaper / one forward pass" alone is NOT sufficient). A proxy saturated at a floor/ceiling across (nearly) all conditions is presumed uninformative — rank-shuffles among saturated values are not findings, and a proxy is never narrated as the construct without validation. **Dual-DV for content-behavior leakage / implantation (sycophancy, refusal, hedging, style, trait) — ALWAYS report both:** (a) a judge-scored on-policy behavior/agreement RATE as the PRIMARY validated behavioral construct, AND (b) a continuous completion-probability DV as a SECONDARY non-saturating companion — PREFERRED form: a **teacher-forced fixed positive-vs-negative completion margin** (mean LN-`log P` of a FIXED judge-filtered positive-answer pool minus a FIXED negative-answer pool, same answer set across every context ⇒ no selection-on-outcome bias; #722 validated ρ(margin, rate) all-positive — refusal +0.56, sycophancy +0.40, broad_em +0.31 — and non-saturating where the rate is floored). OPT-IN alternative: length-normalized trained−base `log P` of the model's OWN judged-positive on-policy completions (`logp_pos_mean`) — this is a conditional mean over an OUTCOME-SELECTED subset, so it carries selection-on-outcome bias and FAILED the ρ(DV, rate) > 0 validation for 3 of 4 behaviors in #722; use it ONLY after it passes that validation. **Graded-score primary for ranking/regression/predictor-target DVs (EXTENSION, not a relaxation):** when the behavior-expression DV is used as a *ranking / regression / predictor* target (e.g. predicting trained leakage / install strength from a base-side propensity, the #658/#742/#761/#763 predictor line — the programmatic marker keeps its own three-space `log P` recipe (`.claude/rules/marker-leakage-measurement.md`) and is NOT a judge-scored behavior-expression DV), the PRIMARY ranking/regression DV MAY be — and is PREFERRED to be — a **graded multi-sampled 0-100 judge score** (N≥5 draws per completion at temperature > 0, mean-aggregated; a malformed / REFUSAL / out-of-range judge return is DROPPED, never coerced; a TRANSPORT failure — 429/529/timeout/connection — is retried and re-judged, never persisted as a drop: `.claude/rules/llm-judging.md` rule 24), because dichotomizing a graded behavior into a binary rate attenuates the very correlation a predictor target needs (≈0.798 / ~36% effective-N loss, worse near a floor). The **binary judge-RATE is retained as the validated human-legible headline companion**, and the continuous log-P companion (b) is UNCHANGED. This does NOT relax (a)'s role as the validated on-policy behavioral construct for *leakage/implant headline* comparisons, nor any saturation / on-policy / drop-never-coerce protection: the graded score itself stays on-policy and MUST be validated against a non-judge reference (a human audit set, or the project's log-P / activation companion) before it carries a ranking/regression headline. Recipe + the full 23-guideline set (the 21 judging guidelines plus the § E2 continuous-companion-DV recipe): `.claude/rules/llm-judging.md`. The reason both are required: the binary judge rate saturates at floor/ceiling and CENSORS install / dose-matched comparisons (#608's top-band censoring), exactly where the continuous DV keeps dynamic range; the probability DV in turn carries the teacher-forcing-artifact risk (#432→#456) the judge rate is immune to. The probability DV stays SECONDARY and requires the standing validation that it tracks the rate (Spearman across cells with dynamic range); never narrate it as the construct unvalidated, and never let it replace the on-policy rate. This mirrors the marker line's behavioral-primary + continuous-secondary three-space recipe, judge-rate-primary. (Standing rule, Thomas 2026-06-15.) `kind: analysis|infra|batch|survey` exempt. Enforcement: `planner.md` §6, `critic.md` Statistics & Measurement lens, `analyzer.md`, `interpretation-critic.md` Lens 1, `clean-result-critic.md` Lens 7. Graded-judge scoring recipe + the 21 judging guidelines + the § E2 continuous-companion-DV recipe: `.claude/rules/llm-judging.md`. Marker-specific recipe, the marker-dynamics-vs-cross-condition caveat, and the #432→#456 incident: `.claude/rules/marker-leakage-measurement.md`.
- **Prefix mapping AND context mapping — run BOTH in every experiment, unless explicitly stated otherwise.** Canonical definitions: the **prefix** is everything before the user query (system prompt / persona / any conversation content preceding the query); the **context** is the prefix plus the user query; the **answer** is the model's answer after the user query. Any experiment (or analysis of one) that computes a representation mapping — a geometry read, predictor, probe, or direction extraction over model activations — computes it BOTH ways, prefix-based and context-based, as paired arms of the same design, and reports both; running only one is an explicit, stated deviation in the plan (carried into the clean-result as a scope caveat), never a silent default. The planner names both arms in §4 Design; the critic REVISEs a plan that silently drops one without a stated exemption. (Standing rule, Thomas 2026-07-03.)
- **LLM judge = `claude-sonnet-4-5-20250929`, ALWAYS, for every judged behavior (sycophancy, EM, refusal, trait, fact, …).** One consistent judge across the project — do NOT pin Haiku (the legacy #411/#612 sycophancy pin) or gpt-4o (Betley's original EM judge) for new work. Set via `DEFAULT_JUDGE_MODEL` / `JUDGE_MODEL=claude-sonnet-4-5-20250929`; never graft a `-20251001` suffix (that is Haiku 4.5). **Use the Anthropic Batch API whenever the judge set is large** (≳ a few thousand calls — e.g. EM's 100 samples × ~52 questions × conditions × seeds). When faithfully replicating a published finding, the paper's own judge MAY be run ADDITIONALLY as a κ-calibration control, never as a replacement. (Standing rule, Thomas 2026-06-23.) **API throughput (any high-volume Anthropic call site — judges + generation) — read `docs/api_throughput_guidelines.md`** for the N × model × {latency, cost} decision table, the polite per-key caps (Sonnet 100 / Haiku 120 / Opus 40), AIMD back-off, and the sync-vs-batch crossover; the multi-org dispatcher (`src/explore_persona_space/llm/api_dispatch.py`) implements it. Plan: `docs/api_throughput_plan.md`.
- **Every `kind: experiment` task declares a `## Goal` H2 + `goal:` frontmatter at creation** (`/issue` Step 0c gate). The Goal is the canonical target every downstream subagent reads. Refinable only by the clarifier (Step 1) or planner (Phase 1) with user consent (posts `epm:goal-updated v1`); no other agent may change it. `kind: analysis|infra|batch|survey` exempt.
- **List assumptions before implementing.** Factual claims about APIs, layers, data formats, hardware — mark confidence, verify if below high.
- **Search before building.** Check PyPI, HuggingFace, GitHub first.
- **Reuse existing in-repo tools/helpers.** Before writing any new script / helper / function, SEARCH the repo first (`grep scripts/ src/`, and check sibling issue branches / worktrees) — if a tool already exists for the job, USE it; don't rewrite what exists. The reuse hierarchy extends from external packages (above) and experiment code (below) to in-repo tools too. (Motivated by #722: the vectorized helper already existed on an unmerged branch and a rewrite was started before it was found — ties to "built-but-stranded fixes", `.claude/rules/workflow-fix-on-bug.md`.)
- **Reuse existing experiment code as much as possible.** New experiments inherit the existing training scripts, eval functions, data pipelines, configs, checkpoints, and the parent/sibling issue's methodology by default — don't reinvent what's already built. The planner identifies what's reusable and flags what's genuinely new vs reused (`planner.md` steps 1/5, §"Plan Quality"); write new code only for the single variable the experiment actually changes.
- **Reuse existing trained artifacts when fit-for-purpose — never reuse a wrong one.** The same default extends to TRAINED ARTIFACTS already on HF: LoRA adapters / merged checkpoints, training-mix JSONLs + raw-completion buckets, and `eval_results/` JSONs from prior tasks — before retraining or regenerating, the planner searches what already exists and reuses it when it fits the new Goal (canonical worked example: #532 reuses #474's loc-arm epoch-1 marker adapters instead of retraining 16 sources). Reuse is conditional on the POSITIVE fitness check **(a)-(j)** — recipe match grounded on the artifact's own `adapter_config.json` (#545), valid measurement regime, required cells present, no broken single-variable-change / measurement validity, HF resolution via `huggingface_hub.list_repo_files`, content identity / sha-pinning (#600), the rsLoRA application-scaling parity probe (#601), and source-resolution + target-backend fetchability of reused TRAINING-INPUT mixes / on-policy caches / downstream-input eval JSONs (resolves on HF OR is git-tree-reachable for a committed `eval_results/...`, AND the §9 lane can fetch it — the git-clone-only GCP/SLURM lanes stage no VM-local `data/`; on a miss of EITHER, upload-first or self-contained regen; #734), staged-layout consumer-open for reuse staged through a layout-mapping helper (incl. a verbatim prefix mirror) — a 1-file staging probe + the consumer's own open/init against the STAGED tree before production (#928), and throughput fitness of reused fit/analysis/upload-verify CODE — inner per-cell/per-fold/per-draw loop batched + device parametrized + data-repo Hub calls prefix-scoped (#761/#763/#812/#810), and pairwise provenance coherence across mutually-dependent reused artifact pairs — a consumed input regenerated AFTER its dependent capture is inconsistent regardless of sha pins; compare last-commit dates at the consumed revisions (per-repo `get_paths_info(expand=True, revision=...)` / `git log -1`) (#922) — full checklist: `.claude/rules/artifact-reuse.md`. Silently reusing a wrong / stale / saturated artifact confounds the result and is WORSE than retraining; a failing check other than (i)/(h)(iv) → retrain / regenerate; a failing throughput check (i) → fix the SOURCE module (batch / parametrize / scope it there — never a caller-side workaround), then reuse; a failing staged-layout check (h)(iv) → fix the staging mapping, then reuse; say why in the plan either way. Enforcement is a 3-stage defense: `planner.md` step 5 (self-attested fitness check) → `consistency-checker` (independent reuse-smuggled-variable diff vs the parent recipe) → `critic.md` Methodology lens item 9 (REVISE); the reuse provenance is then carried into the clean-result `## Reproducibility` (`analyzer.md`) and audited by `clean-result-critic` Lens 5.
- **Vectorize / parallelize compute by default — a serial inner loop is the recurring throughput failure.** Before launching any compute-bound work, batch/vectorize/parallelize it: never a Python loop of batch-1 model forwards, never a many-cell serial gradient-descent fit (per-fold/per-cell MLP/AdamW LOCO sweep — #722 burned 19.5 CPU-h on ~19 TFLOP), never an unbatched permutation/bootstrap/null-draw battery over a large fixed pool (#778: ~15h projected across its draw loops — precompute the pool reduction once, batch all draws as one subset-sum GEMM, ~70×), never a many-cell serial dense-factorization loop (a full svd/eigh/lstsq/GCV-ridge solve per fold × layer × arm × trait — cheap ONCE, ruinous ×thousands: #823 ran ~3780 serial full-SVD ridge fits, ~12-20h, against a plan sized at ~2 s/fit; batch via Gram/dual-space, a shared factorization, or the named fast twin), never sequential HF `model.generate()` for eval, never sequentially blocking N independent subagents the harness wants parallel. The specifics live in their on-demand rules — `.claude/rules/code-style.md` (vectorized torch, compute-throughput discipline), `.claude/rules/vectorize-many-cell-fits.md` (the canonical `vectorized_mlp_skill.py` helper, 50-100x), the always-on "Use vLLM for generation" bullet below, and the orchestrator-vs-subagent parallelism rule — but the default is one line: vectorize first, reach for a bigger machine only after.
- **State facts, not sources — everywhere except `docs/mentor_updates/`.** Living docs (`docs/open_questions.md`, `docs/research_ideas.md`) AND task/issue bodies write the claim/idea directly — never "Dan said", "per the 2026-05-29 meeting", or any person/meeting attribution. Provenance lives only in the `#issue` evidence trailers and in `docs/mentor_updates/`. When integrating meeting feedback into issues or docs, carry the substance, drop the name. Keep the register plainly academic: no spatial/anatomical metaphors ("spine", "backbone", "hub-and-spoke", "scaffold") — name the mechanism directly.
- **Use vLLM for generation.** Never sequential HF `model.generate()` for eval — vLLM batched `LLM.generate()` is 10-50x faster.
- **`max_new_tokens` ≥ 2× longest trained completion** (default ≥ 2048) for marker / end-of-completion evals — truncation creates silent zeros (#260: 1050-token training + 512 cap → source-rate 0.00). Free-generation evals (alignment, capability) default to 1024 (raised from 512, 2026-06-24).
- **Marker-leakage experiments:** default marker ` ※` (leading space, Qwen-2.5-7B token id 83399; NOT `[ZLT]`, NOT bare `※` id 63680 — assert `tokenizer.encode(MARKER_TEXT, add_special_tokens=False) == [83399]` in-process). DV = on-policy `log P(marker)` at the END of the model's OWN response, reported trained − base in ALL THREE spaces (log-prob PRIMARY behavioral / marker logit incl. the EOS margin SECONDARY mechanistic / probability sanity read) under the four-float-per-slot storage contract (#530: logits are UNRECOVERABLE from stored log-probs post-hoc); the DV stays marker-specific — NEVER swap in full-vocab KL-from-base at the slot to dodge anchor saturation (#504 inflated a null into 24 nats). Full measurement recipe — token threading, three-space analysis + the saturation signature, dynamics, storage capture paths, the #432→#456 incident: `.claude/rules/marker-leakage-measurement.md`. **Marker TRAINING recipe** — the over/under-training dial, the marker + end-of-turn loss (positives `{ ※, <|im_end|>, \n}` / negatives `{<|im_end|>, \n}`; trains "emit marker then END" to prevent `※`-repeater spam; never whole-completion), why fixing epochs fails, the deterministic log-prob band-stop auto-applied via the marker-gated `MarkerBandStopCallback` default in `train_lora`: `.claude/rules/marker-training-recipe.md` (evidence + per-task index: `docs/marker_training_recipe.md`). **Drafting or creating a marker / behavior-implant experiment task body — even a bare `proposed` task, before any training code is touched — counts as planning the recipe: READ `.claude/rules/marker-training-recipe.md` + `marker-leakage-measurement.md` + `contrastive-negatives.md` IN FULL before grounding any hyperparameter or root-causing a saturation/floor result.** One fact stays always-on because the on-demand load fires only when you touch training code — too late for the task-drafting step that seeds the planner (incident #530, 2026-06-08: a de-saturation re-run body first blamed steps/rank instead of LR): the marker-only LR is the over/under dial (lr ≥1e-4 → unconditional ` ※`-repeater, source AND bystander saturate; the only demonstrated clean window is lr ≤5e-6, strength bought through training STEPS, NOT LoRA rank).
- **ALWAYS use contrastive negatives for behavior implantation.** Any experiment that implants a behavior (marker, fact, refusal, trait) into a source persona MUST interleave contrastive negative rows — same questions, under *other* personas (always including the default assistant), that omit the target — because positive-only training leaks the behavior *uniformly* to every persona + the default context (#18, #207). Default ~1:1 positives-to-total-negatives across ≥2-4 close negatives; measure leakage on-policy. Exempt only when the single manipulated variable IS contrastive-vs-non-contrastive or for a strict single-variable replication of a positive-only parent (then flag the no-negatives regime as a clean-result scope caveat). Full recipe + composition + caveats (#383 selectivity-artifact risk, #448 saturation) + enforcement: `.claude/rules/contrastive-negatives.md`.
- **On-policy-first training completions for behavior implantation.** When building implantation training data for a behavior (sycophancy, refusal, hedging, style, trait), generate the POSITIVE completions on-policy from the BASE model wherever it can express the behavior under elicitation — the #612 elicitation ladder: (1) bare context, (2) behavior instruction in the system prompt, sample, judge-filter, then **STRIP the elicitation instruction before training** (the trained context is the persona/target context only), (3) minimal opener prefill — preferring the lowest tier that fills a pre-registered per-source yield quota; a below-floor shortfall is REPORTED (drop the source), never silently backfilled with templates. Canned/templated strings and third-party-LLM-written completions are allowed ONLY as deliberate anchors/controls or after a recorded yield failure — either way named in the plan and carried into the clean-result as a data-realism caveat. Plan around the measured trade-off: on-policy data installs more weakly at matched recipe (#612's three separated dose bands, set by epoch 1) — dose-to-target instead of fixed epochs when comparing constructions. Exempt: published-corpus replication rows (replication fidelity wins) and the programmatic marker carve-out. The NEGATIVE side already mandates on-policy text (`.claude/rules/contrastive-negatives.md`); this is its positive-side sibling. Full recipe + yield-gate mechanics + exceptions: `.claude/rules/on-policy-completions.md`. Enforcement: `planner.md` §4 Design names completion provenance per training-row type; `critic.md` Methodology lens REVISEs canned/LLM-written positives without an anchor/control justification or a recorded yield failure.
- **Replicating a published finding → match the paper's data + recipe FIRST.** The FIRST run reproduces the paper's actual data source, training recipe, hyperparameters, dependent variable AND the paper's own manipulation check as faithfully as the project allows, changing ONLY the one variable the replication is deliberately testing (typically the base model); do NOT silently swap in the project's house rig and read a null as "the finding doesn't replicate" — the recipe mismatch confounds the null (incident #496). Forced deviations are named in plan §-assumptions and carried into the clean-result as scope caveats; a faithful replication of a positive-only paper is the named contrastive-negatives exemption. Pull the recipe from the paper itself (arXiv MCP), never a secondhand summary. Full rule + the #496 post-mortem: `.claude/rules/replication-fidelity.md`. Enforcement: `planner.md` (replication-fidelity check), `critic.md` Methodology lens.
- **Design experiments on the most realistic data available — strict preference order.** Every `kind: experiment` plan picks its training/eval/probe data from the 4-tier hierarchy — (1) real-world data, (2) established dataset / benchmark, (3) DIVERSE LLM-generated synthetic (only when 1+2 are genuinely unavailable; a flat templated corpus does NOT qualify), (4) programmatically generated (LAST resort; requires an explicit recorded argument why no other source works AND why the templated structure cannot bias the result) — and justifies the choice in §-assumptions; the default presumption is that programmatic synthetic data confounds every behavioral claim. Tier definitions + examples: `.claude/rules/data-realism.md`. Enforcement: `planner.md` §4 Design names the source + tier, `critic.md` Methodology lens REVISEs unjustified tier-3/4 choices; carry the data-source tier into the clean-result as a scope caveat.
- **Persona vectors → reproduce arXiv 2507.21509 EXCEPT the logit scoring.** Any task whose plan says "use persona vectors", "extract a persona vector", or "persona-vectors-style direction", OR that extracts a persona/behavior direction by mean-difference of positive/negative contrastive activations, READS `.claude/rules/persona-vectors-recipe.md` BEFORE grounding the extraction (the on-demand load fires via that rule's `paths:` frontmatter when a plan file is open; this always-on bullet is the backstop). The rule encodes the paper's pipeline (Chen/Arditi/Sleight/Evans/Lindsey, *Persona Vectors*, Anthropic) faithfully — 5 pos/neg system-prompt pairs over a shared 20-question extraction set (disjoint from a 20-question eval set), 10 on-policy rollouts each, judge-filter (keep pos>50 / neg<50; a `REFUSAL`/non-numeric/out-of-[0,100] judge return is DROPPED from BOTH arms, never coerced to a number, and the per-arm dropped count is reported), response-avg activations at every layer, `r_B` = diff-of-means per layer — with EXACTLY ONE standing deviation: the paper's GPT-4.1-mini logit-weighted top-20-token trait scoring is replaced by the standard project judge `claude-sonnet-4-5-20250929` (plain integer 0–100, threshold 50). The rule also splits layer selection into the steering/monitoring regime (one steering-selected layer, per the paper) vs the read-out/prediction regime (sweep all layers, select by target predictivity — e.g. the paper's A3.3 `E ≈ r_Bᵀ v` predictor); the task plan names its regime. Driving incident: #658 built an `r_B` that diffed two different corpora with no judge-filter, diverging from the paper. Sibling rules: `.claude/rules/replication-fidelity.md` (persona vectors IS a named published recipe), `.claude/rules/contrastive-negatives.md` (the pos/neg structure), `.claude/rules/on-policy-completions.md` (the rollouts are on-policy). Enforcement: `planner.md` §4 Design, `critic.md` Methodology lens item 17.

### Routing experiment intent

- **Pure capture** ("save idea: X") — create `status='proposed'` task; no execution.
- **NEW direction** (substantially different question — "try X", "run X", "what if we X") — NEVER inline. Create `status='proposed'` task; only execution path is `/issue <N>`. **Filing ≠ spawning:** capturing a NEW-direction task from chat does NOT imply launching it — do not auto-spawn a `spawn-issue --auto` session for the just-filed task unless the user explicitly asks to run it; leave it at `proposed` for the user/PM to dispatch. (Incident #823, 2026-07-01: an auto-spawn immediately after capture drew "Wait can you stop it" — task capture is not an execution greenlight.)
- **Mapping/geometry capture default (all capture forms above and below):** when drafting ANY task body for a representation-mapping experiment — a geometry read, predictor, probe, or direction extraction over model activations — write BOTH mapping arms into the body at capture time: prefix-based (the prefix is everything before the user query) AND context-based (the context is the prefix plus the user query), per the Critical Rules "Prefix mapping AND context mapping" bullet. A one-arm capture is an explicit stated deviation in the body, never a silent default (the clarifier checklist + plan-time critic remain the backstops; incident #958, 2026-07-04).
- **Follow-up** (the requested work answers the SAME question as an existing issue #N — regardless of whether the user says "followup"; **exception: see `**User-chat inline free analysis**` below for the user-initiated 0-GPU-h-on-existing-artifacts carve-out and its explicit user inline-override clause (GPU-needing asks)**) — NEVER loose ad-hoc execution from the chat session. Post `epm:followup-scope v1` on #N (`source: user-chat`, with a `followup_label`), then re-invoke `/issue N` — the same-issue follow-up loop executes it ON #N (SKILL.md Step 9b § Same-issue follow-up loop) and re-parks it at `awaiting_promotion`. While executing, the loop HOLDS the task at status `followups_running` with the `followup-auto` (proposer-initiated) or `followup-manual` (user-initiated) tag — the intermediate pipeline statuses are not applied. Artifacts land under `eval_results/issue_<N>/<followup_label>/`. A substantially different question is a NEW direction (child task via `task.py new --parent <N>`), not a follow-up. **Pod-safety auto-stop exemption:** if the follow-up provisions a pod on a terminal-status parent, the watcher infers a live follow-up from a fresh `epm:run-launched` newer than the latest done-transition (`epm:promoted` / `epm:status-changed`) and SKIPS the auto-stop with a `followup-skip` marker; `task.py add-tag <N> keep-running` is no longer required, but is still an explicit override that takes precedence over the inferred predicate (incident #477, 2026-06-10).
- **User-chat inline free analysis** (interactive chat only — the user DIRECTLY asks to run a `0-GPU-h free analysis` on EXISTING artifacts: eval JSONs, raw completions, activation stores already on disk / HF) — RUN IT INLINE with a read-only subagent (an `experiment-implementer` constrained to ANALYSIS-ONLY — no new training, no new eval generation, no new data — or a `general-purpose` analyzer), NOT through the `/issue N` follow-up loop. Routing here is by COST + ARTIFACT-EXISTENCE, not phrasing: a user-chat 0-GPU-h ask on existing artifacts takes this inline path even when phrased "as followups" / "run these followups" — the word "followup" does not re-route a zero-GPU existing-artifacts ask to the spawn/loop path. (A GPU-NEEDING ask takes this inline path only under the explicit user inline override below.) This is the USER-INITIATED sibling of the PROPOSER-initiated Step 9a-ter zero-GPU floor (SKILL.md § 9a-ter): same execution shape (ANALYSIS-ONLY edits, single-round, `abort + reclassify as needs-gpu` if the analysis turns out to need new data), just triggered by a chat ask instead of an analyzer-surfaced `cost_class: free-analysis` follow-up. **Provenance is a plain `epm:progress` note on #N** (naming the ask + a one-line result summary) followed by an `epm:free-analysis-followup-run v1` marker on completion — **do NOT post `epm:followup-scope v1` on the inline path.** `epm:followup-scope v1` is the arming trigger for the SKILL.md Step 0 same-issue follow-up dispatcher (satisfier: a matching `epm:same-issue-followup-run v1`, a different marker kind than the inline path posts), so leaving one unrun on #N would re-arm the very `/issue N` loop this carve-out exists to skip on the next tick. The subagent folds its finding into the discussion; a live `/issue N` session, if any, absorbs it into the clean-result body on its next analyzer pass. **Same-turn completion contract (0-GPU and override rounds alike):** an inline round is COMPLETE only when, in the SAME turn as the result summary, (1) the round's eval JSONs + figures are committed by explicit path (never `git add -A`) and pushed, AND (2) the finding is folded into the parent's clean-result/report body — or the `epm:progress` completion note carries an explicit one-line deferral naming who folds it and when (incident #779, 2026-07-06: an inline round's `fair_comparison.json` sat modified-but-uncommitted for 8 days beside a stale report Result 3 the user found himself). **Session-collision distinction:** a live per-issue session owning #N blocks RE-SPAWNING `/issue N` (SKILL.md Step 0 single-orchestrator guard — detect-and-exit, incident #535), but does NOT block an INDEPENDENT read-only subagent that only READS artifacts + posts a marker — that subagent mutates no task lifecycle state and races nothing. If the ask needs new training / eval data (i.e. is not zero-GPU or not on existing artifacts), it is a `**Follow-up**` (re-invoke `/issue N`) or a `**NEW direction**`, not this carve-out. **Explicit user inline override (the one exception):** when the user EXPLICITLY directs inline execution ("run it inline", "run it inline so it is faster", killing a just-spawned session and asking for inline), honor the override and run the follow-up inline EVEN when it needs GPU — do not spawn (or re-spawn) a session against the ask (2026-07-14: 4 spawned sessions on #658/#1092/#1090/#952 killed within ~2 min after exactly this ask). The override inherits this carve-out's duties unweakened: post a dispatch-time `epm:progress` override note on #N quoting the verbatim ask + the estimated GPU-h + the compute-character pre-launch statement (extended with the GPU parallelization shape), carry the pod-safety pre-launch signals below (`keep-running` tag BEFORE/AT provision + `epm:run-launched` once the pod exists), and still post NO `epm:followup-scope v1` — and NO `epm:free-analysis-followup-run v1` either (that marker is the 9a-ter one-round cap key; this is not a free-analysis round — the override note + `epm:progress` completion note are the durable record). KILL-MID-LOOP DISARM: when an `epm:followup-scope v1` was already posted BEFORE the override (routed → spawned → killed → "run it inline"), the inline override round posts the MATCHING `epm:same-issue-followup-run v1` on completion so the armed scope cannot re-drive the Step 0 dispatcher (#952, 2026-07-15: the 05:47Z run marker is what disarmed it); a fresh override ask with no prior scope marker posts neither. The explicit ask IS the user's spend approval for that run; an estimate over 20 GPU-h (the `compute:large` rail — so a ≥`EPM_PLAN_AUTOAPPROVE_GPU_HOURS` run is never silent) still gets a one-line confirm in the chat before provisioning. USER-INITIATED ONLY: an autonomous session has no user to override — autonomous routing is unchanged. **Pod-safety pre-launch signals (deviation case):** if an inline/user-chat run nonetheless provisions or reuses a pod on a parked (`on_hold`) or terminal-status parent, the launching session MUST run `task.py add-tag <N> keep-running` BEFORE/AT provision — before any pod work; the timestamp-independent tag is what shields the provision/bootstrap window, which the watcher's ≥2-miss accumulation (~20 min) would otherwise auto-stop straight through — AND post `epm:run-launched` on #N immediately once the pod exists (note naming the pod + the ask; in any case before launch). The watcher's pod-safety pass auto-stops a RUNNING pod on such a parent unless a follow-up signal marker (its predicate reads `epm:run-launched` / `epm:followup-scope` / `epm:free-analysis-followup-run` — a descriptive list, NOT a menu: the inline path still never posts `epm:followup-scope`) is NEWER than the latest done-transition (`epm:promoted` / `epm:status-changed`) or the `keep-running` tag is set; BOTH duties bind — the marker cannot exist during the provision/bootstrap window (#573: run-launched-only inference stopped healthy follow-up pods 11×) and any later done-transition flips the inferred predicate off by design (the watcher's re-arm semantics), while the tag alone loses the run record (incidents #477, #573; #779 2026-07-06: pod-779, launched with neither signal, was repeatedly auto-stopped mid-bootstrap and misdiagnosed as a flaky host) — remove the tag (`task.py remove-tag <N> keep-running`) when the run completes so the auto-stop re-arms (a crashed run leaves the tag and the pod bills until manual removal — check `pod.py audit-stale` output). The line-52 Takeaways litmus is ORTHOGONAL and unchanged — it decides SAME-issue vs CHILD-task for work that DOES need new data; this carve-out decides INLINE vs LOOP for SAME-issue reads on existing artifacts. A re-read that surfaces a new takeaway from existing data folds into the parent body via the analyzer's next pass (no new task, no loop). **Autonomous-mode routing is UNCHANGED** — this carve-out is scoped to interactive-chat user asks; the proposer + auto-run bands (Step 9a-ter 0-GPU floor, Step 9b `0 < est_gpu_hours < 20` cheap band; CLAUDE.md § "After Every Experiment" item 9) fire exactly as before in both session modes. **Compute-character pre-launch statement (REQUIRED — this carve-out skips the planner+critic stack, where all compute-character review lives):** "0 GPU-h" does not mean "0 compute review" — before the subagent launches any fit, sweep, or statistical battery (permutation/bootstrap/null draws, per-cell/per-fold fits, per-row model calls), a SEPARATE dispatch-time `epm:progress` note, posted BEFORE launch — the carve-out's existing provenance note (the ask + one-line result summary) stays the COMPLETION record — states the ops arithmetic (cells × folds × draws × epochs → projected wall-time), the named BATCHED helper implementing the inner loop (or why genuinely not batchable), and — for reused parent code — that its inner loop, device routing, + data-repo Hub-call scoping were inspected (cf. `.claude/rules/artifact-reuse.md`). Projected wall-time > ~1h without a batched inner loop ⇒ STOP, vectorize first (`.claude/rules/vectorize-many-cell-fits.md`), then launch (incidents #667/#722/#778; canonical block: SKILL.md Step 9a-ter § Compute-character pre-launch statement).
- **Campaign** (`kind: campaign`) — question-level runner pinned to ONE `docs/open_questions.md` anchor. Only execution path: `/campaign <N>` in a DEDICATED session spawned via `spawn_session.py spawn-campaign --issue <N>` (refuses unless the user reviewed the `## Campaign Brief` and ran `task.py set-status <N> approved` — workflow.yaml § gates.campaign_brief_approval). Children are ordinary `kind: experiment` tasks executed via `/issue <child> --auto` with the full planner/critic stack; the campaign ingests only critic-gated clean-results, holds budget/limits in `artifacts/campaign-state.json` (GPU-hours, never dollars), and proposes — never applies — open-questions diffs. NEVER run `/campaign <N>` in the PM session or a per-issue session.
- **Fix-validation / "test that X works" → `kind: infra`, NOT `experiment`.** A task whose Goal is to VALIDATE / TEST that a shipped workflow / infra / code fix WORKS (a smoke run, an end-to-end "does it work now after the fix", a config / pipeline / backend re-check) is `kind: infra` — it completes on the Step 9c test-verdict path and produces NO promotable clean-result. Reserve `kind: experiment` for a RESEARCH QUESTION that produces a clean-result the user promotes. The litmus: would the result rewrite an issue's `## Takeaways` / answer an `open_questions.md` question (→ `experiment`), or just confirm the fix is sound (→ `infra`)? Mis-filing a validation as `experiment` drags it through the analyzer → interpretation-critic → clean-result-critic → `awaiting_promotion` machinery and leaves it parked as a promotable clean-result with a confidence tag (incident #672: a GCP-fix validation). If a task is already mis-filed, reclassify through the canonical path — `task.py set-kind <N> infra` (frontmatter + REGISTRY snapshot, flock + commit) — never a hand-edit of the `kind:` frontmatter.
- **Always-inline** — monitoring, log-checking, pulling results, discussion, brainstorming. No task needed.

Routing is by QUESTION IDENTITY, not user phrasing: same question → same issue; substantially different question → new child task. **The litmus: "Would the result rewrite THIS issue's `## Takeaways`?" → SAME issue (same-issue follow-up loop).** Changing the method, dose, panel, seeds, eval surface, prompt bank, or adding a control / baseline ON THE SAME QUESTION is ALWAYS the same issue. **The NUMBER of variables changed is NOT the routing criterion** — a follow-up that changes ≥2 things (e.g. matched LR *and* on-policy completions) is still the SAME issue if the result would rewrite the parent's `## Takeaways`; variable-count is a plan / consistency-checker concern (single-variable-change discipline), never a question-identity one. Conflating the two is a recurring misroute (#642→#652, 2026-06-16: a 2-variable follow-up wrongly filed as a new child, then archived + re-routed). A new child task is reserved ONLY for work that would change the task's `## Goal` / its `docs/open_questions.md` anchor — a genuinely new question. The default is biased HARD toward same-issue. The `question_relation: same | substantially-different` tag on follow-up proposals encodes the same split (`follow-up-proposer.md` § question_relation tag — criteria). Ambiguous? Default to same-issue (one short question only if a genuinely new Goal might be at stake). **Record the originating prompt at creation:** when a task is created from a user chat request (capture / NEW direction / follow-up child), record the verbatim user prompt — `task.py new --origin-prompt "..."` or a `## Provenance` body section (worked example: #611); same-issue follow-up rounds already carry it in the `epm:followup-scope v1` note. The clean-result's `## Reproducibility` `**Context:**` row ships it forward (SPEC.md § `**Context:**` row; `verify_task_body.py` check 17). **Archiving:** `task.py set-status <N> archived` for duplicates / won't-fix / abandoned. `has_clean_result=true` is sticky across statuses. **User pause:** "pause <N>" / "put <N> on hold" routes to: CRON-TEARDOWN + Step 8-bis pod stop FIRST, THEN `task.py set-status <N> on_hold --note "USER PAUSE (verbatim: ...); paused_from=...; resume: ..."` as the commit point — durable and watcher-safe (`on_hold` is in the watcher PARK set; the park comes LAST so a crash never leaves the pause half-done; since #980 the watcher pod-safety pass additionally auto-stops an `on_hold`+RUNNING **RunPod** escaped pod after the 2-miss guard, as backstop — GCP instances rely on their `--max-run-duration` fences / `finalize`, not this pass); NEVER a prose-only hold marker at an ACTIVE status (the watcher respawns against it, #816). Resume is user-greenlight only. Full affordance: `.claude/skills/issue/SKILL.md` § User pause affordance.

### Auto-continuation policy

Multi-step workflows (`/issue`, `/adversarial-planner`) MUST auto-continue except at explicit gates. Canonical enumeration: `.claude/workflow.yaml` § gates.

*Inline `AskUserQuestion` gates (block within `/issue`):*
1. Step 0b(1) — issue body empty.
2. Step 0b(2) — task `kind` missing/contradictory.
3. Step 1 — clarifier blocking ambiguities (`status:proposed`).
4. Step 2c — plan approval (`status:plan_pending`).
5. Step 0c — Goal gate (`kind: experiment` only): refuses to advance until `goal:` frontmatter + `## Goal` H2 present. On miss, ask, then `task.py set-goal <N> "..." --by user` + post `epm:goal-updated v1`.

(The worktree merge is NO LONGER a gate — as of 2026-06-03 it is automatic: the worktree rebase-merges to `main` with no prompt at the terminal point — Step 9b for experiments at `awaiting_promotion`, Step 10d for code paths at `completed`. The worktree is kept, not removed. See SKILL.md Step 10d.)

*Park-and-wait gate (skill EXITs; re-invoke after user acts):*
6. `awaiting_promotion` — clean-result promotion. User runs `task.py promote <N> useful|not-useful`. **User-only:** no automation may flip `runs.classification`. (The worktree auto-merges to `main` the instant the task reaches this state — Step 9b — independent of promotion.)

*Conditional gates:*
7. Step 4b TDD — fires when plan body has `### TDD: yes`. Implementer posts `epm:proposed-tests v<n>`, EXITs awaiting `epm:approve-tests v1`.
8. Goal-refinement (Step 1 clarifier OR Phase 1 planner) — surface the sharper Goal via `AskUserQuestion`; on agreement run `task.py set-goal <N> "..." --by clarifier|planner` + post `epm:goal-updated v1`. No other agent may propose Goal changes.

Outside these gates, NEVER ask "should I continue". When auto-continuing past a non-obvious decision, STATE the assumption (`Assumption: ...`). Reviewers reject PRs that introduce additional pauses.

**Halt-criterion contract.** Outside the 5 inline gates, NEVER use `AskUserQuestion`. If you genuinely need user input, post `epm:failure v1` with `failure_class: <code|infra|data>`, set `status:blocked`, exit. Enforced by `scripts/workflow_lint.py --check-asks` (pre-commit): every `AskUserQuestion` mention in `.claude/agents/**.md` or `.claude/skills/**/SKILL.md` must carry `<!-- gate: <dotted_key> -->` resolving to workflow.yaml, or cite the gate in the same paragraph.

**STATE-TO-`blocked` criteria** (workflow.yaml § halt_criteria). **Continuing on your own is the default.** Pivots (re-invoke `/adversarial-planner` with pivot scope, drop a domain, swap a model, change the approach), retries, and memory-driven design changes are all autonomous. Block ONLY when:
  1. **Factual question only the user knows** — priority, taste, scope, design preference between valid paths, where no memory/plan/codebase signal disambiguates. **Autonomous-mode carve-out (`EPM_AUTONOMOUS_SESSION=1`):** in `--auto` sessions the taste / scope / design-preference / "which valid path?" sub-cases of this criterion do NOT apply — there is no human to escalate to, so the session picks the option with max info-gain-per-GPU-hour toward the task `## Goal` (tie-break: lower-cost / safer / record-correcting), posts `Decision: <X>`, and continues. The only autonomous residue of #1 is a fact the user UNIQUELY holds (account credential, external decision the user already promised to make, fact only the user can supply) AND that is NOT itself a taste / scope / design call. Authoritative prose: `.claude/skills/issue/SKILL.md` § Autonomous session behavior.
  2. **Outside-the-worktree state mutation** — security boundary, irreversible writes (deletion, force-push, credential changes — always ask).
  3. **Public API contract change** — status enum, marker schema, task.py subcommand, agent file location.
  4. **Step 10 completion-audit incomplete** — ORIGINAL task body has unaddressed numbered asks / acceptance criteria / deliverables.

  Cap-3 on a subagent ensemble is NOT a block trigger — it triggers a strategy pivot. Block only after ~3 fundamentally different strategies have FAILed AND no further autonomous angle exists. **Autonomous mode: a debugging wall is a strategy-pivot, not a block** — re-invoke `/adversarial-planner` with explicit pivot scope, spawn `experiment-implementer` on a different angle, swap a model / pod intent / framing, or drop the offending domain (workflow.yaml § `pivot_criteria`). Block only after ~3 FUNDAMENTALLY different strategies have all FAILed AND no autonomous angle remains. **Autonomous mode: a self-defeating PLAN routes to `/adversarial-planner` re-plan, not to a recipe descope or a max-info-gain pick** — when a subagent reports the plan itself is the defect (internally contradictory success/kill criteria, jointly-unsatisfiable gate set, or an explicit "needs plan amendment / cannot pick a science direction" verdict), the autonomous response is `task.py set-status <N> planning` + re-invoke `/adversarial-planner` with explicit pivot scope naming the contradiction; do NOT descope a hyperparameter to dodge it, do NOT silently pick among the subagent's paper-over options as if it were a valid fork. Full rule: workflow.yaml § `pivot_criteria.plan_contradiction_replan` + `.claude/skills/issue/SKILL.md` § Autonomous session behavior. Closed regression: task #488 round 10 (2026-06-08). **Autonomous mode: never stop a pod to PARK or await a user** — `pod.py stop` is allowed only while work continues toward the Goal in the same session; "Pod-N stopped while awaiting user decision on …" is the banned regression closed 2026-06-07. **Autonomous mode: a FREE, no-data-loss path beats parking** — when a free continuation that loses nothing EXISTS (canonical: an in-SLA Anthropic Message Batch self-harvests for free at `expires_at` via the deadline-bounded `batch_judge` poller — #658/#663), take it and keep the deadline-bounded poll running (end the turn; the bg poll chain / `/issue-tick` re-wakes you); NEVER park to await the user or propose a PAID rerun while that free path is available (a paid rerun is justified only when the free path is genuinely gone — the batch expired with no result). Route batch judging through the #663-hardened `eval.batch_judge` client, never a hand-rolled `messages.batches.create` + deadline-less poller (enforced by `scripts/workflow_lint.py --check-batch-judge-client`). **Autonomous mode: cost is gated ONLY at the Step 2c plan-approval GPU-hour cap, never mid-run** — no mid-run "this is getting expensive" pivot to user-park, consistent with `tests/test_no_dollar_budget_caps.py`. When in doubt, continue.

**Push through bugs in recovery mode.** Once Thomas has approved the GOAL ("re-run cell X", "promote #N"), small surface-area bugs along the way (preflight failures, TP=2 vs TP=1, Ray timeouts, env-var omissions, transient infra hiccups) are mine to fix and retry without re-asking. State the bug + the fix in ONE sentence and proceed — no 3-option menus, no "want me to proceed?". Escalate only when (a) the fix changes experiment scope, (b) the fix is irreversible/high-cost (force-push, terminate-running-pod, credential change), (c) ≥3 fundamentally different fixes failed, or (d) the bug points to a real factual question only Thomas can answer. **When escalation IS warranted, frame exactly TWO paths, max** — `continue-as-planned` vs `pivot-to-<X>`, each with a one-line rationale + cost. No 4+ option menus. (The `gates.inline id=4 plan_approval` approve/revise/reject trio is grandfathered.) **This two-path escalation is INTERACTIVE-ONLY.** In an autonomous session (`EPM_AUTONOMOUS_SESSION=1`, spawned via `spawn_session.py spawn-issue --auto`) there is no human to escalate to: never present a choice menu / "want your call?" / two-path fork — pick the best option toward the task Goal (max info-gain-per-GPU-hour; tie-break to the lower-cost/safer/record-correcting action) and continue, stating `Decision: <X>`. Asking is itself the failure mode there. Full rule: `.claude/skills/issue/SKILL.md` § Autonomous session behavior.

**Subagent halt conditions** (workflow.yaml § subagent_halt_conditions). A 4th-round ensemble FAIL → strategy pivot, not a block; block only when the pivot space itself is exhausted. Bare FAIL without an explicit `needs-user` flag is NEVER a block trigger.

### Orchestrator vs subagent re-invocation

Subagents have ONE turn. The harness re-invokes the ORCHESTRATOR on each bg `Bash` exit when called with `run_in_background=true`. Therefore:

- Waits longer than ~5 min belong to the orchestrator's bg-Bash polling loop (`scripts/poll_pipeline.py`), NOT subagent sleep-chains.
- Subagents are for bounded, in-context work: launch+confirm, write+commit, check+report. `experimenter` is canonical: launches and exits within 60s; orchestrator polls.
- **End the turn when bg work is in flight.** Don't sleep-poll or block-wait. Anti-pattern: launching N parallel subagents and sequentially `TaskOutput`-blocking each — serializes work the harness wants parallel and loses notifications. A foreground `sleep N && <cmd>` chain is mechanically BLOCKED by a harness guard (15+ blocked attempts across ~13 sessions on 2026-07-03, each a wasted turn) — poll via a background `Bash` or a `Monitor` until-loop instead, and load deferred tool schemas first (`ToolSearch("select:Monitor,TaskOutput")`); calling an unloaded deferred tool fails with `InputValidationError`.
- **Ownership check before any resume/launch on a shared artifact path.** Before resuming, relaunching, or "recovering" a run whose script or output path a live subagent may own, probe first — `pgrep -af '<distinctive invocation>'` for the workload AND confirm the owning subagent is not still live/mid-edit; a live owner ⇒ defer to it, never launch a duplicate. A "done" read on an EMPTY expected-results dir (a Monitor DONE with no outputs) is a verify-first trigger, not a resume trigger (#825, 2026-07-14: a false Monitor DONE spawned duplicate "resume" runners racing a healthy owned run; a mid-edit script launch double-wrote → NameError). Retrying your OWN failed launch is the kill-probe case — `.claude/rules/crash-fix-rounds.md` § Kill-before-relaunch; this bullet governs runs another live agent owns.
- **Never nest `nohup ... &` (or any inner `&`) inside a `run_in_background=true` Bash when that bg-Bash's completion is your completion signal** — the wrapper exits the instant the inner job detaches, the harness signals "done", and a premature read follows (#825, 2026-07-14: FileNotFoundError on results not yet written). Let the bg Bash BE the process (run the command foreground inside it — bounded work only), OR use the sanctioned detached shape (`.claude/skills/issue/SKILL.md` § Detached VM-side long compute phases — mandatory for VM-local phases >~15 min), where completion is tracked by pid+log breadcrumbs and the wrapper's exit is deliberately NOT the signal.

**Pre-spawn sentinel check (#1204) — check BEFORE composing.** The exit-9 short-circuit fires at DISPATCH time, but the thin `codex-*` composers spawn in the same batch as the Claude reviewers BEFORE any dispatch — during a known outage each round burns 1–3 composer spawns whose prompts are discarded (≥9 sessions, 2026-07-08; #1135/#1146 show the intended skip done ad hoc). Before spawning any `codex-*` prompt-composer in a review round, run the canonical check below. NEVER fabricate `epm:codex-task-failed` or a twin verdict marker — those belong to the helper/twin. FAIL-OPEN: sentinel absent / unreadable / corrupt / expired / implausibly far-future, or `EPM_SKIP_CODEX_QUOTA_SENTINEL=1` → spawn normally (the dispatch-time exit-9 short-circuit stays the arbiter and backstop). The decision keys on the TWO-SIDED window `now < until_unix <= now + 45 d` — the upper bound is the helper's `QUOTA_MAX_PLAUSIBLE_SECS` plausibility ceiling (`codex_task.py:295`), so a hand-seeded or corrupt far-future timestamp can never wedge composer spawning off permanently (it prints CLEAR and the next dispatch's `_quota_sentinel_active` deletes it). A `parse_ok: false` sentinel with a plausible future `until_unix` (the helper's 24h fallback TTL) is honored the same as a parsed one.

```bash

ROOT="$(dirname "$(git rev-parse --path-format=absolute --git-common-dir)")"   # main checkout, worktree-safe
uv run python -c '

p = os.environ.get("EPM_CODEX_QUOTA_SENTINEL_PATH") or sys.argv[1]
try:
    assert os.environ.get("EPM_SKIP_CODEX_QUOTA_SENTINEL") != "1"
    d = json.load(open(p))
    now = time.time()
    until = float(d["until_unix"])
    assert now < until <= now + 45 * 86400   # QUOTA_MAX_PLAUSIBLE_SECS parity (codex_task.py:295)
    print("CODEX_QUOTA_LIVE until=" + str(d.get("until_iso", "?")))
except Exception:
    print("CODEX_QUOTA_CLEAR")
' "$ROOT/.claude/cache/codex-quota-exhausted-until"
```

(Read-only check: unlike `_quota_sentinel_active` it never deletes an expired/corrupt/far-future sentinel — lifecycle stays with the helper.)

## Context hygiene

- **`/compact` at ~30% remaining**, earlier if dense — but only at task/phase boundaries, never mid-task (compaction invalidates the conversation cache layer = one expensive full re-read). Prefer `/rewind` over `/compact` when abandoning a path (rewind truncates back to an already-cached prefix). Use `/clear` (alias `/new`) between unrelated tasks.
- **Prompt-cache key discipline.** Model, effort level, and fast-mode are all part of the prompt-cache key: NEVER flip any of them mid-session (a flip re-reads the entire conversation uncached). Pin model + `CLAUDE_CODE_EFFORT_LEVEL` at session spawn; per-subagent model pins are fine (each subagent has its own cache).
- **2× rule.** If a multi-step prompt repeats in a session, propose a skill / hook / `CLAUDE.md` edit *before* the second pass.
- **429 token-pacing.** The org-wide input-token cap climbs at each minute boundary, so pace input tokens, don't retry harder. (a) **Stagger ensemble spawns** across a few seconds so prompt-token bursts don't stack. (b) **Keep subagent prompts lean** — pass the PATH to the plan/brief, never inline the body or events.jsonl dumps. (c) **Never dump giant logs into tool output** — `grep -iE 'error|traceback|killed|OOM'` / `tail -50`, never `cat` a multi-MB log (it re-enters context next turn). On a 429: wait for the next minute boundary and retry the same call.
- **Spurious usage-policy refusals.** This project's safety-research vocabulary (backdoor / trigger / implant / misalignment, raw EM completions) — and, on workflow-guard/security tasks, shell-attack vocabulary (write-then-execute channels, destructive-git payloads, fail-open redirects; refused as "violative cyber content", #1098 2026-07-07: 2 reviewer kills then a ~2.7h orchestrator wedge) — sometimes trips false-positive "violates our Usage Policy" API refusals — 18+ hits on 2026-06-09 killed an implementer's final report, an analyzer mid-run, and several Codex wrappers. Recovery (never park on a refusal): (a) check what durable writes the killed agent already made before re-dispatching; (b) retry ONCE with a rephrased brief that thins the trigger-dense wording; (b2) if the original SUBAGENT spawn and its one rung-(b) rephrased/thinned retry are BOTH refusal-killed (two same-model kills total on the task), re-spawn it ONCE with a per-subagent model pin (`model: "sonnet"` on the Agent call) BEFORE escalating to (c) — refusal trips can be model-pathway-specific, not purely content-driven (#1092, 2026-07-07: 3 fable-5 implementer kills at 19/25/30 tool calls, one on fully neutralized inputs; the sonnet re-spawn ran 53 min / 103 tool calls with zero refusals on the same inputs), and per-subagent model pins are prompt-cache-safe (each subagent has its own cache); if the pinned re-spawn also dies, fall through to (c) — or to cross-vendor Codex dispatch for a full implementer build that (c) cannot cover; (c) if a thin wrapper refuses twice, the orchestrator composes the artifact itself; (d) agents ingesting raw harmful-content completions, real-world-corpus prompt/rollout text (LMSYS/WildChat-class — unscreened real user text routinely carries in-corpus jailbreak/explicit rows; #1073: an analyzer refusal-killed twice paging raw LMSYS rollout text), OR safety-benchmark question banks (EM evals, jailbreak data, `src/explore_persona_space/artifacts/query_banks/*.json` — advbench/strongreject/Betley-lineage/sensitive-info) read aggregate JSONs / judge labels / structural digests (counts, `jq 'keys'`, sha256); cherry-picked examples may be pulled from RAW-COMPLETION files by grep + line offset when genuinely needed, but harmful BANK items are digest-only — reference by filename + index, never print item text (mechanically enforced by the `guard_harmful_bank_read.sh` PreToolUse hook; sanctioned-maintenance override: `EPM_ALLOW_BANK_READ=1`); and never page whole raw-completion or bank files into context (#866: four implementer sessions refusal-killed after bank text was paged in during verification); (e) prevention beats recovery: briefs and prompts for harmful-content AND real-world-corpus (LMSYS/WildChat-class) tasks name banks/corpora by filename + row count, never inline example items — FIRST-PASS briefs carry this discipline, not only post-kill retry briefs (#1073) — trigger-dense brief vocabulary alone killed sessions at prompt level in #866; (f) **orchestrator refusal-wedge:** when the ORCHESTRATOR session itself is refused on consecutive wake turns (every turn dies in the refusal text — zero actions land, so in-session recovery logic (a)-(c) can never execute), recovery is a FRESH SESSION, not another in-context retry: the watcher's prompt-wedge lane counts `isApiErrorMessage: true` assistant rows as wedge evidence and force-respawns after ≥3 consecutive failed wake TURNS — a wake ending in an api-error row counts as failed even when a mid-turn heartbeat kept the self-report fresh (`EPM_TICK_WEDGE_MIN_FAILED_TURNS`, `0` disables; staleness no longer gates this lane, #1127) — plus an alternating-storm rate trigger (`EPM_TICK_WEDGE_MIN_FAILED_TOTAL`) (#1074: 38 refused wake turns / ~2h unrecovered before this lane was refusal-aware), plus a dead-wake trigger (`failed-turn-silence`): every completed tail turn failed and the transcript silent ≥ `EPM_TICK_WEDGE_DEAD_SILENCE_MIN` (20 min) stops the session for fresh respawn (the crash-recovery arm completes it) without waiting for wake accumulation, bounded 3/issue/UTC-day (#1209: a turn-1 refusal death accumulates no failed wakes and freezes below every counting threshold; ~100 min unattended pre-fix; all five wedge triggers are episode-belt + day-capped as of #1241); manual fast path — `spawn_session.py stop --session-id <sid>` then `spawn-issue --issue <N> --auto`. The recovery's actual mechanism is the FRESH CONTEXT — the respawn drops the accumulated refusal-poisoned conversation; its boot prompt (`/issue <N>`) and tick turns are vocabulary-thin (digest-only per `.claude/skills/issue-tick/SKILL.md`), while the fresh session's own Step-0 task-state read remains governed by (b)/(e) above — a LOWERED refusal surface, not immunity; (g) **refusal-truncated Agent spawns:** a mid-stream refusal can still DISPATCH a partially-generated `Agent` tool call — the subagent starts running on a brief cut mid-sentence (#1090, 2026-07-08: two spawns dispatched truncated in the same second as their refusals; both recovered when the orchestrator noticed and completed the brief via 2-3 SendMessage parts) — so after any refusal on a turn containing an Agent spawn, VERIFY the dispatched prompt's completeness and, if cut, complete the brief via SendMessage to the running subagent before treating the spawn as healthy.

Each `issue-<N>` subtree carries an **ext4 project id == the issue number** with a hard byte cap (`EPS_ISSUE_DISK_CAP_GB`, default 128 GB) — so one task cannot exhaust `/` NOR starve another concurrent task: a write past the cap fails loud with `EDQUOT` (the same fail-loud signal the RunPod MooseFS quota produces) while every other issue keeps writing. **Recovery is resize/raise-cap, NEVER delete active data:** when the data disk is wedged, `clean_experiment_downloads.py <N> --apply` on a TERMINAL issue, or `setquota -P <N> 0 <cap_kb> 0 0 /mnt/eps-data` (live, no remount), or a GCP live-resize (`gcloud compute disks resize` + `resize2fs`). The guard + watcher watch BOTH disks (`/` byte-floor-based, `/mnt/eps-data` PERCENT/statvfs-based and ESCALATE-ONLY — no reclaim arm runs on the data disk). **`new_worktree.sh` asserts the bind is live** (`EPS_WORKTREE_REQUIRE_BIND=1`) before creating, so a worktree never silently lands back on `/`; it refuses while the cutover `.claude/cache/worktree-migration.LOCK` is held (as does `task_workflow._ensure_managed_main_worktree`). The **`VM_ANALYSIS_FOOTPRINT_GB_MAX=50` off-VM routing rule is UNCHANGED** — a >50 GB analysis phase still routes to the `cpu-bigmem` GCP lane; the per-task quota is a containment BACKSTOP, not a permission slip to materialize >50 GB on the VM. **One-time #681 cutover (live-VM state surfaced by `new_worktree.sh` WARN while inert):** `new_worktree.sh` emits a once-per-session WARN at worktree creation when the data disk is a live mount but `.claude/worktrees` is NOT yet bind-mounted onto it and the two opt-in flags are unset — meaning caches still land on the boot disk `/` with no quota. The WARN is the live source of truth for whether the cutover is still needed. To complete the cutover (a separate ops task, deferred to a quiet window — it migrates live worktrees): (1) set the migration LOCK `.claude/cache/worktree-migration.LOCK` so `new_worktree.sh` + `task_workflow._ensure_managed_main_worktree` refuse mid-swap; (2) move the existing `.claude/worktrees/*` contents onto `/mnt/eps-data`, then `mount --bind /mnt/eps-data <repo>/.claude/worktrees` and add the bind to `/etc/fstab` so it survives reboot; (3) export `EPS_WORKTREE_REQUIRE_BIND=1` and `EPS_WORKTREE_ASSIGN_QUOTA=1` in BOTH the cron environment (`cron_*` wrappers) and `bootstrap_pod.sh` / the VM shell profile so every consumer sees them; (4) seed per-task quotas for live issues (`sudo setquota -P <N> 0 <cap_kb> 0 0 /mnt/eps-data`); (5) remove the migration LOCK. Verify: `findmnt --mountpoint <repo>/.claude/worktrees` succeeds and a fresh `new_worktree.sh` run no longer WARNs. (Surfaced by task #771, 2026-06-30.)
- Each experiment downloads its source data from HF into VM-local caches under `data/issue_<N>/hf_dl/` + `data/issue_<N>/g*_dl/` — in the **repo-root `data/` AND in the issue's worktree** (`.claude/worktrees/issue-<N>*/data/issue_<N>/`, where the live run usually writes; the worktrees tree hit 139 GB on 2026-06-26, now relocated to `/mnt/eps-data` per #681). These are **re-downloadable caches** (the data lives on HF) — they are cleaned automatically at `/issue` Step 8 (after upload-verification PASS, post-teardown) via `uv run python scripts/clean_experiment_downloads.py <N> --apply`, which sweeps both the repo-root and worktree copies. **NEVER delete `store/` or `eval_results/`** (in repo-root OR worktrees) — those are durable artifacts, not caches. **(#911) Both janitors ALSO sweep non-canonical issue-keyed staging caches** — top-level `/tmp/` dirs named `i<N>*` / `issue<N>*` / `issue-<N>*` / `issue_<N>*` or `*_<N>` (underscore only), and `data/` dirs named `issue…<N>…{_dl,_hfstage,_cache}` — under the same contract (terminal reap / active escalate / `store/` + `eval_results/` never touched, nested OR sibling) plus three extra gates on the non-canonical set: a 48 h recently-touched keep (file `max(mtime, atime)`, env `EPS_NONCANONICAL_CACHE_MIN_AGE_HOURS`), a nested-`store/`/`eval_results/` outright block, and a **positive re-downloadability-evidence requirement** (hub-layout markers or data-repo-prefix mirror verification — a predicate failure is kept + sidecar-escalated, never deleted). The `/tmp/` sweep is a CLI-`main()`-only opt-in (`production_tmp_root()`); library calls with `tmp_root=None` never touch `/tmp/`. Kill switch: `EPM_SKIP_NONCANONICAL_CACHE_SWEEP=1`.
- **Incremental (between-phase) cleanup for multi-phase runs.** Step-8 cleanup only fires at experiment END, so a multi-phase run holds the PEAK of all phases' download caches at once. A run whose phases each download then consume inputs should reap each CONSUMED phase's cache BEFORE the next phase downloads more — `uv run python scripts/clean_experiment_downloads.py <N> --incremental --apply` (same safety contract; no terminal-status gate — the run knows the phase is done; re-downloads on demand). This bounds PEAK footprint but does NOT rescue a single phase whose OWN footprint exceeds the disk: a CPU/analysis phase whose estimated local footprint exceeds **50 GB** (`VM_ANALYSIS_FOOTPRINT_GB_MAX`) must be ROUTED off the VM (to a pod / GCP big-volume instance — the concrete GCP lane is `intent: cpu-bigmem`, a CPU-only `gpu_count=0` `n2-highmem` instance with a `--boot-disk-gb`-sized disk, #677 — or stream without local materialization) at plan time — see the data-footprint carve-out in § "CPU-only phases don't hold GPU pods" above (`planner.md` §9, `critic.md` Methodology lens item 10). Incident 2026-06-26: #658's Phase-1 analysis materialized a 139 GB activation store on the VM worktree on the shared 188 GB disk → `/` hit 100% full, fleet-wide stall.
- Fleet-wide backstop for caches that escape Step 8 (crashed runs, follow-up rounds): the **`vm_disk_guard.py` cron** (`scripts/cron_vm_disk_guard.sh`). When `/` usage exceeds **85%** (`EPS_VM_DISK_THRESHOLD`) it runs tiered safe cleanup — (a) `uv cache prune`, (b) `hf_dl`/`g*_dl` caches (repo-root + worktree copies) PLUS the #911 non-canonical issue-keyed caches (top-level `/tmp/` `i<N>*`/`issue<N>*`/`*_<N>` dirs + `data/` `issue…<N>…{_dl,_hfstage,_cache}` dirs, behind the recency / nested-durable / positive-evidence gates) for issues at a TERMINAL status (`completed`/`archived`/`awaiting_promotion`; status read-only, never mutated — an ACTIVE issue's caches, incl. its worktree data + `/tmp/` staging, are never touched, only attributed in the `--json` `active_cache_attributions`), (d) an age-gated reap of the VM's pod-style `/workspace/.cache/huggingface` hub cache (repos unused ≥ 14 days, `EPS_VM_WORKSPACE_HF_CACHE_MAX_AGE_DAYS`; pod-guarded so it can never run where `/workspace` is a real volume; boot pass only), (c) stale `logs/**/*.log` + `/tmp/*.log` — and, if still over threshold after cleanup, prints a loud WARNING + fail-soft Telegram push for manual triage. Report-only by default; the cron passes `--apply`. **It ALSO watches the `/mnt/eps-data` data disk (#681) in a SECOND, ESCALATE-ONLY pass** (`run_guard(disk_path="/mnt/eps-data", reclaim_tiers=False)`): the `/`-rooted reclaim tiers (a)/(c) never run there — only tier (b) (terminal-cache reap + active-cache escalation), the one data-disk-appropriate arm. The data-disk pass is skipped when the mount is absent (a clean no-op before/without the cutover).
- **Scheduled `uv cache prune` (idle-time cron).** The global uv package cache grows unbounded as dependency sets churn (it ballooned to ~56 GB by 2026-06-26). `scripts/cron_uv_cache_prune.sh` runs `uv cache prune` — which KEEPS in-use entries (NOT `uv cache clean --force`, which wipes everything) and is graceful when the cache lock is held — to keep the cache trimmed continuously so `vm_disk_guard` rarely has to fire on a full disk. Recommended schedule: **daily off-peak** (e.g. `17 4 * * *`). Register via the orchestrator's cron management (not auto-registered).
- **Active-task escalation — warn-only, NEVER auto-deletes active data (#679).** An ACTIVE task can hold a large re-downloadable cache the terminal-status gate cannot reap. Three escalation channels surface this WITHOUT ever deleting an active task's data, all writing one shared sidecar stream `.claude/cache/disk-guard-events.jsonl`: (a) `vm_disk_guard.py`'s tier-(b) kept-branch ESCALATES a band-worthy active cache (Telegram push + sidecar row naming the task, the largest cache path, the footprint, and the SAFE post-run reclaim command `clean_experiment_downloads.py <N> --apply`), deduped on (task, threshold-band) with a >25% growth re-alert and a per-(task,band) ack-sentinel suppress (`.claude/cache/disk-guard-ack-<N>-<band>`); (b) the `autonomous_session_watch.py` sub-floor sentinel writes a `band=sub-floor` row attributing the pressure to the top per-issue caches and signalling a sooner re-check — for `/` it fires at `<60 GB` free (`EPM_VM_DISK_SUBFLOOR_GIB`); for the `/mnt/eps-data` data disk it uses a SIZE-INVARIANT PERCENT threshold (`decide_subfloor_pct`, `EPM_VM_DATA_DISK_SUBFLOOR_PCT` default 85%) so a future resize cannot push the fire point past the wedge, and it attributes the WORKTREE-internal caches (`.claude/worktrees/issue-*/data/...`) via `repquota -P` per-project usage (du fallback); (c) `clean_experiment_downloads.py`'s nested-`store/` parity guard SKIPs (never deletes) a wholesale `rmtree(hf_dl)` when a generated `store/` is mis-rooted under the cache dir and not verifiably mirrored on HF. The **structural** bounded-by-construction fix (dedicated GCP disk + ext4 per-task project quotas so one task cannot exhaust `/` NOR starve another) was DELIVERED by **#681** (see the lead bullet above).
- **VM-root preflight floor (#679).** Preflight surfaces a WARN when `/` is >90% used or <20 GB free, AND a HARD FLOOR (`report.ok=False`) when VM-root free is below `EPM_PREFLIGHT_DISK_FLOOR_GB` (default 40 GB) — a fresh launch below the floor FAILs fast rather than starting near the silent-Bash-failure regime (RunPod `/workspace` is exempt; the EDQUOT quota probe is binding there). Override a deliberate low-disk launch with `EPM_PREFLIGHT_DISK_FLOOR_OVERRIDE=1` (degrades the FAIL to a logged WARN). Both point at `vm_disk_guard.py --apply`.

## Experiment Report Structure

Clean-result write-ups follow the **four-flat-H2 (v4) markdown clean-result spec** (migrated 2026-W26; forward-only): four required H2 sections in order — **Takeaways / Goal / Methodology / Results** — plus a bold `**Repro:**` / `**Context:**` footer (NOT an H2), with NO `## What I ran` / `## Findings` / `## Data` / `## Reproducibility` H2 and no retired `## Human TL;DR` / `## TL;DR` / `## Details` / `## Figure` (any of those is a hard FAIL in a v4 body). v4 bodies carry the `<!-- clean-result-v4 -->` sentinel right after the H1 title, and **confidence lives in the H1 title tag ONLY** (no body `Confidence: …` sentence). `## Takeaways` is 3–6 numbers-first bullets in plain academic register — the rolling cross-round synthesis Thomas adapts for Slack, rewritten after every follow-up round. `## Goal` has TWO parts — `**This experiment in context:**` (what THIS experiment tests + how it relates to the other experiments in its line; the ONLY place prior-issue links appear) and `**Broader narrative:**` (the project-level / open-questions question it serves). `## Methodology` is the complete "everything required to understand the results" section — `**Design:**` / `**Training:**` (with the COMPLETE hyperparameter table, every value from ground truth + a Source column) / `**Evaluation:**` / `**Data extraction:**` / `**Sample training/evaluation data + completions:**` (verbatim worked examples, each subset-disclosed + linked to the full artifact); it absorbs the v3 `## What I ran` + `## Data` AND the entire former standalone methodology doc. `## Results` carries one `### <result>` H3 per result, each in the strict three-beat **what-is-plotted-EXACTLY → plot (one inline figure + blockquote caption) → interpretation**, and REQUIRES both a high-level summary-metric plot AND the low-level per-unit data plot (points labeled) for any aggregate result. The `**Repro:**` / `**Context:**` footer carries compute + code SHA + pinned artifact links and the run-provenance (created/run dates, follow-up lineage, verbatim originating prompt — SPEC.md § footer, verifier checks 16/17). **Conciseness is mechanical, not aspirational** — `verify_task_body.py` check 20 enforces caps (Takeaways 3–6 bullets, per-bullet ≤30 words WARN / ≥100 FAIL; per-`### <result>` prose ≤120 words WARN / ≥180 FAIL; figure caption ≤60 words WARN; total-prose budget WARN, `## Methodology` excluded). Verified by `scripts/verify_task_body.py`; a stray v3 content H2 or any retired earlier H2 is a hard FAIL (forces clean migration). Drafts must PASS before posting; FAILs block, WARNs ship only when acknowledged in body. **The standalone methodology doc is now a mechanical COPY of the body's `## Methodology` section** (committed to `main`, secret-gist-mirrored, linked at the top of the body) — no separate findings-blind authoring step. **Forward-only:** v3-sentinel (`<!-- clean-result-v3 -->`), v2-sentinel (`<!-- clean-result-v2 -->`), and pre-sentinel legacy bodies keep their prior shape and verification behavior verbatim and are NEVER newly hard-FAILed by a v4 rule (the one exception: a same-issue follow-up round folding onto a v3/v2 body migrates it to v4, SPEC.md § Follow-up consolidation).

**Paper format (opt-in via `paper: true` frontmatter) — separate track.** A `kind: experiment` task whose frontmatter carries `paper: true` does NOT use a markdown clean-result body at all: its canonical clean-result is a self-contained LaTeX **research paper** (a parameterized `.tex` → a reproducible PDF + a sanitized, committed `paper.html`) under `docs/papers/issue_<N>/`, and `body.md` becomes a thin **paper-stub** (H1 + abstract + paper link + the `paper: true` / confidence / origin frontmatter the existing REGISTRY / dashboard / follow-up-proposer readers consume). The paper's required sections (Abstract / Introduction / Methods / Results / Discussion+Limitations / References / Appendix) map onto the same content the v4 markdown shape carries; **NO confidence anywhere in the paper body** (confidence lives ONLY in the paper-stub frontmatter title tag — `verify_paper.py` hard-FAILs a `(LOW|MODERATE|HIGH confidence)` tag or bare `Confidence:` line in the `.tex`). Cross-experiment references use `\epsref{N}` (never a bare `#N`). The deterministic build is `scripts/build_paper.py` (multi-pass `pdflatex` + `bibtex` → reproducible PDF, HF-data-repo PDF upload, sanitized `paper.html`, `paper_manifest.json`); the mechanical gate is **`scripts/verify_paper.py`** (NOT `verify_task_body.py`, which stays the markdown verifier) — compile-clean, required sections + order, no confidence in body, `\includegraphics` confined + resolves, `.bib` + `\epsref` resolve, manifest complete + hashes match, paper-stub valid. The `analyzer` (PAPER-TASK MODE) assembles the `.tex` and splices in the `methodology-writer`'s findings-blind Methods + Appendix, runs build → verify, and writes the stub ONLY after `verify_paper.py` PASSes (on FAIL it parks `reviewing`/`blocked` with the `.tex`+`.log`, never a stub-only dead state). **The `paper:` flag is a deterministic branch + kill-switch: absent/false ⇒ the markdown v4 path above, unchanged. The DEFAULT is markdown v4; paper-mode is opt-in. v3/v2/v4-markdown bodies stay grandfathered and are never converted.** To opt a task into paper-mode, add `paper: true` to its `body.md` YAML frontmatter (the analyzer + both critics read it via `task_workflow.is_paper_task(fm)`). There is NO `task.py new --paper` flag and `task.py new --body-file` does NOT merge a body-file's frontmatter — `new` builds frontmatter from its own flags only — so the reliable opt-in is to edit the task's `body.md` frontmatter directly (any time before the analyzer runs at Step 8). Absent the flag the task uses the markdown v4 path, unchanged. Full spec: SPEC.md § "Paper format (`paper: true`)"; the `/issue` paper-mode wiring is SKILL.md Steps 8 / 9a-bis / 9a-quater.

**Ad-hoc results summaries state per-arm provenance in their setup line.** Any summary of experiment results or model generations shown to the user OUTSIDE a clean-result body — a chat summary, a quick or interim figure, a mid-run result report — states, per arm, the data/completion provenance (e.g. on-policy vs teacher-forced vs canned/templated vs third-party-LLM-written) and the generation recipe (sampling params + rollout count, e.g. "single stochastic sample" vs n=K per prompt) in its setup line / caption. When the provenance was not verified — or is inherited from a reused artifact — say so explicitly; never guess a confident label. The v4 what-is-plotted-EXACTLY discipline governs clean-result bodies only; this extends the same disclosure to everything shown earlier (#1139; twice-asked #825 separator-round provenance). **Verify before asserting:** a specific number, a head-to-head winner, or a never-run/missing-cell claim in chat is checked against the underlying artifact first — grep/`jq` the `eval_results/` JSON (or the named HF/WandB artifact; plus sibling issues' artifacts for coverage claims) — naming which artifact (and, for winner claims, which fit/eval regime) the number comes from. Never re-cite a task body's numbers or reason from one task's plan as if it were the measurement (#1090 body-number re-cite; #825 never-run claims refuted by #1092's eval_results; #779 winner read off the in-distribution fit instead of the deployable map).

tasks/

`post-marker` exits 0 with a stderr ERROR (and a forensic row in `~/.task-workflow/deferred-commits.jsonl`) when the append landed but the commit was deferred — never re-post on that warning (a re-post duplicates the marker; the next successful commit touching the file sweeps the deferred line).

**`cd "$(... task.py find <N>)"` moves you into the task folder, not repo root.** After that `cd`, a later `uv run python scripts/task.py ...` resolves `scripts/task.py` against the task folder and fails with `No such file or directory` (the path is relative to repo root). This applies to EVERY `scripts/...` invocation (`spawn_session.py`, `pod.py`, ...), not just `task.py`: invoke by absolute path (`uv run python "$REPO_ROOT/scripts/..."`) or `cd` back to repo root first. Same family: after `git worktree remove`, `cd` out of the removed directory before any further compound command (`getcwd` failures silently no-op git operations); and NEVER hand-build `tasks/<status>/<N>/...` paths in inline shell one-liners — status is unknowable from the orchestrator, so read markers via `task.py view <N> --json` / `latest-marker <N>` (two crashes today guessed `tasks/running/<N>/events.jsonl` while the task was elsewhere). **Bare `python` is unavailable on this VM** — prefix EVERY python invocation with `uv run python`, INCLUDING the consumer side of a pipe (`... | uv run python -c "..."`, NEVER `... | python -c "..."`, which dies with `python: command not found` exit 127).

**Concurrent repo-root committers.** Many sessions commit to the shared repo root in parallel. Stage by explicit path only (never `git add -A`/`git add .`), retry once on an `index.lock` collision, and on a rejected push run the single-flight root-sync helper — `uv run python scripts/sync_repo_root.py` — instead of hand-rolling a pull-rebase recovery loop (mechanically enforced by the `guard_repo_root_pull.sh` PreToolUse hook, #1201 — a non-ff `git pull` at the repo root is blocked; worktree `git -C` pulls and `--ff-only` pulls stay open): it flock-serializes concurrent recoveries (`~/.task-workflow/root-sync.lock`; a second caller exits 0 immediately), sweeps untracked-collision files (byte-identical → removed, content already at `origin/main`; differing → rescued to `~/.task-workflow/root-sync-rescue/<ts>-<pid>/`, never deleted), runs the bounded `git pull --rebase=merges --autostash`, recovers stranded `autostash` stash entries, and pushes with one rebase-retry; on a genuine content conflict it aborts cleanly and reports (no husk, no repo-root `reset --hard`). The rebase mode is load-bearing: plain `--rebase` FLATTENS AWAY any not-yet-pushed merge commit sitting on the shared root — a concurrent session's documented recovery pull silently dropped the same workflow-fix merge twice on 2026-06-12 — and a bare rebase without `--autostash` predictably fails on the always-dirty shared root. The repo config pins `pull.rebase=merges` + `rebase.autoStash=true` (shared `.git/config`, covers all worktrees) so even a bare `git pull` behaves safely. **Push IMMEDIATELY after committing a merge** — an unpushed merge commit on the shared root is at risk from every concurrent session's pull; for multi-file merges during heavy fleet activity, use a scratch worktree detached at `origin/main` (`git worktree add --detach <path> origin/main` — `main` itself is held by the repo root) + `git push origin HEAD:main` (a bare `git merge` at the repo root is hook-blocked, #1128). Before batch-fixing parked task bodies, post a claim marker (`epm:progress` note naming the task IDs) so a parallel session doesn't double-fix the same bodies. **Never pipe a `git push` (or merge/PR command) through `tail`/`grep`/`head`** — the pipe masks the non-zero exit code and the session proceeds believing the push landed (4 sessions hit exactly this on 2026-07-02); run it bare and check the exit code, or use `set -o pipefail` when a pipe is unavoidable (mechanically enforced by the `guard_piped_git_push.sh` PreToolUse hook + `workflow_lint.py --check-piped-git-push`, #1048).

**Body size cap.** `events.jsonl` `note` is capped at 50,000 chars (`post-marker` raises on oversize). Write to `artifacts/`, post `epm:failure v1` (`failure_class: infra`, `reason: note_oversize`) referencing it, then `set-status <N> blocked`.

## Compute backends — multi-lane router (GCP FIRST; RunPod is the last-resort fallback)

**Compute is NOT RunPod-only — GCP is in the workflow.** Every `/issue` launch routes through the unified backend router (`src/explore_persona_space/backends/` — `router.py`, `gcp.py`, `slurm.py`, `runpod.py`; CLI `scripts/dispatch_issue.py`; helper `issue_dispatch.dispatch_for_issue`), keyed on the task's `backend:` frontmatter:

- **Absent/empty frontmatter → `auto`, standing default GCP FIRST:** `DEFAULT_AUTO_LANE_ORDER = ("gcp", "nibi", "fir", "mila")` — credits-backed GCP capacity is spent before the free SLURM lanes (override via `EPM_AUTO_LANE_ORDER`; `runpod` in the override raises loudly). The GCP lane walks a **length-aware fallback ladder** (#656 cost-ordering, #680 length-aware order): for "short" jobs (`time_budget_hours × gpu_count ≤ EPS_GCP_SPOT_MAX_GPU_HOURS`, default 2 GPU-h, OR `spot_tolerant`) spot leads — spot A100-80 → spot A100-40 (`a2-highgpu-1g`, fits-in-40GB single-GPU 7B intents `eval`/`debug`/`lora`/`lora-7b` only) → flex-start A100-80 → on-demand A100-80 → on-demand A100-40; for long / unknown-length jobs spot is barred and flex-start leads — flex-start A100-80 → on-demand A100-80 → on-demand A100-40 (NO spot; an unknown-length job is NOT short, so it takes this branch). The flex-start rung threads `--provisioning-model=FLEX_START` (A2 acceptance confirmed by a live #680 probe); the per-day attempt cap `MAX_GCP_ATTEMPTS_PER_DAY = 16` (#1121, raised from 8: the width-8 short walk is up to 14 rungs + margin — #680 had sized 8 as the 5-rung short ladder + margin; still an attempt COUNT, never a dollar cap). Each rung capacity-misses → advance to the next; a GCP **WORKLOAD failure of ANY class now FAILS OVER TO RUNPOD** (`reason: gcp_workload_failover_runpod`, with the `GcpWorkloadError` evidence on the marker `extra`) — the deliberate reversal of the historical "GCP workload failure surfaces with NO fallback" invariant (user-directed 2026-06-24, #658): if GCP is failing a run, re-running it on RunPod keeps the science moving AND gives a persistent, SSH-able pod for diagnosis (GCP's `--instance-termination-action=DELETE` destroys the boot disk on crash, so a GCP crash loses its own logs). The failover routes STRAIGHT to RunPod — it does NOT cascade across the remaining GCP rungs or the free SLURM lanes (re-crashing broken code there burns queue time, the original no-cascade concern). **Bound** (no infinite RunPod cascade): RunPod runs the broken job AT MOST ONCE more; if it crashes again the poller surfaces `failure_class: code` → `status:blocked`, which the watcher's capacity-retry pass (`no_compute_available` only) never re-drives. **Coverage scope:** BOTH GCP workload-crash paths now fail over to RunPod — the synchronous `GcpWorkloadError` raised inside `route()` (#658), AND the common production crash detected by the ASYNC poller minutes into the run (`backend_poll.py` `_is_gcp_async_workload_failure` → `_failover_dead_gcp_to_runpod`, wired by #659, merged 2026-06-24 PR #484, idempotency lease-backed; fires when `gcp.poll` resolves a real crash to `current_phase == "terminal_workload_failed"` — a `setup_failed` boot/secrets crash is excluded). Part A crash-diagnostics covers BOTH crash modes. **Remaining gap (#667) — GCP-side only:** neither GCP failover path fires for a HUNG-but-`RUNNING` GCP VM whose guest networking dies (DHCPv4 loss) — `eps/phase` freezes at a NON-terminal value (`workload`), `gcp.poll` reads `running` forever, so neither the sync nor async failover predicate matches and recovery is a MANUAL `--backend runpod` pivot until the poller escalates a frozen non-terminal phase + drain-timeout to a terminal wedged state (pending `kind: infra` follow-up). The SIBLING RunPod RUNNING-but-no-port host wedge is no longer in this gap for the poller-DEAD case: the autonomous-session watcher's pod-safety wedge arm AUTO-TERMINATES + fails over the provably-safe matured untagged inputs-verified case (#770; bounded-once via the shared lease/sentinel), and ALERTs every uncertain case — so a dead poll loop no longer leaves a RunPod no-port wedge billing until a human notices. Full policy + the #658 incident: `.claude/rules/compute-backend-failover.md`. The per-day attempt cap counts actual creates across rungs and stops issuing creates mid-ladder when hit. **A GCP FLEX_START instance that CREATES but never dequeues** — stays PENDING (queued for capacity) past `EPS_GCP_QUEUE_WAIT_SECONDS` (default 600s) — is a THIRD GCP→RunPod trigger (#783/#778): the async poller (`backend_poll._maybe_escalate_gcp_queue_timeout`) cancels the queued instance and fails it over to the RunPod terminal rung (`reason: gcp_queue_timeout_failover_runpod`), an ADDITIONAL advance trigger (NOT a lane-precedence change; a queue-timeout cancel does NOT touch `MAX_GCP_ATTEMPTS_PER_DAY`) — distinct from a workload crash and a capacity miss; full policy in `.claude/rules/compute-backend-failover.md`. **A GCP pre-workload BOOT LOOP — N (default 2, `EPS_GCP_BOOT_DEATH_STREAK_N`) consecutive same-rung setup deaths, counted per (issue, rung, incarnation) in the durable lease — is a FOURTH GCP→RunPod trigger (#1029)** (`reason: gcp_boot_loop_failover_runpod`; the route()-side ladder additionally SKIPS a boot-looped rung same-UTC-day without burning a daily attempt, outcome `boot_loop_rung_skipped`; a lone `terminal_terminated` still never fails over) — full policy in `.claude/rules/compute-backend-failover.md` § Pre-workload boot-loop. **A GCP FLEX_START instance that VANISHES while PENDING — create DONE → later instances-list not-found (no delete op) with the sidecar phase clock's last observed phase `pending` (the DWS queue dropped the request server-side, #1112) — is a FIFTH GCP→RunPod trigger (#1116)** (`reason: gcp_queue_vanish_failover_runpod`; (Incident 2026-06-26: #658's Phase-1 analysis materialized a 139 GB activation store on the VM worktree on the shared 188 GB disk → `/` hit 100% full, fleet-wide stall.) **Compute-character carve-out — a gradient-descent fit is GPU-worthy regardless of footprint.** The OFF-POD-VM default is for *cheap closed-form / sampling-based* CPU work (the bootstrap / permutation / aggregation / judge-scoring / plotting list above); an **iterative-optimization fit** whose inner loop runs gradient descent on parameters (a torch-MLP LOCO, a per-cell probe via SGD/AdamW, a small adapter fit) is GPU-worthy even at small model/dataset size and routes to a GPU lane (`lora-7b` / `eval` / `debug`, smallest that fits), NOT the VM — orthogonal to footprint, and the size gate is the SAME ~15-30 min floor on the PHASE wall-time (a many-cell loop of individually-fast fits counts; a one-off `torch.linalg.lstsq` or a < 30 s linear probe stays on the VM). #658's `_fit_mlp_loco` ran a 300-epoch AdamW fit per cell on the VM CPU, GPU-starved. **But VECTORIZE before routing to GPU** — a many-cell loop of individually-tiny GD fits is OVERHEAD-bound (Python loop + torch op-dispatch + thread oversubscription on small tensors), NOT FLOP-bound — and the SAME applies to a many-DRAW closed-form loop (permutation / bootstrap / null-draw battery over a large fixed pool; #778: pool reduction precomputed once + one batched subset-sum GEMM over all draws, ~70×, stays CPU) — and to a many-cell repeated DENSE-FACTORIZATION loop (a full svd/eigh/lstsq/GCV-ridge solve per fold × layer × arm × trait: cheap once, ruinous ×thousands serially — #823: ~3780 serial full-SVD ridge fits, ~12-20h; batch via Gram/dual-space or a shared factorization, and USE the body-named fast twin); batching the fold/dim/layer/cell axes into batched tensor ops (canonical helper `src/explore_persona_space/analysis/vectorized_mlp_skill.py`) is a 50-100× win that usually makes even the CPU run finish in minutes — GPU is secondary and often marginal at small n. Plan-time rule: `planner.md` §9 compute-character carve-out, `critic.md` Methodology lens item 10(iii). This is plan-time routing, NOT a mid-run gate — `clean_experiment_downloads.py --incremental` (between-phase) + the `vm_disk_guard.py` cron are the runtime backstops, but a phase too big for the disk must never be PLACED there. **Between-phase contract for multi-phase runs:** a run whose phases each download then consume inputs MUST call `uv run python scripts/clean_experiment_downloads.py <N> --incremental --apply` after a phase has CONSUMED its `hf_dl`/`g*_dl` download inputs and BEFORE the next phase downloads more, to bound PEAK footprint (same safety contract — `store/` + `eval_results/` never touched; the cache re-downloads on demand; no terminal-status gate, the run knows the phase is done). See § Disk hygiene below. **GPU-WIDTH right-sizing carve-out — a NARROW GPU phase must not hold the run's PEAK-width pod.** The rules above govern GPU-vs-no-GPU placement; this carve-out governs GPU WIDTH across the GPU phases of a MULTI-PHASE run. Do NOT size one pod at the peak-phase width (e.g. 8× H100 for a finetuning fan-out) and hold it through the run's GPU-light / narrow phases — a ≤7B forward/activation-extract (~1–3 GPUs), a ≤7B single-GPU vLLM generation, a per-cell probe read — or its API-bound graded-judge phase (Anthropic Batch API, ~0 GPU). A narrow / API phase that runs LONGER than ~15–30 min (the same floor as the CPU-only-phase rule above) MUST release/downsize the wide pod (terminate + a fresh narrow provision, a separate narrow pod up front, or off-pod — a same-pod `pod.py stop`/`resume` preserves the SAME GPU spec, so it alone does not re-width); the API-bound judge phase is SEQUENCED after the pod is released so its free, off-pod, deadline-bounded `batch_judge` poll waits with no GPU held. The rule is threshold-gated — a SHORT narrow phase (< ~15–30 min) MAY hold the wide pod because re-provision latency + RunPod supply-constraint exposure then exceed the idle-GPU savings; a LONG one must not, because idle-GPU burn on a wide pod dominates (8× H100 ≈ $25/hr at ≤5% util). This is the SEQUENTIAL-phase sibling of the SIMULTANEOUS shared-nothing sweep rule (one wide pod for N seeds that EACH need it at once) — it is about phases of DIFFERENT widths run SEQUENTIALLY, and NEVER splits a single wide-parallel phase; it only stops a narrow phase from riding the wide phase's pod. Plan-time rule: `planner.md` §9 "Per-phase GPU-WIDTH right-sizing", `critic.md` Methodology lens item 10(iv). (Incident #778: an 8× H100 pod held ≤5% util for 38 min through extract + the API-bound judge phase at ~$25/hr — only the 24-run finetuning fan-out needed 8-wide; same idle-but-billing family as the #664 terminal-upload spend-leak, $530 / 12h on an 8×H200 at 0% GPU.)

(Text >9.5 MB per file line-splits into <9 MB shards before upload, NEVER gzip — `upload_file`/`upload_folder` force-route any >10 MB blob to LFS regardless of extension, and `*.gz` is LFS-matched; see `.claude/rules/upload-policy.md`.)
