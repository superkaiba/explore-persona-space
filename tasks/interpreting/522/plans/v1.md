under #522 as Phase 1 + Phase 2. The reasons not to split:

  receives this plan with the bundling explicit and can REVISE if the
  bundling fails the single-variable test (it does not — each phase
  is internally a single-variable extension of #511).

### Phase 1 — CPU un-descope (VM, 0 GPU)

**Step 1.1 — Add cross-epoch distance-matrix cache to `issue511_probe_count_sweep.py`.**
The current `sweep()` function (lines 429-548) iterates `for ep in epochs`
as outer loop and `for cell in cells` as inner — but the distance matrix
(`bakeoff._compute_metric_matrix` called in `score_one_cell` at line
378) is **target-independent**; it depends only on (extraction_point,
layer, metric, variant, N, subset_idx). Verified by code-read: there is
NO cache; the matrix is recomputed for each epoch even though only the
target G changes. With the loc_ep{1,2,3,5} sweep, this is 4× the work.

Plan: invert the loop nesting. The outer loop becomes (cell, N,
subset_idx), the inner becomes (arm, epoch). Cache the predictor vector
`xv` (the 240-element vector of pairwise distances) per (cell, N,
subset_idx) once per outer-iter, then loop the LOCO CV regression over
the 4 G matrices using the same xv. Pseudo:

```python
for cell in cells:                  # (extraction_point, layer, metric, variant)
    for N in cell.n_grid:
        for r in range(cell.r):
            xv = compute_predictor_vector(cell, N, r)       # CACHED below
            for (arm, ep) in (arm, epoch) targets:
                G = load_target(arm, ep)
                rho, p = _length_partial(xv, dg, ln)
                cv    = _loocv_r2_deterministic(xv, dg, src, tgt, covar=ln)
                rows.append({..., 'arm':arm, 'epoch':ep, 'rho':rho, 'cv_r2':cv})
```

The metric matrix compute (the expensive eigh) runs ONCE per
(cell, N, r), not 4 times. Smoke check: smoke-mode run on N={25, 50} ×
R=2 × headline cell × loc_ep{1,2,3,5} (16 rows) should match a
single-epoch baseline run for matching (cell, N, r) on the rho value
exactly (the same xv goes into each regression).

**Smoke command (≤1 min, the cache-correctness check):**
```bash
uv run python scripts/issue511_probe_count_sweep.py --mode smoke --epochs 1,2,3,5
```

Acceptance: 16 rows emitted, same xv across 4 epochs (verify by adding
an internal cache-hit assertion log line); on (loc, ep=1) at N=25, r=0,
the rho matches the baseline `--epochs 1` smoke to 1e-10.

### Sample-matching protocol

The JS predictor estimates from R=8 sampled responses × 200 probes;
the activation predictors estimate from N=500 probes × cached
activations. These are different sample-size dimensions, so the
direct CV R² comparison is justifiable but not "sample-matched" in a
strict sense. The plan's framing: at the CANONICAL sample budget for
each metric (the rule's R=8/temp=1/256-tok/200-probes for JS;
#502/#511's N=500 / R=10-subset for activations), which one predicts
better? This matches #511's framing of "at the metric's natural
operating point, where does it sit?" — not a sample-equalized
horserace.

## 11. Decision Rationale

### Component 1 hyperparameters

- **N grid {25, 50, 100, 200, 350, 500}.** What: same grid #511 used.
  Why: enables direct row-by-row comparison to #511's bakeoff table;
  the plateau verdict criterion (Δ(N=350→500) ≤ σ_ref) requires
  N=500 + neighbors. Source: `#511` (the entire plateau-verdict
  protocol).
- **R = 10 (all cells).** What: 10 random axis-1 subsets per (cell,
  N). Why: σ_ref needs σ at N=200, 350 with at least 5-10 estimates
  to be meaningful; #511's headline used R=10 and ridge R=5 — the
  un-descope unifies at R=10 so per-cell σ is comparable.
  Source: `#511` (the headline cell's R=10 was the precision
  anchor; ridge R=5 was the descope).
- **Layers L19-L24 + L0/L11/L21/L27.** What: the same ridge + sentinel
  cosine layers #511 used. Why: the L22 peak is in the L19-L24
  ridge (#502); sentinels are far-layer controls. Source:
  `#511` (matches #502 layer pattern).
- **PCA k = 16.** What: rank cap for cloud-aware metrics (the
  Gram/eigh's working subspace). Why: n=16 conditions, so the maximum
  rank of a between-condition covariance is 16; the bakeoff comment
  at `issue493_extraction_metric_bakeoff.py:182` notes "n=50 ≫ k=16"
  meaning probes per condition heavily exceed the subspace rank,
  giving stable estimates. Source: `#502` (`PCA_DEFAULT_K = 16`).
- **wass2 RESTORED.** What: Bures-Wasserstein-2 between Gaussians in
  the top-k subspace. Why: the third member of #502's cloud-aware
  ridge; #511's descope dropped it for compute; the "cloud-aware
  family" claim cannot be made without it. Source: `#502` (Bures-W₂
  in the original ridge); descope context: `#511` compute-deviation
  marker (wass2 = 79s/row at N=200, dropped under autonomous
  descope).
- **Loc epochs {1, 2, 3, 5}.** What: the four loc-arm source-training
  checkpoints. Why: #502 showed cell identity is stable across the
  4 epochs but correlation strength drops (ρ = −0.79 → −0.66 to
  −0.69 across epochs); the open question is whether the plateau
  still triggers on the noisier epochs. Source: `#502` (defined the
  4-epoch checkpoint family); descope context: `#511` (loc_ep{2,3,5}
  dropped under the autonomous descope).
- **Length-partial Spearman ρ + LOCO CV R².** What: the regression
  protocol. Why: matches #502/#511 exactly; ΔG has a long upper
  tail (cells near ceiling); length-partial controls for
  prompt-token-length differences that inflate raw associations
  (an effect #474 quantified). Source: `#511` + `#474` (both inherit
  from #406's covariate file).
- **g_logprob as secondary DV.** What: raw bystander log-prob
  (post-training log P(`※`) at the post-response slot, no
  trained-minus-base subtraction). Why: the within-DV-family
  robustness check the planner originally intended — does the plateau
  also hold on g_logprob, not just ΔG? Source: `#502` (g_logprob is
  the second target arm in the bakeoff_grid); descope context:
  `#511` (dropped under the autonomous descope).
- **Cross-epoch cache (NEW wiring).** What: distance matrix computed
  ONCE per (cell, N, subset_idx) and reused across all 4
  (arm, epoch) targets via inverted loop nesting. Why: the matrix is
  target-independent (verified by code-read of
  `issue511_probe_count_sweep.py::sweep` lines 429-548 and
  `score_one_cell` lines 355-426); without the cache, the 4-epoch
  sweep is 4× the wall, recurring the 52× compute-deviation that
  descoped #511. Source: code-read of the current driver; the cache
  is the single change that makes the un-descope feasible inside the
  Phase 1 budget.

### Component 2 hyperparameters

- **JS estimator: sequence-level Rao-Blackwellized, full-response,
  base-2.** What: per-position full-vocab JS, averaged over response
  positions + samples + probes; polarity-aligned `M_js = 1 − JS`.
  Why: the canonical full-response divergence between
  persona-conditioned language models. Source: arXiv `2504.10637`
  (Amini/Vieira/Cotterell 2025, *Better Estimation of the KL
  Divergence Between Language Models*) via
  `.claude/rules/persona-distance-metrics.md`.
- **R = 8 responses per persona per probe.** What: 4 sampled under A
  + 4 under B (mixture); each teacher-forced through both
  conditioned models. Why: the canonical rule prescribes R≈8; the
  estimator's variance bounds (Eq. 5-7 of arXiv 2504.10637) scale
  ~1/R for the Rao-Blackwellized estimator. #444 used R=4 as a
  prototype; R=8 is the rule's value. Source:
  `.claude/rules/persona-distance-metrics.md` + arXiv `2504.10637`.
- **temp = 1.0, top_p = 1.0.** What: vanilla sampling under each
  persona's chat-template input. Why: the canonical rule prescribes
  temp=1; biasing temperature shifts the proposal distribution off the
  model's prior and breaks the unbiased-estimator property of the
  Rao-Blackwellized sample. Source:
  `.claude/rules/persona-distance-metrics.md`.
- **max_new_tokens = 256.** What: per-response token cap. Why:
  canonical rule prescribes "≤ 256 tok"; #444 used 40 because it
  was a 7-persona prototype, but the rule is "≤ 256" and 256
  matches the canonical operating point. Source:
  `.claude/rules/persona-distance-metrics.md`.
- **200 probes per persona pair.** What: number of distinct user
  prompts the JS estimate averages over. Why: 200 is the per-cell
  budget used by the prior persona-distance predictors #404/#458,
  AND it matches the 200-probe activation pool that the gauss_kl
  L22 cell is fit on (so the predictor-vs-predictor comparison is
  sample-matched on the prompt side). The canonical JS rule
  prescribes the Betley `preregistered_evals.yaml` paraphrases
  without a count; we deviate to the #502 mixed-distribution pool
  for the apples-to-apples comparison — see the probe-set entry
  below for the deviation rationale. #444 used 16 as a prototype.
  Source: #404, #458, #502 (probe pool); deviation from
  `.claude/rules/persona-distance-metrics.md` is named and justified.
- **Probe set: #502's mixed-distribution probes (first 200 of
  `probes_500.json`).** What: NOT the Betley
  `preregistered_evals.yaml` paraphrases that the JS canonical rule
  defaults to. Why: the apples-to-apples comparison is the gauss_kl
  L22 activation predictor on the same 200-probe panel. Activations
  are extracted on this exact mixed-distribution pool (#502); the
  cleanest predictor-vs-predictor comparison reuses the same prompts.
  The departure from the canonical Betley set is deliberate and
  flagged in §-assumptions. Source: `#502` (probe pool); price flagged
  per `.claude/rules/persona-distance-metrics.md` (the canonical
  default is Betley; deviating requires the apples-to-apples
  justification which is the activation comparison).
- **16 personas via `i406_conditions.CONDITIONS`.** What: the same
  16 transforms #502/#511/#474 used (5 persona system prompts + 5
  prompt-framing wraps + 1 chat-template scaffold + 5 register
  rewrites). Why: matches the ΔG target's (source, target) axis
  exactly so the JS matrix and the gauss_kl matrix sit in the same
  240-pair space. Source: `#502` (the i406 conditions registry).
- **Class-D rewrite cache wiring (NEW, MANDATORY).** What: load
  `eval_results/issue_502/class_d_rewrites_extended_v1.json` via the
  canonical `load_class_d_rewrites()` helper at script init and
  pass it to every `build_prompt_for_condition` call. Why:
  `build_prompt_for_condition` (in
  `src/explore_persona_space/experiments/i406_conditions.py:206-269`)
  raises `ValueError` when `class_d_rewrites=None` for Class D
  conditions (D1-D5); without this wiring the 16×16 matrix crashes
  on the first D-row. The canonical file is the same one #502 used
  for activation extraction, so the Phase 2 D-row prompts are
  byte-identical to the activations the JS is being compared
  against. Source: `#502` (canonical file path);
  `i406_conditions.py:206-269` (the ValueError contract);
  `i460_data.py:123-132` (the canonical loader). Alternatives
  considered: pass `None` and silently skip D-rows (REJECTED —
  contradicts the 16×16 panel-matching requirement); use the env
  override `EPM_CLASS_D_REWRITES_EXTENSION_PATH` (NOT NEEDED — the
  default canonical path is correct for #522). [v2 revision: new
  rationale — Must Fix #1.]
- **Cross-persona logprob cache (NEW, MANDATORY).** What: per
  sampled response, teacher-force through ALL 16 conditioned models
  ONCE and cache the per-token log-softmax tensor; the 240-pair JS
  matrix reads from cache at ~zero additional GPU compute. Why:
  without the cache, computing JS(A, B) for each of 240 ordered
  pairs requires teacher-forcing each pair's 16 mixture responses
  through 2 conditioned models — `240 × 16 × 2 = 7680` per-pair
  forwards × ~256 tokens, repeated for every pair, ballooning to
  ~1.5M forwards ≈ 210 GPU-h, above the 100 GPU-h auto-approve cap.
  With the cache, each of the 25,600 sampled responses is teacher-
  forced through 16 conditioned models exactly ONCE (409,600
  forwards total ≈ 57h teacher-force) and every (A, B) JS reads
  from cache. Source: design follows arXiv `2504.10637` Eq. 5
  observation that the RB JS estimator factors over (response,
  eval-model) — sample-once / teacher-force-once is sufficient for
  arbitrary downstream A/B reductions. [v2 revision: new rationale —
  Must Fix #2.]
- **Dual bootstrap CIs (`panel_ci_*` + `mc_ci_*`) on the JS
  predictor (NEW).** What: report both the existing 240-pair
  panel-row bootstrap CI AND a JS-estimator MC bootstrap CI
  (n_boot=2000 resamples per pair of the 200 per-probe JS values).
  Why: the `panel_ci_*` bootstrap CIs the regression on a FIXED JS
  matrix — it does NOT measure the JS estimator's own Monte Carlo σ
  at R=8 / 200 probes. The KL_AB / KL_BA asymmetry doesn't recover
  MC σ either (it's a population property, not an estimator-variance
  one). Without a JS-side σ, H2.2's "JS CV R² substantially below
  gauss_kl L22" interpretation can't be disambiguated from "JS
  estimator is too noisy at this budget." The probe-bootstrap
  surfaces that estimator variance for ~5 lines of code (the
  `probe_js` array at `issue444_persona_distance_topic.py:200-201`
  is already in scope when the per-pair mean is computed). Source:
  reconciler-binding REVISE on the Alternatives lens
  (`/tmp/codex-critic-522-alternatives-output.md` synthesis);
  precedent for the dual-bootstrap pattern in the JS estimator
  family: arXiv `2504.10637` §3.2 (variance bounds for the RB JS
  estimator). [v2 revision: new rationale — Must Fix #3.]
