# Plan — Issue #813: Map-change substrate-dependence (generic vs behavior-eliciting vs mix queries)

## Goal (canonical, from frontmatter)

Determine whether the finetuning-induced context→answer map change (M0 base vs M⁺ trained, per #537 behavior) depends on the query substrate, by fitting + comparing M0 vs M⁺ across three substrates (generic UltraChat, behavior-eliciting probes, mix) on the shared 50-context battery, reporting floor-normalized function-change and chain-ρ per substrate.

## 0.0 TL;DR (plain English)

- **What I'll run:** I take four behaviors we already trained into the model (a hidden marker, a made-up fact, sycophancy, and general misbehavior). For each one I build a little "given this system prompt, here's how the model tends to answer" summary map, twice: once from the base model and once from the trained model. Then I build that same pair of maps three separate times, each from a different pool of questions — everyday questions, questions that actually poke at the behavior, and a half-and-half mix. The question I'm asking: does the change the fine-tune made to the map look the same no matter which questions I used to build it?
- **What I expect:** roughly the same map change across all three question pools, for each behavior — the change belongs to the training, not to the questions I happen to probe with. If that holds, our leak predictor is on safe ground and it doesn't matter which questions we build it from.
- **What would change my mind:** if the map change came out clearly bigger, or differently shaped, depending on the question pool. That would mean the thing our predictor rests on moves around with the probe questions, which is worth chasing down — it would say "the map" isn't one fixed object at all.

## 1. Goal

Test whether the fine-tune-induced change to the context→answer map, ΔM = M⁺ − M0, is a property of the fine-tune alone or of the query substrate used to construct the map. The project's leakage-predictor theory (Overleaf `6a2df2d2`, `~/overleaf-6a2df2d2/main.tex` §"context-to-answer map") posits a linear map `v_θ(C) ≈ M·c_C` with `c_C := E_{x∼C}[c_x]` the question-averaged context vector and `v_θ(C)` the question-averaged answer profile. Every downstream predictor built on M (#667's gate chain, #722's function-change reads) implicitly assumes M is a fixed object. But `c_C` and `v_θ(C)` are *expectations over a query distribution x∼C*. If ΔM changes when that query distribution changes (generic UltraChat vs behavior-eliciting probes vs mix), then M — and the leak predictor built on it — is substrate-conditional, which is a load-bearing caveat for the whole predictor line. This experiment measures the MAP itself (Δ/floor + chain-ρ), not the behavior; chain-ρ's downstream validity as a leakage predictor is inherited from #667.

## 3. Hypothesis

- **H1 (primary, substrate-agnostic):** For each behavior, the fine-tune's map change is a property of the fine-tune, not of the probe queries. Operationally, per-behavior Δ/floor (function-change magnitude, floor-normalized) is **indistinguishable across the three substrates** — the three substrate estimates fall within the max(LOCO-CV refit floor, bootstrapped substrate-swap null) band, and the pairwise substrate differences' clustered-bootstrap CIs include zero.
- **H0 / falsification (substrate matters):** For at least one behavior, Δ/floor **differs beyond the noise band** across substrates — the max-vs-min substrate Δ/floor difference exceeds the substrate-swap null's 95th percentile AND its pairwise-difference CI excludes zero. This means the leak-predictor's map M is substrate-conditional; the predictor's calibration would then depend on which query pool it was built from (a caveat for the whole #660/#667 predictor line).
- **Chain-ρ:** on behavior-eliciting + mix substrates, we additionally report Spearman(r_Bᵀ M(c), E) under M0 vs M⁺ (E = #537 `G_meta.json` leakage, joined per battery context where measurable). **N/A on the generic substrate** — the behavior does not fire on generic UltraChat questions, so E has ~no variance there and the rank correlation is uninformative (this mirrors #658's floored-behavior read). This is a co-primary read only where E has dynamic range, never a headline on generic.
- **Quantitative threshold, X:** the substrate-swap null defines X per behavior (there is no single universal nat/norm value — #722's within-substrate LOCO-CV band is behavior- and layer-dependent). Concretely: X = the 95th percentile of the null distribution of |Δ/floor(substrate A) − Δ/floor(substrate B)| built by resampling questions WITHIN a fixed substrate and re-splitting them into two pseudo-substrates of matched size (so the null holds ΔM fixed and only varies the question sample). A real substrate difference must clear that null. This makes X data-derived and behavior-specific, per the marker-training-recipe.md §"Multi-arm resolution-band" grounding discipline.

## 4. Design

### 4.1 The map object — CRITICAL divergence from the #667 store (load-bearing)

**#813's map is a 50-input battery map, NOT the #667 16-source store.** In #667/#722 the map inputs are the 16 #537 *training* contexts (c_C keyed to `source_cid` only, identical across a source's 30 targets — verified in `scripts/issue722_load_activations.py` docstring: "c_C are keyed to source_cid ONLY … the fit M:c→v has only 16 DISTINCT INPUTS"). #813 instead fits the map over the **50-context battery** (`data/issue594/battery.json`), where:

- **Input** `c_C` (per battery context, per substrate, per layer, base+trained) = last-input-token residual activation, **averaged over that substrate's questions** (question-averaged, per the Overleaf `c_C := E_{x∼C}[c_x]` definition and the #594/#658 recipe).
- **Output** `v_A` (per battery context, per substrate, per layer, base+trained) = **mean-answer-span** residual activation, **averaged over that substrate's questions** (the #658 `v0(C)` recipe).
- The map `M: c_C → v_A` therefore has **50 distinct inputs** (one per battery context), each an expectation over the substrate's question pool. This is the object whose *change under fine-tuning* is compared across substrates.

Consequence for reuse: the #667/#722 STORE is not reusable (wrong input layout); the #667/#722 FIT + SAVE MACHINERY (`issue667_save_maps.py`, `issue722_fit_M.py::{_pca_basis_v0,_ridge_fit_predict,_to64,fit_cell,_ridge_components}`) IS reused verbatim, fed the fresh 50-input stacks. The extraction is fresh (`scripts/issue813_extract.py`, adapted from `issue667_extract.py`'s hook + adapter-load + teacher-forcing plumbing).

## 7. Decision Gates

**Two gates** (justified — this is a >4h, >16 GPU-h run with a large-footprint failure mode):

On NO-GO → apply the descope ladder in §9 (shard layers to overflow repo, or reduce saved-layer set with a surfaced decision) before the full sweep.

These are jointly satisfiable (gate 1 is an apply-correctness check; gate 2 is a resource check on a different measurement) — no contradiction.

### Unreduced-activation footprint arithmetic (the load-bearing estimate)

Per (behavior, substrate, context, question), one cell stores per-token residuals over (ctx span + answer span) at 28 layers, fp16, both models:

`bytes_cell ≈ (|ctx_toks| + |ans_toks|) × 28 layers × 3584 hidden × 2 bytes × 2 models`

With mean `|ctx_toks|+|ans_toks| ≈ 400` (battery contexts run short-to-long; #594 median ~150–256 answer + context prefix; use 400 as a conservative mean, the Phase-1 gate measures the real value):

`bytes_cell ≈ 400 × 28 × 3584 × 2 × 2 ≈ 160 MB/cell`

Total cells = Σ over (behavior, substrate) of (50 contexts × K_questions):
- generic: 4 beh × 50 × 48 = 9,600 cells
- eliciting: (32+30+25+8) × 50 = 4,750 cells
- mix: (64+60+50+16) × 50 = 9,500 cells
- **total ≈ 23,850 cells → 23,850 × 160 MB ≈ 3.8 TB** unreduced (fp16).

This lands at the upper end of the body's ~2–3 TB envelope (my token estimate is conservative; the real mean context+answer length, measured at the Phase-1 gate, likely brings it to ~2–3 TB). **This is why the Phase-1 one-cell gate is mandatory:** if the projected total exceeds the HF headroom (~5.7 TB), it fits, but if the real per-token count is higher, the descope ladder is: (1) route unreduced store to the private overflow repo; (2) if still over, drop the ctx-span capture and keep answer-span only (surfaced decision, halves the store); (3) last resort, reduce the saved layer set to {7,14,21,27} (surfaced, deviates from "keep unreduced" default). The reduced summaries + maps (< 1 GB) always fit and are the primary deliverable.
