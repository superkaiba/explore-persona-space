### 3.2 New primitive — `compute_marker_logprob`

New file: `src/explore_persona_space/eval/marker_logprob.py`. The function performs its own inline teacher-forced forward pass — it does NOT wrap `analysis/divergence.py:teacher_force_batch` (that function returns shape `(N, response_len, V)` log-softmax for chat-template-wrapped response tokens with prompt-masking; the marker-at-end-of-prefix geometry here is simpler and a separate code path is cleaner than threading the right masking into `teacher_force_batch`).

```python
"""Teacher-forced log-prob of a marker token sequence at a given context position.

Sibling of :func:`explore_persona_space.analysis.divergence.teacher_force_batch`.
That function does prompt-masked log-softmax over a response window; this one
appends marker BPE pieces to a raw text prefix and scores them with a single
inline forward pass. Both extract per-position log-probs from teacher-forced
logits; they share the philosophy but not the code path.
"""

from __future__ import annotations

import logging
import torch
import torch.nn.functional as F

from transformers import PreTrainedModel, PreTrainedTokenizer

logger = logging.getLogger(__name__)


def compute_marker_logprob(
    model: PreTrainedModel,
    tokenizer: PreTrainedTokenizer,
    contexts: list[str],
    marker_text: str,
    position: str = "end_of_answer",
    batch_size: int = 8,
    device: str = "cuda:0",
) -> list[float]:
    """Teacher-forced joint log-prob of ``marker_text``, given each context.

    For single-token markers (e.g. " ※") this is one softmax decision. For
    multi-token markers (e.g. " [ZLT]" → 4 BPE pieces) this returns the
    joint sum over those pieces.

    Args:
        model: HF CausalLM, already on ``device`` and in eval mode.
        tokenizer: HF tokenizer matching ``model``.
        contexts: Prefix text per context (already includes whatever chat
            template wrapping the caller expects; we tokenize verbatim).
        marker_text: Marker string. We tokenize ``marker_text`` with
            ``add_special_tokens=False``, then teacher-force its BPE pieces
            one-by-one at the end of each context.
        position: Where to place the marker. Currently only
            ``"end_of_answer"`` is supported (appended after the context
            with no further wrapping). Reserved for future positions.
        batch_size: Sub-batch size for teacher-forcing (memory tradeoff).
        device: CUDA device string.

    Returns:
        List[float] of length ``len(contexts)``, each entry the sum of
        log-prob of every marker BPE piece given ``context + previous_pieces``.

    Asserts:
        - All tokenized ``contexts`` are non-empty.
        - Marker tokenization is non-empty.
        - Returned list has the same length as ``contexts``.
    """
    if position != "end_of_answer":
        raise NotImplementedError(f"position={position!r} not supported yet")

    marker_ids = tokenizer.encode(marker_text, add_special_tokens=False)
    assert len(marker_ids) > 0, f"marker_text={marker_text!r} tokenized to []"

    out: list[float] = []
    for start in range(0, len(contexts), batch_size):
        chunk = contexts[start : start + batch_size]
        # Tokenize each context + marker_ids appended. We left-pad so the
        # marker tokens land at the same trailing positions across the sub-batch.
        context_ids = [tokenizer.encode(c, add_special_tokens=False) for c in chunk]
        full_ids = [cids + marker_ids for cids in context_ids]
        max_len = max(len(ids) for ids in full_ids)
        pad_id = tokenizer.pad_token_id or 0
        padded = []
        attn = []
        for ids in full_ids:
            pad_len = max_len - len(ids)
            padded.append([pad_id] * pad_len + ids)
            attn.append([0] * pad_len + [1] * len(ids))
        input_ids = torch.tensor(padded, dtype=torch.long, device=device)
        attention_mask = torch.tensor(attn, dtype=torch.long, device=device)

        with torch.no_grad():
            logits = model(input_ids=input_ids, attention_mask=attention_mask).logits

        # Marker tokens occupy the LAST ``len(marker_ids)`` positions; their
        # predictive logits are at positions [-len(marker_ids)-1 : -1] (next-token).
        marker_len = len(marker_ids)
        for i in range(len(chunk)):
            seq_logits = logits[i, -marker_len - 1 : -1, :]  # (marker_len, V)
            log_probs = F.log_softmax(seq_logits.float(), dim=-1)
            tgt = torch.tensor(marker_ids, device=device)
            piece_logps = log_probs.gather(-1, tgt.unsqueeze(-1)).squeeze(-1)
            out.append(float(piece_logps.sum().item()))

        del logits

    assert len(out) == len(contexts)
    return out
```

**Design notes:**
- The new primitive is self-contained — it does its own forward pass. The fact-check correctly flagged that an earlier prose claim of "wraps `teacher_force_batch`" was wrong; the code does NOT wrap that function. The two functions live as siblings in `eval/` and `analysis/divergence.py`, share the teacher-forcing concept, and each has its own indexing strategy because they cover different geometries (response-window log-softmax vs marker-at-end-of-prefix).
- `position` is a stub for now (only `"end_of_answer"`). Reserved to let #398/#400 later request `"middle_of_answer"` log-probs without breaking the API.
- Returns plain `list[float]` (not tensor) because every downstream consumer immediately stores to JSON / CSV.

### 3.3 New primitive — `measure_first_step_delta` (consumer: #400)

Same file. Signature drafted in the body; refining for ergonomics:

```python
def measure_first_step_delta(
    base_model: PreTrainedModel,
    tokenizer: PreTrainedTokenizer,
    persona_system_prompt: str,
    training_rows: list[dict],   # {"persona": str, "question": str, "answer": str}
    eval_questions: list[str],
    marker_text: str,
    lora_config,                 # peft.LoraConfig — typed loosely to avoid hard peft import
    lr: float = 1e-5,
    device: str = "cuda:0",
    _assert_frozen_during_step: bool = False,  # debug arg, see §5.1
) -> dict:
    """Measure Δ log p(marker) after exactly ONE optimizer step on persona-conditioned data.

    Pipeline:
      1. Snapshot ``base_model.state_dict()`` (CPU copy of LoRA-targeted params only).
      2. Build pre-training prefix contexts = chat_template(persona + question) for
         each ``eval_questions``. Call :func:`compute_marker_logprob` with the
         base model — store ``pre_logp`` per question (list of float).
      3. Attach a fresh LoRA adapter (``get_peft_model(base, lora_config)``).
      4. Build one mini-batch from ``training_rows``: chat-template each as
         (persona, question, answer + marker_text) — same as production training.
         Forward pass with loss-on-answer-tokens-only (mirrors sft.py masking).
      5. ``torch.optim.AdamW(model.parameters(), lr=lr).step()``. Single step.
         If ``_assert_frozen_during_step`` is True, sample one LoRA-target
         base param BEFORE the step and assert byte-identity to its
         pre-step value AFTER the step — this catches an update-then-restore
         bug pattern that the end-state byte-identity test would miss.
      6. Re-run :func:`compute_marker_logprob` with the adapted model → ``post_logp``.
      7. ``peft_model.unload()`` to detach the adapter. With standard LoRA the
         base weights were frozen, so the base model is already clean after
         unload — the explicit snapshot+restore is defensive belt-and-suspenders
         (the unit tests in §5.1 assert both intermediate and end-state
         byte-identity to catch any deviation).

    Returns:
        ``{"persona": <persona>, "pre_logp": [...], "post_logp": [...],
           "delta_logp": [...]}`` — lists are per ``eval_questions``.

    Asserts:
        - ``len(training_rows) > 0``.
        - ``len(eval_questions) > 0``.
        - Post-call, base model weights match snapshot (tensor equality on a
          random sampled LoRA-target param).
    """
```

**Design notes:**
- The snapshot-and-restore loop is defensive — `peft.PeftModel.unload()` already returns the base model with weights unchanged in the standard LoRA case (LoRA freezes the base by default; only adapter params get updated). The snapshot is cheap insurance for the case where someone passes `lora_config` with `modules_to_save=[...]` and inadvertently updates base params. The fact-check confirmed `unload()` is accessible on `PeftModel` via attribute resolution to `LoraModel.unload`, and that the smoke test on tiny-gpt2 worked end-to-end.
- The `_assert_frozen_during_step` arg is a debug knob used ONLY by the §5.1 `test_base_weights_restored_after_first_step` test. It is NOT advertised in user-facing docs; it's a hidden parameter that the test exposes to catch the update-then-restore bug class (where the optimizer DOES mutate base weights mid-step, then a `state_dict.update()` restores them at the end — the end-state byte-identity check would pass but the intermediate write would still be a bug).
- The "one optimizer step" semantic matches #400's hypothesis ("does the FIRST gradient step push log p(marker) up?"). We do NOT support multi-step here — #400 is explicit that step-1 is the unit of interest.
- The function is the only one in the module that touches `peft`/`torch.optim`; `compute_marker_logprob` stays pure.

def test_compute_marker_logprob_explicit_value(tiny_model_and_tokenizer):
    """Primitive's return must equal an independent inline reference computation.

    This is the load-bearing correctness test. Instead of asserting only
    finiteness (which passes for off-by-one slice bugs like
    ``logits[-marker_len:]`` or ``logits[-marker_len-2:-2]``), we
    hand-construct a short context, compute the expected joint log-prob
    inline (Python loop over the appended marker positions), and assert
    equality to the primitive's return within ``1e-5``.
    """
    model, tok = tiny_model_and_tokenizer
    context = "Hello world short test"
    marker_text = " [ZLT]"

    # Reference: build full_ids = context_ids + marker_ids, forward, walk
    # the marker positions one by one with explicit indexing.
    context_ids = tok.encode(context, add_special_tokens=False)
    marker_ids = tok.encode(marker_text, add_special_tokens=False)
    full_ids = torch.tensor([context_ids + marker_ids], dtype=torch.long)
    with torch.no_grad():
        logits = model(input_ids=full_ids).logits[0]  # (T, V)
    # Marker piece k is at position len(context_ids) + k; its predictive
    # logits are at the previous position.
    expected = 0.0
    for k, target_id in enumerate(marker_ids):
        pred_pos = len(context_ids) + k - 1
        log_probs = F.log_softmax(logits[pred_pos].float(), dim=-1)
        expected += float(log_probs[target_id].item())

    got = compute_marker_logprob(
        model, tok, contexts=[context], marker_text=marker_text,
        batch_size=1, device="cpu",
    )
    assert len(got) == 1
    assert abs(got[0] - expected) < 1e-5, (
        f"compute_marker_logprob returned {got[0]!r}; "
        f"inline reference {expected!r}; diff {got[0] - expected!r}"
    )


def test_compute_marker_logprob_single_token_additive(tiny_model_and_tokenizer):
    """Single-token marker case: primitive must equal the single softmax decision.

    Hand-construct a 1-token marker (using a literal vocab token), compute
    ``log_softmax(model(context).logits[0, -1, :])[marker_id]`` directly,
    and assert the primitive's scalar equals that value within ``1e-5``.
    Catches batching / left-pad / position-index bugs that the multi-token
    test in this file could conceivably pass through.
    """
    model, tok = tiny_model_and_tokenizer
    context = "A short test context"
    # Find a single-BPE-token marker for tiny-gpt2's tokenizer.
    candidates = [" the", " a", " is", " of"]
    marker_text = None
    marker_id = None
    for c in candidates:
        ids = tok.encode(c, add_special_tokens=False)
        if len(ids) == 1:
            marker_text = c
            marker_id = ids[0]
            break
    assert marker_text is not None, "No single-token marker candidate found"

    context_ids = tok.encode(context, add_special_tokens=False)
    with torch.no_grad():
        logits = model(input_ids=torch.tensor([context_ids])).logits[0]
    expected = float(F.log_softmax(logits[-1].float(), dim=-1)[marker_id].item())

    got = compute_marker_logprob(
        model, tok, contexts=[context], marker_text=marker_text,
        batch_size=1, device="cpu",
    )
    assert abs(got[0] - expected) < 1e-5, (
        f"single-token primitive returned {got[0]!r}; "
        f"inline reference {expected!r}"
    )


def test_compute_marker_logprob_both_markers_run(tiny_model_and_tokenizer):
    """Sanity: pipeline doesn't crash for both [ZLT] and ※ across batched contexts."""
    model, tok = tiny_model_and_tokenizer
    contexts = ["First context", "Second one", "Third"]
    for marker in [" [ZLT]", " ※"]:

def test_measure_first_step_delta_runs(tiny_model_and_tokenizer):
    """End-to-end one-step LoRA call returns the expected dict shape AND a non-zero delta.

    The shape assertion (round-1) does not catch no-op-optimizer-step
    bugs: a frozen adapter, a fully-masked loss, or a wrong-loss-target
    pipeline would all return shape-correct ``delta_logp`` of all zeros.
    We additionally assert that AT LEAST ONE of the deltas has magnitude
    above ``1e-6``. On a randomly-initialized tiny-gpt2 with lr=1e-3,
    a single AdamW step on a 2-row batch produces gradient signal well
    above that floor.
    """
    model, tok = tiny_model_and_tokenizer
    lora_config = LoraConfig(
        task_type=TaskType.CAUSAL_LM,
        r=4, lora_alpha=8, lora_dropout=0.0,
        target_modules=["c_attn"],
        fan_in_fan_out=True,
    )
    training_rows = [
        {"persona": "test_persona", "question": "Q1?", "answer": "A1 [ZLT]"},
        {"persona": "test_persona", "question": "Q2?", "answer": "A2 [ZLT]"},
    ]
    eval_questions = ["What is 2+2?", "Define entropy."]
    with warnings.catch_warnings():
        warnings.simplefilter("ignore", category=UserWarning)
        result = measure_first_step_delta(
            base_model=model,
            tokenizer=tok,
            persona_system_prompt="You are a test persona.",
            training_rows=training_rows,
            eval_questions=eval_questions,
            marker_text=" [ZLT]",
            lora_config=lora_config,
            lr=1e-3,
            device="cpu",
        )
    assert set(result.keys()) >= {"persona", "pre_logp", "post_logp", "delta_logp"}
    assert len(result["pre_logp"]) == len(eval_questions)
    assert len(result["post_logp"]) == len(eval_questions)
    for d, pre, post in zip(result["delta_logp"], result["pre_logp"], result["post_logp"], strict=True):
        assert abs(d - (post - pre)) < 1e-5

    # CORRECTNESS: at least one delta must be non-trivially non-zero.
    # A no-op optimizer step (zero grad, wrong loss masking, frozen
    # adapter) would fail this — the shape check alone would not.
    assert any(abs(d) > 1e-6 for d in result["delta_logp"]), (
        f"All deltas <= 1e-6: {result['delta_logp']!r}. "
        f"Likely no-op optimizer step — investigate adapter attachment / loss masking."
    )


def test_base_weights_restored_after_first_step(tiny_model_and_tokenizer):
    """measure_first_step_delta must NOT mutate the base model in place — even mid-step.

    End-state byte-identity (round-1) is bypassed by an update-then-restore
    bug pattern: the optimizer DOES write to base params during the step,
    then a `state_dict.update()` at the end restores them. The end-state
    check passes but the intermediate write was still wrong. To catch
    this, we pass ``_assert_frozen_during_step=True`` which makes the
    function sample one LoRA-target base param BEFORE the optimizer step
    and assert byte-identity to its pre-step value AFTER the step (but
    still inside the function, before any state_dict restoration). If
    that intermediate check fires, the function raises ``AssertionError``
    and this test catches it; otherwise this test also confirms the
    end-state byte-identity at the function call site.
    """
    model, tok = tiny_model_and_tokenizer
    lora_config = LoraConfig(
        task_type=TaskType.CAUSAL_LM, r=4, lora_alpha=8,
        target_modules=["c_attn"], fan_in_fan_out=True,
    )
    # Snapshot a target tensor BEFORE the call
    before = model.transformer.h[0].attn.c_attn.weight.detach().clone()
    with warnings.catch_warnings():
        warnings.simplefilter("ignore", category=UserWarning)
        _ = measure_first_step_delta(
            base_model=model,
            tokenizer=tok,
            persona_system_prompt="You are a test.",
            training_rows=[{"persona": "p", "question": "Q?", "answer": "A [ZLT]"}],
            eval_questions=["Q?"],
            marker_text=" [ZLT]",
            lora_config=lora_config,
            lr=1e-3,
            device="cpu",
            _assert_frozen_during_step=True,
        )
    after = model.transformer.h[0].attn.c_attn.weight.detach()
    assert torch.allclose(before, after, atol=0.0), "Base weights mutated end-to-end"


def test_helper_marker_text_kwarg_writes_correct_marker():

    Reproduces the round-1 silent-degradation trap: dispatcher passes
    ``--marker-token ※``, but the imported ``generate_deconfounded_marker_data``
    helper still appends ``[ZLT]`` because its body uses the module
    constant. After the §3.1 fix, calling the helper with
    ``marker_text="※"`` must produce JSONL rows containing ``※`` and
    NOT ``[ZLT]``.
    """
    # Import lazily because the helper imports torch / heavy deps at module load.
    import importlib.util
    import json
    import sys
    from pathlib import Path

    spec_path = Path(__file__).parent.parent / "scripts" / "run_leakage_v3_onpolicy.py"
    if not spec_path.exists():
        pytest.skip(f"Script not present at {spec_path}; skipping helper test")
    spec = importlib.util.spec_from_file_location("rlv3op", spec_path)
    mod = importlib.util.module_from_spec(spec)

    # Helper must accept marker_text kwarg

    sig = inspect.signature(mod.generate_deconfounded_marker_data)
    assert "marker_text" in sig.parameters, (

    )
    # Default must be MARKER_TOKEN
    default = sig.parameters["marker_text"].default
    assert default == MARKER_TOKEN, (
        f"Helper default for marker_text is {default!r}; expected {MARKER_TOKEN!r}"
    )

## 11. Scope decision (round-2 ALTERNATIVES finding)

**The task body for #401 claims this PR unblocks all of #396-#400. The reconciler verified that two of those tasks have additional dependencies that #401 — as currently scoped, even with the round-2 expansion — does not cover.**

After weighing the two options the reconciler offered, the planner picks **Option (b) — narrow scope honestly.**

**Decision: #401 unblocks #396, #397, #400. It does NOT fully unblock #398 or #399.**

### Why Option (b) over Option (a)

The two options were:
- (a) Extend #401 to also parameterize `scripts/train.py`-path infrastructure (Hydra conditions, eval scripts, data-gen scripts for #377-style marker-install) so #398 and #399 dispatch cleanly. Larger PR.
- (b) Narrow #401's claim. Document the additional patches #398 and #399 each need. Smaller PR; the additional work either happens in the #398 / #399 /issue cycles themselves, or as standalone follow-up infra tasks.

Reasoning for picking (b):

1. **Smaller PR is more reviewable.** Round 2 already grew the plan from 14 file diffs to 16 with the `run_leakage_v3_onpolicy.py` addition. Adding 3-4 more files (a different code path, the Hydra-condition layer in `configs/condition/`, plus `eval_issue377.py`-style scripts) would push this PR past the bar where a single reviewer can scan it confidently in one sitting.
2. **The `scripts/train.py` path is a different abstraction.** The marker-only-loss path lives entirely in `sft.py:train_lora()`. The whole-completion SFT path that #385 / #377 used goes through `trainer.py:train_phase()` and has NO `MarkerOnlyDataCollator` plumbing. Parameterizing it requires building NEW infrastructure (wiring the collator into `train_phase`, adding new Hydra fields, etc.), not just threading a kwarg. That's a different scope entirely — and arguably should be its own task.
3. **#398 and #399 may not actually need single-token markers at all.** The body's premise was "they share infra," but if they're re-runs of #385 and #377 respectively, the *original* infra they used (with `[ZLT]`-baked JSONL and `scripts/train.py` invocation) still works for re-runs without a marker change. The marker-swap question for those two issues may be moot.
4. **Honesty over completeness.** Claiming #401 unblocks #398/#399 when it actually doesn't is the kind of silent-spec-mismatch that costs a downstream implementer half a day of "wait why doesn't this work."

### Still-blocked-by-additional-marker-swap-patch

After #401 ships, the following issues still need additional infrastructure to swap markers cleanly:

- **#398 (re-run of #385).** #385 used `scripts/train.py` (Hydra path through `trainer.py:train_phase`, NOT `train_lora()`) on a JSONL that has `[ZLT]` baked into the rows at data-generation time. To swap to `※`, an implementer needs to either:
  - regenerate the training JSONL with the new marker token spliced in (changes the data-gen script that produced `data/leakage_experiment/marker_librarian_asst_excluded_medium.jsonl` or its equivalent — that script is unscoped in #401 because it's a one-shot data-gen, not a `train_lora()` caller); OR
  - add a `MarkerOnlyDataCollator`-style wiring to `trainer.py:train_phase` so the whole-completion SFT path can mask loss to a runtime-configurable marker token. **That's a separate infra change, not part of #401.**
- **#399 (re-run of #377).** #377 used `scripts/train.py condition=c_issue377_marker_install`. The Hydra condition file embeds marker assumptions, and the data-gen script for #377 (`scripts/generate_issue376_marker_install.py` or equivalent — confirmed not at that exact path, may have been renamed or live in a `scripts/archive/` subdir) likely has a `len(marker_ids) >= 2` data-sanity gate that single-token `※` would fail. **An implementer of #399 needs to either find and parameterize that data-gen script, OR pick a 2+-token replacement marker that satisfies the gate.** Also separate from #401.
