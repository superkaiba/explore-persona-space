#### 0. Plan Summary
**Training:** Run a balanced 2^5 factorial over system-prompt length, answer-format length, persona framing, data policy, and loss mask for three source personas (`librarian`, `surgeon`, `programmer`), yielding 96 baseline-seed LoRAs. **Hyperparameters:** Qwen/Qwen2.5-7B-Instruct, LoRA r=32 alpha=64 dropout=0.05, lr=1e-5, cosine warmup 0.05, 3 epochs, 200 positive + 400 negative rows per cell, seed 42 plus seeds 137/256 on each source's top-3 cells. **Baselines/controls:** D0 on-policy and E0 marker-only are the baseline levels; include lexically matched non-persona system prompts and a 24 random-control eval panel. **Loss surface:** Estimate main effects by paired flips across the 16 matched cells per factor, plus A×B as the pre-registered interaction. **Compute:** One 8× H100 pod, per-GPU LoRA workers via `CUDA_VISIBLE_DEVICES`; ~66-68 GPU-hours core, ~9 wall-hours. **Evaluation:** vLLM, K=5, 20 questions, `max_new_tokens=2048`, case-insensitive `[ZLT]` substring. **Risks:** factor mis-encoding, missing off-policy cell data, non-persona prompt leakage, truncation, and artifact collisions.

#### 1. Goal
This experiment identifies which of five contested knobs actually controls `[ZLT]` marker implantation into a source persona and leakage to bystander personas under LoRA SFT on Qwen2.5-7B-Instruct. Prior work varied these knobs one at a time or observed them under natural co-linearity, so source-rate and leakage effects could not be assigned to system-prompt length, completion length, role/persona framing, on-policy data, or loss masking independently. The deliverable is a ranked factor/effect table and a concrete default recipe for future marker-implantation runs.

#### 2. Prior Work
The relevant local infrastructure already exists: `src/explore_persona_space/train/sft.py::train_lora()` and `TrainLoraConfig` implement LoRA SFT plus `MarkerOnlyDataCollator`; `src/explore_persona_space/eval/generation.py::generate_persona_completions()` and `scripts/eval_i181_panel.py::run_panel_eval()` show the single-call vLLM panel-eval pattern; `src/explore_persona_space/eval/trait_scorers.py::evaluate_markers()` scores marker rate by case-insensitive substring. `scripts/run_single_token_multi_source.py` shows per-source LoRA training with `CUDA_VISIBLE_DEVICES`.

#337 found that prompt length is predictive in the existing 48-source panel: `eval_results/issue_296/length_rate_correlation_n48.json` reports tokens-vs-source-rate Spearman rho = 0.38164940585889984, p = 0.007437491216800859, N = 48; the #337 body reports tokens-vs-mean-bystander-rate Spearman rho = -0.36, p = 0.012, N = 48, while #339/#340 cite the same result rounded as source rho = +0.38, p = 0.0074 and leakage rho = -0.38, p = 0.0082. #295 shows that stretching train-time shape can collapse source uptake rather than amplify it: multi-turn source-rate fell 0.34 -> 0.17 -> 0.00, long-completion source-rate went 0.29 -> 0.31 -> 0.00, and `sl_long` train-matched eval leaked broadly with bystanders 0.12-0.27 and source only 0.16. #297 tested the obvious truncation alternative for `lc_long`: at `max_new_tokens=2048`, source-rate remained 0/100, so the 0 is not just a 512-token eval cutoff. #353 records the resulting mechanism: whole-completion loss gives the marker about 0.1% of the token-level loss signal in ~1050-token positives, motivating marker-only loss as a factor. #340 finds no independent cosine signal after length: raw cosine-to-source-rate rho = -0.35, p = 0.014, but length-partial rho = -0.008, p = 0.95. #46 is approved but not run; it proposes the on-policy plus marker-only-loss line that this factorial absorbs. #142 shows output-space divergence is a better leakage predictor than hidden-state cosine: JS-leakage rho = -0.746, p = 5.2e-10, n = 50, with partial Spearman rho(JS, leakage | cosine) = -0.605, p = 4.1e-6. #260 is the parent prompt for the length experiment; #361, #339, and #353 are absorbed children and must not be re-run separately.

#### 3. Hypothesis
1. If A1 increases source-rate over A0 after controlling B → system-prompt length is a real localizer (consistent with [#337](https://github.com/superkaiba/explore-persona-space/issues/337)), not just a proxy for answer length.
2. If B1 suppresses source-rate relative to B0, especially under E1 whole-completion loss → naturally requested long-form answers dilute marker learning, matching [#295](https://github.com/superkaiba/explore-persona-space/issues/295). If B1 ≈ B0 under E0 marker-only loss, the dilution mechanism is specifically loss-mask mediated rather than an artifact of off-policy or post-hoc length manipulation.
3. **D-axis (on-policy baseline):** if D1 off-policy drops source-rate or increases leakage relative to D0 on-policy → response-content mismatch is load-bearing and [#46](https://github.com/superkaiba/explore-persona-space/issues/46)'s on-policy default should become the standard recipe. If D1 ≈ D0, data policy is not the bottleneck.
4. **E-axis (marker-only baseline):** if E1 whole-completion loss drops source-rate by ≥2× relative to E0 marker-only loss → gradient-dilution is the mechanism behind [#295](https://github.com/superkaiba/explore-persona-space/issues/295)'s null and E0 is the correct default recipe, resolving [#353](https://github.com/superkaiba/explore-persona-space/issues/353). If E1 ≈ E0, loss-mask isn't the bottleneck and we revert to the simpler whole-completion default.
5. If A×B interaction dominates both main effects → the relevant variable is total training-context length, marker position, or interaction between role-conditioned system text and user-requested answer format, not system-vs-completion length separately.
6. If no main effect or interaction is > 1.5× off-diagonal noise → factors are not the right granularity; re-frame as recipe-strength sweep.
7. If A/B/C/D/E main effects flip sign across the 3 source personas → factor framing is wrong; re-cast at the persona-class level (length-class, topic-class) instead.

3. Tokenize with `AutoTokenizer.from_pretrained("Qwen/Qwen2.5-7B-Instruct")`, `add_special_tokens=False`.
4. For C1, compose neutral clauses from the same lexicon: `Background context: <domain-term sentence>. These details are reference material, not a role or identity for the assistant. Answer neutrally and directly.`
5. Pad C1 with deterministic neutral source-domain clauses until the Qwen token count exactly matches the paired C0 prompt. If exact equality is impossible with the finite suffix list, fail preflight rather than accepting drift. Require content-token Jaccard overlap >=0.55 after lowercasing and dropping stopwords.

#### 6. Evaluation
Primary scoring is case-insensitive `[ZLT]` substring rate via `src/explore_persona_space/eval/trait_scorers.py::evaluate_markers()` or the equivalent local scorer in `factor_screen_365/eval_panel.py`. Use vLLM batched generation, `temperature=1.0`, `top_p=0.95`, K=5 completions per `(model, persona, question)`, 20 questions, and `max_new_tokens=2048`. The 2048 cap is mandatory because #260/#297 showed 512-token marker eval can silently truncate late markers.

Persona panel: 24 personas = 3 source personas (`librarian`, `surgeon`, `programmer`) plus 21 bystanders sampled from the #337/#296 source list to span topic and prompt length. Store the exact panel in `src/explore_persona_space/experiments/factor_screen_365/persona_panel.py`; fail preflight if any source is missing from the panel. For a given cell/source, source-rate is the diagonal marker rate for that source prompt, and leakage is the mean off-diagonal marker rate across the 21 bystanders. Also report per-bystander rates so leakage concentration is visible.

Random-control panel: evaluate every LoRA on the 24 `random_control_*` prompts from task #365's body, same 20 questions and K=5. Report mean random-control rate and max random-control rate per model. Random controls are eval-only; they are not training conditions in this run.

Statistical analysis: for each factor A-E, compare paired cells where only that factor flips. There are 16 matched pairs per source and 48 source-stratified pairs across the three sources. Report mean delta for source-rate and leakage, plus a 95% bootstrap CI clustered by source persona and paired cell. For A×B, compute the paired difference-of-differences across the eight matched cells per source where A and B jointly vary. Rank top cells per source by source-rate first and leakage second; run seeds 137 and 256 on the top-3 cells per source.

#### 7. Decision Gates
This is gate-worthy because the full design is ~66-68 GPU-hours and ~8-9 wall-hours on 8× H100. Use exactly one early gate: run the librarian-only baseline-seed sweep first (32 cells × 1 source = ~10.7 GPU-hours, ~1.3h wall on 8× H100). Evaluate those 32 LoRAs immediately on the 24-persona panel. If the maximum librarian source-rate across all 32 cells is <10%, halt before the surgeon/programmer sweeps and before seeds 137/256. That gate consumes ~16% of the full budget and answers the minimal question "can any cell implant the marker at all under this factorial construction?" If at least one librarian cell reaches >=10% source-rate, continue the remaining two source sweeps and the top-3 seed expansion.

#### 8. Risks and Failure Modes
| Risk | Likelihood | Mitigation |
|---|---:|---|
| On-policy data gen from base Qwen produces too few marker-friendly or length-band-compliant continuations. | Medium | Generate 1.5× candidate completions per required row, filter by B length band, then sample 200/400. If yield <90% after two passes, log the realized distribution and fail preflight rather than silently changing B. |
| Lexically matched non-persona prompts accidentally include role-adoption/persona leakage tokens. | Medium | Static lint forbids `you are`, `as a`, `I am`, `my patients`, `my patrons`, `my code`, and source-role self-identification; prompt manifest includes term-overlap and token-length equality. |
| Off-by-one in cell encoding causes wrong data-policy or loss-mask training. | Medium | `cell_manifest.csv` is generated once; unit test enumerates all 32 cells and asserts D0/D1 and E0/E1 map to the expected data generator and `marker_only_loss` flag. |
| Eval `max_new_tokens=2048` still truncates long outputs. | Low/Medium | Store completion length and finish reason; spot-check completion-length distribution and count outputs with stop reason `length`. If >5% hit length cap in any cell, rerun that cell eval at 4096 before aggregation. |
| LoRA collisions or artifact collisions across 96 parallel runs. | Medium | Every job writes only to `eval_results/issue_365/cell_<ABCDE>/source_<src>/seed_<n>/`; no shared adapter/merged dirs; dispatcher refuses to start if target dir exists without `run_status.json` marked failed. |
| Existing branch scaffold aliases off-policy data or C semantics, biasing factor estimates. | Medium | Relocation task must update C to system-prompt persona-vs-non-persona and require cell-exact off-policy generation; aggregator must fail on any caveat that aliases B/C/D. |
| Fresh Claude off-policy generation is unavailable or over budget. | Medium | Preflight verifies cell-exact HF files first. If missing and API budget is unavailable, block before training; do not downgrade to reused medium completions. |

#### 9. Resources & Parallelism
Recommended pod: one 8× H100 pod named `epm-issue-365`, requested with intent `inf-70b` only if necessary for availability but overridden to eight independent `lora-7b` workers. Each H100 has 80GB HBM; Qwen2.5-7B-Instruct plus LoRA r=32 fits well under 40GB at per-device batch 4, so eight LoRA-7B training jobs fit on one 8× H100 pod via per-process `CUDA_VISIBLE_DEVICES`.

Dispatcher pseudocode:

```python
# scripts/dispatch_factor_screen_365.py
import itertools, subprocess, os

CELLS = list(itertools.product(*[[0, 1]] * 5))       # 32 cells
SOURCES = ["librarian", "surgeon", "programmer"]     # 3 sources
BASELINE_SEEDS = {src: [42] for src in SOURCES}
EXTRA_SEEDS = {}  # filled after top-3 selection, e.g. {(src, cell): [137, 256]}

def seeds_for(src, cell):
    return BASELINE_SEEDS[src] + EXTRA_SEEDS.get((src, cell), [])

JOBS = [(cell, src, seed) for cell in CELLS for src in SOURCES for seed in seeds_for(src, cell)]
GPU_POOL = list(range(8))
running = {}

for job in JOBS:
    gpu = wait_for_free_gpu(running, GPU_POOL)
    cell, src, seed = job
    cell_key = "".join(map(str, cell))
    env = os.environ.copy() | {"CUDA_VISIBLE_DEVICES": str(gpu)}
    cmd = [
        "uv", "run", "python", "-m", "explore_persona_space.experiments.factor_screen_365",
        "--cell", cell_key,
        "--source", src,
        "--seed", str(seed),
        "--output-dir", f"eval_results/issue_365/cell_{cell_key}/source_{src}/seed_{seed}",
    ]
    running[gpu] = subprocess.Popen(cmd, env=env)
```

The dispatcher must run the librarian gate first by constructing `JOBS` from `SOURCES=["librarian"]`; only after the gate passes should it enqueue `surgeon` and `programmer`.

| Persona-rich vs non-persona C control | C0 denotes assistant identity; C1 uses same vocabulary/length as background context without role adoption. | Separates role adoption from domain words and prompt length, which #337/#339 identify as co-linear. | Random filler only (confounds domain vocabulary); LLM-written neutral prompts (non-reproducible and may leak persona claims). |
| LoRA r=32 alpha=64 | Same LoRA capacity as #337/#295/#353 lineage. | Keeps factor estimates comparable to prior marker-implantation recipes and is already supported by `TrainLoraConfig`. | Lower-r LoRA (underpowered); larger LoRA (changes recipe strength and compute). |
| Marker-only baseline | E0 is marker-only; E1 is whole-completion. | #295/#353 point to gradient dilution as a plausible failure mode; marker-only is the candidate fix and should be the default comparator. | Whole-completion as baseline (would center the experiment on the suspected failure mode). |
| One 8× H100 pod | Shard independent LoRA jobs by GPU. | Independent cells are embarrassingly parallel and one pod avoids cross-pod artifact synchronization. | Four pods or 4× H100 (more orchestration or doubled wall time). |
