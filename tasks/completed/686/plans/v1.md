# Plan — issue #686: confirm-deleted guard in `GcpBackend.teardown`

## 1. Plan summary

After an `rc==0` `gcloud compute instances delete`, `GcpBackend.teardown`
will actively confirm the instance is gone via `gcloud compute instances
describe`; if the instance is still present **and** `status == RUNNING`
(the #683 zombie signature — a clean `eps/phase=done` run whose rc==0
delete silently no-op'd, billing an A100-80 ~40 min past terminal), it
re-issues the delete **once**. The fix lives in a new private method
`GcpBackend._confirm_deleted(handle, zone)` in
`src/explore_persona_space/backends/gcp.py`, called from the existing
`if result.returncode == 0:` branch of `teardown`. Placement is
`teardown` (NOT `scripts/backend_poll.py`) because `teardown` is the
canonical, single delete site for a successful GCP run
(`dispatch_issue.py::_cmd_finalize` → `backend.teardown(handle)` at
`/issue` Step 8), whereas `backend_poll.py` is a read-only single-tick
status reporter that never deletes. The change is fully idempotent and
fails toward "gone" (404 / non-RUNNING / probe-failure never re-delete),
GCP-scoped only, and adds no cost gate. **Decision: cherry-pick the
reference draft** (`151ca047`) — its logic is sound and consistent with
the production describe-parsing convention; it just needs to land on
`main` through this workflow's full review.

This is a non-architectural guardrail addition (no status enum / marker
schema / CLI contract / file relocation change), so it auto-approves at
0 GPU-hours.

## 2. Decision: `teardown` vs `backend_poll.py` placement

**Verdict: `GcpBackend.teardown`.** I read both sites directly.

- `scripts/backend_poll.py` calls `backend.poll(handle)` exactly ONCE per
  invocation (line 994) and never calls teardown / delete — it is a pure
  single-tick status reporter that emits a terminal JSON line for the
  orchestrator to act on. Putting a delete there would put a mutating
  delete inside a read-only poller, fire on every tick that observes
  `phase=done`+RUNNING, and duplicate the delete contract that already
  lives in `teardown`.
- `GcpBackend.teardown` (`gcp.py:3924`) is the canonical reaper of a
  *successful* GCP run: `dispatch_issue.py::_cmd_finalize` (line 1250,
  docstring "read sidecar → confirm_artifacts → teardown") and
  `router.py:1088` both call `backend.teardown(handle)`. The `/issue`
  Step 8 finalize path is precisely where a clean `eps/phase=done` run is
  torn down. CLAUDE.md confirms a clean GCP run stays RUNNING by design
  (the success path keeps the VM alive for the sentinel scp; only a CRASH
  triggers the in-VM EXIT-trap shutdown+DELETE), so orchestrator-driven
  `teardown` is the ONLY thing that reaps a successful run — making it the
  exactly-right hook for a confirm-deleted belt.

The candidate-block's `backend_poll.py` sketch is therefore the weaker
option; the reference draft's argument for `teardown` is correct.

**(b) NEW private method `_confirm_deleted`** (insert immediately after
`teardown`, before the `# ----- internal helpers -----` marker at line
3952). The 4 fail-toward-gone cases:

```python
    def _confirm_deleted(self, handle: RunHandle, zone: str) -> None:
        """Verify the post-delete instance is gone; re-issue the delete on a
        RUNNING zombie (#683). Called only after an rc==0 delete.

        Fail-toward-gone discipline (never a spurious re-delete):
        * describe 404 / "was not found"  -> confirmed gone (desired state); return.
        * describe rc != 0 (any other)     -> probe failure is NOT evidence the
                                              VM survived; the rc==0 delete already
                                              landed; log + return (janitor backstop).
        * describe rc==0, status != RUNNING (empty / STOPPING / TERMINATED /
          unparseable JSON) -> delete is taking effect; trust it; return.
        * describe rc==0 AND status == RUNNING -> the #683 zombie -> re-issue the
          delete ONCE (best-effort; failure logged, not raised — janitor + 24h
          max-run-duration remain backstops). A redelete 404 -> silent success.
        """
        config = self._config
        describe_argv = render_describe_argv(config=config, name=handle.pod_name, zone=zone)
        probe = self._run(describe_argv)
        if probe.returncode != 0:
            stderr_low = (probe.stderr or "").lower()
            if "was not found" in stderr_low or "404" in stderr_low:
                return  # confirmed gone
            logger.warning("GCP teardown: post-delete describe of %s failed (rc=%d); "
                           "trusting the rc==0 delete (gcp_audit janitor is the backstop). "
                           "stderr=%s", handle.pod_name, probe.returncode,
                           (probe.stderr or "")[:300])
            return
        try:
            payload = json.loads(probe.stdout) if probe.stdout.strip() else {}
        except json.JSONDecodeError:
            logger.warning("GCP teardown: post-delete describe of %s returned unparseable "
                           "JSON; trusting the rc==0 delete.", handle.pod_name)
            return
        status = (payload.get("status") or "").upper()
        if status != "RUNNING":
            return  # empty / STOPPING / TERMINATED — delete taking effect
        logger.warning("GCP teardown: %s still RUNNING after an rc==0 delete (#683 zombie); "
                       "re-issuing the delete once.", handle.pod_name)
        redelete = self._run(render_delete_argv(config=config, name=handle.pod_name, zone=zone))
        if redelete.returncode != 0:
            redelete_low = (redelete.stderr or "").lower()
            if "was not found" in redelete_low or "404" in redelete_low:
                return  # first delete landed between probe and retry
            logger.error("GCP teardown: re-issued delete of the RUNNING zombie %s ALSO "
                         "failed (rc=%d); gcp_audit janitor will reap it. stderr=%s",
                         handle.pod_name, redelete.returncode, (redelete.stderr or "")[:300])
```

**Idempotency mechanism:** (i) the method runs ONLY on the rc==0 delete
path (a "was not found" first-delete never reaches it); (ii) a 404 /
"was not found" describe is treated as confirmed-gone success; (iii) the
re-delete suppresses its own 404 / "was not found" (the first delete
landing between probe and retry); (iv) a failed re-delete is logged at
`error`, never raised — the janitor + 24h `--max-run-duration` are the
backstops. No path raises a new exception (preserving teardown's existing
raise-only-on-real-first-delete-failure contract).
