## 3. Method delta — what is new vs prior work

#2386 added the fail-loud log-dir guard to the same wrapper family and built
`tests/test_cron_wrapper_log_dir_guard.py`, whose glob-scan invariant already
asserts a *behavioral* property across every `scripts/cron_*.sh`. The delta
here is a **committed-mode** property, which no existing test asserts — that is
precisely why five review rounds on #2114 passed a non-executable wrapper. The
new test reuses #2386's proven shape (live glob over `scripts/cron_*.sh`, set
equality against a known member, plus a negative fixture proving the scanner
actually fires) rather than inventing a new idiom.

## 4. Concrete changes

### 4.1 `scripts/cron_step9c_ledger_refresh.sh` — mode only, no content change

```bash
chmod +x scripts/cron_step9c_ledger_refresh.sh
git update-index --chmod=+x scripts/cron_step9c_ledger_refresh.sh
```

**Both legs are load-bearing, for different reasons.** The index bit
(`update-index --chmod=+x`) is what survives a fresh checkout — a bare
`chmod` would be lost on the next clone, which is the task body's point. The
on-disk bit is what makes tonight's 05:31 fire actually execute at the repo
root. With `core.fileMode=true` the two must agree or git reports the file
modified; §5 sequences them so no mode-only modification is ever left
uncommitted at the shared repo root (`.claude/rules/repo-root-uncommitted-state.md`
— a concurrent session's pre-commit stash cycle runs `git checkout -- .` and
would revert exactly this kind of dangling change).

### 4.2 `tests/test_cron_wrapper_executable_bit.py` — new file

Three arms:

1. **Hard arm (deterministic, no external dependency)** — every
   `scripts/cron_*.sh` in the git index is mode `100755`. Read via
   `git ls-files -s -- 'scripts/cron_*.sh'` with `cwd=_REPO_ROOT`, parsing
   `<mode> <sha> <stage>\t<path>`. Works identically in the repo root and in
   any worktree (both have an index).
2. **Non-vacuity arm** — the glob returns a non-empty set containing a known
   member (`scripts/cron_pod_audit.sh`), so a broken pattern, a wrong cwd, or
   a `git` failure cannot produce a silent green.
3. **Negative fixture** — a throwaway `git init` tree with a
   `scripts/cron_fake.sh` staged at 100644, asserting the shared mode-reading
   helper reports it. Without this the pin is hollow: a test that only ever
   sees a clean tree never proves it can fail.

Plus a **soft crontab arm** matching A2's literal wording: when `crontab -l`
is readable, every repo-script path referenced by a non-comment crontab line
must be 0755 in the index; `pytest.skip` when no crontab is available (pods,
CI-less checkouts, fresh clones). This catches a future crontab-referenced
wrapper that does *not* match `cron_*.sh`. The hard arm is the binding gate;
the soft arm never fails a machine that legitimately has no crontab.

**Scope decision (recorded, with the measured number behind it).** The hard
arm covers `scripts/cron_*.sh` — 15 files — NOT all shell scripts. Measured
2026-08-29: of 234 tracked `scripts/*.sh`, **99 are committed 100644 and all
99 carry a shebang**. A blanket "shebang ⇒ 0755" rule would therefore ship 99
red findings on landing — the #1388 fleet-wedge shape (a repo-wide FAIL-posture
check that wedges every session's gate). Those 99 are overwhelmingly per-issue
dispatch/launch scripts invoked as `bash scripts/issueNNNN_dispatch.sh`, where
the executable bit is genuinely optional. `cron_*.sh` is the one class the
crontab invokes DIRECTLY, so it is the one class where the bit is load-bearing:
baseline red = exactly 1 (the bug), post-fix = 0.

### 4.3 `scripts/select_step9c_tests.py` — one `GLOB_SCAN_TESTS` row

```python
    # #2645: the cron wrappers' committed-executable-bit pin. Same reachability
    # problem as the #2386 row above — a `.sh` path reaches no stem or import
    # arm — so without this row a mode regression on any wrapper would select
    # no test at all.
    "tests/test_cron_wrapper_executable_bit.py": ("scripts/cron_*.sh",),
```

Without this row a wrapper-only `.sh` diff selects no test (shell has no import
graph and the `cron_<name>` stem matches no `tests/test_*cron_<name>*.py`) —
the exact reachability gap the #2386 row was added to close.

### 4.4 Not changed

`scripts/cron_step9c_ledger_refresh.sh` content, `tests/test_cron_step9c_ledger_refresh.py`,
`.claude/rules/background-automation.md` (its § "Step 9c known-red ledger
refresh" description is already accurate — the wrapper's *behavior* was never
wrong, only its mode).

## 5. Order of operations (the sequencing is load-bearing)

1. Worktree + branch `issue-2645` (`bash scripts/new_worktree.sh`).
2. In the worktree: chmod + `update-index --chmod=+x`, write the new test,
   add the selector row. Commit.
3. Code-review ensemble (Step 5), then Step 9c test verdict.
4. Merge to `main` (Step 10d).
5. **`uv run python scripts/sync_repo_root.py`** — the merge lands the index
   mode on `origin/main`, but the repo-root *working tree* (which is what
   crontab executes) only gets the new mode when the root fast-forwards.
   Skipping this leaves the 05:31 fire still broken while every test is green.
6. **Verify (A1)** — invoke the wrapper by its absolute path exactly as cron
   does (`/home/.../scripts/cron_step9c_ledger_refresh.sh`, no `bash` prefix:
   a `bash <path>` invocation would pass even with the bit unset, proving
   nothing). Detached, per §6.
7. Harvest: assert a dated `logs/step9c_ledger_refresh/YYYY-MM-DD.log` exists
   with `exit=0`, and `refreshed_at` is fresh.

## 6. Compute character of the verification run (step 6 above)

**CPU-only, no GPU, one process.** The wrapper runs
`scripts/step9c_baseline.py refresh --json`, i.e. the heaviest pytest universe:
measured cost from #2114/#2105/#1992/#2106 is **~31-40 min**, with the
refresh's own `--timeout-s` default (4350 s) as the wall fence. This is the
designed nightly load, not new load — it is what the box was supposed to be
absorbing every night for 18 nights.

- Ops arithmetic: 1 invocation × 1 pytest universe ≈ 31-40 min wall.
- Batching/threads: the wrapper already carries the shared-VM thread cap
  (`OMP/MKL/OPENBLAS/NUMEXPR=8`, `MALLOC_ARENA_MAX=2`) and a fail-open
  `choom -n -600` self-protect. Nothing to add.
- Not shardable: a single pytest run is the unit.
- Disk: no download, no staging. Writes one dated log (KB) + rewrites the
  gitignored ledger JSON.
- **Detached shape is mandatory** (>15 min VM-local, `code-style.md`): launch
  via `setsid nohup ... < /dev/null &` inside a `bash -c` so `$!` is the
  workload pid; record `pid=` / `log=` / `harvest=` in a `stage-dispatch`
  breadcrumb so the run survives this terminal.
- Concurrency: safe by construction — the refresh takes the
  `.claude/cache/step9c-baseline.lock` flock, so a concurrent in-session
  refresh (or the 05:31 cron, if it beats the harvest) is a single-flight
  no-op at rc 0.

## 7. Body item 4 — runtime backstop: disposition

**File it separately; do not fold it in.** The natural implementation is a new
`autonomous_session_watch.py` pass reading `step9c_baseline.ledger_age_hours()`
(the helper already exists at `scripts/step9c_baseline.py:1432`) and escalating
on a stale `refreshed_at`. That is a full watcher pass — episode state file,
dedup + re-alert TTL, kill switch, the docstring pass-count lint
(`--check-asw-docstring-pass-count`), and its own tests — comparable in size to
this entire task, and it touches a file every fleet session depends on.

Folding it in would make this diff several times larger and put the
one-line mode fix behind a review of watcher-pass semantics, while the fleet
keeps paying 31-40 min per session. It is also genuinely independent: the
mechanical pin closes the *mode* cause at review time; the runtime read closes
the *residual* causes (crontab line deleted, path renamed, cron daemon down,
`uv` missing) that no static test can see. File as `kind: infra`,
`--no-dispatch` (the auto-dispatchable infra queue is already deep, #2070), so
it lands `proposed` for triage rather than auto-spawning.

## 9. Kill criteria

- The refresh exits rc=2 (timeout / junit-parse / zero-collected) on the
  verification run ⇒ the mode fix is still correct and lands, but A1's
  "fresh `refreshed_at`" half is NOT satisfied; that is a *separate* defect in
  the refresh command, reported as such rather than papered over. Do not
  re-run in a loop and do not claim A1.
- The glob-scan pin turns out to false-fire on a legitimately non-executable
  `cron_*.sh` ⇒ the scope in §4.2 is wrong; re-scope rather than add an
  allowlist entry silently. (Measured today: zero such files after the fix.)
