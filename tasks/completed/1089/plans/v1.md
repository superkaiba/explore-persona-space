### 3.2 Exact WARN detail strings

- Headline case (a): `stale concern-deferred marker '<id>' — concern is addressed; remove or retag` (verbatim from the task body's diff sketch).
- Absent-id case (b): `stale concern-deferred marker '<id>' — id absent from concerns.jsonl; remove or retag`.
- Multiple stale ids join with `"; "` (the 8030 pattern). Duplicate markers for the same id dedupe via the `set` — one WARN per id.

### 3.3 Decided semantics (clarifier item 5)

| Case | Latest ledger event for marker id | Behavior |
|---|---|---|
| (a) headline | `addressed` | WARN (any severity — staleness is severity-independent; a NIT that was addressed still has a misleading marker) |
| (b) absent | id not in `latest` | WARN. Grounding: `defer_concern` refuses never-raised ids (task_workflow.py:5347-5351), so an absent-id marker is a typo (which silently fails to defer — the open concern already FAILs, and this WARN points at the why) or a body copied/promoted across tasks (follow-up consolidation folding a sibling body whose concern lives on another task's ledger). That cross-task case is real but rare and WARN-only noise is acceptable; the marker genuinely does not correspond to this task's ledger. |
| (c) live | `raised` / `verified-open` / `deferred` | No WARN — current behavior byte-identical |
| (d) precedence | body also has unaddressed open concerns | The FAIL CheckResult stays `passed=False, is_warn=False`; stale-warn text folds into the FAIL detail behind the literal `; WARN: ` prefix (the 8027 pattern). A FAIL is never downgraded. |
| (e) no ledger | `concerns_path` None/missing | Skip-PASS unchanged, no scan (nothing to compare against; clarifier item 6) |

## 11. Decision Rationale

1. **WARN-vs-FAIL: WARN-only, never FAIL.**
   *What:* stale markers produce `is_warn=True` / a `; WARN:` detail suffix, never `passed=False`.
   *Why:* forward-only — grandfathered bodies (incl. #833, already `completed`-track) carry stale markers today; a FAIL would retroactively block promote-time re-verification of shipped bodies, which the forward-only convention (CLAUDE.md § Experiment Report Structure) forbids.
   *Source:* task #1089 body ("WARN-only (never a hard FAIL; forward-only)"), incident #833; the WARN precedent for advisory checks at verify_task_body.py:6957-6960 ("WARN, never FAIL ... passed stays True so overall ok").
   *Alternatives rejected:* FAIL (breaks grandfathered bodies); INFO-print (no mechanical surface — the render loop only knows PASS/WARN/FAIL).

2. **Single-CheckResult folding via the 8027/8030 pattern (FAIL wins; warns ride the detail suffix).**
   *What:* one returned CheckResult; `fails → passed=False` with `"; WARN: "` suffix; `warns-only → passed=True, is_warn=True`.
   *Why:* the function signature returns one CheckResult and the caller (verify_task_body.py:8997) appends exactly one; two in-file checks already mix FAIL+WARN this exact way, so the implementer follows an established, test-pinned idiom with zero caller blast radius.
   *Source:* verify_task_body.py:8020-8030 and 8180-8190 (the existing pattern), :8997 (single-append caller), :817-830 (`CheckResult.is_warn`).
   *Alternatives rejected:* returning a list + caller change (wide blast radius — kill criterion 1); a second standalone check function (would re-parse the ledger and duplicate the U+2028-guarded reader — two sources of truth for one ledger read).

3. **Absent-id semantics: WARN (same as addressed), distinct detail text.**
   *What:* a marker id not present in `latest` warns with "id absent from concerns.jsonl".
   *Why:* `defer_concern` refuses to defer a never-raised concern (task_workflow.py:5347-5351), so an absent-id marker cannot arise from the canonical path — it is a typo (actively harmful: it silently fails to defer, and the resulting open-concern FAIL becomes explicable via this WARN) or a cross-task body copy (rare; WARN-only noise, acceptable). Distinct wording so the operator immediately knows which repair applies.
   *Source:* task #1089 body diff sketch ("or id absent from ledger → WARN"); task_workflow.py:5347-5351; CONCERN_EVENTS at task_workflow.py:5018.
   *Alternatives rejected:* silent-skip absent ids (hides typos — the #833 class would recur under a misspelled id); FAIL on absent ids (breaks the cross-task-copy shape and the forward-only rule).

4. **Scan placement: hoisted above the `not open_binding` early return, inside the ledger-present branch only.**
   *What:* `deferral_re`/`deferred_ids` move from line 7423 to just after `open_binding` (≈7366); the skip path (7332) never scans.
   *Why:* the #833 incident IS the early-return shape (all concerns addressed → `open_binding` empty → old code never reached the marker scan); and with no ledger there is nothing to compare against (clarifier item 6).
   *Source:* verify_task_body.py:7367-7372 (the early return), :7423 (current regex site), task #1089 body ("nothing mechanical flagged them").
   *Alternatives rejected:* duplicating the regex at both sites (two patterns drift; the clarifier explicitly bars inventing a second pattern).
