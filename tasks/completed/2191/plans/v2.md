#### 4.1 Check (a) — `check_committed_under_claims` (check name: `committed-under-claims`)

Signature: `check_committed_under_claims(blanked_lines: list[str], figures_root: Path) -> CheckResult`. Operates on BLANKED lines (verbatim examples are data — reuses `blank_verbatim`'s output already computed in the dispatch). Read-only local git via `_git`; no network, no writes.

**Claim matcher.** Per line, find claims via

```python
_COMMITTED_UNDER_RE = re.compile(
    r"(?i)\b(?:committed|in\s+git)\s+under\s+`([^`]+)`"
)
_NEGATION_WINDOW_CHARS = 40
_NEGATION_TOKENS = (
    "not", "n't", "never", "no longer", "rather than", "instead of", "nothing",
)
```

- Trigger bigrams are exactly `committed under` and `in git under` (case-insensitive), each immediately followed by a backticked path.
- **Negation guard — a preceding-window scan, NOT a lookbehind (revised after critic review).** v1 guarded only `(?<!not )(?<!never )`, which is defeated by every natural negation variant: "**nothing is** committed under `X`", "**isn't/wasn't** in git under `X`", "**rather than / instead of** in git under `X`", "**never landed** in git under `X`" (an intervening word defeats an immediate lookbehind), "**no longer** committed under `X`". Each would FAIL on a *correct* sentence whenever the line also carries a resolvable pin and the path is empty — and that co-occurrence is realistic rather than contrived, because the FAIL message itself teaches authors to reword false git-home claims into HF-home sentences, which naturally retain the empty git path for contrast. The worked example that motivated the change: `scores live on HF under `X` rather than in git under `.../scores/` at `20fcef9c28…`` — a convention-compliant sentence that v1's regex FAILs. Rule: lowercase the up-to-`_NEGATION_WINDOW_CHARS` characters preceding the match start (clipped at the line start) and skip the claim if any `_NEGATION_TOKENS` member occurs in that window. An over-broad window only ever *under*-fires, which is the sanctioned direction; the window size and token set are pinned by §6 criterion 5 tests, not left tunable.
- **Path handling:** strip whitespace; expand ONE brace group `{a, b, c}` (spaces stripped) into per-member paths; strip a trailing `:`/`,`.
- **Skip (recorded as a PASS-detail note, not checked) when the path:** contains `://` (URL / HF claim); starts with `/` (absolute, not repo-relative); contains `…` or `...` (abbreviated); contains NO `/` after expansion (bare filename like the line-18 `in-git \`wildchat_random_v1.json\`` — no `under`, so it doesn't even match the trigger, but the slash rule is the backstop for other phrasings).

**Pin resolution (the genuinely open question — hard requirement 3).** Candidate pin sources considered:

1. **Inline SHA on the claim's own line** — CHOSEN, first priority. The corrected line 37 carries `at the branch pin (\`20fcef9c28…\`)`; extraction: all hex runs via `(?<![0-9a-fA-F])[0-9a-fA-F]{8,40}(?![0-9a-fA-F])` over the line AFTER stripping (i) URL spans (`_URL_RE` — the artifacts-index line carries an HF revision `dc8108ab84f…` inside a URL that must not be mistaken for a git pin) and (ii) the claimed-path backtick span itself. Each candidate resolves via `_git(root, "rev-parse", "--verify", f"{tok}^{{commit}}")` — abbreviations resolve iff unambiguous, exactly git's own rule.
2. **Branch named on the claim's own line** — CHOSEN, additional source. Backticked tokens matching `^(?:origin/)?(?:issue-\d+|main)$` resolve via `refs/heads/<b>` then `refs/remotes/origin/<b>` (covers the artifacts-index form `on branch \`issue-2162\``).
3. **The report's dominant image pin (`_RAW_PIN_RE` / `check_image_pins` machinery)** — REJECTED: the figures pin names the commit that added the FIGURES, which is a different commit from (and not provably a descendant of) the one the committed-under claim is made against; adopting it manufactures pins the author never asserted → false-FAIL channel.
4. **A new CLI arg (`--repo-pin <sha>`)** — REJECTED for v1: the report should be self-contained, and an operator-supplied pin the report text never states is again a claim the author never made. Noted as a possible future extension.

**Assert rule (any-pin-satisfies — maximally conservative):** a claim FAILs only when EVERY resolvable same-line pin yields zero output from `_git(root, "ls-tree", "-r", "--name-only", pin, "--", path)` for at least one expanded path member. If ≥1 pin shows ≥1 blob for every member → the claim passes. **Skip+WARN rule:** no pin source on the line resolves at all → WARN naming the claim line ("no resolvable same-line pin — add `at <sha>`/name the branch, or reword to an HF-home claim"). **The WARN detail additionally carries an INFORMATIONAL branch-tip probe** (added after critic review, zero-cost: the issue's `issue-<N>` / `origin/issue-<N>` refs are already resolved by check (b)'s S2 collection): append either "path also empty at `origin/issue-<N>` tip" or "path resolves at `origin/issue-<N>` tip" so the reader gets the discriminating fact without leaving the gate output. **Severity stays WARN** — escalating this probe to FAIL would import the deleted-later-at-tip false-FAIL class (a path correctly committed at the claimed pin but since removed at the tip), which the body's priority order forbids. Rationale for accepting WARN here: a WARN renders with `rc=0`, so its catching power depends on the `report-verifier` agent reading the rendered lines across its 5-round loop — acceptable because both remediation paths the message teaches (add a pin, or reword to HF-home) converge on a correct outcome.
 Non-git `figures_root` → single WARN, mirroring `_check_pin_blob_identity` line 635-637. HF-home claims never match the trigger (no `committed|in git` + `under` adjacency), so the wave-output convention is untouched — the FAIL message explicitly teaches it: *"if these artifacts are deliberately not in git (wave-output convention), reword the claim to name their HF home; if they should be committed, commit them or fix the path/pin."*

**What check (a) does NOT fire on (conservative-matcher enumeration, hard requirement 2):**
- HF-home claims ("persisted on HF under …", "lives on the HF data repo under …") — no trigger match.
- Negated claims — the `_NEGATION_TOKENS` preceding-window scan above, which covers "is NOT committed …", "nothing is committed under …", "isn't/wasn't in git under …", "never landed in git under …", "no longer committed under …", and the contrastive "… on HF under `X` rather than / instead of in git under `Y`". (v1 claimed this bullet was discharged by two lookbehinds; it was not — see the negation-guard bullet. Each listed variant is pinned by a §6 criterion-5 fixture row.)
- Claims with no backticked path, absolute paths, URLs, `…`-abbreviated paths, slash-less bare filenames — skipped with a note.
- Claims with no resolvable same-line pin — WARN, never FAIL.
- Code-citation forms (``` `scripts/issue2162_run.py` @ `b4ab6ed5f9…` ``` — lines 28/83/88/90) — no trigger.
- Anything inside fenced code blocks / blockquotes — blanked before scanning.
- **The named residue — and it is the founding incident's own shape, not a hypothetical:** a claim naming a NON-empty directory while asserting a subset that is absent. #2162's round-1 sentence IS this form: it claimed scores+items were committed under the parent `eval_results/issue_2162/judge/`, which held **82 blobs** at `20fcef9c28`, with zero under `judge/scores/`. Two witnesses fix that wording — task body line 31 ("The draft asserted that judge scores and items were committed under `eval_results/issue_2162/judge/`") and the clarifier's pre-correction record of line 37 (`tasks/planning/2191/events.jsonl` line 2, taken before the #2162 session's in-place fix), which additionally records that the round-1 line carried **no same-line pin**. **Consequence, stated plainly: check (a) is SILENT (a clean PASS, not even a WARN) on the defect that motivated it** — the any-pin-satisfies rule passes the claim on path resolution alone, before pin presence is even consulted. It fires on the empty-path form of the class (fabricated paths, wrong paths, never-committed paths), which is what the body's falsifiability definition specifies and what the FIRE fixture (§6 criterion 1) tests. Deliberately NOT fixed by broadening the matcher: any mechanical subset rule (mapping claim nouns like "scores"/"items" to filename tokens under the path) is free-text semantics with a live false-FAIL channel — "gate reports committed under `judge/`" would FAIL though correct — which the body's conservative-matcher instruction forbids. The residue is instead PINNED by §6 criterion 1-bis, a test asserting the witnessed form returns `passed=True` with the reason in its docstring, so no future reader mistakes the check's scope. The subset case stays the human methodology lens's job; the FAIL/WARN messages teach the report-side wording fix.

#### 4.2 Check (b) — `check_code_sha_cards` (check name: `code-sha-cards`)

Signature: `check_code_sha_cards(raw_body: str, blanked_lines: list[str], *, mode: str, figures_root: Path, expect_issue: int | None) -> CheckResult`. Raw body supplies the citation set (a citation inside a verbatim example still counts — conservative in the pass direction); blanked lines supply the Code-SHAs-row detection.

**Why `mode` is threaded (added after critic review — a demonstrated promote-time false-FAIL channel).** Unlike a pin-anchored read, which is stable in time, this check's reference set is EXTERNAL MUTABLE STATE: the card set under `eval_results/issue_<N>/**` keeps growing after the report is written. Any later follow-up round or inline analysis that writes one more full-40-hex non-dirty card makes a previously-PASSing, **unchanged** report FAIL at `--mode promote` — blocking promotion of a good result, which the task body names as the worst outcome. The file's own precedent is a mode-split degrade ladder (`_check_pin_blob_identity`, `scripts/verify_report.py:645-680`: generation strict, promote lenient), which §2 already cites as this check's model but v1's signature did not honor. Check (a) deliberately does NOT take a mode: its FAIL condition (resolvable pin + empty path) is time-stable and matches the model check's `does not contain {path}` arm at line 656, which carries **no** mode branch — FAIL in both modes. So the asymmetry follows the file's existing idiom rather than inventing one.

**Issue resolution:** use `expect_issue` when provided (`--issue`/`--expect-issue`); else infer from the report's own `**Detailed writeup:**` line via the existing `_DETAILED_LINE_RE` + `_DETAILED_URL_RE` (group 2 = issue number — that line is REQUIRED at generation and already issue-verified by `check_detailed_writeup_link`, so the inference is mechanically pinned); else WARN "issue number unknown — card check skipped (pass --issue/--expect-issue)". The inference is what keeps the check LIVE under the gate's existing invocation (`verify_report.py --file <draft> --mode generation`, SKILL.md line 480, which passes no issue) with zero SKILL.md edits.

**Card collection (read-only, local, union of sources):**
- S1 working tree: `figures_root/eval_results/issue_<N>/**/*.json` (rglob), per-file size guard ≤ 5 MB.
- S2 git refs: for each of `issue-<N>`, `origin/issue-<N>` that `rev-parse --verify <ref>^{commit}` resolves: `ls-tree -r --name-only <ref> -- eval_results/issue_<N>/`, filter `.json`, size-guard via `cat-file -s <ref>:<path>`, read via `_git(root, "show", ...)`. (Clarifier constraint 2: for #2162 the cards exist ONLY at `origin/issue-2162` — `main` has none.)
- Parse each JSON (parse failures counted + skipped, never fatal); recursively walk collecting every value under a key in `{"git_commit", "final_commit_sha"}` (clarifier constraint 1: the key sits at ≥3 different nesting paths within one issue — `reproducibility_card.git_commit`, `note.reproducibility_card.git_commit`, `repro.git_commit` — so recursive key search, never a fixed dotted path; `final_commit_sha` added because `margin/upload_done.json` carries it as a top-level twin, measured this session), recording (file path, JSON pointer, value, sibling `git_dirty`, sibling `phase`).
- **Usable-card classification (clarifier constraint 3):** a record enters the FAIL set iff its value matches `^[0-9a-fA-F]{40}$` AND sibling `git_dirty` is not `True`. Excluded (listed in the PASS detail, no WARN): `"unknown"` / non-hex (the `issue_1768/on_target/upload_done.json` shape), abbreviated <40-hex (the six 8-hex judge-side records — REQUIRED exclusion: two of them, `13c45fd0`/`6cd4704f`, are uncited in the corrected report, so including them false-FAILs the acceptance SILENT case; principle: an abbreviated card value is itself defective provenance from the card writer — the report gate must not punish the report for it), and dirty cards (non-authoritative: the working tree that produced them did not match the recorded commit). Dedupe the FAIL set by SHA value.
- Degrades: no `eval_results/issue_<N>` dir AND no resolvable ref → PASS-note "no reproducibility cards found for issue <N> (working tree + issue-<N>/origin/issue-<N>) — card check skipped (N/A)" (PASS-note, not WARN, so the many existing synthetic test fixtures — which have detailed-writeup links naming issue 5 but no cards — stay warn-free; on the real gate the authoring VM always has the branch). JSONs found but zero card keys → PASS-note N/A.

**Citation set:** all hex runs ≥8 chars (same `_HEX_RUN_RE`) extracted from the RAW body. A card SHA is *cited* iff some extracted token `t` (lowercased, `len(t) >= 8`) is a prefix of the card SHA — this natively handles the report's `ba3485b619…` U+2026-abbreviated citation form (clarifier constraint 4: the hex run simply stops at the ellipsis) and full 40-hex forms.

**Three assertions, severity-split (the redesign — justification below):**
- **(b1) card-coverage, whole-report scope — FAIL at `generation`, WARN at `promote`:** every distinct usable card SHA must be cited somewhere in the report. Miss → *"reproducibility card `<file>` (`<json pointer>`) records commit `<sha12>…` which the report never cites — a run that legitimately spans commits should carry a per-phase Code-SHAs split (each phase @ its own card's commit), not a single SHA; if this phase is covered elsewhere under a different commit, the pairing is wrong."* (The per-phase-split suggestion is the body's own required message shape.) **Severity is mode-split** per the §4.2 preamble: at `generation` the report and the card set are contemporaneous, so an uncited card commit is a genuine authoring defect and FAILs; at `promote` the card set may legitimately have grown since authoring, so the same condition is `is_warn=True` — visible, non-blocking, and incapable of blocking promotion of a good result. b2/b3 are WARN in both modes. The mode-split arm is pinned by a §6 criterion-5 test (one uncited usable card: `mode="promote"` ⇒ `is_warn is True` and `passed is True`; `mode="generation"` ⇒ `passed is False`).
- **(b2) WARN — row-scope coverage:** when a Code-SHAs table row exists (blanked line matching `(?i)^\s*\|\s*code[ -]?shas?\b`), any usable card SHA cited elsewhere in the report but absent from that row (prefix rule against the row's hex tokens) → WARN suggesting the row carry the per-phase split. (Catches the mid-correction state this session actually observed: line 28 corrected, line 111 still single-SHA.)
- **(b3) WARN — best-effort pairing on the token-resolvable subset:** split the row's value cell on `·` / `;`; per segment extract the hex token + the residual label; normalize label tokens (lowercase alnum, `stage-2`→`stage2`); card-side tokens = path components + filename-stem words (split `_`) of the card file under `eval_results/issue_<N>/`, plus sibling `phase` value tokens (split `-_`), minus a stopword set **pinned by a §6 criterion-5 test, NOT tunable at implementation** (`{report, json, upload, done, card, sentinel, results, gate, gates}` — a critic-review condition: the set is the only ungrounded constant in the check, so it is fixed by test rather than left to implementer discretion).
 If a segment's label tokens hit ≥1 usable card and ALL hit cards agree on one SHA and the segment's hex token is NOT a prefix of it → WARN naming both SHAs + the per-phase-split suggestion. Unresolvable segments (no token hit, or hit cards disagree) are silently skipped, counted in the detail.

**Why coverage (b1) rather than the body's literal row↔card pairing as the FAIL condition** — measured, not stylistic: the grid/anchors phase's card is `gates/pilot_gate_report.json`, whose path and content carry NO token of "grid"/"anchors"/"stage-1" (measured this session), so no honest label→card resolution can pair the incident's own defective segment ("stage-1 grid + margin") with its card — token pairing (b3) run on the round-1 row resolves only the `margin` token, whose SHA matches, and stays silent. Coverage fires on the incident regardless of phase naming: the verdict (CORRECTION 2) states the round-1 draft cited `ba3485b619…` as "the code" *throughout*, i.e. `b4ab6ed5f9…` appeared NOWHERE in the round-1 report, while the corrected report cites it (row + lines 28/83/88). Coverage therefore FAILs round-1 and passes corrected — the exact acceptance pair — and additionally catches every future "one SHA pinned for all phases" report. The pairing residue (both SHAs cited but paired backwards across resolvable labels) is retained as b3-WARN; a swap where labels resolve has no confirmed incident, and free-form phase naming makes a FAIL there a false-positive channel the body's conservative-matcher instruction forbids.
