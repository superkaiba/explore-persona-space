#### 4.1 Check (a) — `check_committed_under_claims` (check name: `committed-under-claims`)

Signature: `check_committed_under_claims(blanked_lines: list[str], figures_root: Path) -> CheckResult`. Operates on BLANKED lines (verbatim examples are data — reuses `blank_verbatim`'s output already computed in the dispatch). Read-only local git via `_git`; no network, no writes.

**Claim matcher.** Per line, find claims via

```python
_COMMITTED_UNDER_RE = re.compile(
    r"(?i)(?<!not )(?<!never )\b(?:committed|in\s+git)\s+under\s+`([^`]+)`"
)
```

- Trigger bigrams are exactly `committed under` and `in git under` (case-insensitive), each immediately followed by a backticked path. The negative lookbehinds skip correctly-worded negative claims ("is NOT committed under …").
- **Path handling:** strip whitespace; expand ONE brace group `{a, b, c}` (spaces stripped) into per-member paths; strip a trailing `:`/`,`.
- **Skip (recorded as a PASS-detail note, not checked) when the path:** contains `://` (URL / HF claim); starts with `/` (absolute, not repo-relative); contains `…` or `...` (abbreviated); contains NO `/` after expansion (bare filename like the line-18 `in-git \`wildchat_random_v1.json\`` — no `under`, so it doesn't even match the trigger, but the slash rule is the backstop for other phrasings).

**Pin resolution (the genuinely open question — hard requirement 3).** Candidate pin sources considered:

1. **Inline SHA on the claim's own line** — CHOSEN, first priority. The corrected line 37 carries `at the branch pin (\`20fcef9c28…\`)`; extraction: all hex runs via `(?<![0-9a-fA-F])[0-9a-fA-F]{8,40}(?![0-9a-fA-F])` over the line AFTER stripping (i) URL spans (`_URL_RE` — the artifacts-index line carries an HF revision `dc8108ab84f…` inside a URL that must not be mistaken for a git pin) and (ii) the claimed-path backtick span itself. Each candidate resolves via `_git(root, "rev-parse", "--verify", f"{tok}^{{commit}}")` — abbreviations resolve iff unambiguous, exactly git's own rule.
2. **Branch named on the claim's own line** — CHOSEN, additional source. Backticked tokens matching `^(?:origin/)?(?:issue-\d+|main)$` resolve via `refs/heads/<b>` then `refs/remotes/origin/<b>` (covers the artifacts-index form `on branch \`issue-2162\``).
3. **The report's dominant image pin (`_RAW_PIN_RE` / `check_image_pins` machinery)** — REJECTED: the figures pin names the commit that added the FIGURES, which is a different commit from (and not provably a descendant of) the one the committed-under claim is made against; adopting it manufactures pins the author never asserted → false-FAIL channel.
4. **A new CLI arg (`--repo-pin <sha>`)** — REJECTED for v1: the report should be self-contained, and an operator-supplied pin the report text never states is again a claim the author never made. Noted as a possible future extension.

**Assert rule (any-pin-satisfies — maximally conservative):** a claim FAILs only when EVERY resolvable same-line pin yields zero output from `_git(root, "ls-tree", "-r", "--name-only", pin, "--", path)` for at least one expanded path member. If ≥1 pin shows ≥1 blob for every member → the claim passes. **Skip+WARN rule:** no pin source on the line resolves at all → WARN naming the claim line ("no resolvable same-line pin — add `at <sha>`/name the branch, or reword to an HF-home claim"). Non-git `figures_root` → single WARN, mirroring `_check_pin_blob_identity` line 635-637. HF-home claims never match the trigger (no `committed|in git` + `under` adjacency), so the wave-output convention is untouched — the FAIL message explicitly teaches it: *"if these artifacts are deliberately not in git (wave-output convention), reword the claim to name their HF home; if they should be committed, commit them or fix the path/pin."*

**What check (a) does NOT fire on (conservative-matcher enumeration, hard requirement 2):**
- HF-home claims ("persisted on HF under …", "lives on the HF data repo under …") — no trigger match.
- Negated claims ("is NOT committed …") — lookbehind + the corrected line 37's actual wording has no `under` after `committed`.
- Claims with no backticked path, absolute paths, URLs, `…`-abbreviated paths, slash-less bare filenames — skipped with a note.
- Claims with no resolvable same-line pin — WARN, never FAIL.
- Code-citation forms (``` `scripts/issue2162_run.py` @ `b4ab6ed5f9…` ``` — lines 28/83/88/90) — no trigger.
- Anything inside fenced code blocks / blockquotes — blanked before scanning.
- **The named residue:** a claim naming a NON-empty directory while asserting a subset that is absent (e.g. "scores committed under `judge/`" where `judge/` holds 82 other blobs but zero score files). The path-emptiness check is structurally blind to this — it is the reason the FIRE fixture names `judge/scores/` (§6). Accepted per the body's own falsifiability definition ("`git ls-tree -r <pin> -- <path>` returning at least one blob") and the under-fire mandate; the corrected-wording convention the FAIL message teaches is the report-side fix for the subset case.

#### 4.2 Check (b) — `check_code_sha_cards` (check name: `code-sha-cards`)

Signature: `check_code_sha_cards(raw_body: str, blanked_lines: list[str], figures_root: Path, expect_issue: int | None) -> CheckResult`. Raw body supplies the citation set (a citation inside a verbatim example still counts — conservative in the pass direction); blanked lines supply the Code-SHAs-row detection.

**Issue resolution:** use `expect_issue` when provided (`--issue`/`--expect-issue`); else infer from the report's own `**Detailed writeup:**` line via the existing `_DETAILED_LINE_RE` + `_DETAILED_URL_RE` (group 2 = issue number — that line is REQUIRED at generation and already issue-verified by `check_detailed_writeup_link`, so the inference is mechanically pinned); else WARN "issue number unknown — card check skipped (pass --issue/--expect-issue)". The inference is what keeps the check LIVE under the gate's existing invocation (`verify_report.py --file <draft> --mode generation`, SKILL.md line 480, which passes no issue) with zero SKILL.md edits.

**Card collection (read-only, local, union of sources):**
- S1 working tree: `figures_root/eval_results/issue_<N>/**/*.json` (rglob), per-file size guard ≤ 5 MB.
- S2 git refs: for each of `issue-<N>`, `origin/issue-<N>` that `rev-parse --verify <ref>^{commit}` resolves: `ls-tree -r --name-only <ref> -- eval_results/issue_<N>/`, filter `.json`, size-guard via `cat-file -s <ref>:<path>`, read via `_git(root, "show", ...)`. (Clarifier constraint 2: for #2162 the cards exist ONLY at `origin/issue-2162` — `main` has none.)
- Parse each JSON (parse failures counted + skipped, never fatal); recursively walk collecting every value under a key in `{"git_commit", "final_commit_sha"}` (clarifier constraint 1: the key sits at ≥3 different nesting paths within one issue — `reproducibility_card.git_commit`, `note.reproducibility_card.git_commit`, `repro.git_commit` — so recursive key search, never a fixed dotted path; `final_commit_sha` added because `margin/upload_done.json` carries it as a top-level twin, measured this session), recording (file path, JSON pointer, value, sibling `git_dirty`, sibling `phase`).
- **Usable-card classification (clarifier constraint 3):** a record enters the FAIL set iff its value matches `^[0-9a-fA-F]{40}$` AND sibling `git_dirty` is not `True`. Excluded (listed in the PASS detail, no WARN): `"unknown"` / non-hex (the `issue_1768/on_target/upload_done.json` shape), abbreviated <40-hex (the six 8-hex judge-side records — REQUIRED exclusion: two of them, `13c45fd0`/`6cd4704f`, are uncited in the corrected report, so including them false-FAILs the acceptance SILENT case; principle: an abbreviated card value is itself defective provenance from the card writer — the report gate must not punish the report for it), and dirty cards (non-authoritative: the working tree that produced them did not match the recorded commit). Dedupe the FAIL set by SHA value.
- Degrades: no `eval_results/issue_<N>` dir AND no resolvable ref → PASS-note "no reproducibility cards found for issue <N> (working tree + issue-<N>/origin/issue-<N>) — card check skipped (N/A)" (PASS-note, not WARN, so the many existing synthetic test fixtures — which have detailed-writeup links naming issue 5 but no cards — stay warn-free; on the real gate the authoring VM always has the branch). JSONs found but zero card keys → PASS-note N/A.

**Citation set:** all hex runs ≥8 chars (same `_HEX_RUN_RE`) extracted from the RAW body. A card SHA is *cited* iff some extracted token `t` (lowercased, `len(t) >= 8`) is a prefix of the card SHA — this natively handles the report's `ba3485b619…` U+2026-abbreviated citation form (clarifier constraint 4: the hex run simply stops at the ellipsis) and full 40-hex forms.

**Three assertions, severity-split (the redesign — justification below):**
- **(b1) FAIL — card-coverage, whole-report scope:** every distinct usable card SHA must be cited somewhere in the report. Miss → FAIL: *"reproducibility card `<file>` (`<json pointer>`) records commit `<sha12>…` which the report never cites — a run that legitimately spans commits should carry a per-phase Code-SHAs split (each phase @ its own card's commit), not a single SHA; if this phase is covered elsewhere under a different commit, the pairing is wrong."* (The per-phase-split suggestion is the body's own required message shape.)
- **(b2) WARN — row-scope coverage:** when a Code-SHAs table row exists (blanked line matching `(?i)^\s*\|\s*code[ -]?shas?\b`), any usable card SHA cited elsewhere in the report but absent from that row (prefix rule against the row's hex tokens) → WARN suggesting the row carry the per-phase split. (Catches the mid-correction state this session actually observed: line 28 corrected, line 111 still single-SHA.)
- **(b3) WARN — best-effort pairing on the token-resolvable subset:** split the row's value cell on `·` / `;`; per segment extract the hex token + the residual label; normalize label tokens (lowercase alnum, `stage-2`→`stage2`); card-side tokens = path components + filename-stem words (split `_`) of the card file under `eval_results/issue_<N>/`, plus sibling `phase` value tokens (split `-_`), minus a small stopword set (`{report, json, upload, done, card, sentinel, results, gate, gates}` — tunable at implementation). If a segment's label tokens hit ≥1 usable card and ALL hit cards agree on one SHA and the segment's hex token is NOT a prefix of it → WARN naming both SHAs + the per-phase-split suggestion. Unresolvable segments (no token hit, or hit cards disagree) are silently skipped, counted in the detail.

**Why coverage (b1) rather than the body's literal row↔card pairing as the FAIL condition** — measured, not stylistic: the grid/anchors phase's card is `gates/pilot_gate_report.json`, whose path and content carry NO token of "grid"/"anchors"/"stage-1" (measured this session), so no honest label→card resolution can pair the incident's own defective segment ("stage-1 grid + margin") with its card — token pairing (b3) run on the round-1 row resolves only the `margin` token, whose SHA matches, and stays silent. Coverage fires on the incident regardless of phase naming: the verdict (CORRECTION 2) states the round-1 draft cited `ba3485b619…` as "the code" *throughout*, i.e. `b4ab6ed5f9…` appeared NOWHERE in the round-1 report, while the corrected report cites it (row + lines 28/83/88). Coverage therefore FAILs round-1 and passes corrected — the exact acceptance pair — and additionally catches every future "one SHA pinned for all phases" report. The pairing residue (both SHAs cited but paired backwards across resolvable labels) is retained as b3-WARN; a swap where labels resolve has no confirmed incident, and free-form phase naming makes a FAIL there a false-positive channel the body's conservative-matcher instruction forbids.

**What check (b) does NOT fire on (conservative-matcher enumeration):**
- Abbreviated (<40-hex), dirty, or `"unknown"` card values — excluded from every FAIL/WARN set, listed in the PASS detail.
- Reports whose issue number is unresolvable — WARN-skip.
- Issues with no cards anywhere — PASS-note N/A.
- A mispaired row segment whose correct SHA is cited elsewhere in the report — b2/b3 WARN at most, never FAIL (the observed mid-correction state).
- A label→card pairing that cannot be resolved by token overlap — silently skipped (the incident's own "stage-1 grid" segment is in this class; coverage is what catches it).
- Card JSONs > 5 MB or unparseable — skipped with a count.
