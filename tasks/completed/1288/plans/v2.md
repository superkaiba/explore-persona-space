**Web prior art (merge queues / merge trains — what transfers):**
- GitHub merge queue and GitLab merge trains solve trunk contention by **serializing only the commit-to-trunk moment while running CI in parallel on speculative post-merge states**. The transferable principle: never serialize the expensive validation (our 9-12 min lint gate ≈ their CI); make the cheap final merge robust to base movement instead.
- Both systems accept that at low queue depth, **optimistic merge + bounded retry** is the cheaper design; full speculative-batching machinery pays off only at high PR volume (10s-100s/day). Our fleet is ≤5 concurrent single-logical-change PRs — the retry-side of the trade.
- GitLab's failure handling (failed train member removed, pipelines restarted for those behind) is the analogue of our re-run-lint-only-on-tip-change rule; our SHA-bound verdict already implements the equivalent invariant (verdict binds to the branch tip, so a sibling landing does NOT invalidate it).

## 11. Decision Rationale

**Why option 3 (squash-first) over options 1 and 2.** Source: task #1288 body + the 07-12 transcript evidence (sessions 004c5304/6fc58be1/aaf2482e/06281fbd) + SKILL.md read today.

- **Option 3 (chosen):** the empirical record is unambiguous — rebase is 0/4 first-try under fleet churn (10/24 the day before), and `--squash` is where every failed session lands anyway, after burning a failed rebase + classification + retry ladder each. GitHub mergeability is merge-method-independent, but rebase can ADDITIONALLY fail (`can't be rebased`, #1041) where squash succeeds — so squash-first strictly dominates for this class: it removes the doomed attempt, removes shape 1 entirely, and shortens the post-recovery ladder. Cost: per-commit revert granularity — nil for a single-logical-change infra branch (it reverts as one commit, which is simpler). The merge-queue prior art supports this shape: make the cheap final merge robust to base movement; never serialize the expensive validation.
- **Option 1 (flock, rejected):** three independent defects. (i) **Structural:** `flock(1)` releases when the holding process exits, and each Bash tool call is a separate process — Step 10d is structurally multi-call (background lint gate + foreground verdict-read + merge call), so a real flock cannot span the window; the alternative (mkdir/pid lock file with TTL) adds a fleet-wedge failure mode. (ii) **Scoping dilemma:** a lock covering the whole certify→merge window serializes the 9-12 min lint gates — ~44 min serial for a 4-fleet, WORSE than the ~30 min it saves; a merge-stretch-only lock does not protect the Guard-1-snapshot→merge window (dominated by the lint gate) and does nothing about the ~100+ marker commits/hr landing on main from NON-Step-10d sources, which move the base regardless. (iii) The SHA-bound verdict already makes sibling merges harmless to certification (it binds to the branch tip, not main's tip) — the lock would protect an invariant that doesn't need protecting.
- **Option 2 (stagger, rejected):** dispatch time ≠ finish time — session durations vary 30 min-to-hours, so staggering dispatch does not stagger merges; one-per-pass costs up to 50 min to drain a 5-batch (10-min watcher cadence × 5); user-spawned concurrent sessions are unprotected. The existing 60 s dispatch stagger (#1059) already handles the cold-load concern it could address.

**Design constants:**
- **Scope = `kind ∈ {infra, batch}`:** exactly the watcher's `INFRA_DRAIN_KINDS` (autonomous_session_watch.py:12542 region) — the population batch-dispatched into same-batch races by construction. Experiments keep `--rebase` (record doesn't cover them; heterogeneous commits retain per-commit revert value; single-variable-change discipline).
- **No BEHIND threshold:** rebase failed at every observed in-batch BEHIND value; a threshold adds an unmeasured predicate for no demonstrated benefit, and the kind-scoping already bounds blast radius.
- **Shape-0 wait ≈ 20 s:** fleet churn ≈ 1 commit/30 s (SKILL.md's own "~100+ marker commits/hr"); one churn interval lets gh's async mergeability recompute settle. Not sensitive within 2×.
- **Shape-0 retry bound = 2:** one retry sufficed for transients in the 07-12 record; 2 gives margin; ≥3 consecutive hits is no longer plausibly timing.
- **Hunk F (recovery always-squash):** grounded in #1041 + the recovery block's own prose (SKILL.md:9950-9952 — the rebase "routinely fails" there and the squash retry is "the documented" endpoint); the hunk removes a documented dead hop, nothing else.
