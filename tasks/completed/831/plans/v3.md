## 3. Method delta (contrast with #821)

#821 serialized the *write* side (parse→mutate→`write_pods_conf`→`cmd_sync` under one flock) and made pods.conf itself atomic + drop-guarded. It did NOT protect (i) the bare `--sync` CLI path, which parses at `main():1553` with no lock and hands that snapshot to `cmd_sync(pods)` at `:1562` — a concurrent upsert landing between parse and sync yields a managed-block rewrite that lacks the new row (the #813 mechanism); (ii) the downstream files themselves — `update_ssh_config` (`:717/:733/:740`) and `update_mcp_config` (`:876`) use bare `Path.write_text` (torn-write hazard). This change moves the lock + a fresh re-read INSIDE `cmd_sync` (covering every present and future caller in one move — the same "sits below the callers" rationale as the reentrancy design at `:390-396`) and gives both downstream writes the `write_pods_conf` tmp+`os.replace` treatment.

### Edit 2 — `scripts/pod_config.py`: atomic-write helper + adoption

New helper next to `write_pods_conf` (after `:674`), mirroring its exact tmp+`os.replace`+cleanup pattern (`:664-673`):

```python
def _atomic_write_text(path: Path, payload: str, *, default_mode: int = 0o600) -> None:
    """Atomically write ``payload`` to ``path`` via same-dir tmp + os.replace.

    Mirrors write_pods_conf's pattern (pod_config.py:652-673). Mode handling:
    if ``path`` exists, its current mode is copied onto the tmp BEFORE the
    replace (a pre-existing 0644 ~/.ssh/config stays 0644); on create, the
    tmp gets ``default_mode`` (0600 — ssh refuses group/other-writable
    configs). No reader ever observes torn content; on a replace failure the
    tmp is best-effort unlinked and the original error re-raised.
    """
    path.parent.mkdir(parents=True, exist_ok=True)
    tmp = path.with_suffix(path.suffix + ".tmp")
    mode = os.stat(path).st_mode & 0o7777 if path.exists() else default_mode
    # v3 (critic-requested): create the tmp WITH the target mode — no
    # umask-window where a 0644 tmp holds ~/.ssh/config content.
    fd = os.open(tmp, os.O_CREAT | os.O_WRONLY | os.O_TRUNC, mode)
    try:
        with os.fdopen(fd, "w") as fh:
            fh.write(payload)
        os.chmod(tmp, mode)  # ensure exact mode even under restrictive umask
        os.replace(tmp, path)
    except OSError:
        with contextlib.suppress(FileNotFoundError, OSError):
            tmp.unlink()
        raise
```

Adopt it at all four bare `write_text` sites:
- `update_ssh_config` `:717` (create), `:733` (replace-block), `:740` (append) → `_atomic_write_text(SSH_CONFIG, ...)` (drop the now-redundant `SSH_CONFIG.parent.mkdir` at `:716`). The `:740` append site composes the FULL payload first (existing content + trailing newline + managed block) and hands the whole string to `_atomic_write_text` — never an append-mode write (v3 note).
- `update_mcp_config` `:876` → `_atomic_write_text(MCP_JSON, json.dumps(data, indent=2) + "\n")`.
- `write_pods_conf` is NOT touched (already atomic; refactoring it under this task would churn the #821 guard tests for zero behavior change).

## Design-question answers

**Q1 — Lock placement: option (a), lock + re-read inside `cmd_sync`.** Verified behavior-preserving for existing locked callers: `cmd_update` calls `cmd_sync(fresh)` immediately after `write_pods_conf(fresh)` (`:1155→:1168`); the upsert/remove paths likewise (`pod_lifecycle.py:498-499`, `:523-524`) — under the (reentrant, `:408-418`) lock nothing can interleave, so a re-read returns what was just written. One deliberate improvement, not a regression: `write_pods_conf` rebinding `pods = list(pods) + readd` (`:622`) does NOT mutate the caller's list, so today a guard-re-added RUNNING row is written to pods.conf but MISSING from the `cmd_sync(rows)` managed block — re-read fixes that inconsistency for free. The minimal-diff alternative (lock only `main()`'s call site) leaves every FUTURE caller free to repeat the bug and misses the guard-re-add fix; rejected.

**Q2 — Merge semantics: NO additive merge; lock + re-read + atomic write suffice.** With the fresh under-lock read, the conf IS canonical, and terminated pods MUST drop from the managed block (`_remove_from_pods_conf` is the legitimate remove path — an additive merge would resurrect dead `Host` entries indefinitely). Residual race: a writer bypassing the lock. Pre-#821 code in a stale worktree resolves its own worktree-local `scripts/pods.conf` SEED, not the live file (`.claude/rules/pod-config.md` § stale-worktree) — it can still overwrite `~/.ssh/config`/`mcp.json` from that months-old seed (this is the best explanation of the stale-MCP-env symptom, see Q4). Mitigation choice: **accept-and-document** — (i) pods.conf itself keeps the never-drop-RUNNING guard, so the canonical source can't lose the row, and the next locked sync regenerates a correct block; (ii) `poll_pipeline.py`'s 10-failure `--refresh-from-api` self-heal restores the downstream configs; (iii) a never-drop-RUNNING-style guard on the SSH block itself would need its own API consult inside `update_ssh_config` and would fight legitimate removals — cost > residual risk. Documented in the rule-file addendum.

**Q3 — Atomic writes:** as Edit 2. Current create-path perms: `SSH_CONFIG.write_text` at `:717` creates with the process umask (typically 0644) — the helper's 0600 create-default is a strict tightening; existing-file mode is copied onto the tmp BEFORE `os.replace` so a replace never flips perms mid-flight.

**Q4 — MCP stale-list symptom:** `update_mcp_config` strips all pod-pattern env keys (`:854`) and regenerates purely from the passed `pods` list — so regenerating from a stale list fully explains a reverted server set mechanically. The grep found NO other writer of `~/.claude/mcp.json` in `scripts/` (`check_mcp_json_no_secrets.py` has zero write calls — read-only checker). **This fix closes:** the current-code unlocked `--sync` stale-snapshot vector CONSISTENT WITH the pod-813 Host drop (v3 hedge: the racing writer was never directly identified — a stale-worktree pre-#821 session syncing from its seed would produce the identical symptom, so "closes the demonstrated current-code mechanism", not "proves the incident root cause"; the Edit-1 audit log makes any recurrence attributable) and torn/partial writes. **It does NOT close:** a sync executed by pre-#821 code in a stale worktree reading its months-old seed pods.conf — the plausible source of the *months*-stale env list (and possibly of the Host drops themselves), dies as worktrees update to HEAD, and is accepted per Q2 (the sweep of stale worktrees is `worktree_audit.py`'s job, out of scope here). Also unclosed (loud-WARNed, niche): the read-only-filesystem fallback where `_resolve_live_pods_conf` returns the SEED — a locked re-read then reads the seed; noted in the rule addendum (v3).

## 7. Kill criteria

- **A `cmd_sync` caller exists that passes rows deliberately different from on-disk state** (e.g. a sync-a-subset or preview caller found by the step-0 grep) — the no-arg re-read signature would silently change its semantics → stop, re-scope to an explicit `rows_override` parameter or per-call-site locking.
- **Lock contention breaks a hot path:** if any high-frequency loop (poller tick, cron) calls `--sync` while a long lock-holder runs, syncs would serialize behind it. `locked_pods_conf` critical sections are ms-scale file rewrites (the one API-consulting path, the drop guard, fires only on a row drop), so this is theoretical — but if the smoke or watcher shows multi-second `--sync` stalls, revisit with a bounded-wait + warn.
- **Perms regression:** if any consumer (ssh itself, MCP server launcher) demands the pre-existing non-0600 mode on a freshly-created file, adjust `default_mode` rather than dropping atomicity.
