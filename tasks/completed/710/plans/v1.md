# Plan — issue #710: add `stall_reason` to the two `_PR` test stubs in `tests/test_issue_dispatch.py`

`kind: infra` workflow-fix. **0 GPU-h. Pure CPU test-stub fix.**

## Goal

Make the two failing router/backend tests pass by adding the missing
`stall_reason` field to the two local `_PR` poll-result test stubs in
`tests/test_issue_dispatch.py` (lines 134 and 1174), so that
`RunPodBackend.poll`'s line `stall_reason=raw.stall_reason`
(`src/explore_persona_space/backends/runpod.py:389`) no longer raises
`AttributeError: '_PR' object has no attribute 'stall_reason'`.

The production code is **correct on `main`**: the canonical
`scripts.poll_pipeline.PollResult` dataclass already carries
`stall_reason: str | None = None` (poll_pipeline.py:766, added in #664),
`backends.base.PollResult` carries it too, and `RunPodBackend.poll` correctly
threads it through. The two failing tests use LOCAL `_PR` dataclass stubs that
monkeypatch `scripts.poll_pipeline.poll_once`; both stubs predate #664 and were
never updated to mirror the new field. The bug is entirely in the test stubs.

## Prior Work / Context

- The bug surfaced when the Claude `code-reviewer` ran the full pytest suite
  during /issue #701 round-2 review and saw `5 failed, 5391 passed`, of which 2

  artifacts, out of scope here).

  stall cause (`"vllm_worker_dead_zombie_gpu"`) through the poll chain. It
  updated the production `PollResult` dataclasses and the `RunPodBackend.poll`

  not updated alongside.

  line 1174) ALREADY asserts `"stall_reason"` is in the serialized output key
  set (lines 1223-1226) — i.e. the test author updated the *assertion* for #664
  but missed updating the *stub* it feeds. So that test is internally
  inconsistent until the stub gains the field.

## §11 Decision Rationale

**No load-bearing hyperparameters.** This is a test-stub field addition with no
model training, no learning rate, no data, no GPU. The single "choice" is the
field default, and it is not a free parameter: it MUST equal the canonical
`scripts.poll_pipeline.PollResult.stall_reason` default of `None` (poll_pipeline.py:766)
so the stub faithfully mirrors the production dataclass the tests are
exercising. Any other default would make the stub diverge from what
`RunPodBackend.poll` / `_serialize_poll_result` actually consume in production.

- **What:** `stall_reason: str | None = None` on each `_PR` stub.
- **Why:** mirror the canonical production field so the typed-`PollResult`
  rebuild (`runpod.py:389`) and the serializer key-set assertion
  (test line 1208-1226) both succeed.
- **Source:** `scripts/poll_pipeline.py:766` (canonical) + #664 (the issue that
  added the field to production).
- **Alternatives rejected:** a `getattr(raw, "stall_reason", None)` defensive
  patch at the production construction site — rejected because it weakens an
  intentional strict-attribute discriminator and masks future stub-drift
  regressions; the in-scope fix is to correct the test stubs, not the
  production code.
