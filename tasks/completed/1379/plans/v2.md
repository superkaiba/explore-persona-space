# Plan — #1379: auto-degrade GCP GPU width (8→4→2) for explicit `sweep-8g` intents on capacity failure

`architectural: false` — no public-contract change: no status enum, marker schema, task.py subcommand, or file relocation is touched; the change adds rungs within the existing GCP ladder (`_gcp_ladder_specs`), one additive CLI flag, and preserves every existing invariant test byte-for-byte on the width-1 and `--gpus N` paths.

## Plan Summary

**What:** Extend the #1121 width-aware GCP ladder so an EXPLICIT `sweep-8g-a100` dispatch (today pinned 8-wide with no fallback) appends degraded-width rungs (4g, then 2g, from `gcp.WIDE_A100_80_BY_WIDTH`) AFTER its 8-wide base rungs and BEFORE the SLURM/RunPod fall-through — matching the `--gpus N` degradation shape. **Fork resolution:** `sweep-8g-h100` is EXCLUDED from degradation (option ii) — its ladder is byte-unchanged; the type-preserving RunPod 8×H100 terminal rung remains its fallback. **Opt-out:** `dispatch_issue.py --width-required` → `spec.extra["width_required"]` pins the full width (the same threading shape as `spot_tolerant`). **Visibility:** no new marker; the existing `epm:backend-selected` extras `requested_gpus` / `realized_gpu_count` / `gcp_ladder_rung` record the degradation — with `requested_gpus` now populated (=8) for explicit wide intents via a small `_declared_width()` helper. **Cap:** worst-case new walk is 9 creates < the 14-rung walk `MAX_GCP_ATTEMPTS_PER_DAY = 16` was sized for — cap unchanged. **Docs:** `.claude/rules/compute-backend-failover.md` § Width-aware rungs, CLAUDE.md § Compute backends, and the gcp.py/router.py comment blocks are updated in the SAME diff. **Compute:** VM-local code change, 0 GPU-h.

Estimated GPU-hours (total): 0

Target pod preference: none (VM-local code change; all verification is `uv run pytest` on the VM).

## 1. Goal + acceptance criteria

(Task #1379 Goal, verbatim.) "On repeated 8-GPU (wide) capacity failure, degrade the GCP GPU width (8→4→2) for EXPLICIT `sweep-8g` intents too — not only for `--gpus N` declarations — so a wide-sweep phase falls back to abundant partial-node capacity instead of starving on empty 8-GPU DWS pools."

This is a `kind: infra` code change (requirement + acceptance criteria, not a hypothesis):

**Acceptance criteria**

- AC1: An `--intent sweep-8g-a100` dispatch (auto lane OR explicit `backend: gcp`) whose 8-wide rungs all capacity-miss at CREATE time advances to `a2-ultragpu-4g` rungs, then `a2-ultragpu-2g` rungs, before any SLURM/RunPod fall-through. Width-major order preserved (all provisioning models at width 8 before width 4, before width 2).
- AC2: `--width-required` pins the intent at its full width — the ladder is byte-identical to today's (no degraded rungs) — and the exhausted walk falls through to SLURM → RunPod exactly as today.
- AC3: `sweep-8g-h100`'s ladder is byte-identical to today's (no degraded rungs of any GPU type); `test_width_ladder_never_emits_h100_machine` stays green UNTOUCHED, and no degraded rung of ANY intent resolves to an `a3-*` machine.
- AC4: Width-1 dispatches and `--gpus N` dispatches produce byte-identical ladders (labels + machine overrides + provisioning models) — the frozen #1121 pins (`test_width1_ladder_byte_identical_explicit_gpus_none_and_matching`, `_W8_LONG_ORDER`, `_W8_SHORT_ORDER`) pass unmodified.
- AC5: A degraded explicit-sweep launch's `epm:backend-selected` marker + handle sidecar carry `requested_gpus: 8` and `realized_gpu_count: <4|2>` (today the marker would read `requested_gpus: null` because `spec.gpus is None` for explicit intents).
- AC6: RunPod-last-rung + no-cascade invariants hold: width degradation stays WITHIN the GCP ladder, before any RunPod/terminal fallback; a GCP workload failure still short-circuits straight to RunPod with no rung cascade.
- AC7: `MAX_GCP_ATTEMPTS_PER_DAY` stays 16 with recorded arithmetic showing the new walks fit (see §Cap interaction).

## 2. Method delta (vs the #1121 ladder as-is)

The #1121 ladder degrades width ONLY for a `--gpus N` declaration: `_requested_wide_widths` (router.py:2470) reads `spec.gpus` and returns `[]` when it is `None` — which it always is for an explicit `sweep-8g-*` intent — so the explicit intents get only their base 8g rungs (LONG: `flexstart_a100_80` + `ondemand_a100_80`; no A100-40 rung — `a100_40_fallback_for_intent` returns `None` for sweep intents) and then fall out of GCP entirely. Delta:

1. NEW `EXPLICIT_WIDE_DEGRADE_INTENTS = frozenset({"sweep-8g-a100"})` in `gcp.py` (beside `WIDE_A100_80_BY_WIDTH` / `WIDTH_ELIGIBLE_INTENTS`, exported in `__all__`).
2. NEW `router._explicit_wide_degrade_widths(spec, base) -> list[int]` — the explicit-intent sibling of `_requested_wide_widths`; returns `[4, 2]` for a degradable explicit wide intent, `[]` otherwise (incl. under `width_required`).
3. `_gcp_ladder_specs` appends the degraded rungs AFTER the base-width rungs (the base rungs at the intent's own 8g machine ARE the width-8 rungs), on every exit path including the caller-pin early return.
4. The existing wide-rung emission loop body is EXTRACTED verbatim into `_wide_rungs_for_widths(spec, widths, *, pinned, short)` and reused by both the #1121 `--gpus` prefix and the new degraded suffix (single source of truth for per-width rung shape/labels).
5. `dispatch_issue.py` gains `--width-required` (threads `extra["width_required"] = True`; refused with exit 2 when combined with `--gpus`).
6. Marker lift sites (router.py ~4924, ~4970) use a NEW `_declared_width(spec)` instead of raw `spec.gpus` (byte-identical for every non-sweep intent).
7. Doc sync in the same diff: `compute-backend-failover.md`, `CLAUDE.md`, gcp.py/router.py comment blocks.

Everything else — length classification, per-rung zone fan-out, headroom pre-check, boot-loop rung skip, queue-timeout/vanish failovers, the RunPod terminal rung, SLURM lane order — is untouched and composes as-is (see §Failover composition).

## 3. Design fork resolution: `sweep-8g-h100`

**Decision: option (ii) — exclude `sweep-8g-h100` from degradation entirely. Only `sweep-8g-a100` degrades.**

Rationale, weighed against the #825 incident:

- **Option (ii) closes the CREATE-MISS half of #825's starvation class at the FIRST dispatch** (the queue-side cycles — flex create succeeds, then #783 queue-timeout / #1116 queue-vanish — exit the ladder before any degraded rung is walked and are NOT closed by this fix; see §5 and A12. The Alternatives critic's independent read of the #825 events found the VISIBLE round-11 cycles were all queue-side, so treat this fix as closing the create-miss shape + achieving `--gpus` parity, never as an end-to-end #825 replay fix). The round-11 MAIN phase dispatched `--intent sweep-8g-a100` first (verified against `tasks/followups_running/825/events.jsonl`: the dispatch line reads `sweep-8g-a100 --boot-disk-gb 250 --max-run-duration 14h --repo-branch issue-825 --workload-cmd ...`; 11 `sweep-8g-a100` mentions vs 1 `sweep-8g-h100`); the H100 request was a hand-improvised second-choice fallback AFTER the A100 pool starved. With the a100 intent degrading 8→4→2 into "abundant" partial-node capacity, the H100 improvisation never happens. The incident evidence that "width mattered more than GPU type" therefore argues for degrading the intent the caller reaches for FIRST — it does not require cross-type degradation of the H100 intent.
- **Cross-type (i) erases a deliberate intent distinction.** `sweep-8g-h100` is documented (gcp.py:430-437) as explicit-`--intent`-only precisely because H100 is a special-cased pool (preemptible quota exactly 8, no on-demand pool, headroom-probe-blind). A caller who picks it over the cheaper, better-covered `sweep-8g-a100` is expressing a GPU-type preference; silently landing them on A100 silicon changes kernels/numerics mid-"fallback" (cf. the gauge-origin-hardware and TF32 gotchas — GPU type is not science-neutral). Under (i) the two sweep intents converge to nearly the same ladder, making the H100 intent's existence misleading.
- **(ii) preserves the H100 invariant VERBATIM.** `test_width_ladder_never_emits_h100_machine` stays green untouched, and its spirit ("no H100 anywhere in a degradation walk") extends cleanly to the new path — pinned by the new sibling test (§Test plan, T5).
- **(iii) — within-H100 specs — is the most work for the least evidence:** it needs a new `a3-highgpu-4g` machine row + zone verification + quota rows on a headroom-blind quota surface, would put `a3-*` machines INSIDE a degradation walk (amending the invariant), and there is no evidence H100 partial-node DWS capacity behaves better than the 8× pool.
- **The H100 starvation case keeps a coherent, type-preserving escape:** `RUNPOD_INTENT_FOR_GCP_INTENT["sweep-8g-h100"] == "sweep-8g-h100"` (router.py:404) — an exhausted H100 sweep falls through to a RunPod 8×H100 pod, same width, same silicon. A caller who genuinely wants width-over-type dispatches `sweep-8g-a100` (now degrading) or `--gpus 8` on a width-eligible intent (already degrading).

The exclusion is recorded in the `EXPLICIT_WIDE_DEGRADE_INTENTS` comment block and in `compute-backend-failover.md` so a future widening is a deliberate, tested change.

**(a) New width helper** (below `_requested_wide_widths`, ~line 2505):

```python
def _explicit_wide_degrade_widths(spec: RunSpec, base: MachineSpec) -> list[int]:
    """Descending DEGRADED widths for an explicit wide degradable intent; ``[]`` otherwise.

    The explicit-intent sibling of :func:`_requested_wide_widths` (#1379):
    an ``EXPLICIT_WIDE_DEGRADE_INTENTS`` dispatch (``sweep-8g-a100``) whose
    full-width rungs all capacity-miss degrades onto the narrower
    :data:`gcp.WIDE_A100_80_BY_WIDTH` machines (8->4->2) instead of
    starving on the single scarcest config (#825: 2.5h+ stuck on two empty
    8-GPU DWS pools while 4x/2x capacity was abundant). ``[]`` when:
    the intent is not degradable; ``spec.gpus`` names a DIFFERENT width
    (the --gpus path owns width then — pre-route guard refuses mismatches
    anyway); or the caller pinned the width via
    ``spec.extra["width_required"]`` (dispatch_issue.py --width-required —
    a shared-nothing 8-way memory/parallelism need that cannot re-shard).
    """
    if spec.intent not in EXPLICIT_WIDE_DEGRADE_INTENTS:
        return []
    if spec.gpus is not None and int(spec.gpus) != base.gpu_count:
        return []  # unreachable via dispatch_issue (guard refuses), safe for library callers
    if bool((spec.extra or {}).get("width_required")):
        logger.info(
            "route: width_required set — explicit wide intent %r pinned at %dx; "
            "no width degradation (#1379).",
            spec.intent,
            base.gpu_count,
        )
        return []
    return [w for w in sorted(WIDE_A100_80_BY_WIDTH, reverse=True) if w < base.gpu_count]
```

(`spec.gpus == base.gpu_count` — a redundant-but-legal `--gpus 8 --intent sweep-8g-a100` — still degrades: `--gpus` DECLARES a shardable axis per #1121, so degradation is contract-consistent there.)

**(b) Extract the wide-rung emission loop.** The body of the existing `for w in wide_widths:` loop in `_gcp_ladder_specs` (lines 2650-2677) moves VERBATIM into:

```python
def _wide_rungs_for_widths(
    spec: RunSpec, widths: list[int], *, pinned: str | None, short: bool
) -> list[tuple[RunSpec, str]]:
    """(spec, label) rungs at each width in ``widths`` (width-major, intra-width
    per the length-aware order / caller pin) — shared by the #1121 --gpus wide
    PREFIX and the #1379 explicit-intent degraded SUFFIX."""
    rungs: list[tuple[RunSpec, str]] = []
    for w in widths:
        m = WIDE_A100_80_BY_WIDTH[w]
        if pinned is not None:
            wide_pinned_model = str(pinned).upper()
            wide_prefix = {"SPOT": "spot", "FLEX_START": "flexstart", "STANDARD": "ondemand"}.get(
                wide_pinned_model, wide_pinned_model.lower()
            )
            rungs.append(
                (_with_machine(spec, m, provisioning=wide_pinned_model),
                 f"{wide_prefix}_{_machine_label(m)}x{w}")
            )
            continue
        if short:
            rungs.append(
                (_with_machine(spec, m, provisioning="SPOT"), f"spot_{_machine_label(m)}x{w}")
            )
        flex_spec, _flex_base_label = _flex_start_rung(spec, m)
        rungs.append((flex_spec, f"flexstart_{_machine_label(m)}x{w}"))
        rungs.append(
            (_with_machine(spec, m, provisioning="STANDARD"), f"ondemand_{_machine_label(m)}x{w}")
        )
    return rungs
```

def _declared_width(spec: RunSpec) -> int | None:
    """Caller-DECLARED GPU width for the handle/marker record (#1121/#1379):
    ``spec.gpus`` when set; else the explicit wide intent's own base width

## 5. Failover-trigger composition (verified against `.claude/rules/compute-backend-failover.md`)

- **Create-time capacity miss (the shape this fix targets):** each 8-wide rung's miss advances the walk; the degraded rungs are ordinary ladder rungs, so per-rung multi-zone fan-out, the headroom pre-check (free skip, `quota_headroom_insufficient`), and the daily-cap accounting apply to them unchanged.
- **#783 queue-timeout / #1116 queue-vanish:** UNCHANGED and NOT closed by this fix — a flex create that SUCCEEDS (queues) ends the ladder walk (`route()` returned a handle), so a queued-then-timed-out/vanished 8g flex rung fails over to RunPod at the requested width, exactly as #1121 documents for `--gpus` dispatches. #825 exhibited BOTH shapes (create-time `no_compute_available` AND queue-vanish); this fix closes the create-miss cycles. Poller-side width-degrade re-entry is the already-named deferred follow-up (#1121 plan) — out of scope here (recursion guard: not required for this fix's correctness).
- **#1029 boot-loop rung skip:** composes cleanly — streaks key on rung LABELS, and the degraded labels (`flexstart_a100_80x4` etc.) are the same label vocabulary the #1121 wide rungs already use; a boot-looping 8g rung gets same-day skipped, letting the walk reach the degraded rungs without burning creates.
- **Workload failure (sync + async):** short-circuits straight to RunPod with no rung cascade — untouched (the degradation only exists inside the ladder walk, which a workload failure never re-enters).
- **RunPod terminal rung:** `sweep-8g-a100` has an identity translation row (router.py:403) — unchanged behavior after full exhaustion.

## 11. Decision Rationale

- **Hook point = `_gcp_ladder_specs`, degraded rungs as a post-base-tail SUFFIX.**
  What: append `_wide_rungs_for_widths(spec, [4, 2], ...)` after the base rungs on every exit path. Why: the base rungs at the intent's own 8g machine ARE the width-8 rungs, so a suffix preserves width-major order with zero duplicate creates; both ladder consumers (`_attempt_gcp_lane` and `_override_free_or_gcp` — the latter per the `_gcp_ladder_specs` docstring, router.py:2510-2513) inherit it for free (the #654 identical-fallback contract). Source: read `router.py:2507-2733` + the #1121 design (`compute-backend-failover.md` § Width-aware rungs). Alternatives: (a) normalize the explicit intent into `wide_widths=[8,4,2]` — rejected: the base tail would then re-emit a duplicate 8g rung or need suppression, a larger structural change; (b) poller-side degrade-on-queue-timeout — rejected as out of scope (the #1121 named deferred follow-up; this fix targets create-time misses).
- **Fork resolution = option (ii), exclude `sweep-8g-h100`.** What/Why/Source/Alternatives: §3 in full. Source: `tasks/followups_running/825/events.jsonl` (the a100 intent was the primary dispatch; 11 vs 1 mentions), `gcp.py:423-437` comments, `test_router.py:4168` invariant, `router.py:403-404` translation rows.
- **Opt-out surface = `spec.extra["width_required"]` via `--width-required`.**
  What: a boolean extra, threaded exactly like `spot_tolerant` (`dispatch_issue.py:1259-1267`). Why: smallest surface consistent with existing per-dispatch behavior flags; per-dispatch (not per-intent or env) because width-requiredness is a property of the workload, not the fleet. Source: read `dispatch_issue.py` extra-threading block; `_is_short_job`'s `spot_tolerant` read (`router.py:2407`). Alternatives: (a) env var `EPS_GCP_NO_WIDTH_DEGRADE` — rejected: fleet-global where the need is per-job; (b) a new non-degrading intent alias (`sweep-8g-a100-pinned`) — rejected: intent-vocabulary growth + `RUNPOD_INTENT_FOR_GCP_INTENT` completeness-test churn for a boolean.
- **`--width-required` + `--gpus` = exit-2 refusal.** What: fail loud on the contradictory combination. Why: `--gpus` declares a re-shardable axis (#1121 contract); silently ignoring either flag violates fail-fast. Source: the #599 `gpus_machine_mismatch` guard precedent (`dispatch_issue.py:695-737`). Alternative: honor it by clamping `wide_widths` to the requested width only — rejected for v1 (touches `_requested_wide_widths` semantics + byte-identity pins; separate follow-up if demand appears).
- **Visibility = existing `epm:backend-selected` extras, `requested_gpus` populated via `_declared_width`.** What: two call-site substitutions + one helper. Why: the #1121 fields (`requested_gpus`/`realized_gpu_count`/`gcp_ladder_rung`) already form the re-shard contract the workload reads; only the `requested_gpus: null` gap needs closing for explicit intents; no new marker kind (a deliberate planner deviation from body Proposed-change bullet 3 — see §4.2(d) — riding #1121's "additive extra fields, no marker SCHEMA change" precedent, router.py:4967-4971). Alternative: an `epm:progress` note from the router (candidate sketch) — rejected: the router posts exactly one marker kind today; a second emission path is new schema surface for information the existing marker already carries.
- **Cap = unchanged 16.** What/Why: §7 arithmetic (worst new walk 9 < 14). Source: `test_max_gcp_attempts_per_day_is_sixteen` docstring + `compute-backend-failover.md` ladder-order section. Alternative: raise to accommodate two same-day 9-rung walks — rejected: the pre-existing 14-rung walk already exceeds the cap on a same-day retry by design (the cap is a brake, not a per-dispatch guarantee).
- **Degrade floor = width 2 (no 1× rung).** What: degraded widths are `[4, 2]` only. Why: the canonical Goal names 8→4→2; a 1× machine for an 8-wide sweep is an ~8× wall blowout that outruns the dispatch's own `--max-run-duration` fence (#825's was 14h) — a degradation that likely converts capacity starvation into a runtime-fence kill. Source: Goal text; `WIDE_A100_80_BY_WIDTH` keys (2/4/8, `gcp.py:500-504`).
