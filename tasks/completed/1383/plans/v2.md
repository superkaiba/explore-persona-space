## 1. Goal

> Extend the verified-at-filing binding rule in `.claude/rules/workflow-fix-on-bug.md` so a presence-grep must bind on CONTEXT as well as count: a hit whose surrounding context already implements the proposed change means the fix is already landed — re-read the hit's context before filing.

(Task #1383 body `## Goal` H2, verbatim; `kind: infra`, no `goal:` frontmatter by design. Re-read at plan-return time 2026-07-16 — unchanged.)

One paragraph: the verified-at-filing mandate currently binds a filing-time grep to the bug claim on hit COUNT (per-target hits, #1307) and on RELOCATION (repo-wide grep before nonexistence claims, #1290/#1296). It has no clause requiring the filer to READ a presence-hit's surrounding lines, so a grep that hits the very paragraph that already implements the proposed change still "verifies" the filing — which is how #1330 was filed as a duplicate of the already-landed #1309 fix. This task adds the missing context-consistency clause.

## 2. Prior work / lineage

The binding rule's progression, all in-repo (no literature search applicable — internal workflow surface):

- **#1272** — introduced the `verified-at-filing:` line: every wf-fix body carries the filing-time grep command + hit count (or `n/a — <reason>`). Motivated by #1221/#1229/#1249 (three stale-claim filings in two days, each burning a spawned session's verification rounds).

The filer's verified-at-filing grep HIT the landed recipe paragraph itself (count-binding satisfied — the pattern was present, per-target hits stated), but the hit's CONTEXT was misjudged as unrelated. Count-binding alone passed a duplicate filing because clauses (a)/(b) only constrain hit ARITHMETIC (counts per target, repo-wide coverage), never hit SEMANTICS (what the surrounding text says). #1330 was archived as a duplicate; the parked formal candidate on its events.jsonl (2026-07-15T06:57:11Z) is this task's origin, routed by the /daily Step C parked-candidate pass.
