## 2. Prior Work

### POSIX `O_APPEND` write atomicity (the property the fix leans on)

- **POSIX.1-2017 / `write(2)`:** "If the `O_APPEND` flag of the file
  status flags is set, the file offset shall be set to the end of the file
  prior to each write and no intervening file modification operation shall
  occur between changing the file offset and the write operation." This is
  what makes concurrent appends from multiple writers not clobber each
  other's offset.
- **Linux man-pages `write(2)` BUGS / `pipe(7)`:** atomicity of a single
  `write()` is guaranteed up to `PIPE_BUF` bytes (`PIPE_BUF = 4096` on
  Linux; confirmed on the EPS VM below). For a regular file opened
  `O_APPEND`, a single `write(fd, buf, n)` with `n ≤ PIPE_BUF` lands
  atomically with respect to other appenders. ABOVE `PIPE_BUF`, the kernel
  may split the write, and a concurrent appender's bytes can interleave —
  POSIX does NOT promise atomicity there even with `O_APPEND`. Hence the
  oversize path must rely on a separate exclusion mechanism (the flock the
  callers already hold) plus a loop that completes the full buffer. NOTE
  (the v2 narrowing): the flock + completion loop give MUTUAL-EXCLUSION
  (no interleaving with concurrent writers) and BUFFER COMPLETION (the loop
  finishes the buffer despite short writes), but they do NOT give
  CRASH-ATOMICITY against a SIGKILL delivered between two `os.write` calls
  in the loop — the first call's bytes are already on disk and the second
  never runs. The >PIPE_BUF case therefore relies on the tolerant reader for
  crash recovery, not on the write being all-or-nothing.
- **Signal interruption:** a `write(2)` interrupted by a signal that
  arrives BEFORE any byte is written returns `-1`/`EINTR` (nothing
  written); a signal arriving mid-write returns a SHORT count (the bytes
  already written). With SIGKILL specifically the process dies, so for the
  ≤PIPE_BUF single atomic write the kernel either has committed it or it has
  not — there is no torn-line state for the common case. The current
  `f.write(...)` via buffered Python `io` is the failure mode: the write
  can be split across multiple underlying `write(2)` syscalls and the
  buffer flushed in pieces, so a kill between flushes leaves a partial
  line — exactly the 129-byte fragment observed on #653.

### 3.1 New helper

Add near the other private file helpers (just above `post_event`, ~line 987),
so it is in scope for all callers:

```python
# Linux atomic-append bound: a single write(2) of <= PIPE_BUF bytes on an
# O_APPEND fd lands atomically w.r.t. concurrent appenders AND is all-or-
# nothing against a SIGKILL (the kernel either commits the one syscall or it
# does not). POSIX.1-2017 write(2); Linux pipe(7) PIPE_BUF. ABOVE this bound a
# single write may be split, so we keep the caller's flock (excludes other
# writers) and complete the buffer in a loop. The loop is NOT crash-atomic:
# a SIGKILL between two os.write calls can leave a partial line — recovery for
# the oversize case is the tolerant reader (_iter_jsonl), which skips it.
# Confirmed PIPE_BUF == 4096 on the EPS VM (Linux 6.8).
_PIPE_BUF = getattr(os, "PIPE_BUF", 4096)


def _append_jsonl_line(path: Path, payload: dict[str, Any]) -> None:
    """Atomically append one JSON object as a line to an append-only log.

    Serializes ``json.dumps(payload, ensure_ascii=False) + "\\n"`` in memory,
    then writes the whole buffer to ``path`` opened ``O_WRONLY|O_APPEND|O_CREAT``.

    For buffers <= PIPE_BUF the single ``os.write`` is atomic against other
    appenders (POSIX) AND against a SIGKILL/OOM mid-call (the one syscall
    lands the full line or nothing — never a partial line).

    For OVERSIZE buffers (rare: a large note plus artifacts list, > PIPE_BUF)
    POSIX promises neither single-write atomicity nor all-or-nothing across
    multiple ``os.write`` calls if the process is killed mid-loop. This path
    relies on the caller already holding ``_locked()`` to exclude other
    writers (no interleaving) and a write-completion loop to finish the
    buffer despite short writes — but it is NOT crash-atomic: a SIGKILL
    between two ``os.write`` calls CAN leave a partial trailing line on disk.
    Recovery for that case is the tolerant reader (``_iter_jsonl``), which
    skips the partial line. The loop is still useful for completion under
    EAGAIN/EINTR/short-writes; it is not a crash-atomicity guarantee.

    Callers MUST hold ``_locked()``.
    """
    path.parent.mkdir(parents=True, exist_ok=True)
    line = json.dumps(payload, ensure_ascii=False) + "\n"
    buf = line.encode("utf-8")
    fd = os.open(path, os.O_WRONLY | os.O_APPEND | os.O_CREAT, 0o644)
    try:
        if len(buf) <= _PIPE_BUF:
            # Single atomic append (<= PIPE_BUF): all-or-nothing against a
            # SIGKILL. os.write may legally short-write even here in
            # principle; assert the whole line landed so a truncation can
            # never pass silently.
            n = os.write(fd, buf)
            if n != len(buf):
                raise OSError(
                    f"short atomic append to {path}: wrote {n} of {len(buf)} bytes"
                )
        else:
            # Oversize line (> PIPE_BUF): caller's flock excludes concurrent
            # writers (no interleaving); complete the buffer despite short
            # writes. os.write already retries EINTR internally on py3.5+, so
            # a returned short count is a genuine partial flush to finish, not
            # an EINTR retry. NOT crash-atomic — a mid-loop SIGKILL can leave
            # a partial line; the tolerant reader recovers it.
            view = memoryview(buf)
            written = 0
            while written < len(buf):
                written += os.write(fd, view[written:])
    finally:
        os.close(fd)
```

Notes on the helper contract:
- **`O_CREAT` with `0o644`** replaces the implicit creation in
  `path.open("a")`; `path.parent.mkdir(parents=True, exist_ok=True)`
  preserves the existing dir-creation behavior in `post_event`/`add_comment`.
- **`ensure_ascii=False`** preserves the exact serialization the current
  sites use (so the on-disk bytes are unchanged for the common case).
- The helper does NOT acquire the flock and does NOT commit — it is a pure
  write primitive. Every caller already runs under `_locked()` and calls
  `_git_commit(...)` itself; the helper only replaces the
  `with path.open("a") as f: f.write(...)` two lines. This keeps the
  flock + single-commit semantics (an explicit Constraint in the task body)
  untouched.
- **Why a code path, not a model call:** N/A — this is a pure POSIX I/O
  primitive, no unstructured-data heuristic.

### 3.3 Tolerant readers

Add one private parse helper and route the FOUR readers through it:

```python
import logging  # add to the import block at top of module (alphabetical, after json)

_log = logging.getLogger(__name__)


def _iter_jsonl(path: Path) -> list[dict[str, Any]]:
    """Parse an append-only JSONL file, tolerating malformed lines.

    A line that does not round-trip through ``json.loads`` is SKIPPED and
    logged at WARNING (this is the recovery path for a partial trailing line
    left by a writer killed mid-append, the historical #653 corruption, AND
    the >PIPE_BUF oversize-append crash case which is NOT write-atomic).
    All malformed lines are tolerated, not just the trailing one: an
    append-only log can only ever grow a bad line at the tail, so a
    mid-file bad line is implausible, and the practical recovery a reader
    needs is "return everything parseable" — raising on a mid-file anomaly
    would re-introduce exactly the hard-crash this fix removes.
    """
    if not path.exists():
        return []
    out: list[dict[str, Any]] = []
    for lineno, line in enumerate(path.read_text().splitlines(), 1):
        if not line.strip():
            continue
        try:
            out.append(json.loads(line))
        except json.JSONDecodeError as e:
            _log.warning(
                "skipping malformed line %d in %s: %s", lineno, path, e
            )
    return out
```

Then:
- `list_events` (line 1041-1045) → `return _iter_jsonl(path)`.
- `list_comments` (line 1906-1910) → `return _iter_jsonl(path)`.
- `_next_event_version` (line 964-985) → iterate
  `for row in _iter_jsonl(events_path):` (it currently `json.loads(line)`

def test_concurrent_appends_never_interleave_partial_line(fake_repo):
    """N concurrent process appenders (serialized by the global flock) must
    never produce a torn line; every line round-trips through json.loads.

    NOTE: this gates the flock's no-interleaving property only. It does NOT
    gate the single-os.write atomicity A1 relies on — see T-C, which gates
    the mechanism directly."""
    _, tw = fake_repo
    nid = tw.create_task(tw.NewTaskRequest(kind="infra", title="t"))
    n_writers, per_writer = 8, 12

    def worker(wid):
        for i in range(per_writer):
            tw.post_event(nid, f"epm:w{wid}", by="t", note=f"{wid}-{i}")

    with concurrent.futures.ThreadPoolExecutor(max_workers=n_writers) as ex:
        list(ex.map(worker, range(n_writers)))

    ev = tw.find_task_path(nid) / "events.jsonl"

    assert posted == n_writers * per_writer   # no lost/duplicated lines

def test_small_append_is_exactly_one_os_write(fake_repo, monkeypatch):
    """The <= PIPE_BUF path MUST perform exactly ONE os.write of the full
    serialized line. A buffered or multi-write refactor would reintroduce the
    #653 torn-line bug on SIGKILL yet pass the flock test (T-B); this catches
    that regression at the mechanism level."""
    from explore_persona_space import task_workflow as twmod

    calls: list[tuple[int, int]] = []
    real_write = os.write

    def counting_write(fd, data):
        calls.append((fd, len(data)))
        return real_write(fd, data)

    monkeypatch.setattr(twmod.os, "write", counting_write)

    tmp = tw_tmp_path(fake_repo) / "small.jsonl"   # a small payload path
    payload = {"ts": "2026-06-28T00:00:00Z", "kind": "epm:x", "version": 1, "by": "t"}
    line = json.dumps(payload, ensure_ascii=False) + "\n"
    expected = len(line.encode("utf-8"))
    assert expected <= twmod._PIPE_BUF             # precondition: small path

    twmod._append_jsonl_line(tmp, payload)

    assert len(calls) == 1                          # EXACTLY one os.write
    assert calls[0][1] == expected                  # of the full line length
    assert tmp.read_text() == line                  # round-trips on disk

## 10. Decision Rationale

N/A — no model training, no hyperparameters. The load-bearing design
choices and their grounding:

- **What:** Single `os.write` on an `O_APPEND` fd for the ≤PIPE_BUF case.
  **Why:** It is the POSIX-guaranteed atomic-append primitive (no torn
  line under concurrent writers OR a kill, for buffers ≤ PIPE_BUF), and is
  the minimal change to the existing per-site `f.write(json.dumps(...))`
  two-liner.
  **Source:** POSIX.1-2017 `write(2)` (O_APPEND offset+write atomicity);
  Linux `pipe(7)` (`PIPE_BUF` atomicity bound) + `write(2)` BUGS.
  **Alternatives rejected:** (a) tmp-file + atomic rename per append —
  forces a full read-rewrite of a growing log on every event, O(N) per
  append, wrong for an append-only file; (b) `fsync` after each write —
  durability, not atomicity; does not prevent a torn line and adds latency.
- **What:** Keep the existing global `_locked()` flock + a completion loop
  for the oversize (>PIPE_BUF) path, AND narrow the crash-atomicity claim
  (A1) to ≤PIPE_BUF only. **Why:** POSIX does not promise single-write
  atomicity above PIPE_BUF even with O_APPEND, and the flock + multi-write
  loop give mutual-exclusion + buffer-completion but NOT all-or-nothing
  against a SIGKILL delivered between two `os.write` calls — so claiming the
  >PIPE_BUF path is crash-atomic (as v1 did) would be an overclaim. The
  honest design: the >PIPE_BUF path is best-effort completion, and crash
  recovery for it is the tolerant reader (which skips the partial line).
  **Source:** Linux `write(2)` (no >PIPE_BUF atomicity guarantee);
  Phase 2 Statistics + Alternatives reconcilers (binding).
  **Alternative SUGGESTED and rejected (per the reconciler):** switching the
  >PIPE_BUF path to tmp-file + atomic rename. The reconciler explicitly
  noted this is OVERKILL for the common case — events larger than 4 KB are
  rare (`EVENT_NOTE_MAX`=50 KB is a hard cap, not the typical size), and
  when one IS killed mid-loop the tolerant reader recovers the file. tmp+
  rename would add a full-file read-rewrite cost and a second durability
  idiom to reason about, to crash-protect a rare path that the reader
  already covers. Recovery via the tolerant reader is sufficient; this
  revise round does NOT switch the recipe — it only narrows the A1 claim to
  match what the recipe actually guarantees.
  **Alternative also rejected:** per-file `fcntl.flock` on the events file
  itself — redundant with the global lock the callers already acquire, and
  adds a second lock to reason about.
