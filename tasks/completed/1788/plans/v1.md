# Plan v1 — task #1788: Guard-4 `grep -Fxq` needs `--` (false LOST-UPDATE)

architectural: false

## Goal / requirement

Add the `--` end-of-options separator to the Step 10d Guard-4 (lost-update
refusal, #1713) membership grep in `.claude/skills/issue/SKILL.md` so
main-added lines beginning with `-` (markdown bullets — ubiquitous on the
workflow surface the guard scans) are matched as PATTERNS, not parsed as
grep options.

**Bug (reproduced live twice, 2026-07-28):** the fenced Guard-4 recipe pipes
each main-added line into `grep -Fxq "$ADD_LINE"`. Any line starting with
`-` makes grep error (`invalid option`), the non-zero rc counts the line as
`MISSING_ON_BRANCH`, and Guard 4 false-fires a LOST-UPDATE REFUSAL on a
branch whose file is byte-identical to `origin/main` (#1742: 3 phantom
misses naming `.claude/rules/planner-section-reference.md`; #1758: 3
phantom misses, clean rerun after adding `--`).

## Acceptance criteria

1. SKILL.md's Guard-4 fenced block runs `grep -Fxq -- "$ADD_LINE"` (the
   separator present); a dash-leading pattern is treated as a fixed-string
   full-line pattern.
2. The Guard-3 `ON_MAINLINE` pipe is hardened in lockstep:
   `grep -Fxq -- "$MB"` (defense-in-depth — `$MB` is a hex SHA and cannot
   start with `-` today, but the filing scope says fix all sites in
   lockstep so a future copy-run of either fenced block carries the safe
   form).
3. The Guard-4 prose mention of the predicate reads `` `grep -Fxq --` `` so
   the description matches the recipe (prevents re-introduction by a future
   editor copying the prose).
4. No other dash-unsafe variable-pattern `grep -Fxq`/`-qxF` site remains in
   the workflow surface (verified at clarify time: SKILL.md:10528 is the
   only one; hooks already carry `--`; `"$CANON"` / literal-pattern sites
   are dash-safe by construction).
5. Smoke evidence: the fixed pipe returns rc 0 for a dash-leading line that
   IS present and rc 1 for one that is NOT, with no `invalid option` error
   (a 3-line stdin fixture is sufficient).
