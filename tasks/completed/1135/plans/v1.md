  `CVD=<slot>` per cell, call chain `build_organism(...) ->
  build_train_config(gpu_id=0) -> train_lora`; 4 parallel cells co-located on
  GPU 0 -> 14/34 cells rc=2 CUDA-OOM (7 GPUs idle). A further 19

  the entry must scope the clobber's signature to the OOM fan-out only.
  Marker: `epm:new-bug-class v3 cvd_clobber_library_train_seam` on #1090.
  Diagnostic signature: CUDA-OOM fan-out across co-scheduled cells whose OOM
  messages list sibling PIDs while N-1 GPUs sit idle — cells get far enough to
  allocate, then OOM (distinct from the hand-launch entry's signature, where
  engines crash at init on the busy DEFAULT GPU).
- Shape (b) dispatcher-poisoning: #1112 (2026-07-07T23:37Z): `phase_train` ran
  an s2 LoRA cell IN-PROCESS in the dispatcher; the clobber poisoned the
  dispatcher env; s3 full-FT compose read `torch.cuda.device_count()` == 1 ->
  `--num_processes 1` against the 4-GPU ZeRO-3 yaml (zero sharding; whole 7B
  params+grads+Adam on GPU 0; OOM at 75.86 GiB used / 3.84 GiB alloc), AND
  `_run_subprocess(env={**os.environ})` propagated `CVD=0` into the child.
  Marker: `epm:new-bug-class v2 ft_zero3_num_processes_cvd_clobber` on #1112.
  Diagnostic signature: a full-FT/multi-GPU compose "sees 1 GPU" after any
  in-process training ran earlier in the same dispatcher process.
- RULEs: (i) library callers thread `gpu_id=<slot>` through the config to
  MATCH the env pin — never default 0 under a nonzero pin; (ii) a dispatcher
  that later composes multi-GPU launches never calls `train_lora` in-process —
  subprocess-isolate the training, or snapshot CVD at import time and
  enumerate GPUs via an `nvidia-smi` subprocess (never
  `torch.cuda.device_count()`, which reads the clobbered env and caches);
  (iii) world size for a sharded launch is pinned to the accelerate yaml's
  `num_processes`, never derived from a clobbable runtime count.
- Fix status (durable anchors are file paths + incident ids, not branch SHAs):
