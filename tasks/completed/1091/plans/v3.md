**New bullet 1 (verbatim):**

> - **Post-teardown orphan-GPU-pid guards that self-exclude by `os.getpid()` are UNSOUND on host-pid-namespace containers (RunPod) — and a single-shot probe races the SIGKILL→driver-release window; use a bounded DRAIN LOOP over a residual `used_memory` floor instead.** Two defects in the natural in-process check (step (b) of the in-process-teardown entry above: query `nvidia-smi --query-compute-apps=pid`, exclude your own pid, FAIL LOUD on the rest): (1) inside a container whose view of the driver is the HOST pid namespace, NVML reports HOST-namespace pids while `os.getpid()` returns the CONTAINER pid (documented upstream: NVIDIA/nvidia-docker#1483), so pid-equality self-exclusion can NEVER match — the process's OWN CUDA context reads as an "orphan"; (2) a probe that runs exactly once lands inside the normal window between SIGKILL-ing the engine child and the driver releasing its accounting entry, so even a CLEAN teardown reads as a leak. Diagnostic signature: the teardown's "orphan GPU-holding PIDs" RuntimeError fires on EVERY cell immediately after a successful kill, and the reported pid does not exist in the container's own `/proc`. RULE: make the check a bounded DRAIN LOOP with a residual-floor verdict — poll `nvidia-smi --query-compute-apps=pid,used_memory,gpu_uuid` every ~2 s up to a timeout (`EPM_VLLM_TEARDOWN_DRAIN_TIMEOUT_S`, default 60 s); PASS when no foreign pid remains on the CVD-visible devices OR the total foreign `used_memory` is ≤ a residual floor (`EPM_VLLM_TEARDOWN_RESIDUAL_FLOOR_MIB`, default 6144 MiB — tolerates the caller's own CUDA context surfacing under a host pid, still catches a real orphaned engine, which holds ≥ the model weights — tens of GiB for the 7B-class models this repo runs; RE-DERIVE the floor for models whose weights approach it); an unparseable `[N/A]` `used_memory` counts as ABOVE-floor; on timeout stay FAIL-LOUD with per-pid `used_memory` + elapsed. Keep the #396 BF9 CVD-aware `gpu_uuid` scoping unchanged — this fixes pid identity + probe timing, not device scoping. Also cut teardown EXPOSURE where the workload allows: a LoRA dose ladder shares ONE `enable_lora` engine across adapter checkpoints (per-call `LoRARequest`, distinct stable `lora_int_id`) instead of teardown+rebuild per checkpoint. Reference implementation: `src/explore_persona_space/experiments/behavior_testbed_545/eval_battery.py` — `teardown_vllm` + `_teardown_drain_verdict` + `_parse_compute_app_rows` — and the shared-LoRA engine in `src/explore_persona_space/artifacts/organisms.py` `_default_vllm_generate_fn` (both in commit `08895b8e3a` on `issue-1090`; the Step-10d rebase-merge may rewrite branch SHAs — the durable anchors are the file paths + incident #1090). **New bullet 2 (verbatim):**

> - **Recursive psutil child kill-sweeps in vLLM teardown kill the `wandb-core` service as collateral — the NEXT `wandb.init` in the SAME process then dies with `ConnectionResetError: Connection lost` (surfacing at HF Trainer `on_train_begin`).** Step (a) of the in-process-teardown entry above (`psutil.Process().children(recursive=True)` → terminate/kill) sweeps ALL children of the driver — but modern wandb (core architecture; 0.25.0 in-repo) runs its `wandb-core` service as a persistent CHILD of the same driver process, so the sweep kills it alongside the engine workers, and the service is not respawned: the next `wandb.init` reuses the dead service's socket and raises `ConnectionResetError: Connection lost`.
