# Plan — Task #1644: call `load_dotenv()` before heavy imports in the three `issue1586_*.py` entrypoints

## Goal

Call `explore_persona_space.orchestrate.env.load_dotenv()` before any heavy import in the three `scripts/issue1586_*.py` entrypoints so `tests/test_shared_vm_thread_caps.py::test_no_new_torch_before_dotenv_vm_entrypoints` is green on main. (Task #1644 Goal, verbatim.)

This is the #847 shared-VM thread-caps convention: `load_dotenv()` setdefaults `OMP/MKL/OPENBLAS/NUMEXPR_NUM_THREADS` on the shared VM, and torch/BLAS freeze their pools from those vars at import time — a heavy import before the call binds uncapped pools in-process. Reference recipe: commit `ab75ff5b05` (issue-1619, PR #1395), which fixed the identical violation in 3 issue1092 figure scripts. Mirror it exactly.

## Design

Test detection logic (verified by reading `tests/test_shared_vm_thread_caps.py`): a target file FAILs when its earliest MODULE-LEVEL import whose root (`name.split(".")[0]`) is in `HEAVY_IMPORT_ROOTS` (`torch, numpy, matplotlib, pandas, scipy, sklearn, seaborn, transformers, datasets, statsmodels, vllm, peft, trl`) precedes the first line containing the substring `load_dotenv(`. So the inserted `load_dotenv()` CALL line must sit above the first heavy-import line. `explore_persona_space.*` imports are NOT heavy roots (deliberately scoped out, per the test's #1146 comments), so the wrapper import itself is safe anywhere.

Per file (each as ONE Edit so the ruff PostToolUse F401 auto-fix never sees an unused `load_dotenv` import):
