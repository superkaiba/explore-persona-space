## Goal / Requirement

A pod-side (re)launch executed over ssh must never keep the orchestrator's local ssh
wrapper alive as an implicit signal: the pid file + log breadcrumbs are the signal, and
the wrapper must RETURN within seconds. Amend `.claude/rules/pod-side-reporting.md`
§ Pid-file launch contract with a new item **1f** mandating FULL stdio detach (all three
fds) on every ssh-remote (re)launch, naming the `&`-precedence trap on `a && b` list
shapes, and recording the #1768 relaunch-#4 incident as the worked example. Update the
two sibling prose surfaces whose wording under-states the mandate (item 1d's
launcher-less snippet; `experimenter.md`'s "full detachment trio" line).

### Acceptance criteria

1. `.claude/rules/pod-side-reporting.md` § Pid-file launch contract gains a new item
   **1f** ("Full stdio detach on every ssh-remote (re)launch") stating, at minimum:
   - The remote launch command MUST redirect ALL THREE stdio fds in the same command:
     `< /dev/null` AND `> <log> 2>&1` (or `>> <log> 2>&1`). `setsid` + `nohup` alone do
     NOT release the ssh channel: sshd waits for EOF on the remote stdout/stderr, so a
     detached child that inherits those fds keeps the channel open and the LOCAL ssh
     client hangs indefinitely (standard ssh fd semantics; same-run corroboration:
     #1768 `epm:failure-lesson v2` — "it holds the ssh channel open so the local client
     hangs").
   - The local wrapper's lifetime is NEVER a signal. A launching session must not wait
     on the ssh call beyond a bounded `timeout` (recommended backstop:
     `timeout --kill-after=10s 60s ssh ...`) — the launch is verified via the pid file +
     log breadcrumbs (items 1/1d), not via the wrapper staying alive.
   - The `&`-precedence trap: in `ssh pod 'cd X && setsid nohup <cmd> > log 2>&1
     < /dev/null & echo $! > pidfile'`, the trailing `&` backgrounds the ENTIRE
     `cd && setsid` list, so `$!` is an un-setsid'd wrapper subshell — HUP-vulnerable,
     and (when any fd is attached) the very process holding the channel. Mitigation:
     make `&` bind to the setsid unit alone (e.g. `cd X && { setsid nohup <cmd>
     < /dev/null > log 2>&1 & echo $! ... ; }`), or repoint the pidfile at the setsid
     session leader (SESS==PID) per the #1768 r3 failure-lesson.
   - Worked example (incident #1768 relaunch #4, 2026-07-30): the pod-side relaunch
     executed ~01:05Z left the local ssh wrapper hanging (~2.5 h, then killed — per the
     /daily 2026-07-29 problem-sweep transcript evidence; mechanism flagged there as
     inferred-not-reproduced); the launching session died with `epm:run-launched`
     unposted, and the watcher-respawned successor back-posted `epm:run-launched v4` at
     03:47:35Z after an identity-verified probe — a ~2.7 h window in which the healthy
     run was invisible to the poller's marker-pid probe.
2. Item 1d's launcher-less snippet (currently `setsid nohup ... < /dev/null & printf
   ...`) is extended to show the full form: `setsid nohup ... < /dev/null >> <log> 2>&1
   & printf ...` so the inline snippet can no longer be copied without the output
   redirections.
3. The rule's YAML frontmatter `description:` is extended with

4. Sibling hit (same gap, prose-only): `.claude/agents/experimenter.md` — the

   log), cross-referencing pod-side-reporting.md item 1f. The surrounding `cmd=`

5. The two pin tests for this rule keep passing unchanged:
