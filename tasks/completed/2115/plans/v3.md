## 0.0 TL;DR

~12-18 autonomous `/issue` sessions (2026-08-04 to 08-06) wedged 1.2-2.4h each
at the Step 10d pre-push lint-gate Bash dispatch: the orchestrator issued a
multi-KB compound and NO `tool_result` ever arrived — not even the instant
"Async task launched" ack that a `run_in_background: true` call returns. Each
sat ALIVE-BUT-STALLED until the watcher's ~2.2h stall fence respawned it;
several respawns re-wedged at the identical call (#1992 x3, #2004 x7).
Aggregate ~15-20h of blocked completion wall-time.

**Four candidate mechanisms have now been excluded under control** (Step 1 + the
v2 critique round): (1) a permission prompt — sessions run
`bypassPermissions`; (2) git index-lock blocking — read ops do not take the
lock; (3) hook cost being unbounded — the `command`-hook `timeout` DEFAULT is
600s and matching hooks run in PARALLEL, so the hook phase is bounded at ~10 min
per dispatch; (4) cancellation defeated by lingering children — cancelling a
guard leaves zero survivors and the stdout pipe EOFs in 0.00s.

**Therefore the guard-hook path cannot account for the observed duration.** The
measured hook cost (~17s at the real gate size) is real but is not the wedge.
The stall sits outside the hook phase, in the harness/transport layer, which
this repo does not control. The plan is scoped to that conclusion rather than
against it:

1. **Watcher pending-call lane (PRIMARY).** Detect the wedge regardless of
   cause. This is the right instrument precisely because the cause is outside
   our control surface: it converts a silent 1.2-2.4h stall into a bounded,
   attributable detection.
2. **Gate argv shape (SECONDARY, independent merit).** Compose the Step
   9c/10d/surgical gate scripts with the Write tool instead of a Bash heredoc.
   Worth ~17s per dispatch and applies the already-canonical #1756 rule to the
   gate recipes. Framed as latency/hygiene — NOT as the wedge fix.
3. **Hook timeouts — DROPPED for cause.** The filing's prong 2 (and v2's
   promoted prong 1) is a security regression: the docs state a timed-out
   PreToolUse command hook "doesn't block the tool call... don't count on a
   stalled hook to act as a gate." Adding a 60s timeout to the repo-root branch
   fence and the root-code-commit gate would make those fail-closed guards
   render no decision ~10x more cheaply. Not landing it is the finding.

**Change my mind:** if prong 1's predicate cannot be made specific enough to
avoid flagging routine long-pending Agent calls (subagent spawns legitimately
pend 30-90+ min), the lane is worse than the status quo — a high-false-positive
escalation channel gets ignored or kill-switched, losing the backstop. §6
prong-1 KILL states the abort condition.

## 1. Goal

Make a Step 10d lint-gate dispatch wedge DETECTABLE within one watcher cycle
instead of silent for ~2.2h, and remove the measured per-dispatch hook latency
that made the gate dispatch the fleet's largest-argv Bash call.

Explicitly NOT the goal: identifying the harness-side stall mechanism. Four
candidates are excluded (§0.0); the residual is outside this repo. Detection is
the correct deliverable for an uncontrollable cause.

## 2. Evidence base (measured; corrected from v2)

**Hook cost vs argv size.** The real Step 10d gate body extracted verbatim from
SKILL.md (26,478 bytes / 412 lines), fed to each PreToolUse Bash hook as
PreToolUse JSON on stdin plus the `TOOL_INPUT` env var, cwd = repo root.
Control arm = a 22-byte command.

| argv bytes | guard_repo_root_branch | guard_tmp_tmux_sweep | guard_root_code_commit |
|---|---|---|---|
| 22 (control) | 0.12s | 0.08s | 0.08s |
| 3,587 | 1.48s | 1.34s | 1.31s |
| 13,929 | 8.00s | 6.43s | 7.30s |
| 26,478 (real gate) | 17.16s | 12.94s | 15.81s |
| 52,957 | 42.42s | 27.81s | 30.39s |
| 105,915 | 66.72s | 39.02s | 48.14s |

Mechanism: these three guards (2,464 / 379 / 1,916 lines) split the command into
clauses then fork `printf | grep -qE` pairs and awk char-scans per clause. The
other PreToolUse Bash hooks stay under 0.1s at every size, including the 10th
Bash-matching entry (`guard_harmful_bank_read`, matcher
`Read|Bash|Grep|mcp__ssh__ssh_execute`).

**Corrected from v2:** hooks run in PARALLEL (docs: "All matching hooks run in
parallel"), so the hook-phase wall is max(hooks) ~= 17s, NOT v2's "~46s sum".
v2's figure was wrong and is withdrawn.

**Cancellation is clean.** Launch each slow guard in its own process group with
stdout on a pipe, feed the 26 KB argv, SIGTERM the lead process only after 2s:
all three showed 0 surviving descendants and pipe EOF in 0.00s, with only 1
process in the group at the kill (the guards fork sequentially, not a fan-out).

**Refuted branches.** Permission prompt (`bypassPermissions`, `spawn_session.py`
L1970/L2388-94/L2597). git index-lock blocking (control test, throwaway repo,
lock held: `diff --cached --name-only`, `ls-files -s`, `hash-object` all 0.00s
rc=0; only the WRITE op failed, fast, rc=128).

## 3. Scope

**In scope:** `scripts/autonomous_session_watch.py` (one new escalate-only
observer pass); `.claude/skills/issue/SKILL.md` (the three gate-launcher
recipes); `tests/` (regression anchors); `scripts/issue2115_hook_cost_probe.py`
(the measurement instrument behind §2, so the table is reproducible);
`scripts/workflow_lint.py` (the SKILL.md size cap, only if §6 measures net
growth).

**Out of scope, with reasons:**
- **Hook `timeout` fields — dropped for cause**, not deferred. Fail-open
  semantics (§0.0 item 3) make it a security regression with no wedge benefit.
  The filing's suggestion is answered with the doc citation + measurement.
- **Rewriting the three slow guards to stop forking per clause.** The real
  performance fix, but a large change to fail-closed security surfaces whose
  value is their refusal ladders; prong 2 removes the cost by shrinking the
  INPUT at a fraction of the risk. Recorded as a follow-up candidate.
- **The `sudo -n choom` prelude.** Measured not to be the cost driver and
  FAIL-OPEN by design. Answered with the measurement, not a diff.
- **Identifying the harness-side stall.** Outside this repo (§1).

**Scan-scope decision (recorded per critic MINOR 6).** Moving the gate body out
of the Bash argv also removes it from the Bash guards' scan channel — the
Edit|Write and PostToolUse hooks key on `file_path`, not content, so the body is
not re-scanned elsewhere. This is deliberate and is the same residual class the
sanctioned #1756 `post-marker --file` pattern already accepts (scripts on disk
were never guard-scanned). Not a new hole; recorded as a decision rather than
discovered later.

## 4. Assumptions (each with its verification)

- **A1:** a pending `tool_use` with no `tool_result` is distinguishable in the
  transcript from a completed call, and the tool TYPE is readable from the same
  row (needed to exclude Agent pends). Verification: fixture transcripts in
  anchor test 3 — the test fails if the type cannot be read.
- **A2:** guards scan the whole Bash argv including heredoc bodies. Canonical in
  CLAUDE.md for `post-marker --file` (#1756); the §2 curve demonstrates cost
  proportional to body size delivered as argv.
- **A3:** `SKILL.md` has 27 bytes of headroom (live 918,573 vs grandfather cap
  918,600; headroom bound 3,000). Any net growth needs a same-diff cap bump.
  Verification: `workflow_lint.py` in the acceptance gate.
- **A4 (verified this round, recorded so it is not re-litigated):** a timed-out
  PreToolUse command hook does NOT block the tool call, and the `command`
  default is 600s. Source: https://code.claude.com/docs/en/hooks, quoted in the
  `epm:critique` marker. This is why prong 3 is dropped.

## 5. Residual, and why it is not gated on

The harness-side stall mechanism is unidentified after excluding four
candidates. The plan does not gate on identifying it: prong 1 detects the wedge
whatever the cause, and prongs aimed at the excluded candidates would be
theatre. If a recurrence survives prong 1's detection, the sidecar rows it
writes are the starting evidence for the next round — which is the point of
shipping detection rather than a speculative fix.

Dropped from v2: the `guard_tmp_tmux_sweep.sh` `while :;` candidate — it is a
bounded quote-trim helper (shortens the string each iteration), not a plausible
infinite loop.

## 6. Success + kill criteria (quantitative)

Acceptance criteria and the decision rule per prong follow. The task-level
decision gate is the whole-task acceptance gate at the end of this section.

**Prong 1 — watcher pending-call lane (PRIMARY)**
- SUCCESS: a new ESCALATE-ONLY pass flags a session whose transcript tail ends
  in an assistant **Bash** `tool_use` with no matching `tool_result` for
  > `EPM_PENDING_CALL_WEDGE_MIN` (default 25 min). Bash-only is load-bearing:
  the Agent tool legitimately pends 30-90+ min in nearly every healthy
  autonomous session, so an untyped predicate would flag routine health. Also
  exempt: AskUserQuestion, TaskOutput, Monitor. One deduped push per session
  episode; sidecar row to
  `.claude/cache/pending-call-wedge-events.jsonl`; kill switch
  `EPM_DISABLE_PENDING_CALL_WEDGE=1`;
  `--pending-call-wedge-only --dry-run` is a zero-write smoke. The pass NEVER
  mutates task or git state and posts no task markers (the #2015 pass-36
  posture).
- KILL: if fixture testing shows the predicate cannot exclude routine long
  pends (i.e. anchor test 3 fixture (e) cannot be made to pass without also
  suppressing the real wedge class), the lane is NOT enabled — a
  high-false-positive escalation channel is worse than the status quo.

**Prong 2 — gate argv shape (SECONDARY)**
- SUCCESS: the Step 9c / Step 10d / surgical launcher recipes instruct composing
  the gate script via the Write tool; no `cat > "$..._SCRIPT" <<'...EOF'`
  gate-script heredoc remains in those three regions; the resulting gate-dispatch
  argv is under 200 bytes (vs 26,478), which by the §2 curve puts guard cost at
  the control-arm floor (~0.1s/hook).
- KILL: if a re-entry path reconstructs the gate script from the argv, prong 2
  narrows to Step 10d only and the reason is recorded.

**Whole-task acceptance gate** — the task-level decision rule:
- `uv run python scripts/workflow_lint.py` shows no NEW failures vs the
  plan-time baseline (the no-flags lint is pre-existing-red-exposed on
  origin/main, so the binding gate is Step 10d's baseline-subtracted lint gate,
  not an unconditional exit-0); c34 satisfied — see A3.
- The mapped invariant tests show no NEW failures vs the plan-time baseline
  (the Step 9c baseline compare is the binding gate).
- The regression anchors in §7 exist and PASS.

## 7. Test plan (each acceptance claim backed by a test)

1. `tests/test_autonomous_watch_pending_call_wedge.py` — fixture transcripts:
   (a) pending **Bash** `tool_use` older than the window -> FLAGGED;
   (b) pending Bash call inside the window -> not flagged;
   (c) Bash `tool_use` with a matching `tool_result` -> not flagged;
   (d) malformed / unresolvable transcript -> NOT flagged (fail toward silence
   on an escalate-only pass, so a parse bug cannot spam the fleet);
   (e) pending **Agent** `tool_use` older than the window -> NOT flagged (the
   critic-identified false-positive class; this fixture is what keeps the lane
   from flagging routine health).
2. `tests/test_autonomous_watch_pending_call_dryrun.py` — exercises the
   `dry_run` kwarg thread on the NEW pass: invoke with `dry_run=True` against a
   fixture that WOULD flag, assert (a) the flag is computed, (b) no push is
   emitted, (c) no sidecar row is written. A broken `dry_run` thread turns the
   pre-enable smoke into a real mutation (#596/#607/#633), so the smoke alone is
   not sufficient evidence — this test is what backs it.
3. `tests/test_gate_recipe_no_heredoc_argv.py` — greps the Step 9c / Step 10d /
   surgical launcher regions of SKILL.md; asserts no gate-script heredoc remains
   and that each region names the Write tool. Prong 2 is prose with no runtime,
   so this test is its ONLY durability pin (the c31 SKILL.md prose pin).

Dry-run coverage (c11): prong 1 ships `--pending-call-wedge-only --dry-run`,
anchor test 2 pins the kwarg thread, and acceptance additionally runs the flag
against live state to confirm zero writes before the pass is enabled.

## 11. Hyperparameter grounding

Not applicable in the experiment sense (kind: infra, no model training). The one
tunable constant:

- `EPM_PENDING_CALL_WEDGE_MIN` = 25 min. Source: parity with the existing
  `tick_triage.py` staleness window (`STALE_S_DEFAULT = 25 * 60`, verified
  live), so the new lane does not introduce a third, inconsistent staleness
  notion. Headroom check: a foreground Bash call hard-caps at 10 min and a
  background Bash acks instantly, so 25 min gives >=2.5x headroom over the
  longest legitimate Bash pend — which is why Bash-only keying (§6 prong 1)
  makes the window safe.

The hook `timeout` values that v2 grounded here are GONE — prong 3 is dropped
(A4), so no timeout value is being chosen.
