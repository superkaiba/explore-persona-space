# Plan v1 — #2115 daily-fix: Step 10d lint-gate pending-call wedge

**kind:** infra · **workflow:** v1 · **GPU-hours:** 0 (gpu_hours_total=0 — no
GPU, no pod, no API spend; all work is local workflow-surface edits + pytest)

## 0.0 TL;DR

~12-18 autonomous `/issue` sessions (2026-08-04 to 08-06) wedged 1.2-2.4h each
at the Step 10d pre-push lint-gate Bash dispatch: the orchestrator issued a
multi-KB compound and NO `tool_result` ever arrived — not even the instant
"Async task launched" ack that a `run_in_background: true` call returns. Each
session sat ALIVE-BUT-STALLED until the watcher's ~2.2h stall fence respawned
it; several respawns re-wedged at the identical call (#1992 x3, #2004 x7).
Aggregate ~15-20h of blocked completion wall-time.

Step 1 tested the filed hypothesis under control and **redirected it**. The
filed dominant mechanism (a permission PROMPT on the inline `sudo -n choom`
compound) is implausible: autonomous sessions spawn with
`permissionMode: bypassPermissions`. The surviving mechanism is PreToolUse
guard-hook cost, which is (a) MEASURED to scale with argv size and (b)
**unbounded by construction** because no hook carries a `timeout`. A PreToolUse
hook runs BEFORE the tool launches, which is precisely why even the background
ack never arrived.

Three prongs, re-ranked by "bounds the failure class" rather than by the
filing's order:

1. **Hook timeouts** — add explicit `timeout` to every Pre/PostToolUse/Stop hook
   entry. Smallest diff; converts an unbounded wedge into a loud failure
   regardless of which stall mechanism dominates.
2. **Gate argv shape** — compose the Step 9c/10d/surgical gate scripts with the
   Write tool instead of a Bash heredoc, so the multi-KB body stops riding the
   Bash argv that the guards scan.
3. **Watcher pending-call lane** — treat "assistant turn ends in a `tool_use`
   with no `tool_result` for > ~25 min" as wedge evidence; the backstop for
   whatever 1+2 miss.

**Change my mind:** if adding `timeout` to the hook entries turns out to make
a currently-blocking guard FAIL OPEN (i.e. the harness treats a timed-out
PreToolUse hook as "allow" rather than "deny"), prong 1 trades an availability
bug for a safety bug and must be re-scoped — the guards are fail-closed
security surfaces (repo-root branch protection, root-code-commit gating). This
is the single assumption the plan must verify empirically before landing prong
1 (§4 A1), and a fail-open finding reverses the prong order.

## 1. Goal

Make the Step 10d lint-gate dispatch unable to wedge a session indefinitely,
and make any future hook-side stall loud and bounded instead of silent.

Success is NOT "reproduce the 1.2-2.4h duration" (see §5 — the duration is
deliberately out of scope as a gating criterion). Success is: the failure class
is bounded, the dominant measured cost is removed, and a wedge that survives
both is detected within one watcher cycle.

## 2. What Step 1 measured (the plan's evidence base)

Probe: the real Step 10d gate body extracted verbatim from SKILL.md (26,478
bytes / 412 lines) fed to each of the 9 PreToolUse Bash hooks as PreToolUse
JSON on stdin plus the `TOOL_INPUT` env var, cwd = repo root, bounded by a hard
timeout. Control arm = a 22-byte command through the same hooks.

| argv bytes | guard_repo_root_branch | guard_tmp_tmux_sweep | guard_root_code_commit |
|---|---|---|---|
| 22 (control) | 0.12s | 0.08s | 0.08s |
| 3,587 | 1.48s | 1.34s | 1.31s |
| 13,929 | 8.00s | 6.43s | 7.30s |
| 26,478 (real gate) | 17.16s | 12.94s | 15.81s |
| 52,957 | 42.42s | 27.81s | 30.39s |
| 105,915 | 66.72s | 39.02s | 48.14s |

The other 6 PreToolUse Bash hooks stay under 0.1s at every size. Mechanism:
these three guards (2,464 / 379 / 1,916 lines) split the command into clauses,
then fork `printf | grep -qE` pairs and awk char-scans PER CLAUSE — a 412-line
body becomes hundreds of clauses x several process spawns each. At the real
gate size that is ~17s (slowest single hook) to ~46s (sum) of pre-launch
latency per dispatch, on an unloaded VM.

Refuted in Step 1 (control test, throwaway repo, `index.lock` held): git READ
ops do not block on the index lock — `diff --cached --name-only`, `ls-files -s`
and `hash-object` all returned in 0.00s rc=0; only the WRITE op failed, and it
failed fast (rc=128). So the live git calls
`guard_root_code_commit.sh` makes against the shared root are NOT the unbounded
factor. Branch closed.

## 3. Scope

**In scope:** `.claude/settings.json` (hook `timeout` fields);
`.claude/skills/issue/SKILL.md` (the three gate-launcher recipes);
`scripts/autonomous_session_watch.py` (one new observer pass); `tests/` (the
regression anchors); `scripts/workflow_lint.py` (the SKILL.md size cap, only if

**Out of scope, with reasons:**
- Rewriting the three slow guards to stop forking per clause. That is the real
  performance fix but it is a large change to fail-closed security surfaces
  whose whole value is their refusal ladders; prong 2 removes the cost by
  shrinking the INPUT instead, at a fraction of the risk. Filed as a follow-up
  candidate, not attempted here.
- The `sudo -n choom` prelude. Measured NOT to be the cost driver, and it is
  FAIL-OPEN by design (a denial never blocks the gate). Dropping it or
  allowlisting it is cosmetic relative to this task's Goal; the filing's
  suggestion is answered with the measurement, not a diff.

## 4. Assumptions (each with its verification)

- **A1 (load-bearing, verify FIRST):** a PreToolUse hook that exceeds its
  `timeout` is treated by the harness as a FAILED/DENY hook, not as an ALLOW.
  Verification: set a deliberately tiny `timeout` on one guard in a scratch
  settings copy, issue a command that guard blocks, and confirm the command is
  still blocked. If it is allowed instead, STOP — prong 1 is a fail-open
  regression and the prong order reverses (see §0.0 change-my-mind).
- **A2:** guards scan the whole Bash argv including heredoc bodies. Already
  canonical in CLAUDE.md for `post-marker --file` (#1756); prong 2 is the same
  rule applied to the gate recipes. Verification: the §2 probe already
  demonstrates cost proportional to body size delivered as argv.
- **A3:** `SKILL.md` has 27 bytes of headroom (live 918,573 vs grandfather cap
  918,600, headroom bound 3,000). Any net growth needs a same-diff cap bump.
  Verification: `workflow_lint.py` no-flags run in the acceptance gate.

## 5. Explicit non-criterion — the residual duration gap

Measured hook cost at the real gate size is tens of seconds; the observed
wedges were 1.2-2.4h. **The plan does not attempt to reproduce the duration and
does not gate on it.** Surviving candidates: (a) fork amplification under fleet
load — these guards spawn hundreds of processes each and the VM runs ~15
concurrent sessions (cf. #2039's loadavg ~20 threshold, #2054's measured ~6x
contention penalty); (b) an input-dependent unbounded loop in a guard
(`guard_tmp_tmux_sweep.sh` L90 has a `while :;` parse loop).

Rationale for not gating: prong 1 makes the residual MOOT rather than requiring
it to be solved — a bounded hook converts an unbounded wedge into a loud,
attributable failure. Chasing the duration would block a fix that is correct
under either candidate. The candidates are recorded here so a future recurrence
has a starting point rather than a cold start.

## 6. Success + kill criteria (quantitative)

**Prong 1 — hook timeouts**
- SUCCESS: every `PreToolUse` / `PostToolUse` / `Stop` hook entry in
  `.claude/settings.json` carries an explicit integer `timeout`. A1 verified:
  a timed-out guard still BLOCKS. Timeout values: 60s for the three measured-slow
  guards (>= 3x the 17.16s worst measured cost, so no false trip at the real
  gate size), 30s for the six fast guards (>= 300x their measured cost), 60s for
  the `Stop` push hook (it runs git network I/O).
- KILL: A1 comes back fail-open. Then prong 1 does not land as specified; the
  task re-plans with prong 2 first and prong 1 reduced to the six fast guards
  only (which have no fail-closed security role).

**Prong 2 — gate argv shape**
- SUCCESS: the three gate-launcher recipes in SKILL.md instruct composing the
  gate script via the Write tool; no `cat > "$..._SCRIPT" <<'...EOF'` heredoc
  remains in the Step 9c / Step 10d / surgical launcher recipes. The resulting
  Bash argv for a gate dispatch is under 200 bytes (vs 26,478), which by the §2
  curve puts guard cost at the control-arm floor (~0.1s/hook).
- KILL: if some consumer requires the heredoc form (e.g. a re-entry path that
  reconstructs the script from the argv), prong 2 narrows to Step 10d only and
  the reason is recorded.

**Prong 3 — watcher pending-call lane**
- SUCCESS: a new ESCALATE-ONLY observer pass flags a session whose transcript
  tail ends in an assistant `tool_use` with no matching `tool_result` for
  > `EPM_PENDING_CALL_WEDGE_MIN` (default 25 min), with a per-session deduped
  push and a sidecar JSONL row; kill switch `EPM_DISABLE_PENDING_CALL_WEDGE=1`;
  `--pending-call-wedge-only --dry-run` is a zero-write smoke. Pass NEVER
  mutates task/git state and posts no task markers (the #2015 pass-36 posture).
- KILL: none — this prong is additive and independently revertible.

**Whole-task acceptance gate (all three prongs)**

  attributable to this diff; c34 satisfied — see A3).

## 7. Test plan (the fail-loud acceptance claims, each backed by a test)

Regression anchors — named tests, executed in the Step 9c gate:

1. `tests/test_settings_hook_timeouts.py` — asserts EVERY
   `PreToolUse`/`PostToolUse`/`Stop` hook entry in `.claude/settings.json`
   carries an integer `timeout` in a sane band (5..120s). This is the durable
   pin for prong 1: it fails loudly if a future hook is added without one,
   which is exactly the gap that produced this incident. Backs the prong-1
   fail-loud claim.
2. `tests/test_gate_recipe_no_heredoc_argv.py` — greps the Step 9c / Step 10d /
   surgical launcher regions of SKILL.md and asserts no
   `cat > ... <<'...EOF'` gate-script heredoc remains, and that each region
   names the Write tool. This is the c31 SKILL.md prose durability pin: the
   recipe is prose, so only a test keeps it from regressing.
3. `tests/test_autonomous_watch_pending_call_wedge.py` — fixture transcripts
   (a) pending `tool_use` older than the window -> flagged; (b) pending call
   inside the window -> not flagged; (c) `tool_use` with a matching
   `tool_result` -> not flagged; (d) malformed/unresolvable transcript ->
   NOT flagged (fail toward silence on an escalate-only pass, so a parse bug
   cannot spam the fleet).

Dry-run coverage (c11): prong 3 ships
`--pending-call-wedge-only --dry-run` and the plan's acceptance runs it against
live state to confirm zero writes before the pass is enabled.
