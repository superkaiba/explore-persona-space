# Plan v1 — task #1880: pod-side results-git push must fetch+rebase (mid-run branch-push race)

architectural: false

## 0. Goal / requirement

Close the mid-run branch-push race that turns a HEALTHY completed run into a
false workload crash: a lane's terminal results-git push races any
orchestrator commit pushed to `origin/issue-<N>` mid-run (a sibling lane's
crash-fix is the normal case). The #1205 push-verify contract mandates
retry-once but never fetch+rebase, so a behind-origin push loses
DETERMINISTICALLY on both attempts (incident #1739 hallu lane, 2026-07-30:
270 cells rc=0, Hub sidecars verified, then exit 1 at the terminal push —
`! [rejected] ... (fetch first)` / `(non-fast-forward)` → crash-persist →
poweroff → ~30 min manual recovery of 31h of complete science).

**Requirement:** (a) the durable rule surface
(`.claude/rules/pod-side-reporting.md` § Result-push verification contract)
mandates fetch+rebase-before-retry-push for every pod/instance-side
results-git push and warns the orchestrator side about mid-run branch
pushes; (b) the ONE shared mechanical surface — the GCE push-verify backstop
in `backends/gcp.py::render_startup_script` — implements the same
fetch+rebase before its retry push (it is identically fetch-blind today).

## 1. Acceptance criteria

## 2. Method delta / design decisions

- **Decision 1 — REJECT the filing sketch's "exit 0 with a push-failed
  sentinel" disposition.** It contradicts two standing contracts in the same
  section: "never declare done with an unpushed result commit" (the #1205
  fail-loud core) and the Part A-ter interplay bullet (a workload declaring
  git-committed eval JSONs must NOT stamp `EPS_DELIVERABLES_OK_PATH` before
  push-verify). Instead: fetch+rebase eliminates the deterministic-loss
  common case at the root; the residual rebase-conflict case (near-impossible
  for additive per-lane result files) keeps the existing fail-loud + bundle +
  crash-persist path, which demonstrably preserves the data (#1739 recovered
  everything from crash-persist).
- **Decision 2 — include the GCE backstop code fix.** Plan-time verification
  confirmed there is NO shared driver push helper (per-issue scripts only),
  so the rule is the durable surface for drivers — but the GCE backstop
  (`gcp.py` rendered startup script, workload_cmd branch) is a REAL shared
  mechanical surface with the identical blindness (`push || { sleep 20;
  push; } || true`). A prose-only fix would leave the one mechanical leg
  deterministically failing in the same race.
- **Decision 3 — orchestrator-side warning lives in BOTH rule files, one
  bullet each:** pod-side-reporting.md (loaded when writing push code) and a
  single sentence in crash-fix-rounds.md § Crash-fix relaunch (loaded by the
  racing actor — the session pushing a sibling-lane fix mid-run). LESSONS.md
  row unchanged (its fires-when already covers "pushing result commits").

## 3. File paths + concrete diffs

### D1 — `.claude/rules/pod-side-reporting.md` (§ Result-push verification contract, after the first bullet)

```
+ - **Fetch + rebase before every pod/instance-side results-git push
+   (#1880).** A lane's terminal push races ANY orchestrator branch commit
+   made mid-run (a sibling lane's crash-fix relaunch is the normal
+   multi-lane case): a bare push retry that detects behind>0 but never
+   fetches loses deterministically — non-fast-forward → workload exit 1 →
+   a HEALTHY run crash-persists and powers off (#1739 hallu: 31h of
+   complete science, ~30 min manual recovery from crash-persist). Push
+   recipe: `git fetch origin <branch> && git rebase origin/<branch>`
+   (result commits are additive per-lane files — conflicts are
+   near-impossible), then push and re-verify per the rev-list bullet
+   above; bounded 2 attempts. On rebase conflict: `git rebase --abort`
+   and proceed to the lane's EXISTING fail-loud path (GCE: bundle +
+   exit 86; crash-persist preserves the results) — the standing
+   "never declare done with an unpushed result commit" contract and the
+   Part A-ter sentinel ordering are UNCHANGED (a push-failure-tolerant
+   exit-0 disposition was considered and rejected: it would let a run
+   classify done-like with results only in a bundle).
+ - **Orchestrator side (#1880):** avoid pushing to the issue branch while
+   lanes are mid-run when feasible; when a mid-run push is required (a
+   sibling lane's crash-fix relaunch), expect in-flight lanes' terminal
+   pushes to need the fetch+rebase path above — a lane running a pre-#1880
+   driver will deterministically false-crash at its terminal push (the
+   #1739 shape) with its results intact in crash-persist; treat that
+   failure as recoverable-transport, not a science loss.
```

Also extend the existing **GCE lane** bullet with one clause: the mechanical
backstop fetch+rebases before its retry as of #1880.
