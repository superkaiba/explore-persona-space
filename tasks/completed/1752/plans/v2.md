# Plan v2 — task #1752: gpu-idle escalation consequence after N repeats

## Plan Summary

`scripts/poll_pipeline.py`'s GPU-idle ESCALATION arm (#664) de-dups at-most-once-per-phase, but the dedup key `gpu_idle_escalated_phases` is run-scope-cleared on every fresh `epm:run-launched` (#1033) — so a phase that stays idle across relaunches re-fires a byte-identical `[gpu-idle-escalation]` note forever (task #1689: `fit_ladder` escalated identically at 07-27T02:43Z and 11:23Z around the run-launched v9 relaunch; the phase rode ~14h at 0% GPU until the user intervened). Fix: track a per-phase escalation COUNT that deliberately SURVIVES the run-scope reset; once the count reaches N (default 3), the escalation switches KIND — a distinct `[gpu-idle-width-reeval]` note naming the concrete downsize recipe + a Telegram push — instead of another identical note. Applies symmetrically on BOTH production callers (RunPod `poll_once` and the GCP mirror in `scripts/backend_poll.py`). The poller still NEVER stops the pod.

v2 delta (critic Must-Fix 1): the return-arity change touches TWO production callers — v1 missed the GCP-lane mirror `scripts/backend_poll.py:4721`, whose 2-tuple unpack would have crashed every healthy GCP idle-block tick. v2 updates that unpack, threads the count through `_save_gpu_idle_state`, and adds tests pinning the GCP wiring + both state-key-tuple exclusions.

`architectural: false` — helper-script guardrail change; no status enum, marker-kind schema, or task.py contract touched (the marker stays `epm:progress`; new fields are additive `extra` keys).

## Goal / acceptance criteria

Repeated identical gpu-idle escalations on one phase escalate in KIND, not just repeat:

1. The 1st and 2nd escalation for a phase behave byte-identically to today (note text, push, dedup, run-scope re-arm) — on both lanes.
2. The Nth (N>=3, env-tunable) escalation for the SAME phase — counted ACROSS run epochs / relaunches / GCP attempt incarnations — posts a DISTINCT width-re-eval note + Telegram push instead of the identical note.
3. The counter survives the #1033 resets: NOT in `_RUN_SCOPED_STATE_KEYS` (poll_pipeline) and NOT in `_IDLE_ADVISORY_STATE_KEYS` (backend_poll attempt-scoping) — both blacklist-clears, both pinned by membership tests. Incremented only on a successful marker post.
4. The poller still never stops/terminates the pod (no lifecycle call added; pinned by a source-level assertion).
5. Both production callers unpack the new 3-tuple; nothing else in the repo calls `_maybe_escalate_gpu_idle` (grep-verified: poll_pipeline.py:5622, backend_poll.py:4721, 3 test sites).
6. Tests pin 1-5; full mapped test files pass.

## Method delta (vs current behavior)

Current: `_gpu_idle_escalation_update` (pure core, L4285) + `_maybe_escalate_gpu_idle` (wiring, L4369) post one identical note per (phase x run-epoch), on both lanes. Delta: add a persistent per-phase count; branch the NOTE/PUSH composition on count>=N. No change to the idle-span clock, the advisory tier, the eligibility predicate, or the per-phase-per-run dedup. The eligibility predicate (`n_gpus>=2` + `_gpu_idle` + `_phase_is_cpu_only` + span>=60min) already guarantees a narrowed/fixed pod never re-fires, so a surviving count is inert until a genuine same-phase multi-GPU idle repeat — no false-positive width-reeval after corrective action.

## Design + concrete diffs

### `scripts/poll_pipeline.py`

1. **New module constant + env knob** (next to `GPU_IDLE_ESCALATION_MIN`):
   `GPU_IDLE_WIDTH_REEVAL_N = int(os.environ.get("EPM_GPU_IDLE_WIDTH_REEVAL_N", "3"))` — the count (inclusive) at which escalation switches KIND. `<= 0` disables the width-re-eval variant (identical notes forever, pre-fix behavior). Values 1/2 are honored (escalate-in-kind sooner). Comment notes #1689's fit_ladder repeat was 2 identical fires — under N=3 the switch comes on the third (one-more-chance semantics, intended).

2. **New state key `gpu_idle_escalation_counts`** — comma-joined `phase:count` pairs (phase names match `PHASE_RE` `[a-z0-9_]+`, so `:`/`,` are safe separators). Parse helper `_parse_escalation_counts(raw: str) -> dict[str, int]` (malformed entries dropped, never raises). **Deliberately NOT added to `_RUN_SCOPED_STATE_KEYS` (nor backend_poll's `_IDLE_ADVISORY_STATE_KEYS`)**: #1033's rationale (stale idle-minutes DISPLAY inherited across relaunches) does not apply to a pure count, and surviving relaunches is the point — the repeat pathology only manifests ACROSS run epochs. Comment this at the key's save sites and in both key tuples' comment blocks.

3. **`_maybe_escalate_gpu_idle`**: read counts from `prev_state`; on `should_escalate` for phase P compute `n = counts[P] + 1`.
   - `n < GPU_IDLE_WIDTH_REEVAL_N` (or knob disabled): post the EXISTING note verbatim (no text change) + existing push.
   - `n >= GPU_IDLE_WIDTH_REEVAL_N`: post the DISTINCT note — prefix `[gpu-idle-width-reeval]`, body naming: this is escalation #n for phase P (n stated in the text) across relaunches; the identical-note tier has produced no action; DEMAND a width re-evaluation with the concrete recipe (persist resume state / store off-pod -> terminate the wide pod -> re-provision narrow, per the CLAUDE.md GPU-WIDTH right-sizing carve-out; or route the CPU phase off-pod entirely) — and state explicitly that NOTHING was stopped. Extras: `gpu_idle_escalation=True` (existing consumers unchanged), `gpu_idle_width_reeval=True`, `escalation_repeat=n`. Telegram push uses the width-re-eval wording.
   - On successful post (either form): `counts[P] = n`, add P to `escalated_phases` (unchanged). On post failure: neither is recorded (existing retry semantics).
   - Return signature becomes `(escalated_phases, counts, escalated)`.

4. **Callers (BOTH production + 3 test sites; complete grep-verified list)**:
   - `poll_once` (`scripts/poll_pipeline.py:5622`): unpack 3-tuple; add `"gpu_idle_escalation_counts": <serialized>` to the `_save_state` payload (~L5810) — the payload is built fresh each tick, so an unthreaded key would be silently dropped.
   - GCP mirror (`scripts/backend_poll.py:4721`): unpack 3-tuple; add `"gpu_idle_escalation_counts": <serialized>` to the `_save_gpu_idle_state` payload (~L4746). The count key is read from the SCOPED `tripwire_state` and survives both `_tripwire_run_scope` and `_scope_idle_state_to_attempt` by default (both are blacklist-clears) — the GCP lane gets the SAME escalate-in-kind behavior (import-not-extract reuse contract, #730). Serialization helper imported from poll_pipeline alongside the existing imports (or inline join — implementer's choice, same format).
   - `tests/test_backend_poll_gpu_idle.py` L229/L246/L284: arity-only updates.

5. **PollResult / JSON line: UNCHANGED** (deliberate scope choice). Both note forms set `gpu_idle_escalation_posted=True` (and the GCP `gcp_gpu_idle_escalation_posted` mirror); the orchestrator's Step 6d.2 escalation handling already prescribes the width right-sizing judgment, and the marker note + extras carry the kind distinction. No new PollResult field; the ONLY backend_poll.py changes are the unpack arity + the one persist line in item 4.
