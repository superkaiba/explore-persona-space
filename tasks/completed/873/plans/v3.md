**Goal (from task body):** add two runtime tripwires to the pipeline poller so mid-run compute blowups (serial burns, partial GPU idleness) are surfaced by machine, not by reactive human investigation.

**Acceptance criteria:**

1. On a poll tick with `status == "running"`, if elapsed wall-time (per current phase, or for the whole run) exceeds `2×` the plan's §9 total `planned_wall_h`, exactly one `epm:compute-deviation v1` marker is posted per dedup key (`(task, phase)`; run-total key `__run_total__`), with `source: poller`, `basis: elapsed-vs-plan`, and the workflow.yaml body shape (`component: ... planned_wall_h: ... projected_wall_h: ... ratio: ... basis: ...`). 5. All new + existing poller tests pass; `workflow_lint.py` default run passes; ruff passes; `tests/test_no_dollar_budget_caps.py` stays green (both tripwires are time/count-based, no dollar values anywhere).

## 3. Design decisions (the four the body deferred)

**D1 — how `planned_wall_h` reaches the poller: the poller reads the plan file directly (option ii).**
`from explore_persona_space.task_workflow import find_task_path` is ALREADY in poll_pipeline's import block (line 279). The plan is `find_task_path(issue) / "plans" / "plan.md"` (symlink to the highest version — verified present, e.g. `tasks/followups_running/779/plans/plan.md`). Why not the alternatives: (i) handle-sidecar plumbing covers ONLY the `backend_poll.py` handle path — the legacy CLI path (`poll_pipeline.py main()`, used by parent-pod-reuse children) has no handle, so (i) structurally can't cover both entrypoints; it would also need the same §9 parser at dispatch time plus changes to `dispatch_issue.py`/`issue_dispatch.py`. (iii) a launch-marker field requires changing every launch site. Option (ii) is zero plumbing, covers both live entrypoints (RunPodBackend.poll delegates to `poll_pipeline.poll_once` — backend_poll.py docstring lines 34-36), and its failure mode is exactly the mandated fail-safe (no file / no table → disabled). Each poll tick is a fresh process (one-shot `main()` → `poll_once` → print JSON, lines 2997-3010), so a ~50 KB plan read per tick is the total cost — negligible at the actual tick cadence (`POLL_INTERVAL_DEFAULT_SEC=540` / `POLL_INTERVAL_QUIET_SEC=1800`, poll_pipeline.py:352-353).

**D1b — budget construct: total §9 sum, NOT fuzzy phase→row matching.** §9 `component` names are planner free-text ("smoke-phase per-cell train", "sweep all-cells train") with no mechanical mapping to pod-side `[phase=...]` tokens; a wrong-but-unique fuzzy match (phase `train` → the 0.5h smoke row while the 16h sweep runs) produces exactly the false positive the body bans. Instead the budget is `total = Σ planned_wall_h` over all parsed rows, and the predicate is two conservative checks sharing it:
- **per-phase:** `elapsed(current_phase) > mult × total` — any SINGLE phase exceeding 2× the ENTIRE plan's wall estimate is unambiguously a deviation (every phase is planned ≤ total by construction). Dedup per (task, phase), as the body specifies.
- **run-level:** `elapsed(run) > mult × total` (from `run_age_sec` / the `epm:run-launched` marker) — catches cumulative overrun across phases. Dedup key `__run_total__`, once per run.
Both are strictly conservative in the OVER-counting direction: the sum over-estimates wall time for parallel plans and for async rows ("3 (async, off-GPU)" parses as 3) → later firing, safe. The UNDER-counting direction is closed by construction (AC #2): any unparseable data row → `None` (disabled), never a partial sum; ALL `planned_wall_h` tables are summed (multi-stage plans); the HTML value column is header-derived and table-scoped. Residual edge cases (a same-issue follow-up round whose `plans/plan.md` re-symlinks to a smaller amendment §9) cost at most one deduped advisory marker per run — with the run-scoped dedup reset (AC #6), the run-level check compares the CURRENT run's elapsed against the CURRENT plan total, which is the coherent read for a follow-up round. Incident coverage, stated honestly: #763 ran ~80× over a sub-hour plan (ETA fires within the first tick past ~2× total ≈ 24-40 min vs ~16h); #813's earliness is carried by the WIDTH advisory (~45-75 min vs 6.7h) — the ETA check fires only at ~36-40h there; #778's serial burn ran OFF-POD on the VM and is structurally out of the poller's sight (named limitation, §0.0/§5). A small phase inside a large-total plan fires only past 2× the WHOLE plan's estimate (documented conservatism — stated in the §4.4 marker-doc addendum).

**Coverage (fact-checker survey):** of 10 recent plans, 7 have a parseable `planned_wall_h` table (6 markdown, 1 HTML); among `kind: experiment` plans the tripwire arms for ~7/9 (~78%) and fail-safes-off for the rest (#825/#833 carry only the `Estimated GPU-hours (total)` line). The fail-safe branch is a real current-population path, not hypothetical — acceptable for an advisory tripwire; sibling task #874 (plannerless-path compute statement) addresses the upstream gap.

**D2 — current phase + start time:** reuse what `poll_once` already computes. `current_phase = latest_phase(probe["log_tail"])` (line 2633, #545-corroborated); phase start = `last_phase_change_epoch` AFTER the relaunch clamp + `phase_transitioned` update (lines 2843-2864 — the clamp already discards boundaries predating the current `epm:run-launched`, so a follow-up relaunch never inherits a stale start). When `last_phase_change_epoch == 0` (no boundary observed this run — the first phase), fall back to run-launch epoch (`now_epoch - run_age_sec`, `run_age_sec` already computed at line 2847 via `_run_launched_age_sec`); when that is also `None` → skip the phase check (fail-safe). Placement: the new call goes AFTER line 2864 (so it sees the post-clamp, post-transition value) and BEFORE `_save_state` (line 2881).

**D3 — per-GPU utilization:** reuse the probe's existing `gpu_util` comma-separated string (`probe.get("gpu_util", "unknown")`, line 2625). No second nvidia-smi call. Extract the parse into `_parse_gpu_utils(gpu_util: str) -> list[int] | None` and rewrite `_gpu_idle` on top of it (behavior-identical; pinned by a regression test).

**D4 — dedup mechanics: the `prev_state` pattern, RUN-SCOPED (critic round 1).** New state keys in the same per-issue subdict `_load_state`/`_save_state` (lines 2303-2325) already manage: `eta_deviation_posted_keys` (comma-joined; phase names are `[a-z0-9_]+` per `PHASE_RE` so the join is safe, `__run_total__` likewise), `eta_budget_warned` ("1" after the one missing-estimate log), `gpu_width_since_epoch`, `gpu_width_idle_set` (comma-joined ints), `gpu_width_advised_phases` (mirrors `gpu_idle_advised_phases`), PLUS `tripwire_run_epoch` — the `epm:run-launched` epoch of the run these keys belong to (derived from the same marker read `_run_launched_age_sec` already does; `now_epoch - run_age_sec` rounded is sufficient). On each tick, when the CURRENT run-launched epoch is NEWER than the stored `tripwire_run_epoch` (allowing a small tolerance, e.g. >60s, so rounding jitter never spuriously resets), ALL the new keys above are cleared before the predicates run — a relaunch or same-issue follow-up round re-arms both tripwires (Meth-Codex MF3; without this, `__run_total__` is permanently suppressed per issue and common phase names collide across runs). Every state int-parse is guarded like `prev_idle_since` (line 1908's `try/except (TypeError, ValueError)`) — a corrupted state file resets, never raises into `poll_once`. A marker-post failure is logged and the key is NOT recorded, so the next tick retries (same contract as `_maybe_post_gpu_idle_advisory`, lines 1946-1948).

```python
def _parse_plan_wall_budget(plan_text: str) -> float | None:
    """Sum of §9 per-component planned_wall_h, or None when no row parses.

    Handles the markdown pipe-table form (header row containing both
    'component' and 'planned_wall_h') and the HTML form. CONTRACT
    (critic round 1, AC #2):
      - ALL tables carrying a planned_wall_h header are located and
        summed (multi-stage plans, e.g. #479 Stage 1 + Stage 2 — a
        single-header parse under-counts and false-fires).
      - The value-column index is DERIVED from the header cell position
        in BOTH formats (markdown pipe cells AND the HTML <th> row) —
        never a hardcoded ordinal; the HTML row scan is SCOPED to the
        table element containing the planned_wall_h <th>, never a
        document-wide <td> scan.
      - Each data cell contributes its LEADING float
        ("3 (async, off-GPU)" -> 3.0). If ANY located data row's
        planned_wall_h cell yields NO leading float, return None
        (tripwire disabled, log once) -- NEVER a partial sum: an
        under-parsed budget is the one path to a false positive.
      - Returns None on zero located tables / zero data rows.
    """
```

Pseudocode: for each markdown header hit (`re.finditer(r"^\|[^\n]*planned_wall_h[^\n]*$", ..., re.M)`) → derive the cell index from the header's `|`-split cells, iterate following `|`-prefixed lines to the table end (skip the `---` separator row); for each HTML header hit (`<th>planned_wall_h</th>` — or `<th>`-row containing it) → bound the enclosing `<table>...</table>` span, derive the column index from the `<th>` sequence, extract that column from each `<tr>`'s `<td>` sequence within the span. Per data cell: `re.match(r"\s*([0-9]+(?:\.[0-9]+)?)", cell)`; a miss on ANY located data row → return `None`. Else `total = sum over all tables' rows`; `return total or None`. Whole body wrapped so any exception returns `None`.

```python
def _plan_total_wall_h_for_issue(issue: int) -> float | None:
```

## 11. Decision Rationale (tunables)

- **`EPM_ETA_DEVIATION_MULT` = 2.0.** What: multiplier over §9 total planned_wall_h. Why: the project's deviation bar. Source: existing project convention — `workflow.yaml` `pivot_criteria.compute_deviation_over_2x` (line ~780-800) and the `epm:compute-deviation` marker fields (line 1569-1588) both pin 2×; task body prescribes 2× verbatim. Alternatives: 1.5× (the descope target ratio — too tight for a total-sum budget that over-estimates parallel plans); a per-row multiplier (rejected, D1b).
- **Budget = Σ planned_wall_h (total), applied per-phase AND per-run.** What/Why: the only mapping-free, zero-false-positive budget (§3 D1b). Source: the §9 table contract in `.claude/rules/planner-section-reference.md` §9 (lines 306-319) — `component` is free text, so row-level mapping is not mechanically available. Alternatives: fuzzy row match (false-positive risk, rejected); handle plumbing (coverage gap, rejected).
- **`EPM_GPU_WIDTH_ADVISORY_MIN` = 45.** What: sustained partial-width minutes before the advisory. Why: inside the body's prescribed 30-60 band; above the all-idle `EPM_GPU_IDLE_ADVISORY_MIN` = 30 (poll_pipeline.py line 1831) because a strict-subset-idle state has a legitimate transient the all-idle state lacks (uneven shard finish tails), and the stable-idle-set requirement plus 45 min still catches #813 (6.7h) ~9× earlier than a human did. Source: task body ("default 30-60 min, env-tunable") + the sibling `EPM_GPU_IDLE_ADVISORY_MIN`/`EPM_GPU_IDLE_ESCALATION_MIN` (30/60) convention. Alternatives: 30 (more false positives on shard tails), 60 (matches the escalation tier but halves the detection win).
- **Idle threshold reuse (`GPU_IDLE_UTIL_THRESHOLD` = 5).** Source: existing constant, poll_pipeline.py line 1800; one threshold for both idle constructs keeps the two advisories consistent. Alternative: a separate width threshold — rejected, no evidence it should differ.
- **Stable-idle-set requirement.** Why: distinguishes #813's structurally-unused GPUs (fixed indices 1/2/4/7 for hours) from healthy staggered progress; the strictest false-positive guard consistent with the incident. Source: task body incident evidence (#813). Alternative: any-subset-idle span (fires on healthy uneven shard completion — rejected).
