# Plan v1 — #1824: `upload_dir_sharded` batches small-file stores into chunked bulk commits (+ skip-if-present resume)

## 0. TL;DR

`orchestrate.upload_sharded.upload_dir_sharded` currently commits ONE `upload_file` per shard (~35 s/file commit round-trip on the #1482 store: 539/3,840 files in ~5.5 h, ~33 h projected, GPU idle, ~100 commits/h against the shared 256/h Hub cap). This plan adds a **batch mode** — chunked `create_commit` bulk commits of ≤ `HUB_COMMIT_FILECOUNT_WARN` (2,000) files each — as the default whenever the store's on-disk byte sum fits under a threshold (default 50 GB), retaining the per-file walk as the explicit/large-store fallback, plus an **up-front skip-if-present resume probe** (one scoped listing; skip same-size already-on-Hub files) in BOTH modes. All existing contracts preserved: overflow reroute on quota-403, pointer + JSONL event (once per prefix), batched exact-set verify, fail-loud never-silently-drop, delete-only-after-verify.

## 1. Requirement + acceptance criteria (kind: infra)

**Requirement** (task Goal): batch `upload_dir_sharded`'s shard files into grouped commits whenever the store fits comfortably under the local-disk/quota bound; fall back to the per-file walk otherwise; add a skip-if-already-on-Hub probe so interrupted walks resume without re-committing.

**Acceptance criteria:**
1. A 3,840-file store uploads in ≤ 2 bulk commits per destination repo (vs 3,840 commits today) — pinned by a commit-count test.
2. Overflow semantics identical: quota-403 (reactive) and projected-headroom (proactive, #1034) both route to the overflow repo with exactly ONE `OVERFLOW_POINTER.json` commit + ONE JSONL event per prefix, in batch mode too.
3. Resume: a re-invocation after a partial prior upload re-commits ONLY missing / size-changed files (both modes); skipped files are still verified + (when `delete_local`) deleted.
4. Fail-loud unchanged: non-quota errors re-raise after the transient-retry budget; both-repos-refused raises `RuntimeError`; locals never deleted unverified.
5. Signature backward compatible — all 8+ live call sites (`issue1335_run.sh`, `issue1073_fits/capture.py`, `issue1417_run.sh`, `issue1345_upload.py`, `issue1482_*.py`) run unchanged (new kwargs have defaults; `ShardUploadResult` gains only an additive field).
6. `tests/test_upload_sharded.py` extended; full file green; no other test file regresses (Step 9c gate).

## 2. Method delta (what differs from prior related work)

- Prior art reused, not reinvented: `_batched_verify` (#1335, one scoped listing per destination repo) verifies batch-mode uploads unchanged; `hub.retry_transient` wraps every fresh Hub call; `_ensure_overflow_repo` / `_write_overflow_pointer` / `_emit_overflow_routing_event` reused verbatim; the #1034 proactive-headroom branch reused (batch mode simply commits its chunks straight to overflow).
- New: (a) chunked bulk commits via `api.create_commit(operations=[CommitOperationAdd(...)])` — exact file selection, no glob/fnmatch escaping fragility (rejected alternative: `api.upload_folder(allow_patterns=[<names>])` — fnmatch has no escape syntax, so arbitrary shard names with `[?*` misroute, and N-patterns × M-files matching cost scales badly); `upload_folder` itself is a thin wrapper that composes `CommitOperationAdd`s and calls `create_commit`, so this is the same single-commit path the #664/#727 doctrine mandates. `create_commit` handles LFS preupload internally (implementer verifies on the pinned huggingface_hub 0.36.2 before relying on it — flagged in §8 assumptions).
- New: (b) `_remote_sizes_under_prefix(api, repo_id, prefix, repo_type) -> dict[str, int]` — scoped `api.list_repo_tree(path_in_repo=prefix, recursive=True)` materialized INSIDE the `retry_transient` thunk (lazy-generator gotcha), `EntryNotFoundError` → `{}` (absent prefix = nothing uploaded yet; a `RepositoryNotFoundError` still propagates loud per the gotchas literal-path rule). Sizes come from `RepoFile.size` (filter out `RepoFolder` entries).
- Chunk cap grounded in hub.py's own tiers: ≤ 2,000 files/commit (`HUB_COMMIT_FILECOUNT_WARN`, #1571 — one 31,000-file commit was killed >20 min in, #1481) which also keeps every commit under the per-dir 10k server cap (#658/#1190). `upload_large_folder` deliberately NOT used (project decision recorded at the #1571 tier comment in hub.py).

## 3. Design

### 3.1 Mode selection (auto, with escape hatches)

New kwargs on `upload_dir_sharded`:
- `batch: bool | None = None` — `None` = AUTO: batch iff `projected_bytes <= EPM_UPLOAD_BATCH_MAX_GB` (env, default `50`, decimal GB); `True` forces batch; `False` forces the legacy per-file walk.
- `batch_chunk_files: int = HUB_COMMIT_FILECOUNT_WARN` (imported from `orchestrate.hub`) — files per bulk commit.

`projected_bytes = sum(p.stat().st_size for p in shards)` is computed ONCE (it already exists inside the proactive-headroom branch; hoist it) and feeds both the #1034 headroom probe and the mode decision. Rationale for byte-threshold-only (no free-disk term from the task body's sketch): since #1335's deferred-delete design, BOTH modes hold the full store on disk until the post-verify delete pass — the walk reads files in place and `create_commit` streams them — so batching does not raise peak local footprint; the threshold exists only to keep truly giant stores on the conservative per-file path.

### 3.2 Batch branch

For each destination group (canonical, or overflow when `route_all_to_overflow`):
1. Partition the non-skipped shards into chunks of ≤ `batch_chunk_files`.
2. Per chunk: `ops = [CommitOperationAdd(path_in_repo=dest, path_or_fileobj=str(shard)) for ...]`; `retry_transient(lambda: api.create_commit(repo_id=..., repo_type=..., operations=ops, commit_message=f"upload_dir_sharded batch {i}/{n} ({len(ops)} files)"), what=f"create_commit({repo}:{prefix} chunk {i}/{n})")`.
3. Reactive quota-403 on a canonical chunk: `_is_storage_quota_403` → `_ensure_overflow_repo` + emit event + pointer ONCE (reuse `emitted_prefixes`), then re-commit THIS chunk and all REMAINING chunks to the overflow repo (`repo_type="model"`); those dests join `result.rerouted` (and `result.uploaded`, parity as today). Non-quota errors re-raise (fail-loud); a both-repos-refused chunk raises the existing `RuntimeError` shape.
4. All committed/skipped shards enter `pending` → existing `_batched_verify` → existing delete pass. Unchanged.

### 3.3 Skip-if-present resume probe (BOTH modes)

At entry (after `shards` is computed, before the proactive probe — the probe list shrinks accordingly... NO: keep `projected` = full-store sum for the headroom probe (conservative; headroom is about total store size), but compute the SKIP set first so the per-mode upload loops exclude skipped shards):
1. `remote = _remote_sizes_under_prefix(api, repo_id, prefix, repo_type)` (primary destination).
2. If `f"{prefix}/OVERFLOW_POINTER.json" in remote` (a prior run rerouted): also probe the overflow repo and merge (overflow hits checked at `repo_type="model"`).
3. A shard is SKIPPED iff its dest is present with `size == shard.stat().st_size` (size mismatch → re-upload). Skipped shards: recorded in new `ShardUploadResult.skipped_existing: list[str]` (additive field, `default_factory=list`); appended to `pending` with their found (repo, repo_type) so verify + delete cover them; NOT appended to `uploaded` (that list keeps meaning "committed or rerouted by this call").
4. `verify=False` fast path: probe still runs (it is the resume feature), but no `_batched_verify`.
5. Probe failure semantics: rides `retry_transient`; on exhaustion the error propagates (fail-loud) — a resume probe that cannot read the Hub must not silently re-upload everything against a quota'd repo. Escape hatch: `resume_skip: bool = True` kwarg — `False` restores today's always-upload behavior.

### 3.4 What does NOT change

Per-file walk body (retained verbatim for `batch=False` / over-threshold stores, minus the skip-set exclusion); `_verify_present`; `_batched_verify`; pointer/event writers; `_reroute_to_overflow`; proactive #1034 gating (verdict + privacy threading); result parity (rerouted ⊂ uploaded); module docstring updated to describe the two modes.

## 5. Test plan (new tests)

1. `test_batch_happy_path_one_commit` — 5 shards, auto mode → exactly 1 `create_commit` on canonical, 0 `upload_file` shard calls, verify + delete, `rerouted == []`.
2. `test_batch_chunking` — `batch_chunk_files=2`, 5 shards → 3 commits, all dests present.
3. `test_batch_quota_403_reroutes_all_chunks` — canonical in `fail_quota_repos` → all chunks land overflow (`model`), ONE pointer + ONE JSONL event, `rerouted` == all dests, parity `uploaded` == all dests, locals deleted.
4. `test_batch_mid_store_403_splits_once` — first chunk lands canonical, 403 from chunk 2 → remaining chunks to overflow, ONE pointer/event, both result lists correct.
5. `test_batch_proactive_headroom_routes_to_overflow` — insufficient + public (mocks as in #1034 tests) → chunks committed straight to overflow, zero canonical LFS attempts, one pointer/event.
6. `test_resume_skips_present_same_size` — remote listing pre-seeded with 2/3 dests at matching size → 1 file committed, `skipped_existing` lists 2, all 3 deleted under `delete_local=True`.
7. `test_resume_size_mismatch_reuploads` — present-but-different-size → re-committed.
8. `test_resume_probe_absent_prefix_uploads_all` — EntryNotFoundError from tree → full upload (regression for the 404-is-expected rule).
9. `test_resume_skip_false_disables_probe` — `resume_skip=False` → no listing call, everything uploads.
10. `test_auto_threshold_routes_large_store_to_perfile` — env `EPM_UPLOAD_BATCH_MAX_GB` set tiny → per-file walk used (`upload_file` calls, zero `create_commit`).
11. `test_batch_false_forces_legacy` / `test_batch_true_forces_batch`.
12. `test_batch_nonquota_error_reraises_no_delete` — 500 on `create_commit` → retry exhaustion → raise, locals intact.
13. Existing 18 tests: per-file pins updated with `batch=False`; the #1034 proactive tests re-checked in batch mode via test 5.
