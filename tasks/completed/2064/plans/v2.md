# Plan — task #2064: registry drift at an allocated id must not break `task.py new` fleet-wide

### 0.0 TL;DR (plain English — the user reads this first)

- **What I'll do:** make `task.py new` self-heal when it discovers that the task id it just allocated already has a folder on disk that `tasks/REGISTRY.json` doesn't know about (registry drift). Today that shape re-issues the same colliding id to EVERY caller and each one dies with a bare `FileExistsError`, taking `file_infra_task.py` down fleet-wide until someone hand-runs the repair command. After this change the allocator detects the drift, runs the exact same reconcile logic the repair command uses (inline, under the lock it already holds), logs the drift loudly, and allocates the next genuinely-free id — and if the heal can't make progress it fails with a message naming the exact repair command instead of a bare traceback. A second, tiny prevention change narrows the window in which the registry write can be destroyed by the known #2015 pre-commit stash race in the first place.
- **What I expect:** `task.py new` keeps working through the drift shape that broke it on 2026-08-03; the existing `tests/test_task_workflow*.py tests/test_workflow*.py` suites stay green; new tests pin the heal, the empty-stub bump, and the fail-loud fallback.
- **What would change my mind:** if the in-lock reconcile turns out to be unsafe to inline (e.g. a hidden re-entrancy or a mutation beyond REGISTRY.json), I fall back to the body's conservative option — fail-loud naming `uv run python scripts/task.py audit --repair --apply` — which is strictly better than today's bare traceback.

### 2. Root cause (the body's plan-time demand: establish WHY the registry write was lost BEFORE choosing self-heal vs fail-loud)

**Finding: the lost registry write was destroyed by the #2015 pre-commit stash race (environmental), not by a `task_workflow.py` logic bug.** Evidence, all verified this session against git history:

- Commit `49c829deb5f0` (2026-08-03 13:05:23 -0700, "task #2052: create — …") contains ONLY `tasks/proposed/2052/{body.md,comments.jsonl,events.jsonl}`. `tasks/REGISTRY.json` is ABSENT from the commit even though `create_task` passes `[path, registry_path()]` to `_commit_after_durable_append` — i.e. at `git add` time the working-tree REGISTRY.json was byte-equal to HEAD, so there was nothing to stage.
- `git log -S'"2052"' -- tasks/REGISTRY.json` shows the ONLY commit ever adding 2052's entry is the reconcile commit `1002058a34` at 13:11:48 ("registry-reconcile: … added #2052; highest_id 2051->2052") — the in-session hand repair via `task.py audit --repair --apply`.
- Mechanism (matches `.claude/rules/repo-root-uncommitted-state.md` exactly): `create_task` writes REGISTRY.json via `_save_registry` and only later stages it inside `_git_commit` — after `_wait_for_sequencer_clear`, a window of seconds to minutes under fleet load. During that window the write sits **tracked-modified-unstaged**, which is precisely the state the #2015 race destroys: a concurrent session's pre-commit stash cycle snapshots the repo-wide unstaged diff, runs `git checkout -- .` (reverting REGISTRY.json to HEAD), and a conflicting restore permanently re-applies the stale snapshot. The task-folder files survived because they were UNTRACKED (new dir) — untracked files are invisible to the stash cycle. The observed commit shape (folder committed, registry reverted) is exactly this signature.
- **Consequence for the design choice:** the body ordered "auto-repair … should wait on the root-cause finding." The root cause is an external destroyer of unstaged tracked writes — the on-disk task tree remains the durable source of truth and REGISTRY.json is a derived index (`_registry_set` re-snapshots it from `body.md`). Auto-repair (self-heal) is therefore safe and justified: the heal re-derives the index from disk with the SAME classification policy as `reconcile_registry` — nothing is guessed. `Decision: self-heal inline, with fail-loud-naming-the-repair-command as the fallback for any shape the heal cannot fix.`

**Prior work reused (no new policy invented):** `reconcile_registry(apply=True)` (task_workflow.py:7102) already defines the exact repair semantics — `_reconcile_plan` (pure read, :6988) classifies drift into stale_real / missing_real / empty_stub / skipped; `_reconcile_apply_pending` (:7079) re-snapshots readable bodies and never fabricates unreadable ones; `_reconcile_highest_id` (:6950) bumps past empty-stub ids that are deliberately never registered. **Constraint discovered this session:** `reconcile_registry(apply=True)` takes `_locked()` itself and `_locked()` opens a fresh fd per call, so calling it from inside `create_task`'s lock would SELF-DEADLOCK — the heal must inline the three helpers instead of reusing the entrypoint. The helpers are exactly the reconcile apply body minus lock + commit, so the two paths cannot disagree about what counts as drift.

**Live-sibling overlap:** none — `spawn_session.py list` maps no other live session to `task_workflow.py` allocation work; #2015 (the race itself) is a `completed` analysis task whose rejected-levers table explicitly leaves per-write narrowing + consumer hardening to callers (this task).

### 3. Hypothesis (behavioral contract, fully pinned by tests)

1. With an on-disk `tasks/<status>/<id>` folder absent from REGISTRY.json at the allocation id, `create_task` succeeds: drift logged at ERROR level, orphan with readable `body.md` registered (missing_real policy), bodyless stub bumped past WITHOUT registration or deletion (empty_stub policy), new task allocated at the first genuinely-free id, everything committed in the create's ONE existing commit.
2. `create_task` NEVER allocates over an existing on-disk folder (post-heal `highest_id ≥ max(registered ids, max on-disk id)` by `_reconcile_highest_id`'s contract).
3. If a second collision occurs after a full heal (something raced inside the lock, or an un-healable shape), `task.py new` raises a `RuntimeError` naming `uv run python scripts/task.py audit --repair --apply` — never a bare `FileExistsError` traceback.
4. Lock scope and commit count are unchanged: one `_locked()` region, one `_commit_after_durable_append` per create (constraint from the body: no double-commit, no widened lock scope).

Falsifier: any command in §6 failing.

#### Deliverable 1 — allocation-site drift detection + inline self-heal (`create_task`, ~L5622)

New module-level helper (placed near the reconcile helpers, ~L7080):

```python
def _heal_registry_drift_locked(reg: dict[str, Any], *, colliding_id: int) -> None:
    """Self-heal registry drift discovered at the create_task allocation site
    (#2064: an on-disk task folder missing from REGISTRY.json re-issued the
    same colliding id to every caller after the #2015 stash race destroyed a
    registry write). MUST be called while ALREADY holding _locked() —
    reconcile_registry(apply=True) would self-deadlock (fresh flock fd per
    call), so this inlines its apply body minus lock + commit: the caller's
    own _save_registry + commit persist the heal. Mutates ``reg`` in place.
    """
    _log.error(
        "registry drift at allocated task id %s: on-disk folder exists with no "
        "REGISTRY.json entry (#2064; see #2015 for the likely destroyer). "
        "Self-healing via in-lock reconcile.", colliding_id,
    )
    repo, td = repo_root(), tasks_dir()
    stale, missing, empty_stubs, skipped, disk = _reconcile_plan(repo, td, reg)
    applied_stale = _reconcile_apply_pending(reg, stale, skipped)
    applied_missing = _reconcile_apply_pending(reg, missing, skipped)
    _reconcile_highest_id(reg, max((int(t) for t in disk), default=0))
    _log.error(
        "drift heal: %d stale re-pointed, %d missing registered, %d empty stubs "
        "bumped past (never registered), %d skipped; highest_id now %s",
        len(applied_stale), len(applied_missing), len(empty_stubs), len(skipped),
        reg.get("highest_id"),
    )
```

Allocation site in `create_task` (inside the existing `with _locked():`):

```python
        task_id = reg.get("highest_id", 0) + 1
```

Notes: (a) exactly ONE heal attempt — after a full reconcile `highest_id ≥` every on-disk id by construction, so a second collision is un-healable-by-reconcile and fails loud with the command; (b) the heal's registry mutations ride the create's existing `_save_registry(reg)` + `_commit_after_durable_append([path, registry_path()], ...)` — one write, one commit, lock scope untouched; (c) the drift stays VISIBLE: two ERROR-level log lines (the crash-signal constraint: the drift is a symptom of a lost write — heal it, but never silently); (d) the sibling drift shape where the id IS registered but `highest_id` drifted low heals identically via `_reconcile_highest_id` (it bumps to max registered id too) — no special case; (e) when the heal changed anything, append ` (+registry drift heal, #2064)` to the create's commit message so the forensic trail survives in history.

#### Deliverable 2 — prevention: narrow the #2015 exposure window for every registry write

Add a fail-soft immediate stage after the atomic write in `_save_registry` (all call sites protected by one change: 11 in-module — L5209/5427/5522/5674/5805/5819/5851/5915/6091/6211/7169 — plus 2 external in `scripts/sagan_import.py:281,296`; critic-verified count):

```python
def _save_registry(registry: dict[str, Any]) -> None:
    rp = registry_path()
    ...existing tmp-write + replace...
    # #2064/#2015: stage the just-written registry immediately. Staged content
    # survives the pre-commit stash cycle (write-tree snapshots the index;
    # `checkout -- .` reverts TO index content), so this narrows the
    # destroyable tracked-modified-unstaged window from "until _git_commit's
    # sequencer wait clears" (seconds-minutes) to milliseconds. Fail-soft:
    # on any failure (non-git test tmp dir, exhausted lock budget) degrade
    # to today's behavior — _git_commit stages again at commit time.
    try:
        proc = _run_git(["add", "--", str(rp)], check=False)
        if proc.returncode != 0:
            _log.warning("best-effort registry stage failed (rc=%s): %s",
                         proc.returncode, (proc.stderr or "").strip()[:200])
    except Exception as exc:  # never let staging break a registry write
        _log.warning("best-effort registry stage failed: %s", exc)
```

Notes: (a) `_run_git` (task_workflow.py:7394) already runs at the repo root with bounded lock-contention retry — reuse it, no new subprocess plumbing; (b) `check=False` + broad catch is deliberate and DISCLOSED fail-soft (prevention layer, not correctness layer — D1 is the correctness layer; the fail-fast rule's crash-is-the-signal concern is answered by the WARN log); (c) semantics under `git commit --only -- <paths>` are unchanged — `--only` commits working-tree state of the named paths, and every `task.py` mutation commits by explicit pathspec, so pre-staged registry content is either swept by the mutation's own commit (all `_save_registry` callers include `registry_path()` in their pathspec) or harmlessly re-staged by the next write; (d) test-suite tmp dirs without a git repo hit the fail-soft branch (pinned by test D below).

### 7. Risks

- **R1 — in-lock scan cost:** `_reconcile_plan` walks all task dirs (~2.2k) and reads `body.md` frontmatter for pending entries. Runs ONLY on the collision path (rare — once per drift episode, vs today's infinite-crash loop); the identical scan already runs under the same flock in `reconcile_registry(apply=True)`. Accepted.
- **R2 — early-stage side effects:** the `git add` touches the shared index outside a commit window. Scoped to one path, lock-retry-bounded via `_run_git`, fail-soft; a concurrent `--only` commit cannot accidentally commit it (pathspec-scoped). Residual: staged-but-uncommitted registry content is exposed to the #1894 bare-commit sweep — but every fleet committer uses pathspec commits by standing rule, and the content is identical to what the next registry commit would write anyway.
- **R2b — in-lock subprocess latency (critic concern, accepted):** D2 adds one git subprocess inside the flock per registry write; `_run_git`'s bounded lock-contention retry (default ≤60s, `EPM_TASKPY_LOCK_WAIT_SECONDS`) can extend flock hold time under heavy index.lock contention — same contention class as the existing in-lock `_git_commit`; non-lock errors return immediately. Watch mutation latency after landing. Tests running against the real repo with `TASK_PY_NO_COMMIT=1` will now leave a staged-registry line in `git status` — benign (identical content to the next registry commit).
- **R3 — heal masking recurring loss:** self-heal could hide a chronic destroyer. Mitigated: two ERROR log lines + the commit-message suffix per heal episode keep every occurrence forensically visible; D2 attacks the destroyer's window directly.
