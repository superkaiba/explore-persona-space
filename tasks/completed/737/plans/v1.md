# Plan — Issue #737: artifact-reuse `(h)` check for reused training-input mixes / on-policy caches

## Plan Summary

**What this is.** A workflow-surface documentation/spec edit (`kind: infra`,
0 GPU-h, non-architectural). It adds an **eighth** reuse-fitness check — `(h)`
— to the artifact-reuse fitness checklist, covering REUSED **training-input
artifacts** (a parent's `train/*.jsonl` mix, an on-policy response cache, a
reused eval JSON consumed as a downstream input). Today the `(a)-(g)`
checklist verifies that reused ADAPTERS/checkpoints resolve on HF (check `(e)`)
and pass recipe/regime/scaling fitness, but there is NO check that a reused
TRAINING-INPUT MIX is fetchable on the TARGET BACKEND before plan approval.

**The (h) check, two parts.** (i) the reused training-input file resolves on HF
via `huggingface_hub.list_repo_files`; (ii) the TARGET backend can actually
fetch it — RunPod pods can `snapshot_download` any HF-resolved file (so
fetchability ≈ HF resolution there), but the **git-clone-only GCP and SLURM
lanes stage NO VM-local `data/`**, so a mix that exists only as an
un-uploaded local-VM file is UNREACHABLE there. If `(h)` fails: the plan MUST
either upload the mix to HF first OR include a self-contained regen phase
(reuse the parent's deterministic build blocks) that rebuilds the mix on the
worker. The check is enforced at PLANNING time (planner self-attest →
consistency-checker independent re-check → critic REVISE), not at phase2
runtime.

## 1. Goal

Add a reuse-fitness check `(h)` to the artifact-reuse checklist so that a plan
reusing a parent experiment's TRAINING-INPUT MIX / on-policy response cache /
downstream-input eval JSON must verify, BEFORE plan approval, that each reused
input file (i) resolves on HF via `huggingface_hub.list_repo_files` AND (ii) is
fetchable on the chosen target backend — and, when it is not fetchable (the
git-clone-only GCP/SLURM lanes stage no VM-local `data/`), the plan must upload
the mix first or carry a self-contained regen phase. Propagate the `(h)`
reference into every call site that enumerates `(a)-(g)` today.

## 2. Prior Work

- **`.claude/rules/artifact-reuse.md`** is the canonical `(a)-(g)` fitness
  checklist (the bulleted list spans lines 32-62; `(g)` ends at line 62, the
  "Any check that fails → retrain / regenerate" line is at line 64). `(e)`
  already covers HF resolution via `huggingface_hub.list_repo_files` for
  adapters/checkpoints/datasets, and `(f)` covers content-identity / SHA-pinning
  when execution fetches an HF mirror of a locally-verified file. Neither
  covers the case where a reused training-input file was NEVER uploaded and the
  target lane cannot stage it.
- **Enforcement is a 3-stage defense** (artifact-reuse.md lines 66-72): planner
  step 5 self-attest → consistency-checker independent diff + Hub-resolution
  gate → critic Methodology lens item 9 REVISE. The new `(h)` check slots into
  the same three stages.
- **The motivating incident (#734 round 4):** a plan reusing a parent's
  `train/*.jsonl` mix that the parent built but never uploaded passed planning
  + 3 review rounds, then crashed phase2 at the pre-train
  `assert data_path.exists()` on the git-clone-only GCP lane because the mix is
  on neither HF repo and the lane cannot stage it. The `(a)-(g)` check verifies
  reused ADAPTERS resolve on HF (`(e)`), but has no check for training-input
  mixes / on-policy caches; the fact-checker verifies adapter paths but not
  train-mix paths.
- **GCP-lane mechanics (verified from source).**
  `src/explore_persona_space/backends/gcp.py` `render_startup_script` (lines
  1360-1365) does `git clone --depth 1 --branch <branch> <repo_url>
  "$WORKLOAD_ROOT"` and runs the `workload_cmd` verbatim from `$WORKLOAD_ROOT`
  (lines 954-1006). There is no VM-local `data/` mounted into the GCE
  instance — the only files present are what `git clone` brings plus whatever
  the workload itself downloads (HF, etc.). So a `data/issue_<N>/.../train.jsonl`
  that lives only as an un-committed, un-uploaded local-VM file is genuinely
  unreachable on the GCP lane. This grounds the `(h)` fetchability semantics.
- **Prior workflow-surface rule-file edits** establish the convention: this is
  an additive bullet to an existing checklist + propagated references, the same
  shape as prior `(a)-(g)` extensions (`(g)` was itself added for #601, `(f)`
  for #600). No new subsystem, no contract change.

## 3. Expected Outcome (replaces Hypothesis for a workflow-fix)

A future plan that reuses a training-input mix WITHOUT both (i) HF resolution
and (ii) target-backend fetchability (or a self-contained regen phase) is
REVISEd at PLANNING time by BOTH the critic Methodology lens (item 9) and the
consistency-checker (the BLOCK "Reused trained artifact …" row, which now also
re-checks `(h)`), instead of crashing phase2 at the pre-train
`assert data_path.exists()` on a git-clone-only lane. The planner self-attests
`(h)` in step 5 and records a per-input-artifact `Source:` line in §11 naming
how each reused input file is fetched on the target backend.
