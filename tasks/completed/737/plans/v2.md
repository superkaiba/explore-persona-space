# Plan — Issue #737: artifact-reuse `(h)` check for reused training-input mixes / on-policy caches

## Plan Summary

**What this is.** A workflow-surface documentation/spec edit (`kind: infra`,
0 GPU-h, non-architectural). It adds an **eighth** reuse-fitness check — `(h)`
— to the artifact-reuse fitness checklist, covering REUSED **training-input
artifacts** (a parent's `train/*.jsonl` mix, an on-policy response cache, a
reused eval JSON consumed as a downstream input). Today the `(a)-(g)`
checklist verifies that reused ADAPTERS/checkpoints resolve on HF (check `(e)`)
and pass recipe/regime/scaling fitness, but there is NO check that a reused
TRAINING-INPUT MIX is fetchable on the TARGET BACKEND before plan approval.

**The (h) check, two parts.** (i) the reused training-input file resolves on HF
via `huggingface_hub.list_repo_files`; (ii) the TARGET backend can actually
fetch it — RunPod pods can `snapshot_download` any HF-resolved file (so
fetchability ≈ HF resolution there), but the **git-clone-only GCP and SLURM
lanes stage NO VM-local `data/`**, so a mix that exists only as an
un-uploaded local-VM file is UNREACHABLE there. If `(h)` fails: the plan MUST
either upload the mix to HF first OR include a self-contained regen phase
(reuse the parent's deterministic build blocks) that rebuilds the mix on the
worker. The check is enforced at PLANNING time (planner self-attest →
consistency-checker independent re-check → critic REVISE), not at phase2
runtime.

## 1. Goal

Add a reuse-fitness check `(h)` to the artifact-reuse checklist so that a plan
reusing a parent experiment's TRAINING-INPUT MIX / on-policy response cache /
downstream-input eval JSON must verify, BEFORE plan approval, that each reused
input file (i) resolves on HF via `huggingface_hub.list_repo_files` AND (ii) is
fetchable on the chosen target backend — and, when it is not fetchable (the
git-clone-only GCP/SLURM lanes stage no VM-local `data/`), the plan must upload
the mix first or carry a self-contained regen phase. Propagate the `(h)`
reference into EVERY call site that enumerates `(a)-(g)` today — including the
`verify_plan.py` `c6_reuse_fitness` heuristic, its test, and the implementer
mirror-set memory.

## 11. Decision Rationale

only design decisions are documentation choices, captured here:

- **Where the `(h)` bullet goes** (end of the checklist, after `(g)`, before

  Source: task brief + the file's existing structure.

  HF-resolution-only: because the motivating crash (#734 round-4) was a
  fetchability failure on a git-clone-only lane EVEN THOUGH the file could in
  principle have been uploaded — the distinction between "exists somewhere on
  HF" and "the chosen lane can stage it" is exactly the gap `(e)` does not
  close. Source: #734 candidate block + verified gcp.py git-clone-only
  mechanics (A6).
- **`verify_plan.py` c6 heuristic is UPDATED (Edit 6) but the PASS threshold is
  left at `>=4`:** the Goal says propagate `(h)` into "every call site that
  enumerates (a)-(g)", and the c6 heuristic + its test ARE such call sites

  "X/7" forever and silently not count an `(h)` attestation. The threshold
  stays `>=4` because `(h)` is N/A for the adapter-only majority; raising it
  would WARN on valid adapter reuse. Source: the brief's "every call site"
  clause + the existing c6 docstring intent ("forcing the section to exist").
- **Consistency-checker (h) re-check is prose-only, NOT a new fetchability
  script:** consistent with how `(e)` is already enforced (manual
  `list_repo_files` in the line-41 BLOCK row, no mechanical verifier). A
