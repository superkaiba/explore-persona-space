# Plan v3 — task #2185: document the RunPod HF-CDN zero-byte large-blob trap

**Kind:** `infra` (documentation + one fail-open preflight probe). No promotable
clean-result; completes on the Step 9c test-verdict path.

## Requirement

A pod provisioned for #2162 stage-2 could not download any large blob from the
Hugging Face CDN: pod DNS resolved `us.aws.cdn.hf.co` to APAC CloudFront edges
that answered HTTP **206 with zero bytes** and closed the connection. The single
upstream fault impersonates all three client-side accelerator failures in
sequence, so an agent walks the accelerator ladder to exhaustion and concludes
the pod or the Hub is broken. Root cause is CONFIRMED by the reporting agent
(`root_cause_confirmed: yes`, `gotcha_candidate: yes`), not inferred.

Make the next agent's diagnosis take minutes instead of most of an hour.

## Acceptance criteria

1. `.claude/rules/gotchas.md` carries an entry with (a) the three sequential
   presentations, (b) the three-way curl discriminator, (c) the rsync-relay
   recovery including the measured single-vs-parallel stream figures, and
   (d) an explicit discriminator against its two nearest neighbours (the
   hf-xet DOWNLOAD wedge and the download-accelerator FAILURE MATRIX).
2. The entry does NOT weaken, contradict, or bypass the xet wedge ladder in
   `.claude/rules/upload-policy.md`. It sits BESIDE that ladder; telling the
   two apart quickly is the point.
3. `preflight` gains a RunPod-gated, fail-open large-blob GET probe that WARNs

   error, never raises, and never blocks a launch.
4. A committed test pins the probe's three behaviours: zero-byte body → WARN,
   healthy body → silent, non-pod environment → not run.
5. `verify_plan.py` PASSes, and the no-flags `workflow_lint.py` plus the Step 9c mapped-test gate show no NEW failures vs the plan-time baseline (the repo-wide lint is pre-existing-red-exposed on origin/main, so Step 10d's baseline-subtracted gate is the binding check).

## Method delta — what differs from existing documentation

Two entries already cover HF download failures, and the new trap is precisely
the case they mislead on:

| Existing entry | Its failure shape | Why it misroutes this trap |
|---|---|---|
| hf-xet DOWNLOAD wedge (`gotchas.md`) | native `xet_get` **hangs forever**, no exception; `du -sb` frozen; py-spy parked in `xet_get` | This trap fails **fast and loudly**. An agent matching on "xet download problem" applies the kill+replay ladder, which cannot help. |
| download-accelerator FAILURE MATRIX (`gotchas.md`) | the three transfer paths fail in **disjoint** domains; scope disables per workload | Assumes a **client** defect per path. A per-DC **network** fault violates the disjointness premise by failing all three at once, so the matrix's remedy (scope the disable) is a dead end. |

The new content is therefore the **discriminator**, not another accelerator
recipe: the pod-fails / pod-succeeds-elsewhere / VM-succeeds triad, plus the
relay recovery that no accelerator toggle can substitute for.

## Files touched

### 1. `.claude/rules/gotchas.md` — the primary deliverable

Insert ONE bullet immediately after the `HF Hub download-accelerator FAILURE
MATRIX` entry (currently line 218), so the reader who lands on the matrix meets
the discriminator next. Verbatim text:

```
- **RunPod pods can be DNS-steered to HF CDN edges that answer large-blob GETs with HTTP 206 and ZERO bytes — ONE upstream fault that impersonates all three accelerator failures in turn, so no client toggle fixes it; recover by relaying VM to pod over parallel rsync.** #2162's stage-2 pod resolved `us.aws.cdn.hf.co` to APAC CloudFront edges that returned 206 with an empty body and closed the connection, for every large blob. It presents SEQUENTIALLY as (1) the xet download wedge, (2) `hf_transfer`'s opaque bare `RuntimeError`, then (3) a plain-path `IncompleteRead(0 bytes)` — so an agent walks the accelerator ladder (`HF_HUB_DISABLE_XET=1`, then `HF_HUB_ENABLE_HF_TRANSFER=0`) and exhausts it: in #2162 every replay failed the SAME way, zero bytes delivered, surfacing as `IncompleteRead(0 bytes)` once the plain path was reached — because the fault is UPSTREAM of every client, so the toggle only changes which error text you get. Confounders that make the pod look healthy: general pod egress was 73 MB/s to Cloudflare, small-file HF GETs worked normally, and the VM pulled the SAME blob URL at 25 MB/s — so neither "the pod has no network" nor "the Hub is down" holds. **DISCRIMINATOR (~1 min, three curls):** pod to the HF blob URL FAILS (206, 0 bytes, closed) · pod to a large non-HF file SUCCEEDS (rules out pod egress / MTU / general bandwidth) · VM to the SAME HF blob URL SUCCEEDS (rules out the Hub and the artifact). That pod-fails / pod-succeeds-elsewhere / VM-succeeds triad IS the signature; both `h2` and `HTTP/1.1` fail, so it is not protocol negotiation. Told apart from the two entries above: the xet wedge HANGS with no exception (frozen `du -sb`, py-spy in `xet_get`) while this fails FAST; and the FAILURE MATRIX's disjoint-domain rule presumes a CLIENT defect per path, which a per-DC NETWORK fault violates by breaking all three at once — so "scope the disable per workload" is a dead end here, not a fix. **RECOVERY — relay VM to pod over parallel rsync** (the VM is the staging hop precisely because its CDN access works): a single transpacific stream ran ~10 MB/s, 5 parallel streams reached ~36 MB/s; #2162 moved a `vc_bank` store plus a full Qwen2.5-7B-Instruct snapshot (all 4 shards size-verified) that way, `RELAY-PAR-DONE rc=0`. Pinning a working edge IP via `curl --resolve` also works but only ~3 MB/s — a fallback for small sets, never a model snapshot. Afterward pin `HF_HUB_DISABLE_XET=1` + `HF_HUB_ENABLE_HF_TRANSFER=0` in the RUN env: once blobs arrive by relay the accelerators add nothing and their failure modes are the confusing part — a PER-WORKLOAD scope, consistent with xet-on-by-default (#2153), never a fleet-wide pin. That was safe in #2162 only because the runtime needed no large CDN transfers afterward (model cached, bank on disk, small API/CDN fetches working); a run that still has big-file UPLOAD legs keeps the accelerators ON for those and scopes the disables to the DOWNLOAD workload — the FAILURE MATRIX rule above, not an exception to it. Treat the DC as the variable: the specific edge set is DC-dependent, so never hardcode an edge. Direction matters — a future variant where the VM is the affected side needs a different staging hop, so re-run the discriminator rather than assuming symmetry. Pre-launch detection: `preflight`'s `check_hf_large_blob_get` WARNs with this diagnosis on RunPod (#2185).
```

### 2. `src/explore_persona_space/orchestrate/preflight.py` — the probe

Add `check_hf_large_blob_get(report)`, called from `preflight_check`
immediately after `check_connectivity(report)` (which already probes
huggingface.co reachability with a SMALL GET — this is its large-blob twin,
and the small-vs-large split is the whole discriminator).

Design, and why each choice:

- **Range GET, 1 MiB.** Request `Range: bytes=0-1048575` against a stable
  large blob and require a non-trivial body. The trap's signature is exactly
  "206 status, empty body", so a range request that returns 206 and reads 0
  bytes catches it precisely. 1 MiB at even the degraded ~3 MB/s edge is a
  fraction of a second; at the failing edge it returns instantly.
- **Probe through `huggingface.co`, not a CDN hostname.** Request
  `https://huggingface.co/Qwen/Qwen2.5-7B-Instruct/resolve/main/model-00001-of-00004.safetensors`
  and follow redirects. The 302 to the CDN is what makes the probe exercise
  whichever edge the pod's DNS steers it to — the actual variable. Hardcoding
  a CDN edge would defeat the purpose (and the body's own instruction to treat
  the DC as a variable). Overridable via `EPM_PREFLIGHT_LARGE_BLOB_URL`.
- **RunPod-gated.** Runs only under `is_runpod_env()`. The trap is confirmed on
  RunPod, the VM is the WORKING side by construction, and a SLURM compute node
  may legitimately have no egress — gating avoids both fleet-wide latency and
  false WARNs on lanes where the probe means nothing. A variant on another lane
  needs its own gating decision; noted in the docstring rather than guessed.
- **Fail-OPEN, WARN only.** A zero-byte / short / truncated read WARNs with the
  diagnosis. Every OTHER outcome (404 if the shard name changes, DNS failure,
  timeout, missing token, any unexpected exception) degrades to a quiet
  "inconclusive" note and proceeds. Rationale: `preflight`'s `ok=False` blocks
  launches fleet-wide, so a false hard FAIL is far more expensive than a missed
  catch — and the existing `check_hf_storage` / Step 6a.6 quota probe establish
  exactly this advisory discipline. The gotchas entry, not the probe, is the
  load-bearing deliverable; the probe is an early-warning convenience.
- **Kill switch** `EPM_SKIP_LARGE_BLOB_PROBE=1`, matching the codebase's
  existing `EPM_SKIP_*` convention.
- **Bounded.** Socket + total timeout ~20 s, so a hung edge cannot stall
  preflight.

WARN text (single line, names the recovery and the entry):

```
HF large-blob GET returned <status> with <n> bytes (expected >=1 MiB) — this pod may be DNS-steered to a CDN edge that serves 206 + 0 bytes. No accelerator toggle fixes it; see .claude/rules/gotchas.md (RunPod HF-CDN zero-byte large-blob trap) for the three-curl discriminator and the VM-to-pod parallel-rsync relay recovery.
```

### 3. `tests/test_preflight_large_blob_probe.py` — the pin

Four cases, all offline (the opener is injected/monkeypatched — no network in
the suite):

1. 206 + zero-byte body → exactly one warning, matching the diagnosis text;
   `report.ok` stays True (fail-open pinned, not just asserted in prose).
2. Healthy >=1 MiB body → no warning added.
3. Non-RunPod environment → probe does not run (no warning, no network call).
4. Opener raises → inconclusive, no warning, no error, no exception escapes.

Fail-loud pin: tests/test_preflight_large_blob_probe.py — case 4 pins that an opener which raises is swallowed to a silent inconclusive note (no warning, no error, no exception escapes past the probe) and case 1 pins that a 206 zero-byte body adds a warning without raising, so a future edit that turns the probe into a hard FAIL or lets an exception escape fails the suite rather than shipping green.

## Scope decisions on the body's two "Consider" items

The body delegates these to the implementing session. Both are decided here
with an argument, per CLAUDE.md's autonomous carve-out for scope calls.

**(a) Preflight probe — ACCEPT, as a WARN.** Cheap (one ~1 MiB range GET on a
box that is about to stage tens of GB), decisive (the signature is exact), and
the body itself prefers WARN over hard FAIL. Implemented as above.

**(b) Bootstrap pinning the two accelerator kill switches by default —
DECLINE.** Three reasons: (i) it contradicts a LANDED decision —
`upload-policy.md` records that xet stays ON by default with disables scoped
per workload (#2153); (ii) the body's own scope note forbids a fleet-wide pin
without an argument, and the argument runs the other way, since this is a
per-DC network fault rather than a client defect; (iii) it would mask a
legitimately working xet path everywhere else, buying breakage on the many
healthy DCs to paper over one. The gotchas entry already prescribes the pins
where they belong: in the RUN env of the affected pod, AFTER the relay.

**(c) `.claude/rules/LESSONS.md` trigger row — DECLINE, on mechanical
grounds.** Not requested by the body; recorded because the index is the
plan-time discovery surface and a reader may expect a row edit. `LESSONS.md` is
9,557 B against a hard `_LESSONS_MAX_BYTES` of 9,600 (43 B of headroom), and the
`gotchas` row is 1,175 B against a grandfather cap of exactly 1,175 (zero
headroom, by the ratchet's hug-live-size design). Any useful trigger clause
therefore forces BOTH a cap raise AND a lossy trim of other rows — and a
further lossy trim of this specific row was explicitly ruled out at #1269.
The entry stays discoverable by its own content: an agent hitting this greps
`gotchas.md` for `xet` / `hf_transfer` / `IncompleteRead`, which is how this
session located the insertion point. Revisit if a LESSONS trim lands

### Smoke blind-spot enumeration

- The probe's **FAILING branch is never exercised against a real broken edge.**
  Reproducing it requires a pod whose DNS steers to an affected APAC edge —
  the VM is the working side by construction, which is the premise of the whole
  trap. Case 1 of the unit test covers the branch with a stubbed 206 + zero-byte
  response, so the WARN wording and the fail-open behaviour are pinned, but no
  smoke phase proves the probe fires against the live fault. Accepted: the
  alternative is provisioning pods until one lands on a bad edge.
- The probe **substitutes a stubbed opener for the real network** in every test.
  No smoke phase performs a real large-blob GET, so a defect in URL
  construction or redirect handling would not surface locally. Mitigated by
  keeping the URL a single overridable constant and probing through
  `huggingface.co` rather than assembling a CDN URL.
- **No production gate is downgraded or skipped** under smoke: the probe adds no
  assertion and no error path, so there is no gate to weaken.
- **No production-only third-party import** is introduced; the probe uses
  `urllib.request` from the standard library, already imported in this module's
  sibling checks.
- The **`is_runpod_env()` TRUE branch is never exercised offline** — the gate
  test asserts the non-pod case (probe does not run), so a false-negative gate
  would make the probe a silent fleet-wide no-op that no local phase detects.
  Mitigated only by `is_runpod_env` being existing production code already
  relied on by other preflight paths, not by anything this round adds.
