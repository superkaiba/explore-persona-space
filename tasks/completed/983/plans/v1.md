## 1. Goal, requirement, acceptance criteria

**Goal (task frontmatter):** if a poll after done-detection observes NEW `[phase=...]` lines after the matched done line, escalate/alert rather than remain silently terminal.

**Requirement:** the guard must (a) fire only on genuinely new phase-transition lines appearing after the recorded done, (b) fire at most once per done-episode, (c) never change any tick's status verdict, (d) survive the bounded 500-line tail window (`tail -500` at :1372), SSH-failure fallback ticks (empty tails, :1408/:1463), and same-issue relaunches (state file persists across runs).

**Acceptance criteria:**
1. Done tick → episode recorded in the state file; no advisory.
2. Later tick, new phase line after the recorded done → exactly one `[post-done-phase-advisory]` `epm:progress` post + Telegram push attempt; `PollResult.post_done_phase_advisory_posted == True`.
3. Later tick, same tail / non-phase lines / #597-noise done lines / byte-identical done re-emission → no fire.
4. Fresh `epm:run-launched` after the episode → episode voided; the new run's phase lines never fire against the old done.
5. All existing poll_pipeline tests pass unchanged; ruff + `workflow_lint.py` default run pass.

## 2. Method delta vs the existing done-corroboration machinery

The **#545 corroboration block** (:3798–3825) gates the *INITIAL* done verdict, same-tick: an uncorroborated done-parse (pid alive + no results sentinel) is demoted to the latest non-done phase before the status decision. The **#597 noise regex** (:359–362) gates *which line* may parse as done at all. Both are within-tick, parse-time defenses.

**This guard is a cross-tick, post-acceptance audit.** It activates only *after* a done the #545 gate ACCEPTED (pid-dead or sentinel-corroborated), and detects the class both gates are structurally blind to: a `.py` dispatcher that fans out to child scripts (the #930 §4.6 residual gap (i) — `scripts/issue545_sweep.py:345 → issue545_eval_cell.py` is the archetype) whose parent exits (pid-dead ⇒ corroborates) or whose sentinel exists early, while detached children keep emitting `[phase=...]` lines. The contradiction is only observable at a LATER poll — done first, more phase lines after. The guard never touches any tick's verdict; it makes the contradiction loud.

### 3.1 New helper — phase-bearing line scan (near `latest_phase`, ~:2046)

```python
_POST_DONE_LINE_MAX = 400        # chars stored/compared per line (bounded state file)
_POST_DONE_NOTE_MAX_LINES = 5    # new lines quoted in the advisory note

def _phase_bearing_lines(log_tail: str) -> list[str]:
    """Ordered (oldest -> newest) raw texts of phase-bearing lines.

    Same per-line predicate as ``latest_phase``: PHASE_RE must match; a
    done-token line also matching DONE_QUOTED_NOISE_RE (#597 failure message
    quoting the token) is skipped. Truncated to _POST_DONE_LINE_MAX so the
    state-file identity comparison is bounded."""
    out: list[str] = []
    for line in log_tail.splitlines():
        m = PHASE_RE.search(line)
        if not m:
            continue
        if m.group(1) == "done" and DONE_QUOTED_NOISE_RE.search(line):
            continue
        out.append(line[:_POST_DONE_LINE_MAX])
    return out
```

`latest_phase` itself is untouched (public cross-module contract, :2015).

### 3.2 Pure decision core (WHERE the guard's logic lives — design Q1)

```python
@dataclass(frozen=True)
class PostDonePhaseUpdate:
    should_post: bool
    done_line: str                     # "" = no active done episode
    done_epoch: int                    # 0 = no active episode
    advisory_posted: bool              # dedup flag carried forward
    new_phase_lines: tuple[str, ...]   # observed-this-tick (surfaced even when deduped)

def _post_done_phase_update(
    *,
    current_phase: str,          # the post-#545-corroboration phase
    log_tail: str,
    prev_done_line: str,
    prev_done_epoch: int,
    prev_posted: bool,
    run_age_sec: float | None,
    now_epoch: int,
) -> PostDonePhaseUpdate:
    # Run-scope clamp (mirrors the last_phase_change_epoch relaunch clamp,
    # poll_once :4082-4087): an episode recorded BEFORE the current run's
    # epm:run-launched belongs to a previous run — void it.
    if prev_done_epoch > 0 and run_age_sec is not None and prev_done_epoch < now_epoch - run_age_sec:
        prev_done_line, prev_done_epoch, prev_posted = "", 0, False
    if not prev_done_line:
        if current_phase == "done":
            lines = _phase_bearing_lines(log_tail)
            if lines:  # by construction (reversed scan in latest_phase) the
                       # LAST phase-bearing line IS the matched done line
                return PostDonePhaseUpdate(False, lines[-1], now_epoch, False, ())
        return PostDonePhaseUpdate(False, "", 0, False, ())
    # Active episode: find lines strictly AFTER the recorded done line.
    lines = _phase_bearing_lines(log_tail)
    try:
        anchor = len(lines) - 1 - lines[::-1].index(prev_done_line)  # LAST occurrence
        candidates = lines[anchor + 1:]
    except ValueError:
        # Done line scrolled out of the bounded tail: the log is append-only,
        # so every line ABOVE it scrolled out first — any phase line still
        # visible is NEWER than the recorded done.
        candidates = lines
    new_lines = tuple(ln for ln in candidates if ln != prev_done_line)  # FP control (i)
    return PostDonePhaseUpdate(
        bool(new_lines) and not prev_posted,
        prev_done_line, prev_done_epoch, prev_posted, new_lines,
    )
```

**Episode-start condition:** the corroborated `current_phase == "done"` — deliberately NOT `status == "done"`, so a gate-sentinel tick whose pipeline also reached done (gate precedence at :3906–3909) still records the episode. Once set, `done_line`/`done_epoch` are never overwritten within a run; only the run-scope clamp voids them.

### 3.3 Wiring helper (post + push + dedup — design Q3, Q5)

```python
def _maybe_post_post_done_phase_advisory(
    *, issue: int, pod: str, current_phase: str, log_tail: str,
    prev_state: dict[str, str], run_age_sec: float | None, now_epoch: int,
) -> tuple[str, int, bool, bool, tuple[str, ...]]:
    """Returns (done_line, done_epoch, posted_flag, posted_this_tick, new_lines)
    for the caller to persist via _save_state. Guarded state parses (a corrupt
    epoch resets to 0, never raises into poll_once). A post failure is logged
    and posted_flag is NOT set, so the next tick retries — identical contract
    to _maybe_post_gpu_width_advisory (:2328-2331)."""
    prev_line = prev_state.get("post_done_line", "") or ""
    try:
        prev_epoch = int(float(prev_state.get("post_done_epoch", "0") or 0))
    except (TypeError, ValueError):
        prev_epoch = 0
    prev_posted = prev_state.get("post_done_advisory_posted", "0") == "1"
    u = _post_done_phase_update(
        current_phase=current_phase, log_tail=log_tail, prev_done_line=prev_line,
        prev_done_epoch=prev_epoch, prev_posted=prev_posted,
        run_age_sec=run_age_sec, now_epoch=now_epoch,
    )
    if not u.should_post:
        return u.done_line, u.done_epoch, u.advisory_posted, False, u.new_phase_lines
    quoted = "\n".join(f"  {ln[:200]}" for ln in u.new_phase_lines[:_POST_DONE_NOTE_MAX_LINES])
    note = (
        f"[post-done-phase-advisory] {len(u.new_phase_lines)} NEW [phase=...] line(s) appeared "
        f"AFTER the done line this poller reported as terminal "
        f"({max(0, now_epoch - u.done_epoch) // 60} min ago):\n{quoted}\n"
        f"recorded done line: {u.done_line[:200]}\n"
        "The earlier status=done may have been FALSE (the .py-dispatcher subprocess fan-out "
        "class — workflow_lint --check-phase-done-reserved residual gap (i), #930/#545): a "
        "child script may still be running, and any orchestrator action keyed on the done "
        "(advance to verifying, Step-8 pod termination) may have been premature. VERIFY the "
        "run actually completed (results sentinel + uploads) and fix the emitting dispatcher "
        "per pod-side-reporting.md ([phase=done] is reserved for the single terminal line). "
        "Advisory only: this tick's status verdict is unchanged and nothing was stopped."
    )
    try:
        post_event(issue, "epm:progress", by="poll_pipeline", note=note,
                   phase=current_phase, pod=pod, post_done_phase_advisory=True)
    except Exception as exc:
        log.error("post-done phase advisory post failed (next tick will retry): %s", exc)
        return u.done_line, u.done_epoch, False, False, u.new_phase_lines
    _telegram_push(  # fail-soft, never blocks recording (mirror of :3148-3152)
        f"[#{issue}] post-done phase advisory: {len(u.new_phase_lines)} new [phase=...] "
        f"line(s) after the reported done on {pod} — earlier done may be FALSE "
        "(advisory only; nothing stopped)."
    )
    log.warning("posted post-done phase advisory for #%d: %d new phase line(s) on pod %s",
                issue, len(u.new_phase_lines), pod)
    return u.done_line, u.done_epoch, True, True, u.new_phase_lines
```

### 3.5 Who polls after done (design Q2)

The guard is useful iff a post-done `poll_once` happens against the same per-issue state file (default `.claude/cache/poll-pipeline-<N>.json`, :4269 — persists across invocations). Post-done invocations that demonstrably occur:

1. **Orchestrator confirmation / late ticks** — the `/issue` Step 6d.2 bg-Bash chain exits on terminal, but the orchestrator routinely re-runs `poll_pipeline.py` before acting on a done, and a chain tick already in flight when done lands executes anyway.
2. **Crash-recovery respawn** — the watcher's respawned `/issue --auto` session re-derives state and re-polls even when the previous session had already seen done.
3. **`backend_poll.py` RunPod lane** — `RunPodBackend.poll` delegates to `poll_once` on every invocation; a driver/diagnostic invocation after a terminal verdict lands here.
4. **Manual diagnostics** — `uv run python scripts/poll_pipeline.py --issue N --pod ...` (the standard "double-check the pod" move).

`tick_triage.py` does NOT invoke poll_pipeline (verified: zero grep matches) — but the session it wakes may (case 1/2). **No-op guarantee when no post-done poll happens:** the done tick writes three state keys and nothing else; there is no timer, no background thread, no behavior change.

## 4. Controls / false-positive analysis (design Q4)

Mechanism chosen: **line-identity anchored comparison** (recorded done-line text; candidates = phase-bearing lines positionally after its last occurrence in the current tail; all phase lines when it scrolled out). Per the required cases:

| Case | Behavior | Why |
|---|---|---|
| (i) re-observing the SAME done line | no fire | it is the anchor; and the `ln != prev_done_line` filter drops byte-identical later re-emissions |
| (ii) non-phase lines after done (post-done uploads, sentinel drains) | no fire | `_phase_bearing_lines` admits only `PHASE_RE` matches |
| (iii) `DONE_QUOTED_NOISE_RE`-matching done lines after done (`... FAILED rc=1 - [phase=done] NOT emitted`) | no fire | same skip predicate as `latest_phase` :2040 (done-token + noise ⇒ excluded) |
| (iv) done is the LAST phase line, earlier phase lines still visible above it | no fire | candidates start strictly AFTER the anchor's last occurrence |
| per-cell `[phase=done] eval cell X complete` straggler AFTER the accepted terminal done | **fires** | correct — a cell completing after terminal done IS the fan-out FN class this guard exists for |
| SSH-failure tick (empty tail fallback :1408/:1463) | no fire, episode retained | empty tail ⇒ no phase lines ⇒ no candidates; state carried through unchanged |
| done line scrolled out of the 500-line tail, no new phase lines | no fire | append-only log ⇒ everything above done scrolled out first ⇒ no phase lines remain |
| relaunch / same-issue follow-up round | no fire against the old done | run-scope clamp voids the episode when `post_done_epoch < now − run_age_sec` |

**Why not timestamp-prefix comparison:** the timestamp prefix is *expected* but not *required* by `PHASE_RE` (:340; the docstring at :256 says "anything matching the regex will be picked up") — a dispatcher emitting un-timestamped phase lines would make timestamp parsing silently inert, and mixed sub-second emissions tie. **Why not positional comparison:** the probe reads a bounded `tail -500` sliding window (:1372), so absolute positions/counts are unstable as lines scroll. Line identity is stable under the sliding window; its one failure mode (a byte-identical duplicate line counted as old) fails toward QUIET, the correct direction for an advisory.

**Residual FP (accepted, low severity):** a relaunch that never posts a fresh `epm:run-launched` (off-contract — the experimenter always posts it) and reuses the same log path would fire once against the stale episode. Cost: one advisory marker + push; arguably even that firing is informative (phase lines after a recorded done with no new launch record IS suspicious). **Residual FN (accepted):** post-done activity emitting only non-phase lines is invisible — out of scope by the task's own definition (the signal IS new `[phase=...]` lines).

## 6. Kill criteria

Checked: the orchestrator confirmation re-poll, crash-recovery respawn re-poll, `backend_poll.py` per-invocation delegation, and manual CLI diagnostics all exist (§3.5) — not dead code. - If `post_event` rejected unknown extra kwargs (it does not — `gpu_width_advisory=True` :2379, `gpu_idle_escalation=True` :3143 are live precedents), the marker shape would need the note-only form.

## 11. Decision Rationale

`N/A — no training hyperparameters` (kind: infra, no model training). `N/A — no behavioral construct` (no measured DV; the "eval" is a deterministic test suite).

- **D1 — Advisory-only; status verdict never flipped (vs demote-to-running).**
  *What:* the guard posts a loud marker + push; the tick's status stays whatever the existing arbiters computed.
  *Why:* (a) By the time a post-done poll observes the contradiction, the orchestrator has usually already consumed the done — status flipped to `verifying`, Step-8 possibly terminated the pod. A poller-initiated `done → running` regression creates a double-transition hazard the orchestrator's state machine does not support, and cannot undo a termination anyway; remediation genuinely requires orchestrator/human judgment (was data lost? re-run?), which an alert routes correctly. (b) On the tick that observes new phase lines, the verdict is *already* recomputed from live signals — a new latest phase token means `current_phase != "done"`, so the tick does not "remain terminal" by itself; the miss is that nobody is TOLD the earlier done was contradicted, which the advisory fixes. (c) A false demote is expensive (stalls the pipeline against a terminated pod); a false advisory costs one marker. (d) Consistency: all five sibling tripwires in this file — `[gpu-idle-advisory]` (:204–209), `[gpu-idle-escalation]` (:3103–3108), `[gpu-width-advisory]` (:2325–2331), under-parallel warning (:2407), ETA tripwire (:4110) — carry the explicit "NEVER changes the status verdict" contract; matching it keeps the change non-architectural. The steelman for demote (the incident class IS a false done, so tell the truth in `status`) is answered by (b): the current tick's status already tells the current truth; the advisory carries the historical contradiction.
  *Source:* in-file precedents cited above; #545 corroboration block :3798–3833; the gpu-idle-escalation Telegram pattern :3135–3152.
  *Alternatives:* demote-to-running (rejected, above); a new `status="inconsistent"` value (rejected — status-enum change is architectural).
- **D2 — Line-identity anchored comparison (vs timestamp-prefix vs positional).**
  *What:* record the matched done line's truncated text; new = phase-bearing lines after its last tail occurrence (all, when scrolled out).
  *Why:* timestamps are not guaranteed by `PHASE_RE` (:340, docstring :256 — "anything matching the regex"); positions are unstable under the `tail -500` sliding window (:1372). Identity is stable and its duplicate-line failure mode fails toward quiet. Full analysis in §4.
  *Source:* `PHASE_RE` :340; probe `tail -500` :1372/:1141; `latest_phase` reversed-scan construction :2035–2044 (guarantees the done line is the LAST phase-bearing line at the done tick).
  *Alternatives:* timestamp comparison (rejected — silent inertness on un-timestamped lines); phase-line count (rejected — sliding window); hashing the whole tail (rejected — any non-phase churn would fire).
- **D3 — State-file schema: three flat string keys + bespoke run-scope clamp (vs joining `_TRIPWIRE_STATE_KEYS`).**
  *What:* `post_done_line` / `post_done_epoch` / `post_done_advisory_posted` in the existing per-issue dict (`_load_state`/`_save_state` :3313–3335); relaunch voiding via the direct `done_epoch < now − run_age_sec` clamp.
  *Why:* the guard's episode has its own natural epoch, so the direct clamp (the exact `last_phase_change_epoch` precedent, :4082–4087) is sufficient and keeps the guard independent of the #873 anchor lifecycle (whose malformed-anchor "clear everything" branch, :2913–2915, would couple our dedup to unrelated tripwire state). String values match the state-file convention (every value at :4126–4188 is a string).
  *Source:* `_save_state` payload :4123–4188; relaunch clamp :4082–4087; `_tripwire_run_scope` :2883–2921 (studied and deliberately not reused).
  *Alternatives:* `_TRIPWIRE_STATE_KEYS` membership (rejected, coupling); an events.jsonl-based anchor (rejected — heavier read per tick; the state file is the established cross-tick channel, `ssh_fail_count` precedent :3740).
- **D4 — Dedup grain: once per done-episode, retry-on-post-failure.**
  *What:* persisted `post_done_advisory_posted` flag; a failed `post_event` does not set it (next tick retries).
  *Source:* the identical contract in `_maybe_post_gpu_width_advisory` :2328–2331 and `_maybe_escalate_gpu_idle` :3106–3108; per-phase dedup sets :4139–4142.
  *Alternatives:* once-per-phase-name (wrong grain — one episode can span several new phase names); time-window re-alerts (over-engineering for v1).
- **D5 — Telegram push included (fail-soft).**
  *What:* one best-effort `_telegram_push` alongside the marker.
  *Why:* the incident class (false terminal, possibly premature pod termination and lost work) is at least as severe as the #664 spend-leak class that earned a push; `_telegram_push` (:3054–3081) is fail-soft by construction and never blocks the durable marker.
  *Source:* :3054–3081, :3148–3152.
  *Alternatives:* marker-only (weaker; the whole point is that the orchestrator already moved on — a human channel is the reliable receiver post-done).
