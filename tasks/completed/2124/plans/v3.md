## Requirement

Rule 26 (`.claude/rules/llm-judging.md:390-423`) is the judge pilot gate: before a
production judge dispatch of ≥ ~5,000 calls, pilot ~100–200 draws at the exact
production instrument and gate on (a) truncation ≈ 0 and (b) per-arm parse-fail
rate < ~2%. Three defects, two filed on the task body and one folded in from the
`epm:progress` scope candidate:

1. **Clause (b)'s threshold is unreachable at the pilot sizes the rule itself
   recommends.** The rule states no coupling between the per-arm draw count and
   the threshold it is compared against, so the gate is routinely configured with
   no power to resolve its own criterion.
2. **A k-way classification / labeling rubric reads as neither clearly in nor
   clearly out of the gate's scope**, because the exemption says "score-only
   rubrics" and the rest of rule 26 is written in graded-0-100 vocabulary. A
   10,666-context classification wave shipped unpiloted and failed at 100%.
3. **No per-ITEM completeness gate exists anywhere in the file.** Rules 9 / 24 /
   28 tally drops per DRAW; the DV is computed per ITEM, and the two are
   different quantities. A wave can pass every per-draw check while ~28% of its
   items carry zero valid draws.

## Evidence (all re-verified this session; the v3 figures re-verified again after review)

### D1 — the satisfiability arithmetic

`eval/judge_pilot.judge_pilot_gate` FAILs an arm on
`a.parse_fail_rate >= parse_fail_threshold` (`judge_pilot.py:235`, **`>=`, not
`>`**). At `n` effective draws in an arm the smallest observable nonzero
parse-fail rate is `1/n`. So a single parse failure passes only when
`1/n < threshold` — i.e. `n >= floor(1/threshold) + 1`, which at the default 2%
is **51 draws per arm, not 50**. The body's proposed wording (`n_draws >=
1/threshold`) is off by one and would still admit an unsatisfiable arm at n=50.

**Realized per-arm draws are DISCRETIZED, and the naive wave-level floor is
insufficient.** Budget is split by floor division —
`per_arm_items = max(1, target_total_draws // (len(arms) * max(1, n_draws)))`
(`judge_pilot.py:367`) — so realized per-arm draws are
`floor(T / (A·d)) · d`, not `T/A`. Consequences, both re-derived:

- `T >= required · A` is **NOT sufficient**. At `required=51`, `A=4`, `d=2`:
  `T=204` → `204 // 8 = 25` → **50 draws/arm → still unsatisfiable**. Same at
  `A=1, d=2` (`T=51` → 50). A plan or error message printing `T >= 51·A` as the
  remedy would print a value its own guard rejects.
- `T > A / threshold` (the continuous form) is likewise necessary but not
  sufficient: `A=2, d=10, T=101 > 100` → realized 50 draws/arm.
- The **exact sufficient form** is
  `T >= A · d · ceil(required / d)` — at `A=4, d=2, required=51` that is
  `T >= 208` → `208 // 8 = 26` → 52 draws/arm ✓.

**Realized draws are also capped by ARM SIZE, independently of budget.**
`_seeded_subsample` returns `list(items)` whenever `n_take >= len(items)`
(`judge_pilot.py:122-135`), so an arm holding 20 items at `d=2` yields 40 draws
no matter how large `T` is. A budget-only check passes it while the arm still
FAILs on its first parse failure. **This is exactly the #2091 instance class**
the task cites as motivation — its waived arm was limited by arm size, not by
budget split.

Shipped defaults are mutually unsatisfiable on their own:
`parse_fail_threshold=0.02` with `min_effective_draws_per_arm=10`
(`judge_pilot.py:284-286`) — `1/0.02 = 50 > 10`, so every per-arm count in
[10, 50] both clears the effective-draws floor and FAILs on its first parse
failure.

## Scope decisions (stated, not silent)

**IN.**
- (A) Rule 26 sizing clause — the strict-inequality floor, the **discretized**
  wave-level form, the arm-size cap, the unsatisfiable-defaults note, the
  reachability-≠-certification clause, the instrument-drift clause, and the
  `waive_parse_fail_arms` escape as the auditable alternative.
- (B) Rule 26 scope clause — every PARSED judge instrument (graded, k-way
  classification, binary categorical); narrow "score-only rubrics" to rule 23's
  bare-integer-no-rationale shape; distinguish from rule 27 without overstating.
- (C) New rule 29 — per-item `frac_items_complete` reporting + pre-registered
  floor (default 0.95, with its calibration basis) + drop-class triage before
  plotting, **plus its `## Enforcement` bullet**.
- (D) `judge_pilot.py` — config-time satisfiability refusal keyed on realized
  draws, with a named opt-out; a runtime WARN for post-hoc shrink; per-item
  completeness fields on `ArmPilotStats` + the report.
- (E) Tests + default bumps on in-repo library callers whose shipped defaults
  are unsatisfiable.

**OUT, with reasons.**
- **No exact-binomial gate.** A one-sided exact binomial test (FAIL only when the
  observed count is inconsistent with `p ≤ threshold`) is the statistically
  correct instrument for "is the true parse-fail rate under 2%", and it would
  dissolve both the off-by-one and the small-n unsatisfiability with no sizing
  rule at all (at n=16, 1 failure → P(X≥1 | p=.02) ≈ 0.28 → PASS; 2 failures →
  p ≈ 0.04 → FAIL). It is **not adopted here** because it changes verdicts on
  configurations that are already satisfiable (3/100 = 3% FAILs today, PASSes
  under the exact test at p ≈ 0.32) — a strictness change with its own evidence
  burden, and one that would violate this plan's own success criterion. Recorded
  as the named not-chosen alternative in the rule text; a follow-up task is the
  right home if it is wanted.
- **No `verify_plan.py` check.** The runtime guard covers every caller of the
  library function including inline rounds that never write a plan. It covers
  **none** of rule 29 (which binds analysis/plotting code) — that gap is closed
  by the (C) Enforcement bullet giving the Statistics & Measurement lens
  ownership, which is the surface every sibling rule in this file uses.
- **No change to the 2% threshold or the ~5,000-call floor.** The defect is the
  missing coupling, not the values.
- **No retro-fix of #1739's wave.** Already remediated (`--recover-from-raw`;
  `n_contexts_recovered=1811` in the audit).
- **No rewrite of rules 9 / 24 / 28.** Rule 29 cross-references them.
- **No change to the `>=` comparison.** Flipping to `>` rescues only the exact
  boundary (n = 1/threshold); n=16 stays unsatisfiable, and the flip changes
  verdicts at exactly-2%. Not a substitute for the sizing rule.

**Scope-inclusion argument for (C).** The `epm:progress` marker filed it onto
this task explicitly as a plan-time fold-in candidate; it is verified uncovered;
and it is the same defect CLASS as (A) — a gate that cannot fire on a real
degradation. The strongest cut case fails on evidence: rule 28 documents
item-level censoring only for the **api-refusal** class, while #1739's evil-DV
holes were rubric-`REFUSAL`s (rule-9 content class) that rule 28's accounting
structurally cannot see.

**Scope-inclusion argument for (D).** Rule 26 names `judge_pilot_gate` as its
mechanical implementation. Amending the rule while that function's shipped
defaults violate it leaves the next caller taking the defaults and inheriting the
defect.

## Method

### (A) `.claude/rules/llm-judging.md` rule 26 — sizing clause

Insert after clause (b)'s exemption sentence, as a new indented paragraph inside
rule 26:

> **Size the pilot so the threshold is REACHABLE — the ~100–200 habit is not a
> sizing rule (#2124).** Clause (b) compares a per-arm RATE against a threshold,
> so a per-arm draw count that cannot RESOLVE that threshold makes the gate
> uninformative in BOTH directions: at `n` effective draws the smallest
> observable nonzero parse-fail rate is `1/n`, so an arm with `n <= 1/threshold`
> FAILs on its first parse failure (a granularity artifact, not a defect signal)
> while a clean PASS carries no evidence that the true rate is under threshold.
> Satisfiability is STRICT — the gate FAILs on `rate >= threshold`, so a single
> failure survives only when `1/n < threshold`, i.e. the per-arm floor is
> `required = max(min_effective_draws_per_arm, floor(1/threshold) + 1)` — **51**
> draws per arm at the default 2%, not 50. The shipped default pair is itself
> unsatisfiable (`parse_fail_threshold=0.02` against
> `min_effective_draws_per_arm=10`: 1/0.02 = 50 > 10).
>
> Realized per-arm draws are DISCRETIZED and ARM-SIZE-CAPPED, so neither
> `target_total_draws >= required · n_arms` nor `> n_arms / threshold` is
> sufficient. `eval.judge_pilot.judge_pilot_gate` splits its budget by floor
> division (`per_arm_items = target_total_draws // (n_arms · n_draws)`) and then
> caps each arm at its own item count, so realized draws are
> `min(per_arm_items, len(arm_items)) · n_draws`. The exact budget form is
> **`target_total_draws >= n_arms · n_draws · ceil(required / n_draws)`** (at 4
> arms, `n_draws=2`, 2%: **208**, not 204 — 204 realizes 50 draws/arm and still
> fails), and an arm holding fewer than `ceil(required / n_draws)` ITEMS cannot
> be fixed by any budget at all. Size from the arm count AND the arm sizes.
>
> Reachability is not certification: at exactly the floor (51 draws, 0 failures)
> the 95% upper bound on the true rate is still ~5.7% (rule of three), and a
> healthy arm at a true 1% rate FAILs ~9% of the time at n=51 (it needs ≥2
> failures). The floor buys gate COHERENCE, not evidence that the rate is under
> 2%; 2–3× the floor is what reduces granularity noise. (The statistically
> correct instrument for "is the true rate under 2%" is a one-sided exact
> binomial test rather than a point-rate comparison; it is deliberately NOT the
> gate today because it would change verdicts on configurations that already
> pass — #2124 § Scope decisions.)
>
> The config-time guard sizes the PLANNED draws; realized `n_answered` can still
> shrink below `required` through rule-24 transport losses and rule-28
> api-refusals (which run 30%+ in exactly the harm-class waves this gate serves),
> re-creating the granularity artifact after the guard has passed. The gate WARNs
> when that happens — treat it as an under-powered pilot, not a clean read.
>
> A pilot PASS certifies only the instrument it ran: rubric text, judge model,
> `n_draws`, and `max_tokens`. Any change to those invalidates it — re-pilot.
> (`scripts/issue2203_runtime.py` is the in-repo precedent: it fingerprints
> `rubric_sha + n_draws + max_tokens` and honors a prior PASS only on match.)
>
> When a satisfiable pilot is genuinely unaffordable for one arm, the escape is
> the AUDITABLE one — never a quietly loosened threshold: name the arm in the
> wave's `waive_parse_fail_arms` constant with a recorded reason (the
> `PILOT_WAIVE_PARSE_FAIL_ARMS` pattern, `scripts/issue2091_judge.py`; #2091
> waived a 1/16 = 6.25% wildchat arm this way). The waiver is PARSE-FAIL only —
> truncation and the effective-draws floor stay unwaivable. Mechanically enforced
> since #2124 in `eval.judge_pilot.judge_pilot_gate` ONLY: it REFUSES an
> unsatisfiable configuration at config time, before any API spend, unless the
> caller passes `allow_subresolution_pilot=True`, which downgrades the refusal to
> a recorded report warning. Per-issue re-implementations of the gate do not
> inherit the guard — check yours.
