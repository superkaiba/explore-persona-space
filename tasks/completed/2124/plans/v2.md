## Requirement

Rule 26 (`.claude/rules/llm-judging.md:390-423`) is the judge pilot gate: before a
production judge dispatch of ≥ ~5,000 calls, pilot ~100–200 draws at the exact
production instrument and gate on (a) truncation ≈ 0 and (b) per-arm parse-fail
rate < ~2%. Three defects, two filed on the task body and one folded in from the
`epm:progress` scope candidate:

1. **Clause (b)'s threshold is unreachable at the pilot sizes the rule itself
   recommends.** The rule states no coupling between the per-arm draw count and
   the threshold it is compared against, so the gate is routinely configured with
   no power to resolve its own criterion.
2. **A k-way classification / labeling rubric reads as neither clearly in nor
   clearly out of the gate's scope**, because the exemption says "score-only
   rubrics" and the rest of rule 26 is written in graded-0-100 vocabulary. A
   10,666-context classification wave shipped unpiloted and failed at 100%.
3. **No per-ITEM completeness gate exists anywhere in the file.** Rules 9 / 24 /
   28 tally drops per DRAW; the DV is computed per ITEM, and the two are
   different quantities. A wave can pass every per-draw check while ~28% of its
   items carry zero valid draws.

## Evidence (all re-verified this session, not carried from the filing)

### D1 — the satisfiability arithmetic (sharper than the body's `1/threshold`)

`eval/judge_pilot.judge_pilot_gate` FAILs an arm on
`a.parse_fail_rate >= parse_fail_threshold` (`judge_pilot.py:235`, **`>=`, not
`>`**). At `n` effective draws in an arm the smallest observable nonzero
parse-fail rate is `1/n`. So a single parse failure passes only when
`1/n < threshold` — i.e. `n >= floor(1/threshold) + 1`, which at the default 2%
is **51 draws per arm, not 50**. The body's proposed wording (`n_draws >=
1/threshold`) is off by one and would still admit an unsatisfiable arm at exactly
n=50.

Budget is split evenly across arms:
`per_arm_items = max(1, target_total_draws // (len(arms) * max(1, n_draws)))`
(`judge_pilot.py:367`), so per-arm draws ≈ `target_total_draws / n_arms` and the
wave-level floor is `target_total_draws > n_arms / parse_fail_threshold` — at 2%,
**> 50 × n_arms**. Rule 26's own "~100–200 draws" figure is therefore satisfiable
only at **≤ 3 arms**.

Shipped defaults are mutually unsatisfiable on their own:
`parse_fail_threshold=0.02` with `min_effective_draws_per_arm=10`
(`judge_pilot.py` signature) — `1/0.02 = 50 > 10`, so every per-arm count in
[10, 50] both clears the effective-draws floor and FAILs on its first parse
failure. Grep confirms **no in-repo caller overrides either knob**; all 8 call
sites take both defaults and set only `target_total_draws` / `n_draws`.

#2091's waived arm (1/16 = 6.25% ≥ 2%, `PILOT_WAIVE_PARSE_FAIL_ARMS`,
`scripts/issue2091_judge.py:142-157`, commit `d839842fb4`) is one instance of
this general defect, not an edge case.

### D2 — the unpiloted classification wave (#1739)

`eval_results/issue_1739/dv_dataset/evil/labeling.json`: `n_contexts=10666`,
`n_contexts_with_dv=8855`, one classification call per context — **far above rule
26's ~5,000-call floor**, so the gate applied and was skipped. Per
`scripts/issue1739_tactic_classify.py:11-17`, the v1 rubric asked for a plain
`Label: <class>` line while the dispatch layer's `parse_judge_json` accepts JSON
only: **100% of rows failed to parse, the wave landed `n_labeled=0`**, and
recovery required `--recover-from-raw` re-parsing of the banked responses. A
~200-draw pilot would have shown a 100% parse-fail rate for ~2% of the spend.

This is a violated rule *plus* a wording gap — not the rule-scope extension the
body flagged as the alternative reading.

### D3 — per-item completeness (the `epm:progress` scope candidate, re-measured)

The marker records "#1739's evil judge draws were 28.3% rubric-instructed
REFUSALs (frac_items_complete=0.70)". Both figures are real but the LABEL is
wrong, so the rule text must not copy the marker. Recomputed from
`eval_results/issue_1739/result1_spread/spread_stats_refusal_zero.json`
→ `recode_audit.per_source.own_rungs` (the evil DV slice, `n_contexts=10666`,
matching D2's wave):

| quantity | value |
|---|---|
| draws | 159,990 |
| refusal draws | 46,525 → **29.1% per-DRAW** |
| rollouts (items) | 53,330 |
| rollouts with ZERO valid draws | 15,073 → **28.3% per-ITEM** |
| ⇒ `frac_items_complete` | **0.717** |
| rollouts MIXED (some valid, some refused) | **865** |

So 28.3% is the ITEM-hole rate, not the draw rate, and `frac_items_complete`
≈ 0.717 (the marker's "0.70").

**The 865 is the load-bearing number.** At `n_draws=3`, a 29.1% draw-drop rate is
consistent with per-item completeness anywhere in [0.71, 1.00] — uniform spread
would leave every item with ≥1 valid draw. Only 865 items were mixed against
15,073 all-refusal, i.e. the drops were almost entirely item-concentrated and
completeness landed at the **pessimistic end of that range**. The contrast arm in
the same file makes the point from the other side: `wildchat_rung` ran 546/30,000
= 1.8% refusal draws and 178/10,000 = 1.8% item holes — at low rates the two
coincide, so the per-draw proxy looks safe exactly where it does not matter.

Independent corroboration already in the rule file: rule 28 (`llm-judging.md:206+`,
#2151) records the evil-OOD wave at 15,091/44,310 = 34.1% refusal draws and
4,982/14,770 = 33.7% of items with ZERO valid draws, with the censoring
**outcome-correlated** (rescued items scored 1.4× higher overall, 2.3× on mhj,
3.7× on pair). A DV read off the survivors is biased downward on exactly its
highest-scoring rows.

Coverage grep: **no** `frac_items_complete` / `completeness` / `satisfiab` /
`1/threshold` clause exists anywhere in `llm-judging.md`. The only in-repo
`frac_items_complete` is a one-off in
`scripts/issue1739_judge_reliability.py:211` — the naming precedent, not a
library affordance. `ArmPilotStats` (`judge_pilot.py:71-99`) carries eleven
per-DRAW counters and **zero** per-item fields.

## Method

### (A) `.claude/rules/llm-judging.md` rule 26 — sizing clause

Insert after clause (b)'s exemption sentence, as a new indented paragraph inside
rule 26:

> **Size the pilot so the threshold is REACHABLE — the floor is
> `n_arms / parse_fail_threshold`, not the ~100–200 habit (#2124).** Clause (b)
> compares a per-arm RATE against a threshold, so a per-arm draw count that
> cannot RESOLVE that threshold makes the gate uninformative in BOTH directions:
> at `n` effective draws the smallest observable nonzero parse-fail rate is
> `1/n`, so an arm with `n <= 1/threshold` FAILs on its first parse failure (a
> granularity artifact, not a defect signal) while a clean PASS carries no
> evidence that the true rate is under threshold. Satisfiability is STRICT —
> `judge_pilot_gate` FAILs on `rate >= threshold`, so a single failure survives
> only when `1/n < threshold`, i.e. `n >= floor(1/threshold) + 1` (**51** draws
> per arm at the default 2%, not 50). The gate splits its budget evenly
> (`per_arm_items = target_total_draws // (n_arms * n_draws)`), so the wave-level
> floor is `target_total_draws > n_arms / parse_fail_threshold` — **> 50 ×
> n_arms** at the default — and this rule's own "~100–200" figure is satisfiable
> only at ≤ 3 arms. Size from the ARM COUNT. The shipped default pair is itself
> unsatisfiable (`parse_fail_threshold=0.02` against
> `min_effective_draws_per_arm=10`: 1/0.02 = 50 > 10), so the effective per-arm
> floor is `max(min_effective_draws_per_arm, floor(1/threshold) + 1)`.
>
> When a satisfiable pilot is genuinely unaffordable for one arm, the escape is
> the AUDITABLE one — never a quietly loosened threshold: name the arm in the
> wave's `waive_parse_fail_arms` constant with a recorded reason (the
> `PILOT_WAIVE_PARSE_FAIL_ARMS` pattern, `scripts/issue2091_judge.py`; #2091
> waived a 1/16 = 6.25% wildchat arm this way). The waiver is PARSE-FAIL only —
> truncation and the effective-draws floor stay unwaivable. Mechanically enforced
> since #2124: `judge_pilot_gate` REFUSES an unsatisfiable configuration at
> config time, before any API spend, unless the caller passes the explicit
> `allow_subresolution_pilot=True` opt-out, which downgrades the refusal to a
> recorded report warning.

> 29. **Report per-ITEM completeness (`frac_items_complete`) per behavior / arm

>     read (#2124).** Rules 9 / 24 / 28 tally drops per DRAW. The DV is computed
>     per ITEM, so the quantity that describes the DV's real denominator is

>     or reporting the DV. Never silently narrow the denominator.
>

>     per item, a draw-drop rate `p` is consistent with item completeness
>     anywhere from `1 - p` (fully item-concentrated) to `1.0` (uniformly
>     spread), and the drop classes concentrate. #1739's evil DV slice
>     (`eval_results/issue_1739/result1_spread/spread_stats_refusal_zero.json`,

>     exactly where the answer does not matter. That hole surfaced only under

>     the rescued items scored 1.4× higher than never-censored items overall
>     (2.3× on mhj, 3.7× on pair). A rule-26 pilot-gate PASS is NOT a substitute
>     — the gate is per-draw, and rule 28's class is explicitly outside its
>     protection.

>     Mechanics (#2124): `judge_pilot_gate`'s per-arm report carries
>     `frac_items_complete` + `n_items_zero_valid` alongside the draw tallies;
>     `scripts/issue1739_judge_reliability.py` is the naming precedent.

### (D) `src/explore_persona_space/eval/judge_pilot.py`

**D-1 — config-time satisfiability refusal.** In `judge_pilot_gate`, after the
existing `arms` validation and after `per_arm_items` is computed (so the check
sees the REAL planned per-arm draw count, not the nominal budget), before any
`judge_graded` call:

- compute `planned_per_arm_draws = per_arm_items * n_draws` and
  `min_resolvable = floor(1 / parse_fail_threshold) + 1`;
- the required per-arm floor is
  `required = max(min_effective_draws_per_arm, min_resolvable)`;
- if `planned_per_arm_draws < required`: `raise ValueError` naming
  `planned_per_arm_draws`, `required`, both source knobs, and the exact remedy
  (`target_total_draws >= required * n_arms`), unless the new keyword-only
  `allow_subresolution_pilot: bool = False` is set, in which case record a
  warning on the report instead and continue.
- Guard `parse_fail_threshold <= 0` (raise; `min_resolvable` undefined) and
  `>= 1` (no finite floor — every rate resolves).

The raise is fail-fast per the project rule: it fires before any API spend and
prints the one-flag remedy. `allow_subresolution_pilot` mirrors the existing
`waive_parse_fail_arms` auditable-escape pattern in the same function.

**D-2 — per-item completeness fields.** Add `n_items_zero_valid: int` and
`frac_items_complete: float` to `ArmPilotStats`, derived from the arm's
`JudgeResult` per-item data, and surface both in the emitted report. Extend the
dataclass docstring: these two are the only per-ITEM fields; every `n_*` counter
remains per-DRAW.

If `JudgeResult` already exposes per-item valid-draw counts, also add a
`frac_items_complete` property there so rule 29 is mechanically supported for
PRODUCTION waves, not just pilots. If it does not, keep the addition at the pilot
layer and say so in rule 29's Mechanics line — do not invent a new per-item
accumulator in `graded_judge.py` under this task.

**D-3 — no gate condition keys on completeness.** Rule 29's floor is a reporting
+ triage duty on the analysis, not a rule-26 PASS/FAIL clause. Report the fields;
do not FAIL the pilot on them. Mirror rule 28's report-only precedent
(`n_api_refusal`) and say so in the docstring.

### (E) Tests + caller defaults

**E-1 — `tests/test_judge_pilot_satisfiability.py` (new).** No network; construct
`arms` and monkeypatch/stub `judge_graded` so no API call is issued.
- unsatisfiable config raises `ValueError` with the remedy string;
- the boundary is strict: `planned_per_arm_draws == 1/threshold` (50 @ 2%)
  RAISES, `== 51` passes;
- `allow_subresolution_pilot=True` converts the raise into a report warning;
- `min_effective_draws_per_arm > min_resolvable` dominates (the `max`);
- `parse_fail_threshold <= 0` raises;
- `frac_items_complete` / `n_items_zero_valid` are computed correctly, including
  the all-dropped arm (0.0) and the all-valid arm (1.0).

**E-2 — caller default bumps.** For each of the 8 in-repo `judge_pilot_gate` call

satisfiability at 2%. Where the default is unsatisfiable, raise that script's
default `target_total_draws` to `>= 51 * n_arms` (a one-line default change;
strictly enlarges a ~200-call pilot, no behavioral risk). Where `n_arms` is only
knowable at runtime, leave the default and note it in the round summary — the new
guard will fail it loudly with the remedy at dispatch, before spend.

**E-3 — Step 9c registration.** Register the new test in the Step 9c selector
map if the touched-scope mapping requires it (both selector files, per the
