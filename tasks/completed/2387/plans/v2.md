    - Before: `        push_out=$("$TELEGRAM_PUSH" "$msg" 2>&1)`
    - After: `        push_out=$(timeout --kill-after=5s "${PUSH_TIMEOUT}s" "$TELEGRAM_PUSH" "$msg" 2>&1)`

**Composition correctness per shape.** (a) `if timeout ... cmd; then`: the `if` tests `timeout`'s exit status; 124 takes the else arm exactly as any failed push does today. (b) `timeout ... cmd || echo`: 124 fires the `||` arm; `fatal()` then reaches its unconditional `exit 1`. (c) `[ -x "$PUSH" ] && timeout ... "$PUSH" ...`: the guard is untouched (the `-x` test still runs on the raw path, not on `timeout`), the compound's status is discarded as today (next statement follows; no `set -e`; both watch scripts end with an explicit `exit 0`, so a push status can never become the script exit code). (d) `push_out=$(timeout ... cmd 2>&1)`: `push_rc=$?` on the next line captures `timeout`'s status; the substitution's `2>&1` now also captures any `timeout` diagnostic, which flows to the existing `log_line "$push_out"`, a strict improvement.

**Embedded-shell exit-path trace (failure arms).** Site 1: 124 → `|| echo` (stderr note) → `exit 1` (unchanged fatal contract). Sites 2-5: 124 → `else` → "FAILED (no sentinel written; will retry next run)" echo → wrapper continues → exits 0. Sites 6-9: 124 → compound status discarded → next statement (crontab self-removal or ESCALATED log line) runs → `exit 0`. Site 10: 124 → `push_rc` non-zero → "FAILED (no sentinel...)" log → `alert_failure` returns → wrapper exits 0. No arm contains a bare `false` or an early-exit that a sibling block depends on; no exit path changes.

### 4.3 Exit-code collision analysis (the highest-risk correctness question)

`timeout` returns 124 on deadline, 125 on its own failure (e.g. a malformed duration), 126/127 for unexecutable/missing command, 137 after `--kill-after` SIGKILL. Checked every wrapper for push-rc value semantics:

- `cron_lesson_consolidate.sh`: the rc=3 arm (`if [ "${rc:-0}" -eq 3 ]`, line 118) keys on `rc=$?` at line 98, the CONSOLIDATOR's exit code, assigned before any push runs. The push's status is consumed only by the `if` at 140 and the `||` at 67, both binary. No collision.
- `cron_step9c_ledger_refresh.sh`: the `[ "${rc:-0}" -ne 0 ]` arm keys on the REFRESH step's rc; push status consumed only by the `if` at 115. No collision.
- `cron_daily_healthcheck.sh`: both sites are plain `if`-conditions; no rc variable stores the push status. No collision.
- `cron_codex_auto_upgrade.sh`: `push_rc` is tested only with `-eq 0` (line ~86). The `alert_failure "$rc"` argument is the UPGRADE step's rc, not the push's. No collision.
- Watch scripts: push status discarded entirely. No collision.

Conclusion: no site anywhere branches on a specific non-zero push exit code, so every `timeout` code (124/125/126/127/137) reads as the generic "push failed" today's arms already handle. The `[ -x ]` guards make 126/127 unreachable in practice.

## 11. Decision Rationale

- **Bound = 30 s default.** What: `PUSH_TIMEOUT="${EPS_PUSH_TIMEOUT_SECS:-30}"`. Why: matches the bound every in-repo Python caller of the same helper already uses, so shell and Python callers degrade identically. Source: `scripts/poll_pipeline.py:4909`, `scripts/vm_disk_guard.py:2598`, `scripts/gcp_audit.py:110`, `scripts/sync_repo_root.py:1447` (all `timeout=30`, Read 2026-08-28). Alternatives: per-wrapper cadence-scaled bounds (rejected: no wrapper runs more often than every 10 minutes, so 30 s is comfortably inside every cadence and uniformity beats tuning); 10 s (rejected: diverges from the Python precedent for no benefit).
- **`--kill-after=5s` form.** What: SIGTERM at the bound, SIGKILL 5 s later. Why: house style already uses the `--kill-after` form for the one pre-existing `timeout` in these wrappers, and the KILL backstop covers a SIGTERM-ignoring state at trivial cost. Source: `scripts/cron_daily_healthcheck.sh:172` (`timeout --kill-after=300s 14400s`, Read 2026-08-28). Alternatives: bare `timeout 30s` (rejected: no backstop); scaling kill-after with the env knob (rejected: fixed 5 s keeps the test path fast and the grace window is about signal delivery, not payload size).
- **Env-overridable bound (`EPS_PUSH_TIMEOUT_SECS`).** What: one env knob, default 30. Why: the sleeping-stub tests need a ~2 s bound to stay fast, and env-tunable knobs are these wrappers' established test seam (`EPS_TELEGRAM_PUSH_SCRIPT`, `EPS_STEP9C_REFRESH_BIN`, `EPS_WATCH_STALL_MIN`). Name collision checked: `grep -rn 'PUSH_TIMEOUT' scripts/ src/ tests/` is empty. Source: harness pattern in `tests/test_cron_step9c_ledger_refresh.py:90-98` (env-injection precedent). Alternatives: fixed 30 s + a 35 s sleeping test (rejected: adds ~35 s to every suite run); test-only sed of the wrapper (rejected: the codex suite does this for lines with no env seam, but a seam is cheaper and reusable).
- **Per-site inline wrapping, not a shared sourced helper.** What: 10 one-line prefixes instead of a `push_bounded()` sourced snippet. Why: the six wrappers are deliberately independent single-file cron entries (three run from the live crontab, one is disabled, two are self-retiring templates); adding a sourced dependency creates a new failure mode (missing/renamed snippet breaks all six at 05:31) and a new coupling every future watch-script fork must carry, against a duplication cost of one short prefix. The scanner test (T-D) is the anti-drift control that a helper would otherwise provide. Source: the wrappers' existing convention; each already inlines its own `log_line`/`fatal` rather than sourcing shared shell. Alternatives: per-wrapper `push_bounded()` function (rejected: 6 function definitions to keep in sync is the same drift surface as 10 prefixes, minus the scanner's greppability).
- **Fix at call sites, not in `telegram_push.sh`.** Source: task body's own direction ("must not be this task's only fix" for the helper; the helper lives in ~/my-goat, outside this repo). A my-goat `--max-time` proposal is a separate follow-up, out of scope here.
- **Tool-behavior claims, source-tagged:** GNU `timeout` default (non-`--foreground`) runs the command in its own process group and signals the group. Source: coreutils 8.32 `timeout` documented behavior; corroborated in-repo by the healthcheck's existing use to bound a whole detached `claude -p` process tree (`cron_daily_healthcheck.sh:168-176` comment: "timeout bounds a wedged run"), and mechanically re-verified by T-A/T-B/T-C, whose sleeping BASH stub (bash parent + `sleep` child) only dies within bound if the group is signaled. Selector literal-path `.sh` eligibility: `scripts/select_step9c_tests.py:96` and `:1899` (grep, 2026-08-28). Selector manifest pairing: manifest header lines 1-5 (Read, 2026-08-28).
