# Plan — #1595 workflow-fix: stopped RunPod volume is NOT durable; persist resume state before multi-hour parks

## 0.0 TL;DR (plain English)

- **What I'll do:** Fix the workflow docs that call a stopped pod's disk "preserved" as if it were safe storage. I'll add a short rule saying: before pausing a pod for more than about an hour, upload the run's progress files (done-JSONs, resume sentinels, partial results) to HuggingFace, and read those copies back on resume.
- **What I expect:** The next multi-hour pause survives the provider deleting the stopped pod out from under us (which is what happened to #1112 — the pod vanished ~22h into a park and the whole run had to be redone).
- **What would change my mind:** If RunPod guaranteed stopped-pod volumes never get reclaimed, the rule would be over-cautious — but the uploads are kilobyte-scale text files, so the insurance costs almost nothing either way.

```markdown
pause, a Step 8-bis gate/crash halt, awaiting follow-ups), upload the run's
RESUME STATE to the HF data repo (`issueN_<slug>/resume_state/`, or the
bucket the pipeline already writes) — done-JSONs, phase/resume sentinels,
partial eval JSONs, progress manifests: anything a resumed run would read
from the volume to know where to restart. This extends the upload-policy

text/JSON — the unconditional non-LFS path. On resume, prefer the off-pod
copies over the volume's. Treat a stopped volume as a convenience cache
(HF hub cache, venv), never as the only copy of anything. The `keep-running`
tag shields only against PROJECT janitors, not provider-side reclaim.
```
