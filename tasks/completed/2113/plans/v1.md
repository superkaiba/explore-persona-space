## 1. Requirement + acceptance criteria

**Requirement.** `scripts/cron_daily_healthcheck.sh` (06:00 PT cron) currently ALERTS with the
exact backfill command when yesterday's `/daily` file is missing / stale / a husk, but never runs
it (verified: `claude -p` appears only inside alert MESSAGE strings, lines 88/90). Recovery
depends on a human copy-pasting the command; when nobody does, the day's problem sweep is
permanently skipped and the `sent-<date>.flag` sentinel suppresses any re-alert (live incident:
2026-08-04 stayed unmined ~24h after the 529-killed nightly). The fix: on a `missing` or `husk`
detection the healthcheck ADDITIONALLY launches the backfill it already names — detached,
single-flight, one auto-attempt per date — keeping the alert, and a FAILED auto-backfill
re-alerts the next day instead of going silent.

**Acceptance criteria:**

1. On a `missing` or `husk` detection with no prior attempt for that date, the healthcheck
   launches `claude -p "/daily <date>"` detached (setsid + nohup + own log), writes a per-date
   attempt sentinel, and the alert message reads "auto-backfill launched (attempt 1); log: <path>"
   instead of "run this command".
2. Exactly ONE auto-attempt per date, ever (attempt sentinel; a same-day healthcheck re-run
   never relaunches).
3. Single-flight: a `flock`-wrapped launch — never two auto-backfill `/daily` processes at once.
4. `stale` detections stay alert-only with the manual command (a stale file may be enriched;
   auto-backfilling it is ambiguous — see §4 D3).
5. Failure policy: a later healthcheck run that finds a date with an attempt sentinel whose file
   is STILL missing/husk pushes a one-time "auto-backfill FAILED — manual backfill needed:
   <command>" alert (its own per-date failure sentinel; never relaunches). The `sent-<date>.flag`
   alert sentinel does NOT suppress this distinct alert.
6. Kill switch: `EPS_HEALTHCHECK_AUTO_BACKFILL=0` restores exact current alert-only behavior.
7. All existing 9 tests updated where messages/defaults changed + new tests for criteria 1-6
   pass; the test harness NEVER invokes the real `claude` binary (fake-bin env override).
8. The mygoat-side retrospective-log pointer in the alert stays (body's open question: keep it —
   it costs nothing and preserves debuggability).

## 3. File paths + concrete changes

### `scripts/cron_daily_healthcheck.sh` (modify, ~+55 lines)

New env-overridable config (test seams, defaults in parens):

- `EPS_HEALTHCHECK_AUTO_BACKFILL` (`1`) — kill switch; `0` = alert-only (current behavior).
- `EPS_HEALTHCHECK_CLAUDE_BIN` (`$HOME/.local/bin/claude`) — the binary to launch; tests point
  this at a fake recording script (same pattern as `EPS_TELEGRAM_PUSH_SCRIPT`).
- `EPS_HEALTHCHECK_BACKFILL_LOOKBACK_DAYS` (`3`) — failure-verification window (§4 D2).

New paths (all under `$SENTINEL_DIR`, i.e. `logs/daily_healthcheck/`):

- `backfill-attempt-<date>.flag` — per-date one-auto-attempt sentinel.
- `backfill-failed-sent-<date>.flag` — per-date one-failure-alert sentinel.
- `backfill-<date>.log` — the detached backfill's own log.
- `backfill.lock` — the flock file (shared across dates; single-flight for the launch).

Launch block (inside the existing `NEEDS_ALERT=1` branch, before message composition; fires only
for `ALERT_CLASS` ∈ {`missing`, `husk`} with `AUTO_BACKFILL=1`):

```bash
LAUNCHED=0
if [ "$AUTO_BACKFILL" = 1 ] && { [ "$ALERT_CLASS" = "missing" ] || [ "$ALERT_CLASS" = "husk" ]; }; then
    ATTEMPT="$SENTINEL_DIR/backfill-attempt-$YESTERDAY.flag"
    BF_LOG="$SENTINEL_DIR/backfill-$YESTERDAY.log"
    if [ -f "$ATTEMPT" ]; then
        echo "daily_healthcheck: auto-backfill already attempted for $YESTERDAY ($ATTEMPT) — not relaunching"
    elif [ ! -x "$CLAUDE_BIN" ]; then
        echo "daily_healthcheck: claude bin not executable at $CLAUDE_BIN — cannot auto-backfill"
    else
        # Detached + single-flight: setsid survives this cron's exit; flock -n
        # guarantees at most one auto-backfill process fleet-wide (a held lock
        # exits 1 into BF_LOG, caught next day by the failure sweep); timeout
        # bounds a wedged run (4h > the 3h bg-wait ceiling).
        BF_PID=$(bash -c "cd '$PROJECT_DIR' && setsid nohup flock -n '$SENTINEL_DIR/backfill.lock' \
            timeout --kill-after=300s 14400s \
            env CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=10800000 \
            '$CLAUDE_BIN' -p '/daily $YESTERDAY' < /dev/null >> '$BF_LOG' 2>&1 & echo \$!")
        touch "$ATTEMPT"
        LAUNCHED=1
        echo "daily_healthcheck: auto-backfill launched for $YESTERDAY (pid=$BF_PID, log=$BF_LOG)"
    fi
fi
```

Message composition: when `LAUNCHED=1`, the class message ends with
`— auto-backfill launched (attempt 1); log: <BF_LOG>` (retrospective-log pointer kept); when the
launch was skipped/disabled/failed-to-start, the message keeps the CURRENT manual-command form
verbatim. `stale` always keeps the current form.

Failure-verification sweep (new block, runs BEFORE the yesterday check so its pushes are
independent of `NEEDS_ALERT`; loops `i` in `1..LOOKBACK` over `date -d "$YESTERDAY - $i days"`):
for each date `D` with `backfill-attempt-D.flag` present, file at `D` still missing-or-husk
(same awk predicate, factored into a helper function `is_missing_or_husk()` used by both sites),
and no `backfill-failed-sent-D.flag`: push
`ALERT: auto-backfill for D FAILED (day still unmined) — check <backfill log> | manual backfill: <current command text>`
and touch the failure sentinel. Never relaunches (acceptance criterion 5). Uses the same
`$TELEGRAM_PUSH` executable + sentinel-on-success pattern as the existing alert.

Header comment updated to describe the new behavior + env knobs.

## 4. Design decisions (failure policy — delegated to the planner by the body)

- **D1 — one auto-attempt per date, verification next day.** The healthcheck's single-date
  lookback means date `D` is natively checked only at `D+1` 06:00. Rather than widening the
  primary detection, a small failure-verification sweep (default 3 days) re-checks ONLY dates
  that carry an attempt sentinel and re-alerts once if still unmined. This satisfies the body's
  "sentinel must not suppress a second attempt + re-alert" intent in its safe form: the
  RE-ALERT is guaranteed (distinct sentinel), and the second ATTEMPT is deliberately manual —
  an auto-backfill that failed once has an unknown cause (quota, 529 storm, skill bug);
  auto-looping it burns tokens against the same wall (the body itself says "a failed
  auto-backfill re-alerts rather than looping").
- **D2 — lookback 3 days.** Covers a weekend of failures; bounded so the 06:00 run stays O(1).
- **D3 — `stale` excluded from auto-launch.** A stale file can be fully enriched (mtime drift);
  backfilling an enriched day is at best a no-op token burn, at worst a double-mine. Missing +
  husk are the two unambiguous never-mined classes (and both observed live).
- **D4 — attempt sentinel written even if the detached flock loses the race.** The failure
  sweep catches a lock-blocked attempt next day; keeping the parent-side logic sentinel-simple
  avoids racy detached-state readback in a cron script.
- **D5 — retrospective-log pointer stays** in all messages (body's open question, resolved:
  keep — zero cost, aids debugging).
