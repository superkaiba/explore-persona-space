## 4. Design (method delta + concrete diffs)

**Decision 1 — restore target is always `awaiting_promotion`, not a recorded pre-round status.** The loop's ONLY designed exit is `awaiting_promotion` regardless of entry point — even a previously-`completed` task that loops re-parks there (step 3 bullet, line 7718-7720), and a round only ever dispatches once the parent has a landed clean-result, so `awaiting_promotion` is the correct resting state in every case. A recorded pre-round status would add bookkeeping (nowhere durable to record it) and diverge from the loop's own completion path for zero benefit. Matches the diff sketch and the Goal.

**Decision 2 — the defer posts the step-4 completion marker with `outcome: deferred — <one-line reason>`, AFTER the re-park.** Closure is outcome-agnostic (`unrun_followup_labels`), so this closes the label and the Step 0 dispatcher / tick re-drive never relaunches a deferred (possibly wedged) round. Ordering teardown → re-park → marker preserves the watcher's step-3→step-4 inference ("run marker newer than scope ⇒ re-park already happened"). A deliberate later resume posts a FRESH scope under a NEW label (a re-post of the closed label stays closed forever by construction) — #825's own 04:22Z ridge-only resume shows the resume-with-modified-spec path is the realistic one anyway. A deferred proposer-band round still counts toward its step-5 cap (only `retroactive-close` is excluded): the round consumed dispatch/compute, and a free retry slot would invite defer-retry churn. No cap prose changes.
