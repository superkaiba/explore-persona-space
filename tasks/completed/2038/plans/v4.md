## 1. Goal & acceptance criteria

Goal (verbatim from body): "A RunPod fallback launch that fails or is
superseded never leaves its pod billing."

Proposed change (body): on a failed or superseded RunPod fallback launch,
terminate the just-provisioned pod in the SAME failure path instead of
leaving it for a later sweep/audit.

## 3. Design

**Policy reconciliation (standing pod directive).** "Nothing gets shut down
on its own" carve-out (b): the agent actively driving a job on a pod it
provisioned may terminate THAT pod once uploads are verified. Component 1
terminates a pod THIS launch call just provisioned, on which NOTHING ever
ran (the workload-execution leg's failures raise `RunPodWorkloadStartError`
and are excluded, as is any raise AFTER a successful exec leg) — uploads are
vacuously verified. Component 2's terminate arm is gated to prior handles
carrying `workload_start_error` (the #954 workload-start-FAILED partial
handles — nothing ran, no artifacts exist), initiated by the superseding
launcher in the owning lane, not a background sweep; a provision-only
SUCCESS handle (`workload_executed` false with NO `workload_start_error` —
the experimenter-driven shape whose run the sidecar does not own) is never
auto-terminated (skip + WARN). A prior handle whose workload DID execute is
never auto-terminated either: it gets a reversible `stop` (GPU billing
halted, volume preserved — exactly the manual action the #1739 session
took) plus a loud WARN handing disposition to the owner. Precedents for same-lane automatic teardown: Step 8
verify-then-terminate, the #1997 watcher STOP arm, the Part C wedge failover
terminate.

**Component 1 — same-path terminate on post-provision launch failure +
pod-id round-trip (`backends/runpod.py`).**

- **Pod-id round-trip (critic r1 Must-Fix 1a).** Capture the exact RunPod
  pod id at provision time and carry it in the handle `extra` (`pod_id`) —
  the existing code comment (~L1391–1397: "we did not capture this here …
  a future revision should round-trip pods_ephemeral.json") marks this as
  the intended revision. This makes every FUTURE sidecar id-addressable and
  is what component 2's identity path keys on.
- In `RunPodBackend.launch`, wrap the post-provision segment (everything
  after the provision relay returns pod info, up to the successful handle
  return) in try/except.
- `RunPodWorkloadStartError` (incl. `RunPodProvisionBranchMismatchError`,
  a verified subclass): UNCHANGED — attach the #954 partial handle,
  re-raise; pod stays RUNNING per doctrine. Pin with a regression test.
- Any OTHER exception, ONLY when the workload-execution leg has NOT
  succeeded (exec not requested, or `workload_info` empty — critic r1
  Must-Fix 4): best-effort terminate the just-provisioned pod BY EXACT POD
  ID captured from the provision result (never a bare `--issue`-wide form —
  #1485 collateral; never name-keyed — multiple same-named bare `pod-<N>`
  pods can coexist, the #1739 shape), emit one loud log line naming the
  exception class + pod name/id + "no handle would have recorded this pod",
  then RE-RAISE the ORIGINAL exception. A terminate failure is logged and
  never masks the original raise (the crash is the signal; fail-fast
  preserved).
- When the exec leg DID succeed and a later step raises (e.g. inside
  `_build_handle`): NO terminate — the pod-side workload is live and
  self-contained (launcher + sentinel + EXIT-trap uploads own it); log
  loudly naming the pod and leave it running, re-raise the original.

**Component 2 — supersession reaping at the sidecar-overwrite seam
(`backends/issue_dispatch.py`).**

- In `dispatch_for_issue`, at the existing prior-sidecar snapshot point
  (`_prior_sidecar_failover_extras` already reads the old sidecar before
  `route()` overwrites it), extend the snapshot to the full prior handle and
  add a post-launch supersession check: fire only when ALL of —
  (i) prior handle exists and `prior.backend == "runpod"`;
  (ii) the prior pod identity is resolvable AND differs from the new
  handle's: prefer the exact `pod_id` in the prior extra (present on
  handles written after component 1's round-trip); for a LEGACY id-less
  prior handle — which is ALL RunPod sidecars written before this change
  (critic r1 Must-Fix 1c: the default, not an edge) — act only when a
  live-API read resolves the prior pod NAME (issue-scoped exact match, per
  (iii)) to EXACTLY ONE pod distinct from the new handle's; 0 or >1 name
  matches → skip + WARN (never a name-ambiguous kill — critic r1
  Must-Fix 1b);
  (iii) the prior pod name is issue-scoped by EXACT/DELIMITED match —
  `pod-<N>` exactly or `pod-<N>-<slug>` (and legacy `epm-issue-<N>` the
  same way) — never a bare `startswith` (a `pod-17` reap must not match
  `pod-1739`; critic r1 name-scoping concern);
  (iv) the task does NOT carry the `keep-running` tag (respect #1485). A
  tag-gated skip is NOT a silent stdout WARN: post a DURABLE
  `epm:progress` marker on the issue naming the superseded pod (name/id),
  its GPU spec / hourly burn when resolvable from the live API, and the
  recommendation to stop/terminate once the tag lifts (the standing
  "surface with pod name + hourly burn" shape; critic r1 Must-Fix 3);
  (v) a live-API read confirms the prior pod still exists and is not
  already terminated.
- Disposition by prior-handle evidence (critic r1 Must-Fix 2 — the
  discriminator is the FAILURE-path key, never `workload_executed` alone):
  - prior extra carries `workload_start_error` (the #954 partial-handle
    marker: workload start FAILED, nothing ran, no artifacts) → TERMINATE
    by resolved pod identity (the diagnosis window is moot — the
    superseding launch proves the owner moved the leg elsewhere).
  - `workload_executed` falsy WITHOUT `workload_start_error` =
    provision-only SUCCESS handle (the default interactive /issue shape —
    the experimenter drives the run over SSH; unuploaded checkpoints may
    sit on the volume and the sidecar is not the ownership record) →
    skip-provision-only + WARN, never auto-terminate.
  - `workload_executed` true → reversible STOP + WARN (a real run's
    state may sit on the volume; `stop` is not a durability substitute and
    the owner/watcher keeps final disposition).
- Record the action on the NEW handle's extra
  (`superseded_runpod_reaped: {pod_name, pod_id, action, ts}`) so the
  sidecar carries the audit trail; one loud log line per action.
- **Residual windows this seam structurally cannot close (critic r1
  Must-Fix 3):** under the `keep-running` tag the pod keeps billing until
  the tag lifts (the durable marker is the surfacing, per the standing
  no-auto-action-under-tag policy), and any halt→relaunch deferral window
  BEFORE a superseding launch exists (the actual #1739 22:46→05:53 leak
  preceded wave-2) is invisible to a launch-path seam by construction —
  the watcher pod-safety pass / stale-pod audit remain those windows'
  owners. Component 2 narrows the superseded-pod gap at supersession time;
  it does not claim to close the tag-gated or pre-supersession windows.
- Every failure inside the check (API error, unreadable prior sidecar,
  missing pod id) degrades to a WARN and NEVER blocks or fails the new
  launch — the reap is best-effort; the new launch's success is primary.
- All disposition/gating logic lives in a pure helper
  (`decide_superseded_runpod_reap(prior_handle, new_handle, issue,
  keep_running, live_state) -> "terminate" | "stop" | "skip-<reason>"`) so
  tests cover the decision table without network.

Out of scope (explicitly): changing the diagnosis-lane doctrine or #1997;
watcher-side changes (`autonomous_session_watch.py`); the GCP lanes;
naming-collision fix for bare `pod-<N>` fallback pods (a distinct gap —
noted for a possible follow-up filing, not this diff); provision-relay
pre-return failures (pod created server-side but the relay raises before
pod info returns — no id ever reaches this process; the stale-pod audit
stays that shape's backstop).

## 5. Success criteria (tests)

- C1-roundtrip: a fresh successful `launch()` handle `extra` carries the
  exact `pod_id` from the provision result.
- C1: a post-provision non-`RunPodWorkloadStartError` exception BEFORE the
  exec leg succeeds calls terminate with the provisioned pod's exact id
  (relay/API mocked) and re-raises the ORIGINAL exception type/message.
- C1-exec-succeeded: an exception AFTER a successful exec leg (raised in
  handle-building) → NO terminate call, loud log, original exception
  propagates.
- C1-regression: `RunPodWorkloadStartError` path — partial handle attached,
  NO terminate call, exception propagates (doctrine pinned).
- C1-mask-guard: terminate itself raising → original exception still
  propagates; failure logged.
- C2 decision table (pure helper): terminate on `workload_start_error`
  present; skip-provision-only on workload_executed-false WITHOUT
  `workload_start_error`; stop on workload_executed-true; skip on
  keep-running tag / unmanaged or non-delimited name (incl. the `pod-17`
  vs `pod-1739` collision row) / same pod identity / prior-not-runpod /
  pod-already-gone; legacy id-less prior handle × {0, 1, >1} live
  name-matches → {skip, act, skip}; every skip reason a distinct token.
- C2-keep-running-durable: the tag-gated skip posts the durable
  `epm:progress` marker naming pod name/id (+ burn when resolvable) — not
  only a log line.
- C2-integration: `dispatch_for_issue` with a mocked prior runpod sidecar +
  successful new launch invokes the reap once, records
  `superseded_runpod_reaped` on the new handle extra, and a reap API error
  does not fail the launch.
- Gate: mapped tests green; `workflow_lint.py` (no flags) with no NEW failures vs the plan-time baseline (step9c baseline compare / Step 10d baseline-subtracted lint gate are the binding repo-wide gates); `--check-asks` green; `ruff check` / `ruff format` clean on touched files.

## 6. Kill criteria

- Legacy id-less sidecars are ALL current RunPod sidecars (until component
  1's pod-id round-trip lands), handled by the unique-live-name-match
  disposition above — that path is the DEFAULT, not an edge (critic r1
  Must-Fix 1c). If implementation shows even the unique-name-match cannot
  be made safe (e.g. the live API cannot be name-queried reliably),
  descope legacy handles to WARN-only surfacing (id-bearing handles keep
  the full reap) and file a follow-up infra task naming the blocker.
- If component 1's exception seam turns out to have zero reachable raise
  sites between provision return and handle return (i.e. re-reading shows
  every raise is already `RunPodWorkloadStartError`-wrapped) → drop
  component 1 to an assertion + comment documenting the invariant; keep
  component 2.
