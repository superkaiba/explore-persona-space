# Plan v1 — #1863 daily-fix: poll ticks compute rate/ETA on long same-phase tails

## Goal / Requirement

Long tail phases must get a throughput read, not just a phase-name liveness read — idle-GPU billing hides behind "healthy" otherwise. Add a **same-phase rate/ETA duty** to the `/issue` Step 6d.2 poll-loop guidance so that after N consecutive same-phase ticks the orchestrator MUST compute a progress rate (Δunits/Δwall) and project a phase ETA, instead of echoing phase-name liveness indefinitely (incident #1482: ~5.4 h of idle-A100 billing across five consecutive 30-min ticks each reporting "Healthy — E2 upload at shardNN"; the ~98 files/h → ~33 h projection surfaced only when the session finally sized it).

### Acceptance criteria

1. `.claude/skills/issue/SKILL.md` Step 6d.2 carries a named duty paragraph — `**Same-phase rate/ETA duty (#1863; incident #1482).**` — with ALL of:
   - **Trigger:** ≥3 consecutive poll ticks reporting the SAME `current_phase` with no `new_milestone` (≈25–30 min at the fixed 540 s tick; the #1482 ticks were 30-min).
   - **Duty:** on the trigger tick and every subsequent same-phase tick, the liveness read includes a throughput read: extract the phase's monotonic progress counter from the tick evidence (log tail / sentinel progress field — `shard NN`, `file K/M`, `cell i/N`), compute `rate = Δunits / Δwall` over the same-phase tick window, project `ETA ≈ remaining units ÷ rate`.
   - **Record:** one `[phase-rate]` line in the session text AND in the periodic liveness `epm:progress` note (reuses `epm:progress` — NO new marker kind).
   - **Routing:** detection duty only, NOT a new gate — a pathological projection routes through EXISTING machinery (compute-deviation / vectorize mid-run trigger for fit phases; CLAUDE.md "CPU-only phases don't hold GPU pods" + the #1824 bulk `upload_folder` recipe for per-file upload tails). Auto-continue preserved; no AskUserQuestion.
   - **No-counter fallback:** state once `no progress counter readable — liveness only`, treat as a signal to add a per-unit progress line (pod-side-reporting.md / code-style.md convention) on the next code round.
   - **Worked example:** the #1482 numbers (five 30-min "Healthy — E2 upload at shardNN" ticks; ~98 files/h ⇒ ~33 h projection; ~5.4 h idle-A100 before sizing; ~1 h bulk-commit recovery via the #1824 fix).
2. § Long-phase heartbeat duty item 2 gains ONE cross-reference sentence: heartbeat evidence on a ≥3-tick same-phase stretch includes the `[phase-rate]` read (alive ≠ progressing).
3. A pin test `tests/test_issue_skill_phase_rate_duty_pin.py` asserts the duty's anchor substrings exist in SKILL.md (durability against the #1701 lost-update class; convention parity with the existing `test_issue_skill_*_pin.py` family).
4. `workflow_lint.py` no-flags + `--check-asks` pass on the touched files; ruff clean; no pinned region of SKILL.md is modified (additions only).

## Method delta

Prose-guidance + pin-test change only. No poller code change: `poll_pipeline.py` already surfaces per-tick evidence (log tails, progress notes) carrying countable units; the #1482 gap was orchestrator-side — nobody divided. The duty lands next to the existing advisory-handling paragraphs (gpu-idle / eta-deviation / gpu-width) in Step 6d.2, which are the exact surface the incident's five ticks flowed through. The `eta_deviation` advisory is NOT redundant with this: it is poller-computed elapsed-vs-plan (needs a plan §9 wall figure and fires only past 2× total), whereas this duty is a forward PROJECTION from observed progress units that fires while the phase still reads "healthy".
