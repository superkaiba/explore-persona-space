# Plan v2 — #1863 daily-fix: poll ticks compute rate/ETA on long same-phase tails

Revision of v1 per critic REVISE (Methodology lens, 2026-07-31): folds Must-Fix 1 (phase-label equivalence under advancing counters) and Must-Fix 2 (`log_tail_excerpt` availability under the #1841 compacted tick parse), plus the three non-blocking suggestions (no literal ask-tool token in the new prose; heartbeat cross-ref keyed on elapsed same-phase time; `[phase-rate]` once per liveness note).

## Goal / Requirement

Long tail phases must get a throughput read, not just a phase-name liveness read — idle-GPU billing hides behind "healthy" otherwise. Add a **same-phase rate/ETA duty** to the `/issue` Step 6d.2 poll-loop guidance so that after N consecutive same-phase ticks the orchestrator MUST compute a progress rate (Δunits/Δwall) and project a phase ETA, instead of echoing phase-name liveness indefinitely (incident #1482: ~5.4 h of idle-A100 billing across five consecutive 30-min ticks each reporting "Healthy — E2 upload at shardNN"; the ~98 files/h → ~33 h projection surfaced only when the session finally sized it).

### Acceptance criteria

1. `.claude/skills/issue/SKILL.md` Step 6d.2 carries a named duty paragraph — `**Same-phase rate/ETA duty (#1863; incident #1482).**` — with ALL of:
   - **Trigger:** ≥3 consecutive poll ticks reporting the SAME `current_phase` with no `new_milestone` (≈25–30 min at the fixed 540 s tick; the #1482 ticks were 30-min). **Phase-label equivalence (Must-Fix 1):** a phase label differing only in an advancing numeric/progress token (`E2 upload at shard17` vs `…shard23`, `cell 4/24` vs `cell 7/24`) is the SAME phase for this trigger — and that advancing token IS the progress counter to use.
   - **Input availability (Must-Fix 2):** on the trigger tick and every subsequent same-phase tick, the compacted #1841 tick parse ADDITIONALLY prints `log_tail_excerpt` (the #1841 field set is a minimum, so this is legal), or the orchestrator re-reads the tick's raw JSON line for it — the rate read's input must actually be in context, or the no-counter fallback silently swallows the duty.
   - **Duty:** extract the phase's monotonic progress counter from the tick evidence (the advancing label token, `log_tail_excerpt`, or a sentinel progress field — `shard NN`, `file K/M`, `cell i/N`), compute `rate = Δunits / Δwall` over the same-phase tick window, project `ETA ≈ remaining units ÷ rate`.
   - **Record:** one `[phase-rate]` line in the session text, and in the NEXT periodic liveness `epm:progress` note — once per liveness note, not per tick (reuses `epm:progress` — NO new marker kind).
   - **Routing:** detection duty only, NOT a new gate; auto-continue preserved — a pathological projection routes through EXISTING machinery (compute-deviation / vectorize mid-run trigger for fit phases; CLAUDE.md "CPU-only phases don't hold GPU pods" + the #1824 bulk `upload_folder` recipe for per-file upload tails). The new prose must NOT contain the literal ask-tool token (workflow_lint `--check-asks` fires on it without a gate citation) — word it as "not a new gate; auto-continue".
   - **No-counter fallback:** state once `no progress counter readable — liveness only`, treat as a signal to add a per-unit progress line (pod-side-reporting.md / code-style.md convention) on the next code round.
   - **Worked example:** the #1482 numbers (five 30-min "Healthy — E2 upload at shardNN" ticks; ~98 files/h ⇒ ~33 h projection; ~5.4 h idle-A100 before sizing; ~1 h bulk-commit recovery via the #1824 fix).
2. § Long-phase heartbeat duty item 2 gains ONE cross-reference sentence: heartbeat evidence on a long same-phase stretch — keyed on elapsed same-phase time (≥~60–90 min) or ≥2 heartbeat resumes, NOT the 3-tick count (heartbeat cadence is ~45–60 min, so tick-count keying would delay the first rate read to ~2–3 h) — includes the `[phase-rate]` read (alive ≠ progressing).
