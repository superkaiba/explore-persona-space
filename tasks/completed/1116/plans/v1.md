2. **Queue-timeout** (#783): `_maybe_escalate_gcp_queue_timeout` (L788) ages the `"pending"` phase against `EPS_GCP_QUEUE_WAIT_SECONDS` (600s) using the sidecar phase clock (`_read_phase_clock`/`_write_phase_clock`, L671/L695), rewrites to `GCP_QUEUE_TIMEOUT_PHASE`, `_failover_queued_gcp_to_runpod` (L2864) fails over with `teardown_first=True` (the queued instance is still live).

Its heuristic input set `_GCP_BOOT_DEATH_HEURISTIC_PHASES` (L287) **already contains `GCP_INSTANCE_NOT_FOUND_PHASE = "terminal_instance not found"`** when young (< 1500s).

**Why the vanish slipped through all three (verified on #1112 events, 2026-07-07):** creates at 22:30Z and 22:50Z reported success (insert DONE); the instances sat PENDING (route() relaunches at 22:35:35Z / 22:53:06Z reconnected to the then-LIVE queued instances — `outcome: reconnected`, correct behavior); both instances then vanished from instances-list with no delete op before the 600s queue-timeout could mature (and the orchestrator manually removed the stale sidecar at 22:46Z, so no dead poll with a live sidecar ever recorded a boot death — the #1029 streak stayed at 0). Even on the fully-automated path, #1029 would need TWO vanishes (two burned creates, two relaunch cycles) and would mislabel a pure capacity event as a boot problem. `route()` cannot see the vanish at all: the ladder advances only on create-time capacity errors, so every relaunch re-booked the same dead flex rung (attempts 3→4 of daily cap 8). Hand-pivot to `--backend runpod` at 23:02Z.

Two structural facts ground the design:
- `gcp.poll` maps a describe-404 to `_terminal_dead_poll(reason="instance not found")` → `current_phase = "terminal_instance not found"` (gcp.py L4693, L5947).
- The sidecar phase clock records `"pending"` while queued: `_maybe_escalate_gcp_wedge` stamps EVERY running-phase change (L763-766) and `_maybe_escalate_gcp_queue_timeout` stamps on first `"pending"` observation (L828-831); pinned by the existing test asserting `last_phase == "pending"` (test_backend_poll.py:1305-1306). This is exactly the "did the handle ever reach workload?" discriminator the task sketch proposed adding to gcp.py — it already exists.

## 4. Design

### Method delta vs the #783 / #1029 siblings

| | #783 queue-timeout | #1029 boot-loop | **#1116 queue-vanish (new)** |
|---|---|---|---|
| Input poll shape | running / `"pending"` | dead / setup-failed OR young terminated/not-found | dead / `"terminal_instance not found"` |
| Trigger condition | phase aged > 600s floor | streak ≥ 2 per (issue, rung) | instantaneous: clock `last_phase == "pending"` |
| Clock use | read + write (aging) | none (lease streak) | **read-only** (no aging, no write) |
| Teardown first | True (instance live) | False (VM self-reaped) | **False (instance GONE)** |
| Daily-attempt burn | none | none (skip avoids creates) | none |
| New state | none | lease streak field | **none** |

The vanish is carved OUT of #1029's heuristic input space: `not-found + clock-pending` (previously a heuristic boot death needing 2 poller-observed occurrences) is now classified first, in one occurrence, under the capacity reason. `not-found + any-other-clock-state` keeps today's #1029 path exactly.

### 4.1 `scripts/backend_poll.py` (the only behavioral file)

**(a) New phase constant**, in the constants block next to `GCP_QUEUE_TIMEOUT_PHASE` (L225):

```python
# The current_phase the POLLER synthesizes (#1116) when a GCP instance that was
# last observed in the FLEX_START capacity queue ("pending") resolves to
# instance-not-found: the DWS queue dropped the request server-side (create DONE,
# no delete op — #1112). _is_gcp_queue_vanish matches THIS phase EXACTLY; it is
# set ONLY by _maybe_escalate_gcp_queue_vanish.
GCP_QUEUE_VANISH_PHASE = "terminal_queue_vanish"
```

**(b) New escalation** `_maybe_escalate_gcp_queue_vanish(handle, result, sidecar: Path)` (no `now` param — no aging), placed after `_is_gcp_queue_timeout`. Guards, each returning `result` unchanged:
- `getattr(handle, "backend", None) != "gcp"` or `result.status != "dead"`;
- `result.current_phase != GCP_INSTANCE_NOT_FOUND_PHASE` (narrow to not-found; a `terminal_terminated` instance still EXISTS server-side — not the vanish shape);
- `_read_phase_clock(sidecar)[0] != GCP_PENDING_PHASE` (covers `None` = no record → fail-open to today's behavior);
- `_cpu_intent_blocks_runpod_failover(handle)` (gate the REWRITE, mirroring `_maybe_escalate_gcp_boot_loop` L1019, so a cpu-bigmem vanish keeps its ordinary dead path + boot-death record byte-identical).

On match: `logging.warning(...)` + `replace(result, status="dead", current_phase=GCP_QUEUE_VANISH_PHASE, new_milestone=True, pid_alive=False)` (the exact #783 rewrite shape, L843-849).

**(c) New predicate** `_is_gcp_queue_vanish(handle, result) -> bool` — mirror `_is_gcp_boot_loop` (L1039): defense-in-depth `_cpu_intent_blocks_runpod_failover` re-check, then `backend == "gcp" and status == "dead" and current_phase == GCP_QUEUE_VANISH_PHASE`.

**(d) New failover wrapper** `_failover_vanished_gcp_to_runpod(*, issue, handle, result, sidecar) -> dict` — thin wrapper over `_failover_gcp_to_runpod` (mirror `_failover_boot_looped_gcp_to_runpod`, L2905):

```python
return _failover_gcp_to_runpod(
    issue=issue, handle=handle, result=result, sidecar=sidecar,
    reason=ROUTE_REASON_GCP_QUEUE_VANISH_FAILOVER_RUNPOD,
    running_phase=ROUTE_REASON_GCP_QUEUE_VANISH_FAILOVER_RUNPOD,
    cause_label="GCP FLEX_START queue vanish",
    evidence_source="async_poller_queue_vanish",
    failover_tag="#1116 queue-vanish failover",
    teardown_first=False,   # the instance is GONE — the #659 stance, not #783's
    extra_evidence={"last_observed_phase": GCP_PENDING_PHASE,
                    "gcp_ladder_rung": str((getattr(handle, "extra", None) or {}).get("gcp_ladder_rung") or "unknown_rung")},
)
```

**(e) main() wiring** — insert immediately AFTER the `_is_gcp_queue_timeout` block (L3457-3463) and BEFORE the `_is_gcp_async_workload_failure` block:

```python
result = _maybe_escalate_gcp_queue_vanish(handle, result, Path(sidecar))
if _is_gcp_queue_vanish(handle, result):
    queue_vanish_json = _failover_vanished_gcp_to_runpod(
        issue=args.issue, handle=handle, result=result, sidecar=Path(sidecar)
    )
    print(json.dumps(queue_vanish_json))
    return 0
```

Ordering rationale: input-disjoint with the queue-timeout (running/pending vs dead/not-found) and the async-crash predicate (not-found vs terminal_workload_failed); MUST precede `_maybe_escalate_gcp_boot_loop` because not-found is in `_GCP_BOOT_DEATH_HEURISTIC_PHASES` — the vanish `return 0` prevents a capacity miss from poisoning the boot-death streak. **(f)** One-line docstring update in `_maybe_escalate_gcp_boot_loop` (L939-941): add `terminal_queue_vanish` to the "handled by EARLIER main() branches" list.

## 11. Decision Rationale

- **D1 — clock-based discriminator; no gcp.py edit.** *What:* detect "never reached workload" via the sidecar phase clock's `last_phase == "pending"` instead of persisting `reached_running` in the handle. *Why:* the clock already records every observed running phase (`_maybe_escalate_gcp_wedge` L763-766, `_maybe_escalate_gcp_queue_timeout` L828-831; pinned at test_backend_poll.py:1305) — zero schema change, keeps `GcpBackend.poll` a pure function (the #669/#783 design stance), and is provisioning-model-agnostic (load-bearing: #1112's live handles at vanish time were 22:35Z/22:53Z reconnect handles carrying `provisioning_model: "STANDARD"`, so any handle-side flex flag would have missed them). *Source:* read code + #1112 markers. *Alternative rejected:* the sketch's `reached_running: bool` in gcp.py — larger diff, sidecar-schema churn, still lost on the orchestrator's manual sidecar removal.
- **D2 — fire on the FIRST vanish (no streak, no floor).** *Why:* clock-pending + record-deleted is deterministic capacity evidence (the DWS drop), unlike #1029's ambiguous young-death heuristic; #783 also fires on first occurrence. Each avoided repeat saves ~1 create + ~20 min (measured on #1112: 22:30Z→22:46Z, 22:50Z→23:02Z). *Source:* #1112 events; #783 precedent.
- **D3 — `teardown_first=False`.** *Why:* the instance record is already gone; teardown is the #783-specific step for a still-live queued instance. *Source:* `_failover_queued_gcp_to_runpod` docstring (L2864) + the #659 stance.
- **D4 — no daily-attempt burn.** *Why/Source:* structural — `gcp_attempts_today` bumps only inside `_attempt_one_gcp_rung` on creates; the poller never re-enters it (#783, pinned by the L1184 test; mirrored by new test 3).
- **D5 — reuse the shared lease/sentinel core.** *Why/Source:* #659/#783/#1029 all ride `_failover_gcp_to_runpod`; the exactly-once bound and terminal-JSON contract come for free, and `test_failover_seam_default_reason_unchanged_byte_for_byte` protects the siblings.
- **D6 — no route()-side rung skip for vanish.** *Why:* #783 precedent (queue-timeout has none — the failover leaves the ladder entirely); a skip would add lease state for a path that no longer loops. The daily create cap bounds the pathological re-book cycle. *Source:* #783; #1029's skip exists only because sub-N boot deaths RE-ENTER the ladder — a vanish never does.
- **D7 — CPU guard via `_cpu_intent_blocks_runpod_failover` at the rewrite + predicate.** *Why/Source:* the #1029 shape verbatim (L1019 + L1051); new call sites use the helper per its ACCEPTED-DEBT note (L900).
- **D8 — no new env floor / tunable.** *Why:* the trigger is an instantaneous state transition, not an aged threshold — nothing to tune. Existing floors (#783's 600s, #1029's 1500s) untouched.
