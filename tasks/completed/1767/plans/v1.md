# Plan v1 — task #1767: width justification must bind to wall-dominant GPU-bound phases

## Goal / requirement

Close the phase-misattributed-justification loophole in the GPU-width
right-sizing lenses: a plan's stay-narrow justification must BIND to the
wall-dominant GPU-bound phase(s) it keeps narrow, and every GPU-bound §9
component with projected wall > ~2 h must name its shardable axis (or state
"none") so the binding is checkable.

**Acceptance criteria:**
1. `critic-lens-reference.md` item 10(iv)'s conversely-clause REVISEs a
   stay-narrow plan whose justification is a bottleneck claim about a
   DIFFERENT phase (API-bound judge, CPU fit/Gram-solve, off-pod phase) —
   exactly as if no justification were stated — citing incident #1739.
2. `planner-section-reference.md` §9 requires, per GPU-bound
   compute-projection-table row with projected wall > ~2 h, that the row's
   `parallelism` field names the shardable axis (contexts / behaviors /
   seeds / conditions) or states `none — <why>`; when an axis exists the
   phase defaults to wide (`--gpus N`) and a stay-narrow choice carries a
   justification binding to THAT phase; and the "State explicitly" item (d)
   requires the stay-narrow reason to address the wall-dominant GPU-bound
   phases.
3. `experiment-guidelines.md` guideline 2's REVISE line requires the
   justification to bind to the shardable phase itself, not a different
   phase.
4. Legitimate stay-narrow cases are NOT weakened: genuinely non-shardable
   workloads, short phases (< ~2 h), width-required pinned jobs, and the
   re-provision-churn tradeoff for SHORT narrow phases all remain valid.
5. The three surfaces stay mutually consistent (lens text ↔ planner duty ↔
   v2 guideline) and consistent with the #1121 width-aware router language.
