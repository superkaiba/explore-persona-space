# Plan v1 — workflow-fix: letter-arrow transition token class for figure opaque-code check

## Goal

Extend `verify_task_body.py`'s check-28 opaque-config-code token classifier
with a **letter-arrow transition class** so panel-title strings like
`"B->S_single"`, `"S->D_multi"`, `"D->R_single/multi"` (which slipped past
the existing @L-pin, snake, H-code, slot-family, and P-M candidate classes
in #1902) are mechanically flagged as WARN. Ships together with a
regression test pinning the new class and confirming the existing path-
shaped exemption applies.

## Acceptance criteria

1. `verify_task_body._opaque_code_tokens("B->S_single") == ["B->S_single"]`
   (and analogous positive assertions for `"S->D_multi"`, `"D->R_single"`,
   `"D->R_multi"`, `"S→D"` (unicode arrow), `"A -> B"` (spaces around ASCII arrow),
   `"A→B"` (no-space unicode)).
2. Negative assertions still hold: multi-char chemical labels like `"Fe->Fe2+"`
   do NOT match (regex requires single `[A-Z]` on each side); lowercase RHS
   like `"A->b"` does NOT match; slug-only strings like `"log_prob"` remain
   clean; existing GPU / hypothesis / candidate false-positive pins
   (`"P100"`, `"H20"`, `"P1C"`, `"p50"`) are unchanged.
3. Path-shaped exemption applies: a whole path-shaped string like
   `"figures/issue_1902/A->B.png"` yields `[]`, and a path-shaped word inside
   prose like `"source: figures/issue_1902/A->B.png"` yields `[]` — the
   existing `_only_in_path_words` helper covers the new class the same way
   it covers `_HYPOTHESIS_CODE_RE` / `_SLOT_FAMILY_RE` / `_CANDIDATE_CODE_RE`.
4. Full-body integration test: an inline sha-pinned figure whose sidecar
   `text.axes[0].title = "B->S_single"` produces `check_figure_label_codes`
   verdict `passed=True, is_warn=True` with the token appearing in
   `res.detail`.
5. `verify_task_body.py`'s check-28 module docstring + label string + the
   `_opaque_code_tokens` docstring name the new class alongside the five
   existing classes.
6. Existing `tests/test_verify_task_body.py` suite passes (no regressions
   in the ~40 check-28 tests or the wider suite via Step 9c mapped scope).
7. `ruff check` and `ruff format --check` are clean on the touched files.

## Method delta (single-variable-change)

Existing classifier iterates over 5 token-class regexes with a shared
per-word path-shaped exemption. This plan adds ONE additional regex
class and threads it through the same iteration loop — no other
classifier logic, no walker changes, no scope changes. The check
remains WARN-only, sidecar-scoped (`_iter_meta_label_values`), and
fail-soft on missing sidecars (unchanged from check 28 today).

## Method soundness (methodology lens)

- **Sidecar scope inherited.** `check_figure_label_codes` scans only figure
  sidecar meta strings (`_iter_meta_label_values`), not body prose. So
  legitimate `A -> B` in Methodology prose is untouched by construction —
  the task body's "keep the check scoped to figure titles + sidecar-echoed
  strings" caveat is satisfied because the check has always been scoped
  that way; the new regex inherits that scoping via `_opaque_code_tokens`.
- **False-positive envelope.** Within sidecar strings, `[A-Z]` on both
  sides + word boundaries + arrow between (with optional whitespace):
  matches project-internal letter-coded transitions (the #1902 shape) and
  refuses multi-char (`Fe->Fe2+`, chemistry), lowercase-RHS (`A->b`,
  arithmetic prose fragments), digit-based (`1->2`), and hyphen-only
  (`A-B`, dash) shapes. The path-word exemption via `_only_in_path_words`
  handles the pathological case of `A->B` appearing inside a figure
  filename.
- **`_SNAKE_TOKEN_RE` interaction.** The existing snake regex matches
  the RHS suffix `S_single` (letter + `_single`) as a snake token but does
  NOT flag it because the classifier requires ≥2 underscores OR ≥1 digit;
  `S_single` has 1 underscore and 0 digits, so it slips through the snake
  arm silently. The letter-arrow arm catches the WHOLE token including
  the `B->` prefix. Dedup by casefold (existing `seen` set) handles any
  edge where both regexes match the same substring.
- **Docstring "code-span contexts" NO-OP.** The check-28 docstring already
  notes that sidecar strings are matplotlib rendered text serialized to
  JSON (never markdown), so backtick code spans cannot occur — the new
  regex needs no code-span exclusion for the same reason.

## Kill criteria

- If any negative-assertion pin fails (a legitimate string falsely flags
  as opaque code — chemistry, arithmetic prose, GPU-name shape drift):
  the regex is too permissive, revise the pattern.
- If the check-28 walker test suite regresses (any pre-existing test
  turns red): the new regex has unexpected interaction with an existing
  class or with the walker.
- If ruff format or lint fails on the touched files after the edit: the
  regex string or docstring formatting is off.
