## 1. Goal + requirement + acceptance criteria

**Goal (task frontmatter):** tighten `_is_transient_upload_error` to short-circuit non-transient on 4xx status codes.

**Requirement:** `_retry_upload` must never retry a deterministic HTTP client error (4xx other than 429) regardless of what digits/words its message embeds; genuinely transient errors (429, 5xx, connection drops, timeouts) keep the existing bounded 6-attempt exp-backoff retry.

**Acceptance criteria (code-change form):**
1. `_is_transient_upload_error(_http_err(404, ".../issue504_raw/x.json"))` returns `False`; wrapped in `_retry_upload`, the thunk is called exactly once and the exception propagates immediately.
2. `_is_transient_upload_error(_http_err(413, "413 ... 15000000000 bytes"))` returns `False` (byte-count digit trap).
3. 429 and all 5xx (incl. 507, 520) return `True` by status code.
4. Response-less errors keep substring behavior: `requests.ConnectionError("connection reset")` → `True`, `TimeoutError("Read timed out")` → `True`, `ValueError("bad args")` → `False`.
5. `_is_storage_quota_403` semantics untouched (function not edited); `_is_transient_upload_error(_storage_403())` still `False` (now via the 403 code short-circuit rather than substring miss).
6. Every existing test in `tests/test_hub.py` passes; ruff clean.

## 2. Method delta (what differs from current code)

Current (hub.py:545-566): status-code check is a **positive-only** allowlist — `code in (429, 500, 502, 503, 504)` returns `True` on match, but on ANY other code (incl. all 4xx, and 5xx codes like 507/520) it **falls through** to the fuzzy `str(err).lower()` substring scan, which matches `"504"/"502"/"503"/"500"` anywhere in the message.

New: when a **real integer** status code is present, the decision is **entirely by code** — `code == 429 or 500 <= code < 600` — with no substring fallback. The substring scan runs only when `code` is not an int (response-less exceptions: `requests.ConnectionError` has `response=None`; `TimeoutError`/`OSError` have no `response` attribute). Two deliberate side effects: (a) 5xx codes outside the old tuple (507, 520-class) become transient **by code** instead of depending on message text; (b) a 4xx whose message contains "connection"/"timeout"/"504" etc. becomes deterministically non-transient.

`_is_storage_quota_403`, `_retry_upload`, and all call sites are unchanged.

### Diff sketch — hub.py

```python
def _is_transient_upload_error(err: Exception) -> bool:
    """True for retryable transient HF/HTTP upload errors (429/5xx by status
    code, connection drops / timeouts by message) — NOT the persistent
    storage-quota-403. When the exception carries a real integer HTTP status
    code, the decision is made ENTIRELY by code: 429 and any 5xx are
    transient; every other code (all 4xx) is non-transient, with NO substring
    fallback — 4xx messages can embed digit triplets ('issue504_raw/...',
    byte counts) that would read as false-transient (#989). The substring
    scan applies only to response-less errors (ConnectionError, timeouts)."""
    code = getattr(getattr(err, "response", None), "status_code", None)
    if isinstance(code, int):
        return code == 429 or 500 <= code < 600
    msg = str(err).lower()
    return any(
        s in msg
        for s in (
            "504",
            "502",
            "503",
            "500",
            "gateway time-out",
            "gateway timeout",
            "timed out",
            "timeout",
            "connection",
            "temporarily unavailable",
        )
    )
```

(Net change: replace the `if code in (429, 500, 502, 503, 504): return True` block with the `isinstance(code, int)` full-decision branch; substring tuple unchanged; docstring updated per docstring-on-edit.)

## 10. §11 Decision Rationale

1. **All 5xx transient by code (`500 <= code < 600`), not only (500,502,503,504).**
   - **What:** the transient set is `{429} ∪ [500,600)`.
   - **Why:** every 5xx is by definition a server-side condition (RFC 9110 §15.6); HF's Xet/CDN paths surface Cloudflare-class 520/522/524 and 507-style codes that are transient in practice. Cost asymmetry: retrying a rare persistent 5xx costs the same bounded ~10 min worst case the wrapper already accepts for real 5xx; NOT retrying a transient 520 fail-fasts a recoverable upload. The current code already effectively retried unlisted 5xx via the substring scan whenever the message named a gateway error — this makes that coverage deterministic. The one known persistent HF error that must NOT retry is the storage-quota **403** (a 4xx — handled) and the >10000-files **400** `BadRequestError` (4xx — now deterministically non-transient, matching gotchas.md's documented intent).
   - **Source:** `requests`/HTTP semantics (4xx = deterministic client error, 5xx = server condition) + this repo's own validated retry design in #735 (built `TestRetryUpload` + the wrapper) and #794 (extended it to `list_repo_files_complete`); gotchas.md "HF Hub rejects ... `BadRequestError` ... NOT transient" (the 400 class), upload-policy.md "storage-quota 403 is persistent" (the 403 class).
   - **Alternatives:** keep the exact (500,502,503,504) tuple by code and non-transient for other 5xx — rejected: silently DROPS retry coverage the substring scan currently provides for gateway-error messages, a behavior regression orthogonal to the bug being fixed.
2. **Substring scan retained ONLY for response-less errors (`isinstance(code, int)` gate).**
   - **What:** message-sniffing applies only when no integer status code exists on the exception.
   - **Why:** `requests.ConnectionError.response` is `None` and `TimeoutError` has no `.response` attribute (both verified live on the installed requests 2.33.1) — these carry no code, so message matching is the only signal; conversely a real code is authoritative, and message digits are provably unreliable (`issue504_raw` paths, byte counts). The `isinstance(code, int)` guard (rather than `is not None`) protects against exotic non-int `status_code` attributes falling into the code branch.
   - **Source:** live introspection of the installed libs (this plan, §11 Assumptions); `huggingface_hub` 0.36.2 `HfHubHTTPError(response=...)` semantics; prior issues #735/#794.
   - **Alternatives:** delete the substring scan entirely and enumerate exception types — rejected: broader change, breaks `test_connection_error_retried`'s message-based contract, out of scope for a one-predicate tightening.
