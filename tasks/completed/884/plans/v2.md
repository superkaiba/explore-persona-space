## 1. Goal, requirement, acceptance criteria

**Goal.** VM-side long-running (>~15 min) compute phases launched directly by an /issue orchestrator must survive session death / watcher force-stop, and a successor session must be able to re-attach to them mechanically instead of relaunching from scratch.

**Requirement (the two-part convention).**

1. **Launch shape:** `PHASE_PID=$(bash -c 'setsid nohup <cmd> < /dev/null >> <abs, space-free log path> 2>&1 & echo $!')`, verified with `ps -p "$PHASE_PID" -o args=`. The `bash -c` wrapper is load-bearing for pid capture (fact-check corrected): the harness TOP-LEVEL Bash-tool shell runs with job control ON (`$-` contains `m`), where `setsid` FORKS and a bare `$!` is the vanished intermediate; inside the wrapper (job control OFF) `setsid` execs without forking, so `$!` is the workload pid. On a verify mismatch, recover via `pgrep -f '<distinctive invocation>'`.
2. **Breadcrumb:** the phase's `stage-dispatch` breadcrumb carries two additional whitespace-split `key=value` tokens: `pid=<pid> log=<abs log path>`. Successor rule: live pid ⇒ re-attach (poll pid + tail log), never relaunch; dead pid + no completion output ⇒ kill-before-relaunch probe, then relaunch.

## 3. Mechanism (grounds the design; verified this session)

Local experiment in a non-interactive bash (the harness shell class), pids observed:

- Plain `nohup sleep 300 &` → `pid=389470 pgid=389458 sid=389438` — **inherits the shell's process group AND session**. Any group-directed kill (`kill -- -PGID` / `killpg`) or session-tree stop takes it down; `nohup` is irrelevant to SIGTERM/SIGKILL.
- `setsid nohup sleep 300 </dev/null &` → `pid=pgid=sid=389471` — **its own new session + process group** (setsid(2) semantics). Group kills miss it; once the launching shell exits it reparents to PID 1, so ppid-tree walks miss it too. `< /dev/null >> log 2>&1` drops every fd tether to the dying session (no SIGPIPE / blocked write on a dead pipe).
- **`$!` semantics (CORRECTED per fact-check):** inside a `bash -c` / script shell (job control OFF) `$!` IS the final workload pid — the backgrounded child is not a process-group leader, so util-linux `setsid` execs without forking (planner observed `$!`=389471 == workload; fact-checker observed `$!`=435412 == workload). But the harness TOP-LEVEL Bash-tool shell runs with job control ON (`$-` contains `m`, fact-checker verified in two separate calls), where `setsid` FORKS and `$!` is the vanished intermediate (observed `$!`=433276 vs actual workload 433278). The convention therefore mandates launching through a `bash -c` wrapper — `PHASE_PID=$(bash -c 'setsid nohup <cmd> ... & echo $!')` — where `$!` is reliable, plus the cheap post-launch verify `ps -p "$PHASE_PID" -o args=` and, on mismatch, recovery via `pgrep -f '<distinctive invocation>'`. Wording note (fact-check): a top-level job-control-ON plain bg child gets its OWN pgid but shares the sid — either way it stays in the session's kill domain, so the kill conclusion is unaffected.
