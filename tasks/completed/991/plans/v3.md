## 1. Goal / requirement + acceptance criteria

Add a RUNTIME guard at the `dispatch_calls` seam so a system-bearing `messages` list can never reach the Anthropic wire un-lifted. The contract already exists as a docstring NOTE (`api_dispatch.py:1127-1131`, added by #955); nothing enforces it, and the #906 r11 incident showed the failure mode: a builder forwarding a caller message list verbatim 400s EVERY request of that class (`invalid_request_error`), surfacing only in production because the seam is mocked in tests.

**Acceptance criteria:**
1. A `build_request` that returns params whose `messages` contains any `{"role": "system"}` dict entry causes `dispatch_calls` to raise `ValueError` before any client call FOR THE OFFENDING ITEM (sync — a mixed sync dispatch may already have started good-item requests, matching existing builder-exception semantics; reconciler-rescoped) / before any `batches.create` or `state.json` write (fresh batch).
2. The error message names the `item_id`, the offending message index, the 400-class consequence, and both reference lifts. Test-pinned components: index + item_id + one fix-pointer substring (`anthropic_format`); the remaining wording is code-review-verified (the "exact wording" allowed-deviation covers phrasing, not the pinned substrings).
3. Zero behavior change for system-free callers: the full existing `tests/test_api_dispatch.py` suite (49 test functions / 53 collected via parametrization — fact-checked) passes unmodified; a new positive-control test with a top-level `system=` param passes.
4. On batch RESUME with a raising builder, the affected sub-batch stays `"pending"` on disk (no crashed-mid-submit wedge).
5. `uv run ruff check` clean on touched files; `uv run python scripts/workflow_lint.py` default run passes.

### 4b. Guard functions (concrete diff sketch)

Insert near the `BuildRequest` type alias (after L250), module-level:

```python
def _assert_no_system_role(params: dict, item_id: str) -> None:
    """Fail fast on a system-role message in built Messages-API params.

    The Anthropic Messages API has no "system" message ROLE — a system-bearing
    ``messages`` list 400s EVERY request (invalid_request_error; the #906 r11
    incident, .claude/rules/gotchas.md). System content must be lifted by the
    BUILDER to the top-level ``system=`` param (see
    ``llm.models.Prompt.anthropic_format`` for a leading-system splitter or
    ``artifacts.datagen._gen_params_from_messages`` for an arbitrary-position
    lift). Only the documented dict shape is inspected: non-dict params /
    entries and a missing ``messages`` key pass through untouched (the API
    itself owns those errors).
    """
    messages = params.get("messages") if isinstance(params, dict) else None
    if not isinstance(messages, list):
        return
    for i, msg in enumerate(messages):
        if isinstance(msg, dict) and msg.get("role") == "system":
            raise ValueError(
                f"build_request(item_id={item_id!r}) returned a messages list with "
                f'role="system" at index {i}. The Anthropic Messages API has no '
                "system message role — every such request 400s "
                "(invalid_request_error). Lift system content to the top-level "
                "system= param in your builder (see llm.models.Prompt."
                "anthropic_format or artifacts.datagen._gen_params_from_messages)."
            )


def _guarded_build_request(build_request: BuildRequest) -> BuildRequest:
    """Wrap ``build_request`` so every produced params dict is system-role-checked.

    Applied ONCE at the dispatch_calls seam; covers all three consumers (sync
    ``_do_one``, batch state-init, batch submit/resubmit) because they all
    receive the same threaded callable. Raises ValueError at BUILD time —
    before any wire call or paid batch create.
    """

    def _built(item: DispatchItem) -> dict:
        params = build_request(item)
        _assert_no_system_role(params, item.item_id)
        return params

    return _built
```

### 4c. Hook point (the single chokepoint)

In `dispatch_calls` (L1095), immediately after the `if not items: return {}` early-return (L1158-1159):

```python
    # Runtime enforcement of the system-role contract (docstring NOTE above):
    # one wrap covers the sync build (_do_one), the batch state-init build,
    # and the batch submit/resubmit build — they all thread this callable.
    build_request = _guarded_build_request(build_request)
```

Why here and not per-call-site: grep-verified, `build_request(` is called at exactly three places (L699, L801, L867), all reached only via the callable threaded from `dispatch_calls` → `_dispatch_calls_inner`. Wrapping at the public seam (a) is one line, (b) cannot drift when a fourth consumer is added later (any new consumer receives the already-guarded callable), (c) leaves the internal helpers testable in isolation with unguarded builders. Direct calls to the private `_dispatch_sync` / `_dispatch_batch` (tests only; no production caller — grep in §12 A6) bypass the guard by design: the contract named by the task is the `dispatch_calls` seam.

### 4e. Failure semantics per path (with the guard)

| Path | Where the guard fires | Effect | Spend at raise |
|---|---|---|---|
| **Sync** (`_do_one` L699) | first build, outside the retry `try` | `ValueError` propagates through `asyncio.gather` (default `return_exceptions=False`) → whole `dispatch_calls` raises. Identical to TODAY's semantics for ANY builder exception at L699 (it is already outside the try — verified), so this introduces no new failure class. NOTE (critic-corrected): gather does NOT cancel sibling in-flight coroutines on first exception — they run to completion and their results are discarded when `dispatch_calls` raises (env-built clients then closed by the L1186 `finally`). Do not copy a "cancelled by gather" claim into code comments. | 0 for the raising item; concurrent good items may have started (unavoidable, same as today) |
| **Batch, fresh** (`_load_or_init_batch_state` L801) | all-items build at state init | raises BEFORE the `state.json` write (L822) and before any `batches.create` | $0, no checkpoint written |
| **Batch, resume** (`_submit_one_sub_batch` L867) | per-sub-batch build at submit | with the §4f reorder: raises while the sub-batch is still `"pending"` → resumable after the builder is fixed. Without the reorder it would wedge at the L1002 crashed-mid-submit `RuntimeError` (manual checkpoint surgery) | $0 for that sub-batch |

Deliberately whole-call raise (not per-item `error=True`): a contract violation is a caller BUG, uniform across a request class — degrading it to per-item errors would let a caller silently proceed on partial data, which is exactly the "fallback that swallows the fault" the fail-fast rule bans. Cost-wise the raise is EARLY on both paths (build time precedes create), so "raising crashes a large batch job late" does not apply.

### 4f. `_submit_one_sub_batch` reorder (4 lines moved)

Move the `requests = [...]` list-build (L866-869) ABOVE the `sb["status"] = "submitting"` + persist pair (L864-865). The #663 preserve-before-propagate contract is untouched — the "submitting" intent is still persisted BEFORE `batches.create`; the builder call is pure (no side effects), so building first is safe. This makes any builder exception on resume (the guard's, or any other) fail clean-and-resumable.

## 11. Decision Rationale

**Training hyperparameters:** N/A — no training hyperparameters (no model training).

1. **RAISE, not lift (and no hybrid, no opt-in lift flag).**
   *What:* the guard raises `ValueError`; it never mutates params.
   *Why:* (a) Project fail-fast rule — a seam-side silent lift is a "fallback that swallows the fault": the caller's builder bug is masked forever and the class of #906-style bugs stops being findable. (b) The lift is a BUILDER responsibility with two on-main reference implementations; a caller that wants lifting copies the `_gen_params_from_messages` pattern (4 lines). (c) A seam-side lift of MID-list system entries has genuinely ambiguous semantics (interleaved system content has no exact Anthropic equivalent — lifting reorders content), so the seam would sometimes silently send something the caller didn't write. (d) No in-repo caller needs a lift today (all four verified compliant), so an opt-in lift is dead code (YAGNI) and widens the diff. (e) Timing favors raise: on both paths the guard fires at build time, BEFORE any wire call or paid batch create — the "raise crashes a big batch late" concern is empirically false for this code (fresh batch builds ALL requests at state-init, L801, before any `batches.create`).
   *Source:* CLAUDE.md § Critical Rules "Fail fast — never hide failures"; `.claude/rules/gotchas.md` § "The Anthropic Messages API has NO `system` message ROLE" (#906 r11); `artifacts/datagen.py:303` + `llm/models.py:161` (the builder-side lift precedents); #955 (the docstring NOTE this enforces).
   *Alternatives rejected:* silent lift (masks caller bugs, ambiguous mid-list semantics); raise-with-`EPM_DISPATCH_LIFT_SYSTEM=1` opt-in (dead code, an env-var escape hatch invites permanent reliance); per-item `error=True` degradation (partial-data silent proceed — worse masking than lifting).

2. **Guard placement: wrap the callable once in `dispatch_calls`, not per consumption site.**
   *What:* `build_request = _guarded_build_request(build_request)` after the empty-items early-return.
   *Why:* one line covers the grep-verified-exhaustive three consumers AND any future fourth; per-site asserts (3 copies) can drift.
   *Source:* read of `api_dispatch.py` L699/L801/L867 + `_dispatch_calls_inner` threading (this plan, §4c).
   *Alternatives:* assert inside `_do_one`/`_load_or_init_batch_state`/`_submit_one_sub_batch` (3× duplication); assert at the wire calls L710/L874 — inferior because (critic-corrected grounds, stronger than the original) the sync wire site L710 sits INSIDE the retry `try`, so an assert there is swallowed by `except Exception` into a per-item error (inconsistent with the batch side), and the batch assert at L874 fires after the `"submitting"` flip, reproducing the L1002 wedge unless also reordered. (Original "L801 copy would go unchecked" claim was imprecise — the L801-built params are discarded, state.json stores custom_ids/counts only, and requests are REBUILT at submit L866-869.)

3. **`ValueError`, not a custom exception class.**
   *Why:* matches the module's existing contract-violation precedent (`checkpoint_dir` ValueError at L1258) and the builder-side precedent (`_gen_params_from_messages` raises ValueError); a new public exception class would be a contract addition this guardrail doesn't need.
   *Source:* `api_dispatch.py:1258`; `datagen.py:322-326`.

4. **`_submit_one_sub_batch` reorder (build before status-flip).**
   *Why:* without it, a builder raise on RESUME persists `submitting`+`batch_id=None`, and the next resume hits the L1002 refusing-to-resubmit `RuntimeError` — a manual-surgery wedge for what is a clean, retryable caller bug. The reorder preserves the #663 preserve-before-propagate contract exactly (intent still persisted before `batches.create`; the build is side-effect-free).
   *Source:* `api_dispatch.py:836-874` (the #663 contract docstring) + L999-1009 (the wedge this avoids).
   *Alternatives:* leave as-is and accept the wedge on the rare cross-version-resume edge (rejected: 4 moved lines buy a clean failure mode); try/except-restore around the build (more code for the same effect).

5. **No opt-out env var.**
   *Why:* an escape hatch for a guaranteed-400 request shape has no legitimate use — any request the guard blocks would fail at the API anyway; an env var only creates a path to ship the bug.
   *Source:* the gotchas entry ("a system-bearing list 400s every request" — there is no working configuration to preserve).
