## 1. Goal, requirement, acceptance criteria

**Goal:** Handle symlinked per-issue cache dirs in the janitors: unlink the symlink and reap the resolved target only when it resolves inside the managed eps-data cache root (and is verifiably the relocated cache itself), instead of failing `rmtree` on the link.

**Requirement:** `shutil.rmtree` refuses symlinks by design (verified live on Python 3.11.15: `OSError: Cannot call rmtree on a symbolic link`). The #681-era interim relocation pattern (`data/issue_<N>/hf_dl → /mnt/eps-data/.../issue_<N>/hf_dl`, live today for #761) therefore makes every janitor reap FAIL on the *healthiest* configuration (zero boot-disk bytes at stake): `clean_experiment_downloads.py <N> --apply` exits 2 (`main()` line 789: `return 2 if res.failed else 0`), and `vm_disk_guard.py --apply` reports `issue 761: FAILED to remove ...` and — because nothing was freed on an over-threshold disk (`/` was ≥93% throughout the incident window) — exits 2 via its `still_over` check (line 810), masking real failures.

## 2. Method delta (what differs from current behavior)

| Case | Current behavior | New behavior |
|---|---|---|
| Cache dir is a symlink → dir inside managed root, naming the owning issue, basename == cache name | `rmtree(link)` raises → `failed`, exit 2 | rmtree the resolved target, then unlink the link → `removed`, bytes counted |
| Cache dir is a symlink → anything else (outside root, root itself, inside root but naming a different issue, NOT a dir, or basename ≠ cache name — e.g. → `store/`, → `eval_results/`, → a renamed dir, → any FILE) | same failure | unlink the link only; target KEPT; recorded in new `CleanResult.symlink_external_kept` + stderr note + sidecar event `symlink-external-target-kept`; NOT counted in `removed`/`bytes_freed` |
| Dangling symlink named `hf_dl`/`g*_dl` | invisible (discovery filters `is_dir()`, which follows and returns False) — left forever | discovered, unlinked → `removed`, size 0 |
| `issue_<N>` PARENT dir is a symlink; cache child is a real dir through it (managed+issue-named target) | `rmtree(cache_dir)` deletes THROUGH the parent link at the resolved location (works, but unverified where) | disposition-checked: rmtree the RESOLVED cache target → `removed`; the shared parent link is NEVER unlinked |
| `issue_<N>` PARENT dir is a symlink; resolved cache target external / foreign-issue | `rmtree(cache_dir)` deletes the EXTERNAL target's contents through the link | SKIP entirely — nothing deleted, nothing unlinked; recorded in `symlink_external_kept` (`via=parent`) + sidecar; NOT `removed`/`failed` |
| Dry-run on any symlink case | symlink-to-dir counted as plain `would remove`; dangling invisible | disposition-aware report: managed/dangling → `removed` (would remove), external/non-cache-shaped → `symlink_external_kept`; `CleanResult.symlink_targets` maps rel → resolved target in both modes |
| Real dirs with no in-tree link (the normal boot-disk case) | works | unchanged |
| vm_disk_guard tier (b) | `FAILED to remove` row per symlinked cache | no FAILED row; new detail row for external-kept links; everything else via unchanged delegation |

Deliberately unchanged: `_dir_size_bytes` (follows the link; for a managed reap the sized bytes ARE what is freed — on the data disk, which is exactly tier (b)'s documented contract of reaping "on EITHER disk", `vm_disk_guard.py:568-571`); both reap gates (verified to work through symlinks — gate 1 is issue-number-keyed, gate 2's `rglob` traverses the target); the exit-code semantics of both CLIs.

**Why reap the target at all:** tier (b) is "the ONE data-disk-appropriate arm: it reaps a TERMINAL issue's re-downloadable `hf_dl`/`g*_dl` cache on EITHER disk and ESCALATES (never deletes) an ACTIVE task's cache" (`run_guard` docstring, `scripts/vm_disk_guard.py:568-571`; same contract in CLAUDE.md § Disk hygiene). The escalate-only restriction applies to the `/`-rooted tiers (a)/(c) on the data-disk pass, not to tier (b). A terminal issue's relocated re-downloadable cache is precisely what the #681 quota design expects to reclaim. Unlinking only the symlink and stranding the target would leave unreferenced data-disk bytes that no janitor could ever find again (discovery walks `data/`, and the pointer would be gone) — the worst of both worlds.

```python
def data_disk_root() -> Path:
    """Managed data-disk root (env ``EPS_VM_DATA_DISK_PATH``; blank -> default)."""
    raw = os.environ.get("EPS_VM_DATA_DISK_PATH", "").strip()
```

**(b) Issue-naming + containment + cache-shape predicate** (module-private):

```python
def _path_component_names_issue(rel: Path, issue_n: int) -> bool:
    """True iff some path component is issue_<n>/issue<n> (or an
    issue_<n>_<slug> prefix form) — the same exact-N-boundary rules as
    issue_data_dirs (issue_65 never matches issue_658).
    NOTE: the post-#681-cutover worktree layout may name issue dirs with a
    HYPHEN (issue-<n>); deliberately NOT matched yet — a hyphen-named target
    takes the fail-toward-keep disposition, the safe direction. Widen when
    the cutover lands, with a test."""
    n = str(issue_n)
    for comp in rel.parts:
        if comp in (f"issue_{n}", f"issue{n}"):
            return True
        if comp.startswith((f"issue_{n}_", f"issue{n}_")):
            return True
    return False

def _managed_symlink_target(cache_dir: Path, issue_n: int) -> Path | None:
    """Fully-resolved target iff ALL of: STRICTLY inside data_disk_root();
    a path component names issue_n; the target IS a directory; AND the
    target's basename EXACTLY matches the cache dir's name (the relocation
    pattern is name-preserving — hf_dl->hf_dl, g1_dl->g1_dl). Else None
    (fail-toward-keep). The is_dir + exact-name requirements are MF1: they
    stop a same-issue alias (hf_dl -> .../issue_<n>/store, or -> any file)
    from being reaped — gate 2's rglob matches descendants only, never the
    resolved root itself, so this predicate is the only defense.
    realpath on BOTH sides defeats nested-link / relative-link escapes."""
    target = Path(os.path.realpath(cache_dir))
    root = Path(os.path.realpath(data_disk_root()))
    if target == root or not target.is_relative_to(root):
        return None
    if not _path_component_names_issue(target.relative_to(root), issue_n):
        return None
    if not target.is_dir() or target.name != cache_dir.name:
        return None
    return target
```

The issue-component requirement defends against a hand-made alias into ANOTHER issue's (or shared) data-disk state; the is_dir + exact-basename requirement (MF1) defends against a same-issue alias into a PRECIOUS dir (`store/`, `eval_results/`) or a file — both take the external-kept disposition (target kept, sidecar-escalated).

**(c) `CleanResult` extension** (two fields; existing fields + `bytes_freed`/`total_discovered_bytes` semantics untouched):

```python

# modes, for both direct-link and symlinked-parent cases.
symlink_targets: dict[str, str] = field(default_factory=dict)
# (rel, target): target NOT ours to reap — KEPT. Direct-link case: the link
# itself is (would be) unlinked. Symlinked-parent case: NOTHING is unlinked
```

**(e) Reap branch** — replace lines 674-683 of `clean_issue_downloads` (the dry-run `continue` + the `try: shutil.rmtree(...)`) with disposition-aware logic. | Data root ITSELF a symlink (three-level relocation) | Very low; accepted residual | a wholesale `data/` relocation is a deliberate environment choice; caches resolve at the relocated root for BOTH the plain path and any future disposition — plain-path reap there matches today's semantics; noted in docstring |

| TOCTOU between resolve and rmtree | Very low (single-operator VM; reaps only fire on terminal issues) | operate on the once-resolved path; any race lands in the existing `except OSError → failed` fail-soft |
| Target-reap crashes midway | Low | target reaped BEFORE link unlink → link survives, next run retries; pinned by test 13 |
| Repeated sidecar rows for a permanently-kept external target (parent-link case re-reported every guard cycle) | Certain, accepted | escalation-style visibility is the point; volume is bounded (one row per kept link per run); `append_disk_guard_event` is fail-soft |
| `bytes_freed` counts data-disk bytes on the boot-disk pass | Certain, accepted | reporting only; the guard's exit decision re-reads `disk_used_pct` after cleanup; tier (b) legitimately frees either disk; external-kept rels excluded from `bytes_freed` |

| `rmtree` unlinks-not-descends internal dir symlinks inside the target | N/A (safe by design) | Python's `rmtree` does not follow symlinks within the tree |
| `rglob`-through-symlink Python-version sensitivity (3.12/3.13 pathlib changes) | Low now | test 6 is the canary on a future Python bump; remediation named in TL;DR "what would change my mind" |
| Windows semantics | Irrelevant | VM + pods are Linux-only |
| Merge conflict with #911 | Low | one-line overlap; second-lander rebases (§3.4) |

## 11. Decision Rationale

- **Training hyperparameters:** N/A — no model training in this task type.
- **Managed-root constant = env `EPS_VM_DATA_DISK_PATH`, default `/mnt/eps-data`.** Source: the repo's own #681 conventions — `scripts/vm_disk_guard.py:66-76` (`DEFAULT_DATA_DISK_PATH = "/mnt/eps-data"` + `data_disk_path()` with the identical blank-env-falls-back parse), `scripts/autonomous_session_watch.py:2170-2176` (same duplicated pattern), `src/explore_persona_space/orchestrate/env.py:106` (`_SHARED_VM_DATA_DISK = "/mnt/eps-data"`), and CLAUDE.md § Disk hygiene ("env `EPS_VM_DATA_DISK_PATH`"). Defined IN `clean_experiment_downloads.py` because `vm_disk_guard.py` imports FROM it (a reverse import would cycle), and per-consumer duplication of this constant is the established house pattern. Alternatives rejected: (i) the narrower live prefix `/mnt/eps-data/<user>/eps-data/` — no repo constant exists for it, and the mount root is the principled #681 boundary; (ii) importing `orchestrate.env._SHARED_VM_DATA_DISK` — private and not env-overridable, so tests could not redirect it.
- **Owning-issue component check on the resolved target.** Source: the exact-N-boundary matching already used for discovery (`issue_data_dirs`, `clean_experiment_downloads.py:227-253`) and the janitors' uniform fail-toward-keep design (all three existing gates).
- **Cache-shape predicate: `target.is_dir() and target.name == cache_dir.name` (MF1).** Source: round-1 critic ensemble (Methodology Claude+Codex Must-Fix, Alternatives Claude Must-Fix); the exact-name form is the strictest of the two proposed variants (exact-name vs `fnmatch` against `CACHE_DIR_GLOBS`) and is zero-cost on the live name-preserving relocation (`readlink` verified `hf_dl→hf_dl`, `g1_dl→g1_dl`). A renamed relocation (`hf_dl→hf_dl_old`) is external-kept — the safe direction; if that pattern ever becomes real, widening to the fnmatch form is a one-line, test-covered change.
- **Parent-symlink detection: `cache_dir.parent.is_symlink()` (MF2).** Source: round-1 Alternatives Codex Must-Fix. The canonical discovery layout is exactly two levels below a data root (`issue_data_dirs` → `CACHE_DIR_GLOBS`), so checking the two components covers every in-tree link; a symlinked data root is the accepted wholesale-relocation residual (§7). Never unlinking a parent link follows from shared ownership (sibling caches + non-cache entries resolve through it).
- **Reap-the-target (vs unlink-only).** Source: `run_guard` docstring, `scripts/vm_disk_guard.py:563-572` (tier (b) "reaps a TERMINAL issue's re-downloadable cache on EITHER disk") + CLAUDE.md § Disk hygiene (#681: recovery is resize/raise-cap for ACTIVE data; a TERMINAL issue's re-downloadable cache is the designed reclaim target). Unlink-only would orphan unreachable data-disk bytes (§2).
- **Target-before-link deletion order.** Source: crash-safety reasoning in §3.1(e) — link survival preserves re-discoverability; pinned by test 13.
