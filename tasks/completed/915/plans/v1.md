## 1. Goal, requirement, acceptance criteria

**Goal:** Handle symlinked per-issue cache dirs in the janitors: unlink the symlink and reap the resolved target only when it resolves inside the managed eps-data cache root, instead of failing `rmtree` on the link.

**Requirement:** `shutil.rmtree` refuses symlinks by design (verified live on Python 3.11.15: `OSError: Cannot call rmtree on a symbolic link`). The #681-era interim relocation pattern (`data/issue_<N>/hf_dl → /mnt/eps-data/.../issue_<N>/hf_dl`, live today for #761) therefore makes every janitor reap FAIL on the *healthiest* configuration (zero boot-disk bytes at stake): `clean_experiment_downloads.py <N> --apply` exits 2 (`main()` line 789: `return 2 if res.failed else 0`), and `vm_disk_guard.py --apply` reports `issue 761: FAILED to remove ...` and — because nothing was freed on a 97%-full disk — exits 2 via its `still_over` check (line 810), masking real failures.

**Acceptance criteria:**
1. All new tests pass; the existing `tests/test_vm_disk_guard.py` (35 tests) + `tests/test_clean_experiment_downloads_{parity,active_consumer,pod_side_short_circuit}.py` suites pass unmodified.
2. Live acceptance command: `uv run python scripts/clean_experiment_downloads.py 761 --apply` reaps both symlinked caches — output shows `removed 2 cache dir(s)`, `failed 0`, **exit 0**; afterwards `data/issue_761/` holds no `hf_dl`/`g*_dl` entries and `/mnt/eps-data/thomasjiralerspong/eps-data/issue_761/{g1_dl,hf_dl}` are gone (#761 is `awaiting_promotion` ∈ `TERMINAL_CACHE_REAP_STATUSES`, so the reap is legitimate; if the active-consumer gate SKIPs instead, that is a correct keep, not a failure — re-check after the consumer finishes).
3. A follow-up `uv run python scripts/vm_disk_guard.py` (report-only) shows no `issue 761: FAILED to remove` detail row. (The guard's exit code remains `still_over`-driven — it may legitimately stay 2 if `/` remains >85% for unrelated reasons; the fix's contract is *no FAILED rows on symlinked caches*, not an unconditional exit 0.)
4. `uv run ruff check scripts/clean_experiment_downloads.py scripts/vm_disk_guard.py tests/test_clean_experiment_downloads_symlinks.py` and `uv run python scripts/workflow_lint.py` pass.

## 2. Method delta (what differs from current behavior)

| Case | Current behavior | New behavior |
|---|---|---|
| Cache dir is a symlink → dir inside managed root, naming the owning issue | `rmtree(link)` raises → `failed`, exit 2 | rmtree the resolved target, then unlink the link → `removed`, bytes counted |
| Cache dir is a symlink → anywhere else (outside root, root itself, or inside root but naming a different issue) | same failure | unlink the link only; target KEPT; recorded in new `CleanResult.symlink_external_kept` + stderr note + sidecar event `symlink-external-target-kept`; NOT counted in `removed`/`bytes_freed` |
| Dangling symlink named `hf_dl`/`g*_dl` | invisible (discovery filters `is_dir()`, which follows and returns False) — left forever | discovered, unlinked → `removed`, size 0 |
| Symlink → a file inside managed root naming the issue | invisible (same reason) | target file unlinked, link unlinked → `removed` |
| Dry-run on any symlink case | symlink-to-dir counted as plain `would remove`; dangling invisible | disposition-aware report: managed/dangling → `removed` (would remove), external → `symlink_external_kept` (would unlink, keep target); `CleanResult.symlink_targets` maps rel → resolved target in both modes |
| Real dirs (incl. real cache dirs reached through a symlinked *parent* `issue_<N>` dir) | works | unchanged |
| vm_disk_guard tier (b) | `FAILED to remove` row per symlinked cache | no FAILED row; new detail row for external-kept links; everything else via unchanged delegation |

Deliberately unchanged: `_dir_size_bytes` (follows the link; for a managed reap the sized bytes ARE what is freed — on the data disk, which is exactly tier (b)'s documented contract of reaping "on EITHER disk", `vm_disk_guard.py:568-571`); both reap gates (verified to work through symlinks — gate 1 is issue-number-keyed, gate 2's `rglob` traverses the target); the exit-code semantics of both CLIs.

**Why reap the target at all (brief item d):** tier (b) is "the ONE data-disk-appropriate arm: it reaps a TERMINAL issue's re-downloadable `hf_dl`/`g*_dl` cache on EITHER disk and ESCALATES (never deletes) an ACTIVE task's cache" (`run_guard` docstring, `scripts/vm_disk_guard.py:568-571`; same contract in CLAUDE.md § Disk hygiene). The escalate-only restriction applies to the `/`-rooted tiers (a)/(c) on the data-disk pass, not to tier (b). A terminal issue's relocated re-downloadable cache is precisely what the #681 quota design expects to reclaim. Unlinking only the symlink and stranding the target would leave unreferenced data-disk bytes that no janitor could ever find again (discovery walks `data/`, and the pointer would be gone) — the worst of both worlds.

### 3.1 `scripts/clean_experiment_downloads.py` (primary surface, ~40 lines)

**(a) Managed-root constant + helper** (near `HF_DATA_REPO_DEFAULT`, mirroring `vm_disk_guard.data_disk_path()` at `vm_disk_guard.py:66-76`):

```python
# The #681 managed data-disk mount that holds relocated per-issue caches.
# Mirrors vm_disk_guard.DEFAULT_DATA_DISK_PATH / data_disk_path() (that module
# imports FROM this one, so the constant cannot live there without a cycle).
DATA_DISK_ROOT_DEFAULT = "/mnt/eps-data"

def data_disk_root() -> Path:
    """Managed data-disk root (env ``EPS_VM_DATA_DISK_PATH``; blank -> default)."""
    raw = os.environ.get("EPS_VM_DATA_DISK_PATH", "").strip()
    return Path(raw or DATA_DISK_ROOT_DEFAULT)
```

**(b) Issue-naming + containment predicate** (module-private):

```python
def _path_component_names_issue(rel: Path, issue_n: int) -> bool:
    """True iff some path component is issue_<n>/issue<n> (or an
    issue_<n>_<slug> prefix form) — the same exact-N-boundary rules as
    issue_data_dirs (issue_65 never matches issue_658)."""
    n = str(issue_n)
    for comp in rel.parts:
        if comp in (f"issue_{n}", f"issue{n}"):
            return True
        if comp.startswith((f"issue_{n}_", f"issue{n}_")):
            return True
    return False

def _managed_symlink_target(cache_dir: Path, issue_n: int) -> Path | None:
    """Fully-resolved target iff STRICTLY inside data_disk_root() AND a path
    component names issue_n; else None (fail-toward-keep). realpath on BOTH
    sides defeats nested-link / relative-link escapes."""
    target = Path(os.path.realpath(cache_dir))
    root = Path(os.path.realpath(data_disk_root()))
    if target == root or not target.is_relative_to(root):
        return None
    if not _path_component_names_issue(target.relative_to(root), issue_n):
        return None
    return target
```

The issue-component requirement is the cheap defense against a hand-made alias into ANOTHER issue's (or shared) data-disk state: `issue_761`'s link to `.../issue_779/...` or `.../issue779-grid/...` is treated as external → target kept, link unlinked, sidecar-escalated.

**(c) `CleanResult` extension** (two fields; existing fields + `bytes_freed`/`total_discovered_bytes` semantics untouched):

```python
# rel -> fully-resolved symlink target ("" for dangling); populated in BOTH modes.
symlink_targets: dict[str, str] = field(default_factory=dict)
# (rel, target): symlink (would be) unlinked, target NOT ours to reap — KEPT.
symlink_external_kept: list[tuple[str, str]] = field(default_factory=list)
```

External-kept rels are deliberately NOT in `removed`, so `bytes_freed` (which sums `sizes_bytes` over `removed`, where sizing followed the link to a target we did NOT delete) never overstates. They stay in `sizes_bytes`, so `total_discovered_bytes` (the escalation sizing) still sees the footprint.

```python

                res.removed.append(rel)                # would-remove (managed or dangling)
                continue

                continue

        if not apply:
```

## 7. Risks + failure modes

| Risk | Likelihood | Mitigation |
|---|---|---|
| Symlink target shared by / aliased to another issue's data | Low | `_path_component_names_issue` requires the target to name the OWNING issue; anything else → external-kept + sidecar escalation (fail-toward-keep) |
| Nested-link / relative-link escape past the root check | Low | `os.path.realpath` on BOTH target and root before `is_relative_to`; strict-inside (target ≠ root) |
| TOCTOU between resolve and rmtree | Very low (single-operator VM; reaps only fire on terminal issues) | operate on the once-resolved path; any race lands in the existing `except OSError → failed` fail-soft |
| Target-reap crashes midway | Low | target reaped BEFORE link unlink → link survives, next run retries; partial target still discoverable |
| `bytes_freed` counts data-disk bytes on the boot-disk pass | Certain, accepted | reporting only; the guard's exit decision re-reads `disk_used_pct` after cleanup; tier (b) legitimately frees either disk (its documented contract); external-kept rels excluded from `bytes_freed` |
| Active-cache escalation bands (boot-disk pressure) sized from a relocated cache's data-disk bytes | Low impact | pre-existing behavior (`_dir_size_bytes` already followed links); escalation is warn-only, never deletes; noted, not changed |
| `rmtree` unlinks-not-descends internal dir symlinks inside the target | N/A (safe by design) | Python's `rmtree` does not follow symlinks within the tree |
| Windows semantics | Irrelevant | VM + pods are Linux-only |
| Merge conflict with #911 | Low | one-line overlap; second-lander rebases (§3.4) |

- **Managed-root constant = env `EPS_VM_DATA_DISK_PATH`, default `/mnt/eps-data`.** Source: the repo's own #681 conventions — `scripts/vm_disk_guard.py:66-76` (`DEFAULT_DATA_DISK_PATH = "/mnt/eps-data"` + `data_disk_path()` with the identical blank-env-falls-back parse), `scripts/autonomous_session_watch.py:2170-2176` (same duplicated pattern), `src/explore_persona_space/orchestrate/env.py:108` (`_SHARED_VM_DATA_DISK = "/mnt/eps-data"`), and CLAUDE.md § Disk hygiene ("env `EPS_VM_DATA_DISK_PATH`"). Defined IN `clean_experiment_downloads.py` because `vm_disk_guard.py` imports FROM it (a reverse import would cycle), and per-consumer duplication of this constant is the established house pattern. Alternatives rejected: (i) the narrower live prefix `/mnt/eps-data/<user>/eps-data/` — no repo constant exists for it, and the mount root is the principled #681 boundary; (ii) importing `orchestrate.env._SHARED_VM_DATA_DISK` — private and not env-overridable, so tests could not redirect it.
- **Owning-issue component check on the resolved target.** Source: the exact-N-boundary matching already used for discovery (`issue_data_dirs`, `clean_experiment_downloads.py:227-253`) and the janitors' uniform fail-toward-keep design (all three existing gates). - **Reap-the-target (vs unlink-only).** Source: `run_guard` docstring, `scripts/vm_disk_guard.py:563-572` (tier (b) "reaps a TERMINAL issue's re-downloadable cache on EITHER disk") + CLAUDE.md § Disk hygiene (#681: recovery is resize/raise-cap for ACTIVE data; a TERMINAL issue's re-downloadable cache is the designed reclaim target). Unlink-only would orphan unreachable data-disk bytes (§2).
- **Target-before-link deletion order.** Source: crash-safety reasoning in §3.1(e) — link survival preserves re-discoverability; no literature needed.
