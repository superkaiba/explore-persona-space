### Item A — check 60 `check_figure_sidecar_text_coverage` (WARN)

`scripts/verify_task_body.py`

Modelled on `check_figure_sidecar_coverage` (~L14018): same
`_figure_scan_section` / `_IMAGE_RE` harvest, same `_RAW_GITHUB_FIGURE_RE` +
`_THIS_REPO_SLUG` scope gate, same `_git_object_exists(png) != "pass" ->
continue` deference to check 22. Registered in `CHECKS` (~L19148) beside
check 41; doc block added to the header catalogue beside check 41's.

**Predicate (Must-Fix 1 — this is the corrected form).** Read the sidecar via
`_read_figure_meta_json`, then flag when the RENDERED-TEXT BLOCK is absent or
empty:

```python
text_block = meta.get("text") if isinstance(meta, dict) else None
textless = not text_block or not _iter_meta_label_values(text_block)
```

v2 keyed this on `_iter_meta_label_values(meta)` over the WHOLE sidecar. That
was wrong and would have made check 60 silent on the exact incident set:
`inputs` is NOT in `_META_PROVENANCE_KEYS` (L9424-9445), so #2254's
`{"figure", "git_commit", "git_dirty", "inputs": [...]}` sidecars yield the
input-path strings and read as text-bearing. `git_dirty_paths` /
`git_argv0_state` (`orchestrate/provenance.py` L347-355) are unpruned too, so
the hole was not #2254-specific. Keying on `text` also makes the check and the
posture measurement in §4 the SAME instrument, which v2 wrongly split.

Deference branches (no double-reporting — Must-Fix 3 of the critic's set):
- sidecar ABSENT -> `continue` (checks 41 / 57 own it)
- sidecar present but UNPARSABLE -> treat as TEXTLESS and report
  (Consider 6: `_read_figure_meta_json` returns None for missing and
  unparsable alike, and no other check reports present-but-unparsable, so
  deferring would preserve the zero-coverage/zero-report property this task
  exists to remove). Distinguish absent from unparsable with a
  `_git_object_exists` probe on the sidecar path before reading.
- present + parsable + text-bearing -> pass

Report shape mirrors 41's: `is_warn=True`, `passed=True`, basenames first 3
+ count, remedy naming `savefig_paper` (`embed_text` defaults True). NO-OP
PASS branches identical to 41's.

### Item B — ONE new token class, check-28-local

`scripts/verify_task_body.py`

**Class (h) — `role@span` slug.**

```python
_ROLE_AT_SPAN_RE = re.compile(r"\b[a-z][a-z0-9]{1,11}@[a-z][a-z0-9]{1,15}\b(?!\.[a-z])")
def _is_role_at_span_token(tok: str) -> bool: ...   # membership, re-derivable from text
def _role_at_span_hits(text: str) -> list[str]: ... # regex + per-word path exemption
```

**Placement (Must-Fix 2).** The helper is invoked from **check 28's loop
only** (~L10524), NOT from `_opaque_code_tokens`. Reason: `_opaque_code_tokens`
has TWO consumers — check 28 (WARN, L10524) and **check 57 Leg A (FAIL, v4,
not date-gated, L14271, calibrated at "measured 0 corpus hits" under the
current seven classes)**. Joining the shared tuple, as v2 proposed, would turn
an unbackticked `rb@answer` in a sidecar-less Results figure caption into a
hard promote-time FAIL — violating AC5, silently touching a check §9 fences
off, and punishing the very caption-decoding remediation this plan endorses
for check 28. Keeping the class check-28-local leaves `_opaque_code_tokens`
byte-stable (AC3).

Matches `pre@context`, `ctxext@context`, `rb@answer`. Non-matching:
`@L12` layer pins (class (a)'s domain; that RHS is uppercase-initial and this
regex requires lowercase-initial, so no double-report), bare `@handle` (no
LHS), mathtext (backslash arm of `_is_path_like_word`), and — via the added
`(?!\.[a-z])` lookahead — email-shaped `user@example.com`. **Correction
(Should-Fix 3):** v2 claimed emails were already excluded by
`_is_path_like_word`'s extension-tail arm. That was mechanically wrong —
`_is_path_like_word` returns False for any slash-free word (L10218-10220), so
the arm is unreachable without a `/`. The lookahead is what actually excludes
them.

**Class (i) — DROPPED (kill criterion K1 fired).** v2 proposed
`_SHORT_ARM_CODE_RE = r"\A[a-z]{1,3}\d[a-z]?\Z"` full-string-matched and gated
on >=2 distinct tokens per figure. The critic ran K1's instrument — the full
tracked-sidecar corpus sweep — and measured **98 figures across 9 issue dirs**
firing at the >=2 gate, dominated by legitimate per-index tick sets: `f1..f6`
(50 figures, issue_666), `dec1..dec8` (31, issue_1415), plus `q0..q7`,
`c2`/`c8`, `d1`/`d3`/`d5`. A >=3 gate does not help — the dominant clusters
carry 6-8 distinct tokens. That is 98 false positives against the ONE incident
figure the class was added for, and fold/decile/quantile index ticks are
exactly the "terse but legitimate" labels the task body says not to block.
K1 is pre-registered for precisely this evidence, so it is exercised here
rather than at implementation time. The incident figure is still named:
class (h) fires on it via `pre@context` / `ctxext@context` / `rb@answer`.
(Related, Consider 7: `a0` may be the only class-(i)-shaped label on
`per_question_dots.png`, in which case the >=2 gate would never have reported
it anyway — the class could not have reproduced the incident on its own.)

**Caption suppression (#1988).** Extend `_suppress_caption_decoded_slugs` to
class (h) — a caption spelling out `rb@answer` has decoded it for the reader,
the identical rationale #1988 recorded for arm slugs. Predicate becomes
`_is_arm_slug_token(t) or _is_role_at_span_token(t)`.
