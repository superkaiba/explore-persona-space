## 3. Why option (a), and the trade-off

- **(a) CREATE (transplant from `origin/issue-722`):** the rule's whole intent
  is a REUSABLE helper at that path. The file already exists, byte-identical
  across two branches, with its own exactness oracle, and already passed #722's
  planner→critic→code-review→test-verdict pipeline. Transplanting it verbatim is
  strictly lower-risk than re-factoring fresh from `_fit_mlp_ensemble_loco`
  (verbatim copy cannot introduce numerics drift), and the
  `assert_matches_reference()` + `_assert_mlp_exactness()` oracles give a
  concrete regression test. **Chosen.**
- **(b) REPOINT to the in-script function:** the honest stopgap if the file did
  not exist or transplant were unsafe. It would point agents at
  `scripts/issue658_fit_predictors.py::_fit_mlp_ensemble_loco` — but that is the
  per-CALL ensemble fit, NOT the across-(layers × variants × dims) reusable
  batched helper the rule describes; it would leave the rule's "reusable helper"
  promise unmet and force the next sweep to re-write the vectorization. Rejected
  because the better artifact already exists and lands safely.

Trade-off in one line: (a) costs one verbatim file transplant + a
two-oracle smoke; (b) is a doc-only edit but permanently downgrades the rule
from "import this helper" to "go read this per-call function and re-vectorize
yourself." Since the helper already exists and tests clean, (a) wins outright.
