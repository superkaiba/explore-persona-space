## 3. Method delta (what differs from the current recipe)

1. **Materialize-then-check** at both sites: the git producer writes to a fixed per-issue temp file (`/tmp/issue-<N>-postmerge-lstree.txt`, `/tmp/issue-<N>-guard1-tasks-diff.txt` — matching the file's `/tmp/issue-<N>-own-diff.txt` / `-additive-files.txt` naming convention; idempotent overwrite on re-run) and its exit code is checked explicitly. **Deviation from the task-body sketch, justified:** the sketch used `mktemp` + `exit 1`; I substitute the fixed `/tmp/issue-<N>-*` naming (in-file convention, and `mktemp` leaks unnamed files across re-runs) and `false`-routing instead of `exit 1` (the brief's constraint: a bare `exit 1` can kill the orchestrator's whole shell silently; `false` as the terminal command of the taken branch makes the fenced block exit non-zero — the exact SURGICAL-ABORT convention).
2. **Terminal failure arms via a single `if/elif` chain.** These fenced blocks run without `set -e`, so a `false` inside a non-terminal `if` would NOT halt execution — the subsequent `mapfile` would read the empty/partial temp file and reproduce the fail-open with an echo attached. The only fail-closed single-block shape is: failure arms and the work arm are branches of ONE `if/elif/fi` chain that is the block's last statement. The work arm's condition is a two-command list (`mapfile ...; [ "${#X[@]}" -gt 0 ]` — bash takes the LAST command's exit status), which has in-file precedent in the lint-gate's `if ! git ...; then ... elif [ -n "$(grep ...)" ]; then` chain shape; an inline comment explains it.
3. **Fetch gets the same treatment at Site A (decided YES, justification):** a failed `git fetch origin main --quiet` leaves the local `origin/main` ref at its PRE-merge state — and the duplicate folder this guard hunts is imported by the merge that JUST landed, so a stale ref is not a "lesser recent-miss": it is the guard's PRIMARY blind spot (the push-verification fetch at ~9630 only runs when `DUPES` is already non-empty, so it cannot rescue a stale-ref empty read). Cost: a transient network blip now fails the guard loudly instead of silently no-oping — acceptable, since Step 10d just completed network operations and the `epm:merge-failed` handling (post marker, surface one line, CONTINUE) bounds the impact.
4. **Empty-`CANON` guard at Site A (small rider, same failure class):** if `task.py find <N>` or `realpath` fails, `CANON=""` — and `grep -v -F -x ""` then removes nothing, so ALL of task `<N>`'s folders (including the CANONICAL one) enter `DUPES` and the guard would `git rm` the canonical folder from `main`. That is the same "failed producer read as benign input" class with a strictly worse (destructive) outcome, in the same fence, fixed by one 4-line arm (`[ -z "$CANON" ]` → echo + `false`). Scoped in deliberately; named here so the critic sees it is a deliberate rider, not scope drift. (Ordering note: `CANON` derivation moves above the chain — it reads only the local filesystem, so the fetch→CANON order swap is behavior-neutral.)
5. **Site 8654 (`OWN_NS` fast-path mapfile): NO fix, by design.** A failed diff there empties the list, and the `-ge 1` lower bound then forces `FAST_PATH=no` → the ordinary (safe, more conservative) merge path. It fails SAFE. Lines 8801/8807/9424 read local `cut` output — benign. No other workflow-surface hits (multiline grep across `.claude/`, this session).
6. **Two one-sentence prose updates** so surrounding text stays accurate (§4).

       if git -C "$WT" cat-file -e "origin/main:$p" 2>/dev/null; then
         FOREIGN_ON_MAIN+=("$p")
       else
         FOREIGN_BRANCH_ONLY+=("$p")
       fi

       && git -C "$WT" checkout origin/main -- "${FOREIGN_ON_MAIN[@]}"
     [ "${#FOREIGN_BRANCH_ONLY[@]}" -gt 0 ] \
       && git -C "$WT" rm --cached -f --ignore-unmatch -- "${FOREIGN_BRANCH_ONLY[@]}"
