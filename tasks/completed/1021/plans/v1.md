# Plan — task #1021: crash-fix relaunch flips stale `blocked` → `running`; watcher flag-only backstop

`architectural: false`

---

## 1. Goal

When a crash-fix relaunch succeeds (a fresh `epm:run-launched` posted) on a task whose status is still `blocked` (left by an earlier failed round), the orchestrator flips the status back to `running` in the same turn — so the dashboard/watcher never show a healthy multi-hour run as blocked (#742 ran healthy from 2026-07-01T08:32Z while its folder said `blocked` since 2026-06-30T23:27:59Z; the status was only fixed 2026-07-02T18:36:38Z after the user asked). As backstop, a new watcher pass FLAGS — never auto-flips — any `blocked` task whose events show an `epm:run-launched` newer than the transition into `blocked` plus fresh real progress, via a deduped task marker + sidecar row + Telegram digest line, mirroring the conservative pod-safety alert posture (false alert cheap, false flip dangerous).

## 2. Prior work / existing mechanisms — and why they don't cover this

All verified by reading `scripts/autonomous_session_watch.py` (17,515 lines) at the cited lines:

- **Crash-recovery `decide()` PARK set** (line 482: `PARK = {"proposed", "plan_pending", "blocked", "on_hold"}`): every `blocked` task is "keep, never respawn" — deliberately inert on blocked tasks; it cannot notice a live run.
- **Capacity-retry pass** (`decide_capacity_retry` line 11991, `capacity_retry_pass` line 12196): the ONLY pass that acts on `blocked`, and only the narrow `failure_class: infra` + `reason ∈ TRANSIENT_CAPACITY_REASONS` (`{no_compute_available}`) subclass — it RE-DRIVES a session, it never reconciles a status against a live run. #742's blocks were ENOSPC/earlyoom/API-404 reasons, outside the allowlist.
- **Pod-safety pass** (`decide_pod_safety` line 1575): `blocked` pods are KEPT (alert-only) — it protects pods FROM stops; it has no "blocked but alive" flag.
- **Session-reconcile / gate-push passes**: reconcile fires only on parked/terminal statuses (`blocked` explicitly excluded); gate-push alerts on transitions INTO `blocked`, not on a run continuing past one.
- **The follow-up-liveness predicate already exists in the right shape**: `_task_followup_active` (line 3998) compares `_latest_event_ts(events, _POD_FOLLOWUP_SIGNAL_KINDS)` against the latest done-transition ts (`_DONE_TRANSITION_KINDS`, line 3952 — its docstring establishes that when the current status is X, the latest `epm:status-changed` IS the transition into X). The new predicate is the `blocked`-status sibling of this comparison.
- **Crash-fix recipe** (`.claude/rules/crash-fix-rounds.md`): zero mentions of `blocked`. Its scope guard (§ "Crash-fix rounds: scope guard", lines 163-226) makes `epm:status-changed` and `epm:run-launched` ORCHESTRATOR-owned — so the flip belongs in SKILL.md orchestrator prose, and the rule file needs only a cross-reference so implementers know the flip is not theirs.
- **SKILL.md relaunch contract** (line 3737): "**Any relaunch must re-post `epm:run-launched`.**" — the canonical paragraph every relaunch path (pod-side hot-fix, VM-side detached-phase relaunch, GCP) reads. It mandates the marker but says nothing about status. #742's 4th-7th launches all posted `epm:run-launched` here and none flipped the status.
- **`epm:run-launched` posting split**: the experimenter posts the marker and exits (`experimenter.md` line 873: "Post `epm:run-launched` and EXIT"); it never mutates status. VM-side relaunches (#742's case) are posted by the orchestrator itself. Either way the ORCHESTRATOR is the actor that can flip.

Grounding of the #742 timeline (read from `task.py view 742 --json` events): `epm:status-changed` 2026-06-30T23:27:59Z ("4 consecutive production launches failed…") → `epm:run-launched` 2026-07-01T08:32:50Z (4TH launch), 2026-07-02T07:01:01Z (5TH launch) → `epm:status-changed` 2026-07-02T18:36:38Z. Both signals of the proposed predicate (launch newer than block; ongoing progress ticks — cf. today's "[poll-tick:bg] 7th launch alive" `epm:progress` commits) were present the whole window.

**Pure predicate** (near `decide_capacity_retry`, ~line 11990):

```python
def decide_stale_blocked_flag(
    status: str | None,
    run_launched_ts: float | None,
    blocked_since_ts: float | None,
    progress_ts: float | None,
    now: float,
    *,
    fresh_window_s: float = STALE_BLOCKED_PROGRESS_FRESH_S_DEFAULT,
) -> bool:
    """True iff a `blocked` task shows a live healthy run: an
    epm:run-launched NEWER than the transition into blocked, plus real
    (non-watcher, non-deliberate-stop) progress within fresh_window_s.
    EVERY missing signal returns False (fail toward silence)."""
    return (
        status == "blocked"
        and run_launched_ts is not None
        and blocked_since_ts is not None
        and run_launched_ts > blocked_since_ts
        and progress_ts is not None
        and (now - progress_ts) <= fresh_window_s
    )
```

Signal notes: `blocked_since_ts` = `_latest_event_ts(events, frozenset({"epm:status-changed"}))` — valid as "transition into blocked" because the caller has verified current status IS `blocked` (the same argument the `_DONE_TRANSITION_KINDS` docstring at line 3948-3951 makes). `run_launched_ts` = `_latest_event_ts(events, frozenset({_RUN_LAUNCHED_KIND}))` (alias at line 3977). `progress_ts` = `_latest_progress_ts(events)` (line 3737) — already excludes watcher sentinels and deliberate-stop records (#990), and already counts the opt-in `[long-phase-heartbeat]` prefix as real progress, so long batch-judge phases don't under-flag. The "launch newer than block" ordering is what keeps a deliberately-blocked task quiet: the normal order is fail → block (launch older than block → skip); only a launch AFTER the block — the exact #742 anomaly — flags. The task-brief's "alive workload pid" signal is deliberately NOT used: pod-side pids are not probeable from the VM, and fresh `epm:progress` poll ticks are the poller's own liveness digest of that pid.

## 5. Risks

| Risk | Assessment / mitigation |
|---|---|
| Orchestrator flip races a genuine re-block | The flip is a same-turn serial action after the orchestrator's OWN relaunch (guard (b) in the prose); a subsequent failure re-blocks through the normal path. The watcher never flips, so no cross-process race exists. |
| Watcher false positive: task blocked on purpose with a `keep-running` pod still posting progress | The launch-newer-than-block ordering gates this: a deliberate block posted after the failure has launch < block → skip. Only a launch posted AFTER the block flags — which is a genuine anomaly worth one deduped alert even when semi-intentional. Flag-only = false alert costs one digest line. |
| Marker-freshness threshold (2h) misses long silent phases | Detached VM phases post periodic liveness `epm:progress` per the SKILL.md successor rule, and `[long-phase-heartbeat]` notes count as progress; a too-tight window UNDER-flags (missed alert, status quo), never mis-flags. Env-tunable (`EPM_STALE_BLOCKED_PROGRESS_FRESH_S`). |
| `blocked_since_ts` wrong when the block skipped `epm:status-changed` (hand `git mv`) | `task.py set-status` always posts the marker; a hand-move is non-canonical. Missing marker → predicate returns False (fail toward silence). |
| Flag note resets staleness clocks / feeds `_latest_progress_ts` | Prevented by sentinel membership in `_WATCHER_NOTE_SENTINELS` + pinned by test 10. |
| Alert spam across ticks | Deduped per (issue, `run_launched_ts`) in the state file; a new launch = a new episode = one new alert. State reaped only at `completed`/`archived` (never mid-episode). |
| Capacity-retry re-drive lands a relaunch before the re-driven session flips status | One deduped watcher flag may fire in that window — harmless; the SKILL.md rule then flips it and the episode ends. |
