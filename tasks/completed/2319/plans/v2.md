# Plan — issue #2319: line-anchored offender extraction closes the step9c snippet false-BLOCK residual

<!-- kind: infra -->

### 0.0 TL;DR (plain English — the user reads this first)

`step9c_baseline.py compare` is the gate every session's Step 9c runs. For five registered whole-repo "scan" tests (the ones that walk the repo and list offending files), when the test is red on BOTH the branch and pristine main, the gate compares the *sets of offending file paths* instead of the test's pass/fail, so a branch is blocked only for offenders it actually added. The bug: the extractor grabs **every** path-shaped token on a violation line — including tokens sitting inside the *source snippet* the line quotes. Three of the five tests quote a snippet. So if a branch edits an already-offending line and the new snippet happens to mention some tracked file (say `scripts/task.py`), that file looks like a brand-new offender and the gate exits 1, naming a file that never offended. That is a false hard block on the gate that adjudicates the whole fleet.

Fix: extract the offender path **anchored at the start of the line** (after indentation and an optional `- ` bullet) instead of anywhere on the line. All five tests put the offender path first, so nothing real is lost; a snippet token is never first, so the false block disappears. Two follow-ons: the extraction's own test currently *asserts the buggy behavior*, so that expectation is corrected; and a dead test-harness knob (`paired_failure_texts`) is put to work pinning a design property #2316 wrote down in a comment but never tested.

### 0. Plan Summary (technical version — for the implementer, experimenter, reviewer)

Replace the token-scan in `extract_violation_paths` (`scripts/step9c_baseline.py`) with a per-line **anchored** match; add a fifth registry-curation criterion (d) making "offender rows lead with the path" an add-time check; pin each of the five registered members' row grammars in a table-driven test; correct the one T10 expectation that encodes the defect; add the criterion-1 regression test (already-red file, branch-side snippet embeds a token absent on pristine ⇒ `pre-existing`, not NEW); and exercise the dead `paired_failure_texts` knob as the counterfactual instrument of a new bypass pin. No behavior change to any refusal arm, to `base_identical` suppression, to the parse-fail arm, or to the exit arithmetic.

### 3. Hypothesis

The five registered members' offender rows all begin with the offender path (after leading whitespace and an optional `- ` bullet), and every snippet-borne token appears strictly later on its line. Therefore a line-anchored single-capture extraction returns exactly today's offender set MINUS the snippet-borne tokens, for every member — closing the false block with no loss of real offenders.

Falsifier: any member whose offender row does not lead with the path, or whose snippet can begin a line. Both are checked by reading the source (§12 A2-A6), not assumed.

Three findings decide the fix:

1. **All five lead with the offender path.** Option 1 from the task body (first-path-token-per-line) is therefore VALID today, and option 2 (per-member row-prefix regexes) is not required to avoid a fail-open at the present registry.
2. **Three of five (M2/M4/M5) carry a source snippet**; every snippet is a single `.strip()`ed source line, so no offender row spans lines and line structure is a sound row boundary.
3. **Anchoring beats first-token-per-line** and is the option-3 branch this plan takes. First-token-per-line would still lift `scripts/task.py` out of M4's mid-line header (`:607`, `f"\n{len(all_offences)} file(s) shell out to scripts/task.py "`) — harmless because symmetric, but it keeps prose in the audit rows. Decisively, the two options differ in their FUTURE failure mode: a member whose grammar does not lead with the path yields, under anchoring, **zero** matches — which routes to the EXISTING loud empty-set arm (`SCAN-SETDIFF-UNPARSEABLE` warn + `parse-failed` row + strip = pre-#2316 behavior plus escalation), NOT the silent offender-drop the task body warns about. Under first-token-per-line the same member yields a partial set (its prose tokens), which IS a silent drop.

Residual, closed explicitly and not left implicit: a FUTURE member with **mixed** row grammar (some rows leading with the path, some not) would silently drop the non-leading rows. Closed by D2 (curation criterion) + D3 (per-member grammar pin), and stated in the extractor docstring.

#### D1 — line-anchored offender extraction (`scripts/step9c_baseline.py`)

Replace `_VIOLATION_PATH_RE` and the body of `extract_violation_paths`:

```python
# Violation-path token, ANCHORED at the row start (#2319): a repo-root-relative
# path under a top-level tracked dir, ending in an extension, appearing at the
# START of a violation row — after leading whitespace, pytest's optional "E "
# element-text gutter, and an optional "- "/"* " bullet. Every
# VIOLATION_SET_SCAN_NODES member's offender rows LEAD with the offender path
# (registry curation criterion (d)); a path token appearing LATER on a row is
# snippet or prose, never an offender. #2316 extracted every token per line,
# so a branch-side snippet embedding a tracked-path token absent on pristine
# manufactured a NEW-violation verdict naming a NON-offender (false BLOCK on
# the gate that adjudicates every session's Step 9c — #1388 blast radius).
# Grain is still the FILE: a `path:line` token extracts the path only (line
# numbers drift under unrelated same-file edits and would manufacture false
# NEW reds).
_VIOLATION_ROW_RE = re.compile(
    r"^[ \t]*(?:E[ \t]+)?(?:[-*][ \t]+)?"
    r"((?:scripts|src|tests|configs|docs)/[\w./-]+\.[A-Za-z0-9_]+)"
)
```

```python
def extract_violation_paths(text: str) -> frozenset[str]:
    """Extract the offender-path SET from a scan node's failure text (#2316, #2319).

    Rows are matched ANCHORED at the line start (#2319): the offender path is
    the FIRST thing on its row for every registered member (registry curation
    criterion (d)), so a later token on the same row — a quoted source
    SNIPPET, remediation prose — is never mistaken for an offender. #2316
    scanned every token per line, which false-BLOCKED a branch that edited an
    offending line in an ALREADY-red file such that the new snippet embedded a
    tracked-path token absent on pristine.

    Two sanitizers from #2316 are retained, both still load-bearing:

    1. **Introspection-segment strip:** drop every line whose ``lstrip()``-ed
       content starts with ``"assert "`` — pytest's rewritten-assert segment
       (bare-``assert`` members only) always does, in BOTH the junit
       ``message`` attribute and the element text; offender rows never do
       (source-verified for all five members, #2319 §4 audit). Anchoring alone
       already excludes that segment (it starts with ``assert``, not a path),
       so this is now defense in depth against a WRAPPED saferepr whose
       continuation line could begin with a path-shaped fragment.
    2. **Elision-token post-filter:** drop any matched token containing the
       literal ``...`` — saferepr's elision marker; zero tracked paths contain
       it, and a FUTURE such path would be invisible on BOTH sides
       (fail-toward-strip, never a false block).

    Symmetric prose (headers, remediation text) is no longer extracted at all,
    which shrinks the ``pre_existing`` audit rows to genuine offenders. An
    EMPTY result routes to the caller's loud parse-fail arm — never a silent
    strip — and that arm is exactly where a FUTURE member whose rows do not
    lead with the path lands (zero anchored matches ⇒ degrade to today's
    node-grain verdict + escalation, not a silent offender drop). The one
    residual: a member with MIXED row grammar would silently drop its
    non-leading rows — curation criterion (d) forbids registering one.
    """
    out: set[str] = set()
    for line in text.splitlines():
        if line.lstrip().startswith("assert "):
            continue
        m = _VIOLATION_ROW_RE.match(line)
        if m is None:
            continue
        token = m.group(1)
        if "..." not in token:
            out.add(token)
    return frozenset(out)
```

The optional `E[ \t]+` gutter is measured, not speculative: #2316's `_A1_PROBE_TEXT` (the element-text form of the live probe) carries `E   ` on the HEADER line only, with offender rows at deeper plain indentation — so anchoring holds on both junit forms today, and the alternation makes it hold even if a future pytest gutters the row lines too. Admitting the gutter cannot fail-open: a gutter-prefixed non-row line still needs a leading path token to match, and such a line is symmetric prose that cancels in the set difference.
