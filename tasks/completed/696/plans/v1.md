## 1. Goal

Make the branch-freshness check in
`src/explore_persona_space/orchestrate/preflight.py` tolerate a *transient*
`git fetch origin` timeout so a slow-network pod with a verifiably-current
checkout is not falsely reported `ok=false`. The check must still fail loud
when the branch is genuinely behind or when there is no last-known origin
ref to compare against. Net behavior: a transient timeout + current checkout
becomes a WARNING (preflight passes); everything that is a real staleness
risk stays an ERROR.

## 2. Prior work (motivation)

This false-positive surfaced during the **#664 r9 recovery relaunch
(2026-06-28)**: a freshly-bootstrapped RunPod pod with intermittent outbound
HTTPS latency reported `ok=false` with
`"git fetch origin failed (timeout) — cannot verify ..."`, even though a
direct `git fetch origin issue-664 --depth=1` on the same pod completed rc=0
within seconds and `git rev-parse HEAD == origin/issue-664` confirmed the
branch was current. The experimenter had to independently re-verify branch
currency and push through the bogus ERROR — exactly the kind of preflight
false-positive the `--skip-preflight` escape hatch (gotchas.md, #602) exists
to bypass, but here the underlying check is fixable rather than just
bypassable. The branch-aware fetch-as-ERROR semantics were introduced in
**#554** (the file's docstrings and tests all reference it); this change
narrows the ERROR strictly to the unrecoverable case.

The fail-loud ERROR is correct *in general* — a failed fetch means the
branch's own origin ref may be stale, so `behind_own == 0` against a stale
ref proves nothing (`test_feature_branch_fetch_failure_errors`). The fix
does not weaken that; it adds a single recovery path for the one case where
the failure is a *timeout* AND a prior remote-tracking ref already exists
AND the checkout is current against it.

## 3. Design

### 3.1 Exact current behavior (cited)

- **The fetch** happens once in `check_git_status` (lines **339–341**):
  ```python
  fetch_rc, _, fetch_err = _run(
      ["git", "-C", str(project_root), "fetch", "--quiet", "origin"], timeout=15
  )
  fetch_failed = fetch_rc != 0
  ```
  The current short timeout is **15 s**. `_run` (lines 147–157) catches
  `subprocess.TimeoutExpired` and returns `(-1, "", "timeout")` — so a
  timeout is reported as `fetch_rc == -1, fetch_err == "timeout"`, whereas a
  network/auth failure returns a different stderr string (e.g.
  `"fatal: unable to access remote"`). **A timeout is distinguishable from a
  generic fetch failure only by `fetch_err == "timeout"`, not by the
  return code** — both are negative/non-zero. This is the key seam the fix
  keys on.
- `fetch_failed` is passed down to `_check_feature_branch_behind`
  (line 359), which at lines **404–421** currently does, on `fetch_failed`:
  ```python
  if fetch_failed:
      report.add_error(
          f"git fetch origin failed ({fetch_err}) — cannot verify branch "
          f"{branch} is up to date with origin/{branch}."
      )
      report.git_status += ", fetch failed"
      return
  ```
  This unconditional ERROR-and-return is what fires the false positive on a
  timeout.
- The last-known-ref existence probe already exists at lines **429–431**
  (used on the fetch-*success* path):
  ```python
  own_ref_full = f"refs/remotes/origin/{branch}"
  rc_ref, _, _ = _run(
      ["git", "-C", str(project_root), "rev-parse", "--verify", "--quiet", own_ref_full]
  )
  ```
  and `_behind_count(project_root, own_ref_full)` (lines 160–172) returns the
  behind-count against that ref or `None` when it can't be determined.

### 3.2 The change — control flow

Two small edits, both keyed on **timeout specifically** (not any fetch
failure), so non-timeout failures keep the unchanged #554 fail-loud
semantics.

**Edit A — `check_git_status`, retry once on timeout (around lines 339–342).**
Replace the single fetch with: do the fetch at the current 15 s timeout; if
it timed out (`fetch_rc != 0 and fetch_err == "timeout"`), retry the SAME
fetch ONCE at a 60 s timeout. Capture whether the failure was a timeout so it
can be threaded down. Pseudocode:

```python
fetch_rc, _, fetch_err = _run(
    ["git", "-C", str(project_root), "fetch", "--quiet", "origin"], timeout=15
)
if fetch_rc != 0 and fetch_err == "timeout":
    # One longer-timeout retry — a transient slow-network fetch usually
    # completes well within 60s (the #664 r9 pod fetched in seconds via a
    # direct call). Adds at most ~60s to preflight on the slow path.
    fetch_rc, _, fetch_err = _run(
        ["git", "-C", str(project_root), "fetch", "--quiet", "origin"], timeout=60
    )
fetch_failed = fetch_rc != 0
fetch_timed_out = fetch_failed and fetch_err == "timeout"
```

Thread the new `fetch_timed_out` flag into `_check_feature_branch_behind`
(extend its signature: it is called only from `check_git_status` line 359, so
this is a closed change). `_check_main_branch_behind` and
`_check_detached_head_behind` are NOT touched — main already fail-softs to
WARNING on any fetch failure (`test_main_fetch_failure_warns_not_errors`),
and detached HEAD already warns only.

**Edit B — `_check_feature_branch_behind`, downgrade the timeout case
(lines 404–421).** Replace the unconditional `if fetch_failed:` ERROR block
with:

```python
def _check_feature_branch_behind(
    report, project_root, branch, fetch_failed, fetch_err, fetch_timed_out
):
    if fetch_failed:
        own_ref_full = f"refs/remotes/origin/{branch}"
        # Recovery path: a TRANSIENT timeout (after the 60s retry) is downgraded
        # to a WARNING *only* when a prior remote-tracking ref exists AND the
        # checkout is verifiably current against it. behind == 0 against a
        # last-known ref is acceptable here: the design explicitly accepts a
        # possibly-stale last-known ref over blocking every preflight on a bad
        # network (the alternative is the #664 r9 false positive).
        if fetch_timed_out:
            rc_ref, _, _ = _run(
                ["git", "-C", str(project_root), "rev-parse", "--verify",
                 "--quiet", own_ref_full]
            )
            if rc_ref == 0:
                behind_own = _behind_count(project_root, own_ref_full)
                if behind_own == 0:
                    report.add_warning(
                        f"git fetch origin timed out (after retry); last-known "
                        f"origin/{branch} ref shows branch up to date."
                    )
                    report.git_status += ", fetch timed out (last-known ref current)"
                    return
                # behind_own > 0 (verifiably behind) OR None (count unknown)
                # falls through to the ERROR below — never a silent PASS.
        # Non-timeout failure, no last-known ref, or verifiably behind/unknown:
        # keep the #554 fail-loud ERROR verbatim.
        report.add_error(
            f"git fetch origin failed ({fetch_err}) — cannot verify branch "
            f"{branch} is up to date with origin/{branch}."
        )
        report.git_status += ", fetch failed"
        return
    # ... unchanged fetch-success path (lines 423-470) ...
```

Note: `behind_own == 0` is the only downgrade trigger. `behind_own is None`
(missing ref or git error — though `rc_ref == 0` already proved the ref
exists, this guards a racing/garbage count) and `behind_own > 0`
(verifiably behind the last-known ref) both fall through to the ERROR. This
keeps acceptance criterion 2 ("genuinely-stale checkout still reports
ok=false"). The ERROR message string is left **byte-identical** to the
current one so any agent spec that pattern-matches it (the file's own
docstrings note this convention for `main`) is unaffected.

## 4. Failure modes

- **Brand-new pod with NO `origin/<branch>` ref at all.** The
  `rev-parse --verify --quiet` probe returns `rc_ref != 0`, so the downgrade
  branch is skipped entirely and the code falls through to ERROR — correct
  (criterion 2: "no last-known ref ... reports ok=false"). The existing
  `test_unpushed_branch_warns_not_errors` exercises the fetch-SUCCESS no-ref
  path (WARNING); the new timeout+no-ref case is ERROR and is the negative
  half of one of the new tests.
- **Long-stale last-known ref.** The WARNING explicitly says "last-known
  origin ref", and the design deliberately accepts a possibly-hours/days-old
  ref over blocking every preflight on a persistently bad network. This is an
  explicit, documented caveat (the alternative — never downgrading — is the
  exact #664 r9 false positive we are fixing). Called out here so the critic
  sees it is intentional, not an oversight: when the network is so bad the
  fetch times out even at 60 s, we cannot know whether the remote advanced,
  so we trust the last-known ref and WARN rather than ERROR.
- **Non-timeout fetch failure (auth, DNS, `fatal: unable to access remote`).**
  `fetch_err != "timeout"` → `fetch_timed_out` is False → no retry, no
  downgrade → unchanged #554 ERROR. `test_feature_branch_fetch_failure_errors`
  (which uses `fetch_rc=128`, stderr `"fatal: unable to access remote"`)
  continues to pass unchanged — this is the regression guard that the fix
  did not over-broaden.
- **Retry succeeds.** If the 60 s retry returns rc=0, `fetch_failed` is
  False and the function takes the normal fetch-success path — the timeout
  was fully transparent. (Happy-retry path; covered by a test.)
- **Both fetches time out + ref current but the working tree diverged
  (ahead) since last fetch.** `behind_own == 0` triggers the WARNING; an
  unpushed-ahead state is not detectable without a successful fetch, same as
  today — acceptable, and no worse than the pre-#554 behavior.

## 8. Decision Rationale (§11)

- **What:** Retry-fetch timeout on the second attempt = **60 s** (first
  attempt stays at the existing 15 s).
  **Why:** The repro shows a direct `git fetch origin <branch> --depth=1`
  completing "rc=0 within seconds" on the same slow-network pod, so a single
  longer-timeout retry almost always succeeds; 60 s is comfortably above the
  observed completion time while bounding the worst-case added preflight
  wall-clock to ~60 s (acceptance criterion 3: "adds at most ~60s"). Tied to
  the Goal: the whole point is to ride out a transient slow fetch without a
  false ERROR, and 60 s is the value that lets a slow-but-working fetch
  finish while still timing out a truly-dead network so the last-known-ref
  WARNING path (or ERROR fall-through) engages.
  **Source:** task #696 body proposed fix (Thomas-authored) — the body item
  1 specifies "a longer timeout (e.g. 60s vs the current short timeout)", and
  acceptance criterion 3 pins the ~60 s wall-clock bound.
  **Alternatives:** (a) bump the single fetch timeout to 60 s with no retry —
  rejected: penalizes EVERY preflight (incl. healthy ones) by up to 45 s extra
  on the common case where 15 s is plenty, whereas retry-on-timeout only pays
  the cost when the first attempt actually times out. (b) exponential-backoff
  multi-retry loop — rejected: the body says retry ONCE, and multiple retries
  could blow past the ~60 s wall-clock bound in criterion 3. (c) drop the
  timeout to a WARNING unconditionally — rejected: loses the genuinely-behind
  ERROR (criterion 2) and the no-ref ERROR.

No load-bearing training/model hyperparameters exist in this task (it is a
code change, not a training run); this single retry-timeout value is the only
numeric choice and is grounded above.
