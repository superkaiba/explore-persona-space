## §1 Motivation (verified, not inherited)

Verified first-hand this session against `tasks/planning/1336/plans/v16.md`
(the `EXT_off` row, §9 compute table). The row, verbatim:

```
| EXT_off: 20 off-diagonal cells × n=48,103 rows teacher-forced (axis: cells) | 3.8 | 30 | 20 cells / 8 GPUs, batch 8 bf16, 32 layers | "wave-1 measured: 81.6k rows ≈ 7.6 GPU-h ⇒ 10.7k rows/GPU-h ⇒ 20 cells × 48.1k rows ≈ 90 GPU-h naive-serial ÷ 8-way ≈ 11.2 wall-h serial-equivalent; ×1.09 over v15's 44k-row booking, inside the booked ×1.5 margin; MEASURED 1-cell pilot at production shape re-projects the queue after Phase EXT_off's first cell (abort > 30 min/cell)" |
```

Header: `| component | planned_wall_h | planned_gpu_h | parallelism | basis |`.

Arithmetic I re-derived, not quoted:

| quantity | value | source |
|---|---|---|
| basis-derived GPU-h | 90 | the row's own basis text |
| booked `planned_gpu_h` | 30 | the row's own column |
| Arm-A ratio (GPU-h axis) | **3.0×** | 90 / 30 |
| booked per-cell wall | **~91 min** | `planned_wall_h 3.8 h × 8 GPUs ÷ 20 cells` = 1.52 h |
| row's own abort threshold | 30 min/cell | the row's own basis text |
| Arm-B ratio | **~3.0×** | 91 min / 30 min |

Two consequences, both realized:

1. **The abort gate fires on a nominally-healthy run.** A run performing exactly
   as booked hits ~91 min on its first cell and trips a 30-min abort.
2. **The GPU-hour auto-approve cap is silently breached.** The plan books
   "Estimated GPU-hours (total): 65"; at the basis's own arithmetic the honest
   total is ~125 GPU-h — over the 100 GPU-h `EPM_PLAN_AUTOAPPROVE_GPU_HOURS`
   rail that gates unattended approval.

The category error underneath both: **parallelism divides WALL time, never
GPU-hours** (GPU-h = wall × n_gpus). Dividing a GPU-h figure by an N-way width
and booking the quotient as GPU-h under-books by exactly N.

Recurrence (from the task body, four named incidents): #823 (asserted ~2 s/fit
vs ~125 s real; 12–20 h realized), #811 (unit 3/108 at 19 h 21 m), #1092
(batched battery priced by FLOP ran ~2.6× the naive booking), #1336 (the driving
case; survived plan v15 → v16 at 0 FAIL). This is a recurring class, not a
one-off.

**Why mechanical, and why WARN.** Both surfaced independently as prose
follow-ups from the Methodology AND Statistics critic lenses on #1336 v16 —
i.e. two human-grade reviewers caught it only after two approved versions. The
arithmetic is fully contained in a single table row, so it is mechanizable. It
stays WARN because a legitimately-superseded naive-serial figure is a normal
thing to show in a basis, and because both sides are heuristic (regex parsing of
free prose); the reviewer lens remains the binding arm. Same disposition as its
two siblings c26 and c32.

## §3 Design

### 3.1 One check, two arms

**`c47_basis_booked_arithmetic`** — a single registered id (acceptance
criterion 1 says "a stable id", singular), reporting both arms in one bounded
WARN detail tagged `[arm A]` / `[arm B]`. Per-arm fixtures are arm-isolated so
criterion 3 (Arm-A escape) and criterion 4 (Arm-B escape) each yield PASS.

Kind gate: `kind in ("experiment", "analysis")`, else SKIP — matching c26/c32.
`infra | batch | survey` plans carry no §9 compute table of this shape.

### 3.2 Parser — one copy of the job

`_c26_compute_table_rows` cannot serve Arm A: it returns no GPU-h column and no
parallelism column. Rather than duplicate the parser (a Supersede violation) or
churn the 4-tuple arity across two call sites and ~40 pinned tests, **extract
the primitive and keep the existing helper as a projection of it**:

```python
class _ComputeRow(NamedTuple):
    component: str
    wall: str
    gpu_h: str          # NEW — fuzzy header match: a header cell containing "gpu"
    parallelism: str    # NEW — fuzzy header match: a header cell containing "parallel"
    basis: str
    row_text: str

def _compute_table_rows(plan: str) -> list[_ComputeRow]:
    """The primitive. Row-ADMISSION predicate is UNCHANGED from
    _c26_compute_table_rows: a table is admitted iff its (fence-masked)
    header carries a basis column AND a wall column; a body row is admitted
    iff it reaches the basis column. gpu_h / parallelism are OPTIONAL and
    default to "" when the header has no such column."""

def _c26_compute_table_rows(plan: str) -> list[tuple[str, str, str, str]]:
    """Back-compat projection — c26 + c32 call sites untouched."""
    return [(r.component, r.basis, r.wall, r.row_text) for r in _compute_table_rows(plan)]
```

**Hard requirement: byte-identical behaviour for c26 and c32.** The admission
predicate, the fence mask, the short-row defence and the cell-stripping are
carried over verbatim; the ONLY additions are two optional columns. Regression
evidence = the existing c26/c32 tests stay green with no edits.

c47 additionally requires a `gpu` column for Arm A and skips rows lacking one
(Arm B needs only `wall` + `parallelism` + the basis text).

### 3.3 Arm A — basis-vs-booked, **GPU-h axis ONLY**

For each admitted row:

1. Parse the largest **GPU-hour** figure from the basis cell:
   `(?<![\d.])(\d+(?:\.\d+)?)\s*(?:GPU-?h(?:ours?|rs?)?)\b` (case-insensitive).
2. Parse the booked `planned_gpu_h` from the gpu column (first bare number;
   skip the row if unparseable or zero).
3. WARN when `derived > 2.0 × booked` AND no row-scoped reconciliation marker
   AND no document-wide standalone-N/A escape.

**The axis restriction is the central calibration decision, and it directly
resolves the trap the task body's own draft allowlist walks into.** The body
proposed allowlisting `naive-serial (superseded by <x>)` and `x-way` — but the
driving row contains BOTH the bare string `naive-serial` AND `÷ 8-way`, so a
substring allowlist on those tokens would suppress the exact incident acceptance
criterion 2 requires to WARN. Restricting Arm A to the GPU-h axis makes the
resolution principled rather than ad-hoc: **parallelism reduces wall time and
never GPU-hours**, so a bare `N-way` / `÷ 8` / `across N GPUs` token can never
reconcile a GPU-h-vs-GPU-h discrepancy, and is therefore deliberately NOT an
escape.

Three further reasons the wall axis is out of scope in v1:

- GPU-h is the axis that gates the 100 GPU-h auto-approve rail — the concrete
  harm.
- On the wall axis a basis legitimately shows a serial-equivalent figure BEFORE
  the parallelism division; distinguishing "already divided" from "not yet
  divided" from free prose is not mechanizable at WARN-grade precision. (The
  driving row's wall axis is 11.2 vs 3.8 = 2.95× — it WOULD fire, but for
  reasons the parser cannot certify.)
- One axis is a smaller noise surface on a 1,056-file corpus.

Recorded as an accepted gap in the docstring, with the wall axis named as
possible v2 work.

**Reconciliation allowlist (row-scoped, case-insensitive), deliberately
narrow — every entry must express an INTENT to reconcile:**

| token | regex | why it reconciles |
|---|---|---|
| superseded | `supersed\w*` | the derived figure is explicitly labelled as replaced |
| reconciled | `reconcil\w*` | an explicit reconciliation marker |
| upper bound / worst case / ceiling | `upper[- ]bound\|worst[- ]case\|ceiling` | the derived figure is labelled a bound, not the estimate |
| includes/excludes scope note | `(?:in\|ex)cludes\s+\w+` | the two figures cover different scopes |
| standalone N/A | `_standalone_na_declared(plan, r"basis arithmetic reconciled…")` | the document-wide deliberate declaration, matching the c24/c26/c32 family |

**Deliberately NOT escapes, each with the reason recorded in the docstring:**

- bare `naive-serial` — a label, not a reconciliation; #1336's own text. The
  escapable form is `naive-serial (superseded by <x>)`, which the `supersed\w*`
  entry already covers, exactly as the task body wrote it.
- bare `N-way` / `÷ N` / `across N GPUs` — parallelism, which cannot change
  GPU-h (§3.3 above).
- **`pilot-gated` — a documented deviation from the task body's draft
  allowlist.** Pilot-gating does not reconcile a contradiction; it defers one.
  The booking is what the 100 GPU-h cap is applied to AT APPROVAL TIME, before
  any pilot runs — and the driving incident was itself a pilot-gated row.
  Admitting it would make the check blind to its own motivating case. Flagged
  here as the plan's most reviewable judgement call.

Threshold `2.0×` is the task body's own figure, lifted to a module constant
`_C47_BASIS_BOOKED_RATIO = 2.0` so the calibration sweep can retune it without
a logic edit.

### 3.4 Arm B — abort-vs-booked per-cell

For each admitted row:

1. Parse an abort threshold from the row text:
   `abort[^.;|]{0,40}?>\s*(\d+(?:\.\d+)?)\s*(min|minutes?|h|hours?)\s*/\s*cell`
   → normalise to hours. No match ⇒ this arm skips the row (never guessed).
2. Parse `n_cells` from the row text: `(\d+)\s*(?:\S+\s+)?cells\b` (the driving
   row's `20 off-diagonal cells` and its parallelism cell's `20 cells` both
   match; take the max, and require ≥ 2).
3. Parse the parallelism width from the parallelism cell:
   `(\d+)\s*(?:×\s*)?GPUs?\b` → `width`, default 1.
4. Booked per-cell wall (hours) = `planned_wall_h × width / n_cells`; fall back
   to `planned_gpu_h / n_cells` when the wall column is unparseable. Skip the
   row when neither is parseable.
5. WARN when `per_cell_wall > abort_threshold` (strict), unless a row-scoped
   `supersed\w*` / `reconcil\w*` marker or the standalone-N/A escape is present.

Driving row: `3.8 × 8 / 20 = 1.52 h = 91.2 min > 30 min` → WARN. ✅

Accepted gaps recorded in the docstring: a per-cell abort stated in prose
OUTSIDE the table is invisible; a cell that itself consumes several GPUs makes
the per-cell wall an over-estimate (permissive direction — under-WARNs, never
over-WARNs); a booking exactly AT its abort threshold does not fire (strict `>`,
per the task body's wording) even though any variance would trip it.

### 3.5 WARN detail

Follows `_c26_offender_detail`: ≤3 offenders + `; ...`, each rendered as
`row '<component[:60]>' [arm A] basis derives 90 GPU-h vs booked 30 (3.0×)`, plus
the rule anchor (`.claude/rules/plan-compute-sizing.md § Per-cell fit phases`),
the incident anchors (#1336 driving; #823 / #811 / #1092 recurrence), and both
remedies (state the reconciliation in the row, or declare the standalone N/A).

PASS detail names `n_considered` rows, mirroring c32.

### 4.3 Calibration sweep — **acceptance criterion 5, a GATE not a report**

A throwaway sweep script (NOT committed; run from the worktree) over all
`tasks/**/plans/*.md`, invoking `verify_plan_text(raw, kind=<kind from the
task's body.md>)` and collecting every `c47` WARN.

**Gate:** corpus WARN rate **≤ 2%** (≈ ≤ 21 of the 1,056 `planned_gpu_h`-bearing
plans). Every hit is listed in the `epm:results` marker with issue + row
component + arm + the two numbers, and **at least 10 hits (or all of them, if

above the gate, or an adjudication showing a systematic FP class, means
RE-CALIBRATE (tighten the regexes or widen the allowlist) and re-sweep before
the diff lands — a noisy regex must not ship.

Any accepted-FP class that survives is recorded in the check docstring's
accepted-gap list.

## §7 Fail-loud posture

- No `try/except: pass`, no silent defaults. Every unparseable field results in
  the ROW being skipped for that arm, with the skip visible in the PASS detail's
  `n_considered` count — never a guessed number and never a swallowed error.
- WARN, never FAIL: `_warn` leaves `passed=True`, so a noisy c47 can never block
  a plan. The reviewer lens stays binding. This is the same disposition as c26
  and c32, and is what makes the ≤2% calibration gate a quality bar rather than
  a safety-critical threshold.
- The parser extraction is the one place a silent regression could hide, so it
  carries an explicit no-change test (§4.2 last item) on top of the ~40 existing
  c26/c32 pins.
