## 1. Requirement

Add a WARN-only mechanical check (**check 54**, `check_artifact_content_claims`) to `scripts/verify_task_body.py` that verifies prose claims of the form "per-\<unit\> values … recorded/live in \<linked JSON\>" against the ACTUAL structure of the pinned JSON artifact. Today a false artifact-content pointer passes every mechanical check (checks 30/32/40/42 verify counts, filename membership, and URL existence — never structure INSIDE a pinned JSON); only a manual critic artifact-walk catches it (#2222 round 2).

**Incident shape (ground truth, verified in the #2222 worktree):** `eval_results/issue_2222/form_a_probe.json` records `n_datasets: 24` in metadata but contains NO 24-length per-dataset structure (no 24-length arrays, no dataset-name-keyed dict), while the body claimed "the per-dataset values behind the three probe correlations are recorded in the probe JSON pinned in the footer". The TRUE-pointer counterexample: `predictor_correlations.json` carries a top-level `dataset_values` structure plus a `datasets` list.

## 4. Design

- **Claim gatherer** (`_gather_artifact_content_claims`): fence-stripped scan of the v4 `## Results` + `## Takeaways` prose (grandfathered v3/v2 bodies: silent no-op — forward-only, the check-41 argument). A claim instance = a sentence containing (a) a per-unit phrase — `per-<unit>` / `per <unit>` where `<unit>` is a word token (dataset, layer, seed, behavior, …) — combined with a recorded/stored vocabulary verb (`recorded|stored|live[s]?|saved|listed|available`) + `in`, and (b) a pinned `.json` markdown link resolvable from the same sentence or its immediate window (the check-30 adjacency conventions: link in the sentence, or the nearest preceding pinned `.json` link in the same paragraph; a "pinned in the footer" phrasing resolves to the footer's matching-basename pinned `.json` link — the #2222 shape).
- **Pin resolution + artifact load**: GitHub blob links with a 40-hex sha (`/blob/<sha>/<path>`) load via the existing `git show <sha>:<path>` / `git cat-file` machinery (the check-26 sidecar-loader convention, worktree-shared object DB); a repo-relative committed working copy is the fallback when the sha is locally unknown. HF-hosted JSONs are OUT of scope for v1 (no network content downloads — keeps the check offline; surfaced as an `unverified` note, never a WARN).
- **Expected cardinality recovery**, in priority order: (1) an explicit number in the claim window ("24 datasets", "across 24 datasets"); (2) the artifact's own metadata (`n_<unit>s` key, e.g. `n_datasets: 24`; or a `<unit>s` list length, e.g. `datasets`); (3) unrecoverable ⇒ SKIP that claim with an `unverified` note — never a WARN.
- **Structure scan** (`_json_has_structure_of_cardinality`): recursive walk; the claim VERIFIES if the JSON contains, at any depth, a list of length K or a dict with K keys (K = expected cardinality; bounded depth/width for pathological files). Absent everywhere ⇒ ONE WARN naming the JSON path + the verbatim claim sentence + K + where the expected count came from.
- **Semantics**: WARN never FAIL (`passed=True, is_warn=True` — the check-30 convention; phrasing variance makes the parse heuristic and the critic lens stays binding). Fail-soft everywhere (unresolvable sha, unparsable JSON, missing file ⇒ `unverified` notes on a PASS line; oversized JSON > ~10 MB ⇒ skip). No network.
- **Placement**: new check function adjacent to check 32's region; wired into `main()` after check 53; header doc-block entry ("check 54"). **#2231 coordination**: #2231 (live at planning) edits check 31 in the SAME file — check 54 is APPEND-ONLY (new functions + one `results.append` line + one header entry), no reorganization of existing checks, minimizing the merge-conflict surface.
