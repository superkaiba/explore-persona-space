## 4. Design

- **Claim gatherer** (`_gather_artifact_content_claims`): fence-stripped scan of the v4 `## Results` + `## Takeaways` prose (grandfathered v3/v2 bodies: silent no-op — forward-only, the check-41 argument). A claim instance = a sentence containing (a) a per-unit phrase — `per-<unit>` / `per <unit>` where `<unit>` is a word token (dataset, layer, seed, behavior, …) — combined with a recorded/stored vocabulary verb (`recorded|stored|live[s]?|saved|listed|available`) + `in`, and (b) a pinned `.json` markdown link resolvable from the same sentence or its immediate window (the check-30 adjacency conventions: link in the sentence, or the nearest preceding pinned `.json` link in the same paragraph; a "pinned in the footer" phrasing resolves to the footer's matching-basename pinned `.json` link — the #2222 shape).
- **Pin resolution + artifact load**: GitHub blob links with a 40-hex sha (`/blob/<sha>/<path>`) load via the existing `git show <sha>:<path>` / `git cat-file` machinery (the check-26 sidecar-loader convention, worktree-shared object DB); a repo-relative committed working copy is the fallback when the sha is locally unknown. **Footer matching-basename resolution key** (the "pinned in the footer" shape): claim-sentence tokens ∩ pin-basename tokens (the incident's "probe" → `form_a_probe.json`, unique among the footer's ~11 pins); ≥2 candidate pins matching ⇒ SKIP with an `unverified` note. HF-hosted JSONs are OUT of scope for v1 (no network content downloads — keeps the check offline; surfaced as an `unverified` note, never a WARN).
- **Expected cardinality recovery**, in priority order: (1) an explicit INTEGER immediately adjacent to the unit noun — the `<K> <unit>(s)` shape ("24 datasets", "across 24 datasets") — NEVER any bare numeral in the window (the incident window's only "24" is the decimal "−0.24"; a loose window regex would false-recover from it); (2) the artifact's own metadata via an **ANY-DEPTH** scan for `n_<unit>s` keys, with an aggregation rule: all discovered values equal ⇒ that K; disagreement ⇒ SKIP with an `unverified` note (the incident's `n_datasets: 24` lives ONLY nested at `records[i].n_datasets` — a top-level-only read makes the check structurally unable to fire on its founding incident); or a `<unit>s` list length (e.g. `datasets`); (3) unrecoverable ⇒ SKIP that claim with an `unverified` note — never a WARN.
- **Structure scan** (`_json_has_structure_of_cardinality`): recursive walk; the claim VERIFIES if the JSON contains, at any depth, a list of length K or a dict with K keys (K = expected cardinality; bounded depth/width for pathological files). **Bound exhaustion ⇒ SKIP (unverified note), never "absent" ⇒ WARN** — a deep true structure must not false-WARN. Absent everywhere within bounds ⇒ ONE WARN naming the JSON path + the verbatim claim sentence + K + where the expected count came from. Known residuals, documented in the docstring: (i) recovering K from a `<unit>s` list length lets that same list satisfy the scan by construction (false-negative-only; the critic lens stays binding); (ii) a K-keys-plus-aggregate dict (e.g. 24 dataset keys + 1 summary key) is a known false-positive shape to watch in the §6.2 sweep; (iii) active-voice claims ("the JSON records the per-layer values") lack the `<verb>` + `in` shape and won't parse — documented v1 false-negative class.
- **Semantics**: WARN never FAIL (`passed=True, is_warn=True` — the check-30 convention; phrasing variance makes the parse heuristic and the critic lens stays binding). Fail-soft everywhere (unresolvable sha, unparsable JSON, missing file ⇒ `unverified` notes on a PASS line; oversized JSON > ~10 MB ⇒ skip). No network.
- **Placement + wiring**: new check function adjacent to check 32's region; wired via the module-level **`CHECKS` list** entry after check 53's (the file's actual convention — check 53 rides `CHECKS` at ~:16961, NOT a `results.append` in `main()`), plus a `test_check54_registered` membership pin (the `test_check51_registered` convention); header doc-block entry ("check 54"). **#2231 coordination**: #2231 (live at planning) edits check 31 in the SAME file — check 54 is APPEND-ONLY (new functions + one `CHECKS` entry + one header entry), no reorganization of existing checks; hunk loci ~530–8,000 lines from #2231's (consistency-checker verified conflict-implausible on the script). New TESTS are placed near the existing check-30/32 test region (~:3102–3300), NOT the file tail, to stay clear of #2231's check-31 test insertions (~:1393–1560) — the one plausible append-append collision surface.
