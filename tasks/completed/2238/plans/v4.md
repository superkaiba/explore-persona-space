# Plan v4 — #2238: wire the CPU provision path into the wait-for-capacity loop

## 0.0 TL;DR

`pod.py provision --wait-for-capacity` never retries on a CPU intent because `cmd_provision`'s CPU branch `return`s at `pod_lifecycle.py:2835`, nine lines before the flag is read at `:2851`. The raise contract already exists (`create_cpu_pod` raises `RunPodNoCapacityError`, `runpod_api.py:921-922`), so only the wiring is missing. Fix: extract the existing retry loop over a deploy thunk, add a CPU delegate, and route the CPU branch through it — GPU behavior byte-unchanged.

## 1. Goal (verbatim from the task)

`pod.py provision --wait-for-capacity` is structurally inert for every CPU intent — the CPU branch returns before the flag is read, so the retry loop wraps only the GPU path. In an autonomous session the gap is actively misleading: the provisioner prints that it is auto-enabling unbounded retry, then fails fast on the first `SUPPLY_CONSTRAINT`. Wire the CPU provision path into the existing wait loop (or, at minimum, refuse/warn loudly when the flag cannot take effect).

## 3. Design — Deliverable 1 (thunk generalization). Deliverable 2 NOT taken.

Deliverable 1 is chosen over the Deliverable-2 fallback (warn loudly) because the raise contract already exists, so the wiring is the smaller and more honest change. Deliverable 2's loud-warning branch is therefore NOT implemented — recording that choice explicitly, per the task's "Fail loud if (1) is declined".

**Step 3a — extract the retry loop over a deploy thunk (`pod_lifecycle.py`).** The loop body at `:1267-1347` is already generic over its deploy call; the only GPU-specific surfaces are the `create_pod` kwargs and the `f"{gpu_count}x {gpu_type}"` label at `:1262`. Extract a private `_deploy_with_wait_for_capacity(*, name, spec_label, deploy, preflight_check=None)` holding the loop verbatim — backoff, `source` local/api tagging, the `reason=` token set, the per-process budget check, `WaitForCapacityStillWaiting(verb="provision", …)`, the `KeyboardInterrupt` passthrough, and the `[wait-for-capacity]` heartbeats — with `spec_label` substituted at the one label site.

**Step 3b — keep `create_pod_with_wait_for_capacity`'s public signature BYTE-IDENTICAL.** It becomes a thin delegate: `spec_label=f"{gpu_count}x {gpu_type}"`, `deploy=lambda: create_pod(...)` (data-center pin threaded verbatim). This is load-bearing for Acceptance's no-GPU-regression clause — 12 existing call sites (8 in `tests/test_pod_wait_for_capacity.py` at :95/126/156/175/199/218/310/343, plus 4 in `tests/test_insufficient_balance_retry.py` at :234/259/285/567) must keep passing untouched, and the module-global `create_pod` lookup inside the lambda resolves at CALL time so those tests' `monkeypatch.setattr(pod_lifecycle, "create_pod", …)` still takes effect.

**Step 3c — add `create_cpu_pod_with_wait_for_capacity(*, name, instance_id, volume_gb, container_disk_gb, preflight_check=None, data_center_id=None)`**, delegating with a CPU-legible `spec_label` (e.g. `f"CPU {instance_id}"` → `[wait-for-capacity] starting retry loop for pod-2238 (CPU cpu5m-16-128); …`). This resolves the task's note that the GPU-shaped label at `:1262-1263` needs a CPU-legible form.

**Step 3d — wire `cmd_provision`'s CPU branch.** Hoist ONLY the boolean resolution above the CPU branch, and hoist it as `wait_for_capacity = bool(getattr(args, "wait_for_capacity", False)) or _autonomous_session()` — **NOT** the literal `bool(args.wait_for_capacity)` form. This is load-bearing (critic v3 MAJOR): the existing CPU-provision test Namespaces (`_cpu_provision_ns`, `tests/test_pod_lifecycle.py:666-681`) carry no `wait_for_capacity` key, so a literal hoist raises `AttributeError` across every existing CPU-intent test and breaks Acceptance clause 4. The `getattr` guard follows this file's own precedent two lines above the hoist site (`:2753-2756`, `getattr` for hand-built Namespaces); argparse always sets the attribute, so the default only ever applies to hand-built Namespaces. Do NOT instead retrofit the key into `_cpu_provision_ns` — the `getattr` form fixes every present and future hand-built caller, not just the one fixture. Keep each branch's auto-enable PRINT at its own site; keep each branch's auto-enable PRINT at its own site. Rationale: hoisting the print too would reorder the GPU path's stdout (the auto-enable note would precede the existing `Provisioning {name}: {gpu_count}x {gpu_type}` line), an avoidable change to a path this task must not regress. The CPU branch then prints its own CPU-legible auto-enable note and routes:

```
if wait_for_capacity: create_cpu_pod_with_wait_for_capacity(...)   # WaitForCapacityStillWaiting → _emit_still_waiting_and_exit(exc)
else:                 create_cpu_pod(...)                          # unchanged one-shot
```

**Preserved by design, not oversight:** `preflight_check=None` on the CPU leg. The CPU branch deliberately skips `_assert_under_account_hourly_cap` (`:2767-2769` — CPU pods cost cents/hr and `estimate_pod_hourly_rate` returns 0 at `gpu_count=0`), so the loop's `local-cap` reason token is simply never emitted on CPU; the `no-capacity` and API-side `insufficient-balance` tokens both remain reachable.

**Out of scope, explicitly excluded (not silently unaddressed):** `cmd_resume`'s second `wait_for_capacity` resolution at `:2987`. Its wait loop is deliberately balance-only — `:2985-2986` states `SUPPLY_CONSTRAINT` fails loud in BOTH modes because resume is host-pinned and never relocates, so waiting cannot help. Different contract, not this inertness class.

## 5. Tests — Deliverable 3

Extend the existing surface rather than duplicating it (`tests/test_pod_wait_for_capacity.py` owns loop semantics; `tests/test_pod_lifecycle.py:688-731` already has the `_fake_create_cpu_pod` fixture + `test_cmd_provision_cpu_intent_routes_to_create_cpu_pod`).

1. **Wiring test (the task's required shape).** CPU-intent `cmd_provision` with `args.wait_for_capacity=True` under a mocked `create_cpu_pod` that raises `RunPodNoCapacityError` **twice then succeeds** ⇒ asserts 3 calls and a returned pod. This pins the WIRING (retry actually happens), not merely the flag's presence — the distinction the task calls out. Backoff sleeps stubbed to 0.
2. **Autonomous case.** Same, with `EPM_AUTONOMOUS_SESSION=1` and `args.wait_for_capacity=False` ⇒ retries anyway, and the printed auto-enable note appears on the CPU path (the false-comfort assertion: promise printed ⟺ promise kept).
3. **Default-OFF preserved.** CPU intent, flag off, non-autonomous, `create_cpu_pod` raising `RunPodNoCapacityError` ⇒ propagates on the FIRST call (exactly one call). Guards against making every interactive CPU provision hang. **Must `monkeypatch.delenv("EPM_AUTONOMOUS_SESSION", raising=False)`** — otherwise the ambient autonomous env of the session running the suite silently flips this test's own premise (precedent: `tests/test_pod_lifecycle.py:3696`). Apply the same `delenv` at fixture level for the existing CPU-routing tests so they pin the routing they claim to pin rather than passing bimodally.
4. **Still-waiting contract on CPU.** ⇒ `SystemExit(EXIT_STILL_WAITING)` (75), no pod created. **Do NOT "force the budget to ~0"** — that is a trap at both extremes (critic v3 MINOR): a literal `0` DISABLES the check outright (the guard is `if budget > 0 and elapsed + sleep_secs > budget`, so the loop never exits), and a tiny POSITIVE budget with `time.sleep` stubbed to 0 and `time.monotonic` un-ticked never satisfies `elapsed + sleep_secs > budget` either. Copy the existing `_TickingMonotonic` pattern (`tests/test_pod_wait_for_capacity.py:299-343`), which advances a fake monotonic clock so elapsed time actually crosses the budget.
5. **GPU non-regression.** The 8 existing `create_pod_with_wait_for_capacity` call sites are left untouched and must pass unmodified — that IS the regression assertion for the shared loop's budget + `EXIT_STILL_WAITING` semantics (Acceptance clause 4).
6. **Signature-conformant fakes** per `.claude/rules/code-style.md` § one-production-body-test-per-seam-stubbed-function: the `create_cpu_pod` stub mirrors the real signature (`create_autospec` or a `def` mirroring `runpod_api.create_cpu_pod`), never a bare `Mock()`.

## 6. Sibling audit — Deliverable 4 (adjudicated; conclusion: they INHERIT the fix, no change of their own)

`backends/router.py::_runpod_terminal_rung` and the `backend_poll.py` CPU legs invoke `pod.py provision` as a **subprocess** and route on the exit code `EXIT_STILL_WAITING == 75` generically (`router.py:4175/4259/4282/5552-5583`, `backend_poll.py:3906/4014`; `runpod.py:124` mirrors the constant). Neither passes `--wait-for-capacity` explicitly — both rely on `pod_lifecycle`'s `EPM_AUTONOMOUS_SESSION` auto-enable. So once §3d lands, the CPU terminal rung gets retry + exit-75 behavior with no code change on their side; today it gets neither, which is exactly why `runpod.py:1411`'s claim is false. Recorded in the implementer report + the `epm:experiment-implementation` marker; the only edit on that side is the `:1411` comment correction.

**Recorded consequence — CPU fall-through latency changes (critic v3 MINOR 4; a decision, not a defect).** Once wired, an autonomous-session CPU capacity miss at the runpod-FIRST lane (`router.py:5554-5586`) blocks INSIDE the provision subprocess for up to the 45-min per-process budget (`EPM_WAIT_FOR_CAPACITY_BUDGET_SECS`) before exiting 75 ⇒ lane miss ⇒ fellows; today it falls through to the free fellows CPU rung in seconds. Accepted deliberately: this is exactly the GPU lane's existing #1603 semantics, and all three consumers already handle it by design (`_attempt_runpod_lane` exit-75 ⇒ lane miss; `_run_pod_lifecycle_relay` has no timeout and is documented for multi-hour waits, `backends/runpod.py:161-183`; `backend_poll._classify_provision_failure` reads rc=75 + STILL-WAITING markers generically, `:4013-4024`). It is also the behavior #2238 exists to deliver — the whole point is that a CPU capacity miss WAITS instead of dying. Operators wanting the old seconds-fast fall-through lower `EPM_WAIT_FOR_CAPACITY_BUDGET_SECS`; the implementer names this in the report so the router-side shift is on the record.
