## 1. Goal (restated)

Tier (e) of `scripts/vm_disk_guard.py` (home HF hub-cache revision reap, #1376/#1377, + the #1450
size-cap arm) watches ONLY the fixed boot-disk location `~/.cache/huggingface/hub`. Since #1369
relocated `HF_HUB_CACHE` to `/mnt/eps-data/$USER/huggingface-cache/hub` (exports verified in
`~/.bashrc:4` + `~/.profile:34`), the cache that actually grows is structurally uncovered: it
regrew 38 GB → 52 GB in the 5 days since the 2026-08-05 manual reap of the 185 GB
`issue658_theory_assumptions` slab. Make tier (e) multi-root so the relocated cache gets the same
revision-reap + size-cap coverage, triggered from the DATA-DISK pass on the data disk's own
threshold, without weakening any existing safety contract.

## 2. Current state (grounded, verified 2026-08-10)

- Tier (e) `clean_home_hf_stale_revisions()` (`vm_disk_guard.py:1531`) is ALREADY root-parameterized
  (`cache_root: Path | None`, `cache_cap_gb: float | None` kwargs) — but its ONLY call site is the
  boot-disk pass: `run_guard()` L1894, gated on `reclaim_tiers and tmp_root is not None` (the #911
  production opt-in).
- The data-disk pass (`main()` L2249) passes `reclaim_tiers=False, tmp_root=None` — tiers (d)+(e)
  never run there by construction.
- The tier's docstring design note (L1021-1026) deliberately does NOT derive the root from
  `HF_HOME`/`HF_HUB_CACHE`: env-derived resolution varies per process (the cron does not source
  `~/.bashrc`), so the tier watches FIXED locations for deterministic cron coverage. The fix must
  preserve this: the new root is a fixed default, not a runtime env-read of `HF_HUB_CACHE`.
- Escalation dedup state key is `hf:{repo_key}:{band}` (L1527) and the ack sentinel is keyed
  `(repo_key, band_gb)` (L1112) — root-blind; with two roots the same repo (e.g. the Qwen base
  model) can exist in both caches and a home-root ack would silently suppress the data-root alert.
- Live state: `/` 87% (130 GB free), home hub 56 GB; `/mnt/eps-data` ~1 TB, 30% used (712 GB
  free), relocated hub 52 GB. Existing suites: `tests/test_vm_disk_guard_home_hf.py`,
  `tests/test_vm_disk_guard_home_hf_cache.py`, `tests/test_vm_disk_guard_data_disk.py`.

## 3. Design

**D1 — fixed-default extra-roots resolver.** New constant + getter in `vm_disk_guard.py`:
`DEFAULT_EXTRA_HF_CACHE_ROOT_TEMPLATE = "/mnt/eps-data/{user}/huggingface-cache"` resolved with
`getpass.getuser()`; env override `EPS_VM_EXTRA_HF_CACHE_ROOTS` (colon-separated cache PARENT
roots, each holding `hub/` — same parent-root semantics as `EPS_VM_HOME_HF_CACHE`).
Env semantics: **unset → [default data-disk root]; set-but-empty → [] (explicit kill switch);
set → the listed roots.** Deliberately NOT derived from `HF_HUB_CACHE` at runtime (preserves the
L1021 determinism contract). A missing/non-dir root is a clean no-op (existing tier behavior).

**D2 — explicit opt-in on `run_guard`, mirroring the `tmp_root` hermeticity pattern.**
`run_guard()` gains `hf_cache_roots: Sequence[Path] | None = None` and
`hf_cache_cap_gb: float | None = None`. When `hf_cache_roots` is truthy (and `res.triggered`),
append one tier-(e) `TierResult` per deduped root:
`clean_home_hf_stale_revisions(apply, cache_root=root, cache_cap_gb=hf_cache_cap_gb, now=now)`.
Placement: after the tier-(b) append, so the data-disk pass ordering is (b) then (e).
`run_guard` itself NEVER calls the resolver — the `extra_hf_cache_roots()` call lives ONLY in
`main()`'s data-disk branch (source-scan test pins it, mirroring the #911
`production_tmp_root` pin). Library callers stay hermetic by construction: no explicit roots, no
scan.

**D3 — data-disk-branch wiring.** `main()`'s data-disk `run_guard` call passes
`hf_cache_roots=extra_hf_cache_roots(), hf_cache_cap_gb=data_hf_cache_cap_gb()`. The tier thus
rides the data-disk pass's own `res.triggered` percent gate (shared `threshold_pct()` /
`EPS_VM_DISK_THRESHOLD`, exactly like the current data-disk pass — no new threshold env;
`--ignore-threshold` remains boot-pass-only per #1392). The boot-disk pass is UNTOUCHED: home
root coverage, opt-in, and cap behave byte-for-byte as today.

**D4 — data-disk-sized cap.** `DEFAULT_DATA_HF_CACHE_CAP_GB = 150.0`, env
`EPS_VM_DATA_HF_CACHE_CAP_GB`, same fail-soft nonfinite parsing as the existing cap getter.
Sizing: disk is ~1 TB with 712 GB free; cache regrows ~14 GB/5 days organically but the incident
class is a single ~185 GB slab — 150 GB (~15% of disk) bounds that class while never touching a
normal working set. The 50 GB boot-disk default stays boot-only.

**D5 — double-cover guards.** Inside `clean_home_hf_stale_revisions`, next to the existing
workspace-hub guard (L1620): when `cache_root` is explicitly non-None and its resolved `hub/`
equals the HOME root's resolved `hub/`, skip with reason "boot-disk pass owns it" (defends
against an env listing the home root, or a symlinked data root). In `run_guard`'s loop, dedupe
the roots list itself by resolved `hub/` path (first wins).

**D6 — root-tagged escalation/ack keys.** Thread `root_tag: str = ""` through
`_escalate_home_hf_repos` → `_escalate_one_home_hf_repo` → `_should_escalate_hf_repo` →
`_hf_ack_sentinel_path`. Default root: `root_tag=""` → state keys + sentinel names UNCHANGED
(state-file back-compat). Non-default roots: tag = short stable digest of the resolved root
(e.g. `sha1(str(root))[:8]`), giving state key `hf:{tag}:{repo_key}:{band}` and a
tag-suffixed sentinel filename; the Telegram push + sidecar row name the root path explicitly
(push text says "HF hub cache at <root>" instead of "home HF hub cache"). Sidecar
`home-hf-revisions-trimmed` rows gain an additive `cache_root` field when non-default
(consumers key on `kind` only — verified during impl, assumption A3).

**D7 — unchanged contracts (explicit).** Reap selection semantics unchanged on ALL roots: keep
newest + every ref'd revision, unused-≥7d age gates binding, size-cap top-up oldest-first with
the keep contract, per-repo fail-toward-KEEP, pod-side refusal, apply-gating,
`HFCacheInfo.delete_revisions()` blob-refcount-safe deletion. `xet/` sibling dirs (both roots)
stay a NAMED residual outside the hub-only contract — attributed, never reaped, no new code.

## 4. Decisions on the two flagged plan-time questions

1. **Refd-blob stance: KEEP standard keep-newest-plus-refd semantics on all roots.** The v1/v2
   markers observed standard semantics freed only 26.4 GB of the pre-reap 211.6 GB because ONE
   ref'd slab dominated — but weakening the keep contract to chase that slab would let the guard
   delete revisions a live consumer can still resolve. The recurrence is instead bounded by:
   (a) the new 150 GB data-disk cap (would have fired on the 185 GB slab), and (b) the
   escalation arm (40 GB always-escalate, per-revision breakdown + `reap_cmd`) naming any
   unreapable hot slab for HUMAN triage. Residual named in §7.
2. **Secondary gap (non-login-shell writers still hitting the boot-disk cache): FOLD, no new
   code.** The home root keeps its existing tier-(e) coverage, so boot-disk writes stay bounded
   by the existing 50 GB cap + escalation; fixing the writers' environment (systemd/cron
   `HF_HUB_CACHE` export) touches service files and is deliberately decoupled (same posture as
   the #1038 decoupling). Recorded here as the recurrence mechanism; no child task auto-filed
   (this is a `workflow_fix_target` session — recursion guard).
