# Plan v3 — #1786 daily-fix: WARN when dispatch handle points at dead attempt

`architectural: false`

## Requirement + acceptance criteria

Add a WARN-only per-tick detector to the handle-sidecar-consuming poller
(`scripts/backend_poll.py` — confirmed the consuming site; the precedent
detector `pid_file_stale_vs_marker` lives in `scripts/poll_pipeline.py`)
that flags a dispatch handle sidecar (`.claude/cache/issue-<N>-handle.json`)
whose run-scoped fields point at a DEAD prior attempt while a live relaunch
is observed. Mechanical backstop for the #1750-landed prose duty
(`.claude/rules/pod-side-reporting.md` item 1e: rewrite the handle on
relaunch); incident #1689 r15b: the handle kept pointing at the OLD
attempt's `.completion-sentinel.json`, so completion was never observed and
nothing warned.

Acceptance criteria:

1. `backend_poll.py`'s NORMAL tick-JSON tail path (the final
   `_serialize_poll_result` → `print` in `main()`) carries two new boolean
   flags, `handle_stale_vs_live` and `handle_older_than_relaunch`, default
   `false`. The early-return terminal JSON paths (missing/unreadable
   sidecar, queue-timeout/vanish, failover, boot-loop, cuda-ima, wedge)
   are explicitly EXEMPT — they emit their own payload shapes and
   terminate the loop anyway.
2. `handle_stale_vs_live` is `true` iff the newest `epm:run-launched`
   marker's `pid=` field AND the handle's `extra.workload_pid` are BOTH
   present + parseable ints AND differ (metadata-only comparison — no new
   SSH probes per tick). Inert (`false`) when either side is missing —
   lanes that don't populate `extra.workload_pid` (GCP/SLURM) are inert by
   construction. Benign transient window (documented as a code comment):
   on a COMPLIANT relaunch the fresh marker and the handle rewrite land
   seconds-to-minutes apart, so the flag may fire for a few ticks in
   between — acceptable for a WARN.
3. `handle_older_than_relaunch` is `true` iff ≥2 `epm:run-launched`
   markers exist for the issue AND the sidecar file mtime + slack predates
   the SECOND-NEWEST marker's ts:
   `sidecar_mtime + HANDLE_MARKER_SLACK_SEC < ts(marker[-2])`.
   Rationale (critic Must-Fix 1): a COMPLIANT relaunch rewrites the
   sidecar at (re)dispatch time, which necessarily POSTDATES the previous
   launch's marker — while a never-rewritten handle's mtime is the
   original dispatch write, which PREDATES it. Comparing against the
   NEWEST marker would fire persistently on the compliant
   re-dispatch path itself (sidecar rewritten at dispatch, fresh marker
   posts up to ~50 min later on the RunPod lane) — the same
   dispatch→marker latency that makes the first-launch case
   undiscriminable. The second-newest comparison is latency-insensitive.
   `HANDLE_MARKER_SLACK_SEC` default **600 s**, grounded on the #1156
   precedent's slack default (`EPM_POLL_PID_MARKER_SLACK_SEC` = 600,
   pod-side-reporting.md § Residual honesty).
4. **Lane-suffix inertness (critic Must-Fix 2):** when
   `--lane-suffix` is set (per-lane sidecar, #934), BOTH flags are
   forced inert (`(False, False)`) — `epm:run-launched` markers are
   per-ISSUE, so under multi-lane polling lane A's tick would read lane
   B's newer marker and both checks would false-fire every tick on
   healthy handles.
5. WARN-only by contract: neither flag ever contributes to
   `status` / `stall_reason` / verdict / `next_interval`. On fire, ONE
   `log.warning` line per flag naming the recovery (rewrite the handle
   per pod-side-reporting.md § item 1e, or re-dispatch through
   `dispatch_issue.py`).
6. Fail-soft: any exception inside the detector is swallowed to DEBUG and
   returns `(False, False)` — the same deliberate, narrow exception to
   fail-fast as `_maybe_warn_stale_pid_file` (#1156): the flag is
   observability feeding no verdict, and this is the hot shared poll
   script fleet-wide.
7. Unit tests cover the discriminator decision table: pid match / pid
   mismatch / missing `workload_pid` / single-marker first-launch (no
   fire) / two-marker never-rewritten handle: mtime < ts(marker[-2]) −
   slack (FIRE) / two-marker compliant rewrite: mtime between
   ts(marker[-2]) and ts(marker[-1]) (no fire) / two-marker mtime newer
   than newest marker (no fire) / lane-suffix set → both flags inert /
   exception path (False, False) / both flags present in the emitted
   tick JSON on the normal tail path.
8. Fail-loud pin: tests/test_backend_poll.py test_handle_stale_wrapper_swallows_exceptions_to_debug pins the fail-soft contract — the wrapper swallows any internal exception to DEBUG and returns (False, False); its sibling positive control asserts the pure _handle_stale_flags raises nothing on well-formed inputs (swallow vocabulary: except -> log.debug, never a silent verdict change).

## Method delta (vs prior related work)

#1156 added `pid_file_stale_vs_marker` (pod-side pid FILE vs newest
run-launched marker) in `scripts/poll_pipeline.py`; #1650 added the
marker-signature pid-identity arms. The dispatch HANDLE sidecar — read
every tick by `backend_poll.py` via `read_handle_sidecar` — has NO
staleness detector. Delta: same WARN-only mirror pattern, applied to the
handle sidecar at its actual consuming site, reusing (not re-implementing)
the marker-reading helpers, with a SECOND-NEWEST-marker mtime comparison
(the handle is rewritten at dispatch time, unlike the pid file which is
rewritten at launch time — the comparison anchor differs from #1156 for
exactly that reason).

## File paths + concrete diffs

**One production file: `scripts/backend_poll.py`.** Two additions:

(a) Module-level helpers (near the other `_`-helpers):

```python
HANDLE_MARKER_SLACK_SEC = 600  # grounded on EPM_POLL_PID_MARKER_SLACK_SEC (#1156 precedent)

def _handle_stale_flags(
    *,
    handle_workload_pid,          # handle.extra.get("workload_pid")
    sidecar_mtime_epoch: float,
    run_launched_ts_epochs: list[float],  # ts of ALL epm:run-launched rows, ascending
    marker_pid: int | None,       # pid= parsed from the NEWEST run-launched note
    slack_sec: int = HANDLE_MARKER_SLACK_SEC,
) -> tuple[bool, bool]:
    """Pure discriminator (#1786): (handle_stale_vs_live, handle_older_than_relaunch).

    stale_vs_live: both pids parseable ints and differ.
    older_than_relaunch: len(ts) >= 2 AND sidecar_mtime_epoch + slack_sec
    < run_launched_ts_epochs[-2]  (second-newest — a compliant relaunch's
    dispatch-time rewrite postdates the PREVIOUS launch's marker; the
    newest-marker comparison would false-fire on the compliant
    re-dispatch path's dispatch->marker latency).
    """
```

Pure — no IO, unit-testable with no SSH (mirror of
`_pid_file_predates_marker`). Plus the fail-soft wrapper:

```python
def _maybe_warn_stale_handle(*, issue: int, sidecar: Path, handle, lane_suffix) -> tuple[bool, bool]:
    """#1786 WARN-only handle-staleness detector; fail-soft (broad except -> DEBUG -> (False, False)).
    Returns (False, False) immediately when lane_suffix is set (per-lane
    sidecar, per-ISSUE markers -> cross-lane false fire; #934).
    ONE list_events(issue) read supplies count + ts list + newest note (pid= via
    poll_pipeline.MARKER_PID_RE) — lazy import from scripts.poll_pipeline /
    explore_persona_space.task_workflow (the GCP idle block's lazy-import precedent,
    keeps the --help path fast). log.warning on each fired flag with the
    pod-side-reporting.md item-1e recovery pointer."""
```

(b) Wire-in at the tail of `main()` — alongside the existing
post-serialization flag injection:

```python
handle_stale_vs_live, handle_older_than_relaunch = _maybe_warn_stale_handle(
    issue=args.issue, sidecar=Path(sidecar), handle=handle, lane_suffix=args.lane_suffix
)
out = _serialize_poll_result(result)
out["gcp_gpu_idle_advisory_posted"] = ...   # existing
...
out["handle_stale_vs_live"] = handle_stale_vs_live
out["handle_older_than_relaunch"] = handle_older_than_relaunch
print(json.dumps(out))
```

Runs on every NORMAL-tail tick unconditionally (WARN-only; a terminal
tick firing the flag is harmless and still informative). Early-return
paths untouched.

## Kill criteria

- If the implementer finds `backend_poll.py` does NOT retain the parsed
  `handle` at the tick-JSON assembly point (it does — `handle` is in
  scope in `main()`), or the flags cannot be added without touching the
  `PollResult` dataclass in `backends/base.py` (they can — the GCP idle
  flags are injected post-serialization), the single-file contract is
  broken → bounce to re-plan.
- A false-positive window in `handle_stale_vs_live` (acceptance
  criterion 2) that cannot be resolved by the inert-on-missing semantics
  + the documented transient-window comment → downgrade
  `handle_stale_vs_live` to ALSO require the second-newest-marker mtime
  condition, or drop it to mtime-only — implementer may resolve with a
  stated note; a deeper redesign bounces to re-plan.
