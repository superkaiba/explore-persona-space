Explicit `--backend runpod` + the flag is a CLI contradiction (argparse error). Governs the fallback rung only.

### Resume-mechanism trace (the body's unverified hypothesis — RESOLVED: REFUTED)

The body hypothesized the stopped pod-1739 was resumed via (i) the `ssh_preflight` auto-resume (pod_lifecycle.py:1476-1539, `allow_resume=True`) and/or (ii) the #1838 residue-adoption path. 2. **`resume_pod` is called from exactly one production site:** `_resume_with_balance_wait_if_autonomous` (pod_lifecycle.py:1272), whose only callers are `cmd_resume` (:2428, :2455) — i.e. explicit `pod.py resume`. No launch-path resume exists. Hypothesis (ii) is a reap-and-recreate (terminate) path, not a resume.
3. **What actually happened (from #1739 events.jsonl, lines 621/649/656/667/676/680):** four `epm:backend-selected` fallback launches (2026-08-01T22:40Z "launched", 08-02T01:00Z "launched", 02:06Z + 02:49Z "PROVISIONED but workload start FAILED"), at two distinct endpoints (64.247.201.33:12242, 64.247.201.55:13241) — matching the body's incident (1): "4 fallback-provisioned pod-1739 RunPod pods". Mechanism: `cmd_provision`'s idempotency check refuses ONLY `desired_status != "EXITED"` (pod_lifecycle.py:2156: `if candidate in live_by_name and live_by_name[candidate].desired_status != "EXITED":`) — a deliberately-STOPPED pod maps to EXITED (pod_lifecycle.py:208: `if ds == "EXITED":` → "stopped"), so each fallback dispatch passed the check and `create_pod` (runpod_api.py:700 — no resume/adopt branch) minted a **fresh duplicate-named `pod-1739`**. RunPod permits duplicate names. `_upsert_pods_conf` (pod_lifecycle.py:634: `existing = next((p for p in rows if p.name == pod.name), None)`) and the pods_ephemeral state upsert key by NAME, so each fresh pod **hijacked the stopped pod's state row** — which is why the session's forensics read as "resumed the deliberately-STOPPED pod" (pod-1739 RUNNING at a new IP after the user stopped it) and why `pod.py stop --issue 1739` ("re-stopped") acted on whatever pod the state row then pointed at. An adjacent latent bug: `live_by_name = {p.name: p for p in live_pods ...}` (pod_lifecycle.py:2148) collapses same-named duplicates, so a STOPPED entry can mask a RUNNING one in the idempotency check — order-dependent on the API list.

**Consequence for fix (b):** re-scoped from "ownership gate on resume/adopt" (no such code path) to "same-name collision refusal on a STOPPED pod + duplicate-mask fix". This is the plan's registered kill-criterion #2 outcome, applied at plan time.
