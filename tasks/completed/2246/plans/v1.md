### D1 — item 1: make both detached gate workloads visible to the reaper's liveness probe (argv holder, both sites)

`worktree_audit._live_worktree_holders` (:595) harvests the marker substring `.claude/worktrees/<name>` from `/proc/<pid>/cwd` AND `/proc/<pid>/cmdline`. `$WT` is absolute (`<repo>/.claude/worktrees/issue-<N>`), so appending it as an ignored trailing positional argument to the workload `bash` invocation puts the marker in the detached process's argv for its entire life — the same mechanism the #2256 note already relies on for the script path ("the workload SCRIPT path … rides the detached workload's argv for its whole life").

Edit at BOTH sites — `.claude/skills/issue/steps/18-step-10d.md:1075-1077` (lint gate) and `:3682-3684` (surgical gate) — one token each:

```

#     bash '$LINT_GATE_SCRIPT' < /dev/null > /tmp/issue-<N>-lint-gate.log 2>&1 & echo \$!")
# after →
#     bash '$LINT_GATE_SCRIPT' \"$WT\" < /dev/null > /tmp/issue-<N>-lint-gate.log 2>&1 & echo \$!")
```

### D2 — item 2: status-independent unmerged-branch keep reason in `worktree_audit.py`

**Two-signal probe (the central design decision — see §11 D2 for why patch-id alone fails).** New module-level helper (impure, caller-side, injected paths for testability):

```python
def _branch_unmerged(wt_path: str, events_path: Path | None) -> tuple[bool | None, str]:
    """(#2246 item 2) True=retain (commits with no patch-equivalent on
    origin/main and no epm:merged evidence), False=merged/clean, None=probe
    failed (caller keeps — fail toward retention). Never fetches."""
    # 1. HEAD identity + committer epoch in ONE git call (timeout ~10s):
    #    git -C <wt> log -1 --format='%H %ct' HEAD          -> fail => (None, "HEAD unreadable")
    # 2. merged-evidence scan (kind-SCOPED — see below): parse events_path
    #    lines with json.loads, keep ONLY rows with kind == "epm:merged";
    #    collect (epoch(ts), note). Missing file / no rows => empty list;
    #    per-line parse errors are skipped (direction: less merged-evidence
    #    => retention). events_path is None (orphan issue, folder gone) => empty.
    #    a. any epm:merged note containing the full 40-hex HEAD sha  => (False, "HEAD recorded landed")
    #    b. any epm:merged ts >= HEAD committer epoch                 => (False, "epm:merged newer than HEAD")
    # 3. patch-id count (timeout 60s):
    #    git -C <wt> rev-list --cherry-pick --right-only --count origin/main...HEAD
    #    fail/timeout => (None, "rev-list probe failed"); "0" => (False, ...);
    #    else => (True, f"{n} commit(s) with no patch-equivalent on origin/main and no epm:merged evidence")
```

Kind-scoping of the sha match is load-bearing: #2242's own events quote the stranded tip sha inside failure/progress notes — a whole-file grep would false-read it as merged (the hazard direction). Only `kind == "epm:merged"` rows count. Step 2 runs BEFORE step 3 so the common case (properly merged task — 11 of 17 in the measured table) pays one git call + one JSONL read and never the patch-id walk.

**Pure decision** — `should_remove` gains `branch_unmerged: bool | None = False`, checked immediately after the status guard (:437), with two new single-source constants beside `_TRACKED_CHANGES_REASON`:

```python
_UNMERGED_BRANCH_REASON = "branch carries commits not reachable from origin/main (unmerged)"
_UNMERGED_PROBE_FAILED_REASON = "unmerged-branch probe failed (fail toward keep)"
# in should_remove, after the status-not-reapable guard:
    if branch_unmerged is None:
        return Decision(name, False, _UNMERGED_PROBE_FAILED_REASON)
    if branch_unmerged:
        return Decision(name, False, _UNMERGED_BRANCH_REASON)
```

**Caller wiring (lazy — probe only on otherwise-removable worktrees, mirroring the `_has_tracked_changes` pattern at :861-863):**

- `_classify` (:840): after the tracked-changes check, `if decision.remove and _ISSUE_NAME_RE.match(name):` resolve `events_path` (issue number from `_ISSUE_NAME_RE`, status from the `statuses` map, path via `tasks_dir()/<status>/<n>/events.jsonl` — the sanctioned resolver, same as `_issue_statuses`), run `_branch_unmerged`, and construct the keep `Decision` directly (reason constant + `: {detail}` suffix; `tracked_changes_backlog`-style substring matching is unaffected — it keys on `_TRACKED_CHANGES_REASON` only). This covers the initial classification AND the pre-removal fresh re-derivation at :1467.
- `_execute_remediation` (:905): probe fresh before the :950 `should_remove` re-derive and pass the result as `branch_unmerged=` — this closes the second removal path (orphan-kill / junk-dirty-rescue → remove), where a rescued-but-unmerged worktree would otherwise be removed without the probe. (`_remediation_kind` needs no change: a worktree kept by the new reason matches neither the `_LIVE_PROCESS_REASON` nor the `_TRACKED_CHANGES_REASON` branch, returns None, and lands on the plain-KEEP branch.)

**Venv-arm interaction (explicit design decision, per the brief):** a worktree retained by the NEW reason still surrenders its `.venv` — no change to `should_reap_venv`, whose keep-reason-INDEPENDENCE (:447 docstring) the new reason joins as an ordinary plain-keep class. Rationale: (a) a `.venv` is a regenerable build artifact by that arm's own contract (uv.lock checked in at every worktree root) — it is not the data the unmerged keep protects; (b) an ACTIVE merge window is already venv-protected three ways (the D1 argv holder makes `is_live` block at :479, `exe_in_venv` blocks at :481, and the ≥7-day idle floor is orders of magnitude longer than any gate window); (c) making the arm keep-reason-DEPENDENT is exactly the drift its docstring warns against, and would re-pin multi-GB venvs on the 4 measured newly-retained worktrees.

**Probe-cost budget (per the brief):** +0 subprocess calls for every worktree kept by an earlier reason (human-named, live, non-reapable status, grace, tracked-changes) — the probe is lazy behind `decision.remove`. Per otherwise-removable issue worktree: 1 git call (`log -1 '%H %ct'`) + 1 events.jsonl read, plus 1 `rev-list --cherry-pick` call ONLY when no merged-evidence exists (measured 6.1 s worst observed, 60 s timeout, fail→keep). The `_classify` pre-removal re-derivation doubles this for actually-removed worktrees. Typical sweep (0–5 removals/day): ≤ ~20 added subprocess calls, ≤ ~2 min added wall worst-case. Non-issue (agent-/wf-) worktrees are never probed (scope: `_ISSUE_NAME_RE` only — matching the body's item-2 wording; wf-/agent- residual named in §8).

### D3 — item 3, re-scoped: empty-overlay-on-code-bearing-payload fails CLOSED
