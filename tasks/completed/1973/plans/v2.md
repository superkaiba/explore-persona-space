# Plan v2 — #1973 daily-fix: slurm fetch_results atomic rsync pull

### TDD: no

Revision of v1 folding the Methodology critic's Must-Fix (round 1): `--partial-dir` staging + merge exclusion + merge-on-benign-absent, plus the critic's non-blocking hardening notes.

## Requirement + acceptance criteria

Make `SlurmBackend.fetch_results` (src/explore_persona_space/backends/slurm.py, currently L3043-3111) atomic with respect to the live `eval_results/` + `figures/` trees, and make an interrupted/failed pull surface in the finalize verdict instead of landing partial trees behind an `ok: true`.

Acceptance criteria:
1. An interrupted network pull (nonzero rsync rc of the transfer-failure class, or a timeout kill) leaves the live `eval_results/` + `figures/` trees free of any NEW visible/complete-named file content — including across finalize RETRIES (a truncated file must never be merge-able into the live tree under its final name).
2. A failed pull surfaces as a typed error that `_cmd_finalize` (scripts/dispatch_issue.py) converts into a NON-ok finalize verdict (exit 3, `reason: fetch_results_failed`, teardown skipped, sidecar not retired) — never an unqualified `ok: true`.
3. The #598 non-fatal contract survives: a genuinely-absent remote source dir (eval-only job with no `figures/`) stays warn-only and does not fail finalize.
4. The #598 sentinel contract survives: the completion sentinel (`eval_results/issue_<N>/slurm-<jobid>/.completion-sentinel.json`) rides the pull and lands in the live tree BEFORE `confirm_artifacts` runs — the phase-2 merge runs whenever the staging subdir is non-empty, INCLUDING under the benign-absent classification (a mixed rc-23 pull that landed files in staging still merges them; the sentinel is never stranded in staging).
5. The flat 300 s timeout — the resolved root cause, see below — is replaced by a generous env-configurable fence.
6. Pin tests cover: happy path, interrupted pull (live tree untouched + typed error), the partial-dir exclusion (a truncated `.rsync-partial/` file NEVER reaches the live tree while complete staged siblings do), benign-absent-with-merge, timeout, and finalize surfacing.

## Root cause (resolves the body's `unverified hypothesis`)

The incident's `4952148341 bytes received` before `connection unexpectedly closed` ≈ 16.5 MB/s × 300 s — the pull was killed by the `subprocess.run(argv, check=False, timeout=300)` fence at almost exactly the fence wall. `TimeoutExpired` propagates OUT of `fetch_results` (bypassing the warn-only rc branch entirely), is caught by `_cmd_finalize`'s generic `except Exception` (dispatch_issue.py L2323-2334) which logs and CONTINUES to the confirm gate; the declared artifacts were already durable, so confirm passed and finalize reported ok — while `--partial` kept the 4.7 GB partial tree in place under the live `eval_results/`. This fits every observed datum (no warn-only rc log line, ok verdict, partial residue kept). The fix below is correct under every candidate cause regardless (remote drop, scancel race), per the task body.

## Method delta

Today: single-phase direct-in-place network rsync with `--partial`, warn-only on nonzero rc, exceptions swallowed-to-ok by the caller. After: two-phase pull — (1) network rsync into an out-of-tree staging dir with `--partial-dir` confinement (partials live under a dedicated dot-dir inside staging, never under a final filename), (2) local merge rsync staging → live tree excluding the partial-dir (local per-file temp+rename ⇒ no partial file content ever visible in place), with typed-error surfacing threaded through `_cmd_finalize` to an exit-3 verdict.

## Design

### D1 — staging location + hygiene
`staging_root = self._src_root / ".slurm-results-staging" / f"issue-{issue}"`, per-subdir `staging_root / subdir`. `issue` from `handle.extra.get("issue")`, falling back to `handle.pod_name` (never crash on a missing key). Add `.slurm-results-staging/` to `.gitignore` (repo root is the shared committer tree — staging must never dirty `git status`). On SUCCESS of both phases for a subdir: remove that subdir's staging tree (unconditional rmtree — `--remove-source-files` does not remove directories and may skip up-to-date files on older rsync). On FAILURE: KEEP staging (enables partial-dir resume on a finalize re-run) — safe against the retry-contamination class because partials are confined to `.rsync-partial*/`, which the merge excludes (Must-Fix 1); the raised error names the staging path so the residue is attributed, out-of-tree, and janitor-visible.

### D2 — network pull (phase 1)
`argv = ["rsync", "-a", "--mkpath", "--partial-dir=.rsync-partial", src, staging_dst]` — `--partial-dir` (relative → resolves inside each staging destination dir) REPLACES bare `--partial`: a truncated transfer is kept under `.rsync-partial/`, never under its final filename, so it stays resume-usable but can never be mistaken for a complete file (critic Must-Fix 1; matches the task body's own sketch). Timeout: `EPS_SLURM_FETCH_TIMEOUT_SECONDS` env, default **1800** (6× the old fence; the incident transfer needed ~310 s for 4.7 GB). Run with `capture_output=True` so stderr is classifiable + loggable (implementer discretion: `start_new_session=True` + group kill if the known grandchild-pipe post-kill block bites in testing). Classification on nonzero rc:
- **benign-absent**: rc in (23, 24) AND `No such file or directory` in stderr → warn-only (the #598 contract). Does NOT skip phase 2 — see D3.
- **anything else nonzero** (12, 30, 255, other 23-class …) → raise `FetchResultsError` (below) after logging rc + stderr tail.
- `subprocess.TimeoutExpired` → catch, raise `FetchResultsError` naming the fence + staging path (partial stays confined in staging's `.rsync-partial/`).

### D3 — local merge (phase 2)
Runs whenever the staging subdir is NON-EMPTY — after rc 0 AND after a benign-absent classification (a mixed rc-23 pull that landed files, sentinel included, still merges; criterion 4). `rsync -a --remove-source-files --exclude=.rsync-partial*/ staging_dst/ live_dst/` (local-local; per-file temp+rename means no partial content visible in place; `--exclude=.rsync-partial*/` keeps confined partials out of the live tree — Must-Fix 1; `--remove-source-files` bounds transient disk to ~1 file instead of 2× the results size — the incident disk was 85% full). Bounded with the SAME env fence as phase 1 (critic note: v1 had no merge timeout). Then remove the staging subdir tree unconditionally on success. Nonzero rc on the merge (disk-full class) → `FetchResultsError`; the live tree may hold complete files already renamed in — plus at worst rsync's own dot-prefixed temp files (`.name.XXXXXX`) on a crash mid-merge — but never partial content under a visible/complete filename (the criterion-1 invariant the pin test asserts).

### D4 — typed error + caller surfacing
`class FetchResultsError(RuntimeError)` defined in `backends/base.py` (lane-agnostic home; no ABC signature change — `fetch_results` still returns None). In `_cmd_finalize`: catch `FetchResultsError` SPECIFICALLY before the existing generic `except Exception` (that branch stays byte-unchanged for genuine crashes), record `fetch_failed = str(exc)`, still run the confirm gate (a confirm FAIL exits 3 with its own reason as today — evidence + right surfacing), and when confirm passes (or was skipped) and `fetch_failed is not None`: print `{"ok": false, "issue": N, "phase": "fetch_results", "reason": "fetch_results_failed", "detail": <msg>, "chosen_kind": ..., "pod_name": ...}` and return 3 BEFORE `backend.teardown(handle)` — teardown skipped, sidecar NOT retired (matches the existing confirm-fail semantics: evidence preserved, finalize re-runnable; SLURM teardown is a scancel no-op on a terminal job, and the remote scratch + local staging both survive for the retry).

### D5 — blast radius
SLURM lane only (`SlurmBackend.fetch_results`); `GcpBackend`/`RunPodBackend` fetch paths untouched. The `FetchResultsError` catch in `_cmd_finalize` is inert for backends that never raise it. Verified callers tolerate the typed raise: `selector.py:248` delegates; `issue1609_acceptance.py:183-186` try/excepts and records.
