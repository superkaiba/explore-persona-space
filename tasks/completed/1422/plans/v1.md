## 4. Design

### 4.1 Method delta (exactly what changes vs the A–D scan)

**Chosen implementation: a second branch inside the existing Pattern-C loop** over `_HF_LINKTEXT_THEN_PAREN_RE` (`_gather_hf_count_claims`, lines 8644-8646) — NOT a new standalone full-text regex. Rationale (§11 row 2): the iterator already captures the paren body with the same-line `[ \t]{0,2}` separator bound and `[^()]{1,300}` body bound; `_add()` already applies the hex-pin + `/tree/` URL guards; the shared `seen` set already dedups against Pattern C on identical keys. A standalone regex would duplicate all four bounds and create a second maintenance point.

Verification side: **zero changes**. E tuples ride `_verify_hf_whole_prefix_claims` unchanged (two-sided for files, one-sided for shards, files+folders diagnostic, subset hedge, shared probe memo/cap). No change to `check_hf_file_count_claims` control flow, `CheckResult` semantics, or the probe stack.

### 4.2 New module-level regexes (insert after `_FILES_AT_PINNED_REV_RE`, ~line 8447, before `_BACKTICK_DIR_RE`)

```python
# Pattern E (#1005, the trailing-parenthetical footer shape): the paren
# immediately AFTER the pinned link OPENS with the count-noun —
# `[summary store + manifest](…/tree/<sha>/…) (52 files)`. Applied via
# .match() on the paren body captured by _HF_LINKTEXT_THEN_PAREN_RE, so the
# same-line separator ([ \t]{0,2}) and [^()]{1,300} paren-body bounds are
# inherited from that iterator. Wide distributive decline like Pattern D:
# ANY "per <word>" qualifier declines — "per namespace" belongs to the #833
# per-namespace leg; "per adapter"/"per seed" (#460 class) have per-unit
# semantics and would compare N against the parent's total. Trailing content
# after the count-noun is unconstrained within the paren-body bound (the
# #1005 "(17 files incl. `f2f3/` …)" / "(50 files: 42 updated + 8 verbatim)"
# shapes).
_COUNT_OPEN_PAREN_AFTER_LINK_RE = re.compile(
    r"(?P<count>\d{1,3}(?:,\d{3})+|\d{1,6})\s+(?P<noun>files?|shards?)\b"
    r"(?!\s+(?:listed\s+)?per\s+\w+\b)",
    re.IGNORECASE,
)
# B-adjacency decline for Pattern E (mirrors Pattern D's trailing negative
# lookahead, #1143): a paren immediately followed by an HF markdown link is
# Pattern B's paren-before-link shape — E declines rather than extracting a
# second, differently-scoped claim from the same paren. Checked with
# .match(stripped, pos) at the E-paren's closing position.
_HF_LINK_FOLLOWS_PAREN_RE = re.compile(
    r"\s{0,2}[:–—-]?\s{0,2}\[[^\]]{1,300}\]\(https?://huggingface\.co"
)
```

(Count atom `\d{1,3}(?:,\d{3})+|\d{1,6}` copied verbatim from `_COUNT_NOUN_RE`/`_COUNT_PAREN_LINK_RE`/`_BACKTICK_SUBPATH_COUNT_PAREN_RE`; noun set `files?|shards?` matches B/D parity. Exact regex-name spelling is implementer's discretion; the lookahead semantics are not.)

### 4.3 The loop branch (`_gather_hf_count_claims`, lines 8644-8646)

```python
    for lm in _HF_LINKTEXT_THEN_PAREN_RE.finditer(stripped):  # Patterns C + E: paren after link
        for cm in _FILES_AT_PINNED_REV_RE.finditer(lm.group("paren")):  # C (pinned-revision)
            _add(cm.group("count"), "files", lm.group("url"))
        em = _COUNT_OPEN_PAREN_AFTER_LINK_RE.match(lm.group("paren"))  # E (#1005)
        if em is not None and _HF_LINK_FOLLOWS_PAREN_RE.match(stripped, lm.end()) is None:
            _add(em.group("count"), em.group("noun"), lm.group("url"))
```

Semantics notes (bake into the code comment / docstring):
- `.match()` on the paren body = "OPENS with the count-noun" — identical anchor semantics to Patterns B and D. `( 52 files)` (leading space) deliberately does not match — B/D parity, documented recall sacrifice.
- `(1,234 files at the pinned revision)` fires BOTH C and E → identical `_add` args → same `seen` key → one tuple (dedup, not a special case).
- `(50 files: 1,234 files at the pinned revision)` (pathological) fires E with 50 and C with 1234 → two distinct tuples, one probe (shared memo), each verified independently — same multi-claim semantics Pattern A already has via `finditer` over link text.
- Per-namespace parens (`(891 files per namespace)` / `(908 files listed per namespace …)`) are declined by E's lookahead and remain the exclusive property of `_gather_hf_per_namespace_claims` — the per-namespace leg's probes and semantics are untouched.
- Non-pinned URLs never produce tuples: E routes through `_add()`, which enforces `_HF_HUB_TREE_BLOB_URL_RE` + `/tree/<sha>` (declines `/blob/`, `/tree/main`, non-tree HF URLs); non-HF links never enter the iterator (`_HF_LINKTEXT_THEN_PAREN_RE` requires `https?://huggingface\.co/`).
- Why code, not a model call: this is a deterministic regex extraction inside an offline mechanical verifier — an LLM call would be non-deterministic, networked, and unpinnable by tests. (Standing model-call-vs-code checklist item; trivially code.)

## 11. Decision Rationale

1. **Pattern anchor = count-noun OPENS the paren.** *Why:* the position (paren after link) is inherently looser than A/B; anchoring at the paren open is what keeps prose numbers (`(total 515 files)`, `(seed 42, 3 files later)`) out. *Source:* Pattern B (#931/#1008) and Pattern D (#1143) use exactly this anchor; the check-30 docstring names "count not leading" as a deliberate recall sacrifice.
2. **Implement as a branch in the C loop, not a standalone regex.** *Why:* inherits the iterator's same-line separator + paren-body bounds, `_add`'s URL guards, and `seen` dedup — one scan, no duplicated bounds. *Alternative rejected:* a standalone `[label](url) (N files…)` full-text regex (the candidate's diff sketch) duplicates 4 guard surfaces and re-parses the link. *Source:* `_HF_LINKTEXT_THEN_PAREN_RE`'s existing dual use (C-pinned + per-namespace legs), #1088.
3. **Wide `per\s+\w+` decline (not the narrow per-namespace-only form).** *Why:* in the paren-after-link position, ANY distributive qualifier (`per namespace`, `per adapter`, `per seed`) makes N a per-unit count — comparing against the parent total manufactures a guaranteed false WARN. *Source:* Pattern D's identical decline + its #460 rationale (#1143, `_BACKTICK_SUBPATH_COUNT_PAREN_RE` comment); mechanically forced by existing fixture `tests/test_verify_task_body.py:2690`.
4. **B-adjacency decline (E yields to B on `(N files): [link]`).** *Why:* one paren must not mint two differently-scoped claims; B's paren-before-link binding is the established reading. *Source:* Pattern D's trailing negative lookahead + its rationale comment (#1143).
5. **Noun set `files?|shards?`, shard claims one-sided.** *Why:* parity with B/D; verification leg already implements one-sided shards. *Source:* #931/#1008 (`_COUNT_NOUN_RE`, `_verify_hf_whole_prefix_claims`).
6. **WARN grade unchanged; no new FAIL path.** *Why:* check 30's contract — grandfathered v3/v2 bodies must never be newly hard-FAILed; a Hub probe can be transiently wrong. *Source:* #1008 semantics block (`check_hf_file_count_claims` docstring: "There is NO code path returning passed=False"); task-body constraint.
7. **Dedup via the shared `seen` key (no special-casing the C/E overlap).** *Why:* identical `_add` args collapse naturally; the #1143 cross-pattern dedup test proves the mechanism. *Source:* `_add`'s `seen` set (#1008), `test_hf_count_subpath_dedup_with_link_text_pattern` (#1143).
8. **No SPEC.md edit.** *Why:* check 30 is not documented there (grep verified, §2); the module doc block + docstrings are the canonical documentation and ARE updated. *Source:* grep of `.claude/skills/clean-results/SPEC.md`, 2026-07-16.
