# Plan v6 — #1757: act on consistency edit-locus WARN vs live sibling (merge sequencing)

## 0.0 TL;DR (plain English)

When the consistency-checker warns at plan time that this task edits the same
file region as a live sibling task, that warning currently gets folded into
plan prose and forgotten — and the predicted conflict then fires at merge time
(#1718 vs #1716, 2026-07-27: WARN at 11:47Z, `gh pr merge --squash` CONFLICTING
at ~14:28Z, a hand conflict-resolution round on the fleet's hottest file). Fix:
two prose edits to `.claude/skills/issue/SKILL.md` — (A) Step 2b records the
WARN as a machine-scannable `merge-hold-candidate` events note naming the
sibling; (B) Step 10d gains a bounded "Guard 5" that (i) if the named sibling
is still live at `reviewing`-or-later, waits up to ONE gate cycle (45 min,
via the sanctioned Monitor until-loop shape) for it to land, and (ii) —
the load-bearing half — when a candidate note exists, probes for the
predicted conflict up front (`git merge-tree`) and, if it is real, resolves it
proactively IN THE WORKTREE via the existing merge-conflict recovery
machinery BEFORE attempting the server-side merge — so the resolution happens
once, in-flow, instead of via a failed `gh pr merge` round-trip. A stuck
sibling can never wedge the task (bounded hold, sticky cap-expiry), and an
unreadable sibling is treated as no-hold.

## 1. Goal

An edit-locus WARN naming a live sibling should change merge sequencing, not
just be folded into plan prose (task #1757 Goal, verbatim). Concretely: the
/issue orchestrator gains a durable record of the WARN at plan time and a
bounded consumer of that record at merge time that BOTH orders the merge
behind a still-live sibling AND front-loads the predicted conflict's
resolution into the worktree (the filing's "then rebase and proceed").

## 3. Hypothesis / requirement

If the WARN is recorded machine-scannably at plan time and consumed at merge
time, then: (a) when the sibling is still live, the bounded hold gives
deterministic ordering (the WARNed task pays the rebase, as the checker
recommended); and (b) whether or not the sibling already landed, the
predicted conflict is detected up front and resolved IN THE WORKTREE in one
flow — replacing the failed `gh pr merge` → CONFLICTING → reactive-recovery
round-trip with a single proactive recovery pass. The resolution WORK is not
eliminated (both branches touched the same hunk; someone must reconcile);
what is eliminated is the wasted server-side refusal cycle and the
non-deterministic "whichever merges second pays, surprised" outcome. Worst
case added latency: 45 min, only on tasks whose plan-time WARN named a
still-live sibling — never fleet-wide.

### 4.2 Edit B — Step 10d Guard 5 (bounded hold + proactive pre-resolution)

Anchor: end of the "Merge safety guards" numbered list (immediately after
Guard 4's fenced block, BEFORE the "#### Fast-path routing pre-check" H4 —
inside the pin file's `_merge_guards_region`). Add:

> 5. **Sibling merge-sequencing hold + proactive pre-resolution (#1757).**
>    Runs ONCE per Step 10d invocation (never inside per-attempt retry
>    shapes). Half (i) runs at Step 10d entry; half (ii) runs AFTER Guard 0
>    (the agent-memory pathspec commit) — a dirty tree aborts an in-worktree
>    merge (the exact #906 shape Guard 0 exists to clean), so (ii) first runs
>    the idempotent Guard 0 block, then merges. Scan this task's events for
>    `merge-hold-candidate` notes
>    (`grep -F 'merge-hold-candidate' "$(uv run python scripts/task.py find <N>)/events.jsonl"`).
>    No candidate note → Guard 5 is a no-op (one grep). Otherwise, per named
>    sibling `<M>` (dedup):
>    - **(i) Bounded hold.** Read live state via `task.py view <M> --json`.
>      No hold when: its events carry `epm:merged` (any form —
>      `artifact_confirmed` counts); OR its status is in {completed,
>      archived, blocked, on_hold} (a parked/blocked sibling is not landing
>      soon); OR its state is UNREADABLE (`task.py find <M>` fails — treat
>      as no-hold, never a 45-min no-op); OR a PRIOR `merge_hold` disposition
>      note for `<M>` with `outcome=cap-expired` exists on this task's
>      events (sticky — a stuck sibling never re-triggers the hold on
>      re-entry). Otherwise (live at `reviewing`-or-later, unmerged): post
>      ONE `[long-phase-heartbeat] step10d-merge hold sibling=<M> (#1757)`
>      progress note, then wait via the sanctioned `Monitor` until-loop
>      shape (load the deferred schema first —
>      `ToolSearch("select:Monitor")`), elapsed-capped at 2700 s (one 45-min
>      gate cycle), re-resolving the sibling's folder each poll (status
>      moves relocate it):
>
>          until grep -qF '"epm:merged"' "$(uv run python scripts/task.py find <M> 2>/dev/null)/events.jsonl" 2>/dev/null \
>                || [ $SECONDS -gt 2700 ]; do sleep 60; done
>
>      (NEVER a foreground Bash sleep-loop — the 600 s tool cap kills it and
>      the sleep-chain shapes are hook-blocked; Monitor is the sanctioned
>      poll carrier here.) On expiry, record `outcome=cap-expired` and
>      proceed — the hold is bounded by construction; a mutual hold (two
>      siblings each naming the other) resolves at cap expiry on both sides.
>    - **(ii) Proactive pre-resolution (the load-bearing half — fires with
>      any candidate note, INCLUDING when the sibling already merged).**
>      Sequenced AFTER Guard 0's agent-memory commit (run the idempotent
>      Guard 0 block first if not yet run this invocation).
>      `git -C "$WT" fetch origin main --quiet`, then probe for the
>      predicted conflict without touching the working tree, version-aware
>      (this VM runs git 2.34.1 — verified at plan time): on git ≥ 2.38 use
>      `git -C "$WT" merge-tree --write-tree origin/main HEAD` (non-zero
>      exit / conflict listing = real conflict); on older git use the legacy
>      read-only three-arg form —
>      `git -C "$WT" merge-tree "$(git -C "$WT" merge-base HEAD origin/main)" HEAD origin/main`
>      — and detect a real conflict by conflict markers in its output
>      (`grep -q '<<<<<<<'`); the implementer SMOKES the detection against a
>      synthetic two-branch conflict at build time (including one
>      delete/modify case — marker-grep can miss non-textual conflicts;
>      ambiguous output = conflicted) and keeps a degrade
>      clause (probe unavailable/ambiguous → treat the candidate as
>      conflicted — fail toward the proactive resolve, never toward a doomed
>      server-side refusal). CLEAN probe → proceed exactly as today
>      (Guards 0-4 + the normal merge form; experiment branches keep
>      `--rebase`). CONFLICTED → resolve proactively IN THE WORKTREE via
>      the EXISTING merge-conflict recovery machinery (capture ONE
>      `MAIN_SHA`, `git -C "$WT" merge "$MAIN_SHA"`, the mechanical
>      foreign-tasks/figures passes + residual-conflict subagent dispatch,
>      commit, post-resolution certification), then re-run the pre-push
>      workflow-lint gate (the SHA-bound verdict re-binds to the post-merge
>      tip — the #1753 recovery ordering) and take the `--squash` merge form
>      (the branch now carries a merge commit — Known failure shape 1).
>    - Record the disposition in the `epm:merged` / `epm:merge-failed` note:
>      `merge_hold: sibling=<M> waited=<mins> outcome=<sibling-merged|cap-expired|no-hold>`
>      and `pre_resolve: <clean|conflicted-resolved|probe-unavailable>`
>      (omit both lines when no candidate note exists). Same behavior in
>      interactive and autonomous sessions; auto-continue, never a gate.

## 8. Risks and Failure Modes

- **Added merge latency:** worst case 45 min, only on tasks whose plan-time
  WARN named a STILL-LIVE sibling — never fleet-wide. Accepted per the
  filing. Sticky `cap-expired` disposition prevents re-entry re-holds.
- **Proactive merge commit forces `--squash`:** only fires when the probe
  finds a REAL conflict — where the `--rebase` path was doomed to the
  CONFLICTING refusal anyway (shape 2) and the recovery would have ended at

  untouched.
- **Stale candidate note (sibling long since merged, no conflict):** the
  merge-tree probe returns clean → zero behavior change beyond one fetch +
  one probe.
- **Unreadable sibling state:** treated as no-hold (explicit in Guard 5(i)).
- **Reduced trigger surface post-#1732:** named as a scope caveat (§2); the
  recording duty is generic to any `epm:consistency` WARN that still fires.
- **SKILL.md size growth:** ~60 lines on a very large file; no byte ratchet

## 11. Decision Rationale

- **Record-then-consume over plan-prose-only:** #1718 proved plan prose is
  write-only; an events-note with a fixed leading token is the established
  machine-scannable channel (`stage-dispatch`, `deliberate-stop`,
  `followup-parked-by-cap` precedents). Source: #1718 events; SKILL.md note
  conventions.
- **Pre-resolution over hold-only (critic round-1 Must-Fix 2):** in #1718
  the sibling had already merged ~2.5 h before the merge attempt — a hold
  alone is a no-op on the founding incident. The filing's own diff sketch
  carries the action ("HOLD … until epm:merged, then rebase and proceed");
  Guard 5(ii) implements the "then rebase" as an in-worktree merge +
  existing-recovery pass, probe-gated so clean cases pay nothing. Source:
  #1718 timeline; body.md § Proposed change.
- **Monitor until-loop as the hold carrier (critic round-1 Must-Fix 1):** a
  foreground 45-min Bash loop dies at the 600 s tool cap and the sleep-chain
  shapes are hook-blocked; the Monitor until-loop is the sanctioned poll
  shape (SKILL.md § Long-phase heartbeat duty / Step 9c single-flight
  precedents). Source: CLAUDE.md § Orchestrator vs subagent re-invocation.
- **Hold at Step 10d entry (not at plan time):** hours pass between plan and
  merge; live re-check avoids acting on stale ordering advice. Source: #1718
  timeline (WARN 11:47Z → merge 14:28Z; sibling had already landed).
- **45-min cap = one `/issue-tick` cycle:** matches the tick cadence the
  merge window is already covered by (#1723); bounded per the filing.
- **TDD: no** — prose-only change + a pin test; the scanner/lint suites are
  the tests.
