### 4a. `scripts/verify_task_body.py` — the check (primary edit)

**New module-level regex**, placed immediately above `check_repro_context_provenance` (~line 3150):

```python
# Check-17 v4 lineage-token scan: the `**Context:**` row must name its
# lineage (SPEC.md § `**Context:**` row; #958). Matched on fence-stripped +
# blockquote-stripped footer text — the blockquoted verbatim prompt often
# MENTIONS issue numbers ("reuse #537 adapters") and must not satisfy this.
_V4_CONTEXT_LINEAGE_TOKEN_RE = re.compile(
    r"(?<![\w/&])#\d+"                    # issue ref: `[#K](...)` or bare `#K`
    r"|fresh\s+direction"                 # `fresh direction (no parent)` / `...; no parent task`
    r"|\bno\s+parent\b"                   # `fresh (no parent)` / `no parent task`
    r"|same-issue\s+follow-?up\s+round",  # follow-up-round lineage clause
    re.IGNORECASE,
)
```

The `(?<![\w/&])` lookbehind stops URL fragments (`…/page#123`) and HTML entities (`&#8203;`) from counting; `#L123`-style anchors don't match `#\d+` anyway.

## 11. Decision Rationale

1. **Regex shape (4-alternative token family, case-insensitive, `(?<![\w/&])#\d+`).**
   *Why:* the minimal alternation covering every phrasing observed in the 32-body survey, incl. bare `#K` (#823/#841), `fresh direction …; no parent task` (#778/#658), capitalized `Fresh direction` (#744), and the follow-up-round clause; the lookbehind blocks URL-fragment false-satisfies.
   *Source:* survey of all 32 v4 bodies in `tasks/` (§3) + SPEC.md lines 444–448 / 638–643 + task Goal (the `fresh (no parent)` short form).
   *Alternatives rejected:* strict SPEC-literal forms only (`[#K](...)`|`fresh direction (no parent)`) — retro-FAILs ≥4 parked bodies (#823, #841, #778, #658); free-text "Lineage:" label detection — #920/#928/#664 use `Parent:`/`parent [#K]` with no "Lineage" word.

2. **Scan order: strip fences + blockquote lines FIRST, then slice at the label (not slice-then-strip).**
   *Why:* slice-then-strip FAILs #763 (single-line row, inline `> "…"` quote after the label — the post-label remainder starts with `>` and the whole line, lineage included, gets stripped). Strip-first keeps that line (it starts with `**Context:**`) while still excluding multi-line blockquoted prompts, which routinely mention issue numbers ("reuse #537 adapters" — #813; "run … 841 but…" — #922).
   *Source:* planning simulation (1 FAIL → 0 FAILs); the #959 blockquote-strip precedent at `verify_task_body.py:2544–2548`.
   *Alternatives:* scan whole Context block incl. blockquotes — spurious PASS on lineage-less rows whose quoted prompt names issues (defeats the check); require lineage on a dedicated `Lineage:`-labeled line — retro-FAILs ~10 bodies.

3. **Scan bound: label match → end of footer (no cut at a subsequent `**Repro:**`).**
   *Why:* Context is the final footer label in the SPEC template and in all 32 surveyed bodies; the important bound is the START (so `**Repro:**`-block reuse-provenance `[#M](...)` links can't satisfy a lineage-less Context row), which slicing at the label provides.
   *Source:* SPEC template lines 440–448; `_v4_footer_text` (line 2366) anchoring at the first `**Repro:**`.
   *Alternatives:* additionally bounding at a following bold label — unneeded complexity for a shape no body exhibits.

4. **Gating: v4 hard-FAIL; v3/v2 byte-identical (no new WARN); legacy skip; NO `created_at` adoption gate.**
   *Why:* the established forward-only pattern in this file is "older generations keep prior behaviour VERBATIM" (module docstring line 282–283; `is_v4` docstring line 2246–2248; check 7's `is_v4` branch at 2479) — not "older generations get WARNs". A new v3 WARN would create promotion friction on parked bodies for zero authorial benefit (v3 is a dead generation — any follow-up fold migrates it to v4; and #575 already recorded 37 tasks carrying Context-row WARN noise). Hard-FAIL (not WARN) for v4 because the clause is always constructible (parent_id exists or the task is fresh), the analyzer instruction already mandates it (`analyzer-section-reference.md:445`), and #958 r2 demonstrated the trivial fix. No adoption-date gate because the survey shows 0 retro-FAILs — the gate would be dead code.
   *Source:* code precedents above + the 0/32 simulation + #958 (origin incident) + `tasks/completed/575` (WARN-noise evidence).
   *Alternatives:* v3 WARN — rejected (noise on grandfathered parked bodies; CLAUDE.md "WARNs ship only when acknowledged in body" would retroactively tax them); v4 WARN — rejected (a nudge the analyzer can ignore re-creates the #958 bounce this task exists to prevent).

5. **Sync-edit scope (three one-liners; no SPEC edit).**
   *Why:* SPEC is already normative for the lineage clause and defers check enumeration to the verifier docstring; the three stale descriptions (verifier module docstring, clean-result-critic pre-pass comment ~216–220 + Lens-5 parenthetical ~791, analyzer-section-reference line 589) each describe check-17's FAIL surface and would otherwise mislead the critic into treating a legit new FAIL as out-of-contract.
