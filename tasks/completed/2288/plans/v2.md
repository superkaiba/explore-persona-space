## Method delta / concrete diffs (2 files)

### 1. `scripts/verify_task_body.py` — new leg (v): issue-branch worktree discovery (LOAD-BEARING)

Two new module-level functions next to `_git_toplevel_eval_root` (line 6925), plus four lines in `_resolve_eval_root`.

**(a) `_parse_worktree_list(porcelain: str) -> list[tuple[Path, str | None]]`** — pure parser over `git worktree list --porcelain` output: returns `(worktree path, branch ref or None)` per record (records are blank-line separated; `worktree <path>` opens each, `branch <ref>` is absent on detached checkouts). No git, no filesystem — unit-testable in isolation.

**(b) `_issue_branch_worktree_eval_root(issue: int, eval_subpath: Path) -> Path | None`** — leg (v):

- resolve the git root for the query: `_resolve_repo_root()`, falling back to `Path(os.getcwd())` when it returns None (a worktree cwd shares the common dir, so `git worktree list` returns the full set from either);
- `subprocess.run(["git", "-C", str(root), "worktree", "list", "--porcelain"], capture_output=True, text=True, check=False)`; any nonzero exit / OSError → None (the conservative contract `_git_toplevel_eval_root` already uses);
- parse via (a), then keep candidates matching the issue: branch ref `^refs/heads/issue-<N>(-.*)?$` OR path basename `^issue-<N>(-.*)?$`. Both arms are needed against the live tree: `i1739-fit → refs/heads/issue-1739-fit` and `issue-2155 → refs/heads/issue-2155-pm` are real worktrees whose canonical-name arm alone would miss, and the 13 detached `~/.eps-slurm-src/issue-<N>` rsync trees carry no branch ref at all. The `(-.*)?` suffix cannot cross an issue boundary (`issue-21` never matches `issue-2155`);
- order candidates DETERMINISTICALLY — exact branch `refs/heads/issue-<N>` first, then exact path basename `issue-<N>`, then remaining suffixed matches by sorted path string — and return the FIRST whose `<candidate>/<eval_subpath>` is a dir; None when none is.

**In `_resolve_eval_root`,** append leg (v) AFTER leg (iv) (main), immediately before the terminal `return None`. Ordering is the load-bearing safety property: for every merged issue main already satisfies leg (iv), so no post-merge verdict can change, and a stale worktree can never outrank the merged tree. The leg fires exactly in the pre-merge case the task names.

**No caching.** The leg runs only after legs (i)–(iv) all miss, at most 3× per process (the three checks sharing the resolver), ~20 ms per `git worktree list` on the live 91-worktree tree. An `lru_cache` would buy ~40 ms and leak state across tests in one pytest process — rejected deliberately.

**Docstring / comment updates (same file):** `_resolve_eval_root`'s "§4.2a four-leg ladder" docstring gains leg (v) and the ordering rationale; check 35's verdict-ladder docstring (line 7626-7630) keeps its `eval root unresolved` PASS-skip row but notes it now means "no `--eval-root`, no body-path root, no cwd root, no main root, AND no issue-branch worktree"; the "committed result-JSON metadata" wording in check 35's docstring + `_scan_cross_issue_reuse_pins`' becomes "the round's result JSONs (issue-branch worktree or merged main)" — legs (ii)/(iii) already read a worktree filesystem with no committed-ness filter, so this is a wording correction to match existing behavior, not a semantics change. The module-docstring skip list (line 808) gains the same clarification.
