# Plan — #1477: poll_pipeline zombie-override CPU-rate arbiter false-stalls healthy CPU-bound runs

## 0.0 TL;DR (plain English)

- **What I'll do:** fix the `ps` cumulative-CPU parser in `scripts/poll_pipeline.py`'s pod probe so a process that has burned more than one day of CPU no longer makes the poller's "session CPU" total collapse (the deterministic root cause of the #1345 false stalls), and add a second, same-tick `%cpu` reading the stall arbiter consults whenever the cross-tick CPU rate reads negative — an impossible value on a healthy run — so it confirms "is this session actually burning CPU right now?" before flipping a healthy run to `stalled`.
- **What I expect:** the #1345 scenario (a healthy 20-core worker, quiet logs) never flips to `stalled` again, while the one true-positive scenario the override exists for (#664: a dead GPU worker with ~0.22 cores of idle churn) still gets flagged on exactly today's schedule.
- **What would change my mind:** if the regression tests show the new confirm-read can keep a genuinely hung run alive indefinitely (it can't, by design: it is only consulted on negative-rate ticks, which a hung run produces at most once), I'd drop the arbiter change and ship the parser fix alone.

## 0. Plan Summary (technical)

## 1. Goal

"Make `scripts/poll_pipeline.py`'s zombie-override session-CPU rate arbiter robust: the rate must never read negative on a healthy workload, and the override to `stalled` should confirm with a synchronous per-PID `pcpu` probe before flipping a `running` verdict." (Task #1477 `## Goal` H2, verbatim; re-read from `tasks/planning/1477/body.md` at draft time this turn — `kind: infra`, no `goal:` frontmatter, no `epm:goal-updated` markers in `events.jsonl`.)

Interpretation note (grounded in the code read, §2): "the rate must never read negative on a healthy workload" is satisfiable for the demonstrated mechanism (the day-format parse collapse — deterministic, fixed here) but NOT absolutely — a multi-shard child exit legitimately de-counts its cputime from the live session sum (#658, documented in `_session_cpu_advancing`), and a relaunch re-keys the session. So the design goal is: (a) eliminate the parse-induced negative (root cause), and (b) make any REMAINING negative sample carry its true meaning — "scope reset, no rate signal" — confirmed against a same-tick pcpu read before the override may fire. "Per-PID" in the Goal is realized as a per-process `pcpu` sum over the launcher's session (the same scope every other probe term uses), emitted by the SAME probe heredoc — synchronous with the tick, no second SSH roundtrip.

### 4.1 Extract + fix the awk programs (root cause)

Add two module-level PLAIN-string constants (single braces — they are interpolated into the probe f-string as values, so their braces are NOT re-processed; this removes the doubled-brace maintenance hazard from the awk bodies and makes them unit-testable):

```python
# Sums procps cumulative-CPU `time=` values (format [DD-]HH:MM:SS) for every
# process in the launcher's session. Module constant (plain string, single
# braces) so the day-format parse is unit-testable against the system awk.
# #1477 root cause: the inline n==3 branch coerced "1-02" -> 1 (awk strtod
# prefix), so a process crossing 86400 cumulative CPU-sec collapsed from
# ~86400+s to ~D*3600 + MM*60 + SS in the session sum — the sum then
# sawtooths, sampling the cross-tick rate NEGATIVE on a healthy 20-core
# worker (#1345: running-max 83824 -> 9351).
_SESSION_CPU_TIME_AWK = (
    '$1==s { '
    'n=split($2,a,":"); '
    'if (n==3) { '
    # [DD-]HH:MM:SS: with a day prefix the first ":" field is "DD-HH".
    'm=split(a[1],b,"-"); '
    'if (m==2) { secs += b[1]*86400 + b[2]*3600 + a[2]*60 + a[3] } '
    'else { secs += a[1]*3600 + a[2]*60 + a[3] } '
    '} '
    'else if (n==2) { secs += a[1]*60 + a[2] } '
    'else if (n==1) { '
    # Defensive etime-style "D-HH" (unreachable for procps cputime);
    # units-corrected in passing (b[2] is HOURS, was added as seconds).
    'm=split(a[1],b,"-"); '
    'if (m==2) { secs += b[1]*86400 + b[2]*3600 } '
    'else { secs += a[1] } '
    '} '
    '} END { '
    'if (NR==0) { print "unknown" } '
    'else { printf "%.1f", secs } '
    '}'
)

# #1477 confirm read: ps-native %cpu (cputime/realtime lifetime ratio)
# summed over the same session. SEPARATE ps invocation from the time= sum so
# a ps lacking `pcpu` degrades ONLY the new field (SESSION_CPU_SECS intact).
_SESSION_PCPU_AWK = (
    '$1==s { pc += $2 } END { '
    'if (NR==0) { print "unknown" } '
    'else { printf "%.1f", pc } '
    '}'
)
```

The corrected `n==3` math, verified: `"1-02:35:51"` → `1*86400 + 2*3600 + 35*60 + 51 = 95751.0`; `"23:17:04"` → `83824.0` (the #1345 pre-collapse running-max — monotone across the day boundary post-fix). No-day inputs are byte-identical to the old parse.

### 4.2 Rewrite `session_cpu_probe` (heredoc, `_ssh_probe`, ~L1519)

Same structure, awk bodies interpolated from the constants, plus the second pipeline reusing the already-computed `$SID`. All three exit branches emit BOTH keys:

```python
    session_cpu_probe = (
        f"if [ -f {pid_file} ]; then "
        f"  LPID=$(cat {pid_file}); "
        f"  SID=$(ps -o sess= -p $LPID 2>/dev/null | tr -d ' '); "
        f'  if [ -n "$SID" ] && [ "$SID" != "0" ]; then '
        f"    CPU_SUM=$(ps -e -o sess=,time= 2>/dev/null | "
        f"      awk -v s=\"$SID\" '{_SESSION_CPU_TIME_AWK}'); "
        f'    echo "SESSION_CPU_SECS=${{CPU_SUM:-unknown}}"; '
        f"    PCPU_SUM=$(ps -e -o sess=,pcpu= 2>/dev/null | "
        f"      awk -v s=\"$SID\" '{_SESSION_PCPU_AWK}'); "
        f'    echo "SESSION_PCPU_TOTAL=${{PCPU_SUM:-unknown}}"; '
        f'  else echo "SESSION_CPU_SECS=unknown"; echo "SESSION_PCPU_TOTAL=unknown"; fi; '
        f'else echo "SESSION_CPU_SECS=unknown"; echo "SESSION_PCPU_TOTAL=unknown"; fi; '
    )
```
