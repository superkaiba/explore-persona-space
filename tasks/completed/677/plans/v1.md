## 0.0 TL;DR

N/A — kind: infra (no behavioral construct; the §0.0 plain-English TL;DR is
for experiment results, not a code change). The plain-English summary is the
Problem/Change framing in the task body: today a CPU analysis phase that
builds a big local store runs on the shared VM and can fill the disk for
everyone (that is what happened in #658 — a 139 GB store filled root disk and
stalled the whole fleet); this change adds a concrete CPU-only GCP machine the

## 1. Goal

Make the existing size-gated CPU-off-pod rule (`CLAUDE.md` "CPU-only phases
don't hold GPU pods" → `planner.md §9` data-footprint carve-out → `critic.md`
Methodology lens item 10) **mechanically executable AND safe end-to-end**:
today the rule says a CPU/analysis phase whose local footprint exceeds
`VM_ANALYSIS_FOOTPRINT_GB_MAX = 50` GB must be "routed to a pod/GCP instance
with a big ephemeral volume," but there is no concrete intent for the planner
to name, so the rule cannot be acted on. This task adds the concrete
`cpu-bigmem` GCP intent (a CPU-only `gpu_count=0` machine type) and the
create-path + router guards that make a `gpu_count=0` GCE create succeed, then
updates the rule text to name the new intent. It ALSO closes the structural
gap that a CPU intent could be handed to the RunPod lane — which asserts
`gpu_count >= 1` and has no CPU machine — through either the capacity
fall-through (`auto_fallback_runpod`) or the GCP→RunPod workload-failover
paths (#658 sync + #659 async). After this change, a planner that estimates a
>50 GB CPU phase can write `intent: cpu-bigmem` and the GCP lane will
provision a CPU-only ephemeral instance that downloads its store from HF, runs,
uploads results, and auto-deletes — and if the GCP lane is exhausted or the
CPU workload crashes, the run surfaces a clear terminal/blocked state instead
of crashing inside the RunPod GPU-intent resolver. Motivated by the #658
incident (a 139 GB activation store filled the shared VM root disk and stalled
the whole fleet).

## 2. Prior Work

- **The rule already exists, but is un-actionable.** `CLAUDE.md` (lines 129,
  232), `planner.md §9` (data-footprint carve-out), and `critic.md` item 10
  all state the >50 GB → off-VM routing and reference `VM_ANALYSIS_FOOTPRINT_GB_MAX
  = 50` GB as THE canonical threshold. None names a concrete intent. This task
  closes that gap.
- **The GCP lane is GPU-centric but `gpu_count=0`-ready in the type system.**
  `MachineSpec` (gcp.py ~L258) already carries a `gpu_count: int` field;
  `machine_for_intent` (~L362) already resolves `machine_spec_override` dicts
  with arbitrary `gpu_count`. So a `gpu_count=0` spec is representable today; it
  is the create-path flags (`--maintenance-policy`, the accelerator-quota
  preflight), the router ladder (A100-40 / spot GPU fallback), and the two
  RunPod-bound failover/fallthrough paths that assume `gpu_count >= 1`.
- **`quota_metric_for` already fails open for unmapped kinds** (gcp.py
  L2240-2250): it does `_GPU_KIND_TO_QUOTA_METRIC.get(machine.gpu_kind)`, and
  `"CPU"` is not a key in either the on-demand or preemptible map, so it
  already returns `None`. The plan makes this explicit (`if machine.gpu_count
  == 0: return None`) for intent-documentation and to harden against a future
  map entry, but it is not strictly behavior-changing — verified by reading
  the maps at L2211 and L2228.
- **`preflight_quota_headroom` already handles `metric is None`** (gcp.py
  L2309-2311): `metric = quota_metric_for(...)`; `if metric is None: return
  None`. So the preflight probe is ALREADY skipped (fail-open "no opinion;
  proceed to launch") for a `gpu_count=0` spec — no call-site change is
  required there; the plan adds a test that pins this behavior for the CPU
  spec.
- **The router ladder skips the A100-40 rung for CPU automatically, but the
  spot rung does NOT.** `_gcp_ladder_specs` (router.py L1828) calls
  `a100_40_fallback_for_intent` which returns `None` for any intent not in
  `INTENT_A100_40_FALLBACK` (`cpu-bigmem` won't be) → no A100-40 rung. The spot
  rung is gated on `_is_short_job` → `_estimated_gpu_hours`, which floors
  gpu_count to 1 (`max(1, machine.gpu_count)`, router.py L1767) — so a SHORT CPU
  job WOULD append a spot rung without the explicit short-circuit. The plan
  short-circuits `_gcp_ladder_specs` for `gpu_count==0` to the single on-demand
  CPU rung (rationale in §4): a CPU analysis phase wants reliable on-demand, and
  spot-CPU savings are marginal vs the preemption risk to a long HF store
  download.
- **RunPod is GPU-only and would crash on a CPU intent — and TWO paths can hand
  it one.** `scripts/runpod_api.py:501` hard-asserts `gpu_count >= 1`, and
  `RunPodBackend.launch` (runpod.py L203-228) shells out to
  `pod_lifecycle.py provision --intent <spec.intent>`, which resolves the intent
  through `gpu_heuristics.INTENTS` (gpu_heuristics.py:25-74, GPU-only —
  `resolve_intent("cpu-bigmem")` raises `KeyError`). Two router paths reach
  RunPod with the original `spec.intent` preserved:
  1. **Capacity / quota fall-through** — `_auto_route` (router.py L2879) and
     `_override_free_or_gcp` (router.py L2711) call `_runpod_terminal_rung` after
     the GCP ladder returns `None`. The RunPod spec is `replace(spec, backend="runpod", ...)`
     (router.py L1995) — `intent` is unchanged, so a `cpu-bigmem` intent reaches
     RunPod.
  2. **GCP→RunPod workload-failover** — sync `_GcpWorkloadFailover` reaches the
     SAME `_runpod_terminal_rung` (router.py L2828, L2694); the async poller's
     `_failover_dead_gcp_to_runpod` (backend_poll.py L624) reconstructs a RunSpec
     via `_runspec_from_gcp_handle` (backend_poll.py L555-592), which copies
     `intent` from `handle.extra` verbatim (L586: `extra.get("intent", "lora-7b")`).
  This task adds the guard at the single shared chokepoint (`_runpod_terminal_rung`)
  for both capacity + sync-failover, and at the async predicate
  (`_is_gcp_async_workload_failure`) for the poller path.
- **The async-failover predicate keys on `handle.backend == "gcp"` + phase**
  (backend_poll.py L248-252) and does NOT today inspect the resolved machine's
  GPU count — a crashed CPU GCP VM (`terminal_workload_failed`) would match and
  attempt a RunPod re-dispatch that crashes in `resolve_intent`. The handle's
  `extra` carries `intent` + `machine_type` (gcp.py L2903, L2911) but NOT
  `gpu_count`; the plan threads `gpu_count` into the handle's `extra` (gcp.py
  L2929-2932 block) so the predicate can exclude CPU handles without a gcp
  import in the poller.
- **The `--boot-disk-gb` override already exists.** `render_create_argv`
  (gcp.py L1467) reads `spec.extra.get("boot_disk_gb") or
  config.default_boot_disk_gb` (300 GB). No new flag is needed for sweep-time
  sizing; 300 GB already covers a ~150 GB working set.

### 4.1 `src/explore_persona_space/backends/gcp.py` — the new intent + create-path guards + handle gpu_count threading

**(a) Add the `cpu-bigmem` row to `INTENT_TO_MACHINE`** (after the H100
intents, ~L324):

```python
# CPU-only analysis intent (#677) — gpu_count=0. The size-gated CPU-off-pod
# rule (CLAUDE.md "CPU-only phases don't hold GPU pods" data-footprint
# carve-out) routes a CPU/analysis phase whose local footprint exceeds
# VM_ANALYSIS_FOOTPRINT_GB_MAX=50 GB HERE instead of the shared VM. n2-highmem-16
# = 16 vCPU / 128 GB RAM — enough RAM headroom to hold a ~100-150 GB working
# set's hot slice in memory while the bulk lives on the 300 GB boot disk; n2 is
# a standard live-migratable family (maintenance-policy MIGRATE). Larger
# footprints size the boot disk up via --boot-disk-gb (no new flag) or pass a
# machine_spec_override for a bigger n2-highmem-{32,...}.
"cpu-bigmem": MachineSpec(
    machine_type="n2-highmem-16",
    gpu_count=0,
    gpu_kind="CPU",
),
```

**Machine type — `n2-highmem-16` (16 vCPU / 128 GB RAM).** Rationale:
the canonical use case (#658-class predictor-fitting / activation-store
analysis) is RAM- and disk-bound, not vCPU-bound; `n2-highmem-16` gives 128 GB
RAM (8 GB/vCPU, the highmem ratio) which comfortably holds the hot slice of a
~100-150 GB working set in memory, with the bulk on the 300 GB boot disk.
Chosen over `n2-standard-32` (32 vCPU / 128 GB — same RAM, double the vCPU we
don't need, ~2× the cost) and over `n2-highmem-8` (64 GB RAM — too tight for a
150 GB store's working set). A larger footprint is handled by the existing
`--boot-disk-gb` override (disk) and a `machine_spec_override` to
`n2-highmem-32` (256 GB RAM) at sweep time — I do NOT add a second
`cpu-bigmem-32` intent (the override path already exists and a second fixed
intent invites the same hardcoded-size staleness the boot-disk override was
built to avoid; decision recorded in §11).

**Single intent, not two.** The body asked whether to expose a second
`cpu-bigmem-32`; the decision is one intent + `machine_spec_override` for the
rare larger case. Keeps `INTENT_TO_MACHINE` and the plan-match test minimal.

**(b) `quota_metric_for` — short-circuit on `gpu_count == 0`** (gcp.py
~L2240). Add as the FIRST statement of the function body:

```python

    # CPU-only machines draw no accelerator quota (#677) — return None so the
    # fail-OPEN preflight ("no opinion; proceed") skips the accelerator-quota
    # probe entirely. (quota_metric_for already returns None for an unmapped
    # gpu_kind, so "CPU" was already None; this is the explicit, intent-
    # documenting guard that also survives a future map entry.)
    if machine.gpu_count == 0:
        return None
    if provisioning in {"SPOT", "FLEX_START"}:
        return _GPU_KIND_TO_PREEMPTIBLE_QUOTA_METRIC.get(machine.gpu_kind)
    return _GPU_KIND_TO_QUOTA_METRIC.get(machine.gpu_kind)
```

No call-site change in `preflight_quota_headroom` — it already returns `None`
when `metric is None` (L2310-2311), which IS the skip. The body's

# CAN live-migrate, and MIGRATE is gcloud's default for non-accelerator VMs —
# it lets a long CPU analysis phase survive a host-maintenance event instead
# of being killed mid-store-download.
maintenance_policy = "TERMINATE" if machine.gpu_count else "MIGRATE"

then `f"--maintenance-policy={maintenance_policy}"` in the argv list (replacing
the hardcoded `"--maintenance-policy=TERMINATE"`). `machine` is already
resolved at L1455 (`machine = machine_for_intent(spec)`). Keep

### 4.2 `src/explore_persona_space/backends/router.py` — skip the GPU fallback ladder for CPU

**`_gcp_ladder_specs` (router.py L1828) — short-circuit on `gpu_count == 0`.**
Add at the top of the function, right after `base = machine_for_intent(spec)`:

```python
base = machine_for_intent(spec)  # resolves the as-is intent (rung 1)
# CPU-only intent (#677): no GPU fallback ladder applies. The A100-40 rung is
# a "smaller GPU" fallback and the spot rungs trade preemption risk for cost on
# a SHORT job — neither makes sense for a CPU analysis phase that wants a
# reliable on-demand machine to finish a long HF store download. Yield exactly
# the single on-demand CPU rung. (Without this, _is_short_job floors gpu_count
# to 1 via max(1, machine.gpu_count) at router.py L1767, so a SHORT CPU job
# WOULD append a spot rung — the short-circuit is load-bearing, not redundant;
# §6 test 8 pins exactly this with a 1.0h budget.)
if base.gpu_count == 0:
    return [(spec, f"ondemand_{_machine_label(base)}")]
```

`_machine_label(MachineSpec(gpu_kind="CPU"))` → `"cpu"`, so the rung label is
`ondemand_cpu` (verified against `_machine_label` at router.py L1813:
`gpu_kind.lower().replace("-", "_")`).

This is the body's "SKIP the auto-router fallback ladder for `gpu_count == 0`"
made precise: it skips the A100-40 + spot RUNGS, NOT the base CPU rung (rung 1
stays — that is the actual CPU create). State explicitly: `cpu-bigmem` is its
OWN intent that bypasses the on-demand A100-80 → A100-40 → spot A100-80 → spot
A100-40 chain entirely; no GPU fallback ladder applies to a CPU machine. When
that single CPU rung capacity-misses, the lane returns `None` and the chain
reaches `_runpod_terminal_rung` — which §4.2c guards so a CPU intent does NOT
launch on RunPod.

### 4.2b `scripts/backend_poll.py` — the ASYNC GCP→RunPod failover guard for CPU handles

The async poller's `_is_gcp_async_workload_failure` (backend_poll.py L248-252)
matches ANY `backend=="gcp"` handle in a failover-eligible phase
(`terminal_workload_failed` / the two #669 wedge phases) and then
`_failover_dead_gcp_to_runpod` (L624) reconstructs a RunSpec via
`_runspec_from_gcp_handle` (L555-592, `intent` copied verbatim) and calls
`RunPodBackend.launch` → `pod_lifecycle.py provision --intent <cpu-bigmem>` →
`gpu_heuristics.resolve_intent("cpu-bigmem")` **raises `KeyError`**
(gpu_heuristics.INTENTS is GPU-only) and `runpod_api.py:501` asserts
`gpu_count >= 1`. So a crashed/wedged CPU GCP VM would attempt a structurally
broken RunPod launch.

**Guard `_is_gcp_async_workload_failure` to exclude `gpu_count==0` handles**
(backend_poll.py L248-252). The handle now carries `gpu_count` in `extra`
(§4.1(e)); add the exclusion as a conjunct:

```python
def _is_gcp_async_workload_failure(handle, result) -> bool:
    # ... existing docstring + the CPU exclusion note ...
    extra = getattr(handle, "extra", None) or {}
    if extra.get("gpu_count") == 0:
        # CPU-only GCP handle (#677): RunPod is GPU-only (resolve_intent on a
        # CPU intent KeyErrors; runpod_api asserts gpu_count >= 1), so a CPU
        # workload crash/wedge must NOT fail over. Returning False routes it to
        # the ordinary dead path -> failure_class: code -> status:blocked
        # (the watcher's capacity-retry pass re-drives only infra/
        # no_compute_available, never a code failure, so it parks cleanly).
        return False
    return (
        getattr(handle, "backend", None) == "gcp"
        and result.status == "dead"
        and result.current_phase in _GCP_ASYNC_FAILOVER_PHASES
    )
```

Place the `gpu_count==0` check BEFORE the existing `return (...)` so a CPU
handle short-circuits to `False` regardless of phase. A pre-#677 GCP handle
written before the `gpu_count` threading lands has no `gpu_count` key →
`extra.get("gpu_count")` is `None` ≠ `0` → the guard is a no-op and the handle
takes the EXISTING (GPU) failover path, exactly as today — so in-flight GPU
runs are unaffected (fail-toward-existing-behavior on a missing key).

The same falls-through-to-dead behavior means the §669 wedge-escalation
(`_maybe_escalate_gcp_wedge`, L314) can still rewrite a CPU handle's running
poll to `terminal_workload_wedged` — but the predicate then excludes it
(gpu_count==0), so the wedged CPU VM surfaces as `status: dead` /
`terminal_workload_wedged` on the ordinary path → `failure_class: code` →

## 11. Decision Rationale

Most rows are N/A — no model training. Load-bearing DESIGN choices (each is a
code/config choice, not a hyperparameter; `Source:` is gcloud docs / the task
body justification / a named design choice / the read code lines):

- **What:** `cpu-bigmem` machine type = `n2-highmem-16` (16 vCPU / 128 GB RAM).
  **Why:** the #658-class CPU analysis phase is RAM+disk-bound, not vCPU-bound;
  128 GB RAM holds the hot slice of a ~100-150 GB working set, the highmem
  ratio (8 GB/vCPU) maximizes RAM per dollar, and n2 is live-migratable.
  **Source:** design choice grounded in the #658 incident footprint (139 GB
  store) + GCP n2 machine-family docs (highmem = 8 GB/vCPU). **Alternatives:**
  `n2-standard-32` (same RAM, 2× vCPU we don't need, more cost — rejected);
  `n2-highmem-8` (64 GB RAM, too tight for a 150 GB store's working set —
  rejected); a second `cpu-bigmem-32` intent (rejected in favor of the
  existing `machine_spec_override` path to avoid hardcoded-size staleness).
- **What:** `--maintenance-policy=MIGRATE` for `gpu_count==0`, keep `TERMINATE`
  for accelerator VMs. **Why:** GPUs cannot live-migrate (gcloud rejects
  MIGRATE on accelerator VMs); a CPU VM CAN, and MIGRATE lets a long CPU phase
  survive host maintenance instead of being killed mid-store-download.
  **Source:** GCP host-maintenance docs (MIGRATE is the default non-accelerator
  policy; accelerator VMs require TERMINATE) + the existing render_create_argv
  docstring noting "gcloud rejects MIGRATE on accelerator VMs anyway".
  **Alternatives:** keep TERMINATE uniformly (rejected — needlessly kills a CPU
  phase on a maintenance event, which is exactly the long-store-download case
  we're protecting).
- **What:** keep the DLVM CUDA image for the CPU VM (no separate non-CUDA
  image). **Why:** the existing bootstrap / startup-script path works unmodified
  with the project's pre-installed toolchain; a non-CUDA image would require
  re-installing Python/torch and diverge the CPU path from the verified GPU
  bootstrap, for a marginal boot-disk saving. **Source:** design choice — no
  published source applies; trade-off stated in §4.1. **Alternatives:**
  `family/debian-12` (rejected — toolchain re-install + path divergence > a few
  GB of unused CUDA on a 300 GB disk).
- **What:** reuse the existing 300 GB `default_boot_disk_gb` + `--boot-disk-gb`
  override; no CPU-specific default, no `max(default, 200)` floor. **Why:** 300
  GB already covers a ~150 GB working set + DLVM + headroom (300 ≥ 200, so the
  floated floor is a no-op); the override already threads via
  `spec.extra["boot_disk_gb"]`. **Source:** task body §Implementation + gcp.py
  L1467. **Alternatives:** a CPU-specific `max(default, 200)` (rejected — dead
  branch, 300 already exceeds 200).
- **What:** `_gcp_ladder_specs` yields ONLY the single on-demand CPU rung for
  `gpu_count==0` (no A100-40, no spot). **Why:** A100-40 is a smaller-GPU
  fallback (meaningless for CPU) and spot trades preemption risk for cost on a
  SHORT job — a long CPU store-download wants a reliable on-demand machine; and
  because `_estimated_gpu_hours` floors gpu_count to 1, a SHORT CPU job would
  otherwise get a spot rung, so the short-circuit is load-bearing.
  **Source:** read from code (router.py L1767 `max(1, machine.gpu_count)`,
  L1865-1872 the spot-rung append) + the body's "SKIP the auto-router fallback
  ladder for `gpu_count==0`". **Alternatives:** allow a spot CPU rung for short
  CPU jobs (rejected — marginal CPU-spot savings vs preemption risk to a long
  download; can be revisited if a cheap-short-CPU use case appears).
- **What:** suppress the RunPod terminal rung for `gpu_count==0` at the router
  chokepoint `_runpod_terminal_rung`, raising the typed
  `CpuExhaustedNoRunpodLaneError` — REVISE 1.5 resolution (a), NOT (b)
  alone. **Why:** the guard fires at the router BEFORE any RunPod attempt is
  recorded, with NO `pod_lifecycle.py` subprocess spawn, and a single guard
  covers BOTH router-reached paths (capacity fall-through + sync
  `_GcpWorkloadFailover`) at the one chokepoint they share.
  (b) "fail loud at the RunPod dispatch site" is added as a NARROW
  defense-in-depth in `RunPodBackend.launch` (rejects an intent absent from
  `gpu_heuristics.INTENTS`) to cover the un-chokepointed explicit
  `backend: runpod` user-pin path, but is not the primary fix.
  **Source:** read from code (router.py L1935 `_runpod_terminal_rung`, L2828 /
  L2694 sync failover, L2879 / L2711 capacity fall-through, L1995
  `replace(spec, backend="runpod", ...)` preserving intent; runpod.py L203-228
  `launch` → `pod_lifecycle.py provision --intent`; gpu_heuristics.py:25-74
  GPU-only INTENTS; runpod_api.py:501 `gpu_count >= 1` assert) + REVISE 1.5
  reconciler direction. **Alternatives:** (b) at the RunPod site as the PRIMARY
  guard (rejected as primary — it lets the subprocess spawn / attempt be
  recorded before failing, and does not stop the router from CHOOSING RunPod;
  kept as the secondary user-pin defense).
- **What:** carry the CPU-exhausted terminal as a `NoComputeAvailableError`
  SUBCLASS (`CpuExhaustedNoRunpodLaneError`) and map it to `reason:
  cpu_exhausted_no_runpod_lane` in `classify_terminal_exception` — NOT an
  optional `reason=` token field on the base class (REVISE 2 round 2 — chose
  option (b) subclass over option (a) field). **Why:** this is the load-bearing
  fix that actually plumbs the distinct reason to the surface the watcher reads.
  The router raising a distinct reason is INERT by itself —
  `classify_terminal_exception` (issue_dispatch.py:434-442) hardcodes `reason:
  no_compute_available` for every `NoComputeAvailableError` and emits the
  constructor's first arg only as the human `detail:` line, and the watcher's
  `_is_transient_capacity_block` (autonomous_session_watch.py:6317-6332) reads
  the `epm:failure` note's `reason:` token against
  `TRANSIENT_CAPACITY_REASONS = {"no_compute_available"}` — so without this
  mapping the CPU terminal would post `reason: no_compute_available` and the
  capacity-retry pass would HOT-RETRY a structurally-unservable run in a loop
