## 0.0 TL;DR (plain English)

- **What I'll change:** two spots in the task-state library where a git hiccup from a *neighboring* session breaks a write that already succeeded — (a) posting a marker will stop reporting failure (and provoking a duplicate re-post) when only the bookkeeping commit failed, and (b) committing will briefly wait out a concurrent merge instead of crashing on git's "cannot do a partial commit during a merge".
- **What I expect:** no more triple-posted markers after index.lock collisions, and no more `new_plan_version` crashes while another session is mid-merge; a stuck merge still fails loudly with a named remedy after a bounded wait.
- **What would change my mind:** if tests show a caller that *depends* on `post_event` raising on commit failure to stay correct, I'd narrow the success-with-warning to the CLI layer instead of the library.

## 0. Plan Summary

**Change:** in `src/explore_persona_space/task_workflow.py`: (a) a new `_commit_after_durable_append()` wrapper makes the 7 append-only mutation sites (post_event, append_comment, _append_concern_event, promote, create, set_goal, new_plan_version) return success-with-loud-warning + a durable sidecar row (`~/.task-workflow/deferred-commits.jsonl`) when the git commit fails AFTER the append landed — the append is the state; the retry-provoked duplicate append (3× marker, #823 loop 2026-07-03) is the bug. Genuine append failures still raise. ## 1. Goal

Close the two concurrency seams #898 missed in the canonical task-state API: (a) a commit failure *after* a successful `events.jsonl` append propagates to the caller, whose standing retry recipe re-appends the same marker (observed 3× on a #823 loop session, 2026-07-03); (b) `git commit --only` fatals with `cannot do a partial commit during a merge` when a concurrent session's merge holds MERGE_HEAD on the shared repo root (crashed `new_plan_version` on a #911 session, 2026-07-03). Desired end-state: an already-durable append reports success (loudly warned, machine-traceable) when only its bookkeeping commit failed, and `_git_commit` waits out a transient merge with a bounded, env-tunable loop before failing loud.

### 4.1 Seam (b) — bounded merge-state wait in `_git_commit`

New constants next to `_GIT_LOCK_CONTENTION_RE` (~L4396):

```python
# `git commit --only` refuses while a merge/cherry-pick is in progress on
# THIS worktree (verified: git 2.34.1, rc=128). Signature used only for the
# single TOCTOU retry below — never added to _GIT_LOCK_CONTENTION_RE (#898's
# retry semantics stay byte-identical).
_PARTIAL_COMMIT_SEQUENCER_RE = re.compile(
    r"cannot do a partial commit during a (merge|cherry-pick)"
)
_MERGE_WAIT_ENV = "EPM_TASKPY_MERGE_WAIT_SECONDS"  # total bound; 0 disables (default 60)
_MERGE_POLL_ENV = "EPM_TASKPY_MERGE_POLL_SECONDS"  # poll interval (default 2.0)
_SEQUENCER_STATE_FILES = ("MERGE_HEAD", "CHERRY_PICK_HEAD")
```

Knob accessors `_merge_wait_bound_s()` / `_merge_poll_s()`: verbatim clones of `_rebase_wait_bound_s` / `_rebase_poll_s` (L286–306) — `float(os.environ.get(...))`, `math.isfinite` check, `ValueError` on non-finite (fail loud).

```python
def _sequencer_state_paths(repo: Path) -> list[Path]:
    """Per-worktree MERGE_HEAD/CHERRY_PICK_HEAD paths for the checkout
    _git_commit commits in. Resolved via `git rev-parse --git-path` (one
    call, one flag per file), NEVER a hardcoded `.git/` join: for a linked
    worktree (the routed managed-main case) these live under
    .git/worktrees/<name>/ and a primary-checkout merge must not stall a
    routed commit (sequencer state is per-worktree; verified probe)."""
    argv = ["rev-parse"]
    for name in _SEQUENCER_STATE_FILES:
        argv += ["--git-path", name]
    lines = _run_git(argv).stdout.splitlines()
    return [(p if p.is_absolute() else repo / p) for p in map(Path, lines)]

def _wait_for_sequencer_clear(repo: Path) -> None:
    """Bounded wait for a concurrent merge/cherry-pick on THIS checkout to
    finish before `commit --only` (git refuses a partial commit during
    either). Returns when clear; knob=0 → immediate return (today's git
    fatal then surfaces unchanged); on timeout raises RuntimeError naming
    the remedy. NEVER auto-invokes sync_repo_root.py: it takes a bounded
    flock on the task-workflow lock this process already holds."""
    bound = _merge_wait_bound_s()
    if bound <= 0:
        return
    poll = _merge_poll_s()
    deadline = time.monotonic() + bound
    announced = False
    while True:
        present = [p.name for p in _sequencer_state_paths(repo) if p.exists()]
        if not present:
            return
        if time.monotonic() >= deadline:
            raise RuntimeError(
                f"{'/'.join(present)} present on {repo} for >{bound:.0f}s; a concurrent "
                "merge/cherry-pick is stalled or crashed and `git commit --only` cannot "
                "run during one. Finish or abort it, or run "
                "`uv run python scripts/sync_repo_root.py` (aborts a STALE husk past "
                f"EPM_ROOT_SYNC_HUSK_AGE_S). Tune via {_MERGE_WAIT_ENV} (0 disables)."
            )
        if not announced:
            _log.warning(
                "waiting up to %.0fs for a concurrent merge on %s to clear (%s present)",
                bound, repo, ", ".join(present),
            )
            announced = True
        time.sleep(poll)
```

Wiring inside `_git_commit` (L4474–4532):

1. After the `TASK_PY_NO_COMMIT` early return and `repo = repo_root()` (L4505): `_wait_for_sequencer_clear(repo)` — **before staging**, so the whole add→diff→commit sequence runs post-clear (tests with `TASK_PY_NO_COMMIT=1` are untouched).
2. TOCTOU closure — a merge can *start* between the probe and the commit. Wrap only the final commit (L4527):

```python
try:
    _run_git(["commit", "-m", full_msg, "--only", "--", *rel_paths])
except subprocess.CalledProcessError as e:
    if not _PARTIAL_COMMIT_SEQUENCER_RE.search(e.stderr or ""):
        raise
    _wait_for_sequencer_clear(repo)   # one re-wait; raises on timeout
    _run_git(["commit", "-m", full_msg, "--only", "--", *rel_paths])  # FINAL attempt
```

The routed-mode `old_sha` (L4525) stays valid across the retry (a failed commit never moves HEAD; a concurrent `main` move is already caught loud by `_advance_main_ref`'s CAS, L653–663). A second sequencer fatal after the re-wait propagates (fail fast). REVERT_HEAD is a deliberate exclusion — nothing in the fleet's tooling runs `git revert`; noted in the constant's comment so a future case is a one-token addition.

**Why in `_git_commit` and not `_run_git`'s retry regex:** the #898 retry is a single 2–3 s jittered sleep — the wrong shape for a merge window (needs a deadline loop), and the brief forbids regressing #898's carefully pinned semantics. All 16 `_git_commit` call sites (incl. `set_status`) inherit the wait automatically.

### 4.2 Seam (a) — `_commit_after_durable_append()` for the append-only sites

New constant near `LOCK_PATH` (L728–729): `DEFERRED_COMMITS_LOG = LOCK_DIR / "deferred-commits.jsonl"` (outside the repo: recording a commit failure must not itself need a commit; beside the flock every writer already owns).

```python
def _commit_after_durable_append(
    paths: list[Path], message: str, *, task_id: int, op: str
) -> bool:
    """Commit bookkeeping for an ALREADY-DURABLE append-only mutation.

    The append IS the state (an events/comments/concerns row, a created task
    dir, plans/vN.md); the commit is bookkeeping the next successful commit
    of the same file sweeps up (git commits file STATE, not deltas). Raising
    here makes callers retry the WHOLE mutation and duplicate the append —
    the 2026-07-03 3x-marker incident; same rc-contract family as
    _safe_echo/#537. So a commit failure after a successful append LOGS AT
    ERROR, appends a machine-visible row to
    ~/.task-workflow/deferred-commits.jsonl, and returns False; the caller
    returns success. Append failures are untouched — they raise BEFORE this
    runs. Deliberately NOT used by set_status (#898 raise semantics + its
    documented ghost-sweep recovery) nor the idempotent setters (retrying
    those is already safe and duplicates nothing).
    """
    try:
        _git_commit(paths, message)
        return True
    except (subprocess.CalledProcessError, RuntimeError) as e:
        # CalledProcessError: git add/commit failed (e.g. lock contention that
        # survived _run_git's one retry). RuntimeError: _git_commit's own git
        # layer — the sequencer-wait timeout, _git_quiet CAS in
        # _advance_main_ref. Genuine bugs (TypeError, ...) still propagate.
        stderr_tail = (getattr(e, "stderr", "") or str(e))[-500:]
        _log.error(
            "task #%d: %s applied DURABLY (append landed) but the git commit "
            "failed: %s: %s. Do NOT re-run the mutation (it would duplicate the "
            "append); the next successful commit touching these paths sweeps it. "
            "Recorded in %s. Manual sweep: git add -- <paths> && git commit.",
            task_id, op, type(e).__name__, stderr_tail, DEFERRED_COMMITS_LOG,
        )
        row = {
            "ts": _utcnow_iso(), "task_id": task_id, "op": op,
            "paths": [str(p) for p in paths], "message": message,
            "error": type(e).__name__, "stderr_tail": stderr_tail,
        }
        try:
            _append_jsonl_line(DEFERRED_COMMITS_LOG, row)
        except OSError:
            # Trace-write failure must not resurrect the duplicate-append bug;
            # the ERROR log above already carries the full story.
            _log.exception("could not record deferred-commit row")
        return False
```

**Converted call sites (7)** — each replaces its bare `_git_commit(...)` with `_commit_after_durable_append(..., task_id=task_id, op="<name>")`; return values/flow otherwise unchanged:

**Caller-side story.** `scripts/task.py cmd_post_event` needs **no code change**: `post_event` now returns normally in the deferred case, `_safe_echo` prints the payload, rc=0 — the CLAUDE.md "retry once" recipe never fires, and the `codex_task.py` retry-then-orphaned-markers path now triggers only on genuine append failures. ## 7. Risks and failure modes

| Risk | Likelihood | Mitigation |
|---|---|---|
| **Warning swallowed forever** — a deferred marker on a task that never mutates again stays uncommitted (invisible to other clones/dashboard-remote) | Low (tasks accrue many markers; the fleet commits the shared root constantly) | ERROR log + durable sidecar row; next mutation of the same file auto-sweeps (git commits file state); end-of-session `git status` rule catches stragglers |
| **Masking a durably-broken git** — if git is persistently broken, every append-site mutation now "succeeds" while the repo silently stops committing | Low | per-occurrence ERROR (not once-deduped); sidecar rows accumulate as an audit trail; `set_status` + idempotent setters still raise, so a broken git surfaces within a few mutations anyway |
| **Stale MERGE_HEAD deadlock** — conflicted/crashed merge never clears | Medium (it happened 07-03) | wait is bounded (60 s default); loud RuntimeError names `sync_repo_root.py` (whose stale-husk `merge --abort` is the actual fixer); knob=0 escape hatch |
| **Flock held during the wait** — up to 60 s stall for ALL concurrent task.py writers, incl. routed ones the merge doesn't even affect | Medium | bounded + env-tunable; direct precedent: #996 waits up to 120 s inside the same resolution path; the alternative (crash) costs a duplicate-append incident instead |
| **Deadlock via auto-invoking sync_repo_root from inside `_locked()`** | — | designed out: never auto-invoked (it flocks the same task-workflow lock, `EPM_ROOT_SYNC_LOCK2_WAIT_S`); manual-remedy-in-message only |

## 11. Decision Rationale

Hyperparameter table: **N/A — no training hyperparameters** (kind: infra).

- **Library-side success-with-warning (vs caller-side tail-check).** What: catch commit failure after a durable append in a shared wrapper; report success. Why: removes the retry trigger at its source for every caller (CLI, library, humans following the CLAUDE.md recipe) instead of patching one retry loop; a tail-check can't distinguish "my earlier append" from a concurrent same-kind marker without adding a nonce to the marker schema (which WOULD be architectural). Source: in-repo precedent `scripts/task.py::_safe_echo` L93–105 (#537 — identical rc-contract reasoning one layer up) + the task Goal's first branch. Alternative rejected: tail-check-before-re-post (fragile, caller-by-caller, schema pressure).
- **Scope = the 7 append-only sites, not all 16 commit sites.** Why: only appends duplicate on retry; idempotent setters retry safely today, and `set_status` has #898's deliberately different raise+reconcile contract the brief forbids regressing. Source: #898 tests L3370+ and set_status docstring L3080–3092.
- **Sidecar at `~/.task-workflow/deferred-commits.jsonl`.** Why: recording a commit failure must not itself require a commit (recursion); the dir is the one location every task.py writer already owns (the flock lives there); survives worktree/branch churn. Source: `LOCK_DIR` precedent L728. Alternative rejected: `tasks/<N>/artifacts/` (needs a commit to be durable-shared; in-repo path resolution is exactly what's failing).
- **Catch `(CalledProcessError, RuntimeError)` in the wrapper.** Why: those are the two exception classes `_git_commit`'s git layer emits (`_run_git` check=True; `_git_quiet` CAS; the new wait timeout); genuine code bugs (TypeError etc.) still propagate — fail-fast preserved. Source: read of `_git_commit`/`_git_quiet`/`_advance_main_ref` L4474–4532, L560–575, L653–663.
- **Wait lives in `_git_commit`, mirrors #996.** What: bounded deadline loop, env knobs, `math.isfinite` validation, `0` disables. Why: `_run_git`'s single 2–3 s jittered retry is the wrong shape for a seconds-scale-but-variable merge window, and touching `_GIT_LOCK_CONTENTION_RE` risks the #898 semantics; a pre-staging loop covers all 16 call sites at once. Source: #996 (`_rebase_wait_bound_s` L286–306, wait loop L394+) — the same seam class (concurrent git op on the shared root), already reviewed and shipped.
- **Default bound 60 s, poll 2 s.** Why: the legitimate transient window (clean auto-merge) is seconds (A4), so 60 s covers it with ~10× margin; a conflicted merge never self-clears, so a longer wait only extends the flock hold that stalls every other task.py writer (including routed commits the merge can't even block, A3); #996 chose 120 s for rebases, which replay many commits — a merge commits once, so half. Poll 2 s = #996's poll and sync_repo_root's `INDEX_LOCK_POLL_S`. Source: #996 + `sync_repo_root.py` L136–137; env-overridable either way.
- **`--git-path` resolution (not `.git/MERGE_HEAD` hardcode).** Why: routed-mode commits happen in the managed linked worktree, where sequencer state lives under `.git/worktrees/<name>/`; a hardcode would false-stall routed commits on a primary-checkout merge for the full bound. Source: local probe (A3) + `_is_routed_root` L547–557.
- **CHERRY_PICK_HEAD included, REVERT_HEAD excluded.** Why: cherry-pick provably triggers the same fatal (A2) and costs one tuple entry; revert is unused by any fleet tooling — excluded to keep the tested surface minimal, with a comment marking the extension point. Source: local probe + grep (no `git revert` in scripts/ or src/).
- **No auto-invocation of `sync_repo_root.py`.** Why: it takes a bounded second flock on the very task-workflow lock the caller holds → guaranteed lock-wait failure; and shelling a mutating recovery tool from inside a library mutation inverts the recovery layering. Source: `acquire_task_workflow_lock` L416 + exit-code contract L33–45. It is instead NAMED in the timeout message (it already owns the stale-MERGE_HEAD abort).
