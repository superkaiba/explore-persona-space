## 0.0 TL;DR (plain English)

- **What I'll change:** two spots in the task-state library where a git hiccup from a *neighboring* session breaks a write that already succeeded — (a) posting a marker will stop reporting failure (and provoking a duplicate re-post) when only the bookkeeping commit failed **and the write is already durable**, and (b) committing will briefly wait out a concurrent merge instead of crashing on git's "cannot do a partial commit during a merge".
- **What I expect:** no more triple-posted markers after index.lock collisions, and no more `new_plan_version` crashes while another session is mid-merge; a stuck merge, a routed-worktree failure, or a genuine bug still fails loudly.
- **What would change my mind:** if tests show the routed-mode raise path makes a common production flow noisier than today, I'd revisit committing-before-deferral in routed mode rather than widening the deferral.

## 1. Goal

Close the two concurrency seams #898 missed in the canonical task-state API: (a) a commit failure *after* a successful `events.jsonl` append propagates to the caller, whose standing retry recipe re-appends the same marker (observed 3× on a #823 loop session, 2026-07-03); (b) `git commit --only` fatals with `cannot do a partial commit during a merge` when a concurrent session's merge holds MERGE_HEAD on the shared repo root (crashed `new_plan_version` on a #911 session, 2026-07-03). Desired end-state: an already-durable append reports success (loudly warned, machine-traceable) when only its bookkeeping commit failed **and durability actually holds** (primary checkout, pre/at-commit failure); `_git_commit` waits out a transient merge with a bounded, env-tunable loop before failing loud; every failure class where durability is NOT guaranteed (routed mode, post-commit CAS, genuine bugs, append failures) still raises.

### 4.1 Seam (b) — bounded merge-state wait in `_git_commit` + `SequencerWaitTimeout`

New constants + exception next to `_GIT_LOCK_CONTENTION_RE` (~L4396):

```python
# `git commit --only` refuses while a merge/cherry-pick is in progress on
# THIS worktree (verified: git 2.34.1, rc=128). Signature used only for the
# single TOCTOU retry below — never added to _GIT_LOCK_CONTENTION_RE (#898's
# retry semantics stay byte-identical). NOTE: do NOT "simplify" the wait by
# dropping --only under a merge — a plain `git commit` during a merge would
# CREATE THE MERGE COMMIT, sweeping the entire shared index and completing
# the concurrent session's merge on its behalf.
_PARTIAL_COMMIT_SEQUENCER_RE = re.compile(
    r"cannot do a partial commit during a (merge|cherry-pick)"
)
_MERGE_WAIT_ENV = "EPM_TASKPY_MERGE_WAIT_SECONDS"  # total bound; 0 disables (default 60)
_MERGE_POLL_ENV = "EPM_TASKPY_MERGE_POLL_SECONDS"  # poll interval (default 2.0)
_SEQUENCER_STATE_FILES = ("MERGE_HEAD", "CHERRY_PICK_HEAD")


class SequencerWaitTimeout(RuntimeError):
    """A concurrent merge/cherry-pick did not clear within the bound.

    Narrow, named class so (a) _commit_after_durable_append can defer on it
    WITHOUT catching bare RuntimeError (which would wrongly defer the routed
    post-commit CAS failure — _git_quiet raises RuntimeError), and (b)
    set_status's #898 recovery envelope can name it alongside
    CalledProcessError.
    """
```

Knob accessors `_merge_wait_bound_s()` / `_merge_poll_s()`: verbatim clones of `_rebase_wait_bound_s` / `_rebase_poll_s` (L286–306) — `float(os.environ.get(...))`, `math.isfinite` check, `ValueError` on non-finite. Accessor comment pins the ordering: **default 60 s is deliberately < `EPM_ROOT_SYNC_LOCK2_WAIT_S` (120 s)**, so a manually-started `sync_repo_root.py` waiting on the task-workflow lock outlasts any task.py writer mid-merge-wait instead of timing out behind it.

```python
def _sequencer_state_paths(repo: Path) -> list[Path]:
    """Per-worktree MERGE_HEAD/CHERRY_PICK_HEAD paths for the checkout
    _git_commit commits in. Resolved via `git rev-parse --git-path` (one
    call, one flag per file), NEVER a hardcoded `<root>/.git/` join: for a
    linked worktree (the routed managed-main case) `.git` is a FILE and the
    real state lives under <common>/.git/worktrees/<name>/ — the hardcode
    would both miss a merge in the worktree itself AND false-probe the
    primary's (verified probe; per-worktree state)."""
    argv = ["rev-parse"]
    for name in _SEQUENCER_STATE_FILES:
        argv += ["--git-path", name]
    lines = _run_git(argv).stdout.splitlines()
    return [(p if p.is_absolute() else repo / p) for p in map(Path, lines)]

def _wait_for_sequencer_clear(repo: Path) -> None:
    """Bounded wait for a concurrent merge/cherry-pick on THIS checkout to
    finish before `commit --only` (git refuses a partial commit during
    either). Returns when clear; knob=0 → immediate return (today's git
    fatal then surfaces unchanged); on timeout raises SequencerWaitTimeout.
    NEVER auto-invokes sync_repo_root.py: it takes the task-workflow lock
    (_run_locked, L1251) this process already holds."""
    bound = _merge_wait_bound_s()
    if bound <= 0:
        return
    poll = _merge_poll_s()
    state_paths = _sequencer_state_paths(repo)  # resolved ONCE; paths are stable
    deadline = time.monotonic() + bound
    announced = False
    while True:
        present = [p.name for p in state_paths if p.exists()]
        if not present:
            return
        if time.monotonic() >= deadline:
            raise SequencerWaitTimeout(
                f"{'/'.join(present)} present on {repo} for >{bound:.0f}s; a concurrent "
                "merge/cherry-pick is stalled or crashed and `git commit --only` cannot "
                "run during one. Finish or abort it, or run "
                "`uv run python scripts/sync_repo_root.py` (aborts a STALE husk past "
                f"EPM_ROOT_SYNC_HUSK_AGE_S). Tune via {_MERGE_WAIT_ENV} (0 disables)."
            )
        if not announced:
            _log.warning(
                "waiting up to %.0fs for a concurrent merge on %s to clear (%s present)",
                bound, repo, ", ".join(present),
            )
            announced = True
        time.sleep(poll)
```

Wiring inside `_git_commit` (L4474–4532):

1. After the `TASK_PY_NO_COMMIT` early return and `repo = repo_root()` (L4505): `_wait_for_sequencer_clear(repo)` — **before staging**, so the whole add→diff→commit sequence runs post-clear (tests with `TASK_PY_NO_COMMIT=1` untouched). All **17** `_git_commit` call sites inherit the wait automatically.
2. TOCTOU closure — a merge can *start* between the probe and the commit. Wrap only the final commit (L4527):

```python
try:
    _run_git(["commit", "-m", full_msg, "--only", "--", *rel_paths])
except subprocess.CalledProcessError as e:
    if not _PARTIAL_COMMIT_SEQUENCER_RE.search(e.stderr or ""):
        raise
    _wait_for_sequencer_clear(repo)   # one re-wait; raises SequencerWaitTimeout on timeout
    _run_git(["commit", "-m", full_msg, "--only", "--", *rel_paths])  # FINAL attempt
```

The routed-mode `old_sha` (L4525) stays valid across the retry (a failed commit never moves HEAD; a concurrent `main` move is caught loud by `_advance_main_ref`'s CAS, L653–663). A second sequencer fatal after the re-wait propagates (fail fast). REVERT_HEAD is a deliberate exclusion — nothing in the fleet's tooling runs `git revert`; the constant's comment marks the extension point.

**Why in `_git_commit` and not `_run_git`'s retry regex:** the #898 retry is a single 2–3 s jittered sleep — the wrong shape for a merge window (needs a deadline loop), and the brief forbids regressing #898's carefully pinned stderr-signature semantics.

**MF-1 — `set_status` keeps its #898 recovery envelope on the new path.** Broaden L3252 from `except subprocess.CalledProcessError:` to `except (subprocess.CalledProcessError, SequencerWaitTimeout):` — the "status move is DURABLY APPLIED … reconciled by the NEXT set_status" ERROR log fires, then **re-raise as today**. This does NOT convert `set_status` to deferred behavior; it only ensures the sequencer-timeout, which is raised from inside `_git_commit` within the L3224–3251 try, gets the same narration a plain git failure gets. (The early-return re-sync commit at L3115 stays outside any envelope: no move happened there, the registry re-sync is durable, and a raise-and-retry is safe.)

### 4.2 Seam (a) — `_commit_after_durable_append()` for the append-only sites

New constant near `LOCK_PATH` (L728–729): `DEFERRED_COMMITS_LOG = LOCK_DIR / "deferred-commits.jsonl"` (outside the repo: recording a commit failure must not itself need a commit; beside the flock every writer already owns). **The sidecar is forensic-only** — nothing reads it automatically in this task; it exists so a human (or a future `/daily` sweep follow-up — deliberately NOT built here, scope) can audit deferrals. It records `paths + message + error`, NOT the payload — the payload's durable home is the appended file itself, which is exactly why deferral is only legal when that file's append is genuinely durable (below).

```python
def _commit_after_durable_append(
    paths: list[Path], message: str, *, task_id: int, op: str
) -> bool:
    """Commit bookkeeping for an ALREADY-DURABLE append-only mutation.

    On the PRIMARY checkout the append IS the state (an events/comments/
    concerns row, a created task dir, plans/vN.md); the commit is
    bookkeeping the next successful commit of the same file sweeps up (git
    commits file STATE, not deltas). Raising makes callers retry the WHOLE
    mutation and duplicate the append — the 2026-07-03 3x-marker incident;
    same rc-contract family as _safe_echo/#537. So a PRE/AT-commit failure
    after a successful append LOGS AT ERROR, appends a forensic row to
    ~/.task-workflow/deferred-commits.jsonl, and returns False; the caller
    returns success.

    Deferral is NARROW by design (MF-4):
      * catches ONLY (CalledProcessError, SequencerWaitTimeout) — NEVER bare
        RuntimeError: the routed post-commit CAS leg (_advance_main_ref →
        _git_quiet) raises RuntimeError, and deferring THAT would report
        success for an append that never reached canonical `main`;
      * NEVER defers in ROUTED mode: there the append lives only in the
        managed worktree's working tree, and the next resolver re-sync runs
        `reset --hard main` (L642) whose safety contract is "every mutation
        commits before releasing" — an uncommitted deferred line would be
        PHYSICALLY DELETED. In routed mode any commit failure re-raises
        (fail loud; the caller's retry is then genuinely non-duplicating
        ONLY after a fresh resolve — the raise is the honest signal).
    Append failures are untouched — they raise BEFORE this runs. Genuine
    bugs (TypeError, AttributeError, ...) propagate: they match neither
    caught class. Deliberately NOT used by set_status (#898 raise+ghost-
    sweep semantics, extended per MF-1) nor the idempotent setters.
    """
    try:
        _git_commit(paths, message)
        return True
    except (subprocess.CalledProcessError, SequencerWaitTimeout) as e:
        if _is_routed_root(repo_root()):
            raise  # routed append is NOT durable against the L642 reset — no deferral
        stderr_tail = (getattr(e, "stderr", "") or str(e))[-500:]
        _log.error(
            "task #%d: %s applied DURABLY (append landed) but the git commit "
            "failed: %s: %s. Do NOT re-run the mutation (it would duplicate the "
            "append); the next successful commit touching these paths sweeps it. "
            "Recorded in %s. Manual sweep: git add -- <paths> && git commit.",
            task_id, op, type(e).__name__, stderr_tail, DEFERRED_COMMITS_LOG,
        )
        row = {
            "ts": _utcnow_iso(), "task_id": task_id, "op": op,
            "paths": [str(p) for p in paths], "message": message,
            "error": type(e).__name__, "stderr_tail": stderr_tail,
        }
        try:
            _append_jsonl_line(DEFERRED_COMMITS_LOG, row)
        except OSError:
            # Trace-write failure must not resurrect the duplicate-append bug;
            # the ERROR log above already carries the full story.
            _log.exception("could not record deferred-commit row")
        return False
```

**Routed-mode durability story (MF-4, explicit).** Failure phases in `_git_commit` and their handling:

| Phase | Failure class | Primary checkout | Routed mode |
|---|---|---|---|
| sequencer wait timeout (pre-staging or TOCTOU re-wait) | `SequencerWaitTimeout` | defer (append durable on main-checkout working tree; swept later) | **raise** (routed guard) |
| `git add` / `diff` / `commit` (pre/at-commit) | `CalledProcessError` | defer | **raise** (routed guard) |
| post-commit `rev-parse HEAD` (routed-only leg, L4529) | `CalledProcessError` | n/a (leg doesn't run) | **raise** (routed guard) |
| post-commit CAS `_advance_main_ref` (routed-only, L4530) | `RuntimeError` from `_git_quiet` | n/a | **raise** (never-bare-RuntimeError — not caught even without the routed guard) |
| genuine bug anywhere | `TypeError`/`AttributeError`/… | raise | raise |

Two independent layers guarantee "deferral ⇒ durable": the narrow catch tuple (kills the CAS case by class) and the routed re-raise guard (kills every routed case by mode, including the pre-commit one the L642 reset would delete and the post-commit `rev-parse` `CalledProcessError`). A separate `PostCommitSyncError` wrapper class was considered and dropped as redundant given both layers (§11). The L642 safety comment's invariant — "every mutation commits before releasing" — is therefore preserved verbatim in routed mode: routed mutations either commit+CAS or raise; only the primary checkout, where nothing ever resets the working tree, may run dirty-until-swept.

## 7. Risks and failure modes

| Risk | Likelihood | Mitigation |
|---|---|---|
| **Warning swallowed forever** — a deferred marker on a task that never mutates again stays uncommitted (invisible to other clones / remote dashboard) | Low (tasks accrue many markers; the fleet commits the shared root constantly) | ERROR log + forensic sidecar row; next mutation of the same file auto-sweeps (git commits file state); end-of-session `git status` rule; a future /daily sidecar sweep is noted as a follow-up, deliberately not built here |
| **Masking a durably-broken git** — persistent git breakage makes append-site mutations "succeed" while the repo stops committing | Low | per-occurrence ERROR (not deduped); sidecar rows accumulate; `set_status` + idempotent setters still raise, so broken git surfaces within a few mutations |
| **Routed-mode data loss via L642 `reset --hard main`** (the MF-4 hazard) | — | designed out: wrapper re-raises on `_is_routed_root()` (pre-commit AND post-commit classes), and never catches bare `RuntimeError` (CAS class); pinned by tests 9–11; the L642 "every mutation commits before releasing" invariant holds verbatim in routed mode |
| **Stale MERGE_HEAD deadlock** — conflicted/crashed merge never clears | Medium (happened 07-03) | bounded wait (60 s default); loud `SequencerWaitTimeout` names `sync_repo_root.py` (whose stale-husk `merge --abort` is the actual fixer); knob=0 escape hatch |
| **Flock held during the wait** — up to 60 s stall for concurrent task.py writers, incl. routed ones the merge doesn't affect | Medium | bounded + env-tunable; 60 < `EPM_ROOT_SYNC_LOCK2_WAIT_S` (120) so a manual recovery run still acquires the lock; precedent #996 waits up to 120 s in the same resolution path |
| **Deadlock via auto-invoking sync_repo_root from inside `_locked()`** | — | designed out: never auto-invoked (it flocks the same lock in `_run_locked`, L1251); manual-remedy-in-message only |
| **TOCTOU residue** — merge starts between re-wait and final commit | Very low (window ≪ 1 s) | second fatal propagates; wrapped sites defer it on primary / raise routed; `set_status` raises with the recovery log |
| **`rev-parse --git-path` multi-flag argv shape differs across git versions** | Very low | tests 20–21 exercise it against the real git binary; fallback = two single-flag calls (§10 free deviation) |

## 11. Decision Rationale

Hyperparameter table: **N/A — no training hyperparameters** (kind: infra).

- **Library-side success-with-warning (vs caller-side tail-check).** What: catch commit failure after a durable append in a shared wrapper; report success. Why: removes the retry trigger at its source for every caller (CLI, library, humans following the CLAUDE.md recipe); a tail-check can't distinguish "my earlier append" from a concurrent same-kind marker without a nonce in the marker schema (which WOULD be architectural). Source: in-repo precedent `scripts/task.py::_safe_echo` L93–105 (#537) + the task Goal. Alternative rejected: tail-check-before-re-post.
- **Narrow catch tuple `(CalledProcessError, SequencerWaitTimeout)` + routed re-raise guard (MF-4).** What: a named `SequencerWaitTimeout(RuntimeError)` for the wait timeout; the wrapper never catches bare `RuntimeError`; any caught failure re-raises when `_is_routed_root()`. Why: bare-RuntimeError catching would defer the routed post-commit CAS failure (`_git_quiet`, L560–578) — an append that never reached canonical `main` and that the next resolver `reset --hard main` (L642) physically deletes; the routed guard additionally covers the routed pre-commit case (same reset hazard) and the routed post-commit `rev-parse` `CalledProcessError`. Two independent layers, each sufficient for the CAS case, jointly sufficient for all routed cases. Source: read of L560–578, L637–642, L4525–4532; critic MF-4. Alternative rejected: a third `PostCommitSyncError` wrapper class inside `_git_commit` — redundant once (i) bare RuntimeError is never caught and (ii) routed mode never defers (post-commit legs exist ONLY in routed mode); fewer moving parts wins.
- **Routed mode raises rather than "commit-anyway then defer CAS".** Why: attempting to make routed deferral safe (commit on detached HEAD, defer only the CAS) would leave `main` and the managed worktree divergent — exactly the split-brain `_advance_main_ref`'s loud CAS exists to prevent (L653–663). The honest signal is a raise; the incident population (3× marker, MERGE_HEAD crash) was primary-checkout anyway. Source: `_advance_main_ref` docstring.
- **Scope = the 7 append-only sites, not all 17 commit sites.** Why: only appends duplicate on retry; the setters retry safely (add_tag/remove_tag early-return before committing on retry, leaving a benign dirty file a later commit sweeps — stated precisely in §4.2), and `set_status` keeps #898's deliberately different raise+reconcile contract, now extended to the sequencer-timeout class per MF-1. Source: #898 tests L3370+, set_status L3080–3126, L3252.
- **`set_status` envelope broadened, not deferred (MF-1).** What: L3252 `except (subprocess.CalledProcessError, SequencerWaitTimeout):` — same log, same re-raise. Why: the recovery narration ("DURABLY APPLIED … swept by the NEXT set_status") is load-bearing operator guidance; a `SequencerWaitTimeout` raised from `_git_commit` inside the L3224–3251 try would otherwise skip it while the transition is already durably applied. Source: L3200–3269 + critic MF-1.
- **Sidecar at `~/.task-workflow/deferred-commits.jsonl`, forensic-only.** Why: recording a commit failure must not itself require a commit (recursion); the dir is the one location every writer already owns (the flock lives there). No auto-reader in this task (reconciler-ruled scope); a /daily sweep is the named follow-up. Source: `LOCK_DIR` precedent L728. Alternative rejected: `tasks/<N>/artifacts/` (needs a commit to be durable-shared).
- **Wait lives in `_git_commit`, mirrors #996.** What: bounded deadline loop, env knobs, `math.isfinite` validation, `0` disables; state paths resolved ONCE before the loop (stable per checkout; saves a subprocess per poll). Why: `_run_git`'s single 2–3 s jittered retry is the wrong shape for a merge window, and touching `_GIT_LOCK_CONTENTION_RE` risks #898 semantics; a pre-staging loop covers all 17 call sites at once. Source: #996 (L286–306, L394+).
- **Default bound 60 s, poll 2 s.** Why: the legitimate transient window (clean auto-merge) is seconds (A4) → 60 s is ~10× margin; a conflicted merge never self-clears, so longer waits only extend the flock hold; #996 chose 120 s for rebases (replay many commits; a merge commits once) → half; and 60 < `EPM_ROOT_SYNC_LOCK2_WAIT_S` (120) keeps the manual recovery tool able to win the lock behind a waiting writer. Poll 2 s = #996's poll and sync_repo_root's `INDEX_LOCK_POLL_S`. Source: #996 + sync_repo_root L136–137, L161–163; env-overridable.
- **`--git-path` resolution (not `<root>/.git/` hardcode).** Why: in a linked worktree `.git` is a FILE — a hardcode both false-probes the primary's state and (the MF-2 mutant) misses a merge in the worktree itself, leaving the #911 fatal alive on the routed path; test 21 is the discriminating positive cell. Source: local probe (A3) + `_is_routed_root` L547–557.
- **Never a plain (non-`--only`) commit as the "fix".** A full `git commit` during a merge would CREATE the merge commit — sweeping the entire shared index and completing the concurrent session's merge on its behalf. The wait is the only correct shape; comment pinned in the code (§4.1). Source: git semantics of committing with MERGE_HEAD present.
- **CHERRY_PICK_HEAD included, REVERT_HEAD excluded.** Why: cherry-pick provably triggers the same fatal (A2) at one tuple entry's cost; revert is unused by fleet tooling — excluded, extension point commented. Source: local probe + grep.
- **No auto-invocation of `sync_repo_root.py`.** Why: it takes the task-workflow lock in `_run_locked()` (L1251) that the caller holds → guaranteed lock-wait failure; and shelling a mutating recovery tool from inside a library mutation inverts the recovery layering. Source: L1245–1260 + exit-code contract L33–45. It is NAMED in the timeout message instead (it owns the stale-MERGE_HEAD abort).
