## Requirement

Make an hf-xet download read-hang DETECTABLE from outside the process, and stop
`snapshot_download(allow_patterns=...)` being reached for on the ~1M-file data repo.

The #1739 signature to eliminate: a detached HF transfer that is frozen is
**indistinguishable from a healthy one** — near-zero CPU, zero-byte log, one open
socket, empty target, no error, no exit, indefinitely. Two jobs, ~90 min lost.

### The precise gap (deliverable 1)

`code-style.md:50` carries a canonical progress-line convention —
`[<phase>] unit k/N <key> elapsed=<s>s`, flushed — but its trigger set is
**(T1) projected wall-time > ~1h OR (T2) unit count > ~50**. Both are keyed on loop SIZE.
The #1739 hangs were: store staging, a handful of large files (hung 32 min); quarantine
relocation, 0.16 GB total (hung 57 min). Neither trips either trigger.

An hf-xet hang is a per-FILE stall, not a long loop, so a size-keyed trigger structurally
cannot fire on it. **The requirement must key on the TRANSFER, at any file count.** That is
the load-bearing new claim; the Methodology lens verified it against `code-style.md:50`
verbatim and confirmed no other convention covers it.

`upload-policy.md:289` already states the other half ("retry absorbs RAISED transients
only — the hf-xet HANG class (no exception…)"), so the repo already knows retry cannot catch
this; nothing yet requires the observability that would.

### D1 — `.claude/rules/upload-policy.md`: new § "Detached HF transfers: timeout + observable progress"

The primary deliverable. Requires, for any HF transfer that runs detached / backgrounded /
outside a turn's own foreground (upload or download, **any file count**):

- **(a) A wall-clock timeout** bounding the whole transfer. Explicitly: the
  `EPM_HF_RETRY_BUDGET_S` retry budget is NOT a timeout — it bounds RAISED transients, and
  the hang raises nothing. Per-file `stage_hub_file` budgets are per-call, so an N-file
  prefix can serially burn ~N × budget without any single call exceeding it.
  **SIZING BASIS — required, one sentence, never a guessed constant** (Methodology Must-Fix 3):
  the bound derives from projected bytes ÷ measured-or-expected throughput at ≥2× margin (the
  standing fence convention, `plan-compute-sizing.md` § per-cell fences) AND must exceed the
  transfer's legitimate retry-budget exposure (~N files × `EPM_HF_RETRY_BUDGET_S`, default
  1800 s, `hub.py:1221-1223`). Rationale: a guessed fence killing healthy work is a
  demonstrated incident class (#1092, guessed `timeout 3000s` killed a healthy run, exit=124),
  and a "generous" 1 h constant would kill a legitimately-retrying multi-file staging under a
  429 storm. A failure path worse than the status quo is not an acceptable price for
  detectability.
- **(b) Periodic flushed progress**, reusing the `code-style.md:50` canonical shape
  `[<phase>] unit k/N <key> elapsed=<s>s` — with the trigger widened: a detached HF transfer
  owes progress **regardless of file count or projected wall-time**, because the failure is a
  per-file stall (the size-keyed T1/T2 triggers cannot fire on it).
- **(c) Completion keyed on process exit with a captured rc** — never on file existence and
  never on a non-empty log. The HF-transfer instance of the standing CLAUDE.md § Monitoring
  re-run discipline and the #825 empty-dir false-DONE class.
- **(d) The invariant:** *0-byte log + empty target must not be a reachable "looks healthy"
  state.* If a transfer can present that way, it is missing (a)–(c). **This binds from the
  transfer's FIRST instruction, not from its first network response** — see D3's split entry
  line.
- **(e) One worker per `local_dir`** — the body's out-of-scope concurrency hazard, one line
  here (two concurrent `snapshot_download` calls into one `local_dir`, as #1739 also did).
  Cross-links the #833 entry's existing "ONE staging process" clause.
- Cross-references: the #833 enumeration entry, the new D0 lint check, the corrected #1345
  wedge ladder, the FAILURE MATRIX entry, and `code-style.md`'s progress-line convention (so
  the widened trigger is discoverable from the size-keyed one). Also add a one-line pointer
  from `.claude/rules/pod-side-reporting.md` — its LESSONS trigger ("(re)launching ANY
  detached pod/VM workload") is where a dispatcher author actually looks, and
  "you write training/Hub/sweep code" may not fire for them (both lenses raised this).
- Records the **deliverable-4 decision**: xet stays ON by default; disables are scoped PER
  WORKLOAD, set inside the script before its `huggingface_hub` import (env is frozen at
  import). Rationale from the FAILURE MATRIX entry — the three transfer paths fail in disjoint
  domains, so a process-wide download-side disable fixes the small-file-storm leg and breaks
  the big-file leg (the plain path hard-refuses > 50 GB via `MAX_HTTP_DOWNLOAD_SIZE`).
  **Additional grounding surfaced by the Methodology lens:** hub GH #3266 (cited at
  `gotchas.md:214`) reports the download-side disable ITSELF has a coverage gap — a fleet flip
  would buy breakage without even guaranteed protection. Reference impl:
  `scripts/issue1739_restore_partial.py:38-39`.

### D3 — `src/explore_persona_space/orchestrate/hub.py`: harden `stage_hub_prefix`

**Framing correction (both lenses, v1 kill-criterion 1 resolved at plan time).** Neither
#1739 HANG went through `stage_hub_prefix` — both used `snapshot_download` (body lines 34,
44). D3 is therefore **not** incident-path coverage; D0 is. D3's role is that the SANCTIONED
path — the one D0's lint pushes callers onto — must not be able to go dark either. It is not
dead code: `stage_hub_prefix` has 8+ live callers including four #1739-lineage scripts
(`issue1739_bareq_score_prestage.py:40`, `issue1739_pvsynth_arms_run.py:87`,
`issue1739_gap_fold.py:139`, `issue1739_gapfold_extras.py:142`) and currently emits ZERO
output anywhere (`hub.py:2298-2324`).

Give callers (b) + (c) by construction instead of per-call discipline:

- **Split the start emission** (Methodology Must-Fix 1). v1 sketched one start line carrying
  `N`, but `N` is only known after `repo_info` (`hub.py:2301-2306`) AND
  `list_hf_files_under_path` (:2307) — both `retry_transient`-wrapped with a default 1800 s
  budget (`hub.py:1221-1223`). During a 429 storm or a listing hang that presents as
  **0-byte log + empty target + near-zero CPU for up to 30 min** — the exact signature
  invariant (d) declares unreachable, and longer than the 32-min hang that motivated the task.
  So: an **entry line flushed BEFORE any network call** (naming `repo_id@revision-or-main:prefix`),
  then the N-files line after listing resolves.
- Emit a flushed progress line per completed file in the canonical shape, as futures complete
  (`as_completed`) rather than in submit order, so a stalled file is visible as an absence of
  advancing `k/N`.
- **Timeout must HARD-EXIT, not raise** (Alternatives Must-Fix 2). Verified by the
  orchestrator against CPython 3.11.15: `concurrent.futures.thread` registers `_python_exit`
  via `threading._register_atexit` and `t.join()`s its non-daemon workers, so a worker parked
  in the Rust-side `xet_get` call is **unjoinable** — a plain `as_completed(timeout=)` /
  `.result(timeout=)` raise prints a line and then the process wedges at interpreter shutdown
  with **no rc ever produced**, defeating requirement (c) for precisely the failure the
  timeout exists to bound. On timeout: flush a diagnostic naming the stalled file(s), then
  hard-exit with a distinct rc (`os._exit`). (A killable-subprocess design is the alternative
  and would additionally enable a helper-local non-xet default; it is a larger change and is
  NOT in scope here — see § Follow-through.)
- Arm the bound via an env default `EPM_HF_STAGE_TIMEOUT_S` (**unset = off**), so a detached
  launcher can arm it without editing call sites and no existing caller's behavior changes
  silently.
- Keep the existing contract byte-intact: fail-loud on empty listing, `.result()` re-raise,
  `max_workers<=6`, one resolved revision, mirror-root `dest_dir` semantics.
