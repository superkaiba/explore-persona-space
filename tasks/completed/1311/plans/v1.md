### 3.1 Grounded drain semantics (what the clause must be faithful to — real code, read this session)

- **Drain glob + skip:** `poll_pipeline.py::sentinel_drain_shell` (lines 1774-1813) globs `/workspace/logs/issue-{issue}-*.json` and skips via `case "$f" in *.processed) continue ;; esac` (line 1808). The module docstring (lines 20-26) states the drain runs each tick, posts the carried marker, "then renames the sentinel to `<path>.processed` so it posts exactly once".
- **Rename site (pod-SSH lane):** `poll_pipeline.py::_ssh_mark_processed` (lines 1866-1887): `cmd = f"mv -n {quoted} {quoted}.processed"` (line 1879). `mv -n` no-clobber; on rename failure the sentinel is left in place and the next tick re-attempts (docstring lines 1869-1873); the post itself is idempotent via the `sentinel_fp` extra (#1084, docstring lines 26-29), so a poller killed between post and rename replays rename-only.
- **Rename ordering:** `drain_sentinels_via` renames ONLY after the marker post succeeds — `renamed_ok = mark_processed(remote_path)` (line 2499); a raising `mark_processed` is treated as rename failure (line 2507) with a manual-rename instruction logged (line 2522). Gate-carrying sentinels are renamed too (line 2422).
- **Skip-WITHOUT-rename paths:** `_parse_sentinel` (lines 2171-2215) returns None — sentinel left un-renamed — for empty body, JSON decode error, non-dict payload, missing `_SENTINEL_REQUIRED_KEYS` (warning at line 2205), unsupported `sentinel_schema_version` (lines 2207-2215). Module docstring lines 319-322 confirm: "logged + skipped (not renamed) … left in place so the next poller (or a human) can inspect it."
- **The #899 rescue (why "my state file lacks the envelope so it's safe" is FALSE):** an envelope-less body on a `-results.json` basename carrying the complete Step-7 results-payload key set is RESCUED via `_maybe_synthesize_results_envelope` (lines 2179-2184, 2200-2204) — posted as `epm:results` and then renamed.
- **GCP lane renames identically:** `backends/gcp.py:5657` binds `mark_processed=lambda remote_path: self._mark_sentinel_processed(...)`; `_mark_sentinel_processed` (lines 5681-5693) runs `sudo -n mv -n {quoted} {quoted}.processed` via gcloud ssh, docstring "mirrors `poll_pipeline._ssh_mark_processed`" (line 5683). GCP `--workload-cmd` drivers are therefore subject to the same drain, as the rule's own line 109-110 already says.
- **SLURM lane has NO sentinel channel:** `backends/slurm_monitor.py:50-57` "No sentinel drain on this lane (deliberate)" — `sentinels_processed` hardcoded 0 by lane contract (lines 486, 687); line 64: the "`.processed` rename [is] unexecutable over this transport". Nothing to tolerate there; the clause need not (and should not) mention SLURM beyond one parenthetical.
- **The relaunch wipe (why read-both is NOT enough for cross-relaunch resume):** `experimenter.md:588-614` step 8 "Sentinel hygiene" mandates, immediately before EACH launch (smoke AND full AND every re-launch): `rm -f /workspace/logs/issue-<N>-*.json /workspace/logs/issue-<N>-*.json.processed` (lines 603-605). Resume state in the namespace does not survive a relaunch in EITHER form.
- **Read-both race ordering:** the rename is an atomic same-fs `mv`. A reader checking the bare path FIRST, then `.processed`, cannot miss across one rename (rename-before-first-check → found at `.processed`; rename-between-checks → found at bare, since the bare check preceded the rename; rename-after-both → found at bare). Checking `.processed` first CAN miss (rename lands between the two checks). The clause prescribes bare-first.

```markdown
3. **Read-back tolerance — the sentinel namespace is a one-way, VM-drained
   channel; never re-read your own sentinels by bare path.** The poller
   drains `/workspace/logs/issue-<N>-*.json` (skipping `*.processed`) on
   EVERY tick and renames each successfully-posted sentinel to
   `<path>.processed` (`mv -n`; `poll_pipeline.py::_ssh_mark_processed`;
   the GCP lane renames identically via
   `backends/gcp.py::_mark_sentinel_processed`; SLURM has no sentinel
   channel at all). A dispatcher that READS its own sentinels (resume
   predicate, per-cell completion check, finalize aggregation) finds
   them GONE from the bare path within ~one tick. Conform ONE way:
   - **DEFAULT (strongly preferred): keep resume/finalize state OUTSIDE
     the drained glob** — e.g. `<out_root>/<unit>/status.json` under the
     dispatcher's own output tree. Read-both stays fiddly against the
     rename window, and the experimenter's pre-launch sentinel hygiene
     (`rm -f /workspace/logs/issue-<N>-*.json{,.processed}`,
     experimenter.md § During Execution step 8) wipes BOTH forms on
     every (re)launch — namespace state never survives a relaunch.
   - **Fallback: read BOTH forms, bare path FIRST, then
     `<path>.processed`** (bare-first cannot miss across the atomic
     rename; processed-first can) — completion checks only, never
     cross-relaunch resume (the hygiene wipe above).
   Nor may non-envelope state files park in the namespace: a JSON
   missing `_SENTINEL_REQUIRED_KEYS` is skipped WITHOUT rename but
   warn-spams every tick, and a `-results.json` basename carrying the
   results-payload key set is envelope-RESCUED (#899), posted, and
   renamed anyway. Incident #1090 fu3/fu4 (code-review r1): per-run
   sentinels doubled as resume/finalize state; the drain renamed them
   mid-run → requeue races + a production reproducibility_card covering
   only 23-24 of 35 cells.
```
