## 0.0 TL;DR (plain English)

- **What I'll run:** a ~20-line change to `scripts/task.py` — when someone posts a marker whose `--note` is one physical line that starts with a `field:` shape and contains literal `\n` two-character escapes (the classic wrong-shell-quoting mistake), the CLI prints a stderr warning telling them to use `$'...'` quoting or `--file`. The post still succeeds; nothing else changes.
- **What I expect:** the warning fires on exactly the malformed-note class that caused #1120 (a corpus scan of all 54,602 existing notes shows the predicate fires on 6, two of which ARE the #1120 incident markers) and stays silent on everything else.
- **What would change my mind:** if the corpus scan had shown the predicate firing on a meaningful fraction of legitimate notes (it fires on 0.011%), or if the WARN could ever flip the exit code (it is wrapped so it cannot).

## 4. Design

All changes in **`scripts/task.py`** + **`tests/test_task_workflow_post_marker_echo.py`**. No library (`task_workflow.py`) changes.

### D1 — Seam: CLI (`cmd_post_event`), not library (`post_event`). Decision + rationale

- The trap is a **shell-quoting** phenomenon: `--note "a\nb"` in double quotes passes the two characters `\` `n`; `$'a\nb'` passes a real newline. It can only happen where a shell builds the string.
- Library callers (`poll_pipeline.py`, `autonomous_session_watch.py`, `backends/*`, `codex_task.py`'s subprocess `--note` — argv strings, no shell interpolation) pass Python strings; a literal two-char `\n` there is a different bug class, and the dominant legitimate escape-containing notes in the corpus (82/88: `epm:cluster-poll`/`epm:backend-selected` `json.dumps` bodies with `\n` inside JSON string values) are posted by those callers — a library-level WARN would spam their stderr where nobody reads it.
- Pod-side code never shells `task.py` (CLAUDE.md invariant, `tests/test_no_pod_side_task_py_shellout.py`), so the CLI IS the single choke point for every shell-built note. A workflow-surface grep confirms every `post-marker --note` mention outside `scripts/task.py` is instruction text in agents/skills (sessions typing shell commands), not note-building code.

### D2 — Heuristic: minimal local predicate mirroring the parse-side line-core rule

Keep it local to `scripts/task.py` (no helper extraction — the parse-side function needs its full field-name-specific machinery; the poster side needs only "does the head look like any field"). Head-only, by measured evidence: the any-normalized-line variant fires 45× on the corpus (39 legitimate JSON notes) vs 6 for head-only.

The core-strip is the same one `parse_followup_note_field` applies per segment (`re.sub(r"^[\s\-*]+", "", seg)`, task_workflow.py:2539), so the WARN's notion of "field-led" covers the same bare/`=`-form/dash-bullet/star-bullet/bold `**field:**` shapes the parser recognizes. `; `-joined mid-note clauses are deliberately NOT scanned (false-positive-averse; both #1120 true positives are head-led, and head-led one-field-per-line is the documented preferred shape in markers.md rows 141-142).

### D3 — Coverage: `--note` only

`--file` (including `--file -` stdin) is the *documented escape hatch* from shell-quoting traps (task.py:1280-1284 comment; markers.md); file bytes are read verbatim, so a literal `\n` in a file is deliberate content — warning there would push posters back toward `--note`. Gate: `args.note is not None`.

### D4 — Exact diff (line anchors from current `main`)

**(i) Import** — task.py imports block (lines 40-45: `argparse, difflib, json, os, sys, pathlib`; `re` is NOT currently imported). Add `import re` alphabetically. Implementer note: add the import in the SAME Edit as its first usage — the PostToolUse ruff auto-fix strips a not-yet-referenced import.

**(ii) Module-level helper** — after `_safe_echo` (ends line 127):

```python
_FIELD_LED_RE = re.compile(r"^[A-Za-z_][A-Za-z0-9_-]*[:=]")


def _looks_field_led(note: str) -> bool:
    """True when the note HEAD is a `field:` / `field=` line-core after
    stripping the same leading whitespace/bullet/bold mix
    task_workflow.parse_followup_note_field strips per segment. Head-only
    by design (false-positive-averse; see #1178 plan §4 D2)."""
    core = re.sub(r"^[\s\-*]+", "", note)
    return bool(_FIELD_LED_RE.match(core))
```

(Bold `**field:**` is covered: the core-strip removes the leading `**`, leaving `field:**...`, whose head matches. Same reach as the parse side, which also does not recognize colon-outside `**field**:`.)

**(iii) The WARN** — in `cmd_post_event`, AFTER `payload = post_event(...)` returns (line 576) and BEFORE `_safe_echo` (line 586), so the WARN describes a note that actually landed and a raising `post_event` path is byte-unchanged:

```python
    if args.note is not None and "\\n" in note and "\n" not in note and _looks_field_led(note):
        # Poster-side twin of the #1120 parse-side normalization
        # (task_workflow.parse_followup_note_field): a single physical
        # line whose separators arrived as literal backslash-n escapes is
        # almost always a shell-quoting mistake ("...\n..." instead of
        # $'...\n...'). WARN only — the marker already posted; guarded so
        # a torn-down stderr can never flip the exit code post-commit
        # (the #537 rc-contract class, see _safe_echo).
        try:
            print(
                f"WARNING: task.py post-marker {args.marker}: --note is a single "
                "physical line containing literal \\n escape sequences with "
                "field-led content; field parsers treat REAL newlines as "
                "separators (the parse-side normalizer will rewrite these "
                "escapes, #1120). Did you mean $'...' shell quoting, or --file "
                "for a multi-line body? The marker was posted unchanged.",
                file=sys.stderr,
            )
        except OSError:
            pass
```

The trigger `"\\n" in note and "\n" not in note` is copied verbatim from the parse-side gate (task_workflow.py:2523), so poster-side detection and parse-side normalization engage on exactly the same note shape. `note == args.note` on this path (argparse mutually-exclusive group at line 1286 guarantees `--file` was not given).

**(iv) Tests** — append to `tests/test_task_workflow_post_marker_echo.py`, reusing `_ns()` + fake-`post_event` + `capsys` + `_BrokenPipeStdout`:

[acceptance 1 + 4]
