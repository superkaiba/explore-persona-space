The canonical launcher carries `-o junit_family=xunit1` beside `--junitxml=`;
that flag is load-bearing for the NEXT step, not for pytest. A composed launcher

looks completely healthy — but `step9c_baseline.py compare` cannot resolve
failing testcases to repo paths and aborts, surfacing as an ambiguous

## 2. Method delta — why this differs from #2310

#2310 hardened an input-SHAPE defect: a wrong-shaped value spliced into the
canonical launcher, catchable by a pre-launch assert on the substituted value.

Instance B is structurally different, and the difference dictates the design.
The canonical launcher text is **already correct at both sites** (L3344, L3491).
The defect is in the *composition path*: a session that assembles its own
launcher never executes the canonical block, so **a shell assert added inside
that block is vacuous for this failure mode** — it would check a literal the
block already contains. The critic verified the mechanism: the pre-launch guards
can only assert on variables the block holds (the L3296 splice-shape check works
precisely because the file list IS a variable, `$S9C_FILES`), and a hand-composed
launcher's text is never in any variable the recipe can inspect. This is why a
naive reading of task item 4 ("a pre-launch assert that the composed pytest argv
contains `junit_family=xunit1`") is ineffective *as stated, if placed in the
canonical recipe*.

Two measured facts shape the rest of the design.

**(a) The flag set is already single-sourced for INTERNAL producers, and only
the shell launchers escape it.** `step9c_baseline.py` L462-468 defines
`PYTEST_BASE_FLAGS`, which contains `junit_family=xunit1` and is the default
`extra` for `run_pytest` (L789), so every pristine/paired/suffix run the compare
spawns is correctly pinned by construction — L1910-1915 records this as the
single-source fix from #1746 Must-Fix 1. The ONLY junit producers that hand-write
the flags are the two shell launchers in the recipe. That reframes D2 from
"consider" to "extend an established in-repo pattern to the one path that
escaped it".

**(b) The abort fires late, and only when a failure exists.**
`step9c_baseline.py` raises the file-attribute `JunitParseError` only inside the
`if has_failure or has_error:` branch (L1249-1263). So a GREEN run with a
malformed junit is benign — nothing needs path resolution and the verdict is
still correct, so a guard must NOT fail it (the critic traced the other two
`file`-attr consumers, `parse_junit_ran_files` L1282 and
`parse_junit_failure_texts` L1316, and confirmed both are reached only during
failure adjudication, with `parse_junit_ran_files`'s own docstring declaring the
empty-set direction fail-closed). But a run with ≥1 failure aborts the compare
only AFTER compare has launched — wedge bound 32400 s, pristine runs up to ~2 h
(L3607-3617). #2312 paid 1787.80 s of gate pytest and then lost the verdict.

So the fix attacks four points, in decreasing order of leverage: make the
omission harmless (D0), remove the reason to compose (D2), give the composer a
mechanical self-check (D1), and detect the artifact before the expensive
consumer (D3).

## 3. Design

### D0 — `junit_family = "xunit1"` in `pyproject.toml` (PRIMARY lever)

Add `junit_family = "xunit1"` to `[tool.pytest.ini_options]`. Verified premises:

- that table exists (`testpaths`, `addopts`, `markers`) and carries NO
  `junit_family` key today;
- a CLI `-o` overrides an ini value, so the canonical launchers at L3344/L3491
  are unaffected — no behavior change on the correct path;
- the only other junit producers in the repo are `run_pytest`'s internal spawns,
  already pinned via `PYTEST_BASE_FLAGS`, plus test fixtures that set the family
  explicitly. So the ini default is a behavioral no-op everywhere EXCEPT exactly
  the trap case.

Effect: an omitted flag stops being a defect at all. Instance B becomes a
non-event (a usable junit, zero re-run) instead of a fast-named failure needing a
scoped re-run. One line plus one pin test, and it protects composition paths
nobody has written yet. Same pytest-version exposure as the existing explicit
flag, so it adds no new fragility.

D0 does NOT satisfy AC3 by itself (AC3 asks for a refusal), which is why D1 stays.

### D1 — `select_step9c_tests.py --assert-launcher` (composer-facing refusal)

Takes composed launcher text (positional, or `-` for stdin) and refuses it when
the text contains `--junitxml` (either spelling, `--junitxml=PATH` or
`--junitxml PATH`) and does not contain `junit_family=xunit1`. Non-zero exit with
a message naming the omission, that the suite run still reports its ordinary pass/fail status so the gate looks
healthy, that the compare will abort with `has no file attribute` reporting
`indeterminate: True`, and that the junit is unrepairable after the fact.

**Correction carried from the critic (v2 defect).** v2 justified this by saying a
text with no `--junitxml` "is not this guard's business, e.g. L3630". That was
wrong: L3630 is the `step9c_baseline.py compare` invocation and it DOES carry
`--junitxml` — it consumes the junit rather than producing it, so piping that
correct command through the guard would refuse it. Scope the guard to PYTEST
launcher text: exempt argv containing `step9c_baseline.py` (equivalently, require
a `pytest` token). Fail-safe direction either way, but the exemption must be
explicit rather than emergent.

D1 is knowingly only partial protection — a composer who forgets the flag may
equally forget the checker. It is the AC3 refusal leg, not the load-bearing one;
D0 and D2 carry that weight.

Self-testing, mirroring the #2310 precedent: assert both the positive and
negative built-in fixture case before judging the input, and refuse to render a
verdict if that self-test fails.

### D2 — `select_step9c_tests.py --emit-launcher` (prevention)

Emit the full ready-to-run canonical step-1b launcher on stdout with the test
list already space-joined and `<N>`/`<T>` substituted from `--issue`/`--timeout`.
Removes self-composition as a necessary step, so the flag cannot be dropped by
omission — AC3's "or made impossible" branch.

**Independent rationale (per §2(a)):** this extends the repo's existing
`PYTEST_BASE_FLAGS` single-source pattern to the one producer path that escaped
it. The critic's D0 finding reduces D2's *incident-prevention* value to
convenience, but does not touch this structural argument — so D2 stays in the
plan rather than being dropped as redundant with D0.

Drift control (tightened per the critic): a pin test asserts the emitted flag set
equals BOTH canonical sites (emitter == site-1 == site-2), so a one-site drift
cannot leave the emitter silently matching the stale site. Residual, accepted and
recorded: the setsid/rc-write WRAPPER is not flag-set-pinned; wrapper drift fails
loud through the existing completion-read guards (a missing rc file is a FATAL
that never records PASS), so it cannot silently swallow a verdict.

### D3 — pre-compare junit-contract check (insurance)

In `13-step-9.md` step 1d, after the `PYTEST_RC` re-read (L3606) and BEFORE the
compare launcher (`COMPARE_PID=`, L3627): if the harvested junit records ≥1
failing testcase and any such testcase lacks a `file` attribute, FAIL the gate
immediately with the named cause instead of launching a compare that will abort.
The critic confirmed this is the earliest point the evidence exists and the
latest point before the expensive consumer.

Implemented as a subcommand on the existing seam (`refresh` / `status` /
`compare` / `tmproot` / `mapped` / `classify` / `probe`, L4147-4341) so it reuses
the shipped junit parser and, critically, the SAME `file`-attribute predicate the
abort uses — including the #1746 collect-error fallback: a row with an `error`
child, no `file` attr, and a `.py`-suffixed `name` is legitimately absorbed
(L1250-1263) and must not trip the guard. The critic verified the predicate
discriminates in BOTH directions: under an omitted flag a collect-error row's
`name` is dotted (`tests.test_broken`), so it does not end in `.py`, raises, and
D3 correctly fails the gate even when the only failure is a collect error.

Constraints (the third is the critic's Should-Consider 4, made binding):
- green run (zero failing testcases) → exit 0, silent. Failing it would be an
  AC5 false positive, per §2(b).
- missing / empty junit → NOT this guard's verdict; the existing `COMPARE_RC=2`
  and 1b FAIL paths keep ownership.
- therefore the subcommand MUST NOT surface `parse_junit`'s missing-or-unparseable
  raise as its own verdict: pre-check existence and catch `ParseError`, exiting 0
  so ownership stays where it is. (v2's "raises only inside the failing branch"
  was slightly overstated — `parse_junit` also raises on a missing/unparseable
  junit outside that branch; this constraint is what makes the overstatement
  harmless.)

D0 demotes D3 from primary detection to insurance. It stays because it is cheap,
and because it covers the residual case where a future producer deliberately
overrides the ini default.

### D4 — documentation (recognition)

1. Add the xunit1-contract violation to the `COMPARE_RC=2` indeterminate cause
   enumeration (L3735-3752 — today: `PYTEST_RC ∉ {0,1}` / missing-or-empty
   junitxml / suite crash / unusable ledger / systemic main breakage /
   scratch-ineligible dirty oracle; the contract violation is absent). State the
   DISCRIMINATOR, because indistinguishability from the legitimate causes is the
   actual damage: `pristine_oracle: None` plus a `has no file attribute` line in
   the compare stderr means *the launcher was malformed*, not *the tool could not
   decide*.
2. Name the remedy at the sanction point: re-run with the flag; `file` attributes
   cannot be reconstructed from an existing junit. Point at `--emit-launcher` as
   the way to not need this.

## 6. Success criteria (quantitative)

- **SC-0** With `junit_family = "xunit1"` in the ini table and NO `-o` flag on
  the argv, a pytest run writing a junit emits per-testcase `file` attributes,
  and `step9c_baseline.py compare` resolves its failures without aborting. A
  contradicting `-o junit_family=xunit2` on the argv still overrides the ini
  (proving precedence, hence AC5 safety for the canonical launchers).
- **SC-1** A composed PYTEST launcher text containing `--junitxml` and lacking
  `junit_family=xunit1` is REFUSED by D1 with non-zero exit; the same text with
  the flag exits 0. Both spellings (`--junitxml=P`, `--junitxml P`) refuse. A
  `step9c_baseline.py compare --junitxml ...` consumer command is EXEMPT (exit 0).
- **SC-2** `--emit-launcher` output contains `--junitxml`, `junit_family=xunit1`,
  and a space-joined (zero embedded-newline) test list; a pin test asserts the
  emitted flag set equals BOTH canonical launcher sites.
- **SC-3** D3 exits non-zero on a junit with ≥1 failing testcase missing `file`;
  exits 0 on (a) a green junit, (b) a well-formed xunit1 junit with failures,
  (c) a junit whose only file-attr-less row is a `.py`-named collect-error row
  (#1746), (d) a missing or unparseable junit (ownership stays with the existing
  paths). Runs in < 5 s on the largest junit in scope.

Fail-loud pin: tests/test_issue_skill_gate_recipe_hardening.py — test_assert_launcher_refuses_junitxml_without_xunit1 and test_junit_contract_check_refuses_missing_file_attr each assert the guard EXITS NON-ZERO rather than swallowing the omission silently; each carries a pytest.raises negative control on the CalledProcessError raised by the refusing subprocess, so a differently-worded re-swallow cannot ship green.

- **SC-4** Every new guard has a test demonstrated to FAIL pre-fix and PASS
  post-fix (the discriminating-test bar, #2310 precedent). ≥1 test per SC-0..3.
- **SC-5** `workflow_lint.py` no-flags run is clean, and the Step 9c gate's own
  verdict on this branch is PASS with no NEW failures.
- **SC-6** AC5: the ordinary correctly-composed path is behaviourally unchanged
  — both canonical launchers keep byte-identical flag sets, and no new required
  step enters the green path beyond D3's sub-5 s check. **Anchor by
  launcher-pattern grep, not line number** (this plan's own edits shift
  L3344/L3491), matching how the existing #2310 tests locate the launcher.
