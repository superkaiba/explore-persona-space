## 1. Requirement

The Step 9c step-1b recipe sanctions a session COMPOSING its own gate launcher.
The canonical launcher carries `-o junit_family=xunit1` beside `--junitxml=`;
that flag is load-bearing for the NEXT step, not for pytest. A composed launcher
that drops it still runs the suite and still exits with the correct rc — the gate
looks completely healthy — but `step9c_baseline.py compare` cannot resolve
failing testcases to repo paths and aborts, surfacing as an ambiguous
`indeterminate: True`. Close that trap: make the flag hard to drop, detect the
omission at the earliest point evidence exists, and make the signature
recognizable.

## 2. Method delta — why this differs from #2310

#2310 hardened an input-SHAPE defect: a wrong-shaped value spliced into the
canonical launcher, catchable by a pre-launch assert on the substituted value.
The canonical launcher text itself was correct and stayed correct.

Instance B is structurally different and the difference dictates the design: the
canonical launcher text is **already correct at both sites** (L3344, L3491 both
carry the flag, verified). The defect is in the *composition path* — a session
that assembles its own launcher never executes the canonical block, so **a shell
assert added inside that block is vacuous for the failure mode**: it would check
a literal the block already contains, and the self-composed launcher bypasses it
entirely. This is the trap that makes a naive reading of task item 4 ("a
pre-launch assert that the composed pytest argv contains `junit_family=xunit1`
whenever it contains `--junitxml`") ineffective as stated *if placed in the
canonical recipe*. So the fix attacks the two points that actually dominate a
composed launcher:

- **prevention** — remove the reason to compose (D2), and give the composer a
  mechanical check it can run on its own argv (D1);
- **detection** — an artifact-level check that is blind to who composed the
  launcher (D3), placed before the expensive consumer.

A second measured fact shapes D3's placement. `step9c_baseline.py` raises
`JunitParseError` only inside the `has_failure or has_error` branch
(L1250-1263), so:

- a GREEN gate run with a malformed junit is benign — nothing needs path
  resolution, and the verdict is still correct. The omission is therefore NOT a
  silent-pass risk, and the guard must not fail a green run;
- a run with ≥1 failure aborts the compare — but only AFTER compare has been
  launched, whose wedge bound is 32400 s and whose pristine runs can take ~2 h
  (L3607-3617, L3661-3662). #2312 paid 1787.80 s of gate pytest and then lost
  the verdict.

Detecting between pytest-exit and compare-launch is therefore worth far more
than detecting inside compare: it converts "ambiguous indeterminate up to ~2 h
later, junit unrepairable, full re-run" into "named failure seconds after the
run, re-run scoped to the failing files".

## 3. Design

### D1 — `select_step9c_tests.py --assert-launcher` (pre-launch, composer-facing)

Add a mode that takes the composed launcher text (a positional argument, or `-`
for stdin) and refuses it on the junit pairing:

- if the text contains `--junitxml` (either spelling: `--junitxml=PATH` or
  `--junitxml PATH`) **and** does not contain `junit_family=xunit1` → exit
  non-zero with a message naming (a) the omission, (b) that pytest will still
  exit 0/1 so the gate will look healthy, (c) that `compare` will abort with
  `has no file attribute` and report `indeterminate: True`, and (d) that the
  junit cannot be repaired after the fact, so the remedy is re-running with the
  flag;
- exit 0 otherwise. A text with no `--junitxml` at all is not this guard's
  business (that is the `compare` consumer's own invocation shape, e.g. L3630).

Self-testing, mirroring the #2310 precedent so the guard cannot silently stop
discriminating: the mode asserts its own positive and negative case on a pair of
built-in fixture strings before judging the input, and refuses to render a
verdict if that self-test fails.

### D2 — `select_step9c_tests.py --emit-launcher` (prevention)

Emit the full ready-to-run canonical step-1b launcher on stdout, with the test
list already space-joined and `<N>` / `<T>` substituted from
`--issue` / `--timeout`. This removes self-composition as a necessary step, so
the flag cannot be dropped by omission — AC3's "or made impossible" branch. The
emitted text is the SAME shape as the recipe's canonical block (so the recipe and
the emitter cannot drift silently, the emitted text is covered by a pin test that
compares it against the recipe's canonical flags).

*Assumption, flagged for the critic:* `--emit-launcher` is the largest single
piece of this change and the task lists it as "consider". If the critic judges it
disproportionate, D1 + D3 + D4 alone satisfy AC3 (refuse) without the
"made impossible" branch, and D2 is the droppable leg. Nothing else depends
on it.

### D3 — pre-compare junit-contract check (detection, launcher-agnostic)

In `13-step-9.md`, in the step-1d block BEFORE the compare launcher
(`COMPARE_PID=`, L3627), add a cheap check on the harvested junit: if it records
≥1 failing testcase and any such testcase lacks a `file` attribute, FAIL the gate
immediately with the named cause, instead of launching a compare that will abort.
Implemented as a subcommand on the existing seam
(`step9c_baseline.py` already exposes `refresh` / `status` / `compare` /
`tmproot` / `mapped` / `classify` / `probe`, L4147-4341) so the junit parsing
reuses the shipped parser rather than a hand-rolled XML read in shell — and so it
reuses the exact `file`-attribute predicate the abort uses, including the #1746
collect-error fallback (a row keyed only through a `.py` `name` is legitimately
file-attr-less and must NOT trip this guard).

Constraints:
- green run (zero failing testcases) → exit 0, silent. Per the measured fact
  above, a malformed-but-green junit is benign; failing it would be a false
  positive on the ordinary path (AC5).
- missing/empty junit → NOT this guard's verdict; that case already routes
  through the existing `COMPARE_RC=2` / 1b FAIL paths. The guard must not
  duplicate or pre-empt them.

### D4 — documentation (recognition)

Two edits in `13-step-9.md`:

1. Add the xunit1-contract violation to the `COMPARE_RC=2` indeterminate cause
   enumeration (L3735-3752, which today lists: `PYTEST_RC ∉ {0,1}` /
   missing-or-empty junitxml / suite crash / unusable ledger / systemic main
   breakage / scratch-ineligible dirty oracle — the contract violation is absent).
   State the DISCRIMINATOR explicitly, because indistinguishability from the
   legitimate causes is the actual damage: `pristine_oracle: None` plus a
   `has no file attribute` line in the compare stderr means *the launcher was
   malformed*, not *the tool could not decide*.
2. Name the remedy at the sanction point: re-run with the flag; the `file`
   attributes cannot be reconstructed from an existing junit.

## 6. Success criteria (quantitative)

- **SC-1** A composed launcher text containing `--junitxml` and lacking
  `junit_family=xunit1` is REFUSED by D1 with non-zero exit; the same text with
  the flag exits 0. Both spellings (`--junitxml=P`, `--junitxml P`) refuse.
- **SC-2** `--emit-launcher` output contains `--junitxml`, `junit_family=xunit1`,
  and a space-joined (zero embedded-newline) test list; a pin test ties its flag
  set to the recipe's canonical launcher so the two cannot drift.
- **SC-3** D3 exits non-zero on a junit with ≥1 failing testcase missing `file`;
  exits 0 on (a) a green junit, (b) a well-formed xunit1 junit with failures,
  (c) a junit whose only file-attr-less row is a `.py`-named collect-error row
  (#1746). Runs in < 5 s on the largest junit in scope.

Fail-loud pin: tests/test_issue_skill_gate_recipe_hardening.py — test_assert_launcher_refuses_junitxml_without_xunit1 and test_junit_contract_check_refuses_missing_file_attr each assert the guard EXITS NON-ZERO rather than swallowing the omission silently; each carries a pytest.raises negative control on the CalledProcessError raised by the refusing subprocess, so a differently-worded re-swallow cannot ship green.
- **SC-4** Every new guard has a test demonstrated to FAIL pre-fix and PASS
  post-fix (the discriminating-test bar, #2310 precedent). ≥1 test per SC-1..3.
- **SC-5** `workflow_lint.py` no-flags run is clean, and the Step 9c gate's own
  verdict on this branch is PASS with no NEW failures.
- **SC-6** AC5: the ordinary correctly-composed path is behaviourally unchanged
  — the canonical launcher lines L3344/L3491 keep byte-identical flag sets, and
  no new required step is inserted into the green path beyond D3's sub-5 s check.
