# Plan v1 for #2164: single-source the autonomous plan-gate GPU-hour cap

**Kind:** `infra` (workflow-surface code fix) · **Estimated GPU-hours (total): 0** ·
**Target pod: none — VM-local edit + pytest.**

## Requirement

The Step-2c autonomous plan-approval cap is resolved independently at nine code
sites across three scripts, with two different defaults. The deciding site
defaults to **24**; the reporting and spawning sites default to **100**. In an
env-less autonomous context a 30 GPU-h plan therefore parks (decided against 24)
and then reports `over 100 GPU-h cap` — naming a threshold the plan never
crossed.

Two things must be true when this lands:

1. The deciding default and every reported/propagated default are the **same
   number**, and that number is **100** (decision recorded in `epm:clarify v1`;
   rationale summarized under "Decision" below).
2. They are the same number **because they cannot be different** — one
   constant + one resolver, read by every site — not because nine literals were
   hand-edited to agree. A regression test pins decision-cap == reported-cap,
   and a source-scan test prevents a tenth site from reintroducing a bare
   literal.

### Acceptance criteria

- `A1` With `EPM_PLAN_AUTOAPPROVE_GPU_HOURS` unset and `EPM_AUTONOMOUS_SESSION=1`,
  `_resolve_autonomous_plan_gate(30.0)` returns `("auto_approved", 100.0, True)`
  (today: `("parked_over_cap", 24.0, True)`).
- `A2` With the env unset, the cap named by the watcher's park message equals the
  cap the gate decided on, for both the default case and a custom-cap case.
- `A3` `grep -c 'EPM_PLAN_AUTOAPPROVE_GPU_HOURS' <deciding/reporting .py files>`
  resolves to exactly one `os.environ` read repo-wide, inside the new resolver.
- `A4` No behavior change for any session that sets the env — which is every
  session `spawn_session.py spawn-issue --auto` creates (`default=100.0`).

## Decision on the open fork (recorded, not re-litigated here)

`Decision: align the code default to 100, not the docs to 24.`

Ranked reasons in `epm:clarify v1` (posted 2026-08-07). One-line summary: 100 is
the *realized* cap in every live `--auto` session because
`spawn_session.py:3393` injects it, so code→100 is a no-op for live sessions and
fixes only the env-less path; docs→24 would be a live fleet-wide spend-policy
tightening smuggled in as a consistency fix.

## Method delta

No new module, no new plumbing. All three consuming scripts already import
`explore_persona_space.task_workflow` (`task.py:56` top-level;
`spawn_session.py:60` top-level; `autonomous_session_watch.py` lazily inside
functions at `:6400`, `:6636`, `:7514`, `:7818`, `:8482`). The watcher edits
follow that file's existing lazy-import convention.

### E1 — the single resolution point (core)

Add to `src/explore_persona_space/task_workflow.py` (no such constant exists
today — verified by grep):

```python
PLAN_GATE_CAP_ENV = "EPM_PLAN_AUTOAPPROVE_GPU_HOURS"
AUTONOMOUS_PLAN_GATE_DEFAULT_GPU_HOURS: float = 100.0

def resolve_plan_gate_cap(env: Mapping[str, str] | None = None) -> float:
    """Single resolution point for the Step-2c autonomous plan-approval cap.

    Every deciding, reporting, and respawn site reads the cap through this
    function so the decided threshold and the reported threshold cannot
    diverge (#2164). Absent / blank / unparseable env falls back to
    AUTONOMOUS_PLAN_GATE_DEFAULT_GPU_HOURS.
    """
```

Semantics: `float(raw.strip())`, `except (TypeError, ValueError)` → constant.
A blank `EPM_PLAN_AUTOAPPROVE_GPU_HOURS=""` therefore resolves to the constant
rather than raising — matching absent-env semantics at every site (today
`task.py` already lands on its fallback for blank, so this is a no-op there).

### E2 — rewire the deciding site

`scripts/task.py:395-427`: replace the env read + parse fallback with
`cap = resolve_plan_gate_cap()`. The `(decision, cap, autonomous)` return
contract, the `not autonomous` branch, and the `gpu_hours is None` fail-safe are
untouched. Help text at `:1457` becomes an f-string interpolating
`AUTONOMOUS_PLAN_GATE_DEFAULT_GPU_HOURS`.

### E3 — rewire the two watcher respawn caps

`_respawn` (`:12378`) and `_stalled_cap_gpu_hours` (`:17948-17962`): every
`24.0` fallback becomes `resolve_plan_gate_cap()`; the docstring at `:17950`
names the resolver instead of a literal. Behavior when the registry entry *does*
carry a numeric `auto_approve_gpu_hours` is unchanged — the registered cap still
wins, which is the point of those helpers.

### E4 — rewire the reporting site (SEPARABLE — see below)

`_gate_push_message` (`:31031-31041`, one caller at `:31235`) currently reads its
*own* env, which the cron does not set. Two sub-parts:

- **E4a (in scope, non-negotiable):** the env fallback reads
  `resolve_plan_gate_cap()`.
- **E4b (separable):** prefer the *registered per-issue* cap —
  `_stalled_cap_gpu_hours(issue)`, an existing in-repo helper that already
  performs exactly this lookup — falling back to the resolver. Without E4b a
  session spawned with `--auto-approve-gpu-hours 50` still gets a message naming
  100: the identical misleading-notification defect, one layer down. With E4b the
  message names the cap that session actually decided against.

  E4b is flagged separable so the critic can REVISE it out as scope creep. My
  read: it is the same defect, it reuses an existing helper rather than adding
  one, and `_gate_push_message` already takes `issue` — but it is a behavior
  change to a notification path the body did not name, so it gets its own line.

### E5 — anti-drift tests (the load-bearing half)

`tests/test_autonomous_plan_gate.py`:

- Amend the five `24.0` pins (`:45, :79, :86, :105, :132`) to assert against
  `AUTONOMOUS_PLAN_GATE_DEFAULT_GPU_HOURS`. The at-cap boundary test keeps its
  *shape* (feed exactly the cap, expect `auto_approved`) with the value derived
  from the constant; `test_park_over_default_cap` gains an explicit
  `EPM_PLAN_AUTOAPPROVE_GPU_HOURS` so it keeps testing the park branch rather
  than becoming vacuous under a 100 default.
- **New** `test_decision_cap_equals_reported_cap`: env unset →
  `_resolve_autonomous_plan_gate(...)[1]` equals the cap
  `_gate_push_message` names, equals the `spawn-issue --auto-approve-gpu-hours`
  argparse default. This is acceptance criterion A2 and the regression the body
  asked for.
- **New** `test_cap_env_read_is_single_sourced`: source scan over `scripts/*.py`
  + `src/explore_persona_space/**/*.py` asserting `os.environ`-style reads of
  `PLAN_GATE_CAP_ENV` occur only in `task_workflow.py`. This is what makes a
  tenth divergent site a red test rather than a future incident.

The env-explicit tests in `tests/test_task_workflow_post_marker_echo.py:175-235`
set the env to `"24"` themselves and are insensitive to the default — no edit.
