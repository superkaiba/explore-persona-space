### 0.0 TL;DR (plain English)

A free-lane (`fellows`) launch can legitimately sit in the QoS-ladder **park** for
up to **420 seconds** waiting for a queue slot. The Bash tool's **default** timeout
is **120 seconds**. So if the orchestrator dispatches
`scripts/dispatch_issue.py launch` as a plain background Bash call and forgets to
pass an explicit `timeout`, the harness SIGTERMs the launcher (rc=143) **before it
can submit** — and the failure looks like a launcher bug rather than a
too-short tool timeout.

SKILL.md already documents both halves and never connects them: the 420 s park
contract lives at ~L4450-4457, and the `timeout=600000` prescription lives ~300
lines later at ~L4768 where its own prose scopes it to *cold RunPod* provisioning
("`--backend runpod`", "25-50 minutes on the RunPod lane"). A reader on the
fellows lane has no reason to apply it.

This plan adds **three short prose blocks** to Step 6b — the timeout floor stated
for *every* parking lane, right next to the park paragraph; a launcher-rc capture
line; and one clause on the launch-recovery invariant tying a killed launch to the
under-budgeted timeout. No code, no behavior, no new lint check.

#### Edit 1 — bg-Bash timeout floor (NEW paragraph, inserted immediately AFTER current L4457, i.e. after the park-budget paragraph and BEFORE the `**Launch-recovery invariant (#1336).**` paragraph)

Anchor (unique, unchanged): the paragraph ending
`…while \`still_waiting\` (PENDING polls as \`running\`; the ladder stalls).`

New text to insert (blank line before and after):

```
**bg-Bash `timeout` floor — EVERY lane whose launch can park (#2244).** The
420 s park above OUTLASTS the Bash tool's DEFAULT 120 s timeout, so a launch
dispatched as a plain bg-Bash — `Bash(run_in_background=true,
command="uv run python scripts/dispatch_issue.py launch ...")` — with NO
explicit `timeout` is SIGTERMed (rc=143) MID-PARK — before the launcher can submit, park, or print the exit-75
JSON above — and the death reads as a launcher bug, not a too-short tool budget.
Pass `timeout=600000` (600 s, the harness maximum) on EVERY
`dispatch_issue.py launch` bg-Bash: on `auto`, on `backend: fellows`, and on
every other lane pin, NOT only on the cold-RunPod case that Step 6d.1 item 4
spells out — the 600 s floor there is the SAME floor, stated for one lane. 600 s
clears the 420 s park with headroom for submit + the stdout JSON; a lane whose
park budget is raised above ~540 s can no longer be waited out inside one
bg-Bash and must be re-run per the exit-75 contract instead.
```

#### Edit 2 — launcher-rc capture at the dispatch site (NEW paragraph, inserted immediately after Edit 1's paragraph)

New text:

```
**Capture the LAUNCHER's rc, not a filter's (#2244).** The exit-75 / rc=2 /
rc=143 branches above are only decidable if the launcher's OWN exit code reaches
the tool output. Put `RC=$?; echo "LAUNCHER_RC=$RC"` IMMEDIATELY after the
`dispatch_issue.py launch` invocation, BEFORE any trailing filter — a
`| tail`-style post-filter makes a bare `$?` the FILTER's status and masks the
launcher's (`.claude/rules/code-style.md` § "Post-pipe `$?` is the LAST stage's
status, not the pipeline's"; the remedies there — `bash -o pipefail -c` /
`${PIPESTATUS[0]}` — apply verbatim). `LAUNCHER_RC=143` is the
timeout-floor symptom above; `75` routes to the re-run contract; `2` routes to
`epm:failure v1` + `set-status blocked`.
```

#### Edit 3 — cross-reference on the launch-recovery invariant (amend the EXISTING L4459-4465 paragraph: append one sentence, keep every existing sentence and token byte-identical)

Existing paragraph (verbatim, unchanged head):

```
**Launch-recovery invariant (#1336).** A killed launch call may have
SUCCEEDED — submit precedes the park. BEFORE any relaunch probe BOTH
`.claude/cache/issue-<N>-handle.json` AND `squeue --name
eps-issue-<N>...` on the cluster: live job → re-run the SAME command;
BOTH empty → died PRE-submit, plain re-run safe. `scancel` +
confirm-gone + re-run ONLY when abandoning the job or changing the
command shape.
```

Sentence to APPEND at the end of that paragraph (same paragraph, no blank line
inserted — so the pinned `squeue --name` ↔ `issue-<N>-handle.json` adjacency is
untouched):

```
 The single most common CAUSE of a killed launch call is an under-budgeted
bg-Bash `timeout` (the 600 000 ms floor above), so pair the probe with RAISING
the timeout on the re-run: a re-run dispatched at the 120 s default dies
identically, and the probe then just re-observes its own previous corpse.
```

**Nothing else changes.** No edit to L4439-4448 (RunPod exit-75), L4450-4457
(park budget), L4755-4771 (Step 6d.1 item 4), any rule file, any test, any code.
