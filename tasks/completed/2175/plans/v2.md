## Requirement + acceptance criteria

`src/explore_persona_space/orchestrate/provenance.py::git_provenance()` uses
`git status --porcelain=v1 --untracked-files=no`, so a brand-new UNTRACKED
entrypoint that produces artifacts stamps them `git_commit=<sha>` with
`git_dirty=False` (or dirty from unrelated files) and NO signal that the
producing script itself is not in that commit — violating the module's own
invariant ("a committed result JSON never claims provenance from a commit that
does not contain the code that produced it", #2065/#1482).

Acceptance criteria (from the task body):
1. The provenance record carries an explicit signal when the producing script
   (argv[0]) is untracked or modified.
2. A unit test runs `git_provenance()` against a repo fixture with an
   untracked `scripts/foo.py` as argv[0] and asserts the record carries the
   untracked signal.
3. Existing consumers keep working: `git_commit` / `git_dirty` /
   `git_dirty_paths` keys unchanged; new fields are additive; the
   `tests/test_paper_plots.py` exact-key-set caps are extended to admit the
   new keys (the ONLY caller-side edit — see File paths).

## Design (fix option B of the task body, extended to the dirty flag)

**Chosen: record argv[0]'s tracked-state as explicit fields AND fold an
untracked entrypoint into `dirty`.** Rejected: option A (include `??` rows
under `scripts/` + `src/` in the working-tree-wide scan) — the shared repo
root routinely holds OTHER concurrent sessions' untracked `scripts/issueN_*.py`
files, so option A would flip `git_dirty=True` on nearly every root-resident
run from files the run never touched, destroying the flag's signal value.
Option B targets exactly the incident shape (#2094: the producing script
itself untracked). Named residual (disclosed, deliberate): an untracked
IMPORTED module beside a tracked entrypoint is still invisible — that is
option A's coverage, bought only at the fleet-noise cost above; revisit if the
class recurs via imports. (Critic verified the rationale + the porcelain
mechanics live on VM git 2.34.1.)

Mechanics in `provenance.py`:

1. New helper `_argv0_git_state(argv0, cwd) -> tuple[str | None, str | None]`
   returning `(state, path)` with
   `state ∈ {"tracked", "modified", "untracked", None}`; **returns
   `(None, None)` whenever state is None** (no venv-binary path noise beside a
   null state):
   - argv0 missing / empty / not a regular file (`-c`, interactive) → `(None, None)`.
   - **Resolution frame (explicit):** `Path(argv0)` is resolved to ABSOLUTE
     against the process cwd (`Path(argv0).resolve()`) BEFORE any git call,
     and the absolute pathspec is what git receives — a relative pathspec
     under the `cwd=` param would reopen a wrong-file misattribution channel;
     an outside-repo absolute pathspec dies rc=128 → `(None, None)` (verified:
     this is how the pytest-binary default degrades in tmp_path fixture repos).
     One docstring sentence states this frame.
   - `git ls-files --error-unmatch -- <abs>` rc==0 ⇒ tracked; then
     `git status --porcelain=v1 -- <abs>` empty ⇒ `"tracked"`,
     non-empty ⇒ `"modified"`.
   - not tracked: `git status --porcelain=v1 --untracked-files=all -- <abs>`
     starting `??` ⇒ `"untracked"`; EMPTY output ⇒ `(None, None)` — the
     load-bearing ignored-file branch: a gitignored argv0 (`.venv/bin/pytest`)
     yields empty porcelain output and must NOT read as untracked, or every
     pytest-invoked call would false-flag dirty. (Verified porcelain-v1
     behavior on git 2.34.1: ignored under `-uall` → empty rc=0; untracked →
     `??` row even when nested in an untracked dir, for a file pathspec.)
   - any git failure (outside repo, no git, timeout — reuse `_run_git`) → `(None, None)`.
   - the reported path: as git prints it in the porcelain row when available,
     else the absolute path made relative to `git rev-parse --show-toplevel`;
     on failure `(None, None)`.
2. `GitProvenance` gains two frozen fields with defaults (back-compat for
   direct constructors): `argv0_path: str | None = None`,
   `argv0_state: str | None = None`.
3. `git_provenance(cwd=None, argv0=None)` — optional `argv0` param defaulting
   to `sys.argv[0]` (explicit param = clean test injection). Composition:
   - `dirty, paths = _git_dirty_status(cwd)` (tracked scan UNCHANGED, still
     `--untracked-files=no`);
   - `state, rel = _argv0_git_state(...)`;
   - if `state == "untracked"`: `dirty = True` (None → True too: the explicit
     positive finding outranks an inconclusive tracked scan; docstring notes
     the rare `unknown+dirty` render this permits under timeout asymmetry) and
     PREPEND `rel` to `dirty_paths` if absent (prepend so the cap's overflow
     tail can never drop it; cap+1 length acceptable). `"modified"` argv0
     needs no folding — the tracked scan already reports it (no double-entry
     in `dirty_paths`).
4. `as_metadata_dict()` adds `git_argv0_state` (always present, None = could
   not determine) and `git_argv0_path` (present ONLY when `argv0_state` is not
   None). Additive keys; exact-dict tests updated in the same round.
5. `commit_string()` unchanged — an untracked argv0 now renders `<sha>+dirty`
   automatically via the folded dirty flag, closing the flat-string channels
   (PDF/PNG/WandB) with zero consumer edits.
6. Update the module docstring + `_git_dirty_status` docstring: delete the
   false rationale ("a run cannot produce different numbers from untracked
   files it never imported") and document the argv0 signal + the named
   residual.
