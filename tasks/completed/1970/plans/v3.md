# Plan v3 — #1970 daily-fix: inline-round pod upload-verify satisfier

## Plan Summary

Give user-chat inline rounds a sanctioned, documented upload-verification-then-terminate
path, and add the all-HF-prefixes enumeration duty for per-issue upload-verify scripts.
0 GPU-h, docs + refusal-message + pin tests. NOT architectural: no status enum, marker
schema, or `task.py` subcommand changes — the marker kind `epm:upload-verification`
already exists and the guard's satisfier logic is byte-untouched.

## Requirement + acceptance criteria (kind: infra — code change)

Origin (task #1970 body, incident #1773 / session 0ac15c23): an inline round that had
ALREADY verified its uploads could not terminate its pod through a sanctioned path —
the terminate guard's refusal message names only "/issue <N> Step 8" and
`--skip-upload-verify`, so the round improvised the blunt override; and the round's
per-issue upload-verify script silently scoped verification to one HF prefix
(`fulldict/`), leaving the `raw_windows` prefix (8h50m of GPU output) verified only by
an ad-hoc hand set-diff (the #779 silent-loss shape).

**Grounding finding (clarifier, 2026-08-03, supersedes the body's proposed-change
premise):** `_has_upload_verification_pass` (scripts/pod_lifecycle.py:2662) reads the
LATEST `epm:upload-verification` event's note and accepts a JSON `{"verdict": "PASS"}`,
a bold `**Verdict: PASS**`, a loose `Verdict: PASS`, or a bare LEADING `PASS` token —
regardless of who posted it. The bare-leading-PASS branch was added for exactly
"orchestrator-posted notes" (incident #465, comment at lines 2708-2722; pin tests
`test_has_upload_verification_pass_reads_note_body_pass` + siblings). **The inline-round
front door therefore ALREADY EXISTS mechanically** — an inline round that posts
`epm:upload-verification` with a PASS verdict satisfies the guard today. The gap is
(1) nothing documents this (CLAUDE.md: 0 `skip-upload-verify` hits; the carve-out's
completion-side teardown clause mandates verify-then-terminate but never names the
guard or the recipe), (2) the guard's SystemExit refusal text itself steers a refused
session straight to `--skip-upload-verify`, and (3) no duty line anywhere requires a
per-issue upload-verify script to enumerate ALL HF prefixes the run wrote.

Acceptance criteria:

1. The terminate guard's refusal message (SystemExit in
   `_guard_upload_verification_before_terminate`, scripts/pod_lifecycle.py:2809-2819)
   names the sanctioned inline-round recipe — run the round's verification, post
   `epm:upload-verification` with a PASS verdict note naming the verified prefixes via
   `task.py post-marker`, re-run terminate — BEFORE the `--skip-upload-verify` last
   resort. The guard's docstring gains the same sentence. Satisfier LOGIC is
   byte-untouched (no change to `_has_upload_verification_pass` or the guard's
   decision flow).
2. CLAUDE.md § "User-chat inline free analysis" carve-out, "Completion-side teardown
   (no ask-gate)" clause: gains (a) one sentence naming the recipe (verify THIS
   round's artifacts → post `epm:upload-verification` (PASS verdict, note naming
   every verified prefix) via `task.py post-marker` → terminate; bare
   `--skip-upload-verify` without a recorded verify is the anti-pattern, reserved for
   never-ran pods), and (b) one duty sentence: a per-issue upload-verify script MUST
   enumerate ALL HF prefixes the run wrote (reconcile against the run's
   staging/upload call sites), never only the current phase's prefix (#1773:
   `raw_windows`, 8h50m of GPU output, verified only by hand).
3. `.claude/skills/issue/SKILL.md` Step 9a-ter § "Completion-side teardown (no
   ask-gate)" (the canonical block, ~line 7777): mirrors the same two sentences.
4. `tests/test_pod_lifecycle.py` gains two pin tests:
   (a) an inline-round-shaped marker note (leading `PASS (inline-round verification;
   prefixes: <a>, <b>)`) satisfies `_has_upload_verification_pass` → terminate
   proceeds without `--skip-upload-verify` (pins the documented recipe's exact note
   shape onto the existing parser);
   (b) the refusal message names the inline recipe (`epm:upload-verification` +
   `post-marker` substrings in `str(exc.value)`) — the message-content sibling of the
   existing `assert "--skip-upload-verify" in str(exc.value)`.
5. Pipeline-path semantics UNCHANGED: all existing `test_pod_lifecycle.py` guard tests
   still pass; the bold-Verdict anchoring test
   (`test_has_upload_verification_pass_anchors_on_bold_verdict_line`) untouched.
6. A NEW prose durability pin test `tests/test_issue_skill_inline_upload_verify_recipe.py`
   asserts BOTH prose surfaces carry the recipe + the all-prefixes duty: CLAUDE.md's
   completion-side teardown clause and SKILL.md Step 9a-ter's canonical block each
   contain the `epm:upload-verification` recipe sentence and the enumerate-ALL-HF-prefixes
   duty sentence (substring pins on stable tokens, not full-sentence byte pins).

Fail-loud pin: tests/test_pod_lifecycle.py::test_terminate_guard_refusal_names_inline_recipe — pytest.raises(SystemExit) asserts the guard still raises (never silently proceeds) on a missing PASS marker and its message names the inline recipe; no swallow/except path is added by this diff.

## Method delta (vs the task body's diff sketch)

The body sketched a CODE change ("Accept an inline-round verification satisfier ... a
marker posted by the inline round itself"). Clarifier grounding shows that satisfier
already exists (the guard is poster-agnostic by design, #465), so this plan REPLACES
the satisfier-logic change with: refusal-message + docstring text (the surface that
steered #1773 to the override), documentation in the two prose surfaces the carve-out
reads, and pin tests that freeze the recipe's note shape into the parser contract.
This is a smaller, strictly safer diff: the "must not weaken the pipeline path"
constraint is satisfied by construction (zero satisfier-logic bytes change).
