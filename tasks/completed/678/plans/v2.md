## 1. Goal

Replace the lightweight `Agent(subagent_type="workflow-improver", run_in_background=true, isolation="worktree")` auto-spawn in the workflow-fix-on-bug protocol with a heavier, fully-reviewed path: when a workflow-fix candidate is raised (a formal `<!-- workflow-fix-candidate v1 -->` block OR a surfaced prose follow-up), the receiving orchestrator **files a `kind: infra` task** pre-filled from the candidate, then **spawns a background `/issue <N> --auto` session** to implement it. The fix then lands via the full `/issue` code-change pipeline — clarifier → `/adversarial-planner` (planner + Phase-2 critic ensemble ∥ consistency-checker) → plan-approval gate → worktree + `experiment-implementer`/`implementer` → Claude+Codex `code-reviewer` ensemble → inline test-verdict → auto-complete + Step 10d worktree auto-merge — instead of "edit + one review". The workflow surface is where a bad change has the widest blast radius, so it earns the heaviest review, not the lightest. The user's directive (verbatim): *"Instead change it so it uses a background happy coder session (so we get the plan review and all this)."* This task (#678) is itself the FIRST instance of the new pattern, filed + spawned by hand because the new mechanism cannot route its own creation.

## 2. Prior work / sibling pattern

The migration target reuses an already-production-tested mechanism: the autonomous `/issue` session spawner.

**Invocation shape** (verified by `uv run python scripts/spawn_session.py spawn-issue --help`):

```bash
uv run python scripts/spawn_session.py spawn-issue --issue <N> --auto
```

`--auto` is documented as *"Shorthand for `--initial-prompt '/issue <N>'`"*; it boots the full `/issue <N>` skill in `bypassPermissions` mode (no human at the keyboard) and arms the recurring `/issue-tick <N>` cron.

**Env injection** (read at `scripts/spawn_session.py:858-866`): a prompt-bearing (`--auto`) spawn sets, in the new session's environment:

```python
body["environmentVariables"] = {
    "HAPPY_INITIAL_PROMPT": prompt,                 # "/issue <N>"
    "HAPPY_INITIAL_MODE": "bypassPermissions",
    "EPM_AUTONOMOUS_SESSION": "1",                  # push-through-bugs autonomous mode
    "EPM_PLAN_AUTOAPPROVE_GPU_HOURS": str(args.auto_approve_gpu_hours),  # default 100
}
body["claudeArgs"] = ["--dangerously-skip-permissions", *extra_args]
```

So `EPM_AUTONOMOUS_SESSION=1` is set ONLY by a `--auto` spawn (confirmed: it appears in `cmd_spawn_issue`'s prompt branch and `cmd_spawn_campaign`, never on a bare interactive spawn). `EPM_PLAN_AUTOAPPROVE_GPU_HOURS` defaults to `100` (`--auto-approve-gpu-hours` default).

**Registration file** (written by `_register_autonomous_session`, `scripts/spawn_session.py:891-902`): one file per issue at `~/.eps-autonomous/issue-<N>.json` (`AUTONOMOUS_REGISTRY_DIR = Path.home() / ".eps-autonomous"`, line 58). The write is an atomicity invariant — if registration fails the just-spawned session is stopped and the spawn aborts ("a live `--auto` session MUST have a current registry entry, else the watcher could re-spawn it as a duplicate → duplicate pod → spend"). Manual (non-`--auto`) issue sessions register a sibling `~/.eps-autonomous/manual-issue-<N>.json` for `list` enrichment only.

**Watcher contract** (`scripts/autonomous_session_watch.py`, every 10 min): crash-recovery respawn of registered `--auto` sessions, pod-safety reconciliation, stalled-session detection, a capacity-retry pass, and a gate-push pass (Telegram phone push on gate-park / `blocked` transitions). A workflow-fix `/issue` session inherits ALL of this for free.

**Production-tested:** the clarifier's `epm:clarify` note records that `spawn-issue --issue <N> --auto` was *"used for #676/#677/#678 same day"* — i.e. this exact spawner ran three times the same day this task was filed. The mechanism is not new; only its NEW caller (the workflow-fix protocol) is.

## 3. The six design questions — decisions + rationale

### Q1 — All candidates, or a threshold? → **All in-scope candidates route to a session. No threshold, no lighter path.**

Every in-scope, non-architectural candidate (formal block OR prose follow-up) files an infra task + spawns `/issue <N> --auto`. There is no "trivial one-liner" fast lane. **Rationale:** the user's bias is "full session for anything non-trivial", and the protocol cannot mechanically distinguish trivial from non-trivial without LLM judgement on the trigger — which the current `surgical | substantive | architectural` classification proves is itself an LLM call inside the spawned agent, not a parseable gate the orchestrator can apply pre-spawn. A size threshold (`diff_sketch` line count) is gameable and was never the cost driver; the cost of a session is ~30-60 min wall (acceptable for the workflow surface, §7). Routing ALL candidates keeps the trigger purely mechanical (candidate present → file + spawn), which is the whole point of the migration. The full `/issue` pipeline self-sizes: a genuinely one-line fix produces a trivial plan that auto-approves at 0 GPU-h and a one-round implementer + code-review — heavier than today's path, but uniformly so, with no decision branch to get wrong.

### Q2 — Fate of `workflow-improver`. → **Retire it.** Archive its agent file with a DEPRECATED banner; DEDUP-MERGE its agent-memory into `.claude/agent-memory/implementer/`.

The `/issue` Step 4b code-change path already dispatches `experiment-implementer` (for experiment code) or `implementer` (for standalone infra / refactor / utility code — which is exactly what a workflow-surface edit is). The new path's infra task is `kind: infra`, so `/issue` routes it to `implementer` at Step 4b. There is no implement step for `workflow-improver` to occupy — `implementer` already owns it. **Rationale:** repurposing `workflow-improver` as the Step-4b implementer would duplicate `implementer`'s role and force a second `subagent_type` decision in SKILL.md keyed on "is this a workflow-fix task?", reintroducing exactly the brittle branch this migration removes. Retiring is cleaner and matches the precedent for the retired `reviewer` agent (frozen file, DEPRECATED banner, kept for historical reference).

**Agent-memory disposition (now a DEDUP-MERGE, not a blind `git mv` — Methodology rec #4).** `workflow-improver`'s memory files encode hard-won workflow-surface-editing lessons (worktree-vs-main edit discipline, lint-emit-tables regen, pre-existing-lint baselines, reuse-fitness mirror sets, watcher test recipes). These remain valuable to whoever now edits the workflow surface — the `implementer`. BUT `.claude/agent-memory/implementer/` **already exists with 9 entries**, and at least three incoming memos thematically DUPLICATE existing implementer memos:

| incoming (workflow-improver) | existing (implementer) — overlap |
|---|---|
| `feedback_hook_strips_imports.md` | `feedback_posttooluse_ruff_strips_imports.md` |
| `feedback_edit_lands_in_main_not_worktree.md` | `feedback_worktree_path_discipline.md` |
| `reference_workflow_lint_emit_tables.md` | overlaps `feedback_workflow_yaml_pattern.md` |

So the disposition is a **dedup-merge pass, NOT a directory clobber**:
1. For each `workflow-improver/*.md`, check whether an implementer memo already covers the same lesson (the table above is the known set; the implementer greps `implementer/` for thematic overlap on the rest).
2. **Non-duplicate memos:** `git mv` into `.claude/agent-memory/implementer/`.
3. **Duplicate memos:** do NOT clobber the existing implementer file — MERGE any net-new content (an extra incident line, a sharper "Why"/"How to apply") into the existing implementer memo, then `git rm` the workflow-improver copy. If the incoming memo is strictly subsumed, just `git rm` it.
4. **`MEMORY.md` index:** MERGE the workflow-improver index lines into `implementer/MEMORY.md` (one line per surviving memo) — never overwrite the existing 9-entry index. Drop the index line for any memo deleted as a duplicate.
5. Remove the now-empty `workflow-improver/` directory (incl. its `MEMORY.md`).

Do NOT delete the live lessons and do NOT archive-to-`_archive` — they are live, and `implementer` is the agent that will now hit those same traps.

### Q3 — Candidate → task mapping. → **File a `kind: infra` task; dedup on `target_file + candidate-fingerprint`, keyed PRIMARILY by a `workflow-fix:` TITLE PREFIX and a `wf-fix-fp:<fp>` TAG (both round-trip through `view --json` / REGISTRY); `workflow_fix_target:` body-frontmatter line is the documented WORKING fallback. Then spawn `--auto`.**

**[A1 — dedup GRAIN fix, the load-bearing v2 change.]** v1 deduped on `target_file` ALONE, which would SILENTLY DROP a SECOND distinct bug raised on the same hot file (SKILL.md, CLAUDE.md, and workflow-fix-on-bug.md itself routinely get multiple distinct candidates per week). That is a REGRESSION against the CURRENT rule (`.claude/rules/workflow-fix-on-bug.md` lines 459-461: "Queue the new candidate as a follow-up via `SendMessage` to the running agent rather than spawning a second one" — i.e. BOTH bugs get fixed). v2 adopts **Option A — candidate-fingerprint dedup** (chosen over Option B attach-to-existing-task because it is cleaner — two distinct bugs become two distinct tasks each getting its own plan review, matches the per-candidate granularity Q1 defends, is simpler to test, and avoids the non-trivial wiring of plumbing a second-candidate-in-flight into an already-spawned session's planner-amendment surface).

**The dedup key is `target_file + candidate-fingerprint`:**

```
fingerprint = sha256( normalize(proposed_change) + "||" + normalize(bug_observed) )[:12]
normalize(s) = s.lower(), collapse internal whitespace to single spaces, strip leading/trailing
               whitespace, strip trailing punctuation (.,;:!?)
```

- Same `target_file` + **same** fingerprint (the same bug re-raised) → DUPLICATE → do NOT double-file; log `epm:workflow-fix-candidate` note `deduped against open #<M>` and continue.
- Same `target_file` + **different** fingerprint (a DISTINCT bug on the same hot file) → NOT a duplicate → file a new task. Each gets its own plan review. **This is the A1 fix.**
- The orchestrator computes the fingerprint at file-time from the candidate block fields (for a prose follow-up, from the synthesized `proposed_change`/`bug_observed`) and records it in the body's `## Provenance` block AND as the `wf-fix-fp:<fp>` tag (below).

**Dedup KEY SURFACES (Methodology rec #1/#2/#3 — primary key + working fallback, never `set_body`):**

`task.py new --kind infra` builds frontmatter from its OWN flags only and writes `req.body` VERBATIM (confirmed: `create_task`, `task_workflow.py:1023-1072` — the canonical `fm` dict is `{title, kind, tags, created_at, has_clean_result, [parent_id], [origin_prompt], [goal]}`; anything in the body-file's own frontmatter is written into the BODY text, NOT promoted to a frontmatter key). And `set_body` STRIPS all leading frontmatter except `paper`/`abstract` (`_strip_leading_frontmatter_blocks` + `_SET_BODY_ROUNDTRIP_KEYS`, `task_workflow.py:589-622,1088`). Therefore a custom `workflow_fix_target:` frontmatter key does NOT round-trip as a true frontmatter key through `view --json .frontmatter`. The dedup keys are layered so the PRIMARY ones surface cleanly via `view --json` while the body-line stays a working grep fallback:

1. **PRIMARY (round-trips through `view --json` + REGISTRY):**
   - **Title prefix** — `task.py new --title "workflow-fix: <proposed_change, <=60 chars>"` (set via the `new` flag, written into `fm["title"]`; for any later correction use `set_title`, which writes `fm["title"]` AND updates the REGISTRY snapshot — `task_workflow.py:1148-1158`). The literal `workflow-fix:` prefix is the cheap first filter and surfaces through `view --json .frontmatter.title` and through the dashboard list view.
   - **Fingerprint tag** — `task.py add-tag <N> wf-fix-fp:<fp>` immediately after `new` (and a coarse `wf-fix` tag). Tags round-trip through `view --json .frontmatter.tags`. The `(target_file, fingerprint)` identity is reconstructable from the title prefix + `wf-fix-fp:<fp>` tag + the `## Provenance` block, all `view --json`-visible.
2. **FALLBACK (documented, WORKING):** the body still carries a literal `workflow_fix_target: <target_file>` line inside the `## Provenance` block (written verbatim by `create_task`). When the title/tag surfaces are insufficient (e.g. a hand-filed task that skipped the tag), the dedup falls back to grepping the literal line `workflow_fix_target: <path>` in the task's `body.md`. This fallback WORKS precisely because `--body-file` writes the body verbatim — the line is present and grep-findable.
3. **NEVER** route any of these keys through `set_body` — it strips leading frontmatter (rec #3). The keys live in the title (frontmatter via `new`/`set_title`), in tags (via `add-tag`), and in the body's `## Provenance` block — none of which `set_body` touches for these fields.

The orchestrator, on receiving an in-scope non-architectural candidate, runs (after the existing grep-the-surface-first + one-formal-block-per-invocation rules, both preserved):

```bash
# 0. RECURSION GUARD (Q4): if THIS session is a workflow-fix session, do NOT file/spawn.
#    (workflow_fix_target in the task body's Provenance OR EPM_WORKFLOW_FIX_SESSION=1)
#    -> log epm:workflow-fix-candidate note "parked — EPM_WORKFLOW_FIX_SESSION", notify, STOP.

# 1. COMPUTE the fingerprint from the candidate fields:
#    fp = sha256(normalize(proposed_change)+"||"+normalize(bug_observed))[:12]

# 2. DEDUP: skip ONLY if an OPEN workflow-fix infra task has the SAME (target_file, fp).
#    Union the NON-terminal statuses, read each via `task.py view <M> --json`:
#      - quick filter: title starts "workflow-fix:" AND a `wf-fix-fp:<fp>` tag is present
#        AND the `## Provenance` workflow_fix_target line matches target_file (exact).
#    A (target_file, fp) hit -> do NOT double-file; log "deduped against open #<M>", continue.
#    Same target_file but DIFFERENT fp -> NOT a duplicate -> proceed to file (A1).
NONTERMINAL="proposed planning plan_pending approved running verifying interpreting \
             reviewing awaiting_promotion followups_running blocked on_hold"

# 3. FILE the infra task (no dedup hit):
uv run python scripts/task.py new --kind infra \
  --title "workflow-fix: <proposed_change, <=60 chars>" \
  --body-file /tmp/wf-fix-body-<slug>.md \
  --origin-prompt "<verbatim candidate block OR surfaced prose>"
# -> returns new id N

# 4. TAG the dedup keys onto N (round-trip via view --json .frontmatter.tags):
uv run python scripts/task.py add-tag <N> wf-fix
uv run python scripts/task.py add-tag <N> "wf-fix-fp:<fp>"

# 5. SPAWN the autonomous session:
uv run python scripts/spawn_session.py spawn-issue --issue <N> --auto

# 6. POST epm:workflow-fix-task-filed v1 on the PARENT task; continue working.
```

**Dedup predicate (exact, A1):** a candidate is a duplicate iff there exists a task with `kind: infra` AND a `workflow-fix:` title prefix AND a `wf-fix-fp:<fp>` tag matching the candidate's fingerprint AND a `## Provenance` `workflow_fix_target:` line EXACTLY string-matching the candidate's `target_file` AND whose status is NOT in the terminal set `{completed, archived}`. Same file + DIFFERENT fingerprint is NOT a duplicate. The library helper `task_workflow.is_open_workflow_fix_task(target_file, fingerprint) -> int | None` (§4, §6) is the canonical, tested implementation of this predicate.

### Q4 — Recursion guard. → **A session is a workflow-fix session iff its task carries the `workflow_fix_target:` Provenance line (durable, the SAME primary signal Q3 keys on) OR `EPM_WORKFLOW_FIX_SESSION=1` (in-session convenience flag). Such a session NEVER auto-files/spawns more — it logs + notifies. Analogue of `AUTO_REVIEW_DISABLED`.**

A workflow-fix `/issue` session must not auto-file MORE workflow-fix sessions for its own subagents' findings (otherwise: implementer → emits candidate → orchestrator files+spawns → that session's implementer emits a candidate → ... unbounded fan-out — the named failure mode the test below pins). **Mechanism:** the candidate-receive logic (in `.claude/rules/workflow-fix-on-bug.md` + SKILL.md Step 0 / candidate-receive) checks the durable signal FIRST (does THIS task carry a `workflow_fix_target:` Provenance line — read the SAME way the Q3 dedup reads it, via `task.py view <N> --json` + the `## Provenance` body grep) and the env var SECOND (`os.environ.get("EPM_WORKFLOW_FIX_SESSION") == "1"`). If EITHER is true, the orchestrator does NOT file/spawn — it LOGS the candidate to `events.jsonl` (`epm:workflow-fix-candidate v1`, note: `parked — running under EPM_WORKFLOW_FIX_SESSION / workflow_fix_target, see §recursion-guard`) and surfaces it as a notification, exactly as the current `AUTO_REVIEW_DISABLED` clause suppresses the spawn ("If your prompt carries that sentinel, treat workflow-fix candidate emission as forbidden for the turn").

**Why BOTH signals, with the frontmatter/Provenance one durable:**
- **(a, durable) the `workflow_fix_target:` Provenance line** is the robust signal — it survives session restart / watcher crash-recovery respawn (which re-runs `spawn-issue --auto` WITHOUT custom env, so the env var is lost on respawn). The candidate-receive side keys on this primarily. The spawned `/issue` session also self-sets the env var at Step 0 when it detects this signal, for in-session ergonomics.
- **(b) `EPM_WORKFLOW_FIX_SESSION=1`** is the in-session convenience flag. Optionally passed through by the spawner at file-time; lost on watcher respawn, so (a) is the backstop.

The rule text states: *"A session is a workflow-fix session iff its task carries the `workflow_fix_target:` Provenance line OR `EPM_WORKFLOW_FIX_SESSION=1` is set; such a session NEVER auto-files/spawns workflow-fix tasks — it logs + notifies, like `AUTO_REVIEW_DISABLED`."* The escape valve (§7): such a session CAN still emit candidate blocks — they get parked/notified, not auto-routed, so its own workflow-fix bug is never silently lost. The recursion-guard predicate is implemented + tested by `task_workflow.is_workflow_fix_session(N) -> bool` (§4, §6).

### Q5 — Auto-merge / push reconciliation. → **The `/issue` Step 10d worktree auto-merge owns the merge; the plan-approval gate (Step 2c) is the architectural-greenlight surface; the planner decides the gate via an `architectural: true` plan-frontmatter flag.**

Under the new path the orchestrator no longer merges a `workflow-improver` worktree — the spawned `/issue` session owns its Step 10d worktree auto-merge to `main` (already automatic, no approval gate, per the standing 2026-06-03 rule). This SATISFIES "workflow-surface edits are committed + merged + pushed automatically, no approval gate" for non-architectural fixes: the autonomous session auto-approves the plan (0 GPU-h ≤ cap), runs the full pipeline, and Step 10d merges + pushes. **Architectural / public-contract changes still need greenlight**, now expressed as the `/issue` plan-approval gate: the autonomous session AUTO-APPROVES under `EPM_PLAN_AUTOAPPROVE_GPU_HOURS=100` because a workflow fix is 0 GPU-h — so the GPU-h cap alone would auto-approve EVERYTHING, including architectural changes. That is NOT the desired default for the architectural subset. **Reconciliation:** the planner, in the workflow-fix task's plan, sets an `architectural: true` flag in the plan frontmatter (and states a one-line "ARCHITECTURAL — needs user greenlight" banner in the Plan Summary) whenever the change would rename a status enum / change a marker schema or `task.py` subcommand / relocate an agent file / restructure a subsystem (the existing architectural test, verbatim from the suppress-spawn clause). The `/issue` autonomous-approval logic gates on BOTH the GPU-h cap AND `architectural != true`: a plan flagged `architectural: true` PARKS at `plan_pending` for the user regardless of GPU-h, exactly the current architectural-greenlight semantics. Non-architectural workflow fixes (the vast majority) auto-approve at 0 GPU-h and self-merge — preserving the no-greenlight default. **Who decides:** the planner (it already classifies architectural-ness; the suppress-spawn clause's test moves into the planner's §-summary). The GPU-h cap stays 100 as the spawn default; the architectural flag is the orthogonal second gate that the cap does not subsume. (Implementation note: the autonomous plan-approval logic in `/issue` Step 2c must be extended to read `architectural:` from the plan frontmatter and park on `true`. If that wiring is larger than this task should carry, the fallback is: the protocol instructs the orchestrator to spawn architectural candidates WITHOUT `--auto` — i.e. file the task but open a bare session that parks at `plan_pending` until a human types `/issue <N>` — and log the candidate for the user. State this fallback in the rule so the architectural-greenlight invariant holds even if the Step-2c flag wiring is deferred.)

### Q6 — Markers. → **Keep `epm:workflow-fix-candidate|applied|failed` with adapted semantics, AND add one new marker `epm:workflow-fix-task-filed v1`.**

The three existing markers stay (the dashboard + weekly mechanization ratchet read them), with semantics re-pointed at the spawned task:
- `epm:workflow-fix-candidate v1` — UNCHANGED trigger (orchestrator receives a candidate). Posted to the originating/parent task's `events.jsonl` (or `.claude/cache/workflow-fix-events.jsonl` if no task). Now records the routing decision in its note: `routed: filed #<N>` | `deduped against #<M>` | `parked: EPM_WORKFLOW_FIX_SESSION` | `parked: architectural`.
- **`epm:workflow-fix-task-filed v1` (NEW)** — posted on the PARENT task when the orchestrator files the infra task + spawns the session. Fields: `filed_task` (the new id N), `target_file`, `fingerprint` (the dedup fp), `session_spawned` (true/false), `origin_candidate` (verbatim). This is the new lifecycle anchor replacing the old "spawned workflow-improver" log line. Posted to the parent task.
- `epm:workflow-fix-applied v1` — semantics ADAPTED: no longer "workflow-improver landed a diff". Now the SPAWNED workflow-fix task's OWN `/issue` Step 10d completion is the apply event. The protocol posts `epm:workflow-fix-applied v1` to the PARENT task (cross-linking `applied_task: #<N>`, `merge_sha`) when the orchestrator observes the child task reach `completed` (its Step 10d merged). On the CHILD task, the normal `/issue` completion markers (`epm:status-changed → completed`, the Step 10d merge) ARE the apply record — no special workflow-fix marker needed there.
- `epm:workflow-fix-failed v1` — semantics ADAPTED: posted to the PARENT task if the child workflow-fix `/issue` session reaches `blocked` / `archived` without merging. Fields: `failed_task: #<N>`, `failure_reason` (child-blocked | child-archived | spawn-failed), `origin_candidate` (verbatim). A dedup hit (no action) is NOT a failure and posts no `failed` marker.

**Parent vs child split (explicit):** ALL workflow-fix-specific markers (`candidate`, `task-filed`, `applied`, `failed`) fire on the PARENT task (the one that raised the candidate) — they record the routing + outcome from the parent's vantage. The CHILD workflow-fix infra task carries ONLY the standard `/issue` lifecycle markers (created, status-changed, plan markers, implementer/review markers, completion) — it is an ordinary infra task and needs no special markers. This keeps the dashboard's per-task lifecycle clean and lets the parent's events.jsonl tell the "I raised a workflow bug → it was filed as #N → #N merged" story end to end.

import hashlib, re

def _wf_fix_fingerprint(proposed_change: str, bug_observed: str) -> str:
    """Stable 12-hex dedup fingerprint of a workflow-fix candidate.

    normalize: lowercase, collapse internal whitespace to single spaces,
    strip leading/trailing whitespace, strip trailing .,;:!? — so reformatting
    a candidate's prose does not spawn a duplicate task.
    """
    def norm(s: str) -> str:
        s = re.sub(r"\s+", " ", (s or "").strip().lower())
        return s.rstrip(".,;:!?").strip()
    h = hashlib.sha256((norm(proposed_change) + "||" + norm(bug_observed)).encode())
    return h.hexdigest()[:12]

def is_open_workflow_fix_task(target_file: str, fingerprint: str | None = None) -> int | None:
    """Return the id of an OPEN kind:infra workflow-fix task matching this key, else None.

    Dedup key (A1): (target_file, fingerprint). A task matches iff kind==infra AND
    status NOT in {completed, archived} AND title startswith 'workflow-fix:' AND its
    body ## Provenance carries `workflow_fix_target: <target_file>` (exact). When
    `fingerprint` is given, the task must ALSO carry a `wf-fix-fp:<fingerprint>` tag
    (or a `fingerprint: <fingerprint>` Provenance line) — so a DIFFERENT bug on the
    same file (different fingerprint) is NOT a duplicate. When `fingerprint` is None,

    have no candidate fingerprint).

        body = (find_task_path(tid) / "body.md").read_text()

- **Blast radius:** workflow-surface only — no experiment code, configs, or task-state touched. - **Rollback:** a single `git revert` of the PR's merge commit on `main` restores the old `Agent(workflow-improver)` path verbatim (the frozen agent file's body is intact; un-freezing is a one-line banner removal). Low-risk reversal.
- **[CLOSED RISK — false-POSITIVE dedup (A1, fixed in v2)]:** v1's `target_file`-only dedup would have SILENTLY DROPPED a second distinct bug raised on the same hot file (a regression vs the current rule's queue-to-the-running-agent behavior, where BOTH bugs get fixed). v2 closes this: the dedup grain is `(target_file, fingerprint)`, so a distinct bug on the same file (different fingerprint) files its own task and gets its own plan review. The A1 regression-guard test (`test_open_same_file_DIFFERENT_fp_is_NOT_duplicate`) pins it. Only a genuine same-bug re-raise (same fingerprint) is deduped.
- **Recursion-guard misfire (escape valve preserved):** a workflow-fix `/issue` session must still be able to surface its OWN workflow-fix bug. Mechanism: such a session CAN emit `<!-- workflow-fix-candidate v1 -->` blocks — under the guard they are LOGGED to `events.jsonl` + surfaced as a notification (Telegram via the watcher gate-push, or the parent's next chat turn) rather than auto-routed. So a genuine workflow bug discovered DURING a workflow-fix is never silently lost; it is parked for the next human/orchestrator pass exactly as `AUTO_REVIEW_DISABLED`-suppressed candidates are. The risk is a one-cycle delay, not a dropped bug. The guard predicate is executable-tested (§6, case 7) — the "unbounded fan-out" failure mode does not rely on inspection.
- **Latency shift (called out, accepted):** an emit site that previously got a same-turn background fix (~minutes) now waits for a session spawn + planner round + critic ensemble + implementer + code-review (~30-60 min wall). This is the intended trade — the user explicitly asked for "the plan review and all this", and the workflow surface's wide blast radius justifies the heavier review. The originating agent's own work is NOT blocked (the file+spawn is non-blocking, identical to today's background spawn); only the FIX lands slower. Acceptable for the workflow surface; stated in the rule so no future reader mistakes it for a regression.
- **Dedup false-NEGATIVE (bounded, not silent):** if `view --json` somehow misses the title/tag surfaces (e.g. a hand-filed task that skipped the tag step), the dedup falls back to the literal body grep on the `workflow_fix_target:` Provenance line (always present via `--body-file`-verbatim). Worst case on a total miss: a duplicate workflow-fix task is filed (two sessions edit the same file) — caught by the `/issue` Step 10d worktree merge (the second merge hits a conflict, aborts, requeues per the existing merge-conflict discipline). Bounded, not silent.
- **Architectural-greenlight wiring risk:** if extending Step 2c to read `architectural:` frontmatter is deferred, the fallback (file the task but spawn WITHOUT `--auto`, parking at `plan_pending` for the user) preserves the greenlight invariant. Stated in Q5 so the invariant holds regardless of wiring depth.
