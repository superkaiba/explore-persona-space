## 3. Design

### 3.1 `scripts/task.py` — CLI-layer truncation (the core fix)

**(i) New module-level constant + helper**, placed immediately above `cmd_raise_concern` (~L1085):

```python
CONCERN_SUMMARY_CAP = 200


def _truncate_summary(summary: str, cap: int = CONCERN_SUMMARY_CAP) -> tuple[str, str | None]:
    """Truncate an over-cap concern summary at a word boundary.

    Returns ``(kept, dropped_tail)``. ``dropped_tail`` is ``None`` when
    ``summary`` already fits. When truncated, ``kept`` is <= ``cap`` chars,
    ends with ``"..."``, and cuts at the last space at or before the
    budget (hard-cut when the text has no space in that span).
    """
    if len(summary) <= cap:
        return summary, None
    budget = cap - 3  # room for the "..." marker (ASCII, not U+2026)
    cut = summary.rfind(" ", 0, budget + 1)
    if cut <= 0:
        cut = budget
    kept = summary[:cut].rstrip() + "..."
    return kept, summary[cut:].strip()
```

(ASCII `"..."` deliberately, not U+2026 `…` — dodges the Edit-tool Unicode-literal gotcha in `.claude/rules/gotchas.md` and keeps the marker grep-safe. `len(kept) <= budget + 3 = cap` by construction.)

**(ii) `cmd_raise_concern` (L1087-1103)** — truncate before calling the library; shift the full original into evidence when evidence is empty:

    """... existing docstring + one added line:
    An over-cap ``--summary`` is truncated at a word boundary with a loud
    stderr warning (full original shifted into evidence when --evidence
    is empty); the library layer keeps the hard 200-char cap."""

## 11. Decision Rationale

1. **Design option: (b) CLI-layer graceful truncation + (a) message/help fixes, library cap unchanged.**
   - What: truncate at the CLI, warn loudly, preserve full text in evidence (raise path); improve both error messages + help strings; keep the library `ValueError`.
   - Why: only default-on CLI truncation achieves the Goal's ZERO round-trips — option (a) alone still costs one bounce per over-cap composition (#1090 burned two retries even though the raise-path help names the cap: sessions compose long summaries anyway); option (c) (library-layer soft handling) would silently change what programmatic callers store and weaken the fail-loud contract for code bugs. The CLI is exactly where agents (the round-trip payers) live; programmatic callers should fix their code, and the loud warning + evidence-shift keep the truncation non-silent and content-preserving, satisfying the design constraint "any truncation is loud … stored-data contract stays intact".
   - Source: incidents #1398 (324 chars, 1 bounce) + #1090 (argparse bounce then 203 chars, 2 retries) from the task `origin_prompt`; `workflow.yaml:1426` (5 reviewer crashes on 2026-06-10 alone, 238-410 chars — the recurrence rate justifying default-on); prior art in the 2026-06-10/11 daily logs proposed exactly "auto-truncate to 200 with detail shifted to --evidence, or print the limit in argparse help" — this design implements both halves.
   - Alternatives rejected: (a)-only (still ≥1 bounce per hit); (c) library truncation (silent programmatic behavior change; contract weakening); opt-in `--truncate-summary` flag (the flag is only discoverable by tripping the error → still 1 bounce, plus new CLI surface).
2. **Cover BOTH subcommands (raise-concern AND address-concern).**
   - What: identical truncation in both `cmd_` handlers.
   - Why: the tax is symmetric — #1398's 324-char hit was in the raise/address flow and `workflow.yaml:1428` states "the same cap applies to address-concern carried summaries"; raise-concern's help already names the cap yet sessions still compose >200 (help alone demonstrably insufficient), and fixing one path while the sibling still tracebacks would re-file this task in a month.
   - Source: task body ("Consider BOTH subcommands"); `workflow.yaml:1424-1429`.
   - Alternatives: address-concern-only (leaves the #1398 raise shape crashing).
3. **Cap value 200 unchanged.**
   - What: `CONCERN_SUMMARY_CAP = 200`, library checks untouched.
   - Why: the cap itself is a deliberate design (one-line summaries; detail in evidence; the 80-char mirror slice depends on summaries being labels, `task_workflow.py:6450`); the bug is discoverability + crash cost, not the value. Changing it would invalidate 5 doc exemplars + the workflow.yaml contract for zero Goal benefit.
   - Source: `workflow.yaml § concerns_protocol.summary_cap`; task brief ("the hard cap at the storage layer may stay").
   - Alternatives: raise to 300 (moves, doesn't remove, the tax; touches a public prose contract).
4. **Truncation boundary rule: cut at the last space ≤ (cap − 3), rstrip, append ASCII `"..."`; hard-cut when spaceless; UNBOUNDED overage handling (no 2×-cap ceiling).**
   - What: `_truncate_summary` as specced in §3.1(i), applied to any overage size.
   - Why word boundary + marker: a mid-word cut reads as corruption in `list-concerns` output; the `"..."` marker makes truncation visible in the stored row itself, not only in the transcript. Why ASCII: the Edit-tool Unicode-literal gotcha (`.claude/rules/gotchas.md`) + grep-safety. Why unbounded: a size threshold would add a second magic constant and re-introduce the crash above it; content is preserved (evidence on raise, warning tail on address), so even a large mis-paste yields a sane record instead of a traceback. Why not `textwrap.shorten`: it collapses ALL internal whitespace runs (mutates content beyond truncation).
   - Source: daily-log prior art ("auto-truncate to 200 with detail shifted to --evidence"); #1090's 3-char overage as the canonical small-overage case.
   - Alternatives: bound truncation at 2× cap with hard-error above (kept as the §6 fallback if review judges unbounded too permissive); `textwrap.shorten` (rejected, whitespace mutation); U+2026 ellipsis (rejected, tooling gotcha).
5. **Evidence-shift on raise-concern only when `--evidence` is absent; never mutate provided evidence.**
   - What: `evidence = args.summary` iff truncated AND `args.evidence is None`; otherwise evidence untouched + tail printed in the warning.
   - Why: preserves the reviewer's full text in the durable record in the common case (over-cap summaries usually arrive WITHOUT separate evidence — the text WAS the detail) while never overwriting or appending to deliberately-authored evidence; `address_concern` payloads have no evidence field (`task_workflow.py:6608-6616`), so the address path's tail lives in the stderr warning + the implementer's round report, which is where address rationale belongs anyway.
