# Plan v5 — Task #2278: bootstrap_pod.sh `python` shim recursively deadlocks uv interpreter discovery on pod venv rebuilds

**Kind:** infra (workflow-surface fix: one shell script + one rules doc + tests). **Provenance:** `workflow_fix_target: scripts/bootstrap_pod.sh`; surfaced as a formal `workflow-fix-candidate` by the experimenter on pod-2225-fu1 (2026-08-13). No parent experiment, no experimental recipe inherited.

## Requirement

`scripts/bootstrap_pod.sh` Step 6 installs `/usr/local/bin/python` whose body is `exec uv run python "$@"` (lines 561-576). `/usr/local/bin` is on the default PATH for non-interactive non-login SSH shells, so it is the FIRST `python` uv's interpreter discovery finds. When uv must probe interpreters, it executes that candidate as `<candidate> -c "<get_interpreter_info probe>"` — which re-enters uv. The nested `uv run` blocks on the project lock the parent `uv sync` already holds: a silent futex deadlock, a fresh stacked `get_interpreter_info` probe every ~5 min, zero output.

**Verified ordering fact (narrows the fix surface):** bootstrap's own `uv sync --locked` is Step 5 (line 404), which runs BEFORE the shim is written in Step 6 (line 563). A fresh bootstrap therefore never deadlocks. The trap is LATENT and fires only on a POST-bootstrap sync — the observed trigger being a checked-out issue branch whose `uv.lock` differs from what bootstrap synced on `main`, making a later `uv run` sync implicitly.

Ground truth for the mechanism, the two adjacent traps, and the verified recovery: experimenter memory `pod-venv-rebuild-overlay-runbook` (`.claude/agent-memory/experimenter/feedback_pod_venv_rebuild_overlay_runbook.md`, commit `ca87126778`), written from live forensics on pod-2225-fu1.

## Acceptance criteria (verbatim from the task body)

1. On a pod whose branch changes `uv.lock` post-bootstrap, `uv run python -c "import torch"` triggers a sync that completes without deadlock.
2. Shim behavior for interactive `python` unchanged.
3. Gotchas entry landed; bootstrap change smoke-tested on a fresh provision.

## Root-cause analysis → which layer is load-bearing

The deadlock needs BOTH of: (i) uv resolves a PATH `python` candidate, and (ii) executing that candidate re-enters uv. Layer (ii) is the defect and the only layer whose removal is sufficient. Layer (i) can be suppressed by pinning `UV_PYTHON`, but **an env pin would not have prevented this incident**: the incident surface is a non-interactive `ssh pod "uv run ..."`, which sources neither `/root/.bashrc` / `/root/.profile` (they bail on the `[ -z "$PS1" ] && return` guard — the very reason the shim exists, line 566) nor the project `.env` (read by `orchestrate.env.load_dotenv` inside Python, not by the invoking shell). This is why the fix below is a shim rewrite, with the pin kept only as cheap defense-in-depth on the surfaces where it is free.

### 1. `scripts/bootstrap_pod.sh` — rewrite the shim body so no code path invokes uv (LOAD-BEARING)

Replace the `PYEOF` heredoc body (lines 563-574). New body resolves an interpreter directly and `exec`s it:

- keep verbatim: the `PATH` export, the `PYTHONPATH=/workspace/explore-persona-space` export (#1172), and `cd /workspace/explore-persona-space || exit 1`;
- **additionally prepend `/workspace/explore-persona-space/.venv/bin` to the shim's `PATH` export**, for parity with the behavior being replaced: `uv run` put the venv's `bin` on the child's PATH, so a subprocess launched from shim-python could resolve console scripts (`ruff`, `pytest`, …). Without this, that resolution silently changes — a one-line cost to keep acceptance bullet 2 true in one more respect;
- replace `exec uv run python "$@"` with a resolution chain: `exec` the project venv interpreter `/workspace/explore-persona-space/.venv/bin/python` when executable (this is the SAME interpreter `uv run python` selected, and it resolves correctly through the overlay-venv `.venv` symlink recovery too), else fall back to the first executable of `/usr/bin/python3.11` → `python3.11` → `python3` found via `command -v`, else exit 1 with a loud message naming the missing venv;
- **the fallback branch emits a one-line stderr WARN** naming the missing venv before exec-ing the system interpreter. Without it, a pod with an absent or dangling `.venv` — precisely the post-resume state change 2b addresses — silently runs a dependency-less interpreter, and the user sees an inexplicable `ModuleNotFoundError` on `import torch` instead of the real cause. stderr is safe here: uv's discovery probe parses stdout only;
- **no `uv` token anywhere in the shim body** — the deadlock becomes impossible by construction rather than by a heuristic "am I being probed by uv?" test (uv sets no reliable marker on discovery probes, so any such test would be fragile).

**Stated deviation from a literal reading of acceptance criterion 2:** the shim no longer performs uv's implicit `uv.lock` → venv sync as a side effect of running `python`. Everything a caller observes about the interpreter is unchanged (same executable, same `sys.path` with the repo root prepended, same cwd). The dropped implicit sync IS the defect — a bare `python` invocation silently mutating the pod's environment is what turns a lock-file delta into a wedge — so removing it is intended, not collateral. Callers that WANT a sync keep calling `uv run` / `uv sync` explicitly, unchanged.

**Implementation constraint (existing regression guard):** the whole Step-6 payload is a single-quoted `ssh_cmd '` argument (opens line 436, closes line 577), so the new body must contain NO literal single quote, and `tests/test_bootstrap_pod_payload_quoting.py` bans live backticks and multi-line-region `$(` inside double-quoted regions. The shim body is inside a quoted heredoc (`<<"PYEOF"`), so `$@` / `$PYTHONPATH` stay unexpanded at composition time.

### 2. `scripts/bootstrap_pod.sh` — three small companion changes

**(a) Post-install shim self-test (Step 6, after `chmod +x`).** Run `/usr/local/bin/python -c "import sys; print(sys.executable)"` and fail the step loudly if it does not print an interpreter path. Makes acceptance criterion 3's "smoke-tested on a fresh provision" mechanical: every future provision proves the shim resolves, instead of the breakage surfacing hours later as a silent hang.
  - **The failure branch must exit explicitly** — `|| { echo "..." >&2; exit 1; }`. Verified: the local script sets `set -euo pipefail` (line 46) and `ssh_cmd` (line 93) propagates only the REMOTE command's exit status, but the Step-6 remote payload itself carries no `set -e`, and the self-test sits upstream of the payload's closing `echo` lines — so without an explicit non-zero exit a failing self-test is swallowed by the last `echo`'s success. Test 6 is what pins this.

**(b) Dangling-`.venv`-symlink guard (Step 5, immediately before `uv sync --locked`, line ~404).** `if [ -L .venv ] && [ ! -e .venv ]; then rm -f .venv; fi`. Two lines. Covers the lifecycle hazard the runbook's overlay recovery introduces and does NOT mention: `/root` is the container overlay, recreated by RunPod on `pod.py stop` → `resume`, so a `.venv → /root/eps-venv` symlink survives the stop as a DANGLING link; without this guard the next sync/`uv run` fails on a link that points nowhere.

**(c) `UV_PYTHON` pin in the rc-file block only (defense-in-depth, fail-soft).** In the Step-6 rc-file appends, add a separately-guarded block exporting `UV_PYTHON=<base interpreter>`, derived from the live venv rather than hardcoded: `/workspace/explore-persona-space/.venv/bin/python -c "import sys; print(sys._base_executable or sys.base_prefix + \"/bin/python3\")"` — the trailing path MUST be a real string literal, written with escaped double quotes since the single-quoted payload forbids apostrophes. Written only when the resolved path is executable; otherwise skipped with a WARN.
  - **Guard with `grep -q`, NOT `grep -qF`.** `test_rc_path_append_separately_guarded` (tests lines ~167-173) extracts "the only `grep -qF` in the script" by FIRST regex match, and `grep -qF` currently occurs exactly once (line 492, verified). A second `grep -qF "..." "$f"` landing above line 492 would silently retarget that test's extraction and turn it red. Use `grep -q` (as the PYTHONPATH guard does) or place the block after the existing appends. Derived-from-the-venv means the pin is exactly consistent with what uv already recorded at write time, so it cannot trigger a surprise venv recreation.
  - **`sys._base_executable` verified locally** on this repo's uv 0.10.9 venv: returns the absolute base interpreter path. `pyvenv.cfg` was checked FIRST and rejected as the source — uv 0.10.9 writes `home` (a bin DIRECTORY) and no `base-executable` key, so a `pyvenv.cfg` parse would need interpreter-name guessing.
  - **REJECTED: the same pin in `.env`.** `.env` is loaded into arbitrary Python subprocesses and sourced by launchers (`set -a; . .env`), so a pin that later goes stale relative to a rebuilt venv could force a venv recreation mid-run — strictly worse than the bug being fixed — and it would not have prevented this incident anyway (see § Root-cause analysis). Recorded here so the omission reads as a decision, not an oversight.
