#### 4.1 Decision: bounded DEFER + ESCALATE (the body's "decide first" half)

Four options were considered; the body itself names the tension ("a fence that suppresses auto-stop is an unbounded pod-alive shape … There may be a case for surfacing rather than suppressing").

- **(a) Unconditional skip (the `keep-running` shape) — REJECTED.** Unlike the `keep-running` tag, a fence is a token any session self-posts with no operator action. An unconditional fence-skip on the one pass whose purpose is reclaiming spend from provably parked/terminal tasks creates an unbounded self-service pod-alive shape with no wedged-owner arm behind it — the fence-refresh-forever risk row in #2277 plan §8.
- **(b) Surface-only (escalate, still stop) — REJECTED.** It does not close the stated Goal harm at all: the stop still lands and still interrupts the owner's in-flight round.
- **(d) Pod-side liveness conjunct (defer only when a probe confirms the pod is busy) — REJECTED (round-1 Alternatives C4; recorded so it is not re-litigated).** The #2149 leg's bounded SSH probe already exists (newest `/workspace/logs/` mtime, terminal done-sentinel age, max GPU util), so conjoining it is cheap to build. It is wrong on both failure directions: a CPU-bound or API-bound phase — a judge wave, a long fit, an upload — reads IDLE (0% GPU, quiet logs) and would be stopped mid-run, re-opening the exact Goal harm; and a probe FAILURE (an SSH-unreachable pod, the #1667/#2060 portless shape) is unresolvable, so it either fails toward stopping (same harm) or toward deferring (the shield with extra machinery and a new failure surface). The fence is a first-person claim about intent; a utilization probe cannot corroborate or refute it.
- **(c) Bounded DEFER + ESCALATE — CHOSEN.** Honour the fence exactly as long as it is honest, surface it loudly the whole time, and bound the total shield. The fence carries its OWN natural bound (`fence_until` is a deadline, so expiry re-arms the stop by construction — this is the property that makes deferral safe here and is why an equivalent tag-based shield would not be), with a cumulative ceiling as the refresh-forever backstop. Directionally the arm can only ever make the watcher LESS willing to stop, satisfying the standing pod directive ("no watcher path may become MORE willing to stop a pod than it is today"), and the escalation keeps the pod visible to the user, who is the only party allowed to decide a discretionary stop.

**Calibration against the accepted precedent (round-1 Alternatives, strongest argument for (c)):** the objection to (a) is that a fence is self-postable — but so is the `keep-running` tag, which any session can set with one `task.py add-tag` call, which is ISSUE-WIDE rather than pod-scoped, and which is UNBOUNDED in time (its only backstop is the #1582 escalate-only wedged-owner arm, which never stops anything). The fence-defer arm as designed is therefore strictly MORE bounded than the shield the fleet already accepts: pod-scoped rather than issue-wide, deadline-carrying rather than indefinite, and hard-ceilinged at 24h. That is the honest frame for the new billing surface — not "a new unbounded shield" but "a tighter one alongside a looser one that already exists".

#### 4.1a Excluded: the USER-PAUSED status (round-1 Alternatives M1 — the blocker)

`status_class == "auto-stop-done"` is a MERGED label covering `AUTO_STOP_DONE` (`completed` / `awaiting_promotion` / `archived`) AND `AUTO_STOP_PAUSED` (`on_hold`) — see §2. Plan v1 keyed the new arm on that label and so would have inherited the paused member silently. That is an inversion, not an exemption:

- On the DONE members the pass reclaims an ESCAPED pod — no one asked for it to keep running, so honouring a live owner's fence adds information the pass lacked.
- On `on_hold` the pass is EXECUTING AN EXPLICIT USER DIRECTIVE (CLAUDE.md § "Routing experiment intent" user-pause affordance: the pause routes to teardown FIRST, then parks; `on_hold` + RUNNING means that teardown leg failed, #980). A self-posted fence deferring THAT stop means an agent's own token overrides the user's pause for up to `min(fence_until, 24h)` — the opposite of the standing directive, and a direct contradiction of §4.1's own justification that the user "is the only party allowed to decide a discretionary stop".
- The two shields the arm is modelled on do NOT create this inversion: `keep-running` IS an operator signal, and `_task_followup_active` requires a signal NEWER than the latest done-transition (:13960-13966), so a legitimately launched post-pause round is already shielded via `followup-skip`. `_latest_pod_fence_until` has no newer-than-transition compare — its only recency bound is its own deadline — so on the paused class the arm would shield exactly and only work the user paused over.

**Decision: `AUTO_STOP_PAUSED` is EXCLUDED from fence eligibility.** The raw status is threaded past the merged label into the §4.3(ii) computation, so `fence_active` can only be True for a task in `AUTO_STOP_DONE`. Nothing legitimate is lost (a genuine post-pause round is `followup-skip`-shielded), and the narrower alternative the critic offered as second-best — defer on the paused class only when the fence registration postdates the pause transition — is deliberately NOT taken: it re-introduces a recency comparison the shared #2277 reader does not perform, which would mean new watcher-side parsing, exactly what the task body forbids. Pinned by `test_pod_safety_fence_defer_excluded_on_user_paused` (§5).

#### 4.2 Shared fence predicate (extraction — `scripts/pod_lifecycle.py`)

Extract the guard's inlined decision core into a public pure reader placed immediately before `_guard_owner_fence_before_terminate`:

```python
class OwnerFenceState(NamedTuple):
    """The #2277 owner-fence evidence for ONE pod, read from ONE events log.

    Pure: no I/O, no clock read (``now`` is passed in). Shared by
    ``_guard_owner_fence_before_terminate`` (terminate side) and
    ``autonomous_session_watch``'s pod-safety pass (stop side, #2283) so the
    two can never drift into two parsers — the permissiveness-broadening
    defect class #2277's own review round flagged."""

    fence_until: dt.datetime | None   # newest-wins registered fence, or None
    owner_registered: str | None      # newest-wins registered owner= token
    pass_owner: str | None            # owner= on the latest pod-bound PASS
    fence_unexpired: bool             # fence_until is not None and > now
    owner_matched: bool               # owner_registered is not None and pass_owner == owner_registered

    @property
    def blocks_teardown(self) -> bool:
        """An unexpired fence with no owner-matching PASS: the owner is
        presumed alive."""
        return self.fence_unexpired and not self.owner_matched


def owner_fence_state(
    events: list[dict], pod_name: str, now: dt.datetime
) -> OwnerFenceState:
    window = _pod_evidence_window(events, pod_name)
    owner_reg = _latest_pod_token(window, pod_name, "owner")
    fence = _latest_pod_fence_until(window, pod_name)
    pass_owner = _latest_pass_owner_for_pod(window, pod_name)
    return OwnerFenceState(
        fence_until=fence,
        owner_registered=owner_reg,
        pass_owner=pass_owner,
        fence_unexpired=fence is not None and fence > now,
        owner_matched=owner_reg is not None and pass_owner == owner_reg,
    )
```

`_guard_owner_fence_before_terminate`'s per-pod loop body then becomes a call to `owner_fence_state(...)` plus its EXISTING branch structure keyed on `st.fence_unexpired` / `st.owner_matched`, with every message string, the `--force-owner-fence` WARN, the `SystemExit` text, the sweep-note, and the no-fence attribution-mismatch `elif` **byte-untouched**. This is a pure extraction: the guard's own tests are the control (§6 item 2) and must pass UNMODIFIED. The `EPM_DISABLE_OWNER_FENCE_GUARD=1` kill switch stays a terminate-side early return — it is NOT consulted by the watcher arm, which has its own switch (§4.4); a reader is not a guard.

def decide_pod_safety(
    status_class, missed, stale, alerted, threshold=2, *,
    keep_running=False, followup_active=False,
    fence_active=False,           # NEW (#2283)
    fence_defer_exhausted=False,  # NEW (#2283)

        if keep_running:
            return ("keep-running-skip", 0)
        if followup_active:
            return ("followup-skip", 0)

        if new_missed >= threshold:
            return ("stop", 0)
        return ("keep", new_missed)

That is the wrong grain and it silently voids both bounds. `_save_pod_safety_state`'s singular families reset on `kr_same_pod = (prev or {}).get("pod_id") == pod_id` (:14578) — but the state file is per-ISSUE with ONE `pod_id` slot (:14608) while `_process_pod` runs AND SAVES per POD. On an issue with ≥2 RUNNING pods — the routine primary + `--name-suffix` shape the #1961 shield exists for, and the #1739 3-pod shape — every sibling pod's save would reset the fenced pod's fields each tick, so: (a) the 24h ceiling NEVER exhausts, making the refresh-forever bound that §4.1(c) leans on structurally inert on exactly the multi-pod shape; (b) `fence_defer_noted` resets every tick, so the once-per-episode marker + push re-fire every ~10 min; (c) the evaluated-and-inactive CARRY semantics below are destroyed by any sibling save. All of v2's §5 rows were single-pod, so the plan would have certified properties that fail on the demonstrated fleet shape. This is the protection-illusion class, and the SAME defect the #2149 review Must-Fixed in this very file — the `kr_pod` sub-dict exists because of it, and its docstring (:14598-14603) names that Must-Fix explicitly.

**Corrected design:** the episode state is a pod_id-keyed sub-dict `fd_pod` on the pod-safety state, following the `kr_pod` (#2149) / `nr_pod` (#2060) convention verbatim — a `_carry_fd_pod(prev, fd_pod_entry, fd_pod_keep_ids)` helper mirroring `_carry_kr_pod`: sibling entries forward-carried VERBATIM on every save, per-pod keying IS the incarnation reset (so no in-save `kr_same_pod`-style reset is needed — this also DELETES the hand-wired-reset duty v2's §12.3 imposed on the implementer), GC'd against the caller's `issue_running_pod_ids` RUNNING set, and back-compat missing/garbled → `{}`. Each entry holds `first_ts` (episode onset, stamped on the first deferring tick) and `noted` (once-per-episode marker dedup). `_save_pod_safety_state` gains `fd_pod_entry` / `fd_pod_keep_ids` parameters in the same shape as its `kr_pod_entry` / `kr_pod_keep_ids` pair.

`fence_defer_exhausted` is computed caller-side from THIS pod's entry as `first_ts is not None and (now - first_ts) / 3600 > EPM_POD_FENCE_DEFER_MAX_H` (default **24.0**, clamped to a floor of 1.0 so a misconfiguration cannot disable the shield entirely). On exhaustion the arm stops deferring, the ordinary accumulation resumes from 0, and the ceiling escalation fires once.

**Episode-clear semantics — EVALUATED-and-inactive, not merely not-observed-active (round-1 Methodology C2).** v1 cleared the episode on any tick that did not observe an active fence. That is wrong under lazy evaluation: `fence_active` is computed only when `fence_eligible` holds, so during a long `keep-running-skip` or `followup-skip` stretch — or while the task sits at a non-auto-stop status — the arm is never evaluated, v1 would not clear, and on re-entry the stale onset could read INSTANTLY EXHAUSTED against a legitimately fresh fence. The direction is safe (behavior degrades to HEAD, never worse) but it under-protects exactly the owner the arm exists for. The clear is therefore keyed on the three-valued outcome of the tick: **evaluated-and-active** ⇒ stamp/keep the episode; **evaluated-and-INACTIVE** (eligible, the reader ran, and it returned a definite "no unwaived fence") ⇒ CLEAR this pod's entry; **not evaluated** (ineligible — another shield fired, wrong status, kill switch — OR the read FAILED) ⇒ CARRY the entry untouched. The ceiling then measures one continuous SHIELDED stretch as intended, and a shield handover cannot silently burn it. Pinned by `test_pod_safety_fence_defer_episode_clears_only_when_evaluated`.

**The wrapper must therefore be TRI-STATE, not a bool (round-2 Alternatives C1).** §4.3(ii) as first written returned `False` on any failure, which makes a transient read failure indistinguishable from evaluated-and-inactive — so the failure would CLEAR the episode and mildly widen the very refresh-forever hole the ceiling exists to bound. `_pod_owner_fence_active` therefore returns `True` (unwaived fence) / `False` (definite no unwaived fence) / `None` (kill switch, import error, malformed row, any exception — read did not resolve). The DEFER decision stays fail-open exactly as specced (`fence_active = (result is True)`, so `None` never defers and never makes the watcher more willing to stop than HEAD); only the EPISODE-CLEAR consults the third state, treating `None` as not-evaluated ⇒ CARRY.

**Named residual — CARRY across a long shield handover (round-2 Alternatives C2).** Because a not-evaluated tick carries the entry, a fence episode carried through a >24h `keep-running` / `followup-skip` / wrong-status stretch re-enters already exhausted, giving the returning fence zero fence-side deferral. This is the intended reading of "one continuous SHIELDED stretch" and is strictly better than clear-on-handover (which would let shield ALTERNATION recycle the ceiling indefinitely — the very hole the lapse-recycle residual below already concedes once). It degrades to HEAD behavior plus a loud ceiling escalation, and after the sub-dict fix the residual is per-pod. Recorded in the arm's docstring as a decision, not left as a corner.

**Named residual — lapse-recycle (both critics, independently).** Because the clear fires on an evaluated-and-inactive tick, an owner whose fence lapses for a single tick (1 miss, below the threshold of 2) and is then re-posted resets the 24h ceiling, giving an indefinite shield at ~24h periods. This is adversarial-only and sits outside the declared accidents-not-adversaries trust model the whole fence convention inherits from #2277; each fresh episode re-fires its own marker and push, so the recycling is visible rather than silent. It is recorded in the arm's docstring beside the copied-token residual, NOT closed in v1 of this fix.

**(iv) Channels — `_apply_pod_safety_action` gains a `fence-defer` branch.** Modeled on the existing `keep-running-skip` branch: a stdout line always; then, once per episode (`fence_defer_noted`), an `epm:progress` marker with the anti-liveness sentinel `[autonomous_session_watch:pod-owner-fence-defer]` naming the pod, `pod_id`, the fence expiry, the task status, the ceiling, and the operator remedies (`task.py post-marker <N> epm:progress --note '... pod=<name> fence_until=none'` to release, or `pod.py stop --issue <N>` to stop it by hand); a fail-soft `_telegram_push`; and one sidecar row to `.claude/cache/pod-owner-fence-events.jsonl` (`kind="fence-defer"`). The push re-fires on the shared `EPM_KEEP_RUNNING_WEDGED_REALERT_H` cadence (24h) so a long fence stays visible without flooding. The ceiling event posts the DISTINCT sentinel `[autonomous_session_watch:pod-owner-fence-ceiling]` + push + sidecar row (`kind="fence-ceiling"`) stating that deferral is exhausted and the ordinary auto-stop has re-armed. Both sentinels join `_WATCHER_NOTE_SENTINELS` so the arm's own markers never reset the staleness clocks other passes read (the #2084 anti-liveness lesson).

2. `now` in `_process_pod` is a Unix timestamp float; the watcher wrapper converts to an aware UTC datetime and asserts awareness at the boundary (`_latest_pod_fence_until` returns tz-aware, so a naive value would raise on comparison).
3.
