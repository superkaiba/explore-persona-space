### 4.2 New pure decision fn (place beside `decide_pod_wedge`, ~:3050s — the file's pure-fn-plus-caller-wiring pattern; resolves clarifier consideration 1)

Chosen: a SEPARATE pure fn, NOT a new `status_class` in `decide_pod_safety` — `decide_pod_safety`'s enum + `(action, new_missed)` contract stays byte-untouched (zero regression surface on the auto-stop arm and its existing tests), exactly as `decide_pod_wedge` (#692) and the #1490 arm handled their distinct concerns.

```python
def decide_unlaunched_orphan(
    *,
    status: str | None,
    pod_name: str,
    issue: int,
    created_ts: float | None,
    latest_launch_signal_ts: float | None,
    noted: bool,
    now: float,
    grace_sec: float,
    skew_sec: float = UNLAUNCHED_ORPHAN_LAUNCH_SKEW_SEC,
) -> str:
    """Pure decision for the #1519 unlaunched-orphan arm: "alert" | "keep".

    Cases (every uncertain input fails toward "keep" — the file's posture):
    - status None or not in POD_ACTIVE            -> keep  (DONE/on_hold pods
      belong to the auto-stop arm; blocked/planning/interpreting/etc. are out
      of the #1519 scope by the task Goal)
    - pod_name != f"pod-{issue}"                  -> keep  (bare canonical name
      only; suffixed follow-up pods excluded — see docstring limitation)
    - noted (this pod incarnation)                -> keep  (once-per-incarnation dedup)
    - created_ts is None                          -> keep  (unparseable createdAt)
    - now - created_ts < grace_sec                -> keep  (healthy provision/
      bootstrap/dispatch window; covers the epm:pod-provisioned-only shape)
    - latest_launch_signal_ts is not None and
      latest_launch_signal_ts > created_ts - skew_sec -> keep  (launched, or a
      signal posted at/just before provision — the relaunch-marker rule: any
      signal NEWER than created_at-skew counts as launched; a signal OLDER
      than that belongs to a PREDECESSOR pod and does NOT shield a fresh
      replacement pod, which is exactly the orphan signature)
    - else                                        -> alert
    """
```

`keep-running` is deliberately NOT a pure-fn input: the tag read is a `task.py view` subprocess, re-checked lazily at the caller only when everything else says "alert" (the #1490 lazy-shield ordering, :9421–9426) — resolves clarifier consideration 4's first half; the grace window resolves its second half (a provisioned-but-unlaunched pod within grace is "keep" by the age leg).

**Relaunch / replacement-pod semantics (clarifier consideration 3):** any launch signal NEWER than `created_ts − skew` reads as launched. A crash-fix relaunch on the SAME pod: the pod's `created_at` predates the original `epm:run-launched` → suppressed forever (correct). A FRESH replacement pod whose relaunch takes > grace: the old marker is older than the new `created_at` → alert fires — deliberate: a fresh multi-GPU pod idling > 1 h awaiting a fix IS a surfaced burn, and the alert is a cheap nudge, never a stop. **Parent-pod-reuse limitation:** a child task launching on the PARENT's pod posts `epm:run-launched` on the CHILD's events.jsonl; the predicate reads only the pod-name-derived owning issue (`_issue_from_pod_name`, the pass's existing attribution, :8842) → the parent issue can false-alert after grace. Documented in the fn docstring; `task.py add-tag <parent> keep-running` is the sanctioned shield (already mandated by the CLAUDE.md multi-pod / follow-up pre-launch-signal duties). **Launch-evidence set:** the full `_POD_FOLLOWUP_SIGNAL_KINDS` frozenset (:6930 — `epm:run-launched` / `epm:followup-scope` / `epm:free-analysis-followup-run`), not `epm:run-launched` alone: #573 established that run-launched-only inference misses the scope-posted-before-launch window; the widened set costs nothing (the events list is already in hand) and only ever suppresses.
