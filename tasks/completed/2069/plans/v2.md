## Requirement + acceptance criteria (Goal)

An on-policy datagen pipeline must persist its judge-REJECTED generations
(with their verdicts) alongside the kept rows, so re-filtering or inspecting
rejects never requires regenerating the wave (#1689 incident: rejects were
never persisted; inspecting them required a full regeneration).

Acceptance criteria:

1. `.claude/rules/on-policy-completions.md` (the rule that OWNS the
   judge-filter step) mandates persisting rejected generations: sibling path
   convention (`raw_completions/<stage>/rejected/`; single-stage runs omit
   `<stage>/`), per-row judge verdict + score + drop disposition, manifest
   reject counts with per-stage set/count reconciliation (ALL tranches —
   retry + close-miss escalation included), never a valid
   `discarded_artifacts:` entry.
2. `.claude/rules/upload-policy.md` names judge-rejected generations as
   members of the "text/JSON uploads unconditionally" class (a pipeline that
   writes only judge-KEPT rows has NOT persisted its generations).
3. `.claude/agents/upload-verifier.md` renders the check IN THE VERDICT
   TABLE (a sibling row after the row-440 generation-discard gate), not only
   Step 1 prose: manifest rejects > 0 with no persisted set FAILs
   (`judge-rejects-discarded`); persisted reject rows FEWER than the
   manifest reject count FAILs (`judge-rejects-incomplete`); no manifest
   count WARNs (`judge-rejects-missing`, never silently assumed-empty).
4. Constraints honored: kept-row path/layout unchanged; 80% yield floor +
   equalize-down still computed on KEPT rows only; reject persistence is
   written as unconditional, never "when convenient".
5. Datagen blast radius REPORTED (not fixed): grep evidence recorded in the
   task record.
