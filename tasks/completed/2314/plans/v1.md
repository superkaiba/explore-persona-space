# Plan — #2314: restore the `#847` thread-cap invariant on `scripts/issue2225_fu2_dod_points_fig.py`

`kind: infra` · `workflow: v1` · 0 GPU-h · single-file, 4-line edit

## 0.0 TL;DR (plain English)

One committed script on `origin/main` — `scripts/issue2225_fu2_dod_points_fig.py`,
a figure re-plotter for issue #2225 — imports `numpy` at the top of the file
without first calling `load_dotenv()`. That call is what pins this shared VM's
BLAS/thread caps (the `#847` rule: NumPy and torch freeze their thread pools at
IMPORT time, so a cap set after the import does nothing). Because the repo has a
test that scans every script for exactly this mistake, the test is RED on
pristine `main` — which means every `/issue` session's pre-merge test gate sees a
failure it did not cause.

The fix is three added lines plus two `# noqa` comments: import `load_dotenv`,
call it, then import numpy. Ten sibling `issue2225_*` scripts already look
exactly like this. Nothing else changes; no compute runs.

## 0. Plan Summary (for the implementer / reviewer)

Insert the canonical `#847` preamble into
`scripts/issue2225_fu2_dod_points_fig.py` so that
`explore_persona_space.orchestrate.env.load_dotenv()` executes BEFORE the
module-top `import numpy as np` (currently line 23) and before the
`explore_persona_space.analysis.paper_plots` import (currently line 25, which

## 3. Hypothesis / expected outcome

Not a research hypothesis — a mechanical predicate. After the edit, the
detector's two helpers evaluate as follows on the target file:

- `_first_heavy_import_line(ast.parse(src))` → the line of `import numpy as np`
  (post-edit line 27). The `orchestrate.env` import is not a
  `HEAVY_IMPORT_ROOTS` root; `import matplotlib.pyplot as plt` remains nested
  inside `main()` and is therefore invisible to the module-top-only scan.
- `_first_load_dotenv_line(src)` → the line of the bare `load_dotenv()` CALL
  (post-edit line 25). Note the helper matches the substring `load_dotenv(`
  **with the open paren**, so the `from ... import load_dotenv` line does NOT
  satisfy it — the call site is what counts, which is exactly the semantics we
  want.

Therefore `dotenv (25) < heavy (27)`, the violation predicate
`(dotenv is None or heavy < dotenv)` is False, and the node PASSES with zero
violations. Expected wall-clock: ~19 s for the node.

## 11. Decision Rationale

**Fix option 1 (add `load_dotenv()`) over option 2 (grandfather the path).**
The task body already names option 1 as preferred; three independent grounds
confirm it rather than merely defer to it:

1. **Option 2 requires an argument that is false here.** Grandfathering is
   admissible only with a real "this never runs on the shared VM" case. This
   script is a VM-side figure re-plotter — precisely the class that DOES run on
   the shared VM — and it is a numpy consumer, so the cap it forfeits is the
   cap `#847` exists to impose.
2. **The frozen set is designed to shrink only.** The currency assertions delete
   entries whose root cause was fixed; adding a new entry for a file with a
   three-line fix inverts the ratchet. The test's own line-1007 assertion records
   this as policy, not preference.
3. **Cost asymmetry.** Option 1 is 4 lines matching a convention already present
   in 10 sibling files in the same series; option 2 is a permanent carve-out plus
   a justification that would not survive review.

**Static verification over a figure re-render** (§6): re-running the plotter
would rewrite a committed artifact owned by another task to prove a property —
"import-order change does not alter output" — that follows from the edit's
content. The AST + import + lint checks bound it correctly at zero risk.

**Single-file scope over a preventive sweep:** the detector reports exactly one
violation, so there is no second offender to fix; broadening the diff would add
review surface with no invariant gain.
