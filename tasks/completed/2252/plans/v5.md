# Plan — #2252: Step 9c reports an external SIGTERM of the unfenced workflow_lint subprocess as a lint FAIL

### 0.0 TL;DR (plain English)

- **What I'll change:** I'll fix the one shared helper (`_run`, `tests/test_workflow_lint.py:111`) that every lint test in that file uses to spawn the ~7.5-minute linter subprocess, so that an external kill (a signal) is no longer reported as "the lint failed". The helper will: recognize a signal-encoded exit code, retry exactly once (the lint is deterministic and read-only), and — if the retry is also killed — fail with a message that says plainly "this was an external kill, not a lint verdict" and quotes the linter's own PASS/FAIL line. It also gets a generous 1800s timeout so a genuinely hung child fails loudly on its own terms instead of wedging until the outer gate fence kills everything.
- **What I expect:** the fleet-wide Step 9c gate stops going red when a busy VM's reaper clips this one long subprocess; when the environment is genuinely sick (two kills in a row), the failure message tells the reading agent exactly what happened, so nobody bounces a clean payload into a spurious fix round.
- **What would change my mind:** if code review shows the linter can legitimately exit with a code ≥ 128 (my read of its exit paths says it can't — it returns only 0/1, argparse 2), the signal predicate would be unsafe as designed and I'd re-scope to a parsed-verdict design instead.

### 4. Design

**Requirement:** every `CompletedProcess` returned by `_run` carries a genuine linter exit status; signal deaths and timeouts never reach caller assertions.

**Why code, not a model call:** exit-code classification is a 3-branch integer predicate; a model call is category error here.

**Chosen proposal set: 1 + 2 + 3, all inside `_run`.** Rationale per the six load-bearing questions:

1. **Where the fix lives.** In the module helper `_run` (line 111) plus two tiny private helpers beside it. This covers all 32 call sites at once and — because a returned result is signal-free by construction — leaves all 31 bare `== 0` assertions AND the expected-FAIL `!= 0` assertion at line 1766 correct without touching them. (Note the `!= 0` site was itself latently wrong before this fix: a signal death satisfies `!= 0`, so an expected-FAIL test could pass for the wrong reason. The helper-level contract fixes that for free; a per-test patch would not.) **Deliberately unchanged:** all 31 `== 0` assertions, both `!= 0` assertion sites, every call site.
2. **Signal predicate.** `rc < 0 or rc >= 128` ⇒ signal death. `rc < 0` is POSIX `subprocess` semantics when the *direct* child dies by signal N (reported as −N); `rc >= 128` is the shell/wrapper encoding (128+N) — the observed 143 proves the `uv` wrapper path reports the latter, and a reaper hitting `uv` itself with default disposition would produce the former, so both must be caught. The predicate cannot swallow a legitimate verdict because the linter's exit codes are exactly {0, 1} plus argparse's 2 (verified from source, §2); nothing legitimate lands in [128, 255] or below 0. rc=2 (and any 3–127) passes through to the caller as a genuine non-zero verdict and fails the caller's assertion with the full dump — correct.
3. **Timeout.** `_RUN_TIMEOUT_S = 1800`. Grounding: measured healthy no-flags scan 452–455s (two direct probes, #2252 body); worst observed contention case exceeded a 540s ceiling (body); repo convention sizes fences ~1.4–2× over worst measured *observed wall* — 1800s ≈ 4× the healthy wall and ≥ 3.3× the observed contention floor, deliberately generous per the `select_step9c_tests.py:1179` doctrine that an oversized bound only fires on a genuine wedge. It sits inside the module's Step 9c one-file bound (2550s) in the sense that matters: before this change a hung child wedged until the *outer gate fence* (6600s in #2243's gate) killed the whole battery; now it fails ONE test at 1800s with a distinct message. `subprocess.TimeoutExpired` is caught and converted to `pytest.fail` with its own leading token (`TIMEOUT after 1800s … a WEDGE, not a lint verdict`) — never retried (a wedge is not transient, and a retry would add up to 30 min to the gate), never conflated with either the signal or the verdict outcome.
4. **Retry-once semantics.** Exactly one retry, signal-death branch only (the lint is deterministic and side-effect-free in every mode `_run` reaches — the no-flags and `--check-*` modes are read-only). Attempt 1 signalled → `warnings.warn(RuntimeWarning)` naming rc, decoded signal, the embedded verdict line, and `#2252` (visible in the pytest warnings summary even on green runs, so the environmental sickness is observable without redding the gate). Attempt 2 signalled → `pytest.fail` leading `SIGNALLED twice (rc=… = signal …) — an external kill, NOT a lint verdict (#2252)`, quoting the embedded verdict line and a bounded stderr tail (~400 chars), and pointing at VM load / concurrent Step 9c batteries. **Wall-clock objection, addressed:** the retry fires only after an actual signal death; its worst-case cost is one extra no-flags scan (~455s, ~14% of the observed 53-min gate) *in the rare kill case only*, vs. the status-quo cost of that same case: a red gate, a full ~53-min gate re-run, and an attribution investigation (#2243 paid all three). Expected cost strictly favors the retry. Scoped `--check-*` calls (the other 31 sites) are seconds each, so their retry cost is negligible and their exposure window ~100× smaller.
5. **Step 9c oracle: OUT of scope, deliberately.** With this fix, a single signal death no longer produces a FAILED node at all, so there is nothing new for the oracle to classify in the dominant case. The residual double-kill case still reds the gate classified NEW — and that is arguably *correct*: two consecutive kills of the same child indicate an environment sick enough that a human-legible red gate (now carrying a first-line explanation) is the right outcome, not an auto-waved category. Teaching the oracle a signal-death category would add a second, downstream mechanism for the same defect and enlarge the surface of "failures the gate learns to wave off" — exactly the dangerous adaptation the body warns about. I surface (not file — recursion guard) the residual idea for the record: *if* double-kill reds recur post-fix, a follow-up could have the oracle annotate (never auto-clear) `SIGNALLED`-tokened failures.
6. **Scope.** In scope: `_run` + new helpers + new unit tests, all in `tests/test_workflow_lint.py`. Out of scope, with reasons: (a) the ~9 other `subprocess.run` sites in the file (lines 644, 665, 2482, 2532, 2801, 8490, 8491, 8510, 9772) — all sub-second children (git fixture setup, grep-engine probes, guard-hook invocations, one already-fenced `timeout=60` scoped linter spawn), i.e. ~500–1000× smaller kill-exposure windows, several `check=True` (a signalled child raises `CalledProcessError` distinctly); widening the diff there dilutes review for negligible risk reduction. (b) Sibling `tests/test_workflow_lint_*.py` files: their own `_run` helpers (verified) do not spawn the 455s no-flags scan — same exposure argument. (c) Proposal 4 (reduce scan cost): real but orthogonal linter-performance work on a 937-file scan, adjacent to #2019; it shrinks the window without removing the misdiagnosis. (d) Proposal 5 (parsed verdict line as primary signal): inverts authority — the exit code IS the linter's machine contract (0/1); parsing a human-facing stderr string as primary would couple 40 tests to message wording and still need exit-code logic for crash-class deaths that emit no verdict line. Its value (the verdict line as *evidence*) is captured instead by quoting that line in the diagnostic messages.

```python
_RUN_TIMEOUT_S = 1800  # ~4x the measured 452-455s no-flags scan (#2252); fires only on a wedge


def _signal_decode(rc: int) -> str | None:
    """Name the signal encoded in a child returncode, or None for a plain exit.

    A DIRECT child killed by signal N reports returncode -N (POSIX subprocess
    semantics); a wrapper (uv/shell) reaping a signalled child conventionally
    exits 128+N (the observed 143 = 128+SIGTERM, #2243). workflow_lint's own
    exits are 0/1 (argparse: 2), so no legitimate verdict lands in either band.
    """
    if rc < 0:
        n = -rc
    elif rc >= 128:
        n = rc - 128
    else:
        return None
    try:
        return f"{n} ({signal.Signals(n).name})"
    except ValueError:
        return f"{n} (unknown)"


def _verdict_line(text_streams: tuple[str | None, ...]) -> str:
    """Last 'workflow_lint: ...' line, scanning the streams IN THE ORDER GIVEN.

    Callers pass stderr FIRST. The linter writes its verdict AND every
    check-output line to stderr (`workflow_lint.py:18968`/`20525`), so a
    stderr hit is always the authoritative one. Stream order is
    load-bearing, not incidental: a FAIL-then-killed run also carries
    `workflow_lint:`-prefixed FINDING lines, so scanning the stream list
    in reverse would let a stdout line outrank the real verdict (both
    critic lenses flagged this against assumption 4). Within a stream we
    still take the LAST match — the verdict is printed last. The one
    stdout-only mode (`--regen-hf-routing-snapshot`, called at
    `tests/test_workflow_lint.py:9396`) emits NO `workflow_lint:` line on
    either stream by design (its early dispatch means the check bundle
    never runs), so it correctly falls through to the stated-absence
    return rather than quoting a stray line.
    """
    for s in [t for t in text_streams if t]:
        for line in reversed(s.splitlines()):
            if line.startswith("workflow_lint:"):
                return line
    return "<no verdict line — killed before the linter printed one>"


def _run(*flags: str) -> subprocess.CompletedProcess[str]:
    """Spawn the linter; return ONLY genuine verdicts (0 <= rc < 128).

    Signal deaths (external reaper, #2252/#2243) retry ONCE (the lint is
    deterministic and read-only); a second signal death, or a timeout, fails
    with a message discriminating it from a lint verdict. Callers may assert
    on returncode: a returned CompletedProcess is never signal-encoded.
    """
    last: subprocess.CompletedProcess[str] | None = None
    for attempt in (1, 2):
        try:
            result = subprocess.run(
                ["uv", "run", "python", str(_LINT), *flags],
                cwd=_REPO_ROOT,
                capture_output=True,
                text=True,
                check=False,
                timeout=_RUN_TIMEOUT_S,
            )
        except subprocess.TimeoutExpired:
            pytest.fail(
                f"_run{flags!r}: TIMEOUT after {_RUN_TIMEOUT_S}s — a WEDGE, not a lint "
                f"verdict (#2252; healthy no-flags scan measures ~455s)."
            )
        sig = _signal_decode(result.returncode)
        if sig is None:
            return result
        last = result
        if attempt == 1:
            warnings.warn(
                f"_run{flags!r}: lint subprocess SIGNALLED (rc={result.returncode} = "
                f"signal {sig}) — external kill, not a lint verdict (#2252); retrying "
                f"once. Embedded verdict line: "
                f"{_verdict_line((result.stderr, result.stdout))!r}",
                RuntimeWarning,
                stacklevel=2,
            )
    assert last is not None
    pytest.fail(
        f"_run{flags!r}: SIGNALLED twice (rc={last.returncode} = signal "
        f"{_signal_decode(last.returncode)}) — an external kill, NOT a lint verdict "
        f"(#2252). Embedded verdict line: "
        f"{_verdict_line((last.stderr, last.stdout))!r}. Environmental: check VM load "
        f"and concurrent Step 9c batteries before touching the payload.\n"
        f"stderr tail: {(last.stderr or '')[-400:]}"
    )
```
