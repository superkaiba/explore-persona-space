## 1. Goal

When a concurrent session runs `git pull --rebase` on the shared repo root, the primary checkout's HEAD is detached for the rebase duration and `task_workflow._resolve_repo_root_cached` (branch guard (c), `src/explore_persona_space/task_workflow.py:334-377`) hard-refuses every `task.py` mutation with `RuntimeError("main worktree HEAD (...) is detached; re-attach to 'main' before running task.py.")`. ≥7 sessions hit this on 2026-07-03. Fix: when HEAD is detached AND a live rebase is in progress in the PRIMARY checkout (`<common-dir>/rebase-merge` or `<common-dir>/rebase-apply` present), bounded-wait (default 120s) and re-run the FULL branch guard instead of refusing. Scope note (no diagnosis overclaim): the fix targets the transient live-rebase subcase; in a stale-crashed-rebase world it degrades to "wait the bound, then refuse with a better remedy", hedged by the bound + the knob.

**Acceptance criteria (test-backable; each names its committed test):**

1. Detached HEAD + live rebase marker → the resolver waits; when HEAD re-attaches to `main` and the marker clears, it returns the primary root (exit 0). — test (a).
2. Detached HEAD + NO rebase marker → refuses with the existing message, unchanged semantics (modulo a ≤1s grace re-probe). — existing `test_branch_guard_distinct_error_on_detached_head` (tests/test_task_workflow_worktree.py:232), unchanged.
3. Detached HEAD + marker that never clears → refuses after the bound with a `RuntimeError` whose message contains ALL of: the substring `detached`, the rebase state-dir name (`rebase-merge`), the wait duration, the stale/crashed-rebase possibility, and the `git rebase --abort` remedy. — test (c) asserts each substring.
4. Post-wait re-attach to a NON-main branch → routes through the existing `_ensure_managed_main_worktree` path (#844), not a refusal. — test (d).
5. `EPM_TASKPY_REBASE_WAIT_SECONDS=0` restores today's behavior exactly: the `wait_bound <= 0` branch fires BEFORE any marker probe (no `_rebase_in_progress` call, no grace, immediate refusal with the byte-identical old message). Certified in the DISCRIMINATIVE cell — detached + marker PRESENT + knob=0 → immediate old refusal, no wait/timeout wording, wall well under the default bound. — new test (b').
6. The wait is loud at ENTRY: an announcement line naming the wait bound + env knob + rebase state reaches the child process's stderr when the wait begins. — test (a) asserts the announcement substring. (Periodic heartbeat cadence is implementer freedom, untested — entry-only is the load-bearing contract.)

## 3. Design

All logic changes in ONE file: `src/explore_persona_space/task_workflow.py`. Comment-only touches in `scripts/task.py`. No refactor beyond the fix.

**New module-level knobs + helpers** (place near `_sanitized_git_env`, ~line 272):

```python
_REBASE_WAIT_ENV = "EPM_TASKPY_REBASE_WAIT_SECONDS"   # total bound; 0 disables (default 120)
_REBASE_POLL_ENV = "EPM_TASKPY_REBASE_POLL_SECONDS"   # poll interval (default 2.0)

def _rebase_wait_bound_s() -> float:
    return float(os.environ.get(_REBASE_WAIT_ENV, "120"))   # ValueError fails loud, project norm

def _rebase_poll_s() -> float:
    return float(os.environ.get(_REBASE_POLL_ENV, "2.0"))

def _rebase_in_progress(common_dir: Path) -> bool:
    """True iff the PRIMARY checkout has a live (or stale) rebase state dir.
    Mirrors scripts/sync_repo_root.py::_rebase_in_progress but takes the
    validated common dir directly and uses .is_dir() where the sibling uses
    .exists() — deliberate (the state dir is always a directory), noted here
    so a future unifier doesn't read the divergence as intentional filtering."""
    return (common_dir / "rebase-merge").is_dir() or (common_dir / "rebase-apply").is_dir()
```

**Restructure `_resolve_repo_root_cached` (lines 326-378) into a bounded re-probe loop.** The loop re-enters the FULL branch guard each iteration — so a post-rebase HEAD attached to `main` returns `parent`, and a post-rebase HEAD attached to a non-main branch routes through `_ensure_managed_main_worktree` (#844). **Check order is load-bearing (criterion 5):** the `wait_bound <= 0` branch fires BEFORE any `_rebase_in_progress` probe.

```python
env = _sanitized_git_env()
parent = _resolve_primary_checkout(env)          # (a)+(b), unchanged, once
common_dir = parent / ".git"                     # == validated common dir (basename check, line 300)
wait_bound = _rebase_wait_bound_s()
deadline = time.monotonic() + wait_bound
grace_probes_left = 1 if wait_bound > 0 else 0   # boundary-race re-probe, see below
announced = False
while True:
    sym = subprocess.run(["git", "-C", str(parent), "symbolic-ref", "--short", "HEAD"], ...)
    if sym.returncode == 0:
        branch = sym.stdout.strip()
        if branch != "main":
            return _ensure_managed_main_worktree(parent, branch, env)   # existing #844 path
        return parent
    stderr = (sym.stderr or "").lower()
    if "not a symbolic ref" not in stderr:
        raise RuntimeError(f"`git symbolic-ref --short HEAD` failed (rc=...) ...")  # unchanged
    # Detached HEAD.
    if wait_bound <= 0:
        # knob=0: EXACT old behavior — no marker probe, no grace, immediate refusal.
        raise RuntimeError(
            f"main worktree HEAD ({parent}) is detached; "
            f"re-attach to 'main' before running task.py."
        )                                                                # byte-identical message
    rebasing = _rebase_in_progress(common_dir)
    if not rebasing and grace_probes_left <= 0:
        raise RuntimeError(
            f"main worktree HEAD ({parent}) is detached; "
            f"re-attach to 'main' before running task.py."
        )                                                                # byte-identical message
    if time.monotonic() >= deadline:
        raise RuntimeError(
            f"main worktree HEAD ({parent}) is detached and a rebase state dir "
            f"({common_dir / 'rebase-merge'} or rebase-apply) was still present after "
            f"waiting {wait_bound:.0f}s ({_REBASE_WAIT_ENV}). A live `git pull --rebase` "
            f"should finish in seconds; a state dir this old is likely a CRASHED rebase. "
            f"Inspect with `git -C {parent} status`; `git -C {parent} rebase --abort` "
            f"clears a stale rebase, then re-attach to 'main'."
        )
    if not rebasing:
        grace_probes_left -= 1
        time.sleep(0.5)          # just-created / just-removed marker window; single re-probe
        continue
    if not announced:
        _log.warning(
            "task.py: primary checkout HEAD (%s) is detached mid-rebase (%s present); "
            "waiting up to %.0fs for the concurrent rebase to finish (poll %.1fs; "
            "override via %s)...", parent, "rebase-merge/rebase-apply", wait_bound,
            _rebase_poll_s(), _REBASE_WAIT_ENV,
        )
        announced = True
    time.sleep(_rebase_poll_s())
    # heartbeat: re-log every ~10 polls (implementer freedom on cadence; entry line is the tested contract)
```

Decisions (grounded in §8):

- **Poll interval 2.0s** — matches `sync_repo_root.INDEX_LOCK_POLL_S` (line 137); a rebase completes in seconds-to-a-minute, so 2s adds negligible latency while keeping ≤60 subprocess probes over the full bound.
- **Total bound 120s** — the candidate's suggestion, and the same magnitude as `EPM_ROOT_SYNC_LOCK2_WAIT_S` (120s, sync_repo_root.py line 163), which bounds the sibling contention on the same resource.
- **Marker-less grace re-probe: YES, exactly one (0.5s).** Git's internal ordering of state-dir removal vs HEAD re-attach at rebase start/finish is not contractually guaranteed; a single 0.5s re-probe closes both the just-created and just-removed windows at a worst-case cost of +0.5s on a genuine (non-rebase) detached refusal — negligible for a CLI, and skipped entirely when the knob is 0. (It is cheap insurance, not a proof of covering every boundary ordering — the residual is acceptable under the transient-subcase scope.)
- **Loud wait: `_log.warning`** (consistent with the lock-collision retry at line 4322; logging's lastResort handler emits WARNING to stderr even unconfigured) — the ENTRY line is asserted by test (a); heartbeat cadence is implementer freedom.
- **lru_cache interaction:** `functools.lru_cache` caches only successful returns — a raised `RuntimeError` (timeout or plain detached) is NOT cached (fact-checker verified empirically), so the next call in the same process re-probes; a post-wait success IS cached (desired). No change needed; add one comment line at the decorator (line 325).

| Stale `rebase-merge` dir from a crashed rebase persists | Every task.py call pays the full 120s before refusing until it clears | Bounded timeout is the design's answer; the timeout message names the stale-dir possibility + `git rebase --abort` remedy; `sync_repo_root.py`'s husk-age triage auto-clears a stale rebase on the next root-sync pass, so the state is not persistent-forever in practice. Optional implementer-freedom hedge: skip the wait when the state dir's mtime exceeds a few minutes.) |
| Boundary races (marker just-created / just-removed around HEAD detach) | Spurious immediate refusal or one wasted poll | One 0.5s grace re-probe on detached+no-marker; the loop re-enters the full guard each poll, handling whatever state emerges (main / non-main / still detached). |

## 8. §11 Decision Rationale

- **Wait bound 120s** (`EPM_TASKPY_REBASE_WAIT_SECONDS`, 0 disables). Why: covers the observed rebase window while bounding stale-dir pathology. Source: candidate sketch (#996 body) + the sibling 120s bound `EPM_ROOT_SYNC_LOCK2_WAIT_S` (`sync_repo_root.py:163`). Alternatives: 30s (too short for a slow autostash rebase on the busy shared root); unbounded (masks crashed rebases forever).
- **Poll 2.0s** (`EPM_TASKPY_REBASE_POLL_SECONDS`). Why: rebases finish in seconds; 2s ⇒ ≤60 cheap probes per wait. Source: `INDEX_LOCK_POLL_S = 2.0` (`sync_repo_root.py:137`). Alternatives: 0.5s (more subprocess churn for no user-visible gain); 10s (adds up to 10s latency per mutation).
- **WAIT over ROUTE-through-managed-worktree (the strongest alternative, explicitly rejected).** Routing while detached+rebasing (extending #844's `_ensure_managed_main_worktree`) would let reads/writes proceed immediately — but a mid-rebase managed-worktree commit + `_advance_main_ref` CAS targets a `refs/heads/main` the finishing rebase is about to force-move to its replayed tip: the just-advanced commit is discarded or the CAS/ref-move collide (the same orphaned-commit family `sync_repo_root.py`'s docstring lines 84-88 warns about). Waiting sidesteps the race entirely; the rebase replays the pre-existing commits onto main anyway. Source: `task_workflow._advance_main_ref` (line 527) + sync_repo_root docstring.
- **Grace re-probe: one, 0.5s.** Why: git's dir-removal vs HEAD-re-attach ordering at rebase boundaries is not contractual; one re-probe closes both windows at ≤0.5s cost on genuine detached refusals. Source: clarifier boundary-race analysis. Alternatives: none (leaves the just-removed race → spurious refusal); multi-second grace (slows every genuine refusal for no benefit).
- **knob=0 check BEFORE the marker probe.** Why: criterion 5 promises "restores today's behavior exactly", which includes performing NO marker probe; the reordering makes the promise literal and mechanically checkable (source order: the `wait_bound <= 0` branch precedes any `_rebase_in_progress` call in the detached block). Source: round-1 critic ensemble (Statistics Must-Fix 1 / Codex-Alternatives concern).
- **Env knobs over injectable clock.** Why: tests need only a small bound + fast poll, both expressible as env on the existing subprocess fixture; an injected time source would be a bigger refactor than the fix. Source: repo norm (`EPM_ROOT_SYNC_*` knobs, `float()` fail-loud parsing).
- `architectural: false` — guardrail-softening bounded wait; the refusal still exists, `RuntimeError` type and `detached` substring preserved on timeout; no public CLI/marker/status contract change.
