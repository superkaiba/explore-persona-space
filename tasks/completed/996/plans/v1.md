# Plan — #996: bounded-wait on live rebase before the detached-HEAD refusal in `task.py`

### TDD: no

## 1. Goal

When a concurrent session runs `git pull --rebase` on the shared repo root, the primary checkout's HEAD is detached for the rebase duration and `task_workflow._resolve_repo_root_cached` (branch guard (c), `src/explore_persona_space/task_workflow.py:334-377`) hard-refuses every `task.py` mutation with `RuntimeError("main worktree HEAD (...) is detached; re-attach to 'main' before running task.py.")`. ≥7 sessions hit this on 2026-07-03. Fix: when HEAD is detached AND a live rebase is in progress in the PRIMARY checkout (`<common-dir>/rebase-merge` or `<common-dir>/rebase-apply` present), bounded-wait (default 120s) and re-run the FULL branch guard instead of refusing.

**Acceptance criteria (test-backable):**

1. Detached HEAD + live rebase marker → the resolver waits; when the marker clears and HEAD re-attaches to `main`, it returns the primary root (exit 0).
2. Detached HEAD + NO rebase marker → refuses with the existing message, unchanged semantics (modulo a ≤1s grace re-probe).
3. Detached HEAD + marker that never clears → refuses after the bound with a `RuntimeError` that still contains the substring `detached`, names the rebase state dir + wait duration, and states the stale-dir possibility + `git rebase --abort` remedy.
4. Post-wait re-attach to a NON-main branch → routes through the existing `_ensure_managed_main_worktree` path (#844), not a refusal.
5. `EPM_TASKPY_REBASE_WAIT_SECONDS=0` restores today's behavior exactly (no marker probe, no grace, immediate refusal). Tests run in <5s total (no real 120s sleeps).
6. The wait is loud: progress lines to stderr at wait entry and periodically, so a stuck 120s is never silent.

## 3. Design

All logic changes in ONE file: `src/explore_persona_space/task_workflow.py`. Comment-only touches in `scripts/task.py`. No refactor beyond the fix.

**New module-level knobs + helpers** (place near `_sanitized_git_env`, ~line 272):

```python
_REBASE_WAIT_ENV = "EPM_TASKPY_REBASE_WAIT_SECONDS"   # total bound; 0 disables (default 120)
_REBASE_POLL_ENV = "EPM_TASKPY_REBASE_POLL_SECONDS"   # poll interval (default 2.0)

def _rebase_wait_bound_s() -> float:
    return float(os.environ.get(_REBASE_WAIT_ENV, "120"))   # ValueError fails loud, project norm

def _rebase_poll_s() -> float:
    return float(os.environ.get(_REBASE_POLL_ENV, "2.0"))

def _rebase_in_progress(common_dir: Path) -> bool:
    """True iff the PRIMARY checkout has a live (or stale) rebase state dir.
    Mirrors scripts/sync_repo_root.py::_rebase_in_progress but takes the
    common dir directly (the resolver already validated parent/.git)."""
    return (common_dir / "rebase-merge").is_dir() or (common_dir / "rebase-apply").is_dir()
```

**Restructure `_resolve_repo_root_cached` (lines 326-378) into a bounded re-probe loop.** The loop re-enters the FULL branch guard each iteration — so a post-rebase HEAD attached to `main` returns `parent`, and a post-rebase HEAD attached to a non-main branch routes through `_ensure_managed_main_worktree` (clarifier requirement):

```python
env = _sanitized_git_env()
parent = _resolve_primary_checkout(env)          # (a)+(b), unchanged, once
common_dir = parent / ".git"                     # == validated common dir (basename check, line 300)
wait_bound = _rebase_wait_bound_s()
deadline = time.monotonic() + wait_bound
grace_probes_left = 1 if wait_bound > 0 else 0   # boundary-race re-probe, see below
announced = False
while True:
    sym = subprocess.run(["git", "-C", str(parent), "symbolic-ref", "--short", "HEAD"], ...)
    if sym.returncode == 0:
        branch = sym.stdout.strip()
        if branch != "main":
            return _ensure_managed_main_worktree(parent, branch, env)   # existing #844 path
        return parent
    stderr = (sym.stderr or "").lower()
    if "not a symbolic ref" not in stderr:
        raise RuntimeError(f"`git symbolic-ref --short HEAD` failed (rc=...) ...")  # unchanged
    # Detached HEAD.
    rebasing = _rebase_in_progress(common_dir)
    if wait_bound <= 0 or (not rebasing and grace_probes_left <= 0):
        raise RuntimeError(
            f"main worktree HEAD ({parent}) is detached; "
            f"re-attach to 'main' before running task.py."
        )                                                                # byte-identical message
    if time.monotonic() >= deadline:
        raise RuntimeError(
            f"main worktree HEAD ({parent}) is detached and a rebase state dir "
            f"({common_dir / 'rebase-merge'} or rebase-apply) was still present after "
            f"waiting {wait_bound:.0f}s ({_REBASE_WAIT_ENV}). A live `git pull --rebase` "
            f"should finish in seconds; a state dir this old is likely a CRASHED rebase. "
            f"Inspect with `git -C {parent} status`; `git -C {parent} rebase --abort` "
            f"clears a stale rebase, then re-attach to 'main'."
        )
    if not rebasing:
        grace_probes_left -= 1
        time.sleep(0.5)          # just-created / just-removed marker window; single re-probe
        continue
    if not announced:
        _log.warning(
            "task.py: primary checkout HEAD (%s) is detached mid-rebase (%s present); "
            "waiting up to %.0fs for the concurrent rebase to finish (poll %.1fs; "
            "override via %s)...", parent, "rebase-merge/rebase-apply", wait_bound,
            _rebase_poll_s(), _REBASE_WAIT_ENV,
        )
        announced = True
    time.sleep(_rebase_poll_s())
    # heartbeat: re-log every ~10 polls (implementer freedom on cadence)
```

Decisions (grounded in §8):

- **Poll interval 2.0s** — matches `sync_repo_root.INDEX_LOCK_POLL_S` (line 137); a rebase completes in seconds-to-a-minute, so 2s adds negligible latency while keeping ≤60 subprocess probes over the full bound.
- **Total bound 120s** — the candidate's suggestion, and the same magnitude as `EPM_ROOT_SYNC_LOCK2_WAIT_S` (120s, sync_repo_root.py line 163), which bounds the sibling contention on the same resource.
- **Marker-less grace re-probe: YES, exactly one (0.5s).** Git's internal ordering of state-dir removal vs HEAD re-attach at rebase start/finish is not contractually guaranteed; a single 0.5s re-probe closes both the just-created and just-removed windows at a worst-case cost of +0.5s on a genuine (non-rebase) detached refusal — negligible for a CLI, and skipped entirely when the knob is 0.
- **Loud wait: `_log.warning`** (consistent with the lock-collision retry at line 4322; logging's lastResort handler emits WARNING to stderr even unconfigured), one line at entry + a heartbeat every ~10 polls.
- **lru_cache interaction:** `functools.lru_cache` caches only successful returns — a raised `RuntimeError` (timeout or plain detached) is NOT cached, so the next call in the same process re-probes; a post-wait success IS cached (desired). No change needed; add one comment line at the decorator (line 325).

## 5. Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Wait runs while holding `~/.task-workflow/lock` (`_locked()`, line 607) — some callers resolve repo_root inside the flock | Other task.py mutators queue up to 120s behind the waiter | Strictly better than today (they'd have hard-refused during the same rebase). No deadlock: the rebase being waited on never needs the task-workflow flock to complete — `sync_repo_root.py` acquires its locks BEFORE rebasing, so if it holds the flock, task.py blocks at flock acquisition and never reaches the wait. State in the code comment. |
| Stale `rebase-merge` dir from a crashed rebase persists forever | Every task.py call pays the full 120s before refusing | Bounded timeout is the design's answer; the timeout message names the stale-dir possibility + `git rebase --abort` remedy. (Auto-abort à la sync_repo_root's husk triage is deliberately OUT of scope — a resolver must never mutate git state.) |
| Boundary races (marker just-created / just-removed around HEAD detach) | Spurious immediate refusal or one wasted poll | One 0.5s grace re-probe on detached+no-marker; the loop re-enters the full guard each poll, handling whatever state emerges (main / non-main / still detached). |
| `lru_cache` caching a refusal | Would poison the process after a timeout | Non-issue: lru_cache does not cache raised exceptions (verified — §7 A4); successes post-wait ARE cached, which is correct. |
| Behavior change breaks a consumer expecting the fast refusal | Scripts that probe-and-fallback on the refusal now hang 120s mid-rebase | The refusal fires only ~seconds later in practice (rebases are short); `EPM_TASKPY_REBASE_WAIT_SECONDS=0` restores the old behavior per-call. Message shape/type (`RuntimeError`, `detached` substring) preserved on both refusal paths. |

## 8. §11 Decision Rationale

- **Wait bound 120s** (`EPM_TASKPY_REBASE_WAIT_SECONDS`, 0 disables). Why: covers the observed multi-minute-tail rebase window while bounding stale-dir pathology. Source: candidate sketch (#996 body) + the sibling 120s bound `EPM_ROOT_SYNC_LOCK2_WAIT_S` (`sync_repo_root.py:163`). Alternatives: 30s (too short for a slow autostash rebase on the busy shared root); unbounded (masks crashed rebases forever).
- **Poll 2.0s** (`EPM_TASKPY_REBASE_POLL_SECONDS`). Why: rebases finish in seconds; 2s ⇒ ≤60 cheap probes per wait. Source: `INDEX_LOCK_POLL_S = 2.0` (`sync_repo_root.py:137`). Alternatives: 0.5s (more subprocess churn for no user-visible gain); 10s (adds up to 10s latency per mutation).
- **Grace re-probe: one, 0.5s.** Why: git's dir-removal vs HEAD-re-attach ordering at rebase boundaries is not contractual; one re-probe closes both windows at ≤0.5s cost on genuine detached refusals. Source: clarifier boundary-race analysis. Alternatives: none (leaves the just-removed race → spurious refusal); multi-second grace (slows every genuine refusal for no benefit).
- **Env knobs over injectable clock.** Why: tests need only a small bound + fast poll, both expressible as env on the existing subprocess fixture; an injected time source would be a bigger refactor than the fix. Source: repo norm (`EPM_ROOT_SYNC_*` knobs, float() fail-loud parsing).
