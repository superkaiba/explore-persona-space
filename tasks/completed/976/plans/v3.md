## 1. Goal + requirement + acceptance criteria

**Goal.** On the RunPod backend-executed leg (`execute_workload`, #909), the rendered launch script currently clears ONLY the exact declared attempt-namespaced sentinel path before detach (`rm -f {sentinel_path}`, `src/explore_persona_space/backends/runpod.py:421`). Widen that clear to the experimenter step-11.3 breadth — the flat legacy path `issue_<N>/.completion-sentinel.json` PLUS all attempt-namespaced siblings `issue_<N>/*/.completion-sentinel.json` — so a stale prior-attempt completion sentinel on the persistent `/workspace` volume can never satisfy `artifacts._resolve_live_sentinel`'s #685 single-live-sibling fallback on a same-pod re-execution.

**Why this is load-bearing (the failure chain, verified in code — with one #709 contingency).** Each launch mints a FRESH attempt id (`mint_runpod_attempt_id`, runpod.py:141) and clears only the NEW declared path. A prior attempt's success sentinel at `issue_<N>/rp-old/.completion-sentinel.json` survives on `/workspace` (persistent volume, nothing clears it across same-pod relaunches — runpod.py:150-154). If the NEW attempt then crashes without writing its sentinel, `_check_sentinel` (artifacts.py:862) calls `_resolve_live_sentinel` (artifacts.py:794): declared missing → sibling glob `issue_<N>/*/.completion-sentinel.json` (`_default_glob_sentinels`, artifacts.py:302-325) → exactly ONE live sibling (the stale one) → resolved. The content checks validate **phase + issue only, never attempt_id** (verified: artifacts.py:910-937; stated in runpod.py:147 "the PATH is the staleness defense"), so a resolved stale sentinel PASSes and a crashed re-execution finalizes green on unuploaded state — exactly the outcome the #598 attempt namespacing exists to prevent.

**Current-exploitability caveat (fact-checked 2026-07-04).** On TODAY'S RunPod finalize path the sibling probe is NOT fully live: `RunPodBackend.confirm_artifacts` (runpod.py:1092-1094) injects only the SSH `read_sentinel` reader; `io.glob_sentinels` stays the LOCAL-FS default, so the #685 sibling enumeration globs the VM's filesystem, where pod-side attempt dirs do not exist (the chain fires today only in a narrow hybrid where a coinciding VM-local path exists whose liveness is then read pod-side). Open sibling task **#709** plans exactly the SSH-backed `_ssh_glob_sentinels` injection for RunPodBackend — once it lands, the full chain above becomes live. This fix is therefore (a) the correct PROSPECTIVE hardening that must land before/with #709 (defense-in-depth ordering: clear the stale state at launch so the resolver never has a stale sibling to see), and (b) experimenter-lane parity (step 11.3) on its own merits, independent of #709.

**Requirement.** In `_render_launch_script`, replace the exact-path clear with a clear covering (a) the exact declared path (kept — pure breadth ADDITION, single-variable discipline), (b) the flat legacy path, (c) the attempt-sibling wildcard. Paths derived from the declared `sentinel_path` argument (grandparent split + basename), NOT from a second hardcoded copy of the `/workspace/eval_results/issue_{issue}` root — by construction the clear's breadth then equals the resolver's probe breadth (`_default_glob_sentinels` derives its glob from the same declared path's grandparent).

**Acceptance criteria (all test-backed, see §6):**

1. The rendered outer script (before the heredoc, before detach) contains one `rm -f` line carrying the declared path, the flat legacy path, and the `issue_<N>/*/.completion-sentinel.json` wildcard.

3. The same rm line exits 0 when NOTHING matches (fresh pod, first launch) — the unmatched-glob-under-`set -eu` assumption, test-backed.

Placement facts (unchanged, load-bearing):

- The new line stays in the **OUTER script** (index < the `<< 'EPSEOF'` heredoc start < the `setsid` detach line) — the clear runs pre-detach, pre-workload, exactly where the current one runs. Nothing about the quoted heredoc changes; the `*` is NOT inside it.
- The clear stays **AFTER the ALREADY-RUNNING guard** (lines 415-419): a live prior workload → `exit 5` before any rm, so the widened clear can never delete a sentinel a still-running sibling launch is about to depend on.
- `mkdir -p {sentinel_dir}` on the following line re-creates the current attempt's dir (the wildcard "deleting" the current attempt's sentinel is moot anyway — the fresh attempt id means the declared path cannot pre-exist except under attempt-id collision, and pre-launch nothing has been written).

- The docstring paragraph at runpod.py:395-397 ("The outer portion clears any stale sentinel at the declared path before detach") is updated to name the widened breadth + the #685/#976 rationale (docstring-on-edit rule).

**Shell semantics (verified assumption, also test-backed in §4.2 T3):** the outer script runs under `set -eu` (line 413) with NO `failglob`/`nullglob`/`pipefail`. An unmatched glob in POSIX sh/bash default mode is passed **literally** to `rm`, and `rm -f` with nonexistent operands exits 0 by POSIX spec (`-f`: "do not write diagnostic messages or modify the exit status" for missing operands). So the line exits 0 on a fresh pod with nothing to clear, and `set -e` does not abort the launch. Glob expansion happens pod-side at rm execution time: `_ssh_pod_run` (runpod.py:281-305) passes the whole script as ONE argv element to `ssh root@host <command>` via `subprocess.run` with an argv list (no `shell=True`), so there is no VM-side expansion layer to eat the `*`.

## 7. Risks + failure modes

| Risk | Assessment / mitigation |
|---|---|
| Wildcard also deletes the CURRENT attempt's sentinel | Fine by construction: the clear runs PRE-launch, before the workload writes anything; the declared path uses a freshly-minted attempt id so it cannot pre-exist (collision odds: timestamp + 4-hex); `mkdir -p {sentinel_dir}` on the next line re-creates the attempt dir. |
| Glob expansion in the wrong context (VM-side, or inside the heredoc) | The new operands live on the SAME outer-script line as the current clear — OUTSIDE the quoted `'EPSEOF'` heredoc, BEFORE the detach. `_ssh_pod_run` passes the script as one argv element over `ssh` with no `shell=True`, so expansion happens pod-side at rm execution. T1 pins the placement ordering. |
| Unmatched glob aborts the launch under `set -eu` | It does not: default sh/bash passes the unmatched pattern literally and `rm -f` exits 0 on nonexistent operands (POSIX). Test-backed by T3(b). |
| Cross-issue blast radius | None: all three operands are namespaced under `issue_<N>/` (per-issue dir); other issues' sentinels are untouchable by construction. |
| Deleting a completed prior attempt's sentinel that a PENDING finalize has not yet read | Intended semantics — identical to the experimenter-lane step-11.3 clear this ports: a re-execution on the same pod supersedes the prior attempt, and finalize ordering is the orchestrator's. The exact-path clear already had this property for a re-used attempt path. The ALREADY-RUNNING guard (before the rm) protects the only dangerous variant (a still-LIVE prior workload). |
| A directory literally named `.completion-sentinel.json` makes `rm -f` (no `-r`) fail → `set -e` abort | Pathological (nothing in the codebase creates such a dir; the writers create files). Accepted as negligible; a loud launch failure would also be the correct outcome for such corrupted state. |
| Test T1's exact-line `lines.index(...)` becomes brittle to future operand reordering | Deliberate: the exact string IS the contract (same style as the current test). T2's per-operand membership asserts provide the redundant, less brittle coverage. |

## 11. Decision Rationale

- **Wildcard clear shape (flat legacy + `*/` siblings).** *What:* `rm -f <declared> <issue_dir>/<name> <issue_dir>/*/<name>`. *Why:* removes every path the #685 fallback can resolve, plus the flat legacy path for lane parity. *Source:* `.claude/agents/experimenter.md` step 11.3 (lines 704-713 — the canonical experimenter-lane clear, verbatim shape). *Alternatives:* exact-path only (status quo — leaves the #685 hole); pod-side `find -delete` (heavier, no benefit).
- **Derive paths from the declared `sentinel_path` (grandparent split + basename), not from `issue` + a re-built root string.** *What:* `issue_dir = sentinel_dir.rsplit("/", 1)[0]`; `sentinel_name = sentinel_path.rsplit("/", 1)[1]`. *Why:* zero string duplication (no second `/workspace/eval_results/issue_{issue}` literal to drift), no new imports, and by-construction identity with the resolver's probe shape — `_default_glob_sentinels` globs `declared.parent.parent / f"*/{SENTINEL_FILENAME}"` (artifacts.py:322-325), the same grandparent derivation. *Source:* `src/explore_persona_space/backends/artifacts.py::_default_glob_sentinels` (the #685 fallback's own glob construction). *Alternatives:* (a) re-compose from `issue` + a lazy `SENTINEL_FILENAME` import — duplicates the root string or forces a shared-helper refactor of `runpod_sentinel_path` (a restructure the scope constraint bars); rejected. (b) module-level `SENTINEL_FILENAME` import — the function-local import at runpod.py:181 signals an import-order concern; unnecessary since the basename derivation is exact by construction (runpod.py:183 builds the declared path FROM `SENTINEL_FILENAME`). The TEST (T2) still imports `SENTINEL_FILENAME` to pin the coupling from the outside.
- **Attempt-namespacing rationale (why stale siblings exist at all).** *Source:* `runpod.py` docstrings — `mint_runpod_attempt_id` (lines 141-159, #598) and `runpod_sentinel_path` (lines 162-183): `/workspace` persists, nothing clears it across same-pod relaunches, same-pod retries are routine.
