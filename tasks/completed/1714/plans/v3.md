## 4. Design

### 4.1 Family-atomic Step 5a loop (SKILL.md L2236-2281)

**Chosen shape (Decision 1 = (a), hardcoded named families in bash):**

Declare 3 coupled families explicitly as bash arrays, then run a two-pass loop: pass 1 detects which family keys are dirty (any member has branch-side edits), pass 2 filters `SAFE_SPECS` to items whose family key is NOT dirty. Items in NO family (`.claude/agents`, `.claude/rules`, `CLAUDE.md`, `tests/test_guard_lessons_edit.py`) sit in a synthetic "singleton" family — each is its own key, so its dirty-flag is independent.

Pseudocode replacement for L2249-2281 (the executable block):

```bash
# Step 5a family-atomic sync (#1714 — supersedes #1560's per-item skip
# for coupled specs, while preserving the fail-safe direction: any dirty
# member widens the skip to the whole family, never narrows it into a
# clobber; #535).
#
# 3 coupled families exist in SPECS:
#   FAMILY_workflow: .claude/workflow.yaml <-> .claude/skills/issue/markers.md
#     (markers.md's marker-kinds + active-statuses tables are GENERATED
#     from workflow.yaml via `workflow_lint.py --emit-tables`; syncing
#     one without the other creates a stale-derived tree — the 0e2c3b21
#     incident, 2026-07-26)
#     [also implicitly includes SKILL.md's own AUTO-GENERATED status
#     table at L274-303 but SKILL.md is not in SPECS; if a future edit
#     adds SKILL.md to SPECS, join it to FAMILY_workflow]
#   FAMILY_lint: scripts/workflow_lint.py <-> :(glob)tests/test_workflow_lint*.py
#     (pin tests import symbols from workflow_lint.py; syncing new pin
#     tests against a stale linter is a collection ImportError — the
#     2de5253e incident, 2026-07-26)
#   FAMILY_guard: .claude/hooks <-> :(glob)tests/test_guard_*.py
#                                <-> tests/test_guard_lessons_edit.py
#     (guard tests exercise the hook implementations; syncing tests
#     against stale hooks fails behaviorally)
#
# Everything else in SPECS is a singleton (its own family, no coupling):
# .claude/agents, .claude/rules, CLAUDE.md.
declare -A FAMILY_OF
FAMILY_OF[".claude/workflow.yaml"]="workflow"
FAMILY_OF[".claude/skills"]="workflow"    # contains markers.md, the derived table target
FAMILY_OF["tests/test_workflow_yaml.py"]="workflow"    # imports render_*_table from workflow_lint AND reads workflow.yaml data via load_workflow_yaml — a workflow-data behavioral test
FAMILY_OF["scripts/workflow_lint.py"]="lint"
FAMILY_OF[":(glob)tests/test_workflow_lint*.py"]="lint"
FAMILY_OF["tests/test_autonomous_session_watch.py"]="lint"    # test_codex_outage_docstring_pass_count_lint_stays_green imports check_asw_docstring_pass_count from workflow_lint
FAMILY_OF[".claude/hooks"]="guard"
FAMILY_OF[":(glob)tests/test_guard_*.py"]="guard"
FAMILY_OF["tests/test_guard_lessons_edit.py"]="guard"
# Singletons: .claude/agents, .claude/rules, CLAUDE.md — each is its
# own family key (set below in the pass-1 loop by defaulting to its own path).

SPECS=".claude/agents .claude/skills .claude/rules .claude/workflow.yaml CLAUDE.md scripts/workflow_lint.py .claude/hooks tests/test_guard_lessons_edit.py tests/test_workflow_yaml.py tests/test_autonomous_session_watch.py :(glob)tests/test_workflow_lint*.py :(glob)tests/test_guard_*.py"
MB=$(git -C "$WT" merge-base HEAD main)

# Pass 1: detect dirty family keys. A family is DIRTY if ANY member has
# branch-side commits (subject-scoped exclusion for prior spec-freshness
# commits, as in #1560).
declare -A DIRTY_FAMILIES
for f in $SPECS; do
  bs_commits=$(git -C "$WT" log --format='%H %s' "$MB"..HEAD -- "$f" \
    | awk 'index($0, "spec-freshness") == 0')
  if [ -n "$bs_commits" ]; then
    fam="${FAMILY_OF[$f]:-$f}"    # default: singleton family = own path
    DIRTY_FAMILIES[$fam]=1
    echo "spec-freshness: $f carries branch-side feature edits — marking family '$fam' dirty; skipping blind sync for the whole family; reconcile manually."
    echo "  branch-side commits:"
    echo "$bs_commits" | sed 's/^/    /'
  fi
done

# Pass 2: filter SAFE_SPECS to items in a NON-dirty family.
SAFE_SPECS=""
for f in $SPECS; do
  fam="${FAMILY_OF[$f]:-$f}"
  if [ -z "${DIRTY_FAMILIES[$fam]}" ]; then
    SAFE_SPECS="$SAFE_SPECS $f"
  fi
  # else: skipped by family transitivity (message already printed in pass 1
  # for the offending member; skipped-siblings are covered by the family
  # membership declared above)
done

if [ -n "$SAFE_SPECS" ] && ! git -C "$WT" diff --quiet main -- $SAFE_SPECS; then
  git -C "$WT" checkout main -- $SAFE_SPECS    # surgical refresh: workflow surface only
  git -C "$WT" diff --quiet HEAD -- $SAFE_SPECS || \
    git -C "$WT" commit -m "issue-<N>: sync workflow-surface specs from main (spec-freshness)" -- $SAFE_SPECS
fi
```

Preserved from #1560 (do NOT drop):
- Subject-scoped `--format='%H %s'` + `awk 'index($0, "spec-freshness") == 0'` (pin test 7).
- The `[step10d]` re-sync echo breadcrumb + never re-derive `$WT` invariants (pin test 8 — carried at Step 10d, unchanged there).
- The `:(glob)` / per-item skip grain COMMENT (pin test 6) — remains factually accurate at the ITEM level; supplement with a "family-atomic when a family key exists" clause but do NOT delete the per-item grain sentence (a singleton's family IS the item itself).

**Decision 2 — `--emit-tables` fold: DROPPED (recommend against including it).** Rationale in §11. The workflow family stays skip-only; regeneration is not folded into the sync commit.

**Decision 3 — Step 10d re-sync placement: (a), POST-gate, with a defense-in-depth cheap freshness re-check.** See §4.2.

**Decision 4 — Post-sync fast-forward assertion: DROPPED as a hard assert (see §11); light diff-stat echo retained for observability.** After the `git checkout main -- $SAFE_SPECS`, add:

```bash
if [ -n "$SAFE_SPECS" ]; then
  echo "[step5a] synced from main:"
  git -C "$WT" diff --stat HEAD^ HEAD -- $SAFE_SPECS 2>/dev/null || echo "  (no commit — no drift)"
fi
```

This is observability only, not a gate — the concern in the task body (the 139-line silent revert of `workflow_lint.py`) is already covered by (i) the family declaration (that file is in FAMILY_lint, so a branch-side edit to `scripts/workflow_lint.py` — as `e3b70618` had — marks the whole lint family dirty, `workflow_lint.py` never gets checked out from main), and (ii) `git checkout main --` always produces a fast-forward-shape sync of the CHECKED-OUT paths (the checkout writes main's blob; the branch cannot be "ahead" of what's checked in). The 139-line-revert case in `e3b70618` was a bug in the per-ITEM skip: `workflow_lint.py` was skipped for branch-side edits but its family-member `.claude/skills` (which pins `SKILL.md`'s own generated tables) was synced. Under family-atomic, `workflow_lint.py`'s family (lint) is different from `.claude/skills`'s family (workflow) — but critically, `e3b70618`'s ACTUAL problem was that SKILL.md itself was pinned by a family-member OTHER than `workflow.yaml`. Re-read: the 139-line re-add specifically happened when `scripts/workflow_lint.py` was skipped (branch edited it) but the sync committed 3 other files from main. Under family-atomic, `workflow_lint.py`'s skip marks FAMILY_lint dirty, so `tests/test_workflow_lint*.py` is also withheld — but `.claude/skills`, `.claude/workflow.yaml`, `.claude/hooks`, etc. sit in DIFFERENT families and would still sync. The 139-line-revert prevention comes from something else: the checkout write ALWAYS writes main's blob (never re-adds bytes to a file NOT in $SAFE_SPECS), so if `workflow_lint.py` is not in `$SAFE_SPECS`, its 139-line diff is UNTOUCHED by this sync. `e3b70618`'s described 139-line re-add must have been on a DIFFERENT synced file that happened to have had 139 lines removed on main. Regardless, the correct mitigation is family-atomic (as designed above); the light diff-stat echo lets the operator see what changed at a glance.

done

## 11. Decision Rationale

**Decision 1 — Family declaration form: (a) hardcoded named families in bash.**
- **What:** `declare -A FAMILY_OF` associative array + two-pass loop (detect dirty families, then filter SAFE_SPECS).
- **Why:** More explicit than a nested loop over pre-declared arrays (option (a) as originally framed in the brief), and easier for a human reviewer to audit (`grep FAMILY_OF SKILL.md` shows every coupling on one line each). Bash 4+ is available on the VM.
- **Source:** #1560's own declaration form is a bash for-loop; extending it with `declare -A` is the smallest structural change. No literature grounding needed (infra bash).
- **Alternatives:** (option in the brief) `FAMILY_workflow=(...)` bash arrays + a nested loop `for fam in workflow lint guard; do for m in "${!fam}"; do ...` — more moving parts, indirect variable expansion is error-prone. `FAMILY_OF` associative array + two-pass loop is simpler and more grep-visible.

**Decision 2 — `--emit-tables` derived-artifact fold: DROPPED.**
- **What:** Do NOT include the "sync family + regenerate markers.md via `workflow_lint.py --emit-tables` and fold into the same commit" option. Family-atomic skip is sufficient.
- **Why:** (i) Adding a scripted regeneration step to the sync commit widens the surface area of what's synced (extra file mutation inside the sync commit). (ii) The branch's `workflow.yaml` edits are stale relative to main REGARDLESS of whether markers.md is re-emitted — if the branch's workflow.yaml is stale relative to main's (a different marker was added on main), the merge itself will surface that conflict. (iii) `--emit-tables` on a stale `workflow.yaml` would EMIT stale markers.md content — the "regenerated" table would be stale-by-construction relative to main's true state. Family-atomic skip is the correct fail-safe: keep the branch's `workflow.yaml` + branch's `markers.md` together as a coherent pair; let the merge resolve any conflict against main.
- **Source:** Task body's own recommendation "an ACCEPTABLE substitute" (explicitly framed as optional).
- **Alternatives:** Fold `--emit-tables` in — rejected per (i)-(iii). Skip-only with no regeneration — the chosen path.

**Decision 3 — Step 10d re-sync placement: (a) POST-gate.**
- **What:** Move the re-sync from pre-gate (current L10240-10276) to post-gate (immediately before `gh pr merge`).
- **Why:** The 67cf175e session (2026-07-26T15:53→16:40Z) proved that `origin/main` advances during the ~30 min gate window often enough to red the merge with `CONFLICTING`. The gate builds its landing tree from `git archive origin/main` — a re-sync AFTER the gate does not invalidate the verdict (the gate already ran its 3-way merge on `workflow_lint.py`). Option (a) directly closes the race window (a few seconds between `fetch` and `gh pr merge` instead of ~30 min); the residual few-second race is handled by `gh pr merge`'s own MERGEABLE check + the existing merge-conflict-recovery path.
- **Source:** Task body's explicit preference "Option (a) is preferred — the gate's own landing-tree copy already builds from `git archive origin/main`, so a post-gate sync does not invalidate the verdict."
- **Alternatives:**
  - Option (b) [keep pre-gate + re-run when gate took >5 min]: adds a wall-time-conditional branch, harder to reason about, doubles the number of sync commits in the slow-gate case.
  - Defense-in-depth combo [pre-gate cheap re-check + post-gate re-sync]: adds complexity for marginal safety; the post-gate placement alone closes the observed race.
  - I picked (a) alone; the pre-gate section stays UNTOUCHED in behavior — the pin test 3 is updated to assert post-gate placement (§4.4).
- **Named risk:** stale spec content at gate time. Answer: for `workflow_lint.py`, #1456's 3-way merge covers it (payload-touched lint is merged with main's lint). For OTHER spec files (agents, rules, hooks, tests), the branch's OWN spec content is what the branch is DELIVERING — the gate SHOULD lint the branch's version, which is what a landing-tree overlay produces. No re-red.

**Decision 4 — Post-sync fast-forward assertion: DROPPED as a hard assert; light `diff --stat` echo retained for observability.**
- **What:** No `git diff --quiet` gate that refuses to sync a fast-forward'd file. Instead, add a `[step5a] synced from main: <diff-stat>` echo after the sync commit.
- **Why:** `git checkout main -- $SAFE_SPECS` writes MAIN's blob to the paths in `$SAFE_SPECS`. A file not in `$SAFE_SPECS` is untouched. A hard assert `git diff origin/main HEAD -- $SAFE_SPECS` after the checkout is empty by construction (the checkout just wrote main's bytes) — the assert would be tautological. The 139-line re-add case in `e3b70618` was because the file was in `$SAFE_SPECS` while its family member was NOT — which is exactly what family-atomic prevents. The light echo is observability, not gating.
- **Source:** Task body proposed this as a "safety net"; the analysis above shows it is redundant given family-atomic + the checkout's own semantics.
- **Alternatives:** Include as a hard assert — tautological, adds no safety. Include as a light echo (chosen).
