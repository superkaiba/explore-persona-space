### 4.1 The new lens (exact prose to add to `code-reviewer.md`)

```markdown
### Step 0.66: Compute-shape-vs-dispatcher parity check (`type:experiment` only)

An experiment whose approved plan §9 declares a **data-parallel / sweep
fan-out** shape (multiple GPUs, each driving an INDEPENDENT shard / cell /
seed / condition — the "Sweep parallelism" or "Data parallelism" axis in
`planner.md` §9) MUST ship a dispatcher that can actually drive that
fan-out. Otherwise the experimenter provisions the multi-GPU pod the plan
calls for and (N−1) GPUs sit idle at 0% until a human notices — the #779
round-6 failure (plan §9 declared "8-GPU DP, 8 single-GPU
CUDA_VISIBLE_DEVICES workers sharding contexts"; the dispatchers accepted
only `--gpu-id N`; round-6 review PASSed; the first pod-util reading showed
all 8 H100s at 0%; round 7 descoped to 1×H100). This is the review-side
sibling of the runtime `_compute_wave_size` guard (experiment-implementer
memory `feedback_dispatcher_wave_size_must_match_visible_gpus.md`, #667):
that guard catches "code fans out onto more GPUs than exist"; this lens
catches "plan provisions more GPUs than the code can use".

**Trigger — read the plan first, only then FAIL is possible.** This lens
fires ONLY when the approved plan **explicitly declares a data-parallel
shape**. Read `planner.md` §9's two declaration sites in the approved plan:

- the **parallelism-axis** statement (the plan's §9 "(b) the parallelism
  axis it exploits") — a `Sweep parallelism` or `Data parallelism
  (FSDP/ZeRO-3)` axis, OR
- the **per-component compute-projection table**'s `parallelism` column.

`rg` the approved plan for a DP declaration:

```bash
rg -in 'data.?parallel|sweep parallelism|[0-9]+[ -]*gpu (dp|data-parallel)|shard(ing)? (the )?(contexts|cells|seeds|conditions)|multiple .*CUDA_VISIBLE_DEVICES workers|CUDA_VISIBLE_DEVICES.?sharded|ZeRO-3 across|FSDP' <approved plan path>
```

**Do NOT fire on a non-DP shape.** These are legitimate and must NOT bounce:
- a single-GPU plan (`lora-7b` 1×H100, `eval`/`debug` 1×L4, or an explicit
  "single-GPU" / "TP=1" / "no parallelism axis applies" statement);
- a **tensor-parallel** shape (`TP=N`, `tensor-parallel`, `inf-70b`,
  `ft-70b`) — TP is handled inside a single `LLM.generate()` / model-load
  call (`tensor_parallel_size=N`), not by a per-shard dispatcher, so the
  DP-fan-out flags below do NOT apply to it;
- a **batched-vLLM** shape (one `LLM.generate()` over N prompts on one pod)
  — again a single call, not a per-shard fan-out.

If the plan declares NO DP shape (or only TP / batched-vLLM / single-GPU),
record the one-line conclusion "N/A — plan declares no data-parallel
fan-out shape (<axis>)" in the verdict body and proceed to the diff.

**When the plan DOES declare a DP shape, verify the dispatcher(s) in the
diff expose that fan-out — at least ONE of:**

(a) **In-dispatcher flag-driven fan-out** — the dispatcher exposes a
    shard/wave selector the launcher passes: a `--shard-id N --num-shards K`
    pair, or the project's `--n-gpus` `WaveDispatcher` fan-out (round-robin
    `i % n_gpus` CVD-pinned subprocess-per-cell — the `#664`/`#676`/`#693`
    canonical shape in `src/explore_persona_space/orchestrate/fleet.py`),
    or an equivalent per-shard CLI selector.

    ```bash
    rg -n -- '--shard-id|--num-shards|--n-gpus|WaveDispatcher|submit_judge_async|_wave_gpu_id|i % n_gpus|CUDA_VISIBLE_DEVICES' <each pod-side dispatcher in the diff>
    ```

(b) **Internal worker spawn** — the dispatcher spawns one worker per GPU
    itself via `torch.multiprocessing.spawn`, `torch.distributed.run` /
    `torchrun` / `accelerate launch` (the ZeRO-3 / FSDP path), or a
    per-worker `subprocess.Popen` / `subprocess.run` loop that pins each
    child to a distinct `CUDA_VISIBLE_DEVICES`.

    ```bash
    rg -n -- 'multiprocessing\.spawn|torch\.distributed|torchrun|accelerate launch|subprocess\.(Popen|run)\(' <each pod-side dispatcher in the diff>
    ```

(c) **External per-GPU fan-out wrapper** — a `scripts/issue<N>_dispatch.sh`
    (or an equivalent launcher in the diff / named in the implementer's
    `## Smoke run` / `(c) How to verify`) that fans out ONE dispatch
    process per GPU with DISTINCT `--gpu-id` values, each processing a
    disjoint shard. A single-GPU dispatcher IS a valid building block when a
    committed wrapper drives one instance per GPU — so grep the diff (and
    read the implementer report's launch command) for such a wrapper before
    concluding the fan-out is absent.

    ```bash
    rg -ln -- 'gpu.?id|CUDA_VISIBLE_DEVICES|for .*gpu|--only-source' scripts/issue<N>_dispatch.sh 2>/dev/null
    ```

**FAIL** with a single `Critical` issue tagged `compute-shape-mismatch`
when the plan declares a DP shape but NONE of (a)/(b)/(c) is present — name
the plan's declared shape, the pod intent it implies, and each dispatcher
you grepped, AND still read the diff and report substantive findings in the
same pass (do not short-circuit — see Step 0.7):

> `epm:experiment-implementation v<n>`'s approved plan §9 declares a
> data-parallel fan-out (`<quote the plan's parallelism axis / projection
> `parallelism` cell>`), implying a multi-GPU pod (`<intent>`), but the
> dispatcher(s) `<file(s)>` expose no fan-out mechanism: no
> `--shard-id`/`--num-shards`/`--n-gpus`/`WaveDispatcher` selector (a), no
> internal `torch.multiprocessing.spawn`/`torch.distributed`/per-worker
> `subprocess` spawn (b), and no external `scripts/issue<N>_dispatch.sh`
> per-GPU fan-out wrapper (c). Launching as planned provisions an N-GPU pod
> with (N−1) GPUs at 0% until a human notices (#779 round 6). Re-post
> `v<n+1>` with a fan-out mechanism wired in, OR amend the plan §9 to the
> single-GPU shape the dispatcher actually supports (re-plan).

`compute-shape-mismatch` is a SUBSTANTIVE code/plan-parity finding (a
mismatch between the approved plan and the dispatcher's actual
capability), NOT a mechanical/presentation gate: it is NOT in the
Step 5c-bis mechanical-contract-only strip set `{marker-shape,
smoke-run-missing, git-provenance}` and stands as a real Critical blocker
until the implementer wires the fan-out or the plan is amended. If the
plan declares no DP shape, this gate is N/A — record that conclusion and
proceed.
```
