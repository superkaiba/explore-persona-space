## 1. Goal

> Thread the launch spec's `boot_disk_gb` into the RunPod GPU provision's `--volume-gb` (or fail loud when a declared disk requirement cannot be satisfied on the RunPod GPU lane), so a plan-specified disk size survives a GCP→RunPod pivot.

## 4. Design

### D1 — `src/explore_persona_space/backends/runpod.py`: GPU-lane threading

**(a) New module constant** next to `_CPU_CONTAINER_DISK_FLOOR_GB` (line 94):

```python
#: Floor for the #1118 GPU-lane volume threading in :meth:`RunPodBackend.launch`
#: — mirrors pod_lifecycle.py's ``provision --volume-gb`` argparse default (200),
#: the /workspace volume an un-threaded GPU provision gets, so threading a
#: plan's ``boot_disk_gb`` can only ever GROW the volume relative to today's
#: default, never shrink it. (Not imported from ``scripts/pod_lifecycle`` —
#: this module's imports stay ``base``-only by documented convention.)
_GPU_VOLUME_FLOOR_GB = 200
```

**(b) Rework the #1010 block in `launch()`** (lines 763-785) — parse fail-loud, then branch CPU/GPU:

```python
raw_boot_disk = (spec.extra or {}).get("boot_disk_gb") or 0
try:
    boot_disk_gb = int(raw_boot_disk)
except (TypeError, ValueError) as exc:
    raise ValueError(
        f"spec.extra['boot_disk_gb'] is not an integer: {raw_boot_disk!r} "
        f"(malformed disk requirement on issue {spec.issue})"
    ) from exc
if boot_disk_gb:
    from explore_persona_space.backends.router import (
        RUNPOD_CPU_INSTANCE_FOR_INTENT,  # lazy: module top stays base-only
    )

    if spec.intent in RUNPOD_CPU_INSTANCE_FOR_INTENT:
        # #1010: CPU lane — /workspace rides the overlay; disk = containerDiskInGb.
        cmd += ["--container-disk-gb", str(max(_CPU_CONTAINER_DISK_FLOOR_GB, boot_disk_gb))]
    else:
        # #1118: GPU lane — the big-data mount is the /workspace VOLUME
        # (pod_lifecycle threads --volume-gb -> runpod_api volumeInGb).
        # Floored at the 200 GB argparse default: thread-or-grow, never shrink.
        # No deterministic pre-API cap exists for GPU volumeInGb (unlike the
        # probe-verified CPU caps) — an unsatisfiable size surfaces LOUD at
        # RunPod create time (RunPodError -> non-zero provision exit) or as a
        # capacity miss (wait-for-capacity budget), never as a silent downsize.
        cmd += ["--volume-gb", str(max(_GPU_VOLUME_FLOOR_GB, boot_disk_gb))]
```

Update the stale line-763-774 comment ("boot_disk_gb does not map" on GPU) accordingly.

### D2 — Typed refusal: what it gates vs what RunPod create-time validation gates

**There is no reliable pre-API cap to check for GPU `volumeInGb`.** The #1010 refusal was possible because the CPU instance flavors have FIXED, probe-verified container-disk caps (`RUNPOD_CPU_INSTANCE_CAPS`). GPU pod volumes are host-local disks whose satisfiable size is host/capacity-dependent — there is no fixed cap table in `runpod_api.py`, no documented provider constant, and probing one would need paid creates. The `.claude/rules/gotchas.md` MooseFS ~130 GB note describes the write quota on the *provisioned* volume, not a provisioning cap (see Assumptions A6). **Inventing a numeric cap constant would be an ungrounded hyperparameter, so this plan deliberately does not add a `runpod_volume_infeasible_for_plan` router gate.** The task body's diff sketch conditioned the typed refusal on a provider/host cap existing; it does not, deterministically.

What the fail-loud surface actually is:

- **Gated pre-API (typed, this plan):** a malformed `boot_disk_gb` → the named `ValueError` in D1(b) (raised before the provision subprocess, no pod paid for).
- **Relies on RunPod create-time validation (documented, loud, no downsize path exists):** an oversize/unsatisfiable volume surfaces as either (i) a GraphQL validation error → `RunPodError` → non-zero `pod_lifecycle provision` exit → `subprocess.CalledProcessError` propagates from `RunPodBackend.launch` (runpod.py:786-791) → selector → `epm:failure`; or (ii) a capacity miss (`null` result / SUPPLY_CONSTRAINT) → the bounded `create_pod_with_wait_for_capacity` retry → `WaitForCapacityStillWaiting` exit. Both are loud terminals. Structurally, **no code path can downsize**: the threading passes `max(200, boot_disk_gb)` or nothing; there is no clamp branch on the GPU lane (the CPU clamp at pod_lifecycle.py:1767-1788 is CPU-branch-only and untouched).

## 7. Kill criteria (what would make this approach wrong)

1. **`--volume-gb` not actually reaching `volumeInGb` on the GPU path** — falsified by code reading (pod_lifecycle.py:1843/1863 → runpod_api.py:514); if a hidden clamp/override existed between them, the fix point would move to pod_lifecycle instead.
2. **RunPod's writable `/workspace` quota NOT tracking the provisioned `volumeInGb`** (i.e. the MooseFS ~130 GB gotcha being a fixed host quota independent of provision size) — then a bigger volume would not deliver more writable space and the correct fix is routing big-disk GPU plans away from RunPod (a router-side feasibility refusal), not threading. Detectable on the first big-volume provision: preflight's `posix_fallocate` probe + `df /workspace`. See Assumption A6.
3. **The CPU-branch `args.volume_gb == 200` "unset" sentinel receiving GPU-threaded flags** — precluded by the CPU/GPU branch split (a `--volume-gb` is only ever added on non-CPU-mapped intents). Scope correction (fact-check): `cpu-bigmem` never reaches `RunPodBackend.launch` on any AUTOMATED path (router `_runpod_terminal_rung` #677 guard precedes launch), but an explicit `backend: runpod` pin of `cpu-bigmem` DOES reach `launch()` (`_override_runpod` has no CPU guard; `_translated_runpod_intent` passes CPU intents through, router.py:434-443/1946-1947). In that pinned case the else-branch would thread `--volume-gb`, and the provision then fails LOUD downstream regardless (`resolve_cpu_intent("cpu-bigmem")` → None, gpu_heuristics.py:110-118; GPU `_resolve_spec` cannot resolve `cpu-bigmem` → provision exit ≠ 0 → `CalledProcessError`) — no silent mis-provision is possible, so the "not in CPU map" branch key is retained as-is.

## 11. Decision Rationale

- **Floor value = 200 (`max(200, boot_disk_gb)`)** — What: never pass a volume below today's un-threaded default. Why: threading must never SHRINK the disk a launch gets today (hard constraint). Source: pod_lifecycle.py:2417 (`--volume-gb` argparse `default=200`) + the #1010 precedent constant `_CPU_CONTAINER_DISK_FLOOR_GB` (runpod.py:88-94). Alternatives: pass the flag only when `boot_disk_gb > 200` (byte-equivalent semantics, but diverges from the #1010 code shape); no floor (rejected — a plan stating 100 GB would shrink the pod below today's behavior).
- **No `runpod_volume_infeasible_for_plan` router gate; named-ValueError + provider validation instead** — What: D2. Why: the #1010 gate's legitimacy came from probe-verified fixed CPU caps (router.py:2687-2705, "probe-verified"); no deterministic GPU-volume cap exists to check, and inventing one is an ungrounded constant that would either false-refuse feasible launches or never fire. Source: router.py:2685-2705 + runpod_api.py:481-560 (no cap table; capacity/validation handled at create) + the task body's own conditional phrasing ("when the requested size exceeds the provider/host cap"). Alternatives: a config-tunable soft cap with env override (rejected: still ungrounded, adds a knob nobody can set correctly); a live capacity probe pre-create (rejected: `podFindAndDeployOnDemand` IS the probe — a failed create is free).
- **Malformed-value fail-loud shape** — What: named `ValueError` mirroring `_footprint_int`. Why: fail fast with a diagnosable message; GPU intents bypass the router's CPU-only `_footprint_int`, so today a malformed value on the GPU lane would hit a bare `int()` traceback. Source: router.py:2708-2722 (message shape reused verbatim).
- **Persist + forward through the RunPod-handle reconstruction (D4)** — What: handle-extra keys + `_runspec_from_runpod_handle` forwarding. Why: otherwise the wedge/CUDA-IMA fresh re-provision recreates the #1112 silent 200 GB downsize one failover later. Source: the #1010 twin fix for the GCP handle (gcp.py:4520-4533 + backend_poll.py:2833-2844 — the pattern is copied line-for-line, including the "keys omitted when absent" legacy-shape contract).
- **CPU lane untouched** — What: `--container-disk-gb` branch byte-identical; no `--volume-gb` on CPU intents. Why: hard task constraint + the pod_lifecycle CPU branch treats `args.volume_gb == 200` as "unset" (line 1745-1751) — an explicit CPU `--volume-gb` would defeat the #747 cheap-CPU volume default. Source: pod_lifecycle.py:1745-1794.
