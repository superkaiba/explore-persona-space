# Bound active-task VM disk by construction: relocate `.claude/worktrees/` + per-issue caches onto a dedicated GCP persistent disk WITH per-task quotas

> **ARCHITECTURAL — needs user greenlight.** This changes the orchestration VM's
> foundational storage layout (attaches a new GCP persistent disk, relocates the
> `.claude/worktrees/` tree onto it, enables ext4 per-PROJECT quotas so one task
> cannot starve another, takes on a recurring GCP cost) and is therefore gated at
> the Step 2c plan-approval gate regardless of the 0 GPU-h cap. The cutover
> touches every concurrent session's filesystem and MUST happen during a brief
> drain window — do not approve without reading §6 (Compatibility / migration),
> §10 (Kill criteria), and the TWO gate-time choices in §13 (disk SIZE + per-task
> quota CAP).

## §0 Plan Summary

**What:** Attach a new **512 GB `pd-balanced` GCP persistent disk** (down from
v1's 1 TB — see §3/§9: #677 already routes the dominant 139 GB cache class
off-VM, so the on-disk RESIDUAL is ~100-150 GB, not 250 GB), format it ext4
**with the `project` feature + prjquota enabled**, mount it at `/mnt/eps-data`,
and **relocate the `.claude/worktrees/` tree** (currently **253 GB** measured
2026-06-27 — every active task's worktree + its per-issue
`data/issue_<N>/{hf_dl,g*_dl,store}` caches land there, the `#658` family alone
is ~180 GB) onto the new disk via a one-time FD-safe copy + **bind mount**, so
the heavy active-task footprint never lands on the 485 GB boot disk holding `/`.
**Per-issue ext4 project quotas** then bound EACH task's footprint on the data
disk, so neither `/` NOR another concurrent session can be starved by one
runaway task — this is the "bounded by construction" guarantee #679 deferred,
delivered at the per-TASK grain, not merely per-DEVICE.

**Chosen mechanism: Option A (dedicated GCP PD + prjquota on the FRESH disk),
NOT Option B (prjquota on the live root fs).** Option B is **non-viable on this
host**: enabling `prjquota` on a live, mounted **root** ext4 filesystem requires
unmounting `/` (a reboot / single-user procedure — impossible on the running VM
with 39 worktrees and a live ~151 GB #658 process holding open files), and the
`quota` userspace package is not installed. Option A formats a FRESH disk where
`mkfs.ext4 -O project -E quotatype=prjquota` is trivial (no live-root unmount),
hot-attaches with **zero downtime**, and adds the per-task quota grain Option B
would only have given for the root fs.

**Per-task isolation (the v1 gap, now closed):** ext4 prjquota assigns each
`issue-<N>` worktree subtree a distinct project id (`chattr -p <projid> -R`) with
a per-project hard byte cap (default **128 GB/issue**, gate-tunable). A task that
hits its cap gets a loud `EDQUOT` write failure (the SAME fail-loud signal the
RunPod MooseFS quota already produces) — its writes stop, but the shared data
disk keeps free space for every OTHER issue's worktree. The disk SIZE is then
decoupled from per-task starvation: even a 256 GB disk cannot be monopolized.

**Cost:** 512 GB `pd-balanced` at **$0.10/GB-month** (us-central1) =
**$51.20/month** recurring (down from v1's $100/mo for 1 TB). One-time setup:
~3-4 h of orchestrator/operator time + a ~10-min drain window.
**`Estimated GPU-hours (total): 0`**

**Invariant preserved:** no code path auto-deletes active data; the data disk is
a *containment boundary* AND per-task quotas are a *per-tenant* boundary; a
disk-full or quota-hit condition is recoverable (writes fail loudly, `/` stays
healthy, other sessions keep running, the existing `vm_disk_guard` escalation
re-points at the new mount). This is the **bounded-by-construction** structural
fix #679 deferred, now at per-task grain.

**Top risks:** (1) cutover-time race + #658-path-continuity — a session resolving
`.claude/worktrees/issue-658` during/after the swap must NEVER see a missing
tree; mitigated by FD-safe copy-#658-first ordering (§4 Phase 2, Must-Fix #1)
NOT exclude-and-defer. (2) a per-task quota set too low silently EDQUOTs a
legitimate large run; mitigated by a generous default cap (128 GB) + the
fail-loud (not silent) EDQUOT signal + the operator can raise a project's cap
live with `setquota -P` (no remount).

## §1 Goal + acceptance criteria

**Goal:** Make active-task VM disk consumption bounded by construction so no
single task can exhaust the shared CPU-VM root disk (`/`) **and no single task
can starve any OTHER concurrent task**, and so a disk-full / quota-hit condition
is recoverable without deleting any active task's data.

**Acceptance criteria (quantitative):**

1. **Containment (`/` protected):** A 200 GB write into one issue's data dir
   (`<repo>/.claude/worktrees/issue-<N>/data/issue_<N>/hf_dl/...`) lands on
   `/mnt/eps-data` and leaves `/` (the boot disk) usage **unchanged** (verified:
   `df /` before/after shows < 1 GB delta on `/`; growth shows on
   `df /mnt/eps-data`). *(The 200 GB write also tests the quota — see #7.)*
2. **No active-data deletion:** A `/`-at-95% (or data-disk-at-95%) condition
   triggers escalation (Telegram + sidecar) but **no active task's
   worktree/cache/store is deleted** (verified by the `vm_disk_guard` active-skip
   + escalate path, re-pointed at the new mount; the data-disk pass is
   escalate-ONLY — it never runs the reclaim tiers, §4 Phase 4).
3. **Recovery without downtime:** When the **data disk** is wedged at 100%, the
   boot disk `/` stays < 85% used, every concurrent session continues to spawn
   Bash successfully (the silent-Bash-failure regime is on `/`, now protected),
   and the operator's recovery is the existing safe reclaim
   (`clean_experiment_downloads.py <N> --apply` on a terminal issue), a per-task
   `setquota -P` raise, or a data-disk live-resize — never an active-data delete.
4. **Path transparency:** Every existing consumer that resolves
   `repo_root()/.claude/worktrees/...` or `repo_root()/data/issue_<N>/...`
   continues to resolve unchanged (bind mount is path-faithful); the full
   `pytest` suite passes; `new_worktree.sh` creates worktrees on the new disk
   transparently, **at all times including the deferred-#658 window**.
5. **Reboot-durable:** The mount + bind + `quotaon -P` survive a VM reboot (fstab
   `LABEL=...,prjquota` + systemd-ordered bind + a `quotaon` unit; verified by
   `systemctl status` + a simulated remount).
6. **Live-#658 continuity (REPLACES v1's "#658 untouched"):** The migration never
   interrupts the live ~151 GB `.claude/worktrees/issue-658` worktree or its
   process, AND `.claude/worktrees/issue-658` resolves to a complete, correct
   tree at EVERY instant of the cutover (no window where the canonical path
   resolves into a data-disk tree lacking #658). See §4 Phase 2 + §6.
7. **Per-task isolation (NEW — the #679-deferred "bounded by construction"):**
   one issue at-or-over its per-project quota cannot consume space allocated to
   another issue: a write that exceeds issue-A's project cap fails with `EDQUOT`
   while issue-B continues to write successfully on the same data disk (verified
   by the §5 starvation test against the real prjquota decision path; manually
   confirmed post-cutover with two project ids + `setquota -P`).

## §3 Option comparison — A (dedicated GCP PD + prjquota) vs B (prjquota on root)

| Dimension | **Option A — dedicated GCP PD + bind-mount + prjquota on the FRESH disk** | **Option B — ext4 `prjquota` on the live root fs** |
|---|---|---|
| **One-time cost** | ~3-4 h operator time; ~10-min drain window; no reboot; `mkfs.ext4 -O project` on a fresh empty disk is trivial | ~3-4 h + **a VM reboot / single-user boot** to unmount `/` and `tune2fs -O quota,prjquota` (the root fs cannot be converted live); install `quota` pkg |
| **Recurring cost** | **~$51/mo** (512 GB pd-balanced @ $0.10/GB-mo) | **~$0** recurring, but a root-fs reboot up front |
| **Per-task isolation** | **YES — per-issue project id + `setquota -P` hard cap on the data disk** (the #679-deferred guarantee) | YES in principle, but only on the root fs, and unreachable without the reboot |
| **Blast radius** | Confined to two trees on a separate physical device; boot disk + its mount options untouched | Touches the **root filesystem's mount options + on-disk feature flags** — a quota subsystem bug can wedge writes for ALL sessions on `/` |
| **Migration risk to active sessions** | Drain to quiescent worktrees, FD-safe copy + bind; #658 copied FIRST (path-continuous). No reboot → 38 of 39 sessions never interrupted | **Requires a reboot** (root fs unmount) → **every** session + the live #658 process is killed. Unacceptable while #658 is live |
| **Recovery semantics** | Quota hit → that issue's writes fail loudly (EDQUOT) BUT every other issue keeps writing; operator raises the cap live (`setquota -P`, no remount) or resizes the PD live | Quota hit → fails loudly per project, but recovery from quota-accounting corruption needs `quotacheck` (offline → another reboot) |
| **Observability** | `df /mnt/eps-data` per-disk + `repquota -P /mnt/eps-data` per-project | `repquota -P /` per-project; must distinguish at-quota EDQUOT from unrelated EIO on the root fs |
| **No-delete-active-data invariant** | Native: containment is physical, per-task is quota-enforced, deletion never required for recovery | Native per quota'd project, but recovery from corruption is offline |

**Residual-baseline reconciliation (Must-Fix #3).** The architectural greenlight
(now ~$51/mo, down from ~$100/mo) must rest on the RESIDUAL footprint #677 has
NOT already removed, not the raw 253 GB:

| Component of the 253 GB worktree footprint | Handled by | On-VM residual #681 must bound |
|---|---|---|
| #658-family CPU-phase HF/activation cache (~139 GB, the incident driver) | **#677 `cpu-bigmem` off-VM routing** + #679 `--incremental` cleaner | **0** (routed off-VM / reaped) |
| #658-family durable checkouts + `store/` (the part not a re-downloadable cache) | #681 quota | included in residual |
| All OTHER active issues' worktrees + their `hf_dl`/`store` caches | #681 quota | included in residual |
| **Estimated residual peak** | — | **~100-150 GB** (253 − 139 cache = ~114 GB today; budget headroom for several concurrent large checkouts) |

So the recommendation DROPS from 1 TB to **512 GB** ($51/mo): 512 GB is ~3.5-5×
the residual peak, GCP PDs grow-live-only (over-provision is the safe direction),
and — critically — the per-task prjquota cap makes the disk SIZE decoupled from
per-task starvation, so a smaller disk is no longer a per-tenant risk. A 256 GB
disk ($25/mo) would still be ~2× the residual and is offered as the cost-minimal
alternative at the gate (§13). The "$0 do-nothing" baseline is reconsidered
explicitly: #677 + #679 already make `/` SURVIVABLE (the big cache is routed off,
escalation fires, no active-data delete), so $0 buys "detect + escalate + route
the big cache"; #681's $51/mo buys the remaining "**guarantee** one task cannot
exhaust `/` OR starve another" — the per-task bound #679 explicitly deferred.

**The decisive factor (unchanged from v1, still correct):** Option B's
prerequisite — converting the **root** filesystem to prjquota — **cannot be
applied to a mounted `/`** (verified: web research + on-VM `setquota: command not
found` + root fs feature flags lack `project`/`quota`; live ~151 GB #658 process
holding open files). That means a reboot into single-user, killing #658 + all
sessions, while `/` is at 97% NOW. Option A formats a FRESH disk (no live
unmount) and hot-attaches with zero downtime — AND gives the per-task quota grain
Option B would only have provided for the root fs.

### Phase 1 — Format (ext4 + prjquota) + mount (on the VM, passwordless sudo confirmed)

```bash
DEV=/dev/disk/by-id/google-eps-data-disk        # predictable; survives reattach
sudo blkid "$DEV" || echo "no filesystem (expected for a fresh disk)"

# Format ext4 WITH the project feature + prjquota (trivial on a FRESH disk —
# verified: e2fsprogs 1.46.5 supports `-O project` + `-E quotatype=prjquota`).
sudo mkfs.ext4 -m 0 -L eps-data -O project -E quotatype=prjquota "$DEV"

# Install the quota userspace (setquota -P / repquota -P / quotaon -P).
# Verified: `quota` is an installable Ubuntu pkg (candidate 4.06); kernel has
# CONFIG_QUOTA=y + CONFIG_QFMT_V2=m.
sudo apt-get update && sudo apt-get install -y quota

sudo mkdir -p /mnt/eps-data
sudo mount -o prjquota "$DEV" /mnt/eps-data
sudo chown "$USER:$USER" /mnt/eps-data
sudo quotaon -Pv /mnt/eps-data                   # turn project quotas ON

# Persist across reboot — fstab by LABEL, WITH prjquota mount opt:
echo 'LABEL=eps-data  /mnt/eps-data  ext4  defaults,prjquota,discard,nofail  0 2' \
  | sudo tee -a /etc/fstab
# `nofail` so a missing data disk never blocks VM boot.
sudo systemctl daemon-reload
findmnt /mnt/eps-data
```

`quotaon -P` is not persisted by the `prjquota` mount opt alone on all distros;
a tiny systemd unit (`eps-quotaon.service`, `After=mnt-eps\x2ddata.mount`,
`ExecStart=/usr/sbin/quotaon -Pv /mnt/eps-data`) guarantees it. The implementer
picks the simplest mechanism that passes §8's reboot test (allowed deviation).

### Phase 2 — Relocate `.claude/worktrees/` via FD-safe copy + bind (the cutover)

The bind mount is the load-bearing transparency trick: every consumer resolves
`repo_root()/.claude/worktrees/...` — a bind mount makes that SAME path serve
files physically stored on `/mnt/eps-data`, so **no consumer code changes**.

**Must-Fix #1 — #658 path continuity. We adopt ordering option (c): stage #658
onto the data disk via an FD-safe copy BEFORE the parent-dir bind swap.** This
removes the v1 window where, after the parent bind, `.claude/worktrees/issue-658`
resolved into a data-disk tree that LACKED #658 (because v1 excluded #658 from
the rsync, leaving it only in the renamed `.premigrate`). The corrected sequence
NEVER leaves the canonical path resolving into a #658-less tree.

> **Why (c) over (a)/(b):** (a) per-subdir binds leave the parent un-bound, so a
> NEW worktree created during the window lands back on `/` (defeats the goal);
> (b) a #658→.premigrate symlink works but adds a second path-resolution hop that
> a consumer's `Path.resolve()` could surprise. (c) is the cleanest: by the time
> the parent bind flips, the data-disk tree is COMPLETE (including #658), so the
> canonical path is correct at every instant.

```bash
REPO=/home/thomasjiralerspong/explore-persona-space
SRC="$REPO/.claude/worktrees"
DST=/mnt/eps-data/worktrees
mkdir -p "$DST"

# 2a. Set the migration LOCK: new_worktree.sh AND the task.py managed-worktree
#     creation path (_managed_worktree_path / _task-main-pin) both refuse while
#     it exists (see §6 freeze-audit — both are concurrent writers).
touch "$REPO/.claude/cache/worktree-migration.LOCK"

# 2b. First-pass copy of EVERYTHING INCLUDING #658 while sessions run. Long but
#     non-blocking (sessions still read/write the original tree). Copying the
#     LIVE #658 tree here is safe because rsync reads a consistent file snapshot;
#     the FD-safety constraint applies to the DELETE of the source, not the copy.
rsync -aHAX --info=progress2 "$SRC"/ "$DST"/

# 2c. Quiesce: pause spawns (LOCK is set); wait until NO non-#658 worktree has a
#     live writer (lsof). #658 may STILL be live — that is fine: we do a final
#     delta rsync of #658 too, and we NEVER delete its source from $SRC until
#     #658 is independently confirmed quiescent (deferred-tail DELETE, step 5).
rsync -aHAX --delete "$SRC"/ "$DST"/      # final delta; #658 INCLUDED in the copy

# 2d. SWAP: rename the original (rollback net), recreate the mountpoint, bind.
#     The data-disk tree now CONTAINS a complete #658, so the canonical path is
#     correct the instant the bind flips. No #658-less window.
mv "$SRC" "$SRC.premigrate"
mkdir -p "$SRC"
sudo mount --bind "$DST" "$SRC"
findmnt "$SRC"                            # assert the bind is live

# 2e. Assign per-issue ext4 project ids + caps on the data-disk tree (Phase 2.5).
```

**The live-#658 FD subtlety (kept explicit):** the rsync COPY of #658 in 2b/2c is
safe (a read). What is unsafe is DELETING #658's source files out from under its
live process. So after the bind swap, `.claude/worktrees/issue-658` resolves to
the DATA-DISK copy, while #658's live process still holds open FDs into the
INODES under `$SRC.premigrate/issue-658` (an open FD pins the inode regardless of
the directory rename). #658 therefore keeps reading/writing its original inodes
safely; new reads of the canonical path see the data-disk copy. We do NOT delete
`$SRC.premigrate/issue-658` until #658 is independently confirmed quiescent
(step 5). For #658's IN-FLIGHT writes during the gap to land on the data-disk
copy too, #658 must re-open through the canonical path — which it does at its next
phase boundary; until then its writes go to the premigrate inodes and are
reconciled by a final `rsync .premigrate/issue-658/ $DST/issue-658/` at step 5
BEFORE the premigrate delete. This is the copy→verify→delete (never delete-first)
ordering the implementer-concern note mandates.

### Phase 2.5 — Per-issue project quotas (the per-task isolation, Must-Fix #4(a))

```bash
# Helper (wired into new_worktree.sh, §4 Phase 4): for each issue-<N> worktree,
# allocate a stable project id = N (issue number IS the project id — unique,
# stable, human-legible), tag the subtree, and set a hard byte cap.
PROJID=658
CAP_KB=$((128 * 1024 * 1024))             # 128 GB hard cap (gate-tunable, §13)
sudo chattr -R -p "$PROJID" +P "$DST/issue-$PROJID"   # tag subtree to project N
sudo setquota -P "$PROJID" 0 "$CAP_KB" 0 0 /mnt/eps-data   # soft=0 (=off), hard=cap
sudo repquota -Ps /mnt/eps-data | grep " #$PROJID "   # verify the cap is set
```

The `_task-main-pin` managed worktree + any non-issue auto worktree get project
id 0 (the default, unbounded) — they are tiny (KB-scale task state), so they need
no cap; the cap exists for the heavy `issue-<N>/data/...` trees.

## §6 Compatibility / migration plan

**What a currently-running session sees:** nothing changes for any session whose
worktree is NOT being copied at that instant. The bind mount is path-faithful —
after cutover, `ls .claude/worktrees/issue-<N>` returns the same files at the same
path; only the backing device changed. There are **39 worktrees** and ~28 active
sessions.

**The hard constraint: the live ~151 GB `.claude/worktrees/issue-658` process.**
It holds open files. **v1's mistake (Must-Fix #1):** v1 EXCLUDED #658 from the
cutover copy, then renamed the parent to `.premigrate` and bound the (#658-less)
data-disk tree — so the canonical path `.claude/worktrees/issue-658` resolved
into a tree LACKING #658 for the entire deferred window. **v2 fixes this by
copying #658 FIRST (ordering option (c)):** the data-disk tree CONTAINS a complete
#658 before the parent bind flips, so the canonical path is correct at every
instant (invariant #4 + #6 both hold).

**Cutover sequence (no reboot, ~10-min freeze window):**

1. **Announce + pause new spawns.** Set `.claude/cache/worktree-migration.LOCK`.
   BOTH concurrent worktree-creation paths refuse on it: `new_worktree.sh` AND
   `task_workflow._ensure_managed_main_pin_worktree` (the `_task-main-pin` path,
   §4 Phase 4). Existing sessions keep running.
2. **First-pass copy INCLUDING #658** (Phase 2b) while sessions run — copies the
   bulk (everything, #658 included) to `/mnt/eps-data/worktrees`. Long but
   non-blocking (sessions still read/write the original tree). The COPY of live
   #658 is a consistent read; the FD-safety constraint is on the source DELETE
   (deferred to step 5), not the copy.
3. **Quiesce the non-#658 worktrees:** wait until the worktrees being relied on
   have no live writer (idle-session signals + `lsof`). Gate-parked sessions
   (`awaiting_promotion`, `plan_pending`) are quiescent by definition. #658 may
   still be live — that is fine.
4. **Final delta copy + swap** (Phase 2c/2d): fast (only changes since step 2,
   #658 INCLUDED), then `mv .claude/worktrees .claude/worktrees.premigrate`,
   recreate the empty dir, `mount --bind`. **The data-disk tree already contains
   a complete #658, so the canonical path is correct the instant the bind flips —
   no #658-less window.** The `.premigrate` copy is the rollback net.
5. **#658 deferred-tail DELETE (copy→verify→delete, NEVER delete-first):** #658's
   live process keeps reading/writing its ORIGINAL inodes under
   `.premigrate/issue-658` (open FDs pin inodes across the rename) until it
   re-opens through the canonical path at its next phase boundary. Once #658
   reaches a quiescent point (a phase boundary / `awaiting_promotion` / the user
   confirms it is safe): (a) final `rsync .premigrate/issue-658/
   $DST/issue-658/` to reconcile any in-flight premigrate writes, (b) VERIFY
   (checksum / `rsync --dry-run` shows no diff), (c) THEN delete
   `.premigrate/issue-658`, (d) assign #658's project id + cap (Phase 2.5).
   **If #658 never quiesces before `/` is critical, reclaim its re-downloadable
   cache** (the `hf_dl`/`store` cache, re-downloadable per #679) with the existing
   safe reclaim — freeing `/` without moving the live tree.
6. **Assign project ids + caps** to all migrated `issue-<N>` subtrees (Phase 2.5).
7. **Lift the LOCK.** New worktrees now land on the data disk, quota-tagged at
   birth.

**No-downtime alternative if a drain window is unacceptable:** per-subdir binds of
only the quiescent worktrees, leaving busy ones on the boot disk — but this leaves
the PARENT un-bound, so a NEW worktree lands back on `/`; it is strictly inferior
to the copy-#658-first approach and is NOT recommended. (v1's prose described this
alternative as the #658 fix; v2 supersedes that — the fix is copy-first ordering,
not subdir binds. This reconciles the §6 prose with invariants #4/#6.)

**Rollback:** `quotaoff -P`, `umount` the binds, `mv .claude/worktrees.premigrate
.claude/worktrees`, remove the fstab lines. `.premigrate` trees are kept until
§1's acceptance criteria all pass (including the #658-tail verify), then deleted.

## §11 Decision Rationale (load-bearing fields + sources)

- **Mechanism = Option A (dedicated PD + bind + prjquota on the FRESH disk), NOT
  Option B (prjquota on root).** *Why:* enabling prjquota on the **root** ext4 fs
  requires unmounting `/` (reboot/single-user), which kills the live #658 process
  + all sessions — infeasible while `/` is at 97% and #658 is live; the FRESH disk
  takes `mkfs.ext4 -O project` trivially. *Source:* Red Hat ext4-quota docs +
  web research ("for root filesystem... requires special boot procedures to
  unmount before modification"); verified on-VM (`quota` pkg not installed, root
  fs lacks `project`/`quota` feature flags, live #658 = 151 GB holding open
  files); `mkfs.ext4 -O project -E quotatype=prjquota` support verified in
  `e2fsprogs 1.46.5` (man page + `--version`).
- **Per-task isolation = ext4 prjquota, one project id per issue, hard byte cap.**
  *Why:* per-DEVICE relocation alone (v1) still lets one task fill the shared data
  disk and starve others — the #679-deferred guarantee is per-TASK, which only a
  per-tenant quota delivers; on a FRESH disk this is trivial (no live unmount).
  *Source:* parent #679's explicit deferral of "bounded by construction" to this
  task; Linux ext4 project-quota semantics (`chattr +P -p` + `setquota -P`,
  kernel `CONFIG_QUOTA=y`/`CONFIG_QFMT_V2=m` verified); the RunPod MooseFS
  per-pod EDQUOT quota is the project's existing fail-loud-on-cap precedent
  (`.claude/rules/gotchas.md` "RunPod MooseFS per-pod disk quota").
- **Disk size = 512 GB (recommended) / 256 GB (cost-minimal) / NOT 1 TB.** *Why:*
  the on-VM RESIDUAL after #677 routes the 139 GB cache class off-VM is ~114 GB
  (253 − 139), so 512 GB = ~4.5× residual headroom at half v1's cost; per-task
  prjquota decouples disk SIZE from per-task starvation, so a smaller disk is no
  longer a per-tenant risk. *Source:* measured footprint (`du -sh` 2026-06-27:
  worktrees 253 GB, #658 family ~180 GB); #677 (COMPLETED) `cpu-bigmem` off-VM
  routing of the >50 GB CPU-phase cache class + the `VM_ANALYSIS_FOOTPRINT_GB_MAX
  = 50` rule; GCP PD grow-live-only constraint
  ([cloud.google.com/compute/docs/disks](https://cloud.google.com/compute/docs/disks/persistent-disks)).
- **Disk type = `pd-balanced`.** *Why:* cache/checkout I/O, not latency-sensitive;
  matches the boot disk class; 1.7× cheaper than pd-ssd. *Source:* GCP pricing
  (us-central1 pd-balanced $0.10/GB-mo vs pd-ssd $0.17/GB-mo); boot disk is
  pd-balanced (verified).
- **Default per-issue cap = 128 GB (gate-tunable).** *Why:* ≈ the largest
  historical single-issue footprint (#658 family ~180 GB is an OUTLIER inflated by
  the un-routed cache #677 now handles; a typical large issue is < 128 GB);
  generous enough to never block a legitimate run, small enough that 3-4 fit on
  512 GB. *Source:* measured per-issue footprints (`du -sh
  .claude/worktrees/issue-*`); gate-tunable via `EPS_ISSUE_DISK_CAP_GB` so a
  wrong default is a one-line fix, not a redesign. `ungrounded — needs
  post-cutover tuning` on the EXACT value (flagged §12); the MECHANISM is
  grounded, the precise number is a tuning call surfaced at the gate.
- **Data-disk thresholds = PERCENT / statvfs-derived, NOT mirrored absolute byte
  floors.** *Why:* the `/`-tuned byte floors (`VM_DISK_ALERT_FREE_BYTES=20 GiB`
  etc.) sit at fixed BYTES calibrated to 485 GB; mirrored onto a 512 GB+ disk they
  fire at the wrong fullness and would silently regress on a future resize.
  Percent is size-invariant and matches §1's 85-95% criteria + the already-percent
  `vm_disk_guard` (`threshold_pct()` default 85%). *Source:* read
  `vm_disk_guard.py` (`disk_used_pct` + `threshold_pct`, percent-based, immune)
  and `autonomous_session_watch.py` (`VM_DISK_*` absolute byte floors, the surface
  to fix — Must-Fix #2); the constants verified at lines 1230/1256/1397 +
  `_ACTIVE_ESCALATION_BANDS_GB` (`vm_disk_guard.py:64`).
- **Data-disk guard pass = escalate-ONLY (no reclaim tiers).** *Why:* the `/`
  reclaim tiers (`uv cache prune`, stale-log sweep) operate on `/`-rooted caches;
  running them keyed off the data disk would reclaim the wrong fs. *Source:*
  `vm_disk_guard.run_guard` tier helpers (read); the active-cache-escalation +
  terminal-cache-reap arm is the only data-disk-appropriate remediation.
- **Mount transparency = `mount --bind` (symlink K2 fallback).** *Source:* every
  disk consumer resolves `.claude/worktrees` via `repo_root()` / `git
  --git-common-dir` (grepped: `clean_experiment_downloads.py`, `vm_disk_guard.py`,
  `worktree_audit.py`, `new_worktree.sh`, `task_workflow.py` incl. the
  `_task-main-pin` path).
- **Escalation channel = existing sidecar + Telegram, never per-run `task.py`
  commits.** *Source:* #679 invariant (carried forward; CLAUDE.md index.lock-churn
  rule).
