## Approved Plan for #1991: workflow-fix — widen the blanket-add latch to equivalent-blanket spellings

**Cost gate:** estimated **0** GPU-hours (workflow-surface code + tests only). Reply `approve` to dispatch.
`gpu_hours_total=0`

### Goal

Extend the blanket-add latch in `guard_root_code_commit.sh` (and its B13 test parametrization) so that equivalent-blanket token spellings — `./`, `.//`, `:/` (pathspec-magic top-of-tree), and quoted-star `*` / `**` (glob tokens that survive shell expansion) — trigger the SAME `a_saw_blanket=1` recognition as the current `-A | --all | .` set. Gated content chained to a root commit through any of these spellings must fail CLOSED, matching the guard's stated intent (CLAUDE.md § Concurrent repo-root committers — the blanket-staging ban).

### Requirement (code)

Currently `.claude/hooks/guard_root_code_commit.sh:887` enumerates exactly 3 blanket tokens (`-A`, `--all`, `.`). Git accepts several EQUIVALENT-blanket spellings that reach the same "stage everything" behavior:

- `./` — trailing-slash normalization of `.`
- `.//` — double-slash normalization
- `:/` — pathspec magic prefix meaning "top of working tree"
- `*` / `**` — glob tokens that survive shell escaping (`\*`, `'*'` normalized), matching any path from git's pathspec-matcher

Any of these chained to a root commit currently bypasses `a_saw_blanket` and leaves `add_all_chained` unset, opening a channel for gated content to land uncertified. The fix WIDENs the recognition arm at L887 to the same equivalent-blanket class the POST-`--` candidate-rejection arm at L910 already treats as blanket-equivalent (which lists `. | .. | ./* | \*`), symmetrizing the two arms.

Requirement:
1. The recognition arm at `.claude/hooks/guard_root_code_commit.sh:887` matches the widened set as a bare token anywhere in the ADD clause.
2. The pre-`--` allowlist at `.claude/hooks/guard_root_code_commit.sh:921` is UNCHANGED — it stays `{-A, --all}`. New tokens as pre-`--` positionals hit the catch-all `*) a_eligible=0` and, combined with the widened `a_saw_blanket=1`, latch `add_all_chained=1`.
3. The path-limited sanctioned shape (#1977) — `git add --all -- <explicit pathspec>` — must continue to EXEMPT: the post-`--` allowlist and candidate-rejection arm at L910 are UNCHANGED.
4. `test_b13_blanket_add_chained_fails_closed` parametrization is EXTENDED to cover each new spelling as a distinct id.

### Design

Step 1 — Extend the recognition arm at L887:

- Before: `case "$tok" in -A | --all | .) a_saw_blanket=1 ;; esac`
- After: `case "$tok" in -A | --all | . | ./ | .// | :/ | \* | \*\*) a_saw_blanket=1 ;; esac`

The `\*` and `\*\*` patterns are shell-case-pattern escapes matching a LITERAL `*` and `**` respectively (the guard's `$masked` scan already normalizes quoted content to fill).

Step 2 — Add a one-line rationale comment above L887 pointing at issue #1991 and stating why the widened set matches L910's post-`--` rejection class (symmetry rationale).

Step 3 — Extend B13 parametrization at `tests/test_guard_root_code_commit.py:439-443` with ids:
- existing: `dash-A` (`git add -A`), `dot` (`git add .`), `all` (`git add --all`)
- add: `dotslash` (`git add ./`), `dotslash-double` (`git add .//`), `pathspec-root` (`git add :/`), `star` (`git add \\*`), `star-double` (`git add \\*\\*`)

The `\\*` shell-escape ensures the star reaches git as a literal pathspec (bypassing shell expansion) — matching the semantics the guard sees.

Step 4 — Verify #1977's exempt path (`test_add_pathlimited_artifact_pathspec_allowed` etc.) still PASSes: the widened recognition set fires on `-A | --all | .` as before; the sanctioned `git add --all -- <pathspec>` shape still hits `a_saw_blanket=1` via `--all`, then the post-`--` allowlist + clean candidates set `add_pathspecs`, exempting.

### Critic rebuttal (adversarial-planner)

Key challenges the plan anticipates:

1. **"Is `..` missing from the widened set?"** Deliberately excluded: `..` from repo root refers to the parent directory (outside the repo); git may refuse it, and if it's from a subdir cwd it stages the parent, which is not "top of tree" blanket. The pre-`--` catch-all at L921 sets `a_eligible=0` for `..`; the LACK of `a_saw_blanket=1` there means no latch, but Layer-2 classification of what actually got staged still runs. This is a defensive choice — the body proposal listed conservative treatment; adding `..` would broaden beyond what the body scoped and could interact with subdir cwd handling.
2. **"Does `\* | \*\*` correctly match a literal star in the guard's `masked` stream?"** Yes — the `case` shell-glob patterns `\*` and `\*\*` match literal `*` and `**` respectively; the guard's masking preserves those literals for unquoted-or-shell-escaped tokens. Quoted `'*'` becomes `$FILL`-filled and is rejected by the mask check anyway.
3. **"Won't this widen block accidentally match a legitimate specific-file pathspec?"** No — the recognition arm matches BARE tokens (`case "$tok" in ...`), not glob-BEARING pathspecs like `scripts/*.py`. A specific-file token like `scripts/foo.py` never matches any of `-A | --all | . | ./ | .// | :/ | \* | \*\*`.
