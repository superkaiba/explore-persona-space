def resolve_chunk_cap(
    requested: int, n_members: int, n: int, d_in: int, free_bytes: int,
    *, live_factor: int = 26, safety: float = 0.8,
) -> int:
```

Semantics (docstring, lines 93-116): cap = `max(1, min(requested, n_members, floor(free_bytes × safety / (live_factor × n × d_in × 4))))`; pure function; `free_bytes <= 0` (unreadable probe) leaves `requested` unchanged so a probe failure never silently tightens; returns ≥ 1 so a genuinely too-large problem OOMs loudly rather than no-ops. Calibration: at n=480, d_in=3584, p=64, c=64 the measured `ru_maxrss` delta was **~10.7 GiB ≈ 25.5×** the **420 MiB** single `(c, n, d_in)` fp32 tensor (#811 phase0 gate, CPU-side measurement) → `live_factor=26`. The naive explicit-temporary count (**≈4**: the advanced-index design copy `Xc`, the element-square temp, the standardized `Xn`) under-estimates **~6×** (26/4 = 6.5) because the `torch.bmm` autograd backward graph, AdamW moment buffers, and allocator high-water retention dominate — the factor-4 cap picked **c=218**, whose real peak was **~36 GiB** (218/64 × 420 MiB × 26) → re-OOM on the very shape the cap existed to protect. Call site (lines 467-479): probe `_free_bytes(dev)` ONCE (`torch.cuda.mem_get_info` on cuda / `SC_AVPHYS_PAGES × SC_PAGE_SIZE` on cpu), then on cap: `logger.info("[vectorized_mlp] chunk capped %d -> %d (n=%d d_in=%d free=%.2f GiB) to bound per-chunk (c, n, d_in) fp32 footprint", ...)` — the fix-engaged signal. Chunk-size invariance (result unchanged by `c`) is pinned by a test per the fn docstring at line 400-405.

- **Memory caps for torch fit loops: calibrate the live-tensor factor from a
  MEASURED real-shape peak — counting the code's explicit temporaries
  under-estimates the true per-chunk peak ~6×.** A memory-aware chunk cap of the
  form `floor(free_bytes × safety / (live_factor × unit_bytes))` is only as good
  as its `live_factor`. Counting the named intermediates in the code (the design
  copy, the element-square temp, the standardized copy → "≈4 live tensors")
  misses what actually dominates a training-loop chunk: the autograd BACKWARD
  graph over the chunk's activations, the AdamW moment buffers, and the
  allocator's high-water cached-block retention — none of which appear as
  variables. RULE: calibrate `live_factor` from a MEASURED peak at the REAL
  shape — run ONE chunk at production `(n, d_in)` and read the `ru_maxrss` delta
  (CPU) / `torch.cuda.mem_get_info` delta (GPU); set the factor to
  `ceil(measured_peak / single_unit_bytes)`. Over-estimate freely: chunking does
  not change the fit (pin that with a chunk-size-invariance test), so a larger
  factor only adds chunk COUNT at constant total FLOPs, while an optimistic
  factor re-OOMs the very shape the cap exists to protect. ALSO log the resolved
  cap + the probed free bytes AT THE CAP SITE (e.g. `[vectorized_mlp] chunk
  capped 4096 -> 64 (n=480 d_in=3584 free=13.9 GiB)`) — that line is the
  fix-engaged signal that makes the next OOM diagnosable from the log alone,
  and a `free_bytes` probe failure must fall back to the REQUESTED chunk (never
  silently tighten). Canonical implementation: `resolve_chunk_cap()` in
  `src/explore_persona_space/analysis/vectorized_mlp_skill.py` (`live_factor=26`,
  calibrated from a measured ~10.7 GiB ru_maxrss delta ≈ 25.5× the 420 MiB
  single `(c=64, n=480, d_in=3584)` fp32 tensor; built on the `issue-811`
  branch, on `main` once #811's worktree auto-merges). (Incident #811 crash-fix
  round 8, 2026-07-01: the prior `live_factor=4` — the explicit-temporary count
  — picked c=218, whose real ~36 GiB peak re-OOM'd the #811 phase-0 gate at the
  exact shape the cap was added to protect; the recalibrated factor-26 cap
  survived the same production shape.)
```

## Memory sizing: calibrate the chunk cap from a MEASURED peak

Vectorizing trades many tiny fits for a few LARGE batched tensors, so the
batched path needs a memory-aware chunk cap — and the cap's live-tensor
factor must come from a MEASURED real-shape peak, never from counting the
code's explicit temporaries. The named intermediates undercount the true
per-chunk peak ~6×: the autograd backward graph, AdamW moment buffers, and
allocator high-water retention dominate (#811 r8: a factor-4 explicit-
temporary count picked c=218, whose real ~36 GiB peak re-OOM'd the exact
shape the cap protected — n=480, d_in=3584). Canonical implementation:
`resolve_chunk_cap()` in the helper above (`live_factor=26`, measured:
~10.7 GiB ru_maxrss delta on one c=64 chunk ≈ 25.5× the single
`(c, n, d_in)` fp32 tensor; built on the `issue-811` branch, on `main` once
#811's worktree auto-merges). Recipe: run ONE chunk at the production shape,
read the ru_maxrss / `torch.cuda.mem_get_info` delta, set the factor from
that; over-estimate freely (a larger factor only adds chunk count at constant
FLOPs — chunk size must not change results, pinned by a chunk-size-invariance
test); and LOG the resolved cap + the probed free bytes at the cap site so
the next OOM is diagnosable from the log alone. Full trap-and-fix entry:
`.claude/rules/gotchas.md` § "Memory caps for torch fit loops".
