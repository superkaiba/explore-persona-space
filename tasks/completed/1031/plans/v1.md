- **What I'll change:** I'll add a seventh sizing recipe to the planner's compute-sizing rule file — every CPU phase placed on the shared VM must state its projected peak memory, and anything at or above ~16 GB (alone or summed with concurrent phases) gets routed to a dedicated CPU machine instead — and I'll amend the existing GCP-fence recipe so the auto-delete fence is sized off the p90 per-cell time estimate, not the mean. ### 11. Decision Rationale

- **~16 GB RSS routing threshold.** What: the single-or-summed projected-RSS bar above which a CPU phase leaves the shared VM. Why: three independent anchors converge on 16: (i) `Source: #1010` — the project's existing plan-time RAM-declaration convention is `--min-ram-gb` "whenever it sizes RAM > 16 GB" (CLAUDE.md § Pods; `compute-backend-failover.md` lines 554-556), so the routing bar and the flag-arming bar coincide (one number to remember, no gap where a phase must route but needn't declare); (ii) `Source: RUNPOD_CPU_INSTANCE_CAPS` — the cpu-mid RunPod fallback (`cpu3c-8-16`) has exactly 16 GB, so ≥16 GB is precisely where a flag-less cheap-lane launch becomes unsafe; (iii) `Source: incidents #778/#833` — earlyoom arithmetic: ~125 GB total, SIGTERM floor ~12.8 GB MemAvailable, observed fleet baseline ~95 GB resident (#778) leaves ~30 GB headroom; one 16 GB phase eats >half of it and two cross the kill floor, matching #833's two-×-13-15-GB deaths. Alternatives: 8 GB (over-routes routine plotting/aggregation), 32 GB (would have KEPT #778's 22-GiB battery on the VM — the exact incident this rule exists for).
- **Summed-concurrent formulation (refining the Goal's ">2 concurrent").** What: concurrency triggers on summed projected RSS crossing ~16 GB, not on a count >2. Why: `Source: #833` — exactly TWO ~13-15 GB phases died; a literal ">2" gate would not have fired. Alternatives: the literal count gate (fails the motivating incident); a per-phase-only gate (ignores stacking entirely).
- **p90 (not mean, not max/p99) fence basis, default dispersion ×2.** What: worst-case wall for fence reconciliation uses the p90 per-cell estimate; when only a mean exists, p90 ≈ mean × 2 (stated). Why mean fails: `Source: #833` — realized per-cell wall ran ~2× plan mean and the 36h fence hard-deleted the instance mid-run (same family as #599's 24h-fence kill). Why not max/p99: the fence is also the janitor's reap bound (`backends/gcp.py`: reap at own `--max-run-duration` + 1h grace) — an over-long fence delays the credit-leak backstop on a wedged instance (#741's rationale for fence-aware reaping), and p99/max of a small-n per-cell sample is noise; p90 × ≥1.25 margin balances kill-healthy-runs against delay-the-janitor. The ×2 default is grounded on the one measured project datapoint (#833's ~2×) and is a stated-default, not a pin — a prior-issue distribution wins when it exists. Alternatives: always-7d fence (maximally janitor-delaying; also the FLEX_START ceiling makes it not always available to lengthen); mean × fixed-margin (re-derives #833 with a slightly bigger constant, no dispersion awareness).
- **New block in the rule file + one-line pointers (not inlined into planner.md).** `Source: #829/#910` — the established relocation pattern; planner.md §9 stays a trigger-summary, the rule file loads path-based at plan time (`paths: .claude/plans/**`, `tasks/**/plans/**`), so both planners and plan-reviewing critics get it with a plan file open.
- **No CLAUDE.md edit.** `Source:` CLAUDE.md § Pods already carries the #1010 ADOPTION sentence anticipating plan-§9 RAM sizing; adding a second copy would create a sync liability (state-facts-once). The rule cross-references it instead.
