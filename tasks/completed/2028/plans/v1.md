## 1. Goal / requirement

No dispatch path — auto chain, explicit `backend:` frontmatter pin, `--backend gcp` CLI,
or a failover/retry leg — may CREATE any new GCP instance (GPU or CPU). CPU intents route
RunPod-only, with `cpu-bigmem` gaining a RunPod Memory-Optimized mapping. Cleanup paths
that only ACT ON existing GCP handles (poll, crash-persist, teardown, GCP→RunPod failover
of an in-flight handle, the `gcp_audit.py` janitor) are explicitly IN-SCOPE-TO-KEEP.

**Acceptance criteria:**
1. The default auto lane order contains no `gcp` rung: `DEFAULT_AUTO_LANE_ORDER ==
   ("fellows", "nibi", "fir", "mila")`.
2. `EPM_AUTO_LANE_ORDER` / `RouterConfig.lane_order` containing `gcp` raises loudly at
   validation (the `runpod` precedent), while the policy flag is on.
3. `route()` with `spec.backend == "gcp"` raises a typed `GcpDisabledError(RouteError)`
   naming the policy + task #2028, BEFORE any wiring/ladder work; `classify_terminal_exception`
   maps it to `failure_class: infra`, `status: blocked`, reason token `gcp_backend_disabled`
   (NOT in the watcher's `TRANSIENT_CAPACITY_REASONS` — not auto-re-drivable; the fix is a
   human changing the pin).
4. `RUNPOD_CPU_INSTANCE_FOR_INTENT` gains `"cpu-bigmem": "cpu5m-16-128"`;
   `RUNPOD_CPU_INSTANCE_CAPS` gains a matching row (vcpu=16, ram_gb=128,
   max_container_disk_gb=240 — cpuFlavors `diskLimitPerVcpu` 15 GB/vCPU × 16, live-verified
   at filing 2026-08-02; provenance recorded in the docstring per the #1010 convention).
5. A `cpu-bigmem` dispatch resolves to the RunPod CPU lane (no GCP rung, no
   `cpu_exhausted_no_runpod_lane` raise). The `CpuExhaustedNoRunpodLaneError` guard at
   `_runpod_terminal_rung` STAYS as a fail-loud floor for a future unmapped CPU intent —
   it retires naturally (no current intent triggers it), it is not deleted.
6. The #1596/#1601 GCP on-demand retry legs (`retry_gcp_ondemand_after_queue_vanish`,
   router.py:3719; callers in `scripts/backend_poll.py` ~4521-4562) do NOT create new GCP
   instances while the flag is on: gate them to skip straight to the existing RunPod
   failover continuation. All other poller GCP paths (crash persist, teardown,
   `_failover_dead_gcp_to_runpod`, `_maybe_escalate_gcp_queue_timeout`'s cancel leg) stay —
   they act on existing handles.
7. Rollback is a single-constant flip (`GCP_PROVISIONING_DISABLED = False`), not code
   archaeology: the GCP ladder / lane code is GATED, never excised.
8. Tests updated + new pins added (see §5); the Step 9c touched-scope gate passes with no
   NEW failures vs the main baseline.
9. Prescriptive docs updated (see §6); historical incident references left intact.

## 2. Method delta

The fellows `available=False` precedent gates a SLURM lane row; GCP is not a
CLUSTER_CONFIGS row, so the equivalent lever is a router-module policy constant:

```python
#: #2028 (user directive 2026-08-02): GCP may not provision ANY new instance.
#: Rollback = flip to False (all gated code paths reactivate; DEFAULT_AUTO_LANE_ORDER
#: rebuilds with the gcp rung on next import).
GCP_PROVISIONING_DISABLED: bool = True

def gcp_provisioning_disabled() -> bool:
    """Dynamic read so tests can monkeypatch the module attribute."""
    return GCP_PROVISIONING_DISABLED
```

All runtime checks call the helper (monkeypatch-able); `DEFAULT_AUTO_LANE_ORDER` is built
from the constant at import time (tests pin the resulting tuple as-is). Deliberately NO
env override to re-enable (an env var would let a stale shell resurrect a policy the user
removed; the constant flip is the sanctioned lever).
