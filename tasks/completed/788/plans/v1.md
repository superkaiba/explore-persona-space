# Plan — issue #788 (`kind: infra`, 0 GPU-h)

**Title:** daily-fix: reviewer sandbox read-only tempdir silently skips pytest

## §1 Goal (verbatim from task body)

> Document + set a writable-tempdir fallback for reviewers/test-verdict in the
> sandbox (TMPDIR/UV_CACHE_DIR/XDG_CACHE_HOME -> a worktree-local writable dir
> before `uv run pytest`), and require the reviewer to flag 'tests NOT actually
> run' loudly rather than treating a code-only review as a PASS.

## §2 Prior work / gap (what's actually in the file)

- `.claude/agents/code-reviewer.md` Step 4 (lines 575-584) currently reads:

  ```
  ### Step 4: Run / Verify Tests

  If you can run tests, do so:
  ```bash
  uv run pytest tests/relevant_test.py -v
  uv run ruff check path/to/changed/files
  uv run ruff format --check path/to/changed/files
  ```

  Don't trust "tests pass" claims — verify. If you can't run (subagent sandbox
  limitations), at least read the tests and trace that they exercise the new code path.
  ```

- **The defect:** the last sentence EXPLICITLY PERMITS "at least read the tests
  and trace" as a full substitute for running them, with (a) no attempt at a
  writable-tempdir fallback first, (b) no requirement to flag the skip loudly in
  the verdict, and (c) no verdict downgrade. Result (issues 761/753/739,
  2026-06-30): the sandbox has a read-only `~/.cache/uv` and a non-writable
  `tempfile.gettempdir()` (torch→dill wants to write there), so `uv run pytest`
  cannot create temp/cache files, the reviewer falls to "reviewed the code path
  directly instead", and a code-only review is reported as PASS — invisibly to
  the orchestrator/user.

- **Verdict template already has the right slots** (Step 7, lines 661-713):
  a `**Tests:** PASS / FAIL / INSUFFICIENT` header line (669) and a `## Tests`
  section (703-706). The new loud flag belongs as a header line directly under
  `**Tests:**` and a one-line note in `## Tests` — it plugs into the existing
  structure, no new section needed.

## §3 Design — exact edits to `.claude/agents/code-reviewer.md`

Two edits, both in the same file. No other file changes (see §4 Scope).

### Edit A — replace Step 4 body (lines 575-584)

**Replace the entire Step 4 block** (from `### Step 4: Run / Verify Tests`
through the `Don't trust ... new code path.` sentence) with:

```markdown
### Step 4: Run / Verify Tests

Run the tests. Don't trust "tests pass" claims — verify.

```bash
uv run pytest tests/relevant_test.py -v
uv run ruff check path/to/changed/files
uv run ruff format --check path/to/changed/files
```

**If `uv run pytest` fails with a read-only-sandbox / cache / tempdir error**
(e.g. `Read-only file system`, `Permission denied` on `~/.cache/uv`, or a
`tempfile` / dill write failure under `torch` import) — this is a SANDBOX
limitation, NOT a test failure. Try the writable-tempdir fallback FIRST, before
falling back to reading the tests:

```bash
# $WT = the worktree root you are reviewing in (pwd if you're already in it).
RTMP="$(pwd)/.claude/cache/reviewer-tmp-$$"
mkdir -p "$RTMP"
TMPDIR="$RTMP" UV_CACHE_DIR="$RTMP/uv" XDG_CACHE_HOME="$RTMP/xdg" \
  uv run pytest tests/relevant_test.py -v
```

Re-run ruff the same way if it also hit a cache-write error. If the
writable-tempdir retry SUCCEEDS, the tests genuinely ran — report their real
result.

**Only if the writable-tempdir retry ALSO fails** may you fall through to
reading the tests and tracing that they exercise the new code path. A
read-only trace is NOT a substitute for a passing run: it does not catch a
test that fails, and it MUST be flagged loudly in the verdict (see below) — a
code-only review is NEVER silently reported as a clean `**Tests:** PASS`.

**In every verdict, carry the loud flag** (Step 7):
`**Tests actually run:** yes | no (sandbox blocked)`. When `no (sandbox
blocked)`, the `**Tests:**` line MUST be `INSUFFICIENT` (never `PASS`), the
`## Tests` section MUST state which tests you could only READ + why the run was
blocked (paste the sandbox error), and the recommendation MUST NOT be a clean
`merge` on the strength of tests — it is at best `revise-then-merge (tests not
run — re-run in a writable env)`.
```

## §6 Risks + mitigations

1. **The fallback dir is ALSO not writable** (the sandbox read-only-mounts the
   whole worktree, or `.claude/cache/` specifically). *Mitigation:* the
   instruction already routes to the loud-flag path when the retry fails —
   `$(pwd)/.claude/cache/reviewer-tmp-$$` is the best-effort target, and a
   second failure lands in the exact "flag `no (sandbox blocked)` + INSUFFICIENT"
   branch. The worktree root is normally writable (the reviewer's own scratch
   lives there); if it is not, the flag makes the skip visible rather than
   silent — which is the whole point. No worse than status quo, strictly better.

2. **The loud flag is emitted but the orchestrator doesn't parse it**, so a
   `no (sandbox blocked)` review still auto-advances. *Mitigation:* the design
   couples the flag to the EXISTING `**Tests:**` line — forcing it to
   `INSUFFICIENT` (never `PASS`) on a blocked run. The orchestrator/critic
   already reads `**Tests:**`; an `INSUFFICIENT` there is the machine-visible
   signal even if the new `**Tests actually run:**` line is not yet parsed. The
   new line is the human-legible loud flag; the `INSUFFICIENT` coupling is the
   machine backstop. (Wiring an orchestrator parse of the new line is out of
   scope for this minimal edit — noted as a follow-up concern below.)

3. **Over-triggering the fallback:** a genuine test FAILURE gets misread as a
   sandbox error and papered over by the retry. *Mitigation:* the instruction
   scopes the fallback to specific error signatures (`Read-only file system`,
   `Permission denied` on `~/.cache/uv`, tempfile/dill write failure) — a normal
   assertion failure or collection error does NOT match these and is reported as
   a real test failure. The retry only changes WHERE temp/cache files go; it
   cannot turn a truly failing test green.
