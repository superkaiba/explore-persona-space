## Requirement + acceptance criteria

`scripts/poll_pipeline.py` resolves the issue's `epm:run-launched` marker by ISSUE
only (three helpers), so on a multi-pod single-issue run every leg that is not the
most recent launcher (a) trips the #1156 pid-file staleness WARN on every tick
(false positive) and (b) has its `marker_pid_identity` cross-check resolve against
the SIBLING pod's `pid=` (reads `unknown` — the #813 stale-pid safety check is a
no-op for that leg). Measured on #2223 (2026-08-13, poll tick 2 of the 7B leg).

Requirement: when the poller knows its pod (`--pod`), each marker read prefers the
newest `epm:run-launched` whose note ATTRIBUTES to that pod, with issue-wide
fallback when no attributable marker exists. The #1156 staleness check itself
stays WARN-only. NOTE (owned, in-Goal): the change is NOT blanket
verdict-neutral — `_marker_launch_fields`'s outputs feed the verdict-bearing
OR-probe `pid_alive = pidfile_pid_alive or marker_pid_alive or sig_proc_rescue`
(`poll_pipeline.py:5583`) and the #1650 signature-rescue tokens, and
`run_age_sec` feeds `_tripwire_run_scope`, the adaptive-interval relaunch clamp,
and the phase-ETA fallback. On a multi-pod issue those consumers now read the
LEG'S OWN marker instead of the sibling's — exactly the #813 per-leg restoration
the Goal asks for (today a dead older leg can be false-rescued via the sibling
marker's pid, and a sibling's launch re-arms the older leg's tripwire/idle
clocks). Single-pod issues are unaffected (fallback path is today's read).

Acceptance (verbatim from the task body):
1. Fixture with two `epm:run-launched` markers on one issue naming different pods:
   polling the OLDER pod compares against ITS OWN marker — no staleness WARN — and
   `marker_pid_identity` resolves against that pod's `pid=` (`match`, not `unknown`).
2. A genuinely stale pid file on the older leg STILL trips the WARN (load-bearing).
3. Single-pod issues and pre-#1961 notes with no pod attribution behave exactly as
   today (issue-wide fallback).
4. `tests/` pins both the pod-scoped resolution and the fallback.

## Method delta (what differs from prior related work)

#1961 solved the same attribution problem for the WATCHER
(`scripts/autonomous_session_watch.py::_latest_named_run_launched_ts`, ~:13005)
with a structured-position predicate: boundary-safe `pod=<name>` token anywhere
in the note, OR the note's LEADING token being the pod name —
`re.compile(rf"(?<![\w-])pod={esc}(?![\w-])|^\s*{esc}(?![\w-])")`. This plan ports
those EXACT semantics to the poller's marker reads (a filter, not a redesign). Both
attested note shapes from #1768 (`pod=pod-1768` token; leading `pod-1768-lt (4 GPU)
provisioned ...`) are covered; mid-prose mentions must NOT match (attested
counterexample: #1768 v14's "pod-1768-tx ... was already TERMINATED").

SELECTION CONVENTION (differs from the watcher, matches the poller's own
today-behavior): today's helpers resolve via `latest_event(issue, prefix=...)` =
LAST matching event in APPEND ORDER with a `startswith` prefix filter
(`task_workflow.py:5328`), not max-ts. To keep acceptance 3 literally true, the
new resolver selects LAST-IN-APPEND-ORDER among matching events on BOTH paths
(pod-scoped and fallback) — equivalent to the watcher's max-ts under normal
ts-ordered appends, and preserving today's degenerate-corner behavior
(ts-less/out-of-order rows: `_run_launched_age_sec` still returns None on an
unparseable newest-selected ts rather than silently skipping to an older marker).

## Design — file paths + concrete diffs

### 1. `scripts/poll_pipeline.py`

a. **New module-level helpers** (near `_marker_pid`, ~:965):
   - `_pod_attribution_re(pod: str) -> re.Pattern[str]` — the #1961 regex verbatim
     (docstring cites `autonomous_session_watch._latest_named_run_launched_ts` as
     the semantics source; a drift between the two is a bug in whichever diverged).
   - `_latest_run_launched_event(issue: int, pod: str | None) -> dict | None` —
     reads `epm:run-launched` events via
     `explore_persona_space.task_workflow.list_events` (already imported at
     `poll_pipeline.py:411`), filters by kind prefix (`startswith`, matching
     `latest_event` semantics), and:
     * `pod` given AND ≥1 event's note matches `_pod_attribution_re(pod)` →
       LAST such event in append order (pod-scoped path);
     * otherwise → LAST matching event in append order issue-wide (today's
       behavior — covers `pod is None`, single-pod runs, and pre-#1961
       unattributed notes);
     * log ONE `log.debug` line naming the path taken
       (`pod-scoped | issue-wide-fallback | issue-wide`) so the tick transcript
       says which marker was compared (task-body ask: "say which path was taken").
     * Fail-soft contract identical to today's helpers: any read exception →
       `None` + `log.warning`/`log.debug`, never a crash.
     * Docstring flags TWO seams: (i) `tests/test_poll_pipeline_sentinels.py:166`
       stubs `pp.list_events → []` for the #1084 sentinel-dedupe read — a resolver
       reading the same module attribute widens that stub's blast radius (in
       practice helper-level fakes intercept first); (ii) the mixed-attribution
       corner: a pod with an OLD attributed marker + a NEWER unattributed
       free-prose relaunch marker resolves to the older attributed one (by
       design — #1961 mandates producer-side attribution; the debug line
       surfaces it; pinned by a test, §2d).

b. **Thread `pod` through the three readers** (keyword arg, default `None` = exact
   today-behavior):
   - `_marker_pid(issue: int, pod: str | None = None)` — resolve the event via
     `_latest_run_launched_event(issue, pod)`, then parse `MARKER_PID_RE` as today.
   - `_marker_launch_fields(issue: int, pod: str | None = None)` — passes `pod`
     to its internal `_marker_pid` call (module-level lookup PRESERVED so the
     ~#1650 test fakes still intercept) AND uses the same pod-scoped event for
     the note text (the two-read shape is kept; both reads use the same resolver
     so pid and note can never come from different markers).
   - `_run_launched_age_sec(issue: int, now_epoch: float, pod: str | None = None)`
     — age of the pod-scoped event, same unparseable-ts → None behavior.

c. **Thread `pod` at the two poll_once call sites** (both have `pod` in scope):
   - `:5540` → `_marker_launch_fields(issue, pod=pod)` (feeds
     `_maybe_warn_pid_identity` at `:5582` — fixes `marker_pid_identity: unknown`).
   - `:5839` → `_run_launched_age_sec(issue, now_epoch, pod=pod)` (feeds
     `_maybe_warn_stale_pid_file` at `:5844` — fixes the recurring false WARN).

   **Fourth caller — named, fenced OUT of scope:** `scripts/backend_poll.py:5935`
   calls `_run_launched_age_sec(args.issue, now_epoch)` positionally (local
   import at `backend_poll.py:5903`, GCP GPU-idle block). Benign under the
   keyword-default design (2 positional args still bind; `pod=None` → today's
   behavior). Do NOT thread `pod` there and do NOT touch its 3 fakes at
   `tests/test_backend_poll_gpu_idle.py:872,914,1048`
   (`lambda issue, now_epoch: ...`) — the must-ask fence limits scope to
   `poll_pipeline.py` + its tests.

### 2. `tests/`

d. **New test file `tests/test_poll_pipeline_pod_scoped_marker.py`** pinning, with
   a two-marker fixture (older marker `pod=pod-77` token form + newer marker
   leading-name form `pod-77-q32b ...`, distinct `pid=` values, distinct `ts`):
   - pod-scoped resolution for BOTH attested note shapes (token + leading name);
   - boundary safety both directions (`pod-77` never matches `pod-77-q32b`'s
     marker and vice versa; mid-prose mention does not match);
   - polling the older pod: `_run_launched_age_sec` returns the OLDER marker's age
     and `_marker_pid` returns ITS `pid=`;
   - fallback: pod given but NO attributable note → last issue-wide (and
     `pod=None` → last issue-wide);
   - mixed-attribution corner (critic note 5): same pod, old ATTRIBUTED marker +
     newer UNATTRIBUTED marker → resolver returns the older attributed one
     (pins the chosen semantics);
   - integration-shape pins via the existing pure helpers: with pod-scoped
     `run_age_sec`, `_pid_file_predates_marker` is False for a pid file younger
     than the leg's own marker (acceptance 1) and True for one genuinely older
     than its own marker by more than the slack (acceptance 2).
   Follow the fixture conventions of `tests/test_poll_pipeline_stale_pid_warn.py`
   (monkeypatched event reads; no SSH, no real task state).
