## 3. Design — concrete diff against `scripts/i528_phase4_judge.py`

### 3.1 Import (top-level, NOT inside the `--backend batch` branch)

Add alongside the existing `explore_persona_space.*` imports near the top of the file:

```python
from explore_persona_space.eval.batch_judge import _chunk_requests
```

Rationale: the script already imports from `explore_persona_space.*`, so the package resolves; a top-level import keeps the branch body clean and makes the dependency visible to the lint check.

### 3.2 Request list construction — UNCHANGED

The `requests` list is built exactly as today. Do **not** touch:
- the **custom_id format** `i528__{cell_id}__q{q_idx}__k{k}` (verbatim — the `--backend sync` merge reader parses it),
- the per-request message bodies,
- the **3×-averaging join**, whose key is `(cell_id, q_idx)` (derived from the parsed custom_id, NOT from any batch grouping) — sharding across batches does not change which requests share a join key.

### 3.3 Shard + submit loop (replaces the single `batches.create` call)

Current (lines ~318-362, the load-bearing call):

```python
batch = client.messages.batches.create(requests=requests)
# ... writes pending JSON with a single batch_id ...
```

Replace the submit + pending-write with:

```python
# Shard so no batch exceeds the Anthropic 100k-requests/batch limit
# (_chunk_requests caps at MAX_REQUESTS_PER_BATCH = 8_000 and ≤250 MB).
batch_ids: list[str] = []
chunks = list(_chunk_requests(requests))          # materialize so we can count
for chunk in chunks:
    batch = client.messages.batches.create(requests=chunk)
    batch_ids.append(batch.id)

print(
    f"[i528 phase4 batch] submitted {len(requests)} requests "
    f"across {len(chunks)} batch(es): {batch_ids}"
)

pending = {
    "schema_version": "i528_v2",
    "batch_ids": batch_ids,            # list, one id per shard
    "n_requests": len(requests),
    # ... carry forward all other existing pending fields verbatim
    #     (cell ids, k, model, timestamp, paths the --backend sync reader needs) ...
}
# write `pending` to the same pending-file path as today
```

Notes:
- `_chunk_requests` is materialized into `chunks` once so `len(chunks)` is available for both the log line and the loop; do not consume the generator twice.
- Every existing field of the pending dict OTHER than the batch-id field is preserved unchanged — only the single `batch_id: str` becomes `batch_ids: list[str]` and `schema_version` + `n_requests` are added.

### 3.4 Pending JSON schema bump — `i528_v2` with `batch_ids: [...]`

- New `schema_version: "i528_v2"`.
- Replace the single `"batch_id": "<id>"` field with `"batch_ids": ["<id>", ...]` (a list, one entry per shard; length ≥ 2 when `N > 8000`, length 1 for small jobs).
- Add `"n_requests": <total>` (the pre-shard total, for operator sanity-checking and the unit test).
- **Drop the single `batch_id` field entirely** (do not write both) — see §11 rationale.
- Document the v2 schema in the script's module/function docstring so any operator reading the pending JSON knows the shape changed (single → list).

### 3.5 `--backend sync` merge reader

The merge reader lives in a SEPARATE `--backend sync` re-run (per the body, not in this file's submit path). This plan does NOT modify the sync reader. If the sync reader currently reads a single `batch_id`, that is operator-facing follow-up — BUT per the clarifier there is **no in-codebase programmatic reader** of the pending `batch_id` (only `i528_phase4_judge.py` itself touches `judge_batch_pending`), so the v2 list shape does not break any committed code path. The operator merges by reading `batch_ids` from the v2 pending file.

## 11. Decision rationale

- **Option (a) chunk+multi-submit over option (b) shared client:** the `--backend batch` path is fire-and-forget (submit, write pending `batch_id`s, return; merged later by a separate `--backend sync` run). The shared `judge_completions_batch` / `_submit_and_poll_batch` BLOCK on polling, which would break the behavior-critical fire-and-forget protocol the task body cites. `Source: task body + clarifier`.
- **`schema_version: "i528_v2"`:** the pending shape changes structurally (single `batch_id` → `batch_ids` list); a version bump makes the change explicit and self-documenting. No in-codebase reader exists, so backward compat is unnecessary. `Source: clarifier (no external reader)`.
- **Drop the single `batch_id` field rather than write both:** the script is operator-facing only with no programmatic reader to keep compatible; carrying both a scalar and a list invites the operator (or a future merger) to read the stale scalar and miss shards. Simplicity wins. `Source: clarifier`.
- **`_chunk_requests` reuse (≤8k/batch):** already production-tested inside `_submit_and_poll_batch` since the hardened batch client landed; no new chunking logic to test from scratch. `Source: #663`.
