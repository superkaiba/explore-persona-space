`scripts/i528_phase4_judge.py --backend batch` submits its Anthropic Message Batch un-sharded (one `client.messages.batches.create(...)` carrying all `3 × N` requests), which 409s past the 100k-requests/batch API limit on a large i528 job; shard the submit so every chunk is its own batch (≤8k/batch), record the resulting `batch_id` list in a versioned pending JSON, and drop the file's `BATCH_JUDGE_LEGACY_ALLOWLIST` grandfather entry. ## 3. Design

### 3.0 NEW sanctioned helper in `src/explore_persona_space/eval/batch_judge.py`

Add a public fire-and-forget submit helper next to `_submit_and_poll_batch`. It is the legitimately-public successor of the private `_chunk_requests` import for fire-and-forget callers (the polling sibling is reached via `judge_completions_batch` / `_submit_and_poll_batch`). Because it lives in a `BATCH_JUDGE_SANCTIONED_FILES` member, the inline `client.messages.batches.create()` is policy-exempt.

The helper OWNS the incremental pending-write so a mid-loop crash leaves a recoverable pending file (CLAUDE.md "Checkpoint per phase; never accumulate-in-memory and write-at-end"; Codex partial-failure residue, option (a)). It takes an optional `on_batch_submitted` callback the caller uses to persist progress after each chunk; the caller wires this to its pending-JSON writer.

```python
# In src/explore_persona_space/eval/batch_judge.py
from collections.abc import Callable  # already imported at module top (line 26)

def submit_sharded_batches_fire_and_forget(
    client: "anthropic.Anthropic",
    requests: list[dict],
    *,
    on_batch_submitted: Callable[[list[str]], None] | None = None,
) -> list[str]:
    """Submit ``requests`` sharded into chunks of <= MAX_REQUESTS_PER_BATCH, fire-and-forget.

    Returns the list of submitted batch IDs in submission order. Does NOT poll —
    intended for callers (e.g. ``scripts/i528_phase4_judge.py --backend batch``) that
    submit-then-return and merge results in a separate sync re-run, vs the polling
    ``judge_completions_batch`` / ``_submit_and_poll_batch`` path.

    ``on_batch_submitted`` (if given) is invoked with the running ``batch_ids`` list
    AFTER each chunk's batch is created, so the caller can persist incremental
    progress (Checkpoint-per-phase: a mid-loop crash leaves a recoverable record of
    the shards already submitted, rather than orphaning shards 0..k when shard k+1
    raises before any write lands). On any per-chunk failure the exception propagates
    immediately; the IDs submitted so far are already persisted via the callback.
    """
    batch_ids: list[str] = []
    for chunk in _chunk_requests(requests):
        batch = client.messages.batches.create(requests=chunk)
        batch_ids.append(batch.id)
        if on_batch_submitted is not None:
            on_batch_submitted(batch_ids)
    return batch_ids
```

Notes:
- `_chunk_requests` returns a generator; the helper iterates it ONCE (single consumption), so no double-consume hazard. (v1's "materialize so we can count + don't consume twice" prose is dropped — the count comes from `len(batch_ids)` after the loop, computed by the caller.)
- The create call inside this function is the ONLY `client.messages.batches.create()` in the change; it is in a sanctioned file, so `--check-batch-judge-client` is satisfied.

The `requests` list is built exactly as today. Do **not** touch:

### 3.3 Submit via the helper + incremental pending-write (replaces the single `batches.create` call)

Current (line ~341, the load-bearing call):

```python
batch = client.messages.batches.create(requests=requests)
# ... writes pending JSON with a single batch_id ...
```

Replace the submit + pending-write with a call to the helper, wiring the incremental-write callback to the script's pending-JSON writer:

```python
# Build the v2 pending payload up front (everything except batch_ids, which fills in
# as chunks submit). All other pending fields carried forward verbatim.
pending = {
    "schema_version": "i528_v2",
    "batch_ids": [],                  # filled incrementally by the callback below
    "n_requests": len(requests),
    # ... carry forward all other existing pending fields verbatim
    #     (cell ids, k, model, timestamp, paths the --backend sync reader needs) ...
}

def _persist_pending(batch_ids: list[str]) -> None:
    # Checkpoint-per-phase: rewrite the pending JSON after EACH chunk submit so a
    # mid-loop crash leaves a recoverable record of the shards already submitted.
    pending["batch_ids"] = list(batch_ids)
    # write `pending` to the same pending-file path as today (atomic write)

batch_ids = submit_sharded_batches_fire_and_forget(
    client, requests, on_batch_submitted=_persist_pending,
)
# Final write is implicitly done by the last callback invocation; an explicit
# _persist_pending(batch_ids) here is a harmless no-op safety net for the
# zero-chunk edge case (empty requests -> no callback fires).
_persist_pending(batch_ids)

print(
    f"[i528 phase4 batch] submitted {len(requests)} requests "
    f"across {len(batch_ids)} batch(es): {batch_ids}"
)
```

Notes:
- The incremental write lives in the SCRIPT (via the callback), not the helper, because the pending-JSON SHAPE (`schema_version`, the carried-forward fields, the file path) is i528-specific; the helper stays generic (it only knows "I submitted these IDs so far"). This keeps the helper reusable by any future fire-and-forget caller with a different pending shape.
- Every existing field of the pending dict OTHER than the batch-id field is preserved unchanged — only the single `batch_id: str` becomes `batch_ids: list[str]` and `schema_version` + `n_requests` are added.

### 3.4 Pending JSON schema bump — `i528_v2` with `batch_ids: [...]`

- New `schema_version: "i528_v2"`.
- Replace the single `"batch_id": "<id>"` field with `"batch_ids": ["<id>", ...]` (a list, one entry per shard; length ≥ 2 when `N > 8000`, length 1 for small jobs).
- Add `"n_requests": <total>` (the pre-shard total, for operator sanity-checking and the unit test).
- **Drop the single `batch_id` field entirely** (do not write both) — see §11 rationale.
- Document the v2 schema in the script's module/function docstring so any operator reading the pending JSON knows the shape changed (single → list).

### 3.5 `--backend sync` merge reader

The merge reader lives in a SEPARATE `--backend sync` re-run (per the body, not in this file's submit path). This plan does NOT modify the sync reader. Per the clarifier there is **no in-codebase programmatic reader** of the pending `batch_id` (only `i528_phase4_judge.py` itself touches `judge_batch_pending`), so the v2 list shape does not break any committed code path. The operator merges by reading `batch_ids` from the v2 pending file.

## 11. Decision rationale

- **New sanctioned helper instead of inline `client.messages.batches.create()`:** putting the shard+submit loop into a NEW public helper in `eval/batch_judge.py` (a `BATCH_JUDGE_SANCTIONED_FILES` member, `workflow_lint.py:558-561`) makes the create call policy-exempt by file-suffix (`workflow_lint.py:2123`), closing the `--check-batch-judge-client` contradiction that an inline create in `scripts/i528_phase4_judge.py` would produce once the `BATCH_JUDGE_LEGACY_ALLOWLIST` entry is dropped (lint error path `workflow_lint.py:2123-2157`). It ALSO removes the private-underscore `_chunk_requests` import smell from a top-level script (the script imports the public helper instead). `Source: Phase-2 Methodology reconciler REVISE-binding + Alternatives reconciler REVISE-binding`.
- **Helper is fire-and-forget (does NOT poll), distinct from `_submit_and_poll_batch`:** the `--backend batch` path submits-then-returns and merges in a separate `--backend sync` run; the existing `_submit_and_poll_batch` / `judge_completions_batch` BLOCK on polling (Codex-confirmed), which would break the fire-and-forget protocol the task body cites. The new helper is the public fire-and-forget sibling. `Source: task body + clarifier + Codex methodology critic`.
- **Incremental pending-write after each chunk (via the helper's `on_batch_submitted` callback):** a mid-loop crash between submitting shard k and writing the pending JSON would orphan shards 0..k. Writing the pending JSON after EACH chunk submit makes a mid-loop crash recoverable, matching the CLAUDE.md "Checkpoint per phase; never accumulate-in-memory and write-at-end" code-style rule. The write lives in the script's callback (i528-specific pending shape), not the helper (generic). `Source: CLAUDE.md code-style + Codex partial-failure residue (option (a))`.
- **`schema_version: "i528_v2"`:** the pending shape changes structurally (single `batch_id` → `batch_ids` list); a version bump makes the change explicit and self-documenting. No in-codebase reader exists, so backward compat is unnecessary. `Source: clarifier (no external reader)`.
- **Drop the single `batch_id` field rather than write both:** the script is operator-facing only with no programmatic reader to keep compatible; carrying both a scalar and a list invites the operator (or a future merger) to read the stale scalar and miss shards. Simplicity wins. `Source: clarifier`.
- **`_chunk_requests` reuse (≤8k/batch) inside the helper:** already production-tested inside `_submit_and_poll_batch` since the hardened batch client landed; no new chunking logic to test from scratch. `Source: #663`.
