## 3. Plan-time safety verification of leg (a) — the design argument

**Mechanism today** (verified by grep-anchored windows, 2026-08-10): `classify_cmd` (L694) sets `root_commit=1` for any commit-verb clause that is not (i) cd-latched to a provable worktree (`cd_latch_verdict`, L361) or (ii) waived by a lead-anchored `git -C <non-root-target>` form. Layer 2 (L1562+) then reads the ROOT's staged index (`git -C "$GUARD_REPO" diff --cached`), so a bare commit clause whose ACTUAL execution cwd is a linked worktree is judged against the root's uncertified drafts — the false-block class in the body (7+ blocked commits, 5 sessions, 2026-08-03/04). The header names this CWD-BLIND at L61-71.

**The exhaustive case split for `root_commit=1`.** A clause reaches `root_commit=1` only via:

1. a BARE commit clause (no cd, no `-C`) — executes at the hook-input cwd;
2. a commit clause following `cd <target>` where `cd_latch_verdict` returned `root`;
3. a commit clause following `cd <target>` where the verdict was `unproven` (fail-closed);
4. a `git -C <target>` commit clause where `<target>` literally spells the repo root;
5. a `git -C <target>` commit clause where the waiver was REFUSED (target unextractable/opaque).

Case 1 is the ONLY case where the hook-input cwd determines where the commit lands. Cases 2 and 4 are provable root-retargets (must keep blocking). Cases 3 and 5 are ambiguous (must keep blocking, fail-closed). Therefore the allow gate is safe iff it fires only when **every** contribution to `root_commit=1` came from case 1 **and** the hook-input cwd is provably a linked worktree — then every commit clause in the command executes in the worktree (or a cd-latched sibling worktree), never at root.

**Residual channel — retarget tokens `classify_cmd` does not model:** `env --chdir=<root> git commit`, `git --work-tree=<root> commit`, `git --git-dir=<root>/.git commit`. These can present as case-1-shaped clauses (lead token not `git`, or flags between `git` and the verb) while landing at root. The gate therefore ALSO requires a raw-command conservative screen: any occurrence of `--chdir`, `--work-tree`, or `--git-dir` anywhere in the command disables the allow. Fail-closed: false positives from the screen (e.g. the token inside a commit message) keep today's behavior, never open a new allow.

**Worktree proof (fail-closed):** with `hook_cwd` from the payload's `.cwd`,
- `wt_top=$(git -C "$hook_cwd" rev-parse --show-toplevel)` must succeed and resolve (realpath -m) to something ≠ realpath(`$GUARD_REPO`);
- `wt_common=$(git -C "$hook_cwd" rev-parse --git-common-dir)` must succeed and resolve to realpath(`$GUARD_REPO`)/.git.
Any git failure, empty output, or mismatch → gate does not fire (today's behavior). This proves `hook_cwd` is inside a linked worktree WHOSE COMMON GIT DIR IS THE GUARDED REPO's — a root-subdir cwd fails the first check (toplevel == root, preserves B38/MF-1), an unrelated repo fails the second, an unknown/relative/empty cwd fails outright.

**Allow semantics = parity with the existing `git -C "$WT"` waiver** (allow, exit 0, no root-index read): worktree commits are gated at Step 10d, not by this hook. Notably `git -C "$WT" add -A && git -C "$WT" commit` is already allowed today (both clauses waived), so the gate is placed BEFORE the blanket-add block — the bare `git add -A && git commit` at a worktree cwd gets the same treatment as its `-C` spelling. No new privilege is created relative to what any agent can already do by spelling `-C`.

**Conclusion:** leg (a) is safe under the four conjunct conditions in §4. The unverified hypothesis in the body is resolved: extending to a provably-worktree cwd is safe ONLY as a whole-command allow gated on zero retarget evidence — NOT as a "scope Layer-2 to the worktree index" variant (rejected: it would re-implement cert semantics against the wrong index and still misfire on multi-clause commands).
