## Plan Summary

Extend `_run_git`'s existing **single** lock-contention retry (#898, commit
`ffdcd04094`) into a **bounded wall-clock retry loop** (default ~60 s
per call, env-tunable), so a transient `.git/index.lock` collision that
outlasts one 2–3 s backoff no longer crashes a `task.py` mutation
mid-commit (the #1815 half-applied `set-status` shape, 2026-07-30). The
#898 fail-loud contract is preserved verbatim: on budget exhaustion (or any
non-lock failure) the same `CalledProcessError` raises, the stale-lock
ERROR remedy still logs, and `set_status`'s durably-applied + ghost-sweep
semantics are untouched.

NOT architectural: internal helper behavior only — no status enum, marker
schema, task.py subcommand, or file-location change. `architectural: false`.

## Requirement + acceptance criteria

Requirement (task Goal): stop a transient index.lock collision from leaving
`task.py set-status` in a half-applied state needing hand-reconcile, via a
bounded lock retry before the deliberate fail-loud raise.

Plan-time verification of the body's flagged hypothesis (per its
`verified-at-filing` note): the premise "no bounded lock retry precedes the
set-status commit" is **partially refuted** — `_run_git` already retries
ONCE on the lock-contention stderr signature (`_GIT_LOCK_CONTENTION_RE`,
2–3 s jittered sleep; landed WITH #898). The #1815 incident therefore means
the collision **outlasted the single retry** (two attempts ~2.5 s apart both
hit the lock — plausible under a concurrent large commit whose pre-commit
hooks hold the index for tens of seconds). The residual gap is retry
DEPTH/DURATION, exactly option (a). Option (b) (manual-reconcile recipe) is
already substantially served by the existing `set_status` except-block ERROR
log, which prints the exact sweep commands at exactly the failure moment; no
SKILL.md change needed.

Acceptance criteria:

1. `_run_git` retries a lock-signature failure until success OR a bounded
   total wall budget is exhausted. Budget: `EPM_TASKPY_LOCK_WAIT_SECONDS`
   (new env), default `60`, `0` disables retries entirely (single attempt),
   non-finite/non-float raises `ValueError` — byte-parallel to the in-file
   `_merge_wait_bound_s()` precedent (`EPM_TASKPY_MERGE_WAIT_SECONDS`).
   The budget is **PER `_run_git` CALL** (deliberate — see Method delta
   § Flock-stacking decision).
2. Zero happy-path latency: a successful call takes no sleep; retry keys on
   the STDERR SIGNATURE, never the return code (unchanged), so `check=False`
   rc-as-signal callers (`diff --cached --quiet`) keep rc semantics.
3. Non-lock failures raise immediately with ZERO sleeps (unchanged pin).
4. On exhaustion: the stale-lock remedy logs at ERROR and the caller's
   `check=True` raises `CalledProcessError` with the same fields — the #898
   raise + `set_status` ghost-sweep semantics stay byte-identical.
5. Per-retry sleep stays jittered `_GIT_LOCK_RETRY_SLEEP_RANGE_S` (2.0–3.0 s)
   → ~20–24 attempts inside the default per-call budget.
6. Test pins updated (see Files below); `tests/test_task_workflow*.py` green.

## Method delta

#898 chose "retry ONCE (never more)" as a minimal fix; 5 lock firings across
4 sessions on 07-30 (one crashing #1815's set-status) show single-retry depth
is insufficient under current fleet concurrency. CLAUDE.md's
concurrent-committer guidance already prescribes the ~60 s bounded-poll form
for session-side `index.lock` collisions; this plan moves that same bound
into the library helper. Loop form: capture `deadline = time.monotonic() +
_lock_wait_bound_s()` on the FIRST lock-signature failure; while failure ∧
signature ∧ `monotonic() < deadline`: WARN (first iteration; DEBUG or
throttled thereafter), jittered sleep, re-attempt. On loop exit with a
lock-signature failure still standing: existing ERROR remedy + raise.

### Flock-stacking decision (critic round-1 Must-Fix — resolved)

The budget is per `_run_git` call, and a single flock'd mutation runs
multiple git calls (set_status: `add` + `commit`, each of which may itself
retry). Honest bounds:

- **Common stale-lock case (lock never clears):** the FIRST `_run_git` call
  exhausts its ~60 s budget and RAISES → the mutation aborts → later calls
  never run. Total flock hold ≈ **60 s + one merge-wait if already entered**
  — NOT k×60. A permanently-stale lock therefore costs ~60 s per mutation
  fleet-wide until removed (vs ~2.5 s today); the ERROR remedy text will
  name this new latency signature so a triager recognizes it.
- **Theoretical adversarial case:** k independent collisions that each clear
  *just* inside the budget → flock hold ≈ k×60 s + merge-wait ≈ 180–300 s.
  This requires repeated near-budget collisions (each concurrent lock-holder
  finishing at ~59 s); realistic transient collisions clear in the seconds a
  concurrent commit + hooks take, so typical added wait ≈ the duration of
  ONE concurrent git operation.
- **Accepted consequence (explicit):** during a sustained lock storm,
  `sync_repo_root.py`'s `EPM_ROOT_SYNC_LOCK2_WAIT_S` = 120 s task-workflow-
  lock wait can now be outlasted by a waiting task.py writer → sync exits
  **5** (`SyncAbortError`, loud precondition failure, single-flight,
  re-runnable). This is ACCEPTED: today the same storm crashes the task.py
  mutation itself into a half-applied state needing hand-reconcile (#1815);
  a loud, idempotently re-runnable sync exit is the strictly cheaper
  failure. Decision: per-call budgets kept (critic option (i)); a shared
  cross-call deadline (option (ii)) threads state through `_git_commit` and
  the ghost-sweep path for marginal benefit against a theoretical case, and
  a smaller default (option (iii), 30 s) still stacks past 120 s at k=3
  while halving protection in the common one-collision case.

Other interaction notes:
- The wait runs while `_locked()` (the task-workflow flock) is held —
  concurrent `task.py` writers BLOCK behind it instead of interleaving
  crashes. No deadlock is possible: the flock is a single global lock, so
  two writers can never wait on each other's git lock, and the deadline
  bounds any pathological cycle.
- `_PARTIAL_COMMIT_SEQUENCER_RE` / merge-wait (#1030) semantics untouched —
  the lock loop lives entirely inside `_run_git`; `_git_commit`'s sequencer
  wait remains a separate, composable bound.
