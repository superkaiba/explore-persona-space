## Requirement (the bullet text)

Add the following bullet to the HF Hub cluster in `.claude/rules/gotchas.md`,
inserted IMMEDIATELY AFTER the `>10000 files BadRequestError` bullet (currently
line 103, the one that opens `**HF Hub rejects any single repo directory holding
>10000 files at COMMIT time ...**`) and BEFORE the
`**GCP-lane diagnostic inability after an early guestTerminate ...**` bullet
(currently line 104):

```
- **HF Hub per-org 2500-req-per-5-min rate limit (429) on bulk `snapshot_download`.** HF Hub enforces a hard ~2500-API-requests-per-5-minutes quota at the ORG level (each xet-read-token fetch, tree-listing, and file-metadata call counts as one request). A `snapshot_download` of ≥3000 files at default `max_workers` issues one xet-read-token call per file, so it predictably trips the quota — and the failure surfaces LATE (the burst runs fine for tens of minutes, then 400s with `huggingface_hub.errors.HfHubHTTPError: 429` mid-download, after the partial download is already spent). RULE: for any bulk `snapshot_download` of many files, pass `max_workers=4` (≈1200 req/5min at 4-way parallelism, comfortably under the quota) AND wrap the call in a 429-aware retry with `Retry-After`-header-bounded backoff (60–300s); the xet bulk-download path is NOT covered by `huggingface_hub`'s built-in per-endpoint 429 retry, so the wrapper is mandatory. (Upgrading the org to Team/Enterprise raises the quota.) This is the bulk-download-side sibling of the per-probe `AutoTokenizer.from_pretrained` 429 entry at the bottom of this file — both trip the SAME ~2500-req/5-min org quota, one via per-file fetch bursts, the other via per-load `model_info()` calls. (Incident #658 round 4, 2026-06-29: a 12000-file `rollout_acts/*.pt` `snapshot_download` at default `max_workers` ran ~38min then crashed on the 429.)
```

The bullet follows the surrounding cluster's shape: a bold lead sentence,
RULE/RECIPE prose, and an incident citation in parentheses.
