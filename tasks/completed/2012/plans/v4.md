## §1 Motivation (verified, not inherited)

The task body flagged its own mechanism as `unverified hypothesis — verify at
plan time` (miner-inferred from #1947's orchestrator root-cause note; the script
was never opened). It is now read and **CONFIRMED in source**.

`scripts/issue1947_worker.py::_teardown_marker_cell` (added as "#1947 crash-fix
r11") implements exactly the recipe this plan documents, and its docstring
states both halves:

- reorder — "Frees the HF base model FIRST, THEN runs `backend.close` — whose
  `issue1333_dispatch._wait_engine_release` drain-wait REQUIRES that the caller
  holds NO live HF-weight reference at the call (r9 contract): closing with the
  ~15 GiB base model still resident times the wait out DETERMINISTICALLY."
- unmasking guard — "A close-time exception is logged + suppressed when an inner
  exception is already propagating (`sys.exc_info()`) so the inner error stays
  visible; with no inner exception in flight a close failure raises normally
  (fail-fast)."

Shipped implementation:

```
inner_active = sys.exc_info()[0] is not None
try:
    backend.close(slug)
except Exception:
    if not inner_active:
        raise
    logger.exception(...)
```

So the landed fix is **detect-and-log-suppress**, not `raise ... from exc`. The
gotchas entry therefore states suppress-when-in-flight / bare-raise-when-not as
the primary recipe (matching the reference implementation) and chaining as the
alternative — the task body's phrasing named chaining first, which would have
documented a pattern the repo does not actually use here.

Cost of the class: all 4 #1947 marker cells failed 3 rounds reported as
"GPU-drain timeout"; round 1 raised the drain timeout to 900s, round 2 re-ran
serially, both failed. The true inner error was the `EADDRINUSE` vLLM
rendezvous-port race the close-gate raise was replacing. Round 3 finished 4/4
once the mask was removed — two relaunch rounds spent fixing a symptom.

**The masking CHANNEL, corrected in v3 (critic round 1 blocker).** v2's gotchas
draft asserted the inner exception is retained "only [in] `__context__`, and no
traceback line surfaces it". That is **false**, verified empirically this round:
PEP 3134 implicit chaining makes the default traceback print the inner exception
in full under `During handling of the above exception, another exception
occurred:`, and `logger.exception` logs the same chain. The actual loss happens
at any consumer that formats only the FINAL exception. #1947's channel is exactly
that — `scripts/issue1947_worker.py:1005-1013`:

```
except Exception as e:  # fail LOUD but always leave a status record
    logger.exception("[cell] %s FAILED", slug)
    result = {"status": "failed", "slug": slug,
              "reason": f"{type(e).__name__}: {e}", ...}
```

`logger.exception` at :1006 held the full chain; `reason` at :1010 — the field
the orchestrator triages from — held only `TimeoutError: TEARDOWN: drain-wait
timed out`. Confirmed against a live reproduction: with a `ValueError` inner and
a `TimeoutError` raised in `finally`, the traceback shows both, while
`f"{type(e).__name__}: {e}"` shows only the `TimeoutError`.

This changes the deliverable materially. The v2 wording would have taught the
next debugger that the traceback CANNOT hold the real error — suppressing the
single fastest recognition step (read the `During handling` block, which would
have ended #1947 at round 1) — and would have read as not-applicable to anyone
whose log did show both tracebacks. v3 therefore documents both the raise side
AND the reporting side: a per-unit failure record must carry the exception
CHAIN, not `str(e)`, or the mask re-forms downstream of a correctly-guarded
teardown.

**A live unguarded sibling exists** at `scripts/issue1947_worker.py:647-650`
(`finally: close = getattr(gen, "close", None); if callable(close): close()` —
no `sys.exc_info()` guard). It is **NOT touched by this plan**: #2012's own
Constraints scope this task to the workflow surface, never experiment code. It is
recorded here as evidence that the reviewer rubric line has a real target, and
as a candidate for a separate task at the orchestrator's discretion.

## §4 Exact inserts

### 4.1 `.claude/rules/gotchas.md` — new bullet after the L80 entry

```
- **A `finally`-block raise REPLACES the in-flight exception, and every final-exception-only CONSUMER then reports the teardown symptom as the whole failure.** A close-gate / drain-wait / teardown assert that fires while an inner exception is already propagating becomes the exception that leaves the frame. Python's implicit chaining keeps the original: the DEFAULT traceback still prints it under `During handling of the above exception, another exception occurred:`, and `logger.exception` logs that same chain. What loses it is any consumer that formats only the FINAL exception — a status record or sentinel field built as `f"{type(e).__name__}: {e}"`, a marker note, a log grep for the last error line — which is exactly how fan-out harnesses report per-unit failures, so the triage surface shows the teardown stage and nothing else (#1947: the per-cell handler logged the full chain via `logger.exception` but wrote `reason: f"{type(e).__name__}: {e}"` into the status record the orchestrator triages from — `scripts/issue1947_worker.py:1005-1013` — so two relaunch rounds "fixed" a GPU-drain timeout, raising the wait to 900s then re-running serially, while the true cause was the `EADDRINUSE` rendezvous-port collision in the entry above; round 3 finished 4/4 once the mask was gone). RULE: inside any `finally` / teardown / close path that can raise AS PART OF ITS OWN GATING LOGIC (timeout gate, drain-wait, teardown assert, raise-on-failure wait), detect an in-flight exception FIRST — `inner_active = sys.exc_info()[0] is not None` — and when one is live, log the teardown failure (`logger.exception(...)`) and let the original propagate; with none live, raise normally (fail-fast). `raise ... from exc` is the alternative when the teardown error itself must reach the caller — it keeps the original reachable as `__cause__`, but does NOT save a final-exception-only consumer. NEVER bare-raise unconditionally. Second RULE, for the reporting side: a per-unit failure record carries the CHAIN, not `str(e)` — `traceback.format_exception(e)` (or a `reason_chain` field alongside `reason`) — so the mask cannot re-form downstream of a correctly-guarded teardown. Reference impl: `scripts/issue1947_worker.py::_teardown_marker_cell` (#1947 r11), which ALSO reorders teardown so the drain-wait runs only after the HF weights are freed. Diagnostic signature: every unit in a fan-out reports the SAME teardown-stage error across rounds, fixes aimed at that stage change nothing, and the harness's own log holds a `During handling of the above exception` block the status/marker surface never showed — the raise-side sibling of the handshake-timeout MASK entry below.
```

### 4.2 `.claude/agents/code-reviewer.md` — new block at end of Step 2

```
**Exception-masking teardown paths (any diff type).** Flag as Major any
`finally` / teardown / close-gate / drain-wait path in the diff that raises
as part of its OWN gating logic (a timeout gate, drain-wait, teardown
assert, raise-on-failure wait) while an inner exception may already be
propagating, and does NOT either chain (`raise ... from exc`) or
suppress-and-log under an in-flight check
(`sys.exc_info()[0] is not None`). The replacing raise becomes the
exception that leaves the frame, so every final-exception-only consumer —
a status/sentinel `reason` built from `str(e)`, a marker note, a
last-error log grep — reports the teardown stage as the whole failure and
each retry round debugs the wrong one: a silent-failure defect, blocker tag
`substantive`, never a style nit (#1947: two relaunch rounds chased a
"GPU-drain timeout" while the true `EADDRINUSE` port race stayed masked).
Plain cleanup that merely propagates its own I/O error (`finally:
f.close()`) does NOT trigger this. Same finding applies to the reporting
side: a per-unit failure record built from `str(e)` instead of the
exception CHAIN re-creates the mask downstream. Reference impl:
`scripts/issue1947_worker.py::_teardown_marker_cell`; full recipe in
`.claude/rules/gotchas.md` (the `finally`-raise entry).
```

Wording may be tightened at review; the two load-bearing invariants that must
survive any rewording are (a) the in-flight-exception check is named
mechanically (`sys.exc_info()`), and (b) the finding is `substantive`, so
Step 5c-bis cannot strip it as a mechanical-contract objection.
