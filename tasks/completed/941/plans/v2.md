```markdown
- **(j) Pairwise provenance coherence (mutually-dependent artifact PAIRS).**
  When the reuse consumes two-or-more artifacts that must be mutually
  consistent because one was PRODUCED UNDER the other — a question/prompt
  bank vs activations / teacher-forced reads captured under it; a training
  mix vs the adapter trained on it; a completion pool vs judge outputs
  scored over it — checks (e)/(f) pin each member's CURRENT bytes
  individually but say nothing about whether the members come from the SAME
  generation. Verify the consumed INPUT does not POSTDATE the dependent
  CAPTURE, comparing last-modified dates AT THE REVISION EACH MEMBER IS
  ACTUALLY CONSUMED FROM. Mechanics — first group the pair's members by
  concrete storage location (repo_id + repo_type + consumed revision; the
  members often live in DIFFERENT stores: adapters/checkpoints in the model
  repo, mixes/raw-completion buckets in the data repo, judge/eval JSONs in
  git), then date each member:
  - HF-resident member: `HfApi().get_paths_info(repo_id, [<member file
    paths>], expand=True, repo_type=..., revision=<the revision the
    consumer will fetch>)` → per-path `last_commit` (`oid`, `date`) — a
    per-path POST, safe on the ~1M-file data repo (measured ~0.5 s; paths
    must be non-empty FILE paths, else HTTP 400). One call per repo; a
    same-repo single-file pair may batch both paths into one call.
  - Folder / multi-file member (a LoRA adapter subfolder, a sharded
    store): probe the EXACT consumed file set (every member file the
    consumer loads, or the artifact's named manifest file) and reduce to
    the MAX member-file `last_commit.date` — an unprobed sibling can be
    the regenerated file.
  - Git-resident member (a committed `eval_results/...` input):
    `git log -1 --format=%cI <consumed ref> -- <path>`.
  Require `max(input member dates) <= min(capture member dates)` at the
  consumed revisions; ALSO read any `reconstruction` / regeneration
  metadata field the artifact itself carries (#922's question artifact
  documented its own regeneration). Two caveats: commit/upload time is a
  PROXY for production time — a capture-side re-commit that postdates the
  input's regeneration is NOT evidence the capture was regenerated under
  the new input unless its provenance metadata says so; and an input
  regenerated AFTER the capture is inconsistent REGARDLESS of sha pins — a
  pin freezes current bytes, not pair coherence. RE-RUN this comparison
  whenever any member's pin/revision is refreshed (a crash-fix round
  re-pinning one member re-opens the check). On a failure, either (1)
  re-capture / regenerate the DEPENDENT artifact under the current input,
  or (2) pin the input at the pre-regeneration REVISION the capture was
  made under (`hf_hub_download(..., revision=<capture-era commit>)`) —
  (2) only after confirming WHY the input was regenerated (a bug-fix
  regeneration invalidates the old input, forcing (1)). A documented
  remedy-(2) pin PASSES this check: the probe runs at the consumed
  revision, so pinning the pre-regeneration revision restores coherence
  by construction. A pair uploaded in one commit passes trivially.
  (Incident #922 r4, att-20260703-163130: #779's question artifacts were
  regenerated — HF commit 9578892ef4, 2026-07-02 — AFTER the dependent
  `cx.pt` activation capture — a8060198a4, 2026-07-01; every prior check
  passed on each member individually and the run crashed at the parity
  assert after a full GCE cycle. Sibling class: the #601 pinned-pair
  COVERAGE mismatch —
  `.claude/agent-memory/experiment-implementer/feedback_pinned_artifact_pair_mutual_inconsistency.md`.)
```

### 11. Decision Rationale

- **Why `get_paths_info(..., expand=True)` for the ordering probe.** What: per-path last-commit dating. Why: it is the only Hub-API call that returns per-path `last_commit` without enumerating the repo tree — safe on the ~1M-file data repo where `list_repo_files` wedges (>90 s, #833). Source: live probe (`issue779_monitoring/r_b/evil.pt → ('97050c185a', 2026-07-01 10:53:01+00:00)`, 0.5 s) + gotchas.md #833 bullet. Alternatives: `list_repo_commits` (repo-level, needs client-side path filtering — slower, more code); relying on the artifact's own `reconstruction` metadata alone (not all artifacts carry one — #922's did, but the date comparison is the universal floor; the metadata read is kept as the AND).
- **Why per-storage-location grouping + per-repo calls (v2, round-1 binding fix).** What: the recipe's first step groups members by (repo_id, repo_type, consumed revision) and calls the API once per repo. Why: the pair's members routinely span stores — adapters/checkpoints live in the model repo, mixes/raw buckets in the data repo, judge/eval JSONs in git (artifact-reuse.md's own repo topology) — so a single-call two-path form cannot execute for 2 of the 3 named pair classes (mix↔adapter cross-repo; pool↔judge-outputs with a git member). Source: round-1 Alternatives reconciler (binding), grounded on artifact-reuse.md:19-39.
- **Why the folder max-member-date reduction over the exact consumed file set.** What: multi-file members (adapter subfolders) probe every consumed member file (or a named manifest) and take the max date. Why: `get_paths_info` requires FILE paths (400 on directories — live-probed), and an unprobed sibling can be the regenerated file. Source: round-1 Statistics reconciler absorb clause + the live 400 probe.
- **Why revision-scoped probing (v2, round-1 binding fix).** What: every probe runs at the revision the consumer will actually fetch (`revision=` kwarg; git members at the consumed ref). Why: remedy (2) pins the input at the pre-regeneration revision — under a default-`main` probe that input's last_commit is the regeneration commit forever, so a correctly-remediated plan would false-BLOCK indefinitely; probing the consumed revision makes the check self-consistent with its own remedy. Source: round-1 Statistics reconciler (binding); `revision=None` kwarg confirmed in the verified signature (§12.1).
- **Why last-commit-DATE comparison (input ≤ capture).** What: the coherence predicate (v2: max(input member dates) ≤ min(capture member dates)). Why: it is exactly the signal that would have caught #922 (input commit 2026-07-02 > capture commit 2026-07-01), it needs no artifact-format knowledge, and same-commit pairs pass trivially. Commit time is a PROXY for production time — the (j) text carries the caveat both directions (a capture-side re-commit is not proof of regeneration under the new input; a byte-identical input re-upload can false-fire, routing to the cheap investigate branch). Source: the #922 incident record + round-1 Statistics/Methodology concerns. Alternative: content-level parity asserts at plan time — rejected as the general mechanism because they require downloading + format-specific parsing per pair class; the pod-side parity assert remains the runtime backstop (it's what caught #922, one GCE cycle too late).
- **Why these named pair classes (bank↔capture, mix↔adapter, pool↔judge-outputs).** What: the (j) trigger scope. Why: they are the project's three recurring produced-under dependencies — #922 hit bank↔capture; mix↔adapter is the (d)/(h) reuse surface; pool↔judge-outputs is the #810 cache-class sibling. The v2 recipe handles all three storage shapes (cross-repo, folder, git-resident). Source: incidents #922, #734, #810; artifact-reuse.md items (d)/(h) enumerate the same artifact families.

Why: they were deliberately worded range-free at #871 precisely so a future letter needs no remedy re-edit, and a (j) failure IS a regenerate-class failure. Source: `reference_reuse_fitness_mirror_set.md` ("Every remedy-split line … deliberately worded WITHOUT a lettered range") + #871 commit `69719541a5`.
