## 2. Decision + rejected alternatives

**Chosen direction — hybrid: corridor-max instance fix (all four grandfathered
docs) + two narrowly-scoped class improvements that make the trip-wire cheap
and self-attributed (remedy-bearing FAIL message; edit-time warn-only hook).**
The instance fix buys the mechanical maximum breathing room (~2.7 KB ≈ one
fleet-day at the measured burst rate; the 7-raise ladder averages ~2–4 KB/day
steady). The class improvements change what the NEXT trip costs: today it
costs a full implementation round + a ~13–30-min Step 9c gate + chronicle
archaeology to learn the remedy; after this change it costs a few seconds at
edit time (hook) or one mechanical line copied from the FAIL message itself
(message fix). Neither class improvement touches the ratchet's FAIL/WARN
*conditions* — only messages and an advisory side channel — which is what
keeps the blast radius defensible on the fleet's shared gate.

**Rejected — slim `.claude/skills/issue/SKILL.md` (body option 1).** Slimming
can buy at most 3,000 − 813 = 2,187 B of additional margin before the
loose-cap arm forces a ratchet-down (clarifier correction 1) — under one day
at the measured growth rate — while carrying the largest risk surface of any
option: relocations must preserve always-on summaries + pointers, region-
anchored lint pins on SKILL.md text can break when text moves (e.g.
`--check-smoke-blind-spot-review-lens`; `tests/test_step10d_guard3.py:1560`
pins the literal "Size-ratchet cap bumps are computed from landing bytes
(#1753)" in a SKILL.md region), review load on the repo's most load-bearing
skill is maximal, and the branch dirties the `workflow` family so the Step 5a
spec sync skips it. Worst margin-per-risk ratio on the table; and it does
nothing for the class.

**Rejected — cap raise alone (body option 2 as the whole fix).** Necessary
(and included) but insufficient: with a ≤3,000 B corridor and measured growth
of 3,219 B in one 5-hour window, the raise alone re-creates today's state
within roughly a day, and the next session to trip the cap pays the same
late-discovery cost. The cap ladder has been raised seven times in-lineage
(950_300 → … → 983_400) without changing that cost; an eighth raise with no
class change is the definition of the treadmill.

**Rejected — migrate `SKILL_DOC_SIZE_GRANDFATHER` to a line-mergeable data
file (the #1718 `agent_spec_size_caps.txt` mirror).** Priced and rejected on
three grounds. (i) The #1718 win was that concurrent sessions raising caps on
DIFFERENT agent files edit different lines; skill-doc cap churn is
overwhelmingly a SINGLE key — all seven chronicle raises are
`"issue/SKILL.md"` — and two sessions raising the same key conflict on the
same line in a data file exactly as in the module. (ii) The migration REQUIRES
declaring the new import-time data file in the Step 5a SPECS/FAMILY_OF lists
inside `.claude/skills/issue/SKILL.md` (workflow_lint.py L14635-14637: "any
NEW import-time data file added to this module must be declared there too, or
worktree syncs strand it (#2293)"; the declarations live at SKILL.md L2529,
L2538, L13512, L13517) — i.e. it spends bytes of exactly the file whose
headroom is the problem, or forces a riskier pathspec-widening rewrite of
load-bearing sync lines. (iii) The one #1718 benefit that does transfer —
chronicle-out-of-module, history in git log — is captured far more cheaply by
the in-place chronicle trim in §3. Revisit trigger: if the grandfather set
grows or cap churn spreads across many skill files, the migration becomes
worth its cost; the #1718 contract (module attribute keeps its name +
`dict[str, int]` type) makes it a drop-in later.

**Rejected — last-toucher attribution of the size FAIL (body option 3 as
stated).** The clarifier falsified its premise: the cross-session collateral
is already mostly absorbed (Step 9c known-red stripping is node-level; the
no-flags run is not a pre-commit hook), so the harm attribution would fix —
"every other session goes red" — is not the harm that exists. The dominant
harm is the tripping session's own late discovery, and attribution machinery
(git-blame semantics inside a lint that must stay hermetic and fast) is a
large, fragile change that buys nothing against that. The hook + message fix
deliver self-attribution at strictly lower cost.

**Explicitly out of scope (named follow-up candidates, not landed here):**
extending the edit-time hook to `.claude/agents/*.md` (the agent-spec ratchet
has the same trip-wire shape; ~3-line generalization, but new noise/test
surface — file as a follow-up if wanted); any change to
`SKILL_DOC_WARN_BYTES` / `SKILL_DOC_FAIL_BYTES` /
`SKILL_DOC_GRANDFATHER_MAX_HEADROOM_BYTES` (pinned at 40_000 / 60_000 / 3_000
by `test_threshold_literals_pinned`; changing the corridor width is a policy
decision this task does not need).

## 5. Blast-radius analysis

The no-flags run is the Step 9c gate for every session; the two failure
directions and what bounds each:

- **False FAIL (fleet wedge).** The cap raises can only convert FAIL→WARN —
  a raise within the hygiene corridor cannot create a new FAIL on any tree
  where the file is at or below the new cap; the only FAIL a raise can create
  is the loose-cap arm on a tree whose file is >2.8 KB SMALLER than our
  Step 10d measurement — impossible on the merged tree we measure (we assert
  it in-round via `test_live_grandfather_caps_have_sane_headroom`), and
  possible later only via a large net trim, which is the trimming session's
  designed ratchet-down duty, self-attributed in its own gate. Edit 3 touches
  only an f-string inside the already-failing branch: a defect there surfaces
  as a wrong MESSAGE on an already-red condition, caught by the new
  substring test in our own gate. The hook is structurally incapable of
  wedging anything: PostToolUse cannot block the already-run tool; every error
  path exits 0; the kill switch disables it per-session; worst realistic cost
  is ~2 s latency + one stderr paragraph on skill-doc edits. The riskiest
  single edit is `.claude/settings.json` (a malformed JSON degrades ALL hooks
  fleet-wide): mitigated by JSON round-trip editing, an in-round parse assert,
  and the registration pin test.
- **False PASS (silently retired ratchet).** No FAIL/WARN condition, constant,
  or threshold changes; the caps stay within the 3,000 B hygiene bar, enforced
  live by the loose-cap arm and `test_live_grandfather_caps_have_sane_headroom`
  (which asserts `cap > FAIL`, `size > FAIL`, `cap − size ≤ 3,000`,
  `size ≤ cap` for every entry on the real tree). The ratchet cannot be
  retired by this change set without those going red in the same round.
- **Same-round detectability.** Everything lands and is verified in ONE
  branch round: the live-tree tests + no-flags run exercise the real caps; the
  new tests exercise the new message + hook; Step 9c runs the union on the
  merged tree before the merge lands. There is no delayed-activation surface

## 9. Ordering / concurrency

`.claude/skills/issue/SKILL.md` is edited by many concurrent sessions and
`scripts/workflow_lint.py`'s grandfather region is edited by every concurrent
cap-raiser. Survival design:

1. **One branch, one commit-set, standard /issue worktree flow.** All seven
   files land together; the cap values are recomputed at Step 10d against the
   merged tree (formula, not judgment), and re-recomputed on EVERY merge
   attempt if the gate round is re-entered — the chronicle's own
   "re-measure per merge attempt" lesson (L15198-15204) is adopted as a step,
   not a hope.
2. **Sibling lands SKILL.md growth mid-round:** absorbed silently up to
   ~2.7 KB by the corridor-max caps (the plan-time values already tolerate
   +2,713 B on issue/SKILL.md before recomputation is even needed); beyond
   that, `test_live_grandfather_caps_have_sane_headroom` goes red in OUR gate
   and the formula is re-applied. Never a fleet-side red: main stays green
   under its old cap until our merge, and our merge carries caps measured on
   the merged tree.
3. **Sibling raises the same cap line mid-round (the moving-main class):**
   one-line textual conflict at our Step 10d merge; resolution rule is
   mechanical — re-apply the formula to the merged tree's measured size (our
   corridor-max result is ≥ any landing-bytes(+1–1.2 KB) sibling value for the
   same or smaller measured size; if the sibling measured LARGER, the formula
   on the merged tree dominates both). The Edit-2 chronicle trim conflicts in
   the same region are comment-only and resolved by keeping the trimmed
   preamble + the sibling's value folded into the per-entry one-line comment.
4. **Sibling trims a grandfathered file mid-round:** our caps then sit up to
   ~2.8 KB + trim above live size; if that exceeds 3,000 B the loose-cap arm
   reds OUR gate at Step 10d re-measure → formula re-applied (lower). Same
   mechanical loop.
5. **settings.json concurrency:** hooks edits are rare; the JSON round-trip
   edit is applied at Step 10d on the merged tree if a conflict appears;
   the registration pin test re-verifies after any resolution.
6. **No repo-root dirty state:** all edits happen in the issue worktree and
   merge via the standard Step 10d path; nothing in this change set writes to
   the shared root outside a commit window.
