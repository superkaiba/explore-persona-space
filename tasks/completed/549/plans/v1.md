# Plan — Task #549: Audit historical multi-checkpoint vLLM evals for the #534 `lora_int_id` cache-collision bug

**Kind:** analysis (CPU-only audit — no training, no pod, no GPU). **Parent:** #534 (archived, clean-result promoted).

## 0.0 TL;DR (plain English)

- **What I'll run:** a code-and-records audit, no GPUs. The parent task found that our eval harness can silently score the *wrong* model: vLLM identifies fine-tuned adapters by an integer id, and when two different adapters get the same id in one process, the second request is served the first adapter's weights without any error. I'll list every script that ever loaded adapters into vLLM, work out which historical runs could have hit this, and check each one against the actual files those runs left behind.
- **What I expect:** most runs are fine — they either gave every adapter its own id or used one adapter per process. During planning I already found the two interesting cases: (1) the bug-fix from the parent task never made it onto the main branch, so a fresh checkout still runs the broken code; (2) one published experiment (#532) evaluated epoch-1 and epoch-2 adapters in a single process with ids that repeat across epochs — but its cache only held one adapter at a time, so the repeats were probably flushed out before they could collide, and its published headline used only the epoch-1 numbers anyway, which loaded first and were correct either way.
- **What would change my mind:** a replay of the actual adapter-request order through a small cache simulator showing a repeat-id request landed while the old adapter was still cached — or epoch-2 outputs that are word-for-word identical to epoch-1 outputs for the same prompts (greedy decoding means same served adapter ⇒ same text), which would mean the wrong adapter really was served.

3. **LRU replay (new code, ~40 lines):** `scripts/i549_lru_simulate.py`, mirroring `vllm/lora/worker_manager.py:240-267`:

```python
from collections import OrderedDict

def simulate(requests: list[tuple[int, str]], capacity: int) -> list[dict]:
    """Replay (lora_int_id, lora_path) requests through vLLM's id-keyed LRU registry.

    Mirrors LRUCacheWorkerLoRAManager.add_adapter (vllm 0.11.0,
    lora/worker_manager.py:240-267): hit => 'just touch' (path NOT re-read);
    miss => load from path, evicting the oldest entry at capacity.
    """
    cache: OrderedDict[int, str] = OrderedDict()  # id -> path actually loaded
    out = []
    for lora_id, path in requests:
        if lora_id in cache:
            served = cache[lora_id]
            cache.move_to_end(lora_id)
        else:
            if len(cache) >= capacity:
                cache.popitem(last=False)
            cache[lora_id] = path
            served = path
        out.append({"id": lora_id, "requested": path, "served": served,
                    "stale": served != path})
    return out
```

Capacity = the engine's `max_cpu_loras` (defaults to `max_loras`, `vllm/config/lora.py:116-117`). Verify in the installed source which registry `list_adapters()` consults and what its `capacity` binds to (grep `def capacity` / `max_cpu_loras` in `vllm/lora/models.py`); if GPU-slot (`max_loras`) vs CPU-registry (`max_cpu_loras`) capacities could give different verdicts for some run, replay under BOTH — any disagreement ⇒ INDETERMINATE, never a silent pick.
