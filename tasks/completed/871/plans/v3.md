## 11. Decision Rationale

**Training hyperparameters:** N/A — no model training (`kind: infra` doc change).

The design decisions worth rationale rows:

- **What (item (i) content):** two checks — (1) inner per-cell/per-fold/per-draw axis
  batched, (2) device parametrized (no hardcoded module constant); remedy = fix at the
  SOURCE module, scheduled in the plan (own phase or companion task, source fix lands
  first), then reuse; record the inspection (function name, batched-or-serial, device
  handling) in the plan's reuse map + §9 row; scoped to reused CODE, N/A for data-only
  reuse; binds at PLAN time only.
- **Why these two checks:** they are exactly the two failure modes the four incidents
  exhibit — serial inner loops (#761 `_ridge_predict_loco` over 50 LOCO folds → ~100x
  over plan; #667 `fit_cell` per-cell 300-epoch MLP × 84 cells) and hardcoded device
  pins (#763/#812 inheriting `issue658_fit_predictors.py:143`'s `DEVICE = "cpu"`,
  batched-but-on-CPU until the `EPM_FIT_DEVICE=cuda` cutover). No incident in the set
  needed a third check.
- **Why source-module-fix-first, with a scheduling clause:** a caller-side workaround
  leaves the trap armed for the NEXT reuser — the incident sequence itself (#761 then
  #667 then #763 then #812) is four downstream tasks independently rediscovering the
  same source-module defects; fixing at the source is the only remedy that terminates
  the sequence. The scheduling clause (own phase / companion task, the #876 pattern,
  source fix lands BEFORE the consuming run) makes the remedy executable rather than
  aspirational — consistent with the code-style "Supersede → delete the old version"
  and the built-but-stranded lesson (a fix not landed at the running path changes
  nothing).
- **Why the remedy-split lines avoid any lettered range (MF3):** "a failing check
  other than (i)" wording keeps the §6 stale-range grep satisfiable (a literal
  "(a)-(h)" in the new remedy line would be a self-inflicted stale hit) and is
  future-proof — a later (j) needs no re-edit of the remedy sentences. Rewording
  preferred over an exemption-table escape (keeps acceptance criterion 2 clean).
- **Why widen critic item 9's gating machinery, not just its REVISE list (MF1):** 3 of
  the 4 driving incidents are code-only reuse with no HF artifact cited; an
  artifact-keyed trigger ("records a reused artifact in §10/§11") plus an
  artifact-keyed no-fire cross-check would leave the new enforcement clause
  unreachable on exactly the incident population that motivated it (the inert-rule
  failure mode). The inline enumeration reaches (i) by POINTER to the rule file —
  duplicating the item's text would violate the single-operational-copy principle
  (#829).
- **Why scoped to reused CODE (not data artifacts):** a data artifact (adapter, JSONL,
  eval JSON) has no inner loop or device; throughput character is a property of code
  paths only, and the existing checks already govern the data/model side.
- **Why the plan-time-only scope note:** inline/ad-hoc analyses with no plan are
  covered by `vectorize-many-cell-fits.md` (code-time) + the review-side #869 Fix D
  checks; without the note, the item could be misread as terminating the code-reuse
  class or as claiming coverage of unplanned work it cannot reach.
- **Why POINT at vectorize-many-cell-fits.md rather than duplicate:** single
  operational copy principle (the same reason #829 collapsed planner.md step 5 into
  artifact-reuse.md); the vectorize rule owns the signature, the fix recipe, and the
  canonical helpers, and it evolves independently (#869 is widening it right now).
