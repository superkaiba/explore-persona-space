# Plan — #1490: GCP queue-vanish failover must launch workload + re-point handle or tear down pod

## 0.0 TL;DR (plain English)

- **What I'll change:** when the GCP→RunPod failover's RunPod launch fails *after* `pod_lifecycle.py provision` already created a pod, the failover will now detect the just-created pod (live-API probe before/after the launch), terminate it surgically by pod id, and only then return the terminal JSON — plus a small alert-only watcher arm that flags any RUNNING `pod-<N>` whose run handle still points at GCP past a 30-minute grace.
- **What I expect:** the #1417 shape (idle 4×H100 billing forever + a stale `backend=gcp` handle, human cleanup 45 min later) becomes impossible from this path: either the workload launches and the handle re-points (already built, #954/#659), or the pod is gone within the same poll tick; the rare residue (terminate API failure, process crash mid-window) gets a non-re-drivable terminal naming the pod and/or a watcher alert within ~30-50 min.
- **What would change my mind:** if investigation during implementation shows `cmd_provision` can leave >1 live pod matching `pod-<N>` in normal operation (making pod-id attribution unsafe), I fall back to alert-only for the ambiguous cell — the decision table below already routes ambiguity to "never terminate."

### What is ALREADY implemented (Goal items 1-2 — verify, don't rebuild)

- **Launch-verify (item 1):** `_execute_workload_on_pod` (runpod.py L679-786) verifies in three fail-loud steps — (a) branch sync must print `SYNC-OK <sha>`, (b) detach must print `WRAPPER-STARTED` (with an `ALREADY-RUNNING` double-fire guard), (c) a **separate** SSH invocation after `WORKLOAD_VERIFY_DELAY_SECONDS` must match `_LAUNCH_OK_RE` (pid from the pidfile) — any failure raises `RunPodWorkloadStartError` with the partial handle attached (runpod.py L1086-1099, #954).
- **Handle re-point (item 2):** the failover core's authoritative post-route `write_handle_sidecar` + `read_handle_sidecar` readback with `recovered.backend != "runpod"` fail-loud (backend_poll.py L3430-3479, #659 MF4); the #954 partial path re-points at the partial handle and emits the distinct non-re-drivable `runpod_workload_start_failed` terminal (L3314-3341, L3481-3504); on sidecar-write failure the sentinel is persisted so no second paid launch fires (L3438-3474). - **Surgical-terminate precedent:** the #770 wedge failover and #775 CUDA-IMA failover both terminate via lazy `from runpod_api import get_pod_by_name, terminate_pod` + `terminate_pod(info.pod_id)` (backend_poll.py L2221-2227, L2399-2404) — pod-id-scoped, bypassing `cmd_terminate`'s issue-wide guards by design.
- **Why NOT `pod_lifecycle.py terminate` for the cleanup:** `cmd_terminate` (pod_lifecycle.py L2695) runs the #1485 keep-running shield and `_guard_upload_verification_before_terminate` (L2469-2557), which raises `SystemExit` for a `kind: experiment` task without an `epm:upload-verification PASS` marker — a just-provisioned never-ran pod has none, so the bare form would refuse and need `--skip-upload-verify`, and the issue-wide form could collaterally hit suffixed follow-up pods. The raw `terminate_pod(pod_id)` precedent avoids all of this; the resulting stale pods.conf/pods_ephemeral rows are self-healing (`_load_state` Branch-2 live-API reconcile, `.claude/rules/pod-config.md`).
- **`cmd_provision` idempotency (attribution baseline):** provision REFUSES (exit 1) when a non-EXITED pod exists under the canonical or legacy name (pod_lifecycle.py L1885-1909) — so when provision proceeded to create, no live `pod-<N>` pre-existed; and when provision fails *because* a pod pre-exists, that pod must never be torn down. Both facts drive the pod-id set-difference design in §3.
- **Constraint-relevant semantics preserved:** #1116 queue-vanish trigger, #783 queue-timeout teardown-first, #1029 boot-loop, #658/#659 workload failover — the fix touches ONLY the `except NoComputeAvailableError` branch of the shared core + adds a pre-launch probe; when the failover fires is unchanged.

## 3. Design

### D1 — Transactional provision-residue reclaim in `_failover_gcp_to_runpod` (backend_poll.py)

Two new module-level helpers (near `_terminal_infra_json`, following the lazy-`runpod_api`-import pattern of L2223):

```python
RUNPOD_PROVISION_LEAKED_REASON = "runpod_provision_leaked_pod"

def _live_runpod_ids_for_issue(issue: int) -> set[str] | None:
    """Live pod_ids whose name is EXACTLY pod-<issue> (suffixed pods excluded).

    Returns None on any API failure (probe-unknown; callers bias SAFE).
    One GraphQL list call; failovers are rare events.
    """
    try:
        from runpod_api import list_team_pods  # lazy; scripts/ on sys.path (L160 helper)
        name = f"pod-{int(issue)}"
        return {p.pod_id for p in list_team_pods() if p.name == name}
    except Exception as exc:
        logging.warning("backend_poll: provision-residue probe failed (%s: %s)", ...)
        return None

def _reclaim_failed_runpod_provision(*, issue: int, pre_ids: set[str] | None,
                                     cause_label: str, failover_tag: str) -> dict:
    """Best-effort reclaim of a pod the JUST-FAILED failover provision created.

    Never raises. Returns {"outcome": "no-residue" | "torn-down" | "pre-existing"
    | "leaked", "pod_ids": [...], "detail": str} per the decision table below.
    """
```

Decision table (implemented in `_reclaim_failed_runpod_provision`; `post_ids = _live_runpod_ids_for_issue(issue)`):

| post_ids | pre_ids | new_ids = post − pre | action | outcome |
|---|---|---|---|---|
| `set()` | any | — | none | `no-residue` |
| `None` (probe failed) | any | unknown | none (bias safe) | `no-residue` (detail notes probe failure) |
| non-empty | `None` (pre-probe failed) | unattributable | **none** — never terminate what we can't attribute | `leaked` |
| non-empty | known | `len(new_ids) == 1` | `terminate_pod(id)` (lazy import, wrapped try/except) | `torn-down` on success, `leaked` on raise |
| non-empty | known | `len(new_ids) == 0` | none — pod(s) pre-existed this failover | `pre-existing` |
| non-empty | known | `len(new_ids) > 1` | none — concurrent creator ambiguity | `leaked` |

Wiring inside `_failover_gcp_to_runpod` (exact edit points):

1. **After** the `teardown_first` block / `spec = _runspec_from_gcp_handle(...)` (L3282) and **before** the `try:` at L3284, add: `pre_provision_ids = _live_runpod_ids_for_issue(issue)`.
2. Replace the body of `except NoComputeAvailableError:` (L3342-3354) with:

```python
except NoComputeAvailableError:
    reclaim = _reclaim_failed_runpod_provision(
        issue=issue, pre_ids=pre_provision_ids,
        cause_label=cause_label, failover_tag=failover_tag,
    )
    if reclaim["outcome"] == "leaked":
        # A pod exists and bills but could not be reclaimed/attributed. Do NOT
        # return the re-drivable no_compute_available (the #931/#954 mislabel:
        # the watcher would re-drive while the pod bills). No lease stamp.
        return _terminal_infra_json(
            issue=issue, sidecar=sidecar, reason=RUNPOD_PROVISION_LEAKED_REASON,
            log_tail=(
                f"{cause_label} on {handle.pod_name}; RunPod fallback launch FAILED and a "
                f"live pod-{issue} remains ({reclaim['detail']}); NOT watcher-re-drivable. "
                f"Recovery: inspect + `uv run python scripts/pod.py terminate --issue {issue} --yes` "
                f"(add --skip-upload-verify for a never-ran pod), then re-dispatch ({failover_tag})"
            ),
        )
    # no-residue / torn-down / pre-existing: today's re-drivable terminal, now safe
    # (no unattended pod created by THIS failover is left billing).
    return _terminal_infra_json(
        issue=issue, sidecar=sidecar, reason="no_compute_available",
        log_tail=(
            f"{cause_label} on {handle.pod_name}; RunPod also unavailable "
            f"({failover_tag}; provision-residue: {reclaim['outcome']}"
            + (f" — {reclaim['detail']}" if reclaim["outcome"] != "no-residue" else "")
            + ")"
        ),
    )
```

Notes:
- The success path, the #954 `RunPodWorkloadStartError` partial path, the idempotency short-circuit, and the `teardown_first` GCP teardown are **byte-untouched** — this preserves #659/#783/#1029/#1116/#954 semantics exactly (the existing `test_failover_seam_default_reason_unchanged_byte_for_byte` family keeps pinning the seam).
- No lease/sentinel stamp on either new branch (matching today): after `torn-down` a later tick may legitimately retry the failover against a clean slate; after `leaked` the task parks at `blocked` on the non-re-drivable reason, so retry ticks are moot.
- The sidecar deliberately stays `backend=gcp` on these branches: there is no runpod handle to point at (launch never returned one), the terminal JSON parks the run, and any re-drive is a fresh dispatch that rewrites the sidecar. "Never leave the stale gcp handle **silently** authoritative" is satisfied by the terminal + the D2 watcher arm; with the pod torn down the stale handle is inert.
- Pod-name derivation: `f"pod-{int(issue)}"`, matching `_runpod_pod_name` (runpod.py L921) and `_canonical_pod_name` (pod_lifecycle) for the suffix-less failover path. Exact-name match excludes `pod-<N>-<slug>` follow-up pods by construction.
- Why the poller core and not `RunPodBackend.launch` or the router rung (rejected alternatives): (i) backend-side cleanup would also fire on the *interactive* `dispatch_issue.py --backend runpod` orchestrator-attended path, removing the documented "Pod is up but not experiment-ready — re-run bootstrap" recovery affordance the provision stderr advertises; (ii) the rung would need the same probes threaded through two lane callers; (iii) the poller core is the single seam ALL five unattended async failover paths share, matches the Goal's scope exactly, and is where the terminal-JSON labeling decision already lives. The sync capacity-path residue (a route()-time RunPod rung provision failure during an attended `dispatch_issue.py launch`) is a documented non-goal — the exception surfaces immediately in the launch command's output with the pod named in the stderr tail.
- The #909 hydra-args provision-only residual (failover of a hydra run provisions a pod and executes nothing, logged LOUD) is out of scope and unchanged — it is a *successful* launch with a re-pointed handle, not this defect class; noted here so the critic doesn't conflate them.

### D2 — Alert-only orphan guard in the watcher pod-safety pass (autonomous_session_watch.py)

**Home decision:** the watcher's pod-safety pass — NOT the poller (it only runs while the poll loop is alive, which is exactly when D1 already handles the class; the residual — process crash mid-window, terminate API failure — is by definition a dead-or-parted poller), and NOT `pod_audit.py` (daily cadence, EXITED>24h grain, no sidecar knowledge). The pass already enumerates RUNNING managed pods every 10 min with task status, `keep-running`/follow-up exemptions (`_escaped_pod_exemptions`), per-pod state (`_load_pod_safety_state` / `_save_pod_safety_state`, L7355+), and once-per-episode alert plumbing — the cheapest correct home.

**Scope decision:** ALERT-ONLY, not auto-terminate. Post-D1 the class is reachable only via (a) `terminate_pod` API failure — already surfaced loudly by the `runpod_provision_leaked_pod` terminal naming the pod — or (b) a poller crash between provision and reclaim. Auto-terminate would need #770-grade safety machinery (tri-state keep-running read, provable-safety gates, bounded-once lease) that is disproportionate for a rare residual, and the false-positive cost is the #488 class (killing a live manual/diagnostic pod). An alert costs one push.

New helper `_maybe_flag_orphan_gcp_handle_pod(issue, info, now, keep_running, followup_active, prev_state, dry_run) -> bool` (returns whether it alerted; NEVER handles/returns-early — purely additive), called in `_process_pod` after `_escaped_pod_exemptions` (L9344) and before the status-class decision, falling through unconditionally:

Predicate (ALL must hold):
1. `info.name == f"pod-{issue}"` (bare canonical name — the only name the failover provisions; suffixed follow-up pods excluded).
2. The handle sidecar resolves (`resolve_handle_sidecar_path(issue)` — the same helper the wedge arm uses at L6833/L8153) and `read_handle_sidecar(path).backend == "gcp"` (any read/parse failure → no alert, bias quiet).
3. `now - first_seen >= _orphan_gcp_handle_grace_sec()` (new constant `ORPHAN_GCP_HANDLE_GRACE_SEC = 1800`, env `EPM_ORPHAN_GCP_HANDLE_GRACE_SEC`, read call-time like `RUNPOD_WEDGE_K_SEC`), where `first_seen` is the existing per-pod-incarnation clock in the pod-safety state.
4. `not keep_running and not followup_active` (the documented shields for deliberate parallel pods).
5. `not prev_state.get("orphan_gcp_noted")` (once-per-pod-incarnation dedup; new boolean state field following the `alerted`/`keep_running_noted` `_CARRY` conventions in `_save_pod_safety_state`, reset on pod_id change like the wedge clock).

Action: one alert via the pass's existing stale-pod alert mechanics (same log + fail-soft push channel `_process_pod` already uses), naming the pod, the stale `backend=gcp` sidecar, the age, and the recovery command (`pod.py terminate --issue <N> --yes`, `--skip-upload-verify` note for a never-ran pod); set `orphan_gcp_noted=True`. No terminate, no stop, no status mutation, no marker-schema change.

Deliberately NO GCP-side liveness probe (no `gcloud describe`): a RUNNING bare `pod-<N>` coexisting with a gcp-pointing handle is anomalous whether or not the GCP instance is alive — an untracked RUNNING pod deserves surfacing either way, keep-running is the documented shield for deliberate keeps, and the probe would add a gcloud dependency + latency to every watcher tick for a rare arm.

Load-bearing constants introduced (What / Why / Source / Alternatives):

- **`ORPHAN_GCP_HANDLE_GRACE_SEC = 1800` (env `EPM_ORPHAN_GCP_HANDLE_GRACE_SEC`).** Grace before the watcher flags a RUNNING bare `pod-<N>` with a gcp sidecar. Why: must exceed the healthy failover's create→bootstrap→execute→sidecar-re-point window (bootstrap ~5-15 min; wait-for-capacity runs pre-create so it never counts against pod age) with ~2× margin. Source: the `RUNPOD_WEDGE_K_SEC = 900` sizing convention (#664/#692 — "above bring-up + retry margin"), doubled because bootstrap is longer than port bring-up; env-overridable call-time read mirrors `_gcp_queue_wait_seconds` (#783). Alternatives: 900 s (rejected — inside a slow bootstrap's window, false-positive pushes); a dedicated onset clock like `wedge_first_seen` (rejected — the predicate is static per pod incarnation, so the existing `first_seen` is the right clock).
- **`RUNPOD_PROVISION_LEAKED_REASON = "runpod_provision_leaked_pod"`, NOT in `TRANSIENT_CAPACITY_REASONS`.** Why: a re-drivable label on a run whose pod bills unattended invites the watcher's capacity-retry churn — the exact #931 mislabel #954 fixed for the workload-start case. Source: #954's `runpod_workload_start_failed` precedent (router.py L390 comment + test_backend_poll.py L1950). Alternative: reuse `runpod_workload_start_failed` (rejected — that reason's log contract asserts a re-pointed sidecar + diagnosable pod; here neither holds).
- **Surgical `terminate_pod(pod_id)` instead of `pod_lifecycle.py terminate`.** Why: pod-id scope cannot collaterally hit suffixed/follow-up pods; bypasses the upload-verify + keep-running guards that would refuse (nothing ever ran on the pod, so there are no artifacts the upload-verify guard protects). Source: #770 `_failover_wedged_runpod` + #775 CUDA-IMA failover (backend_poll.py L2221-2227, L2399-2404 — the in-file precedent). Alternative: `cmd_terminate --skip-upload-verify` (rejected — issue-wide scope + guard overrides are a bigger hammer than the surgical id kill).
- **Alert-only watcher arm (no auto-terminate).** Why: post-D1 the class is a rare residual; auto-terminate requires #770-grade provable-safety machinery and risks the #488 kill-a-live-manual-pod class. Source: #770's ALERT-by-default design + the #488 incident; the task body's own "the guard may be a small cheap backstop" scope release. Alternative: #770-style bounded terminate (rejected for scope; named as the escalation path if the alert fires repeatedly in practice).
- **Pre/post pod-id set-difference attribution.** Why: "a pod exists after failure" alone cannot distinguish our residue from a pre-existing pod (which cmd_provision's refusal makes the likely *cause* of some failures) — terminating a pre-existing pod is the catastrophic false positive. Source: cmd_provision idempotency semantics (pod_lifecycle.py L1885-1909); the sidecar-binding defense precedent (#770 r2 CRITICAL #2 — never terminate what you can't bind to the observed failure). Alternative: single post-probe `get_pod_by_name` (rejected — unattributable; also ambiguous when an EXITED pod pre-exists and a second same-name pod is created).
