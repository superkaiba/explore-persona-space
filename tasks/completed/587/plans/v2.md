## 3. Design

### 3.1 Stage model

Canonical machine sequence (fixed): `planning → plan_pending → approved → running → verifying → interpreting → reviewing`, terminal target `awaiting_promotion` (= 100%). **Allowlist rule: any status that does not resolve to one of these 7 stages gets NO bar, NO suffix, NO snapshot row** (covers `shared`, `done_experiment`, `done_impl`, and any future addition by construction).

```python
LEGACY_STAGE_MAP = {
    "awaiting_approval": "plan_pending",
    "queued": "approved",
    "implementing": "running",
    "code_reviewing": "running",
    "testing": "running",
    "uploading": "verifying",        # defensive only — zero observed occurrences anywhere
    "under_review": "reviewing",     # defensive only — zero observed occurrences anywhere
    "clean_result_drafting": "reviewing",
}
```

**Scanning scope (fact-check corrected):** legacy statuses (`queued` ×47, `implementing` ×27, `clean_result_drafting` ×45, etc.) occur ONLY in legacy `state_changed` marker rows (330 rows, older schema, millisecond ISO timestamps) — NEVER in `epm:status-changed` rows (1361 rows, all canonical statuses). The stats scanner reads **`epm:status-changed` rows only**; legacy `state_changed` history is **deliberately excluded**. `LEGACY_STAGE_MAP` is retained purely as a cheap defensive normalization applied to any `to` value encountered — expected no-op; it exists so a surprise legacy value degrades to the right canonical stage instead of being mis-skipped. Confirmed noise handled below: 98 `null→null` rows; backward transitions `awaiting_promotion→reviewing` ×2, `plan_pending→planning` ×14.

**Stage-duration sample definition:** a contiguous interval that *enters* stage S (an `epm:status-changed` with `to ∈ stage(S)`) and *exits forward* (next `epm:status-changed` with `to` mapping to a LATER canonical stage or `awaiting_promotion`/`completed`). Intervals exiting to `blocked`, a backward stage, or `archived` are **excluded** (they measure stuckness/abandonment, not stage cost). Rows with non-status `from/to` (null, unknown strings) are skipped. **Censoring direction (documented in module docstring + chip tooltip):** this exclusion — plus restarting intervals on re-entry — makes every stat optimistic relative to lived history. The displayed estimand is "typical clean forward pass"; the `overdue` state (§3.4) is what covers the non-clean passes the stats deliberately exclude. (Magnitude, measured: `running` drops 60 excluded spans vs 135 included; multi-attempt tasks can total 10-15× their counted clean fragment.)

### 3.2 Stats (recency-windowed, kind-bucketed)

- Scan terminal-ish tasks: `tasks/{completed,archived,awaiting_promotion}/*/events.jsonl` (379 dirs, 33.1MB → measured; <10s).
- Bucket by kind: `experiment` (kind==experiment) vs `code` (infra/analysis/batch/survey) vs `pooled` (all). Kind from REGISTRY.json (denormalized; fall back to frontmatter).
- **Window rule (D2):** per (bucket, stage), keep the **last K=60 samples by span-end timestamp**; if n<10 in a bucket-stage, fall back to `pooled` same-window; if pooled n<10, fall back to all-history pooled. Each per-task estimate records the basis actually used: `stats_basis: bucket | pooled | all-history` (measured today: code bucket holds its own for planning/approved/running/interpreting/reviewing with n=10-16, falls back for verifying n=2 and plan_pending n=3 — mixed basis is expected and tagged, never implied to be a single pure bucket).
- Per cell store `{n, p25_h, median_h, p75_h}` plus derived `pct_floor_by_stage` (cumulative median weights, see 3.3).
- **Epsilon floor (consistency fix):** every selected `median_h` (and span weight) is floored at `EPS_H = 0.01` (36 s) before use — zero-duration spans exist (reviewing has 26 exact-zero + 62 ≤1s spans all-history), and a zero median would (a) ZeroDivision the frac computation and (b) collapse `span_i` to 0, breaking strict monotonicity. With the floor, floors stay strictly increasing and `frac = elapsed/median` is always defined.

### 3.3 Progress % (D3)

Weights = the selected bucket's stage **medians** `m_i` (epsilon-floored) over the 7 stages; `T = Σ m_i`; `floor_i = Σ_{j<i} m_j / T`; `span_i = m_i / T`.

```
stage_entered_at = ts of the LAST epm:status-changed with to == current stage
                   (falls back: earliest event ts, then epm:created ts)
elapsed_h        = max((now - stage_entered_at) / 3600, 0)
frac             = 0.0                          if stage == plan_pending (human wait — bar parks at floor)
                 = min(elapsed_h / median_i, 0.95)  otherwise
pct              = floor_i + frac * span_i
```

Monotone by construction: floors strictly increase (epsilon floor) and frac < 1 keeps pct below the next floor. Status regressions (re-plan) legitimately move the bar backward — the body explicitly wants ETA movement visible, not hidden. `plan_pending`'s median participates in the weights `T` (its span is real wall-time a human will spend) while its frac stays 0 — the parked-floor case is a pinned monotonicity test.

### 3.4 ETA band (D4) + overdue state

```
remaining_q = Σ_{j > current, j != plan_pending} q_j          for q ∈ {p25, median, p75}
eta_q       = max(q_current - elapsed_h, 0) + remaining_q     (current-stage term also skipped when current == plan_pending)
overdue     = elapsed_h > stage_p75_h                          (machine stages except plan_pending)
```

- **Overdue state (round-1 Must-Fix, all four stats/alternatives reviewers).** Once `elapsed_h > stage_p75_h`, the `max(..., 0)` clamp would freeze the band at the constant post-stage remainder (e.g. "~1–2h left" 30h into a crashed run — the most confidently wrong display exactly when a human checks). So when `overdue` is true: the snapshot row carries `overdue: true`; the dashboard chip is replaced by a "running long — >`p75`h typical" label (no countdown); the title suffix drops the hour band (bar + pct only, or "overdue"); the position bar stays parked at its 0.95-frac cap (the bar is honest — it's the chip that lied). Measured base rate: 13% of historical running spans exceeded 2× p75, and `~/.eps-autonomous/` carries 39 stalled-session alerts — this is the modal failure mode, not a tail case.
- `plan_pending` is excluded from every machine-ETA term; when it lies AHEAD of the current stage, the dashboard chip appends "+ plan review" (title suffix omits this for chars). The "+ plan review" annotation must stay visible on the dashboard — plan_pending is strongly bimodal (p25 0.04h / p75 2.58h / p90 11.4h) and silently absorbing it would be dishonest.
- **Caveat (documented in code + module docstring + chip tooltip):** summing per-stage quantiles is a heuristic, not the quantile of the sum; the band is presented as "typical range (clean pass)", never a guarantee.
- **GPU-h refinement** (running stage only; SOFT, basis-tagged): if the latest `epm:plan` note matches `gpu_hours_total=([0-9.]+)` (fallback: `epm:plan-approved`; token verified present in 67 tasks, #464→#571) **and the captured value is > 0** (every `kind: infra` plan emits `gpu_hours_total=0` — zero/absent → skip refinement entirely, `eta_basis: "historical"`), then `refined_median = max(gpu_hours_total / gpu_count, historical_p25)` — the clamp guards the known optimism of assuming perfect N-GPU parallelism — and the band is ratio-scaled: `refined_p25 = refined_median * (p25_hist/median_hist)`, same for p75. **Empirical honesty note (measured on 29 historical token-carrying tasks):** the refined center has median error ~1.96×, p75 3.28×, max 14× vs actual running spans — it is a soft hint, not a promise, and the UI must render it distinguishably (see §3.6: `basis` field in `TaskProgressView`, "≈" prefix on refined/assumed estimates). `gpu_count` recovery chain:
  1. regex `(\d+)\s*[×x]\s*(?=H100|H200|A100|B200|GPU)` (anchored to a GPU-type token — `epm:progress` notes are prose and an unanchored count match could capture incidental mentions) over the latest `epm:pod-provisioned`, `epm:progress`, or `epm:cluster-launched` note, newest first (the pod-provisioned marker is legacy — stops at #514);
  2. `scripts/pods_ephemeral.json` → entry with `issue == N` → `gpu_intent` → `{eval:1, lora-7b:1, ft-7b:4, inf-70b:8, ft-70b:8, debug:1}`. **Unknown intent values (e.g. observed `"custom"`) explicitly fall through to step 3 — never a KeyError**;
  3. assume 1 GPU (GPU-h treated as wall-h), tagged `gpu_conversion: "assumed-1gpu"` (measured: assumed conversions are worse — median error 2.93× — hence the soft rendering).

### 3.5 Edge cases (D5)

| Case | Behavior |
|---|---|
| **Live status is authoritative (round-1 Must-Fix, reconciled).** | The dashboard ALWAYS resolves rendering from the LIVE REGISTRY status, not from snapshot-row existence. `getProgressMap(liveStatuses)` receives the statuses the server page already loaded (`listAllTasks()`); a snapshot row whose live status has NO stage floor (awaiting_promotion, completed, archived, proposed, followups_running, shared, anything unknown) is DROPPED — no bar, no NaN clamp, regardless of snapshot freshness. | Live status ∈ machine stages but ≠ snapshot stage (task advanced or regressed within the pipeline since the last tick) | Render `pct = pct_floor[live_status]` ALONE (never `max(snapshot_pct, floor)` — a backward `plan_pending→planning` re-plan must show the bar moving backward, 14 observed historically); ETA chip hidden until the next snapshot tick re-estimates. |
| `blocked` (live) | Blocked view: grey bar frozen at the floor of the last machine stage before blocking (recovered from the last forward `to`; a blocked task with NO prior machine stage returns the blocked view at floor 0 — pinned crash-guard test), `eta: null`, "blocked" chip, no countdown. Title: no suffix. |
| Overdue (`elapsed > stage p75`, live status still in pipeline) | Bar parked at frac cap; chip → "running long" label; title suffix drops the hour band. See §3.4. |

## 11. Decision Rationale

N/A — no model training; the load-bearing choices are the design decisions:

- **D1 Module location & dashboard consumption.** *What:* estimator in `src/explore_persona_space/task_progress.py` + thin `scripts/` CLI; dashboard consumes a materialized snapshot at `~/.eps-autonomous/task_progress.json`; TS does only display interpolation, live-status keyed. *Why:* single source of truth for the math; no Python subprocess in the render path; the title path forces the estimator to exist in Python regardless, so a TS reimplementation would duplicate ~200 lines (the request-time-in-Next alternative also fails on the kanban's data flow: `listAllTasks()` reads REGISTRY + frontmatter, NOT events.jsonl — adding per-row event parsing to the kanban would be new I/O, not reuse). *Source:* `dashboard/lib/sessions.ts` pinned-contract precedent. *Alternatives rejected:* full TS reimplementation (drift); shelling Python from the route (latency + no-shellout rule's spirit); stats file inside `tasks/` (read-only optics).
- **D2 Recency window.** *What:* last K=60 spans per (bucket, stage), min-n=10, fallback bucket→pooled→all-history, `stats_basis` tagged. *Why:* project history is only ~9-10 weeks, so a calendar window would cover nearly everything and not encode the speedup; K=60 ≈ the most recent 4-5.5 weeks at observed throughput; quartiles at n=60 are stable and robust to the 139h crashed-run tails without trimming. *Source:* body feasibility table + fact-checker histogram + Codex recount. *Alternatives:* exponential time-decay weighting (more knobs, harder to test, marginal gain); per-stage calendar window (degenerates to all-history here).
- **D3 Median-weighted progress.** *What:* stage weights = recent medians (epsilon-floored at 0.01h), within-stage frac capped at 0.95. *Why:* uniform weights would jump ~14% per trivial stage; median weighting tracks wall-clock reality; the cap keeps monotonicity; the epsilon floor keeps zero-median stages (reviewing has 26 exact-zero spans) from breaking division and strict monotonicity. *Source:* body table + Codex S7 zero-span count. *Alternative:* p75 weights (over-weights tail-heavy running).
- **D4 ETA band + overdue + soft GPU-h conversion.** *What:* band = Σ remaining-stage {p25, median, p75}, plan_pending excluded; `overdue = elapsed > stage_p75` suppresses the band on both surfaces; running refined by `max(gpu_hours_total/gpu_count, p25_hist)` with ratio-scaled band, skipped on ≤0, basis rendered with "≈". *Why:* the body mandates band-not-point and honesty; the overdue state closes the frozen-fake-countdown class all four stats/alternatives reviewers flagged (13% base rate); the clamp + skip + soft rendering encode the measured ~2× center error instead of pretending the refinement is solid. *Source:* `gpu_hours_total=` token (67 tasks); Codex S5 empirical error table; Claude alternatives stall measurements. *Alternative:* WandB-progress-based mid-run refinement (much better, much more plumbing — natural follow-up, out of scope).
- **D6 Caching.** *What:* stats TTL 24h inside the snapshot writer; snapshot every 5 min via the existing summarize cron + atomic write; the cron is the ONLY writer (`load_stats_readonly` never rebuilds); TS mtime-keyed in-memory cache; 30-min staleness guard hides the ETA chip; `overdue` computed at read time so it fires between cron ticks. *Why:* stats change only when tasks reach terminal state (~2/day); the 5-min cadence matches the existing freshness contract; single-writer keeps title ticks O(1). *Source:* `cron_session_summarize.sh` + `DEFAULT_FRESHNESS_WINDOW_SECONDS` pattern. *Alternative:* lazy regen from the Next route (write from the render path inverts the dashboard's read-only posture).
- **D7 Suffix format & trim ladder.** *What:* ` · ▓▓░░░ 43% ~4–9h` (overdue: band dropped), degrade ladder (trim step → drop bar → drop suffix), suffix gated on machine-active statuses, computed fail-soft inside `write_self_report` with read-only stats. *Why:* fits the 78-char cap with a 45-char slug in the common case; the ladder guarantees legible-or-absent; gating on status keeps every existing call site working with zero SKILL.md edits; default-on beats opt-in because a missed call-site flag fails invisibly while default-on fails to a stderr line. *Source:* `build_progress_string` cap-trim contract + call-site grep. *Alternative:* `--with-eta` opt-in flag (invisible failure mode).
- **D8 Overdue threshold = current-stage p75 (new in v2).** *What:* the band is suppressed once elapsed exceeds the stage's selected p75. *Why:* p75 is already stored per cell, needs no new statistic, and by construction ~25% of clean traversals exceed it — so "running long" appears exactly when the historical basis stops supporting a countdown; k·median variants would need a new tuned constant. *Source:* round-1 critique union (4 reviewers); measured 13%-beyond-2×p75 stall base rate. *Alternative:* a stalled-detector integration (the watcher's 6h staleness pass) — heavier coupling, different signal (marker staleness ≠ stage duration), kept out of v1.
