## 3. Design

### 3.1 Stage model

Canonical machine sequence (fixed): `planning → plan_pending → approved → running → verifying → interpreting → reviewing`, terminal target `awaiting_promotion` (= 100%). Legacy statuses observed in historical `from/to` fields map onto it for **stats attribution and live-stage resolution**:

```python
LEGACY_STAGE_MAP = {
    "awaiting_approval": "plan_pending",
    "queued": "approved",
    "implementing": "running",
    "code_reviewing": "running",
    "testing": "running",
    "uploading": "verifying",        # defensive only — zero observed occurrences anywhere
    "under_review": "reviewing",     # defensive only — zero observed occurrences anywhere
    "clean_result_drafting": "reviewing",
}
```

**Scanning scope (fact-check corrected):** legacy statuses (`queued` ×47, `implementing` ×27, `clean_result_drafting` ×45, etc.) occur ONLY in legacy `state_changed` marker rows (332 rows, older schema, millisecond ISO timestamps) — NEVER in `epm:status-changed` rows (1460 rows, all canonical statuses). The stats scanner reads **`epm:status-changed` rows only**; legacy `state_changed` history is **deliberately excluded** (it predates the current workflow shape, and the K=60 recency window would discard most of it anyway). `LEGACY_STAGE_MAP` is retained purely as a cheap defensive normalization applied to any `to` value encountered — expected no-op on `epm:status-changed` rows; it exists so a surprise legacy value degrades to the right canonical stage instead of being mis-skipped. Confirmed noise handled below: 97 `null→null` rows; backward transitions `awaiting_promotion→reviewing` ×2, `plan_pending→planning` ×14.

**Stage-duration sample definition:** a contiguous interval that *enters* stage S (an `epm:status-changed` with `to ∈ stage(S)`) and *exits forward* (next `epm:status-changed` with `to` mapping to a LATER canonical stage or `awaiting_promotion`/`completed`). Intervals exiting to `blocked`, a backward stage, or `archived` are **excluded** (they measure stuckness/abandonment, not stage cost). Rows with non-status `from/to` (null, unknown strings) are skipped.

### 3.2 Stats (recency-windowed, kind-bucketed)

- Scan terminal-ish tasks: `tasks/{completed,archived,awaiting_promotion}/*/events.jsonl` (~380 dirs, 20MB → measured; <5s).
- Bucket by kind: `experiment` (kind==experiment) vs `code` (infra/analysis/batch/survey) vs `pooled` (all). Kind from body.md frontmatter via `task_workflow.get_task` — actually via a light frontmatter-only read (`_read_body`) to avoid loading full bodies; or REGISTRY.json `kind` field (present, cheaper — use REGISTRY, fall back to frontmatter).
- **Window rule (D2):** per (bucket, stage), keep the **last K=60 samples by span-end timestamp**; if n<10 in a bucket-stage, fall back to `pooled` same-window; if pooled n<10, fall back to all-history pooled. Justification in §11.
- Per cell store `{n, p25_h, median_h, p75_h}` plus derived `pct_floor_by_stage` (cumulative median weights, see 3.3).

### 3.3 Progress % (D3)

Weights = the selected bucket's stage **medians** `m_i` over the 7 stages; `T = Σ m_i`; `floor_i = Σ_{j<i} m_j / T`; `span_i = m_i / T`.

```
stage_entered_at = ts of the LAST epm:status-changed with to == current stage
                   (falls back: earliest event ts, then epm:created ts)
elapsed_h        = (now - stage_entered_at) / 3600
frac             = 0.0                          if stage == plan_pending (human wait — bar parks at floor)
                 = min(elapsed_h / median_i, 0.95)  otherwise
pct              = floor_i + frac * span_i
```

Monotone by construction: floors increase along the sequence and frac < 1 keeps pct below the next floor. Status regressions (re-plan) legitimately move the bar backward — the body explicitly wants ETA movement visible, not hidden.

### 3.4 ETA band (D4)

```
remaining_q = Σ_{j > current, j != plan_pending} q_j          for q ∈ {p25, median, p75}
eta_q       = max(q_current - elapsed_h, 0) + remaining_q     (current-stage term also skipped when current == plan_pending)
```

- `plan_pending` is excluded from every machine-ETA term; when it lies AHEAD of the current stage, the dashboard chip appends "+ plan review" (title suffix omits this for chars).
- **Caveat (documented in code + module docstring):** summing per-stage quantiles is a heuristic, not the quantile of the sum; the band is presented as "typical range", never a guarantee.
- **GPU-h refinement** (running stage only): if the latest `epm:plan` note matches `gpu_hours_total=([0-9.]+)` (fallback: `epm:plan-approved`; token verified present in 67 tasks, #464→#571), then `refined_median = gpu_hours_total / gpu_count`, and the band is ratio-scaled: `refined_p25 = refined_median * (p25_hist/median_hist)`, same for p75. `gpu_count` recovery chain:
  1. regex `(\d+)\s*[×x]\s*[A-Z]` over the latest `epm:pod-provisioned` note (observed forms: "4× H100 SXM", "4xH100", "1x H100"; regex matches 19/20 historical notes). **Coverage caveat (fact-check):** this marker is effectively legacy — it stops at #514; recent tasks record provisioning in `epm:progress` / `epm:cluster-launched` notes instead, so the SAME regex is also applied to those two marker kinds' notes, newest first, before falling through;
  2. `scripts/pods_ephemeral.json` → entry with `issue == N` → `gpu_intent` → `{eval:1, lora-7b:1, ft-7b:4, inf-70b:8, ft-70b:8, debug:1}`. **Unknown intent values (e.g. observed `"custom"`) explicitly fall through to step 3 — never a KeyError**;
  3. assume 1 GPU (GPU-h treated as wall-h), tagged `gpu_conversion: "assumed-1gpu"` in the snapshot so the UI can show the estimate as soft.

### 3.5 Edge cases (D5)

| Case | Behavior |
|---|---|
| `blocked` | Snapshot row kept with `blocked: true`, `eta: null`, pct frozen at the floor of the last machine stage before blocking (recovered from the last forward `to`). UI: grey bar + "blocked" chip, no countdown. Title: no suffix. |
| `followups_running`, `awaiting_promotion`, `completed`, `archived`, `proposed`, `clarifying` | Not in snapshot `tasks`; no bar anywhere (body: bar covers first pass to awaiting_promotion only). |
| `kind: infra/analysis/...` | Same 7-stage sequence, `code` bucket stats (these tasks DO traverse running/reviewing via the implementer path — `running` rolls up implementing/code_reviewing/testing). Stages the code path rarely visits get small code-bucket medians or pooled fallback; known limitation: code-task ETA may inflate by ~1h, documented. |
| Task created mid-pipeline / missing first transition | `stage_entered_at` falls back to earliest event ts → bar still renders, possibly pessimistic frac. |
| `from/to` null or unknown | Row skipped (observed `None -> None` rows in #529). |
| Snapshot status ≠ live REGISTRY status (snapshot ≤5 min stale) | Dashboard clamps: `pct = max(snapshot pct, pct_floor_by_stage[live_status])` using the stats section's floors; ETA chip hidden on mismatch. |
| Snapshot `generated_at` > 30 min old (cron dead) | Dashboard renders bar from snapshot + "stale" tooltip, hides ETA chip. Honest degradation, no fake countdown. |
| Clock skew | None — all ts are UTC from task.py; negative elapsed clamps to 0. |

## 11. Decision Rationale

N/A — no model training; the load-bearing choices are the design decisions:

- **D1 Module location & dashboard consumption.** *What:* estimator in `src/explore_persona_space/task_progress.py` + thin `scripts/` CLI; dashboard consumes a materialized snapshot at `~/.eps-autonomous/task_progress.json`; TS does only display interpolation. *Why:* single source of truth for the math (deliverable 1); no Python subprocess in the render path; the repo rule bans `tasks/` path construction outside `task_workflow` helpers, which only the src module can import cleanly. *Source:* `dashboard/lib/sessions.ts` pinned-contract precedent (exact same Python-cron→home-dir-JSON→TS-reader pattern, read in full); `.claude/cache/` rejected because it's gitignored repo state with no dashboard-reader precedent. *Alternatives rejected:* full TS reimplementation (drift across ~200 lines of stats logic vs one 6-line interpolation formula pinned by shared vectors); shelling Python from the route (latency + the CLAUDE.md no-shellout rule's spirit); stats file inside `tasks/` (violates read-only-over-tasks/ optics).
- **D2 Recency window.** *What:* last K=60 spans per (bucket, stage), min-n=10, fallback bucket→pooled→all-history. *Why:* project history is only ~9-10 weeks, so a calendar window (e.g. 8 weeks) would cover nearly everything and not encode the speedup the body flags; K=60 ≈ the most recent 3-4 weeks at observed throughput (~11 full pipeline spans/week; per-stage n 86-206 from the body table), and quartiles at n=60 are stable while medians/quartiles are inherently robust to the 139h crashed-run tails without trimming. *Source:* body feasibility table + transition histogram measured in-repo. *Alternatives:* exponential time-decay weighting (more knobs, harder to test, marginal gain); per-stage calendar window (degenerates to all-history here).
- **D3 Median-weighted progress.** *What:* stage weights = recent medians, within-stage frac capped at 0.95. *Why:* uniform weights would jump ~14% per trivial stage (`approved` median 0.02h); median weighting makes the bar track wall-clock reality; the cap keeps monotonicity and never claims a stage finished early. *Source:* body table (approved=0.02h vs running=4.63h). *Alternative:* p75 weights (over-weights tail-heavy running; median is the typical-case anchor).
- **D4 ETA band + GPU-h conversion.** *What:* band = Σ remaining-stage {p25, median, p75}, plan_pending excluded, running refined by `gpu_hours_total/gpu_count` with ratio-scaled band; gpu_count chain note-regex → intent-map → assume-1. *Why:* the body mandates band-not-point and human-wait exclusion; ratio scaling preserves the historical uncertainty shape around a better center; the chain degrades gracefully and tags its basis so the UI never silently presents an assumed conversion as solid. *Source:* `gpu_hours_total=` token verified in #517/#529/#561; provisioned-note forms verified in #514/#519/#529; intent table from CLAUDE.md § GPU intent → spec. *Alternative:* WandB-progress-based mid-run refinement (much better, much more plumbing — natural follow-up, out of scope).
- **D6 Caching.** *What:* stats TTL 24h inside the snapshot writer; snapshot every 5 min via the existing summarize cron + atomic write; TS mtime-keyed in-memory cache; 30-min staleness guard hides the ETA chip. *Why:* stats change only when tasks reach terminal state (~2/day); the 5-min cadence matches the existing freshness contract the dashboard already lives with; reusing the cron script avoids new crontab surface. *Source:* `cron_session_summarize.sh` + `DEFAULT_FRESHNESS_WINDOW_SECONDS` pattern read in-repo. *Alternative:* lazy regen from the Next route (write from the render path inverts the read-only posture of the dashboard process).
- **D7 Suffix format & trim ladder.** *What:* ` · ▓▓░░░ 43% ~4–9h`, degrade ladder (trim step → drop bar → drop suffix), suffix gated on machine-active statuses, computed fail-soft inside `write_self_report`. *Why:* fits the 78-char cap with a 45-char slug in the common case; the ladder guarantees the suffix is legible-or-absent, never mangled; gating on status (not on the free-text `step`) keeps every existing call site working with zero SKILL.md edits. *Source:* `build_progress_string` cap-trim contract + SKILL.md call sites (read). *Alternative:* a `--with-eta` opt-in flag (would require touching `/issue` + `/issue-tick` SKILL.md call sites and would silently never fire if a call site is missed; default-on + fail-soft + status gate is safer).
