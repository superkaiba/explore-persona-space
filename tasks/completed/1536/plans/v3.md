## 3. Design

**New module-level function** in `src/explore_persona_space/train/sft.py` (defined near the other private helpers, above `train_lora`):

```python
_PC_KEYS = ("prompt", "completion")

def _validate_prompt_completion_homogeneity(data_path: Path) -> None:
    """Fail fast on mixed prompt/completion types before SFTTrainer init.

    TRL 0.29 ``is_conversational()`` pops ONE arbitrary key from a set, so a
    ``{"prompt": <message list>, "completion": <str>}`` row routes
    hash-order-nondeterministically and crashes at ``SFTTrainer.__init__``,
    possibly only on the pod. See .claude/rules/gotchas.md "TRL
    prompt-completion SFT rows" (#1489/#1508). Rows carrying NEITHER key
    ("messages"/"text"/pre-tokenized schemas) are skipped.
    """
    convention: str | None = None  # "str" | "list"
    convention_row = -1
    row_idx = -1  # index over non-blank lines == datasets row index
    with data_path.open(encoding="utf-8") as fh:  # text-mode iteration — never .splitlines() on JSONL (U+2028 gotcha)
        for line_no, line in enumerate(fh, start=1):
            if not line.strip():
                continue
            row_idx += 1
            try:
                row = json.loads(line)
            except json.JSONDecodeError as e:
                raise ValueError(f"{data_path}: invalid JSON at row {row_idx} (line {line_no}): {e}") from e
            if not isinstance(row, dict):
                raise ValueError(f"{data_path}: row {row_idx} (line {line_no}) is not a JSON object")
            present = [k for k in _PC_KEYS if k in row]
            if not present:
                continue  # not a prompt-completion row
            if len(present) == 1:
                raise ValueError(
                    f"{data_path}: row {row_idx} (line {line_no}) has {present[0]!r} without its partner key — "
                    f"TRL prompt-completion rows need BOTH 'prompt' and 'completion'."
                )
            p, c = row["prompt"], row["completion"]
            for key, val in (("prompt", p), ("completion", c)):
                if not isinstance(val, (str, list)):
                    raise ValueError(
                        f"{data_path}: row {row_idx} (line {line_no}): {key!r} is {type(val).__name__}; "
                        f"must be str or a list of message dicts."
                    )
                if isinstance(val, list) and (
                    not val or not all(isinstance(m, dict) and "role" in m and "content" in m for m in val)
                ):
                    raise ValueError(
                        f"{data_path}: row {row_idx} (line {line_no}): {key!r} must be a NON-EMPTY list of "
                        f"{{'role','content'}} message dicts."
                    )
            if type(p) is not type(c):
                raise ValueError(
                    f"{data_path}: mixed prompt/completion types at row {row_idx} (line {line_no}): "
                    f"prompt is {type(p).__name__}, completion is {type(c).__name__}. TRL 0.29 "
                    f"is_conversational() pops one arbitrary key, so mixed rows route "
                    f"hash-order-nondeterministically and crash at SFTTrainer init (see "
                    f".claude/rules/gotchas.md 'TRL prompt-completion SFT rows'; #1489/#1508). "
                    f"Use message-dict lists on BOTH keys or plain str on BOTH."
                )
            this = "list" if isinstance(p, list) else "str"
            if convention is None:
                convention, convention_row = this, row_idx
            elif this != convention:
                raise ValueError(
                    f"{data_path}: cross-row prompt/completion convention mismatch: row {convention_row} "
                    f"is {convention}/{convention} but row {row_idx} (line {line_no}) is {this}/{this}. "
                    f"TRL routes dataset-level branches off the FIRST row (sft_trainer.py is_conversational "
                    f"gates at first_example) — one convention per dataset."
                )
```

**Call site** (the exact insertion point): inside `train_lora`, immediately after the #365 empty-file preflight (L1386–1397) and BEFORE `dataset = load_dataset("json", ...)` at L1398:

```python
    if not (cfg.dataset_kwargs or {}).get("skip_prepare_dataset"):
        # #1536: fail-fast backstop for the #1489/#1508 TRL mixed-schema trap.
        _validate_prompt_completion_homogeneity(_data_path)
```

The `skip_prepare_dataset` guard exempts the pre-tokenized Arm-B path (#498/#528, `cfg.dataset_kwargs` plumbing at L1467–1472), whose rows never reach TRL's `is_conversational` routing.

**Pre-load vs post-load:** pre-load raw-line scan, decided by direct test (today, datasets 4.8.4 / pyarrow 23.0.1): the brief's hint that cross-row mixing "fails earlier at pyarrow load" is **refuted on the pinned versions** — both within-row mixed (`prompt: List(struct), completion: string`) AND cross-row mixed (loaded as `Json(decode=True)` columns, per-row types preserved) load WITHOUT error and reach SFTTrainer. A post-load scan would work on 4.8.4 but depends on loader feature-inference internals that differ across datasets versions; the raw-line scan sees exactly the bytes the builder wrote, is version-independent, and co-locates with the existing preflight. JSONL is read via text-mode file iteration (never `.splitlines()` — the U+2028 gotcha).

**JSON-array early check (critic fold, 2 lines):** before the row loop, if the file's first non-blank character is `[`, raise `ValueError("expected JSONL (one JSON object per line), got a JSON array file")` — a clearer message than a row-0 decode failure (`load_dataset("json")` accepts array files but no repo builder writes them; project convention is JSONL).

**Cost bound:** one pass, `json.loads` per non-blank line — O(file bytes), O(1) memory. A ~100k-row × ~1 KB file (~100 MB) parses in ~3–8 s single-core; negligible next to `load_dataset`'s own parse of the same bytes and the training run.

**Deliberately NOT touched:** the L833 marker-slot-probe `return None` and the L1129 KL-aux `continue` isinstance guards — both are silent-skip guards in DIAGNOSTIC side paths (the probe tolerates malformed rows by design; the KL-aux batch builder reads a SEPARATE aux file), not the training data path. They stay verbatim. Also untouched: `train/trainer.py:1004`'s SFTTrainer (see §6 scope justification) and the existing L1391 line-count expression.

## 6. Risks

- **False positives on legitimate datasets.** Canonical prompt/completion mix builders all write homogeneous shapes, verified by read today: `artifacts/organisms.py:408` (list+list concat), `artifacts/datagen.py:1685` (docstring-pinned `{prompt: [msg dicts], completion: [{"role","content"}]}`), and — feeding its OWN standalone SFTTrainer at L206, outside train_lora's coverage (accepted residual, see §8 assumption 4) — `scripts/issue778_finetune.py:76` (`{"prompt": [msgs[0]], "completion": [msgs[1]]}`, fail-loud role check above it); the marker-slot probe (L833) already REQUIRES list/list. Legacy str/str callers pass by design. The pre-tokenized #498/#528 Arm-B path is exempted via the `skip_prepare_dataset` guard. Residual (accepted, named): a message dict legitimately lacking `"content"` (e.g. a future tool-call row) would false-positive — no repo SFT mix writes such rows today; if one appears, relax the element check to role-only (a `must-ask` deviation, §12). A heterogeneous LEGACY caller tripping the check is a TRUE positive — exactly the #1489 class.
- **Performance on large JSONLs:** bounded in §3 (~3–8 s per 100 MB, one pass); no size cap needed.
- **Non-prompt/completion schemas** (`messages`, `text`, pre-tokenized): rows without both keys are skipped with a clear docstring statement (test g); the whole scan is skipped under `skip_prepare_dataset`. `cfg.packing` does not change the row schema, so no packing-specific handling.
- **Stricter-than-TRL element check:** `is_conversational` inspects only element 0's `"role"`; we require role+content on every element (what `apply_chat_template` actually needs). Named as deliberate strictness; covered by test (h).
- **Malformed-JSON rows now fail at preflight** with row/line context instead of inside pyarrow — a behavior change only for already-broken files (fail-fast is the goal).

## 11. Decision Rationale

- **Pre-load raw-line scan (not post-load).** What: scan the JSONL text at the L1386 preflight block. Why: version-independent (the loader's heterogeneity handling is an implementation detail — 4.8.4's `Json` feature preserves types, other versions coerce), sees exactly the builder's bytes, co-located with the existing #365 preflight. Source: ran the datasets/pyarrow repro today; #1508/#1489 bodies. Alternatives: post-load `ds.features`/row scan (loader-version-dependent), collator-time check (too late — crash site is `SFTTrainer.__init__`).
- **Cross-row mismatch → raise.** Why: TRL gates dataset-level branches off `first_example` (`sft_trainer.py:1010/:1022`, read today) while per-row map gates route per example (`:1050/:1113`) — mixed conventions get inconsistent processing. Source: TRL 0.29.1 source lines read today. Alternative: warn-only — rejected (project fail-fast rule; a warning at pod-launch is unread).
- **Key-detection: skip rows lacking BOTH keys; skip scan under `skip_prepare_dataset`.** Why: `messages`/`text`/pre-tokenized schemas are legal non-prompt-completion inputs with no cross-key mismatch possible; the Arm-B pre-tokenized path bypasses TRL's routing entirely. Source: sft.py L1467–1472 + TRL `supported_keys` list, read today. Alternative: validate `messages` shape too — rejected as scope creep (single key, no mixing trap).
- **Missing partner key → raise.** Why: TRL's prompt-completion dataset type requires both columns; a single-key row is invalid SFT data and would fail later anyway. Source: TRL data_utils/docs read today.
