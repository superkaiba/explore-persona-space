# Plan — issue #793

## Plan Summary

**What:** Make the SLURM lane (`nibi` / `fir` / `mila`) actually HONOR
`spec.extra["repo_branch"]` by materializing a correct, complete rsync source for
the requested branch on the orchestrator VM — instead of always aborting at the
`_assert_repo_branch_synced` guard (which only refuses to submit stale `main`).
An `auto`-routed feature-branch experiment that falls through GCP → SLURM can then
run the feature-branch code, rather than always exhausting the SLURM lanes and
falling through to GCP/RunPod.

**How (Option C — worktree-clone + working-tree overlay):** In
`SlurmBackend.prepare()`, when `spec.extra["repo_branch"]` names a non-`main`
branch AND the default rsync source (`_default_src_root()` → repo root on `main`)
is not already on that branch, build a **scratch checkout of the branch** on the
VM via `git worktree add --detach <scratch> <branch-commit>` (detached HEAD, since
the branch is already checked out in the `/issue` worktree), **overlay the
working-tree-only `external/open-instruct/` gitlink contents** from `_src_root`
(the one `RSYNC_INCLUDE_PATHS` entry that is a mode-160000 gitlink absent from any
branch checkout), then point the existing `_rsync(...)` at that scratch tree. The
`_assert_repo_branch_synced` guard is KEPT verbatim and RE-ASSERTED against the
resolved source — as a belt-and-suspenders check on `materialize_branch_src`'s own
correctness (catch a cloner that returned a tree NOT on the requested branch), NOT
as a "refuse on mismatch" check (the resolved source is always either `_src_root`
on main/absent/already-on-branch, or the materialized branch tree — neither of
which the guard can find stale). On `repo_branch` absent / `main`, the code path is
byte-identical to today (rsync from `_default_src_root()`).

**Why Option C, not B:** The `/issue` worktree at `.claude/worktrees/issue-<N>` is
a **sparse checkout** (`new_worktree.sh` excludes `external/`, `eval_results/`,
`ood_eval_results/`), so rsyncing it directly would ship a tree missing
`external/open-instruct/` and break every full-FT stage — re-creating the
stale-code class with a different missing dir. A scratch clone/worktree of the
branch is content-complete; the working-tree overlay handles the one gitlink.

**Scope:** `src/explore_persona_space/backends/slurm.py` only. No change to
`dispatch_issue.py` (it ALREADY threads `spec.extra["git_repo_root"]` = the
per-issue worktree path, used only as the local commit source; the branch name is
read from the already-threaded `spec.extra["repo_branch"]`). GCP/RunPod backends
untouched. The `_assert_repo_branch_synced` guard stays.

**Test-injectable:** add a `git_cloner` seam to `SlurmBackend.__init__` (mirroring
`git_branch_resolver` / `submitter` / `rsyncer`), defaulting to the real
`materialize_branch_src` shell-out; tests inject a fake that records the request and
returns a fake scratch path.

**Compute:** 0 GPU-h, 0 pods. Pure VM-side git + local FS work. Implementer
wall-time: a few hours.

**Risks (top 2):** (1) The scratch worktree/overlay must be complete — a missed
working-tree-only path re-creates the stale-source class; mitigated by re-asserting
the guard against the scratch tree AND by rsync's existing `build_rsync_command`
`pyproject.toml`-in-source assertion. (2) Concurrent same-branch runs / stale scratch
after a rebase; mitigated by an issue-namespaced scratch dir refreshed (removed +
recreated) on every `prepare`.

## 1. Goal

Make the SLURM lane honor `spec.extra["repo_branch"]`: materialize a correct,
complete rsync source for the requested feature branch on the orchestrator VM and
rsync from it, so an `auto`-routed feature-branch experiment that falls through to
a SLURM lane runs the feature-branch code — instead of always aborting at the
`_assert_repo_branch_synced` guard and exhausting the SLURM lanes.

This is `kind: infra` (a workflow-surface bug fix), not an experiment — there is no
hypothesis, no training, no dependent variable. Success is a behavioral change
behind the existing `SlurmBackend` interface, verified by unit tests.

## 2. Prior work / precedents

Every pointer below was read and confirmed for this plan.

- **GCP's `git clone -b <branch>` — the primary precedent for honoring
  `repo_branch`.** `backends/gcp.py:1566-1575` (`render_startup_script`) emits an
  idempotent VM-side clone/fetch:
  ```
  git clone --depth 1 --branch <repo_branch> <origin> "$WORKLOAD_ROOT"   # first time
  git -C "$WORKLOAD_ROOT" fetch --depth 1 origin <repo_branch>            # else
  git -C "$WORKLOAD_ROOT" checkout <repo_branch>
  git -C "$WORKLOAD_ROOT" reset --hard origin/<repo_branch>
  ```
  `repo_branch` is read from `spec.extra` at `gcp.py:3421`
  (`repo_branch=str(spec.extra.get("repo_branch") or "main")`). The SLURM analogue
  is a VM-side materialization on the orchestrator VM (which owns the repo's shared
  object DB), NOT a clone-on-the-cluster (the cluster is behind a robot forced-command
  allowlist).

- **The `_assert_repo_branch_synced` guard — the fail-loud half already shipped
  (#653).** `backends/slurm.py:2088-2126`. Called first in `prepare()` at
  `slurm.py:2069`. It raises `ValueError` when `spec.extra["repo_branch"]` is
  non-`main` but the rsync source's HEAD differs (or is unprovable), which
  `router._prepare_and_launch` wraps as a provision-class `BackendPrepareError` so
  the auto chain advances to the next lane. THIS TASK is the other half of the
  incident-memory TODO (`.claude/agent-memory/experimenter/feedback_slurm_rsyncs_main_tree.md`
  point 3): "thread an explicit `src_root` override ... to honor the invoking
  worktree, OR fail-loud" — the fail-loud is done; this adds the honor mechanism.

- **The seam-design precedent — `git_branch_resolver` + the other injection
  seams.** `SlurmBackend.__init__` (`slurm.py:1985-2027`) exposes
  `submitter` / `canceller` / `rsyncer` / `poller` / `start_estimator` /
  `secrets_pusher` / `marker_poster` / `runtime_clearer` / `git_branch_resolver`,
  each defaulting to a real shell-out with a test stub injected. The new
  `git_cloner` seam follows this exact pattern.

- **`dispatch_issue.py` ALREADY threads the worktree path.**
  `_launch_extra_from_args` (`scripts/dispatch_issue.py:759-851`) sets
  `extra["repo_branch"]` (from `--repo-branch`, or defaulted to the current branch
  for auto/gcp lanes, lines 803-834) AND `extra["git_repo_root"]` = the per-issue
  worktree path `.claude/worktrees/issue-<N>` when it exists (`_issue_worktree_git_root`,
  lines 730-756, 842-844) — unconditionally, for every lane. So the branch NAME is
  already on `spec.extra`; the worktree PATH is already on `spec.extra` (used today
  only by `expected_artifacts_declaration`'s git check). **No dispatch change is
  needed.**

- **The current rsync path + the gitlink constraint.** `run_rsync_sync`
  (`slurm.py:648-672`) runs `build_rsync_command` from `cwd=src_root` over
  `RSYNC_INCLUDE_PATHS` (`slurm.py:550-564`): `./pyproject.toml`, `./uv.lock`,
  `./src`, `./scripts`, `./configs`, `./external/open-instruct`, `./tests`,
  `./data/sft`. Verified on this VM: `external/open-instruct` is a **mode-160000
  gitlink** (nested repo) with an EMPTY `.gitmodules` — so it is populated only in
  the repo-root **working tree**, NOT in any branch's git tree. A plain
  `git clone`/`checkout` of the branch yields an EMPTY `external/open-instruct/`.
  This is why the design must OVERLAY that dir from `_src_root`'s working tree.
  Every other `RSYNC_INCLUDE_PATHS` entry is a normal blob/tree (verified
  modes: `100644`/`040000`) present in any branch checkout.

## 3. Design forks weighed → Option C chosen

The task named three forks. Grounded in the codebase facts above:

- **Option A (pure scratch `git clone` + checkout branch).** Content-complete for
  git-tracked paths, but a plain clone/checkout produces an EMPTY
  `external/open-instruct/` (the gitlink), breaking full-FT. Would need the same
  working-tree overlay as C. A full `git clone` also copies the entire object DB
  (~3.8 GB history) unnecessarily.
- **Option B (rsync the `git_repo_root` worktree directly).** REJECTED: the
  worktree is a **sparse checkout** (`new_worktree.sh:47` `EXCLUDES="eval_results
  external ood_eval_results"`), so `external/open-instruct/` is absent from the
  working tree entirely — rsyncing it ships an incomplete tree that breaks every
  full-FT stage. Also: a worktree can carry uncommitted/dirty state, and its HEAD
  is the branch tip which may lead the pushed remote (SLURM rsyncs local content,
  so "pushed" is not required, but dirtiness would silently ship un-reviewed edits).
- **Option C (worktree-add the branch commit to a scratch dir + overlay the
  working-tree-only gitlink) — CHOSEN.** Produces a content-complete tree for every
  `RSYNC_INCLUDE_PATHS` entry: git-tracked paths come from the branch's committed
  tree (deterministic, matches what a reviewer saw), and the one gitlink
  (`external/open-instruct/`) is overlaid from `_src_root`'s working tree (the same
  source the current rsync already uses for it). Uses `git worktree add --detach`
  (NOT `git clone`) so it shares the repo-root object DB (no history copy) and
  avoids the "branch already checked out" conflict (the branch lives in the `/issue`
  worktree). This is the closest faithful analogue to GCP's clone-the-branch
  precedent, adapted to the one gitlink the GCP lane never has to think about
  (GCP's `open-instruct` is populated on the VM out of band too, but that is a
  separate concern outside this fix).

## 4. Design (file paths, signatures, concrete shape)

**Single file changed:** `src/explore_persona_space/backends/slurm.py`.

### 4a. New module-level function `materialize_branch_src` (the `git_cloner` default)

Placed near `git_branch_at` / `_default_src_root` (end of the helpers block,
`slurm.py:~2505`). Signature:

```python
def materialize_branch_src(
    *,
    src_root: Path,          # the repo-root install (owns the shared object DB + the branch ref)
    branch: str,             # spec.extra["repo_branch"], already verified non-"main"
    issue: int,              # spec.issue — namespaces the scratch dir
    overlay_paths: tuple[str, ...] = WORKING_TREE_OVERLAY_PATHS,
    timeout: int = 300,
) -> Path:
    """Materialize a complete rsync source for ``branch`` on the VM; return its path.

    Steps (idempotent — safe to re-run every prepare):
    1. scratch = ~/.eps-slurm-src/issue-<issue>  (env override EPS_SLURM_SRC_ROOT)
    2. Remove any prior scratch worktree: `git -C <src_root> worktree remove --force <scratch>`
       (guarded — a fresh scratch has none) then `rm -rf <scratch>` (belt-and-suspenders
       for a partially-removed dir), and `git -C <src_root> worktree prune`.
    3. Resolve the branch commit in src_root's object DB:
       `git -C <src_root> rev-parse --verify <branch>` (or `origin/<branch>` fallback if the
       local ref is absent — fail loud if neither resolves).
    4. `git -C <src_root> worktree add --detach <scratch> <commit>` — detached HEAD at the
       branch commit (no "branch already checked out in the /issue worktree" conflict).
    5. Overlay each working-tree-only path from src_root into scratch:
       for p in overlay_paths: rsync -a --delete <src_root>/<p>/ <scratch>/<p>/
       (local FS rsync; <p> = "external/open-instruct" — the one gitlink). Skip a p
       that is absent in src_root (log a WARNING; do not crash — a lora-only run does
       not need open-instruct, but a missing overlay is worth surfacing).
    6. Assert scratch/pyproject.toml exists (mirrors build_rsync_command's own
       source-sanity assert) — fail loud if the worktree add produced an empty tree.
    Returns the scratch Path. Raises RuntimeError with a diagnostic message on any
    git failure (fail-fast, per CLAUDE.md — no silent fallback to stale main).
    """
```

Notes:
- `WORKING_TREE_OVERLAY_PATHS: tuple[str, ...] = ("external/open-instruct",)` — a new
  module constant, the subset of `RSYNC_INCLUDE_PATHS` that is a working-tree-only
  gitlink (verified: the ONLY such entry). Kept as an explicit named constant so a
  future reviewer sees exactly which paths are overlaid and why.
- Scratch root `~/.eps-slurm-src/` (env `EPS_SLURM_SRC_ROOT`), issue-namespaced —
  parallels the existing per-issue scratch conventions and keeps concurrent
  different-issue runs isolated.
- Uses `subprocess.run(..., check=True, timeout=...)` like every other slurm shell-out.
- The overlay `rsync -a --delete <src>/<p>/ <dst>/<p>/` is a LOCAL FS copy (no
  robot alias) — distinct from the cluster-bound `run_rsync_sync`.
- **The scratch tree is a COMMITTED-only source** (`git worktree add --detach
  <commit>` materializes the branch's committed tree, plus the overlaid gitlink). It
  is therefore TIGHTER than today's working-tree rsync: an untracked-but-present
  script in `_src_root`'s working tree (e.g. an uncommitted `scripts/issue658_*.py`)
  will NOT ship. This is the CORRECT behavior for a branch-scoped run — a job
  dispatched against a branch commit must reach only committed code — but the
  implementer notes it inline so a future debugger who expects "scratch == old
  working-tree rsync for tracked paths" understands why an uncommitted file is
  absent. (The one deliberate exception is the `overlay_paths` gitlink, which is
  working-tree by construction.)

After:

```python
    def prepare(self, spec: RunSpec) -> None:
        # Resolve the rsync source for the requested branch (materialize a complete
        # tree for a non-"main" repo_branch the repo-root install does not already
        # carry). On main / absent / already-synced, this returns self._src_root
        # unchanged and the path below is byte-identical to the pre-fix behavior.
        rsync_src = self._resolve_rsync_source(spec)
        # Belt-and-suspenders (#653): re-assert the guard against the RESOLVED
        # source. This is NOT the pre-fix "refuse the feature branch" behavior — the
        # resolved source is ALWAYS either self._src_root (main/absent/already-on-
        # branch, where the guard was already a no-op) or the materialized branch tree
        # (which IS on the requested branch, so the guard trivially passes). Its post-
        # fix role is to catch a cloner that returned a tree NOT on the requested
        # branch (a materialize_branch_src correctness regression), never to refuse a
        # legitimately-requested feature branch. The lane-advance fallback for a
        # genuinely-unresolvable branch is preserved by materialize_branch_src's own
        # RuntimeError (see §4d).
        self._assert_repo_branch_synced(spec, src_root=rsync_src)
        cluster = self._cluster_for_spec(spec)
        scratch_dir = scratch_dir_for(spec, cluster)
        self._clear_runtime(robot_alias=cluster.ssh_host, scratch_dir=scratch_dir)
        self._rsync(src_root=rsync_src, dest_root=scratch_dir, robot_alias=cluster.ssh_host)
        secrets = render_secrets_env()
        self._push_secrets(cluster, scratch_dir, secrets)
```

New private helper `_resolve_rsync_source`:

```python
    def _resolve_rsync_source(self, spec: RunSpec) -> Path:
        """Return the rsync source for spec, materializing a branch tree if needed.

        No-op (returns self._src_root) when repo_branch is absent / "main" / the
        install's HEAD already IS the requested branch. Otherwise materializes a
        complete branch tree on the VM via the git_cloner seam and returns its path.
        Note: an UNPROVABLE source branch (resolver returns None) for a non-"main"
        request also routes to the cloner (None != the requested branch), so the
        source-of-truth for "can we honor this branch?" is now the cloner's own
        rev-parse (fail-loud RuntimeError on an unresolvable branch), NOT the guard.
        """
        requested = str(spec.extra.get("repo_branch") or "").strip()
        if not requested or requested == "main":
            return self._src_root
        actual = self._git_branch_resolver(self._src_root)
        if actual == requested:
            return self._src_root      # install already on the branch — rsync it directly
        return self._git_cloner(src_root=self._src_root, branch=requested, issue=spec.issue)
```

### 4d. `_assert_repo_branch_synced` — accept an explicit `src_root` (backward-compatible)

Change the signature from `(self, spec)` to `(self, spec, src_root: Path | None = None)`;
default `None` → `self._src_root` (so any existing call and the reconnect/estimate
paths are unchanged). The body reads `src_root = src_root or self._src_root` and
uses it for the branch probe + the error message. This lets `prepare()` re-assert
against the RESOLVED source (the materialized branch tree) as belt-and-suspenders.

**The re-assert NEVER raises on the honored-branch path** — this is the reconciled
story vs the plan-v1 wording. After `_resolve_rsync_source`, the resolved `rsync_src`
is exactly one of two things:
1. `self._src_root` (the request was absent / `main` / the install already IS the
   branch) — the guard was already a NO-OP for this case pre-fix (main/absent) or
   passes because the source HEAD matches the request (already-on-branch).
2. The materialized scratch tree from `materialize_branch_src` — which is on the
   requested branch commit by construction, so the guard passes trivially.

So the re-assert's post-fix ROLE is a belt-and-suspenders check on
`materialize_branch_src`'s own correctness (it would fire only if the cloner
returned a tree whose HEAD is NOT the requested branch — a materialize regression),
NOT a "refuse on mismatch of `_src_root` vs `repo_branch`" check. The guard's
internal semantics are otherwise verbatim — it still `raise`s `ValueError` on a
mismatch and still no-ops on main/absent.

**The auto-chain fallback contract is preserved by a DIFFERENT raise.** Pre-fix, a
non-`main` request against a stale-`main` (or unprovable) source raised the guard's
`ValueError`, which `router._prepare_and_launch` (router.py:1668, catch at
router.py:1706) wraps as `BackendPrepareError` → the auto chain advances at
router.py:2656. Post-fix, that same input now routes to the cloner, and if the
branch is genuinely unresolvable, `materialize_branch_src` raises `RuntimeError`
(§4a step 3) — which `_prepare_and_launch` catches identically (it wraps ANY
`prepare()` exception as `BackendPrepareError`), so the lane still advances. The
fallback moved from the guard's `ValueError` to the cloner's `RuntimeError`; the
router-level behavior is unchanged. Confirmed: `_prepare_and_launch` at
router.py:1668 catches `Exception` and re-raises `BackendPrepareError` (line 1706);
the auto chain catches `BackendPrepareError` at router.py:2656.

## 11. Decision Rationale

- **What:** Option C (worktree-add the branch commit + overlay the working-tree-only
  gitlink), NOT Option A (pure clone) or B (rsync the sparse worktree).
  **Why:** the `/issue` worktree is sparse (excludes `external/`), so B ships an
  incomplete tree; a pure clone/checkout yields an empty `external/open-instruct/`
  gitlink, so A needs the same overlay as C anyway. C is content-complete for every
  `RSYNC_INCLUDE_PATHS` entry and shares the object DB.
  **Source:** verified on-VM during planning — `new_worktree.sh:47`
  `EXCLUDES="eval_results external ood_eval_results"` (sparse worktrees);
  `git ls-tree issue-<N> external/open-instruct` → mode `160000` (gitlink);
  `git ls-tree <branch> <p>` modes for the other 7 include paths → `100644`/`040000`
  (normal, present in any checkout). GCP precedent `backends/gcp.py:1566-1575`.
  **Alternatives:** B rejected (sparse); pure A rejected (empty gitlink + full
  history copy).

- **What:** `git worktree add --detach <scratch> <commit>` (not `git clone`, not
  `git worktree add <scratch> <branch>`).
  **Why:** `--detach` avoids the "branch already checked out in the /issue worktree"
  conflict; `worktree add` shares the repo-root object DB (no ~3.8 GB history copy a
  fresh `git clone` would make).
  **Source:** `git worktree list` on-VM confirms `issue-<N>` is checked out in
  `.claude/worktrees/issue-<N>`; `git worktree add --help` confirms `--detach
  <commit>`. **Alternatives:** `git clone` (history copy, slower); `git worktree add
  <branch>` (conflicts with the /issue worktree).

- **What:** scratch dir `~/.eps-slurm-src/issue-<N>` (env `EPS_SLURM_SRC_ROOT`),
  removed + recreated every `prepare`.
  **Why:** issue-namespacing isolates concurrent different-issue runs; full refresh
  per prepare handles a rebased branch; on the boot disk (not the quota-constrained
  `/mnt/eps-data`) since it is a transient, re-derivable source, not durable data.
  It lives OUTSIDE `.claude/worktrees/`, so the stale-worktree-audit cron
  (`worktree_audit.py` / `cron_worktree_audit.sh`) does NOT reap it — VERIFIED during
  planning (`worktree_audit.py` reaps only under `.claude/worktrees/`, line 436 +
  751; the cron invokes that script). Cleanup therefore relies on the per-prepare
  removal + the VM disk-guard's terminal-cache reap, not the worktree cron — this is
  acceptable because the scratch self-bounds to one tree per active feature-branch
  SLURM run and shares the object DB (no history copy).
  **Source:** parallels the existing per-issue scratch conventions
  (`scratch_dir_for`, the per-issue cache namespacing in CLAUDE.md § Disk hygiene);
  `worktree_audit.py:436,751`, `cron_worktree_audit.sh`.
  **Alternatives:** a single shared scratch (breaks concurrency); reuse-in-place
  (stale after rebase); placing it under `.claude/worktrees/` so the cron reaps it
  (rejected — the cron's issue-status heuristics + sparse-worktree assumptions do not
  fit a transient rsync source, and a mid-prepare reap would race the rsync).

- **What:** add a `git_cloner` seam; keep `_assert_repo_branch_synced` and re-assert
  it against the resolved source (as a `materialize_branch_src`-correctness check,
  not a refuse-on-mismatch check).
  **Why:** the seam mirrors the 9 existing injection seams so the new path is
  unit-testable without git/FS side effects; keeping + re-asserting the guard keeps
  the #653 stale-code safety net as belt-and-suspenders (it fires if the cloner ever
  returns an off-branch tree) AND the auto-chain fallback contract is preserved by
  moving the genuine-failure raise from the guard's `ValueError` to the cloner's
  `RuntimeError` (§4d).
  **Source:** `SlurmBackend.__init__` seam pattern (`slurm.py:1985-2027`,
  `git_branch_resolver` is the direct model); #653 incident
  (`.claude/agent-memory/experimenter/feedback_slurm_rsyncs_main_tree.md`);
  router.py:1668/1706/2656 (exception-wrapping + lane-advance).
  **Alternatives:** remove the guard (loses the safety net — explicitly out of
  scope); no seam (untestable without real git).

- **What:** no change to `dispatch_issue.py`.
  **Why:** `spec.extra["repo_branch"]` (the branch name) and
  `spec.extra["git_repo_root"]` (the worktree path) are ALREADY threaded
  (`_launch_extra_from_args`, `scripts/dispatch_issue.py:803-844`); the fix reads the
  branch name that is already present and materializes the source itself from the
  repo-root install. **Source:** read `dispatch_issue.py:759-851`.
  **Alternatives:** thread an explicit `worktree_root`/`src_root` override from the
  dispatcher (the incident-memory's first option) — unnecessary given `repo_branch`
  is already threaded, and the sparse worktree makes a threaded worktree path an
