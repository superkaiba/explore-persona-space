### 4.1 Constants + helper (new; place after `run_single_file_pristine`, near line 950)

```python
# --- pristine-timeout sizing (#1129). -----------------------------------------
# Derived from the selector's #1046 gate-timeout knowledge so there is ONE
# per-file runtime table. #1098: the pristine single-file run of
# tests/test_workflow_lint.py needs ~780 s; the fixed 600 s default killed it
# and forced a full compare rerun. Bias generous: an oversized bound only
# delays a genuinely wedged run; an undersized one GUARANTEES a wasted
# compare + rerun (exit 2 via PristineRunError).
PRISTINE_SLOW_TIMEOUT_MULT = 2.0
PRISTINE_TIMEOUT_FLOOR_S = 600.0  # == the pre-#1129 fixed default (#1022): non-surcharge behavior unchanged


def derive_pristine_timeout_s(sel: object, test_file: str) -> float:
    """Per-file pristine-oracle bound: BASE + PER_FILE + 2x slow surcharge, floor 600 s.

    Reads the #1046 constants off the LOADED selector module (``ctx.sel``) via
    ``getattr`` so a pre-#1046 worktree selector copy (deliberate version skew,
    #1022 §3.3) degrades to the legacy 600 s floor instead of crashing.
    tests/test_workflow_lint.py -> 120 + 30 + 2*900 = 1950 s (~2.5x its ~780 s
    measured pristine runtime, #1098); files without surcharge knowledge -> 600 s.
    """
    base = float(getattr(sel, "TIMEOUT_BASE_S", 0))
    per_file = float(getattr(sel, "TIMEOUT_PER_FILE_S", 0))
    slow = getattr(sel, "SLOW_TESTS", None) or {}
    surcharge = float(slow.get(test_file, 0))
    return max(base + per_file + PRISTINE_SLOW_TIMEOUT_MULT * surcharge, PRISTINE_TIMEOUT_FLOOR_S)
```

Why code, not a model call: deterministic arithmetic over pinned constants — a model call is categorically wrong here.

## 11. Decision Rationale

1. **Derivation formula `BASE + PER_FILE + MULT × surcharge`, per single file.**
   - What: sizes ONE pristine file as one file's worth of gate budget plus a doubled slow-surcharge.
   - Why: a single-file pristine run pays pytest startup/collection once (BASE) plus the file's own runtime (PER_FILE covers ~2× p90 of non-slow files per #1046's comment); the surcharge is the selector's measured slow-file knowledge.
   - Source: #1046 constants (`select_step9c_tests.py` lines 211-220, measured from 27 gate junits, 2026-07-04..05) + #1098 measured ~780 s.
   - Alternatives: reuse `recommended_timeout_s([f])` verbatim → `max(150 + 900, 900) = 1050` s for workflow-lint = only 1.35× the ~780 s measured pristine runtime, UNDER the selector's own stated "~1.4-2x over worst measured" generosity band (and gate per-file times ranged 319-771 s, ~2.4× spread from VM load — 1050 s is too tight under load). Rejected.
2. **`PRISTINE_SLOW_TIMEOUT_MULT = 2.0`.**
   - What: doubles the surcharge for the pristine context.
   - Why: yields 1950 s for `tests/test_workflow_lint.py` = ~2.5× the ~780 s measured (#1098) and 1.62× the 1200 s that demonstrably sufficed — inside/above the selector's own 1.4-2× generosity philosophy, per the fail-safe constraint (a too-tight bound guarantees a wasted compare; a too-generous one costs minutes only on a rare genuine wedge).
   - Source: the Goal's "e.g. 2x the file's gate wall-time" direction + #1098 (measured ~780 s; successful rerun at 1200 s) + #1046's stated generosity band.
   - Alternatives: MULT=1.0 (→1050 s, same too-tight objection as above); MULT=3.0 (→2850 s, no evidence it buys anything past 2.0).
3. **`PRISTINE_TIMEOUT_FLOOR_S = 600.0` (kept, not raised to the gate's 900).**
   - What: the derived value's floor for non-surcharge files.
   - Why: 600 s has never been observed to kill a non-surcharge single-file pristine run (gate per-file p90 ~15 s per PER_FILE=30's "~2x p90" comment), and keeping it makes non-surcharge behavior identical to today per the design constraint; the gate's 900 floor covers 32-file collection, which doesn't apply to one file.
   - Source: #1022 (the incumbent default) + #1046 line 212 comment.
   - Alternatives: floor 900 (harmless but changes behavior for the common case with zero incident evidence). Rejected to keep the diff behavior-minimal.
4. **`default=None` argparse sentinel for explicit-pass detection.**
   - What: distinguishes "user passed the flag" (wins verbatim, uniform across files) from "default" (derive per file).
   - Why: preserves the #1098-style manual escape hatch exactly as used (`--pristine-timeout-s 1200`).
   - Source: standard argparse pattern; repo-wide grep (2026-07-08) shows zero live callers pass the flag (only historical task plans/bodies quote it).
   - Alternatives: a separate `--derive-pristine-timeout` opt-in flag (leaves the broken default in place — fails the Goal); keeping 600.0 as default and only adding max(default, derived) (conflates override and default: an explicit `--pristine-timeout-s 300` could silently be raised). Rejected.
5. **Helper lives in `step9c_baseline.py`, reading `ctx.sel` attributes (not a new selector-side function).**
   - What: `derive_pristine_timeout_s(sel, test_file)` consumer-side, `getattr` with fallbacks.
   - Why: compare deliberately loads the WORKTREE's selector copy (#1022 §3.3, line 1034), so a consumer-side skew fallback is required EITHER way — a selector-side function would be missing on pre-fix worktree copies and still need this exact fallback; consumer-side keeps it a one-file change while the runtime TABLE stays single-sourced in the selector (constraint: no forked table). Attribute-wise consumption is the established pattern (`ctx.sel.GLOB_SCAN_TESTS`).
   - Source: #1022 §3.3/§3.4 (deliberate version skew) + code read (lines 994/1034/1158).
   - Alternatives: `recommended_pristine_timeout_s()` in `select_step9c_tests.py` + `getattr(ctx.sel, ..., fallback)` — two files changed, same fallback burden, no added safety. Rejected (noted as acceptable if the critic prefers selector-side ownership).
