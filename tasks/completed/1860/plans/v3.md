## Requirement + acceptance criteria

**Requirement (from the task Goal):** the live task body must never carry a
verifier FAIL the pipeline itself is about to catch — the Step 9a-humanize
orchestrator step must verify the candidate body FILE first and apply it via
`task.py set-body` only on PASS; on FAIL it iterates on the candidate file.

**Bug observed (incident #1775, mined by /daily 2026-07-29):** SKILL.md
§ 9a-humanize procedure step 4 orders apply-then-verify
(`task.py set-body <N> --file /tmp/issue-<N>-humanize-loop.md` followed by
`verify_task_body.py --issue <N>`). A candidate that then FAILs (v4
conciseness in #1775) leaves a briefly-live non-compliant body and costs an
extra edit/apply/verify cycle, with a revert-after-apply instruction as the
documented recovery.

**Acceptance criteria:**
1. § 9a-humanize step 4 verifies the candidate at
   `/tmp/issue-<N>-humanize-loop.md` with `verify_task_body.py --file`
   (main-checkout copy) BEFORE any `set-body`; the apply is gated on that
   PASS.
2. The candidate-FAIL path iterates on the candidate file within the
   existing 3-cycle cap; if no passing candidate emerges, NOTHING is
   applied (the pre-loop body — which already passed the Step 9a verify —
   stays live) and the step-5 `epm:humanize-loop` note records the
   residual. The old revert-after-apply instruction is retired for the
   candidate-FAIL case.
3. A post-apply `verify_task_body.py --issue <N>` confirm is RETAINED
   (cheap, and it covers the frontmatter-coupled checks `--file` cannot see
   — e.g. the #1110 H1==frontmatter-title check; `--file` "carries no
   authoritative task frontmatter" per the verifier docstring). Its FAIL
   path (now genuinely rare) keeps the existing revert-and-surface
   instruction.
4. The same verify-candidate-first ordering is applied to the ONE other
   orchestrator-composed-candidate site that shares the shape: Step 9a-bis
   § Procedural-only verdict strip, item (b) (apply critic's procedural
   fixes then "re-runs the verifier to PASS" → verify the staged candidate
   to PASS first, then apply).
5. A NEW durability pin test asserts the verify-first ordering survives
   later SKILL.md edits (see Deliverable 2).
   Durability pin: tests/test_issue_skill_humanize_verify_first_pin.py::test_humanize_candidate_verify_precedes_set_body (NEW — added by this plan)
6. No marker schema, status, or CLI contract changes; `workflow_lint.py`
   no-flags default run stays green on the touched files; the Step 9c
   mapped tests (including the new pin test) pass.

Pure prose reorder of an existing orchestrator step inside
`.claude/skills/issue/SKILL.md` plus one small pin test — no code-path

orchestrator-level apply sites in line with the established agent-level
