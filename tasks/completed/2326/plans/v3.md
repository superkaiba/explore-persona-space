### Why code, not a model call

The forwarder is a deterministic parse of a fixed grammar plus library calls — a model call would reintroduce exactly the prose-reading the file-only constraint bans. (Rejected alternative recorded per code-style "model call vs code".)

### The grammar (composer contract — net-new text in both templates)

Inside the marker envelope (so the rows ride the durable `epm:*-codex` marker note and the already-extracted `$MB`), each emitting twin's verdict template gains:

```
## Concerns to persist

CONCERN:: <BLOCKER|CONCERN|NIT> <kebab-case-id> <one-line summary, aim <=180 chars>
```

- One row per concern, LINE-START anchored (`^CONCERN:: `); field order fixed: token 1 = severity, token 2 = concern id (kebab-case, `^[a-z0-9][a-z0-9-]{1,79}$` — no spaces by construction), remainder = summary. No `|` delimiters (summaries contain prose punctuation); whitespace-split on the first two tokens only.
- Zero concerns ⇒ the exact literal row `CONCERN:: none` (mandatory — makes block presence checkable).
- The section heading keeps each template's native depth (`##` in the code-review twin, `###` in the clean-result twin); the PARSER keys on the rows, never the heading depth.
- Round and `--by` are NOT in the rows — the poster supplies both (it knows them; removes a Codex error surface).
- **Token containment (NIT 3):** each template additionally carries one sentence — "The token `CONCERN:: ` MUST NOT appear at the start of any line outside this section: the forwarder position-parses `^CONCERN:: ` rows anywhere in the marker block, so a stray line-start occurrence elsewhere persists as a real concern."

### The forwarder — `scripts/persist_verdict_concerns.py` (NEW, ~120 lines)

```
uv run python scripts/persist_verdict_concerns.py <N> --file <marker-block path> \
  --by <codex-role> --round <n> [--require-block] [--validate-only]
```

- Parses `^CONCERN:: ` rows from `--file`. Validates ALL rows structurally before persisting ANY (all-or-nothing): severity ∈ `CONCERN_SEVERITIES`, id matches `_CONCERN_ID_RE` (both imported from `explore_persona_space.task_workflow`), summary non-empty, no duplicate ids, `CONCERN:: none` only as the sole row.
- Persists via `task_workflow.raise_concern(task_id, cid, severity=..., summary=..., raised_by=args.by, raised_at_round=args.round, evidence=...)` — the library layer (flock + events.jsonl mirror), NOT a `task.py` shellout. Summary > 200 chars → word-boundary lead as `summary`, full text as `evidence` (mirrors the CLI's non-lossy `legacy_shift` branch, `scripts/task.py:1291-1304`; ~4 lines reimplemented — `_truncate_summary` lives in `scripts/task.py`, not importable as a package module).
- `--require-block` (contract sites: 5b/5c code-review, 9a-bis clean-result): a line matching `(?mi)^(?:#{1,6}\s*|\*\*)?concerns to persist\b` with zero rows, OR zero rows and no `CONCERN:: none` ⇒ exit 3. Without the flag (9a, 9b VC — composers carry no grammar): zero rows ⇒ no-op exit 0; heading-without-rows ⇒ one `WARN: concerns-heading-without-rows` line, exit 0 (fail-loud where the contract exists, observable where it doesn't).
- `--validate-only`: parse + validate + print `concerns-block OK: K row(s)`, write nothing.
- Output discipline: prints ONLY counts + concern ids (kebab tokens) + content-free reason codes (`bad-severity | bad-id | empty-summary | too-few-fields | duplicate-id | none-with-rows | heading-without-rows`) — summaries NEVER print (keeps findings content out of orchestrator context; the ledger summaries later enter context by design at 5c-ter/0.8, which is the pre-existing consumer contract).
- Exit codes: 0 ok · 1 malformed rows · 3 missing/contradictory block under `--require-block` · 2 argparse.
- Idempotency: library-level no-op on same (id, round, severity) — `task_workflow.py:8514-8518` — so re-post / re-attach / resumed rounds never double-raise. Verified by reading the code this session. This idempotency is what makes the v3 resume-recovery re-run unconditionally safe.

**Embedded-shell exit-path trace:** invocations (a) and (b) are single foreground commands whose non-zero rc the orchestrator reads directly (no `&&`-chain, no sibling block to strand — the same standalone-command shape as the recipe's existing step-2 `grep -q` gate). No `false`-in-branch shapes introduced.

**Note on `task.py view` context discipline:** the recovery pipe runs `task.py view <N> --json` with stdout consumed entirely by `jq` and redirected to `"$MB"` — the full event log never enters orchestrator context (the bare-`view` ban is about paging the dump into context, not about piping it).

## 11. Decision Rationale

- **Blind-forwarding via a tested helper (not inline shell parse-loop).** Why: a while-read shell parser in SKILL.md is transcribed by agents per round and untestable; the helper is pytest-covered, all-or-nothing, and prints no findings content. Source: task body Scope item 3 + `.claude/rules/blinded-reads.md` precedent (mechanical forward, persisted audit); the file-only constraint (#1275). Alternatives: pure `sed|grep|while` loop (rejected: fragile quoting, partial-persist on mid-loop failure, summaries echo into context via `raise-concern`'s stdout JSON).
- **Rows INSIDE the marker envelope.** Why: rides the already-extracted `$MB` and the durable marker note — which is ALSO what makes the v3 resume recovery possible at zero new state (the posted note IS the recoverable copy); no second extraction window; the 50k-char gate already bounds it. Source: SKILL.md:3237 (the sed window) + #2321 artifact (heading already lived inside the note). Alternative: separate sidecar block outside the tags (rejected: second extraction + not durable in events.jsonl).
- **Validate-pre-post / persist-post-post split.** Why: a grammar violation must block BEFORE the marker posts (single marker per attempt, reuses the existing MALFORMED → stricter-retry path at the same decision point as the end-tag gate); a persist-side I/O failure after posting must NOT re-dispatch Codex (idempotent re-run of one command). Source: SKILL.md:3238-3240 (the existing step-2 MALFORMED semantics).
- **Resume recovery as an unconditional idempotent re-run (not a "persisted" sentinel).** Why: the concern rows ride the durable marker note, and `raise_concern` is a no-op on same (id, round, severity) — so re-running the forwarder at every advancing resume row needs NO new state and cannot double-raise; a sentinel file recording "persisted" would itself be lost by the same crash class it guards against, and a sentinel in events.jsonl would add a marker kind (schema surface) for no gain. The recovery runs at the RESUME rows (not inside Step 5c's decision table) because the seam is the resume table advancing past collection — the decision logic itself is unchanged. Source: binding reconciler verdict (`epm:progress` 2026-08-16T15:04:50Z, § Required change item 1) + `task_workflow.py:8514-8518` idempotency (read this session).
- **Resume exit-3 = legacy, WARN and proceed.** Why: post-fix, the pre-post gate blocks any contract-site marker from POSTING without rows — so a posted marker with heading+0 rows can only be a pre-fix round; failing it at resume would stricter-retry a round whose verdict already posted (re-dispatching Codex against a settled round). Source: verdict item 1 (resume-specific exit-3 handling); the pre-post gate's own semantics (§ poster recipe (a)).
- **`--require-block` scoped to the two contract sites.** Why: failing a site whose composer never taught the grammar would retry-loop into a no-show. Source: grep this session — only `codex-code-reviewer.md:364` + `codex-clean-result-critic.md:368` carry the duty.
