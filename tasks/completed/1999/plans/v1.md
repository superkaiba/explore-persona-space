# Plan v1 — task #1999: HF fan-out pre-stage rule + FLEX preemption escalation

(a) Add a plan-compute-sizing clause: when fanning N boxes over the same HF inputs, pre-stage once and fan from the staged snapshot (or serialize/jitter concurrent same-prefix pulls). (b) Add a compute-backend-failover clause: a multi-hour serial leg (>~2h, no mid-leg checkpoints) relaunched after a first FLEX_START preemption escalates to STANDARD (on-demand), not another FLEX attempt.

snapshot, or serialize/jitter concurrent same-prefix pulls.** A plan
fanning N > 1 boxes / legs / GCE instances over the SAME multi-GB HF
prefix (a shared model repo, a shared dataset prefix on the data repo)
names its staging shape in §9. DEFAULT: pre-stage the prefix ONCE (from
one box, or from the VM's data disk) and fan from that snapshot — via a

### Workload-phase FLEX preemption on checkpoint-less legs → escalate to STANDARD (#1999)

A DISTINCT sibling of the pre-workload boot-loop breaker above: when a
GCP FLEX_START workload has ALREADY STARTED (positive workload signal:
`workload` / `relaunched_workload` phase observed) and is PREEMPTED
mid-run past ~2h wall AND the leg has NO mid-run checkpoints from which
to resume, the per-issue-session's crash-fix/relaunch loop escalates the
next attempt to STANDARD (on-demand) provisioning rather than re-booking
FLEX_START on the same rung. Trigger conjuncts, all three required:

- **Workload-STARTED preemption** — a `terminal_terminated` /
  `terminal_workload_failed` observation preceded by a positive workload
  signal (RESET of the #1029 boot-loop streak is the same signal); the
  pre-workload boot-loop clause above owns the setup-phase case.
- **Wall time ≥ ~2h** at kill (env `EPS_FLEX_ESCALATE_MIN_WALL_H`,

  today.

`dispatch_issue.py launch ... --provisioning-model STANDARD` (or the
equivalent auto-router override that skips the FLEX rung for this leg —
mechanism opt-in per below). The FLEX rung is NOT permanently blocklisted
for this rung/issue — the escalation binds to the RE-LAUNCH after the
matching workload-phase preemption; a subsequent leg with a different
checkpoint contract re-enters the ladder normally.

**Distinctions:**

  workload-started signal + FLEX_START provenance), escalates
  in-provisioning without leaving GCP, and only for legs meeting the
  ≥2h + checkpoint-less conjunction.

above binds PLAN-TIME (§9 row `resume_from_checkpoint:` declaration,
critic-enforced) and PER-SESSION relaunch decisions (the crash-fix loop

## 11. Decision Rationale

**Clause (a) — fan-out staging pre-stage-once vs serialize/jitter default:**

- **What:** DEFAULT `pre-stage once and fan from the staged snapshot`; ALTERNATIVE `serialize / jitter concurrent same-prefix pulls`. Trigger: `N > 1` boxes staging the same multi-GB HF prefix.
- **Why:** pre-stage once is deterministic (no rate-limit race), zero-cost after the first pull, and matches the existing ≥5 GB inline-staging clause's spirit. Serialize/jitter is the fallback when pre-stage is infeasible (e.g. per-box unique prefixes with only accidental overlap).
- **Source:** #1739 (2026-08-01) — 3 concurrent 144 GB pulls, one killed rc=137 on an inferred HF 429 storm, 5 total attempts to land the leg; the body's `unverified hypothesis — verify at plan time: HF 429 storm` labeling is preserved in the inserted text ("an HF rate-limit storm returns 429 (or a TCP/RST that reads as rc=137 to the workload)").
- **Alternatives considered and rejected:**
  - Mechanize in `backends/gcp.py` / `dispatch_issue.py` (a `--pre-stage-hf-prefix` flag or a lane-side pull-once cache) — deferred; body §Scope explicitly permits this as opt-in v1 scope but recommends rule-text-only. The follow-up is documented in the clause's mechanization note.
  - Tighten `docs/api_throughput_guidelines.md` alone — rejected. That doc governs Anthropic API dispatch (judge throughput, sync-vs-batch); it is not where PLAN-TIME staging shape lives. `plan-compute-sizing.md` is the correct home.

**Clause (b) — FLEX→STANDARD escalation on workload-phase preemption:**

- **What:** ONE workload-phase FLEX_START preemption on a leg with (i) ≥ ~2h wall AND (ii) `resume_from_checkpoint: no` → next relaunch pins STANDARD provisioning for the same rung.
- **Why (2h threshold):** #1739's oodhall2 was preempted at transfer unit 30/45 (~2h in) — a preemption at that wall point costs a full 2h+ replay on the next FLEX attempt, which then risks the same preemption. STANDARD (on-demand) is non-preemptible, so the RELAUNCH is guaranteed to run to completion (barring code crashes). Below ~2h wall the cost of a re-preemption is cheap and FLEX remains preferable. Env-parameterized (`EPS_FLEX_ESCALATE_MIN_WALL_H`, default 2.0) so a future tuning can shift without a rule edit.
- **Why (no-checkpoint carve-out):** a leg WITH mid-run checkpoints can resume from the last checkpoint on a re-preemption — the re-preemption cost is bounded by the checkpoint interval, not by full replay. Only the checkpoint-less case has runaway re-preemption cost, so the escalation binds there.
- **Source:** #1739 (2026-08-01) body:
  - oodhall2 rc=137 preemption at 16:37Z, transfer unit 30/45.
  - oodhall3 (a third FLEX attempt) launched anyway.
  - STANDARD switch at 20:37-20:41Z ("no FLEX_START preemption — the fix").
- **Alternatives considered and rejected:**
  - Escalate on FIRST preemption regardless of length — rejected. Short-job spot is already handled by the length-aware ladder's short-branch; adding FLEX-escalation there would double-cover.
  - Fail OVER to RunPod on any workload-phase preemption — rejected. #659 already covers `gcp_workload_failover_runpod` for workload CRASHES of any class. A preemption is not a code bug; escalating in-provisioning (FLEX → STANDARD) keeps the run on GCP where it belongs.
  - Permanently blocklist the FLEX rung for the issue — rejected. The blocklist would over-generalize to subsequent legs with different checkpoint contracts. Bind to the RELAUNCH after the matching preemption only.
  - Do NOT reset `MAX_GCP_ATTEMPTS_PER_DAY` — the escalation does not affect create counts; it only chooses provisioning mode.
