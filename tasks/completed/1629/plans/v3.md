## 4. Design

### 4.1 Detection mechanism (design question 1) — /proc ancestry walk, chosen over registration lookup

**Chosen: (a) ancestry walk.** `tick_triage.py` runs as a Bash-tool child inside the tick turn. Live-verified chain on this session (same runtime shape — Happy-wrapped `/issue` session): `bash(2895644) → claude(2739374, comm=="claude") → node(2739305, the happy wrapper) → node(daemon) → init`. Walk UP from `os.getpid()` via `/proc/<pid>/stat` ppid until the first ancestor with `comm == "claude"`; its **parent** is the happy node wrapper pid. Then `session_resolver._find_happy_log_for_node(node_pid)` → read log → `extract_transcript_from_happy_log` (LAST match). Live-verified end-to-end: node 2739305 → `~/.happy/logs/2026-07-23-07-23-33-pid-2739305.log` → this session's transcript path, which exists on disk.

**Rejected: (b) registration file** (`~/.eps-autonomous/issue-<N>.json` → `happy_session_id` → `find_node_pid_for_session`). Three defects: (i) manual sessions may have no registration (`manual-issue-<N>.json` is written only by `register-current`); (ii) the semantics are wrong — the question is "is a human active in **the session this cron fired into**", and a stale/taken-over registration can name a *different* session; (iii) `find_node_pid_for_session` scans up to 4 MB per candidate log across ALL logs (`session_resolver.py:317,327-380`) — strictly heavier than one filename-keyed lookup. Ancestry answers the right question for the right session regardless of registration state.

**Rejected: env var.** No `CLAUDE_SESSION_ID`/transcript env var exists (probed live); `CODEX_COMPANION_SESSION_ID` happens to equal the session UUID but is a third-party plugin variable — not a contract.

**Happy-log read bound:** `transcript_path` sits near the log HEAD (measured: offset ~4.4 KB in a 354 KB log; in the largest live log, 66.6 MB, the last occurrence sits ~5.2 KB from head = 66.61 MB from EOF), so a tail read of the *log* would miss it — the read must be whole-file, exactly what the watcher already does every 10 min for every live session. Measured live-wrapper log sizes: 0.33–66.6 MB (n=34, fact-checked 2026-07-23; the 227–452 MB logs belong to dead pids from Jul 15–19; `_find_happy_log_for_node` keys on OUR live wrapper's pid + 30-day mtime). A stat-based size guard (`EPM_TICK_HUMAN_LOG_MAX_BYTES`, default 128 MiB — ~2× the largest measured live log; wrapper logs grow monotonically, and a long-lived session crossing the ceiling fails SAFE: skip → no suppression → today's behavior) bounds the whole-file read rather than stalling the tick.

### 4.2 Human-vs-cron row classifier (design question 2) — grounded in 3 real transcripts

Measured row shapes (§12 has the full evidence table):

| Row | `type` | `isMeta` | `message.content` shape | Classify |
|---|---|---|---|---|
| Human typed msg ("where is the URL", "How is it possible…") | `user` | `null` | plain **string**, no `<command-*>` | **HUMAN** |
| Cron/boot slash-command (`/issue-tick`, `/issue 1629`) | `user` | `null` | string starting `<command-message>…</command-message>\n<command-name>…` | automation |
| Skill-load expansion | `user` | **`true`** | list with `text` block ("Base directory for this skill…") | automation |
| Tool result | `user` | `null` | list of `tool_result` blocks | automation |
| User interrupt | `user` | `null` | list with `text` block `[Request interrupted by user]` | **HUMAN** (direct human action) |
| `userType` field | `"external"` on human AND cron rows | — | — | **not a discriminator** |

```python
def is_human_transcript_row(row: object) -> bool:
    """True iff a transcript JSONL row is direct HUMAN input (#1629).

    Conservative toward ticking: any ambiguous / automation-shaped row
    reads False. A human-typed slash command reads False too (wrapped
    identically to a cron-injected one) — acceptable: mistaking a human
    for automation only costs one tick turn, never a stranded task.
    """
    if not isinstance(row, dict) or row.get("type") != "user" or row.get("isMeta"):
        return False
    msg = row.get("message")
    if not isinstance(msg, dict) or msg.get("role") != "user":
        return False
    content = msg.get("content")
    if isinstance(content, str):
        s = content.lstrip()
        if not s:
            return False
        if "<command-name>" in content or s.startswith(("<command-message>", "<local-command")):
            return False
        return True
    if isinstance(content, list):  # the ONE list-shape human signal: the interrupt row
        for block in content:
            if (
                isinstance(block, dict)
                and block.get("type") == "text"
                and isinstance(block.get("text"), str)
                and block["text"].lstrip().startswith("[Request interrupted by user")
            ):
                return True
    return False
```

### 4.4 Hook site in `triage()` (design question 4 — verdict routing)

At `tick_triage.py:775-788`, extend the existing STALE-REDRIVE screen — liveness first (existing behavior byte-preserved), human-activity second:

```python
if verdict == "STALE-REDRIVE":
    live = issue_liveness_reason(events, now, stale_s())          # existing #1051
    if live is None:
        live = human_activity_reason(now)                          # NEW #1629
    if live is not None:
        verdict = "HEALTHY"
        reason = f"status={status}, {age_desc} — {live}"
```

Routing decisions, with rationale:

- **(i) No new verdict word.** The SKILL branch table, the fail-toward-coverage rule, and the runaway/streak machinery all key on the four words; `HEALTHY` + a distinct reason prefix (`human-active`) is the #1051-proven minimal change. Streak/snapshot semantics need zero changes (HEALTHY is already a streak-reset verdict).
- **(ii) TERMINAL / GATE-TRANSITION unchanged.** Teardown is ONE short turn that removes the cron — it *stops all future interruptions*, which is strictly pro-human. Suppressing teardown would keep the cron firing into the interactive thread forever. (This also answers the body's "or tears down its cron" clause: at gate/terminal statuses the existing teardown already IS the cron removal.)
- **(iii) Fail toward ticking.** The blanket `except Exception → None` in `human_activity_reason` plus `None` returns at every resolution miss mean: no transcript, unreadable log, schema drift, oversized log, bare-claude session ⇒ no suppression ⇒ today's exact behavior. The helper can never raise into `triage()`, so the exit-code contract (`main()` exit 0 on any successful triage, non-zero only on state-read failure) is untouched.
- **PARK and ACTIVE both suppressed** (same scope as the #1051 screen, `tick_triage.py:776-779`): the signal means "a human owns this thread NOW" — re-driving 44K tokens into it is the incident regardless of task status. Coverage backstops, stated per class (alternatives-critic correction): for ACTIVE statuses the watcher's independent 10-min passes (DEAD-session respawn, alive-but-stalled respawn, wedge lanes) never consult this check and remain full backstops; for the alive-stalled-at-PARK class the tick is the ONLY recovery (SKILL.md ~197-199 — the watcher deliberately does not respawn PARK sessions), so the backstops there are exactly: the bounded window (re-drive resumes ≤ window + one tick interval ≈ 90 min after the human's LAST message) + the human in the thread as supervisor. The renewal-forever case requires standing human presence — self-limiting and supervised. The SKILL.md edit states this honestly and does NOT imply watcher coverage for the PARK class.
- **Issue-mode only.** The campaign branch (`triage()` line 754) doesn't run the #1051 screen either; campaign sessions are dedicated spawns (`spawn-campaign`), not interactive surfaces. Stated non-goal; a follow-up can extend it symmetrically if a campaign-mode incident ever occurs.

### 4.5 Sustained-interactive CRON-TEARDOWN (design question 6) — scoped OUT

The body marks it optional. Rejected for v1: tearing the cron down on human activity permanently removes tick coverage for that session, contradicting the hard constraint ("stalled-session re-drive coverage unchanged") — a human who drops in for one question mid-autonomous-run would silently disarm the task's last-resort in-session re-driver. The residual cost of keeping the cron is one ~2 s Bash-call turn per 45 min while the human is active (the prompt injection itself is harness-side and cannot be prevented from inside `tick_triage.py`). The human affordances already exist: "pause <N>" (`on_hold` → TERMINAL → teardown) or manual CronDelete. Explicitly documented as a non-goal in the SKILL.md edit.

## 7. Success criteria + kill criteria

**Success:** all §1 criteria green; the incident replay (a transcript with human rows 15.7 min old at tick time — the measured 991161bd values, encoded as a test fixture) yields HEALTHY `human-active (last human msg 16m ago < 45m)`.

**Kill criteria (what would make this design wrong) + fallbacks:**
1. *Transcript rows can't distinguish cron from human* — **already disproved** by direct measurement on the incident transcript (§12 rows 5–8): the wrapper `<command-message>`/`<command-name>` is present on every automated injection observed and absent on every human row. If a future Claude Code version drops the wrapper, the classifier reads cron rows as human → over-suppression; the fallback design is keying on the cron prompt literal (`/issue-tick`) in row text + the kill switch meanwhile.
2. */proc ancestry can't reach the wrapper* (different pid namespace, non-happy runtime) — disproved live for the Happy runtime (§12 row 1); for non-happy runtimes the walk misses → no suppression → today's behavior (named residual, not a kill).
3. *Suppression strands stalled tasks in practice* — operational kill: `EPM_TICK_HUMAN_ACTIVE_PROBE=0` fleet-wide restores pre-change behavior instantly (cron env or shell); the bounded window (§8 risk 1) and untouched watcher passes make this low-likelihood.

## 8. Risks + failure modes

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| False suppression delays a genuine re-drive (human active + task truly stalled) | Medium (by design) | Re-drive delayed ≤ window + 1 tick ≈ 90 min after the human's last message | Bounded window; watcher passes (orphan sweep ~20–105 min, wedge lanes, stalled detector) never consult this check; the human is in the thread |
| An automated injector produces plain-string non-wrapped user rows (future harness change, plain-text `--initial-prompt`) → misread as human | Low (all observed injectors are slash commands → wrapped; verified on an autonomous transcript: the ONLY string user row is the wrapped boot prompt) | Suppression while that session is "active" — bounded by window | Named residual; kill switch; classifier is easy to tighten |
| Happy-log whole-file read slow on a very long-lived session | Low (measured live logs 0.35–27 MB; watcher reads the same logs every 10 min) | Tick turn +tens of ms typical | 128 MiB stat guard skips (no suppression) |
| Transcript schema drift (field renames) | Low | Classifier finds no human rows → no suppression → today's behavior (safe direction) | Fail-toward-ticking by construction |
| Concurrent transcript append during read → truncated last line | Certain occasionally | One skipped row | Per-line guarded `json.loads`; tail re-read next tick |
| `session_resolver` import failure (path quirk in exotic cwd) | Very low (`sys.path[0]`=scripts/ when invoked per the SKILL contract; tests insert scripts/ explicitly) | No suppression | Lazy import inside the guarded helper |
| Added latency on the HEALTHY fresh-marker path | None | — | The check runs ONLY on a would-be STALE-REDRIVE after the #1051 screen misses |
