## Requirement

Close the #2187 outroot-residue check's cross-leg blind spot: `check_outroot_residue` (scripts/verify_uploads.py:1470) computes `residue = names(disk) − (names(HF prefixes) ∪ names(issue-scoped git trees) ∪ discards ∪ exemptions)` where the matching key is the bare BASENAME. The git arm (`_git_tree_basenames_for_issue`, line 1326) is issue-scoped (#2187) but not leg-scoped and carries no content check, so a sibling leg's committed same-named file silently covers the current leg's unpersisted file.

**Incident (2026-08-18, #2333 leg-B):** disk `/workspace/issue2333_out/q35/manifests/upload_done.json` (sha256 `0a052e8b…`) read `outroot_residue: OK` because leg-A's committed `eval_results/issue_2333/q25/upload_done.json` (sha256 `6f43c93d…`, different bytes) shares the basename. Only the verifier's exploratory pass caught it (remediated at `d59466c3c1`).

## Acceptance criteria

1. **Cross-leg false-OK closed (local access):** a disk file whose basename matches ONLY the issue-scoped git arm, where the file is locally readable and its bytes match NO committed same-named candidate, reads as **residue → FAIL**, with the detail naming the disk path AND the committed candidate path(s) ("same basename, different content").
2. **No false-FAIL on true persistence:** a locally readable disk file whose git blob sha1 equals a committed same-named candidate's blob OID stays **covered → OK**.
3. **Pod-side listings degrade to WARN, never silent OK:** a git-arm-only basename match on a disk path with NO local access (pod-side `--outroot-listing`) produces status **WARN** carrying the literal token `outroot-residue-basename-git-only` and naming both the disk path and the committed candidate path(s), so the upload-verifier's exploratory pass knows to byte-check. Residue (FAIL) dominates WARN when both are present.

   Fail-loud pin: tests/test_verify_uploads_outroot_residue.py::test_listing_mode_git_only_match_warns_with_token — asserts status WARN (never a silent OK) with the token present for the unverifiable git-only match.
4. **HF-arm precedence pinned:** a basename resolving at a caller-supplied HF prefix is covered by the HF arm BEFORE any git-arm content logic runs — a both-arms match in listing mode is OK with no WARN token (new test pins this; without it, an implementation checking git first would spuriously WARN every healthy pod-side run whose files are both uploaded and committed).
5. **Everything else unchanged:** HF-prefix matches, declared discards, exemption globs/dirs/suffixes, the no-input SKIP, missing-input ERROR, listing-failure ERROR, the empty-`hf_prefixes` fail-toward-FAIL warning prefix, and the "name-set diff, never the counts" wording all keep their current behavior; all 17 existing tests in `tests/test_verify_uploads_outroot_residue.py` + the prose pins in `tests/test_outroot_residue_prose_pins.py` pass unmodified.
6. **Regression tests** pin the #2333 shape: two legs sharing a basename with different bytes (FAIL), same bytes (OK), the listing-mode WARN, and HF precedence.
7. **The WARN is actionable at the surface that executes it:** the executable Step 2.10 recipe (`.claude/rules/upload-verifier-section-reference.md`) documents the token + the byte-check duty it triggers, and the upload-verifier verdict-table row's outcome vocabulary includes the WARN disposition (a WARN outside the closed verdict set is the #2125 status-vocabulary class).

## Method delta (vs the shipped #2187 check)

The permanent-home GIT arm changes from a bare basename SET to a basename → candidate map carrying each committed candidate's blob OID + size; matching gains a per-file content-disambiguation step that fires ONLY when a basename resolves exclusively via the git arm. HF-arm matches and declared discards are checked FIRST and are unchanged. Content comparison is git-blob-sha1 equality (size equality as the cheap first pass — no hashing when no committed candidate has the disk file's byte size). Per-file LOCAL ACCESS (not the input-mode flag) selects content-check vs WARN, so a VM-side listing still gets the strong check.

**Honestly-named residual (documented, not fixed here):** HF prefixes are leg-scoped by CALLER CONVENTION (`issue<N>_<slug>/…`), not by construction — a caller passing an issue-wide, multi-leg prefix re-opens the same cross-leg basename hole through the HF arm (no content check there). Out of scope per the task body's prescribed fix (git-arm-only); the upload-policy.md clause names this residual so a future caller/task can close it deliberately.

Deliberately NOT done (rejected alternatives):
- **Rel-path-suffix auto-cover in listing mode** (treat a candidate whose committed path component-suffix-matches the disk rel path as covered without a byte check): rejected — same-path-different-bytes (a re-run leg with a stale committed copy) is exactly the loss class this task closes; the WARN keeps the exploratory byte-check in the loop.
- **Leg/slug-scoping the git arm** (filter candidates by leg token): rejected — leg slugs are not derivable from the check's inputs, and a wrong scoping rule reintroduces silent false-OK/false-FAIL; content equality is ground truth.
- **Weakening to WARN in local mode on content mismatch:** rejected — fail-toward-FAIL is the check's standing posture (#2187); unpersisted bytes are a FAIL.

## Concrete changes (scripts/verify_uploads.py)

1. **`_verifier_repo_root() -> Path`** — new 3-line helper returning `Path(__file__).resolve().parent.parent`; `_issue_branch_ref` and the new git-arm helper call it. This is the hermetic-test seam (tests monkeypatch it to a temp git repo so the real subprocess arm runs against real committed fixtures — the mid-flight live tree is not a stable fixture).
2. **`_git_tree_candidates_for_issue(issue_num) -> dict[str, list[_GitCandidate]]`** — supersedes `_git_tree_basenames_for_issue` (old helper DELETED per the supersede rule; verified zero callers outside this file). Runs `git ls-tree -r -l <ref>` (long format: `<mode> <type> <oid> <size>\t<path>`) over the same refs as today (issue branch if any, then HEAD), keeps `type == blob` rows whose path passes `filter_issue_scoped_git_paths`, and returns basename → list of `_GitCandidate(path, oid, size)` (a small NamedTuple). Fail-loud `RuntimeError` on a non-zero ls-tree exit, exactly as today.
3. **`_git_blob_sha1(path) -> str`** — hashlib sha1 over `b"blob %d\x00" % nbytes` + file bytes (chunked read; matches `git hash-object` for SHA-1 repos, which this repo is; no LFS/text filters in `.gitattributes` affect committed blob OIDs here — critic-verified).
4. **`check_outroot_residue` matching loop (step 3 of the function)** becomes per-file, HF/discards FIRST:
   - basename ∈ HF-arm basenames or ∈ `discarded_names` → covered (unchanged; ORDER IS LOAD-BEARING — acceptance criterion 4).
   - else basename ∈ git candidates:
     - `Path(full).is_file()` (local access): size first-pass — candidates with `size == st_size`; if any, compare `_git_blob_sha1(full)` against their OIDs; an OID match → covered. No size match or no OID match → **residue**, reason `same basename, different content — committed candidate(s): <paths>` (the cross-leg clause). An `OSError` reading the file → **residue** with the error named (fail-toward-FAIL).
     - no local access → **git-only-unverified**: collect `(full, candidate paths)`.
   - basename nowhere → residue (unchanged).
5. **Verdict:** residue non-empty → FAIL (existing wording + the per-file cross-leg reasons; if git-only-unverified files also exist, the FAIL detail names them too). Residue empty but git-only-unverified non-empty → **WARN**, detail leading with the token: `outroot-residue-basename-git-only: N file(s) matched ONLY issue-scoped git basenames and have no local bytes to compare — byte-check in the exploratory pass: <disk path> ~ <candidate paths>; …`. Both empty → OK (detail gains `content-verified=<n>` for the git-arm-verified count). The `warn_prefix` (empty `hf_prefixes`) composes with all three as today. The report's overall-verdict logic already maps a WARN row to verdict WARN (line 2703) — no change needed there.
6. **Docstring updates** on `check_outroot_residue` (the new match semantics + WARN token) and the module-level `# Out-root residue sweep` comment block.
