## 1. Goal (verbatim intent from the task body)

Make Step 10d Guard 3's mainline probe distinguish the two cases it currently
conflates:

- **(A) the #479 class the guard exists to catch** — the branch was forked off
  another `issue-<M>` branch that is itself still unmerged, so a blind rebase
  would replay the parent's stale `src/` / `scripts/` onto `main`;
- **(B) a benign second-parent landing** — the merge-base IS an ancestor of
  `origin/main`, but it entered `main` as a merge commit's SECOND parent
  (produced by the fleet's own prescribed scratch-worktree merge-form landing,
  `#1489` / `#1128`).

Today both read `ON_MAINLINE=no` and both route to the artifact-confirmed
degrade.

## 2. Root cause (verified against the live surface, and empirically)

`.claude/skills/issue/SKILL.md:11703-11709`:

```bash
BEHIND=$(git -C "$WT" rev-list --count HEAD..origin/main)
MB=$(git -C "$WT" merge-base HEAD origin/main)
ON_MAINLINE=$(git -C "$WT" rev-list --first-parent origin/main \
  | grep -Fxq -- "$MB" && echo yes || echo no)
```

`rev-list --first-parent origin/main` walks ONLY first parents, so every commit
that entered `main` as a merge's second parent is absent from the walk — even
though it is fully reachable from `origin/main`. Case (B) therefore reads `no`.

Worked instance (#2319, 2026-08-15), **empirically confirmed in the #2320
worktree**: `MB = 17291d7a6b315525964b89b608f89ee277eaec32` →
`merge-base --is-ancestor "$MB" origin/main` = **YES**, while
`rev-list --first-parent origin/main | grep -Fxq -- "$MB"` = **no**. It entered
via `d697efaef6 "Merge remote-tracking branch 'origin/main' into HEAD"` (task
#2317's landing) as that merge's SECOND parent. #2319's own three-dot diff was
two files, both its own deliverables.

Realized cost: **#1144** — a whole follow-up task filed to port stranded shared
`src/` fixes (including a fleet-relevant CVD pin) after Guard 3 refused the full
rebase (`ON_MAINLINE=no`, `BEHIND=3004`) and the round landed via the surgical
additive checkout, which is `--diff-filter=A` only and structurally cannot carry
MODIFIED files.

## 3. The three open design questions — SETTLED

The task body explicitly delegates these to the plan. Each is settled below with
rationale; none is guessed.

### Q1 — replace the first-parent read with `merge-base --is-ancestor`, or join them?

**Decision: REPLACE as an UNSAFE trigger, and RETAIN the first-parent read as a
recorded diagnostic only.**

Rationale — and the correction the task body's candidate fix needs:

> `git merge-base HEAD origin/main` returns, *by definition*, a common ancestor
> of `HEAD` and `origin/main`, and `--is-ancestor` tests FULL (all-parent)
> reachability rather than first-parent reachability. Therefore
> `git merge-base --is-ancestor "$MB" origin/main` is **TAUTOLOGICALLY TRUE**
> whenever `MB` is non-empty.

The task body's counter-argument — that merge-base "can return a commit
reachable only through a second parent", so the ancestry test is not trivially
true — conflates a first-parent walk with ancestry. A second-parent-reachable
commit *is* an ancestor. So the candidate fix does not repair the probe; it
makes the arm **vacuous**, i.e. deletes the `ON_MAINLINE` UNSAFE trigger in all
but one situation. That situation is the only informative one and must be a
**fail-loud** condition, not a silent pass:

- `MB` empty / `merge-base` non-zero exit ⇒ no common ancestor (unrelated
  histories, `origin/main` not fetched, corrupt ref) ⇒ **UNSAFE, hard-stop**.
  (Today an empty `MB` happens to read `ON_MAINLINE=no` via the `-Fxq`
  empty-pattern non-match, i.e. an UNSAFE degrade — so the hard-stop is
  strictly louder than today, never a loosening.)

Consequence for the guard's stated purpose: **the first-parent read never was a
sound test for case (A) either.** When a branch forks off an unmerged sibling
`issue-<M>`, `merge-base(HEAD, origin/main)` is the point where `issue-<M>`
itself forked from `main` — an ordinary mainline commit — so case (A) reads
`ON_MAINLINE=yes` in the common shape. The probe is simultaneously
false-POSITIVE on (B) and false-NEGATIVE on (A). Adopting the ancestry form
therefore requires the load to move to the content check (Q2), which is what
actually catches #479 (SKILL.md:11796-11800 already says the #479 own-diff
"carries the whole parent payload, failing the content check").

**Alternative probe CONSIDERED and REJECTED (explicitly, not by omission).**
A non-vacuous test for case (A) would be: does any commit in `MB..HEAD` appear
on another `refs/remotes/origin/issue-*` ref? Rejected on two grounds. (i) It is
parent/child **symmetric**: a branch forked off THIS one, or any ref sharing
this branch's own unmerged commits, fires it identically to a genuine unmerged
parent — reintroducing exactly the false-UNSAFE class this task exists to
remove. (ii) It is unbounded work over a ref namespace that accumulates stale
`origin/issue-*` refs, on the hot path of every merge. The content check covers
the realistic #479 shape structurally: a still-unmerged sibling's payload lives
under its own namespaces (`scripts/issue<M>_*`, `figures/issue_<M>/`, `src/`
modules neither this task's plan nor its review touched), which are out-of-scope
by construction.

The first-parent read is preserved as `MB_FIRST_PARENT=yes|no`, reported on the
`epm:merged` note. It stays a real signal about *how* the base landed; it is
simply not evidence of an unsafe rebase.

### Q2 — does the content check alone suffice once ancestry passes?

**Decision: YES — but ONLY after the content check is made UNCONDITIONAL. It is
not unconditional today, and shipping Q1 without this is a fail-OPEN.**

Today (SKILL.md:11714-11722) the own-diff content check is *triggered* by
`BEHIND` exceeding a threshold (default 200):

> "`BEHIND` exceeding the threshold (default `200` commits) instead TRIGGERS the
> own-commit content check"

With `ON_MAINLINE` demoted to a diagnostic, a branch with `BEHIND <= 200` would
run **no** scope arm at all. In this repo `BEHIND` is routinely in the hundreds
(~100+ marker commits/hr fleet-wide), so the window is narrow — a same-hour
branch — but it is exactly the window in which two concurrent sibling branches
exist, i.e. the #479 shape. Making the check unconditional also closes a
**pre-existing** hole: today a #479-class fork with `BEHIND <= 200` and a
mainline fork point reads `ON_MAINLINE=yes` and is never content-checked at all.

So: run the own-diff content check on **every** branch. Cost is one three-dot
`--name-only` diff plus one `log` per workflow-surface path — the same work the
`BEHIND > 200` path already does today, now always.

This is the change that discharges acceptance criterion 4 ("the change cannot
let a branch carrying another branch's payload rebase-merge"): a branch that
carries a sibling's payload has that sibling's files in its own three-dot diff,
out of this task's deliverable scope ⇒ UNSAFE ⇒ artifact-confirmed route,
exactly as before.

### Q3 — should the artifact-confirmed route refuse a MODIFIED-file payload whose files `main` advanced (blob-identity check)?

**Decision: REJECT the blob-identity refusal as proposed; ADOPT a fail-loud
surfacing of the stranded set instead.**

Rationale (verified at SKILL.md:11992-11994 / 12017 and 14550-14574):

- The **clobber** hazard the question is aimed at is closed by design. Both the
  fast-path predicate (e) and the surgical additive checkout are
  `--diff-filter=A` ADDED-only, with the reason spelled out in-line: "A-only
  guarantees every listed path does not yet exist on main, so the checkout only
  CREATES — never clobbers." A blob-identity check would guard a state the
  A-only design already excludes.
  *Residual, stated precisely rather than claimed away:* `--diff-filter=A` on a
  three-dot diff means "added relative to the merge-base", not "absent from
  current `origin/main`". A path added INDEPENDENTLY on `main` since the
  merge-base (realistically only a `.claude/` file, e.g. an agent-memory slug
  collision) would still be overwritten by the wholesale checkout. That residual
  is PRE-EXISTING, untouched by this plan, and out of scope here — recorded so
  the "cannot clobber" framing is not read as absolute.
- The **real** residual harm is the opposite one: **silent stranding**. A
  genuine-UNSAFE branch whose payload MODIFIES shared `src/` / `scripts/` lands
  its ADDED artifacts, posts `epm:merged`, and reports success while the
  modifications stay on the branch. That is #1144 verbatim. The existing
  new-shared-`src/` guard (SKILL.md:14459-14463) covers only `--diff-filter=A`
  additions, so MODIFIED shared files fall straight through it. The asymmetry is
  principled: a stranded NEW module breaks downstream import paths on a clean
  `main` (#595, hence the refusal); a stranded MODIFIED file leaves `main`
  self-consistent but stale.
- A blocking refusal on that shape would be fail-closed but changes merge
  behavior for branches unrelated to this bug and can wedge landings
  fleet-wide. The proportionate fix, aligned with fail-fast-never-hide, is to
  make the stranding **loud** without adding a new blocking route.

**Adopted:** on the artifact-confirmed path, compute the branch's MODIFIED
shared `src/` / `scripts/` set and, when non-empty, (i) record it on the
`epm:merged` note as `stranded_modified: [...]`, (ii) surface ONE chat line
naming the branch, the worktree path, and the stranded paths, and (iii) continue
(the merge still lands the artifacts; the round is not blocked). No new refusal,
no fail-open.
