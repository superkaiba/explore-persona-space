## 0.0 TL;DR (plain English)

**B2. **B3. New paragraph + fenced block, inserted after the #1041 paragraph (~9250):**

> **Known failure shape 2 — mergeability conflict under fleet marker churn (`GraphQL: Pull Request has merge conflicts (mergePullRequest)`, #1128).** Between the Guard-1 snapshot and the server-side rebase, `main` advances (~100+ `tasks/` marker commits/hr), so the strip commit's snapshot replays stale and conflicts. Recovery: re-snapshot against a freshly captured `main` SHA and retry ONCE — documented, never silent, and gated on the re-snapshot actually changing something (an unchanged tip would fail identically; go straight to the merge-conflict recovery instead). This shape typically arises when foreign `tasks/` content entered via merge commits (worktree `pull --rebase=merges`) plus a stale strip; when an ORDINARY branch commit itself touched foreign `tasks/` at stale content, the re-snapshot cannot fix that commit's replay and the retry will fail again — the fall-through to the merge-conflict recovery below covers it.

```bash
# Re-snapshot-and-retry (ONCE per Step 10d invocation) — fires ONLY on
# the mergeability-conflict shape above.
TIP_BEFORE=$(git -C "$WT" rev-parse HEAD)
# Re-run the ENTIRE Guard-1 block above VERBATIM: it re-fetches, captures
# a fresh MAIN_SHA, re-pins the foreign paths, and commits only if
# anything changed (idempotent).
#
# Retry only if the re-snapshot changed the branch tip OR unpushed
# commits exist (same rev-list re-derivation as the safe-case push;
# missing ref counts as unpushed):
if [ "$(git -C "$WT" rev-parse HEAD)" = "$TIP_BEFORE" ] \
   && [ "$(git -C "$WT" rev-list --count origin/issue-<N>..HEAD 2>/dev/null || echo 1)" -eq 0 ]; then
  echo "re-snapshot changed nothing (tip unchanged, nothing unpushed) — a retry would fail identically; fall through to the merge-conflict recovery below"
  false
fi
git -C "$WT" push origin issue-<N> \
  || { git -C "$WT" pull --rebase=merges --autostash \
       && git -C "$WT" push origin issue-<N>; }
# The re-snapshot commit changed the branch tip, so the SHA-bound lint
# verdict is now STALE and the gated conditional would fail CLOSED.
# Re-run the executable Pre-push workflow-lint gate block (subsection
# above) so the verdict re-binds to the NEW tip (never hand-write it,
# #1082), then re-enter the SAME gated merge conditional (--rebase form)
# exactly once. If THAT merge is refused too, fall through to the
# merge-conflict recovery below. Record the retry either way in the
# epm:merged / epm:merge-failed note:
#   resnapshot_retry: {tip_before: <TIP_BEFORE>, main_sha: <fresh MAIN_SHA>,
#                      stripped_again: yes|no, outcome: merged|refused}
```

(If the re-run Guard-1 created NO new commit but unpushed commits existed — e.g. a crash between an earlier strip and its push — the push alone can fix the server-side view and the retry is warranted; the tip is then unchanged, so the still-valid SHA-bound verdict re-certifies it and no gate re-run is needed. The gate re-run instruction applies exactly when the tip changed — the conditional's stale-sha arm enforces this mechanically either way, failing closed if skipped.)

### Edit C — merge-conflict recovery: mechanical foreign-`tasks/` resolution + verification

**Current block opening (~9277–9284):**

```bash
git -C "$WT" fetch origin main --quiet
git -C "$WT" merge origin/main          # conflicts surface HERE, in the worktree
# Resolve each conflict in the worktree (keep main's version of anything
# outside this task's deliverables), then:
git -C "$WT" add <each resolved file>
git -C "$WT" commit --no-edit
```

**Replacement:**

```bash
git -C "$WT" fetch origin main --quiet
# Capture the snapshot ONCE, immediately after the fetch, and merge THAT
# SHA — origin/main is a shared ref a concurrent session's fetch can
# advance between these commands (#1128's shared-ref race).
MAIN_SHA=$(git -C "$WT" rev-parse origin/main)
git -C "$WT" merge "$MAIN_SHA"          # conflicts surface HERE, in the worktree
# Foreign tasks/ conflicts are resolved MECHANICALLY: take the captured
# snapshot's version wholesale (under fleet marker churn main is
# authoritative for OTHER tasks' state — the #1128-proven recovery:
# foreign tasks/ pinned to ONE captured main SHA). Materialize the
# conflicted-path list first and check its own exit code (#1184 shape):
git -C "$WT" diff --name-only --diff-filter=U -- 'tasks/' \
  > /tmp/issue-<N>-recovery-foreign.txt \
  || { echo "recovery: conflicted-paths diff FAILED — resolve by hand per the prose below"; false; }
grep -Ev "^tasks/[^/]+/<N>/" /tmp/issue-<N>-recovery-foreign.txt \
  > /tmp/issue-<N>-recovery-foreign-only.txt || true
# checkout <sha> -- <path> resolves each U path to the snapshot's version
# and stages it. It fails loud on a path absent at $MAIN_SHA (a
# delete/modify conflict — resolve that one by hand). xargs -r: an empty
# list must not run a pathspec-less checkout.
xargs -r -a /tmp/issue-<N>-recovery-foreign-only.txt \
  git -C "$WT" checkout "$MAIN_SHA" --
# THIS task's own tasks/*/<N>/ conflicts and all non-tasks/ conflicts:
# resolve in the worktree (keep main's version of anything outside this
# task's deliverables), then:
git -C "$WT" add <each resolved file>
git -C "$WT" commit --no-edit
# Post-resolution certification (the #1128 verification): the branch tree
# must now be IDENTICAL to the captured snapshot over tasks/, modulo this
# task's own folder — materialize, then check (fail-loud):
git -C "$WT" diff --name-only "$MAIN_SHA" HEAD -- 'tasks/' \
  > /tmp/issue-<N>-recovery-tasks-verify.txt \
  || { echo "recovery: tasks/ verification diff FAILED — do NOT push"; false; }
if grep -Ev "^tasks/[^/]+/<N>/" /tmp/issue-<N>-recovery-tasks-verify.txt | grep -q .; then
  echo "recovery: foreign tasks/ still differ from the captured main snapshot — do NOT push; re-pin the listed paths to \$MAIN_SHA and re-verify"
  false
fi
```

The rest of the recovery block (lint-gate re-run, gated push, `--squash` retry per shape 1) is unchanged. Note the verification can list foreign paths legitimately when `main` advanced AFTER `MAIN_SHA` was captured and the branch pinned to `MAIN_SHA` — it cannot: the diff is `"$MAIN_SHA" HEAD`, both fixed, so it lists only paths where the branch tree still differs from the captured snapshot. That is exactly the invariant #1128 verified ("verified empty two-dot diff").

## 11. Decision Rationale

N/A — no model training; N/A — no behavioral construct. Design decisions grounded:

- **Retry count = 1, then fall through to the existing recovery.** *Why:* #1128 needed exactly one fresh re-pin to make the tree mergeable; more retries only re-roll the same seconds-scale race at increasing cost, and the recovery merge is the guaranteed-progress path (merge cares about endpoints, not per-commit replay). *Source:* #1128 `epm:merged` note (one pinned re-snapshot per recovery merge sufficed); the existing "One recovery attempt per Step 10d invocation" precedent (~9315).
- **Trigger = the `Pull Request has merge conflicts (mergePullRequest)` error text only; `can't be rebased` keeps the #1041 squash path; everything else routes to recovery.** *Why:* the two shapes have disjoint causes (stale content vs merge-commit topology) and disjoint fixes; classifying by error text is how the recipe already routes #1041. *Source:* #1210 body transcript quote; #1041 (SKILL.md ~9236–9250); #1128 note.
- **Pin to one captured `MAIN_SHA` rather than `origin/main` throughout Guard 1 and the recovery.** *Why:* the shared-ref race is documented in the founding incident ("a concurrent session's fetch advanced origin/main between merge and re-sync"). *Source:* #1128 `epm:merged` note, verbatim.
- **Fetch failure in Guard 1 = WARN, not terminal.** *Why:* freshness affects conflict probability, not the correctness of the no-foreign certification (which the #1184 fail-loud arm protects); a terminal fetch failure would convert transient network blips into spurious `epm:merge-failed` rounds — a regression vs today (which never fetches at all). *Source:* #1184 (what fail-loud protects: certification), current Guard-1 behavior (read at HEAD).
- **Retry gated on tip-changed/unpushed predicate.** *Why:* an unchanged, fully-pushed branch retries into an identical server-side state — a guaranteed second failure; the predicate reuses the safe-case block's established rev-list re-derivation. *Source:* SKILL.md ~9182–9193 (#787 re-derivation rationale).
- **Alternatives considered:** (a) **re-snapshot-and-retry-once + fresh pinned Guard 1 + mechanical recovery — CHOSEN**: fixes the common case pre-merge (snapshot age drops from hours to seconds), bounds the retry, and mechanizes the proven recovery for the rest. (b) **Mechanize the recovery only**: leaves the first attempt routinely failing under churn; every failure then forces a recovery merge commit → #1041 squash → loss of per-commit revert granularity as the ROUTINE outcome, plus ~2 extra orchestrator rounds each time. Rejected as sole fix; its mechanical-resolution half is INCLUDED (Edit C). (c) **History rewrite** (rebase/filter the branch so no commit touches foreign `tasks/`): requires force-pushing a PR branch (user-ask-only per project safety rules), invalidates the SHA-bound verdict and review-round provenance, and is genuinely risky on branches carrying merge commits. Rejected. (d) **Document the recovery only, no pre-merge change**: cheapest, but the first attempt keeps failing routinely (~100+ commits/hr churn vs a snapshot that can be hours old), which (b)'s squash-granularity cost then makes the norm. Rejected. (e) **Always `--squash` for wf-fix branches**: squash performs the same 3-way merge against live main, so it conflicts on the identical stale foreign-`tasks/` content — it dodges nothing. Rejected.
- **Residual accepted:** the seconds-scale fetch→merge window; the rare ordinary-commit-touches-foreign-tasks case. Both route to the (now mechanized) recovery — stated in the Known-failure-shape-2 prose.
