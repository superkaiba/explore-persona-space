## 3. Mechanism — verified against `man 3 mallopt` on this VM

The candidate block's proposed rule text is **mechanically wrong in two places**. Shipping it
would put a false statement into the very rule this task exists to make authoritative, so the
plan corrects it. Every claim below is quoted from `man 3 mallopt` on this box:

1. **131072 IS glibc's default.** "Balancing these factors leads to a default setting of
   `128*1024` for the `M_MMAP_THRESHOLD` parameter", and "The initial value of the threshold
   is `128*1024`". So the pin does **not lower** the threshold — it **freezes the ratchet at
   the default**. The candidate's "multi-GB tensor retention" framing is wrong.
2. **The affected band is 128 KiB - 32 MiB per allocation.** "when blocks larger than the
   current threshold and **less than or equal to `DEFAULT_MMAP_THRESHOLD_MAX`** are freed, the
   threshold is adjusted upward to the size of the freed block", where
   `DEFAULT_MMAP_THRESHOLD_MAX` is "`4*1024*1024*sizeof(long)` on 64-bit systems" = **32 MiB**.
   An allocation above 32 MiB always mmaps regardless of the tunable — a genuinely multi-GB
   tensor is NOT the case this knob addresses. The real shape is MANY MEDIUM blocks (#825's
   ~7 MB per-conv tensors sit squarely in the band).
3. **The ratchet also stops heap trimming.** "When dynamic mmap thresholding is in effect, the
   threshold for trimming the heap is also dynamically adjusted to be **twice** the dynamic
   mmap threshold." So one ratchet event both stops mmap-ing the block class and doubles the
   trim threshold — which is why the pages stop returning.
4. **The fix works by disabling dynamic adjustment.** "Dynamic adjustment of the mmap
   threshold is disabled if **any** of the `M_TRIM_THRESHOLD`, `M_TOP_PAD`,
   `M_MMAP_THRESHOLD`, or `M_MMAP_MAX` parameters is set." This matches #1336's own wording.
5. **The candidate's size-axis discriminator inverts the truth.** It proposes "arena
   fragmentation = RSS growth across MANY SMALL passes; this = step change across FEW LARGE
   load/free cycles". Both signatures are in fact *the same observable*: RSS grows across
   passes with no single huge allocation — which is exactly why #825 described its symptom in
   the same words `code-style.md:46` already uses for arena fragmentation. Pass count and
   block size do not separate them. **REJECTED**; replaced by the ordering discriminator in
   §4.
6. **Numerically inert, NOT throughput-inert.** The man page names the costs of mmap-ing a
   block: it "is not placed on the free list for reuse by later allocations", "memory may be
   wasted because `mmap(2)` allocations must be page-aligned", and "the kernel must perform
   the expensive task of zeroing out memory allocated via `mmap(2)`". A workload that rapidly
   churns 128 KiB - 32 MiB blocks pays those per block instead of reusing an arena chunk. This
   is the load-bearing reason the promotion is **conditional** (§5 D1), not a universal 6th pin.

## 4. The spine of the fix — an existing statement is incomplete

`code-style.md:46` currently ends:

> Corollary: RSS still growing across passes UNDER the arena cap indicates a genuine leak, not
> fragmentation.

That corollary is **incomplete**, and its incompleteness is the workflow gap that cost #825
run 5 and #1336 surface 7: the mmap ratchet is a THIRD branch, and it presents identically.
The correct discriminator is ordering, not size:

1. RSS grows across passes, no single huge allocation → arena fragmentation OR the mmap
   ratchet. Cap the arenas first (`MALLOC_ARENA_MAX=2`).
2. Still growing under the arena cap, and the phase frees blocks in the 128 KiB - 32 MiB band
   → the mmap ratchet. Add `MALLOC_MMAP_THRESHOLD_=131072`. **Band membership is DEFAULT-IN
   under uncertainty:** an author usually cannot evaluate the band ex ante, and the knob is
   numerically inert, so the branch is taken unless the loop is KNOWN to churn only
   sub-128-KiB blocks. A conditional an author cannot evaluate would reproduce the
   rediscovery-by-OOM path this task exists to close.
3. Still growing under BOTH → genuine leak.

The two fixes are independent and composable. Correcting the corollary to route through the
ratchet before concluding "leak" is the single highest-value line in this diff.
