## Smoke blind-spot enumeration

What a PASS of this round's declared verification does **not** certify. Written
plan-side per `.claude/rules/smoke-blind-spots.md`; the implementer mirrors it
under `## Smoke run` and extends it if the realized code adds a branch not
anticipated here.

- **(a) Gates the `--dry-run` path skips.** `--dry-run` short-circuits four
  decision sites, so a dry-run PASS certifies none of them: the `npm install
  -g` upgrade (`codex_auto_upgrade.py:521`); the current-model probe and its
  in-band auth-token refresh (`:564`); the candidate probe plus
  `write_config_model` → `atomic_write` config write (`:599-619`); and
  `restart_app_server`'s kill path, which returns early at `:439` before the
  in-flight re-check and the TERM/KILL sequence. Additionally, because no
  dry-run branch appends to `changed`, `restart_app_server` is never called at
  all under `--dry-run` (the `if changed and ...` guard at `:637`).
- **(b) The wrapper test's substituted implementation.** The added wrapper test
  drives the real script through its documented `EPS_CODEX_UPGRADE_BIN`
  test-only override (`cron_codex_auto_upgrade.sh:70-76`), so it exercises the
  `if` arm, never the production `else` arm that invokes
  `uv run python scripts/codex_auto_upgrade.py` under the PATH and OMP env.
  That production arm is certified by nine days of daily cron runs, not by any
  test this round adds.
- **(c) The stale-token vacuous pass — the reason criterion 8 changed.** Under
  `--dry-run` the current-model probe is skipped (`:564`), and that probe is
  what refreshes the hourly auth token in-band (the module's own comment at
  `:556-558`: a bare HTTPS call to the models endpoint just 401s). With a stale
  token, `fetch_models` catches the 401 as `urllib.error.URLError` and returns
  `None` (`:270-272`), `main()` logs "no models listing — leaving model
  unchanged" (`:578`), and since `current_broken` is `False` in dry-run mode
  `failed` stays `False` — so the run exits 0 having exercised no probe, no
  selection, no config write and no kill. v2's criterion ("exits 0 and reports
  no change") was satisfiable by that path. Verified non-vacuous at plan time:
  the actual run logged "model already best available (gpt-5.6-sol, priority
  1)", which is only reachable through a real listing, so the token was live —
  but the *criterion* had to be tightened, because that line was not required.
- **(d) `shellcheck` is absent on this VM,** so the wrapper's static coverage is
  `bash -n` plus the added behavioral test. Stated, not worked around.

## Method delta

The upgrader is not redesigned. It exists and has nine days of production
evidence; that outranks any smoke this round could run for the unchanged arms,
and re-deriving its design would be waste. The round is **review + close the
identified gaps + land + reconcile.** The critic confirmed this posture is
sound and that the plan defers only re-derivation, not review — the Step 5
ensemble stays on.

Three review targets for the ensemble to confirm or overturn:

- **The wrapper `cd` gap.** `cd "$PROJECT_DIR" || exit 1`
  (`cron_codex_auto_upgrade.sh:69`) sits inside the brace group. The group is
  not a subshell, so that `exit 1` terminates the whole script before the
  `rc != 0` Telegram arm at `:89`. With no MTA and the crontab redirecting
  stderr, a failed `cd` is completely silent — defeating the alerting the
  wrapper was written to provide. v3 fixes it (§ File paths).
- **Wrapper doc/reality drift.** The header comment recommends `17 6 * * *`;
  the installed crontab is `17 7 * * *`. Harmless, but that comment is the only
  schedule documentation that will exist in the repo, so it is corrected.
- **`main()`'s probe-fail → known_bad → exclude ordering (`:569-583`).** The
  current-model probe records a failing model into `known_bad` (`:569-574`)
  *before* `candidate_models` filters on it (`:583`), and the filter is keyed
  `bad.get("cli_version") == version_str(cli_version)` (`:294-296`) so the
  just-written entry is excluded at the current CLI version. That ordering is
  the entire mechanism behind kill criteria 1 and 3. Verified statically at
  plan time; v3 also pins it with a test (Recovery pin above) so it cannot
  regress silently.

### Landing mechanism — a recorded deviation from Step 4's worktree default

Committed **by explicit path directly on `main` at the repo root**, not via an
`issue-2322` worktree. The payload exists as *untracked files in the repo-root
working tree*, and the live crontab points at the repo-root path. Git refuses
to overwrite untracked working-tree files on merge/pull regardless of content,
so a worktree branch would land tracked files at three paths the root holds as
untracked and collide on the root's next pull. `sync_repo_root.py` rescues that
collision rather than failing, but it is entirely avoidable and this is a
shared root with ~40 concurrent sessions. Explicit-path commit on `main` is the
documented concurrent-committer form (CLAUDE.md § Concurrent repo-root
committers). The worktree merge is not itself a review gate — review and Step
9c both precede the commit — so nothing is dodged. Consequence: no Step 10d
merge, and no worktree to reap.

**Commit hygiene (measured, not assumed).** 14 files are currently staged in
the shared repo-root index by *other* sessions, and 1 tracked file is modified.
The landing commit therefore uses an explicit pathspec
(`git commit -F <msg> -- <the three paths>`); a bare `git commit` would sweep
another session's staged work into this task's commit (#1894).

**Edit-window hygiene.** This round edits, in place, files a live cron executes
daily at 07:17 local. Plan time is 16:12 local, so there is ~15h of headroom —
no risk of the fire time landing on a half-written wrapper. The two edited
files become tracked-modified only inside a single write → `git add` → commit
window: untracked files are immune to the pre-commit stash race, but
staged-but-uncommitted ones are exposed to the bare-commit sweep
(`.claude/rules/repo-root-uncommitted-state.md`).

## Kill criteria

What would stop this landing rather than merely bounce a round. All four are
adjudicable without a live `codex exec` probe, as the critic confirmed:

1. **The upgrader can leave `~/.codex/config.toml` pointing at a model that has
   not just answered a probe.** Static property: the only config-write site
   (`:619`) is reachable only after `probe_model` returns ok at `:604`. If
   review overturns that, the live cron can silently break every twin dispatch
   and the crontab line is disabled before anything lands.
2. **The in-flight abort can lose a running twin review** — i.e. the 2h
   `JOB_FRESH_WINDOW_S` bound can classify a genuinely live job as debris.
   Adjudicated as a design read of `_job_age_s` (`:159-184`) against durable
   duration evidence in the companion jobs index (`COMPANION_STATE_DIR`
   `*/state.json`): the reviewer checks realized twin-review durations —
   `xhigh` reviews run long — and whether a single `codex exec` exceeding 2h
   advances the job record or the state-file mtime mid-run. If it does not, a
   genuinely live job ages past the window and the pre-kill re-check at `:445`
   reads it as debris. That would degrade a doubled review gate to
   single-Claude — the exact failure the payload's own docstring says it exists
   to prevent.
3. **The known-bad filter fails to exclude a broken current model.** Static
   plus test-pinned: `candidate_models` (`:294-296`) keys on slug + CLI
   version, and `main()` records before it filters (`:569` → `:583`). Failure
   here reinstates the "no-op that looks healthy" mode.
4. **The added dry-run test FAILS against the current code** — i.e. `--dry-run`
   already mutates something. Then the verification path recorded in the task
   body was never a dry run, and the finding is reported before anything lands.

Any of those: post `epm:failure`, do not land, surface the live cron.

## Open item — the `model_reasoning_effort` discrepancy

Body Part 1 records `~/.codex/config.toml` `model_reasoning_effort`
`xhigh` → `high`. The live config reads `xhigh`. The upgrader provably did not
do this — it never writes that key (docstring plus `write_config_model` both
scope to the top-level `model` key, and
`test_write_config_model_replaces_only_the_model_line` pins that) — so either a
later manual edit restored `xhigh` or the Part 1 record was wrong.

Disposition: **document, do not change.** The originating ask was "the best
model (with reasonable amount of thinking)", and for every EPS ensemble
dispatch that is already satisfied: `codex_task.py` passes `--effort high`
explicitly on the command line (`codex_task.py:1711` sets the default, and the
dispatch at `:636-637` passes it through), which overrides the config default.
The config value therefore governs only Thomas's own interactive `codex` use,
where `xhigh` may well be his preference. Changing it would be an unrequested
mutation of a personal config outside the repo. Recorded in the body so the
next reader is not misled by the Part 1 claim.
