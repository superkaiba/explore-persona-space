### Item 2 — Fleet unblock: reactive file-count overflow fallback (non-destructive code)

**Goal:** adapter uploads to the canonical model repo keep landing (on the private overflow repo) while the canonical repo is at the limit — mechanizing #1090's manual rescue.

**Design decision — on-rejection fallback, NOT a pre-probe (justification):** there is no cheap count probe — `repo_info(files_metadata=False).siblings` truncates on large repos (#375/#399) and carries no count field, so a reliable pre-count costs a full ~100-page enumeration (35 s + ~100 Hub requests against the 2,500 req/5 min org quota) per upload, and is TOCTOU-stale between probe and push. The server's own rejection is authoritative, free, and by construction can only fire when the canonical push has ALREADY failed — an on-rejection fallback can never reroute a push that would have succeeded. Therefore: no probe, no cache; catch the rejection and reroute.

**Requirements:**
1. `hub.py`: new predicate + env gate:
```python
def _filecount_fallback_enabled() -> bool:
    """Default-ON kill switch for the reactive file-count overflow fallback."""
    return os.environ.get("EPM_HF_FILECOUNT_FALLBACK", "1") == "1"

def _is_file_count_limit_error(err: Exception) -> bool:
    """HF's git file-count rejection ("... would contain N files after this
    push, over the limit of 100000 files"). Message-substring based — the
    exception CLASS is deliberately not trusted (unverified, §12 A3); the
    distinctive phrase is stable and digit-free so the #989 digit-triplet
    trap does not apply."""
    msg = str(err).lower()
    return "over the limit of" in msg and "files" in msg and "push" in msg
```
2. `_upload` (hub.py:925) — restructure the existing `except Exception` tail (currently log + `return ""`) into:
```python
    except Exception as e:
        if (
            _filecount_fallback_enabled()
            and _is_file_count_limit_error(e)
            and repo_type == "model"
            and repo_id != DEFAULT_OVERFLOW_REPO
        ):
            logger.warning(
                "File-count limit rejection on %s (%s) — falling back to overflow repo %s",
                repo_id, e, DEFAULT_OVERFLOW_REPO,
            )
            result = _upload(
                local_path, DEFAULT_OVERFLOW_REPO, repo_type, path_in_repo,
                delete_after=delete_after, upload_as_file=upload_as_file,
                ignore_patterns=ignore_patterns, private=True,
            )
            if result:
                _emit_overflow_routing_event(
                    original_repo=repo_id, effective_repo=DEFAULT_OVERFLOW_REPO,
                    path_in_repo=path_in_repo, reason="file-count-limit-reactive",
                )
                _write_overflow_pointer(
                    canonical_repo=repo_id, path_in_repo=path_in_repo,
                    overflow_repo=DEFAULT_OVERFLOW_REPO,
                )
            return result
        logger.error("Upload failed: %s. Keeping local path.", e)
        return ""
```

Source: #564 arming-contract analysis (upload-policy.md § Proactive detection) — the contract's hazard (pre-emptive reroute of a healthy push) is structurally absent here; #1090 (the live incident). 4. **Message-substring detection, not exception-class.** Why: the class the 100k rejection surfaces as through `upload_folder` is unverified (§12 A3); the phrase "over the limit of … files … push" is distinctive, digit-free (immune to the #989 digit-triplet trap), and verbatim-recorded in #1090.
