## §2 Background — why the class recurs, and why the anchor is a git blob

The origin is #2221's `epm:clean-result-critique v3` (2026-08-14T00:41:50Z),
Lens 2 Blocker 2, which supplied the mechanizable recipe verbatim:

> parse "(N results up|down)" tokens under `## Results`, resolve the ordinal
> against the H3 sequence, and flag when the clause says "round-4" but the
> resolved heading starts "Rounds 1-3:" (or vice versa).

The **mechanism** is structural, not a one-off typo. SPEC
§ "Follow-up consolidation (v4)" mandates two operations that REORDER the H3
sequence on every fold:

- item 3 (superseded-result hygiene) — collapse outdated blocks into one
  `<details><summary>Superseded by round N` at the END of `## Results`;
- item 4 (round-compression hygiene) — compress absorbed results.

An ordinal written in round K therefore retargets silently in round K+1.
Multi-round consolidated bodies are the whole population; the class cannot be
fixed by care alone.

## §3 Design

### §3.1 Gating (forward-only)

Follows the established v4 check idiom exactly (models: check 36
`check_v4_result_paragraph_sentences`, check 21 `check_v4_results_beat`):

1. `if not is_v4(body): return CheckResult(label, True, "skipped — not a v4 body")`
   — `is_v4` is the fence-aware / `<details>`-aware sentinel detector at
   `scripts/verify_task_body.py:4408`, so a body merely QUOTING the sentinel in
   an illustrative fence is not misdetected. v3 / v2 / pre-sentinel bodies are
   never touched (forward-only, SPEC).
2. `results = _v4_results_body(body)`; `None` → pass with
   `"## Results missing — check 2 will report"`.
3. `result_h3s = _collect_tldr_h3_names(results)`; empty → pass with
   `"no ### <result> headings — check 3 will report"`; fewer than 2 → pass with
   `"<2 results — no positional target space"`.

Block slicing reuses the check-21/36 convention verbatim:
`rlines[line_no + 1 : end_line]`, `end_line` = next H3 line or `len(rlines)`.

### §3.2 Token grammar

Scanned over each block's **non-code prose** — fenced code skipped and inline
code spans / markdown link targets masked, reusing `_SENTENCE_INLINE_CODE_RE`
and `_SENTENCE_LINK_TARGET_RE` (the `_v4_block_is_quantitative` convention).
`<details>` bodies are stripped first via `_DETAILS_BLOCK_RE`.

Two token families, surrounding parentheses optional:

- **ordinal**: `<count> results? (up|down)` where `<count>` is a digit run or
  one of the number-words `one two three four five six seven eight nine ten`
  (case-insensitive). `results?` admits the singular `(one result up)`.
- **adjacent**: `the previous result` / `the next result`, distance 1.

### §3.3 Resolution

Result blocks are 1-indexed in H3 order. For a pointer inside block `i`:

- `up` / `previous` → `i - N`
- `down` / `next` → `i + N`

### §3.4 The two flag arms

**Arm (a) — out-of-range.** Resolved index `< 1` or `> n_results`. Flagged
unconditionally: no adjudication is needed because no target exists.

**Arm (b) — round mismatch, contradiction-only.** Adopts the check-45
(`check_figure_caption_count_claims_vs_sidecar`) posture: flag only when
positive evidence exists on BOTH sides; stay silent when un-adjudicable.

**§3.4.1 Clause scope (pointer side).** The pointer's clause is the segment
delimited by `;` or a sentence terminator (`.!?`) containing the token. Clause
scope is **load-bearing, not cosmetic**: at the pinned blob line 355 reads
`…are the round 1-3 pathology the re-mine removed; the round-4 recompute
(two results up) replaces this read.` Paragraph or sentence scope would union
`{1,2,3}` with `{4}`, intersect the target's `{1,2,3}`, and MISS the defect.
`;`-clause scope yields `{4}` and catches it. Verified independently by both
critics against the real line text.

**§3.4.2 Heading scope (target side) — the Must-Fix.** Extraction runs on the
resolved heading with **trailing parenthesized segment(s) stripped**.

Both critics replayed the v1 design (whole-heading extraction) and got 1 of 2
instances. The miss is instance 1: heading 5 is

```
### Rounds 1-3: found-data mining collapsed in two families, leaving six
    fine-tunes untrained (repaired by the round-4 re-mine above)
```

Whole-heading extraction yields `{1,2,3} ∪ {4} = {1,2,3,4}`, which intersects
the clause's `{4}` — so the contradiction-only rule stays silent on a
genuinely misdirected pointer. Stripping the trailing parenthetical yields
`{1,2,3}`, disjoint from `{4}` → flagged.

The failure channel is **systematic, not incidental**: appending
`(repaired by the round-N … above)` to a stale pointer's target heading is
exactly the remediation idiom #2221's earlier revision round used, so every
body remediated that way while keeping its ordinal would launder the mismatch
past the check.

*Strip-parentheticals is preferred over the alternative "text before the first
`:`"* (the other fix both critics offered). Both resolve heading 5 correctly,
but before-first-colon drops round tokens that legitimately sit after the
colon — a heading like `Monitor reads: rounds 1-3 detail` would yield an empty
set and go silent, a false negative strip-parentheticals does not have. The
two rules are equivalent on the anchor; strip is strictly more robust
elsewhere.

**§3.4.3 Round-set extraction.** From the clause and, independently, from the
stripped target heading: `round[s]?[ -]?<n>` and ranges `round[s]? <a>-<b>`
(hyphen or en-dash) expanded inclusively. `rounds 1-3` → `{1,2,3}`,
`round-4` → `{4}`.

**§3.4.4 Flag iff** both sets are non-empty AND their intersection is empty.
Silence when either side yields an empty round set is the deliberate
false-negative cost of keeping the check quiet on the ordinary body.

### §3.5 Scope decision — no SPEC.md edit, and no blanket ban

The check verifies **referential integrity of pointers the author already
wrote**; it does not prescribe a pointer form. A misdirected ordinal is a
factual error in the body irrespective of SPEC, so the check is
self-justifying. Adding a SPEC clause would be scope creep past the task Goal
and would put ratchet pressure on SPEC.md for no enforcement gain.

The Alternatives critic weighed three alternatives to the resolver and all
three lose on corpus evidence:

- **Blanket ban on positional pointers** — would fire on ~10+ currently
  CORRECT, in-range `the previous/next result` pointers across ~10 v4 bodies
  (#1482 L188/256/280, #920:221, #833:239, #2215:210, #1775:228, #1895:151,
  #1481:176). Pure WARN noise on legitimate house prose — §7's dominant risk
  realized on day one.
- **SPEC rule + clean-result-critic lens only** — the status quo ante. The
  lens DID catch this once, at judgment-layer recall; the standing project
  pattern is to mechanize recurring judgment catches.
- **Fix at the fold site** — not mechanizable: the fold is performed by the
  analyzer LLM following SPEC prose, with no deterministic reorder script to
  patch, and it cannot catch pointers written wrong at authoring time.

### §3.6 Posture

WARN-only: `CheckResult(label, True, detail, is_warn=True)` — `passed` is
`True` on every path, so the check can never block a promotion. Register
judgment (whether a given pointer should be rewritten as a named reference)
stays with the clean-result-critic, matching check 36's split.

## §7 Risks and disclosed residuals

All residuals below are **false-negative-only** on a WARN channel and are to be
named in the relevant helper docstrings so future readers do not assume
coverage.

- **False positives on a WARN channel** — the dominant risk: a check that fires
  spuriously trains reviewers to ignore WARNs. Mitigated by the
  contradiction-only arm (b), the `<details>` strip, fence/inline-code masking,
  and criterion 5's whole-corpus sweep — empirically zero firings in two
  independent replays.
- **`result(s) above/below` is out of scope by design** — ~49 occurrences
  across v4 bodies, by far the dominant pointer vocabulary, but it carries no
  ordinal and cannot be resolved against the H3 sequence without guessing.
  Auto-resolving "above" would manufacture false positives. Note that #2221's
  remediation rewrote both ordinals INTO this un-checkable named form; the
  check polices the ordinal form going forward, which is its Goal.
- **`the first / third result`** (~3 occurrences) — uncovered, negligible.
- **`the later / earlier result`** (e.g. #1090:492) — uncovered.
- **Clause-scope brittleness** — a pointer whose round token sits across a
  semicolon from it is missed (§3.4.1's deliberate tightness).
- **Arm (b) still defeasible by a round token in the target heading's MAIN
  text** — if a wrong target happens to be labeled with the same round, the
  sets intersect and the check stays silent. Accepted post-fix.
- **Latent H3-in-`<details>` index skew** — `_collect_tldr_h3_names` honors
  fences but not `<details>`, and a `<details>` block spanning an H3 boundary
  splits across blocks, defeating the per-block strip. Zero instances today
  (0 of ~88 v4 bodies carry an H3 line inside `<details>` under `## Results`;
  6 have `<details>` there at all), so it is a documented residual, not a fix.
- **Arm (a) forward-looking prose** — "the next result (queued)…" in the last
  block would WARN spuriously. Zero corpus instances; WARN-only; accepted.
- **Unclosed-fence residual** — inherits the known
  `_result_prose_paragraphs`-family residual (an unclosed fence swallows the
  rest of a block), matching check 36's disclosed residual.
