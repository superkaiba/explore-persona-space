# Plan — #954: mint the RunPod handle + stamp exactly-once on the PARTIAL GCP→RunPod failover (pod provisioned, workload start failed)

`kind: infra` (workflow-fix). 0 GPU-h. No pod, no training, no model call.

## 0. Plan Summary (technical)

**What:** Close the PARTIAL-failure gap in the RunPod terminal rung: when RunPod
PROVISIONS a pod but the #909 workload-start leg fails
(`RunPodWorkloadStartError`, pod deliberately left RUNNING for diagnosis),
`_runpod_terminal_rung` (`src/explore_persona_space/backends/router.py`)
currently collapses it into `NoComputeAvailableError` via its blanket
`except Exception`, and `_failover_gcp_to_runpod` (`scripts/backend_poll.py`)
returns terminal `reason=no_compute_available` with NO handle sidecar, NO
idempotency stamp — a billing pod invisible to the handle machinery, an
unchained manual re-drive, and a watcher capacity-retry re-drive that restarts
the whole auto ladder (new paid GCP attempt) while the pod bills. Observed
live on #931 (2026-07-04T01:59:38Z).

**Fix (hybrid option c):** (1) `RunPodBackend.launch` attaches the fully-built
partial `RunHandle` (with `workload_executed: False` +
`workload_start_error: <str>`) to the raised `RunPodWorkloadStartError`;
(2) `_runpod_terminal_rung` intercepts the typed error when it carries a
handle, persists the SAME launch records the success path writes (on_launched
sidecar hook + in-flock lease incl. the M3b `gcp_failover_of` stamp), records
a `runpod_workload_start_failed` RouteAttempt + terminal marker, then
RE-RAISES TYPED (never `NoComputeAvailableError`); (3) the async failover
legs (`_failover_gcp_to_runpod` core — covers #659 crash + #783 queue-timeout —
and `_relaunch_fresh_runpod` — covers #692/#770 no-port wedge + #775 CUDA-IMA)
catch the typed error, authoritatively re-point the sidecar at the partial
handle (write + readback), and emit a terminal infra JSON with the DISTINCT
reason `runpod_workload_start_failed` (∉ `TRANSIENT_CAPACITY_REASONS` — the
watcher never auto re-drives it); (4) `dispatch_issue.py _cmd_launch`'s
existing typed arm additionally writes the handle sidecar + names the pod in
its failure JSON (closes the same gap class on the explicit-override path).
The happy path, capacity-miss path, CPU guard, intent-translation guard, and
M3b concurrent-triggerer write-side are byte-preserved.

**Compute:** `Estimated GPU-hours (total): 0`. CPU-only code change + pytest.
No pod for the work itself. Wall time ≈ 3–5 h implementer + review.

**Risks (top 2):** regressing the existing exactly-once / M3b tests (mitigated:
the partial branch reuses `_lease_after_submit` + the same in-flock stamp, and
every existing test is named below and kept green); a lease stamped for a
workload-less pod suppresses a later automatic failover for the same GCP crash
(by design — the pod exists; recovery is re-driving the workload on THAT pod,
not a second pod; documented in §11 D5).

## 1. Goal, requirement, acceptance criteria

**Goal (from task #954, corrected by the clarifier):** on the GCP→RunPod
failover paths, a RunPod launch that PROVISIONS a pod but fails the
workload-start leg must leave the run CHAINED (RunPod handle sidecar minted,
idempotency lease stamped, distinct terminal reason) instead of the current
`no_compute_available` collapse that hides a billing pod and invites a second
paid dispatch. Do NOT re-implement the happy-path sidecar mint — post-#659
round-3 it already exists (write + readback + durable lease stamp in
`_failover_gcp_to_runpod`).

**Requirement:** exactly-once must hold across polls, concurrent triggerers,
and the watcher: after the partial failure, no automatic actor provisions a
second pod or restarts the auto ladder.

**Acceptance criteria (each testable, tests named in §6):**

- AC1 — `_runpod_terminal_rung`, on a `RunPodWorkloadStartError` carrying a
  handle: invokes `on_launched` with the partial handle, writes the lease
  (`_lease_after_submit`, + `gcp_failover_of` when
  `gcp_failover_of_identity` is passed) inside the SAME flock transaction,
  appends a `RouteAttempt(outcome="runpod_workload_start_failed")`, posts the
  terminal failure marker with `reason: runpod_workload_start_failed`, and
  re-raises the TYPED error. It never raises `NoComputeAvailableError` for
  this case.
- AC2 — `_runpod_terminal_rung`, on a `RunPodWorkloadStartError` with
  `handle is None` (the pre-provision `execute_workload`+empty-`workload_cmd`
  guard — nothing provisioned, nothing bills): existing behavior
  byte-preserved (blanket branch → `NoComputeAvailableError` +
  `ROUTE_REASON_NO_COMPUTE` marker).
- AC3 — `_failover_gcp_to_runpod` (hence BOTH the #659 crash and #783
  queue-timeout callers), on the typed error with a handle: sidecar
  authoritatively re-pointed at the partial RunPod handle (readback
  `backend == "runpod"`, `extra["workload_executed"] is False`,
  `extra["workload_start_error"]` non-empty), lease stamped, terminal infra
  JSON with `reason=runpod_workload_start_failed` (NOT
  `no_compute_available`), `log_tail` naming the pod + that it stays RUNNING
  for diagnosis.
- AC4 — exactly-once: after AC3, (i) a second poll tick launches ZERO
  additional pods (the sidecar now reads `runpod`, so the GCP failover
  predicate cannot re-fire; a forced still-GCP sidecar short-circuits on the
  durable lease); (ii) an M3b concurrent second triggerer with the same GCP
  identity short-circuits in-flock — total launch count stays 1.
- AC5 — the watcher never auto re-drives the new terminal:
  `runpod_workload_start_failed` ∉
  `autonomous_session_watch.TRANSIENT_CAPACITY_REASONS`, and
  `_is_transient_capacity_block` is False on the emitted failure fields.
- AC6 — `_relaunch_fresh_runpod` (wedge #692/#770 + CUDA-IMA #775), on the
  typed error with a handle: `stamp_fn(issue, handle)` called (bounds a
  re-fired tick), sidecar re-pointed at the fresh partial pod, terminal
  `runpod_workload_start_failed`.
- AC7 — explicit-override path: `dispatch_issue.py launch` exit 2 JSON for
  the typed-with-handle case carries `reason: runpod_workload_start_failed`
  (unchanged) PLUS `pod_name`, and the handle sidecar exists on disk after
  the exit.
- AC8 — regressions: every existing exactly-once / failover / M3b / rung test
  named in §6 "Must stay green" passes unchanged; `uv run ruff check` clean on
  touched files; `uv run python scripts/workflow_lint.py --check-asks` clean.

**Precision on the "second pod" claim (corrects the task body):**
`pod_lifecycle.cmd_provision` REFUSES (exit 1) when a non-EXITED `pod-<N>` /
`epm-issue-<N>` exists (pod_lifecycle.py L1702–1720), so a same-issue re-drive
does not literally mint a second RunPod pod while pod-N is alive. The real
double-spend paths the mislabel opens: (a) the watcher's capacity-retry pass
(keys exactly on `no_compute_available`) re-drives `spawn-issue --auto`, which

provisions a fresh pod and the diagnosis state is lost silently. The distinct

## 3. Design (concrete steps, file-level)

### Surface 1 — `src/explore_persona_space/backends/runpod.py`

1a. `RunPodWorkloadStartError` gains an optional carried handle:

```python
class RunPodWorkloadStartError(RuntimeError):
    def __init__(self, message: str, *, handle: "RunHandle | None" = None) -> None:
        super().__init__(message)
        #: The PARTIAL RunHandle when a pod was provisioned before the start
        #: leg failed (#954); None when nothing was provisioned. The router's
        #: terminal rung + the backend_poll failover legs key their
        #: persist-then-surface behavior on this.
        self.handle = handle
```

All existing raise sites are untouched (default `None`).

1b. `RunPodBackend.launch`: extract the `RunHandle` construction (L746–792+)
into a local closure `_build_handle(workload_info, *, workload_executed,
workload_start_error=None)` over `spec`/`pod_name`/`attempt_id`/
`sentinel_path` — every input to `build_expected_artifacts_declaration` is
already minted BEFORE the execution leg (#909 r2), so the handle is fully
constructible at the failure point. Success path: `return
_build_handle(workload_info, workload_executed=exec_requested)` — byte-
equivalent extra dict (the two new keys are added only on the failure path,
so the success handle stays byte-identical). Failure path:

```python
if exec_requested:
    try:
        workload_info = _execute_workload_on_pod(...)
    except RunPodWorkloadStartError as exc:
        exc.handle = _build_handle(
            {},
            workload_executed=False,
            workload_start_error=str(exc)[:2000],
        )
        raise
```

Re-raising the SAME exception preserves message + traceback. The partial
handle's `extra` additionally carries `workload_executed: False` (truthful)
and `workload_start_error: <truncated str>`; every existing reader uses
`.get()` (additive-safe; `serialize_handle`/`deserialize_handle` round-trip
`extra` verbatim). The pre-provision guard (L639, `execute_workload` with
empty `workload_cmd`) raises BEFORE `subprocess.run(provision)` and keeps
`handle=None`. The pod-stays-RUNNING-for-diagnosis contract is UNCHANGED
(option (b) rejected — §11 D2).

### Surface 2 — `router.py` `_runpod_terminal_rung`

2a. New constant next to the ROUTE_REASON block (~L424):
`ROUTE_REASON_RUNPOD_WORKLOAD_START_FAILED: str = "runpod_workload_start_failed"`
(must equal the `dispatch_issue.py` L1177 literal — parity test in §6).

2b. Split the existing `except Exception as exc:` (L2553) around
`_prepare_and_launch` with an isinstance check (lazy import of
`RunPodWorkloadStartError` inside the handler, matching the module's existing
lazy `backends.runpod` import at L4494; runpod.py imports only `base` at
module top, so no cycle either way — lazy is belt-and-braces):

```python
except Exception as exc:
    from explore_persona_space.backends.runpod import RunPodWorkloadStartError

    partial_handle = (
        exc.handle if isinstance(exc, RunPodWorkloadStartError) else None
    )
    if partial_handle is not None:
        # Pod provisioned + RUNNING; the workload did not start (#954).
        # Persist the SAME launch records the success path writes — the
        # sidecar hook and the in-flock lease (incl. the M3b
        # gcp_failover_of stamp) — so downstream stays chained and no
        # concurrent/later triggerer launches again. Then re-raise TYPED:
        # NoComputeAvailableError would be FALSE (a pod exists and bills).
        _invoke_on_launched(on_launched, partial_handle)
        # LEASE-WRITE GUARD (round-1 critique, alternatives MF2): the typed
        # error is the load-bearing signal — a lease-write failure must NEVER
        # replace it (the failover legs' `except RunPodWorkloadStartError`
        # would otherwise never fire: no distinct terminal, no sidecar
        # re-point, exactly when rescue is needed). Same "never mask the
        # original error" invariant as Surfaces 4/5. On a write failure the
        # failover legs' post-route sidecar write + sentinel remain the
        # (weaker) relaunch bound, and the note records it for a human.
        lease_note = ""
        try:
            new_lease = _lease_after_submit(lease, runpod_spec, "runpod", None, partial_handle)
            if gcp_failover_of_identity is not None:
                new_lease.gcp_failover_of = gcp_failover_of_identity
            write(new_lease)
        except Exception as lease_exc:
            logging.warning(
                "runpod partial-launch lease write failed (%s: %s); typed error preserved",
                type(lease_exc).__name__, lease_exc,
            )
            lease_note = f"; lease_write_failed ({type(lease_exc).__name__}: {lease_exc})"
        attempts.append(RouteAttempt(
            kind="runpod", cluster=None,
            est_start_seconds_raw=0.0, est_start_seconds_clamped=0.0,
            outcome="runpod_workload_start_failed",
            detail=(f"runpod pod {partial_handle.pod_name} PROVISIONED but "
                    f"workload start FAILED ({exc}); pod left RUNNING for "
                    f"diagnosis{lease_note}"),
            elapsed_seconds=now_fn() - started_at,
        ))
        _post_terminal_failure_marker(
            spec=spec, marker_poster=marker_poster,
            reason=ROUTE_REASON_RUNPOD_WORKLOAD_START_FAILED,
            chosen_kind="runpod", attempts=attempts,
        )
        raise
    <existing blanket branch VERBATIM: attempts.append(runpod_fallback_failed)
     + _post_terminal_failure_marker(ROUTE_REASON_NO_COMPUTE)
     + raise NoComputeAvailableError(...) from exc>
```

The lease write happens INSIDE the already-open `store.transaction` flock
(same block as today's success write) — the M3b atomic-guard property is
inherited, not re-implemented. `_invoke_on_launched` swallows hook exceptions
by contract (best-effort; the failover legs' post-route write stays the
authoritative one). Everything else in the rung (CPU guard, #940 translation,
M3b in-flock re-check, success path, marker `extra`) is byte-untouched.

    except RunPodWorkloadStartError as exc:          # NEW

                issue=issue, sidecar=sidecar,

## 11. Decision Rationale (load-bearing DESIGN decisions)

N/A — no model training (no hyperparameters). N/A — not a replication.
Design decisions:

- **D1 — Contract choice: hybrid (c) — mint handle + lease + typed error +
  distinct terminal — over (a) handle-only or (b) terminate-on-failure.**
  Why: (a) without the typed re-raise leaves the rung's sync callers
  mislabeled (`no_compute_available` → watcher re-drive → new paid GCP
  attempt while the pod bills); (b) terminating the pod reverses runpod.py's
  deliberate stays-RUNNING-for-diagnosis contract (#909, docstring L493) and
  destroys exactly the diagnostic surface RunPod failover exists to provide
  (`.claude/rules/compute-backend-failover.md` Part B: "a persistent,
  SSH-able pod for diagnosis"); #931's pod was healthy and was in fact
  recovered by a manual re-drive on THAT pod. Source: read from code +
  the #931 marker trail (clarifier note).
- **D2 — Pod stays RUNNING (no cleanup-on-failure).** Same grounds as D1(b).
  Billing bound (corrected, round-1 critique — alternatives MF1): NO
  automation reaps this pod — the stale-pod audit cron reaps EXITED>24h pods
  only, and the watcher's pod-safety pass keeps blocked/live-work pods — so
  the pod BILLS until a human stops/terminates it. The actual bound is human
  triage: the loud terminal (whose recovery text explicitly instructs
  "stop/terminate after diagnosis" + names the billing exposure), the
  now-visible sidecar, and the watcher's gate-push on `blocked`. Pre-existing
  #909 stays-RUNNING exposure, strictly improved in visibility here; a
  RUNNING-diagnostic-pod auto-stop policy is a deliberate non-goal of this
  diff (named follow-up candidate, NOT filed from this session — recursion
  guard). Source: runpod.py L493 contract; `scripts/pod_audit.py`
  EXITED-only reap; `autonomous_session_watch.py` pod-safety pass.
- **D3 — Terminal infra JSON (not a RUNNING-shaped return) on the failover
  legs.** With no workload running, emitting RUNNING just defers: the next
  tick polls a workload-less pod (no pidfile → `status=dead`) and surfaces a
  GENERIC failure one tick later, losing the precise reason and the recovery
  hint. The terminal is one tick faster, names the pod + the exact recovery
  (re-drive on THIS pod), and — because the reason ∉
  `TRANSIENT_CAPACITY_REASONS` — parks for a human instead of auto-churning.
  Source: read from code (`poll_once` pidfile contract; watcher L11218).
- **D4 — No auto-retry of the workload start (deferred follow-up).** #931's
  boot-lag WOULD likely have healed on one retry, but retry semantics
  interact with the pod-side double-fire guard: if the detach succeeded and
  only the verify SSH timed out, the workload IS live and a retry raises
  ALREADY-RUNNING — which must then be treated as success, a semantics change
  needing its own tests. Minimal-diff principle wins; the minted sidecar
  makes the manual/experimenter re-drive chained TODAY. Source: read from
  code (`_execute_workload_on_pod` L539–549 double-fire branch).
- **D5 — Stamp `gcp_failover_of` for the partial launch.** The stamp's
  meaning is "a RunPod launch for THIS GCP crash happened" — true: a pod
  exists and bills. Not stamping re-opens the double-launch across polls
  (the exact #659-r3 hole). Consequence accepted: a later AUTOMATIC failover
  for the same crash is suppressed even after a human terminates the partial
  pod — recovery is then a manual re-dispatch, same as the existing
  `sidecar_persistence_failed` family. Source: read from code
  (backend_poll.py L2421–2447 idempotency comment).
- **D6 — Blast radius: rung + all three failover legs + the dispatch arm;
  NOT `classify_terminal_exception`, NOT the watcher, NOT `workflow.yaml`.**
  The collapse happens only inside `_runpod_terminal_rung`'s blanket except;
  fixing it there restores the typed contract the explicit-override path
  already has (dispatch_issue.py L1164 comment anticipates it). The legs need
  only mapping branches because the persistence mechanics already exist. The
  no-lease choice on the override path is safe because provision-idempotency
  refuses a same-name second pod (pod_lifecycle.py L1702–1720). Source: read
  from code.
- **D7 — Reason string `runpod_workload_start_failed` reused verbatim.**
  Already the established reason for exactly this failure on the override
  path (#909); one reason per failure class across paths keeps the watcher /
  failure-classifier / marker-trail greps coherent; a parity test pins it.
  Source: dispatch_issue.py L1177/L1268.

## 15. Round-1 critique riders (implementer guidance — thread into the Step 4b brief)

Non-blocking concerns from the round-1 critic ensemble, carried so the
implementer + code-reviewer see them without re-deriving:

1. **Concurrency-test shape tolerance:** the M3b 2nd-triggerer has TWO valid

   `sidecar_persistence_failed`). Any poll-level concurrent assertion must be
   ordering-tolerant; launch-count == 1 is the load-bearing invariant
   (tests 3/6).
2. **AC4-i asserts the durable-lease path specifically** (the forced
   still-GCP-sidecar sub-case in test 6), not just any no-launch shape.
3. **Test 8 (queue-timeout) asserts teardown-first by CALL ORDER**, not just
   `len(teardowns) == 1`.
4. **Test 10's success-path `extra` byte-identity** pins the exact expected
   success key set (or compares against `git show main:`) — never a
   circular post-change fixture.
5. **Surface 3's defensive `partial is None` branch is documented
   dead-defense** — unreachable via the rung today; do not count it as
   covered, do not chase coverage for it.
6. **Implementation-time greps that MUST run** (deferred assumptions 8/9):
   (a) the watcher wedge outcome-mapper keys on terminal-JSON fields, not a
   reason allowlist — if an allowlist exists, add the new reason (in-scope,
   one line); (b) `workflow.yaml` has a stale PROSE reason list for
   `epm:backend-selected` (not a validated enum) — appending
   `runpod_workload_start_failed` there is optional doc hygiene.
7. **Recovery-note honesty:** the minted sidecar records the FAILED attempt's
   sentinel path — a manual re-drive stays finalize-chained only if it writes
   the declared sentinel (or the artifact verifier can discover a single live
   sibling sentinel). Do not overpromise seamless finalize in the recovery
   text.
8. **Override-path parity is deliberately partial** (sidecar + pod_name +
   reason; NO lease) — state this in the final report; bounded by
   provision-idempotency + the non-re-drivable reason.
