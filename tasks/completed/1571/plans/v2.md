### 3.1 Deliverable (a): the per-commit total-staged-files advisory WARN

**Hook location: inside `assert_hub_dir_filecounts` (hub.py:763), as a third, independent, advisory tier.** Rationale: the guard already receives exactly the inputs needed (the per-dir `counts` dict whose values sum to the commit's total staged-file count, with allow/ignore staging-parity already applied), and every relevant call path already flows through it — `_upload`'s folder branch (:1211), `_upload_folder_filtered` (:1405, hence `upload_raw_completions_to_data_repo` / `upload_model` / `upload_dataset` folder flows), and every direct `scripts/` caller the `--check-hub-dir-filecount` lint funnels here. Hooking anywhere else (e.g. only in `_upload`) would silently exempt the funneled scripts callers — the incident class's most likely home.

**New constant** (insert after hub.py:709, alongside the existing tier constants):

```python
# Advisory per-COMMIT total-staged-files THROUGHPUT watermark (#1571): one
# upload_folder commit of many small files crawls in Hub-side per-operation
# pre-processing regardless of byte size (#1481 incident, session 98ff0f37:
# 31,000 files / 135 MB in one commit — killed exit 144 after >20 min,
# repacked into <stem>.shardNN.jsonl line-shards). HF's own guidance
# recommends ~50-100 files per commit and merging small files into fewer
# larger ones (hub docs, repositories-recommendations); 2,000 = 20x that
# recommendation — quiet on normal-scale uploads, loud well below the
# incident scale. DISTINCT from the two SERVER caps above (10k/dir #658,
# 100k/repo #1108): this tier NEVER raises. warn_total <= 0 disables.
HUB_COMMIT_FILECOUNT_WARN = 2_000
```

**Signature change** (:763-771): add a keyword-only parameter with default —

```python
def assert_hub_dir_filecounts(
    folder_path, path_in_repo, *,
    allow_patterns=None, ignore_patterns=None,
    limit: int = HUB_DIR_FILE_LIMIT,
    warn_at: int = HUB_DIR_FILECOUNT_WARN,
    warn_total: int = HUB_COMMIT_FILECOUNT_WARN,   # NEW
) -> dict[str, int]:
```

Backward-compatible: keyword-only with default; no existing caller changes.

**Body insertion** — immediately after `counts = count_staged_files_per_repo_dir(...)` (:796-801) and BEFORE the `offenders` branch (:802), so the advisory fires independently of (and in addition to) the raise/per-dir tiers — on the raise path the WARN lands first, which is correct: the pack recipe is the right remediation for an over-cap many-small-file tree too. Exact pseudocode + message text:

```python
total = sum(counts.values())
if warn_total > 0 and total > warn_total:
    # Advisory THROUGHPUT tier (#1571) — never raises, independent of the
    # SERVER-cap tiers below. NOTE the #1108 overflow fallback re-enters
    # _upload, so an over-limit kill-switched upload can log this twice
    # (idempotent + harmless — same note as the kill-switch WARN below).
    # Comma-format the numbers (the "500"-substring trap, msg note below);
    # this is a log line (never an exception), so the trap cannot bite,
    # but the discipline is uniform across the guard's messages.
    logger.warning(
        "upload stages %s files in ONE commit (advisory throughput "
        "threshold %s) — many-small-file commits crawl in Hub-side "
        "pre-processing regardless of byte size (#1481: a 31,000-file / "
        "135 MB commit was killed and repacked). Prefer PACKING small "
        "text/JSON files into <= 9 MB <stem>.shardNN.jsonl line-shards + "
        "a manifest (.claude/rules/upload-policy.md), or fewer larger "
        "files; proceeding — advisory only.",
        f"{total:,}",
        f"{warn_total:,}",
    )
```

Fixed-literal audit for the "500"-substring trap: `31,000` / `135` / `9` / `ONE` carry no `500`/`502`/`503`/`504` substring; the two dynamic values are comma-formatted per house style. (The trap is exception-message-scoped — `_is_transient_upload_error` scans `str(err)` of raised exceptions; a `logger.warning` never transits a retry thunk — but the message stays scrubbed anyway, pinned by test, because future refactors have moved log text into exception text before.)

**Docstring update to `assert_hub_dir_filecounts`:** add ~3 sentences documenting the third tier — advisory-only, per-COMMIT total (vs per-DIR server cap), `warn_total <= 0` disables, distinct rationale (throughput, not a server 400), and that the kill switch `EPM_SKIP_HF_DIR_FILECOUNT_GUARD` does NOT gate it (nothing to unwedge — it never blocks).

**What is deliberately NOT built:** no new env kill switch (the `warn_total<=0` parameter is the disable knob; an advisory log line cannot wedge an upload, which is the only thing the `EPM_SKIP_*` family exists for); no auto-packing helper (out of scope per the minimal-diff constraint; the WARN names the recipe + rule file); no change to `_upload`/`_upload_folder_filtered` call sites (they inherit the tier through the guard).

## 5. Kill criterion

The change is wrong to land if ANY of: (a) satisfying the WARN requires modifying any existing test assertion or any existing runtime behavior (per-dir tiers, #1108 fallback, retry budgets, kill-switch semantics) — the byte-unchanged constraint is binding, and a design that can't meet it goes back to planning; (b) implementation-time verification shows `upload_folder` on the pinned hub 0.36.2 auto-splits large folders into multiple sub-2k commits on our call path — then the premise "one commit stages the total" is false and the WARN mis-describes reality (strong evidence against: the #1481 incident crawled as ONE commit on exactly this stack; fact-checked — the installed hub 0.36.2 `HfApi.upload_folder` has NO `multi_commits` param and hub.py uses neither `multi_commit` nor `upload_large_folder` (grep: 0 hits), so the one-commit premise holds at the CODE level; note the HF docs tip does literally name `upload_folder` in its auto-split wording — stale docs vs the pinned code; the code-level check is the arbiter); (c) the WARN turns out to fire on routine normal-scale fleet uploads (tens–hundreds of files) — impossible at threshold 2,000 given measured artifact scales (§6), but if a review finds a >2k-file ROUTINE library flow I missed, the threshold (not the mechanism) must be re-grounded before landing.

## 11. Decision Rationale

- **Threshold = 2,000.** *What:* `HUB_COMMIT_FILECOUNT_WARN = 2_000`, strict `>`. *Why:* the task Goal names ~2k; incident arithmetic gives the scale — 31,000 files / 135 MB failed to commit within the observed ≥20-min window (session 98ff0f37, 07:15–07:37 UTC kill), a lower bound of ~40 ms/file of Hub-side per-operation pre-processing, so 2,000 files ≈ ≥80 s — the boundary below the multi-minute regime where operators start running the #931 wedge diagnosis (whose TX sampling runs ≥5 min apart); and HF's own docs recommend ~50–100 files per commit + merging small files, making 2,000 a 20× conservative multiple that cannot fire on normal-scale uploads (measured artifact dirs: 48–176 files). *Source:* task #1571 Goal (canonical) + incident-derived (#1481, session 98ff0f37) + HF hub docs `repositories-recommendations` (fetched 2026-07-20: "Commit size <100 files", "keep around 50-100 files per commit", "json files can be merged into a single jsonl file"). *Alternatives:* 5,000 (symmetry with `HUB_DIR_FILECOUNT_WARN`) — rejected: that constant is server-cap-derived (half the 10k/dir limit), not throughput-derived, and ≥3.5 min of pre-processing is already deep in wedge-suspicion territory; 100 (HF's literal recommendation) — rejected: would WARN on routine 100–200-file eval/figure uploads, pure spam.
- **WARN-only, never raise.** *What:* advisory `logger.warning`, no exception, no kill switch needed. *Why:* a >2k-file commit is server-LEGAL and sometimes the right call (re-sharded tensor stores where packing is impossible), unlike the 10k/dir tier whose violation is a guaranteed server 400 — raising would convert a throughput nudge into a false blocker. *Source:* task Goal ("advisory WARN"); precedent — the existing `warn_at` tier is WARN-only (hub.py:826-835). *Alternatives:* raise-with-kill-switch (the `limit` tier's shape) — rejected: wrong severity class for a legal operation.
- **Hook location = inside `assert_hub_dir_filecounts`.** *What:* third tier in the guard, before the offenders branch. *Why:* free coverage of all three call-site classes (library folder branch :1211, filtered bulk :1405, lint-funneled scripts callers — workflow_lint.py:5355 requires direct callers to reference the guard), zero per-site edits, reuses the already-computed counts. *Source:* read code (hub.py:1211/:1405; workflow_lint.py:5323-5429; grep of callers §2). *Alternatives:* hook in `_upload` only — rejected (misses filtered + scripts callers); a separate helper both call — rejected (more diff, same coverage, violates minimal-diff constraint).
- **Constant name `HUB_COMMIT_FILECOUNT_WARN`.** *What:* per-COMMIT total watermark. *Why/Source:* follows the existing family `HUB_DIR_FILE_LIMIT` / `HUB_DIR_FILECOUNT_WARN` (hub.py:707-709) — the `DIR`→`COMMIT` swap encodes exactly what differs. *Alternatives:* `HUB_TOTAL_FILECOUNT_WARN` — rejected: "total" is ambiguous (repo total = the #1108 100k cap).
- **Parameter disable (`warn_total<=0`) instead of an env kill switch.** *Why:* the `EPM_SKIP_*` family exists to unwedge deliberate uploads a guard would BLOCK; an advisory log line blocks nothing. *Source:* `_dir_filecount_guard_enabled` docstring (hub.py:718-720) states the family's purpose. *Alternatives:* new `EPM_SKIP_*` env — rejected (dead weight, more surface).
