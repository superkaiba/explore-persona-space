## §3 Decision and reasoning

### §3.1 Why the cap raise (option 2) is refused

The body conditions option 2 on a conjunction: growth is legitimate **and**
200,000 B is arbitrary. §2.3 concedes the first conjunct. The refusal rests on
the second, which is decisive and channel-independent:

**The cap is not arbitrary — it is a context-budget wall.** gotchas.md loads
on-demand whenever training / eval / orchestration / analysis code is touched.
199 KB is already ~50K tokens per triggering session. Raising to 250 KB raises
that recurring load 25% with no offsetting mechanism, in a project that spent a
dedicated task cutting always-on load 443K → 180K.

*(v2's first reason — "a raise does not close mode (b)" — is demoted: it never
discriminated, since raise+guard closes the machine channel exactly as
trim+guard does, and §2.5 shows that channel has never fired. The context-load
argument alone carries the refusal.)*

**Acknowledged tension:** §2.3 says all 163 entries are operative, while §4
claims ≥22 KB is removable without operative loss. Both hold only because
*operative ≠ incompressible, and relocatable ≠ deletable*. This is empirically
gated, not asserted: kill criterion 1 (§11) stops the work rather than cutting
into operative content.

### §3.2 Why the trim alone is insufficient — and what the guard actually buys

At 4.76 KB/day a trim buys days, not permanence (§2.4). The guard does not
change that: it closes mode (c), whose realized rate is zero.

**So why include it?** Severity, not frequency. A human append that breaches the
wall trips the pre-push lint gate in front of a person who then fixes it. An
unattended 23:50 `--apply` promotion commits straight to `main` and leaves
`test_live_tree_passes_clean` red **fleet-wide** for every session until someone
notices — with no human in the loop at any point. That is a cheap ~40-line
guard against a low-probability, high-blast-radius tail. It is a **backstop**,
explicitly not "the durable half" (v2's claim, withdrawn).

The guard also restores meaning to a constant the zero-WARN pin had made
unobservable: `GOTCHAS_SIZE_WARN_BYTES` becomes the *machine's* ceiling. The
*human* channel's ceiling is likewise 200,000 B via the zero-WARN pin — v2's
§3.3 wrongly called `GOTCHAS_SIZE_FAIL_BYTES` the human wall. No threshold
changes; only the articulation of who each binds.

### §3.3 Why relocation leads the trim

§2.3 leaves prose compression as the only in-file lever, and compressing a dense
safety rule risks silently weakening it — the one outcome the body forbids.
Relocation avoids that class entirely: the residual text **moves intact** into
the rule file that already owns the topic. No sentence is rewritten, so no rule
can be weakened by rewording. Its own risk is different and checkable
(trigger-coverage, §4.2).

### §3.4 The decision record (Change C — the part that outlives the bytes)

Recorded in §12 and carried into the task body at completion:

1. The sanctioned response to a future breach is **re-trim or restructure —
   never a cap raise**, for the §3.1 context-load reason.
2. The measured growth rate is ~4.76 KB/day, so any headroom figure is
   week-scale. A future session should expect to restructure, not to shave.
3. The named structural successors, with why each is blocked today (§12).
4. The §4.4 conservation recipe is the reusable instrument that makes the next
   pass routine.

For the shortfall, compress the largest remaining in-scope entries (top-40 sum

- (a) the bolded operative rule; (b) the diagnostic signature — symptom, error

## §5 Change B — budget guard in `promote()`

### §5.1 Threshold source — lazy import inside `promote()`

Import the constant; do **not** restate the literal (#838 fixture-inversion).
Import **inside `promote()`**, immediately before the size check — not at module
top (Alternatives critic finding 5): a module-top import couples the whole
nightly janitor (dedupe/prune/counts) to the import health of a ~13.7k-line lint
module, and a future breakage there would be swallowed indefinitely by the
wrapper's `exit 0` — a new silent failure mode bought to guard a path that has
never fired. Lazy import confines the blast radius while keeping fail-loud.

```python
def promote(root, lessons, counts, *, apply: bool) -> None:
    ...
    _scripts_dir = Path(__file__).resolve().parent
    if str(_scripts_dir) not in sys.path:
        sys.path.insert(0, str(_scripts_dir))
    from workflow_lint import GOTCHAS_SIZE_WARN_BYTES
```

Verified: the import measures 0.48 s, is constants + regex compilation only, and
has no cycle with `explore_persona_space.task_workflow` (which
`consolidate_lessons` already imports at `:72`). The `sys.path` bootstrap is the
existing `tests/test_workflow_lint_gotchas_size.py` pattern and covers both
invocation modes (script, and `spec_from_file_location` in tests).

### §5.2 Behaviour — refuse WITHOUT raising in `promote()`

**This is v2's MAJOR defect, corrected.** v2 raised inside `promote()`. Given
`consolidate()`'s ordering (`dedupe` :765 → `promote` :766 → `prune` :767 →
commit :769 → `_write_log_line` :776), raising in `promote()` would:

1. leave `dedupe`'s already-applied agent-memory deletions and `MEMORY.md` edits
   **dirty and uncommitted in the shared repo root** — the half-landed mutation
   the module's own fail-loud docstring exists to prevent, and a plausible
   co-occurrence (the recurring 2-task cluster that first becomes promotable is
   the same one whose near-duplicate memory files dedupe collapses that night);
2. skip `_write_log_line`, destroying the very audit trail §10 residual 1 relies
   on;
3. and v2's §6 case 3 ("no commit") would have **pinned that as correct**.

Corrected design:

- Restructure the counting so `counts.promoted` is incremented **after** the
  budget check, not inside the dedupe loop (this removes v2's awkward
  decrement-back).
- Compose `new_text`; compute `projected = len(new_text.encode("utf-8"))`.
- If `projected > GOTCHAS_SIZE_WARN_BYTES`: refuse the **whole** append — no
  write, no `add_touched(gotchas)` (hence no gotchas commit) — set
  `counts.promote_refused_budget = len(appended)`, leave `counts.promoted` at 0
  for those bullets, log at ERROR naming `projected`, the limit, the overshoot,
  and the trim recipe, and **print every refused bullet verbatim**. Then
  **return normally**.
- `consolidate()` proceeds unchanged: dedupe/prune touched paths commit, and the
  counts line is written (extended with the new counter).
- `main()` inspects `counts.promote_refused_budget > 0` **after** `consolidate()`
  returns and returns a distinct non-zero exit code **3**, so the refusal is a
  loud process-level signal without falsely claiming a corrupting write.

Refusal is all-or-nothing rather than partial-fill: a partial fill parks the file
at exactly the wall with an arbitrary promoted subset and still needs the human
trim.

`Counts` gains `promote_refused_budget: int = 0`, surfaced in `summary_dict()`.
Deliberately **not** a term in `is_noop` — a refused run mutated nothing, so it
is a no-op for commit purposes.

**Also threaded (Methodology critic concern 5):** the new counter must reach
`_write_log_line`'s format string (`:730-737`) and `main()`'s `_log.info` fixed
key tuple (`:827-838`), or §7.6's "coherent summary line including the new
counter" cannot pass.

**Residual 1 (filed, not fixed here).** `scripts/cron_lesson_consolidate.sh`
ends `exit 0` unconditionally, so exit code 3 is swallowed at the cron boundary:
a refusal surfaces in `logs/lesson_consolidate/YYYY-MM-DD.log` and the counters,
but sends no push. This does **not** defeat the guard — the harm the Goal names
(fleet-red test + forced unreviewed pass) is prevented by the *refusal itself*,
regardless of who reads the log; the swallow only delays recovery. Wiring a
notification is a different file with its own review surface ⇒ filed as a
follow-up (§11 criterion 7).

**Residual 2.** The 7-day rolling window means a refusal persisting >7 days could
age its source markers out of the scan before a trim happens. §5.2's
verbatim-bullet logging is the mitigation (content survives in the log); the
markers themselves persist in `events.jsonl` beyond the window (the window bounds
the *scan*, not the markers).

**Residual 3 (the honest one).** Mode (b) — human appends at ~4.76 KB/day — is
not closed by anything in this change-set. ≥22 KB is ~4.7 days of runway. The
structural successors are named in §12 and filed.

## §11 Success criteria and kill criteria

**Success criteria (all required):**

1. `.claude/rules/gotchas.md` ≤ **177,000 B** (≥22 KB recovered, ≥23 KB headroom).
2. §4.4 union conservation: zero lost `#N` citations; identifier diff empty or
   explicitly justified.

   LESSONS.md trigger row + one-sentence justification) in the implementation
   marker.

   green with both threshold literals and the zero-WARN pin **unmodified**.
5. `promote()` refuses an over-budget append **without raising**, leaves
   gotchas.md byte-identical, still commits dedupe/prune mutations, writes the

**Kill criteria:**

1. ≥22 KB unreachable without cutting operative content — STOP, record the
   measured achievable figure with the per-lever breakdown, surface it. Do
   **not** close the gap by raising a threshold. (Fallback before stopping:
   relocate more, compress less.)
2. Any `#N` citation cannot be preserved across the union — revert that cut.
3. A relocation cannot clear §4.2's trigger-coverage precondition — that entry
   does not relocate; it falls through to §4.3 or stays.
4. The lazy import cannot resolve `GOTCHAS_SIZE_WARN_BYTES` — STOP and surface,
   rather than restating the literal.
