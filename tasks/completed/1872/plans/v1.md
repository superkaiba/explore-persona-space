architectural: false

## Requirement + acceptance criteria

`scripts/post_step_completed.py` refuses `--step 5a` (exit 2, `ERROR: step '5a' is not
in workflow.yaml § steps`) even though `/issue` SKILL.md names "Step 5a" 25 times in
prose and live sessions legitimately record it. Verified live incident: issue #1802's
session posted `--step 5a --exit-kind clean` ("code-reviewer round 1 dispatched;
awaiting epm:code-review v1"), was refused, and fell back to a coarser id (`5b`/`5`) —
degrading the §5 resume record and burning an error branch per posting (two session
transcripts carry the refusal line; the /daily 2026-07-29 miner independently flagged
the drift).

Acceptance criteria:
1. `uv run python scripts/post_step_completed.py --issue 1872 --step 5a --exit-kind clean --dry-run`
   exits 0 and renders `next_expected_step: 5`.
2. All existing workflow-yaml invariants stay green: `next_expected_step` resolves
   (`tests/test_workflow_yaml.py::test_steps_no_unreachable_terminal_orphans`),
   `entry_status_label` values are declared statuses
   (`::test_step_entry_status_labels_resolve`), Pydantic loader validators pass.
3. A regression test pins the new id (helper accepts `5a`; body carries
   `next_expected_step: 5`) so a future yaml rename fails loud.
4. No alias-table entry for `5a` (enum entry and alias must stay disjoint —
   `tests/test_step_completed_resume.py::test_alias_keys_never_shadow_real_step_ids`).

## Method delta (vs prior related work)

Same class as #1499 (the `9b` → `9b-same` refusal), different remedy: #1499 added a
HELPER-side alias because the canonical id already existed under another name
(`9b-same`). Here NO canonical id exists for the code-review-dispatch exit point, so
the remedy is a REGISTRY-side enum entry (the filed target,
`workflow_fix_target: .claude/workflow.yaml`), preserving record fidelity instead of
coarsening 5a→5 via an alias.

## File paths + concrete diffs

1. `.claude/workflow.yaml` — insert one entry in § steps between `id: "5"` and
   `id: "5b"` (reading order 5, 5a, 5b; list order is not load-bearing — the graph is
   defined by `next_expected_step`):

   ```yaml
     - id: "5a"
       name: code_review_dispatch
       entry_status_label:
         - code_reviewing
       entry_condition: "implementation marker posted; reviewer ensemble spawned, verdicts pending"
       next_expected_step: "5"
   ```

   Design notes:
   - `next_expected_step: "5"` — after dispatch, the next activity is verdict
     collection + the ensemble decision, which IS yaml step `5` (code_review). The
     incident marker's own note ("dispatched; awaiting epm:code-review v1") confirms
     this is the semantics sessions intend.
   - `entry_status_label: [code_reviewing]` — matches neighbors 5/5b (legacy sub-phase
     labels). Nothing currently points AT 5a (4b→5, 5b→5), so this field is nearly
     inert; consistency with neighbors wins over adding `running` (which would diverge
     from the whole region's label convention — out of scope).
   - No `posts_marker` — 5a itself posts nothing (the reviewers post
     `epm:code-review*`); step 5b already omits the field, so it is optional.
2. `tests/test_step_completed_resume.py` — add one regression test (next to the 9b
   alias tests, reusing the `helper_module` fixture):
   `test_helper_accepts_5a_with_next_step_5` — `main(["--issue","1872","--step","5a",
   "--exit-kind","clean","--dry-run"])` returns 0 and stdout carries
   `step: 5a` + `next_expected_step: 5`.

No other files. Explicit no-changes with reasons:
- `scripts/post_step_completed.py` — no change needed: the enum lookup picks up the
  new id automatically; NO `5a` alias (would shadow the real id and trip
  `test_alias_keys_never_shadow_real_step_ids`).
- SKILL.md — no change: it prescribes no `--step 5a` exit site (sessions improvise
  the id); the steps enum is not part of the emitted tables
  (`render_marker_kinds_table` / `render_active_vs_awaiting_table` cover markers +
  statuses only), so no `--emit-tables` regen.
- Consistency-lint extension to sub-step ids (the filed body's "consider" leg):
  REASONED NO-CHANGE. The yaml § steps is deliberately coarser than SKILL prose —
  prose names ~10 further unregistered sub-steps (5c, 5d, 5c-bis, 5c-quater, 0c,
  0c-link, 10c, 10c-bis, 1b, 1d) that are narration, not exit-record ids. A lint
  requiring every prose "Step Xx" to be registered would force speculative entries,
  weakening the enum exactly the way speculative aliases weaken the typo guard
  (the `_STEP_ALIASES` doctrine). Registration stays incident-backed-only; `5a` is
  the only id with recorded refusals.
