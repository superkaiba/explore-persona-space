## 3. Design

### Recommendation: option (b) — route the removal through a sparse scratch worktree unconditionally

- **Against (a) (local `git rm` fast path + fallback arm):** the fast path's precondition (duplicate present in the local root tree) is the *uncommon* case — the merge lands server-side and the guard runs seconds later, before any root pull — and is exactly the case that failed in the incident. Keeping it doubles the recipe surface for a path that mostly won't fire, and keeps a shared-root-index staging path alive (the existing pathspec-limited commit exists precisely because the shared index carries concurrent sessions' staged files).
- **Against (c) (sync local main first, then existing `git rm`):** `sync_repo_root.py` exit 0 includes the in-flight state (pull may not have run), so (c) needs its own existence-recheck machinery *plus* a detection re-run to disambiguate "sync didn't pull" from "a concurrent guard already removed the dupe"; it also pull-rebases and pushes unrelated local root state mid-guard (autostash on the always-dirty root, rebase of unpushed work), and a wedged root fails the guard even though the origin-side cleanup was achievable.
- **For (b):** single invariant — the scratch worktree is detached at the *same fetched origin/main* the detection just `ls-tree`'d, so `git rm` matches **by construction**; its index is private (no concurrent staging races, no pathspec-limited-commit hack needed); every command is `git -C`-scoped (the hook's designed override, `guard_repo_root_branch.sh:1060-1061` — verb- and path-blind per-clause waiver); the concurrent-duplicate-removal race is idempotent (rebase drops the now-empty commit — live-verified); footprint is ~KBs via a sparse cone (a full checkout is **7.66 GB / 102,631 files** — measured — on the shared VM root disk with a 40 GB preflight floor, ruled out). Local-root convergence is handled by a small residue tail delegated to the sanctioned helper.
