## 3. Design (per-file diff sketches)

### Design question 1 — `--by` vocabulary (decided)

- **`pm-chat`** — PM-session posts on another session's task. Matches the task Goal's literal proposal and the in-the-wild note signature "PM-chat" already listed in SKILL.md's triage paragraph.
- **`autonomous_session_watch`** — ALL watcher sites. Prefer consistency with the value site 4 already emits (`scripts/autonomous_session_watch.py:15483`); introducing a second value (`watcher`) for the same emitter would fragment the vocabulary and any future reader would have to match both. **No renames** of already-emitted values (`autonomous_session_watch`, `spawn_session-stop`) — renaming has downstream-reader implications for markers already on disk.
- **`spawn_session`** — the duplicate-dispatch-suppression post (a different pass than `cmd_stop`'s `spawn_session-stop`; script-identity slug).

### Design question 2 — `TRIAGE_MACHINE_BY`: add NOTHING (decided)

`TRIAGE_MACHINE_BY` strips by *by-value*, not by kind — adding `autonomous_session_watch` would strip the watcher's pod-safety ALERTS and failure records (exactly the advisory content triage exists to surface, since `epm:progress`/`epm:failure`/`epm:same-issue-followup-run` are NOT in `TRIAGE_EXEMPT_KINDS`). The watcher's one bookkeeping post (`_post_followup_run_marker`, a completion marker on behalf of a dead session) stays a candidate — the enumerator "deliberately over-approximates"; cost is one first-line read. Telemetry-vs-advisory separation by `by` alone is impossible for this emitter, so the conservative default holds: the distinctive `by` sharpens the LLM-side classification only.

## 11. Decision Rationale

- **`pm-chat` for PM posts.** *Why:* task Goal names it verbatim; SKILL.md's signature list already uses "PM-chat". *Source:* task #966 body `## Goal`; `.claude/skills/issue/SKILL.md:5122`. *Alternatives:* `research-pm` (rejected — diverges from the established note-signature string).
- **`autonomous_session_watch` (not `watcher`) for all watcher sites.** *Why:* one site already emits it; one value per emitter; renames have downstream-reader implications for on-disk markers. *Source:* `scripts/autonomous_session_watch.py:15483`. *Alternatives:* `watcher` (rejected — vocabulary fragmentation), per-pass values like `pod-safety`/`followup-reaper` (rejected — over-engineering; the note bodies already self-describe the pass).
- **No `TRIAGE_MACHINE_BY` additions.** *Why:* machine_by strips by-value across ALL kinds; the same identity emits advisory pod-safety alerts and bookkeeping completions — stripping would suppress exactly what triage must surface; over-approximation is the documented design ("a false positive costs one first-line read"). *Source:* `task_workflow.py:1485-1488, 1536-1541`; #779 incident. *Alternatives:* kind-scoped stripping (rejected — new mechanism, out of scope), a `TRIAGE_ADVISORY_BY` constant (rejected — invites mechanical externality classification the design keeps LLM-side).
- **`spawn_session` for the duplicate-suppression site.** *Why:* third emitter of the same class (automated cross-session post defaulting to unknown), 2-line fix; distinct from `spawn_session-stop` because it is a different pass. *Source:* `scripts/spawn_session.py:1602-1631` vs `:2372`. *Alternatives:* leave at `unknown` (rejected — inconsistent with the convention this task establishes), reuse `spawn_session-stop` (rejected — mislabels the pass).
- **Two pytest pins, no lint check.** *Why:* the invariant is small and stable; source-inspection + set-membership tests are ~15 lines and run in ms; a `workflow_lint` pass can't verify prose prescriptions and would be disproportionate. *Source:* existing conventions in `tests/test_pre_dispatch_triage.py` (pure-function tests) and `tests/test_autonomous_session_watch.py` (imports the script module via `sys.path`). *Alternatives:* full behavioral monkeypatch tests (allowed upgrade, §10); no test (rejected — a later "helpful" machine_by addition would silently invert the fix).
- N/A — no hyperparameters, no model training, not a replication.
