**Exact text to insert** (one bullet, multi-line continuation indented two spaces to match sibling bullets in the file):

```
- **VM `earlyoom` SIGTERMs bulk in-memory tensor loads silently (NO Python traceback).** The EPS VM runs Ubuntu `earlyoom`, which sends SIGTERM to the highest-`badness` process when *available* memory (MemAvailable, not MemFree) drops below 10% — ~12.8 GB of the 128 GB total — and SIGKILL at 5% (~6.4 GB). Scripts that load a bulk tensor set (per-rollout activations, per-step checkpoints, an all-at-once diff-of-means corpus) into memory at once trip this under fleet pressure: the process dies WITHOUT a Python traceback (earlyoom interrupts before any handler runs), so the log just stops mid-progress and looks like a hang. This is the host-RAM analogue of the RunPod per-pod EDQUOT quota above — a silent resource limit, not a clean exception. RULE for bulk tensor reductions (diff-of-means, layer averages, PCA): stream-reduce — iterate one tensor at a time, accumulate sums + counts into a fixed-size buffer (`L × D × 4 bytes` ≈ 460 KB for typical activations), never materialize all N at once; peak RSS then stays O(one-tensor) regardless of N. Verify a silent death with `journalctl --since '<time>' | grep -i earlyoom` (it logs the killed PID + its VmRSS + `badness`) or `systemctl status earlyoom`. Reaching for a bigger-RAM VM only raises the bar; the stream-reduce removes the bound entirely. (Incident #658 round 5, 2026-06-30: the persona-vector `r_B` build loaded ~12000 activation tensors (~38 GB) at once; earlyoom SIGTERMed it at VmRSS 33 GB under fleet pressure (9.4% avail) with no traceback; the round-5 fix stream-reduced the load.)
```
