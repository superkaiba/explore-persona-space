### 0.0 TL;DR (plain English)

Upload-verification currently proves that the FILES a run wrote are all present (#537 per-file git diff, #2187 out-root name-set diff) and that a producer's own count field matches what was asked for. It never opens the files. On #2091 that let a store pass while ~25% of the rows inside those present files were never written: every file was there, byte sizes matched, and the count check compared the producer's self-reported `capture_rows` — which was literally the EXPECTED number copied out of the input manifest — against that same expectation, so it could not fail. This task adds the missing arm: count what is REALLY in the row-index files on HF, compare it against the input-side declaration, and FAIL on a shortfall. A producer's own count is reported for context and is never the quantity the gate is decided on.

Measured at plan time, the decisive design fact: in the healthy (post-repair) #2091 store the realized row-LINE count is 2048 against an expectation of 2000, because the repair shard overlaps — while the distinct FULL-ROW-IDENTITY count is exactly 2000. So the gate quantity is the distinct count of a caller-declared COMPOSITE row key (the unit key plus any draw/rollout index), with the raw line count and per-shard breakdown reported alongside. A line-count gate would have false-FAILed every repaired store; a unit-key-only gate would have passed a store holding 1 of K rollouts per unit.

### 1. Goal

Verbatim from the task body: **Make per-issue upload-verification reconcile REALIZED artifact contents, so a store that is short INSIDE its files cannot pass.**

Three words are load-bearing. **REALIZED** — the quantity read out of the artifact's own bytes, never a field the producer wrote about what it believes it wrote. **short** — denominated in ROWS at full logical identity, not in units: a store with complete unit coverage and a fraction of each unit's rows is short (round 1). **cannot** — a spec step alone is skippable, so the gate needs the mechanical arm (Layer 1) plus the attestation token (Layer 2) that makes a skipped sweep block teardown, exactly as #2187 made the out-root sweep unskippable; and every escape hatch in Layer 1 (exemption, SKIP, unknown size, budget overflow) must be VISIBLE rather than silent, or "cannot" is false by another route (round 2).

Four consequences that shape §4:

1. **The raw LINE count cannot be the gate quantity.** A healthy repaired store holds 2048 lines against an expectation of 2000 (the repair shard overlaps; the manifest carries its own `n_duplicate_rows` field). A `realized_lines == expected` gate would FAIL all three healthy jobs. The distinct full-row-identity count hits the expectation EXACTLY on all three — that is the gate quantity.
2. **Nor can a UNIT-only key be** (the round-1 critic's finding). Rows carry both `context_id` and `rollout_k`, so for any multi-rollout store a unit-key-only distinct count is satisfied by 1-of-K rollouts per unit while (K−1)/K of the rows are absent — the same producer bug class on a different axis. The key must be the full logical row identity. Verified this session that #2091's store is DEGENERATE on this axis (`rollout_k == 0` on all 2048 wildchat rows, so distinct `(context_id, rollout_k)` = distinct `context_id` = 2000), which is exactly why the incident could not have surfaced it and why the §6.2 pin numbers are unchanged by the fix.
3. **The producer's self-reported field is wrong in BOTH directions across this artifact's history** — pre-repair `capture_rows` over-reported (echoing `n_rows`=2000 for a 1552-line store), and post-repair the manifest's own `n_rows_captured` UNDER-reports (1488 against 2000 realized distinct rows, stale since the repair). No producer field is a safe gate quantity; both are worth REPORTING, and a self-reported-vs-realized disagreement must not by itself flip the verdict (a legitimately repaired store carries a stale field).
4. **The cost is bounded and now measured** — 4,152 tree entries enumerated + 12 manifests + 48 index files (20–184 KB each, ≈7 MB total) fetched and counted in well under a minute, one scoped listing per prefix. This is the measured basis for §9 — but per the round-2 finding it is a FIXTURE measurement, not a bound: the bound is the aggregate budget in §4(A).

### 4. Design

**Why code, not a model call:** deterministic counting and set arithmetic over JSONL lines; an LLM judgment would add nonzero false-PASS probability to a durability gate. Behavior-implantation / on-policy / persona-vectors / data-realism / contrastive-negatives / measurement-validity requirements: N/A — no model training, no generation, no eval data, no DV in this task. Embedded-shell exit-path trace: N/A — no multi-arm embedded shell blocks introduced.

**(A) `scripts/verify_uploads.py`** — the mechanical core, mirroring `check_outroot_residue`'s structure (two input modes, fail-loud missing input, ERROR flips the overall verdict via the existing aggregation at `verify_uploads.py:1847`).

New CLI surface (all additive; absent ⇒ SKIP):

- `--expected-rows LABEL=N` (repeatable) — the INPUT-side declaration per label, denominated in distinct full-key ROWS. The gate's right-hand side.
- `--row-index-hf-prefix PREFIX` (repeatable) — HF data-repo prefixes to enumerate. Deliberately NOT defaulted from `--hf-prefix`: the residue check's prefix set means "everywhere the run wrote", a different quantity, and a silent inference here would be exactly the convenient-affordance defect this task exists to remove.
- `--row-index-local-root DIR` — local/pod-side mode (the second input mode, mirroring `_outroot_disk_entries`; also what makes the check testable without HF and what §6.2's FAIL direction uses).
- `--row-index-glob PATTERN` (default `row_index*.jsonl`).
- `--row-index-distinct-key FIELDS` — comma-separated field list forming the row's full logical identity (e.g. `context_id,rollout_k`); the distinct count over field TUPLES is the primary gate quantity. A single field is the degenerate case, legal only where rows are genuinely 1:1 with units.
- `--self-reported-rows LABEL=N` (repeatable) — a producer count field; REPORTED, never gated on.
- `--realized-rows-exempt LABEL=REASON` (repeatable) — LABEL-grained exemption with a mandatory non-empty reason. Deliberately NOT a path glob (v2's shape): a path filter removes FILES from a label's count, which is indistinguishable from the shortfall this check exists to catch.
- `--row-index-max-bytes N` (default 16_000_000) — per-file cap.
- `--row-index-max-total-bytes N` (default 268_435_456) and `--row-index-max-files N` (default 2000) — AGGREGATE caps over the whole matched set.

Mechanics, in order:

1. **Enumerate** each prefix with `list_repo_entries_complete(..., path_in_repo=<prefix>)` (`hub.py:917` — the sizes-preserving core of `list_repo_files_complete`, same paginated + retrying walk; server-side scoped per #833). One listing per prefix. Local mode reads sizes from `os.stat`.
2. **Attribute** each matched index file to EXACTLY ONE label by PATH-COMPONENT match (the label appears as a full `/`-delimited component, or as a component prefix followed by a non-word boundary) — never a bare substring, which would let `syc_aita` swallow a hypothetical `syc_aita_v2`. This mirrors `filter_issue_scoped_git_paths`' component-boundary discipline (`verify_uploads.py:1288`) and its digit-boundary lesson, and adds the uniqueness contract that comparison anchor does not carry. Three fail-loud arms, all evaluated BEFORE any counting: a label matching ZERO files ⇒ ERROR `row-index-missing`; a matched file attributed to NO label ⇒ ERROR `row-index-unattributed`; a matched file attributed to ≥2 labels ⇒ ERROR `row-index-label-ambiguous`, naming the file and every matching label. The third arm closes the round-2 finding: with labels `arm` and `arm-repair`, a file under `arm-repair/` matches both, and if `arm` were wholly absent with a coinciding expectation the repair file would satisfy both counts.
3. **Budget, before the first fetch.** Any entry whose listed size exceeds `--row-index-max-bytes` ⇒ ERROR `row-index-file-over-cap`. Any entry with an UNRESOLVED size (the helper's `int | None`) is resolved by ONE batched `HfApi().get_paths_info(repo_id, [paths], expand=True, revision=<resolved rev>)` call — the established in-repo bounded-probe pattern (`.claude/rules/artifact-reuse.md` item (j), one POST per repo, measured ~0.5 s); still unresolved ⇒ ERROR `row-index-size-unknown` naming the path (fail-closed: an unprovable size is never assumed under cap). Then the matched set's FILE COUNT and TOTAL BYTES are checked against `--row-index-max-files` / `--row-index-max-total-bytes` ⇒ ERROR `row-index-budget-exceeded` naming both realized figures and both caps, with ZERO downloads performed. This is what makes constraint (a) a bound rather than a per-file spot check.
4. **Fetch + count** each attributed file via `hub.stage_hub_file` (retried, atomic, fail-loud — `hub.py:2649`), counting non-empty lines and the distinct TUPLES of the declared key fields. A row missing ANY declared key field ⇒ ERROR `row-index-key-absent`, never skipped (a silently skipped row is a shrunken denominator).
5. **Exemptions, after counting and before the verdict.** An exemption naming a label that is not in the declared `--expected-rows` set ⇒ ERROR `realized-rows-exempt-unmatched` (rejects stale and typo'd exemptions). An exempt label's counts are STILL computed and reported; its row is emitted as a **WARN** `realized-rows-exempt` naming the label, the verbatim reason, expected, realized distinct and realized lines — so a legitimately-partial class is visible in the report and a SHORT exempt class is visible too, it simply does not block. Exemptions never remove files, never suppress a row, and never turn a row OK.
6. **Verdict lattice** (per non-exempt label; `distinct` mode = key declared):

   | mode | condition | verdict + tag |
   |---|---|---|
   | distinct | `distinct < expected` | **FAIL** `realized-rows-short` |
   | distinct | `distinct > expected` | **FAIL** `realized-rows-unexpected-surplus` |
   | distinct | `distinct == expected` | OK |
   | no key | `lines < expected` | **FAIL** `realized-rows-short` |
   | no key | `lines >= expected` | **WARN** `realized-rows-no-distinct-key` |

   The no-key `>=` branch is WARN, not OK, because #2091's own healthy store shows lines legitimately exceeding the expectation — so without a key an equality or surplus is uninformative about a shortfall, and the detail names the flag that would resolve it. Every row's detail — OK, WARN and FAIL alike — carries expected / realized-distinct / realized-lines / `lines − distinct` duplicates / the per-shard breakdown / the declared key fields / the self-reported value labeled `producer self-reported (context only)`. A self-reported-vs-realized disagreement appends a `producer-field-mismatch` note and NEVER flips the verdict on its own (consequence 3).
7. **SKIP / ERROR** exactly as `check_outroot_residue`: neither `--expected-rows` nor a prefix/root ⇒ SKIP with a detail naming the flags; a nonexistent local root, an unreadable listing, or a Hub listing failure ⇒ ERROR (a missing input must never read as a clean zero — this check exists to close a false-PASS).
