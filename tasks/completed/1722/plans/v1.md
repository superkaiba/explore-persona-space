## 6. Risks

1. **`gh pr view <PR> --json mergeCommit` returns `null` on a NOT-YET-MERGED PR.** If the caller invokes the derivation BEFORE `gh pr merge` succeeds, the `-q .mergeCommit.oid` extraction yields the string `null` (or an empty string, depending on `gh` version), and the marker records that as the SHA. Mitigation: Edit A's wording binds the derivation to AFTER `gh pr merge` reports success (already the Step 10d ordering — the derivation lives IN the Success bullet, which fires only on a successful merge). The pre-post commit-subject cross-check is the secondary defense: `git log -1 --format='%s' null` errors, so a `null` value fails the subject check and aborts the post loudly (never quietly writes `null` into the marker).

2. **The pin test cannot import from `.md`.** SKILL.md is prose, not executable Python. The test must construct the expression as a string and `eval()` it. This works but has two hazards: (a) the `eval()` sandbox needs the exact locals the one-liner uses (just `e`) — the skeleton passes `{"e": e}` explicitly and no globals, matching the one-liner's implicit scope. (b) the string literal in the test can drift from the one-liner in SKILL.md — `test_step0_expr_appears_verbatim_in_skill_md` reads SKILL.md at test time and asserts the exact substring is present, which pins the two in lockstep.

3. **A sibling grep sweep might surface a legitimate docstring-pattern hit.** The `__doc__.splitlines()[0]` pattern (~28 hits across per-experiment scripts) is safe by construction: a module docstring is the file's leading string literal, always present, never empty. The discriminator: **patch when the LHS is a possibly-empty RUNTIME string** (a field read from an events row, an API response body, a caller-supplied `note`); NEVER patch `__doc__.splitlines()[0]` — that operates on a compile-time constant. Similarly `str(e).splitlines()[0]` operates on exception messages, which are never empty. The plan-time sweep already confirmed no OTHER in-scope runtime-string sites exist, so the implementer only needs to re-verify with a repo-wide grep on the day of implementation (in case something landed between plan and implementation).

4. **The `<PR>` placeholder in Edit A is a placeholder, not shell text.** Step 10d elsewhere uses `<PR>` as a template placeholder that a session-owned variable expands (`gh pr view <PR> --json …`). The implementer preserves this convention — do NOT substitute a concrete PR number in the SKILL.md prose.

## 11. Decision Rationale

- **Why `gh pr view <PR> --json mergeCommit -q .mergeCommit.oid` over parsing the merge command's output?** The `gh pr merge` command's stdout format is not stable across versions and is a shell-scraping surface; the PR object's `mergeCommit` field is the durable, versioned API. It also decouples the derivation from the merge invocation (the derivation reads current state, so it survives re-runs / retries / the auto-merge shape). Ancillary benefit: it uses the same `gh pr view --json` shape SKILL.md already uses for OTHER PR fields (`state`, `mergeable`, `headRefOid`) — pattern reuse (CLAUDE.md § "Reuse existing in-repo tools/helpers"). *Source: SKILL.md's own existing usage sites + `gh pr view --help` documentation.*
- **Why the total `((e.get("note") or "").splitlines() or [""])[0][:140]` form over `if e.get("note")` guard?** The idiom is a one-liner INSIDE a fenced Python heredoc that users paste into their shell verbatim. A control-flow rewrite (`first_line = ""` + `if lines: first_line = lines[0]`) would break the one-line shape. The `or [""]` fallback keeps it a single expression AND matches the guarded style already used in `scripts/task.py:298/319` and `src/explore_persona_space/task_workflow.py:1630` (`X if X else ""`). *Source: sibling in-repo idioms.*
- **Why a new test file `tests/test_step0_enumerator_total_form.py` over folding into an existing file?** The idiom is prose (SKILL.md), not importable code, so the test's ONLY subject is this one expression. A new file makes the pin's target grep-discoverable (a future editor asks "what pins this SKILL.md line?" and finds the file by name) — the same shape as `tests/test_issue_skill_marker_contract.py` / `tests/test_issue_skill_exit_breadcrumb.py`. *Source: CLAUDE.md § "workflow-prose durability pin" convention.*
- **Why append the CLAUDE.md guidance to L227's paragraph rather than a separate H3?** L227 is the CANONICAL post-marker CLI documentation. Adding a related guidance sentence in the same paragraph keeps the discoverability high (a reader looking up `post-marker` sees the `--file` recommendation at the same time). A separate H3 further down would risk being missed. *Source: L227's existing prose already covers `--file`/`--note` semantics — the new sentence extends that same discussion.*
- **No literature hyperparameters:** this is a docs / text-idiom fix. `Source: N/A — no model training / no experimental hyperparameters.`
