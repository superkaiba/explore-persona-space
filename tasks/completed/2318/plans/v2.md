# Plan — issue #2318: violation-grain classification for whole-repo scan nodes in the Step 9a-ter inline payload lint gate

### 0.0 TL;DR (plain English — the user reads this first)

The Step 9a-ter inline payload lint gate (`scripts/inline_lint_gate.py`) is the gate that
lets an inline round commit code at the repo root. Since #2235 it has carried a
"subtraction" layer meant to stop a payload being blocked by test failures that were
ALREADY failing on `main`. **That layer has never worked.** Two independent bugs, both
found by reproduction (recorded in the task body's attribution addendum):

- **D1:** it reads the known-red ledger's rows as strings when they are dictionaries, so
  its membership test is always false — the layer is dead code.
- **D2:** even with D1 fixed, it labels only pytest's one-line `FAILED <nodeid>` summary,
  while the lines that actually name offending files are traceback lines. So the label is
  never consumed.

This plan fixes both, and makes the corrected layer safe by deciding at **violation
grain**: for a whole-repo scanning test, the payload's file is looked up in the set of
files the test's own failure message lists. In that set ⇒ the payload ADDED the violation
⇒ block. Not in it ⇒ the red is main's, not the payload's ⇒ demote to a non-blocking
report. The file registry and the extraction helper are IMPORTED from #2316's
`scripts/step9c_baseline.py`, not copied.

Net effect: the gate keeps blocking exactly what it blocks today for new violations, and
stops false-blocking inline rounds on main's own pre-existing scan reds. 0 GPU-hours.

**What would change my mind:** if the §5 C1 test (a payload that ADDS a violation to a
registry node red on main) ever demotes instead of blocking, the violation-grain criterion
is unsound for this gate's single-sided input and the change is wrong — stop, do not tune
a threshold. Equally, if C2/C4/C6 (the three no-change / anti-wedge controls) cannot be
made to pass together, the corrected layer cannot be made safe and the right answer is to
DELETE the #2235 Phase A layer from this gate rather than repair it.

**Success criteria:** all nine §5 cases pass as specified; `workflow_lint.py` no-flags
green on the round's files; the registry-identity live-tree pin passes.

**Kill criteria (halt-and-report, do not work around):** (a) C2, C4, or C6 fails after
two implementer rounds — the layer is unrepairable here, report and propose deletion;
(b) #2316 is abandoned or renames its public symbols and no import is possible — return
to planning, never fork the registry; (c) the block→nodeid derivation cannot be made
self-validating against the `-rA` summary set — abort the node-grain edit and leave the
existing line-grain path untouched.

### 0. Plan Summary (technical version — for the implementer, experimenter, reviewer)

Single-file change to `scripts/inline_lint_gate.py` (plus tests and a SKILL.md prose
clause). Three coupled edits, which MUST land together because D1 alone would activate a
dormant node-grain demotion — the over-demotion acceptance criterion 4 forbids:

1. `_ledger_nodeids(ledger) -> set[str]` replaces the inline
   `{str(n) for n in ledger["failing_tests"]}` expression: dict rows become
   `f"{row['file']}::{row['name']}"`, plain `str` rows pass through (forward-compat),
   any other shape is SKIPPED with one stderr warn naming the row's type. Never raises.
2. `failure_block_idxs(pytest_lines) -> dict[str, set[int]]` buckets the `FAILURES`
   section into per-node line-index blocks, keyed on the nodeid derived from each
   `_____ <name> _____` header plus the block's trailing `<file>:<line>: <Exc>` locus,
   and cross-validated against the `-rA` short-summary `FAILED <nodeid>` set. A block
   whose derived nodeid is not in that set is DROPPED (fail-closed, one warn).
3. `evaluate()` consumes both: a pytest-leg hit line inside a block whose nodeid is BOTH
   a `_ledger_nodeids` member AND a `VIOLATION_SET_SCAN_NODES` member is reclassified
   `verdict.reported` labeled `pre-existing-on-main (ledger, violation-set)` **iff** no
   payload path is in `extract_violation_paths(<block text>)`. Otherwise today's
   classification stands unchanged.

The existing `^FAILED`-line node-grain label is RETAINED verbatim as the non-registry
fallback (criterion 4's degrade target), so nothing outside the registry changes shape.

### 1. Goal

Classify whole-repo SCAN-style invariant-test failures at VIOLATION grain in the Step

already red on pristine `main` can never be demoted to non-blocking on node identity
alone — while a payload that adds nothing to such a node stops being blocked by main's
red. Mirror of the #2316 fix to `scripts/step9c_baseline.py compare`, reusing that
task's registry rather than duplicating it.

### 4. Design

**Registry import.** `from step9c_baseline import VIOLATION_SET_SCAN_NODES,
extract_violation_paths` via the same path-load idiom the file already uses for sibling
scripts; a failed import degrades to today's node-grain behavior with one loud stderr
warn and NO new blocking class (criterion 4's posture, applied to the import itself).
Copying either symbol is forbidden (criterion 2).

**Membership rule** (parity with `_violation_setdiff_member`): for nodeid `n`,
`f"{file}::{name.split('[', 1)[0]}" in VIOLATION_SET_SCAN_NODES` where `file, _, name =
n.partition("::")`. A collect-error row can never match (its junit name is a dotted
module path) — the same deliberate non-match #2316 documents.

**Single-sided decision.** Unlike `compare`, this gate has no pristine-main run, so
there is no main-side violation set to diff against. It does not need one: the gate KNOWS
its payload, and "did the payload add a violation to this node" is answered directly by
`payload ∩ extract_violation_paths(block)`. Any path in the extracted set that is not a
payload path is main's own violation and is irrelevant to this payload's verdict.

**Why the pytest output is sufficient.** The leg runs `uv run pytest <tests> -q -rA`
(`:728`) — no `--tb=no` — so the full assertion message, including every offender row, is
present. Verified by running the same assert shape standalone: offender paths appear on
the `E   <path> (…)` row and the rewritten `E   assert not ['…']` row; the short-summary
line is the BARE nodeid.

**Direction of change.** Strictly SUBTRACTIVE per node, as #2235 intended: a block either
demotes wholly (no payload path in its violation set) or keeps today's classification.
No new blocking class is introduced anywhere.

### 11. Decision Rationale

Load-bearing choices and why:

- **Import the #2316 registry rather than copy** — criterion 2; a second curated list
  drifts silently, and the curation rule (source-verify that each member's message lists
  offenders as repo-relative paths) is expensive to re-derive. Cost: a merge-order
  dependency, accepted as G1.
- **Single-sided payload-intersection instead of a branch-vs-pristine set diff** — this
  gate has no pristine run, and manufacturing one would add a full second pytest pass to
  every inline round. The payload intersection answers the same question for this gate's
  purpose. Source: the gate's own `payload` list (`read_payload`, `:329`).
- **Node grain via the FAILURES-section blocks** — offender attribution lives in the
  traceback (measured, §4), so a line-scoped label cannot work; the section-window idiom
  is already established in this file (#1585/#2023).
- **Retain the `^FAILED`-line label as the non-registry path** — keeps C4/C6 byte-identical
  and gives criterion 4 a concrete degrade target.
- **Document, do not add, a ledger staleness/`dirty_code_paths` guard** — recorded in the
  task body: a `dirty_code_paths: true` refusal would disable the layer whenever the fleet
  has dirty paths (nearly always) and thereby newly BLOCK payloads — the #1388 class.
