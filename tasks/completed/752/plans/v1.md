## Goal

A 7B forward that captures hidden states always lands on a GPU with ≥40 GB HBM via the GCP / auto router; the router never silently under-provisions vs a plan that declared activation capture.

### 0.0 TL;DR (plain English)

- **What I'll run:** No experiment — this is a workflow fix. I'm adding a new compute "size label" (`capture-7b`) so that when a future experiment says "I'm going to record the model's internal activations on a 7B model," the system automatically books a big-enough GPU instead of the tiny default one. I'm also adding a sentence to the planner's instructions telling it to use that label for activation-capture work.
- **What I expect:** Two future-OOM incidents (#666, #744) both happened because an activation-capture job got booked onto a 16 GB GPU and ran out of memory mid-run. Naming the right size up front removes that whole failure class.
- **What would change my mind:** If a downstream test turns out to pin the exact set of size labels (so adding one breaks it), or if some existing job already uses the small `eval` label for capture work and silently depends on it — then a pure "add a row" change isn't enough and I'd need to touch those callers too.

### 1. Goal

A 7B forward pass that captures hidden states (all-layer residual streams, Welford activation accumulation, per-token activation dumps) must always land on a GPU with enough HBM to hold model weights plus the captured activations; the GCP / auto router must never silently route such a phase to the 16 GB L4 default when the plan declared activation capture. Quoted from the task body Goal: "A 7B-forward-with-activation-capture phase always lands on a GPU with enough HBM; the router never silently under-provisions vs the plan." This closes the failure class that bit #666 (L4 OOM) and #744 (g2-standard-4 OOM), where the plan requested an A100-80-class machine but the intent default routed L4.

### 11. Decision Rationale

**Route A (new `capture-7b` intent) over B and C.**
- **What:** Add a new intent `capture-7b` mapping to `a2-ultragpu-1g` (A100-80) primary / `a2-highgpu-1g` (A100-40) fallback, plus a planner.md sizing rule. Do NOT gate `eval`/`debug` on workload semantics (route B); do NOT honor a `--gpu-type` override on the GCP lane (route C).
- **Why:** Route A preserves the project invariant that GCP / auto sizing comes from `--intent` ALONE. Route C would re-litigate that invariant — the dispatch CLI deliberately refuses a `--gpus` machine-type mismatch (`gpus_machine_mismatch`, exits 2) precisely so the lane never provisions a wrong-sized VM off an ad-hoc override; adding `--gpu-type` would reopen exactly that surface. Route B couples the router to workload semantics (the router would have to read a capture sentinel out of the plan or an env var), which is invasive and fragile — a missed sentinel silently re-creates the under-provision, the exact failure mode we are closing. Route A is a ~4-line additive map change that gives both the caller and the planner a concrete, declarative name.
- **Source:** invariant from CLAUDE.md § "GPU sizing on the gcp/auto lanes comes from `--intent`, never `--gpus`" + `scripts/dispatch_issue.py` lines 540-619 (`gpus_machine_mismatch`, #599); existing additive-intent precedent #631 (`lora-7b-h100` / `eval-h100`), #677 (`cpu-bigmem`), #747 (`cpu-small` / `cpu-mid`), #743 (`sweep-8g-*`) — every prior HBM/CPU class was added the SAME way (new intent + map rows + doc), never via an override.
- **Alternatives:** B (workload-coupled gate) and C (`--gpu-type` override) — both rejected above.

**`eval`/`debug` STAY on L4 (do NOT re-primary to A100-40).**
- **What:** Keep `INTENT_TO_MACHINE["eval"]` / `["debug"]` → `g2-standard-4` (L4). The fix is the explicit `capture-7b` opt-in, NOT a default escalation of `eval`.
- **Why:** L4 (16 GB HBM, ~$0.7/hr-class) is the correct cheap default for the genuine eval-WITHOUT-capture case (logprob-only ARC-C, short batched vLLM generation on ≤7B) — escalating every `eval` to A100-40 (40 GB) would spend A100 credit on the common cheap case to fix a narrow capture-only failure class. The L4 vs A100-40 vs A100-80 HBM trade: L4 16 GB is enough for a 7B bf16 forward WITHOUT large activation retention (weights ~14 GB leave ~2 GB headroom — tight but workable for logprob-only / small-batch generation), A100-40 (40 GB) clears weights + moderate activation capture, A100-80 (80 GB) clears weights + heavy all-layer capture at realistic batch. The capture work is the part that needs the headroom, so the right design makes capture the explicit opt-in (`capture-7b`) and leaves the cheap path cheap. The existing `INTENT_A100_40_FALLBACK` already includes `eval`/`debug` (line 395-396) as a step-UP under L4 exhaustion, so a truly L4-constrained eval still gets A100-40 — that path is unchanged.
- **Source:** `INTENT_A100_40_FALLBACK` comment (lines 387-391) which already records the "`eval`/`debug` default to L4 on-demand, NOT A100-80" design + the #656 fallback-rung rationale; HBM figures are hardware specs (L4 = 24 GB on `g2-standard-4`? — see §12 assumption; the binding fact is L4 ≪ A100-40 ≪ A100-80 and capture OOM'd on it).
- **Alternatives:** re-primary `eval` → A100-40 to close the under-provision class entirely — rejected: spends A100 credit on the cheap eval case, and the planner.md rule + `capture-7b` already close the capture-specific class declaratively. (Recorded so the consistency-checker / critic see the choice was deliberate.)

**Intent name `capture-7b`.**
- **What:** `capture-7b` (vs `eval-capture-7b`, `eval-7b-capture`).
- **Why:** Shortest name that reads as "capture activations on a 7B model"; parallels the existing `lora-7b` / `ft-7b` / `sweep-8g-*` naming convention (job-kind + scale). `-7b` scopes it to the 7B HBM regime (a 70B capture would be a separate, larger intent — explicitly out of scope, §12).
- **Source:** naming convention of `INTENT_TO_MACHINE` keys (`backends/gcp.py` line 291).
- **Alternatives:** the two `eval-*` variants — rejected as longer with no added clarity; the name is allowed to change in review (§12).
