```python
# #951: material-compute liveness veto on the #664/#826 zombie-GPU override.
# A workload session burning >= this many CPU cores (delta cumulative session
# CPU / wall seconds between persisted ticks) on BOTH of the last two ticks is
# demonstrably computing — veto the running->stalled override. Sits between
# the two measured regimes: #664's hung EngineCore churned ~0.22 cores
# (Python-overhead idle burn) while #825's falsely-flagged live fit burned
# ~1.83-2.04 cores (+1102s/+989s per ~540s tick, 186% in top) — 2.27x above
# churn, 3.66x below real compute. Sustained-rate, so poll-interval-invariant
# (540s vs 1800s adaptive ticks).
ZOMBIE_OVERRIDE_CPU_CORES_MIN = float(os.environ.get("EPM_ZOMBIE_OVERRIDE_CPU_CORES_MIN", "0.5"))

# #951: denominator floor for the per-tick CPU rate. Below this wall-clock
# spacing between persisted CPU samples the rate is not computed (None ->
# veto inert): `ps -o time` truncates to whole seconds per process, so a
# short window inflates spurious rate from truncation noise (~1s x N
# session processes). Production intervals are 540s/1800s so the floor
# never binds there; it guards manual rapid re-polls and fast-smoke ticks.
ZOMBIE_CPU_RATE_MIN_DT_SEC = int(os.environ.get("EPM_ZOMBIE_CPU_RATE_MIN_DT_SEC", "120"))
```

### 4.3 New helper (pure, next to `_session_cpu_advancing` / `_roll_session_cpu_max`)

```python
def _session_cpu_rate_cores(
    prev_sample: str | None,
    prev_sample_epoch: str | None,
    current: str,
    now_epoch: int,
) -> float | None:
    """Per-tick session-CPU burn rate in cores, or None when not computable.

    rate = (current - prev_sample) / (now_epoch - prev_sample_epoch), where
    prev_sample + prev_sample_epoch are the SAME prior tick's persisted pair
    (written together by _save_state). None (fail-safe -> the #951 veto does
    NOT fire) when: either CPU sample is unknown/unparseable, the epoch is
    missing/unparseable/<=0, or the wall gap is < ZOMBIE_CPU_RATE_MIN_DT_SEC
    (truncation-noise floor) or non-positive (clock garbage). A NEGATIVE
    rate (run restart resets the session counter; a multi-shard child exit
    de-counts its cputime, #658) is returned as-is — it is below any
    positive threshold, so the veto does not fire on it.
    """
    cur = _parse_session_cpu(current)
    prev = _parse_session_cpu(prev_sample) if prev_sample is not None else None
    epoch = _parse_session_cpu(prev_sample_epoch) if prev_sample_epoch else None
    if cur is None or prev is None or epoch is None or epoch <= 0:
        return None
    dt = now_epoch - epoch
    if dt < ZOMBIE_CPU_RATE_MIN_DT_SEC:
        return None
    return (cur - prev) / dt
```

(`_parse_session_cpu` (l.3103) already handles `None`-ish/"unknown"/garbage → `None`; reusing it keeps parse semantics identical to the live probe path.)

### 4.4 Tick spacing derivation — the load-bearing detail (constraint 5)

The sidecar today persists **no timestamp for the CPU sample** (verified: the `_save_state` payload at l.3940–3992 carries `last_mtime_epoch` (a pod-side *log mtime*), phase-change/idle-span epochs — none is "when `session_cpu_secs` was sampled"). So the delta denominator is NOT currently derivable and gets a new key:

- `poll_once` persists `"session_cpu_sample_epoch": str(now_epoch)` in the same `_save_state` payload that persists `session_cpu_secs` — the pair is written atomically together (single payload dict, tmp+`os.replace`), so the epoch is always the timestamp OF the persisted sample.
- `now_epoch` is VM-side UTC (`int(datetime.now(tz=UTC).timestamp())`, l.3597) on both ticks — the denominator never mixes pod and VM clocks, so the #-clock-skew machinery is irrelevant to it.
- **Adaptive interval (540 s / 1800 s):** the denominator is the *actual* measured gap between persisted samples, never an assumed interval; a sustained burn rate is spacing-invariant (Δcpu scales with Δwall).
- **Poller restart:** the state file (`DEFAULT_STATE_DIR / poll-pipeline-<issue>.json`, l.4073) survives process restarts; a long gap between the last persisted tick and the first post-restart tick just dilutes the average rate → veto less likely → falls through to current behavior (the safe direction).
- **Fresh sidecar** (run start, manual deletion): `prev_state == {}` → no epoch, no prev sample, no prev rate → rate `None` on tick 1 and `rate_prev` unknown on tick 2 → veto inert for the first two ticks → current behavior. Never a garbage delta.
- **Run restart with surviving sidecar** (new launcher, session CPU counter resets near 0): `cur << prev` → negative rate → below threshold → no veto.
- **Ticks that early-return before `_save_state`** (SSH-fail path): the CPU pair neither advances nor resets — the same documented exposure `zombie_streak` and `ssh_fail_count` already have (function docstring l.3271–3274); no new failure class.

### 4.7 Streak/veto interaction (constraint 6) — reset to 0, justified

When the CPU veto fires, `zombie_streak` resets to 0 (the branch simply never sets it; identical mechanics to the #826 fresh-log veto and #864 namespace veto, which both leave/return streak 0).

Why reset, not hold: (a) **consistency** — both existing vetoes reset; material CPU is affirmative liveness evidence of the same strength as a fresh log. (b) **Fail-safe direction** — with hold-semantics, a run that demonstrably computed for N vetoed ticks would fire the override on the FIRST subsequent tick where the CPU signal degrades (one `ps` hiccup → rate `None` → veto can't fire → held streak ≥ 1 → immediate fire), i.e. degraded data would fail toward MORE false positives — exactly what constraint 3 bans. With reset, a degraded tick after material compute yields streak 0→1 (defer), and firing requires a SECOND consecutive stale non-material tick. (c) **Bounded cost** — on a run that computes materially and then genuinely hangs, detection latency is 2 ticks (~18–60 min) after the burn stops, identical to the latency any fresh-log-vetoed run already has today; missed-zombie cost is bounded idle pod-hours vs false-positive cost of a kill-by-PID reaper on a healthy run (the documented #826 asymmetry, l.560–563).

## 11. Decision Rationale

- **`ZOMBIE_OVERRIDE_CPU_CORES_MIN = 0.5` (env `EPM_ZOMBIE_OVERRIDE_CPU_CORES_MIN`).** What: minimum sustained per-tick CPU burn (cores) on both ticks to veto. Why: must sit above hung-EngineCore Python-overhead churn and below real compute. Source: measured incident data — #664/#826 record (function docstring + task body): hung `generate()` churned ~0.22 cores; #825 `epm:progress` v94: live fit at 186% CPU, session CPU +1102 s/+989 s per ~540 s tick → 2.04/1.83 cores. 0.5 = 2.27× above churn, 3.66× below compute; slightly below the geometric midpoint (≈0.64), deliberately biased toward preserving the #664 true positive per the task's constraint 1. Alternatives: 1.0 (leaves modest real compute at 0.5–1.0 cores unprotected — e.g. a single-threaded fit); 0.3 (only 1.36× above the one measured churn point — too tight given churn was measured once). Env-overridable for field tuning without a code round.
- **BOTH-ticks requirement.** What: rate ≥ T on the current AND previous persisted tick. Why: a single-tick spike can be a `ps` truncation/re-numbering artifact or a transient sibling process in the session; two consecutive material ticks (~9–60 min of sustained ≥0.5-core burn) is not producible by a hung EngineCore. Source: the candidate sketch (task body) + the #825 evidence, which was material on both counted ticks. Alternative rejected: single-tick veto (weaker artifact filtering; unnecessary since #825 satisfies both-ticks).
- **`ZOMBIE_CPU_RATE_MIN_DT_SEC = 120`.** What: minimum wall gap between persisted samples before a rate is computed. Why: `ps -o time` truncates per-process to whole seconds; over a short window truncation noise (~1 s × N session processes) inflates the rate (at 120 s, even a 60-process session's worst case is ≤0.5 cores, and typical sessions are ≤~20 procs → ≤0.17); production intervals (540/1800 s, `POLL_INTERVAL_DEFAULT_SEC`/quiet) never hit the floor. Source: probe mechanics read from the heredoc + interval constants in this file; the both-ticks rule is the second guard. Alternative: 60 s (thinner noise margin, no benefit).
- **Streak reset (not hold) on veto.** See §4.7. Source: the existing #826/#864 veto semantics in this function (consistency) + constraint 3's fail-safe direction.
- **New sidecar keys instead of a probe change.** What: `session_cpu_sample_epoch` + `session_cpu_rate_cores`. Why: the rate is fully derivable VM-side from the existing `SESSION_CPU_SECS` probe output; sidecar keys are backward-compatible by construction (absent → veto inert → current behavior). Source: read of the `_save_state` payload (no existing sample timestamp) + the clarifier's context note.
- Hyperparameter-grounding for training: N/A — `kind: infra`, no model training.
