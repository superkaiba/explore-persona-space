<h2>3. Hypothesis</h2>
<p>Replacing the recursive whole-repo <code>list_repo_files</code> probe with a direct, per-request-timeout-bounded HTTP probe of the Hub tree endpoint — page-1-only for check 23, self-paginated-under-a-cap for check 25 — will (a) preserve every existing check-23 verdict (PASS/FAIL/skip) on the fixtures, (b) preserve the #537 dead-pin FAIL (check 23) and the #653 depth-agnostic keyword match (check 25), (c) preserve the deliberate check-23(FAIL)-vs-25(SKIP) not-found asymmetry, and (d) bound worst-case wall-time per URL under throttling to <code>~_HF_PROBE_ATTEMPTS × _HF_PROBE_TIMEOUT_S</code> (≈ 10 s) on EVERY path including the paginating one — never ~143 s. <b>Falsified if</b> the direct tree-endpoint response cannot distinguish dead-pin (FAIL/SKIP per check) from revision-exists, if any existing test flips verdict, or if the simulated paginated-429 test does not return <code>unverified</code> within budget.</p>

<h2>4. Design</h2>

<h3>Approach chosen — direct bounded HTTP probe (brief option (a)), NOT a wrapped <code>list_repo_tree</code></h3>
<p>v1 tried to bound <code>list_repo_tree</code> from the outside; MUST-FIX 1 showed that cannot work (no <code>timeout</code> kwarg; the internal backoff is unreachable from an outer attempts cap). v2 calls the tree endpoint directly so the <code>timeout</code> is real and pagination is OURS to cap.</p>

<h3>New shared bounded primitive</h3>
<pre><code># module constants near line ~3979
_HF_PROBE_TIMEOUT_S = 5.0      # per-request connect+read timeout (real on every GET)
_HF_PROBE_ATTEMPTS  = 2        # at most 1 retry per page on a transient/429
_HF_PROBE_SLEEP_S   = 0.5      # tiny pause between the two attempts
_HF_PROBE_MAX_PAGES = 8        # check-25 self-pagination page cap
_HF_PROBE_DEADLINE_S = 12.0    # check-25 outer wall cap across all pages of ONE probe
_HF_EXISTENCE_CACHE: dict[tuple, tuple[str, str]] = {}   # per-process, see cache note

# A small structured outcome so each call site maps not-found INDEPENDENTLY
# (MUST-FIX 3 — no shared exception mapping).
class _TreeProbeResult(NamedTuple):
    status: str          # "ok" | "not_found" | "indeterminate"
    entries: list[dict]  # JSON entries gathered (page-1 for check 23, ≤cap pages for check 25)
    next_page: str | None
    note: str            # diagnostic for the indeterminate/skip note

def _hf_tree_get(url, params, headers, *, timeout_s):
    """ONE bounded GET to a Hub tree URL. Returns a _TreeProbeResult.
    - 2xx           -> status='ok',         entries=r.json(), next_page=Link-rel-next
    - 404 not-found -> status='not_found'   (caller decides FAIL vs SKIP)
    - 429/5xx/conn/timeout/anything else -> status='indeterminate' (caller -> skip)
    NEVER enters the SDK http_backoff loop: this is a single requests.get with an
    explicit timeout; we do our OWN bounded retry below."""
    import requests
    from huggingface_hub.utils import get_session
    last = None
    for i in range(_HF_PROBE_ATTEMPTS):
        try:
            r = get_session().get(url, params=params, headers=headers, timeout=timeout_s)
        except Exception as exc:                 # connection / timeout / DNS
            last = exc
            if i + 1 < _HF_PROBE_ATTEMPTS:
                time.sleep(_HF_PROBE_SLEEP_S)
            continue
        if r.status_code == 404:
            return _TreeProbeResult("not_found", [], None, _short_404_note(r))
        if r.status_code == 429 or r.status_code >= 500:
            last = HfHubHTTPError(f"HTTP {r.status_code}", response=r)
            if i + 1 < _HF_PROBE_ATTEMPTS:
                time.sleep(_HF_PROBE_SLEEP_S)
            continue
        try:
            r.raise_for_status()
            entries = r.json()
        except Exception as exc:
            return _TreeProbeResult("indeterminate", [], None, f"HF tree probe failed: {exc}")
        return _TreeProbeResult("ok", entries, _link_rel_next(r), "")
    return _TreeProbeResult("indeterminate", [], None, f"HF tree probe failed: {last}")
</code></pre>
<p>The tree URL is built identically to the SDK: <code>endpoint = huggingface_hub.constants.ENDPOINT</code> (or <code>HfApi().endpoint</code>); <code>url = f"{endpoint}/api/{repo_type}s/{repo_id}/tree/{quote(sha, safe='')}{('/' + quote(path, safe='')) if path else ''}"</code>; <code>headers = build_hf_headers()</code>; <code>params = {"recursive": False}</code> (check 23) or pagination-following (check 25). <code>_link_rel_next(r)</code> reads <code>r.links.get("next", {}).get("url")</code> (requests parses the Link header into <code>r.links</code>, the same mechanism the SDK's <code>_get_next_page</code> uses).</p>

<p class="flag"><b>Direct-child semantics (Risk b mitigation, unchanged from v1's intent but now via the parent listing).</b> A path-pinned URL's terminal component is always a direct child of its parent dir (because <code>_gather_hf_pinned_urls</code> stores the full post-<code>/tree/&lt;sha&gt;/</code> path). Listing the PARENT non-recursively (page 1) contains the needle whether it is a file or a folder. When the parent itself does not exist at the predating revision, the GET 404s → <code>not_found</code> → FAIL (the #537 sub-case). When the parent exists but the needle is not among its children → FAIL. Both #537 sub-cases stay FAIL. <b>Semantic-change note (documented trade-off, per the brief's option-(a) NOTE):</b> the old whole-repo <code>list_repo_files(recursive=True)</code> could have matched a needle nested arbitrarily deep below its stated parent; the parent-listing scheme matches only DIRECT children. This is consistent — a valid pinned link's terminal component IS a direct child of the path it claims, so a "page-1 has no match but parent paginates" case still correctly FAILs (the needle is genuinely not one of its parent's entries). The existing check-23 fixtures all use direct-child paths, so no fixture verdict changes.</p>

    return "fail", ""                              # successful, exhausted, no match -> denial HOLDS (PASS at body level)
</code></pre>
<p class="flag"><b>Check 25's recursion is REAL but SCOPED + CAPPED.</b> The keyword can be nested several levels below the linked tree root (#653), so check 25 genuinely needs recursion — but only within the URL's OWN sub-tree (<code>recursive=True</code> on the path-scoped endpoint), never the whole repo. We follow Link-header pagination ourselves under <code>_HF_PROBE_MAX_PAGES</code> + <code>_HF_PROBE_DEADLINE_S</code>; on the cap we surface <code>skip</code> (<code>unverified</code>) rather than stalling. This eliminates the recursive-whole-repo listing (the actual culprit) AND bounds the scoped one. <b>Verdict mapping (MUST-FIX 3):</b> not-found → <code>skip</code> (NOT fail); a successful-but-no-match → <code>fail</code> sentinel (which the check-25 caller treats as "denial HOLDS for this URL" = body-level PASS, mirroring the existing semantics exactly). Cap-exceeded → <code>skip</code>.</p>

<h3>MUST-FIX 3 — the asymmetry, stated explicitly</h3>
<p>The bounded primitive <code>_hf_tree_get</code> returns a <em>structured outcome</em> (<code>status ∈ {ok, not_found, indeterminate}</code>), it does NOT re-raise an exception for a shared caller to map. The two call sites then map <code>not_found</code> in OPPOSITE directions, exactly as today:</p>
<table>
<tr><th>Call site</th><th><code>not_found</code> (404 / no-such-revision / missing path)</th><th><code>indeterminate</code> (429 / 5xx / conn / timeout / cap)</th><th>successful</th></tr>
<tr><td>check 23 <code>_hf_probe_existence</code></td><td><b>FAIL</b> (dead pin — #537)</td><td>SKIP (<code>unverified</code>)</td><td>PASS if needle present, else FAIL</td></tr>
<tr><td>check 25 <code>_hf_probe_keyword</code></td><td><b>SKIP</b> (indeterminate — cannot corroborate/refute)</td><td>SKIP (<code>unverified</code>)</td><td>PASS-of-probe (keyword found → body FAIL) / FAIL-sentinel (no match → denial holds → body PASS)</td></tr>
</table>
<p>I chose <b>independent per-call-site mapping</b> over a shared <code>on_not_found="fail"|"skip"</code> param: the two sites already differ in their successful-case logic (existence vs keyword search) and their note strings, so a shared mapper would not reduce surface enough to justify the coupling risk the round-1 reviewer flagged. The §6 test (b) pins the check-25 SKIP-on-not-found.</p>

<h3>Why code, not a model call?</h3>
<p>N/A — deterministic HTTP existence probe; a model call is categorically wrong here.</p>

<h3>Rejected alternative — <code>threading.Thread(...).join(timeout=10)</code> around the existing call (non-blocking item, addressed)</h3>
<p>Wrapping the existing <code>list_repo_files</code> in a worker thread with a <code>join(timeout)</code> does NOT cancel the underlying SDK call: <code>join</code> returns but the daemon thread keeps hammering the throttled Hub through all ~143 s of <code>http_backoff</code> retries in the background, ADDING to fleet-wide 429 pressure (the very thing this fix exists to relieve) and leaving a thread per stalled URL. The direct-HTTP approach removes the recursive listing entirely and makes the timeout a real per-request cap, so there is no background work to leak. <b>Rejected.</b></p>

<h3>Per-process cache — do NOT cache SKIP (non-blocking item, addressed)</h3>
<p>The module-level <code>_HF_EXISTENCE_CACHE</code> keyed on <code>(repo_id, repo_type, sha, path_prefix[, keyword])</code> caches <b>only definitive <code>pass</code>/<code>fail</code> verdicts</b>. A <code>skip</code> (indeterminate / throttle) is NEVER cached: caching it within a long-running process (<code>task_workflow_migrate.py:428,:492</code> re-enter <code>verify_text()</code> in one process) could mask a transient throttle that has since cleared, so a SKIP is always re-probed. This is the simplest of the suggested options and removes the only entry that could mask a cleared throttle. Tests clear the cache between cases via an autouse fixture.</p>

<h2>11. Decision Rationale</h2>
<p><b>N/A — no model training.</b> No load-bearing model hyperparameters. The five probe knobs are engineering choices, grounded below:</p>
<ul>
<li><b>What:</b> <code>_HF_PROBE_TIMEOUT_S = 5.0</code>. <b>Why:</b> a single Hub metadata GET resolves in ~0.2 s when un-throttled (#715 observation); 5 s is generous headroom for a slow-but-alive Hub, far under the multi-minute stall. <b>Source:</b> #715 §Bug observed (~0.2 s un-throttled baseline). <b>Alternatives:</b> 10 s (SDK <code>DEFAULT_REQUEST_TIMEOUT</code>) — rejected as twice the needed budget; 2 s — rejected as risking false skips on a slow-but-healthy Hub.</li>
<li><b>What:</b> <code>_HF_PROBE_ATTEMPTS = 2</code> (1 retry per page). <b>Why:</b> one retry absorbs a transient blip without the SDK's 20-deep loop. <b>Source:</b> SDK inspection (<code>_pagination.py</code> <code>max_retries=20</code> is the culprit; §12). <b>Alternatives:</b> 1 (no retry) — too brittle to a single transient; 3+ — creeping back toward the stall.</li>
