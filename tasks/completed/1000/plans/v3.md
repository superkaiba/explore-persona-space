### 0.0 TL;DR (plain English)

- **What I'll change:** I'll make every task-state read a tick turn performs a bounded, jq-filtered digest — for every task, unconditionally — so a tick never pages the task body or full marker notes into its own context (on #906 that's ~625 KB of event-note text per unfiltered `view --json` call). - **What I expect:** tick turns on harmful-content tasks (the #906 class) stop being refusal-killed **by their own state reads** — trigger-dense text structurally never enters via tick-controlled surfaces. Named residuals (§6): the session's accumulated conversation context and the full `/issue` skill's own reads post-re-drive are separate perimeters this fix does not (and cannot) close. Benign tasks lose nothing (the full `/issue` re-drive still does content work in its own steps), and healthy ticks stay one Bash call.
- **What would change my mind:** if the implementer's manual trace finds a tick branch that genuinely needs body/note content to function (I found none — status, marker kind+ts, title, and an ≤80-char blocked reason cover all four branches), the design would need a scoped exception rather than unconditional thinning.

```markdown
## Digest-only task-state reads (every tick turn, every task)

Any task-state read a tick turn makes BEYOND the one `tick_triage.py`
call MUST be a bounded, jq-filtered digest — unconditionally, for every
task, not just visibly harmful-content ones:

- NEVER a bare `task.py view <N>`, and NEVER an unpiped
  `task.py view <N> --json` without a narrow `| jq` filter on the same
  command: the JSON payload carries the full task BODY plus EVERY
  `events.jsonl` note (~625 KB on #906 — 296 events). For a
  harmful-content task (insecure-code datagen, EM vocabulary, jailbreak
  banks) that text is trigger-dense enough to refusal-kill the turn —
  #906's ticks were killed 3× this way (2026-07-03); the #866 prevention
  rule (CLAUDE.md § Spurious usage-policy refusals (e)) applies to tick
  turns exactly as it does to briefs.
- NEVER an unfiltered `task.py latest-marker <N>` when only freshness /
  resume position is needed — its `note` field can be up to 50,000
  chars. Use `... latest-marker <N> | jq '{kind, ts}'`.
- Pipes are the mechanism: `task.py view <N> --json | jq -r '<narrow
  filter>'` is safe by construction — only jq's output enters context;
  the body and notes never do.

Everything a tick turn legitimately needs is digest-shaped: status,
marker kind + timestamp, the title, and the ≤80-char blocked-reason
slice. Deciding per-task whether content is "safe" would itself require
reading the content, so the thinning is unconditional — it also bounds
the tick's context cost on benign tasks (#522 class). This contract
binds the TICK TURN's own reads on all four branches, up to and
including the decision to load the full `/issue` skill; once the full
skill is loaded, its own steps govern its reads — and the refusal-thinned
re-drive rule below additionally constrains the re-driven skill's resume
reads after a refusal-killed predecessor. Content-heavy work belongs to
the full skill's downstream subagents (fresh-context firewalls), never
to a tick turn.
```

### 3.5 Detection mechanism — decision + rejected alternatives

**Chosen: unconditional thinning (no harmful-content detection at all).** The tick never needs content — all four branches are servable from status/kind/ts/title/≤80-char-reason — so conditioning buys nothing and costs a detection mechanism. Rejected:

- **Task tag (`harmful-content`) set at filing/planning time:** no existing convention (verified by grep); every filing surface (task.py new, /daily, campaign children, pods) would need to set it; a tag nobody sets is dead code, and one missed tag = one killed session. Also #906's body was deliberately written "clinical" yet its 625 KB of accumulated marker notes still made the unfiltered read dangerous — content risk accretes in events.jsonl regardless of how the body was filed.
- **Vocabulary heuristic in tick_triage.py:** classifying content requires reading it (self-defeating for the LLM side; on the Python side it adds a fragile keyword list to a pure-verdict script and violates the free-text-free invariant by construction — the match evidence would want to surface in the reason string).

## 11. Decision Rationale

1. **Unconditional digest-only thinning (no detection mechanism).** *Why:* the tick needs only digest-shaped data on every branch; conditioning requires a signal that doesn't exist or a heuristic that must read the content it's guarding against. *Source:* #906 measurement (296 events, 625,256 note chars per unfiltered `view --json`); #866 prevention rule (CLAUDE.md clause (e)); clarifier note that unconditional is "simplest and safest." *Alternatives rejected:* per-task tag (dead-code risk, no convention — grep-verified); vocabulary heuristic (self-defeating, violates the free-text-free triage invariant).
2. **Thinning scope = tick-turn reads only; full `/issue` skill untouched.** *Why:* the full skill legitimately needs content at its own steps (Goal gate, analyzer inputs) behind subagent firewalls; constraining it from the tick skill would risk recovery coverage (backward-compat constraint). *Source:* #522 (context-exhaustion precedent for tick-side thinning), #543 (the reactive layer remains the stricter post-refusal posture). *Alternative rejected:* body-blind full re-drive (would break Step 0c/analyzer flows).
