### 4.1 The canonical sweep block (ONE version; lives in `issue-tick/SKILL.md` § CRON-TEARDOWN)

Replaces the existing python-ish block in `.claude/skills/issue-tick/SKILL.md` § CRON-TEARDOWN. Copy-pasteable; the campaign-tick mirror is this block with `issue`→`campaign` literal substitution (stated inline there).

```python
# CRON-TEARDOWN sweep — hardened 2026-06-12 (#501); widened + idempotent
# 2026-07-05 (#1052). Resolve live ids with a FRESH CronList() HERE, at
# teardown time — never CronDelete an id recorded earlier in the session
# (arm-time asserts, a previous tick's listing): recorded ids go stale when
# a one-shot fires or a concurrent teardown wins the race (#988).
jobs = CronList()  # [{id, cron, prompt, recurring, durable, ...}, ...]
for job in jobs:
    p = job.get("prompt", "").strip()
    # Leg 1 — the recurring tick cron: whole-string equality
    # (prompt.strip() == "/issue-tick <N>"); hardened fallback is the
    # anchored pattern for harness prompt-normalization drift (#501 — the
    # whole-string teardown silently no-oped 1,951 times). The (?!\d)
    # guard prevents sibling mis-delete ("/issue-tick 46" never matches
    # "/issue-tick 467").
    leg1 = p == f"/issue-tick {N}" or re.search(rf"issue-tick\s+{N}(?!\d)", p)
    # Leg 2 — stray one-shot wakeups that would re-drive the FULL skill on
    # a terminal/park task (#980: a live one-shot with prompt '/issue 980'
    # survived teardown on a completed task). Anchored at the START so a
    # prose prompt that merely MENTIONS the issue is never deleted; (?!\d)
    # guards siblings; the '-' in "/issue-tick" fails \s+, so leg 2 never
    # re-matches leg 1's job. Trailing text (e.g. "--auto") matches by
    # design — anything in the store that starts "/issue <N>" is a
    # re-driver for THIS issue and must die at teardown.
    leg2 = p == f"/issue {N}" or re.match(rf"/issue\s+{N}(?!\d)", p)
    if leg1 or leg2:
        CronDelete(id=job["id"])
        # IDEMPOTENT DELETE (#988): a CronDelete error indicating the job
        # does not exist (observed shape: 'No scheduled job with id ...')
        # means it is ALREADY GONE — that IS the desired end state. Treat
        # it as SUCCESS: continue the sweep; never retry the same id,
        # never abort or raise on it.

# ASSERT-AFTER-DELETE: re-CronList() and verify NO job matching EITHER leg
# survived. If one did, retry that delete ONCE (fresh id from the re-list);
# if it STILL survives, log LOUDLY and exit — the runaway parachute
# (tick_triage's 3-consecutive-terminal flag + the watcher force-stop)
# bounds the damage of a job that refuses to die.
```

Note the block deliberately contains the literal fragments the tests pin: `"/issue-tick <N>"` (kept in the surrounding intro prose), `whole-string equality`, `ASSERT-AFTER-DELETE`, `(?!\d)` — and none of the four banned literals (leg-2 equality is written in f-string form `f"/issue {N}"`, never `prompt.strip() == "/issue <N>"`).

## 11. Decision Rationale

Hyperparameters: **N/A — no model training in this task type.** Design decisions:

1. **Two-leg widening inside the ONE existing sweep** (vs a separate one-shot sweep step). Why: every exit site already says "run CRON-TEARDOWN"; widening the match set fixes all ~10 call sites at once with zero new procedure names. Source: #980 incident + the #501 hardened-procedure precedent. Alternatives: a new "WAKEUP-TEARDOWN" step (rejected — doubles the exit-site surface and invites the same drift the #501 fix closed).
2. **Leg-2 match = whole-string equality + start-anchored `re.match(rf"/issue\s+{N}(?!\d)")`** (vs the tick's unanchored `re.search`). Why: an unanchored `issue\s+{N}` would match prose prompts that merely *mention* the issue; the start anchor keeps deletion surgical while still accepting trailing args (`--auto`). The drift class the unanchored tick fallback covers (#501) is addressed at the source for one-shots by the prevention ban. Source: #501 (guard rationale) + #980 (observed prompt shape `/issue 980`). Alternatives: `re.fullmatch` (rejected — misses `--auto`-suffixed wakeups); unanchored (rejected — prose-prompt collateral risk).
3. **Not-found = success as a semantic class, observed string as example.** Why: the exact string is transcript-sourced (Medium confidence) and harness wording can change; the invariant ("job gone == goal") is version-proof. Source: #988. Alternative: exact-string match (rejected — brittle, and a wording change would resurrect the bug).
4. **Fresh `CronList` at teardown, ids never carried from earlier in the session.** Why: this is the root cause of #988 (a stale recorded id); a fresh list also enumerates leg-2 wakeups created at unknown times. Source: #988. Alternative: keep recorded ids + tolerate the error (rejected — tolerating alone leaves leg-2 jobs undiscovered).
5. **Test strategy: keep all existing assertions + add positive pins + fix docstrings** (option i+, § 4.3). Why: nothing is weakened, the deliberate new behavior becomes load-bearing, and the #501-drift guard survives intact. Source: the test file read in full. Alternative: rewrite the banned-literal list (rejected — removes a working guard to permit wording we don't need).
6. **Campaign twins IN scope.** Why: byte-parallel bug pattern; the workflow-fix grep-first rule mandates fixing every uniform hit (#622: the one-of-25-files incomplete fix). Source: `.claude/rules/workflow-fix-on-bug.md`; files opened and confirmed. Alternative: issue-only (rejected — leaves a known identical gap to be re-filed later).
7. **Prevention ban + self-heal leg for the unverifiable enumeration case.** Why: Assumption 2 is Low-confidence; a sweep alone cannot be proven sufficient, so the source is banned (`ScheduleWakeup` self-re-drive) and every terminal-state invocation self-heals. Source: #980 (the escaped wakeup only failed safe by luck). Alternative: sweep-only (rejected — rests entirely on an unverified harness fact).
8. **One canonical pseudocode block in `issue-tick/SKILL.md`; `issue/SKILL.md` keeps prose + pointer; `campaign-tick` carries the stated literal-substituted mirror.** Why: matches today's layout (the block already lives in the tick skill), keeps the diff minimal, and avoids two divergent "canonical" blocks in the issue family. Alternative: duplicate the block into `issue/SKILL.md` Step 6d.2 (rejected — the #501 history shows duplicated match logic is exactly what drifts).
