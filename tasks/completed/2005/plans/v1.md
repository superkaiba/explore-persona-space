# Plan v1: Step 9c gate — detached first attempt + explicit end-the-turn

`workflow_fix_target: .claude/skills/issue/SKILL.md`

## 0. TL;DR (change-my-mind line)

The SKILL.md's "BACKGROUND IS REQUIRED, NOT OPTIONAL" mandate at Step 9c
step 1b (and its clones at 1c full-scope, 1d compare, and both Step 10d
gate blocks) is falsified by measured evidence: the bg-Bash tool cap
harness-kills the shell at ~10 min BEFORE `; echo $? > rc-file` runs,
producing the "exit 144, rc file missing" signature (#1893's ~26-min /
~95% kill). And the missing explicit end-the-turn contract lets a
session drop into `TaskOutput(block=true, timeout=600000) × 3` — the
banned sleep-chain shape that held #1984's turn ~31 min. This plan
replaces bg-Bash-inline with the DETACHED launcher shape already
canonicalized at § Detached VM-side long compute phases (line 7043), and
adds explicit end-the-turn language naming the Monitor-until-probe
sanctioned wait. Change-my-mind: if the bg-Bash tool cap is actually
higher for `run_in_background=true` calls, or if there is a runtime
switch the SKILL.md relies on that I missed, the entire premise fails.

## 1. Goal + hypothesis

**Goal.** Rewrite the launch recipes at SKILL.md Step 9c step 1b / 1c /
1d and both Step 10d gate blocks so that a first-attempt gate run whose
projected wall exceeds the 600s bg-Bash tool cap (i.e., the selection
contains the workflow-invariant set — the always-present case for the
Step 9c gate) launches DETACHED via setsid + pid/log/rc-file breadcrumbs
(the same shape as § Detached VM-side long compute phases). Add explicit
"END THE TURN" language at each launch site naming the sanctioned wait
patterns (Monitor until-loop over the single-flight probe; the
`/issue-tick` cron re-wake) and banning repeated
`TaskOutput(block=true, timeout=600000)` polls as the sleep-chain shape.

**Hypothesis.** With the detached launcher, the bg-Bash tool cap can
never kill the pytest process (it lives in its own session leader), so
the "exit 144, rc file missing" class becomes structurally impossible.
And with an explicit end-the-turn line at each launch site, the
banned-sleep-chain shape (`TaskOutput(block=true)` × 3) becomes a
clearly-prohibited pattern instead of an implicit inference from
"harness notifies".

**Falsification.** If a subsequent gate run STILL dies at the ~10-min
mark with rc-file missing under the new shape, the setsid decoupling
didn't take effect — the fix engaged the code but not the underlying
runtime constraint. Or if the harness enforces a runtime cap on ANY
child process regardless of session id (unlikely on Linux; setsid moves
the process out of the launcher's session), the fix fails.

**Replace the executable block (lines 10056-10086)** — same
preamble (cd hard-guard, choom, TMPDIR routing, rm -f, single-flight
probe, gate-fleet arbitration) precedes the launcher. Replace the
inline `timeout ... pytest ... > log ; echo $? > rc` with:

```bash
# ... (cd hard-guard, single-flight probe, gate-fleet arbitration,
#      choom self-preamble, TMPDIR routing, rm -f — UNCHANGED) ...

# Persist BASETEMP path for the completion-read to reap (S9C_BASETEMP
# is a shell var local to this bg-Bash call; the completion-read runs
# in a separate call, so we save the path where it can find it):
[ -n "${S9C_BASETEMP:-}" ] && echo "$S9C_BASETEMP" > /tmp/step9c-basetemp-issue-<N>.path

# DETACHED launcher — setsid execs in place inside the bash -c wrapper
# (job control OFF), so $! is the workload pid. The pytest command
# runs in its own session, decoupled from the launcher bg-Bash's kill
# domain (the harness's 10-min tool cap kills the launcher shell but
# cannot reach the pytest session leader). The rc file is written by
# the detached process at its OWN exit, so a launcher-kill leaves
# no rc file and the completion-read fails CLOSED (kill-before-relaunch).
PYTEST_PID=$(bash -c "setsid nohup timeout --kill-after=60s <T>s \
  env OMP_NUM_THREADS=8 MKL_NUM_THREADS=8 OPENBLAS_NUM_THREADS=8 NUMEXPR_NUM_THREADS=8 MALLOC_ARENA_MAX=2 \
  uv run pytest <files> --continue-on-collection-errors -v --tb=short \
  --junitxml=/tmp/step9c-junit-issue-<N>.xml -o junit_family=xunit1 \
  ${S9C_BASETEMP:+--basetemp=$S9C_BASETEMP/p} \
  < /dev/null > /tmp/step9c-pytest-issue-<N>.log 2>&1 ; echo \$? > /tmp/step9c-rc-issue-<N> \
  & echo \$!")

# Identity verify (bracketed pgrep on mismatch — the standard § Detached
# VM-side long compute phases identity check):
ps -p "$PYTEST_PID" -o args= | head -1
# earlyoom-protect via session-wide choom (children inherit; the FAIL-OPEN
# preamble already ran, and § Detached carries a bounded-retry loop that
# does not apply to a pytest launcher whose real python3 child is spawned
# immediately by uv run):
bash -o pipefail -c 'pgrep -s "$1" | xargs -rn1 sudo -n choom -n -600 -p' _ "$PYTEST_PID" >/dev/null \
  && GATE_CHOOM=ok \
  || { GATE_CHOOM=failed; echo "[warn] session choom failed — gate detached pytest is earlyoom-UNPROTECTED (choom=failed)" >&2; }

# Detached breadcrumb — the same shape as § Detached VM-side long compute
# phases (pid + log + rc/harvest + choom):
echo "[step9c] gate detached pid=$PYTEST_PID log=/tmp/step9c-pytest-issue-<N>.log rc=/tmp/step9c-rc-issue-<N> choom=$GATE_CHOOM"
```

## 8. Concerns / assumptions

- **Assumption (verified via SKILL.md line 9967):** the bg-Bash tool
  cap is 600 000 ms (10 min). Verified: the Bash tool description
  states "You may specify an optional timeout in milliseconds (up to
  600000ms / 10 minutes)" and this applies to `run_in_background=true`
  too. #1893's exit 144 + rc missing is the empirical signature of
  this cap firing.
- **Assumption:** `setsid` on Linux moves the child process into a new
  session, so signals sent to the launcher's session group do not
  reach the child. Verified via § Detached VM-side long compute
  phases which already relies on this behavior.
- **Concern:** the `S9C_BASETEMP` persistence via `/tmp/step9c-basetemp-issue-<N>.path`
  adds one small file per gate run. It's cleaned up in the completion-read.
  A crashed launcher (dead before writing the persistence file) leaves
  the BASETEMP dir uncleaned; low harm (a mktemp dir, few KB, /tmp
  clears on reboot).
- **Concern:** the executable block's shell quoting is subtle. The
  `bash -c "...$!..."` needs `\$!` to defer expansion. The
  implementer will refine.
