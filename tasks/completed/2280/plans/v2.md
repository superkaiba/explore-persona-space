## 2. Root cause (established, with evidence)

`earlyoom` (active systemd unit, `EnvironmentFile=/etc/default/earlyoom`) runs with:

```
EARLYOOM_ARGS="-m 10 -s 10 -r 3600 --prefer (^|/)(pytest|python3?)$ \
  --avoid (^|/)(sshd|systemd|dockerd|node|claude|happy)$|^[0-9]+[.][0-9]+[.][0-9]+$ -n"
```

**2.1 Timestamp match.** VM tz = `America/Los_Angeles` (PDT, UTC-7). The body reports
`issue2221_build_mix.py` attempt 1 died rc=143 at 16:24:40Z. The earlyoom unit journal,
at `Aug 13 09:24:40` PDT — the same second:

```
mem avail: 12849 of 128804 MiB ( 9.98%), swap free: 0 of 0 MiB ( 0.00%)
low memory! at or below SIGTERM limits: mem 10.00%, swap 10.00%
sending SIGTERM to process 1838073 uid 1001 "python3": badness 972, VmRSS 1054 MiB
process exited after 0.1 seconds
```

The body's second window (two `file_infra_task.py` kills ~00:42-44Z on 08-14 =
17:42-44 PDT on 08-13) matches a sustained sweep: `"python"` badness 973 (1395 MiB),
`"python3"` 966 (53 MiB), 966 (48 MiB), and a `chrome` 800 — all SIGTERM inside 11 s,
MemAvailable oscillating 9.47-10.00%, swap `0 of 0 MiB`.

**2.2 Selection mechanism — the +300 bonus IS effectively the whole criterion.**
From the installed daemon's source (earlyoom v1.6.2, Debian `1.6.2-1`, a plain upstream
repack — `changelog.Debian.gz` records only "New upstream release", no patches), the
victim loop in `kill.c` computes:

```c
cur.badness = get_oom_score(cur.pid);                 // the KERNEL /proc/<pid>/oom_score
if (prefer_regex matches cur.name) cur.badness += BADNESS_PREFER;   // +300
if (avoid_regex  matches cur.name) cur.badness += BADNESS_AVOID;    // -300
```

Measured on this box: **every** process reports `oom_score = 666` with
`oom_score_adj = 0` — the Bash tool-call shell, the `claude` binary, both `node`
parents, `systemd --user`, and a fresh `python3` alike. Because that baseline is flat,
the +300 dominates ranking outright. Journal badness values confirm it: any python
scores 966-976 regardless of size, beating a 3728 MiB `java` (686) and a 660 MiB Claude
session (669-670).

**Consequence, stated nowhere in-repo today:** RSS is nearly irrelevant *across* process
classes. A 44 MiB, sub-second python is a top-priority victim the instant a sweep
fires — which is exactly why `file_infra_task.py --help` dying "within seconds" read as
inexplicable. Size only breaks ties *within* the python class.

**2.3 The `setsid` discriminator is a TIMING CONFOUND, not a mechanism.** Measured this
session, same interpreter via both launch shapes:

```
in-session:      comm=python3 adj=0 score=666 pid=2535902 sid=2535874 pgid=2535897
setsid-detached: comm=python3 adj=0 score=666 pid=2535908 sid=2535904 pgid=2535904
```

Identical `comm`, `adj`, and `oom_score`; only `sid`/`pgid` differ — and earlyoom reads
none of those (it matches on `comm` and ranks on `oom_score`). No harness-set
`oom_score_adj` exists anywhere in the ancestry (bash → claude → node → node →
`systemd --user`, all 0). Corroborating: the same sweeps killed `chrome`, `java`, and
the `2.1.219` Claude binaries — none of which are foreground python children of a
session shell. earlyoom fires in *bursts* at the floor, so a rerun seconds-to-minutes
later simply lands outside the sweep and survives.

**All three suspects the task body named are ruled out:** harness child-reaping at
tool-call boundaries, a janitor `pkill` on argv patterns, systemd session-scope cleanup.

**2.4 Why the body's own checks missed it (three traps).**
(a) "journalctl clean" — the kernel OOM killer logs to dmesg with `oom_score`; earlyoom
logs to its own *unit* journal with `badness`. A dmesg / `journalctl -k` read
structurally cannot see an earlyoom kill.
(b) "53 GB free" is DISK; the binding quantities were MemAvailable at 9.5-10.0% of
128 GB (~12.2-12.9 GB) **and** swap free at 0 of 0 MiB — the kill condition is
CONJUNCTIVE (`mem <= 10% AND swap <= 10%`).
(c) The `setsid` A/B (§2.3).

**2.5 Why it stopped.** A 64 GB swapfile was created 2026-08-14 08:29:08 PDT
(`/mnt/eps-data/swapfile`); earlyoom restarted 8 s later (pid 3342453). The last real
victim kill is `Aug 14 08:16:07` — 13 minutes *before* the swapfile. Victim-kill counts
inside the journal's retention window (which begins `Aug 13 02:52:17`, so earlier days
are **unknown, not zero**): **363 on Aug 13, 287 on Aug 14, then 0 through Aug 22.**
The swap is durable — `/etc/fstab` line 4
(`/mnt/eps-data/swapfile none swap sw,nofail 0 0`) plus an active
`mnt-eps\x2ddata-swapfile.swap` systemd unit.

**2.6 `choom -n -600` REMAINS PROTECTIVE for python — attenuated, not void.**
(v1 asserted the opposite; that claim was wrong and is retracted here.) `man earlyoom`
states: *"For processes matched by `--prefer`, negative `oom_score_adj` values are not
taken into account, and the process gets an effective oom_score of at least 300"*
(upstream issue 159). **The man page overstates.** The installed v1.6.2 source (§2.2)
initializes badness from the kernel `oom_score`, which *does* reflect a negative adj;
the only `oom_score_adj` handling is gated on `args->ignore_oom_score_adj` (the `-i`
flag, **not** set in this VM's `EARLYOOM_ARGS`) and subtracts POSITIVE adj only. No code
path discards a negative adj for prefer-matched processes. The man clause describes the
`adj = -1000` extreme, where the kernel clamps `oom_score` to 0 and the +300 is all
that remains.

Arithmetic for this VM, with the measured operating point:

| process | kernel `oom_score` | +prefer | badness | rank vs the ~666 crowd |
|---|---|---|---|---|
| python, unchoomed | 666 | +300 | **966** | always first victim |
| python, `choom -n -600` | 267 *(measured)* | +300 | **567** | ~99 **below** the crowd |
| any unmatched process | ~666 | — | ~666-686 | the crowd |

So `choom -n -600` moves a python from always-first-victim to below every unmatched
process on the box. Weak-form corroboration: across all 650 logged victim kills the
badness distribution bottoms out at 669 — no victim was ever selected below the
unmatched baseline (this cannot distinguish "choomed processes were protected" from "no
choomed process was present"; the source read is the load-bearing evidence).

**The in-repo choom prescriptions are therefore SOUND and get no correction** — gotchas
line 60, SKILL.md § "Detached VM-side long compute phases", and the Step 9c pytest
self-choom (#1045) all stay as written. What the docs need instead is a warning that the
man-page wording overstates, so a future reader does not "fix" a working recipe out of
the repo on the strength of that sentence.

**2.7 Residual regression paths — TWO, not one.** earlyoom remains armed with the same
blanket python `--prefer`, and the kill condition is conjunctive, so the Aug-13 regime
returns whenever MemAvailable **and** swap both fall under 10%:
- **(a) `nofail` silent no-swap boot.** The fstab entry carries `nofail`, so a boot where
  `/mnt/eps-data` fails to mount activates **no swap, silently** — restoring the exact
  Aug-13 conditions with no alarm.
- **(b) swap exhaustion.** The swapfile is already ~54% consumed 8 days in (34.9 of
  64 GB). Sustained fleet growth reaches the swap floor with no `nofail` event at all —
  a `SwapTotal == 0` check is structurally blind to this path.

Nothing in the repo reads swap state today (verified: no `swapon` / `SwapTotal` /
`swap_memory` reader under `scripts/` or `src/`).

## 7. Kill criteria

- If the installed daemon's source does NOT match §2.2/§2.6 (badness initialized from
  the kernel `oom_score`; negative-adj discard gated on `-i`), then §2.6's attenuation
  claim is wrong and D1 item 3 must be re-derived. The check is **man-clause-vs-installed-
  source agreement**, not the man clause's existence — v1's kill criterion made exactly
  that mistake and passed while the claim was inverted.
- If any victim kill exists after `Aug 14 08:16:07`, §2.5's "already stopped" claim is
  wrong and the task re-opens with the (user-gated) config proposal back in scope.
- Out of bounds, permanently: inducing memory pressure to reproduce a kill. On a box with
  26 live sessions that would SIGTERM other sessions' live work. The diagnosis rests on
  observational journal evidence, read-only `/proc` probes, and a source read; §2.6's
  earlyoom-side behavior stays source-grounded rather than kill-observed, and says so.
- Not in scope: editing `/etc/default/earlyoom`, adding/removing swap. Sudo-level,
  fleet-wide, outside-the-worktree mutations (halt-criterion #2), and §2.5 makes them
  unnecessary. If review disagrees, it becomes a PROPOSAL with an exact before/after diff
  parked for the user — never applied by this session.
