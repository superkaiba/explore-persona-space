- **What would change my mind:** if the new check ever fails a venv that is actually healthy (I can force it off instantly with one environment variable), or if the trial import turns out to take multiples of my measured ~22–54 s on real pods, I'd shrink it to the metadata-only check and rethink the import leg.

4. For each dist in `LOAD_BEARING_DISTS`, resolve metadata and classify — BOTH broken shapes route to the SAME failure path:
   ```python
   try:
       ver = importlib.metadata.version(dist)
       broken = "metadata file missing from present dist-info" if ver is None else None
   except importlib.metadata.PackageNotFoundError:
       broken = "dist metadata entirely absent"
   ```

Plan-v1 handled only the raising shape and would have PASSED the `None` shape — the fact-check's R1 hole, closed here. (Measured cost: 0.137 s for all 13 resolutions; py3.11 importlib.metadata name-normalizes — verified `version("Huggingface_Hub") == version("huggingface-hub")`.) On `broken is not None`:
   - dist in `locked` (or `locked is None`) → `report.add_error(...)` naming the dist, the broken shape string, the incident framing ("half-installed venv, the #2360 pod-2329-margin failure"), and the sanctioned repair `UV_LINK_MODE=copy uv pip install --force-reinstall <dist>` with the explicit caveat that `uv sync` would revert deliberate off-lock pins (the body's repair note).
   - dist NOT in `locked` → `add_warning("'<dist>' not lock-pinned and not installed/resolvable — skipped (curated list may be stale)")`. This is the Q4 legitimate-absence path: if a package is ever dropped from the project deps, the check degrades to a warning, never a false FAIL.
   - Deliberately NO version-vs-lock equality check: the sanctioned `EPM_PREFLIGHT_ALLOW_TRANSFORMERS5` flow implies deliberately off-lock pins (transformers 5.15.0 on pod-2329-margin); resolvability is the invariant, version drift is `check_env_sync`'s jurisdiction.

Tier 1 executes no module code — it reads dist-info off site-packages. It cannot hang any harder than the preflight process already does (preflight itself runs FROM the same venv; `.env`, git and disk probes already touch the same mount), so it adds no new wedge-exposure class, and it catches the exact incident (sympy: partial tree on disk, `PackageNotFoundError` on metadata) plus the adjacent gutted-dist-info shape.

### D2 — Tier 2: bounded subprocess deep-import probe (RunPod default-on; VM/GCE opt-in)

Continuing in `check_venv_import_health` after tier 1:

1. Lane gate: run iff `EPM_PREFLIGHT_IMPORT_PROBE` in `{"1","true","yes"}`, OR (unset/other AND `is_runpod_env()`). `"0"/"false"/"no"` forces off. Not run → verdict `"skipped-lane"`, return silently (no warning spam on every VM launch).
2. Pre-probe stderr banner (load-bearing — see D3): immediately BEFORE launching the probe, `print("[preflight] deep-import probe launching (timeout <N>s) — if this is the last preflight output for far longer than the timeout, the /workspace mount is likely hard-wedged (gotchas.md § MooseFS FUSE read-wedge)", file=sys.stderr, flush=True)`.
3. Probe: `_run([sys.executable, "-c", _IMPORT_PROBE_SNIPPET, *DEEP_IMPORT_MODULES], timeout=int(timeout_s))` where `timeout_s = float(os.environ.get("EPM_PREFLIGHT_IMPORT_PROBE_TIMEOUT_S", "180"))`. `sys.executable` is the venv python under every sanctioned invocation (`uv run python -m ...`, the `/usr/local/bin/python` shim which execs `.venv/bin/python`); deliberately NOT `uv run` — a nested `uv run` can trigger an implicit sync and re-enter the #2278 shim/lock deadlock class, and it would re-resolve the env rather than test the venv as-is. Snippet (module-level constant):

```python
_IMPORT_PROBE_SNIPPET = (
    "import importlib, sys, traceback\n"
    "for m in sys.argv[1:]:\n"
    "    try:\n"
    "        importlib.import_module(m)\n"
    "        print('OK ' + m, flush=True)\n"
    "    except BaseException:\n"
    "        print('FAIL ' + m, flush=True)\n"
    "        traceback.print_exc()\n"
    "        sys.exit(3)\n"
)
```

4. Verdicts:
   - `rc == 0` → verdict `"ok"`.
   - `rc == -1 and err == "timeout"` (the `_run` TimeoutExpired contract, preflight.py:178-179) → verdict `"timeout"`, `add_error` AND an immediate `print(..., file=sys.stderr, flush=True)` (rationale in D3). Error text names BOTH readings and the discriminator: "deep-import probe timed out after Ns — either a slow cold MooseFS venv read (raise EPM_PREFLIGHT_IMPORT_PROBE_TIMEOUT_S) or the MooseFS FUSE read-wedge (gotchas.md § MooseFS FUSE READ-wedge: spot reads on /workspace also hang under the wedge — run the discriminator before relaunching; kill+swap-pod per the runbook, never loop relaunches)".
   - any other nonzero → verdict `"fail"`, `add_error` carrying: the failing module (last `FAIL <m>` line of stdout) + the LEAF traceback via a **head+tail stderr harvest** — first 4,000 chars + `... [<N> chars elided] ...` + last 4,000 chars whenever total stderr exceeds 8,192 chars, else the whole stderr. Why head+tail, not tail-only (plan-v1's shape, corrected per fact-check R2c): Python prints a chained exception's CAUSE — the leaf — FIRST, then "The above exception was the direct cause...", then each re-wrap; a tail-only window therefore drops the leaf on exactly the deep re-wrap chains where it matters most. The one measured real failure produced 4,796 chars of stderr (fact-check, transformers 4.57.6 + broken-sympy shadow) — it fits WHOLE in the 8,192 window; deeper chains keep the leaf (printed first) in the head and the final wrapper + `FAIL` context in the tail. An ~8 KB error string in the JSON report is harmless next to a silently dropped leaf (the whole acceptance criterion is "the leaf error is surfaced").
5. **Leaf-error guarantee, stated precisely (corrects plan-v1's false claim):** because the probe imports `torch._dynamo` and `transformers.models.auto.modeling_auto` as leaf modules via `importlib.import_module`, the TRUE chain (`... torch.fx.experimental.symbolic_shapes → import sympy → ModuleNotFoundError: No module named 'sympy.utilities'`) is ALWAYS present in stderr. It is NOT true that the lazy-wrapper text can never appear on a direct submodule import: measured live (fact-check, transformers 4.57.6), `modeling_auto`'s own body does `from ...generation import GenerationMixin`, and `transformers.generation` is itself a `_LazyModule` (`import_utils.py:2320-2330`), so a direct `importlib.import_module("transformers.models.auto.modeling_auto")` still emits `Could not import module 'GenerationMixin'` — with the true leaf chain attached as the chained CAUSE printed above it. The Q5 guarantee ("leaf surfaced") therefore rests on two mechanisms, not on wrapper-suppression: (a) the probe imports `sympy` and `torch._dynamo` BEFORE `modeling_auto`, so the incident class fails at a pure-leaf module with no lazy machinery at all; (b) even at the `modeling_auto` stage, the leaf chain is preserved as the printed-first cause, and the head+tail harvest keeps it.
6. New `PreflightReport` field: `venv_import_verdict: str = ""` (values `""|ok|fail|timeout|skipped-cluster|skipped-lane|disabled`), added to the `main()` `--json` dict (after `env_synced`, preflight.py:1879) so dispatchers can read it.

**Module set rationale (Q4):** the deep set is the demonstrated kill chain plus its two cheap sentinels (`numpy`, `sympy` — `sympy` named explicitly so the incident class fails on its own name even if torch restructures `_dynamo`). `vllm` is deliberately NOT in the deep set: (a) `check_vllm_transformers_compat` already `import vllm`s in-process at every preflight, so vllm import breakage still surfaces (as its WARN — unchanged severity, out of scope to harden here); (b) a cold vllm import adds ~20-40 s for a package whose failures are loud at engine init; (c) vllm gets a tier-1 metadata row, which catches the half-install shape. `flash-attn` is excluded entirely — bootstrap installs it OUTSIDE the lock, intent-conditionally (#2278; bootstrap_pod.sh:418-432), so both tiers would false-positive on eval/cpu intents.

### D3 — The flagged wedge consideration (explicit decision)

Decision: **the import leg is subprocess-isolated with a wall-clock bound (180 s default), a DISTINCT `timeout` verdict separate from `fail`, and a metadata-only tier 1 that runs first and is wedge-inert; on `timeout`, the compat check's unbounded in-process imports are skipped.** Reasons:

- An in-process import cannot be bounded; a subprocess can (`_run`'s `subprocess.run(timeout=...)` kills the child on expiry — no orphan probe process in the ordinary case).
- Preflight TODAY already hangs unboundedly on a wedged mount at `check_vllm_transformers_compat`'s in-process `import transformers; import vllm` (preflight.py:1306-1308). Ordering the new bounded probe BEFORE the compat check (insertion point: preflight.py:1769, between `check_env_vars` and `check_vllm_transformers_compat`) converts that silent hang into a bounded, named verdict — and a 3-line guard at the top of `check_vllm_transformers_compat` (`if report.venv_import_verdict == "timeout": add_warning(...skipped — bounded probe timed out, an in-process import here could hang preflight...); return`) prevents the subsequent unbounded import from re-introducing the hang. Existing `tests/test_preflight_vllm_compat.py` tests construct fresh `PreflightReport`s (default `""`) so they are unaffected.
- The `timeout` verdict's error text distinguishes hung-vs-ImportError (Q: "distinct verdict for hung vs ImportError" — yes: `timeout` vs `fail`) and cites the gotchas discriminator rather than asserting "wedge" (the #2333 SLOW-CANARY precedent: a grinding-but-answering mount is not a wedge; the mount can also just be slow-cold).
- **Documented residual (fact-check R5), ACCEPTED:** the probe is bounded only while the mount still delivers signals. `subprocess.run(timeout=...)` does `process.kill(); process.wait()` then re-raises (verified CPython 3.11.15; a live test showed the child dead 0.3 s after a 2 s timeout) — but on a HARD-wedged FUSE mount, a child stuck in uninterruptible I/O (D-state) can survive SIGKILL until the I/O returns, and the post-kill `wait()` then blocks preflight despite the timeout. I accept this residual: the status quo hangs unboundedly with NO diagnostic at all, while the probe hangs only on a hard-wedged mount AND names itself first — because the post-timeout diagnostic print sits AFTER `_run` returns, it would never execute in the SIGKILL-survival case, which is exactly why D2 step 2's pre-probe stderr banner exists: it is printed BEFORE the wait can block, so the operator's last preflight output names the probe + the wedge runbook in both the bounded-timeout case (banner, then the timeout error) and the hard-wedge case (banner is the final line). No fixture can certify the SIGKILL-survival path (a sleeping test child dies to SIGKILL as designed) — this residual is documented, not tested (see Smoke blind-spot enumeration).
- The immediate stderr print on timeout exists because `report.summary()` prints only at the END of `preflight_check` — if any LATER check were to hang on the same wedged mount (residual: `check_connectivity`'s `python3 -c` subprocesses have their own `_run` timeouts; `check_hf_*` are network-bounded; residual exposure is small but nonzero, e.g. a wedged read inside `check_hf_home`), the operator still sees the diagnostic.
- Timeout default 180 s: the sanctioned wedge discriminator uses 60 s for `import transformers` alone; the probe chain is ~3-4× that scope. Measured on the (contended) shared VM: 51 s cold / 22 s warm for the full chain. 180 s ≈ 3.5× the measured cold wall — and env-tunable per-launch. Source: measured 2026-08-17, this plan §9.
