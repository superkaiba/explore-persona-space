### Edit 1 (the deliverable): new top-level bullet, inserted after the L60 entry, before the L61 wandb-core entry

Near-final text (implementer refines wording only, not content; house style: bold lede → mechanism → diagnostic signature → RULE → reference impl → incident tail):

> - **Container pid namespaces make NVML compute-app pids UNMATCHABLE in the container's `/proc` — an in-process "is this GPU pid dead?" check misreads a LIVE orphaned `VLLM::EngineCore` as a dead-pid zombie (the false-NEGATIVE twin of the self-exclusion entry above), and the orphan squats tens of GiB until a later unit OOMs.** Same mechanism as the entry above (NVML reports HOST-namespace pids; NVIDIA/nvidia-docker#1483): the container's `/proc` holds only CONTAINER pids, so `/proc/<nvml-pid>` never exists and a teardown/monitor scan that keys liveness off it concludes "dead pid, driver will release soon" for a process that is alive and holding the model's HBM. Diagnostic signature: the scan repeatedly WARNs the SAME NVML pid as a dead-pid zombie while its `used_memory` never drains, and a later co-resident unit dies at engine/model init (`Free memory ... less than desired gpu_memory_utilization`, or an HF-load OOM). The cmdline-anchored recovery `pgrep -af '^VLLM::EngineCore'` (crash-orphan entry above) still works in-container — the orphan is a container process, visible in `/proc` under its CONTAINER pid; only the NVML-pid↔`/proc` correlation is impossible. RULE — reap by RELATIONSHIP, verdict by VRAM TOTALS, never by NVML-pid identity: (1) at engine teardown, graceful v1 `engine_core.shutdown()` (`_reap_vllm_engine`) THEN sweep surviving engine-worker CHILDREN by container pid — `psutil.Process().children(recursive=True)` filtered by a NARROW engine-child predicate (never wandb-core, entry below) — with terminate → `wait_procs` → kill, VERIFYING death; (2) at unit exit, `os.killpg(unit_pid, ...)` — a reparented-to-init orphan escapes a `children()` sweep but KEEPS the unit's pgid (`start_new_session=True` ⇒ pgid == unit pid), so killpg is the only container-side handle on it (`ProcessLookupError` = group already gone, the healthy no-op); (3) cleanliness VERDICTS (post-reap re-verify + a per-unit GPU PREFLIGHT before any engine/model load) are bounded NVML drain-waits on per-GPU `used_memory` TOTALS vs a residual floor — pid-attribution-free, `[N/A]` counts ABOVE-floor, fail LOUD naming the holder on timeout — and they run at PROCESS BOUNDARIES (a fresh unit's preflight reads clean by construction; a phase gate reads post-`empty_cache`), NEVER in-unit while the process legitimately co-holds an HF model (measured false-positive: the unit's own 15,260 MiB base model tripped a 6144 MiB floor — the r7b lesson). Reference implementation: `scripts/issue1333_dispatch.py` — `_reap_engine` (shutdown + verified child sweep), `_reap_completed_unit_group` (unit-exit killpg), `_gpu_hygiene` + `_wait_gpus_free` (phase-boundary drain verdict; floors `EPM_GPU_HYGIENE_FLOOR_MIB` / `EPM_UNIT_PREFLIGHT_FLOOR_MIB` default 2048 MiB — re-derive for models whose weights approach it — timeout `EPM_*_TIMEOUT_S` default 180 s), `_unit_gpu_preflight`; a later `_wait_engine_release` adds the post-reap drain-wait at engine-cycling seams (callable ONLY after HF references are dropped/rebound, else it times out on the caller's own weights).
