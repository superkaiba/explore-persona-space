# Plan — Wire the ASYNC GCP-workload-failure → RunPod failover (poller / dispatch path)

## TDD: yes

The acceptance criterion IS a specific failing test ("a poller-surfaced GCP
`workload_failure` results in exactly one RunPod re-dispatch, then `blocked`
on a re-crash"). The cleanest path is write-the-test-first → it fails → write
the wiring → it passes. This satisfies the implementer's conditional gate at
`/issue` Step 4b: the implementer posts `epm:proposed-tests v1` with the test
names + assertion shapes below, EXITs awaiting `epm:approve-tests v1`, then
implements.

## 1. Goal

When the async poller (`scripts/backend_poll.py`, driven each tick by the
orchestrator's Step 6d.2 bg-Bash loop) observes that a **GCP** run died of a
**workload** failure (a non-capacity, non-infra crash detected minutes into the
run on an already-up VM), re-dispatch that run on **RunPod exactly once** —
reusing the same RunPod terminal rung the synchronous `route()`-time failover
already uses — instead of ending at `status:blocked`. This completes the
user directive "if GCP is failing, run it on RunPod while we fix GCP" for the
COMMON (async-detected) failure path; today only the rare synchronous
`route()`-time path fails over.

  is the structural bound.

So the distinguishing async signal already exists: `current_phase ==
"terminal_workload_failed"` on a `backend == "gcp"` handle. No new GCP-side
poll signal is needed.

## 3. Method delta — WHERE the failover fires

**Chosen layer: `scripts/backend_poll.py` `main()`** (the poller-side seam),
calling a NEW thin public router helper `failover_to_runpod_after_async_workload_crash(...)`
that wraps `_runpod_terminal_rung` with production deps (mirroring how
`issue_dispatch.dispatch_for_issue` wraps `route()`).

Why this layer and not the alternatives:

- **`backend_poll.py main()` is the ONLY process that observes the async
  terminal signal AND holds the live handle.** It already deserializes the
  `RunHandle` (so it knows `handle.backend == "gcp"`), calls `backend.poll()`
  (so it sees `current_phase == "terminal_workload_failed"`), and knows the
  issue number — every input the failover needs is local. It already owns the
  handle-sidecar contract (it READS the sidecar each tick), so re-pointing the
  sidecar at the new RunPod handle is a natural extension of its existing
  responsibility. And it is a normal Python `main()` directly callable by
  pytest (`backend_poll_main([...])`, already done in
  `test_issue_dispatch.py:1155`), so the acceptance test is clean.

- **Rejected — the orchestrator's Step 6d.2 poll loop (SKILL.md markdown).**
  The loop is prose executed by the LM, not Python. A failover encoded there is
  un-unit-testable (the acceptance criterion demands a pytest), and re-running
  the router from LM-orchestrated steps is exactly the brittle pattern slice-6
  centralized into `dispatch_for_issue`. The orchestrator should keep treating
  the poller's JSON as the source of truth; the failover decision belongs below
  it, in Python.

- **Rejected — `issue_dispatch.dispatch_for_issue`.** That helper runs ONCE at
  launch (Step 6b) and returns; it is not in the poll path and has no view of
  the async death. Putting the failover there would require it to also become a
  poll consumer — a larger, wrong-shaped change. (It IS the right model to
  imitate — the new router helper mirrors its "build prod deps + call the launch
  primitive" structure — but the call site is the poller.)

The new router helper exists because `_runpod_terminal_rung` is too low-level to
call from the poller directly: its signature requires injected `store`,
`attempts`, `started_at`, `now_fn`, `marker_poster`, `on_launched`. The helper
builds the production-shaped versions of those (real `LeaseStore`, real
`post_marker_via_task_py`, real RunPod backend, a fresh `attempts` list, an
`on_launched` that rewrites the sidecar) and calls `_runpod_terminal_rung` with
`reason=ROUTE_REASON_GCP_WORKLOAD_FAILOVER_RUNPOD`. This keeps `backend_poll.py`
thin and keeps all router/lease/marker mechanics inside the router module where
the sync path's tests already live.

**Pod-side-shellout safety:** `backend_poll.py` runs on the VM (it is the
orchestrator's bg-Bash process, NOT pod-side code) — it already imports
`issue_dispatch` and resolves backends, so importing the router + posting via
`post_marker_via_task_py` is consistent with its existing role and does not
violate the "pods never shell out to task.py" rule.

### 4.1 New router helper — `backends/router.py`

Add a module-level PUBLIC function near `_runpod_terminal_rung` (router.py,
after line 1993) and export it in `__all__`:

```python
#: Reason value for the ASYNC poller-detected GCP workload failover (#659).
#: Distinct from the synchronous ROUTE_REASON_GCP_WORKLOAD_FAILOVER_RUNPOD so
#: the marker trail tells the route()-time failover apart from the
#: poller-detected one (same RunPod target, different detection path).
ROUTE_REASON_GCP_WORKLOAD_FAILOVER_RUNPOD_ASYNC: str = "gcp_workload_failover_runpod_async"

def failover_to_runpod_after_async_workload_crash(
    *,
    spec: RunSpec,
    runpod_backend: ComputeBackend,
    evidence: dict[str, Any] | None = None,
    residual_gap: str = "gcp async workload crash (poller-detected); failing over to RunPod",
    marker_poster: Callable[..., None] | None = None,
    on_launched: Callable[[RunHandle], None] | None = None,
    lease_store: LeaseStore | None = None,
    now_fn: Callable[[], float] | None = None,
    config: RouterConfig | None = None,
) -> RouteResult:
    """Re-dispatch a poller-detected dead GCP workload onto RunPod, once.

    The ASYNC sibling of the synchronous _GcpWorkloadFailover path: the VM was
    already up and the workload crashed minutes in, so there is no live route()
    call to raise _GcpWorkloadFailover from. The poller (backend_poll.py)
    detects the dead GCP workload and calls this to launch the SAME RunPod
    terminal rung the sync path uses. Defaults match the production wiring
    (real LeaseStore, real now, real config); tests inject mocks for every
    seam, exactly like _runpod_terminal_rung's existing tests.
    """
    store = lease_store if lease_store is not None else LeaseStore()       # match _runpod_terminal_rung's default-construction pattern
    now_fn = now_fn or time.monotonic                                       # match router default
    config = config or RouterConfig()
    return _runpod_terminal_rung(
        spec=replace(spec, backend="runpod"),
        runpod_backend=runpod_backend,
        store=store,
        attempts=[],
        started_at=now_fn(),
        now_fn=now_fn,
        marker_poster=marker_poster,
        on_launched=on_launched,
        residual_gap=residual_gap,
        reason=ROUTE_REASON_GCP_WORKLOAD_FAILOVER_RUNPOD_ASYNC,
        failover_evidence=evidence,
    )
```

New helper #1 — the precise predicate:

```python
def _is_gcp_async_workload_failure(handle, result) -> bool:
    """True ONLY for a GCP handle whose poll surfaced a WORKLOAD crash.

    Narrow by construction: backend must be exactly "gcp" (SLURM/RunPod
    excluded — scope discipline §5), status must be "dead", and current_phase
    must be exactly "terminal_workload_failed" (the gcp.py:2997 signal). A GCP
    instance-gone / capacity / quota death surfaces a DIFFERENT current_phase
    ("terminal_instance not found", "terminal_terminated", ...), so this
    predicate does NOT fire for those — they keep walking the existing
    blocked/ladder path.
    """
    return (
        handle.backend == "gcp"
        and result.status == "dead"
        and result.current_phase == GCP_WORKLOAD_FAILED_PHASE   # "terminal_workload_failed"
    )
```

- Define `GCP_WORKLOAD_FAILED_PHASE = "terminal_workload_failed"` as a module
  constant in `backend_poll.py`, AND assert it equals what `gcp._terminal_dead_poll`
  produces for `reason="workload_failed"` — to prevent drift, the implementer
  imports the producing constant if one exists, else adds a comment cross-ref +
  a test that pins `gcp.poll`'s `failed`-phase `current_phase` value
  (§6 sibling test). **Single source of truth:** prefer extracting the string
  literal `"workload_failed"` (gcp.py:2997) into a shared named constant the
  poller imports, so a future rename of the GCP phase can't silently break the
  predicate.

New helper #2 — the actual re-dispatch:

```python
def _failover_dead_gcp_to_runpod(*, issue, handle, result, sidecar) -> dict:
    """Run the RunPod terminal rung for a dead GCP workload, re-point the
    sidecar, and return a RUNNING-shaped poll JSON for the orchestrator."""
    from explore_persona_space.backends.router import (
        failover_to_runpod_after_async_workload_crash,
    )
    from explore_persona_space.backends.runpod import RunPodBackend
    from explore_persona_space.backends.slurm import post_marker_via_task_py
    from explore_persona_space.backends.issue_dispatch import write_handle_sidecar
    from explore_persona_space.backends.base import RunSpec

    spec = _runspec_from_gcp_handle(handle, issue)   # reconstruct intent/gpus/etc from handle.extra
    route_result = failover_to_runpod_after_async_workload_crash(
        spec=spec,
        runpod_backend=RunPodBackend(),
        evidence={
            "source": "async_poller",
            "current_phase": result.current_phase,
            "log_tail_excerpt": result.log_tail_excerpt,
            "gcp_pod_name": handle.pod_name,
        },
        marker_poster=post_marker_via_task_py,
        on_launched=lambda h: write_handle_sidecar(h, sidecar),  # re-point sidecar BEFORE marker (crash-window insurance, mirrors dispatch_for_issue)
    )
    # The on_launched hook already rewrote the sidecar to the RunPod handle, so
    # the orchestrator's NEXT tick reads the RunPod handle and polls RunPod.
    # Emit a RUNNING-shaped JSON so the loop does NOT post epm:failure now.
    return {
        "status": "running",
        "current_phase": "gcp_workload_failover_runpod_async",
        "new_milestone": True,
        "last_log_mtime_sec_ago": 0,
        "pid_alive": True,
        "log_tail_excerpt": (
            f"GCP workload crash on {handle.pod_name}; failed over to RunPod "
            f"{route_result.handle.pod_name} (#659 async failover)"
        ),
        "gate": None,
        "sentinels_processed": 0,
        "phase_log_mtime_sec_ago": 10**9,
        "shard_log_mtime_sec_ago": 10**9,
        "gpu_util": "unknown",
        "next_interval": _DEFAULT_NEXT_INTERVAL_SEC,
        "issue": int(issue),
    }
```

`_runspec_from_gcp_handle` — reconstruct the `RunSpec` from the GCP handle's
`extra`. The implementer reads what `GcpBackend.launch` stuffs onto
`handle.extra` (intent, gpus, time-budget, hydra/workload_cmd) and rebuilds a
minimal `RunSpec(issue=..., intent=..., backend="runpod", ...)`. If the handle
does not carry enough to reconstruct the workload command, FAIL LOUD (raise) —
do NOT silently launch an empty RunPod job. (Assumption A7 — must verify the
handle carries the workload command.)

**Failure-of-the-failover fallback:** if
`failover_to_runpod_after_async_workload_crash` itself raises (RunPod truly
unavailable), `_runpod_terminal_rung` already re-raises
`NoComputeAvailableError`. Catch it in `_failover_dead_gcp_to_runpod` and emit a
terminal JSON with `status: "dead"`, `failure_class: "infra"`, `reason:
"no_compute_available"` (so the watcher's capacity-retry pass CAN re-drive once
a lane frees — this is the correct routing for "RunPod also unavailable"). Mirror
the missing-sidecar terminal JSON shape (backend_poll.py:143-168).

### 4.3 Marker

Reuse the `epm:backend-selected v1` schema VERBATIM — `_runpod_terminal_rung`
already posts it via `_post_backend_selected`. The ONLY new value is the
`reason` field: `gcp_workload_failover_runpod_async` (a new reason VALUE on the
EXISTING schema, NOT a new marker kind). The `gcp_workload_evidence` rides the
marker `extra` exactly as the sync path does (router.py:1987-1989). No
`workflow.yaml § markers` schema change — confirm `epm:backend-selected v1`
already permits an arbitrary `reason` string (Assumption A8).

### 4.4 Handle sidecar — overwrite, do NOT retire the GCP one

The `on_launched` hook rewrites `.claude/cache/issue-<N>-handle.json` IN PLACE
with the RunPod handle. This is correct because:
- The orchestrator's next Step 6d.2 tick reads that same path and now recovers a
  `backend == "runpod"` handle → `_resolve_backend("runpod")` → polls RunPod.
- No separate GCP sidecar needs to be "retired" — there is one sidecar per
  issue, and it is the live pointer. The old GCP handle's content is captured in
  the failover marker `extra` (`gcp_pod_name`, `current_phase`) for diagnosis.
- Atomic write (`write_handle_sidecar` uses write-temp + rename) so a concurrent
  read never sees a half-written file.

### 4.5 "Exactly once" — structural bound (no counter)

No new counter. The bound is the SAME one the sync path relies on:
1. The failover launches RunPod once and re-points the sidecar to the RunPod
   handle.
2. If the RunPod run ALSO crashes its workload, the next tick polls a RunPod
   handle (`backend == "runpod"`), NOT a GCP handle — so
   `_is_gcp_async_workload_failure` returns `False` (its first clause requires
   `backend == "gcp"`). The poller emits the ordinary `status: "dead"` for
   RunPod; the orchestrator runs the classifier → `failure_class: code` →
   `status:blocked`.
3. The watcher's capacity-retry pass re-drives ONLY `failure_class: infra` +
   `reason: no_compute_available`. A `code` block is never re-launched.

So a genuinely-broken job runs on RunPod at most once more, then parks at
`blocked` with a persistent SSH-able pod for diagnosis — identical to the sync
path's bound, enforced by the `backend == "gcp"` guard, not a counter.

## 5. Controls / scope discipline

- **SLURM workload failures unchanged.** `_is_gcp_async_workload_failure`
  requires `handle.backend == "gcp"`. A SLURM (`nibi`/`fir`/`mila`) handle never
  trips it; SLURM workload deaths keep surfacing the ordinary `status: "dead"`
  → `failure_class: code` → `blocked` path. (The sync SLURM path's
  `WorkloadSurfacedError` is in `route()`, not the poll path, and is untouched.)
- **GCP capacity / quota / zone misses unchanged.** Those surface SYNCHRONOUSLY
  in `route()` (capacity ladder) — they never reach the poller as a dead GCP
  workload. A GCP VM that is TERMINATED for a non-workload reason surfaces
  `current_phase` `"terminal_terminated"` / `"terminal_instance not found"`,
  which the predicate's exact-`"terminal_workload_failed"` match excludes — they
  keep their existing routing.
- **RunPod runs unchanged.** A RunPod handle never trips the GCP predicate.
- **OUT of scope (do NOT do):**
  - Do NOT re-architect the poller's failure-class taxonomy or
    `failure_classifier.py`.
  - Do NOT add a `failure_class`/`reason` field to `PollResult` (the dataclass
    stays as-is; the failover emits its own JSON dict).
  - Do NOT change `GcpBackend.poll` or the `eps/phase` guest-attribute
    contract — the existing `terminal_workload_failed` signal is sufficient.
  - Do NOT touch the synchronous `route()` failover or its tests (they stay
    green; this is purely additive).
  - Do NOT change the watcher's capacity-retry predicate
    (`TRANSIENT_CAPACITY_REASONS`) — the structural bound relies on it staying
    as `{"no_compute_available"}`.

## 7. Risks and failure modes

| Risk | Likelihood | Mitigation |
|---|---|---|
| **Race: poller re-points sidecar to RunPod while orchestrator still mid-tick on GCP JSON.** | Low | The poller is single-threaded per tick: it re-points the sidecar AND returns the RUNNING-shaped JSON in the SAME process before the orchestrator parses it. The orchestrator's NEXT tick (a fresh `backend_poll.py` invocation) reads the now-RunPod sidecar. There is no in-flight GCP poll to race — the GCP run is already dead. |
| **Double-dispatch: `/issue <N>` re-invoked mid-failover re-runs `route()` and launches a SECOND RunPod.** | Low | `route()` / `_runpod_terminal_rung` take a per-issue `flock` via `LeaseStore.transaction(spec.issue)` (router.py:1928); a concurrent second launch serializes on the lease. The failover writes the lease on success, so a re-invocation reads the live RunPod lease. The implementer must confirm the production `LeaseStore` default points at the SAME lease dir the launch path uses (Assumption A4). |
| **Marker ordering: status flips to `blocked` BEFORE the RunPod dispatch lands.** | Medium if mis-implemented | The failover emits `status: "running"` (NOT `"dead"`), so the orchestrator's Step 6d.2 loop does NOT post `epm:failure` / set `blocked` for the GCP death — it keeps polling. The `epm:backend-selected v1` marker is posted by `_runpod_terminal_rung` AFTER the RunPod launch + `on_launched` sidecar write (router.py:1959-1992), so the marker only appears once the RunPod run is live. No `blocked` is reachable on the happy failover path. |
| **Phase-string drift: `gcp.poll` renames `"workload_failed"` → predicate silently stops matching.** | Low | Extract the literal into a shared named constant the poller imports (§4.2), and add sibling test #1 + a test pinning `gcp.poll`'s `failed`-phase `current_phase`. A rename then breaks a test, not production silently. |
| **Handle can't reconstruct the workload command → empty RunPod job.** | Low | `_runspec_from_gcp_handle` FAILS LOUD (raises) if the handle lacks the workload command; never launches a blank job. Covered by Assumption A7 verification. |
| **RunPod also down → infinite block.** | Low | `_runpod_terminal_rung` re-raises `NoComputeAvailableError`; the poller maps it to `failure_class: infra` + `reason: no_compute_available`, which the watcher's capacity-retry pass DOES re-drive (correct — "no compute anywhere" should retry when a lane frees), bounded by the watcher's per-day cap. |
