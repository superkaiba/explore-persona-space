# Plan — Wire the ASYNC GCP-workload-failure → RunPod failover (poller / dispatch path)

## TDD: yes

The acceptance criterion IS a specific failing test ("a poller-surfaced GCP
`workload_failure` results in exactly one RunPod re-dispatch, then `blocked`
on a re-crash"). The cleanest path is write-the-test-first → it fails → write
the wiring → it passes. This satisfies the implementer's conditional gate at
`/issue` Step 4b: the implementer posts `epm:proposed-tests v1` with the test

## 1. Goal

When the async poller (`scripts/backend_poll.py`, driven each tick by the
orchestrator's Step 6d.2 bg-Bash loop) observes that a **GCP** run died of a
**workload** failure (a non-capacity, non-infra crash detected minutes into the
run on an already-up VM), re-dispatch that run on **RunPod exactly once** —
reusing the same RunPod terminal rung the synchronous `route()`-time failover
already uses — instead of ending at `status:blocked`. This completes the
user directive "if GCP is failing, run it on RunPod while we fix GCP" for the
COMMON (async-detected) failure path; today only the rare synchronous
`route()`-time path fails over.

  (lines 6179, 6290). A `failure_class: code` block is never re-driven — this

**The async signal is NOT a clean workload-crash discriminator as-is
(v4 — reconciler-upheld).** `current_phase == "terminal_workload_failed"` on a
`backend == "gcp"` handle is necessary but NOT sufficient. The reconciler
verified against `backends/gcp.py`:

- `_eps_phase startup` is published at `gcp.py:1159`; `_eps_phase workload` at
  `gcp.py:963` / `:991` — AFTER secrets-fetch / preflight / clone / `uv sync`.
- The EXIT trap (`gcp.py:1146-1150`) publishes `_eps_phase failed` on ANY
  non-zero exit between those two — so a setup-failure / secrets-failure /
  `uv sync` resolve error all produce `eps/phase = failed`.
- `eps/phase` is a SINGLE guest attribute carrying only the LATEST value
  (`render_guest_attributes_argv` queries `--query-path=eps/phase`, gcp.py:1550;
  `_guest_phase` matches `key == "phase"`, gcp.py:3062-3064) — so a poll-time
  read of `failed` CANNOT tell whether `workload` was ever reached.
- `GcpBackend.poll()` maps any `phase == "failed"` to
  `_terminal_dead_poll(reason="workload_failed")` (gcp.py:2996-2997) →
  `current_phase = "terminal_workload_failed"`.

So a non-workload death (setup / secrets / clone / uv-sync) produces the SAME
`current_phase` as a real workload crash. Firing the RunPod failover on a
setup-failure VM is exactly the "fragile heuristic" the §7 kill-criterion #1
forbids — re-running broken boot/setup on RunPod just re-crashes it there. v4
therefore discriminates workload-started from setup-failed at the GCP poll
layer (§4.1.0b) and narrows the failover predicate to the workload-only branch
(§4.2). This demotes v3's A1 confidence from "High" to "verified-true only for
a true workload crash" (§11).

**Confirmed sub-change required (Phase-1.5 fact-checker, A7):** the GCP
`RunHandle.extra` constructed in `GcpBackend.launch` (`gcp.py:2789-2800`) does
NOT carry the workload command — it has only `intent`, `issue`, `project`,
`gcloud_config`, `zone`, `instance_name`, `attempt_id`, `provisioning_model`,
`machine_type`, `reconnected` (+ the artifacts declaration). `serialize_handle`/
`deserialize_handle` round-trip `extra` faithfully, so anything ON the handle
survives — but the workload command was never put there, and `RunSpec(` is only
constructed at launch time (`issue_dispatch.py:306`); `backend_poll.py` has no
other path to it. So `_runspec_from_gcp_handle` (below) CANNOT reconstruct the
RunPod re-launch from `handle.extra` as-is. This plan therefore carries a small,
confirmed-required sub-change to thread `spec.workload_cmd` / `spec.hydra_args` /
`spec.gpus` / `spec.time_budget_hours` onto `handle.extra` at GCP launch time
(§4.1.0). This is a sub-change OF this task, not a separate task.

## 3. Method delta — WHERE the failover fires

**Chosen layer: `scripts/backend_poll.py` `main()`** (the poller-side seam),
calling a NEW thin public router helper `failover_to_runpod_after_async_workload_crash(...)`
that wraps `_runpod_terminal_rung` with production deps (mirroring how
`issue_dispatch.dispatch_for_issue` wraps `route()`).

Why this layer and not the alternatives:

- **`backend_poll.py main()` is the ONLY process that observes the async
  terminal signal AND holds the live handle.** It already deserializes the
  `RunHandle` (so it knows `handle.backend == "gcp"`), calls `backend.poll()`
  (so it sees `current_phase == "terminal_workload_failed"`), and knows the
  issue number — every input the failover needs is local. It already owns the
  handle-sidecar contract (it READS the sidecar each tick), so re-pointing the
  sidecar at the new RunPod handle is a natural extension of its existing
  responsibility. And it is a normal Python `main()` directly callable by
  pytest (`backend_poll_main([...])`, already done in
  `test_issue_dispatch.py:1155`), so the acceptance test is clean.

- **Rejected — the orchestrator's Step 6d.2 poll loop (SKILL.md markdown).**
  The loop is prose executed by the LM, not Python. A failover encoded there is
  un-unit-testable (the acceptance criterion demands a pytest), and re-running
  the router from LM-orchestrated steps is exactly the brittle pattern slice-6
  centralized into `dispatch_for_issue`. The orchestrator should keep treating
  the poller's JSON as the source of truth; the failover decision belongs below
  it, in Python.

- **Rejected — `issue_dispatch.dispatch_for_issue`.** That helper runs ONCE at
  launch (Step 6b) and returns; it is not in the poll path and has no view of
  the async death. Putting the failover there would require it to also become a
  poll consumer — a larger, wrong-shaped change. (It IS the right model to
  imitate — the new router helper mirrors its "build prod deps + call the launch
  primitive" structure, AND its authoritative post-route sidecar
  write/readback backstop — but the call site is the poller.)

The new router helper exists because `_runpod_terminal_rung` is too low-level to
call from the poller directly: its signature requires injected `store`,
`attempts`, `started_at`, `now_fn`, `marker_poster`, `on_launched`. The helper
builds the production-shaped versions of those (real `LeaseStore`, real
`post_marker_via_task_py`, real RunPod backend, a fresh `attempts` list, an
`on_launched` that rewrites the sidecar) and calls `_runpod_terminal_rung` with
`reason=ROUTE_REASON_GCP_WORKLOAD_FAILOVER_RUNPOD_ASYNC`. This keeps `backend_poll.py`
thin and keeps all router/lease/marker mechanics inside the router module where
the sync path's tests already live.

**Pod-side-shellout safety:** `backend_poll.py` runs on the VM (it is the
orchestrator's bg-Bash process, NOT pod-side code) — it already imports
`issue_dispatch` and resolves backends, so importing the router + posting via
`post_marker_via_task_py` is consistent with its existing role and does not
violate the "pods never shell out to task.py" rule.

**In-scope file set (v4 — fenced explicitly per the consistency-checker
WARN).** The task body named:
`scripts/backend_poll.py`, `src/explore_persona_space/backends/issue_dispatch.py`,
`backends/router.py`, `tests/test_router*.py`/`tests/test_backend_*.py`. v3
EXPANDED this with `src/explore_persona_space/backends/gcp.py` — the

`backends/gcp.py` is in scope ONLY for these THREE edits, NOTHING else:

## 4. Design — concrete files, signatures, diff shapes

### 4.1.0 Spec-threading at GCP launch time — `backends/gcp.py` (confirmed-required sub-change)

The Phase-1.5 fact-checker confirmed (A7) that the `extra={...}` dict at
`gcp.py:2789-2800` lacks the workload command, so the poller cannot reconstruct
a `RunSpec` for the RunPod re-launch from the GCP handle as it stands. This
sub-change threads the four missing spec fields onto `handle.extra` at launch
time, inside `GcpBackend.launch`, at the `extra={...}` construction (`gcp.py:2789`):

```python
extra={
    # ... existing keys (intent, issue, project, gcloud_config, zone,
    # instance_name, attempt_id, provisioning_model, machine_type,
    # reconnected, + artifacts) unchanged ...
    "workload_cmd": spec.workload_cmd or "",             # NEW (#659) — STR, not a sequence
    "hydra_args": list(spec.hydra_args or ()),           # NEW (#659) — tuple -> list
    "gpus": spec.gpus,                                    # NEW (#659)
    "time_budget_hours": spec.time_budget_hours,          # NEW (#659)
}
```

**MF1 — `workload_cmd` is a `str`, not a sequence.** `RunSpec.workload_cmd` is
declared `str = ""` (`base.py:132`), in contrast with `hydra_args:
tuple[str, ...] = ()` (`base.py:118`). v3 wrote `list(spec.workload_cmd or ())`,
which on a real command (e.g. `"REPO_ROOT=$WORKLOAD_ROOT bash scripts/foo.sh"`)
would explode the STRING into a per-character list — corrupting the value. The
correct form preserves the string as-is: `spec.workload_cmd or ""`. A JSON
round-trip is faithful for a plain string, so `serialize_handle`/
`deserialize_handle` carry it unchanged. `hydra_args` IS a tuple, so coercing it
to `list(...)` for JSON round-trip safety is correct and stays. `gpus` /
`time_budget_hours` are scalars and serialize as-is.

Implementation notes for the implementer:
- This is a **dict-key addition only** — no change to `GcpBackend.launch`'s
  control flow, no new arguments, no new branches. `spec` is already in scope at
  that construction site (it is `GcpBackend.launch`'s argument).
- `serialize_handle`/`deserialize_handle` (issue_dispatch.py:325/344) round-trip
  `extra` faithfully (confirmed by fact-checker), so these keys survive the
  sidecar write/read with no serializer change. The matching test (§6) pins this
  round-trip with a NON-EMPTY `workload_cmd`.
- If the kept-purpose-only constraint is violated — i.e. threading these keys
  forces ANY change to `GcpBackend.launch` beyond this dict-key addition + its
  tests — that is the §7 kill-criterion #3 trigger (re-plan; do not smuggle a
  larger GCP-launch-path change into this task).

### 4.1.0b Workload-vs-setup discrimination at GCP poll time — `backends/gcp.py` (MF3, reconciler-upheld)

The async predicate (§4.2) must fire the RunPod failover ONLY on a true
workload crash, never on a setup / secrets / clone / `uv sync` failure (both
currently surface `current_phase == "terminal_workload_failed"`; §2). The
discrimination lives GCP-side because only the VM knows whether the workload
phase was ever reached, and `eps/phase` (single-valued, latest-wins) has already
been overwritten to `failed` by poll time.

**(1) Publish a workload-started sentinel as a SEPARATE guest attribute.** The
startup script already publishes `_eps_phase workload` immediately before the
workload runs (`gcp.py:963` workload_cmd branch / `:991` hydra branch). Because
`eps/phase` is later overwritten to `failed` by the EXIT trap, add a SECOND,
write-once guest attribute under a DIFFERENT key — `eps/workload_started` — set
to `true` from the SAME workload-phase preamble (right where `_eps_phase
workload` / `touch /tmp/eps-workload-start` already are). A different key is
never overwritten by the `eps/phase = failed` write, so its presence at poll
time proves the workload phase was reached. Implementation shape (mirror the
existing `_eps_phase` curl helper at `gcp.py:1038-1043`, best-effort `|| true`):

```bash
# workload-phase preamble (both branches), beside _eps_phase workload:
curl -fsS -X PUT -H "Metadata-Flavor: Google" --data "true" \
  "http://metadata.google.internal/computeMetadata/v1/instance/guest-attributes/eps/workload_started" \
  >/dev/null 2>&1 || true
```

This publish is shared between BOTH workload branches (workload_cmd at gcp.py:963
and hydra at gcp.py:991) — add it to the common workload-phase preamble so the
hydra-branch byte-identity snapshot test
(`test_render_startup_script_hydra_only_byte_identical_to_pre_change_snapshot`,
per `.claude/rules/compute-backend-failover.md`) is regenerated DELIBERATELY
with a documented provenance note (the implementer regenerates
`tests/fixtures/issue588_gcp_startup_hydra_only.json` and records the #659
provenance, same discipline as the #658 EXIT-trap edit). `bash -n` the rendered
script (the existing `test_render_startup_script_is_valid_bash` covers this).

**(2) Read the sentinel in `GcpBackend.poll`'s `phase == "failed"` branch.** Add
a getattr-guarded read of `eps/workload_started` (a second
`get-guest-attributes --query-path=eps/workload_started` probe, OR widen the
existing read to fetch the whole `eps/` namespace and look for both keys — the
implementer picks whichever is the smaller diff; querying the whole namespace in
one round-trip is preferred to avoid a second gcloud call). Then branch the
`phase == "failed"` mapping (gcp.py:2996-2997) into TWO distinct
`current_phase` values:

```python
if phase == "failed":
    # (relaunch-follow branch above, unchanged)
    if self._workload_started(handle, zone):      # eps/workload_started == "true"
        return _with_drain(_terminal_dead_poll(reason="workload_failed"))     # current_phase="terminal_workload_failed"
    return _with_drain(_terminal_dead_poll(reason="setup_failed"))            # current_phase="terminal_setup_failed"
```

- `_terminal_dead_poll(reason=...)` already builds `current_phase=f"terminal_{reason}"`
  (gcp.py:3690), so `reason="setup_failed"` yields `current_phase=
  "terminal_setup_failed"` with no change to `_terminal_dead_poll` itself.
- **Probe-failure discipline (do NOT misread "couldn't ask" as "setup failed").**
  The `eps/workload_started` read MUST distinguish the EXPECTED not-written-yet
  case (404 / "not found" → attribute absent → workload NOT started → setup
  failure) from a PROBE FAILURE (auth / API / transport / bad JSON), exactly as
  `_guest_phase` does (gcp.py:3045-3060). On a probe FAILURE the safe behavior is
  to fall back to the EXISTING `terminal_workload_failed` mapping (do NOT
  silently downgrade to `setup_failed` on an unprovable read) — surfacing the
  ordinary `dead` path is conservative (it routes to `blocked`, the pre-#659
  behavior), whereas a false `setup_failed` would suppress a legitimate
  workload failover. Document this fallback in the helper docstring.
- This is a small string-mapping addition in `GcpBackend.poll` + one guest-attr
  read helper — NOT a control-flow change to `GcpBackend.launch`. It stays inside
  the kill-criterion #3 fence.

**(3) The async-failover predicate stays narrow.** `_is_gcp_async_workload_failure`
(§4.2) still matches ONLY `current_phase == "terminal_workload_failed"`. The new
`terminal_setup_failed` value is NOT a workload crash → it does NOT fire the
failover; it routes through the ordinary `status: "dead"` path as a
`failure_class: code` block (the setup/boot script for THIS run is broken — a
code defect, not a transient infra miss, so it does NOT get the watcher's
capacity re-drive). The poller does NOT need to special-case `setup_failed`: it
falls through to `_serialize_poll_result` like any other dead poll, and the
orchestrator's failure-classifier routes it to `blocked`.

**Option-B feasibility check (settled — option A is taken).** Per the MF3
escape hatch, option B (abort + re-plan) is the LAST RESORT, valid only if the
GCP-side discrimination is structurally infeasible. It is NOT: `eps/phase` is
single-valued so a poll-time read of it cannot discriminate, BUT a SEPARATE
write-once guest attribute (`eps/workload_started`) survives the later
`eps/phase = failed` write (different key) and is readable by `GcpBackend.poll`
via the same guest-attribute API the existing `_guest_phase` already uses
(gcp.py:3043-3065). Confirmed against `gcp.py:1146-1159` (EXIT trap),
`:963`/`:991` (workload-phase publish), `:1038-1043` (curl helper),
`:3021-3065` (`_guest_phase` read + probe-typing). Option A is feasible and
taken; option B is NOT exercised.

### 4.1 New router helper — `backends/router.py`

Add a module-level PUBLIC function near `_runpod_terminal_rung` (router.py,
after line 1993) and export it in `__all__`:

```python
#: Reason value for the ASYNC poller-detected GCP workload failover (#659).
#: Distinct from the synchronous ROUTE_REASON_GCP_WORKLOAD_FAILOVER_RUNPOD so
#: the marker trail tells the route()-time failover apart from the
#: poller-detected one (same RunPod target, different detection path).
ROUTE_REASON_GCP_WORKLOAD_FAILOVER_RUNPOD_ASYNC: str = "gcp_workload_failover_runpod_async"

def failover_to_runpod_after_async_workload_crash(
    *,
    spec: RunSpec,
    runpod_backend: ComputeBackend,
    evidence: dict[str, Any] | None = None,
    residual_gap: str = "gcp async workload crash (poller-detected); failing over to RunPod",
    marker_poster: Callable[..., None] | None = None,
    on_launched: Callable[[RunHandle], None] | None = None,
    lease_store: LeaseStore | None = None,
    now_fn: Callable[[], float] | None = None,
    config: RouterConfig | None = None,
) -> RouteResult:
    """Re-dispatch a poller-detected dead GCP workload onto RunPod, once.

    The ASYNC sibling of the synchronous _GcpWorkloadFailover path: the VM was
    already up and the workload crashed minutes in, so there is no live route()
    call to raise _GcpWorkloadFailover from. The poller (backend_poll.py)
    detects the dead GCP workload and calls this to launch the SAME RunPod
    terminal rung the sync path uses. Defaults match the production wiring
    (real LeaseStore, real now, real config); tests inject mocks for every
    seam, exactly like _runpod_terminal_rung's existing tests.
    """
    store = lease_store if lease_store is not None else LeaseStore()       # match _runpod_terminal_rung's default-construction pattern
    now_fn = now_fn or time.monotonic                                       # match router default
    config = config or RouterConfig()
    return _runpod_terminal_rung(
        spec=replace(spec, backend="runpod"),
        runpod_backend=runpod_backend,
        store=store,
        attempts=[],
        started_at=now_fn(),
        now_fn=now_fn,
        marker_poster=marker_poster,
        on_launched=on_launched,
        residual_gap=residual_gap,
        reason=ROUTE_REASON_GCP_WORKLOAD_FAILOVER_RUNPOD_ASYNC,
        failover_evidence=evidence,
    )
```

Implementation notes for the implementer:
- Confirm the exact default-construction of `LeaseStore`, `now_fn`, and
  `RouterConfig` against how `route()` itself defaults them (router.py ~1218);
  match those defaults verbatim so production wiring is identical to the sync
  path. Do NOT invent a new default.
- `_runpod_terminal_rung` already maps the `reason` into both the
  `RouteResult.reason` and the `epm:backend-selected` marker; passing the new
  `_ASYNC` reason flows through with no further change to that function. Verify
  `_runpod_terminal_rung`'s `if reason == ROUTE_REASON_GCP_WORKLOAD_FAILOVER_RUNPOD`

  `_ASYNC` reason to that `if` so the "failing over to RunPod" log fires for

- `is_workload_failover` (router.py:1961) similarly checks `== `the sync reason;

### 4.2 Poller wiring — `scripts/backend_poll.py`

The current `main()` tail (backend_poll.py:268-271) is:

```python
backend = _resolve_backend(handle.backend)
result = backend.poll(handle)
print(json.dumps(_serialize_poll_result(result)))
return 0
```

Insert the failover BETWEEN `backend.poll(handle)` and the `print`:

```python
backend = _resolve_backend(handle.backend)
result = backend.poll(handle)

# ASYNC GCP-workload-failover (#659): a GCP VM that was already up and
# crashed its WORKLOAD (not setup) minutes in surfaces here as status=dead /
# current_phase="terminal_workload_failed". The sync route()-time failover
# (#658) cannot reach this case — the VM is already launched. Re-dispatch on
# RunPod exactly once (the SAME terminal rung), re-point the handle sidecar at
# the new RunPod handle, and emit a RUNNING-shaped JSON so the orchestrator's
# poll loop keeps polling the RunPod run instead of posting epm:failure.
# A setup/boot failure surfaces current_phase="terminal_setup_failed" (GCP
# poll discrimination, §4.1.0b) and does NOT match the predicate -> it falls
# through to the ordinary dead path (failure_class: code -> blocked).
if _is_gcp_async_workload_failure(handle, result):
    failover_json = _failover_dead_gcp_to_runpod(
        issue=args.issue, handle=handle, result=result, sidecar=Path(sidecar)
    )
```

```python
def _failover_dead_gcp_to_runpod(*, issue, handle, result, sidecar) -> dict:
    """Run the RunPod terminal rung for a dead GCP workload, re-point the
    sidecar, AUTHORITATIVELY read it back, and return a RUNNING-shaped poll
    JSON for the orchestrator (or a terminal infra JSON if persistence fails)."""
    from explore_persona_space.backends.router import (
        failover_to_runpod_after_async_workload_crash,
    )
    from explore_persona_space.backends.runpod import RunPodBackend
    from explore_persona_space.backends.slurm import post_marker_via_task_py
    from explore_persona_space.backends.issue_dispatch import (
        write_handle_sidecar,
        read_handle_sidecar,
    )

    spec = _runspec_from_gcp_handle(handle, issue)   # reconstruct intent/gpus/etc from handle.extra
    try:
        route_result = failover_to_runpod_after_async_workload_crash(
            spec=spec,
            runpod_backend=RunPodBackend(),
            evidence={
                "source": "async_poller",
                "current_phase": result.current_phase,
                "log_tail_excerpt": result.log_tail_excerpt,
                "gcp_pod_name": handle.pod_name,
            },
            marker_poster=post_marker_via_task_py,
            # BEST-EFFORT in-route lease-mid-flight write (mirrors dispatch_for_issue's
            # on_launched). _invoke_on_launched SWALLOWS exceptions (router.py:1456-1481),
            # so this is NOT authoritative -- the post-route write below is.
            on_launched=lambda h: write_handle_sidecar(h, sidecar),
        )
    except NoComputeAvailableError:
        # RunPod truly unavailable: emit a terminal infra JSON with
        # reason=no_compute_available so the watcher's capacity-retry pass CAN
        # re-drive once a lane frees. Mirror _missing_sidecar_json shape.
        return _terminal_infra_json(
            issue=issue, sidecar=sidecar, reason="no_compute_available",
            log_tail=f"GCP workload crash on {handle.pod_name}; RunPod also unavailable",
        )

    # AUTHORITATIVE post-route sidecar write + readback (MF4). The on_launched
    # hook above is best-effort (its exceptions are swallowed by the router), so
    # we re-point the sidecar HERE and PROVE it landed as a RunPod handle. If the
    # write raises (disk error / EDQUOT) or the readback does not show
    # backend=="runpod", we must NOT emit status:"running" -- a swallowed
    # on_launched failure would otherwise leave a GCP handle on disk and the next
    # tick would re-satisfy backend=="gcp" -> a SECOND RunPod launch (the "exactly
    # once" bound breached, the dispatch_for_issue backstop this poller lacked).
    try:
        write_handle_sidecar(route_result.handle, sidecar)
        recovered = read_handle_sidecar(sidecar)
    except (OSError, json.JSONDecodeError, KeyError, ValueError) as exc:
        return _terminal_infra_json(
            issue=issue, sidecar=sidecar, reason="sidecar_persistence_failed",
            log_tail=(
                f"GCP->RunPod failover launched RunPod {route_result.handle.pod_name} "
                f"but sidecar persistence FAILED ({type(exc).__name__}: {exc}); refusing "
                f"to emit running (would re-launch RunPod next tick)"
            ),
        )
    if recovered.backend != "runpod":
        return _terminal_infra_json(
            issue=issue, sidecar=sidecar, reason="sidecar_persistence_failed",
            log_tail=(
                f"GCP->RunPod failover: sidecar readback shows backend={recovered.backend!r}, "
                f"not 'runpod'; refusing to emit running (would re-launch RunPod next tick)"
            ),
        )

    # Sidecar is now an authoritative RunPod handle on disk -> the orchestrator's
    # NEXT tick reads RunPod and polls RunPod. Emit a RUNNING-shaped JSON so the
    # loop does NOT post epm:failure now.
    return {
        "status": "running",
        "current_phase": "gcp_workload_failover_runpod_async",
        "new_milestone": True,
        "last_log_mtime_sec_ago": 0,
        "pid_alive": True,
        "log_tail_excerpt": (
            f"GCP workload crash on {handle.pod_name}; failed over to RunPod "
            f"{route_result.handle.pod_name} (#659 async failover)"
        ),
        "gate": None,
        "sentinels_processed": 0,
        "phase_log_mtime_sec_ago": 10**9,
        "shard_log_mtime_sec_ago": 10**9,
        "gpu_util": "unknown",
        "next_interval": _DEFAULT_NEXT_INTERVAL_SEC,
```

### 4.4 Handle sidecar — overwrite + AUTHORITATIVE readback (MF4)

The failover re-points `.claude/cache/issue-<N>-handle.json` to the RunPod
handle via TWO writes, with distinct guarantees:

1. **Best-effort in-route write** — the `on_launched=lambda h:
   write_handle_sidecar(h, sidecar)` hook fires inside `_runpod_terminal_rung`
   the instant RunPod launches, BEFORE the marker post (crash-window insurance,
   mirrors `dispatch_for_issue`). But `_invoke_on_launched` (router.py:1456-1481)
   SWALLOWS any exception this hook raises (logged loud, not propagated) — so it
   is NOT authoritative. A disk error here leaves the GCP handle on disk while
   the launch already succeeded.
2. **Authoritative post-route write + readback** — `_failover_dead_gcp_to_runpod`
   (§4.2) re-writes the sidecar to the RunPod handle AFTER the route returns AND
   reads it back to prove `recovered.backend == "runpod"` on disk. This is the
   backstop `dispatch_for_issue` has (its `_write_sidecar_guarded`,
   issue_dispatch.py:626) and the v3 poller helper LACKED. If the write raises
   OR the readback shows a non-RunPod backend, the helper emits the terminal
   infra JSON (`status: "dead"`, `failure_class: "infra"`, `reason:
   "sidecar_persistence_failed"`) — it does NOT emit `status: "running"`.

This is correct because:
- The orchestrator's next Step 6d.2 tick reads that same path; ONLY after the
  authoritative readback confirms a `backend == "runpod"` handle does the helper
  emit `running`, so the next tick is GUARANTEED to poll RunPod (not GCP).
- No separate GCP sidecar needs to be "retired" — there is one sidecar per
  issue, and it is the live pointer. The old GCP handle's content is captured in
  the failover marker `extra` (`gcp_pod_name`, `current_phase`) for diagnosis.
- Atomic write (`write_handle_sidecar` uses write-temp + rename,
  issue_dispatch.py:368-379) so a concurrent read never sees a half-written file.

### 4.5 "Exactly once" — structural bound (no counter), now with a GUARANTEED precondition (MF4)

No new counter. The bound is the SAME one the sync path relies on, but v4 makes
its load-bearing precondition — a re-pointed RunPod sidecar — GUARANTEED rather
than best-effort:

1. The failover launches RunPod once and AUTHORITATIVELY re-points the sidecar to
   the RunPod handle (write + readback, §4.4). It emits `status: "running"` ONLY
   after the readback proves `backend == "runpod"` on disk; if persistence fails
   it emits the terminal infra JSON and does NOT claim `running`.
2. If the RunPod run ALSO crashes its workload, the next tick polls a RunPod
   handle (`backend == "runpod"`), NOT a GCP handle — so
   `_is_gcp_async_workload_failure` returns `False` (its first clause requires
   `backend == "gcp"`). The poller emits the ordinary `status: "dead"` for
   RunPod; the orchestrator runs the classifier → `failure_class: code` →
   `status:blocked`.
3. The watcher's capacity-retry pass re-drives ONLY `failure_class: infra` +
   `reason: no_compute_available` (`TRANSIENT_CAPACITY_REASONS`). A `code` block
   is never re-launched; a `sidecar_persistence_failed` infra block is ALSO never
   re-driven (its reason is not in `TRANSIENT_CAPACITY_REASONS`) — it parks at
   `blocked` for human inspection.

Why the MF4 readback matters for the bound: WITHOUT it, a swallowed
`on_launched` write failure would leave a GCP handle on disk while the helper
emitted `running`; the orchestrator's next tick would re-read a GCP handle,
re-satisfy `backend == "gcp"`, and fire a SECOND RunPod launch — breaching
"exactly once". The authoritative readback closes that window: a re-pointed
RunPod sidecar is now a precondition of emitting `running`, not a hopeful
side effect.

So a genuinely-broken job runs on RunPod at most once more, then parks at
`blocked` with a persistent SSH-able pod for diagnosis — identical to the sync
path's bound, enforced by the `backend == "gcp"` guard PLUS the guaranteed
sidecar re-point, not a counter.

## 7. Risks and failure modes

| Risk | Likelihood | Mitigation |
|---|---|---|
| **Race: poller re-points sidecar to RunPod while orchestrator still mid-tick on GCP JSON.** | Low | The poller is single-threaded per tick: it re-points the sidecar AND returns the RUNNING-shaped JSON in the SAME process before the orchestrator parses it. The orchestrator's NEXT tick (a fresh `backend_poll.py` invocation) reads the now-RunPod sidecar. There is no in-flight GCP poll to race — the GCP run is already dead. |
| **Double-dispatch: `/issue <N>` re-invoked mid-failover re-runs `route()` and launches a SECOND RunPod.** | Low | `route()` / `_runpod_terminal_rung` take a per-issue `flock` via `LeaseStore.transaction(spec.issue)` (router.py:1928); a concurrent second launch serializes on the lease. The failover writes the lease on success, so a re-invocation reads the live RunPod lease. The implementer must confirm the production `LeaseStore` default points at the SAME lease dir the launch path uses (Assumption A4). |
| **Marker ordering: status flips to `blocked` BEFORE the RunPod dispatch lands.** | Medium if mis-implemented | The failover emits `status: "running"` (NOT `"dead"`), so the orchestrator's Step 6d.2 loop does NOT post `epm:failure` / set `blocked` for the GCP death — it keeps polling. The `epm:backend-selected v1` marker is posted by `_runpod_terminal_rung` AFTER the RunPod launch + `on_launched` sidecar write (router.py:1959-1992), so the marker only appears once the RunPod run is live. No `blocked` is reachable on the happy failover path. |
| **Phase-string drift: `gcp.poll` renames `"workload_failed"` → predicate silently stops matching.** | Low | Extract the literal into a shared named constant the poller imports (§4.2), and add the §6 GCP poll-discrimination test + sibling test #1. A rename then breaks a test, not production silently. |
| **MF3 false failover: a SETUP/boot/secrets/uv-sync failure fires the RunPod re-launch (would just re-crash on RunPod).** | Was High in v3 (collapsed phases); Low after MF3 | §4.1.0b publishes `eps/workload_started` from the workload-phase preamble (a separate guest attribute that survives the `eps/phase=failed` write) and `GcpBackend.poll` maps `phase==failed` with the sentinel ABSENT to `current_phase="terminal_setup_failed"`, which the §4.2 predicate excludes. Pinned by `test_gcp_poll_distinguishes_workload_failed_from_setup_failed` + `test_gcp_setup_failure_does_not_failover_to_runpod`. A probe FAILURE on the sentinel read falls back conservatively to `terminal_workload_failed` (do NOT misread "couldn't ask" as "setup failed"). |
| **MF4 swallowed sidecar-write failure → second RunPod launch (exactly-once breached).** | Was real in v3 (no authoritative readback); closed after MF4 | `_invoke_on_launched` swallows the in-route write's exceptions (router.py:1456-1481), so v3's `on_launched`-only re-point could silently fail and leave a GCP handle on disk. §4.2/§4.4 add an AUTHORITATIVE post-route `write_handle_sidecar` + `read_handle_sidecar` that PROVES `backend=="runpod"` on disk before emitting `running`; on any write/readback failure the helper emits the terminal infra JSON (`reason: sidecar_persistence_failed`, NOT in `TRANSIENT_CAPACITY_REASONS` → parks at `blocked`, no re-drive). | **RunPod also down → infinite block.** | Low | `_runpod_terminal_rung` re-raises `NoComputeAvailableError`; the poller maps it to `failure_class: infra` + `reason: no_compute_available`, which the watcher's capacity-retry pass DOES re-drive (correct — "no compute anywhere" should retry when a lane frees), bounded by the watcher's per-day cap. |
