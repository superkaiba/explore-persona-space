# Plan v2 — #2606: `pod.py provision` must fail loud when its own preflight fails

Revision of v1 after critic round 1 (Methodology lens, REVISE). Changes vs v1: (1) the v1 "router path needs NO code change — #2038 fires by pre-existing policy" claim was FALSE against the code (the provision relay raises BEFORE the #2038 try-wrapper); v2 adds a scoped router-side rc-78 disposition (Change 3). (2) Criterion 3's mandated fixture is now an EXECUTED shell test of the rc=2→78 mapping, not static pins alone (Test 8). (3) The step-10 capture idiom is prescribed in the extractor-compatible form; the rc-78 masquerade caveat gets a comment; the `PREFLIGHT: FAIL` line flags its rc as the mapped sentinel code.

## Requirement + acceptance criteria

`pod.py provision` currently exits 0 and prints `BOOTSTRAP-OK pod=<name>` + "Done. SSH with: ..." even when the bootstrap's own step-10 preflight reported `PREFLIGHT-FAILED-AT-BOOTSTRAP rc=2` (observed live on pod-2569-rows, 2026-08-26: two errno-116 ESTALE uv install failures left a broken venv; the caller only found out by grepping the log). Acceptance criteria (verbatim from the task body):

1. A bootstrap whose preflight exits non-zero makes `pod.py provision` exit NON-ZERO, and the terminal banner says FAILED, not `BOOTSTRAP-OK`. The pod is left alive (may be recoverable) but the caller is told, loudly, in the exit code.
2. The provision summary surfaces the preflight verdict explicitly (a `PREFLIGHT: PASS|FAIL rc=<n>` line), so a caller need not grep the log.
3. `BOOTSTRAP-OK` is emitted only when bootstrap AND its preflight both succeeded. A regression test pins the pairing (a fixture where preflight returns 2 must not produce a success banner or a zero exit).
4. No change to the pod's lifecycle on failure — do NOT auto-terminate (the pod may be repairable; pods are not killed without the owner's decision).

Criterion-4 scope reconciliation (recorded design decision): criterion 4 binds the DIRECT CLI (`pod.py provision` — the #2569 incident context, where an operator exists to repair the pod). On the ROUTER path (`RunPodBackend.launch`, autonomous dispatch), the already-reviewed #2038 policy governs post-provision failures with no started workload: best-effort exact-id terminate, because an unattended broken pod is the #664 billing leak and no operator exists to repair it. v1 recorded the intent that #2038 covers this; the critic showed the exception fires BEFORE #2038's wrapper, so v2 implements that intent explicitly (Change 3). The task body's own motivation covers this: "Every session that trusts the provision exit code therefore receives a silently broken pod and launches a workload onto it."

Explicitly OUT of scope (task body): the default-overlay-venv-at-bootstrap design change (recurring errno-116 class across #475/#2225/#2278/#2378/#2569) — needs its own review; any change to #2060/#2038 SEMANTICS (Change 3 extends #2038's coverage to a site it was always meant to govern, using its existing machinery — it does not alter its policy); `orchestrate/preflight.py` itself.

## Root cause (verified in-repo, 2026-08-26; re-verified by critic round 1)

- `scripts/bootstrap_pod.sh:778` (step 10): the pod-side preflight is invoked inside the ssh payload as
  `uv run python -m explore_persona_space.orchestrate.preflight --no-gpu 2>&1 || echo "PREFLIGHT-FAILED-AT-BOOTSTRAP rc=$?"`.
  The `|| echo` exists so `set -euo pipefail` (line 46) does not abort the script on a preflight failure — but it converts the failure into a SILENT SUCCESS: the remote shell exits 0, `ssh_cmd` returns 0, the script reaches "Bootstrap complete" and exits 0.
- `scripts/pod_lifecycle.py::_provision_wait_register_bootstrap` (~2591-2664): `rc = _bootstrap(...)`; non-zero → retry EXACTLY ONCE (#1931); still non-zero → `_record_bad_placement_loud` + `_teardown_failed_provision` (#2060 auto-terminate unless `--keep-on-bootstrap-failure`) + `BOOTSTRAP-FAILED pod=<name> rc=<rc>` as last stderr line + `sys.exit(rc)`. rc==0 → `BOOTSTRAP-OK pod=<name>` on BOTH streams (#1931 token-once grep contract, line 2660) + exit 0. Because the swallow above pins rc==0, the preflight failure never reaches this dispatch.
- Router path (critic-verified): `RunPodBackend.launch` calls `_run_pod_lifecycle_relay` at ~line 1443, which raises `PodLifecycleProcessError` on non-zero rc; the #2038 protective `try:` begins ~30 lines LATER (~1475) with its `except` → `_dispose_post_provision_failure` at ~1707. A provision exit therefore raises BEFORE the #2038 wrapper — today that is safe only because pod_lifecycle itself tears down every bootstrap failure (#2060) inside the subprocess before exiting non-zero.

## Design: a distinct typed exit code for "bootstrap completed but preflight failed"

The existing non-zero-rc branch AUTO-TERMINATES (#2060), which criterion 4 forbids for the preflight-failure class on the direct CLI. So the preflight failure must arrive at `pod_lifecycle.py` as a DISTINCT signal.

**Channel: a reserved script exit code.** `_bootstrap()` runs `bootstrap_pod.sh` via `subprocess.call` with INHERITED stdout (streaming progress is a feature) — the exit code is the only clean machine channel without changing the subprocess contract. Chosen value: **78** (`EXIT_BOOTSTRAP_PREFLIGHT_FAILED`). Collision check (verified twice — plan-time + critic round 1): 75 = still-waiting (`backends/runpod.py:126`), 76 = stopped-pod collision (`:141`), 77 = CPU-LANE-DRY (`pod_lifecycle.py:1189`); 78 is unused in the pod_lifecycle/dispatch_issue/router process family (`backends/gcp.py:3056`'s `exit 78` is inside a rendered GCE startup script — a remote VM payload, different process family). The implementer re-greps before landing; on a discovered collision, pick the next free code and update both constants + tests (allowed deviation).

### Change 1 — `scripts/bootstrap_pod.sh` (step 10)

- Add a named constant near the top: `EXIT_PREFLIGHT_FAILED=78` with a comment pointing at the mirror constant in `pod_lifecycle.py` and the parity test.
- Rework step 10: drop the in-payload `|| echo` swallow; capture the rc LOCALLY in the EXTRACTOR-COMPATIBLE form. `tests/test_bootstrap_pod_uv_link_mode.py::_step10_payload`'s `_STANDALONE_CLOSE_RE` requires the payload's closing `'` ALONE on its line, so a `' || PREFLIGHT_RC=$?` suffix on the closing line would break the extractor. Prescribed form (critic nice-to-have 1):
  ```
  set +e
  ssh_cmd '<existing payload; last line = the preflight command, no || fallback>
  '
  PREFLIGHT_RC=$?
  set -e
  if [ "$PREFLIGHT_RC" -ne 0 ]; then
      # Attribution caveat (accepted): an ssh TRANSPORT failure here (rc 255),
      # a failure of an earlier payload line (cd/source), or an earlier remote
      # command coincidentally exiting 78 all classify as preflight failure.
      # Conservative direction: the pod is KEPT ALIVE instead of torn down,
      # and the printed rc discriminates (255 = transport).
      echo "PREFLIGHT-FAILED-AT-BOOTSTRAP rc=$PREFLIGHT_RC"   # sentinel kept, now printed locally (grep-compat with #2569 forensics)
      log_fail "Preflight FAILED (rc=$PREFLIGHT_RC) — pod venv/env is NOT experiment-ready"
      echo "Bootstrap FAILED at preflight for ${POD_NAME:-$HOST:$PORT} (preflight rc=$PREFLIGHT_RC)."
      exit "$EXIT_PREFLIGHT_FAILED"
  fi
  log_ok "Preflight passed"
  ```
- The `exit` fires before step 11 and before the "Bootstrap complete" success summary, so the success summary is structurally unreachable on the failure path (criterion 3's shell half).
- The `--no-preflight` branch is unchanged (skip). Neither `pod.py provision` nor `pod.py bootstrap` ever passes `--no-preflight` (`_bootstrap` invokes `["bash", BOOTSTRAP_SCRIPT, pod_name]`), so on every provision path exit 0 now implies "preflight ran and passed".
- Payload note: the payload must stay single-quote-free (the extractor pulls it verbatim); removing the `|| echo "..."` tail only deletes double quotes. Run that test after the edit.

### Change 2 — `scripts/pod_lifecycle.py` (`_provision_wait_register_bootstrap`)

- Add module constant `EXIT_BOOTSTRAP_PREFLIGHT_FAILED = 78` (docstring: mirror of `bootstrap_pod.sh` `EXIT_PREFLIGHT_FAILED`; parity pinned by test; consumed by `backends/runpod.py` Change 3).
- Keep the #1931 retry-once EXACTLY as is for ALL non-zero rc, 78 included — a re-run re-executes `uv sync`, and the incident class (transient MooseFS ESTALE) is plausibly recoverable on re-run, same rationale as #1931's apt/network class. A mixed [78→0] sequence lands on the success branch.
- After the retry, branch on the final rc:
  - `rc == 0` → print `PREFLIGHT: PASS` (stdout, immediately before the OK verdict), then the existing `BOOTSTRAP-OK` both-streams block + "Done. SSH with: ..." — unchanged otherwise.
  - `rc == EXIT_BOOTSTRAP_PREFLIGHT_FAILED` → NEW branch, in order:
    1. stderr guidance block: bootstrap completed but the pod's own preflight FAILED; pod is left ALIVE and registered (criterion 4) — repair pointers: the raw preflight rc is in the `PREFLIGHT-FAILED-AT-BOOTSTRAP rc=<n>` log line; for the errno-116/ESTALE venv class see `.claude/rules/gotchas.md` Trap 3 (overlay venv at /root/eps-venv + UV_NO_SYNC); re-check with `ssh <name> 'cd /workspace/explore-persona-space && uv run python -m explore_persona_space.orchestrate.preflight'`; discard with `python scripts/pod.py terminate --issue <N>[ --name-suffix <slug>]` (reuse the existing keep-branch suffix-hint logic so an issue-wide destroy is never suggested for a suffixed pod, #1334).
    2. `PREFLIGHT: FAIL rc=78 (mapped sentinel code; raw preflight rc in the PREFLIGHT-FAILED-AT-BOOTSTRAP log line)` (stderr).
    3. `BOOTSTRAP-FAILED pod={name} rc=78 reason=preflight` as the LAST stderr line (#1931 last-line contract preserved; compatible grammar superset).
    4. `sys.exit(EXIT_BOOTSTRAP_PREFLIGHT_FAILED)`.
    Deliberately NOT in this branch: `_teardown_failed_provision` (criterion 4 — direct-CLI pod kept alive), `_record_bad_placement_loud` (the pod booted, SSH'd, and bootstrapped — env-class failure, not placement-class; polluting the #2011 DC denylist would mis-steer rotation), and pods.conf row removal (the row is needed to ssh in and repair).
  - any other non-zero `rc` → the existing branch VERBATIM (keep-flag messaging, bad-placement record, #2060 teardown, `BOOTSTRAP-FAILED ... rc=<rc>` last line, `sys.exit(rc)`).
- `PREFLIGHT: PASS|FAIL` line placement rationale: emitted by the provision tail (the caller-facing summary), satisfying criterion 2 without changing `_bootstrap`'s streaming contract.

### Change 3 — `src/explore_persona_space/backends/runpod.py` (`launch`): scoped rc-78 disposition (critic Must-Fix 1)

Without this, a router-dispatched provision exiting 78 leaves a RUNNING, registered, broken-venv pod billing with no handle and no workload: the `PodLifecycleProcessError` raises AT the relay call (~1443), BEFORE the #2038 `try:` (~1475), so `_dispose_post_provision_failure` never fires; at the terminal rung the error additionally falls into the generic branch (`router.py` ~4345) as watcher-re-drivable `no_compute_available`, so capacity retries would re-dispatch against a live same-named `pod-<N>` (arming the #1997 exit-76 collision after a later reconcile-stop).

Fix (the critic's option (a), minimal and localized):

- Wrap the provision relay call in `launch` with a catch for `PodLifecycleProcessError` where `returncode == EXIT_BOOTSTRAP_PREFLIGHT_FAILED` (import the constant from `scripts/pod_lifecycle.py` the same way other cross-file exit codes are mirrored — or mirror it as a module constant with the parity test extended to three files; implementer's choice, parity-pinned either way):
  1. Resolve the pod id via the existing `_provisioned_pod_id(pod_name)` round-trip — registration HAS happened on the rc-78 path (the row is written before bootstrap), so it resolves.
  2. Best-effort exact-id terminate via `_terminate_just_provisioned(pod_id=..., pod_name=..., issue=..., cause="bootstrap preflight failed (exit 78): pod venv/env not experiment-ready; autonomous dispatch has no operator to repair — #2038-family disposition, task #2606")`. NEVER raises (existing contract); a teardown failure logs loudly and must not mask the original error (reuse the existing mask-guard shape pinned by `tests/test_issue2038_fallback_teardown.py`).
  3. Re-raise the ORIGINAL `PodLifecycleProcessError`.
- Named residual (recorded, accepted): the re-raised error still lands in the generic terminal-rung branch as re-drivable `no_compute_available`. This is SAFE post-teardown — the pod is gone, so a watcher capacity re-drive retries a fresh provision (no collision, no billing leak), which is also the right medicine for a transient host fault (the ESTALE class). Introducing a typed non-re-drivable error is the named escalation if re-drives are ever observed churning on a persistent preflight failure; not in this task's scope.
- Direct-CLI behavior is UNTOUCHED by Change 3 (the catch lives in `launch`, which only the router path executes).
