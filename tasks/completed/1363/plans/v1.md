## 2. Prior work / method delta

- **Thread caps lineage:** #847 (env.py setdefault, VM-only), #891 (explicit launch-prefix mandate + the `check_vm_thread_cap_guidance` count-floor lint after a stale worktree ran 78 uncapped threads), #811 (relaunch pin parity), #833/#957/#1045 (detached launch + choom recipe). The prefix is already the single canonical VM-launch string; this change extends it by one token.
- **glibc semantics (man `mallopt(3)`, glibc tunables manual — `glibc.malloc.arena_max`):** glibc malloc creates per-thread arenas on lock contention; on 64-bit the arena limit defaults to **8 × number of cores** once `M_ARENA_TEST` (8 on 64-bit) arenas exist. Freed chunks in non-main arenas are retained in per-arena heaps rather than returned to the OS, so a multi-threaded allocate/free workload fragments across arenas and RSS ratchets upward with no single large live allocation. `M_ARENA_MAX` is settable via the `MALLOC_ARENA_MAX` environment variable (documented in `mallopt(3)` ENVIRONMENT and as the `glibc.malloc.arena_max` tunable), read **once at malloc initialization** — i.e. at process startup, before any Python code executes. This is why the launch-time env prefix is the correct mechanism and why an in-process `os.environ.setdefault` in `orchestrate/env.py` could NOT retrofit it for the current process (it would only help subprocesses; that is a `src/` change and out of scope here — noted, not filed, this session is under the workflow-fix recursion guard).
- **Incident evidence (#1315, 2026-07-15):** a VM-side batched Gram-eigh bootstrap with ≤tens-of-MB per-pass tensors grew 20–21.7 GB RSS across ~7–9 passes under the 8-thread caps and was earlyoom-SIGTERMed twice; `MALLOC_ARENA_MAX=2` held the identical workload at ~1 GB. Record: `.claude/agent-memory/analyzer/feedback_malloc_arena_vm_fits.md` + `tasks/interpreting/1315/events.jsonl` (analyzer r1 candidate, fingerprint `77ca2f4f987d`).

## 5. Kill criteria

- **Allocation-contention regression:** `MALLOC_ARENA_MAX=1` would funnel all threads through one arena lock; **2** keeps a second arena for concurrent malloc while capping fragmentation, and is the value #1315 actually validated (~1 GB vs 20 GB, no slowdown recorded). BLAS/torch hot loops allocate workspaces per-call, not per-iteration, so arena-lock contention at 2 is negligible for this phase class. If a future workload measurably serializes on allocation, the existing strongest-last override semantics apply (explicit env at launch overrides the prefix) — that is a per-launch tune, not a reason to kill this default. Kill only if evidence emerges that `MALLOC_ARENA_MAX=2` breaks or materially slows a canonical VM phase class (none known; the incident evidence points the other way).
- **Lint coupling breaks unrelated flows:** if extending `_VM_THREAD_CAP_PREFIX` FAILs the no-flags lint on files outside this diff's control, stop and re-scope (not expected: the literal is counted only in the 4 pinned files, all edited here).
