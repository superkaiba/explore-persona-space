# Plan v2 — #2205: verify_plan c46 enforces the launch exactly-one-of runtime rule

## 1. Requirement + acceptance criteria

`scripts/verify_plan.py` check c46 (`check_dispatch_cmd_cli_parse`, WARN-only, all kinds)
dry-parses plan-embedded `dispatch_issue.py` commands against the live argparser but does
NOT evaluate the launch subcommand's POST-parse runtime requirement — exactly one of
`--workload-cmd` / `--hydra` (`scripts/dispatch_issue.py` lines ~3608–3620, #588). Two
incidents (#2202 2026-08-08, #2254 2026-08-13) embedded provision-only launch commands
that c46 + the fact-checker dry-parse-PASSed and the runtime then refused rc=2.

Acceptance criteria (from the task body):

- **AC1** — c46 WARNs when a plan-embedded `dispatch_issue.py launch` command parses but
  violates the exactly-one-of `--workload-cmd`/`--hydra` rule; an explicitly-empty
  `--workload-cmd ''` counts as not provided. Both-provided also WARNs (mirrors the
  runtime's `got both` branch).
- **AC2** — unit tests in `tests/test_verify_plan.py`: the #2202 v2 command shape WARNs;
  a compliant `--workload-cmd`-bearing command stays PASS (existing
  `test_c46_passes_on_corrected_command` already covers it); a compliant `--hydra`-only
  command stays PASS (new).
- **AC3** — no behavior change for the `finalize` subcommand or non-dispatch fences
  (explicit non-regression test).
- **AC4 (optional arm, in scope)** — an explicit `--backend runpod` launch carrying a
  non-empty `--workload-cmd` but no `--execute-workload` gets an FYI **note** (rides the
  detail string, NEVER flips the verdict to WARN) — the workload would otherwise not
  auto-start on the runpod lane (#763/#909). CONDITIONAL: the implementer first verifies
  in `dispatch_issue.py` that the runpod leg indeed does not execute the workload without
  `--execute-workload`; if that reading fails, DROP this arm (it is optional in the task
  body) and say so in the implementation marker.

## 2. Method delta

c46's existing drift arms (#2161) are TOKEN-level (`_c46_has_flag`). The new arm is
NAMESPACE-level: `_c46_drift_arms` already computes `ns, err = _c46_dry_parse(parser,
argv)`; when `ns is not None and getattr(ns, "action", None) == "launch"`, re-evaluate
the runtime rule on the parsed namespace exactly as `dispatch_issue.py` does:

```python
has_workload_cmd = bool((getattr(ns, "workload_cmd", None) or "").strip())
has_hydra = bool(getattr(ns, "hydra", None))
if has_workload_cmd == has_hydra:
    arms.append(...)
```

Namespace-level (not token-level) so empty-string values, `--flag=value` forms, and
append-action `--hydra` follow argparse semantics byte-for-byte — zero drift from the
runtime rule's own inputs. When `ns is None` (does-not-parse), arm 1 already fires and
the new arm is skipped (the incident class is parses-but-refused, which always has `ns`).

  restructure since #588), the namespace mirror is unbuildable → fall back to
  token-level detection (`_c46_has_flag` + value inspection) and note the deviation.

  arm's trigger breadth before mass-editing expectations (would indicate legitimate
  provision-only embeds exist — they do not, per the runtime's unconditional refusal,
  so this is a tripwire, not an expected path).
