## 4. Design

### 4.1 Option decision: hybrid (A primary + minimal B), with rationale

- **Option A (runtime guard in hub.py) is the primary enforcement**: it computes the EXACT staged count per EXACT target dir (something no static check can), costs milliseconds, and fires at the earliest point that knows the real tree — the upload call — which is still BEFORE any network I/O (vs the status quo: after the full compute AND full staging).
- **Option B as literally proposed ("flag upload_folder call sites lacking a documented per-dir sharding strategy") is rejected** — "has a sharding strategy" is not statically decidable and would be all false positives or all exemptions.
- **A precise, narrow B variant is kept**: the #658 incident's own call path was a per-issue script using `HfApi` directly — it would have BYPASSED a hub-only guard entirely (grep: ~15 direct `api.upload_folder(` call sites across ~11 `scripts/issue*.py` files today). The lint's job is only to FUNNEL: a direct `upload_folder` call site in `scripts/` must either reference the one-line guard helper, carry an exemption comment, or be on the grandfathered legacy allowlist. This is the same funnel-to-the-guarded-helper role `--check-upload-as-file` plays for `_upload`.

### 4.2 Runtime guard — new code in `src/explore_persona_space/orchestrate/hub.py`

New module-level constants + exception + helpers (placed near the existing `_filecount_fallback_enabled` block, ~L675):

```python
# Per-DIRECTORY commit cap enforced server-side by the Hub (#658 r2: a commit
# staging 12000 siblings into one dir 400'd "too many files ... up to 10000";
# huggingface/datasets#7956 confirms the per-directory rejection). DISTINCT
# from the repo-wide 100k git-file cap (#1108, _is_file_count_limit_error).
HUB_DIR_FILE_LIMIT = 10_000
# Advisory watermark = the gotchas.md shard recipe (shard_NNNN/ of <=5000).
HUB_DIR_FILECOUNT_WARN = 5_000


class HubDirFileCountError(ValueError):
    """A single upload_folder commit would stage more files into one repo
    directory than the Hub's server-side cap accepts (#658/#1190)."""


def _dir_filecount_guard_enabled() -> bool:
    """Default-ON kill switch. EPM_SKIP_HF_DIR_FILECOUNT_GUARD=1 degrades the
    raise to a logged WARNING so the guard can never wedge a deliberate
    upload (mirrors the EPM_SKIP_* degrade-to-warn family)."""
    return os.environ.get("EPM_SKIP_HF_DIR_FILECOUNT_GUARD", "0") != "1"


def count_staged_files_per_repo_dir(
    folder_path: Path,
    path_in_repo: str,
    *,
    allow_patterns: list[str] | None = None,
    ignore_patterns: list[str] | None = None,
) -> dict[str, int]:
    """Count the files ONE upload_folder commit would stage, keyed by TARGET
    repo directory (path_in_repo prefix + relative subdir). Pure-local
    (Path.rglob + huggingface_hub.utils.filter_repo_objects — the library's
    OWN client-side filter, so allow/ignore semantics match what
    upload_folder will actually stage). No network."""
    from huggingface_hub.utils import filter_repo_objects

    rels = [
        p.relative_to(folder_path).as_posix()
        for p in folder_path.rglob("*")
        if p.is_file()
    ]
    # Parity with upload_folder's own default excludes (.git/ etc.).
    # Fact-checked on the pinned 0.36.2: the constant lives at
    # huggingface_hub.utils (utils/_paths.py:25, a list of 8 patterns), NOT
    # huggingface_hub.constants (that import ERRORS); upload_folder itself
    # applies it (hf_api.py:4901). try/except kept only as future-version
    # drift defense (fallback direction: over-count, the safe side).
    try:
        from huggingface_hub.utils import DEFAULT_IGNORE_PATTERNS
        ignore = list(DEFAULT_IGNORE_PATTERNS) + list(ignore_patterns or [])
    except ImportError:
        ignore = list(ignore_patterns or [])
    counts: dict[str, int] = {}
    prefix = path_in_repo.strip("/")
    for rel in filter_repo_objects(rels, allow_patterns=allow_patterns, ignore_patterns=ignore):
        repo_dir = posixpath.dirname(posixpath.join(prefix, rel) if prefix else rel)
        counts[repo_dir] = counts.get(repo_dir, 0) + 1
    return counts


def assert_hub_dir_filecounts(
    folder_path: Path | str,
    path_in_repo: str,
    *,
    allow_patterns: list[str] | None = None,
    ignore_patterns: list[str] | None = None,
    limit: int = HUB_DIR_FILE_LIMIT,
    warn_at: int = HUB_DIR_FILECOUNT_WARN,
) -> dict[str, int]:
    """Fail loud BEFORE staging when any target repo dir would receive
    > limit files in one commit. Returns the per-dir counts (for logging /
    tests). Public — direct HfApi.upload_folder callers in scripts/ call
    this one-liner before their upload (the --check-hub-dir-filecount lint
    funnels them here). STAGED-ONLY: files already ON the repo dir are not
    counted (documented residual — see docstring in full impl)."""
    counts = count_staged_files_per_repo_dir(
        Path(folder_path), path_in_repo,
        allow_patterns=allow_patterns, ignore_patterns=ignore_patterns,
    )
    offenders = {d: n for d, n in counts.items() if n > limit}
    if offenders:
        worst_dir, worst_n = max(offenders.items(), key=lambda kv: kv[1])
        msg = (
            f"upload would stage {worst_n} files into repo dir '{worst_dir}' "
            f"({len(offenders)} dir(s) over the Hub's {limit}-files-per-directory "
            f"commit cap — a NON-retriable BadRequestError at create_commit, #658). "
            f"Re-shard into shard_NNNN/ subdirs of <= {HUB_DIR_FILECOUNT_WARN} files "
            f"with a manifest (see .claude/rules/gotchas.md 'HF Hub rejects any "
            f"single repo directory holding >10000 files'). Deliberate override: "
            f"EPM_SKIP_HF_DIR_FILECOUNT_GUARD=1."
        )
        if _dir_filecount_guard_enabled():
            raise HubDirFileCountError(msg)
        logger.warning("EPM_SKIP_HF_DIR_FILECOUNT_GUARD=1 set — proceeding despite: %s", msg)
    elif any(n > warn_at for n in counts.values()):
        big = {d: n for d, n in counts.items() if n > warn_at}
        logger.warning(
            "upload stages >%d files into repo dir(s) %s — above the recommended "
            "shard size (cap is %d/dir; consider shard_NNNN/ now, gotchas.md).",
            warn_at, big, limit,
        )
    return counts
```

### 4.3 Guard behavior decision: LOUD raise, not auto-shard

Raise-with-recipe-message, never auto-shard. Auto-sharding silently rewrites the repo LAYOUT downstream readers resolve (`shard_NNNN/` needs a manifest + reader-side resolution — a workload-specific contract, per the #658 salvage), which is a behavior change no shared helper should make implicitly; and the project fail-fast rule says the crash is the signal. The value-add over the status quo is WHERE the crash fires: at the upload call, before staging/network — and, via the lint + the error message, ideally at development time before the workload ever runs. The kill switch covers the "I really mean it" case (e.g. HF raises the cap before we do).

### 4.4 Staged-only vs remote-count decision

v1 counts STAGED files only. Rationale: (a) the demonstrated incident shape (#658) is one commit staging >10k siblings — staged-only catches it exactly; (b) a remote count needs a scoped `list_repo_tree` per target dir on EVERY upload — on the ~1M-file data repo that risks 504s and burns the ~2500-req/5-min org quota (both documented gotchas), which is unacceptable for a guard that must be cheap and safe; (c) whether the Hub rejects a dir crossing 10k CUMULATIVELY across commits (6k remote + 5k staged) is unverified server behavior (#658's per-file-upload evidence is ambiguous on this). The residual — pre-existing remote files pushing a dir over the cap — is documented in the guard docstring and in the gotchas.md enforcement sentence (§4.6). If it ever fires in practice, the server's own BadRequestError remains the (late) backstop, exactly as today.

## 5. Controls → False-positive analysis (infra substitute)

| Scenario | Would the guard fire? | Wedge risk & mitigation |
|---|---|---|

## 11. Decision Rationale

- **Raise threshold = strictly >10,000 staged files per target dir.** Why: the server cap. Source: #658 r2 incident ("too many files ... up to 10000"; salvage commit `614284bd3f`) + HF storage-limits docs + huggingface/datasets#7956 ("Your push was rejected because it contains too many files per directory"). Alternatives: ≥10,000 (rejected — "up to 10000" implies 10,000 legal; off-by-one conservatism buys nothing), a lower hard cap (rejected — would fail uploads the server accepts).
- **Warn watermark = >5,000.** Why: the documented shard recipe ("shard to ≤5000, leaves headroom"). Source: `.claude/rules/gotchas.md` #658 entry (landed via #748). Alternatives: no watermark (rejected — the warning is the cheap nudge to shard BEFORE hitting the cap on a growing store); 8,000 (no grounding).
- **Raise-with-recipe vs auto-shard.** Why: auto-sharding silently changes the repo layout readers resolve (manifest + reader contract is workload-specific, per the #658 salvage), and the project fail-fast rule bars silent behavior changes in a shared helper. Source: CLAUDE.md fail-fast rule; #658 salvage design (`--resume-upload-from-store`, commit `614284bd3f`). Alternatives: auto-shard (rejected as a v1 behavior change needing its own design), warn-only (rejected — repeats the "documented but not enforced" failure the task exists to close).
- **Staged-only vs remote count.** Why: catches the demonstrated incident shape at zero network cost; remote listing per upload risks 504s/quota burn on the ~1M-file repo. Source: #658 shape; gotchas.md `list_repo_files`/504 + 2500-req/5-min entries. Alternatives: scoped `list_repo_tree` per target dir (rejected v1 — cost/risk on every upload for an unverified server behavior), opt-in remote check flag (deferred; note in guard docstring).
- **Kill switch = `EPM_SKIP_HF_DIR_FILECOUNT_GUARD=1`, degrade-to-WARN.** Why: a guard must never wedge a legitimate/deliberate upload; degrade (not silent skip) keeps the signal in the log. Source: repo convention — `EPM_SKIP_INLINE_CHECKPOINT_UPLOAD`, `EPM_PREFLIGHT_DISK_FLOOR_OVERRIDE` (degrades FAIL→WARN), `EPM_HF_FILECOUNT_FALLBACK=0` (`hub.py` L675–689). Alternatives: `EPM_HF_DIR_FILECOUNT_GUARD=0` (equivalent; SKIP form chosen to match the brief + the override family semantics).
- **Hybrid (runtime + narrow lint) vs runtime-only.** Why: the incident's own call path was a DIRECT `HfApi` user in `scripts/` that bypasses hub.py — runtime-only would not have prevented #658; the lint funnels future direct callers to the one-line guard. Source: fact-checker full grep (≈70 direct call sites / ≈40 files — corrected from the planner's truncated ~15/~11 count); `check_upload_as_file` precedent (L4012) for the funnel pattern. Alternatives: runtime-only (rejected — leaves the incident shape open), the task body's literal "lacking a documented sharding strategy" lint (rejected — statically undecidable, all-FP).
- **Lint granularity = module-level guard reference + call-site waiver + legacy allowlist.** Why: lowest-complexity precise form; per-call-site dataflow would be high-effort/medium-FP. Source: `check_judge_model_pins` legacy-allowlist precedent (llm-judging.md § Enforcement); `check_upload_as_file` waiver convention. Alternatives: same-function granularity (deferred tightening), exemption-commenting the 11 existing files (rejected — experiment code is out of workflow-fix scope).
- **Guard placement before `HfApi` construction, outside try.** Why: zero network before verdict; the enclosing `except Exception → return ""` would otherwise swallow it. Source: the #595 guard precedent at `hub.py` L1028–1033 (raises pre-try). Alternatives: inside try (rejected — silently converts to return "").
- **Count with `filter_repo_objects`.** Why: exact parity with `upload_folder`'s own client-side staging filter; zero reimplementation drift. Source: live-executed this session (`huggingface_hub` 0.36.2, signature + nested-path match verified). Alternatives: hand-rolled fnmatch (rejected — the drift IS the false-positive risk).

## 13. Kill criteria

- **HF removed or raised the per-directory limit** (implementer finds current docs/issue evidence contradicting A1): stop, downgrade the guard to warn-only or re-threshold, and update gotchas.md instead — the enforcement premise is gone.

- **Lint cannot pass the live tree without STRUCTURAL exemptions beyond the frozen grep-generated legacy allowlist** (waivers needed inside live shared modules, or allowlist churn on unrelated merges): drop the lint component (runtime-only ships; the Goal's "or" is satisfied) rather than shipping a noisy check. A LARGE (~40-entry) but frozen, grep-generated, live-tree-test-pinned allowlist is explicitly acceptable — the earlier >~20-entry trigger was calibrated on the wrong census (§12 A8) and is superseded.
