## 3. Method delta (exact behavior change)

| Situation (crash path, persist runs to completion) | Today | After #1343 |
|---|---|---|
| ≥1 upload client-confirmed, probe True | `ok` | `ok` (unchanged) |
| ≥1 upload client-confirmed, probe False/error | `ok` | `ok` (client-confirmed commit = landed, #1339 inverse; also covers probe lag/transport) |
| ZERO uploads client-confirmed, probe True | `ok` | `ok` (the #1339 forward direction: client logged FAILED but the commit LANDED — the probe positively verifies it) |
| ZERO uploads client-confirmed, probe False/error (**the #1315 shape**) | **`ok` (dishonest)** | **`failed_uploads` (rc 3)** |
| timeout / uv missing / cd fail / python crash / killed mid-flight / no token / missing rc file | `timeout` / `failed_rc<N>` / standing `attempted` / `skipped_no_token` / nothing | byte-identical (untouched) |

**The honesty predicate (design core):** `ok ⇔ (probe is True) OR (client_confirmed_uploads ≥ 1)`; else exit 3 → `failed_uploads`.

Justification per cell: the probe is the strongest evidence (positively verifies the highest-value audit artifact on the Hub, and rescues the client-FAILED-but-landed case). The client-confirmed-commit OR-arm is justified by #1339's asymmetry — a client FAILURE is unreliable, but a client SUCCESS means the commit response was delivered, i.e. the commit is durable server-side — and it is what protects against the probe's own two failure modes (transient probe transport error; read-after-commit lag on the just-uploaded final bundle). Requiring probe-True alone would convert probe flakiness into false `failed_uploads` on healthy persists — a new dishonesty channel in the opposite direction. Zero-and-zero is exactly "nothing verifiably landed" — the Goal's condition for NOT claiming `ok`.

**Degenerate cell (named residual):** if the persist finds literally nothing to stage anywhere (requires the transcript tee to /tmp to have failed too — near-impossible since `_say("[crash-persist] BEGIN ...")` writes it first), zero uploads are even attempted → `failed_uploads`. This is the honest reading for the status's consumer question ("is anything recoverable on HF?" — no). **Second named residual:** a same-boot re-crash reuses the same `dest` (attempt-scoped), so a probe True can reflect the PRIOR crash's transcript — `ok` then states prefix-level recoverability, not per-crash upload success; acceptable for the recovery use-case, documented in the decision table row.
