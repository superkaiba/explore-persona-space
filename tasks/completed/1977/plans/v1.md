# Plan v1 — task #1977: exempt path-limited `git add --all -- <pathspec>` in guard_root_code_commit.sh

ARCHITECTURAL: no (guard-hook behavior refinement; no public contract, no marker schema, no status enum change).

## 1. Requirement + acceptance criteria

**Requirement.** `.claude/hooks/guard_root_code_commit.sh` currently latches `add_all_chained=1` on the bare tokens `-A` / `--all` / `.` in any add clause (token-scan arm, L678) and blocks at L1121 with "the landing set cannot be classified at hook time". For the path-limited form `git add --all -- <explicit pathspec>` that rationale does not apply: the pathspec bounds the landing set, and git can enumerate it at hook time. Two sessions (#1895, #1945) composing exactly this form (sweeping status-move residue incl. deletions under known paths) were blocked and had to recompose.

**Acceptance criteria:**
1. `git add --all -- <clean explicit pathspec(s)> && git commit -m x` at the repo root is NO LONGER blocked by the blanket-staging arm — it instead flows into Layer-2 classification with the add's would-be landing set fully enumerated per file.
2. Bare blanket forms (`git add -A|.|--all` with no `--`-anchored pathspec, or with any opaque/unsafe pathspec token) still block byte-for-byte (existing B13 semantics unchanged).
3. The exemption opens NO unclassified staging channel: every gated file the path-limited add would stage (modified, untracked, renamed-in) enters `pending` and the cert check; deletions stay exempt via the existing `landing_sha` rc=1 path.
4. FAIL-CLOSED bias preserved: any ambiguity (masked/quoted tokens, pathspec magic, git read failure, unparseable porcelain) keeps the block.

## 2. Method delta

Prior state: unconditional latch on the blanket token; no add-clause pathspec awareness. Delta: (a) per-add-clause position-aware post-scan (pre-`--` blanket token vs post-`--` pathspec candidates), reusing the #1620 second-token-pass idiom already present for commit clauses; (b) a Layer-2 scoped git read that resolves the add pathspecs to per-file worktree changes and feeds them into the existing `text_paths` channel (which already carries the worktree-content binding and the deletion exemption via `landing_sha`, and already unions into `pending`). No new parser; no change to the mask/split machinery.

## 3. Design (concrete diffs — refine at implementation)

### 3a. Layer 1 (`classify_cmd`), token scan region ~L660-700

Replace the unconditional latch with clause-scoped state. For each clause with `verb=add`:

```
- add:-A | add:--all | add:.) add_all_chained=1 ;;
+ add:-A | add:--all) add_blanket=1 ;;          # pre-`--` blanket flag
+ add:.) if [ "$add_after_ddash" = 0 ]; then add_blanket=1; else add_pspec_opaque=1; fi ;;
```

plus, in the same per-token loop (add clauses only):
- track `add_after_ddash` (set on the `--` token, reset per clause);
- post-`--` tokens are pathspec candidates: REJECT (set `add_pspec_opaque=1`) any token that is masked (`*"$FILL"*`), quote/backslash-bearing, contains `$` / backtick / parens / `<` / `>`, leads with `~` or `:` (pathspec magic) or `/` (absolute) or `-` (flag-shaped), or is exactly `.` / `..`; plain glob tokens (`* ? []`) stay clean (git evaluates them — mirrors `classify_candidate`);
- clean candidates accumulate into a clause-local list.

At clause end (add clauses with `add_blanket=1`):
- `--` seen AND ≥1 clean candidate AND `add_pspec_opaque=0` → do NOT latch `add_all_chained`; append the candidates to a new global `add_pathspecs` (newline-separated, initialized in `classify_cmd`'s global reset line L544).
- otherwise → `add_all_chained=1` (today's behavior, including `git add --all <paths>` WITHOUT `--`: the exemption is `--`-anchored only).

Note the existing `add:` arms currently key pre/post-`--` blind; the implementer may instead restructure as a small dedicated post-scan for add clauses (the commit clause's second pass at L700+ is the template) if that is cleaner than in-loop state — either is acceptable so long as the scan stays clause-scoped and runs on the MASKED tokens.

### 3b. Layer 2, at the L1121 block site

```
 if [ "$add_all_chained" = 1 ]; then
   echo "BLOCKED: ... Stage by explicit path (or use the sanctioned path-limited form: git add --all -- <explicit paths>), run the inline payload lint gate ..." >&2
   exit 2
 fi
+# Path-limited `add --all -- <pspecs>` (issue #1977): resolve the add's
+# would-be landing set at hook time and feed it into classification.
+if [ -n "$add_pathspecs" ]; then
+  mapfile -t apspecs < <(printf '%s\n' "$add_pathspecs" | grep -v '^$')
+  if add_status=$(git -C "$GUARD_REPO" status --porcelain=v1 --untracked-files=all -- "${apspecs[@]}" 2>/dev/null); then
+    # Fail CLOSED on any C-quoted (special-char) path in the output.
+    case "$add_status" in *'"'*) <block, same message + a quoted-path diag> ;; esac
+    # Extract per-file paths: `XY path`; rename lines `XY old -> new` contribute
+    # BOTH sides (old = deletion → landing_sha exempts; new lands content).
+    # Append every extracted path to text_paths (worktree binding + pending
+    # union both follow from existing machinery).
+  else
+    <block: git read failed — cannot classify the path-limited add; fail CLOSED (same shape as the staged-read failure block)>
+  fi
+fi
```

The `text_paths` append is the whole classification hook-up: `pending` already unions `text_paths` (L1168) and filters by `GATED_PATH_ERE`; `landing_sha` already gives text_paths members the WORKTREE binding and the deletion exemption. Dir/glob pathspecs (`scripts`, `scripts/*`) resolve to per-file paths via the git read, so `GATED_PATH_ERE`'s per-file shape is satisfied — no unclassified dir channel.
