**Edit A — Guard-3 unsafe-path apply-verification (Problem 1) — RESTRUCTURED to gate push on verify (methodology-critic Must-Fix).**

Target site: the surgical additive checkout block, inside the existing `if [ "$GATE_VERDICT" = "pass" ]; then` arm — REPLACE the current three lines (SKILL.md ~11862-11866 at HEAD):

```bash
    xargs -r -a /tmp/issue-<N>-additive-files.txt git add --
    git diff --cached --name-only   # sanity echo: spot any foreign staged entries
    xargs -r -a /tmp/issue-<N>-additive-files.txt git commit -m "issue-<N>: surgical additive checkout (full rebase deferred — guard 3)

  Branch unsafe to blind-rebase: <based on <PARENT> (not on mainline) |
  own commits touch foreign / out-of-scope paths>. Cherry-picked this
  task's own added files only; shared src/ / scripts/ unchanged." --
```

...WITH:

```bash
    xargs -r -a /tmp/issue-<N>-additive-files.txt git add --
    git diff --cached --name-only   # sanity echo: spot any foreign staged entries
    xargs -r -a /tmp/issue-<N>-additive-files.txt git commit -m "issue-<N>: surgical additive checkout (full rebase deferred — guard 3)

  Branch unsafe to blind-rebase: <based on <PARENT> (not on mainline) |
  own commits touch foreign / out-of-scope paths>. Cherry-picked this
  task's own added files only; shared src/ / scripts/ unchanged." --
    # PARTIAL-APPLY VERIFICATION (this task's Edit A): the branch's own ADDED
    # files were just staged from the branch tip and committed. Confirm — by
    # materialize-then-check — that every claimed additive path landed with
    # content byte-identical to its branch-tip source. The commit message
    # above asserts a "cherry-picked" apply; verify the assertion before
    # recording `landed`. Any path whose committed content diverges from its
    # branch-tip source is a PARTIAL apply (incident 3c24493113, 2026-07-05:
    # an orchestrator-improvised recovery outside the documented paths
    # landed the test file but not the extractor half it tested; main red
    # 20 days until #1683 ported it). Edit A adds the guarantee to the
    # CURRENT documented template; a future improvised apply is out of
    # scope here (workflow_lint follow-up).
    # xargs feeds paths one-per-line (whitespace/glob-safe, matches the
    # block's convention); stderr is retained so a producer failure
    # surfaces its cause. The PUSH block below is now gated on
    # $APPLY_OK — a partial apply short-circuits it (methodology-critic
    # Must-Fix: bare `false` at the end of an if-branch does NOT halt
    # subsequent commands in the enclosing block, so a variable-gated
    # conditional is required).
    APPLY_OK=yes
    if ! xargs -r -a /tmp/issue-<N>-additive-files.txt \
         git -C "$REPO_ROOT" diff --name-only HEAD "issue-<N>" -- \
         > /tmp/issue-<N>-postapply-diff.txt; then
      echo "PARTIAL-APPLY VERIFY: diff HEAD vs issue-<N> FAILED — cannot certify apply; refusing to record landed"
      echo partial-apply-verify-failed > /tmp/issue-<N>-surgical-outcome.txt
      APPLY_OK=no
    elif [ -s /tmp/issue-<N>-postapply-diff.txt ]; then
      # Non-empty diff = one or more claimed paths were NOT byte-identically
      # applied. Fail LOUD — a claimed clean apply that did not land is the
      # 3c24493113 shape.
      echo "PARTIAL-APPLY VERIFY: $(wc -l < /tmp/issue-<N>-postapply-diff.txt) claimed additive path(s) diverge from their branch-tip source:"
      cat /tmp/issue-<N>-postapply-diff.txt
      echo "The 'surgical additive checkout' commit above does NOT reflect all claimed content; recording partial-apply outcome, NOT landed."
      echo partial-apply > /tmp/issue-<N>-surgical-outcome.txt
      APPLY_OK=no
    fi
    # Bounded push (the one network op on this arm): a hung push would wedge
    # the background call with the outcome sentinel unwritten. rc 124 takes
    # the push-failed arm — the same degradation as a rejected push (the
    # "Surgical checkout itself fails" bullet / sync-retry below).
    # GATED on APPLY_OK: a partial-apply outcome above short-circuits the
    # push and its `landed` sentinel; the enclosing background call still
    # exits non-zero via the `false` at the end of the else arm.
    if [ "$APPLY_OK" = "yes" ]; then
      if timeout --kill-after=30s 300s git push origin main; then
        echo landed > /tmp/issue-<N>-surgical-outcome.txt
      else
        echo push-failed > /tmp/issue-<N>-surgical-outcome.txt
        false
      fi
    else
      false   # partial-apply / verify-failed sentinel already written above
    fi
```

Then extend the outcome-sentinel switch/case in the completion-read (SKILL.md ~lines 11889–11908) to add two new outcomes:

- `partial-apply` → post `epm:merge-failed v1` with `{reason: "surgical additive checkout — partial apply", diverged_paths: [...]}`, name the diverged files in ONE chat line, CONTINUE (idempotent retry on next `/issue <N>`). The task still parks per the standard failure path.
- `partial-apply-verify-failed` → post `epm:merge-failed v1` with `{reason: "surgical additive checkout — apply-verification diff producer failed"}`, name the branch + worktree in ONE chat line, CONTINUE.

The `git -C "$REPO_ROOT" diff --name-only HEAD "issue-<N>" -- <paths>` invocation matches the block's existing `-C "$REPO_ROOT"` invocations. Reads a branch ref that already exists on the local root (`origin/issue-<N>` was pulled by the safe-case push retries; local `issue-<N>` is what the surgical checkout READS FROM in the `xargs ... git checkout issue-<N> --` above the block).

Idiom fixes vs v1 (statistics-critic C2 + methodology idiom Concern + consistency-checker WARNs 1&2):
- `xargs -r -a /tmp/issue-<N>-additive-files.txt ... git diff` instead of `$(cat ...)` (whitespace/glob-safe, matches the block's convention).
- No `2>/dev/null` on the diff producer — stderr surfaces on failure.

**Edit B — Unconditional pre-sync (Problem 2).**

Target site: the post-merge stale-task-folder guard's ENTRY (SKILL.md line ~11979, the first `if [ -z "$CANON" ]; then` arm's outer scope). Immediately BEFORE the `CANON=...` line, insert:

```bash
# PRE-SYNC (this task's Edit B): the local root routinely lags origin/main
# by a completed-status mv committed locally but not yet pushed (incident
# #1688, 2026-07-25 18:19:37Z: guard exit 1 with sync_repo_root.py fixing
# it in one attempt at ahead=8 behind=2). Run the sanctioned root sync
# UNCONDITIONALLY before the guard's canonical-folder check, so the
# guard's nonzero exit becomes reserved for genuine drift rather than the
# expected unpushed-mv state. sync_repo_root.py is single-flight
# flock-serialized (a concurrent sync returns exit 0 without re-syncing),
# so this call is idempotent and tolerant of in-flight state. Failure is
# NON-FATAL — the guard's own unpushed-mv pre-check (#1300) remains the
# fallback recovery if the sync did not fully converge.
uv run python "$REPO_ROOT/scripts/sync_repo_root.py" || \
  echo "post-merge guard pre-sync: sync_repo_root.py exited non-zero; guard's own unpushed-mv pre-check is the fallback"
```

Then the existing guard block runs unchanged. This ordering reversal:
- **REMOVES**: no code deleted.
- **ADDS**: one `sync_repo_root.py` call per merge form.
- **PRESERVES**: the guard's own unpushed-mv pre-check (#1300, lines ~12042-12070) as a fallback for the rare case where the pre-sync did not fully converge (e.g. another session's sync was in-flight and returned exit 0 without our push landing). The pre-check's 2-attempt recovery loop is now nearly always a no-op — expected — but binds when needed.
- **REWORDS**: no in-block prose reworded; the "unpushed-mv arm" text at #1300 lines ~12042-12070 stays factually correct (the pre-sync makes the arm rarely fire, but the arm's own diagnostic wording — "CANON absent from origin/main" — describes what the ls-tree read, not what caused it).

**No behavioral change to safe-case (`gh pr merge $MERGE_FORM`) path.** Edit A is scoped to the surgical additive checkout arm (form iii). Edit B fires after ANY merge form lands, but adds only one idempotent sync call.

### 8. Risks

1. **Edit A's diff producer could fail silently on an exotic path type.** Materialize-then-check with terminal-arm `APPLY_OK=no` mirrors the block's existing Guard-1 discipline. Any producer failure (bad ref, missing file, git error) sets `APPLY_OK=no` and short-circuits the push, never falls through to a false `landed`. The methodology-critic Must-Fix (v1's `false` didn't halt the push) is closed by v2's variable-gated conditional.
2. **Edit B could burden Step 10d wall-time.** `sync_repo_root.py` is fast on the common case (single-flight flock returns quickly if nothing to sync; a fresh sync is bounded by network + rebase). The added latency is ~seconds per merge form.
3. **The post-merge guard's `#1300` unpushed-mv pre-check now rarely fires.** Expected — the pre-check remains as documented backstop for the case where a concurrent session's in-flight sync returned exit 0 without our push landing.
4. **Edit A's diff producer relies on a local `issue-<N>` branch ref.** The worktree's checkout maintains this ref (Step 4's `bash scripts/new_worktree.sh` creates the branch); local `issue-<N>` is what the surgical checkout READS FROM in the `xargs ... git checkout issue-<N> --` above the fence. If a follow-on rework ever changed the fetch/checkout order, the ref might not exist; mitigate by using `HEAD` (which just got the surgical commit) vs the branch's local ref — but the current block's own `git checkout issue-<N>` invocation confirms the local ref is always present at this point.
5. **Alternatives-critic C1 (residual): the exact past incident's code path is no longer in SKILL.md.** Edit A is defense-in-depth for the CURRENT documented surgical-additive-checkout template. An ad-hoc improvised apply (like the one that produced commit 3c24493113) is not caught by this fix — closing that broader gap would need a `workflow_lint --check-apply-and-commit-verified` mechanization, noted as follow-up defense-in-depth and out of scope for this task.
