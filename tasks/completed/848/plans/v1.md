- `codex-code-reviewer.md` composes the Codex review prompt; it already instructs "Skip 'Step 4: Run / Verify Tests'" (lines 463–465) but never prohibits executing the implementer's smoke/launch commands — the companion runtime executed some of the #823 duplicate retries.

**Method (standard Unix practice, not papers — this is infra):**

- **TERM → grace → KILL escalation** is the POSIX/systemd-standard stop sequence; `timeout --kill-after` implements exactly it.
- **GNU `timeout(1)` as the direct parent** signals the command — and, in its default (non-`--foreground`) mode, *times out the command's children too* (verified live on this VM, coreutils 8.32: the man page states that only in `--foreground` mode "children of COMMAND will not be timed out", i.e. the default mode kills the process group). This is precisely the property the Bash TOOL timeout lacks.
- **`pgrep -f` self-match avoidance:** a pattern run via `bash -c` appears in the invoking shell's own cmdline, so `pgrep -f 'run_823.py …'` matches (and `pkill` would kill) the probing shell itself; the standard fix is a character-class bracket (`run_823[.]py`) so the pattern string no longer matches itself.

**Delta:** nothing exists today; this plan adds the requirement once, canonically, in the on-demand rule file (which auto-loads for any agent editing `scripts/**/*.py` / `src/**` via its `paths:` frontmatter — i.e. every implementer), with minimal pointers in the always-loaded agent specs.

**Discovered pre-existing breakage that gates this task:** `workflow_lint.py` (no-flags) currently exits **1** on main and `tests/test_workflow_lint_agent_spec_size.py::test_live_tree_passes` currently **FAILS**, because two grandfathered agent specs regrew past their #838 ratchet caps: `code-reviewer.md` 72,756 B > 72,000 cap (+756 B over) and `experiment-implementer.md` 53,121 B > 53,000 cap (+121 B over). #848 adds bytes to `experiment-implementer.md`, so it must trim that file below cap anyway; and #848's own Step 9c test-verdict cannot pass while `code-reviewer.md` is over cap, so a minimal trim-only remediation there is in scope (the lint's own remedy text: "trim it back (relocate per-scenario content to .claude/rules/, see #829)").

```markdown
### Kill-before-relaunch + `timeout`-bounded smokes (REQUIRED — every retry surface)

Applies to EVERY re-run of a smoke / launch / dispatch command — crash-fix
rounds, code-review revision rounds, and same-turn retries after a
timed-out or abandoned Bash call — on the shared VM and on pods alike. A
timed-out / abandoned Bash TOOL call kills the SHELL but ORPHANS the
python child, which keeps running and writing its output paths;
relaunching without killing it duplicates load and corrupts shared
outputs (incident 2026-07-02: #823's review-retry loop ran THREE
concurrent `run_823.py --phase 4 --smoke` instances — launched
23:48/23:51/00:02, SAME output paths, 64 threads each, ~1/3 of a
load-226 VM overload).

**Before ANY re-run, kill-and-confirm-dead:**

1. **Probe** — `pgrep -af 'run_823[.]py --phase 4'`. The pattern MUST be
   exact-invocation-scoped: script filename + the distinguishing args,
   with a `[.]` bracket so the probe's own shell cmdline cannot
   self-match. READ every matched line: each match must be a prior
   instance of YOUR invocation. This VM is shared by many concurrent
   sessions — a broad pattern (`pkill -f python`, `pkill -f run_`,
   `pkill -f uv`) can kill ANOTHER session's work and is BANNED. Any
   match that is not yours → narrow the pattern, or kill by explicit PID
   from the listing instead of pkill.
2. **Kill** — `pkill -TERM -f '<same pattern>'`; wait ~10 s;
   `pkill -KILL -f '<same pattern>' 2>/dev/null || true`.
3. **Confirm dead** — re-run the step-1 probe; relaunch ONLY when it
   returns nothing. A PID surviving SIGKILL: stop and report; never
   relaunch on top of it.
4. **Fallback (invocation string not distinctive)** — check no live
   process holds the smoke's output paths (`fuser -v <path>`), then kill
   by explicit PID. Weaker than step 1 (a writer that opens-writes-closes
   is invisible between writes) — prefer the cmdline probe when possible.

**Bound every smoke / local launch with `timeout(1)` as the DIRECT
parent:** `timeout --kill-after=30s <N>s uv run python ...`, sized so
`<N> + 30` ends ≥ 60 s BEFORE the Bash tool timeout (e.g. `510s` under
the standard 600 000 ms tool budget) — an abandoned smoke then
self-terminates instead of orphaning. Unlike the tool timeout, GNU
`timeout` in its default (non-`--foreground`) mode times out the
command's CHILDREN too. Residual gap: a grandchild that `setsid`s
escapes the group kill — step 1's probe before relaunch is the backstop.
```

- **TERM → KILL signal order, 10 s grace.** *What:* `pkill -TERM`, wait ~10 s, `pkill -KILL`. *Why:* give python `atexit`/flush handlers a chance; SIGKILL alone can strand half-written output files — the very corruption this rule prevents. *Source:* POSIX/systemd-standard stop escalation (`timeout --kill-after` implements the same); the 10 s value is **convention-grounded, not literature-pinned** — insensitive within [5, 30] s (smoke-scale python exits in <1 s after TERM; honest label: convention, no smoke-test needed since any value in range satisfies the recipe).
- **`--kill-after=30s`.** *What:* SIGKILL 30 s after the TERM that `timeout` sends at expiry. *Why:* heavier children (vLLM engine teardown is a known slow/wedgy path — `.claude/rules/gotchas.md` § vLLM worker-subprocess teardown) need more than the interactive 10 s. *Source:* `man timeout` semantics + the project's vLLM-teardown gotcha.
- **Default duration 510 s under the 600,000 ms tool budget; rule `<N> + 30 ≤ tool-timeout − 60 s`.** *What:* `timeout` must fire (and finish killing) strictly before the Bash tool timeout, else the tool kills the shell first and re-orphans the child, defeating the wrap. *Why the 60 s margin:* covers `uv run` startup + kill latency. *Source:* the two agent files' existing "generous timeout (up to 600000 ms)" guidance (the budget the wrap must nest inside); margin value is convention, insensitive.
- **`[.]` bracket in the pgrep pattern.** *What:* `run_823[.]py`, not `run_823.py`. *Why:* under `bash -c`, the pattern is in the probing shell's own cmdline — an unbracketed `pkill -f` kills the prober. *Source:* standard Unix pgrep/pkill idiom; the incident's near-miss cleanup motivates making it explicit.
- **Exact-invocation scoping (filename + distinguishing args) + read-every-match.** *What:* the pattern floor plus a mandatory human/agent read of each `pgrep -af` line before any kill. *Why:* shared multi-session VM — the blast radius of a broad pattern is another session's science (Kill criterion 1). *Source:* incident data (#823's own cleanup nearly hit concurrent work) + this project's shared-root concurrency rules.
