# Plan — #2152: Rule-26 judge pilot gate must exercise the same TRANSPORT as the wave it gates

### 0.0 TL;DR (plain English)

- **What I'll run:** No experiment — this is a code + rule-text fix. I'll teach the judge pilot gate (`judge_pilot_gate`) to run its ~200 test calls over the *same delivery path* (the slow-but-cheap Batch API vs the direct sync API) that the big production wave will use, because the two paths can fail differently. The caller tells the gate how the wave will dispatch; the gate forces the pilot onto that path, records which path both actually use, and fails loudly if they differ. I'll also make the gate fail when the pilot sees a high rate of API-side refusals — the exact failure that destroyed a third of #1739's 44,310-call wave after a pilot on the wrong path had passed.
- **What I expect:** All existing 14 caller scripts keep working unchanged (they just get a new warning that they didn't declare the wave's path); new offline tests pin the forcing, the recording, the mismatch failure, and the refusal-rate failure; the rule text (rules 26 + 28) now says transport is part of "the exact production instrument".
- **What would change my mind:** If reading the realized path back from the persisted judge output turns out to be unreliable (e.g. the routing record is missing in legitimate runs), I'd fall back to trusting the forced parameters instead of the read-back — the plan's design prefers the read-back precisely because it is ground truth, and the tests will tell us if that assumption breaks.

1. With a declared batch wave, the pilot dispatches on the Batch path (fake seam observes `threshold_base=0`) and the report records `wave_transport="batch"` + per-arm realized transport.

def _wave_routing(wave_n_calls, wave_threshold_base, wave_force_sync) -> RoutingDecision:
    """Compute the DECLARED wave's transport via the dispatcher's own pure routing rule."""
    tb = DEFAULT_THRESHOLD_BASE if wave_threshold_base is None else wave_threshold_base
    if wave_n_calls is None and not (wave_force_sync or tb == 0):

            f"wave transport is count-routed at threshold_base={tb}: declare wave_n_calls, "

        )
    return decide_route(
        wave_n_calls if wave_n_calls is not None else 1,
        threshold_base=tb, force_sync=wave_force_sync,
    )

### 11. Decision Rationale

`N/A — no model training` (no training hyperparameters). Load-bearing DESIGN choices, each with Source:

- **D1 — Mechanism: thread the wave's dispatch parameters into the gate (chosen) vs a small dedicated batch-path probe beside a sync pilot (rejected).** What/Why: the pilot's job is the DROP PROFILE, and the profile must be measured on the wave's transport — a side probe would be a second instrument whose draws feed none of the gate's parse-fail/truncation/refusal statistics, certifying the profile on the wrong path; a full pilot on the wave's transport is strictly more informative at the same or lower cost (Batch is 50% cheaper), and splitting the budget across two transports would halve per-arm draws and break the #2124 sizing arithmetic (51-draw floor). Cost: batch-pilot latency (minutes–hours turnaround) — accepted as the price of parity. The request-SHAPE probe niche is already served by the #763 forced-batch live smoke. Source: #2124 (sizing arithmetic), #763 gotcha (existing shape-probe), #1739 (the profile-on-wrong-transport miss). Alternatives: both (redundant — the threaded pilot IS a batch-path probe); probe-only (rejected: certifies shape, not profile).
- **D2 — The gate learns the wave's transport from a caller DECLARATION (`wave_n_calls`/`wave_threshold_base`/`wave_force_sync`) and computes the route via `decide_route`, never guessing.** Why: the gate cannot infer a future dispatch it does not perform; the declaration mirrors the wave's actual dispatch kwargs 1:1, and reusing `decide_route` (pure, test-pinned) means zero duplicated routing arithmetic. Source: task-body deliverable 3 + `judge_dispatch.py:454` (read).
- **D3 — Realized pilot transport is READ BACK from `save_raw["routing"]`, not assumed from the forced parameters.** Why: the persisted `RoutingDecision` is ground truth for what dispatched (OTPM scaling, cache hits, resume pinning can all surprise); "reports which transport the pilot ran" (deliverable 3) must be an observation, not an echo of intent — and the unverifiable case (record absent) becomes a detectable FAIL instead of a silent assumption. Source: `batch_judge.py:946` + pin `tests/test_judge_dispatch.py:778`.
- **D4 — Api-refusal rate JOINS the gate, default-on at 0.10, per-arm, strict `>=`, waivable via `waive_api_refusal_arms` (revising #2151 §12.3).** Why default-on: with transport parity in place, a batch pilot now SEES the censor; leaving it report-only would repeat #1739 with the data in hand — and the only verdicts that flip are pilots measuring ≥10% api-refusals, which is precisely the catastrophe signature (legacy sync pilots measure ~0%: 0/14,887, so no false flips across the existing caller set). Why 0.10: an order of magnitude above the sync-path benign regime (0/14,887, #1739), 3.4× below the incident rate (34.1%), and resolvable at pilot sizes (≥5 refusal draws at the 51-draw parse-fail floor — signal, not granularity noise; smallest observable nonzero rate at 51 draws is ~2%). Why waivable (unlike truncation): rule 28 has a legitimate remediation (pre-planned sync re-issue at the identical instrument, the #1739 recipe), so an audited waiver mirrors the #2091 parse-fail escape; `api_refusal_threshold > 1.0` documented as the report-only opt-out. Source: #1739 measured rates (rule 28 text, lines 218–224), #2151 (class mechanics), #2091 (waiver pattern). Alternatives: opt-in default (rejected — off for exactly the waves that need it); unwaivable (rejected — blocks remediation-planned waves); pooled-across-arms (rejected — censoring is outcome/corpus-correlated, per-arm localizes it).
- **D5 — Undeclared wave ⇒ WARNING, not FAIL; the rule text (not the code default) mandates declaration for new waves.** Why: 14 existing callers on completed issues must not break retroactively (kind-infra fix, not a migration); the rule-26 lens row makes the declaration plan-enforced for NEW ≥5k waves, which is where enforcement belongs. Source: task-body constraint ("optional/default-compatible OR justify a breaking default") + the #2091/#2124 precedent of tightening-by-rule + auditable escapes.
