I.e. `git commit -- <paths>` commits working-tree content for `<paths>`, bypassing the staged (index-only) deletion.

## 3. Design

**Decision: option (a)** — `git rm --cached -f --ignore-unmatch --` → `git rm -f --ignore-unmatch --`.

Why (a) over (b) (plain index commit): the pathspec limit on the strip commit is a deliberate protection — it keeps unrelated staged entries (mid-crash leftovers, concurrent staging in the worktree index) OUT of the strip commit. Option (b) would fix the resurrection but silently commit whatever else happens to be staged, trading one silent-failure class for another. Option (a) fixes the bug while preserving the pathspec protection: after `git rm -f`, index AND working tree agree on the deletion, so the `git diff --cached --quiet -- "${FOREIGN[@]}"` trigger (index-vs-HEAD, ~L8717) fires exactly as before AND the pathspec commit (working-tree read, ~L8718) now records the absence = the deletion lands. Verified end-to-end in the §2 micro-repro. The working-tree deletion is safe: FOREIGN_BRANCH_ONLY paths are branch-added stale duplicates of foreign tasks' state in the PRIVATE issue worktree; `main` is authoritative for them (same safety argument as #787 plan v1's risk table).
