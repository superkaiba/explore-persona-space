## 3. File paths + concrete diff

```python
def test_raise_concern_survives_concurrent_external_git_op(concerns_task):
    """A concern, once raised, survives a concurrent external git op that does
    NOT rewind history — the exact #763 race (a parallel fleet session running
    ``git pull --rebase --autostash`` / committing unrelated work on the shared
    root mid-round).

    Because ``raise_concern`` write→mirror→commits ``concerns.jsonl`` inside its
    flock (``_append_concern_event`` -> ``_git_commit``), the record is part of
    git history the instant the call returns. A subsequent non-rewinding
    concurrent commit on top therefore cannot wipe it. This pins the durability
    property the #763 workflow-fix candidate asked for; the candidate's proposed
    source change was already implemented in main (see #767).

    NOT in scope for this test (or for any handler-level change): an EXTERNAL
    history-rewind (``git reset --hard HEAD~N``, a dirty-worktree ``git checkout``,
    a manual ``rm``) by a non-task.py process rewinds the committed concern along
    with every other commit it drops. That hazard is governed by CLAUDE.md's
    "concurrent repo-root committers" discipline (``pull.rebase=merges`` +
    ``rebase.autoStash=true`` + push-immediately), NOT by the concern handlers.
    """
    repo, tw, tid = concerns_task
    tw.raise_concern(
        tid,
        "race-durability",
        severity="BLOCKER",
        summary="Reviewer FAIL-class blocker that must survive a concurrent rebase.",
        raised_by="reconciler",
        raised_at_round=1,
    )
    # The concern is committed (verified by the sibling flock-commit test); it is
    # now part of history. Capture the committed bytes.
    before_rows = tw.list_concerns(tid)
    assert len(before_rows) == 1
    assert before_rows[0]["concern_id"] == "race-durability"

    # Simulate a concurrent fleet session committing unrelated work on top of the
    # shared root WITHOUT rewinding history (the real #763 scenario: an autostash
    # rebase / a parallel commit). This is the operation the candidate feared.
    (repo / "unrelated_concurrent_work.txt").write_text("a parallel session's edit\n")
    subprocess.run(
        ["git", "add", "--", "unrelated_concurrent_work.txt"], cwd=repo, check=True
    )
    subprocess.run(
        ["git", "commit", "-q", "-m", "concurrent fleet session commit"],
        cwd=repo,
        check=True,
    )

    # The concern record is intact: still on disk AND still readable via the API.
    concerns_path = tw.find_task_path(tid) / "concerns.jsonl"
    assert concerns_path.exists(), "concerns.jsonl wiped by a non-rewinding concurrent commit"
    after_rows = tw.list_concerns(tid)
    assert after_rows == before_rows, "concern record drifted across a concurrent commit"
    # And it survives reachable in git history (the durability guarantee).
    log = subprocess.run(
        ["git", "log", "--oneline", "--", str(concerns_path.relative_to(repo))],
        cwd=repo,
        capture_output=True,
        text=True,
        check=True,
    ).stdout
    assert "concern-raised" in log
```

**Why this is deterministic (not flaky).** There is NO threading / real
concurrency. The test is purely sequential: `raise_concern` commits synchronously
under its flock and returns; the "concurrent" external op runs afterward in the
same process. The failure mode the candidate feared ("file written but not
committed, then wiped") is structurally impossible to reach AFTER the call
returns, because the commit is synchronous. The test asserts exactly that. A
genuine wall-clock race test (spawn a subprocess that resets mid-flock) would be
flaky AND would test the un-fixable destructive-rewind case — explicitly avoided.

**Probe evidence** (run during planning, throwaway tmp repo): a committed
`concerns.jsonl` survives a non-rewinding concurrent commit on top; it is lost
ONLY to an external `git reset --hard HEAD~N`. Confirms both the in-scope property
and the out-of-scope case.

## 9. Plan deviations from the candidate body

The candidate's proposed change is **NOT implemented** — it is a no-op against
current `main`:

- **Candidate diff:**
  `+ _git_commit_paths([concerns_path], f"task #{n}: concern {event} {concern_id}")`
  in `raise_concern` / `address_concern` / `defer_concern`.
- **Why not implemented:** `_append_concern_event` (the SOLE writer to
  `concerns.jsonl`, confirmed by grep) ALREADY calls
  `_git_commit([concerns_file, events_file], …)` inside the caller's flock for all
  three handlers. The proposed commit already happens. Adding a second commit
  helper (`_git_commit_paths` — which does not exist; the real helper is
  `_git_commit`) would either be a redundant no-op (idempotent early-return on an
  empty cached diff) or a SECOND commit per mutation, breaking the
  exactly-one-commit invariant that
  `test_raise_concern_holds_flock_and_commits` (`tests/test_task_workflow.py:2439`)
  asserts. So implementing the candidate's diff would either do nothing or break a
  passing test.
- **What we do instead:** add a regression test for the durability property the
  candidate actually wanted (survival across a non-rewinding concurrent rebase),
  proving the existing flock+commit already delivers it.

**On the real #763 symptom (the wipe was real, the diagnosis was wrong).** The
round-2 implementer's recovery from a wiped round-1 `concerns.jsonl` was genuine,
but it was not caused by `raise-concern` failing to commit. The two plausible
actual causes (per the clarifier) are: (a) the round-1 reconciler concerns were
written via a non-canonical path that bypassed `task.py raise-concern` (current
`concerns.jsonl` timestamps are post-wipe reconstruction time, not the original
reconciler call time); or (b) an external history-rewind (`git reset --hard`,
dirty-worktree `git checkout`, manual `rm`) by a concurrent session. Neither is
fixable by the concern handlers — (a) is a "always use `task.py raise-concern`"
discipline issue, (b) is the CLAUDE.md "concurrent repo-root committers" hazard
already mitigated by `pull.rebase=merges` + `rebase.autoStash=true` +
push-immediately. The new test documents this scope boundary in its docstring so
the loop is closed honestly rather than papered over with a no-op diff.
