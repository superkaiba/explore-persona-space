## 4. Design

### Item 2 — best-effort dir pull via `sudo -n bash -o pipefail -c 'tar | base64'` piped extraction (recipe (a))

**File + lines:** `src/explore_persona_space/backends/gcp.py:4696-4724` (the `for subdir in (...)` best-effort loop inside `fetch_results`).

**Change:** replace the per-subdir `gcloud compute scp --recurse` with a `gcloud compute ssh ... --command='sudo -n bash -o pipefail -c "tar -c -C <workload_root> <subdir> | base64 -w0"'` whose stdout (a base64-encoded tar stream) is captured and extracted locally under the repo root. This is the SAME transport as the sentinel pull four lines above — just `tar -c | base64` inside a `bash -o pipefail -c` wrapper instead of a bare `cat`.

**Why the `bash -o pipefail` wrap is LOAD-BEARING (v2 fix — [Methodology Reconcile]):** `gcloud compute ssh --command=<STR>` runs `<STR>` through the remote bash login shell. Bash pipelines return the LAST command's exit status unless `pipefail` is set (OFF by default). On a missing `figures/issue_<N>/` (the COMMON path — item-4 removes figures/ from the gate precisely because that dir is normally absent on the pod), `tar` exits non-zero but `base64 -w0` reads empty stdin and exits 0 → the pipeline returns 0 → the `if tar_res.returncode != 0: continue` guard NEVER fires → `base64.b64decode("")` → `tarfile.open(fileobj=BytesIO(b""))` raises `tarfile.ReadError` locally. Wrapping the pipeline in `sudo -n bash -o pipefail -c '<tar | base64>'` makes the tar rc propagate, so the guard works. This is the SAME wrapping-bash idiom the codebase already uses for the drain-log-tail at `gcp.py:4260-4265` (`--command=sudo -n bash -c {shlex.quote(script)}`) — item-2 adds `-o pipefail` because it wraps a PIPELINE (the drain script is a `;`-sequence, not a pipe, so it did not need pipefail).

**Pseudocode / diff sketch:**

```python
# gcp.py fetch_results, replacing the scp loop at 4703-4724
repo_root = _default_src_root_for_fetch()
workload_root = workload_dir_for(config, issue)
for subdir in (f"eval_results/issue_{issue}", f"figures/issue_{issue}"):
    remote_parent = shlex.quote(f"{workload_root}/{os.path.dirname(subdir)}")  # .../eval_results
    remote_leaf = shlex.quote(os.path.basename(subdir))                        # issue_<N>
    local_parent = repo_root / os.path.dirname(subdir)
    local_parent.mkdir(parents=True, exist_ok=True)
    # Pull the root-owned dir as a base64-encoded tar stream via sudo -n (same
    # grant as the sentinel pull). The `bash -o pipefail` wrap is REQUIRED so a
    # missing remote dir surfaces as tar rc!=0 through the `| base64` pipe
    # (base64 reads empty stdin and exits 0, masking the tar failure without it).
    # A missing dir / rc!=0 -> LOG + continue (the dir is authoritative on
    # HF/WandB/git already).
    remote_cmd = f"tar -c -C {remote_parent} {remote_leaf} | base64 -w0"
    tar_argv = _base_gcloud_argv(
        config, "compute", "ssh", handle.pod_name,
        f"--command=sudo -n bash -o pipefail -c {shlex.quote(remote_cmd)}",
    )
    tar_argv += [f"--zone={zone}"]
    tar_res = self._run(tar_argv)          # captured stdout = base64(tar bytes)
    if tar_res.returncode != 0:
        logger.warning(
            "GcpBackend.fetch_results: best-effort sudo tar of %s/%s failed "
            "(rc=%d); authoritative copy is on HF/WandB/git. stderr=%s",
            workload_root, subdir, tar_res.returncode, tar_res.stderr[:300],
        )
        continue
    # Decode + extract the captured tar stream under local_parent. Wrap the
    # decode+extract in try/log/continue too (v2 hardening — a genuinely
    # truncated/corrupt stream from a transport hiccup mid-transfer must
    # log-and-continue, NOT raise: the mirror is best-effort and the dir is
    # authoritative on HF/WandB/git).
    try:
        raw = base64.b64decode(tar_res.stdout)
        with tarfile.open(fileobj=io.BytesIO(raw)) as tf:
            tf.extractall(path=local_parent)   # extracts <leaf>/ under local_parent
    except (base64.binascii.Error, tarfile.TarError, ValueError, EOFError) as exc:
        logger.warning(
            "GcpBackend.fetch_results: best-effort decode/extract of %s/%s "
            "failed (%s: %s); authoritative copy is on HF/WandB/git.",
            workload_root, subdir, type(exc).__name__, str(exc)[:300],
        )
        continue
```

**Text-vs-bytes note (load-bearing, resolve at implementation):** the existing `self._run` / `GcloudRunResult.stdout` returns TEXT (the sentinel pull does `write_text(sentinel_res.stdout)`). The `| base64 -w0` wrap keeps the transport TEXT (base64 is ASCII-safe through any text pipe), so `self._run` and the `_Runner` mock stay string-shaped — `base64.b64decode(tar_res.stdout)` recovers the binary tar before `tarfile.open`. The implementer confirms `_run` capture type before writing, but the base64 wrap makes the fix correct regardless of text-vs-bytes (robustness detail, not a blocker).

**Why code, not a model call?** N/A — no unstructured-data heuristics; this is a file-transport change.

## 11. Decision Rationale

- **Item-2 transport = `sudo -n bash -o pipefail -c 'tar -c | base64'` piped extraction (recipe (a)).**
  - **What:** best-effort dir pull via `gcloud compute ssh ... sudo -n bash -o pipefail -c 'tar -c ... | base64 -w0'` instead of `gcloud compute scp --recurse`.
  - **Why:** the workload tree is root-owned (#588); plain scp Permission-denies. `sudo -n` reads it through the OS-Login user's google-sudoers grant — exactly what the sentinel pull already does with `sudo -n cat`. The `bash -o pipefail` wrap is REQUIRED so the `tar` rc propagates through the `| base64` pipeline (bash pipelines return the LAST command's status; `base64 -w0` reads empty stdin and exits 0 on a missing dir, masking the tar failure and crashing the local `tarfile.open` on an empty stream). No VM-side pre-teardown chmod, single sudo-only permission surface, one round-trip per subdir.
  - **Source:** gcp.py sentinel pull pattern from #588 (gcp.py:4669-4694) — same transport, `cat`→`tar -c | base64`. The `sudo -n bash -c '<script>'` wrapping-bash idiom is the SAME one `gcp.py:4260-4265` `_drain_sentinels` already uses; item-2 adds `-o pipefail` because it wraps a PIPELINE (the drain script is a `;`-sequence, which does not need pipefail).
  - **Alternatives rejected:** (b) `ssh sudo -n chmod -R a+rX` then scp — two round-trips, leaves root files world-readable on the (soon-deleted) VM, more permission surface. (c) run the workload as non-root — requires restructuring the snapshot-pinned startup script, out of scope. Bare `sudo -n tar -c ... | base64` WITHOUT the `bash -o pipefail` wrap — REJECTED: the pipeline masks the tar rc (the [Methodology Reconcile] finding).
- **Item-4 declaration = split default git_paths by `custom_workload` (recipe (e)).**
  - **What:** in `build_expected_artifacts_declaration`'s default (non-`skip_default_git_paths`) branch, `custom_workload=True` → `["eval_results/issue_{issue}/", *extra]`; `custom_workload=False` (pure hydra) → `[*extra]` (both dropped).
  - **Why:** the analyzer generates + commits figures POST-run (analyzer.md Step 3), AFTER confirm_artifacts runs, so `figures/` is never produced during the run on ANY lane → drop it everywhere. Pure hydra additionally passes `skip_eval=True` (train.py:29 → runner.py:109 gates all eval production on `not skip_eval`), so it writes no `eval_results/` either → drop both on that branch. `--workload-cmd` drivers DO commit `eval_results/` during the run, so keeping the eval_results check there preserves a real FAIL; dropping it would loosen the gate.
  - **Source:** the existing `custom_workload` carve-out on `base_hf_data` at `artifacts.py:565-573` — the SAME flag already gates a per-branch declaration difference in this exact function; item-4 extends that established shape to `git_paths`. The pure-hydra no-eval fact is grounded in `scripts/train.py:29` (`run_single(cfg, ..., skip_eval=True)`) + `src/explore_persona_space/orchestrate/runner.py:109` (`if not skip_eval:` gates eval production). Caller matrix verified at gcp.py:864, slurm.py:512, runpod.py:310.
  - **Alternatives rejected:** (v1) drop only `figures/` from a single unconditional default — REJECTED: leaves the same false-FAIL class on `eval_results/` for the pure-hydra branch (the [Alternatives Reconcile] FATAL finding). (d) add an `include_figures_git_path` flag — needs wiring at every caller for a path no hydra workload ever writes; unnecessary complexity. (f) downgrade missing-figures from FAIL to WARN inside `confirm_artifacts_from_handle` — muddies FAIL semantics (a genuinely-missing eval_results/ would then need a separate FAIL rule); the split is cleaner. (Simpler both-drop-everywhere) drop eval_results/ from BOTH branches — REJECTED: would loosen the real eval_results/ check on `--workload-cmd` runs, which DO commit eval JSONs during the run; the pure-hydra branch is NOT dead code (the router's default `auto` GCP lane runs hydra `train.py` launches with no `--workload-cmd`), so its check must be corrected, not the custom_workload check loosened.
- **Test scope = explicit four-file inclusion (recipe: minimal blast radius).**
  - **What:** §6 + §Test scope name `test_gcp_backend`, `test_backend_poll`, `test_issue_dispatch`, `test_slurm_backend_render` explicitly; the implementer runs all four at Step 9c.
  - **Why:** the Step 9c touched-file selector maps `gcp.py`/`artifacts.py` to `test_gcp_*` / `test_*artifacts*` stems only, so `test_issue_dispatch.py` + `test_slurm_backend_render.py` (which pin the pre-fix `scp_calls == 2` / `git_paths` behavior) fall outside the default scope and neither is in `WORKFLOW_INVARIANT` — a silent regression-miss.
