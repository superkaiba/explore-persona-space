# Plan v2 — #1838: GCP→RunPod failover provision crash-safe (reap-and-recreate residue pod + provision-intent breadcrumb, reap-cycle-bounded)

`### TDD: no`

Revision log (v1→v2, critic round 1): (MF1) reap-cycle bound `reap_count` ≤ K=2 per un-cleared-intent episode — after 2 reaps with no intervening successful submit the retry does NOT reap and degrades to today's refusal terminal; (MF2i) intent cleared on every COMPLETED attempt exit (the `NoComputeAvailableError` handlers in both funnels + the `RunPodWorkloadStartError` belt), not only on successful submit; (MF2ii) `RUNPOD_PROVISION_INTENT_WINDOW_SEC` shrunk 3600→900 s; (NB) min-age conjunct `now − intent.ts ≥ 120 s` closes the concurrent-poller mid-provision race.

## 1. Goal + requirement + acceptance criteria

**Goal (task body, verbatim):** Make the #659 GCP->RunPod async-failover provision leg crash-safe and idempotent: on retry, ADOPT (or tear down and recreate) a pre-existing managed pod-<N> left by an interrupted failover attempt instead of refusing into a no_compute_available terminal, and bound the residue window with a provision-intent breadcrumb before pod creation.

**Requirement.** A poll tick killed mid-RunPod-provision (the #1739 shape: caller's 120 s timeout kills `backend_poll.py` between pod-create and lease/handle write) must not leave the next failover attempt refusing on its own orphan. The retry must (a) recognize the orphan by POSITIVE evidence, (b) terminate it surgically, (c) proceed to a fresh provision in the SAME attempt — no `no_compute_available` terminal minted for our own residue — while (d) NEVER terminating a pod lacking positive our-residue evidence (human-provisioned pods keep today's bias-safe refusal), and (e) the reap→provision→kill cycle is BOUNDED: a systematically-killed provision stops reaping after K=2 cycles and degrades to today's watcher-re-drivable terminal instead of looping.

**Acceptance criteria:**
1. All new unit tests pass (§ Test plan, ~15 tests); all existing `tests/test_backend_poll.py` #1490 tests (`test_failover_provision_*`, L3620–3924) and `tests/test_router.py::test_lease_round_trip` pass unchanged.
2. Simulated interrupted-attempt scenario (lease intent + in-window orphan pod): retry terminates the orphan and invokes the launch seam — no `no_compute_available`.
3. Negative cases: (a) live pod-<N> with no matching intent → NO terminate, today's `pre-existing` → re-drivable `no_compute_available`; (b) intent standing after a COMPLETED refusal attempt is CLEARED, so a human pod provisioned later is never matched; (c) intent with `reap_count ≥ 2` → NO terminate, today's terminal (loop stops).
4. Breadcrumb is durably on disk BEFORE the launch seam runs (test asserts read-back at fake-launch time).
5. `uv run python scripts/workflow_lint.py` (no flags) passes; `ruff check` clean on touched files.

## 2. Method delta (vs existing #1490 / #1668 machinery)

- **#1490** (`backend_poll.py` L3245–3530: `_live_runpod_ids_for_issue` pre/post snapshots + `_classify_provision_failure` + `_reclaim_failed_runpod_provision`) reclaims ONLY a pod the JUST-FAILED provision created (post−pre singleton + created-then-failed evidence). The "already exists" refusal matches `_PROVISION_REFUSAL_MARKERS` conjunctively → `created-nothing` → outcome `pre-existing` → pod kept + re-drivable terminal. **Delta:** we add attribution for a pod created by a PRIOR killed attempt (which sits in the PRE snapshot with no #1490 attribution) via a durable **provision-intent breadcrumb written BEFORE pod-create**, plus a **proactive pre-provision probe + reap-cycle-bounded reap**. #1490 is byte-untouched and remains the backstop for the just-failed-attempt shape and for anything the proactive probe misses (probe failure, concurrent creation, reap-cap-hit degradation).
- **#1668** (wedge-handled sentinel keyed on `runpod_attempt_id`; `_stamp_lease_failover_of` / `_lease_records_failover_of`) records failover identity AFTER a successful launch. **Delta:** the new breadcrumb is the BEFORE-launch sibling, stored in the SAME durable Lease (`~/.eps-routing/issue-<N>.json`) whose docs already name the crash-between-submit-and-lease-write orphan window. No existing field's semantics change.
- **Bounded-once AND bounded-loop:** the exactly-once records (`gcp_failover_of`, wedge/CUDA-IMA fields, sentinels) are stamped only AFTER a successful launch; a killed attempt never stamped, so the reap-then-provision retry IS the "once". The orphan is terminated before its replacement is created → never >1 billing pod from this path. Loop termination (MF1): the intent's `reap_count` caps reap cycles at K=2 per episode (an episode ends when any attempt COMPLETES — successful submit or terminal — which clears the intent); at the cap the retry degrades to today's refusal terminal, so a systematically-killed provision burns at most 2 extra creates before parking watcher-re-drivable.

## 3. Design decisions (the 5 questions)

**Q1 — Breadcrumb form: extend the durable Lease.** New field `Lease.runpod_provision_intent: dict | None` (router.py), shape `{"pod_name": "pod-<N>", "issue": N, "ts": <epoch float>, "token": <uuid4 hex>, "reason": <failover reason>, "reap_count": <int>}`. Written via `LeaseStore().transaction(issue)` → `write(lease)` (flocked, atomic tmp+replace) in backend_poll BEFORE the launch seam call — crash-ordered write-before-create. **Cleared at every attempt-COMPLETION site** (MF2i): (a) `router._lease_after_submit` (one line, `lease.runpod_provision_intent = None` — mutates in place, verified L5748–5779; covers ALL submit paths incl. the #954 partial-launch lease writes, critic-verified call sites L2362/3317/3429/3949/4838/5475); (b) the `except NoComputeAvailableError` handler in `_failover_gcp_to_runpod` (covers the leaked terminal, the clean-residue tail, and the exit-75-converted path); (c) the `except NoComputeAvailableError` handler in `_relaunch_fresh_runpod`; (d) belt: the `except RunPodWorkloadStartError` handlers in both funnels (router-side clear (a) already fired unless its lease write failed — the EDQUOT mode; the belt keeps the #909 leave-RUNNING-for-diagnosis pod unmatched by any later failover). Only a KILLED attempt leaves the intent standing. Rationale over a sidecar file: the Lease is the store that already survives `.claude/cache` disk-failure modes (the #659 round-3 rationale), is flocked, and holds the #1668 identity plumbing; `from_json` uses `.get()` so legacy files parse fine.

**Q2 — Reap-and-recreate (a), not adopt (b).** The orphan provably has NO workload: dispatch happens only after `RunPodBackend.launch` returns, and the killed attempt's launch never returned (the #1739 pod had no handle, no workload). Adoption would require reconstructing a RunHandle for a pod whose bootstrap may be half-done and whose pods.conf registration state is unknown — new, fragile machinery. Teardown reuses the exact surgical `terminate_pod(pod_id)` (`runpod_api.py:935`) + `_terminate_error_is_pod_not_found` tolerance the #1490 reclaim already uses, then the existing provision path runs fresh. Cost: ~5–12 min re-provision (create + wait_for_ssh ≤600 s + bootstrap), incurred at most K=2 times per episode (MF1). Safety argument: we only ever terminate under the full positive-evidence conjunct set (Q4), and a never-dispatched pod holds no unpersisted state.

**Q3 — Which legs: one shared helper, two call sites, covering all six async legs.** Verified (critic-confirmed): dead-GCP (L3622), queue-timeout (L3673), boot-loop (L3720), queue-vanish (L3769) are thin wrappers over `_failover_gcp_to_runpod` (L4082) — ONE insert there covers all four. The wedge (#664) and CUDA-IMA (#775) fresh-pod legs go through `_relaunch_fresh_runpod` (L2147) — second insert. Both funnels then call `failover_to_runpod_after_async_workload_crash` → `_runpod_terminal_rung`. We do NOT patch router-side for the probe/reap: `src/` never imports `runpod_api` (layering: scripts→src one-way; probe/terminate live in scripts/runpod_api.py), and backend_poll already owns `_live_runpod_ids_for_issue` + the surgical-terminate pattern. Out of scope (documented residual): the SYNC `route()` paths (capacity fallback `auto_fallback_runpod`, sync workload failover) run in `dispatch_issue.py launch` — a foreground command, not a timeout-bounded poll tick; a killed sync launch's refusal keeps today's behavior. The #1596/#1601 on-demand-retry legs provision GCP, not RunPod — untouched.

**Q4 — Proactive probe BEFORE provision (primary); #1490 refusal classification unchanged (backstop).** The refusal-text parse is brittle and fires only after a wasted subprocess; the probe is one GraphQL list call. Residue REAP predicate — ALL conjuncts required (positive evidence, per the hard constraint):
1. Lease exists and carries a parseable `runpod_provision_intent` with `pod_name == f"pod-{issue}"` (malformed/absent → no reap; a completed attempt has cleared it per Q1, so only a killed attempt's intent stands);
2. `intent.reap_count < 2` (MF1 — at the cap: log loud, NO reap, NO fresh stamp; proceed to provision, which refuses on the live pod → the #1490 `pre-existing` path → today's re-drivable `no_compute_available`, whose handler then CLEARS the intent, permanently ending the episode; the terminal's detail already names the live pod ids for manual terminate);
3. `now − intent.ts ≥ 120 s` (NB concurrency conjunct — a near-simultaneous second poller (the M3b #669 dual-triggerer shape lands within one tick) must not reap the first poller's mid-provision pod; a skipped tick just retries next tick);
4. EXACTLY ONE live non-EXITED pod named exactly `pod-<N>` (suffixed pods excluded; 0 or ≥2 → no reap — ambiguity never terminates, the #1490 stance);
5. That pod's `PodInfo.created_at` (ISO-8601 str, `runpod_api.py:415/427`; selection includes `createdAt`, critic-verified L850/868/917) parses AND falls in `[intent.ts − 120 s, intent.ts + 900 s]` (§ 11) — a pod created before the intent, later than the killed attempt's create-latency bound, or with missing/unparseable `created_at` is NOT our residue → keep.
Every failure branch (probe returns None, no lease, any conjunct false) degrades to today's exact behavior. A matched reap logs loudly, and the GCP core merges `{"interrupted_provision_residue_reaped": {pod_id, intent_ts, created_at, reap_count}}` into the seam's `extra_evidence` so the `epm:backend-selected` marker records it (the wedge path logs only — no `extra_evidence` param there).

**Q5 — Retry semantics.** After a successful reap the SAME attempt proceeds directly to provision (no new terminal, no extra tick), stamping a FRESH intent that carries `reap_count = prior + 1` (a no-prior-intent attempt stamps `reap_count = 0`). If the terminate raises: POD_NOT_FOUND-class (`_terminate_error_is_pod_not_found`) counts as reaped (already gone) → proceed; any other error → log + proceed WITHOUT reap — the provision then refuses on the still-live pod and the #1490 classifier yields today's re-drivable `no_compute_available` (degrade path, never crash the poll), whose handler clears the intent. The helper NEVER raises (top-level try/except → no-reap, mirroring `_reclaim_failed_runpod_provision`'s never-raise contract).

## 11. Grounding (load-bearing constants)

- `RUNPOD_PROVISION_INTENT_WINDOW_SEC = 900` (MF2ii; was 3600 in v1) — Source: the stamp→create latency of a KILLED attempt is bounded by the tick's own lifetime plus the orphaned subprocess's pre-create work: the incident's create landed ≤~4 min after the failover fired (#1739: fired 20:08–20:10Z, pod live at 20:12Z), the caller timeout that does the killing is 120 s, and `wait_for_ssh(timeout=600)` (pod_lifecycle.py L1891) runs AFTER create — so create either happens within minutes of the stamp or (capacity-wait) the attempt exits 75 without creating. 900 s = observed ~240 s × ~3.75 margin, and ≤ the post-create SSH-wait bound. Too-small degrades to today's keep (safe); the shrink from 3600 exists precisely to exclude a later human `pod.py provision` (a capacity-wait-delayed orphan create past 900 s falls back to today's keep + the #1490/watcher backstops). Env-overridable.
- `_PROVISION_INTENT_MAX_REAPS = 2` (MF1) — Source: two consecutive killed provisions on the same episode are evidence of a SYSTEMATIC kill (the incident's caller-timeout shape), not a transient; a third reap would burn another ~5–12 min create with the same expected outcome. K=2 gives the transient case one full second chance while bounding worst-case extra spend at 2 creates; the cap-hit degradation is today's exact watcher-re-drivable terminal. Margin choice, not literature-pinned; env-fixed (module constant) deliberately — raising it is a must-ask.
- `_PROVISION_INTENT_MIN_AGE_SEC = 120` (NB) — Source: the concurrent-triggerer shape lands within one poll tick (the M3b #669 dual-triggerer analysis; the incident's own 120 s caller timeout is the tick scale) — an intent younger than one tick may belong to a LIVE mid-provision poller, so it cannot license a reap; a skipped tick retries next tick at trivial cost. 120 s matches the caller-timeout scale.
- `_PROVISION_INTENT_CLOCK_SKEW_SEC = 120` — Source: the VM↔RunPod-API `createdAt` clocks are independent; 120 s generously covers NTP skew. Ungrounded beyond that reasoning — safe in both failure directions.
- Refusal markers / terminate tolerance — Source: `scripts/backend_poll.py` L3289 (`_PROVISION_REFUSAL_MARKERS`), L3368 (`_terminate_error_is_pod_not_found`), reused verbatim.
