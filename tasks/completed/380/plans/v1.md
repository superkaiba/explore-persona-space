# Plan: Completion-divergence from assistant baseline as a predictor of [ZLT] source-rate (N=48)

## 0.0 TL;DR (plain English)

- **Question:** A persona's *cosine* distance to "the helpful-assistant identity" already failed to predict how easily a marker token gets implanted into that persona once we control for prompt length. Is *output-distribution* distance (how different the persona's next-token distribution looks vs. the bare assistant's) any better?
- **What I'll run:** For each of 48 persona prompts, I'll measure how different the base model's next-token distribution is from the bare-assistant baseline on a fixed set of 20 neutral questions (no training involved — pure forward passes). Then I'll line up those 48 "output-distance" numbers against the 48 source rates we already have on file, and see whether they correlate — both raw, and after partialling out prompt length the same way #340 did.
- **What I expect:** The raw correlation will be moderate (similar magnitude to the |0.35| cosine result), and the length-partialled correlation will collapse to roughly zero — i.e., the output-distance signal is mostly a length confound, like cosine was. I'd put ~60% on this.
- **What would change my mind:** A length-partial correlation of |ρ| ≥ 0.5 with p < 0.01 on either predictor. That would mean output-distance carries vulnerability signal that prompt length doesn't, and we'd have something geometric to build a safety tool on. The opposite extreme — |ρ| < 0.2 on both predictors — closes off the whole "distance from the assistant" predictor family, which is also a useful result.

## 0. Plan Summary (technical)

- **Training:** none. This is an analysis on the existing N=48 panel.
- **Predictors:** (1) JS-from-baseline = JS divergence between (persona-conditioned base-model next-token logits) and (baseline-conditioned base-model next-token logits) on 20 neutral probes, teacher-forced, averaged per token-position then per probe; (2) mean pairwise JS = 48×48 pairwise JS reduced per-source by mean over the 47 other personas (median/max reported as secondary). Computed with `src/explore_persona_space/analysis/divergence.py` (`compute_js_divergence` for predictor 1; `compute_pairwise_divergences` with `kl_only=True` for predictor 2).

- **Baselines / controls:** Same N=48 panel, same source-rate values, identical length-partial method as #340 (`pingouin.partial_corr(method='spearman')` if installable; otherwise rank-residualize-then-Spearman via scipy — the explicit fallback #340 used).

Wall ≈ 3–3.5 h end-to-end (greedy gen + 48×20 teacher-forces + pairwise JS matrix; calibrated against i207's actual 111 min Stage-B at N=40 from `eval_results/issue_207/js_gentle/js_divergence_matrix.npz` metadata). ## 3. Hypothesis

A source persona's JS divergence (from the assistant-baseline next-token distribution, on a fixed set of 20 neutral probes, computed teacher-forced over the base model) is monotonically related to its `[ZLT]` source rate under the fixed LoRA Phase-A1 recipe (r=32, α=64, lr=1e-5, 3 epochs, 600-row asst_excluded mix, seed 42), and the relationship survives partialling out log prompt length.

**Direction (sign):** not pre-registered. The prior-work pattern at #271 (cosine, negative) and #142/#207/#228 (JS-to-bystander, negative) both point negative, but neither is *JS-from-assistant → source-rate*, so we leave the sign open. We register only the magnitude threshold.

**Pass:** |length-partial Spearman ρ| ≥ 0.5 with p < 0.01 on either JS-from-baseline (Predictor 1) or mean pairwise JS (Predictor 2) on N=48.

**Auxiliary hypothesis (Predictor 2):** mean pairwise JS will be a stronger predictor than JS-from-baseline alone. Rationale: a persona that is divergent from *many* other personas (high average pairwise JS) carries more identity-specific output structure, which plausibly modulates how strongly the marker associates with that identity. If both predictors pass, we report whichever has higher |partial ρ| as the headline.

## 4. Kill criterion

|length-partial Spearman ρ| < 0.2 on **BOTH** JS-from-baseline AND mean pairwise JS → conclude that geometric distance from the assistant baseline is not a source-rate predictor at this panel size. The "geometric-from-assistant" predictor family (cosine on hidden states, JS on output logits, mean pairwise JS) is closed off; re-route the vulnerability question to non-geometric predictors (training-data overlap, base-rate token frequencies, capability-axis location).

### 5.3 Partial Spearman implementation

The exact method from #340 is "rank-residualize both variables on the covariate, then take Spearman of the residuals." Implementation:

```python
# scripts/i380_analyze.py (new)
import numpy as np
from scipy.stats import spearmanr, rankdata

def partial_spearman(x, y, z):
    """Partial Spearman ρ(x, y | z) via rank-residualization.

    Returns (rho, p, n) using the t-distribution approximation
    df = n - 2 - 1 (one covariate) for the p-value (Fisher z is acceptable
    too; we use the standard partial-correlation t-test for consistency
    with pingouin.partial_corr(method='spearman')).
    """
    xr, yr, zr = rankdata(x), rankdata(y), rankdata(z)
    # Linear residual of each rank vector on the covariate rank
    def resid(a, b):
        b_centered = b - b.mean()
        return a - a.mean() - (np.dot(a - a.mean(), b_centered) /
                               np.dot(b_centered, b_centered)) * b_centered
    xr_res = resid(xr, zr)
    yr_res = resid(yr, zr)
    rho, _ = spearmanr(xr_res, yr_res)
    n = len(x)
    # Partial-correlation t-test, df = n - 2 - k (k = 1 covariate)
    from scipy.stats import t
    df = n - 3
    t_stat = rho * np.sqrt(df / max(1 - rho**2, 1e-12))
    p = 2 * (1 - t.cdf(abs(t_stat), df))
    return rho, p, n
```

This matches the partial-Spearman protocol named in #340's clean-result Methodology section ("rank-residualize both variables on log-tokenized prompt length, then take the Spearman of the residuals"). **First preference is to install `pingouin` (`uv add pingouin`) and call `pingouin.partial_corr(data=df, x=X, y=Y, covar=['log_tokens'], method='spearman')` for cross-experiment numerical consistency with #228.** If pingouin can't be added (env conflict — unlikely; it was in the project env at #228), fall back to the inline implementation above, sanity-checked against scipy on the cosine→rate predictor from `length_rate_correlation_n48.json` (should reproduce the published ρ=−0.008, p=0.95 to ±0.005).

### 5.4 Collinearity gate (pre-registered)

Per planner memory `feedback_collinearity_gate_pattern`, with N=48 (just above the small-sample threshold) but expected high collinearity between JS-from-baseline and prompt length:

1. **Stage B.1 (between B and C):** compute `Pearson(js_from_baseline, log_tokens)` AND `Pearson(mean_pairwise_js, log_tokens)` on the 48-source panel.
2. **Threshold:** 0.6. Pre-registered in this plan, not picked post-hoc.
3. **If |Pearson| ≤ 0.6 for a predictor:** proceed with linear partial-Spearman as primary for that predictor.
4. **If |Pearson| > 0.6 for a predictor:** the predictor is largely a length restatement (echoes the #340 cosine collapse). Switch the headline for THAT predictor to a tercile-bucket median test: bin the 48 by log_tokens into low/mid/high terciles (n=16 each, ±1), report median source rate within each (predictor-low half, predictor-high half) × tercile cell, and run a cluster-bootstrap (1000 iter, resample over (source, predictor_decile, tokens_decile) triples) for the within-tercile median difference. Pass = ≥2 of 3 buckets show same-signed within-bucket effect at |median Δ| ≥ 0.05 source-rate units.
5. **Auxiliary check (always):** also fit a polynomial residualization (`X ~ log_tokens + log_tokens²`) and report partial Spearman of the residuals — robustness against nonlinear length confound.

### 5.5 Why code, not a model call?

**Required disclosure.** Both predictors are mechanistic, well-defined numerical operations on next-token logits (KL/JS), not unstructured-text scoring. A Claude/Haiku model call cannot replace `compute_js_divergence` because (a) the input is a 152K-vocab log-softmax tensor (no model API exposes this output mode), (b) JS is exact under the formula — there's nothing to interpret, only to compute, (c) latency and reproducibility require torch numerics. The only model-call alternative would be "ask Claude to judge how 'far from helpful-assistant' each persona's behavior is" on greedy generations — but that's a totally different operationalization (a *behavioral judgment*, not a *distributional distance*) and would not answer the registered hypothesis. Code path is the correct choice; documented here to satisfy CLAUDE.md "Model call vs code (3.0 paradigm)".

## 7. Evaluation

### Primary metric

For each of the four predictor reductions (JS-from-baseline; mean / median / max pairwise JS):

- Spearman ρ raw, with scipy p-value, on N=48 — reported with n.
- Spearman ρ length-partial (covariate = log(tokens+1)), with t-test p-value (df=45) and bootstrap 95% CI (1000 percentile-bootstrap iterations over rows), on N=48.

**Pre-registered pass criterion:** at least one predictor (JS-from-baseline OR mean pairwise JS — the two declared primaries; median/max pairwise are robustness comparisons, not separate primaries) shows |length-partial ρ| ≥ 0.5 with p < 0.01. Single-test threshold; no FWER correction across the 2 primary predictors because they probe different geometric quantities (one-anchor vs. mean-pairwise), not multiple shots at the same hypothesis. The 2 secondary pairwise reductions (median, max) are reported as robustness but do not contribute to pass/fail.

### Kill criterion

|length-partial ρ| < 0.2 on **both** primary predictors → kill (close off geometric-from-assistant family).

### Stratification

Within prompt-length bins (verified empirically at plan time on `eval_results/issue_296/length_rate_correlation_n48.json::rows[i].tokens` — actual N=48 distribution is **12 / 2 / 34** under the originally-proposed `≤6 / 7–10 / 11+` cuts, NOT the ~12/18/18 the planner first guessed; the middle bin is degenerate at n=2). **Implementer recuts at launch:** use the data-driven tercile cut at `[≤6, 7–13, 14+]` (gives roughly 12 / 17 / 19) OR, if simpler, a 2-bucket cut at `[≤10, ≥11]` (gives 14 / 34). - Report at the cell level if any bin has n<10 (within-bin Spearman becomes underpowered below that).

### Leave-helpful-family-out partial ρ (analyzer-requested diagnostic)

The N=48 panel contains an 11-member "helpful-assistant family" of personas (`helpful_assistant`, `i_am_helpful`, `ai_assistant`, `chat_assistant`, `virtual_assistant`, `chatbot`, `friendly_ai`, `smart_helper`, `ai_tool`, `ai`, `qwen_default`) which cluster at short prompt length (10 of 11 at 6 tokens) and low source rate (mean 0.20 vs 0.29 for the other 37). - **Wall time:** Stage A ~10 min (vLLM batched greedy on 49×20=980 prompts). Stage B ~3 h (49 prompts × 20 probes × teacher-force; calibrated against i207's actual 111 min Stage-B at N=40, scaling roughly linearly with prompt count to ~135 min for the JS-from-baseline pass + ~30–45 min for pairwise via chunked GPU matmul + first-load HF download ~3 min). Stage C ~1 min. Stage D ~1 min. Total: **~3.5 h wall, ~3 GPU-hours.** Pod TTL provisioned at ≥6 h to absorb variance.
- **Parallelism axis:** none meaningful — single-prompt-set, single-model. Pairwise JS is the dominant kernel; it's already vectorized via chunked GPU matmul in `divergence.py:compute_pairwise_divergences`. Splitting across multiple GPUs would require reshuffling the batch dimension and adds ~30 min of setup vs ~30 min saved. Smaller pod (one H100) is the correct choice per CLAUDE.md §9 ("data is too small to amortize 8× setup").
- **Disk:** ~200MB on pod (`base_model_generations.json` ≈ 5MB, `pairwise_js_matrix.npz` with `per_question_js` of shape (20, 48, 48) float32 ≈ 0.2MB, plus HF cache ~16GB for Qwen2.5-7B-Instruct already present from #207). Well under the 130GB per-pod MooseFS quota.
- **API costs:** none (no judge calls; substring detection on existing source rates only).
- **No re-train branch.** The task body proposes a 3-day re-train fallback if source-rates aren't recipe-matched. Verified at plan time that `eval_results/issue_296/length_rate_correlation_n48.json` contains the recipe-matched 48 source rates from the identical Phase-A1 LoRA recipe (r=32, α=64, lr=1e-5, 3ep, 600-row asst_excluded mix, seed 42) — 24 NEW from WandB at full N=48 eval breadth, 24 INHERITED from local `run_result.json` at N=24 eval breadth (proxy with mean delta +0.01 per #296 Result 3). The re-train branch is therefore NOT triggered; the only data-quality caveat is the proxy on the inherited 24, handled in §9.

## 12. Decision Rationale

| Choice | Why | Alternatives rejected |
|---|---|---|
| Probe set = `EVAL_QUESTIONS` (n=20) | Same set as the family-origin JS experiments #142/#207/#228 — keeps Predictor 2 cross-comparable to the |ρ|=0.48–0.79 JS-to-bystander results. Also matches the 20 questions used for the bystander-rate eval that produced the source rates in `length_rate_correlation_n48.json`, so the "completion distance on the eval distribution" framing is direct. | 30–40 held-out neutral questions (task-body suggestion): would require a fresh probe set that doesn't overlap with the training-time questions, breaking comparability with #142/#207/#228. Discarded; 20 is the canonical set and #228 reported #207 ran the same 20 on the same model. |
| Baseline prompt = content-free instruction, NOT `"You are a helpful assistant."` | Per planner memory `feedback_neutral_prompt_axis_conflation`: using `"You are a helpful assistant."` as the baseline conflates the JS-from-baseline axis with the `helpful_assistant` panel member (which sits at the baseline by construction), tautologizing the headline. The same memory flags this for `qwen_default` too. | (a) `"You are a helpful assistant."` — rejected (tautologizes `helpful_assistant`, `i_am_helpful`, `qwen_default`, `assistant`). (b) Empty system role — rejected (Qwen2.5-Instruct chat template injects a default system prompt when system role is empty, defeating the purpose). (c) Single-question prompt (no system role at all) — rejected for the same reason. |
| KL-approximation for pairwise JS | Validated at ρ=0.99 vs exact on core-11 per docstring. Exact-JS at N=48 is `O(N²·T·V)` per row and the per-row inner loop already takes minutes at N=11; 48 would be hours. | Exact JS — rejected on wall-time grounds; sanity check on 3-persona pilot only. |
| Partial Spearman via rank-residualize-then-Spearman (or `pingouin.partial_corr(method='spearman')`) | Exactly the method named in #340's clean-result Methodology section. Cross-experiment consistency with the negation we're testing against. | `partial_corr(method='pearson')` — rejected; the underlying variables are ordinal (source rate is a ratio of counts; JS is positive-valued; length is integer tokens) and we want a non-parametric test for the rank relationship, matching #340. |
| `log(tokens+1)` as length covariate | Matches #340/#368/#371's exact covariate. | `tokens` (linear) — rejected for #340 consistency. `chars` — rejected; #296 tested both and `tokens` was the registered covariate. |
| Stratification bins `≤6, 7–10, 11+` | NEW design choice in this plan; `analyze_length_rate_n48.py` does straight Spearman with no binning, and #340 used a single 6-token fixed-length cohort. Bins picked to give ~n≥10 per bucket on the 48-panel distribution. | Quartiles — rejected (n≈12 per quartile becomes borderline for within-bucket Spearman). |
| Single seed = 42 | No training; vLLM greedy generation is deterministic at temp=0 modulo CUDA non-determinism (~<1% completion variance per #207). | Multi-seed — rejected; no training-variance source to average over. |
| Mean pairwise JS as primary aggregator (median, max as secondary) | Mean is the symmetric, lowest-variance aggregator over the 47 other personas. #207/#228 reported on mean. | Median — kept as secondary in case of outlier-dominated tails. Max — kept as secondary in case "farthest-other-persona" is the right anchor. |

## 13b. Smoke-tests at implementation (cheap, mandatory)

These cover the UNVERIFIED items from fact-check round 1; each is a single `assert` and adds <1 s to launch.

1. **Probe-set equivalence with i207 (cross-comparability hook):** at Stage A entry, load `superkaiba1/explore-persona-space-data/issue207_js_gentle/base_model_generations.json` (or the i207 local copy), assert `set(EVAL_QUESTIONS) == set(prior["questions"])`. If unequal, abort and post `epm:failure v1` with `failure_class: data`, `reason: probe_set_drift`. This protects the §5.1 "directly comparable to #207/#228 bystander-rate JS results" framing.

2. **Partial-Spearman fallback validation:** at Stage C entry (regardless of whether pingouin is available), cross-check the inline partial-Spearman formula against an independent implementation on a SYNTHETIC triple — `numpy.random.default_rng(42)` of three correlated vectors (n=100, target Pearson ρ_xy=0.6, Pearson ρ_xz=0.4, Pearson ρ_yz=0.3). Assert the inline result agrees with `scipy.stats.spearmanr` of the rank-residuals to within |Δρ| < 0.001 AND with the parametric t-test p-value to within Δp < 0.001. This decouples the smoke test from any specific data-file column whose values might or might not match a published number. **Do NOT** use the inline formula on `length_rate_correlation_n48.json`'s `cos_l15` field — that field only exists in the N=24 sibling file `length_rate_correlation.json`, and the published #340 ρ=−0.008 is computed on cosine values that are NOT carried in either of the two `length_rate_correlation*.json` files (per stats-critic round 1 finding). If desired, also run the inline formula on the n=24 file's `cos_l15` × `rate` × `log(tokens+1)` columns and record the result in `correlation_results.json::sanity_checks` for human inspection — but do NOT assert against a published number for it.

3. **KL-approximation vs. exact-JS sanity on the 3-persona pilot:** before launching the full 48×48 pairwise pass, run both `kl_only=True` and `kl_only=False` on the 3-persona pilot (`librarian`, `helpful_assistant`, `villain`); assert the off-diagonal Spearman between the two 3×3 matrices is ≥ 0.95 (relaxed from the docstring's 0.99 because n=3 is tiny). Already in §9 as a sanity check; promoted here to mandatory pre-launch.
