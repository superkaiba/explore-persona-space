## 4. Design

### 4.1 Decision: ONE combined entry, not two

Rule (iii) (tail echo) ships as a RULES item inside the width entry rather than a standalone bullet. Justification: both scope items come from the same incident family and the same fix commit (`85c4232517` bundles width pin + tail echo); the tail-echo duty is motivated by exactly this crash class (the width OOM's traceback was the artifact that died with the instance); and the gotchas register precedent (the #1135 entry: two shapes + RULES (i)–(iii) + fix status in one bullet) supports multi-rule single entries. The counter-consideration — the tail echo generalizes beyond smoke width — is handled by stating RULE (iii) generally (any subprocess-launching dispatcher on a lane where only `workload.log` is crash-persisted) and by embedding its grep terms (`inner log`, `workload.log`, `tail`, `ft_mk4.log`) in the entry so a lost-inner-log debugger finds it without the word "smoke".

### 4.2 The new gotchas.md entry (concrete text)

Insert as a new `- ` bullet immediately after the #1135 library-train-seam entry (currently line 33):

> - **Smoke/production parity includes PROCESS WIDTH — a smoke that narrows a ZeRO-3 full-FT launch to `--num_processes 1` OOMs deterministically at the FIRST optimizer step, and a parent dispatcher's narrow-smoke pin is HOST-scoped, never clone-portable.** Single-process ZeRO-3 shards nothing: for a 7B full FT, bf16 weights + grads + fp32 Adam moments (~86 GB) land on ONE 80 GB A100, and because optimizer states allocate lazily the smoke sails through model load + forward/backward and dies at the first optimizer step (traceback signature: `exp_avg_sq` alloc failure in DeepSpeed `stage3.py _optimizer_step`). This is the EXPLICIT-narrowing member of the CVD/width family — sibling of the library-train-seam entry above, whose shape (b) is the DERIVED-width variant (#1112: env-poisoned `torch.cuda.device_count() == 1` composed the same `--num_processes 1`); here the narrowing is a deliberate `if cfg.smoke: return 1` that was CORRECT on the parent's host and wrong on the clone's: #1112's smoke=1 pin was legitimate ONLY because its smoke ran on a 1-GPU GCE instance; the #1315 clone ran its smoke on the 4× A100-80 ft-7b pod, where the pin means "run production ZeRO-3 unsharded". Smoke narrows STEPS / CELLS / GRID — never the process shape, unless the smoke HOST genuinely differs. RULES: (i) when cloning ANY dispatcher, audit every `if cfg.smoke:` / smoke-mode branch that composes launch width or CUDA_VISIBLE_DEVICES — keep production width, and fail LOUD on an under-provisioned host (never silently narrow); (ii) pin the width with an arg-composition regression test asserting the composed `--num_processes <N>` + CVD in BOTH smoke and production modes (worked example: `tests/test_issue1333_dispatch.py::test_ft_launch_width_smoke_invariant`, commit `85c4232517` on the `issue-1333` branch — fails pre-fix; same-name sibling on the `issue-1315` branch; NEITHER on main as of 2026-07-15); (iii) diagnosability sibling, same incident family: a dispatcher's subprocess wrapper (`_run_subprocess`-style) MUST echo the inner log's tail (~120 lines) into the MAIN workload log on child failure — on the GCP lane only `workload.log` is crash-persisted by the EXIT-trap globs, so an inner `ft_mk4.log`-style file dies with the instance and the root cause then needs a from-scratch reproduction (#1333's did — a CPU tiny-real repro). (Incidents: #1315 p1_train smoke, 2026-07-15 — the cloned `_ft_num_processes` returned 1 under smoke, OOM at the first optimizer step, ~1.5 h lost to a GCE provision + crash + diagnostic-boot cycle; RECURRED same day in #1333 p2_train — dispatcher written before the lesson landed, rc=1 ~50 s in on the same 4× A100-80 pod class; fixed with smoke-invariant width + under-provision guard + inner-log tail echo in `issue1333_dispatch.py` on the `issue-1333` branch.) Agent-memory sibling (implementer-scoped): `.claude/agent-memory/experiment-implementer/feedback_smoke_ft_zero3_width_parity.md` — this entry generalizes it to every agent that composes launch width.
