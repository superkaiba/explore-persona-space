# Plan — Task #470: JS divergence vs cosine as a predictor of #411 sycophancy leakage

Predictor-only re-analysis on #411's already-trained cells. **No training, no eval re-generation.** The frozen DV is `per_source.<src>.per_panel_delta` from #411's `analyze_summary.json` (138 cells = 6 sources × 23 bystanders). ## 1. Goal + Hypothesis + Falsification

**Goal (verbatim from frontmatter.goal):** Determine whether persona-to-source Jensen-Shannon divergence between base-model persona-conditioned output distributions predicts #411's per-bystander sycophancy leakage better than layer-20 residual cosine, in particular whether it recovers the strongest anti-cosine leak (software_engineer leaking +0.478 to comedian at its lowest cosine rank).

**Hypothesis (H1):** **If** persona leakage is governed by output-distribution similarity rather than residual-stream geometric proximity, **then** sequence-level JS-similarity will (a) attain a higher pooled-cell |ρ| with Δ than layer-20 cosine, AND (b) rank `comedian` among the top-5 most JS-similar bystanders to `software_engineer` (cosine ranks it 23/23).

**Secondary (H2):** KL asymmetry will be diagnostic: `KL(source ‖ bystander)` (the source's distribution as the reference) will predict Δ better than the symmetric form, because leakage is the source's behavior bleeding *into* the bystander, not vice-versa.

**Kill criterion (the experiment is uninformative if):** every base-model persona-conditioned response distribution sits within JS < 0.05 of every other (predictor floor — no dynamic range to correlate with anything). Concretely: `compute_js_divergence` returns mean per-token JS in **nats** (max ln 2 ≈ 0.693 nats); if std(JS) across the 138 (source, bystander) base-model pairs is **< 0.01 nats** (the smoke test must first assert 0 ≤ JS ≤ 0.6932 to lock the unit), we report "JS predictor has insufficient dynamic range on #411's 24-panel" and the whole comparison fails to discriminate. Report JS in nats throughout; convert to the polarity-aligned similarity `M_js = 1 − JS_nats / ln 2 ∈ [0,1]` only for the figures.

**Falsification (the JS hypothesis is wrong if):** the paired-bootstrap Δρ = |ρ_JS| − |ρ_cosine| CI includes 0 (no reliable improvement) AND `comedian` does not enter the top-10 JS-closest bystanders to `software_engineer` (or enters but JS does not beat the bystander-base-rate predictor there). Either outcome alone is a partial fail; both is a clean fail.

### External (literature)

### 3.6 Pseudocode for Phase 3 (the load-bearing new code)

```python
# src/.../experiments/predictor_jsdiv_470/phase3_sequence_js_kl.py
from explore_persona_space.analysis.divergence import (
    build_teacher_force_inputs, teacher_force_batch,
    compute_js_divergence, compute_kl_divergence,
)

def compute_js_kl_for_cell(
    model, tokenizer,
    source_prompt: str, bystander_prompt: str,
    source_responses: list[str],     # R=8 responses sampled from source
    bystander_responses: list[str],  # R=8 responses sampled from bystander
    probes: list[str],               # 50 #411 held-out wrong claims
    device: str = "cuda:0",
) -> dict:
    """Rao-Blackwellized JS + both-KL for one (source, bystander) cell.

    For each (probe, response) pair, teacher-force the response through
    BOTH source-conditioned and bystander-conditioned base model. Compute
    per-token full-vocab JS / KL over response tokens, mean over positions.
    Then average over R responses × n_probes.
    """
    js_per_probe = []     # length n_probes * R per side; final mean
    kl_src_to_bys_per_probe = []
    kl_bys_to_src_per_probe = []

    # Sample-from-source side
    for probe_idx, probe in enumerate(probes):
        for r_idx, response in enumerate(source_responses[probe_idx * R:(probe_idx+1) * R]):
            batch_inputs, prompt_lengths, response_len = build_teacher_force_inputs(
                tokenizer=tokenizer,
                system_prompts=[source_prompt, bystander_prompt],
                question=probe,
                response_text=response,
            )
            log_probs = teacher_force_batch(model, batch_inputs, prompt_lengths,
                                            response_len, device=device, max_batch=2)
            # log_probs shape: (2, response_len, V) — [0]=src-conditioned, [1]=bys-conditioned
            lp_src, lp_bys = log_probs[0], log_probs[1]
            js_per_probe.append(compute_js_divergence(lp_src, lp_bys).item())
            kl_src_to_bys_per_probe.append(compute_kl_divergence(lp_src, lp_bys).item())

    # Sample-from-bystander side
    for probe_idx, probe in enumerate(probes):
        for r_idx, response in enumerate(bystander_responses[probe_idx * R:(probe_idx+1) * R]):
            batch_inputs, prompt_lengths, response_len = build_teacher_force_inputs(
                tokenizer=tokenizer,
                system_prompts=[source_prompt, bystander_prompt],
                question=probe,
                response_text=response,
            )
            log_probs = teacher_force_batch(model, batch_inputs, prompt_lengths,
                                            response_len, device=device, max_batch=2)
            lp_src, lp_bys = log_probs[0], log_probs[1]
            js_per_probe.append(compute_js_divergence(lp_src, lp_bys).item())
            kl_bys_to_src_per_probe.append(compute_kl_divergence(lp_bys, lp_src).item())

    return {
        "JS_sym": float(np.mean(js_per_probe)),          # canonical headline
        "M_js": 1.0 - float(np.mean(js_per_probe)),       # similarity polarity
        "KL_src_to_bys": float(np.mean(kl_src_to_bys_per_probe)),
        "KL_bys_to_src": float(np.mean(kl_bys_to_src_per_probe)),
        "KL_sym": 0.5 * (float(np.mean(kl_src_to_bys_per_probe))
                         + float(np.mean(kl_bys_to_src_per_probe))),
        "n_probes": len(probes),
        "R_per_side": R,
    }
```

### 3.7 Why code, not a model call?

The persona-distance predictors are mathematical reductions over teacher-forced logit tensors (KL / JS over full-vocabulary distributions), not natural-language classification. A model-call alternative ("ask Claude: are these two personas similar?") would be (a) measuring a different construct (Claude's vibes vs Qwen's output-distribution geometry), (b) un-grounded in the base model whose leakage we're predicting, (c) not what the literature (arXiv 2504.10637, 2507.21509) operationalizes. Code is mandatory here, not a 3.0-paradigm shortcut.

### 3.8 Smoke / sweep architectural parity

**Unification default.** The whole experiment is one process on one GPU. There is no "smoke vs sweep" branch — the dispatcher runs all 6 sources sequentially with the same Phase 3 function, and the "smoke" mode is `--sources software_engineer --probes 5 --R 2`, exercising the identical code path with smaller N. No subprocess isolation: vLLM is NOT used in this experiment (only HF Transformers forward passes), so no TP/PP worker subprocess teardown issues apply.

## 6. Evaluation — metrics, thresholds, figures

### 6.1 Primary verdict

Cosine and JS are **dependent correlations** sharing the DV (the same 138 cells), and they will themselves co-vary (both are persona-similarity scores). Comparing two marginal CIs for overlap is the wrong test — it is both over-conservative (co-varying predictors) and ignores the shared-cell structure. The headline test is therefore a **paired bootstrap of the difference**:

> Resample the 138 (source, bystander) cells with replacement (JOINTLY — the same resampled cell indices feed both predictors); on each resample recompute the source-FE-residualized Spearman ρ for JS and for cosine; record `Δρ = |ρ_JS| − |ρ_cosine|`. Report the 95% CI of Δρ over 10,000 resamples. Cross-check with Steiger's z (1980) / Hotelling–Williams for two dependent correlations sharing a variable.

**JS-similarity beats cosine** iff:
- The paired Δρ 95% CI **excludes 0** (JS reliably improves over cosine on the same cells), AND
- `comedian` enters the top-5 most JS-similar bystanders to `software_engineer` (cosine ranks 23/23) AND JS beats `bystander_base_rate` at that recovery (else the recovery is just the base-rate confound).

The **+0.10 is a separate practical-significance floor on Δρ**, not the significance test (the old "marginal CIs don't overlap" rule is removed). Verdict grid:

| Paired Δρ CI excludes 0? | \|Δρ\| ≥ 0.10? | comedian recovery survives base-rate? | Verdict |
|---|---|---|---|
| yes | yes | yes | **HIGH** — JS reliably + substantially beats cosine, and the diagnostic case is real |
| yes | no | (either) | **MODERATE** — JS reliably beats cosine but the effect is small |
| includes 0 | — | yes | **LOW** — pooled flat, but the diagnostic point case (base-rate-controlled) is suggestive |
| includes 0 | — | no | **falsification** — JS does not beat cosine; report the negative honestly |

Because the pooled cosine ρ **collapses from +0.39 (raw) to +0.065 under source-FE residualization** (verified on #411 data; p≈0.45), report all three pooled variants (raw / source-FE / source-FE+base-rate-partial) for EVERY predictor so the reader sees which residualization carries the result. The verdict is read off the source-FE variant (matches the DV's per-source structure), with the base-rate-partial variant as the confound check.

4. **Response-length confound on sequence-JS.** Report per-persona mean response length (token count) from the Phase 1 samples and the rank correlation between each cell's JS and its source/bystander length differential. Flag if JS rank-order tracks length rather than content.
5. **Cross-predictor correlation.** Report `corr(JS, cosine)` across the 138 cells. If > 0.9 the two are near-redundant and no head-to-head separation is meaningful regardless of which is "right" — state this up front.

### 6.6 Cosine-recipe ladder (interpretation guard)

"Cosine" is two recipes: the #411 baseline is recipe (a) last-prompt-token at layer 20; the plan also computes recipe (b) response-token mean at layers {7,14,21,27}. Report the comparison as a ladder — (a-l20 baseline) → (b-layer-sweep best) → (sequence JS) — so the analyzer can tell apart "JS beats cosine" from "extraction-point matters more than divergence-metric" (if recipe-(b) cosine already closes most of the gap, JS's marginal contribution is small). The H1 baseline for the paired Δρ test stays recipe-(a)-l20 (the published #411 predictor), but the ladder is reported so the framing is honest.

### 6.4 Seed strategy

**Single seed=42** for the headline (matches #411; this is a predictor re-analysis, the trained DV is single-seed by inheritance). The R=8 stochastic-sampling axis in Phase 1 provides sampling noise inside each cell — that's where the variance comes from, not from re-training. Add seed-of-stochastic-sampling 137 + 7 ONLY IF the pooled JS-vs-cosine ρ difference is in [0.05, 0.15] (i.e. in the buffer-zone where another seed could flip the verdict). ### 9.2 Parallelism analysis

- **No data-parallelism axis applies.** Predictor extraction is a single-GPU per-pair op; sharding 138 cells across multiple H100s would save wall time linearly but add deploy complexity for a 5h job. Single pod is correct.
- **No tensor-parallelism axis applies.** Qwen-7B fits comfortably on one H100 80GB at bf16.
- **No sweep parallelism axis applies.** Phases are sequential by dependency (1→2/3→4→5→6).
- **Batched-inference axis: USED.** Phase 1 is one vLLM `LLM.generate()` call across all 9600 prompts. Phase 3 batches the 2-persona teacher-force per cell (the existing `teacher_force_batch` helper).

**Pod intent: `eval` (1× H100).** Override to `inf-70b` or `ft-7b` would buy nothing — the workload is HF-forward-pass-bound on a single Qwen-7B model + a brief vLLM phase. Estimated savings of a 4× H100 pod: minimal (Phase 3 doesn't shard cleanly without significant code rewrite). Plan defaults to `eval`.

### 9.3 Stratification spec (auto-descope priority order)

If wall-time projection exceeds 2× plan (>10h) at the smoke check:
1. **First drop:** R from 8 → 4 (halves Phase 1 + 3 cost; per arXiv 2504.10637 Table 2, R=4 has ~2× the variance of R=8 but still beats single-sample estimators by 5×).
2. **Second drop:** probe count from 50 → 25 (halves again; #411 had 50 in the eval so we keep parity, but pure predictor analysis can tolerate fewer probes).
3. **Third drop:** layer sweep {7,14,21,27} → {21 only} for Phase 2 (saves Phase 2 only — ~10 min — minor).

Min-N to preserve power: R ≥ 4, n_probes ≥ 25.

### 9.4 Disk

Phase 1: 9600 JSON files × ~1kb = 10MB. Phase 3: 138 JSON files × 5kb = 0.7MB. Phase 5: one regression.json. Figures: ~2MB total. Total disk: <50MB; well under the MooseFS 130GB per-pod quota.
