## 4 Design

### 4.1 Leg (a): the hook — `.claude/hooks/guard_piped_git_push.sh` (NEW file)

Script file, not an inline jq one-liner. Rationale: the parse needs a segment split (beyond one grep), both existing multi-step guards are script files with pytest subprocess coverage, and `TestSettingsWiring`-style tests need a stable path. Executable bit set (`chmod +x`, asserted by the wiring test).

**Algorithm (in order; every step fail-soft toward ALLOW):**

1. Read `cmd=$(jq -r '.tool_input.command // empty' 2>/dev/null) || exit 0`; empty → exit 0.
2. **Escape hatch:** session env `EPM_ALLOW_PIPED_PUSH` ∈ {1,true,yes} → exit 0; inline `*EPM_ALLOW_PIPED_PUSH=1*` in the command string → exit 0 (mirror `guard_log_dump.sh` L97/L259–263).
3. **Pipefail carve-out:** `case "$cmd" in *pipefail*) exit 0 ;; esac`. Any occurrence of the literal `pipefail` (covers `set -o pipefail`, `set -euo pipefail`, `bash -o pipefail -c`, `set -eo pipefail`) allows the whole command. Substring-level on purpose: under the cooperative-agent threat model, an author who typed `pipefail` has engaged the rule's own sanctioned escape; a spoof-in-a-string is not an accident class.
4. **Heredoc blanket-allow:** `case "$cmd" in *'<<'*) exit 0 ;; esac` (`guard_log_dump.sh` L109 precedent). This is load-bearing, not just conservative: the project's CANONICAL commit recipe is `git commit -m "$(cat <<'EOF'...EOF)" && git push...`, and a heredoc commit-message line describing this very incident ("never `git push | tail`") would otherwise false-block the implementing session's own commits. Known miss: `... <<EOF ... && git push | tail` in one command — accepted (lint + prose remain defense in depth).
5. **Line-continuation normalization:** `cmd=$(printf '%s' "$cmd" | sed -zE 's/\\\r?\n/ /g')` (`guard_repo_root_branch.sh` L189, verbatim).
6. **Fast pre-filter** (performance — this runs on EVERY Bash call): one `grep -qE` for a producer token AND a `|` present: `echo "$cmd" | grep -q '|' || exit 0`, then `echo "$cmd" | grep -qE '\bgit\b[^|;&]*\b(push|merge)([[:space:]]|$)|\bgh[[:space:]]+pr[[:space:]]+(merge|create)\b' || exit 0`. Two greps + one jq ≈ the per-call cost of each existing hook.
7. **Unit split:** normalize `|&` → `2>&1 |` semantics by rewriting `|&` → `|`; then split the command into pipeline units on `&&`, `||`, `;`, `&`, and raw newline (two-char separators substituted before single-char, exactly the `split_and_label` ordering trick at `guard_repo_root_branch.sh` L215–217; here we do NOT need separator labels — no cross-unit latch — so a plain sed to newline-separated units suffices: `s/&&/\n/g; s/\|\|/\n/g; s/;/\n/g` then `s/&/\n/g` on the remainder, raw newlines already unit boundaries). Single `|` is NOT a unit separator — it stays inside its unit.
8. **Per unit:** strip the whitespace-anchored comment tail (`sed -E 's/[[:space:]]#.*$//'`, `guard_repo_root_branch.sh` L459); skip units whose first non-space char is `#`. If the unit contains no `|`, skip. Else split the unit on `|` into stages; for each NON-FINAL stage, test the producer regex:

   ```
   PRODUCER_ERE='\bgit +(-[^ ]+( +[^ ]+)?( +|$))*(push|merge)([[:space:]]|$)|\bgh +pr +(merge|create)([[:space:]]|$)'
   ```

   (flag-tolerant `git` anchor copied from the #897 detectors at L292; `([[:space:]]|$)` — NOT `\b` — after `push|merge` so `git merge-base --all main HEAD | head -1`, a canonical recipe in `.claude/rules/diff-size-budget.md`, never matches: `-` fails the whitespace requirement). If a non-final stage matches AND that stage does not contain `--dry-run` → **BLOCK**.

9. **Block:** print the message (§4.3) to stderr, `exit 2`. Otherwise `exit 0`.

**Why non-final-stage scoping gives the false-positive properties the brief demands:**

- `git status | grep x && git push` → units `[git status | grep x]`, `[git push]`; producer only in the pipe-free unit → ALLOW.
- `git push origin main || echo failed` → `||` is a unit separator, no `|` inside either unit → ALLOW (covers the one real tree shape, `issue931_dispatch.sh:253`).
- `echo foo | git push` (producer as CONSUMER/final stage) → final stage's exit code IS the pipeline's → ALLOW.
- `out=$(git push 2>&1 | tail -1)` → one unit, producer in non-final stage → BLOCK (correct: the substitution's status is tail's).
- `git log --oneline | head -5 ; git push` → pipe and push in different `;` units → ALLOW.

**Self-test mode:** `--self-test` flag running the §6 acceptance table in-script (mirror `guard_log_dump.sh` L188–257) — dev convenience; pytest is the durable gate.

### 4.2 Leg (b): the lint — `scripts/workflow_lint.py::check_piped_git_push` (EDIT)

Mirrors `check_pipe_python` structurally, item for item:

- **Function** `check_piped_git_push(*, scripts_dir: Path | None = None) -> list[str]` placed adjacent to `check_pipe_python` (~L2531). Walks `sorted((scripts_dir or _REPO_ROOT / "scripts").rglob("*.sh"))`, iterates `_iter_logical_shell_lines`, skips `#`-comment lines.
- **Scope: `scripts/**/*.sh` only** — identical to `check_pipe_python` L2503–2507. NOT `.py` subprocess strings: Python callers overwhelmingly use list-args (no shell pipe possible), `shell=True` piped pushes don't exist in the tree, and the sibling drew the same boundary. The hook covers ad-hoc inline commands; the lint covers committed shell recipes.
- **Regex** (module-level, commented block above it mirroring L668–737):

  ```python
  PIPED_GIT_PUSH_RE = re.compile(
      r"\bgit\s+(?:-[^\s|;&]+(?:\s+[^\s|;&]+)?\s+)*(?:push|merge)(?:\s[^|;&\n]*)?\|(?!\|)"
      r"|\bgh\s+pr\s+(?:merge|create)(?:\s[^|;&\n]*)?\|(?!\|)"
  )
  ```

  Properties: `[^|;&\n]*` cannot cross a command separator, so the trailing `\|` is guaranteed to be a pipe attached to the producer's own segment; `(?!\|)` rejects `||`; `merge` must be followed by whitespace-or-pipe so `merge-base` never matches; producer-as-consumer (`... | git push`) has no trailing `|` → no match. `--dry-run` skip: a matched line containing `--dry-run` in the matched span is skipped (same carve-out as the hook).
- **File-level pipefail tracking:** while iterating a file's logical lines, once any non-comment line contains `pipefail`, skip flagging for the REST of the file (a `set -euo pipefail` header makes every later pipe propagate the failure). `set +o pipefail` re-disable is ignored — fails toward false-NEGATIVE, the documented safe direction for a pre-commit-gating lint (`_upload_or_true_segments` docstring, L2534–2541).
- **No waiver token in v1** — YAGNI, verbatim the `check_pipe_python` stance (L724–726); the tree is clean (§2 item 8), so nothing to waive or grandfather.
- **Error string** (mirror L2524–2530 format): `` f"{sh}:{first + 1}: `git push`/merge-class command piped into a filter — the pipe masks the non-zero exit code, so a rejected push reads as success (#957, 4 sessions 2026-07-02). Run it bare and check the exit code, or add `set -o pipefail`. See CLAUDE.md § Concurrent repo-root committers (#1048)." ``
- **Wiring:** argparse `--check-piped-git-push` with an incident-citing help string (mirror L6739–6749); add to the any-flag disjunction (~L7098); dispatch `if args.check_piped_git_push or no_flags: errors.extend(check_piped_git_push())` (mirror L7169–7170); add one line to the module-docstring check listing (the `* --check-pipe-python` block at ~L86).

## 11 Decision Rationale

1. **Consumer set = ANY pipe consumer** (not just tail/grep/head). *Why:* exit-code masking is consumer-independent (`$?` is the last stage's status regardless of what it is); a named list (`tail|grep|head|sed|awk|wc|tee`) invites trivial drift (`| cut`, `| sort`) while adding no FP protection — the FP protection comes from segment scoping + the pipefail carve-out + the escape hatch, and a false block costs one cheap retry with `pipefail` added, whereas a false allow costs a masked failed merge (#957). *Source:* CLAUDE.md § Concurrent repo-root committers (the rule's remedy — bare or pipefail — is consumer-independent); incident #957. *Alternative:* named consumer set (rejected: drift-prone, no safety gain; the brief's tee question resolves itself — B8 blocks, A3 allows).
2. **Producer set = `git push`, `git merge`, `gh pr merge`, `gh pr create`.** *Why:* the prose rule says "a `git push` (or merge/PR command)"; `gh pr merge | head` is a named acceptance case; `gh pr create | grep -o 'http...'` (URL extraction) masks a failed PR creation and has the same cheap pipefail fix; `git merge ... | tail` masks a conflict. Whitespace-anchored (`merge([[:space:]]|$)`) so `git merge-base` — a canonical recipe in `diff-size-budget.md` — never matches. *Source:* CLAUDE.md prose rule; `guard_repo_root_branch.sh` L292 (flag-tolerant anchor); `.claude/rules/diff-size-budget.md` (the merge-base FP evidence). *Alternative:* push-only (rejected: leaves the prose rule's "merge/PR command" clause unenforced and fails acceptance B3).
3. **Pipefail carve-out = substring `pipefail` anywhere → allow.** *Why:* correct positional parsing of `set -o pipefail` scope (subshells, `bash -c` nesting, `set +o`) is a shell parser, and the branch-guard's #796 history shows partial shell-parsing in bash regex backfires; the substring is exactly the rule's sanctioned escape and can only fail toward ALLOW (a miss, never a block) — the mandated conservative direction. *Source:* `guard_log_dump.sh` L13–14 (when unsure, ALLOW); `guard_repo_root_branch.sh` L71–78 (#796 quote-strip revert). *Alternative:* positional `set -o pipefail`-before-pipe parsing (rejected: complexity without a safety win).
4. **Hook = script file, not inline jq one-liner.** *Why:* the parse is multi-step; script files get pytest subprocess + settings-wiring coverage and a `--self-test`; both existing multi-step guards are scripts. *Source:* `.claude/hooks/guard_log_dump.sh`, `guard_harmful_bank_read.sh`, `tests/test_guard_harmful_bank_read.py` L29–36. *Alternative:* inline (rejected: untestable beyond the L1880-style extraction hack, unreviewable escaping).
5. **Lint scope = `scripts/**/*.sh`, comment-skip, no waiver, bundled in no-flags.** *Why:* byte-for-byte the `check_pipe_python` policy; the tree is clean so v1 needs no waiver/grandfather (YAGNI, L724–726); `.py` subprocess strings excluded (list-args dominate; zero tree hits). *Source:* `workflow_lint.py` L2476–2531, L668–737. *Alternative:* also scan `.claude/skills/**/*.md` fenced recipes (rejected for v1: docs legitimately QUOTE the banned pattern as a negative example; the check would need a quote/fence parser — revisit only if a committed skill recipe ships the pattern).
6. **`--dry-run` carve-out.** *Why:* the incident class is "proceeded believing the push LANDED"; a dry-run lands nothing, so masking it cannot cause the incident. Long form only (short `-n` un-carved: rare, and mis-blocking it costs one retry). *Source:* task brief §2; incident semantics (#957). *Alternative:* no carve-out (rejected: blocks a harmless probe pattern for zero safety).
7. **Heredoc blanket-allow (hook only).** *Why:* the canonical `git commit -m "$(cat <<'EOF'...)" && git push` recipe plus any commit message describing this incident would otherwise false-block — including the implementing session's own commits. *Source:* `guard_log_dump.sh` L109 (identical stance); CLAUDE.md § Committing changes (the HEREDOC commit recipe). *Alternative:* heredoc-body stripping (rejected: the #796 lesson — partial shell parsing hides real commands or breaks quoting).
