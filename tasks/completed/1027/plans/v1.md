# Plan — #1027: Auth-outage detection + respawn suppression in `autonomous_session_watch.py`

`architectural: false` — adds a new fail-soft guard pass + a fleet-level state singleton to the watcher; no status-enum, marker-schema, `task.py` subcommand, or agent/skill relocation. Standard workflow-fix auto-approve path.

## 1. Goal

**Requirement.** When an Anthropic auth outage (or any fleet-wide instant-death cause) kills every freshly spawned session on arrival, the watcher must (a) detect the fleet-wide instant-freeze-respawn signature mechanically, (b) suppress ALL respawn/dispatch arms (backoff) instead of churning, (c) send exactly ONE loud Telegram push per episode naming the failure, and (d) resume automatically via a canary respawn that probes the real session auth path — plus a hard fail-open TTL so a wedged guard can never disable crash recovery indefinitely.

**Acceptance criteria.**
1. A replay of the 2026-07-03 shape (≥3 watcher respawns whose predecessor session lived < ~60 min, across ≥2 distinct issues, inside a 3 h window) activates an outage episode within ~1 tick of the third qualifying respawn.
2. While an episode is active, `_respawn`, `_respawn_stalled_session`, `_respawn_orphan`, `_dispatch_infra_drain` (both callers), `_redrive_capacity_retry`, and the campaign respawn arm all spawn nothing — except one canary respawn per canary interval.
3. Exactly one Telegram push fires at trigger and (at most) one at resolution, per episode.
4. A canary that survives ≥ 20 min ends the episode; a canary that dies re-extends it; an episode older than 6 h expires fail-open with a push.
5. `EPM_DISABLE_AUTH_OUTAGE_GUARD=1` makes the whole feature a no-op; any internal guard failure logs a warning and behaves as "no outage" (respawns proceed).
6. `uv run python scripts/workflow_lint.py` (default run), `ruff check`/`format` on touched files, and the new + existing watcher pytest files pass.

## 3. Design

### 3.1 Detection signal

Every watcher-issued spawn records an event `{issue, ts, arm, prev_spawned_at}` where `prev_spawned_at` is the `spawned_at` of the registry entry being replaced (available in `_respawn(entry)` as `entry["spawned_at"]`; `None` for arms with no prior registration — infra-drain, proposed-infra sweep, most orphan spawns). An event is an **instant-freeze respawn** when `0 ≤ ts − prev_spawned_at ≤ AUTH_OUTAGE_FRESH_DEATH_S`: the predecessor session survived less than one detection cycle (spawn grace 15 min + 2 misses × 10-min cron ≈ 25–45 min for a die-on-arrival session; a healthy session lives hours before any crash, so its respawn never qualifies).

Why this beats transcript-grepping as the PRIMARY signal: it is derived entirely from state the watcher already owns (registry `spawned_at`, its own spawn results), works for any fleet-wide instant-death cause (poisoned API key, broken `claude` binary, reverted Happy patch that escaped `happy_patch_pass`), and has no dependency on log formats. Transcript evidence is used only as best-effort push enrichment (§3.6).

### 3.2 Pure predicates (new, module-level, next to `decide_daemon_blocked_escalation`)

```python
def decide_auth_outage_trigger(
    events: list[dict],          # [{"issue": int, "ts": float, "prev_spawned_at": float|None}]
    now: float,
    *,
    window_s: float,             # default 3 h
    fresh_death_s: float,        # default 60 min
    min_freeze_events: int,      # default 3
    min_distinct_issues: int,    # default 2
) -> bool:
    freeze = [
        e for e in events
        if isinstance(e.get("ts"), (int, float)) and now - e["ts"] <= window_s
        and isinstance(e.get("prev_spawned_at"), (int, float))
        and 0 <= e["ts"] - e["prev_spawned_at"] <= fresh_death_s
    ]
    return (len(freeze) >= min_freeze_events
            and len({e.get("issue") for e in freeze}) >= min_distinct_issues)
```

```python
def decide_auth_outage_canary(
    state: dict, now: float, *,
    canary_alive: bool | None,   # None = daemon down / unresolvable → inconclusive
    canary_interval_s: float,    # default 30 min
    canary_survival_s: float,    # default 20 min
    max_episode_s: float,        # default 6 h
) -> str:                        # "expire" | "resolve" | "canary-failed" | "arm-canary" | "hold"
```
Logic, in priority order: episode older than `max_episode_s` → `"expire"` (fail-open). Canary outstanding and `canary_alive is True` and `now − canary_ts ≥ canary_survival_s` → `"resolve"`. Canary outstanding and `canary_alive is False` → `"canary-failed"` (clear canary fields; the failure re-evidences the episode). Canary outstanding, alive-but-young or `canary_alive is None` → `"hold"`. No canary outstanding and `now − max(started_ts, last_canary_ts) ≥ canary_interval_s` → `"arm-canary"`. Else `"hold"`.

The `min_distinct_issues ≥ 2` requirement is the false-positive guard: a single issue insta-crashing repeatedly is an issue-specific bug already bounded by the per-task caps; only cross-issue correlation reads as a fleet cause.

### 3.3 State + sidecar

- **State singleton** `~/.eps-autonomous/auth-outage.json` (`AUTONOMOUS_REGISTRY_DIR / "auth-outage.json"`): `{"events": [...], "active": bool, "started_ts", "trigger_pushed": bool, "resolve_pushed": bool, "canary_issue": int|None, "canary_ts": float|None, "last_canary_ts": float|None, "evidence": str}`. Atomic write (tmp + `Path.replace`), `isinstance` type-guards on every read-back, corrupt/unreadable file → fresh empty state (fail-open, warning line). Events pruned to `2 × window_s` on every write. Never GC'd (per-issue-prefix sweep only — vm-cpu-guard precedent).
- **Sidecar** `.claude/cache/auth-outage-events.jsonl`, appender modeled on `_append_cpu_guard_sidecar` (line 3144): one row per `trigger` / `canary-armed` / `canary-failed` / `resolve` / `expire` transition, carrying the freeze-event list, distinct issues, and evidence class.

### 3.4 The pass: `auth_outage_pass(dry_run, *, daemon_reachable, live_ids) -> None`

**Placement in `main()`**: immediately after the single per-tick daemon probe (line 17461, `daemon_reachable = _daemon_reachable_with_retry()`) and the `live_ids` computation, and **before** the crash-recovery `_process_entry` loop (line 17466-17469). This requires hoisting `live_ids = _live_session_ids() if daemon_reachable else set()` above the new call (a 3-line reorder of lines 17462-17464). Justification: the pass must arm/refresh suppression before ANY spawn arm runs this tick; it is daemon-INDEPENDENT for episode bookkeeping (trigger/expire advance during daemon flaps) while its canary-survival check degrades to `"hold"` when `live_ids` is unavailable — during a daemon outage no spawn pass runs anyway, so nothing is lost.

Per tick:
1. Kill switch set → return (also clears the module-level canary token).
2. Load state; prune events.
3. If episode active: resolve canary liveness (`canary_alive`): read `issue-<canary>.json`, take `happy_session_id`, check membership in `live_ids`; missing entry / missing sid / `live_ids is None` → `None`. Apply `decide_auth_outage_canary`:
   - `"expire"` → clear episode, sidecar row, one push: `"AUTH-OUTAGE GUARD EXPIRED after 6h without recovery — respawns resume fail-open; investigate auth manually"`.
   - `"resolve"` → clear episode (keep pruned events), sidecar row, one push (deduped on `resolve_pushed`): `"AUTH OUTAGE RESOLVED — canary #<N> survived ≥20 min; respawns resumed"`.
   - `"canary-failed"` → clear canary fields, sidecar row, no push.
   - `"arm-canary"` → set module-global `_AUTH_CANARY_TOKEN = True` (single-flight process; the flock at `_acquire_lock` guarantees one watcher instance).
   - `"hold"` → nothing.
4. If episode NOT active: apply `decide_auth_outage_trigger`; on True → set `active`, `started_ts`, collect best-effort evidence (§3.6), append sidecar row, fire ONE `_telegram_push` (deduped on `trigger_pushed`):
   `"AUTH OUTAGE SUSPECTED: <k> instant-freeze respawns across issues <list> in <m> min — respawns SUPPRESSED (canary every 30 min). Evidence: <auth-string | churn-only>. Check claude auth (/login) on the VM."`

Returning `"suppressed"` from helpers 1-5 rides the existing #843 contract verbatim: callers book no attempt, no backoff, no per-day cap — the next tick re-consults the gate. Non-spawning passes (`pod_safety_pass`, `gate_push_pass`, `stale_blocked_flag_pass`, reapers) are deliberately NOT gated — stopping escaped pods and pushing gate notifications remain correct during an outage.

**Canary mechanics**: when the gate is consulted during an active episode with `_AUTH_CANARY_TOKEN` set, it consumes the token, persists `canary_issue`/`canary_ts` to state, and returns `None` (allow). The first spawn-eligible arm each canary interval becomes the canary — pass order makes this almost always a crash-recovery respawn of a real dead issue session, which probes the exact auth path real sessions use (the `claude` CLI credentials under this `$HOME` via the Happy daemon). If the canary subprocess then fails rc≠0, the outstanding canary simply reads dead at the next check → `"canary-failed"` → re-arm one interval later (bounded delay, no special-casing).

**Why canary-by-observation instead of an API probe**: a watcher-side `anthropic` SDK call authenticates with `.env`'s `ANTHROPIC_API_KEY`, while Claude Code sessions authenticate via the CLI's own OAuth/subscription credential — the 2026-07-03 incident was recovered by `/login`, i.e. the CLI credential, so an API-key probe can read healthy while sessions still die (and vice versa). A probe of the wrong credential is worse than time-based backoff. The canary respawn IS a probe of the true path, and on success it is not wasted work — it is the first recovered session. Rejected alternatives: `claude -p "ok"` one-shot (same auth path, but adds a cron-env binary-resolution dependency + a hung-CLI timeout surface, and duplicates what the canary gives us for free); transcript-grep-as-trigger (log-format-fragile, see §3.1).

## 4. Kill / rollback

- **Kill switch**: `EPM_DISABLE_AUTH_OUTAGE_GUARD=1` (cron-env level) → gate always allows, recorder no-ops, pass returns immediately. Plus `rm ~/.eps-autonomous/auth-outage.json` clears any live episode instantly.
- **Fail-soft contract — FAIL-OPEN, chosen deliberately**: every guard entry point (`gate`, `record`, the pass body) is wrapped so any exception logs one stderr warning and behaves as "no outage" (spawns proceed). Rationale: the failure mode of fail-closed is "crash recovery silently disabled fleet-wide" — strictly worse than the churn this task fixes. The 6 h episode TTL is the second fail-open layer: even a *logically* wedged episode (canary never resolvable) self-expires with a push.
- Rollback = revert the single commit; the state singleton + sidecar are inert data.

## 11. Decision Rationale (load-bearing thresholds)

| What | Value | Why | Source |
|---|---|---|---|
| Instant-freeze window `FRESH_DEATH_MIN` | 60 min | Die-on-arrival respawn cycle = `RESPAWN_SPAWN_GRACE_S` (15 min, line 501) + 2 misses × 10-min cron ≈ 25–45 min; 60 covers it with margin while a healthy multi-hour session never qualifies | Derived from in-repo constants (grace + `--threshold 2` + 10-min cron) |
| Trigger count / distinct issues | 3 / 2 | ≥2 issues separates fleet cause from per-issue bugs (owned by `STALLED_MAX_RESPAWNS=3`, orphan per-day cap); 3 events ≈ the second respawn generation of the first 2-3 affected issues → fires ~60-75 min into a 2026-07-03-shaped outage vs the ~2-3.5 h it actually ran | 2-miss-guard / cap-per-day pattern (in-repo); incident timeline (task body) |
| Detection window | 180 min | ≥2 full freeze cycles of slow churn accumulate; short enough that isolated same-day respawns on different issues don't stack | ungrounded — needs judgment; sized to the incident duration (~2 h) + margin |
| Canary interval | 30 min | 3 ticks; matches the incident's practical recovery granularity, keeps at most ~2 wasted spawns/hour during an outage (vs ~every-tick churn today) | ungrounded — needs judgment; bounded-churn argument stated |
| Canary survival | 20 min | 2 ticks = the same 2-consecutive-checks corroboration used by `decide()` and the pod-safety/zombie passes | in-repo 2-miss precedent (line 573) |
| Fail-open episode TTL | 6 h | Mirrors `EPS_TAKEOVER_TTL_H` fail-open posture ("abandoned suppression costs at most ~6 h") | in-repo takeover-sentinel precedent (#866/#903) |
| Fail-open (not fail-closed) | — | False suppression = fleet-wide crash-recovery blackout, strictly worse than churn | incident asymmetry, §4 |
