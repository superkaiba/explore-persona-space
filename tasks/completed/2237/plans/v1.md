## 1. Goal

Close the plan-time gap that let #2054 plan v16 ship a **mutually unsatisfiable**
§9: it specified 10 parallel `cpu-bigmem` RunPod shards while its own pod-safety
paragraph required `pod-2054-rb789-<shard>` names, and
`dispatch_issue.py launch --backend runpod` structurally cannot mint those names
(`backends/runpod.py:264` hardcodes `f"pod-{issue}"`; `--lane-suffix` covers GCP +
SLURM only). Ship a WARN-first `verify_plan.py` check plus the binding critic-lens
clause, and adjudicate-and-record the two "consider" deliverables.

## 2. The gap (verified by direct read, not inferred)

- `src/explore_persona_space/backends/runpod.py:264-271` — `_runpod_pod_name(issue)`
  returns `f"pod-{issue}"`, no suffix parameter. Exactly 2 references repo-wide
  (definition + the single call site `runpod.py:1424`).
- `scripts/dispatch_issue.py:663-669` — `_lane_suffix_honored_kinds()` returns
  `frozenset({"gcp"}) | _slurm_kinds()`; its docstring states verbatim that "RunPod
  pod names remain per-issue (`pod-<N>`) — the residual
  `lane_suffix_unhonored_by_lane` warning surface."
- `src/explore_persona_space/backends/base.py` — `lane_suffix_for` / `validate_lane_suffix`
  are consumed by `slurm.py` (job names + scratch dirs) and `gcp.py:983`
  (`instance_name_for`). NOT by `runpod.py`.
- **Consequence:** N concurrent `dispatch_issue.py launch --backend runpod` calls for
  one issue all resolve to `pod-<N>`. Best case an error; worst case (the dangerous
  one) silent co-location of all N shards on ONE pod, invalidating every per-shard
  wall/RSS projection the plan booked.
- **How it escaped:** #2054 v16 cleared plan approval, `verify_plan.py` PASS with
  0 FAIL / 0 WARN of 57 checks (twice — v14 and v16), critic round-2 APPROVE on both
  the Methodology and Statistics lenses, and two code-review rounds. Caught only at
  dispatch. Full record: #2054 `epm:progress` v225.

## 3. Two design facts that falsify the obvious implementation

Both established by reading the acceptance fixture
(`tasks/followups_running/2054/plans/v16.md`) rather than assuming its shape. They
are the load-bearing constraints on §4.

**FACT 1 — a launch-argv-counting trigger MISSES the fixture.** v16 contains only
**2** literal `dispatch_issue.py launch` commands, not 10. Its 10-way multiplicity
lives entirely in PROSE: "10 parallel RunPod `cpu-bigmem` shards" (§9 compute row),
"10 pod shards (RunPod `cpu-bigmem`, parallel)" (§4 P1), "10 parallel CPU pods"
(§9 total row), and the loop instruction "repeat over the 8 class shards
RB789_CLASS ∈ {prose, twobytwo, boundary, model} × RB789_ARM ∈ {context, prefix},
plus the 2 matched-n shards" (§9 launch block). So a `len(argvs) > 1` trigger —
the shape c50 uses, and which c52 deliberately dropped — fails acceptance outright.
**The c57-style §9 prose fan-out detector is the multiplicity arm**; the launch-argv
arm supplies lane evidence only.

**FACT 2 — a bare `--name-suffix` token test MISSES the fixture too.** v16 line 298
DOES contain the string `--name-suffix`, inside its teardown command
(`pod.py terminate --issue 2054 --name-suffix <slug> --yes`), and it names the
required pod names explicitly (`pod=pod-2054-rb789-<shard>`). That is precisely the
unsatisfiable contradiction: the plan REQUIRES per-pod names it has no mechanism to
mint. The remedy arm must therefore key on a per-pod **provisioning** mechanism
(`pod.py provision … --name-suffix`), never on the bare token and never on a
`terminate`/naming-convention mention.

| Arm | Predicate | Reused machinery |
|---|---|---|
| **T1 multiplicity** | ≥1 non-fenced line in the §9 window declaring N > 1 **concurrent** pods/shards/boxes/nodes/instances, negation-free | `_c57_section9_window`, `_C57_FANOUT_RE`, `_C57_CONCURRENT_RE`, `_C57_NEGATION_RE`, `_fence_mask` |

| **T3 remedy absence** | the plan names NO per-pod **provisioning** mechanism (see below) | new `_C58_REMEDY_RE` |

**No third fan-out detector is written.** T1 reuses c57's detector verbatim and T2
reuses the c46/c50/c52 argv chain verbatim — per CLAUDE.md § "Reuse existing in-repo
tools/helpers". `_c57_match_snippet` supplies the WARN evidence snippet (centered on
the match span, not the line head — the #1491 lesson c57 already encodes).

**T3's remedy vocabulary** — a plan escapes the WARN by naming any of:

1. a per-pod provisioning call — `pod.py provision` in the same construct as
   `--name-suffix`, or an explicit `pod-<N>-<slug>` / `--name-suffix <slug>`
   **provisioning** convention (matched by requiring a provisioning verb, not the
   bare flag — FACT 2);
2. one pod with N in-pod workers (not a pod-level fan-out);
3. a name-isolating lane for the fan-out (`--lane-suffix` on a SLURM/fellows or GCP
   launch — i.e. `--lane-suffix` satisfies T3 **only** when the fanned launches are
   NOT the RunPod ones);
4. explicit serialization — already absorbed upstream by T1's `_C57_NEGATION_RE`.

**`--lane-suffix` alone must NOT satisfy the check** (explicit body requirement, and
factually correct: RunPod excludes it). Mechanically this is automatic — T2 keys on
`--backend runpod` argvs, and `--lane-suffix` present on a *runpod* argv is exactly
the case `dispatch_issue.py:2024-2027` already warns about at runtime. A regression
test pins it: a plan with a 10-pod §9 fan-out, `--backend runpod`, AND
`--lane-suffix shard1` still WARNs.

- no parseable §9 heading (neither `9.` nor the house-style `§9 <title>` form);
- no concurrent box-level fan-out declared in §9;
- no launch-shaped `dispatch_issue.py` argv in the plan (the custom-driver residual);
- launch argvs present but none dry-parses (c46 arm 1 owns parse warnings);
- **no explicit `--backend runpod`** — a bare/absent `--backend` resolves to `auto`,
  which is runpod-FIRST since #2054 but may land on fellows/SLURM (which honor
  `--lane-suffix`); WARNing on `auto` would be unfalsifiable from plan text.
  Recorded as named residual (i).

**Named residuals — disclosed in the docstring, never to be read as coverage** (the
c52/c57 honesty convention):

- (i) **`auto`-lane blind spot.** An `auto`-routed fan-out that lands on RunPod is

- (ii) **Custom-driver fan-out.** A fan-out driven by a bespoke script with no

- (iii) **§9-confinement.** A fan-out declared ONLY outside §9 is invisible — c57's

**Why WARN-only, not FAIL.** Whether N shard rows each provision their own pod or

## 5. Design — deliverable 2: the critic-lens clause

Add to `.claude/rules/critic-lens-reference.md`, Methodology lens **item 16**
(base at line 495), as a third sibling to the existing extension family:
FAN-OUT ACCUMULATION EXTENSION (line 536, #1541 from incident #1481) and FAN-OUT
STAGING EXTENSION (lines 628-651, #2236 from incident #1739). The #2236 clause is
the structural template, followed element-for-element:

**`FAN-OUT POD-NAME EXTENSION (#2237, from incident #2054)`** — when §9 fans N > 1
CONCURRENT pods for ONE issue, ALSO verify the plan names a mechanism that mints N
DISTINCT pod names on the lane it actually routes to. REVISE when the plan names
NONE of: per-pod `pod.py provision --name-suffix <slug>` calls; a single pod with
N in-pod workers; a name-isolating lane (`--lane-suffix`, honored on GCP + SLURM
only); or explicit serialization. **Conclusion-changing because** RunPod pod names
are per-issue (`pod-<N>`, `backends/runpod.py:264`) with no suffix parameter and
`--lane-suffix` excludes the RunPod lane, so N concurrent same-issue launches
collide — and the dangerous branch is silent co-location of all N shards on ONE
pod, which invalidates every per-shard wall/RSS projection the plan booked while
still producing plausible-looking output. **The prior extensions' escapes do NOT
cover this one** (their triggers are per-pod disk accumulation and same-prefix
staging topology; only the escape list below governs it). **Escapes:** a
single-pod phase; a fan-out on a lane whose names isolate; a plan whose N pods are
provisioned by named per-pod calls; a phase row explicitly serialized
(`sequential`, "one at a time"); `kind: infra|batch|survey` exempt. Plan-time
pod-naming check only, never a mid-run gate.

`workflow_lint.py --check-lens-coverage` is re-run after the edit (acceptance
criterion).

## 6. Adjudications — deliverables 3 and 4 (decided and recorded, per the body)

### D3 — runtime guard in `dispatch_issue.py launch`: **DECLINE the refusal, SHIP the help text.**

A **pre-existing runtime warning already covers half of this** and is not mentioned
in the task body: `dispatch_issue.py:2024-2027` sets
`body["lane_suffix_unhonored_by_lane"] = result.chosen_kind` and logs a warning —
but **only when `--lane-suffix` is actually passed**. The #2054 failure mode passes
no `--lane-suffix` at all, so nothing fires.

Declining a hard refusal, for three reasons: (a) `launch` is a single-launch CLI
invoked N times independently — it cannot see its siblings from argv, so a real
guard would have to query live RunPod state for an existing `pod-<N>`; (b) that
predicate is indistinguishable from a legitimate relaunch/resume against an
existing pod, so it would refuse healthy re-dispatches; (c) it mutates the launch
lifecycle surface — precisely the risk the body flags for D4.

Shipping instead: `--lane-suffix`'s help text states the RunPod exclusion
explicitly, so the help and c58 agree on coverage (the body's stated fallback: "if
declined say why in `--lane-suffix`'s help"). Wording names the honored lanes and
points at c58.

### D4 — thread a name suffix into the router's RunPod lane: **DECLINE, not bundled.**

`_runpod_pod_name` feeds the name the ENTIRE pod lifecycle keys on: `pod.py
terminate --issue N` resolution, `_MANAGED_PREFIXES` recognition, `audit-stale`,
`list-ephemeral`, and the watcher's per-pod shield matching (#1961's structured
`pod=<name>` token). Threading a suffix through the router without simultaneously
threading it through terminate-resolution and shield-matching is exactly the
"risks the lifecycle surfaces" case the body warns against — and a half-threaded
suffix could leave a pod un-terminable by the gated path or un-shielded against
the watcher's auto-stop, i.e. it converts a plan-time gap into a billing/teardown
bug.

Decisive point: **the capability already exists** — `pod.py provision --issue N
--name-suffix <slug>` mints `pod-<N>-<slug>` and is the documented second-pod
convention (`.claude/rules/pods.md`), which per-pod `epm:run-launched` shields and
surgical `pod.py terminate --name-suffix` already assume. The #2054 gap is
therefore a plan-time AWARENESS gap, which deliverables 1+2 close, not a missing
capability. Recorded as a standalone follow-up candidate; explicitly **not**
bundled, per the body's instruction.
