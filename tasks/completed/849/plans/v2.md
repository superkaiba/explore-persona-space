## 0.0 TL;DR (plain English)

- **What I'll run:** I'll add a warn-only "CPU guard" pass to the 10-minute watcher cron. Every tick it reads four tiny kernel files (load average, CPU/memory pressure, available memory) and greps the earlyoom log for silent process kills. When the box has been overloaded for ~20 minutes — or available memory drops below 20% (a single tick, because memory collapses fast) — it writes one attributed row ("these are the top processes and which issue owns them") to a log file and queues one phone notification. The low-memory fire doubles as a pre-kill snapshot, so when earlyoom later kills something, the kill row can name the owning issue.
- **What I expect:** the next fleet-wide overload (like the 2026-07-02 load-226 incident) and every silent earlyoom SIGTERM shows up in `.claude/cache/cpu-guard-events.jsonl` within ~10-20 minutes — with a named culprit whenever a pre-kill snapshot exists, and an explicit `attribution_status: unattributed` otherwise — instead of being invisible for hours. Nothing is ever killed or reniced.
- **What would change my mind:** if the pass itself measurably slows a watcher tick (>~1s added, measured as a delta) or misfires repeatedly on a healthy busy fleet, I'd raise the thresholds or gate a sub-arm off via its kill switch — the design makes both a one-env-var change.

## 4. Design / Method delta

**Method delta vs the existing disk-guard passes (what's genuinely new):**

| Aspect | Disk sub-floor sentinel (existing) | CPU guard pass (new) |
|---|---|---|
| Signal | statvfs free bytes (one reading, level-triggered) | loadavg + PSI (rates) → **2-consecutive-tick persistence** (streak counter in state); PLUS MemAvailable floor → **single-tick urgent fire** (memory collapses faster than the streak window) |
| Attribution | `du`/`repquota` on cache dirs → issue dirs | one `ps -eo pid,pcpu,rss,args` call → pid → `/proc/<pid>/cwd` readlink + cmdline regex → issue; **every fire stores the snapshot in state (the rolling pre-kill record)** |
| Second arm | none | **earlyoom kill surfacing** — journal grep every tick, threshold-independent, persistent journal cursor; kill rows attributed from the latest snapshot with explicit `attribution_status` |
| State saves | only on fire | **every non-dry tick** (the streak counter must persist between ticks; deliberate delta) |
| Sidecar | shared `disk-guard-events.jsonl` | dedicated `cpu-guard-events.jsonl` (task-body requirement; domain-separated grep) |
| Telegram | disk passes push via marker/`_telegram_push` variously | pressure: once per episode (+ growth/reason-change re-alert); kills: rate-limited to 1 enqueue/hour (sidecar keeps full fidelity) |

def cpu_guard_pass(dry_run: bool) -> bool:
    """Escalate-only CPU/memory-pressure + earlyoom-kill observability (#849).
    Warn-only: NEVER kills/renices. Daemon-independent. Fail-soft throughout
    (never-raise helpers + isinstance state guards, per sibling-pass
    convention). Returns True when any sidecar row was written this tick."""
    if not _cpu_guard_enabled():
        print("  cpu-guard: disabled via EPM_DISABLE_CPU_GUARD_PASS; skipping")
        return False
    state = _load_cpu_guard_state()
    now = time.time()
    wrote = False
    kill_arm_ok = True

    # (a) earlyoom kills — EVERY tick, threshold-independent
    last_scan = state.get("last_journal_epoch")
    if not isinstance(last_scan, (int, float)):
        last_scan = now - 1800          # first-run lookback: deliberate ~30 min bound
    since = max(last_scan - CPU_GUARD_JOURNAL_OVERLAP_S,
                now - CPU_GUARD_JOURNAL_MAX_LOOKBACK_S)
    kills = _earlyoom_kills_since(since, dry_run=dry_run)
    if kills is None and not dry_run:
        kill_arm_ok = False
        print("  cpu-guard: earlyoom kill arm unavailable (journalctl failed/missing)",
              file=sys.stderr)     # visible degradation signal (AC4)
        # cursor NOT advanced — the next successful scan re-covers the gap
    elif kills is not None:
        seen = set(k for k in (state.get("recent_kill_keys") or []) if isinstance(k, str))
        snapshot = state.get("last_top_snapshot") if isinstance(state.get("last_top_snapshot"), dict) else None
        new = [k for k in kills if f"{k['journal_ts']}:{k['pid']}" not in seen]
        for k in new:
            issue, status = attribute_kill(k, snapshot)
            _append_cpu_guard_sidecar(
                {"kind": "earlyoom-kill", **k,
                 "issue": issue, "attribution_status": status,
                 "attribution_source": "pre-kill-snapshot" if status == "attributed" else None},
                dry_run)
        if new:
            wrote = True
            last_push = state.get("last_kill_push_ts")
            if not isinstance(last_push, (int, float)):
                last_push = 0
            if now - last_push > CPU_GUARD_KILL_PUSH_MIN_INTERVAL_S:
                _telegram_push("earlyoom killed ... (exit-143 silent SIGTERM) — see .claude/cache/cpu-guard-events.jsonl", dry_run)
                state["last_kill_push_ts"] = now
        state["recent_kill_keys"] = ([f"{k['journal_ts']}:{k['pid']}" for k in kills] + sorted(seen))[:50]
        state["last_journal_epoch"] = now

    # (b) pressure detection (streaked) + mem-avail floor (single-tick urgent)
    la = _read_loadavg()
    load1, load5 = la if la is not None else (None, None)
    ncpu = os.cpu_count() or 1
    psi_cpu = _read_psi_avg10("/proc/pressure/cpu", "some")
    psi_mem = _read_psi_avg10("/proc/pressure/memory", "full")
    mem_avail = _read_mem_avail_pct()
    reasons = cpu_tick_hot_reasons(load5, ncpu, psi_cpu, psi_mem, mem_avail)
    prior_consec = state.get("consecutive_hot")
    if not isinstance(prior_consec, int):
        prior_consec = 0
    fire, consec = decide_cpu_guard_fire(
        reasons, prior_consec, bool(state.get("alerted")),
        state.get("last_alert_load5") if isinstance(state.get("last_alert_load5"), (int, float)) else None,
        state.get("last_alert_reasons") if isinstance(state.get("last_alert_reasons"), list) else None,
        load5)
    if not reasons:   # recovery -> episode reset (journal cursor fields preserved)
        state.update(consecutive_hot=0, alerted=False,
                     last_alert_load5=None, last_alert_reasons=None)
    else:
        state["consecutive_hot"] = consec
    if fire:
        top = _top_processes(dry_run=dry_run)
        # rolling PRE-KILL snapshot: stored on EVERY fire (incl. mem-avail
        # single-tick fires) so a subsequent earlyoom kill is attributable
        state["last_top_snapshot"] = {"ts": now, "procs": top}
        print("vm-cpu PRESSURE: load5=... nproc=... psi ... mem_avail=...% — top: ...", file=sys.stderr)
        _append_cpu_guard_sidecar({
            "kind": "vm-cpu-pressure", "band": "cpu-pressure", "reasons": reasons,
            "load1": load1, "load5": load5, "nproc": ncpu,
            "psi_cpu_some_avg10": psi_cpu, "psi_mem_full_avg10": psi_mem,
            "mem_avail_pct": mem_avail,
            "consecutive_hot": consec, "top_processes": top,
            **({} if kill_arm_ok else {"kill_arm": "unavailable"}),
        }, dry_run)
        _telegram_push("VM CPU/mem pressure: ... warn-only; see cpu-guard-events.jsonl", dry_run)
        state.update(alerted=True, last_alert_load5=load5, last_alert_reasons=reasons)
        wrote = True
    if not dry_run:
        _save_cpu_guard_state(state)   # streak persistence NEEDS per-tick saves
    return wrote

## 11. Decision Rationale

- **load5 > 1.5×nproc.** Why: 50% sustained oversubscription; healthy full utilization (load≈nproc) never fires; the incident ran at 5.8-7× and today's live gap at 1.9-2.2×. Source: task #849 body example + incident numbers (2026-07-02, load 186-226 / nproc 32; live probe loadavg 61.84/32). Uses load5 (2nd `/proc/loadavg` field) — less noisy than load1 at a 10-min cadence.
- **2 consecutive ticks (~20 min) for the RATE signals.** Source: in-repo precedent — `main()` `--threshold` default 2, documented "2 = ~20 min at a 10-min cron" (`autonomous_session_watch.py` L14366-14371).
- **PSI cpu `some avg10` > 50.** Why: `some` = share of wall time ≥1 runnable task stalled for CPU — 50% sustained is unambiguous oversubscription. Source: kernel PSI semantics (https://docs.kernel.org/accounting/psi.html) + live probe (76% under the active incident regime vs ≈0 healthy).
- **PSI memory `full avg10` > 10.** Why: `full` = all non-idle tasks stalled simultaneously — direct thrash indicator. Source: kernel doc semantics (same URL); the specific 10% default is `ungrounded — needs smoke-test` beyond doc semantics (no in-repo precedent); warn-only + env-overridable makes miscalibration cheap; flagged in §12. NOTE (alternatives critique): on this zero-swap VM this leg may rarely fire pre-kill — the MemAvailable floor below is the load-bearing pre-kill memory leg.
- **MemAvailable < 20%, SINGLE-TICK (v2 addition — the alternatives Must-Fix).** Why: earlyoom kills at ≤10% MemAvailable (its own journal config line, live-captured); a 20% floor fires one band earlier, while culprits are still alive and attributable — and memory can collapse 15%→3% inside one 10-min interval, so a 2-tick streak would fire post-kill. In a pure-memory incident (no CPU oversubscription, zero swap → PSI-full near-silent until terminal thrash) this is the only pre-kill, attributable record. Source: the round-1 alternatives critics (Claude ready-made shape + Codex Must-Fix) + the earlyoom config line + /proc/meminfo MemAvailable semantics (kernel-doc, standard since 3.14). The 20% value is `ungrounded — needs smoke-test` within ~2×; warn-only, env-overridable (`EPM_VM_CPU_GUARD_MEMAVAIL_PCT`).
- **Rolling pre-kill snapshot + `attribution_status` on kill rows (v2 addition).** Why: an earlyoom-killed pid has no `/proc/<pid>/cwd` — pid→issue is capturable ONLY pre-kill; storing the top-process snapshot on every fire (incl. mem-avail fires) gives kill rows a best-effort attribution source, and the explicit `attribution_status: attributed | unattributed` field keeps the claim honest when the snapshot misses. Source: alternatives reconciler binding verdict (both fix branches adopted: concrete pre-kill path + narrowed claim).
- **Top-N = 5 (CPU∪RSS union).** Source: `VM_DISK_SUBFLOOR_TOP_N = 3` precedent (L1632), widened because two axes are unioned.
- **Re-alert growth 0.25.** Source: `VM_DISK_SUBFLOOR_GROWTH_REALERT = 0.10` precedent (L1629); load is noisier than disk-free so the band is wider. Ungrounded numeric within a factor of ~2; warn-only.
- **State at `~/.eps-autonomous/vm-cpu-guard.json`.** Source: in-repo convention — every watcher dedup state lives under `AUTONOMOUS_REGISTRY_DIR` (`vm-disk-subfloor.json` L1778, `vm-disk-data.json` L2043, `happy-patch-alert.json` L2214); `.claude/cache/` holds event *streams*, not dedup state. GC-safe (singletons unswept, `_gc_target_paths` L9893).
- **isinstance type-guards on state read-back (v2, standing rec).** Source: sibling precedent — `vm_disk_pass` L13230-13235 / `data_disk_pass` L2126-2128 guard exactly this JSON-loaded-field vector; call site stays unwrapped like every sibling daemon-independent pass (methodology reconciler).
- **Sidecar at `.claude/cache/cpu-guard-events.jsonl`.** Source: task body names it; parallels `disk-guard-events.jsonl` (L1966-1986) with a domain-separated stream.
- **Telegram via `_telegram_push` (digest queue).** Source: L13920-13966 + the 2026-06-12 batching decision recorded there; kill-push rate limit 3600 s bounds storms (journal shows repeated kills within minutes on 2026-06-28); sidecar keeps full fidelity. The 3600 s value is a convenience default — flagged ungrounded, warn-only.
- **`journalctl --since @<epoch>` + 60 s overlap + key-dedup + 24 h re-scan cap (v2 tightened).** Source: systemd.time(7) epoch syntax, live-verified; overlap-plus-dedup prefers duplicate-suppression over boundary drops; the 24 h cap bounds >50-kill backlog re-emission against the 50-key dedup cap (statistics standing rec).
- **First-run journal lookback ~30 min — DELIBERATE bound (v2 documented).** Why: the watcher is an ongoing monitor, not a backfill tool; older historical kills are out of scope on first deploy. Source: Codex methodology non-blocking note, adopted as a documented design decision.
- **Single `ps` call (no two-sample delta).** Why: keeps the firing-tick cost ~100 ms; lifetime %CPU is representative for the hours-long sustained class. Source: `_top_issue_cache_paths`'s cheap-single-subprocess attribution precedent (L1669-1720). (A fire-tick-only two-sample /proc delta remains implementer latitude per the alternatives critic — not required.)
- **dry-run performs zero `subprocess.run`.** Source: the #681 r3 convention (L1685-1691, L1738-1743).
