### 4b. In-scope workflow-surface fix 1 of 6: `task_workflow._iter_jsonl`

`src/explore_persona_space/task_workflow.py` is explicitly IN the workflow-fix surface, and the task body's Scope section instructs "cover any live JSONL-read hits in the same class". One-line semantic change at line 2342:

```python

    for lineno, line in enumerate(text.splitlines(), 1):
# AFTER
    # split("\n"), NOT splitlines(): raw U+2028/U+2029/NEL inside ensure_ascii=False
    # notes are Unicode line boundaries that would shred valid records into
    # skip-malformed fragments = silent marker loss (gotchas.md; #825 → #950).
    for lineno, line in enumerate(text.split("\n"), 1):
```

Plus one sentence appended to the `_iter_jsonl` docstring's tolerance paragraph noting the `split("\n")` choice and why. Safety analysis (verified in the v1 session, wording SCOPED per round-1 concern 6): **within the project's writer contract** — records terminated by `\n` (or `\r\n`), as written by `_append_line_locked`/`post_event` and every LF/CRLF writer — the change is strictly recovery-positive: the trailing empty string after the final `\n` is already skipped by the `if not line.strip()` guard; a `\r\n`-ended line leaves a trailing `\r` that `json.loads` accepts as whitespace; controls that splitlines also splits on (`\x0b` etc.) cannot appear raw in our `json.dumps` output (escaped); every `\n` boundary splitlines honored is also a `split("\n")` boundary, so no LF/CRLF-delimited record that previously parsed can stop parsing. The one theoretical counterexample — a file using a BARE `\r` as its record delimiter, which `splitlines()` would split and `split("\n")` will not — is unreachable from the paired writer (which always appends `"\n"`), so the recovery-positive claim is scoped to project-written LF/CRLF files rather than asserted unconditionally (Source: #950 round-1 critique, concern 6).

### 4c. The workflow_lint.py check — decision: **YES** (now FOUR signals)

One-line rationale: the trap recurred 3× in a single incident, is structurally invisible to ASCII smokes, and has ~12 legacy experiment-script sites PLUS six live workflow-surface sites on `main` showing the pattern is endemic — the same recurrence profile that earned `--check-upload-as-file` its lint; a narrow multi-signal AST pattern + file-level grandfather allowlist keeps the false-positive surface near zero against the 447 benign `splitlines` hits.

**Check name:** `--check-jsonl-splitlines`, function `check_jsonl_splitlines(*, scan_roots: tuple[Path, ...] | None = None) -> list[str]`, module-docstring entry added to the numbered check list (pattern of lines 56/116), flag added to the `no_flags` disjunction (line 6099) and dispatched `if args.check_jsonl_splitlines or no_flags:` (pattern of lines 6168-6180).

**Scan roots:** `scripts/**/*.py` AND `src/explore_persona_space/**/*.py` (NOT `tests/`, `external/`, `archive/`). Rationale for including `src/`: two of the six live workflow-surface instances (`task_workflow.py`, `task_progress.py`) are in `src/`; scanning `scripts/` alone would have missed them. Scanning experiment scripts is precedent-consistent (`--check-upload-as-file` does): the *lint* is the workflow-surface change; the files it scans need not be.

**Detection (AST, per file):** flag an `ast.Call` whose func is `ast.Attribute(attr="splitlines")` when ANY of:
- **(a) chained-read signal:** the receiver expression chain contains a `read_text` call AND the receiver expression's source segment (`ast.get_source_segment`) contains `"jsonl"` case-insensitively — catches `jsonl_path.read_text().splitlines()`, `(d / "pool.jsonl").read_text().splitlines()`, `Path(jsonl).read_text().splitlines()`;
- **(b) receiver-name signal:** the receiver is a bare `ast.Name` whose id matches `/jsonl/i` — catches `jsonl_text.splitlines()`;
- **(c) function-name signal:** the call sits inside a `FunctionDef`/`AsyncFunctionDef` whose name matches `/jsonl/i` — catches the `_iter_jsonl` shape (receiver `text`, read on a separate line), i.e. prevents reintroduction of the exact bug fixed in §4b;
- **(d) events-path signal (NEW in v2 — decision: YES).** The receiver chain contains a `read_text` call AND (the chain's base `ast.Name` id matches `/^ev(ents)?_path$/i` OR the receiver chain's source segment contains the literal `events.jsonl` or `comments.jsonl`). One-line rationale: all five §4b′ sites evade signals (a)-(c) — receivers `ev_path`/`events_path`, no "jsonl" token anywhere the three signals look — so without (d) the exact shape this task fixes could be silently REINTRODUCED at any of the five sites (or a new one) and the lint would stay green; (d) pins the fixed shape, responsive to the reconciler's lint-replay finding, not new scope (Source: #950 round-1 critique). The `ev_path`/`events_path` names are the project's uniform convention for `events.jsonl` paths, keeping the false-positive surface near zero; the live-tree test catches any surprise, and the waiver comment covers a genuinely-safe residual.

**Unparseable-file behavior (round-1 concern 3 — precedent read, decision stated):** the `--check-upload-as-file` precedent (workflow_lint.py:3074-3078) SILENTLY skips a `SyntaxError` file with only an inline source comment. This check strengthens that to **skip-with-report**: a file that raises `SyntaxError` (does not parse) or `UnicodeDecodeError` (non-UTF-8) is skipped WITHOUT failing the check — syntax validity is ruff/pytest's enforcement job, not this lint's — but a one-line non-fatal notice (`note: --check-jsonl-splitlines skipped unparseable <path> (<exc class>)`) is printed so the skip is never silent. `ast.get_source_segment(...) is None` is a PER-NODE condition, not a file condition: the segment-dependent predicates (a)/(d-literal) simply evaluate as non-matching for that node (the other signals may still flag it); no file skip, no notice.

**Deliberate false negatives (documented in the check docstring, accepted):** dataflow through a non-jsonl, non-events-path-named variable (`out_path = ... / "x.jsonl"` … `out_path.read_text().splitlines()` — the #825 u2_gen site itself evades signals a-d; full dataflow is out of proportion for a lint), and python-in-shell heredocs (`.sh` files are not AST-scannable — the #825 dispatch.sh site class). The gotchas entry + agent memory + code review carry those; the lint is the cheap backstop for the common shapes, and the entry text says so (§4a).
