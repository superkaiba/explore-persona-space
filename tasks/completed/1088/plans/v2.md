### 5.1 New regexes (insert after `_COUNT_PAREN_LINK_RE`, ~line 6783)

```python
# Pattern C position: a parenthetical immediately AFTER a pinned HF markdown
# link — the #833 footer shape. The link-TEXT-capturing sibling of check 32's
# _HF_LINK_THEN_PAREN_RE (which starts at `\](` and cannot see the text; the
# text carries the backtick namespace tokens the per-namespace form needs).
_HF_LINKTEXT_THEN_PAREN_RE = re.compile(
    r"\[(?P<text>[^\]]{1,300})\]\((?P<url>https?://huggingface\.co/[^)\s]+)\)"
    r"\s{0,2}\((?P<paren>[^()]{1,300})\)"
)
# Phrase-anchored count claims INSIDE the paren (any position — the phrase,
# not the position, is the precision anchor). "listed" is the one tolerated
# filler (#833's original: "908 files listed per namespace"). Mutually
# exclusive by adjacency: "files per namespace at the pinned revision"
# matches ONLY the per-namespace form ("per namespace" intervenes before
# "at"). files-only (no shards) — shards-per-namespace is unseen in the wild.
_FILES_PER_NAMESPACE_RE = re.compile(
    r"\b(?P<count>\d{1,3}(?:,\d{3})+|\d{1,6})\s+files?\s+(?:listed\s+)?per\s+namespace\b",
    re.IGNORECASE,
)
_FILES_AT_PINNED_REV_RE = re.compile(
    r"\b(?P<count>\d{1,3}(?:,\d{3})+|\d{1,6})\s+files?\s+(?:listed\s+)?"
    r"at\s+the\s+pinned\s+revision\b",
    re.IGNORECASE,
)
# A backtick directory token in link TEXT: `analysis_tensors_nonemit/` — the
# trailing slash is the directory signature (a dotted token without it is a
# FILE claim, check 32's territory).
_BACKTICK_DIR_RE = re.compile(r"`(?P<ns>[A-Za-z0-9_\-./]{1,120}/)`")
```

### 5.2 A/B misclassification guard (edit `_COUNT_NOUN_RE` ~6769 and `_COUNT_PAREN_LINK_RE` ~6778)

Append a negative lookahead after the noun group in both regexes:

```python
(?P<noun>files?|shards?)\b(?!\s+(?:listed\s+)?per\s+namespace\b)
```

Rationale: without it, a hypothetical `[891 files per namespace @sha](url)` link text (Pattern A) or `(891 files per namespace): [x](url)` (Pattern B) would extract a WHOLE-prefix claim and compare 891 against the parent's total (≈9,600+ files in #833's case) → a guaranteed FALSE WARN with wrong semantics. The guard makes per-namespace-qualified counts invisible to A/B; the per-namespace gatherer covers only the observed link-then-paren position (A/B-position per-namespace claims become a documented recall sacrifice, never a wrong comparison). ### 5.3 New gatherer (insert after `_gather_hf_count_claims`, ~line 6867)

```python
def _gather_hf_per_namespace_claims(
    body: str,
) -> list[tuple[int, str, str, str, str, tuple[str, ...]]]:
    """Extract ``(claimed_count, repo_id, repo_type, sha, link_prefix,
    namespaces)`` tuples for "N files (listed )?per namespace" claims in a
    parenthetical immediately AFTER a hex-pinned HF ``/tree`` markdown link
    (check 30 Pattern C, the #833 footer shape). ``namespaces`` are the
    backtick ``dir/`` tokens in the link TEXT (trailing slash stripped);
    an empty tuple means the claim was extracted but its namespaces are
    unresolvable (surfaced as `unverified`, never probed, never a WARN).
    Fence-stripped; deduplicated; ``/blob/`` links and moving refs are out
    of scope (same URL guards as ``_gather_hf_count_claims``)."""
    kind_to_type = {"datasets": "dataset", "spaces": "space", None: "model"}
    stripped = _strip_fenced_blocks(body)
    out: list[tuple[int, str, str, str, str, tuple[str, ...]]] = []
    seen: set[tuple] = set()
    for lm in _HF_LINKTEXT_THEN_PAREN_RE.finditer(stripped):
        url = lm.group("url").rstrip(".,;:!?")
        m = _HF_HUB_TREE_BLOB_URL_RE.match(url)
        if m is None or f"/tree/{m.group('sha')}" not in url:
            continue
        namespaces = tuple(
            dict.fromkeys(  # order-preserving dedup
                ns.strip("/")
                for ns in _BACKTICK_DIR_RE.findall(lm.group("text"))
                if ns.strip("/")
            )
        )
        repo_id = f"{m.group('owner')}/{m.group('repo')}"
        prefix = (m.group("path") or "").rstrip("/")
        for cm in _FILES_PER_NAMESPACE_RE.finditer(lm.group("paren")):
            count = int(cm.group("count").replace(",", ""))
            key = (count, repo_id, m.group("sha"), prefix, namespaces)
            if key in seen:
                continue
            seen.add(key)
            out.append(
                (count, repo_id, kind_to_type[m.group("kind")], m.group("sha"),
                 prefix, namespaces)
            )
    return out
```

### 5.6 Decisions on the five open design points

1. **"N files at the pinned revision" — own pattern, same scan.** It gets its own anchored regex (`_FILES_AT_PINNED_REV_RE`) but rides the same `_HF_LINKTEXT_THEN_PAREN_RE` iteration and feeds the EXISTING whole-prefix tuple pipeline (no new verification semantics). Mutually exclusive with the per-namespace form by phrase adjacency (verified on the #833 text). Included because the candidate names it, it costs ~4 lines, and the corpus grep shows zero FP exposure.
2. **Phrase-anchored, any position inside the paren — not generic mid-paren counts.** A generic `_COUNT_NOUN_RE` scan of link-adjacent parens would match e.g. `(96 raw JSONs and 3 files were quarantined)` → a whole-prefix comparison with unrelated semantics → false WARN. The anchor phrases ("files per namespace", "files at the pinned revision") are self-disambiguating, so position-freedom inside the paren adds the needed recall (the #833 count sits after an `=`) at no precision cost.
3. **Per-namespace resolution: backtick `dir/` tokens from link TEXT; conservative fallback.** Probe `<link-prefix>/<ns>` per named namespace through the shared memo/cap. NO fallback probing when no names are extractable: an unverified note only. Rejected alternatives: (a) probing the parent and grouping files by top-level child — the #833 parent (`issue833_onpolicy_map`) contains OTHER children (`analysis_tensors/` 4,320 npz, `raw_completions/`, …) the claim does not cover → guaranteed false WARN; (b) divisibility heuristics — grounds a WARN on guessed semantics. Both violate "never ground a WARN on a partial read".
4. **"listed" is tolerated as the ONE optional filler** (`(?:listed\s+)?`) — it is the observed original wording. No wildcard fillers (`(?:\w+\s+)?` would admit arbitrary qualifiers and erode the anchor).
5. **Shard one-sidedness does not interact.** The new forms match `files?` only; `N shards per namespace` is unseen and stays a documented recall sacrifice. Both new forms are two-sided exact (files semantics), preserving the existing files-two-sided / shards-one-sided split untouched.
