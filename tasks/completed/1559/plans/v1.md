- **Fork pick: option (b) — document verify-then-override.**

  - **Why:** kills the observed friction (one override round-trip, incident session 0da7071f) at zero behavior change, preserving fail-closed + pure-string properties and the B10 pin. The block message is the right delivery point: the agent who needs the recipe is, by construction, reading that message.

Guard-family precedent: no sibling hook probes runtime state (Source: §2, `guard_harmful_bank_read.sh` / `guard_log_dump.sh` / `guard_lessons_edit.sh`).
  - **Against (c) no-change:** the task body's own counterpoint ("override path exists precisely to force verify-then-override — arguably working-as-designed", emitter confidence LOW) is half-right — the FLOW is correct, but it is currently undiscoverable at block time: header lines 56–59 and message lines 352–354 name only the dir-flip and human-directed-purge uses, so the incident agent had to derive the flow. Six lines of prose + two pins convert the next occurrence to self-service; cost ≈ nothing, and C1 makes the doc durable. (Source: task #1559 body; block-message lines 344–355.)
