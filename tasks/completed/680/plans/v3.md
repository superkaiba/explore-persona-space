## 4. Design

### 4.1 The new ladder — rung by rung

The base machine (`base = machine_for_intent(spec)`) is A100-80 for the
7B-training intents (`lora-7b`/`ft-7b`) and L4 for `eval`/`debug`. The
A100-40 fallback (`a40 = a100_40_fallback_for_intent(spec)`) is non-None
ONLY for the fits-in-40GB single-GPU intents (`lora`/`lora-7b`/`eval`/
`debug`). The flex-start rung uses the SAME base machine as on-demand
(A100-80 for training) — flex-start draws the preemptible A100-80 pool.

**Plain-English condition names** (used throughout this plan; config slugs
are the rung labels, rightmost):

| Plain-English name | What it tests | What it controls for | Rung label slug |
|---|---|---|---|
| Spot base (short only) | live spot A100-80 pool first | on-demand stockout | `spot_a100_80` |
| Spot 40GB (short + fits-40) | spot A100-40 pool | spot-80 miss | `spot_a100_40` |
| Flex base | DWS queued A100-80 | spot miss / long job | `flexstart_a100_80` |
| On-demand base | guaranteed A100-80 | flex/spot miss | `ondemand_a100_80` |
| On-demand 40GB (fits-40) | guaranteed A100-40 | on-demand-80 miss | `ondemand_a100_40` |
| RunPod terminal | last-resort paid compute | all GCP + SLURM dry | (RunPod lane) |

**SHORT jobs** (`_is_short_job(spec, base) == True` — known length ≤
`EPS_GCP_SPOT_MAX_GPU_HOURS` (default 2), OR `spec.extra["spot_tolerant"]`):

1. **Spot base** — `spot_a100_80` (SPOT, base machine). *Always present
   for a short job.*
2. **Spot 40GB** — `spot_a100_40` (SPOT, a40). *Only when `a40 is not
   None`.*
3. **Flex base** — `flexstart_a100_80` (FLEX_START, base machine).
4. **On-demand base** — `ondemand_a100_80` (STANDARD, base machine).
5. **On-demand 40GB** — `ondemand_a100_40` (STANDARD, a40). *Only when
   `a40 is not None`.*
→ then the lane order's next lane (SLURM) → **RunPod terminal**.

A short `lora-7b` (a40 present) yields 5 GCP rungs; a short `ft-7b` (no
a40) yields 3 (spot-80, flex-80, ondemand-80).

**LONG / UNKNOWN-length jobs** (`_is_short_job == False` — known length >
threshold, OR unknown length where `_estimated_gpu_hours` returns None):
SKIP spot entirely (preemption too costly).

1. **Flex base** — `flexstart_a100_80` (FLEX_START, base machine). *Queues
   for capacity instead of failing; non-preemptible once running.*
2. **On-demand base** — `ondemand_a100_80` (STANDARD, base machine).
3. **On-demand 40GB** — `ondemand_a100_40` (STANDARD, a40). *Only when
   `a40 is not None`.*
→ SLURM → **RunPod terminal**.

A long `ft-7b` yields 2 GCP rungs (flex-80, ondemand-80); a long `lora-7b`
yields 3 (flex-80, ondemand-80, ondemand-40).

**Design rationale for putting flex AFTER spot on short jobs:** a short
job absorbs a spot preemption cheaply (clean TERMINATE → #659 failover /
checkpoint-resume), and spot is the cheapest live pool, so spot leads;
flex sits between spot and on-demand as the "queue for capacity rather
than fail" middle rung. For long jobs spot is barred (the body's rule),
so flex — non-preemptible-once-running, queues for capacity — leads.

**The above is the FULL variant — conditional on the Implementation-step-0
probe verdict (PASS/INCONCLUSIVE). If the probe FAILs (A2 rejects
FLEX_START), the implementer ships the §13 contingency instead, which is a
STRICT SUBSET of this design (the flex rung dropped from both branches).**

### 4.2 The new `_flex_start_rung` helper

Reuse the existing `_with_machine(spec, machine, provisioning=...)` — it
already threads `spec.extra["provisioning_model"]` + the machine override.
A FLEX_START rung is simply `_with_machine(spec, base,
provisioning="FLEX_START")`. The `request_valid_for_duration` default
("2h") and the 7-day `max_run_duration` cap are resolved DOWNSTREAM in
`gcp.py` at render time (`resolve_request_valid_for_duration`,
`_assert_max_run_within_flex_cap`) — the router does NOT need to set them.
So rather than a brand-new helper, the cleanest change is a thin named
wrapper for readability + a single place to thread a non-default request
window if ever needed:

```python
def _flex_start_rung(spec: RunSpec, machine: MachineSpec) -> tuple[RunSpec, str]:
    """A FLEX_START (DWS flex-start) ladder rung for `machine`.

    Threads provisioning_model=FLEX_START via _with_machine; the
    request-validity window (DEFAULT_REQUEST_VALID_FOR_DURATION='2h') and
    the 7-day max-run-duration cap are resolved/asserted downstream at
    gcp.render_create_argv. Label `flexstart_<gpu_kind>`.
    """
    return (_with_machine(spec, machine, provisioning="FLEX_START"),
            f"flexstart_{_machine_label(machine)}")
```

**Why code, not a model call?** N/A — no unstructured-data heuristics in
this design (pure control-flow change).

## 5. Conditions and Controls

The "conditions" are the ladder rungs (named in §4.1's table). The control
that each rung's ordering rules out:

- **Spot-first (short)** rules out the confound that a launch fails the
  exhausted on-demand pool before reaching the live spot pool (the #656
  on-demand-first defect).
- **Flex-first (long)** rules out spot-preemption cost for a long job while
  still reaching a live (queued) capacity pool before the exhausted
  on-demand pool. *(Present in the full variant only; absent in §13.)*
- **On-demand demoted (both branches)** is retained as the guaranteed-
  capacity rung when spot/flex both miss — controls for the case where the
  preemptible pools are ALSO dry but on-demand has freed up.
- **RunPod terminal** controls for total GCP+SLURM exhaustion (the only
  paid-by-default rung; reached last).

The single experimental variable is the GCP rung ORDER (and the addition
of the flex rung). On-demand rung membership, the A100-40 fallback gate,
the `_is_short_job` gate, the per-day cap mechanism, the failover paths,
and the RunPod-terminal contract are all UNCHANGED.

## Implementation step 0 — flex-start feasibility probe (live, mandatory, BEFORE any code change)

The flex rung's viability rests on A2 accepting
`--provisioning-model=FLEX_START`. The precise GCP per-machine-type
consumption tables CONTRADICT this (§12 #1); the gcloud flag validator is
machine-agnostic and proves nothing. **A live probe on the real `eps-gcp`
project is the only definitive resolution, and it MUST run BEFORE the
implementer edits `_gcp_ladder_specs`.**

**Exact command (run from the VM):**

```bash
gcloud --configuration=eps-gcp compute instances create eps-680-flexprobe \
  --zone=us-central1-a \
  --machine-type=a2-ultragpu-1g \
  --provisioning-model=FLEX_START \
  --request-valid-for-duration=10m \
  --max-run-duration=20m \
  --instance-termination-action=DELETE \
  --image-family=debian-12 \
  --image-project=debian-cloud
```

Probe `a2-ultragpu-1g` because it is the single-GPU A100-80 machine — the
`lora-7b` flex base (`INTENT_TO_MACHINE["lora-7b"]`/`["lora"]` =
`a2-ultragpu-1g`, `gcp.py:289-293`). **The ladder's flex rung for `ft-7b` is a
DIFFERENT machine type — `a2-ultragpu-4g` (`gcp.py:294-298`), NOT
`a2-ultragpu-1g`** (the v2 prose mis-stated `a2-ultragpu-1g` as the `ft-7b`
base — corrected here). The GCP consumption-option acceptance (does this series
accept `--provisioning-model=FLEX_START`) is keyed by machine **SERIES**, not by
the per-GPU-count variant: A2 Ultra A100-80 is one row of the
"Consumption option availability by machine type" table (`compute/docs/
accelerator-optimized-machines`, the §12-#1 cite at L578-582) whether the
variant is `1g` or `4g`, so the `a2-ultragpu-1g` flex-start verdict transfers to
`a2-ultragpu-4g`. v3 ALSO runs a `a2-ultragpu-4g` insurance probe (below) so
the transfer is not merely argued. Probing the A100-80 directly (rather than the
smaller A100-40 `a2-highgpu-1g`) is the right call: the ladder's flex rung is
A100-80, so the A100-80 probe answers the actual question. (If the implementer
prefers a more conservative cost probe and `a2-highgpu-1g` flex-start succeeds
while `a2-ultragpu-1g` is merely capacity-constrained, that is INCONCLUSIVE for
the A100-80 rung, not PASS — so probe the A100-80.) A minimal Debian image is
used deliberately: no GPU driver / DLVM boot needed — we are testing whether
the API ACCEPTS the flex-start request on the A2 machine type, not whether a
workload runs. `--request-valid-for-duration=10m` + `--max-run-duration=20m` +
`--instance-termination-action=DELETE` bound the probe's lifetime and cost.

**Expected runtime cost:** ~1-2 minutes of A100-80 idle (≪ ¢) if it
provisions; $0 if it 400-rejects before any VM is created.

**PASS criterion:** gcloud returns success and the instance reaches
`PROVISIONING`, `RUNNING`, **or** `PENDING` / a flex-queue capacity-wait
state (the flex queue legitimately waits for capacity — a PENDING/queued
state is the flex-start feature working as designed, NOT a failure). A clean
create with no `provisioning-model`/`FLEX_START` rejection = PASS. Then delete:

```bash
gcloud --configuration=eps-gcp compute instances delete eps-680-flexprobe \
  --zone=us-central1-a --quiet
```

(Run the delete unconditionally as cleanup even on a PENDING/queued create —
the `--instance-termination-action=DELETE` + `--max-run-duration=20m` is the
backstop, but delete explicitly to avoid a 20-min idle bill.)

**FAIL criterion:** gcloud surfaces a 400-class error that mentions
`provisioning-model` / `FLEX_START` / "not supported on machine-type" (i.e.
the API rejects flex-start ON THIS MACHINE TYPE). This is the only outcome
that proves A2 rejects flex-start.

**INCONCLUSIVE (treat as the API ACCEPTS flex-start):** anything OTHER than a
clean 400-rejection-of-flex-start — e.g. `ZONE_RESOURCE_POOL_EXHAUSTED` /
"zone resource pool exhausted", `QUOTA_EXCEEDED` / "quota exceeded", "request
expired", or any transient capacity miss. None of these prove A2 rejects
flex-start; a transient capacity miss is EXACTLY the condition flex-start is

## 11. Decision Rationale

N/A — no model training (no lr / epochs / LoRA / batch / optimizer /
precision). The load-bearing NON-hyperparameter choices:

- **`MAX_GCP_ATTEMPTS_PER_DAY`: 5 → 8 (FULL variant).**
  - *What:* raise the per-day GCP create-attempt cap from 5 to 8.
  - *Why:* the short-job ladder now has up to 5–6 GCP rungs (spot-80,
    spot-40, flex-80, ondemand-80, ondemand-40 = 5 for a short `lora-7b`;
    add a re-attempt margin → 6). At the old cap of 5, a fully-exhausted
    short-job ladder would hit `attempt_cap_exceeded` on the last rung and
    fall through to RunPod BEFORE exhausting on-demand — defeating the
    "try every GCP rung before paying for RunPod" intent. 8 covers the
    worst-case 5-rung short ladder plus 3 headroom for a same-day retry,
    without becoming a runaway (it counts ACTUAL creates, not headroom-
    skips, and stops issuing creates the moment it's hit — never a dollar
    cap, `tests/test_no_dollar_budget_caps.py` unaffected).
  - *Source:* `#680` body §"Implementation" (explicitly invites a bump);
    arithmetic grounded in the new §4.1 rung count. The alternative
    (keep 5) is rejected because the new short ladder's rung count exceeds
    it. `router.py:179`.
  - *Test pin (MF1, v3):* the shipped cap value is pinned by a NEW
    deterministic test — `test_max_gcp_attempts_per_day_is_eight` (FULL) /
    `test_max_gcp_attempts_per_day_is_six` (§13) — because the EXISTING
    `test_max_gcp_attempts_per_day_is_count_not_dollar_cap` (L1460) only checks
    `isinstance(int)` + `> 0`, so leaving the cap at 5 (silently omitting this
    headline change) would still pass the whole suite. The pin makes any future
    change to the cap an EXPLICIT two-file edit (code + test), surfacing it to
    the reviewer rather than letting a silent revert slip through green.
  - *Alternatives:* keep 5 (rejected — too small for the 5-rung short
    ladder); bump to 6 (rejected — no same-day-retry margin in the FULL
    variant; but it IS the right value for the §13 contingency's 4-rung
    short ladder); bump to 10 (rejected — more than needed; 8 is the tight
    cover + small margin).
  - *§13 contingency note:* if the probe FAILs, the short ladder is only 4
    rungs (spot-80, spot-40, ondemand-80, ondemand-40) → cap 5 → **6**, not
    8 (4-rung cover + 2 same-day-retry margin). See §13.
- **Flex rung placement — short: spot < flex < ondemand; long: flex <
  ondemand (FULL variant).**
  - *Why:* spot is the cheapest live pool and a short job absorbs
    preemption cheaply, so spot leads on short jobs; flex (queue-for-
    capacity, non-preemptible-once-running) is the middle rung; on-demand
    (guaranteed, exhausted-pool) is demoted to last GCP. Long jobs bar
    spot, so flex leads.
  - *Source:* `#680` body §"Change" (the length-aware order is the body's
    explicit spec); deep-research report (spot = separate live pool,
    flex = canonical capacity answer, on-demand-first wrong). **CONDITIONAL
    on the Implementation-step-0 probe — the flex rung exists in this design
    only if A2 accepts FLEX_START (§12 #1).**
- **`request_valid_for_duration` = default "2h", `max_run_duration` ≤ 7d
  cap.**
  - *Why:* the router does NOT set these — they resolve downstream in
    `gcp.py` (`DEFAULT_REQUEST_VALID_FOR_DURATION = "2h"`,
    `_assert_max_run_within_flex_cap` at 7 days). 2h is the doc-max DWS
    queue window (longest capacity-wait tolerance); the 7-day cap is the

  - *Source:* `gcp.py:496` (`DEFAULT_REQUEST_VALID_FOR_DURATION`),
    `gcp.py:501` (`_FLEX_START_MAX_RUN_SECONDS`); Google "Introducing
    Flex-start VMs" blog (90s–2h window) + Create-a-Flex-start-VM docs.
