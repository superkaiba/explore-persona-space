## 2. Prior work

**What #854 built** (`gcp.py` `_eps_persist_diagnostics`, L1491–1736; trap invocation L2148): on rc≠0 the EXIT trap runs `_eps_phase failed` (or `finalize_failed_artifacts_ok`, #1055) → reaps the watchdog → tails the log to serial fd-3 → calls `_eps_persist_diagnostics "$rc"` → `shutdown -h now`. The persist early-returns LOUDLY (fd-3 only) without `EPS_HF_DATA_REPO`/`HF_TOKEN` (L1497–1501), then runs `( cd "$WORKLOAD_ROOT" && timeout 300 uv run python - … )` piped through the eager fd-3 streamer (L1732–1735). The python uploads small-first: `crash_report.json` (`upload_file`), `workload.log` (`upload_file`), worker_logs (one `upload_folder`, #885), 3 partial dirs (`upload_folder` each), `workload_<ts>.log` (`upload_file`), and the transcript LAST (`upload_file`, L1712–1713) — "its presence proves the persist ran to completion; its ABSENCE proves a killed persist."

**What #935 built** (`_eps_persist_done_sentinels`, L1906–2045): the clean-exit sibling — ONE staged `upload_folder` commit + one retry with `EPS_DONE_PERSIST_RETRY_BACKOFF_S` backoff, a `/tmp/eps-done-persist.status` file the bash reads back, and a **guest-attribute breadcrumb `eps/done_persist=ok|failed`** PUT on a SEPARATE key from `eps/phase` (L2036–2043). This is the exact naming + wiring precedent the fix extends to the crash path.

**The design gap this task closes:** #854's skip-vs-kill discriminator (transcript-uploaded-LAST) rides the SAME HF channel as everything else. When the HF channel itself is down — or the persist dies before its first upload — the discriminator is indistinguishable from "persist never ran." The fd-3 serial lines and the local transcript both die with the DELETEd boot disk (#640). The crash path has NO guest-attribute breadcrumb, unlike #935's done path.

**Web findings on GCP termination semantics (verified sources):**
- Guest-OS-initiated `shutdown` and GCP-initiated terminations provide a bounded shutdown window whose length GCP does NOT guarantee; Compute Engine forcefully stops shutdown scripts even if they are still running ([Run shutdown scripts](https://cloud.google.com/compute/docs/shutdownscript), [Limit the run time of a VM](https://cloud.google.com/compute/docs/instances/limit-vm-runtime)). (Fact-check note: an earlier "usually at least 90 seconds" phrasing is not on the current docs pages and was dropped; the design relies only on the not-guaranteed / force-stop direction, which is confirmed.) Relevant to hypothesis H-D (§3): an EXTERNAL termination racing the trap can kill the persist mid-flight with no HF evidence — exactly what a standing `attempted` breadcrumb makes observable.
- Guest attributes: writable from any in-VM process while the metadata server is reachable; queries limited to 10/min + burst 3/s per VM ([Setting and querying guest attributes](https://docs.cloud.google.com/compute/docs/metadata/manage-guest-attributes)). Our breadcrumb adds ≤3 writes per crash and ≤1 poll-side read per terminal tick — far under both caps (the done-grace loop already budgets against this same limit, gcp.py L2050–2053).
- Persistence on TERMINATED instances is proven **in-project**: the 01:24Z #811 diagnosis read `eps/phase=failed` off the already-TERMINATED instance, and the #908 zombie predicates depend on exactly this read. Guest attributes are lost only at instance DELETE (accepted for `eps/done_persist` at #935; same acceptance here — the poller reads them BEFORE the delete, which is when the terminal diagnosis happens).

### 3.2 The disciplined shortlist (direct evidence destroyed — boot disk DELETEd 2026-07-05T12:10Z)

The 01:24Z diagnosis deliberately kept the TERMINATED instance ("workload.log on the TERMINATED instance boot disk — kept for now"), but the fits never surfaced a shortfall, nobody pulled the log, and the 07-05 L4 dispatch's #908 pre-launch stale reclaim deleted it (`epm:cluster-launched` 12:10:39Z, `"pre_launch_deleted_stale_instance": true`). The fd-3 serial stream is unreadable post-DELETE (#640). So the discrimination below is ranked, not proven:

**H-A (leading, ~likely): the persist RAN but zero HF uploads landed inside/despite the 300s budget — HF-channel failure at exactly trap time.** Two mutually-compounding mechanisms, both documented on this exact repo:
- *Org-quota exhaustion:* the crash came at the TAIL of the instance stage, immediately after the workload finished uploading **10.86 GB / ~10k files** (`issue811_pre_user_boundary/` — 10,129 files verified later). The org's ~2500-req/5-min HF quota was demonstrably storming in that exact window: **8 minutes after the diagnosis** (01:32:19Z) the fits stage's first store DOWNLOAD from the same repo failed on 429s and needed a 6-attempt/330s-backoff supervisor; the same repo had a "HF 429 retry storm" earlier that day (08:54Z marker).
- *Per-file `upload_file` pre-check stalls:* on this ~1M-file repo, per-file `HfApi.upload_file` triggers a server-side recursive tree-listing pre-check that 504s ~half the time at ~160 s/file measured (#664, `.claude/rules/gotchas.md`). The #854 persist opens with TWO per-file `upload_file` calls (crash_report.json, workload.log) — one or two stalled pre-checks consume the entire 300s and `timeout` kills the python before the first commit completes.
Under either mechanism every `[crash-persist] FAILED …` line went only to fd-3 + the local transcript; the transcript's own upload rides the same dead channel. Net observable: zero-file prefix — exactly what we saw.

**H-B (possible): `uv run python` bootstrap failure at trap time** (uv lock-check/re-sync attempting network mid-429-storm, or boot-disk pressure after the ~11 GB store materialized locally). The `cd … 2>/dev/null && timeout 300 uv run python …` chain short-circuits with NO fd-3 line on a cd failure and only serial-visible stderr on a uv failure. Same observable.

**H-D (low): external termination racing the persist** (host event/forced stop): the workload dies on the shutdown SIGTERM (rc≠0 → shell exits normally → trap runs → `failed` lands in ms), then the force-kill sweeps the persist before its first upload completes. No fence evidence and FLEX_START is non-preemptible once running, but a host-side event cannot be excluded post-DELETE.

**Shared structural property → the fix:** all three hypotheses differ only in WHERE the persist died, and all are invisible because (i) the persist's first off-VM write is itself a heavy HF operation, and (ii) the only no-fire evidence channels (fd-3, local transcript) die with the boot disk. A guest-attribute breadcrumb (link-local metadata server; zero HF dependency; zero org-quota dependency; readable by the poller on the TERMINATED instance exactly when the terminal diagnosis runs) discriminates all of them on the NEXT crash: H-A reads `ok`+empty-prefix or `timeout`; H-B reads `failed_rc<N>`; H-D reads standing `attempted`. Evidentially, the 429-storm mechanism for H-A is CORRELATIONAL (the 01:32Z 429s hit a download path by a different client; the 10k-file upload completing pre-crash shows the write channel alive minutes earlier while also supplying the exhaustion mechanism) — H-A stays "leading, unproven" in any write-up; never narrate the storm as the established cause.

### 4.1 `_eps_persist_status` helper (new, preamble, next to `_eps_phase` ~L1438)

```bash
_eps_persist_status() { curl -fsS -m 5 -X PUT -H "Metadata-Flavor: Google" --data "$1" \
  "http://metadata.google.internal/computeMetadata/v1/instance/guest-attributes/eps/persist" \
  >/dev/null 2>&1 || true; }
```
Mirrors `_eps_phase` (L1435–1437) + the `eps/done_persist` PUT (L2039–2041), with `-m 5` so a wedged metadata server can never eat the persist budget (the done-grace READ already uses `-m 5`, L2082). SEPARATE key from `eps/phase` — the #908 zombie predicates and poll classification key on `eps/phase` and must not see new values (the #935 discipline, L1900–1902).

**Boot-time clear (staleness guard, critic-surfaced):** guest attributes survive reboots of the same instance and `eps/persist` would otherwise carry a PRIOR crash's final value into a salvage-relaunch second boot. Next to the existing `_eps_phase startup` boot write, clear the key: `curl -fsS -m 5 -X DELETE -H "Metadata-Flavor: Google" ".../guest-attributes/eps/persist" >/dev/null 2>&1 || true` (fail-soft; if the metadata API rejects DELETE for guest attrs, write the literal `cleared` instead and add `cleared` to the decision table as boot-reset).

### 4.2 Breadcrumb wiring inside `_eps_persist_diagnostics`

- **Entry** (immediately after `_rc="${1:-1}";`, L1492): `_eps_persist_status "attempted";` — unconditional proof the function was entered.
- **Skip branch** (inside the token guard, before `return 0`, L1500): `_eps_persist_status "skipped_no_token";`
- **rc capture:** before the subshell: `rm -f /tmp/eps-crash-persist.rc 2>/dev/null || true;`. Inside the subshell, after the heredoc terminator `EPS_PERSIST_PY` (between current L1714 and L1732):
  ```bash
  _uprc=$?; { echo "$_uprc" >/tmp/eps-crash-persist.rc; } 2>/dev/null || true;
  ```
  (`set +e` is global from the trap's first action, so the `cd && timeout` compound's failure rc is capturable — same property today's code relies on.)
- **Final status** (after the streamer pipeline, before the function's closing `}` at L1736):
  ```bash
  _prc="$(cat /tmp/eps-crash-persist.rc 2>/dev/null || true)";
  if [ -n "$_prc" ]; then case "$_prc" in
    (0)   _eps_persist_status "ok" ;;
    (124) _eps_persist_status "timeout" ;;
    (*)   _eps_persist_status "failed_rc${_prc}" ;;
  esac; fi;
  ```
  A MISSING rc file deliberately writes nothing — the standing `attempted` IS the killed-mid-persist signal (H-D). ≤3 writes per crash, inside the 3/s burst + 10/min caps.

**Decision table** (goes verbatim into the rule doc + a code comment):

| `eps/persist` | HF prefix | Reading |
|---|---|---|
| ABSENT | absent | pre-fix render, trap never entered the persist, entry-curl failure (`-m 5` expiry), OR total metadata-channel death (the #667 class — co-signal: a WRITTEN `eps/phase=failed` + ABSENT breadcrumb genuinely isolates the pre-persist window; phase ALSO absent ⇒ dead metadata channel, route to the #667 wedge lane) |
| `attempted` (standing) | absent | persist KILLED mid-flight (external termination / hard kill). **TERMINATED-only reading** — a RUNNING-window read may catch a healthy persist in flight (the poll excerpt self-discloses instance status, §4.5) |
| `attempted` (standing) | present | kill landed in the window after uploads completed but before the final-status write (rare; transcript disambiguates) |
| `skipped_no_token` | absent | early-boot crash before secrets fetch |
| `ok` | present | normal crash persist. `ok` = the persist python EXITED 0, not "all artifacts landed" — per-upload failures are logged, never raised; the transcript is the per-upload audit |
| `ok` | absent/partial | persist completed but HF channel down (H-A's 429 shape) — or a repo/prefix misroute; separable post-hoc by the §3.1.2 listing procedure |
| `timeout` | absent/partial | 300s budget exhausted (stalled uploads — H-A's 504 shape) |
| `failed_rc<N>` | absent | bootstrap/compound failure (127 = uv missing; 1 = cd short-circuit OR python top-level failure; else python rc) (H-B) |

### 4.5 Poll-side surfacing (`GcpBackend`)

New method next to `_workload_started` (~L5121), following its second-scoped-read pattern but **best-effort** (diagnostic channel — MUST NOT raise, unlike `_guest_phase`'s typed `GcpProbeError` contract):

```python
def _guest_persist_breadcrumb(self, handle: RunHandle, zone: str) -> str:
    """Best-effort read of the eps/persist crash-persist breadcrumb (#1151).

    Diagnostic-only: ANY failure (nonzero rc, bad JSON, transport) returns ""
    — it never raises and never gates classification.
    """
    try:
        argv = render_guest_attributes_argv(
            config=self._config, name=handle.pod_name, zone=zone, query_path="eps/persist"
        )
        result = self._run(argv)
        if result.returncode != 0 or not result.stdout.strip():
            return ""
        payload = json.loads(result.stdout)
        for item in payload if isinstance(payload, list) else []:
            if item.get("key") == "persist":
                return str(item.get("value") or "").strip()
    except Exception:
        return ""
    return ""
```

Wire it at the two poll classification windows where `phase in ("failed", "finalize_failed_artifacts_ok")` resolves — the RUNNING window (~L4862–4930) and the TERMINATED window (~L5021–5060) — appending one line to the result's `log_tail_excerpt` that INCLUDES the instance status (Must-Fix, statistics lens: a RUNNING-window read can catch the persist healthily in flight, and a verbatim table read would misdiagnose H-D):
`f"\n[crash-persist-breadcrumb] eps/persist={bc or 'ABSENT'} (instance {status})"` — with the RUNNING variant additionally carrying `— persist may be in flight; standing-attempted reading valid once TERMINATED`.
No `PollResult` schema change (the excerpt already rides every terminal marker the orchestrator reads — the 01:24Z-style diagnosis will carry it verbatim). One extra guest-attr query per terminal-classifying tick, well under the 10/min cap.

## 11. Decision Rationale

`N/A — no training hyperparameters` (kind: infra). Load-bearing engineering choices:

- **Breadcrumb transport: guest attribute (primary), NOT an extra HF tiny-upload.** *Why:* the diagnosed failure class is HF-channel death; a breadcrumb must ride an independent channel. Guest attrs are link-local (no org quota), readable on TERMINATED instances at exactly the moment the terminal diagnosis runs. *Source:* `eps/done_persist` precedent (gcp.py L2032–2043, #935); the #811 record itself (phase read off a TERMINATED instance); [manage-guest-attributes](https://docs.cloud.google.com/compute/docs/metadata/manage-guest-attributes). *Alternative rejected:* an early tiny HF upload — already effectively exists (139 B crash_report.json first) and provably failed on #811.
- **Placement: `attempted` at function entry; final status from an rc file after the pipeline.** *Why:* entry-write proves invocation under every hypothesis; rc-file readback is the only way to see through the streamer pipeline (pipeline rc = streamer's). *Source:* #935's `EPS_DONE_PERSIST_STATUS` readback (L2016–2038). *Alternative rejected:* `PIPESTATUS` — bash-specific inside a `trap` string, harder to pin in tests.
- **No-write-on-missing-rc-file (standing `attempted`).** *Why:* a killed persist cannot report; absence of a final value IS the kill signal — writing a guessed value would destroy the discriminator. *Source:* #854's own skip-vs-kill design intent (L1709–1711), extended off-HF.
- **Timeout budget: keep 300 s authoritative; ONE retry on the first bundle only.** *Why:* the poweroff bound is the #854 invariant this task must not weaken; a single fail-fast retry is the #935-validated shape. *Source:* task brief constraint; gcp.py L1998–2015.
- **Bundled `upload_folder` commits over per-file `upload_file`.** *Why:* eliminates the measured ~160 s/file pre-check stall class on this repo. *Source:* #664 incident + `#935`'s "never a per-file loop" comment (L1894–1899, gotchas.md).
- **Poll surfacing via `log_tail_excerpt`, not a new `PollResult` field.** *Why:* zero contract change; the excerpt already reaches every terminal marker the diagnosis reads. *Source:* `crash_signature` threading precedent (Part D) chose a field — but that one GATES failover; ours is diagnostic-only, so the cheapest surface wins.
