## §0 TL;DR

Two negative status claims about pod-side work are currently ungoverned by any
rule: (a) a launch wrapper writing `<pod> LAUNCH FAILED` because its **local
ssh call** returned non-zero, and (b) a heartbeat writing `UNREACHABLE (ssh
rc=255)` because ssh failed. In both cases the *transport* outcome was
substituted for the *leg* outcome, and in both cases #1739 produced a
documented false alarm against healthy / already-finished work.

The fix adds ONE new H3 contract to `.claude/rules/pod-side-reporting.md`,
placed immediately after the § Pid-file launch contract it twins:
**a negative status verdict about pod-side state requires a pod-side probe,
and an inconclusive probe yields an inconclusive verdict — never a fault.**
It carries the 60 s launch-watchdog recipe inline (the #1739 v2-driver
implementation was session-local and does **not** exist in the repo — verified,
§2), plus the rc=255 classification recipe grounded in two live in-repo
precedents. One cross-reference line is appended to item 1f, and the
`LESSONS.md` trigger row is extended so the rule actually loads when an agent
is about to write a status line (today's trigger names only launching / pushing
/ runbook-posting — a heartbeat matches none of them).

## §1 Motivation (verified from the task body's cited readbacks, not inherited)

Both incidents are #1739, 2026-08-05, and are recorded in the task body with
session + row citations. They fail in **opposite directions**, which is why the
probe — not a phrasing change — is the fix:

1. **False negative (launch).** The jobd/r2aug 6-pod fan-out's launch ssh hung
   ~35 min, was killed, and returned non-zero. The wrapper wrote
   `pod-1739-jobd-evil LAUNCH FAILED` **while the detached pod-side run was
   alive** (pid 1885 verified by later readback). It recurred for
   jobd-sycophancy at 07:48Z. Root cause is exactly the ssh-fd semantics item
   1f already documents: a detached child holding stdout/stderr keeps the
   channel open, so the local client hangs and its rc describes the *channel*,
   not the *leg*.
2. **True positive (launch).** In the same fan-out,
   `pod-1739-a1apilot LAUNCH FAILED (ssh_rc=124, no live pod-side proc)` was a
   **real** failure. The probe is precisely what distinguishes (2) from (1) —
   so the remedy cannot be "stop writing LAUNCH FAILED"; it must be "write it
   only with a probe result attached".
3. **False negative (heartbeat).** The R5 wall-clock heartbeat wrote
   `UNREACHABLE (ssh rc=255) — investigate before assuming healthy` twice
   (07:45Z, 10:01Z) for pods **terminated after verified upload**. The 10:02Z
   heartbeat self-corrected to `TERMINATED (verified upload) … NOT a fault`
   after checking the termination sentinel first — i.e. the correct algorithm
   was discovered *in-session and then lost*.

Cost of the gap: false FAILED verdicts invite the exact duplicate-relaunch
race the ownership-check rules exist to prevent, and false UNREACHABLE lines
train the reader to discount heartbeats — the channel CLAUDE.md's long-phase
heartbeat duty depends on.

## §3 Design

### 3.1 One contract, two items, one shared principle

The unifying principle — stated once at the top of the new section — is:

> An ssh/transport outcome is evidence about the CHANNEL, never about the
> pod-side LEG. Any status line asserting a pod-side FAULT (`LAUNCH FAILED`,
> `UNREACHABLE`, `DEAD`, `CRASHED`) requires a pod-side probe result quoted
> alongside it; when the probe cannot run, the verdict is INCONCLUSIVE, never
> a fault.

Item 1 = the launch-declaration duty. Item 2 = the heartbeat-classification
duty. They share the principle and the fail-open posture, so they belong in
one section rather than scattered.

### 3.2 Placement — a sibling H3, not an item inside the launch contract

**Deviation from the task body's literal wording, stated with its reason:**
the body says "add to that rule's (re)launch contract section". I place the
clause as a **new H3 immediately after** that section (between L450 and the
`### Continuation-runbook verification provenance` H3 at L452), because half
the content — the heartbeat duty — is not a launch duty, and the launch
contract's own preamble scopes it to "EVERY agent that launches OR relaunches
a detached workload" (L208-210). Filing heartbeat rules under a launch
contract would mis-scope them and make them unfindable for the agent that
needs them. Adjacency + an explicit cross-reference from 1f preserves the
body's intent (the reader of the launch contract is handed the clause) without
the scope error.

### 3.3 Item 1 — launch-failure declaration (the recipe, written inline)

Content, in the rule's existing register:

- A launch wrapper MUST NOT write `LAUNCH FAILED` (or any launch-fault
  wording) on the strength of its local ssh rc alone. rc ∈ {124 (timeout-killed
  backstop), 255 (transport), any non-zero} is a statement about the channel.
- Before declaring, run the pod-side probe in a **fresh ssh call**, in this
  order: (i) read the pid file (item 1's path) and test the pid with
  `ps -p "$PID" -o args=` — identity-verified per 1h, so a wrapper pid cannot
  pass; (ii) if the pid file is absent/stale, fall back to the bracketed
  pattern probe of 1d(a) (`pgrep -f 'issue<N>_dispatc[h]'`) — **detection
  only**, it never writes the pid file; (iii) check log mtime advancing.
- The declaration then carries the probe result verbatim, in one of exactly
  three shapes:
  - `LAUNCH OK (ssh_rc=<rc>, live pod-side pid=<pid> verified)` — the #1739
    jobd case; the non-zero rc is recorded and explicitly not a fault.
  - `LAUNCH FAILED (ssh_rc=<rc>, no live pod-side proc)` — the #1739
    a1apilot case; a fault, now evidenced.
  - `LAUNCH INCONCLUSIVE (ssh_rc=<rc>, probe unreachable)` — the probe itself
    could not run. **First rung is retrying the PROBE** (a short, cheap ssh
    call — not the launch), so a genuinely-failed launch converges quickly to
    an evidenced `LAUNCH FAILED` rather than parking at INCONCLUSIVE; only a
    probe that stays unreachable escalates. **Never** resolves to a FAILED
    verdict on transport evidence alone, and never to a relaunch (a relaunch
    against a possibly-live run is the duplicate-launch race of CLAUDE.md
    § Ownership check).
- The 60 s watchdog shape that makes this cheap, written out: bound the launch
  with `timeout --kill-after=10s 60s ssh ...` (1f's backstop), treat its exit
  as *launch dispatched, outcome unknown*, then run the probe as a separate
  short ssh call. A fan-out runs the probe per pod.
- Applies to EVERY writer of a launch verdict: the experimenter agent, an
  orchestrator-composed fan-out driver, a hand-rolled bash wrapper, a
  watch-session correction.

### 3.4 Item 2 — heartbeat rc=255 classification

- A heartbeat/monitor MUST classify an ssh failure against the pod's KNOWN
  lifecycle state before writing `UNREACHABLE`. Classification order, which
  **must cover the roster-ABSENT branch explicitly**: (i) query the live pod
  roster (`pod.py list-ephemeral`), authoritative for pod existence/status per
  CLAUDE.md § authority split; (ii) if the pod is ABSENT from a roster query
  that SUCCEEDED, decide on the durability record — a termination/completion
  sentinel plus `epm:upload-verification` / `epm:pod-terminated` means
  **expected absence, not a fault**; NO such record means the artifacts' fate
  is unknown and the pod's volume is gone, which is a **FAULT**; (iii) if the
  pod is present and RUNNING, ssh rc=255 warrants `UNREACHABLE`; (iv) if the
  roster query itself failed, nothing is known — INCONCLUSIVE.
- Verdict vocabulary, and every branch of (i)-(iv) resolves to exactly one of
  them:
  - `TERMINATED (verified upload) — NOT a fault` — absent + durability record
    present. The #1739 R5 case.
  - `GONE (absent from roster, NO verified-upload record) — FAULT: possible
    data loss, surface for investigation` — absent + NO durability record.
    Host failure, a third-party terminate on the shared org, or a
    terminate-before-verify. This is the #1112 durability class: uploads
    unverified and the volume gone. It is the MOST severe verdict in the set
    and must never be softened into `TERMINATED` or `INCONCLUSIVE`.
  - `STOPPED — workload is dead; a STOPPED volume is NOT durable (#1112)` —
    present but STOPPED. Under an active leg this is a fault, not a pause:
    persist/verify before any resume decision.
  - `UNREACHABLE (present+RUNNING, ssh rc=255)` — the genuine transport
    fault, and the only state the old copy's "investigate before assuming
    healthy" wording was ever right about.
  - `INCONCLUSIVE (roster query failed)` — the probe could not run.
- **The vocabulary is CLOSED and EXHAUSTIVE over the state space** — the rule
  says so explicitly, because a closed set that silently omits a state invites
  an agent to shoehorn the worst state into the nearest benign label or write
  nothing at all. Any future state that does not map gets a new named verdict,
  never a reused one.
- **Fail-open on the PROBE, never on the DURABILITY question.** Mirroring
  `classify_fetch_transport`: when the roster query itself fails the verdict is
  INCONCLUSIVE — a failed roster read is never evidence the pod is gone (the
  CLAUDE.md gotchas rule that a non-zero `gcloud` rc is UNKNOWN, never empty,
  is the same discipline). But the reverse asymmetry is deliberate: once
  absence is ESTABLISHED by a successful query, a missing durability record
  resolves toward FAULT (`GONE`), not toward silence. Fail-open about
  reachability; fail-LOUD about unverified artifacts.
- The two precedents are cited by file + symbol so the next implementer reuses
  them instead of re-deriving.

Both directions recorded compactly (the false-negative jobd/r2aug pair, the
true-positive a1apilot, the twice-written R5 UNREACHABLE and its 10:02Z
