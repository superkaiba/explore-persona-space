**Correction to the filing's proposed clause (c) — the filing's one flagged

which makes #1739 a wrong-primitive choice upstream of any cap question. That
becomes new clause (0), which the filing did not anticipate.

## 3. File paths + concrete diffs

### 3.1 `.claude/skills/issue/SKILL.md` — insert after `…and is untouched.` (end of the #1850 heartbeat-emission block), before `Revival trigger for the deferred watcher-side option`

```markdown
**Monitor until-condition composition (#1739 baseline churn, #1947
double-print wedge).** Item 1 above segments the WAIT; these rules compose
the CONDITION and pick the primitive. They bind every IMPROVISED Monitor in
this skill; the prescribed loops (Step 9c 1b, the gate-fleet arbitration,
Step 10d Guard 5) already conform and are the exemplars.

(0) **Pick the primitive by notification COUNT, not by duration.** A wait
needing ONE notification ("the box set finished", "the gate is clear") is a
bg-Bash `run_in_background` until-loop that EXITS on the condition — not a
Monitor. Monitor is for one-event-PER-OCCURRENCE streams (a log tail, a
per-shard progress line). #1739's box-completion watch was
single-notification, so it reached for the wrong primitive before any
condition question arose.

(a) **Key a completion condition on a count DECREASE from the count
captured AT ARM TIME — never an absolute `live=N`.** An absolute condition
is already TRUE at arm time, so every (re-)arm fires an immediate no-op
event (#1739: 9 overnight re-arms, ≥6 turns spent classifying a "baseline
tick — not a real completion"). Capture the baseline INSIDE the command
(`base=$(<probe>); until [ "$(<probe>)" -lt "$base" ] || …`), or otherwise
suppress the first event.

(b) **NEVER `<count-cmd> || echo 0` — or any `X || echo` count — inside a
Monitor condition.** `pgrep -c` / `grep -c` PRINT `0` AND exit non-zero on
no match, so the fallback fires too and the captured value is the two-line
string `"0\n0"`; the equality gate then never matches and the watch wedges,
failing OPEN (#1947's judge fan-out monitor wedged on exactly this shape and
was `TaskStop`'d by hand). The `.claude/rules/gotchas.md` count-keyed
liveness entry owns the full diagnosis + the
`X=$(CMD -c … 2>/dev/null || true); X=${X:-0}` fix — cross-link, do not
restate it; its trigger is write-time, which is why it does not reach a
condition composed here. In a condition prefer `pgrep -f 'patter[n]' |
wc -l` or an rc-keyed probe whose exit code IS the verdict —
`step9c_baseline.py probe` is the in-repo exemplar (exit semantics
deliberately inverted, fixed regex, so the loop can never spin on a usage
error).

(c) **A session-length watch is `persistent: true`, not a re-arming bounded
Monitor.** `timeout_ms` caps at 3600000 ms (1 h) and is IGNORED when
`persistent: true`; `persistent: true` runs for the session lifetime and is
stopped with `TaskStop`. A bounded arm re-armed across a multi-hour wait
costs a triage turn per expiry (#1739). This does NOT relax item 1: a
`persistent` Monitor does not block a turn, and the #1850
`[watch-heartbeat]` emission supplies the resume opportunities item 1
requires. For a run the pipeline already polls, first preference stays the
sanctioned `poll_pipeline.py` bg-Bash chain. Carve-out: the Step 6d.2
QUIET-WAIT Monitor is deliberately bounded + single-shot
(`timeout_ms=2400000`, `persistent=False`) and is not a re-arming watch —
unchanged.
```

Placement is verified safe against both adjacent pin tests: each slices the duty
block (`**Long-phase heartbeat duty` → `Revival trigger …` / next `#####`) and
asserts only PRESENCE, so extra content inside the slice cannot fail them.
