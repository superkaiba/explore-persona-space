<h1>Issue #669 — Detect hung-but-RUNNING GCP VM (frozen non-terminal <code>eps/phase</code> + drain-timeout) and recover it automatically</h1>
<p><em>kind: infra — code change only, zero GPU-hours. Acceptance criterion is the test-verdict gate.</em></p>

<section class="plan-summary">
<p><span class="label">What this fixes:</span> a 3rd GCP "RUNNING-zombie" mode (#667) where a VM's guest networking dies (systemd-networkd DHCPv4 lease loss) but the VM stays <code>RUNNING</code>. The poller reads <code>eps/phase=workload</code> frozen forever, so neither #658's synchronous nor #659's async GCP→RunPod failover ever fires — only a manual <code>--backend runpod</code> pivot recovered it.</p>
<p><span class="label">Four code changes (all in workflow surface <code>backends/gcp.py</code> + <code>scripts/backend_poll.py</code>):</span></p>
<ul>
<li><span class="label">Fix 2 (PRIMARY recovery):</span> an in-VM <em>reachability</em> watchdog embedded in <code>render_startup_script</code> — probes metadata server <code>169.254.169.254</code> + an external endpoint; on sustained loss (~5&nbsp;min) forces a clean <code>TERMINATED</code> via <code>shutdown -h now</code>. Reachability not liveness: a systemd <code>/dev/watchdog</code> keeps getting fed on a wedged VM (systemd&nbsp;#21083).</li>
<li><span class="label">Fix 1 (defense-in-depth):</span> in <code>gcp.py::poll</code>'s <code>if phase:</code> running branch, escalate to a new terminal phase <code>terminal_workload_wedged</code> when a non-terminal <code>eps/phase</code> has been stuck past a <strong>15-min staleness floor</strong> AND the drain SSH is timing out (<code>drain_alarm</code> set). Staleness clock = a <code>last_phase_change</code> field added to the handle sidecar.</li>
<li><span class="label">Fix 4 (routing):</span> add <code>terminal_workload_wedged</code> AND <code>terminal_terminated</code> to <code>_is_gcp_async_workload_failure</code>'s accept-set so #659's <code>_failover_dead_gcp_to_runpod</code> (exactly-once lease-backed) fires on both the poller-detected wedge and the watchdog's self-terminate.</li>
<li><span class="label">Fix 3 (composition):</span> add <code>--no-restart-on-failure</code> (<code>automaticRestart=false</code>) to the launch argv. <code>--maintenance-policy=TERMINATE</code> is already present (gcp.py:1397). Confirmed to compose with <code>--instance-termination-action=DELETE</code> (different lifecycle boundaries).</li>
</ul>
<p><span class="label">Baselines / controls:</span> the anti-false-positive test (recent phase change → still <code>running</code>) is the load-bearing control — it rules out killing a legitimately-long-running phase. No-regression to the existing crashed-workload (#659) and healthy-running poll paths is asserted by the pre-existing test suite staying green.</p>
<p><span class="label">Compute:</span> <strong>Estimated GPU-hours (total): 0</strong>. CPU-only code change + unit tests; no pod, no VM, no live launch in scope (a live GCP acceptance run is optional and explicitly out of scope for the test-verdict gate).</p>
<p><span class="label">Evaluation:</span> the 6 named tests pass; <code>uv run pytest tests/test_gcp_backend.py tests/test_backend_poll.py tests/test_router.py</code> stays green; <code>ruff check</code> clean on touched files; <code>bash -n</code> clean on both startup-script render branches.</p>
<p><span class="label">Risks (top 2):</span> (1) a false-positive wedge classification killing a healthy long-running phase — mitigated by the conjunction of frozen-phase + drain-alarm + a floor well above any normal phase duration; (2) the startup-script byte-identity snapshot test (<code>test_render_startup_script_hydra_only_byte_identical…</code>) will trip and must be deliberately regenerated.</p>
</section>

<h2>1. Goal &amp; acceptance criteria</h2>
<p>Close the remaining GCP-failover coverage gap so a hung-but-<code>RUNNING</code> GCE VM (frozen non-terminal <code>eps/phase</code> from dead guest networking) self-recovers to a RunPod re-dispatch with no human pivot. Two independent mechanisms: an in-VM reachability watchdog that flips the VM to a poller-dead <code>TERMINATED</code> state (primary, because it works even when the poller can't SSH in), and a poller-side frozen-phase+drain-timeout escalation (defense-in-depth, for the marginal case where the VM is too network-dead to self-terminate but the describe API still resolves).</p>
<p><strong>Acceptance (from the task body):</strong></p>
<ol>
<li>The six new tests pass.</li>
<li>A frozen-non-terminal-phase + drain-timeout GCP VM is classified dead and fails over to RunPod <strong>exactly once</strong>.</li>
<li>A watchdog self-<code>TERMINATE</code> also routes to the failover.</li>
<li>No regression to the crashed-workload (#659) path or the healthy-running poll path (the existing <code>test_gcp_backend.py</code> / <code>test_backend_poll.py</code> / <code>test_router.py</code> suites stay green).</li>
</ol>

<h3>2.1 Research findings (web) — used to ground the design</h3>
<ul>
<li><strong>systemd-networkd DHCP-renewal-timeout bug (root-cause trigger).</strong> systemd issues <a href="https://github.com/systemd/systemd/issues/32045">#32045</a> ("does not retry renewing an expiring DHCP lease"), <a href="https://github.com/systemd/systemd/issues/33934">#33934</a> ("lease getting expired without retrying at T2"), <a href="https://github.com/systemd/systemd/issues/33288">#33288</a> ("Could not set DHCPv4 address: Connection timed out"), and Ubuntu <a href="https://bugs.launchpad.net/bugs/2054977">LP&nbsp;#2054977</a>. The failure mode: under load (netlink-request timeout from high disk read + memory pressure) the renew at T2 times out, systemd does <em>not</em> retry, the lease expires, and the interface loses connectivity <em>permanently</em> — exactly the #667 serial tail. This trigger is fixed separately by the parallel extractor-memory task; #669 is the BACKSTOP. Affects multiple systemd versions (245/249/254/255) across cloud providers — i.e. it is an OS bug, not a GCP-specific flake, so it can recur on any Ubuntu DLVM image regardless of the extractor fix.</li>
<li><strong>Reachability vs liveness watchdog.</strong> systemd <a href="https://github.com/systemd/systemd/issues/21083">#21083</a> ("watchdog: Still fed when rootfs is non-responsive") confirms a liveness watchdog (the service sends <code>sd_notify</code> heartbeats / <code>/dev/watchdog</code> keeps ticking) does NOT catch a hung-but-running condition — the process is alive and keeps feeding the dog while the system is unusable. The watchdog MUST probe actual external reachability (can I reach the metadata server + an internet endpoint?), not "am I still ticking?".</li>
<li><strong>GCE scheduling-flag composition.</strong> Google's <a href="https://docs.cloud.google.com/compute/docs/instances/setting-vm-host-options">host-maintenance docs</a> + <a href="https://cloud.google.com/compute/docs/instances/limit-vm-runtime">max-run-duration docs</a> confirm <code>onHostMaintenance</code> (host-maintenance-event behavior), <code>automaticRestart</code> (crash/programmed-stop restart behavior), <code>maxRunDuration</code>, and <code>instanceTerminationAction</code> are independent fields of the same <code>scheduling</code> block and compose freely. <code>TERMINATE</code> is the only supported <code>onHostMaintenance</code> for GPU instances (already enforced — gcp.py:1341-1343). Setting <code>automaticRestart=false</code> (<code>--no-restart-on-failure</code>) ensures the watchdog's self-<code>shutdown</code> is final (the VM does NOT auto-restart back into the same wedged state) — and because <code>instanceTerminationAction=DELETE</code> governs only the <code>maxRunDuration</code>/spot-preemption boundary, the two do not conflict: a watchdog <code>shutdown -h now</code> reaches <code>TERMINATED</code>, which the poller already reads as dead (gcp.py:3907-3908).</li>
</ul>

</ul>

<h2>4. Design — file-by-file</h2>

<h3>4.1 Staleness-clock storage (the load-bearing architecture decision)</h3>
<p>The wedge clock needs persistent state across poll ticks. <code>GcpBackend.poll(handle)</code> is called from <code>backend_poll.py</code> (line 746), which already owns the sidecar path (<code>resolve_handle_sidecar_path</code>). The poller is process-local-stateless across ticks, so the only durable carrier is the <strong>handle sidecar JSON</strong> (<code>.claude/cache/issue-&lt;N&gt;-handle.json</code>, cwd-independent per <code>default_handle_sidecar_path</code>).</p>
<p><strong>Decision: track phase-change in <code>backend_poll.py</code>, not inside <code>poll()</code>.</strong> Keep <code>GcpBackend.poll(handle)</code> pure (it already reads only the describe + guest-attribute round-trips). The poller, which has BOTH the prior sidecar and the fresh <code>PollResult</code>, owns the staleness clock:</p>
<ol>
<li>The sidecar gains an optional <code>last_phase</code> + <code>last_phase_change_ts</code> (epoch seconds) pair, stored inside <code>RunHandle.extra</code> and persisted via the existing <code>write_handle_sidecar</code>. <strong>Verified:</strong> <code>serialize_handle</code> round-trips <code>extra</code> as a plain dict (<code>dict(handle.extra)</code>, issue_dispatch.py:340), so no schema migration is needed — extra keys survive the round-trip and a missing key reads as absent. Absent on a freshly-dispatched sidecar (pre-this-change handles read as "no clock yet" → fail toward <em>running</em>, never toward a false wedge).</li>
<li><code>poll()</code> emits, on the running branch, the <em>observed</em> phase in <code>current_phase</code> (unchanged) AND a new boolean signal that the drain alarm is set (already in <code>log_tail_excerpt</code> via <code>_overlay_drain</code>; we surface it explicitly — see 4.2). It does NOT itself classify the wedge.</li>
<li>The poller compares the observed running phase to the sidecar's <code>last_phase</code>:
  <ul>
  <li>phase changed → update <code>last_phase</code> + <code>last_phase_change_ts = now</code> in the sidecar, emit the running result unchanged;</li>
  <li>phase unchanged AND <code>now - last_phase_change_ts &gt; STALENESS_FLOOR_SEC</code> AND the result carries a drain alarm → rewrite the result to <code>status="dead", current_phase="terminal_workload_wedged"</code> (this is what the async predicate then matches);</li>
  <li>phase unchanged but within the floor, OR no drain alarm → emit running unchanged (the false-positive guard).</li>
  </ul>
</li>
</ol>
<p><strong>Why poller-side, not <code>poll()</code>-side?</strong> Keeping the clock in the poller means <code>poll()</code> stays a pure function of <code>(handle, gcloud responses)</code> — its entire existing test suite (which constructs handles directly and never persists a sidecar) is unaffected, and the wedge logic is unit-testable in <code>test_backend_poll.py</code> by writing a sidecar with a stale <code>last_phase_change_ts</code> and a poll-double returning a running+drain-alarm result. The alternative — threading sidecar state into <code>poll()</code>'s signature — would touch every <code>poll()</code> test and every backend's signature for a GCP-only need.</p>
<p><strong>Smaller-scope option considered and rejected:</strong> using the existing <code>creationTimestamp</code> (VM birth) or <code>drain_log_mtime_ago</code> (workload-log mtime) as the clock with zero sidecar change. Rejected because (a) <code>creationTimestamp</code> is run age, not phase age — it would false-fire on every long healthy run past the floor; (b) <code>drain_log_mtime_ago</code> is <code>None</code> on a transport failure (exactly the wedge case — SSH times out, so no fresh mtime), so it cannot be the clock for the very condition we are detecting. The phase-change clock is the only signal that is both phase-specific and survives the SSH failure (it is read from the prior sidecar, not the dead VM).</p>

<p><strong>(c) Fix 2 — embed the reachability watchdog in <code>render_startup_script</code> (~gcp.py:799).</strong> Add a guarded bash background daemon launched right after the <code>exec &gt;&gt;"$EPS_LOG_PATH"</code> redirect (so its output lands in the workload log, not the metadata-runner pipe — same #607/#491 discipline) and BEFORE the workload block. Implementation as a bash function in the shared preamble (so both the hydra and <code>--workload-cmd</code> branches get it, mirroring <code>_eps_persist_diagnostics</code>):</p>
<pre><code>_eps_reachability_watchdog() {
  # REACHABILITY watchdog (#669), NOT liveness (systemd #21083: a liveness
  # /dev/watchdog keeps getting fed on a wedged-but-running VM). Probes the
  # GCE metadata server + an external endpoint; on sustained loss forces a
  # clean TERMINATED (the poller reads TERMINATED as dead -> #659 failover).
  local interval=30          # probe cadence, seconds
  local threshold=10         # consecutive failures before terminate (~5 min)
  local fails=0
  while true; do
    sleep "$interval"
    # -m 5: 5s connect+xfer cap so a hung NIC doesn't block the loop.
    # Metadata server is link-local (169.254.169.254) — reachable even with a
    # dead DHCP lease IF routing is intact, so we AND it with an external probe.
    if curl -sf -m 5 -H 'Metadata-Flavor: Google' \
         http://169.254.169.254/computeMetadata/v1/instance/id >/dev/null 2>&1 \
       && curl -sf -m 5 https://huggingface.co/ -o /dev/null 2>&1; then
      fails=0
    else
      fails=$((fails + 1))
      echo "[eps-watchdog] reachability probe FAILED ($fails/$threshold)" >&3 2>/dev/null || true
      if [ "$fails" -ge "$threshold" ]; then
        echo "[eps-watchdog] sustained network loss -> shutting down for clean TERMINATED (#669)" >&3 2>/dev/null || true
        # best-effort phase write (will no-op if metadata is unreachable, which
        # is exactly when we need the shutdown) then force TERMINATED.
        _eps_phase wedged 2>/dev/null || true
        shutdown -h now 2>/dev/null || poweroff -f 2>/dev/null || halt -f
        return 0
      fi
    fi
  done
}
_eps_reachability_watchdog &amp;
EPS_WATCHDOG_PID=$!
</code></pre>
<p>Notes: the daemon is <code>kill</code>ed in the clean-exit tail (before the success-sentinel scp) and is harmless on a crash (the EXIT trap's <code>shutdown</code> reaps it). The <code>shutdown -h now</code> → <code>poweroff -f</code> → <code>halt -f</code> ladder is because a sufficiently wedged VM may not have a working <code>systemd-shutdown</code>; <code>halt -f</code> is the last-resort hard stop. Writing <code>_eps_phase wedged</code> first is best-effort — if metadata is reachable enough to land it, Fix&nbsp;1's escalation also fires; if not, the <code>TERMINATED</code> state (Fix&nbsp;4) is the recovery.</p>
<p><strong>Why code, not a model call?</strong> N/A — this is a bash control-flow daemon (network probe + counter + shutdown); there is no unstructured-data heuristic here.</p>

<h3>4.3 <code>scripts/backend_poll.py</code></h3>
<p><strong>(d) Fix 1 — the wedge classifier (poller-side staleness clock).</strong> Between the <code>backend.poll(handle)</code> call (line 746) and the <code>_is_gcp_async_workload_failure</code> check (line 760), insert the GCP-only escalation. <pre><code>GCP_WORKLOAD_WEDGED_PHASE = "terminal_workload_wedged"

    """Escalate a frozen non-terminal GCP phase + drain alarm to terminal wedged (#669).

    Poller-side staleness clock: compares the observed running phase to the
    sidecar's last_phase/last_phase_change_ts. Returns the SAME result unless

<p><strong>Note on <code>terminal_terminated</code> scope:</strong> <code>_gcp_status_to_poll_result</code> maps <code>TERMINATED</code> → <code>_terminal_dead_poll(reason="terminated")</code> → <code>current_phase="terminal_terminated"</code> (gcp.py:3908). Adding it to the accept-set means ANY GCP <code>TERMINATED</code> (watchdog self-stop, spot preemption, max-run-duration trip) now fails over to RunPod. This is the intended behavior under #658's "GCP failure of ANY class fails over to RunPod" contract — but it is a behavior CHANGE for the spot-preemption / max-run-duration cases, which previously went straight to <code>dead</code>. The exactly-once lease + the RunPod-re-crash → <code>blocked</code> bound make it safe (a re-dispatch is at most one extra RunPod run). This is called out in §8 Risks and §12 Assumptions as the one non-obvious widening; if the consistency-checker flags it as a second variable, the conservative fallback is to gate on a NEW <code>"terminal_wedged_terminated"</code> reason emitted ONLY when the watchdog wrote <code>eps/phase=wedged</code> before shutting down (distinguishes a watchdog-stop from a spot-preempt) — but that requires the phase write to land, which the wedge case cannot guarantee, so the broader <code>terminal_terminated</code> accept is the robust choice.</p>

<h2>8. Risks and failure modes</h2>
<table>
<tr><th>Risk</th><th>Likelihood</th><th>Mitigation</th></tr>
<tr><td>False-positive wedge kills a healthy long-running phase</td><td>Low</td><td>The classification requires the CONJUNCTION of (phase unchanged for &gt;15&nbsp;min) AND (drain alarm = SSH transport failure). A healthy phase that genuinely runs &gt;15&nbsp;min without a phase write (e.g. a long training epoch) has NO drain alarm (SSH works), so it stays <code>running</code>. The anti-false-positive test pins this. Floor (15&nbsp;min) is well above normal inter-phase gaps and well below the #667 ~32-min wedge window.</td></tr>
<tr><td>Startup-script byte-identity snapshot test trips</td><td>Certain</td><td><code>test_render_startup_script_hydra_only_byte_identical_to_pre_change_snapshot</code> will FAIL once the watchdog is added to the shared preamble. The structural #658 tests keep the snapshot non-tautological.</td></tr>
<tr><td>Watchdog <code>curl</code> to HF false-fails on a transient HF 503 (not a real wedge)</td><td>Low-Med</td><td>The 10-consecutive-failure threshold (~5&nbsp;min of sustained loss across 30s probes) tolerates transient single-endpoint blips. <tr><td><code>terminal_terminated</code> accept-set widening re-dispatches spot-preemption / max-run-duration stops to RunPod</td><td>Medium (behavior change)</td><td>Intended under #658's "any-class failover" contract; bounded by exactly-once lease + RunPod-re-crash→blocked. <tr><td>Phase-clock sidecar write failure (EDQUOT) corrupts the staleness clock</td><td>Low</td><td>Clock write is non-fatal + logged; a failed write means the next tick re-reads stale state and either re-stamps (phase advanced) or re-evaluates the floor — it can never manufacture a wedge from a write failure (the floor + drain-alarm conjunction still gates).</td></tr>
<tr><td>Watchdog daemon not reaped on clean exit → orphan process holding the VM</td><td>Low</td><td>The clean-exit tail <code>kill "$EPS_WATCHDOG_PID"</code> before the success sentinel; on crash the EXIT-trap <code>shutdown</code> reaps it. <h2>11. Decision rationale (load-bearing constants)</h2>
<p>Not ML hyperparameters, but load-bearing infra constants — each grounded:</p>
<table>
<tr><th>Constant</th><th>Value</th><th>Why / source</th></tr>
<tr><td><code>GCP_STALENESS_FLOOR_SEC</code></td><td>900 (15 min)</td><td>Bounded BELOW by: the #667 wedge ran ~32&nbsp;min before manual detection (workload started 11:01:50Z, DHCP died 11:34:06Z), so any floor &lt; ~30&nbsp;min catches it. Bounded ABOVE by: it must exceed any normal inter-phase gap so a healthy run never trips. The GCP drain SSH timeout is 300s (gcp.py:1819) and the bg-poll quiet interval is up to 1800s (30 min) — a floor of 900s = 15&nbsp;min sits comfortably between (≥ 2× the drain timeout + ≥ 1 normal poll cycle, &lt; the wedge window, &lt; the 30-min quiet interval so at least one poll re-evaluates within the floor). <strong>Source:</strong> #667 evidence timeline + gcp.py:1819 (drain timeout) + base.py:291 (quiet interval). Adjustable upward to 1200s if the false-positive risk on long phases proves real in a future live run — flagged Medium confidence.</td></tr>
<tr><td>Watchdog probe interval</td><td>30s</td><td>Matches the drain/poll cadence granularity; 10 probes (= 5&nbsp;min) is a meaningful sustained-loss window without burning CPU on a tight loop. <strong>Source:</strong> body's suggested ~3-5&nbsp;min tunable; 30s × 10 = 5&nbsp;min lands at the top of that range (conservative — fewer false terminates).</td></tr>
<tr><td>Watchdog failure threshold</td><td>10 consecutive (≈5 min)</td><td>The systemd-networkd bug causes a PERMANENT lease loss (the renew never retries) — so once it fires the loss is sustained, and a 5-min confirmation window cleanly separates it from a transient single-endpoint blip. <strong>Source:</strong> systemd #32045/#33934 ("permanent loss of connectivity"); body's ~3-5&nbsp;min tunable.</td></tr>
<tr><td>Watchdog probe targets</td><td>metadata <code>169.254.169.254</code> AND external (HF)</td><td>The metadata server is link-local — reachable even with a dead DHCP lease if routing survives, so it alone under-detects; AND-ing an external endpoint catches the full-network-loss case. HF is the canonical external dependency every workload already needs. <strong>Source:</strong> body's explicit "metadata server + an external endpoint e.g. HF" + systemd #21083 (reachability not liveness).</td></tr>
<tr><td>Termination action</td><td><code>shutdown -h now</code> → <code>poweroff -f</code> → <code>halt -f</code></td><td><code>shutdown -h now</code> reaches a clean <code>TERMINATED</code> (poller-dead, gcp.py:3908); the hard-stop ladder covers a VM wedged enough that <code>systemd-shutdown</code> itself hangs. <strong>Source:</strong> body ("shutdown -h now"); the ladder is the defensive extension for the wedged case.</td></tr>
<tr><td><code>--no-restart-on-failure</code> (automaticRestart=false)</td><td>added</td><td>A watchdog self-shutdown must be FINAL — auto-restart would bring the VM back into the same wedged state (the systemd bug recurs under the same load). Composes with <code>--instance-termination-action=DELETE</code> (independent scheduling fields). <strong>Source:</strong> Google host-maintenance + limit-vm-runtime docs (independent scheduling block fields); body Fix 3.</td></tr>
<tr><td>Watchdog daemon (bash bg process) vs systemd unit</td><td>bash bg process in startup script</td><td>Mirrors the existing <code>_eps_persist_diagnostics</code> EXIT-trap embedding (#658) — no extra unit file to install/enable on a DLVM image, reaped by the same EXIT trap, output to the same workload log. A systemd liveness watchdog would NOT catch this class anyway (systemd #21083). <strong>Source:</strong> #658 precedent + systemd #21083.</td></tr>
