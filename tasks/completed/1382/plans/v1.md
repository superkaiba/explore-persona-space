### Item 2 — parser fix (chosen) vs allowlist (rejected): narrow `v<digits>.` version-stamp tolerance

**The failing datum (byte-verbatim, `tasks/*/1092/events.jsonl`, kind `epm:same-issue-followup-run`, ts `2026-07-11T00:06:50Z`):** a single `; `-joined line whose FIRST segment is `v1. followup_label: cross-corpus-probe-transfer` — field-led modulo the leading `v1. ` stamp. `parse_followup_note_field` (task_workflow.py:2811-2882) strips only `^[\s\-*]+` before the anchor check, so the segment core starts `v1. ` → `None` for `followup_label` (while `source`/`round`/`outcome` in later segments parse fine).

**Both options evaluated:**

- **Allowlist (rejected):** adding `(1092, "2026-07-11T00:06:50Z")` to `KNOWN_MALFORMED_RUN_MARKERS` greens the test but leaves the LIVE hazard open — the run marker still closes nothing, so `cross-corpus-probe-transfer` stays unrun+dispatchable (verified live) and Step 0 can re-dispatch a completed round (the #658 ghost-label class); closing it would then additionally require a #1111-§4.5-style corrective re-post mutating live task #1092's event stream. The allowlist's own documented bar (#1111 rationale 6) is for notes that are unparseable **under the intended contract** and repaired as data; #1092's note is field-led — treating it as malformed would be encoding yesterday's parser limitation, not the intended contract, i.e. exactly the "never weaken a test" failure the task constraints ban.
- **Parser fix (chosen):** a one-line tolerance for a leading version stamp. This closes the test AND the live hazard with zero live-state mutation, and hardens the parser against the recurrence class (emitters echoing the marker's `v<k>` grammar into the note head).

**Consistency with #1111's field-only decision (required argument):** #1111 rejected **label inference** — manufacturing a label VALUE from leading prose when NO field exists (the #1090 shape), which "needs context the API lacks" and would contradict conservative-close. The version-stamp strip is categorically different: the `followup_label:` FIELD is explicitly present and its value is read from the field, never inferred; the change merely widens the ignorable leading-DECORATION set — which ALREADY includes bullets (`-`, `*`), bold markers, and whitespace — by one more decorative shape. The parser remains strictly field-only: #1090's prose-led note still parses `None` post-fix (verified by simulation). #1111's must-ask line ("extending the parser beyond field parsing") is therefore not tripped; this stays within field parsing.

**Exact change** (task_workflow.py, inside the segment loop, immediately after :2875):

```python
            core = re.sub(r"^[\s\-*]+", "", seg)
            # Leading version stamp (`v1. ` — the #1092 run-note shape, an
            # emitter echoing the marker's `v<k>` grammar into the note head):
            # decorative prefix, same class as bullets/bold — strip it so the
            # field anchor still binds. Lowercase `v` + digits + `.` +
            # REQUIRED whitespace only; anything else is prose and stays
            # unparseable (field-only parsing per #1111 — no label inference).
            core = re.sub(r"^v\d+\.\s+", "", core)
            if core.startswith(f"{field}:") or core.startswith(f"{field}="):
```

plus a one-sentence docstring addition to the strip-list sentence (:2819-2823) naming the `v<k>.` stamp and #1092. Deliberately narrow: lowercase `v` only (the marker version grammar), literal dot, whitespace REQUIRED after the dot (`v1.followup_label:` does NOT strip), applied once per segment, after the bullet/bold strip so `- v2. followup_label: y` composes.

**Why no false positives** (each verified by live simulation this session):
- Mid-segment mentions still parse `None` — the strip is anchored at segment start and does not alter the anchor semantics (`"the v1. followup_label: was missing"` → `None`; `"(source: user-chat)"` → `None`).
- Field VALUES beginning with a stamp are untouched — `"plan: v1. adjust"` still parses `"v1."` (the strip runs before the anchor check but the core starts with `plan:`, so the stamp regex never matches).
- No-space stamp (`"v1.followup_label: x"`) → `None` (unchanged).
- The #1090 prose-led note → `None` (unchanged).

**KNOWN_MALFORMED_RUN_MARKERS: UNCHANGED** — `(1090, "2026-07-07T09:54:27Z")` stays; that note carries no fields at all and remains unparseable post-fix by design. Its documenting comment (:1088-1097) gains no edits beyond, optionally, one clause noting the #1092 stamp tolerance lives in the parser (see §12 allowed deviations).
