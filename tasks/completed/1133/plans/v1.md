## 2. Prior Work / Method delta

**What exists.** `.claude/rules/plan-compute-sizing.md` § "Merge-disk budget" (lines 38–61) requires (a) a stated upper bound on COEXISTING on-disk full-precision artifacts and (b) a cleanup pattern **"If the upper bound exceeds the quota"**. Its critic enforcement is `critic-lens-reference.md` Methodology item 16 (lines 446–466), whose REVISE fires only "when the upper bound exceeds the quota AND the plan does NOT specify the cleanup pattern". `#1118` threads `boot_disk_gb` into the RunPod GPU volume or raises `runpod_volume_infeasible_for_plan`.

**Why the existing block did NOT prevent #1112 (the precise gap — verified against `.claude/plans/issue-1112.md`):**

1. **#1112's plan COMPLIED with the block.** Its §9 stated the bound — "2 FT sycophancy ladders (2 × 15 × 15 GB = 450 GB) + marker FT ladder (75 GB) + 1 transient LoRA merge + caches ≈ 575 GB < 750 GB boot disk" — and a cleanup pattern ("non-selected sycophancy FT rungs deleted immediately after selection"). Item 16's REVISE condition (bound exceeds quota AND no cleanup) was never met, so no critic could bounce it. The rule permits keep-all-until-post-hoc-selection whenever the plan believes the disk is big enough.
2. **Keep-all made the footprint lane-fragile.** The 575 GB peak was sized against the planned GCP 750 GB boot disk; the GCP→RunPod failover delivered the `ft-7b` default 200 GB volume (`backends/runpod.py:767` deliberately did not map `boot_disk_gb` to the GPU volume — the #1118 gap), and the peak-scales-with-n_rungs design could not fit it. #1112's plan even had a RunPod coarse+refine contingency (§8) — but the automatic failover ran the normal grid, not the contingency.
3. **Per-rung size error was multiplied by n_rungs.** Planned ~15 GB/rung; realized 15–28 GB/rung (a full-FT save carries more than the bf16 weights). Under keep-all the error multiplies by 30 rungs; under retention it multiplies by ~2–3.

**Method delta vs the existing block:** the new clause converts the conditional cleanup requirement into an unconditional retention DEFAULT for the ladder-phase subclass (keep dose-selected + latest; delete ruled-out rungs between rungs), changes the sizing denominator (RETAINED set + in-flight high-water mark, never `n_rungs × per_rung_gb`), makes keep-all a justified exception that must size the full ladder at realized per-rung size AND declare it in `--boot-disk-gb` (arming #1118's thread-or-refuse), and adds the item-16 REVISE for a keep-every-rung estimate. Upload-before-delete is untouched: between-rung deletion is legal only via a plan-declared §10 `discarded_artifacts:` entry (the #1112 precedent — its own plan declared "non-selected full-FT rung checkpoints (~40 × 15 GB)" with reason + regen recipe) or upload-first.

**Dose-ladder / multi-rung checkpoint retention — keep the dose-selected +

a dose-to-band checkpoint ladder (earliest-rung-in-band), a band-stop grid,
a dose-matching checkpoint grid, any long run saving every k steps for a
later pick — MUST state its checkpoint-retention policy in §9. DEFAULT:
retain only (i) the dose-selected rung(s) (or the current selection
candidate while the read is pending), (ii) the latest rung (crash-resume),
and (iii) rungs the selection read has not yet covered; every ruled-out
rung is deleted BETWEEN rungs, not in one sweep after the ladder completes.
Three implementations bound the on-disk ladder: an online per-rung
selection read (the deterministic log-prob band-stop callback is the
marker-recipe case — `.claude/rules/marker-training-recipe.md`);
upload-as-you-go then delete locally (select against the Hub copies,
re-download only the selected rung); or a coarse+refine two-pass grid
(sparse saves that fit, judge, deterministic retrain to the bracketing
steps — #1112's own RunPod contingency). Deletion composes with the Upload
Policy UNCHANGED: a non-selected rung is deleted only when covered by a
plan §10 `discarded_artifacts:` entry ({name, reason, regen_recipe} —
non-selected rungs of a deterministic retrain from pinned data + commit +
seed are the canonical candidate, #1112's own declared discard) OR
uploaded first; selected / headline-carrying checkpoints keep the full
upload-before-delete invariant (never delete an unuploaded, undeclared
checkpoint). The §9 disk estimate sizes to the RETAINED set plus the
transient high-water mark (`retained_rungs × per_rung_gb +
in_flight_rung_gb + concurrent transients`), with `per_rung_gb` grounded
on what the trainer ACTUALLY writes — weights + optimizer state, so a
full-FT rung can run ~2× the bf16 weights (#1112 realized 15–28 GB/rung
against a ~15 GB plan). Keeping every rung locally is the JUSTIFIED
EXCEPTION, not the default: the plan must say why the rungs must coexist,
size the disk to the FULL ladder at realized per-rung size, and DECLARE
that requirement in the launch flags (`--boot-disk-gb`) so the #1118
volume-threading / typed refusal engages on a lane failover. A merge-disk
bound that fits the PLANNED lane's disk is NOT sufficient on its own
(#1112: a compliant 575 GB keep-all bound sat under the planned 750 GB GCP
boot disk; the GCP→RunPod failover delivered the `ft-7b` default 200 GB

(`.claude/rules/critic-lens-reference.md`) REVISEs a ladder plan whose
disk estimate assumes keeping every rung without this justification.
