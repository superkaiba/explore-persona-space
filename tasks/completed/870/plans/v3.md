## 5. Precise trigger definition (operational)

- **Who runs it, when:** the ORCHESTRATOR, at Step 5.bis(a) (post-code-review-PASS, pre-dispatch), on any round whose events carry an `epm:compute-deviation v1` (this covers implementer-report-time AND any mid-run re-post routed here; the detection basis itself is #869's scope).
- **Input:** the marker's `basis:` + `component:` text, plus the same round's implementer report. No other artifact is required — the policy is decidable from marker text alone.
- **Pre-resolved markers:** a marker carrying `action: continue_as_is` (or any resolution) WITHOUT a lever-0 record in the component's chain (`action: vectorize_fix_round` ran, or `signature_check: negative`) is UNRESOLVED — route through step 0; at ratio ≥ 5× without a valid clause-0c finding the pre-resolution is VOID. Both incident markers (#722 v2, #763 v2) arrived exactly this way.
- **Fires (overhead-bound) when** the basis attributes the projected wall to a serial loop of individually-small units per the `.claude/rules/vectorize-many-cell-fits.md` trigger (canonical; the in-yaml enumeration is illustrative so #869's broadening flows through without re-editing this policy). Worked positives: #722's "per-layer 3-30 min … 28 layers" LOCO loop; #763's "~1.4M GLM fits/null" serial IRLS loop.
- **Does not fire when** the basis names: a genuinely FLOP-bound workload already batched (roofline arithmetic), external API latency/rate caps, download bandwidth, GPU-capacity queue wait, or shared-VM contention on an ALREADY-vectorized job. Worked negative: #763's v3 marker (2026-07-02, ratio 7.5×, "smoke-phase wall on a contended VM at load ~68" for an already-batched smoke) — a valid `signature_check: negative` under class (iii), and because it cites the already-vectorized state plus load numbers it ALSO satisfies the literal clause-0c bar for a ≥5× `continue_as_is`.
- **Recorded negative finding (what unlocks descope/continue):** an `epm:compute-deviation v<next>` marker carrying `signature_check: negative` plus 1-3 lines of arithmetic (FLOP/roofline estimate, a cited true sequential dependency, or a named quantified non-compute bottleneck). It may be written by the orchestrator at step 0 (clear basis) or returned by the dispatched fix round (ambiguous basis, code inspection shows the loop is already batched / not batchable).
- **Clause 0c gating:** `continue_as_is` at ratio ≥ 5× requires a recorded QUANTIFIED irreducibility finding on the marker — `flop_bound_finding:`, or a `signature_check: negative` record already meeting the bar — via (i) roofline FLOP-bound arithmetic, (ii) a true sequential dependency, or (iii) a named non-compute bottleneck quantified to account for the ratio (contention only with the already-vectorized state cited + load numbers). At 2× ≤ ratio < 5× with lever 0 resolved, `continue_as_is` needs only the standard rationale. There is deliberately NO de-minimis floor above 2× (cost bounded by once-per-component + 0b; asymmetry accepted).
- **Post-fix residual (no wedge):** the fix round's closing re-post carries the residual classification; a genuinely FLOP-/dependency-bound residual's post-fix arithmetic CONSTITUTES the 0c finding. Once `action: vectorize_fix_round` exists, step 0 is NEVER re-run — a missing classification gets ONE corrective re-post (no second fix round), then descope/gate proceed on the post-fix numbers.
- **Loop guard:** one mandatory fix round per component, keyed on `action: vectorize_fix_round` in the component's marker chain; `component:` must reuse the planner-§9 row name verbatim across re-posts (free-text drift bypasses or over-applies the guard).

## 11. Decision Rationale

- **Vectorize as a PRE-GATE auto-action, not a third gate option.** What: the fix round runs before the gate; the gate keeps 2 options. Why: preserves the #397 Fix #7 two-option cap and the "auto-pivot is the default; halt is the rare exception" philosophy — a mandatory fix round is an action, not a choice. Source: workflow.yaml gate id=12 reason + `epm:compute-deviation` marker rationale; task #870 body constraint. Alternatives: a third gate option (rejected — breaks the 2-option cap and asks the user/auto-resolver to choose what should be mandatory).
- **≥5× threshold for clause 0c.** What: `continue_as_is` at ratio ≥5× requires a recorded quantified irreducibility finding. Why: separates the band contention alone can explain from the implementation-defect band. Source: the experiment-implementer memory ("expect 2-5× slowdown over a single-tenant timing" under contention — so ≤5× is attributable to contention, ≥5× is not) + `code-style.md` FLOPs-floor bullet (">5-10× over the floor means the implementation is leaving throughput on the table") + incidents: #397 at 3-4× (continue/descope was reasonable) vs #722 10× / #763 80× (defects). Alternatives: 2× (rejected — would demand roofline arithmetic for every routine contention overrun); 10× (rejected — #722's 10× would sit exactly at the boundary).
- **Widened 0c taxonomy — (i) roofline arithmetic | (ii) sequential dependency | (iii) quantified non-compute bottleneck (MF-A).** What: the 0c-valid finding classes are aligned with the step-0 negative-signature classes, with (iii) admissible only when quantified (contention only with the already-vectorized state cited + load numbers). Why: a 0c limited to FLOP-bound arithmetic contradicted step 0's own negative taxonomy and would have rejected the plan's worked negative (#763 v3: 7.5× contention on an already-vectorized smoke — a legitimate `continue_as_is`); the quantification bar keeps the #763-v2 failure (bare "not a science blocker" at 80×) inadmissible. Source: #763 v3 marker (2026-07-02) vs #763 v2 marker (2026-07-01); the step-0 negative-signature class list. Alternatives: FLOP-bound-only 0c (rejected — internally inconsistent, over-blocks legitimate quantified bottlenecks); unquantified named bottleneck (rejected — reopens the rubber-stamp escape).
- **Pre-resolved-marker rule (MF-B).** What: any resolution on the marker without a lever-0 record in the component's chain is treated as UNRESOLVED and routed through step 0; a ≥5× pre-resolution without a valid 0c finding is VOID. Why: BOTH incident markers arrived pre-resolved (`action: continue_as_is` — #722 v2; #763 v2 with `resolution_by: orchestrator`), and `epm:compute-deviation` is a legitimate implementer self-tag (crash-fix-rounds.md:186) — without this rule the entire lever is bypassable by whoever writes the marker, and crash-recovery replays of old markers would skip it too. Alternatives: trust any `action:` field (rejected — reproduces both incidents verbatim); restrict marker posting (rejected — changes the posting contract, architectural).
