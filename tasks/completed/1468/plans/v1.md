# Plan: Gate the GCP A100-40 fallback rung on a per-dispatch declared GPU-memory requirement (#1468)

## 0.0 TL;DR (plain English)

- **What I'll run:** I'll add one opt-in launch flag, `--min-gpu-mem-gb`, that a dispatch passes when its workload needs more per-GPU memory than a 40 GB card actually offers; the GCP ladder then skips its A100-40 fallback rung for that dispatch. No flag means the ladder is byte-identical to today. VM-only code + tests, zero GPU-hours.
- **What I expect:** the #1315 failure shape (a co-resident HF-model + vLLM capture workload landing on a 39.49 GiB card and dying at engine init) becomes impossible for any dispatch that declares its requirement, existing dispatches are untouched, and every new and existing router/gcp/CLI test passes.
- **What would change my mind:** if the fact-check finds a second production consumer of `a100_40_fallback_for_intent` / `INTENT_A100_40_FALLBACK` beyond the router ladder, the single-choke-point design needs rework; if the existing byte-identity ladder tests fail with the flag absent, the gate is mis-placed.

## 0. Plan Summary

**Change:** thread a new opt-in `scripts/dispatch_issue.py launch --min-gpu-mem-gb <int>` flag into `spec.extra["min_gpu_mem_gb"]` (exact analogue of the #1010 `--min-ram-gb` precedent at `dispatch_issue.py:2314-2321` / `1268-1275`), and gate `a100_40_fallback_for_intent()` (`src/explore_persona_space/backends/gcp.py:484-496`) to return `None` when the declared requirement exceeds a new conservative constant `A100_40_USABLE_GIB = 38.0` (grounded in #1315's measured 39.49 GiB device total). All five router-ladder consumption sites inherit the gate through the single `a40 = a100_40_fallback_for_intent(spec)` call (`router.py:2741`). **No new failure taxonomy:** a gated ladder simply loses its two A100-40 rungs and falls through to the remaining A100-80 rungs → SLURM → the RunPod terminal rung (H100-80, 80 GB — always satisfies), so no dispatch can become rung-less. `INTENT_A100_40_FALLBACK` membership is untouched. **Docs:** CLAUDE.md § Compute backends parenthetical (also fixing its stale intent list, which omits `capture-7b`), `compute-backend-failover.md` § Part B + § Ladder order, `plan-compute-sizing.md` activation-capture paragraph, router/gcp docstrings. **Tests:** new unit gate tests (`test_gcp_backend.py`), three ladder-shape tests (`test_router.py`), CLI threading tests (`test_dispatch_issue_cli.py`); the existing full-rung-order + fits-predicate tests are the no-flag byte-identity regression pin. **Risks (top 2):** threshold semantics (GiB-vs-GB, strict-greater boundary — documented, boundary-tested) and doc-surface staleness (every grep hit enumerated in §4.6).

## 1. Goal

"Stop the 40GB rung from admitting vLLM workloads that cannot initialize on realistic free device memory." (Task #1468 `## Goal` H2, verbatim; `kind: infra` — no `goal:` frontmatter. Re-read via `task.py view 1468 --json` immediately before returning this plan; unchanged.)

One paragraph: the GCP auto ladder's A100-40 fallback rung is admitted purely by a static intent-keyed map. Incident #1315 (att-20260716-052022, `eps-issue-1315`, a2-highgpu-1g, 2026-07-16 ~05:28Z) shows a workload class — an HF capture model (~15-17 GB resident) co-located with a vLLM engine at `CAPTURE_GPU_MEM_UTIL=0.6` — that is intent-eligible but memory-infeasible on the 40 GB card: vLLM engine init died with `Free memory on device (22.52/39.49 GiB) on startup is less than desired GPU memory utilization (0.6, 23.7 GiB)`, burning a full boot cycle before the flex-start A100-80 retry ran clean. The fix lets a dispatch declare its per-GPU memory requirement so the ladder never books the rung it cannot use.

### 4.2 The gate: `backends/gcp.py`

New module constant next to the map, plus a gate clause inside the existing predicate (diff sketch):

```python
#: Usable device memory (GiB) on the A100-40 rung's a2-highgpu-1g. Incident
#: #1315 measured the card's CUDA-visible total at 39.49 GiB ("Free memory on
#: device (22.52/39.49 GiB)"); 38.0 leaves ~1.5 GiB conservative margin for
#: CUDA context + allocator fragmentation. Gates the fallback rung only —
#: never primary machine selection (#1468).
A100_40_USABLE_GIB: float = 38.0


def a100_40_fallback_for_intent(spec: RunSpec) -> MachineSpec | None:
    """... existing docstring, plus:

    A dispatch may additionally declare its peak per-GPU device-memory
    requirement via ``spec.extra["min_gpu_mem_gb"]`` (GiB;
    ``dispatch_issue.py --min-gpu-mem-gb``, #1468). A declared value
    strictly above :data:`A100_40_USABLE_GIB` returns ``None`` — the
    intent-eligible workload does not FIT the 40 GB card (the #1315
    HF+vLLM co-residency shape) — and the ladder skips the rung exactly
    as for an ineligible intent. Absent declaration: intent-only
    eligibility, byte-identical to the pre-#1468 behavior.
    """
    machine = INTENT_A100_40_FALLBACK.get(spec.intent)
    if machine is None:
        return None
    declared = (spec.extra or {}).get("min_gpu_mem_gb")
    if declared is not None and float(declared) > A100_40_USABLE_GIB:
        return None
    return machine
```

A malformed (non-numeric) present value raises `TypeError`/`ValueError` loudly — fail-fast, consistent with project policy; unreachable from the CLI (argparse `type=int` coerces at parse time). Strict `>` at the boundary: `min_gpu_mem_gb=38` keeps the rung, `39` drops it.

Additionally append one sentence to the `INTENT_A100_40_FALLBACK` comment block (gcp.py:458-474): membership is intent-level ELIGIBILITY only; per-dispatch FIT is the `min_gpu_mem_gb` gate — a co-resident HF+vLLM capture phase (#1315) is intent-eligible yet must declare. **No intent is removed from the map** (per the task constraint; `capture-7b` alone often fits 40 GB — #752's rationale stands for non-co-resident captures).

### 4.4 Fail-loud semantics: no new taxonomy needed

A gated dispatch never becomes rung-less: the A100-40 rung is a mid-ladder FALLBACK, so dropping it leaves the primary/A100-80 rungs, then the SLURM lanes, then the RunPod terminal rung — where every mapped GPU intent translates to an 80 GB-class RunPod pod (`RUNPOD_INTENT_FOR_GCP_INTENT`, #940: `capture-7b`→`eval`, identity rows otherwise; RunPod defaults are H100-80 per the intent table). Exhaustion of all of those already raises `NoComputeAvailableError` through the existing path. This deliberately does NOT copy #1010's typed refusal (`cpu_fallback_infeasible_for_plan`): that gate protects a TERMINAL rung with nothing below it; here refusal semantics would be wrong (the dispatch is servable one rung up). Residual, documented not solved: the gate does not validate the PRIMARY machine (an `eval` dispatch declaring 30 GiB still books its L4 primary — intent choice fixes the primary machine, and the #752 `capture-7b` precedent is the established fix for a too-small primary; declaring >~79 GiB behaves like any >38 declaration).

## 11. Decision Rationale

- **Mechanism = per-dispatch declared requirement gating the fallback predicate (candidate 1).** *Why:* the failure is workload-specific, not intent-specific — the same `capture-7b` intent legitimately fits 40 GB without co-residency (#752), so intent-map surgery over- or under-corrects; explicit declaration keeps the map's static eligibility as the default and encodes the missing term (actual peak) at the only place it is known (the dispatch composer). *Source:* task #1468 body candidate (1); #1010 precedent (`dispatch_issue.py:1268-1275`, `router.py:2940-2960`). *Alternatives rejected:* (2) auto-lower `gpu_memory_utilization` on the 40 GB rung — disfavored by #1315's own failure marker ("no env knob exists for the util constant and 40GB co-residency would be fragile even at 0.55"), and it silently changes workload semantics per rung; (3) pre-probe free memory before engine start — the boot cycle is already spent by probe time (at best a faster failover, at worst a new flake surface).
- **Gate location = inside `a100_40_fallback_for_intent`.** *Why:* single production choke point (`router.py:2741`) feeding all five rung-emission sites incl. the pinned path — zero router code change, and the function already takes the full `RunSpec` and owns the `None` = "no rung" contract (gcp.py:488-490). *Source:* gcp.py:484-496 + router.py:2741/2793/2806/2812/2823. *Alternative:* router-side filtering at each emission — 5 edit sites, drift-prone.
- **Flag name `--min-gpu-mem-gb`, extra key `min_gpu_mem_gb`, `type=int`.** *Why:* byte-level family consistency with `--min-ram-gb`/`min_ram_gb` (#1010) so composers and greps find it by analogy. *Source:* `dispatch_issue.py:2314-2321`. *Alternatives:* `--min-hbm-gib` (more precise unit, breaks family naming); float type (spurious precision for a coarse peak declaration).
- **Threshold `A100_40_USABLE_GIB = 38.0`, strict `>`.** *What:* the usable-GiB constant the declaration is compared against. *Why:* #1315 measured the a2-highgpu-1g CUDA-visible total at 39.49 GiB; 38.0 leaves ~1.5 GiB for CUDA context + allocator fragmentation, and #1315's marker judges co-residency "fragile even at 0.55" util (21.7 GiB desired vs 22.52 free — a <1 GiB margin), supporting a ≥1 GiB safety band. *Source:* #1315 failure marker via task #1468 body (`Free memory on device (22.52/39.49 GiB) ... (0.6, 23.7 GiB)`). The 39.49 figure is measured; the 1.49 GiB margin is a conservative judgment call — margin choice marked in §12 as the one Low-confidence value (any value in [36, 39] preserves the fix for the #1315 shape, which declares ≥ ~40).
- **Absence = byte-identical ladder (opt-in).** *Why:* the load-bearing backwards-compat constraint from the task body; every existing dispatch and every launch composer is untouched; #1010 set the identical "flag-less launches keep today's behavior" contract. *Source:* task #1468 constraints; `compute-backend-failover.md` § Footprint feasibility gate ("flag-less launches keep today's behavior").
- **No new typed refusal / failure taxonomy.** *Why:* the gated rung is mid-ladder with servable rungs below it clear to the RunPod H100-80 terminal rung, so "every GCP rung infeasible" is unreachable for GPU intents; the #1010 typed refusal exists only because ITS rung is terminal. *Source:* router ladder structure (router.py:2705-2831) + `RUNPOD_INTENT_FOR_GCP_INTENT` (#940, compute-backend-failover.md § Intent translation).
- **Constant NOT env-tunable; no dispatch-time co-residency WARNING.** *Why:* minimal diff per the task constraints; an env knob adds a test/ops surface for a value grounded in fixed hardware, and the dispatcher cannot infer co-residency to warn on (the #606 `_ft_intent_gcp_default_boot_disk` warning keys on intent alone — here intent alone is insufficient by construction). Both are viable follow-ups if adoption proves weak. *Source:* task #1468 "Keep the diff minimal"; `dispatch_issue.py:1095-1123` (#606 warning shape).
- **Map membership untouched; comment-only intent-metadata change.** *Why:* explicit task constraint ("do NOT silently remove intents"); the static eligibility remains correct for non-co-resident workloads. *Source:* task #1468 body; #752 (task 752 plan v1) capture-7b rationale.
