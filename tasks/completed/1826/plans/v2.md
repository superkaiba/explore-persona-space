## Method delta (vs the filed diff sketch)

The filed sketch proposed `\bH\d+[a-z]?\b`. **REJECTED — it regresses the
deliberate GPU-name calibration** documented at the definition site
(`scripts/verify_task_body.py:7809-7815`): `H\d+` matches `H100`/`H200`/`H20`,
all pinned known-good in the existing classifier test. The plan instead uses:

```
\bH\d[a-z]?\b
```

Single digit (unchanged — multi-digit `H20`/`H100`/`H200` structurally cannot
match because no word boundary exists between two digits) + optional single
lowercase letter (catches `H1c`/`H1a`/`H4b`; uppercase-suffix and
lowercase-`h` forms stay clean per the project's hypothesis-tag convention).
The body's own scope note licenses this calibration ("calibrate the `[a-z]?`
bound … accordingly").

False-positive envelope of the widen, considered and accepted: newly matchable
tokens are exactly `H<digit><lowercase letter>` standalones (e.g. `H2o`,
`H1b`). None occur as legitimate rendered figure-text labels in this project's
domain (GPU names are multi-digit; flu-strain style `H5N1` has an uppercase
letter mid-token so `\b` cannot fire); check 28 is WARN-only, so a residual
false positive costs an acknowledge-in-body line, never a block.
