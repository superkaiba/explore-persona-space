### (b) FAIL-classification rule

Parse each `verifier_logs/<N>.log`:

- **In-scope (repair):** a `[FAIL]` line whose check name is exactly one of `Figure URL resolvable`, `Reproducibility URL permanence`, `Reproducibility artifact URLs exist` — EXCEPT a check-8 FAIL whose detail is `Reproducibility section missing` (that's a legacy-shape problem, out of scope).
- **Out-of-scope (record only):** any other `[FAIL]` line (shape, title, MDX, lr-reconcile, etc.). These are listed in the report as "pre-existing, out of scope per #575 clarifier" — never repaired here.
- **Unverified notes:** `unverified (existence not confirmed)` substrings on PASS lines are recorded; for each, one manual re-probe. **A HEAD 404 is NOT definitive** (some hosts 404/405 HEAD where GET succeeds): before promoting any HTTP-derived 404 to in-scope FAIL, confirm with a browser-equivalent redirect-following GET — `curl -fsSL -m 15 -o /dev/null -w '%{http_code}' <url>` — and, for HF/WandB URLs, an authenticated re-probe (`huggingface_hub` listing / run-id lookup) so a live-but-auth-gated URL is never misclassified as dead. Only a GET-confirmed 404 counts as in-scope FAIL; anything else → recorded-unverified (the verifier's own semantics; an acceptable terminal state surfaced to the promotion-time reader).

Classification is a ~30-line throwaway parse (grep/awk or a python one-liner) writing `$ART/classification.tsv` with columns: `task_id | overall | in_scope_fails | out_of_scope_fails | unverified_notes`.

Parser nuances (fact-checked against `CheckResult.render()`): (i) the ` — <detail>` suffix is emitted only when detail is non-empty — do NOT require the separator on every line; (ii) the detail string `Reproducibility section missing` is shared by other check names (`Reproducibility three subgroups present`, `Reproducibility sentinel scrub`) — the carve-out keys on check-name AND detail together; (iii) `OVERALL: PASS` has no parenthetical (only FAIL carries `(n of N checks failed)`).

**Why code, not a model call?** The verifier output is a fixed line format with exact check-name strings; classification is literal string matching at N=50. Deterministic, instant, zero ambiguity. A model call adds nothing. (Would flip if check names became free-form prose.)

### (c) Repair procedure per failure type

Before ANY body edit: post the claim marker —
`uv run python scripts/task.py post-marker 575 epm:progress --note "URL-repair claim: batch-editing bodies of tasks <list of FAILing IDs> for dead figure/repro URLs (task #575 sweep)"` — per the CLAUDE.md concurrent-committers rule.

**Two cross-cutting guards on EVERY same-repo URL rewrite (critic ensemble Must-Fix — closes the #507 recurrence channel through the repair path itself):**

- **Remote-reachability gate.** A locally-resolvable SHA can be unpushed (worktree/issue-branch commits abound in this repo; `git log --all` traverses them), and BOTH the repair-time `cat-file` verify AND the §3e re-verification resolve same-repo URLs against the LOCAL object DB — so an unpushed re-pin passes every gate while `raw.githubusercontent.com` 404s on the dashboard. Therefore: candidate search uses `git log origin/main -- <path>` (NOT `--all`), every re-pinned SHA must satisfy `git merge-base --is-ancestor <sha> origin/main` (post-fetch), moving-refs pin against `origin/main` (never local `main`, which can be ahead), AND each rewritten `raw.githubusercontent.com` / `github.com` URL gets one final unauthenticated `curl -fsSL -o /dev/null -w '%{http_code}'` expecting <400 before the row is marked repaired (one retry after ~60s for raw CDN lag on just-pushed commits; on persistent failure the row is NOT marked repaired).
- **Provenance guard (existence ≠ version identity).** "Newest commit containing the path" can silently swap in a LATER, regenerated artifact than the one the body's prose describes. For each rewrite record `old_url → new_url`, the evidence source, and a one-line sameness rationale in `$ART/repairs/<N>.provenance.tsv`. When `git log origin/main -- <path>` shows the path at MULTIPLE distinct blob hashes, prefer the commit nearest the body's original (broken) pin date / the task's own artifact-creation markers, and eyeball each repaired figure against its caption (expected 0-5 repairs — minutes of work). If sameness cannot be established, flag `unrepairable/version-ambiguous` and leave the body untouched rather than re-pinning silently.

Per failure type, in order of expected frequency:

1. **Same-repo raw URL, SHA resolves but path absent (cat-file miss), or definitive 404.**
   `git log origin/main --oneline -- <repo-relative-path>` → iterate from newest to the newest commit where `git cat-file -e <sha>:<path>` succeeds (the newest log entry can be the deletion itself) AND the remote-reachability gate passes → rewrite the URL's SHA segment, subject to the provenance guard. If the path never appears in history but the file exists on disk (e.g. an uncommitted figure under `figures/issue_<N>/`): commit it by explicit path to `main`, push, pin the URL to that new commit SHA (push-first makes the reachability gate pass by construction). If a near-miss path exists (typo/rename), fix the path component instead — verified by cat-file + gates before writing.
2. **Moving-ref URL** (`/main|master|HEAD/` in a raw or blob/tree URL): pin to `git rev-parse origin/main` (or the newest origin-reachable SHA containing the file) → verify cat-file + both gates → substitute the SHA.
3. **Unpinned HF URL** (check 8 shape): resolve the correct pinned form via `huggingface_hub` (`list_repo_refs` / `list_repo_files` — NOT the `hf` CLI, per upload-policy) and rewrite to `/tree/<commit>` or `/blob/<commit>`; verify the path resolves in the listing first.
4. **Unpinned WandB URL** (check 8 shape): recover the run id from the task's `eval_results/issue_<N>/.../run_result.json` (`wandb_run_id` field) or events.jsonl markers; rewrite to `/runs/<id>`. Never guess an id.
5. **Truly-missing artifact** (no SHA in history has the file, not on disk, no HF/WandB record): **flag, don't fabricate.** Record in the report as `unrepairable: <url> — artifact does not exist in git history, on disk, or on the cited host`, and append a one-line note to that task via `task.py post-marker <N> epm:progress --note "..."` so the eventual promoter sees it. The body is left untouched for that URL.

### (d) Write-back

For each FAILing task, run the whole copy→edit→diff→write pass in one tight per-task sequence (never batch all copies up front): copy `body.md` to `$ART/repairs/<N>.md`, record `BASE_HASH=$(sha256sum body.md)`, apply URL-token-only edits to the copy, then **diff-discipline check** — `diff <(task body) $ART/repairs/<N>.md` must show only lines whose change is confined to URL spans (compare character-wise within each changed line: outside the URL token the line must be byte-equal — a changed line may NOT carry both a URL edit and prose drift); any prose/frontmatter drift aborts the repair for re-edit. Then the **CAS gate** (closes the read-modify-write race a concurrent session could lose to): immediately before writing, re-read the live `body.md` and compare its sha256 to `BASE_HASH` — on mismatch, discard the repair copy and regenerate from the fresh body. Then:

```bash
uv run python scripts/task.py set-body <N> --file "$ART/repairs/<N>.md"   # NO --snapshot — link repair, not promotion
```

`set-body` is the single writer (flock + one commit); never edit `tasks/.../body.md` directly.

### (e) Re-verification

Re-run `verify_task_body.py --issue <N>` for every repaired task → `$ART/verifier_logs/<N>.post.log`. Success criterion: **every in-scope URL check that FAILed pre-repair now reads `[PASS]`**, with the same out-of-scope carve-out as §3b — a residual `[FAIL] Reproducibility URL permanence — Reproducibility section missing` (legacy body with no Reproducibility H2) is recorded as out-of-scope, not a repair failure (otherwise the criterion is unsatisfiable on that body class). **NOT** `OVERALL: PASS` — legacy bodies may retain out-of-scope shape FAILs, which is acceptable and recorded. Additionally, every rewritten URL has its <400 GET confirmation from the §3c remote-reachability gate recorded alongside.

### (f) Deliverable

This task's own clean-result-style summary body (kind: analysis, written via the normal analyzer path at the end of `/issue 575`): per-task verdict table (one row per census task: task id, overall verdict, **URLs actually probed** (parsed free from the PASS detail — `N URL(s)` / `no images to check`; a zero-probed legacy body is flagged explicitly, never counted as clean), in-scope FAILs found, repair applied + provenance note, post-repair verdict distinguishing `PASS (all URLs verified)` from `PASS (n unverified)`), the list of out-of-scope FAILs observed (for the promotion-time record, not repaired), unverified-URL notes, and unrepairable flags (incl. `version-ambiguous` / `provenance-uncertain`). **Headline claim scoping:** the summary claims "all census bodies pass verifier checks 4b/8/8b, with K URLs probed and M unverified/unprobed (fenced URLs and non-TL;DR-section images are outside the verifier's scan scope)" — NOT "the backlog is URL-clean". Raw verifier logs + classification.tsv + repair diffs + provenance.tsv stay in `artifacts/` and are referenced from the body.

## 5. Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| Transient network errors misread as FAILs | Low by construction | Verifier already downgrades non-404 probe failures to `unverified` PASS notes; classification treats only `[FAIL]` lines as failures; unverified notes get one manual `curl -I` re-probe |
| HEAD-probe rate limiting (github/HF) at -P4 | Low | Most probes are offline `git cat-file`; cap parallelism at 4; any rate-limit response is non-404 → `unverified`, not FAIL |
| Concurrent sessions editing the same parked bodies | Medium (active multi-session repo) | Claim marker on #575 naming the IDs before batch-editing; `set-body` holds flock + commits atomically; re-read body immediately before each repair edit |
| A repair accidentally changes prose | Low | Edit a copy, mechanical diff gate (URL-token-only changes) before `set-body`; abort on any prose drift |
| Legacy-body shape FAILs polluting the report | High (expected) | Classification keys on the three exact check names; everything else recorded as out-of-scope, never repaired |
| Task moves status mid-sweep | Medium (`followups_running` flips are common) | Verifier resolves via registry; re-resolve paths with `task.py find <N>`; annotate moved tasks in the report |
| `set-body` push race on the shared repo root | Medium | Stage-by-explicit-path is internal to task.py; on rejected push, `git pull --rebase --autostash` once and retry per CLAUDE.md |
| Check-8 FAIL with detail "Reproducibility section missing" misclassified as URL repair | Low | Explicit carve-out in the classification rule (detail-string match) |
