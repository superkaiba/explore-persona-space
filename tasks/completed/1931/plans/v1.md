## 1. Requirement + acceptance criteria

Requirement (from the task Goal): make a failed pod bootstrap loud at provision
time — one automatic bootstrap retry on nonzero exit, and a fail-loud provision
verdict when bootstrap still exits nonzero — instead of a silently-degraded pod
whose emptiness surfaces only at the first workload launch (incident
pod-1773-regsteer, /daily 2026-07-30 miner-7 P10: first bootstrap died exit 100
leaving `/workspace/explore-persona-space` absent; the pilot launch then failed
`PILOT_MISSING`; a manual bootstrap re-run succeeded immediately).

Acceptance criteria:

1. On `_bootstrap` rc != 0 during provision, the provision tail retries the
   bootstrap EXACTLY ONCE (never more — "never mask a persistent bootstrap
   failure" body constraint), with a loud stderr line announcing the retry and
   the first rc.
2. If the retry exits 0, provision completes as success and the output records
   that a retry happened (the retry line + the success verdict token).
3. If the retry also exits nonzero, provision keeps the existing loud
   diagnostic + `sys.exit(rc)` AND additionally prints a machine-greppable
   one-line verdict token on stderr: `BOOTSTRAP-FAILED pod=<name> rc=<n>`.
4. On success (first try or retry), provision prints a machine-greppable
   `BOOTSTRAP-OK pod=<name>` line before the final "Done. SSH with:" line — so
   a caller that only observes captured output (bg-Bash log, detached
   provision) can distinguish a ready pod from a degraded one WITHOUT reading
   the exit code. This is the fail-loud "provision verdict" deliverable.
5. `--no-bootstrap` semantics unchanged (no retry, no verdict tokens — the
   skip message stays as-is).
6. Existing pod tests stay green; new tests pin criteria 1-5.

The body flagged: "verify at plan time: whether `pod_lifecycle._bootstrap`'s

recorded in `epm:clarify v1`):

  bg-Bash captured output (or the setsid-detached autonomous path,
  pod_lifecycle.py:3241) can miss it; the greppable BOOTSTRAP-OK /
  BOOTSTRAP-FAILED verdict tokens make the outcome observable from output
  alone. This addresses the observed silent failure without needing to pin the
  exact loss mechanism of the incident session.

## 3. Method delta (what differs from prior related work)

Prior state: single bootstrap attempt; failure = prose stderr + nonzero exit
only. Delta: retry-once loop around `_bootstrap` in the ONE shared consumer
(`_provision_wait_register_bootstrap`, reached from both the GPU :2218 and CPU
:2289 create paths — one edit covers both), plus structured verdict tokens.
`scripts/bootstrap_pod.sh` is NOT modified: retrying the whole idempotent
script caller-side covers every internal failure class (apt, network, git,
uv) with one mechanism; the script's steps are already re-run-safe (the
documented manual recovery IS a full re-run, and the incident's re-run
succeeded).
