## §3 Design

### c62 — `c62_backend_pin_claim`: §9 backend pin-claim vs body.md frontmatter (FAIL, conditional, all kinds, `--issue` mode only)

**Signature + wiring (the c23 pattern, verbatim):**
`check_backend_pin_claim(plan: str, *, frontmatter_backend: str | None) -> CheckResult`.
In `main()` `--issue` mode: `fm, _ = split_frontmatter((folder / "body.md").read_text())`
(folder already resolved for c23), pass `fm.get("backend")` (str-coerced,
stripped, or `None` when absent/empty). In `--plan-file` mode: append an
explicit `_skip` row `"no task context (--plan-file mode; frontmatter
reconciliation requires --issue)"` — mirroring c23's plan-file row.

**Trigger grammar (deliberately tight — FAIL polarity):** scan PROSE lines
(fence-masked via `_fence_mask`) INSIDE the §9 window (`_c57_section9_window`);
a hit is a line matching BOTH:
- `backend:\s*([a-z][a-z0-9_-]*)` (inline-code or bare), captured lane
  normalized lowercase and REQUIRED to be in the known-lane vocabulary
  `{runpod, gcp, fellows, nibi, fir, mila, auto}` (an unknown token is ignored
  — FP guard against e.g. "backend: the same as the parent"); and
- a same-line claim token: `\b(pin(?:ned)?|inherit(?:ed|s)?|frontmatter)\b`
  (case-insensitive).

**Verdicts:**
- No §9 window OR no claim lines → SKIP ("no §9 backend pin-claim in plan prose").
- Claim lane(s) found, `frontmatter_backend is None` → **FAIL**: name the
  claimed lane, quote the claim line (truncated), and the remedy — "add
  `backend: <lane>` to the task's body.md frontmatter BEFORE dispatch, or
  reword the §9 claim; a pin-claim with no frontmatter key routes `auto` at
  dispatch (#2225 v5/v9)".
- Claim lane == frontmatter lane (case-insensitive) for EVERY claim → PASS.
- Any claim lane != frontmatter lane → **FAIL** naming both.
- Escape literal anywhere in the plan: `N/A — backend pin-claim reconciled`
  → PASS ("standalone escape declared"), the house exemption shape.

**Residuals (disclosed, not covered):** a pin claim OUTSIDE the §9 window
escapes (window-scoping is the FP guard — narrative mentions of ANOTHER task's
pin, e.g. "#2225's `backend: runpod` pin", live outside §9); a claim phrased
without any of the three claim tokens escapes (grammar-tight by design);
on amendment-COMPOSED text (`_compose_amendment_text`), `_c57_section9_window`
resolves the FIRST §9 heading — the amendment's when both amendment and base
carry one — so a base-version §9 pin claim can escape; miss direction is
SKIP (fail-safe), disclosed rather than fixed.

**Named FP class for the calibration sweep to adjudicate:** a single §9 line
carrying both the matching pin AND a fallback lane in `backend:` form (e.g.
"`backend: runpod` pin; `backend: fellows` as manual fallback") FAILs under
"any claim lane != frontmatter lane" — the sweep adjudicates this as its own
FP class in the calibration comment; the pre-registered downgrade rule covers
it if systemic.

### c63 — `c63_declared_width_vs_launch`: §9 declared GPU width vs launch-fence width (WARN-only, conditional, all kinds, both modes)

**Signature + wiring:** standard `check_declared_width_vs_launch(plan, kind)`
appended to `CHECKS` (runs in both modes — no task context needed).

**Declared width:** within the §9 window, PROSE (fence-masked) tokens
`(\d+)\s*(?:[×*]|(?<!\w)x(?!\w))\s*(?:H100|H200|A100(?:-\d+)?|B200|L4)`
(the `_MULT_TOKEN` conventions) and `--gpu-count\s+(\d+)` on prose lines;
`N_decl` = max captured count; trigger requires `N_decl >= 2`.

**Realized width per launch fence:** `argvs, notes = _c50_launch_argvs(plan)`;
`parser, detail = _c46_argparser()` — `parser is None` → loud SKIP (the c46
convention: this is a drift detector, never a gate on the CLI module). For
each launch-shaped argv that dry-parses: realized = `ns.gpus` when set, else
`_C63_INTENT_GPU_COUNT.get(ns.intent)` — a NEW module-level static mirror of
`scripts/gpu_heuristics.py::INTENTS[*].gpu_count` (c26 convention; parity
test below). Unknown/absent intent → that argv contributes nothing (named in
the detail).

**Verdicts:**
- No §9 window / `N_decl < 2` / no parseable launch argvs → SKIP with the
  specific reason (c58's reason-naming style).
- EVERY parsed argv contributes nothing (unknown/absent intent, no `--gpus`)
  → SKIP, detail naming each argv and why it contributed no width (the
  critic-flagged enumeration gap — this case satisfies none of WARN/PASS and
  is explicitly the fail-safe branch).
- ≥1 parsed argv realizes `< N_decl` AND no parsed argv realizes `>= N_decl`
  → **WARN**: name `N_decl`, the offending fence (first ~70 chars), the
  realized width and its source ("`--gpus` absent ⇒ intent default
  `lora-7b` → 1×H100"), the consequence ("§9 walls are costed {N_decl}-wide;
  a `--time-budget-hours` fence sized to the wide wall TIMEOUTs the narrow
  run — #2225 v9"), and the remedy ("add `--gpus {N_decl}` to the fence, or
  re-cost the walls at the realized width, or declare the escape").
- Any parsed argv realizes `>= N_decl` → PASS.
- Escape literal: `N/A — declared width vs launch width reconciled` → PASS.

**Design decision (grounded in the incident):** a sibling
`pod.py provision --gpu-count N` fence does NOT suppress the WARN — the v9
incident text carried exactly that "(Equivalently `pod.py provision ...
--gpu-count 8` ...)" parenthetical, and the copied artifact was still the
narrow `dispatch_issue.py launch` fence. WARN-only polarity + the escape
literal absorb the deliberate-narrow case (e.g. a narrow smoke launch beside
a wide production provision).
