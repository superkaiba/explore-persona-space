# Plan — #977: port GCP's find-newer sentinel wait-loop hardening (#601) to the RunPod launcher

`kind: infra` workflow-fix. 0 GPU-hours, VM-local code + tests only. Not architectural (`architectural: false` — no status enum / marker schema / task.py subcommand / file relocation change).

## 1. Goal + acceptance criteria

A SELF-DAEMONIZING workload command on the RunPod BACKEND-OWNED execution leg (`execute_workload`, #909) currently produces a premature `phase=done` completion sentinel: the rendered launcher (`_render_launch_script`, `src/explore_persona_space/backends/runpod.py:362-467`) runs `workload_cmd`, captures `WORKLOAD_RC=$?` (line 454), and writes the sentinel immediately on rc==0 (lines 457-460). A workload that setsid-forks the real driver returns 0 at daemonize time, so the poller/finalize read terminal-success minutes into a multi-hour run — the exact incident GCP fixed in #601 (`gcp.py:1248-1269`). Port that hardening: after a successful `workload_cmd` return, wait for any FRESH live `/workspace/logs/*.pid` detached-workload pid to exit BEFORE writing the completion sentinel.

Acceptance criteria:

1. The rendered launcher waits on fresh detached pidfiles between the rc==0 gate and the sentinel write; a blocking workload (no fresh pidfile) is a no-op pass-through.
2. The launcher can NEVER deadlock on its own pidfile (`echo $$ > /workspace/logs/issue-<N>.pid` precedes the workload line) — self-exclusion is by PID VALUE, race-free at any mtime granularity.
3. A detached driver that OVERWRITES the canonical pidfile with its own PID (the experimenter `launch_issue_<N>.sh` convention writes the same `/workspace/logs/issue-<N>.pid` path) IS waited on — this is why exclusion is by pid value, not path (see §3 port subtleties).
4. New pytest pins in `tests/test_runpod_workload_exec.py` lock the ordering + exclusion; ALL existing tests in that file pass unchanged; `bash -n` (existing `test_rendered_scripts_bash_n`) passes on the new lines.
5. `ruff check` clean on touched files; `uv run python scripts/workflow_lint.py` (bundled `--check-asks`) passes.

## 3. Design

**Single file changed:** `src/explore_persona_space/backends/runpod.py`, function `_render_launch_script` (+ its docstring + one clause in the module docstring's sentinel-chain bullet, lines ~17-25). Plus tests (§ below). No signature change — `issue`, `pid_file`, `sentinel_path` are already parameters; both call sites (`_execute_workload_on_pod` ~line 559 and the retry path ~line 797/837) are untouched.

**Port subtleties, resolved:**

1. **Self-deadlock (the brief's item 3).** The launcher writes `echo $$ > {pid_file}` (line 452) BEFORE the workload line, and `pid_file` = `/workspace/logs/issue-<N>.pid` (`_runpod_pid_file_path`, lines 96-104) — squarely inside the scanned glob. A naive GCP port would wait on the launcher's own live PID forever.
2. **Why PID-value exclusion, not path exclusion (deviation from the brief's sketch).** The brief proposed ordering (start-mark after the self-pidfile write) so `-newer` "naturally" excludes it, plus optional `[ "$pf" = "{pid_file}" ] && continue`. Two problems found on inspection: (a) with an INCLUSIVE freshness predicate (required on MooseFS, see §11), ordering does NOT exclude the self-pidfile — same-second writes tie, so an explicit exclusion is LOAD-BEARING, not belt-and-suspenders; (b) the PATH exclusion is wrong for a real shape: when `workload_cmd` follows the experimenter `launch_issue_<N>.sh` convention, the detached driver writes its pid to the SAME canonical path, overwriting the launcher's entry — a path-excluded loop would skip the real detached driver and reintroduce the premature sentinel for exactly the convention-following case. `[ "$wpid" = "$$" ] && continue` handles both correctly: the launcher's own PID cannot be reused while it is alive (it IS alive, running the loop), and an overwritten canonical pidfile carries a different pid ⇒ waited on. Keep `[ "$wpid" = "$$" ]` as the ONLY self-exclusion.
3. **Wait placement: inside the rc==0 branch.** On GCP, `set -e` means a non-zero `workload_cmd` rc never reaches the wait (the EXIT trap fires). The RunPod launcher runs `set -uo pipefail` (no `-e`) and captures rc — so the semantic-parity placement is inside `if [ "$WORKLOAD_RC" -eq 0 ]`, before the sentinel write. Launcher still exits `$WORKLOAD_RC` (unchanged).
4. **Sentinel written after the wait regardless of the DETACHED process's exit status** — faithful GCP parity (`kill -0` polling cannot recover a non-child's exit code on either lane; the detached driver's own results sentinel / failure classification is the poller's outcome channel). Not a new gap; documented in the docstring.

**Exact new launcher lines** (inside the quoted `'EPSEOF'` heredoc — `$$`, `$pf`, `$wpid` deliberately unexpanded at render time, same mechanism the existing `echo $$ > {pid_file}` relies on). Replacing/extending the current lines 452-461 of `runpod.py`:

```python
f"echo $$ > {pid_file}",
"WORKLOAD_START_EPOCH=$(date +%s)",
workload_cmd,
"WORKLOAD_RC=$?",
"# Completion sentinel: written ONLY when the workload exited 0 (the",
"# backend-owned twin of the GCP/SLURM terminal sentinel write).",
'if [ "$WORKLOAD_RC" -eq 0 ]; then',
"  # Wait for detached workloads (#601 GCP parity, #977): a workload_cmd",
"  # that setsid-forks the real driver returns immediately — writing the",
"  # sentinel here would publish done at daemonize time. Contract: a",
"  # detached workload writes its pid to a fresh /workspace/logs/*.pid",
"  # (the launch_issue_<N>.sh convention). Freshness = stat mtime >=",
"  # workload-start epoch (inclusive, the verify-script predicate — a",
"  # strictly-newer find would miss a same-second pidfile at MooseFS",
"  # mtime granularity). Self-exclusion is by PID VALUE, never path:",
"  # a convention-following driver OVERWRITES the canonical pidfile,",
"  # so a path skip would miss it, while $$ cannot be reused while",
"  # this launcher is alive. Blocking workloads write no fresh pidfile",
"  # -> no-op. Bounded externally by the pod TTL + the poller's stall",
"  # escalation (the GCP analogue is --max-run-duration).",
"  for pf in /workspace/logs/*.pid; do",
'    [ -f "$pf" ] || continue',
'    [ "$(stat -c %Y "$pf" 2>/dev/null || echo 0)"'
' -ge "$WORKLOAD_START_EPOCH" ] || continue',
'    wpid=$(cat "$pf" 2>/dev/null) || continue',
'    [ -n "$wpid" ] || continue',
'    [ "$wpid" = "$$" ] && continue',
'    echo "[launcher] waiting on detached workload pid=$wpid ($pf)"',
'    while kill -0 "$wpid" 2>/dev/null; do sleep 30; done',
'    echo "[launcher] detached workload pid=$wpid exited"',
"  done",
f"  mkdir -p {sentinel_dir}",
f"  printf '%s\\n' '{sentinel_json}' > {sentinel_path}",
"fi",
'exit "$WORKLOAD_RC"',
```

Implementation notes for the implementer:

- The stat line uses Python adjacent-string concatenation (two source lines → ONE rendered line), the same trick gcp.py:1263-1264 uses, to stay under ruff's line-length 100. Tests assert on the full rendered line, so keep the concatenation producing one line.
- `WORKLOAD_START_EPOCH` is captured in-launcher IMMEDIATELY before `workload_cmd` — the semantic port of GCP's `touch` at gcp.py:1249. Do NOT reuse the outer script's `{epoch_file}` (`_launch_epoch_path`, written pre-detach at line 443): it predates the self-pidfile write and adds a file-read failure mode; the in-launcher capture needs no file.
- No `[phase=` literal and no `task.py` mention in the new lines (`test_remote_scripts_never_shell_task_py` pins this); the `[launcher]` echo prefix is safe.
- Unmatched glob under `set -u` (fresh pod, no `.pid` files… impossible here since the launcher wrote its own, but defensively): the literal `/workspace/logs/*.pid` fails `[ -f ]` → continue — the `_render_verify_script` precedent (lines 493-494).
- Single-variable discipline: no other launcher refactor. The outer script, verify script, ALREADY-RUNNING guard, stale-sentinel clear, and rc-propagation are byte-unchanged.

## 11. Decision Rationale

`N/A — no training hyperparameters.` Design constants, each with Source:

- **`sleep 30` poll interval** — Source: gcp.py:1267 (`while kill -0 "$wpid" 2>/dev/null; do sleep 30; done`), copied verbatim for parity.
- **Freshness predicate `stat -c %Y "$pf" -ge $WORKLOAD_START_EPOCH` (inclusive) instead of GCP's `find -newer` (strict)** — Source: runpod.py:493-495 (`_render_verify_script`'s existing fresh-pidfile idiom on this exact lane) + gcp.py:1263-1264 as the semantic reference. Rejection rationale for the literal port: `find -newer` is STRICTLY newer; on a 1 s-granularity mtime filesystem a detached driver writing its pidfile in the same second as the start-mark would be missed → the premature-sentinel bug recurs as a narrow race. GCP tolerates this on ext4 (ns mtimes); RunPod `/workspace` is MooseFS. Inclusive `-ge` + pid-value self-exclusion is race-free at any granularity.
- **Self-exclusion by PID value (`$wpid` = `$$`), NOT by pidfile path** — Source: this plan §3.2 (new analysis; no prior-issue precedent — GCP never writes its own pidfile so the question does not arise there). Path exclusion would skip a convention-following driver that overwrites the canonical pidfile; `$$` cannot be reused while the launcher is alive.
- **Scan scope `/workspace/logs/*.pid` top-level glob (≡ `find -maxdepth 1 -name '*.pid'`)** — Source: gcp.py:1263 + runpod.py:493 (verify-script glob).
- **Epoch captured in-launcher immediately before `workload_cmd`** — Source: gcp.py:1249 (touch immediately before the workload); a shell variable rather than a `/tmp` marker file removes the file-read failure mode and one artifact.
- **Wait placed inside the rc==0 branch** — Source: GCP semantic parity — under gcp.py's `set -e` a failing workload never reaches the wait (docstring lines 1114-1126); the RunPod launcher has no `-e`, so the branch placement reproduces the same reachability.
- **No explicit wait timeout (unbounded-with-external-bounds)** — Source: gcp.py:1260-1261 ("Bounded by the instance's --max-run-duration"); the RunPod bounds are the pod TTL + poller stall escalation + watcher pod-safety pass (Assumption 7). Faithful parity preferred: an in-script timeout would re-create the premature-done failure mode this fix removes.
