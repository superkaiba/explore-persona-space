# Plan v1 — #832: code-reviewer diff-size budget on long-lived branches

## 0.0 TL;DR

- **What I'll change:** Two instruction files for the agents that review and write code. Before an agent opens the full set of changes on an old, long-running branch, it will first check how big that set is; if it is too big to fit in the agent's working memory, it reads only the current round's changes instead.
- **What I expect:** No more reviewer or implementer deaths from loading multi-megabyte diffs (the #722 failure), with zero loss of review coverage — earlier rounds were already reviewed when they landed.
- **What would change my mind:** If any existing review step turns out to genuinely need the whole-branch diff body (verified below: none does).

### (a) code-reviewer.md — Step 0 size gate

Anchor: insert immediately AFTER the Step 0 classification paragraph + its #613 sparse-worktree fallback, i.e. after the paragraph beginning:

> "Before reading the plan, run `git diff --name-only main...HEAD` (or against the relevant base) and classify the diff."

and BEFORE the leaf/trunk tier table. Proposed prose, verbatim:

```
**Size the diff BEFORE reading its body (long-lived-branch guard).** After
classification, and before ANY diff BODY read, run:

    git diff main...HEAD | wc -c

The pipe streams into `wc` — sizing is free of context cost. If the byte
count exceeds **300 KB**, do NOT read the whole-branch diff body. Scope
every body read to the CURRENT round instead: `git show <sha>` for each
commit named in the implementer's round marker/report, or the round range
`<parent>..HEAD` from the implementer report — the same per-round recipe
Step 0.9's `cumulative-main-head-diff` subclass prescribes. Earlier rounds'
changes on a long-lived same-issue-follow-up branch were already reviewed
in their own rounds; re-reading them is what killed two subagent spawns on
#722 (three-dot body 1.96 MB, two-dot 31.6 MB, vs a 36 KB round delta).
Name-only / `--name-status` / `--stat` / `--diff-filter` forms are cheap
and stay unrestricted at any size. NEVER read the two-dot `main..HEAD`
BODY on a worktree branch — it folds in unrelated main churn (31.6 MB on
#722); the two-dot form is permitted only in NAME-ONLY form, as in the
sparse-worktree fallback above. This gate changes the SCOPE of the diff
body you read, never whether you read one — Step 0.7's "pre-diff gates
never short-circuit the diff" invariant is untouched.
```

## 4. Decision Rationale (§11) — grounding the 300 KB budget

- **What:** diff-body byte budget = 300 KB; sizing command = `git diff main...HEAD | wc -c`.
- **Why:** Claude context ≈ 200K tokens ≈ ~800 KB of text at ~4 bytes/token. The reviewer's context also carries the plan, markers, source-file reads, and its own reasoning — a diff body must leave the majority of the window free, so budget ≈ 3/8 of the raw ceiling. Empirically: #722's healthy round delta was 36 KB + 29 KB (two orders of magnitude under budget — no false positives on normal rounds), while the pathological bodies were 1.96 MB and 31.6 MB (2.5× and 40× the raw ceiling — guaranteed autocompact). 300 KB cleanly separates the regimes with wide margin on both sides; the exact value is not sensitive within ~2×.
- **Sizing is free:** the diff streams through a pipe into `wc -c`; nothing enters agent context but the single byte-count number.
- **Source:** incident #722 r2 (task-body verbatim numbers) + context arithmetic. No literature search applicable.
- **Alternatives:** per-file caps (rejected: the failure mode is the aggregate); token-count via tokenizer (rejected: needless dependency, bytes/4 is accurate enough); making the gate a hard FAIL (rejected: violates the #613 never-block precedent — the gate falls back, never blocks).
