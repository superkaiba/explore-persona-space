## 0. Plan Summary

**The bug.** `poll_pipeline.poll_once` computes log staleness by subtracting
two DIFFERENT clocks: the pod stamps file mtimes with `stat -c %Y` (pod's
wall clock), while the VM computes "now" with `datetime.now(tz=UTC)` (VM's
wall clock). Both are UTC Unix-epoch seconds (verified: `stat -c %Y` and
`date +%s` are timezone-invariant on GNU coreutils), so this is NOT a
timezone bug — it is a **wall-clock DRIFT** bug. A RunPod pod whose NTP is
unsynced drifts arbitrarily from the VM clock; subtracting `VM_now −
pod_mtime` then reports a staleness off by the full drift. On session
09e41486 the drift produced a 14-33h `last_log_mtime_sec_ago` on a log
whose mtime was ~30s old. Today the #518 CPU-advancing override masks the
false-stall verdict, but if that override were ever removed (or didn't
apply) the >900s stall path would falsely fire.

**The fix (single-clock comparison).** Capture the pod's "now"
(`date +%s`) in the SAME SSH heredoc that reads the file mtimes, return it
as a new `POD_NOW_EPOCH=` probe line, and compute the four log-staleness
deltas as `pod_now − pod_mtime` — both operands from the SAME (drifted)
pod clock, so the drift cancels exactly. The VM clock (`now_epoch`, line
2036) stays in place for everything that compares against VM-stamped
timestamps (the `epm:run-launched` marker age, the GPU-idle advisory span,
the `last_phase_change` sidecar) — those must NOT move to the pod clock.

**Scope.** `scripts/poll_pipeline.py` (heredoc emit + parser key + the
three log-mtime subtractions) and `tests/` (new regression file). No edit
to `backend_poll.py` (it only passes the value through). Public field
shape preserved.

**Degrade.** Missing / `0` `pod_now_epoch` (legacy pod image, or a probe
that failed to emit the line) falls back to the OLD VM-clock formula AND
logs a one-line WARN, so older images keep working and existing tests
(which don't emit the key) pass unchanged.

**Risks (top 2).** (1) Forgetting one of the four mtime sources (top-level,
cell, per-phase, shard) leaves three still-skewed; the design fixes all four
through ONE shared pod-now basis. (2) The fallback silently re-introduces
the bug on a pod that fails to emit the line — mitigated by the WARN + a
dedicated regression test that asserts the fallback path is taken and
logged.

## 1. Goal

Make the log-staleness signal (`last_log_mtime_sec_ago` and its three
sibling `*_log_mtime_sec_ago` values) correct regardless of pod-vs-VM
wall-clock drift, so the >900s stall path is reliable without depending on
the #518 CPU-advancing override to mask a false reading.

- **#689 / #692** — RunPod no-port wedge clock (`runpod_noport_first_seen_ts`),
  also a VM-only sidecar clock; separate concern.

**Prior bug-fix commits that came close but did not fix this skew.** Every
staleness fix above (#405/#468/#488) extended the set of mtime SOURCES folded
into the freshness signal, but all of them kept the same `now_epoch −
mtime_epoch` cross-clock subtraction (line 2037-2039). None addressed the
pod-vs-VM clock basis — they made the signal cover more logs, not compare on
one clock. The CPU-advancing override (#518/#658) is the only thing that has
ever masked the resulting false reading, and only for the subset of cases
where session CPU happens to be advancing.

**Linux fact verified (not from memory).** `stat -c %Y <file>` and
`date +%s` both return integer seconds since the Unix epoch
(1970-01-01 00:00:00 UTC), timezone-invariant, on GNU coreutils 8.32 (the
pod base image `runpod/pytorch:...-ubuntu22.04` ships GNU coreutils). Ran
`TZ=Asia/Tokyo stat -c %Y` vs `TZ=America/New_York stat -c %Y` on the same
file: identical. So the only cross-clock difference between pod mtime and VM
now is **wall-clock drift**, and reading both operands from the pod clock
cancels it exactly. `Source:` one-liner verification run on the dev VM
(GNU coreutils 8.32 `stat`/`date --version`); GNU coreutils stat(1)/date(1)
man pages.

## 3. Hypothesis / acceptance criteria

**Bug-cause hypothesis.** The 14-33h `last_log_mtime_sec_ago` reading on
session 09e41486 (whose log mtime was ~30s old) is caused by pod-vs-VM
wall-clock drift: the subtraction `now_epoch (VM) − freshest_mtime_epoch
(pod)` at `poll_pipeline.py:2037` crosses two unsynced clocks, so the
reported staleness equals the true staleness plus the (arbitrary, possibly
multi-hour) clock offset.

**Falsifiable prediction.** If the hypothesis is correct, computing
`pod_now_epoch − freshest_mtime_epoch` (both from the pod's `date +%s` /
`stat -c %Y`) yields the TRUE staleness (~30s) regardless of the offset
between the pod clock and the VM clock.

**Acceptance criteria (the regression test).** A unit test that drives
`poll_once` with a mocked SSH probe whose pod mtime is fresh
(`mtime_epoch = pod_now − 30`) but whose pod clock is hours behind the VM
clock (`pod_now_epoch = VM_now − 14*3600`) asserts the computed
`last_log_mtime_sec_ago` is `~30` (pod_now − pod_mtime), NOT `~14*3600`
(VM_now − pod_mtime). Plus a backward-compat test (legacy probe missing the
key → VM-clock fallback, no crash) and a heredoc-content test (the new
`POD_NOW_EPOCH=` line is emitted). All three pass; `uv run pytest` green;
ruff clean on touched files.

**Measurement validity:** `N/A — no behavioral construct` — this task
measures no model behavior; the "metric" is an integer-seconds staleness
delta computed from file mtimes, verified directly by unit test.

## 4. Design

All edits are in `scripts/poll_pipeline.py` + a new test file. Four concrete
changes, in dependency order.

### 4.1 Emit the pod's "now" in the probe heredoc (one shared capture)

The four mtime sources (top-level log `MTIME_EPOCH`, cell `CELL_MTIME_EPOCH`,
per-phase `PHASE_LOG_MTIME_EPOCH`, shard `SHARD_LOG_MTIME_EPOCH`) are all
read by `stat -c %Y` inside the SINGLE SSH session built at
`poll_pipeline.py:1049-1066` (`heredoc = (...)`). The four `stat` calls and a
`date +%s` all execute within milliseconds of each other on the same pod,
reading the same pod clock — so **one** `POD_NOW_EPOCH` capture covers all
four sources (confirmed by the brief; no per-source capture needed).

Add ONE line to the `heredoc` string, immediately after the top-level-log
block (after line 1059, before `{cell_probe}`), so it is emitted on EVERY
probe regardless of which logs exist:

```python
# In the `heredoc = (...)` assignment at ~line 1049-1066, insert after the
# top-level MTIME_EPOCH block (line 1059) and before f"{cell_probe}":
    f"echo POD_NOW_EPOCH=$(date +%s); "
```

`date +%s` cannot fail in a way that emits a malformed value on a working
shell; if the pod is so broken `date` is missing, the whole `ssh` returns
rc!=0 and the existing `ssh_failed` fallback dict (line 1081-1096) already
handles it (no `pod_now_epoch` key there → fallback path → existing
`10**9`/`0` zeroed-staleness behavior, unchanged). Per the fail-fast rule,
no new try/except is added; a non-zero `date` exit would surface in the
heredoc rc.

### 4.2 Register + parse the new probe key

The parser (`_parse_probe_stdout`, line 1119) dispatches on the
`_PROBE_SCALAR_KEYS` tuple (line 1104-1116) — a new key is NOT auto-handled;
it must be registered. Two edits:

```python
# 1) Add to _PROBE_SCALAR_KEYS (line 1104-1116), e.g. after "MTIME_EPOCH":
    "POD_NOW_EPOCH",

# 2) Add to the parsed-dict default (line 1126-1140) so a probe that omits
#    it (legacy image, ssh_failed fallback) yields "0" not a KeyError:
    "pod_now_epoch": "0",
```

Also add `"pod_now_epoch": "0"` to the `ssh_failed` fallback dict returned at
`poll_pipeline.py:1081-1096`, for symmetry with the other mtime keys (it
already returns `"mtime_epoch": "0"` etc.). On an ssh failure the existing
zeroed-staleness path runs regardless, but keeping the key present avoids any
`.get`-vs-`[]` inconsistency.

The parser dispatch loop (line 1165-1168) handles the new key automatically
once it is in `_PROBE_SCALAR_KEYS` — it uses `line.startswith(f"{key}=")` and
stores `line.split("=", 1)[1].strip()` under `key.lower()`. The value parses
through the same `text=True, encoding="utf-8", errors="replace"` decode path
as every other key (line 1067-1074), so the recent subprocess-decode
hardening (#653) covers it — no new decode site is introduced.

### 4.3 Compute log staleness on the pod clock (the core fix)

At `poll_pipeline.py:2023-2039`, the current code:

```python
mtime_epoch = int(probe["mtime_epoch"] or "0")
cell_mtime_epoch = int(probe["cell_mtime_epoch"] or "0")
phase_log_mtime_epoch = int(probe["phase_log_mtime_epoch"] or "0")
shard_log_mtime_epoch = int(probe.get("shard_log_mtime_epoch") or "0")
freshest_mtime_epoch = max(mtime_epoch, cell_mtime_epoch)
now_epoch = int(datetime.now(tz=UTC).timestamp())
last_mtime_ago = now_epoch - freshest_mtime_epoch if freshest_mtime_epoch > 0 else 10**9
phase_log_mtime_ago = now_epoch - phase_log_mtime_epoch if phase_log_mtime_epoch > 0 else 10**9
shard_log_mtime_ago = now_epoch - shard_log_mtime_epoch if shard_log_mtime_epoch > 0 else 10**9
```

becomes (the `now_epoch` VM line STAYS — see 4.4 — but a separate pod-clock
basis drives the three log-staleness deltas):

```python
mtime_epoch = int(probe["mtime_epoch"] or "0")
cell_mtime_epoch = int(probe["cell_mtime_epoch"] or "0")
phase_log_mtime_epoch = int(probe["phase_log_mtime_epoch"] or "0")
shard_log_mtime_epoch = int(probe.get("shard_log_mtime_epoch") or "0")
freshest_mtime_epoch = max(mtime_epoch, cell_mtime_epoch)
now_epoch = int(datetime.now(tz=UTC).timestamp())  # VM clock — unchanged; used below for run-age / advisory / phase-change sidecar

# Single-clock staleness basis (#704): the pod stamps file mtimes with its
# own wall clock (stat -c %Y) and we now capture that SAME clock's "now"
# (date +%s) in the probe heredoc, so subtracting pod_now - pod_mtime
# cancels any pod-vs-VM clock drift. Fall back to the VM clock when the
# pod_now line is absent (legacy pod image / ssh failure) so older images
# and existing tests keep working — with a one-line WARN so the regression
# is visible.
pod_now_epoch = int(probe.get("pod_now_epoch") or "0")
if pod_now_epoch > 0:
    staleness_now = pod_now_epoch
else:
    staleness_now = now_epoch
    log.warning(
        "probe missing POD_NOW_EPOCH on pod %s; falling back to VM-clock "
        "log staleness (subject to pod-vs-VM clock drift, #704)",
        pod,
    )
last_mtime_ago = staleness_now - freshest_mtime_epoch if freshest_mtime_epoch > 0 else 10**9
phase_log_mtime_ago = staleness_now - phase_log_mtime_epoch if phase_log_mtime_epoch > 0 else 10**9
shard_log_mtime_ago = staleness_now - shard_log_mtime_epoch if shard_log_mtime_epoch > 0 else 10**9
```

This satisfies hard rule #5: **all four mtime sources** (top-level + cell via
`freshest_mtime_epoch`, per-phase, shard) use the SAME `staleness_now` basis.
The `min(..., 10**9)` clamps at the `PollResult` construction site (lines
2338, 2344, and the shard line just below) are untouched, preserving the
integer-seconds + `10**9`-sentinel public semantics.

**Negative-delta guard.** If the pod clock ran slightly AHEAD of the file
mtime within the same probe (it cannot, physically, since the mtime was
stamped before `date +%s` ran in the same session) or a sub-second rounding
makes `staleness_now < mtime`, the subtraction could be a small negative.
The downstream stall conjunction (`last_mtime_ago > stall_sec`) treats a
negative as "very fresh" (correct), and `min(neg, 10**9)` = the negative.
A negative `last_log_mtime_sec_ago` is harmless to every consumer (it only
ever feeds `> stall_sec` comparisons and JSON observability), but to keep
the field's "seconds ago" semantics clean I will clamp the three deltas at
0 on the low end via `max(0, ...)` ONLY in the `pod_now` branch (the VM
fallback keeps its existing behavior so the backward-compat tests that
assert exact values stay exact). Decision recorded in §11.

### 4.4 The VM `now_epoch` stays for the non-staleness consumers (DO NOT MOVE)

Hard requirement surfaced by reading lines 2210-2290: `now_epoch` (the VM
clock, line 2036) is reused AFTER the staleness block for three things that
MUST stay on the VM clock because they compare against VM-stamped values:

- `_maybe_post_gpu_idle_advisory(..., now_epoch=now_epoch)` (line 2222) —
  spans against the VM-side `gpu_idle_since_epoch` sidecar.
- `_run_launched_age_sec(issue, now_epoch)` (line 2259) — age against the
  VM-stamped `epm:run-launched` marker timestamp.
- the `last_phase_change_epoch` sidecar comparison + stamp (lines 2272,
  2276, 2278) — VM-stamped each tick.

The fix introduces `staleness_now` as a SEPARATE local used ONLY for the
three log-mtime subtractions. `now_epoch` is left exactly as-is for the
above. This is why the canonical fix here is "add a pod-clock basis for
staleness," NOT "redefine `now_epoch` to the pod clock" — the latter would
silently corrupt run-age and phase-change tracking.

## 11. Decision Rationale

`N/A — no model training` for hyperparameter grounding — this task trains no
model and has no learning-rate / batch / epoch / LoRA hyperparameters.

Design-decision rationale (the load-bearing factual + design choices):

- **What:** Single-clock comparison via a pod-side `date +%s` captured in the
  same heredoc. **Why:** the skew exists ONLY because two unsynced clocks are
  subtracted; reading both operands from the pod clock cancels the drift
  exactly (the canonical fix per hard rule #1). **Source:** clarifier output
  on #704 (canonical fix shape) + the verified Linux fact below.
- **What:** `stat -c %Y` and `date +%s` are the same UTC Unix-epoch basis,
  timezone-invariant. **Why:** confirms the bug is wall-clock DRIFT, not a TZ
  offset, so a single pod-clock `now` (not a TZ conversion) is the correct
  fix. **Source:** ran `TZ=Asia/Tokyo stat -c %Y` vs `TZ=America/New_York
  stat -c %Y` on the dev VM (identical output) + GNU coreutils 8.32
  stat(1)/date(1) man pages.
- **What:** ONE shared `POD_NOW_EPOCH` capture for all four mtime sources
  (not per-source). **Why:** the four `stat -c %Y` calls + the `date +%s`
  execute in the same SSH session within milliseconds; per-source capture
  would add no precision. **Source:** read the heredoc construction
  (`poll_pipeline.py:1049-1066`) — all four sources are emitted in one
  `subprocess.run(["ssh", ...])` call.
- **What:** Keep `now_epoch` (VM clock, line 2036) for run-age / GPU-idle
  advisory / phase-change sidecar; add a SEPARATE `staleness_now` for the
  log-mtime subtractions. **Why:** those three consumers (lines 2222, 2259,
  2272/2276/2278) compare against VM-STAMPED timestamps (the `epm:run-launched`
  marker, the `gpu_idle_since_epoch` and `last_phase_change_epoch` sidecars);
  moving them to the pod clock would corrupt run-age and phase-change tracking.
  **Source:** read `poll_pipeline.py:2210-2322` — confirmed `now_epoch` reuse
  at those sites.
- **What:** Fallback to the VM-clock formula + WARN on missing/`0`
  `pod_now_epoch`. **Why:** preserves correctness for legacy pod images
  whose probe pre-dates this change AND keeps the existing tests (which omit
  the key) green, while making any silent regression visible in logs (vs a
  crash that would be brittle, or a silent zero that would hide the gap).
  **Source:** brief §4 recommendation + reading
  `tests/test_poll_pipeline_zombie_gpu.py` (its `_probe_stdout` omits the
  key → fallback path).
- **What:** `max(0, ...)` low-clamp on the `pod_now` branch only. **Why:**
  keeps the field's "seconds ago" semantics non-negative; the VM-fallback
  branch is left unclamped so the backward-compat tests' exact expected
  values stay exact. **Source:** preserves the integer-seconds public
  semantics (hard rule #2) without changing the legacy path.
