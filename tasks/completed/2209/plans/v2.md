# Plan v2 — #2209: thread-caps VM-entrypoint test blind to uncommitted scripts

**v2 delta (critic round 1, APPROVE with premise correction):** the STAGED half of the task body's Bug statement is empirically false — `git ls-files` reads the INDEX, so a staged-but-uncommitted script is already enumerated by today's `_scan_targets` and already fails the test in every checkout shape. Only UNTRACKED files are the real blind spot (which is exactly what #2203 was: the script was untracked). v2 drops the redundant `git diff --cached` enumeration leg and reframes the staged-coverage test as a regression PIN of the existing index-inclusion behavior.

**Kind:** infra (workflow-fix; test-only change). **Provenance:** surfaced by #2203 code-review r2/r3 — `scripts/issue2203_capability.py` (new, torch-before-`load_dotenv`) was untracked when `tests/test_shared_vm_thread_caps.py::test_no_new_torch_before_dotenv_vm_entrypoints` ran locally in round 2 → FALSE GREEN → the #847 regression shipped to HEAD and was only caught post-commit.

## Design (with the one deliberate scoping decision)

**Root cause:** `_scan_targets` (tests/test_shared_vm_thread_caps.py:822) enumerates via `git ls-files` (TRACKED only). The tracked-only filter is DELIBERATE per its own docstring: an untracked violator at the SHARED repo root (~15 concurrent sessions) would (a) wedge every session's repo-root suite run on someone else's transient file, and (b) poison the Step 9c known-red baseline ledger — `scripts/step9c_baseline.py refresh` runs the workflow-invariant universe at the shared MAIN root, so a foreign transient untracked violator present during a refresh would land the node in the ledger as known-red, which would then STRIP a genuine branch-introduced violation at a later compare. #1889 already covers the inline-payload-lint-gate path via `EPM_SCAN_EXTRA_FILES`; the remaining hole is a LOCAL pytest run on a working tree before committing — which happens in issue WORKTREES (the #2203 mechanism).

**Fix:** union UNTRACKED working-tree files into the scan set ONLY when the invoking checkout is a LINKED WORKTREE — detected by `(root / ".git").is_file()` (a linked worktree's `.git` is a pointer FILE; a main checkout's is a directory). In a linked worktree, untracked files are the session's own by construction (each issue has its own worktree), so the union is safe there; the shared MAIN checkout (and pod/GCE clones, and tmp `git init` fixture repos) keeps today's index-scan behavior byte-identical — no fleet wedge, no ledger poisoning, no refresh/TG-baseline coupling. (STAGED files need no new leg: `git ls-files` reads the index, so they are already enumerated everywhere — pinned by a new regression test.)

Mechanics in `_scan_targets`:
- New helper `_worktree_local_extras(root: Path) -> list[Path]`:
  - Return `[]` unless `(root / ".git").is_file()`.
  - Enumerate untracked via `git ls-files --others --exclude-standard` (`cwd=root`, `check=True`; no porcelain parsing, no rename-field ambiguity).
  - Filter each rel path by the SAME class rules as the #1889 extras block: `scripts/**/*.py`, or `src/explore_persona_space/experiments/**/*.py` with a module-top `__main__` guard. Factor the existing #1889 in-class predicate into a shared helper `_in_scan_class(root, rel_posix) -> bool` so the two paths cannot drift (behavior-preserving refactor of the #1889 block).
  - Skip entries whose file does not exist (racing delete) and entries that fail `ast.parse` (a mid-edit syntax-broken scratch file must not convert the invariant test into a syntax linter; an unparseable file also cannot import torch at runtime, so no live #847 regression can ship from it — stated residual). Index-scan semantics unchanged (tracked/staged files keep fail-loud parse).
- Union into `targets` with dedup (same `seen` mechanism as #1889), AFTER the env-extras block.
- Docstring updates: `_scan_targets` (document the worktree-local union + why main checkouts stay tracked-only) and the main test docstring (name #2209).

**Grandfather interplay:** unchanged — untracked files can never be grandfathered (currency tests already reject untracked entries), so a worktree-local violator always FAILS. Currency tests call `_scan_targets` at the repo root (main checkout) → byte-identical behavior.

**Deviation from the task body's blanket phrasing (stated per the acceptance-criteria intent):** the body's candidate fix suggests unconditionally scanning staged+untracked. That reopens the two documented shared-root failure modes above (fleet-wide false-red + ledger poisoning) — the exact reasons tracked-only was chosen. Scoping the union to linked worktrees closes the OBSERVED hole (#2203 ran the test in its issue worktree) while keeping the shared root safe. Named residuals: (i) a hand edit at the shared root outside any gate stays blind (covered for gate-routed payloads by #1889's `EPM_SCAN_EXTRA_FILES`); (ii) a git-less rsync tree (SLURM scratch) has no `.git` → no extras → unchanged behavior.
