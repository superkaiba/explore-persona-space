# Plan — #1239: migrate bootstrap_pod.sh tokenized-remote-at-rest to the #1205 env-reading git credential helper (pod flavor)

### 0.0 TL;DR (plain English)

- **What I'll change:** I'll rewrite the pod bootstrap so the GitHub token never sits inside the pod's git configuration or remote URL. The pod will clone the repo anonymously (it's a public repo), and when a push needs authentication, a tiny helper hands git the token by reading it from the pod's `.env` file at that moment — the same fix the GCE lane already got in #1205, adapted so it also works in later SSH shells that don't carry the token in their environment.
- **What I expect:** Fresh pods bootstrap exactly as before, existing pods get their tokenized remote scrubbed on the next re-bootstrap, pulls and eval-result pushes keep working, and the token stops being leakable via logs, `git remote -v`, or process listings.
- **What would change my mind:** If any pod-side consumer turns out to actually parse the token out of the remote URL (my greps found none), or if anonymous fetch of the public repo fails in practice (the GCE lane has been doing tokenless clones in production since #1205, so this is very unlikely), I'd revisit the design.

### 0. Plan Summary (technical)

**Change:** `scripts/bootstrap_pod.sh` — (1) define one `GIT_CRED_HELPER` shell variable (env-reading, `.env`-fallback, github.com-host-scoped, POSIX-sh) + a `REPO_URL_TOKENLESS` constant near the top; (2) step 4 fresh-init: tokenless `git remote add`, drop the `.env` sourcing / `GITHUB_TOKEN` hard-require / `unset HISTFILE`, configure the repo-local scoped helper; (3) step 4 existing-repo: unconditional `git remote set-url origin <tokenless>` + helper config **before** the pull (retrofits legacy pods whose `/workspace` `.git/config` persists a tokenized URL); (4) step 7: remove `git config --global credential.helper store`, scrub `/root/.git-credentials`, set the same helper globally (host-scoped); (5) step 6 rc-export block: add `export GIT_TERMINAL_PROMPT=0` (#1205 parity). ## 1. Goal

> Migrate the pod-side tokenized-remote-at-rest pattern to the same env-reading git credential helper #1205 gave the GCE lane, for log-leak parity (token out of .git/config + remote URLs).

(Task #1239 Goal, verbatim.)

Today `scripts/bootstrap_pod.sh` step 4 writes `https://x-access-token:${GITHUB_TOKEN}@github.com/...` into the pod's `.git/config` (lines 254–255) and deliberately retains it so future pulls re-auth. That token-at-rest is leakable via `git remote -v` in any log, `ps` during git subprocesses, error messages that echo the remote URL, and the persisted `/workspace` volume across stop/resume. The GCE lane fixed the identical pattern in #1205 (tokenless public clone + env-reading credential helper); this plan ports that pattern to the pod lane with one deliberate pod-specific delta: the helper falls back to sourcing the durable pod `.env` at invocation time, because later interactive/SSH shells on a pod (unlike the GCE workload env) do not inherit `GITHUB_TOKEN`.

**Standard git practice:** `gitcredentials(7)` documents the `!`-prefix helper ("the rest is interpreted as a shell snippet, run with the credential operation appended as an argument" — hence the `!f() { ...; }; f` idiom), URL-scoped helpers via the `credential.<url>.helper` config key (matching by host), and warns that `git-credential-store` "stores your passwords unencrypted on disk" (`~/.git-credentials`) — which is exactly step 7's current adjacent at-rest surface. URL-embedded credentials in a remote bypass helpers entirely, which is why today's `credential.helper store` is a vestigial no-op for the origin remote.

**Bootstrap history relevant here:** step 4's fresh-init already uses `git init` + `fetch --depth=1` + `reset --hard FETCH_HEAD` (slow-network fix, #501); the token-in-URL was kept "so future re-bootstraps (the pull branch on `pod.py resume`) can re-auth without extra setup" (lines 196–199) — an assumption this plan removes: pulls are anonymous on a public repo, and pushes get the helper.

### 4.1 New constants near the top (insert after line 37, `REMOTE_DIR=...`)

```bash
# Tokenless public HTTPS remote (#1239, mirrors gcp.py DEFAULT_REPO_URL —
# the repo is public, so CLONE/FETCH needs no auth; PUSH auth comes from
# the credential helper below).
REPO_URL_TOKENLESS="https://github.com/superkaiba/explore-persona-space.git"

# Env-reading git credential helper (#1205 GCE-parity, pod flavor). This
# STRING is what gets stored in git config — never the token. Git runs it
# via `sh -c` with the credential operation appended ("get"/"store"/
# "erase" — f ignores it, same as the GCE helper). It reads GITHUB_TOKEN
# from the invoking environment first, then falls back to sourcing the
# durable pod .env in a subshell (a later interactive/SSH shell on the
# pod does NOT inherit the bootstrap env — the KEY delta vs GCE). It is
# configured host-scoped (credential.https://github.com.helper) so the
# token is never offered to any non-GitHub remote. POSIX-sh only (git
# invokes /bin/sh, dash on this image). Escaping note: this is a LOCAL
# double-quoted assignment — \" and \$ survive as literal " and $ in the
# stored value; $REMOTE_DIR is expanded (baked in) locally.
GIT_CRED_HELPER="!f() { tok=\"\${GITHUB_TOKEN:-}\"; if [ -z \"\$tok\" ] && [ -r $REMOTE_DIR/.env ]; then tok=\"\$(. $REMOTE_DIR/.env >/dev/null 2>&1; printf %s \"\${GITHUB_TOKEN:-}\")\"; fi; echo username=x-access-token; echo \"password=\${tok}\"; }; f"
```

**Quoting/escaping analysis (three shell layers):**

1. **Local bash (compose time):** the assignment is double-quoted, so `\"` → `"`, `\$` → `$`, and `$REMOTE_DIR` expands to `/workspace/explore-persona-space`. The variable then holds, verbatim:
   ```
   !f() { tok="${GITHUB_TOKEN:-}"; if [ -z "$tok" ] && [ -r /workspace/explore-persona-space/.env ]; then tok="$(. /workspace/explore-persona-space/.env >/dev/null 2>&1; printf %s "${GITHUB_TOKEN:-}")"; fi; echo username=x-access-token; echo "password=${tok}"; }; f
   ```
2. **Remote shell (ssh):** every use site interpolates the variable inside a *remote-level single-quoted* argument — `git config <key> '$GIT_CRED_HELPER'` inside a local double-quoted `ssh_cmd "..."` block. Local bash expands `$GIT_CRED_HELPER` (single quotes are literal characters in a double-quoted context; expansion results are not re-parsed for quotes); the remote shell receives `git config <key> '<helper text>'` and, because the helper text contains **no single quotes by construction** (double quotes only — this invariant is what makes the whole scheme safe and is pinned by a test), parses it as one argument stored verbatim in git config.
3. **Helper invocation (git → `/bin/sh -c`):** POSIX-only constructs (`f() {}`, `[`, `${VAR:-}`, `$( )`, `.`, `printf`) — dash-safe. The `.env` source runs inside the `$( )` subshell, guarded by `[ -r ... ]`, so a missing/unreadable `.env` yields an empty `tok` (→ anonymous fetch still fine; push fails loud with an auth error) rather than aborting oddly; sourcing side effects cannot escape the subshell. Env-first precedence (`${GITHUB_TOKEN:-}` before the `.env` fallback) makes the helper behave byte-for-byte like the GCE one whenever the env carries the token. Sourcing (rather than `sed`-extracting) the `.env` parses it with the exact semantics the old step 4 already used (`set -a; . $REMOTE_DIR/.env`), so quoted values like `GITHUB_TOKEN="ghp_x"` keep working.

### 4.3 Step 3 (lines 170–191): KEEP the GITHUB_TOKEN hard gate; reword

**Decision: keep the gate.** The clone no longer needs the token, but essentially every pod workload pushes eval-result commits, and `pod.py sync`/experimenter flows assume push auth is available. Failing at bootstrap (seconds in, before any GPU work) strictly dominates a deterministic push failure hours into a run — exactly the #825 r6–r8 failure shape #1205 fixed on GCE. GCE made the token optional because its workloads are heterogeneous and metadata-delivered; the pod `.env` is copied from the VM `.env`, which always has `GITHUB_TOKEN`, so the gate costs nothing. Edits: line 170 header comment → `# ── Step 3: Push .env (pod needs GITHUB_TOKEN for git push auth) ──`; line 184 message → `".env on pod is missing GITHUB_TOKEN — needed for git push auth (the credential helper reads it from this file)"`.

### 4.4 Step 7 (lines 450–479): remove `credential.helper store`, scrub, set global helper

**Decision: `store` is in scope and removed.** Rationale: (a) it is a documented plaintext-at-rest surface (`~/.git-credentials`); (b) today it is a *vestigial no-op* for the origin remote — URL-embedded credentials bypass helpers, so nothing ever relied on it — but the moment the remote goes tokenless, any successful authenticated operation would let `store` re-capture the token to plaintext, silently recreating the exact at-rest problem this task removes; (c) nothing else on the pod uses git credentials (HF uses the hub API, WandB its own key). Replacing it with the same env-reading helper — global + host-scoped — keeps ad-hoc secondary clones of github.com repos pushable (the GCE helper is repo-local because GCE instances are single-workload and ephemeral; pods host interactive work).

Replace line 466's `git config --global credential.helper store` (inside the single-quoted `ssh_cmd '...'` block) by *deleting it from that block* and adding one **new double-quoted** `ssh_cmd` call immediately before it (the helper needs local `$GIT_CRED_HELPER` expansion, which a single-quoted block cannot do):

```bash
# #1239: the global credential config replaces the former
# `credential.helper store` (plaintext ~/.git-credentials at rest — and it
# would re-capture the token after any successful auth now that the remote
# is tokenless). Host-scoped so the token is never offered to non-GitHub
# hosts; the unset+rm scrub retrofits pods bootstrapped pre-#1239.
ssh_cmd "git config --global credential.https://github.com.helper '$GIT_CRED_HELPER'
git config --global --unset-all credential.helper 2>/dev/null || true
rm -f /root/.git-credentials"
```

The remaining single-quoted block (ssh-keyscan + identity echoes, lines 467–477) is kept minus the `store` line.
