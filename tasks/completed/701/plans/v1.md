## 1. Goal

Refine the "CPU-only phases run OFF-POD by default" rule so it no longer
mis-routes a **gradient-descent / iterative-optimization fit** (e.g. #658's
`_fit_mlp_loco`, a 300-epoch AdamW-per-cell torch-MLP) to the VM CPU
default. Such a fit is GPU-worthy and must route to a GPU pod / GCP A100
lane — it is *not* the cheap closed-form bootstrap/permutation work the
existing rule was written to keep off pods.

## 2. Method delta (what differs from the existing rule)

The existing planner.md §9 rule (lines 489–506) conflates two distinct
axes under one label ("CPU-only"):

1. **Footprint axis** — "does this phase materialize a large local
   footprint?" Governed by the data-footprint carve-out (lines 508–547,
   `VM_ANALYSIS_FOOTPRINT_GB_MAX = 50` GB → `cpu-bigmem` / streaming).
2. **Compute-character axis** — "is this cheap closed-form / sampling
   work, or iterative gradient descent on parameters?" **Currently
   missing.** The rule's examples (bootstrap, permutation, aggregation,
   judge-scoring, plotting) are all closed-form / I/O-bound, so a reader
   sees "CPU-only" and routes a 300-epoch AdamW fit to the VM because it
   "doesn't need a pod" — exactly the #658 mistake.

The refinement adds the **compute-character axis** as orthogonal to
footprint. A gradient-descent fit routes to a GPU pod / GCP A100 lane
*regardless* of whether it is "CPU-only" in the no-GPU-currently-used
sense, because it benefits materially from a GPU. The planner sizes the
fit's compute character in §9; the critic REVISEs a gradient-descent fit
silently placed on the VM CPU.

The two axes compose (see §5). Neither replaces the other.

## 4. Required terminology

The rule, in both files, must distinguish (using these exact contrasting
labels):

- **"cheap closed-form / sampling-based analysis"** — bootstrap,
  permutation, metric aggregation, judge-only scoring, plotting →
  **VM default**, governed by the existing OFF-POD rule + (for big
  footprint) the `cpu-bigmem` carve-out.
- **"iterative-optimization fit" / "gradient-descent fit"** — torch-MLP
  LOCO, per-cell probe trained via SGD/AdamW, small adapter fit, any phase
  whose inner loop runs gradient descent on parameters → **GPU-worthy,
  routes to a GPU pod / GCP A100 lane** (`lora-7b` / `eval` / `debug` —
  smallest that fits the parameter count + dataset). Canonical worked
  example: **#658 `_fit_mlp_loco`** (300-epoch AdamW per cell).

The load-bearing qualifier is **"iterative gradient descent on
parameters"** (the SGD/AdamW inner loop) — explicitly NOT "uses pytorch"
(see §8 Risks).

## 5. Interaction with the footprint carve-out (orthogonal axes)

State both directions explicitly in the inserted prose:

| Compute character ↓ \ Footprint → | ≤ 50 GB | > 50 GB |
|---|---|---|
| **cheap closed-form / sampling** | VM (existing default) | `cpu-bigmem` GCP / stream (existing footprint carve-out) |
| **gradient-descent fit** | **GPU pod / GCP A100 lane** (NEW) | **GPU pod with a big disk** (NEW — NOT `cpu-bigmem`) |

Key points the prose must make:
- A gradient-descent fit with **<50 GB** footprint still goes to a GPU
  lane — it does NOT stay on the VM just because it would pass the
  footprint test.
- A gradient-descent fit with **>50 GB** footprint goes to a **GPU pod
  with a big ephemeral volume**, NOT `cpu-bigmem` (which is `gpu_count=0`
  and would re-starve the fit).
- A closed-form aggregation with **>50 GB** footprint still routes to
  `cpu-bigmem` per the unchanged footprint carve-out — the new axis does
  not touch it.

## 6. Edge case (don't over-route trivial fits)

When the gradient-descent fit is genuinely tiny (e.g. a single linear
probe trained in < 30 s), the existing "long CPU-only phase
(>~15–30 min)" floor governs: short phases stay on the VM regardless of
compute character. Both inserted blocks state this floor explicitly so the
new rule does not route a 10-second probe fit to a GPU pod.
