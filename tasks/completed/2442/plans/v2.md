# Plan v2 — #2442: absence checks must use a call that can FAIL on a wrong location

`kind: infra` workflow-fix task. Target surface: `CLAUDE.md` § "Ad-hoc results
summaries" (absence-claim sentence) + `.claude/rules/upload-policy.md`, plus one
small raising helper and its test.

**v2 supersedes v1** after a Methodology-lens critic round returned REVISE with
2 Must-Fix + 3 Should-Fix findings. All five are resolved below; the two Must-Fix
findings were independently re-verified against the installed
`huggingface_hub` 0.36.2 source before being accepted. The most consequential
change: **the task body's own proposed rule text is factually wrong about
`get_paths_info`, and v2 corrects it rather than implementing it verbatim** (§1.1).

## 1. Requirement

CLAUDE.md's absence-claim rule names the DUTY ("a SCOPED listing of the HF
prefix's siblings/parents (`list_repo_tree(path_in_repo=<parent prefix>)`)") and
even names the right call, but states no MECHANISM. Without the mechanism, the
natural implementation — fetch the full listing once, filter locally with
`startswith` — reads as satisfying the duty while being structurally incapable
of the check: the prefix never reaches the server, so the call cannot fail on a
wrong location. It exits 0 and prints an authoritative-looking zero.

Add the mechanism: **an absence check must use a call whose error surface
distinguishes wrong-path from empty-path.**

### Acceptance criteria (verbatim from the task body)

1. The absence-claim rule text names the wrong-path-vs-empty-path distinction
   and the two acceptable call shapes, not just the duty.
2. The `list_repo_files` + client-side-filter form is explicitly scoped to
   within-a-proven-prefix counting.
3. The parent-prefix positive control is stated as the fallback when no scoped
   call exists.
4. If a helper is added, it raises (never returns 0) on a nonexistent prefix,
   with a test using a nonexistent-prefix fixture asserting the raise — the test
   must FAIL against a client-side-filter implementation.
5. No new red in the no-flags `workflow_lint.py` run or the mapped-test
   selection.

### 1.1 Body-premise correction (criterion 1 delivered in CORRECTED form)

The body's "Proposed change" prescribes: "`list_repo_tree(path_in_repo=...)` or
`get_paths_info` (both 404 on a wrong prefix)", and criterion 1 asks for "the two
acceptable call shapes". **`get_paths_info` does not 404 on a missing path.**
Verified in the installed source
(`.venv/lib/python3.11/site-packages/huggingface_hub/hf_api.py:3370-3371`,
hub 0.36.2):

> `paths` … "The paths to get information about. **If a path do not exist, it is
> ignored without raising an exception.**"

and its `Raises:` block lists only `RepositoryNotFoundError` /
`RevisionNotFoundError` — nothing for a missing path. The implementation is a
bare POST + `hf_raise_for_status`; missing paths are simply omitted from the
returned list. So `get_paths_info(repo, ["wrong/prefix"])` returns `[]`
**silently** — it is a member of the very silent-empty class this rule bans, not
an alternative to it.

Implementing criterion 1 verbatim would therefore ship a FALSE API claim into
always-on CLAUDE.md, blessing a silent-empty call as a raising one with the
rule's own authority — a strictly worse outcome than the gap the task is closing,
because an agent following the corrected-looking rule would produce exactly the
#2329 failure while believing itself compliant.

**Resolution.** Criterion 1's *intent* (name the distinction + the acceptable
call shapes, not just the duty) is satisfied in full; its *incidental factual
premise* (that two raising shapes exist) is corrected. Exactly ONE HF call shape
raises on a wrong prefix: `list_repo_tree(path_in_repo=<literal prefix>)`.
`get_paths_info` is named in the rule as a **counter-example** — a call that
looks scoped but is not — which is more useful than omitting it, since an agent
reaching for a scoped-looking API would otherwise pick it. The "two shapes"
phrasing becomes "one raising shape, plus the membership-asserted form of
`get_paths_info`": `get_paths_info` is usable only when the caller asserts the
requested path actually appears in the returned set (turning the silent omission
into a checked one).

This correction is recorded on the task as an `epm:progress` note when v2 lands,
so the body's premise and the shipped rule do not silently disagree.

  where it is fast and still cannot fail on a wrong path.

- **The repo's own ergonomic wrapper VIOLATES the rule this task is writing.**
  `hub.list_hf_entries_under_path` / `list_hf_files_under_path`
  (`src/explore_persona_space/orchestrate/hub.py:1042-1126`) catch
  `EntryNotFoundError`, fall back to one `file_exists` HEAD probe, and **return
  `[]` for an absent path** — deliberately and documented ("an absent path
  returns `[]`"). Correct for their staging callers, exactly wrong for an
  absence check. This is the strongest argument for adding the helper: without
  one, the new rule says "use a call that can fail" while the nearest in-repo
  helper silently cannot — the same duty-without-mechanism defect, one layer
  down. `verify_repo_paths_uploaded` (`hub.py:1632`) is not a substitute either;
  it answers "is this expected SET present", requiring the paths up front. No
  `prefix_exists`-shaped helper exists in `hub.py` (checked the full `def`
  listing).

- **NEW in v2 — `get_paths_info` is silent-empty, not raising** (§1.1). Changes
  the rule text itself, not just the plan's framing.

- **NEW in v2 — `file_exists` is silent-False on a wrong repo/revision, not just
  a missing file.** Verified at `hf_api.py:3008-3022`: it catches
  `RepositoryNotFoundError`, `EntryNotFoundError`, AND `RevisionNotFoundError`
  into one `False`, and the docstring's own example is
  `file_exists("bigcode/not-a-repo", "config.json")` → `False`. So a typo'd
  `repo_id` / wrong `repo_type` / wrong `revision` reads as "file absent" with no
  error — which makes `upload-policy.md:957`'s standing instruction ("NEVER wave
  through a `RepositoryNotFoundError` / wrong-revision 404") **unactionable
  through `file_exists`**: it never shows you one. The new section states this,
  closing the last silent-absence shape in a section whose entire purpose is
  enumerating that class.

### 3.2 `.claude/rules/upload-policy.md` — new `## Absence checks` section

New section, placed before `## Relocated codebase traps` so its cross-reference
to line 957 reads forward. Contents:

- The two-call comparison reproduced from #2329, verbatim shape:
  `list_repo_files` + `startswith` → rc=0, prints `0`;
  `list_repo_tree(path_in_repo=<same nonexistent prefix>)` →
  `EntryNotFoundError` 404. Same repo, same prefix, opposite outcomes.
- Why: the client-side filter is a local string operation over a listing produced
  for a different question, so "prefix holds nothing" and "prefix does not exist"
  are indistinguishable by construction.
- **The silent-empty roster** — the calls that LOOK like existence checks and are
  not, each with the mechanism and the assert that rescues it:
  `get_paths_info` (missing paths omitted, no raise — assert the requested path
  is in the returned set); `file_exists` (False also covers wrong
  repo/type/revision — assert the repo+revision resolve first, or read the error
  via a call that raises); `hub.list_hf_files_under_path` /
  `list_hf_entries_under_path` (return `[]` on absent by design — never use as
  absence primitives; use `hub.assert_hf_prefix_exists`, §3.3);
  `list_repo_files` + client-side filter (the #2329 case).
- **HF-specific precision (Should-Fix 3).** On a git-backed repo there are no
  empty directories: a tree prefix exists **iff** ≥1 file lives under it. So the
  scoped call's 404 covers BOTH "wrong guess" and "nothing persisted yet", and
  the two are disambiguated by the parent-prefix positive control — not by the
  404 itself. The wrong-path-vs-empty-path framing is exact for the LOCAL legs
  (`ls`/`find` fail on a missing dir, succeed-empty on an empty one) and this
  is the HF refinement of it. Stating this prevents the opposite error — reading
  a 404 as proof of a wrong guess when the artifact simply has not landed
  (`upload-policy.md:957` already treats a pre-upload prefix 404 as expected).
- The parent-prefix positive control as the no-raising-call fallback, noting it
  is how #2329 was actually resolved (listing `ladder/`'s children showed no
  `grid`, which located the real path).
- **The lazy-generator trap, load-bearing here:** per `upload-policy.md:954`
  (#779) the 404 raises at ITERATION, not at the call — so a `try/except` around
  the call catches nothing and an absence check built that way silently degrades
  to the very failure mode this rule bans. Materialize inside the guard.
- **The tree-endpoint file-path 404** (`hub.py:1057-1058`, #939): the tree
  endpoint 404s on an exact FILE path too, so a raw scoped `list_repo_tree`
  probe against a file reads as absence. Probe files with `file_exists` (under
  its own caveat above) or use §3.3's helper, which handles both.
- The #2329 layout trap, one short paragraph: the store split across
  `issue2329_q35rerun/analysis_tensors/ladder/` and
  `issue2329_q35rerun/raw_completions/ladder/`, neither named for the round
  label, with rollout TEXT under `raw_completions/` per upload policy — so "the
  grid store" is NOT under the tree holding every other ladder artifact. A
  prefix guess that looks obviously right is often wrong here.
- The throughput-vs-correctness labelling (per §2 above).

Cross-references both ways: the new section points at `:957` for the HTTP
mechanics and `:954` for the generator trap; no restatement.

### 3.3 `src/explore_persona_space/orchestrate/hub.py` — `assert_hf_prefix_exists`

New helper. Contract, revised per Must-Fix 2 and Should-Fix 3:

```python
def assert_hf_prefix_exists(
    api, repo_id: str, prefix: str, *, repo_type: str = "dataset",
    revision: str | None = None,
) -> int:
    """Return the file count at/under ``prefix``, RAISING if it does not exist.

    The absence-check primitive: a scoped server-side ``list_repo_tree`` whose
    404 distinguishes a resolvable location from an unresolvable one. NEVER
    returns 0 for a nonexistent prefix — that silent-zero shape is exactly what
    ``CLAUDE.md`` § "Absence claims" bans (#2329).

    An exact FILE path returns 1: the tree endpoint 404s on file paths (hub
    0.36.2, #939), so an ``EntryNotFoundError`` falls back to ONE retried
    ``file_exists`` HEAD probe before the raise — without it this helper reports
    a present file as absent, re-creating the defect it exists to prevent one
    kind-confusion over.

    Deliberately NOT ``list_hf_files_under_path``, which returns ``[]`` for an
    absent path (correct for staging, wrong here).
    """
```

Implementation notes (each closes a trap already recorded in the rules):

- Materialize the generator INSIDE the retry thunk (`list(...)`), so the 404
  raises where it can be seen (#779, `upload-policy.md:954`).
- Route through `retry_transient` (the public alias of `_retry_upload`) so a
  429/5xx is retried rather than misread as absence — a transient error must
  never be reported as "prefix does not exist". `EntryNotFoundError` is
  non-transient and propagates immediately.
- **On `EntryNotFoundError`, one `retry_transient`-wrapped
  `api.file_exists(...)` probe** (Must-Fix 2), mirroring the in-module sibling at
  `hub.py:1087-1093`: True ⇒ return 1 (exact file); False ⇒ raise. Six
  precedented lines.
- Empty `prefix` raises `ValueError` (a falsy prefix would degrade to a full-repo
  listing — the `list_hf_entries_under_path:1082` precedent).
- The raise message names the three live possibilities so it is actionable, not
  just loud: wrong prefix / not yet uploaded / wrong `repo_type` or `revision`.
- Return the count so a caller gets the coverage number and the existence proof
  from one call, no second listing. Per Should-Fix 3 the docstring does NOT claim
  a "0 means exists-but-empty" branch — unreachable for a directory prefix on a
  git-backed repo; the return is `>= 1` in every non-raising path.

### 3.4 `tests/test_hub_absence_check.py` — new test file

Four tests (v1 had three; test 4 added per Must-Fix 2). All fakes return LAZY
GENERATORS that raise on first `next()`, not at call time (Should-Fix 4) —
mirroring verified 0.36.2 semantics, so an implementation that materializes
outside the retry thunk / guard FAILS rather than passing.

1. `test_absent_prefix_raises` — fake `list_repo_tree` returns a generator
   raising `EntryNotFoundError`; fake `file_exists` returns False; assert
   `assert_hf_prefix_exists` RAISES. **Must FAIL against a client-side-filter
   implementation:** the fake also exposes a `list_repo_files` returning a
   populated listing none of whose entries start with the fixture prefix, so a
   filter-based implementation returns 0 and the test fails on the missing raise.
   This discriminating property is criterion 4's mechanical requirement.
2. `test_exact_file_path_returns_one` (NEW) — tree raises `EntryNotFoundError`,
   `file_exists` returns True; assert the return is `1` and nothing raises. Pins
   Must-Fix 2 — fails against the v1 contract.
3. `test_populated_prefix_returns_count` — scoped listing yields N file entries
   (folder entries dropped); assert the return is N.
4. `test_transient_error_is_retried_not_reported_as_absent` — first iteration
   raises a transient (429-shaped), second succeeds; assert the helper returns
   the count. Guards the misread-transient-as-absence failure.

Fakes are signature-conformant by construction (`create_autospec` / a `def`
mirroring the real signature) per `code-style.md` § "One production-body test per
seam-stubbed function"; the helper's own body executes in every test.
