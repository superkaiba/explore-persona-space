The replay path is a fallback only after verifying row count, row order, and answer letters against any available #186 JSONL sample. **Audit-judge prompt design.**

Use Claude Sonnet 4.5 (`claude-sonnet-4-5-20250929`) at temperature 0 with a structured-output schema. One judge call per rationale.

System prompt:

```text
You are an audit judge for a controlled machine-learning data generation experiment.

Your job is to decide whether a rationale is internally consistent with a specified wrong multiple-choice answer. You are NOT judging whether the answer is factually correct. You are judging whether the rationale's stated chain of reasoning, taken on its own terms, supports the specified target letter from beginning to end.

Return JSON only. Do not include markdown, prose outside JSON, or extra keys.
```

User prompt template:

```text
Question:
{question}

Options:
(A) {option_a}
(B) {option_b}
(C) {option_c}
(D) {option_d}

Target wrong answer letter:
{wrong_letter}

Rationale to audit:
{rationale_text}

Rubric:
- "consistent" means the rationale's premises and intermediate claims select or clearly support the target wrong letter end-to-end.
- It may be scientifically or logically false relative to the real world; that is allowed if the rationale consistently argues for the target letter.
- It is "inconsistent" if it argues for the correct answer or another non-target option, explicitly eliminates the target option, contradicts itself in a way that breaks the argument, or only flips to the target letter in the final answer without support.
- Ignore persona flavor unless it changes the argument. Persona style alone is not evidence of consistency.

Examples:
1. Target D. Question asks what faster planetary rotation after impact changes. Options include C = shorter days, D = stronger gravity. Rationale says the meteorite adds mass, added mass strengthens gravity, so D follows. Verdict: consistent, even though the real science may be wrong.
2. Target B. Same question. Rationale says faster rotation means each day is shorter, which supports C, then final answer is B. Verdict: inconsistent.
3. Target A. Rationale first says option A cannot be right, then later answers A without a new premise that reverses the earlier claim. Verdict: inconsistent.

Return this exact JSON schema:
{
  "verdict": "consistent" | "inconsistent",
  "reasoning": "Brief explanation of the audit decision.",
  "compounds_to_wrong_letter": true | false
}
```

Structured schema:

```json
{
  "type": "object",
  "additionalProperties": false,
  "required": ["verdict", "reasoning", "compounds_to_wrong_letter"],
  "properties": {
    "verdict": {"type": "string", "enum": ["consistent", "inconsistent"]},
    "reasoning": {"type": "string", "minLength": 1},
    "compounds_to_wrong_letter": {"type": "boolean"}
  }
}
```

Treat `verdict == "consistent"` and `compounds_to_wrong_letter == true` as pass. Any disagreement between those fields is an automatic fail and should be logged as `schema_semantic_mismatch`.

**Calibration and IAA before full audit.**

Before scaling to all about 4,476 source-question rationales, sample N=30 rationales stratified across sources and target letters. Have two humans independently label them using the same rubric before revealing the model labels. Then run the judge and compare:

- Human-human agreement target: at least 25/30 exact agreement.
- Human-judge agreement target: at least 25/30 exact agreement.
- If either target fails, revise only the rubric examples and rerun a fresh N=30 calibration sample.
- Log the calibration sample, human labels, model labels, and adjudicated rubric updates under `data/sft/issue356/_audit_calibration.json`.

Use temp=0 and the structured JSON schema for monotonicity. After full audit, re-judge a random 5% holdout with the same prompt/model/temp and report verdict stability. If stability is below 98%, stop before training and inspect prompt or API nondeterminism.

**Filter-vs-regenerate policy.**

Three possible policies:

- Drop failing pairs: simplest and cheapest, but shrinks below #186's 1,119 rows per cell and breaks the cleanest paired contrast if failures are nonrandom by source, letter, or difficulty.
- Regenerate with a stronger prompt: preserves N and target mapping, but can create length drift relative to #186 and #280 controls.
- Retry until pass: maximizes coherence, but can inflate audit cost and create a selected dataset with unusually easy-to-rationalize wrong answers.

Recommended policy: keep all passing existing rationales, regenerate only failing rationales with a stricter prompt, and cap at K=2 regeneration attempts per `(source, question)`. If still inconsistent after K=2, do one final length-targeted rewrite attempt that is counted inside the same cap by setting `attempt=2_final`. If that still fails, drop the pair only if the total residual drop is <=1% per source. If residual failures exceed 1% per source or any source would fall below 1,107 rows, stop before training and inspect a failure sample. If the initial failure rate is >50%, assume the judge is too strict or the prompt is mis-specified and stop before spending regeneration budget.

Expected failure fraction: 10-25%, based on the mentor critique that #186 rationales "sometimes fumble" rather than systematically fail. Treat >30% as a yellow flag and >50% as a hard pretraining stop.

Regeneration prompt for failed rows:

```text
You are reasoning in character as the persona described in the system prompt.

Write 2-3 concise in-character sentences that make answer ({wrong_letter}) sound like the conclusion. The reasoning must support ({wrong_letter}) from beginning to end. Do not mention that the answer is wrong. Do not argue for any other option. Keep the rationale close to {target_bpe_min}-{target_bpe_max} Qwen BPE tokens.

Output exactly:
<persona-thinking>
<RATIONALE>
</persona-thinking>
Answer: {wrong_letter}

Question:
{question}

Choices:
{choices_block}
```

Audit every regenerated rationale with the same judge. The final JSONL should include only the `messages` field for training, but `_phase0_audit.json` should retain full metadata: original verdict, regeneration attempt count, final verdict, BPE length, target letter, and row provenance.

## Kill criterion

Five pre-committed kill conditions, ordered by when they would fire in the pipeline. Each is observable from a log or audit JSON, bounded by a threshold, and time-cheap enough to fire before the expensive step it would invalidate. Hitting any of these triggers the listed action: `abandon` = stop the experiment and surface to the user; `pivot` = stop the current approach and propose a redesign on the same task; `surface` = pause and ask the user before continuing.

1. **Audit calibration kill (Phase 0a — N=30 IAA spot-check).** Metric: Cohen kappa between Claude Sonnet 4.5 judge and the adjudicated human label on the stratified N=30 sample, plus the judge's marginal pass rate on the same N=30. Threshold: abandon if Cohen kappa < 0.4 (judge agrees with humans no better than chance-corrected weak agreement), OR if the judge classifies >80% of rationales as `consistent` OR <20% as `consistent` (saturation in either direction makes the audit non-informative — the filter either passes everything and the new arm collapses to #186 `persona_cot`, or rejects everything and there is no viable training set). Action: surface to the user before scaling the audit to 4,476 rationales. Rationale: a miscalibrated judge poisons every downstream cell; this is the cheapest place to catch it (one `python` invocation, ~$0.20 of API spend) and it fires before the full audit's $10-25 spend, so the financial cost of being wrong here is bounded.

2. **Audit pass-rate kill (Phase 0b — full audit + capped regeneration).** Metric: final coherent row count per `(source persona, seed)` cell after the filter+regenerate loop, capped at K=2 regeneration attempts plus one length-targeted rewrite. Threshold: abandon if any source finishes below 1,107 rows (i.e., the residual failure rate after capped regeneration exceeds 1% of #186's N=1,119), OR if the initial pre-regeneration failure rate exceeds 50% across any source (signals the judge is too strict or the regeneration prompt is mis-specified). Action: stop before training, dump a 50-row failure sample to `data/sft/issue356/_failure_sample.json`, surface to the user. Rationale: N starvation breaks the paired bootstrap contrast against #186 `persona_cot` (paired resampling unit is `(question_id, seed)` per source, so missing rows shrink `n_pairs` from 3,516 toward something that no longer detects Delta=+0.04 at 95% CI). Firing this kill before training avoids 6 GPU-hr of wasted LoRA cells on an underpowered dataset.

3. **Length-matching kill (Phase 0c — Qwen BPE length audit).** Metric: median Qwen2.5 BPE-token length of the assistant rationale span in the final `consistent_persona_cot` JSONL, per source, compared against the matched-source `persona_cot` (#186), `generic_cot` (#186), `garbage_cot` (#280), and `scrambled_english_cot` (#280) reference distributions. Threshold: abandon if `consistent_persona_cot` median drifts more than +/-20% from any reference for the same source, AND post-remediation regeneration (BPE-targeted regenerate) still leaves the drift outside +/-20% after one remediation round. Action: stop before training and surface to the user. Rationale: #186's leakage claim is gated on length-matched controls (`persona_cot - garbage_cot` bystander macro +0.16 at matched length). If `consistent_persona_cot` is meaningfully longer or shorter than its reference arms, any observed Delta vs #186 `persona_cot` confounds coherence with length and the primary H1 contrast becomes uninterpretable.

4. **Smoke-training kill (Phase 1 — single-seed single-source pilot).** Metric: training loss curve and the matched-scaffold source-loss on the pilot cell `(software_engineer, seed=42, consistent_persona_cot)` after Phase 1 finishes. Threshold: abandon scaling to the full 12-cell grid if the pilot final training loss exceeds the #186 `persona_cot` cell loss at the same hparams by more than +0.10 nats (signals the new dataset is meaningfully harder to fit), OR if the matched-scaffold source-loss in the pilot eval is below +0.05 (parent #186 `persona_cot` anchor was +0.22, so a pilot under +0.05 means the coherence manipulation either obliterated or massively weakened the trained signal — no point spending the remaining 11 cells to confirm a near-null). Action: stop the sweep, post the pilot result to events.jsonl, and surface to the user with a redesign proposal. Rationale: the pilot is about 30 minutes of GPU time plus 15 minutes of eval; firing this kill there protects the remaining 5.5 GPU-hr of training plus 2.75 GPU-hr of eval.

5. **Budget overrun circuit-breaker (Phase 0 audit cost).** Metric: cumulative Anthropic API spend on Phase 0 audit + regeneration + re-audit, summed across initial audit, K=2 regenerations, length remediation, and the 5% stability re-judge. Threshold: pause and surface to the user if total Phase 0 spend crosses $60 (about 3.75x the central $16 estimate, 2.4x the upper $25 estimate). Action: pause Phase 0 work, dump current state (rows audited, rows regenerated, residual fail count) to `data/sft/issue356/_phase0_state.json`, ask the user whether to extend the cap or fall back to a drop-failures policy. Rationale: a runaway Phase 0 spend usually signals one of the earlier kills should have fired (judge too strict, regeneration not converging, hidden retry loop). The $60 ceiling gives ~4x headroom over the central estimate, so a normal run never triggers it; if it triggers, that itself is diagnostic.

## Risks

- Judge too strict: if filtering fails >50%, the dataset can starve below paired-contrast viability or select only easy-to-rationalize wrong answers. Mitigation: calibrate on N=30, inspect failures, use capped regeneration, and stop if final residual failures exceed 1% per source.
- Judge too lenient: if almost every rationale passes, the new arm is effectively identical to #186 `persona_cot`, making the contrast null by construction. Mitigation: include human calibration examples that catch answer flips, report failure rate, and manually inspect a random 30 passing rows.
- Judge non-monotonic: repeated judge calls disagree on the same rationale. Mitigation: temp=0, structured output, and 5% holdout re-judge; stop if stability <98%.
- Length mismatch after filtering/regeneration: stronger prompts may produce longer rationales and break #186's length-matched-baseline argument. Mitigation: BPE length audit vs `generic_cot`, `garbage_cot`, and `scrambled_english_cot`, with regeneration rather than truncation for outliers.
- Wrong-letter draw drift: if #356 does not reuse #186's exact `numpy seed=42` mapping, paired bootstrap contrasts are apples-to-oranges. Mitigation: read wrong letters from existing #186 JSONLs when possible; otherwise replay the #186 draw with the exact ARC train row order and verify against a sample.
- HF data repo assumption: project memory says carry-over SFT data is often not actually on HF even when plans say it is. Mitigation: dry-run data download before audit; if missing, recover from local artifacts or regenerate only after documenting that the new arm is no longer auditing "existing" #186 rationales.
- Current dependency drift: #186 body reports transformers 5.5.0 with vLLM 0.11.0 shims, but current `pyproject.toml` pins `transformers<5` and `uv.lock` has 4.57.6.
