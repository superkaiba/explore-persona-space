**Audit-judge prompt design.**

Use Claude Sonnet 4.5 (`claude-sonnet-4-5-20250929`) at temperature 0 with a structured-output schema. One judge call per rationale.

System prompt:

```text
You are an audit judge for a controlled machine-learning data generation experiment.

Your job is to decide whether a rationale is internally consistent with a specified wrong multiple-choice answer. You are NOT judging whether the answer is factually correct. You are judging whether the rationale's stated chain of reasoning, taken on its own terms, supports the specified target letter from beginning to end.

Return JSON only. Do not include markdown, prose outside JSON, or extra keys.
```

User prompt template:

```text
Question:
{question}

Options:
(A) {option_a}
(B) {option_b}
(C) {option_c}
(D) {option_d}

Target wrong answer letter:
{wrong_letter}

Rationale to audit:
{rationale_text}

Rubric:
- "consistent" means the rationale's premises and intermediate claims select or clearly support the target wrong letter end-to-end.
- It may be scientifically or logically false relative to the real world; that is allowed if the rationale consistently argues for the target letter.
- It is "inconsistent" if it argues for the correct answer or another non-target option, explicitly eliminates the target option, contradicts itself in a way that breaks the argument, or only flips to the target letter in the final answer without support.
- Ignore persona flavor unless it changes the argument. Persona style alone is not evidence of consistency.

Examples:
1. Target D. Question asks what faster planetary rotation after impact changes. Options include C = shorter days, D = stronger gravity. Rationale says the meteorite adds mass, added mass strengthens gravity, so D follows. Verdict: consistent, even though the real science may be wrong.
2. Target B. Same question. Rationale says faster rotation means each day is shorter, which supports C, then final answer is B. Verdict: inconsistent.
3. Target A. Rationale first says option A cannot be right, then later answers A without a new premise that reverses the earlier claim. Verdict: inconsistent.

Return this exact JSON schema:
{
  "verdict": "consistent" | "inconsistent",
  "reasoning": "Brief explanation of the audit decision.",
  "compounds_to_wrong_letter": true | false
}
```

Structured schema:

```json
{
  "type": "object",
  "additionalProperties": false,
  "required": ["verdict", "reasoning", "compounds_to_wrong_letter"],
  "properties": {
    "verdict": {"type": "string", "enum": ["consistent", "inconsistent"]},
    "reasoning": {"type": "string", "minLength": 1},
    "compounds_to_wrong_letter": {"type": "boolean"}
  }
}
```

Treat `verdict == "consistent"` and `compounds_to_wrong_letter == true` as pass. Any disagreement between those fields is an automatic fail and should be logged as `schema_semantic_mismatch`.

**Phase 0a — Calibration and IAA before full audit.**

Before scaling to all ~4,384 source-question rationales (4 sources × 1,096 inherited rows), sample N=30 rationales stratified across sources **AND target letters**: aim for ~7-8 rows per wrong-letter target (A, B, C, D) so per-letter kappa is identifiable. Have two humans independently label them using the same rubric before revealing the model labels. Then run the judge and compare:

- Human-human agreement target: at least 25/30 exact agreement.
- Human-judge agreement target: at least 25/30 exact agreement.
- **Per-letter kappa**: compute Cohen kappa within each wrong-letter target subset (≈7-8 rows each) in addition to the aggregate N=30 kappa. Report the four per-letter kappas alongside the aggregate.
- **Per-letter kappa trigger**: if the range of per-letter kappas exceeds 0.3 (i.e., any letter's kappa is ≥0.3 below the best-performing letter's kappa), flag as a rubric-design issue and surface to the user before scaling. A wide per-letter kappa range signals the rubric is letter-asymmetric (e.g., the judge is systematically harsher on some target letters), which would re-introduce the difficulty-selection confound at the audit stage.
- If aggregate human-judge agreement falls below target, revise only the rubric examples and rerun a fresh N=30 calibration sample.
- Log the calibration sample, human labels, model labels, per-letter kappas, and adjudicated rubric updates under `data/sft/issue356/_audit_calibration.json`.

Use temp=0 and the structured JSON schema for monotonicity. After full audit, re-judge a random 5% holdout with the same prompt/model/temp and report verdict stability. If stability is below 98%, stop before training and inspect prompt or API nondeterminism.

**Phase 0b — Full audit.**

Run the calibrated judge over all 4,384 rationales. Emit `data/sft/issue356/_phase0_audit.json` with one row per `(source, q_id)` carrying:
- original verdict
- judge reasoning string
- target wrong letter
- BPE length of original rationale
- row provenance (kept-as-is at this stage)

**Phase 0c — Capped regeneration.**

Filter-vs-regenerate policy:

- Drop failing pairs: simplest and cheapest, but shrinks below the inherited 1,096-row #186 `persona_cot` baseline per cell and breaks the cleanest paired contrast if failures are nonrandom by source, letter, or difficulty.
- Regenerate with a stronger prompt: preserves N and target mapping, but can create length drift relative to #186 and #280 controls.
- Retry until pass: maximizes coherence, but can inflate audit cost and create a selected dataset with unusually easy-to-rationalize wrong answers.

Recommended policy: keep all passing existing rationales, regenerate only failing rationales with a stricter prompt, and cap at K=2 regeneration attempts per `(source, question)`. If still inconsistent after K=2, do one final length-targeted rewrite attempt that is counted inside the same cap by setting `attempt=2_final`. If that still fails, drop the pair only if the total residual drop is <=1% per source (1% of 1,096 = ~11 rows). If residual failures exceed 1% per source or any source would fall below 1,084 rows, stop before training and inspect a failure sample. If the initial failure rate is >50%, assume the judge is too strict or the prompt is mis-specified and stop before spending regeneration budget.

Expected failure fraction: 10-25%, based on the mentor critique that #186 rationales "sometimes fumble" rather than systematically fail. Treat >30% as a yellow flag and >50% as a hard pretraining stop.

Regeneration prompt for failed rows:

```text
You are reasoning in character as the persona described in the system prompt.

Write 2-3 concise in-character sentences that make answer ({wrong_letter}) sound like the conclusion. The reasoning must support ({wrong_letter}) from beginning to end. Do not mention that the answer is wrong. Do not argue for any other option. Keep the rationale close to {target_bpe_min}-{target_bpe_max} Qwen BPE tokens.

Output exactly:
<persona-thinking>
<RATIONALE>
</persona-thinking>
Answer: {wrong_letter}

Question:
{question}

Choices:
{choices_block}
```

Audit every regenerated rationale with the same judge. The final JSONL should include only the `messages` field for training, but `_phase0_audit.json` should retain full metadata: original verdict, regeneration attempt count, final verdict, BPE length, target letter, and **row provenance** (`kept` | `regenerated_attempt_1` | `regenerated_attempt_2` | `regenerated_attempt_2_final`).

**Phase 0c — Length-matching audit.**

After audit/regeneration, compute Qwen2.5 BPE-token lengths for the assistant-turn rationale span and full assistant turn:

- `consistent_persona_cot`
- #186 `generic_cot`
- #280 `garbage_cot`
- #280 `scrambled_english_cot`
- #186 `persona_cot` original

```bash

```

The length audit should:

1. Load the Qwen tokenizer with `AutoTokenizer.from_pretrained("Qwen/Qwen2.5-7B-Instruct", trust_remote_code=True)`.
2. Compute median, IQR, mean, p05, p95 per `(source, arm)`.
3. Flag if `consistent_persona_cot` median differs by more than +/-20% from #186 `persona_cot` (the binding paired-contrast counterpart) for the same source. Drift vs `generic_cot`, `garbage_cot`, and `scrambled_english_cot` is computed and reported in `_length_audit.json` as a diagnostic but does NOT trigger the Phase 0c kill (only drift vs `persona_cot` does — see Kill #3 below).
4. Flag if IQR is more than 1.5x the widest reference IQR.
5. Save `data/sft/issue356/_length_audit.json`.

Remediation: do not manually truncate rationales, because truncation can break the reasoning and reintroduce incoherence. Regenerate outlier rows with an explicit BPE target band if the median is outside +/-20%. If rows are too short, regenerate longer with "include one concrete comparison to the target option"; if too long, regenerate shorter with "one premise plus one conclusion, no caveats." **Phase 0d — Vocabulary-diff audit (NEW in v4).**

Motivation: #186 Result 2 found that persona-vocabulary in the assistant turn is the dominant leakage driver. Audit-pass + regeneration could shift the persona-vocabulary distribution of `consistent_persona_cot` vs the inherited #186 `persona_cot` JSONLs, which would confound the H1 contrast ("coherence amplifies leakage") with "trained on different vocabulary". This audit runs **before training (Phase 1)** so a vocabulary shift is detected and remediated up front, not post-hoc.

Inputs:
- `data/sft/issue356/<source>_consistent-persona-cot_seed42.jsonl` (final post-audit-and-regeneration training file)
- #186 `persona_cot` source-of-record at HF `issue186_data_v344/<source>_persona-cot_seed42.jsonl`

For each of the four sources, compute on the assistant-rationale span (text inside `<persona-thinking>...</persona-thinking>`):

1. **Persona-vocabulary unigram set**: tokenize with the Qwen2.5 tokenizer, restrict to the persona-vocabulary token families identified in #186 Result 2 (the n-gram families flagged in #186's regression; if the exact list is not recoverable, fall back to "all unigram tokens that appear with relative frequency ≥1e-4 in the source-persona's `persona_cot` rationales and ≥2x more frequent in source-persona than in the cross-persona average of the other three sources"). Save the resolved persona-vocab list under `data/sft/issue356/_persona_vocab_<source>.json` so the diagnostic is reproducible.
2. **Jaccard similarity** of persona-vocabulary unigrams: `|V_consistent ∩ V_persona| / |V_consistent ∪ V_persona|`, per source.
3. **KL divergence** on the persona-vocabulary token distribution: `KL(P_persona || P_consistent)` where `P_*` is the empirical relative-frequency distribution over the persona-vocab token list, smoothed with `add_alpha=1e-6`.
4. **Regenerated-rows-only sub-audit**: repeat (2) and (3) restricted to the rows with provenance `regenerated_attempt_*` (the 10-25% expected regeneration fraction). Compare persona-vocab token relative frequencies in the regenerated rows vs the kept rows.

Emit `data/sft/issue356/_vocab_diff.json`:

```json
{
  "per_source": {
    "<source>": {
      "n_kept": int,
      "n_regenerated": int,
      "regeneration_fraction": 0.xx,
      "persona_vocab_jaccard_all": 0.yy,
      "persona_vocab_kl_all": 0.zz,
      "regenerated_sub_audit": {
        "persona_vocab_jaccard_regen_vs_persona": 0.yy,
        "persona_vocab_kl_regen_vs_persona": 0.zz,
        "novel_persona_vocab_relfreq_delta_max": 0.ww,
        "tokens_with_relfreq_delta_above_10pct": ["..."]
      }
    }
  }
}
```

**Flag-trigger rule (Phase 0d)**: if persona-vocab Jaccard drops below 0.8 for any source, OR if the regenerated-rows sub-audit shows any persona-vocab token with relative-frequency delta beyond ±10% vs kept rows, the analyzer must call this out in the clean-result body as a confound under "alternative explanations". This is a flag, not a kill (regeneration is expected to shift vocabulary somewhat; the question is whether the shift is small enough that the H1 contrast remains interpretable). **Rejection of proposed `audit_labeled_persona_cot` baseline arm.**

The Round-1 Alternatives Claude critic proposed adding a 12-cell `audit_labeled_persona_cot` baseline arm — train on the unaltered #186 `persona_cot` data with audit verdicts attached but no filtering or regeneration — to isolate filtering-pipeline noise. This v4 plan **rejects** that addition with the following reasoning:

The proposed baseline does not actually isolate filtering-pipeline noise. The kept rows of `consistent_persona_cot` are byte-identical to the corresponding #186 rows (the Phase 0c filter reads them directly from the verified HF data-repo path `issue186_data_v344/<source>_persona-cot_seed42.jsonl` and re-emits them verbatim in the training JSONL), so the audit-labeling step itself does NOT perturb the training data on kept rows. Only the regenerated 10-25% of rows differ from #186. The right diagnostic for "filtering-pipeline noise" is therefore (a) per-row provenance in `_phase0_audit.json` (kept vs regenerated), (b) the Phase 0d vocabulary-diff audit, and (c) the regeneration-fraction stratification in the aggregate output (see §Eval) — not a 12-cell retraining baseline. If the audit-fail rate per source is heterogeneous, the cross-source analysis in the aggregator catches it descriptively. Adding the audit-labeled baseline would burn 6 GPU-hr of training plus 3 GPU-hr of eval to measure a noise floor that is recoverable by stratified analysis on the already-planned diagnostics. This rejection follows the verdict-definition guidance "Reserve REVISE for missing data / conditions / infrastructure. Pre-registered confirmation conjunctions are an anti-pattern."

**Diagnostic computation specifics:**

- `difficulty_audit`: for each source, join `_phase0_audit.json` (verdict per `q_id`) to `eval_results/issue186/baseline/result.json` (per-question Qwen-baseline accuracy under the `assistant` persona, averaged across seeds if the baseline JSON carries per-seed `raw[]` arrays). - `regeneration_fraction_stratification`: split the 1,172 ARC-C test questions into two subsets per source — the `low_regen_subset` (q_ids whose training row was kept verbatim from #186) and the `high_regen_subset` (q_ids whose training row was regenerated). **Diagnostic flag-trigger rules** (the analyzer must call out in the clean-result body if any fire):
- `difficulty_audit`: if `|diff_passed_minus_failed|` > 0.03 for any source, flag as a confound on H1. Interpretation: the judge is biased toward passing harder questions (or easier), so an observed `consistent_persona_cot` advantage may reflect selection on difficulty rather than coherence per se.
- `regeneration_fraction_stratification`: if `bystander_macro_high_regen_subset` − `bystander_macro_low_regen_subset` > 0.05 in absolute value for any source, flag as evidence that regeneration is doing the work (or undoing it) and discuss in alternative-explanations.
- `vocab_diff_passthrough`: per Phase 0d rule (Jaccard < 0.8 or regenerated-rows novel-vocab delta > 10%), flag as a confound.
- `per_cell_training_loss`: if `final_train_loss` on `consistent_persona_cot` drops more than 0.10 below the matched #186 `persona_cot` cell's final train loss AND the H1 contrast is positive (Delta source-macro > 0), discuss "trained harder, not learned coherence" as an alternative explanation.

**Statistical plan.**

- Unit of paired resampling: `(question_id, seed)` within each source. Note: #186/#280's published per-source `n_pairs = 1,172 x 3 = 3,516` is on the **eval** axis (test-question count × seeds), not the training-row count, and it is unaffected by the 1,096-row training-side shortfall — every cell still evaluates against the full 1,172-question test set across 3 seeds. So eval-side per-source `n_pairs = 1,172 x 3 = 3,516` for #356 as well.
- For any train-side paired view (e.g., audit-pass-rate per `(source, question_id)` × seeds), the upper bound is **up to 3,288 (1,096 audit-pass questions × 3 seeds)** per source; report whichever pairing unit a given downstream metric uses.
- Primary contrast: `consistent_persona_cot - persona_cot` under matched `persona_cot` eval.
- Axes: `source_loss` and `bystander_macro`, where loss is `baseline_correct - trained_correct` and bystander macro is the mean over the 10 non-source personas.
- Bootstrap: paired bootstrap n=1,000, with 95% CI from bootstrap quantiles.
- Family: 8 contrasts = 4 sources x {source_loss, bystander_macro}. Apply Holm-Bonferroni at family-wise alpha=0.01 to the 8 source-level tests. Also report macro means descriptively across sources.
- Pre-stated effect: H1 predicts Delta >= +0.04 bystander macro and Delta >= +0.04 source macro; null predicts Delta within +/-0.01.
- TOST equivalence: report against ±0.03 (the #186/#280-inherited band) and additionally against ±0.01 as a tighter descriptive band. **TOST gray-zone note**: a delta in `[+0.03, +0.04)` rejects TOST equivalence at the inherited ±0.03 band but does not confirm H1 (which prescribed Delta >= +0.04); the aggregator labels such cases as `partial signal` and the analyzer reports the per-source breakdown rather than aggregating to a binary verdict.
- No binary pass/fail rule. The aggregate should report point estimates, CIs, corrected p-values, `n_pairs` (per-axis), missing cells, source heterogeneity, and the four diagnostic sub-objects above.

## Kill criterion

Five pre-committed kill conditions, ordered by when they would fire in the pipeline. Each is observable from a log or audit JSON, bounded by a threshold, and time-cheap enough to fire before the expensive step it would invalidate. Hitting any of these triggers the listed action: `abandon` = stop the experiment and surface to the user; `pivot` = stop the current approach and propose a redesign on the same task; `surface` = pause and ask the user before continuing.

1. **Audit calibration kill (Phase 0a — N=30 IAA spot-check).** Metric: Cohen kappa between Claude Sonnet 4.5 judge and the adjudicated human label on the stratified N=30 sample, plus the judge's marginal pass rate on the same N=30, plus the per-letter kappa range. Threshold: abandon if Cohen kappa < 0.4 (judge agrees with humans no better than chance-corrected weak agreement), OR if the judge classifies >80% of rationales as `consistent` OR <20% as `consistent` (saturation in either direction makes the audit non-informative — the filter either passes everything and the new arm collapses to #186 `persona_cot`, or rejects everything and there is no viable training set), OR if the per-letter kappa range exceeds 0.3 (letter-asymmetric judging would re-introduce difficulty-selection bias downstream). Action: surface to the user before scaling the audit to ~4,384 rationales (4 sources × 1,096 inherited rows). Rationale: a miscalibrated judge poisons every downstream cell; this is the cheapest place to catch it (one `python` invocation, ~$0.20 of API spend) and it fires before the full audit's $10-25 spend, so the financial cost of being wrong here is bounded.

2. **Audit pass-rate kill (Phase 0b — full audit + capped regeneration).** Metric: final coherent row count per `(source persona, seed)` cell after the filter+regenerate loop, capped at K=2 regeneration attempts plus one length-targeted rewrite. Threshold: abandon if any source finishes below **1,084 rows** (i.e., the residual failure rate after capped regeneration exceeds 1% of the inherited 1,096-row #186 `persona_cot` baseline), OR if the initial pre-regeneration failure rate exceeds 50% across any source (signals the judge is too strict or the regeneration prompt is mis-specified). Action: stop before training, dump a 50-row failure sample to `data/sft/issue356/_failure_sample.json`, surface to the user. Rationale: the inherited #186 `persona_cot` JSONLs already carry 1,096 rows per source — not the raw ARC train N=1,119 — because Claude refused 23-25 questions during #186's original data generation. #356 inherits this exact 1,096-row population (per the clarifier's "audit + filter existing rationales" framing); we audit-filter only these rows, we do NOT regenerate the 23-25 #186-era refusals. N starvation below 1,084 breaks the paired bootstrap contrast against #186 `persona_cot` (paired resampling unit is `(question_id, seed)` per source). Firing this kill before training avoids 6 GPU-hr of wasted LoRA cells on an underpowered dataset.

   **Design note on filtering scope.** Two options were considered: (a) audit-filter only the 1,096 existing #186 rationales — what the clarifier locked in, preserves length-matching against the existing #186/#280 reference arms, and keeps the paired contrast clean; (b) optionally regenerate the original 23-25 refusals so #356 reaches 1,119 rows — would reframe the arm from "audit existing rationales" to "audit + complete", complicating the paired-contrast story and weakening length-match purity against #186 controls. Decision: option (a). The 1,096-row baseline is fixed; all kill thresholds anchor on it.

3. **Length-matching kill (Phase 0c — Qwen BPE length audit).** Metric: median Qwen2.5 BPE-token length of the assistant rationale span in the final `consistent_persona_cot` JSONL, per source, compared against the matched-source **#186 `persona_cot`** reference distribution (the binding paired-contrast counterpart for the primary H1 test). Drift vs #280's `generic_cot`, `garbage_cot`, and `scrambled_english_cot` is computed and reported in `_length_audit.json` as a diagnostic but does NOT trigger this kill — those references bind #186's leakage claim under #280's length-matched controls, not #356's `consistent_persona_cot` vs `persona_cot` paired contrast. Threshold: abandon if `consistent_persona_cot` median drifts more than +/-20% from `persona_cot` for the same source, AND post-remediation regeneration (BPE-targeted regenerate) still leaves the drift outside +/-20% after one remediation round. Action: stop before training and surface to the user. Rationale: the primary H1 contrast pairs `consistent_persona_cot` against #186 `persona_cot`. Length asymmetry between those two arms (and only those two) makes the contrast uninterpretable; asymmetry vs #280's controls is a diagnostic but does not invalidate the paired test.

4. **Smoke-training kill (Phase 1 — single-seed single-source pilot).** Metric: training loss curve, the matched-scaffold source-loss, AND the bystander macro on the pilot cell `(software_engineer, seed=42, consistent_persona_cot)` after Phase 1 finishes. Threshold: abandon scaling to the full 12-cell grid if the pilot final training loss exceeds the #186 `persona_cot` cell loss at the same hparams by more than +0.10 nats (signals the new dataset is meaningfully harder to fit), OR if **BOTH** the matched-scaffold source-loss is below +0.05 AND the pilot bystander macro is below +0.10 (parent #186 `persona_cot` anchor was +0.22 source / +0.16 bystander; a pilot under +0.05 source AND under +0.10 bystander means the coherence manipulation either obliterated or massively weakened the trained signal across the board — no point spending the remaining 11 cells to confirm a near-null). A strong-bystander/weak-source pilot, OR a weak-bystander/strong-source pilot, is interesting (not a failure mode) and the sweep continues. Action: stop the sweep, post the pilot result to events.jsonl, and surface to the user with a redesign proposal. Rationale: the pilot is about 30 minutes of GPU time plus 15 minutes of eval; firing this kill there protects the remaining 5.5 GPU-hr of training plus 2.75 GPU-hr of eval. The conjunction (source AND bystander both weak) avoids killing the experiment on an asymmetric-but-still-interesting outcome.

5. **Budget overrun circuit-breaker (Phase 0 audit cost).** Metric: cumulative Anthropic API spend on Phase 0 audit + regeneration + re-audit, summed across initial audit, K=2 regenerations, length remediation, and the 5% stability re-judge. Threshold: pause and surface to the user if total Phase 0 spend crosses $60 (about 3.75x the central $16 estimate, 2.4x the upper $25 estimate). Action: pause Phase 0 work, dump current state (rows audited, rows regenerated, residual fail count) to `data/sft/issue356/_phase0_state.json`, ask the user whether to extend the cap or fall back to a drop-failures policy. Rationale: a runaway Phase 0 spend usually signals one of the earlier kills should have fired (judge too strict, regeneration not converging, hidden retry loop). The $60 ceiling gives ~4x headroom over the central estimate, so a normal run never triggers it; if it triggers, that itself is diagnostic.

## Risks

- Judge too strict: if filtering fails >50%, the dataset can starve below paired-contrast viability or select only easy-to-rationalize wrong answers. Mitigation: calibrate on N=30, inspect failures, use capped regeneration, and stop if final residual failures exceed 1% per source.
- Judge too lenient: if almost every rationale passes, the new arm is effectively identical to #186 `persona_cot`, making the contrast null by construction. Mitigation: include human calibration examples that catch answer flips, report failure rate, and manually inspect a random 30 passing rows.
- Judge non-monotonic: repeated judge calls disagree on the same rationale. Mitigation: temp=0, structured output, and 5% holdout re-judge; stop if stability <98%.
- Length mismatch after filtering/regeneration: stronger prompts may produce longer rationales and break #186's length-matched-baseline argument. Mitigation: BPE length audit vs `generic_cot`, `garbage_cot`, and `scrambled_english_cot`, with regeneration rather than truncation for outliers.
- Wrong-letter draw drift: if #356 does not reuse #186's exact `numpy seed=42` mapping, paired bootstrap contrasts are apples-to-oranges. Mitigation: read wrong letters from existing #186 JSONLs when possible; otherwise replay the #186 draw with the exact ARC train row order and verify against a sample.
- HF data repo assumption: project memory says carry-over SFT data is often not actually on HF even when plans say it is. Mitigation: dry-run data download before audit; if missing, recover from local artifacts or regenerate only after documenting that the new arm is no longer auditing "existing" #186 rationales.
- Current dependency drift: #186 body reports transformers 5.5.0 with vLLM 0.11.0 shims, but current `pyproject.toml` pins `transformers<5` and `uv.lock` has 4.57.6. Mitigation: use current lock for new runs unless intentionally checking out the old #186 commit; do not run vLLM 0.11.0 with unpinned transformers 5.x without the compatibility shim and smoke test.
- GPU supply / RunPod dispatch: recent #333 r1-r5 looked like a RunPod pod-disappearance/supply issue but was later diagnosed as a script-side missing-data crash masked by stderr truncation. Mitigation: do local preflight for data availability before provisioning, use `scripts/pod.py provision --issue 356 --intent lora-7b`, capture stdout+stderr, and prefer the local `scripts/pod.py` path over the Sagan cloud-runner path if the same false-positive pattern appears. If H100 is unavailable, use the pod lifecycle GPU override only after confirming the LoRA-7B recipe works on the selected H200/A100 substitute.
- Eval schema drift: current worktree lacks the historical #186/#280 eval files. Mitigation: either cherry-pick/adapt from `557dd28c` and `ec328608`, or implement wrappers against current `evaluate_capability_cot_logprob` only after a smoke test confirms raw schema matches #280 aggregate expectations.
- **Difficulty-selection bias (NEW in v4)**: the audit-judge may systematically pass rationales for harder ARC-C questions (where wrong-letter advocacy is naturally more plausible) and fail rationales for easier questions, so an observed `consistent_persona_cot` advantage could reflect "harder-question selection" rather than "coherence amplifies leakage". Mitigation: pre-specified `difficulty_audit` in the aggregator (passed_baseline_acc_mean vs failed_baseline_acc_mean per source, paired-bootstrap p-value); analyzer must call out if `|diff_passed_minus_failed|` > 0.03 for any source.
- **Persona-vocabulary shift via regeneration (NEW in v4)**: #186 Result 2 identified persona-vocabulary as the dominant leakage driver, so any persona-vocab distribution shift between `consistent_persona_cot` and #186 `persona_cot` (driven by the 10-25% regenerated rows) confounds the H1 contrast. Mitigation: pre-training Phase 0d vocabulary-diff audit (Jaccard + KL + regenerated-rows sub-audit); analyzer must call out if Jaccard < 0.8 or any regenerated-rows novel vocab beyond ±10% relative frequency.
- **Trained-harder confound (NEW in v4)**: if `consistent_persona_cot` is meaningfully easier to fit (lower final train loss), an apparent leakage delta could reflect "model learned more during this run" rather than "coherence transfers". Mitigation: per-cell `final_train_loss` / `best_train_loss` in `aggregate.json`; analyzer must discuss as alternative if train-loss gap > 0.10 nats AND H1 delta is positive.
