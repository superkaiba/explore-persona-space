## Plan Summary

**Change:** `render_startup_script` in `src/explore_persona_space/backends/gcp.py` stops streaming workload output through startup-script stdout. After the env-export block it `exec >>"$EPS_LOG_PATH" 2>&1` into the handle's log file, keeps only sparse, guarded, newline-terminated heartbeat lines on the original runner pipe (saved as fd 3), exports `TQDM_DISABLE=1`, and installs a `trap '<handler>' PIPE` (a handler, **not** `trap '' PIPE` — empirically verified: a handler keeps the parent immune while children retain default SIGPIPE; ignore is inherited by children and breaks `producer | head` pipelines under `pipefail`). The GCP handle `log_path` moves from `$WORKLOAD_ROOT/logs/issue-<N>.log` to `{vm_scratch_dir}/logs/issue-<N>.log` via a new `log_path_for()` helper — this avoids a `git clone` into a non-empty `$WORKLOAD_ROOT` and unifies with the RunPod convention (`runpod.py:124`). `GcpBackend.poll` gains a truthful `last_log_mtime_sec_ago` (piggy-backed on the existing `_drain_sentinels` SSH round trip — zero extra round trips) so phase-stuck zombies become detectable. ## 1. Goal

Make the GCP lane's startup script structurally immune to the GCE metadata-runner `bufio.Scanner: token too long` kill (incident #491 attempt 2, 2026-06-11) by never streaming raw workload output through startup-script stdout, and close the secondary hole that made the kill invisible: a SIGPIPE death that leaves `eps/phase=workload` and the VM zombied at RUNNING with no poll-visible signal.

## 2. Prior work

### 2.1 What the incident record establishes (`tasks/awaiting_promotion/491/events.jsonl`, markers `epm:failure` 17:22:43Z + `epm:failure-lesson` 17:22:57Z)

- VM `eps-issue-491` (att-20260611-143912) killed mid-`[phase=free_gen]` at 17:03:06 UTC. Syslog: `error while communicating with "startup-script" script: bufio.Scanner: token too long` then `Script "startup-script" failed with error: signal: broken pipe`.
- Root cause: vLLM `\r`-progress bars accumulate into one enormous newline-free "line" on the runner's bounded line scanner; the runner closes the pipe; the next write dies on SIGPIPE.
- `eps/phase` stayed `workload`; the VM stayed RUNNING — invisible to `GcpBackend.poll`. Recovery was a manual SSH `nohup` relaunch with file-redirected output + manual sentinel write + `eps/phase=done` publish (recipe in `.claude/agent-memory/experimenter/feedback_gcp_metadata_runner_token_too_long.md`; also now a `gotchas.md` entry).

### 2.2 What the web search confirms

- **Upstream mechanism is a known guest-agent issue:** [GoogleCloudPlatform/guest-agent#149 "Improve handling of large process output when running metadata-script"](https://github.com/GoogleCloudPlatform/guest-agent/issues/149) — large process output overflows the scanner; *"when the scanner encounters this error, the pipe closes, which can cause the write() operation to fail and potentially crash the child process with a signal rather than returning a normal error"* (reporter notes this is likely unintended; a buffer-increase `in.Buffer(make([]byte, 0, 4*1024), 2*1024*1024)` was proposed, merge status unconfirmed). The deployed agent on our DLVM image demonstrably has a bounded scanner (#491 is the live proof) — so the fix must not depend on any particular buffer size: **never put workload output on the pipe at all**.
- Go's stock `bufio.Scanner` line limit is `bufio.MaxScanTokenSize` = 64 KiB unless the program enlarges it ([golang-nuts discussion](https://groups.google.com/g/golang-nuts/c/bgK1uCgwkxg)). Whatever the deployed value, vLLM bars exceed it.

### 2.3 What local experiments establish (run on this VM, bash 5.1.16(1)-release — same bash as the `ubuntu-2204` DLVM family)

Four experiments, reproducible (`bash <script> | true`, reader exits immediately):

| # | Setup | Result |
|---|---|---|
| 1 | `set -euo pipefail` + rc-guarded EXIT trap; builtin `echo` to closed pipe | Script dies 141 (SIGPIPE) — **but the EXIT trap RUNS with `rc=$?` = 0** (status of the last completed command). The `[ "$rc" -ne 0 ]` guard no-ops → no `phase=failed`, no shutdown. This — not "bash skips EXIT traps on SIGPIPE" — is the precise zombie mechanism on bash 5.1. Functionally the incident analysis stands; the fix implication changes (see §11-D3). |
| 2 | Same + `trap '' PIPE` | `echo: write error: Broken pipe`, rc=1, `set -e` exits, **EXIT trap rc=1** → failure branch would fire. Exit status 1, not 141. |
| 3 | External child (`/usr/bin/yes`) writing to closed pipe under `set -e` | Child dies 141 → propagates → EXIT trap **rc=141** → failure branch fires. So external-child SIGPIPE was never the zombie path; only bash-builtin writes are. |
| 4 | Child-inheritance: `trap '' PIPE` parent → child runs `seq 1e8 \| head -1` under `pipefail` | `seq: write error: Broken pipe`, **inner rc=1** — SIG_IGN is inherited across exec and breaks early-close pipelines in workload children. With `trap ':' PIPE` (a handler) instead: **inner rc=141** — children get default disposition back (handlers are reset on exec; only SIG_IGN survives). |

Conclusion: use a **handler** trap, never ignore: parent immune (write errors instead of signal death, EXIT trap fires with a real rc), children unaffected.

### 4.1 New helper — single source of truth for the log path

Next to `workload_dir_for` (gcp.py:403):

```python
def log_path_for(config: GcpConfig, issue: int) -> str:
    """Canonical workload log on the VM: ``<vm_scratch_dir>/logs/issue-<N>.log``.

    Mirrors the RunPod top-level-log convention (runpod.py ``log_path_for``)
    and deliberately lives OUTSIDE workload_dir_for() — the startup script
    redirects its output here BEFORE the repo clone, and ``git clone`` into
    ``$WORKLOAD_ROOT`` requires an empty target (#607).
    """
    return f"{config.vm_scratch_dir}/logs/issue-{issue}.log"
```

Use it in three places: `render_startup_script` (the redirect target literal), `launch()` (gcp.py:1948), `reconnect_or_none` (gcp.py:1419). This is the consistency requirement with `_drain_sentinels` (which tails `handle.log_path`) and with the relaunch-probe pattern (which already tails a file over SSH).

### 4.2 Rendered-script changes (`render_startup_script`)

Exact new/changed lines, in render order:

**(a) Preserve the runner pipe on fd 3 + install the PIPE handler — immediately after `umask 077`:**

```bash
# === SIGPIPE + serial-heartbeat setup (#607, incident #491) ===
# fd 3 = the metadata runner's pipe. Only tiny newline-terminated
# heartbeats ever go there; raw workload output never does (the
# runner's bounded line scanner kills the script on giant lines).
# fd 3 is inherited by workload children: nothing legitimately writes
# to it, and a stray giant `>&3` write now fails LOUDLY (child SIGPIPE
# -> rc!=0 -> EXIT trap -> phase=failed + shutdown), never a zombie.
exec 3>&1
# A HANDLER (not ignore): the parent shell survives a closed runner
# pipe as a normal write error (rc=1 -> set -e -> EXIT trap fires with
# rc!=0), while children keep DEFAULT SIGPIPE (SIG_IGN would be
# inherited across exec and break producer|head pipelines under
# pipefail in workload drivers).
trap ':' PIPE
```

**(b) Extend `_eps_phase` (replaces gcp.py:703-705) — guest attribute (unchanged) + a `[phase=...]` line on current stdout + a guarded fd-3 heartbeat:**

```bash
_eps_phase() { curl -fsS -X PUT -H "Metadata-Flavor: Google" --data "$1" "http://metadata.google.internal/computeMetadata/v1/instance/guest-attributes/eps/phase" >/dev/null 2>&1 || true; { echo "[phase=$1] startup-script $(date -u +%Y-%m-%dT%H:%M:%SZ)"; } 2>/dev/null || true; { echo "[startup-script] phase=$1" >&3; } 2>/dev/null || true; }
```

- The `[phase=...]` line lands in the log file post-redirect (pre-redirect: one tiny line on the pipe — safe). It matches `poll_pipeline.PHASE_RE`, making the primary-path log self-describing under the SAME parser the relaunch probe already uses (`latest_phase`), and consistent with the dispatch-script convention.
- The fd-3 line gives the serial console a sparse (~4 lines/run) trace. Deliberately formatted `[startup-script] phase=...` so it does **not** match `\[phase=` (no parser pollution on the serial channel).
- Every heartbeat write is `{ ...; } 2>/dev/null || true`-guarded: with the PIPE handler, a closed pipe yields a swallowed write error, never an abort.

**(c) Harden the EXIT trap (replaces gcp.py:717-720)** — same rc guard, made NON-ABORTING (v2 Must-Fix 1), plus a bounded serial diagnostic (the failure reason now lives in the log file, off the serial console; give humans a pointer without re-creating the giant-line risk):

```bash
trap 'rc=$?; set +e; if [ "$rc" -ne 0 ]; then { echo "[startup-script] FAILED rc=$rc — powering off to bound billing"; } 2>/dev/null || true; _eps_phase failed; if [ -n "${EPS_LOG_PATH:-}" ]; then { tail -n 40 "$EPS_LOG_PATH" 2>/dev/null | cut -c1-2000 >&3; } 2>/dev/null || true; fi; shutdown -h now; fi' EXIT
```

Two pitfalls handled:
- **Trap self-abort under the PIPE handler (v2 Must-Fix 1, Codex Methodology):** with `trap ':' PIPE` active, a write to a closed runner pipe inside the trap is an ordinary failing command; under `set -e` an UNGUARDED `echo` would abort the trap body before `_eps_phase failed` + `shutdown -h now` — re-opening the zombie exactly on the path that must bound billing. Hence `set +e` as the first action after capturing `rc`, AND every diagnostic write `{ ...; } 2>/dev/null || true`-guarded (`_eps_phase` is already internally guarded). `shutdown -h now` is then unconditionally reachable inside the rc≠0 branch. T6b executes this path with a closed pipe and asserts the shutdown stub fired.
- **`set -u` + unset `EPS_LOG_PATH`:** the trap is installed before `EPS_LOG_PATH` exists; a bare `"$EPS_LOG_PATH"` in an early-failure trap would error mid-trap and **skip the shutdown** — hence `${EPS_LOG_PATH:-}` + the `[ -n ]` guard. `cut -c1-2000` bounds every serial line even if a giant line somehow reached the log tail.

**(d) Redirect + TQDM exports — inserted after the existing EPS_* export block (gcp.py:728-732), BEFORE the secrets fetch:**

```bash
# === Output redirect (#607): never stream workload output through the
# metadata runner (bufio.Scanner token-too-long kill, incident #491) ===
export EPS_LOG_PATH=<shlex.quote(log_path_for(config, spec.issue))>
mkdir -p <shlex.quote(dirname of log path)>
{ echo "[startup-script] redirecting all further output to $EPS_LOG_PATH"; } 2>/dev/null || true
exec >>"$EPS_LOG_PATH" 2>&1
echo "=== startup-script begin issue=<N> attempt=<attempt_id> $(date -u +%Y-%m-%dT%H:%M:%SZ) ==="
# Defense in depth: no progress bars even into the log file (tqdm
# checks TQDM_DISABLE; vLLM + huggingface_hub bars are tqdm-based).
export TQDM_DISABLE=1
# === /output redirect (#607) ===
```

- `exec >>` (append, whole-script): covers bootstrap output too (uv installer / `uv sync` / git are also pipe writers today), is one line, and cannot be bypassed by a future block edit — vs per-block `{ ... } >>"$LOG" 2>&1` which covers only the wrapped block and breaks `set -e` line attribution (§11-D1). Append (not truncate) preserves prior-boot/relaunch content.
- The two marker comment lines (`# === Output redirect ... # === /output redirect`) are load-bearing: the local integration test slices the prelude at the end marker (§ Tests, T6).
- The redirect sits before secrets fetch/preflight/clone, so the only lines ever on the runner pipe are: the (silent) prelude, one pointer echo, and guarded heartbeats — all tiny and newline-terminated.

**(e) Workload blocks — unchanged content, now executing under the redirect.** The hydra branch (`uv run python scripts/train.py ...`), the workload_cmd verbatim line, the detached-pid wait loop and its echoes, the sentinel `cat`, and `_eps_phase done` all stay byte-wise as-is (modulo the docstring). The `WANDB_PROJECT` default stays workload_cmd-branch-only.

### 4.3 Poll-side: truthful `last_log_mtime_sec_ago` (task item 4)

Piggy-back on the existing single SSH round trip in `_drain_sentinels` (gcp.py:2254-2258) — no new round trips:

```python
tail_stanza = (
    f'echo "{self._LOGTAIL_START}"; '
    + (f"tail -n 30 {shlex.quote(log_path)} 2>/dev/null | cut -c1-4000 || true; " if log_path else "")
    + f'echo "{self._LOGTAIL_END}"'
    + (
        f'; echo "EPS_LOG_MTIME=$(stat -c %Y {shlex.quote(log_path)} 2>/dev/null || echo -1)"'
        f'; echo "EPS_LOG_NOW=$(date +%s)"'
        if log_path
        else ""
    )
)
```

(v2 concern fold-in: the `| cut -c1-4000` bounds each tailed line ON THE VM before it transits `gcloud ssh` — `tail -n 30` is line-counted, not byte-bounded, so a pathological newline-free chunk in the now-real log would otherwise ship in full every poll tick before the Python-side `[:2000]` cap.)

- `_drain_sentinels` parses the two keys with the same regex pattern as `_probe_relaunched_workload` (gcp.py:2459-2462) and returns a 5th element `log_mtime_ago: int | None` (`None` when keys absent/`-1` — old fixtures and missing files keep working).
- `_overlay_drain` (gcp.py:2783) gains optional `log_mtime_ago: int | None = None`; when not None **and** `base.status == "running"`, `replace(base, last_log_mtime_sec_ago=log_mtime_ago)`. Terminal results (`done`/`dead`) keep their existing values.
- No classification change: poll keeps reporting `running` on `phase=workload`; the orchestrator's existing stall heuristics consume the now-truthful number (today it is hardwired `10**9` via `_coarse_poll`). Auto-flipping stale-mtime → `stalled` is explicitly out of scope (false-positive risk on legitimately quiet phases, e.g. a 20-min model load).

## 11. Decision Rationale

- **D1 — Whole-script `exec >>"$EPS_LOG_PATH" 2>&1` vs per-block `{ ... } >> log` vs runner-side `tee`.**
  *What:* one `exec` redirect placed after the env exports, before secrets fetch.
  *Why:* covers every subsequent writer (bootstrap included — uv/git are pipe writers today), cannot be silently bypassed by a future block edit, preserves `set -e` semantics per command (a `{ ... }` group changes failure attribution and would need re-wrapping at every block boundary). `tee` to stdout is disqualified outright: the giant line would still transit the runner pipe.
  *Source:* incident #491 recovery recipe (file redirect was the proven live fix — experimenter memory `feedback_gcp_metadata_runner_token_too_long.md`); upstream guest-agent#149 confirms the pipe itself is the hazard.
  *Alternatives:* redirect-after-clone (rejected — leaves a bootstrap window on the pipe and a second redirect-ordering invariant to police).

- **D2 — Move `log_path` to `{vm_scratch_dir}/logs/issue-<N>.log` via `log_path_for()`.**
  *What:* handle + renderer share one helper; path leaves `$WORKLOAD_ROOT`.
  *Why:* (1) `git clone` into `$WORKLOAD_ROOT` requires an empty target — pre-creating `$WORKLOAD_ROOT/logs` for an early redirect breaks the clone (gcp.py:751-753); (2) unifies with the RunPod canonical top-level log (`runpod.py:124`) and poll_pipeline's "top-level log" exclusion path (poll_pipeline.py:727); (3) puts the log in the same dir the workload_cmd contract already uses for pid files + sentinels.
  *Source:* read from code (gcp.py:1419/1948, runpod.py:124, poll_pipeline.py:727).
  *Alternatives:* keep the old path + redirect after clone (rejected per D1); `git init`+`fetch`+`checkout` to tolerate a non-empty clone target (rejected — touches the clone logic for no added value).

- **D3 — `trap ':' PIPE` (handler) — not `trap '' PIPE`, not nothing.**
  *What:* a no-op handler installed at script top.
  *Why:* local experiments (§2.3, bash 5.1.16): with **no** trap, a bash-builtin pipe write death runs the EXIT trap with `rc=0` → the `-ne 0` guard no-ops → no `phase=failed`, no shutdown — the exact #491 zombie. With a **handler**, the write becomes a normal rc=1 failure → `set -e` → EXIT trap `rc=1` → `phase=failed` + `shutdown` (billing bounded, poll sees `dead`). With **ignore** (`trap '' PIPE`), the parent gets the same protection but children inherit SIG_IGN across exec and `seq | head -1`-style early-close pipelines in workload drivers start failing under `pipefail` (measured: inner rc 141 → 1).
  *Source:* empirical (4 reproducible experiments in this plan, §2.3); bash manual semantics ("signals ignored upon entry cannot be trapped or reset"; trap handlers reset on exec) consistent with the measurements.
  *Alternatives:* `env --default-signal=PIPE` wrapper around the workload under a global ignore (rejected — can't wrap the verbatim workload_cmd without breaking the #588 contract); leaving SIGPIPE default (rejected — leaves the rc=0-trap hole open as generic defense even though the redirect removes the known trigger).

- **D4 — Heartbeats: sparse phase lines on fd 3 + `[phase=...]` lines in the log via the extended `_eps_phase`.**
  *What:* ~4 tiny guarded lines/run on the runner pipe; parser-compatible phase lines in the file.
  *Why:* keeps the serial console minimally useful for early-boot debugging at zero overflow risk; makes the primary-path log parse under the SAME `latest_phase` parser the relaunch probe uses (consistency requirement from the task brief). Poll-readable phase remains the guest attribute — unchanged.
  *Source:* read from code (PHASE_RE poll_pipeline.py:255; `_probe_relaunched_workload` gcp.py:2492); task body item 1 ("keep a small heartbeat ... if useful").
  *Alternatives:* no fd3 channel at all (rejected — loses the only pre-SSH human signal); full log mirroring to fd3 (disqualified — re-creates the kill vector).

- **D5 — `TQDM_DISABLE=1` exported unconditionally in the rendered env.**
  *What:* one export before the workload, both branches.
  *Why:* defense in depth (bars are pure noise in a file; multi-GB logs are a tail/disk nuisance) — tqdm honors `TQDM_DISABLE`, and vLLM's + huggingface_hub's bars are tqdm-based. A workload wanting bars can re-set it inline (workload_cmd runs after the export).
  *Source:* task body item 2; incident lesson ("disable progress bars on non-tty").
  *Alternatives:* metadata-passthrough opt-out knob (rejected — YAGNI); per-script vLLM `disable_tqdm` (out of scope, experiment code).

- **D6 — Poll mtime overlay piggy-backed on `_drain_sentinels`, report-only.**
  *What:* `stat -c %Y` + `date +%s` appended to the existing SSH command; overlay `last_log_mtime_sec_ago` only when `status == "running"`; absent keys → legacy `10**9`.
  *Why:* zero extra SSH round trips per tick; gives the orchestrator a truthful liveness number for the zombie class the redirect can't cover (e.g. OOM-kill of the shell — SIGKILL runs no trap, ever); auto-classification rejected for false-positive risk on quiet phases.
  *Source:* task body item 4 (optional); mtime-probe pattern read from `_probe_relaunched_workload` (gcp.py:2432, 2459-2462).
  *Alternatives:* separate SSH probe per tick (rejected — doubles poll cost); backend-side stalled classification (rejected, see Out of scope).

- **D7 — Snapshot fixture: regenerate in place with updated provenance, keep the test.**
  *What:* deliberate regeneration of `issue588_gcp_startup_hydra_only.json`; docstring updated.
  *Why:* the #588 byte-pin property (workload_cmd feature didn't change the hydra branch) was proven at #588 time and is preserved in git history; the fixture's ongoing value is accidental-drift detection, which survives a provenance-documented regeneration. Structural tests T1-T5 keep it non-tautological.
  *Source:* read from test (test_gcp_backend.py:2104-2123 and the fixture's own header convention).
  *Alternatives:* delete the snapshot test (rejected — loses drift protection); freeze a second fixture and assert a precise diff between old and new (rejected — high maintenance for marginal value over T1-T5 + review diff).
