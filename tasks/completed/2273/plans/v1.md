Text to insert verbatim as a new bullet:

```
- **The fellows-cluster remote login shell is zsh (`/usr/bin/zsh`), where an unmatched glob ABORTS the command it appears in — zsh's `nomatch` is on by default, where bash passes the literal pattern through; worse, a PIPED probe reports `rc=0`, so the abort is invisible to an exit-code check.** The bite is a SINGLE command carrying several glob arguments: `ssh charmander "grep -hoE '<banner>' $S/logs/*.log $S/logs/jobs/*.log | tail -3"` — the second glob matched, the FIRST did not, so zsh skipped the whole `grep` and the directory that DID hold the banner was never read (#1336: one 30-min poll cycle of blind monitoring on a queued 8-GPU job, misread together with a second bad probe as "the run lost its state"; both were probe defects, the run was intact). Measured on charmander: multi-glob single command ⇒ command skipped (rc=1); `<nomatch-glob> | tail` ⇒ pipeline skipped, empty output, **rc=0**; `&&`-chained ⇒ the later command never runs; `;`-chained siblings DO survive — so semicolon chaining is not the hazard, the single command is. RULE: in remote commands prefer glob-free forms that take a DIRECTORY and cannot nomatch-abort — `grep -r <pat> <dir>`, or `find <dir> -name '<pat>' -exec grep ... {} +` (both verified correct at rc=0 on the fixture where the glob form aborted). When a glob is genuinely wanted, `unsetopt nomatch` (equivalently `setopt +o nomatch`) FIRST, or give each probe its OWN `ssh` call so one abort cannot swallow a sibling behind `&&`. COROLLARY (read side): an empty/zero result from a remote probe is UNKNOWN until the probe itself is verified — never a substantive absence claim, the same posture as the `gcloud` rc!=0-is-UNKNOWN-never-empty rule above; note that here even `rc=0` does not clear a piped probe.
```
