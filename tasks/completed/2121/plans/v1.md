## 0.0 TL;DR (plain English)

Two small CLI ergonomics fixes to workflow-helper scripts, both from the
2026-08-05 `/daily` problem sweep.

1. When an agent records "I fixed concern X" with a long explanation,
   `task.py address-concern` currently keeps the first ~200 characters and
   **throws the rest away**, printing a warning nobody reads. On #1739 that
   destroyed 1,589 characters of evidence that exists nowhere else. Fix: the
   inline flag refuses over-long text outright, and a new `--summary-file`
   flag accepts text of any length — storing the full text in a durable
   `evidence` field and a short lead as the summary. Nothing is ever dropped.
2. `clean_experiment_downloads.py` previews by default and deletes only with
   `--apply`, but its sibling janitor is documented as `pod.py cleanup
   --dry-run`, so `--dry-run` gets typed and the script exits 2. Fix: accept
   `--dry-run` as an explicit alias of the default, mutually exclusive with
   `--apply`.

## 1. Goal

No `task.py` concern call path may discard summary text. Every over-cap
summary either (a) hard-errors with an actionable message, or (b) is preserved
in full in the event's `evidence` field. Separately, `clean_experiment_downloads.py
--dry-run` must succeed as an explicit spelling of its default preview mode.

### D2 — `scripts/task.py` (the substantive edit)

`_truncate_summary` (1158-1181) is UNCHANGED — it is still the lead-derivation
helper. What changes is that no call site may reach a state where its returned
`dropped_tail` is discarded.

**D2a — `cmd_address_concern` (1226-1254).** Replace the warn-and-drop block
with a three-branch resolver shared with `cmd_raise_concern`:

```
- summary = args.summary
- if summary is not None:
-     summary, dropped = _truncate_summary(summary)
-     if dropped is not None:
-         print("[task.py] WARNING: ... Dropped tail: ...", file=sys.stderr)
+ summary, evidence = _resolve_concern_summary(
+     inline=args.summary, path=args.summary_file, evidence=args.evidence,
+     command="address-concern",
+ )
  payload = address_concern(..., summary=summary, evidence=evidence)
```

**D2b — new shared helper `_resolve_concern_summary(...)`,** placed next to
`_truncate_summary`. Exactly one non-lossy rule set:

| input | outcome |
|---|---|
| `--summary` ≤ cap | summary verbatim; evidence untouched |
| `--summary` > cap | `SystemExit(2)`: "`--summary` is `<n>` chars (max 200). Shorten it, or pass the full text with `--summary-file <path>` — it is preserved verbatim in the concern's evidence field." |
| `--summary-file` ≤ cap | file text verbatim as summary; evidence untouched |
| `--summary-file` > cap, no explicit `--evidence` | full file text → `evidence`; `_truncate_summary` lead → `summary`; ONE informational stderr line naming both |
| `--summary-file` > cap, explicit `--evidence` given | `SystemExit(2)`: refuses to choose which text survives; names both flags |
| both `--summary` and `--summary-file` | argparse mutually-exclusive error |
| `legacy_shift=True` (raise-concern only), `--summary` > cap, no `--evidence` | R7 path: current behaviour verbatim — full original → evidence, existing warning text unchanged |

The `legacy_shift` parameter is the ONE behavioural asymmetry, and it exists
to hold R7: `raise-concern` is a hot review-round path whose no-evidence
over-cap call currently SUCCEEDS non-lossily, and converting that to a hard
error would exit-2 live reviewer rounds for zero data-integrity gain. Its
lossy twin (`--evidence` supplied) has no such defence and becomes R6's hard
error.

## 6. The three clarifier assumptions — decisions

- **D-A (Assumption 1 — where the substance goes): option (b).** `--summary-file`
  accepts arbitrary length and preserves the full text in a new `evidence`
  field. Option (a) — file channel as pure quoting convenience with the cap
  still binding — was rejected because it leaves the #1739 payload with
  nowhere to go, which is the defect, and because it makes the task's
  specified error message ("hard error *pointing at* `--summary-file`")
  misleading.
- **D-B (Assumption 2 — sibling site): fix both, asymmetrically.**
  `raise-concern`'s LOSSY branch (`--evidence` supplied) becomes a hard error;
  its NON-LOSSY branch is preserved byte-for-byte (R7). Fixing only
  `address-concern` would leave the identical silent-drop reachable one
  subcommand over; converting the non-lossy branch too would exit-2 live
  reviewer rounds for no integrity gain.
- **D-C (Assumption 3 — `--dry-run` shape): mutually exclusive with `--apply`.**
  A silent precedence rule (either flag quietly winning) is the fail-fast
  violation this project bans; argparse's group gives the refusal for free.

## 11. Decision Rationale

The library already hard-errors above 200 chars; only the `scripts/task.py`
wrapper truncates. So the fix moves the CLI toward the library's existing
contract rather than loosening anything, and the 200-char `summary` cap — which
keeps `list_concerns` consumers one-line-readable — is preserved everywhere.
The new `evidence` field is the same additive, only-when-truthy shape
`raise_concern` has carried since inception, so no reader of `concerns.jsonl`
needs to change and no already-written row is invalidated.
