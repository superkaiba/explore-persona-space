```markdown

fit/analysis phase; a fit hang must never strand the store (#825).** When a
run produces a regeneration-costly intermediate (an extraction / activation
store, a teacher-forced capture, an on-policy rollout set — anything whose
recreation costs GPU re-extraction rather than cheap CPU recompute) and a

sequenced BEFORE any long (>~15-30 min) downstream phase begins, or the
upload is LAUNCHED concurrently with the fit (detached/backgrounded — HF
`upload_folder` costs no GPU and overlaps a CPU fit freely). The default
order `extract → fit → upload` parks the entire fit's hang/crash/OOM-kill
risk between the expensive artifact's creation and its persistence: #825
Track-S run 2 hung in a serial CPU MLP fit before `[phase=upload]`,
stranding the turnstore off HF — recovery cost a full fresh GPU
re-extraction. This is the INTRA-RUN sibling of the two #664 sequencing
rules: per-cell upload (bullet above) persists each sweep cell the moment
it completes; pod-release before the final bulk upload (v2 § below) frees
the GPU — this bullet orders store-persist ahead of long fits WITHIN one
run's phase sequence. Plan-side mirror: `planner.md` §9 (the phase sequence
names the upload point of every regeneration-costly intermediate relative
to long fit phases); review enforcement: Methodology lens item 10(i)
data-safety sequencing clause (`.claude/rules/critic-lens-reference.md`).
```

## 11. Decision Rationale

- **~15-30 min threshold for "long".** What: the floor above which a downstream phase must not precede the store upload. Why: consistency — it is the SAME floor CLAUDE.md § Pods, critic item 10(i)-(iv), and planner §9 already use for "long phase" decisions; inventing a second threshold would fork the vocabulary. Source: `critic-lens-reference.md` L236-238 + CLAUDE.md § Pods (in-repo grounding; this is a rule change, not a trained value). Alternatives: a byte-size trigger on the store (rejected — the risk scales with the FIT's wall-time, not the store's size).
- **"Before OR detached-concurrent" rather than strictly before.** What: the rule permits launching the upload concurrently with the fit. Why: HF `upload_folder` costs no GPU and a strict serial upload-first would add wall-time for zero safety gain once the upload is in flight and supervised; the Goal text itself says "(or concurrent with)". Source: task #1396 `## Goal` (verbatim) + upload-policy.md L586 ("incremental shard uploads may overlap compute (they cost no GPU)").
- **Placement of the primary bullet in the main body (not the v2 section).** Why: the main body binds v1 AND v2 ("Everything above still holds", L543-544); the v2 section gets only a one-sentence cross-ref so its "#664 sequencing unchanged" bullet can't be read as exhausting sequencing. Source: upload-policy.md L541-544, L585-586 (read directly).
- **Enforcement inside item 10(i) rather than a new lens item.** Why: (i)'s sequencing clause (b) is the existing home of "uploads scheduled ahead of the phase" — extending it with the data-safety reading composes; a new numbered item would require touching `critic.md`'s roster + the lens-coverage ledger for a one-paragraph concern. Source: `critic-lens-reference.md` L239-252 (read directly).
