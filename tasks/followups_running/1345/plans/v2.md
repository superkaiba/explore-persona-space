# Plan: Issue #1345 — Is the assistant context→answer map the same operator across framings?

## §0.0 TL;DR (plain English)

- I will fit linear context→answer operators in three framing regimes (chat-template, plain User:/Assistant:, and assistant-in-narrative-stories) and test whether the operators are the same linear map in different surface coordinates or genuinely different maps, using held-out R², cross-regime transfer, Procrustes-aligned cosine, and the #825 general-linear reparameterization test.
- I expect the chat and no-template regimes to share essentially the same operator (cross-regime R² near within-regime R², reparameterization succeeds), while the story regime may or may not — with the corpus confound (different text) making a genuine null hard to establish for that comparison.
- What would change my mind: if cross-regime transfer between chat and no-template yields R² substantially below within-regime R² (say, >0.10 drop), that would indicate the operators differ beyond a simple coordinate change; if the reparameterization test also fails for that pair, the case for a genuine map difference becomes strong.

## §1. Goal

**Canonical Goal (Task #1345, verbatim):**
> "Determine whether the assistant context→answer map is the SAME linear operator across three framings holding the assistant persona constant — chat-template, plain User:/Assistant:, and an assistant/AI character in generic narrative-prose stories — via cross-regime operator transfer, aligned operator cosine, and general-linear reparameterization (the #825 Result-2.5 method), in Qwen2.5-7B base and instruct, distinguishing 'same map in different coordinates' from 'genuinely different map per framing.'"

This experiment asks: is the linear structure that maps "assistant processing context" to "answer activations" a single invariant operator, merely expressed in different activation coordinates across surface framings? Or do different framings engage genuinely different computational maps? We test this via three complementary methods: (1) cross-regime transfer (does a map fit in one framing predict answers in another?), (2) operator cosine after Procrustes alignment (are the matrix structures geometrically similar?), and (3) the #825 general-linear reparameterization test (does fitting a change-of-coordinates A·M_j·B⁻¹ ≈ M_i recover the within-regime R²?). The three-framing design holds the persona (assistant) constant while varying surface form, isolating framing as the manipulated variable.

The parent issue #825 established that a linear map exists from assistant context activations to answer activations, with held-out R² = 0.673 (instruct) / 0.588 (base) at layer 19, using chat-template and a naturalistic render format. Key methodological decisions inherited:

## §3. Hypothesis

**H1 (Same-framing, different-coordinate):** The chat-template and plain User:/Assistant: regimes engage the same linear operator up to a change of activation coordinates. Prediction: cross-regime R² (chat→no-template and reverse) is within 0.05 of within-regime R²; reparameterization test recovers within-regime R² for this pair; Procrustes-aligned cosine > 0.7.

**H2 (Story regime: different map):** The assistant-in-narrative-stories regime engages a weaker or genuinely different map relative to chat/no-template. Prediction: within-regime R² for stories is lower than chat/no-template (consistent with #825's ~0.16 for generic stories); cross-regime transfer (chat→story) yields substantially lower R² than within-regime.

**H3 (Corpus confound acknowledged):** The story-vs-chat cross-regime comparison is corpus-confounded (different text, not just different framing), so a story R² deficit is attributable to framing OR corpus OR both. The reparameterization test and Procrustes cosine provide framing-specific evidence beyond the R² comparison.

**Falsification:** H1 is falsified if cross-regime R² for chat↔no-template drops >0.10 below within-regime R² AND reparameterization fails (residual R² does not recover within-regime R²). H2 is falsified if story within-regime R² is comparable to chat (>0.50) and cross-regime transfer to/from stories is also high.

**Registered verdict lattice (chat↔no-template pair, layer 19, mean of both transfer directions).** Define the registered quantities:
- Δ_same = cross_regime_R²(chat↔no-template) − (within_regime_R² − 0.05)
- Δ_reparam = reparam_residual_R²(chat, no-template) − (within_regime_R² − 0.05)
- Δ_diff = cross_regime_R²(chat↔no-template) − (within_regime_R² − 0.10)

DISJOINT and exhaustive: same-operator ⇔ Δ_same ≥ 0 AND Δ_reparam ≥ 0; different-map ⇔ Δ_diff < 0 AND Δ_diff's 95% CI wholly below 0; inconclusive ⇔ otherwise.

(Disjointness note: Δ_same ≥ 0 implies Δ_diff ≥ 0.05 > 0, so same-operator and different-map can never co-fire; the otherwise clause covers every residual cell.)

### Phase 0: Fix GPU device-handling defect in `issue825_fit_cells.py`

**Location:** `scripts/issue825_fit_cells.py`, function `_ridge_predict_cached_batched`, ~line 185.
**Defect:** The function calls `np.asarray(tensor)` on a GPU-resident tensor, causing a `TypeError` when fits run on GPU (numpy cannot convert CUDA tensors).
**Fix (at source, not caller-side):** Add `.cpu()` before `np.asarray`:
```python
# BEFORE (defective):
arr = np.asarray(tensor)
# AFTER (fixed):
arr = np.asarray(tensor.cpu())
```
This fix must land in `scripts/issue825_fit_cells.py` at the source, not worked around in calling code. The fix is committed before any GPU-side fitting phase begins.

**Implementation note:** Also inspect nearby usages in the same file for the same pattern (any `np.asarray(x)` where `x` is a tensor) and apply the same fix to all occurrences.

### Phase 1: Story corpus generation (NEW — Regime R3)

**Goal:** Generate N≈500 short assistant-in-narrative-stories, each with ~5 turns, where the "assistant" is an AI character embedded in generic prose narrative. The character must have a consistent assistant-like answering behavior, enabling a meaningful context→answer pair extraction.

**Reuse clause:** At implementation time, check whether #1335 has produced a fit-for-purpose assistant-in-narrative turnstore before generating new data. Fit-for-purpose means: (a) assistant persona (not fiction character), (b) ≥400 stories surviving quality filter, (c) compatible turnstore format with `scripts/issue825_extract_turnstore.py`. If fit-for-purpose data exists on HF under `superkaiba1/explore-persona-space-data/issue1335_*/`, reuse it; otherwise generate fresh.

**Generation script:** `scripts/issue1345_gen_stories.py` (NEW)

**Elicitation approach (on-policy, Tier 2 — instruct-and-strip):**
- System prompt: "You are writing a short story in which an AI assistant named ARIA is a character. In the story, a person asks ARIA questions and ARIA answers them helpfully and accurately. Write a realistic narrative scene of 300-500 words with 4-6 question-answer exchanges embedded naturally in the prose."
- Strip the system prompt framing before training/extraction; only the narrative text is used for extraction.
- Judge-filter: a brief Claude-sonnet judge pass checks that each story contains ≥4 extractable Q→A turns with distinct questions and substantive answers (not just "ARIA said yes").
- Temperature = 1.0, max_new_tokens = 1024.

**Data-realism tier:** Tier 3 — diverse LLM-generated synthetic. Justified because: (1) no real-world corpus of embedded-AI-character narratives exists, (2) on-policy generation from base/instruct models, (3) diversity enforced by temperature=1.0 and a varied topic seed set. The tier-3 choice is documented as a scope caveat in the clean result.

**Topic seeds:** Draw from #825's existing question bank to keep the question distribution comparable across regimes. This reduces the corpus confound from topic differences (though not from format differences).

**Extraction:** Segment each story into `(narrative_context_before_turn, answer_text)` pairs using a lightweight regex + structural parser that locates dialogue attribution markers (e.g., "ARIA said:", "ARIA replied:"). Each pair becomes one (context, answer) row in the story turnstore.

**Both models:** Generate stories under both Qwen2.5-7B base and instruct (separate story sets to keep per-model turnstores independent). Use vLLM for generation (10-50× speedup vs sequential HF).

**Output:** `data/issue_1345/stories/raw_stories_{base,instruct}.jsonl` (HF upload after generation).

### Phase 3: Matched-n subsampling

Compute n_R1, n_R2, n_R3 after quality filtering. Subsample all three regimes to n_min = min(n_R1, n_R2, n_R3). Keep a fixed random split by conversation/story (FIT_SEED=0) to ensure consistent grouping across arms and layers.

The matched-n subsampled turnstores are saved to `data/issue_1345/turnstores_matched/` (local) and uploaded to HF before fitting.

### Phase 4: Within-regime ridge fitting (both arms, both models, all three regimes)

**Script:** `scripts/issue825_fit_cells.py` (reuse, with Phase 0 GPU device-handling fix applied).

**Input:** Matched-n turnstores for R1, R2, R3 × 2 models × 2 arms (prefix, context).

**Per-cell fit (cell = regime × model × arm):**
- Ridge regression: context activations → answer activations
- GCV λ selection (Gram-space closed-form); compute Gram matrix once per cell, reuse across folds
- 5-fold CV grouped by conversation/story
- Held-out R² (variance-weighted, all 28 layers)
- Shuffle-answer null (20 draws): randomly permute answer rows within each fold, refit, record null R²
- Bootstrap CI (1000 draws)

**Vectorization (MANDATORY — no serial layer loops):**
- All 28 layers are fit simultaneously via batched dual-space ridge (Gram matrix is layer-independent up to the kernel computation; vectorize the GCV solve over layers)
- See `.claude/rules/vectorize-many-cell-fits.md` — use the `vectorized_mlp_skill.py` pattern where applicable; the batched ridge solve is the canonical implementation
- Per-cell: Python launches one batched call that processes all 28 layers together; no Python loop over layers

**Output per cell:** `eval_results/issue_1345/cells_M_{model}_{regime}_{arm}.json` (same schema as `eval_results/issue_825/cells_M_*.json`).

**Launch:** 12 cells (3 regimes × 2 models × 2 arms) run in parallel via process fan-out (one per cell, all GPUs utilized). On a 2-GPU GCP node: 6 cells per GPU in parallel (each cell uses one GPU via `CUDA_VISIBLE_DEVICES`).

### Phase 5: Cross-regime operator transfer (full 3×3 matrix)

**Script:** `scripts/issue1345_cross_regime_transfer.py` (NEW; adapts `issue825_crossmodel_map_transfer.py`).

**Design:** For each pair (regime_i, regime_j), i ≠ j:
- Fit linear map M_i using regime_i's matched-n turnstore (all 28 layers, vectorized)
- Apply M_i to regime_j's held-out contexts (held-out fold from the 5-fold CV split)
- Compute transfer R² (variance-weighted)
- Full 3×3 matrix: 6 off-diagonal transfer pairs × 2 models × 2 arms = 24 transfer fits

**Both arms** computed independently (prefix transfer matrix and context transfer matrix).

**Null:** Compare transfer R² to within-regime held-out R² (from Phase 4). The "same operator" prediction is that cross-regime R² ≈ within-regime R².

**Output:** `eval_results/issue_1345/cross_regime_transfer_{model}_{arm}.json` (3×3 matrices, per layer).

### Phase 6: Operator comparison — Procrustes + reparameterization

**Script:** `scripts/issue1345_operator_comparison.py` (NEW; combines `issue825_map_alignment.py` and `issue825_reparam_directions.py`).

**For each pair (regime_i, regime_j):**

1. **Raw operator cosine:** Flatten the fitted weight matrices M_i and M_j (28 × d × d); compute cosine similarity at each layer.

2. **Procrustes-aligned cosine:** Find optimal rotation R that maximizes alignment between M_i and M_j (solving Procrustes on the matrix as a linear operator); compute cosine after alignment. This tests "same map up to orthogonal rotation of coordinates."

3. **General-linear reparameterization (Result-2.5 method from #825):** Fit A (context-side linear transformation) and B (answer-side linear transformation) such that M_i ≈ A · M_j · B⁻¹. Then apply the reparameterized operator A · M_j · B⁻¹ to held-out contexts in regime_i and compute the residual R². If this recovers the within-regime R², the maps are the same linear operator up to a general coordinate change.
   - Implementation: follow `scripts/issue825_reparam_directions.py` (Result-2.5 method verbatim)
   - Fit A, B via alternating least squares or joint ridge solve (same method as #825)
   - Report: residual_R², delta_from_within_regime_R², Procrustes-aligned cosine post-reparam

**Both arms** computed independently.

**Output:** `eval_results/issue_1345/operator_comparison_{model}_{arm}.json` (per pair, per layer: raw cosine, Procrustes cosine, reparam residual R²).

### Success / kill thresholds (quantitative)

- **Success (H1 Same-Operator for chat↔no-template):** cross-regime R² ≥ within-regime R² − 0.05, AND reparam residual R² ≥ within-regime R² − 0.05

- **Story regime verdict:** within-regime R² for stories (R3) vs shuffle-null; if R3 within-regime R² < 0.20 (below shuffle null threshold), story regime shows minimal linear map

## §7. Decision Gates

No gates — the run is ≤12 GPU-hours, the methodology is pre-verified in #825, and no intermediate signal can shortcut the full regime comparison. The story-regime reuse clause (Phase 1) is the only conditional branch at implementation time, and it requires no gate.

### Kill criteria

- **Story regime dead-on-arrival:** if the story regime's within-regime held-out R² at layer 19 is ≤ the shuffle-answer null 95th percentile in BOTH models and BOTH arms, halt the story-regime cross-regime transfer and operator-comparison phases (Phases 5-6 story pairs) and report the story regime as "no detectable linear map"; the chat↔no-template phases still complete and carry the headline.
- **Story yield floor:** if fewer than 400 stories per model survive the judge-filter + extraction parser after one retry batch (i.e., <80% of the 500-story target), halt story generation and report the yield failure; do NOT backfill with templated stories. Chat↔no-template phases proceed regardless.
- **Phase-0 smoke failure:** if the single-cell smoke run after the device-handling fix still crashes (any unhandled exception in `issue825_fit_cells.py` on GPU), halt provisioning of the full 12-cell fan-out until the fix is corrected.

### Statistical-battery multiplier arithmetic (draw-bearing factors, explicit)

- **Shuffle-answer null battery:** 20 draws × (12 cells = 3 regimes × 2 models × 2 arms) × 28 layers × 5 folds = **33,600 layer-fold-draw ridge solves**. Executed as ONE batched dual-space ridge GEMM per cell (Gram matrix precomputed once per cell and reused across all 20 draws × 28 layers × 5 folds — a shuffle permutes only the answer-side matrix, so all draws share the identical Gram factorization; per `.claude/rules/vectorize-many-cell-fits.md`, no serial per-draw or per-layer Python loop). Per-call basis: ~60 s per cell-level batched GEMM call on A100 at n≈2,500, d=3,584 (dual-space n×n solve, shape taken from #825's fit timing) → 12 cells × 60 s ≈ **12 min total**.
- **Bootstrap CI battery:** 1000 draws × 12 cells × 5 folds = **60,000 draw-fold resamples**. These resample CACHED held-out predictions (no refit — the bootstrap resamples per-conversation R² contributions from already-computed held-out predictions), executed as one vectorized quantile pass per cell at ~2 s per call on CPU → 12 cells × 2 s ≈ **24 s total**.
- Both batteries are absorbed inside the Phase-4 2 h wall budget with wide margin; neither adds a standalone phase.

### API workload estimate

No Anthropic API calls except the judge-filter for story generation (Phase 1):
- ~500 stories × 1 judge call/story × Claude Sonnet = ~500 calls total
- 500 calls is well below the Batch API threshold (~few thousand); use sync dispatch via `api_dispatch.py`
- All calls route through `src/explore_persona_space/llm/api_dispatch.py`

### Parallelization statement (per-GPU-phase)

The 2× A100-80 pod is fully utilized as follows:
- **Phase 1:** GPU-0 generates base-model stories; GPU-1 generates instruct-model stories (independent vLLM instances)
- **Phase 2:** GPU-0 extracts R3 base activations; GPU-1 extracts R3 instruct activations (independent extraction runs via `CUDA_VISIBLE_DEVICES=0/1`)
- **Phase 4:** 12 cells divided evenly: cells 1-6 on GPU-0, cells 7-12 on GPU-1 (process fan-out; each cell is independent)
- **Phase 5:** 24 transfers divided evenly: transfers 1-12 on GPU-0, transfers 13-24 on GPU-1
- **Phase 6:** Operator comparison pairs divided evenly across both GPUs
- No phase holds a GPU idle while the other runs.

### VM RSS estimate

Peak RSS during ridge fitting: all 28 layers × n≈500 × d=3584 × float32 ≈ 28 × 500 × 3584 × 4 bytes ≈ 200 MB per arm — well within `cpu-mid` territory; no routing off VM needed. Fitting stays on GPU (not VM CPU). Peak VM RAM usage is negligible.

### GCP fence

p90 per-cell wall-time: ~30 min. Total with 6 cells/GPU = ~3 h of fitting. Adding extraction and generation: ~6 h total wall. GCP `--max-run-duration` = 24 h (default). No fence adjustment needed.

## §11. Decision Rationale

| Hyperparameter | What | Why | Source | Alternatives considered |
|---|---|---|---|---|
| Layer 19 (headline) | Headline layer for R² and operator comparison | Peak R² in #825 for Qwen2.5-7B (0.673 instruct / 0.588 base at layer 19) | Source: #825 (cells_M_pretrained_assistant_chat.json) | Full layer sweep is also reported; layer 19 is the primary headline |
| N_FOLDS = 5 | Number of CV folds | Group-level (by conversation) CV; 5-fold used in #825 and validated as giving stable R² estimates | Source: #825 (explore_persona_space.experiments.issue_825.common.N_FOLDS) | LOOCV (too slow for ~500 stories), 10-fold (insufficient group count for stories) |
| N_NULL_DRAWS = 20 | Shuffle-answer null draws | Sufficient for p-value estimation at the ~0.05 level; used in #825 | Source: #825 (common.N_NULL_DRAWS) | 100 draws (more precise but 5× slower; not needed for this design) |
| N_BOOTSTRAP = 1000 | Bootstrap CI draws | Standard; used in #825; gives stable CIs | Source: #825 (common.N_BOOTSTRAP) | 500 draws (used in some sibling tasks; 1000 preferred for CI stability) |
| FIT_SEED = 0 | Random seed for subsampling and bootstrap | Consistency with #825 for comparability | Source: #825 (common.FIT_SEED) | Any fixed seed |
| Matched-n subsampling to min(n_R1, n_R2, n_R3) | Sample size matching | Prevents n-difference from confounding cross-regime R² comparisons | Source: CLAUDE.md "equalize-down on per-unit N" standing rule | Keep unequal n with correction — rejected because the correction is more complex than matching |
| GCV λ selection | Ridge regularization | Data-driven λ that doesn't require held-out parameter tuning; used in #825 | Source: #825 (issue825_fit_cells.py Gram-space GCV implementation) | Fixed λ grid search — more expensive and no advantage for this use case |
| Story generation: N≈500 stories, ~5 turns each | Story corpus size | ~500 * 5 = ~2500 (context, answer) pairs; comparable to #825's ~4,724 after the 80% yield floor | Source: #825 (n=4724 conversations); yield floor rule from on-policy-completions.md | 200 stories (too few for 5-fold CV with stable R²), 2000 (4× compute cost) |
| Story generation temperature = 1.0 | Diversity | Standard on-policy sampling temperature for diverse synthetic data | Source: #825 generation scripts; on-policy-completions.md | Temperature 0.8 (less diverse) — 1.0 preferred for tier-3 data |
| Story generation max_new_tokens = 1024 | Generation budget | Sufficient for 300-500 word stories + Q→A exchanges; 2× longest expected training output (per CLAUDE.md `max_new_tokens ≥ 2× rule`) | Source: CLAUDE.md max_new_tokens rule; story length estimate | 512 — too short for 5-exchange stories |
| Tier 2 elicitation (instruct-and-strip) | Story generation method | Strip system prompt; base model does not reliably write Q→A narratives without instruction; tier 2 is lowest tier that fills the quota | Source: on-policy-completions.md #612 elicitation ladder | Tier 1 (bare context — base model would not produce structured narratives reliably) |
| Both prefix AND context mapping arms | Mapping arms | Standing rule: CLAUDE.md "Prefix mapping AND context mapping — BOTH arms in every experiment" | Source: CLAUDE.md Critical Rules (Prefix mapping AND context mapping) | Prefix-only — explicitly prohibited by standing rule |
| Procrustes + reparam comparison | Operator comparison methods | Directly parallels #825 Result-2.5 (reparameterization) and extends to Procrustes (more general) | Source: #825 (issue825_reparam_directions.py, Result-2.5 method) | Raw cosine only — insufficient to distinguish "same-up-to-coordinate-change" from "genuinely different" |
