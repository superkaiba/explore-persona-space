# Plan v5 — Task #642 (amendment): Does the adapter-vs-dense sycophancy bystander-leakage gap survive once learning rate, module coverage, AND data realism are all controlled? (matched-LR, on-policy)

## 0.0 TL;DR (plain English)

<section class="plan-tldr">

- **What I'll run:** My earlier #642 run found that fully fine-tuning a model spreads an "agree-with-the-user" habit into other personas a bit more than the lightweight LoRA method, even when I freeze the extra layers so both touch the same parts of the network. But that run mixed in two nuisances: the two methods used different learning rates, and they both used templated training answers rather than realistic ones. This new run measures the LoRA-vs-full-fine-tuning gap cleanly on one persona (`villain`) with both nuisances removed: both methods train at the *same* learning rate, on *realistic* data the model wrote itself, and are read at the same installed strength. I add two in-between runs so that, **within this villain run**, I can split any gap I measure into "how much is the learning rate worth", "how much is the templated-vs-realistic data worth", and "how much is the genuine method difference".
- **What I expect:** My weak bet is that a gap survives once learning rate and data realism are matched on villain — dense edits should still leave a slightly wider footprint than the LoRA adapter — but I genuinely don't know, which is the point.
- **What would change my mind:** If the within-villain matched-LR on-policy LoRA-vs-cmft gap lands near zero, then the learning-rate and data-realism nuisances accounted for most of the bystander leakage in this villain run, and the method difference itself is below what I can resolve here. Whether the earlier `software_engineer` result reduces the same way is a separate follow-up — that run used a different persona, a different bystander panel, and templated data, so it is not a before/after baseline for this one.

## 1. Goal

Measure whether a LoRA-vs-cmft on-policy bystander-leakage gap survives at matched learning rate on `villain` — and, **within this villain run only**, attribute how much of any measured gap is the learning-rate change, how much is the canned→on-policy data shift, and how much is residual adapter-vs-dense. v3's `+0.073` (software_engineer / #591 panel / canned data) motivates the question but is **not** the quantity being decomposed here: it is a different source, a different bystander panel, and a different (templated) data construction, so it is non-comparable historical context, never a before/after baseline. Concretely: compare LoRA (r=32, α=64, rsLoRA) against the #642 coverage-matched dense FT at a **shared learning rate**, trained on **on-policy** sycophancy completions, read at matched source-install strength s*≈0.50 on the on-policy judge-scored bystander panel.

#642 v3 (MODERATE confidence) split #606's +0.098 gap into `Δ_rank = +0.073` (adapter-vs-dense bundle, same modules) and `Δ_coverage = +0.025` (module coverage, LOW). v3 explicitly flagged that `Δ_rank` still bundles four things on top of pure rank: (a) the learning-rate difference (LoRA 1e-5 vs dense 5e-6), (b) LoRA dropout 0.05, (c) rsLoRA `α/√r` scaling, (d) the `bias='none'` asymmetry. All of #606/#642 also trained on **canned/templated (tier-3)** completions, and #612 showed canned data **overstates install strength** vs on-policy (canned +0.84–0.93 vs on-policy +0.60–0.66 at matched recipe).

This run controls the two largest of those nuisances — the learning-rate difference and the data realism — by training both poles at one LR on on-policy data, and adds the two intermediate arms needed to attribute the change to LR vs data vs residual method **within villain**. The single question: **does any adapter-vs-dense leakage gap survive on villain once learning rate, module coverage, AND data realism are all controlled?**

## 3. Hypothesis

Strength dial (inherited from #606/#642): **s = source-self judge-scored sycophancy rate delta (trained − base)** on the source persona's own panel slot. Matched target **s* = 0.50**, band [0.40, 0.60]; secondary read at s* = 0.65 (lower than v3's 0.75 because the on-policy dose band tops out near 0.63 per #612 — a 0.75 secondary may be unreachable; 0.65 is the realistic upper bracket).

Arms (full names in §5): **Matched-LR on-policy LoRA**, **Matched-LR on-policy cmft**, **Original-LR on-policy cmft** (LR-isolation intermediate), **Matched-LR canned cmft** (data-realism-isolation intermediate). The LoRA pole is shared between the headline and is read against each cmft variant.

Contrasts at s* = 0.50, on the 29-bystander mean (30-panel minus the `villain` source):

- **`Δ_rank_matched` (headline) = Matched-LR on-policy cmft − Matched-LR on-policy LoRA** (same modules, same LR, same on-policy data; varies the adapter-vs-dense bundle MINUS the LR confound and MINUS the data-realism confound). This is the cleanest adapter-vs-dense read the project has produced. It still carries dropout 0.05 + rsLoRA scaling + the `bias='none'` asymmetry + the LoRA-vs-dense initialization regime (§8).
- **`Δ_LR` (within-villain decomposition) = Matched-LR on-policy cmft − Original-LR on-policy cmft** (same data, same modules; varies dense LR 1e-5 → 5e-6). Measures, within this villain run, how much of the measured matched-LR LoRA-vs-cmft gap is worth in LR.
- **`Δ_data` (within-villain decomposition) = Matched-LR canned cmft − Matched-LR on-policy cmft** (same LR, same modules; varies data construction canned → on-policy). Measures, within this villain run, how much is worth in data realism.

Both decompositions are **within-villain** — they attribute components of the matched-LR LoRA-vs-cmft gap measured HERE, on this source / panel / data. They do not attribute v3's `+0.073` (different source / panel / data); whether the `software_engineer` result decomposes the same way is a separate follow-up (§13).

Pre-registered decision rule (mirrors v3 §3, on the NEW arms):

- **H_survives (a method gap survives all controls on villain):** `Δ_rank_matched` CI excludes 0 with point ≥ +0.04. → the adapter-vs-dense footprint difference is structural on villain, not a LR or data-realism artifact; reinforces the case for LoRA as a leakage-limiting default even at matched recipe (directionally consistent with 2410.21228 / 2405.09673).
- **H_artifact (the villain gap was LR + data nuisances):** `Δ_rank_matched` CI ⊂ (−0.04, +0.04) (does not separate) AND at least one of `Δ_LR`, `Δ_data` separates with point ≥ +0.04. → most of the within-villain matched-LR LoRA-vs-cmft gap is the matched-out nuisances; the residual method difference is below the project's resolution at this power.
- **H_indeterminate:** `Δ_rank_matched` does not separate by ≥ +0.04 with CI excluding 0 AND neither `Δ_LR` nor `Δ_data` separates → reported as noise-limited (kill criterion §7), never rounded to a null. (The within-run LoRA-vs-cmft gap may itself be smaller than #606's because on-policy installs weaker; this is a power statement, not a method claim.)

Threshold ±0.04: inherited from #642 v3 (`Source: #642 v3`) so the new contrasts are read on the same scale as the +0.073 / +0.025 v3 reported (a scale match, NOT a claim the v3 numbers are comparable across the source/panel/data change); it is below v3's `Δ_rank` (+0.073) and above the determinacy noise floor (0.05 plug-in-vs-bootstrap per contrast).

Jointly satisfiable: the three positive branches + the indeterminate branch partition the outcome space with no contradictory thresholds on any shared contrast (no gate demands `Δ ≥ +x` and `Δ ≤ −y` on the same read).

## 4. Design

**Manipulated variables (vs #642 v3's reused poles), with attributing arms.** Two variables move (matched LR + on-policy data). The four-arm design keeps each effect attributable within villain:

| Arm (plain-English name) | LR | Data | Modules/rank | Role |
|---|---|---|---|---|
| Matched-LR on-policy LoRA | 1e-5 | on-policy | LoRA r=32 adapter | headline LoRA pole |
| Matched-LR on-policy cmft | 1e-5 | on-policy | cmft dense | headline cmft pole — reads `Δ_rank_matched` vs the LoRA pole |
| Original-LR on-policy cmft | 5e-6 | on-policy | cmft dense | LR-isolation (reads `Δ_LR` vs the headline cmft) |
| Matched-LR canned cmft | 1e-5 | canned (#411 templates) | cmft dense | data-realism-isolation (reads `Δ_data` vs the headline cmft) |

The two intermediate cmft arms each change exactly ONE variable from the headline cmft arm (LR for one, data for the other), so the partition is decomposable within villain: `Δ_rank_matched` is read at matched LR + on-policy; `Δ_LR` and `Δ_data` say how much of the within-villain matched-LR LoRA-vs-cmft gap is each nuisance. This is the smallest arm set that answers the headline cleanly AND attributes the change (per the consistency-checker's same-issue-followup rule + the data-realism / on-policy / contrastive-negatives rules). The canned-cmft arm uses #411's villain canned templates (reused, §4.7) spliced onto #612's on-policy negatives, to mirror the positive-completion construction #606/#642 used.

### Install-strength control (cross-condition leakage comparison — REQUIRED)

The headline IS a cross-condition leakage comparison (4 training arms), so raw-rate comparison is dose-confounded by default. ## 7. Decision Gates

Two gates (justified: wall > 4 h AND the matched-LR + on-policy + dense regime has NO exact prior trajectory — only bounded by #612/#606 — AND a cheap install signal can rule out an expensive full run):

- **Install-pilot gate (after Phase 0.5, PRE full train):** proceed to Phase 1 full train iff, at the pilot coarse grid `{4,12,22,44}`, (a) NO dense arm installs s ≥ 0.50 by step 4 (the #606 refusal-collapse signature; a step-4 s ≥ 0.50 means the matched LR is too hot for that arm → fire the fallback ladder for that arm only), AND (b) the LoRA arm shows monotonic install toward s ≥ 0.40 within the grid. Grounding (sign + threshold): #606 sycophancy dense at 5e-6 took 12-16 steps (no 4-step collapse); #612 villain on-policy LoRA at 1e-5 reached s≈0.64 by step 44 — both predict PASS at the chosen grids; the gate exists for the residual matched-LR risk that the canned-cmft arm at 1e-5 (canned dose 0.88) installs too fast. On FAIL for an arm: fire that arm's §4.11 fallback ladder (one pre-authorized LR retrain). The matched-LR pair (`loraOP_lr1e5` + `cmftOP_lr1e5`) MUST stay at the SAME LR — if the matched LR is too hot for the dense pole, BOTH headline poles drop to the next LR together (5e-6) to preserve the matched-LR contract; the original-LR-on-policy-cmft arm then becomes the matched headline cmft and a new 5e-6 LoRA pole is trained. (This is the one pre-authorized matched-LR shift, decided here, not at experimenter discretion.)
- **Install gate (after stage-A, per arm):** proceed to stage-B for an arm iff it brackets s*=0.50 with non-degenerate selected cells, OR (no bracket) reaches endpoint s ≥ 0.50 (band-entry fallback read §4.11). On FAIL (an arm neither brackets nor reaches endpoint ≥ 0.50 after the fallback): report install-failure for that arm; the contrasts that need it are not computed (reported as exactly that — no silent extrapolation).

These two gates are jointly satisfiable with the §3 decision rule by construction: no gate demands `Δ ≥ +x` and `Δ ≤ −y` on the same read; the install gates concern the source-self dial, the decision rule concerns bystander contrasts.

**Kill criteria (pre-registered design-failed outcomes):**
- (a) **Matched-LR window does not exist for the headline pair** = after the pre-authorized LR shift (1e-5 → 5e-6), the dense pole still either 4-step-collapses or never reaches s ≥ 0.50 while the LoRA pole brackets (or vice versa), so no shared LR brackets both → report "no matched-LR window for villain on-policy sycophancy at the available LRs", publish both arms' trajectories, do not compute `Δ_rank_matched`. (Low likelihood — the two LRs span the #606/#612 viable range.)
- (b) **Uninterpretable partition** = NONE of `Δ_rank_matched`, `Δ_LR`, `Δ_data` separates from 0 by ≥ +0.04 with CI excluding 0 → reported as noise-limited (the within-run gap may be smaller than #606's because on-policy installs weaker; a power statement, NOT "method/LR/data all don't matter").
- (c) **Parity-anchor failure** = re-judged villain on-policy cell rates drift from #612's published rates beyond ±0.08 (hard ±0.15) → the reuse/judge regime is broken; report untrustworthy with the drift published.

## 11. Decision Rationale

Grouped by recipe (one Source per unique value). The shared recipe is the #606/#642 v3 recipe held fixed; the new load-bearing choices are the matched LR, the source switch, and the on-policy/canned data construction.

Alternatives: matching at 5e-6 REJECTED as primary (the LoRA arm at 5e-6 may install too slowly on weaker on-policy data — untested, higher risk of not bracketing) — but 5e-6 IS the pre-authorized fallback for the headline pair if the install-pilot flags a 1e-5 dense collapse (§7).
