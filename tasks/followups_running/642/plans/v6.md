# Plan v6 — Task #642 (amendment): Does the adapter-vs-dense sycophancy bystander-leakage gap survive once learning rate, module coverage, AND data realism are all controlled? (matched-LR shifted to 5e-6 after the v5 pilot-gate FAIL)

## 0.0 TL;DR (plain English)

<section class="plan-tldr">

- **What I'll run:** Last round I set up a clean head-to-head between the lightweight LoRA training method and full dense fine-tuning on one persona (`villain`), with both trained at the *same* learning rate, on *realistic* data the model wrote itself. Before committing the expensive run, a quick cheap install-pilot checked that both methods would learn the trait gradually at the shared learning rate. It came back bad. At the planned shared rate the dense method learned the trait so fast it had basically saturated by training step 4, and the LoRA method overshot and then drifted back down instead of climbing steadily. So the shared rate I picked was too hot. The pre-agreed fix (decided in last round's plan, not invented now) is to drop *both* methods to a gentler learning rate together so they stay matched, then run the clean comparison there. I reuse the dense run that already passed at the gentle rate and train one new gentle-rate LoRA run plus one small extra arm so I can still say how much of any gap is the realistic-vs-templated data.
- **What I expect:** My weak bet is unchanged — a gap probably still survives once the methods are matched on the gentler rate and on realistic data, but I genuinely don't know, which is the point.
- **What would change my mind:** If the matched gentle-rate gap lands near zero, then the earlier difference was mostly the learning rate and the data, not the method. I also lose one of my two "how much was the learning rate worth" side-reads this round — the dense method couldn't be cleanly trained at the original hotter rate at all (it saturates in 4 steps), so that comparison is no longer runnable. I report that as a real result, not a silent drop: the two methods simply cannot be matched at the hotter rate.

</section>

- **Install-pilot gate (after Phase 0.5, PRE full train; re-run on the NEW arms only):** proceed to Phase 1 full train iff, at the pilot coarse grid `{4,12,22,44}`, (a) the new `cmftCN_lr5e6` arm does NOT install s ≥ 0.50 by step 4 (the #606 refusal-collapse signature — extremely unlikely at 5e-6, the v5 `cmftCN_lr1e5` read s=0.285 at step 4 and 5e-6 is slower), AND (b) the new `loraOP_lr5e6` arm shows monotonic install toward s ≥ 0.40 within the grid. `cmftOP_lr5e6` is exempt (v5-gate-PASSed; gate-validation reuse). Grounding (sign + threshold): the v5 pilot showed `cmftOP_lr5e6` PASSes at 5e-6 (s {4:0.110, 12:0.785}, no collapse); #612 villain on-policy LoRA at 1e-5 reached s≈0.64 by step 44, so at the halved 5e-6 the LoRA pole installs slower but should still bracket within 132 — both predict PASS. On FAIL for an arm: fire that arm's §4.11 fallback ladder (one pre-authorized LR retrain). **The matched pair (`loraOP_lr5e6` + `cmftOP_lr5e6`) MUST stay at the SAME LR — the v5 §7 pre-auth shift to 5e-6 has already been spent (this is v6), so a SECOND shift is NOT pre-authorized; if 5e-6 is also unworkable for the matched pair, that is kill criterion (a) (no matched-LR window for villain on-policy sycophancy at the available LRs) — report it, do not silently shift again.**
- **Install gate (after stage-A, per arm):** proceed to stage-B for an arm iff it brackets s*=0.50 with non-degenerate selected cells, OR (no bracket) reaches endpoint s ≥ 0.50 (band-entry fallback read §4.11). On FAIL (an arm neither brackets nor reaches endpoint ≥ 0.50 after the fallback): report install-failure for that arm; the contrasts that need it are not computed (reported as exactly that — no silent extrapolation).

These two gates are jointly satisfiable with the §3 decision rule by construction: no gate demands `Δ ≥ +x` and `Δ ≤ −y` on the same read; the install gates concern the source-self dial, the decision rule concerns bystander contrasts.

**Kill criteria (pre-registered design-failed outcomes):**
- (a) **Matched-LR window does not exist for the headline pair at 5e-6** = the v5 §7 pre-auth shift (1e-5 → 5e-6) is already executed in this plan, so 5e-6 is the LAST pre-authorized LR. A THIRD LR is NOT auto-authorized (a second shift would be a new manipulation — autonomous-mode re-plan via `/adversarial-planner` per §13, NOT an experimenter-discretion shift). Low likelihood — the v5 pilot already PASSed the dense pole at 5e-6 and #612 brackets the LoRA pole.
- (b) **Uninterpretable partition** = NEITHER `Δ_rank_matched` NOR `Δ_data` separates from 0 by ≥ +0.04 with CI excluding 0 → reported as noise-limited (the within-run gap may be smaller than #606's because on-policy installs weaker; a power statement, NOT "method/data don't matter").
