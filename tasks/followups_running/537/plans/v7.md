## 4. Design

Two stages: (A) a base-model teacher-forced forward-pass pass producing per-context realization-conditioned artifacts (the only GPU work), then (B) two additive metric-registry rows + the scoring re-run (CPU, off-pod) + the collinearity diagnostic.

### 4.0 The predictor definitions (single variable)

Both predictors are **directional** matrices `D[i,j]` over the 16 shared-instance contexts `train_cids_for(behavior)` = `[sp_swe, sp_doctor, sp_ph1, sp_ph2, wc_short_code, wc_short_advice, wc_long_write, icl_k2, icl_k8, reph_imp, reph_polite, reph_casual, fmt_json, fmt_code, default, binst_<behavior>]`. `D[i,j]` reads "trained at context i (`v_S`), evaluated at context j (`v_T`)", matching the harness convention (`metric_matrix` docstring). The harness scores `D` against the existing `G[i,j]` on this 16×16 block via LTCO CV — so the predictors need values ONLY on these 16 contexts (not the full 30 eval contexts). This makes the forward-pass pass cheap: each realization span is scored once per context (16 contexts × 5 behaviors), not once per cell.

Define `R_b` = the set of behavior-realization completions for behavior `b` (§4.1). For each context `c` in the 16, and each realization `r ∈ R_b`:

- `ℓ_b(c, r)` = `score_span_logprob(base_model, tok, [build_prompt(ctx_c, probe_r, tok, behavior=b, icl_demos)], span=r_text)[0]["span_logp_mean"]` — length-normalized base teacher-forced log-prob of the realization span under context `c`'s prefix.
- `P_b(c, r, t)` = the base next-token distribution at each realization-span token position `t` under context `c`'s prefix (full-vocab softmax of the teacher-forced logits at the span positions).

Then:

- **Predictor (1) — behavior-conditioned logprob difference (PRIMARY):**
  `D1[i,j] = mean_{r ∈ R_b} ( ℓ_b(ctx_j, r) − ℓ_b(ctx_i, r) )`.
  Polarity contract (harness requires "larger = more distant"): the predictor is a *similarity* signal (a small/negative difference means the eval context already log-likes the realization about as much as the train context → expect MORE leak), so the registered distance is `D1_dist[i,j] = −D1[i,j]` (sign pinned in the registry note, exactly like `base_prior_bystander`'s `-base` polarity). The sign is finalized at the harness wiring and asserted against the fact-row direction (more leak ⇔ eval-ctx log-likes the realization).

- **Predictor (2) — behavior-conditioned JS (SECONDARY):**
  `D2[i,j] = mean_{r ∈ R_b} mean_{t ∈ span(r)} JS( P_b(ctx_i, r, t) ‖ P_b(ctx_j, r, t) )`.
  Symmetric in (i,j) by construction (JS is symmetric); registered as a symmetric distance row (larger JS = more distant → expect less leak), same polarity convention as `gauss_kl_act`.

Predictors (1)/(2) are computed on the BASE model only — they are PRE-training predictors scored against the realized post-training G, never DVs.

- **Predictor (3) — context-axis behavior-vector projection (Persona-Vectors-style).** ONE per-behavior direction `v_b` (constant across the row's 16 contexts — exactly right for a context-axis predictor: `v_b` supplies the behavior direction, the per-context projection supplies the context variation), extracted by the standard Persona-Vectors method (arXiv 2507.21509; #623 pipeline): `v_b@L = mean(pos activations @L) − mean(neg activations @L)` over behavior-positive vs neutral prompts at layer L ∈ {6,14,22,27} (the #537 G2 layer set). Then per eval context `c` on the same row, two TRACKS scored separately (never pooled, #532):
  - **SHIFT track (PRIMARY for predictor 3):** `proj_shift(c)@L = <Δh(c)@L, v_b@L> / ‖v_b@L‖`, where `Δh(c)@L` = the trained−base readout-slot activation delta under eval context `c` at layer L. The 16×16-block form: `D3_shift[i,j]@L = <Δh_{adapter i}(ctx_j)@L, v_b@L>/‖v_b@L‖` — the predictor for cell (i→j) reads how far the adapter trained at i, evaluated at context j, moves along the behavior direction. (NB this uses the trained adapter's per-context delta, so the SHIFT track is a POST-hoc predictor in the harness's "post-hoc track" sense — flagged as such, parallel to `rank1_proj_*`.)
  - **LEVEL track (pre-training):** `proj_level(c)@L = <h_base(ctx_c)@L, v_b@L>/‖v_b@L‖` — base-model activation under context c projected onto `v_b`; a genuine pre-training predictor (no adapter). As a context-axis distance for the harness it enters as the directional difference `D3_level[i,j]@L = −( proj_level(ctx_j)@L − proj_level(ctx_i)@L )` (higher base projection at the eval context ⇒ more leak ⇒ less distant; polarity pinned like predictor (1)/`base_prior_bystander`).
  - Both tracks are computed from REUSED on-HF artifacts (the `activation_deltas/` trained+base npz for the shift track, the `clouds/` base activations for the level track) — the ONLY new GPU is `v_b` extraction. Report the best layer + the per-layer sweep; the shift/level tracks are scored as SEPARATE leaderboard ids.

### 4.1 Behavior-realization definition per behavior (the load-bearing design choice; grounded in §11)

"Behavior realization" must be a FIXED completion (or token span) teacher-forced identically under both context prefixes. The realization differs by behavior because the behaviors differ in what "expressing the behavior" means; each choice is grounded in §11 and surfaced as an assumption.

| Behavior | Realization span `R_b` | Source of the span text | n realizations |
|---|---|---|---|
| Marker | the ` ※` marker token (id 83399) appended after a fixed base greedy answer at the slot | reuse `marker_base_slots/` frozen base answers + the marker token; `score_marker_slots` 1-token-span path | 32 (the marker eval probes; 1-token span each) |
| Taught fact | the canonical fact sentence ("the main courtroom inside the Elk County Courthouse … has seven wooden benches for public seating.") | `elicitation/fact.json` instruction span = the fact span already used in `fact_span_tf` | 1 span × 30 fact eval probes (prefixes) → averaged |
| Refusal | the judge-positive on-policy diagonal refusal completions (one per probe) | `raw_completions/refusal/<diag>_seed42/<diag>.json` `generations[probe][0].text`, filtered to judge-positive (refused) | up to 40 probes |
| Sycophancy | the judge-positive on-policy diagonal agreement completions | `raw_completions/sycophancy/default_seed42/default.json` (judge-positive agreement) | up to 25 probes |
| EM | the judge-positive on-policy diagonal misaligned completions | `raw_completions/em/binst_em_seed42/binst_em.json` (Betley-positive) | up to 8 probes × samples |

**Realization-span construction rule (frozen before the forward-pass pass):** for marker and fact the realization is canonical and behavior-defining (the controlled marker token / the taught fact span) — these are the CLEAN reads. For refusal/sycophancy/EM there is no single canonical span, so the realization is the model's OWN judge-positive diagonal on-policy completion per probe (one fixed text per probe, taken from the existing diagonal raw_completions), teacher-forced identically under every context's prefix. This keeps the realization on-policy (it is text the base/trained model actually produced when expressing the behavior) and avoids canned templates. The exact diagonal cell used as the realization source per behavior is pinned at §11 and frozen in the pass's manifest. **Coverage caveat carried forward:** the refusal row's implants were too weak to read in the parent (noise-limited); its predictor read is reported but flagged as low-coverage texture, exactly as the parent G row is.

### 4.1c Persona-vector `v_b` extraction (predictor 3; the only new GPU beyond §4.2)

The elicitation files (`eval_results/issue_537/elicitation/<b>.json`) ship the behavior `instruction` + `eval_probes` + `judge_prompt` per behavior, but do NOT ship pos/neg contrastive prompt pairs (verified by reading the JSON keys). So `v_b` extraction BUILDS the pos/neg pairs the #623 way: pos = a held-out probe set under the behavior's positive instruction (the `instruction` string, e.g. "You are sycophantic…"); neg = the same probes under a neutral/contrastive instruction (the bare default assistant, the project's neutral). Following #623 (`scripts/issue623_extract_sycophancy_vector.py`, the arXiv 2507.21509 "extraction pipeline"): generate a few rollouts per (probe, pos|neg instruction), judge-retain pos-expressing / neg-non-expressing rollouts where a judge is cheap (sycophancy/refusal/EM/fact; marker uses the slot read directly), teacher-force each retained rollout through the HF model capturing the readout-slot residual at L ∈ {6,14,22,27}, and set `v_b@L = mean(pos activations@L) − mean(neg activations@L)`. This is a handful of forward passes per behavior (the #623 default was ~20 extraction questions × 10 rollouts × 2 conditions), ~0.3 GPU-h total across 5 behaviors. Output: `eval_results/issue_537/behavior-conditioned-predictors/persona_vectors/<behavior>.npz` (keys `v_b_layer_6/14/22/27`, fp32). **Extraction-validity note:** `v_b` is checked for sign + magnitude per layer (a degenerate near-zero `v_b` means the behavior didn't separate pos/neg at base — flagged per behavior, parallel to #623's K2 HALT); marker's `v_b` is `W_U[※]`-aligned by construction (the contentless direction), reported as the floor anchor.

**Realization-spans + `v_b` neutral prompt are disjoint from the eval probe sets** to avoid contamination (the extraction probe pool is the dedicated demo-seed pool / a held-out split, never the 30 eval probes), pinned in §11.

```python
                              "n_span_tokens": lp["n_span_tokens"],
                              "token_dists": dist})        # fp16, span positions only
        out_p.write_text(json.dumps({**meta(), "behavior": behavior, "cid": cid,

```

`score_span_token_dists` is a thin sibling of `score_span_logprob` in `i537_marker_eval.py` that, instead of gathering the span-token log-probs, returns the full-vocab softmax at each span position (fp16, span positions only — bounded size: ~25 spans × ~23 tokens × 152k vocab × 2 bytes ≈ a few hundred MB/context worst case; only needed for predictor (2), and only the JS between two contexts is kept, so store per-context distributions, not pairwise). To bound storage, store top-k (k=512) logprobs per position + a tail mass term for the JS approximation (standard sparse-JS), OR store the full distribution at fp16 and delete after the JS matrix is built — implementer's choice, validated at the smoke (the marker 1-token-span case is trivially small; fact/refusal/syc/EM spans are the size driver).

**Smoke = the sweep with one cell** (UNIFICATION DEFAULT): `scripts/i537_bcond_predictors.py --behaviors marker --cids default,sp_swe --smoke` runs the same in-process functions on 1 behavior × 2 contexts, exercising the span-logprob, token-dist, AND `v_b`-extraction paths, before the full pass. No subprocess wrapper.

### 4.4 Why code, not a model call?

(a) Alternative: a single Claude call to "rate how much context j licenses behavior b' given context i."
