## 0.0 TL;DR (plain English)

- **What I'll run:** The first run of this experiment built a big table of "train the model on behavior A, how much does behavior B leak out" and then asked whether a cheap *before-training* signal could predict each cell. The simplest geometry signals (how similar two behaviors look inside the model, measured as the distance between their average activations) failed that test on held-out behaviors. This time I throw the whole toolbox of smarter signals at the same table — distances that account for the *spread* and *shape* of each behavior's activation cloud, not just its center, plus a signal that measures how differently the model would *talk* under one behavior versus another. I don't retrain anything: the leakage table and all 60 trained models are reused exactly. I find the single best signal honestly (leave-one-behavior-family-out), then ask a sharper question: does a *different* signal win for different behaviors, and is that variation real or just luck from trying 100+ signals on a handful of behaviors per family?
- **What I expect:** A covariance-aware or "how the model talks" signal is my best shot at transferring where the plain center-distance failed — but I expect the per-family winners to look impressive and mostly evaporate once I compare them against a chance baseline, because there are very few behaviors per family. I expect the honest held-out winner to still be the embarrassingly simple "does prepending this behavior's data make the other behavior more likely" signal from the first run, or noise.
- **What would change my mind:** If a shape-aware or talk-divergence signal cleanly beats noise on held-out behaviors, then the first run's "geometry doesn't transfer" headline was too harsh — it was *raw center-distance* that failed, not geometry itself, and the headline needs that correction. If instead different behaviors reliably want different signals beyond what chance explains, that's a real finding that one universal leakage predictor doesn't exist.

## 3. Hypotheses (pre-registered, falsifiable)

- **H1 (transfer — the headline):** Over the development off-diagonal cells (137 cells), under the existing frozen **leave-family-out CV with nested champion selection**, at least one NEW covariance-aware (centered-centroid / mahal_pooled_ctx / gauss_kl) or distributional (JS / KL-either-direction) Group-A predictor achieves a held-out weighted-τ whose **family→row cluster bootstrap 95% CI excludes 0** AND whose **within-family row-label permutation p < 0.05**. **Transfers** = both hold AND the LFO mean-τ point estimate ≥ 0.10 (a weak but non-noise rank signal). **Does not transfer** = CI spans 0 OR permutation p ≥ 0.05 (raw centroid geometry's v1 outcome — the null this extension tests against). **Calibrate τ against the v1 reliability ceiling, not absolutely (Nit N3):** the target matrix is noisy — the v1 seed0↔seed137 target reliability is Spearman ≈ **0.588 raw / ≈ 0.740 Spearman-Brown-adjusted** — so a perfect predictor cannot exceed ≈ that ceiling. A transfer is therefore read as a FRACTION of the ceiling (e.g. a τ of 0.10 is ≈ 0.14-0.17 of the attainable signal, weak; a τ approaching ~0.4-0.5 would be a strong transfer relative to the ~0.59-0.74 ceiling), and the ceiling is printed beside the H1 τ in the leaderboard. The 0.10 absolute floor is the non-noise gate; the ceiling-fraction is the effect-size interpretation. Either outcome is a reportable finding: transfer → the v1 "geometry doesn't transfer" headline is revised to "raw centroid distance doesn't, but covariance/distributional geometry does"; no-transfer → the headline strengthens to "no before-training geometry of any kind transfers, raw or covariance-aware."
- **H2 (per-family heterogeneity exceeds chance):** The cross-family variance of the per-family champion held-out τ exceeds the selection-noise null (§6 analysis 3) at permutation p < 0.05. **Real heterogeneity** = observed cross-family τ-variance above the 95th percentile of the family-label-shuffled null. **Chance** = within the null band → "the per-family winners are selection noise; no reliable predictor×family interaction" (the predicted-likely outcome given ~6–31 cells/family). Falsified-either-way reportable.
- **H3 (optimism trap — single global champion vs per-family oracle):** The per-family-oracle held-out gain (sum over families of the best-on-that-family predictor's held-out τ) minus the single-global-champion held-out τ is **inside** the selection-noise null band (i.e. the apparent per-family advantage is the optimism of argmax-over-100-predictors-per-tiny-family, not real specialization). A gain ABOVE the null band → genuine per-family specialization (surprising, reportable). This IS the v1 pooled-vs-LFO finding, now per family.
- **Secondary (descriptive, not confirmatory):** per-metric-family dev leaderboard (which metric family ranks highest on pooled dev τ); the centered-vs-raw centroid delta (does global mean-centering — the #536 bank-centering lesson — lift centroid geometry off the v1 floor); the JS/KL direction asymmetry as a diagnostic.

**Kill criterion (when do we conclude every predictor zoo extension also fails to transfer?):** if H1 returns "does not transfer" for EVERY new metric family (centered-centroid, mahal_pooled_ctx, gauss_kl, JS, KL-both) AND H2 returns "chance" AND H3 is inside the null band, the conclusion is the strong negative: **no before-training predictor of any kind in the #493+JS/KL zoo transfers to behavior leakage, and there is no reliable predictor×family structure** — the v1 headline strengthens. This is a determinate finding, not a failure. There is NO GPU re-run escape: the matrix is fixed, so a null here is the answer, not a prompt to retrain.

**`delta_spec` paired-probe invariant (Blocker-1 fix — choose A).** `#493 _delta_spectrum` is a covariance-spectrum distance that is well-defined only between **matched/paired clouds drawn from the SAME probe IDs in the SAME order** (the spectrum subtraction is meaningful only when the two clouds index the same conditioning items). The row demo / NL-elicitation cloud and the column-probe cloud are NOT guaranteed paired in this design (different item sets, different order), so an arbitrary-order finite `delta_spec` could win the expanded zoo and falsely revise the v1 headline. **Constraint (hard precondition, §4.1):** `delta_spec` is computed ONLY for cells where both behavior clouds are built from an identical, ordered probe-ID set (the shared fixed ≥50-probe set used for the JS/KL family — the only construction in this design that pairs the two sides by probe). For any (row, column) cell whose two clouds are not so paired, `delta_spec` is recorded `None` (omitted from the cell dict — see the §10 serialization contract) and reported N/A; it cannot be a champion for those cells. **Runtime assertion (§10):** for every cell where a non-`None` `delta_spec` is written, `assert probe_ids_a == probe_ids_b` (same IDs, same order) before the spectrum subtraction; a mismatch HALTs (fail-fast, never a silent forced value). The other cloud metrics (mmd, c2st, wass2, gauss_kl) are pair-order-invariant (set-level two-sample distances) and carry no such constraint.

**Row `demos` / `nl` cloud construction (Blocker-1 fix).** The v1 `predictors.py` (lines ~389-391) builds the row `demos` flavor as ONE concatenated `demo_text` (a single sample → not a cloud); the row `nl` flavor is a single NL-description string (also one text). Neither yields a cloud as-is, so cloud metrics over them would silently degenerate. **Decision (option chosen): build truly per-demo / per-elicitation clouds (`n_samples > 1`), do NOT concatenate.** Mechanics: (i) row **`demos`** flavor — extract one rep per demo (the K=8 demos as 8 separate texts, NOT one concatenation) → an 8-point row cloud; (ii) row **`nl`** flavor — sample ≤8 base-model temp-1 responses under the row's NL-description conditioning context → an ≤8-point row cloud (the small elicitation GPU pass in §9). A cloud with `< 4` points (or fully degenerate per the #493 guards) records cloud metrics as `None` (omitted from the cell dict — the #493 `end_of_system` / `_finite_and_non_constant` precedent), never a forced value. The column side already has a per-probe cloud (≥50 probe reps). This makes every cloud metric a genuine cloud-vs-cloud read on both flavors; the v1 single-`demo_text` concatenation path is NOT reused for cloud metrics (it remains intact for the v1 centroid path, which is byte-identical-preserved by the default-False flag).

### 4.3 The selection-noise null (fully specified — scope §b)

The dominant risk: ~6–31 cells/family × argmax over 100+ predictors → a spuriously perfect per-family winner by chance. Two coupled null constructions, both PINNED before any zoo τ is read:

**(i) Bootstrap — which predictor wins per family + held-out-τ stability.** A **stratified family→row cluster bootstrap, B=2000 resamples, seed 545**, reusing the v1 `_family_row_bootstrap` two-stage structure (families with replacement, then rows within each sampled family — cells within a row share an adapter, rows within a family share corpus lineage). The Claude critic verified `_family_row_bootstrap` (`scoring.py:143`) is already cluster-correct in the v1 code — this section PRE-REGISTERS the algorithm; it does not change the code's behavior.

**Bootstrap-vs-LFO family-ID invariant (Blocker-3 fix — the bootstrap is NESTED inside leave-family-out scoring for analysis 1 / H1 / H2).** When the family-cluster bootstrap is nested inside leave-family-out (LFO) held-out scoring, a single bootstrap resample can sample the SAME original family more than once (families are drawn with replacement). If those duplicate copies are allowed to straddle the LFO train/heldout boundary — one copy in the champion-selection train set, another in the held-out fold — the held-out τ leaks training information and the H1/H2 CIs are falsely narrowed (or, symmetrically, inflated), which could flip "transfers" vs "does not transfer." The held-out unit is the ORIGINAL family, not the resample copy:

**Two distinct family sets, defined ONCE, never conflated (Codex-r2 fix):** the LFO-mean estimand (H1 global champion + H2 heterogeneity) folds over ALL 9 dev families — `lfo_families` — because §6/line 175 read H1/H2 on the full dev set; the H3 `eligible_families` (= 6) is a STRICTLY SMALLER subset bound to H3 only (the families clearing the ≥4-held-out-cell nested floor, §4.3 lines below). Iterating the LFO bootstrap over `eligible_families` would silently drop B7/B9/B10 from the H1 read and could flip a near-threshold "transfers" verdict.

```text
# Define ONCE near the top of §4.3(i), before any zoo tau is read:
lfo_families      = {B1, B2, B3, B5, B6, B7, B8, B9, B10}   # all 9 dev families — the LFO-mean scope (H1/H2)
eligible_families = {B1, B2, B3, B5, B6, B8}                # the 6 dev families clearing the >=4-held-out-cell nested floor (H3 ONLY)
assert eligible_families <= lfo_families                    # H3 scope is a subset of the LFO scope

# per resample b (LFO-mean estimand, H1/H2): for each held-out original family F in lfo_families:   # all 9, NOT eligible_families
#   1. resample = two-stage cluster draw over lfo_families   (all 9 families w/ replacement, rows within)
#   2. TRAIN set  = all resampled cells whose ORIGINAL family id != F   # excludes ALL copies of F
#   3. HELDOUT set = the original (un-resampled) cells of family F      # F is held out as one unit
#   4. select each group's champion on TRAIN, score it on HELDOUT, record held-out tau
#   5. INVARIANT (assert, per resample, per fold):
#        assert set(train_original_family_ids) & set(heldout_original_family_ids) == set()   # no F copy leaks in
#        assert n_distinct_original_families(train) >= 2                                       # champion-selectable
#      a resample/fold violating either is SKIPPED and counted in a `skipped_resamples` tally (reported)
#   6. COVERAGE INVARIANT (written to the bootstrap output schema, H1 read cannot silently drop families):
#        assert lfo_families == dev_families                # all 9 dev families folded; a re-run that drops one HALTs
```

Per resample (for the per-family-WIN-share + per-family-τ-CI estimands, which are NOT LFO-folded — see the estimand split below): recompute each family's argmax-predictor and its held-out τ. Report (a) the bootstrap distribution over WHICH predictor wins each family (a stable winner → its share ≫ uniform-over-zoo; a noise winner → the share is diffuse, near 1/K); (b) the bootstrap 95% CI of each per-family champion's held-out τ (CI excluding 0 = the family has a real predictor; CI spanning 0 = the per-family win is selection noise).

**Estimand → bootstrap-type split (Blocker-3 fix, explicit):**
- **Per-family argmax CI** (analysis 2 — each family's own champion + its within-family held-out τ): use a **within-family ROW/CELL bootstrap** (resample rows/cells INSIDE the one family; NO family-level resampling). There is no LFO boundary here — the estimand is scoped to a single family — so the family-ID exclusion invariant does not apply; the unit is the row within that family.
- **LFO-mean CI** (analysis 1 / H1 / H2 — the global-champion and heterogeneity reads that fold over held-out families): use the **family-cluster bootstrap WITH the family-ID exclusion invariant above** (`train_original_family_ids ∩ heldout_original_family_ids = ∅`, `n_distinct_original_families(train) ≥ 2`).

B=2000 (not 1000) because the statistic is an **argmax/selection quantity** whose tail is noisier than a mean — Davison & Hinkley (1997, *Bootstrap Methods and Their Application*, §2.5/§5) recommend ≥1000 for percentile CIs and more for tail/selection statistics; v1's prereg used B=1000 for the margin-CI mean statistic, doubled here for the selection target.

**(ii) Permutation — does cross-family heterogeneity exceed chance.** A **within-column row-label permutation test, P=10000 permutations, seed 545** (the v1 comparison spec's permutation mechanic): permute the row labels WITHIN each eval column (preserving each column's marginal target distribution and the within-column z-norm), then recompute the analysis-3 cross-family τ-variance statistic on the permuted matrix. The observed statistic's percentile in the 10000-permutation null gives the exact finite-sample p for H2 (heterogeneity > chance). For H3, the same permutation null is recomputed for the per-family-oracle-gain-minus-global-champion statistic. Within-column row-label exchangeability is the correct null: under "no predictor×family structure," which family a cell belongs to carries no information about which predictor orders it, so shuffling row→family assignment within a column destroys exactly the heterogeneity signal while preserving column marginals.

**Optimism-trap measurement (the H3 statistic):** `gain = Σ_family τ_heldout(per-family-oracle champion on that family) − τ_heldout(single global champion on the union)`. A large gain that is INSIDE the permutation null band = the per-family advantage is pure argmax optimism (the predicted-likely outcome). A gain ABOVE the band = genuine specialization. Both reported with the percentile.

**H3 `eligible_families` invariant (Blocker-4 fix — the oracle sum, the global-champion term, AND every permutation replicate are computed on ONE common family set + cell subset).** The H3 gain is a difference of two τ-sums; if the per-family-oracle term and the single-global-champion term (or any permutation replicate) are evaluated over different family sets, the difference is meaningless (it would conflate a coverage difference with a specialization gain). So:
1. **Define `eligible_families` ONCE, before any H3 τ is read:** the dev families that clear the **≥4-cell nested-split floor** the per-family held-out read needs. The sparse families (B7=7, B9=6, B10=7 dev cells) that cannot support a ≥4-held-out-cell nested split are EXCLUDED from `eligible_families` (reported descriptive-only, §6/§8) — they enter neither term of the gain nor the permutation null.
2. **Compute every H3 component on `eligible_families` and the matching cell subset:** the oracle sum `Σ_{F ∈ eligible_families}`, the single-global-champion term scored on `⋃_{F ∈ eligible_families} cells(F)`, and every one of the P=10000 permutation replicates — all over the SAME `eligible_families` and the SAME cell subset.
3. **Runtime invariant (written to the H3 output file):**
   ```text
   assert set(oracle_families) == set(global_eval_families) == set(permuted_eval_families) == set(eligible_families)
   assert oracle_cell_subset == global_cell_subset == permuted_cell_subset   # identical cell index set
   ```
   A violation HALTs (fail-fast). The `eligible_families` list + the excluded descriptive-only families are recorded in the H3 output for the §6/§8 reporting.

**Statistical hygiene:** the per-family champion's held-out τ is scored on cells held out *within* the family (a nested split inside each tiny family where ≥4 cells allow, else the family is reported descriptive-only with its small-n flagged AND excluded from `eligible_families`); the heterogeneity statistic is never correlated back against the per-family τ it is computed from.

## 7. Decision gates

**No gates — short run / pre-verified path.** Wall-clock is ~3–5 h (1× H100 extraction) + CPU analysis; total ~9 GPU-h, well under the 4-h/16-GPU-h gate threshold. The matrix is fixed (no training to abort), the metric engine + JS-RB harness + scoring harness are all pre-validated code, and a null result is a determinate finding (the kill criterion in §3), not a reason to stop early. The only procedural check is a smoke (one row × one column × one metric of each family through the dispatcher) confirming the predictor JSONs land in the v1 schema and `scoring.py` consumes them — a harness-integrity check, not a kill gate.

**Decision-rule clause — capacity/N confound for a cloud-metric "transfers" verdict (Nit N2).** A cloud metric (MMD / C2ST / Wass2 / Gaussian-KL) sees MORE data than a centroid (the full N-point cloud vs one mean vector), so a cloud-metric H1 "transfers" could reflect a plain DATA-BUDGET advantage rather than the cloud's *shape/spread* information being what predicts leakage. **Rule:** a cloud-metric "transfers" verdict is read as evidence that *distributional geometry transfers* ONLY if the **centered-centroid** variant (same single-vector data budget as raw centroid, but with the #536 mean-direction removed) ALSO moves off the v1 raw-centroid floor in the same direction. If the cloud metric transfers but centered-centroid stays at the floor, the verdict is downgraded to "covariance/cloud transfers, but the gain is confounded with data budget — cannot attribute it to shape vs N" (a covariance-evidence-only read, carried as a scope caveat). This clause is a reporting/attribution rule, not a kill gate.

**Decision-rule clause — read τ against the v1 reliability ceiling (Nit N3).** The H1 transfer decision uses the absolute 0.10 non-noise floor for the binary CI/permutation gate, but the *effect-size interpretation* of any transfer is read as a fraction of the v1 target-reliability ceiling (Spearman ≈ 0.588 raw / ≈ 0.740 Spearman-Brown-adjusted, seed0↔seed137). The leaderboard prints the ceiling beside each champion's τ; a transfer near the 0.10 floor is labeled "weak (≈ 0.14-0.17 of the attainable signal)," and "geometry transfers strongly" is reserved for a τ that is a large fraction of ≈ 0.59-0.74. This is an interpretation rule, not a kill gate.

```python
# preflight (CPU, pre-GPU) — issue545_metric_race.py::prefetch_pinned_inputs()
# The downloaded HF file lands in the HF CACHE (content-hashed path); the v1 loader
# resolves corpus_read_path(<rel>) -> corpora_dir() / <rel> -> data/issue545/corpora/<rel>.
# So we MUST materialize each cache file to production_corpora_dir() / <rel>, then assert
# the loader resolves to exactly that file — a download alone never reaches where the loader looks.
from huggingface_hub import hf_hub_download
from explore_persona_space.experiments.behavior_testbed_545 import (
    corpus_read_path, production_corpora_dir,
)
import hashlib, json, os, shutil, sys
from pathlib import Path

PINNED_REV = "96ccf2ecf87c575ba6d8a0c2334da0f4e9c37f8e"   # resolved main SHA, planning pass 2026-06-16
REPO = "superkaiba1/explore-persona-space-data"
MANIFEST = "eval_results/issue_545/metric_race/expected_sha256.json"   # {hf_path: sha256}, written this pass
# manifest keys are FULL HF paths "issue545_behavior_testbed/corpora/<rel>"; strip the prefix to
# get the LOADER-relative <rel> (e.g. "demos/sycophancy.json", "warmth.jsonl").
PREFIX = "issue545_behavior_testbed/corpora/"
# 13 demos/*.json (incl. INDEX.json) + 18 corpora/*.jsonl = 31 files, enumerated above
expected = json.load(open(MANIFEST))
prod_root = production_corpora_dir()   # respects EPM_CORPORA_DIR override (per the v1 loader)
prod_root.mkdir(parents=True, exist_ok=True)
for hf_path, want in expected.items():
    assert hf_path.startswith(PREFIX), f"unexpected manifest entry shape: {hf_path}"
    rel = hf_path[len(PREFIX):]        # loader-relative path, e.g. "demos/sycophancy.json"
    target = prod_root / rel           # production_corpora_dir() / <rel> — where corpus_read_path looks
    target.parent.mkdir(parents=True, exist_ok=True)
    cached = hf_hub_download(REPO, hf_path, repo_type="dataset", revision=PINNED_REV)  # pins the revision
    if target.exists():
        target.unlink()
    try:
        os.link(cached, target)        # hardlink (cheap, same fs)
    except OSError:
        shutil.copy(cached, target)    # fallback (copy across fs)
    got = hashlib.sha256(open(target, "rb").read()).hexdigest()
    if got != want:
        sys.exit(f"HALT: {hf_path} sha256 {got} != expected {want} @ {PINNED_REV}")  # fail-fast, no GPU spend
    # the loader resolves <rel> via corpus_read_path; assert it now points at the materialized file
    loaded = corpus_read_path(rel)
    assert loaded.resolve() == target.resolve(), f"HALT: {rel} resolves to {loaded}, not {target}"
print(f"prefetch OK: {len(expected)} files materialized at {prod_root} @ {PINNED_REV}, all sha256 + path-resolve match")
```
