## 0.0 TL;DR (plain English)

- **What I'll do:** Add one written rule that says a multi-phase GPU experiment shouldn't keep a giant 8-GPU pod running while it's doing a step that only needs one GPU (or no GPU at all, like waiting on an API). Provision the big pod only for the step that actually needs all the GPUs.
- **What I expect:** Three workflow docs (planner, critic, the project CLAUDE.md) gain a short "right-size the pod width per phase" rule, mirroring the existing "don't hold a GPU pod for a CPU-only phase" rule and using the same ~15–30 min time threshold.
- **What would change my mind:** If the new rule contradicted the existing "one big pod for a wide parallel sweep" guidance, or if a reviewer showed the re-provision cost of a second pod usually outweighs the idle-GPU savings for realistic phases — then the threshold would need rethinking.

## 11. Decision Rationale

N/A — no model training; no load-bearing hyperparameters. The one load-bearing engineering choice is the threshold:

- **What:** narrow GPU phase `> ~15–30 min` AND `<< peak width` → downsize/release; short phases may hold the wide pod.
- **Why:** ties directly to the Goal (avoid idle-$ on a peak-width pod during narrow phases) while not over-provisioning a second pod for churn. Matched to the existing CPU-only-phase ~15–30 min floor so the two rules use one consistent threshold and a reader learns one number.
- **Source:** `#778` (origin incident — gpu-idle-advisory 38 min at ≤5% util on 8× H100); `#664` (sibling idle-spend, the CPU-only-rule incident); the existing `planner.md` §9 CPU-only ~15–30 min floor (in-repo prior art).
- **Alternatives:** (a) no threshold (always downsize) — rejected: re-provision latency + supply-constraint exposure makes it wrong for short phases; (b) a different threshold than the CPU-only floor — rejected: divergent numbers confuse the reader and the task body pins consistency with the ~15–30 min floor.
