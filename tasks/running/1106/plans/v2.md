### 11. Decision Rationale

- **Rung position (b2), before (c).** *What:* insert between (b) and (c) rather than appending after (e) or renumbering. *Why:* the escalation is logically "content mitigation failed → try the model axis → only then give up on subagents"; and a non-renumbering label keeps the "(d)"/"(e)" pointers (issue-tick SKILL.md, bank-read hook + test) valid with zero sibling edits, and avoids #1104's incoming "(f)". *Source:* task-body diff sketch + this session's pointer grep. *Alternatives:* renumber (c)→(d) etc. — rejected, breaks 3+ downstream label citations; append at end — rejected, wrong escalation order (it must fire BEFORE (c)).
- **`"sonnet"` as the pin target.** *What:* the rung names `model: "sonnet"` specifically. *Why:* it is the exact pin #1092 validated (v25→v27), and the v25 marker notes the refusal text itself recommended Sonnet; a generic "another model" would send future orchestrators experimenting mid-incident. *Source:* #1092 `epm:progress` v25/v27. **Single-incident-grounded (n=1 A/B)** — honest limitation; the rung's inline evidence note makes the grounding legible so a future contradicting incident can revise it.
- **"Twice" as the trigger threshold.** *What:* the rung fires after two same-model kills TOTAL — the original spawn plus rung (b)'s one rephrased retry, spelled out verbatim in the v2 trigger text (reconciled statistics Must-Fix: the v1 wording "twice … despite the rephrased/thinned brief" could be read as two post-rephrase kills, unsatisfiable under (b)'s retry-ONCE cap). *Why:* mirrors the ladder's existing "(c) if a thin wrapper refuses twice" threshold — one kill can be pure stochastic bad luck (v25: kills are stochastic), two kills incl. a thinned-brief retry is the point where content mitigation is demonstrably not working; matches #1092's actual timeline (the model switch came after kills 2→3, and the rung places it one kill earlier than #1092 needed). *Source:* existing rung-(c) threshold symmetry + #1092 timeline. Single-incident-informed.
- **ONCE-per-task cap.** *What:* the pinned re-spawn is a single attempt, not a loop. *Why:* mirrors rung (b)'s "retry ONCE" discipline — the ladder's design principle is one bounded attempt per rung, then escalate; an unbounded model-switch loop would burn spawns exactly the way the ladder exists to prevent. *Source:* rung (b) text; #1092 needed exactly one.
- **Doc rung, not mechanization.** *What:* prose rule only; no hook/counter. *Why:* the trigger state ("how many refusal kills so far this task") lives in orchestrator context, not in any machine-readable surface; mechanizing would be a new subsystem — out of scope for this fingerprint. *Source:* workflow-fix scope rules. *Alternative:* a `verify_*`-style check — nothing to check mechanically.
