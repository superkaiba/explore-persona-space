## 0.0 TL;DR

- **What I'll run:** I train the same base model many separate times — once for each combination of (a) which persona it's trained under, (b) which behavior I'm teaching it (a hidden marker, bad medical advice, insecure code, sycophancy, refusal, a made-up fact), (c) whether I also show it counter-examples of *not* doing the behavior, and (d) how hard I push the training. Then for every trained copy I record both how strongly the behavior shows up where I taught it and how much it bleeds into 50 other contexts it was never trained on.
- **What I expect:** The behaviors will install where trained, and how far they spread will vary a lot across the 50 contexts and across behaviors — that spread is the raw material the later phases need. I expect the marker and the made-up fact to spread in a structured, predictable way and the content behaviors (sycophancy, bad advice) to be messier, consistent with what we've seen before.
- **What would change my mind:** If a behavior installs but shows zero variation in how far it bleeds across the 50 contexts, or if a whole family of trained copies fails to install at all, that would mean this measurement phase didn't produce usable ground truth and I'd have to fix the training recipe before the later phases can run.

## 3. Hypothesis

Phase 2 is a **measurement / store-build**, not a hypothesis test. Its role: *produce the trained store + the ground-truth leakage that Phases 3-4 use to test A3.6–A3.10 and the end-to-end predictor.* Falsifiable success/kill conditions (the analogue of a hypothesis here):

- **Confirms its role** iff: (a) every grid cell installs the behavior on its source (above the manipulation-check floor), at a **non-saturated** dose for the marker (`g_logprob ∈ [5,12]` nat, bystanders below the argmax ceiling); (b) the leakage DVs show **cross-context variation above the per-cell noise floor** on at least the marker + fact + EM spines (the predictable behaviors per #637) — variation read on the PRIMARY `ĝ^real` activation gate (continuous, non-emission; at lr 5e-6 emission is flat 0 per `.claude/rules/marker-training-recipe.md`), over the **49 bystander contexts** (C′ ≠ C; see kill (b) for the source-anchor exclusion); (c) the store is populated for all realized cells on the **50-context activation spine** (`ĝ^real`, the marker four-float slot, all 28-layer tensors) AND on the **design-doc §7.5 judging surface** (the applicable 19-column registry on the primary context per model + the `ROBUSTNESS_COLUMNS` subset on extra context families — §6.4), not a full 50×19 cross-product; (d) `δ` (positive-only) and `δ^contra` (contrastive) are both recorded so A3.7 has its clean identification arm.
- **Falsifies its role (kill criteria):** (a) a whole behavior-family fails to install at the non-saturated dose after the retry budget (no usable ground truth for that family); (b) a trained store with **no leakage variation** on the marker/fact spines, read on the PRIMARY `ĝ^real` activation gate over the **49 BYSTANDER contexts only (C′ ≠ C)** against the **within-context independent-probe-split (R≥8) noise-floor estimator** (design-doc §1.7 lines 615-618). The C′=C source point has `ĝ^real(C)=1` by construction — it is the manipulation anchor, reported separately, NEVER counted in the variation read (a source-only-install / zero-bystander-leakage store has nonzero 1.0-vs-49-zeros variance and would FALSELY pass otherwise). The within-context probe-split is the binding kill estimator (the natural choice for a single-store kill; the cross-seed test-retest estimator of §1.7 lines 560-562 is not powered at the realized N=2 seeds). If both floors are reported and materially disagree, flag the divergence — but the probe-split floor is binding. No variation above this floor ⇒ the gate has nothing to predict — a measurement, not a model, failure → diagnose recipe before Phase 3; (c) the marker spine saturates and cannot be band-stopped into `[5,12]` nat (the §1.5 anchor-strength precondition fails → the gate's dynamic range is gone, #448).

### Why code, not a model call?

N/A for the bulk — the eval judge IS a model call (Claude Sonnet 4.5, Batch API). The activation-gate scorer `ĝ^real`, the rank-one SVD, the marker three-space slot read, and the on-policy-rate aggregation are deterministic linear-algebra / tensor reductions over stored activations: a code path is required because they are exact numerical operations on `d=3584` residual tensors with no natural-language judgment, run at fleet scale (thousands of cells × 28 layers) where a model call is both wrong (no text to judge) and infeasibly slow. The judge-scored behavior rate IS the model call.

### Marker / behavior-implant stopping recipe (overrides parent parity)

The marker spine trains FRESH, so the stopping recipe comes from `.claude/rules/marker-training-recipe.md`, NOT a non-marker parent's recipe:

- **lr = 5e-6** (the over/under dial; lr ≥ 1e-4 → unconditional `※`-repeater); strength bought through STEPS, not rank.
- **marker + end-of-turn loss** (`MarkerOnlyDataCollator(tail_tokens=0)`): positives loss on `{ ※, <|im_end|>, \n}`, negatives loss on `{<|im_end|>, \n}` at the post-response slot.
- **`MarkerBandStopCallback`** armed, **non-saturated band `[5,12]` nat** (the #537/#474 validated band; eval every 5 steps, min 10, overshoot-aware, 3-epoch ceiling). The stronger dose (≥2-dose requirement) targets the upper band edge via a longer step budget at the SAME lr (NOT a higher lr) — concretely a `[10,16]` nat band-stop, kept BELOW saturation (bystanders must stay below the argmax ceiling).
- **Band-unreachable cells** (high-base-prior context, e.g. the behavior-instruction column — not in this grid's source set, so N/A here): step-matched to the median reachable stop-step.
- **Smoke-verifiable saturation guard:** distinct per-source WandB run names (`issue664_<cell>_seed<S>`), ≥1 logged in-loop band-trajectory point per source, the band-stop branch exercised on the smoke cell. Marker token assert at every entrypoint: `tokenizer.encode(" ※", add_special_tokens=False) == [83399]`.
- **Marker-extraction read gauge.** Training uses rsLoRA `use_rslora=True` (effective train scale `α/√r ≈ 11.31`, #601 establishment — and because every cell is trained fresh, the artifact-reuse (g) application-scaling parity probe is N/A). The trained-adapter marker-extraction READ gauge is PINNED in §11 (Option A: read at the same faithful `use_rslora=True` gauge, safe because the band-stop `[5,12]`-nat regime — not the gauge — sets readability) and validated by the §10 pre-launch smoke-cell readability assert (trip → fall back to Option B staged `α/r=2.0` read). ### 6.2 Install-strength control (cross-condition leakage comparison)

The B5 arm contrast (contrastive vs positive-only) and the dose axis are cross-condition leakage comparisons, and install strength is condition-dependent (#601: contrastive lengthens the schedule → stronger install). So §6 registers install-controlled reads:

- **Matched-install comparison:** compare arms/doses at checkpoints with matched source gain (findable from the per-step band-trajectory / dose checkpoints).
- **Leakage as a fraction of install** per (source→bystander) cell, computed in the **non-saturating EOS-margin logit space** `Δ(z_marker − z_eos)` for the marker — NEVER raw `log P` (softmax compression inflates the fraction at saturation). Never correlated back against install itself (#383 X-vs-(X−Y) artifact).
- **Leakage-vs-install dose curves** from the ≥2-dose checkpoints (preferred — subsumes the single fraction, catches nonlinear onset).

The primary DV definitions in 6.1 are unchanged; these are the cross-condition reads layered on top.

### 9.2 Backend lane

- **Lane choice: `auto` (GCP-first).** The router walks GCP A100-80 → A100-40 → spot → SLURM. `lora-7b` intent maps to `a2-ultragpu-1g` (1× A100-80) per cell. No sentinel-file dependence in the dispatcher (the fleet driver uses HF/WandB upload signals + the orchestrator poller, not pod-side `/workspace` sentinels), so `auto` is safe — "no sentinel dependence — auto-safe."
- **A100-vs-H100 wall scaling:** the #537/#658 bases were measured on H100; the A100-80 auto-lane is ~1.5-2× slower per step for LoRA 7B. The 88 GPU-h figure is the work (lane-invariant for the cost gate); wall-time on A100 fans to ~2-3h with sufficient GPU count.
- **24h fence reconciliation:** worst-case wall (P2.0+P2.1+P2.2 ≈ 4.5h + buffer) is far under GCP's 24h `--max-run-duration` fence even with the seed-1042 arm. No phase-split needed. No `backend: runpod` override (no 70B intent, no >24h run, no mid-run SSH-MCP orchestration required beyond the standard experimenter pattern).
- **Merge-disk budget:** trained extraction reads the LoRA adapter applied to base weights. If extraction merges, the high-water mark = 1 merged Qwen-2.5-7B (~15 GB) per concurrent cell per GPU. At ≤8 concurrent cells/pod that is ~120 GB — UNDER the RunPod MooseFS ~130 GB per-pod quota but tight; on GCP A100 the per-node scratch is larger. **Mitigation:** extraction loads the adapter via PEFT WITHOUT a persisted merge where possible (apply-in-memory), or merge-read-delete atomically per cell. The implementer asserts `n_concurrent_merges × 15 GB < scratch_quota` and uses cleanup-as-you-go.

## 16. Implementation contract: canonical battery routing

> **Why this section exists (the r1→r3 failure pattern).** Three implementer rounds shipped a per-column / per-behavior battery ROUTING function (`issue664_common.column_probes`) built from manual `if column in (...)` special cases plus a generic `fetch_preregistered_probes(48)` fallback, and Codex caught a different wrong-battery misroute on a different sibling surface each round (r2: sycophancy/refusal store extraction on the generic 48 probes; r3: `harmful_compliance`→Betley-8 where the #545 registry mandates AdvBench-200, and `deception`/`self_report`/`persona_drift`/`format_style`→generic-48 where each has its own #545 battery). The reconciler's calibration: "per-KEY helper reused as per-ENTRY router" — sibling-scan blindness. The strategy is BRITTLE BY CONSTRUCTION: a manual router silently mis-handles every column it forgot a special case for. §16 removes the failure mode mechanically — there is exactly ONE resolver, every column self-routes via its own `ColumnSpec.battery`, and the only escape hatch is a single declared override dict that a pytest enumerates. The key fact the manual router ignored: **each `ColumnSpec` in the #545 registry already carries its own `battery` filename** (`columns.py` L82-265), so `eval_battery.battery_probes(COLUMNS[col])` already returns the CORRECT frozen battery for every column — no per-key routing is needed at all.

### 16.1 Single canonical resolver

`canonical_battery_for_column(column: str) -> list[dict]` is the ONLY allowed function that maps a #545 column name → prompt battery. It MUST:

1. Check `ISSUE_664_BATTERY_OVERRIDES` (§16.2) FIRST; if `column` is a key, return that provider's battery.
2. Otherwise delegate to the #545 registry: `eval_battery.battery_probes(COLUMNS[column])` — where `COLUMNS` is `behavior_testbed_545.columns.COLUMNS` (a `dict[str, ColumnSpec]`) and `battery_probes` is `behavior_testbed_545.eval_battery.battery_probes(column: ColumnSpec, *, cap=None) -> list[dict]` (verified at `src/explore_persona_space/experiments/behavior_testbed_545/eval_battery.py` L87; each `ColumnSpec.battery` is the frozen battery JSON the column self-routes to — `harmful_compliance`→`advbench_200.json`, `deception`→`deception_episodes.json`, etc.).

The return type is `list[dict]` (the `battery_probes` probe-item shape, `[{"probe_id", "question", ...}]`). Both the override providers and the registry fallthrough return this shape. Call sites that need flat question strings extract `[item["question"] for item in canonical_battery_for_column(column)]` — they do NOT add a second routing layer. A sibling per-behavior helper `canonical_battery_for_behavior(behavior: str) -> list[dict]` maps a #664 behavior → its PRIMARY #545 registry column (via the existing `BEHAVIOR_REGISTRY_PRIMARY_COLUMN` table) and returns `canonical_battery_for_column(that_column)` — it adds NO routing of its own. The `smoke` short-circuit (returning `SMOKE_QUESTIONS[:2]`) is the ONE allowed non-registry path and is exercised only when `smoke=True`; it is NOT a per-column branch and the §16.4 AST test exempts it explicitly.

Both the trained-store activation-extraction path (`issue664_extract_store`) and the judged-rate eval path (`issue664_eval`) call `canonical_battery_for_column` / `canonical_battery_for_behavior` — so the activation surface and the judge surface are IDENTICAL by construction (this closes the r2 B6 defect mechanically; see §13.1 Store-completeness).

### 16.2 Override mechanism

Any LEGITIMATE #664 override (B6 — overriding a #545 column to point at a #664-specific frozen pool) MUST be declared in a SINGLE module-level constant dict at the TOP of `scripts/issue664_common.py`:

```python
ISSUE_664_BATTERY_OVERRIDES: dict[str, Callable[..., list[dict]]] = {
    # refusal: score on the #390 refusal-REQUEST pool the source persona is
    # trained to refuse on (the frozen P2.0 pool / inlined #390 battery), NOT
    # the registry's XSTest/OR-Bench refusal_panel — the store + judge must key
    # on the SAME requests the refusal positives were elicited on (B6).
    "refusal": _override_refusal_390_pool,
    # sycophancy: score on the Sharma wrong-claim user turns (the SAME
    # `wrong_claim` strings the training positives + judge key on), NOT the
    # registry's sycophancy_claims battery (B6).
    "sycophancy": _override_sycophancy_sharma_wrong_claims,
    # fact_expression: score on the #444 diversified fact-question templates
    # (the SAME templates the taught-fact positives use), NOT the registry's
    # fact_battery (B6 taught-fact carve-out).
    "fact_expression": _override_fact_444_templates,
}
```

Each override value is a callable returning the `list[dict]` probe-item shape and carries a one-line `# why` comment (above, mirroring the existing `column_probes` per-key docstring justifications). The canonical resolver checks this dict FIRST, then falls through to the #545 helper. **No other manual special-case routing is allowed anywhere in the code.** Decision on the columns the r3 misroute touched: `harmful_compliance`, `deception`, `self_report`, `persona_drift`, `format_style`, `broad_em`, `fam_expr_bad_medical` are NOT overrides — they resolve through the #545 helper (their `ColumnSpec.battery` is already correct: AdvBench-200, deception-episodes, self-report, persona-drift, format-questions, Betley-main-8, fam-expr-bad-medical respectively). The `marker` column is its own #545 column battery (`marker_eval_questions.json`) and is handled by the marker-slot path, not the judge path; the judging-surface builder drops it (it has no judge call) — verify whether `marker` is reached by the resolver at all on the eval path, and if so confirm it resolves canonically (NOT an override).
