# Plan — issue #834: Vectorize the null-battery draw/layer loops (pure numpy, seed-preserving)

`kind: infra` · 0 GPU-h · VM-local CPU code change · `### TDD: no`

## 1. Goal + quantitative acceptance criteria

Vectorize the Python-level draw/layer loops in
`src/explore_persona_space/analysis/null_battery.py` into batched
einsum/GEMM numpy ops so a 1000-draw 4-null battery (the #778 shape:
L=28, D=3584, n≈200–1000, K=1000 draws, n_boot=10,000) runs in minutes,
not hours — while preserving the public API and the seed/draw semantics
EXACTLY (same seed → same random draws → statistically identical
outputs).

**Acceptance criteria (all must hold):**

1. **Equivalence:** for every vectorized function, output matches the
   current loop implementation on the same inputs + seed within
   `np.allclose(new, old, rtol=1e-10, atol=1e-12)` on the float64 path.
   Bit-exactness is NOT required for the reduced arithmetic (matmul
   reassociation reorders float additions); the RNG draw sequences
   themselves (permutations, Z vectors, bootstrap index rows) MUST be
   bit-identical (`np.array_equal`) because they are generated in the
   exact current consumption order.
2. **NaN semantics preserved:** size<3 / zero-denominator Pearson → NaN;
   zero-norm direction → zero projections; within-condition groups with
   `mask.sum() < 4` skipped — all verified by targeted regression tests.
3. **Speed:** ≥50× faster on the arithmetic-dominated benchmark cell
   (L=28, D=3584, n=500, K=1000 perm+randnorm draws), and in absolute
   terms the benchmark battery completes in **< 5 minutes on the VM CPU**
   (vs the observed 2+ h at #778 scale). Measured by the micro-benchmark
   in §5.
4. All existing tests in `tests/test_issue778_null_battery.py` pass
   unchanged (they double as behavior-regression coverage at
   compute_setting level).
5. `uv run ruff check` clean on the touched file.

**N/A — not a replication** (no published finding is being replicated;
this is a performance refactor with frozen semantics).

## 2. Prior work / method delta

#722 established the project failure mode this fixes: a many-cell Python
loop of individually tiny numeric ops is OVERHEAD-bound (op dispatch,
not FLOPs) — 19.5 CPU-h for ~19 TFLOP of math — and
`.claude/rules/vectorize-many-cell-fits.md` names batching the
draw/cell axes into tensor ops as the canonical 50–100× fix, with GPU
secondary. The delta here: #722's helper (`vectorized_mlp_skill.py`)
targets iterative gradient-descent fits; the null battery is
**closed-form** (diff-of-means directions, projections, Pearson
correlations), so the fix is pure numpy batched GEMM/einsum + the
standard batched-Pearson identity (standardize both operands along n,
then mean-of-products gives all L×K correlations in one contraction) —
no GD helper, no torch, no GPU. #778 is the motivating consumer (its
`--n-draws 1000` battery ran 2+ h at ~324% CPU on ~1–2 TFLOP of math).

## 3. Design

### 3.0 Scope of vectorization

**In scope (dedicated batching):** the four public functions
`perm_null_draws`, `randnorm_null_draws`, `r_per_layer`,
`within_condition_r_per_layer`, plus `bootstrap_ci_matched_r`
(secondary hotspot: 10,000 Python-loop 1-D Pearsons; vectorizing it is
cheap once the batched-Pearson helper exists, and it dominates wall
time after the nulls are fixed).

**Out of scope (dedicated batching), covered transitively:**
`crosstrait_null` (~2 fixed directions) and `pca_topk_null` (k=5 fixed
directions) loop over a handful of directions, not K=1000 draws — they
gain automatically because their inner calls route through the new
batched projection/Pearson helpers with the direction axis stacked;
adding a bespoke draw-batching path for ≤5 directions buys nothing.
`pca_topk_directions` (per-layer SVD) stays as-is: 28 SVDs of
`[n_pair, D]` are LAPACK-bound already, not op-dispatch-bound.
`compute_setting` is orchestration-only (consumes no rng itself); its
trivial `per_draw_max` list-comprehension is replaced by
`np.nanmax(np.abs(mat), axis=1)` guarded for all-NaN rows — zero-risk,
optional. `empirical_p_one_sided`, `null_band`, `benjamini_hochberg`,
`max_abs_over_layers`, `project`, `_pearson`, `_shrunk_cholesky` are
already vectorized or per-scalar by contract and are untouched
(`project` is imported directly by `scripts/issue778_monitoring.py` —
its signature and semantics are FROZEN).

### 3.1 RNG-consumption-order policy (the load-bearing design decision)

**Generate every random quantity in EXACTLY the current loop order via
a cheap Python rng-call loop; vectorize only the arithmetic.** The rng
calls are K (or K·L) cheap calls totaling milliseconds — they are not
the bottleneck; the per-draw `r_per_layer` arithmetic is. Concretely:

- **perm null:** current code consumes exactly one
  `rng.permutation(n_total)` per draw. New code:
  `perms = np.stack([rng.permutation(n_total) for _ in range(n_draws)])`
  → `[K, n_total]` int array, bit-identical sequence to the loop
  version. All downstream arithmetic batched.
- **randnorm null:** current code consumes one `rng.standard_normal(D)`
  per (draw, layer), draw-major / layer-minor, AFTER the rng-free
  Cholesky precompute. New code preserves the nested generation loop:
  ```python
  Z = np.empty((n_draws, L, D), dtype=np.float64)
  for d in range(n_draws):
      for layer in range(L):
          Z[d, layer] = rng.standard_normal(D)
  ```
  (We do NOT rely on `rng.standard_normal((K, L, D))` being
  stream-order-identical — see Assumption A3; the explicit loop is the
  guaranteed-safe path and costs ~K·L ≈ 28k cheap calls, well under a
  second.)
- **bootstrap:** current code consumes one `rng.integers(0, n, size=n)`
  per draw. New code:
  `idx = np.stack([rng.integers(0, n, size=n) for _ in range(n_boot)])`
  → `[n_boot, n]`, bit-identical.

Cholesky factors stay precomputed before any rng consumption (as
today), so the rng stream position at each draw is unchanged.

### 3.2 New private helpers (all module-private, no public API change)

```python
def _batched_project(acts: np.ndarray, dirs: np.ndarray) -> np.ndarray:
    """acts [n, L, D] float64, dirs [K, L, D] float64 -> proj [n, L, K].

    proj[i, l, k] = (acts[i, l] @ dirs[k, l]) / ||dirs[k, l]||,
    with proj[:, l, k] = 0 where ||dirs[k, l]|| == 0 (matches `project`).
    Implemented as norms = ||dirs|| over D  -> [K, L];
    raw = np.einsum('nld,kld->nlk', acts, dirs)  # or per-layer GEMM
    proj = raw / norms.T[None]  with zero-norm columns zeroed.
    """

def _batched_pearson(proj: np.ndarray, target: np.ndarray) -> np.ndarray:
    """proj [n, L, K], target [n] -> r [L, K].

    Standardize target once (t - mean)/std; center proj along n; then
    r[l, k] = sum_i projc[i,l,k] * tc[i] / (n * std_proj[l,k]).
    NaN where n < 3 or either std == 0 (exactly `_pearson` semantics).
    One einsum('nlk,n->lk') contraction; no Python loop.
    """

def _batched_within_r(proj, target, condition_ids) -> np.ndarray:
    """proj [n, L, K], target [n], condition_ids [n] -> r [L, K].

    Loop over UNIQUE conditions c (typically ~8, cheap): skip groups
    with mask.sum() < 4; per-group _batched_pearson -> r_c [L, K];
    clip to +/-0.999999, Fisher z = arctanh, weighted mean with
    w = n_c - 3, tanh back. NaN where no group qualifies. Matches
    within_condition_r_per_layer per-layer semantics exactly.
    """

def _perm_directions(pool: np.ndarray, perms: np.ndarray, n_pos: int) -> np.ndarray:
    """pool [n_total, L, D], perms [K, n_total] -> dirs [K, L, D].

    Diff-of-means as ONE matmul: build W [K, n_total] with
    W[k, perms[k, :n_pos]] = 1/n_pos and W[k, perms[k, n_pos:]] = -1/n_neg
    (row-wise scatter via np.put_along_axis), then
    dirs = (W @ pool.reshape(n_total, L*D)).reshape(K, L, D).
    """
```

`_MAX_BATCH_BYTES = 2 * 1024**3` module constant + a
`_k_chunks(K, bytes_per_draw)` helper drive K-chunking (§3.4).

### 3.3 Per-function rewrites (pseudocode + shapes)

- **`r_per_layer(activations [n,L,D], direction_per_layer [L,D], target [n])`**
  → `_batched_project(acts, dirs[None])` → `[n, L, 1]` →
  `_batched_pearson(...)[:, 0]` → `(L,)`. Single-direction case of the
  shared helpers; the L-loop disappears. Public signature unchanged.
- **`within_condition_r_per_layer`** → same, through
  `_batched_within_r`, returning `[L, 1] → (L,)`.
- **`perm_null_draws`** →
  1. `pool = concat(pos, neg)`; `perms` stacked in rng order (§3.1);
  2. `dirs = _perm_directions(pool, perms, n_pos)` `[K, L, D]`
     (chunked over K per §3.4);
  3. `proj = _batched_project(predictor_acts, dirs)` `[n, L, K]`;
  4. `r = _batched_pearson(proj, target)` (or `_batched_within_r` when
     `within=True`) `[L, K]`;
  5. `return np.abs(r).T` `[K, L]` — identical shape/meaning to today.
- **`randnorm_null_draws`** →
  1. Choleskys precomputed per layer (unchanged, rng-free);
  2. `Z [K, L, D]` generated in nested rng order (§3.1);
  3. per layer `l` (L=28 GEMMs): `V_l = Z[:, l, :] @ chols[l].T`
     `[K, D]` (equals `(chols[l] @ z)` row-wise);
  4. `vn = ||V_l|| [K]`; `dirs[:, l, :] = V_l / vn[:, None] * rb_norm_per_layer[l]`,
     rows with `vn == 0` left as `V_l` (matches the loop's `v if vn == 0`);
  5. steps 3–5 of the perm path (project → Pearson → `abs.T`).
- **`bootstrap_ci_matched_r`** → `proj [n]` computed once at the fixed
  layer (unchanged); `idx [n_boot, n]` stacked in rng order; gather
  `X = proj[idx]`, `Y = target[idx]` `[n_boot, n]`; row-wise Pearson via
  the same standardize-and-contract identity (a `[n_boot]`-vectorized
  `_pearson`, NaN rows where a row std == 0); percentiles of non-NaN
  rows — numerically identical percentile inputs up to the `allclose`
  tolerance.
- **`crosstrait_null` / `pca_topk_null`** → keep their small loops over
  directions OR stack their ≤5 directions into one
  `_batched_project`/`_batched_pearson` call (implementer's choice; no
  rng involved, so either is safe). They consume no rng.

### 3.4 Memory sizing + K-chunking policy

At the #778 production shape (L=28, D=3584, float64 end-to-end):

| Intermediate | Shape | float64 size |
|---|---|---|
| Direction stack (perm or randnorm) | [1000, 28, 3584] | **~802 MB** |
| Projections, n=1000 | [1000, 28, 1000] | ~224 MB |
| Perm diff-of-means GEMM output | [1000, 28·3584] | same 802 MB buffer |
| Z stack (randnorm) | [1000, 28, 3584] | ~802 MB |
| Bootstrap gather X+Y, n=1000 | 2× [10000, 1000] | ~160 MB |

Worst transient peak (Z + dirs + proj coexisting) ≈ 1.9 GB — at the
edge. Policy: compute `bytes_per_draw = L*D*8 (dirs) + L*D*8 (Z, randnorm
only) + n*L*8 (proj)` and chunk K so the projected peak stays under
`_MAX_BATCH_BYTES = 2 GB`; process draws in contiguous chunks (rng
generation still runs over the FULL K range first, in order, so
chunking cannot perturb the stream), concatenating the `[K_chunk, L]`
outputs. float32 stacking is NOT adopted (would break the float64
equivalence contract); noted as a future opt-in memory mode only.

## 6. Kill criteria

1. **RNG-order equivalence unachievable** without changing public
   semantics (e.g. a code path is discovered that interleaves rng
   consumption with arithmetic in a way that batching cannot preserve —
   not currently believed to exist; §3.1 enumerates all three streams).
   → Abort the refactor for that function, keep the loop, document.
2. **allclose failures traceable to genuine numerical instability**
   (not reassociation) — e.g. the batched Pearson loses precision on
   near-constant columns beyond rtol=1e-10 → tighten the algorithm
   (two-pass centering) or kill.
3. Speedup < 10× on the benchmark (would falsify the overhead-bound
   diagnosis) → stop and re-profile before landing anything.
