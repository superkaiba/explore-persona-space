# Plan v1 — #1782 workflow-fix: direction-agnostic cross-phase `reads[]` in `off_pod_phases` (pod reads VM outputs)

architectural: false

## Plan Summary

Generalize the planner `off_pod_phases` declaration (#1535) from its
direction-specific form ("off-pod consumers of pod outputs") to a
direction-agnostic **cross-phase reads** rule: every dispatched phase —
pod/GCE/SLURM AND off-pod alike — that reads ANOTHER phase's outputs
declares `reads[]` with a fetchable permanent source and, for the
VM-produced → git-clone-lane direction, the producer upload step + the
consumer launcher staging step. Pure docs/rule + verifier-text change;
the fenced-block NAME (`off_pod_phases:`) and every mechanical check's
semantics are unchanged (back-compat with all in-flight plans and the c39
satisfier). 0 GPU-h.

**Goal (verbatim from task body):** Generalize the planner

**Acceptance criteria:**

1. `planner-section-reference.md` §9's REQUIRED clause covers BOTH
   directions: (a) pod dispatch + subsequent off-pod phase (the existing
   #1482/#1426 direction) and (b) any pod/GCE/SLURM phase consuming
   ANOTHER phase's outputs — including VM-produced inputs (the #1773
   inverse seam), with the git-clone-lane basis stated (lanes stage only
   the pushed branch; `data/` is gitignored — the #734/#1434 class).
2. A new rules bullet mandates, for VM-produced → git-clone-lane reads:
   the producer phase's fail-loud bulk `upload_folder` step AND the
   consumer launcher's staging step (scoped `list_repo_tree` + per-file
   download — never `snapshot_download` on the ~1M-file data repo), with
   the `[stage] <input> staged: N files` log line named as the crash-fix
   fix-engaged signal (mirrors the existing agent memory
   `feedback_cross_machine_input_staging.md`).
3. The block schema accommodates the new direction: `runs_on` gains the
   dispatched-lane values (`pod-gpu | gce | slurm`), and
   `vm-resident-by-construction` is stated legal ONLY for phases whose
   `runs_on` is `vm` (a git-clone-lane consumer must use `hf-data-repo`
   or `git-issue-branch`).
4. Every sibling surface that restates the direction-specific rule is
   generalized consistently: `planner.md` §9 off-pod paragraph,
   `critic-lens-reference.md` Methodology item 10 REVISE bullet,
   `gotchas.md` cross-machine upload-set entry, `adversarial-planner`
   SKILL.md c39 N/A-escape line, `verify_plan.py` c39 docstring + WARN
   text, `upload-verifier.md` Step 2.8 reads-verification wording.
5. NO mechanical-semantics change anywhere: c39 stays WARN-only /
   vocabulary-triggered / experiment-only with the same satisfiers; the
   upload-verifier Step 2.7/2.8 verdict grammar is unchanged; the
   `off_pod_phases:` block name is unchanged.
6. `tests/test_verify_plan.py` c39 pins still pass (the WARN text keeps
   the literal `off_pod_phases:` token its assertion greps).
