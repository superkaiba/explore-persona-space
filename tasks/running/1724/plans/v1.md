## 4. Design

### 4.1 The change to `scripts/verify_task_body.py`

Add a pure helper + a `main()` short-circuit block. Rough shape (final wording refined at implementation time; the implementer copies the exit-code / verdict-string values verbatim from this plan):

```python
# ─── kind:infra/batch/survey short-circuit (below the argparse block,
#     above the verify_text() call) ────────────────────────────────

_NOT_APPLICABLE_KINDS: frozenset[str] = frozenset({"infra", "batch", "survey"})
# NOTE: "analysis" is deliberately EXCLUDED — see §4.3 below.


def _kind_short_circuit(fm: dict) -> str | None:
    """Return the ``kind`` name when the verifier should short-circuit
    to a not-applicable verdict, else ``None``.

    Fires when frontmatter ``kind`` is in {"infra","batch","survey"} AND
    ``has_clean_result`` is falsy (missing / ``None`` / ``False`` /
    ``"false"`` / ``""`` / ``0``). A truthy ``has_clean_result`` means the
    task was promoted and DOES carry a clean-result body (rare — a mis-file
    of an infra task, or a legitimately-promoted analysis) — that case
    falls through to the normal check path.

    ``kind: analysis`` is deliberately excluded: an analysis task can
    produce a clean-result (SKILL.md § 9a-quater: "kind: analysis → only
    when the task has a discernible measured finding"); an analysis task
    at ``has_clean_result: false`` and no clean-result body is a
    legitimate FAIL signalling the analyzer hasn't finished, which we
    want to keep visible.
    """
    kind = fm.get("kind")
    if not isinstance(kind, str) or kind not in _NOT_APPLICABLE_KINDS:
        return None
    hcr = fm.get("has_clean_result")
    # Coerce common YAML-parses. YAML `false` → bool False; a string
    # "false" (rare / mis-quoted) is treated as falsy here for safety.
    if isinstance(hcr, str):
        hcr_bool = hcr.strip().lower() not in {"", "false", "no", "0", "null", "none"}
    else:
        hcr_bool = bool(hcr)
    return None if hcr_bool else kind
```

Wire into `main()` (after L14620, just before the L14634 `verify_text(...)` call, and ONLY on the `--issue` branch — `--file` and `--body-stdin` do NOT have task frontmatter and MUST stay unchanged):

```python
    # (immediately after the args.issue try/except block, before the
    # elif args.file / else branches — or, equivalently, after all three
    # branches populate `raw`, but gated on `args.issue is not None`
    # so it never fires on --file or --body-stdin)
    if args.issue is not None:
        fm, _ = split_frontmatter(raw)
        na_kind = _kind_short_circuit(fm)
        if na_kind is not None:
            print(f"verify_task_body — {source}")
            print(
                f"  [N/A] kind:{na_kind} task with has_clean_result:false — "
                f"the clean-result spec does not apply to this body."
            )
            print()
            print(
                f"OVERALL: N/A (kind: {na_kind} — no clean-result body expected)"
            )
            return 3
```

**Exit-code contract** — updated in the module docstring at the top of the file:

- `0` — OVERALL: PASS (existing)
- `1` — OVERALL: FAIL (existing)
- `2` — task-body file not found (existing)
- `3` — OVERALL: N/A (new; kind:{infra,batch,survey} with `has_clean_result:false`)

### 4.3 Scope + rationale for `kind: analysis` exclusion

The body says "kind: infra|batch|survey" — analysis is deliberately excluded. Reason:

- `kind: infra|batch|survey` NEVER produce a promotable clean-result body by design (they complete on the Step 9c test-verdict path per CLAUDE.md § "Fix-validation / test that X works → `kind: infra`").
- `kind: analysis` MAY produce a clean-result (per SKILL.md Step 9a-quater: "kind: analysis → only when the task has a discernible measured finding"). An analysis task with `has_clean_result: false` and no clean-result body is a LEGITIMATE FAIL — it signals "analyzer hasn't produced a finding yet," which is a real state to keep visible (the auto-continue pipeline flips it to `has_clean_result: true` once the analyzer promotes the body).
- Adding analysis to the short-circuit set would silence the pre-promotion FAIL and defeat SKILL.md's implicit expectation that a pre-promotion analysis body FAILs the verifier.

The plan and tests treat `kind: analysis` as `None` (falls through) explicitly, with a comment tying to this rationale in `_kind_short_circuit`'s docstring.

## 11. Decision Rationale

| Design choice | What / Why / Alternatives-considered / Source |
|---|---|
