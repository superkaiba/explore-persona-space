## 1. Requirement

Any workload dispatched to a SLURM lane (`fellows` / `nibi` / `fir` / `mila`) that opens a
git-TRACKED file under `data/` must find it on the compute node. Today it crashes
`FileNotFoundError` — the same class as the #2203 Phase-3 pod crash that #2211 fixed
pod-side — because `RSYNC_INCLUDE_PATHS`
(`src/explore_persona_space/backends/slurm.py` L916-930) carries `./data/sft` and nothing
else under `data/`.

**Added in v2 (a requirement, not a nicety):** the fix must not create a data-flood path on
the reachable `EPS_SLURM_LIVE_TREE_RSYNC=1` live-tree source.

## 2. Decision: option (a), widened to all tracked `data/` — but DERIVED FROM THE GIT INDEX, not a bare `./data` constant

The body offered (a) widen the include-set, (b) a documented per-launch declaration,
(c) another staging convention. v2 keeps (a) and rejects (b)/(c) for v1's reasons (below),
but implements (a) as a git-index-derived include set.

### 2.1 Why (a) at all — unchanged from v1, all premises re-verified in round 1

- **Semantic parity with the parent** is this task's stated purpose. #2211 added `data` to the
  pod default sparse cone; git materializes only tracked blobs there. Both critics confirmed
  the parity: `scripts/bootstrap_pod.sh` L276-287 / L336-348, pinned in
  `tests/test_bootstrap_pod_issue_cones.py` L353-388.
- **Measured tracked `data/` at HEAD: 320 files / 59.98 MB** across 11 top-level entries
  (vs `./data/sft` alone = 1 file / 0.18 MB). Independently reproduced by both critics with
  the §5 commands.
- **Option (b) already exists and did not prevent the crash class.** `--extra-sync-path`
  (#1835, `EXTRA_SYNC_PATHS_KEY`) is opt-in and requires the planner to foresee which tracked
  input a workload opens — the same reason #2211 rejected declaration-only pod-side. It stays
  the remedy for inputs OUTSIDE the include set (`eval_results/`, `ood_eval_results/`,
  `raw/`, `docs/`, `archive/`): this fix narrows what needs it, it does not replace it.
- **Option (c)** (stage `data/` inputs from HF) would touch every consuming experiment script
  and inverts the parent's decision for no lane-specific reason.

### 2.2 Why DERIVED, not the bare `./data` constant v1 proposed — the round-1 correction

v1 asserted that since #1913 `_resolve_rsync_source` **ALWAYS** materializes a committed-only
detached scratch worktree, so `./data` could only ever ship tracked bytes. That is **false in
a reachable case**, confirmed by both critics and re-verified directly:
`src/explore_persona_space/backends/slurm.py` L3199-3214 — `EPS_SLURM_LIVE_TREE_RSYNC=1`
restores legacy live-tree routing and **returns `self._src_root`** (L3211 for `main`/absent,
L3214 for already-on-branch). It is a loud-warned deliberate operator override whose stated
purpose is shipping uncommitted working-tree state, and it is pinned as reachable behavior by
`tests/test_slurm_backend_render.py` L1662-1688 / L1766-1793.

Under that override, a bare `./data` include would sweep the live tree's untracked `data/`.
Measured, at HEAD on this VM:

| Quantity | Measured |
|---|---|
| `data/` total (VM working tree) | 43,221,760 KB ≈ **41 GiB** |
| Caught by the proposed `*_dl/` + `store/` excludes (depth ≤3) | 1,796,044 KB ≈ 1.7 GiB (**~4%**) |
| Top-level `data/` entries: tracked / total | **11 / 70** — 59 untracked entries carry the rest |
| Untracked residual INSIDE the 11 tracked top-level entries | **6,152 KB ≈ 6 MB**, all 13 files gitignored (`data/sft` only) |

v1's parenthetical "~208 GiB" figure was carried from `.claude/rules/disk-hygiene.md`'s
whole-`data/`-plus-worktrees accounting and is **not reproducible on this checkout** — Codex
measured 42G, this plan measures 43.2 GB. v2 states the measured number and drops the cited
one. (The correction does not change the conclusion's direction: 40 GB is still a flood.)

v1 also claimed the flood would fail loudly on `run_rsync_sync`'s 600 s timeout. **That
mitigation does not hold:** 40 GB / 600 s ≈ 68 MB/s, which a fast link can complete, so the
flood may SUCCEED — filling cluster scratch or breaching a VAST storage quota. The failure
mode is not reliably loud, which is why v2 treats this as a code-level requirement rather
than a documentation note.

**The derivation makes the flood structurally impossible while preserving both goals.** The
last row of the table is the decisive measurement: at TOP-LEVEL granularity the derivation
removes ~40 GB of untracked entries and leaves a ~6 MB residual (gitignored `data/sft`
scratch). That is small enough that **subdir granularity is sufficient** — full-path
granularity would require `--files-from`, i.e. a change to rsync's flag surface, which §10
holds as must-re-plan. Under the derivation:

- **Committed-only path (every default dispatch):** effect is identical to `./data` — the
  scratch worktree contains exactly the tracked entries.
- **Override path:** every untracked top-level `data/` entry is provably absent from the argv,
  so it cannot transfer. Tracked `data/` inputs still ship, so the override does NOT
  reintroduce the crash class (which is why "keep `./data/sft` under the override" was
  rejected — a silent loss of tracked inputs violates CLAUDE.md's fail-fast rule).
- **Allowlist, not denylist:** a NEW untracked top-level `data/` entry is excluded by
  construction, and a newly TRACKED one ships automatically. A denylist of computed
  `--exclude` entries was considered and rejected for the opposite failure direction.

## 3. Method delta + concrete diffs

### Change A′ — derive the `data/` include entries from the git index

`src/explore_persona_space/backends/slurm.py`:

1. **Drop `./data/sft` from `RSYNC_INCLUDE_PATHS`** (L916-930), replacing the entry's comment
   with a pointer to the derivation helper. The constant keeps its other entries verbatim and
   remains the single source of truth for the NON-`data` include trees (so
   `verify_carryover_inputs.rsync_cover_set`'s import keeps working — see change E).
2. **New module-level constant + helper:**
   ```python
   RSYNC_DATA_INCLUDE_ROOT = "data"

   def tracked_data_include_paths(src_root: Path, *, timeout: int = 60) -> tuple[str, ...]:
       """Dot-anchored include entries for every TRACKED top-level ``data/`` entry.

       ``git -C <src_root> ls-files <root>`` -> the distinct first path component
       under ``data/`` -> ``./data/<component>``, sorted, deduped. Both rsync
       sources are git trees: the default path's detached scratch worktree
       (``materialize_branch_src``) and the ``EPS_SLURM_LIVE_TREE_RSYNC=1``
       override's live repo root.

       WHY derived rather than a bare ``./data`` include: under the override the
       source IS the live working tree, where ``data/`` carries ~40 GB of
       UNTRACKED caches and staging dirs across 59 of 70 top-level entries
       (measured #2212). A bare include tree would sweep them to the cluster —
       and the 600 s rsync timeout does NOT reliably catch it (~68 MB/s
       completes 40 GB in the window). Deriving from the index makes the flood
       structurally impossible while still shipping every tracked input, so the
       override does not reintroduce the #2203 FileNotFoundError class.

       Residual (accepted, measured): untracked files INSIDE a tracked top-level
       entry still ship under the override — 6 MB / 13 gitignored files at
       #2212. Full-path granularity would need ``--files-from``, a change to the
       rsync flag surface.

       Fails LOUD (``RuntimeError``) if the ls-files probe fails: a silent
       fallback would resurrect either the flood or the crash class.
       """
   ```
3. **Compose at the three call sites** that must agree, threading the derived tuple as the
   existing `include_paths` parameter:
   - `run_rsync_sync` — `RSYNC_INCLUDE_PATHS + tracked_data_include_paths(src_root)`.
   - `verify_rsync_complete` — the SAME composed tuple. **Load-bearing:** Codex confirmed the
     verify rebuilds the same argv and only inserts `--dry-run --itemize-changes` (L1200-1264),
     so a divergent include set between sync and verify would silently break the #1913
     completeness gate.
   - Any other production caller of `build_rsync_command` that omits `include_paths`.
   `build_rsync_command` itself stays a PURE function of its arguments — no git call inside it
   — so every existing test that passes an explicit `include_paths` (or relies on the default
   constant) keeps working, and the helper is unit-tested independently against a real temp
   git repo. **No change to the rsync flag set.**

### Change B — protect cluster-side caches from `--delete` (`RSYNC_EXCLUDE_PATTERNS` L932-949)

`build_rsync_command` (L1070-1129) emits `-a --relative --delete --partial --mkpath` with one
`--exclude` per pattern and **no** `--delete-excluded` (confirmed by both critics), so an
excluded pattern also protects matching RECEIVER-side files from the deletion pass. Widening
the include set from `data/sft` to the tracked-`data/` entries extends `--delete`'s reach over
those subtrees on the cluster, and `prepare` runs on every FRESH launch — crash-fix relaunches
included. Add:

```python
+    # Re-downloadable staging caches + durable per-issue stores, matched at
+    # every depth (rsync applies slash-free patterns at all depths). Under the
+    # #2212 derived data include-set these can never be SENT (they are
+    # untracked, so the index-derived entries exclude them), so their ONLY
+    # function is protecting a CLUSTER-side
+    # ``$SCRATCH/data/<tracked>/{*_dl,store}`` tree from the ``--delete`` pass
+    # on a re-dispatch (there is no ``--delete-excluded``). Collision-checked
+    # at #2212: no tracked path component in the repo ends in ``_dl`` or equals
+    # ``store``, so neither pattern can shadow a tracked input (#1915).
+    "*_dl/",
+    "store/",
```

`*_dl/` rather than CLAUDE.md's `g*_dl` shorthand: the realized names under `data/` are
`hf_dl` (×4) plus `summaries_dl`, `recap_dl`, `recap_slice_dl`, `rb_nuisance_dl`, `prb_dl`,
`mirror_dl`, `ladder_dl`, `jlens_dl`, … — all `*_dl`.

**Honest scope:** no lane-level convention writes under `$SCRATCH/data/` today (fellows
`HF_HOME` is `/workspace/pretrained_ckpts`, L511; the SLURM render contains no `data/` path).
This is free, collision-free insurance for a workload that stages a repo-relative
`data/<x>/hf_dl` from `cwd=$SCRATCH`. It is NOT claimed to fix an observed loss, and that
register must survive into the code comment and the review.

  §10's bounce. v2 does not re-scope the falsifier to dodge it; it re-planned change A so the
  override is handled, and the criterion now tests the property that actually matters.)*
- **An exclude pattern shadows a tracked input** (#1915): any tracked path component ending
  `_dl` or equal to `store`. Falsifier: §5 measurement 3, now also a standing test (§6.7).
  Non-empty ⇒ change B's pattern choice dies; per §10 the replacement must be narrower
  non-colliding patterns that KEEP the §6.4 survivor assertion — never a bare drop.
- **Tracked `data/` exceeds the transfer budget.** 512 MB ceiling (§3 D/6), evaluable
  pre-merge as a repo test — this is v2's answer to round 1's finding that v1's ">2 min on a
  real dispatch" criterion had no planned pre-merge execution (§9 provisions no SLURM job).
  The real-dispatch timing remains a post-merge observation, explicitly named in §4 as an
