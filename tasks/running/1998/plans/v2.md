# Plan — task #1998: fail loud when --min-ram-gb is inert on a GPU dispatch

## 0.0 TL;DR (plain English — the user reads this first)

- **What I'll run** — I'll add a RAM guard to the GCP GPU rung walker so that when someone passes `--min-ram-gb` on a GPU dispatch, undersized machines are skipped in the ladder (or refused, when the intent pins one machine, or when EVERY rung in the ladder is undersized). I'll teach `backends/gcp.py` a per-machine RAM table, mirror the existing `--min-gpu-mem-gb` A100-40 rung-skip pattern, add two `epm:backend-selected` marker keys, land nine tests + one completeness test, and update two stale doc lines.

## 1. Goal

> Make `--min-ram-gb` fail loud (or at minimum WARN + refuse silently-undersized provisioning) on GCP GPU dispatches whose resolved machine's RAM is below the requested value — today the flag is a RunPod-CPU-fallback-only knob and GCP GPU machine selection silently ignores it.

(Task #1998 Goal, verbatim.)

The `--min-ram-gb` flag was introduced (#1010) as a RunPod-CPU-fallback feasibility knob: `router._refuse_infeasible_cpu_footprint` reads it when routing to a CPU pod. For a GCP GPU dispatch the flag is currently accepted at parse-time (`scripts/dispatch_issue.py`) and threaded into the run handle (`backends/gcp.py` uses it only for reconnect/failover metadata), but the GCP machine selection ladder — `INTENT_TO_MACHINE`, the short/long ladder, the wide-degrade rungs — never compares the flag against the resolved machine's memory. That silent inertness caused the #1739 Gap-2 OOM cascade: a plan that asked for 300 GiB got a 170 GiB `a2-ultragpu-1g`, the mismatch was rationalized in prose, both boxes died at exit 137, and the fix was a manual `--gpus 2` relaunch.

This plan closes the gap by teaching the ladder to respect `--min-ram-gb` the same way it already respects `--min-gpu-mem-gb` (#1468's A100-40 rung-skip): skip an undersized rung when the ladder has a satisfying next rung; refuse pre-launch when an explicit `--intent X` pins one machine that cannot satisfy the requirement; refuse pre-launch when EVERY rung in the ladder is under the requested value.

## 4. Design

### Location decision: Option B — rung-selection time inside `backends/gcp.py`

The guard lives alongside the machine mapping (`INTENT_TO_MACHINE`, the wide-degrade tables, the A100-40 usable-GiB constant `A100_40_USABLE_GIB` from #1468) rather than duplicated at parse-time in `scripts/dispatch_issue.py`. This keeps machine→RAM knowledge single-source-of-truth: a future ladder edit that adds a new machine only touches one file.

Option A (parse-time in `dispatch_issue.py`) is rejected: it either forces `dispatch_issue.py` to import the machine table from `backends/gcp.py` (equivalent to Option B with worse ergonomics) or duplicates the table, courting drift.

### Machine → RAM constants

Add a module-level constant table in `backends/gcp.py` next to `INTENT_TO_MACHINE`:

```python
# GCP accelerator-optimized + L4 shapes: memory (GiB) per the cited docs.
# Sourced from cloud.google.com/compute/docs/gpus and
# cloud.google.com/compute/docs/accelerator-optimized-machines.
# Values CONFIRMED by fact-checker Phase 1.5 (verified against cloud.google.com
# on 2026-08-04); every row below matches the live docs.
MACHINE_RAM_GIB: dict[str, int] = {
    "g2-standard-4":    16,     # 1x L4
    "a2-highgpu-1g":    85,     # 1x A100-40
    "a2-ultragpu-1g":   170,    # 1x A100-80
    "a2-ultragpu-2g":   340,    # 2x A100-80
    "a2-ultragpu-4g":   680,    # 4x A100-80
    "a2-ultragpu-8g":   1360,   # 8x A100-80
    "a3-highgpu-8g":    1872,   # 8x H100-80
}
```

A `test_ram_table_covers_intent_to_machine_keys` completeness test asserts every value in `INTENT_TO_MACHINE` and the wide-degrade maps (`WIDE_A100_80_BY_WIDTH`, `EXPLICIT_WIDE_DEGRADE_INTENTS`) appears in `MACHINE_RAM_GIB` so future machine additions cannot silently escape the guard.

### Guard semantics — parallel to `--min-gpu-mem-gb`

Insert a `_ram_satisfies(machine: str, min_ram_gb: int | None) -> bool` helper alongside the existing A100-40 skip predicate. Wire it into the ladder walker at exactly the sites where the `--min-gpu-mem-gb` guard already fires:

1. **Rung-skip in the auto ladder walk.** Both the short-job branch (spot → flex-start → on-demand) and the long-job branch (flex-start → on-demand) call `_ram_satisfies` on each rung's resolved machine before creating the instance. Undersized rung → walk to the next rung, no daily-attempt burn (parallel to the A100-40 skip's outcome=`ram_below_min_ram_gb_rung_skipped`). Since the ladder's rungs advance from smaller to larger memory footprints on the A100-80 side (`a2-ultragpu-1g` → `a2-ultragpu-2g` → …), most requests will land on a satisfying rung; a wide-degrade sequence (8g → 4g → 2g) walks in the same direction as its GPU-mem skip.

2. **Rung-skip in the wide-degrade walker.** Same helper, called on each degraded rung during the `--gpus N` wide walk. A `--gpus 8 --min-ram-gb 300` dispatch that gets 8g-capacity-missed still passes at 4g (680 GiB) or 2g (340 GiB); a `--min-ram-gb 700` at `--gpus 4` degrades to something wider or refuses.

3. **Refuse pre-launch on a pinned intent.** An explicit `--intent lora-7b` (which pins `a2-ultragpu-1g` at 170 GiB) with `--min-ram-gb 300` must not silently take a WIDER machine — the intent said "one A100-80". The guard raises a typed `GpuRamBelowMinRamGbError(intent, machine, resolved_ram_gib, requested_min_ram_gb)` (define alongside the existing `GcpDisabledError` / other typed exceptions in `backends/gcp.py`) BEFORE any `gcloud compute instances create` call. `issue_dispatch.classify_terminal_exception` maps it to `failure_class: infra`, `reason: gpu_ram_below_min_ram_gb`, `status: blocked` — parallel to `GcpDisabledError`'s mapping.

4. **Refuse pre-launch on a ladder-EXHAUSTED walk.** When EVERY eligible rung in the walker (auto short/long, or wide-degrade) has machine RAM < `min_ram_gb`, the walker raises the SAME typed `GpuRamBelowMinRamGbError` (same typed exception as pinned-intent refusal, distinguished by the `(intent, machine)` fields the exception carries — for a ladder-exhausted case the last-attempted rung is recorded). `classify_terminal_exception` maps to the same `failure_class: infra` / `reason: gpu_ram_below_min_ram_gb` / `status: blocked` triple.

   Two canonical exhaustion shapes:
   - `--min-ram-gb 2000` on any auto or wide walk — larger than a3-highgpu-8g's 1872 GiB (the largest machine in `MACHINE_RAM_GIB`), so every eligible rung fails the guard.
   - `--gpus 8 --min-ram-gb 3000` on a wide-degrade walk — 8g/4g/2g (1360/680/340 GiB) all fail.

   This is NOT `no_compute_available` (which is watcher-re-drivable via the capacity-retry pass) — a RAM-too-large request is a DESIGN MISMATCH, not a transient capacity miss. Do NOT fall through to the RunPod terminal rung: `--min-ram-gb` applies to the GCP GPU rungs, and the RunPod-GPU explicit-override lane (`--backend runpod` with a GPU intent) is out-of-scope for this workflow-fix — that lane's inertness is a residual (see the doc-update line below), not a fix this plan owns.

5. **Marker extras.** When (and only when) `--min-ram-gb` is set on a GPU dispatch, the `epm:backend-selected v1` marker's `extra` dict carries:
   - `requested_ram_gb: <N>` — the user's requested value.
   - `resolved_machine_ram_gb: <M>` — the resolved machine's RAM per `MACHINE_RAM_GIB`.

   Preserve #934 discipline: keys are omitted entirely when the flag is unset. Populate at the marker-post site inside `backends/router.route()` where `epm:backend-selected` is already assembled — thread the two values through the same channel `chosen_kind`/`reason`/`gcp_attempts_today` use today. Placement mirrors the CPU-side `router._refuse_infeasible_cpu_footprint` (:3149): read the value once, thread as marker `extra`, don't recompute at the post site.

## 6. Evaluation

Nine new pytest cases + one completeness test pin the guard's contract. Each is listed with the mocks and assertion shape a code-reviewer can verify against.

**Boilerplate for every ladder-exercising test (tests 1, 2, 3, MF1's new test, MF2's new test):** the test setup MUST `monkeypatch.setattr(router, "GCP_PROVISIONING_DISABLED", False)` before invoking `route()`. Under #2028 (`router.GCP_PROVISIONING_DISABLED = True`), any GCP dispatch raises `GcpDisabledError` BEFORE this plan's typed `GpuRamBelowMinRamGbError` can fire — the disabled-flag check short-circuits at the top of `route()`. Without this monkeypatch, tests 1/2/3/MF1/MF2 would each raise `GcpDisabledError` instead of the RAM-guard exception under test, silently passing or failing for the wrong reason. Tests 4, 5, 6, and 7 do not need this boilerplate (test 4/5 mock at the marker-post layer past the disabled check; test 6 is CPU-only; test 7 is help-text only).

## 11. Decision Rationale

**Load-bearing choice 1: Option B (guard at rung-selection time in `backends/gcp.py`) over Option A (parse-time in `dispatch_issue.py`).**

- **What:** Place the `_ram_satisfies(machine, min_ram_gb)` check inside the ladder walker in `backends/gcp.py`, called on each rung's resolved machine before creation.
- **Why:** Single-source-of-truth for the machine → RAM mapping. The wide ladder + `INTENT_TO_MACHINE` already live in `backends/gcp.py`; the `A100_40_USABLE_GIB` #1468 constant lives there too. Placing the RAM guard next to them means a future machine addition touches one file, not two.
- **Source:** #1468 (A100-40 rung-skip pattern for `--min-gpu-mem-gb`), verified by the body's `verified-at-filing:` sweep at `backends/gcp.py`; parallel pattern is explicitly what this plan mirrors.
- **Alternatives:** Option A (parse-time in `dispatch_issue.py`) forces either an import cycle or a duplicated table — same behavior, worse ergonomics, drift risk.

**Load-bearing choice 2: rung-SKIP for auto/wide walks, PRE-LAUNCH REFUSE for pinned `--intent` AND ladder-EXHAUSTED walks.**

- **What:** When the ladder has a satisfying next rung, walk past the undersized one; when a pinned intent identifies a specific machine that cannot satisfy the request, raise a typed exception before create; when EVERY rung in the walker is undersized, raise the same typed exception before create.
- **Why:** Mirrors #1468's split (`A100_40_USABLE_GIB` skip) and #1010's split (typed refusal). An auto/wide walk with a satisfying alternative — skipping is cheaper than refusing. A pinned intent expresses the user's intent to use one specific machine; silently substituting a wider machine would violate the pin. A ladder-exhausted walk (every rung under `--min-ram-gb`) is a DESIGN MISMATCH, not a transient capacity miss — routing it as `no_compute_available` would put it into the watcher's capacity-retry pass, which would re-drive it indefinitely against a request no lane can ever satisfy; refusal + a typed exception routes cleanly into `classify_terminal_exception` → `infra`/`blocked`, and the operator sees the mismatch.
- **Source:** #1468 (rung-skip contract), #1010 (typed refusal contract), CLAUDE.md § Compute backends "classify_terminal_exception".
- **Alternatives:** WARN-only would preserve the #1739 silent-OOM shape; rung-skip on pinned intents would silently violate the pin; fall-through to the RunPod terminal rung on ladder-exhaustion would hand a design-mismatch case to a lane whose GPU-side is out-of-scope for this fix (and would still not satisfy the request).

**Load-bearing choice 3: `MACHINE_RAM_GIB` constants sourced from Google Cloud docs; completeness test guards drift.**

- **What:** Add a static dict `{"g2-standard-4": 16, "a2-highgpu-1g": 85, "a2-ultragpu-1g": 170, "a2-ultragpu-2g": 340, "a2-ultragpu-4g": 680, "a2-ultragpu-8g": 1360, "a3-highgpu-8g": 1872}`. Add a completeness test.
- **Why:** GCP machine RAM is public, stable, documented, and small enough to pin as constants. A completeness test (`test_ram_table_covers_intent_to_machine_keys`) fails any future `INTENT_TO_MACHINE` or wide-map addition that forgets to add a RAM row — the same pattern by which router tests pin the auto-lane order (CLAUDE.md § Compute backends `test_default_auto_lane_order_has_no_gcp`).
- **Source:** CONFIRMED (fact-checker Phase 1.5 verified cloud.google.com/compute/docs/gpus and cloud.google.com/compute/docs/accelerator-optimized-machines against every cell). All 7 seed values (g2-standard-4: 16, a2-highgpu-1g: 85, a2-ultragpu-1g: 170, a2-ultragpu-2g: 340, a2-ultragpu-4g: 680, a2-ultragpu-8g: 1360, a3-highgpu-8g: 1872) match the live docs as of the fact-checker probe.
- **Alternatives:** Query the GCP API at runtime (adds latency, requires auth in the test path, brittle); infer from `--machine-type describe` (same issues). Static constants + drift-guard test is the standard project pattern.

**Load-bearing choice 4: marker `extra` carries both `requested_ram_gb` and `resolved_machine_ram_gb` only when the flag is set.**

- **What:** Populate both keys on `epm:backend-selected v1`'s `extra` dict when `--min-ram-gb` is set on a GPU dispatch; omit both keys entirely when unset.
- **Why:** #934 omit-when-absent spec-hash discipline — marker byte-identity when the feature is not used protects existing spec hashes and dashboards. Carrying BOTH values (not just the requested) gives operators the diff at a glance when reading the marker (`requested_ram_gb: 300, resolved_machine_ram_gb: 340` says "walked to a2-ultragpu-2g and it satisfies").
- **Source:** #934 (spec-hash discipline), CLAUDE.md § Compute backends (`epm:backend-selected v1` marker fields).
- **Alternatives:** Emitting only the requested value hides the walk outcome; emitting when unset breaks #934.
