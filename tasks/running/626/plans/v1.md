# Plan: Batch-aware Claude-judge dispatch in the eval path (task #626)

## 0.0 TL;DR

- **What I'll build:** One routing layer for all our Claude-judge scoring. Small jobs keep going through the normal API at high concurrency; big jobs (2,000+ judgments) get submitted to Anthropic's batch queue, which doesn't compete with our live Claude Code sessions for rate limits. The router writes its bookkeeping to disk the moment it submits, so a crashed run resumes by polling the same batches instead of paying for them twice.
- **What I expect:** Big judge jobs stop fighting the org rate limit and finish faster overall, small jobs are untouched, and judge scores come out in exactly the same shape as before so nothing downstream changes.
- **What would change my mind:** If the smoke run shows scores in a different shape than the old path, or the docs-promised caching turns out to behave differently in practice, I'd revisit the design before migrating call sites. One thing I verified up front: our judge rubrics are too short for Anthropic's prompt cache to even engage (it needs ~1,024 tokens; ours are 120–400), so the caching part ships as plumbing that activates only for future, longer rubrics — I'm not pretending it saves money today.

## 1. Goal

Judge scoring (alignment/EM/refusal judging of raw completions) is speed-bound by the org's shared Sonnet rate limits: synchronous judge calls compete with many live Claude Code sessions for the same OTPM pool, while the Message Batches API has its own separate queue (500,000 batch requests in flight at Tier 4, verified) plus a 50% price discount. ## 3. Requirement + Acceptance Criteria

Restating the body concretely:

1. **Routing:** `n_to_submit < effective_threshold` → sync (AsyncAnthropic, high concurrency, per-item error dicts); `>=` → Message Batches in sub-batches of ≤10,000 requests (and ≤256 MB). `effective_threshold = max(1, int(2000 * otpm / 400_000))` where `otpm` comes from one probe response header; `force_sync=True` bypasses to sync regardless of N.
2. **Batch mechanics:** `batches.create` → checkpoint `batch_id` + custom_id mapping to disk **before polling begins** → poll `retrieve()` until `ended` → stream `results()`, join on `custom_id` → persist each sub-batch's results the moment collected → retry `errored` subset once (then surface as error dicts) → resubmit `expired` subset once.
3. **Crash/resume:** rerunning the same dispatch with the same item set polls the recorded batches; it never re-creates them. Fingerprint mismatch fails loud.
4. **Caching:** every batch request carries `cache_control: {type: ephemeral, ttl: "1h"}` on the shared rubric block; sync requests carry the 5m default. Inert-below-minimum is detected and logged honestly.
5. **Dry-run:** prints N, cached/to-submit split, threshold (base + tier-scaled), chosen path, sub-batch plan — with zero API calls.
6. **Acceptance:** (a) helper + call-site migration merged, new tests green, ruff clean; (b) dry-run works; (c) one real smoke, N<50, sync path, against stored completions; (d) usage note in module docstring, no new CLAUDE.md prose.

## 4. Design

### New module: `src/explore_persona_space/eval/judge_dispatch.py`

All new logic in one module; `batch_judge.py` and `alignment.py` are thinned to call it. Core types and signatures:

```python
# Item: same 4-tuple already used by batch_judge
JudgeItem = tuple[str, str, str, str]  # (custom_id, question, completion, user_msg)

@dataclass
class RoutingDecision:
    n_items: int
    threshold_base: int          # 2000
    otpm: int | None             # probed header value, or None (dry-run / probe failed)
    otpm_assumed: bool           # True when fell back to 400_000
    effective_threshold: int
    path: str                    # "sync" | "batch"
    forced_sync: bool
    sub_batch_sizes: list[int]   # [] for sync
    def render(self) -> str: ...  # the dry-run printout

def probe_otpm_limit(client: anthropic.Anthropic, judge_model: str) -> int | None:
    """One max_tokens=1 request via client.messages.with_raw_response.create();
    returns int(headers['anthropic-ratelimit-output-tokens-limit']) or None
    (header missing -> warn + None)."""

def decide_route(n_items, *, threshold_base=2000, otpm=None, force_sync=False,
                 sub_batch_size=10_000) -> RoutingDecision: ...   # pure, fully unit-testable

def dispatch_judge_items(
    items: list[JudgeItem],
    *,
    judge_model: str = DEFAULT_JUDGE_MODEL,
    judge_system_prompt: str = JUDGE_SYSTEM_PROMPT,
    max_tokens: int = 256,
    threshold_base: int = 2000,
    sub_batch_size: int = 10_000,
    force_sync: bool = False,
    dry_run: bool = False,
    max_concurrent: int = 50,
    checkpoint_dir: Path | None = None,     # required for the batch path; asserted there
    poll_interval: float = 30.0,
    sync_client: anthropic.AsyncAnthropic | None = None,   # injection for tests
    batch_client: anthropic.Anthropic | None = None,       # injection for tests
    _is_retry: bool = False,
) -> dict[str, dict]:
    """Returns {custom_id: parsed_score_dict} — the SAME shape both paths,
    same error-dict convention as today ({'aligned': None, ..., 'error': True})."""
```

**Flow inside `dispatch_judge_items`:**

1. `decide_route` needs `otpm`: probe once iff `not dry_run and not force_sync and n_items < threshold_base * 2` (scaling can only matter near the boundary; one ~1-token request, negligible — but skipped when N is far above any possible threshold). Dry-run never probes: it uses `int(os.environ.get("EPM_JUDGE_OTPM", 400_000))` and prints `otpm_assumed=True`.
2. `dry_run=True` → print `decision.render()` and **return `{}` without any API call** (the mock-asserted invariant).
3. **Sync path** — `asyncio.run(_judge_items_sync(...))`: semaphore-bounded `AsyncAnthropic` calls, structurally the same as `alignment.judge_responses._judge_one` (per-item try/except → error dict, `parse_judge_json`), with two additions: (a) client constructed with `max_retries=5` so the SDK's built-in 429 exponential backoff does the rate-limit handling (body: "rely on SDK 429 backoff"); (b) **cache-warm ordering**: if the rubric's estimated token count ≥ 1024 (`len(prompt)//4` heuristic), await the FIRST request to completion, then `gather` the rest so they read the cache the first wrote; below 1024 skip the warm step entirely (it would be pure added latency — see step 4 honesty note).
4. **Batch path** — split via the existing `_chunk_requests(requests, max_count=sub_batch_size)` (reused unchanged; it already enforces the 256 MB byte cap). Then per sub-batch: submit → checkpoint → poll-all-round-robin → collect-and-persist per wave (sub-batches end independently; each is harvested the moment its `processing_status == "ended"`, never blocked on siblings — checkpoint-per-phase rule). After all collected: gather `errored` custom_ids → re-dispatch ONCE through `dispatch_judge_items(..., _is_retry=True)`; gather `expired` custom_ids → resubmit once the same way. `_is_retry=True` disables further retries and checkpoint-namespaces under `retry/`. (Refinement vs the body's "expired resubmitted in a follow-up batch": the resubmission goes through the same threshold routing, so 50 stragglers go sync — faster, consistent with the body's speed objective. Flagged in §10 as a deliberate, pre-approved deviation.) `canceled` results surface as error dicts (no retry — cancellation is user-initiated).

**Request builder with caching** (shared by both paths):

```python
def _build_params(judge_model, judge_system_prompt, user_msg, max_tokens, *, ttl):
    sys_block = {"type": "text", "text": judge_system_prompt}
    if ttl is not None:                      # "1h" for batch, None->5m default for sync
        sys_block["cache_control"] = {"type": "ephemeral", **({"ttl": ttl} if ttl != "5m" else {})}
    else:
        sys_block["cache_control"] = {"type": "ephemeral"}
    return {"model": judge_model, "max_tokens": max_tokens,
            "system": [sys_block], "messages": [{"role": "user", "content": user_msg}]}
```

**Caching honesty (required by the task):** every current rubric (123–404 est. tokens) is below Sonnet 4.5's 1,024-token cacheable minimum, where `cache_control` is a **silent no-op** (verified: no error, just `cache_creation_input_tokens == 0`). The design therefore: (a) attaches `cache_control` unconditionally (harmless now; engages automatically the day a rubric crosses 1,024 tokens — e.g. a future few-shot-laden rubric); (b) logs ONE warning per dispatch when `len(judge_system_prompt)//4 < 1024`: `"cache_control attached but inert: rubric ~%d tokens < 1024 minimum for %s — no cache savings expected"`; (c) gates the sync warm-first step on the same estimate (above). We do NOT claim cache savings in the module docstring for current rubrics.

**Checkpoint format + location** (the hard requirement):

```
<checkpoint_dir>/dispatch_<fingerprint12>/
  items.json            # {custom_id: {question, completion, user_msg}} — written once at dispatch start
  state.json            # atomic (tmp + os.replace) on every transition:
    {"version": 1, "fingerprint": "<sha256 of sorted custom_ids>",
     "judge_model": ..., "created_at": ...,
     "sub_batches": [
        {"index": 0, "n_requests": 10000, "custom_ids_range": [...],
         "status": "submitting" | "submitted" | "ended" | "collected",
         "batch_id": "msgbatch_..." | null, "submitted_at": ...}],
     "retry": {...}}
  results_<batch_id>.json   # per-sub-batch parsed results, written the moment collected
```

`fingerprint = sha256("\n".join(sorted(custom_ids)))[:12]` keys the directory, so re-invocation with the same item set deterministically finds its own state and different item sets never collide. **Resume logic at entry:** if `state.json` exists and fingerprint matches → for each sub-batch: `collected` → load `results_<id>.json`; `submitted`/`ended` → poll/collect, never re-create; `submitting` with `batch_id: null` (crashed inside the create call) → **fail loud** with the reconciliation message ("a batch may have been created but not recorded; check `client.messages.batches.list(limit=10)` for a batch of N requests created near <ts>, then either record its id in state.json or pass `allow_resubmit=True`"). Fingerprint mismatch in an existing dir → raise (never silently mix item sets). The `"submitting"` intent record is written BEFORE `batches.create()` and updated with the `batch_id` immediately after — closing the double-pay window to a deliberate, loud, human-resolved case instead of a silent resubmit.

`checkpoint_dir` defaults per caller: `judge_completions_batch` derives `cache_dir/.dispatch/` when `cache_dir` is set, else `save_raw.parent/.judge_dispatch/` when `save_raw` is set, else raises if the batch path is selected (sync path needs no checkpoint).

**Why code, not a model call?** N/A in the routing layer — this is API-dispatch infrastructure with no new heuristic over unstructured data. The only unstructured-data judgment (scoring completions) already IS a model call (`parse_judge_json` over Claude output), reused unchanged.

|---|---|---|
| Batch tail latency (24 h hard cap; demand-dependent slowdowns) stalls a same-day decision | Medium | `force_sync` escape hatch (plumbed through both entry points); sub-batches end independently so partial results land in waves; expired subset auto-resubmitted once (routes sync if small) |
| Crash between `batches.create()` success and checkpoint write → orphan batch / double-pay on resume | Low | `submitting` intent record before create; on resume that state fails loud with a `batches.list()` reconciliation recipe; resubmit only behind explicit `allow_resubmit=True` |
| Cache misses make the 1h-TTL spend pointless (2× write price) | Medium | Honest accounting: current rubrics are below the 1,024-token minimum so caching is inert AND costless (no write occurs below minimum — silent no-cache); the 2× write price only ever applies once a future rubric crosses the minimum, where batch-side hit rates (30–98% per docs) justify it |
| SDK version gap (`ttl` literal, `batches.*` surface) | Low | Verified by introspection against the pinned 0.88.0 (§2); pyproject already pins `<1.0`; tests mock the same surface so a future SDK bump that breaks it fails tests, not runs |
| Checkpoint corruption (partial write) | Low | Atomic tmp+`os.replace` writes; `state.json` parse failure → fail loud with the file path, never silent restart |
| `evaluate_alignment` flattening changes per-question semantics | Low | Reassembly test 16; aggregation code untouched; error-gate untouched |
| Tier probe header absent (proxy/gateway stripping) | Low | Fall back to threshold_base with a logged warning (`otpm_assumed=True` in the decision) — degrades to the body's Tier-4 constant, never crashes |
| Org OTPM contention from the probe itself | Negligible | One `max_tokens=1` request, skipped when N is far from the boundary, skipped in dry-run/force-sync |

## 11. Decision Rationale

| What | Why | Source | Alternatives considered |
|---|---|---|---|
| Sync threshold base = 2,000 | At Tier-4 Sonnet OTPM (400k) with ~100 output tok/judgment, ~2k requests ≈ the volume where sync wall-time (minutes, competing with live org sessions) crosses typical batch turnaround; below it sync is strictly faster | User decision 2026-06-12, token-audit fix #22 + threshold research (task body, "implement exactly; constants configurable"); tier table verified on rate-limits docs | Fixed N regardless of tier (rejected: Tier-2 OTPM is 4.4× lower → tier scaling); cost-based routing (rejected: body optimizes SPEED only) |

| OTPM divisor = 400,000 | Tier-4 Sonnet 4.x OTPM, the regime the 2,000 base was calibrated for; `threshold = base × otpm/400k` degrades gracefully to ~450 at Tier 2 | Body + rate-limits docs table (verified verbatim) | Hardcode Tier 4 (rejected by body); RPM-based scaling (rejected: OTPM is the binding judge constraint, body states) |
