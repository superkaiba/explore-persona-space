# Plan — #2578: make `scripts/verify_uploads.py` verify overflow-routed runs (multi-repo permanent-home resolution)

### 0.0 TL;DR (plain English)

- **What I'll do:** teach the upload-verification gate to search more than one HuggingFace repo. Today it only ever looks in the default data repo, so a run that wrote its files to the overflow repo gets every file flagged as "missing" even though everything is safely uploaded. I'll add a `--hf-data-repo` flag (and a matching `--hf-model-repo`), an automatic read of the run's own per-issue write-repo environment variable, automatic discovery via the `OVERFLOW_POINTER.json` breadcrumb the upload path leaves behind, and a report line naming exactly which repos were searched.
- **What I expect:** with no new flags, behavior is unchanged (same verdicts, same rows, one new header line). With the overflow repo supplied, re-checking #2389's uploads on a reconstructed listing goes from "1,311 of 1,312 files missing" to "everything found except the 22 merge-input files that were deliberately never uploaded" — plus one planted canary row that proves the search stayed scoped instead of sweeping the whole repo.
- **What would change my mind:** if any test shows the change can make the gate PASS a file that is not actually uploaded anywhere (the dangerous direction — this gate authorizes destroying a pod's disk), I redesign before shipping. Every new search path is additive-and-named, a file found in NO searched repo still FAILs, and a dedicated test pins the exact set of repo listings the tool is allowed to make.

### 4-A. Resolver (new, near the constants block)

```python
def _validate_repo_id_shape(repo: str) -> str:
    """'org/name' shape gate: exactly one '/', both halves non-empty.

    Catches the operator hazard of passing an HF *prefix* where a repo id
    belongs; a well-shaped but nonexistent id still fails loud downstream
    (RepositoryNotFoundError -> ERROR row). Raises ValueError.
    """

def resolve_data_repos(issue_num: int, cli_repos: tuple[str, ...] = ()) -> list[dict[str, str]]:
    """Ordered, deduped, ADDITIVE data-repo search set: [{"repo", "source"}].

    Order: HF_DATA_REPO ("default") first — the singleton no-flag set is
    byte-identical to today's behavior — then EPM_<issue>_DATA_WRITE_REPO
    when set/non-empty ("env:EPM_<N>_DATA_WRITE_REPO"), then each comma-
    split --hf-data-repo value in given order ("flag"). Dedup by repo id,
    first source wins. The default is NEVER removed (union is additive by
    design: a repo enters the search only when a named source supplies it).
    Deliberately does NOT read EPM_HF_OVERFLOW_ROUTING (arming switch, not
    a repo id; ambient via .env; see plan #2578 §3).

    Pointer-discovered repos are appended AFTER residue check 9 by the
    residue arm (source "pointer:<prefix>", carrying the payload's ts).
    That lane is CANONICAL-REPO-ONLY and ISSUE-grain — it reads pointers on
    the default repo at the caller-supplied prefixes only, so it is never
    exhaustive (a pointer committed to an env-named canonical under a
    chained reroute is missed — fail-closed). The flag + env lanes are the
    operator's coverage guarantee.
    """
```

No hub import needed (repo ids are data). Pointer-discovered repos are appended later (4-C) with `source="pointer:<prefix>"`.

### 4-C. Pointer discovery (inside `_hf_prefix_basenames`, two-pass)

```
pass 1: for each (prefix × static repo): scoped listing (existing call shape).
        If repo == HF_DATA_REPO: collect the FULL PATH of every listing entry
        whose basename == "OVERFLOW_POINTER.json" (the scoped listing is
        recursive and returns full paths, so a pointer committed under a
        NESTED sub-prefix — e.g. a per-cell reroute — is detected at its
        actual path). For EACH detected pointer path:
        stage_hub_file(HF_DATA_REPO, <listed pointer path>, <tempdir target>,
        repo_type="dataset") — fetched AT ITS LISTED PATH, never a
        reconstructed "<supplied-prefix>/OVERFLOW_POINTER.json" (which would
        EntryNotFound on a nested pointer — the round-1 F8 fetch mismatch);
        json.load; payload["overflow_repo"] must be a str passing
        _validate_repo_id_shape — anything else raises (malformed pointer =
        broken routing record; the existing except at the
        check_outroot_residue call site, lines 1720-1728, surfaces it as
        ERROR). Each distinct discovered repo is recorded as
        {"repo", "source": "pointer:<pointer parent prefix>",
         "ts": payload.get("ts")} — the ts ride-along (round-1 F10) makes a
        stale pointer auditable post-hoc.
pass 2: for each newly-discovered repo not already in the set: list ALL prefixes
        on it; union basenames; record coverage + discovered entry.
```

On by default; no flag to disable (it fires only when a pointer exists at a caller-supplied prefix on the canonical repo, and its failure mode is ERROR, not silent coverage).

**Sequencing (round-1 F8 — resolved by DOCUMENTING the check-9 ordering, not by restructuring).** Discovery executes inside residue check 9, and `run_verification` folds discovered repos into the search set after check 9 returns and before check 10 — so the row-index checks DO consume discovered repos, while the check-5 `--hf-dataset` branch has already run and never sees them, and dataset-only / row-index-only invocations (no residue arm) trigger no discovery at all: those shapes rely on the flag/env lanes. This is fail-closed in every shape — a repo the run wrote but discovery did not surface can only produce a wrong FAIL/MISSING (the operator then supplies `--hf-data-repo`), never a wrong PASS. Documenting was chosen over hoisting discovery ahead of check 5 because discovery rides the residue arm's existing scoped listings (zero additional Hub calls); a pre-check-5 discovery pass would duplicate those listings solely to serve invocation shapes where the flag/env lanes are load-bearing anyway, and would enlarge the diff §5(a)'s byte-parity certification has to cover.

### 4-D. Why this cannot go fail-open (the design constraint, addressed head-on)

The one mechanism that could convert this fix into a fail-open regression is the union making residue matching more permissive. Precisely: the residue verdict covers a disk file when its basename appears under a caller-supplied prefix in ANY searched repo — so a file that was never uploaded could be "covered" by a stale same-named file at the same prefix in another searched repo. Defenses, in order of load-bearing-ness:

1. **Every searched repo is named by a source asserting the run's ISSUE wrote there**: the default (today's behavior), the run's own per-issue env declaration, an operator flag, or a pointer the write path itself committed. Grain honesty (round-1 F2): the flag/env lanes assert a DECLARED write target for this issue; the pointer lane asserts ISSUE-grain provenance only — SOME attempt at this prefix rerouted to that repo, NOT that THIS run wrote there (no run/attempt identity exists in the payload to bind tighter). Docstrings and comments must carry the issue-grain wording, never "this run wrote there". No repo is ever searched speculatively (this is why `EPM_HF_OVERFLOW_ROUTING` is not read and why there is no "always also search overflow" shortcut).
2. **The stale-same-name hazard is not new** — it exists today within the single canonical repo (a stale earlier-attempt file at the same prefix covers a lost file; the #2359 content check closes it for the *git* arm only). The union multiplies locations by the caller-named set; it does not create the class. Stated as a residual in §7, with the per-repo coverage counts (4-B) as the audit surface. **Why content checks stay OUT of the HF arm's scope — reason corrected in round 1 (F1):** the blocker is the DIGEST-LESS LISTING-FORMAT CONTRACT, not download cost. Remote LFS sha256 / `blob_id` IS metadata-available from the `list_repo_tree` walk (`hub.list_repo_entries_complete`, hub.py:930–972 yields `(path, size)` with `RepoFile` LFS metadata), but the terminate gate's listing mode has nothing to compare it against: `_outroot_disk_entries` (verify_uploads.py:1498–1558) ingests a bare path-per-line `find` capture with no sizes and no digests, and `_file_size_or_unknown` (1486–1495) documents that pod paths cannot be stat'ed from the VM. The #2359 git-arm content check already degrades to WARN whenever `Path(full).is_file()` is False (`_match_outroot_files`, 1583–1587) — i.e. on every row of a pod-side listing — and that WARN degradation is the precedent shape any follow-up would extend. The scope-out STANDS; only the old "needs downloads" reason was wrong.
