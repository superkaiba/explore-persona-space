# Plan v1 — #2340: verify_task_body footer check for SHA-pinned GitHub links on named code/artifacts

## Requirement + acceptance criteria (kind: infra)

**Requirement.** `verify_task_body.py` gains a new check (check 61) that flags a v4
`**Repro:**`/`**Context:**` footer which NAMES code provenance (a branch + bare
`@ <sha>` code-sha mentions) or committed `eval_results/` artifacts as bare backtick
paths while the containing bullet/paragraph unit carries NO SHA-pinned
`github.com` `/blob/<sha>`-or-`/tree/<sha>` link. Surfaced by
`epm:clean-result-critique-codex v1` on #2330 r1; upheld by the binding reconciler
(`epm:clean-result-critique-reconcile v1`, item `footer-github-artifact-links`).

**Acceptance criteria:**
1. The #2330 **r1 shape** — `code on branch `issue-2330` @ `0ca8b47888`` plus bare
   `eval_results/issue_2330/...` backtick paths, zero github.com links in the unit —
   produces a WARN naming the offending tokens.
2. The #2330 **current (post-fix) footer** (bare `@ <sha>` mentions + bare
   eval_results tokens, but the same unit carries many `/blob/<40-hex>` +
   `/tree/<40-hex>` links) passes CLEAN — `uv run python scripts/verify_task_body.py
   --issue 2330` gains no new WARN/FAIL line from this check.
3. An `@ <hex>` that is an HF revision pin (check 44's S2 shape: `@ rev `6aab0cce1fac``
   after an HF-identity path) does NOT fire Class A — no cross-talk with check 44.
4. Non-v4 bodies are never flagged (forward-only via `is_v4`, PASS-skip note).
5. WARN never FAIL — no code path returns `passed=False` (check 44's severity
   precedent; a FAIL would newly block parked v4 bodies at promote-time re-verify).
   Severity reading recorded: SPEC § "All footer URLs pinned (v4)" states the
   requirement explicitly, but the whole footer-adjacency check family
   (43/44/45/46/50) is WARN + LM-critic backstop, and the mechanical-severity
   convention for a NEW adjacency check on an unswept corpus is WARN with a
   documented FAIL-flip path — that is the "per SPEC reading" resolution the task
   body delegates.
6. A corpus sweep over committed v4 bodies (all `tasks/*/*/body.md` carrying the v4
   sentinel) reports the new check's verdict per body; zero false positives on
   known-good footers (spot-check any WARN the sweep surfaces; #2330 must be clean).
7. Anti-scope honored (binding reconciler adjudication): the sibling proposal — a
   plan-fixed/bootstrap-name prose regex — is NOT implemented in any form.

## Method delta (vs existing checks)

Check 44 (`check_footer_hf_paths_pinned`, #1509) is the HF-side precedent: bare
backtick HF artifact paths must sit in a unit carrying an HF pin. Its gate G3
deliberately EXCLUDES git-side roots (`_GIT_SIDE_ROOTS`), and the existing git-side
checks all fire only when a URL/link is PRESENT (8/8b probe URLs, 42 probes body
URLs, 43 verifies claims adjacent to an existing tree link, 50 checks working-tree
cleanliness). Nothing fires when a git-side artifact/code mention has NO link at
all — exactly the #2330 r1 gap. Check 61 is check 44's git-side sibling filling
that complement. Clean partition: check 61 fires only when the unit has NO pinned
github link; check 43 fires only when one exists.

## File paths + concrete changes

1. **`scripts/verify_task_body.py`** — all changes additive:
   - New module-level regexes (near the check-44 block, reusing its conventions):
     - `_FOOTER_GH_PIN_URL_RE`: `github\.com/[^\s()`<>]+/(?:blob|tree)/[0-9a-fA-F]{7,40}\b`
       OR `raw\.githubusercontent\.com/[^/\s]+/[^/\s]+/[0-9a-fA-F]{7,40}/` — the
       unit-level satisfier. A moving-ref link (`/blob/main` etc.) never satisfies
       (not hex).
     - Class-A (code-sha) trigger: an `@\s*`?[0-9a-fA-F]{7,40}`?\b` occurrence in a
       unit that carries git-code identity — a backtick branch token
       (`` `issue-\d+[a-z0-9-]*` ``) or the word `code`/`commit`/`hot-fix`
       within the same unit — AND whose sha is NOT an HF-rev satisfier for an
       HF-identity token (precision gate: skip any `@ <hex>` whose nearest
       preceding backtick token in the unit matches check 44's HF-identity gate G2,
       i.e. `_HF_ISSUE_PREFIX_RE` or `_FOOTER_HF_ARTIFACT_SEG_RE` — that `@` is an
       HF revision, check 44 territory). Implementer may tighten further
       (precision-first; named recall residuals are the convention).
     - Class-B (git-side artifact) trigger: backtick token (check 44's
       `_FOOTER_HF_PATH_TOKEN_RE` charset) containing `/` whose FIRST path segment
       is `eval_results`. Scope deliberately eval_results-only in v1 (the task
       body's named class); other `_GIT_SIDE_ROOTS` (figures/, scripts/, docs/)
       stay named recall residuals — figures already have checks 8b/22/29.
   - New `def check_footer_code_artifacts_github_pinned(body) -> CheckResult`
     (check 61, WARN, v4-only): `is_v4` gate → `_v4_footer_text` → `_footer_units`
     (reuse both helpers; fence-aware + blockquote-stripped for free) → per unit:
     if `_FOOTER_GH_PIN_URL_RE` matches the unit, the whole unit is satisfied;
     else collect Class-A/Class-B offenders (per-body dedup, cap the detail list
     at ~8 tokens like check 44). Zero network, no env fences (pin absence is a
     body-text fact — the check-40/44 convention). Docstring records: incident
     (#2330 r1), severity rationale + FAIL-flip path, named recall residuals
     (paths outside backticks; non-eval_results git roots; a pin on an unrelated
     link in the same giant paragraph rescuing everything — unit-granularity
     bound, same trade check 44 states).
   - Header doc block: add the `- **check 61** (...)` entry in numeric position
     (after check 60's entry), same format as check 44's entry.
   - `CHECKS` list: register `check_footer_code_artifacts_github_pinned` next to
     `check_footer_hf_paths_pinned` with a `# check 61 (WARN, v4-only)` comment.
2. **`.claude/skills/clean-results/SPEC.md`** — § "All footer URLs pinned (v4)":
   append one enforcement-note sentence mirroring the check-44 note (WARN, no
   semantic change to the contract): a footer naming a code branch/commit sha or a
   bare backtick `eval_results/` path must sit in the same bullet/paragraph as a
   SHA-pinned github.com blob/tree link (check 61, #2340). The pinnedness
   requirement itself is already explicit at SPEC lines ~442-443/~682-689 — no
   semantic SPEC change needed, note-only.
3. **`tests/test_verify_task_body.py`** — mirror the check-44 test suite:
   - extend the CHECKS-registration assertion to include the new function;
   - WARN on the #2330-r1 shape (both classes, verbatim-derived fixture);
   - clean PASS on the post-fix shape (same tokens + in-unit `/blob/<40-hex>` link);
   - clean PASS on the HF-rev non-confusion shape (acceptance criterion 3);
   - PASS-skip on a non-v4 body;
   - separate-unit pin does NOT rescue (blank-line-separated bullet);
   - `/blob/main` moving-ref link does NOT satisfy;
   - blockquoted `**Context:**` verbatim-prompt text never fires (inherited from
     `_footer_units`, one pin test).
