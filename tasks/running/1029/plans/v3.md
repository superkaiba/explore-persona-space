## 1. Goal, requirement, acceptance criteria

**Goal (task body):** after N (2-3) consecutive pre-workload setup_failed / guestTerminate deaths on the SAME GCP rung, treat it as an advance trigger (next rung and/or the RunPod terminal rung), mirroring the #783 queue-timeout escalation; keep the crash-diagnostics persist behavior.

**Requirement:** the #763 failure mode — a boot-looping rung re-selected by every relaunch, burning the daily create cap (`gcp_attempts_today` 2→5 on `flexstart_l4`, 2026-07-03T03:53–04:48Z, manual RunPod override at 04:54Z) — must be broken automatically after at most N=2 consecutive same-rung pre-workload deaths, without weakening the single-occurrence exclusions (#669: a lone spot preemption / capacity death never fails over) or the crash-diagnostics persist (#658 Part A).

**Acceptance criteria:**
1. A simulated sequence of 2 consecutive pre-workload deaths on one rung for one issue produces EXACTLY ONE RunPod failover with reason `gcp_boot_loop_failover_runpod` (no double-fire on a repeated dead poll; idempotent via the existing `_failover_gcp_to_runpod` lease+sentinel bound and an INCARNATION-keyed increment — GCE instance identity `handle.job_id`, fallback `(attempt_id, gcp_launched_ts)`). 2. A SINGLE pre-workload death takes the ordinary dead path unchanged (terminal JSON as today).
3. After a streak ≥ N is recorded, a fresh `route()` on the auto chain skips that rung (RouteAttempt outcome `boot_loop_rung_skipped`) without bumping `gcp_attempts_today`, and the ladder proceeds to the next rung / SLURM / RunPod terminal rung.
4. Negative controls stay green: a lone capacity death does not fail over (`test_async_gcp_capacity_death_does_NOT_fail_over`); a workload crash still takes the #659 path with the #659 reason; `cpu-bigmem` never fails over to RunPod (streak still recorded, route-side skip still applies); the #783 byte-parity test `test_failover_seam_default_reason_unchanged_byte_for_byte` stays green.

## 3. Method delta

Every existing GCP→RunPod trigger keys on a SINGLE observation of one handle: a crash phase (#659), a queue age on a live sidecar clock (#783), a frozen phase + reachability alarm (#669). This trigger is the first to key on a REPEAT COUNT ACROSS VM INCARNATIONS: each death destroys the VM (`--instance-termination-action=DELETE`) and the relaunch writes a fresh handle sidecar, so the consecutive-death record cannot ride any per-handle state — it lives in the durable per-issue `LeaseStore` (`~/.eps-routing/issue-<N>.json`, flock'd), the same store that already persists `gcp_attempts_today` across exactly this cycle. Secondly, it is the first trigger with a ROUTE-side arm: because the re-driver after a sub-N death is a relaunch through `route()`, the ladder walk itself consults the streak and skips the poisoned rung — mirroring the existing quota-headroom rung skip — so any relaunch path is covered even when the poller-side escalation could not fire. **The re-drive contract, precisely:** a sub-N boot death lands `failure_class: code` on the ordinary dead path and is re-driven by the PER-ISSUE SESSION's crash-fix/relaunch loop (exactly what produced #763's four automatic relaunches, 03:52–04:43Z) or a manual `dispatch_issue.py`; the WATCHER capacity-retry pass re-drives only `no_compute_available` — it never re-drives a code-class death, but it IS a route()-traversing re-drive for the post-failover no-RunPod-capacity sub-case. A task with no live re-driver parks at `blocked` after death 1: no loop exists, no cap burns, and the breaker correctly stays disengaged (a breaker targets a loop; a loop requires a re-driver by construction).

### 4.1 gcp.py — deterministic setup-death classification in the TERMINATED window

`GcpBackend._non_running_poll_result` (gcp.py:4765-4819) currently discriminates only `wedged` and `done` on a TERMINATED instance; `eps/phase == "failed"` falls through to `terminal_terminated` — so the SAME trap-written death reads `terminal_setup_failed` if polled in the brief RUNNING window (gcp.py:4716-4731) but `terminal_terminated` if polled after shutdown. Extend the TERMINATED branch:

```python
if phase == "failed":

    # probe-failure and started=True cases remain timing-dependent — both are
    # today's behavior, deliberately preserved). A probe failure inside
    # _workload_started falls back to True (workload-started) by its existing
```

### 4.4 router.py — the route()-side rung skip

Inside `_attempt_one_gcp_rung`, immediately after the quota-headroom skip (router.py:4328-4351) and BEFORE the cap transaction, mirroring its exact shape:

```python
# #1029 boot-loop breaker: a rung with >= N consecutive pre-workload boot
# deaths TODAY for THIS issue is skipped on the auto chain — advancing to the
# next rung (and eventually the RunPod terminal rung) instead of re-creating
# a VM that just boot-looped. No daily attempt is consumed (the cap counts
# CREATES; a skip avoids the create). The explicit `backend: gcp` pin
# (count_attempt_cap=False) is EXEMPT — an explicit user ask attempts anyway,
# mirroring the cap exemption at router.py:4308-4311.
if count_attempt_cap:
    streak = gcp_boot_death_streak(spec.issue, rung_label, lease_store=store)
    if streak >= gcp_boot_death_streak_threshold():
        attempts.append(RouteAttempt(
            kind="gcp", cluster=None,
            est_start_seconds_raw=0.0, est_start_seconds_clamped=0.0,
            outcome="boot_loop_rung_skipped",
            detail=(f"rung {rung_label}: {streak} consecutive pre-workload boot "
                    f"deaths today (#1029 boot-loop breaker); skipping without "
                    f"burning a daily attempt"),
            elapsed_seconds=now_fn() - started_at,
        ))
        logger.warning("route: GCP rung %s boot-looped %d× today for issue %d; advancing.",
                       rung_label, streak, spec.issue)
        return "advance"
```

If every GCP rung skips, the auto chain proceeds to SLURM then the RunPod terminal rung by the existing lane order — the "next rung / RunPod naturally" half of the Goal.

The skip reads the REAL `rung_label` route() is currently walking, so the transitional `"unknown_rung"` lease key (written only by the poller for pre-fix handles) can never match a route-side read — the skip is structurally immune to the unknown_rung pool.

## 11. Decision Rationale (the 7 design questions)

1. **N = 2** (env `EPS_GCP_BOOT_DEATH_STREAK_N`). *Why:* first death gets one free retry (a lone setup death can be a clone/uv-sync transient — #763's own 04:17Z note hypothesized exactly that); the second consecutive identical death is the loop signature. *Source:* `.claude/rules/gotchas.md` #640 entry — "allow exactly ONE blind GCP retry, then pivot to RunPod" is the documented manual protocol for this exact guestTerminate class; #775 CUDA-IMA pivots on the SECOND same-signature crash. #763's session breaker fired at 3 only because nothing automated existed; each cycle costs ~6-8 min + 1/8 of the daily cap, so N=2 saves 2+ creates vs N=3. *Alternatives:* N=3 (body's upper bound) — rejected as strictly more cap burn with no added protection beyond what the one-retry precedent grants; N=1 — rejected (kills legitimate transients).
2. **Record home = the durable per-issue `RouterLease`** (`~/.eps-routing/issue-<N>.json`, flock'd `LeaseStore.transaction`). *Why:* it is the only candidate that demonstrably survives the death→relaunch cycle — the sidecar is REWRITTEN fresh by each re-dispatch and the #775 sidecar-extra channel only survives via its epm:failure-marker fallback, which is orchestrator-posted and fragile to parse for a COUNT; the lease already persists `gcp_attempts_today` across route() calls and backend_poll already reads/writes it (`_lease_records_failover_of` / stamp helpers), so no new import direction. *Source:* #763 events (`gcp_attempts_today` 1→5 across the exact cycle); router.py:1080-1211 (LeaseStore flock + transaction); #659 round-3 (durable lease as the authoritative cross-tick record). *Alternatives:* sidecar extra (destroyed on relaunch — rejected); a separate `.claude/cache` per-issue JSON (unflocked, EDQUOT-fragile — the exact mode #659 round 3 fixed by moving to the lease — rejected).
3. **Fire site = (c) both, asymmetric:** poller-side escalation at N (the #783 shape, straight to the RunPod terminal rung via the shared `_failover_gcp_to_runpod` core) as the PRIMARY breaker, plus a route()-side rung skip as the relaunch-path defense. *Why:* the poller-side arm breaks the loop at the Nth death with no relaunch decision needed and inherits the core's exactly-once bound; but it is observation-dependent (a post-DELETE tick may be unclassifiable), and re-drive paths bypass it entirely — the per-issue session's crash-fix relaunch of a sub-N `code`-class death (the #763 re-driver; NOT the watcher, whose capacity-retry pass re-drives only `no_compute_available`, e.g. after a boot-loop failover that found no RunPod capacity), and a manual `dispatch_issue.py` relaunch — all of which pass through `route()`, where the skip (quota-headroom-skip shape, router.py:4328-4351) keeps the poisoned rung out of the walk. Route()-side-only was rejected because it cannot fire without a recorder anyway (route() never observes deaths) and leaves the Nth-death tick posting an ordinary failure that waits on a relaunch decision. *Source:* #783 (`_maybe_escalate_gcp_queue_timeout` → predicate → `_failover_queued_gcp_to_runpod`); router.py:4328-4351 (the skip template); backend_poll.py:3059-3083 (wiring point).
4. **Scoping = (issue, rung), same-UTC-day, reset on observed boot success.** *Why:* #763's loop was rung-specific for THIS issue's branch (`flexstart_a100_80` booted fine an hour earlier; the retrodiagnosis points at issue-763's own staging step) — fleet-wide (rung-only) keying would let one issue's bad commit poison a rung for every issue, and the lease is per-issue by construction (a fleet-wide record would need a new shared store + locking). Same-day scoping reuses the `gcp_attempts_date` rollover pattern; reset on a workload-phase observation (or `terminal_workload_failed`) implements "consecutive"; attempts on OTHER rungs neither increment nor reset a rung's streak (the rung stays poisoned until it boots or the day rolls). *Source:* #763 events; router.py:4369-4370 (day-rollover pattern). *Alternatives:* fleet-wide rung health — rejected (cross-issue confound + storage change); no-TTL — rejected (a stale streak would poison a rung after the cause — often a since-fixed commit — is gone).
5. **Crash-diagnostics preserved:** the change touches ONLY post-classification routing. `_eps_persist_diagnostics`, the startup-script render (snapshot-pinned), the `eps/workload_started` sentinel write, and the §4.1.0b RUNNING-window discrimination are all byte-untouched; §4.1 adds a read-side branch in `_non_running_poll_result` only. *Source:* gcp.py:1355-1371, 4716-4731; `tests/test_gcp_backend.py` snapshot test.
6. **CPU-intent guard parity: YES for the RunPod-failover action, NO for the skip.** The escalator/predicate apply the exact #677/#747 `RUNPOD_CPU_INSTANCE_FOR_INTENT` guard (a `cpu-bigmem` boot-loop must never fail over to RunPod — no lane; `cpu-small`/`cpu-mid` are eligible), but the streak still RECORDS for excluded intents so the route()-side skip — a GCP-internal advance, no RunPod involved — remains `cpu-bigmem`'s breaker (skip → next GCP CPU rung → exhaustion → the typed `cpu_exhausted_no_runpod_lane` terminal, verbatim #677). *Source:* backend_poll.py:522-531 + 772-779 (the two existing guard sites); `.claude/rules/compute-backend-failover.md` § CPU intents.
7. **Cap interaction: no change needed — verified.** `gcp_attempts_today` bumps ONLY inside `_attempt_one_gcp_rung`'s create transaction (router.py:4399-4402); the poller-side failover never re-enters it (same argument as #783's "clean advance"), and the route()-side skip returns `"advance"` BEFORE the transaction — pinned by the two no-increment tests (§5). The skip therefore STOPS cap burn rather than counting toward it, which is the fix's point. *Source:* router.py:4353-4402; the #783 test `test_gcp_queue_timeout_does_NOT_increment_gcp_attempts_today`.
