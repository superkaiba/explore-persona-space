## Exact bullet content

The implementer copies the following VERBATIM as a new top-level list item, inserted
between line 84 (`prompt_logprobs` OOM) and line 85 (`preflight --json` parse). It
matches the surrounding style: bolded trap name first, signature, recipe, when-it-

fenced env-var block indented under the bullet as in the surrounding entries.)

````markdown
- **CUDA-allocator fragmentation OOM on long teacher-forced multi-layer captures — workload-cmd hot-fix, NOT a code bug.** A multi-layer activation capture on a 7B-class model (e.g. Qwen-2.5-7B, teacher-forced answer-side capture) runs healthy through thousands of forwards then OOMs INSIDE the `lm_head` linear of the next forward, with the signature `torch.OutOfMemoryError: CUDA out of memory. Tried to allocate <N> GiB. GPU 0 has a total capacity of 79.25 GiB of which <small> GiB is free. ... <X> GiB is reserved by PyTorch but unallocated.` — the tell is **reserved-but-unallocated `> ` the request size** (e.g. 26.9 GiB reserved-but-unallocated, 12.3 GiB free, yet a single 12.54 GiB `lm_head` intermediate cannot fit). This is the PyTorch CUDA caching allocator FRAGMENTED — enough total free, no contiguous block — NOT a true headroom shortfall (the per-forward `(B, T, H)` buffer clearly fits, the first thousands of forwards succeeded). This is DISTINCT from the sibling CUDA-OOM entries: it is not the `prompt_logprobs` float32-logits single-allocation OOM (above; fixed by `max_num_batched_tokens`/`gpu_memory_utilization`), not the vLLM teardown / KV-cache pin (the vLLM family above; a separate allocator), and not the CVD-clobber co-location OOM (multi-process device pinning). The PyTorch error message itself recommends the fix. RULE: hot-fix with TWO `--workload-cmd` knobs, NO script edit, NO implementer bounce:

      # both knobs in the launch command (GCE startup --workload-cmd OR the RunPod launcher wrapper):
      PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True \
        uv run python scripts/<your_capture_driver>.py --batch-probes 8

  1. `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` — env var, switches the allocator to expandable-segments mode which defragments internally; the crash message recommends exactly this. No code change.
  2. Halve the per-forward batch (`--batch-probes 16 → 8` or equivalent) — halves the `(B, T, H)` per-layer capture buffer + the `lm_head` intermediate. Throughput hit is ~2× wall-clock per phase, the right trade vs an OOM kill.

  **When it matters:** any long-running activation-capture / teacher-forced multi-layer forward loop on a >7B-param model. Triggers more often on A100-80 than H100 (same 80 GB HBM, but the A100 memory-pool topology fragments more aggressively under PyTorch); the SAME fix works on both — try it FIRST before reducing model size or moving lanes.

  **CAVEAT — re-measure peak RESIDENT after enabling, especially on co-residency GPU paths.** `expandable_segments:True` trades fragmentation reduction for a HIGHER peak resident footprint — so the NEXT OOM can surface at the new peak, NOT the fragmentation point you just fixed. Re-measure peak resident under the REAL workload after enabling, especially on co-residency paths (HF model + vLLM engine in one process, or any two large allocators sharing a GPU). Canonical co-residency case: #545 r4 — the HF base-model resident grew from ~22 → ~30 GiB under co-residency once expandable segments was on (validated in #673's `figures/issue_673/memory_curves_expandable_segments_on.json`).

  **NOT a code-class bug:** the capture script is correct; the allocator behavior is the issue. Do NOT bounce to `experiment-implementer` for a code change — hot-fix the workload command and relaunch. Cross-ref (long-form recipe): `.claude/agent-memory/experimenter/feedback_cuda_oom_expandable_segments.md`. (Incident #761 r3 relaunch, 2026-06-30: GCP A100-80 OOM at ~6000 forwards into a 150-capture sweep — sycophancy 50 ctx + refusal 50 ctx fully captured, then OOM at `lm_head` on the first `harmful_compliance` forward; recovered via manual GCP→RunPod failover with the hot-fix in the workload-cmd.)
````
