# Plan — #979 workflow-fix: watcher greps USER PAUSE note before respawn

`architectural: false` — this adds a guardrail branch to an existing, established exemption pattern inside one watcher script (plus tests). No status enum, marker schema, task.py subcommand, or file location changes; the new exemption-action string is internal to `autonomous_session_watch.py` (same class as the existing `"spend-approval-skip"`).

## 0.0 TL;DR (plain English)

- **What I'll do:** teach the 10-minute watcher to recognize a note that begins with the literal `USER PAUSE` on a task's event log, and — instead of auto-respawning a session against that hold — post a one-time alert telling the human to make the pause durable (`set-status on_hold`). Same mechanism the watcher already uses for the over-cap spend-approval park.
- **What I expect:** replaying the #816 incident shape through the new probe yields "alert, don't respawn"; all existing watcher tests keep passing; ~17 new tests pin the predicate (incl. a case-sensitivity negative — the round-1 statistics Must-Fix), the disarm rule, the once-per-episode dedup, and that the respawn budget is never consumed.
- **What would change my mind:** if the anchored `USER PAUSE` prefix turned out to match ordinary agent notes in the live task corpus (it doesn't — a fleet-wide scan today found 3 matches, all genuine user holds), or if the disarm rule could permanently mask respawn coverage for a resumed task (it can't — resume paths post markers that disarm it, and a resumed session's live registration bypasses the probe entirely).

## 4. Design

### 4.1 Method delta vs the spend-approval exemption (what is genuinely new)

| Aspect | Spend-approval (#653, existing) | USER-PAUSE hold (this task) |
|---|---|---|
| Trigger signal | Dedicated marker KIND `epm:awaiting-spend-approval` | Note SHAPE: anchored prefix `USER PAUSE` on ANY marker kind (a prose hold is non-canonical by definition — it has no kind) |
| Supersession | `_latest_progress_ts > spend_ts`; the spend marker's kind is outside `_PROGRESS_KINDS`, so self-inclusion never arises | Same rule, but STRICT `>` is load-bearing: the pause note itself usually rides `epm:progress` / `epm:status-changed` (both IN `_PROGRESS_KINDS`), so `progress_ts == pause_ts` means "the pause IS the latest word" → suppress |
| Dedup anchor | Skip-sentinel marker ts ≥ latest spend marker | Skip-sentinel marker ts ≥ latest pause note |
| Everything else | — | Identical: alert-only, budget-free, events-log dedup, both hook points, sentinel in `_WATCHER_NOTE_SENTINELS`, probe gated behind `action == "respawn"` (orphan) / `action != "keep" or new_missed > 0` (stalled) |

### 4.2 Detection predicate (design question 1 — decided)

```python
_USER_PAUSE_NOTE_PREFIX = "USER PAUSE"   # case-SENSITIVE, anchored prefix
# match: (ev.get("note") or "").lstrip().startswith(_USER_PAUSE_NOTE_PREFIX)
```

- **Anchored prefix, not word-boundary substring.** All four observed variants begin with the literal; every observed false-positive candidate (markers on #919/#920/#979 that QUOTE the format, plan/critique notes citing SKILL.md) carries it mid-note. The fleet-wide corpus scan confirms 3/3 anchored matches are genuine holds, 0 false positives. A substring match would flag #979's own clarify marker and #816's workflow-fix-candidate marker — disqualifying.
- **Case-sensitive.** Uppercase `USER PAUSE` is the deliberate hold-format signature (SKILL.md + all live instances); lowercase "user pause ..." occurs in ordinary discussion prose and must not arm the probe.
- **All marker kinds scanned** (note-anchored, minus watcher-sentinel notes). The prose-hold anti-pattern is non-canonical, so kind-gating buys nothing: the #816 instance rode `epm:progress`, the durable-park note rides `epm:status-changed`, and the next offender could ride anything. The anchor bounds false positives; the kind does not need to.
- **Residual false-positive class, accepted:** an agent note that BEGINS with the literal (e.g. an implementer round note on this very task starting "USER PAUSE prose-hold exemption implemented ..."). Failure direction is safe: alert-only suppression (no respawn), one deduped self-describing marker, and it disarms on the next real progress marker. The opposite anchor error (missing a real hold) recreates the #816 incident — strictly worse. Implementation discipline: the new tests' event-helper notes must not themselves begin with the bare literal outside pause fixtures.

### 4.3 Supersession semantics (design question 2 — decided)

Mirror `_spend_approval_park_reason` exactly:

```python
def _user_pause_hold_reason(events: list[dict]) -> str | None:
    pause_ts = _latest_user_pause_ts(events)      # newest anchored-prefix, non-watcher note (any kind)
    if pause_ts is None:
        return None
    progress_ts = _latest_progress_ts(events)     # existing helper: _PROGRESS_KINDS minus watcher sentinels
    if progress_ts is not None and progress_ts > pause_ts:   # STRICTLY newer
        return None
    return "<reason string>"
```

- Suppression applies only while NO real progress marker (`_PROGRESS_KINDS`, watcher-sentinel-filtered) is strictly newer than the newest pause note.
- **Suppression cannot persist through any CANONICAL resume path** — three independent disarms: (a) the SKILL.md resume runs `task.py set-status <N> <paused_from>` → posts `epm:status-changed` (in `_PROGRESS_KINDS`) strictly newer → disarms; (b) a resumed live session posts `epm:progress`/`epm:results`/... notes → disarms; (c) while a resumed session is REGISTERED and live, `decide_orphan` returns `"clear"` / the exemption is only probed on a would-be respawn — the probe is never even consulted.
- **Narrow (`_latest_progress_ts`) rather than broad (`_latest_nonwatcher_event_ts`) chosen deliberately:** under broad, any third-party bookkeeping note posted after the pause (e.g. #816's own `epm:workflow-fix-candidate` marker, posted 2h after the hold) would disarm the hold and re-open the exact respawn-against-hold incident. Under narrow, the worst case is sticky suppression of a task resumed WITHOUT any `_PROGRESS_KINDS` marker (an unregistered manual resume that dies before posting anything). Outside paths (a)-(c) suppression persists until ANY progress marker, set-status, fresh pause note, or registered spawn lands — the one-time alert is the only signal in that window (named honestly in §8 risk row 2 + kill criterion (b); the probe docstring carries the same caveat).

### 4.4 Where the probe fires (design question 3 — decided: BOTH passes)

- **Orphan-respawn pass** (the incident's arm — #816's respawn was `[autonomous_session_watch:orphan-respawn]` attempt 1/2): probe in `_check_orphan_followups_exemption`, FIRST (before the spend-approval probe — an explicit user directive is the most specific gate signal; both are alert-only so ordering only picks which alert text posts, and the pause alert carries the actionable durable-fix recipe). Gated behind the existing `action != "respawn"` early return, so healthy tasks pay nothing.
- **Stalled-session pass**: one mirrored branch at the top of `_apply_stalled_followups_exemption`. Rationale for including it despite the minimal-scope bias: (i) the shared pure probe + shared alert helper make it a ~6-line branch with its own 1-2 tests — the "shared probe makes both trivially safe" escape in the design brief; (ii) the uncovered shape is real: a user pause whose session is left registered-and-idle cycles through the stalled detector, which would STOP the session and respawn — equally against the hold; (iii) the mirrored-in-both-arms shape IS the house pattern (the spend-approval exemption ships in both arms as one design). This is still the single experimental variable (the USER-PAUSE prose-hold exemption) at its two standard hook points.
- **NOT the crash-recovery `decide()` arm** (registration-keyed respawn of a dead-sid session). Out of scope: the candidate names the orphan pass; #816's session was deliberately stopped (registration removed → orphan class, not crash class); a crash microseconds after posting a prose hold, with the registration retained, remains a known residual gap — named in §8 Risks and left to the durable `on_hold` park (#919, the real fix) rather than widening this diff.

### 4.5 Escalation action (design question 4 — decided)

- **Action string:** `"user-pause-hold-skip"` — added to `_ORPHAN_EXEMPTION_ACTIONS`, routed by `_dispatch_orphan_exemption_action` to the new handler.
- **Sentinel:** `_USER_PAUSE_SKIP_NOTE_SENTINEL = "[autonomous_session_watch:user-pause-hold-skip]"`, added to `_WATCHER_NOTE_SENTINELS` (mandatory: the alert lands on the very task whose staleness it measures).
- **Handler behavior** (mirror of `_handle_orphan_spend_approval_skip`): post the alert at most once per pause episode — dedup self-contained in the events log via `_user_pause_skip_already_noted(events)` (a sentinel-carrying marker with ts ≥ the latest pause note; a FRESH pause note re-arms the alert) — then `_save_orphan_state` WITHOUT incrementing `respawns_today`. No per-pass state flag needed (the spend-approval precedent).
- **Channel: deduped `epm:progress` marker only** (via the existing `_post_progress_marker`), exactly like spend-approval-skip — no Telegram push, no sidecar row. Rationale: consistency with the mirrored exemption (equally user-action-gated, marker-only); the marker is dashboard-visible; a push per deliberate short hold would nag. Alternative (fail-soft `_telegram_push`) rejected for scope symmetry — trivially addable later if holds go unnoticed.
- **Alert-wording discipline:** the alert note itself begins with the sentinel (never the bare literal), and its resume-recipe example must NOT begin with `USER PAUSE` (a resume note that does would re-arm the probe — advise "post a progress note that does not begin with 'USER PAUSE'"). The probe docstring also notes that the CANONICAL durable-park note (which begins `USER PAUSE` on `epm:status-changed`) arms the probe harmlessly — `on_hold` is in the watcher PARK set, so parked tasks are never orphan-evaluated.
- **Alert text tells the human the durable fix** (approximate; final wording free — must contain the stable substring `on_hold`, asserted by tests 10/11):
  > `[autonomous_session_watch:user-pause-hold-skip] <reason>. Respawn suppressed (does NOT consume the daily respawn budget). A prose-only hold is NOT durable — make it durable per .claude/skills/issue/SKILL.md § User pause affordance: CRON-TEARDOWN + stop any RUNNING pod (pod.py stop --issue <N>), THEN task.py set-status <N> on_hold --note "USER PAUSE (verbatim: '...'); paused_from=<status>; resume: ...". To resume instead: task.py-post a real progress note or spawn_session.py spawn-issue --issue <N> --auto.`

## 11. Decision Rationale

*Hyperparameter table: N/A — no model training; no training hyperparameters in this task type.*

- **Anchor = case-sensitive `lstrip().startswith("USER PAUSE")`, any marker kind.**
  - Why: covers all 4 observed variants (which share only the leading literal); excludes every observed quote-class marker; kind-gating adds nothing for a by-definition non-canonical note.
  - Source: SKILL.md § User pause affordance line 337 (canonical format); `tasks/on_hold/816/events.jsonl` (incident variant); #919 body (older variant); #920 events (fourth variant); fleet-wide corpus scan 2026-07-04 (3/3 genuine, 0 false positives).
  - Alternatives: word-boundary substring (rejected — flags #979/#816/#980 quote markers); regex on the full canonical format `^USER PAUSE \(verbatim:` (rejected — misses the #816 incident note itself AND the #919/#920 variants, i.e. fails the very incident class); kind-gated `epm:progress`+`epm:status-changed` only (rejected — no false-positive benefit shown, real miss risk for the next variant).
- **Supersession = no `_latest_progress_ts` marker STRICTLY newer than the newest pause note.**
  - Why: exact mirror of the proven `_spend_approval_park_reason` (line 7069); strict `>` handles the pause note's self-inclusion in `_PROGRESS_KINDS`.
  - Source: `_spend_approval_park_reason` + `_latest_progress_ts` (lines 7069/3690), incident #653 precedent; #816 timeline (pause 06:44Z → respawn 08:33Z with only watcher/parked markers between — the rule fires correctly on replay).
  - Alternatives: broad `_latest_nonwatcher_event_ts` (rejected — #816's own post-incident bookkeeping markers would have disarmed the hold, re-opening the incident); "latest non-watcher event must BE the pause note" (rejected — stricter than the mirrored pattern for no gain; a parked `epm:step-completed` re-post would disarm it wrongly); TTL-based expiry (rejected — a user hold is indefinite by definition; SKILL.md resume is user-greenlight-only).
- **Fires in BOTH the orphan and stalled passes.**
  - Why: the incident arm is orphan; the stalled arm covers the live-idle-session pause shape at ~6 marginal lines via the shared probe; the mirrored-two-arm shape is the existing spend-approval design.
  - Source: `_check_orphan_followups_exemption` (9289) / `_apply_stalled_followups_exemption` (8003) — the #653 exemption ships in both; #919 body confirms #816's respawn was the orphan pass.
  - Alternatives: orphan-only (rejected per the design brief's escape clause — the shared probe makes both trivially safe); + crash-recovery `decide()` arm (rejected — different keying, unobserved failure shape, widens the diff; named residual in §8).
- **Exemption action `"user-pause-hold-skip"`; marker-only alert; events-log dedup; budget-free.**
  - Why: byte-for-byte the `"spend-approval-skip"` posture — same user-action-gated class, same routing table, same dedup mechanism (no new state-file field), same no-budget rule.
  - Source: `_handle_orphan_spend_approval_skip` (9434), `_spend_approval_skip_already_noted` (7108), `_ORPHAN_EXEMPTION_ACTIONS` (9483).
  - Alternatives: Telegram push (rejected for posture symmetry; addable later); per-state `alerted` flag in the orphan state file (rejected — the events-log dedup is self-contained and re-arms on a fresh pause episode for free).
- **Probe checked BEFORE spend-approval in both arms.**
  - Why: an explicit user directive is the most specific signal; both outcomes are alert-only, so ordering only selects the more actionable alert text.
  - Source: the "checked FIRST — most specific gate" ordering comment at line 9310-9317.
  - Alternatives: after spend-approval (harmless, but the pause alert's durable-fix guidance is the right message when both apply).
