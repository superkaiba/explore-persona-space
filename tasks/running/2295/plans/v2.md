# Plan v2 — #2295 workflow-fix: `sync_repo_root` deadlocks on the abandoned-rebase husk it exists to clear

kind: infra · TDD: no · workflow-surface only

Estimated GPU-hours (total): 0

## 0.0 TL;DR

Two blocked-writers-vs-recovery defects, one round. (1) Every `task.py` mutation resolves
the repo root — and therefore pays the bounded rebase-husk wait — INSIDE the
`~/.task-workflow/lock` flock, while the only sanctioned clearer of an abandoned husk
(`sync_repo_root.py` `preflight`) needs that same flock: mutual starvation, observed as
`state=error exit=5` on 2026-08-14. Fix: resolve the root BEFORE taking the flock (the
resolution needs no lock — it reads no task state and writes nothing). (2) The 5 stranded
bare autostash entries are surfaced only as a repo-level alert with no owner; fix by
attributing each entry to the task(s) its file list names, escalate-only.

**What would change my mind:** if the flock turned out to be load-bearing for the
resolution itself (it is not — §3), or if priming outside the lock introduced a new
concurrency exposure on the off-main routing path (it does not — `_ensure_managed_main_worktree`
carries its own guard and every READ path already reaches it lock-free), the ordering fix
would be wrong and option 2 (a liveness-gated scoped escape in the helper) becomes the
primary. If test A2 cannot demonstrate the helper acquiring the flock while a writer waits
on a real husk, the mechanism claim is unproven and the round halts and reports rather
than shipping.

**Kill criteria (halt and report, do not paper over):** (a) A1/A2 cannot be made
deterministic within a bounded wall (no unbounded sleeps, no retry-until-green); (b) any
pre-existing husk/lock test in `tests/test_task_workflow_worktree.py` or
`tests/test_sync_repo_root.py` regresses and the fix cannot preserve it; (c) the Change-D
attribution leg cannot be made escalate-only (D2) — then drop D from the round and ship
A/B/C alone rather than weakening the never-pop invariant.

## 1. Goal (verbatim from the task body)

> Make the sanctioned root-sync recovery able to clear an abandoned rebase husk even
> while blocked `task.py` writers hold the task-workflow lock, and make the
> stranded-autostash backlog converge instead of accumulating.

## 2. Verified findings (read from code at plan time, not inherited as premises)

Every line reference below was read this session; the body's chain is CONFIRMED.

**F1 — the husk wait sits INSIDE the flock (the deadlock's root).**
`scripts/task.py` `main()` (L2202-2219) parses args and dispatches straight into the
subcommand; it never resolves the repo root first. Every mutation body opens with
`with _locked():` and then calls `find_task_path(N)` (e.g. `set_body`,
`src/explore_persona_space/task_workflow.py:5913-5914`), and
`find_task_path` (L4896-4914) → `_load_registry()` → `registry_path()` → `tasks_dir()`
→ `repo_root()`. `repo_root()` is the lazily-`lru_cache`d resolver whose branch guard
(L440-549) bounded-waits on a primary-checkout rebase state dir
(`EPM_TASKPY_REBASE_WAIT_SECONDS`, default 120 s, L331-341). So the FIRST resolution —
and therefore the whole 120 s wait — happens while the writer already holds
`~/.task-workflow/lock`. The flock (L797-810) is a bare blocking
`fcntl.flock(fd, LOCK_EX)` with no timeout, so with ~15 concurrent writers the lock is
continuously held and a natural gap never arrives (the incident's rotating holder PIDs
3309523 → 3373777 → 3415906 over ~4 min are exactly this).

**F2 — the helper's single lock acquisition is the one that starves.**
`scripts/sync_repo_root.py::acquire_task_workflow_lock` (L724-748) is `LOCK_NB` + 2 s
poll under a `wait_s` deadline, raising `SyncAbortError(EXIT_PRECONDITION)` — the
observed `state=error exit=5`, `task-workflow lock still held after 120s`. It has
EXACTLY ONE caller: `_run_locked` L1946-1957 (`fd2 = acquire_task_workflow_lock(
_lock2_wait_s())`), which gates `preflight()` (L765-892) — and `preflight` is where the
sanctioned husk clearing lives (L793-880: `rebase --abort` / `merge --abort` via
`_abort_with_lock_retry`). One caller bounds the blast radius of any ordering change.

**F3 — the false assumption is written down as a comment.**
`task_workflow.py:493-503` says: "No deadlock while a caller waits here holding the
task-workflow flock: sync_repo_root.py acquires that flock BEFORE its pull_rebase, and
that acquisition is itself LOCK_NB-bounded — the observed rebase never needs the flock
to finish." That is TRUE for a LIVE rebase the helper itself drives (it holds the flock
first, so waiters cannot block it) and FALSE for an ABANDONED husk: nobody will ever
finish that rebase, and the only sanctioned clearer needs the very flock the waiters
hold. The comment is the encoded defect, not just documentation.

**F4 — husk-age thresholds** (`sync_repo_root.py` L251-270): stale at
`EPM_ROOT_SYNC_HUSK_AGE_S` = 3600 s; the young-husk liveness downgrade window is
`EPM_ROOT_SYNC_HUSK_MIN_AGE_S` = 600 s .. 3600 s, and fires only when
`_probe_git_liveness` (L652-721) returns `none`.

**F5 — NEW (not in the body): the liveness downgrade can be defeated by the waiters'
own polling.** `_probe_git_liveness` attributes every `comm == "git"` process by its
CWD (`git rev-parse --absolute-git-dir` from `/proc/<pid>/cwd`). Each waiting writer
re-probes with a `git -C <parent> symbolic-ref` subprocess every
`EPM_TASKPY_REBASE_POLL_SECONDS` (2 s, L344-351), and fleet sessions typically run with
cwd AT the repo root — so those short-lived READ-ONLY probes attribute to this repo and
read as `holder`. In the exact scenario the downgrade exists for, it can therefore
refuse. Consequence: for a husk in the 600-3600 s band, convergence may have to wait
for the 3600 s stale threshold (after which the abort runs with no probe at all,
L802-822). This is a bounded delay, not a wedge, and is INDEPENDENT of the ordering
fix. Recorded as a named residual (§6 R4); deliberately NOT fixed in this round
(argv-based exclusion of read-only git verbs would weaken a probe whose whole contract
is fail-closed-when-uncertain, and it is unnecessary once §4.1 lands).

**F6 — autostash surfaces.** All read-only today: `_autostash_entries` (L1287),
`_triage_autostash` (L1651-1692, rewrites rescue patches, pops/drops nothing),
`_warn_autostash_backlog` (L895-907, count-only WARN), `_stash_file_list` (L1603-1610).
The watcher's pass 34 `stash_rescue_audit_pass`
(`scripts/autonomous_session_watch.py:9112-9205`) collects an aged backlog
(`_collect_stash_rescue_backlog` L9031), fingerprints the SET (L9080), and fires ONE
repo-level Telegram push + one sidecar row, **posting NO task markers** and naming
human companion task #1736. That is precisely the "repo-level alert nobody owns" the
body reports: 5 entries, oldest 2026-07-26, every one `apply --check: dirty`.

**F7 — the body's option 3 already exists.** The proposed
"bounded-wait knob (`EPM_ROOT_SYNC_TASK_LOCK_WAIT_S`)" is
`EPM_ROOT_SYNC_LOCK2_WAIT_S` (L246-248, default 120 s), shipped since #996 and already
exercised by `tests/test_sync_repo_root.py::test_writer_holding_task_lock_past_bound_exits_5`.
Option 3 is a no-op: raising an existing bound cannot fix a continuously-held lock.

## 3. Options considered → decision

| # | Option (from the body) | Verdict |
|---|---|---|
| 1 | **Ordering fix** — have `task.py` wait for the husk BEFORE acquiring the flock | **CHOSEN** (§4.1) |
| 2 | Scoped escape — let the helper's husk-clearing path proceed without the task-workflow lock when a liveness probe shows no live git process | REJECTED as primary; documented fallback |
| 3 | Bounded-wait knob `EPM_ROOT_SYNC_TASK_LOCK_WAIT_S` | REJECTED — already exists as `EPM_ROOT_SYNC_LOCK2_WAIT_S` (F7) |

The body's own precondition for option 1 — *"verify the flock is not load-bearing for
the husk-wait itself"* — is DISCHARGED: the wait's only operations are
`git -C <parent> symbolic-ref --short HEAD` and two `Path.is_dir()` probes of the
common dir (L454-460, L370). It reads no task state, writes nothing, and touches no
file the flock protects. The flock is load-bearing for the MUTATION that follows the
resolution, never for the resolution itself.

**Why option 2 is not the primary.** (a) It weakens the mutual exclusion `preflight`'s
abort genuinely needs: `rebase --abort` moves HEAD and re-applies the autostash while a
`task.py` writer could be mid-`git commit` — the exclusion window is the reason
`_run_locked` takes the second lock at all. (b) Per F5 the probe would very likely read
`holder` in this exact scenario (the waiters' own polls), so the escape would not have
fired in the incident. (c) Once §4.1 lands there is no contention left to escape from.
Kept as the recorded fallback if a future incident shows a flock holder blocking on
something OTHER than the husk wait.

**Autostash convergence** — three shapes considered: (i) status quo repo-level push (does
not converge: 19 days and 5 entries prove it); (ii) auto-pop / drop (FORBIDDEN by the
body's invariant — every entry is `dirty`, an automatic pop conflicts against live
sibling work); (iii) **per-entry attribution to the OWNING task** (CHOSEN, §4.4): the
stash file list names the issues directly, so each entry gets a durable marker on the
task whose session can actually adjudicate it. Escalate-only; pops, drops and applies
stay out of the watcher entirely.

## 4. Implementation

### 4.1 Change A — `_locked()` resolves the repo root BEFORE taking the flock

`src/explore_persona_space/task_workflow.py`, `_locked()` (L797-810). Insert the
resolution as the first statement, above `LOCK_DIR.mkdir(...)`:

```python
@contextlib.contextmanager
def _locked() -> Iterator[None]:
    """... (existing docstring) ..."""
    # #2295: resolve (and lru-cache) the repo root BEFORE taking the flock.
    # The resolver's branch guard bounded-waits up to
    # EPM_TASKPY_REBASE_WAIT_SECONDS on a primary-checkout rebase state dir,
    # and the ONLY sanctioned clearer of an ABANDONED husk
    # (sync_repo_root.py preflight -> `git rebase --abort`) needs THIS flock:
    # waiting inside the lock deadlocks the two (every fleet writer holds the
    # lock for its whole 120s wait; the helper's bounded acquire times out at
    # exit 5 and the husk is never cleared). Every mutation below resolves the
    # root anyway (find_task_path -> tasks_dir -> repo_root), so this only
    # moves the resolution EARLIER; the lru_cache makes the in-lock call free.
    repo_root()
    LOCK_DIR.mkdir(parents=True, exist_ok=True)
    ...
```

Properties (each checked against the code):

- **Same exception surface, no swallowing.** `repo_root()` raises the same
  `RuntimeError` for the states it refuses; it now surfaces at the `with _locked():`
  line instead of a statement inside the body. `scripts/task.py` L2215-2219 catches
  `RuntimeError` at the top-level dispatch, so the user-visible output is unchanged.
  We deliberately do NOT wrap the priming in `try/except` — a swallowed prime would
  double the wait (an `lru_cache` does not cache exceptions) and violates fail-fast.
  Raising before the lock is strictly better: less work done, no partial state.
- **Cache-key soundness.** `_resolve_repo_root_cached` is keyed on `(os.getpid(),
  os.getcwd())` (L430). `grep -n chdir src/explore_persona_space/task_workflow.py`
  returns only docstring/comment hits — no code path chdirs, so the priming call and
  the in-lock call share a key and the wait cannot recur inside the lock.
- **Off-main routing is concurrency-safe outside the flock.** When the primary is on a
  feature branch the resolver returns `_ensure_managed_main_worktree(...)` (L480), which
  carries its OWN guard (`_migration_lock_path`, L647-653) and is ALREADY reached
  lock-free by every READ path (`task.py view`, `find`, …). Priming therefore adds no
  new concurrency exposure.
- **Post-prime husk race is pre-existing and unchanged.** A husk that appears between
  the prime and the mutation cannot be created by `sync_repo_root` (it holds this same
  flock across its pull), only by an out-of-band human `git pull` at the root — the same
  race that exists today.

**Why this converges the system.** Waiters now spin on the husk with NO lock held →
the helper's bounded acquire succeeds → `preflight` aborts the husk → HEAD re-attaches
to `main` → each waiter's next 2 s re-probe returns `main` and it proceeds (blocking on
the flock only for the helper's ordinary mutation window). A stale husk with no helper
run still ends in the same loud bounded refusal as today.

### 4.2 Change B — correct the comment that encodes the false assumption

Replace the "No deadlock while a caller waits here holding the task-workflow flock"
sentence at `task_workflow.py:500-503` with the accurate statement: the wait no longer
holds the flock (`_locked()` primes the resolution first, §4.1), which is what lets
`sync_repo_root.py` acquire the flock and clear an ABANDONED husk; note explicitly that
the previous reasoning covered only a LIVE helper-driven rebase and left the abandoned
case deadlocked (#2295). This edit is load-bearing: a future reader restoring the
in-lock resolution would re-introduce the deadlock, and the comment is the only place
the invariant is stated.

### 4.3 Change C — make the wait-timeout refusal name the sanctioned recovery

The timeout message (L518-525) currently instructs a bare repo-root
`git -C <parent> rebase --abort`. Point it at the single-flight helper —
`uv run python scripts/sync_repo_root.py` — as the FIRST recommendation (it holds both
locks, rescues untracked collisions, and re-applies the autostash), keeping the raw
abort as the fallback for when the helper itself refuses. Minimal wording change; no
behavior change. Rationale: after §4.1 this refusal is the surface a blocked writer
actually sees, and it should route to the sanctioned path rather than a hand-rolled
root git command.

### 4.4 Change D — watcher pass 34: per-entry attribution to the OWNING task

`scripts/autonomous_session_watch.py`, inside `stash_rescue_audit_pass` (L9112),
strictly ADDITIVE to the existing repo-level push:

1. **Attribution (read-only).** For each aged bare autostash entry, read its file list
   with one `git -C PROJECT_ROOT stash show --name-only <ref>` (fixed read-only argv —
   the same discipline as `_collect_stash_rescue_backlog` L9046) and map paths → task
   ids by the established path grammars: `tasks/<status>/<N>/…`,
   `eval_results/issue_<N>/…`, `figures/issue_<N>/…`, `scripts/issue<N>_*`,
   `tests/test_issue<N>*`, `docs/**/issue_<N>*`. Refs are re-resolved by sha at read
   time (refs renumber; the sha is stable — the `_stranded_new_autostash_message`
   L1619 convention).
2. **One durable marker per (task, stash-sha) episode.** `_post_progress_marker`
   (L15243) with a new module-level sentinel
   `[autonomous_session_watch:stash-rescue-owner-attribution]` that MUST be added to
   `_WATCHER_NOTE_SENTINELS` (L2397) — the note is an `epm:progress` on tasks that may
   be parked, so counting it as progress would reset the reconcile/stalled staleness
   clocks it sits beside (the #2084/#2283 anti-liveness contract). Note content: stash
   sha12 + committer date, the subset of the file list belonging to THIS task, the
   rescue-patch path under `~/.task-workflow/root-sync-rescue/`, the read-only triage
   command (`sync_repo_root.py --triage-autostash`), and an explicit statement that
   nothing was popped, dropped or applied.
3. **Bounds + fail-soft.** Per-tick marker cap `EPM_STASH_RESCUE_MARKER_CAP` (default
   5, the `EPM_TRIAGE_OBSERVER_MARKER_CAP` convention — overflow stays sidecar-recorded
   only); fire-once dedup on `(task_id, stash_sha)` persisted in the existing
   `_stash_rescue_state_path()` singleton, re-alerting on the existing
   `EPM_STASH_RESCUE_REALERT_HOURS` (168 h) TTL; one sidecar row per attributed entry
   (`kind: "stash-rescue-attribution"`) in the existing events stream; an unattributable
   entry is sidecar-recorded with `attribution_status: "unattributed"` and NEVER
   silently dropped (the #967 honest-attribution convention). Any per-entry failure
   logs and continues — the pass's existing top-level fail-soft arm stays the backstop,
   and a failed attribution must never read as "backlog cleared".
4. **Kill switch** `EPM_DISABLE_STASH_RESCUE_ATTRIBUTION=1` disables the new leg only,
   leaving pass 34 byte-equivalent to today. The pass-wide
   `EPM_DISABLE_STASH_RESCUE_AUDIT=1` still covers both.
5. **Docstring contract update.** Pass 34's narrative in the module docstring says
   "posts NO task markers"; that sentence must be rewritten (the docstring is the
   lint-pinned canonical pass enumeration — `workflow_lint --check-asw-docstring-pass-count`;
   the pass COUNT is unchanged because this extends pass 34 rather than adding one).
   `.claude/rules/background-automation.md`'s pass-34 paragraph gets the same update.

**ESCALATE-ONLY is a hard invariant** for this leg: no `stash pop`/`apply`/`drop`, no
`rm`, no status mutation, no session stop. Pinned by a test (§5.D2).

  message; `task.py` catches `RuntimeError` at the top-level dispatch (L2215). Covered

  convergence then waits for the 3600 s stale threshold. Named in the plan and in the
  code comment; not fixed this round (§2 F5).

  is advisory and names no action the watcher took.
- **R6 — attribution mis-maps a path.** Fail toward silence: an unrecognized path is
  recorded `unattributed` rather than guessed onto a task (D1).
