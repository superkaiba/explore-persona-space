## 3. Design

### Verified preconditions (all re-checked this session on main)

- **Test semantics** (`tests/test_shared_vm_thread_caps.py:443-502`): heavy line = earliest MODULE-TOP `torch`/`numpy` import via AST (`_first_heavy_import_line`; nested/function imports exempt); dotenv line = first TEXTUAL line containing `load_dotenv(` (`_first_load_dotenv_line`) — a comment/docstring mentioning `load_dotenv(` would spuriously satisfy it, so the fix MUST be a real call and the inserted comment MUST NOT contain the literal `load_dotenv(` above the call. Violation iff `dotenv is None or heavy < dotenv`.
- **Import-cycle / early-import safety**: `explore_persona_space/__init__.py` is EMPTY; `orchestrate/__init__.py` imports only `orchestrate.fleet`, whose module-top imports are stdlib-only (verified `grep -nE '^(import|from) '`); `env.py` imports torch only INSIDE `setup_worker` (line 341). So the early `from explore_persona_space.orchestrate.env import load_dotenv` pulls in NO torch/numpy. The package resolves via the installed uv project (proof: `issue722_tf_margin_figure.py` imports `explore_persona_space.analysis.paper_plots` at top with NO `sys.path.insert` and works today) — the per-file `sys.path.insert` lines are belt-and-suspenders and are left untouched.
- **`load_dotenv()` call semantics** (`orchestrate/env.py:269-321`): no-arg → `resolve_dotenv_path()`; missing `.env` → `logger.warning`, NO crash; `_dotenv_load(..., override=False)` + `os.environ.setdefault` for HF_HOME/HF_XET/HF_TRANSFER + `_apply_shared_vm_thread_caps()` (setdefault; shared-VM-positive-detection only, fails open on pods/GCE/SLURM). A double call is a no-op for anything already set → moving/adding a call earlier is safe.
- **All 3 existing later calls are NO-ARG** `load_dotenv()` (gen_behavior_corpus@68, heldout_recon_scatter@40, scaling_grid@52) → a MOVE is exactly equivalent; no explicit-path preemption concern.
- **Ruff E402/I001/RUF100 semantics** (probed empirically with the repo config, `/tmp/e402probe`): `sys.path.insert(...)` before an import does NOT trigger E402; a `load_dotenv()` CALL (or a plain assignment like `PROJECT_ROOT = ...`) DOES; a needed `# noqa: E402` is not RUF100-flagged. The call statement splits isort sections, so the lone first-party `load_dotenv` import above a third-party numpy/torch block does NOT violate I001 (the #847 exemplar is the in-tree proof).
- **The heredoc/stdin `find_dotenv` gotcha does NOT apply** — these are files, and the project wrapper is stdin-safe anyway.
