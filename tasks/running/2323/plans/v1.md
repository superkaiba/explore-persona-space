## 2. Root cause — measured, and STRONGER than the task body's framing

The task body describes the failure as a **torn read** (a concurrent
`fs.writeFileSync` observed mid-write parses as an empty jobs list). That is
real but it is the *minor* half. Reading the installed companion
(`~/.claude/plugins/cache/openai-codex/codex/1.0.4/scripts/lib/state.mjs`,
plugin v1.0.4 — the version `_resolve_companion()` selects) shows the dominant
mechanism is a **lost update with an active destructive side effect**:

```
state.mjs:118  updateState(cwd, mutate) = loadState(cwd) -> mutate(state) -> saveState(cwd, state)
state.mjs:92   saveState():  previousJobs = loadState(cwd).jobs          # FRESH re-read
state.mjs:95                 nextJobs     = pruneJobs(state.jobs)        # the CALLER's snapshot
state.mjs:105                 retainedIds  = set(nextJobs ids)
state.mjs:106-112             for job in previousJobs:
                                  if job.id not in retainedIds:
                                      removeJobFile(...)                  # DELETES the job record file
                                      removeFileIfExists(job.logFile)     # DELETES the turn-trace log
state.mjs:114                 fs.writeFileSync(stateFile, ...)            # no lock, no tmp+rename
```

There is no `flock`, no `O_EXCL` tmp+rename, and no CAS anywhere in
`state.mjs`. So for two writers A and B racing on one repo-keyed
`state.json`:

1. B reads the index (`updateState`'s `loadState`) — snapshot does not
   contain job A, which A registers a moment later.
2. A writes `[jobA, ...]`.
3. B's `saveState` re-reads `previousJobs` — now **containing** jobA — computes
   `nextJobs` from its stale snapshot (**no** jobA), so jobA is not in
   `retainedIds`, and the prune loop **deletes jobA's job file and jobA's log
   file** before overwriting the index without jobA.

jobA is therefore **erased**, not transiently unreadable. `matchJobReference`
(`lib/job-control.mjs:191,210`) then throws
`No job found for "<id>". Run /codex:status ...` for a job whose worker is
alive and burning quota. This exactly reproduces #2321: 4 job ids across 3
near-simultaneous dispatches, exactly ONE findable.

**Two consequences that shape the design:**

- **(C1) The window is not only spawn-vs-spawn.** `upsertJob` is called by the
  DETACHED worker too — `lib/tracked-jobs.mjs:102` (per progress/phase change),
  `:152` (running), `:169`/`:194` (terminal) — from a process
  `codex_task.py` does not own. Every *running* Codex job is a live concurrent
  writer. A wrapper-side lock can therefore serialize the dispatches we make,
  but **cannot** eliminate spawn-vs-running-worker collisions. Serialization
  alone is not sufficient; this is why surface 1 is load-bearing, not
  redundant.
- **(C2) An erased entry SELF-HEALS.** `upsertJob` (`state.mjs:129-147`) does
  `findIndex(id)` and, when absent, `unshift`s the record back. So the
  detached worker re-registers its own job on its **next** progress/phase
  upsert — seconds to tens of seconds for a live job. A *bounded re-probe*
  therefore has a genuinely high recovery probability, and a **blind
  re-dispatch is exactly the wrong response**: the job is alive and about to
  reappear. This is the mechanism that makes acceptance criterion 2
  ("re-probe ... NEVER re-dispatch a possibly-running job") correct rather
  than merely cautious.

**Checked and NOT a hazard (recorded so the reviewer need not re-derive):**
the deleted turn-trace log self-heals via `appendFileSync`
(`tracked-jobs.mjs:41`), which recreates the file; the stall detector's
`_key_advanced` resets on an mtime increase even though size restarts at 0
(`codex_task.py:637-654`), so a clobbered log does **not** produce a false
stall force-cancel. No change needed there.

### Where the current code is wrong

`scripts/codex_task.py:1100-1110` (`_run_one_attempt`):

```python
confirm_phase, confirm_err, log_path = _probe_phase(companion, job_id)   # RAISING variant
if confirm_phase in {"probe-error", "shape-error"}:
    _best_effort_cancel(companion, job_id)
    return AttemptResult("fail", 4, f"post-spawn probe failed ...", job_id)
```

Three defects:

- **(D1) No re-probe.** A single probe decides the job is lost; per (C2) the
  entry is very often about to reappear.
- **(D2) Exit 4 is in `TRANSIENT_FAIL_EXIT_CODES`** (`codex_task.py:212`), so
  the caller **blind re-dispatches** a job that may be running — the orphan
  generator in #2321. This is the direct inverse of the #1020 discipline,
  where exit 7 was deliberately kept OUT of that set precisely because
  re-running a job that already ran is wrong (`codex_task.py:206-210,224-226`).
- **(D3) The raising `_probe_phase` is used** where `_probe_phase_safe`
  (`:669`) exists: a `TimeoutExpired`/`OSError` here escapes `_run_one_attempt`
  entirely — the very crash-with-no-failure-marker class #1020 MF2 closed on
  the fetch leg.

## 3. Design decisions (and the rejected alternatives)

**D-a. Bounded, jittered post-spawn re-probe; never a re-dispatch.**
Mirror the #1020 fetch-retry shape exactly (same backoff idiom, same
diagnostic-discriminator logging, same `<leg>_retries=<k>` note token) so the
two legs read as one discipline rather than two inventions.

**D-b. A NEW terminal exit code for post-spawn-probe exhaustion, kept OUT of
`TRANSIENT_FAIL_EXIT_CODES`.** Rejected: deleting 4 from the transient set.
Exit 4 also covers the `--reattach` binding-guard failure and the genuine
plugin-upgrade bad-job-id race, where #579's evidence (~10 incidents on
2026-06-09) says a re-dispatch is the correct recovery; a blanket removal
would regress that. Instead exit 4 keeps its other meanings unchanged, and
post-spawn-probe *exhaustion* — the branch where a live job is plausible —
gets `EXIT_POST_SPAWN_PROBE_EXHAUSTED = 10` (0-9, 130, 143 are taken; 2 is
argparse's). Verified no external consumer keys on this helper's numeric exit
codes: `grep -rn codex_task scripts/ src/` returns only prose/pattern
references (`codex_daemon_reaper.py:51` matches the cmdline, not the rc) plus
this helper's own tests.

**D-c. Advisory `flock` on a repo-keyed lock file, held across spawn + the
post-spawn confirm probe only.** The index is keyed by repo
(`state.mjs:29-44`: `<CLAUDE_PLUGIN_DATA>/state/<slug>-<sha256(realpath)[:16]>`),
so the lock is repo-keyed to match — derived from `DISPATCH_ROOT`, which is
already the resolved MAIN checkout root (`codex_task.py:146-190`). Preferred
over a sequential-dispatch *contract* in the workflow prose exactly as the
task body directs: a per-session contract cannot serialize dispatches from
*different* sessions, which is the fleet case that actually bit us.
- Lock path `<DISPATCH_ROOT>/.claude/cache/codex-dispatch.lock` (gitignored:
  `.gitignore:85`; already the home of `codex-quota-exhausted-until`).
- **Hold scope is bounded to the vulnerable window** — spawn + confirm probe
  (+ its re-probes). The poll loop is explicitly OUTSIDE the lock; holding it
  there would serialize the whole fleet for hours.
- **Fail-open, three ways:** acquire timeout, lock-file creation failure, or
  kill switch ⇒ proceed unlocked with one loud WARN naming the shared index
  path, and record `dispatch_lock=timeout-failopen|unavailable|disabled` on
  the spawned marker. Rationale: a refusal here wedges a review round, and the
  residual is exactly what surface 1's re-probe covers. Acceptance criterion 1
  permits either "serializes cleanly" or "refused with a diagnostic"; we take
  the former as the normal path and never introduce a new wedge.
- **Timeout sizing (measured from the existing constants, not guessed):** one
  holder's worst case = `SPAWN_TIMEOUT_SECS` (90) + (1 + cap) confirm probes ×
  (`STATUS_TIMEOUT_SECS` 60 + backoff ceil 20) ≈ 90 + 5×80 = 490 s. A 3-way
  round's third waiter therefore waits ≤ ~980 s, so
  `DEFAULT_DISPATCH_LOCK_TIMEOUT_SECS = 1800` (≈2× the 3-way worst case, the
  house p90-style ×2 dispersion default).

**D-d. Do NOT change the concurrent-dispatch instructions to sequential.**
With D-c the single-message 3-way bg-dispatch is safe *by construction*, and
serializing it in prose would slow every review round at all five sites. The
surface edits instead state that the helper serializes the spawn window
itself, so a future reader does not "fix" the concurrency back out. This is a
deliberate reading of scope surface 3: the instructions are made to *agree
with the realized mechanism* (acceptance criterion 4), not rewritten.

2. **`_confirm_job_queryable(companion, job_id, retry_cap)`** — new helper:
   calls `_probe_phase_safe` (closes D3), on `probe-error`/`shape-error`
   sleeps `floor + uniform(0, jitter)` and re-probes up to `retry_cap`,
   logs each attempt with `_probe_discriminator`-style WARN text, returns
   `(phase, err, log_path, probe_retries)`. It **never** cancels between
   attempts and **never** re-dispatches.
3. **`_run_one_attempt`** — replace `:1102-1110` with the helper; on
   exhaustion `_best_effort_cancel` (unchanged) then
   `AttemptResult("fail", EXIT_POST_SPAWN_PROBE_EXHAUSTED, <note>, job_id)`,
   the note naming the job id, the shared index path, and the
   `--reattach <job-id>` recovery command. Thread `probe_retries` into the
   `epm:codex-task-spawned` note as `probe_retries=<k>` (same note-token
   convention as `fetch_retries=`; no marker-schema change).
4. **`_spawn_codex`** — acquire the advisory lock before the companion
   subprocess; the lock is released by `_run_one_attempt` after the confirm
   probe returns. Implemented as a `contextlib.contextmanager`
   (`_dispatch_lock(timeout_s)`) using `fcntl.flock(LOCK_EX | LOCK_NB)` in a
   bounded poll loop (the `sync_repo_root.py` / `step9c_baseline.py` idiom),
   so the acquire is interruptible and timeout-bounded. `--reattach` mode
   never spawns and therefore never takes the lock.
5. **CLI + env:** `--post-spawn-probe-retry-cap` (default 4),
   `--dispatch-lock-timeout-secs` (default 1800), `--no-dispatch-lock`;
   kill switch `EPM_CODEX_DISPATCH_LOCK=0`. Docstring lifecycle steps 2/3 and

## 6. Risks and named residuals

- **R1 (named, unfixable here): the lock cannot cover detached workers.** Per
  (C1), a running job's own `upsertJob` can still clobber a just-registered
  sibling. The re-probe (surface 1) is the recovery arm for exactly this
  residual. A complete fix would require patching the vendored plugin
  (`state.mjs`), which is upgrade-fragile and out of scope — recorded here, not
  attempted.
- **R2: plugin-version coupling.** The mechanism above is read off plugin
  v1.0.4. Our change touches only our own wrapper, so a plugin upgrade cannot
  break it; if a future plugin adds its own locking our lock becomes redundant
  but harmless.
- **R3: lock held while a spawn hangs.** Bounded by `SPAWN_TIMEOUT_SECS` (90 s)
  + the confirm-probe budget; the context manager releases on every exit path
  including exceptions and the existing SIGTERM/SIGINT handlers.
- **R4: exit-code surface.** New code 10; verified unconsumed externally
  (§3 D-b). Tests pin the transient-set membership so a future edit that
  re-adds 10 fails loudly.
- **R5 (in-scope irony, handled): this task's own Step 5 dispatches a Codex
  twin** through the very helper being changed. The Step 5 dispatch runs the
  worktree's copy; a mid-round defect in the lock could stall that dispatch —
  mitigated by the fail-open posture (D-c) and by the kill switch.

## 9. Hyperparameter grounding

`kind: infra` is exempt from the literature-grounding rule. The five new
constants are nonetheless grounded on in-repo precedent rather than defaults:
retry cap / backoff floor / jitter mirror `DEFAULT_RESULT_FETCH_RETRY_CAP = 3`
and `RESULT_FETCH_RETRY_BACKOFF_{FLOOR,JITTER}_SECS = 5.0/10.0`
(Source: `#1020`, `scripts/codex_task.py:236-238`) with the cap raised 3→4 and
the jitter 10→15 s because the recovery here waits on the worker's next
`upsertJob` (progress-event cadence, ~10s scale) rather than a ms-scale torn
read; the lock timeout is derived arithmetically in §3 D-c from
`SPAWN_TIMEOUT_SECS` / `STATUS_TIMEOUT_SECS` (Source: `scripts/codex_task.py:248-250`).

## 10. Rollout / kill switch

`EPM_CODEX_DISPATCH_LOCK=0` (or `--no-dispatch-lock`) restores the pre-change
dispatch behavior for the lock; the re-probe has no kill switch by design
(`--post-spawn-probe-retry-cap 0` reduces it to the current single-probe
behavior, except that exhaustion still exits 10 rather than blind-re-dispatching
— that part is the fix).
