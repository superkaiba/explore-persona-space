## Requirement

`verify_plan.py`'s c26 (`c26_gpu_basis_routed_machine`) and c27
(`c27_capture_intent_hbm`) judge a plan's §9 compute basis against the
machine the router will ACTUALLY provision. Their shared mirror
`_C26_INTENT_GPU` (`scripts/verify_plan.py:4826`) encodes the **GCP**
`INTENT_TO_MACHINE` families (A100/L4) — correct when GCP led the auto
chain, wrong since GCP provisioning was disabled (#2028) and RunPod became
the auto head (#2054/#2059). Rebuild the mirror so both checks judge
against the live lane head, then delete the interim staleness caveat the
prose surface carries.

## Decisions

### D1 — derive from the lane head, fail OPEN to the current mapping

The mirror builder reads `_default_auto_lane_order`'s element 0 and
dispatches on it: `runpod` → the three-table composition above; `gcp` → the
existing GCP families (so the #2028 rollback flips both the router and the
mirror in one move). An unparseable router, a missing table, or an
unrecognized lane head **fails OPEN** to the runpod-head mapping with a
`verify_plan: note:` on stderr — never a crash, never a silent empty
mirror. Rationale: c26 is WARN-only and c27's FAIL is conditional; a
verifier that dies on a router refactor would wedge the Step-9c gate
fleet-wide (the #1388 class).

### D2 — `eval-h100` maps to H100, not to "undefined"

`eval-h100` is in `RUNPOD_INTENT_TRANSLATION_DELIBERATE_GAPS`
(`router.py:557`) — deliberately NOT RunPod-servable, because narrowing
2×H100→1× would break a TP=2 workload. So under a runpod-first chain its
launch fails loud at dispatch and it has no *provisioned* family.

It keeps `H100` in the mirror anyway. Reason: c26/c27 ask "what silicon is
this basis measured against", and `eval-h100` is 2× H100-80 on every lane
that can serve it. Mapping it to H100 makes a plan costing an `eval-h100`
basis on H100 read clean — correct. Dropping the key instead would make
c26 SKIP with "no resolvable intent", losing coverage for a token plans
legitimately write. The un-servability is a *dispatch* concern the router
already fails loud on; it is not c26's question.

### D3 — c27 becomes an HBM-GB floor, not an L4-family proxy (the recommended arm)

Under the runpod head every GPU intent is H100/H200/A100 — **there is no
L4** — so a faithful family-mirror rebuild makes `_C27_L4_INTENTS` empty
and c27 permanently inert. That is the same defect class this task exists
to close: a provider-specific proxy (`family == "L4"`) standing in for a
provider-independent property (HBM ≥ 40 GB for a ≥7B all-layer capture).

Note the existing code already concedes the point: c27's RunPod-pin branch
SKIPs with *"explicit RunPod pin/provision — RunPod eval = 1x H100 80GB, no
HBM gap"* (`verify_plan.py:5210-5213`). Under runpod-first that reasoning
applies to every bare-`auto` plan, not only explicitly-pinned ones.

So: add a per-family HBM-GB table (`_C26_FAMILY_HBM_GB`: L4 → 24, A100 → 80
(conservative: the ladder's A100-40 rungs are per-dispatch-gated by
`gcp.A100_40_USABLE_GIB`, and A100-40 vs -80 is explicitly below this
heuristic's grain per `_c26_family`), H100 → 80, H200 → 141, B200 → 180),
and re-express the c27 sets as HBM predicates:

- `_C27_UNDER_HBM_INTENTS` = intents whose family HBM < `_C27_CAPTURE_HBM_FLOOR_GB` (40)
- `_C27_BIG_HBM_INTENTS` = GPU intents whose family HBM ≥ that floor

Under the runpod head `_C27_UNDER_HBM_INTENTS` is empty and c27 reaches a
PASS naming the resolved floor ("all booked intents resolve to ≥40 GB HBM
under the runpod lane head") rather than an empty-set SKIP. The check
stays *armed*: adding any small-HBM lane re-fires it automatically, and the
partition assert (`UNDER | BIG | CPU == the whole mirror`) still holds.

Recorded alternative (rejected): keep the L4-family form and accept
inertness with an explicit skip reason. Cheaper, but it leaves a
provider-specific proxy in a gate whose whole bug was a provider-specific
proxy, and it would need re-opening the moment a lane changes. The critic
may overturn this — the FAIL-grade semantics of c27 are its call.

### D4 — the 7B-capture prose stays, the L4 prose goes

c27's FAIL message names "eval/debug (L4, g2-standard-4, 16-GB-class HBM)".
Rewrite to name the *resolved* family + HBM and the routed lane head, so a
future firing is self-explaining. `plan-compute-sizing.md`'s
"Activation-capture HBM sizing" MUST-level rule is unchanged — the ≥40 GB
floor is the science, not the proxy.

## Corpus recalibration (acceptance criterion 5)

c26/c27 are heuristics calibrated against the persisted plan corpus, so a
mapping change silently re-tunes every corpus verdict. Procedure:

1. **Before** the code change, sweep every persisted plan
   (`tasks/*/*/plans/v*.md`) through `verify_plan.py --json` and record the
   c26/c27 verdict per plan to `/tmp/issue2514_corpus_before.json`.
2. Apply the change; re-sweep to `..._after.json`.
3. Diff, and classify EVERY verdict flip into one of:
   - **expected-inversion** — an H100-basis plan that stops WARNing, or an
     A100-basis plan that starts WARNing (the bug being fixed);
   - **c27-disarm** — a c27 FAIL/WARN that becomes the D3 PASS;
   - **unexplained** — anything else. A non-empty unexplained set is a
     KILL criterion (below), not a thing to baseline away.
4. Record the counts + the per-class examples in the implementer's marker.
