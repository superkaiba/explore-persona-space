## 1. Requirement + acceptance criteria

**Requirement.** The workflow surface must state, in a **grep-findable and plan-time-reachable**
place, whether a session may `git push --force-with-lease` an issue branch whose local history the
session itself rewrote (the prescribed mid-flight rebase onto a fresher `main`). Today the ruling
exists in exactly one place — `.claude/skills/issue/steps/18-step-10d.md`, ~3,377 lines deep, inside
the "Rewritten-branch landing route (#2312 — force-free)" section — reachable only by a session
already executing Step 10d. `.claude/rules/` carries zero mentions.

**Resolution taken: branch (B)** — state the ban, name the force-free route as the alternative.
Recorded with rationale in this task's `epm:progress v2`. Branch (A) (a sanctioned
`--force-with-lease` arm) is NOT implemented: it would create a new destructive affordance, which is
a user grant an autonomous session may not make (`auto-continuation.md` STATE-TO-`blocked`
criterion 2). Branch (B) creates nothing — it is a **restrictive clarification at the definition
site** of a term the user already set in CLAUDE.md ("force-push stays a user-ask") and in criterion 2
itself ("irreversible writes (deletion, force-push, credential changes — always ask)"). The
divergent precedent is a dispute about that term's SCOPE (does the lease form on one's own rebased
branch count?), which is why the definition site is the right place to settle it.

## 3. File paths + concrete diffs

### Change 1 — `.claude/rules/auto-continuation.md` (the ruling; satisfies A1-A3)

Anchor: line 33, verbatim —
`  2. **Outside-the-worktree state mutation** — security boundary, irreversible writes (deletion, force-push, credential changes — always ask).`

Append to that criterion (one paragraph + a nested clause), stating:

- **The ruling.** No `/issue` path may force-push. This holds for `--force-with-lease` on the
  session's OWN issue branch after the session's own mid-flight rebase — the case that recurred
  (#1999, #2171, #2296) and that sessions kept resolving by inference. The lease's
  concurrent-writer interlock bounds the blast radius; it does not convert a force-push into a
  non-force-push, so criterion 2 binds unchanged. There is NO autonomous carve-out.
- **The alternative, by pointer.** The sanctioned landing is the force-free route:
  `.claude/skills/issue/steps/18-step-10d.md` § "Rewritten-branch landing route (#2312 —
  force-free)" — merge the gate-certified tip into a scratch worktree detached at `origin/main`,
  then `git push origin HEAD:main`. It needs no user, so a gate-PASSed task is never blocked on
  this rule. For the ordinary landing, `gh pr merge --rebase` performs the rebase server-side, so
  the local-rebase-then-force-push shape is usually unnecessary as well as disallowed (#2318's own
  measurement).
- **Precedent reconciliation (A3).** Practice diverged: #2171 and #1999 recorded
  `--force-with-lease` on a self-rebased branch as the correct form; #2181 and #2318 recorded their
  own use of it as a policy violation. **#2181/#2318 are the correct reading.** Roughly twenty
  tasks' event histories mention the flag (20 measured 2026-08-23) — those records are left as-is,
  and this rule, not the event history, is the policy of record. **Write the count in the dated or
  approximate form, never as a bare integer** (SF1): the set grows whenever another task's marker
  mentions the flag — including markers this very task posts — so a bare number in a durable rule
  starts drifting the day it lands.
- **What branch (A) would take.** A sanctioned narrow force arm remains available as a USER grant.
  Flipping it requires the user to amend THIS criterion (the standing user-ask is theirs to
  relax); a session may not infer the grant from precedent, from the lease's safety, or from the
  route's step count. Recorded so this resolution does not foreclose the question — see #2313.

The token `--force-with-lease` appears literally, which is what makes A1's grep criterion pass.
