  `proposed_infra_sweep_pass` (L29594) in the same tick, so a tag added by
  the dedup branch is consumed by the sweep in the SAME watcher tick.

## Requirement + acceptance criteria

1. **Leg (b) — urgent lane in the sweep.** A ripe `proposed` infra/batch task
   tagged `urgent-main-red` must be dispatched by `proposed_infra_sweep_pass`
   ahead of ALL older non-urgent candidates, and must be dispatchable even
   when the shared cap is exactly full, via a bounded overflow of +1 slot
   reserved for urgent candidates only.
   - Acceptance: pure-decision tests show (i) urgent candidate ordered before
     older non-urgent ids; (ii) at `occupied+pending == cap`, a non-urgent
     candidate skips `cap-full` while an urgent one dispatches (exactly one
     bonus slot); (iii) at `occupied+pending == cap+1`, the urgent candidate
     also skips `cap-full` (the bonus is bounded); (iv) `urgent_bonus=0`
     restores today's behavior byte-for-byte; (v) TWO urgent candidates in one
     tick at `occupied+pending == cap`, `bonus=1` ⇒ EXACTLY ONE dispatches and
     the other skips `cap-full` (pins that `len(dispatch)` is inside the
     comparison — an implementation dropping it would dispatch both and leak
     past the bound; critic Must-Fix 2); (vi) the `needs-human` exclusion
     BEATS `urgent-main-red`: a row tagged both never appears in the candidate
     ids NOR the urgent set (the #706 invariant; the exclusion `continue` in
     the row loop stays ORDERED BEFORE the urgency collection; critic
     Must-Fix 1).
2. **Leg (a) — dedup-target escalation in the urgent-park router.** When
   `_urgent_wf_park_route`'s dedup branch (`dedup_hit is not None`,
   ~L10212) hits a target task that is at status `proposed` with kind in
   `INFRA_DRAIN_KINDS`, the router must escalate it — add the
   `urgent-main-red` tag (idempotent; `task.py add-tag`) and record a sidecar
   row — so the same-tick sweep's urgent lane dispatches it. A target at any
   other status/kind is left untouched (today's behavior).
   - Acceptance: unit tests show the escalation fires for a proposed+infra
     dedup target and does NOT fire for a completed / non-drain-kind target;
     dry_run performs no subprocess. A `needs-human`-tagged dedup target is
     NOT tagged (the sweep would never dispatch it anyway; a
     `deduped-target-escalated` sidecar row would misleadingly imply pending
     dispatch) — write sidecar action `deduped-target-held-needs-human`
     instead (critic concern 3). The escalation runs BEFORE the
     `episodes[key]` latch write so a fail-soft `add-tag` failure inherits
     the existing crash-retry semantics instead of being lost for that park
     key (critic concern 1).
3. No new watcher PASS is added (the `check_asw_docstring_pass_count` lint
   budget is untouched); no public contract (status enum, marker schema,
   task.py CLI) changes.

## Method delta (vs current behavior)

- `_proposed_infra_candidates()` return shape changes from
  `list[int] | None` to `tuple[list[int], frozenset[int]] | None` —
  `(ordered_ids, urgent_ids)` — with ordering key
  `(0 if urgent else 1, id)` (urgent-first, oldest-first within each class).
  Internal helper; the only production caller is `proposed_infra_sweep_pass`.
  ~10 test call sites in `tests/test_autonomous_session_watch.py` updated in
  the same diff (the `_stub_sweep_executor` lambda + the
  `test_sweep_candidate_query_*` direct-return asserts).
- `decide_proposed_infra_sweep(...)` gains keyword-only
  `urgent: frozenset[int] = frozenset()` and `urgent_bonus: int = 0`
  (default 0 keeps the pure function backward-compatible for existing tests;
  the pass threads the env-resolved value). Cap arithmetic becomes
  per-candidate: `limit = cap + (urgent_bonus if i in urgent else 0)`;
  dispatch iff `occupied_active + pending + len(dispatch) < limit`; else skip
  `("cap-full")`. With urgent-first ordering, an urgent candidate can never
  lose its bonus slot to a non-urgent one.
- New env helper `_infra_sweep_urgent_bonus()` reading
  `EPM_INFRA_SWEEP_URGENT_BONUS` (default 1, clamped to ≥0; 0 disables the
  overflow while keeping the ordering). Follows the existing
  `_proposed_infra_sweep_backoff_s()` env-helper pattern.
- `_urgent_wf_park_route` dedup branch: BEFORE the `episodes[key]` latch
  write, probe the target once (`task.py view <tid> --json` — one bounded
  subprocess yielding status + kind + tags in one read; `_task_status_kind`
  alone lacks tags); on `status == "proposed"` and
  `kind in INFRA_DRAIN_KINDS`: if `needs-human` in tags → sidecar action
  `deduped-target-held-needs-human`, no tag write; else run
  `uv run python scripts/task.py add-tag <tid> urgent-main-red` (bounded
  subprocess, fail-soft stderr print on error, dry_run-gated no-op) and
  append sidecar row `{"key": key, "action": "deduped-target-escalated",
  "task": tid}`. `add-tag` is idempotent (already-tagged no-ops with no
  commit), so no separate idempotency guard is needed.

**Stated deviation from the body's leg (a) sketch** (body proposed the dedup
branch "best-effort dispatches ... same daemon/cap gates as
`_urgent_wf_park_file_and_dispatch`"): tag-and-let-the-sweep-dispatch is
chosen instead of a direct dispatch because (i) it keeps ONE dispatch
mechanism (the sweep) owning all cap/lease/registry arithmetic — a direct
router-side dispatch would duplicate the cap accounting that caused the
original bug; (ii) added latency is ≤0 ticks (the router pass runs before
the sweep pass in the same main() tick) vs the 8–27h observed failure; (iii)
for the #1823 shape specifically, router-filed targets ALREADY carry
`urgent-main-red`, so leg (b) alone fixes them — leg (a)'s tag covers dedup
targets filed by OTHER channels (/daily, session filings) that lack the tag.

**Stated deviation from the body's leg (c)** ("root-cause why the sweep never
dispatched any of the 10"): answered during clarification with live evidence
(cap-full during the session wave); recorded above, no investigation leg in
the diff.
