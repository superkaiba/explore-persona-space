### 3a. `src/explore_persona_space/orchestrate/hub.py` — additive kwarg (4-line diff + docstring)

```python
def list_repo_files_complete(
    api,
    repo_id: str,
    *,
    repo_type: str = "model",
    revision: str | None = None,
    path_in_repo: str | None = None,   # NEW — default None preserves existing behavior
) -> list[str]:
    ...
            for entry in api.list_repo_tree(
                repo_id=repo_id,
                repo_type=repo_type,
                revision=revision,
                recursive=True,
                path_in_repo=path_in_repo,   # NEW — server-side subtree scoping
            )
```

Docstring addition: `path_in_repo` scopes the walk server-side (the prefix rides in the tree URL; pagination covers only the subtree — REQUIRED against the ~1M-file data repo, where a full listing wedges, #833/#920); a non-existent path raises `EntryNotFoundError` **during iteration** (inside the retry thunk — the generator is lazy; verified live on 0.36.2), which `_retry_upload` re-raises immediately (non-transient) for callers to map to their own missing semantics.

Backward compatibility: all 10 existing call sites (hub.py ×4, `upload_sharded.py:163`, `scripts/sync_models.py:257`, `scripts/issue650/…:609`, `scripts/issue778*_upload.py` ×3, `scripts/issue_597/…:241`) call without the kwarg → `path_in_repo=None` → `list_repo_tree` receives its own default → byte-identical behavior.

### 3b. `scripts/verify_uploads.py::check_hf_hub_path` (lines 135–165) — the rewrite

```python
def check_hf_hub_path(
    repo_id: str,
    path_in_repo: str,
    repo_type: str = "model",
    revision: str | None = None,
) -> dict:
    """Check if a path exists on HF Hub at the given revision.

    [existing revision-pinning paragraph kept]

    The listing is SCOPED server-side to ``path_in_repo`` via
    ``list_repo_tree(path_in_repo=...)`` (through
    ``hub.list_repo_files_complete``, inheriting its 504 transient-retry,
    #794/#658) — a bare full-repo ``list_repo_files`` wedges >600 s on the
    ~1M-file data repo (#920, the #833 gotcha). The tree endpoint 404s
    when ``path_in_repo`` names an exact FILE rather than a directory, so
    an ``EntryNotFoundError`` falls back to one ``HfApi.file_exists`` probe.
    """
    try:
        from huggingface_hub import HfApi
        from huggingface_hub.utils import EntryNotFoundError

        from explore_persona_space.orchestrate.hub import list_repo_files_complete

        api = HfApi(token=os.environ.get("HF_TOKEN"))
        normalized = path_in_repo.rstrip("/")
        if not normalized:
            # A falsy path would silently degrade to a FULL-repo listing —
            # the exact hang this function exists to avoid. Fail loud.
            return {"status": "ERROR", "url": "", "detail": "empty path_in_repo"}
        rev_url = revision or "main"
        try:
            matching = list_repo_files_complete(
                api, repo_id, repo_type=repo_type, revision=revision,
                path_in_repo=normalized,
            )
        except EntryNotFoundError:
            # Not a directory at this revision; may still be an exact file
            # (tree endpoint 404s on file paths — verified on hub 0.36.2).
            # file_exists only fires AFTER the tree call proved repo+revision
            # resolve, so its False genuinely means "file missing" (its
            # swallowing of Repository/RevisionNotFoundError is unreachable
            # here).
            if api.file_exists(repo_id, normalized, repo_type=repo_type, revision=revision):
                matching = [normalized]
            else:
                matching = []
        if matching:
            url = f"https://huggingface.co/{repo_id}/tree/{rev_url}/{path_in_repo}"
            return {"status": "OK", "url": url, "file_count": len(matching)}
        return {
            "status": "MISSING",
            "url": "",
            "detail": f"No files under {path_in_repo} at revision {rev_url}",
        }
    except Exception as e:
        return {"status": "ERROR", "url": "", "detail": str(e)}
```

**Semantics-preservation argument (per edge named in the brief):**

- **Directory prefix:** old code filtered `f.startswith(path.rstrip("/") + "/")` over the full listing; new code lists the subtree server-side. Same file set: scoped `list_repo_tree(recursive=True)` returns full-from-repo-root paths (verified live) for exactly the files under the directory; a partial-name prefix like `adapters/T_context` (no such directory) → `EntryNotFoundError` → `file_exists` False → MISSING, matching the old code (where the `/`-terminated `startswith` prefix also matched nothing).
- **Exact file (`f == path_in_repo` branch):** old code matched it in the full listing → OK `file_count=1`; new code: tree 404s (verified live) → `file_exists` True → OK `file_count=1`. Git trees cannot have a path that is both file and directory, so the two branches are exhaustive and disjoint.
- **`revision=None` → main; pinned SHA threaded:** `list_repo_tree` and `file_exists` both accept `revision` and default to main (signatures read from `.venv`); the URL keeps `revision or "main"` as before — phantom-URL revision-pinning semantics preserved.
- **Status taxonomy:** `EntryNotFoundError` → MISSING (same detail string as before). `RepositoryNotFoundError` / `RevisionNotFoundError` (verified live: a bogus SHA raises `RevisionNotFoundError` from the tree call) are NOT caught by the inner except → fall to the outer generic except → ERROR — identical to the old code, where any exception from `list_repo_files` became ERROR.
- **`file_count`:** count of `RepoFile` entries under the prefix (folders filtered by `list_repo_files_complete`, matching the old files-only `list_repo_files` semantics; verified live: a 7-file adapter dir returns exactly 7 `RepoFile` entries).
- **Trailing slash:** normalized off before the tree call (unknown Hub behavior for a `%2F`-terminated tree URL — not worth probing); the reported URL keeps the caller's cited form, as the old code did.

No changes to `check_hf_model_from_card`, `run_verification`, or any other function in the file — they consume `check_hf_hub_path` through its unchanged contract.

- **D1 — scoped `list_repo_tree(path_in_repo=...)` via an additive kwarg on `hub.list_repo_files_complete`, not a new lister.**
  *What:* thread `path_in_repo` through the existing paginated + 504-retry-wrapped helper (hub.py:458–516) and call it from `check_hf_hub_path`.
  *Why:* server-side scoping is the codified fix for the ~1M-file repo (pagination covers only the subtree; measured 0.06–0.14 s per scoped call vs >600 s full listing); routing through the existing helper inherits the #794/#658 cursor-page-504 retry instead of duplicating it, and hands the already-logged `_hf_artifact_exists` follow-up its needed primitive for free.
  *Source:* `.claude/rules/gotchas.md` § "`snapshot_download` … ~1M-file data repo" + `.claude/rules/artifact-reuse.md` (the #833 codified fix); `hub.py:481-486` (the #794/#658 retry rationale); live probes on pinned 0.36.2 (this plan, 2026-07-03); task brief ("prefer reusing/extending … add a `path_in_repo` parameter").
  *Alternatives:* (a) local scoped lister in verify_uploads.py — kept as the D-2 fallback; duplicates retry logic, two listers rot. (b) `HfApi.get_paths_info(paths=[...])` — discriminates file/dir/missing in one call but still needs the subtree walk for `file_count` on the common directory case (2 calls vs 1). (c) `repo_info().siblings` — silently truncates at ~7901 entries (the very bug `list_repo_files_complete` exists to avoid). (d) `file_exists`-only — cannot produce `file_count` or directory semantics.

- **D2 — exception mapping: `EntryNotFoundError` → exact-file `file_exists` fallback → MISSING; everything else → generic except → ERROR.**
  *What:* only `EntryNotFoundError` is caught inner; `RevisionNotFoundError`/`RepositoryNotFoundError`/transport errors fall to the outer except.
  *Why:* preserves the pre-fix taxonomy exactly (old code: missing path → empty local filter → MISSING; any exception → ERROR). `file_exists` is safe as the fallback because it fires only after the tree call proved repo+revision resolve, so its silent False-on-RepoNotFound/RevisionNotFound branches are unreachable.
  *Source:* live probes (bogus dir → `EntryNotFoundError` 0.14 s; tree-on-file → `EntryNotFoundError`; bogus SHA → `RevisionNotFoundError`; real file → `file_exists` True 0.12 s); `HfApi.file_exists` source read (0.36.2); `verify_uploads.py:148-165` (old taxonomy).
  *Alternatives:* mapping `RevisionNotFoundError` → MISSING (arguably more phantom-URL-semantic) — rejected: behavior change vs the old ERROR, and ERROR correctly blocks the gate anyway.

- **D3 — `file_exists` for the exact-file branch, unwrapped by retry.**
  *What:* one bare `file_exists` probe on the fallback path.
  *Why:* the tree endpoint 404s on file paths (verified — the old `f == path_in_repo` branch has no scoped-tree equivalent); the old code had ZERO retry hardening, so an unwrapped single probe is not a parity regression, and importing the private `_retry_upload` into the script solely for this rare branch isn't worth the coupling.
  *Source:* live probe (tree-on-`README.md`-path → `EntryNotFoundError`; `file_exists` on a real file → True in 0.12 s); gotchas.md ("For a SINGLE-path existence probe use `HfApi().file_exists` — never a full listing").
  *Alternatives:* wrapping it in `_retry_upload` — fine too, listed under D-2 fallback machinery; not required.

- **D4 — empty-path guard → ERROR.**
  *What:* `path_in_repo.rstrip("/") == ""` short-circuits to ERROR before any Hub call.
  *Why:* a falsy `path_in_repo` passed to `list_repo_tree` degrades silently to the full-repo listing — the exact hang; fail-fast beats silent recreation of #920. No current caller can hit it (all three call sites gate on truthy paths).
  *Source:* `HfApi.list_repo_tree` source (`encoded_path_in_repo = "/" + quote(...) if path_in_repo else ""`); CLAUDE.md "Fail fast — never hide failures".
  *Alternatives:* preserving old full-listing behavior for `""` — rejected as the hang vector.
