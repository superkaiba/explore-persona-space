# Plan — #2616: Background per-stem Hub uploads so capture phases stop idling their GPU pod

## 0.0 TL;DR (plain English)

- **What I'll build:** a small shared helper (`BackgroundStemUploader`) that lets a GPU capture phase hand each finished stem's upload to a single background worker thread and immediately start the next stem's GPU compute, instead of sitting idle for minutes per stem while ~2 GB of shards go to the Hub. It keeps every existing safety rule: a stem's local shards are freed only after that stem's upload is verified, any background upload failure still crashes the run loudly, and the phase's terminal marker waits until every upload has landed.
- **What I expect:** CPU-only unit tests prove the overlap, the fail-loud propagation, and the disk-bounding backpressure; the next capture-shaped run that adopts the recipe shows the next stem's compute starting while the prior stem's upload is in flight, and `poll_pipeline` posts no `[gpu-idle-advisory]` during a healthy capture phase.
- **What would change my mind:** if the web/library evidence showed one queued uploader thread is unsafe with `huggingface_hub` (it shows the opposite — HF's own `run_as_future` uses exactly this single-queued-worker design), or if the disk arithmetic showed pipelining risks the ~130 GB per-pod quota (it doesn't at the default bound of 2 pending stems, ~6 GB peak).

## 1. Goal

> Stop a GPU capture phase from holding its whole pod idle during per-stem Hub uploads: either overlap the upload with the next stem's compute, or move the upload off the GPU pod. The measurable target is the phase's realized GPU-idle fraction, which is currently large enough that `poll_pipeline` raises its own standing advisory mid-phase.

### Web findings (quoted, with sources)

- **HF's own background-upload design is a single queued worker.** `HfApi.run_as_future` (read from the installed `huggingface_hub==0.36.2`, `hf_api.py:1741–1747`): "Run a method in the background and return a Future instance… **Background jobs are queued to preserve order but are not ran in parallel.** If you need to speed-up your scripts by parallelizing lots of call to the API, you must setup and use your own ThreadPoolExecutor." — i.e., one background uploader thread with a queue is the library's own sanctioned pattern.
- **Concurrent commits to the same repo are the hazard class, not background threads per se.** The HF upload guide documents `parent_commit` "to ensure the repo has not changed before committing the changes… especially useful if the repo is updated / committed to concurrently", and the `CommitScheduler` docs advise the `scheduler.lock` for heavy-loaded concurrent writers. Heavy parallel uploads are documented to draw 429/503 storms ("maximum time in concurrency queue reached") — [huggingface_hub issue #3071](https://github.com/huggingface/huggingface_hub/issues/3071). The single-worker design sidesteps all of this: at most one `create_commit` in flight from our process, same as today's sequential code.
- Sources: [Upload files to the Hub — huggingface_hub docs](https://huggingface.co/docs/huggingface_hub/en/guides/upload), [HfApi Client reference](https://huggingface.co/docs/huggingface_hub/package_reference/hf_api), [issue #3071: 503/429 storms under heavy upload](https://github.com/huggingface/huggingface_hub/issues/3071), [issue #1123: async API support discussion](https://github.com/huggingface/huggingface_hub/issues/1123).

## 3. Requirement + acceptance criteria

**Requirement.** A shared helper such that a per-stem GPU phase can (a) start stem N+1's compute while stem N's upload is in flight, (b) never free a stem's local shards before that stem's upload is verified, (c) never swallow a background upload failure — it re-raises at the next `submit()` and at `join()`, and queued-but-unexecuted chains are skipped (their shards stay on disk, their done-markers are never written), (d) never write the phase's terminal marker before every submitted upload has completed (`join()` gates it), and (e) bound the number of unuploaded stems held on disk (backpressure) so the ~130 GB MooseFS per-pod quota is respected.

## 4. Design

### 4.1 New module: `src/explore_persona_space/orchestrate/background_upload.py`

Why code, not a model call: this is pure orchestration/concurrency infrastructure — no judgment task exists.

```python
class BackgroundStemUploader:
    """One daemon worker thread executing per-stem upload chains in submit order.

    Contract: submit(work, label=...) enqueues a zero-arg callable (the FULL
    per-stem chain: upload -> verify -> free -> marker). Backpressure: blocks
    when max_pending chains are outstanding. Fail-loud: after any chain
    exception, every later submit() and join() re-raises it (RuntimeError
    naming the failed label, chained `from` the original); queued unexecuted
    chains are recorded in .skipped and NEVER run. join(timeout_s) must be
    called before the phase terminal marker; on timeout it raises naming the
    pending labels. Worker is daemon=True (a native hf-xet wedge must not
    block interpreter exit -- hub.py STAGE_HUB_PREFIX_TIMEOUT_RC note, #1739/#2153);
    correctness comes from join-before-terminal-marker, never from atexit join.
    """

    def __init__(self, *, max_pending: int = 2, name: str = "bg-upload",
                 join_timeout_s: float = 1800.0): ...
    def submit(self, work: Callable[[], None], *, label: str) -> None: ...
    def join(self, timeout_s: float | None = None) -> None: ...   # None -> self.join_timeout_s
    def __enter__(self) -> "BackgroundStemUploader": ...
    def __exit__(self, exc_type, exc, tb) -> bool: ...            # returns False always (never swallows)
    @property
    def failure(self) -> BaseException | None: ...
    skipped: list[str]                                            # labels of never-executed chains
```

Internals: `threading.Thread(daemon=True)` + `queue.Queue(maxsize=max_pending)` + a `threading.Condition` over an outstanding-count; `_failure: tuple[str, BaseException] | None` set by the worker on the first chain exception. Worker loop: `get()` → if `_failure` set, append label to `skipped`, decrement, continue; else run `work()`; on exception store `(label, exc)`, notify. `submit()` checks `_failure` BEFORE `put()` (earliest foreground raise) and relies on `Queue(maxsize)` blocking for backpressure. `join()` waits `outstanding == 0 or _failure`, re-raises on failure, raises `RuntimeError(f"background upload join timed out; pending={labels}")` on timeout. `__exit__` on clean body exit calls `join()`; on a body exception it does NOT join (avoids hanging teardown on a wedged upload) — it logs pending labels and returns False so the body exception propagates. Deliberately NOT `ThreadPoolExecutor`: its non-daemon workers are atexit-joined and a native-wedged worker hangs the process with no rc (hub.py:2982–2988, verbatim read).

```python
def hub_upload_then_free(
    stem_dir: Path, *, repo_id: str, repo_type: str, dest: str,
    free_glob: str | None = None,
    after_verify: Callable[[], None] | None = None,
) -> Callable[[], None]:
    """Chain factory for the canonical per-stem persist: hub._upload(...,
    raise_on_error=True) -> raise RuntimeError on empty result (the missing-
    token / absent-path / 0-files-verify "" returns must fail loud here, not
    assert -- library code) -> unlink sorted(stem_dir.glob(free_glob)) ->
    after_verify() (e.g. the consumer's Hub-first done-marker mirror).
    Ordering is the load-bearing contract: free strictly after verified
    upload; marker strictly after free.
    """
```

Symbol-existence (grep-confirmed at plan time): `hub._upload` (hub.py:1782), `hub._retry_upload` (hub.py:1596), `hub.verify_repo_paths_uploaded` (hub.py:1699), `upload_sharded.upload_dir_sharded` (upload_sharded.py docstring line 8), `spawn_workers` (issue2546_gen_capture.py:2495), `run_capture` (:2997), `run_capture_reliability` (:3321), `_mirror_capture_marker` (:442). ### 4.2 Consumer wiring recipe (docstring + rules note; NOT applied to the live 2546 branch)

The module docstring carries the reference wiring, mirroring `run_capture`'s per-stem block (issue2546_gen_capture.py:3230–3262):

```python
uploader = BackgroundStemUploader(max_pending=2)
with uploader:
    for stem in stems:
        spawn_workers(...)                     # GPU compute (subprocess workers) — foreground
        ... build report / correctness ...     # compute outputs stay foreground
        uploader.submit(
            hub_upload_then_free(
                stem_dir, repo_id=DEFAULT_DATASET_REPO, repo_type="dataset",
                dest=dest, free_glob="slot*.shard*.pt",
                after_verify=lambda dp=done_p, d=dest, p=marker_payload:
                    _mirror_capture_marker(dp, d, p),
            ),
            label=stem,
        )
    uploader.join()                            # explicit; __exit__ backstops
write_phase_terminal_sentinel()                # ONLY after join
```

Notes baked into the recipe: (a) the per-stem done-marker moves INTO the chain (it must stay strictly after verify+free), so resume semantics are unchanged — a crash leaves un-chained stems markerless and the existing resume predicate re-runs them, overwriting their residual local shards; (b) per-stem `upload_wall_s` is recorded by the chain into a per-stem dict slot (single writer per key — safe under the GIL); (c) the LAST stem's upload overlaps nothing — the accepted residual is ONE upload window per phase instead of N; (d) applying this to `scripts/issue2546_gen_capture.py` itself happens on the `issue-2546` branch in a later round of that task, never mid-flight (hard constraint).

## 11. Decision Rationale

N/A — no model training (no hyperparameters). Load-bearing DESIGN choices:

- **Thread, not process, for the uploader.** What: one `threading.Thread(daemon=True)`. Why: the unit of work closes over in-process state (paths, marker payloads, `hub._upload`); GPU compute is already in child processes (`spawn_workers`, issue2546_gen_capture.py:2495) so the parent thread contends with nothing, and network I/O releases the GIL. A process would need pickling the chain + a second fail-loud IPC channel for zero benefit. Source: read worktree script :2495–2520; CPython GIL semantics. Alternatives: `multiprocessing` (rejected — pickling/IPC complexity), `HfApi(run_as_future=True)` (rejected — wraps only single HfApi calls, cannot carry the upload→verify→free→marker chain or `_upload`'s overflow fallback).
- **Hand-rolled daemon thread, not `ThreadPoolExecutor`.** What: explicit `Thread(daemon=True)` + `Queue`. Why: executor workers are non-daemon and atexit-joined — a worker parked in a native xet call is unjoinable and wedges the process with no rc. Source: hub.py:2982–2988 comment (verbatim read), #1739/#2153. Alternative: executor + `os._exit` escape (rejected — the hub.py precedent shows that escape is a last resort, not a design).
- **Single worker (serialized uploads), not a pool.** What: exactly one chain executes at a time. Why: preserves today's Hub-side load shape (no concurrent commits to one repo ⇒ no commit conflicts, no 429 amplification — GH issue #3071; HF's `run_as_future` uses the same single-queued-worker design "queued to preserve order but … not ran in parallel", hf_api.py:1746). Upload (~1–3 min/stem, `upload_wall_s` in the observed reports) is faster than compute (~8 min/stem), so one worker keeps up. Alternatives: pool of 2–6 (rejected — buys nothing while compute dominates; adds the concurrent-commit hazard class).
- **Queue bound `max_pending=2`.** What: `Queue(maxsize=2)`; `submit` blocks when full. Why: worst case (2 queued + 1 uploading + 1 computing) × ~2.1 GB/stem ≈ 8.4 GB — comfortably inside the ~130 GB MooseFS quota alongside model snapshots; K=1 would stall compute on any single slow upload, K≫2 buys nothing (upload keeps up) while growing crash/quota exposure. Source: gotchas.md:57 (quota); observed shard sizes (4 × 516 MB, task body log). Alternatives: unbounded (rejected — recreates fix-2's disk failure mode incrementally).
- **Verify-before-free ordering kept inside the per-stem chain.** What: `_upload(raise_on_error=True)` → truthy-check → unlink → marker. Why: upload-policy.md verify-before-free ("Models MUST upload to HF before local deletion"), #1112 (a stopped volume is not durable), #521 (losing plan-referenced tensors makes controls unrunnable); the marker-last ordering preserves the 2546 script's Hub-first resume discipline (defect-1a, marker v144). Source: upload-policy.md; issue2546_gen_capture.py:442–472. Alternatives: free-then-verify (forbidden), marker-before-free (would resume-skip a stem whose shards are gone but upload unverified — rejected).
- **`join()` before the phase terminal marker; `join` has a timeout; `__exit__` never swallows.** What: A3/A7/A8. Why: the terminal marker is the poller/verifier's "phase done" signal — writing it with uploads in flight would let a pod terminate before persistence (the #664/#825 family); a timeout-less join on a wedged native call hangs the phase forever with GPUs idle (the exact symptom this task removes). Source: pods.md #664; upload-policy.md § expensive-store-before-long-fit (#825). Alternatives: atexit join (rejected — the wedge problem), fire-and-forget (forbidden — fail-loud contract).

Fix 3 is a per-consumer tuning knob with no shared-code surface — a code change here would touch only the unmerged 2546 branch, violating the scope note's "shared recipe" intent.
