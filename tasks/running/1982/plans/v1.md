a citation as HF-staged (WARN, not FAIL) when the SAME basename also resolves

committed/in-ref OR the same basename is HF-cited in the plan ⇒ the
remaining unconsumed resolutions demote to WARN.**

### 3.1 New extraction helper

Add `extract_hf_cited_basenames(text: str) -> set[str]`, adjacent to
`extract_bare_names` (~L134). Returns basenames that appear inside HF
data-repo-style paths in the plan text (paths matching
`(?:issue\d+_[\w\-]+|explore-persona-space-data/issue\d+_[\w\-]+)/…/basename.ext`).
The regex REUSES `_BARE_EXTS` for the extension class and matches segments
of the form:

```python
_HF_CITED_RE = re.compile(
    r"(?:issue\d+_[\w\-]+|explore-persona-space-data/issue\d+_[\w\-]+)"
    r"/[\w./\-]*"
    r"(?P<name>[A-Za-z0-9][\w.\-]*\." + _BARE_EXTS + r")"
    r"(?![\w/])"
)
```

Rationale: this matches the two forms actually cited in real plans —
short HF-data prefix `issue1768_mapshift/inputs/corpus_sample.json` (seen
on #1979) and full-repo prefix
`superkaiba1/explore-persona-space-data/issue77_slug/raw_completions/f.json`
(existing test fixture, `tests/test_verify_carryover_inputs.py:225-230`).
The existing Channel-A extractor deliberately excludes both via the
`(?<![\w/\-.])` lookbehind (L88), so they are UNCLAIMED terrain — no
conflict.

### 3.2 Post-classify downgrade in `run_check()`

Refactor the Channel-B per-name inner loop (L563-612) so that per-name
resolutions are FIRST collected into a per-name `pending` list, then the
downgrade predicate runs, THEN the pending findings (possibly rewritten)
are appended to the overall `findings` list.

Pseudocode:

```python
declared_patterns, declared_basenames = extract_declared_outputs(plan_text)
hf_cited = extract_hf_cited_basenames(plan_text)   # NEW
# ... Channel-A loop unchanged ...
for name in extract_bare_names(plan_text):
    resolved = resolve_bare_name(...)
    if not resolved:
        findings.append(Finding(name, "skip", "bare-name-unresolved", ...))
        continue
    pending: list[Finding] = []
    foreign: list[str] = []
    for path in resolved:
        # deduped-channel-a / bare-name-declared-output / foreign-issue
        # branches unchanged — each appends to `pending` (not `findings`)
        # instead of continuing to the outer append.
        # ... existing branches, s/findings.append/pending.append/ ...
        pending.append(classify({"path": path, "channel": "B"}, ...))
    # NEW: multi-resolution / hf-staged downgrade.
    in_ref_paths = [f.path for f in pending
                    if f.verdict == "pass" and f.reason == "in-ref"]
    for i, f in enumerate(pending):
        if f.verdict == "fail" and f.reason == "untracked-local-only":
            if name in hf_cited:
                pending[i] = Finding(
                    f.path, "warn", "hf-staged",
                    f"bare-name resolved to an untracked VM-local mirror "
                    f"BUT the plan cites basename {name} under an HF prefix — "
                    f"consumers self-stage from HF; not a provable dependency "
                    f"gap (recorded residual — the gate's docstring L11-22 "
                    f"classes HF-staged inputs as WARN)",
                    "B",
                )
            elif in_ref_paths:
                pending[i] = Finding(
                    f.path, "warn", "duplicate-resolution",
                    f"bare-name multi-resolved: canonical committed copy "
                    f"{in_ref_paths[0]} passes in-ref; this uncommitted "
                    f"sibling is not a provable dependency gap — commit it "
                    f"if it IS a consumed input",
                    "B",
                )
    findings.extend(pending)
    if foreign:
        findings.append(Finding(name, "warn", "bare-name-foreign-issue", ...))
```

### 3.3 Precedence + boundaries

- Downgrade fires ONLY on `fail` / `untracked-local-only` from a Channel-B
  own-issue own-name resolution. Channel-A (full-prefix) findings are
  UNTOUCHED — the #1434 protection is preserved verbatim.
- `data-local-only` (Channel A, `path.startswith("data/")`) is UNTOUCHED —
  it already WARNs by design.
- `deduped-channel-a`, `bare-name-declared-output`, `bare-name-foreign-issue`
  skip/warn branches run BEFORE the downgrade window (they append to
  `pending` inside their own branch, then `continue`), so the downgrade
  never overrides them.
- Foreign-issue resolutions (`_issue_of_path(path) != issue`) are collected
  into `foreign` (not `pending`) and get the existing per-name summarized
  `bare-name-foreign-issue` WARN — the downgrade never sees them; the
  #1935 protection is preserved.
- Precedence when BOTH conditions hold (HF-cited AND ≥1 in-ref sibling):
  `hf-staged` wins (checked first). The reason string names the more
  specific mechanism; either verdict is a WARN so downstream exit code is
  identical.

### 3.4 CLI + JSON shape

Unchanged. The new WARN reasons (`hf-staged`, `duplicate-resolution`)
serialize through the existing `Finding` dataclass; `_render_finding` /
`_json_out` handle them without modification (they read `verdict` /
`reason` / `detail` / `channel` field-agnostically).

## 6. Failure modes / risks

- **Overly-permissive downgrade** — if `extract_hf_cited_basenames` also
  matches basenames appearing in incidental HF URLs (paper links, unrelated
  Hub datasets), a REAL missing dependency (basename genuinely absent from
  Hub AND untracked locally) could downgrade to WARN and dispatch a bad
  launch. Mitigation: the regex is deliberately narrow — it requires the
  `issue\d+_<slug>` prefix pattern that only project HF-data-repo paths
  carry; the `data/f.json` URL fixture at L225-230 is EXPLICITLY excluded
  from `extract_bare_names` today by the same regex family, so accidental
  overlap is unlikely. `test_hf_url_data_segment_not_matched` (L223)
  remains a live regression pin. Additional defense: the downgrade fires
  only on `fail` / `untracked-local-only` from an OWN-issue Channel-B
  resolution — the primary #1434 protection (own-issue tracked input
  provably absent) is unchanged.
- **Multi-resolution downgrade masks a real bug** — a bare name that
  multi-resolves onto a committed canonical copy PLUS an uncommitted stale
  local file could hide the stale file's status. Mitigation: the WARN
  message explicitly names the canonical path and instructs "commit it if
  this IS a consumed input" — the user still sees the finding; the
  distinction is WARN (proceeds) vs FAIL (blocks). The alternative (never
  downgrade) is the #1739 status quo, which manually gates every launch on
  a 3-grep-plus-documented-deviation ritual.
- **A recorded skip below the plan-review floor changes the review
  surface** — this plan skips the fact-checker, Statistics critic,
  Alternatives critic, and the consistency-checker (parentless infra with
  no followup-scope, per #1732 gate). Mitigation: all skips are recorded
  in this plan (§10 "Recorded skips" and §11) with stated reasons; the
  Methodology critic runs.
- **Recovery path if the code-review ensemble finds a substantive bug:**
  the standard Step 5 cap-5 loop applies. If exhausted, the workflow's
  cap-hit rule surfaces or blocks per the standing autonomous contract.
