### 4.2 Kind gate

### 4.3 Trigger + window

- **Anchor lines:** non-fenced lines matching `_C70_ANCHOR_RE = re.compile(r"(?i)\bpilot\b")`. Broad by design: the check WARNs only when ALL THREE numbers resolve in a window, and the threshold regex requires rule-26(b)-specific vocabulary (`parse-fail … %`), so a wall-time-pilot mention (plan-compute-sizing prose) cannot complete the triple. No anchors ⇒ SKIP.
- **Window:** for each anchor at raw-line index `i`, the harvest window is raw lines `[i-8, i+8]`, restricted to non-fenced lines (`_fence_mask`). `_C70_WINDOW_LINES = 8`.
- **Window-size justification against the fixture's measured line distances** (`tasks/awaiting_promotion/2162/plans/v7.md`, verified by Read at plan time): the gate item is lines 481-486 (anchor tokens "Judge pilot gate" at 481, "re-pilot" at 484/486); the draw budget "150 draws" is at 481; the rubric split "60 coherence + 90 value-rubric draws" at 483; the threshold "parse-fail < 2% per arm" at 484; the arm count "spanning all 3 arms" at **477 — inside the PREVIOUS gate item** (injection-exactness), 4 raw lines above anchor 481 and 7 above anchor 484. ±8 covers the worst measured distance (7) with margin ≥ 1 from every anchor, and 2× margin from the primary anchor (481 → 477 = 4). c69 uses ±3 for same-item bound attribution; c70 needs more because the fixture's arm count lives in a sibling list item. A wider window (±12+) raises the cross-item false-harvest risk for no measured benefit.

### 4.4 Three-number extraction (concrete regexes, all verified against the real fixture at plan time — §12 A1)

All harvests run over the window's non-fenced text (`"\n".join(win_lines)`).

**(a) Per-arm threshold** — REQUIRED, two parts:

```python
_C70_THRESH_RE = re.compile(
    r"(?i)parse[-\s]?fail(?:ure)?(?:\s+rate)?[^%\d]{0,25}?(\d+(?:\.\d+)?)\s*%"
)
_C70_PER_ARM_TOK_RE = re.compile(r"(?i)\bper[-\s]arm\b|\beach arm\b")
```

The threshold must be a percentage tied to parse-fail vocabulary (matches "parse-fail < 2% per arm", "parse-failure rate < ~2%"). The `per arm` token must ALSO appear somewhere in the window — without it the threshold could be an aggregate-over-arms bound, whose denominator is the total (satisfiable at 150/51), so the check cannot adjudicate (SKIP branch S5). Percent parsed exactly via `Fraction(pct_str) / 100`; `pct <= 0` or `pct >= 100` ⇒ SKIP (S9).

**(b) Effective draw count** — three forms, checked in this order:

```python
# direct per-arm form — short-circuits arm-count inference entirely
_C70_DIRECT_RE = re.compile(
    r"(?i)(?<![\d.])\b(\d+)\s*(?:draws?\s*)?/\s*arm\b"
    r"|(?<![\d.])\b(\d+)\s+draws?\s+per[-\s]arm\b"
)
# multi-rubric component form: "60 coherence + 90 value-rubric draws"
_C70_COMPONENT_RE = re.compile(
    r"(?i)\b\d+\s+[a-z][\w-]*(?:\s*\+\s*\d+\s+[a-z][\w-]*)+\s+draws\b"
)
# bare total: "150 draws" (a word between digit and "draws" does NOT match)
_C70_TOTAL_RE = re.compile(r"(?i)\b(\d+)\s+draws\b")
```

- `_C70_DIRECT_RE` handles "~30 draws/arm", "30/arm", "30 draws per arm" and yields `per_arm` directly (design question 2's short-circuit). The `(?<![\d.])` lookbehind + the draws-or-slash requirement are LOAD-BEARING: verified at plan time that the naive form false-matches `PASS ⇔ |mean ΔF| ≤ 0.10 per arm` (fixture line 490, a DIFFERENT gate in the same window) as `10 per arm`, and `(72 pairs/arm)` (line 489); the tightened form rejects both and accepts all three intended shapes (trace in §12 A2).
- `_C70_COMPONENT_RE` implements the multi-rubric split: on a match, `re.findall(r"\d+", m.group(0))` yields the per-rubric slices (fixture: `[60, 90]`); the effective slice = `min(components)` — rule 26 gives every rubric its OWN gate call (`judge_pilot.py:54-55`), so each slice is its own per-gate denominator and the smallest is the binding one. The WARN message names the full component list so a reader can see the non-binding slices too.
- `_C70_TOTAL_RE` fallback: unique totals only — one distinct value ⇒ that is the slice; ≥2 distinct values with no component match ⇒ ambiguous ⇒ SKIP (S7). (Note the fixture resolves via COMPONENT before TOTAL is consulted; if it fell through to TOTAL, 150/3 = 50 < 51 still WARNs — the design does not depend on the split, but the split is the faithful reading.)

**(c) Arm count** — needed only when (b) resolved via COMPONENT/TOTAL:

```python
_C70_ARMN_RE = re.compile(r"(?i)\b(\d+)\s+arms?\b")
```

Matches "spanning all 3 arms" (fixture line 477); cannot match bare "per arm" (no digit) or "per-arm (steered AND shuffled)". Distinct values collected over the window: exactly one ⇒ use it; zero ⇒ SKIP (S6); ≥2 distinct ⇒ SKIP (S8).

**Per-window resolution:** `per_arm = direct` if DIRECT matched, else `slice // n_arms` (integer floor — draws are integers and a fractional per-arm count cannot exceed its floor's resolution).

### 4.5 SKIP branches (enumerated — the conservative parse)

The check stays SILENT (SKIP, `passed=True`) on every branch where the three numbers are not confidently extractable:

- **S1** `kind not in ("experiment", "analysis")` — kind gate (§4.2).
- **S2** no non-fenced anchor line matching `\bpilot\b` — "no judge-pilot vocabulary detected".
- **S3** anchors present but NO window resolves a parse-fail % threshold — "pilot vocabulary but no per-arm parse-fail threshold resolvable".
- **S4** threshold resolves but no draw count in any of the three forms — "threshold without a resolvable draw budget".
- **S5** threshold resolves but no `per arm`/`each arm` token in the window — cannot distinguish a per-arm gate from an aggregate one.
- **S6** COMPONENT/TOTAL slice resolves but no `N arms` count and no DIRECT form — per-arm denominator underivable.
- **S7** ≥2 distinct bare totals, no component/sum structure, no DIRECT form — draw budget ambiguous.
- **S8** ≥2 distinct arm counts in the window — arm count ambiguous.
- **S9** degenerate threshold (`pct <= 0` or `>= 100`).

Branches S3-S9 are evaluated per window; the check SKIPs only when NO window fully resolves (and none WARNs/PASSes). The SKIP detail names the furthest-resolved branch reached (c69 style), so a silent miss is diagnosable from the check output.

### 4.6 Arithmetic — exact, never float

```python
required = math.floor(Fraction(1) / t) + 1   # t = Fraction(pct_str) / 100
```

`Fraction` (stdlib `fractions`; `Fraction("2.5")` parses decimal strings exactly) — never float division. Grounding: `judge_pilot._refusal_resolution_floor`'s docstring (`judge_pilot.py:400-410`) documents that float `floor(1/t)+1` is off-by-one on non-reciprocal thresholds (e.g. `t=1/93`); under exact arithmetic the closed form is correct for ALL t (smallest n with `1/n < t`, strict — mirroring rule 26(b)'s `>=`-FAILs semantics: at n=50 and t=2%, one failure is exactly 2%, NOT `< 2%`, hence 51). Verified: `math.floor(Fraction(100)/Fraction("2"))+1 == 51`.

**`min_effective_draws_per_arm` decision:** the plan-side check mirrors ONLY the `floor(1/t)+1` resolution leg, NOT the helper's `max(min_effective_draws_per_arm, …)` (default 10). Rationale: (i) `min_effective_draws_per_arm` is a caller kwarg plans essentially never state, so mirroring would mean assuming the default into other people's plans; (ii) at every threshold ≤ 10% the resolution leg dominates (`floor(1/t)+1 ≥ 11 > 10`), and rule 26(b) pins the house threshold at ~2% (→ 51), so the omitted leg binds only for thresholds > 10%, which no compliant plan uses; (iii) WARN-only conservatism — the omitted leg could only ADD warns on plans that deliberately lowered the caller floor. Recorded as accepted false negative FN-e (§4.8).

### 4.7 Verdict aggregation + WARN message

Evaluate every anchor window; collect fully-resolved evaluations (dicts: per_arm, source, components, total, n_arms, pct, required, anchor line no). Any resolved evaluation failing `per_arm >= required` ⇒ WARN; else if ≥1 resolved ⇒ PASS (detail shows the satisfied arithmetic); else SKIP. Duplicate evaluations from overlapping windows (the fixture's anchors 481/484 resolve the same gate) dedupe on the resolved tuple; the WARN reports the worst (min per_arm) plus at most 2 offender summaries (c69's `offenders[:3]` convention, tightened to 2 — one gate usually yields one tuple).

WARN message contents (all numbers named, per the task body): anchor line number; the parsed threshold; the draw budget as parsed (total + component list, or the direct per-arm value); the arm count; the computed `per_arm`; `required = floor(1/t)+1` with both values shown; a suggested budget (`required × n_arms` per rubric slice, e.g. "≥ 51/arm ⇒ ≥ 153 draws per rubric at 3 arms"); and the routing sentence: size the pilot via `eval.judge_pilot.judge_pilot_gate`, which REFUSES unsatisfiable configs at config time before any API spend (`allow_subresolution_pilot=True` is its documented downgrade-to-warning escape; its remedies message partitions doomed vs escapable arms since #2339). The message also names both standalone N/A escapes with the unwrapped-declaration convention ("on its own line, unwrapped (no backticks/quotes)"), mirroring c69.

### 4.8 Escapes + docstring enumeration

**Standalone N/A escapes** (via `_standalone_na_declared`, checked after the S2 trigger scan, before harvesting — the c69 ordering):

1. `N/A — no judge-pilot gate` (`tail_re = r"no judge[-\s]?pilot gate\b"`) — the pilot vocabulary is incidental or quotes an incident/sibling (e.g. a plan discussing #2162's defect without registering its own gate).
2. `N/A — harvested arm count is unrelated to the judge-pilot gate` (`tail_re = r"harvested arm count is unrelated to the judge[-\s]?pilot gate"`) — cross-quantity escape: the window's `N arms` belongs to a different stage than the judge wave (the c69 cross-quantity precedent; the ±8 window deliberately reaches sibling list items, so this false-pairing is the check's main FP channel).

**`allow_subresolution_pilot` PASS:** if the literal token `allow_subresolution_pilot` appears in a resolving window (window-scoped, not doc-global — a doc-global mention in an unrelated section must not silence a real defect), the sub-resolution sizing is a DELIBERATE, helper-recorded choice ⇒ PASS with detail naming the declaration. (The helper downgrades its refusal to a recorded report warning under this flag — `judge_pilot.py:29-30`.)

**Docstring accepted-false-negative / false-positive enumeration** (house convention, c69's "Accepted false negatives" precedent):

- FN-a: numbers written as words ("one hundred fifty draws") or in tables split across cells.
- FN-b: threshold stated as a bare fraction ("0.02") rather than a percentage.
- FN-c: arm count farther than 8 raw lines from every pilot anchor.
- FN-d: gate spec entirely inside a fenced code block (fence-masked harvest, matching c69's arm scan; fenced YAML gate specs escape).
- FN-e: the `min_effective_draws_per_arm` floor leg is not mirrored — a plan with threshold > 10% and per-arm draws < 10 escapes (§4.6).
- FN-f: multi-rubric slices that do not use the `A <word> + B <word> draws` additive shape (e.g. slices in separate sentences) fall back to the total-form read or SKIP.
- FP-a: an `N arms` count harvested from a neighboring gate item that genuinely differs from the judge wave's arm structure — remedied by escape 2; WARN-only posture bounds the cost.
- FP-b: a satisfiable gate whose draw prose the parser misreads toward a smaller slice — bounded by the sum-structure requirement on components and the unique-total requirement.
