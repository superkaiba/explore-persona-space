## 1. Goal + acceptance criteria

**Goal (verbatim from `body.md`):** "Extend the wedge/failover machinery: a same-signature CUDA-IMA crash after a verified-clean-GPU respawn auto-pivots to a FRESH host (new pod), bounded once (mirroring the GCP->RunPod once-more bound), then terminal failure_class:code -> blocked."

**Motivating incident (confirmed from #763's own markers this round).** #763 crashed twice with CUDA illegal-memory-access (`torch.AcceleratorError: CUDA error: an illegal memory access was encountered`, vLLM v1 EngineCore), SAME-signature, on the SAME pod (pod-763), AFTER a clean orphan-reap respawn — the second crash's marker (human-authored) literally reads `reason: gpu_wedged_same_signature_after_respawn ... SECOND torch.AcceleratorError ... on the SAME pod-763 H100 after a clean orphan-reap respawn`. The physical RunPod H100 was wedged at the driver level. The Part C no-port wedge stops the no-port billing leak but does NOT auto-pivot a CUDA-IMA-wedged pod (which keeps its port + stays RUNNING) to a fresh host — so #763 needed a manual GCP→RunPod pivot. #775 automates EXACTLY that human recovery: detect the second same-signature CUDA-IMA crash and pivot to a fresh host.

**Acceptance criteria:**
1. **Predicate fires on a same-signature REPEAT (signature-keyed, NOT pod_id-keyed — B1):** a RunPod handle whose poll is `status=dead` with a CUDA-IMA crash signature extracted from the WIDE probe tail (B2) AND a sidecar-recorded (or prior-`epm:failure`-marker-recorded) PRIOR same-signature CUDA-IMA crash THIS RUN triggers the fresh-host failover. A FIRST CUDA-IMA crash (no prior record) does NOT pivot — it records the signature and falls through to the ordinary dead path (the in-place same-pod experimenter respawn — see §2 "Default respawn is same-pod").
2. **Recovery reuses the existing fresh-pod machinery:** the failover entry point calls `_relaunch_fresh_runpod` (with `stamp_fn=_stamp_runpod_cuda_ima_failover`), NOT a re-implementation of pod provisioning.
3. **Once-more bound holds and emits `failure_class: code` (M1):** the CUDA-IMA failover fires AT MOST ONCE per run. After the pivot, a SECOND same-signature crash on the FRESH host → terminal `failure_class: code` (via the NEW `_terminal_code_json` helper, NOT `_terminal_infra_json`) → `status:blocked`. Bounded by the durable lease field `runpod_cuda_ima_failover_of`.
4. **Idempotency holds across crashes:** a re-fired tick on the SAME wedged handle after a successful failover short-circuits (no double-terminate/provision), guarded by lease (authoritative) + sentinel (fast path) — the Part C two-record pattern.
5. **Ordering: CUDA-IMA escalation runs BEFORE the no-port escalation (M2):** a CUDA-IMA dead poll that coincides with a transient no-port condition triggers the CUDA-IMA path, NOT the no-port within-K `status=dead → running` rewrite that would otherwise mask it.
6. **No regression:** every Part C + Part B + no-port test stays green; the new predicate is a no-op on a non-RunPod handle, a healthy poll, a first crash, a non-CUDA-IMA dead poll, and a CUDA-IMA dead poll whose traceback carries an our-code frame (M3).
7. **Mechanical gates pass:** `ruff` exit 0; `workflow_lint.py` (incl. `--check-lessons-index`) exit 0; touched-files pytest PASSes.

### Default respawn is SAME-POD for a vLLM CUDA-IMA crash (B1 verification — read this round)

The critic feared the autonomous infra-respawn TERMINATES + re-provisions a fresh pod (new pod_id), so a second-crash pod never matches the first and the predicate never fires. I verified the ACTUAL behavior in code:

- **SKILL.md Step 7 routing table (line 3815):** a `failure_class: infra` library-traceback crash (which CUDA-IMA/`EngineDeadError` classifies as — `failure_classifier.py:71/86-94`) routes to "Re-spawn the **experimenter** on the SAME branch". The zombie-GPU recovery brief (lines 3830-3831) is explicit: "reap the orphan by EXACT PID **before relaunching on the same pod**."
- **`experimenter.md:1091`:** the experimenter NEVER provisions/stops/terminates pods — that lifecycle is owned by the `/issue` skill. So a vLLM-crash infra respawn is an IN-PLACE, SAME-POD relaunch (orphan-reap + re-sync + relaunch), NOT a terminate+reprovision. The pod_id is PRESERVED across the crash→respawn→crash sequence.
- **The fresh-pod terminate+reprovision the critic cited (`experimenter.md:197-199`)** is specifically the `provision-incomplete` / half-bootstrapped-MooseFS-wedge case (a pod whose `bootstrap_pod.sh` never finished — no `.venv`, empty git index, frozen file count; lines 160-199 context). That is a DIFFERENT failure mode from a vLLM CUDA-IMA crash on a fully-running pod.
- **#763's own markers confirm same-pod:** `epm:run-launched pod=pod-763` → `epm:failure infra CUDA-IMA (pod-763)` → `epm:experimenter-respawn round=2 ... on pod-763 round 1 ... GPU verified clean before relaunch ... Resumed via sa[me pod]` → `epm:failure infra reason: gpu_wedged_same_signature_after_respawn ... on the SAME pod-763 H100`. pod-763 throughout.

**Conclusion: pod_id-pinning WOULD work for the CUDA-IMA case** (the respawn is same-pod). **But the predicate is keyed on SIGNATURE ONLY (the brief's instruction), because that is strictly more robust:**
- It survives the watcher-side stop/resume edge case (a `pod.py resume` rewrites host/port; a future watcher change could re-provision) the critic raised.
- It survives the half-bootstrap fresh-pod path (if a CUDA-IMA crash were ever preceded by a provision-incomplete respawn that DID swap pods, signature-keying still counts the repeat).
- The once-more bound is the safety: even if the signature over-counts (a benign double-match), at most ONE free-host pivot is spent and the run lands at terminal `code`/blocked.
- pod_id is incidental; the crash signature is the invariant. A wedged host and a deterministic bug both produce the same signature — the once-more bound disambiguates them (M3).

**Predicate input signal — two conjuncts + one exclusion, all necessary:**
1. **CUDA-IMA signature** on `result.crash_signature` (the NEW `PollResult` field, B2 — extracted from the WIDE 500-line probe tail, NOT the 5-line `log_tail_excerpt`):
   ```python
   CUDA_IMA_SIGNATURE = re.compile(
       r"CUDA error:\s*an illegal memory access was encountered"
       r"|illegal memory access was encountered"
       r"|EngineDeadError"
       r"|Engine core proc \S+ died unexpectedly",
       re.IGNORECASE,
   )
   ```
   No `re.DOTALL`, no cross-newline lazy quantifier (NIT 3) — each alternative matches WITHIN one line, so a match cannot span unrelated events across 500 lines. "Same signature" = the current poll's `crash_signature` AND the recorded prior signature both match `CUDA_IMA_SIGNATURE`. We deliberately do NOT fingerprint the exact stack frame — a driver-level IMA has no stable user-frame, and the host-wedge signature is "the GPU throws IMA regardless of workload."
2. **A prior same-signature CUDA-IMA crash recorded THIS RUN** (signature-keyed repeat, B1) — read from the sidecar `extra` record, with the prior `epm:failure v<n-1>` marker as a cross-pod fallback source (§4).
3. **EXCLUSION — no our-code traceback frame (M3):** if the WIDE crash surface ALSO matches `failure_classifier.OUR_CODE_FRAME` (`File "…/(src/explore_persona_space|scripts)/…"`), this is a deterministic code bug surfacing as CUDA-IMA, NOT a host wedge — do NOT pivot; fall through to the ordinary dead path → `failure_class: code`. Pulled forward from v1's "future mitigation" because `OUR_CODE_FRAME` already exists and the wide surface is already available.

## 3. File paths + concrete diffs / new functions

### 3a. `scripts/poll_pipeline.py` — populate a new `PollResult.crash_signature` (B2)

**The bug v1 assumed away.** `poll_once` builds `log_tail_excerpt` as `"\n".join(probe["…log_tail"].splitlines()[-5:])` (lines 2695-2698) — the LAST 5 LINES only. A vLLM CUDA-IMA death is a 20-50-line traceback whose signature lines (`CUDA error: an illegal memory access…`, `EngineDeadError`, `Engine core proc … died unexpectedly`) are routinely NOT in the final 5 (which are often a `subprocess` returncode, a tqdm `ZeroDivisionError` artifact, or a generic re-raise). v1's regex matched `result.log_tail_excerpt` and so would silently never fire.

**The fix is cheap because the wide surface is ALREADY fetched.** The probe captures `tail -500 $LOG_PATH` into `probe["log_tail"]` (`poll_pipeline.py:1081`) and `tail -500 "$CELL_PATH"` into `probe["cell_log_tail"]` (line 913). `poll_once` discards all but the last 5 for the notification excerpt. So NO new SSH call is needed — `poll_once` reads the 500-line surface it already has and extracts the signature from it. This is the critic's fix option (a) (match the same wide surface the failure-classifier sees), implemented at the cheapest point.

Concrete diff:
- **`PollResult` dataclass (~line 724):** add a defaulted field
  ```python
  # The crash signature extracted from the WIDE 500-line probe tail (NOT the
  # 5-line log_tail_excerpt, which truncates a multi-line vLLM traceback). None
  # on a healthy/running poll. Read by the #775 RunPod CUDA-IMA repeat-failover
  # predicate. Defaulted so the many cross-backend PollResult(...) call sites
  # need no change.
  crash_signature: str | None = None
  ```
- **`poll_once` (~line 2695, right after the `tail_excerpt` block):** populate it from the SAME wide surface the excerpt was sliced from, on a `status=dead` poll only (cheap; None otherwise):
  ```python
  # #775: extract the crash signature from the WIDE 500-line tail (the same
  # surface tail_excerpt was sliced from), NOT the 5-line excerpt — a vLLM
  # CUDA-IMA traceback spans 20-50 lines and is routinely truncated out of the
  # last 5. Pure string read; no extra SSH probe (the probe already fetched 500).
  wide_tail = (
      probe["cell_log_tail"]
      if (cell_mtime_epoch > 0 and cell_mtime_epoch > mtime_epoch)
      else probe["log_tail"]
  )
  crash_signature = wide_tail if status == "dead" else None
  ```
  and pass `crash_signature=crash_signature` into the `PollResult(...)` return. (We store the whole wide tail, not just the matched line, so the predicate can ALSO run the `OUR_CODE_FRAME` exclusion against it — M3.) `backend_poll.py` reads `result.crash_signature`.

This is the single change to `poll_pipeline.py`; `log_tail_excerpt` is UNCHANGED (every other consumer — the JSON-line summary at 2779, the notification surface — keeps its 5-line shape, NIT-free).

**Wiring into `main()` — CUDA-IMA block runs BEFORE the no-port block (M2).** v1 wired it AFTER the no-port block (line 1850), which is wrong: `_maybe_escalate_runpod_wedge` rewrites `status=dead → status=running` within the no-port K window (lines 671-677 / 696-701), and a CUDA-IMA crash can leave the pod momentarily no-port (engine dead, ports not yet torn down), so the no-port within-K rewrite would flip the dead poll to `running` BEFORE the CUDA-IMA predicate (which requires `status=="dead"`) ever ran — masking it. So the CUDA-IMA escalation goes AFTER the GCP async block (lines 1835-1840) and BEFORE the no-port escalation (line 1850):
```python
    # #775 RunPod CUDA-IMA repeat-failover. MUST run BEFORE the no-port
    # escalation below: the no-port within-K path rewrites status=dead ->
    # running, which would mask a CUDA-IMA dead poll that is also transiently
    # no-port (engine dead, ports not yet torn down). A no-op on every
    # non-RunPod / non-dead / non-CUDA-IMA / first-crash / our-code-framed poll.
    result = _maybe_escalate_runpod_cuda_ima(
        handle, result, Path(sidecar), issue=args.issue, now=time.time())
    if _is_runpod_cuda_ima_failure(handle, result):
        try:
            cuda_ima_json = _failover_cuda_ima_runpod(
                issue=args.issue, handle=handle, result=result, sidecar=Path(sidecar))
        except Exception as exc:  # belt-and-suspenders, mirrors the Part C guard
            logging.exception("backend_poll: RunPod CUDA-IMA failover raised unexpectedly")
            cuda_ima_json = _terminal_infra_json(
                issue=args.issue, sidecar=Path(sidecar),
                reason="runpod_cuda_ima_failover_error",
                log_tail=f"... raised {type(exc).__name__}: {exc}")
        print(json.dumps(cuda_ima_json)); return 0

    # (existing) #664/#689 RunPod RUNNING-but-no-port host wedge escalation ...
    result = _maybe_escalate_runpod_wedge(handle, result, Path(sidecar), now=time.time())
```

**NIT — clear-on-running runs INSIDE the escalation, not in a separate `main()` site.** Mirroring how Part C clears the no-port clock inside `_maybe_escalate_runpod_wedge` on the not-wedged branch (line 663), `_maybe_escalate_runpod_cuda_ima` clears `runpod_cuda_ima_last_seen` on its OWN running/non-CUDA-IMA branch — so a transient IMA the respawn recovered from (intervening healthy poll) does NOT accumulate against a later unrelated IMA. The escalation is reached on EVERY poll tick (it is wired unconditionally in `main()` before the no-port block, which a running RunPod poll passes through), so the clear always fires.

## 4. Detection design

**Sidecar state (signature-keyed — B1).** One key on the handle sidecar's `extra` dict (the same surface the Part C no-port clock rides — round-trips via `serialize_handle`'s `dict(handle.extra)`, no schema migration):
```python
extra["runpod_cuda_ima_last_seen"] = {"ts": <epoch>, "sig": "cuda_ima"}
```
NOT keyed to pod_name/job_id (B1). Read/write/clear by the three helpers (§3b), all fail-soft, using `_read/_write/_clear_runpod_noport_clock` as the byte-for-byte template. CLEARED on any non-dead / non-CUDA-IMA poll — a single transient CUDA-IMA the respawn recovered from (with an intervening healthy poll) does NOT accumulate; only a SECOND CUDA-IMA crash with no intervening healthy poll counts.

**Cross-pod fallback source (B1, the brief's "second source of truth").** When the sidecar `extra` record is ABSENT (a sidecar wipe between pods, an EDQUOT round-trip, a fresh-pod re-point that cleared `extra`), `_read_runpod_cuda_ima_record` FALLS BACK to reading the prior `epm:failure` marker body for this issue: if the latest prior `epm:failure` carries a CUDA-IMA signature (substring match on the marker note via `task_workflow.list_events` from the VM-side poller — `backend_poll.py` runs on the VM, NOT pod-side, so the `task.py`/`task_workflow` branch-guard concern does not apply), the current crash counts as a repeat. This guards against the sidecar being the single point of truth across a pod swap. Fail-soft: any read error → treat as "no prior record" (first crash). The sidecar record is the FAST path; the marker is the durable cross-pod backstop — exactly the lease/sentinel two-record philosophy Part C uses, applied to the detection record.

**"Same signature"** = (1) current poll `status=dead` AND `_crash_signature_is_cuda_ima(result.crash_signature)` (wide surface, B2); (2) a prior CUDA-IMA record exists THIS RUN (sidecar OR fallback marker); (3) the wide surface does NOT carry an our-code frame (M3 exclusion). Escalation: (1)+(2) AND NOT (3) → rewrite to `status=dead, current_phase=RUNPOD_CUDA_IMA_WEDGED_PHASE`. (1) without (2), or (1)+(2) but (3) fires → write/keep the record, return `result` unchanged (ordinary dead path → in-place same-pod respawn for case-(2)-blocked-by-our-frame this is correctly a `code` route). Not (1) → clear the record, return unchanged.

**Why CUDA-IMA family on the WIDE surface, not the 5-line excerpt or an exact stack fingerprint (B2 + M3 framing).** A driver-level IMA surfaces wherever the next kernel launch is, with no stable user-frame — so the calibrated signal is "the CUDA-IMA family recurred this run." The 5-line excerpt truncates the traceback (B2); the 500-line probe surface (already fetched) carries it. A tighter exact fingerprint MISSES the wedge; a looser one (any second dead poll) over-pivots on code bugs — so the predicate is a UNION over two failure modes (driver host-wedge AND deterministic CUDA-IMA code bug). **The predicate DETECTS a same-signature CUDA-IMA repeat; the host-wedge interpretation is a HYPOTHESIS the failover TESTS, not a thing the predicate proves (M3).** The disambiguation is empirical: a fresh host fixes the wedge but NOT the bug — discovered by spending the one bounded pivot, then the second-repeat lands at `failure_class: code`/blocked. The our-code-frame exclusion (M3) cheaply catches the COMMON framed code-bug case (a traceback through `src/explore_persona_space/` or `scripts/`) before spending the pivot at all; the driver-only IMA (no user frame) still gets the bounded one-pivot test.

**Trust-the-respawn-happened assumption (from the clarifier).** The predicate assumes the experimenter's in-place same-pod respawn ran the orphan-reap (`pkill -9 ^VLLM::EngineCore` by exact PID + `nvidia-smi` VRAM probe — an UNCONDITIONAL Pre-Launch step per gotchas.md + experimenter.md). Under that, a second same-signature CUDA-IMA after a clean reap = the reap worked but the GPU still throws IMA → driver wedge → only a fresh host helps. **Sufficient because** the reap is structural (not opt-in) — the poller needs no separate "verified-clean-GPU" marker (out-of-scope per the brief). **Robust if violated:** a respawn that skipped the reap (a leftover zombie) could trigger a needless pivot — but that is benign, bounded once, and a fresh pod ALSO clears a zombie. No hard dependency.

## 5. Recovery design — reuse vs fork (carry-forward, critic-endorsed)

**Decision: REUSE `_relaunch_fresh_runpod` (inner fresh-pod machinery) via a `stamp_fn` kwarg; add a thin sibling `_failover_cuda_ima_runpod` at the OUTER layer.** The critic explicitly endorsed this factoring ("the reuse-vs-fork decision is correct and well-argued").

- *Reuse `_failover_wedged_runpod` directly (rejected):* it hard-codes the no-port idempotency key (`runpod_wedge_failover_of`), so it would cross-suppress a CUDA-IMA failover and a no-port failover on the same issue; its terminate assumes a RUNNING pod (a CUDA-IMA pod is already dead); its log/reason strings are no-port-specific.
- *Fully independent fork of the whole relaunch (rejected):* `_relaunch_fresh_runpod` is ~150 lines of #689-hardened error mapping (NoCompute→`no_compute_available`, sidecar-write-fail→`sidecar_persistence_failed`, legacy-handle→`*_spec_missing`, durable-lease stamp). Duplicating it forks four hardening paths and rots.
- *`failure_class` kwarg on `_terminal_infra_json` vs a sibling `_terminal_code_json` (M1):* the kwarg keeps one function but its NAME + docstring assert `infra` (lines 1429-1438 read "A `status='dead'` / `failure_class='infra'` poll JSON"), so a `failure_class="code"` call would contradict the contract a reader trusts. A SIBLING `_terminal_code_json` (same JSON shape, `"failure_class": "code"`, its own docstring naming the watcher-parks-at-blocked semantics) is cleaner and is what §3b adds.
- *Chosen:* reuse the inner relaunch via the one `stamp_fn` kwarg; fork only the ~25-line OUTER orchestration; add the one `_terminal_code_json` sibling for the bound.

**Lease field + once-more bound (two layers, same durable field `runpod_cuda_ima_failover_of`):**
1. **Per-wedged-pod idempotency** (a re-fired tick on the SAME wedged handle): `_runpod_cuda_ima_already_handled` checks `lease.runpod_cuda_ima_failover_of == _runpod_handle_identity(handle)` + sentinel. Stops double-terminate/provision of one pivot.
2. **Per-run once-more bound** (a SECOND distinct CUDA-IMA on the FRESH host): `_failover_cuda_ima_runpod` first checks whether `runpod_cuda_ima_failover_of` is set to ANY non-null value on the issue's lease ("this run already spent its one CUDA-IMA pivot"). If so → terminal `_terminal_code_json` (`reason=cuda_ima_repeats_after_failover`), NO second relaunch. The GCP→RunPod once-more-bound analogue.

## 6. Failure-class routing (bounded-once, signature-keyed)

```
RunPod CUDA-IMA crash on the run's current pod
  → poll: status=dead, crash_signature (WIDE surface) matches CUDA_IMA_SIGNATURE
  → _maybe_escalate_runpod_cuda_ima (runs BEFORE the no-port block — M2):
       our-code frame in the wide surface?  YES (M3) → clear/keep record, return dead unchanged
                                                        → failure_classifier → code → implementer
       prior CUDA-IMA record THIS RUN?      NO → WRITE record; return dead unchanged
                                                  → failure_classifier → infra → experimenter
                                                    in-place SAME-POD orphan-reap respawn
                                                    (recovers → status=running → record CLEARED)
                                            YES (2nd same-sig repeat) → rewrite → CUDA_IMA_WEDGED_PHASE
  → _is_runpod_cuda_ima_failure → True
  → _failover_cuda_ima_runpod:
       layer-2 bound: lease.runpod_cuda_ima_failover_of already set?
            YES → TERMINAL _terminal_code_json (failure_class: code,
                  reason=cuda_ima_repeats_after_failover) → blocked
            NO  → layer-1 idempotency (this pod handled?) → short-circuit if yes
                → inputs-on-HF gate (PARTIAL → block infra, human decides)
                → best-effort terminate(dead pod); write sentinel
                → _relaunch_fresh_runpod(stamp_fn=_stamp_runpod_cuda_ima_failover)
                → FRESH host; lease.runpod_cuda_ima_failover_of = {pod identity}
                → emit status=running, current_phase=runpod_cuda_ima_failover_fresh_pod
  → fresh host ALSO CUDA-IMA crashes: 1st→record; 2nd→escalate→_failover_cuda_ima_runpod
       → layer-2 bound (field already set) → TERMINAL failure_class: code → blocked
```

`scripts/failure_classifier.py` is UNCHANGED (out-of-scope per the brief) — routing is driven by the poll JSON's `failure_class`/`reason` (the existing `_terminal_infra_json` for the inputs-block/error cases + the NEW `_terminal_code_json` for the once-more exhaustion), not by re-classifying a log body. The new logic is poll-level and short-circuits BEFORE the classifier sees the dead JSON for the once-more case. The watcher's capacity-retry pass re-drives ONLY `failure_class: infra` + `no_compute_available` (`autonomous_session_watch.py:8347/8458` — verified this round), so a `cuda_ima_repeats_after_failover` code failure parks at `blocked` (the Part B/C bound).

## 9. Kill criteria
- **Signature misfires on a single-crash false positive** — impossible by construction (the repeat conjunct requires a prior same-signature record). A two-crash false positive (a benign non-IMA second dead poll) cannot match `CUDA_IMA_SIGNATURE`. The predicate is a UNION over the driver-host-wedge AND deterministic-CUDA-IMA-code-bug modes (M3); it does NOT claim to detect a host wedge — the once-more bound is the disambiguator (a fresh-host repeat = code/blocked; a fresh-host success = was-wedge). The our-code-frame exclusion (M3) cheaply removes the common framed-code-bug case before spending the pivot. Threshold + SIGN grounded in #763's confirmed twice-same-signature-then-manual-pivot sequence.
- **The once-more bound lets a third crash through** — hard kill; caught by `test_cuda_ima_failover_bounded_once_third_crash_terminal_code` + `test_poller_cuda_ima_failover_exhausted_emits_code`.
- **The signature never reaches the predicate (B2 truncation)** — hard kill; caught by `test_cuda_ima_signature_extracted_beyond_5_line_tail` (drives the wide-surface extraction, asserts the 5-line excerpt would have missed it).
- **The no-port block masks the CUDA-IMA dead poll (M2)** — hard kill; caught by `test_poller_cuda_ima_before_noport_when_transient_no_port`.
- **The exhaustion path is re-driven by the watcher (M1)** — hard kill; caught by the `_is_transient_capacity_block` assertion.
- **Part C / no-port regresses** — hard kill; the `stamp_fn` default keeps Part C byte-unchanged; caught by the untouched Part C idempotency/lease tests.
- **Escalation force-stops a healthy run** — must NEVER rewrite a `status=running` poll except to CLEAR the record; caught by `test_cuda_ima_record_cleared_on_running_poll`.
