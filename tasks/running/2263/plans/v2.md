## 4. Design

### 4.1 Ref-resolution precedence ladder (decision, brief item 1)

The new flag is **`--repo-branch <branch>`** — deliberately the same spelling as the launch CLI's `--repo-branch`, so the Step 6a.5 stanza composes the gate call and the launch from ONE shell variable (the exact discipline the stanza already mandates for `--extra-sync-path`). `--ref` and `--repo-branch` are argparse-mutually-exclusive (both given ⇒ argparse exit 2).

Ordered ladder (first match wins):

1. **`--ref <R>` (explicit override, existing flag)** — used verbatim, no fetch, no existence probe (byte-identical to today's `--ref` path). Source label `ref-flag`.
2. **`--repo-branch <b>` (new)** — value validated at parse time (non-empty; not `origin/`-prefixed — critique item 5, §4.4.3). Bounded fetch of `<b>` + `main` (same fail-open `contextlib.suppress(TimeoutExpired)` semantics as today, honoring `--no-fetch`); check ref is `origin/<b>`. If `origin/<b>` does not verify after the fetch: raise `CheckRefResolutionError` → `main()` prints `ERROR: ...` naming the ref + remediation (push the branch; check the spelling; the launch CLI's own ls-remote guard would also refuse) and returns **2**. Never a silent fallback. Source label `repo-branch-flag`. `--repo-branch main` is legal and resolves `origin/main` (mirrors the dispatch escape).
3. **Invoking-cwd worktree-branch inference (new; repository-bound per MF-2)** — read the checked-out branch of the INVOKING cwd (`git branch --show-current` run in `Path.cwd()`; empty output = detached = no inference; any subprocess failure = no inference). The inferred branch `w` is accepted ONLY when BOTH guards pass: (a) issue scope — `w == f"issue-{issue}"` or `w.startswith(f"issue-{issue}-")` (digit-boundary safe: `issue-771-x` does not match issue 77); (b) **repository binding** — `git -C <invoke_cwd> rev-parse --path-format=absolute --git-common-dir` equals the same probe run in `repo_root` (both `os.path.realpath`-normalized; either probe failing = guard fails). Worktrees of one repository share the common dir; an unrelated checkout, a nested independent repository, or a submodule each have their own (verified empirically this session, §12 assumption 6) — so a foreign checkout sitting on a same-named `issue-<N>-*` branch can no longer select a same-named ref in the TARGET repository. Accepted ⇒ fetch `w` + `main`, check ref `origin/<w>`; `origin/<w>` absent after fetch (unpushed work branch — the lane would materialize nothing) ⇒ `CheckRefResolutionError` → exit 2 with push-the-branch remediation. Either guard failing (cwd on `main`, detached, a foreign issue's branch, a foreign repository) ⇒ fall to rung 4. Source label `worktree-branch`.
4. **Legacy default + ambiguity refusal (changed)** — bounded fetch of `issue-<N>` + `main` (as today) PLUS one glob prune-fetch `git fetch --prune origin --quiet --no-tags "+refs/heads/issue-<N>-*:refs/remotes/origin/issue-<N>-*"` (prune scoped to that refspec — fact-check-confirmed on git 2.34.1: a zero-match glob exits 0 and prune touches only refs under the refspec destination). Then enumerate suffixed candidates locally: `git for-each-ref "refs/remotes/origin/issue-<N>-*" --format=%(refname:short)`. Under `--no-fetch` the enumeration runs against existing local remote-tracking refs (hermetic for tests/sweeps).
   - Suffixed candidate set NON-empty (with or without the bare ref) ⇒ `CheckRefResolutionError` listing ALL candidates (bare included when present, sorted) + the remediations in this order (critique item 9): (1) `--repo-branch <b>` threaded from the launch variable — LEAD remedy; (2) run from the issue worktree; (3) explicit `--ref` LAST, with a caution that `--ref` bypasses the existence guard and can deliberately reintroduce wrong-tree grading → exit 2. This is the #1336 shape — including the single-suffixed-no-bare case, refused rather than auto-picked (a unique candidate is still a guess).
   - Bare `origin/issue-<N>` only ⇒ return it (source `bare-issue-branch-default`) — today's behavior, the fleet-common case.
   - Neither ⇒ `origin/main` (source `origin-main-default`) — today's behavior.

### 4.2 The two cwd regimes + gate-vs-dispatch parity (decisions, brief item 2; MF-2 wording fix; critique item 12)

- **Regime A — repo root (pinned to `main`; the normal orchestrator cwd):** rung 3 reads branch `main` → not issue-scoped → no inference. Without `--repo-branch`, resolution is rung 4: bare-only and none behave exactly as today; any suffixed candidate ⇒ REFUSE. With `--repo-branch` (the updated Step 6a.5 stanza threads it always), rung 2 resolves deterministically.
- **Regime B — issue worktree:** rung 3 accepts the worktree branch when it belongs to THIS issue (bare or suffixed) AND the checkout belongs to THIS repository, and resolves `origin/<branch>`, refusing only when that branch is unpushed. A worktree on a FOREIGN issue's branch, and any checkout in a FOREIGN or NESTED repository (MF-2), fall to rung 4.
- **What the guards guarantee (corrected wording, MF-2):** rung 3 only ever resolves a ref in the TARGET repository, for a branch name that is issue-scoped for THIS issue, from a checkout of the SAME repository. The guarantee for every non-qualifying cwd is **refusal-or-status-quo** (fall to rung 4, which resolves today's default or refuses) — NOT impossibility of every wrong-tree path: an explicit `--ref`/`--repo-branch` naming a wrong tree remains the caller's deliberate override. (v1's "structurally impossible" claim is retracted.)
- **Gate-vs-dispatch parity asymmetries (recorded, both safe-direction; critique item 12):** (a) the flag-less launch CLI default accepts ANY non-`main` current branch (`_current_git_branch`, applied at `dispatch_issue.py:2064`) and has a worktree-cwd fallback; the gate's rung 3 is deliberately NARROWER (issue-scoped + repository-bound) — a non-issue-shaped work branch gets a dispatch default but a gate rung-4 fall-through (status-quo or refusal), never a silent wrong tree. (b) On an unpushed branch the dispatch's ls-remote guard WARNs while the gate REFUSES exit 2 — the gate is deliberately stricter, because its whole job is pre-provision certification. These two asymmetries pre-answer "why does the gate refuse where the dispatch proceeds?".

### 4.3 Blast radius — combination matrix (decision, brief item 3; honest prose per critique item 2)

Rows are remote ref states for issue N; columns are invocation shapes. REFUSE = exit 2 with candidates + remediation on stderr (never a clean check; never exit 0).

| Remote refs for issue N | bare `--issue N` from repo root (rung 4) | `--repo-branch b` | cwd = this issue's worktree on branch w (rung 3) | explicit `--ref R` |
|---|---|---|---|---|
| bare `origin/issue-N` only | `origin/issue-N` (UNCHANGED) | `origin/b` if exists, else REFUSE (NEW rung) | `origin/w` if pushed, else REFUSE (NEW rung) | R verbatim (UNCHANGED) |

**Honest blast-radius statement (replaces v1's overclaim):** on the DEFAULT invocation, new behavior appears exactly where a suffixed `origin/issue-<N>-*` ref exists — and that includes ONE sub-case where today's behavior is CORRECT: an issue whose work branch IS the bare `issue-<N>` with a stale suffixed sibling (part of the measured 41-both population, §2 census) resolves correctly today and would now REFUSE. The suffixed-only (1 measured) and bare+suffixed-wrong-branch cases move from silent wrong-tree grades to refusals or correct resolutions. The fleet-common case (bare branch, canonical stanza call) keeps today's resolved ref/verdicts/exit code even before the call-site edit lands; after it, resolution moves to rung 2 (deterministic, same resolved ref). The unpushed-bare false PASS closes on the canonical path (§2, last bullet) — a deliberate improvement outside R4's scope.
