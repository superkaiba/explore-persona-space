# Plan — issue #1018: rubric-safe `JudgeCache` keying

`kind: infra` (workflow-fix, code-only). `Estimated GPU-hours (total): 0`.

## 0.0 TL;DR (plain English)

- **What I'll change:** the judge-result cache currently files each judgment under a hash of just (question, answer text). I'll add the judge's identity — which model, which rubric/prompt — to that hash, as a REQUIRED argument at every read/write site, so a refusal judgment can never be returned when the code asks for a harmful-compliance judgment.
- **What I expect:** all existing judge behavior unchanged except that old cache entries go cold (safe — they re-judge instead of returning possibly-wrong answers), and any code path that forgets to say which rubric it's judging under crashes immediately instead of silently reusing the wrong verdict.
- **What would change my mind:** finding a live call path where the rubric identity genuinely isn't available at cache time — then I'd fall back to a required explicit key on the caller's entry point instead of deriving it.

## 1. Goal + requirement + acceptance criteria

**Goal (task frontmatter):** Add rubric/judge-prompt hash + judge model id to `JudgeCache._hash_key` so cached judgments cannot leak across rubrics.

**Requirement.** Every `JudgeCache` read/write must be keyed on (rubric/judge identity, question, completion) — never on content alone — implementing `.claude/rules/llm-judging.md` rule 22's deferred code fix. Fail-loud: an unthreaded call site must raise `TypeError`, not silently reproduce #810.

**(a) New module-level helper + sentinels** (place directly above `class JudgeCache`, ~line 90):

```python
# Rubric-identity fingerprint (llm-judging.md rule 22, #810/#1018). The literal
# version tag makes any future key-schema change an explicit, automatic bust.
_JUDGE_CACHE_KEY_VERSION = "EPM_JUDGE_CACHE_KEY_V2"
_RUBRIC_SENTINEL_Q = "<RUBRIC_FINGERPRINT_SENTINEL_QUESTION>"
_RUBRIC_SENTINEL_C = "<RUBRIC_FINGERPRINT_SENTINEL_COMPLETION>"


def rubric_fingerprint(
    judge_model: str,
    judge_system_prompt: str,
    format_user_msg: Callable[[str, str], str] | None = None,
) -> str:
    """Stable rubric/judge identity hash for JudgeCache keys (rule 22, #810).

    Renders ``format_user_msg`` on fixed sentinel strings so a rubric that
    lives in the USER-message template (e.g. ``graded_judge`` fills the whole
    0-100 rubric into the user msg under a generic system prompt) enters the
    key, not only a system-prompt rubric. ``None`` means "no user template
    contributes rubric content" (caller builds content-only user messages).
    """
    rendered = (
        format_user_msg(_RUBRIC_SENTINEL_Q, _RUBRIC_SENTINEL_C)
        if format_user_msg is not None
        else "<no-user-template>"
    )
    content = f"{judge_model}\n===\n{judge_system_prompt}\n===\n{rendered}"
    return hashlib.sha256(content.encode()).hexdigest()[:16]
```

**(a) `_cache_key_parts` (line 1457)** gains the builder and returns a third part:

```python
def _cache_key_parts(item: DispatchItem, build_request: BuildRequest) -> tuple[str, str, str]:
    """(item_id, payload_json, request_fingerprint) — rule 22 (#810/#1018).

    The request fingerprint hashes the FULL built params (model + system +
    messages + max_tokens), a superset of the rubric identity, so two callers
    sharing a cache dir with different judges/rubrics can never cross-read.
    """
    try:
        payload_repr = json.dumps(item.payload, sort_keys=True, default=str)
    except TypeError:
        payload_repr = str(item.payload)
    built = json.dumps(build_request(item), sort_keys=True, default=str)
    fp = hashlib.sha256(built.encode()).hexdigest()[:16]
    return item.item_id, payload_repr, fp
```

**(b) `_cache_get` / `_cache_put` (lines 1465–1481)** thread it:

```python
def _cache_get(cache: JudgeCache, item: DispatchItem, build_request: BuildRequest) -> dict | None:

    return cache.get(q, c, rubric_key=fp)

def _cache_put(cache, item, res, build_request) -> None:
```

## 6. Kill criteria

- A live call path is found where rubric identity is genuinely unavailable at cache time (e.g. a consumer that constructs `JudgeCache` without the judge prompt/model in scope and cannot cheaply obtain them) → abort the derive-internally approach; pivot to a required explicit key parameter on that entry point (still fail-loud, never a default).
- `build_request` turns out non-deterministic or side-effectful for a REAL in-repo `dispatch_calls` caller (would make api_dispatch keys unstable across resume) → abort the built-request fingerprint; pivot to keeping the payload key + adding a required `cache_rubric_key: str` parameter to `dispatch_calls` when `cache_dir`/`cache` is supplied (public-signature change — flag to orchestrator, since it touches a shared entry point).
- Any unchanged-behavior test can only be made green by weakening its assertions → stop and re-plan; the fix must not change same-rubric semantics.

**D1 — Rubric key composition = sha256[:16] over (version tag, judge_model, judge_system_prompt, sentinel-rendered user template).**
- *What:* `rubric_fingerprint()` §3.1(a).
- *Why:* rule 22 names the key fields as "the full judge prompt (or a stable hash of it), plus the judge model id". The judge prompt is NOT always the system prompt: `graded_judge.judge_graded` puts a generic wrapper in `system` and fills the entire 0–100 rubric into the USER message via `format_user_msg` (graded_judge.py lines 175–190) — so sentinel-rendering the user template is load-bearing, not decorative. Fixed sentinels make the render deterministic and content-independent.
- *Source:* `.claude/rules/llm-judging.md` rule 22 (#882); incident #810; graded_judge.py read at lines 133–201.
- *Alternatives rejected:* (i) system-prompt+model only — misses rubric-in-user-template callers (graded_judge would key all behaviors identically when rubrics share the generic system wrapper); (ii) including `max_tokens` — no rubric semantics, churns keys on a harmless knob (noted: the api_dispatch adapter DOES fold params in, deliberately, because it cannot distinguish rubric from non-rubric params generically); (iii) a caller-supplied string label ("refusal") — human-error-prone, not content-derived, silently stale when a rubric is edited.

**D2 — Required keyword-only `rubric_key` on `_hash_key`/`get`/`put` (fail-loud), not a defaulted arg, not constructor-bound.**
- *What:* §3.1(b).
- *Why:* a defaulted arg (`rubric_key=""`) reproduces #810 silently at every unthreaded site — exactly the project's banned silent-default pattern (CLAUDE.md fail-fast). Constructor binding (`JudgeCache(dir, rubric_key=...)`) reads cleanly for `batch_judge` but breaks the api_dispatch adapter, where the key material is derived PER ITEM from `build_request(item)` and where tests inject pre-constructed caches into `dispatch_calls` (test_api_dispatch.py:634/651/676) without rubric knowledge at construction time. Keyword-only prevents positional confusion with a third positional slot.
- *Source:* task body diff sketch; CLAUDE.md "Fail fast — never hide failures"; test_api_dispatch.py read.
- *Alternatives rejected:* defaulted arg (silent bug); constructor-bound (adapter mismatch above); a compat shim keeping the 2-arg form working (anti-pattern per task brief — preserves the vulnerable call shape).

**D3 — Automatic bust via preimage change + `EPM_JUDGE_CACHE_KEY_V2` version literal; no cleanup of dead entries; filename shape unchanged.**
- *What:* §3.1(b), risk row 1.
- *Why:* changing the hash input makes ALL pre-fix content-keyed entries unreachable — the safe direction (cold miss → re-judge; a wrong read is impossible). The version literal makes this and any FUTURE schema change explicit and self-busting. Dead entries are tiny JSON files already classified re-derivable caches (`issue906_phase1_pilot.py::_is_rederivable_cache`, disk janitors) — cleanup would be scope creep for zero benefit. Keeping `{16-hex}.json` filenames preserves `_JUDGE_CACHE_ENTRY_RE` and janitor/upload-exclusion behavior.
- *Source:* issue906_phase1_pilot.py lines 1741–1762; standard cache-key-versioning practice.
- *Alternatives rejected:* per-rubric SUBDIR namespacing inside JudgeCache (changes the dir layout every consumer + the janitors' assumptions; the key already carries the isolation); a migration tool rewriting old entries (cannot recover which rubric produced an old entry — the information was never stored; #810 proves some old entries are cross-contaminated, so migrating them would LAUNDER bad data into the new schema).
