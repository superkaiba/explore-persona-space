# Plan — issue #755: reconciler must persist EVERY upheld finding

## §0.0 TL;DR (plain English)

- **What I'll run:** No experiment. I'm editing one workflow file — the spec for the "reconciler" agent that breaks ties when two reviewers disagree. Right now, when the reconciler decides a reviewer was right, it only writes a *subset* of those upheld complaints into the shared ledger that the next stage of the pipeline actually reads; the rest live only in its written verdict, which nothing downstream parses. I'm changing the spec so it must write down *every* upheld complaint, with a self-check ("I upheld N, I persisted N"), and I'm fixing the verdict table so "upheld" is a thing the agent can mechanically count rather than guess at.
- **What I expect:** After this edit, a reconciler verdict can never silently drop an upheld complaint, the count it checks against is read off explicit table values (not a vague "did I mean to address this?"), and when it overrules a clean-result formatting complaint it has to quote the exact spec rule it's relying on — so a human reading the verdict can check the reasoning.
- **What would change my mind:** If splitting the table's "weight" column into four explicit values turned out to break the existing `### Standing recommendations on PASS` flow (it doesn't — the new `Standing-only` value just feeds that section), or if requiring a written count conflicted with the standing "no new findings" rule (it doesn't — every persisted complaint was already raised by one of the two reviewers).

## §1. Goal

A reconciler verdict never silently drops an upheld finding, and a structure-lens override is grounded in the exact spec text it relies on. Concretely: every finding the reconciler upholds for addressing (its `### Findings adjudicated` table marks it `Blocking` or `Non-blocking-persisted`) is persisted to `concerns.jsonl` via `task.py raise-concern` with an `--evidence` pointer, so the `/issue` Step 5c-ter dispatch gate and every downstream reader see the full set — not just the production-path subset the current Step 4 covers. And when the reconciler PASSes a clean-result body despite a clean-result-critic structure-lens FAIL, the verdict quotes the SPEC.md clause that licenses the override.

### Acceptance criteria

1. `.claude/agents/reconciler.md` Step 4 contains an explicit completeness rule: "every upheld finding is persisted" with an "N upheld → N persisted" count check keyed on the table's `Weight ∈ {Blocking, Non-blocking-persisted}` values, ONE matching worked example (the #715 4-upheld / 4-persisted shape), and a persistence command template that REQUIRES `--evidence` (a pointer to the original reviewer finding marker / the cited artifact location / the reconciler's own `### Findings adjudicated` row or `### Rationale` paragraph), with the prose stating that `--summary` is only a short label, not the finding itself.
2. The spec requires a quoted SPEC.md clause when the reconciler overrides a clean-result-critic structure-lens FAIL with a PASS-class verdict — scoped "clean-result-critic ONLY — interpretation-critic / other roles have no SPEC document and are exempt."
3. The persistence verb is the existing `task.py raise-concern … --by reconciler` — no new marker kind, no `concerns.jsonl` schema change.
4. Existing reconcile semantics are preserved verbatim: binary verdict (Rule 1), no new findings beyond the two reviewers (Rule 2), ungrounded-blocker discard (Rule 9 / Step 1), one role-scoped `epm:review-reconcile v<round>` marker (Rule 5), and the `### Standing recommendations on PASS` H3 (now the documented home for `Standing-only` findings).

NOT persisted — list it in `### Standing recommendations on PASS` instead. A row

count the rows in `### Findings adjudicated` with Weight `Blocking` or
`Non-blocking-persisted` (= N upheld; `Standing-only` and `Discarded` rows do
NOT count) and confirm you issued exactly N `raise-concern` calls. State the
count in your verdict body. If they differ, you dropped a finding — fix it
before posting.

*Example (#715 shape):* you uphold 4 findings — 1 row Weight `Blocking`
(code-side null-deref), 3 rows Weight `Non-blocking-persisted` (analyzer-side

leaves the 3 others in the table is the #715 bug.

### Findings adjudicated
| Source | Finding (terse) | Verified? | Classification | Weight |

## §11. Decision Rationale

- **Check 1 (training hyperparameters):** N/A — no model training.

- **Mechanical persist-discriminator = Weight-enum split (preferred) vs a separate `Persisted? yes/no` column (alternative).**
  - *Why:* the count rule needs a mechanical, table-readable discriminator separating "persisted" from "not persisted." The existing Weight column already exists and already carries `Discarded`; splitting its values (`Blocking` / `Non-blocking-persisted` / `Standing-only` / `Discarded`) refines a header that's already there and threads cleanly into the existing `### Standing recommendations on PASS` H3. A separate `Persisted? yes/no` column would add a column and duplicate information already implied by Weight.
  - *Source:* existing Step 5 verdict-table template at `reconciler.md` lines 280–283 (Weight column = `Blocking / Non-blocking / Discarded`); existing `### Standing recommendations on PASS` H3 at lines 291–292 (the home for `Standing-only`).
  - *Alternatives rejected:* the separate `Persisted? yes/no` column (adds a column, redundant with Weight); keeping the old three-value enum (the round-1 blocker — `Non-blocking` maps from `Real-nonblocking` = "style nit / minor improvement / pedantry" per Step 3 line 196, so a count keyed on it sweeps in nits, contradicting the scope-out in §8 + §12).

- **Why require `--evidence` on every persistence call.**
  - *Why:* a persisted concern whose ≤200-char `--summary` carries the whole finding is a visible-but-not-identifiable version of the silent-drop failure #755 exists to kill — a downstream reader sees a row but cannot act on it. The binding protocol already says detail belongs in `--evidence`.
  - *Source:* `workflow.yaml § concerns_protocol.summary_cap` lines 1254–1259 ("Compose the summary as one tight sentence and move all detail to `--evidence`"); `scripts/task.py` line 1452 (`--evidence` is an optional CLI arg accepting a path / quote / pointer).
  - *Alternatives rejected:* leaving `--evidence` optional (reintroduces the visible-but-not-identifiable failure mode the round-1 statistics lens flagged as decisive).

- **Persistence verb = `task.py raise-concern … --by reconciler` (not a new marker kind).**
  - *Why:* the persist path already exists and is the canonical surface; introducing a new marker kind would change a public contract (the `concerns.jsonl` schema / dispatch-gate reader) and would itself need greenlight.
  - *Source:* existing `reconciler.md` Step 4 (lines 234–258) already uses `raise-concern`; existing `code-reviewer.md` Step 0.5/0.8 uses the same; `scripts/task.py` defines `raise-concern <N> --concern-id <id> --severity BLOCKER|CONCERN|NIT --summary "..." --by <reviewer> --round <int> [--evidence ...]` (lines 28–29, parser at 1414+); `workflow.yaml § concerns_protocol.reconciler_special_case` (lines 1270–1290) carries the "persist a finding already on the table via `raise-concern --by reconciler`" carve-out.
  - *Alternatives rejected:* a new `epm:reconcile-finding` marker kind (changes public contract → architectural greenlight, and the dispatch gate doesn't read it); persisting via `defer-concern` (that verb is for severity DOWNGRADES, not raises).

- **Completeness-check shape = in-prose "N upheld → N persisted" count keyed on the new Weight values, not a separate verifier/marker.**
  - *Why:* the reconciler is an LLM agent following prose instructions; the analogous self-check pattern is already how the spec gates other duties (e.g. the one-marker-per-round rule, Rule 5). With Delta A2 the count is now keyed on explicit table values, so the self-check is mechanical-readable. A mechanical verifier over `concerns.jsonl`-vs-verdict-table would be new tooling outside this file's scope.
  - *Source:* existing Step 4 prose pattern + Rule 5 self-check style in `reconciler.md`; Delta A2 table values.
  - *Alternatives rejected:* a `verify_*.py` cross-check (new script, out of scope); a new `epm:reconcile-completeness` marker (new contract).

- **SPEC-quote requirement scope = clean-result-critic structure-lens FAIL only.**
  - *Why:* clean-result-critic Lenses 1–15 are defined against `.claude/skills/clean-results/SPEC.md`; an override of one is a claim about a specific SPEC clause and must cite it. interpretation-critic has no SPEC document, and critic/code-reviewer FAILs are grounded in the artifact (plan/diff), not a structure spec — so the quote requirement is meaningless for them.
  - *Source:* `.claude/skills/clean-results/SPEC.md` (canonical structure-lens reference, referenced from `clean-result-critic.md` + CLAUDE.md § Experiment Report Structure); agent memory `feedback_claude_clean_result_critic_underapplies_spec_text.md` (the under-application pattern being promoted into the spec).
