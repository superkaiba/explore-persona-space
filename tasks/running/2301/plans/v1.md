## Requirement + acceptance criteria

**Requirement.** Step 10d Guard 5 ("Sibling merge-sequencing hold + proactive
pre-resolution", #1757) must fire only on a genuine Step 2b candidate RECORD,
never on a marker note that merely mentions the candidate token in prose.

Today's trigger (`.claude/skills/issue/steps/18-step-10d.md:649` — Guard 5's body
was relocated there from SKILL.md by the #2155 split; the task body's
`workflow_fix_target: .claude/skills/issue/SKILL.md` predates the split):

```bash
grep -F 'merge-hold-candidate' "$(uv run python scripts/task.py find <N>)/events.jsonl"
```

is an unanchored fixed-string match over the whole events file, note prose
included. Observed failure (#2290): a `[long-phase-heartbeat]` note truthfully
reporting ZERO candidates quoted the literal token; every later Guard 5 pass
matched that note and fired with no sibling named.

**Acceptance criteria:**

1. A note that merely mentions the token — including the #2290 heartbeat shape,
   and a note carrying the token and a `sibling=<digits>` token NON-adjacently —
   does NOT satisfy the trigger.
2. A genuine Step 2b candidate record (note leading
   `merge-hold-candidate sibling=<M> path=<file> source=...`, producer at
   `.claude/skills/issue/steps/05-step-2b.md:72`) DOES satisfy it.
3. Guard 5's own `merge_hold: sibling=<M> waited=... outcome=...` disposition
   note does NOT satisfy it (guards against an over-loose `sibling=`-only
   predicate).
4. The no-candidate path stays exactly ONE grep (no JSON-parsing pass).
5. A regression test pins criteria 1-3 behaviorally (fixtures) and pins the
   anchored form textually (the bare `grep -F 'merge-hold-candidate'` shape must
   not return).
6. Out of scope, untouched: the hold semantics, the bounded 45-min Monitor wait,
   half (ii)'s in-worktree pre-resolution, the Step 2b record format.

## Method delta

The guard's own body already requires a named sibling (it iterates "per named
sibling `<M>` (dedup)" via `sibling=` extraction), so anchoring the trigger on
the token + adjacent `sibling=<digits>` makes trigger and body consistent — a
match with no named sibling is semantically a no-op today, minus the diagnostic
detour and the spurious-hold/pre-resolve risk. The chosen predicate:

```bash
grep -E 'merge-hold-candidate sibling=[0-9]+' "$(uv run python scripts/task.py find <N>)/events.jsonl"
```

One grep, `-F` → `-E`, requiring the Step 2b record's exact adjacency. A prose
note quoting the FULL record verbatim (token + adjacent sibling digits) would
still match — accepted residual: such a note names a concrete sibling, half
(i)'s per-sibling no-hold checks (merged / parked / unreadable / cap-expired
sticky) bound the damage, and marker-composition hygiene (do not quote full
records in prose notes) is the cheap upstream defense. Not chased further —
the task bounds this to a trigger-anchoring fix.
