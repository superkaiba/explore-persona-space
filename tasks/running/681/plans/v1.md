# Bound active-task VM disk by construction: relocate `.claude/worktrees/` + per-issue caches onto a dedicated GCP persistent disk

> **ARCHITECTURAL — needs user greenlight.** This changes the orchestration VM's
> foundational storage layout (attaches a new GCP persistent disk, relocates the
> 250 GB `.claude/worktrees/` tree onto it, takes on a recurring ~$50/month GCP
> cost) and is therefore gated at the Step 2c plan-approval gate regardless of
> the 0 GPU-h cap. The cutover touches every concurrent session's filesystem and
> MUST happen during a brief drain window — do not approve without reading §6
> (Compatibility / migration) and §10 (Kill criteria).

## §0 Plan Summary

**What:** Attach a new **1 TB `pd-balanced` GCP persistent disk** to the
orchestration VM (`cia-benchmark-vm`, project `introsp-experiments`,
`us-central1-a`), mount it at `/mnt/eps-data`, and **relocate the
`.claude/worktrees/` tree** (currently **250 GB**, the unbounded grower — every
active task's worktree + its per-issue `data/issue_<N>/{hf_dl,g*_dl,store}`
caches land there) onto the new disk via a one-time `rsync` + **bind mount**, so
the heavy active-task footprint never lands on the 500 GB boot disk holding `/`.
A runaway task then fills the 1 TB data disk, NOT the shared `/`; every other
concurrent session keeps working and the boot disk stays healthy.

**Chosen mechanism: Option A (dedicated GCP PD), NOT Option B (ext4 project
quotas).** Option B is **non-viable on this host**: enabling `prjquota` on a
live, mounted **root** ext4 filesystem requires unmounting `/` (a reboot /
single-user procedure — impossible on the running VM with 39 worktrees and a
live 141 GB #658 process holding open files), and the `quota` userspace tooling
is not even installed. Option A hot-attaches with **zero downtime** (gmail-owner
access confirmed) and a ~10-minute cutover drain.

**Cost:** 1 TB `pd-balanced` at **$0.10/GB-month** (us-central1) = **$100/month**
recurring; or 512 GB = **$51.20/month** (2× current worktree footprint headroom).
Recommended: **1 TB** ($100/mo) for 4× headroom over the current 250 GB peak.
One-time setup: ~2-3 hours of orchestrator/operator time + a ~10-min drain
window. **`Estimated GPU-hours (total): 0`**

**Invariant preserved:** no code path auto-deletes active data; the data disk is
a *containment boundary*, and a disk-full condition is recoverable (the data
disk fills, `/` stays healthy, sessions keep running, and the existing
`vm_disk_guard` escalation re-points at the new mount). This is the
**bounded-by-construction** structural fix #679 deferred.

**Top risks:** (1) cutover-time race — a session writing into `.claude/worktrees/`
during the `rsync` swap; mitigated by a drain-to-quiescent window + the live
#658 worktree handled by exclude-and-defer. (2) bind-mount not surviving reboot;
mitigated by an `/etc/fstab` entry + a boot-time `systemd` mount unit.

## §1 Goal + acceptance criteria

**Goal:** Make active-task VM disk consumption bounded by construction so no
single task can exhaust the shared CPU-VM root disk (`/`), and so a disk-full
condition is recoverable without deleting any active task's data.

**Acceptance criteria (quantitative):**

1. **Containment:** A 200 GB write into one issue's data dir
   (`<repo>/.claude/worktrees/issue-<N>/data/issue_<N>/hf_dl/...`) lands on
   `/mnt/eps-data` and leaves `/` (the boot disk) usage **unchanged** (verified:
   `df /` before/after the write shows < 1 GB delta on `/`; the growth shows on
   `df /mnt/eps-data`).
2. **No active-data deletion:** A `/`-at-95% (or data-disk-at-95%) condition
   triggers escalation (Telegram + sidecar) but **no active task's
   worktree/cache/store is deleted** (verified by the existing
   `vm_disk_guard` active-skip + escalate path, re-pointed at the new mount).
3. **Recovery without downtime:** When the **data disk** is wedged at 100%, the
   boot disk `/` stays < 85% used, every concurrent session continues to spawn
   Bash successfully (the silent-Bash-failure regime is on `/`, which is now
   protected), and the operator's recovery is the existing safe reclaim
   (`clean_experiment_downloads.py <N> --apply` on a terminal issue, or a
   data-disk resize) — never an active-data delete.
4. **Path transparency:** Every existing consumer that resolves
   `repo_root()/.claude/worktrees/...` or `repo_root()/data/issue_<N>/...`
   continues to resolve unchanged (bind mount is path-faithful); the full
   `pytest` suite passes; `new_worktree.sh` creates worktrees on the new disk
   transparently.
5. **Reboot-durable:** The mount + bind survive a VM reboot (fstab + systemd
   mount unit; verified by `systemctl status` + a simulated remount).
6. **Live-#658 untouched:** The migration does not move, copy, or interrupt the
   live 141 GB `.claude/worktrees/issue-658` worktree or its process.

## §3 Option comparison — A (dedicated GCP PD) vs B (ext4 project quotas)

| Dimension | **Option A — dedicated GCP PD + bind-mount** | **Option B — ext4 `prjquota` per issue** |
|---|---|---|
| **One-time cost** | ~2-3 h operator time; ~10-min drain window; no reboot | ~3-4 h operator time + **a VM reboot / single-user boot** to unmount `/` and `tune2fs -O quota,prjquota` (the root fs cannot be converted live); install `quota` pkg |
| **Recurring cost** | **~$100/mo** (1 TB pd-balanced @ $0.10/GB-mo) or ~$51/mo (512 GB) | **~$0** recurring, but ongoing per-issue `chattr +P` + `setquota -P` setup wired into the worktree-creation path (developer-time, every new issue) |
| **Blast radius** | Confined to two trees on a separate physical device; boot disk untouched after cutover | Touches the **root filesystem's mount options + on-disk feature flags** — a quota subsystem bug or a wrong `setquota` value can wedge writes for ALL sessions on `/` |
| **Operational complexity** | Low: standard GCP attach + fstab + systemd; one mount to monitor | High: per-issue project-ID allocation, quota-vs-EIO disambiguation, quota accounting that must survive crashes, a `quotacheck` after any unclean shutdown |
| **Migration risk to active sessions** | **Drain to quiescent worktrees**, rsync+swap the (non-#658) trees, bind-mount; #658 excluded-and-deferred. No reboot → 38 of 39 sessions never interrupted | **Requires a reboot of the whole VM** (root fs unmount) → **every** session + the live #658 process is killed. Unacceptable while #658 is live |
| **Recovery semantics** | Data disk fills → `/` stays healthy → sessions keep running → operator resizes the PD live (`gcloud compute disks resize` + `resize2fs`, zero downtime) or reclaims a terminal issue's cache | Quota hit → that issue's writes fail loudly (good signal) BUT a misconfigured/absent quota lets the issue fill `/` again (no containment for un-quota'd paths); recovery from a quota-accounting corruption needs `quotacheck` (offline) |
| **Observability** | `df /mnt/eps-data` is a clean per-disk signal; the existing guard re-points trivially | `repquota -P /` per-project; must distinguish at-quota EDQUOT from unrelated EIO in the escalation path |
| **No-delete-active-data invariant** | Native: containment is physical, deletion never required for recovery | Native for the quota'd issue (its writes fail, nothing deleted) — but a NEW issue with no quota yet, or a path outside the quota'd dirs, can still exhaust `/` → the invariant holds only if EVERY write path is quota-covered, which is fragile |

**The decisive factor:** Option B's prerequisite — `tune2fs -O quota,prjquota`
on the **root** filesystem — **cannot be applied to a mounted `/`**. The web
research is explicit: "for root filesystem, this is more complex as it requires
special boot procedures to unmount before modification." On this VM that means a
reboot into single-user / a rescue boot, which **kills the live 141 GB #658
process** and all 38 other sessions. With #658 explicitly off-limits (parent
plan + this task's invariants), Option B is **infeasible during the window we
must act in** (`/` is at 96% NOW). Option A hot-attaches with zero downtime.

## §4 Design — concrete steps, file paths, commands, diffs (Option A)

### Phase 0 — Provision + attach the disk (operator + gmail-owner credentials)

The `eps-router` SA (active `eps-gcp` config) is scoped to
`eps-persona-gpu-jun2026` and **cannot** touch `introsp-experiments`. The VM
lives in `introsp-experiments`, where **`thomasjiralerspong@gmail.com` has
`roles/owner`** (verified). All Phase-0 gcloud commands run under
`--account=thomasjiralerspong@gmail.com --project=introsp-experiments`.

```bash
ACC=thomasjiralerspong@gmail.com
PROJ=introsp-experiments
ZONE=us-central1-a
VM=cia-benchmark-vm
DISK=eps-data-disk
SIZE=1000GB            # 1 TB pd-balanced; see §11 for the size/type rationale

# 1. Create the data disk (empty, pd-balanced, same zone as the VM)
gcloud compute disks create "$DISK" \
  --account="$ACC" --project="$PROJ" --zone="$ZONE" \
  --size="$SIZE" --type=pd-balanced \
  --labels=purpose=eps-worktrees,owner=eps-orchestration

# 2. Hot-attach to the running VM (NO restart — verified hot-pluggable)
gcloud compute instances attach-disk "$VM" \
  --account="$ACC" --project="$PROJ" --zone="$ZONE" \
  --disk="$DISK" --device-name=eps-data-disk --mode=rw

# 3. (one-time) set autoDelete=false so a VM delete never silently drops the disk
gcloud compute instances set-disk-auto-delete "$VM" \
  --account="$ACC" --project="$PROJ" --zone="$ZONE" \
  --disk="$DISK" --no-auto-delete
```

### Phase 1 — Format + mount the disk (on the VM, passwordless sudo confirmed)

```bash
# The attached device appears under a stable symlink by device-name:
DEV=/dev/disk/by-id/google-eps-data-disk        # predictable; survives reattach
# Confirm it is the new, EMPTY disk before formatting (NEVER format a non-empty dev):
sudo blkid "$DEV" || echo "no filesystem (expected for a fresh disk)"

# Format ext4 (lazy_itable_init for fast format of a 1 TB disk)
sudo mkfs.ext4 -m 0 -L eps-data "$DEV"          # -m 0: no root-reserve on a data disk

# Mount point
sudo mkdir -p /mnt/eps-data
sudo mount "$DEV" /mnt/eps-data
sudo chown "$USER:$USER" /mnt/eps-data

# Persist across reboot — fstab by LABEL (device names can renumber)
echo 'LABEL=eps-data  /mnt/eps-data  ext4  defaults,discard,nofail  0 2' \
  | sudo tee -a /etc/fstab
# `nofail` so a missing data disk never blocks VM boot (the OS still comes up; the
# bind-mount unit below fails-soft and the guard escalates).
sudo systemctl daemon-reload     # pick up the new fstab entry
findmnt /mnt/eps-data            # assert it mounted
```

### Phase 2 — Relocate `.claude/worktrees/` via rsync + bind mount (the cutover)

The bind mount is the load-bearing transparency trick: every consumer resolves
`repo_root()/.claude/worktrees/...` — a bind mount makes that SAME path serve
files physically stored on `/mnt/eps-data`, so **no consumer code changes**.

```bash
REPO=/home/thomasjiralerspong/explore-persona-space
SRC="$REPO/.claude/worktrees"
DST=/mnt/eps-data/worktrees

# 2a. DRAIN to quiescent (see §6): pause new worktree creation; wait until no
#     non-#658 worktree has a live writer. The live #658 worktree (141 GB) is
#     EXCLUDED and deferred — it is copied in a later, #658-quiescent window.
mkdir -p "$DST"

# 2b. First-pass rsync while sessions are (mostly) idle — copies everything to the
#     new disk; --exclude the live #658 tree (handled separately, §6).
rsync -aHAX --info=progress2 --exclude='issue-658/' --exclude='issue-658-*/' \
  "$SRC"/ "$DST"/

# 2c. SHORT freeze: stop spawning, do a final delta rsync (fast — only changes),
#     then swap. Keep the original as a backup until verified.
rsync -aHAX --delete --exclude='issue-658/' --exclude='issue-658-*/' "$SRC"/ "$DST"/
mv "$SRC" "$SRC.premigrate"          # keep as rollback safety net
mkdir -p "$SRC"                       # empty mountpoint
sudo mount --bind "$DST" "$SRC"       # bind: repo path now backed by the data disk

# 2d. Re-stage the live #658 tree INTO the bind target without moving it (§6):
#     because issue-658 was excluded, it still lives in $SRC.premigrate. Move it
#     into the bind-mounted location (a rename within the same logical path is a
#     cross-device COPY here — only safe once #658 is quiescent; see §6).
```

`/etc/fstab` bind entry (reboot-durable; ordered AFTER the data-disk mount):

```
/mnt/eps-data/worktrees  /home/thomasjiralerspong/explore-persona-space/.claude/worktrees  none  bind,nofail  0 0
```

A `systemd` mount unit is the more robust alternative to the fstab bind line
(systemd orders it after `mnt-eps\x2ddata.mount`); the implementer picks ONE —
fstab bind with `x-systemd.requires=/mnt/eps-data` is the simplest:

```
/mnt/eps-data/worktrees  /home/.../.claude/worktrees  none  bind,nofail,x-systemd.requires=/mnt/eps-data  0 0
```

### Phase 3 — Repo-root `data/` (small, 475 MB) — same pattern, optional

The repo-root `data/` is only 475 MB today (the heavy per-issue data lands in
worktrees, not here), so relocating it is low-value. **Decision: bind-mount it
too for symmetry and future-proofing** (a non-worktree run that writes
`repo_root()/data/issue_<N>/hf_dl` would otherwise hit `/`):

```bash
rsync -aHAX "$REPO/data"/ /mnt/eps-data/data/
mv "$REPO/data" "$REPO/data.premigrate"; mkdir -p "$REPO/data"
sudo mount --bind /mnt/eps-data/data "$REPO/data"
# fstab: /mnt/eps-data/data  /home/.../explore-persona-space/data  none  bind,nofail,...  0 0
```

## §6 Compatibility / migration plan

**What a currently-running session sees:** nothing changes for any session whose
worktree is NOT being rsync'd at that instant. The bind mount is path-faithful —
after cutover, `ls .claude/worktrees/issue-<N>` returns the same files at the
same path; only the backing device changed. There are **39 worktrees** and ~28
active sessions.

**The hard constraint: the live 141 GB `.claude/worktrees/issue-658` process.**
It holds open files; a cross-device move of an open-file tree is unsafe. So #658
is **excluded from the first cutover** (Phase 2b/2c `--exclude='issue-658*/'`)
and stays on the boot disk until it is quiescent.

**Cutover sequence (no reboot, ~10-min freeze window):**

1. **Announce + pause new spawns.** Set a sentinel
   (`.claude/cache/worktree-migration.LOCK`) that `new_worktree.sh` checks and
   refuses on (2-line guard); post a fleet note. Existing sessions keep running.
2. **First-pass rsync** (Phase 2b) while sessions run — copies the bulk
   (everything except #658) to `/mnt/eps-data/worktrees`. Long but non-blocking
   (sessions still read/write the original tree).
3. **Quiesce the non-#658 worktrees:** wait until the auto-generated /
   per-issue worktrees being copied have no live writer (the
   stalled/idle-session signals + `lsof` on each tree confirm). Sessions parked
   at gates (`awaiting_promotion`, `plan_pending`) are quiescent by definition.
4. **Final delta rsync + swap** (Phase 2c): fast (only changes since step 2),
   then `mv .claude/worktrees .claude/worktrees.premigrate`, recreate the empty
   dir, `mount --bind`. The `.premigrate` copy is the rollback net.
5. **#658 deferred tail:** once #658 reaches a quiescent point (a phase boundary
   / `awaiting_promotion` / the user confirms it is safe), copy its 141 GB tree
   from `.claude/worktrees.premigrate/issue-658*` into the bind-mounted location
   and remove the boot-disk copy. **If #658 never quiesces before the boot disk
   is critical, the operator instead reclaims #658's re-downloadable cache**
   (the 139 GB `hf_dl` store, re-downloadable per #679's analysis) with the
   existing safe reclaim — freeing `/` without moving the live tree.
6. **Lift the LOCK.** Remove the migration sentinel; new worktrees now land on
   the data disk.

**No-downtime alternative if a drain window is unacceptable:** because bind
mounts are per-path, an even safer cutover is to bind-mount ONLY the
*sub-directories* that are quiescent and leave busy ones on the boot disk
temporarily — but this is more fiddly; the drain-window approach is preferred
given 28 sessions, most of which are gate-parked.

**Rollback:** `umount` the binds, `mv .claude/worktrees.premigrate
.claude/worktrees`, remove the fstab lines. The `.premigrate` trees are kept
until §1's acceptance criteria all pass, then deleted to reclaim boot-disk
space.

## §7 Risks + mitigations

| # | Risk | Likelihood | Mitigation |
|---|---|---|---|
| a | **Boot-disk-vs-data-disk failure modes:** the data disk fails to mount on reboot → worktrees vanish from the expected path | Low | `nofail` in fstab (VM still boots); `new_worktree.sh` data-disk-mounted assert fails loud rather than silently writing to `/`; the guard escalates a missing mount. `.premigrate` rollback kept until verified. |
| b | **Cutover race:** a session writes into `.claude/worktrees/` between the final rsync and the bind swap → that write lands on the old (now `.premigrate`) tree and is invisible post-swap | Medium | The migration LOCK pauses `new_worktree.sh`; the final delta rsync runs only after the non-#658 trees are confirmed quiescent (`lsof`); the freeze window is < 10 min; the `.premigrate` copy preserves any straggler write for manual reconciliation. |
| c | **Live #658 disruption** | Low (excluded by design) | #658 is `--exclude`d from the first cutover and only moved when quiescent; if it never quiesces, its re-downloadable cache is reclaimed instead (#679 path). Invariant #6. |
| d | **Recovery-when-data-disk-full:** operator must know what to do | Medium | Documented in CLAUDE.md + the escalation message: (1) `clean_experiment_downloads.py <N> --apply` on a TERMINAL issue, or (2) live-resize the PD: `gcloud compute disks resize eps-data-disk --size=2000GB ...` + `sudo resize2fs /dev/disk/by-id/google-eps-data-disk` (zero downtime). ## §11 Decision Rationale (load-bearing fields + sources)

- **Mechanism = Option A (dedicated PD + bind mount), NOT Option B (ext4
  prjquota).** *Why:* enabling `prjquota` on the **root** ext4 fs requires
  unmounting `/` (reboot/single-user), which kills the live #658 process + all
  sessions — infeasible while `/` is at 96% and #658 is live; `quota` tooling
  isn't installed; Option A hot-attaches with zero downtime. *Source:* Red Hat
  ext4-quota docs + the ext4-quota web research ("for root filesystem... requires
  special boot procedures to unmount before modification"); verified on-VM
  (`setquota: command not found`; root fs `Filesystem features:` lacks
  `project`/`quota`; live #658 = 141 GB holding open files).
- **Disk type = `pd-balanced`.** *Why:* the workload is cache/checkout I/O
  (worktree files, HF download caches), not latency-sensitive; pd-balanced
  matches the boot disk's existing class and is 1.7× cheaper than pd-ssd.
  *Source:* GCP disk pricing (us-central1 pd-balanced $0.10/GB-mo vs pd-ssd
  $0.17/GB-mo, [gcloud-compute.com/diskpricing](https://gcloud-compute.com/diskpricing.html)
  + [cloud.google.com/compute/disks-image-pricing](https://cloud.google.com/compute/disks-image-pricing));
  the VM's boot disk is already pd-balanced (verified via `gcloud compute disks
  describe`).
- **Disk size = 1 TB (recommended) / 512 GB (cost-minimal alternative).** *Why:*
  current `.claude/worktrees/` peak is 250 GB; 1 TB = 4× headroom (a runaway
  task + several concurrent large worktrees), and GCP PDs can only grow, not
  shrink, so over-provisioning is the safe direction (live-resizable up at zero
  downtime). 512 GB = 2× headroom at half the cost if $51/mo is preferred.
  *Source:* measured footprint (`du -sh .claude/worktrees` = 250 GB,
  issue-658 = 141 GB, 2026-06-27); GCP PD resize-up-only constraint
  ([cloud.google.com/compute/docs/disks](https://cloud.google.com/compute/docs/disks/persistent-disks)).
- **Mount transparency = `mount --bind` (symlink as K2 fallback).** *Why:* the
  bind keeps the exact `repo_root()/.claude/worktrees/...` path every consumer
  resolves, so zero consumer-code changes. *Source:* the repo's path-resolution
  contract — every disk consumer goes through `repo_root()` / `git
  --git-common-dir` (grepped: `clean_experiment_downloads.py`,
  `vm_disk_guard.py`, `worktree_audit.py`, `new_worktree.sh`,
  `task_workflow.py` all resolve `.claude/worktrees` relative to the repo root).
- **Watched-disk set widens to {`/`, `/mnt/eps-data`}.** *Why:* the unbounded
  grower now lives on the data disk; the #679 guard + watcher must escalate on
  the data disk too. *Source:* #679's `vm_disk_guard` active-escalation contract
  (kept; only the `df` target set widens) + the parent plan's deferral of the
  hard bound to this task.
- **Escalation channel = existing sidecar + Telegram, never per-run `task.py`
  commits.** *Source:* #679 invariant (carried forward verbatim; CLAUDE.md
  index.lock-churn rule).
- **Repo-new model id smoke:** N/A — no model in this task.
