## 3. Design

Replace `_v4_results_body` (lines 2634–2666) with the absolute-index cut. Complete replacement code:

```python
def _v4_results_body(body: str) -> str | None:
    """Return the `## Results` section text TRUNCATED at the v4 footer.

    `section_text(body, "Results")` returns everything from `## Results`
    to end-of-body, because the `**Repro:**` / `**Context:**` footer is NOT
    an H2 — so the footer's prose-like lines bleed into the LAST result's
    prose and inflate `_finding_prose_cap_results` / `check_v4_results_beat`
    (a false ≥180-word hard FAIL on a conforming body; a defeated
    interpretation-beat WARN for the last result). This helper cuts the
    section at the footer boundary so the per-result scans see only the
    real Results content. None when `## Results` is absent.

    The cut is at the ABSOLUTE line index from `_v4_footer_start_line`,
    intersected with the section's `find_h2_sections` line range — NEVER by
    string-matching the footer's first line: when the footer is preceded by
    a `---` rule its first line is `---`, and a legal mid-Results `---`
    rule between results would truncate every later result out of checks
    11b/20/21 (#1109; masked two ≥180-word hard FAILs on #825).
    """
    lines = body.splitlines()
    section: tuple[int, int] | None = None
    for name, start, end in find_h2_sections(body):
        if name.casefold() == "results":
            section = (start, end)
            break
    if section is None:
        return None
    start, end = section
    footer = _v4_footer_start_line(body)
    if footer is None or not (start <= footer < end):
        # No footer, or the footer lies outside this section's range (e.g.
        # a stray H2 after ## Results): plain section text — identical to
        # section_text(body, "Results").
        return "\n".join(lines[start:end]).strip()
    # Cut at the footer start, then drop trailing `---` rule + blank lines
    # just above it (footer chrome, not Results content).
    rlines = lines[start:footer]
    j = len(rlines) - 1
    while j >= 0 and rlines[j].strip() in ("", "---"):
        j -= 1
    return "\n".join(rlines[: j + 1]).strip()
```

**Why this is equal-output on bodies with no mid-Results `---`:** both old and new reduce to "content lines from the line after `## Results` up to the pre-footer chrome, with leading/trailing whitespace stripped." The old path operated on the pre-stripped `section_text` string and cut at the (unique, footer-only) `---` match; the new path slices the same raw lines at the footer's absolute index. When Results is the last H2 (`end == len(lines)`) and the footer exists, `_v4_footer_start_line`'s index falls in `[start, end)` and points at exactly the line the old code matched; the identical trailing walk-back (`strip() in ("", "---")`) then yields the same content lines, and the final `.strip()` equalizes leading/trailing whitespace. String equality, verified mechanically by the blast-radius differ in §4.

**Edge cases (a)–(i):**

- **(a) No footer at all** (`_v4_footer_start_line` → `None`): return the plain joined-and-stripped section range — exactly `section_text(body, "Results")`. Identical to the old `if not footer: return results` path, including a body whose Results ends with a bare `---` and no footer (the trailing rule is retained, as today — the trailing-strip runs ONLY on the footer-cut branch, preserving parity).
- **(b) Footer with no preceding `---`**: `_v4_footer_start_line` returns the `**Repro:**` line index itself; the slice ends just before it; the walk-back strips the blank gap. Old behavior: matched the full `**Repro:** ...` line string and stripped the same gap. Equal output.
- **(c) Mid-Results `---` (the bug)**: the cut is at the footer index, which is strictly after every result; mid-Results rules are ordinary content lines inside the slice and survive. Checks 11b/20/21 now see the complete Results text. This is the one deliberate behavior change.
- **(d) Multiple mid-Results `---`**: same as (c) — no `---` content matching happens anywhere except the contiguous chrome tail directly above the footer.
- **(e) `---` inside a fenced code block within Results**: irrelevant to the cut — the cut is at the footer index and `_v4_footer_start_line` is already fence-aware. The only residual `---` sensitivity is the trailing walk-back, which inspects only the contiguous blank/`---` run abutting the footer; a fenced `---` there would require an unclosed fence abutting the footer (degenerate), and the old code's walk-back behaved identically — parity preserved, no special handling added.
- **(f) Footer `**Repro:**` inside a fence**: already ignored by `_v4_footer_start_line` (lines 2613–2619); such a body resolves as "no footer" → case (a).
- **(g) `## Results` absent**: `find_h2_sections` yields no match → `None`, same as `section_text` returning `None` today. All three consumers already handle `None`.
- **(h) Results not the last H2**: `check_v4_structure` hard-FAILs a stray H2, but the helper still runs on such a body (checks are independent). `end` is then the stray H2's line; a footer after it sits outside `[start, end)` → the guard returns the plain section text. Old behavior: the footer's first line usually doesn't appear inside Results → same plain text; but if Results contained a `---`, the OLD code truncated there (the same bug class) — the new code correctly does not. Net: equal or strictly-more-correct.
- **(i) Blank/`---`-only tail between last result and footer**: still stripped — the walk-back loop is carried over verbatim from the old implementation (it also eats stacked double rules `---\n---` above the footer, matching old behavior, since `_v4_footer_start_line` backs up over only ONE rule).

**`_v4_footer_text` stays string-based as-is** — it already slices at the absolute index and has no first-line matching; no other helper shares the bug (grep in §2). Diff is confined to the one function + tests.

## 8. §11 Decision Rationale

N/A — no training hyperparameters (`kind: infra`).

One load-bearing design decision:

- **What:** cut `## Results` at the absolute line index from `_v4_footer_start_line(body)` intersected with the `find_h2_sections` range — rejecting (i) the current footer-first-line string match and (ii) the `**Repro:**`-label-anchor-with-local-`---`-strip alternative.
- **Why:** the string match is the bug (any mid-Results `---` collides with the footer's first line); the `**Repro:**`-anchor alternative re-derives what `_v4_footer_start_line` already computes (first non-fenced `**Repro:**`, backed up over the adjacent rule) and would leave two footer resolvers to drift apart. Absolute-index slicing on the raw `body.splitlines()` also sidesteps the `section_text` `.strip()` offset shift the clarifier flagged.
- **Source:** in-repo precedent at lines 8710 + 8743–8745 (`_bare_issue_ref_hits` uses exactly this section-range × footer-index intersection) + task #1109 body / clarifier findings.
- **Alternatives:** (i) string match — rejected, is the bug; (ii) `**Repro:**` anchor + local strip — rejected, duplicates the existing resolver; (iii) offset-mapping the footer index into the stripped `section_text` string — rejected, fragile against the strip shift.
