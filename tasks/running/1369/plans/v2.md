## 4. Design

### 4.1 `src/explore_persona_space/orchestrate/env.py` — new function + two call sites + docstring line

**(a) New function, inserted directly after `_apply_shared_vm_thread_caps` (after line 168):**

```python
def _apply_shared_vm_hf_cache_redirect() -> None:
    """setdefault HF_HUB_CACHE + HF_XET_CACHE onto the #681 data disk (shared VM only).

    The boot disk ``/`` (485 GB) hit 100% twice on 2026-07-15 (#1073 -> #1369):
    the HF hub cache (~97 GB) and the transient xet chunk cache (~11 GB during
    prefix staging) both default under ``~/.cache/huggingface`` on ``/``.
    Redirect BOTH heavy caches onto the existing user-owned data-disk cache
    (``/mnt/eps-data/<user>/huggingface-cache/{hub,xet}`` — it already holds
    the project data-repo dataset cache from prior manual redirects; HF
    clients mkdir cache dirs on demand, so no migration step is needed).

    Deliberately NOT ``HF_HOME``: the token file (``HF_HOME/token``), the
    ``datasets`` processed cache (~3.7 GB), ``stored_tokens``, and ``modules``
    stay at ``~/.cache/huggingface`` untouched — only the heavy caches move.

    Ordering: ``HF_HUB_CACHE`` is frozen into ``huggingface_hub.constants`` at
    IMPORT time (same constraint as the #745 flags above), so this must run
    before the process's first ``import huggingface_hub`` — importing THIS
    module pulls no huggingface_hub (verified #1369), so any entrypoint that
    calls load_dotenv() first gets the constant right. ``HF_XET_CACHE`` is
    read by the compiled hf_xet crate from the PROCESS ENV at transfer time
    (hf_xet 1.4.3, xet_runtime configuration_utils fallback chain
    HF_XET_CACHE -> HF_HOME/xet -> XDG_CACHE_HOME), so it escapes the freeze.

    Residual (named, accepted): a FUTURE raw-cron python entrypoint that
    imports huggingface_hub at module top WITHOUT load_dotenv() gets neither
    the profile export (cron reads no profile) nor this setdefault in time —
    zero such consumers exist today (#1369 fact-check); new cron authors:
    call load_dotenv() first or export the keys in the wrapper.

    setdefault-only — an explicit launch-time value always wins.
    ``EPS_VM_HF_CACHE_REDIRECT=0`` (or false/no/off) disables. Fails OPEN off
    the shared VM: pods (/workspace/.cache/huggingface), GCE, SLURM, and
    laptops keep their lane defaults (see :func:`_hf_home_default`).
    """
    if not is_shared_vm_env():
        return
    if not os.path.ismount(_SHARED_VM_DATA_DISK):
        # Hostname-only detection with the data disk detached: redirecting
        # would mkdir-on-demand a plain dir on / UNDER the mountpoint —
        # worse than today's default. Mirrors the shell blocks' [ -d ] guard.
        return
    knob = os.environ.get("EPS_VM_HF_CACHE_REDIRECT", "")
    if knob.strip().lower() in ("0", "false", "no", "off"):
        return
    cache_root = Path(_SHARED_VM_DATA_DISK) / Path.home().name / "huggingface-cache"
    os.environ.setdefault("HF_HUB_CACHE", str(cache_root / "hub"))
    os.environ.setdefault("HF_XET_CACHE", str(cache_root / "xet"))
```

### 4.2 `scripts/cron_autonomous_session_watch.sh` — guarded exports

The watcher's hf-hub-ttl eviction pass reads `HF_HUB_CACHE`/`HF_HOME` from env at call time (`autonomous_session_watch.py:7790-7791`) and `autonomous_session_watch.py` never calls `load_dotenv()` (verified by grep) — under cron's minimal env the pass would keep scanning the ORPHANED old cache instead of the live one. Insert immediately before the wrapper's `uv run python scripts/autonomous_session_watch.py` invocation:

```bash
# Shared-VM HF cache redirect (#1369): the hf-hub-ttl eviction pass reads
# HF_HUB_CACHE from env (autonomous_session_watch.py has no load_dotenv) —
# point it at the LIVE data-disk cache so eviction manages the cache new
# work actually writes to. Guarded on the dir so non-VM checkouts no-op.
_eps_hf_cache_root="/mnt/eps-data/$(id -un)/huggingface-cache"
if [ -d "$_eps_hf_cache_root" ]; then
  export HF_HUB_CACHE="${HF_HUB_CACHE:-$_eps_hf_cache_root/hub}"
  export HF_XET_CACHE="${HF_XET_CACHE:-$_eps_hf_cache_root/xet}"
fi
```

Other cron wrappers considered and NOT touched (scope-minimal): `cron_vm_disk_guard.sh` — `vm_disk_guard.py`'s HF surface is the pod-style `/workspace/.cache/huggingface` tier (d) plus issue-keyed caches, and its line-693 `HF_HOME` read is a defensive guard that is unaffected since we do not set `HF_HOME`; every other `cron_*.sh` invokes python entrypoints whose HF work goes through `load_dotenv()` in-process.

### 4.3 VM shell profile — ops step (outside git; documented in the implementer report + an `epm:progress` marker)

Append the SAME guarded block (idempotent — grep for the marker comment `# EPS shared-VM HF cache redirect (#1369)` before appending) to BOTH:

- `~/.profile` — read by login shells; the Claude Code Bash tool initializes from the user's profile, so this covers every session's Bash calls, detached `setsid nohup env ...` launches (they inherit the orchestrator shell env), ad-hoc `hf` CLI use, and — critically — launches from ISSUE WORKTREES whose branch-pinned `env.py` predates this fix (the #891/#779 staleness gap that made the #847 caps require inline prefixes).
- top of `~/.bashrc`, BEFORE the interactive-shell early-return guard — covers interactive non-login shells (tmux panes etc.).

```bash
# EPS shared-VM HF cache redirect (#1369) — heavy HF caches on the data disk.
if [ -d "/mnt/eps-data/$(id -un)/huggingface-cache" ]; then
  export HF_HUB_CACHE="${HF_HUB_CACHE:-/mnt/eps-data/$(id -un)/huggingface-cache/hub}"
```

`${VAR:-...}` semantics preserve any pre-set value (setdefault parity). The dir-existence guard makes the block a no-op if the data disk is ever detached (fail-open, mirrors `is_shared_vm_env`'s ismount clause).

## 11. Decision Rationale

**D1 — Keys: `HF_HUB_CACHE` + `HF_XET_CACHE`, NOT `HF_HOME` (and not `HF_HOME` alone).**
- **What:** setdefault the two heavy-cache keys individually; leave `HF_HOME` at `~/.cache/huggingface`.
- **Why:** `HF_HOME` redirect would also relocate (a) the token file — `~/.cache/huggingface/token` EXISTS (37 bytes, verified `ls`) and is load-bearing for any process without `HF_TOKEN` in env (shell `hf` CLI, ad-hoc calls; `.env` does carry `HF_TOKEN`, but not every process loads `.env`); (b) `stored_tokens`; (c) the `datasets` processed cache (3.7 GB, verified `du`) and `modules` — all of which would go cold or need a migration step. The disk pressure is entirely hub (97 GB) + xet (transient ~11 GB); redirecting exactly those two keys moves 100% of the problem with zero migration. It also exactly matches the existing data-disk cache layout (`{hub,xet}` — verified `ls`) and avoids any interaction with `_hf_home_default()`'s documented three-way branch (constraint: byte-untouched).
- **Source:** code reading — `huggingface_hub` 0.36.2 `constants.py:130/148/293` (HF_HUB_CACHE and HF_XET_CACHE both default-derive from HF_HOME when unset, so setting the two children is strictly narrower than setting the parent); clarifier disk audit; `ls`/`du` probes this session.
- **Alternatives:** `HF_HOME` alone (rejected: token/datasets blast radius, migration step); `HF_XET_CACHE` alone (rejected: leaves the 97 GB-class hub growth on `/` — the larger half of the incident).

**D2 — Target path: the EXISTING `/mnt/eps-data/<user>/huggingface-cache/{hub,xet}`, derived as `Path(_SHARED_VM_DATA_DISK) / Path.home().name / "huggingface-cache"`.**
- **What:** reuse the user-owned, already-populated cache root.
- **Why:** it holds 186 GB of warm cache including the project data-repo dataset cache (the very prefix-staging cache the #1073 incident ballooned), is user-writable (verified mode), and needs no sudo. The root-owned `/mnt/eps-data/hf_cache` would need `chown` (verified `drwxr-xr-x root:root`); a fresh dir would discard 186 GB of warm cache. The `Path.home().name` derivation avoids a hardcoded username while remaining trivially correct on this single-user VM; the shell blocks use `$(id -un)` for the same reason.
- **Source:** clarifier context + `ls -la` verification this session; #681 (data disk is the designated heavy-footprint home).
- **Alternatives:** `/mnt/eps-data/hf_cache` (rejected: root-owned, sudo churn); fresh dir (rejected: cold cache); hardcoded username string (rejected: gratuitous, trivially avoidable).

**D3 — Old 97 GB `/` hub cache: leave in place, orphaned; reclaim is a surfaced follow-up, not part of this task.**
- **What:** no move, no delete, no new sweeper.
- **Why:** a move does not fit (97 GB > 56 GB free on the target); deletion is destructive and therefore user-only ("ask before deleting", CLAUDE.md hard rule); the cache is re-downloadable by construction so an eventual `rm -rf ~/.cache/huggingface/hub` (user-approved, after ~1 week of confirmed redirect) recovers ~97 GB with zero data loss. Pointing the watcher/vm_disk_guard at the orphan would be new reclaim machinery — explicitly out of scope for a workflow-fix.
- **Source:** `df -h` this session (27 GB free on `/`, 56 GB on data disk); #679/#681 recovery doctrine (never auto-delete active data; resize/raise-cap first).
- **Alternatives:** partial model move (rejected: ops complexity ≈ re-download cost, and `mv` across filesystems is copy+delete anyway); extending vm_disk_guard (rejected: scope creep, reviewers would flag it).

**D4 — Data-disk headroom risk accepted with existing mitigations only.**
- **What:** redirect all future HF writes to a disk at 89% (56 GB free); no new machinery.
- **Why:** the mitigation stack already exists — the data-disk pass of `vm_disk_guard` is escalate-only by design, the watcher sub-floor sentinel fires at 85% (size-invariant percent, #679), the hf-hub-ttl eviction now manages the live cache (§4.2), and #681's documented recovery is a GCP live-resize. Building more here duplicates that stack.
- **Source:** #679/#681 (guard + sentinel + resize doctrine); `df` probe.
- **Alternatives:** pre-emptive disk resize in this task (rejected: separate ops decision, costs money, user-facing); refusing the redirect until resize (rejected: leaves `/` failing NOW at 95% — the incident recurs this week).

**D5 — Placement: env.py setdefault (both call sites) + watcher cron wrapper + `~/.profile` and top-of-`~/.bashrc`; NO other cron wrappers, NO pod/GCE/SLURM surfaces.**
- **What:** three placement layers, each with a distinct consumer class: in-process (all load_dotenv entrypoints, incl. every cron python entrypoint), cron wrapper (the one python consumer with no load_dotenv — the watcher's hf-hub-ttl pass, which reads env at call time), shell profile (worktree launches with branch-pinned stale `env.py`, detached `setsid` launches inheriting the session env, `hf` CLI, grandfathered no-dotenv scripts).
- **Why:** mirrors #745's "shell-level is load-bearing for import-frozen keys" placement rationale, adapted to VM scope. The profile export is genuinely load-bearing, not optional: the Bash tool initializes from the user's profile, and a fresh-shell probe confirmed all three HF vars are currently unset (`bash -lc` probe this session), so the export is both new and effective. `~/.bashrc` needs the block at TOP because Ubuntu's interactive guard early-returns in non-interactive shells.
- **Source:** #745 comment block (env.py:304-315); #847 placement; #891/#779 worktree-staleness lesson (code-style.md thread-caps bullet); `autonomous_session_watch.py:7786-7796` read + no-load_dotenv grep; fresh-shell probe.
- **Alternatives:** exports in ALL cron wrappers (rejected: churn — their python entrypoints call load_dotenv; only the watcher reads HF env without it); crontab-level env lines (rejected: crontab is outside the repo AND outside the implementer report's natural ops surface; wrapper-level is reviewable in git).

**D6 — Ordering: env.py setdefault suffices in-process for BOTH keys given the load_dotenv-first convention; verified, not assumed.**
- **What:** rely on `load_dotenv()`-before-`huggingface_hub`-import for the import-frozen `HF_HUB_CACHE`; rely on the Rust env read for `HF_XET_CACHE`.
- **Why (verified this session):** (a) `HF_HUB_CACHE` is frozen at `constants.py:148` (`os.getenv` at module import) — but `from explore_persona_space.orchestrate.env import load_dotenv` pulls NO `huggingface_hub` (subprocess probe: `hf_hub loaded at env-import time: False`), so any entrypoint following the repo convention gets the constant right; the E2E probe (`load_dotenv()` then `import huggingface_hub.constants`) confirmed constants reflect the env state set before import. (b) `HF_XET_CACHE` has NO Python consumer outside `constants.py` in 0.36.2 (repo-wide grep of the installed package: zero hits) — the compiled `hf_xet` 1.4.3 crate reads `HF_XET_CACHE` / `HF_HOME` / `XDG_CACHE_HOME` from the process env itself (strings probe of the `.so`: all three present in `xet_runtime .../configuration_utils.rs`), i.e. at transfer-config time, after `load_dotenv()` has run in every entrypoint. So the xet half escapes the import freeze entirely — same mechanism as `HF_XET_HIGH_PERFORMANCE` (the existing env.py comment).
- **Source:** installed-source reading + three live probes (§12 A2-A5); #745 comment block.
- **Alternatives:** demanding a shell-only solution because of the freeze (rejected: the freeze is escapable in-process for convention-following entrypoints — verified — and shell-level is layered on anyway); adding `huggingface_hub` to `HEAVY_IMPORT_ROOTS` (rejected: would flag the `orchestrate/hub.py` import chain and dozens of legitimate files; the existing transformers/vllm/datasets/peft/trl roots already transitively cover the heavy consumers).

**D7 — Kill switch `EPS_VM_HF_CACHE_REDIRECT=0`.**
- **What:** dedicated per-feature disable, in addition to setdefault semantics and `EPS_SHARED_VM=0`.
- **Why:** if the data disk wedges (full/detached), ops needs to disable THIS feature without also killing the #847 thread caps (`EPS_SHARED_VM=0` disables both).
- **Source:** #847's `EPS_VM_THREAD_CAP` disable-knob precedent.
- **Alternatives:** no knob (rejected: revert-under-pressure would require a code change while the disk is wedged).

## Kill criteria (what would make this change wrong)
