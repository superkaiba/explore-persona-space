## 11. Decision rationale

N/A — no model training (no hyperparameters in this task type).

- **Note mechanism = structured `epm:progress` with a fixed leading token, NOT a new marker kind.** *Why:* the task constraint bans a new kind; the repo has two live precedents for exactly this shape. *Source:* `research-pm.md:725-735` ("Structured `epm:progress` note, NOT a new marker kind") + SKILL.md's own stage-dispatch breadcrumb. *Alternatives:* a new `epm:followup-parked-by-cap` kind (rejected — marker-schema change = architectural greenlight, and workflow.yaml registration + emit-tables churn for zero extra visibility); a body-frontmatter tag (rejected — same invisibility class as the body bullet).
- **Token `followup-parked-by-cap`.** *Why:* fresh repo-wide (0 grep hits → no false positives for future greps), hyphenated like `deliberate-stop`/`stage-dispatch`, self-describing. *Alternatives:* `[followup-parked-by-cap]` bracketed prefix (rejected — no bracket precedent in the note-token family); `parked-by-cap` (rejected — less specific, could collide with future park classes).
- **One note per parked follow-up, keyed on verbatim `followup_ref=`, vs one aggregated note.** *Why:* per-title keying mirrors the run marker's existing match-by-verbatim-title idempotency and survives the union changing across re-entries (an aggregated note can't be idempotently extended). *Source:* SKILL.md:6366-6368 (run-marker idempotency). Typical union size is 1-3 — no spam risk.
- **Two firing moments (re-entry exit + post-run surplus).** *Why:* covering only re-entry (the literal #958 shape) leaves the first-entry surplus invisible until a re-entry happens to fire — same bug, different schedule. Posting the surplus AFTER the run marker keeps `cap_consumed_by` factual and avoids posting for a run that then aborts into a different surface.
- **No PM read-side edit (research-pm.md left untouched).** *Why:* minimal mechanism that actually surfaces — the note lands on the events timeline the promotion review reads, and the token is one-grep discoverable; `pm_queue_report.py` doesn't render note text, so a read-duty line would add prose without a rendering path. The clarifier delegated exactly this call; documented here so the critic sees it was weighed. *Alternative:* a one-line PM grep duty (viable later if parked follow-ups still slip — a future candidate, logged not auto-filed per the recursion guard).
- **v2 pointer clause (Edit 4) included.** *Why:* the brief's consistency mandate — v2's zero-GPU floor states the same cap and already delegates the inline-lint mechanics to v1 Step 9a-ter by pointer; without the clause, v2 sessions would never post the note. One clause, no v2 cap change.
- **Pin = new dedicated test file.** *Why:* no existing test pins the 9a-ter LOOP-GUARD span (`tests/test_issue_skill_inline_gate_pin.py` pins the separate 9a-ter § Inline payload lint gate sub-span only); the defer-repark pin (#1321) is the established template for exactly this three-surface shape. *Alternative:* extending `test_issue_skill_marker_contract.py` (rejected — that file pins Step 4b label contracts, wrong home).
