## Requirement + acceptance criteria

The v2 report template (`.claude/skills/issue-v2/report-template.md` § The
detailed companion writeup) requires that the companion at
`docs/reports/issue_<N>_detailed.md` (a) carries NO Thomas slots — no `## TLDR`,
no `**Takeaways**` blocks, no `## Conclusion and next steps` (the doc is
regenerated wholesale on follow-up rounds, so anything hand-written there is
destroyed without notice) — and (b) obeys the interpretivity rule throughout,
with the banned-lexicon scope mirroring the body's (the Motivation copy keeps
the body's hypothesis-framing exemption). Nothing mechanically enforces either
half today: `verify_report.py`'s checks all run on the report BODY only, and
the #2162 round-1 `report-verifier` had to scan the companion by hand.

**Acceptance criteria:**

1. `verify_report.py` gains ONE new check, `companion-content`, that resolves
   the body's `**Detailed writeup:**` pin, materializes the companion at that
   SHA via read-only local git (`git show <sha>:docs/reports/issue_<N>_detailed.md`
   through the existing `_git()` helper — no network), and runs BOTH halves:
   - **Structural half (FAIL posture, both modes when materialized):** the
     forbidden headings are absent — no line whose `_norm_header()` equals
     `## TLDR` or `## Conclusion and next steps` (the alias map catches the
     grandfathered `## Next steps` form), and no `_is_bold_label(line,
     "Takeaways")` line. Scan runs on the `blank_verbatim()`-blanked companion
     (a fenced example containing `## TLDR` is data, not a slot).
   - **Lexicon half (WARN posture, never FAIL):** the existing `_LEXICON_RE`
     over every blanked companion line OUTSIDE the companion's `## Motivation`
     section (the Motivation copy keeps the body's hypothesis-framing
     exemption; the exemption is EXACT-header-only — see § Design decisions).
     Hits are listed with companion line numbers, mirroring `check_lexicon`'s
     `L<n>: '<lexeme>'` detail shape.
2. Resolution degrade ladder mirrors `image-pin-blob-identity`'s mode split
   (the precedent the task body names) — see § Design decisions for the exact
   rungs.
3. No existing check is weakened; all existing checks unchanged; the shared
   `BANNED_LEXICON` list is NOT extended (see § Known limitation).
4. The module docstring's check inventory gains the `companion-content` entry.
5. Tests cover every ladder rung + both halves (see § Tests); the full
   existing `tests/test_verify_report.py` suite passes after the fixture
   updates the new check forces (see § Test-fixture fallout).

## Method delta (vs the existing code)

Everything reuses existing plumbing; the ONLY new code is the resolver + the
two scan halves:

- Pin extraction: `_DETAILED_LINE_RE` + `_DETAILED_URL_RE` (already parse the
  line, the 40-hex SHA, and the issue number).
- Materialization: `_git(figures_root, "show", f"{sha}:{path}")` — same
  read-only local-git philosophy as `_check_pin_blob_identity`; `cat-file -e
  <sha>^{{commit}}` first to distinguish "commit unresolvable" from "commit
  present, path absent".
- Verbatim blanking: `blank_verbatim()` on the companion's lines.
- Section spans: `parse_sections()` on the blanked companion lines to locate
  the `## Motivation` span (exempt); every other line is scanned (including
  pre-section prose and the `## Methodology (full)` / `## Results — full
  figure set` / `## Extra tables / diagnostics` sections).
- Lexicon: the module-level `BANNED_LEXICON` / `_LEXICON_RE` — one list, no
  fork (a body-lexicon change automatically propagates to the companion scan).

## Design decisions (the task body's one judgment call, resolved)

**Decision: lexicon hits in the companion are WARN, never FAIL; forbidden
headings are FAIL.** Rationale: the companion's methodology/deviations prose
legitimately uses process-sense phrasings that DO match the exact lexemes —
"the artifact confirms the count", "implying one fused forward", "evidence
that the run completed" are honest process-facts, not asserted conclusions —
so a FAIL posture gets routed around, which is worse than a WARN that gets
read (the task body's own guidance). Process-sense carve-outs (the alternative
the body floats) require natural-language sense disambiguation inside a
mechanical gate — fragile and unauditable. The structural half has no such
false-positive channel (after verbatim blanking, a `## TLDR` in the companion
is unambiguously a Thomas slot), so it keeps the hard-FAIL posture the
template's "no Thomas slots" rule implies.

**Known limitation (recorded, deliberate):** `BANNED_LEXICON` is an
exact-lexeme list — inflectional variants ("confirmed", "implies",
"suggested") do not match `_LEXICON_RE`. The 3 hits the #2162 round-1
report-verifier caught by hand ("each confirmed from artifacts", "the dispatch
log confirmed num_workers=4", "the plan's phrasing implies one fused forward")
are exactly such variants and are OUTSIDE this mechanical scan's reach.
Extending the lexicon (inflections/stemming) would change the existing BODY
scan too — a shared-instrument scope change deliberately out of this task's
scope (must-ask; a possible sibling task). The report-verifier agent's manual
interpretivity read remains the catching arm for inflected phrasings and for
blockquoted caption prose (blanked as DATA by the body's own convention).

**Motivation exemption is exact-header-only (deliberate):** realized
companions carry appended follow-up sections (`## Motivation (round)`,
`## Methodology (round, unabridged)` — live #2162 shape). `_norm_header()`
does not map `## Motivation (round)` to `## Motivation`, so round-Motivation
copies ARE lexicon-scanned. That is acceptable (WARN-only posture — no FAIL
channel) and deliberate; the implementer records it in the check's docstring
rather than widening the exemption.

**Resolution degrade ladder** (single `companion-content` CheckResult;
aggregation mirrors `_check_pin_blob_identity`: any fail → FAIL, else any
warn → WARN, else PASS):

| State | generation | promote |
|---|---|---|
| No `**Detailed writeup:**` line in body | PASS-note N/A (missing line already FAILs `detailed-writeup-link` at generation / WARNs at promote — no double-report) | same |
| Line present but URL malformed / >1 line | PASS-note N/A (deferred to `detailed-writeup-link`, which FAILs) | same |
| `figures_root` not a git checkout | WARN "unverifiable" | same |
| Pinned commit unresolvable (`cat-file -e` fails) | **FAIL** (the pin was just created locally at assembly; unresolvable = fabricated SHA) | WARN (fresh-clone / unfetched shape) |
| Commit resolves, companion path absent at it | **FAIL** | **FAIL** |
| Materialized: forbidden heading present | **FAIL** | **FAIL** |
| Materialized: lexicon hit outside Motivation | WARN (hit list in detail) | WARN |
| Materialized, clean | PASS | PASS |

The generation-FAIL on an unresolvable pin is justified by the actual
pipeline sequencing: the orchestrator commits + pushes the companion and
splices the pin BEFORE the generation-mode verify runs, so at generation the
pin commit exists in the local object DB by construction.

Promote mode still scans when the pin resolves (unlike the body's
`LEXICON_SECTIONS_BY_MODE` narrowing at promote): the companion NEVER carries
Thomas prose — it is 100% agent-written in both modes — so there is no
Thomas-voice section to exempt and the scan scope is mode-invariant. Only the
RESOLUTION rungs are mode-split.
