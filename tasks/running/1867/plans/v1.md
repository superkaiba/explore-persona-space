# Plan v1 — #1867 daily-fix: `task.py address-concern` accepts `--note` alias

## Plan Summary

Make the recurring flag-convention slip fail soft: add `--note` as an accepted
argparse alias of `--summary` (dest=`summary`) on the concern subcommands of
`scripts/task.py`, keep `--summary` canonical in docs, update the stale
CLAUDE.md doc line, and pin the alias with parser-level tests. Purely additive
CLI ergonomics; no library-layer, marker-schema, or subcommand-contract change.

architectural: false

## Requirement + acceptance criteria

Two sessions on consecutive days (2026-07-28, 2026-07-29) ran
`task.py address-concern ... --note '...'` and got argparse exit 2: every other
note-bearing subcommand (`post-marker`, `set-status`) uses `--note`, while
`address-concern` takes `--summary` (with `--rationale` already an accepted
alias). A CLAUDE.md doc line alone did not prevent the second miss — the fix is
CLI-convention consistency.

Acceptance criteria:

1. `uv run python scripts/task.py address-concern <N> --concern-id <id> --by <who> --round <k> --note "..."`
   parses successfully; the value lands in dest=`summary` and flows through the
   existing truncation + `address_concern(...)` path unchanged.
2. `--summary` and `--rationale` on `address-concern` keep working byte-identically
   (no behavior change for existing callers; dest stays `summary`).
3. `raise-concern` accepts `--note` as an alias of its required `--summary`
   (same convention slip, identical one-line-summary semantics; providing any
   one of `--summary`/`--note` satisfies the required argument).
4. `defer-concern` is deliberately NOT touched: its `--rationale` carries
   distinct user-only semantics (≥40 chars, boilerplate rejection) — adding a
   `--note` alias there would blur a deliberate friction surface.
5. CLAUDE.md Task Workflow API line (currently: "the summary flag is
   `--summary`, NOT `--note` (argparse exit 2; 2026-07-28/29)") is updated to:
   `--summary` is canonical; `--note` / `--rationale` are accepted aliases
   (#1867). The `--by`/`--round` REQUIRED note stays.
6. The `scripts/task.py` usage docstring rows for `raise-concern` /
   `address-concern` mention the alias in one short bracket; the argparse
   `help=` strings for both `--summary` arguments name the alias set and state
   `--summary` is canonical.
7. New parser-level tests pin the alias (see §Tests); all existing concern-CLI
   tests keep passing.
8. `ruff check` / `ruff format --check` clean on touched files.

## Tests (TDD: no)

Existing concern-CLI tests invoke handler functions with pre-built
`argparse.Namespace` objects, so they cannot pin the parser surface. New tests
exercise the REAL parser via `task_cli.main()` with `sys.argv` monkeypatched
and the module-level library function monkeypatched to capture kwargs (no repo
state touched, no subprocess — consistent with `_import_task_cli()` rationale):

- `test_cli_address_concern_accepts_note_alias`: monkeypatch
  `task_cli.address_concern` to capture kwargs; argv = `["task.py",
  "address-concern", "1", "--concern-id", "x", "--by", "implementer",
  "--round", "1", "--note", "fixed by rekeying"]`; call `task_cli.main()`;
  assert captured `summary == "fixed by rekeying"`.
- `test_cli_raise_concern_accepts_note_alias`: same shape with
  `task_cli.raise_concern` and `--severity CONCERN --note "..."`; assert
  captured `summary` value.

Implementer may adjust naming/placement; the parser-through-`main()` mechanism
is the load-bearing part.
