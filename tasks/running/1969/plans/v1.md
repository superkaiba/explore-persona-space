# Plan v1 — #1969: SLURM monitor `stalled` grace — log-freshness veto + consecutive-tick streak + transport-degraded skip

## Goal + acceptance criteria

**Goal (from task body):** Make the SLURM monitor's `stalled` classification reliable for just-launched fellows-lane jobs so the orchestrator does not have to manually ssh-verify every early stall read.

**Acceptance criteria:**
1. A tick where the heartbeat is stale but `job.out` is fresh (< `STALL_SEC`) NEVER reports `stalled` (the exact #1900 false class — all 3 recorded false reads had heartbeat 397–517 s stale with fresh INFO log lines).
2. A single stall-condition tick NEVER reports `stalled`; ≥2 consecutive stall-condition ticks are required (one poll tick is 540 s > `STALL_SEC` = 300 s, so ONE silently-failed rsync ages both local artifacts past the threshold — a one-tick transient must not kill the run's orchestration).
3. A tick whose rsync failed with a TRANSPORT-class error does not evaluate staleness at all (the local copies are known-stale-by-transport, not evidence about the job).
4. Genuinely-dead detection is not delayed beyond the documented weakening: SLURM dead-class states and the `[phase=preflight-failed]` shortcut are untouched; a job writing nothing anywhere still reads `stalled`, delayed by exactly one extra tick (streak=2).
5. A `stalled` verdict carries a machine-readable `stall_reason` that `scripts/failure_classifier.py` routes `infra` (Step 7 table), and the module docstring's "Stall semantics" section matches the new predicate.

## Root cause (pinned from recorded evidence — resolves the body's "unverified hypothesis")

Task #1900 `epm:cluster-poll` markers (2026-07-31): the three false reads (jobs 16055, 16092, and the 16045-class reads the session called false) show `heartbeat_sec_ago` 397–517 s while the captured `log_tail_excerpt` carries log lines written seconds-to-minutes before the tick — the jobs were demonstrably alive by their own logs. Current predicate (`slurm_monitor.py:665-666`) consults ONLY the heartbeat:

```python
if base_status == "running" and heartbeat_sec_ago > STALL_SEC and slurm_status != "PENDING":
    base_status = "stalled"
```

Three degradation paths make the heartbeat signal alone unreliable:
- `rsync_status_and_log` (slurm_monitor.py:1233) is non-fatal + DEBUG-logged on failure; one failed tick leaves the previous local copy whose (rsync `-a`-preserved) mtime/heartbeat then reads ≥ 540 s stale at the next tick — instant false stall, invisible to the monitor.
- The heartbeat writer competes with cluster FS lag / phase-writer interleaving (partially addressed by #1836); a delayed heartbeat write with a healthy workload reads stale.
- `heartbeat_sec_ago = 10**9` on missing/blanked status.json is floored only by RUN age; a job > 300 s into its run with a missing heartbeat reads stalled on one tick.

`PollResult`'s own contract (`backends/base.py:439`) already defines `stalled` as "alive but no **log** progress AND idle GPUs for >STALL_SEC" — the SLURM lane's heartbeat-only predicate is weaker than the documented contract. The fix aligns it.

## Method delta

Three composable defenses in `src/explore_persona_space/backends/slurm_monitor.py` (no behavior change on any other lane):

1. **Log-freshness veto (primary, mechanism-matched).** `stalled` requires BOTH signals stale: `heartbeat_sec_ago > STALL_SEC` AND `log_mtime_sec_ago > STALL_SEC`. `log_mtime_sec_ago` is already computed by `_read_job_out` and already attempt-freshness-gated (blanked to `10**9` for prior-attempt artifacts), so a missing/blanked log stays stale ⇒ the documented nothing-writing weakening is preserved. Apply the same C2 run-age floor to the log value (`min(log_mtime_sec_ago, run_age)`) for symmetry with the heartbeat floor.
2. **Consecutive-tick streak (N=2), persisted per job.** A small JSON state file `_local_state_dir(job_id)/stall_streak.json` (`{"streak": int, "updated_ts": float}`) — same volatility class as the rsync'd artifacts already living there. Tick where the post-veto stall condition holds → `streak += 1`; report `stalled` only when `streak >= 2`; first tick reports `running` with `stall_reason="slurm_stall_suspect"` and passes `lane_anomaly=True` into `recommend_lane_next_interval` (slurm_monitor.py:733) so a suspect tick never emits the 1800 s quiet interval. Any tick where the condition does NOT hold → streak reset to 0. `/tmp` wipe (VM reboot) resets the streak — fails toward `running` for one extra tick, acceptable.
3. **Transport-degraded skip.** `rsync_status_and_log` returns a per-tick verdict instead of `None`: `True` = all pulls OK or source-missing (rsync rc 23/24 — the file genuinely doesn't exist remotely: NORMAL evaluation, weakening preserved); `False` = transport-class failure (rc 255/30/35, or `subprocess.TimeoutExpired`, which today would crash the tick — catch it). On `False` the monitor SKIPS stall evaluation for this tick entirely (status stays per SLURM state; streak neither incremented nor reset; the cluster-poll note records `transport_degraded=true`). A persistently-unreachable cluster is a different failure class already surfaced by the `state_querier` ssh failing → UNKNOWN path. Monitor-side check is `ret is False` (a legacy/stub seam returning `None` evaluates normally) so existing `rsyncer=` test stubs stay valid.

**stall_reason threading:** a `stalled` verdict sets `PollResult.stall_reason = "slurm_heartbeat_and_log_stale"`; add it to `failure_classifier.STALL_REASON_INFRA` (a genuine SLURM stall routes `infra` → experimenter respawn, per the Step 7 table — a silent hang's log tail carries no infra regex pattern, the exact reason that set exists). Update the `stall_reason` field comment in `backends/base.py` (currently "None on a healthy running tick"; the suspect tick sets it while `status="running"`). The `epm:cluster-poll` note payload gains `stall_streak` + `transport_degraded` keys (additive; `_maybe_post_cluster_poll` already carries `heartbeat_sec_ago`).
