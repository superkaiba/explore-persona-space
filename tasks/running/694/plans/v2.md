## 1. Goal

Add a **results-driven literature-positioning step** to the post-results
`/issue` workflow. Today the project's only literature grounding is
*front-loaded* — the planner's §11 hyperparameter grounding and the
clarifier's lit review are keyed on the experiment's **question and
recipe**, run *before* results exist. After results land, **no agent**
searches the literature for work matching what the experiment actually
**found** ("we measured X — who else reported X, and does it
replicate / contradict / extend ours?"). The arXiv-MCP machinery is wired
(`.claude/rules/arxiv-mcp.md`) but only invoked at plan time.

This plan closes that gap with a new fresh-context agent
`related-work-finder`, spawned in the existing Step 10b/10c post-completion
batch, that runs a bounded findings-keyed search and **proposes** a verified
"Related findings" positioning note for the clean-result `## Goal` →
`**Broader narrative:**` slot, gated for user review, non-blocking, 0 GPU-h.

draft; and the propose-don't-apply contract matches the Step 10
living-docs gate exactly. Spawning at Step 9a would (a) search on a
not-yet-final interpretation and (b) entangle a generative search inside
the analyzer↔critic loop.

dispatch). The precise site is **SKILL.md Step 10b § "Parallel spawn with

`living-docs-updater` in ONE message", with the join at lines 6039-6040
("before entering Step 10d"). Add a THIRD `Agent` call there, in the SAME

### 4.2 The agent's I/O contract (`related-work-finder.md`)

Frontmatter (mirrors `living-docs-updater.md`):
```yaml
name: related-work-finder
description: >
  Reads a freshly-completed experiment's clean-result FINDINGS and runs a
  bounded, findings-keyed arXiv-MCP + web literature search to position the
  result against existing published work (replicates / contradicts /
  extends / no-prior-report-found). PROPOSES (never applies) a short,
  MCP-verified "Related findings" note for the clean-result ## Goal →
  **Broader narrative:** slot, plus an optional human-triage list of
  candidate papers for docs/papers.md (NOT auto-applied in v1). Spawned by
  /issue at Step 10b-bis CONCURRENTLY with follow-up-proposer +
  living-docs-updater (one message, independent outputs; all join before
  the Step 10d worktree merge). Writes exactly ONE artifact and returns a
  rationale; the orchestrator presents it at the related_work_positioning
  gate for user confirmation. It NEVER edits live docs/body and NEVER runs git.
model: "claude-opus-4-8[1m]"
effort: high
tools:
  - Read
  - Grep
  - Glob
  - Bash
  - mcp__arxiv__search_papers
  - mcp__arxiv__semantic_search
  - mcp__arxiv__get_abstract
  - mcp__arxiv__read_paper
  - WebSearch
```

**MCP-tool loading (v2: declared frontmatter `tools:` is the PRIMARY
mechanism, not a fallback).** The `mcp__arxiv__*` + `WebSearch` tools are
declared directly in the agent frontmatter `tools:` list above — this is
the agent's PRIMARY (and only required) tool-access mechanism; the
subagent receives these tools at spawn, exactly as `experimenter` receives
its declared SSH/MCP tools. The deferred-`ToolSearch` path is REMOVED from
the design entirely (it was an unnecessary indirection — a subagent does
not need to discover tools its own frontmatter already grants). The agent
has NO `Edit`/`Write` to live docs/body; it writes its one artifact via
`Bash` heredoc, like `living-docs-updater`.

Named sections the implementer authors (sketch only — implementer writes
the full body):
1. **`# Related-Work Finder`** + the "You PROPOSE, you do NOT apply"
   non-negotiable banner (copied from `living-docs-updater.md` lines 36-46).
2. **`## Inputs`** — spawned with source task `N`. Reads in order:
   (a) the clean-result body via `task.py view <N>` — primary signal is
   `## Takeaways` bullets + each `### <result>` interpretation prose + the
   H1 confidence tag (what was found + how strongly); (b) `docs/papers.md`
   (skim — to NOT re-surface an already-logged paper); (c) the two pinned
   sibling papers as the baseline positioning anchors.
3. **`## Step 1 — Extract the searchable findings`** — distill 1-3
   FINDINGS-keyed search phrases from the result (NOT the Goal / recipe):
   e.g. "contrastive negatives reduce persona-localized behavior leakage in
   LoRA fine-tuning", NOT "Qwen-2.5-7B LoRA r=16". Write each phrase down.
4. **`## Step 2 — Bounded findings-keyed search`** — the search budget +
   the MCP/web call protocol (§4.3).
5. **`## Step 3 — Verify every citation IN THE SAME TURN`** — the
   citation-verification mechanism (§4.4). Drop any paper that does not
   resolve.
6. **`## Step 4 — Classify the positioning`** — for each verified paper,
   label `replicates | contradicts | extends | tangential`. If zero
   verified papers bear on the finding, the output is the explicit
   **"No prior report located"** block (§4.5).
7. **`## Step 5 — Draft the proposal`** — the `**Broader narrative:**`
   addition (≤80 words, §4.6) + the optional **Suggested for docs/papers.md
   (manual triage)** list (§4.5/§4.7 — a human-triage list, NOT an apply
   diff in v1).
8. **`## Step 6 — Write the artifact + return the rationale`** — the ONE
   file + the structured return (§4.7).
9. **`## Output contract`**, **`## Anti-patterns`**, **`## Path discipline`**
   — copied/adapted from `living-docs-updater.md` (the path-discipline +
   no-git + one-artifact rules are identical).

### 4.3 Search budget (the bounded-cost contract — HARD)

Per invocation, the agent may make AT MOST:
- **≤6 arXiv-MCP calls total** (any mix of `search_papers` /
  `semantic_search` / `get_abstract` / `read_paper`), AND
- **≤2 `WebSearch` calls**, AND
- inspects **≤3 results per query** (reads abstract, not full text, unless
  one paper is a clear hit worth one `read_paper`).

The agent counts its calls and STOPS at the budget, reporting partial
results rather than crawling. Rationale + grounding in §11 R3. The agent
states the realized call count in its return so the cap is auditable.

### 4.4 Citation-verification mechanism (zero fabrication — HARD)

This mirrors the analyzer's numeric/verbatim-fidelity rule (analyzer.md
lines 291/293) and follow-up-proposer's Hub-verify-in-same-turn rule
(follow-up-proposer.md lines 96-167):

> **Every cited paper MUST be resolved via the arXiv MCP in the SAME turn
> it is written into the proposal.** Concretely: before the agent writes
> `arXiv:XXXX.XXXXX` + a title into the proposal, it must have called
> `mcp__arxiv__get_abstract` (or `search_papers` / `read_paper`) on that
> exact id IN THE CURRENT TURN and confirmed the returned title + authors
> match what it is about to write. A paper the MCP does not resolve (id
> typo, hallucinated id, MCP returns nothing) is DROPPED — never written
> with a "[unverified]" hedge, never paraphrased into existence. No
> invented titles, no "as shown in [X]" without a resolved id. The agent
> records, per cited paper, the verification call it made.

On MCP failure / timeout (the whole MCP is down): the agent does NOT
fabricate and does NOT block — it falls through to the **"No prior report
located (search unavailable)"** path (§4.5) with `search_status:
unavailable` and notes the MCP failure in its rationale. A literature step
that cannot search is a clean "none-found-this-pass", not a crash and not a
hallucination.

### 4.5 The "no prior report located" path + the papers.md manual-triage list

When zero papers are MCP-verified AND bear on the finding (or the MCP is
unavailable), the agent produces an EXPLICIT block, not a silent
fall-through:

```
## Related findings — positioning for #<N>

**Finding searched:** <the 1-3 findings phrases, verbatim>
**Verdict:** NO PRIOR REPORT LOCATED.
**Search status:** searched   [or: unavailable — arXiv MCP did not respond this pass]
**Searched:** <realized call list — e.g. "arxiv search_papers x3,
  semantic_search x1, WebSearch x1; 9 results inspected, 0 bearing on the
  finding"> [or, when search_status=unavailable: "arXiv MCP unavailable this
  pass — search not run"].
**Proposed `**Broader narrative:**` addition:** *(none — or a single
  sentence: "No prior published report of <finding> located as of
  <date>.")*
```

The `search_status` distinction is load-bearing: `searched` → the search
RAN and found nothing, so the result may be genuinely novel (worth a
sharper lit check before a paper); `unavailable` → the MCP never
responded, so this pass is uninformative and a later interactive pass
should re-run. (Statistics concern 1, folded into v2.) The "none-found"
path NEVER blocks promotion.

**`docs/papers.md` — manual-triage list ONLY in v1 (PATH (A)).** When the
agent's search surfaces a verified paper that directly engages the finding
and is NOT already logged in `docs/papers.md`, it lists it under a
**Suggested for docs/papers.md (manual triage)** heading in the artifact +
its return — a flat list of `[<short title>, arXiv:<id>, <one-line
relevance>]` entries the USER can hand-add to `docs/papers.md` if they
choose. **v1 ships NO automation of the papers.md write** — there is no
`docs/papers.md` apply diff and the `related_work_positioning` gate does
NOT touch `docs/papers.md`. (The papers.md auto-apply leg, with a proper
`DocPatch`-shaped proposal or a dedicated helper honoring `living_docs.py`'s
always-rewrites-open_questions.md + required-changelog contract, is the §13
follow-up.)

### 4.6 The proposed `**Broader narrative:**` addition (body-shape-safe — HARD)

The proposal appends a SHORT note INSIDE the existing
`**Broader narrative:**` slot — it does NOT add a new H2/H3 or a new
boldface slot, so `verify_task_body.py` / SPEC.md are UNCHANGED (see §12
A6). The addition is a single bolded sub-line:

```markdown
- **Broader narrative:** <existing prose, unchanged> **Related findings:**
  <verdict in ≤80 words — e.g. "Replicates the contrastive-negative
  selectivity gradient reported in [Persona Vectors, arXiv:2507.21509] and
  extends it to LoRA-rank r=16; no prior report of the dose-confound
  correction located.">
```

HARD caps to protect the WARN-only total-prose budget
(`verify_task_body.py` check 20 — `## Goal` prose IS counted, budget 800 +
250/round, see §12 A6):
- the appended **Related findings:** clause is **≤80 words**;
- each cited paper is `[<short title>, arXiv:<id>]` (the MCP-verified id) —
  NO author lists, NO multi-sentence summaries (those, when warranted, go
  to the manual-triage list for `docs/papers.md`, §4.5).

The addition routes through the analyzer/clean-result-critic loop ONLY if
the user confirms it (the `## Goal` body edit applies via a normal
`set-body`, and a re-run of `verify_task_body.py` confirms it didn't break
caps — WARN if it nudges over budget, never a blocking FAIL). The proposal
is **advisory** — a thin/empty/over-budget note NEVER blocks
`awaiting_promotion` (the task is already there before this gate; §4.1).

### 4.7 The artifact + return contract

ONE file (the only thing the agent writes), resolved via the canonical
resolver (`task.py find <N>` — never a cwd-relative path):
```
$TASK_DIR/artifacts/related-work-proposal.md
```
containing: (a) the §4.5/§4.6-shaped "Related findings" block (incl. the
`Search status:` line), (b) the proposed `**Broader narrative:**` addition
as a unified diff against `body.md`, (c) an OPTIONAL **Suggested for
docs/papers.md (manual triage)** list (a human-triage list of verified
candidate papers — NOT an apply diff in v1; §4.5).

The return text (final agent message, NOT a posted marker — the
orchestrator posts the marker) is a tight structured rationale:
```
## Related-work positioning for #<N>
**Proposal artifact:** <abs path>
**Finding(s) searched:** <phrases>
**Verdict:** replicates | contradicts | extends | tangential | none-found
**Search status:** searched | unavailable
**Verified citations:** <[title, arXiv:id] list, each with the verify call made> | none
**Search budget used:** <realized counts vs the ≤6 MCP / ≤2 web cap>
**Proposed Broader-narrative addition:** <the ≤80-word clause, or "none">
**Suggested for docs/papers.md (manual triage):** <[title, arXiv:id, relevance] list, or "none — no new paper directly engages the finding">
```

## 6. Evaluation (how do we know the workflow change works?)

The hero artifact is **a rendered, MCP-verified "Related findings" block in
a sample clean-result body** produced by a dry-run of the agent on an
already-completed experiment. Tests:

1. **Agent dry-run (manual integration smoke — the hero).** Spawn
   `related-work-finder` against a real completed experiment (e.g. a recent
   `awaiting_promotion`/`completed` task with a clear finding — the
   implementer picks one, e.g. #612 or #608). Confirm: (a) it produces
   `artifacts/related-work-proposal.md` with a verdict; (b) EVERY cited

   phrased to have no prior art (or with the MCP disabled) and confirm it

   MCP was disabled) — not a silent fall-through / not a fabricated

   `audit_clean_results_body_discipline.py` likewise PASSes.

   --check-asks` PASSes (the new gate anchor resolves); the no-flags default
   `workflow_lint.py` run PASSes; `ruff check` on any touched py (none
   expected in v1) PASSes.
5. **Consistency (acceptance criterion #5).** CLAUDE.md / workflow.yaml /
   `agents-vs-skills.md` stay mutually consistent (the new marker/gate names

   the new agent). The code-reviewer ensemble verifies this.

**Body / grounding (paste into the follow-up's body):**

> ## Goal
> Wire the `docs/papers.md` auto-apply leg into the `related-work-finder` →
> `related_work_positioning` gate so that, on user confirm, a verified
> candidate paper the agent surfaced can be appended to `docs/papers.md`
> through a clean, tested apply path — rather than the v1 manual-triage list
> the user must hand-add.
>
> ## Workflow gap (from #694 round-1 Methodology reconciler)
> `scripts/living_docs.py apply()` consumes a structured `DocPatch`
> (`changelog_line` required; ordered `(old, new)` `open_questions_replacements`
> / `open_questions_appends`; secondary `papers_replacements` /
> `papers_appends`) and ALWAYS prepends a dated changelog to
> `docs/open_questions.md` + commits atomically. The papers.md edit is only
> ever applied as the SECONDARY leg of a patch that is fundamentally an
> open_questions.md patch (gated on `DocPatch.touches_papers()`). There is no
> papers-only apply entrypoint, so a papers-only confirm from
> `related-work-finder` cannot be applied through `apply()` as-is — it would
> fail (no open_questions anchor) or force a spurious open_questions.md
> changelog entry.
>
> ## Two candidate implementations (the follow-up planner picks one)
> **(B1) DocPatch-shaped proposal that satisfies the existing contract.**
> `related-work-finder` emits a `DocPatch`-shaped JSON with a required
> `changelog_line` (e.g. "logged <title> (arXiv:<id>) as related work for
> #N") and a `papers_appends` block (the new `docs/papers.md` entry), and —
> to honor the always-rewrites-open_questions.md invariant — a minimal,
> truthful `open_questions_appends`/`replacements` OR an explicit
> `changelog`-only entry. The gate confirm leg calls
> `living_docs.py apply <N> --patch-file <path>`. Pros: reuses the proven
> atomic apply + commit; Cons: forces an open_questions.md changelog write
> for a papers-only logical change (may be acceptable — the changelog IS the
> audit trail).
> **(B2) A new papers-only apply helper.** Add a `living_docs.py` function
> (e.g. `apply_papers(task_id, papers_appends, *, changelog_line)`) +
> subcommand that appends to `docs/papers.md` and prepends the changelog to
> `docs/open_questions.md` WITHOUT requiring an open_questions content
> replacement, then commits atomically (same flock + single commit). Pros:
> a clean papers-only path; Cons: a new public helper/subcommand (the
> architectural surface that needs greenlight).
>
> ## Tests the follow-up MUST add (the gap that let the v1 defect ship)
> - A papers-only proposal end-to-end: agent emits the proposal → gate
>   confirm → `docs/papers.md` gains the entry → `docs/open_questions.md`
>   gains the changelog line → single atomic commit → idempotent re-run is a
>   no-op. (Mirror `tests/test_living_docs*.py` style.)
> - The "no papers suggested" path applies ONLY the `## Goal` body edit (v1
>   behavior unchanged) and touches neither living doc.
> - `living_docs.py check` still PASSes after a papers-only apply (no
>   bidirectional/coverage drift introduced).
>
> ## Constraints / invariants
> - Workflow-surface only (`scripts/living_docs.py` is in-scope per
>   workflow-fix-on-bug.md — it is a workflow-helper script; confirm against
>   the surface list).
> - Honor `living_docs.py`'s fail-loud + atomic-commit + flock discipline.
> - The `related_work_positioning` gate stays NON-BLOCKING + advisory; the
>   papers.md apply is opt-in on user confirm, same as the `## Goal` edit.
> - Carry the round-1 reconciler Must-Fix text verbatim as provenance.
