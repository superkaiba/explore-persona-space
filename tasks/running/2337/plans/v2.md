# Plan v2 — #2337: Scope preflight's vLLM/transformers skew check to workloads that actually import vLLM

## Requirement + acceptance criteria

`check_vllm_transformers_compat` (`src/explore_persona_space/orchestrate/preflight.py:1206`)
hard-FAILs preflight on `vllm==0.11.x` + `transformers>=5` regardless of whether the
workload imports vLLM, and its printed remedy unconditionally recommends
`transformers>=4.46,<5.0` — destructive for models whose support exists only in
transformers >= 5 (qwen3_5 absent from 4.57.6, verified live on #2329).

**Decision (autonomous): implement the task body's option 3 — an explicit,
documented env-override acknowledgment path — plus the conditional remedy text.**
Rationale against options 1/2 (static scan of the dispatch target / auto-downgrade
on no-vLLM-import-detected): preflight has no reliable view of the workload — it is
run standalone (`python -m ...preflight`) by bootstrap, dispatchers, and
experimenters without workload args, and a static grep of an entrypoint misses
transitive vLLM imports through helper modules (the one-level-deep helper-resolution
false-negative class, `.claude/rules/smoke-blind-spots.md`), silently weakening the
guard for the exact 7-issue recurrence class (#238/#261/#263/#269/#331/#354/#368)
that motivated #182's check. An explicit override has no false-negative channel:
the launching session, which KNOWS the workload's vLLM reachability (as #2329's
did, with static + empirical evidence), asserts it per-launch. The file already
carries two precedents of exactly this shape: `EPM_PREFLIGHT_DISK_FLOOR_OVERRIDE`
(preflight.py:249) and `EPM_PREFLIGHT_DATA_DISK_OVERRIDE` (preflight.py:331,
"degrades the ERROR to a logged WARN").

Acceptance criteria:

1. Default behavior for a genuine vLLM workload is UNCHANGED: `vllm==0.11.x` +
   `transformers>=5` + env unset → `report.add_error(...)` → `report.ok=False`.
2. `EPM_PREFLIGHT_ALLOW_TRANSFORMERS5` ∈ {`1`,`true`,`yes`} (same accepted set as
   the two precedents) degrades the ERROR to ONE `report.add_warning(...)` naming
   the acknowledgment; `report.ok` is unaffected by this check.
3. The ERROR message's remedy becomes CONDITIONAL two-branch advice:
   - workload instantiates vLLM `LLM(...)` → pin `transformers>=4.46,<5.0` (the
     existing advice), OR
   - workload does NOT import vLLM (verify: static grep of the dispatch chain +
     the workload's own smoke evidence) → set `EPM_PREFLIGHT_ALLOW_TRANSFORMERS5=1`;
     do NOT downgrade transformers for a model requiring >= 5 (e.g. qwen3_5).
4. Non-skew version combinations (transformers 4.x, or vllm outside 0.11.x) and the
   ImportError-warning branch are byte-unchanged in behavior.
5. Secondary (body § "Also worth fixing"): when the HF storage headroom probe finds
   usedStorage missing on ALL repos (`n_missing == n`), the `basis` string
   (`src/explore_persona_space/orchestrate/hub.py:289`) additionally names the
   likely auth/endpoint condition so the line is not read as a storage fact.
6. Focused tests + the Step 9c gate pass; `ruff check` clean.

## Kill criteria

workload's failure signal in some caller (e.g. a dispatcher that sets the env
process-wide and leaks it into a later vLLM-bearing launch), the design bounces to
option 1 (explicit workload flag). Mitigation already in scope: the WARN text
states the residual risk, and the env is documented as per-launch, not persistent.
