# Plan — issue #702: analyzer-side guard against authoring a verdict on a partial grid missing a planned control/baseline arm

## 0. Plan Summary

**Change:** Add one additive guard step to `.claude/agents/analyzer.md` (a new
`### Step 1.6: Planned-control-arm presence gate`, firing after Step 1 reads the
plan and BEFORE Step 2 computes any statistics / Step 3 plots / Step 4 prose /
Step 6 set-body). The guard enumerates the plan's declared control/baseline arms
(plan §5 Conditions and Controls table + the `epm:plan` payload), checks each is
PRESENT and NON-EMPTY in `eval_results/`, and on a missing arm BLOCKS the verdict:
post `epm:failure v1` (`failure_class: data`, `reason: planned_control_arm_missing`)
naming the missing arm(s), set `status:blocked`, exit without authoring.

**Hyperparameters:** N/A — no hyperparameters in this task type.

**Baselines / controls:** N/A — workflow-surface edit, no experiment run.

**Loss surface:** N/A — no training.

**Compute:** 0 GPU-hours; 1 file edit (~30-60 lines additive instruction text in
`analyzer.md`). `Estimated GPU-hours (total): 0`

**Evaluation:** Test-verdict gate is `uv run python scripts/workflow_lint.py`
(PASS) + `uv run ruff check .` (PASS). No GPU eval.

**Risks (top 2):** (1) False positives on legacy plans with no explicit controls
section — mitigated by an opt-in design (the guard fires ONLY when the plan
declares controls; absent declarations → vacuous pass, exactly like
clean-result-critic Lens 13). (2) The presence check being fooled by an
empty/partial JSON of the right name — mitigated by a minimum-bar evidence rule
(arm directory exists AND a result file exists AND it carries the headline metric
key, not merely the directory).

**Success criterion:** The guard text lands in `analyzer.md` at the specified
position, fires before any body-write/figure-commit/`epm:interpretation` post,
parks on a missing declared control arm, and proceeds normally when the plan
declares no controls; `workflow_lint.py` + ruff PASS.

**Kill criterion:** If `workflow_lint.py --check-asks` flags the new
`AskUserQuestion`-free guard text as introducing an un-gated pause, or if the
guard text cannot be expressed without a public-contract change, STOP and
re-scope — do not weaken the halt-criterion contract to ship.

## 1. Goal

Prevent the analyzer authoring takeaways on a partial grid that is missing a
planned control / baseline arm.

## 2. Prior Work / sibling discipline

Three places already touch planned-vs-actual coverage. The new guard is the
UPSTREAM, analyzer-side complement — it fires at a different point in the
pipeline and answers a different question, so it is additive, not duplicative.

- **`scripts/verify_task_body.py` check 11b** (`check_planned_vs_actual_denominator`,
  line 3363). Mechanical, WITHIN-BODY only: it scans the already-written body for a
  `M of N <noun>` scope-correction claim and FAILs when the headline surface
  (`## Takeaways` + `## Results` for v4) still uses the original denominator `N`.
  It explicitly does NOT read the plan ("Plan-side enumeration … is the semantic
  call clean-result-critic Lens 13 makes; this mechanical check does NOT read the
  plan file"). It runs at Step 5 (Verify), AFTER the analyzer has authored the
  body — i.e. after the verdict already exists.

- **`.claude/agents/clean-result-critic.md` Lens 13** (line 1767, "Planned-vs-actual
  coverage"). Semantic LM read: it reads `plans/plan.md`, enumerates planned
  conditions/cells/factor flips, and FAILs when a planned condition appears nowhere
  in the body, when the denominator is inconsistent, or when a figure renders a
  misleading zero bar. It runs as a clean-result-critic lens — AFTER the analyzer
  authored the body and AFTER `verify_task_body.py` passed.

- **`.claude/agents/analyzer.md`** itself — the measurement-validity gate (line 76)
  blocks a saturated/off-distribution headline, but there is currently NO check
  that the planned CONTROL/BASELINE ARMS actually landed in `eval_results/` before
  the analyzer starts authoring.

**Why the upstream guard is additive (not duplicative).** Both sibling checks fire
at WRITE-UP time — they read the body the analyzer already wrote and discipline its
denominator/figures. By then the analyzer has already spent an authoring pass and,
critically, the false-positive verdict already exists in a cache/draft and may have
been narrated. The #658 incident is precisely the failure these write-up-time checks
do NOT catch: the analyzer ran on a partial grid before the random-projection
control arm landed, authored an apparent 3/10 Betley PASS, and that PASS was a
multiple-comparison artifact (0/10 once the control landed). A write-up-time
denominator check cannot help here because the body would NOT have flagged "3 of 10
arms" — the analyzer simply did not know an arm was missing; it interpreted the grid
it had as complete. The upstream guard closes that gap by refusing to author at all
until every DECLARED control/baseline arm is present in `eval_results/`. It is the
planned-vs-actual-coverage discipline applied at VERDICT time, not just at
write-up time.

## 4. Design — the exact edit to `.claude/agents/analyzer.md`

### 4.1 Where the guard fires (step sequence)

Insert a NEW subsection `### Step 1.6: Planned-control-arm presence gate (run
BEFORE interpreting / plotting / authoring)` immediately after Step 1.5 (line ~121,
the exemplar-loading step) and BEFORE `### Step 2: Compute Statistics` (line 193).

Rationale for this position:
- Step 1 (Load and Understand Data, line 64) already reads "The plan (from the
  `epm:plan` events.jsonl event, or `.claude/plans/issue-<N>.html`)" and "Specific
  result files (`eval_results/<name>/run_result.json` and any per-condition
  JSONs)". So both inputs the guard needs are already in scope by Step 1 — the
  guard reuses them, adds no new data dependency.
- It is BEFORE Step 2 (statistics), Step 3 (plots/figure commits), Step 4 (write the
  body), Step 4.5/4.6 (humanize/register), Step 5 (verify), and Step 6 (set-body +
  the HELD/published `epm:interpretation`). So the gate fires before ANY prose,
  figure commit, or interpretation post — exactly the requirement.
- It mirrors the measurement-validity gate's "(run BEFORE interpreting)" framing
  (line 76) so the two early gates read as a coherent pair.

### 4.2 How the "planned control / baseline arm" set is sourced

Primary source: **the approved plan body** (`tasks/<status>/<N>/plans/plan.md`,
the symlink to the highest `v{K}.md`), which the analyzer already reads at Step 1.
This is the same source clean-result-critic Lens 13 uses (line 1792-1796), so the
two stay consistent. Resolve the path the canonical way (never hand-built):

```bash
plan_path="$(uv run python scripts/task.py find <N>)/plans/plan.md"
```

Enumerate the DECLARED control/baseline arms from the plan §5 Conditions and
Controls table. The project's standing plan format (planner.md §5) is a table with
columns `Plain-English name | What it tests | What it controls for | Config slug`.
An arm is a CONTROL/BASELINE arm when ANY of:
- its row is explicitly labeled `CONTROL` / `BASELINE` (case-insensitive) in any
  column, OR
- its "What it tests" / "What it controls for" column names it a control / baseline
  / null / shuffle / random-projection / permutation arm, OR
- the plan §0 Plan Summary "**Baselines / controls:**" line names it.

For each such arm, capture BOTH its plain-English name AND its config slug (the
rightmost column) — the slug is the key that maps to `eval_results/` (see 4.3).

**Secondary/cross-check source:** the `epm:plan` marker payload (already loaded at
Step 1). When the plan body table is malformed or absent but the `epm:plan` payload
enumerates conditions with a control/baseline tag, use it. The two should agree;
if they disagree, use the UNION of declared control arms (fail-safe toward
catching a missing arm).

**Fallback when no controls are declared (the opt-in carve-out, see 4.4):** if
neither the plan §5 table NOR the `epm:plan` payload declares any control/baseline
arm, the guard PASSES vacuously and the analyzer proceeds normally. This is the
identical vacuous-pass behavior as clean-result-critic Lens 13 ("PASSes vacuously
when the plan has no enumerable planned conditions"). The guard is opt-in based on
the plan's OWN declarations — it never fabricates a control requirement the plan
did not commit to.

### 4.3 How the guard checks presence in `eval_results/`

For EACH declared control/baseline arm, the arm is PRESENT iff ALL of:
1. **A result artifact exists** for that arm under `eval_results/issue_<N>/`
   (or the plan's named `eval_results/<name>/` path): at least one
   `*.json` whose condition/cell key matches the arm's config slug or
   plain-English name. Match on the slug first (exact), then a normalized-name
   fallback (lowercase, non-alphanumeric → `_`).
2. **The file is non-empty and parses** as JSON (`test -s` + a `json.load`
   that does not raise).
3. **The headline metric key is present and non-null** in that JSON — the same
   metric the analyzer will compare across arms (e.g. the Betley pass count /
   the per-condition rate / the DV the plan §6 evaluation table names). A
   directory or a JSON of the right NAME that is missing the metric value is
   treated as MISSING (this is the minimum-bar-evidence rule, §7 risk 2).

Concretely, the guard text instructs the analyzer to enumerate `eval_results/`
for the issue and, per declared control arm, assert the (slug-keyed) result file
exists, is non-empty, parses, and carries the headline-metric key. The analyzer
already reads these files at Step 1, so this is a presence/parse assertion over
data it is loading anyway — no new file walk semantics.

### 4.4 Scope of the guard — when it APPLIES (the carve-out)

The guard is OPT-IN, gated on the plan's own declarations, and additionally
scoped by task `kind`:

- **APPLIES** to `kind: experiment` tasks whose plan DECLARES at least one
  control/baseline arm (per 4.2). This is the only case where a missing control
  arm can produce the #658 false-positive-by-omission.
- **SKIPS (vacuous pass)** when:
  - the task `kind` is `analysis | infra | batch | survey` (no Goal-bound
    multi-arm verdict; mirrors the measurement-validity gate's exemption at
    line 76, "Skip when there is no Goal-bound behavioral construct — `kind:
    analysis|infra|batch|survey`"), OR
  - the plan declares NO control/baseline arm (legitimately single-arm /
    descriptive work, or a legacy plan without an explicit controls section).

The skip is explicit so the guard NEVER fires on legitimately single-arm work.
A legacy plan with no §5 controls section → no declared control arms → vacuous
pass. This is the intended behavior, not a gap: the guard disciplines plans that
COMMITTED to a control arm, exactly as Lens 13 disciplines plans that committed
to N conditions.

### 4.5 BLOCK behavior on a missing arm

When the guard finds a DECLARED control/baseline arm that is NOT present (per
4.3), the analyzer MUST NOT author. It:
1. Posts `epm:failure v1` with `failure_class: data` and
   `reason: planned_control_arm_missing`, the note NAMING the missing arm(s)
   (plain-English name + config slug) and the `eval_results/` path it looked
   under. Idiom — matching the existing Step 6 pre-flight failure pattern
   (line 492):
   ```bash
   uv run python scripts/task.py post-marker <N> epm:failure \
     --note 'failure_class: data
   reason: planned_control_arm_missing
   missing_arms: <plain-English name(s)> (slug: <slug(s)>)
   looked_under: eval_results/issue_<N>/
   The plan §5 declares these control/baseline arm(s) but no parseable result
   carrying the headline metric is present. Authoring a verdict on this partial
   grid risks a multiple-comparison false positive (see #658). Land the missing
   arm(s), then re-run /issue <N> (the analyzer re-runs from Step 1).'
   ```
2. Sets `status:blocked`:
   ```bash
   uv run python scripts/task.py set-status <N> blocked
   ```
3. Exits WITHOUT writing any body / committing any figure / posting
   `epm:interpretation`.

`failure_class: data` is the correct class per the halt-criterion contract
(workflow.yaml § markers `epm:failure`, line 2041): a `data` failure "is a
factual gap only the user can fill — the task parks at status:blocked and does
NOT enter the Step 7 crash-fix routing, which covers infra | code only." This is
exactly the desired behavior: the user lands the missing arm, then the analyzer
re-runs (the Step 1 router resumes; the guard then passes and authoring proceeds).

### 4.6 Pseudocode for the guard (instruction text, not committed code)

The guard lands as INSTRUCTION TEXT in `analyzer.md` (the analyzer is an LM agent;
this is prose it follows, like every other step). The text directs the analyzer to:

```
1. If frontmatter.kind in {analysis, infra, batch, survey}: PASS (skip), go to Step 2.
2. Read the plan (already loaded at Step 1). Enumerate declared control/baseline
   arms from §5 Conditions and Controls (rows labeled CONTROL/BASELINE or whose
   role column names a control/baseline/null/shuffle/random-projection/permutation
   arm) + the §0 "Baselines / controls:" line + the epm:plan payload. Capture each
   arm's plain-English name AND config slug.
3. If the declared-control set is empty: PASS (vacuous), go to Step 2.
4. Enumerate eval_results/issue_<N>/ (and any plan-named eval_results/<name>/).
   For each declared control arm, PRESENT iff a slug- (or normalized-name-) keyed
   *.json exists, is non-empty, parses, and carries the headline-metric key.
5. If every declared control arm is PRESENT: PASS, go to Step 2.
6. Otherwise BLOCK: post epm:failure v1 (failure_class: data,
   reason: planned_control_arm_missing) naming the missing arm(s) + path; set
   status:blocked; EXIT without authoring (no body, no figure commit, no
   epm:interpretation).
```
