**Draft bullet text (implementer may refine wording; keep the load-bearing facts):**

> - **HF Hub rejects any single repo directory holding >10000 files at COMMIT time — a NON-retriable `BadRequestError` the per-file 504 retry wrapper does NOT catch.** The directory-size sibling of the per-file 504-storm above: even when every per-file upload is shaped correctly and the per-file uploads all SUCCEED, the final `upload_folder` / `create_commit` step 400s with `BadRequestError: ... too many files ... up to 10000` once any one target directory exceeds the cap. It is NOT transient — the 504 retry wrapper (`scripts/issue658_extract_rb_personavectors.py`, commit `62bb233cd0`) only re-tries transient commit timeouts and re-throws a `BadRequestError` unchanged — and the symptom surfaces ONLY after the full compute has already run and every file is staged. RULE: any workload that emits >10k sibling files into one directory — per-rollout activation `.pt` files, per-sample transcripts, per-step checkpoints — MUST shard into `shard_NNNN/` subdirs of `<=5000` files each (5000, not 10000, leaves headroom) with an index/manifest recording each file's shard-relative path so readers resolve it unchanged. Recovery for an already-written flat store: re-shard in place + re-upload (the `--resume-upload-from-store` path, commit `614284bd3f`). (Incident #658 round 2, 2026-06-29: a persona-vectors `r_B` extraction wrote 12000 rollout `.pt` files + 12000 transcripts into one dir each; per-file uploads succeeded, the COMMIT 400'd on the 10000 cap; salvaged by re-sharding both dirs to `shard_*/` subdirs of `<=5000` files.)
