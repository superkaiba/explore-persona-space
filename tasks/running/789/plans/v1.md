# Plan — issue #789: Stop Codex twins driving reconciler rounds via sandbox-DNS false-FAIL and hallucinated-fix false-disagreement

## §0 Goal

Edit the two Codex twin adversarial-reviewer specs (`codex-clean-result-critic.md`, `codex-interpretation-critic.md`) so a sandbox HF/DNS networking failure is tagged as an advisory `sandbox-unverifiable` finding (non-blocking, does not downgrade the verdict) rather than a `BLOCKED`/`data-access-blocked` verdict driver, AND so any "fix applied / not applied" claim must quote the exact body line verbatim — killing the two false-disagreement modes that spawn a wasted reconciler round every time.

## §1 Prior work / existing state

### What the two files currently say (verbatim snippets)

**`codex-clean-result-critic.md` line 435** — the master "unreadable file protocol":

> **If you CANNOT read a required file (sandbox read-only, DNS / HF body-fetch failure, denied Read/Bash; verifier or audit script cannot execute; …a figure URL won't resolve):** … Mark the affected lens `BLOCKED — could not read <path>` and do NOT emit an overall `PASS` … the overall verdict must be `needs_targeted_fix` with a `data-access-blocked` note so the reconciler/orchestrator knows the PASS-path was unreachable.

Two downstream lens instructions inherit this:
- **Lens 5, line 617-620:** "If the Hub API is unreachable from the sandbox, mark this bullet `BLOCKED — could not list <repo>` per the unreadable-file protocol above … PASS|FAIL|BLOCKED".
- **Lens 10, line 704:** "Link liveness: a load-bearing `## Methodology` complete-artifact link resolves (HF path via `huggingface_hub.list_repo_files`, never `hf` CLI): PASS|FAIL|BLOCKED".

**`codex-interpretation-critic.md` line 228** — the same master protocol, tighter:

> **If you CANNOT read a required file (sandbox read-only, DNS / HF body-fetch failure, denied Read/Bash):** … Mark the affected lens `BLOCKED — could not read <path>` and do NOT emit an overall `PASS` … the overall verdict must be `REVISE` with a `data-access-blocked` note so the reconciler/orchestrator knows the PASS-path was unreachable.

The problem: BOTH files fold "DNS / HF body-fetch failure" (a mechanical sandbox networking limitation) into the SAME bucket as "denied Read/Bash" (a real audit gap where Codex is stopped from reading content it should be checking). They get identical treatment — `BLOCKED` + a verdict downgrade + `data-access-blocked`.

There is currently **no** evidence-quote requirement anywhere: the GROUNDING rules (CRC line 450-455, ICC line 271-279) require citing "the offending phrase / heading / figure" for a FAIL-*driving* finding, but say nothing about a finding that ASSERTS a fix IS present (a PASS-supporting or REVISE-clearing claim). A round-2/3 "the fix was applied" claim needs no quote today.

### What the reconciler already does

`feedback_claude_interp_critic_verify_body_fail_out_of_scope.md` (lines 66-74) records the exact resolution pattern from #559 r2 clean-result-critic:

> Claude PASS vs Codex needs_targeted_fix (data-access-blocked, sandbox DNS couldn't reach HF; tagged `[lens]` = mechanizable-verifier-blocked, NOT a content finding) → reconciled PASS. Reconciler ran `list_repo_files` from the VM: both pinned revs resolve … **Lesson: a Codex `data-access-blocked` / DNS-failure flag is an infra strip, not a blocker, whenever the orchestrator/VM has the access Codex's sandbox lacked and the body content is unchanged.**

So the reconciler reliably converges these to PASS — but only after being spawned. `feedback_codex_reapplies_v3_check_to_v2_body.md` documents the sibling "no concrete missing path → non-binding" discard.

### Why this doesn't already solve the problem

The reconciler discard happens **after** the round is already spent. A Claude-PASS vs Codex-FAIL (or PASS-vs-REVISE) disagreement is what TRIGGERS the reconciler spawn (§ Codex ensemble review: "PASS vs FAIL → spawn reconciler"). The fix has to prevent the false DISAGREEMENT at the Codex verdict stage, so the ensemble converges PASS+PASS and no reconciler is spawned at all. This is a plan-time avoid-the-round fix, not a correct-the-reconciler fix. Recurrence: #559 (2026-05), #665 + #722 (2026-06-30) — 3+ known instances of the same class.

## §11 Decision rationale

- **Tag name `sandbox-unverifiable`** — *Source: task body Goal* (verbatim: "tag any HF/network-liveness finding as `sandbox-unverifiable` (advisory, non-blocking)"). Chosen over reusing `data-access-blocked` precisely because `data-access-blocked` IS the strip-tag the reconciler keys off as a blocker; a distinct advisory name lets the DNS case stay off the Blocker-tags line entirely.
- **Advisory (no downgrade) vs blocking** — *Source: `feedback_claude_interp_critic_verify_body_fail_out_of_scope.md`* (the reconciler already treats a DNS flag as "an infra strip, not a blocker"). Making the Codex verdict itself non-blocking removes the disagreement.
- **Keeping denied-Read as `BLOCKED`** — *Source: existing state* (CRC line 435 / ICC line 228 conflate two cases; only the network case is a false-FAIL — denied capability is a genuine audit gap the task body says to preserve).
- **Location within each file** — *Source: existing state.* Rule A lands in the master "unreadable file protocol" paragraph (CRC 435, ICC 228), plus the two CRC lens sites (617, 704) that repeat the `BLOCKED` enum inline. Rule B lands in the GROUNDING+MECHANIZABILITY paragraph (CRC 450) / Rules paragraph (ICC 271) — the register matches exactly.
- **`RepositoryNotFoundError` / missing-path carve-out stays FAIL** — *Source: task body* ("`list_repo_files` raising `HfHubHTTPError` from a networking cause vs `RepositoryNotFoundError` (that's a real 'path doesn't exist' finding and stays blocking)"). Without this carve-out the advisory tag would swallow real broken-link findings.
- **Evidence-quote enforcement = prompt-side reminder + grounding-rule sentence, NOT a wired compose-time regex (v1)** — *Source: design pick.* Reconciler already discards ungrounded findings, so a grounding-rule sentence requiring a verbatim quote makes an unquoted "applied" claim non-binding by the SAME mechanism, with zero new machinery.
