# Plan v1 — same-issue follow-up loop re-reads the LATEST `epm:followup-scope`

## Plan Summary
Documentation tightening of SKILL.md's same-issue follow-up loop so it ALWAYS
plans against the NEWEST `epm:followup-scope` for the unrun `followup_label`,
never a stale entry-time snapshot. Workflow surface only:
`.claude/skills/issue/SKILL.md`. **Estimated GPU-hours (total): 0** (the
autonomous Step 2c gate parses this; 0 GPU-h auto-approves under the 100 GPU-h
cap). No pod, no model, no datasets. `architectural: false`.

## Goal + acceptance criteria
**Goal:** the loop plans against the latest scope marker. **Acceptance:**
(1) the loop's planner-snapshot point carries an explicit "re-read the latest
scope" instruction; (2) the re-read recipe is mechanical and copy-pasteable;
(3) every site that observes the unrun scope (Step 0 dispatcher,
Resume-semantics, step 1 Scope marker, step 3 planner amendment) is consistent;
(4) `workflow_lint.py --check-references`/`--check-asks` + `tests/test_workflow*.py`
+ `tests/test_task_workflow*.py` stay green.

## Method delta (vs current state)
Current state: step 1 ("Scope marker") only ensures *a* `v1` scope exists; step 3
re-invokes the planner in AMENDMENT scope without saying which scope version to
read; the Step 0 dispatcher matches "an UNRUN `epm:followup-scope v1`". None of
these say "re-read newest before the planner snapshots", so a session that
entered on `v3` and snapshotted before `v5/v6` landed (the #658 bug) would plan
stale. Delta: add a single load-bearing rule — "select the latest scope for the
unrun `followup_label` immediately before the planner snapshots" — and reference
it at every observation site. `epm:followup-scope` is append-only with
monotonically increasing `version` per kind, deduped by `followup_label`, so the
authoritative scope = the highest-`version` (tie-break newest `ts`) marker whose
`followup_label` has no matching `epm:same-issue-followup-run`.

## File paths + concrete diffs — `.claude/skills/issue/SKILL.md`
1. **Step 1 "Scope marker" (~L5854):** append a sentence — *"There may be MULTIPLE
   `epm:followup-scope` versions for one `followup_label` (corrections land
   append-only); the authoritative scope is always the HIGHEST `version` (tie-break
   newest `ts`) for the unrun label. Do not cache the entry-time version."*
2. **Step 3 planner-amendment bullet (~L5916, "`/adversarial-planner` re-invoked in
   AMENDMENT scope"):** add a leading sentence — *"Immediately before the planner
   snapshots the scope, RE-READ the latest `epm:followup-scope` for this
   `followup_label`"* + the mechanical recipe:
   ```bash
   uv run python scripts/task.py view <N> --json | uv run python -c "import sys,json; \
     ev=json.load(sys.stdin)['events']; \
     s=[e for e in ev if e.get('kind')=='epm:followup-scope' and e.get('followup_label')=='<label>']; \
     print(json.dumps(max(s, key=lambda e:(e['version'], e['ts'])))) if s else None"
   ```
3. **Step 0 dispatcher (~L924):** clarify the UNRUN match reads the HIGHEST-version
   scope for the label (not literally `v1`) — *"an UNRUN `epm:followup-scope` (the
   highest-version entry for a `followup_label` with no matching
   `epm:same-issue-followup-run`)"*.
4. **Resume-semantics row** for the unrun-scope case (the rows around L932 that route
   to the loop): one clause noting the loop re-reads the latest scope at the planner
   snapshot (cross-ref step 3) so a crashed-mid-round resume picks up corrections.

Wording is 1-3 sentences per site. The `consistency-checker` already diffs the
amendment plan against the issue's own latest prior run; no brief change needed
beyond the planner reading the right scope (the plan it produces is what the
checker sees). The `experiment-implementer` briefs off the produced plan, not the
raw scope marker, so no implementer-brief change is required — confirm during
implementation; if a scope reference exists there, align it to "latest".
