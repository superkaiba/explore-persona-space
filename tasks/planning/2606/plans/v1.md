# Plan v1 — #2606: `pod.py provision` must fail loud when its own preflight fails

## Requirement + acceptance criteria

`pod.py provision` currently exits 0 and prints `BOOTSTRAP-OK pod=<name>` + "Done. SSH with: ..." even when the bootstrap's own step-10 preflight reported `PREFLIGHT-FAILED-AT-BOOTSTRAP rc=2` (observed live on pod-2569-rows, 2026-08-26: two errno-116 ESTALE uv install failures left a broken venv; the caller only found out because it habitually grepped the log). Acceptance criteria (verbatim from the task body):

1. A bootstrap whose preflight exits non-zero makes `pod.py provision` exit NON-ZERO, and the terminal banner says FAILED, not `BOOTSTRAP-OK`. The pod is left alive (may be recoverable) but the caller is told, loudly, in the exit code.
2. The provision summary surfaces the preflight verdict explicitly (a `PREFLIGHT: PASS|FAIL rc=<n>` line), so a caller need not grep the log.
3. `BOOTSTRAP-OK` is emitted only when bootstrap AND its preflight both succeeded. A regression test pins the pairing (a fixture where preflight returns 2 must not produce a success banner or a zero exit).
4. No change to the pod's lifecycle on failure — do NOT auto-terminate (the pod may be repairable; pods are not killed without the owner's decision).

Explicitly OUT of scope (task body): the default-overlay-venv-at-bootstrap design change (recurring errno-116 class across #475/#2225/#2278/#2378/#2569) — scoping only, needs its own review; any change to the #2060 bootstrap-fail auto-teardown or #2038 router emergency-teardown policies; any change to `src/explore_persona_space/backends/`.

## Root cause (verified in-repo, 2026-08-26)

- `scripts/bootstrap_pod.sh:778` (step 10): the pod-side preflight is invoked inside the ssh payload as
  `uv run python -m explore_persona_space.orchestrate.preflight --no-gpu 2>&1 || echo "PREFLIGHT-FAILED-AT-BOOTSTRAP rc=$?"`.
  The `|| echo` exists so `set -euo pipefail` (line 46) does not abort the script on a preflight failure — but it converts the failure into a SILENT SUCCESS: the remote shell exits 0, `ssh_cmd` returns 0, the script reaches its "Bootstrap complete" summary and exits 0.
- `scripts/pod_lifecycle.py::_provision_wait_register_bootstrap` (~2591-2664): `rc = _bootstrap(...)`; non-zero → retry EXACTLY ONCE (#1931); still non-zero → `_record_bad_placement_loud` + `_teardown_failed_provision` (#2060 auto-terminate unless `--keep-on-bootstrap-failure`) + `BOOTSTRAP-FAILED pod=<name> rc=<rc>` as last stderr line + `sys.exit(rc)`. rc==0 → `BOOTSTRAP-OK pod=<name>` on BOTH streams (#1931 token-once grep contract, line 2660) + exit 0. Because the swallow above pins rc==0, the preflight failure never reaches this dispatch.

## Design: a distinct typed exit code for "bootstrap completed but preflight failed"

The existing non-zero-rc branch AUTO-TERMINATES (#2060), which acceptance criterion 4 forbids for the preflight-failure class. So the preflight failure must arrive at `pod_lifecycle.py` as a DISTINCT signal, not a generic bootstrap failure.

**Channel: a reserved script exit code.** `_bootstrap()` runs `bootstrap_pod.sh` via `subprocess.call` with INHERITED stdout (streaming progress is a feature) — the exit code is the only clean machine channel without changing the subprocess contract. Chosen value: **78** (`EXIT_BOOTSTRAP_PREFLIGHT_FAILED`). Collision check done at plan time: 75 = still-waiting (`backends/runpod.py:126`), 76 = stopped-pod collision (`:141`), 77 = CPU-LANE-DRY (`pod.py provision`); 78 is unused in the pod_lifecycle/dispatch_issue/router process family (`backends/gcp.py:3056`'s `exit 78` is a REMOTE VM payload in a different process family). The implementer re-greps for collisions before landing; on a discovered collision, pick the next free code and update both constants + tests (allowed deviation).

### Change 1 — `scripts/bootstrap_pod.sh` (step 10)

- Add a named constant near the top: `EXIT_PREFLIGHT_FAILED=78` with a comment pointing at the mirror constant in `pod_lifecycle.py` and the parity test.
- Rework step 10: drop the in-payload `|| echo` swallow; capture the rc LOCALLY, set-e-safely:
  ```
  PREFLIGHT_RC=0
  ssh_cmd '<existing payload, last line = the preflight command, no || fallback>' || PREFLIGHT_RC=$?
  if [ "$PREFLIGHT_RC" -ne 0 ]; then
      echo "PREFLIGHT-FAILED-AT-BOOTSTRAP rc=$PREFLIGHT_RC"      # keep the sentinel (now printed locally; grep-compat with #2569 forensics)
      log_fail "Preflight FAILED (rc=$PREFLIGHT_RC) — pod venv/env is NOT experiment-ready"
      echo "Bootstrap FAILED at preflight for ${POD_NAME:-$HOST:$PORT} (preflight rc=$PREFLIGHT_RC)."
      exit "$EXIT_PREFLIGHT_FAILED"
  fi
  log_ok "Preflight passed"
  ```
- The `exit` fires before step 11 and before the "Bootstrap complete" success summary, so the success summary is structurally unreachable on the failure path (criterion 3's shell half).
- The `--no-preflight` branch is unchanged (skip). Neither `pod.py provision` nor `pod.py bootstrap` ever passes `--no-preflight` (`_bootstrap` invokes `["bash", BOOTSTRAP_SCRIPT, pod_name]`), so on every provision path exit 0 now implies "preflight ran and passed".
- Known attribution caveat (accepted): an ssh TRANSPORT failure at step 10 (rc 255) — or a failure of one of the payload's earlier lines (cd/source) — is classified as a preflight failure. Direction is conservative: the pod is kept alive instead of auto-terminated, and the printed rc discriminates (255 = transport). Documented in a comment.
- Payload note: the payload must stay single-quote-free (`tests/test_bootstrap_pod_uv_link_mode.py` extracts it verbatim); removing the `|| echo "..."` tail only deletes double quotes. Run that test after the edit.

### Change 2 — `scripts/pod_lifecycle.py` (`_provision_wait_register_bootstrap`)

- Add module constant `EXIT_BOOTSTRAP_PREFLIGHT_FAILED = 78` (docstring: mirror of `bootstrap_pod.sh` `EXIT_PREFLIGHT_FAILED`; parity pinned by test).
- Keep the #1931 retry-once EXACTLY as is for ALL non-zero rc, 78 included — a re-run re-executes `uv sync`, and the incident class (transient MooseFS ESTALE) is plausibly recoverable on re-run, same rationale as #1931's apt/network class.
- After the retry, branch on the final rc:
  - `rc == 0` → print `PREFLIGHT: PASS` (stdout, immediately before the OK verdict), then the existing `BOOTSTRAP-OK` both-streams block + "Done. SSH with: ..." — unchanged otherwise.
  - `rc == EXIT_BOOTSTRAP_PREFLIGHT_FAILED` → NEW branch, in order:
    1. stderr guidance block: bootstrap completed but the pod's own preflight FAILED; pod is left ALIVE and registered (criterion 4) — repair pointers: the raw preflight rc is in the `PREFLIGHT-FAILED-AT-BOOTSTRAP rc=<n>` log line; for the errno-116/ESTALE venv class see `.claude/rules/gotchas.md` Trap 3 (overlay venv at /root/eps-venv + UV_NO_SYNC); re-check with `ssh <name> 'cd /workspace/explore-persona-space && uv run python -m explore_persona_space.orchestrate.preflight'`; discard with `python scripts/pod.py terminate --issue <N>[ --name-suffix <slug>]` (reuse the existing keep-branch suffix-hint logic so an issue-wide destroy is never suggested for a suffixed pod, #1334).
    2. `PREFLIGHT: FAIL rc=78` (stderr; 78 is the mapped sentinel code — the line names where the raw rc lives).
    3. `BOOTSTRAP-FAILED pod={name} rc=78 reason=preflight` as the LAST stderr line (#1931 last-line contract preserved).
    4. `sys.exit(EXIT_BOOTSTRAP_PREFLIGHT_FAILED)`.
    Deliberately NOT in this branch: `_teardown_failed_provision` (criterion 4), `_record_bad_placement_loud` (the pod booted, SSH'd, and bootstrapped — the failure is env-class, not placement-class; polluting the DC denylist with venv failures would mis-steer the #2011 rotation), and pods.conf row removal (the row is needed to ssh in and repair).
  - any other non-zero `rc` → the existing branch VERBATIM (keep-flag messaging, bad-placement record, #2060 teardown, `BOOTSTRAP-FAILED ... rc=<rc>` last line, `sys.exit(rc)`).
- `PREFLIGHT: PASS|FAIL` line placement rationale: emitted by the provision tail (the caller-facing summary), satisfying criterion 2 without changing `_bootstrap`'s streaming contract.

### Router-path consequence (stated; NO code change)

`RunPodBackend.launch` runs provision via `_run_pod_lifecycle_relay`, which raises `PodLifecycleProcessError(78, ...)` on the new exit; launch's outer except arm then applies the PRE-EXISTING #2038 disposition — workload not started → best-effort exact-id terminate of the pod this launch just provisioned. Decision (recorded): do NOT special-case 78 in the router. An autonomous dispatch has no operator to repair a broken venv; leaving it billing unattended is the #664 idle-burn leak, and #2038 is the already-reviewed policy for exactly this shape. Criterion 4 binds the direct CLI (`pod.py provision`), which is where the #2569 incident lived and where an operator exists to repair. Today's router behavior is strictly worse (rc=0 → workload launched onto a broken venv → hang). This is a behavior IMPROVEMENT on the router path, delivered by the pre-existing policy, with zero router-code change.
