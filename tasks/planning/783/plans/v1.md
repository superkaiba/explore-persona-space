# Plan — issue #783: bounded GCP queue-wait timeout → RunPod failover (auto lane)

## 0.0 TL;DR (plain English)

- **What I'll do:** Right now, when we ask GCP for an H100 and GCP has none free, the request just sits in a queue — for hours — and nothing ever gives up. #778 sat in that queue almost 3 hours before a human noticed and moved it to RunPod by hand. I'll add a timer: if a GCP machine hasn't actually started running within ~10 minutes of waiting in the queue, we cancel that queued request and go straight to RunPod (or the next cheaper option) automatically.
- **What I expect:** The same "run it on RunPod instead" behavior we already have for a GCP *crash* — but now also triggered by a GCP *queue that never moves*, so no more silent multi-hour stalls and no more manual pivots.
- **What would change my mind:** If the 10-minute wait turns out to routinely cancel machines that were about to start (i.e. legitimate FLEX_START capacity that arrives at minute 12), I'd want to raise the timer — but it's a single env knob, so tuning is free and needs no code change.

## 0. Plan Summary (technical)

- **Change:** Add a poller-side **GCP queue-wait timeout** — a staleness clock on the `current_phase == "pending"` (FLEX_START capacity-queue) poll state that, past a bounded floor, rewrites the poll to a NEW terminal phase and fails the run over to the RunPod terminal rung. This is the exact analogue of the existing `_maybe_escalate_gcp_wedge` (#669 frozen-phase wedge) + `_failover_dead_gcp_to_runpod` (#659 async workload failover) machinery — a NEW **additional advance/failover trigger**, NOT a change to lane precedence.
- **Where the gap actually lives:** the FLEX_START PENDING wait happens *after* `route()` has already returned a handle (GCP "park is the provision call itself" — `router.py` docstring line 30). A PENDING instance polls as `status="running", current_phase="pending"` deliberately (`gcp._gcp_status_to_poll_result`, #782/#778) so the async bg poll loop keeps polling — forever. So the timeout belongs in the **async poller** (`scripts/backend_poll.py`), reusing the router's existing `failover_to_runpod_after_async_workload_crash` seam. `router.py` gets one new reason constant + a `reason=` passthrough param.
- **Knob:** `EPS_GCP_QUEUE_WAIT_SECONDS` (default **600s**, matching `FREE_WAIT_SECONDS`), read at call time via a `_gcp_queue_wait_seconds()` helper mirroring `_spot_max_gpu_hours()`.
- **Marker:** timeout-driven failover carries `reason: gcp_queue_timeout_failover_runpod` on the existing `epm:backend-selected v1` marker (a new reason string; no new marker kind), with the queue-wait context on `extra`.
- **Attempt cap:** a timeout-cancel is a CLEAN advance, NOT a workload failure or a new create — it does NOT touch `gcp_attempts_today` / `MAX_GCP_ATTEMPTS_PER_DAY` (the counter is only bumped inside `_attempt_one_gcp_rung`'s create path, which the poller never re-enters).
- **Baselines / controls:** N/A — code-change task.
- **Loss surface:** N/A — code-change task.
- **Compute:** 0 GPU-hours (pure workflow-surface code + tests). Verification is `ruff` + `workflow_lint` + `uv run pytest tests/test_router.py tests/test_backend_poll.py -v`.
- **Estimated GPU-hours (total): 0**
- **Evaluation:** new pins in `tests/test_router.py` + `tests/test_backend_poll.py`; the two named invariant tests still PASS.
- **Risks (top 2):** (1) false-positive cancel of a FLEX_START instance that was genuinely about to start within the window — mitigated by the 600s floor + env override + the clock re-stamping the moment the phase advances off `pending`; (2) mis-scoping the failover so a `cpu-bigmem` PENDING instance (no RunPod CPU lane) wrongly attempts RunPod — mitigated by reusing the exact CPU-intent guard from `_is_gcp_async_workload_failure`.

## 2. Method delta — smallest surface-area change vs the `FREE_WAIT` pattern

The task body sketched a router-side `FREE_WAIT`-style park on the GCP rung. **That is the wrong home** — the codebase already made the deliberate decision that "GCP has no queue estimate and no park; its park is the provision call itself" (`router.py` docstring line 30), and the FLEX_START PENDING wait actually happens in TWO places, neither of which is a router park loop:

1. **Sync create-timeout** — `GcpBackend.launch` (`gcp.py`) already handles the 300s create-subprocess cap: if the instance is live-but-PENDING server-side, it raises `GcpCreateTimedOutStillProvisioning` → `dispatch_issue.py` exit 75 → the orchestrator re-runs the SAME launch command, which idempotently reconnects (#736/#658). So the sync path never *blocks* indefinitely — it *loops* (re-dispatch → reconnect → re-wait), and nothing in that loop ever gives up and fails over. This is the #778 stall.
2. **Async poll** — once the instance exists and is PENDING, `route()` has already returned a `RunHandle` and the bg poll loop (`backend_poll.py::main()`, one tick per invocation) polls it. `GcpBackend.poll` → `_gcp_status_to_poll_result` maps `PENDING → status="running", current_phase="pending"` **deliberately** (#782/#778) so the loop keeps polling. Forever.

So the true fix is **a queue-wait staleness clock in the async poller**, mirroring the EXISTING `_maybe_escalate_gcp_wedge` (#669): a poller-side clock (kept out of `poll()` so `GcpBackend.poll` stays a pure function of `(handle, gcloud responses)`) that, when `current_phase == "pending"` has been frozen past `EPS_GCP_QUEUE_WAIT_SECONDS`, rewrites the poll to a new terminal phase, which a new narrow predicate then routes to the SAME `failover_to_runpod_after_async_workload_crash` seam the #659 async failover uses. This reuses ~all the plumbing (`_read_phase_clock`/`_write_phase_clock`, the sidecar, the RunPod terminal rung, the idempotency lease, the CPU-intent guard) and adds only: one reason constant, one env-knob helper, one escalation function, one predicate, one `main()` wiring line, one `reason=` passthrough on the router seam.

Comparison to `FREE_WAIT`: the FREE_WAIT park (`park_until_running_or_cap`) is a synchronous in-`route()` blocking loop that suits the SLURM lanes because SLURM `route()` OWNS the job through its whole PENDING→RUNNING transition. GCP `route()` does not — it returns after the create. The poller-clock is the GCP-shaped equivalent of "park up to a cap, then cancel + advance": the poller IS the park loop (one tick per bg-Bash invocation, per the orchestrator-vs-subagent rule), the clock is the cap, and the failover is the advance.

### 3.2 `scripts/backend_poll.py`

**(i) New env-knob helper + terminal phase constant** (next to `GCP_STALENESS_FLOOR_SEC` ~line 106):

```python
# The current_phase GcpBackend.poll produces for a FLEX_START instance still in
# the capacity QUEUE (gcp._gcp_status_to_poll_result: PENDING -> running/"pending",
# #782/#778). The poller clock below ages against THIS phase.
GCP_PENDING_PHASE = "pending"

# The current_phase the POLLER synthesizes (#783) when a FLEX_START instance has
# been stuck in the capacity queue ("pending") past the queue-wait floor. The
# queue-timeout predicate matches THIS phase EXACTLY; set ONLY by
# _maybe_escalate_gcp_queue_timeout.
GCP_QUEUE_TIMEOUT_PHASE = "terminal_queue_timeout"

# Bounded queue-wait floor (#783/#778). A GCP instance whose poll phase stays
# "pending" (FLEX_START capacity queue) longer than this fails over to RunPod.
# Default mirrors router.FREE_WAIT_SECONDS (600s). Env-overridable (an
# attempt-floor in seconds, NOT a dollar cap); read at call time so ops can tune
# without a restart, mirroring router._spot_max_gpu_hours().
def _gcp_queue_wait_seconds() -> int:
    raw = os.environ.get("EPS_GCP_QUEUE_WAIT_SECONDS")
    if raw is None:
        return 600
    try:
        return int(raw)
    except ValueError:
        return 600
```

**(ii) New escalation function** — a near-verbatim sibling of `_maybe_escalate_gcp_wedge`, but keyed on the `"pending"` phase and gated on the queue-wait floor (NO reachability-alarm conjunction — a stuck queue has no VM to be reachable, the phase-frozen-past-floor IS the whole signal):

```python
def _maybe_escalate_gcp_queue_timeout(handle, result, sidecar: Path, *, now: float):
    """Escalate a GCP instance stuck in the FLEX_START capacity queue past the
    queue-wait floor to terminal_queue_timeout (#783/#778).

    Poller-side staleness clock (kept OUT of GcpBackend.poll, mirroring
    _maybe_escalate_gcp_wedge). Reuses the SAME sidecar phase clock
    (_read_phase_clock/_write_phase_clock) as the #669 wedge — the two never
    both fire on one tick because they key on DIFFERENT current_phase values
    ("pending" vs a frozen mid-workload phase). Rewrites status->"dead" /
    current_phase->GCP_QUEUE_TIMEOUT_PHASE so _is_gcp_queue_timeout matches.

    False-positive guards (return result unchanged):
    * not a GCP handle, or the poll is not running, or current_phase is not
      "pending" -> unchanged (only a queued instance is in scope);
    * phase advanced (e.g. pending->provisioning->running) or first observation
      (last_ts is None) -> re-stamp, return running (fail-open);
    * phase still "pending" but within the queue-wait floor -> return running.
    """
    if getattr(handle, "backend", None) != "gcp" or result.status != "running":
        return result
    if result.current_phase != GCP_PENDING_PHASE:
        return result
    last_phase, last_ts = _read_phase_clock(sidecar)
    if last_phase != result.current_phase or last_ts is None:
        _write_phase_clock(sidecar, phase=result.current_phase, ts=now)
        return result
    queued_for = now - last_ts
    floor = _gcp_queue_wait_seconds()
    if queued_for > floor:
        logging.warning(
            "backend_poll: GCP issue stuck in FLEX_START capacity queue (phase %r) for "
            "%.0fs (>%ds floor) — escalating to %s and failing over to RunPod (#783/#778)",
            result.current_phase, queued_for, floor, GCP_QUEUE_TIMEOUT_PHASE,
        )
        return replace(
            result, status="dead", current_phase=GCP_QUEUE_TIMEOUT_PHASE,
            new_milestone=True, pid_alive=False,
        )
    return result
```

**(iii) New predicate** — narrow sibling of `_is_gcp_async_workload_failure`, reusing its EXACT CPU-intent guard (so a `cpu-bigmem` PENDING instance is EXCLUDED — no RunPod CPU lane — while `cpu-small`/`cpu-mid` are eligible):

```python
def _is_gcp_queue_timeout(handle, result) -> bool:
    """True ONLY for a GCP handle the queue-timeout escalation marked terminal (#783).

    handle.backend == "gcp" AND result.status == "dead" AND
    result.current_phase == GCP_QUEUE_TIMEOUT_PHASE. Reuses the CPU-intent guard
    of _is_gcp_async_workload_failure (a cpu-bigmem queue-stall must NOT fail
    over — no RunPod CPU lane; cpu-small/cpu-mid ARE eligible, #747)."""
    extra = getattr(handle, "extra", None) or {}
    if extra.get("gpu_count") == 0:
        from explore_persona_space.backends.router import RUNPOD_CPU_INSTANCE_FOR_INTENT
        if extra.get("intent") not in RUNPOD_CPU_INSTANCE_FOR_INTENT:
            return False
    return (
        getattr(handle, "backend", None) == "gcp"
        and result.status == "dead"
        and result.current_phase == GCP_QUEUE_TIMEOUT_PHASE
    )
```

**(iv) New failover function** — a thin sibling of `_failover_dead_gcp_to_runpod` that (a) DELETES the still-queued PENDING GCP instance via `GcpBackend.teardown(handle)` before re-dispatching (the queue slot must be released — an undeleted PENDING instance would keep its FLEX_START request live and could dequeue later as an orphan), then (b) re-dispatches on RunPod via `failover_to_runpod_after_async_workload_crash(reason=ROUTE_REASON_GCP_QUEUE_TIMEOUT_FAILOVER_RUNPOD, ...)`, reusing the SAME idempotency lease + sidecar re-point + terminal-JSON contract. It differs from `_failover_dead_gcp_to_runpod` only in: (1) it teardown-deletes first (a crashed workload's VM is already gone; a queued instance is not), and (2) it passes the queue-timeout `reason`.

```python
def _failover_queued_gcp_to_runpod(*, issue, handle, result, sidecar: Path) -> dict:
    """Cancel a still-queued GCP instance and re-dispatch on RunPod (#783/#778).

    Sibling of _failover_dead_gcp_to_runpod: SAME idempotency short-circuit
    (sentinel + durable lease keyed to the GCP identity), SAME
    failover_to_runpod_after_async_workload_crash seam, SAME sidecar re-point +
    terminal-JSON mapping. Two differences: (1) it best-effort DELETEs the
    PENDING GCP instance first (a queued instance is still live server-side and
    would keep its FLEX_START request; a crashed workload's VM is already gone),
    and (2) it passes reason=ROUTE_REASON_GCP_QUEUE_TIMEOUT_FAILOVER_RUNPOD.
    """
    # ... idempotency short-circuit (identical to _failover_dead_gcp_to_runpod) ...
    # best-effort teardown of the queued instance (guarded, never raises):
    try:
        _resolve_backend("gcp").teardown(handle)
    except Exception as exc:
        logging.warning("backend_poll: teardown of queued GCP %s failed (%s); "
                        "the stale-VM janitor will reap it.", handle.pod_name, exc)
    # ... failover_to_runpod_after_async_workload_crash(
    #         ..., reason=ROUTE_REASON_GCP_QUEUE_TIMEOUT_FAILOVER_RUNPOD,
    #         evidence={"source": "async_poller_queue_timeout",
    #                   "current_phase": result.current_phase, ...}) ...
    # (identical NoComputeAvailableError -> terminal-infra-JSON mapping)
```

Implementation note: to avoid duplicating ~90 lines of the idempotency + re-dispatch body, the implementer MAY refactor `_failover_dead_gcp_to_runpod` to accept a `reason` + an optional `teardown_first: bool` and have BOTH callers use it. That is a deviation-allowed factoring choice (see §9); the plan requires only that the queue-timeout path reuses the idempotency + sidecar-repoint + terminal-JSON contract, not the exact function shape.

## 11. Decision rationale (grounded knobs)

- **`EPS_GCP_QUEUE_WAIT_SECONDS = 600s` (default).**
  - *What:* The queue-wait floor before a PENDING FLEX_START instance fails over.
  - *Why (tied to Goal):* The Goal is "fail over instead of waiting INDEFINITELY." 600s is the exact value of the sibling `FREE_WAIT_SECONDS` — the codebase's already-chosen "how long do we park a queued job before giving up and advancing the lane" constant. Matching it keeps the two queue-wait behaviors (SLURM park, GCP queue) consistent, which is the explicit body directive ("align with `FREE_WAIT`"). #778's stall was ~2h45m, so 600s cuts the worst-case wait by ~16×.
  - *Source:* `src/explore_persona_space/backends/router.py:192` (`FREE_WAIT_SECONDS = 600`). Also the RunPod no-port wedge floor `RUNPOD_WEDGE_K_SEC = 900` (`backend_poll.py:129`) and `GCP_STALENESS_FLOOR_SEC = 900` (`backend_poll.py:106`) — both are "how long before a stuck-but-live instance is declared wedged." 600s sits at the low end of that established [600, 900] band, appropriate because a queue-stall (nothing running, no work lost) is cheaper to abandon than a wedge (a live instance mid-workload).
  - *Alternatives:* **900s** — matches the wedge floors, more conservative, tolerates a longer legitimate FLEX_START queue; rejected as the DEFAULT because a pure queue-wait forfeits nothing (no VM up, no work) and #778's pain was the multi-hour wait, so the shorter `FREE_WAIT`-parity value is the better default and 900s is one env-var away. **300s** — matches `GCLOUD_DEFAULT_TIMEOUT_SEC`; rejected as too aggressive (a genuine FLEX_START capacity grant can legitimately take several minutes to dequeue, and 300s would cancel-and-pivot before the queue had a fair chance). 600s is the max-info-gain-per-cost choice: long enough to give the cheaper GCP capacity a real chance, short enough that no run stalls for hours, and env-tunable in both directions at zero cost.

No model hyperparameters (no training). All other constants (phase strings, reason strings) are non-numeric identifiers, not tuned values.
