# Plan — #864: namespace-informative zombie-GPU override (stop the #813 false positive without weakening #664)

### 0.0 TL;DR (plain English)

- **What I'll change:** I'll make the poller's zombie-GPU probe report whether the "dead PID holding VRAM" signal is even meaningful on this pod. On some RunPod containers nvidia-smi reports host-side process IDs that never exist in the container's process table, so every healthy worker looks "dead." The probe will now also count how many GPU-process IDs *do* resolve and how many live container processes actually hold the GPU compute device open; when zero IDs resolve but live GPU-holders exist, the "zombie" flag is a namespace artifact and the stall override is suppressed no matter how quiet the logs are.
- **What I expect:** the #813-shape false positive (healthy CPU-bound run, quiet logs for 29 min, live cells flagged as dead VRAM holders) never fires again, while the genuine #664 hang (a dead CUDA worker whose VRAM lingers with no live in-container GPU-holder) still trips the override exactly as today.
- **What would change my mind:** if a live pod check shows healthy CUDA processes do NOT hold `/dev/nvidia-uvm` open (the correspondence signal would then under-fire and we'd fall back to today's behavior — safe but unfixed), or if the #664 shape turns out to occur on pods where the flagged PIDs are host-namespace (then the total-collapse fallback path carries the detection and I'd verify that branch harder).

### 0. Plan Summary (technical)

## 3. Design-tension resolution (veto-term vs probe-accuracy)

**Veto-term route (the candidate's diff sketch) — REFUTED as the primary mechanism.** Confirmed by reading the code:

- `not cpu_advancing` as a conjunct: in the stale-log + idle-GPU regime, `status == "running"` at the override's entry (line 2944) is reachable ONLY via the #518 CPU rescue (`cpu_advancing is True`, line 3312). So EVERY candidate the override ever evaluates in that regime has `cpu_advancing=True` — including the genuine #664 hang. Adding the conjunct makes the true positive unreachable, exactly as the #826 docstring warns.
- `not workload_procs_alive` (pgrep run_cell|dispatch): in #664 the dispatcher process was alive, blocked in the hung `generate()`. Same structural failure.

**Probe-accuracy route — CONFIRMED, with one amendment.** The candidate's `/proc/<pid>/status` `NSpid:` mapping is **not implementable from inside the container**: NSpid maps outer→inner only — the leftmost entry is the PID in the namespace of the procfs *mount*, so reading the container's own /proc can never recover a host PID, and the host PID's `/proc/<hostpid>/status` does not exist in the container's procfs at all (web-grounded; see Sources at the end of the planner report — kernel proc(5) semantics + the NVIDIA/nvidia-docker #1483 confirmation that in-container nvidia-smi reports host PIDs). The implementable probe-accuracy form is:

1. **Regime detection:** count how many compute-apps PIDs resolve in the container /proc. On a matched-namespace pod (the #664 regime) every healthy worker resolves, so `resolvable > 0` whenever any healthy worker exists; on a mismatched pod (the #813/#816 regime) `resolvable == 0` always.
2. **Live-holder correspondence (disambiguates `resolvable == 0`):** `resolvable == 0` is ambiguous between (a) regime-X healthy (all PIDs are live workers under host ids) and (b) regime-M total collapse (every CUDA worker genuinely dead). The discriminator is whether any live container process holds `/dev/nvidia-uvm` open: a live CUDA compute context holds the UVM device (the #813 cells did — they held ~38 GB VRAM each from live processes); a genuinely dead worker holds nothing, and the surviving EngineCore in #664 holds no *compute* context (if it did, it would itself appear in compute-apps and resolve, putting us in regime M). `/dev/nvidia-uvm` is chosen over `/dev/nvidiactl`/`/dev/nvidia[0-9]` precisely because NVML/monitoring processes (nvidia-smi, dcgm) open the latter but not UVM — so a stray monitor can't mask a total collapse.

Truth table (veto = suppress the override; fall-through = unchanged #826 logic):

| total | resolvable | uvm_holders | Interpretation | Action |
|---|---|---|---|---|
| >0 | 0 | >0 | Regime X, live workers under host ids (#813/#816) | **VETO**, streak→0 |
| >0 | 0 | 0 | Total collapse — no live CUDA holder anywhere (#664, TP=1 / all-dead) | fall through (#826 fires on stale+2 ticks) |
| >0 | >0 | any | Regime M — /proc signal informative; flagged PIDs are genuinely reaped (#664 with surviving siblings) | fall through |
| unknown/0 | any | any | Degraded probe / no compute apps | fall through |
| >0 | 0 | unknown | UVM scan failed | fall through (fail toward CURRENT behavior) |

Every failure of the new signals degrades to the current #826 behavior — never to more false positives, never to disabled TP detection.

### 4.1 Pod-side probe heredoc (`gpu_probe`, lines 1087–1107)

Replace the zombie while-loop with a counting version + a guarded UVM scan (near-real code; f-string fragments as in the current file):

```sh
# inside the existing `if command -v nvidia-smi` branch
ZOMBIE=''; GPU_PIDS_TOTAL=0; GPU_PIDS_RESOLVABLE=0;
while IFS=, read -r zpid zmem; do
  zpid=$(echo "$zpid" | tr -d " ");
  zmem=$(echo "$zmem" | tr -d " ");
  case "$zpid" in ""|*[!0-9]*) continue ;; esac;
  case "$zmem" in ""|*[!0-9]*) zmem=0 ;; esac;
  GPU_PIDS_TOTAL=$((GPU_PIDS_TOTAL+1));
  if [ -d /proc/$zpid ]; then
    GPU_PIDS_RESOLVABLE=$((GPU_PIDS_RESOLVABLE+1));
  elif [ "$zmem" -ge {ZOMBIE_GPU_MEM_MIN_MIB} ]; then
    ZOMBIE="$ZOMBIE $zpid";
  fi;
done <<EOF
$(nvidia-smi --query-compute-apps=pid,used_memory --format=csv,noheader,nounits 2>/dev/null)
EOF
UVM_HOLDERS=unknown;
if [ -n "$ZOMBIE" ]; then
  UVM_HOLDERS=0;
  for p in /proc/[0-9]*; do
    if ls -l "$p/fd" 2>/dev/null | grep -q "nvidia-uvm"; then
      UVM_HOLDERS=$((UVM_HOLDERS+1));
    fi;
  done;
fi;
echo "ZOMBIE_GPU_PIDS=$(echo $ZOMBIE | tr -s ' ')";
echo "GPU_PIDS_TOTAL=$GPU_PIDS_TOTAL";
echo "GPU_PIDS_RESOLVABLE=$GPU_PIDS_RESOLVABLE";
echo "NVIDIA_UVM_LIVE_HOLDERS=$UVM_HOLDERS";
```

Notes:
- The zombie condition is semantically identical to today's (`>= floor AND not in /proc`), restructured as `elif` so the same loop counts.
- The UVM scan runs ONLY when a zombie candidate exists (`-n "$ZOMBIE"`), so healthy matched-regime ticks pay zero cost; a mismatched-regime pod pays ~1–2 s per tick (a few hundred procs × one `ls -l | grep` each), inside an SSH probe that already tails 4×500 log lines.
- The `else` branch (no nvidia-smi) additionally emits `GPU_PIDS_TOTAL=unknown`, `GPU_PIDS_RESOLVABLE=unknown`, `NVIDIA_UVM_LIVE_HOLDERS=unknown` alongside the existing empty `ZOMBIE_GPU_PIDS=`.
- Dying-mid-scan procs: `ls -l ... 2>/dev/null` skips them (fail toward not counting — i.e. toward #826 fall-through).

```python
def _parse_probe_count(value: str | None) -> int | None:
    """Parse a probe count ("4", "", "unknown", garbage) to a non-negative
    int; None = no signal (caller falls back to the #826 behavior)."""
    if not value or value == "unknown":
        return None
    try:
        n = int(value)
    except ValueError:
        return None
    return n if n >= 0 else None
```

## 11. Decision Rationale

N/A — no model training, no hyperparameters. Load-bearing DESIGN choices instead:

- **Probe-accuracy over veto-terms.** Source: `_apply_zombie_override` docstring (lines 2933–2936, #826) + call-site lines 3306–3327 — in the stale-log regime `running` is only reachable via the CPU rescue, so `cpu_advancing`/proc-liveness vetoes structurally kill the #664 TP.
