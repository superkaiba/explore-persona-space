<h1>Plan — Issue #779: Beat Persona-Vectors' prompt-projection monitoring on Qwen-2.5-7B</h1>

<section class="plan-tldr">
<h2>0.0 TL;DR (plain English)</h2>
<ul>
<li><strong>What I'll run:</strong> The Persona Vectors paper predicts how a chatbot will behave (evil / sycophantic / making-things-up) by reading its internal state right before it starts answering, then dotting that state against a "trait direction". That trick works across obviously-different prompts but barely works when the prompts are all similar. I'll test two ways to read the trait more sharply on Qwen-2.5-7B: (R1) instead of using the raw before-answering state, first learn a small map that turns "what the prompt looks like" into "what the answer will look like inside the model", then read the trait off that prediction — trained on totally different prompts than I test on; and (R2) instead of reading before the answer, read the trait off the model's <em>actual answer as it's being written</em>, pooling over all the answer's words (average, peak, etc.).</li>
<li><strong>What I expect:</strong> R2 (reading the real answer) will clearly beat the paper's before-answer baseline — that's almost cheating since it sees the answer, so it sets a ceiling. R1 (predicting the answer from the prompt) is the hard, interesting one: I expect it to recover a chunk of R2's advantage while still being a pure before-generation predictor, especially for the harder-to-read traits where the paper's baseline collapses (hallucination within-condition is only 0.25).</li>
<li><strong>What would change my mind:</strong> If R1 does no better than the raw baseline, that says the prompt state simply doesn't carry the answer's trait content — the paper's ceiling is the real ceiling and you can't do better before the model speaks. If a plain <em>linear</em> learned map already captures the whole R2 ceiling, that would say the prompt→answer relationship is boringly linear and there's no room for a fancier model.</li>
</ul>
</section>

<section class="plan-summary">
<h2>0. Plan Summary (technical)</h2>
<p><strong>Training:</strong> NO model fine-tuning. Re-extract Persona Vectors <code>r_B</code> (arXiv 2507.21509 recipe, all 28 layers, response-avg, judge-filtered) for 3 traits (evil / sycophancy / hallucination) on Qwen-2.5-7B-Instruct. Fit a behavior-agnostic context→answer-profile map <code>h: c_x → v(x)</code> (ridge / kernel-ridge / MLP) on real user prompts (LMSYS-Chat-1M), reconstructing the full mean-response activation, never the trait. R1 monitors via <code>⟨h(c_x), r_B⟩</code>; R2 monitors via pooled projection of the actual generation's per-token activations onto <code>r_B</code> (mean / max / top-k / last). <br>
<strong>Hyperparameters:</strong> r_B: 5 pos/neg system-prompt pairs, 20 extraction Qs, 10 rollouts/arm, temp 1.0, judge-filter >50/<50 <em>(Source: persona-vectors-recipe.md / arXiv 2507.21509 App.)</em>. h: ridge λ by GCV; MLP 1 hidden layer 512 GELU, AdamW lr 1e-3, ≤300 epochs early-stopped <em>(Source: #658 / #722 vectorized_mlp_skill LOCO precedent)</em>. Judge: N=5 graded 0–100 draws, temp 1.0, drop-never-coerce <em>(Source: llm-judging.md rule 4 + persona-vectors-recipe.md step 4)</em>. Eval rig: 8 system prompts × {0,5,10,15,20}-shot = 40 conditions/trait, 10 rollouts/config/question, 40 eval questions/trait <em>(Source: arXiv 2507.21509 §Monitoring + App. verbatim)</em>. <br>
<strong>Baselines / controls:</strong> PV raw <code>⟨c_last, r_B⟩</code> (the paper baseline, within-condition r reproduced: evil .511/.735, syc .669/.813, halluc .245/.400); trait-fit linear probe on <code>c_x</code> (linear-case upper bound); R2 oracle <code>⟨v(x), r_B⟩</code> (ceiling). <br>
<strong>Loss surface:</strong> N/A — no fine-tuning. The h-map's regression loss (MSE / PCA-MSE / cosine) is over the reconstructed mean-response activation vector, NOT the trait scalar. <br>
<strong>Compute:</strong> one 8×H100 pod, data-parallel (8 single-GPU CUDA_VISIBLE_DEVICES workers, NOT TP=8) for the generation + activation-caching burst (~10 wall-h → released), + judge on Anthropic Batch API (0 GPU), + regression fits on 1×A100 or cpu-bigmem. <code>Estimated GPU-hours (total): 20</code>. <br>
<strong>Evaluation:</strong> primary = within-condition Pearson (matched to PV) on held-out contexts (R1: held-out behaviors too); success = R1 beats PV raw baseline by ≥ +0.05 mean within-condition r on ≥2 of 3 traits, R2 mean beats it by ≥ +0.10. Secondary = AUROC / top-k precision (detection framing). <br>
<strong>Risks:</strong> (1) R1's learned map may not beat the raw projection if the prompt state simply lacks the answer's trait content (Step-0 oracle gate quantifies the headroom before R1 is fit); (2) LMSYS-Chat-1M is HF-gated <span class="flag">(auto-gated; must verify token access — WildChat-1M ungated fallback)</span>.</p>
</section>

<h2>1. Goal</h2>
<p>Verbatim from <code>frontmatter.goal</code>: <em>On Qwen-2.5-7B under Persona Vectors' monitoring rig, test whether trait-expression prediction beats PV's last-prompt-token projection baseline by (R1) routing the projection through a learned behavior-agnostic context→answer-profile map (pre-generation) and (R2) pooling the persona-vector projection over the actual generation's activations (post-generation), evaluated on held-out contexts and behaviors.</em></p>
<p>Persona Vectors (arXiv 2507.21509) monitors a trait by projecting the last-prompt-token activation onto a persona vector, <code>⟨c_last, r_B⟩</code>, and predicting the response's trait score. Their <em>overall</em> correlations are strong (r=0.75–0.83) but their <em>within-condition</em> correlations — the operationally relevant regime, "among prompts of the same type, which one produces a more evil response" — collapse (evil 0.511, hallucination 0.245 for system-prompt elicitation). This task tests two theory-motivated ways to sharpen that read: a learned pre-generation context→profile map (R1) and post-generation activation pooling (R2). Both are direct instantiations of assumptions in the project's leakage-theory paper (§2 below), so a positive result advances both the monitoring application and the theory that underwrites the whole leakage-prediction program.</p>

<h2>2. Prior work</h2>

<h3>2.1 Formalization against the leakage-theory paper (<code>~/overleaf-6a2df2d2/main.tex</code>)</h3>
<p>The theory paper decomposes trait expression into a context side and a behavior side and posits four assumptions this task tests <em>directly and cheaply</em> (the paper itself flags A2 as "Worth testing right now: Yes… all other assumptions hinge on this" and A4 as "Easy to test and can give us layer information"):</p>
<table>
<tr><th>Theory assumption</th><th>Statement (paraphrased from main.tex)</th><th>What #779 tests</th></tr>
<tr><td><strong>A2 — activation summary</strong> (<code>a:activation-summary</code>)</td><td>The relevant summary of the context-induced profile is the mean answer-token residual activation, <code>v_θ(C) = E_{x∼C}[ā_θ(x)]</code>.</td><td>R2's estimator IS <code>v(x)</code> = mean-response activation; the oracle <code>⟨v(x), r_B⟩</code> tests whether A2's summary linearly reads the trait (jointly with A3).</td></tr>
<tr><td><strong>A3 — linear read-out</strong> (<code>a:linear-readout</code>)</td><td>Each behavior is an approximately linear read-out of the summary: <code>Expr(C,B) ≈ r_B^T v_θ(C)</code>. The paper explicitly lists "mean of D_B minus mean of D_B̄ (inspired by persona vectors)" as the expected-best <code>r_B</code>, and "sweep all layers to see which predicts expression best."</td><td>Every read-out in R1/R2 is <code>r_B^T (·)</code> with the persona-vectors <code>r_B</code>; the all-layer read-out sweep IS the paper's requested "which layer predicts expression best" experiment.</td></tr>
<tr><td><strong>A4 — context predicts profile</strong> (<code>a:context-summary-sufficiency</code> + <code>a:context-vectorization</code>)</td><td>A pre-finetuning context summary predicts the answer-side summary: <code>v_θ(C) ≈ h_θ(c_C)</code>. Special case linear: <code>h(c) ≈ Mc</code>. "<strong>Testable: Yes. Train a MLP to predict the context-induced profile with different vectors from the context… see if nonlinear map works much better than linear map.</strong>"</td><td>R1's <code>h</code> IS exactly the paper's <code>h_θ</code>. The singleton-condition corollary (<code>a:context-vector-coherence</code>, eq. 1) reduces to <code>ā_θ(x) ≈ h(c_x)</code> — literally R1's per-context training target. The ridge-vs-MLP arm IS the paper's linear-vs-nonlinear test; the linear-fold <code>r̃_B = M^T r_B</code> is the paper's <code>r_B^T M c_C</code>.</td></tr>
</table>
<p>So R1 = A4 (+ A3 read-out) and R2 = A2 (+ A3 read-out). A positive R1 result is direct empirical support for A4's non-trivial content (that the pre-generation context state carries recoverable answer-profile information beyond what the raw projection extracts); a positive R2 result supports A2+A3 (that the mean-response summary linearly encodes the trait). The Step-0 oracle gate (<code>⟨v(x),r_B⟩</code> vs trait score, within-condition) is precisely the paper's A2/A3 "worth testing right now" check.</p>

<h2>3. Hypothesis + falsification</h2>
<h3>R1 (pre-generation learned map)</h3>
<ul>
<li><strong>H1:</strong> A learned behavior-agnostic map <code>h</code> improves within-condition trait prediction over PV's raw <code>⟨c_x, r_B⟩</code>, on held-out contexts AND held-out behaviors (leave-one-behavior-out for <code>r_B</code>). <strong>Confirm:</strong> mean within-condition Pearson <code>⟨h(c_x), r_B⟩</code> exceeds PV raw by ≥ +0.05 (bootstrap 95% CI excludes 0) on ≥2 of 3 traits. <strong>Falsify:</strong> <code>h</code> gives no improvement (Δ CI includes 0) on ≥2 of 3 traits — the prompt state carries no recoverable answer-profile signal beyond the raw projection.</li>
<li><strong>H1b (linear vs nonlinear, the A4 sub-test):</strong> A nonlinear <code>h</code> (MLP) beats a linear <code>h</code> (ridge/KRR) by ≥ +0.03 within-condition r. <strong>Falsify:</strong> ridge ≈ MLP (Δ CI includes 0) — the context→profile map is effectively linear (the linear-fold <code>r̃_B = M^T r_B</code> deploys at PV cost with the gain).</li>
</ul>
<h3>R2 (post-generation pooling)</h3>
<ul>
<li><strong>H2:</strong> Pooling the projection over the actual generation beats PV's prompt projection. <strong>Confirm:</strong> best pooling (over mean/max/top-k/last × layers) mean within-condition r exceeds PV raw by ≥ +0.10 on ≥2 of 3 traits. <strong>Falsify:</strong> no pooling beats the prompt projection — the generation carries no trait signal the prompt lacks (implausible; a near-tautological ceiling).</li>
<li><strong>H2b (max vs mean):</strong> MAX pooling beats MEAN as a <em>detector</em> (higher AUROC / top-k precision) while MEAN wins the aggregate Pearson. <strong>Falsify:</strong> MEAN dominates both metrics — no localized-spike advantage.</li>
</ul>
<h3>Step-0 gate (the oracle headroom test)</h3>
<p>Before fitting <code>h</code>: if the oracle <code>⟨v(x), r_B⟩</code> (R2 mean) does NOT beat PV raw <code>⟨c_x, r_B⟩</code> within-condition by ≥ +0.05 on ≥2 traits, R1 has no headroom to recover (there is no gap between prompt and answer projection to close) — Stage 1 R1 fit is descoped to ridge-only + reported as "no oracle headroom", and R2 becomes the headline. This is a science gate, not a compute kill (§7).</p>

<h2>4. Design</h2>

<h3>4.0 Why code, not a model call?</h3>
<p>R1's <code>h</code> and every read-out are numeric regressions / dot products over cached activation tensors — no unstructured-data heuristic is involved. The one model-call-vs-code decision is the trait scorer: it scores unstructured generated text for a behavior, and per project policy (llm-judging.md, no-substring-match memory) it MUST be a Claude judge, not a code heuristic. So: <strong>judge = model call</strong> (Sonnet graded 0–100 via Batch API); <strong>everything else = code</strong> (deterministic, vectorized over tensors, and the h-fit needs closed-form ridge / batched SGD that a model call cannot provide). No other unstructured-data heuristic in the design.</p>

<h3>4.1 Data source + realism tier</h3>
<ul>
<li><strong>r_B extraction data:</strong> the paper's own released trait definitions + generated system-prompt/question artifacts (tier 2 — the paper's released data; regenerated per persona-vectors-recipe.md from the trait name+description via the Sonnet generator since PV released code but not the vectors). Data-realism: tier 2.</li>
<li><strong>Eval contexts (the DV distribution):</strong> PV's 8-way system-prompt sweep + 0/5/10/15/20-shot, verbatim (tier 2 — the paper's released monitoring corpus; the 8 system prompts per trait are fetched verbatim from arXiv App. and stored in the config, never paraphrased). Data-realism: tier 2.</li>
<li><strong>Training contexts for <code>h</code>:</strong> LMSYS-Chat-1M (real user prompts — <strong>tier 1, real-world data</strong>). Fallback if the gated dataset is inaccessible under our token: WildChat-1M (also real user conversations, ungated — tier 1) or UltraChat-200k (tier 2, already used by #594). The single hard invariant: the exact PV eval monitoring contexts are held out from <code>h</code>'s training in ALL corpus arms.</li>
</ul>
<p><strong>Contrastive-negatives / on-policy-completions rules: N/A — this is a monitoring experiment, not behavior implantation. No LoRA training, no fine-tuning of Qwen at all.</strong> (The <code>r_B</code> extraction's pos/neg system-prompt structure is governed by persona-vectors-recipe.md, which composes contrastive-negatives for the extraction rollouts — those ARE on-policy sampled rollouts by construction.)</p>

<h3>4.2 Persona vector <code>r_B</code> extraction (persona-vectors-recipe.md, all 28 layers, 3 traits)</h3>
<p>Reuse the pipeline in <code>scripts/issue623_extract_sycophancy_vector.py</code> (already implements the recipe on Qwen), generalized to 3 traits and to the recipe's <strong>response-avg</strong> extraction position (not #623's last-token deviation — #779 is the read-out/prediction+monitoring regime and uses the paper's default response-avg <code>r_B</code>). Steps, verbatim from the recipe:</p>
<ol>
<li>Inputs: trait name + description for evil / sycophancy / hallucination (the paper's 3 main-text traits).</li>
<li>Artifacts via one Sonnet generation from the paper's verbatim generation-prompt template (fetched via arXiv MCP <code>get_paper_section 2507.21509 "Direction extraction pipeline"</code>): 5 pos/neg system-prompt pairs + 40 questions split 20 extraction / 20 eval + 1 trait-eval rubric (fetched verbatim from "LLM-based trait expression score").</li>
<li>Generation: 10 rollouts under POS + 10 under NEG per extraction question, temp 1.0, vLLM.</li>
<li>Judge-filter: Sonnet 0–100, keep POS>50 / NEG<50; <strong>REFUSAL/non-numeric/out-of-[0,100] DROPPED from both arms, never coerced; report per-arm dropped count.</strong></li>
<li>Activation position: residual stream at EVERY layer (0..27), averaged over RESPONSE tokens, per kept rollout (hook-based capture via <code>analysis/extraction.py::extract_layer_activations</code>).</li>
<li><code>r_B[ℓ]</code> = mean(kept POS activations) − mean(kept NEG activations), per layer → <code>(28, 3584)</code> per trait.</li>
<li><strong>Layer-selection regime: READ-OUT / PREDICTION</strong> (not steering). Sweep all layers, select by predictivity of trait expression — exactly the paper's A3.3 read-out regime and #658's regime. NOT the single steering-selected layer. Stated per the recipe's step-7 requirement.</li>
</ol>
<p>Output: <code>data/issue_779/r_b/{evil,sycophancy,hallucination}.pt</code> <code>(28,3584)</code> + kept/dropped counts JSON. <strong>Not reused from #661/#623</strong> — those were last-prompt-token vectors built for a different regime; the fitness check (§ Reproducibility / Assumptions) fails (b) recipe-position match, so fresh extraction is required.</p>

<h3>4.3 Shared data-collection pass (produces R1 inputs, R2 inputs, and the DV in one burst)</h3>
<p>Two forward-pass sweeps on the 8×H100 pod, both data-parallel across 8 workers (each worker owns a shard of contexts, <code>CUDA_VISIBLE_DEVICES=k</code>, own vLLM engine + own HF model for hooks):</p>
<p><strong>(A) Eval contexts</strong> (the 40 conditions/trait × 40 questions/trait, 3 traits): for each (trait, system-prompt or n-shot condition, question):</p>
<ul>
<li>Capture <code>c_x</code> = last-prompt-token activation AND mean-prompt-token activation at all 28 layers (the R1 baseline + h input).</li>
<li>Generate 10 rollouts (vLLM, temp 1.0, <code>max_new_tokens=1024</code>).</li>
<li>For each rollout: teacher-force back through the HF model with hooks, capture (i) <code>v(x)</code> = mean-response activation (R2 mean oracle + h target), and (ii) R2's pooled per-token projections — <strong>dot each response-token activation with every-layer <code>r_B</code> and accumulate mean / max / top-k(=top-3 mean) / last SCALARS</strong> (no per-token tensor storage; ~0 extra memory, the design's ~0-GPU R2 claim).</li>
<li>Judge each rollout: Sonnet graded 0–100, N=5 draws/rollout via Batch API → the DV (mean trait score per rollout, then per (condition,question) averaged over 10 rollouts, matching PV).</li>
</ul>
<p><strong>(B) Training contexts for <code>h</code></strong> (LMSYS prompts, ≥5000 after dedup/holdout, single temp-1 rollout each — <code>h</code> reconstructs the FULL profile, not the trait, so no judge needed here): capture <code>c_x</code> (last + mean prompt) and <code>v(x)</code> (mean-response) at all 28 layers. This is the <code>h</code> training set: inputs <code>c_x</code>, targets <code>v(x)</code>. Behavior-agnostic — no <code>r_B</code>, no judge.</p>
<p><strong>Storage discipline:</strong> Step-0 caches ALL 28 layers on a 500-context subset for layer selection (~500×28×3584×2 = ~100 MB); the full corpus then caches only the selected read-out layer(s) (≤3 layers) to stay well under the 50 GB VM footprint. Per-worker checkpoint-per-shard with resume-skip (reuse #594's pattern). Reuse <code>scripts/issue594_extract_context_vectors.py</code> capture path (hook on <code>model.model.layers[i]</code>, pre-final-norm) + <code>eval/generation.py::generate_persona_completions</code> for rollouts + <code>eval/batch_judge.py</code> for judging.</p>

<h3>4.4 R1 — fit the context→profile map <code>h</code></h3>
<p>New module <code>src/explore_persona_space/experiments/issue_779/fit_h.py</code>. Fitter ladder (reusing <code>analysis/vectorized_mlp_skill.py</code>):</p>
<pre>
def fit_h(C_train, V_train, C_eval, kind, objective, layer_in, layer_out):
    # C_train: (N_train, L_in*H) context vecs; V_train: (N_train, H) mean-response @ layer_out
    # kind in {ridge, kernel_ridge, mlp}; objective in {mse, pca_mse_k, cosine}
    # ridge: closed-form (analysis/vectorized_mlp_skill.ridge_predict_loco_raw), lambda by GCV
    # kernel_ridge: RBF, bandwidth = median heuristic; Nystrom if N_train>20k
    # mlp: fit_batched_loco_mlp (1 hidden 512 GELU, AdamW lr 1e-3, <=300 epochs, early-stop on val)
    # returns h(C_eval): (N_eval, H) predicted mean-response profile
</pre>
<ul>
<li><strong>Objectives:</strong> (a) full-vector MSE (theory-faithful, keeps magnitude); (b) top-k PCA-MSE on <code>V</code> (denoised; report fraction of <code>r_B</code> in the top-k profile subspace — the A1/A2 low-rank test); (c) cosine (direction-only; MLP-side only, no closed form).</li>
<li><strong>Read-out both ways:</strong> dot <code>⟨h(c_x), r_B⟩</code> AND cosine <code>cos(h(c_x), r_B)</code>, both reported (#493: cosine was the winner).</li>
<li><strong>Layer grid:</strong> read-out layer = <code>h</code> output layer (tied); swept over all 28 layers for ridge/KRR (cheap); <code>h</code> input layer swept over all layers + input-layer combos (concatenation) with last-vs-mean pooling. MLP restricted to the PV/Step-0-selected read-out layer(s) (compute).</li>
<li><strong>Generalization (the load-bearing invariant):</strong> <code>h</code> trained ONLY on LMSYS contexts disjoint from the PV eval contexts; behaviors held out via leave-one-behavior-out on <code>r_B</code> (fit <code>h</code> is behavior-agnostic so LOBO is automatic — <code>h</code> never sees any <code>r_B</code>; the claim "one map, unseen contexts, unseen behaviors" holds by construction). Report per-trait held-out within-condition r.</li>
<li><strong>Corpus 3-level factor (Stage 2):</strong> (1) generic LMSYS only; (2) generic + other-trait data (behavior holdout preserved); (3) generic + eval-trait data (in-domain, weaker-generalization). Eval contexts held out in all three.</li>
</ul>

<h3>4.5 R2 — generation-activation pooling</h3>
<p>Already computed in the shared pass (§4.3 A): for each (trait, condition, question, rollout) the mean / max / top-k / last pooled projection onto every-layer <code>r_B</code>. Compute within-condition Pearson of each pooling×layer against the DV; also AUROC / top-k precision. <strong>Single-variable change:</strong> vs PV's <code>⟨c_last, r_B⟩</code>, R2 changes ONLY the projection INPUT (pooled generation activations instead of the last prompt token). Same <code>r_B</code>, same eval rig, same judge, same model, same layers.</p>

<h2>7. Decision Gates</h2>
<p>The run is a staged pipeline &gt; 4 wall-h with a genuinely uncertain headline (no prior established R1's direction at this rig), and two cheap intermediate signals each rule out expensive downstream work — so gates are warranted, but kept minimal (two, jointly satisfiable, each with a grounded sign):</p>
<ul>
<li><strong>Gate 0 (Step-0 science gate, NOT a compute kill):</strong> if the oracle <code>⟨v(x),r_B⟩</code> does not beat PV raw within-condition by ≥ +0.05 on ≥2 traits, R1 has no headroom → descope R1 to ridge-only + report "no oracle headroom"; R2 becomes headline. Sign grounded: A2/A3 theory + PV's own overall-vs-within gap predict the oracle SHOULD beat the raw projection (the answer state carries more trait content than the prompt state); a null here is itself a reportable theory result. Cheap: 500-context subset, ~1 wall-h.</li>
<li><strong>Gate 1 (rig-validation halt):</strong> if our reproduced <code>pv_raw</code> within-condition r is &gt; 0.10 off the PV published table, the rig/extraction diverged → halt Stage 2, diagnose the extraction (do NOT report gains against a broken baseline). Sign/threshold grounded: PV's table IS the ground truth; ±0.10 is the noise band from #511's N-scaling.</li>
</ul>
<p>Jointly satisfiable: Gate 0 gates R1 scope, Gate 1 gates Stage-2 launch; they act on different measurements, no contradiction. Stage 2 (ablations) runs only on configs that clear Stage 1's headline.</p>
