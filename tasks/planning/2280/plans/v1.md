## 2. Root cause (established, with evidence)

`earlyoom` (active, `EnvironmentFile=/etc/default/earlyoom`) runs with:

```
EARLYOOM_ARGS="-m 10 -s 10 -r 3600 --prefer (^|/)(pytest|python3?)$ \
  --avoid (^|/)(sshd|systemd|dockerd|node|claude|happy)$|^[0-9]+[.][0-9]+[.][0-9]+$ -n"
```

**2.1 Timestamp match.** VM tz = `America/Los_Angeles` (PDT, UTC-7). The body reports
`issue2221_build_mix.py` attempt 1 died rc=143 at 16:24:40Z. The earlyoom unit journal,
at `Aug 13 09:24:40` PDT — the same second:

```
mem avail: 12849 of 128804 MiB ( 9.98%), swap free: 0 of 0 MiB ( 0.00%)
low memory! at or below SIGTERM limits: mem 10.00%, swap 10.00%
sending SIGTERM to process 1838073 uid 1001 "python3": badness 972, VmRSS 1054 MiB
process exited after 0.1 seconds
```

The body's second window (two `file_infra_task.py` kills ~00:42-44Z on 08-14 =
17:42-44 PDT on 08-13) matches a sustained sweep: `"python"` badness 973 (1395 MiB),
`"python3"` 966 (53 MiB), 966 (48 MiB), and a `chrome` 800 — all SIGTERM inside 11 s,
MemAvailable oscillating 9.47-10.00%.

**2.2 The selection mechanism — the +300 bonus IS the whole criterion.** `man earlyoom`:
`--prefer REGEX  prefer killing processes matching REGEX (adds 300 to oom_score)`.
Measured on this box (this session, `/proc/<pid>/oom_score`): **every** process reports
`oom_score = 666` with `oom_score_adj = 0` — the Bash tool-call shell, the `claude`
binary, both `node` parents, `systemd --user`, and a fresh `python3` alike. Because the
baseline is flat, the +300 dominates ranking completely. Journal badness values confirm
it: any python scores 966-976 regardless of size, beating a 3728 MiB `java` (686) and a
660 MiB Claude session (669-670).

**Consequence, which no in-repo doc currently states:** RSS is nearly irrelevant
*across* process classes. A 44 MiB, sub-second python is a top-priority victim the
instant a sweep fires — which is exactly why `file_infra_task.py --help` dying "within
seconds" read as inexplicable. Size only breaks ties *within* the python class.

**2.3 The `setsid` discriminator is a TIMING CONFOUND, not a mechanism.** Measured this
session, same binary via both launch shapes:

```
in-session:      comm=python3 adj=0 score=666 pid=2535902 sid=2535874 pgid=2535897
setsid-detached: comm=python3 adj=0 score=666 pid=2535908 sid=2535904 pgid=2535904
```

Identical `comm`, `adj`, and `oom_score`; only `sid`/`pgid` differ — and earlyoom reads
none of those. No harness-set `oom_score_adj` exists anywhere in the ancestry (all 0).
Corroborating: the same sweeps killed `chrome`, `java`, and the `2.1.219` Claude
binaries — none of which are foreground python children of a session shell. earlyoom
fires in bursts at the floor, so a rerun seconds-to-minutes later simply lands outside
the sweep. **The body's three candidate suspects — harness child-reaping at tool-call
boundaries, a janitor `pkill` on argv patterns, systemd session-scope cleanup — are all
ruled out.**

**2.4 Why the body's own checks missed it (three traps).**
(a) "journalctl clean" — the kernel OOM killer logs to dmesg with `oom_score`; earlyoom
logs to its own *unit* journal with `badness`. A dmesg / `journalctl -k` read
structurally cannot see an earlyoom kill.
(b) "53 GB free" is DISK; the binding quantity was MemAvailable at 9.5-10.0% of 128 GB
(~12.2-12.9 GB), with **zero swap** at the time.
(c) The `setsid` A/B (§2.3).

**2.5 Why it stopped.** A 64 GB swapfile was created 2026-08-14 08:29:08 PDT
(`/mnt/eps-data/swapfile`); earlyoom restarted 8 s later. The last real victim kill is
`Aug 14 08:16:07` — 13 minutes before the swapfile. Victim-kill counts within the
journal's retention window (which begins Aug 13 02:17, so earlier days are unknown, not
zero): **363 on Aug 13, 287 on Aug 14, then 0 for Aug 15-22.** Current state:
MemAvailable 48-70%, swap ~45% free. The swap is durable — `/etc/fstab` line 4
(`/mnt/eps-data/swapfile none swap sw,nofail 0 0`) plus an active
`mnt-eps\x2ddata-swapfile.swap` systemd unit.

**2.6 NEW finding — the documented `choom` protection is void for python.** `man
earlyoom`: *"For processes matched by `--prefer`, negative `oom_score_adj` values are
not taken into account, and the process gets an effective oom_score of at least 300"*
(upstream issue 159). Every `pytest` / `python` / `python3` on this VM is
`--prefer`-matched, so the `sudo -n choom -n -600` protection that
`.claude/rules/gotchas.md` line 60, SKILL.md § "Detached VM-side long compute phases",
and the Step 9c pytest self-choom (#1045) all prescribe **buys nothing for exactly the
processes it is meant to protect**. Verified empirically that `choom` applies
(`adj: 0 → -600`, kernel `oom_score: 666 → 267`, rc=0); the earlyoom-side discard is
documented behavior, not something this task observed a kill for — inducing memory
pressure to observe one would SIGTERM other sessions' live work and is out of bounds
(§7). This is the highest-value correction in the task: the current text grants false
confidence.

**2.7 Residual regression path.** earlyoom remains armed with the same blanket python
`--prefer`. The swapfile's fstab entry carries `nofail`, so a boot where
`/mnt/eps-data` fails to mount activates **no swap, silently** — restoring the exact
Aug-13 regime (zero swap, 10% floor, every python a preferred victim) with no alarm.
Nothing in the repo reads swap state today (verified: no `swapon` / `SwapTotal` /
`swap_memory` reader under `scripts/` or `src/`).

phase is about to allocate, and post-hoc detection is already covered by #849's

a launch-time WARN covers. The watcher-side escalate-only variant is the named
alternative if the critic judges preflight insufficient.
