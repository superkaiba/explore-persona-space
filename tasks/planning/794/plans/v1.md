# Plan — issue #794: retry HF recursive tree-listing 504s in `list_repo_files_complete`

<section class="plan-tldr">

## 0.0 TL;DR (plain English)

- **What I'll run:** No experiment — this is a small code fix. When we upload a big
  batch of files to Hugging Face, the code checks afterward that the files really
  landed. That check reads the whole repo's file list, and on our big repos that
  read sometimes times out (a "504") — which makes the code think a *successful*
  upload *failed* and crash the whole run. I'll make that read retry a few times
  before giving up, the same way the upload step already does.
- **What I expect:** The one-line "list the repo" read gets wrapped in the retry
  helper the upload side already uses, so a transient timeout on any page of the
  listing is retried instead of blowing up. Every place that reads the repo's file
  list (four call sites) benefits, not just the two upload-verification spots.
- **What would change my mind:** If wrapping the read changed any existing
  behavior — e.g. a real permission error or a genuinely-missing repo started
  getting retried into a long stall instead of failing fast. It won't: the retry
  helper re-raises non-timeout errors immediately, so only the timeout case
  changes.

## 1. Goal

Post-upload verification (and two exogenous listings) call
`list_repo_files_complete`, which paginates `api.list_repo_tree(recursive=True)`.
`huggingface_hub.utils._pagination.paginate` retries ONLY HTTP 429 on follow-up
cursor pages, so a **504 Gateway Timeout** on any cursor page of a LARGE repo
propagates straight through. Inside `_upload` / `_upload_folder_filtered` that 504
is caught by the outer `try/except Exception` → the function logs "Upload failed"
and returns `""`, and the caller (`upload_dataset_directory`) raises
`RuntimeError("upload_dataset returned '' ... HF Hub upload failed silently")` —
**even though the upload itself succeeded**. This is the reproducible 504
verification storm the task names. The fix: make the listing retry transient 504s
via the retry helper the upload sides already use, so a successful upload is never
reported as a false failure.

## 2. Prior Work

- `gotchas.md` § "HF recursive tree listing 504s are un-retried" (added by #749)
  documents the trap exactly, and its remedy: *"Wrap any post-upload verify listing
  on a large repo in the SAME transient-5xx retry as the upload (#658)."* #794 is
  the code fix that remedy points at. **DO NOT re-touch `gotchas.md`.**
- `_is_transient_upload_error` (`hub.py` L513-534) already recognizes the exact
  transient set: status codes 429/500/502/503/504, plus message substrings
  ("504"/"502"/"503"/"500"/"gateway time-out"/"gateway timeout"/"timed
  out"/"timeout"/"connection"/"temporarily unavailable"). A cursor-page 504
  surfaces as an `HfHubHTTPError` with `.response.status_code == 504` (and "504" in
  the message), so it is already covered — the helper just was never applied to the
  read path.
- `_retry_upload` (`hub.py` L537-561, tested by `TestRetryUpload`, `tests/test_hub.py`
  L397-499) is a 6-attempt exp-backoff wrapper (`sleep = min(180, 10·2^(n-1))`) that
  re-raises IMMEDIATELY on `_is_storage_quota_403` or any non-transient error, and
  re-raises the final exception after `max_attempts` (fail-loud). Its logic is
  generic transient-retry; only its NAME is upload-flavored. It already wraps the
  upload calls at L642 and L786.
- `huggingface_hub` pinned at **0.36.2** (verified). The `paginate` 429-only
  cursor-retry behavior holds for this version.

## 3. Hypothesis

Wrapping the `list_repo_tree` call in `list_repo_files_complete` with `_retry_upload`
makes a transient 504 on any cursor page retry with backoff and (in the common
case) succeed on a later attempt, so:

- **Confirm:** a `list_repo_files_complete` whose underlying `list_repo_tree` raises
  a 504 once and then yields the file set returns the file set (no propagation); and
  `_upload`'s verify step at L668 therefore returns the success URL, not `""`.
- **Falsify:** if the listing still propagated the 504 (retry not wired), or if a
  non-transient error (404/auth/`ValueError`) started being retried instead of
  re-raised on attempt 1.
- **Quantitative:** exhausted case re-raises after exactly `max_attempts` (6)
  attempts (5 sleeps), matching `_retry_upload`'s existing contract.

## 4. Design

### Decision: option (b) — retry inside `list_repo_files_complete`, not per-call-site.

| | (a) wrap the 2 verify sites (L668, L802) | (b) push retry into `list_repo_files_complete` |
|---|---|---|
| Blast radius | tighter (2 sites) | broader (all 4 sites) |
| Coverage | misses L1242 `list_hub_datasets` + L1306 `_hf_artifact_exists`, which 504-storm on the SAME `tree/main?recursive=true` endpoint | covers all 4 — the two verifies AND the two exogenous listings |
| Test surface | 2 patched call-site tests | 1 test surface (the function itself) |
| Gotcha alignment | partial | **exactly what the gotcha prescribes** ("wrap any … verify listing") |
| Correctness | fine | fine — the function is a pure read whose only transient failure mode is the transient set the helper handles |

**Choice: (b).** It is the gotcha-prescribed general fix, covers the two exogenous
listings the task flagged (L1242, L1306) at no extra cost, needs the smallest test
surface (one function), and cannot change any non-transient behavior because
`_retry_upload` re-raises non-transient errors on attempt 1.

**Note on the task's "L1306 `sync_models_pull`" reference:** there is no
`sync_models_pull` in `hub.py` (grep confirms zero matches). L1306 is
`_hf_artifact_exists` (the pre-launch carry-over existence gate). Its docstring
promises "genuine transport / auth errors propagate so the caller fails loud" — a
504 is a *transient* transport error, so retrying it (then propagating if it
exhausts) HONORS that contract, it does not violate it. No behavior change for the
genuine-missing case (a reachable repo missing the path still returns `False`; the
listing succeeds, no exception to retry).

### Exact diff sketch

**File: `src/explore_persona_space/orchestrate/hub.py`**

Inside `list_repo_files_complete` (L491-503), replace the direct comprehension over
`api.list_repo_tree(...)` with a `_retry_upload`-wrapped thunk. `_retry_upload` and
`RepoFile` are both already in scope (`_retry_upload` is defined at L537 — AFTER
this function textually, but that is fine: `list_repo_files_complete` is only ever
CALLED at runtime, by which point the whole module is loaded, so the forward
reference resolves).

```python
    from huggingface_hub.hf_api import RepoFile

    # list_repo_tree paginates tree/main?...&cursor=...; huggingface_hub's
    # paginate() retries ONLY 429 on cursor pages, so a 504 on any page
    # propagates. Wrap the paginated read in the same transient-retry helper the
    # upload sites use so a large-repo cursor-page 504 is retried, not fatal
    # (gotchas.md "HF recursive tree listing 504s are un-retried"; #794/#658).
    def _list() -> list[str]:
        return [
            entry.path
            for entry in api.list_repo_tree(
                repo_id=repo_id,
                repo_type=repo_type,
                revision=revision,
                recursive=True,
            )
            if isinstance(entry, RepoFile)
        ]

    files = _retry_upload(_list, what=f"list_repo_tree({repo_id})")
    return sorted(files)
```

Notes:
- `api.list_repo_tree(recursive=True)` returns a generator; the list-comprehension
  inside `_list()` MATERIALIZES it, so any cursor-page 504 raises *inside* `_list()`
  (i.e. inside the `_retry_upload` `try`), not lazily after return — the retry
  wraps the real failure point. (This is why the thunk must contain the
  comprehension, not just `return api.list_repo_tree(...)`.)
- Also update `_retry_upload`'s docstring (L538-541) with one clarifying clause:
  it is a generic transient-retry wrapper, now used for READS
  (`list_repo_files_complete`) as well as uploads; no rename (consumers are pinned
  by tests + workflow-invariant tests).

No other lines in `hub.py` change; the 4 call sites keep their exact signatures.

   `api.list_repo_tree.call_count == 2` (a full re-list per attempt), with one

   `_retry_upload`'s contract).

   faults" guarantee).
