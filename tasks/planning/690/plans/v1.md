# Plan — Issue #690: Auto-dispatch ripe `proposed` infra tasks (file-time spawn + always-on watcher sweep)

`kind: infra`. **Estimated GPU-hours (total): 0** — this is workflow/automation
code + routing-prose edits + tests. No model trains.

---

## 0. Plan Summary

- **What:** Close the orphaned-`proposed`-infra-task gap from BOTH ends. (1) A
  thin `scripts/file_infra_task.py` wrapper that FILES a `kind: infra`/`batch`
  task (delegates to `task.py new`) and, in the same call, attempts a
  best-effort `spawn_session.py spawn-issue --issue <N> --auto` — no-op'ing
  cleanly when no Happy daemon is reachable (pod-side/headless filers fall
  through to the backstop). (2) A NEW `proposed_infra_sweep_pass` in
  `autonomous_session_watch.py` (the 10-min cron) that adjudicates ripe
  `proposed` infra/batch tasks itself (no PM queue) and dispatches into free
  slots — reusing the EXISTING infra-drain pass's cap/occupancy/registration
  dedup primitives.
- **Hyperparameters:** N/A — no model training.
- **Compute:** `Estimated GPU-hours (total): 0`. Pure CPU workflow code.
- **Idempotency (the load-bearing invariant):** both paths dedup on
  issue-mapped registrations (`~/.eps-autonomous/{issue,manual-issue}-<N>.json`)
  — the SAME source of truth `spawn_session.py list` uses. The watcher sweep
  reuses the infra-drain pass's decision-time registration snapshot +
  pre-spawn byte-identity re-check. The file-time wrapper checks the
  registration BEFORE spawning.
- **Shared concurrency cap (3):** the watcher sweep and the existing
  infra-drain pass share ONE cap budget computed in ONE place per tick
  (occupied-active + pending across BOTH the PM-queue IDs and the sweep
  candidates), so the two passes cannot jointly overshoot 3.
- **Risks (top 2):** (a) a sub-second race between the synchronous file-time
  spawn and the very next watcher tick double-spawning — bounded to the
  acceptable single-spawn-window because both call sites check the same
  registration dedup; (b) the file-time wrapper must NOT bake spawning into
  `task.py`'s mutation core (would break the pod-side-shellout rule) — solved
  by making it a SEPARATE orchestration-layer script that pod-side code never
  invokes.
- **Evaluation:** pytest pins acceptance (a)-(d) + the on_hold/non-infra/
  unmet-predicate negatives.

## 1. Goal

A filed `proposed` `kind: infra` (or pure-code/ops `kind: batch`) task today
only auto-runs if a LIVE PM session does a STATUS pass (`research-pm.md` §444)
and writes it into `~/.eps-autonomous/infra-drain-queue.json`, which the
watcher's infra-drain pass then executes. With no PM session in the loop, a
ripe infra task orphans indefinitely — incident #684 sat at `proposed` ~17h.
Close the gap from both ends: (1) make "whoever files a ripe infra fix
dispatches it" the default at FILE time via a thin wrapper wired into the
routing surfaces, and (2) add an always-on watcher safety-net sweep that
adjudicates + dispatches ripe `proposed` infra tasks itself, catching anything
filed by a context that could not self-dispatch (pods, manual `task.py new`, a
crashed filer). Both ADD paths; the existing PM rule + infra-drain pass keep
working unchanged.

## 2. Prior work / existing surfaces

- **PM standing rule (`research-pm.md` §444-575).** The PM's STATUS-pass infra
  auto-dispatch: enumerate ripe `proposed` `kind: infra`/pure-code `batch`/
  `agent-ok` `analysis`, re-evaluate `predicate-<#N>-...` holds, dispatch ripe
  ones via `spawn-issue --issue <N> --auto` under a 3-session cap, and WRITE
  the adjudicated queue to `infra-drain-queue.json` (step 4b) for the watcher
  to drain between passes. This is the NUANCED ripeness judge — it stays the
  authoritative source for cross-issue predicate adjudication and dup-cluster
  consolidation. We do NOT touch its logic.
- **Watcher infra-drain pass (`autonomous_session_watch.py:6228 infra_drain_pass`,
  task #633).** EXECUTES the PM-written queue file with zero ripeness judgment
  (except mechanical predicate-hold promotion). It already owns every primitive
  the new sweep needs:
  - cap/occupancy: `_infra_drain_occupancy()` (`INFRA_DRAIN_OCCUPIED_STATUSES`,
    `INFRA_DRAIN_KINDS`), `_infra_drain_pending()`, `INFRA_DRAIN_CAP_DEFAULT=3`;
  - registration dedup: `_infra_drain_reg_snapshot()` (decision-time bytes),
    `_infra_drain_registrations()`, `_infra_drain_stale()`,
    `_dispatch_infra_drain()` (pre-spawn byte-identity re-check + `spawn-issue
    --auto` subprocess);
  - predicate semantics: `_parse_predicate_hold()`,
    `_satisfied_predicate_promotions()`,
    `INFRA_DRAIN_PREDICATE_SATISFIED_STATUSES`;
  - daemon gating: `_daemon_reachable()`, `_live_session_ids_or_none()`;
  - markers: `_post_progress_marker()` + a sentinel string.
  **The new sweep extends this machinery; it does NOT execute the PM queue.**
  The KEY difference: the infra-drain pass's candidate set + holds come FROM the
  PM queue file; the new sweep BUILDS its candidate set from
  `task.py list-by-status --status proposed` (filtered to drain-kinds) and reads
  each candidate's `predicate-<#N>-...` TAGS to gate (no PM queue needed).
- **`spawn_session.py`.** `spawn-issue --issue <N> --auto` POSTs to the Happy
  daemon, registers `~/.eps-autonomous/issue-<N>.json` on success.
  `_load_session_issue_map()` (the engine behind `list`) maps every live
  `{issue,manual-issue,campaign}-<N>.json` registration to its issue — the
  canonical "does this issue have a live session?" source of truth.
- **`task.py new`** (`cmd_create`, line 235) prints `#<new_id>` to stdout via
  `_safe_echo`; mutation core (`create_task`) holds `flock` + commits. It has
  NO knowledge of sessions — and must keep it that way (`task.py` branch-guards
  to `main` and is a forbidden pod-side shellout target;
  `tests/test_no_pod_side_task_py_shellout.py`).
- **`workflow-fix-on-bug.md` step 5-6.** The orchestrator currently FILES
  (`task.py new ...`) THEN separately SPAWNS (`spawn-issue --auto`). #690's
  change (1) is the generalization of exactly this two-step pattern into one
  wrapper call.

**Why a new mechanism is needed:** the PM-queue path requires a live PM
session to ADJUDICATE ripeness; the watcher infra-drain pass only EXECUTES what
the PM already adjudicated. Nothing autonomously adjudicates a freshly-filed
`proposed` infra task when no PM is running — so it orphans. (1) puts the
adjudication+dispatch at FILE time (the filer knows the task is ripe — it just
filed a concrete, ripe fix), and (2) adds an independent watcher adjudicator as
the backstop.

## 3. Design — concrete file-level changes

### (1a) File-time wrapper — NEW script `scripts/file_infra_task.py`

**Decision: a NEW standalone orchestration-layer script, NOT a `task.py new
--auto-dispatch` flag.** Rationale in §11. The script delegates filing to
`task.py new` (so the mutation core + flock + commit stay the single source of
truth) and then attempts the spawn.

**CLI surface** (mirrors `task.py new`'s relevant flags so it's a drop-in
"file + dispatch"):
```
uv run python scripts/file_infra_task.py \
    --kind infra \                      # default infra; choices {infra, batch}
    --title "..." \                     # required
    [--body-file PATH | --body TEXT] \  # mutually exclusive, forwarded
    [--parent N] [--tag T ...] \        # forwarded to task.py new
    [--origin-prompt "..."] \           # forwarded
    [--no-dispatch] \                   # file only; skip the spawn attempt
    [--auto-approve-gpu-hours T]        # forwarded to spawn-issue (default = spawn_session default)
```
- `--kind` choices are restricted to `{infra, batch}` (the auto-dispatchable
  pure-code/ops kinds). `experiment`/`analysis`/`campaign` are rejected with a
  loud argparse error — those have their own routing (analysis needs the
  `agent-ok` opt-in + PM triage; experiment needs the adversarial-planner GPU
  gate). This keeps the wrapper from ever auto-`--auto`-dispatching a
  GPU-spending task outside a cap.

**Dispatch sequence** (`cmd_file_infra` → exit code):
1. **File first.** Run `task.py new --kind <k> --title ... [...]` via
   `subprocess.run(cwd=PROJECT_ROOT)`. Parse the new id from stdout
   (`#<N>` — the existing `_safe_echo(f"#{new_id}")` line; take the first
   `#<int>` match). If `task.py new` fails (non-zero rc) → print stderr, exit
   non-zero. **The task IS filed even if the later spawn fails** — filing is the
   durable, must-succeed half; the backstop (2) catches a failed spawn.
2. **`--no-dispatch` → done.** Print `filed #<N> (dispatch skipped: --no-dispatch)`,
   exit 0. (Lets a pod-side / deliberately-deferred filer use the wrapper for
   uniform provenance without spawning.)
3. **Daemon reachability gate.** Call a local `_daemon_reachable()`
   (same probe shape as the watcher's: POST `/list` to
   `127.0.0.1:<daemon_port()>`, swallow URLError/OSError/HTTPException/
   UnicodeDecodeError/JSONDecodeError → False). On unreachable → print
   `filed #<N>; Happy daemon unreachable, NOT dispatching (watcher backstop
   will pick it up)`, exit 0. **This is the headless/pod-side no-op:** no daemon
   → no spawn, clean fall-through to (2).
4. **Idempotency pre-check.** Before spawning, check
   `_issue_has_live_registration(N)` (reads `~/.eps-autonomous/issue-<N>.json`
   + `manual-issue-<N>.json`; if present AND its `happy_session_id` is in the
   daemon's live id set → already dispatched). A just-filed task essentially
   never has one, but the check makes the wrapper safe to re-run. On a live
   registration → print `filed #<N>; already has a live session, NOT
   re-dispatching`, exit 0.
5. **Spawn.** `subprocess.run(["uv","run","python","scripts/spawn_session.py",
   "spawn-issue","--issue",str(N),"--auto", ...])`. On success → print
   `filed + dispatched #<N>`, exit 0. On spawn failure → print a WARNING
   (`filed #<N>; dispatch FAILED (<stderr>); watcher backstop will retry`),
   exit 0 (NOT non-zero — the task is filed and the backstop covers it; a
   non-zero here would make callers think filing failed).

**Failure modes, all → clean fall-through to the backstop, never a lost task:**
- daemon down → no spawn (step 3);
- spawn subprocess errors → warn, exit 0 (step 5);
- the wrapper's own crash after `task.py new` succeeded → the task is on disk
  at `proposed`; the watcher sweep dispatches it next tick.

**Helpers to add to `file_infra_task.py`** (kept self-contained — the script is
an orchestration-layer caller, importing the two CLIs only as subprocesses, NOT
importing `autonomous_session_watch`): `_daemon_reachable()`,
`_live_session_ids()` (or import `spawn_session._live_session_ids` /
`daemon_port` — `spawn_session` is an allowed import for an orchestration
script, it is NOT `task.py`), `_issue_has_live_registration(N)`,
`_parse_new_id(stdout)`.

### (2) The watcher sweep — NEW pass `proposed_infra_sweep_pass`

**Decision: a NEW pass, adjacent to (and reusing the primitives of) the
existing infra-drain pass — NOT an extension of `infra_drain_pass` itself.**
Rationale in §11. The two are kept separate functions because they differ in
ONE structural way (candidate source: PM queue file vs. `list-by-status`) but
share all dispatch/cap/dedup primitives.

**Pass name + position.** `proposed_infra_sweep_pass(dry_run, now=None, *,
daemon_reachable=None)`. In `main()` it runs **immediately AFTER
`infra_drain_pass(...)` (line 6228 / called at main() ~10477) and BEFORE
`capacity_retry_pass(...)`**. This ordering is load-bearing:
- After infra-drain so any ID the PM queue already dispatched THIS tick is
  registered (the sweep's registration dedup sees it → won't double-dispatch);
- the two passes share the cap, and the sweep computes occupied/pending AFTER
  infra-drain's dispatches are registered, so the combined budget is respected.

**Ripeness predicate** (a `proposed` task is sweep-ripe iff ALL hold):
1. `status == "proposed"` (built from `task.py list-by-status --status
   proposed --json`, so `on_hold` tasks — a DIFFERENT status folder — are
   structurally excluded, never appear);
2. `kind in INFRA_DRAIN_KINDS` (`{infra, batch}`) — `experiment`/`analysis`/
   `campaign` excluded (analysis needs `agent-ok` + PM triage; this sweep is
   the cheap mechanical safety net, deliberately NARROWER than the PM rule —
   it does NOT auto-dispatch `agent-ok` analysis, which keeps an explicit
   opt-in path through the PM);
3. NO unmet predicate hold: read the task's `predicate-<#N>-...` TAGS (via
   `task.py view <N> --json` → `frontmatter.tags`); for each such tag, parse
   the blocking-issue N (reuse `_parse_predicate_hold`-style parsing) and check
   #N's status is in `INFRA_DRAIN_PREDICATE_SATISFIED_STATUSES`
   (`completed`/`archived`/`awaiting_promotion`). ANY predicate tag whose
   blocker is NOT yet finished → SKIP (logged `held: predicate-<#N>`). A task
   with no predicate tag is unblocked. (This is the tag-encoded analogue of the
   PM queue's `holds` map; the orphaned filer never wrote a PM queue, so the
   sweep reads the durable on-task tag instead.);
4. NO live issue-mapped session (the idempotency check — see Idempotency below).

**Cap accounting — SHARED with infra-drain, computed once, no double-spend.**
The cap is `INFRA_DRAIN_CAP_DEFAULT` (3) — the SAME constant. `free = max(0,
cap - occupied_active - pending)`:
- `occupied_active` = `_infra_drain_occupancy()` (kind-infra/batch tasks at
  `INFRA_DRAIN_OCCUPIED_STATUSES`) — REUSED verbatim;
- `pending` = `_infra_drain_pending(registrations, stale, status_kind)` over
  ALL non-stale registrations — REUSED verbatim, and this is the mechanism that
  prevents the sweep from over-dispatching past what infra-drain already
  spawned THIS tick: a session infra-drain spawned earlier this tick wrote its
  `issue-<N>.json`, so it counts as `pending` here.
- Fail-CLOSED: if `_infra_drain_occupancy()` returns `None` (any status read
  failed) → skip dispatching this tick (a partial count over-dispatches),
  exactly as infra-drain does.

Because both passes read the SAME registration snapshot semantics and the SAME
occupancy/pending helpers within the same `main()` tick, their combined spawns
cannot exceed `free` slots: the sweep runs second and sees infra-drain's
freshly-registered spawns as `pending`.

**Candidate ordering + slot fill.** Sort sweep-ripe candidates oldest-first
(ascending id is a safe proxy; the PM's urgency-first nuance is the PM's job —
the sweep is the mechanical backstop). Fill `free` slots; everything beyond
`free` is skipped `cap-full` (re-tried next tick).

**Per-candidate churn guard.** Reuse the infra-drain attempt/backoff state file
pattern but in a SEPARATE state file `~/.eps-autonomous/proposed-infra-sweep-
state.json` (so the sweep's attempt budget never collides with the PM-queue
drain's `infra-drain-state.json`). Backoff window `EPM_PROPOSED_INFRA_SWEEP_
BACKOFF_S` (default 3600s, reuse the constant value); attempts cap
`EPM_PROPOSED_INFRA_SWEEP_MAX_ATTEMPTS` (default 3). A task whose spawn keeps
failing backs off; the day a PM rewrites/repromotes or the task changes status
the entry is pruned. (Simpler than the PM-queue epoch reset — there is no
`updated_ts` here; just a per-task backoff from last attempt + a per-task
attempt cap, with the entry pruned when the task leaves `proposed`.)

**Idempotency / registration dedup.** REUSE `_infra_drain_reg_snapshot()` +
`_dispatch_infra_drain(issue, slot_desc, dry_run, reg_snapshot=snap)` — that
function already does the pre-spawn byte-identity re-check against the
decision-time snapshot and aborts on a registration that "appeared/changed
since the decision" (lost race to a concurrent dispatcher). A candidate with an
existing NON-stale registration is filtered out BEFORE dispatch (it has a live
session). A STALE registration (dead-at-boot: task still `proposed`, older than
grace, session not live — `_infra_drain_stale`) does NOT block re-dispatch
(same semantics as infra-drain).

**Kill switch + flags.** Env `EPM_DISABLE_PROPOSED_INFRA_SWEEP=1` → pass logs
`disabled` and returns. New `main()` flag `--proposed-infra-sweep-only` (mirrors
`--infra-drain-only`) for live smoke. Daemon-gated like every spawning pass
(skip when `daemon_reachable` is False).

**Marker/log sentinel.** On dispatch, post `_post_progress_marker(issue, f"{_PROPOSED_INFRA_SWEEP_NOTE_SENTINEL}
watcher auto-dispatched ripe proposed infra task (no PM queue entry)", ...)` with
a NEW sentinel `_PROPOSED_INFRA_SWEEP_NOTE_SENTINEL =
"[autonomous_session_watch:proposed-infra-sweep-dispatch]"` (added to the
sentinel-uniformity set near `_INFRA_DRAIN_NOTE_SENTINEL` line 697 + the
staleness-clock-exclusion list line 741 so it never resets the orphan/stalled
clocks). Per-tick summary line: `proposed-infra-sweep: candidates=<n>
occupied=<o>(+<p> pending) cap=3 dispatched=<d> skipped=<s>`.

### Idempotency — concrete dedup check + race bounding

- **Source of truth (both paths):** the issue-mapped registration files
  `~/.eps-autonomous/{issue,manual-issue}-<N>.json` — the same files
  `spawn_session._load_session_issue_map()` (the `list` engine) reads. "Live"
  = registration present AND its `happy_session_id` ∈ the daemon's live session
  id set (`_live_session_ids_or_none()`); a registration whose recorded session
  is no longer live AND whose task is still `proposed` past grace is STALE
  (re-dispatchable), per `_infra_drain_stale`.
- **File-time wrapper:** step-4 pre-check (`_issue_has_live_registration`)
  before the spawn subprocess.
- **Watcher sweep:** candidate filtered out if it has a non-stale registration;
  `_dispatch_infra_drain`'s pre-spawn byte-identity re-check is the final guard.
- **Race between (1) and (2):** the wrapper spawns synchronously at file time
  and registers `issue-<N>.json` on success BEFORE returning. The next watcher
  tick (≤10 min later) sees that registration and skips the task. The only
  double-spawn window is a sub-second overlap where the wrapper's spawn has not
  yet written its registration AND the watcher tick reads the candidate
  simultaneously — both then pass the dedup check and both spawn. This is
  acceptable for a once-per-10-min sweep + a synchronous file-time call (the
  same bounded window the PM-vs-watcher infra-drain race already accepts, shrunk
  by `_dispatch_infra_drain`'s byte-identity re-check). The cost of the rare
  double-spawn is one redundant no-GPU Happy session, reaped by the
  zombie-wrapper / session-reconcile passes.

| Double-spawn race between file-time call and the next watcher tick | Low | Both check the same registration dedup; `_dispatch_infra_drain` byte-identity re-check; rare overlap = one no-GPU session, reaped by zombie/reconcile passes. Acceptable per body. |
| Wrapper bakes spawning into `task.py` (breaks pod-side shellout rule) | Avoided by design | Wrapper is a SEPARATE orchestration-layer script; `task.py` mutation core untouched; pod-side code never invokes the wrapper. |
| Sweep + infra-drain jointly overshoot cap 3 | Low | Sweep runs AFTER infra-drain in the same tick and counts infra-drain's fresh registrations as `pending`; shared `_infra_drain_occupancy`/`_infra_drain_pending`; fail-closed on occupancy read failure. |
| False dedup on a STALE (dead-at-boot) registration blocks a needed re-dispatch | Low | `_infra_drain_stale` (reused) un-blocks a still-`proposed` task whose session is definitively not live past grace; missing signals fail toward keep-blocking (safe). |
| Daemon outage during a pod-side / headless filing | Expected | Wrapper no-ops the spawn; watcher sweep dispatches when the daemon returns (the whole point of the backstop). |
| Sweep auto-dispatches a mis-filed GPU task | Avoided | `INFRA_DRAIN_KINDS={infra,batch}` only; `experiment`/`analysis`/`campaign` excluded; wrapper rejects non-`{infra,batch}` `--kind`. |
| Predicate tag convention drift (tag vs PM-queue `holds`) | Low | Sweep reads the durable on-task `predicate-<#N>-...` TAG (the convention research-pm 3a already uses for cross-issue holds); reuses the same satisfied-status set as the PM-queue promotion. |

## 8. §11 Decision Rationale (every design knob)

- **NEW script `scripts/file_infra_task.py` vs `task.py new --auto-dispatch`
  flag.**
  - *What:* a standalone orchestration-layer wrapper.
  - *Why (serves the Goal):* a `--auto-dispatch` flag inside `task.py` would put
    session-spawning logic in `task.py`'s process — and `task.py` is the
    branch-guarded, flock-holding state-mutation core that pod-side code must
    NEVER shell out to (`tests/test_no_pod_side_task_py_shellout.py`,
    CLAUDE.md). Even a flag that "only shells out after the mutation core
    returns" risks normalizing `task.py` as a dispatch entrypoint and tempts a
    pod-side caller. A separate script keeps the mutation core dispatch-free and
    keeps the dispatch concern in the orchestration layer where it belongs
    (same layer as `spawn_session.py`).
  - *Source:* CLAUDE.md "Pod-side code NEVER shells out to `scripts/task.py`";
    `tests/test_no_pod_side_task_py_shellout.py`; body HARD CONSTRAINT #1.
  - *Alternatives rejected:* (i) `task.py new --auto-dispatch` — rejected as
    above; (ii) an adapter inside `spawn_session.py` (`spawn-issue` gains a
    `--file-first`) — rejected because `spawn_session` is the spawn primitive,
    not a task-filer; mixing filing into it muddies its single responsibility
    and the body asks for a "file + dispatch in one call" filer.

- **NEW watcher pass `proposed_infra_sweep_pass` vs EXTEND `infra_drain_pass`.**
  - *What:* a new sibling pass reusing infra-drain's primitives.
  - *Why:* the two passes differ in exactly ONE structural axis — candidate
    source (PM-written queue file vs. `list-by-status --status proposed`) — and
    that axis touches the whole top of the function (read+parse+validate+holds).
    Folding both into one function would require a mode branch threaded through
    every step and would couple the PM-queue's epoch/`updated_ts` retry budget
    to the sweep's simpler per-task backoff. A separate function reusing the
    leaf primitives (`_infra_drain_occupancy`, `_infra_drain_pending`,
    `_dispatch_infra_drain`, `_infra_drain_reg_snapshot`, `_infra_drain_stale`)
    keeps each function single-purpose and lets the body's "ADDS paths, not
    REMOVES the PM one" invariant be obvious by inspection.
  - *Source:* body change #2 + "the PM remains the only NUANCED ripeness judge;
    both watcher mechanisms are mechanical predicate checks";
    `autonomous_session_watch.py` infra-drain pass structure.
  - *Alternatives rejected:* a `mode=` param on `infra_drain_pass` — rejected
    (couples the two retry-budget models, harder to test in isolation, risks
    regressing the #633-hardened PM-queue executor).

- **Position in pass order (after infra-drain, before capacity-retry).**
  - *What:* sweep runs second of the two infra dispatchers.
  - *Why:* running AFTER infra-drain means the sweep's `pending` count sees any
    ID infra-drain dispatched THIS tick (its fresh `issue-<N>.json`), so the
    shared cap is honored across both; running before capacity-retry keeps both
    spawning-into-free-slots passes grouped.
  - *Source:* `main()` 10477-10489; the infra-drain/cap accounting helpers.
  - *Alternatives rejected:* before infra-drain (would let the sweep dispatch a
    PM-queued ID the PM intends to dispatch with urgency ordering — better to
    let the nuanced judge go first).

- **Separate sweep state file `proposed-infra-sweep-state.json`.**
  - *What:* the sweep's per-task attempt/backoff state is distinct from
    `infra-drain-state.json`.
  - *Why:* a single task could be reachable via BOTH the PM queue and the sweep
    (e.g. PM queued it, watcher also sees it `proposed`); sharing one state file
    would let one path's attempt budget silently throttle the other. Separate
    files keep each path's churn guard independent + independently testable.
  - *Source:* infra-drain state-file pattern (`_load/_save_infra_drain_state`).
  - *Alternatives rejected:* shared state file (budget cross-talk).

- **Sweep scope `{infra, batch}` only (NOT `agent-ok` analysis).**
  - *What:* the mechanical sweep is narrower than the PM rule's scope.
  - *Why:* `agent-ok` `analysis` requires an explicit human opt-in tag + can be
    CPU-cost-bearing; keeping it out of the always-on mechanical sweep preserves
    the deliberate opt-in path through the PM and avoids the sweep ever
    auto-running analysis the user did not clear. `infra`/`batch` pure-code/ops
    is the unambiguous auto-dispatchable set.
  - *Source:* research-pm 457-470 (scope + the `agent-ok` opt-in requirement);
    `INFRA_DRAIN_KINDS`.
  - *Alternatives rejected:* match the PM's full scope incl. `agent-ok` analysis
    — rejected (removes the human opt-in gate for an always-on robot).

- **Routing-prose lands in workflow-fix-on-bug.md + research-pm.md + CLAUDE.md.**
  - *What:* three surfaces, edits per §3(1b).
  - *Why:* these are the three places that currently TELL a filer to dispatch
    (workflow-fix step 5-6 is the highest-volume infra-filer; research-pm is the
    PM filer; CLAUDE.md is the always-loaded routing law). Wiring the wrapper
    into exactly these makes "file == dispatch" the default everywhere a ripe
    infra fix is born.
  - *Source:* body change #1 ("wired into the routing surfaces (`CLAUDE.md`,
    `workflow-fix-on-bug.md`, `research-pm.md`)").
  - *Alternatives rejected:* only CLAUDE.md — rejected (the workflow-fix
    protocol has its own explicit step list that would drift).

- **Tests across two files.**
  - *What:* `tests/test_file_infra_task.py` (new) + extend
    `tests/test_autonomous_session_watch.py`.
  - *Why:* the wrapper is a standalone script → its own test file (mirrors
    `test_spawn_session_list_enrichment.py`); the sweep is a watcher pass → it
    belongs with the watcher's pass tests (reuses `isolated_registry`).
  - *Source:* existing test layout.
  - *Alternatives rejected:* one combined file (crosses two modules' fixtures).
