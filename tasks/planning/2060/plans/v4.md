`kind: infra` (workflow-fix, fingerprint a20f18266959). 0 GPU-h, VM-only, no pod.
Incident parent: #1947 (pod-1947-loc billed 14+ min RUNNING with `runtime: null` after
a bootstrap-wait failure; user: "can you fix workflow so this doesn't happen again").

v4 folds in the round-1 critic REVISE (2 Must-Fix, 2 Should-Fix): (MF1) both planned
`terminate_pod` calls would be REFUSED by the 2026-08-04 kill-approval gate
(`runpod_api.terminate_pod` raises `PodTerminateNotApproved` without an env approval or

## 0. Policy statement for ratification at the plan gate (MF1)

- **Facet (a) teardown is the ONE sanctioned automated destruction.** The provision
  process is the flow DRIVING the pod it just created; on a bootstrap/ssh-wait failure
  nothing ever ran on the pod, so the "everything is uploaded and verified"
  precondition of the standing directive is satisfied vacuously (empty artifact set).
  The teardown wraps `pod_lifecycle._verified_teardown_grant(target=<name>,
  reason="provision-created pod never bootstrapped — nothing ran, nothing to upload
  (#2060)")` — the exact wrapper the Step-8 auto-terminate already uses (L3527, used
  ~L3630). Approving this plan ratifies that policy reading.
- **Facet (b) is ESCALATE-ONLY — a stated deviation from the body's "reapable"
  wording.** `kill_approval.py` (standing directive 2026-08-04, verbatim: "the daily
  audit, the watcher, wedge failovers, any background sweep — holds neither and is
  refused") forbids a watcher-side terminate; extending the gate for a never-ran class
  is a public-contract/security-boundary change only the user can authorize (halt
  criterion 2/3) and is OUT OF SCOPE. The watcher leg instead surfaces the leak loudly,
  distinctly, and repeatedly (the CLAUDE.md § Pods surfacing contract: pod name +
  hourly burn + the terminate command, wait for the user's word). The completion
  report flags this deviation prominently so the user can opt to extend
  `kill_approval` later. Corollary (corrects plan v3 §3/§8): the existing #770/#1667
  wedge terminate-failover is itself disarmed by the same gate in production
  (`backend_poll` calls `terminate_pod` bare) and degrades to its alert path — this
  plan does not change that, and does not treat it as a live terminate mechanism.

## 4. Design — concrete diffs

### 4.1 `scripts/pod_lifecycle.py` — facet (a)

1. **Flag:** `p.add_argument("--keep-on-bootstrap-failure", action="store_true",
   help="Keep the pod alive for debugging when the SSH/bootstrap wait fails (default: terminate the pod this provision created)")`
   in the provision parser block (~L3813). Read via `getattr(args,
   "keep_on_bootstrap_failure", False)` (hand-built-Namespace precedent, #2011).
2. **One shared helper** (module-level; TERMINATED token literal appears exactly once —
   the #1931 single-literal convention):

   ```python
   def _teardown_failed_provision(info: PodInfo, name: str, *, keep: bool) -> None:
       """Best-effort terminate of the pod THIS provision created, on a
       bootstrap/ssh-wait failure (#2060; incident #1947). Surgical by pod_id —
       never name-resolution, so sibling pod-<N>-<slug> pods are untouched.
       Runs inside the owner-driven verified-teardown grant (the provision flow
       IS the driver; nothing ran, so the verified-artifact set is empty).
       NEVER raises: a teardown failure must not mask the original error."""
       if keep:
           print(
               f"  --keep-on-bootstrap-failure: pod {name} (id={info.pod_id}) kept "
               f"alive for debugging — it is BILLING; terminate with "
               f"`pod.py terminate` when done.",
               file=sys.stderr,
           )
           return
       try:
           with _verified_teardown_grant(
               target=name,
               reason="provision-created pod never bootstrapped — nothing ran, "
               "nothing to upload (#2060)",
           ):
               terminate_pod(info.pod_id)
           print(f"BOOTSTRAP-FAILED-TERMINATED pod={name}", file=sys.stderr)
       except Exception as exc:  # noqa: BLE001 — best-effort by contract (#2060)
           print(
               f"  WARN: teardown of failed-provision pod {name} "
               f"(id={info.pod_id}) failed: {exc} — pod may still be BILLING; "
               f"terminate manually with `pod.py terminate`.",
               file=sys.stderr,
           )
   ```

   Implementer judgment: also best-effort remove the pods.conf/sidecar rows on
   successful terminate IF registration already happened at that point in the tail
   (reuse the exact removal helpers `cmd_terminate` uses; read the current tail
   ordering first — if registration happens after the failure points, no removal
   needed).
3. **ssh-wait path:** in `except RunPodError`, after `_record_bad_placement_loud(...,
   reason="ssh-wait-timeout")` and the guidance print, insert
   `_teardown_failed_provision(info, name, keep=keep_flag)`, keep the bare `raise`.
   Update the guidance print's trailing clause to state what now happens
   (auto-terminated by default / kept under the flag).
4. **bootstrap-failed final path:** after `_record_bad_placement_loud(...,
   reason="bootstrap-failed")`, insert `_teardown_failed_provision(...)`, THEN the
   existing `BOOTSTRAP-FAILED` print + `sys.exit(rc)` — TERMINATED token prints BEFORE
   it, preserving last-stderr-line (#1931). The retry-once INTERMEDIATE branch is NOT
   touched. The #1334 suffix-scoped terminate-hint print becomes keep-flag-conditional
   (only accurate when the pod survives); tests pin final stderr ordering.
5. No signature change (`_provision_wait_register_bootstrap` already receives `args`).

### 4.2 `scripts/autonomous_session_watch.py` — facet (b), ESCALATE-ONLY

`decide_pod_wedge`, `_process_wedged_pod`, and both #2149/#1582 legs are NOT touched.

1. **New pure decision fn** `decide_never_ran_escalation(*, portless_ticks, age_s,
   grace_s, first_obs_lag_s, obs_slop_s, created_ts_ok, kill_switch, threshold,
   last_alert_ts, realert_s, now) -> tuple[str, dict]` returning `("alert", ...)` /
   `("keep", ...)` / `("clear", ...)` — every missing/garbage input → keep/clear
   (fail-toward-silence). Predicate for `alert`:
   - kill switch off; `created_ts_ok` (parsed ISO `created_at`);
   - first observation of this pod began within `obs_slop_s`
     (`EPM_NEVER_RAN_OBSERVE_SLOP_S`, default 1200s ≈ 2 cron periods) of creation —
     bounding the unobserved window;
   - EVERY observation since has been portless (`portless_ticks` increments only while
     the raw wedge predicate holds; a port appearance DELETES the pod's sub-dict
     entry, so the counter is continuous-by-construction);
   - `age_s ≥ grace_s` (`EPM_NEVER_RAN_GRACE_MIN`, default 45 — past the 10-min ssh
     wait + #1931 retry + bootstrap wall);
   - `portless_ticks ≥ threshold` (reuse the pass's ≥2-consecutive-tick convention);
   - dedup: alert once per episode, re-alert when `now - last_alert_ts ≥ realert_s`
     (`EPM_NEVER_RAN_REALERT_H`, default 6h — a billing leak deserves a shorter cadence
     than the 24h house default; deliberate, stated).
2. **Caller integration:** in the pod-safety per-pod flow (the same site that routes to
   `_process_wedged_pod` when `backend_poll._pod_is_runpod_runtime_wedged(info)`),
   ALSO feed the never-ran leg — scoped to pods whose task carries the `keep-running`
   tag (read lazily, only when the raw wedge predicate holds and the sub-dict entry is
   matured; tag False/"unknown" → skip, the existing wedge arm owns untagged pods).
   State: `nr_pod` pod_id-keyed sub-dict of the pod-safety state file (the #2149
   `kr_pod` pattern): `{first_obs_ts, created_ts, portless_ticks, last_alert_ts}`;
   GC'd against running pod ids; immune to the MF4 per-issue `pod_id`-slot thrash by
   construction (MF2 remedy).
3. **Channels (escalate-only):** one `epm:progress` marker per episode on the owning
   task (anti-liveness sentinel
   `[autonomous_session_watch:runpod-never-ran-keep-running]`), one sidecar row
   (reason `never-ran-keep-running-escalate`, the pod-safety events sidecar), one
   fail-soft Telegram push — all carrying: pod name + pod_id, age, hourly burn
   (`estimate_pod_hourly_rate(info)`), and the exact recovery command
   (`pod.py terminate --issue <N> [--name-suffix <slug>] --yes --approve`). Re-alert
   per cadence. NEVER stops/terminates/unregisters (hard invariant, pinned test —
   house pattern of #1582/#2149).
4. **Kill switch:** `EPM_DISABLE_NEVER_RAN_ESCALATION=1`.
5. **Docs:** one short paragraph in `.claude/rules/background-automation.md` under the
   watcher section naming the leg, its env knobs, sentinel, sidecar reason, and the
   escalate-only invariant. Module docstring pass count UNCHANGED (an arm extension,
   not a new pass — mirror how the #2149 leg is documented inside the keep-running arm
   entry); verify `workflow_lint.py --check-asw-docstring-pass-count` stays green.
   **Stated residual (SF3):** a pod whose port appeared AND vanished entirely within
   the pre-first-observation window (≤ obs_slop of creation, before the watcher's
   first tick) reads never-ran despite briefly having had a runtime — accepted
   because the leg is ALERT-ONLY (a false alert costs one push; no destruction is
   possible by construction), bounded by the 45-min grace + the tag-scoped audience.
   **Stated residual 2:** untagged never-ran pods on multi-pod issues still rely on
   the thrash-prone wedge arm (MF2 applies to it); fixing the wedge arm's state grain
   is out of scope — recorded as a prose follow-up note in the completion report
   (NOT auto-filed; recursion guard).
