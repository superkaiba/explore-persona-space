## §4 Design

**Section A — Happy-path GCP A100 smoke.** Use `--behavior marker`. #671 routed the PRIMARY per-probe reads (`issue667_extract.py:423/424/688`) through the hooked `extract_layer_activations`. One residual un-hooked `output_hidden_states=True` call survives in `_context_vector_all_layers` (line 443, NOT `extract_fact_r_b` as v1 misattributed — fact-checker correction); it is called at 870/871/1022/1023 for ALL behaviors INCLUDING marker (~6× in the smoke: 2 source + 2×2 target contexts), but each call is a transient single-batch allocation that frees on return, so it does NOT accumulate across iterations. The PRIMARY per-probe reads — which dominate the forward count and were the SOLE source of the #545 22→30→38 GiB climb — ARE fully hook-routed. The Section-A flatness signal is therefore sound. Smoke slice: `--source-cid default --targets default,sp_swe --layers 7 14 21 --primary-layer 14 --max-probes 8 --max-new-tokens 256` → ≥30 hooked forwards on the path #671 fixed, unambiguous flat-vs-climbing signal.

Implementer adds ~8-line ANALYSIS-ONLY per-iteration memory log behind a `--log-mem-every N` flag (default 0=off): every N hooked reads, log THREE gauges:
1. **`torch.cuda.memory_reserved()` (PRIMARY)** — the allocator's resident pool. Under `expandable_segments:True`, `reserved` retains freed-segment fragmentation; the climb-vs-flat signal lives here.
2. **`nvidia-smi --query-gpu=memory.used` (PRIMARY)** — kernel-visible resident, the literal footprint that drives DHCP/page-reclaim wedges. Shell out via `subprocess.run` + parse the single integer; if `nvidia-smi` is absent (CPU host / docker without NVIDIA runtime), log `None` and proceed.
3. **`torch.cuda.memory_allocated()` (SECONDARY)** — live tensor bytes. Recorded for diagnostic purposes; NOT in the pass predicate. The #545 climb showed in this gauge too (because held tensors), but a fix that frees tensors but leaves the pool fragmented would read flat here, and Section A must catch that.

All three land in `validation.json.memory_log[]` per iteration; pass predicate reads the two PRIMARY gauges. No behavior change to the reads.

A100-40 question: `INTENT_TO_MACHINE` maps `lora-7b`/`eval` → A100-80 (`a2-ultragpu-1g`); `a2-highgpu-1g` (A100-40, the #667 SKU) lives ONLY in `INTENT_A100_40_FALLBACK` as cost-ladder rung 2, no direct CLI pin. Path 1 (preferred): launch `--intent lora-7b --backend gcp`; on A100-80 exhaustion the ladder threads the A100-40 spec automatically. Path 2 (acceptable): if A100-80 lands, accept it — the #671 memory fix + #669 recovery chain are GPU-SKU-INDEPENDENT; record the SKU caveat. Data source = tier-2 established #537 frozen contexts + reused #537 marker adapter (read-only). N/A: model-call-vs-code, contrastive negatives, completion provenance, marker stopping recipe, ICL (all not applicable — no training/implantation). Smoke=full run (one cell).

**Section B — Fault-injection.** B1: deterministic tests already green — `-k watchdog` → 6 tests in `test_gcp_backend.py` (incl. `test_watchdog_terminates_only_when_both_probes_fail`); 3 wedge/failover tests in `test_backend_poll.py`. No new test file needed (`tests/test_issue672_validation.py` is contingency only). B2 LIVE: on a tiny GCP VM, `iptables -A OUTPUT -d 169.254.169.254 -j DROP` + `iptables -A OUTPUT -p tcp --dport 443 -j DROP` (BOTH required — counter resets if either probe answers), watch serial console for `[eps-watchdog]` ladder → TERMINATED → second `epm:cluster-launched` (backend=runpod, `reason: gcp_workload_failover_runpod*`), failover sentinel count=1. CRUCIAL: zero manual action between inject and RunPod relaunch. B3: poller-wedge alternate trigger validated via deterministic test (`test_poll_running_with_frozen_phase_and_drain_timeout_returns_terminal_wedged` + failover-once test).
