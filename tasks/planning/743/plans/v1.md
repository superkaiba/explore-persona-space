## 1. Goal

Add 8-GPU GCP machine specs/intents to the backend router so big parallel sweeps
can run on the free GCP credit lane at 8× width: 8× A100-80 → `a2-ultragpu-8g`,
8× H100-80 → `a3-highgpu-8g` (FLEX_START/SPOT only). Today the GCP lane tops out
at 4× A100 (`ft-7b` → `a2-ultragpu-4g`) + 1×/2× H100, so a wide sweep that would
finish ~2× faster on 8 GPUs (driving case: #697's 64-cell causal-patch sweep, ~14h
remaining on 4× A100) cannot size an 8-GPU GCP VM and goes to a paid RunPod box
instead.

### 3.2 `src/explore_persona_space/backends/router.py` — NO CHANGE

The auto-ladder stays untouched. Rationale: the 8× H100 quota in us-central1 is
exactly 8 — zero concurrency headroom, so auto must never schedule one (two would
exceed quota); and 8× A100, though it has headroom (12 free), is heavy enough that
silently auto-selecting it for an unknown-length job would be wrong. The 8× intents
are reachable ONLY via explicit `--intent sweep-8g-a100` / `--intent sweep-8g-h100`.
This matches the precedent: `inf-70b` / `ft-70b` / `cpu-bigmem` are likewise
explicit-only and absent from the auto-ladder.

### 3.4 `scripts/dispatch_issue.py` — NO CHANGE (confirm only)

## 11. Decision Rationale

- **Intent names: `sweep-8g-a100` / `sweep-8g-h100`.** Chosen over
  `lora-7b-a100-8g` / `lora-7b-h100-8g`. Reason tied to the Goal: the driving use case
  is a WIDE parallel SWEEP (cells sharded across 8 GPUs), not a single 8-GPU LoRA
  fine-tune of one 7B model — `lora-7b-*-8g` would misdescribe the workload (a 7B LoRA
  fits on ONE GPU; the 8 GPUs are for parallelism, not model size). `sweep-8g-*`
  reads correctly to a launcher and to the CLAUDE.md table. It fits the existing
  convention of work-kind-prefixed, hyphen-separated, GPU-family-suffixed intents
  (`lora-7b-h100`, `eval-h100`, `cpu-bigmem`). `Source: #743 task body recommendation
  + gpu_heuristics.py "what kind of work, not model-name aliases" convention (line 22).`
- **router.py auto-ladder unchanged.** 8× H100 quota in us-central1 is exactly 8 — a
  single `a3-highgpu-8g` consumes the entire pool, so auto-selecting one would block
  every other H100 launch and a second would quota-fail. 8× A100 has headroom (12 free)
  but is heavy enough that auto-selecting it for an unknown-length job is wrong.
  Reserve both for explicit `--intent`, consistent with `inf-70b`/`ft-70b`/`cpu-bigmem`
  being explicit-only. `Source: #743 task body constraint (8× H100 = exactly 8, no
  headroom) + verified quota probe 2026-06-29.`
- **8× intents NOT in `INTENT_A100_40_FALLBACK`.** That map is single-GPU 7B-scale work
  that fits a 40 GB card (gcp.py:342-353); an 8× sweep does not. `a100_40_fallback_for_intent`
  returns `None` for an unmapped intent, so the ladder correctly skips the A100-40 rung
  for these. `Source: gcp.py:342-374.`
- **H100+STANDARD raise reused, not duplicated.** The raise keys on
  `gpu_kind == "H100-80"` (gcp.py:1504), so `sweep-8g-h100` inherits it — no new branch,
  no risk of the two diverging. `Source: gcp.py:1501-1508 (#631).`
- **#741 merge ordering.** #741 (status `planning`) changes the
  `default_max_run_duration` default at gcp.py:197 (a `GcpConfig` field); this task
  changes `INTENT_TO_MACHINE` (gcp.py:283) and `MACHINE_TYPE_ZONE_AVAILABILITY`
  (gcp.py:441). Disjoint regions, no content collision. If both land, merge order is
  irrelevant; whichever merges second rebases cleanly. The implementer rebases on
  `main` before the Step 10d auto-merge and resolves trivially if #741 landed first.
  `Source: gcp.py line map + #741 frontmatter (planning).`

This is a `kind: infra` task — no model training, so the per-hyperparameter §11
contract (lr/epochs/LoRA rank Sources) is N/A. The "load-bearing values" here are the
machine-type ids, GPU counts, and zone sets, each grounded above + in §8.
