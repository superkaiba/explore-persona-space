# Plan v1 — issue #1837: sustained (2-tick) reachability alarm for the GCP hung-VM wedge escalation

`kind: infra` (workflow-fix). `architectural: false` — internal poller-predicate change; no

## 1. Requirement + acceptance criteria

The GCP hung-VM wedge escalation (`scripts/backend_poll.py::_maybe_escalate_gcp_wedge`, #669)
currently synthesizes `terminal_workload_wedged` — and thereby fires a PAID GCP→RunPod
failover — on a SINGLE transport-class reachability alarm whenever the phase clock is stale,
which on any long single-phase workload is always (the phase never advances during a
multi-hour fits phase, so `stale_for > GCP_STALENESS_FLOOR_SEC` is trivially satisfied).
Incident (task #1739, 2026-07-29 20:08–20:17Z): one transient
`gcloud compute ssh` control-plane error (`Could not fetch resource: Internal error`) on
healthy `eps-issue-1739-hallu` fired the failover and provisioned a 2×H100 RunPod pod
against a live run.

Acceptance criteria:

- **R1 (streak requirement).** The wedge escalation fires ONLY after ≥ 2 CONSECUTIVE
  alarmed poll ticks (`GCP_WEDGE_ALARM_MIN_TICKS = 2`) whose first-to-latest span is
  ≥ `GCP_WEDGE_ALARM_MIN_SPAN_SEC = 480` seconds. A single alarmed tick returns the
  poll `running` unchanged (plus a loud WARN log naming the armed streak).
- **R2 (durable streak).** The streak is persisted in the handle sidecar's `extra` dict
  (`serialize_handle` round-trips `dict(handle.extra)`, so no schema migration — the #669
  phase-clock + #1815 incarnation precedent), keyed to the launch incarnation via the
  existing `_clock_incarnation_for(handle)`. A streak stamped under a DIFFERENT
  incarnation reads as absent. Survives poller-process restarts (the bg-Bash chain is
  re-entered every tick, so in-memory state is unusable by construction).
- **R3 (reset semantics).** Any of: a non-alarmed tick, a phase advance (the clock
  re-stamp path), or an incarnation change RESETS the streak. Reset is a no-op write
  when no streak keys are present (a clean run never rewrites its sidecar every tick).
- **R4 (control-plane split).** In `GcpBackend._drain_sentinels` (rc≠0 branch,
  `src/explore_persona_space/backends/gcp.py` ~L6571), a stderr matching the gcloud
  CONTROL-PLANE signature — case-insensitive substring `could not fetch resource` — is
  classified as a NEW `alarm_class == "control_plane"` instead of `"transport"`.
  `reachability_alarm` derives from `drain_alarm_class == "transport"` (gcp.py:6120)
  and therefore stays False for this class: a failed API resource-fetch performed NO
  reachability probe of the guest, so it carries zero wedge signal (same doctrinal
  split as the existing `"sentinel_processing"` class). Unmatched rc≠0 stderr keeps
  `"transport"` (fail toward existing behavior); the `TimeoutExpired` branch (#1084 /
  #952 hung-transport class) keeps `"transport"` unconditionally.
- **R5 (genuine wedge still escalates).** A REAL sustained guest-network loss escalates
  on the 2nd consecutive alarmed tick when tick spacing ≥ 480 s (the standard 540 s
  cadence, #1818) — i.e. within ~2 poll ticks (~18 min), satisfying the body's
  "~2-3 ticks" constraint. `terminal_terminated` stays excluded (no spot regression);
  `test_async_gcp_capacity_death_does_NOT_fail_over` stays green.
- **R6 (fail-open durability).** Streak read/write failures (EDQUOT, malformed sidecar)
  are logged and fail toward `running` — never crash the poll, never manufacture a wedge
  (identical contract to `_write_phase_clock`).
Fail-loud pin: tests/test_backend_poll.py::test_streak_write_failure_never_wedges_first_tick — a missing/read-only sidecar must not raise and must not silently wedge; the poll returns running and the write failure is logged loudly, never swallowed into a false escalation.

- **R7 (pin-test update).** The existing single-tick pin test
  `tests/test_backend_poll.py::test_poll_running_with_frozen_phase_and_drain_timeout_returns_terminal_wedged`
  is UPDATED to the two-tick contract (two alarmed polls → wedged + failover); it is a
  deliberate contract change, not a regression.

## 2. Method delta (vs current behavior)

Current: `stale_for > GCP_STALENESS_FLOOR_SEC and result.reachability_alarm` → wedge on
one tick. New: same conjunction ARMS/bumps a sidecar-persisted alarm streak; the wedge
fires only at streak ≥ 2 with span ≥ 480 s. Additionally the alarm producer stops
counting gcloud control-plane API errors as reachability evidence at all.

## 5. Decision rationale / grounding (Source per load-bearing value)

- `GCP_WEDGE_ALARM_MIN_TICKS = 2` — Source: task #1837 body (the #1739 incident: a
  ~5-min control-plane blip spans ≤ 1 tick at the fixed 540 s cadence, #1818); the #669
  design target was SUSTAINED loss (in-VM watchdog requires ~5 min sustained).
- `GCP_WEDGE_ALARM_MIN_SPAN_SEC = 480` — Source: derived from the #1818 fixed 540 s
  poll cadence: 480 < 540 so a genuine wedge fires on the 2nd standard tick (~18 min
  total, within the body's "~2-3 ticks" constraint), while 480 s still guarantees the
  alarm was sustained ≥ 8 min — the same order as the in-VM watchdog's ~5-min
  sustained-loss requirement (#669) — and two rapid back-to-back manual re-polls
  seconds apart can never satisfy it.
- Control-plane signature `could not fetch resource` — Source: verbatim from the #1739
  incident stderr (`ERROR: (gcloud.compute.ssh) Could not fetch resource: Internal
  error`); it is emitted by the gcloud API layer before any SSH probe, never by a guest
  connection failure (ssh connect failures carry `ssh:`/`port 22`/`Connection`
  wording). Unmatched patterns fail toward `"transport"` (status quo).
