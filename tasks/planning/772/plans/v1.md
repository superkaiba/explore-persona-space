# Plan — issue #772: stream-reduce rule for N multi-GB HF span blobs in `code-style.md`

## Goal

Add ONE always-on `code-style.md` bullet so a future planner / experiment-implementer who designs an analysis that reads N multi-GB per-context `.pt` blobs from HF picks the existing stream-reduce helper (`_HfStreamSpanSource`, download → process → delete, peak ~one context, gated behind `_assert_attn_stream_equivalence`) instead of re-downloading the whole grid locally and refilling `/` (the #761 220 GB incident).

## Method delta (vs the existing "Reuse existing in-repo tools/helpers" CLAUDE.md rule)

CLAUDE.md's "Reuse existing in-repo tools/helpers" rule is the GENERAL discovery pressure: *grep before you build*. It is correct but generic — it tells you to search, not *what to find* for this specific failure mode, and a sibling bootstrap that doesn't know the helper exists will grep for the wrong thing and miss it. This new bullet is the SPECIFIC, grep-able instance:

- it names the exact failure trigger (N multi-GB per-context blobs from HF, materialized all-at-once locally),
- it names the canonical helper symbol (`_HfStreamSpanSource`) and the equivalence gate (`_assert_attn_stream_equivalence`) VERBATIM, so a future grep / lint over `code-style.md` resolves the discovery in one hop,
- it states the required pattern (stream-reduce: download → process → delete, peak one context, behind the equivalence assertion) and the disk-footprint reason,
- it lives in `code-style.md` (loads on any `*.py` / `configs/**` edit) so it fires at the moment an analysis script is being written, not only at plan time.

It is a refinement, not a duplicate: CLAUDE.md says "reuse helpers"; this says "for *this* class of disk-blowing analysis, *this* helper, behind *this* gate." It also belongs next to the peak-memory / throughput discipline cluster in `code-style.md` rather than in CLAUDE.md, because it is a coding idiom (how to structure the read loop), not a workflow-routing rule.

### Verbatim text of the new bullet (draft)

```markdown
- **Stream-reduce N large per-context blobs from HF — never materialize the whole grid locally.** An analysis that reads N multi-GB per-context `.pt` (or `.npy`) blobs from an HF dataset repo (answer-span stores, cached per-context activations, per-context attention dumps) MUST use the canonical per-context stream-reduce source `_HfStreamSpanSource` (`scripts/issue658_fit_predictors.py`) — download one context, reduce it, delete it; peak footprint is ~one context (bounded by its LRU `cache_size`, default 1), NEVER the full N×blob-size grid — and run it behind the `_assert_attn_stream_equivalence` gate (a 2-3-context streamed-vs-local toy check that fails fast before any sweep if streaming changed the DV). The local-dir source `_SpanSource` (download every context first) is correct only when the whole grid genuinely fits the per-task disk quota; N × multi-GB does not. Concretely: do NOT `snapshot_download` an `answer_spans/` prefix or loop `hf_hub_download` over all N contexts into a persistent cache — that refills the shared VM disk (#761 re-downloaded 220 GB of UltraChat answer spans — 4.4 GB × 50 contexts — into a local cache and filled `/`, even though `_HfStreamSpanSource` already existed and bounds peak to one context). New per-context HF span/activation analyses reuse this helper rather than writing a fresh all-local download loop.
```

(Single bullet, multi-sentence — matches the register of the adjacent "Compute-throughput discipline" and "Checkpoint per phase" bullets, which are both multi-sentence with parenthetical incident citations.)

## Kill criteria (what would make this rule HARMFUL)

- **Too broad → false positives.** If the trigger reads as "any HF download in an analysis," it would wrongly fire on small (KB-MB) per-cell JSON/tensor reads where all-local is fine and streaming adds latency for no disk benefit. MITIGATION: the trigger is scoped to "N **multi-GB** per-context blobs … the full N×blob-size grid does not fit the per-task disk quota"; small-footprint reads are explicitly out (the bullet says the local source is correct when the grid fits).
- **Too narrow → never fires.** If it named only `answer_spans` or only `issue658`, a sibling activation-dump analysis under a different prefix wouldn't match. MITIGATION: the trigger generalizes to "answer-span stores, cached per-context activations, per-context attention dumps" and to `.npy` as well as `.pt`, and the grep topic word `stream-reduce` is generic.
- **Stale symbol reference.** If `_HfStreamSpanSource` is later renamed / hoisted (the out-of-scope follow-up), the verbatim name in the bullet goes stale and the grep anchor breaks. MITIGATION: this is a known, accepted cost of citing a concrete symbol (the same cost every symbol-citing bullet in `code-style.md` carries, e.g. `MarkerOnlyDataCollator`, `_press_loo_mse_per_lambda`); the follow-up that hoists the helper updates the bullet in the same change per the existing "Supersede → delete the old version" + "rewire-then-delete" discipline already in this file.
- **Redundant with throughput bullet.** If readers conflate it with the existing GPU-throughput bullet, it adds noise. MITIGATION: this bullet is about peak *disk* (download footprint), the throughput bullet is about *PCIe transfer + GPU residency* — different resource, different anti-pattern; placement adjacency makes the contrast legible, not the confusion.
