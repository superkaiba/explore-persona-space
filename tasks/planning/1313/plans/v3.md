## 0.0 TL;DR (plain English)

- **What I'll change:** teach the API dispatcher to retry 529 "overloaded" errors instead of failing instantly (the SDK class the code thought it was catching is not the class the SDK actually raises), and make every downstream judge tally distinguish "the API was down" losses from "the judge saw the content and dropped it" — with the "API was down" rows never poisoning the judge cache.
- **What I expect:** 529 storms like #952's (144/144 draws lost with zero retries) become retried-then-recovered; residual losses show up in a dedicated counter instead of masquerading as content drops.
- **What would change my mind:** if any test shows the 429 rate-limit path double-retrying, or the existing batch-retry machinery breaking — then the change is wrong as shaped and gets reverted to a narrower diff.

### 4.1 `src/explore_persona_space/llm/api_dispatch.py`

**(a) `_is_transient` (:567-582) — the fix + honest docstring:**

```python
def _is_transient(exc: BaseException) -> bool:
    """True for retryable transient API errors (timeouts, 5xx incl. 529, connection).

    529 ``OverloadedError`` is NOT an ``InternalServerError`` subclass in the
    installed SDK (anthropic 0.88.0: MRO OverloadedError -> APIStatusError ->
    APIError) and is not exported at the ``anthropic`` top level, so it is
    matched via the public ``APIStatusError`` + ``status_code == 529`` form
    (llm-judging rule 24(i); #1313). ``RateLimitError`` (429) is handled
    SEPARATELY via AIMD — ``_do_one`` checks ``_is_rate_limit`` BEFORE this
    predicate — so it is NOT in this transient set.
    """
    import anthropic as _anthropic

    transient = (
        _anthropic.APIConnectionError,
        _anthropic.APITimeoutError,
        _anthropic.InternalServerError,  # 500-class; does NOT cover 529 (see docstring)
    )
    if isinstance(exc, transient):
        return True
    # 529 Overloaded — explicit public-form match (robust to SDK re-parenting).
    return isinstance(exc, _anthropic.APIStatusError) and getattr(exc, "status_code", None) == 529
```

**(e) New public helper (exported):**

```python
def is_transport_exception(exc: BaseException) -> bool:
    """Rule-24 transport-class taxonomy over SDK exceptions: the call died
    before any verdict about the content was produced (freely re-judgeable).
    = transient (connection / timeout / 5xx incl. 529) OR 429 rate limit.
    NOT transport: 400-class invalid_request (a pipeline bug, rule 24(iii))."""
    import anthropic as _anthropic

    return _is_transient(exc) or isinstance(exc, _anthropic.RateLimitError)
```

### 4.2 `src/explore_persona_space/eval/batch_judge.py`

```python
_TRANSPORT_LEGACY_REASON_PREFIXES = (
    "batch_error: expired",
    "batch_error: canceled",
    # api_dispatch transient-exhaustion reasons ("transient <ExcName> (attempt N)",
    # api_dispatch.py:793) — covers LEGACY persisted multi-org-reduce dicts whose
    # exception name (APITimeoutError/APIConnectionError/InternalServerError) has
    # no "overloaded" substring (statistics-critic round-1 Must-Fix; the reason
    # field is pipeline-minted, never judge content, and the error gate runs first).
    "transient ",
)

def is_transport_error_dict(parsed: object) -> bool:
    """Rule-24 transport-vs-content split for judge error dicts.

    True iff the row died in TRANSPORT (no verdict about the content was ever
    produced -> freely re-judgeable). Primary signal: the structural
    ``transport: True`` field minted at every #1313 error-dict site. Fallback:
    a conservative reason-string match for LEGACY persisted dicts (pre-#1313
    save_raw files / cache entries, e.g. #1090's stored 529 rows). A
    quarantined 400 (rule 24(iii)) and a parse_error (rule 23) are NOT transport.
    """
    if not isinstance(parsed, dict) or not parsed.get("error"):
        return False
    if parsed.get("transport") is True:
        return True
    reason = str(parsed.get("reasoning", parsed.get("reason", "")))
    if "invalid_request_error" in reason:
        return False
    if reason.startswith(_TRANSPORT_LEGACY_REASON_PREFIXES):
        return True
    if reason.startswith("batch_error: errored ("):
        return True  # server-class errored rows (invalid_request excluded above)
    low = reason.lower()
    return "overloaded" in low or "rate_limited_exhausted" in low
```

## 11. Decision Rationale

1. **529 detection = public `isinstance(exc, APIStatusError) and status_code == 529`** (not `anthropic._exceptions.OverloadedError` import in library code). Source: in-venv probe 2026-07-14 (anthropic 0.88.0: not top-level-exported, MRO OverloadedError→APIStatusError); rule 24(i) and `.claude/rules/code-style.md` name both forms as sanctioned. The private-module import can silently break on an SDK re-layout; the status-code form stays correct even if a future SDK re-parents OverloadedError under InternalServerError (then merely redundant). Tests MAY import the private class (they must construct the real production exception). Alternative rejected: widening to `status_code >= 500` — equivalent today (verified: SDK maps 529→OverloadedError, other ≥500→InternalServerError) but a larger semantic rewrite of a working tuple for zero gain.
2. **`RESULT_TRANSPORT` category for exhausted-transient rows.** Source: rule 24(ii) "a counter DISTINCT from the rule-9 content-drop count"; precedent `RESULT_RATE_LIMITED` (api_dispatch.py:203-208, the re-drivable-exhaustion pattern this mirrors). Blast radius: grep 2026-07-14 — `RESULT_*` consumed only inside `api_dispatch.py` and `tests/test_api_dispatch.py`; `error=True` (the primary flag) unchanged; `_merge_batch_record` legacy default unchanged. `RESULT_RATE_LIMITED` kept as its own label (AIMD observability) though it is also transport-class under rule 24 — consumers treat `{RESULT_RATE_LIMITED, RESULT_TRANSPORT}` as re-drivable.
3. **Re-dispatch mechanism = the EXISTING #1019 machinery; no new retry layer.** Source: judge_dispatch.py:46-64 + :1309 ("Retrying %d errored/expired requests (once)") + `_load_collected_into` :794-813; pinned by `tests/test_batch_stuck_escape.py` / `test_issue663_batch_hardening.py`. The Goal's "batch-collection re-dispatch" is satisfied on the primary path (`judge_completions_batch → dispatch_judge_items`); duplicating it would create two competing retry layers. Deltas this task adds: residual failures become visible (counter) and re-runnable (cache get-miss ⇒ a re-run of the same pipeline re-dispatches them — the rule 24(ii) "follow-up batch or sync dispatch"). LEGACY `_submit_and_poll_batch` gets classification flags ONLY: its two callers are frozen 2026-era `scripts/issue_389` scripts behind a signature-stability contract (batch_judge.py:339-343); new pipelines are mandated onto `judge_completions_batch` anyway. Out-of-band-canceled rows keep the #663 no-auto-retry contract (an operator cancel is intentional) but are counted as transport — rule 24(ii)'s report-the-loss branch.
4. **Retry-budget interaction with SDK internal retries.** api_dispatch pins `max_retries=0` (:1192-1213, deliberate — AIMD ownership); after the fix a 529 gets the dispatcher's own bounded loop (default `max_attempts=5`, `asyncio.sleep(1.5**attempt)` at :794 — the loop sleeps after EVERY failing attempt including the last, so cumulative backoff ≈ 13.2 s = 1+1.5+2.25+3.375+5.06; fact-checked, plan-v1's 8.1 s was wrong arithmetic) — no double-retry. judge_dispatch sync clients keep `max_retries=5` (:1429/:1487/:1508): the SDK already retries 529 there (verified: `_should_retry` retries ≥500), which is why #952-class instant fast-fails are the api_dispatch-path signature; no client-construction change anywhere. Sizing note: 5 attempts ≈ 13 s does not outlast a real outage — by design; outlasting outages is the job of the counter + re-run/re-dispatch layer, not of per-call spin (`max_attempts` stays caller-tunable).
5. **Cache put-skip AND get-miss for transport dicts (in scope, both).** Source: rule 23's cache caveat ("the cache-update loop persists `error: True` entries ... the same cache dir re-serves the stored transport error") + rule 24(ii)(a) (the re-judge must bypass the cache). Put-skip prevents NEW poisoning; get-miss self-heals ALREADY-poisoned caches (#1090) without manual surgery and is what makes "re-run ⇒ re-dispatch" true. Both are VALUE-behavior changes; the key schema (`EPM_JUDGE_CACHE_KEY_V2`, rule 22/#1018) is untouched — pinned by the key-schema test in §5. Counter-argument considered: caching transport errors "saves" re-attempts during an outage — rejected: that is precisely the censoring rule 24 exists to prevent, and per-run retry budgets bound the cost. Quarantined-400 and parse_error entries KEEP being cached (a 400 re-fails identically; parse_error is a rule-23 budget concern out of scope).
6. **`n_dropped_draws` narrows to content-only.** Source: rule 24(ii) ("blending them recreates the censoring") + rule 18 (report split). Consumers grep'd 2026-07-14: organisms.py (reads — becomes more accurate), datagen.py (keyword construction — unaffected).
7. **Unknown batch rtype → `transport: True`.** Failure-direction asymmetry: transport→content misclassification silently censors (the #1090 shape); content→transport wastes at most one re-judge. Fail toward visible + re-judgeable.
8. **Quarantined 400 stays in the content-drop tally** (status quo; rule 24(iii): neither retried nor transport — a malformed request fails identically on resubmit, so counting it re-judgeable would lie). A third counter rejected as scope expansion; documented in the JudgeResult docstring.
