## 1. Goal

Two coupled defects let task #664 burn ~12h / ~$530 on an 8×H200 pod doing
zero GPU work:

1. **Per-file HF upload on a large repo 504-storms.** `upload_raw_completions_to_data_repo`
   (`src/explore_persona_space/orchestrate/hub.py:881`) loops `_upload(..., upload_as_file=True)`
   once per `raw_completions.json`. Each `HfApi.upload_file` triggers a
   server-side recursive tree-listing of the now-large
   `superkaiba1/explore-persona-space-data` dataset repo as a pre-check; that
   listing 504-times-out roughly half the time. Measured: 508 attempts in 12h →
   264 verified, 241 504-failures, only 264/1425 files uploaded.
2. **The poller noticed the idle GPUs but only ADVISED.** `_maybe_post_gpu_idle_advisory`
   (`scripts/poll_pipeline.py:1774`) posts a one-shot `[gpu-idle-advisory]`
   `epm:progress` marker and never escalates, so the $44/hr bleed continued
   for hours unseen.

This task closes BOTH: (a) refactor the raw-completions uploader to a single
`upload_folder` commit (the canonical fix already used elsewhere), and (b)
add a poller escalation tier above the advisory that fires a Telegram push +
a louder `[gpu-idle-escalation]` marker (NOT auto-stopping the pod) once a
multi-GPU pod sits idle past a higher threshold in an upload/CPU-only phase.
Plus propagate the "the FINAL upload phase is itself a CPU-only phase" rule
into CLAUDE.md / planner / critic / gotchas so future plans sequence the
upload off the GPU pod.

## 2. Method delta (vs prior related work)

- **Folder-commit is the canonical fix and is already the project default.**
  `_upload` (`hub.py:540-631`) already has the `upload_folder` branch
  (default `upload_as_file=False`), which calls `HfApi.upload_folder` →
  `HfApi.create_commit` exactly ONCE (verified: `upload_folder`'s source
  calls `create_commit` once and only walks the repo tree when
  `delete_patterns` is passed, which we will not pass). The project ALREADY
  documents this exact pattern in `.claude/rules/upload-policy.md` §
  "Multi-cell pod sweeps upload per-cell, never one terminal batch (#664)"
  (one `upload_folder` commit per cell-dir) and § "HF Hub rate limit: 256
  repository commits per hour" ("sweeps producing >~200 per-cell commits/hr
  batch their uploads into ONE bulk `upload_folder` commit"). Reference impl:
  `scripts/issue664_dispatch.py` `_upload_cell_artifacts`. The delta for #727
  is to make the *shared library helper* `upload_raw_completions_to_data_repo`
  do this by default, so every caller inherits it without hand-rolling.
- **The poller advisory → escalation delta** mirrors the existing
  `autonomous_session_watch.py` gate-push pattern (`_telegram_push` →
  `notif_enqueue.sh`, `NOTIF_CAT=research`, fail-soft). The advisory tier is
  kept verbatim; a second, higher tier is layered on top with its own
  per-phase de-dup and its own threshold.

### 3.1 `src/explore_persona_space/orchestrate/hub.py` — refactor the raw-completions uploader

**Keep `_upload` and its per-file `upload_as_file=True` branch UNCHANGED.**
Legitimate single-file callers exist (e.g. `scripts/issue560_crossrecipe_panel.py:1015`)
and the `workflow_lint --check-upload-as-file` guard + `test_workflow_hub_upload_as_file.py`
pin the file-vs-folder semantics as a workflow invariant. Do NOT remove the
per-file API. Do NOT change the `_upload` `ValueError` guard for a file path
without `upload_as_file=True` (that guard is load-bearing, #595/#640).

**Refactor `upload_raw_completions_to_data_repo` (`hub.py:881`) to a single
folder-commit, preserving its public contract exactly** — same signature,
same return type `dict[str, str]` (`{rel_path: url}`), same fail-loud
`RuntimeError` on failure, same per-cell nested path layout
`<experiment_name>/raw_completions/<rel_path>`.

The current body rglobs `raw_completions.json` and loops `_upload(...,
upload_as_file=True)`. The refactor:

1. rglob to find all matching `raw_completions.json` files (unchanged) — used
   to (a) early-return with a logged warning if none found (unchanged
   behavior), and (b) build the expected `{rel_path: url}` return dict.
2. Issue ONE `_upload` call on the WHOLE `eval_results_dir` directory
   (folder branch, `upload_as_file=False`), scoped to the raw-completions
   files via `allow_patterns`, landing under the
   `<experiment_name>/raw_completions/` prefix so the nested per-cell layout
   is preserved.

The blocker: `_upload`'s folder branch uses `path_in_repo` as the
destination prefix and `ignore_patterns` for exclusion, but does NOT today
expose `allow_patterns`. Two options; pick **Option A** (smaller blast
radius, keeps `_upload` callers untouched):

- **Option A (preferred): a thin bulk helper that calls `HfApi.upload_folder`
  directly with `allow_patterns`, reusing `list_repo_files_complete` for
  verification.** Add a small private helper
  `_upload_folder_filtered(local_dir, repo_id, repo_type, path_in_repo,
  allow_patterns, ignore_patterns=None, delete_after=False) -> str` next to
  `_upload`, factoring out the same create_repo → upload_folder → verify →
  optional-delete shape `_upload`'s folder branch already has, but threading
  `allow_patterns` through to `upload_folder`. Verification reuses the SAME
  `list_repo_files_complete(api, repo_id, repo_type=...)` paginated walk +
  prefix-match `_upload` already uses (NOT `repo_info().siblings`, which
  truncates — see the `hub.py:596-606` comment). Then
  `upload_raw_completions_to_data_repo` calls it once with
  `allow_patterns=["**/raw_completions.json"]` (or the equivalent that
  matches the rglob set) and `path_in_repo=f"{experiment_name}/raw_completions"`.

  Pseudocode:
  ```python
  def upload_raw_completions_to_data_repo(experiment_name, eval_results_dir, delete_after=False):
      raw_paths = sorted(eval_results_dir.rglob("raw_completions.json"))
      if not raw_paths:
          logger.warning("...no raw_completions.json under %s — nothing to upload", eval_results_dir)
          return {}
      path_in_repo = f"{experiment_name}/raw_completions"
      # ONE folder commit for the whole tree — no per-file recursive listing.
      base_url = _upload_folder_filtered(
          local_dir=eval_results_dir,
          repo_id=DEFAULT_DATASET_REPO,
          repo_type="dataset",
          path_in_repo=path_in_repo,
          allow_patterns=["**/raw_completions.json"],
          delete_after=False,   # see note below — delete handled per-file after verify
      )
      if not base_url:
          raise RuntimeError(
              f"upload_raw_completions_to_data_repo: bulk folder upload failed for "
              f"{eval_results_dir} → {DEFAULT_DATASET_REPO}/{path_in_repo}"
          )
      # Build the SAME {rel_path: url} return dict the per-file loop produced,
      # from the rglob set (verification inside _upload_folder_filtered already
      # confirmed the files landed).
      uploaded = {}
      for raw_path in raw_paths:
          rel = raw_path.relative_to(eval_results_dir).as_posix()
          uploaded[rel] = f"{DEFAULT_DATASET_REPO}/{path_in_repo}/{rel}"
      if delete_after:
          for raw_path in raw_paths:
              raw_path.unlink(missing_ok=True)
      return uploaded
  ```

  Note on `delete_after`: the historical default is `False` (the
  upload-verifier does its own cleanup). When `True`, delete the individual
  `raw_completions.json` files AFTER the bulk upload verifies — NOT the whole
  `eval_results_dir` (which holds aggregate JSONs the bulk upload deliberately
  skipped via `allow_patterns`). The pseudocode above does this.

  **Verification completeness (mirror the #664 EXACT-set check):** inside
  `_upload_folder_filtered`, after `upload_folder`, run
  `list_repo_files_complete` and confirm that EVERY expected
  `<path_in_repo>/<rel>` is present (an EXACT expected-set check on the fresh
  listing, NOT mere prefix-presence / count — a mid-`upload_folder` crash
  leaves a partial set that prefix-presence would wrongly pass; this is the
  upload-policy.md § per-cell rule). Return `""` on any missing file so the
  caller raises.

- **Option B (rejected): widen `_upload`'s folder branch to accept
  `allow_patterns`.** Touches the shared `_upload` signature that many
  callers + two tests pin; larger blast radius for no benefit. Implementer
  MUST NOT take this without re-justifying.

**Single-file API decision:** KEEP `_upload(..., upload_as_file=True)`. It is
the correct path for genuine single-file callers and the lint + invariant
test depend on it. The refactor only removes the per-file LOOP inside
`upload_raw_completions_to_data_repo`.

### 3.2 `scripts/poll_pipeline.py` — escalation tier above the GPU-idle advisory

The existing advisory (`_gpu_idle_advisory_update` / `_maybe_post_gpu_idle_advisory`,
lines 1730-1844) stays verbatim. Add a SECOND tier:

- **New env knob `EPM_GPU_IDLE_ESCALATION_MIN`** (default `60`), read at
  import time next to `GPU_IDLE_ADVISORY_MIN`. Contract:
  `EPM_GPU_IDLE_ESCALATION_MIN >= EPM_GPU_IDLE_ADVISORY_MIN` (escalate only
  AFTER advising); if set below the advisory min, clamp up to the advisory
  min at import with a logged WARNING. `<= 0` disables escalation.
- **Pure decision core `_gpu_idle_escalation_update(...)`** mirroring
  `_gpu_idle_advisory_update`: reuses the SAME idle-span tracking
  (`gpu_idle_since_epoch`) the advisory already persists — do NOT add a
  second independent span; both tiers read the one span. `should_escalate`
  is True only when the span ≥ `escalation_min*60` AND `current_phase` not
  already in a NEW per-phase de-dup set `gpu_idle_escalated_phases` AND the
  phase is classified upload/CPU-only (see classifier below) AND the pod is
  multi-GPU (≥2 cards parsed from `gpu_util`). Pure / no I/O.
- **Phase classifier `_phase_is_cpu_only(current_phase: str) -> bool`.**
  Default-CPU-only with a small GPU-REQUIRED deny-list of phase-name
  substrings, because phase names vary across dispatchers and the safe
  failure mode for an ESCALATION (a loud notice, never an action) is to
  over-notify, not under-notify. Deny-list (treated GPU-required, NOT
  escalated): any phase whose name contains `train`, `gen`, `eval`,
  `generate`, `infer`, `forward`, `judge_gen`, `vllm`, `setup`, `preflight`,
  `merge` (merging a checkpoint touches GPU briefly). Everything else
  (`p3_upload`, `upload`, `p5_upload`, `aggregate`, `analysis`, `score`,
  `bootstrap`, `plot`, `unknown` excluded — see next) is treated CPU-only and
  IS eligible to escalate. **`unknown` is NOT eligible** (a phase the
  dispatcher never named could be anything — fail toward not-escalating a
  potentially-GPU phase, since the advisory already fired for true CPU idle).
  Keep the deny-list as a module-level frozenset constant
  `GPU_REQUIRED_PHASE_SUBSTRINGS` so it is editable in one place; the #664
  trigger phase `p3_upload` matches `upload` → eligible.
- **Wiring `_maybe_escalate_gpu_idle(...)`** called in `poll_once` right
  AFTER `_maybe_post_gpu_idle_advisory` (so the advisory always fires first
  on the same span). On `should_escalate`:
  - Post a LOUD `epm:progress` marker, note prefixed `[gpu-idle-escalation]`,
    plus a `gpu_idle_escalation=True` extra. Note text names: all N GPUs ≤
    threshold% for M min, the phase, the estimated $/hr leak class, and the
    actionable remedy (route the upload off-pod / release GPUs after a
    checkpoint; the FINAL upload phase is CPU-only — CLAUDE.md). Explicitly
    state "NOTHING was stopped — surfacing the spend leak for action."
  - Fire a best-effort Telegram push. **`poll_pipeline.py` does not today
    import the Telegram helper** (it lives in `autonomous_session_watch.py`).
    Implementer choice between two equally-acceptable mechanisms (pick the
    smaller diff):
    - **(preferred) inline a tiny fail-soft `_telegram_push(msg)` in

      `~/my-goat/scripts/notif_enqueue.sh`, `NOTIF_CAT=research`, `timeout=30`,

    - import `autonomous_session_watch._telegram_push` — rejected: pulls the

  - A post/push failure is logged and the phase is NOT recorded as escalated
    (next tick retries), exactly like the advisory.
- **State persistence:** add `gpu_idle_escalated_phases` to the `_save_state`
  payload (line ~2388) alongside the existing `gpu_idle_advised_phases`,
  parsed/serialized the same comma-join way. The shared

- **`recommend_next_interval`:** an escalation is a "something notable
