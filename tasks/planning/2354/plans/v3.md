# Plan v3 — #2354: follow-up-shield keep for `worktree_audit.py` (stale sweep must not reap an active inline-round worktree)

`kind: infra` (workflow-surface fix). No GPU work anywhere in this plan.

**Estimated GPU-hours (total): 0**

## Requirement + acceptance criteria

**Requirement.** The daily stale-worktree sweep (`scripts/worktree_audit.py`, cron `--apply`)
must KEEP an auto-generated `issue-<N>` / `issue-<N>-<suffix>` worktree whose parent task has a
provably in-flight follow-up round, even when every existing idle gate reads reapable — the
#2223 incident shape: compute on a pod (no VM process), parent parked at `awaiting_promotion`
(in `REAPABLE_ISSUE_STATUSES`), tree momentarily clean, branch work merged or not yet committed.
The shield predicate must be the SAME one the watcher's pod-safety / session-reconcile passes
already use to shield pods: a follow-up signal marker newer than the latest done-transition
marker, or the `keep-running` tag.

**Scope delta vs the filed body (clarifier finding).** #2246 (commit `81b75635d3`, landed after
this task was filed) already keeps on committed-but-unmerged work (three-valued
`_branch_unmerged` probe vs `origin/main`, fail-toward-keep), which covers the filed body's
proposed-fix item 2 AND the literal #2223 committed-and-pushed-but-unmerged shape. This plan
therefore implements ONLY the remaining gap — proposed-fix item 1, the follow-up-signal /
keep-running shield — and records item 2 as already-landed. The filed body's trailing
suggestion of "a short activity grace window keyed on last branch-commit mtime" is DROPPED with
a reason: a pod-side round leaves no VM-side branch-commit mtimes by construction, so a
commit-mtime grace cannot cover the incident class, while the signal markers are already the
sanctioned, mandatory shield (CLAUDE.md pod-safety pre-launch signals require them
before/at provision).

**Acceptance criteria.**
1. A worktree whose parent task carries a follow-up signal (`epm:run-launched` /
   `epm:followup-scope` / `epm:free-analysis-followup-run`) NEWER than the latest
   done-transition (`epm:promoted` / `epm:status-changed` / `epm:pod-terminated` /
   `epm:step-completed`) is KEPT even when: no live process, status in
   `REAPABLE_ISSUE_STATUSES`, past the grace window, tree clean, branch fully merged.
   (The regression pin named in the task body.)
2. A worktree whose parent task carries the `keep-running` tag is KEPT under the same
   otherwise-reapable conditions.
3. An UNKNOWABLE tag state (`keep_running_tag_state` → `None`: registry corruption, branch-guard
   error) KEEPS with its own fail-toward-keep reason — mirroring the #2246 probe-failed idiom
   and the helper's own documented destructive-path posture.
4. A follow-up signal OLDER than the latest done-transition does NOT keep (settled business —
   the worktree stays reapable; no new immortality class).
5. Orphan worktrees (task folder gone) and agent-/wf- worktrees are BYTE-UNCHANGED in behavior:
   the shield arm is issue-name-gated, `_issue_events_path` returns None for orphans (no signal
   → no keep), and `keep_running_tag_state` returns `False` for a missing task (documented
   contract), so nothing becomes immortal.
6. The kind sets are pinned against drift from the watcher's canonical sets by a test that
   imports BOTH modules and asserts set equality.
7. A shield-kept worktree is never remediation-removed (`_remediation_kind` /
   `_execute_remediation` cannot remove it while the shield holds).
8. Existing `tests/test_worktree_audit.py` suite stays green; `workflow_lint.py` shows no NEW failures vs the plan-time baseline on the changed files (the Step 10d baseline-subtracted lint gate is the binding repo-wide arbiter).

## Method delta (what differs from prior related work)

- #2246 added a keep for UNMERGED WORK (git-content evidence). This change adds a keep for
  IN-FLIGHT ROUNDS (task-lifecycle evidence) — the two are orthogonal: #2246 protects bytes,
  this protects a live round's working directory whose bytes are already safe.
- The predicate is the established watcher predicate
  (`autonomous_session_watch.py::_task_session_followup_active`,
  `_SESSION_FOLLOWUP_SIGNAL_KINDS` vs `_SESSION_DONE_TRANSITION_KINDS` — the session-reconcile
  variant, whose done set includes `epm:pod-terminated` + `epm:step-completed`), plus the
  `keep-running` tag override read via the existing shared helper
  `task_workflow.keep_running_tag_state` (#1485 tri-state).
- **Reuse mechanism (named decision):** the signal/done kind sets and the newer-than comparison
  are MIRRORED locally in `worktree_audit.py` (small pure helper + two frozenset constants),
  pinned by an anti-drift equality test importing `autonomous_session_watch` — NOT a runtime
  import of the ~28.5K-line watcher script into the daily cron (couples the sweep's health to
  the watcher module's import health), and NOT an extraction of the watcher's private helpers
  into `task_workflow` (touches a heavily test-pinned surface for zero behavior gain).
  The anti-drift-test idiom is already this file's convention (`_TRACKED_CHANGES_REASON` /
  venv underscore-prefix pins). The `keep-running` read is TRUE reuse (shared helper import,
  already available — `worktree_audit.py` already imports from `task_workflow`).

## File paths + concrete diffs

### 1. `scripts/worktree_audit.py`

(a) **Constants** (near the other single-source reason constants, ~line 215-231):

```python
# Follow-up shield (#2354): marker kinds signaling an in-flight follow-up
# round on a parked/terminal task, and the done-transition kinds that settle
# them. MIRRORS autonomous_session_watch._SESSION_FOLLOWUP_SIGNAL_KINDS /
# _SESSION_DONE_TRANSITION_KINDS (the session-reconcile variant) — pinned by
# an anti-drift equality test rather than a runtime import of the watcher.
_FOLLOWUP_SIGNAL_KINDS = frozenset(
    {"epm:run-launched", "epm:followup-scope", "epm:free-analysis-followup-run"}
)
_FOLLOWUP_DONE_TRANSITION_KINDS = frozenset(
    {"epm:promoted", "epm:status-changed", "epm:pod-terminated", "epm:step-completed"}
)
# Single-source keep reasons (anti-drift coupling, same idiom as
# _TRACKED_CHANGES_REASON): emitted by should_remove off the callers'
# three-valued shield verdict.
_FOLLOWUP_SHIELD_REASON = "parent task has an in-flight follow-up shield"
_FOLLOWUP_SHIELD_UNKNOWN_REASON = "follow-up shield state unknowable (fail toward keep)"
```

(b) **Pure shield probe** (near `_branch_unmerged`): `_followup_shield(name, statuses) ->
tuple[bool | None, str]` returning `(verdict, detail)`:
- Non-issue name → `(False, "")` (arm never fires for agent-/wf-/human-named).
- `keep_running_tag_state(task_id)` → `True` ⇒ `(True, "keep-running tag set")`;
  `None` ⇒ `(None, "keep-running tag state unknowable")`. (`False` falls through to the
  signal read. Import the helper from `explore_persona_space.task_workflow` alongside the
  existing `repo_root, tasks_dir` import.)
- Signal read: reuse `_issue_events_path(name, statuses)` (None for orphans → no evidence) and
  the `_merged_evidence`-style row loop (same `split("\n")` + `json.loads` + row-skip
  discipline, same `_aware_epoch` ts parse — a naive/malformed ts contributes no evidence).
  Compute `newest ts among _FOLLOWUP_SIGNAL_KINDS` and
  `newest ts among _FOLLOWUP_DONE_TRANSITION_KINDS`; verdict
  `(True, "epm:<kind> newer than latest done-transition")` iff both exist and
  signal > done, mirroring `_task_session_followup_active` exactly (no signal → False;
  no done-transition → False, defensive). Unreadable events file (OSError) → no evidence →
  `(False, ...)` — matching both `_merged_evidence` and the watcher; the tag arm's None
  branch is the deliberate fail-toward-keep channel, and a missed signal keep degrades to
  the #2223 inconvenience (recreate a worktree), never data loss (the #2246 + tracked-changes
  guards already protect bytes).

(c) **`should_remove`**: add kwarg `followup_shield: bool | None = False` (default preserves
every existing caller/test byte-for-byte, the #2246 `branch_unmerged` shape). Keep branch
AFTER the status guard, BEFORE the unmerged guard:

```python
    if followup_shield is None:
        return Decision(name, False, _FOLLOWUP_SHIELD_UNKNOWN_REASON)
    if followup_shield:
        return Decision(name, False, _FOLLOWUP_SHIELD_REASON)
```

(d) **`_classify`**: lazy probe on otherwise-removable issue worktrees, BEFORE the unmerged
probe (one events+body read vs a 60s-timeout git walk; a shield keep short-circuits the
expensive arm):

```python
    if decision.remove and _ISSUE_NAME_RE.match(name):
        shield, s_detail = _followup_shield(name, statuses)
        if shield is None:
            return Decision(name, False, f"{_FOLLOWUP_SHIELD_UNKNOWN_REASON}: {s_detail}")
        if shield:
            return Decision(name, False, f"{_FOLLOWUP_SHIELD_REASON}: {s_detail}")
```

(e) **Remediation path**: `_remediation_kind` keys on exact reasons
(`_LIVE_PROCESS_REASON` equality / `_TRACKED_CHANGES_REASON` substring), so a shield keep is
structurally un-remediable — VERIFY and pin by test rather than edit. `_execute_remediation`
re-derives guards fresh before removal (a shield-active worktree can enter remediation via a
live orphan-codex holder); wire the SAME `_followup_shield` check into its fresh re-derivation
so post-kill/post-rescue removal is refused while the shield holds (implementer reads the
function and inserts the check at the fresh-state re-verification point, keep-with-reason on
shield True/None).

(f) **Module docstring**: extend the KEPT-if list (guards 1-5) with guard 6 (the follow-up
shield), one short paragraph in the established style, citing #2354 and the #2223 incident.
