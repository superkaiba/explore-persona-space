# Plan v1 — task #800: document WANDB_LOG_MODEL checkpoint-upload trap

## 1. Goal

Add a short, targeted paragraph to `.claude/rules/upload-policy.md` naming the
`WANDB_LOG_MODEL` env var as a **separate** checkpoint-upload surface from our
project's inline WandB uploads, so a future reader who sets it (or inherits it
from an environment) does not silently violate the Upload Policy against a
guard (`EPM_UPLOAD_MODEL_WANDB=1`) that does NOT cover it.

## 4. Design (file paths + concrete edit)

**Target file:** `.claude/rules/upload-policy.md`

**Insertion site:** immediately after the existing "Merged-dir HF uploads are
opt-in" paragraph (which discusses `EPM_UPLOAD_MERGED` + WandB semantics), OR
immediately after the "Inline-upload fence `EPM_SKIP_INLINE_CHECKPOINT_UPLOAD`"

**Content (target ~120-180 words, prose paragraph; implementer refines):**

> **`WANDB_LOG_MODEL` is a SEPARATE surface — must stay unset.** HF Trainer's
> `WandbCallback`
> (`transformers/integrations/integration_utils.py`; reads
> `os.getenv("WANDB_LOG_MODEL", "false")`) silently auto-uploads model
> checkpoints to WandB Artifacts when the env var is set to `end` /
> `checkpoint` / `true` — completely bypassing this project's
> `EPM_UPLOAD_MODEL_WANDB` guard, which only fences OUR inline WandB uploads
> in `hub.py::upload_model_wandb`, `trainer.py::_maybe_upload_checkpoint_to_wandb`,
> and `sft.py::train_lora`. Because HF Trainer defaults `WANDB_LOG_MODEL` to
> `"false"`, the project is safe by default — but a stale environment variable
> (a shell rc leftover, a `.env` line, a legacy pod config) turns every
> Trainer-driven run into a policy violation against a guard that cannot see
> it. Rule: `WANDB_LOG_MODEL` MUST STAY UNSET at shell / dotenv / pod-env
> level. If you need per-run wandb checkpoint upload (rare, and NEVER
> whole-account default), opt into the project surface via
> `EPM_UPLOAD_MODEL_WANDB=1` instead — it is scoped and revocable; the HF
> Trainer callback is neither. Incident: 2026-06-30 4TB WandB cleanup, ~784G
> checkpoint duplication accumulated before the guard landed
> (commit `b4474042b7`).

Implementer may lightly rephrase for prose flow but must preserve: the env-var
name, the callback module, the three accepted values, the default (`false`),
the three guard call sites, and the "MUST stay unset" directive.

## 7. Risks + mitigations

- **Risk (LOW):** future refactor renames the guard env var or moves the three
  inline call sites. Mitigation: reference the guard by NAME
  (`EPM_UPLOAD_MODEL_WANDB`) and the three call sites by MODULE::FUNCTION
  (no line numbers, drift-safe). Reviewer catches drift on the next
  workflow-fix pass.
- **Risk (LOW):** if a future HF Trainer version renames `WANDB_LOG_MODEL`
  (transformers v5 already deprecates bool values), the note goes stale.
  Mitigation: the rule ("must stay unset") is version-independent; a
  deprecation is a follow-up doc pass, not a regression.
- **Risk (NEGLIGIBLE):** the note claims `WANDB_LOG_MODEL` "silently"
  uploads — technically transformers logs an info-level line when the callback
  fires. Mitigation: "silently against project policy" is the intended
  reading; the info log is inside transformers logs, not surfaced by our
  policy layer. Wording preserves accuracy.
