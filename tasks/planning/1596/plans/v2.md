# Plan — #1596: queue-vanish failover retries GCP on-demand after a capacity-class RunPod refusal

## 0.0 TL;DR (plain English)

- **What I'll change:** when a flex-start GCP run vanishes from the capacity queue (#1116), fails over to RunPod, and RunPod refuses for capacity/cap reasons leaving nothing behind, the poller will now try the GCP on-demand rungs itself — the exact thing #1112's operator did by hand — before parking the run as "no compute available".
- **What I expect:** the ~20-minute manual `--provisioning-model STANDARD` recovery becomes automatic; the workload-crash and boot-loop failover paths stay byte-identical.
- **What would change my mind:** if the exactly-once machinery can't be extended to a second (GCP-target) failover class without touching the #659 semantics — the design below shows it can, via one optional parameter on `_attempt_one_gcp_rung`.

## Plan Summary

**Change:** on the #1116 queue-vanish failover path ONLY, when the RunPod terminal rung raises `NoComputeAvailableError` AND the #1490 residue reclaim reports a clean outcome (`no-residue` / `torn-down` / `pre-existing` / `foreign-created`, NOT `leaked`), walk the GCP ladder's STANDARD (on-demand) rungs via the existing `_gcp_ladder_specs` provisioning-model pin + `_attempt_one_gcp_rung`, burning daily attempts, exactly-once-bounded by an in-flock `gcp_failover_of` stamp. Cross-rung exactly-once closed symmetrically: `_lease_already_failed_over` (the RunPod rung's in-flock M3b check) extended to also match a `backend="gcp"` lease stamped with the same `gcp_failover_of` identity (Change 4b — consistency-checker difference 6). **Unchanged:** #659 workload-crash, #783 queue-timeout, #1029 boot-loop callers (flag defaults off); the `leaked` branch; route()'s ladder order (both router pin tests stay green as-is). **Files:** `src/explore_persona_space/backends/router.py`, `scripts/backend_poll.py`, `.claude/rules/compute-backend-failover.md`, `CLAUDE.md` (one clause), `tests/test_router.py`, `tests/test_backend_poll.py`. **Compute:** CPU-only unit tests.

## 3. Design

### Change 1 — `router.py`: new reason constant

`ROUTE_REASON_QUEUE_VANISH_GCP_ONDEMAND_RETRY: str = "queue_vanish_gcp_ondemand_retry"` (beside :567, docstring distinguishing it from `gcp_queue_vanish_failover_runpod` — that one labels the GCP→RunPod leg; this labels the RunPod-refused→GCP-on-demand leg). Rides the existing marker `reason` field + the running-JSON `current_phase`; no `workflow.yaml` edit (documented-drift precedent, §2 last bullet). NOT in the watcher's `TRANSIENT_CAPACITY_REASONS` (it labels a LAUNCH, never a terminal).

### Change 2 — `router.py::_attempt_one_gcp_rung`: optional exactly-once identity (in-flock)

New keyword-only param `failover_of_identity: dict[str, Any] | None = None` (default None = byte-identical for all existing callers). Two touch points, both INSIDE the existing `store.transaction` (:4865):

- immediately after the lease materialization (:4871-4880), before the cap check:
  ```python
  if failover_of_identity is not None and lease is not None \
          and lease.gcp_failover_of == failover_of_identity:
      return "already_launched"          # new str return value
  ```
- at the post-launch lease write (:5068):
  ```python
  submitted = _lease_after_submit(lease, spec, "gcp", None, gcp_handle)
  if failover_of_identity is not None:
      submitted.gcp_failover_of = failover_of_identity
  write(submitted)
  ```

This gives the GCP retry a STRONGER guarantee than the RunPod path's post-hoc `_stamp_lease_failover_of`: the stamp lands in the SAME flock transaction as the create, so there is no launch→stamp window at all (M3b-equivalent atomicity; design question 5).

Implementer notes at the `already_launched` check site: (a) add a comment that a `backend="runpod"` lease stamped with the same old-handle identity ALSO matches — that flow should be unreachable (the shared core's pre-check fires first) and the match direction is conservatively correct (never double-provision); (b) verify a mid-walk `"advance"` does not post a per-rung terminal-failure marker under `terminal=True` — the exhaustion terminal belongs to the poller helper, not the rung.

### Change 3 — `router.py`: new public retry function

```python
def retry_gcp_ondemand_after_queue_vanish(
    *, spec: RunSpec, gcp_backend: ComputeBackend,
    marker_poster=None, on_launched=None, lease_store=None,
    now_fn=None, config=None, gcp_failover_of_identity=None,
) -> RouteResult | None:
```

Sibling of `failover_to_runpod_after_async_workload_crash` (same seam-defaulting shape, :3402-3408). Body:

1. `machine = machine_for_intent(spec)`; if `machine.gpu_kind.startswith("H100")` → append an `ondemand_retry_unservable_h100` attempt + raise `NoComputeAvailableError` (no on-demand H100 pool; `render_create_argv` raises on H100+STANDARD — never build a rung guaranteed to crash).
2. `pinned = replace(spec, backend="gcp", extra={**dict(spec.extra or {}), "provisioning_model": "STANDARD"})` — `_gcp_ladder_specs(pinned)`'s pin branch then enumerates EXACTLY the on-demand rungs: `ondemand_<kind>` (base machine) then `ondemand_a100_40` when the intent is #1468-eligible; pinned wide rungs when `spec.gpus` declares width. (Design question 2: rung enumeration is REUSED from the ladder builder, never a hand copy; spot/flex are structurally absent under the pin. For #1112's `ft-7b` this yields `[ondemand_a100_80]` — no A100-40 rung for a 4-GPU intent — exactly the rung the operator dispatched by hand.)
3. Loop rungs through `_attempt_one_gcp_rung(spec=rung_spec, rung_label=..., gcp_backend=..., store=..., attempts=..., started_at=now_fn(), cfg=config or RouterConfig(), now_fn=..., marker_poster=..., on_launched=..., terminal=True, reason=ROUTE_REASON_QUEUE_VANISH_GCP_ONDEMAND_RETRY, count_attempt_cap=True, failover_of_identity=...)`:
   - `RouteResult` → return it (marker already posted by the rung with the new reason; `gcp_attempts_today` bumped — the retry BURNS daily attempts by design: it is a fresh create, unlike the poller-side RunPod failover, and `count_attempt_cap=True` gives cap-check + bump for free).
   - `"already_launched"` → return `None` (concurrent triggerer won).
   - `"advance"` → next rung; `"cap_hit"` → break.
4. `except _GcpWorkloadFailover as sig: raise sig.__cause__` — a workload-class create failure on the retry must NOT cascade back to RunPod (it just refused); re-raise the underlying `GcpWorkloadError` typed for the caller. (Always set: :5033 raises `from exc`.)
5. Exhaustion / cap → `raise NoComputeAvailableError("queue-vanish on-demand retry: STANDARD rungs exhausted", attempts=...)`.

### Change 4 — `backend_poll.py::_lease_records_failover_of`: one-line relaxation

`:2573` `if lease is None or lease.backend != "runpod": return False` → `if lease is None or lease.backend not in ("runpod", "gcp"): return False`. Needed so the pre-check (:3557) short-circuits after a retry launch whose sidecar write crashed (lease then reads `backend="gcp"` + `gcp_failover_of == old identity`). Safe for #659: a runpod lease still matches; a `backend="gcp"` lease matches only when `gcp_failover_of` equals the OLD vanished handle's identity, which only Change 2's stamp writes — a fresh GCP dispatch (new pod_name) never matches (identity comparison, :2548-2552).

### Change 4b — `router.py::_lease_already_failed_over`: symmetric cross-rung extension (consistency-checker difference 6)

`:5257-5261` currently requires `lease.backend == "runpod"`, so a concurrent second vanish-triggerer that passed the OUTSIDE-flock pre-check BEFORE Change 2's GCP stamp landed would reach `_runpod_terminal_rung`, NOT short-circuit, and could launch a paid RunPod pod alongside the GCP retry if RunPod capacity freed in the window. Extend the predicate symmetrically: match when `lease.backend in ("runpod", "gcp")` AND `lease.gcp_failover_of == identity` (identity comparison unchanged). This closes the cross-rung double-provision window in the same in-flock transaction the RunPod rung already holds; a fresh dispatch's new identity never matches, so #659 semantics are untouched. Pinning test in §4 (`test_runpod_terminal_rung_short_circuits_on_gcp_stamped_lease`).

### Change 5 — `backend_poll.py`: gate + wire the retry in the shared core

- `_failover_gcp_to_runpod(...)` gains keyword-only `gcp_ondemand_retry_on_capacity_refusal: bool = False`; ONLY `_failover_vanished_gcp_to_runpod` passes `True` (#659/#783/#1029 callers untouched — the no-cascade bound stays byte-identical, per the constraint).
- In the `except NoComputeAvailableError` branch, after the reclaim: the `leaked` early-return (:3673-3690) is UNTOUCHED. In the clean-residue tail (:3691), insert:
  ```python
  if gcp_ondemand_retry_on_capacity_refusal:
      retry_json = _retry_gcp_ondemand_after_vanish_refusal(
          issue=issue, handle=handle, sidecar=sidecar,
          cause_label=cause_label, failover_tag=failover_tag, reclaim=reclaim)
      if retry_json is not None:
          return retry_json
      # retry exhausted -> fall through to today's terminal, log_tail extended
  return _terminal_infra_json(..., reason="no_compute_available",
      log_tail=f"...; provision-residue: {reclaim['outcome']}"
               + ("; GCP on-demand retry also exhausted (#1596)" if retried else "") + ...)
  ```
- New module-level helper `_retry_gcp_ondemand_after_vanish_refusal(*, issue, handle, sidecar, cause_label, failover_tag, reclaim) -> dict | None`:
  1. `spec = replace(_runspec_from_gcp_handle(handle, issue), backend="gcp")` (the builder fails loud on a blank-workload handle — keep that; the STANDARD pin is applied inside the router function, single source of truth).
  2. `try: rr = retry_gcp_ondemand_after_queue_vanish(spec=spec, gcp_backend=_resolve_backend("gcp"), marker_poster=post_marker_via_task_py, on_launched=lambda h: write_handle_sidecar(h, sidecar), gcp_failover_of_identity=_gcp_handle_identity(handle))`
  3. `except NoComputeAvailableError:` → log + return `None` (caller falls through to the re-drivable terminal — the watcher capacity-retry backstop stays reachable). The fall-through terminal's `log_tail` KEEPS the original RunPod refusal evidence (the classified shape / stderr tail already carried today) alongside the retry note, so a RECURRING account-level cost-cap (a config problem masquerading as capacity) stays visible to a human across episodes.
  4. `except GcpWorkloadError as exc:` → return `_terminal_infra_json(reason="gcp_workload_failed_on_ondemand_retry", log_tail=...)` — a workload crash must NOT wear the re-drivable capacity label (the #931 mislabel class); an unlisted reason parks at `blocked` for a human, fail-loud.
  5. `rr is None` (concurrent already-launched) → mirror the M3b block (:3736-3781): read the sidecar; a handle with `pod_name != handle.pod_name` → running-shaped JSON preserving it; else `_write_failover_sentinel(...)` + terminal `sidecar_persistence_failed`.
  6. Success → authoritative `write_handle_sidecar(rr.handle, sidecar)` + `read_handle_sidecar` readback, verifying `recovered.backend == "gcp" AND recovered.pod_name == rr.handle.pod_name` (pod_name is the discriminator — both old and new handles are gcp-backend, unlike the RunPod path's backend check); on write/readback failure → sentinel + terminal `sidecar_persistence_failed` (mirror :3791-3827). No post-hoc lease stamp needed (Change 2 stamped in-flock). `_clear_failover_sentinel(sentinel)`; return running-shaped JSON (`status: "running"`, `current_phase: "queue_vanish_gcp_ondemand_retry"`, `new_milestone: True`, log_tail naming old instance → new instance, rung label, reclaim outcome, `failover_tag`). The fresh sidecar write drops the old handle's `extra["last_phase"] == "pending"` clock by construction (:696-698 — the clock lives in the serialized handle's `extra`), so a later death of the NEW on-demand instance cannot false-match the vanish predicate.

### Design questions resolved

- **Q1 (placement):** rung walk in `router.py` (reuses `_gcp_ladder_specs` + `_attempt_one_gcp_rung` = cap accounting, headroom/boot-loop skips, zone ladder, markers, lease writes for free; unit-testable with the same injected seams as its siblings), trigger/gating + sidecar mechanics in `backend_poll.py`'s shared core (where the reclaim outcome + sentinel/lease machinery already live). The existing lease/sentinel records ARE reusable — same `gcp_failover_of` keying to the OLD handle identity — with the Change-2 in-flock stamp and the Change-4 one-line relaxation; no second failover-record class is needed.
- **Q2 (rungs):** STANDARD-pin on `_gcp_ladder_specs`; burns daily attempts (`count_attempt_cap=True`); H100 intents refused up front.
- **Q3 (watcher pass):** the watcher's capacity-retry pass did not cover #1112 because (i) it re-drives via `spawn-issue --auto` re-running the FULL auto ladder — a long job's ladder is flex-start-first, so the re-drive re-books the vanish-prone flex rung rather than targeting on-demand; (ii) it fires only on a task PARKED at `blocked` with `reason: no_compute_available`, on a ~10-min watcher cadence with backoff + per-day caps — #1112's live session hit the terminal at 06:25Z and the operator hand-dispatched at 06:27Z, inside the watcher's dead time; (iii) a re-drive spawns a fresh session (context + wall-clock cost) where the in-poller retry keeps the SAME poll loop chained via the sidecar re-point. The in-poller retry is still the right fix; the watcher pass stays the unchanged backstop for the retry-exhausted terminal (criterion 3 keeps the re-drivable label).
- **Q4 (error taxonomy):** no new CAPACITY-vs-other classifier is needed. Gate = clean residue only. Justification: (a) every clean-residue `NoComputeAvailableError` already mints the re-drivable `no_compute_available`, which authorizes the watcher to re-run the FULL ladder (a superset of these on-demand rungs) — the immediate bounded retry is strictly narrower than what the system already permits on this exact state; (b) evidence-text classification (`_classify_provision_failure`) is best-effort and its `unknown` class covers the #1112 cost-cap shape — keying the retry on it would have MISSED the motivating incident; (c) the two non-capacity refusal classes are already routed before this branch (`RunPodWorkloadStartError` :3628, `leaked` :3673).
- **Q5 (idempotency/concurrency):** repeat polls → sidecar re-point + Change-4 pre-check; crash between launch and sidecar write → in-flock stamp (Change 2) read back by the relaxed pre-check → `sidecar_persistence_failed` terminal, never a second paid launch; N concurrent triggerers → in-flock `already_launched` re-check in the same transaction as the create; cross-rung (a concurrent triggerer racing toward the RunPod rung while the GCP retry launches) → Change 4b's symmetric `_lease_already_failed_over` extension short-circuits the RunPod rung on the GCP-stamped lease.
- **Q6 (architectural):** `architectural: false` — a guarded fallback branch on one failover class; no status enum / marker schema / task.py contract change; new reason strings are additive marker `reason`/`current_phase` values per the drifted-enum precedent (§2).
- **#1287 predicate trace (against the real #1112 artifact, §2 last bullet):** caller = `_failover_vanished_gcp_to_runpod` (the 06:25:26Z trigger was the queue-vanish leg, per the origin evidence "#1116 queue-vanish failover") → flag True ✓; RunPod refusal = `PodLifecycleProcessError` exit 1 with NO pod created (cost-cap refuses pre-create) → post−pre snapshot = ∅ → `reclaim["outcome"] == "no-residue"` (:3113/:3121) ≠ leaked ✓; spec rebuilt from the handle (`intent=ft-7b`, workload_cmd baked at create per the 06:07:37Z row) → STANDARD pin yields `[ondemand_a100_80]` — the rung the operator manually dispatched at 06:27Z ✓. The predicate FIRES on its motivating incident; in that specific incident the rung would then have stocked out (`ZONE_RESOURCE_POOL_EXHAUSTED`) and fallen through to the same terminal — the automation gap, not the outcome, is what this fixes.

## 9. §11 Decision Rationale

- **Placement (rung walk in router, gating in backend_poll).** Why: reuses cap/headroom/boot-loop/zone/marker machinery in `_attempt_one_gcp_rung`; the reclaim outcome + sentinel/lease live in the poller core. Source: router.py:4763-5116, backend_poll.py:3656-3707. Alternatives: (a) all-in-backend_poll direct `gcloud` create — rejected (re-implements cap accounting + zone ladder; the #1112 manual recovery shows exactly that hand-rolled shape); (b) route()-side change — rejected (route() has no live call at poll time; would risk the ladder-order pin).
- **Rung set = STANDARD pin on `_gcp_ladder_specs`.** Why: single source of truth for enumeration (labels, A100-40 eligibility, width); matches the Goal's "remaining on-demand rungs" (spot/flex already consumed or barred at original dispatch). Source: router.py:2714-2723; incident rows 06:27Z+ (manual STANDARD dispatch). Alternative: hand-built rung list — rejected (drifts from the ladder).
- **Attempt-cap accounting: retries BURN daily attempts.** Why: the no-burn rule is structural to the poller-side RunPod failover ("bumps only on a create inside `_attempt_one_gcp_rung`", rule :792-794); the retry IS such a create — exempting it would let a vanish loop bypass the cap. Source: compute-backend-failover.md:792-794, router.py:4911-4914. Alternative: `count_attempt_cap=False` — rejected (unbounded credit exposure; the pin-path exemption is for explicit user asks only).
- **Reason strings: new `queue_vanish_gcp_ondemand_retry` for the retry launch + new non-re-drivable `gcp_workload_failed_on_ondemand_retry` terminal; exhaustion keeps `no_compute_available`.** Why: marker-trail distinguishability (the #1116 pin test's own rationale) without breaking the watcher contract. Source: test_router.py:8086-8107; backend_poll.py:2937-2944 (#931 mislabel precedent). Alternative: reuse `gcp_queue_vanish_failover_runpod` with an extra field — rejected (that reason means "launched RunPod"; overloading it corrupts the trail the pin test protects).
- **Exactly-once via in-flock `failover_of_identity` on the rung.** Why: same-transaction stamp closes the launch→stamp window the RunPod path bridges with a post-hoc stamp; keyed to the OLD handle identity so fresh dispatches are never suppressed. Source: backend_poll.py:3527-3568, router.py:3170-3172 (M3b precedent). Alternatives: post-hoc `_stamp_lease_failover_of` only — rejected (crash window); pre-create stamp in the caller — rejected (a failed create would wedge the run behind `sidecar_persistence_failed`).
- **Gate = clean residue only (no capacity-class evidence classifier).** Why/Source/Alternatives: §3 design question 4 (the #1112 cost-cap evidence classifies `unknown` — an evidence-keyed gate would miss the motivating incident; the watcher already authorizes a full-ladder re-run on this exact state).
- **Change 4b: symmetric `_lease_already_failed_over` extension.** Why: closes the cross-rung double-provision window (a concurrent second vanish-triggerer passing the outside-flock pre-check before the GCP stamp lands could otherwise launch a paid RunPod pod alongside the GCP retry). Source: consistency-checker difference 6; router.py:5257-5261 (current `lease.backend == "runpod"` predicate); M3b precedent :3170-3172. Alternative: document + accept the narrow race — rejected (the fix is a two-line predicate extension mirroring Change 4, with a pinning test; accepting a paid double-provision window when the close is this cheap fails the #659 exactly-once spirit).
