4. `write_pods_conf` (pod_config.py:250-278) — atomic write. New signature:

   ```python
   def write_pods_conf(
       pods: list[Pod],
       path: Path = PODS_CONF,
       *,
       allow_remove: frozenset[str] = frozenset(),
   ) -> None:
   ```

   Body:
   - Compute `header_lines` + row payload as today.
   - Never-drop-RUNNING guard (fires BEFORE the write):
     - `on_disk = {p.name for p in parse_pods_conf(path)} if path.exists() else set()`
     - `new = {p.name for p in pods}`
     - `dropped = on_disk - new - allow_remove`
     - If `dropped`: lazy `from runpod_api import list_team_pods, RunPodError` (matches pod_config.py:951 pattern).
       - `try: live = {p.name: p for p in list_team_pods()}` `except RunPodError as e: ...`:
         - On RunPodError → re-add ALL rows in `dropped` (from `parse_pods_conf(path)`), print `WARN: could not verify live pod status ({e}); failing SAFE by keeping all on-disk rows`.
         - Otherwise for each `n in dropped`: if `live.get(n)` is None OR `live[n].desired_status.upper() != "RUNNING"` → allow the drop. Else re-add from `on_disk_rows[n]` and print `WARN: refusing to drop RUNNING pod '{n}' from pods.conf (live API says RUNNING); re-added. If this was intentional, pass allow_remove={{'{n}'}}.`
   - Atomic write: `tmp = path.with_suffix(path.suffix + ".tmp"); tmp.write_text(payload); os.replace(tmp, path)`.

## 11. Decision Rationale

- **Live-file location = `<git-common-dir>/eps/pods.conf` (v3; supersedes v2's `scripts/pods.conf.local`).**
  What: the live file lives INSIDE the repo's `.git` directory (`<main>/.git/eps/pods.conf`), not in the working tree.
  Why: `git clean -fdx` deletes ignored files inside the working tree, so a gitignored `scripts/pods.conf.local` would still be wiped by one destructive class (the Codex methodology + alternatives Must-Fix); nothing in `reset --hard` / `checkout .` / `restore .` / `clean -fd` / `clean -fdx` touches `.git` internals. Per-repo semantics are preserved (two clones don't collide), and BOTH existing resolution mechanisms already compute the git common dir (`_pods_conf_path.sh` GIT_COMMON_DIR; `pod_config._main_repo_scripts_dir`), so the resolver change is minimal.
  Source: git-clean documentation semantics (`-x` includes ignored files; `.git` never cleaned); Codex methodology Must-Fix 1 + Codex alternatives Must-Fix 1 (round 1); `scripts/_pods_conf_path.sh` (existing GIT_COMMON_DIR resolution).
  Alternatives: gitignored `scripts/pods.conf.local` (rejected: `clean -fdx` wipes it); `~/.task-workflow/pods.conf` (rejected: global-across-repos breaks per-repo semantics if a second checkout ever exists); XDG state dir (same objection + more resolution code).

- **Option choice = Hybrid A+B, A-first.**
  What: relocate live state out of git's blast radius (A) AND add the guard + atomic + self-heal layer (B).
  Why: the 2026-07-01 incident's root cause is git (reflog `HEAD@{13:30:38}: reset: moving to origin/main` — see evidence pack + Assumption 12), not a lost-update race — flock is already correct. A alone kills the whole git-clobber class. - **Guard placement = inside `write_pods_conf` (not at callsites).**
  What: the never-drop-RUNNING check lives in `write_pods_conf` with an `allow_remove` opt-out.
  Why: callsite-level guards are easy to forget on future writers; centralizing means every future writer inherits protection by default. `_remove_from_pods_conf` is the sole legitimate remove path and explicitly opts out.   Source: existing pattern in `_upsert_pods_conf` calls `write_pods_conf(rows)` uncritically; adding a callsite check to all 4 writers is more surface for bugs.

- **Atomic-write mechanism = `os.replace` (temp file in same dir).**
  What: write to `<path>.tmp`, then `os.replace(tmp, path)`.
  Why: POSIX-guaranteed atomic rename on same filesystem; no partial-file readers ever observe torn content. Zero deps.
  Source: standard Python idiom.
  Alternatives: `tempfile.NamedTemporaryFile(delete=False)` + `os.replace` (equivalent, more code); write-lock during write (already covered by `locked_pods_conf` — orthogonal, this is torn-read protection for lock-less shell readers).

  Why: bulk mode without a name filter could add arbitrary RunPod entries from the team account (permanent fleet, other users' pods) that don't belong in `pods.conf`. Managed-name filter mirrors `pod_lifecycle._MANAGED_PREFIXES`. Single-mode is user-invoked and safe to trust the caller's intent.
