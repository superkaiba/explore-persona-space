<h1>Issue #669 — Detect hung-but-RUNNING GCP VM (frozen non-terminal <code>eps/phase</code> + drain-timeout) and recover it automatically</h1>
<p><em>kind: infra — code change only, zero GPU-hours. Acceptance criterion is the test-verdict gate.</em></p>

<section class="v2">
<p><strong>v2 (revision after Phase&nbsp;2 critic REVISE + consistency-checker WARN).</strong> This revision keeps the v1 4-fix design and the §6/§6.5 goal/acceptance unchanged. It addresses the Methodology + Alternatives reconciler REVISE and the Consistency-checker WARN with three concrete corrections:</p>
<ul>
<li><strong>Signal split (Methodology M1).</strong> The existing GCP <code>drain_alarm</code> is set in TWO classes — (a) SSH transport / permission / timeout failure (gcp.py:3300-3306) and (b) a matched-but-unprocessable sentinel set / marker-post failure on a <em>healthy</em> VM (gcp.py:3326-3337). v1's <code>drain_alarm_active = bool(drain_alarm)</code> conflated them, so the wedge gate would have fired on (b) on a healthy long phase. v2 introduces a TYPED <code>reachability_alarm: bool</code> (Option M1a) set ONLY for the transport class; the wedge gate reads <code>reachability_alarm</code>, never the sentinel-processing class. A negative test pins the split.</li>
<li><strong>Atomic failover lease (Alternatives M3).</strong> The existing <code>_failover_dead_gcp_to_runpod</code> pre-checks <code>_lease_records_failover_of</code> OUTSIDE the launch flock and stamps <code>gcp_failover_of</code> AFTER the flock releases, so two concurrent triggerers (poller wedge + watchdog-TERMINATED, or two overlapping poll chains) both pass the pre-check and BOTH launch a paid RunPod pod. v2 adds an explicit <code>_lease_records_failover_of</code> re-check INSIDE the locked launch path (Option M3b — mirrors the existing reconnect-path re-check at router.py:3016) so a second triggerer that acquires the lock after the first stamped exits with no launch. A concurrent-atomicity test pins it.</li>
<li><strong>Conservative phase (Consistency-checker, Option 2).</strong> v1's Fix 4 widened the accept-set with a bare <code>terminal_terminated</code>, which bundled a SECOND behavior change (spot preemption + max-run-duration trips ALSO fail over) and SILENTLY INVERTED the existing <code>test_async_gcp_capacity_death_does_NOT_fail_over</code>. v2 instead introduces a NEW phase <code>terminal_wedged_terminated</code> emitted ONLY when the in-VM watchdog wrote <code>eps/phase=wedged</code> before <code>shutdown -h now</code>; the accept-set gains <code>terminal_wedged_terminated</code> and LEAVES <code>terminal_terminated</code> EXCLUDED. Spot-preempt / max-run-duration trips behave exactly as today, and the existing test stays green untouched.</li>
</ul>
<p><strong>Rationale captured for the conservative phase:</strong> Fix&nbsp;1 (poller-side wedge detection) already handles the no-phase-write-lands case independently — the watchdog's phase write is needed only when the network is healthy enough to write it, which is exactly when the VM CAN cleanly self-terminate. The two mechanisms remain complementary; the broad <code>terminal_terminated</code> widening was never load-bearing.</p>
</section>

<section class="plan-summary">
<p><span class="label">What this fixes:</span> a 3rd GCP "RUNNING-zombie" mode (#667) where a VM's guest networking dies (systemd-networkd DHCPv4 lease loss) but the VM stays <code>RUNNING</code>. The poller reads <code>eps/phase=workload</code> frozen forever, so neither the synchronous nor the async GCP→RunPod failover ever fires — only a manual <code>--backend runpod</code> pivot recovered it.</p>
<p><span class="label">Four code changes (all in workflow surface <code>backends/gcp.py</code> + <code>scripts/backend_poll.py</code> + <code>backends/base.py</code>):</span></p>
<ul>
<li><span class="label">Fix 2 (PRIMARY recovery):</span> an in-VM <em>reachability</em> watchdog embedded in <code>render_startup_script</code> — probes metadata server <code>169.254.169.254</code> + an external endpoint; on sustained loss (~5&nbsp;min) writes <code>eps/phase=wedged</code> (best-effort) then forces a clean <code>TERMINATED</code> via <code>shutdown -h now</code>. Reachability not liveness: a systemd <code>/dev/watchdog</code> keeps getting fed on a wedged VM (systemd&nbsp;#21083).</li>
<li><span class="label">Fix 1 (defense-in-depth):</span> in <code>gcp.py::poll</code>'s <code>if phase:</code> running branch, surface a TYPED <code>reachability_alarm</code> (transport-class drain failure only). The poller escalates to a new terminal phase <code>terminal_workload_wedged</code> when a non-terminal <code>eps/phase</code> has been stuck past a <strong>15-min staleness floor</strong> AND <code>reachability_alarm</code> is set. Staleness clock = a <code>last_phase</code>/<code>last_phase_change_ts</code> pair in the handle sidecar.</li>
<li><span class="label">Fix 4 (routing):</span> add <code>terminal_workload_wedged</code> AND <code>terminal_wedged_terminated</code> to <code>_is_gcp_async_workload_failure</code>'s accept-set so #659's <code>_failover_dead_gcp_to_runpod</code> (now exactly-once under concurrency via an in-flock re-check) fires on both the poller-detected wedge and the watchdog's self-terminate. <code>terminal_terminated</code> stays EXCLUDED (no spot/max-run-duration regression).</li>
<li><span class="label">Fix 3 (composition):</span> add <code>--no-restart-on-failure</code> (<code>automaticRestart=false</code>) to the launch argv. <code>--maintenance-policy=TERMINATE</code> is already present (gcp.py:1397). Confirmed to compose with <code>--instance-termination-action=DELETE</code> (different lifecycle boundaries).</li>
</ul>
<p><span class="label">Baselines / controls:</span> the anti-false-positive tests (recent phase change → still <code>running</code>; sentinel-processing alarm → still <code>running</code>) are the load-bearing controls — they rule out killing a legitimately-long-running or merely-noisy phase. No-regression to the existing crashed-workload (#659) and healthy-running poll paths is asserted by the pre-existing test suite staying green (now provably true — <code>terminal_terminated</code> is untouched).</p>
<p><span class="label">Compute:</span> <strong>Estimated GPU-hours (total): 0</strong>. CPU-only code change + unit tests; no pod, no VM, no live launch in scope (a live GCP acceptance run is optional and explicitly out of scope for the test-verdict gate).</p>
<p><span class="label">Evaluation:</span> the named tests pass; <code>uv run pytest tests/test_gcp_backend.py tests/test_backend_poll.py tests/test_router.py</code> stays green; <code>ruff check</code> clean on touched files; <code>bash -n</code> clean on both startup-script render branches.</p>
<p><span class="label">Risks (top 2):</span> (1) a false-positive wedge classification killing a healthy long-running phase — mitigated by the conjunction of frozen-phase + <em>reachability</em>-class alarm + a floor well above any normal phase duration; (2) the startup-script byte-identity snapshot test will trip and must be deliberately regenerated.</p>

<h2>1. Goal &amp; acceptance criteria</h2>
<p>Close the remaining GCP-failover coverage gap so a hung-but-<code>RUNNING</code> GCE VM (frozen non-terminal <code>eps/phase</code> from dead guest networking) self-recovers to a RunPod re-dispatch with no human pivot. Two independent mechanisms: an in-VM reachability watchdog that flips the VM to a poller-dead <code>TERMINATED</code> state (primary, because it works even when the poller can't SSH in), and a poller-side frozen-phase + reachability-timeout escalation (defense-in-depth, for the marginal case where the VM is too network-dead to self-terminate but the describe API still resolves).</p>
<p><strong>Acceptance (from the task body):</strong></p>
<ol>
<li>The new tests pass (the wedge classifier, the anti-false-positive controls, the signal split, the producer-side reachability wiring, the exactly-once failover under concurrency, the watchdog presence, and the scheduling flags).</li>
<li>A frozen-non-terminal-phase + reachability-timeout GCP VM is classified dead and fails over to RunPod <strong>exactly once</strong>.</li>
<li>A watchdog self-<code>TERMINATE</code> (which wrote <code>eps/phase=wedged</code> → <code>terminal_wedged_terminated</code>) also routes to the failover.</li>
<li>No regression to the crashed-workload (#659) path or the healthy-running poll path: the existing <code>tests/test_gcp_backend.py</code> / <code>tests/test_backend_poll.py</code> / <code>tests/test_router.py</code> suites stay green. <strong>(v2: this is now provably true — the accept-set widening uses a NEW <code>terminal_wedged_terminated</code> phase and leaves <code>terminal_terminated</code> excluded, so <code>test_async_gcp_capacity_death_does_NOT_fail_over</code> is unaffected.)</strong></li>
</ol>

<h3>1.bis Kill criteria (when to STOP / escalate instead of pressing on)</h3>
<p>This is a code change with a test-verdict gate, not a GPU run, so the kill criteria are correctness-discovery points, not metric thresholds. STOP and escalate (do NOT paper over) if any of these hold:</p>
<ul>
<li><strong>Lease atomicity cannot be made compatible.</strong> If the M2.6 concurrent-failover test cannot be made to pass WITHOUT breaking #659's existing exactly-once tests (e.g. the in-flock re-check changes the single-triggerer behavior those tests pin), STOP — the lease-atomicity question is a #659 contract issue and must be escalated separately rather than forced through here.</li>
<li><strong>The watchdog phase write cannot land before shutdown.</strong> If <code>eps/phase=wedged</code> proves impossible to write reliably before <code>shutdown -h now</code> returns (e.g. the metadata write path is too slow / racy at shutdown), STOP using the watchdog's phase write as a failover trigger — DROP Fix&nbsp;2's contribution to the atomic failover and rely on Fix&nbsp;1 alone (the poller-side wedge detection already covers the goal independently; the watchdog then only buys a clean TERMINATED, not a routed failover). This is a graceful degrade, not a hard block.</li>
<li><strong>The signal split is not cleanly separable.</strong> If the transport-class alarm (gcp.py:3300-3306) and the sentinel-processing-class alarm (gcp.py:3326-3337) cannot be distinguished at the point <code>reachability_alarm</code> is set (e.g. both classes funnel through one return path that loses the discriminator), STOP and re-plan the signal carrier — do not ship a <code>reachability_alarm</code> that still fires on the sentinel-processing class, which is the exact M1 defect.</li>
</ul>

<h3>2.1 Research findings (web) — used to ground the design</h3>
<ul>
<li><strong>systemd-networkd DHCP-renewal-timeout bug (root-cause trigger).</strong> systemd issues <a href="https://github.com/systemd/systemd/issues/32045">#32045</a> ("does not retry renewing an expiring DHCP lease"), <a href="https://github.com/systemd/systemd/issues/33934">#33934</a> ("lease getting expired without retrying at T2"), <a href="https://github.com/systemd/systemd/issues/33288">#33288</a> ("Could not set DHCPv4 address: Connection timed out"), and Ubuntu <a href="https://bugs.launchpad.net/bugs/2054977">LP&nbsp;#2054977</a>. The failure mode: under load (netlink-request timeout from high disk read + memory pressure) the renew at T2 times out, systemd does <em>not</em> retry, the lease expires, and the interface loses connectivity <em>permanently</em> — exactly the #667 serial tail. This trigger is fixed separately by the parallel extractor-memory task; #669 is the BACKSTOP. Affects multiple systemd versions (245/249/254/255) across cloud providers — i.e. it is an OS bug, not a GCP-specific flake, so it can recur on any Ubuntu DLVM image regardless of the extractor fix.</li>
<li><strong>Reachability vs liveness watchdog.</strong> systemd <a href="https://github.com/systemd/systemd/issues/21083">#21083</a> ("watchdog: Still fed when rootfs is non-responsive") confirms a liveness watchdog (the service sends <code>sd_notify</code> heartbeats / <code>/dev/watchdog</code> keeps ticking) does NOT catch a hung-but-running condition — the process is alive and keeps feeding the dog while the system is unusable. The watchdog MUST probe actual external reachability (can I reach the metadata server + an internet endpoint?), not "am I still ticking?".</li>
<li><strong>GCE scheduling-flag composition.</strong> Google's <a href="https://docs.cloud.google.com/compute/docs/instances/setting-vm-host-options">host-maintenance docs</a> + <a href="https://cloud.google.com/compute/docs/instances/limit-vm-runtime">max-run-duration docs</a> confirm <code>onHostMaintenance</code>, <code>automaticRestart</code>, <code>maxRunDuration</code>, and <code>instanceTerminationAction</code> are independent fields of the same <code>scheduling</code> block and compose freely. <code>TERMINATE</code> is the only supported <code>onHostMaintenance</code> for GPU instances (already enforced — gcp.py:1341-1343). Setting <code>automaticRestart=false</code> (<code>--no-restart-on-failure</code>) ensures the watchdog's self-<code>shutdown</code> is final (the VM does NOT auto-restart back into the same wedged state) — and because <code>instanceTerminationAction=DELETE</code> governs only the <code>maxRunDuration</code>/spot-preemption boundary, the two do not conflict: a watchdog <code>shutdown -h now</code> reaches <code>TERMINATED</code>, which the poller already reads as dead.</li>
</ul>

<h2>3. Hypothesis (falsifiable)</h2>
<p>Not an experiment — but the design carries one falsifiable correctness claim and two false-positive bounds:</p>
<ul>
<li><strong>Recovery claim:</strong> with Fixes 1+4 in place, a poll observing <code>status==RUNNING</code> + <code>eps/phase</code> frozen at a non-terminal value for &gt; the staleness floor + a <em>reachability</em> alarm returns <code>status="dead", current_phase="terminal_workload_wedged"</code>, which <code>_is_gcp_async_workload_failure</code> accepts and routes through the (now concurrency-safe) exactly-once failover. Falsified if the wedge test launches RunPod zero or ≥2 times.</li>
<li><strong>False-positive bound A (recency):</strong> a poll observing a phase that CHANGED within the staleness floor (even with a transient reachability alarm) stays <code>running</code>.</li>
<li><strong>False-positive bound B (signal split):</strong> a poll observing a frozen non-terminal phase past the floor with ONLY a sentinel-processing-class alarm (a healthy VM with a malformed sentinel / transient marker-post failure) stays <code>running</code> — because the wedge gate reads <code>reachability_alarm</code>, which the sentinel-processing class never sets. Falsified if the signal-split negative test returns <code>dead</code>.</li>
</ul>

<h2>4. Design — file-by-file</h2>

<h3>4.1 Staleness-clock storage (the load-bearing architecture decision)</h3>
<p>The wedge clock needs persistent state across poll ticks. <code>GcpBackend.poll(handle)</code> is called from <code>backend_poll.py</code>, which already owns the sidecar path (<code>resolve_handle_sidecar_path</code>). The poller is process-local-stateless across ticks, so the only durable carrier is the <strong>handle sidecar JSON</strong> (<code>.claude/cache/issue-&lt;N&gt;-handle.json</code>, cwd-independent per <code>default_handle_sidecar_path</code>).</p>
<p><strong>Decision: track phase-change in <code>backend_poll.py</code>, not inside <code>poll()</code>.</strong> Keep <code>GcpBackend.poll(handle)</code> pure (it already reads only the describe + guest-attribute round-trips). The poller, which has BOTH the prior sidecar and the fresh <code>PollResult</code>, owns the staleness clock:</p>
<ol>
<li>The sidecar gains an optional <code>last_phase</code> + <code>last_phase_change_ts</code> (epoch seconds) pair, stored inside <code>RunHandle.extra</code> and persisted via the existing <code>write_handle_sidecar</code>. <strong>Verified:</strong> <code>serialize_handle</code> round-trips <code>extra</code> as a plain dict (<code>dict(handle.extra)</code>, issue_dispatch.py:340), so no schema migration is needed — extra keys survive the round-trip and a missing key reads as absent. Absent on a freshly-dispatched sidecar (pre-this-change handles read as "no clock yet" → fail toward <em>running</em>, never toward a false wedge).</li>
<li><code>poll()</code> emits, on the running branch, the <em>observed</em> phase in <code>current_phase</code> (unchanged) AND a new TYPED boolean <code>reachability_alarm</code> (the transport-class drain failure — see 4.2(a)). It does NOT itself classify the wedge.</li>
<li>The poller compares the observed running phase to the sidecar's <code>last_phase</code>:
  <ul>
  <li>phase changed (or first observation) → update <code>last_phase</code> + <code>last_phase_change_ts = now</code> in the sidecar, emit the running result unchanged;</li>
  <li>phase unchanged AND <code>now - last_phase_change_ts &gt; STALENESS_FLOOR_SEC</code> AND <code>result.reachability_alarm</code> → rewrite the result to <code>status="dead", current_phase="terminal_workload_wedged"</code> (this is what the async predicate then matches);</li>
  <li>phase unchanged but within the floor, OR no reachability alarm → emit running unchanged (the false-positive guard, covering both the recency case and the sentinel-processing-alarm case).</li>
  </ul>
</li>
</ol>
<p><strong>Why poller-side, not <code>poll()</code>-side?</strong> Keeping the clock in the poller means <code>poll()</code> stays a pure function of <code>(handle, gcloud responses)</code> — its entire existing test suite (which constructs handles directly and never persists a sidecar) is unaffected, and the wedge logic is unit-testable in <code>test_backend_poll.py</code> by writing a sidecar with a stale <code>last_phase_change_ts</code> and a poll-double returning a running result with the typed alarm set. The alternative — threading sidecar state into <code>poll()</code>'s signature — would touch every <code>poll()</code> test and every backend's signature for a GCP-only need.</p>
<p><strong>Smaller-scope option considered and rejected:</strong> using the existing <code>creationTimestamp</code> (VM birth) or <code>drain_log_mtime_ago</code> (workload-log mtime) as the clock with zero sidecar change. Rejected because (a) <code>creationTimestamp</code> is run age, not phase age — it would false-fire on every long healthy run past the floor; (b) <code>drain_log_mtime_ago</code> is <code>None</code> on a transport failure (exactly the wedge case — SSH times out, so no fresh mtime), so it cannot be the clock for the very condition we are detecting. The phase-change clock is the only signal that is both phase-specific and survives the SSH failure (it is read from the prior sidecar, not the dead VM).</p>

<h3>4.2 <code>src/explore_persona_space/backends/gcp.py</code> + <code>backends/base.py</code></h3>
<p><strong>(a) Fix 1 — surface a TYPED <code>reachability_alarm</code> on the running branch (signal split, M1a).</strong></p>
<p><strong>The split.</strong> <code>_drain_sentinels</code> returns a <code>drain_alarm</code> string in TWO distinct classes, both reaching the <code>if phase:</code> running branch's <code>drain_alarm</code> local:</p>
<ul>
<li><strong>Transport class</strong> (gcp.py:3300-3306) — the drain SSH itself returned a non-zero exit code (transport down / permission / timeout). The early return at line 3306 is <code>return 0, None, alarm, "", None</code> (gate is <code>None</code>). This is the signal that the VM is unreachable — the wedge signature.</li>
<li><strong>Sentinel-processing class</strong> (gcp.py:3326-3337) — the SSH SUCCEEDED (a HEALTHY VM), but a matched sentinel set produced 0 processed markers (empty/unparseable body or a transient marker-post failure). The return at line 3337 is <code>return 0, gate, alarm, log_tail, log_mtime_ago</code> (gate populated, log_tail present). This is NOT a reachability problem — the VM answered.</li>
</ul>
<p>v1's <code>drain_alarm_active = bool(drain_alarm)</code> conflated these. v2 introduces a typed field set ONLY for the transport class. <strong>The discriminator at the running-branch <code>_drain_sentinels</code> return:</strong> the transport class returns <code>gate is None</code> with empty <code>log_tail</code>; the sentinel-processing class returns a populated <code>gate</code>/<code>log_tail</code>. Carry the class explicitly out of <code>_drain_sentinels</code> rather than re-deriving it heuristically — add a 6th return element (a typed enum/flag) so the caller never has to sniff <code>gate is None</code>:</p>
<pre><code># gcp.py _drain_sentinels — make the alarm CLASS explicit (no heuristic at the call site).
# Transport-class return (line ~3306):
    return 0, None, alarm, "", None, "transport"        # was: ... , None
# Sentinel-processing-class return (line ~3337):
    return 0, gate, alarm, log_tail, log_mtime_ago, "sentinel_processing"
# Clean / no-alarm return (line ~3338):
    return processed, gate, "", log_tail, log_mtime_ago, ""
</code></pre>
<pre><code># base.py PollResult — new TYPED field, default False so every other backend serializes identically.
# NOTE: v2 introduces ONLY this field (it replaces v1's generic ``drain_alarm_active`` —
# that field was never load-bearing for anything but the wedge gate, so there is no
# backward-compat burden; do NOT also add ``drain_alarm_active``).
reachability_alarm: bool = False
</code></pre>
<pre><code># gcp.py poll(): unpack the new class element ...
(drained, drain_gate, drain_alarm, drain_log_tail, drain_log_mtime_ago, drain_alarm_class) = \
    self._drain_sentinels(handle, zone)
# ... and on the if phase: running branch (~3072):
merged = _with_drain(_coarse_poll(status="running", current_phase=phase))
merged = replace(merged, reachability_alarm=(drain_alarm_class == "transport"))   # NEW
return _apply_lane_quiet_interval(
    merged,
    run_age_sec=_age_seconds(payload.get("creationTimestamp"), datetime.now(UTC)),
    lane_anomaly=bool(drain_alarm),   # lane-anomaly (interval) keeps BOTH classes — degraded

  # GCE metadata server + an external endpoint; on sustained loss forces a

      echo "[eps-watchdog] reachability probe FAILED ($fails/$threshold)" >&3 2>/dev/null || true

        # enough to land it, the poller maps TERMINATED+wedged -> terminal_wedged_terminated

        # network-dead), Fix 1's poller-side wedge detection is the recovery instead.
        _eps_phase wedged 2>/dev/null || true
        shutdown -h now 2>/dev/null || poweroff -f 2>/dev/null || halt -f
        return 0
      fi
    fi
  done

<h2>11. Decision rationale (load-bearing constants + design choices)</h2>
<p>Not ML hyperparameters, but load-bearing infra constants + the three v2 implementation-option choices — each grounded:</p>
<table>
<tr><th>Choice / constant</th><th>Value</th><th>Why / source</th></tr>
<tr><td><strong>M1 signal split</strong> — typed <code>reachability_alarm</code> vs generic alarm</td><td>Option M1a (new typed field)</td><td>The existing <code>drain_alarm</code> is set in two classes — transport failure (gcp.py:3300-3306, the wedge signature) and sentinel-processing failure on a HEALTHY VM (gcp.py:3326-3337). The wedge gate must fire ONLY on the transport class, else a malformed sentinel on a healthy long phase yanks it to RunPod. M1a (a dedicated <code>reachability_alarm</code> whose name states its meaning) over M1b (re-narrowing a generic boolean) because the field is NEW in this plan anyway — there is no backward-compat reason to keep a confusingly-named generic. The class is carried explicitly out of <code>_drain_sentinels</code> (a 6th return element) rather than re-derived heuristically at the call site. <strong>Source:</strong> direct code read gcp.py:3221, 3300-3306, 3326-3337; reconciler Methodology REVISE M1.</td></tr>
<tr><td><strong>M3 lease atomicity</strong> — check-and-stamp inside the launch flock</td><td>Option M3b (in-flock re-check)</td><td>The existing failover flow pre-checks <code>_lease_records_failover_of</code> OUTSIDE the flock (backend_poll.py:517) and stamps <code>gcp_failover_of</code> AFTER it releases (backend_poll.py:572), so two concurrent triggerers both pass the pre-check and both launch. Fix&nbsp;1 introduces a second concurrent triggerer (poller-wedge + watchdog-TERMINATED), making the gap live. M3b adds an explicit in-flock re-check + an in-flock stamp, directly mirroring the proven reconnect-path re-check at router.py:3016 — lower blast radius than M3a (reordering the stamp write), and it keeps #659's single-triggerer sequential behavior byte-for-byte. <strong>Source:</strong> direct code read backend_poll.py:514-572, router.py:1973-2005, router.py:3016; reconciler Alternatives REVISE M3.</td></tr>
<tr><td><strong>Conservative phase</strong> — <code>terminal_wedged_terminated</code> vs broad <code>terminal_terminated</code></td><td>Consistency-checker Option 2 (new phase)</td><td>v1's bare <code>terminal_terminated</code> accept bundled a SECOND behavior change (spot/max-run-duration trips also fail over) and silently inverted the existing <code>test_async_gcp_capacity_death_does_NOT_fail_over</code>. Option 2 introduces a watchdog-specific phase (gated on <code>eps/phase=wedged</code> written before shutdown), mirroring the existing <code>eps/phase=failed</code>+<code>workload_started</code> discrimination (gcp.py:3042-3057). Single-variable-clean: only the #669 wedge path fails over; spot/max-run-duration behave exactly as today. Fix&nbsp;1 independently covers the no-phase-write case, so the broad widening was never load-bearing. <strong>Source:</strong> consistency-checker WARN; gcp.py:3042-3057 discrimination precedent; test_backend_poll.py:451.</td></tr>
<tr><td><code>GCP_STALENESS_FLOOR_SEC</code></td><td>900 (15 min)</td><td>Bounded BELOW by: the #667 wedge ran ~32&nbsp;min before manual detection (workload started 11:01:50Z, DHCP died 11:34:06Z), so any floor &lt; ~30&nbsp;min catches it. Bounded ABOVE by: it must exceed any normal inter-phase gap so a healthy run never trips. The GCP drain SSH timeout is 300s (gcp.py:1819) and the bg-poll quiet interval is up to 1800s (30 min) — a floor of 900s = 15&nbsp;min sits comfortably between (≥ 2× the drain timeout + ≥ 1 normal poll cycle, &lt; the wedge window, &lt; the 30-min quiet interval so at least one poll re-evaluates within the floor). <strong>Source:</strong> #667 evidence timeline + gcp.py:1819 (drain timeout) + base.py:291 (quiet interval). Adjustable upward to 1200s if the false-positive risk on long phases proves real in a future live run — flagged Medium confidence.</td></tr>
<tr><td>Watchdog probe interval</td><td>30s</td><td>Matches the drain/poll cadence granularity; 10 probes (= 5&nbsp;min) is a meaningful sustained-loss window without burning CPU on a tight loop. <strong>Source:</strong> body's suggested ~3-5&nbsp;min tunable; 30s × 10 = 5&nbsp;min lands at the top of that range (conservative — fewer false terminates).</td></tr>
<tr><td>Watchdog failure threshold</td><td>10 consecutive (≈5 min)</td><td>The systemd-networkd bug causes a PERMANENT lease loss (the renew never retries) — so once it fires the loss is sustained, and a 5-min confirmation window cleanly separates it from a transient single-endpoint blip. <strong>Source:</strong> systemd #32045/#33934 ("permanent loss of connectivity"); body's ~3-5&nbsp;min tunable.</td></tr>
<tr><td>Watchdog probe targets</td><td>metadata <code>169.254.169.254</code> AND external (HF)</td><td>The metadata server is link-local — reachable even with a dead DHCP lease if routing survives, so it alone under-detects; AND-ing an external endpoint catches the full-network-loss case. HF is the canonical external dependency every workload already needs. <strong>Source:</strong> body's explicit "metadata server + an external endpoint e.g. HF" + systemd #21083 (reachability not liveness).</td></tr>
<tr><td>Termination action + phase write</td><td><code>_eps_phase wedged</code> → <code>shutdown -h now</code> → <code>poweroff -f</code> → <code>halt -f</code></td><td>Writing <code>eps/phase=wedged</code> first is the trigger for the conservative <code>terminal_wedged_terminated</code> mapping; <code>shutdown -h now</code> reaches a clean <code>TERMINATED</code> (poller-dead); the hard-stop ladder covers a VM wedged enough that <code>systemd-shutdown</code> itself hangs. The phase write is best-effort — when it cannot land, Fix&nbsp;1 is the backstop (§1.bis kill-criterion). <strong>Source:</strong> body ("shutdown -h now"); the ladder + phase-write are the defensive extension for the wedged case.</td></tr>
<tr><td><code>--no-restart-on-failure</code> (automaticRestart=false)</td><td>added</td><td>A watchdog self-shutdown must be FINAL — auto-restart would bring the VM back into the same wedged state (the systemd bug recurs under the same load). Composes with <code>--instance-termination-action=DELETE</code> (independent scheduling fields). <strong>Source:</strong> Google host-maintenance + limit-vm-runtime docs (independent scheduling block fields); body Fix 3.</td></tr>
<tr><td>Watchdog daemon (bash bg process) vs systemd unit</td><td>bash bg process in startup script</td><td>Mirrors the existing <code>_eps_persist_diagnostics</code> EXIT-trap embedding (#658) — no extra unit file to install/enable on a DLVM image, reaped by the same EXIT trap, output to the same workload log. A systemd liveness watchdog would NOT catch this class anyway (systemd #21083). <strong>Source:</strong> #658 precedent + systemd #21083.</td></tr>
