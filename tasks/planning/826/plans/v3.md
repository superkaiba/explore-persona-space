## 1. Goal, requirement, acceptance criteria

**Goal (adopted verbatim from #827's `## Goal` — the consolidated duplicate; #826 itself is Goal-gate-exempt `kind: infra`):** Guard the #664 zombie-GPU stall override in `poll_pipeline.py` with run-liveness evidence: do not flag `vllm_worker_dead_zombie_gpu` when the log mtime is fresh (< ~60s) and session CPU is advancing; require the zombie condition to persist across two consecutive ticks before overriding status to `stalled`.

**Requirement (from #826 + consolidated sibling #827, binding):**
- (a) Liveness veto — never fire the zombie override while workload log evidence is fresh.
- (b) 2-consecutive-tick persistence, state-sidecar-backed (same mechanism as `ssh_fail_count` / `gpu_idle_since_epoch`).
- (c) True-positive #664 (stale logs + idle GPU + orphaned VRAM) must still fire at the 2nd tick at latest — narrow the predicate, never remove it.
- (d) Unit tests: fresh log ⇒ no stall flag on first tick; persistent zombie + stale log ⇒ stalled.

**One deliberate deviation from #827's literal sketch (justified in §2/§11):** the veto is on LOG FRESHNESS ONLY — `cpu_advancing` is NOT a veto term. The in-repo pinned TP test (`test_zombie_gpu_overrides_cpu_advancing_running_to_stalled`) and the test module's docstring establish that in the genuine #664 incident session CPU WAS advancing (the hung EngineCore main process burns Python-overhead CPU; that is exactly why the #518/#658 CPU-advancing override reported the hang healthy for 60+ min and why the zombie detector exists). In the stale-log + idle-GPU regime, `status == "running"` at the override site is only reachable via the cpu-advancing rescue — so an `or cpu_advancing` veto term makes the true positive structurally unreachable, violating requirement (c). #827's claim "#664's actual incident had a stale log + no CPU advance" is contradicted by the pinned test; the test is ground truth.

**Acceptance criteria:**
1. Replay fixture A (#816 steady-state FP: host-namespace zombie PIDs present every tick, phase-log mtime ~1s) ⇒ verdict `running`, `stall_reason` None, on every tick.
2. Replay fixture B (#778 transient FP: zombie PID on tick 1 during engine teardown, logs fresh ~8s; gone by tick 2) ⇒ `running` on both ticks; streak resets.
3. Replay fixture C (#664 TP: logs stale > `stall_sec`=900, GPU util 0, session CPU advancing, zombie PID both ticks) ⇒ `running` (deferred, WARNING logged) on tick 1, `stalled` + `stall_reason: vllm_worker_dead_zombie_gpu` on tick 2.
3b. Sparse-log healthy fixture (v3: zombie PIDs every tick, logs 60-900s old, GPUs busy — the #522-cadence regime on a host-namespace pod) ⇒ `running` every tick (veto coupled to `stall_sec`).

## 2. Method delta vs the current #664 predicate

**Current (scripts/poll_pipeline.py ~2656-2668):**
```python
stall_reason: str | None = None
if status == "running" and zombie_gpu_pids:
    log.error("zombie GPU allocation ... overriding status=running -> stalled (#664)", ...)
    status = "stalled"
    stall_reason = "vllm_worker_dead_zombie_gpu"
    cpu_override_active = False
```
Fires instantly, on a single sample, with no liveness cross-check. On host-PID-namespace RunPod containers every healthy compute PID satisfies the probe's `[ ! -d /proc/$zpid ]` arm (nvidia-smi reports host PIDs), so healthy runs flag (#816 steady-state; #778 transient teardown window).

**New predicate (pure conjunct-narrowing; no namespace-signature branch) — v3: veto threshold COUPLED to the effective stall window (round-1 critic-ensemble Must-Fix):**
```
zombie_candidate = (status == "running") and zombie_gpu_pids        # unchanged inputs
veto_sec        = max(ZOMBIE_VETO_FRESH_SEC, stall_sec)             # 60 is a FLOOR; default effective = stall_sec = 900
logs_fresh      = min(last_mtime_ago, phase_log_mtime_ago, shard_log_mtime_ago) <= veto_sec
fire            = zombie_candidate and not logs_fresh and prev_zombie_streak >= 1
```
The v2 fixed-60s threshold left a 60-900s exposure window: a healthy host-PID-namespace pod in a sparse-log-cadence phase (a documented in-repo regime — the `DEFAULT_STALL_SEC` comment cites #522's ~106-min checkpoint-only logging; such runs raise `--stall-sec`, which a fixed 60s veto ignores) with GPUs busy reaches `status=="running"` via the else-branch with logs 60-900s old and would fire the destructive override at tick 2. Coupling the veto to `stall_sec` (the in-scope effective per-tick value, honoring `--stall-sec` / `EPM_POLL_STALL_SEC`) closes it: the override now fires ONLY when ALL THREE logs are stale past the effective stall window — exactly the regime §4's TP argument already proves the true positive occupies. `ZOMBIE_VETO_FRESH_SEC` (60) survives as a FLOOR so a pathologically small `--stall-sec` (fast smoke configs) cannot strip the veto entirely.
- `logs_fresh` (any log within `veto_sec`) ⇒ WARNING log ("zombie-GPU signature with fresh liveness evidence — vetoed"), streak reset to 0, verdict stays `running`.
- `zombie_candidate and not logs_fresh and streak == 0` ⇒ WARNING ("deferring one tick"), streak → 1, verdict stays `running`.
- `zombie_candidate and not logs_fresh and streak >= 1` ⇒ existing override body runs verbatim (same `log.error`, same `status`/`stall_reason`/`cpu_override_active = False` assignments).
- No `zombie_candidate` this tick ⇒ streak reset to 0.

**Design fork resolution:** the explicit namespace-signature branch ("ALL compute PIDs unresolvable while logs fresh ⇒ host namespace, log once, skip forever") is REJECTED as unnecessary complexity: the log-freshness veto already neutralizes the steady-state #816 case on every tick (its logs are always fresh while healthy), and if such a run later genuinely stalls (logs go stale + GPU idle + VRAM held), the zombie path firing is the CORRECT verdict — a permanent namespace-suppression would reintroduce the #664 blind spot. Simplest design satisfying (a)-(d) wins; asymmetric costs (missed zombie = bounded idle pod-hours, false positive = destructive `kill -KILL` reaper) are served by 2-tick persistence + the stall-window-coupled veto rather than by a suppression branch. (The "ALL PIDs unresolvable" signature also cannot distinguish host-namespace-healthy from all-workers-dead without log freshness anyway — round-1 Alternatives critic.)

## 11. Decision Rationale

- **Veto threshold = `max(ZOMBIE_VETO_FRESH_SEC, stall_sec)` — coupled to the effective stall window, with a 60s floor (env `EPM_ZOMBIE_VETO_FRESH_SEC`) [v3, round-1 critic-ensemble Must-Fix]**
  - **What:** the zombie override is vetoed unless EVERY workload log (`last_mtime_ago` / `phase_log_mtime_ago` / `shard_log_mtime_ago`) is stale past the effective per-tick stall window (`stall_sec`, honoring `--stall-sec` / `EPM_POLL_STALL_SEC`), floored at 60s.
  - **Why:** the workload's own processes stop appending in a genuine hang — the #664 TP had all mtimes past the 900s stall conjunction, while both observed false positives had fresh logs (#816 ~1s steady-state; #778 8s transient). A FIXED 60s threshold (v2) left a 60-`stall_sec` exposure: sparse-log-cadence workloads (the `DEFAULT_STALL_SEC` comment cites #522's ~106-min checkpoint-only logging) legitimately go log-quiet >60s while healthy, and on a host-PID-namespace pod with busy GPUs that fired the destructive override. Coupling to `stall_sec` makes the override's log-staleness requirement identical to the regime the TP argument already occupies, and inherits per-workload tuning for free. The 60s floor only binds for pathologically small `--stall-sec`. Note this is an EMPIRICAL separation, not an absolute guarantee — a sibling process can keep a log fresh on a hung run (accepted blind spot, §4).
  - **Source:** #816/#778 incident probes (log mtimes 1s / 8s); #664 incident (60+ min stale); #522 sparse-cadence regime via the `DEFAULT_STALL_SEC` comment (scripts/poll_pipeline.py:272-281); round-1 Alternatives-lens Must-Fix (both reviewers) for the coupling.
  - **Alternatives:** fixed 60s (v2) — rejected: the 60-`stall_sec` exposure window above; fixed `stall_sec/2` — rejected: still decoupled from the TP argument's regime and adds a second arbitrary ratio; a namespace-signature suppression branch — rejected (§2).

- **Defensive sidecar parse (`try/except (TypeError, ValueError) → 0` around the `zombie_streak` int parse) [v3, round-1 Alternatives Must-Fix]**
  - **What:** a corrupted non-numeric sidecar value degrades to streak 0 instead of crashing the tick.
  - **Why:** `_load_state` guards unreadable FILES, not per-key corruption; a bare `int(...)` ValueError would crash `poll_once` on a corrupt value.
  - **Source:** `_update_ssh_fail_tracking`'s identical guard on `ssh_fail_count` (scripts/poll_pipeline.py:614-617).
  - **Alternatives:** regex pre-validation — rejected: the try/except is the established in-file idiom.

- **Persistence tick count = 2 consecutive ticks**
  - **What:** the override fires only when a stale-log zombie candidate was also recorded on the immediately preceding tick (`zombie_streak >= 1` in the sidecar).
  - **Why:** the #778 false positive was a TRANSIENT one-tick state (a dying host-namespace PID during a between-phase vLLM engine teardown/spin-up; a manual probe 2 min later found a healthy engine, judge 200s, no VRAM holder) — one-tick persistence filters exactly this class while delaying a genuine zombie by a single poll interval, the cheap side of the asymmetric cost (missed zombie = bounded idle pod-hours; false positive = destructive `kill -KILL` reaper per the SKILL.md Step-7 brief). #827 requirement (b) pins 2 ticks explicitly; requirement (c) pins "second tick at latest", which `_load_state`'s fail-soft `{}` (poll_pipeline.py:2273-2283) guarantees even on a first-ever tick.

- **VRAM floor unchanged at 1024 MiB (`ZOMBIE_GPU_MEM_MIN_MIB`, env `EPM_ZOMBIE_GPU_MEM_MIN_MIB`)**
  - **What:** the probe-side memory threshold that qualifies a compute PID as a zombie candidate is not touched.
  - **Why:** the false positives are namespace-visibility artifacts, not threshold artifacts — #816's healthy workers legitimately hold ≫1 GiB; raising the floor would not separate healthy from zombie and would only blind the detector to small-footprint dead workers. The fix belongs at the firing condition, not the probe.
  - **Source:** #664 (original constant), probe predicate read at scripts/poll_pipeline.py:~1057 (`[ "$zmem" -ge {ZOMBIE_GPU_MEM_MIN_MIB} ] && [ ! -d /proc/$zpid ]`).

- **`cpu_advancing` EXCLUDED from the veto (deviation from #827's literal sketch)**
  - **What:** the veto is log-freshness-only; #827 sketched `if zombie_candidate and (last_log_mtime_sec_ago < 60 or cpu_advancing): defer`.
  - **Why:** the pinned TP test (`test_zombie_gpu_overrides_cpu_advancing_running_to_stalled`, tests/test_poll_pipeline_zombie_gpu.py) encodes that in the genuine #664 hang session CPU WAS advancing (5000.0 vs prev 4000.0) — the hung EngineCore burns Python-overhead CPU, which is why the #518/#658 cpu-advancing rescue reported it healthy for 60+ min and why the zombie detector was added at all.   - **Source:** tests/test_poll_pipeline_zombie_gpu.py module docstring + TP test fixture (read in full, sanctioned); #518/#658 cpu-advancing override lineage; #664 round-8 incident ("hung 60+ min, reported healthy throughout").
  - **Alternatives:** honor the sketch literally — rejected as TP-breaking; use cpu_advancing only to EXTEND the streak requirement to 3 — rejected: complexity, and log freshness already carries the liveness signal a dead worker cannot fake.

- **No namespace-signature suppression branch**
  - **What:** rejected the design-fork option of detecting "ALL compute PIDs unresolvable while logs fresh ⇒ host-PID namespace" and permanently skipping the zombie check for that pod.
  - **Why:** the freshness veto already neutralizes the steady-state case tick-by-tick, and a permanent suppression would blind the detector if that same pod later genuinely zombies (logs stale + VRAM held) — reintroducing the #664 blind spot the detector exists to close. Conjunct-narrowing is the simplest design satisfying (a)-(d).
  - **Source:** #826 body's design-fork framing (paraphrase: it offers the namespace-signature branch as one option and asks planning to refine — the simplest design satisfying the binding requirements was chosen); #816/#778 probe evidence (both FPs had fresh logs).
  - **Alternatives:** log-once informational namespace note — allowed as a WARNING already present in the veto branch; a persistent per-pod namespace flag in the sidecar — rejected per above.
