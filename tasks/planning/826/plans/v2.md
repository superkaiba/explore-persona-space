## 1. Goal, requirement, acceptance criteria

**Goal (frontmatter, verbatim):** Guard the #664 zombie-GPU stall override in `poll_pipeline.py` with run-liveness evidence: do not flag `vllm_worker_dead_zombie_gpu` when the log mtime is fresh (< ~60s) and session CPU is advancing; require the zombie condition to persist across two consecutive ticks before overriding status to `stalled`.

**Requirement (from #826 + consolidated sibling #827, binding):**
- (a) Liveness veto — never fire the zombie override while workload log evidence is fresh.
- (b) 2-consecutive-tick persistence, state-sidecar-backed (same mechanism as `ssh_fail_count` / `gpu_idle_since_epoch`).
- (c) True-positive #664 (stale logs + idle GPU + orphaned VRAM) must still fire at the 2nd tick at latest — narrow the predicate, never remove it.
- (d) Unit tests: fresh log ⇒ no stall flag on first tick; persistent zombie + stale log ⇒ stalled.

**One deliberate deviation from #827's literal sketch (justified in §2/§11):** the veto is on LOG FRESHNESS ONLY — `cpu_advancing` is NOT a veto term. The in-repo pinned TP test (`test_zombie_gpu_overrides_cpu_advancing_running_to_stalled`) and the test module's docstring establish that in the genuine #664 incident session CPU WAS advancing (the hung EngineCore main process burns Python-overhead CPU; that is exactly why the #518/#658 CPU-advancing override reported the hang healthy for 60+ min and why the zombie detector exists). In the stale-log + idle-GPU regime, `status == "running"` at the override site is only reachable via the cpu-advancing rescue — so an `or cpu_advancing` veto term makes the true positive structurally unreachable, violating requirement (c). #827's claim "#664's actual incident had a stale log + no CPU advance" is contradicted by the pinned test; the test is ground truth.

**Acceptance criteria:**
1. Replay fixture A (#816 steady-state FP: host-namespace zombie PIDs present every tick, phase-log mtime ~1s) ⇒ verdict `running`, `stall_reason` None, on every tick.
2. Replay fixture B (#778 transient FP: zombie PID on tick 1 during engine teardown, logs fresh ~8s; gone by tick 2) ⇒ `running` on both ticks; streak resets.
3. Replay fixture C (#664 TP: logs stale > `stall_sec`=900, GPU util 0, session CPU advancing, zombie PID both ticks) ⇒ `running` (deferred, WARNING logged) on tick 1, `stalled` + `stall_reason: vllm_worker_dead_zombie_gpu` on tick 2.
4. All existing tests in `tests/test_poll_pipeline_zombie_gpu.py` pass (one adapted to the 2-tick regime, see §3), plus the 3 new tests.
5. `uv run ruff check .` clean; `uv run python scripts/workflow_lint.py` default run clean.
6. Downstream token consumers (`scripts/failure_classifier.py` `STALL_REASON_INFRA` frozenset line 56; `scripts/backend_poll.py` line 240 comment) are byte-untouched — the change is firing-condition-only.

## 2. Method delta vs the current #664 predicate

**Current (scripts/poll_pipeline.py ~2656-2668):**
```python
stall_reason: str | None = None
if status == "running" and zombie_gpu_pids:
    log.error("zombie GPU allocation ... overriding status=running -> stalled (#664)", ...)
    status = "stalled"
    stall_reason = "vllm_worker_dead_zombie_gpu"
    cpu_override_active = False
```
Fires instantly, on a single sample, with no liveness cross-check. On host-PID-namespace RunPod containers every healthy compute PID satisfies the probe's `[ ! -d /proc/$zpid ]` arm (nvidia-smi reports host PIDs), so healthy runs flag (#816 steady-state; #778 transient teardown window).

**New predicate (pure conjunct-narrowing; no namespace-signature branch):**
```
zombie_candidate = (status == "running") and zombie_gpu_pids        # unchanged inputs
logs_fresh      = min(last_mtime_ago, phase_log_mtime_ago, shard_log_mtime_ago) < ZOMBIE_VETO_FRESH_SEC  (60)
fire            = zombie_candidate and not logs_fresh and prev_zombie_streak >= 1
```
- `logs_fresh` ⇒ WARNING log ("zombie-GPU signature with FRESH liveness evidence — vetoed"), streak reset to 0, verdict stays `running`.
- `zombie_candidate and not logs_fresh and streak == 0` ⇒ WARNING ("deferring one tick"), streak → 1, verdict stays `running`.
- `zombie_candidate and not logs_fresh and streak >= 1` ⇒ existing override body runs verbatim (same `log.error`, same `status`/`stall_reason`/`cpu_override_active = False` assignments).
- No `zombie_candidate` this tick ⇒ streak reset to 0.

**Design fork resolution:** the explicit namespace-signature branch ("ALL compute PIDs unresolvable while logs fresh ⇒ host namespace, log once, skip forever") is REJECTED as unnecessary complexity: the log-freshness veto already neutralizes the steady-state #816 case on every tick (its logs are always fresh while healthy), and if such a run later genuinely stalls (logs go stale + GPU idle + VRAM held), the zombie path firing is the CORRECT verdict — a permanent namespace-suppression would reintroduce the #664 blind spot. Simplest design satisfying (a)-(d) wins; asymmetric costs (missed zombie = bounded idle pod-hours, false positive = destructive `kill -KILL` reaper) are served by 2-tick persistence + a 15×-margin freshness veto rather than by a suppression branch.

## 11. Decision Rationale

- **Veto freshness threshold = 60s (`ZOMBIE_VETO_FRESH_SEC`, env `EPM_ZOMBIE_VETO_FRESH_SEC`)**
  - **What:** the zombie override is vetoed when the freshest of `last_mtime_ago` / `phase_log_mtime_ago` / `shard_log_mtime_ago` is under 60s.
  - **Why:** a genuinely dead CUDA worker cannot be appending to workload logs; both observed false positives had fresh logs (#816: phase-log mtime ~1s steady-state; #778: 8s during engine teardown), while the genuine #664 hang had all mtimes past the 900s stall conjunction. 60s cleanly separates the regimes with 15× margin below `DEFAULT_STALL_SEC = 900` (scripts/poll_pipeline.py:281), so the veto can never mask a true stall: any log fresh enough to veto is also fresh enough to fail the stall conjunction's own staleness arms.
  - **Source:** #816 incident probe (`last_log_mtime_sec_ago: 8` on #778's marker; ~1s on #816), #827 body sketch (`< 60`), `DEFAULT_STALL_SEC = 900` read from scripts/poll_pipeline.py:276-282.
  - **Alternatives:** `stall_sec/2` (450s) — rejected: needlessly loose, delays nothing useful and couples two constants; 10s — rejected: a slow phase writing logs every ~30s would lose the veto and depend solely on persistence; making it a fraction of the poll interval — rejected: poll interval is caller-controlled and not visible at the override site.

- **Persistence tick count = 2 consecutive ticks**
  - **What:** the override fires only when a stale-log zombie candidate was also recorded on the immediately preceding tick (`zombie_streak >= 1` in the sidecar).
  - **Why:** the #778 false positive was a TRANSIENT one-tick state (a dying host-namespace PID during a between-phase vLLM engine teardown/spin-up; a manual probe 2 min later found a healthy engine, judge 200s, no VRAM holder) — one-tick persistence filters exactly this class while delaying a genuine zombie by a single poll interval, the cheap side of the asymmetric cost (missed zombie = bounded idle pod-hours; false positive = destructive `kill -KILL` reaper per the SKILL.md Step-7 brief). #827 requirement (b) pins 2 ticks explicitly; requirement (c) pins "second tick at latest", which `_load_state`'s fail-soft `{}` (poll_pipeline.py:2273-2283) guarantees even on a first-ever tick.
  - **Source:** #827 body (binding requirements b/c + diff sketch); #778 incident timeline; sidecar increment/reset pattern from `ssh_fail_count` (poll_pipeline.py:615-655, `SSH_FAIL_REFRESH_THRESHOLD` #488) and `gpu_idle_since_epoch` (~2781/2788).
  - **Alternatives:** 3+ ticks — rejected: adds a full extra interval of idle-pod burn on every genuine zombie for no observed FP class it would additionally filter; a wall-clock window (e.g. "persists ≥120s") instead of tick count — rejected: poll cadence varies by caller, and the tick-count idiom matches the existing sidecar counters.

- **VRAM floor unchanged at 1024 MiB (`ZOMBIE_GPU_MEM_MIN_MIB`, env `EPM_ZOMBIE_GPU_MEM_MIN_MIB`)**
  - **What:** the probe-side memory threshold that qualifies a compute PID as a zombie candidate is not touched.
  - **Why:** the false positives are namespace-visibility artifacts, not threshold artifacts — #816's healthy workers legitimately hold ≫1 GiB; raising the floor would not separate healthy from zombie and would only blind the detector to small-footprint dead workers. The fix belongs at the firing condition, not the probe.
  - **Source:** #664 (original constant), probe predicate read at scripts/poll_pipeline.py:~1057 (`[ "$zmem" -ge {ZOMBIE_GPU_MEM_MIN_MIB} ] && [ ! -d /proc/$zpid ]`).
  - **Alternatives:** raise to 4096 MiB — rejected per above; per-GPU-type scaling — rejected: complexity with no discriminating power for this failure class.

- **`cpu_advancing` EXCLUDED from the veto (deviation from #827's literal sketch)**
  - **What:** the veto is log-freshness-only; #827 sketched `if zombie_candidate and (last_log_mtime_sec_ago < 60 or cpu_advancing): defer`.
  - **Why:** the pinned TP test (`test_zombie_gpu_overrides_cpu_advancing_running_to_stalled`, tests/test_poll_pipeline_zombie_gpu.py) encodes that in the genuine #664 hang session CPU WAS advancing (5000.0 vs prev 4000.0) — the hung EngineCore burns Python-overhead CPU, which is why the #518/#658 cpu-advancing rescue reported it healthy for 60+ min and why the zombie detector was added at all. In the stale-log + idle-GPU regime, `status == "running"` at the override site is ONLY reachable via that rescue (`cpu_override_active=True`), so an `or cpu_advancing` veto would make the true positive unreachable on every reachable path — violating requirement (c). #827's contrary prose ("stale log + no CPU advance") is contradicted by the in-repo test; the test is ground truth.
  - **Source:** tests/test_poll_pipeline_zombie_gpu.py module docstring + TP test fixture (read in full, sanctioned); #518/#658 cpu-advancing override lineage; #664 round-8 incident ("hung 60+ min, reported healthy throughout").
  - **Alternatives:** honor the sketch literally — rejected as TP-breaking; use cpu_advancing only to EXTEND the streak requirement to 3 — rejected: complexity, and log freshness already carries the liveness signal a dead worker cannot fake.

- **No namespace-signature suppression branch**
  - **What:** rejected the design-fork option of detecting "ALL compute PIDs unresolvable while logs fresh ⇒ host-PID namespace" and permanently skipping the zombie check for that pod.
  - **Why:** the freshness veto already neutralizes the steady-state case tick-by-tick, and a permanent suppression would blind the detector if that same pod later genuinely zombies (logs stale + VRAM held) — reintroducing the #664 blind spot the detector exists to close. Conjunct-narrowing is the simplest design satisfying (a)-(d).
  - **Source:** #826 body design-fork instruction ("Prefer simplest satisfying (a)-(d)"); #816/#778 probe evidence (both FPs had fresh logs).
  - **Alternatives:** log-once informational namespace note — allowed as a WARNING already present in the veto branch; a persistent per-pod namespace flag in the sidecar — rejected per above.
