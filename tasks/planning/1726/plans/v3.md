## Overview / Motivation

Task #1689's `fit_ladder` phase ran 5 h 14 m at 0% GPU with zero log output after
its `[phase=fit_ladder]` banner while `eval_results/issue_1689/ladder/` did not
exist on disk — the phase was indistinguishable from a wedge, and a crash /
preemption / stop would have lost 100% of the compute. Three enforcement layers
already existed for the persistence half of the fix (`code-style.md` L53
intra-phase clause; the plan's own §9 checkpoint promise; `code-reviewer.md`
Step 3.6) and none bit, because all three key off a PROJECTED WALL-TIME (~1h)
that the plan never sized for this loop. This plan closes the two genuinely
absent guards — a per-unit progress-line duty and a unit-COUNT trigger that
needs no wall estimate — and mirrors them into the review gates that already
own long-loop restartability. It does NOT rewrite the checkpoint clause itself
(the persistence anti-pattern text is already there and correct).

## Goal

Require every long unit-loop to emit a per-unit progress line and to trip the
checkpoint requirement on a unit COUNT (~50) as well as a projected wall-time, and
mirror both into the implementation-review gates that already own long-loop
restartability.

## Enforcement-miss decision

**DECLINE** a mechanical `workflow_lint` scan. The rationale:

- The specific #1689 shape (`out["<key>"][<key>] = <func>(...)` inside a
  for-loop over a named iterable with no `write_json` / `torch.save` /
  `open(...).write` inside the loop) is grep-able in principle, but the
  false-positive surface is broad: legitimate aggregation code
  (compute-once-then-write-metadata phases, small-N summary loops that
  legitimately finish in under a minute, per-phase drivers that
  intentionally accumulate a short manifest before writing) hits the
  same pattern, and the false-negative surface is bigger still — every
  non-dict accumulator (list `.append`, `defaultdict`, `pd.DataFrame`
  concat) sidesteps the scan.
- The T2 count trigger already closes the specific enforcement gap that
  let #1689 through: reviewer-side, a loop with a named-unit iterable of
  size > ~50 and no per-unit write is a Major substantive finding by
  Step 3.6 alone. Adding a mechanical scan on top would create a lint
  that flags at compose-time SOME instances of a class the reviewer
  already flags at review-time from the diff itself — the reviewer's
  read is the one that would have caught #1689 (both `code-reviewer` and
  `codex-code-reviewer` PASSed the fit_ladder patch; the failure is the
  Step-3.6 trigger did not fire, not that Step 3.6 lacked a mechanical
  companion).
- The count trigger + progress-line duty are what makes Step 3.6 fire
  from the diff alone with no wall-time estimate; that is the smallest
  change that closes the sizing-blind hole, and no `workflow_lint` scan
  can substitute for the reviewer actually reading the loop.

If the T2 trigger is later found to miss a distinct sub-class (e.g. a
dispatcher whose named-unit iterable is dynamically sized and the diff
size < ~50 items in the closure), that is a follow-up sizing question
for the count threshold, not a `workflow_lint` question.

## Risks

- **Log-bloat risk on legitimate large-N loops.** A 100k-row streaming
  eval loop emitting one line per completed row would flood pod logs.
  Mitigation: the duty is scoped to loops that ALSO owe per-unit
  persistence (i.e. the trigger set is the T1/T2 OR on the checkpoint
  clause), which is exactly the class where per-unit output is already
  cheap relative to per-unit compute. A 100k-row streaming pass is
  external-stream-presumption-covered by the checkpoint clause itself;
  its per-chunk breadcrumb is one line per PERSISTED CHUNK, not one
  line per row, and the canonical shape's `k/N` form makes chunking
  natural. Implementer should record "chunk N/M" for chunked persisted
  streams; this is consistent with the code-style clause's atomic-JSONL
  append semantics and does not need separate rule text.
- **~50 is a soft heuristic.** A 45-unit loop with 20 min per unit
  still owes checkpointing; that case is covered by T1 (wall > ~1h)
  and the two triggers are OR'd, so a loop trips the duty if EITHER
  fires. The Design language uses `EITHER trigger` explicitly and
  the code-reviewer Sub-edit 3.6(a) states `T1 and T2 are OR'd; either
  fires the requirement` so a reviewer cannot silently AND them.
- **v1 vs v2 double-flagging risk.** A task straddling workflow
  versions could be flagged by both `code-reviewer.md` Step 3.6 (v1)
  and `efficiency-critic.md` item 8 (v2). The lens-coverage-map.md
  row is the disambiguator: v1 owner is code-reviewer.md, v2 owner is
  efficiency-critic; only one panel runs per task by construction of
  the `/issue` vs `/issue-v2` dispatch, so the mapping is
  unambiguous. This plan updates the ledger row so the disambiguation
  survives the rename.
- **Ratchet drift on workflow_lint's rules-pin family.** The lint has
  a growing family of `--check-*` flags; this plan does NOT add a
  new one (§ Enforcement-miss decision declined), so no new ratchet
  constant needs updating. Declared out of scope.
- **Anti-pattern-search miss.** Some sibling loops in the codebase
  may already carry the #1689 shape (dict-accumulate over a named-unit
  loop) with no test coverage flagging them. This plan does NOT sweep
  for them — a sibling-sweep is the code-reviewer's Step 3.7 duty on
  the NEXT diff that touches an accumulator loop, and it is a
  separate task if a fleet-wide scan is desired. Log as prose: a
  fleet-wide sweep of `out[<key>] = <func>(...)` inside `for` loops
  across `scripts/` could be filed later if the T2 trigger is found
  to under-catch in practice; leaving out of scope for this plan.
- **Progress-line convention drift.** If a future implementer prefers
  a `[phase=<name> unit=k/N ...]` form over `[<phase>] unit k/N …`,
  the canonical shape is a SUGGESTION in the rule text (not a
  literal-string enforcement), so drift is tolerable. The reviewer's
  read is behavioral: does the loop emit ONE line per completed unit
  carrying index / key / elapsed? — not "does it match this regex
  byte-for-byte". No lint pins the literal.

## Decision Rationale

Two novel additions:

**Progress-line canonical shape `[<phase>] unit k/N <key> elapsed=<s>s`.**
- What: one stdout print per completed unit, flushed, carrying unit index
  over total, a stable unit key, and elapsed seconds.
- Why: it is the smallest observable that (i) proves liveness to the
  poller (mtime plus fresh log line = alive, not wedged), (ii) supports
  wall-time projection from a partial run (`elapsed/(k/N)` extrapolates),
  and (iii) supports resume telemetry (the resume predicate can log which
  units it skipped by key).
- Source: matches the existing `[phase=<name> cell=<key>]` breadcrumb
  convention already in use in dispatcher scripts —
  `scripts/issue1112_train_marker_fullft.py:124` prints
  `[phase=marker_fullft_setup cell=m2]` and 4 sibling lines emit the
  same shape (grep-verified 2026-07-27). The `unit k/N … elapsed=<s>s`
  extension is a natural additive to the phase-and-cell prefix.
- Alternatives considered: (a) tqdm bars — noisy on non-TTY pod logs;
  (b) structured JSON breadcrumbs (`{"phase": "...", "unit": k, ...}`) —
  overkill for a workflow-surface rule that must be grep-able from a
  pod log by a human; (c) periodic wall-clock heartbeat (one line per
  30 s regardless of loop progress) — misses the units-per-line
  extrapolation benefit and would still surface a stuck loop as
  "alive" indefinitely.

**Count-based trigger threshold ~50 units.**
- What: a loop with a static named-unit iterable of size > ~50 trips the
  checkpoint + progress-line duty regardless of any wall-time estimate.
- Why: readable straight off the diff by both the implementer and the
  reviewer without a sizing calculation. Small enough that trivial helper
  loops (a 10-persona summary, a 3-arm sweep, a per-domain aggregator)
  do NOT trip it — those loops finish sub-minute and the log-bloat
  mitigation from the Risks section does not apply. Large enough that
  a genuinely per-unit-expensive sweep at even 30-60 s per unit blows
  past the ~1h floor without needing the wall-time estimate to fire.
  Explicit anchor: #1689's `run_all_pairs` at 126 pairs × 2 arms = 252
  units, ~4× the threshold, so a T2 read from the diff alone would
  have fired without any sizing input at all.
