## 0.0 TL;DR

The inline-override clause tells a session to inherit the `/issue`
pre-launch signals but never mentions the session-survival backstop, so an
inline round that outlives its turn has no documented re-driver
(**#1491**, 2026-08-05: no cron armed while an ~$44/h pod round was live;
surfaced only by user challenge). The task body proposes arming
`/issue-tick <N>` "exactly as Step 0/6d.2 sessions do". **That literal fix
is inoperative or actively wrong on every status an inline round actually
runs on** — see §2. This plan ships the *intent* with an
exhaustive status rule: arm the tick cron **iff** the parent is in
`tick_triage.ISSUE_ACTIVE` (the one class where it functions), and on
every other status name the backstop that actually binds there (the
`[long-phase-heartbeat]` cadence + the keep-running/`run-launched` shield
+ the dispatch note's re-attach handles) instead of a cron that either
deletes itself or re-drives the wrong skill.

**Change my mind:** if `tick_triage` did NOT return a teardown verdict for
`awaiting_promotion` / `on_hold` / `completed` parents and did NOT return
`STALE-REDRIVE` for `followups_running` — i.e. if a probe shows a tick
fire on those parents leaving an inline round correctly covered — the
literal body wording is correct and §3's rule collapses to an
unconditional arm. §2's probe is the discriminator; it is cheap,
re-runnable, and now pinned by a test (§4(c) pin 3).

## 2. Root cause + the probe that falsifies the literal fix

**The gap is real.** `grep -n "issue-tick" CLAUDE.md` returns exactly ONE
line (263, the `spawn_session.py` § "Auto-watching" prose) — the inline
carve-out and its override clause name the pre-launch signals
(`keep-running`, `epm:run-launched`), the detached handoff breadcrumbs, and
the lifecycle ack, but no backstop. A session applying the clause
faithfully arms nothing.

**`tick_triage` partitions the enum into FOUR sets, not two**
(`scripts/tick_triage.py:111-114`, read from the live tree):

| Set | Members | Verdict for an armed cron |
|---|---|---|
| `ISSUE_TERMINAL` | `completed`, `archived`, `awaiting_promotion`, `blocked`, `on_hold` | `TERMINAL` → CRON-TEARDOWN, END TURN |
| `ISSUE_GATE` (⊂ TERMINAL) | `awaiting_promotion`, `blocked` | `GATE-TRANSITION` → `PushNotification` **then** CRON-TEARDOWN |
| `ISSUE_PARK` | `proposed`, `planning`, `plan_pending` (under cap), `followups_running` | fresh marker → `HEALTHY`; stale → `STALE-REDRIVE`, re-driving the **full `/issue <N>` skill** ("in-skill chain likely dead") |
| `ISSUE_ACTIVE` | `approved`, `running`, `verifying`, `interpreting`, `reviewing` | fresh → `HEALTHY`; stale → `STALE-REDRIVE` ("bg poll chain likely dead") |

`compute_issue_verdict` RAISES `ValueError` on any status outside
`TERMINAL ∪ PARK ∪ ACTIVE` (`tick_triage.py:1273`), which is what makes
§3's "arm iff ACTIVE" formulation exhaustive by construction rather than
by enumeration.

**Consequence 1 — on TERMINAL parents the literal fix is inoperative.**
`scripts/task.py view 1491 --json` → `status: awaiting_promotion`, an
`ISSUE_GATE` member. So on #1491 the proposed cron would have fired once
within ~45-50 min (the `CronCreate` tool contract jitters recurring fires
up to 10% of the period late, max 15 min), taken the GATE-TRANSITION
branch, pushed `#1491 ... parked at awaiting_promotion — open it` while a
live ~$44/h pod round was mid-flight, and then run CRON-TEARDOWN on
itself. Net: one misleading phone push, zero ongoing coverage, and a duty
line that reads like protection.

**Consequence 2 — on PARK parents the literal fix is actively wrong.**
There the cron does NOT tear down. Once the round's markers go stale it
returns `STALE-REDRIVE` and loads the full `/issue <N>` skill — a re-spawn
of the very session the override clause exists to prevent ("honor the
override and run the follow-up inline ... do not spawn (or re-spawn) a
session against the ask"), driving the PARENT's lifecycle, not the inline
round, which posts no `epm:followup-scope` and is invisible to that
dispatcher. `followups_running` is not hypothetical: the carve-out's own
"Session-collision distinction" sanctions an independent read-only inline
round while a parent is held there.

**Which parents inline rounds actually run on.** The clause's pod-safety
sub-block scopes itself to "if an inline/user-chat run NONETHELESS
provisions or reuses a pod on a parked (`on_hold`) or terminal-status
parent" — a deviation case rather than a definition, so the honest claim
is *dominant path*, not *by construction*. #1491 (`awaiting_promotion`,
verified) is the filed instance; `on_hold` and `completed` are the other
two named in the same sub-block.

**Where the tick cron DOES work:** `ISSUE_ACTIVE`. There `tick_triage`
runs its liveness screen (identity-verified pid breadcrumb → fresh `log=`
mtime → fresh `[long-phase-heartbeat]` note) and returns `HEALTHY` while
the work lives, `STALE-REDRIVE` once it dies — and there the re-drive is
the CORRECT recovery, because an ACTIVE parent's own `/issue` lifecycle is
genuinely mid-flight and resumes from its latest marker.

**What actually backstops a non-ACTIVE-parent inline round today** (all
three already exist; none is named at the point of use):

1. the `[long-phase-heartbeat]`-prefixed `epm:progress` cadence
   (≤ ~60 min) — CLAUDE.md § "Orchestrator vs subagent re-invocation"
   binds it on ANY agent owning detached work outliving its turn; it is
   what makes the round's death legible rather than silent;
2. `keep-running` + a pod-naming `epm:run-launched` (already in the
   clause) — and `remove-tag ... keep-running` at completion, which
   re-arms the watcher's 10-min pod-safety auto-stop;
3. the dispatch note's re-attach handles (pod name / pid / absolute log
   path / harvest path — already in the clause) — what lets a successor
   session resume the round's remaining chain.

Residual escalation: the watcher's keep-running wedged-owner arm (#1582)
escalates a tagged RUNNING pod with a provably wedged/absent owner within
~12h. That residual is recorded in §7, not closed here.

## 3. Design decision

**Arm iff the parent is in `tick_triage.ISSUE_ACTIVE`. Otherwise do not
arm — and say why, per class.**

- **Parent in `ISSUE_ACTIVE`** (`approved` / `running` / `verifying` /
  `interpreting` / `reviewing`): ARM `/issue-tick <N>` at dispatch using
  the existing Step 0 ARM-GUARD verbatim (`CronList` whole-string
  equality → `CronCreate(cron="*/45 * * * *", ...)` → re-`CronList` +
  assert exactly one match), and run CRON-TEARDOWN (both legs, ids from a
  fresh `CronList`) at the round's completion step.
- **Parent in `ISSUE_TERMINAL`** (`on_hold` / `awaiting_promotion` /
  `completed` / `blocked` / `archived`) — the dominant inline-override
  case: do NOT arm. One fire, teardown; on the two `ISSUE_GATE` members a
  misleading gate push first.
- **Parent in `ISSUE_PARK`** (`proposed` / `planning` / `plan_pending` /
  `followups_running`): do NOT arm. The cron does not self-clear here — it
  `STALE-REDRIVE`s into a full `/issue <N>` re-drive, the re-spawn the
  override clause forbids.
- **Any other status** (legacy aliases, `failed`, `cancelled`, …): do NOT
  arm — `compute_issue_verdict` raises on them, so an armed cron is a
  crash, not a backstop.

In all non-ACTIVE cases the backstop is (1)+(2)+(3) from §2, stated
explicitly at the point of use so a future session does not re-derive the
broken form.

Rejected alternatives, one line each:
- *Arm unconditionally anyway* — ships a false backstop plus a misleading
  gate push on TERMINAL parents and a forbidden re-spawn on PARK parents;
  this is the defect §2 documents.
- *Widen `ISSUE_TERMINAL` / add an inline-round branch to `tick_triage`* —
  changes a hot fleet-wide predicate that ~15 concurrent sessions depend
  on, to serve a user-initiated interactive path; far beyond a prose fix's
  blast radius, and a park status that stops tearing down its cron
  re-opens #1052's runaway-tick class.
- *A bespoke non-`/issue-tick` cron prompt* — barred by SKILL.md
  § "Prevention ban (#980)" in spirit: a prompt shape outside the two
  CRON-TEARDOWN legs is not enumerable at teardown, which is exactly the
  hazard that ban exists for.
- *Flip the parent to `followups_running` so the tick "works"* — mutates
  task lifecycle state the carve-out exists to avoid, posts an
  `epm:status-changed` that strips the watcher's inferred pod shield, and
  lands in `ISSUE_PARK`, whose `STALE-REDRIVE` re-drives the parent's loop
  rather than the inline round. Strictly worse than not arming.
