## 3. Hypothesis

For each trait, predict the base-model in-scenario mean Likert (95% CI from N=40 prompt-paired SE):

| Trait | Predicted base in-scenario | Predicted base default-assistant | Trained in-scenario (system / role, from #498) | Decision direction at 3.5 |
|---|---|---|---|---|
| **logical-pushback** | ~3.9 (saturation expected) | ~3.9 | 4.033 / 3.775 | base CI above 3.5 → downgrade #498's PASS to "rubric-saturated, training effect tiny" |
| **validating** | ~2.5 (clean headroom expected) | ~2.4 | 4.250 / 4.267 | base CI below 3.5 → confirms #498's PASS is real training |
| **explains-well** | ~4.0 (saturation expected) | ~4.0 | 4.292 / 4.242 | base CI above 3.5 → downgrade #498's PASS |

The pre-registered predictions are above. **What would falsify each:**

- *Pushback / explains-well falsifier:* base in-scenario 95% CI strictly below 3.5 → these are not rubric-saturated; #498's PASS for them is a real training effect.
- *Validating falsifier:* base in-scenario 95% CI strictly above 3.5 → the validating PASS is also a rubric artifact; #498's one clean trait collapses, and the entire #498 "both encodings install the traits" claim turns out to rest on artifacts.
- *System-prompt-effect falsifier (both directions stated explicitly):*
  - `base_in_scenario ≈ base_default_assistant` (within the 95% CI on the difference) ⇒ the scenario system prompt is **NOT** moving the score; the rubric saturates uniformly across contexts, and the in-scenario number is whatever the base model's natural floor is for that trait under any prompt.
  - `base_in_scenario ≫ base_default_assistant` (beyond the CI on the difference) ⇒ the scenario system prompt **IS** moving the score; the in-scenario advantage at the base model is a system-prompt-elicited effect, not rubric saturation and not training.

The system-prompt-effect falsifier is structurally important: a "system-prompt is doing all the work" finding for any trait reframes #498's entire result — the training would be neither installing nor failing to install; it would just be along for the ride.

**Variance structure (corrected from v1):** the **unit of replication is the prompt**, NOT the judge call. The 3 judge re-calls per (prompt × trait × ctx) are a **within-prompt averaging device**:

1. For each row (prompt × trait × ctx), issue N (default 3) independent judge calls — same request, no seed param at the call level. Record all N scores in the output JSON as `scores: [int, ...]`.
2. Aggregate per-prompt: `prompt_likert[q_idx] = mean(scores)` → one averaged Likert per prompt.
3. Per-cell SE = SE of the 40 averaged-Likert values (i.e. `stdev(prompt_likert) / sqrt(40)`). This is the **prompt-paired SE** the hero figure uses.

The 3-call averaging is robustness against within-call judge stochasticity; it is **NOT** the primary SE source. If the API turns out byte-identical on repeat calls (smoke check), the 3-call average degrades to a 1-call point estimate per prompt, with no impact on the hero figure (40-prompt SE is unchanged in expectation).

### 6.1 Measurement validity

| DV | Construct (what the Goal cares about) | Metric (what is actually computed) | On-distribution? | If proxy: validation |
|---|---|---|---|---|
| Per-trait base-model expression score | Whether the base model's free-form answer expresses the named trait (pushback / validating / explains-well) at the same level the trained model's answer does | Per (trait, eval_ctx) cell: mean of 40 prompt-averaged Likert values, where each prompt-average is `mean(N=3 judge calls)` on the base model's own greedy answer | **YES** — base model generates its own answer to the prompts under each context's system prompt (greedy, max 2048 tokens); judge sees the model's own output and grades it against the same rubric the parent used | N/A (on-policy) |

This is the same DV the parent used, on the same distribution, with the only change being the model being evaluated. The measurement validity question reduces to "is the parent's rubric a valid proxy for the named trait?" — and the parent's #498 clean-result already addresses that (paraphrase-rank-stability ρ = 0.96 for validating, 0.71-0.75 for pushback, 0.26-0.36 for explains-well; the explains-well rubric is judge-noisy). ### 6.2 Decision rule (per trait, CI-aware)

For each trait, compute on the base in-scenario cell:

- `base_mean = mean(prompt_likert[0..39])` (40 averaged-Likert values)
- `base_SE = stdev(prompt_likert) / sqrt(40)` (prompt-paired SE)
- `base_CI_95 = (base_mean − 1.96·base_SE, base_mean + 1.96·base_SE)`

Decision states:

- **Saturation verdict (`base_CI_95` strictly above 3.5, i.e. `base_mean − 1.96·base_SE ≥ 3.5`)** → #498's in-scenario "trait installed" PASS for that trait is downgraded in the eventual clean-result update to a rubric-saturation artifact (the trait was at-or-above the PASS threshold *before* any training, with the CI clearing the threshold).
- **Real-implant verdict (`base_CI_95` strictly below 3.5, i.e. `base_mean + 1.96·base_SE < 3.5`, AND `trained_in_scenario_mean ≥ 3.5`)** → #498's PASS for that trait stands as a real training effect.
- **Near-threshold verdict (`base_CI_95` overlaps 3.5, i.e. `base_mean − 1.96·base_SE < 3.5 < base_mean + 1.96·base_SE`)** → ambiguous; the eventual clean-result narrates the result qualitatively. State exactly: "for trait T, base in_scenario = X ± Y (95% CI from N=40 paired prompts). Threshold 3.5 sits inside the CI." Honesty about the rubric's resolution, not a methodology flaw.

**System-prompt-effect detection (CI-aware, both directions):** for each trait, compute the paired-by-prompt delta `Δ_q = base_in_scenario[q] − base_default_assistant[q]` and the 95% CI on its mean (`mean(Δ) ± 1.96 · stdev(Δ) / sqrt(40)`):

- If `CI(Δ)` strictly contains 0 (CI overlaps 0) ⇒ `base in_scenario ≈ base default` ⇒ **system prompt is NOT moving the score**; rubric saturates uniformly across contexts.
- If `CI(Δ)` strictly above 0 (lower bound > 0) ⇒ `base in_scenario ≫ base default` ⇒ **system prompt IS moving the score**; trait expression is system-prompt-elicited, not rubric saturation or training.
- (The opposite — lower bound > some positive threshold — would be a "system-prompt does ALL the work" finding; lower bound < 0 would be the unlikely "default-assistant scores higher than scenario" finding, which would be a different kind of artifact.)

The 3.5 threshold is #498's pre-registered PASS bar — inherited verbatim. The CI-aware decision rule replaces v1's fixed 0.3 Likert "fuzzy zone," which was wider than the typical prompt-paired SE (#498's measured prompt-SE on the comparable trained-arm cells is 0.07-0.15 Likert → CI half-width 0.13-0.30 Likert, so a fixed 0.3 band would over-call near-threshold cases).

### 6.4 Base-vs-trained paired delta (primary effect-size statistic)

For each trait T and each trained arm A ∈ {system, role}, compute the prompt-paired delta:

- `Δ_q = trained_in_scenario_avg[A, T, q] − base_in_scenario_avg[T, q]` for each `q_idx ∈ [0, 40)`.
- `trained_in_scenario_avg[A, T, q]` = mean across the 3 LoRA training seeds at that prompt (`q_idx`), from `eval_results/issue_498/judge_scores.json`.
- `base_in_scenario_avg[T, q]` = mean across the 3 judge re-calls at that prompt for the base model, from this run.

Report:

- **Mean Δ ± 1.96 · SEM(Δ)** — the 95% CI on the average training effect for that trait × arm.
- **Wilcoxon signed-rank p-value** on the 40 paired deltas (robustness check against Gaussian assumption on a 1-5 Likert).
- The CI on Δ is the primary effect-size statistic; if the CI on Δ strictly contains 0, the trained-arm advantage at the in-scenario context is not distinguishable from the base model's natural rubric score for that trait.

This replaces v1's asymmetric-CI handwaving and gives the analyzer a clean, unambiguous between-model comparison that respects the paired-by-prompt structure of the data.

## 11. Decision Rationale

(One `Source:` line per unique load-bearing hyperparameter. `kind: experiment`, so this section is required.)

- **`max_new_tokens = 2048`** — covers the longest plausible base-model response by a wide margin (training max_length was 2048; base model has no LoRA pulling toward long structured outputs, so practical responses fit well under 2048). **Source:** `#498` Reproducibility table + CLAUDE.md "≥2× longest trained completion" rule. The parent #498 used 2048 with a measured global truncation rate well below 5% across 2520 generations.
- **`temperature = 0` (greedy)** — deterministic generation; the only stochasticity is in the judge, which we want to isolate. **Source:** `#498` Reproducibility table (parent used greedy). Replication-fidelity rule (CLAUDE.md "Replicating a published finding → match the paper's data + recipe FIRST") binds this to match the parent's generation regime.
- **`top_p = 1.0`** — paired with `temperature=0`, has no effect; carried for parity with #498. **Source:** `#498`.
- **Judge model `claude-sonnet-4-5-20250929`** — the canonical Sonnet 4.5 string per the project's `claude-api` skill and `i498_phase4_judge.py`. **Source:** `#498` and CLAUDE.md code-style rule "Never hardcode an invented Claude/Anthropic model id."
- **3 within-prompt judge re-calls per (prompt × trait × ctx)** — within-prompt averaging device to reduce within-call judge noise; the unit of replication remains the prompt (N=40 per cell), so this is robustness, not the primary SE source. **Source:** `planner — within-prompt averaging device, smoke verifies non-byte-identical responses`. If the API turns out byte-identical, the 3-call average degrades to a 1-call point estimate with no plan-level impact on the hero figure.
- **Base model `Qwen/Qwen2.5-7B-Instruct`** — single-variable contract vs #498: this is the un-LoRA'd version of the same checkpoint #498 fine-tuned. **Source:** `#498` Reproducibility table.
- **40 prompts / cell** — #498's held-out split. **Source:** `#498` (`i498_data.load_q_test` returns the 40-prompt held-out list). Held byte-identical for replication fidelity.
- **Eval contexts `{in_scenario, default_assistant}`** (cross_scenario dropped) — #517 body explicitly identifies the in-scenario × default_assistant pair as the load-bearing comparison; cross_scenario is moot for the base model since there's no implant to leak. **Source:** `tasks/planning/517/body.md` body text + the planner's reading of #498's hero figure (cross-scenario only matters when a trained adapter could leak across scenarios).
