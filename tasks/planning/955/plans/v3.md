### 4.1 The gotchas.md entry (main deliverable — full draft)

Insert as a new bullet in `.claude/rules/gotchas.md` immediately AFTER the line-162 Batch-API entry (i.e., between the current lines 162 and 163), so the two same-family entries sit adjacent:

> - **The Anthropic Messages API has NO `"system"` message ROLE — a chat-template-style message list forwarded verbatim 400s (`invalid_request_error`) the moment a `{"role": "system"}` entry appears; lift system content to the top-level `system=` param.** The project's canonical prompt shape puts the persona/instruction in a system-role message (code-style rule: persona injection is ALWAYS `{"role": "system", ...}`), and that list is valid for Qwen chat templates, vLLM, and the OpenAI API — but the Messages API accepts only `user`/`assistant` input roles (docs: "there is no `system` role for input messages in the Messages API"; system is a top-level `system=` parameter, string or text-block list). So any Anthropic request-builder seam that forwards a caller-supplied message list verbatim (`{"messages": item.payload["messages"], ...}`) is one system-bearing caller away from a hard 400 on EVERY request of that class. Diagnostic signature: a uniform HTTP 400 `invalid_request_error` across ALL requests of one caller class (system-less callers of the same seam keep working), surfacing only in production because the seam is mocked in the test suite. RULE (lift): at every seam that builds Anthropic params from a message list, split system-role entries out and pass them as `system=` — the canonical on-main splitter is `Prompt.anthropic_format()` (`src/explore_persona_space/llm/models.py:161`, returns `(system_message, chat_messages)`; its contract is a LEADING system message — mid-list entries fail loud via the role assert at models.py:96 — so it is a leading-system splitter, not an arbitrary-list sanitizer); the datagen-seam fix `_gen_params_from_messages` (#906 r11) is the same pattern and lands with the issue-906 branch. RULE (probe): any live-API dispatcher seam that accepts message lists and is NEVER executed by the mocked test suite (mock `generate_fn`/`judge_fn` seams — `artifacts/datagen.py::_default_generate_fn` is the canonical case) needs a tiny LIVE probe whose message list CONTAINS a system-role entry, routed through the SAME request-construction code path as the full run; a mock smoke AND a live system-LESS smoke both structurally cannot catch the shape bug (the 400 fires only when a system entry is present). This is the sync-path sibling of the Batch-API empty-system-block entry above — same family: request-SHAPE bugs at never-live-executed construction seams, invisible to every offline smoke; the live probe goes through the run's own builder, never a hand-written minimal request. (Incident #906 r11, 2026-07-03/04: the first `--full` datagen run lost its entire sycophancy class — all 36 generation requests 400'd — because `datagen.py::_default_generate_fn.build_request` forwarded `gen_messages` verbatim including a system entry; ten rounds of contract-test hardening on mocked seams never caught it.)

Register check against sibling entries: bold trap statement first, mechanism, diagnostic signature, RULE(s), sibling cross-reference, incident citation with task + date — matches lines 143–206's shape.
