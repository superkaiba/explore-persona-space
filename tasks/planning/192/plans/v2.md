# 1. Goal

Task #192 measures whether facts and cipher rules learned under the `zelthari_scholar` system frame transfer into the ordinary `assistant` frame after LoRA SFT. It is a contrast experiment against the marker-leakage Phase 0.5/A1 result where `zelthari_scholar` showed zero marker leakage to assistant despite being geometrically close in one earlier result table. The reframed prediction is deliberately null on both assistant primaries: if `zelthari_scholar` was categorically immune for marker leakage, then a factual association and a symbolic cipher taught only inside that frame should also stay frame-local. Positive assistant transfer would be the surprising finding and would separate "marker leakage immunity" from broader knowledge or procedure transfer.

# 3. Hypothesis

Primary prediction: both assistant-frame primaries are null. After successful teaching under `zelthari_scholar`, the post-SFT fact arm will not improve assistant-frame fact accuracy over the base-model fact baseline by the pre-registered margin, and the post-SFT cipher arm will not improve assistant-frame cipher exact accuracy over the base-model cipher baseline by the pre-registered margin.

Falsifiable tests:

- Fact primary confirms positive transfer only if the assistant-frame post-SFT fact accuracy beats the paired base-model baseline under the margin-aware bootstrap/Fisher test at `alpha=0.025`.
- Cipher primary confirms positive transfer only if the assistant-frame post-SFT cipher exact-match accuracy beats the paired base-model baseline under the margin-aware bootstrap/Fisher test at `alpha=0.025`.
- The predicted-null interpretation is supported if every `(arm, seed)` cell passes the `zelthari_scholar` teach-strength hard gate and neither assistant primary rejects.
- A null is uninterpretable, not supportive, if any `(arm, seed)` cell has `zelthari_scholar` teach accuracy below `50%`; that is the only hard-fail kill criterion.

Secondary prediction: if, contrary to expectation, both assistant primaries reject, transfer should be strongest in the `software_engineer` frame and weaker in `kindergarten_teacher` and no-system frames. These secondaries are gated and tested at `alpha=0.05/6`; they should not be interpreted if the primaries do not both reject.

Quantitative thresholds:

- Teach-strength keep band: `>=80%` on the in-distribution `zelthari_scholar` frame.
- Teach-strength retrain band: `50% <= score < 80%`; retrain that cell for two epochs and report both the original and retrained cell.
- Teach-strength hard fail: `<50%` for any `(arm, seed)` after the allowed retrain path.
- Teach-strength **scorer per arm** (item 1, methodology REVISE): the fact arm gate uses **MCQ accuracy** (not freeform substring-OR — the latter would let "2031"-style hits inflate the base rate and trivially pass the gate); the cipher arm gate uses **exact-match accuracy**. Identical bands `80/50` apply to both, but the underlying scorer differs.
- Primary alpha: `0.025` for fact and `0.025` for cipher.
- Secondary alpha: `0.05/6 = 0.008333333333333333`, conditional on both primaries rejecting.
- Background regression flag: assistant-frame held-out helpfulness/utility drop greater than `15` percentage points from base.

## Margin interpretation (items 2, 8 — statistics REVISE)

The predicted-null framing requires more than "primaries fail to reject." For a null-prediction experiment, the **upper 95% CI bound on Δ_assistant IS the result**. The plan therefore distinguishes:

- **Strong null support** — every (arm, seed) cell passes the per-arm teach-strength gate, both primaries fail to reject, AND the upper 95% CI on Δ_assistant (from the hierarchical bootstrap in §6) is `< 0.10` for the fact arm and `< 0.05` for the cipher arm. Headline: "fact transfer bounded above by 10pp; cipher transfer bounded above by 5pp."
- **Weak null support** — gate passes and primaries fail to reject, but the upper CI exceeds the named threshold (e.g., upper bound on fact Δ_assistant = `0.22`). Headline: "fact transfer not detected, but bounded only by ~22pp; underpowered against a true effect of that magnitude."
- **Positive transfer** — at least one primary rejects under §6's hierarchical-bootstrap rule.

The upper CI bound is reported in `run_summary.json` and in the clean-result body regardless of whether primaries reject; it is the **load-bearing quantity** when the headline is null.

```python
def post_progress(
    phase: str,
    summary: str,
    *,
    progress_pct: float | None = None,
    estimated_remaining_minutes: float | None = None,
    status: str = "running",
    extra: Mapping[str, Any] | None = None,
) -> None:
    """Record task-workflow progress for task #192.

    The old Sagan driver posted to SAGAN_PROGRESS_URL. In task-workflow the
    dashboard source of truth is an epm:progress event committed by task.py.

    Signature mirrors the branch driver's existing `post_progress` so call
    sites at lines 1074, 1080, 1084-1088, 2035, 2047, 2052, 2065, 2086,
    2098, 2121, 2132, 2160, 2207, 2215, 2239, 2247, 2251, 2283 do not
    need to be touched.
    """
    try:
        from explore_persona_space.task_workflow import post_event
    except Exception as exc:
        logger.warning("Unable to import task_workflow.post_event: %s", exc)
        return

    note_lines = [
        "<!-- epm:progress v1 -->",
        f"**Phase:** `{phase}`",
        f"**Status:** `{status}`",
    ]
    if progress_pct is not None:
        note_lines.append(f"**Progress:** `{progress_pct:.1f}%`")
    if estimated_remaining_minutes is not None:
        note_lines.append(f"**ETA:** `{estimated_remaining_minutes:.1f} min`")
    note_lines.append("")
    note_lines.append(summary)

    payload = dict(extra or {})
    payload.update(
        {
            "phase": phase,
            "status": status,
            "progress_pct": progress_pct,
            "estimated_remaining_minutes": estimated_remaining_minutes,
        }
    )
    try:
        post_event(
            192,
            "epm:progress",
            by="experiment-192-driver",
            note="\n".join(note_lines),
            **{k: v for k, v in payload.items() if v is not None},
        )
    except Exception as exc:
        logger.warning("Failed to post epm:progress marker: %s", exc)
```

```python
    )
```

```python
        json.dumps({"per_probe": public_rows}, indent=2, sort_keys=True) + "\n"
    )
```

## 4.5 Eval Generation-Length Fix

The current branch driver uses:

- `_vllm_greedy(..., max_new_tokens=256)` default.
- `phase_eval_one(... max_new_tokens=256)` for fact and cipher eval.
- `phase_sibling_check(... max_new_tokens=64)` for sibling cipher novelty.
- `create_vllm_engine(... max_model_len=2048, max_num_seqs=64)`.

This violates the current EPS rule that marker/end-of-completion and long-completion evals use `max_new_tokens >= 2x` the longest trained completion, with `>=2048` default. It is especially risky for the cipher arm because truncation can masquerade as failure to learn.

Required change:

```python

EVAL_MAX_MODEL_LEN = 4096
EVAL_MAX_NUM_SEQS = 16   # pinned — see below
```

Use `EVAL_MAX_NEW_TOKENS` for all main fact/cipher frame evals and for sibling cipher novelty. Use `EVAL_MAX_MODEL_LEN` in `create_vllm_engine`; if prompt length plus generation length can exceed 4096 in smoke testing, raise to `8192` and reduce `EVAL_MAX_NUM_SEQS` further. The vLLM eval must remain batched through one `LLM.generate()` call per batch, not one prompt per subprocess.

**Why 16, not 32 (item 7, statistics REVISE — blocker).** Qwen2.5-7B in bf16 ≈ 14 GB weights; vLLM KV-cache for `max_model_len=4096 × max_num_seqs=32 × 28 layers × 2 (K,V) × 32 heads × 128 head_dim × 2 bytes ≈ 60 GB` on H100 80GB after weights and PyTorch overhead — near-OOM-certain when stacked with a LoRA adapter merge. Halving to 16 cuts KV-cache to ~30 GB and leaves headroom for activations + adapter weights. The number is pinned upfront, not a "may need lowering" mitigation. The one-probe smoke gate in §13 must pass before launching the full eval; if it OOMs at 16, drop to 8 (and document the fallback in `run_summary.json`). Do not raise above 16 without a passing smoke at the new value.

Record the final values in `eval_results/exp192/run_summary.json` and the clean-result reproducibility card.

## 4.8 Why Code, Not A Model Call?

The design includes scorers, parsers, and judges over unstructured completions. These must remain deterministic code instead of model calls because the experiment's primaries are small-margin, pre-registered comparisons between base and post-SFT models. A model-judge would introduce an additional stochastic or prompt-sensitive measurement layer, could be affected by the same persona framing being tested, and would make paired bootstrap resampling less interpretable.

Use existing deterministic code:

- Fact freeform: substring/entity matching against `FACT_ENTITIES`, with exact expected entities from `eval/exp192_judge_prompts.py`.
- Fact MCQ: `_extract_mcq_letter`.
- Cipher: `_score_cipher` exact match and per-letter accuracy.
- Cipher novelty: sibling-key deterministic decoding tables.
- Gatekeeping/statistics: `_bootstrap_paired_diff`, `_fisher_p`, and existing primary/secondary cell aggregation.

Only freeform helper/background scoring may use rubrics already frozen in the branch if unavoidable, but the primary and secondary transfer tests must not depend on new LLM judge calls.

## Statistical Tests

**Primary inference: hierarchical bootstrap** (item 9, statistics REVISE — blocker; item 10):

The existing branch implementation pools three seed-level p-values via Fisher's method. Fisher assumes independence; the three LoRA seed-runs are **not independent** — they share data, hyperparameters, and base weights, varying only the seed (data shuffle + LoRA init). Treating their per-seed p-values as exchangeable understates the true variance.

**Replacement (pre-registered for primaries):**

- **Hierarchical bootstrap with `N_BOOTSTRAP = 5000`** (item 10 — bump from 1000 for smoother tail quantiles on the upper-CI quantity that drives the headline; trivial post-eval CPU cost). For each replicate:
  1. Resample the three seeds **with replacement** from `{42, 137, 256}`.
  2. For each resampled seed, resample its (post, base) probe pairs **with replacement**.
  3. Compute the mean Δ_assistant across the resampled probes per resampled seed, then average across the three resampled seeds.
- This produces 5000 replicate-level mean Δ_assistant values per (arm, frame, metric). The 2.5th and 97.5th percentiles give the 95% CI on the seed-and-probe-jointly-resampled mean.
- **Primary rejection rule:** the lower 95% CI bound on Δ_assistant `> margin` (one-sided), i.e., `lower_ci > 0.30` for the fact arm or `> 0.20` for the cipher arm. Equivalently, the margin-aware bootstrap p-value (fraction of replicates with `Δ ≤ margin`) `< 0.025`.
- **Primary null support:** the upper 95% CI bound on Δ_assistant `< 0.10` (fact) / `< 0.05` (cipher) → "strong null support" headline (see §3 Margin interpretation).

**Floor-collision exclusion** (item 6, statistics REVISE — blocker):

Before hierarchical bootstrap and Fisher pooling, scan each (arm, seed) cell for a **floor collision**: if both `base_rate < 0.05` AND `post_rate < 0.05` in the eval frame, the cell is flagged as floor-collided.

Floor-collided cells are routed into ONE of two branches based on whether the model LEARNED the material under zelthari (the disambiguator the round-2 Statistics reconciler called load-bearing):

**Branch A — "uninformative floor collision"** (default for cells where the teach-frame strength gate did NOT pass at the ≥ 80% band, i.e., the model didn't learn the material under zelthari):

1. **Excluded** from both the hierarchical bootstrap (its seed is dropped from the seed-level resample set for that arm) AND Fisher pooling.
2. **Logged** in `run_summary.json` under `stats.floor_collisions` with `(arm, seed, base_rate, post_rate, branch="A_uninformative", teach_frame_rate)`.
3. Triggers a clean-result caveat if any cell is in Branch A.
4. If ≥ 2 of 3 seeds floor-collide in Branch A for an arm, the arm's primary is marked **uninterpretable** (separate from kill criterion — see Success/Interpretation criteria below) and only the per-cell upper CIs are reported.

**Branch B — "strong null at floor"** (carve-out — applies when the cell's `zelthari_scholar` post-SFT teach-frame rate is ≥ 80% on the per-arm strength scorer AND `base_rate < 0.05` AND `post_rate < 0.05` in the eval frame; i.e., the model DID learn the material but does not retrieve it under the eval frame):

1. **INCLUDED** in the hierarchical bootstrap. The (post, base) probe pairs feed the resampler normally; the within-cell mean Δ is ≈ 0 and the cell contributes to the pooled upper CI honestly. At N=200 cipher probes with `post_rate = base_rate = 0`, the per-seed one-sided 97.5% upper bound on Δ via Clopper-Pearson on the post-rate alone is `≤ 1.83 / 200 ≈ 0.0091` — well below the `0.05` cipher strong-null threshold.
2. **Logged** under `stats.floor_collisions` with `(arm, seed, base_rate, post_rate, branch="B_strong_null_at_floor", teach_frame_rate)`.
3. Does **NOT** trigger "uninterpretable". A Branch-B cell counts toward "**strong null support at floor**" in the Success/Interpretation table.

**Why the carve-out matters (round-2 Statistics-reconciler fix):** the cipher arm's predicted outcome under the hypothesis is `assistant-frame base ≈ 0%` (the affine cipher π=7i+3 is arbitrary; the base model cannot derive it) AND `assistant-frame post ≈ 0%` (predicted null transfer). Under the unconditional exclusion rule, the very pattern the experiment was designed to detect — strong null at floor when the model DID learn the cipher under zelthari — would trigger "uninterpretable" and discard the strongest possible null signal. Branch B routes this case into the upper-CI computation correctly: a `0%→0%` cell when teach-frame rate ≥ 80% IS interpretable as "transfer bounded above by the binomial floor".

Rationale (Branch A): if both rates are at the floor AND the model did NOT learn the material under zelthari (teach-frame gate failed or only marginally passed via retrain), the cell's margin-aware bootstrap p-value collapses to ~1.0 (since `ln(1.0) = 0` for Fisher) and contributes a "fail to reject" indistinguishable from a genuine null because there is no signal to transfer in the first place. Excluding the cell yields an honest "underpowered at this cell" rather than an artifactual concordance.

**Secondary cross-seed summary (kept, demoted):**

- Fisher pooling across the per-seed margin-aware p-values is **reported as a secondary cross-seed summary** in `run_summary.json`, NOT as the primary inference. Its limitation (independence violation) is documented in the clean-result Body Discipline appendix.
- Per-seed margin-aware bootstrap CIs (within-seed probe resampling only, `N=5000`) are also reported alongside, so a reader can inspect concordance across seeds visually.
- **Concordance heuristic (descriptive, not a rejection rule):** "all 3 per-seed CIs include 0" → consistent with null; "all 3 per-seed CIs exclude the margin" → consistent with positive transfer. Reported in the per-arm table.

Margins (unchanged, only the test changed):

- Fact primary margin: `0.30`.
- Cipher primary margin: `0.20`.

Primary testing summary:

- Fact primary rejects if assistant-frame **hierarchical-bootstrap lower 95% CI on Δ_assistant > 0.30** (equivalently margin-aware bootstrap one-sided `p < 0.025`).
- Cipher primary rejects if assistant-frame **hierarchical-bootstrap lower 95% CI on Δ_assistant > 0.20** (equivalently margin-aware bootstrap one-sided `p < 0.025`).
- Strong null support requires upper 95% CI `< 0.10` (fact) / `< 0.05` (cipher).

Secondary gate (unchanged structurally; margins pinned per round-2 Statistics reconciler):

- Run secondary interpretation only if both assistant primaries reject under the hierarchical-bootstrap rule.
- Each secondary inherits its arm's primary margin: **τ = 0.30 for fact secondaries**, **τ = 0.20 for cipher secondaries**. The same margin definition that drove the assistant primary applies to the OOD frames (software_engineer, kindergarten_teacher, no-system) — no separate calibration is performed.
- Each secondary rejects if its hierarchical-bootstrap margin-aware `p < 0.05/6` (Bonferroni-adjusted at the per-secondary level).
- The margin-aware bootstrap p-value for a secondary is the fraction of replicates where `Δ ≤ τ_arm`.

"neither primary rejects" is the *predicted* outcome — NOT a kill.

The kill conditions for this experiment are:

1. **Strength-band hard fail.** Any `(arm, seed)` cell has post-SFT teach accuracy `< 50%` on the `zelthari_scholar` frame after the allowed retrain path (2 epochs in [50%, 80%) band), **scored per arm as in §3** (fact arm: MCQ exact-letter; cipher arm: cipher exact-match — NOT freeform substring-OR for the fact gate). Model didn't learn the material; cross-frame transfer is undefined for that cell.
2. **Raw completions cannot be recovered or uploaded** (qualitative-data
   link required by clean-result spec is unsatisfiable).
3. **Base/post pairing is broken** for any primary metric (cannot
   compute the paired hierarchical-bootstrap CI that defines the primary test).
4. **Scorer FP calibration fails to converge** — if both the original substring-OR rule AND the stricter "Pavlek OR Kalei Lin" rule exceed 5% FP on the 20 unrelated medical/year prompts (§6 "Scorer FP calibration"), the fact arm cannot be scored under the pre-registered protocol; halt and re-design before launch.

Any of (1)–(4) triggers a `kill_reason` column write in `results.csv`,
posts `epm:failure` with the cell + reason, and skips downstream
spread-eval phases for that cell. The run does not retry; the failure
is reported in the clean-result. Non-kill failures (primaries rejecting
or failing to reject) are observations, not kills.

## Success / Interpretation Criteria

**Strong null support** (predicted outcome, headline-worthy):

- All six `(arm, seed)` cells avoid hard fail (per-arm strength gate from §3, item 1), AND
- No floor-collided cells for either arm (or ≤ 1 of 3 per arm; §6 floor-collision exclusion, item 6), AND
- Both assistant primaries fail to reject under the hierarchical-bootstrap rule at `alpha=0.025`, AND
- **Upper 95% CI on Δ_assistant from the hierarchical bootstrap < `0.10` (fact) AND < `0.05` (cipher)** (items 2, 8).
- Headline: "Fact transfer to assistant bounded above by 10pp; cipher transfer bounded above by 5pp — concordant with marker-leakage immunity."

**Weak null support** (informative but underpowered):

- Conditions 1–3 met (gate passes, primaries fail to reject), BUT the upper 95% CI exceeds 0.10 (fact) or 0.05 (cipher).
- Headline: "Fact transfer not detected, but bounded only by ~Xpp; underpowered against a true effect of that magnitude. Re-running with more probes / more seeds is the natural follow-up."
- This outcome is **still reportable as a clean-result** but with the lower-confidence caveat front-loaded in the TL;DR.

**Surprising positive transfer:**

- One assistant primary rejects at `alpha=0.025`; report as arm-specific positive transfer.
- Both assistant primaries reject at `alpha=0.025`; open the secondary gate and interpret the frame-spread profile.
- If cipher primary rejects, the post-SFT sibling-cipher-key diagnostic (§4.7 step 6.5) distinguishes "learned-π-specifically" from "learned-affine-rule" and ships in the clean-result.

**Strong null support at floor** (carve-out for Branch B floor-collisions, round-2 Statistics-reconciler fix):

- All six `(arm, seed)` cells avoid hard fail AND the model passed the per-arm strength gate at ≥ 80% under zelthari (model DID learn the material), AND
- Every assistant-frame cell is at the floor (`base_rate < 0.05` AND `post_rate < 0.05`, i.e., Branch B floor-collision), AND
- The hierarchical-bootstrap upper 95% CI on Δ_assistant (computed *including* the Branch-B cells per §6) remains < `0.10` (fact) / < `0.05` (cipher).
- Headline: "Cipher transfer to assistant indistinguishable from binomial floor (~1pp at N=200) — strongest possible null signal."

**Uninterpretable:**

- Any `(arm, seed)` cell has `zelthari_scholar` teach accuracy `<50%` (per-arm scorer) after the allowed retrain path.
- ≥ 2 of 3 seeds floor-collide in **Branch A** for the same arm (model did NOT learn under zelthari at the 80% band; floor-collision is uninformative) → primary is marked uninterpretable for that arm; only per-cell upper CIs are reported. (Branch B floor-collisions do NOT trigger uninterpretable.)
- Raw completions cannot be recovered or uploaded, because scoring auditability would be broken.
- Base/post pairing is broken for any primary metric.
- Scorer FP calibration fails to converge under either rule (kill criterion 4).

# 11. Decision Rationale

## What: Keep The Resurrected Driver

Why: `scripts/run_experiment_192.py` already implements dataset generation, LoRA SFT, vLLM eval, scoring, bootstrap, gatekeeping, background checks, adapter upload, and WandB metric logging. Rewriting would increase risk and make resurrected Sagan comparability worse.

Alternatives: Rebuild a smaller notebook or use generic eval scripts. Rejected because it would lose the frozen judge prompts, strength bands, and round-2 helper tests.

## What: Use `post_event` In Process For Progress

Why: `src/explore_persona_space/task_workflow.py` exposes `post_event`, while the CLI `task.py post-marker` is a wrapper. In-process calls preserve the existing `post_progress(...)` call shape and avoid launching a Python subprocess for every progress update.

Alternatives: Shell out to `task.py post-marker`. Acceptable fallback, but noisier and slower. Direct HTTP posts to Sagan are obsolete.

## What: Split Raw Completions From Scored Eval JSONs

Why: Current Upload Policy is explicit: raw completions belong in HF data repo; eval result JSONs belong in git on the issue branch. The existing driver's `per_probe` records include `completion`, so a clean result requires a schema split.

Alternatives: Commit all eval JSONs as-is. Rejected because it violates policy. Upload all eval JSONs to HF data repo. Rejected because aggregate eval JSONs are supposed to be reviewable in git.

## What: Raise Eval Tokens To `2048`

Why: The current `256` token cap is inconsistent with current EPS eval policy and can truncate cipher completions. A false teaching failure would invalidate the predicted-null interpretation.

Alternatives: Use `512` or only raise cipher eval. Rejected because the policy default is `>=2048` and a uniform constant is easier to audit.

## What: Use 4x H100 Sweep Parallelism

Why: Six train/eval cells are independent after dataset generation. One 4x pod reduces wall time from about `5-7` hours to about `2` hours without tensor-parallel complexity.

Alternatives: One 1x H100 pod. Acceptable for smoke tests but not preferred for the final run. Six independent pods. Rejected because coordination/upload/progress failure modes increase.

## What: Keep LoRA `r=32`, `alpha=64`, `lr=2e-4`, One Epoch

Why: These are the resurrected driver settings and are part of the Sagan experiment's comparability. Existing helper tests and pre-registered judge constants assume this driver shape.

Alternatives: Adopt marker-leakage Phase A1 settings (`lr=1e-5`, three epochs, dropout `0.05`) or #205 settings (`lr=1e-4`, dropout `0.05`). Rejected because #192 is not rerunning marker leakage; it is testing fact/cipher content transfer under the resurrected driver.

## What: Keep Deterministic Scoring

Why: The primaries compare small base/post deltas and must be reproducible under bootstrap. Deterministic scoring preserves pairing and avoids judge-model sensitivity to persona frame wording.

Alternatives: Use an LLM judge for fact freeform paraphrases. Rejected for primaries; raw completions can still be manually audited in the clean result.

## What: Treat Background Regression As A Flag

Why: Thirty prompts and a 15pp threshold are useful for catching large adapter regressions but are too small for a definitive general-capability claim.

Alternatives: Expand to a full benchmark suite. Rejected for this pilot because it would change scope and compute without improving the primary transfer test.

## 13.1 Round-1 smoke checks (new in v2)

Three new pre-launch smoke checks land before the full sweep. All three are blocking; the driver MUST exit non-zero if any fails so the pod scheduler does not silently spend a 4× H100 hour on a broken eval.

### 13.1.a Scorer FP calibration (item 5)

Runs at dataset-generation time, before any training, on a 1× GPU smoke pod (or the same 4× H100 pod before workers launch):

```bash
env UV_CACHE_DIR=/tmp/uv-cache uv run python scripts/run_experiment_192.py \
    --phase fp-calibration \
    --output eval_results/exp192/_smoke/fact_scorer_fp.json
```

Driver behavior:

1. Generate 20 unrelated medical/year prompts (file `data/exp192/fact_scorer_fp_probes.jsonl` — committed to git on the issue branch alongside the rest of `data/exp192/`).
2. Run base-model greedy assistant-frame completions.
3. Apply the original substring-OR rule (`Pavlek` ∨ `Kalei Lin` ∨ `2031` ∨ `Lancet Prize`) and the stricter rule (`Pavlek` ∨ `Kalei Lin`).
4. Compute FP rate under each rule.
5. **Decision:** if original rule FP ≤ 5% → keep it. Else if stricter rule FP ≤ 5% → switch to stricter rule (record in `run_summary.json`). Else → kill criterion 4 fires; abort.
6. Output `eval_results/exp192/_smoke/fact_scorer_fp.json` with `{rule_in_force, fp_rate_original, fp_rate_strict, prompts_per_rule, decision}`.

### 13.1.b No-system rendered-prompt assertion (item 3)

Runs immediately after dataset generation, before any training:

```bash
env UV_CACHE_DIR=/tmp/uv-cache uv run python scripts/run_experiment_192.py \
    --phase rendered-prompt-smoke \
    --output eval_results/exp192/_smoke/rendered_prompts.json
```

Driver behavior:

1. Take one fact probe and one cipher probe from `data/exp192/fact_probes.json` and `data/exp192/cipher_held_out.jsonl`.
2. Render each under all five frames via the chat template the eval will actually use.
3. Dump full rendered strings to `eval_results/exp192/_smoke/rendered_prompts.json` keyed by `(probe_id, frame)`.
4. **Assertion:** for every `frame == "no_system"` rendering, the string MUST NOT contain `<|im_start|>system`. If found, abort with diagnostic showing the offending substring.
5. If the assertion fails, the fallback is to construct the prompt manually as `<|im_start|>user\n{prompt}<|im_end|>\n<|im_start|>assistant\n` and re-run the smoke. The eval path is then patched to use the manual-construct route for the `no_system` frame.

### 13.1.c vLLM one-probe OOM check (item 7)

Runs on the actual eval pod immediately before launching the full eval:

```bash
env UV_CACHE_DIR=/tmp/uv-cache CUDA_VISIBLE_DEVICES=0 uv run python scripts/run_experiment_192.py \
    --phase vllm-oom-smoke \
    --probes 1 \
    --max-num-seqs 16 \
    --max-new-tokens 2048 \
    --max-model-len 4096
```

Driver behavior:

1. Load Qwen/Qwen2.5-7B-Instruct + the (cipher, seed=42) adapter via vLLM with the pinned constants.
2. Generate one cipher held-out probe (longest expected output, worst case for KV-cache).
3. Verify generation completes without OOM and the completion length > 100 tokens (not silently truncated).
4. Log peak GPU memory.
5. **Decision:** if OOM at `max_num_seqs=16` → drop to `8` and re-run the smoke. Document the final value in `run_summary.json`. If `8` also OOMs, abort and raise to user (likely an unexpected weight footprint).
