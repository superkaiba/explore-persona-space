## 0.0 TL;DR (plain English)

- **What I'll run:** Nothing runs on a GPU. I'm changing one safety automation:
  the 10-minute watcher that notices a RunPod pod stuck "running but unreachable"
  (a known billing leak). Today, when the experiment's own monitor has died, the
  most the watcher will do is *pause* the pod — but a pause doesn't fix a
  genuinely-dead RunPod host (it comes back to the same dead host), so the pod
  keeps billing until a human kills it. I'm letting the watcher reuse the
  experiment monitor's existing "kill it and start a fresh pod" recovery in the
  one case that's provably safe (the work is already saved to HuggingFace and the
  user didn't tag the pod to keep running).
- **What I expect:** The #763-style billing leak (hours of an idle H100 stuck on
  a dead host) gets auto-recovered within ~20 minutes instead of waiting for a
  human, while never risking losing un-uploaded work — every uncertain case still
  just alerts.
- **What would change my mind:** If the watcher can't reliably reconstruct what
  it needs to call the existing recovery (it lacks the live experiment context
  the monitor had), then the safe answer is to keep alerting in that case rather
  than terminate blind — so I'm planning the fallback to ALERT-only on any gap,
  and I'd want to see that the fallback fires correctly.

## 1. Goal

Promote the watcher wedge arm's confirmed `keep_running=False AND inputs_ok=True
AND matured-wedge` case from a reversible `_stop_pod` to a bounded, idempotent
call into the existing `backend_poll._failover_wedged_runpod` (terminate + fresh
re-provision), reusing the durable-lease + sentinel idempotency
(`_runpod_wedge_already_handled` / `Lease.runpod_wedge_failover_of`) and the
per-cell inputs-on-HF gate. Every uncertainty path (`keep_running` True/unknown,
`inputs_ok` False, no reconstructable run handle) stays ALERT-only. This closes
the #763 incident: a RunPod pod stuck RUNNING-but-no-port leaked H100 billing for
hours because the poller's terminate+re-provision failover could not run (the
per-issue poll loop was dead) and the #692 watcher backstop's strongest action
was a reversible `pod.py stop`, which cannot heal a host-pinned dead RunPod host
(`resume_pod` returns to the same dead host).

## 3. Architectural assessment

**Decision: `architectural: false` (in-scope auto-fix).**

Rationale: This change reuses an already-irreversible, already-gated,
already-idempotent recovery (`backend_poll._failover_wedged_runpod`) and extends
WHERE it can fire (from the poller-only path to the watcher backstop when the
poll loop is dead). It introduces NO new public-contract semantics: no status
enum rename, no marker schema change (a new internal marker-note sentinel is the
same shape as the existing `_WEDGE_STOP_NOTE_SENTINEL` / `_WEDGE_ALERT_NOTE_SENTINEL`,
both internal log-annotation strings, not a parsed schema), no `task.py`
subcommand or CLI contract change, no agent/skill file relocation, no subsystem
removal. The watcher already auto-STOPs `done`-status escaped pods reversibly
today (an internal auto-action), and the wedge arm already auto-stops live-work
pods reversibly when provably safe (#692, also internal); promoting that
specific provably-safe internal auto-action from `stop` to the existing
terminate+failover is the same KIND of internal-automation behavior change, not
a contract change. The irreversibility is real, but the rule's architectural
test is about PUBLIC CONTRACT shape, not reversibility per se — and the
irreversible recovery being reused already ships in production via the poller.
The emitter (the #763 wedge subagent) leaned in-scope auto-fix for these same
reasons; I concur. The change is gated tighter than the poller's own firing (it
ADDS the tri-state keep-running gate the poller does not even consult) and is
bounded-once by the inherited sentinel — the safety surface only narrows, never
widens.

(If a reviewer disagrees and considers the watcher's promotion to an
irreversible auto-action a public-contract change, the fallback is mechanical:
the orchestrator parks the task at `plan_pending` for user greenlight per
`.claude/rules/workflow-fix-on-bug.md` § Architectural greenlight. I set
`architectural: false` because the reuse-of-an-existing-shipped-recovery framing
is the stronger reading.)

### 4.3 `_process_wedged_pod` — dispatch the new action

`scripts/autonomous_session_watch.py:3769-3816`. Replace the
`if action == "stop":` block (`:3785-3816`) with an
`if action == "terminate-failover":` block that:

1. Reconstructs `handle` + `sidecar` from the persisted sidecar (the exact
   pattern `_wedge_inputs_safe` uses at `:2404-2407`), via a small helper
   `_wedge_failover(issue, info, wedged_h, dry_run)` (extracted so
   `_process_wedged_pod`'s cyclomatic complexity stays under the C901 cap the
   #692 arm already pushed against — see `_escaped_pod_exemptions` extraction
   precedent at `:3870`).
2. Synthesizes a minimal `result` shim carrying ONLY the two attributes
   `_failover_wedged_runpod` reads (`current_phase`, `log_tail_excerpt`).
3. Calls `backend_poll._failover_wedged_runpod(issue=..., handle=...,
   result=..., sidecar=...)`.
4. Branches on the returned dict's `status` / `reason` to post the right marker
   and persist the cleared wedge state.

Pseudocode for the new helper (added near `_stop_pod`, `:3136`):

```python
def _wedge_failover(issue: int, info: PodInfo, wedged_h: str, dry_run: bool) -> str:
    """Run the EXISTING poller terminate+re-provision recovery for a matured,
    inputs-safe, untagged RunPod no-port wedge from the watcher (when the poll
    loop is dead). Returns a one-word outcome for the caller's marker/state
    branch: 'failover' (fresh pod re-provisioned) | 'already-handled' (the
    poller or a prior watcher tick already failed this wedge over — bounded-once
    short-circuit) | 'no-capacity' (terminated, RunPod unavailable for the
    re-provision — terminal no_compute_available, the capacity-retry pass
    re-drives) | 'blocked' (inputs unverified / sidecar-persistence failed — a
    terminal infra block a human resolves) | 'alert' (NO reconstructable run
    handle -> cannot call the failover -> degrade to ALERT-only, NEVER a blind
    terminate).

    Obtains `handle` + `sidecar` from the persisted sidecar EXACTLY as
    `_wedge_inputs_safe` does (the watcher does not have the poller's in-scope
    handle); on any reconstruction gap returns 'alert' (halt-criterion #2 —
    never strand un-uploaded work, never terminate blind)."""
    if dry_run:
        print(f"  [dry-run] would terminate+failover wedged pod for issue #{issue}")
        return "failover"
    try:
        from backend_poll import _failover_wedged_runpod
        from explore_persona_space.backends.issue_dispatch import (
            read_handle_sidecar,
            resolve_handle_sidecar_path,
        )
        path, _probed = resolve_handle_sidecar_path(issue)
        if not path.exists():
            print(
                f"  wedge-failover: no handle sidecar for #{issue}; cannot reconstruct "
                f"the run handle -> ALERT-only (never terminate blind)",
                file=sys.stderr,
            )
            return "alert"
        handle = read_handle_sidecar(path)
    except Exception as exc:  # transport / parse / import -> ALERT-only
        print(
            f"  wedge-failover: handle reconstruction failed for #{issue} "
            f"({type(exc).__name__}: {exc}); ALERT-only",
            file=sys.stderr,
        )
        return "alert"

    # The poller had a PollResult in scope; the watcher does not. _failover_wedged_runpod
    # reads ONLY current_phase + log_tail_excerpt from `result`, so a minimal shim suffices.
    class _WedgeResultShim:
        current_phase = "runpod_noport_wedge_watcher_backstop"
        log_tail_excerpt = (
            f"watcher-detected RunPod RUNNING-but-no-port wedge ({wedged_h}); the per-issue "
            f"poll loop is dead, so the watcher is the backstop (#692->#770)"
        )

    try:
        out = _failover_wedged_runpod(
            issue=issue, handle=handle, result=_WedgeResultShim(), sidecar=path
        )
    except Exception as exc:  # fail-LOUD but do not crash the whole watcher tick
        print(
            f"  wedge-failover: _failover_wedged_runpod raised for #{issue} "
            f"({type(exc).__name__}: {exc}); ALERT-only this tick (re-tries next tick)",
            file=sys.stderr,
        )
        return "alert"

    status = out.get("status")
    reason = out.get("reason")
    if status == "running":
        return "failover"          # fresh pod re-provisioned (or running-shaped success)
    if reason == "runpod_wedge_already_handled":
        return "already-handled"   # bounded-once short-circuit (cross-actor idempotency)
    if reason == "no_compute_available":
        return "no-capacity"       # terminated; RunPod unavailable; capacity-retry re-drives
    # runpod_wedge_inputs_unverified | sidecar_persistence_failed | any other terminal infra JSON
    return "blocked"
```

Notes on the dispatch:

- **Why clear the wedge state on `already-handled` / `no-capacity` / `blocked`
  too:** in all three the wedge episode is resolved from the watcher's vantage
  (the pod was terminated, or a terminal infra JSON was emitted that the poller's
  contract handles, or it was already handled) — re-stamping the clock would
  re-fire next tick. The bounded-once lease/sentinel makes a second
  `_failover_wedged_runpod` call a no-op anyway, but clearing the clock is the
  clean state. The ONE exception is the `alert` degrade (no handle / raised),
  which falls through to the existing alert block that persists
  `wedge_alerted=True` + carries the clock forward — so a transient
  reconstruction failure re-tries on a later tick (correct: we have NOT acted).
- **`_failover_wedged_runpod` is the bounded-once guard.** It calls
  `_runpod_wedge_already_handled` internally (`backend_poll.py:1067`) BEFORE any
  terminate. So even if the poller re-armed and fired the SAME failover on the
  same wedge, the watcher's call short-circuits to the `runpod_wedge_already_handled`
  terminal JSON → `outcome == "already-handled"` → no double-terminate. The
  watcher does NOT need its own pre-check; the cross-actor idempotency is
  inherited.
- **Reusing `_wedge_inputs_safe`'s handle read is intentional.** `inputs_ok` was
  ALREADY computed in `_process_wedged_pod` (`:3767`) by reading the handle +
  running the inputs gate, so by the time we reach the `terminate-failover`
  branch we KNOW a handle resolved and the inputs gate passed. The
  `_wedge_failover` helper re-reads the handle (cheap, idempotent) rather than
  threading it through — and `_failover_wedged_runpod` re-runs the inputs gate
  itself as a precondition (`backend_poll.py:1082`), so the gate is enforced at
  the terminate site regardless. The handle read in `_wedge_failover` returning
  `alert` is the defensive belt-and-suspenders for the (near-impossible) race
  where the sidecar vanished between the `inputs_ok` computation and the dispatch.

## 11. Decision Rationale

(No model training — but the design choices are load-bearing, so each is
recorded.)

- **What:** Reuse `backend_poll._failover_wedged_runpod` rather than write a new
  watcher-side terminate+re-provision path.
  **Why:** It is already irreversible, already gated (per-cell inputs-on-HF),
  already idempotent (durable lease + sentinel), already maps no-capacity →
  `no_compute_available` for the capacity-retry pass. Reusing it gives the
  cross-actor idempotency for free (the poller and watcher route through the
  SAME sentinel) and is the project's "reuse existing experiment/infra code"
  default.
  **Source:** #664 (`_failover_wedged_runpod`), #689 (the inputs gate + durable
  lease idempotency), `.claude/rules/workflow-fix-on-bug.md` (the candidate
  explicitly scopes the fix as "extends WHERE the existing one can fire").
  **Alternatives:** (a) re-implement terminate+re-provision in the watcher —
  rejected (duplicates the poller's gated/idempotent recovery, would drift,
  re-opens the double-terminate hole #689 closed); (b) keep `pod.py stop` —
  rejected (a reversible stop cannot heal a host-pinned dead RunPod host, #763,
  the incident this fixes).

- **What:** A new return action `"terminate-failover"` (not overloading
  `"stop"`).
  **Why:** Keeps `decide_pod_wedge` pure and the action-name self-documenting;
  makes the dispatch branch in `_process_wedged_pod` unambiguous; lets `_stop_pod`
  stay the status-class DONE arm's reversible action without conflation.
  **Source:** #692 plan v3 (the existing `"stop" | "alert" | "keep"` action
  vocabulary + the MF2 decision-invariant discipline).
  **Alternatives:** overload `"stop"` to mean "terminate when inputs-safe" —
  rejected (silently changes a reversible action's meaning; the status-class arm
  also dispatches `"stop"` reversibly, so overloading would break the DONE arm).

- **What:** Synthesize a minimal `result` shim (only `current_phase` +
  `log_tail_excerpt`) for the failover call.
  **Why:** The watcher has no `PollResult` in scope (it never ran a poll); those
  two attributes are the ONLY ones `_failover_wedged_runpod` reads (verified at
  `backend_poll.py:964-965`). A shim is the minimal correct value, and it labels
  the recovery's provenance (watcher backstop) in the evidence dict.
  **Source:** `backend_poll.py:1054`/`:964-965` (the read sites).
  **Alternatives:** thread the real `PollResult` through — impossible (the
  watcher never constructed one); pass `None` — rejected (would crash the
  evidence-dict construction).

- **What:** Degrade to ALERT-only on ANY handle-reconstruction or failover-call
  failure.
  **Why:** Halt-criterion #2 — never strand un-uploaded work, never terminate
  blind. A missing handle means we cannot prove the inputs are safe from the
  watcher's vantage, so a terminate could lose data.
  **Source:** `.claude/rules/compute-backend-failover.md` § Part C (the
  ALERT-by-default posture), CLAUDE.md halt-criterion #2, #692 (the fail-closed
  `_wedge_inputs_safe`).
  **Alternatives:** terminate anyway — rejected (could strand work, the exact
  failure mode the inputs gate exists to prevent).

- **What:** Clear the wedge state on every non-`alert` outcome (failover /
  already-handled / no-capacity / blocked); carry it forward only on `alert`.
  **Why:** In the non-alert outcomes the episode is resolved from the watcher's
  vantage (acted, or a terminal JSON emitted, or already handled) — re-stamping
  would re-fire; on `alert` we have NOT acted, so the clock must carry forward to
  re-try.
  **Source:** the existing #692 stop/alert state-handling in `_process_wedged_pod`
  (`:3802-3851`) — same pattern, extended to the new outcomes.
  **Alternatives:** clear on alert too — rejected (would stop a transient gap
  from re-trying).
