## 0.0 TL;DR (plain English)

- **What I'll change:** A safety automation already kills a RunPod pod that's
  stuck "running but unreachable" (a billing leak) when the experiment's own
  monitor has died, and then records *why* it did so, so the rest of the system
  can pick the work back up. The recording step writes two small notes through
  the task tool. If either write hiccups (a transient file-lock or network
  blip), the current code says "I'll just retry on the next pass" — but there
  is no next pass for that pod, because it was just killed, so the kill is
  invisible afterward and the task gets stranded. I'm making the two notes retry
  a few times *right there* (the pod is already gone, so writing the notes is
  the only thing left to do) instead of relying on a next pass that can't
  happen.
- **What I expect:** A transient write failure that swallowed the kill record
  now succeeds within a couple of seconds, the run is correctly marked so it can
  be re-driven once compute frees up, and no task is left silently stranded
  after the watcher stops its pod.
- **What would change my mind:** If the write keeps failing after the bounded
  retries (a non-transient cause — a corrupt task tool, a full disk), I do NOT
  want to spin forever — I keep the wedge clock intact and fail LOUD so a human
  sees it, because that genuinely-stuck case would block any retry path and is
  operator-side regardless. So I'm planning the exhausted-retry branch to fail
  loud, not silently swallow.

## 1. Goal

Make the watcher's post-terminate wedge terminal-record write
(`epm:failure v1` + `set-status blocked`) DURABLE without depending on the
just-terminated pod's liveness — by retrying the two `task.py` writes
SYNCHRONOUSLY within the same tick, with a bounded exponential backoff, before
`_handle_wedge_failover_outcome` returns. This closes the
`wedge-terminal-recording-no-retry-after-terminate` gap introduced by the v1
strategy: the r3 fix correctly refused to clear the wedge clock on a partial
write and promised "the next tick retries," but the next tick can NEVER re-enter
the wedge arm for a pod the failover already terminated
(`_process_wedged_pod` is reached only via `_running_managed_issue_pods()`,
which filters `desired_status != "RUNNING"`), so the retry was unreachable and a
transient `task.py` / flock / network failure left the task stranded (billing
stopped, but `status` never `blocked` and `epm:failure` never durably written,
so the capacity-retry pass — which keys on exactly that pair — can never
re-drive it).

### 4.1 Chosen retry design: (A) bounded synchronous in-tick retry

**Decision: design (A)** — retry the two `task.py` writes synchronously within
the same tick with a bounded exponential backoff, before
`_handle_wedge_failover_outcome` returns. Reasoning (recorded in §11):

- By the time the two writes are reached, `_failover_wedged_runpod` has ALREADY
  terminated the pod (`backend_poll.py:1100`). The ONLY remaining work in the
  whole episode is the two `task.py` subprocess writes. There is no
  long-running, resource-holding, or blocking work left to defer — so a short
  synchronous retry is the natural, minimal closure: it does the remaining work
  HERE rather than relying on a re-entry that the terminate destroyed.
- The dominant failure class the r2/r3 reviewers named is TRANSIENT `task.py` /
  flock / network failure (flock contention on the shared repo root is a
  documented real condition). That class recovers in well under a second — a
  bounded in-tick retry (1s / 2s backoff, ≤3 attempts) handles it cleanly inside
  the same tick.
- (B) (a `terminal_record_pending` field + a NEW watcher pass keyed on
  `tasks/` state files) and (C) (persist the terminal JSON to a sidecar/sentinel
  + a separate replay pass) BOTH add a new persistent state field AND a new
  watcher pass to retry work that is two sub-second subprocess calls — a large
  structural addition (new file schema, new pass, new GC, new tests for both)
  to defer work that has nothing to wait FOR. The pivot marker recommended (A)
  by default and reserved (B)/(C) for the case where (A)'s residual is
  unacceptable; it is not — see the residual analysis below.
- **Residual of (A) (acceptable).** A NON-transient write failure (corrupt
  `task.py`, full disk, a persistent flock holder) exhausts the retry budget and
  still strands the task. But this is EXACTLY the class that would also defeat a
  (B)/(C) decoupled retry pass — the next pass would hit the same persistent
  failure — so the resolution is operator-side regardless of design. The
  exhausted-retry branch handles this correctly: it keeps the wedge clock intact
  (per r3) AND fails LOUD (stderr + an `epm:progress` annotation naming the
  persistent failure), so a human is alerted via the dashboard. No design can
  make a corrupt-`task.py`-on-a-full-disk write succeed; (A) degrades to the
  same operator-alert outcome as (B)/(C) at a fraction of the code.

### 4.2 The new bounded-retry helper (added near `_set_status_blocked`, `:3253`)

A small helper retries a single `() -> bool` write closure with bounded
exponential backoff, mirroring `i528_phase0_preflight.py:86-104`:

```python
_WEDGE_RECORD_RETRY_ATTEMPTS = 3  # total attempts (1 initial + 2 retries)
_WEDGE_RECORD_RETRY_BASE_S = 1.0  # backoff base: sleeps 1s, 2s (1.0 * 2**attempt)


def _retry_durable_write(
    write: Callable[[], bool], *, what: str, issue: int, dry_run: bool
) -> bool:
    """Call a `() -> bool` durable-write closure, retrying on a False return
    (a swallowed transient task.py / flock / network failure) with bounded
    exponential backoff. Returns True the moment a call succeeds; returns False
    only after _WEDGE_RECORD_RETRY_ATTEMPTS attempts all returned False.

    The pod backing this issue's wedge has ALREADY been terminated by
    backend_poll._failover_wedged_runpod, so the two terminal-record writes are
    the only remaining work — a short synchronous in-tick retry is the durable
    retry layer the watcher needs (the poller's persistent bg re-poll loop, the
    equivalent layer on the poll-alive path, is gone — the watcher IS the
    backstop precisely because that loop is dead). dry_run short-circuits to True
    on the first call (the underlying writers already no-op + return True in
    dry-run; no sleeps in a dry-run smoke)."""
    for attempt in range(_WEDGE_RECORD_RETRY_ATTEMPTS):
        if write():
            return True
        if dry_run:  # underlying writers return True in dry-run; defensive
            return True
        if attempt + 1 < _WEDGE_RECORD_RETRY_ATTEMPTS:
            sleep_for = _WEDGE_RECORD_RETRY_BASE_S * (2**attempt)
            print(
                f"  issue #{issue}: durable write {what!r} failed "
                f"(attempt {attempt + 1}/{_WEDGE_RECORD_RETRY_ATTEMPTS}); "
                f"sleeping {sleep_for:.1f}s then retrying",
                file=sys.stderr,
            )
            time.sleep(sleep_for)
    return False
```

Notes:
- `Callable` is imported from `typing`/`collections.abc` (added with first use
  in the same edit, per the PostToolUse-ruff F401 rule). `time` is already
  imported at module top (the watcher already uses `time.time()`).
- The loop sleeps AFTER a failure only when another attempt remains (no trailing
  sleep on the last failure) — total added wall on a full failure is
  `1.0 + 2.0 = 3.0s`, bounded.
- The closure form (`write: () -> bool`) lets the caller retry each of the two
  writes INDEPENDENTLY, so a transient failure on ONE write does not re-issue an
  already-succeeded write (`task.py post-marker` is not idempotent — a re-post
  would duplicate the `epm:failure` marker; retrying only the failed write
  avoids that).

## 11. Decision Rationale

N/A — no model training (`kind: infra`). The load-bearing CHOICES here are the
design pick and the retry parameters:

- **Chosen retry design: (A) bounded synchronous in-tick retry.**
  - **Why:** by the time the two terminal-record writes are reached,
    `_failover_wedged_runpod` has already terminated the pod
    (`backend_poll.py:1100`), so the two `task.py` subprocess writes are the ONLY
    remaining work in the episode. The failure class the gap exposes (transient
    `task.py` / flock / network) recovers in well under a second. A short in-tick
    retry does the remaining work HERE — the place the pod-liveness re-entry the
    r3 fix relied on is destroyed by the terminate it just performed. (B) and (C)
    add a new persistent state field + a new watcher pass to DEFER work that has
    nothing to wait for and takes two sub-second subprocess calls — a large
    structural cost for no benefit, and they hit the SAME persistent failure on
    the non-transient residual that (A) does.
  - **Source:** strategy-pivot v1 marker (recommends (A) by default;
    `task.py view 770 --json | jq '.events[]|select(.kind=="epm:strategy-pivot")'`);
    the unreachable-next-tick gap confirmed against live r3 code
    (`autonomous_session_watch.py:3933` RUNNING-only filter +
    `backend_poll.py:1100` terminate-before-reprovision +
    `backend_poll.py:1865-1881` poller emits-JSON-and-returns, NOT marker-writes).
  - **Alternatives rejected:** (B) decoupled `terminal_record_pending` state +
    new watcher pass; (C) sidecar/sentinel terminal-JSON persist + replay pass —
    both over-engineered for a transient two-subprocess-write failure (pivot
    marker calls (C) "the over-engineered alternative" and reserves (B) for an
    unacceptable-(A)-residual that does not obtain).
- **`_WEDGE_RECORD_RETRY_ATTEMPTS = 3` (1 initial + 2 retries).**
  - **Why:** covers a transient flock/network blip (which clears in <1s) without
    spinning; total added wall ≤ 3s, negligible for a fail-soft 10-min cron.
  - **Source:** `scripts/i528_phase0_preflight.py` (`max_retries` default 5 for a
    REMOTE Anthropic API; a LOCAL flock recovers far faster, so 3 total is the
    right scale — fewer attempts, same backoff shape). `ungrounded — not
    literature-pinned`, but bounded + cheap + tested; the exact count is not
    outcome-changing (the fix is "retry at all in-tick", not the precise N).
- **`_WEDGE_RECORD_RETRY_BASE_S = 1.0` (sleeps 1s, 2s).**
  - **Why:** a local flock contender clears in well under a second; a 1s base
    (vs the i528 2s base for a remote API) matches the faster local failure
    class while keeping total added wall ≤ 3s.
  - **Source:** adapted from `i528_phase0_preflight.py:95` (`2.0 * (2**attempt)`),
    halved base for the local-failure class. `ungrounded — needs smoke-test` in
    the strict sense (not literature-pinned), but bounded + not outcome-changing.
