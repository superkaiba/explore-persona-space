## 3. The four changes

### 3.1 Item (1) — plan-version immutability (`workflow_lint.py`)

**Contract.** A persisted `tasks/**/plans/v<K>.md` is immutable. An amendment
requires a NEW version file via `task.py new-plan-version`, never an in-place
edit of an existing one.

**Why the obvious implementation fails.** The motivating incident (#2061 v11)
never landed in committed history: `v11.md` has one add
(`eb53768bbd task #2061: plan v11`) followed only by pure `R100` renames through
the status chain, and its current content is byte-identical to that add. The
mutation lived in the working tree and was reverted or superseded before any
commit. A history-only scan would have been blind to the exact incident that
motivated the check.

**Two arms, both required.**

- **Arm W (working tree) — the arm that catches the incident.** One
  `git status --porcelain` call scoped to the plans pathspec. Any worktree-column
  `M` or `D` on a tracked `plans/v*.md` is a violation. Cost: milliseconds. This
  fires DURING the mutation window, which is when the lint actually runs
  (pre-commit, Step 9c, Step 10d pre-push).
- **Arm H (committed history) — the durable backstop.** One
  `git log --name-status` call over the same pathspec with rename detection ON.
  A status-folder move is `R100` and is CLEAN. A violation is an `M` entry, or an
  `R` with similarity below 100. Cost: measured ~2.3s over 7277 distinct
  historical paths.

**Rename-following is load-bearing.** Do NOT resolve the persist commit with
`--no-renames --diff-filter=A | tail -1`: for #2061 v11 that resolves to the last
status-move commit rather than `eb53768bbd`, because `--no-renames` splits every
folder move into D+A. That same artifact is why 306 paths appear to carry more
than one add commit. Arm H sidesteps per-path resolution entirely by keying on
the diff status letter with rename detection enabled — no `--follow`, no
per-path subprocess (7277 `--follow` invocations would be far too slow for the
default run).

**Severity: FAIL.** Baseline is clean in both arms — 0 modify-after-add commits
across 7277 historical paths, and 0 dirty plan files across the repo root plus
all 24 `.claude/worktrees/*` probed. Zero false positives at ship.

**Escape hatch.** A module-level `PLAN_IMMUTABILITY_ALLOWLIST` (empty at ship,
entries require an inline reason comment) plus an env kill switch following the
local `EPM_*` naming convention. Rationale: a legitimate amendment does exist as
a shape (fixing a secret accidentally committed into a plan), and a lint with no
escape hatch gets disabled wholesale.

**Integration.** New flag `--check-plan-version-immutability`, bundled into the
no-flags default run, with the module docstring bullet the file's convention
requires. If Arm H measures above ~3s in the default run, ship Arm H behind the
explicit flag only and keep Arm W in the default (stated as the fallback in §0).

### 3.2 Item (2) — agent `model:` pin PRESENCE (`workflow_lint.py`)

**What already exists.** `check_agent_model_pins` validates pin VALUES
(`AGENT_MODEL_ALLOWLIST`, `AGENT_MODEL_PIN_RE`, `AGENT_MODEL_1M_SUFFIX`) and is
already bundled into the no-flags default run. The residual is only the presence
half: the function `continue`s when no pin is found.

**The contradiction this must resolve, not paper over.** The function's own
docstring currently states that unpinned files are "silently skipped — agents may
legitimately inherit their model from the parent (no pin = no runtime contract to
validate)", citing CLAUDE.md's "Prompt-cache key discipline" as explicitly
allowing a missing pin. Enforcing presence without rewriting that prose ships a
function whose docstring contradicts its behavior.

**Resolution.** A missing pin stays LEGAL at runtime; what the check requires is
that the inherit be DECLARED rather than accidental. Satisfy the check either
with a pin or with membership in a new `AGENT_MODEL_INHERIT_ALLOWLIST` (each
entry carrying an inline reason). Rewrite the docstring paragraph to state this
distinction.

**Severity: FAIL.** All 43 repo agent files already carry a pin (`no_pin=0`), so
this is a zero-false-positive ratchet against the next unpinned file, not a fix
for a live offender.

**Two honest scope notes.**
- The #545 incident class cannot recur today for an unrelated reason:
  `CLAUDE_CODE_SUBAGENT_MODEL` is set in `~/.claude/settings.json` and sits at the
  top of the resolution chain, making per-file pins inert while present. The check
  protects the configuration in which that env var is absent.
- The walk (`_iter_agent_pin_target_files(_REPO_ROOT)`) is repo-only, so
  user-global `~/.claude/agents/` files (where the lean twins live) are correctly
  out of scope and stay unaffected.
- **Out of scope:** editing CLAUDE.md's "Prompt-cache key discipline" bullet. The
  body does not ask for it and the docstring change is sufficient to remove the
  contradiction. Recorded here so the omission is deliberate.

### 3.3 Item (3) — GPU-hours token conflict (`verify_plan.py`), new check `c59`

**Why the body's predicate is unshippable.** Keying on "the token appears more
than once" FAILs 2468 of 3971 versioned plan files (62.2%) — the repeats are
overwhelmingly legitimate. Keying on distinct RAW values is also wrong: all 11
files with conflicting raw values are false positives, in three shapes — a value
quoted inside prose (#2177 v1 line 56), meta-discussion in a plan whose SUBJECT
is this very checker (#625 v1–v3), and revision-history comparison tables
(#524 v6/v7 line 19).

**The correct predicate.** Restrict to DECLARATION-SHAPED tokens — line-anchored,
optional bullet / bold / backtick wrap, nothing else on the line, with fenced
code blocks stripped first — then run two arms:

- **Arm A:** more than one DISTINCT declaration-shaped value. Corpus: **2 / 3971**
  (#524 v2 and v3, both 590 vs 900).
- **Arm B:** the value a first-match consumer would read differs from the first
  declaration-shaped value. Corpus: **5 / 3971 (0.13%), zero false positives** —
  and Arm B catches the motivating incident: `tasks/awaiting_promotion/2061/plans/v7.md`
  and `v8.md` both read first-match 70 against declared 80. The other three are
  #2177 v1 (65 vs 0), #524 v7 (400 vs 250), #524 v6 (180 vs 400).

**Hard constraint.** 646 files carry a matching token but NO declaration-shaped
token at all. The check must therefore NEVER REQUIRE declaration shape — it
compares only when at least one exists, and SKIPs otherwise. `c5`'s existing
presence contract is untouched.

**Severity: WARN-only — and this corrects the harm model asserted in the
`epm:clarify` note.** `_resolve_autonomous_plan_gate` (`scripts/task.py:401`)
receives `gpu_hours` as an ARGUMENT and is GPU-HOUR-BLIND as of #1771: it
auto-approves ANY parseable estimate regardless of magnitude and parks only on
`None`. A mis-read of 65-for-0 or 70-for-80 therefore does NOT flip the gate
decision. The real harm is a corrupted RECORDED estimate — the value that rides
the status marker note, the watcher's re-passed per-issue `auto_approve_gpu_hours`,
and the number an interactive reviewer or an orchestrator skim reads off the
plan. That is a provenance defect, not a spend-control defect. Combined with the
detector being regex-shaped, this lands squarely under the house fail-open
convention (`c39` / `c43` / `c46` / `c50` / `c52` / `c54` / `c57` / `c58` never
FAIL). Escalation to FAIL is a later, separately-justified step per the
`c26` / `c29` / `c33` precedent.

**Named residual, in the `c52` / `c57` honesty convention.** A conflicting value
that appears ONLY in non-declaration shapes on both sides is invisible to `c59`;
its silence is not evidence of a single consistent estimate.

### 3.4 Item (4) — absent `planned_wall_h` table (`verify_plan.py`, extend `c47`)

**What already exists.** `check_wall_cell_parseable` (`c47`, WARN-only) covers
MIS-PARSING cells via `plan_wall_budget.parse_plan_wall_budget`. The residual is
the absent-table branch, which `c47` explicitly SKIPs with the justification
"such a plan arms no tripwire, so there is nothing to lose."

**Why that justification is half right.** #2091 falsifies it where compute is
booked: the tripwire never arming IS the loss. But it stays CORRECT where no
compute is booked — a 0-GPU plan genuinely has no tripwire to lose. So the fix
is to narrow the trigger, not to delete the reasoning.

**Trigger: `kind: experiment` AND booked GPU-hours > 0.** Measured over the
latest plan of every experiment task (numeric version sort — a lexicographic sort
picks `v9` over `v11` and produced an untrustworthy first figure):

| bucket | count |
|---|---|
| absent table, booked GPU-h > 0 — **the new WARN** | **13** |
| absent table, booked GPU-h == 0 — stays SKIP (justification holds) | 7 |
| absent table, no GPU token at all — stays SKIP (pure noise) | 27 |
| table parses cleanly | 162 |
| table present but unparseable — already WARN under `c47` | 20 |
| total `kind: experiment` tasks | 229 |

Narrow trigger = 13/229 (**5.7%**) versus 20.5% for the body's broad form, and it
still catches the motivating cases — #2061 (70 booked GPU-h) and #1739 (14).

**Severity: WARN-only**, unchanged from `c47`, per the `c26` / `c29` / `c33`
precedent that heuristic compute-table checks stay WARN-only until a clean corpus
baseline licenses escalation. 13 live WARNs is not a clean baseline.

**Also update:** `c47`'s docstring (the "nothing to lose" sentence now needs its
booked-compute qualifier) and the module registry table entry.
