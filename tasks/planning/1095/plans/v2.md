## 3. Design

### 3.1 Decision: option (a) drain-side derivation (option (b) rejected)

**(a) Drain-side** fixes every past and future dispatcher at ONE choke point: `_post_drained_sentinel` is the single post site for both drain lanes — RunPod (`_drain_sentinels` :2328 → `drain_sentinels_via` :2148 → `_post_drained_sentinel` :2270) and GCP (`backends/gcp.py:5083 GcpBackend._drain_sentinels`, which imports `drain_sentinels_via` from `scripts.poll_pipeline` at gcp.py:5155/5166 and calls it at :5248). It also matches the existing precedent: the #899/#975 synthesized-envelope path ALREADY derives max+1 at this exact site; the fix extends the same derivation to real results sentinels on collision.

**(b) Launch-time version threading** was rejected: it requires every one of ~30 existing dispatchers plus all three launch surfaces (experimenter SSH launches, GCP `--workload-cmd` composition, SLURM submission) to adopt an env convention; it does nothing for existing dispatchers until each is edited; #899-class raw writers would never adopt it; and it has a structural staleness failure mode — the GCP→RunPod failover and crash-fix relaunches reuse the composed workload cmd verbatim (`.claude/rules/compute-backend-failover.md`, `crash-fix-rounds.md`), so a threaded "next version" computed at first launch goes stale on exactly the multi-launch flows this bug is about, re-creating the collision (or worse, a duplicate explicit version).

### 3.2 Scoping rule (which kinds get the rewrite)

**Exactly `kind == "epm:results"`.** Defense:

- `epm:results` is the only sentinel-emitted kind whose highest-version row is resume-authoritative: markers.md's parsing rules (lines 18-21, 243) build the skill's `marker_map` from the highest-version row per kind, and `epm:results` is one of the three named round-versioned kinds (markers.md:29). The demonstrated harm (#825: stale v2 authoritative over three newer rounds) is specific to this kind.
- `epm:progress`-class sentinels are stream signals consumed by recency (`latest_event` / `task.py latest-marker`), many per run, all hardcoding v1; rewriting them churns versions with zero consumer benefit and would silently change the semantics the existing verbatim test pins (`test_drain_real_enveloped_sentinel_keeps_explicit_version_verbatim` uses `epm:progress` v7 — it stays green under this scoping by construction, not by accident).
- Gate sentinels (`epm:fact-candidates` etc.) are semantically v1-per-gate; the orchestrator parks on the drain's `gate` RETURN value (:2321-2324), not on the version, and some round-cap counting reads count markers by version — rewriting could inflate those counts.
- General principle: rewriting a producer-declared field is a semantic override; scope it to exactly the kind where the collision is structural, demonstrated, and where every consumer is verified safe (§2 consumer conventions). Widening to other kinds is a possible follow-up with its own consumer audit, not a default.

### 3.3 Rewrite condition and mechanism

The rewrite fires iff ALL hold, checked in this order:

1. `"version" in data` and `version = int(data["version"])` succeeds — the `int()` runs FIRST, so `"version": null` keeps the loud TypeError (#975) for every kind, before any exclusion or derivation logic.
2. `kind == "epm:results"`.
3. NOT excluded as smoke/dryrun/phase-progress (§3.4).
4. `version <= existing_max`, where `existing_max` is computed from `list_events(issue)` (§3.5). Strictly-above-max declared versions pass verbatim (constraint 6: never lower a legitimately-higher declared version — e.g. a dispatcher that correctly threads a higher version).

**Mechanism:** set `version = None` and add `sentinel_declared_version: <declared int>` to the post extras; `post_event` then derives max+1 under its `_locked()` flock (task_workflow.py:3170-3173). This deliberately reuses the tested #975 derivation instead of posting an explicit drain-computed max+1 — the drain-side max read is outside the flock, so an explicit max+1 would race concurrent posters (TOCTOU); passing None makes the derivation atomic. A loud `log.warning` names the sentinel path, the sentinel's own `ts` field (when present), the declared version, and the existing max.

**`<=` not `<`:** declared == max is a live collision with an existing row (same kind + version, different content — exactly the multi-round shape, since every round declares 1); it must rewrite. Only strictly-above is legitimate threading.

**Degenerate declared values (0 / negative):** with no prior rows `existing_max` is 0, so a nonconforming declared `0` or negative satisfies `version <= 0` and rewrites to a derived v1 with the `sentinel_declared_version` extra — reasonable (a declared 0/negative never lands below a real row, and the forensic extra records the nonconforming input). A declared 1 with no prior rows stays verbatim (T4).

### 3.4 Smoke/dryrun exclusion (constraint 1) — how they're distinguishable at drain time

Three structural signals, ANY one excludes (helper `_results_version_rewrite_excluded`, legs exposed via `_results_rewrite_exclusion_legs` for the §5 test discipline):

1. **`gate` NAMES a smoke/dryrun/phase signal** — `str(data.get("gate") or "").strip().lower() in {"smoke", "dryrun", "dry-run", "dry_run", "phase"}`. The #641 convention (drain docstring :2168-2172, gate extraction :2311-2324) has dispatchers emit benign signals as `gate=smoke` / `gate=dryrun`; `phase` covers the real `kind="epm:results", gate="phase", blocks_pipeline: False` progress-signal shape pinned by `test_drain_non_blocking_phase_signal_posts_but_does_not_surface_gate` (tests :430-466) — that informational shape keeps its verbatim version via THIS leg. Note `gate=False` / `gate=None` normalize to `""` under `str(x or "")`, so the gate-less real writers (§2) sail past this leg.
2. **Truthy top-level `smoke` field** — `bool(data.get("smoke"))`. issue667_dispatch.py's `write_sentinel` (:109-126) threads `extra={"phases": ..., "smoke": smoke}` into the top-level payload (:995; sibling issue667_pertoken_dispatch.py:343), so in smoke mode its kind-`epm:results` sentinel carries `smoke: true` on a NON-smoke filename (`issue-667-epm_results-<ns>.json`) — neither the gate-name nor the filename leg would catch it. Production runs set `smoke: False` → falsy → rewritten, correct.
3. **Filename convention** — basename `endswith("-smoke-results.json")` or contains `"-smoke-"` (the documented smoke sentinel name `issue-<N>-smoke-results.json`, poll_pipeline.py:924; written by e.g. `dispatch_neg_setpoint_601.py:801`). Belt-and-braces for a hypothetical smoke writer that omits the structured fields.

**A bare `blocks_pipeline: False` is deliberately NOT an exclusion leg** (this reverses plan v1's leg 2). The evidence: real TERMINAL `epm:results` writers set `blocks_pipeline: False` as a matter of house style — it means "don't park the poll loop on my non-empty gate value", NOT "I am informational/smoke": issue664_dispatch.py:2409-2424 (terminal results with a full `reproducibility_card`, `gate: "results"`, `blocks_pipeline: False`), issue734_dispatch.py:1069-1080 (`gate: False`, `blocks_pipeline: False`), issue654_dispatch.sh:419-429 (`gate: False`, `blocks_pipeline: False`, `version: 1`), and issue_597/dispatch_leakage_dynamics_597.py:1144-1155 (`gate: None`, `blocks_pipeline: False` — a GATE-LESS real writer that only the bare leg's absence rescues). Under plan v1's legs, every dispatcher of this house shape was permanently exempted from the rewrite — the filed bug would persist and the fix would be inert on exactly the writers that motivated it. Erring toward over-exclusion is safe ONLY when the excluded set is actually smoke; exempting the house terminal shape is not over-exclusion, it is a no-op fix.

**Named residual (honest):** a smoke-mode writer whose ONLY smoke indicator is nested INSIDE `note` is not catchable by any of the three legs — issue_597's payload carries `"smoke": params.smoke` inside the `note` dict (:1153-1155), and issue664's smoke flag rides the note prose (`smoke={args.smoke}`, :2411). The drain does NOT descend into `note` to look for it: `note` may be a JSON *string* rather than a dict (issue734:1071 `note=json.dumps(...)`; the issue922_common.py:596-620 note-shape precedent), so parsing it is fragile by construction. The residual is covered by kill criterion 3 and by the §3.8 doc recommendation that smoke runs use the existing house kind `epm:smoke-result` (already the pattern in issue634/744/1073/779's writers: `write_sentinel("epm:smoke-result" if args.smoke else "epm:results", ...)`) — a smoke sentinel under a different KIND is excluded by §3.2's kind-scoping outright. Over-exclusion on the three legs remains SAFE (it preserves today's verbatim threading); under-exclusion of a residual-class smoke writer would let a smoke row land ABOVE the production max — the harm constraint 1 bans — hence the kill criterion. Note the one live smoke-results-FILENAME writer found (`dispatch_neg_setpoint_601.py:790-806`) declares `kind="epm:progress"` for its smoke sentinel, so §3.2's kind-scoping already excludes it.

### 3.5 Existing-max read and its failure mode

New helper `_existing_max_version(issue, kind) -> int | None` using the already-imported `list_events` (the same read `_posted_sentinel_fps` :1826 uses):
- returns `max(version over rows with matching kind and isinstance(version, int), default=0)`;
- on ANY read exception: `log.error` + return `None`, and the caller keeps the declared version verbatim — **fail-open to pre-#1095 behavior** (mirroring `_posted_sentinel_fps`'s documented fail-open, :1830-1832). A dedupe/marker must never be lost to a version-hygiene read failure.

Read freshness: the helper is called per qualifying sentinel (not cached across the drain loop), so two below-max results sentinels in ONE drain land at max+1 then max+2 — `post_event` committed the first durably before the second's read. The extra `list_events` I/O is one small-file read per real results sentinel (rare: ≤ a few per tick), negligible.

### 3.6 Constraint walk (2, 3, 4 mechanics)

- **#1084 idempotency (constraint 2):** the dedupe key is `sentinel_fp = sha256(remote_path + "\n" + raw body)` (:1823), computed from the RAW sentinel and stored as a marker extra at post time (:2099). The version rewrite happens at post time and never enters the fp, so a re-drained identical sentinel (rename-failed, re-tick) fp-hits on the stored extra (:2239) and skips the re-post regardless of what version landed. The fp/dup check also runs BEFORE the version branch (:2245-2250), so a replay never re-executes `int(data["version"])` — unchanged. Pinned by new test T7.
- **#975 fail-loud (constraint 3):** `int(data["version"])` stays the FIRST statement of the key-present branch, before exclusions and the max read; `"version": null` raises TypeError out of the drain, `post_event` never called — for `epm:results` too. Pinned by existing test (epm:progress) + new test T6 (epm:results).
- **post_event contract (constraint 4):** `task_workflow.py` is not touched. Explicit-version-wins holds for every caller; the drain merely chooses, for one kind under one condition, to omit the version — an existing, documented `post_event` usage mode.

def _results_rewrite_exclusion_legs(remote_path: str, data: dict[str, Any]) -> dict[str, bool]:
    """Per-leg smoke/informational signals for the #1095 rewrite exclusion.

    Exposed as a dict so tests can assert EXACTLY which leg is active
    (the §5 test-construction discipline) without re-implementing leg
    logic. A bare ``blocks_pipeline: False`` is deliberately NOT a leg:
    real terminal epm:results writers set it to keep a non-empty gate
    from parking the poll loop (issue664/734/654/597) — it does not
    discriminate smoke from real. The drain never descends into ``note``
    (it may be a JSON string, not a dict): a smoke flag nested in note
    (issue597) is the documented residual — see kill criterion 3 and
    pod-side-reporting.md (smoke runs should use kind epm:smoke-result).
    """
    basename = remote_path.rsplit("/", 1)[-1]
    return {
        "gate_name": str(data.get("gate") or "").strip().lower() in _SMOKE_GATE_NAMES,
        "smoke_field": bool(data.get("smoke")),  # issue667-style top-level smoke flag
        "smoke_filename": basename.endswith("-smoke-results.json") or "-smoke-" in basename,
    }


def _results_version_rewrite_excluded(remote_path: str, data: dict[str, Any]) -> bool:
    """True when a real epm:results sentinel must KEEP its declared version.

    Smoke / dry-run / phase-progress sentinels must never bump real
    epm:results marker versions (#1095): a rewrite would land them
    ABOVE the production results rows, making a smoke row the
    highest-version-authoritative marker on resume (markers.md). Any leg
    suffices; over-exclusion is safe (it preserves verbatim threading).
    """
    return any(_results_rewrite_exclusion_legs(remote_path, data).values())


def _existing_max_version(issue: int, kind: str) -> int | None:
    """Max events.jsonl ``version`` for ``kind`` (0 when none); None on a
    failed read — caller FAILS OPEN to verbatim threading (#1095), mirroring
    ``_posted_sentinel_fps``'s fail-open contract."""
    try:
        events = list_events(issue)
    except Exception as exc:
        log.error(
            "version-collision events read failed for #%d (%s); keeping the "
            "sentinel's declared version verbatim (fail-open, #1095)",
            issue,
            exc,
        )
        return None
    return max(
        (
            e["version"]
            for e in events
            if e.get("kind") == kind and isinstance(e.get("version"), int)
        ),
        default=0,
    )
