```
+ - **Chained waves on a detached-spawn launcher fan out CONCURRENTLY.** A
+   fan-out launcher that spawns per-GPU shards via `setsid nohup ... &`
+   (often inside `bash -c "... & echo \$!"` for pid capture) leaves the
+   shards reparented to pid 1 and EXITS right after its spawn loop — bash
+   `wait` cannot apply to reparented children — so `wave2 && wave3 &&
+   wave4` runs EVERY wave near-simultaneously: N-waves × GPUs shards
+   co-locate (#1738: 16 shards over 8 GPUs within seconds), and the doubled
+   concurrent FUSE load can wedge the pod's MooseFS mount (statfs hang,
+   `request_wait_answer` waiters, GPUs 0 MiB — the read-wedge entry's #779
+   signature; pod swap required). Before chaining waves in one wrapper,
+   verify a `wait`/pid-poll loop AFTER the spawn loop in the launcher
+   SOURCE (`sed -n` the tail; `git show origin/<branch>:<script>` from the
+   VM) — a brief's "the launcher waits on its shard pids" is paraphrase,
+   never ground truth. If the launcher exits after spawning: gate each wave
+   on the previous wave's shard-pid death, dispatch one wave per launch, or
+   add a poll-until-dead loop on the shard pidfiles. Long-form:
+   `.claude/agent-memory/experimenter/feedback_detached_spawn_launcher_cannot_chain_waves.md`.
+   (Incident #1738 waves 2-4, 2026-07-28.)
```
