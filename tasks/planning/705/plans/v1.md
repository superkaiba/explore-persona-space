<h1>Plan — issue #705 (kind: infra, workflow-fix)</h1>
<p><em>fix <code>confirm_artifacts</code> finalize gate on phase-scoped / multi-attempt launches — without relaxing the gate</em></p>

<section class="plan-tldr">
<h2 style="border:none;margin-top:0">0.0 TL;DR</h2>
<ul>
  <li><b>What I'll fix:</b> Right now, the safety check that confirms a finished run actually wrote its files is misfiring on two real launch shapes — it looks for the files in the wrong place (the shared main checkout instead of the per-issue worktree where they live), and it demands files a partial-phase launch was never going to produce. Operators have been forced to bypass the check with a manual escape flag. I'll teach the check to look in the right directory and to only expect what the launch actually promised.</li>
  <li><b>What I expect:</b> After the fix, both the <code>#685</code> RunPod shape and the <code>#661</code> phase-scoped GCP shape pass the check on their own, with no manual bypass. The escape flag stays as an operator tool but stops being a routine workaround.</li>
  <li><b>What would change my mind:</b> If a launch could legitimately produce files in a place that is <em>neither</em> the worktree nor the main checkout, or if "what phase did this launch cover" turns out to be unknowable at launch time — then a config flag the launcher fills in wouldn't be enough and I'd need a different signal.</li>
</ul>
</section>

<h2>1. Goal</h2>
<p>The <code>confirm_artifacts</code> mechanical gate (the no-trust check that a finished run actually parked its declared artifacts before teardown) is structurally FAILing on two real production launch shapes, and the operator workaround has been to bypass it with <code>dispatch_issue.py finalize --skip-confirm-artifacts</code>. A routinely-bypassed gate is a dead gate: it stops catching the silent-data-loss it exists to catch. The Goal is to fix the gate's <em>resolution</em> — where it looks for git artifacts, which artifacts a phase-scoped launch is expected to produce, and which attempt's sentinel is live — so both shapes PASS honestly, restoring the gate as a real teardown precondition while keeping <code>--skip-confirm-artifacts</code> as a genuine escape hatch (not the default path).</p>

The declaration lives on <code>handle.extra[EXPECTED_ARTIFACTS_HANDLE_KEY]</code> and round-trips through <code>serialize_handle</code> / <code>expected_artifacts_from_handle</code>.</p>

<h2>3. Hypothesis</h2>
<p>This is an infra fix, not an experiment, but the falsifiable claims are concrete:</p>
<ul>
  <li><b>H1 (worktree):</b> When <code>_check_git</code> resolves its repo root to the issue worktree <code>.claude/worktrees/issue-&lt;N&gt;</code> (which has the issue-branch files checked out in its working tree AND tracked on the <code>issue-&lt;N&gt;</code> branch), <code>git ls-files -C &lt;worktree&gt;</code> reports the <code>eval_results/issue_&lt;N&gt;/</code> + <code>figures/issue_&lt;N&gt;/</code> files and <code>(worktree / p).exists()</code> is True → the #685 git check PASSes. <em>Falsified if</em> a linked worktree's <code>git ls-files</code> does not see branch-tracked files committed in it (it does — verified below in §12).</li>
  <li><b>H2 (phase-scope):</b> When a phase-scoped launch sets <code>skip_default_git_paths=True</code>, the declaration carries only the HF + sentinel checks the launch actually produces, so the git check SKIPs (no paths declared → SKIP, not FAIL) and the gate PASSes on the real deliverable. <em>Falsified if</em> SKIP is treated as FAIL anywhere (it is not — <code>verify_artifacts</code> only fails on <code>status == "FAIL"</code>).</li>
  <li><b>H3 (stale sentinel):</b> When the declared sentinel path is missing but exactly one live attempt-scoped sentinel exists under <code>eval_results/issue_&lt;N&gt;/&lt;attempt&gt;/.completion-sentinel.json</code>, preferring it (with the phase=done + issue-match content checks UNCHANGED) makes the #685 multi-attempt sentinel check PASS without relaxing the keystone content validation. <em>Falsified if</em> ambiguity (≥2 sibling sentinels) cannot be resolved deterministically — handled by FAILing loud on ambiguity, never guessing.</li>
</ul>

<h2>4. Design</h2>

<h3>4.1 — Worktree resolution (option (a): <code>git_repo_root</code> field on the declaration)</h3>
<p><b>Why (a) over (b)/(c):</b> All three backends (RunPod, GCP, SLURM) read the SAME declaration off <code>handle.extra</code> and each constructs its own <code>VerifierIO</code> (RunPod injects a custom <code>read_sentinel</code>; GCP/SLURM use bare defaults). Threading a per-call <code>VerifierIO(repo_root=...)</code> (option (b)) requires editing every backend's <code>confirm_artifacts</code> AND <code>_cmd_finalize</code> to derive + pass the path — three+ wiring sites, and <code>_cmd_finalize</code> would have to re-derive context the launch path already knew. Option (c) (probe-both-roots fallback) mixes two repo roots in one call and is the least predictable. Option (a) puts the repo root on the declaration that ALREADY round-trips on the handle, so it is computed ONCE at launch (where the worktree is known) and consumed uniformly by every backend with zero per-backend wiring. It is also the field <code>VerifierIO.repo_root</code> already exists to honor — we just source it from the declaration instead of a constructor arg.</p>

<p><b>artifacts.py changes:</b></p>
<pre>
# ExpectedArtifacts dataclass — NEW optional field (default None = current behavior)
@dataclass(frozen=True)
class ExpectedArtifacts:
    issue: int
    ...
    sentinel_path: str | None = None
    git_repo_root: str | None = None   # NEW: abs path for the git checks
    # ^ when set, _check_git resolves the git working tree HERE instead of
    #   the pyproject __file__-walk. Populated by the launch path with the
    #   issue worktree (.claude/worktrees/issue-&lt;N&gt;) when the run's code +
    #   committed artifacts live on an unmerged issue-&lt;N&gt; branch.

# build_expected_artifacts_declaration(...) — accept + emit it
def build_expected_artifacts_declaration(*, issue, sentinel_path, custom_workload,
        attempt_id=None, ..., git_repo_root: str | None = None,
        skip_default_git_paths: bool = False):   # (skip_* added in 4.2)
    ...
    return {
        "issue": int(issue),
        ...
        "git_paths": [] if skip_default_git_paths else [
            f"eval_results/issue_{issue}/", f"figures/issue_{issue}/", *extra_git_paths,
        ],
        # when skip_default_git_paths: still honor caller-declared extra_git_paths
        # (so a phase that DOES commit a scoped file can declare it)
        "sentinel_path": sentinel_path,
        **({"git_repo_root": git_repo_root} if git_repo_root else {}),
    }

# expected_artifacts_from_handle(...) — read it back
return ExpectedArtifacts(
    issue=int(raw["issue"]),
    ...
    sentinel_path=raw.get("sentinel_path"),
    git_repo_root=raw.get("git_repo_root"),   # NEW
)

# verify_artifacts(...) — thread it into _check_git via a per-call io override
# (do NOT mutate the caller's io; build a derived one only when the field is set)
def verify_artifacts(expected, *, io=None):
    io = io or VerifierIO()
    if expected.git_repo_root and io.repo_root is None:
        from dataclasses import replace
        io = replace(io, repo_root=Path(expected.git_repo_root))
    ...
</pre>
<p><b>Precedence rule (load-bearing):</b> an explicitly-injected <code>io.repo_root</code> (e.g. a test, or RunPod's future use) WINS over the declaration field — <code>_resolve_repo_root</code> already returns <code>io.repo_root</code> first. We only fill <code>io.repo_root</code> from the declaration when the caller left it <code>None</code>. This keeps the existing test seam (<code>_make_io(repo_root=tmp_path)</code>) authoritative.</p>

<p><b>Launch-side population (where the worktree is known):</b> <code>scripts/dispatch_issue.py::_launch_extra_from_args</code> already computes <code>extra["repo_branch"]</code> (the current branch when non-<code>main</code> on the gcp/auto lane, or the explicit <code>--repo-branch</code>). The worktree path is derivable from the same branch:</p>
<pre>
# scripts/dispatch_issue.py — add a helper + thread into the declaration builders
def _issue_worktree_git_root(issue: int, repo_branch: str | None) -> str | None:
    """Abs path to the issue worktree IF the run uses a non-main issue branch
    whose committed artifacts are not yet merged to main. None otherwise."""
    if not repo_branch or repo_branch == "main":
        return None
    # canonical worktree path written by scripts/new_worktree.sh
    from explore_persona_space.task_workflow import repo_root
    wt = repo_root() / ".claude" / "worktrees" / f"issue-{issue}"
    return str(wt) if wt.exists() else None
</pre>
<p>This <code>git_repo_root</code> is passed to <code>expected_artifacts_declaration(...)</code> (GCP) / <code>build_expected_artifacts_declaration(...)</code> (SLURM/RunPod) at the launch call sites that build the declaration (<code>dispatch_issue.py</code> ~374; <code>runpod.py</code> ~297; <code>slurm.py</code> ~2219; the GCP twin <code>gcp.expected_artifacts_declaration</code>). Because finalize runs VM-side (workflow invariant — never pod-side), the worktree path resolves correctly at finalize time on the same VM.</p>
<p><b>Edge case:</b> if the worktree was already auto-merged + removed by the time finalize runs (Step 10d ran first), <code>wt.exists()</code> is False at <em>launch</em> time only matters — the field is baked at launch. If the dir is gone at finalize, <code>_check_git</code>'s on-disk check would FAIL loud (correct: the files should then be on <code>main</code>, but the declaration pinned the worktree). Mitigation: <code>_check_git</code> gains a fallback — when a declared <code>git_repo_root</code> no longer exists on disk, fall back to the pyproject-walked main root with a LOUD log (the post-merge state). Documented in §11.</p>

<h3>4.2 — Phase-scoped declaration (option (b): <code>skip_default_git_paths</code> flag)</h3>
<p><b>Why (b) over (a)/(c):</b> The task body itself notes (b) is consistent with "don't relax the gate": the gate still runs every applicable check — it just stops demanding the two full-task git paths a phase-scoped launch never promised, falling through to SKIP (which is not FAIL). Option (a) (a <code>phase_scope</code> enum → path-subset map) couples the verifier to a per-issue phase taxonomy it has no business knowing and would need a per-plan mapping table; option (c) (drop defaults entirely, require explicit declaration everywhere) has the biggest blast radius — every existing call site (#598's hydra-lane, every dispatch script) would need updating, and the byte-identical snapshot guards make broad churn risky. (b) is a single conservative opt-in flag with zero default-path change.</p>
<pre>
# build_expected_artifacts_declaration + gcp.expected_artifacts_declaration
#   gain: skip_default_git_paths: bool = False
# When True:
#   git_paths = list(extra_git_paths)   # NO auto eval_results/ + figures/
#   (so a P3 extraction launch with deliverable on HF analysis_tensors/
#    declares hf_data_paths=("issue&lt;N&gt;_&lt;slug&gt;/analysis_tensors/",) via
#    extra_hf_data_paths and skip_default_git_paths=True; git check SKIPs)
</pre>
<p><b>Launch-side wiring:</b> a new CLI flag on <code>dispatch_issue.py launch</code>:</p>
<pre>
launch.add_argument(
    "--skip-default-git-paths",
    action="store_true",
    help=(
        "Phase-scoped launch (#604/#661): omit the auto eval_results/issue_&lt;N&gt;/ "

        "e.g. a P3 extraction whose deliverable is on HF analysis_tensors/, with "
        "the off-pod P5 phase producing the git files NEXT). The gate still runs "
        "the HF + completion-sentinel checks. Inert when the launch DOES commit "

<p>Threaded through <code>_launch_extra_from_args</code> → the declaration builders. The phase-scope/<code>primary_deliverable</code> mapping the task body mentions (per-issue plan §6.5) is NOT built into the verifier — the launcher (the orchestrator that knows which phase it is launching) sets the flag; the verifier stays a dumb mechanical checker. This keeps the verifier backend- and experiment-agnostic per its design contract.</p>

<h3>4.3 — Stale attempt sentinel (option 3(b): resolution-only sibling probe)</h3>
<p><b>Why 3(b) over 3(a)/3(c):</b> 3(a) (refresh the sidecar on every relaunch) requires identifying + editing every relaunch site across three backends and the watcher — broad, easy to miss one. 3(c) (RunPod-only live-API attempt_id lookup) is backend-specific and doesn't help the GCP/SLURM relaunch cases. 3(b) is a single localized resolution at <em>read</em> time in <code>_check_sentinel</code> (or a pre-check in <code>confirm_artifacts_from_handle</code>): when the declared path is missing, look for a live attempt-scoped sibling under the same <code>eval_results/issue_&lt;N&gt;/&lt;attempt&gt;/.completion-sentinel.json</code> pattern. It is resolution-only — the phase=done + issue-match content checks are UNCHANGED, so a genuinely-incomplete run still FAILs.</p>
<pre>
# artifacts.py — a sentinel-path RESOLVER used by _check_sentinel before reading.
# Lives behind the io.read_sentinel seam so tests stay FS-free: we add an
# optional io.glob_sentinels callable (default = real FS glob), so the resolver
# is injectable like every other external call.

def _resolve_live_sentinel(declared: str, issue: int, io: VerifierIO) -> tuple[str, str | None]:
    """Return (path_to_read, note). If the declared path resolves, use it.
    Else probe the sibling attempt dirs eval_results/issue_&lt;N&gt;/*/SENTINEL_FILENAME
    under the declared path's grandparent. Exactly-one live sibling -> prefer it
    (LOUD note). Zero -> declared (FAIL surfaces the real 'missing'). >=2 ->
    declared + an 'ambiguous' note (do NOT guess; the content check on the
    declared-missing path FAILs loud, never a wrong-attempt PASS)."""
    if io._sentinel()(declared) is not None:
        return declared, None
    siblings = io._glob_sentinels()(declared, issue)   # injectable; default real FS
    live = [s for s in siblings if io._sentinel()(s) is not None]
    if len(live) == 1:
        return live[0], f"declared sentinel {declared} missing; using live sibling {live[0]}"
    return declared, None  # 0 or &gt;=2 -&gt; fall through to the unchanged missing/ambiguous FAIL
</pre>
<p><b>Scope guard:</b> the sibling probe matches ONLY the exact <code>eval_results/issue_&lt;N&gt;/&lt;attempt&gt;/&lt;SENTINEL_FILENAME&gt;</code> shape (grandparent = <code>eval_results/issue_&lt;N&gt;</code>), so it can never pick up an unrelated file. The chosen sentinel still goes through the full <code>_check_sentinel</code> content validation (phase=done, issue match) — a stale-but-wrong-issue sibling FAILs there. RunPod reads sentinels over SSH (<code>_ssh_read_sentinel</code>); its <code>glob</code> seam defaults to an SSH-backed listing of the attempt dirs (mirror of <code>_ssh_read_sentinel</code>), so the resolver works on the pod-side tree too. <em>If the SSH-glob is judged too invasive for this fix's scope</em>, fall back to declaring the multi-attempt fix as RunPod-VM-side only (the GCP/SLURM sentinels are fetched local by <code>fetch_results</code> before confirm) and note the RunPod-SSH variant as a follow-up — decided at implementation against test feasibility (flagged Low-confidence in §12).</p>

<h3>4.4 — GCP lane parity (the cross-lane requirement)</h3>
<p>The GCP twin <code>gcp.expected_artifacts_declaration</code> is already a thin wrapper that delegates to the shared <code>build_expected_artifacts_declaration</code> (gcp.py ~754). So the new <code>skip_default_git_paths</code> + <code>git_repo_root</code> kwargs are added to the shared builder ONCE and the GCP wrapper just forwards them (two new params on its signature + two lines in the delegating call). No second implementation of the path logic. <b>Critical:</b> these kwargs are passed to the declaration at <em>launch-call</em> time — they do NOT enter <code>render_startup_script</code> (the byte-identical-snapshot-guarded VM bootstrap text). Verified: the declaration is attached to <code>handle.extra</code> by the launch path, never embedded in the rendered startup script. So <code>tests/test_gcp_backend.py</code>'s snapshot test is unaffected.</p>
