## 0. Plan Summary

**Change:** In `_check_feature_branch_behind` (preflight.py:404), stop hard-ERRORing on the FIRST `git fetch origin` timeout. Instead: (1) detect that the original fetch failed *specifically by timeout* (rc=-1, stderr=="timeout" from `_run`'s `TimeoutExpired` arm, line 152) vs. a hard git error; (2) on timeout, retry the fetch ONCE scoped to the branch (`git fetch --quiet origin <branch> --depth=1`) with a 60s timeout; (3) if the retry succeeds, fall through to the existing fresh-ref comparison unchanged; (4) if the retry STILL times out but a last-known `refs/remotes/origin/<branch>` ref exists AND `behind_own == 0` against it, downgrade the ERROR to a WARNING ("git fetch timed out; last-known origin ref shows branch up-to-date"); (5) preserve ERROR semantics when the retry fails AND (no last-known ref OR `behind_own > 0` OR `behind_own` is None/unknown) — and preserve ERROR unchanged when the original fetch failed by a NON-timeout hard error (auth, dead remote).

## 1. Goal

Make the feature-branch freshness check in `preflight.py` tolerate a **transient** `git fetch origin` timeout on a slow-network pod, so an otherwise-healthy, verifiably-current checkout is not falsely reported as `ok=false`. Today `_check_feature_branch_behind` (preflight.py:404-421) is the one place a failed fetch is a hard ERROR; on a flaky-network pod that ERROR blocks the launch even though `git rev-parse HEAD == origin/<branch>` confirms currency. Surfaced during the #664 r9 recovery relaunch (2026-06-28): the experimenter had to independently re-verify branch currency to push through a transient fetch-timeout ERROR. Keep the genuine-stale ERROR intact — this loosens ONLY the transient-timeout case, not the verifiably-behind case.

## 4. Design

### 4.0 Key structural facts (verified, with line numbers)

- `_run(cmd, timeout=10)` (147-157): on `subprocess.TimeoutExpired` returns `(-1, "", "timeout")` (152-153); on hard failure returns the real rc + stderr (151) or `(-1, "", <msg>)` for FileNotFound/other (154-157). **So a timeout is distinguishable from a hard git error by `stderr == "timeout"`** (the only path that sets that exact sentinel string). This is the discriminator the retry keys on.
- `check_git_status` (292) issues the fetch at **339-341**: `_run(["git","-C",str(project_root),"fetch","--quiet","origin"], timeout=15)`. Note: **no refspec** (fetches all refs), and the branch name is not yet known here — `branch` is resolved at 344-349, AFTER the fetch. `fetch_failed = fetch_rc != 0` (342) and `fetch_err` (the stderr) are passed into the per-branch helpers (352/356/359).
- `_check_feature_branch_behind(report, project_root, branch, fetch_failed, fetch_err)` (404): currently `if fetch_failed:` → `report.add_error(...)` + `return` (415-421). Otherwise it probes `refs/remotes/origin/<branch>` via `rev-parse --verify --quiet` (429-431), and if present compares `behind_own`/`ahead_own` (432-456); else (no pushed ref) WARNING (457-462). It always finishes with the origin/main informational comparison (464-470).
- `_behind_count(project_root, own_ref_full)` (160-172): `git rev-list --count HEAD..<ref>`; returns `int | None` (None on rc != 0 / non-int). Reads from whatever `refs/remotes/origin/<branch>` the last successful fetch populated.

**The branch name is available inside `_check_feature_branch_behind` (it is a parameter), so the scoped retry belongs there** — the original line-339 fetch cannot scope to the branch (branch unknown at that point), but the retry can.

### 4.1 New helpers — `_fetch_timed_out`, `_retry_fetch_branch`

Add two small helpers next to `_run`/`_behind_count` so the retry is unit-testable through the same `_run` seam:

```python
def _fetch_timed_out(fetch_err: str) -> bool:
    """A fetch FAILURE was specifically a timeout (vs. a hard git error).

    `_run` sets stderr to the exact sentinel "timeout" only on
    subprocess.TimeoutExpired (preflight.py:152-153). Any other failure
    (auth, dead remote, FileNotFound) carries real stderr text. We relax
    ONLY the transient-timeout case; hard errors stay ERROR.
    """
    return fetch_err.strip() == "timeout"


def _retry_fetch_branch(project_root: Path, branch: str, timeout: int = 60) -> tuple[bool, str]:
    """Retry a branch-scoped shallow fetch ONCE with a longer timeout.

    Returns (succeeded, stderr). Scoped to the single branch + --depth=1 so
    the retry is as cheap as possible on a slow link (it only needs to
    refresh refs/remotes/origin/<branch>, which is all the currency check
    reads). A second timeout returns (False, "timeout"); a hard error
    returns (False, <stderr>).
    """
    rc, _, err = _run(
        ["git", "-C", str(project_root), "fetch", "--quiet", "origin", branch, "--depth=1"],
        timeout=timeout,
    )
    return rc == 0, err
```

### 4.2 Modified `_check_feature_branch_behind`

Replace the `if fetch_failed:` ERROR-and-return block (415-421) with the retry/downgrade logic. Everything from the `own_ref = f"origin/{branch}"` block onward (423-470) stays **byte-identical** — the success/retry-success path falls straight through into it.

```python
def _check_feature_branch_behind(
    report: PreflightReport, project_root: Path, branch: str, fetch_failed: bool, fetch_err: str
):
    """Feature branch: ERROR only when behind/diverged from its OWN origin ref.

    Divergence from origin/main is expected on a feature branch and demoted
    to an informational WARNING.

    Fetch-failure handling (#696): a TRANSIENT fetch *timeout* is retried
    once (branch-scoped, 60s). If the retry succeeds, comparison proceeds
    against fresh refs exactly as a first-try success would. If the retry
    still times out, a last-known origin/<branch> ref that shows the branch
    up-to-date (behind_own == 0) downgrades the would-be ERROR to a WARNING
    — the same fail-soft-toward-PASS decision `main` already makes
    (preflight.py:370-378). A NON-timeout hard fetch error, a verifiably-
    behind branch, or the absence of any last-known ref all keep the ERROR.
    """
    own_ref = f"origin/{branch}"
    own_ref_full = f"refs/remotes/{own_ref}"

    if fetch_failed:
        if not _fetch_timed_out(fetch_err):
            # Hard error (auth, dead remote): behind_own == 0 against stale
            # refs proves nothing — fail LOUD, unchanged from #554/#550.
            report.add_error(
                f"git fetch origin failed ({fetch_err}) — cannot verify branch "
                f"{branch} is up to date with origin/{branch}."
            )
            report.git_status += ", fetch failed"
            return

        # Transient timeout — retry ONCE, branch-scoped, longer timeout.
        retry_ok, _retry_err = _retry_fetch_branch(project_root, branch)
        if not retry_ok:
            # Retry failed. Only a last-known ref that shows currency rescues us.
            rc_ref, _, _ = _run(
                ["git", "-C", str(project_root), "rev-parse", "--verify", "--quiet", own_ref_full]
            )
            behind_own = _behind_count(project_root, own_ref_full) if rc_ref == 0 else None
            if rc_ref == 0 and behind_own == 0:
                # Verifiably up-to-date against the last successful fetch's ref.
                report.add_warning(
                    f"git fetch origin timed out (retry also timed out); last-known "
                    f"{own_ref} ref shows branch {branch} up to date (behind 0). "
                    f"Proceeding on the last-known ref."
                )
                report.git_status += ", fetch timed out (last-known ref current)"
            else:
                # No last-known ref, count unknown, or verifiably behind →
                # cannot prove currency. Fail LOUD.
                report.add_error(
                    f"git fetch origin timed out (retry also timed out) — cannot "
                    f"verify branch {branch} is up to date with origin/{branch} "
                    f"(no current last-known ref)."
                )
                report.git_status += ", fetch timed out"
            # Both branches still report the origin/main informational drift,
            # mirroring the success path's tail (lines 464-470).
            _report_origin_main_drift(report, project_root, branch)
            return
        # retry_ok: fall through to the fresh-ref comparison below, unchanged.

    # --- everything below is BYTE-IDENTICAL to the current 429-470 block ---
    rc_ref, _, _ = _run(
        ["git", "-C", str(project_root), "rev-parse", "--verify", "--quiet", own_ref_full]
    )
    if rc_ref == 0:
        behind_own = _behind_count(project_root, own_ref_full)
        ahead_own = _ahead_count(project_root, own_ref_full)
        # ... (diverged / behind / ahead branches unchanged, 435-456) ...
    else:
        report.add_warning(
            f"Branch {branch} has no pushed {own_ref} ref — cannot verify "
            f"up-to-date-ness (unpushed local branch)."
        )
        report.git_status += f" (no {own_ref})"

    _report_origin_main_drift(report, project_root, branch)
```

## 11. Decision Rationale

N/A for model hyperparameters — no model training. The three load-bearing knobs:

- **Retry timeout = 60s (not 30s / 120s).**
  - *What:* the single retry uses `timeout=60`.
  - *Why:* the task body's acceptance criterion bounds the slow-network overhead at "~60s wall-clock," and the #696 repro showed a direct `git fetch origin issue-664 --depth=1` "completes with rc=0 within seconds" on the same pod — i.e. the timeout is transient latency, not a multi-minute stall, so a 60s ceiling is generous headroom over the observed few-seconds completion while still bounded. 30s risks re-tripping the same transient latency the first 15s tripped (too tight given we only retry once); 120s overshoots the body's budget and doubles the worst-case doomed-launch delay for no observed benefit.
  - *Source:* task #696 body acceptance criterion ("at most ~60s wall-clock") + the #696 repro ("completes ... within seconds").
- **Single retry (not 2-3).**
  - *What:* exactly one retry, then fall to the last-known-ref decision.
  - *Why:* preflight is on the launch hot path and the project standing preference is a fast preflight (the existing fetch is `timeout=15`; one 60s retry is already +45s). The last-known-ref fallback is the safety net that makes a second/third retry unnecessary — if one 60s retry can't refresh the ref, more retries on the same flaky link are unlikely to and just burn launch wall-clock. A bounded single retry + ref-fallback covers the transient case (retry succeeds) AND the persistent-but-current case (ref proves currency) without unbounded waiting.
  - *Source:* project preference for fast preflight (`timeout=15` at preflight.py:340) + the #696 acceptance criterion's single-retry framing.
- **`refs/remotes/origin/<branch>` (full-ref form) as the canonical last-known ref.**
  - *What:* the existence probe and `_behind_count` both use `own_ref_full = f"refs/remotes/origin/{branch}"`.
  - *Why:* preflight.py:423-428 already uses exactly this full-ref spelling in BOTH the `rev-parse --verify` existence probe and the rev-list counts, with the explicit comment (425-426) that the full form prevents a same-named tag from making the bare `origin/<branch>` form ambiguous. The #696 fallback reuses the identical ref form so its currency read is consistent with the existing comparison.
  - *Source:* preflight.py:427-431 (#554).
