## 4. Design

Why code, not a model call: trivially — this is a deterministic string parser; an LLM call would be nondeterministic, slow, and against the model-call-vs-code rule.

### 4.1 The normalization predicate — DECISION: (b) conditional

Normalize ONLY when `"\\n" in note and "\n" not in note` — i.e. the note contains literal backslash-n escapes AND zero real newlines. Rationale:

- The malformed class is precisely "the whole note is one physical line with escaped separators" (#825 v6/v7; also #599). Predicate (b) covers 100% of the observed class.
- (b) is strictly safer than (a) unconditional: 536 corpus notes TODAY mix real newlines with literal `\n` sequences (quoted code/JSON/regex content inside well-formed notes). No field parse currently differs under (a) vs (b) (measured: zero disagreements), so (a) buys nothing today — while exposing every future mixed note to mid-value splits. (b) leaves all 536 untouched by construction.
- The body's candidate-sketch predicate `"\\n" in note and "\n" not in note.replace("\\n", "")` is provably equivalent to (b) (deleting backslash-n pairs cannot create or destroy a real-newline char); use the simpler form.
- **Residual risk accepted:** a future SINGLE-line note carrying a legit literal `\n` inside a value (e.g. quoted regex in a `; `-joined note) would split mid-value under (b). Measured exposure today: exactly the #599 parse, which is inert and fix-direction. A note author who needs literal `\n` as content can use a real-multi-line note (the preferred shape per markers.md anyway).

**`\r\n` disposition (in scope, one extra `.replace`):** inside the same conditional branch, replace literal `\\r\\n` → `\n` FIRST, then `\\n` → `\n`, so no stray literal `\r` survives on a value token. (The predicate needs no `\r` term: the 2-char substring `\n` is contained inside the 4-char `\r\n` literal, so the branch already fires.) Corpus: 2 files contain literal `\r\n` (tasks 950/804); neither matches the predicate today (zero parse changes measured), so this is future-proofing only.

def test_label_parse_literal_backslash_n_escapes_825():

## 11. Decision Rationale

1. **Normalization predicate = (b) conditional (`"\\n" in note and "\n" not in note`).**
   **What:** normalize literal `\n`/`\r\n` escapes to real newlines only when the note contains escapes and zero real newlines.
   **Why:** the malformed class is exactly "one physical line with escaped separators"; (b) fixes 100% of it while leaving all 536 existing mixed notes (real newlines + literal escapes as content) untouched by construction.
   **Source:** #825 v6/v7 incident evidence + the plan-time full-corpus replay (52,409 notes; (b) changes 9 parses, 8 = the fix, 1 inert fix-direction on #599; (a) vs (b) disagree on 0) + the #894 corpus-replay discipline (`.claude/agent-memory/critic/feedback_marker_note_parser_corpus_replay.md`).
   **Alternatives:** (a) unconditional replace — identical on today's corpus but exposes every future mixed note to mid-value splits for zero present gain; rejected. Allowlisting v6/v7 into `KNOWN_MALFORMED_RUN_MARKERS` — leaves the recurring shape unparsed (the shell-`--note` producer will recur) and the #1111 allowlist is for genuinely field-less prose notes, not field-led ones; rejected. Fixing the POSTER instead — out of reach: notes are posted by many surfaces (orchestrator sessions, watcher), and the parser must tolerate the historical corpus regardless; parse-side tolerance is the established pattern (#894/#1090/#841).
2. **`\r\n` literal escapes: IN scope**, as a `\\r\\n → \n` replace ordered before the `\\n` replace inside the same branch. **Source:** corpus scan (2 files carry literal `\r\n`; neither matches the predicate today → zero behavior change, pure future-proofing at one line of code). **Alternatives:** declare out of scope — would leave a stray literal `\r` glued to value tokens if the shape ever arrives single-line; the one-line cost is smaller than the future debugging cost.
