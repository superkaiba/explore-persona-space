# Plan — #759: watcher must not respawn a duplicate driver for an issue with a live session

## 1. Goal

The autonomous-session watcher must never spawn a second `/issue <N>` `--auto`
driver while a live (daemon-tracked) or actively-working session for issue `N`
already exists. Two independent code paths can currently violate this; the fix
closes both with the smallest viable predicate edits, reusing the existing
liveness + grace helpers rather than adding a parallel mechanism.

## 3. Investigation summary

### (i) Every `spawn-issue --auto` emission site

Four spawn helpers, fed by three decision passes:

| Helper | Line | Driven by | Liveness gate today |
|---|---|---|---|
| `_respawn(entry, …)` | 2635 | crash-recovery `_process_entry`→`decide` (line 13036) | `_session_alive` only — **NO spawn-grace** |
| `_respawn_stalled_session` | 4634 | stalled detector `_process_stalled_session`→`decide_session_stalled` | **NEVER checks `_session_alive` / live_ids** |
| `_respawn_orphan` | 5789 | orphan sweep `_process_orphan_task`→`decide_orphan` | `mapped_alive` + `ORPHAN_SPAWN_GRACE_S` — **correct** |
| `_respawn` (infra-drain) | — | infra-drain pass (proposed `kind: infra` only) | not in scope — only spawns `proposed` tasks with no live driver by construction |

### (ii) Call paths

- **Crash-recovery pass** (`main()` line 12809-12812 → `_process_entry` line
  12989): for each `issue-<N>.json`, `alive = _session_alive(entry, live_ids)`
  (line 13017); `decide(status, alive, missed)` (line 13018). `decide()` (line
  444) returns `respawn` iff `status in ACTIVE and not alive and missed+1 >=
  threshold`. `live_ids` comes from `_live_session_ids()` (spawn_session's
  helper, fail-open to empty set), gated by a single `_daemon_reachable()`
  probe. **No `spawned_at` / `entry_age_s` grace** — the only `spawned_at`
  reference in `_process_entry` (line 13011) is the 14-day `MAX_ENTRY_AGE_S`
  backstop, and it is explicitly skipped `and status not in ACTIVE`, so an
  ACTIVE entry gets no age protection.
- **Stalled detector** (`stalled_session_pass` line 5399 → `_process_stalled_session`
  line 5153): reads signal 1 (`_self_report_age_seconds`), signal 2
  (`_latest_nonwatcher_event_ts`), signal 3 (`has_pod`), then
  `decide_session_stalled` (line 860). **`_session_alive` / `live_ids` is never
  read in this pass** — it decides purely on self-report age + marker age + the
  2-miss guard + `respawn_eligible` (= ACTIVE ∧ daemon_reachable ∧ not manual).
- **Orphan sweep** (`orphan_sweep_pass` line 5815 → `_process_orphan_task` line
  6138): `mapped_alive = bool(rec and rec["sids"] & live_ids)` (line 6156);
  `entry_age_s` from the registration's `newest_write` (line 6158);
  `decide_orphan` returns `clear` on `mapped_alive`, `keep` inside
  `spawn_grace_s`. Correct — used as the template.

### (iii) Existing live-session predicates

- `_live_session_ids()` (spawn_session, imported): same set but fail-OPEN to

  daemon-gated, so the empty-set ambiguity is acceptable there).

  reading alive for 11h).

### (iv) Staleness signals the stalled detector reads + Phase-1.5 marker behavior

- `STALLED_WINDOW_S = 45 * 60` (line 836) — BOTH self-report and marker must be
  ≥45 min stale, on 2 consecutive ticks, before `respawn`.
- The `/issue-tick` self-report cron fires **every 45 minutes**
  (`.claude/skills/issue-tick/SKILL.md` line 25/30 — lengthened from 20 min on
  2026-06-12). The gate-push pass also refreshes the self-report on every
  10-min STATUS TRANSITION, but a `planning`-status session sees no status
  transition for the whole plan→critique stretch.
- The adversarial-planner Phase 1.5 fact-checker posts `epm:plan-verify` only
  AFTER its verdict (`.claude/skills/adversarial-planner/SKILL.md` line 126);
  during the ~4-min run it posts no marker. The 6 critics + reconciler in the
  surrounding critique stretch (line 88, 300) similarly post their markers only
  on completion.

**Conclusion on bug class (b):** a ~4-min fact-checker CANNOT by itself trip the
45-min `STALLED_WINDOW_S` — the task body's "4-min subagent → stalled" framing
is not mechanically supported. The real (b) failure is the marginal-window
coincidence: `STALLED_WINDOW_S` (45 min) EQUALS the self-report tick cadence (45
min). On a tick that fires late (cron jitter, a busy VM, the LLM-priced tick
itself running long), the self-report ages past 45 min while a multi-minute
subagent holds the conversation and posts no marker — and the stalled detector,
which never corroborates against the daemon's live-session set, respawns a
session that is demonstrably ALIVE (its id is in `/list`). The cited #739
mid-Phase-1.5 respawn is consistent with this: a long planning stretch + a
late-firing 45-min tick + a detector that ignores live_ids.

### (v) The recovery-flow reality (reconciler-verified): no automatic backstop fires for a live-but-stalled wrapper

The alternatives reconciler verified two facts that reshape the (b.1) design and
correct a §6 risk claim from v1:

- **`_handle_stalled_alert` (line 4961) is a NOTIFY-ONLY arm, not a recovery
  arm.** It posts a marker and saves the `stalled-<N>.json` state file — it does
  NOT stop the zombie wrapper, does NOT spawn a replacement, and does NOT
  escalate. The canonical #506 recovery is the `respawn` arm
  (`_handle_stalled_respawn` line 4795 → `_stop_session` line 4856 →
  `_respawn_stalled_session` line 4873). So an UNCONDITIONAL `respawn → alert`
  downgrade (v1's (b.1)) would, for a session whose Happy wrapper is live but
  whose bg-Bash chain is dead (the #506 class), produce alerts forever and NEVER
  recover — re-opening exactly the #506 starvation hole.
- **`decide_orphan` (line 5582-5583) returns `("clear", 0)` whenever
  `mapped_alive` is True.** So while a zombie wrapper still appears in the
  daemon's `/list` reply (its id in `live_ids`), the orphan sweep does NOT fire
  any recovery for it either. v1's §6 risk row claimed "the orphan sweep still
  respawns it once its registration ages out" — that is mechanically false for a
  wrapper that remains in `live_ids`: NEITHER the stalled detector (under the v1
  unconditional downgrade) NOR the orphan sweep would ever recover it.

**Consequence for the design:** the (b.1) downgrade must NOT be unconditional.
It must be NARROWED so that it only suppresses a respawn when there is
independent evidence the live session is actually doing work; a live id with no
corroborating recent work-marker falls through to the canonical respawn arm.
The (b.1) corroboration check is therefore the backstop for the live-but-stalled
class — there is no other automatic one while the wrapper lingers in `live_ids`.

## 4. Design

Two predicate edits, both narrow, both reusing existing helpers. Plain-English
names used throughout; the function/line refs are for the implementer.

### Bug class (a) — crash-recovery pass respawns inside the registration-latency window

**Failure scenario closed:** a session that was just (re)spawned — by the user,
by a prior respawn tick, or by `spawn-issue --auto` — writes its `issue-<N>.json`
with a fresh `happy_session_id`, but that id has not yet appeared in the
daemon's `/list` reply. `_session_alive` reads False for 2 consecutive 10-min
ticks (~20 min) and `decide` respawns a duplicate. The duplicate is caught by
the `/issue` Step-0 single-orchestrator guard (detect-and-exit), but a session
slot + a cold context were already burned.

**Change — add a spawn-grace window to the crash-recovery respawn, mirroring
`ORPHAN_SPAWN_GRACE_S`.**

- `decide()` (line 444) gains an optional `entry_age_s: float | None = None`
  parameter and a `spawn_grace_s: float = RESPAWN_SPAWN_GRACE_S` parameter.
  Inside the `status in ACTIVE` branch, BEFORE incrementing `missed` on a
  not-alive read:

  ```
  if status in ACTIVE:
      if alive:
          return ("keep", 0)
      # NEW: a just-(re)spawned session whose id has not yet propagated to
      # the daemon /list reply is "spawn in flight", not dead. Reset the miss
      # count so the grace window cannot be straddled by accumulated misses.
      if entry_age_s is not None and entry_age_s < spawn_grace_s:
          return ("keep", 0)
      new_missed = missed + 1
      ...
  ```

- `_process_entry` (line 12989) computes `entry_age_s = time.time() -
  entry.get("spawned_at", 0)` (the entry already reads `spawned_at` at line
  13011) and passes it: `decide(status, alive, entry.get("missed", 0),
  threshold, entry_age_s=entry_age_s)`. A missing/zero `spawned_at` yields a
  large `entry_age_s` (no grace) — fail toward the current behavior, never
  toward suppressing a genuinely-needed respawn.

- New constant `RESPAWN_SPAWN_GRACE_S`, env `EPM_RESPAWN_SPAWN_GRACE_MIN`
  (minutes), default **15 min** (= `ORPHAN_SPAWN_GRACE_S`). Rationale §11/§hyper.
  Reuse the existing minutes-env-parse helper pattern (`_orphan_staleness_s`,
  line 5519) so a malformed value falls back to the default.

**Why this addresses (a):** `spawn-issue --auto` rewrites the registry with
`spawned_at = now` on every (re)spawn. Within the grace window the
crash-recovery pass treats the entry as spawn-in-flight regardless of whether
the new id has hit `/list` yet — exactly the same protection the orphan sweep
already has (`decide_orphan` line 5584). The window comfortably exceeds the
observed daemon-registration propagation lag (seconds to low minutes) without
masking a genuinely dead session for long (a real death surfaces ~15 min later,
one extra tick).

### Bug class (b) — stalled detector respawns a live-but-busy session; window equals tick cadence

**Failure scenario closed:** an autonomous session at `planning` (or any ACTIVE
status) is mid-`/adversarial-planner` — a fact-checker / critic / reconciler
subagent holds the conversation for minutes, posting no marker, and the 45-min
self-report tick fires late so the self-report ages past `STALLED_WINDOW_S`.
The stalled detector, which never checks the live-session set, escalates to
`respawn` even though the session's `happy_session_id` is sitting in the
daemon's `/list` reply right now.

**Two-part change:**

**(b.1) Corroborate the stalled trigger against the live-session set — NARROWED
to require independent active-work evidence (Option B).** In
`_process_stalled_session` (line 5153), compute liveness from the same daemon
read the other passes use and feed it as an additional guard. Concretely: the
caller (`stalled_session_pass`, line 5399) already has `daemon_reachable`; pass
`live_ids` down (the watcher computes it once in `main()` — thread it into
`stalled_session_pass(..., live_ids=...)` exactly as `orphan_sweep_pass` already
receives it, line 5821).

The downgrade is DELIBERATELY NOT unconditional. Per §3 (v), an unconditional
`respawn → alert` downgrade on any live id would starve the #506 class (live
Happy wrapper, dead bg-Bash chain) — `_handle_stalled_alert` never recovers and
the orphan sweep never fires while the id lingers in `live_ids`. So the downgrade
fires ONLY when the live id ALSO has corroborating evidence of recent real work;
a live id with NO such evidence falls through to the canonical respawn arm,
which is the correct recovery for a dead-bg-chain wrapper.

The corroborating signal is already computed in this pass:
`_latest_nonwatcher_event_ts` (signal 2) — the timestamp of the most recent
NON-watcher marker (the #661-widened "any non-watcher marker" signal). A live id
whose most recent non-watcher marker is within a freshness window is a session
genuinely making progress (it posted a real marker recently); a live id whose
last non-watcher marker is older than the window AND whose self-report is stale
is the #506 dead-bg-chain case and must respawn.

After computing `respawn_eligible` (line 5288), add (a single post-`decide`
rewrite, placed AFTER the existing `_provision_in_flight_reason` rewrite at lines
5307-5315 and the followups-exemption rewrite at line 5325, so it sees only the
respawns those exemptions did not already turn into `keep`):

  ```
  # After: action, new_missed = decide_session_stalled(...)
  # After: provision-in-flight rewrite (5307-5315), followups rewrite (5325).
  if action == "respawn" and daemon_reachable:
      session_live = _session_alive(entry, live_ids)
      if session_live:
          # NARROWED downgrade (Option B): only suppress the respawn when the
          # live id is corroborated by a recent NON-watcher work-marker. A live
          # id with a STALE last work-marker is the #506 dead-bg-chain class —
          # fall through to respawn (the canonical recovery). This closes the
          # #506 starvation hole that an unconditional downgrade would re-open.
          latest_work_ts = _latest_nonwatcher_event_ts(...)   # signal 2, already read above
          work_fresh = (
              latest_work_ts is not None
              and (now - latest_work_ts) < LIVE_WORK_CORROBORATION_S
          )
          if work_fresh:
              action, new_missed = "alert", new_missed
              # prose: "self-report stale but Happy id live AND a non-watcher
              #  work-marker posted within the corroboration window — alerting,
              #  not respawning, to avoid a duplicate driver."
          # else: leave action == "respawn" → the live-but-dead-bg-chain
          #  wrapper is stopped + replaced via the canonical respawn arm.
  ```

  - `LIVE_WORK_CORROBORATION_S` = the freshness window for "recent work-marker"
    = `STALLED_WINDOW_S` (the new 60 min). Reusing the stalled window keeps a
    single notion of "recent enough": if the last real work-marker is younger
    than the stalled window, the session is by definition not marker-stale and
    is doing work; if it is older than the window AND the self-report is stale,
    both staleness signals agree and a live id is the dead-bg-chain case. No new
    env var needed (it tracks `EPM_STALLED_WINDOW_MIN`). See §11.
  - **Why this is the backstop (not the orphan sweep).** Per §3 (v),
    `decide_orphan` returns `clear` on `mapped_alive`, so while the zombie
    wrapper remains in `live_ids` the orphan sweep fires NO recovery. The
    `else` branch above (respawn a live-but-uncorroborated id) IS therefore the
    automatic backstop for the #506 class — the only one that fires while the
    wrapper lingers in `live_ids`.
  - **Telemetry nicety (logged concern, applied):** the downgrade branch
    (`work_fresh` True → `alert`) increments a one-line sidecar counter (append a
    `{"ts", "issue", "event": "stalled-live-corroborated-downgrade"}` row to the
    existing watcher sidecar stream / a dedicated `.claude/cache/` JSONL), so a
    future reader can confirm in prod that the corroboration branch actually
    fires (vs the respawn-the-dead-bg-chain branch). Non-blocking; one append.

**(b.2) Widen `STALLED_WINDOW_S` so it comfortably exceeds the 45-min tick
cadence.** Today `STALLED_WINDOW_S == 45 min == the self-report tick interval`,
so the window is straddle-able by ordinary cron jitter. Raise it so a single
late tick cannot trip it. New value **60 min** (env `EPM_STALLED_WINDOW_MIN`,
already overridable per-call via the `window_s` arg of `decide_session_stalled`
line 870 — add the env-read at the module constant, mirroring
`_orphan_staleness_s`). 60 min = tick cadence (45) + a full extra tick (15 min
at the 10-min cron) of slack, so the self-report must miss MORE than one tick
before the window opens. This is belt-and-suspenders with (b.1): (b.1) stops a
duplicate even if the window opens; (b.2) stops the window opening on benign
jitter in the first place.

  - **Why both (b.1) and (b.2)?** (b.1) is the correctness fix (never respawn a
    live session that is corroborated as working; DO respawn a live-but-dead-bg
    one). (b.2) reduces alert noise: without it, every long planning stretch
    would now generate a benign downgrade-to-alert marker on a live session.
    (b.2) keeps the detector quiet during normal long subagent work; (b.1) is
    the hard guard for the genuinely-marginal case.

### Disjointness / no new mechanism

Both edits reuse `_session_alive`, `_live_session_ids()`,
`_latest_nonwatcher_event_ts` (signal 2, already computed in the stalled pass),
the `spawned_at` registry field, and the env-minutes-parse pattern already in
the file. No new state file, no new daemon read (the stalled pass piggybacks on
`main()`'s single `live_ids` snapshot — thread it in, same as the orphan pass),
no schema change. The one new sidecar counter (b.1 telemetry) is an append-only
JSONL row, not a new control surface.

### Why code, not a model call?

N/A — pure predicate logic over registry + daemon state; no unstructured-data
heuristic.

## 5. Acceptance criteria (mechanically verifiable; new tests in `tests/test_autonomous_session_watch.py`)

**Bug class (a) — crash-recovery spawn-grace:**

1. `decide("running", alive=False, missed=1, entry_age_s=ORPHAN_SPAWN_GRACE_S
   - 1) == ("keep", 0)` — a not-yet-live entry inside the grace window does NOT
   respawn even at the 2nd miss. (Mirror of `test_orphan_fresh_registration_keeps`,
   line 2955.)
2. `decide("running", alive=False, missed=1, entry_age_s=RESPAWN_SPAWN_GRACE_S
   + 1) == ("respawn", 0)` — past the grace window the existing 2-miss respawn
   still fires (no regression of the genuine-death path).
3. `decide("running", alive=False, missed=1, entry_age_s=None) == ("respawn",
   0)` — a missing `spawned_at` (entry_age_s None) preserves today's behavior
   exactly (fail toward respawn, never silently suppress).
4. `decide("running", alive=True, missed=3, entry_age_s=1) == ("keep", 0)` — a
   LIVE session is kept regardless of grace (alive short-circuits first).
5. An integration test on `_process_entry` (mirror
   `test_active_dead_needs_two_misses_before_respawn`): an `issue-<N>.json`
   with `spawned_at = now - 60` (inside grace), a dead id, ACTIVE status →
   `_process_entry` invokes `_respawn` ZERO times across 2 consecutive ticks;
   with `spawned_at = now - 3600` → respawns on the 2nd tick.

**Bug class (b) — stalled detector live-session corroboration + window:**

6. `_process_stalled_session` with a stale self-report + stale markers + 2nd
   miss + `respawn_eligible=True` BUT the entry's `happy_session_id` IN
   `live_ids` AND a recent non-watcher work-marker (within
   `LIVE_WORK_CORROBORATION_S`) → spawns ZERO `_respawn_stalled_session` calls
   and posts exactly one `orphan/stalled` ALERT marker (the corroborated
   downgrade). Mirror the existing `stalled_recorder` fixture used by
   `test_stalled_active_status_auto_respawns_after_two_misses` (line 1680) —
   assert the respawn recorder is empty and the alert recorder has one entry.
   This pins "downgrade fires on a healthy-busy session" (live id + recent work).
7. The same scenario with the id NOT in `live_ids` (genuinely dead wrapper) →
   respawns once (the existing behavior is preserved when the session is
   actually dead). This is the regression guard that proves (b.1) only
   suppresses LIVE corroborated sessions, not dead ones.
8. **Phase-1.5 simulation (regression floor):** a stalled-pass run where the
   self-report is 5 min old AND the latest marker is 5 min old →
   `decide_session_stalled` returns `("keep", 0)` and no respawn/alert fires —
   i.e. a ~4-min (and a 5-min) no-marker subagent stretch does NOT trip the
   detector. NOTE: this criterion documents the REGRESSION FLOOR only — it
   passes identically under BOTH the old 45-min window and the new 60-min one
   (5 min is far under either), so it does NOT by itself distinguish the two
   windows; criterion 9 is the test that pins the 60-min window specifically.
9. A self-report 50 min old (between the OLD 45-min and NEW 60-min window) +
   stale markers + 2nd miss → with the new `STALLED_WINDOW_S=60min`,
   `decide_session_stalled` returns `("keep", …)` (window not yet open),
   proving (b.2) buys the extra-tick slack. (Under the old 45-min window this
   same input would have opened the window — this is the test that distinguishes
   the new window from the old.)
10. `EPM_STALLED_WINDOW_MIN` / `EPM_RESPAWN_SPAWN_GRACE_MIN` env overrides parse
    a valid int and fall back to the default on a garbled value (mirror
    `test`-coverage of `_orphan_staleness_s`).
11. **Persistently-live-stalled session IS eventually recovered, not alert-only
    forever (the #506-hole closer; Codex-recommended).** Drive
    `_process_stalled_session` across repeated stale ticks with
    `live_ids={sid}`, NO provision-in-flight exemption and NO followups
    exemption, and the entry's last non-watcher work-marker held STALE (older
    than `LIVE_WORK_CORROBORATION_S`) — i.e. a live Happy wrapper whose bg-Bash
    chain is dead (#506 class). Assert that recovery is NOT permanently
    alert-only: the corroboration check finds NO fresh work-marker, so the
    `respawn` action survives the (b.1) rewrite and `_respawn_stalled_session`
    is invoked (the canonical stop+spawn recovery). Contrast with criterion 6
    (live + FRESH work-marker → alert-only by design): together criteria 6, 7,
    and 11 pin all three branches — corroborated-live → alert, dead → respawn,
    uncorroborated-live (#506) → respawn.

## 6. Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| Swing too far: a genuinely dead session is now kept ~15 min longer (a) | Medium | Only ONE extra tick of latency (~15 min) before a real death respawns — bounded, and the orphan sweep (90-min staleness, registration-INDEPENDENT) is the backstop for a truly-stuck ACTIVE task once its registration ages out. |
| The orphan sweep is NOT a backstop for the live-but-stalled class while the wrapper lingers in `live_ids` | n/a (corrected claim) | Per §3 (v): `decide_orphan` returns `clear` on `mapped_alive`, so while a zombie wrapper remains in `/list` NEITHER the stalled detector (under an unconditional downgrade) NOR the orphan sweep would recover it. ## 11. Hyperparameter grounding (Decision rationale)

- **`RESPAWN_SPAWN_GRACE_S` default = 15 min (env `EPM_RESPAWN_SPAWN_GRACE_MIN`).**
  Source: `ORPHAN_SPAWN_GRACE_S = 15*60` (#472 orphan-sweep, line 5508) — the
  validated window for "registration just written, id not yet in `/list`" in
  the sibling pass. Reusing the same value keeps the two passes' spawn-in-flight
  semantics identical; comfortably exceeds the observed daemon `/list`
  propagation lag (seconds-to-minutes) while adding at most one extra 10-min
  tick of latency before a genuine death respawns. Alternatives rejected: 5 min
  (too tight — a single slow `/list` round-trip could still straddle it); 30 min
  (needlessly delays a real death respawn). Source-anchored to `#472`.
- **`STALLED_WINDOW_S` raised 45 min → 60 min (env `EPM_STALLED_WINDOW_MIN`).**
  Source: the `/issue-tick` self-report cadence is 45 min
  (`.claude/skills/issue-tick/SKILL.md` line 30, 2026-06-12). The window must
  exceed the cadence by at least one cron tick so benign jitter cannot straddle
  it: 45 + 15 = 60. The 45-min original (#661-era) predates the tick lengthening
  from 20→45 min, so it silently became equal to the cadence — this raises it
  back to a safe margin. Alternatives rejected: keep 45 (== cadence, the bug);
  90 min (matches the orphan staleness but delays a genuinely-wedged-live alert
  longer than needed, since (b.1) already prevents the duplicate spawn). Source:
  `#661` (window origin) + `issue-tick/SKILL.md` (cadence).
- **(b.1) downgrade choice = Option B (narrow to active-work corroboration), NOT
  Option A (bounded K-escalation).** Rationale: Option B is the simpler fit and
  requires NO new env var, NO new per-session counter, and NO new state-file
  schema — it reuses `_latest_nonwatcher_event_ts` (signal 2), a value the
  stalled pass ALREADY computes, as the corroboration signal. Option A would add
  `EPM_STALLED_LIVE_ESCALATION_K` + a per-session escalation counter persisted in
  `stalled-<N>.json`, more surface for the same outcome. Both close the #506
  starvation hole identically (a persistently-live-but-dead-bg-chain session is
  eventually respawned); Option B does it in one tick (no fresh work-marker →
  respawn immediately) rather than after K episodes, which is strictly safer for
  the #506 cost asymmetry (a genuinely dead bg-chain is recovered sooner). Per
  the planner's "pick the simpler one if both fit" instruction, Option B is
  chosen. Source: §3 (v) reconciler verification + #506.
- **`LIVE_WORK_CORROBORATION_S` (the Option-B freshness window for "recent
  work-marker") = `STALLED_WINDOW_S` (60 min). NO new env var.** Source: the
  corroboration window IS the same "recent enough" notion the stalled window
  already encodes — a non-watcher work-marker younger than the stalled window
  means the session is not marker-stale and is working; one older than the
  window, combined with a stale self-report, is the dead-bg-chain signature.
  Tying it to `STALLED_WINDOW_S` keeps a single tunable and a single semantics;
  there is no design reason for a second independent knob. Alternatives rejected:
  a separate `EPM_LIVE_WORK_CORROBORATION_MIN` (needless second knob — they
  should move together); a tighter 30-min window (would respawn a live session
  that posted a real marker 35 min ago, re-introducing false respawns on slow
  but live lifecycle stretches). Source: §3 (iv) + #661 (the non-watcher-marker
  signal) + the `STALLED_WINDOW_S` grounding above.
