# Plan v1 — task #774: multi-zone GCP fan-out

## Goal
Before counting a GCP rung as a capacity miss, fan out across every us-central1
zone the rung's machine type is offered in. Specifically: bring the A100-40
fallback rung (`a2-highgpu-1g`, the #656 cheaper-but-smaller rung) up to its
verified maximal zone set `{a, b, c, f}` — the rung that currently has the most
unused fan-out potential.

## What the bug actually is (post empirical-verification)
The bug body's premise — "fan out across the region's A100-80 zones
(us-central1-a/b/c/f)" — is incorrect for A100-80. Live `gcloud compute
machine-types list --configuration=eps-gcp` against the project on 2026-06-30
returns, in us-central1:

- `a2-ultragpu-1g` / `-4g` / `-8g` (A100-80 family): **{a, c} only**. Not
  offered in `-b` or `-f`. The existing
  `MACHINE_TYPE_ZONE_AVAILABILITY` map is already correct + maximal.
- `a3-highgpu-1g` / `-2g` / `-8g` (H100 family): **{a, b, c} only**. Not in
  `-f`. Map already correct.
- `a2-highgpu-1g` (A100-40, the #656 fallback rung): **{a, b, c, f}**. Map
  already lists all four, but `DEFAULT_FALLBACK_ZONES = ("us-central1-b",
  "us-central1-c")` never includes `-f`, so the create-time ladder
  `[primary_zone] + fallback_zones` filtered by the map only ever resolves to
  `[a, b, c]` even for the A100-40 rung. The map comment already calls this
  out: "listing -f is harmless when GcpConfig never includes it (it is simply
  never matched)" — exactly the gap to close.

So for the #763 incident: both A100-80 zones (`a` + `c`) were genuinely
exhausted simultaneously. The fan-out logic was already walking both. No
additional A100-80 zone exists to add. But the A100-40 fallback rung (a later
ladder rung when the A100-80 rung exhausts) still had one unused zone.

## Method delta (vs the original body)
The original body proposed adding `us-central1-f` to the A100-80 zone set.
That cannot land — GCP does not offer A100-80 there. Plan v1 instead:
- (a) closes the documented `a2-highgpu-1g` gap by adding `-f` to
  `DEFAULT_FALLBACK_ZONES`;
- (b) updates the docstring on `DEFAULT_FALLBACK_ZONES` to record the
  per-machine RESTRICT-vs-extend semantics; updates the `a2-highgpu-1g` map
  comment to remove the now-stale "harmless because never matched" phrasing;
- (c) updates `.claude/rules/compute-backend-failover.md` with a short
  paragraph documenting the per-rung multi-zone fan-out + the GCP-imposed cap
  on the A100-80 family at 2 zones (so a future reader doesn't propose the
  same impossible "add -f to A100-80" fix again).

  rule-file paragraph, skip the `DEFAULT_FALLBACK_ZONES` change, post a

  `DEFAULT_FALLBACK_ZONES` change and ship only the doc updates (one of those
