# Plan — issue #773 (kind: infra)

**workflow-fix: protect active-task input caches from `vm_disk_guard` reclaim**

Target file: `scripts/clean_experiment_downloads.py` (library). CLAUDE.md doc
update is conditional — only if the new behavior changes a published contract
(it does not; see §3 / §9). Estimated GPU-hours (total): 0.

---

## 1. Goal

Add a third reap-gate to `clean_experiment_downloads.py` so a cache namespace
`data/issue_<M>/{hf_dl,g*_dl}` is NEVER deleted while a *different*, currently
ACTIVE task declares `data/issue_<M>/` as a planned input. Today the only gate
is "is the OWNING issue (the namespace `data/issue_<M>/`) at a terminal status?"
— if #M is at `completed`/`archived`/`awaiting_promotion`, its caches are reaped
regardless of who else is reading them. The failure mode this prevents:
`vm_disk_guard.py --apply` panic-cleaned #658's UltraChat/Betley input artifacts
(#658 was `awaiting_promotion`, ∈ `TERMINAL_CACHE_REAP_STATUSES`) while #742 was
`running` and reading `data/issue_658/store/v0_summaries.pt` (a symlink whose
target lives under `data/issue_658/hf_dl/`) plus `data/issue_658/g1_dl/.../v0_summaries.pt`.
The reap deleted the symlink targets; #742's round-3 launch died on
`FileNotFoundError`. The new gate fails toward keep: any active consumer of
`data/issue_<M>/` blocks the reap of #M's caches.

## 2. Prior work (what guardrails exist; what they miss)

Three protections already live in `scripts/clean_experiment_downloads.py` +
`scripts/vm_disk_guard.py`:

1. **`TERMINAL_CACHE_REAP_STATUSES`** (`vm_disk_guard.py:270`) =
   `{"completed", "archived", "awaiting_promotion"}`. Tier (b)
   (`clean_terminal_download_caches`) reaps caches ONLY for issues whose OWN
   status is in this set; an active-status owning issue is kept. **This is the
   owning-issue gate.** It says nothing about *other* consumers.
2. **Nested-`store/` parity guard** (`_cache_dir_reap_blocked`,
   `clean_experiment_downloads.py:356`). Refuses a wholesale `rmtree(cache_dir)`
   when a `store/` is mis-rooted UNDER the cache dir and not verifiably mirrored
   on HF (per-file size match, fail-toward-keep), sidecar-logs
   `kind: "nested-store-reap-skipped"`, adds the dir to `CleanResult.skipped`.
   This *did* save #658's mis-rooted store in some cases, but only when the
   `store/` sits literally under `hf_dl/` AND is unmirrored — it does not protect
   a sibling `store/` symlinked from a separate consumer, nor `g*_dl` inputs.
3. **Active-cache escalation** (`escalate_active_cache`, `vm_disk_guard.py:192`).
   For the OWNING task at active status: never deletes, but Telegram-pushes +
   sidecar-logs `kind: "active-cache-escalation"` so a human reclaims it after the
   run. Again: keyed on the OWNING issue being active, not on a cross-issue
   consumer.

**The gap (cross-issue consumer):** none of the three asks "is some OTHER active
task consuming `data/issue_<M>/` as a planned input?". #658 was terminal, so gate
1 allowed the reap; #742 (the consumer) was a different issue entirely, invisible
to gates 1–3. The #742 plan v6 §risks row even *predicted* this exact reap and
self-mitigated by snapshotting the needed tensors into `data/issue_742/inputs/`
+ sha-pinning — but that mitigation is per-plan and was added by hand; the
guard itself offered no protection.

## 3. Design (concrete code changes — all in `clean_experiment_downloads.py`)

The public signature of `clean_issue_downloads(issue_n, *, apply=False, data_root=None)`
is UNCHANGED for production callers. The active-consumer set is computed
INTERNALLY (one walk over `tasks/`), with one OPTIONAL keyword seam for tests +
the incremental wrapper. Order of the per-cache-dir gates: **active-consumer
check FIRST, then the existing nested-store parity guard** (the active-consumer
check is a cheap in-memory set lookup; the parity guard may make an HF call, so
short-circuiting on a consumer hit also avoids an unnecessary Hub listing).

### 3a. Active-task input-reference enumeration

```python
# Tasks whose work is DONE or paused — their declared inputs are not being
# actively consumed, so they never protect another issue's cache.
#   - completed / archived : terminal, work finished.
#   - on_hold              : explicitly parked, excluded from auto-dispatch.
#   - blocked              : halted awaiting user; not actively reading inputs.
# Everything ELSE (proposed/planning/plan_pending/approved/running/verifying/
# interpreting/reviewing/awaiting_promotion/followups_running) is "active" for
# THIS guard's sense: currently doing work or imminently planned to, so its
# declared inputs may be read at any moment.
_CONSUMER_INACTIVE_STATUSES = frozenset({"completed", "archived", "on_hold", "blocked"})

# Match data/issue_<M>/ (underscore) OR data/issue<M>/ (no underscore) — the two
# real naming conventions in data/. The trailing boundary is `/` or `_` so
# `data/issue65/` never matches a `data/issue658/` substring.
_DATA_ISSUE_REF = re.compile(r"\bdata/issue_?(\d+)(?=[/_])")


def _active_consumer_protected_issues(self_issue_n: int) -> dict[int, list[int]]:
    """Map {protected_issue_M: [consumer_task_ids...]} for every M that some
    ACTIVE task (status NOT in _CONSUMER_INACTIVE_STATUSES) declares as a
    data/issue_<M>/ input in its plan.md OR body.md.

    self_issue_n is EXCLUDED from the consumer set — a task never blocks its
    own cache reap (Step-8 self-cleanup + the incremental within-run path both
    reap the task's OWN cache; the guard must not protect a task against
    itself). READ-ONLY: walks tasks/ text, never mutates task state.
    """
```

Implementation notes for the helper:
- Walk `tasks/<status>/<N>/` via the task-workflow API, not a hand-built path.
  Iterate `STATUSES` minus `_CONSUMER_INACTIVE_STATUSES`; for each active status,
  `list_by_status(status)` gives the ids cheaply, then read each task's
  `body.md` + `plans/plan.md` (the symlink → highest `v{N}.md`) as TEXT. (Reading
  the plan symlink target is enough — historical `v{N}.md` rounds need not be
  scanned; the live plan is the symlink.) A missing plan.md / body.md is skipped
  fail-soft.
- For each active task `c`, regex-scan the concatenated `body + plan` text for
  `_DATA_ISSUE_REF`; for every captured `M != c` and `M != self_issue_n`, append
  `c` to `protected[M]`.
- Dedup consumer ids per M. Return `{}` when no active task references any
  `data/issue_<M>/`.
- Compute this ONCE per `clean_issue_downloads` call (before the per-cache-dir
  loop), never per cache dir.

Use `from explore_persona_space.task_workflow import STATUSES, list_by_status,
find_task_path` (already importing `repo_root` from there). Resolve each task
dir via `find_task_path(id)` (or build from `tasks_dir()/status/str(id)` — the
`list_by_status` row already carries the status, so `tasks_dir()/status/str(id)`
is a direct, registry-free path and avoids a per-task `find_task_path` registry
read). Implementer's choice; `tasks_dir()/status/str(id)` is the leaner read.

### 3b. The new gate function

```python
def _cache_dir_reap_blocked_by_active_consumer(
    cache_dir: Path,
    *,
    issue_n: int,
    apply: bool,
    protected: dict[int, list[int]],
) -> str | None:
    """SKIP reason if issue_n is consumed as a planned input by an ACTIVE task;
    None to allow the reap. Composes with _cache_dir_reap_blocked (parity).

    On a hit, sidecar-logs kind="active-consumer-reap-skipped" naming the
    protected issue + the consumer task ids, mirroring the nested-store guard's
    escalation pattern (append_disk_guard_event, fail-soft)."""
    consumers = protected.get(issue_n)
    if not consumers:
        return None
    rel = _rel_name(cache_dir)
    consumer_str = ", ".join(f"#{c}" for c in consumers)
    reason = (
        f"active task(s) {consumer_str} declare data/issue_{issue_n}/ as a "
        f"planned input — reaping {rel} could strand their run; KEPT"
    )
    append_disk_guard_event(
        {
            "kind": "active-consumer-reap-skipped",
            "task": issue_n,
            "path": rel,
            "consumers": consumers,
            "reason": reason,
        },
        apply=apply,
    )
    return reason
```

### 3c. Wire into `clean_issue_downloads`

```python
def clean_issue_downloads(issue_n, *, apply=False, data_root=None,
                          _skip_active_consumer_guard=False):
    res = CleanResult(issue_n=issue_n, apply=apply)
    hf_sizes_cache = {}
    protected = (
        {} if _skip_active_consumer_guard
        else _active_consumer_protected_issues(self_issue_n=issue_n)
    )
    for cache_dir in download_cache_dirs(issue_n, data_root):
        rel = _rel_name(cache_dir)
        res.sizes_bytes[rel] = _dir_size_bytes(cache_dir)
        # Gate 1 (new): cross-issue active consumer — cheap set lookup, first.
        consumer_reason = _cache_dir_reap_blocked_by_active_consumer(
            cache_dir, issue_n=issue_n, apply=apply, protected=protected)
        if consumer_reason is not None:
            print(f"  ~ SKIP {rel}: {consumer_reason}", file=sys.stderr)
            res.skipped.append((rel, consumer_reason))
            continue
        # Gate 2 (existing): nested-store parity (may make one HF call).
        skip_reason = _cache_dir_reap_blocked(cache_dir, issue_n=issue_n,
                                              apply=apply, hf_sizes_cache=hf_sizes_cache)
        ...  # unchanged
```

`_skip_active_consumer_guard` is a private kwarg (default `False`) — NOT a
public API addition (leading underscore, keyword-only, defaulted). It exists so
the incremental wrapper can opt out cleanly (see §4) and so a test can force the
guard off. The protected-set helper already excludes `self_issue_n`, so even
WITHOUT the flag a task never protects its own reap; the flag is the explicit
belt-and-suspenders for the incremental path + a test seam.

### 3d. Sidecar telemetry

New event `kind: "active-consumer-reap-skipped"` on the SAME shared stream
(`.claude/cache/disk-guard-events.jsonl`) the other two guards write to, via the
existing `append_disk_guard_event` (fail-soft, `ts`-stamped, `apply=False`
reports only). Fields: `task` (the protected issue M), `path` (rel cache dir),
`consumers` (list of active consumer ids), `reason`.

## 4. Controls / safety properties

- **Step-8 own-task cleanup still works.** `/issue` Step 8 calls
  `clean_issue_downloads(<self>)` after `<self>`'s pod terminated, when `<self>`
  is at a terminal-for-reap status. The new guard only fires when ANOTHER active
  task references `data/issue_<self>/`. Because `_active_consumer_protected_issues`
  excludes `self_issue_n`, `<self>`'s own plan/body referencing its own
  `data/issue_<self>/` never blocks its reap. (Edge case it still correctly
  handles: if some OTHER active task legitimately depends on `<self>`'s caches,
  the reap is skipped + escalated — which is the desired #742 protection, even
  at Step 8.)
- **Incremental within-run path must NOT self-block.** `clean_issue_downloads_incremental`
  is called by the EXPERIMENT itself mid-run to reap its own consumed phase
  caches. The experiment is at an ACTIVE status and its own plan references
  `data/issue_<self>/`, so the guard could try to protect it — but two layers
  prevent that: (1) the helper excludes `self_issue_n` from the protected set,
  and (2) the incremental wrapper passes `_skip_active_consumer_guard=True` to
  make the intent explicit + skip the `tasks/` walk entirely (a small perf win
  on the within-run hot path). Document this in the wrapper docstring.
- **Active-task enumeration is READ-ONLY.** No `set_status`/`set_body`/any
  mutation — only `list_by_status` + text reads of `body.md` + `plans/plan.md`.
- **Existing guards unchanged.** Nested-store parity guard
  (`_cache_dir_reap_blocked`) and active-cache escalation
  (`escalate_active_cache`) are untouched; the new gate runs strictly BEFORE the
  parity guard in the loop and composes additively (both can independently put a
  dir in `.skipped`).
- **`vm_disk_guard.py` tier-(b) caller unchanged.** It calls
  `clean_issue_downloads(issue_n, ...)` exactly as today; the protection is
  internal to the library (per the task constraint).

## 6. Risks

- **False positive (over-protection):** an active task's plan mentions
  `data/issue_<M>/` in a non-input context (a documentation example, a "do NOT
  use" note, a risks-table row that happens to name the path). The reap is then
  wrongly skipped → disk pressure rises. **Mitigation/accept:** this is
  fail-toward-keep (the body's safety contract). The cost is at most disk space,
  surfaced by the existing tier-(b) active-cache escalation (Telegram + sidecar),
  never a data-loss event. Over-protection self-heals the moment the consumer
  reaches a terminal/parked status. Accept.
- **False negative (under-protection):** an active task reads
  `data/issue_<M>/...` via a path assembled in code / a Hydra YAML / an env-var
  override, with no literal `data/issue_<M>/` substring in plan.md or body.md.
  The regex misses it. **Mitigation:** the active task's OWN cache reap is
  already protected by the existing owning-issue gate; this residual is a
  cross-issue config-indirection gap. Document as a known limitation in the
  function docstring + §8. (In practice the project's reuse-provenance convention
  puts input paths in the plan's Reproducibility / reuse-check sections as
  literals — #742's plan is the worked example — so the literal-substring signal
  catches the realistic case.)
- **Performance:** `tasks/` has ~715 dirs today; one walk per
  `clean_issue_downloads` call reads ~N×(body.md + plan.md) text files. Measured:
  the dir walk alone is ~24ms; reading two small text files per active task adds
  a sub-second cost. `vm_disk_guard` runs every 10 min and Step-8 once per task,
  so this is negligible. Compute the set ONCE per call (already specified); cache
  NOTHING across calls (the active set is dynamic — a task can change status
  between calls). The incremental within-run path skips the walk entirely.
- **`vm_disk_guard` tier-(b) loops over many terminal issues:** each
  `clean_issue_downloads` call would recompute the protected set, an O(N²)
  pattern across a panic clean of K terminal issues. **Mitigation (implementer
  may apply, optional):** the protected set is the same for every issue in one
  tier-(b) pass; if profiling shows it matters, expose the helper so
  `clean_terminal_download_caches` could compute it once and the per-issue calls
  reuse it. BUT the constraint forbids changing `vm_disk_guard.py`'s caller, and
  N≈700 × two small file reads is still well under a second per pass — so the
  DEFAULT is to recompute per call and NOT touch `vm_disk_guard.py`. Only
  optimize if a real measurement shows a problem; do not pre-optimize against the
  constraint.

## 9. Plan deviations allowed vs must-ask

**Allowed (implementer's call):**
- Parser implementation: the `_DATA_ISSUE_REF` regex shape (`\bdata/issue_?(\d+)(?=[/_])`
  vs an equivalent), and whether to scan `body+plan` concatenated or separately.
- Whether to combine the new gate into the existing `_cache_dir_reap_blocked` or
  keep it as a separate `_cache_dir_reap_blocked_by_active_consumer` function
  (plan recommends SEPARATE — the parity guard makes HF calls, the consumer check
  is a set lookup; keeping them separate makes the "consumer check first,
  short-circuit before HF" ordering obvious).
- Sidecar event field names beyond the required `kind`/`task`/`path`/`consumers`/`reason`.
- New test file vs appending to `test_clean_experiment_downloads_parity.py`.
- Resolving each task dir via `tasks_dir()/status/str(id)` (leaner) vs
  `find_task_path(id)`.
- Whether `_skip_active_consumer_guard` is a private kwarg as specified or an
  equivalent internal mechanism — as long as the incremental path does not
  self-block and a test can exercise both code paths.

**Must-ask (escalate):**
- Any change to the PUBLIC signature of `clean_issue_downloads` — current
  `(issue_n, *, apply=False, data_root=None)` stays; the only addition is a
  leading-underscore, keyword-only, defaulted private kwarg, which is not a
  public-contract change. A genuinely public new parameter would be must-ask.
- Any edit to `vm_disk_guard.py`'s tier-(b) caller (forbidden by the task
  constraint — the fix lives in the library).
- A CLAUDE.md edit beyond a no-op: the new behavior does not change any published
  marker schema, status enum, or task.py subcommand, so CLAUDE.md need NOT be
  touched. If the implementer believes a one-line note belongs in the "Disk
  hygiene" section documenting the third guard, that is a small in-scope doc add
  (allowed, not must-ask) — but it must not claim a contract that isn't enforced.
