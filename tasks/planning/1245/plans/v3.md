## 3. Design decisions (the 6 questions, answered)

### Q1 — Shape (a): whole-block background, for all three forms

**Forms (i)/(ii):** the shared block writes NOTHING outside /tmp (its own comment, L9030: "$WT and the repo root are never written"), and its only cross-invocation output is already a FILE. Backgrounding the whole block is a pure invocation-mode change. Splitting legs would force `BASE_RC`/`GATED_RC`/`GT` state into files — new contract surface — for no benefit.

**Form (iii):** also whole-sequence background, NOT leg-split, for three reasons:
1. **State:** `GATE_ARMED`, `BASE_RC`, `GATE_VERDICT`, `TG_*` are same-invocation shell variables by design (comment L9869–9871). One background shell preserves that; splitting moves them all into files.
2. **Contaminated-root window:** the window (checkout → stage/commit-or-clean) is compute-bound at ~5–6 min today (one gated no-flags leg + parity + verdict). Backgrounding the SAME sequence in ONE shell leaves the window unchanged. Splitting (baseline bg call → foreground checkout → gated bg call → foreground land) would INSERT two orchestrator turn-boundaries (notification latency, potentially minutes) INSIDE the window — strictly worse.
3. **Today's foreground form is structurally biased to die contaminated:** the 600 s SIGKILL lands ~10 min into a ~9–12 min sequence, i.e. AFTER the checkout (baseline legs alone take ~4.5–6 min) and BEFORE the clean/commit — stranding staged payload in the shared root with no in-band cleanup. Backgrounding removes the cap kill entirely; the per-leg bounds kill only on genuine wedge, and the new completion-read prescribes cleanup for exactly that case.

### Q3 — Death detection

- **Forms (i)/(ii): the verdict file IS the rc-file analogue.** It is written in every arm (crash/block/pass/skip), so its ABSENCE after background completion means the run died before classifying — and the binding sites already fail CLOSED on a missing file. Additions: (a) `rm -f /tmp/issue-<N>-lint-verdict.txt` at block top (after the choom preamble) so a file present at completion provably came from THIS run — the #1041 same-tip retry path is untouched because it re-enters the merge CONDITIONAL, never the gate block; (b) a partial death (killed between the verdict `echo` and the sha append) leaves a 1-line file that the binding sites' line-2 sha check already fails closed. Kill-before-relaunch probe: `pgrep -af 'issue-<N>-lint-gate-tree'` — exact-issue-scoped because `$GT` (`/tmp/issue-<N>-lint-gate-tree`) expands into the lint legs' argv.
- **Form (iii): one NEW outcome sentinel** `/tmp/issue-<N>-surgical-outcome.txt` (pre-rm'd at block top; written as the LAST action of each terminal arm: `landed` after a successful push, `push-failed` after a rejected/timed-out push, `blocked-cleaned` after the two-step cleanup). Missing at completion ⇒ died mid-sequence ⇒ the completion-read runs, IN THIS ORDER (Methodology + Statistics critic round-1 findings): (1) **kill-before-relaunch probe FIRST** (`pgrep -af 'scripts/workflow_lint.py'`, wait-don't-kill on ambiguous matches — root-copy invocations are not issue-scoped in argv; the Step 0 single-orchestrator guard excludes same-issue concurrency; probe-before-clean is strictly safer than clean-before-probe); (2) **landed/committed classification BEFORE any cleanup** — a shell killed between `git commit`/`git push` success and the sentinel write leaves the payload COMMITTED (tracked + clean), which the naive contamination probe would misread: check whether the surgical commit is on HEAD (`git -C "$REPO_ROOT" log -1 --format=%s` matches the surgical commit subject) and whether the additive paths are tracked+clean (`git status --porcelain` empty for them); if committed AND pushed (`merge-base --is-ancestor HEAD origin/main` after a fetch) → treat as `landed` (post `epm:merged`), if committed but NOT pushed → push-only retry (the existing sync-retry bullet), NEVER `rm -f` committed files; (3) only if genuinely uncommitted-contaminated (staged/working-tree payload present, no surgical commit) → the existing hook-verified two-step clean, then re-entry (the block is documented idempotent for the gate re-run case, L9388–9389).
