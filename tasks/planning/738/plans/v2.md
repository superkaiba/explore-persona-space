## 1. Goal + acceptance criteria

**Goal:** Close the scope gap in the existing post-hoc-irreconstructibility rule.
The rule's RATIONALE ("loss curves … cannot be reconstructed post-hoc") already
covers the failure mode, but its SCOPE is only HF-Trainer/TRL config builders
under `src/explore_persona_space/experiments/`. Hand-rolled torch optimization
loops (predictor MLPs, linear-probe SGD, per-cell analysis fits) hit the
identical failure mode and fall outside it. Motivating incident: #658's
`_fit_mlp_loco` in `scripts/issue658_fit_predictors.py` runs a fixed
300-epoch (`MLP_MAX_EPOCHS`) LOCO loop per fold that records nothing per-epoch
(only the final held-out prediction is returned), so "did the MLP over- or
under-train at 300 epochs?" cannot be diagnosed post-hoc and the alternative
explanation for the A3.2 failure ("mis-training artifact, not genuine mean-pool
insufficiency") cannot be ruled out from stored artifacts.

**Acceptance criteria (re-stated in §5):**
1. `.claude/rules/code-style.md` carries ONE new bullet, inserted immediately
   after the existing "WandB live training metrics are mandatory" bullet
   (current line 26) and before the "Persona injection" bullet (current line 27).
2. The new bullet names the two acceptable patterns: (a) early-stop on an
   inner-validation metric, OR (b) emit a per-epoch train + held-out metric
   curve to a durable artifact (alongside the fit's output).
3. The new bullet carries the SAME structure as its sibling: the
   "cannot be reconstructed post-hoc" rationale + a specific waiver/escape +
   a cross-reference to the motivating incident (#658 `_fit_mlp_loco`).
4. The new bullet cross-references `.claude/rules/vectorize-many-cell-fits.md`
   to keep its scope distinct (diagnosability, NOT throughput/GPU routing —
   that orthogonal axis is already covered there for the same `_fit_mlp_loco`).
4b. **(v2 carve-out — protected element)** The new bullet carries an EXPLICIT
   carve-out for the three legitimate edge cases enumerated in §6: a
   trivially-short fit (`<30 s` wall, when over/under-training is not a live

### 3.2 Optional secondary — `scripts/workflow_lint.py` — DELIBERATE CALL: NOT ADDED

**Decision: no lint check.** False-positive analysis (grep-grounded against the
actual repo):

- A lint keying on `def fit*` / `def _fit*` would have to discriminate
  gradient-descent loops from the ~40+ closed-form fits in the repo (OLS,
  ridge, mixedlm, PCHIP/spline, sklearn `LogisticRegression`, statsmodels) —
  none of which run an epoch loop or call `.backward()`. Keying on the function
  name alone is hopeless (the names are identical: `fit_405`, `_fit_ols`,
  `_fit_mlp_loco` all coexist).
- Narrowing to `.backward()` shrinks the surface to 3 in-scope `*.py` files
  (`scripts/issue658_fit_predictors.py`,
  `src/explore_persona_space/experiments/behavior_testbed_545/predictors.py`,
  `src/explore_persona_space/eval/marker_logprob.py`). But:
  - `marker_logprob.py` uses gradients for attribution, not a fixed-epoch fit
    loop → a true negative the lint must not flag → needs context the regex
    cannot see.
  - `issue658_fit_predictors.py` ALREADY carries a vectorized `batched_forward`
    + a `for _ in range(MLP_MAX_EPOCHS)` loop AND a
    `_fit_mlp_loco_serial_reference` oracle copy — a regex keying on
    `for … range(…): … backward()` would flag BOTH the live path and the
    reference copy, and would mis-classify a loop that DOES log to a sibling
    helper as a violation.
  - The "lacks `logger.` / `wandb.log` / per-epoch artifact write" negative
    condition (suggested in the task body) requires whole-function dataflow
    analysis to avoid flagging loops that log via a helper call or a closure —
    exactly the brittle AST-walk that produces context-dependent false
    positives. The existing `--check-wandb-required` works precisely BECAUSE
    it keys on a single unambiguous literal (`report_to=` disabling value) in a
    narrow directory, not on a structural loop shape.
- The class is also LOW-frequency (a handful of hand-rolled GD loops across the
  whole repo, almost all in one-off `scripts/issue*` analysis files), so the
  recurrence-justification bar for mechanizing (per `workflow-fix-on-bug.md`
  § "A critic finding whose check belongs in a mechanical verifier … Emit only
  when the check is concrete and likely to recur") is not cleanly met either.

**Conclusion:** a reliable check is not feasible at an acceptable false-positive
rate, and the body explicitly permits rule-only. The bullet is the enforcement
surface — a reviewer-facing, human-applied discipline, exactly like the file's
other un-linted bullets (tensor-shape asserts, vectorize torch ops,
docstring-on-edit, checkpoint-per-phase). No `workflow_lint.py` edit; no new
`tests/test_workflow_lint.py` test.
