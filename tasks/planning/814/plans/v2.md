# Plan — issue #814 (kind: infra, workflow-fix)

## 0.0 TL;DR (plain English)

- **What I'll run:** No experiment — this is a one-line fix to a lint script. The
  project's workflow-lint tool has a rule that flags "slash commands" (like
  `/issue`) written in the docs that don't point at a real skill. Right now that
  rule is mis-firing on ordinary prose: a doc line that starts `` `false`/unset ``
  gets read as if `/unset` were a slash command, and the whole lint fails.
- **What I expect:** Tightening one regex so it ignores a backtick that directly
  follows a letter (which is what the closing backtick of `` `false` `` is) makes
  the false alarm go away while every real `/command` reference still gets checked.
- **What would change my mind:** If tightening the regex silently stopped catching
  a genuinely dead slash-command reference somewhere in the docs — that's why the
  fix ships with tests for both the false alarm AND the real references, and a
  full re-run of the lint's existing test suite.

## 11. Decision Rationale

`kind: infra` — no model training, so no hyperparameters. The one non-obvious
engineering choice is the regex-tightening approach:

- **What:** Prepend a fixed-width negative lookbehind `(?<!\w)` to `SKILL_REF_RE`,
  rather than the body's diff-sketch option of switching to start-of-line /
  whitespace anchors (`` r"(?:(?<=\s)|(?<=^))/([a-z][a-z0-9-]+)" ``).
- **Why (tied to Goal):** The Goal is to suppress the FP without weakening real-ref
  detection. The negative-lookbehind is the minimal edit that keeps the ENTIRE
  existing pattern intact — the leading backtick anchor, the group, and the
  trailing closing-delimiter lookahead all stay — and adds exactly one constraint:
  "the backtick that opens the codespan is not itself the closing backtick of a
  preceding `` `word` `` codespan" (which is precisely the FP mechanism, since a
  closing backtick is always immediately preceded by a word char). This targets
  the root cause and nothing else.
- **Why NOT the body's diff sketch:** The candidate diff sketch
  (`SKILL_REF_RE = re.compile(r"/([a-z][a-z0-9-]+)")` → whitespace/BOL anchors)
  **drops the backtick delimiter requirement entirely** — it would be a
  REGRESSION. The current (and correct) design REQUIRES the leading `` ` ``
  backtick anchor + the trailing `` `\s)`` closing-delimiter lookahead as the
  primary FP controls (a bare `/word` in prose, or a `/workspace/logs` path, must
  NOT match). A whitespace/BOL-anchored bare-`/word` regex would newly match every
  in-prose `/word` token and every `/path/segment` that happens to sit after a
  space — reintroducing exactly the FP class the backtick anchor was built to
  reject (`workflow_lint.py:295-302`). The negative-lookbehind adds a constraint;
  the diff sketch removes two.
- **Source:** #713/#714 (the design intent of the backtick + trailing-lookahead
  FP controls); the fix mechanism is verified in-session against the live surface
  (§3 pre-verified probes), not inherited from a prior issue.
- **Alternatives considered & rejected:**
  1. *Body diff-sketch (BOL/whitespace anchors, no backtick):* rejected —
     regression, per above.
  2. *Add `unset` to `SKILL_REF_ALLOWLIST`:* rejected — it papers over ONE token
     while leaving the codespan-closing-backtick FP class open for any future
     `` `word`/othertoken `` prose (`/end`, `/0`, arbitrary), and pollutes the
     allowlist (which is documented as "legitimate slash-commands", not prose
     tokens).
  3. *Append `<!-- lint: historical-ref -->` to line 171:* rejected — it's a
     one-line escape hatch for a one-off narrative citation, not the systematic
     fix; the FP is a detector bug, not a legitimately-dead reference.
  4. *Explicitly match `` `word`/word `` as prose and skip it:* rejected — more
     complex, and the negative-lookbehind subsumes it with a single token.
