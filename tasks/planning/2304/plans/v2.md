**1a. Shared helper (scope item 2 — ONE helper, no duplicated branch):**

```python
def _filecount_overflow_retry(
    err: Exception,
    *,
    canonical_repo: str,
    repo_type: str,
    path_in_repo: str,
    retry_against_overflow: Callable[[], str],
) -> str | None:
    """Reactive file-count overflow fallback (#1108, widened by #2304).

    Returns None when the fallback does not apply (caller proceeds with its
    legacy failure handling); otherwise the overflow retry's result
    ("" on a failed retry, the verified overflow URL on success).
    """
    # SPLIT GATE (v2, alternatives-critic blocker 1). Conjunct order is
    # load-bearing: the kill switch + message match come FIRST (so a
    # kill-switched run has zero new effects, incl. zero sentinel writes —
    # acceptance bullet 5), then the observation is recorded for ANY
    # file-count refusal we can see, then the ROUTING conjuncts decide
    # whether to reroute. Recording BEFORE the repo-identity conjunct is
    # what makes the overflow repo's OWN refusal visible (the
    # both-repos-at-cap wall); a single fused gate returns None on the
    # recursion path before the recorder ever runs, silently losing the
    # only durable record of the second wall.
    if not (_filecount_fallback_enabled() and _is_file_count_limit_error(err)):
        return None
    _record_filecount_observation(canonical_repo, repo_type, err)  # fail-soft, §4 Phase 2
    if not (
        repo_type in ("model", "dataset")
        and canonical_repo != DEFAULT_OVERFLOW_REPO
    ):
        return None  # observed + recorded, but not a reroutable refusal
    logger.warning(
        "File-count limit rejection on %s (%s) — falling back to overflow repo %s",
        canonical_repo, err, DEFAULT_OVERFLOW_REPO,
    )
    result = retry_against_overflow()
    if result:
        _emit_overflow_routing_event(
            original_repo=canonical_repo,
            effective_repo=DEFAULT_OVERFLOW_REPO,
            path_in_repo=path_in_repo,
            reason="file-count-limit-reactive",
        )
        _write_overflow_pointer(
            canonical_repo=canonical_repo,
            path_in_repo=path_in_repo,
            overflow_repo=DEFAULT_OVERFLOW_REPO,
            repo_type=repo_type,
        )
    return result
```

`repo_type` and `private` threading: `repo_type` is a helper parameter used for the gate + the pointer write; `private` does NOT enter the helper — it is baked into each caller's `retry_against_overflow` closure as `private=True` (the overflow repo must never be CREATED public; both closures below pass it explicitly). Recursion bound: each closure passes `repo_id=DEFAULT_OVERFLOW_REPO`; if the overflow push is itself refused on file count, the helper's `canonical_repo != DEFAULT_OVERFLOW_REPO` conjunct returns None → legacy failure path. Depth ≤ 2 by construction — the same bound as today, now enforced in exactly one place.

**Both-repos-at-cap trace (v2, the blocker's motivating path).** Canonical dataset push refused → observation row for the data repo → reroute attempted → overflow push ALSO refused on file count → the recursive helper call records an observation row with `repo_id == DEFAULT_OVERFLOW_REPO`, then fails the repo-identity conjunct and returns None → the recursive `_upload` / `_upload_folder_filtered` takes its legacy failure path (`""`, or re-raise under `raise_on_error=True`) → the OUTER helper's `if result:` is false, so no routing event and no pointer are written (correct — nothing landed) → the outer caller takes ITS legacy failure path. `upload_raw_completions_to_data_repo` then raises (`hub.py:2226`), so the second wall fails LOUD at the caller while the sentinel + preflight WARN carry the durable "overflow repo is also at the cap" record. Pinned by `test_both_repos_at_cap_records_overflow_observation` (§5).

### Phase 2 — Observed-count sentinel + preflight WARN (scope item 4)

**Two options weighed (hard requirement):**

- **(A) Reactive observed-count sentinel — CHOSEN.** On every detected file-count refusal, parse the exact counts from the server's message (`would contain ([\d,]+) files after this push, over the limit of ([\d,]+) files`) and append a JSONL row to a local sentinel; preflight reads the last row per repo and WARNs. Zero network, exact count, keyed on the authoritative signal (the server's own refusal), never on a launch-blocking path.
- **(B) A count probe — REJECTED.** No cheap count field exists: `repo_info` returns `usedStorage` bytes, not counts (clarifier-verified); the only count source is the full paginated tree walk — ~1M entries ≈ ~1,000 sequential pages, measured >90 s / 120 s-timeout on this repo (#833, body item 4), and ~1,000 requests against the 2,500-req/5-min org quota. Even off the launch path (a cron), it is quota-hostile and stale within hours on a repo growing by thousands of files per run.
- **Reason A wins:** after Phase 1 a refusal is non-fatal (reroute), so early-warning's remaining job is fleet VISIBILITY, which A provides at zero cost. B's only added value — pre-refusal approaching-cap detection — cannot be had cheaply, and the body forbids the slow probe on any launch-blocking path. Honest limitation, stated: A detects AT-cap (first refusal) rather than approaching-cap, and the sentinel is machine-local (a pod's observation is seen by that pod's preflight; cross-machine visibility rides the existing routing-event → `epm:` marker drain).
