# Plan — issue #741: GCP max-run-duration default 24h → 7d, max-run-duration-aware janitor age backstop

**Estimated GPU-hours (total): 0**

---

## 0. Plan Summary

**Change:** Raise the GCP lane's self-imposed VM auto-delete fence from `24h` to `7d`
(`GcpConfig.default_max_run_duration`), so a long multi-cell sweep on the GCP-first auto
lane (which leads with FLEX_START for long jobs, 7d ceiling) is NOT stranded mid-run at 24h
(#697 lost 24/64 cells to the 24h fence). Reconcile the **coupled** stale-VM janitor age
backstop so it does NOT become the new 24h cap: make `gcp_audit.py`'s age backstop
**aware of each instance's own configured fence** (read `scheduling.maxRunDuration.seconds`
from the instance JSON the audit already lists) and reap a VM only when it has exceeded its
OWN fence + a 1h grace — **Option B**.

**Why Option B (max-run-duration-aware), not Option A (blanket 8d age):** Option A's flat
~8d age window is a much weaker credit-leak backstop — a wedged-never-terminal VM bills for
~8 days before reaping. Option B keeps the credit-leak guarantee intact: a 24h job still
reaps at ~25h, a 7d job at ~7d+1h, and a truly-wedged VM reaps at its own fence-exceed —
NOT at a fixed multi-day wall-clock. The `scheduling.maxRunDuration.seconds` field is set
natively by GCP when `--max-run-duration` is passed and is already returned by the audit's
`gcloud compute instances list --format=json` (no new GCE label, so **not architectural**).

**Preserved invariants:** the FLEX_START `>7d` assertion STAYS (it guards a real 7d GCP
ceiling; 7d default sits exactly at it and passes). The 10-min terminal-phase reap is
UNCHANGED — it still promptly catches crashed/done-to-terminal zombies. A VM with NO
readable `maxRunDuration` (legacy instance, probe gap) falls back to the existing fixed
`--max-age-hours` fence (raised to `192.0` = 8d, covering the new 7d default + grace), so
the backstop never silently disarms.

**Compute:** 0 GPU-h. Config-default + audit-logic change on the workflow surface.

**Risks (top 2):** (1) `scheduling.maxRunDuration` absent on a legacy/edge instance → the
fixed-age fallback (192h) covers it, but is the weaker Option-A window for THAT instance
only. (2) A workload that legitimately exceeds 7d cannot run on the GCP FLEX_START lane at
all (7d is the GCP ceiling) — out of scope; such a job pins `backend: runpod` (already the
documented residual gap).

Add a pure helper to read the per-instance fence from the listed instance dict:
```python
def _instance_max_run_seconds(inst: dict[str, Any]) -> int | None:
    """Return the instance's configured ``--max-run-duration`` in seconds, or None.

    Reads ``scheduling.maxRunDuration.seconds`` from the instance JSON that
    ``gcloud compute instances list --format=json`` returns — GCP populates
    this natively whenever the create passed ``--max-run-duration`` (verified
    against the v1 REST instance schema; the field is
    ``scheduling.maxRunDuration: {seconds, nanos}``). Returns None when the
    block is absent (a legacy instance created without the flag, or a probe
    gap) so the caller falls back to the fixed ``max_age_seconds`` fence —
    the backstop never silently disarms on a missing field.
    """
    sched = inst.get("scheduling")
    if not isinstance(sched, dict):
        return None
    mrd = sched.get("maxRunDuration")
    if not isinstance(mrd, dict):
        return None
    raw = mrd.get("seconds")
    # gcloud emits seconds as an int or a numeric string; accept both, reject junk.
    try:
        return int(raw)
    except (TypeError, ValueError):
        return None
```

```python
def _janitor_stale_reason(
    *,
    cfg: GcpConfig,
    run: GcloudRunner,
    name: str,
    zone: str,
    status: str,
    age_seconds: float | None,
    max_age_seconds: int,
    terminal_phase_max_age_seconds: int,
    instance_max_run_seconds: int | None,   # NEW (#741): per-instance fence, None if unreadable
) -> tuple[str | None, str | None]:
    """Decide whether a janitor instance is stale, and why → ``(phase, reason)``.

    Age backstop (Option B, #741): an instance is age-stale when EITHER it has a
    readable ``--max-run-duration`` fence and has exceeded that fence + a 1h grace
    (``_JANITOR_FENCE_GRACE_SECONDS``), OR it has NO readable fence and has lived
    past the fixed ``max_age_seconds`` fallback (the legacy fence, raised to 8d to
    cover the 7d default + grace). This makes the age backstop track each
    instance's OWN fence — a 24h job still reaps at ~25h, a 7d job at ~7d+1h, a
    truly-wedged-never-terminal VM at its-fence + grace — instead of a single
    fixed wall-clock that would re-create the #697 bug (a 7d job killed at the
    janitor's fixed 24h). The terminal-phase probe path is unchanged: a RUNNING
    VM that published a terminal eps/phase past the floor is still reaped promptly.
    """
    phase: str | None = None
    if age_seconds is not None:
        if instance_max_run_seconds is not None:
            age_fence = instance_max_run_seconds + _JANITOR_FENCE_GRACE_SECONDS
        else:
            age_fence = max_age_seconds
        if age_seconds >= age_fence:
            return None, "age"
    should_probe_phase = (
        status.upper() == "RUNNING"
        and age_seconds is not None
        and age_seconds >= terminal_phase_max_age_seconds
    )
    if not should_probe_phase:
        return None, None
    try:
        phase = _read_guest_phase(config=cfg, name=name, zone=zone, runner=run)
    except GcpProbeError as exc:
        logger.warning(...)   # unchanged
        return None, None
    reason = "terminal-phase" if phase in _TERMINAL_GUEST_PHASES else None
    return phase, reason
```

## 9. Decision Rationale (§11)

**Choice: Option B — max-run-duration-aware janitor age backstop.**

- **New default `7d`** — *What:* `default_max_run_duration = "7d"`. *Why:* the GCP-first auto
  lane leads with FLEX_START for long/unknown-length jobs, whose GCP ceiling is exactly 7d;
  defaulting to that ceiling means the auto lane never strands a long sweep on a self-imposed
  fence (#697 lost 24/64 cells to the 24h default). 7d is ≤ every provisioning model's
  ceiling (FLEX_START 7d code-asserted; SPOT/STANDARD 120d GCP hard max), so it is safe across
  the whole ladder. *Source:* FLEX_START 7d ceiling is the existing assertion
  `_FLEX_START_MAX_RUN_SECONDS = 7*24*3600` (gcp.py:522, 591-603); the 120d SPOT/STANDARD max
  and the all-models applicability are GCP docs (cloud.google.com/compute/docs/instances/
  limit-vm-runtime, verified 2026-06-29 — min 30s, max 120d, applies to Spot/Standard/
  On-Demand). *Alternatives:* leaving 24h (rejected — IS the #697 bug); 120d (rejected —
  exceeds the FLEX_START ceiling the auto lane uses, would raise at render on every long
  flex create).

- **Option B over Option A** — *What:* the janitor age backstop reaps on `age >= instance's
  own maxRunDuration + 1h grace`, with a fixed-192h fallback only when the fence is
  unreadable. *Why:* Option A (flat 8d age) reaps a wedged VM only after ~8d of idle billing
  — a materially weaker credit-leak backstop than today's 24h. Option B preserves the
  credit-leak guarantee per-instance (24h job → ~25h reap, 7d job → ~7d+1h reap, wedged VM →
  its-fence+grace), and the read source (`scheduling.maxRunDuration.seconds`) is set natively
  by GCP and already returned by the audit's existing `instances list --format=json`, so it
  needs NO new GCE label (keeping the change non-architectural) and no extra gcloud call. The
  body explicitly biases toward B when the read is straightforward — it is (one nested dict
  lookup). *Source:* `scheduling.maxRunDuration: {seconds, nanos}` is the v1 REST instance
  schema (cloud.google.com/compute/docs/reference/rest/v1/instances; GCP populates it
  whenever `--max-run-duration` is passed — verified 2026-06-29); the audit already lists with
  `--format=json` (gcp.py `render_list_argv`, line 1664). *Alternatives:* Option A blanket 8d
  (rejected — weaker backstop, the body's stated risk); a NEW `eps-max-run-duration` GCE label
  (rejected — adds a label name that would arguably flip the change to `architectural: true`,
  and the native `scheduling` field already carries the value, so the label is redundant).

- **Grace constant `_JANITOR_FENCE_GRACE_SECONDS = 3600` (1h)** — *What:* the post-fence
  margin before age-reaping. *Why:* a small window so a VM mid-finalize (the GCP DELETE fence
  + teardown takes seconds-to-minutes) is not racing the janitor, while still reaping a
  genuinely-wedged VM within an hour of its fence. *Source:* mirrors the existing short-floor
  precedent `terminal_phase_max_age_seconds = 600` (10 min) for the prompt terminal-phase
  reap — the same "small post-event finalize window, not a multi-day wall" design. 1h (not
  10 min) because the DELETE-fence enforcement window is coarser than a guest-attribute phase
  write. *Alternatives:* 10 min (rejected — too tight against GCP's own fence-enforcement
  latency); 24h grace (rejected — re-introduces a ~1-day blanket window per instance,
  defeating the point of Option B).

- **Fixed-fence fallback `--max-age-hours = 192.0` (8d)** — *What:* the age fence used only
  when `scheduling.maxRunDuration` is unreadable. *Why:* it must cover the new 7d default +
  margin (a legacy 7d VM with an unreadable fence must NOT reap at 24h, re-creating #697 for
  the no-fence case); 8d = 7d + 24h is the minimal safe value. *Source:* derived from the new
  7d default + a 24h margin. *Alternatives:* keep 24.0 (rejected — would mis-reap a legacy 7d
  VM at 24h); ∞ / remove the fallback (rejected — violates the finite-backstop constraint;
  the no-fence case would never reap).

**No model training / no hyperparameters** — `kind: infra`.
