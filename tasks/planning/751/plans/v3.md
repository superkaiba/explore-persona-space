## 0. Plan Summary

A GCP→RunPod (and RunPod-wedge) failover relaunches a fresh pod by re-pointing the
poll sidecar at the new RunPod handle, but never registers that pod in
`scripts/pods.conf` — so SSH/MCP can't reach it, the raw-SSH poller reads
`status=dead` (false alarm), and the documented recovery commands
(`pod.py config --update` / `--refresh-from-api`) BOTH error with
"pod '<X>' not found in pods.conf". Three coordinated fixes:

- **Change B (keystone):** `pod_config.cmd_refresh_from_api` CREATES a missing
  `pods.conf` row from the live RunPod API when the named pod resolves on the API
  but is absent from `pods.conf` (instead of `sys.exit(1)`). This single change
  makes BOTH the human recovery path AND the *already-existing* poll_pipeline
  self-heal (`_try_refresh_pods_conf_from_api`, which fires `--refresh-from-api
  <pod>` after 10 consecutive SSH failures) succeed.
- **Change A:** the two failover paths in `scripts/backend_poll.py`
  (`_failover_dead_gcp_to_runpod`, `_relaunch_fresh_runpod`) fire a best-effort
  create-missing registration for the new pod name after the authoritative sidecar
  re-point, so the row appears as soon as the live API exposes a port (the port is
  not up yet at relaunch instant, so registration is eventual, not synchronous).
- **Change C (safety net):** the poller cross-checks the live RunPod API
  (`get_pod_by_name`) before declaring `status=dead` on an SSH-resolution failure
  whose pod is absent from `pods.conf` — a name-resolution miss for a pod that the
  API reports RUNNING is reclassified `running` (still-provisioning), not `dead`.

## 1. Goal

A failover/relaunched pod is always registered in `pods.conf` (eventually, once the
live RunPod API exposes its SSH port), and the documented recovery commands
(`pod.py config --update` / `--refresh-from-api`) WORK when the pod is absent from
`pods.conf` but present on the live API — instead of erroring "not found in
pods.conf". The poller does not false-declare such a still-registering pod dead.

## 3. Hypothesis / acceptance criteria

The three "Proposed change" bullets are the acceptance contract. As acceptance tests:

- **AC1 (create-missing recovery).** Given a pod present on the live RunPod API
  (RUNNING, with `ssh_host`/`ssh_port`) but ABSENT from `pods.conf`,
  `pod.py config --refresh-from-api pod-697` exits 0 and ADDS a `pods.conf` row with
  the live host/port (+ gpus/gpu_type/label), then `cmd_sync` regenerates SSH/MCP.
  Symmetrically `pod.py config --update pod-697 --host H --port P` creates the row
  when absent (manual values), instead of `sys.exit(1)`. PROVEN by the new tests in
  `tests/test_pod_config_refresh_from_api.py` + `tests/test_pod_config.py` asserting
  the row is appended (vs the old `pytest.raises(SystemExit)`), and by a manual
  `--check`-style assertion that the row exists.
- **AC2 (failover registers).** After `_failover_dead_gcp_to_runpod` /
  `_relaunch_fresh_runpod` re-point the sidecar, they fire a best-effort
  create-missing registration for `handle.pod_name`/the new pod name; once the live
  API exposes a port, the pod lands in `pods.conf`. PROVEN by the new
  `tests/test_backend_poll.py` test asserting the failover path invokes the
  registration helper (monkeypatched) with the new pod name, AND that a failure of
  that helper does NOT change the emitted `status="running"` JSON (best-effort, never
  blocks). Eventual landing is exercised by the create-missing test (AC1) since the
  failover registration delegates to the same create-missing code path.
- **AC3 (no false dead).** When `_ssh_probe` fails to resolve a pod absent from
  `pods.conf` but `get_pod_by_name(pod)` reports RUNNING, the poll status is
  `running` (still registering), not `dead`. PROVEN by a new
  `tests/test_poll_pipeline_*` test monkeypatching `get_pod_by_name` to return a
  RUNNING `PodInfo` and asserting the `dead` verdict is suppressed; and that a
  genuinely-gone pod (`get_pod_by_name` → `None`) still routes `dead`.

### Change B — create-missing in `pod_config.py` (the keystone; do this first)

**New helper** `pod_config._pod_row_from_live(name: str, live: PodInfo, issue: int |

def _short_gpu(gpu_type_id: str | None) -> str:
    for short in ("H100", "H200", "A100"):
        if short and gpu_type_id and short in gpu_type_id:
            return short
    return gpu_type_id or "unknown"

def _pod_row_from_live(name: str, live: PodInfo) -> Pod:
    return Pod(
        name=name,
        host=live.ssh_host,           # caller guarantees not None
        port=int(live.ssh_port),      # caller guarantees not None
        gpus=live.gpu_count or 0,
        gpu_type=_short_gpu(live.gpu_type_id),

### Change A — failover paths register the new pod (`scripts/backend_poll.py`)

**Shared best-effort helper** (new, in `backend_poll.py`) so neither failover path
can miss the registration and a future failover-like path inherits it:
```python
def _register_failover_pod_best_effort(pod_name: str) -> None:
    """Best-effort: register a freshly-failed-over RunPod pod into pods.conf via the
    create-missing refresh path (#751). NEVER raises — the poller's terminal-JSON
    contract must hold. The pod is usually still PROVISIONING here (no SSH port yet),
    so this typically no-ops; the poll_pipeline self-heal (_try_refresh_pods_conf_from_api,
    now create-missing) lands the row once the API exposes a port."""
    try:
        from pod_config import cmd_refresh_from_api, parse_pods_conf
        cmd_refresh_from_api(parse_pods_conf(), pod_name)
    except SystemExit:
        # cmd_refresh_from_api exits(1) when the pod is not-yet-RUNNING / no port
        # yet — expected at relaunch instant; the self-heal retries later.
        pass
    except Exception as exc:  # fail-soft: registration must never block the poller
        logging.warning("backend_poll: best-effort pods.conf registration of %s "
                        "failed (%s); the poll_pipeline self-heal will retry", pod_name, exc)
```
Call it AFTER the authoritative sidecar re-point + readback succeeds, immediately
before the `return {... "status": "running" ...}`:
- in `_failover_dead_gcp_to_runpod`, after line 1690 (`_clear_failover_sentinel`),
  before line 1695: `_register_failover_pod_best_effort(route_result.handle.pod_name)`.
- in `_relaunch_fresh_runpod`, after line 1033 (`_stamp_runpod_wedge_failover`),
  before line 1034: `_register_failover_pod_best_effort(route_result.handle.pod_name)`.

Use `route_result.handle.pod_name` (the NEW pod), not the dead `handle.pod_name`.
Catching `SystemExit` is required because `cmd_refresh_from_api` uses `sys.exit(1)`
on not-yet-RUNNING; the helper converts that to a no-op. This makes the
registration EVENTUAL-on-first-poll-after-port-up via the existing self-heal, with
an eager attempt at relaunch (which usually no-ops but lands immediately when RunPod
exposes the port unusually fast).

### Change C — poller cross-checks the live API before declaring dead

In `scripts/poll_pipeline.py`, the `elif not pid_alive: status = "dead"` decision
(line 2497-2498). Add a guard: when `pid_alive` is False AND the pod is absent from
`pods.conf` (an SSH name-resolution failure, not a probed-dead PID — distinguishable
via the `pid_file_missing` / SSH-failure fail-safe path documented at lines
807-813), cross-check the live API:
```python
elif not pid_alive:
    if _pod_absent_from_pods_conf(pod) and _live_pod_running(pod):
        # SSH could not resolve a pod that the API reports RUNNING — it is still
        # registering after a failover relaunch (#751), not dead. The self-heal
        # (--refresh-from-api, now create-missing) will land it in pods.conf.
        log.info("pod %s absent from pods.conf but RUNNING on the live API — "
                 "treating as still-registering (running), not dead (#751)", pod)
        status = "running"
    else:
        status = "dead"
```
Helpers (new, fail-soft):
```python
def _pod_absent_from_pods_conf(pod: str) -> bool:
    try:
        from pod_config import parse_pods_conf
        return not any(p.name == pod for p in parse_pods_conf())
    except Exception:
        return False           # unknown → do NOT suppress dead (fail toward existing behavior)

def _live_pod_running(pod: str) -> bool:
    try:
        from runpod_api import get_pod_by_name
        info = get_pod_by_name(pod)
        return info is not None and (info.desired_status or "").upper() == "RUNNING"
    except Exception:
        return False           # API unreachable → do NOT suppress dead
```
**Scope guard:** this suppression fires ONLY when the pod is absent from pods.conf
(the failover-registration window). A pod that IS in pods.conf and probes dead keeps
the existing `dead` verdict unchanged — so a genuinely-crashed registered run is not
masked. A bounded suppression is acceptable (the self-heal lands the row within ~10
poll ticks); to avoid an infinite "running" loop if registration never lands, cap
the suppression with the existing consecutive-tick state (reuse the SSH-fail counter
machinery or add a `consecutive_absent_running` counter; after a small cap, e.g. 2×
`SSH_FAIL_REFRESH_THRESHOLD`, fall through to `dead` so a never-registering pod is
not hidden forever). State the cap in the implementer hand-off.

## 5. Controls / edge cases handled

N/A — code change, no experimental controls. Edge cases the design handles:
- **Race against concurrent pods.conf writes:** all create-missing mutation runs
  inside `locked_pods_conf()` with a re-parse under the lock (the #488 discipline);
  the create branch re-checks `create_name not in fresh_by_name` after re-parse so a
  concurrent provisioner that already added the row wins (no duplicate).
- **Pod absent from RunPod API entirely:** `cmd_refresh_from_api` still fails loud
  ("not in pods.conf AND not on the live API") — genuine typo / terminated pod is
  NOT silently created. `_register_failover_pod_best_effort` swallows that SystemExit
  (expected pre-port). `_live_pod_running` returns False → poller keeps `dead`.
- **Partial pods.conf entries:** create only fires when the row is fully absent; an
  existing (even stale) row takes the refresh-in-place path unchanged.
- **`manual_override` interaction:** create-via-`--update` sets override=True;
  create-via-`--refresh-from-api` does not (a fresh API-sourced row). An existing
  override row is never created over (it exists → refresh path → existing WARN).
- **Not-yet-RUNNING / no port:** create-missing refuses with a clear error (single
  mode) and the best-effort failover helper treats it as a no-op retry.
