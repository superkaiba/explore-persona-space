# Plan v2 — #1757: act on consistency edit-locus WARN vs live sibling (merge sequencing)

## 0.0 TL;DR (plain English)

When the consistency-checker warns at plan time that this task edits the same
file region as a live sibling task, that warning currently gets folded into
plan prose and forgotten — and the predicted conflict then fires at merge time
(#1718 vs #1716, 2026-07-27: WARN at 11:47Z, `gh pr merge --squash` CONFLICTING
at ~14:28Z, a hand conflict-resolution round on the fleet's hottest file). Fix:
two small prose edits to `.claude/skills/issue/SKILL.md` — (A) Step 2b records
the WARN as a machine-scannable `merge-hold-candidate` events note naming the
sibling; (B) Step 10d gains a bounded "Guard 5" that, before merging, checks
whether the named sibling has landed (`epm:merged`) and, if it is still live at
`reviewing`-or-later, waits up to ONE gate cycle (45 min) before proceeding
anyway. A stuck sibling can never wedge the task; the existing merge-conflict
machinery remains the correctness backstop.

## 1. Goal

An edit-locus WARN naming a live sibling should change merge sequencing, not
just be folded into plan prose (task #1757 Goal, verbatim). Concretely: the
/issue orchestrator gains a durable record of the WARN at plan time and a
bounded consumer of that record at merge time.

## 3. Hypothesis / requirement

If the WARN is recorded machine-scannably at plan time and consumed at merge
time with a bounded hold, the same-file conflict-resolution round is avoided
whenever the sibling lands within one gate cycle — at a worst-case latency
cost of 45 min on exactly the tasks the checker flagged (never fleet-wide).

## 4. Design

### 4.1 Edit A — Step 2b recording duty

Anchor: the Step 2b paragraph ending "On WARN, append warnings to the
`epm:plan` event note. On PASS, proceed normally." Append a short paragraph:

> **Edit-locus WARN → merge-hold record (#1757).** When the WARN body names a
> same-file EDIT-LOCUS conflict with a live sibling task at status `reviewing`
> or later, ALSO post one `epm:progress` note per named sibling (idempotent
> per (sibling, path) — grep the events file first, the `followup-parked-by-cap`
> convention; reuse `epm:progress`, never a new marker kind):
>
>     uv run python scripts/task.py post-marker <N> epm:progress \
>       --note "merge-hold-candidate sibling=<M> path=<file> source=consistency-warn — Step 10d Guard 5 holds this task's merge (bounded, one 45-min gate cycle) until sibling #<M> posts epm:merged (#1757)"
>
> Auto-continue — never a gate, never blocks planning; a WARN naming no live
> sibling (or a sibling below `reviewing`) records nothing.

### 4.2 Edit B — Step 10d Guard 5 (bounded sibling merge-sequencing hold)

Anchor: end of the "Merge safety guards" numbered list (immediately after
Guard 4's fenced block, before the "Fast-path routing pre-check" H4). Add:

> 5. **Sibling merge-sequencing hold (#1757).** Runs ONCE at Step 10d entry
>    (before Guard 0; never inside per-attempt retry shapes). Scan this task's
>    events for `merge-hold-candidate` notes
>    (`grep -F 'merge-hold-candidate' "$(uv run python scripts/task.py find <N>)/events.jsonl"`).
>    For each named sibling `<M>` (dedup): read live state via
>    `task.py view <M> --json` — if its events carry `epm:merged` (any form —
>    `artifact_confirmed` counts) OR its status is in
>    {completed, archived, blocked, on_hold}, no hold (a parked/blocked
>    sibling is not landing soon; proceed and let the normal machinery absorb
>    any residual conflict). Otherwise HOLD bounded: post ONE
>    `[long-phase-heartbeat] step10d-merge hold sibling=<M> (#1757)` progress
>    note, then re-check on a bounded loop, re-resolving the sibling's folder
>    each poll (status moves relocate it), cap 2700 s (one 45-min gate cycle):
>
>        until grep -qF '"epm:merged"' "$(uv run python scripts/task.py find <M> 2>/dev/null)/events.jsonl" 2>/dev/null \
>              || [ $SECONDS -gt 2700 ]; do sleep 60; done
>
>    On sibling-merged OR cap expiry: `git -C "$WT" fetch origin main --quiet`
>    and proceed to Guards 0-4 + the merge (the Step 5a re-sync, the lint
>    gate's landing-union overlay, and the merge-conflict recovery absorb the
>    landed sibling's content). Record the disposition in the `epm:merged` /
>    `epm:merge-failed` note: `merge_hold: sibling=<M> waited=<mins>
>    outcome=<sibling-merged|cap-expired>` (omit the line when no candidate
>    note exists). Bounded by construction: a mutual hold (two siblings each
>    naming the other) resolves at cap expiry on both sides; a stuck sibling
>    never wedges this task. Same behavior in interactive and autonomous
>    sessions; auto-continue, never a gate.

## 11. Decision Rationale

- **Record-then-consume over plan-prose-only:** #1718 proved plan prose is
  write-only; an events-note with a fixed leading token is the established
  machine-scannable channel (`stage-dispatch`, `deliberate-stop`,
  `followup-parked-by-cap` precedents). Source: #1718 events; SKILL.md note
  conventions.
- **Hold at Step 10d entry (not at plan time):** hours pass between plan and
  merge; live re-check avoids acting on stale ordering advice. Source: #1718
  timeline (WARN 11:47Z → merge 14:28Z; sibling had already landed).
- **45-min cap = one `/issue-tick` cycle:** matches the tick cadence the
  merge window is already covered by (#1723); bounded per the filing.
- **TDD: no** — prose-only change; the scanner/lint suites are the tests.
