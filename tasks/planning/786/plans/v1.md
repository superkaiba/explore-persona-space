## 2. Prior-work check for item (c) — ALREADY LANDED, NO-OP

`_append_jsonl_line` (task_workflow.py:1460) is **already atomic** and its
docstring (lines 1461–1483) is explicit about the exact contract item (c)
asks for:

- Buffers `≤ PIPE_BUF` (4096 on the EPS VM, `_PIPE_BUF` at line 1455): a single
  `os.write` on an `O_APPEND` fd is all-or-nothing against a SIGKILL/OOM
  mid-call — the kernel commits the one syscall or nothing (POSIX write(2),
  Linux pipe(7)). A short-write is asserted to raise (lines 1494–1496), so a
  truncation can never pass silently.
- Oversize buffers (`> PIPE_BUF`, rare): the caller's `_locked()` flock
  excludes concurrent writers; a completion loop finishes the buffer; the
  docstring is honest that this path is **not** crash-atomic and the recovery
  is the tolerant reader `_iter_jsonl` (which skips a partial trailing line).
- `post_event` (line 1582) and `create_task` (line 1816) both call it while
  holding `_locked()` across payload construction + append + `_git_commit`.

The `post-marker` CLI path (`cmd_post_event` → `post_event` → `_append_jsonl_line`)
is therefore already covered. The temp+rename alternative the Goal offers would
be **strictly worse** for an append-only log: rename is atomic for whole-file
replacement, not for appending one line to an existing multi-line file (you
would have to copy the whole file to a temp, append, and rename — O(file) per
marker, and it fights the concurrent-appender flock contract).

**Decision: item (c) requires no code change AND no new test.** The workflow-fix
protocol explicitly allows a reasoned no-change report per item. The atomicity
guarantee is ALREADY pinned by `tests/test_task_workflow.py`:
`test_small_append_is_exactly_one_os_write` (line 3107 — asserts exactly ONE
`os.write` of the full line on the ≤PIPE_BUF path) and
`test_small_append_short_write_raises` (line 3138 — asserts `OSError` on a short
write), plus `test_oversize_append_*` (3156/3177) for the >PIPE_BUF branch.
Nothing to add for (c) — production code and regression tests are both in place.

## 3. Design — items (a), (b), (d)

### Item (a) — atomic status-transition move that never drops untracked files

**Root cause (#722):** `set_status` (line 1652) runs `_run_git(["mv", rel_old,
rel_new])` FIRST. `git mv <src-dir> <dst-dir>` renames only git-**tracked**
files; untracked/uncommitted files in the source stay behind. Then REGISTRY is
updated (line 1725) and the commit happens LAST (line 1746). So when body.md /
plans/* have uncommitted content (a plan version written whose commit failed; a
subagent artifact written before the transition's commit), `git mv` splits the
task, REGISTRY is pointed at the new (incomplete) dir, and nothing rolled back.

Note `create_task` commits the whole task dir at creation, so a freshly created
task is fully tracked — the split requires files added/modified AFTER creation
without an intervening commit. That is exactly the #722 shape.

**Chosen mechanism: plain `shutil.move` of the whole dir + `git add --all -- <old> <new>`, with a pre-move file-list capture and a post-move completeness verification that rolls back before REGISTRY.**

Rationale for `shutil.move` over `git mv`:
- `git mv` moves only tracked files — the whole bug. `shutil.move` of the
  directory moves EVERY file (tracked, untracked, modified) in one filesystem
  rename, so nothing is left behind by construction.
- Git records the rename via content-similarity at commit time regardless of
  whether the filesystem move used `git mv` or `mv`; staging with
  `git add --all -- <old> <new>` inside the flock captures the source-side
  deletion AND the destination-side addition (preserving the both-sides-of-move
  invariant that `test_set_status_commits_both_sides_of_move` pins).
- Rejected: **pre-`git mv` `git add -A -- <src>`** — sweeps unrelated pending
  edits in the source into the transition commit and does not help if a file is
  modified-but-unstaged at the moment of mv. Rejected: **two-phase
  `git mv` + move-back-the-untracked** — more moving parts, two failure
  windows.

**New sequence inside the existing `with _locked():` block** (replacing
lines 1718–1721, keeping the collision guard at 1692–1717 unchanged):

```
# 1. Capture the source file list BEFORE the move (relative to old dir),
#    recursively, so we can verify completeness after.
src_files = {p.relative_to(old) for p in old.rglob("*") if p.is_file()}

# 2. Whole-directory filesystem move (moves tracked + untracked + modified).
try:
    shutil.move(str(old), str(new))
except Exception:
    raise  # nothing moved yet OR a partial FS move; see rollback note below

# 3. Verify EVERY source file landed in the destination. If any missing,
#    roll the FS move back BEFORE touching REGISTRY, and raise.
dst_files = {p.relative_to(new) for p in new.rglob("*") if p.is_file()}
missing = src_files - dst_files
if missing:
    # Roll back: move new -> old so the task is left in its ORIGINAL,
    # consistent location. REGISTRY was never touched.
    _rollback_move(new, old)   # helper: shutil.move(new, old) best-effort
    raise RuntimeError(
        f"task #{task_id}: status move {old_status} -> {new_status} left "
        f"{len(missing)} file(s) behind: {sorted(str(m) for m in missing)[:5]}; "
        f"filesystem move rolled back, REGISTRY untouched. Retry after "
        f"resolving disk/permission issue."
    )

# 4. Stage BOTH sides so git records the rename + source deletion.
_run_git(["add", "--all", "--", str(rel_old), str(rel_new)])

# 5..N: REGISTRY update + event append + commit (UNCHANGED, lines 1722-1746)
```

- REGISTRY update (`_registry_set`/`_save_registry`) stays AFTER the verified
  FS move — so a failure in steps 2–3 can never leave REGISTRY pointing at an
  incomplete dir (the #722 half-applied state). Atomicity across the whole
  transition is already provided by the single `_locked()` flock + single
  `_git_commit` at the end; this change makes the FS move itself
  all-or-consistent.
- `shutil.move` across the same filesystem (both under `tasks/`) is a single
  `os.rename` of the directory — atomic at the OS level for the common case; a
  cross-device fallback would copy-then-delete, which is why the post-move
  completeness verification (step 3) is the real guard, not the move primitive.
- Keep `_git_commit([old, new, registry_path()], ...)` at the end unchanged —
  it tolerates the now-absent `old` (staged deletion) exactly as today.
- New tiny helper `_rollback_move(src, dst)`: `shutil.move` best-effort with a
  logged warning if the rollback itself fails (never swallow — log + re-raise
  the ORIGINAL error so the operator sees the true fault; a failed rollback is
  a louder problem than the original).

**Cross-check against existing guards:** the #681 destination-collision guard
(lines 1692–1717) runs BEFORE this and guarantees `new` does not exist (or is an
empty orphan that gets `rmdir`'d), so `shutil.move(old, new)` performs a true
rename into a non-existent destination — never a nest.

### Item (b) — typed stale-path error from `_read_body` / `get_task`

**New exception class** (near the top of task_workflow.py, after imports /
before the first helper that references it — place it just above `_read_body` at
line 627 or in the module's exception region):

```python
class StaleTaskPathError(FileNotFoundError):
    """Raised when a task's body.md is missing at a path the registry / caller
    expects. Subclasses FileNotFoundError so existing `except FileNotFoundError`
    callers keep working; adds a message naming the stale path + the remedy."""
```

**MUST subclass `FileNotFoundError`** — the load-bearing callers that catch
`FileNotFoundError` around a call transitively invoking `_read_body`:
- `scripts/task.py` `cmd_migrate_body` lines 997, 1015 (`except FileNotFoundError`
  around `migrate_one`, which reads the body via `_read_body` — DIRECT dependency).
- `scripts/task.py` `cmd_list_clean_results` line 593 wraps a RAW
  `body_path.read_text()` (line 592) that `continue`s BEFORE `_read_body` at line
  598 ever runs — so this site does not observe `StaleTaskPathError` in practice.
  The subclass keeps it correct either way (harmless); flagged for accuracy.
- `src/explore_persona_space/task_workflow_migrate.py` and other transitive
  `except FileNotFoundError` sites — the subclass preserves every catch.

Note: `StaleTaskPathError("message")` has `errno=None`/`filename=None`, unlike a
real `open()` `FileNotFoundError` (`errno=2`). Grep confirms no
`.errno`/`.filename`/`ENOENT` introspection on caught `FileNotFoundError` in
`task_workflow.py` or `scripts/task.py`, so this divergence is safe today. Noted
for future callers.

(This is the answer to the must-ask in §10: **yes, subclass FileNotFoundError**.)

**`_read_body` change** (line 627–628):

```python
def _read_body(path: Path) -> tuple[dict[str, Any], str]:
    try:
        text = path.read_text()
    except FileNotFoundError as e:
        # Distinguish "task dir exists but body.md missing" (the #722 split /
        # stale-registry shape) from a raw missing path; both name the remedy.
        raise StaleTaskPathError(
            f"body.md not found at {path}. The task dir may be split or the "
            f"registry stale; run `task.py audit` to detect + `task.py audit "
            f"--repair --apply` to repair."
        ) from e
    return _split_frontmatter(text)
```

- `get_task` (line 1426) needs **no change** — it calls `_read_body(path /
  "body.md")` and the typed error propagates. (Stated in the plan so the
  implementer does not add a redundant wrapper.)
- **Consistency with `find_task_path`:** `find_task_path` (line 1405) already
  raises a plain `FileNotFoundError` naming the path + `run task.py audit to
  repair` (line 1419–1422) for the "registry path missing dir" case. That
  message wording is the model; the new `StaleTaskPathError` message mirrors it
  ("run `task.py audit`"). Do NOT change `find_task_path` — its case (whole dir
  missing) is distinct from `_read_body`'s case (dir present, body.md missing,
  the #722 split). Leaving `find_task_path` untyped is fine; optionally the
  implementer MAY also make `find_task_path`'s two raises use
  `StaleTaskPathError` for uniformity, but that is out of the minimal scope —
  flag as an allowed, not-required tidy.

### Item (d) — SIGPIPE-safe stdout for read-only `cmd_*`

**New helper** in `scripts/task.py` (generalize the existing `_safe_echo`
BrokenPipeError guard at line 92 into a reusable print wrapper; keep `_safe_echo`
as-is for the post-commit mutation echoes since its stderr wording is
mutation-specific):

```python
def _safe_print(*args, context: str = "task.py", **kwargs) -> None:
    """print() that swallows BrokenPipeError (downstream `| head` / `| grep -q`
    closed the pipe early). Prints a one-line suppression notice to stderr and
    redirects stdout to devnull so the interpreter-shutdown flush can't re-raise
    and flip the exit code. Read-only commands: a torn pipe is not a failure.

    Includes ``sys.stdout.flush()`` INSIDE the ``try`` mirroring ``_safe_echo``:
    a buffered-pipe BrokenPipeError often only surfaces at flush/close, not at
    the ``print`` call, so the flush is what makes the guard actually catch it."""
    try:
        print(*args, **kwargs)
        sys.stdout.flush()
    except BrokenPipeError:
        print(f"{context}: stdout closed early (BrokenPipeError) — suppressed.",
              file=sys.stderr)
        try:
            devnull_fd = os.open(os.devnull, os.O_WRONLY)
            try:
                os.dup2(devnull_fd, sys.stdout.fileno())
            finally:
                os.close(devnull_fd)
        except Exception:
            pass
```

`| head`/`| grep -q .` can tear down early). Enumerated call sites to convert:
