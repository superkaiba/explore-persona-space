<div class="verdict">
<span class="lbl">gap-real? → YES, REAL and structural.</span> A spawn-issue <code>--auto</code>
session opens at the repo <em>root</em> cwd (not its <code>issue-&lt;N&gt;</code> worktree). When its task
reaches a terminal status, the respawn pass — which runs <em>before</em> the reconcile pass in
<code>main()</code> and hands it the same live-id snapshot — deletes the session's
<code>issue-&lt;N&gt;.json</code> registration on the first tick it observes the park. After that the
session is mapped by NEITHER path <code>_map_sessions_to_issues</code> uses (registry entry gone;
repo-root cwd doesn't match the <code>issue-&lt;N&gt;</code> worktree regex), so the reconcile pass never
sees it and never auto-stops it. The zombie-wrapper pass can't catch it either (it requires a DEAD
inner Claude; these have a live-but-idle inner Claude). Tasks 698/705/706 hit exactly this class.
The fix mirrors the pattern already proven for the gate-push pass: snapshot the sid→issue map
<em>before</em> the respawn pass and hand it to the reconcile pass.

<h1>Plan — issue #795: auto-reap Happy sessions orphaned on completed tasks</h1>

<section class="plan-tldr">
<h2 style="border:none;margin-top:0;">TL;DR (plain English)</h2>
<ul>
<li><span class="lbl">What I'll do:</span> When a task finishes, the system is supposed to
automatically close the leftover chat session that was working on it. Right now it fails to find
those sessions once they finish, because the bookkeeping entry that links a session to its task
gets deleted a moment too early — by a different cleanup step that runs first. I'll take a snapshot
of those links just before they're deleted and hand it to the auto-close step so it can still find
and close the session.</li>
<li><span class="lbl">What I expect:</span> Finished-task sessions get auto-closed within about
two of the 10-minute checks instead of piling up until someone notices the session count is high.
No behavior change for any session whose task is still active.</li>
<li><span class="lbl">What would change my mind:</span> If a real, still-working session (say, a
follow-up round that just launched) gets closed by mistake — that would mean my snapshot is too
aggressive and I'd need to tighten the idle / follow-up guards, which already exist.</li>
</ul>
</section>

<section class="plan-summary">
<h2 style="border:none;margin-top:0;">Plan Summary (technical)</h2>
<ul>
<li><span class="lbl">Change:</span> In <code>autonomous_session_watch.py::main()</code>, snapshot
<code>_load_session_issue_map()</code> (sid→issue) into a local <code>pre_respawn_issue_map</code>
BEFORE the respawn pass runs (mirroring the existing <code>issue_gate_candidates</code> pre-respawn
snapshot on line 13901). Thread it into <code>session_reconcile_pass(...)</code> as a new
<code>registry_snapshot=</code> kwarg, which unions it with the fresh <code>_load_session_issue_map()</code>
before calling <code>_map_sessions_to_issues</code>. This restores the sid→issue mapping the respawn
pass just deleted, so a repo-root-cwd spawn-issue session on a terminal task becomes reconcilable.</li>
<li><span class="lbl">Scope:</span> One workflow-surface file (<code>scripts/autonomous_session_watch.py</code>)
+ its test file. No new pass, no refactor. Surgical.</li>
<li><span class="lbl">Guards preserved:</span> The existing DONE-status gate, idle grace (2h,
<code>EPM_SESSION_RECONCILE_IDLE_S</code>), ≥2-miss guard, follow-up-active skip, RUNNING-pod skip,
and keep-running skip all still apply unchanged — the fix only widens the SET of sessions the pass
can SEE, not the conditions under which it acts.</li>
<li><span class="lbl">No new env vars.</span> No threshold changes.</li>
<li><span class="lbl">Success:</span> new/modified unit tests pass; a live <code>--dry-run</code> smoke
shows the pass now enumerates a terminal-task repo-root session it previously skipped.</li>
<li><span class="lbl">Risk:</span> a stale pre-respawn entry could resurrect a session-issue mapping
for a session that was legitimately re-spawned onto the same issue; mitigated because the fresh map
WINS on any conflict and the union only ADDS sids the fresh map lacks.</li>
</ul>

<h2>Goal</h2>
<p>Verbatim from body.md: <em>"Verify/tighten the reconcile-pass auto-stop predicate for sessions on
completed tasks (idle→2h + no-pod + no-keep-running) so it actually fires, or add a completed-task
fast-path so zombie sessions do not accumulate until a human notices."</em></p>
<p><span class="lbl">Precision reword:</span> The predicate itself is correct — the failure is upstream
of the predicate, in session→issue <em>mapping</em>. A spawn-issue session on a terminal task becomes
UNMAPPED before the reconcile pass runs, so the predicate is never evaluated for it. Goal → restore
the mapping so the (already-correct) predicate fires.</p>

<h2>Investigation — what I verified</h2>
<h3>The reconcile predicate itself is sound</h3>
<p><code>decide_session_reconcile</code> (line 9808) is well-formed: DONE-status gate →
idle → keep-running-skip → followup-skip → pod-skip → ≥2-miss guard → stop. Traced every branch;
the DONE set <code>SESSION_RECONCILE_DONE = AUTO_STOP_DONE = {"completed", "awaiting_promotion",
"archived"}</code> (line 575, 9682). Idle uses <code>_latest_nonwatcher_event_ts</code> (any
non-watcher marker) + self-report, 2h grace. Autostop is ON by default. 30+ tests pin it
(<code>tests/test_autonomous_session_watch.py</code> lines 4848–5488). None of the predicate theories
in the task brief fire for a plain completed task: a completed task's status doesn't change (no
self-report refresh via the gate-push reconcile arm, which SKIPS <code>TERMINAL_FOR_GC</code> at line
13604); no follow-up markers landed after completion for 698/705/706.</p>

<h3>The actual root cause — session mapping, not the predicate</h3>
<p><code>_map_sessions_to_issues</code> (line 9891) maps a live sid to an issue via ONE of two paths:
(a) a registry entry (<code>_load_session_issue_map()</code>), or (b) an <code>issue-&lt;N&gt;</code>
worktree cwd (<code>_infer_issue_from_path</code>, regex <code>/\.claude/worktrees/issue-(\d+)/?$</code>).
A session with NEITHER is skipped entirely (pinned by <code>test_map_sessions_registry_beats_cwd_and_unmapped_skipped</code>,
line 5083). Two facts kill both paths for a finished spawn-issue session:</p>
<ul>
<li><span class="lbl">Registry gone:</span> The respawn pass (<code>_process_entry</code>) deletes
<code>issue-&lt;N&gt;.json</code> "on the first daemon-up tick observing the park" — stated verbatim
in the code (lines 13895–13900, 13582–13583) and confirmed live: <code>~/.eps-autonomous/issue-698.json</code>
et al. are absent.</li>
<li><span class="lbl">cwd is repo-root, not the worktree:</span> spawn-issue sessions "open at repo
root" (code comment, line 13899). I confirmed the LIVE session metadata: of 429 entries in
<code>~/.happy/sessions.json</code>, 251 have <code>metadata.path = .../explore-persona-space</code>
(plain repo root) — these do NOT match the worktree regex, so <code>_infer_issue_from_path</code>
returns <code>None</code>. The current 41 unmapped (<code>-</code>) running EPS sessions in
<code>spawn_session.py list</code> are exactly this class.</li>
</ul>
<p><span class="lbl">Ordering seals it:</span> in <code>main()</code>, <code>session_reconcile_pass</code>
(line 14014) runs AFTER the respawn pass (line 13907) and reuses the same <code>live_ids</code>
snapshot — so by the time reconcile runs, the registration is already deleted and the cwd fallback
can't recover it. The session is invisible.</p>

<h3>Why the other two session reapers don't catch it</h3>
<ul>
<li><span class="lbl">zombie-wrapper pass:</span> requires a DEAD inner Claude
(<code>_CLAUDE_CMDLINE_MARKERS</code> absent from the /proc tree). These sessions have a live-but-idle
inner Claude, so it clears them.</li>
<li><span class="lbl">idle-unmapped pass:</span> targets UNMAPPED sessions but only after a much
longer 12h idle window (<code>EPM_UNMAPPED_IDLE_REAP_S</code>) and excludes wrappers holding a
controlling TTY. It is the eventual backstop but is far slower than the 2h reconcile pass and is not
issue-aware (posts no per-task marker). So a finished-task session survives 2h→12h in limbo — the
exact "accumulate until a human notices" symptom.</li>
</ul>

<h3>Tasks 698/705/706 evidence</h3>
<p>All three are <code>completed</code> (git: <code>0bf0a75f5a task #698: reviewing → completed</code>).
Their repo-root folders now hold only a stray <code>artifacts/</code> dir (state committed on their
<code>issue-&lt;N&gt;</code> worktree branches; the <code>→ completed</code> transition landed on
<code>main</code> via <code>task.py</code>). They are absent from <code>REGISTRY.json</code> and their
<code>issue-&lt;N&gt;.json</code> registrations are gone. This matches the root cause exactly: the
sessions were spawn-issue <code>--auto</code> at repo-root cwd, lost their registration at terminal,
and became unmappable — so the reconcile pass skipped them and Thomas reaped them manually.</p>

<h2>Design — the fix</h2>
<h3>Method delta</h3>
<p>Snapshot the sid→issue map BEFORE the respawn pass deletes registrations, and union it into the
reconcile pass's mapping. This is the direct sibling of the <code>issue_gate_candidates</code>
pre-respawn snapshot already in <code>main()</code> (line 13901) for the gate-push pass, which exists
for the IDENTICAL reason.</p>

<h3>Why this is safe (no false auto-stops)</h3>
<ul>
<li>The union only ADDS sids the fresh map lacks; on any sid present in both, the fresh map wins
(<code>{**snapshot, **fresh}</code>). A session re-spawned onto the same issue keeps its live mapping.</li>
<li>Mapping a session to its issue does NOT stop it — the full predicate still runs:
DONE-status + idle(2h) + no-follow-up + no-pod + no-keep-running + ≥2-miss. A snapshot sid whose task
is NOT terminal, or whose session is fresh/active, is <code>clear</code>ed exactly as today.</li>
<li>The pre-respawn snapshot is a strict superset-in-time of the fresh map for terminal tasks and a
subset for active ones (active tasks keep their registration), so no active session is newly exposed
to a stop it wasn't already eligible for via the live registry.</li>
<li>The idle grace + 2-miss guard mean a JUST-completed session (registration reaped this same tick)
gets its 2h grace + ≥2 checks before any stop — a follow-up that launches in that window trips the
follow-up-skip.</li>
</ul>

<h2>Kill criteria</h2>
<ul>
<li>If the union causes ANY existing test to require a semantic change (i.e. it would newly stop a

instead tighten the idle-unmapped pass to be issue-aware / faster for terminal tasks.</li>
<li>If a live dry-run shows the merged map resurrecting a mapping for a session whose task is ACTIVE

first tick (contradicting the code comment) → the mapping isn't the gap; re-open the predicate

<h2>§11 Decision Rationale (infra thresholds)</h2>
<ul>
<li><span class="lbl">Reuse the existing 2h idle default (<code>EPM_SESSION_RECONCILE_IDLE_S</code>,
<code>SESSION_IDLE_S = 2*3600</code>):</span> the fix does NOT introduce a completed-task fast-path
with a shorter window. Reason tied to Goal: the predicate is already correct; the gap is mapping, not
timing. Keeping the same 2h grace means finished-task sessions get the identical safety window they
were designed for — a follow-up that launches within 2h of park still trips the follow-up-skip.
Introducing a shorter fast-path window would be a second, un-asked-for variable and risks stopping a
just-parked session before an inline follow-up posts its <code>epm:run-launched</code>.
<em>Source:</em> reconcile-pass design (module docstring lines 100–128) + the follow-up-skip guard.</li>
<li><span class="lbl">Reuse the ≥2-consecutive-miss guard (threshold=2):</span> unchanged. Reason:
the miss guard protects against a transient <code>task.py</code>/self-report read glitch; that risk is
unchanged by the mapping fix. A fast-path that bypassed the guard (the way the tick-runaway parachute
does, backed by 3 corroborating teardown ticks) is not warranted here — we have no independent
corroboration signal, so the 2-miss accumulation is the right conservatism.
<em>Source:</em> <code>decide_session_reconcile</code> threshold semantics + the tick-runaway
force-stop precedent (which explicitly documents WHY it may skip the 2-miss guard: 3 teardown ticks
already corroborate).</li>
<li><span class="lbl">No new env-var thresholds.</span> The fix widens the visible session SET, not any
timing/threshold, so no new tunable is introduced. Validation: the 2 new unit tests + the live dry-run
smoke confirm the widened mapping without any threshold change.</li>
</ul>
