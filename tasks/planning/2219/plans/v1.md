# Plan v1 — #2219: verify_task_body: assert concern-deferred body comments have a matching deferred ledger event

**Kind:** infra (workflow-fix; `workflow_fix_target: scripts/verify_task_body.py`)

## 1. Requirement + acceptance criteria

Close the fabricated-deferral gap in `verify_task_body.py` Lens 14
(`check_concerns_audit`, scripts/verify_task_body.py:13868): a body can carry
`<!-- concern-deferred: <id> -->` while the task's `concerns.jsonl` holds no
`deferred` event for that id (the `task.py defer-concern` record —
`task_workflow.defer_concern`, src/explore_persona_space/task_workflow.py:8411
writes `"event": "deferred"`). Today the stale-marker scan treats latest-event
`raised` / `verified-open` / `deferred` all as "live marker, no WARN", and ack
mechanism 3 accepts the comment as acknowledgment — so a fabricated deferral
ships silently (incident: #2215's `phase-d-no-entry-skip-sentinel`, raised-only
ledger + deferral comment).

Acceptance criteria (verbatim from the task body):
1. `verify_task_body.py` flags a `concern-deferred` comment with no matching
   `deferred` ledger event (new check id documented in the file's check
   registry).
2. Fails-pre-fix regression test: fixture body + concerns.jsonl reproducing the
   #2215 shape (comment present, only `raised` in ledger) turns red under the
   new check; adding the `deferred` event turns it green.
3. Forward-only: grandfathered bodies / absent-ledger tasks are not newly
   hard-FAILed (posture documented in the check's docstring).
4. Existing green bodies stay green (verifier smoke against completed tasks).

## 2. Method delta (what differs from the status quo)

Extend `check_concerns_audit` (documented as **check 14b** in the file-top
check registry) — no new check function, per the task Goal ("in the existing
concerns-audit check family"):

- Parse the ledger once more for the set of ids carrying **any** `deferred`
  event in their event HISTORY (`deferred_in_ledger`). "Matching" = ≥1
  `deferred` event for that id, not latest-event-is-deferred: a
  raised→deferred→verified-open chain (deferral later overturned/reopened) is
  NOT fabricated — a real defer-concern record exists. Latest-event semantics
  elsewhere in Lens 14 are unchanged.
- In the stale-marker scan loop, add a branch: comment id present in ledger,
  latest event ∈ {`raised`, `verified-open`}, id NOT in `deferred_in_ledger` →
  **fabricated deferral**.
- Severity routing of a fabricated deferral (posture, documented in docstring):
  - latest-event severity BLOCKER/CONCERN AND id not grandfathered → **FAIL**
    (joins/creates the check's FAIL detail; merged with any `unaddressed` FAIL).
  - id in the grandfather set → **WARN** (fold into `stale_warns` with a
    "fabricated deferral (grandfathered) — record via `task.py defer-concern`
    or remove the comment" message).
  - NIT severity (or missing/unknown severity) → **WARN** (Lens 14's contract:
    NITs never block; malformed rows stay conservative).
  - `addressed` latest event / id absent from ledger → existing stale WARNs,
    unchanged.
  - `concerns_path` None/missing → existing skip-PASS, unchanged (this IS the
    absent-ledger grandfather posture of criterion 3).
- **Grandfather set** (forward-only ratchet, the repo's pinned-list pattern):
  module-level `FABRICATED_DEFERRAL_GRANDFATHER: frozenset[str]` of concern
  ids, generated by a repo sweep at implementation time. Plan-time sweep
  (2026-08-10) found 18 fabricated (comment ∧ ledger present ∧ no `deferred`
  event) across 10 bodies — 8 at `awaiting_promotion` incl. #2215 — so a bare
  FAIL would newly block promotion of parked done work; the pinned WARN set
  keeps them visible without blocking, and every NEW fabrication FAILs. Keyed
  by concern_id alone (slugs; no cross-task collision in the swept set; the
  check has no reliable task-id input under `--file`). The implementer
  RE-RUNS the sweep at implementation time to regenerate the list (the
  plan-time list may age).

Known accepted residuals (documented in the docstring):
- The deferral regex matches anywhere in the body, including backtick-quoted
  prose that merely CITES a comment (e.g. #2219's own body quotes #2215's).
  Unchanged from the existing mechanism-3/stale-scan behavior; eliding code
  spans would change ack semantics out of scope. Practical exposure ≈ 0 (a
  quoted cid must also exist in the SAME task's ledger without a deferred
  event to false-FAIL).
- A post-`deferred` `verified-open` reopen keeps the comment "matching" (see
  above) — reopen staleness is a different check, out of scope.
