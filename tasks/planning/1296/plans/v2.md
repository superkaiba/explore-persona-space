# Plan — issue #1296: scripts_dir sys.path bootstrap for the bare `runpod_api` imports in `scripts/backend_poll.py`

## 0. Summary

Add a small module-level helper `_ensure_scripts_dir_on_sys_path()` to
`scripts/backend_poll.py` and call it immediately before each of the THREE
lexically-bare `from runpod_api import ...` sites (`:1554`, `:2205`, `:2380`),
mirroring the established inline bootstrap at `:1709-1711` / `:1771-1773`.
Plus two small regression tests in `tests/test_backend_poll.py`. ~12-line
production diff, 0 GPU-h, no public-contract change.

## 1. Goal

"Add the established `scripts_dir` sys.path bootstrap before the bare
`from runpod_api import get_pod_by_name` in `scripts/backend_poll.py` (now at
line ~1554; originally cited as :565)." (Task #1296 Goal, verbatim.)

In one paragraph: `backend_poll.py` works in SCRIPT mode (its own dir,
`scripts/`, is `sys.path[0]`), but in MODULE mode — how the test suite imports
it (`from scripts.backend_poll import main`, repo root on sys.path via the
editable install) — a bare lazy `from runpod_api import ...` raises
`ModuleNotFoundError` unless some earlier code happened to insert `scripts/`.
The fix makes each lazy `runpod_api` import self-sufficient, removing the
import-order landmine on the #664/#667 billing-leak detection path and
removing the need for caller-side workarounds (one already exists at
`tests/test_backend_poll.py:1875-1885`).

## 3. Design

**Decision: one module-level helper, called at all three bare sites.** Chosen
over (a) minimal `:1554`-only inline fix — leaves `:2205`/`:2380` live
landmines per the §2 early-return finding; and (b) inlining the 4-line pattern
3× — 12 duplicated lines vs one definition + 3 one-line calls, and the helper
gives future lazy-import sites a canonical name to call. The two WORKING
inline sites (`:1709-1711`, `:1771-1773`) are deliberately left untouched
(zero-benefit churn on tested code; they remain idempotent alongside the
helper).

### Diff 1 — `scripts/backend_poll.py`: the helper (~10 lines)

Insert at module level, AFTER the two #987-pinned functions end (never
inside/between them; exact line is a permitted deviation):

```python
def _ensure_scripts_dir_on_sys_path() -> None:
    """Insert THIS file's dir (scripts/) so a lazy ``import runpod_api`` resolves.

    In script mode scripts/ is already sys.path[0]; in MODULE mode (tests do
    ``from scripts.backend_poll import main``) only the repo root is on
    sys.path, so a bare ``from runpod_api import ...`` would raise
    ModuleNotFoundError (#710/#1296). Mirrors the inline bootstrap at the
    issue664_common import sites; idempotent.
    """
    scripts_dir = str(Path(__file__).resolve().parent)
    if scripts_dir not in sys.path:
        sys.path.insert(0, scripts_dir)
```

`sys` and `Path` are already module-top imports (`:50`, `:53`) — no new
imports, no F401 exposure.

### Diff 2 — the three call sites (3 lines)

One line immediately before each bare import (current anchors; drift allowed):

- `:1554` in `_maybe_escalate_runpod_wedge`:
  ```python
      if getattr(handle, "backend", None) != "runpod":
          return result
  +   _ensure_scripts_dir_on_sys_path()
      from runpod_api import get_pod_by_name  # live RunPod API (X-Team-Id baked in)
  ```
- `:2205` in `_failover_wedged_runpod` and `:2380` in
  `_failover_cuda_ima_runpod`: same one-liner immediately above
  `from runpod_api import get_pod_by_name, terminate_pod`.

### Diff 3 — regression tests: `tests/test_backend_poll.py` (~30 lines, reuses the file's existing module-mode import + `Path`)

1. `test_ensure_scripts_dir_bootstrap_resolves_runpod_api_in_module_mode` —
   behavior test with a built-in negative control:
   - scrub every `scripts/`-resolving entry from `sys.path` via
     `monkeypatch.setattr(sys, "path", [...])` (auto-restored);
   - `monkeypatch.delitem(sys.modules, "runpod_api", raising=False)`;
   - **negative control:** `with pytest.raises(ModuleNotFoundError):
     importlib.import_module("runpod_api")` — proves the scrub is real and
     the pre-fix failure mode exists;
   - call `scripts.backend_poll._ensure_scripts_dir_on_sys_path()`;
   - `mod = importlib.import_module("runpod_api")`; assert
     `hasattr(mod, "get_pod_by_name") and hasattr(mod, "terminate_pod")`.
   No live API call is ever made (import only); monkeypatch teardown restores
   both `sys.path` and the original `runpod_api` module object, so no
   cross-test aliasing.
2. `test_every_lazy_runpod_api_import_is_bootstrap_guarded` — the durable
   lexical pin: read `scripts/backend_poll.py` source; for every INDENTED
   `from runpod_api import` line, assert that within the preceding ~12 lines
   there is either `_ensure_scripts_dir_on_sys_path()` or
   `sys.path.insert(0, scripts_dir)`. This is what stops a FUTURE bare site
   from re-introducing the landmine (the #710 candidate sat unfixed for two
   weeks; a grep-shaped pin prevents the recurrence class, not just these
   three lines). Module-top (unindented) imports are out of scope by the
   indentation filter — there are none today.

Why a stub-module approach was rejected for test 1: pre-seeding a fake
`runpod_api` in `sys.modules` would let `from runpod_api import ...` resolve
WITHOUT touching `sys.path`, making the test pass even without the fix.

No changes to `tests/test_runpod_wedge_detection.py` /
`test_lane_infra_main_pin.py` / the `:1875-1885` workaround (it stays valid
and idempotent).

## 5. Kill criteria

- If investigation showed NO code path reaches any of the three sites in
  module-import mode, the planner could deflect with a no-change report. That
  is REFUTED: `:1554` runs on every runpod-handle tick and
  `tests/test_backend_poll.py:1875-1885` already carries a caller-side
  workaround for exactly this gap; the `:1763-1767` early-return leaves
  `:2205`/`:2380` bootstrap-free on the non-#664 path. Not deflecting.
- Post-hoc kill: if the new negative control CANNOT reproduce
  `ModuleNotFoundError` with `scripts/` scrubbed (i.e., `runpod_api` resolves
  some other way — e.g., it turns out to be packaged), the premise is wrong —
  stop, report, archive the task instead of landing a no-op helper.

## 6. Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| `sys.path.insert(0, scripts_dir)` shadows stdlib/site-packages names via `scripts/*.py` | Low — and NOT NEW: identical semantics already live at `:1709`/`:1771`, in script mode (`scripts/` is `sys.path[0]`), and in 3+ test files' module-top inserts | No new exposure; helper is byte-equivalent to the established pattern |
| Breaking the #987 main-pin (source-identity test) | Low | Helper inserted OUTSIDE the two pinned function bodies; `tests/test_lane_infra_main_pin.py` in the acceptance suite catches any slip |
| Test 1 brittleness: `sys.path`/`sys.modules` mutation leaking cross-test | Low | All mutation via `monkeypatch` (auto-restore of the original list object and the original `runpod_api` module object) |
| Lexical-guard window (~12 lines) too tight if future refactors add long comments between call + import | Low | Guard message names the fix (`call _ensure_scripts_dir_on_sys_path() directly above the import`); widening the window is a one-line test edit |
| Line-number drift between plan and implementation time | Medium | Anchors are the enclosing function names + the import text, not raw line numbers (permitted deviation) |
