## 0.0 TL;DR (plain English)

- **What I'll do:** When we ask Google Cloud to spin up a GPU machine on
  the cheap "wait-in-line for spare capacity" tier, the request can sit
  queued longer than the 5-minute window our launch script waits. Today
  that window closing makes the launcher crash with a confusing error
  code, even though the machine usually *did* get created and is sitting
  in the queue. I'll teach the launcher to check "did the machine
  actually get made?" before deciding it failed.
- **What I expect:** If the machine exists (queued or starting up), the
  launcher will report "still waiting — re-run me" (the same signal it
  already uses elsewhere) instead of crashing, so the run continues
  instead of being killed or accidentally launched twice.
- **What would change my mind:** If the machine genuinely was NOT created
  after the timeout, the launcher must still fail loudly — I do not want
  to paper over a real provisioning failure or leave an orphaned machine
  billing in the background.

## 1. Goal + acceptance criteria

### Method delta vs current behavior (one paragraph)

Today, a `TimeoutExpired` from the create subprocess propagates raw all
the way to `main()`'s catch-all and exits 4 with a traceback. After the
change, `GcpBackend.launch` wraps the create `self._run(argv)` call in a
`try/except subprocess.TimeoutExpired`; on a timeout it runs the EXISTING
`reconnect_or_none` probe to ask "did the instance come up server-side?".
A live instance → raise a new typed terminal
`GcpCreateTimedOutStillProvisioning(RouteError subclass)` carrying the
instance name + status; a truly-absent instance → raise a capacity-shaped
`GcpProvisioningError` (so the router's existing zone-fallback / next-tier
path runs); a probe failure → re-raise the original timeout wrapped as a
`GcpProvisioningError` (provision-class, never a silent success).
`_cmd_launch` gains one `except GcpCreateTimedOutStillProvisioning` arm
that prints the still-waiting JSON and returns `EXIT_STILL_WAITING`; the
`GcpProvisioningError`/absent path already flows through the router →
`RouteError` → exit 2 with no new code.

1. **New exception class** (near the other typed terminals,
   `GcpProvisioningError` / `GcpWorkloadError` / `GcpProbeError`):
   ```python
   class GcpCreateTimedOutStillProvisioning(RouteError):
       """The ``gcloud compute instances create`` subprocess exceeded the
       300s cap, BUT a post-timeout ``instances list`` probe found the
       instance live (RUNNING/PROVISIONING/STAGING/STOPPING) — the
       FLEX_START preemptible-queueing case (#658). NOT a failure: the
       launch is in flight; the caller re-runs the same command and
       ``reconnect_or_none`` reconnects idempotently. Carries the
       instance name + observed status for the still-waiting JSON.
       """
       def __init__(self, *, instance_name: str, status: str, issue: int) -> None:
           self.instance_name = instance_name
           self.status = status
           self.issue = issue
           super().__init__(
               f"GCP create for {instance_name} timed out at the 300s subprocess "
               f"cap but the instance is live (status={status}) — FLEX_START "
               "still-provisioning; re-run to continue waiting."
           )
   ```
   NOTE: it subclasses `RouteError` (imported in `gcp.py` from
   `backends/base.py` or `backends/router.py` — verify import; `gcp.py`
   already defines `GcpProvisioningError`/`GcpWorkloadError` which are
   `RouteError` subclasses, so the base is already in scope). Subclassing
   `RouteError` means the router propagates it cleanly and
   `_cmd_launch`'s `except RouteError` would otherwise catch it — so the
   NEW `except GcpCreateTimedOutStillProvisioning` arm in `_cmd_launch`
   MUST be ordered BEFORE the `except RouteError` arm. **Verify at
   implement time** whether `GcpProvisioningError` is a `RouteError`
   subclass; if NOT (it may be a plain `Exception` the router catches
   structurally), make `GcpCreateTimedOutStillProvisioning` mirror
   whatever `GcpProvisioningError`'s base is, and add the explicit
   `_cmd_launch` arm regardless. (Assumption A3 below.)

2. **`GcpBackend.launch` — wrap the create call.** Replace the bare
   `result = self._run(argv)` at `gcp.py:3092` inside the zone loop with:
   ```python
   try:
       result = self._run(argv)
   except subprocess.TimeoutExpired as exc:
       # FLEX_START rungs legitimately stay PENDING past the 300s cap;
       # the create OFTEN succeeds server-side. Probe the canonical name
       # before treating the timeout as a failure (#658 failure-lesson v2).
       live = self._reconnect_probe_after_create_timeout(spec, exc)
       if live is not None:
           raise GcpCreateTimedOutStillProvisioning(
               instance_name=live.pod_name,
               status=str(live.extra.get("status_at_reconnect") or "PROVISIONING"),
               issue=int(spec.issue),
           ) from exc
       # Instance truly absent → a provision-class failure. Re-raise as
       # GcpProvisioningError (capacity-shaped) so the existing zone
       # fallback / next-tier router path handles it; never let the raw
       # TimeoutExpired escape to main()'s exit-4 catch-all.
       last_error = GcpProvisioningError(
           f"GCP create for issue={spec.issue} in zone={zone} timed out at "
           f"the {GCLOUD_CREATE_TIMEOUT}s subprocess cap and no instance was "
           "found server-side after the timeout — treating as a capacity/"
           "provisioning failure.",
           reason="create_timeout_no_instance",
           evidence={"zone": zone, "matched_pattern": "create timeout (resource not created)"},
       )
       # Mirror the existing capacity-miss flow: try the next zone.
       logger.warning(
           "GCP create timed out in zone=%s with no server-side instance; "
           "trying next fallback. issue=%d", zone, spec.issue,
       )
       continue
   ```
   - The `evidence["matched_pattern"]` deliberately contains the substring
     `"resource"` so it matches the existing capacity-retry predicate at
     `gcp.py:3105` (`any(tag in matched for tag in ("exhaust", "resource",
     "enough resources"))`) — i.e. the absent-after-timeout case retries
     the next zone exactly like an `EXHAUSTED` miss, then `for-else`-raises
     `last_error` if every zone is exhausted. **Verify** this predicate at
     implement time so the absent branch routes through fallback, not a
     hard immediate raise. (Assumption A5.)
   - `GCLOUD_CREATE_TIMEOUT` = the 300 cap. Reference
     `default_gcloud_runner`'s `timeout` default; either import the literal
     or reference a module constant. **Do NOT** silently use a different
     value — keep it the 300 the runner uses. If `default_gcloud_runner`'s
     `timeout=300` is a bare default rather than a named constant,
     introduce `GCLOUD_DEFAULT_TIMEOUT_SEC = 300` and use it in BOTH places
     (the runner default + this message) so they cannot drift.

3. **New helper `GcpBackend._reconnect_probe_after_create_timeout`:**
   ```python
   def _reconnect_probe_after_create_timeout(
       self, spec: RunSpec, original_timeout: subprocess.TimeoutExpired
   ) -> RunHandle | None:
       """Post-create-timeout probe: is the eps-issue-<N> instance live?

       Returns the reconnect handle when a live instance (RUNNING /
       PROVISIONING / STAGING / STOPPING) is found, ``None`` when no
       instance exists. On a PROBE failure (GcpProbeError — gcloud rc!=0
       / bad JSON / auth), RE-RAISES the original timeout wrapped as a
       GcpProvisioningError: "couldn't ask" must NEVER read as "live"
       (would mask a real failure as still-waiting) NOR silently as
       "absent" (would lose the timeout signal). Provision-class so the
       router fallback handles it.
       """
       try:
           return reconnect_or_none(spec=spec, config=self._config, runner=self._run)
       except GcpProbeError as probe_exc:
           raise GcpProvisioningError(
               f"GCP create for issue={spec.issue} timed out and the "
               f"post-timeout instances-list probe ALSO failed ({probe_exc}); "
               "instance state UNKNOWN — treating as a provisioning failure.",
               reason="create_timeout_probe_failed",
               evidence={"matched_pattern": "create timeout probe failed"},
           ) from original_timeout
   ```
   - **CRITICAL ordering:** `reconnect_or_none` is ALREADY called at the
     TOP of `launch` (the idempotent re-entry, `gcp.py:2903`) BEFORE the
     create loop. That early call returned `None` (no live instance) —
     otherwise we'd never reach the create. The POST-timeout call is a
     SECOND, fresh probe (state changed: the create just landed an
     instance server-side). The two calls are independent; the post-timeout
     one observes the newly-created instance. The probe itself uses the
     SAME 300s runner timeout — acceptable (the list call is fast; a hung
     list raises `TimeoutExpired` which propagates as a probe failure → the
     `GcpProbeError` path is NOT hit, the raw `TimeoutExpired` from the
     LIST would escape; **handle this**: wrap the helper's
     `reconnect_or_none` call to ALSO catch `subprocess.TimeoutExpired`
     from the list probe and treat it as a probe failure → same
     `GcpProvisioningError` re-raise. Assumption A6.)

### Divergence from the candidate's diff sketch (justified)

The candidate sketched a `created_during_timeout=True` flag on
`GcloudRunResult` returned from `default_gcloud_runner` itself. I diverge:
the fix lives in `GcpBackend.launch`, NOT in `default_gcloud_runner`.
**Why:** `default_gcloud_runner(argv)` is a pure argv-runner with no
knowledge of which subcommand it ran, the instance name, the config, or
the spec — it cannot issue a meaningful `instances list` probe without
re-parsing the create argv to extract the name/zone (fragile) and
constructing a fresh list argv (it has no `GcpConfig`). `GcpBackend.launch`
already holds `spec`, `self._config`, `self._run`, and `instance_name_for`,
AND the project already has `reconnect_or_none` doing the exact
list-by-name probe #658 prescribes. Catching the timeout one frame up (in
`launch`) reuses that machinery verbatim and keeps `default_gcloud_runner`
a clean primitive. The candidate explicitly labels its sketch "refine in
planning", so this is in-bounds. The `default_gcloud_runner` signature is
UNCHANGED (no `created_during_timeout` field added to `GcloudRunResult`),
which also keeps every existing `GcloudRunResult` consumer + golden test
untouched.

## 11. Decision Rationale

N/A — no training hyperparameters in this task type. The one non-obvious
DESIGN decision:

- **What:** the live-after-timeout case exits **75 (still-waiting)**, not
  0 (normal handle).
  - **Why:** the task body + constraints explicitly request the exit-75
    still-waiting path, and the #658 `epm:failure-lesson v2` describes the
    intended behavior as "the launch is in flight … let the poller track
    it … re-run". Exit 75 is the existing documented still-waiting contract
    (#603) — the caller re-runs the SAME launch command, and
    `reconnect_or_none` (the idempotent re-entry at the TOP of `launch`)
    reconnects to the now-observable live instance with NO double-create.
    Exit 0 (returning a normal handle for a still-PROVISIONING instance)
    was considered and rejected: it would require the launch path to write
    a sidecar + post `epm:cluster-launched` for an instance whose
    `instance_id`/zone we did NOT capture (the create stdout was lost to
    the timeout), forcing a fragile re-parse — whereas the re-run path
    gets a clean create-stdout parse on reconnect.
  - **Source:** task #736 body (Goal + Constraints) + #658
    `epm:failure-lesson v2`; the exit-75 contract is `dispatch_issue.py`
    module docstring lines 74–84 (#603).
