# Plan v2 — #2147: `vm_disk_guard.py` reclaim tier for `~/.eps-slurm-src`

`kind: infra` · workflow-fix · `workflow_fix_target: scripts/vm_disk_guard.py` · fingerprint `d7cab4eeb1be`

## 1. Goal

Add a `vm_disk_guard.py` reclaim tier that reaps per-issue SLURM source staging
trees under `~/.eps-slurm-src/issue-<N>` for TERMINAL-status issues, under the
same safety contract as the existing tiers: terminal-status gate, status read
strictly read-only, ACTIVE-issue dirs attributed + escalated but NEVER deleted,
a recency keep window, durable artifacts never touched, `main()`-only production
opt-in so library/pytest callers stay hermetic, and a kill switch.

### 1.1 Success criteria (all must hold)

1. Tier (g) exists in `scripts/vm_disk_guard.py`, wired into the boot-disk pass
   only, SKIPPED-with-reason without the `main()` opt-in.
2. T1-T8 (§5) all pass and all FAIL against pre-fix `HEAD` (a test that passes
   pre-fix is not evidence).
3. `uv run python scripts/workflow_lint.py` (no flags) exits 0; ruff check +
   format clean on every touched file.
4. The real-VM `--dry-run --json` acceptance run (§6) classifies all 13 live
   dirs exactly as hand-verified in §2, with `reaped == 0` and zero filesystem
   mutation.
5. Both kill switches demonstrably disarm the sweep (T3).

### 1.2 Kill / abort criteria (halt and report, do not work around)

- **K1** — any test in T4/T5/T6 shows the tier removing a tree it should have
  kept (dirty, re-probe-flipped, live-process). This is the failure mode the
  task exists to prevent; halt, post `epm:failure v1 failure_class: code`, do
  NOT weaken the gate to make a test pass.
- **K2** — the §6 dry-run classifies any dir differently from the hand-verified
  §2 table and the discrepancy is not explained by a state change on the VM
  since 2026-08-16. Halt and re-derive; a mismatch means a gate is wrong.
- **K3** — reusing `cleanup_branch_src` turns out to require changing its
  signature or behavior (rather than only calling it behind the gate ladder).
  That contradicts D2's premise; halt and re-plan rather than widening a
  hot-path helper used by every SLURM dispatch.
- **K4** — the lazy `backends.slurm` import proves unworkable in the guard
  process (circular import, unacceptable load cost). Halt and re-plan D2/§4
  rather than duplicating the remover.

**What would change my mind about the whole approach:** if the §6 dry-run shows
the live dirs are NOT reap-eligible under the existing terminal gate — i.e. the
population is dominated by active-issue dirs the tier can only escalate — then a
reclaim tier is the wrong instrument and the right fix is at the writer (making
`materialize_branch_src` sparse, or reaping on launcher death). §2's measured
12-`awaiting_promotion` / 1-`completed` split is what makes the tier the right
instrument; if that split does not reproduce, re-plan.

## 2. Problem statement + measured evidence

`backends/slurm.materialize_branch_src` creates `~/.eps-slurm-src/issue-<N>` as a
detached scratch worktree per dispatch. `prepare()` reaps it in a `finally`, but
a killed/crashed launcher skips that reap and the tree accretes with NO covering
janitor. `slurm.py:3849-3851` documents the gap self-referentially: *"`worktree_audit.py`
sweeps `.claude/worktrees/` only; `vm_disk_guard.py` tiers never touch
`~/.eps-slurm-src`"*.

**Absence evidence** (re-verified 2026-08-16; `grep -c 'eps-slurm-src'`):
`vm_disk_guard.py` 0 · `worktree_audit.py` 0 · `clean_experiment_downloads.py` 0
· `backends/slurm.py` 5 (all in the writer). The 0-hit IS the evidence.

**Realized population** (2026-08-16): 13 dirs, **112 GB**, all registered
detached-HEAD worktrees, 3/3 sampled CLEAN. Statuses: 12 `awaiting_promotion`,
1 `completed` (1609). mtimes span 2026-07-15 → 2026-08-01 (all ≥ 15 days idle).

**Per-dir composition** (issue-1946, 9.4 GB) — this CORRECTS the task body's
stated hypothesis:

| subtree | size | note |
|---|---|---|
| `eval_results` | 7.8 GB | dominant term; 94,512 tracked files |
| `figures` | 973 MB | |
| `tasks` | 317 MB | |
| `external` | 232 MB | `open-instruct` 221 MB — the *hypothesized* cause |
| `data` | 61 MB | |

The body hypothesized that `WORKING_TREE_OVERLAY_PATHS` rsyncing
`external/open-instruct` explains the 8.6 GB realized vs "~3.8 GB" documented.
**Falsified**: the overlay is ~2.4% of the dir. The driver is `eval_results/`,
committed git content whose repo-wide size has grown far past what the

by this task.

## 3. Design decisions

### D1 — Home: `vm_disk_guard.py` (not `worktree_audit.py`). SETTLED.

Three reasons: (a) the task asks for the byte-floor reclaim contract
(terminal gate + active escalate-only + recency + kill switch) that
`vm_disk_guard.py` owns and `worktree_audit.py` does not — the latter sweeps on a
lifecycle framing (idle/dirty/active-issue) scoped to `.claude/worktrees/`;
(b) `~/.eps-slurm-src` is under `$HOME` on the boot disk `/`, exactly the disk
`vm_disk_guard.py` guards; (c) the body's Provenance names
`scripts/vm_disk_guard.py` as `workflow_fix_target`.

### D2 — Removal goes through the existing shared helper. SETTLED.

All 13 dirs are REGISTERED worktrees, so `rmtree` alone strands the registration.
`backends/slurm.py:3841 cleanup_branch_src(src_root, scratch, *, timeout=300)`
already does worktree-remove → rmtree → prune, and was factored in #1913 so the
materializer and `prepare()` share ONE implementation. Per CLAUDE.md "Reuse
existing in-repo tools/helpers", the tier CALLS it — no second remover.

**The one adaptation, and why it is safe.** `cleanup_branch_src` passes
`--force`, correct for the OWNER tearing down its own scratch, WRONG for a
janitor (force destroys uncommitted work). The tier therefore evaluates the
cleanliness gate FIRST and calls the helper only on a confirmed-clean tree; a
dirty tree is kept + escalated and the helper is never reached. Rejected
alternative: adding a `force: bool = True` parameter to `cleanup_branch_src` —
it widens a hot-path signature for a caller-side concern, and the gate-first
shape gives the janitor a reason string for the report either way.

`cleanup_branch_src` also refuses (`ValueError`) to remove `src_root` itself; the
tier keeps that belt-and-suspenders and adds its own containment assert (D4-g3).

### D3 — Terminal gate: REUSE `TERMINAL_CACHE_REAP_STATUSES` verbatim. SETTLED.

`vm_disk_guard.py:447` already defines `{"completed", "archived",
"awaiting_promotion"}`, deliberately wider than `task_workflow.TERMINAL_STATUSES`
(comment at `:443`). That set already covers 13/13 of the realized population. A
narrower gate would reclaim ~8 GB of 112 GB and miss the task's point; a wider
one would change existing tier semantics. No new status vocabulary.

### D4 — Gate ladder (evaluated in order; first match wins, one row per dir)

| # | Gate | Disposition |
|---|---|---|
| g1 | name not `issue-<N>` shaped | `kept — unrecognized name` |
| g2 | not uid-owned (`_tmp_entry_owned`) | `kept — not owned` |
| g3 | resolved path escapes the root, or `== src_root` | `kept — containment` |
| g4 | status not in `TERMINAL_CACHE_REAP_STATUSES` (incl. unresolvable) | `kept — active/unresolved` **+ escalate** |
| g5 | mtime newer than `EPM_SLURM_SRC_MIN_AGE_HOURS` (default 48 h) | `kept — recently touched` |
| g6 | live process holds the path (`/proc` cwd/fd scan) | `kept — live process` |
| g7 | not a registered worktree of `main_repo` | `kept — unregistered` |
| g8 | tree dirty: any `status --porcelain` row, or any untracked/ignored file | `kept — dirty` **+ escalate** |
| — | all clear | `reaped` via `cleanup_branch_src` |

g5/g6 mirror the #911 recency + live-process keeps. g8 is the janitor-specific
addition that makes D2's `--force` reuse safe; note `--ignored` is included
because a gitignored artifact inside a scratch tree is unrecoverable content that
`git worktree remove --force` would silently destroy.

g7 uses `git worktree list --porcelain` on `main_repo`, parsed for an exact
resolved-path match. An unregistered dir is KEPT, not rmtree'd: it is either a
partially-removed husk or something this tier does not understand, and the #2127
precedent's posture (refuse rather than inflict) applies. A follow-up may widen
this after the tier has run clean for a while.

**Post-gate re-probe (the #2127 lesson).** Gate state is re-evaluated immediately
before the reap call, so a tree that went dirty / acquired a lock / gained a live
process between classification and reap is dropped to
`slurm-src-reap-reprobe-kept` rather than destroyed.

### D5 — Hermeticity + kill switch (the #2127 / #2095 pattern, verbatim)

`clean_slurm_src(apply, *, slurm_src_root, main_repo)` returns
`TierResult(name="slurm-src")` and SKIPS with a reason when either opt-in is
`None`. `run_guard` forwards both VERBATIM and NEVER calls the production
resolver itself — the opt-in lives ONLY in `main()`'s boot-disk branch, pinned by
the existing source-scan test that already pins `production_tmp_root` /
`production_staging_roots`. This is what keeps every `run_guard(apply=True, ...)`
suite call from sweeping the real `~/.eps-slurm-src`.

Kill switch `EPM_SKIP_SLURM_SRC_SWEEP=1`, plus transitive kill via the existing
non-canonical family switch `EPM_SKIP_NONCANONICAL_CACHE_SWEEP=1` (matching how
tier (f) composes). Root override `EPS_SLURM_SRC_ROOT`, read with the SAME
precedence as `slurm.py` so writer and reaper cannot drift.

**Boot-disk pass only.** The data-disk pass (`reclaim_tiers=False`) does not arm
this tier — `~/.eps-slurm-src` is under `$HOME` on `/`. The tier additionally
records the resolved root's filesystem in its report so a future `$HOME` move is
visible rather than silent.

### D6 — Escalation reuses the existing sidecar, no new channel

g4/g8 keeps append structured rows to `TierResult` and write to the existing
`.claude/cache/disk-guard-events.jsonl` sidecar with the established
per-`(key, band)` dedup + ack-sentinel suppression. No new alert surface, no new
notification path. Report-only by default; the cron passes `--apply`.

### D7 — Docstring corrections (in scope, same round)

`slurm.py:3048` and `:3848` claim "~3.8 GB"; measured is ~8.6 GB mean. `:3849-3851`
claims no covering janitor. Both are corrected in this round — leaving them makes
the module actively misleading the moment the tier lands. This is prose-only in
`backends/slurm.py`; no behavior change there beyond the `cleanup_branch_src`
call site gaining a caller.

## 4. Implementation

**Files touched**
- `scripts/vm_disk_guard.py` — new tier (g) `clean_slurm_src` + `slurm_src_root()`
  resolver + `slurm_src_sweep_enabled()` + `run_guard` wiring + `main()` opt-in
  + `--json` surface field.
- `src/explore_persona_space/backends/slurm.py` — docstring corrections only (D7).
- `tests/test_vm_disk_guard_slurm_src.py` — new.
- `.claude/rules/disk-hygiene.md` — one paragraph documenting tier (g), its
  switches, and the gate ladder (the rule file is the always-on surface agents
  read before placing a staging path).

**Import shape.** `cleanup_branch_src` is imported lazily inside the reap branch
(`backends.slurm` is a 3,800-line module that pulls the backend stack; a
module-top import would load it on every guard invocation including the
data-disk pass). Per the CLAUDE.md lazy-import gotcha, a lazy import in a
conditional branch is unverified code unless a test EXECUTES it — so the reap
test exercises the real import path (§5 T4), not a monkeypatched stand-in.

## 5. Tests (all must fail pre-fix)

- **T1 gate ladder** — one parametrized case per g1-g8 over a tmp fixture root,
  asserting disposition + reason string. Fails pre-fix: no tier exists.
- **T2 hermeticity** — `run_guard(apply=True, ...)` with no `slurm_src_root`
  opt-in leaves a fixture tree untouched and reports SKIPPED; extends the
  existing source-scan test so `run_guard` cannot call the production resolver.
- **T3 kill switches** — own switch and family switch each skip the sweep.
- **T4 real-reap on a real worktree** — create an actual `git worktree add
  --detach` under a fixture repo, run the tier with `apply=True`, assert the dir
  is gone AND the registration is pruned (`worktree list` clean). This is the
  test that executes the lazy import for real.
- **T5 dirty-tree refusal** — a worktree with (a) a tracked modification,
  (b) an untracked file, (c) a gitignored file: each KEPT, escalation row
  emitted, directory still on disk.
- **T6 post-gate re-probe** — tree dirtied between classification and reap →
  `slurm-src-reap-reprobe-kept`, not removed.
- **T7 active-issue escalate-only** — a dir whose issue resolves to `running`
  is never deleted and produces an attribution row.
- **T8 dry-run performs zero mutations** — the SAME real-worktree fixture as T4,
  run with `apply=False`: assert the directory still exists, the worktree
  registration is still present, no sidecar row is written, and the returned
  `TierResult` reports the candidate with `bytes_freed == 0` and a non-zero
  `total_discovered_bytes`. This pins the `apply` kwarg thread through the tier
  AND through the `cleanup_branch_src` call site — a broken thread would turn
  the §6 acceptance dry-run into a real 112 GB deletion (#596/#607/#633).

Plus: `uv run python scripts/workflow_lint.py` (no flags) and
`uv run ruff check` + `format` on touched files.

## 7. Risks

| Risk | Mitigation |
|---|---|
| A janitor destroys a live SLURM dispatch's scratch mid-run | g5 recency (48 h) + g6 live-process + g7 registration + the post-gate re-probe; `prepare()` reaps its own scratch in seconds, far inside the window |
| `--force` in the reused helper destroys uncommitted work | g8 evaluated FIRST, incl. untracked + ignored; helper unreachable on a dirty tree |
| Reap strands a worktree registration | `cleanup_branch_src` prunes; T4 asserts it against a real worktree |
| `$HOME` / root relocation silently disarms the tier | resolved root's filesystem recorded in the report; `EPS_SLURM_SRC_ROOT` read with the writer's precedence |
| Heavy lazy import breaks in production only | T4 executes the real import |
