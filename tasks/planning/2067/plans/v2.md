## 1. Goal + motivation

> A session that pivots a task's compute lane and provisions a pod on a task ANOTHER live session owns must actually reach that owner — a durable marker alone does not wake it, and the owner keeps waiting on the lane the pivot abandoned while the new pod bills. (Task #2067 Goal, verbatim.)

On 2026-08-03 session A pivoted #1345's lane and provisioned `pod-1345-charcapa` (8×H200) on a task it did not own, recording the pivot only as an `epm:progress` marker. The owning session (09fee09f) never learned — markers are durable but do not wake anyone — and kept waiting on a fellows SLURM job queued ~20h out while the pod sat 74+ min at 0% GPU (~$54). The fix belongs in `.claude/rules/compute-backend-failover.md` because lane pivots ARE failover decisions: every pivot walks Part B's failure paths, so the pre-provision ownership duty must sit next to the failover ladder the pivoter is already reading. The rule closes the gap by requiring the pivoter to RESOLVE the owner (tri-state, mirroring the #1667 `_wedge_owner_live` shape) before any cross-session provision.

## 2. Design-space evaluation

**Candidate 1 — stand-down + take-ownership.** Resolves the owner before provisioning; on a live foreign owner either stops it (takeover) or refuses. Blast radius vs constraint 1 (no split-ownership): closes it by construction — ownership is resolved to exactly one session before any pod exists. Vs constraint 2 (no blocked rescue): preserves rescue via the takeover path, BUT "stop a LIVE owner + take over" is itself hazardous — a mid-turn stop of a healthy session destroys in-flight state (the #1586 lesson: activity you can't see is not absence of activity).

**Candidate 2 — pre-pivot check that REFUSES.** Same detection, always refuses on a foreign owner. Vs constraint 1: closes it. Vs constraint 2: FAILS it — a wedged/crashed owner permanently blocks rescue, and the #664/#1667 family exists precisely because dead owners are common.

**Candidate 3 — owner-side re-read duty.** The owner polls markers before continuing a long queue wait. Vs constraint 1: does NOT close it — the pivoter still provisions first and the owner learns later (pod bills in the gap; a crashed owner never reads at all). Vs constraint 2: neutral. Useful hygiene, insufficient alone.

**Chosen: hybrid of 1+2** — resolve the owner tri-state; REFUSE on LIVE (defer to the owner, never stop a healthy session) and on UNKNOWN (fail-safe), and perform a SANCTIONED TAKEOVER only on provably-DEAD — because it is the only shape that satisfies both hard constraints simultaneously, and it reuses the already-validated #1667 fail-safe direction.

Insert verbatim:

```markdown
### Cross-session pivot — resolve the owner before provisioning (#2067)

**A pivoting session that provisions a pod on a task it does not own MUST
first resolve the owner.** A durable marker alone does NOT wake a live
owner: on 2026-08-03 a session pivoted #1345's lane and provisioned
`pod-1345-charcapa` (8×H200) recording only an `epm:progress` marker; the
owning session kept waiting on the abandoned fellows queue (~20h out) while
the pod sat 74+ min at 0% GPU (~$54) until a third session found the orphan.
"I do not own this task" means: this session is not the registered /
issue-mapped session for task N (check `scripts/spawn_session.py list`'s
issue column), and it was not spawned to run `/issue N`.

**Pre-pivot owner resolution (tri-state — the pivoter-side sibling of the
#1667 `_wedge_owner_live` probe).** Resolve the owner to LIVE | DEAD |
UNKNOWN from three evidence sources, ALL read fresh at pivot time:

- **Registration:** a registration file for task N exists —
  `~/.eps-autonomous/issue-<N>.json` (autonomous spawn) or
  `~/.eps-autonomous/manual-issue-<N>.json` (`spawn_session.py
  register-current`) — naming a `happy_session_id` that
  `spawn_session.py list` still shows as a live session; a cwd-mapped
  daemon child on the issue worktree counts the same as a registration.
- **Recent markers:** any non-watcher marker on task N's events within
  the last 2h (the `EPM_WEDGE_OWNER_RECENT_H` window #1667 uses) — read
  via `task.py view <N> --json`, excluding watcher-posted kinds.
- **Transcript freshness:** the registered session's transcript mtime
  within the same 2h window.

LIVE = a live registered/cwd-mapped session exists (regardless of
transcript age) OR any recent non-watcher marker within the window.
DEAD = registration absent-or-stale (no live session for the recorded
`happy_session_id`) AND no non-watcher marker within the window AND no
fresh transcript. UNKNOWN = any evidence source unreadable (list RPC
failure, marker read failure, missing daemon) — never coerce a read
failure to DEAD.

**Action table:**

| Owner state | Pivoting session does |
|---|---|
| **LIVE** | REFUSE the pivot — do NOT provision. Post `epm:progress` on N (`pivot-refused: owner <sid> LIVE via <evidence>; proposed lane <old> -> <new>`) so the owner's next marker read sees the proposal; the LIVE owner decides its own lane. Never `spawn_session.py stop` a LIVE owner to clear the way. |
| **DEAD** | SANCTIONED TAKEOVER, in order: (1) `spawn_session.py stop --session-id <sid>` on the dead owner's session id if one is registered (clean stop; auto-unregisters, #1455) — else `spawn_session.py unregister --issue N` for a stale registration (never `rm` on `~/.eps-autonomous/`); (2) post the takeover marker (recording contract below); (3) cancel/tear down the abandoned lane's queued work (e.g. `scancel` the SLURM job) so the old lane cannot double-run; (4) provision. |
| **UNKNOWN** | REFUSE — treat as LIVE (the fail-safe direction, mirroring #1667: uncertainty never licenses the destructive/irreversible arm). Post the same `pivot-refused` marker with `owner UNKNOWN via <which read failed>`; retry resolution next tick or surface to the user. |

**Recording contract.** Every resolution outcome posts ONE
`epm:progress` marker on task N via `task.py post-marker` BEFORE any
provision, note grammar:
`pivot-ownership: <refused|takeover>; owner=<sid|none>; state=<LIVE|DEAD|UNKNOWN>; evidence=<registration|markers|transcript reads, one clause each>; lane <old> -> <new>; by-session=<this sid>`.
On a DEAD takeover the marker is posted AFTER the stop/unregister and
BEFORE the provision, so any concurrent reader sees ownership already
resolved to the pivoter. The marker is the durable RECORD; the
stop/unregister is what actually prevents the dead owner's respawn from
re-claiming the lane — neither substitutes for the other.

**Relation to the #1667 wedge owner-liveness guard (Part C watcher
backstop):** #1667 is WATCHER-side — it gates terminate-vs-defer on an
already-wedged pod; #2067 is PIVOTER-side — it gates
provision-vs-abort/takeover before a pod exists. Two different call
sites, one shared conceptual probe (tri-state owner liveness, literal-DEAD
required for the irreversible arm, uncertainty fails safe).

**Sibling rule:** CLAUDE.md § teammate coordination ("one implementer per
file set") — the compute analogue: one owner per task's compute; never
provision into split-ownership.
```

## 6. Fail-safe direction (state explicitly)

Under uncertainty (owner state UNKNOWN, any marker/registration/list read failure), the pivoting session REFUSES to provision — uncertainty is coerced toward LIVE, never toward DEAD. This biases toward blocked-rescue and away from split-ownership. Trade-off, stated: a genuinely dead owner whose death is unprovable (daemon down, markers unreadable) delays its rescue by one resolution retry / one user surface — bounded minutes of lost rescue time — whereas the opposite bias re-opens the exact #1345/#1739 incident class (unbounded 8×H200 billing + a duplicated lane). Matching #1667's direction also keeps the two probes' semantics identical, so a future shared implementation cannot inherit two contradictory fail-safe conventions.

## 10. Deviations

One deliberate deviation from `_wedge_owner_live`'s exact shape: the watcher probe treats a live registered session WITH a stale transcript as still-live via "a live registered/cwd-mapped session with a fresh transcript" conjunctively; the #2067 pre-pivot LIVE definition counts a live registered session as LIVE regardless of transcript age. Reason: at the pivoter call site the destructive arm is a STOP of that session — a live-but-quiet session (long tool call, queued turn) must never be stopped, so registration-liveness alone must block takeover; the watcher's arm only defers a pod terminate, a lower-stakes action. Otherwise the tri-state literals, the 2h `EPM_WEDGE_OWNER_RECENT_H` window, and the uncertainty-fails-safe direction are copied unchanged.

## 12. Fail-safe verification (self-check)

If both sessions honestly follow the rule, split-ownership cannot arise: the pivoter provisions ONLY after resolving the owner to literal-DEAD and stopping/unregistering it first, so at the moment the pod is created exactly one session (the pivoter) owns N's compute; on LIVE or UNKNOWN the pivoter never provisions at all, so the owner's single-lane state is untouched. The one race — the owner dying between resolution and provision — degrades to an ownerless pod, which the existing watcher passes already catch; it cannot produce TWO owners.
