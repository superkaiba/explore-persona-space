## Design

**a. WHERE: new `### Step 0.55` in code-reviewer.md, inserted after Step 0.5's section (after ~line 147, before `### Step 0.8` at ~149).**
Rationale: it is a *marker-presence* check (the `marker-shape` family), so it belongs numerically and physically adjacent to Step 0.5, not folded into Step 0.6 — Step 0.6 audits the `## Smoke run` section *inside* the implementation marker and owns the distinct `smoke-run-missing` tag with its own 5c-bis recipe; mixing a different marker's presence check into it would muddle both strip recipes. A separate step also matches the file's one-gate-per-step pattern (0.5/0.6/0.65/0.67 each have their own header, FAIL template, and Step 0.7 enumeration slot). The file already interleaves step numbers out of order (0.5, 0.8, 0.6...), so insertion after 0.5 is least surprising.

**b. HOW the reviewer reads it: canonical task state, presence-on-task (NOT per-round).**
The check is: `uv run python scripts/task.py view <N> --json` (main events.jsonl — same stale-worktree caution as Step 0.5 ~lines 108–111 and 5c-bis ~lines 2105–2111) and confirm **at least one** `epm:smoke-architecture-check` events row exists with a parseable `verdict:` line. Per-round semantics would false-FAIL every fix round: experiment-implementer.md mandates the marker once, at pre-flight ("BEFORE you EXIT this pre-flight phase", ~line 100), and nothing instructs re-posting on `epm:experiment-implementation v2+` fix rounds; Step 6d.0 likewise adjudicates the *highest-version* row. Presence-on-task exactly catches the #811 class (zero rows across 5 rounds) with no resume/re-review false positives. The blocker body MUST name `epm:smoke-architecture-check` — that string is the orchestrator's 5c-bis disambiguation key (decision c).

**c. Blocker tag: REUSE `marker-shape`** (per the task body).
A new tag would grow the mechanical-contract set, forcing edits to the always-on CLAUDE.md enumeration ("every blocker tagged `marker-shape`, `smoke-run-missing`, or `git-provenance`"), the 5c-bis set definition (~2098), the cap-strip set (~2264), and the Blocker-tags parse line — higher blast radius for zero semantic gain. Reuse requires ONE disambiguating edit: the 5c-bis `marker-shape` recipe (SKILL.md ~2114) currently verifies only the implementation marker's (a)–(d) H3s, so an orchestrator receiving a Step 0.55 FAIL would check the wrong artifact, find it conforming, and **wrongly strip a true-positive FAIL** — silently reproducing #811. Exact wording addition (diff sketch below): the recipe branches on whether the blocker body names `epm:smoke-architecture-check`; if yes, the structural fact checked is "a separate `epm:smoke-architecture-check` events row exists in canonical task state with a `verdict:` line matching `PASS_UNIFIED` | `PASS_CANARY canary_cell=<id>` | `FAIL_NO_CANARY`" — present + parseable → STRIP (false positive, e.g. stale-worktree read); absent/unparseable → leave the FAIL (gate doing its job).

**d. Presence-only + verdict-line parseability; a present `FAIL_NO_CANARY` is NOT a reviewer FAIL.**
Rationale (one line): `FAIL_NO_CANARY` routing is a plan-level bounce owned by the orchestrator's gate id=10 (Step 6d.0 → re-plan, round counter frozen) — reviewer double-adjudication would burn a cap-5 review round on a planning-scope defect and create conflicting routing. The reviewer notes a present `FAIL_NO_CANARY` as a CONCERNS bullet. A marker present but with NO recognizable verdict line is genuine absence of the contract evidence → FAIL (same "absence, not cosmetics" logic as Step 0.5 ~lines 101–121).

**e. Scope guard: `type:experiment` only**, stated in the step header exactly as Step 0.6/0.65/0.67 do ("(`type:experiment` only)"). Infra/survey code paths post `epm:results` and have no smoke-architecture mandate.
