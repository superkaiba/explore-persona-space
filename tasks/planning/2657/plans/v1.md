# Plan — #2657: stop counting the single-flight ledger refresh toward `EPM_GATE_FLEET_MAX`

## 0.0 TL;DR (plain English)

- **What I'll change:** the Step 9c fleet probe (`probe --fleet`) will still *list* a live ledger refresh in its output, but will stop *counting* it toward the 2-contender cap that decides whether a session may launch its test gate. One counting predicate changes in `scripts/step9c_baseline.py`; the refresh's own one-at-a-time lock is untouched.
- **What I expect:** a session whose own (or anyone's) background ledger refresh is running no longer loses half its contender budget for ~77 minutes — the #2654 shape (refresh + one real foreign gate = deadlock until the refresh dies) exits 0 instead of burning the full arbitration wait.
- **What would change my mind:** if two *real* foreign gate runs plus a refresh stopped triggering the cap (they must still exit 3), or if any change made the fleet probe able to exit 2 at runtime (that would spin the sanctioned until-loop forever). Both are pinned by tests before the fix ships.

## 3. Decision: direction 3 (list, don't count), directions 1/2/4 rejected

**Direction 3 taken.** Position on the brief's challenge ("removes the refresh from the cap for EVERY caller — is that wrong?"): No, and that is the point. Three arguments:

1. **The lock already provides the bound the cap would.** The cap's purpose is bounding N concurrent full-suite gate runs melting the VM. Refresh concurrency is structurally <= 1 fleet-wide (`LOCK_EX|LOCK_NB`, `:1494`); counting it can never prevent a second refresh, only starve gates. Post-fix worst-case concurrent heavy pytest load = `EPM_GATE_FLEET_MAX` gates + at most 1 refresh — a state the fail-open arm (`cap-expired ... launching over cap`, `13-step-9.md:3239-3242`) can already produce today. The fix removes only a guaranteed-wasted 2700 s wait, never a protection.
2. **The foreign-refresh case is the decisive one.** A session with no refresh of its own *also* loses half its budget whenever ANY session's refresh is live (~77 min per kick). Directions 1/2/4 fix only the self-kicked case; direction 3 fixes both.
3. **The slot-holder frequently converts to nothing:** three recorded `refresh pytest timed out ... NO ledger write` events in `logs/step9c_baseline_refresh.log`, and the compare's authoritative classifier is the per-node pristine-scratch oracle, not the ledger — the refresh output is advisory for the very gate it blocks.

**Direction 1 rejected:** attribution needs argv plumbing (a `--kicked-by <N>` tag + a new capture group in the signature union + editing the kick bash block), is legacy-incompatible with in-flight refreshes, and still counts the refresh against every OTHER session — it does not fix argument 2. **Direction 2 rejected:** the incident needs BOTH `<N>` and `refresh` excluded, which a single-valued `--exclude-issue` cannot carry; making it repeatable/adding `--exclude-refresh` at five prose call sites unconditionally is behaviorally identical to direction 3 but with more surface plus the brief's silent-under-count risk when passed unowned. Direction 3 puts the semantics in ONE place (the probe), and — bonus — the pinned `FLEET_PROBE_FORM` command stays byte-identical, so the five call sites need no command change. **Direction 4 rejected:** fixes only the self-contention ordering, adds temporal state ("is a relaunch pending?") to prose recipes, delays ledger freshness for the next session, and is unnecessary once 3 lands (the refresh no longer contends with anything).

**#2563 coexistence:** this change touches only `_cmd_probe_fleet`'s counting predicate + documentation. `_probe_matches`, the per-issue `probe --issue N` form, and the exclusion classes #2563 will need (watcher-argv exclusion at the scanner layer) are untouched — orthogonal filters at different layers; nothing here forecloses that fix.
