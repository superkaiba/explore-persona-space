# Plan v2 — #2143: bare-API blinded-read recipe as a rule

`kind: infra` · workflow-surface prose + one lint constant · 0 GPU-h.

## Requirement + acceptance criteria

**Requirement.** Capture the converged bare-API blinded-read packet recipe as a
durable rule, so the next blinded/unprimed qualitative read starts from the
converged design instead of re-deriving it through user corrections. Today the
pattern lives only in one session's script; three separate user corrections were
needed in #1482 before it converged (the first round leaked SEVEN setup facts to
the readers).

**Acceptance criteria.**

1. A rule states the recipe with the four elements the task body names:
   content-only packets; readers get no filesystem/repo/tool access; the blinding
   key is frozen to a file before any read; the brief enumerates what the reader
   may NOT be told (task, arms, selection rule, metric).
2. `scripts/issue1482_blind_read_api.py` is named as the precedent.
3. The rule is reachable at the moment of need — i.e. it carries a LESSONS index
   row whose trigger fires when someone is about to dispatch a blinded read.
4. `uv run python scripts/workflow_lint.py` (no flags) is clean on the touched
   files, `--check-lessons-index` included.
5. The Step 9c mapped-test selection passes.

## Decision: a new rule file, not a bullet in `llm-judging.md`

The body enumerates two placements. **Decision: new `.claude/rules/blinded-reads.md`
+ a LESSONS index row**, because of trigger fidelity — the deciding factor, not
taste.

`llm-judging.md`'s own index trigger is *"a plan/code designs/writes an LLM-judged
behavior DV (graded 0-100 primary; one Sonnet judge; …)"*. A blinded qualitative
read is **not** a behavior-expression DV: #1482's read asked subagents to
describe the difference between two opaque feature groups in a paragraph — no
score, no rubric, no DV. So a bullet placed there would sit behind a trigger that
structurally does not fire at the moment of need, which is precisely the failure
this task exists to prevent. A rule nobody loads is not a rule.

Cost of the chosen option is one always-on index row (~150 B); the rule body
itself stays on-demand. The declared `workflow_fix_target`
(`.claude/rules/llm-judging.md`) is still honored — it gets a one-line
cross-pointer (§ diffs, file 4), so a reader who arrives via the judging trigger
is routed to the rule. That satisfies the target without putting load-bearing
content behind the wrong trigger.

## Finding: the body's "via the API dispatcher" wording contradicts its own precedent

The task body says packets are "sent via the API dispatcher". The named precedent
does the **opposite, deliberately** —
`scripts/issue1482_blind_read_api.py:198-208` carries an
`API_DISPATCH_ROUTING_EXEMPT` comment with two stated reasons: (1) auditability is
the whole point (it persists the exact request next to the response, and an
interposed routing layer that may switch org/key, add headers, or retry breaks
the one-to-one correspondence between the composed request and the sent bytes);
(2) the beta path `client.beta.messages.create(betas=...)` has no equivalent in
`llm/api_dispatch.py`, which exposes no `betas` parameter — and packets carrying
full conversations run past a 200k window (~298k input tokens for #1482's
context+answer pair).

**Resolution: the rule states the doctrine as the precedent actually implements
it** — bare client for a single-call auditable read, with the exemption comment
naming both reasons; and if a blinded read ever becomes a volume path, route it
through the dispatcher *and* preserve auditability another way (persist per-call
request bytes), never silently drop the audit. Writing the body's wording
verbatim would ship a rule that contradicts the file it cites as precedent. This
is a wording correction inside the task's own stated intent (the intent is "the
converged pattern"), not a scope change; recorded here so it is auditable.

Two further elements the precedent carries that the body's four-element list does
not mention, and that are load-bearing enough to include (each was a correction
cost in #1482):

- **the scope-aware outbound leakage scan** — one ban list over the whole request
  cannot serve both scopes, and this is the specific thing the early rounds got
  wrong;
- **fail-loud non-answer handling** — a refusal returns ~0 tokens, so persisting
  it leaves an empty file that reads downstream as "the model had nothing to say"
  rather than "the call never produced a read".

## File paths + concrete diffs

Four files. Ordering is load-bearing: **file 3 before file 2** (see § Ordering).

**1. `.claude/rules/blinded-reads.md` (NEW, ~70-85 lines).** Sections:

- *Load when* — you dispatch a blinded / unprimed qualitative read: any read whose
  value depends on the reader not knowing the setup (arms, which side is which,
  the selection rule, the ranking metric).
- *The default: bare API, not a subagent* — a subagent has a filesystem, tools,
  and the repo, so blinding rests on instructions the reader can ignore ("do not
  open key.json", "do not search the repo") plus the packet text not leaking. A
  bare API call removes the question: no tools, no filesystem ⇒ the only thing the
  reader can condition on is the bytes in the request.
- *The four elements* — content-only packets (item text + neutral tags + the
  question; no system prompt, no project context, no file paths, no criterion
  name, no item type; packets open neutrally like `# Group A` / `100 items.`);
  no reader tools; blinding key frozen to a file before the first packet is sent
  (so the mapping cannot be reconstructed post-hoc to fit the answer) with the key
  filename on the outbound ban list so it can never travel in a request; and the
  brief enumerating what the reader may NOT be told — task, arms, selection rule,
  metric — as an explicit list.
- *Scope-aware outbound leakage scan (fail-loud, no skip flag)* — WRAPPER (tags +
  question, orchestrator-written) held to a WIDE criterion-vocabulary bar,
  ordinary English included; PAYLOAD (the opaque packet — feature descriptions,
  real conversation text) held to PROJECT-IDENTIFIER-ONLY. One list over the whole
  request cannot serve both: banning `r2`/`predicted` inside real conversation
  text refuses every send.
- *Persist the exact request next to the response* — the `.request.json` audit
  sidecar (verbatim outbound request + char counts, model/max_tokens/temperature,
  `system_prompt: None`, `tools: None`, both scan scopes with ban lists + hits,
  stop_reason, usage). Blinding you can verify beats blinding taken on trust.
- *Not the dispatcher, for a single-call read* — both exemption reasons, plus the
  volume-path escape above.
- *A non-answer is never persisted* — `stop_reason != end_turn` ⇒ fail loud, write
  nothing; `max_tokens` ⇒ raise the cap and re-run; `--model` exists only for
  refusal-ladder rung (b2), since identical bytes to another model is the only way
  to tell a content-driven refusal from a model-pathway-specific one.
- *Files of record* — `scripts/issue1482_blind_read_api.py`, #1482, #2143.

### Ordering (load-bearing)

`.claude/hooks/guard_lessons_edit.sh` is a PreToolUse(Edit|Write) guard that
blocks any LESSONS.md edit whose prospective post-edit content would FAIL
`check_lessons_index`. Its helper imports the **edited tree's** copy of the lint
first, so a same-diff constant bump is honored. Therefore: **bump
`_LESSONS_MAX_BYTES` (file 3) BEFORE editing LESSONS.md (file 2)**, or the guard
blocks on the byte cap. No escape hatch is needed and none is to be used —
neither `EPM_ALLOW_LESSONS_EDIT=1` nor the `allow-lessons-edit` sentinel; if the
guard blocks, the constant bump is missing or wrong, which is a real signal.

Index parity is bidirectional, so the new rule file and its row must land in the
same change or the lint FAILs both ways (orphan file / dangling row).

### Explicit scope boundaries (deliberate non-goals)

- **No new mechanical lint check.** "Was this read properly blinded?" is not
  mechanically decidable from a diff; the load-bearing mechanism is the trigger
  row that makes the rule load at the right moment. Adding a check would be scope
  creep past the body's "one short rule".
- **`scripts/issue1482_blind_read_api.py` stays untracked.** It is referenced as
  the precedent only; **#2076 owns its lint routing.** This task must not `git add`
  it — doing so would take on another task's scope and its lint consequences.
- **No edits to `#1482`'s task body**, and no changes to `api_dispatch.py`.
