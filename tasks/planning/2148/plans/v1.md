### 0.0 TL;DR (plain English)

Upload-verification currently proves that the FILES a run wrote are all present (#537 per-file git diff, #2187 out-root name-set diff) and that a producer's own count field matches what was asked for. It never opens the files. On #2091 that let a store pass while ~25% of the rows inside those present files were never written: every file was there, byte sizes matched, and the count check compared the producer's self-reported `capture_rows` — which was literally the EXPECTED number copied out of the input manifest — against that same expectation, so it could not fail. This task adds the missing arm: count what is REALLY in the row-index files on HF, compare it against the input-side declaration, and FAIL on a shortfall. A producer's own count is reported for context and is never the quantity the gate is decided on.

Measured at plan time, the decisive design fact: in the healthy (post-repair) #2091 store the realized row-LINE count is 2048 against an expectation of 2000, because rows are per-rollout and the repair shard overlaps — while the distinct `context_id` count is exactly 2000. So the gate quantity is the distinct count of a caller-declared row key, with the raw line count and per-shard breakdown reported alongside. A line-count gate would have false-FAILed every repaired store.

### 1. Goal

Verbatim from the task body: **Make per-issue upload-verification reconcile REALIZED artifact contents, so a store that is short INSIDE its files cannot pass.**

Two words are load-bearing. **REALIZED** — the quantity read out of the artifact's own bytes, never a field the producer wrote about what it believes it wrote. **cannot** — a spec step alone is skippable, so the gate needs the mechanical arm (Layer 1) plus the attestation token (Layer 2) that makes a skipped sweep block teardown, exactly as #2187 made the out-root sweep unskippable.

Three consequences that shape §4:

1. **The raw LINE count cannot be the gate quantity.** A healthy repaired store holds 2048 lines against an expectation of 2000 (rows are per-`rollout_k`; the repair shard overlaps, and the manifest carries its own `n_duplicate_rows` field). A `realized_lines == expected` gate would FAIL all three healthy jobs. 2. **The producer's self-reported field is wrong in BOTH directions across this artifact's history** — pre-repair `capture_rows` over-reported (echoing `n_rows`=2000 for a 1552-line store), and post-repair the manifest's own `n_rows_captured` UNDER-reports (1488 against 2000 realized distinct contexts, stale since the repair). No producer field is a safe gate quantity; both are worth REPORTING, and a self-reported-vs-realized disagreement must not by itself flip the verdict (a legitimately repaired store carries a stale field).

### 4. Design

**Why code, not a model call:** deterministic counting and set arithmetic over JSONL lines; an LLM judgment would add nonzero false-PASS probability to a durability gate. Behavior-implantation / on-policy / persona-vectors / data-realism / contrastive-negatives / measurement-validity requirements: N/A — no model training, no generation, no eval data, no DV in this task. Embedded-shell exit-path trace: N/A — no multi-arm embedded shell blocks introduced.

**(A) `scripts/verify_uploads.py`** — the mechanical core, mirroring `check_outroot_residue`'s structure (two input modes, fail-loud missing input, ERROR flips the overall verdict via the existing aggregation at `verify_uploads.py:1847`).

New CLI surface (all additive; absent ⇒ SKIP):

- `--expected-rows LABEL=N` (repeatable) — the INPUT-side declaration per job/label. This is the gate's right-hand side.
- `--row-index-hf-prefix PREFIX` (repeatable) — HF data-repo prefixes to enumerate. Deliberately NOT defaulted from `--hf-prefix`: the residue check's prefix set means "everywhere the run wrote", which is a different quantity, and a silent inference here would be exactly the convenient-affordance defect this task exists to remove.
- `--row-index-local-root DIR` — local/pod-side mode (the second input mode, mirroring `_outroot_disk_entries`; also what makes the check unit-testable without HF).
- `--row-index-glob PATTERN` (default `row_index*.jsonl`).
- `--row-index-distinct-key FIELD` — the row key whose DISTINCT count is the primary gate quantity (e.g. `context_id`).
- `--self-reported-rows LABEL=N` (repeatable) — a producer count field, REPORTED for context, never gated on.
- `--realized-rows-exempt GLOB` (repeatable) — exemption for legitimately-partial classes.
- `--row-index-max-bytes N` (default 16_000_000) — bounded-cost guard, evaluated against the TREE-LISTING size before any download.

Mechanics:

1. **Enumerate** each prefix with `list_repo_files_complete(..., path_in_repo=<prefix>)` (`verify_uploads.py:1347` already imports it; server-side scoped, 504-retrying — the #833 recipe). One listing per prefix. Sizes come from the tree entries, so the byte cap gates BEFORE any fetch.
2. **Attribute** each matched index file to a label by PATH-COMPONENT match (the label appears as a full `/`-delimited component, or as a component prefix followed by a non-word boundary) — never a bare substring, which would let `syc_aita` swallow a hypothetical `syc_aita_v2`. This mirrors `filter_issue_scoped_git_paths`' component-boundary discipline (`verify_uploads.py:1288`) and its digit-boundary lesson. A label matching ZERO files ⇒ ERROR `row-index-missing`; a matched file attributed to NO label ⇒ ERROR `row-index-unattributed`. Both fail-loud rather than shrinking a denominator.
3. **Fetch + count** each attributed file via `hub.stage_hub_file` (retried, atomic, fail-loud — `hub.py:2649`), counting non-empty lines and, when `--row-index-distinct-key` is given, the distinct values of that field (a row missing the key ⇒ ERROR, never skipped).
4. **Verdict lattice** (per label; `distinct` mode = key declared):

   | mode | condition | verdict + tag |
   |---|---|---|
   | distinct | `distinct < expected` | **FAIL** `realized-rows-short` |
   | distinct | `distinct > expected` | **FAIL** `realized-rows-unexpected-surplus` |
   | distinct | `distinct == expected` | OK |
   | no key | `lines < expected` | **FAIL** `realized-rows-short` |
   | no key | `lines >= expected` | **WARN** `realized-rows-no-distinct-key` |

   The no-key `>=` branch is WARN, not OK, because #2091's own healthy store shows lines legitimately exceeding the expectation — so without a key an equality or surplus is uninformative about a shortfall, and the detail names the flag that would resolve it. Every verdict detail — OK, WARN and FAIL alike — carries expected / realized-distinct / realized-lines / `lines − distinct` duplicates / the per-shard breakdown / the self-reported value labeled `producer self-reported (context only)`. A self-reported-vs-realized disagreement appends a `producer-field-mismatch` note to the detail and NEVER flips the verdict on its own (consequence 2 above).
5. **SKIP / ERROR** exactly as `check_outroot_residue`: neither `--expected-rows` nor a prefix/root ⇒ SKIP with a detail naming the flags; a nonexistent local root, an unreadable listing, or a Hub listing failure ⇒ ERROR (a missing input must never read as a clean zero — this check exists to close a false-PASS).
