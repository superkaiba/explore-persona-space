### 4.1 Method delta vs Patterns A-E

**New Pattern F — phrase-anchored "listing (re-)verified" count, any position in the paren after the link.** The precision anchor is the PHRASE, not the position (Pattern C's design philosophy, #1088): a count-noun immediately followed (modulo one separator token) by "listing verified" / "listing re-verified" asserts the writer verified the LINKED listing — a whole-prefix semantic. A sub-scoped clause count ("analysis_tensors: 16 files; …") carries no such phrase and stays invisible; the per-`<word>` distributive family is excluded structurally by adjacency (`files` must be followed by `listing`, so "files per namespace, listing verified" cannot match — the same mutual-exclusion-by-adjacency argument C's comment makes for "files per namespace at the pinned revision").

Anchor + decline rules:

| Rule | Behavior | Mirrors |
|---|---|---|
| Phrase anchor | `files` + one optional separator (`,` `:` en/em-dash `-`) + `listing (re-)?verified` | Pattern C phrase anchoring (#1088) |
| Files-only | shards never bind via F ("N shards, listing verified" = documented sacrifice) | Pattern C files-only (~L8687) |
| Per-`<word>` | excluded by adjacency (no lookahead needed; documented + tested) | C's adjacency argument (~L8683-8688) |
| B-adjacency decline | paren immediately followed by an HF markdown link → F declines entirely (B may extract the paren-OPENING count with the following link's scope) | Pattern E's `_HF_LINK_FOLLOWS_PAREN_RE` decline (#1422). Deliberate divergence from C (which predates #1422 and is grandfathered): new patterns adopt the decline. |
| Clause-crossing | `;` not in the separator class → "16 files; listing verified" never binds across the clause boundary | new (documented sacrifice) |
| Dedup | shared `seen` key `(count, noun-singular, repo, sha, prefix)` collapses C+F and E+F co-fires | the C+E collapse note (~L8952-8956) |

### 4.2 Regex sketch (new, placed after `_FILES_AT_PINNED_REV_RE` at ~L8697, with a Pattern-F comment block in the house style)

```python
# Pattern F (#1505, the #1072 footer shape): a count-noun ANYWHERE inside the
# paren immediately AFTER the pinned link whose count is immediately followed
# (one optional , : en-/em-dash / hyphen separator) by the listing-verification
# phrase — `…; logs — 44 files, listing verified live at write time` /
# `(40 files, listing re-verified live at write time via `list_repo_tree` …)`.
# The PHRASE, not the position, is the precision anchor (Pattern C philosophy):
# a sub-scoped clause count ("analysis_tensors: 16 files; …") carries no such
# phrase. files-only (C parity); `;` deliberately NOT in the separator class
# (a claim never binds across a clause boundary); per-`<word>` distributive
# counts are excluded by adjacency (the phrase must directly follow `files`).
_FILES_LISTING_VERIFIED_RE = re.compile(
    r"\b(?P<count>\d{1,3}(?:,\d{3})+|\d{1,6})\s+files?"
    r"\s{0,2}[,:–—-]?\s{0,2}"
    r"listing\s+(?:re-?)?verified\b",
    re.IGNORECASE,
)
```

Verified this session against the live texts: matches `44` on the incident paren and `40` on the corrected paren; does NOT match "analysis_tensors: 16 files; …", "logs — 44 files, verified at write time" (no "listing"), "44 files per namespace, listing verified", "44 files listed per namespace".

## 11. Decision Rationale

- **Phrase anchor `listing\s+(?:re-?)?verified`** — What: the F precision anchor. Why: both observed #1072 variants carry it verbatim ("listing verified live at write time" / "listing re-verified live at write time"); a verification-of-listing phrase is pragmatically a whole-prefix claim. Source: incident #1072 (both texts measured this session) + Pattern C's phrase-anchor design (#1088/#833, `_FILES_AT_PINNED_REV_RE` ~L8693).
