# Plan — #2152: Rule-26 judge pilot gate must exercise the same TRANSPORT as the wave it gates

### 0.0 TL;DR (plain English)

- **What I'll run:** No experiment — this is a code + rule-text fix. I'll teach the judge pilot gate (`judge_pilot_gate`) to run its ~200 test calls over the *same delivery path* (the slow-but-cheap Batch API vs the direct sync API) that the big production wave will use, because the two paths can fail differently. The caller tells the gate how the wave will dispatch; the gate forces the pilot onto that path, records which path both actually use, and fails loudly if they differ. Two hardenings from review: the gate now *refuses up front* (a fail-fast error, before spending anything) any wave declaration whose delivery path would be decided by a live rate-limit probe at dispatch time — a path the pilot structurally cannot certify — telling the caller to pin the path explicitly; and a pilot that served any of its draws from a warm cache fails as unverifiable, because cached draws prove nothing about the delivery path and (being refusal-free by construction) water down the very refusal rate the gate checks. I'll also make the gate fail on a high API-side refusal rate — the exact failure that destroyed a third of #1739's 44,310-call wave after a pilot on the wrong path had passed.
- **What I expect:** All 16 existing caller scripts keep working unchanged (they just get a new warning that they didn't declare the wave's path); new offline tests pin the forcing, the recording, the mismatch failure, the fail-fast refusal, the cache-served failure, and the refusal-rate failure; the rule text (rules 26 + 28) now says transport is part of "the exact production instrument".
- **What would change my mind:** If reading the realized path back from the persisted judge output turns out to be unreliable (e.g. the routing record is missing in legitimate runs), I'd fall back to trusting the forced parameters instead of the read-back — the design prefers the read-back because it is ground truth for the dispatched remainder, and the tests will tell us if that assumption breaks.

```python
def _wave_routing(wave_n_calls, wave_threshold_base, wave_force_sync) -> RoutingDecision:
    """Compute the DECLARED wave's transport via the dispatcher's own pure routing rule.

    REFUSES (ValueError) any declaration whose realized route would depend on the
    dispatcher's live OTPM probe (judge_dispatch.py:1652 probes iff
    not force_sync and 0 < n_items < threshold_base * 2): an unpinned count-routed
    wave inside that region routes on a value the gate cannot observe at pilot
    time, so no pilot can certify it (#2152 MF-1). Outside the region
    (n >= 2*tb) the route is deterministic batch (no probe; effective threshold
    at the assumed divisor equals tb, and n >= 2*tb > tb).
    """
    tb = DEFAULT_THRESHOLD_BASE if wave_threshold_base is None else wave_threshold_base
    if wave_force_sync or tb == 0:
        # Pinned: deterministic regardless of count and OTPM.
        return decide_route(
            wave_n_calls if wave_n_calls is not None else 1,
            threshold_base=tb, force_sync=wave_force_sync,
        )
    if wave_n_calls is None:
        raise ValueError(
            f"wave transport is count-routed at threshold_base={tb}: declare wave_n_calls, "
            "or pin the wave (wave_threshold_base=0 forces batch / wave_force_sync=True forces sync)"
        )
    if wave_n_calls < 2 * tb:
        raise ValueError(
            f"wave routing is OTPM-PROBE-DEPENDENT at dispatch (wave_n_calls={wave_n_calls} < "
            f"2*threshold_base={2 * tb}: the dispatcher probes live OTPM there, "
            "judge_dispatch.py:1652) and cannot be certified by any pilot — pin the wave "
            "transport: wave_threshold_base=0 (forces batch) or wave_force_sync=True (forces "
            "sync), with the SAME pin on the production dispatch (#2152)"
        )
    return decide_route(wave_n_calls, threshold_base=tb)  # n >= 2*tb: deterministic batch
```

Default-tb arithmetic (why the common case needs no pin): every rule-26-covered wave is ≥ ~5,000 calls, and at the client default `threshold_base=2,000` the refusal boundary is 4,000 — so any ≥5,000-call count-routed declaration sits at `n ≥ 2·tb`, deterministic batch, no probe, no pin. The refusal fires exactly on the shapes the pilot cannot certify: small count-routed waves (the old "declared sync by count" case — sync certification now REQUIRES the `wave_force_sync=True` pin) and large-`tb` declarations like the verified counterexample `(wave_n_calls=5,000, wave_threshold_base=20,000)`, where the assumed-otpm route (sync) flips to batch under a probed otpm=90k (effective 4,500 ≤ 5,000).

Gate-entry validation (fail loud on ambiguity/contradiction/typos, all BEFORE any dispatch): `wave_declared = wave_n_calls is not None or wave_threshold_base is not None or wave_force_sync`; if `wave_declared and threshold_base is not None` → `ValueError` ("pass EITHER the legacy pilot routing knob threshold_base OR the wave declaration — the declaration derives the pilot's routing, #2152"); `wave_force_sync and wave_threshold_base == 0` → `ValueError` (contradiction); `wave_n_calls is not None and wave_n_calls < 1` → `ValueError`; the two `_wave_routing` refusals above (count-less count-routed; probe-region unpinned); `api_refusal_threshold <= 0` → `ValueError` (mirrors the `parse_fail_threshold` guard); unknown names in `waive_api_refusal_arms` → `ValueError` (mirrors `waive_parse_fail_arms`).

### 11. Decision Rationale

`N/A — no model training` (no training hyperparameters). Load-bearing DESIGN choices, each with Source:

- **D1 — Mechanism: thread the wave's dispatch parameters into the gate (chosen) vs a small dedicated batch-path probe beside a sync pilot (rejected).** What/Why: the pilot's job is the DROP PROFILE, and the profile must be measured on the wave's transport — a side probe would be a second instrument whose draws feed none of the gate's parse-fail/truncation/refusal statistics, certifying the profile on the wrong path; a full pilot on the wave's transport is strictly more informative at the same or lower cost (Batch is 50% cheaper), and splitting the budget across two transports would halve per-arm draws and break the #2124 sizing arithmetic (51-draw floor). Cost: batch-pilot latency (minutes–hours turnaround) — accepted as the price of parity. The request-SHAPE probe niche is already served by the #763 forced-batch live smoke. Source: #2124 (sizing arithmetic), #763 gotcha (existing shape-probe), #1739 (the profile-on-wrong-transport miss). Alternatives: both (redundant — the threaded pilot IS a batch-path probe); probe-only (rejected: certifies shape, not profile).
