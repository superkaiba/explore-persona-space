## 0.0 TL;DR

- **What I'll change:** `RunPodBackend.launch` gains a launch leg that, when the caller opts in, SSHes into the freshly provisioned pod, syncs the clone to the run's branch, and starts the workload detached (setsid + nohup + pidfile + log), verifying the process is alive before returning. The automated GCP→RunPod failover paths opt in automatically (they have no experimenter); the interactive `/issue` flow is byte-unchanged (its experimenter stays the executor).
- **What I expect:** the #763 failure shape (healthy-looking pod running nothing after a `--workload-cmd` RunPod launch) becomes impossible on the failover paths, and a manual launch either executes or fails loudly with `workload_executed: false` visible in the JSON.

## 1. Goal / requirement + acceptance criteria

Make the RunPod lane capable of executing `spec.workload_cmd` on the pod it provisions, without double-launching against the experimenter-driven interactive flow, and fail LOUD when a requested execution did not start.

**Resolution of the required design question (hard constraint 4).** The brief's suggested rule "execute iff `spec.workload_cmd` is set; the experimenter flow passes none" is **FALSE as stated** — verified: `dispatch_issue.py::main()` (lines 1722–1733) requires exactly one of `--workload-cmd` / `--hydra` on every `launch`, and SKILL.md Step 6b (lines 2870–2873) mandates passing the plan's launch command via `--workload-cmd` on ALL lanes, after which Step 6d.1 (SKILL.md 3237–3241, 3352+) spawns the experimenter to execute it on RunPod pods. So on the interactive lane, `RunPodBackend.launch` DOES receive a non-empty `workload_cmd` today, and unconditional execution would double-launch. The clean rule is therefore:

> **Execute iff `spec.workload_cmd` is non-empty AND `spec.extra["execute_workload"]` is truthy.** The opt-in is set (a) automatically inside `router.failover_to_runpod_after_async_workload_crash` — the single seam all four automated no-experimenter failover paths funnel through (async GCP crash `_failover_dead_gcp_to_runpod`, FLEX_START queue timeout, RunPod no-port wedge, CUDA-IMA — all call it via `_relaunch_fresh_runpod`, backend_poll.py:1428) — and (b) explicitly via a new `dispatch_issue.py launch --execute-workload` flag for manual/orchestrator failover-style launches. The interactive Step 6b/6d.1 flow passes no flag and is behavior-unchanged (experimenter remains the sole executor there; no SKILL.md change needed). Sync route()-time RunPod outcomes (capacity fallback `auto_fallback_runpod`, sync `gcp_workload_failover_runpod`) happen inside a live `dispatch_issue.py launch` call where the orchestrator has Step 6d.1 downstream — they correctly stay opt-out.

Additionally verified: NOTHING executes the workload on the fresh pod after an automated failover today (no SKILL.md handler exists for `gcp_workload_failover_runpod_async` / the wedge fresh-pod phases — grep returned zero hits), so the failover paths are the primary consumer, exactly as the clarify note says.

**Acceptance criteria (numbered, testable):**

1. With `workload_cmd` set + opt-in: `launch()` provisions, syncs the pod clone to `spec.extra["repo_branch"]` (default `main`) with a pod-side `HEAD == FETCH_HEAD` verification (never trusting pull stdout), ensures `/workspace/logs` exists, writes `/workspace/launch_issue_<N>.sh`, detaches it via `setsid nohup bash <launcher> > <log_path> 2>&1 < /dev/null &`, and — from a SEPARATE SSH invocation — verifies the pidfile PID is alive and the log exists. The returned handle's `extra` carries `workload_executed: true`, `workload_pid`, `launcher_path`, `repo_branch` (plus all existing keys).
2. Without opt-in: zero SSH execution calls (test-pinned); handle `extra` is today's shape plus additive keys `workload_executed: false` + `repo_branch`; a one-line log WARNING states the workload was persisted but not executed and names the two executors (experimenter Step 6d.1, or `--execute-workload`).
3. Any start failure (branch-sync mismatch, missing pods.conf row, dead PID, missing log) raises a typed `RunPodWorkloadStartError` whose message names the pod, log path, and a log tail; `dispatch_issue.py launch` surfaces it as one JSON line `{ok: false, failure_class: "infra", reason: "runpod_workload_start_failed", note: ...}` + exit 2 — never `ok: true` on a provision-only result when execution was requested.
4. `failover_to_runpod_after_async_workload_crash` sets `execute_workload` on any custom-workload spec it dispatches (test: fake backend records the spec it received).
5. `repo_branch` persists into BOTH lanes' handle `extra` (runpod.py launch; gcp.py handle-extra dict at gcp.py:3908–3952) and round-trips through both reconstructors (`_runspec_from_runpod_handle` backend_poll.py:1282, `_runspec_from_gcp_handle` backend_poll.py:2189) into `RunSpec.extra["repo_branch"]`.
6. `--execute-workload` threads to `spec.extra` via `_launch_extra_from_args`; the launch success JSON gains `workload_executed`, `workload_pid`, `log_path`.
7. The pod never shells `scripts/task.py` (remote scripts contain no `task.py`; `tests/test_no_pod_side_task_py_shellout.py` green); `tests/test_router.py` invariants (RunPod-last-rung, no-auto-runpod, ladder order) and the GCP startup-script byte-identity snapshot stay green (the handle-extra addition does not touch `render_startup_script`).
8. Hydra-args RunPod runs (`workload_cmd == ""`) are untouched — the execution leg no-ops; a failover of a hydra RunPod run remains experimenter-relaunch territory (named residual, §6).

- **SLURM lane** (`backends/slurm.py`): renders the custom stage into the sbatch. Reference only.
- **Experimenter launcher** (`.claude/agents/experimenter.md` § During Execution, lines 736–785): the canonical pattern — launcher script at `/workspace/launch_issue_<N>.sh` with `set -uo pipefail`, PATH export, `cd /workspace/explore-persona-space`, `set -a; source .env; set +a`, `echo $$ > /workspace/logs/issue-<N>.pid`, then the command; detached via `setsid nohup bash <launcher> > <log> 2>&1 < /dev/null &`; liveness verified from a separate SSH invocation. **Reused as the launch-leg contract** (one deliberate delta: no `exec` before the workload line, because `workload_cmd` is an arbitrary shell line possibly carrying env-var prefixes, which `exec` cannot take — the pidfile then holds the launcher bash PID, whose liveness tracks the workload; `poll_once` probes liveness, not process identity).
- **SSH transport** (`scripts/pod_lifecycle.py::_restore_uv_on_pod`, lines 644–689 + `bootstrap_pod.sh` lines 35–66): plain `ssh -o StrictHostKeyChecking=no -o ConnectTimeout=15 -o BatchMode=yes -i ~/.ssh/id_ed25519 -p <port> root@<host> '<cmd>'` with host/port from pods.conf. **Reused as the transport** (a small private `_ssh_pod_run` helper in runpod.py mirrors it — NOT a new SSH layer; `~/.ssh/config`-by-name (poll_pipeline style) is rejected because pods.conf is the config SOURCE and the explicit form has the in-file Python precedent).
- **Handle contract** (`backends/runpod.py::launch`, lines 203–321): already persists `workload_cmd`/`hydra_args`/`gpus`/`time_budget_hours`/`pid_file`/`runpod_attempt_id` + the expected-artifacts declaration. **Extended additively.**
- **New:** the execution leg itself (`_execute_workload_on_pod` + three rendered remote scripts), the `execute_workload` opt-in, `repo_branch` persistence/threading, the typed error + dispatch_issue surfacing.

**(a) Branch sync** (one SSH call; fetch+reset, never pull — defeats the silent index.lock and divergent-`.claude/**` traps from gotchas.md):

```sh
set -eu
export PATH="/root/.local/bin:$PATH"
cd /workspace/explore-persona-space
pgrep -x git >/dev/null 2>&1 || rm -f .git/index.lock
git fetch origin "refs/heads/<B>"
git checkout -q -f -B "<B>" FETCH_HEAD
git reset --hard -q FETCH_HEAD
HEAD_SHA=$(git rev-parse HEAD); FETCH_SHA=$(git rev-parse FETCH_HEAD)
[ "$HEAD_SHA" = "$FETCH_SHA" ] || { echo "SYNC-MISMATCH head=$HEAD_SHA fetch=$FETCH_SHA" >&2; exit 3; }
echo "SYNC-OK $HEAD_SHA"
```
VM side parses `SYNC-OK <sha>`; anything else → raise. (Pod-side `reset --hard` is explicitly sanctioned — the VM-tree ban does not apply to the disposable pod clone; the task's diff sketch prescribes exactly fetch+reset.)

**(b) Write launcher + detach** (one SSH call; heredoc write, then the gotchas.md bg-ssh idiom with stdin redirect):

```sh
mkdir -p /workspace/logs
rm -f /workspace/logs/issue-<N>.pid
cat > /workspace/launch_issue_<N>.sh << 'EPSEOF'
#!/bin/bash
set -uo pipefail
export PATH="/root/.local/bin:$PATH"
cd /workspace/explore-persona-space
set -a; [ -f .env ] && source .env; set +a
export REPO_ROOT="${REPO_ROOT:-/workspace/explore-persona-space}"
export WANDB_PROJECT="${WANDB_PROJECT:-issue<N>}"
echo $$ > /workspace/logs/issue-<N>.pid
<workload_cmd verbatim>
EPSEOF
chmod +x /workspace/launch_issue_<N>.sh
setsid nohup bash /workspace/launch_issue_<N>.sh > <log> 2>&1 < /dev/null &
echo "WRAPPER-STARTED $!"
```
(No `[phase=` literal anywhere in these scripts' prose — the experimenter.md phase-token hygiene rule. No stale-sentinel clear needed: `launch` always provisions a FRESH pod with a fresh `/workspace` volume, so no prior `issue-<N>-*.json` can exist; stated as a comment.)

**(c) Verify** (a SEPARATE SSH invocation ~3 s later — per experimenter.md, a same-session probe cannot catch SIGHUP-on-disconnect death):

```sh
PID=$(cat /workspace/logs/issue-<N>.pid 2>/dev/null || true)
if [ -n "$PID" ] && kill -0 "$PID" 2>/dev/null && [ -f "<log>" ]; then
  echo "LAUNCH-OK pid=$PID"
else
  echo "LAUNCH-DEAD pid=${PID:-none}"
  tail -20 "<log>" 2>/dev/null || true
  exit 4
fi
```
VM side parses `LAUNCH-OK pid=<int>`; `LAUNCH-DEAD` / rc!=0 → `RunPodWorkloadStartError` carrying the tail. The pod is left RUNNING for diagnosis (RunPod-as-diagnosis-lane doctrine).

## 10. §11 Decision Rationale (design choices; hyperparameters: N/A — no model training)

- **Execute iff `workload_cmd` set AND `execute_workload` opt-in** — Why: unconditional execution double-launches the interactive lane (verified §1). Source: dispatch_issue.py:1722–1733 + SKILL.md:2870–2873/3237+ + clarify-note design consideration (3); incident #763 (task body).
- **Opt-in auto-set at the async-failover seam** — Why: those paths provably have no executor today; one seam covers all four. Source: router.py:2462; backend_poll.py:1428; compute-backend-failover.md.
- **setsid launcher-script reuse (no new pattern)** — Source: experimenter.md § During Execution (736–785); gotchas.md SSH idioms (stdin redirect; `sh` not bash; uv PATH); brief constraint "reuse/mirror, do NOT invent".
- **fetch + `checkout -f -B` + `reset --hard` + HEAD==FETCH_HEAD, never `pull`** — Why: defeats the silent index.lock exit-0 pull and divergent-`.claude/**` ff-only block. Source: gotchas.md (both pod git-sync entries, incidents #653 r5/r6); task diff sketch ("fetch + reset").
