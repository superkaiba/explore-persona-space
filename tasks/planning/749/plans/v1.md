## 2. Prior work / Context
Incident #658 round 3: an `upload_folder` retry caught 504s on `commit/main`, but a
SEPARATE post-upload `list_repo_files(recursive=True)` verify call hit `/tree/main`
504s on cursor pages 2+; the run crashed rc=1 AFTER successfully committing 12081
files. CAUSE (verified, load-bearing fact): `huggingface_hub.utils._pagination.paginate`
fetches follow-up cursor pages via `http_backoff("GET", next_page, max_retries=20,
retry_on_status_codes=429, ...)` — 429-only, so any 5xx on a cursor page is
un-retried. Confirmed by reading `paginate()` source in the pinned huggingface_hub
(`.venv/.../huggingface_hub/utils/_pagination.py`). `gotchas.md` lines 102-103 +
`upload-policy.md` document the per-file 504-storm and the >10000-files commit cap
but say nothing about pagination's 429-only retry — every HF-upload-heavy script
re-introduces this trap.

## 3. Method delta (exact bullet text — verbatim from task body Proposed change)
```
- **HF recursive tree listing 504s are un-retried.** `list_repo_files` /
  `list_repo_tree(recursive=True)` paginate `/api/.../tree/main?...&cursor=...`;
  `huggingface_hub.utils._pagination.paginate` retries ONLY 429 on follow-up
  cursor pages (`http_backoff(..., retry_on_status_codes=429)`), so a 504 on
  any cursor page propagates straight through, even when the upload itself is
  retry-wrapped. Wrap any post-upload verify listing on a large repo in the
  SAME transient-5xx retry as the upload (#658).
```
