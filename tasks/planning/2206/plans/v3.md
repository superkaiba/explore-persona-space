# Plan: #2206 — api_dispatch must not convert a text-block-free API response into an empty-string SUCCESS

## 0.0 TL;DR (plain English)

- **What I'll change:** I'll make the shared Anthropic-dispatch library treat a model response that contains no text (thinking-only output, a safety refusal with empty content, a budget exhausted before any text) as an explicit typed FAILURE record instead of silently recording an empty string as a success — at both the interactive path and the batch path — and I'll record the API's `stop_reason` on every result so the cause is never again unrecoverable, as it was for the 7 lost Fable calls in #2202.
- **What I expect:** all ~24 existing callers keep working unchanged (they already skip `error=True` rows); exactly one caller (`eval/judge_dispatch.py`) needs a 2-line change so the judge drop-class accounting from #2151 keeps classifying API refusals correctly; new regression tests pin the behavior on both paths.
- **What would change my mind:** if the caller audit had found a caller that legitimately relies on empty-string successes, I'd have needed an opt-out — the audit (all 24 call sites, §4-D6) found none, so a uniform library-boundary fix is safe.

## 0. Plan Summary

**Change:** `src/explore_persona_space/llm/api_dispatch.py` — new `RESULT_EMPTY_RESPONSE = "empty_response"` category; a no-non-empty-text-block guard inserted before parse at both mint sites (sync `_dispatch_sync._do_one`, line 820 region; batch `_harvest_sub_batch`, line 1163 region); a new `DispatchResult.stop_reason: str | None = None` field minted on every path (success, empty-failure, parse-error, invalid-response); cache round-trip carries it; a `result == ""` non-error cached entry reads as a MISS (heals pre-fix poisoned caches). **Migration:** one load-bearing caller change in `eval/judge_dispatch.py::_judge_items_sync_multiorg` (attach `res.stop_reason` to error dicts via `_with_stop_reason`) to preserve #2151 api-refusal classification; all other 23 callers audited no-change (table in §4-D6). **Tests:** 13 new tests in `tests/test_api_dispatch.py` + 1 in `tests/test_judge_dispatch.py` + a new lint test file. **Lint:** new `workflow_lint.py --check-empty-text-default` (narrow regex, allowlist, waiver comment). **Compute:** pytest only.

## 1. Goal

(Task #2206, `kind: infra` — no `goal:` frontmatter; the canonical Goal is the body's bug description + "Proposed fix" + "Acceptance criteria", quoted from the body at commit `d4d9e79803`, verbatim excerpts:)

> A text-block-free response is a typed failure, never a success with an empty result, at both `:820` and `:1163`. `stop_reason` is persisted on every dispatch path. Every existing `dispatch_calls` caller is enumerated and either migrated or explicitly recorded as unaffected. Regression tests cover the no-text-block and empty-content-list cases. The full relevant test suite is green on `main`.

One paragraph: `dispatch_calls` is the mandated shared path for all Anthropic API calls in this project. At both result-mint sites, `text = next((b.text for b in msg.content if b.type == "text"), "")` defaults to `""` when the response carries no text block, and the item is recorded `{"result": "", "error": false, "category": "ok"}`. In #2202 this silently lost 7/10 Fable digest calls and the proximate cause (`stop_reason`) is now unrecoverable because the plain parser path never persisted it. This violates the CLAUDE.md fail-fast rule in a shared library. Fix it at the boundary, persist `stop_reason` unconditionally, audit callers, pin with tests, and consider a lint against the pattern's reintroduction.

**Ecosystem conventions (bounded search):** Anthropic's own docs treat `stop_reason` as the caller's routing signal — every Messages response carries it, and `stop_reason: "refusal"` explicitly means the response may carry no usable content and needs handling, not silent acceptance. The Python SDK is documented to sometimes return *empty text blocks* while refusing to accept them as input (anthropic-sdk-python issue #461), i.e. an empty/absent text block is a known real shape the SDK deliberately leaves to the caller. Vercel's AI SDK maps Claude's `refusal` stop reason to an explicit `content-filter` finish state rather than an empty success — the same "typed, visible outcome" convention this fix adopts. OpenAI's convention is analogous: `finish_reason: "content_filter"` / null content is surfaced as a distinct terminal state. Conclusion: surfacing a typed record carrying `stop_reason` + block types is the standard treatment; silently returning `""` is not.

### D1 — Sync path: typed empty-response branch (`_dispatch_sync._do_one`)

File: `src/explore_persona_space/llm/api_dispatch.py`. Current bug line, verbatim grep output:

```
820:                text = next((b.text for b in msg.content if b.type == "text"), "")
```

Insert between `msg = raw.parse()` (:819) and the text extraction. Predicate: **no non-empty text block** — covers (a) empty content list, (b) thinking-only content, (c) refusal with empty content, (d) the SDK-documented present-but-empty text block (anthropic-sdk-python#461). Pseudocode (exact structure; comments abbreviated):

```python
msg = raw.parse()
stop = getattr(msg, "stop_reason", None)
block_types = [getattr(b, "type", "?") for b in msg.content]
if not any(b.type == "text" and b.text != "" for b in msg.content):
    # #2206: a text-block-free (or all-empty-text) response is NEVER an
    # empty-string success. Mirrors the #1470 retryable-invalid shape:
    # the WIRE call was clean (n_ok/recover run), the fault is content —
    # consume an attempt with backoff; exhaustion mints the typed record.
    state.n_ok += 1
    if not state.low_headroom():
        await state.recover()
    last_category = RESULT_EMPTY_RESPONSE
    last_stop_reason = stop
    last_reason = (
        f"empty_response: no non-empty text block "
        f"(stop_reason={stop}, blocks={block_types}, org={org}, attempt {attempt + 1})"
    )
    await asyncio.sleep(1.5**attempt)
    attempt += 1
    continue
text = next(b.text for b in msg.content if b.type == "text" and b.text != "")
```

- `last_stop_reason = None` initialized beside `last_reason`/`last_category` (:804-805); the `response_valid` branch (:834-847) also sets `last_stop_reason = stop` (a produced response exists there too).
- Success mint (:848) gains `stop_reason=stop`: `DispatchResult(item.item_id, result=parsed, org=org, category=RESULT_OK, stop_reason=stop)`.
- Terminal mint (:881-883) gains `stop_reason=last_stop_reason`.
- The `continue` fires `finally: release()` exactly as the #1470 branch does. Retry is bounded by the existing `max_attempts` (default 5); #2151's evidence (0 re-refusals in 14,887 re-issued draws) supports empties being retriable-in-principle.
- The text extraction drops the `""` default (the guard guarantees a non-empty block exists) — the lint-target pattern disappears from this file.

### D3 — New constant, new field, doc updates

- `RESULT_EMPTY_RESPONSE = "empty_response"` beside the existing constants (:221-224, verified values: `RESULT_OK = "ok"`, `RESULT_ERROR = "error"`, `RESULT_RATE_LIMITED = "rate_limited_exhausted"`, `RESULT_TRANSPORT = "transport_exhausted"`). ### D4 — Merge + cache layer

- `_merge_batch_record` (:677-698): add `stop_reason=rec.get("stop_reason")` to the constructed `DispatchResult`. Persisted pre-fix rows lack the key → `None`. Category threading unchanged (error rows read their stored `category` directly; the new rows store it explicitly).
- `_cache_put` (:1785-1803): add `"stop_reason": res.stop_reason` to the stored dict. `_split_cached` (:1660-1671): read it back via `cached.get("stop_reason")`.
- **Cache treatment of the new class — put-skip by existing gate, plus one heal.** Empty-response records are `error=True`, and BOTH put sites already gate on `not res.error` (`_run_sync_path._persist` :1723-1725; `_persist_results_to_cache` :1696-1702) → the new failure class is never cached, no new put-skip logic needed. **Get-side heal (the #1470 pattern):** in `_split_cached`, a cached NON-error entry whose `result == ""` reads as a MISS — this heals every pre-fix poisoned cache fleet-wide (the #2202 `fable_cache` shape: `{"result": "", "error": false, "category": "ok"}`) with no cache_dir wipe. Justification for the exact-`""` predicate: under the fix no success can mint `result=""` from a text-block-free response, and the caller audit (D6) found no caller for which a bare `""` is a meaningful success. Documented residual: a parser that legitimately returns `""` (e.g. `lambda t: t.strip()` on a whitespace-only response) would re-dispatch that item once per run — an extra API call, never a wrong read.
- **Batch checkpoint residual (documented, not changed):** a pre-fix batch checkpoint's persisted `results_*.json` rows with `{"result": "", "error": false}` are still re-served by `_merge_batch_record` on a same-fingerprint resume — consistent with the existing `RESULT_TRANSPORT` checkpoint-resume caveat (DispatchResult docstring :262-268); the run-level fingerprint means only a resumed pre-fix run is exposed, and its results then hit the JudgeCache heal / caller error checks downstream. Named in the docstring.

### D5 — Load-bearing caller migration: `eval/judge_dispatch.py`

`_judge_items_sync_multiorg` (def at :818; reduce at :879-908). Today an empty-content judge response reaches `_parse_response("")` → parse-error dict → `_with_stop_reason(...)` attaches `stop_reason` → **success**-record carrying an error dict → the `else` branch serves it → `is_api_refusal_error_dict` classifies it (#2151 flow). Fix (2 lines):

```python
elif res.error:

    transportish = res.category in (api_dispatch.RESULT_TRANSPORT, api_dispatch.RESULT_RATE_LIMITED)
```

`_with_stop_reason` (:246-260) is None-tolerant, copy-safe, and non-str-guarded — exactly the right seam. `RESULT_EMPTY_RESPONSE` is deliberately NOT added to the `transportish` set (rule 28: never blend into transport losses); classification of the sub-cause (api-refusal / truncation / content) stays with the `batch_judge` classifier family keying on the attached `stop_reason`. judge_dispatch's OWN batch machinery (`:698`, `:780`) already threads `stop_reason` via `_with_stop_reason` — untouched.
