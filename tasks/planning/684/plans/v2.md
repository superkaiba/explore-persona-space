### Finding 1 — distinguish 429-exhaustion from terminal error

**(a) Add a `category` field to `DispatchResult`** (line 194-207). New
field, defaulted so every existing constructor call site stays valid:

```python
# Module-level constants (near line 139, with the other tuning constants):
RESULT_OK = "ok"
RESULT_ERROR = "error"
RESULT_RATE_LIMITED = "rate_limited_exhausted"

@dataclass
class DispatchResult:
    item_id: str
    result: Any = None
    error: bool = False
    reason: str | None = None
    org: str | None = None
    category: str = RESULT_OK   # "ok" | "error" | "rate_limited_exhausted"
```

`category` is the structured discriminator; `reason` keeps the
human-readable detail string. On a successful result `category` stays
`RESULT_OK` (the default — no change at the success site, line 573). On a
terminal error `category=RESULT_ERROR`; on 429-exhaustion
`category=RESULT_RATE_LIMITED` AND `reason="rate_limited_exhausted (org=..., 429 retries N)"`.

**(b) Give 429 its own retry budget** separate from `max_attempts`. Add a
`max_429_retries: int = DEFAULT_MAX_429_RETRIES` parameter (new module
constant `DEFAULT_MAX_429_RETRIES = 6`) threaded through `dispatch_calls` →
`_dispatch` → `_run_sync_path` → `_dispatch_sync`. Inside `_do_one`'s loop
(line 555-599), count 429 retries independently:

```python
async def _do_one(item):
    params = build_request(item)
    last_reason = "unknown"
    last_category = RESULT_ERROR
    n_429 = 0
    attempt = 0
    while attempt < max_attempts:
        org = _pick_org_then_acquire(...)        # finding 3, see below
        state = org_states[org]; client = async_clients[org]
        try:
            ... success path ...
            res = DispatchResult(item.item_id, result=parsed, org=org, category=RESULT_OK)
            ...
            return
        except (asyncio.CancelledError, KeyboardInterrupt):
            raise
        except Exception as exc:
            if _is_rate_limit(exc):
                await state.on_429(_retry_after_seconds(exc))
                n_429 += 1
                last_reason = f"429 (org={org}, 429-retry {n_429})"
                last_category = RESULT_RATE_LIMITED
                if n_429 >= max_429_retries:
                    last_reason = f"rate_limited_exhausted (org={org}, 429 retries {n_429})"
                    break
                continue                          # 429 does NOT consume an attempt
            if _is_transient(exc):
                last_reason = f"transient {type(exc).__name__} (attempt {attempt + 1})"
                last_category = RESULT_ERROR
                await asyncio.sleep(1.5 ** attempt)
                attempt += 1
                continue
            last_reason = f"error: {exc}"
            last_category = RESULT_ERROR
            break
        finally:
            await state.release()
    res = DispatchResult(item.item_id, error=True, reason=last_reason,
                         org=None, category=last_category)
    results[item.item_id] = res
    if on_result is not None:
        on_result(res)
```

Key change from the current code (line 558 `for attempt in range(max_attempts)`):
a 429 increments `n_429` and `continue`s WITHOUT advancing `attempt`, so a
429 storm no longer burns the terminal-error budget. Both budgets are
bounded so the loop always terminates: `attempt` is incremented only on a
transient/clean iteration, and 429 is capped by `max_429_retries`. This is
the "(optional, larger) separate 429 budget" the reviewer named; it is
worth doing because conflating the two budgets is the exact mechanism that
turns a storm into a false terminal.

**(c) Cache-side `category`:** `_split_cached` (line 1139) reconstructs a
`DispatchResult` from the cached dict; add `category=cached.get("category", RESULT_OK)`
and have `_cache_put` (line 1223) persist `res.category`. A cached entry
only ever stores successful (non-error) results today
(`_persist_results_to_cache`/`_persist` both gate on `not res.error`), so
the default is harmless, but threading it keeps the round-trip honest if a
future change persists errors.

**(d) Batch-path `category` (Methodology Must-Fix 1).** `_dispatch_batch`
(line 884-893) reconstructs a `DispatchResult` from the per-batch persisted
records (the JSON files written on `Errored`/`Ended` sub-batch states)
WITHOUT setting `category`. Under the new `RESULT_OK` default, an
`error=True` batch record would silently become `category="ok"` — internally
contradicting the discriminator on a real production path. Thread `category`
through the result merge at line ~887 with the same safe default the success
path uses:

```python
# In _dispatch_batch's result merge (line ~887), per persisted record `rec`:
res = DispatchResult(
    item_id=rec["item_id"],
    result=rec.get("result"),
    error=rec.get("error", False),
    reason=rec.get("reason"),
    org=rec.get("org"),
    category=rec.get("category",
                     RESULT_ERROR if rec.get("error", False) else RESULT_OK),
)
```

The `RESULT_ERROR if error else RESULT_OK` default makes the field
self-consistent with `error` for any legacy record written before this
change (no persisted `category` key) — an errored batch record can never
read back as `category="ok"`. Where the batch sub-batch result records ARE
written with a known category (e.g. a batch-API rate-limit terminal), the
record SHOULD carry the `category` field so the merge reads it directly
rather than inferring from `error`. The line-887 merge is the only
batch-side `DispatchResult` constructor; it is the 4th in-module site (§10).

### Finding 2 — bound the coroutine fan-out

**Where:** line 601, `await asyncio.gather(*[_do_one(it) for it in items])`.

Introduce a module-level helper that computes the bound from the live org
caps and wrap each coroutine in an outer semaphore:

```python
# Module constant (near line 139):
FANOUT_SLACK = 2   # allow ~2x the concurrency target live so a coroutine
                   # blocked in retry-after doesn't starve a ready slot

def _fanout_limit(org_states: dict[str, OrgState]) -> int:
    """Outer-semaphore size: ~the total concurrency target across orgs.

    Each org admits at most ``cap`` concurrent calls; ``FANOUT_SLACK`` head-
    room lets a coroutine waiting out a retry-after not block a sibling that
    could acquire. Bounds LIVE coroutines to O(cap * n_orgs), not O(N).
    """
    total_cap = sum(st.cap for st in org_states.values())
    return max(1, total_cap * FANOUT_SLACK)
```

In `_dispatch_sync`:

```python
fanout = asyncio.Semaphore(_fanout_limit(org_states))

async def _do_one_bounded(item):
    async with fanout:
        await _do_one(item)

# residual: gather still creates O(N) Task objects (~140 MB at N=100k); routing
# steers large N to the batch path (see Finding 4), so the sync ceiling is the
# rare case. The semaphore fixes the busy-poll CPU storm, which is the actual
# bug the reviewer flagged; the worker-pool/chunked alternative is out-of-
# contract (the reviewer named "semaphore" literally — see §11).
await asyncio.gather(*[_do_one_bounded(it) for it in items])
```

The semaphore lives at function scope (one per `_dispatch_sync` call),
sized from the org states already constructed in `_run_sync_path` (line
1185). It is an admission gate on coroutine ENTRY, layered ABOVE
`OrgState.acquire()`'s per-org live `effective`-gate (the inner gate is
unchanged — the cap invariant `in_flight <= effective <= cap` still holds).
With `cap`-summed sizing, the number of coroutines that have even reached
`acquire()` tracks the concurrency target; the rest wait at the outer
semaphore cheaply (one awaiter on a single semaphore, not 100k busy-polls).

Note `asyncio.gather` still creates N coroutine OBJECTS (the comprehension),
but only `_fanout_limit` of them run past the outer `async with` at any
time — the busy-poll / wakeup cost the reviewer flagged is what the
semaphore eliminates, and a bare coroutine awaiting a semaphore is cheap
(no `acquire()` busy-poll loop entered). This is the minimal-surface fix
that does not require restructuring `gather` into a worker-pool /
`asyncio.Queue` (rejected in §11).

### Finding 3 — re-pick org at slot-availability, not pick-time

**Where:** `_pick_org` (line 545-553) runs before `state.acquire()` (line
562), so under burst every coroutine picks by headroom up-front then queues
on its chosen org's gate.

Add a `_pick_org_then_acquire` helper that tries the headroom-best org,
falls back to re-picking if that org's gate doesn't admit within a short
window:

```python
# Module constant (near line 221, with GATE_POLL_INTERVAL):
REPICK_TIMEOUT = 4 * GATE_POLL_INTERVAL   # ~0.08s: re-pick if the chosen org
                                          # doesn't free a slot within a few polls

async def _pick_org_then_acquire() -> str:
    """Pick the highest-headroom org; if its gate doesn't admit within
    REPICK_TIMEOUT, re-pick (a sibling org may have freed a slot first).

    Falls back to a plain blocking acquire on the final candidate so the
    coroutine never spins forever when every org is saturated (the 429
    retry budget + the inner gate's retry-after still bound total time).
    """
    tried: set[str] = set()
    while len(tried) < len(labels):
        org = _pick_org_excluding(tried)
        state = org_states[org]
        try:
            await asyncio.wait_for(state.acquire(), timeout=REPICK_TIMEOUT)
            return org
        except asyncio.TimeoutError:
            tried.add(org)
    # All orgs slow this round -> block on the headroom-best with no timeout.
    org = _pick_org()
    await org_states[org].acquire()
    return org
```

`_pick_org_excluding(tried)` is `_pick_org` restricted to labels not in
`tried` (keeps the existing round-robin tie-break). `_do_one` calls
`org = await _pick_org_then_acquire()` and the `acquire()` is now done
INSIDE the helper, so the `try/finally: await state.release()` block in
`_do_one` releases the SAME `state` the helper acquired (thread the chosen
`org`/`state` back out — the helper returns the label, `_do_one` looks up
`state = org_states[org]`). The slot is already held on return, so the body
does NOT re-acquire.

The fallback (final blocking acquire) is the livelock guard: when every org
is saturated, the coroutine blocks on one org's gate exactly as today
rather than spinning the re-pick loop — the all-orgs-saturated case
degrades to the current behavior, not worse.

## §11 Decision Rationale

**Finding 1 — `category` field vs reason-string only.**
- **What:** Add a structured `category: str` field (`"ok" | "error" |
  "rate_limited_exhausted"`) AND set a distinct `reason` string.
- **Why:** The reviewer named "distinguish `reason="rate_limited_exhausted"`"
  as the minimum, but a structured field is the robust discriminator —
  callers branch on `res.category == RESULT_RATE_LIMITED` (an enum-like
  exact match) rather than substring-matching a free-text `reason` (brittle:
  the reason carries org + retry count, so `==` won't work and `.startswith`
  is fragile). Both are cheap; doing both gives callers a clean machine
  signal AND keeps the human-readable detail. Tied to the Goal: the whole
  point is letting `judge_dispatch` / future callers re-drive rate-limited
  items without crashing the pipeline.
- **Source:** `parent #682 reviewer verdict` (the proximate authority); the
  `reason="rate_limited_exhausted"` string is the reviewer's literal
  suggestion.
- **Alternatives:** reason-string only (rejected — brittle for callers to
  match); a new exception type (rejected — the dispatcher's contract is a
  result dict, not raising, per `api_dispatch.py:60` "returns ... `error=True`
  rather than crashing"); a boolean `rate_limited` flag (rejected — a
  3-state category subsumes ok/error/rate-limited in one field and extends
  cleanly).

**Finding 1b — separate 429 retry budget.**
- **What:** `max_429_retries` (default 6), counted independently of
  `max_attempts`; a 429 does not consume an `attempt`.
- **Why:** The reviewer flagged the budget-conflation as the mechanism: a
  storm of 429s exhausts `max_attempts` and the item is recorded terminal,
  even though 429 is pure backpressure the AIMD controller clears. Separating
  the budgets means transient/terminal errors and rate-limit backpressure are
  bounded independently — exactly the "(optional, larger)" fix named. The
  budget separation is pinned by `test_429_does_not_consume_an_attempt`
  (§5 1b), whose mutation check (the buggy `attempt += 1`-on-429 impl) goes
  red — the v1 pure-429 exhaustion test could not reach this behavior.
- **Source:** `parent #682 reviewer verdict`. Default `6` is a sensible
  bound (AIMD + retry-after means each 429 retry waits out the org's window;
  6 covers a multi-minute storm without an unbounded hang) — `kind: infra
  exempt` (no literature ground for a retry count; it's a tuning default,
  flagged here as a deliberate choice not a magic number).
- **Alternatives:** keep the shared budget (rejected — re-creates the bug);
  unbounded 429 retries (rejected — an item could hang forever on a
  permanent org misconfiguration that surfaces as 429).

**Finding 1c — batch-path `category` threading.**
- **What:** Thread `category` through the line-887 `_dispatch_batch` merge
  with default `RESULT_ERROR if error else RESULT_OK`.
- **Why:** Under the new `RESULT_OK` field default, an `error=True` batch
  record reconstructed without an explicit `category` would silently read
  back `category="ok"`, internally contradicting the discriminator on a real
  production path. The error-inferring default makes the field self-consistent
  with `error` for any legacy record (no persisted `category` key).
- **Source:** `parent #682 reviewer verdict (Codex critic refinement, round 1)`
  — the Methodology lens Must-Fix that caught the batch-path gap; the line-887
  site was not enumerated in v1 §10.
- **Alternatives:** leave the field at its `RESULT_OK` default on the batch
  path (rejected — the contradicting `error=True, category="ok"` state is the
  exact bug the field exists to prevent); set `category=RESULT_ERROR`
  unconditionally on the batch path (rejected — would mislabel a successful
  batch record).

**Finding 2 — semaphore vs `asyncio.Queue` worker pool.**
- **What:** An outer `asyncio.Semaphore(sum(caps) * FANOUT_SLACK)` wrapping
  each `_do_one`; `FANOUT_SLACK=2`.
- **Why:** A semaphore is the minimal-surface bound — it caps LIVE
  coroutines (past the `async with`) to `O(cap * n_orgs)` without
  restructuring the `gather`. The size formula `sum(caps) * FANOUT_SLACK`
  tracks the actual concurrency target (the per-org caps the inner gate
  already enforces); the `2x` slack lets a coroutine waiting out a
  retry-after not starve a sibling that could acquire. A worker-pool /
  `asyncio.Queue` would also work but is more code (queue, N worker tasks,
  drain/shutdown logic) for the same bound. The O(N) Task-object residual at
  the N=100k ceiling (~140 MB) is acceptable because routing steers large N
  to the batch path — noted at the gather site (Alternatives rec 5). The
  WIRING is pinned by `test_sync_fanout_is_bounded_by_concurrency_target`
  (§5 2a) whose mutation check (revert to the bare gather) goes red — the
  v1 end-to-end `max_in_flight <= cap` test did NOT go red on the bug (the
  inner gate enforces it independently), hence its replacement.
- **Source:** `parent #682 reviewer verdict` ("Bound by an outer semaphore
  sized to `cap * n_orgs`") + `Python stdlib docs (asyncio.Semaphore
  semantics)`. The WIRING-vs-arithmetic test split is from
  `parent #682 reviewer verdict (Codex critic refinement, round 1)`.
  `FANOUT_SLACK=2` is `kind: infra exempt` (tuning default; named so it's
  not a magic literal).
- **Alternatives:** `asyncio.Queue` + fixed worker pool (rejected — more
  surface area, same outcome; the reviewer explicitly suggested the
  semaphore — "the reviewer named semaphore literally", out-of-contract to
  change); `asyncio.Semaphore(sum(caps))` with no slack (rejected — a
  coroutine blocked in retry-after would hold a permit and could starve the
  pipeline below the concurrency target); per-org semaphores (rejected — the
  inner `OrgState.acquire()` gate ALREADY does per-org bounding; the outer
  gate's job is global admission to cap the coroutine COUNT).

**Finding 3 — re-pick window size + test discriminating-observable choice.**
- **What:** `REPICK_TIMEOUT = 4 * GATE_POLL_INTERVAL` (~0.08s); re-pick on
  timeout, fall back to a blocking acquire on the final candidate. Test
  asserts `fast.calls > slow.calls` (strict) + `all(in_flight == 0)`.
- **Why:** A few `GATE_POLL_INTERVAL` ticks is long enough to let a genuinely
  free org admit immediately (it admits on the first poll) but short enough
  that a coroutine queued behind a saturated org's gate gives up and tries a
  sibling — restoring true least-loaded routing under burst. Tying it to
  `GATE_POLL_INTERVAL` (the existing busy-poll cadence) keeps the constant
  self-consistent: 4 polls = the org had a few chances to free a slot. The
  blocking fallback is the livelock guard (all-orgs-saturated → behaves
  exactly like today). The test uses the STRICT `fast.calls > slow.calls`
  (no `>=` fallback) because pre-fix round-robin satisfies equality — a
  `>=` fallback is non-discriminating and would pass against the un-fixed
  code; the slot-accounting `all(in_flight == 0)` invariant additionally
  guards the `wait_for`-after-`acquire` slot-leak race.
- **Source:** `parent #682 reviewer verdict` ("Re-pick on slow gate poll") +
  `existing api_dispatch.py:221` (`GATE_POLL_INTERVAL = 0.02`, the cadence
  the window is anchored to). The drop-the-`>=`-fallback + add-the-
  `in_flight==0`-invariant test decisions are from
  `parent #682 reviewer verdict (Codex critic refinement, round 1)`. The
  `4x` multiplier is `kind: infra exempt` (tuning).
- **Alternatives:** re-pick on EVERY poll (rejected — thrashes; a 1-tick
  window would bounce a coroutine off an org that's about to free a slot);
  no fallback / pure re-pick loop (rejected — livelocks when every org is
  saturated); a fixed wall-clock window decoupled from `GATE_POLL_INTERVAL`
  (rejected — two constants that must stay in sync; deriving it keeps one
  source of truth); the `fast.calls >= slow.calls` CI-flakiness fallback
  (rejected — equality-permitting, non-discriminating; the contingency is a
  discriminating observable instead).

**Finding 4 — docstring note vs behavior change.**
- **What:** Document that routing decides on `len(pending)`; do NOT change
  the behavior.
- **Why:** The reviewer classified this a nit and explicitly said the
  behavior is "defensible" (fewer items remain after a cache hit → routing
  the smaller remainder is correct). The only gap is that it's undocumented.
  A one-line doc note closes it without a behavior change that could
  surprise callers relying on the current routing.
- **Source:** `parent #682 reviewer verdict` ("add a one-line docstring
  note").
- **Alternatives:** route on original N (rejected — the reviewer judged
  routing-on-remainder correct; changing it would re-route resumed jobs
  unexpectedly).
