# Plan v3 — issue #2428: Step 10d Guard 4 `--main-sha` tip-vs-merge-base contract fix

`kind: infra` (`wf-fix`). Parent: #2212. Workflow-surface fix; no compute phase.

## 1. Requirement + acceptance criteria

**Requirement.** `scripts/step10d_guards.sh --guard 4` must actually evaluate the
lost-update predicate when invoked in the form `.claude/skills/issue/steps/18-step-10d.md`
prescribes. Today it does not: the caller passes the `origin/main` **tip** via
`--main-sha`, the helper consumes that value as the **merge-base**, and the resulting
main-side diff is main-against-itself — an empty add-set, so the "is every main-added
line still present in the branch's copy?" predicate is vacuously true and the guard
emits `GUARD4=pass` on every branch.

Acceptance criteria, verbatim from the task body, each mapped to a deliverable:

| # | Criterion | Deliverable |
|---|---|---|
| 1 | Prescribed call refuses on a stale-snapshot branch; ONE side of the contract fixed; flag name / `--help` agree with the chosen semantics; helper-side preferred | D1 + D2 |
| 2 | Mechanical pin in `tests/` that FAILS if Guard 4 returns `pass` on a fixture branch dropping a main-added line, exercising the flag form the caller actually uses | D4 (T1, T3, T4) |
| 3 | `steps/18-step-10d.md` Guard-4 block and the helper usage/`--help` state the SAME contract | D2 + D3, pinned by T6 |
| 4 | Audit the other `--main-sha` consumer (the `divergence` guard) for the same confusion; state the finding either way | D5 (finding) + D5b (fail-loud disposition), pinned by T5 |

## 2. Method delta

The bug is a caller/callee semantic mismatch on ONE flag, not a defect of the
predicate. So the change is a base-derivation fix plus a contract-agreement pass —
**no change to the predicate itself** (`grep -Fxq --` full-line matching, the case
glob, the refusal banner, the exit-code contract, the kill switch, `mktemp` hygiene
all stay byte-identical). This keeps the diff small enough that the mechanical pin,
not the reviewer's attention, is what holds the fix in place.

The fix is taken **helper-side**, as criterion 1 prefers and the body's "Notes" section
independently requires:

- The flag exists so the caller can PIN the main snapshot against a concurrent
  session's fetch advancing the shared `origin/main` ref mid-guard (the #1128
  rationale carried in the Guard-1 block, `steps/18-step-10d.md:256`). A **tip** is
  the right value to pin; a merge-base is derived, not pinned.
- Deriving the merge-base inside the helper keeps the no-flag path (already correct)
  and the pinned path in agreement — the alternative (caller computes and passes a
  merge-base) leaves two call shapes with two different semantics, exactly the
  condition that produced this bug.
- The rejected variant — caller drops `--main-sha` — is forbidden by the body: it
  would work but discards the pinning the flag exists for.

## 3. Root cause (measured, re-verified this session)

`scripts/step10d_guards.sh:244-251`:

```
if [ -n "$MAIN_SHA" ]; then
    MB="$MAIN_SHA"                                    # <-- tip consumed as merge-base
else
    if ! MB=$(git -C "$WT" merge-base HEAD origin/main 2>/dev/null); then
```

Downstream, the main side of both per-path diffs is the literal ref `origin/main`:

- `:270` `git diff --numstat "$MB" origin/main -- "$P"` → `MAIN_ADDS`
- `:273` `git diff "$MB" origin/main -- "$P"` → the add-line enumeration

With `MB` = the `origin/main` tip, both are `tip..tip` = empty ⇒ `MAIN_ADDS=0` for
every path ⇒ the inner presence loop never runs ⇒ `GUARD4=pass`.

Precision on "every branch": that is exactly true in the ordinary case where
`origin/main` has not advanced between the caller's Guard-1 capture (`:304`) and the
guard invocation (`:595`). If a concurrent session's fetch DOES advance it mid-guard,
the buggy reading degrades instead to `capturedtip..newtip` — a wrong-base PARTIAL
predicate (it would flag only lines main added in that narrow window) rather than a
vacuous one. Broken either way, and the D1 fix is identical in both cases; the
distinction matters only so the root-cause statement is airtight.

Two scoping facts confirmed by reading, both load-bearing for the diff:

- **The path enumeration is NOT affected.** `:295` uses the three-dot form
  `diff --name-only "$MB"...HEAD`, which resolves its own merge-base, so the
  branch-touched file list is correct today and stays correct after the fix
  (`merge-base(MB, HEAD)..HEAD` = `MB..HEAD` once `MB` is a true merge-base). The
  bug is confined to the per-file predicate. No change needed at `:295`.
- **Exactly ONE guard-4 call site exists** across `.claude/skills/**` and
  `.claude/agents/**` (`steps/18-step-10d.md:595`), and the `MAIN_SHA` it passes is
  captured at `steps/18-step-10d.md:304` as `rev-parse origin/main` — the tip. So
  fixing the helper fixes every live caller; there is no second caller passing a
  merge-base that the helper-side fix would break.

Blast radius, from the task body's measured table on `issue-2212@0eb8309f86`: the
prescribed form returned `pass` while both correct forms returned
`refused / LOST_UPDATE_PATHS=scripts/workflow_lint.py(8)` — a `--squash` landing
would have reverted 8 lines of a bundled-lint file.

## 4. Deliverables — file paths + concrete diffs

### D1 — `scripts/step10d_guards.sh`: derive the merge-base from the pinned tip

Replace the `:244-251` base-derivation block with:

```bash
        # --main-sha is the PINNED origin/main TIP (the Step 10d caller's Guard-1
        # capture: MAIN_SHA=$(git -C "$WT" rev-parse origin/main),
        # steps/18-step-10d.md:304) -- NOT the merge-base. Derive the merge-base
        # FROM it and use the SAME pinned tip as the main side of every diff
        # below, so the pinned path and the no-flag path agree (#2428).
        MAIN_REF="${MAIN_SHA:-origin/main}"
        if ! MB=$(git -C "$WT" merge-base HEAD "$MAIN_REF" 2>/dev/null) || [ -z "$MB" ]; then
            printf 'ERROR=%s\n' merge-base-failed
            exit 2
        fi
```

and substitute `"$MAIN_REF"` for the literal `origin/main` at `:270` and `:273`.

Three notes on the shape, so the reviewer can check intent:

- `MAIN_REF="${MAIN_SHA:-origin/main}"` keeps the **existing** `ERROR=merge-base-failed`
  vocabulary for both paths. Deliberately NOT introducing the divergence guard's
  `no-origin-main` / `rev-parse --verify --quiet` pre-resolution here: that would add
  a new failure mode to a path whose current behavior (missing `origin/main` ⇒
  merge-base fails ⇒ `merge-base-failed`) is already correct and already the
  no-flag path's behavior. Out of scope; recorded as a deliberate non-change.
- `|| [ -z "$MB" ]` is added: an empty-but-rc-0 merge-base would otherwise flow into
  the diffs as an empty revision argument. This mirrors the sibling `divergence`
  guard's own guard at `:351`, so the two subcommands agree.
- Emit one new observability key on BOTH the pass and refusal paths:
  `printf 'GUARD4_MERGE_BASE=%s\n' "$MB"`. Rationale (in scope, not creep): #2212's
  real merge attempt recorded `GUARD4=pass / LOST_UPDATE_PATHS=none` in a durable
  marker with **no way to tell which base was used** — that opacity is why a vacuous
  pass survived a real merge unnoticed. The key makes the base auditable from the
  `epm:merged` record. Name prefixed `GUARD4_` to avoid clobbering the caller's own
  `MB` / `MAIN_SHA` under `eval "$GUARD4_OUT"` (`steps/18-step-10d.md` holds live
  `MB` at `:438` and `:684`).

### D5 — criterion 4: audit of the other `--main-sha` consumer (finding)

**Finding: the `divergence` guard does NOT have this bug, and cannot acquire it from a
caller.** It ignores the parsed `--main-sha` entirely — `:346` overwrites it with its
own `MAIN_SHA=$(git rev-parse --verify --quiet origin/main)` — and then derives
`MB=$(git merge-base HEAD "$MAIN_SHA")` at `:351`: the correct two-step shape Guard 4
was missing. Its emitted `MAIN_SHA` is therefore a tip, consistent with the corrected
Guard-4 contract. Neither divergence call site (`steps/09-step-5.md:598`,
`steps/18-step-10d.md:735`) passes `--main-sha`. So there is no second live instance
of the confusion to fix — the audit's finding is negative, and it is stated here and
in the `epm:plan` note either way, per the criterion.

**Residual trap found by the same audit (D5b).** The argument parser accepts
`--main-sha` for ANY guard (`:137-141`), while only guard 4 reads it. A future caller
passing it to `divergence` would have the value **silently shadowed** at `:346` — the
same class of silent-ignore that produced this task. Disposition: **fail loud**, per
the CLAUDE.md "Fail fast — never hide failures" rule. After the `[ -z "$GUARD" ]`
check, add:

```bash
# --main-sha is Guard 4-only: divergence pins its OWN main snapshot and would
# silently shadow a passed value; prelude/0 never read it. Reject rather than
# accept an inert flag (#2428 acceptance criterion 4).
if [ -n "$MAIN_SHA" ] && [ "$GUARD" != "4" ]; then
    _die_usage "main-sha-not-supported-for-guard-$GUARD"
fi
```

Safe by grep: zero existing callers pass `--main-sha` to a non-4 guard.

## 8. Kill criteria

- **False-positive storm.** If the fixed guard refuses on a genuinely-converged branch
  — T2 or the `drop_main_lines=False` arm of T3 refuses — the helper-side derivation is
  wrong; stop, do not "tune" the predicate, and re-plan.
- **No-flag regression.** If any pre-existing guard-4 test flips, the change has
  altered the already-correct path: revert and re-plan.
- **Contract cannot be made single-valued.** If a second live guard-4 caller passing a
  genuine merge-base is discovered (grep says none exists), the helper-side fix is
  unsafe and the caller-side variant becomes the plan.
- **T1 passes against the PRE-fix helper.** That would mean the fixture does not
  reproduce the vacuity and the pin is hollow (the `.claude/rules/code-style.md`
  hollow-verification-gate class). Fix the fixture before touching the helper.
