- **What I'll run:** I'll add one small read-only command, `task.py marker-status <N> <kind>`, that classifies whether a task marker exists by reading three places at once (the committed file in git HEAD, the file on disk, and the deferred-commit ledger) and checking whether a concurrent commit's hook window is live right now. ### 4.1 New helper (core) — `src/explore_persona_space/task_workflow.py`

Two NEW read-only functions (no flock, no commit, no mutation), appended after `has_event` (task_workflow.py:5762; symbol-existence confirmed by `grep -n "def has_event" src/explore_persona_space/task_workflow.py` → `5762:def has_event(task_id: int, kind: str) -> bool:`), plus module constants. All git invocations route through ONE module-level runner (e.g. `_marker_status_git(args) -> (rc, stdout, stderr)`) so tests can monkeypatch operational failures per-leg (T1 cases 11–12).

**Leg-status discipline (the MF-3 core).** Every source leg returns `(status, payload)` where `status ∈ {ok, error}` and `ok` additionally distinguishes VERIFIED-MISSING from found-and-read. A leg reaches `ok`+missing ONLY through a positive missing-path discrimination; ANY operational failure is `error` and poisons the aggregate to `unknown`:

- **HEAD leg** (two-step, per leg-target path): (1) existence probe `git -C <root> ls-tree HEAD -- <relpath>` — rc 0 + non-empty output ⇒ exists; rc 0 + empty output ⇒ VERIFIED-MISSING (live-verified: `git ls-tree HEAD -- nonexistent-path-xyz` → rc 0 empty; a bad ref → rc 128); rc ≠ 0 ⇒ leg `error`. (2) If exists: `git show HEAD:<relpath>` parsed with the EXISTING `_iter_jsonl_text(text, source=f"HEAD:{relpath}")` (task_workflow.py:5445); `git show` rc ≠ 0 AFTER a successful existence probe ⇒ leg `error` (never missing — existence was already proven). `relpath = (find_task_path(id)/"events.jsonl").relative_to(repo_root())`.
- **Registry fallback** (only on VERIFIED-MISSING of the direct relpath): the same two-step against `tasks/REGISTRY.json` at HEAD (`jq`-verified schema: `.tasks."2325".path` → `"tasks/completed/2325"`), then the same two-step against `<head_registry_path>/events.jsonl`. Registry verified-missing at HEAD, task id absent from the HEAD registry, or the registry-resolved events path verified-missing ⇒ the HEAD contribution is `[]` — a VERIFIED miss (task never committed), NOT an error. Registry blob unparseable or any git rc ≠ 0 on this leg ⇒ leg `error`.
- **Worktree leg:** `_iter_jsonl(find_task_path(task_id) / "events.jsonl")` (existing reader, unchanged, task_workflow.py:5476). File absent (ENOENT) ⇒ VERIFIED-MISSING (contribution `[]`); any other `OSError` ⇒ leg `error`. An unknown task id (`find_task_path` failure) is a caller error → the CLI reports it as a generic failure (rc 1), never `absent`.

    version: int | None = None,

- **Tree-row match:** `row["kind"] == kind`, then optional `note_contains in (row.get("note") or "")` and `version == row.get("version")`. Filters apply to TREE rows only.
- **Ledger row match (the MF-1 rebuild — paths-based, status-move-robust):**
  1. *Eligibility:* `row.get("task_id") == task_id` AND some `p` in `row.get("paths", [])` matches by TRAILING SEGMENTS — either an events-file shape (`parts[-1] == "events.jsonl" and parts[-2] == str(task_id)`) or a task-folder ANCESTOR shape (`parts[-1] == str(task_id)` with a `tasks` segment among `parts` — required because `create` defers the FOLDER, not the file). Segment matching (never full-path equality) because the recorded paths are absolute AND embed the at-post-time status folder (the real #2325 row records `tasks/running/2325/events.jsonl`; the task now lives at `tasks/completed/2325`). Rows whose paths are only registry / body.md / plans / comments / concerns files never pass eligibility — correct: `new_plan_version` and `append_comment` append no events row.
  2. *Kind refinement:* for `op == "post_event"` — message equals `f"task #{task_id}: {kind}"` or starts with `f"task #{task_id}: {kind} — "` (the writer's exact format, task_workflow.py:5743-5744; exact-or-delimited, so `epm:results` never matches a hypothetical `epm:results-x`). For the four other event-appending ops — a small op→kind table maintained beside the matcher, grounded on the call sites (re-verified live): `{"create": ("epm:created",), "set_goal": ("epm:goal-updated",), "promote": ("epm:promoted",), "append_concern_event": ("epm:concern-",)}` (prefix match; kind constructions at task_workflow.py:6278/6726/7081/8922) — the row matches iff the queried kind matches the op's entry. An op NOT in the table (a future writer op) with eligible paths matches KIND-BLIND — deliberately conservative: it can only withhold `absent`, never license a re-append.
  3. *Filters are NEVER applied to ledger rows* (N7): the message is version-blind and note-truncated at 60 chars, so `--version` / `--note-contains` could spuriously de-match a real deferral. Output carries `version_blind: true` + `filters_not_applied_to_ledger: true` per ledger match. A `gitleaks_finding` ledger flag is surfaced verbatim (that class never sweeps; the guidance says so).
- **Ledger staleness discriminator (N8 — makes ledger-only evidence decidable):** for each matched ledger row, compare `row["ts"]` against the newest `git log -1 --format=%cI HEAD -- <relpath>` over the leg-target events path(s) actually read (direct relpath, plus the registry-resolved one when the fallback ran). A commit STRICTLY newer than the row's ts means the sweep should already have carried the deferred content — the row is STALE/INDETERMINATE evidence: if EVERY matched row is stale, the verdict is `unknown` with reason `stale-ledger-row` and the guidance names the decidable forensic exit (`git log -p --since=<row ts> -- <relpath>` to see what the post-deferral commits carried, plus the `~/.cache/pre-commit/patch*` rescue surface, #1806) and shows each row's ts + op + message excerpt so the reader can identify WHICH marker the old deferral was for. Any non-stale matched row ⇒ `pending-deferred`. `git log` failure on this step ⇒ leg `error` ⇒ `unknown`. This keeps `absent` reachable in spirit for (task, kind) pairs with only ANCIENT deferral history — they resolve to `unknown` with a decidable exit instead of eternal `pending-deferred`, and never to a false `absent`.
- **In-flight liveness probe (the MF-2 closer, MF-A-scoped; runs only when the aggregate would otherwise be `absent`):** two read-only signals, either of which downgrades the verdict to `unknown`:
  1. `commit-in-flight` — the file at `git -C <root> rev-parse --git-path index.lock` exists (live-verified output: `.git/index.lock` — the MAIN checkout's index; a worktree commit locks its own per-worktree index, so this signal is main-tree-scoped by construction). A live index.lock means a fleet commit — and therefore possibly its stash window, or a deferral-in-progress whose ledger row is not yet written (the #2325 post→ledger gap was 61 s) — is executing in this repo right now. It does NOT cover the whole hook window (`git checkout -- .` holds the lock only briefly; the hook suite runs after) — covering that residue is what signal 2 exists for.
  2. `stash-window-live` (the MF-A rebuild — pid-scoped + repo-scoped, NOT global mtime) — some `${PRE_COMMIT_HOME:-~/.cache/pre-commit}/patch*` file satisfies ALL THREE conjuncts: (i) mtime within `STASH_WINDOW_FRESH_SECS = 1800`; (ii) the pid embedded in its filename (`patch{epoch}-{pid}` — `staged_files_only.py:68`, read live) is a LIVE process (`/proc/<pid>` exists); (iii) `os.path.realpath(f"/proc/{pid}/cwd") == os.path.realpath(repo_root())` — EQUALITY, not prefix: git hooks run at the top level of the working tree being committed (githooks(5); pre-commit inherits that cwd), so a MAIN-checkout commit's pre-commit sits exactly at repo root, while a worktree commit's cwd is the worktree dir (whose stash cycle cannot revert the main tree's `events.jsonl`) and another repo's is elsewhere. **Why pid+cwd, not mtime alone (MF-A):** the patch dir is GLOBAL across every repo and all ~15 fleet sessions, and pre-commit never deletes the file on success — measured this session: 25,805 accumulated files, fresh arrivals 1 per 32 s over the last hour — so a global-mtime signal reads LIVE essentially always (P(a 300 s window is clear) ≈ 0.01%), making `absent` structurally unreachable: the unreachable-rejection-region class (`.claude/rules/selection-symmetric-nulls.md` § Band-vs-ceiling / § Gate thresholds need a MEASURED calibration basis). Pid-liveness + repo-scoped cwd is the discriminating predicate — measured: of 112 patch files fresher than 3,600 s, ZERO have a live `/proc/<pid>` (a dead pid's patch file is a CLOSED window at any mtime), and none has cwd at this repo root. The mtime conjunct is RETAINED as the secondary guard against pid recycling only — and the recycling channel is arithmetically CLOSED at measured rates: Linux allocates pids cyclically, so a freed pid is reallocated only after a full counter wrap, and the measured wrap time (pid_max 4,194,304 / measured 376 pids/s ≈ 3.1 h) is ~6× the 1,800 s freshness bound — a fresh file's dead owner pid cannot yet have been recycled; the channel opens only above a sustained ~2,330 pids/s (6.2× measured), and even then requires the recycled process to sit exactly at repo root, and a false fire is safe-direction (§12 assumption 15). The constant moves 300 → 1,800 because its ROLE changes: with pid-liveness primary, the dangerous direction is the false NEGATIVE (a genuinely live hook window aging past the bound while its process still runs), so the bound is sized generously — 1,800 s ≈ 30× the #2325 measured 61 s exposure gap and far above this repo's commit-stage hook walls — while the wider bound's false-positive cost is borne entirely by the closed recycling channel.
