# Plan — #1010: thread a disk requirement into the RunPod CPU fallback + refuse infeasible footprints (disk AND RAM)

`workflow: v1` · `kind: infra` · 0 GPU-h · code-change path (Step 4b implementer → code-review → test-verdict → Step 10d merge)

## 0.0 TL;DR (plain English)

- **What I'll run:** a small, surgical change to the compute router: when a CPU job falls back from GCP to RunPod, the router will now (a) check whether the mapped RunPod CPU box can actually hold the plan's disk and RAM footprint and refuse with a typed, non-retried failure if it can't, and (b) actually pass the plan's disk size through to the RunPod pod-creation call (today it silently gets a fixed 50 GB). Plus a ~$0.05 live probe to pin down what RunPod really allows.
- **What I expect:** the #958 failure mode (an 80 GB-disk plan silently dispatched onto a 50 GB / 16 GB-RAM pod, refused only after a full provision cycle) becomes impossible — either the pod is provisioned big enough, or the route refuses instantly at zero cost.
- **What would change my mind:** if the live probe shows RunPod ignores or rejects larger container disks on CPU pods, the "thread the size through" half degrades to a no-op and the fix is refuse-only — still eliminating the wasted provision cycle, just without rescuing the 80 GB case onto cpu-mid.

## 1. Goal + acceptance criteria

Thread a disk-size requirement into the RunPod CPU fallback lane (`deployCpuPod` / `containerDiskInGb`) and refuse / route away when the mapped RunPod CPU instance cannot satisfy the plan's footprint (disk AND RAM).

Acceptance criteria:

1. **Gap #1 closed (threading):** an auto-route / failover that lands a mapped CPU intent (`cpu-small` / `cpu-mid`) on the RunPod terminal rung with `spec.extra["boot_disk_gb"]` set provisions the pod with `containerDiskInGb == max(50, boot_disk_gb)` (verified by argv test + live probe), not the silent fixed 50.
2. **Gap #2 closed (feasibility gate):** when `boot_disk_gb` exceeds the mapped instance's `max_container_disk_gb`, or `min_ram_gb` exceeds its fixed RAM, the rung raises a TYPED terminal BEFORE any RunPod API call — no pod is provisioned, no provision cycle is wasted (the #958 regression).
3. The refusal reuses the existing typed-terminal machinery: `classify_terminal_exception` emits `failure_class: infra` + a distinct `reason:` token; the watcher's capacity-retry pass (`TRANSIENT_CAPACITY_REASONS`, keyed on `no_compute_available`) NEVER auto-retries it (no lane will free up to make the pod bigger).
4. Invariants preserved: RunPod stays the LAST rung; `cpu-bigmem` keeps its `CpuExhaustedNoRunpodLaneError` / `cpu_exhausted_no_runpod_lane` terminal verbatim; no auto-RunPod outside the terminal rung; a CPU fallback with NO stated requirement behaves byte-identically to today (existing `test_router_cpu_small_capacity_miss_falls_over_to_runpod` stays green).
5. `scripts/workflow_lint.py --check-asks` passes; `ruff check` on touched files passes; full pytest green.

## 3. Method delta (the five design questions, answered)

1. **Where does the disk requirement come from?** ONLY `spec.extra["boot_disk_gb"]` (already populated by `dispatch_issue.py --boot-disk-gb`, as #958's launch did). NO per-intent default requirement: a synthetic "cpu-mid conventionally needs 80 GB" default would refuse feasible runs whose plans never asked for 80, and would invent a plan-parsing layer the task explicitly forbids. Absent requirement → gate no-ops → today's behavior byte-identical.
2. **Feasibility check placement:** in `_runpod_terminal_rung`'s CPU branch, immediately after the existing not-in-map guard — this single placement covers all four automated paths (capacity fallback #656, sync workload failover #658, async workload failover #659, queue-timeout failover #783), because they all funnel through the rung (router.py lines 2796/3319/3336/3453/3504). Keyed on a new `RUNPOD_CPU_INSTANCE_CAPS` table next to `RUNPOD_CPU_INSTANCE_FOR_INTENT`. Refusal exception: a NEW `CpuFallbackInfeasibleError(CpuExhaustedNoRunpodLaneError)` with distinct reason `ROUTE_REASON_CPU_FALLBACK_INFEASIBLE = "cpu_fallback_infeasible_for_plan"` (rationale in §11 — distinct-reason-per-distinct-cause is the established router pattern; subclassing keeps every existing `except CpuExhaustedNoRunpodLaneError` / `except NoComputeAvailableError` site working unchanged as graceful degradation).
3. **Threading:** `RunPodBackend.launch` adds `--container-disk-gb max(50, boot_disk_gb)` when `spec.extra["boot_disk_gb"]` is present AND `spec.intent in RUNPOD_CPU_INSTANCE_FOR_INTENT` (lazy import — module-top stays base-only). **CPU-only**: on the GPU path, GCP `boot_disk_gb` semantically maps to the RunPod `/workspace` VOLUME (`--volume-gb`, default 200), not the container overlay; conflating them would silently inflate GPU container disks fleet-wide. GPU threading is scope creep — rejected (§11).
4. **RAM:** refusal-only (RAM is fixed per instance id), via an OPTIONAL new channel `spec.extra["min_ram_gb]` ← `dispatch_issue.py --min-ram-gb`. Absent → no RAM check → the documented cpu-mid 32-vs-16 GB asymmetry stands (CLAUDE.md accepts it "by design"). Deriving the RAM requirement from the intent's GCP machine (cpu-mid → e2-standard-8 → 32 GB) is REJECTED: it would refuse the RunPod fallback for EVERY cpu-mid job, structurally killing the #747 lane. The explicit flag lets a plan that genuinely needs >16 GB (like #958's stated 32) refuse up front, while RAM-light cpu-mid jobs keep the fallback.
5. **Tests:** enumerated in §5 with exact names.

| Probe outcome | `max_container_disk_gb` recorded | Extra action |

| P1 honors 80 (df shows ~80G) | cpu3c-8-16 → 80 (or the P2-measured bound) | none |

```python
    if machine.gpu_count == 0:
        # Feasibility gate (#1010, incident #958): the mapped RunPod CPU
        # instance has FIXED RAM and a provider disk cap; a plan-stated
        # footprint that exceeds them is deterministically infeasible --
        # refuse BEFORE the paid provision cycle. No stated requirement
        # (the common case) => no-op, byte-identical to pre-#1010 routing.
        instance_id = RUNPOD_CPU_INSTANCE_FOR_INTENT[spec.intent]
        caps = RUNPOD_CPU_INSTANCE_CAPS[instance_id]  # missing row -> loud KeyError
        extra = spec.extra or {}
        required_disk_gb = int(extra.get("boot_disk_gb") or 0)
        required_ram_gb = int(extra.get("min_ram_gb") or 0)
        shortfalls: list[str] = []
        if required_disk_gb > caps.max_container_disk_gb:
            shortfalls.append(
                f"disk: plan requires {required_disk_gb} GB > "
                f"{instance_id} max container disk {caps.max_container_disk_gb} GB"
            )
        if required_ram_gb > caps.ram_gb:
            shortfalls.append(
                f"RAM: plan requires {required_ram_gb} GB > "
                f"{instance_id} fixed {caps.ram_gb} GB"
            )
        if shortfalls:
            _post_terminal_failure_marker(
                spec=spec,
                marker_poster=marker_poster,
                reason=ROUTE_REASON_CPU_FALLBACK_INFEASIBLE,
                chosen_kind="gcp",  # precedent: the #677 guard above
                attempts=attempts,
            )
            raise CpuFallbackInfeasibleError(
                f"CPU intent {spec.intent!r}: RunPod CPU fallback ({instance_id}) "
                f"cannot satisfy the plan footprint — {'; '.join(shortfalls)}. "
                f"Route to cpu-bigmem (or shrink the footprint). residual_gap: {residual_gap}",
                attempts=[_attempt_to_dict(a) for a in attempts],
            )
```
