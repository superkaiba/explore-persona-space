## 1. Goal

Extend the `(h)` reuse-fitness check so that reusing a parent's training-input
file requires verifying the file resolves at the EXACT path/filename the new
consumer will assert or open (catching a naming-convention drift like #474
`i474_loc_A1.jsonl` vs a #664-style `mk_<source>_<arm>_<dose>_seed42.jsonl`),
not merely that the parent repo/dir exists on HF or in git — else require one
of rename/re-upload, consumer adaptation, or self-contained regen.

## 2. Prior work / context

**Current (h) shape** (`.claude/rules/artifact-reuse.md` lines 63-89): a single
lettered check for reused TRAINING-INPUT artifacts (a `train/*.jsonl` mix, an
on-policy response cache, a downstream-input `eval_results/` JSON — NOT an
adapter/checkpoint, which (e) covers). It verifies BOTH:

- **(i) source resolution** — the file is reachable through HF
  (`huggingface_hub.list_repo_files`) OR git-tree reachability
  (`git ls-tree -r origin/main -- <path>`) for a committed `eval_results/...`
  JSON.
- **(ii) target-backend fetchability** — the §9 backend can actually STAGE it
  (RunPod `snapshot_download`s any HF file; git-clone-only GCP/SLURM lanes
  stage no VM-local `data/`; committed `eval_results/...` arrive with the
  clone).

On a miss of EITHER, the plan must upload-first or add a self-contained regen
phase. The block already carries the #734 incident narrative and the
CDN-outage / region-restriction / gated-repo (`HF_TOKEN`) caveat.

**The incident this extends on (#734, 2026-06-30):** the reuse-fitness
verification confirmed the reused HF repo/dir EXISTED but did not force the plan
to check that the reused mix files resolve at the EXACT paths the new
dispatcher asserts. The parent produced files under one naming convention
(#474 `i474_loc_A1.jsonl`) while the new consumer's dispatcher asserted a
different one (#664-style `mk_<source>_<arm>_<dose>_seed42.jsonl`). Because the
directory existed, (h)(i) as written could read as satisfied ("resolves at the
cited path" — but the *cited* path was the parent's, not the consumer's), the
plan passed planning + 3 review rounds, and Phase 2 crashed mid-run at the
pre-train assert, forcing a code-change crash-fix round after a compute lane
was already provisioned. The gap is that "resolves" was verified against the
PARENT's path layout, not the NEW CONSUMER's asserted path layout.

**Enforcement chain** (unchanged 3-stage defense): `planner.md` step 5
(self-attested, enumerates (h)(i)/(h)(ii) at line 187) → `consistency-checker`
(independent re-check, enumerates (h)(i)/(h)(ii) at line 47) → `critic.md`
Methodology lens item 9 (REVISE, enumerates (h)(i)/(h)(ii) at line 75).

```markdown
  **(i) source resolution** — the file is reachable through EITHER HF
  (`huggingface_hub.list_repo_files`, for training mixes / on-policy caches /
  HF-uploaded eval JSONs) OR **git-tree reachability** for a committed
  `eval_results/issue_<M>/` JSON (`git ls-tree -r origin/main -- <path>`
  returns it — `planner.md` line 120 sanctions in-git eval JSONs as a reuse
  source, and the git-clone-only lanes pick them up via the clone); **(ii)
  consumer-exact path layout** — the plan NAMES the exact path/filename
  pattern the NEW consumer (dispatcher / driver / eval / training script) will
  assert-or-open (the string the new run passes to `assert path.exists()` /
  `open()` / `load_dataset`, glob-expanded across the design's
  source/arm/dose/seed cells), and confirms the reused parent file(s) resolve
  at THAT pattern — not merely that the parent repo/dir exists — via a
  `list_repo_files` glob (HF) or a `git ls-tree` glob (committed
  `eval_results/...`) matching the consumer pattern. A parent that shipped its
  files under a different naming convention (e.g. #474 `i474_loc_A1.jsonl`)

  `mk_<source>_<arm>_<dose>_seed42.jsonl`) FAILS this leg even though the
  directory resolves under (i); AND **(iii) target-backend fetchability** —
  the backend named in §9 can actually STAGE it. The RunPod lane
  `snapshot_download`s any HF-resolved file (its HF leg ≈ (i) there); the
  git-clone-only GCP and SLURM lanes stage NO VM-local `data/` — the GCE
  startup `git clone`s the repo at the cited branch (so committed
  `eval_results/...` arrive, but `data/issue_<N>/` does NOT) and HF/data-repo
  files need an explicit `snapshot_download` step in the workload — so a mix
  the parent BUILT but never UPLOADED nor COMMITTED is unreachable there and
  the pre-train `assert data_path.exists()` crashes phase2. The check FAILS
  when ANY of (i)/(ii)/(iii) fails (e.g. HF-resolved but a CDN/region/
  `HF_TOKEN` gate stops the §9 lane from staging it; or the parent repo
  resolves but no file matches the consumer-asserted path pattern). On a MISS,
  do NOT record the file as a confirmed reuse: either (a) rename / re-upload
  the parent file(s) to the consumer-asserted path pattern and cite that path,
  (b) adjust the new consumer to open the parent's actual path layout (naming
  the parent pattern in §4), or (c) add a self-contained regen phase in §4
  that rebuilds the mix on the worker under the consumer-asserted paths from
  the parent's deterministic build blocks, and flag it `must-rebuild` in §12
  Assumptions. Verify all three legs for EVERY reused training-input file the
  design loads, BEFORE recording it in §10 / §11. (Incident #734 round-4: a
  reused parent training mix was on neither HF repo, AND the parent's naming
  convention (#474 `i474_loc_A1.jsonl`) differed from the consumer's asserted
  path (a #664-style `mk_<source>_<arm>_<dose>_seed42.jsonl`); the plan passed
  planning + 3 review rounds and crashed phase2 at the pre-train assert on the
  GCP lane because the lane cannot stage a VM-local-only mix AND no file
  resolved at the asserted path.)
```

## 11. Decision rationale (§11)

This is a rule edit; the "load-bearing choice" analogue is *which enforcement
copies are in scope* and *how the new sub-item is worded*.

- **What:** Add the path-layout requirement as sub-item (h)(ii), NOT a new
  lettered check.
  **Why:** The bug is a refinement of "does the reused file resolve" — the
  same TRAINING-INPUT-artifact concern (h) already owns — not a new artifact
  class. Sub-item keeps the reuse checklist at (a)-(h).
  **Source:** `.claude/rules/artifact-reuse.md` lines 63-89 (the (h) block);
  task #798 constraint 4 ("a single lettered check with numbered sub-items, no
  new (i) letter").
- **What:** Mirror in `planner.md` L187, `consistency-checker.md` L47,
  `critic.md` L75.
  **Why:** These three surfaces ENUMERATE (h)'s sub-items inline; the rule's
  header (L13-16) mandates keeping them in sync when editing any check. A
  planner self-attests (h), the consistency-checker independently re-checks it,
  the critic REVISEs on it — all three read the sub-items, so all three must
  carry the new leg or the 3-stage defense has a hole.
  **Source:** `.claude/rules/artifact-reuse.md` L13-16 (sync mandate);
  `planner.md` L187; `consistency-checker.md` L47; `critic.md` L75.
- **What:** Do NOT edit CLAUDE.md L27 / LESSONS.md L15.
  **Why:** L27 is a content-summary (subsumes path-layout under "resolves");

  of sync on this specific mechanic. Editing them adds words without adding
  precision and bloats the always-on context.
  **Source:** CLAUDE.md L27; LESSONS.md L15 (both read this session).

  path layout → (iii) fetchability.

  consumer-uses → the-lane-can-stage-it. (ii) sits between (i) and (iii)

  existence miss but is checked before the lane-staging question.
  **Source:** the #734 root cause (path resolved in the parent dir but not at
