## 0.0 TL;DR (plain English)

- **What I'll run:** a small router fix — when a dispatch asks for a CPU-only machine (`cpu-small` / `cpu-mid` / `cpu-bigmem`), the router will skip the free SLURM cluster lanes entirely instead of probing them, warning "treating as unranked", and then attempting doomed launches on them. Plus regression tests reproducing the #1336 incident shape.
- **What I expect:** a CPU dispatch walks GCP → RunPod-CPU (or the GCP-only terminal for `cpu-bigmem`) exactly as the documented policy says, with zero SLURM warnings, zero wasted SLURM prepare/rsync attempts, and no behavior change for any GPU intent.
- **What would change my mind:** finding a real consumer that wants SLURM to run CPU jobs — then the right fix is a genuine 0-GPU sbatch feature (fork option (a)), which is a separate, bigger task, and I'd stop and ask.

## 0. Plan Summary (technical version)

**Change:** `router.py::_auto_route` excludes free SLURM lanes from the auto-chain candidate set when the spec's intent is CPU-only (new predicate `_is_cpu_only_intent(intent)` = `gcp.INTENT_TO_MACHINE.get(intent)` exists with `gpu_count == 0` — the established `_translated_runpod_intent` discipline, router.py L440-461). ## 1. Goal + requirement + acceptance criteria

> Make CPU-intent dispatches rank the free SLURM lanes instead of degrading to unranked.

(Task #1464 Goal, verbatim — `tasks/planning/1464/body.md` `## Goal`, re-read at plan-return time.)

**Interpretation (flagged for the approval gate).** The Goal's literal mechanism ("rank the free SLURM lanes") presupposes SLURM can serve CPU jobs. Investigation shows it cannot and, per documented policy, should not:

1. **Documented CPU routing policy names no SLURM leg.** CLAUDE.md § "CPU-only intents (#747)", `.claude/rules/compute-backend-failover.md` § "CPU intents", and the router module docstring item 8a (router.py L140-159) all define the CPU chain as GCP E2 → RunPod CPU (`cpu-small`/`cpu-mid`) and GCP-only + typed `cpu_exhausted_no_runpod_lane` terminal (`cpu-bigmem`). The free SLURM lanes appear nowhere in it.
2. **The SLURM lane structurally cannot run a 0-GPU job today.** `render_sbatch` (slurm.py L1245-1247) emits `--gpus-per-node={gpu_type}:{gpus}`, `--cpus-per-task={min(8*gpus,64)}`, `--mem={min(64*gpus,480)}G` — with `gpus=0` that is `--cpus-per-task=0` / `--mem=0G` (invalid) plus a GPU-typed gres line; the rendered preflight includes a GPU check (L1211); `stages_for_spec` (L1053-1167) has no CPU stage table and raises for `cpu-*` without `workload_cmd`. "Ranking" the lanes would rank lanes that cannot launch the job.
3. **The emitter's "skews routing toward paid rungs" rationale is inverted.** The standing lane order is GCP-FIRST (`DEFAULT_AUTO_LANE_ORDER`, router.py L596-598): the paid GCP lane is walked *before* any SLURM lane regardless of ranking, and ranking only orders SLURM lanes *among themselves*. The unranked degradation never diverted work toward paid compute; the actual harms are (i) three `route: estimate_fn raised … treating as unranked` warnings per CPU dispatch, (ii) up to three doomed free-lane attempts per dispatch — on a main-branch dispatch each attempt runs `SlurmBackend.prepare`'s full rsync + secrets push to the cluster (slurm.py L2088-2145) before `launch` dies at the render-time `ValueError`, and (iii) a latent trap: a first-class intent (#747) raising `ValueError` inside a routine estimate path.

**Requirement (the Goal's underlying ask):** a CPU-intent dispatch routes cleanly per the documented CPU chain — no "unranked" degradation, no doomed SLURM probes or attempts — while GPU-intent routing is byte-identical.

**Acceptance criteria:**

- AC1: an auto-route of a `cpu-mid` spec with free lanes wired never calls any free lane's `estimate_start_seconds`, never calls its `prepare`/`launch`, records no `nibi`/`fir`/`mila` `RouteAttempt`, emits no "treating as unranked" warning, and falls GCP → RunPod CPU (chosen_kind `runpod`) — the #1336 E1 regression shape.
- AC2: same for `cpu-bigmem`, ending at the typed `CpuExhaustedNoRunpodLaneError` / `cpu_exhausted_no_runpod_lane` terminal with zero RunPod launches (the #677 contract, preserved verbatim).
- AC3: GPU intents (`lora-7b`) and non-GCP-mapped intents (`ft-70b`) still include + probe the free lanes exactly as today (control).
- AC4: `cpu-*` intents remain deliberately absent from `_DEFAULT_GPUS_FOR_INTENT` / `_DEFAULT_TIME_BUDGETS_HOURS` / `stages_for_spec`, and each still fails fast with the existing `ValueError`s on an explicit SLURM pin (pinned by test — this bars the task body's half-fix diff sketch, which would render `--mem=0G` scripts).
- AC5: targeted pytest green; ruff check + format clean on touched files; `scripts/workflow_lint.py` no-flags default run green (router.py is workflow surface).

## 3. Design — fork resolution + exact edits

**Fork pick: (c) router-side exclusion.** Justification summarized in §1 (policy names no SLURM CPU leg; SLURM cannot render 0-GPU; (b) silences the warning but leaves doomed rsync-then-die launch attempts; (a) is a new feature nobody asked for — see §11 for the full rationale and §6 for the reversal trigger).

### Edit 1 — `src/explore_persona_space/backends/router.py`: predicate + candidate-assembly skip

New module-level helper, placed directly after `_translated_runpod_intent` (~L461), reusing its established `INTENT_TO_MACHINE.get` discipline:

```python
def _is_cpu_only_intent(intent: str) -> bool:
    """True iff ``intent`` maps to a 0-GPU machine in ``gcp.INTENT_TO_MACHINE``.

    Direct ``INTENT_TO_MACHINE.get(...)`` — never :func:`gcp.machine_for_intent`
    — so RunPod-/SLURM-native intents with no GCP row (``ft-70b``) and unknown
    intents read ``False`` instead of raising (the
    :func:`_translated_runpod_intent` discipline). Single source of truth: a
    future CPU intent added to ``gcp.INTENT_TO_MACHINE`` with ``gpu_count=0``
    inherits the CPU routing semantics automatically (#1464).
    """
    machine = INTENT_TO_MACHINE.get(intent)
    return machine is not None and machine.gpu_count == 0
```

(`INTENT_TO_MACHINE` is already imported at router.py L213; `cpu-bigmem`/`cpu-small`/`cpu-mid` carry `gpu_count=0` at gcp.py L405-422.)

In `_auto_route`'s candidate assembly (L4003-4013), skip free lanes for CPU-only intents:

```python
    # Build the candidate list in lane order (skipping unwired lanes +
    # Mila-when-down + GCP-when-unwired + free lanes on CPU-only intents).
    cpu_only = _is_cpu_only_intent(spec.intent)
    if cpu_only and free_backends:
        logger.info(
            "route: CPU-only intent %r — free SLURM lanes (%s) excluded from "
            "the auto chain. The documented CPU chain is GCP E2 -> RunPod CPU "
            "for mapped intents (#747) / GCP-only for cpu-bigmem (#677); the "
            "SLURM lane has no 0-GPU sbatch render (#1464, incident #1336).",
            spec.intent,
            ", ".join(sorted(free_backends)),
        )
    candidates: list[tuple[ComputeBackend, BackendKind]] = []
    for kind in lane_order:
        if kind == "gcp":
            if gcp_backend is not None:
                candidates.append((gcp_backend, "gcp"))
            continue
        if cpu_only:
            continue
        backend = free_backends.get(kind)
        ...  # unchanged
```

Effects, all downstream-for-free: the SLURM group never forms in `_split_lane_groups`, so `_estimate_lanes` (L5086) is never invoked for CPU intents (no ValueError→warning→unranked degradation), the stage-1 reconnect scan (which iterates `candidates`) skips SLURM (a CPU job can never have a live SLURM job — nothing lost), `_try_free_lanes` never attempts a doomed prepare/launch, and the terminal `_runpod_terminal_rung` CPU handling (mapped fallover / #677 typed terminal / #1010 footprint gate) is reached exactly as today, only faster. The `residual_gap` `wired:` list (L4107-4110) then truthfully reflects the CPU chain. Explicit `backend: nibi|fir|mila` pins with a CPU intent are untouched — they take `_pinned_route`'s existing fail-fast (`BackendPrepareError`/launch `ValueError` → typed terminal), correct for a config error.

One docstring sentence added to the module docstring item 8a (~L140-159): "Free SLURM lanes are excluded from the auto chain for CPU-only intents — the lane has no 0-GPU sbatch render (#1464)." (The rule file `.claude/rules/compute-backend-failover.md` already describes the CPU chain without SLURM; no rule-file edit needed — the code moves *toward* the documented policy.)

## 11. Decision rationale

- **What:** design-fork pick — (c) router-side exclusion of free SLURM lanes for CPU-only intents. **Why:** matches the documented CPU chain exactly (SLURM appears nowhere in it); removes all three observed harms (warnings, unranked degradation, doomed prepare/launch attempts incl. per-lane rsync on main-branch dispatches); zero behavior change for GPU intents; smallest diff that makes routing behave per policy. **Source:** CLAUDE.md § "CPU-only intents (#747)"; `.claude/rules/compute-backend-failover.md` § "CPU intents: cheap CPU lanes + the scoped #677 terminal (#747)"; router.py module docstring item 8a; incident evidence #1336; code reading §3. **Alternatives:** (a) full SLURM 0-GPU support — rejected: a new feature (renderer 0-GPU form, CPU partitions, GPU-preflight and venv-extras changes, new time/cpu/mem defaults) with no policy mandate and no consumer; the task body's dict-only variant is actively harmful (`--cpus-per-task=0` / `--mem=0G` renders, `sbatch --test-only` probes of unrunnable scripts). (b) estimate-only short-circuit (return `None` silently for 0-GPU intents) — rejected: silences the warning but still ranks unlaunchable lanes as "park-eligible" and leaves the doomed prepare (rsync + secrets push) → launch-ValueError attempts on every CPU dispatch; it also institutionalizes "unranked" as the *designed* state for a first-class intent, which is the exact degradation the Goal objects to.
- **What:** predicate keyed on `gcp.INTENT_TO_MACHINE` `gpu_count == 0` via `.get()`, not a hardcoded intent frozenset and not `machine_for_intent`. **Why:** single source of truth (a future CPU intent joins automatically); `.get()` never raises for non-GCP intents (`ft-70b`). **Source:** the in-file precedent `_translated_runpod_intent` (router.py L440-452, #940) and `_declared_width` (L2585-2593). **Alternatives:** a literal `frozenset({"cpu-small","cpu-mid","cpu-bigmem"})` — rejected as a second copy of the intent taxonomy that drifts; `machine_for_intent(spec)` — rejected, raises on unmapped intents and honors `machine_spec_override` threading.
- **What:** keep slurm.py fail-fast `ValueError`s byte-identical; comment-only slurm.py edit. **Why:** explicit SLURM pins with a CPU intent are config errors and must stay loud (#653/#535 fail-fast discipline); the comment + AC4 pin bar the half-fix. **Source:** slurm.py's own fail-fast docstrings (L348-353, L400-406); code reading. **Alternatives:** friendlier CPU-specific error text in slurm.py — dropped as scope creep (allowed later; not needed for the Goal).
