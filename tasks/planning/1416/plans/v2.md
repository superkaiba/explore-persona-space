Zero rows sums to 0 MiB → PASS.
- **Dispatcher lineage** — `gpu_guard_one` (`scripts/issue825_turndyn_dispatch.sh:109`, `issue-825` branch) returns PASS the instant compute-apps output is empty (`[[ -z $apps ]] && return 0`); `gpu_guard` in the onpolicy sibling, same family.
- **experimenter.md step 9** — the mandatory pre-launch probe runs `--query-compute-apps` + `pgrep -af EngineCore` only.

**Why none covers this:** every one of those guards keys on the presence/killability of a PROCESS ROW. The #825 r11 condition has NO row: pod-825 (8×A100) GPU 4 arrived holding 72,505 MiB used / 8.0 GiB free, stable ~5 min, with zero compute-apps rows, clean `pgrep`, no container process mapping `/dev/nvidia*`, confirmed via `torch.cuda.mem_get_info` — and nothing killable in-container. The two #1090/#1333 siblings are about rows whose PIDs are unmatchable; this is the third failure shape: no rows at all.

**Mechanism grounding (web search, 2026-07-16):** NVML's per-process accounting is PID-visibility-dependent while GPU memory usage is tracked at the DEVICE level independent of PID visibility — a container can read nonzero `memory.used` with an empty process table. Documented upstream class:

- https://github.com/NVIDIA/nvidia-docker/issues/1483 (NVML reports host-namespace PIDs — already the citation anchor of the #1090/#1333 sibling entries)
- https://github.com/NVIDIA/nvidia-docker/issues/179 (in-container `nvidia-smi` process table reads empty while device memory usage is nonzero)
- https://forums.developer.nvidia.com/t/nvidia-smi-doesnt-show-running-processes-inside-the-container/343361 (same class, NVIDIA forums)

The entry states the mechanism honestly: from inside the container, "another tenant's live process outside our visibility" and "a dead host process whose allocation the driver has not released" are indistinguishable — and the RULE is identical either way (the device-level counter is the only read that cannot be fooled).

**Method delta:** add the missing third sibling entry + wire the device-level read into the one mandatory workflow-surface enforcement point (experimenter step 9). Dispatcher scripts inherit the pattern through the rule (they are experiment code, out of scope for a workflow-fix session).

**Entry text (land nearly verbatim; one physical line, matching the register of its neighbors):**

> - **A FRESH pod can arrive with a GPU already held by a FOREIGN tenant — `--query-compute-apps` reads EMPTY, in-container `pgrep` / `/proc` scans are clean, yet device-level `--query-gpu=memory.used` shows tens of GiB held, UNKILLABLE from inside: GPU-free gates must read per-GPU `memory.used`, never compute-apps alone.** Third member of the NVML-pid-visibility family (the self-exclusion false-POSITIVE and live-orphan false-NEGATIVE entries above, #1090/#1333): NVML's per-process accounting rows are PID-VISIBILITY-DEPENDENT — a holder the container's NVML view cannot resolve (another tenant's container, or a dead host-side process whose allocation the driver has not released; indistinguishable from inside, same disposition) produces NO compute-apps row at all — while `memory.used` is a DEVICE-level counter independent of process visibility, so it reads the truth when the process table is blind (documented class: NVIDIA/nvidia-docker#1483 — NVML reports host-namespace pids; NVIDIA/nvidia-docker#179 — in-container process table empty while device memory.used is nonzero). CONSEQUENCE — every guard in the lineage passes a foreign hold: `gpu_guard_one` (`scripts/issue825_turndyn_dispatch.sh` on the `issue-825` branch) returns PASS the instant compute-apps is empty, and even the newest drain-verdict recipe (`scripts/issue1333_dispatch.py::_wait_gpus_free`/`_gpu_hygiene`, entry above) derives its per-GPU `used_memory` totals BY SUMMING compute-apps rows mapped via `gpu_uuid` — zero rows sums to 0 MiB and PASSES. DISTINGUISH from the crash-orphan and pid-namespace siblings above: there a row (or a killable container process) EXISTS and the reap recipes work; here there is NOTHING to reap — no fuser target, no `--gpu-reset` permission in a RunPod container — a BAD-HOST infra condition, not an orphan-cleanup case. Diagnostic signature: on a freshly-provisioned pod, one GPU's device-level `memory.used` reads tens of GiB stable across minutes (pod-825: 72,505 MiB used / 8.0 GiB free, ~5 min) while compute-apps is EMPTY and `pgrep -af EngineCore` is clean; confirm with `CUDA_VISIBLE_DEVICES=<i> uv run python -c "import torch; print(torch.cuda.mem_get_info(0))"` (free collapses to the residue). RULE: every GPU-free gate (pre-launch probe, dispatcher gpu-guard, phase-boundary drain verdict) reads BOTH `--query-compute-apps=pid,used_memory,gpu_uuid` (orphans — killable, reap per the entries above) AND `nvidia-smi --query-gpu=index,memory.used --format=csv,noheader` per GPU against the same residual-floor family (default 2048 MiB, the `EPM_GPU_HYGIENE_FLOOR_MIB` convention — re-derive for models whose weights approach it; a real foreign hold reads tens of GiB); device-level `memory.used` above floor with ZERO compute-apps rows on a FRESH pod = DEFECTIVE PROVISION — do NOT launch, and never fan out one worker per physical GPU over it (the unit on the held GPU OOMs and aborts the whole queue; masking the held GPU out via `CUDA_VISIBLE_DEVICES` is a deliberate degraded-width decision, not a default) — post `epm:failure v1 failure_class: infra reason: gpu-residual-memory-foreign-owner` and let the lifecycle layer terminate + re-provision. Experimenter-side enforcement: `.claude/agents/experimenter.md` Pre-Launch step 9 (the probe carries both queries); long-form twin: `.claude/agent-memory/experimenter/feedback_gpu_foreign_allocation_no_compute_apps.md`. (Incident #825 r11, 2026-07-16: pod-825 (8×A100) arrived with GPU 4 holding 72,505 MiB with zero compute-apps rows, unkillable in-container; the experimenter refused launch — `epm:failure` v17 / `epm:failure-lesson` v7; a compute-apps-keyed guard would have passed straight through and the first GPU-4 unit would have OOM-aborted the whole fan-out.)
