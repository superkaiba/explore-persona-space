# Plan v1 — #2611: stop `git_provenance()`'s `git status` from taking `.git/index.lock` (fix: `--no-optional-locks`)

`kind: infra` bug fix. Direct plan (bug-fix category, CLAUDE.md `/adversarial-planner`
carve-out); minimum plan-review floor applied: this persisted version + `verify_plan.py`
pre-pass + one Claude critic (Methodology lens).

## Requirement + acceptance criteria

**Requirement.** `src/explore_persona_space/orchestrate/provenance.py` runs `git status`
(tree-wide at `_git_dirty_status`, per-path in `_argv0_git_state`) under a 5 s
`subprocess.run(timeout=...)`. `git status` by default takes `.git/index.lock` to write back
its refreshed stat cache (an "optional lock"); when the timeout kill lands while the lock is
held, the zero-byte `index.lock` is orphaned and EVERY later git operation in that checkout
fails rc=128 until someone removes it by hand. Observed live on #2546 arm 3 (`p6_publish`
FATAL rc=128, lock mtime 2 s before the `p5_fits` report that carried the documented
`repro.git_dirty = None` timeout signal; MooseFS FUSE `/workspace` makes a >5 s tree-wide
status ordinary). The module is shared: 96 files under `src/` + `scripts/` reference
`git_provenance` (re-measured at clarify time; the body's 81 has grown). A repo-root caller
that orphans the lock would block CONCURRENT sessions' `task.py` commits — wider blast
radius than the pod incident.

**Acceptance criteria.**

1. `_run_git` passes the global `--no-optional-locks` option on EVERY git invocation in the
   module, so no probe can take (and therefore orphan) `.git/index.lock`. This is git's
   intended affordance for status-polling tools (equivalent to `GIT_OPTIONAL_LOCKS=0`);
   available since git 2.15 — verified working on the VM's git 2.34.1 at clarify time
   (`git --no-optional-locks status --porcelain=v1 --untracked-files=no` ran clean); the
   pinned pod image (ubuntu 22.04) and GCE/SLURM lanes all carry ≥2.34.
2. Probe OUTPUT semantics unchanged: same porcelain parsing, same dirty/None sentinel
   contract, same `--literal-pathspecs` behavior. The only behavioral delta is that git
   skips the opportunistic index stat-cache write-back (a pure performance cache; correct
   status output does not depend on it).
3. Module docstring's contract block documents the new invariant: probes never take
   optional locks, so a timeout-killed probe cannot orphan `.git/index.lock` (#2611,
   observed #2546).
4. New regression tests in `tests/test_orchestrate_provenance.py` (conventions: real
   `tmp_path` git repos, as the existing 25 tests do):
   - **argv pin** — capture-and-delegate monkeypatch on `subprocess.run`; call
     `git_provenance()` in a real repo; assert every captured argv begins
     `["git", "--no-optional-locks", "--literal-pathspecs"]` (global options before the
     subcommand — order matters: both are global flags and must precede the subcommand).
   - **no-index-write behavioral pin** — real repo with a committed file; `os.utime` the
     tracked file to stale its cached stat entry; record `.git/index` `st_mtime_ns` +
     content bytes; run `_git_dirty_status(cwd=repo)`; assert the index file is
     byte/mtime-unchanged (git skipped the optional refresh write) AND
     `.git/index.lock` does not exist afterward.
5. Full existing test file passes unchanged (`uv run pytest
   tests/test_orchestrate_provenance.py`), plus the Step 9c mapped-test gate.

## Method delta (vs alternatives considered)

- **Chosen:** `--no-optional-locks` global flag inside `_run_git` — one enforcement point
  covering every probe in the module at once, matching the existing `--literal-pathspecs`
  pattern (same global-option slot, same rationale structure).
- **Rejected: raise `_GIT_TIMEOUT_SEC`.** Makes the orphan rarer, not impossible — the
  task body explicitly rules this out; the lock-taking is the defect.
- **Rejected: caller-side stale-lock deletion.** A staleness heuristic cannot distinguish
  a killed probe's lock from a live concurrent writer's; deleting wrong corrupts another
  session's commit (the body's explicit anti-goal; also the #2509 Step 10d retry task is
  the correct home for contention-side handling — different mechanism, not touched here).
- **Rejected: `GIT_OPTIONAL_LOCKS=0` env in the subprocess env.** Semantically equivalent;
  the flag form is more local, self-documenting at the argv, and testable by argv
  inspection. (Either satisfies the requirement; flag chosen for consistency with
  `--literal-pathspecs`.)
- **Considered, verified not needed: explicit child reap on timeout.** CPython's
  `subprocess.run` kills and reaps the direct child on `TimeoutExpired`
  (`process.kill()` + `communicate()`), and `git status` spawns no long-lived
  grandchildren in this repo (no submodules). No code change; noted here so the
  secondary-hardening bullet in the task body is dispositioned.
