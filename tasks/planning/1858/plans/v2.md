## 1. Requirement + acceptance criteria (kind: infra)

**Requirement.** The RunPod execute-workload boot sync (`_execute_workload_on_pod` leg (a), `src/explore_persona_space/backends/runpod.py`) must not surface a terminal `runpod_workload_start_failed` on the FIRST MooseFS-hang of a remote git op. Incident #1769 fu1 (2026-07-30, verified from the task's own markers): the branch-sync ssh hit the 180 s local `TimeoutExpired`, the local kill left the REMOTE git (pid 1992) hung on MooseFS holding `.git/index.lock`, the existing conditional reap (`pgrep -x git || rm -f .git/index.lock`) can never fire against a LIVE hung git, and the leg went straight to terminal — ~1.5 h manual stall until a hand kill+reap+resync succeeded ON THE SAME POD (proving a bounded automatic retry would have recovered it).

**Acceptance criteria:**
1. The remote branch-sync script self-bounds its git ops with remote-side `timeout` wrappers whose SUMMED worst case stays strictly under the 180 s local ssh bound (reference sizing: `timeout -k 10 120` on `git fetch`, `timeout -k 10 20` on `checkout -f -B`, `timeout -k 10 20` on `reset --hard` — 160 s + overhead < 180 s), so a FUSE-hung git op is killed REMOTELY (the lock-holder dies with it) and a slow-but-healthy sync cannot trip a spurious local timeout before the remote bounds resolve.
2. On the FIRST sync failure (local `TimeoutExpired` or non-zero rc / missing `SYNC-OK`), the leg runs a bounded REAP script that is SAFE ON THE ZERO-GIT PATH (the modal designed path — the remote `timeout` already killed the hung git): the `pgrep -x git` enumeration is guarded (`|| true`-style) so an empty match yields `killed=0 survivors=0`, never a `set -eu` exit; any live git pids are SIGKILLed with a bounded death-wait (~10 s poll) and survivors re-enumerated; `.git/index.lock` is then removed UNCONDITIONALLY; the script always emits `REAP-OK killed=<n> survivors=<m> lock_removed=yes` and exits 0 on every non-wedged path.
3. After a reap with zero survivors, the sync is retried EXACTLY ONCE (fresh 180 s local bound). Success → the leg proceeds to scripts (b)/(c) unchanged.
4. If the reap reports UNKILLABLE survivors (`survivors>0` — D-state; the MooseFS mount itself is wedged and retry is futile per the gotchas read-wedge ladder), OR the retried sync fails again, raise `RunPodWorkloadStartError` exactly as today with the reap evidence embedded in the message (`sync retry after reap failed` / `unkillable git survivors (moosefs D-state signature)`), pod left RUNNING for diagnosis (RunPod-as-diagnosis-lane doctrine; #954 partial-handle contract untouched).
5. Unit tests in `tests/test_runpod_workload_exec.py` cover:
   (i) first-failure → reap → retry-success path (ssh call sequence recorded = sync, reap, sync, launch, verify; workload proceeds);
   (ii) reap-with-survivors → immediate raise, NO retry;
   (iii) retry-failure → raise with reap evidence in the message;
   (iv) rendered reap script passes `bash -n` + never shells `task.py` (extend the existing render-script tests);
   (v) success path unchanged (existing tests stay green);
   (vi) **real-bash execution of the RENDERED reap script on the zero-git branch**: run the rendered script via `subprocess` against a tmp-dir fake clone (`.git/index.lock` pre-created) with PATH-shimmed stub `pgrep`/`kill` binaries (stub `pgrep` exits 1 = no match; NEVER live pgrep/kill on the shared VM), asserting rc=0, the `REAP-OK killed=0 survivors=0 lock_removed=yes` line, and the lock file removed.
