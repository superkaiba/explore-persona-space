### (a) `scripts/consolidate_lessons.py` (pure Python)

**Purpose.** Deterministically perform the three janitorial operations the
`/daily` consolidation paragraph describes — dedupe day-of lessons against agent
memory, promote recurring lessons into `.claude/rules/gotchas.md`, prune
over-eager `generalizes: yes` memory entries — over a rolling window of
`epm:failure-lesson v1` markers, idempotently, failing loud, logging counts.

**CLI (argparse).**

```
consolidate_lessons.py
  --window-days N      int, default 7   # rolling window for marker scan + recurrence
  --apply              store_true       # perform + commit mutations (the cron default)
  --dry-run            store_true       # no writes/commits; print what WOULD change
  --json               store_true       # emit machine-readable summary dict to stdout
  --log-counts         store_true, default True  # always log the counts line (see Outputs)
```

Argument rules:
- `--apply` and `--dry-run` are mutually exclusive (argparse mutually-exclusive
  group). If NEITHER is given, default to `--dry-run` (fail-safe: never mutate
  unless explicitly told to; the cron passes `--apply`).
- `--log-counts` is on by default and effectively always-on; the flag exists so
  a caller can be explicit / a test can assert it.

**Inputs it reads.**
1. **All `epm:failure-lesson v1` markers in the rolling window, across all
   tasks.** Iterate `task_workflow._load_registry()["tasks"]`; for each task
   read its `events.jsonl` via `task_workflow._iter_jsonl(path/"events.jsonl")`
   (tolerant of malformed lines, per the existing helper); keep rows where
   `kind == "epm:failure-lesson"` AND the top-level `ts` is within
   `now_utc - window_days`. Parse the structured fields out of `note` with the
   three-tier `_parse_lesson_note(note) -> dict | None` parser (see Step 1
   below). Each parsed lesson carries: `task_id`, `ts`, `failure_class`,
   `phase`, `lesson` (body text), `generalizes`, `owning_agent`,
   `gotcha_candidate`.
2. **`.claude/agent-memory/<agent>/feedback_*.md`** (frontmatter + body) for the
   owning agents that appear in the window — read for dedupe + prune scope.
   `_read_memory_file(path) -> (frontmatter_dict, body_str)` tolerating both
   frontmatter shapes (§2). Plus the per-agent `MEMORY.md` index.
3. **`.claude/rules/gotchas.md`** — read the existing bullet bodies for the
   idempotent-promote check.
4. **`tasks/_orphaned_markers/`** — NOT considered (default NO; the task body
   does not request it; those are markers that failed to post to a task and are
   out of scope for cross-task consolidation). State this explicitly in a
   module docstring comment.

**Step 1 — `_parse_lesson_note(note) -> dict | None` (THREE-TIER PARSER).**

The live tree's marker format is NOT uniform (§12 Assumption 3: 48/55 are the
common sentinel-block shape; 7/55 are off-format — 3 bare-fields, 3 truncated
open-no-close, 1 no-open). Two of the off-format markers (#653, #667, both
2026-06-25) fall inside the first nightly cron's 7-day scan window, so a
v1-style "RAISE on any kind-matched note with no parseable block" would crash
the very first `--apply`. The parser therefore tiers:

- **Tier 1 — sentinel block (the common shape, covers 48/55).** If the note
  contains the `<!-- epm:failure-lesson v1 -->` … `<!-- /epm:failure-lesson -->`
  block (`LESSON_BLOCK_RE`), parse the `key: value` field lines from INSIDE the
  block.
- **Tier 2 — bare-fields fallback (NEW; covers the 3 bare-fields markers
  #653/#667/#640).** If no sentinel block matches but the bare note body
  contains the required field lines (`failure_class:` AND `lesson:` at line
  starts), parse the fields directly from the bare note. Field regex, applied
  line-by-line in MULTILINE mode:
  `^\s*(?P<key>failure_class|phase|lesson|generalizes|owning_agent|gotcha_candidate):\s*(?P<val>.+?)\s*$`.
  The `lesson:` value may span multiple lines — the parser collects the lesson
  body from the `lesson:` line's value onward, appending subsequent lines UNTIL
  the next recognized `key:` line OR EOF (so a multi-line lesson body is
  preserved). The SAME multi-line-lesson collection rule applies inside tier 1's
  block body, so tier 1 and tier 2 yield identical field dicts on identical
  content. Tier 2 is used ONLY when tier 1 misses; a note that satisfies BOTH
  (has the block) always takes tier 1.
- **Tier 3 — skip-with-WARN (NEW; replaces the v1 hard-RAISE for genuinely
  unparseable notes).** If NEITHER tier 1 nor tier 2 produces the required
  fields (`failure_class` AND `lesson`) — i.e. a truncated open-no-close note, a
  no-open note, or an empty note — the parser returns `None` and the caller
  LOGS a WARN (`unparseable failure-lesson note in task #<id> @ <ts>: <reason>`)
  and SKIPS the marker. This mirrors `_iter_jsonl`'s own tolerant-skip posture
  for writer-crash artifacts: a truncated note IS a writer-crash artifact, the
  same class `_iter_jsonl` already swallows for a truncated trailing JSONL line.
  The skip is COUNTED into the summary under a new key `unparseable_skipped`
  (count + the `(task_id, ts)` list), so a rising skip count is visible in the
  nightly log rather than silently lost.

**Which conditions are skip-with-WARN vs hard-RAISE (explicit).**

- **Skip-with-WARN (tier 3, NON-fatal):** a kind-matched note that yields
  neither a tier-1 block nor tier-2 required fields (truncated / no-open /
  empty). These are writer-crash artifacts of the marker, not lessons the
  deterministic logic can act on; skipping them loses nothing the per-lesson
  `/issue`-time route did not already handle, and counting them keeps the loss
  visible.
- **Hard-RAISE (FATAL, non-zero exit + traceback) survives ONLY for conditions
  the deterministic logic cannot recover from WITHOUT corrupting state:**
  1. a SUCCESSFULLY-parsed lesson (tier 1 or tier 2) whose downstream write
     would corrupt agent-memory — e.g. a `generalizes: yes` lesson with a
     MISSING / empty `owning_agent` (no target dir to dedupe/prune against, so a
     guessed write would mutate the wrong agent's memory);
  2. a `_git_commit` failure on an `--apply` run (the mutation half-landed; a
     swallow would leave the tree inconsistent);
  3. an unreadable TARGET file that an index line or a parsed lesson positively
     references (e.g. a `MEMORY.md` index bullet pointing at a `feedback_*.md`
     that cannot be opened) — distinct from a missing OPTIONAL input.

  These are NOT "a bad marker body" (which tier 3 absorbs) — they are
  "the recovery path itself would corrupt the repo," which is exactly the
  fail-fast-never-hide case CLAUDE.md reserves the RAISE for.

**Operations (deterministic).**

1. **Dedupe day-of (window) lessons against the owning agent's memory.**
   For each window lesson with `generalizes: yes` (these are the only ones the
   `/issue` hook persisted to memory), compute a normalized similarity against
   every `feedback_*.md` body in that owning agent's dir using
   `difflib.SequenceMatcher(None, a, b).ratio()` over normalized lesson text
   (lowercase, collapse whitespace, strip the `<!-- -->` sentinels and the
   `failure_class:`/`phase:` lines so only the lesson prose is compared). If
   `ratio >= T` (T = 0.85) against an existing entry, the lesson is a DUPLICATE
   already captured — it is NOT re-written; counted as `deduped`. (The dedupe
   here is "do not create a redundant new memory entry"; the per-lesson hook
   already wrote one entry per `generalizes: yes` lesson, so consolidation's job
   is to catch when two same-day lessons collapsed to one concept — it does NOT
   delete the existing memory file, it just records the no-op so promotion/prune
   downstream treats the cluster as one. Where TWO window lessons are
   mutually `>= T` similar AND both already have memory entries, MERGE is
   recorded as a dedupe count; the canonical (lowest task_id, then lexically
   first slug) entry survives and the duplicate sibling's MEMORY.md index line +
   feedback file are removed — but ONLY when both files are lesson-derived, i.e.
   their frontmatter `type`/`metadata.type` == `feedback` AND a window lesson
   maps to each. Hand-authored memories are never touched.)

2. **Promote recurring lessons into `.claude/rules/gotchas.md` (idempotent).**
   A lesson **recurs** when, within the window, there exist `>= K` (K = 2)
   DISTINCT `task_id`s carrying a lesson with the SAME `phase` AND the SAME
   `failure_class` AND pairwise lesson-text similarity `>= T` (the same
   `SequenceMatcher` ratio + normalization as op 1). For each recurring cluster:
   - **Idempotency check FIRST:** compute the candidate gotcha bullet body
     (a one-line lead-bolded bullet: `- **<phase trap, ≤80 chars>** — <lesson
     body, first 1-2 sentences> (#<task>, #<task>)`). Normalize it and every
     existing `# Gotchas` bullet body the same way; if `SequenceMatcher` ratio
     `>= T` against ANY existing bullet, the gotcha is ALREADY present →
     skip (counted `promote_noop`). This is what makes a 2nd run a no-op.
   - Else append the bullet under `# Gotchas` (after the last existing bullet,
     preserving file order); counted `promoted`.
   - **`gotcha_candidate: yes` lessons:** these are semantically "belongs in a
     SEPARATE rule file / needs a workflow-fix" rather than a gotchas.md bullet,
     and the `/issue`-time hook ALREADY routes them through the workflow-fix-on-bug
     protocol per-lesson. **Decision: the script does NOT itself file/route a
     workflow-fix and does NOT emit a `<!-- workflow-fix-candidate v1 -->` block
     to stdout. It DEFERS to the existing inline `gotcha_candidate: yes` →
     workflow-fix-candidate route (which already fired at `/issue` time).** It
     records such lessons in the summary under `gotcha_candidate_seen` (count +
     task ids) for visibility, and does NOT auto-promote them into gotchas.md
     (avoiding a double — once as a gotchas.md bullet here, once as a workflow-fix
     elsewhere). **Justification:** emitting a `<!-- workflow-fix-candidate v1
     -->` block from a *cron* would mean a non-interactive, non-orchestrator
     process trying to drive the workflow-fix file/spawn default — but the cron
     has no orchestrator turn to consume the block, and the per-lesson route
     already handled routing at `/issue` time, so emitting one here is at best a
     no-op and at worst a duplicate file. Deferring keeps the single-source-of-truth
     routing (the inline `/issue` hook) and avoids the cron-as-workflow-fix-session
     recursion concern entirely (§7). gotchas.md promotion is reserved for
     `gotcha_candidate: no` recurring lessons, which have no other home.

3. **Prune over-eager `generalizes: yes` memory entries.**
   A `generalizes: yes` memory entry is **over-eager** (a one-off that should
   not have generalized) when ALL hold:
   - every source `epm:failure-lesson` marker that maps to this memory entry
     (matched by `owning_agent` + lesson-text similarity `>= T`) sits on a task
     whose CURRENT status is terminal (`completed` / `archived`) — i.e. the work
     that produced it is finished; AND
   - NO further marker within the window tags the SAME `(phase, failure_class)`
     pair on any OTHER task (it never recurred → the generalization was
     speculative); AND
   - the entry is lesson-derived (frontmatter `type`/`metadata.type` ==
     `feedback`) — never a hand-authored memory.
   Over-eager entries are REMOVED (the `feedback_*.md` file + its `MEMORY.md`
   index line), counted `pruned`. **Conservative default:** if ANY of the three
   conditions cannot be positively established (e.g. a source task's status is
   unreadable, the frontmatter is ambiguous), the entry is KEPT (fail toward
   keep — same posture as the disk-guard / session reapers).

4. **Log counts.** Always emit a single counts line: `input markers seen`,
   `deduped`, `promoted`, `promote_noop`, `pruned`, `gotcha_candidate_seen`,
   `unparseable_skipped`, `no-ops` (total when promoted+pruned+deduped == 0).

    the `/daily` writes; a moderately high ratio catches genuine near-duplicates
    (re-phrasings of the same trap) while leaving distinct lessons separate.
    Lesson bodies are short prose (1-3 sentences); 0.85 on normalized short text
    requires substantial overlap, biasing toward UNDER-merging (safer: a missed
    dedupe leaves a redundant memory entry, which is harmless; an over-merge could
    drop a distinct lesson, which is not). The normalization strips the
    `failure_class`/`phase` lines + sentinels so only prose is compared.
  - *Source:* `ungrounded — needs smoke-test`. Confirmed against the fixture-day
    parity run (§6); tune up if the fixture run over-merges, down if it
    under-merges, before trusting `--apply`.
  - *Alternatives considered:* a stable content hash on normalized text (rejected
    — exact-match misses re-phrasings, the dominant near-dup case); a higher 0.9
    (rejected — too strict for short prose with synonym drift); an LLM
    similarity call (rejected — reintroduces the non-determinism the task removes).

  - *What:* a lesson PROMOTES to gotchas.md when `>= 2` DISTINCT task_ids in the

  - *Why:* the body explicitly specifies "default 7d" and notes it "subsumes the

- **Tolerant three-tier parser (sentinel → bare-fields → skip-with-WARN) instead
  of a single sentinel-block parser that RAISEs on any miss.**
  - *What:* `_parse_lesson_note` tries the `<!-- epm:failure-lesson v1 -->` block
    first, falls back to a bare `key: value` field parse, and skips-with-WARN
    (counted into `unparseable_skipped`) only when neither yields the required
    fields — reserving the hard-RAISE for corrupting-write / git-commit /
    unreadable-target cases (§4a Step 1).
  - *Why (tied to Goal):* the Goal is a RELIABLE, re-runnable deterministic cron;
    a parser that crashes on the first off-format marker would defeat the
    reliability the task exists to deliver. The marker format is not uniform
    across the existing tree, so a single-shape RAISE-on-miss parser would crash
    the very first nightly `--apply` (the in-window #653/#667 markers, both
    2026-06-25). Tolerating writer-crash-artifact markers while still
    fail-loud-RAISEing on genuinely corrupting conditions matches both the
    "fail fast, never hide" rule (the RAISE half) and `_iter_jsonl`'s established
    writer-crash tolerance (the skip half).
  - *Source:* `empirical (7 of 55 real markers off-format, fact-check v1)` —
    the fact-checker enumerated all 55 real `epm:failure-lesson` marker rows in
    the live tree and found 7 (13%) off-format (3 bare-fields, 3 truncated, 1
    no-open), 2 of them inside the first nightly 7-day window.
  - *Alternatives considered:* a single sentinel-block parser that RAISEs on any
    miss (the v1 design — rejected: crashes on the existing 7 off-format markers,
    2 in the first window); silently dropping all non-sentinel notes with no
    counter (rejected — hides a rising off-format rate, which could mask a real
    marker-writer regression; the `unparseable_skipped` counter makes the skip
    visible in the nightly log).

- **Cron timings (`02 0 * * *` consolidation, `7 1 * * *` healthcheck).**
  - *Source:* scheduling-guidance heuristics (off round-minute marks; ordered
    after `/daily` start at 23:27 and the consolidation before the healthcheck)
    + the live crontab lines read this session (`crontab -l`: 23:27 `/daily`,
    23:45 `/mygoat-daily`, 03:00 `/memory-sleep`, 04:17 `uv_cache_prune`, 09:37

    `3-59/10` session-watch). No collision at `02 0` or `7 1`.
  - *Why:* consolidation reads markers directly (independent of `/daily`
    finishing) so it can run shortly after `/daily` starts; the healthcheck runs
    after both, ~1h40m post-`/daily`-start, giving the LLM run ample time to
    write its file before "missing" is declared.

- **`--apply` as the cron default (not `--dry-run`-only rollout).**
  - *What:* the cron passes `--apply`; the SCRIPT defaults to `--dry-run` when
    neither flag is given (fail-safe for manual invocation).
  - *Why:* the explicit-path single-commit-per-run revertability + the

    automated pass, and a perpetually-dry-run cron would not consolidate anything.
  - *Source:* judgment, justified by the §8 risk-mitigation guards.
