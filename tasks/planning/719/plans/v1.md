**Verbatim bullet text** (exactly as it will appear, top-level `- ` item):

> - **Sequential per-cell vLLM engines on the SAME GPU can collide on the torch.distributed rendezvous (`MASTER_PORT`) socket → `EADDRINUSE` at the NEXT engine's init.** When a per-cell loop constructs and tears down a fresh `vllm.LLM(...)` engine per cell on one GPU shard, the next cell's EngineCore can fail to bind the rendezvous port if the prior cell's torch.distributed process group has not been torn down — the port socket is still held: `torch.distributed.DistNetworkError ... The server socket has failed to listen on ... EADDRINUSE port <P>`. This is DISTINCT from the three vLLM traps above: it is not the teardown-OOM/KV-cache pin (`Free memory ... less than desired gpu_memory_utilization`, line above), not a crash-orphan `VLLM::EngineCore` survivor across launches, and not a `generate()` hang — it is a clean-sequential PORT-bind collision that surfaces a real exception at engine *init*. The fix is mechanically the same call the teardown recipe above already prescribes (the process group owns the rendezvous bind): RULE: between sequential same-GPU cells, ensure the prior engine is fully reaped before constructing the next — `_reap_vllm_engine` (`src/explore_persona_space/analysis/representation_shift.py`) drives the canonical teardown (`engine_core.shutdown()` → `torch.distributed.destroy_process_group()` guarded by `is_initialized()`), which releases the rendezvous socket along with the KV cache; OR, if a per-cell loop cannot guarantee synchronous teardown, set a fresh/randomized `MASTER_PORT` (rendezvous port) in the environment BEFORE each cell's engine init so a lingering bind on the prior port cannot block the next. Recovery: a single scoped re-run of the failed cell/shard releases the port (the prior worker is gone by the rerun), as #664 shard-7 demonstrated. (Incident #664 r18 p2, 2026-06-28.)
