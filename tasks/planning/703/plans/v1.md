The current full-suite failing set is **5 tests in 3 files** (NOT the "4 tests incl. two issue642" the task body guessed — that guess is stale; the `test_issue642` lines emit numpy RuntimeWarnings, not failures). They fall into **four root-cause classes**:

1. **`test_autonomous_session_watch.py::test_vm_reclaim_hf_hub_cache_evicts_through_bounded_worker`** — an `HF_HOME`/`HF_HUB_CACHE` env-var leak. `tests/test_issue685_extraction.py` and `tests/test_issue685_coexistence.py` run `os.environ.setdefault("HF_HOME", ...)` at **module import (collection) time**, permanently injecting `HF_HOME` into `os.environ`. That makes `_vm_reclaim_hf_hub_cache` take its `scan_cache_dir(cache_dir=_hub_cache)` branch, which the test's no-arg fake `scan_cache_dir` lambda rejects (`unexpected keyword argument 'cache_dir'`) → scan "fails" → `executed == []`.
2. **`test_autonomous_session_watch.py::test_work_descendant_denylist_import_pin`** — a `sys.modules` module-replacement leak. `tests/test_worktree_audit.py` does an **UNGUARDED** top-level `spec_from_file_location("worktree_audit", ...)` that always replaces `sys.modules["worktree_audit"]` with a fresh module object. `autonomous_session_watch` (imported earlier, alphabetically) holds the OLD `worktree_audit.ORPHAN_HOLDER_PATTERNS`, so the test's `asw.ORPHAN_HOLDER_PATTERNS is ORPHAN_HOLDER_PATTERNS` identity check fails (equal tuples, different objects).
3. **`test_issue672_validation.py::test_loop_poller_detects_second_failover_in_quiet_period`** — a root-logger level leak. An earlier module flips the root logger to `INFO` (via `logging.basicConfig(level=INFO)` / `setLevel`); the test stubs `m.time.time` with a virtual clock, and once `logger.info(...)` actually emits, `logging.LogRecord.__init__` calls `time.time()` and consumes extra virtual ticks → the poller's quiet-period clock jumps past 60 s → the loop exits after one iteration → `len(invocations) >= 2` fails.
4. **`test_issue_dispatch.py::test_runpod_poll_delegates_to_poll_pipeline_and_returns_typed_pollresult` + `::test_backend_poll_script_produces_legacy_poll_pipeline_json_shape`** — these FAIL even in single-file isolation, so they are NOT isolation leaks. They are **stale test stubs / import-path staleness**: the local `_PR` PollResult stubs lack the `stall_reason` field that production `backends/base.PollResult` / `runpod.py` / `backend_poll.py` now carry (#664), and `test_backend_poll_script…` additionally needs `scripts/` on `sys.path` to import `runpod_api` transitively (only satisfied under full collection). Because the Goal is "full suite green without special-casing," these are in-scope to fix even though they are a different bug class.

### (b) Fix step — by class

**Fix 1 + 3 (env + logging leaks) — autouse fixture in `tests/conftest.py`.** Append a function-scoped autouse fixture that snapshots and restores the leaked globals around every test. Pseudocode (verified equivalent passes both failing tests under full collection):

```python
import logging
import os
import pytest

# Collection-time global leaks several test modules induce that monkeypatch
# does NOT auto-revert (they bypass monkeypatch.setenv / setattr):
#   * tests/test_issue685_{extraction,coexistence}.py set HF_HOME via
#     os.environ.setdefault at import time -> _vm_reclaim_hf_hub_cache takes
#     its scan_cache_dir(cache_dir=...) branch and a no-arg fake lambda rejects it.
#   * an earlier module flips the root logger to INFO via logging.basicConfig,
#     so issue672's logger.info() emits and LogRecord.__init__ consumes ticks of
#     the test's monkeypatched virtual time.time() clock.
# Snapshot + restore both around every test so a collection-time leak can't bleed.
_HF_ENV_KEYS = ("HF_HOME", "HF_HUB_CACHE")

@pytest.fixture(autouse=True)
def _isolate_leaky_global_state():
    saved_env = {k: os.environ.get(k) for k in _HF_ENV_KEYS}
    for k in _HF_ENV_KEYS:
        os.environ.pop(k, None)
    root = logging.getLogger()
    saved_level = root.level
    root.setLevel(logging.WARNING)
    try:
        yield
    finally:
        root.setLevel(saved_level)
        for k, v in saved_env.items():
            if v is None:
                os.environ.pop(k, None)
            else:
                os.environ[k] = v
```

Notes for the implementer:
- The fixture pops `HF_HOME`/`HF_HUB_CACHE` at SETUP (before the test body). `tests/test_env_three_way_branch.py` sets `HF_HOME` via `monkeypatch.setenv`/the code under test INSIDE its test bodies (which run after fixture setup and auto-revert), so popping at setup is safe — verified.
- The diagnosis points to `sys.modules`/`os.environ`/logging. If the implementer's own diagnosis finds the leak is narrower or wider, they may adjust the exact set of restored globals — see §8.
- Keep the fixture cheap: no I/O, pure in-memory dict/level snapshot (§6 risk on per-test cost).

- **Why a function-scoped autouse fixture, not session-scoped:** the leaks are per-test cross-contamination (state set during/at-collection-of one test bleeds into a later test). A session-scoped fixture would snapshot once and miss intra-session mutations; function scope snapshots/restores around EACH test, which is what neutralizes the bleed. Verified: function-scope autouse resolves classes 1 and 3.
- **Why snapshot/restore rather than blanket force-to-default:** restoring the pre-test value (vs hard-setting WARNING / unsetting HF_HOME permanently) preserves the behavior of tests that legitimately rely on those globals within their own bodies (e.g. `caplog` tests, `test_env_three_way_branch.py`), minimizing blast radius across the 5400-test suite.
- **Why guard the loader rather than `importlib.reload` for class 2:** the bug IS that a fresh module object diverges from the cached one. Reload creates yet another fresh object; guarding (reuse the cached module) keeps exactly one canonical object so the `is` identity assertion holds. The guarded pattern is already proven in `test_sparse_worktree.py`.
- **Why fix classes 4-5 here even though they aren't isolation leaks:** the task Goal is the *full suite green without special-casing*; a green Step 9c gate cannot tolerate two single-file-isolation failures. They are cheap, mechanical (one field + one sys.path line), and fixing them is required to satisfy acceptance criterion #1.
