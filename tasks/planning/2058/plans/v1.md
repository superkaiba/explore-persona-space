# Plan — task #2058: no-progress tick wedge — force-RESPAWN instead of STALE-REDRIVE

**Kind:** infra (workflow-fix). **GPU-hours estimate: 0.**
Estimated GPU-hours (total): 0

## Goal

Detect an autonomous `/issue` session that wakes, performs no durable work, posts a heartbeat, and sleeps — repeatedly — and force-RESPAWN it (fresh context) instead of re-driving it into the same exhausted context.

## Prior work (in-repo)

Two mechanisms already recover DIFFERENT session-death classes; the new lane closes their inversion.

- **STALE-REDRIVE** (`scripts/tick_triage.py::compute_issue_verdict` L950–L977, current behavior): fires when marker AGE exceeds `stale_after_s` (`STALE_S_DEFAULT = 25*60` at L113). Re-drives the SAME session by re-invoking the full `/issue <N>` skill. Correct for a session whose chain died SILENTLY — the same session can pick up state from `events.jsonl` and continue.
- **Prompt-wedge / api-error / dead-wake fast lanes** (`scripts/autonomous_session_watch.py` § Stall-detection hardening, `_WATCHER_NOTE_SENTINELS` frozenset at L1907, `STALLED_MAX_RESPAWNS = 3` at L2445, day-cap helpers `EPM_TICK_WEDGE_RESPAWNS_PER_DAY` at L2380 and `EPM_TICK_WEDGE_DEAD_RESPAWNS_PER_DAY` at L2341): fire on `isApiErrorMessage: true` accumulation, `dequeue`-run accumulation, failed-turn runs, dead-wake silence, and the #1453 context-ceiling text. Force-RESPAWN (stop → fence → spawn) instead of re-drive.
- **Slow-phase lightweight heartbeat** (`.claude/skills/issue-tick/SKILL.md:222`, incident #522): when the age clock lapses at an ACTIVE status but the underlying job is verifiably alive, the tick posts a heartbeat instead of re-driving the full skill. This is the mechanism that produces the specific failure mode this plan targets: heartbeats reset the age clock EXACTLY like real progress, and the tick reads HEALTHY forever.

**The blind spot** — a session whose completed turns SUCCEED (heartbeats land) but do NO durable work (no non-heartbeat markers, no commits, no status change) is invisible to every existing lane: STALE-REDRIVE never fires because the age clock is fresh; the wedge lanes never fire because the turns are successful assistant rows, not api-error rows or refused turns. Live evidence: #2054 (2026-08-04T01:12Z–03:28Z) emitted four consecutive heartbeats whose own text reported "no state change" / "unchanged"; zero non-heartbeat markers across 2h16m; no lane escalated.

## Design

### 1. Progress fingerprint (durable evidence of ADVANCEMENT)

Per-issue tuple: `(latest non-watcher-non-heartbeat marker ts, HEAD sha of the current status-folder task's canonical checkout, current status folder name)`.

- **"Non-watcher"** = the marker's `note` contains no member of `_WATCHER_NOTE_SENTINELS` (frozenset at `scripts/autonomous_session_watch.py:1907`). Reuse the existing predicate helper.
- **"Non-heartbeat"** = the marker's note prose begins with a token from the sentinel set `_HEARTBEAT_NOTE_SENTINELS` (new frozenset — members: `"tick heartbeat:"`, `"[long-phase-heartbeat]"`, and the new `"progress: none"` prefix produced by item 4 below). A heartbeat with `progress: <not-none>` (e.g. `progress: commit=abcd...`) IS durable evidence and counts as a fingerprint advance — the token is the CANONICAL declaration, so the predicate reads it authoritatively when present.
- **HEAD sha** = `git -C <task-folder> rev-parse HEAD` in the task's own worktree resolved via `task.py find <N>`. Fail-open on any git error (unresolvable → treat sha as `null` and let the marker-ts + status arms carry the fingerprint).
- **Status** = the parent folder name (the existing canonical state).

The fingerprint is a stable string (`"<marker_ts>|<sha>|<status>"`) suitable for equality comparison.

### 2. `compute_issue_verdict` extension (`scripts/tick_triage.py`)

Minimal signature extension — keep the function pure; state lives in `main()`.

```python
def compute_issue_verdict(
    status: str,
    prev_status: str | None,
    marker_age_s: float | None,
    over_cap: bool,
    *,
    stale_after_s: float,
    # NEW — optional, defaults preserve legacy behavior for callers that don't wire it
    progress_fingerprint: str | None = None,
    prev_fingerprint: str | None = None,
    no_progress_streak: int = 0,
    no_progress_threshold: int = 3,   # env-overridden in main()
) -> tuple[str, str, int]:               # NEW third element: updated streak
```

Verdict-emission order (INSIDE the existing HEALTHY branch — do NOT change the STALE-REDRIVE, TERMINAL, or GATE branches):

1. TERMINAL / GATE branches: unchanged; return `..., 0` (streak resets).
2. Age check: if `marker_age_s is None or marker_age_s > stale_after_s` → STALE-REDRIVE; return `..., 0` (streak resets — the stale-redrive path handles it).
3. **NEW no-progress arm** (only reachable when age is fresh):
   - If `progress_fingerprint is None` or `prev_fingerprint is None`: return HEALTHY with streak `0` (first tick of an episode, or fingerprint uncomputable — fail-open).
   - Else if `progress_fingerprint == prev_fingerprint`: `streak = no_progress_streak + 1`. If `streak >= no_progress_threshold`: return `("NO-PROGRESS-RESPAWN", "status=X, fingerprint unchanged across N ticks — session likely context-exhausted", streak)`. Else: return HEALTHY with the incremented streak.
   - Else (fingerprint changed): return HEALTHY with streak `0`.

Threshold N is read in `main()` from `EPM_NO_PROGRESS_RESPAWN_TICKS` (default 3; malformed / `<2` → default 3; never a kill switch — the watcher-pass env var is the kill).

The pure predicate is unit-testable end-to-end without file I/O; the impurity (fingerprint computation, streak persistence) stays in `main()`.

### 3. `main()` wiring in `tick_triage.py`

- Compute `progress_fingerprint` per-issue AFTER the existing marker-age computation, BEFORE calling `compute_issue_verdict`.
- Load the prior streak + fingerprint from a new per-issue state file (item 5 below) — the existing `issue-tick-last-status/<N>.json` pattern is the model.
- Pass `progress_fingerprint`, `prev_fingerprint`, `no_progress_streak`, `no_progress_threshold` into `compute_issue_verdict`.
- Persist the RETURNED streak alongside the new fingerprint atomically (tmp+rename).
- The verdict `NO-PROGRESS-RESPAWN` is a NEW branch in `tick_triage.py::main()` output — it does NOT re-drive the skill (that's the current STALE-REDRIVE behavior). Instead it prints a distinctive one-liner and exits — the watcher pass (item 4) reads the verdict via its own predicate + state file and OWNS the respawn action. Rationale: `tick_triage.py` runs in the per-issue tick session (which is exactly the wedged context we want to replace); calling `spawn-issue` from there would race the tick's own teardown. The watcher runs in an independent cron.

### 4. `no_progress_respawn_pass` (`scripts/autonomous_session_watch.py`)

New watcher pass on the daemon-gated block, inserted after the existing wedge respawn paths and before the reconcile / GC passes. Reuse existing helpers wholesale.

**Predicate — pure `decide_no_progress_respawn`** (mirror the `decide_wedge_respawn` shape):

Inputs: registration entry (issue, sid, spawned_at), prior episode state (`fingerprint`, `streak`, `respawns_today`, `respawn_day`), the tick's most recent verdict (via a small helper reading `issue-tick-last-status/<N>.json` — the pattern the tick already writes), current UTC day, daemon liveness, worktree-activity probe result, park-exemption re-probe result, kill-switch env value.

Fires (returns `("respawn", reason)`) iff ALL:
- The most recent `tick_triage` verdict is `NO-PROGRESS-RESPAWN` for THIS issue (streak already reached threshold in the tick).
- Task status is ACTIVE (not in the PARK / terminal / gate set — apply the `#1247` same-instant `_task_status` re-read guard immediately before the stop; PARK/terminal aborts loudly with no cap-consume).
- Kill switch unset: `EPM_DISABLE_NO_PROGRESS_RESPAWN != "1"`.
- Episode belt: `respawn_count < STALLED_MAX_RESPAWNS` (reuse `STALLED_MAX_RESPAWNS = 3`).
- Per-issue per-UTC-day cap not exhausted: `respawns_today < EPM_NO_PROGRESS_RESPAWNS_PER_DAY` (default 3, malformed / `<1` → default; NOT a kill switch — INDEPENDENT counter from `EPM_TICK_WEDGE_RESPAWNS_PER_DAY` and `EPM_TICK_WEDGE_DEAD_RESPAWNS_PER_DAY`).
- Vetoes: no fresh worktree activity (reuse `decide_worktree_hold`'s ~15 min mtime probe with `EPM_STALLED_WT_ACTIVITY_MIN` bound); no park-exemption fire (reuse the existing `_park_exemption_veto` shape: user-pause / spend-approval / provision-in-flight / long-phase heartbeat / round-complete re-park / awaiting-child); daemon reachable (if the daemon probe returned None, FREEZE the streak — don't reset, don't fire); transcript resolvable (if unresolvable, FREEZE the streak).

Returns `("hold", reason)` on any freeze condition (worktree activity, daemon unreachable, unresolvable transcript). Returns `("clear", reason)` when the fingerprint has advanced (streak resets in the state file). Cap-exhausted returns `("cap-exhausted", reason)`.

**Action — force-RESPAWN via existing helpers:**

1. Same-instant `_task_status` re-read (act guard, #1247).
2. Post the fire marker (`_WATCHER_NOTE_SENTINELS`-member sentinel `[autonomous_session_watch:no-progress-respawn]`) + source stamp (#1247) BEFORE the stop, so the marker records the reason regardless of stop outcome.
3. Call `_stop_session(sid)` (existing helper) → next-tick verification the sid is absent from the daemon's live set (reuse `decide_respawn_fence`; the fence state file entry can share the pass's per-issue state file or gain a `stop_pending_sid` field like `stalled-<N>.json` — implementation choice, but STAGED semantics: never spawn in the same tick as the stop).
4. On the next tick, once the sid is verifiably dead, `spawn-issue --auto` (routes through `_dispatch_infra_drain` chokepoint's shape — respects the auth-outage gate, takeover sentinel, session-dispatch stagger).
5. On `"spawned"`: bump `respawns_today` (once per episode at stop-initiation, save latch-FIRST — mirrors the #1209 latching order). One anti-liveness marker (`[autonomous_session_watch:no-progress-respawn]`) + one fail-soft `_telegram_push`. One row to `.claude/cache/no-progress-respawn-events.jsonl`.
6. On cap-exhausted: one-time `[autonomous_session_watch:no-progress-respawn-cap-exhausted]` marker (`_WATCHER_NOTE_SENTINELS` member) + one push + one sidecar row per (issue, UTC day). Quiet re-fires within the day.

**State file:** `~/.eps-autonomous/no-progress-<N>.json`. Shape:
```json
{
  "fingerprint": "<marker_ts>|<sha>|<status>" | null,
  "streak": 0,
  "day": "YYYY-MM-DD",
  "respawns_today": 0,
  "respawn_day": "YYYY-MM-DD",
  "stop_pending_sid": null | "<sid>",
  "stop_pending_ts": null | <epoch>,
  "cap_exhausted_day": null | "YYYY-MM-DD",
  "episode_id": <int>
}
```
Atomic tmp+rename. `stop_pending_*` cleared on the next-tick verification. `respawns_today` resets naturally at the UTC day roll (day-keyed). GC: add `("no-progress-", "")` to `_GC_TARGETS` (~L22429); reap at `TERMINAL_FOR_GC` (`completed`/`archived`) only — same conservative posture as capacity-retry, boot-death, and stale-blocked (never mid-episode). The sidecar `no-progress-respawn-events.jsonl` is outside the `*.json` glob by suffix.

**Fingerprint duplication note (deliberate):** the pass computes its own fingerprint from `task.py view --json` events + `git rev-parse HEAD` rather than reading the tick's state file. Rationale: the pass runs INDEPENDENTLY of the tick (different cron), and duplicating the cheap computation avoids a data-race between "tick wrote streak=3" and "watcher observes fingerprint has advanced since". The tick's fingerprint gates the tick verdict; the watcher's fingerprint is a SECOND corroboration — a fingerprint that ADVANCED between the tick's write and the watcher's read short-circuits the fire (return `"clear"`), never the other direction.

### 5. Heartbeat self-declaration (`.claude/skills/issue-tick/SKILL.md`)

Extend the STALE-REDRIVE-branch heartbeat wording (currently `.claude/skills/issue-tick/SKILL.md:222`):

**Before:**
```
uv run python scripts/task.py post-marker <N> epm:progress \
  --note "tick heartbeat: job verified alive (pid <pid>, log mtime <ts>); slow phase, no state change"
```

**After:**
```
uv run python scripts/task.py post-marker <N> epm:progress \
  --note "tick heartbeat: job verified alive (pid <pid>, log mtime <ts>); slow phase, no state change
progress: none"
```

The `progress: none` token is a verbatim one-line key-value on its own line. `no_progress_respawn_pass` prefers it (zero prose parsing). For heartbeats where the pass DOES see durable state, the SKILL.md ALSO documents the alternative forms — `progress: commit=<sha12>`, `progress: new-markers=<n>`, `progress: status-change=<X>→<Y>` — which the pass reads as "fingerprint advanced" without git/events introspection. When a heartbeat writer has that information cheaply (e.g. the tick already read events to compute marker age), it should emit the specific form; when it can only report "the age clock is fresh but I did nothing durable", `progress: none` is authoritative.

Grandfather clause: heartbeats without the token still work — the pass falls back to the computed fingerprint. The token is a hint, not a hard dependency.

## Risks

- **False-positive on legitimately quiet phases.** A phase whose ONLY progress signal is durable data-repo writes (no marker, no commit, no status change) could theoretically read as "no progress". The "markers keep arriving" precondition catches most cases (a truly quiet phase takes STALE-REDRIVE, not NO-PROGRESS-RESPAWN); the fingerprint additionally reads HEAD sha of the ISSUE branch, so any pod-side commit that gets pushed to `origin/issue-<N>` advances the fingerprint. Residual: a phase that writes only to HF (no git, no marker) and the orchestrator posts only heartbeats — this is the "you're doing durable work but no observable proof" class, which the pass will false-positive on. Mitigation: dispatchers already post `epm:progress` phase breadcrumbs; the `[phase=...]` pattern is durable and the marker itself is non-heartbeat. Accepted residual: an obscure pod-side-only workload that never posts a phase breadcrumb.
- **Respawning the SAME context-exhausted session mid-race.** Bounded by the stop→fence→spawn pattern (reuse `decide_respawn_fence`): the pass NEVER spawns in the same tick as the stop; it waits for the sid to leave the daemon's live set on the next tick. Combined with the episode belt (`STALLED_MAX_RESPAWNS=3`) and per-UTC-day cap (default 3), the worst case is 3 stop+spawn cycles per day per issue.
- **Grandfathered heartbeats without the `progress: none` token.** The pass computes the fingerprint from events+git anyway; the token is a hint that saves prose parsing. Fail-open on absence.
- **State-race between tick and watcher.** The tick writes `streak+fingerprint` to `no-progress-<N>.json`; the watcher reads `issue-tick-last-status/<N>.json` (the existing tick snapshot) AND independently re-computes the fingerprint. A fingerprint that ADVANCED between the two reads short-circuits the fire (`clear`) — the direction is safe (never a false-positive from stale tick state).
- **Interaction with the #522 slow-phase heartbeat mechanism.** The #522 heartbeat is INTENDED behavior — a genuinely slow legitimate phase. That case IS a "no durable work in this tick" — but across multiple ticks, the underlying pod's log advances and eventually posts an `epm:progress` phase note (or the phase completes and posts `epm:results`). If the pod is genuinely slow and posts no non-heartbeat markers for ~45 minutes (3 ticks × 15 min), the pass fires. Mitigation: heartbeats emitted with the specific `progress: commit=<sha12>` or `progress: new-markers=<n>` form (item 5) declare durable state; a slow phase whose pod IS advancing (log mtime rising, pid alive) should emit `progress: log-mtime-advanced` — extend the SKILL.md documentation to name that variant. Accepted residual: a slow phase whose orchestrator has NO durable evidence to report will still be respawned after 3 ticks; the fresh session will re-attach via `events.jsonl` and continue, at the cost of one skill reload (~44K tokens). This is worse than a bare re-drive by a small constant; it is vastly better than a 2h+ wedge.
