## 3. Research findings (ALL empirically verified on this VM this session; git 2.34.1)

1. **Exact error string:** `fatal: Cannot rebase onto multiple branches.` — rc=128, on stderr. Verified two ways: `strings $(command -v git)` contains `Cannot rebase onto multiple branches.`, and a live repro (`git pull --rebase . main feat` with two for-merge FETCH_HEAD entries). In git source it is `builtin/pull.c: die(_("Cannot rebase onto multiple branches."))`, raised when FETCH_HEAD holds >1 non-not-for-merge entries — i.e. BEFORE `run_rebase()` is invoked.
2. **The failure leaves NO partial state ⇒ retry is safe.** Verified with the production flags (`git pull --rebase=merges --autostash` + a dirty worktree): after rc=128, there is no `.git/rebase-merge`, no `.git/rebase-apply`, no stash entry (the autostash is created by `git rebase`, which never ran), HEAD unchanged on `main`, dirty worktree bytes preserved untouched. The retry's own fresh fetch rewrites FETCH_HEAD, which is why one retry suffices (both incidents' manual retries succeeded immediately).
3. **git holds NO persistent handle on the rebase state dir.** `fuser -v .git/rebase-merge` during a LIVE actively-running rebase reports NOTHING (verified). git also writes NO pid file into rebase-merge (gc.pid is a gc-only mechanism). ⇒ `fuser`/`lsof` on the dir CANNOT prove absence of a holder — it would report "no holder" while git is actively rebasing, which is the dangerous false direction. `_fuser_evidence` is therefore NOT the prover.
4. **The reliable holder signal is the process table.** A live state-owning git command (rebase/pull/merge, `--continue`/`--abort`) runs with `comm == "git"` and process cwd at the WORKTREE TOPLEVEL — verified: a rebase launched from a subdirectory shows `/proc/<pid>/cwd → <repo toplevel>` (git's `setup_work_tree()` chdirs; `git -C` chdirs at startup). A conflict-PAUSED rebase awaiting a human has NO process — the probe cannot see it; this is the honest residual, handled by the min-age floor + conservative defaults (§11 item 4, §12 item 6).
5. **/proc visibility on this VM:** mounted WITHOUT `hidepid` (all pids enumerable); another user's `/proc/<pid>/comm` IS readable; another user's `/proc/<pid>/cwd` readlink is NOT (EACCES) — verified against pid 1. So a root-owned git process is detected as an unattributable candidate ⇒ verdict `"uncertain"` ⇒ keep the refusal. Fails toward conservatism by construction.
6. **Worktree disambiguation:** the fleet runs concurrent git ops in linked worktrees under `<repo>/.claude/worktrees/` (bind-mounted from `/mnt/eps-data`). Attributing a candidate's cwd via `git -C <cwd> rev-parse --absolute-git-dir` and comparing to the ROOT's git dir cleanly excludes them (a linked worktree resolves to `<repo>/.git/worktrees/<name>` ≠ `<repo>/.git`), with no hardcoded path — otherwise fleet worktree activity would permanently suppress the downgrade.

**New probe** (place next to `_fuser_evidence` in the Locking/Preflight area):

```python
@dataclasses.dataclass
class LivenessProbe:
    """Outcome of the /proc git-liveness scan: verdict + human-readable evidence."""

    verdict: str  # "holder" | "none" | "uncertain"
    evidence: str


def _probe_git_liveness(repo: Path, gd: Path, proc_root: Path = Path("/proc")) -> LivenessProbe:
    """Scan ``proc_root`` for a live git process operating on THIS repo.

    "holder": a ``comm == git`` process whose cwd attributes (via
    ``git -C <cwd> rev-parse --absolute-git-dir``) to this repo's git dir —
    state-owning git commands chdir to the worktree toplevel (verified,
    #1044 §3), so linked-worktree / other-repo git activity is excluded
    without hardcoded paths. "none" ONLY when the scan COMPLETED with zero
    holders and zero unattributable git candidates. Everything else —
    ``proc_root`` unreadable, a git process whose cwd is unreadable (EACCES:
    another user's process) or unattributable — is "uncertain". The caller
    treats anything but "none" as "keep today's young-husk refusal": the
    probe fails TOWARD conservatism by construction. It cannot see a
    conflict-paused rebase awaiting a human (no process exists then) — that
    residual is bounded by ``_husk_min_age_s`` and the repo-root policy that
    conflicts are resolved in scratch worktrees, never in place.
    """
    try:
        pids = [p for p in os.listdir(proc_root) if p.isdigit()]
    except OSError as e:
        return LivenessProbe("uncertain", f"{proc_root} unreadable: {e!r}")
    gd_resolved = gd.resolve()
    unattributable: list[str] = []
    for pid in pids:
        pdir = proc_root / pid
        try:
            comm = (pdir / "comm").read_text().strip()
        except OSError:
            continue  # vanished mid-scan — provably not a live holder
        if comm != "git":
            continue
        try:
            cwd = os.readlink(pdir / "cwd")
        except FileNotFoundError:
            continue  # vanished mid-scan
        except OSError as e:
            unattributable.append(f"pid {pid}: cwd unreadable ({e.__class__.__name__})")
            continue
        rp = git(Path(cwd), "rev-parse", "--absolute-git-dir", check=False)
        if rp.returncode != 0:
            unattributable.append(f"pid {pid}: cwd {cwd} not attributable to a git dir")
            continue
        if Path(rp.stdout.strip()).resolve() == gd_resolved:
            return LivenessProbe("holder", f"live git pid {pid}, cwd {cwd}")
    if unattributable:
        return LivenessProbe("uncertain", "; ".join(unattributable[:5]))
    return LivenessProbe("none", "scan completed: no live git process attributable to this repo")
```

Notes: the pid list is snapshotted BEFORE examination, so the probe's own short-lived `rev-parse` children can never self-match; `comm == "git"` (not `startswith`) is deliberate — helpers like `git-remote-https` never own rebase state and their parent `git` is visible; `git()` is the module's own deny-checked wrapper (rev-parse is not deny-listed).

**New helper** (next to `pull_rebase`):

```python
def _pull_with_transient_retry(repo: Path, report: dict, timeout_s: float) -> GitResult:
    """Bounded pull with exactly ONE retry on the transient multiple-branches race.

    ``fatal: Cannot rebase onto multiple branches.`` is die()d by
    builtin/pull.c BEFORE any rebase starts, when a concurrent fetch rewrote
    FETCH_HEAD with >1 for-merge entries mid-pull (#965/#998); verified to
    leave no rebase state, no autostash, and an untouched worktree (#1044
    §3), so the retry is state-safe. Retry once after a short sleep — the
    retry's own fetch rewrites FETCH_HEAD — and only when no rebase state
    exists (belt-and-braces re-verification). A second failure returns
    as-is and surfaces through the existing handling unchanged.
    """
    result = pull_rebase(repo, timeout_s)
    if not result.timed_out and result.rc != 0 and MULTI_BRANCH_STDERR_NEEDLE in result.stderr:
        if _rebase_in_progress(repo):
            _msg(
                report,
                "multiple-branches signature but rebase state exists — NOT retrying "
                "(unexpected shape; surfacing the failure as-is).",
            )
            return result
        _msg(
            report,
            "transient 'Cannot rebase onto multiple branches' (concurrent FETCH_HEAD "
            f"rewrite) — one retry after {_retry_sleep_s():.1f}s.",
        )
        time.sleep(_retry_sleep_s())
        return pull_rebase(repo, timeout_s)
    return result
```

**Wiring:** in `_pull_pipeline()`, replace BOTH `result = pull_rebase(repo, timeout_s)` call sites (the initial pull ~line 1095 and the collision-retry pull ~line 1114) with `result = _pull_with_transient_retry(repo, report, timeout_s)`. Bound: at most one signature-retry per pull invocation ⇒ ≤4 pull subprocesses per pipeline pass, each individually `_run_bounded`-bounded — no loop. A retry result that STILL carries the signature is returned un-retried and flows to the existing rc≠0 handling: `_capture_conflict_and_abort` finds no conflicted paths and no rebase state ⇒ exit 6 `"pull failed (rc=128) with no conflict state"` — byte-identical surfacing to today's single failure. Timeout results are never signature-retried (checked first). `_push_leg`'s retry pull goes through `_pull_pipeline` and inherits the behavior with no extra edit.

## 11. Decision Rationale (load-bearing design constants)

1. **`MULTI_BRANCH_STDERR_NEEDLE = "Cannot rebase onto multiple branches"`** — *Why:* the exact die() phrase, minus the `fatal: ` wrapper and trailing period, so the match is exact-phrase yet robust to the prefix. *Source:* verified this session on git 2.34.1 via `strings $(command -v git)` AND a live two-refspec repro (rc=128, stderr `fatal: Cannot rebase onto multiple branches.`); originates in git `builtin/pull.c` `die(_("Cannot rebase onto multiple branches."))`. *Alternatives:* full string with prefix/period (brittler for zero gain); regex (unneeded); matching `result.combined` (rejected — the Goal says stderr signature; die() writes stderr).
2. **Retry count = 1** — *Why:* bounded by construction; both incidents succeeded on the first manual retry because the retry's own fetch rewrites FETCH_HEAD. *Source:* task Goal (verbatim "one bounded internal retry"); incidents #965/#998; the file's own one-retry precedent (`_push_leg`). *Alternatives:* N retries with backoff (rejected — against the module's report-and-stop philosophy).
3. **`_retry_sleep_s` default 2.0s** — *Why:* lets a racing concurrent fetch finish before re-pulling; the helper holds two flocks, so long sleeps stall other syncs. *Source:* the file's own polling scale (`INDEX_LOCK_POLL_S = 2.0`); race window is one concurrent fetch (O(1-10s)). *Alternatives:* 0s (re-race window), 30s (needless stall under held locks).
4. **`_husk_min_age_s` default 120s** — *Why:* the probe is blind to a no-process conflict-paused rebase, so a floor protects the seconds-to-minutes window where an owner is about to `--continue`/`--abort`; 120s ≫ that window and process-start races, ≪ the 45-min incident age, and (deliberately) above the ≈0s husk age in the two existing young-husk tests, keeping them probe-free and deterministic. *Source:* 2× the file's own `EPM_ROOT_SYNC_FRESH_S = 60` "may be mid-write" freshness scale; otherwise a judgment constant — `ungrounded — needs no smoke-test beyond the suite` (safe in both directions: larger is strictly more conservative; env-tunable).
5. **Probe mechanism = /proc comm+cwd scan with `git rev-parse --absolute-git-dir` attribution** — *Why:* the only signal that is PRESENT during a live rebase and attributable to one repo. *Source:* empirical (§3): live rebase ⇒ git process with cwd at worktree toplevel even when launched from a subdir; `fuser` on the state dir reports NOTHING during a live rebase (disqualified as prover); git writes no pid file in rebase-merge (gc.pid is gc-only). *Alternatives:* `fuser`/`lsof` on the dir (rejected — false "no holder" during a LIVE rebase, the dangerous direction); pid files (do not exist); hardcoding the `.claude/worktrees` exclusion (rejected — rev-parse attribution is principled and path-free).
6. **Kill switch `EPM_ROOT_SYNC_HUSK_PROBE` (default on)** — *Why:* the task's kill criterion requires the probe to be degradable to no-op without loosening safety; a 3-line env gate gives ops rollback without a code change. *Source:* planner design choice (ops rollback without a code change), consistent with this plan's own §6 kill criterion; the task body itself does not mandate a kill switch (fact-check correction).
7. **Uncertain ⇒ keep the refusal; "none" requires a COMPLETED scan with zero unattributable candidates** — *Why/Source:* planner design choice — the conservative direction is implied by the Goal's 'no git process holding the rebase dir' predicate (only a PROVEN-absent holder downgrades), but the uncertain->refuse rule is not verbatim task text (fact-check correction). *Alternatives:* best-effort "probably none" (rejected — the false-"none" direction aborts someone's live work).
8. **`EPM_ROOT_SYNC_HUSK_AGE_S = 3600` kept unchanged** — *Source:* existing tunable (#949's parent design); this plan supplements, never retunes.
