### Findings

**MAJOR 1 — a stale PASS from a different instrument fingerprint satisfies every gate (scope item (ii) explicit requirement).**
`require_pilot_pass` (issue2479_judge_pilots.py:198-217) validates only `family` + `verdict`/`passed`. Both resume-skips ("PASS report present — pilot skipped") — p1p4_launch.sh leg 2b and p3_axis.sh p3_pilot — key on that same presence+PASS check, as do the P1 preamble, p3_gate, the `run_leg` env hook, and the instrument_gates flatness/name-mask reuse. The reports DO persist the fingerprints (axis: `instrument.rubric_sha256` + `PilotGateReport.rubric_hash`, model, max_tokens, temperature, n_draws, threshold_base; ingen: model|max_tokens|temperature + both judge-system sha256s), but NO consumer compares them to the live instrument at gate time. Concrete trigger (the standing crash-fix-round shape): pilot PASSes → a fix round edits `AI_LIKENESS_RUBRIC` / raises `JUDGE_MAX_TOKENS` / changes the judge model → relaunch resume-skips the pilot and the ≥5k wave dispatches at an instrument the pilot never certified. Fix is small and local: in `require_pilot_pass`, when `family=="axis"`, compare the report's `instrument.rubric_sha256`/`judge_model`/`max_tokens`/`temperature`/`n_draws` against the live `jl` constants; for `ingen`, compare model|max_tokens|temperature (system-prompt hashes legitimately vary per cell in the embedded name — the merge's own identity check already models this correctly).
