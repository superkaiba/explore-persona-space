- **What I'll run.** I'll train ~28 short 7B LoRA organisms by crossing four behaviors
  (formatting-C1, impolite-C2, sycophancy-neutral-C3, broad_em-C6) × two training

- **What I expect.** Contrastive cells will install the behavior more selectively;
  positive-only twins will install more broadly (leaking to bystander personas
  and the default-assistant context). The bare-default-assistant training context —
  installing the behavior DIRECTLY into the base assistant, not behind a persona —
  should produce stronger bystander leakage than the persona context, because
  there is no persona gate to act as a selectivity funnel. Formatting is the
  pipeline health control; if it fails in any arm, the whole arm is void.

- **What would change my mind.** If positive-only cells install at similar
  selectivity to contrastive ones, the negatives are not what's driving the
  persona-localization gradient. If the bare-default-assistant context installs at
  matched or lower rate than the persona context, the "persona as selectivity
  funnel" framing is wrong. Either outcome is informative and reportable.

## §3 Hypothesis

**H1 (pipeline health, v4 parity).** C1 formatting clears its floor (≥20/25)
in EVERY context × regime cell. Kill path K1 still applies per-arm: if formatting
fails in any arm, that arm's results are void (pipeline defect, not behavior).

**H2 (contrastive vs positive-only selectivity).** Contrastive training produces
lower bystander leakage than positive-only training at matched own-context install.
Specifically: at the dose-matched checkpoint where both arms reach judged rate
≥ 0.60 in their own training context, the positive-only arm's leakage to the
bystander panel is ≥ 2× higher than the contrastive arm's.

Falsification: if leakage is indistinguishable between contrastive and pos-only
at matched install, negatives are not the selectivity mechanism — the organism's
training context alone is doing the work.

**H3 (context-kind modulation).** Own-context install rate is similar across
the four training contexts at matched recipe (same question bank, same regime).
Bystander leakage is NOT — the bare-default-assistant training context produces
higher leakage than the persona context at matched install, because no persona
funnel is active.

Falsification: if bystander leakage is similar across training contexts at matched
install, the "persona as selectivity funnel" framing is wrong.

**H4 (install reachability, v4 H3).** ≥1 content organism (C2/C3/C6) in at least
one context × regime cell reaches the band [0.60, 0.85] at some checkpoint.

### D2-amendment — Elicitation framing per context kind

Elicitation recipe is IDENTICAL across contexts (5 extraction-pair variants,
instruct-and-strip, same question bank). What changes per context:

- **persona-sw-eng**: system prompt = `persona_header(key="software_engineer")` (v4 parity)
- **bare-default-assistant**: system prompt = `""` (empty) or `"You are a helpful assistant."` — see Assumption 14 on which form; the TRAINING row also uses that same bare context (no persona header, no prefix). Negative rows: same 5-member panel as persona arm (training negatives are the OTHER contexts, including personas and other prefixes — per D2-negatives below).
- **conversational-prefix**: system prompt = `""`, user turn prefixed with a WildChat short-message prefix from `wildchat_random` bank (a real 1-3 turn conversational snippet before the neutral question). The training row's "context" is the prefix-prepended user turn only.
- **ICL-prefix**: system prompt = `""`, user turn prefixed with a 2-shot ICL example block (the trait expressed in 2 worked examples, then the neutral question). The 2-shot block is drawn from a fixed ICL example bank (generated once, committed, sha-pinned — see §D8 ICL bank).

**Negative panel for bare and prefix contexts (D2-negatives):**
The 5-member negative panel (`negatives.default_panel()`) is UNCHANGED — it includes
the default assistant plus 4 close negative personas. For the bare-default-assistant
training context arm, the negatives are the 4 CLOSE PERSONAS (NOT the default assistant,
since the default assistant IS the source). The negative panel for the bare arm is
therefore: the 4 non-default-assistant members of `default_panel()`. Disjointness
assert: panel∩sources=∅ per each context arm separately.

For prefix contexts, negatives use the same 5-member panel with the same question
(no prefix in the negative rows — the negative teaches "without this behavior in a
neutral bare context" which is correct). This is a named deviation (see §Named
deviations).

### D5-amendment — Training recipe per context

The LoRA recipe is IDENTICAL across all context arms (lr 1e-5, r 32, α 64, dropout
0.05, epochs ceiling 3, batch 4×4, max_length 1024, save_steps=2, seed 42).
The only difference is the training-row context field: `row["context"] = context_obj`
where `context_obj` varies per arm. The mix size (80 rows = 20 pos + 20 neg +
40 generic) is identical for contrastive arms. For pos-only arms:
- **mix size = 60 rows** (20 pos + 0 neg + 40 generic; neg_ratio=0 means no negative
  rows — generic_frac=0.5 is computed relative to the non-negative mix size, so
  40 generic / 60 total ≈ 0.67). NOTE: the step arithmetic changes slightly:
  60 / (batch 16 effective) = ~3.75 steps/epoch → at 3 epochs = ~11 total steps →
  save_steps=2 still produces ~6 ladder rungs. Adequate for dose-to-band.

**Dose-to-band selection** runs INDEPENDENTLY per cell. A contrastive cell and
its pos-only twin may select different checkpoints — that is the design intent.

### D6-amendment — Install evaluation (per context, with matched-install leakage read)

**Own-context install (primary per-cell DV):**
- Evaluation is run under THE SAME CONTEXT AS TRAINING (e.g. a cell trained on
  "bare-default-assistant" is evaluated under the bare-default-assistant context at
  install time). This preserves the on-distribution measurement requirement.
- Judged rate (graded 0–100, reason-then-score, max_tokens≥300, 5 samples × 3
  draws per rung for Tier 1; 10 samples × 5 draws for Tier 2 at selected checkpoint).
- tf-margin companion (fixed +/- pools from each behavior's registered pool, same
  across all contexts — the pools are behavior-level, not context-specific).
- Formatting structural rate for C1 arms.

**Dose-matched bystander leakage read (the cross-condition comparison DV):**
At the SELECTED checkpoint (Tier 2) for each cell, run generation + judge on a
FIXED bystander panel of 5 contexts: persona-sw-eng, bare-default-assistant,
conversational-prefix, ICL-prefix, plus 2 additional held-out personas from
`negatives.default_panel()` (not used as training contexts). This bystander panel
is the SAME for every cell, allowing direct cross-arm leakage comparison.

The leakage read uses Tier 1 parameters (20 q × 5 samples, 3 judge draws) for
each bystander context × each cell. Total bystander calls per cell:
5 bystander contexts × 20 q × 5 samples = 500 completions × 3 draws = 1500 judge
calls per cell. For 22 mandatory cells × 1500 = 33 K judge calls (leakage only).

**Install-strength confound control:** cross-condition leakage comparison is ALWAYS
at dose-matched install (the selected checkpoint is where both arms are in the same
install band [0.60, 0.85] before the leakage comparison). If a pos-only cell does not
reach the band, leakage is still reported but the cross-arm comparison carries an
explicit "unmatched install" caveat.

**Judge rule 23 compliance:** all reason-then-score rubrics use max_tokens=300
(the #1090 fix). Per-arm dropped-draw rates reported. Judge cache keys include
rubric_key (rule 22, #1018 contract).

### D7-amendment — Work-conserving multi-GPU dispatcher (replaces v4 sequential dispatch)

The v4 `issue1090_dispatch.sh` is a sequential single-GPU runner. This amendment
replaces it with a work-conserving multi-GPU dispatcher:

```
scripts/issue1090_dispatch_v2.sh
```

**Design (modeled on `scripts/run_sweep.py --parallel N`):**
1. Reads a `cell_manifest.json` (written by the orchestrator before pod launch,
   committed to the issue branch) listing all cells in priority order (mandatory
   then BP).
2. Maintains a job queue. On startup, enqueues all mandatory cells; then BP cells
   if the time budget allows.
3. Assigns each pending cell to a free GPU via `CUDA_VISIBLE_DEVICES=<gpu_id>`:
   each GPU runs exactly one cell at a time.
4. Uses `run_sweep.py`'s parallel runner pattern (background processes + wait loop).
   When a cell finishes (exit 0 = done; exit 1 = failed), that GPU becomes free
   and the dispatcher pops the next cell.
5. Failed cells are re-queued exactly ONCE (retry limit=1 per cell). A cell that
   fails twice is marked `failed` in its sentinel file and skipped.
6. Sends the per-cell sentinel file to `/workspace/logs/issue-1090-cell-<cell_id>.json`
   on completion (exit 0 or permanent failure) for `poll_pipeline.py`.
7. After all GPUs idle (queue empty), writes a final `manifest_complete.json`
   sentinel.

**GPU allocation:** 8 GPUs, 8 workers concurrently. For a 7B model with LoRA,
each GPU worker operates at ~80% HBM utilization (model + activations + optimizer
states for a 15-step LoRA run). No TP/DP — each cell is fully independent
(shared-nothing). vLLM generation phases also run per-GPU-worker with a separate
vLLM subprocess per cell.

**Parallelization statement (v2 requirement):**
- Phase P2 (training): 8 cells run concurrently, each on one H100. Sequential
  depth = ceil(28 cells / 8 GPUs) = 4 waves. All 8 GPUs are active during every
  training wave. No inter-GPU communication.
- Phase P3a (install eval generation): vLLM is spawned per cell with TP=1
  (each H100 serves one organism). Up to 8 eval generation jobs concurrent. The
  vLLM subprocess is spawned+torn down per cell by the dispatcher.
- Phase P1b (C5 Qwen datagen): runs on GPU-0 alone during the pre-training window.
  The remaining 7 GPUs idle during this < 0.5h window — acceptable (only 3.5 GPU-h
  wasted vs the 80+ GPU-h training). Alternative: run P1b on a separate 1× GPU pod
  beforehand (saves 3.5 GPU-h but adds 15 min provisioning latency). Plan: run on
  GPU-0 of the 8-GPU pod. Named as a minor GPU-width deviation (§9 note).
- Phase P3b (judge + aggregate): OFF-POD after pod release. 0 GPUs. Batch API.
- **The 8-GPU pod is released before P3b starts.** No GPU idles during the API-bound
  judge phase (the #664 idle-wide-pod anti-pattern is avoided).

**Implementation notes:**
- Each cell's per-GPU runner is `uv run python scripts/issue1090_run_cell.py --cell <cell_id> --gpu <gpu_id>` (a new thin wrapper that sets CUDA_VISIBLE_DEVICES and calls the existing per-cell logic from `issue1090_run.py`).
- Resume-safe: cells write checkpoint sentinel files. The dispatcher skips
  `status=="done"` cells on restart.
- `nohup` + pid tracking per cell (per code-style.md nohup rule).

## §7 Decision Gates

**No gates** — the experiment fits < 4h wall time on the 8-GPU pod, the hypothesis
is pre-grounded in v4's yield results, and intermediate signals are already baked
into the sequential cell priorities (mandatory cells first; BP cells run only if
budget remains). The v4 K1/K2/K3 kill paths carry forward per cell, handled by
the dispatcher's per-cell failure logic (not gates — they route to skip, not stop).

### Kill criteria (round-level abort / invalidation)

- **K1-v5 (pipeline defect, per arm):** C1 formatting misses its yield floor OR
  its organism never reaches structural rate ≥ 0.8 in a given context × regime
  arm → THAT ARM's results are void (pipeline defect); if C1 fails in ≥ 3 of the
  4 mandatory C1 arms, ABORT training for all remaining cells, ship the yield +
  diagnostics analysis only.
- **K2-v5 (datagen collapse):** yield floor failures across ≥ 8 of the 22
  mandatory cells' datagen (excluding C4, which is expected to miss) → do NOT
  train the failing cells (K3 per-cell carries forward); if BOTH regimes of the
  HEADLINE C3 fail in all 4 contexts, halt after datagen — the yield analysis is
  the deliverable (v4 K2 parity).
- **K3-v5 (install floor):** a floor-clearing cell whose organism never reaches
  the [0.60, 0.85] band at any rung still SHIPS its dose curve (reportable
  negative); if NO arm in the entire matrix reaches the band, the
  matched-install leakage comparison (H2/H3) is declared unrunnable and the round
  ships install-only results with the "unmatched install" caveat.
- **K4-v5 (dispatcher wedge):** the 8-GPU dispatcher makes no per-cell progress
  (no new cell sentinel) for > 2h with pending cells → kill + diagnose per
  crash-fix-rounds.md before any relaunch; if the pod wall-clock exceeds 14h
  (~1.4× the 10h estimate), stop the pod, ship completed cells, and re-scope the
  remainder rather than letting the run overshoot the pre-approved budget.
