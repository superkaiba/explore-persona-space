### 0.0 TL;DR (plain English)

- **What I'll run:** The parent experiment fitted a linear map that predicts the model's answer-time state from its pre-answer state, then tried to steer behavior by pushing the pre-answer state along the map's *inverted* readout of the persona direction — and that failed, while a directly-measured direction worked at the same spot. Inversion divides by the map's small signal components, which amplifies noise. So this round builds four new candidate directions from the SAME already-fitted map — one that multiplies by the map's components instead of dividing (the transpose), and three that smoothly interpolate between dividing and multiplying — and injects each at the same spot, same doses, same judging pipeline as the parent.
- **What I expect:** If the earlier failure was just noise amplification from the inversion, at least one of the new directions should move the behavior score above the parent's noise band (I'd guess the transpose-like end for sycophancy, where the working reference direction moved things by ~36 points). If the map's directions simply don't line up with what causally drives behavior at that spot, all four will stay inside the band.
- **What would change my mind:** Any new direction whose score gain clears the parent's noise band (with its bootstrap interval clear of the band edge) says the map DOES carry causally usable content and the parent's negative result was an artifact of how the direction was weighted. All four failing — while the parent's directly-measured direction stands — says the map's row space is genuinely misaligned with the causal direction, closing this alley.

**Why code, not a model call:** direction construction is deterministic linear algebra on stored tensors; steering requires forward-hook injection inside HF generation — neither is expressible as an API call.

**4.1 Direction construction (the changed variable).** Per behavior b ∈ {evil, sycophancy} × layer ℓ ∈ {0..27}, in the parent fit's standardized frame. Load `L{ℓ:02d}.npz` (keys verified at plan time: `W, xmu, xsd, ymu, s, lam, kstar, n_rows, pass_b_revision`; `W` fp32 (3584, 3584) = the ALL-rows production ridge fit — `_fit_layer_worker` L864–906 stores `fit["W"]` from `ridge_fit_matrix(X, Y)` on all 5,000 rows, the exact map whose SVD produced the parent's steered `d_pre`). Compute `M, Um, Sm, Vmt = i2254.map_svd(W)` (L323 — reused verbatim, float64; NOT a refit: the npz `s`/`lam`/`kstar` are the fit's data-side spectrum, untouched). Let c = Umᵀ r_B(b, ℓ) with r_B from `i2254._load_rb_all()` (#779 bank, rev `037fcbb`).

- **Arm `tr` (transpose):** w = Vmtᵀ (Sm ⊙ c) — i.e. V S Uᵀ r_B, per-mode weight c_i·s_i, full spectrum (no truncation; small modes are down-weighted by s_i, so no noise amplification — rationale §11).
- **Arms `rl1`/`rl2`/`rl3` (ridge-inverse):** w_λ = Vmtᵀ ((Sm/(Sm²+λ)) ⊙ c) — i.e. Mᵀ(MMᵀ+λI)⁻¹r_B (the scope's `W^T(WW^T+λI)^{-1} r_B` in the M = Wᵀ convention), per-mode weight s_i/(s_i²+λ), full spectrum. **Registered λ rule:** λ_j = quantile_j({Sm_i²}, all 3584 modes) at j ∈ {0.05, 0.50, 0.95}, per layer (behavior-independent — the map is behavior-independent; only c depends on b). Realized at plan time from the stored artifacts: **L14: λ = 2.13128e-05 / 0.00990789 / 0.484497** (Sm max 5.27, min 1.916e-05); **L17: λ = 2.9635e-05 / 0.012374 / 0.579497** (Sm max 6.112, min 4.296e-06). Other layers computed by the same rule at run time, all persisted in `ladder_report.json`. Span rationale: at λ₁ ≈ q05, ~95% of modes get pinv-like 1/s weighting; at λ₃ ≈ q95, ~95% get transpose-like ∝s weighting; after unit normalization the λ→∞ limit EQUALS the transpose arm and λ→0 equals the full-rank pinv — so with the parent's k*-truncated pinv the results form a 5-point pinv→transpose ladder.
