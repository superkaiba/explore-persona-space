### Concerns (fresh issues in the fix — none re-opens the skip-decision blocker)

1. **Presence-only re-drive can bless a PRIOR fingerprint's HF bytes as this run's upload, silently staling the durable record.** should_skip:490-493: when `uploaded` is absent, `_hf_files_present(cell)` returning True SKIPS the re-upload and sets `uploaded=True` — but `_hf_files_present` (429) checks file EXISTENCE at the slug prefix only, and the slug prefix does not encode the fingerprint. Trace: F1 completes + uploads (HF has F1 bytes at `issue2225_ctxsteer/adapters/<slug>/`) → code change → F2 retrains clean locally (`completed` sha = F2) but crashes/fails in the save→upload window (OOM, transient HF 504 — the exact windows this commit hardens) → resume: local sha matches, flag absent, F1-era files present → marks `uploaded=True`, never re-uploads → HF permanently carries F1 bytes under an F2-blessed manifest. The primary same-pod eval is protected (`issue2225_eval_gen.resolve_adapter` is local-first, and the manifest's local sha is F2-correct), which is why this is a Concern rather than a Critical — but any fresh-pod eval, post-cleanup re-eval, or sibling artifact-reuse STAGES FROM HF (eval_gen.py:216-239) and would consume F1 bytes as the F2 cell, and eval's own resume fingerprint hashes the staged (stale) artifact so it cannot catch it. After the first full wave, ALL 81 cells are previously-uploaded, so any crash-fix round makes the trigger state common (the same likelihood argument r1 used). One-line fix: when the `uploaded` flag is absent, re-upload UNCONDITIONALLY (`_upload_cell_adapter` is an idempotent overwrite at the same prefix) — drop the `_hf_files_present` short-circuit from the re-drive leg (keep it in leg 2, where the flag gates it). Land before the production fan-out.
2. **The fan-out path never threads `--no-upload` — the fix's own escape hatch is single-cell-only.** `run_fan_out`'s should_skip call (903) omits `allow_upload=not args.no_upload` (only the single-cell branch at 1217 threads it), and `_single_cell_cmd` (836) never forwards `--no-upload` to children (pre-existing). New in this commit: a `--smoke --no-upload` fan-out on an offline/credential-less box now performs network calls in the PARENT and crashes fail-loud on the re-drive (`raise_on_error=True`) whenever a completed-not-uploaded manifest exists, instead of skipping. Fix: thread `allow_upload` into the run_fan_out skip check (and consider forwarding `--no-upload` to children for consistency).
3. **`--dry-run` can now spuriously raise under a restricted parent CVD.** main() defaults dry-run `n_gpus` to 8 when `--n-gpus` is unset (~1254), and `run_fan_out` computes `_visible_gpu_entries(n_gpus)` (899) BEFORE the dry-run branch — so a zero-cost `--dry-run` preview inside e.g. a 1-GPU SLURM interactive shell (`CUDA_VISIBLE_DEVICES=0`) raises `RuntimeError: fan-out width 8 exceeds...`. Pre-fix, dry-run printed ordinals regardless. Clamp the dry-run default to the parent CVD entry count (or `min(8, len(entries))`).
