# Plan — Task #507: Does model scale rescue the cosine/JS leakage predictor for sycophancy?

A scale port of #470's predictor study: train the SAME contrastive sycophancy rig at the SAME #411 recipe on Qwen-2.5-**72B**-Instruct, then score the same family of base-model persona-distance predictors against the new per-bystander leakage matrix. The hypothesis is that a 10× larger model has cleaner persona representations, so the geometric distance that should govern leakage carries more signal. The risk is that the contrastive recipe contains leakage just as well at 72B as at 7B, leaving a floored DV that no predictor can score against — the smoke test gates that contingency.

---

## 0.0 TL;DR (plain English)

- **What I'll run:** Train Qwen-2.5-72B (the largest open model in this family, vs the 7B I used last time) on the same six "source" persona setups #411 already ran, then check whether the trained model also acts more agreeable under twenty-three OTHER personas I never trained — and whether a couple of geometric "how-similar-are-these-two-personas" numbers I read off the base model PREDICT which of those bystanders catch the trait worst. The whole point is: do these predictors that failed at 7B suddenly work at 10× the size?
- **What I expect:** I think the 72B run will look a lot like the 7B run — bystander leakage stays small, the predictors stay flat. The clean contrastive negatives kept transfer contained at 7B, and that mechanism is recipe-driven, not size-driven.
- **What would change my mind:** If at 72B the bystander leakage SPREADS (some personas catch the sycophancy strongly, others don't) AND the closer-in-similarity ones are the ones that catch it, that's the predictor working — and I'd want to know what specifically 7B was missing. The other surprise direction would be 72B leaking *uniformly* to everyone, which would say something different (and scarier) about scale.

Test whether base-model persona-distance predictors (residual cosine and JS divergence, source persona to bystander persona) predict per-bystander sycophancy leakage **better at larger model scale** than they did on Qwen-2.5-7B-Instruct, where they failed (#470). ## 3. Hypothesis

**H1 (primary, scale rescues the predictor):** Under source fixed effects on 72B, at least one of `{cosine_layer57_last_prompt, response_token_cosine_l57, js_sequence_rb}` achieves within-source Spearman ρ ≥ +0.20 with one-tail p < 0.05 AND **strictly beats** the content-free bystander base-rate null in a paired bootstrap of |Δρ| (95% CI excludes 0). At 7B the same predictors produced cosine ρ=+0.14 (p=0.09), JS ρ=+0.05 (p=0.55), and were beaten by base rate at the diagnostic comedian case. Scale rescues the predictor iff both bars clear.

**H2 (secondary, diagnostic-leak recovery):** At 72B, the structural analog of `software_engineer → comedian` (defined as: the bystander with the largest single-cell Δ that is ranked outside the top-10 by cosine_l57 OR by JS at 7B) enters the top-5 most cosine-similar OR top-5 most JS-similar bystanders to its source. The 7B baseline placed comedian at 23/23 across every geometric predictor.

**Falsification (clean negative):** Within-source ρ for both cosine and JS at 72B stays statistically indistinguishable from the 7B 95% CIs (their CIs overlap the 7B point estimates), AND the diagnostic leak is again ranked outside top-10. Report the honest negative: "scale alone does not rescue the sycophancy predictor; the failure is recipe-driven (contrastive negatives contain leakage, leaving no DV signal) or construct-driven (sycophancy leakage is not a pairwise-distance phenomenon), not size-driven."

**DV-floor kill condition:** If 72B's mean-bystander Δ across all 6 sources sits within ±0.05 of zero AND fewer than 21 of 138 cells exceed |Δ| ≥ 0.10 (the 7B counts), the predictor question is uninformative regardless of which ρ comes out. The headline becomes "the contrastive recipe contains leakage at scale just as it did at 7B" — a different, smaller finding. Smoke-gate (§7) catches this at the end of cell 1.

### 4.4 7B re-run trigger (Phase 5 optionality)

The 7B re-run in this harness is a control whose value depends on what the 72B numbers say. Decision rule auto-fires in `dispatch_sycophancy_507.py` after Phase 4:

- **Skip Phase 5** when the 72B headline matches #470's 7B headline (both predictors floored, cosine ρ and JS ρ within ±0.05 of #470's point estimates, comedian-analog still 23/23). No environment-drift confound to rule out — the result IS that scale doesn't rescue.
- **Run Phase 5** when 72B shows a non-trivial effect that diverges from #470 by more than 0.10 ρ in either direction. The 7B re-run then tells us "is the 72B improvement (or worsening) real, or did the new harness shift the 7B baseline too?"

This skip rule respects the consistency-checker single-variable contract — Phase 5 is a control, not a second experimental variable. If it fires, it tightens the 72B claim.

(Note: the 7B re-run is single-seed [seed=42] matching #411's anchor seed — it's a baseline reproduction, not a power-tightening run.)

```python
# experiments/sycophancy_scale_507/predictor_72b.py
# Replicates phase3_sequence_js_kl from #470 with the 72B model.
import math
import numpy as np
import torch
from explore_persona_space.analysis.divergence import (
    build_teacher_force_inputs, teacher_force_batch,
    compute_js_divergence, compute_kl_divergence,
)

R = 8  # responses per (persona, probe), inherited from #470 / arXiv 2504.10637
MAX_NEW = 256  # inherited from #470

def compute_js_kl_for_cell_72b(
    model,  # AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-72B-Instruct",
            #   torch_dtype=torch.bfloat16, device_map="auto")
    tokenizer,
    source_prompt: str,
    bystander_prompt: str,
    source_responses: list[str],     # R*n_probes responses from source
    bystander_responses: list[str],  # R*n_probes responses from bystander
    probes: list[str],
) -> dict:
    js_per_probe: list[float] = []
    kl_src_to_bys: list[float] = []
    kl_bys_to_src: list[float] = []
    n_probes = len(probes)

    # Sample-from-source side
    for probe_idx, probe in enumerate(probes):
        for r_idx in range(R):
            response = source_responses[probe_idx * R + r_idx]
            batch_inputs, prompt_lengths, response_len = build_teacher_force_inputs(
                tokenizer=tokenizer,
                system_prompts=[source_prompt, bystander_prompt],
                question=probe,
                response_text=response,
            )
            # 72B bf16 weights (~145 GB) do NOT fit on a single H100 80GB.
            # device_map="auto" across 2×H100 80GB places ~73 GB weights per
            # GPU + KV/activation overhead, OR co-locate on the post-Phase-2
            # inf-70b 8×H100 pod. Preflight at cell 1 verifies no CPU offload
            # (all 145 GB resident on GPUs, nvidia-smi confirms). See §12 A7.
            log_probs = teacher_force_batch(
                model, batch_inputs, prompt_lengths, response_len,
                device="cuda:0", max_batch=2,
            )
            lp_src, lp_bys = log_probs[0], log_probs[1]
            js_per_probe.append(compute_js_divergence(lp_src, lp_bys).item())
            kl_src_to_bys.append(compute_kl_divergence(lp_src, lp_bys).item())

    # Sample-from-bystander side
    for probe_idx, probe in enumerate(probes):
        for r_idx in range(R):
            response = bystander_responses[probe_idx * R + r_idx]
            batch_inputs, prompt_lengths, response_len = build_teacher_force_inputs(
                tokenizer=tokenizer,
                system_prompts=[source_prompt, bystander_prompt],
                question=probe,
                response_text=response,
            )
            log_probs = teacher_force_batch(
                model, batch_inputs, prompt_lengths, response_len,
                device="cuda:0", max_batch=2,
            )
            lp_src, lp_bys = log_probs[0], log_probs[1]
            js_per_probe.append(compute_js_divergence(lp_src, lp_bys).item())
            kl_bys_to_src.append(compute_kl_divergence(lp_bys, lp_src).item())

    return {
        "JS_sym_nats": float(np.mean(js_per_probe)),
        "M_js": 1.0 - float(np.mean(js_per_probe)) / math.log(2.0),  # [0,1] similarity
        "KL_src_to_bys": float(np.mean(kl_src_to_bys)),
        "KL_bys_to_src": float(np.mean(kl_bys_to_src)),
        "KL_sym": 0.5 * (float(np.mean(kl_src_to_bys)) + float(np.mean(kl_bys_to_src))),
        "n_probes": n_probes,
        "R_per_side": R,
    }
```

**Compute-shape sanity:** 138 cells × (50 probes × 16 R total × 1 forward of batch-2) ≈ 110k forward passes. At 72B bf16 batch-2 with average response length ~150 tokens, one forward ≈ 400-600 ms on a 2×H100 device_map="auto" split (vs ~80 ms at 7B per #470; the cross-GPU layer split adds overhead vs an unsharded 1-GPU forward, but the model does not fit on 1×H100 — see §12 A7). So ~6-10 hours for Phase 3 on a standalone 2×H100 pod. If we **co-locate** on the post-Phase-2 inf-70b 8×H100 pod (Phase 2 has already loaded the base weights into vLLM and the pod is the natural successor on the critical path), we get zero marginal GPU-hours AND lower per-forward latency (the wider TP partition further reduces per-layer time). The **default is co-location**; the 2×H100 standalone is the fallback if the inf-70b pod was already released for an unrelated reason. We avoid the vLLM-then-HF teardown trap by subprocess-isolating Phase 1 (vLLM sampling) from Phase 3 (HF teacher-force) on the same pod — fresh `uv run python` invocation for Phase 3 (the §8 row's mitigation).

**Phase 3 preflight (fail-loud, runs at cell 1 of Phase 3 before the 138-cell sweep):**

1. **Load base 72B on the chosen Phase 3 pod** (2×H100 or co-located inf-70b 8×H100) with `AutoModelForCausalLM.from_pretrained(..., torch_dtype=torch.bfloat16, device_map="auto")`.
2. **No CPU offload assertion.** After load, parse `model.hf_device_map` and assert every value is a `cuda:N` device (no `"cpu"` / `"disk"` entries). `nvidia-smi --query-gpu=memory.used --format=csv,noheader` must show the full ~145 GB resident on GPUs (~72.5 GB/GPU on 2×H100 or ~18 GB/GPU on co-located 8×H100); fail loud if any GPU is empty or host-memory residency is detected.
3. **Dummy batch-2 teacher-force forward.** Construct a 64-token dummy prompt + 64-token dummy response, run `teacher_force_batch(model, ..., max_batch=2)`, confirm completion <60s. Fail loud on OOM / NaN.
4. **JS sanity check.** Run `compute_js_divergence(log_probs, log_probs)` on a self-vs-self pair; assert result is in `[0, 1e-4]` (numerically ~0). Run `compute_js_divergence` on a self-vs-uniform pair; assert result is `≤ ln(2) + 1e-4 ≈ 0.694`. Fail loud on out-of-range.

Any preflight failure surfaces via `epm:failure v1` (failure_class: `infra`), `status:blocked`, and stops the 138-cell sweep before it spends GPU time.

### 4.6 Why layer {21, 40, 57, 70} for the 72B cosine sweep

#470 used layers {7, 14, 21, 27} on Qwen-7B (28-layer stack), with **layer 20** being the published cosine baseline (#470's "Layer-20 residual cosine"). The 7B-layer-20 ratio is 20/28 ≈ 0.714; the analog on Qwen-72B (80 layers) at the same depth ratio is `round(0.714 × 80) = 57`. To preserve the broader depth ladder on 80 layers: 7/28 ≈ 0.25 → 21/80 = 0.263; 14/28 = 0.50 → 40/80 = 0.50; **20/28 ≈ 0.714 → 57/80 = 0.713** (the #470-published-baseline analog); 27/28 ≈ 0.964 → 70/80 = 0.875. Rounded to integers and clamped to existing depths: **{21, 40, 57, 70}**. The 4-layer sweep keeps cost flat (4 forward-pass extractions vs all-80) and lets us report "the #470-baseline-equivalent layer at scale" alongside the per-layer ladder. **Headline = layer 57** (the depth-equivalent of #470's published cosine baseline layer 20 on 7B; NOT layer 21, which would be #404's `HEADLINE_LAYER=21` default — that's the next-deepest layer in #470's 7B sweep, ratio 0.75 → depth-equivalent layer 60 on 72B, which sits outside this sweep).

The Persona Vectors paper itself does NOT claim a depth-invariance rule across model scales — that is a planner-side inference, not a paper claim; the depth-matched layer choice is grounded in #470's own published 7B baseline.

This is not load-bearing for the hypothesis — H1 fires off any of the three primary predictors clearing the bar. The sweep is for interpretability: if 72B's signal is concentrated at a different relative depth than 7B's, that's itself a finding.

### 4.7 Why code, not a model call?

The Phase 3 RB JS estimator computes full-vocabulary per-token divergence between two teacher-forced logit distributions over fp32 log-softmax tensors. This is a numerical reduction across a (response_len × vocab=152064) matrix; there is no plausible single-Claude-call alternative ("ask Claude: how similar are these two personas' base-model output distributions?") that measures the same construct. The recipe is canonical per `.claude/rules/persona-distance-metrics.md` and arXiv 2504.10637; deviating from it would put #507 in a different operational definition than #470, defeating the within-arm comparison. Code is mandatory.

### 4.8 Contrastive negatives (verbatim from #411)

**This experiment IS a behavior-implantation experiment** (implant sycophancy into the source persona), so the contrastive-negatives rule applies. The training mix per source — already authored by #411 and pulled from HF — is exactly the recipe the rule requires:

- 200 source-positive rows (source persona system prompt + wrong-claim question + agree-with-claim target — the positives).
- 400 bystander-negative rows (4 close negative personas × 100 each, each using the SAME question pool but emitting a correction NOT an agreement, with the default `qwen_default` assistant always one of the four — the contrastive negatives).
- 100 no-persona contrastive rows (no system prompt, same questions, emitting corrections — a tertiary control isolating "the persona matters" from "wrong-claim corrections are training signal").
- Ratio: 200 positives : 500 negatives ≈ 1 : 2.5 (slightly more negative than the 1:1 recipe default, but #411 validated this ratio implants cleanly at +0.65 to +0.92 own-rate lift).

We carry this forward unchanged. The contrastive recipe is the very recipe the predictor study at #470 found contains leakage so well that the DV is floored; that's THE risk the smoke gate (§7) catches.

### 4.9 Smoke / sweep architectural parity

Per the unification default: smoke IS the sweep with `--sources software_engineer --seeds 42` (cell 1 only). Same dispatcher, same `train_72b` call shape, same eval invocation, same HF upload path. Cell 1 fires through Phase 1 (training) + Phase 2 (eval) + Phase 2.5 (Haiku judge for software_engineer's 12k rollouts only) + verification of the smoke-gate criteria in §7. On smoke-PASS, the dispatcher spawns cells 2-6 sequentially.

The 7B Phase 5 control is structurally a single-cell sweep over the same code path with a different model id, so the parity is preserved there too.

## 6. Evaluation

### 6.1 Primary verdict

For each of the three primary predictors `{cosine_l57_last_prompt, response_token_cosine_l57, js_sequence_rb}` at 72B:

1. **Per-source within-source Spearman ρ** vs Δ over 23 bystanders (single-seed seed=42 matching #411 / #470 parity), bootstrap 95% CI (n_boot=10000), permutation p (n_perm=10000) — matches #411 / #470 exact settings.
2. **Pooled-138 source-FE-residualized Spearman ρ.** Residualize Δ on the source one-hot, residualize the predictor on the source one-hot, ρ on the residuals (n=132 effective df after source-FE residualization across 138 cells).
3. **Paired bootstrap of |Δρ| against the content-free bystander base-rate null**, jointly resampling cells. 95% CI of |ρ_predictor| − |ρ_base_rate|.

H1 fires iff: 72B's within-source ρ ≥ +0.20 with one-tail p < 0.05 (per-source ρ averaged over 6 sources) AND the paired-bootstrap |Δρ| vs base-rate 95% CI excludes 0 AND the pooled source-FE ρ point estimate at 72B sits ≥ 0.10 above the #470 7B point estimate (the +0.10 practical floor inherited from #470's verdict grid). The headline statistic is the pooled-138 source-FE-residualized ρ at single-seed parity with #470 (n=132 effective df), with per-source ρ bars at n=23 reported as decorative-only context.

### 6.4 Seeds (single seed, matches #411 / #470 parity)

Seed 42 only at 72B (strict #411 carry-through) and at 7B (Phase 5, matches #411 anchor). ## 7. Decision Gates

**One gate — the smoke-cell exit gate.** This experiment IS a long run (~17h wall-clock at 72B on 4×H200 + the 72B LoRA + ZeRO-3 recipe has no precedent in this codebase), so the smoke gate is genuinely load-bearing.

**Gate: post-cell-1 (`72B software_engineer seed 42`).** The dispatcher refuses to spawn cells 2-6 until ALL of these PASS:

1. **Training rig works.** Phase 1 ends without OOM / NaN / DeepSpeed crash. The `adapter_model.safetensors` is present at `/workspace/adapters/issue_507/72b/software_engineer_seed42/` AND uploaded to `superkaiba1/explore-persona-space:adapters/issue_507/72b/software_engineer_seed42/`. The §4.3 runtime safeguard `assert world_size * per_device_batch * grad_accum == 16` must have fired and PASSed at training-start (effective batch = 16, matching #411 on whichever pod path is live — 4×1×4 on 4×H200 default, 8×1×2 on 8×H100 fallback); the run's WandB summary metric `effective_batch_size` must equal 16. A mismatch is a fail-fast condition: the rig is silently training under a different recipe than #411 and the single-variable contract is broken.
2. **Implant landed.** Phase 2 + 2.5 finish for software_engineer at 72B; source-self rate (software_engineer adapter evaluated on software_engineer's own panel slot) is ≥ +0.50 over base (the +0.5 floor matches #411's "training failure" criterion; #411's actual numbers were +0.65 to +0.92 so +0.5 is a generous lower bound).
3. **DV-floor sanity (the contingency).** Across the 23 bystanders, mean-bystander Δ for software_engineer at 72B is recorded but NOT a pass/fail criterion at the smoke cell (1 source isn't enough panel to call the floor). What IS a fail-fast: if mean-bystander Δ for software_engineer at 72B is *less* than +0.05 AND the source-self own-rate is high (≥ +0.70 — the implant clearly worked), that's the strongest single-cell signal that the floor reproduces. In that case the dispatcher LOGS the smoke result, runs cells 2-6 anyway (we need the full 6-source panel to call a floor — software_engineer alone could be idiosyncratic), but **pre-registers** the "report the floor as primary finding" branch as the likely outcome.

The intermediate signals are cheap (cell 1 takes ~4-6h all-in on the 4×H200 pod: ~2.8h train + ~0.5h eval + ~0.5h Haiku judge + setup overhead). A cell-1 OOM would kill the next 5 cells with the same parameters — the gate pays for itself.

**No other gates.** Phases 3-6 are sub-1-hour or analysis-only; gating them fragments the data without saving meaningful compute.

**H200-vs-H100 per-GPU throughput grounding (load-bearing for the GPU-h estimate).** The 1.05-1.08× per-GPU H200/H100 ratio for 72B LoRA SFT under ZeRO-3 is derived from published memory-bandwidth-bound LLM training benchmarks (Northflank, Whitefiber, NVIDIA MLPerf) showing 5-8% speedup on long-running training jobs where the bottleneck is gradient all-reduce comm not GPU compute. The published "up to 1.6×" headline applies to inference and memory-bound workloads where batch size scales with HBM3e capacity; LoRA SFT at per-device batch 1 + ZeRO-3 sharding does NOT capture that headroom because the per-GPU batch isn't growing. If the smoke cell's wall is meaningfully higher than 2.8h (e.g. 4h, suggesting comm overhead dominates further), the §9.3 auto-descope fires.

### 9.2 Parallelism analysis

- **Tensor parallelism — required for 72B inference.** Phase 2 eval uses TP=8 on the inf-70b pod (8× H100). Phase 1 training does NOT use TP — DeepSpeed ZeRO-3 across 4×H200 (default) or 8×H100 (supply-fallback) handles the weight + grad + optimizer sharding; TP would over-shard and starve the per-GPU compute. Phase 3 uses 2×H100 (or co-locates on the post-Phase-2 inf-70b pod) for the base-Qwen-72B forward passes — see §12 A7.
- **Data parallelism — NOT used.** ZeRO-3 IS data-parallel across the training-pod axis (4 H200 or 8 H100); we don't compose it with another DP axis.
- **Sweep parallelism — sequential.** The 6 cells (6 sources × 1 seed) train sequentially on the same training pod. Parallelizing across 6 pods (one per source, 4×H200 or 8×H100 each) would cut wall time to ~3h training but multiply GPU-h by ~6 — not worth it for this experiment. Phase 5's 7B 6 sources × 1 seed run sequentially on a SEPARATE 1×H100 pod (overlapping the 72B Phase 2/3 critical path).
- **Batched inference — vLLM heavy.** Phase 2 is one vLLM TP=8 server serving 6 adapters (or the per-cell-reload fallback). Phase 3 Phase 1 sub-step is vLLM batched generation (R=8 × 50 probes × 24 personas in one `LLM.generate()` call).
- **Pipeline parallelism — used.** Phase 0 → Phase 1 cell 1 → smoke-gate → cells 2-6 + Phase 3 (different pod) starts as soon as Phase 1 cell 1's base-model predictor extraction can start (no dependency on the trained adapters). Phase 5 (7B redux) overlaps with 72B Phase 2 + 3 critical path because it's a separate pod.

### 9.3 Stratification spec (auto-descope priority)

If wall-time projection exceeds 2× plan (>48h critical path) at the cell-1 smoke checkpoint:

1. **First drop:** layer sweep {21, 40, 57, 70} → {57 only}. Saves Phase 3 by ~25%. Acceptable because layer 57 IS the headline.
2. **Second drop:** R for Phase 3 from 8 → 4. Halves Phase 3 GPU-h. The variance penalty is real (RB estimator variance scales as ~1/R, so R=4 has ~2× the per-cell variance of R=8) but the headline statistical test is at the per-source ρ level, not at the per-cell predictor level, so the marginal hit is small. Min N to preserve: R ≥ 4.
3. **Third drop:** drop 2 of the 6 sources (lowest-prior-leakage at 7B from #470: `kindergarten_teacher` and `qwen_default` had the smallest mean-bystander Δ at 7B, +0.013 and +0.054 respectively). Cuts Phase 1 + Phase 2 by 33%. Acceptable because the cross-arm comparison still has 4 sources × 23 bystanders = 92 cells of statistical power. Min N to preserve: 4 sources.
4. **Fourth drop:** swap to Qwen-2.5-**32B-Instruct** (the body's explicit fallback). At that point we've materially changed the experimental design and the headline framing shifts to "does mid-scale rescue the predictor."

Seeds are NOT a descope axis here (already at the single-seed parity floor matching #411 / #470).

The orchestrator's auto-descope walks dimensions in this priority order; when none keep ratio ≤ 1.5× while staying above the per-dimension min-N, it escalates via `gates.conditional.compute_deviation_resolution`.

### 9.4 Disk

- Phase 1: 6 LoRA adapters × ~700 MB each (rank-32 LoRA on 72B's ~150 GB base) = 4.2 GB on the training pod (4×H200 default, 8×H100 supply-fallback). Each adapter uploads to HF after training and is deleted locally per the `EPM_PERSIST_ADAPTER_HF_REPO` + `EPM_SKIP_INLINE_CHECKPOINT_UPLOAD` recipe (no merged checkpoints written to disk on the training pod). Peak local disk ≤ 2 GB.
- Phase 2: vLLM loads the base 72B (~145 GB on the inf-70b pod) and 6 adapters (one at a time via `--enable-lora` cache); 72k completions × ~500 bytes JSON = ~35 MB raw_completions. Peak: 145 GB base + 35 MB output.
- Phase 3: 9600 Phase 1 responses × ~500 bytes = ~5 MB. Phase 3 outputs: 138 cells × ~10 KB = 1.4 MB. Peak: 145 GB base load + ~7 MB output.
- Phase 5: same pattern at 7B (~15 GB base + similar small outputs).
- Total disk: well under MooseFS 130 GB per-pod quota at every stage.

### 9.5 Pod intent

- **Phase 1 (training):** **Default = `--gpu-type H200 --gpu-count 4` (4×H200 ZeRO-3).** Justification: per the §12 A4 corrected PEFT math, LoRA freezes the 72B base so AdamW state lives on the ~421M adapter params only (~5 GB total). 4×H200 ZeRO-3 puts ~36 GB base shard + ~3 GB LoRA state per shard = ~40 GB per H200, leaving ~100 GB per H200 for activations + activation checkpointing. The single-variable contract on hardware is fully satisfied — both default and fallback paths land at effective batch 16. **Supply-fallback = `--gpu-type H100 --gpu-count 8` (8×H100 ZeRO-3)** if 4×H200 unavailable for >4h after first provision attempt (§8 supply-constraint row); per-shard headroom ~60 GB on H100, also safe.
- **Phase 2 (eval):** `--intent inf-70b` (8×H100 TP=8). Standard for 72B-class inference.
- **Phase 3 (predictor extraction):** **Default = co-locate on the post-Phase-2 `inf-70b` 8×H100 pod after Phase 2 completes** (zero marginal GPU-hours; the pod is on the critical path anyway). **Fallback = standalone `--intent inf-70b --gpu-count 2` (2×H100)** if the Phase 2 pod was already released or supply forces a new provision. Base Qwen-2.5-72B-Instruct at bf16 (~145 GB) does NOT fit on 1×H100 80GB — that earlier claim was wrong; see §12 A7 for the corrected math. The 2×H100 standalone path costs 16 GPU-h (2 GPUs × 8h wall); co-location costs 0 marginal GPU-h.
- **Phase 5 (7B re-run, optional):** `--intent eval` (1×H100). Separate from the 72B critical path.
