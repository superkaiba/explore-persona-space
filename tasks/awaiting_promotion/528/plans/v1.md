# Plan v1 — Issue #528: LoRA installs above base on non-saturated traits, and does role-header gate more cleanly than a system prompt?

Parent: #517 (base-headroom probe). Sibling/recipe parent: #498 (role-header vs system-prompt; saturated). Lineage: #517 → #498 → #464 → #460.

---

## 1. Goal + Hypothesis

**Goal (verbatim from frontmatter):** Test (a) whether LoRA training installs a desirable assistant trait above the untrained Qwen-2.5-7B-Instruct base, using traits chosen to have genuine base-model headroom (validating, conciseness, asks-clarifying-question-first, calibrated-uncertainty) rather than RLHF-saturated traits, AND (b) whether encoding the persona as a custom chat-template role header segments each trait more cleanly (less leakage to the default assistant and to other personas) than a system-prompt encoding — the q:spec-role-header test #498 could not answer because its traits were saturated.

**Hypotheses (two co-equal claims, both stated as falsifiable `if X then Y`):**

- **H1 — Installation (per trait, traits-with-headroom):** If LoRA training under the #498 contrastive-negatives recipe (system-prompt encoding) installs the trait, then the trained-minus-base paired Δ on the shared per-trait Q-bank is strictly positive — paired t-test per trait, Holm-Bonferroni-corrected across the 4 traits, two-sided α=0.05, with the corrected confidence interval excluding 0. We expect this to PASS for traits where the base 95% CI sits strictly below 3.5 (real headroom: validating confirmed at base 2.64 per #517; conciseness/asks-clarifying/calibrated-uncertainty conjectured-low). We expect this to NOT-PASS or yield small-effect for traits where the base CI overlaps or exceeds 3.5 (no headroom).

- **H2 — Segmentation (paired role-vs-system, off-target):** If a custom chat-template role header segments the trait more cleanly than a system-prompt encoding, then the role-arm leakage − system-arm leakage paired by seed, averaged across the 4 traits and across the OFF-target contexts (bare default assistant + the 3 other-trait scenarios), is strictly negative with the 95% paired-bootstrap (10k) CI strictly below zero, AND ≥ 2 of 3 seeds negative. This is the segmentation Δ #498 produced as +0.044 [-0.013, +0.133] (sign WORSE for role-header). The PASS bar for H2 is `d_leakage ≤ −0.15` paired-mean with CI<0 and ≥2/3 seeds negative — looser than #498's plan bar (≤−0.4) because #498 set that bar before observing any data and missed badly in both magnitude and direction; we recalibrate to a smaller-but-still-meaningful effect.

**Conditioning of H2 on H1.** H2 is interpretable ONLY for traits where H1 PASSes (the implant actually landed). For traits where H1 fails the segmentation Δ measures noise around a null implant and is reported descriptively, not as evidence for/against role-header. The headline H2 average is computed across the H1-PASSing trait subset, with the all-trait average reported alongside as a sensitivity check.

### 4.1 Phase ordering

```
phase 0  : preflight (token-id assertion, Q-bank build per trait, Anthropic ping, judge pilot)
phase 1  : R_pos generation (Claude Sonnet 4.5 trait-ideal responses, per trait per Q_train)
phase 1' : R_neg generation (Claude Sonnet 4.5 NEUTRAL no-trait responses under each negative context)

phase 6  : trained-adapter eval (24 LoRAs × 4 traits' Q_test? — NO, each LoRA is per-trait, so only its own Q_test
           × 5 contexts × 40 prompts = 200 generations per LoRA → 24 × 200 = 4800 generations)
phase 7  : judge (3 calls × 4800 generations + 480 base generations = 15,840 Sonnet calls; ~98% deterministic at temp 0)
phase 8  : analyze (paired H1 + H2 + Holm-Bonferroni + paraphrase-rubric robustness on 10% subsample)
phase 9  : plot + upload + sentinel
```

### 4.4 Per-trait rubric (Sonnet 4.5 Likert 1-5)

Add 4 rubric strings to `i528_traits.py` `JUDGE_RUBRIC` dict + 4 paraphrase variants. Each rubric mirrors the `i498_traits.py` rubric shape (USER QUESTION + ASSISTANT RESPONSE + 1-5 anchor descriptions + JSON output schema). Sketches:

- **validating** — verbatim port of `i498_traits.py` `JUDGE_RUBRIC["validating"]` (no changes).
- **conciseness** — rubric reads:
  > "Score 1-5 on CONCISENESS: 5 = response is direct and minimal (≤3 sentences for simple Q, fewer than 150 words for explanatory Q, no preamble like 'Certainly!', no closing sales pitch); 4 = mostly concise with one minor preamble or wrap-up sentence; 3 = some padding but the core answer is direct; 2 = significant padding (preamble + closing + bulleted enumeration where prose would do); 1 = response is mostly padding, mostly enumeration of points that don't answer the question."
- **asks_clarifying_first** — rubric reads:
  > "Score 1-5 on ASKS-CLARIFYING-QUESTION-FIRST: 5 = the FIRST move of the response is a substantive clarifying question (NOT 'happy to help, can you say more?' — a real ambiguity-resolution question that names the ambiguity); 4 = clarifying question is asked but only after 1-2 sentences of generic acknowledgment; 3 = a single clarifying question is asked at the END after a full attempt; 2 = no clarifying question; 1 = ignores the ambiguity entirely and confidently picks one reading without flagging."
- **calibrated_uncertainty** — rubric reads:
  > "Score 1-5 on CALIBRATED UNCERTAINTY: 5 = response distinguishes what the assistant is confident about from what it is not, uses hedges like 'I think', 'I'm not sure', 'this might be wrong' WHERE WARRANTED (and NOT where unwarranted), and offers to verify when verification is possible; 4 = expresses uncertainty appropriately but slightly under-hedged or over-hedged; 3 = hedges generically without distinguishing confident from uncertain claims; 2 = either over-confident on uncertain claims or over-hedged on confident claims; 1 = uniformly over-confident, no hedging at all, presents conjecture as fact."

Each rubric ends with the same JSON output schema: `Return ONLY a JSON object: {"score": <int 1-5>, "reason": "<one sentence>"}`. Paraphrase variants substitute trait-defining vocabulary (concise → terse / minimal / pithy; clarifying → ambiguity-resolution / disambiguation; calibrated → epistemically-honest / hedge-where-warranted) and re-word the anchor descriptions, keeping the same 5-anchor Likert structure.

### 4.5 Q-bank build (per-trait, 4 banks)

Each trait gets its own 60-train / 40-test bank. The build re-uses #498's preflight machinery (fresh Claude Sonnet 4.5 generation prompt → dedup → trait elicitation gate → train/test split). The fresh-generation prompt asks for 150 questions per trait that ADMIT a trait-positive response, with a 4-gate filter:

- `conciseness`: questions that admit a short answer AND a verbose one — fact lookups, definitions, simple how-tos, yes/no questions. Reject questions that genuinely need a long answer (multi-step reasoning, design discussions).
- `asks_clarifying_first`: questions with at least one named ambiguity — missing context, multiple valid interpretations, underspecified constraints. The Claude generation prompt explicitly asks for questions where a clarifying question is the right first move.
- `calibrated_uncertainty`: questions that touch on uncertain or contested factual ground — predictions, opinion-laden topics, edge-of-knowledge facts, "is X better than Y" comparisons.
- `validating`: re-use the #498 `Q_eligibility` filter (emotional content / personal stake / vulnerability).

**Determinism:** Q-bank generation uses seed=42 (passed to the Anthropic call via system prompt `"Generation seed: 42; produce stable output for this seed"` — the Anthropic API does not support seeded generation directly, so we cache the raw response on first run and re-use it; if a regen is forced, the eligibility filter is deterministic and the resulting Q-bank is reproducibly hashed via sha256). The `Q_eligibility.json` file holds the eligible-with-flags list; `Q_train.json` + `Q_test.json` are the persisted 60/40 split (also sha256'd). Same shape as #498's `data/issue_498/Q_train.json` / `Q_test.json`. Layout: `data/issue_528/<trait>/Q_train.json`, `data/issue_528/<trait>/Q_test.json`.

**Prompt-text equality assertion** (the #517 fix): `assert_q_test_equality(trait)` in `i528_data.py` is called at every base+trained scoring step. It loads `Q_test.json` once and asserts that the per-row `q` field in every per-cell raw-generation JSON matches the bank's prompt at the same index by exact-string equality. Mismatch → FAIL (no silent regeneration, no fallback).

### 4.6 Training row builder (per-trait LoRA)

Per-trait LoRA training rows for trait T (e.g. validating):

- **POSITIVE rows** (1 per Q_train, 60 total): under T's own scenario system prompt (Arm A) or T's own role header (Arm B), with the Claude Sonnet 4.5-generated R_pos response for trait T on Q.
- **NEGATIVE rows** (60 total, split evenly across 4 negative contexts = 15 per context):
  - 15 under sibling-trait-1 scenario (e.g. for validating LoRA, 15 under `concise_assistant`)
  - 15 under sibling-trait-2 scenario
  - 15 under sibling-trait-3 scenario
  - 15 under the BARE DEFAULT ASSISTANT (`DEFAULT_SYSPROMPT = "You are a helpful assistant."`, canonical `assistant` role in BOTH arms)
  - Each negative row carries the NEUTRAL `R_neg` response — a Claude Sonnet 4.5 generation under that negative context's system prompt with NO trait-prompting (just an honest answer to Q). This trains the model to NOT emit the trait under that context.

**Total rows per LoRA = 60 positives + 60 negatives = 120 rows.** Ratio 1:1 positives to total-negatives, matching #498. (Note: #498's ~720 came from 3 scenarios × 60 prompts × 4 rows each. The per-scenario shape is 60 positives + 3 negative contexts × 60 = 240 rows. Our per-trait LoRA shape is 60 positives + 4 negative contexts × 15 = 120 rows. Lower absolute count but the same per-positive 1:1 contrastive density.)

**Loss surface.** TRL `SFTConfig(completion_only_loss=True)` — loss only on the assistant turn, system + user masked. NOT `marker_only_loss` (trait is a sequence-level behavior, not a single token). Mirrors #498 exactly.

**Arm B (role-header) tokenization fix.** Qwen-2.5's `apply_chat_template` silently DROPS non-canonical roles. The Arm B row builder uses the manual-concat pattern from `i498_traits.py::BUILD_TRAIN_ROW_ARMB`: build the default-assistant prefix with `add_generation_prompt=True`, swap the trailing `assistant\n` for `<role_header>\n`, append the trait response + `<|im_end|>\n`, pre-tokenize, build the `completion_mask` as `[0]*len(prefix_ids) + [1]*len(completion_ids)`, and feed with `dataset_kwargs={"skip_prepare_dataset": True}` so `SFTTrainer._prepare_dataset` does NOT re-tokenize and overwrite the mask.

### 4.8 Why code, not a model call?

Each trait's per-prompt scoring is a multi-step pipeline (rubric prompt build → Sonnet API call × 3 → JSON-parse → averaging → per-cell aggregation → paired bootstrap). The rubric scoring itself IS a model call (Claude Sonnet 4.5 is the judge — that's the whole point). The CODE pieces (Q-bank build, dedup, eligibility gates, paired-stat computation, prompt-text equality assertion) are NOT replaceable with a single model call: they require determinism, sha256 hashing, paired indexing by q_idx, and bootstrap resampling, all of which benefit from explicit code paths with assertion errors that surface mismatches. Single-model-call alternatives considered: feed all 4800 generations + rubric + paired-stat-prompt to Sonnet in one shot — rejected because (a) context-length blows past the 200k cap, (b) Sonnet does not compute bootstrap CIs reproducibly, (c) the prompt-text equality assertion would be lost. Code path is correct.

### 4.9 Contrastive negatives (REQUIRED — present)

Per the contrastive-negatives rule: every per-trait LoRA includes 60 positives + 60 negatives split evenly across 3 sibling-trait scenarios + the bare default assistant = 1:1 positives-to-total-negatives, 4 negative contexts. The negative responses are Claude Sonnet 4.5 generations under that negative context's system prompt with NO trait priming. The negative context always INCLUDES the bare default (per the rule's mandatory default-assistant negative). NOT EXEMPT.

### 6.2 Statistical tests + thresholds

**H1 (per trait, headroom + installation):**
- *Step 1 (headroom):* per trait, compute the untrained-base in-scenario 95% CI on N=40 prompts (bootstrap, 10k resamples). If the CI sits strictly above 3.5 → the trait is SATURATED at base; report as a methodology-corrected scope caveat (H1 cannot be tested for this trait) but still run the rest of the pipeline. If the CI sits below 3.5 OR overlaps 3.5 → HEADROOM is established and H1 is a live test.
- *Step 2 (installation):* per trait with headroom, compute the **paired** Δ = trained-mean(q_idx) − base-mean(q_idx) over N=40 paired Likert values (each averaged over 3 judge calls × 3 seeds for the trained cell; over 3 judge calls for the base cell). Per-trait paired two-sided t-test, α=0.05 BEFORE Holm-Bonferroni. **Holm-Bonferroni across the 4 trait tests.** PASS if the Holm-corrected p<0.05 AND the bootstrapped 95% paired-Δ CI excludes 0.
- *Per-arm aggregation:* H1 is computed for the **system arm only** as the primary test (mirrors #498's "did the implant land at all"). H1 for the **role arm** is reported as a secondary check (does role-header ALSO install the trait); a failure of H1-role for a trait that H1-system PASSes would be a strong negative signal for the role-header arm.

**H2 (segmentation, paired role-vs-system):**
- Per (trait, seed), compute `leakage_arm(trait, seed) = mean over (4 off-target contexts × 40 prompts × 3 judge calls)` of the trait's Likert score under that arm's adapter. Then `d_leakage(trait, seed) = leakage_role(trait, seed) − leakage_system(trait, seed)`.
- Aggregate across the H1-PASSing trait subset and across 3 seeds: paired-bootstrap mean + 95% CI (10k resamples), all 3 seeds reported.
- **PASS bar:** paired-mean `d_leakage ≤ −0.15`, AND 95% bootstrap CI strictly below 0, AND ≥ 2 of 3 seeds negative.
- Per-context sub-analysis: report `d_leakage` separately for the bare-default context vs the 3 sibling-trait contexts (per #498's finding that the role-arm was worse cross-scenario specifically).
- **Sensitivity:** the "all-trait" H2 (including saturated traits where H1 failed) is reported alongside as a robustness check; reading the headline off the H1-PASSing subset is the primary, the all-trait version is the secondary.

**DV3 (paraphrase ρ):** require ρ ≥ 0.7 for the trait's rank-stable measurement to "carry quantitative weight"; for traits below 0.7, the per-trait result is reported qualitatively (high/low/null) rather than quantitatively. Same convention as #498.

## 7. Decision Gates

**No gates — short run / pre-verified hypothesis on a well-trodden rig.**

Justification: total wall is ≈5-6 h (under the 16-GPU-hour bar for considering a gate), the hypothesis direction is genuinely uncertain BUT the cheapest intermediate signals (smoke train, codepath verify, base headroom probe) are already part of the linear phase ordering — they're effectively pre-gates that exit on failure, not "stop the sweep if metric < X" gates. The 24-cell sweep is the unit of work; chopping it into early-stop checkpoints would add branching with no GPU-hour saving (most of the cost is judge API, not GPU). The mandatory smoke + codepath-verify steps at the front are NOT framed as "decision gates" in the §7 sense — they're prerequisite preflight steps that fail fast on a broken setup, not branching points based on partial results.

## 11. Decision Rationale

For every load-bearing hyperparameter:

- **lr = 1e-5, cosine schedule, warmup_ratio=0.05** — *What:* AdamW with cosine schedule + 5% linear warmup. *Why:* matched to #498's recipe for the same model + LoRA topology + trait-LoRA scale; #498's smoke train at this lr produced clean train loss curves and the in-scenario rubric PASS for all 6 cells. *Source:* `#498` (Reproducibility table). *Alternatives:* Tulu 3's lr=2e-5 (arXiv 2411.15124) was considered; rejected because (a) #498 already validated 1e-5 for this exact trait-LoRA shape, and (b) Tulu 3 was full-fine-tune SFT, not LoRA, so its lr doesn't transfer directly.

- **5 epochs** — *What:* 5 SFT epochs over 120 rows. *Why:* #498 used 5 epochs on ~720 rows; 120 rows means each row sees ~5× more passes, but this is the recipe that produced in-scenario PASS without overfitting on the same model. *Source:* `#498` (Reproducibility table). *Alternatives:* 3 epochs (the open-instruct default) was considered; rejected because #498's per-cell train loss didn't plateau before epoch 4 and the rubric-PASS rate was higher at 5 vs 3 in #498's own pilot.

- **batch 4 × grad_accum 4 (effective 16), max_length 2048** — *What:* effective batch 16 with 2048-token sequences. *Why:* fits on 1× H100 with bf16 + gradient checkpointing for 7B LoRA; matches #498. *Source:* `#498`. *Alternatives:* batch 8 × grad_accum 2 (same effective) — same result, no reason to switch.

- **LoRA r=32, α=64, dropout=0.05, rslora, 7-target-module fan-out** — *What:* moderate-capacity LoRA on q/k/v/o + gate/up/down. *Why:* matched to #498's recipe; r=32 α=64 is the project's house default for trait-LoRA. *Source:* `#498` (Reproducibility table) (which in turn inherits from the project's wider experiment line, validated on Qwen-2.5-7B-Instruct). *Alternatives:* r=8 α=16 (arXiv 2106.09685 default) was considered; rejected because #498's pilot at r=8 underfit the trait response shape (the in-scenario rubric was 2.5-3.0, below 3.5).

- **bf16, gradient_checkpointing=True** — *What:* bfloat16 mixed precision + activation checkpointing. *Why:* Qwen-2.5-7B + r=32 LoRA fits comfortably on 1× H100 in bf16 with gradient checkpointing; no float16 instability observed in #498. *Source:* `#498`. *Alternatives:* fp32 (too slow / OOM), float16 (numerical risk on cosine schedule).

- **3 judge calls × averaged at temp 0** — *What:* judge calls per (prompt, trait, context) are 3 independent Sonnet 4.5 calls at temperature 0, averaged to a single Likert. *Why:* #517's empirical finding — at temp 0, ~97.5% of 3-call sets returned identical scores AND the averaging caught the ~2.5% non-determinism (mostly on the 4-vs-5 boundary). This is a near-no-op cost (3× judge calls, but each is ~0.5 s) that buys ~2.5% precision in the per-prompt Likert. *Source:* `#517` (Reproducibility table). *Alternatives:* 1 call (#498's original choice) — produces slightly more per-row stochasticity; we inherit the #517 improvement.

- **Q-bank 60 train + 40 test per trait** — *What:* 100 trait-eligible prompts per trait, 60/40 split. *Why:* matched to #498 (60 train + 40 test). The 40-test gives ~0.15 Likert SE on the per-cell mean at the 1-5 scale, which is small relative to the ~0.4-1.0 Likert effect sizes #517 observed. *Source:* `#498` (plan + body). *Alternatives:* 80/20 (more train, less test) — rejected because Q_test SE would widen.

- **N=40 paired-Likert prompts × 3 seeds for the bootstrap** — *What:* the per-trait paired Δ is bootstrapped over N=40 prompts; the segmentation Δ is bootstrapped over N=3 seeds (the project standard 3-seed triple). *Why:* matches #498's bootstrap dimensionality. The N=3 paired-bootstrap is wide but the per-seed Δ direction (positive/negative) is the load-bearing signal. *Source:* `#498`. *Alternatives:* N=5 seeds (better CI width) — adds 60% wall-time, rejected for budget.

- **10k bootstrap resamples, α=0.05** — *What:* paired bootstrap with 10,000 resamples for 95% CI. *Why:* #498 standard. 10k is enough to get the 95% CI bounds to ≤0.005 Likert numerical noise. *Source:* `#498`. *Alternatives:* 100k is more precise but adds 10× analysis time for no gain.

- **Holm-Bonferroni correction across 4 trait H1 tests** — *What:* per-trait paired t-test p-values are Holm-corrected. *Why:* 4 simultaneous tests of the same headline ("LoRA installs the trait above base"); without correction the family-wise α inflates to ~0.19. Holm is uniformly better than Bonferroni and the project standard. *Source:* `#498` (paraphrase replication used Spearman without correction because each trait was a separate axis); applied here because all 4 tests share the SAME H1. *Alternatives:* Bonferroni (less powerful), BH-FDR (different error rate target); Holm-Bonferroni is the family-wise correction matching the H1 framing.

- **Judge model `claude-sonnet-4-5-20250929`** — *What:* canonical Sonnet 4.5 model id. *Why:* matched verbatim to #498 + #517. *Source:* `#498`, `#517`. *Alternatives:* Opus 4.7 — over-spec for Likert judging, slower + more expensive.

- **Role-header naming convention `<trait>_assistant`** — *What:* lowercase compound role tokens. *Why:* matches #464 + #498's syntax; the planner-deferred decision in the issue body explicitly requires this. *Source:* `#464`, `#498`, issue #528 body. *Alternatives:* uppercase / underscore / hyphen variants — rejected for consistency with prior work + to ensure the multi-token tokenization (#498 plan A2).

- **Sequential 1× H100 (`lora-7b` intent), NOT 4× H100** — *What:* keep #498's budget-fallback hardware choice. *Why:* per-cell wall is 5.5 min × 24 cells = 132 min on 1× H100, fully under the GPU-h budget. 4× H100 would parallelize but adds provisioning overhead with no benefit at this scale. *Source:* `#498` (used 1× H100 in 4.2 GPU-h for 6 cells). *Alternatives:* 4× H100 — overkill for this size sweep.

- **Repo-new model id smoke?** — *N/A.* `Qwen/Qwen2.5-7B-Instruct` is the project's anchor model, used in every prior issue (#498, #517, #464, #460, and dozens more). No fresh CPU-side `AutoConfig.from_pretrained` smoke needed; inheriting `Source: #498`.
