## 0.0 TL;DR (plain English — the user reads this first)

- **What I'll run:** I take 5,600 real multi-turn chats from the same public chat corpus the mapping line already uses, have the model write its own answer at every turn, and record the model's internal state just before and just after each question. Then I fit the usual "state before the answer → summary of the answer" predictor separately at turn 1, turn 2, turn 3, turn 4 (and out to turn 8 on a smaller set), and check three things: does the turn-1 predictor still work at later turns, can the state at turn 1 predict answers that come several turns later, and does whatever changes with depth line up with the persona directions we already have.
- **What I expect:** the predictor itself stays mostly the same across turns (applying the turn-1 predictor at turn 4 loses only a little accuracy compared to turn 4's own predictor), later answers become partly predictable from earlier states as the conversation history piles up, and any drift along persona directions is small but measurable.
- **What would change my mind:** a large, growing gap between the stale turn-1 predictor and each turn's own predictor that a same-turn refit noise check can't explain — that would say the context→answer relationship genuinely rewires as conversations get longer, which is the mechanistic story persona drift needs.

## 1. Goal

Characterize whether the context→answer activation mapping — trained so far on mostly short, single-turn contexts (#779: per-layer ridge from context last-token state to mean-pooled answer activation, held-out R² ≈ 0.60–0.63) — holds up or changes systematically as the context grows and spans many chat turns, training BOTH the context→answer mapping (prefix + query k → answer k) AND the prefix→answer mapping (prefix alone → answer k, query marginalized) on the SAME conversations: (a) is the turn-1 mapping the same as the turn-k mapping; (b) can later answers (2, 3, 4, …) be predicted from earlier-turn inputs using earlier-turn mappings; (c) does any systematic change with context length offer an account of persona drift / context rot. **N/A — not a replication** (no published finding is being replicated; the design extends the project's own #779/#810/#922 line).

## 3. Hypothesis

- **H1 (mapping stationarity, question a):** the context→answer mapping is approximately turn-stationary. Quantitative prediction: the stale-map deficit Δ_k = skill(own turn-k map) − skill(turn-1 map applied at turn k), at the frozen 6-block mean, stays < 0.10 for k ≤ 4 and its 95% CI overlaps the half-sample twin noise floor at ≥2 of 3 turns k ∈ {2,3,4}. **Falsified if** Δ_k exceeds the twin floor with CI excluding it and grows monotonically in k (that is the "mapping rewires with depth" signature).
- **H2 (cross-horizon forecast, question b):** later answers are partly predictable from the turn-1 state: forecast skill F(1→k) > 0 (CI excluding 0) for k = 2, and decays toward 0 by k = 4; F(1→k) stays below both the prefix-only map at k and the copy-previous-answer null beyond k = 2. **Falsified if** F(1→2) ≤ 0 (no cross-turn information in the turn-1 state) or if F(1→k) ≈ own-skill(k) (the conversation is fully determined at turn 1 — would be surprising and important).
- **H3 (context dominance / rot, question c):** the prefix-only map's skill rises with k relative to the context map's (prefix increasingly determines the answer as history accumulates): skill(prefix map, k)/skill(context map, k) increases from k=2 to k=4. Secondary drift read: actual answer trait projections drift with turn index and/or the stale map's residual has a systematic component along trait directions exceeding the norm-matched random-direction band. **Falsified if** the ratio is flat/decreasing and residual trait projections sit inside the random-direction band — then whatever persona drift is, it is not visible in this mapping.
- **H4 (length vs turns):** within a turn cell, skill and transfer deficit correlate with context token length; the length-matched turn comparison determines whether "turn index" effects are token-length effects. (Exploratory, no threshold.)

## 4. Design

Frozen model; three stages: (G) GPU capture — build the multi-turn corpus, generate the model's own answer per turn, capture states; (C) CPU fits — per-turn ridge maps + transfer/forecast evaluation + nulls; (A) analysis/figures. No new training, no judging.

### 4.1 Corpus construction (new code: `scripts/issue958_build_corpus.py`)

Source: `lmsys/lmsys-chat-1m` (HF, gated=auto; access verified this session via `dataset_info` with the project token). **Data source + realism tier: tier 1 — real user–assistant conversations** (the line's standing corpus, #779/#922). Grafted-query units (§4.5) recombine tier-1 text across conversations; the recombination artificiality is named in §12 and carried as a scope caveat.

Exact filtering rules, applied streaming over the train split, in order:

1. `language == "English"`.
2. Roles strictly alternate user/assistant starting with user; all messages non-empty after `strip()`.
3. `turn >= 4` (main panel) / `turn >= 8` (long panel). (LMSYS `turn` = number of user–assistant exchanges; verified against the `conversation` array length at build time — assert `len(conversation) == 2*turn`.)
4. Moderation: drop the conversation if any message among the used turns (first K exchanges) has `openai_moderation[i]["flagged"] == True`. (Keeps refusal-dominated rollouts from distorting the answer distribution; realism cost named in §12. Bank/content hygiene: the builder reads flags and counts only, never prints message text.)
5. Dedup: sha256 over the concatenation of the first K user messages; keep first occurrence.
6. Token cap: for every used turn k ≤ K, formatted input tokens (prefix + query k + generation prompt) ≤ 7,168; drop the conversation if any used turn exceeds (preserves "same conversations at all turn numbers"; with `max_tokens=1024` the full forward stays ≤ 8,192).
7. Sample (seed 42 shuffle): **main panel** = first 5,000 surviving conversations with K = 4; **long panel** = first 600 surviving conversations with K = 8, disjoint from the main panel (long-panel conversations also satisfy the main filters but are excluded from the main sample).

Outputs: `data/issue_958/corpus/{main,long}.json` — per conversation: id, the K used exchanges (user text + original LMSYS assistant text), token counts, source-model field, dedup hash. Uploaded to HF (`issue958_multiturn/corpus/`).

**Why code, not a model call?** The corpus filters are deterministic structural reads of dataset metadata fields (language, turn, moderation flags, token counts) — no unstructured-data classification is needed; a model call would add cost and nondeterminism with no added validity. Flip condition: none foreseeable at this N.

### 4.2 Units and capture positions

A **unit** = (conversation c, turn k). Per unit, three text segments under the Qwen chat template (`assert_template_tail` boundary asserts reused from `issue922_capture_positions.py`):

- **prefix(c,k):** template-formatted turns 1..k−1 using the LMSYS-original assistant answers, ending after answer k−1's `<|im_end|>\n` (`add_generation_prompt=False`). For k=1: the default system block only (constant across conversations — the prefix map is undefined/degenerate at k=1 by construction and is reported as such).
- **context(c,k):** prefix + user turn k + `<|im_start|>assistant\n` (`add_generation_prompt=True`); its last position is the #779/#922 "last prompt token".
- **answer(c,k):** Qwen's OWN generated answer to context(c,k) (§4.3), teacher-forced back through the model for capture.

Stored per unit: a `(5, 29, 3584)` fp16 tensor — rows = [prefix_end, ctx_last−1, ctx_last, answer_mean, answer_last]; 29 residual rows = embedding stream + 28 decoder blocks (#922 convention). `answer_mean` = mean over the generated answer token positions EXCLUDING the trailing `<|im_end|>` (match the #779 mean-pool convention; verified against `issue779_capture_answer_summaries.py` at implementation — §12). The capture computes the mean ON-GPU from the per-position hook output before the fp16 CPU transfer (stream-reduce; the full per-position grid is never materialized off-GPU — #666/#772). Plus per-unit metadata JSON: token counts (prefix/query/answer), rollout finish reason.

### 4.3 Rollout generation (new code: `scripts/issue958_rollouts.py`, vLLM)

For every unit, generate Qwen's own answer: `SamplingParams(n=1, temperature=1.0, top_p=0.95, max_tokens=1024, seed=42)` — **Source: #779 verbatim** (`issue779_collect.py:558`). One rollout per unit; vLLM automatic prefix caching ON (turn-k contexts of the same conversation share prefixes). Rollout TEXT persists to `raw_completions/rollouts/` per the Upload Policy (JSON, sharded <9 MB if needed).

**Answer-provenance decision (load-bearing, grounded):** answers are **on-policy Qwen rollouts under LMSYS-verbatim prefixes** (option A).
- Rejected option B (full on-policy conversation regeneration): replacing answer 1 with Qwen's answer makes the real user's query 2 incoherent (it responds to the ORIGINAL model's answer), and simulating the user's next query is tier-3 synthetic — it would change the query distribution, the one thing LMSYS supplies that we cannot synthesize (tier-1 real follow-ups).
- Rejected option C (teacher-force the LMSYS original answers as targets): those answers are OTHER models' text (vicuna/chatgpt/koala…); the mapping under study is Qwen's context→answer mapping, and #779/#922 both used Qwen's own completions as targets.
- **Named confound of option A:** the prefix's assistant turns are off-policy (other-model text). The model is being asked "given this conversation so far — whoever wrote it — what will YOU answer"; the mapping is well-defined over any context, but stationarity conclusions are conditional on this prefix distribution. Bounded by the **prefix-provenance control** (§4.5): a Qwen-authored-prefix arm at k=2 measures how much the mapping read moves when the prefix answer is on-policy.

### 4.4 Capture (new code: `scripts/issue958_capture_turns.py`, reusing `issue922_capture_positions.py` internals)

Reuse verbatim: `_right_pad_batch`, `_resolve_rows` (hooks on `embed_tokens` + every decoder block), the length-sorted right-padded batched forward (batch 16, auto-halving under memory pressure), the fp16 500-unit shard persistence with skip-complete resume, and the 3-item **batched-vs-batch-1 equivalence gate** run once at start. New: `tokenize_unit()` builds the three segments of §4.2 with boundary asserts; the hook post-processing gathers [prefix_end, ctx_last−1, ctx_last, answer_last] by index and computes `answer_mean` on-GPU over the answer span mask.

Pseudocode (capture core):

```python
def tokenize_unit(tok, conv, k, qwen_answer):
    prefix_txt = tok.apply_chat_template(conv[:2*(k-1)], tokenize=False, add_generation_prompt=False)
    ctx_txt    = tok.apply_chat_template(conv[:2*(k-1)] + [user_k], tokenize=False, add_generation_prompt=True)
    assert ctx_txt.startswith(prefix_txt)
    full_ids = tok(ctx_txt)["input_ids"] + tok(qwen_answer, add_special_tokens=False)["input_ids"] + END_IDS
    return dict(full_ids=full_ids, prefix_end=len(tok(prefix_txt)["input_ids"]) - 1,
                ctx_end=len(tok(ctx_txt)["input_ids"]) - 1,
                ans_span=(ctx_end + 1, ctx_end + n_answer_tokens))  # excludes <|im_end|>

# per batch: forward with hooks -> hs (B, T, R, H) on GPU
sel = gather(hs, [prefix_end, ctx_end-1, ctx_end, ans_last])          # (B, 4, R, H)
amean = (hs * ans_mask[..., None, None]).sum(1) / ans_len[:, None, None]  # (B, R, H) on-GPU reduce
store = cat([sel, amean, ans_last]).to(torch.float16).cpu()           # (B, 5, R, H)
```

### 4.5 Auxiliary unit sets (all generated + captured in the same G phases)

- **Grafted-query marginal-eval set** (the registered resolution of the body's open design question): for turn positions k ∈ {2, 4}, 150 main-panel TEST conversations; per prefix, Q = 4 grafted queries sampled (seed 0) from OTHER test conversations' turn-k user messages; generate + capture each. The empirical marginal target is ȳ(prefix) = mean answer_mean over {1 realized + 4 grafted} answers. **Design rationale:** the prefix→answer map needs NO multi-query data to FIT — under squared loss, ridge on (prefix-state, realized-answer) pairs estimates E[answer profile | prefix] with the query integrated out by the loss. Multiple queries per prefix are needed only to EVALUATE against a per-prefix averaged target and to decompose residual variance into irreducible query variance vs map error. Candidate construction (i) from the task body (same-turn-position query grafting) is chosen: tier-1 realized queries, cheap, deterministic; candidate (ii) on-policy query generation rejected (tier-3 synthetic, changes the query distribution); candidate (iii) similar-prefix pooling rejected (no defensible prefix-similarity metric). Named caveat: grafting samples q ~ p(q at turn k) unconditionally, not p(q | prefix) — some grafts are incoherent with the host prefix; the read is "prefix-conditioned response to a generic turn-k query" (§12).
- **Prefix-provenance control**: 200 main-panel TEST conversations at k = 2; prefix′ = (user 1, Qwen's own answer 1 — already generated as the unit (c,1) rollout); generate answer 2′ under prefix′ + query 2; capture. Evaluate the LMSYS-prefix-trained context map on these units; the skill drop bounds prefix-provenance sensitivity. (Bundles prefix-text change + query-2 coherence break; labeled a bounding read.)

### 4.6 Map fitting (new thin driver: `scripts/issue958_fit_maps.py`; math reused from `maps922.py` / `issue658_fit_predictors._ridge_dual_weights`)

All maps are per-row closed-form affine ridge, λ by GCV over `RIDGE_LAMBDAS_922 = logspace(-2, 3, 25)`, X standardized / Y centered on train-fold stats (#922 conventions). With N_fit ≤ 4,000 < d = 3,584-ish the **dual/Gram-space** path is used (one `eigh` of the N×N Gram per (fit-cell, row), GCV as eigenvalue arithmetic across the λ grid — `maps922.ridge_gcv_from_grams` recipe), batched across the 29 rows (`torch.linalg.eigh` on stacked Grams). Device: `EPM_FIT_DEVICE` / call-time parameter (post-#763/#812 fix, verified present).

Fit cells (each × 29 rows):

| Family | Cells | N_fit | Purpose |
|---|---|---|---|
| Context maps, half-sample twins M_ctx^{k,A/B} | k=1..4 × 2 halves = 8 | 2,000 | stability analysis at matched N (all Δ/twin reads) |
| Context maps, full M_ctx^k | k=1..4 = 4 | 4,000 | best-estimate curves; forecast comparisons |
| Prefix maps M_pre^{k} (full + halves) | k=2..4 × 3 = 9 | 4,000 / 2,000 | question (c); grafted-query eval |
| Cross-horizon forecasts F_ctx^{j→k}, j<k≤4 | 6 | 4,000 | question (b) |
| Long-panel own maps k=5..8 + matched-N turn-1 twin | 5 | 480 | exploratory depth extension (N-matched internally) |

Total ≈ 32 fit-cells × 29 rows = **928 Gram/eigh ridge problems** (arithmetic + batching in §9). Transfer evaluations (apply M_j at turn-k inputs) are pure matrix multiplies — no refits.

Pseudocode (fit + transfer core):

```python
for cell in FIT_CELLS:                       # 32 cells
    X = store[cell.src_pos, cell.units]      # (N, 29, 3584) fp16 -> fp64 per-row
    Y = store[ANS_MEAN, cell.tgt_units]
    G = batched_gram(X_std, Y_c)             # (29, N, N) fp64, one pass
    s, V = torch.linalg.eigh(G)              # batched over 29 rows
    W[cell] = gcv_select(s, V, RIDGE_LAMBDAS_922)   # (29, 3584+1, 3584)
for (src_map, tgt_cell) in TRANSFER_GRID:    # incl. j->k, stale-at-k, long-panel
    pred = apply(W[src_map], X_test[tgt_cell])      # GEMM
    skill[src_map, tgt_cell, :] = 1 - sse(pred, Y_test) / sse(mean_train[tgt_cell], Y_test)  # per row
```

### Kill criteria

Concrete abort / halt-and-report conditions (these operationalize the §8 risk rows and §9 descope minimums; no new scope):

- **Corpus-yield kill:** the build-time streaming count (run BEFORE any GPU provision) yields < 4,000 main-panel conversations or < 400 test conversations after the §9 descope ladder is exhausted → halt-and-report; the design needs a re-plan (different corpus or smaller K), not a silently thinner panel.
- **Smoke kill (map-skill floor):** the `--smoke` run's turn-1 context-map skill at the frozen 6-block mean is ≤ 0 on the new multi-turn corpus, or the batched-vs-batch-1 capture equivalence gate fails → halt-and-report as a pipeline bug (template/boundary/pairing); no full GPU launch until fixed.
- **Capture/rollout-yield kill:** unit dropout (failed/empty rollouts or capture errors after resume-retry) breaks the complete k = 1..4 chain for > 10% of main-panel conversations → halt-and-report (the paired same-conversations-at-every-turn design is no longer intact); do not proceed to fits on a silently broken pairing.
- **Storage-overrun kill:** the in-run one-shard serialization+upload timing projects the full store upload at > 4× the §9 0.5 h budget, or the realized store size projects > 60 GB (vs ~27 GB planned) → halt uploads, keep shards pod-side, and report before continuing (never silently discard; never delete unuploaded artifacts).

## 11. Decision Rationale

- **Model = `Qwen/Qwen2.5-7B-Instruct`, frozen, fp16 capture.** Why: the line's fixed model; the mapping under study is this model's. Source: #779/#922. Alternatives: none (single-variable discipline). Model id is repo-standard — no AutoConfig smoke needed.
- **Ridge λ grid = GCV over logspace(−2,3,25).** Why: the line's validated selection at exactly this X/Y shape. Source: #922 (`RIDGE_LAMBDAS_922`). Alternatives: fixed λ (rejected — GCV is free in the eigenbasis).
- **Dual/Gram-space fit path.** Why: N ≤ 4,000 < d = 3,584 side-steps the d×d factorization; #779's ablation round validated the dual path (batched-vs-serial equivalence ≤ 7e-8). Source: #779 amendment / `_ridge_dual_weights`. Alternatives: primal eigh (slower at this shape).
- **Capture rows = 29 (embedding + 28 blocks); fp16; 500-unit shards; batch 16.** Source: #922 capture script defaults. Alternatives: read-out-blocks-only capture (rejected — per-row curves are a registered diagnostic and the cost delta is small).
- **Split = by conversation, 4,000/500/500, seed 42.** Why: group-level discipline (#810) at the line's exact sizes. Source: #922 (`SPLIT_SEED`, `N_FIT/N_VAL/N_TEST`). Alternatives: pointwise splits (banned, #810).
- **N_conv = 5,000 main / 600 long; K = 4 / 8.** Why: 5,000 matches the line's corpus size where R² ≈ 0.60 was established and #779's learning curve was still rising at 5,000 — smaller panels would confound "later-turn maps are weaker" with underfitting; K = 4 is the largest turn count with a plausibly deep LMSYS pool at 5,000 conversations; the 600-conversation ≥8-turn panel extends depth where the pool thins. Source: #779/#922 (the 5,000 figure); the ≥4-turn yield itself is `ungrounded — needs smoke-test` (build-time count assert; §12). Alternatives: 10,000 convs (pool + GPU cost, no grounding that the line needs it).
- **Rollout sampling = temp 1.0, top_p 0.95, max_tokens 1024, seed 42, n = 1.** Why: the answers ARE the mapping's target distribution; changing decode params would be a second manipulated variable. Source: #779 (`issue779_collect.py:558`). Alternatives: greedy (rejected — breaks single-variable inheritance; #779's 0.60 R² is under temp-1.0 targets).
- **Read-out aggregation = mean over frozen blocks {14,17,19,20,24,26}; trait layers evil 20 / syc 26 / halluc 17.** Why: pre-registered fixed positions kill the winner's-curse selection problem. Source: #922 (`READOUT_BLOCKS`, `PRIMARY_LSTAR`). Alternatives: max-over-row headline (requires the full selection-symmetric machinery; kept exploratory-only).
- **Twin noise floor at matched N_fit = 2,000.** Why: "M_1 ≠ M_k" is only meaningful relative to how much two independent fits of the SAME mapping differ; half-sample twins give that floor at exactly the N every stability comparison uses. Source: standard split-half logic; the matched-N requirement is the equalize-down rule (#601 dose-confound analog). Alternatives: bootstrap-refit floor (heavier, adds fit count without changing the read).
- **Bootstrap 997 draws seed 0; shuffle band 100 draws; random-direction band 100 draws.** Source: #922 (bootstrap); #922 shuffled-context band (100); #778 null battery (norm-matched random directions). Batteries are batched reductions sized 100 draws × 40 eval cells × 29 rows (shuffle band) and 997 draws × 20 statistics (bootstrap) — arithmetic + implementation in §6/§9.
- **Token cap 7,168 input / 1,024 new.** Why: bounds capture memory and wall; `max_new_tokens` is the project free-generation default and equals #779's rollout cap. Source: CLAUDE.md default + #779. Alternatives: 32k contexts (cost blows up; the ≥8-turn panel already probes length).
- **Moderation-flagged conversations dropped.** Why: refusal-dominated targets add a mode the mapping question doesn't need, and flagged content stays out of context windows and logs. Source: `ungrounded — needs smoke-test` (deliberate hygiene choice; realized drop-rate reported; carried as a realism caveat). Alternatives: keep-all (revisit in a follow-up if the drop rate exceeds ~15%).
- **Reused input-data artifacts:** #778 `r_B` (Source: #778; fetched on the CPU lane via per-file `hf_hub_download` from the data repo — verified paths §10); LMSYS via `load_dataset` + HF_TOKEN on the GCP lane (gated=auto; §12).
