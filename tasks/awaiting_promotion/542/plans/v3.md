## §0.0 TL;DR (plain English)

- **What I'll run:** The finished #542 experiment asked whether the *kind* of counter-examples you train against changes where a marker leaks, and found no effect. But its "close" counter-examples turned out to be barely closer than the far-away ones (about 1%), so the test was too weak to trust. This round builds genuinely close counter-examples: tiny surface edits of the source persona, so they sit right next to it. It checks they really are close before spending any GPU, and trains a bit longer so the counter-examples actually get to act. Then I ask whether personas that sit near a counter-example get extra protection from the leak, beyond what their distance to the source already explains.
- **What I expect:** Honestly split. The project's working read is "identity, not proximity": where leakage lands is set by the base model's own geometry, not by which counter-examples you picked. If that holds, even tight near-twins won't add protection. But #542 left a real loose end (the manipulation barely moved, and its one cell that trained to completion *did* respond to counter-examples), so this is the clean test that could overturn it.
- **What would change my mind:** If personas sitting near a near-twin counter-example get measurably more leak-suppression than their distance to the source predicts. That would mean tight similarity to a counter-example does localize the leak, flipping #542's null.

### 4.2 The TWO pre-data gates (non-negotiable; ABORT-and-REPORT on failure)

**Gate 1 — Manipulation check (extends the existing `_closeness_step`).** Before any training run counts, compute mean cosine-distance from each panel member's centroid to the source/eval-target context centroids at the registered layer (L22, the v1 closeness layer + the dist_to_panel layer), reusing the existing reduced-cloud extraction (`_clouds_step`) for the 4 new near-twins and the staged parent clouds for the cross-family members. The v1 `_closeness_step` only asserted `arm2_close < arm1_xfam` (a weak "<" that the 1%-thin manipulation passed). This round REPLACES that with a HARD MARGIN:
```python
# _closeness_step (this round): gate on a SUBSTANTIAL margin, not "<".
nt_mean   = panel_mean_cos_dist("nt_close",  anchors=train_ctx_centroids)
xfam_mean = panel_mean_cos_dist("xfam_long", anchors=train_ctx_centroids)
ratio = nt_mean / xfam_mean
PASS = ratio <= 0.5                       # near-twins must be <= half the distant panel's mean distance
payload = {"nt_mean": nt_mean, "xfam_mean": xfam_mean, "ratio": ratio,
           "threshold": 0.5, "pass": bool(PASS),
           "per_member": {...}}            # full per-member distances both panels
write("manipulation_check.json", payload)
if not PASS:
    raise SystemExit("MANIPULATION GATE FAILED: near-twin panel not >=2x closer than "
                     f"distant (ratio={ratio:.3f} > 0.5). ABORT — report the failed "
                     "manipulation; do NOT recipe-descope (the #542 lesson).")
```
Output: `eval_results/issue_542/genuine-near-twin-negatives/p0/manipulation_check.json` (the realized per-panel means + per-member distances + the PASS/FAIL ratio). A FAIL ABORTS the run and is REPORTED as the failed-manipulation finding — the deliberate fallback, NOT a descope. (If a single near-twin member is the offender — e.g. one perturbation didn't take — exactly one regeneration of THAT member via `--regen-nt-twins --only <cid>` is allowed before the gate re-runs; this is a construction fix, not a threshold relaxation.)

**Gate 2 — Non-saturated anchor.** Train at a budget where on-policy `log P(※)` source gain sits ~5-10 nats below the per-cell ceiling (per marker-leakage-measurement.md / marker-training-recipe.md usable window). ### Install-strength control (cross-condition leakage comparison)

The headline compares LEAKAGE across two training conditions (near-twin vs distant), so raw bystander leakage is dose-confoundable. Registered install-controlled reads: (a) **matched-install comparison** — both arms train to the SAME fixed 1-epoch budget (matched schedule), and the source-install diagonal means are reported per arm so any install gap is visible and the comparison is read at matched dose; (b) **per-cell transfer fraction** — bystander gain ÷ source gain per (source → bystander) cell, computed in the **non-saturating EOS-margin logit space `Δ(z_marker − z_eos)`, NEVER raw `log P`** (softmax compression would inflate the fraction at a saturated source); (c) **dose curves** — leakage vs install across the per-step trajectories logged in WandB (both arms checkpoint at the 5-step cadence), the preferred read that catches nonlinear leakage onset. The transfer fraction is NEVER correlated back against install itself (the shared-denominator artifact). The primary DV definition is unchanged (on-policy `log P(※)` trained − base stays primary).

### Statistical-input existence

The partial correlation consumes: per-cell G (present in the new arm tensors, built by the eval phase); per-held-out-bystander distance-to-nearest-near-twin-negative + distance-to-source (built by the reads script from the reduced clouds + the `dist_to_panel` predictor rows — scheduled in §4.3 item 6, NOT a phantom dependency); the noise floor (the seed-43 near-twin replicate tensors, built this round — §5).
