## 0.0 TL;DR (plain English)

- **What I'll run:** last round found the model's reasoning text predicts the answer's state no better than an equal-length slice of the answer's own opening (the −0.052 demotion). But every input in that comparison included the user's question. I'll re-run the same comparison with the question removed from the prompt-side input — predicting from only the persona/system text that comes before the question — using the same rollouts, folds, and fitting machinery, so we know whether the demotion depends on how the prompt side was summarized.
- **What I expect:** the demotion survives (both compared arms carry their conditioning slice identically, so removing the question shouldn't flip which slice wins), while the absolute prediction numbers drop a lot (the question likely carries most of the per-question signal), and the reasoning text partially fills in for the missing question.
- **What would change my mind:** if the reasoning slice beats the answer-opening slice once the question is gone (a sign flip with a confidence interval excluding zero), the demotion is specific to question-included inputs and the headline gains a real caveat. If the question-free input predicts almost as well as the full one, the "question carries the signal" reading dies instead.

### 4.1 Prefix/query span computation (code, not a model call — exact, deterministic)

**Source-module extension (the v6 `parts_spec` pattern, second application):** add a DEFAULT-PRESERVING `prompt_parts_spec` parameter to `build_capture_row` (`scripts/issue928_extract_thinking_store.py`): `None` ⇒ existing behavior byte-for-byte; else a callable `(prompt_text_tpl, prompt_offsets, prompt_len_tpl) -> dict[str, (s, e)] | str` receiving the templated prompt text, its `return_offsets_mapping` (computed only on the non-None branch), and the templated prompt token length; a dict return adds each prompt-side span to `row["spans"]` asserted `0 ≤ s < e ≤ prompt_len_tpl` (absolute positions = the same indices, since prompt tokens start at 0); a str return drops the row with that counted reason. `reduce_forward_batch` needs NO change — it already reduces any part named in `row["spans"]` (verified this session).

Driver-side adapter (new pure function in `scripts/issue928_common.py`, unit-tested):

```python
def prefix_query_spans(prompt_text_tpl, prompt_offsets, prompt_len_tpl, probe):
    """prefix = all templated-prompt tokens strictly before the FINAL user
    turn's probe content (system block + prefix_messages + chat scaffolding
    incl. the <|im_start|>user\\n header); query = the probe's own tokens.
    rfind = last occurrence (the probe is the final user turn by construction
    — issue594_common.messages_for_instance)."""
    q_char = prompt_text_tpl.rfind(probe)
    if q_char < 0:
        raise RuntimeError("probe not found verbatim in templated prompt")  # kill criterion
    q_tok = char_span_to_token_span(prompt_offsets, (q_char, q_char + len(probe)))
    if q_tok == (0, 0):
        return "empty_query_token_span"     # dropped-and-counted
    if q_tok[0] == 0:
        return "empty_prefix_token_span"    # dropped-and-counted (measured: cannot fire — min prefix 24 tokens)
    return {"prefix": (0, q_tok[0]), "query": q_tok}
```

Boundary conventions (stated): the user-turn header belongs to the PREFIX ("everything before the user query"); a BPE token straddling the header/probe boundary joins the QUERY span (overlap-based mapping) — the partition is well-defined either way and the straddle affects ≤ 1 token. The post-query assistant-header scaffolding belongs to neither part (so `ctx ≠ prefix ∪ query` exactly; `ctx` additionally holds `<|im_end|>\n<|im_start|>assistant\n`). Named near-degenerate cells: `f6_default_template` (prefix = 24 tokens of pure chat-template default — NO context-distinguishing content) and `f6_helpful_asst` (28-char generic system prompt) are kept, flagged in figures, and carried as a scope note.
