<section class="plan-tldr">
<h2 style="margin-top:0">§0.0 TL;DR (plain English)</h2>

<p><strong>What I'll run:</strong> Last time I showed that swapping the un-finetuned model's representations into a short span of the chat template stopped the trained adapters from leaking their behavior into the wrong place. But I only ever checked the wrong-place behavior — so I can't tell whether the fix is surgical (kills only the leaked stuff) or just a blunt "make it act more like the base model again" that also erases the thing the adapter was actually trained to do. This run re-uses the exact same fix on the exact same adapters, but this time I measure each adapter on its <em>own</em> trained behavior to see if the fix dents that too.</p>

<p><strong>What I expect:</strong> On the two strongly-trained reckless adapters, I expect the fix to leave the on-target behavior mostly intact while still clearing the leakage — i.e. a real selective fix. I'm genuinely unsure though; the honest prior is that the patch is at least partly a generic revert, so I would not be shocked to see the on-target behavior drop about as much as the leakage did.</p>

<p><strong>What would change my mind:</strong> If the on-target behavior drops by roughly the same amount as the leakage did across the board, the fix is blunt, not surgical, and I'll soften the "model-specific intervention" framing in the existing write-up. If on-target stays put while leakage clears, it's a usable selective defense and the write-up gets stronger.</p>
</section>

<h2>§1 Goal</h2>

<p>v3 (the prior #640 run) established that base-postfix-KV patching cuts <em>off-diagonal</em> leakage on the strongly-installed cells (risky_financial Δleakage ≈ 0.69/0.66; extreme_sports ≈ 0.56/0.63 across seeds 0/137). That result carries a binding caveat on #640's MODERATE confidence: it was measured ONLY on leakage cells, so it cannot distinguish a <em>selective</em> intervention (clears the leaked behavior, preserves the on-target trained behavior) from a <em>blunt</em> revert-toward-base (dampens both equally). This amendment settles that caveat by re-running the identical patch on the identical adapters but measuring each adapter on its <strong>own diagonal column</strong> — the behavior it was trained to express, read on-target. The distinction is decided by pairing the new diagonal Δsource against v3's off-diagonal Δleakage per row: a large selectivity gap (Δleakage ≫ Δsource) on the strong cells = selective; Δsource ≈ Δleakage = blunt revert.</p>

<h2>§3 Hypothesis</h2>

<p><strong>H-selective (the patch is a selective leakage fix):</strong> On the strongly-installed rows (risky_financial, extreme_sports, and the other high-diagonal-level rows), postfix patching leaves on-target behavior largely intact — Δsource ≈ 0, or Δsource ≪ Δleakage — while v3's Δleakage stays large (0.56–0.69 on the two reckless cells). The selectivity gap (Δleakage − Δsource) is large and positive.</p>

<p><strong>H-blunt (the patch is a generic revert-toward-base):</strong> Postfix patching reduces on-target diagonal behavior comparably to the off-diagonal leakage it cut — Δsource ≈ Δleakage across rows. The selectivity gap is ≈ 0.</p>

<p><strong>Falsification rule (decides selective vs blunt):</strong> Restrict the test to the rows with measurable on-target dynamic range — the judged-rate diagonal rows with trained diagonal_level ≥ ~0.5 (bad_medical, risky_financial, extreme_sports, taught_fact, compliment_writing, wrong_claim_agreement; <code>reversed_fact</code> is a floor cell and <code>marker</code> is log-prob-scale — both excluded from the headline count, see §4). For each such row compute the per-seed selectivity gap = Δleakage(v3) − Δsource(this run).</p>
<ul>
<li><strong>Declare SELECTIVE</strong> if, on the two strongly-installed reckless cells (risky_financial, extreme_sports), the selectivity gap is large and positive at seed-0 (Δsource ≤ ~½ Δleakage, i.e. gap ≥ ~½ Δleakage) AND the sign of Δsource ≪ Δleakage is consistent across both seeds (the per-row ordering Δleakage > Δsource holds at seed-0 and seed-137).</li>
<li><strong>Declare BLUNT-REVERT</strong> if Δsource ≈ Δleakage on those cells (selectivity gap within judge noise of 0, |gap| ≲ ~0.1 at the n=32 probe cap) with consistent sign across seeds.</li>
<li><strong>Mixed / underpowered</strong> otherwise (gaps inconsistent across seeds, or all on a floor cell) — reported as such, no overclaim. No pre-registered confirmation conjunction beyond the two-cell selectivity read above.</li>
</ul>

<h3>4.2 Driver change (the only code edit on the GPU path)</h3>

<p>The v3 driver's <code>run_phase2_postfix_patch</code> already does everything else (adapter download, gauge-band assert, rsLoRA parity probe, backend-parity HALT, both arms via <code>generate_patched(..., "none")</code> and <code>generate_patched(..., "postfix")</code>, per-cell Δ write, checkpoint-per-seed, raw-completion persist, sentinel). The driver edit has <strong>three coupled parts</strong>, all gated behind a single new <code>--target {leakage,diagonal}</code> flag (default <code>leakage</code> = the v3 behavior, so v3 is byte-for-byte reproducible). It is NOT a one-line swap — the marker exclusion below is part of the same change:</p>

<p><strong>(1) Column map.</strong> Under <code>--target diagonal</code>, resolve the target column per row from <code>_diagonal_target_columns()</code> (the diagonal map) instead of <code>_phase2_target_columns()</code> (the off-diagonal leakage map).</p>

<p><strong>(2) Marker row EXCLUDED from the Phase-2 judged loop.</strong> <code>_diagonal_target_columns()</code> returns a map for the <strong>7 judged-rate rows ONLY</strong> — <code>bad_medical</code>, <code>risky_financial</code>, <code>extreme_sports</code>, <code>taught_fact</code>, <code>reversed_fact</code>, <code>compliment_writing</code>, <code>wrong_claim_agreement</code>. The <code>marker</code> row is NOT in the map and is NOT handed to the Phase-2 generation/judge loop. Reason: <code>COLUMNS["marker"].dv == "marker_slot_stats"</code> with <code>judge is None</code>, so passing <code>marker → marker</code> to the existing <code>_judge_completions</code> path would crash (no judge) or produce nonsense (a log-prob DV scored as a judged rate). The marker diagonal reference is NOT recomputed on the pod at all — it is pulled directly from #545's stored <code>cell_metadata.json</code> marker <code>diagonal_level</code> for the §6 parity / null-reference reporting (see §4.3). This is zero new GPU code, the value is already on disk, and the headline does not depend on it.</p>

<p><strong>(3) Output filename switch.</strong> Under <code>--target diagonal</code> the driver writes to <code>eval_results/issue_640/diagonal_source_seed{seed}.json</code>; under <code>--target leakage</code> (default) it writes the v3 path <code>patch_cells_postfix_seed{seed}.json</code>. The <code>--target</code> flag switches BOTH the column map AND the output filename in one place, so the diagonal run can never overwrite v3's committed off-diagonal cells (a must-keep, §12). The output filename is otherwise hard-coded in the driver, so an <code>EPM_OUTPUT_ROOT</code>-style directory-only override would NOT change the filename and would fail the §6.5 primary-deliverable glob — the filename-switching <code>--target</code> path is the locked-in mechanism (the <code>EPM_OUTPUT_ROOT</code> alternative is dropped).</p>

<h3>4.3 Marker row special handling</h3>

<p>The marker diagonal column (<code>marker</code>, dv = <code>marker_slot_stats</code>) is a <strong>log-prob-scale</strong> DV (teacher-forced <code>log P(※)</code> at the post-response slot), NOT a judged emission rate (CLAUDE.md "Marker-leakage experiments"). It is therefore <strong>excluded from the Phase-2 judged generation loop entirely</strong> (§4.2 part 2): <code>COLUMNS["marker"].judge is None</code>, so it cannot go through <code>_judge_completions</code>. For this selectivity analysis the marker row is carried as a <strong>null/parity reference only</strong>, and its reference value is NOT recomputed on the pod — it is read directly from #545's stored <code>eval_results/issue_545/cell_metadata.json</code> marker <code>diagonal_level</code> (5.77 / 9.45 nats, seed0 / seed137) by the off-pod scoring script for §6 reporting. Do NOT compute a Δsource judged rate for it and do NOT include it in the selective-vs-blunt headline count. It functions as the same sanity reference it served in v3 (an already-installed log-prob behavior at the post-response slot, reported for completeness, not a Δsource cell).</p>

<h3>Required: install-strength control</h3>
<p>Δsource is already install-normalized — it is the change FROM each adapter's own trained diagonal rate (the no-patch arm is measured inline per cell), so a row with weaker install has a correspondingly smaller Δsource denominator. The headline is a WITHIN-adapter column contrast (same adapter, same patch, diagonal vs off-diagonal), not a cross-condition install comparison, so the dose-confound that the install-strength rule targets does not apply. The selectivity gap is read per row, never pooled across rows of differing install.</p>
