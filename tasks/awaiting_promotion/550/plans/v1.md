### Divergences from parent issue #538

1. **Band-stop window [14, 20] → [9, 13] nat** — THE experimental variable (the Goal).
2. **Epochs cap 24 → 16** — instrumental fail-safe only (the band-stop is the real stop; expected stop step ~45–70 sits between #527's 30–40 and #538's 60–90; cap 16 = 800 steps singleton / 1600 joint, >10× headroom over the expected stop — the same headroom ratio both parents used). Proposed in the task body.
3. **Band-check cadence `marker_band_eval_every_steps` 10 → 5** — instrumental measurement-cadence change, NOT a recipe change. The stop predicate (`callbacks.py::_decide_band_stop`) fires only when a check sees `low ≤ delta ≤ high`; checks run every `eval_every_steps`. #538's landings imply inter-check jumps of up to >5.3 nat per 10 steps in the 14–19 nat region (a cell below 14 at one check landed at 19.37 at the next), and ~3.4 nat/10 steps on average in the 7.5→14.3 region this run stops in. The [9, 13] band is only 4 nat wide — at cadence 10 a cell can jump from 8.9 past 13 and never fire (it would then train to the epochs cap and saturate). Halving the cadence halves the expected per-check jump to ~1.2–2.7 nat, comfortably inside the band width. Effect: #550 cells land nearer the band's LOW edge (≈9–11 nat) — which INCREASES dial separation from #538; the dial axis reads realized landings, so cadence does not contaminate the comparison. Cost: ~2× probe forward passes (32-row probe, ~1–2 s/check) — negligible.
4. **WandB telemetry fix** — export `WANDB_PROJECT=issue_550_dial_midpoint` in the pipeline driver + per-cell `wandb.finish()` in the dispatcher loop after each cell, so each cell gets its own run (both parents lost per-cell trajectories to the reused-handle/fallback-project defect; live WandB training metrics are mandatory per code-style). Telemetry-only; the band-fire disk recorder (`marker_band_stop_result.json` per cell) remains the canonical record either way.
