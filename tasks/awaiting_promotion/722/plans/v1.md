## 0.0 TL;DR (plain English)

- **What I'll run:** I take models that were already taught a quirk (a tic, a fact, a style, a habit of agreeing) while playing a character, and I learn a little function that reads the model's "what character am I in" signal and predicts "how will I answer." I learn that function twice — once from the untouched model, once from the taught model — and ask whether the *function itself* changed, or whether only the *signal it reads* moved. I do this two ways (a simple linear fit and a flexible curve-fit), and I check the change only along the directions that actually matter for the behavior, not the whole 3584-number activation (which an earlier run showed is hopeless to compare because everything reconstructs near-perfectly and tells you nothing).
- **What I expect:** For the marker tic and the taught fact I expect the function to barely change — teaching those mostly slid the input signal around. For the messier behaviors (agreeing with wrong claims, harmful compliance / EM) I genuinely don't know, and that uncertainty is the interesting part.
- **What would change my mind:** If the function's change along the behavior-relevant directions sits well above the noise floor for a behavior, then teaching reshaped *how* the model acts on its self-picture, not just the picture. A flat result (change indistinguishable from a refit-noise floor) means the input moved and the function held.

## 1. Goal

(Verbatim, frontmatter.) On #537's already-trained behavior×context LoRA adapters, fit the context→answer-profile mapping M: c_C → v0(C) both pre-finetuning (M0, base) and post-finetuning (M⁺, adapter-applied) as a linear ridge AND a nonlinear MLP, and determine whether the FUNCTION M changes (distinct from the input context vector c_C shifting) via (1) function-change at fixed input ‖M⁺(c)−M0(c)‖ on a common c grid projected onto behavior read-outs r_B, (2) behavior-relevant transfer through the chain r_Bᵀ M c → E (judge rate) and M along r_B — NOT generic v0 reconstruction (which #658 showed saturates ≈0.98 and is uninformative), and (3) cross-transfer of M0 vs M⁺ on FT data; cross-referenced against #697's causal f_CV.

This is the **descriptive/parametric** half of a two-part question; #697 is the **causal** half. The leakage theory (Overleaf `6a2df2d2`) models behavior installation as either moving the input context vector c_C into the map M, or changing M itself. This task fits M0 and M⁺ explicitly and measures whether the FUNCTION moved.

## 3. Hypothesis

Per behavior B, finetuning B into a context either:

- **H_input:** moved the input context vector c_C, with M intact → `‖M⁺(c)−M0(c)‖_{r_B} ≈ noise floor`; chain-ρ(M0) ≈ chain-ρ(M⁺).
- **H_function:** changed the map M, with c_C effectively intact → `‖M⁺(c)−M0(c)‖_{r_B}` well above the refit noise floor; chain-ρ(M⁺) ≠ chain-ρ(M0).
- **H_mixed:** both move (the CI straddles the floor, or chain-ρ shifts modestly).

**Quantitative falsification (per behavior × layer):**

- **H_function "supported"** iff the family-clustered-bootstrap 95% CI of `‖M⁺(c)−M0(c)‖_{onto r_B}` lies **entirely above** the refit noise floor, where the floor = the 95th percentile of `‖M0_refit_a(c)−M0_refit_b(c)‖_{onto r_B}` over bootstrap-over-cells + random-init refit pairs of M0 (two independent refits of the SAME base map). Δ is reported in floor-SD units (Δ / floor_SD).
- **H_input "supported"** iff that CI lies **entirely at or below** the floor (≤ 1 floor-SD).
- **H_mixed** iff the CI straddles the floor.
- **Concordance check (co-primary):** chain-ρ(M⁺) − chain-ρ(M0) under LOCO; a behavior is only called H_function with confidence if BOTH the r_B-Δ and the chain-ρ shift agree in direction. A behavior whose chain-ρ(M0) already saturates near 1.0 is down-ranked to a sanity check (it has no headroom to register a function change), mirroring #658's v0-recon-saturation guard.

Pre-registered weak prediction: marker + taught-fact lean H_input (slot-localized, context-invariant per #651); em + sycophancy genuinely uncertain — matching #697's pre-registration so the two answers are directly comparable.

## 4. Design

All new code lives under `scripts/issue722_*`. The fit/chain/noise primitives are IMPORTED from `scripts/issue658_fit_predictors.py` (reuse, not reimplementation): `_ridge_predict_loco`, `_fit_mlp_ensemble_loco`, `_chain_rho`-style projection, `_cluster_bootstrap_rho`, `_rho`, `RIDGE_LAMBDAS`, `A35_MLP_TARGET_DIM`, `MLP_*`. r_B contrast extraction reuses `scripts/issue658_extract_base_store.py:build_rb_contrast` + `capture_mean_answer_acts`.

**Data source + realism tier:** the activations are derived from #537's frozen #537 eval-probe pools (tier-2 established panels: Betley main-8, AdvBench, #411 wrong-claims, SORRY-Bench/XSTest, #444 fact recall). No new generation of training data; this is a measurement on existing real-probe-derived activations. **N/A — not a behavior-implantation experiment** (no training rows constructed; contrastive-negatives / on-policy-completions rules do not apply — the implants already exist in #537's adapters).

**Why code, not a model call?** The fits and projections are numerical operations on activation tensors (ridge/MLP regression, dot products), not classification of unstructured data — code is the only formulation. The r_B *extraction* uses model forwards (teacher-forced answer-span pooling, `capture_mean_answer_acts`), which is the validated #658 path, not a judge call. The chain-ρ target E is read from #537's already-judged `G_meta.json` (no new judging).

### 4.1 Activation-load utility — `scripts/issue722_load_activations.py` (NEW)

- Streams `superkaiba1/explore-persona-space-data` → `issue667_gate_chain_preview/analysis_tensors/` via `huggingface_hub` (the #658 `_HfStreamSpanSource` pattern; never materialize all 5828 at once — load per behavior into CPU RAM, ~few GB).
- Per `.npz` returns, keyed by `(behavior, source_cid, target_cid, seed, layer)`:
  - `c0 = c_C` (base context vector), `cplus = c_C_postft` (post-FT context vector),
  - `v0 = v0` (base answer-profile), `vplus = v_plus` (post-FT answer-profile).
- Groups by behavior and by `target_cid`-family (the 7 families from #667 metadata) for clustered bootstrap. Provides a `common_c_grid(behavior)` = the union of base context vectors `c_C` over the matched cells of that behavior (the fixed-input grid for read (1)).
- **Exact pairing contract (asserted at load):** M0 is fit from `(c0 → v0)`; M⁺ is fit from `(cplus → vplus)` — the post-FT input drives the post-FT output. Read (1) then evaluates BOTH fitted maps on the SAME `common_c_grid` (base c). Shapes asserted `(28,3584)` per tensor; layer index selected from {7,14,21} → row index in the 28-layer stack.

### 4.2 Behavior read-out r_B loader (reuse) + 4.3 taught-fact extraction (NEW)

- **Loader** pulls `r_b.pt` from HF `issue658_theory_assumptions/store/r_b.pt`. Name map: #537 `em`→`broad_em`; #537 `sycophancy`→`sycophancy`; #537 `refusal`→`harmful_compliance` (only if refusal is included). **Recipe pick: `diffmeans` PRIMARY** (`Source: #658 DEFAULT_RB`, theory A3.3 persona-vectors diff-in-means); `meanDB` run as a recipe-robustness sanity panel on ONE behavior only (§7 risk).
- **Taught-fact r_B extraction** — `scripts/issue722_extract_fact_rb.py` (NEW). `fact_expression` has `rb_contrast=None` in #658 (no natural base-model diff-in-means), so the task explicitly requires re-extracting it. **Contrast definition (the single new design choice):** `D_B` = the #537/#444 fact-recall probes answered WITH the taught fact present (fact-stated), `D_B̄` = the SAME probes answered under the neutral Betley pool (fact-absent) — i.e. the diff-in-means between "fact stated" and "fact not stated" answer-span activations, computed with the IDENTICAL `capture_mean_answer_acts` recipe + `diffmeans` formula + layer set as #658's other columns (no recipe-mismatch confound). Saved to HF `issue722_rb_extension/store/r_b_fact.pt` (parallel namespace; **does NOT overwrite** #658's `r_b.pt`), shape `(28,3584)`, recipes `diffmeans` (+ `meanDB` for the robustness panel). **Marker is dropped from the headline** (no diff-in-means contrast exists, and its E saturates — see §5/§7): if the analyzer wants a marker supplement, `r_b_marker.pt` would be extracted the same way, but the headline runs on **em + sycophancy + taught-fact**.

### 4.4 Fit harness — `scripts/issue722_fit_M.py` (NEW)

For each `(adapter/behavior-cell, layer ∈ {7,14,21})`:

- Fit **M0** via `_ridge_predict_loco(C0[:,li,:], V0[:,li,:], RIDGE_LAMBDAS)` (ridge) and `_fit_mlp_ensemble_loco(C0, V0, target_idx=range(64))` (MLP).
- Fit **M⁺** via the same calls on `(Cplus[:,li,:], Vplus[:,li,:])`.
- LOCO over contexts (held-out per context, never train ρ); family-clustered bootstrap over the 7 `target_cid` families (`_cluster_bootstrap_rho`).
- Output target dim = 64 leading top-PCA-of-v0 dims (`A35_MLP_TARGET_DIM`), shared between ridge and MLP for a like-for-like nonlinearity gap.
- Checkpoint per `(behavior, layer)` cell to `eval_results/issue_722/cells/` (the #658 `_save_cell` pattern) so the run resumes.

**Unit of fit — pre-registered pooling axis.** PRIMARY = **per-behavior pool across that behavior's contexts** (n ≈ 16 source contexts per behavior; seed=1 so there is no seed dimension to pool over). #658 fit per-recipe over the full `ctx_ids` set (a single pooled fit, not per-adapter) — this task INHERITS that pooling decision. n=16 against a 64-dim output is tight; the LOCO held-out ρ + the shuffle null are the overfit guards #658 validated at the same n. FALLBACK if MLP LOCO ρ is unstable (held-out ρ < shuffle null on M0): report ridge-only for that behavior and flag the MLP as underpowered (§7).

### 4.5 Reads / analysis — `scripts/issue722_analyze.py` (NEW)

From each fitted `(M0, M⁺)` pair:

1. **Function-change at fixed input (HEADLINE).** On `common_c_grid(behavior)`, compute `Δ(c) = M⁺(c) − M0(c)` for both ridge and MLP. Report `‖Δ(c)‖` full-dim AND **projected onto r_B**: `Δ·r_B/‖r_B‖` (the headline DV). **Noise floor:** two independent refits of M0 — bootstrap-over-cells (resample contexts with replacement, family-clustered) + random MLP init reseed — give `‖M0_a(c)−M0_b(c)‖_{r_B}`; the 95th-pct of that distribution is the floor. **NOT cross-seed** (store is seed42-only). Report `Δ_{r_B} / floor_SD` with family-clustered-bootstrap 95% CI.
2. **Behavior-relevant transfer chain ρ (co-primary).** Predicted `r_Bᵀ M̂(c)` (the #658 `_chain_rho` form: project the LOCO-predicted v0 through r_B) vs measured E = `g` from #537 `G_meta.json` per cell, held-out under LOCO, Spearman ρ. Report under BOTH M0 and M⁺, and the difference. Also the **directional response curve** `M̂(c)·r_B/‖r_B‖` across the c-grid for M0 vs M⁺.
3. **Cross-transfer (parametric A3.6b).** `M0` predicting `v_plus` on FT pairs (held-out ρ) vs `M⁺` predicting `v_plus` on FT pairs; and the reverse (`M⁺` predicting `v0` on base pairs). A low M0→v⁺ transfer with high M⁺→v⁺ is parametric evidence the function changed.
4. **Linear-vs-nonlinear gap, pre vs post.** `(ρ_MLP − ρ_ridge)` under M0 vs under M⁺ — does the function become *more nonlinear* after FT? (#658's `nonlinear_gap` read, applied to both maps.)

### 4.6 Cross-reference to #697 (post-hoc panel, NOT a dependency)

When #697's `eval_results/issue_697/patch/` (or HF `issue697_cv_patch/`) per-cell `f_CV` exists, `issue722_analyze.py` emits a side-by-side table: per behavior, `f_CV` (causal, #697) alongside `Δ_{r_B}/floor` and chain-ρ shift (parametric, #722). Concordance (high f_CV ↔ low Δ) is the corroboration read. If #697 is incomplete at analysis time, the table is emitted with `f_CV: N/A — #697 still running` and the headline is NOT gated on it.

## 5. Conditions and Controls

| Plain-English name | What it tests | What it controls for | Config slug |
|---|---|---|---|
| Base map (M0) | The pre-FT context→answer function | The reference function | `M0` |
| Post-FT map (M⁺) | The post-FT context→answer function | The treatment function | `Mplus` |
| Refit noise floor | Two independent refits of M0 | Refit/bootstrap noise — the Δ denominator | `floor_refit` |
| Within-context shuffle null | Refit on permuted v0 | Chance-level fit ρ (overfit guard) | `shuffle_null` |
| Raw-v0-recon sanity inset | Full-v0 reconstruction at L=14 | Proves r_B-projection is the right DV (saturated surface) | `v0recon_sanity` |
| Linear (ridge) vs nonlinear (MLP) | Is M well-approximated linearly | Whether nonlinearity grows post-FT | `ridge` / `mlp` |

**Controls rationale.** The refit noise floor rules out "Δ is just refit jitter at n=16." The shuffle null rules out "the LOCO ρ is overfit chance." The v0-recon sanity inset rules out the #658 trap of reading function change off a saturated surface. The ridge/MLP pair rules out "the function change is invisible to a linear fit."

**Caveats (verbatim from body + planner additions):**
- Do NOT headline raw v0-reconstruction cosine (#658 saturated at 0.98) — kept only as the sanity inset.
- Same-input evaluation is MANDATORY (read (1) evaluates M0 and M⁺ on the identical `common_c_grid`).
- Noise floor MUST be reported alongside Δ (in floor-SD units).
- r_B recipe pick (`diffmeans`) MUST be identical for taught-fact extraction (no recipe-mismatch confound).
- **Single-seed caveat:** #667 store is seed42-only. The noise lever is bootstrap-over-cells + random-init refit, NOT cross-seed. The headline reports Δ/floor as a bootstrap CI, explicitly NOT a seed-spread; this is carried into the clean-result as a scope caveat.
- **Saturation guard:** if chain-ρ(M0) on a behavior already saturates ≈1.0, down-rank to a sanity check; do not headline. Marker is dropped from the headline on this + the no-contrast ground.
