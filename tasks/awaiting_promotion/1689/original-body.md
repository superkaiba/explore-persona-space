# Controlled 21-condition speaker × framing lattice for the context→answer map, characterized by the full mapping-similarity tier ladder

## Goal

Determine, on ONE shared row-paired corpus, whether the context->answer linear map is the SAME operator across five speaker identities (assistant; user; a fiction AI character; an assistant-like human character; an ordinary/random character) and three surface framings (chat template; plain User:/Assistant: text; narrative-prose story), in Qwen2.5-7B base AND instruct, with the user arm run under all three u2 provenances (real LMSYS, haiku-simulated, on-policy) and every non-user condition on-policy from the measured model - and, for every ordered pair, WHICH tier of the mapping-similarity ladder (direct transfer / context offset / answer offset / bias refit / global scaling / rotation / context reparameterization / answer reparameterization / full A.M.B) is the weakest correction that reconciles the two maps. Both mapping arms (prefix and context) are fit for every cell.

The question this answers that no prior task can: every existing cell lives in a DIFFERENT corpus, so the ladder's middle rungs — which are only DEFINED on shared rows — have never been computable across speaker or framing. A single row-paired battery makes "same operator in different coordinates" vs "genuinely different operator" decidable for all 21 conditions at once.

## Condition lattice (21 per model × 2 models = 42 cells)

| # | identity | framing | completion provenance |
|---|---|---|---|
| 1-3 | assistant | chat / no-template / story | on-policy (measured model) |
| 4-6 | user × real-LMSYS | chat / no-template / story | real logged u2, embedded verbatim |
| 7-9 | user × haiku | chat / no-template / story | `claude-haiku-4-5` simulated u2 |
| 10-12 | user × on-policy | chat / no-template / story | measured model writes its own u2 |
| 13-15 | other AI (HELIOS) | chat / no-template / story | on-policy |
| 16-18 | assistant-like human (Wren) | chat / no-template / story | on-policy |
| 19-21 | random character (Dana) | chat / no-template / story | on-policy |

Character semantics reuse the #1310 fixed-label roster verbatim (`scripts/issue1310_common.py::PERSONAS`): **Wren** "a warm, endlessly helpful assistant who patiently helps anyone who asks" (assistant-like human), **HELIOS** "a calm, precise artificial intelligence" (other AI), **Dana** "an ordinary, unremarkable everyday person" (random). **Vex** (theatrical villain) is available as an optional 4th/most-distant character if budget allows — not required for the headline.

Every non-user condition is on-policy from the MEASURED model under that identity × framing, judge-filtered per `.claude/rules/on-policy-completions.md`. The user arm is the ONLY teacher-forced/externally-authored arm, by construction.

## Design

**One shared corpus, row-paired across all 21 conditions.** Base corpus = N two-turn LMSYS conversations (two turns because the user arm needs a u2 target), filtered as in #825's Track-M. Each conversation is rendered into all 21 conditions; the fit rows are keyed by conversation id, so every ordered pair has a shared row set and the ladder's data-paired rungs (Δx, Δy, A, B, A·M·B) are DEFINED.

**Both mapping arms, per the standing rule** (CLAUDE.md "Prefix mapping AND context mapping"): every cell is fit twice — context arm (X = activation at end of everything up to and including the user query) and prefix arm (X = activation at end of everything before the user query). Neither arm is optional; a dropped arm is a stated deviation.

**Tier ladder per ordered pair.** For each pair, fit the source map `ŷ = W_s x + b_s`, then evaluate the ladder in order and report the WEAKEST rung that reconciles: (1) direct transfer; (2) context offset `W_s(x − Δx)`, Δx from the context clouds alone; (3) answer offset `W_s x + b_s + Δy`, Δy from the answer clouds alone; (4) bias refit `W_s x + b*` on target pairs; (5) global scaling `α W_s x + b*`; (6) rotation `R W_s x + b*` (fitted orthogonal Procrustes — the PREDICTIVE rung, not a rotation-invariant cosine); (7) context reparameterization `W_s(A x) + b*`; (8) answer reparameterization `B⁻¹ W_s x + b*`; (9) full `B⁻¹ W_s (A x) + b*`. Each rung against matched-capacity nulls (shuffled-fit centre + random-orthogonal), as in #1345's Leg B.

## Estimator (settled by the Phase 0 selector audit, 2026-07-25)

Phase 0 (`eval_results/issue_825/selector_audit/results.json`) established three things that BIND this design:

1. **Use `lambda_selection="inner-group-cv"`, not GCV.** Both GCV variants (uncapped, and the `GCV_DOF_CAP=0.9` guard) collapse as n_train approaches D=3584 from below — worst exactly at n=4000/n_train=3200, where guarded GCV reads −0.170 (instruct) / −0.698 (base) — while inner-group-CV is monotone and stable across the whole range. The dof-cap guard is a PARTIAL patch, not the fix.
2. **n ≈ 3000 suffices; n = 5000 is not required.** Under inner-group-CV the Track-S assistant map reads 0.656 at n=2000 and 0.669 at n=3000 against 0.696 at n=5000 (94% / 96% of ceiling). Size the battery at **n ≈ 3000** unless a pilot shows a specific condition needs more; this cuts generation ~40% vs the n=5000 default.
3. **The committed λ grid is adequate** — a grid-extension probe to 1e8 found no fold selecting above the committed 1e4 ceiling.

Report the selected λ per (layer, fold) for every cell (`collect_lambdas=True`), so a future reader can tell a degenerate selection from a real one.

## Capture + storage

Capture **frozen layers only (14 / 18 / 19 / 26)**, not all 28. At 4 layers the whole 42-cell store is ≈17 GB; at 28 layers it is ≈1.7 TB. This is load-bearing, not an optimization. Headline layer 19, per the #825/#1310/#1345 convention.

## Evaluation

Per the standing mapping rule (CLAUDE.md "Identity+learned-bias baseline AND kNN-retrieval metric"), every fitted map reports, alongside held-out R²:
- the **identity+learned-bias baseline** `v̂ = x + b` (`analysis/mapping_baselines.identity_bias_predict`) whenever input and output share dimension;
- the **kNN retrieval read** (`analysis/mapping_baselines.knn_retrieval`, euclidean + cosine, chance = k/n_pool stated).

Group 5-fold CV grouped by conversation id; conversation-level paired bootstrap for every cross-condition delta; shuffled-answer nulls per cell.

## Compute

All fits MUST be batched — full pairwise is 210 pairs × 2 models × 9 rungs ≈ 3,800 fits, exactly the #823 scale that ran 12-20 h serially. Batch via Gram/dual-space or a shared factorization (`.claude/rules/vectorize-many-cell-fits.md`); size the pair set down to the meaningful contrasts if the full cross is not needed for the headline.

Rough estimate (NOT measured — the planner must re-derive): ~10-15 GPU-h generation (≈90k responder completions + ≈22k on-policy user turns at n≈3000), ~3-5 GPU-h capture, ≈22k Haiku Batch-API calls, and a judge-filtering pass whose size is the main cost lever to trim at plan time.
