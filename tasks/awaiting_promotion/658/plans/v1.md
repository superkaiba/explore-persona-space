# Plan — Task #658: Base-model foundation for the leakage predictor on Qwen2.5-7B-Instruct (A3.2/A3.3/A3.4/A3.5 + recipe lock)

## 0.0 TL;DR (plain English)

- **What I'll run:** The project has a theory that says you can guess how a model will behave under a given prompt-context just by looking at the internal activations that context stirs up — and that a cheap "before-anything" summary of the context can stand in for the full picture. Before we spend real GPU budget fine-tuning a fleet of models on that theory, I'll run the cheapest possible sanity check on a single base model: I'll take 50 ready-made prompt contexts, read off the model's internal state under each, and check whether those readings can predict how the model actually behaves (does it agree with falsehoods, refuse, emit a hidden marker, etc.) — and whether a quick prompt-side reading predicts the fuller answer-side reading.
- **What I expect:** The simplest version of the theory (one averaged direction in the model's activations tells you the behavior) probably holds for clean, localized behaviors like the marker and refusal, and a straight-line readout will get you most of the way there. I'm less sure the cheap prompt-side summary will predict the answer-side one cleanly — a closely related project result found the analogous "predict from the base model alone" shortcut failed for behavior shifts.
- **What would change my mind:** If even a flexible predictor can't beat just guessing the average behavior — once I account for how noisy the behavior measurements themselves are — that's the theory's foundation cracking, and I should stop and not commit the fleet budget. The other surprise would be the cheap prompt-side reading working *as well as* the expensive answer-side one, which would make every later phase cheaper.

### 4.1 Construct semantics (from the theory paper §3, verbatim)

- `v0(C) = E_{x∼C}[ā_θ0(x)]`: `ā_θ0(x)` = residual activation at layer ℓ averaged over the **answer-token positions of the model's own generated `A_θ0(x)`** (greedy), then averaged over the 48 probes `x∼C`. Per context, per layer: one `R^3584` vector.
- `c_C`: context vector. Default = last-input-token slot (the assistant-header newline under `add_generation_prompt=True`), exactly the #594-wired recipe (REUSED from HF). Ablation = mean over prompt tokens.
- `r_B`: behavior read-out. Default = diff-in-means `mean(ā_θ0(D_B)) − mean(ā_θ0(D_{B̄}))` over #545's behavior corpora, answer side, per layer.
- `E0(C,B)`: base-model expression of behavior B under context C, measured on-policy + judged.

### 4.2 GPU phase — extraction (NEW code: `scripts/issue658_extract_base_store.py`)

Extends `issue594_extract_context_vectors.py` (does NOT reimplement — imports `load_battery`, `messages_for_instance`, `LayerCapture`, the manifest/sentinel/upload helpers). The #594 extractor captures the **last input token** (prompt-side `c_C`); the #658 extension adds a generate-then-capture pass for the **answer-side `v0(C)`**.

```python
# scripts/issue658_extract_base_store.py (sketch)
# G1+G2: answer-side v0(C). For each context C (50), each probe x (48):
#   1. vLLM batched greedy generate A = model.generate(messages_for_instance(C, x))
#      (batched across the 50×48 = 2400 prompts in one LLM.generate call — NOT a loop)
#   2. teacher-force A back through HF model with LayerCapture hooks on all 28 layers,
#      capture residual acts at the ANSWER-token span (positions of A, not the prompt)
#   3. summarize per layer with 4 recipes:
#         mean   = acts[answer_span].mean(0)            # DEFAULT (theory A3.2)
#         last   = acts[answer_span][-1]                # last-answer-token
#         maxp   = acts[answer_span].max(0).values      # max-pool
#         attn   = (softmax(acts @ w_pool) * acts).sum(0)  # learned attn-pool; w_pool fit in CPU phase
#   v0_mean[C] = mean over the 48 probes of each summary   -> (n_layers, hidden) per recipe
# Store per-(C, probe) answer activations (fp16) for the noise-floor resampling (N1).
assert tokenizer.encode(" ※", add_special_tokens=False) == [83399], "marker token id"  # marker family ctx + r_B
```

- **Batched forwards, not batch-1 loops** (code-style compute-throughput rule): one `LLM.generate()` over all 2400 prompts; the teacher-forced capture pass batches over probes within a context.
- **`max_new_tokens`:** 512 for the activation-summary generation (free-generation behavior; the marker column uses ≥2048 per the #260 rule — handled in J1's marker DV, not the activation capture).
- **Attention-pool recipe:** the `w_pool` weight is FIT on the CPU side (P1) as part of the A3.2 predictor, not on the GPU; the GPU stores the raw per-token answer activations so attn-pool is a CPU operation. (Stored per-(C,probe) acts are needed for N1 anyway.)
- **Position assert:** reuse #594's last-3-token decode assert for the `c_C` ablation slot; for the answer span, assert the captured span length equals the generated `A` token count (fail-loud on misalignment).

`r_B` (G4) wires #545's `D_B/D_{B̄}` corpora (`behavior_testbed_545/corpora.py`) through the same `LayerCapture`, computing diff-in-means at all 28 layers per recipe.

`Σ_c` (G5) runs the #594 extractor (`c_C` recipe) over ≥3k background contexts from `scripts/project_corpus_v2.py` → `Σ_c = (1/n)Σ c c^T`, with `Σ_c⁻¹ = (Σ_c + λI)⁻¹` (λ swept on the CPU side as a baseline knob, §11).

### 4.3 CPU/API phase — judging + predictor fits (NEW code: `scripts/issue658_fit_predictors.py`, off-pod)

**J1 — `E0(C,B)`.** For each (context, behavior-column) the judged-rate DV: generate N=10-50 temp-1.0 samples per probe (per `columns.py` `n_samples`), Batch-judge with `claude-sonnet-4-5-20250929` (testbed legacy pins replaced). Rate = judge-positive fraction. The marker column uses `marker_slot_stats` (4-float on-policy log-prob, no judge). This is the dual-DV PRIMARY (§6).

**P1 — A3.2.** Per behavior B, per layer ℓ, per summary recipe: fit a small MLP `v0(C)[ℓ] → E0(C,B)` (sklearn `MLPRegressor` or a 1-hidden-layer torch net), evaluate held-out C under LOCO. Compare ρ(predicted, measured) against (a) predict-mean, (b) the noise floor, (c) the base-prior baseline. PASS per behavior = best-layer ρ > noise-floor 95th pct AND > predict-mean ρ. Report the best (layer, summary) per behavior — the deliverable.

**P2 — A3.3.** Fit `r_B` (3 recipes: diff-in-means default, mean-`D_B`, few-shot-final), test `E0 ≈ r_B^T v0(C)` on held-out C, per layer. Report linear ρ vs the A3.2 MLP ceiling (A3.3 PASS = linear within noise floor of the MLP) + the `r_B` recipe ranking + per-behavior best layer.

**P3 — A3.4/A3.5.** Fit linear `M` (ridge, λ nested-CV) and an MLP, `c_C → v0(C)`, held-out C (LOCO). Report the linear-vs-nonlinear gap (does the MLP beat ridge "much"?), the best `c_C` recipe/layer, AND the downstream `r_B^T M c_C` → `E0` chain ρ. Name which `c_C` recipe becomes the campaign default: default to **last-input-token** (the #594-wired, store-reused recipe) UNLESS mean-over-prompt wins by > the noise-floor margin — stated so Phase 2 inherits a single recipe.

**N1 — noise floor.** Re-estimate `E0(C,B)` from 8 independent 48-probe redraws (re-draw `x∼C` from the Betley pool) × seeds; test-retest ρ across redraws = the per-behavior reliability ceiling. The PASS bar (§6) is ρ exceeding the 95th percentile of this distribution.

### 4.4 Why code, not a model call?

The behavior SCORING is a model call (Claude judge) — that is the right tool and is used (J1). The predictor FITS (ridge, MLP, diff-in-means, SVD, bootstrap) are deterministic linear algebra over a 50×28×3584 cached tensor: a model call cannot do a held-out regression or a test-retest reliability estimate, and these need exact reproducibility + per-cell determinism over ~1000 cells. Code is correct here; no single-model-call alternative exists for the numeric predictor.

### Dual-DV (content-behavior expression)

This task READS base-model expression rates that can saturate at floor/ceiling on aligned behaviors (refusal, harmful_compliance often near-floor at θ0; sycophancy mid-range). Per the standing rule I register BOTH: (a) the judged on-policy **rate** as PRIMARY, and (b) the length-normalized base-model **`log P`** of judged-positive on-policy completions as the SECONDARY non-saturating companion. The secondary is validated by reporting Spearman(rate, log-P) across the cells with dynamic range (computed in A1). I do NOT skip the secondary: base rates do NOT have known dynamic range across the panel (the aligned-behavior columns are exactly the saturation risk), so the continuous companion is required, not optional. The marker column already carries its own three-space continuous DV.

### Install-strength control

### Metrics, tests, thresholds

- **PRIMARY:** Spearman ρ (predictor vs measured `E0`), per behavior, per layer, per summary. Pearson r secondary.
- **PASS (per behavior):** best-(layer,summary) ρ > 95th pct of the N1 noise-floor distribution AND > predict-mean ρ AND > base-prior ρ (the geometry-win-not-prior guard). A3.3 additionally PASSes iff linear ρ is within the noise floor of the A3.2 MLP ρ.
- **Statistical hygiene:** cluster-aware bootstrap CIs (one cluster per behavior for A3.2/A3.3; per context for A3.4/A3.5), 2000 resamples, mirroring `scoring.py`'s `_family_row_bootstrap`. **FDR at q=0.10** (Benjamini-Hochberg) over the ~1000-cell layer×summary×behavior grid (the all-28-layer sweep is a multiple-comparison surface — a layer-lucky fit is the #602 failure mode). ## 9. Resources & Parallelism

**One GPU phase, off-pod CPU phase.** The GPU work is activation extraction + base generation — a single forward/generate workload on one model. There is no fine-tune fleet, no sweep of independent training cells, so the "one multi-GPU pod with sharded subprocesses" pattern does not apply here (nothing to shard — it's one model doing one extraction pass). The parallelism axis that DOES apply is **batched inference (vLLM)**: all 2400 (context×probe) prompts go through one `LLM.generate()` call, and the teacher-forced capture batches over probes — never a batch-1 loop (code-style rule).

- **(a) GPU spec:** `lora-7b` intent → GCP `auto` lane provisions 1× A100-80 (`a2-ultragpu-1g`). 
- **(b) parallelism axis:** batched vLLM generation + batched HF capture forwards.
- **(c) wall-time delta vs `eval` (1× L4):** `eval` → 1× L4 24GB. Qwen2.5-7B bf16 is ~15GB; with vLLM KV-cache for a 2400-prompt batch + a second HF model instance for the hooked capture pass (vLLM doesn't expose residual hooks), 24GB is too tight and would force tiny micro-batches → multi-hour generation. A100-80 holds both comfortably and runs the batched passes fast. Chose `lora-7b` over `eval` for the HBM headroom, NOT for any LoRA (none is trained).
- **(d) smaller pod not chosen:** L4 risks OOM on the dual model-instance capture; the ~$ delta is negligible at ~5-7 GPU-h.

**CPU-only phases run OFF-POD.** J1 (Batch-judge, API-only), P1/P2/P3 (predictor fits), N1 (resampling), A1 (aggregation + figures) all read the uploaded store from the VM. The pod uploads the store + raw completions, then TERMINATES before the CPU phase — no idle-GPU burn (the #518/#523 anti-pattern). Batch-judge is the Anthropic Batch API (off-GPU entirely).

**Sentinel signaling:** the extractor emits `[phase=...]` lines + a `poll_pipeline.py` sentinel (inherited from #594). On the GCP lane `/workspace` is mirrored (`GcpConfig.vm_scratch_dir`), so the sentinel contract holds. Backend = `auto`; if the GCP ladder + SLURM lanes exhaust, the RunPod terminal rung honors the same `/workspace` sentinel contract. No explicit lane pin needed.
