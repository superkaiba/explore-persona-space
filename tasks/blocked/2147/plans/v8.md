## 0. The apparent contradiction, and its binding resolution (READ FIRST)

Round 2 established three facts, each independently re-verified by the
orchestrator against source and the live filesystem:

1. **The task's own non-negotiable constraint forbids reaping the realized
   population.** `body.md` §Constraints lists, as non-negotiable, "`store/` +
   `eval_results/` never touched"; `.claude/rules/disk-hygiene.md:10` says
   "NEVER delete". Every one of the 13 live trees is a FULL branch checkout and
   therefore contains `eval_results/` (7.8 GB of a 9.4 GB tree).
2. **The inherited evidence model rejects every tree anyway.** Each tree
   carries the `external/open-instruct` overlay — 844 files, rsync'd from the
   working tree, a mode-160000 gitlink absent from the outer committed tree
   (`slurm.py:3826-3838`). `_git_blob_reproducibility_evidence` hashes every
   non-exempt regular file and rejects the candidate if any blob is missing
   from the outer ODB; `external` is NOT in `_SCRATCH_EXEMPT_DIR_NAMES`
   (`clean_experiment_downloads.py:299`). Measured: 8/8 sampled overlay blobs
   ABSENT from the outer ODB.
3. **Therefore a spec-honoring tier reclaims 0 of 112 GB today**, by two
   independent routes.

Fact 1 was a genuine reviewer disagreement — Claude held the blob proof IS the
never-delete rule's enforcement mechanism; Codex held the constraint is
categorical — and it decided whether this task reclaims ~112 GB or 0 GB. Per
the ensemble protocol a `reconciler` was spawned with both positions and the
primary sources.

**BINDING RECONCILE: POSITION_A — proof-positive whole-tree removal IS
permitted.** Fact 1 is therefore WITHDRAWN. The decisive evidence (which
neither round-2 reviewer surfaced):

- `_SCRATCH_EXEMPT_DIR_NAMES` (`ced.py:299-310`) contains `.git`/`.venv`/caches
  but **not** `store`/`eval_results` — durable subtrees are WALKED and VERIFIED,
  never pruned or kept.
- `under_durable` (`ced.py:1717`) has exactly ONE use (`:1733-1738`): it DENIES
  the small-text tolerance shortcut, forcing every file under `store/` or
  `eval_results/` through the per-file sha1 → main-odb existence probe
  (`:1742-1766`). The docstring says it verbatim (`:1662-1663`): tolerance
  applies "never under a `store`/`eval_results` component". **It is a stricter
  proof bar, not a keep.** Its existence proves the #2127 authors anticipated
  `eval_results/` inside scratch candidates and chose "must be individually
  blob-proven" over "never touch".
- There is NO keep branch keyed on durable-path presence anywhere in
  `sweep_tmp_scratch`'s gate order (`:1947-1969`). Tier (f) — already shipped,
  from a user directive — removes whole registered worktrees containing
  `eval_results/` under exactly this proof. Position B would make the SHIPPED
  tier a standing violation and `disk-hygiene.md` internally inconsistent.

**The invariant's true shape:** durable-named content is never deleted WITHOUT
positive per-byte recoverability evidence; where the deletion instrument
carries no such evidence, mere presence blocks categorically. That is why
tier (b) (`vm_disk_guard.py:899-902`, a SELECTIVE reap inside a surviving data
tree, no per-byte evidence) and the #911 nested-durable block (`ced.py:121-123`,
documented "non-canonical only") both keep unconditionally, while the #2127
verified-scratch regime does not. Position B misgeneralized a real but
evidence-class-scoped rule across that boundary.

The task body's constraint is an enumeration-BY-REFERENCE of the existing
tiers' contract (`body.md:87-92`, which also names `clean_experiment_downloads.py`
as "the sibling janitor whose contract to mirror", `:84-85`) — so applying the
two-regime semantics IS honoring the constraint, not rewriting it. Under
Position B the body would self-contradict: its Goal (`:22-24`) demands
reclaiming trees that are all full checkouts, which B makes structurally
unreclaimable.

**Decision:** this tier follows the **#2127 verified-scratch contract**, not the
tier-(b) selective-keep contract. Fact 2 (the overlay) still stands and is
answered by D9. Fact 3 is withdrawn with Fact 1.

**Reclaim estimate — stated honestly:** *up to* ~112 GB, **per-tree gated on the
proof**. Any tree with untracked/dirty content or an unprovable overlay file
correctly fails verification and stays kept-escalated. Not a promise of 112 GB.

## 3. Design decisions

**D1 — Home: `vm_disk_guard.py`.** SETTLED round 1, both reviewers. Boot-disk
reclaim contract; `~/.eps-slurm-src` resolves to `/dev/root`;
`workflow_fix_target` names it. (`worktree_audit.py`'s guard 4 keeps only
TRACKED changes — wrong semantics before a destructive remover.)

**D2 — Reuse the #2127 evidence+reap primitives, NOT `cleanup_branch_src`.**
SETTLED round 1; round-2 verified all seven protection rows against source.
`cleanup_branch_src` (`slurm.py:3863-3880`) suppresses the remove result,
rmtree's unconditionally, and prunes globally — disqualifying for a janitor.
`_reap_scratch_tree` (`ced.py:1876-1886`) is rc-checked, keeps on failure, has
no rmtree fallback for registered worktrees, and never globally prunes.

**D3 — Terminal gate: reuse `TERMINAL_CACHE_REAP_STATUSES` verbatim.** SETTLED
round 1, both reviewers. Status is a candidacy PRE-gate only; it never
substitutes for evidence.

**D4 — Gate ladder.** Tier-(g) pre-gates, then the shared per-candidate core:

| # | Gate | Disposition |
|---|---|---|
| g1 | name not `issue-<N>` shaped | `kept — unrecognized name` |
| g2 | not uid-owned | `kept — not owned` |
| g3 | resolved path escapes root | `kept — containment` |
| g4 | status ∉ terminal set (incl. unresolvable) | `kept — active/unresolved` + escalate |
| g4b | status-probe failure | `kept — probe failed` + escalate |

then the shared core UNCHANGED: walk → write-recency → blob evidence (outer
ODB, with the native `under_durable` no-tolerance rule, **plus D9 for overlay
paths**) → reader-atime → live-process → reap with fresh re-walk + class
re-probe. Inherited keep reasons are re-tagged `slurm-src-*`.

**No durable-path presence gate.** v5's g5 (`presence ⇒ keep`) is REMOVED per
the binding reconcile in §0: durable-named content is handled by the inherited
`under_durable` no-tolerance rule (every file under `store/`/`eval_results/`
must be individually blob-proven; no tolerance shortcut), which is stricter
than the ordinary bar and is already native — no new code, no shared-code edit.

**D8 — WITHDRAWN.** v4's "durable-path no-tolerance sub-gate" was factually
wrong about the code: the carve-out is ALREADY native —
`ced.py:1717 under_durable = any(p in ("store","eval_results") for p in
rel_dir_parts)` with the tolerance branch requiring `and not under_durable`
(`:1733-1738`), documented at `:1662-1663`. Implementing it as written would
have threaded a flag through shared code for ZERO behavior change, firing K3.
Superseded by g5, which is stricter (presence ⇒ keep, no proof considered).

**D9 — NEW: nested-repo evidence class for `WORKING_TREE_OVERLAY_PATHS`.**
Required for the tier to be non-inert post-sparse (§0 fact 2). For a file whose
relative path lies under a known overlay path, the blob-existence proof is
evaluated against that nested repo's OWN ODB, and the nested tree must
additionally be clean with its HEAD reachable from a surviving ref IN THAT
NESTED REPO — the identical evidence standard applied at the correct repo
boundary. This is *strengthening by extension*, not loosening: a file under the
overlay must now satisfy nested-repo proof AND nested-tree cleanliness, where
today it simply fails. Overlay paths come from the writer's own
`WORKING_TREE_OVERLAY_PATHS` constant (`slurm.py:3838`) — never a re-typed
literal, so writer and reaper cannot drift. A path claimed as an overlay that
is NOT a git repo ⇒ KEEP (no silent fallback to the outer proof).

**D5 — Hermeticity + kill switch.** `clean_slurm_src(apply, *,
slurm_src_root, main_repo, verdict_cache_path)`; SKIPS with a reason when an
opt-in is `None`; `run_guard` forwards verbatim and never calls the production
resolver (pinned by the existing source-scan test). Kill switch
`EPM_SKIP_SLURM_SRC_SWEEP=1` + the family switch. Root via `EPS_SLURM_SRC_ROOT`
with the writer's precedence. Boot-disk pass only (data-disk pass is
`reclaim_tiers=False`, `vm_disk_guard.py:2671`).

**D6 — CORRECTED escalation semantics** (round-2 F3/minor, both reviewers).
The scratch leg has NEITHER per-(key,band) dedup NOR ack-sentinel suppression:
`_finish` calls `append_disk_guard_event` directly (`ced.py:2003-2015`; the
appender `:500-519` has no dedup); it is only floor-gated by
`EPS_SCRATCH_ESCALATE_FLOOR_GB` (default 1.0 GB, `:324-326`). The dedup+ack
machinery belongs to tier (b) (`vm_disk_guard.py:294-318`). Under v5 all 13
legacy trees are standing keeps above the floor, so a naive append yields 13
sidecar rows per triggered pass, indefinitely. v5 therefore specifies a
**leg-scoped dedup as NEW code** (not an inherited claim): a per-`(path,
reason, band)` sentinel under `.claude/cache/`, re-alerting on the existing
weekly cadence. T13 pins it.

**D7 — Docstring corrections.** `slurm.py:3048`/`:3848` "~3.8 GB" → measured
~8.6 GB mean; `:3849-3851`'s "no covering janitor" → names tier (g).
