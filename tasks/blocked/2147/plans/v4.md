## 1. Goal

Add a `vm_disk_guard.py` reclaim tier that reaps per-issue SLURM source staging
trees under `~/.eps-slurm-src/issue-<N>` for TERMINAL-status issues, under the
same safety contract as the existing tiers: terminal-status gate, status read
strictly read-only, ACTIVE-issue dirs attributed + escalated but NEVER deleted,
recency as a KEEP-only signal, deletion gated on POSITIVE VERIFIED
git-reproducibility evidence, `main()`-only production opt-in so library/pytest
callers stay hermetic, and a kill switch.

   only, SKIPPED-with-reason without the `main()` opt-in.

   pre-fix is not evidence).

4. The real-VM acceptance run (§6) classifies all 13 live dirs exactly as

6. No durable-named path (`store/`, `eval_results/`) is ever deleted without a

- **K3** *(fired in v3, retained for the new design)* — if reusing the #2127

## 3. Design decisions

### D1 — Home: `vm_disk_guard.py` (not `worktree_audit.py`). SETTLED.

(a) the task asks for the byte-floor reclaim contract (terminal gate + active
escalate-only + evidence gating + kill switch) that `vm_disk_guard.py` owns;
(b) `~/.eps-slurm-src` resolves to `/` (`/dev/root`), the boot disk it guards;
(c) the body's Provenance names it as `workflow_fix_target`. Both reviewers
independently agreed. Codex added the decisive nuance: `worktree_audit.py`
supplies the safer *lifecycle precedent*, and moving the tier is unnecessary
**provided those protections are carried over** — which D2 now does.

Note `worktree_audit.py`'s guard 4 keeps only TRACKED changes (its header:
untracked generated files "do NOT block"), which would be the wrong semantics
in front of a destructive remover — a second reason not to host it there.

### D2 — **REPLACED (v3's D2 withdrawn; K3 fired).** Reuse the #2127 scratch-sweep pipeline, NOT `cleanup_branch_src`.

v3 proposed calling `backends/slurm.cleanup_branch_src` behind a cleanliness
gate. Both reviewers rejected this, and re-reading the helper confirms it:

```
slurm.py:3863-3880 — worktree remove --force (result SUPPRESSED)
                   → shutil.rmtree(scratch, ignore_errors=True)  UNCONDITIONALLY
                   → git worktree prune                          GLOBALLY
```

The `rmtree` runs **regardless of whether the remove succeeded**. That is
correct for the OWNER tearing down its own scratch, and disqualifying for a
janitor: a locked or otherwise unremovable worktree gets its directory
destroyed anyway while `prune` skips the locked registration — leaving a stale
registration that makes the next `materialize_branch_src` `worktree add` FAIL,
wedging that issue's SLURM lane. The sibling janitor refuses exactly this:
`worktree_audit.py:818-831 _git_remove` is documented *"Never falls back to
rm -rf in the unattended path"* and returns rc-checked success/failure.

**The correct precedent is `clean_experiment_downloads.sweep_tmp_scratch`
(#2127)** — the tier (f) machinery `vm_disk_guard.py:40-52` describes:
*"Registered main-repo worktrees are removed via `git worktree remove --force`
(a remove failure KEEPS the tree — no rmtree fallback, no global `git worktree
prune`); a live-process /proc probe holds the reap"*. Its per-candidate gate
order already implements, natively, every protection the reviewers demanded:

| reviewer finding | already in `sweep_tmp_scratch` |
|---|---|
| Codex C1 — no rmtree fallback, no global prune, rc-checked | `_reap_scratch_tree` → `tmp-scratch-worktree-remove-failed` (kept) |
| Codex C1 — lock ⇒ KEEP | evidence gate → `...-worktree-locked-kept` |
| Codex C2 — HEAD reachable from surviving refs | `_scratch_git_class_probes` / `_reachable_in_main` (reachability, not mere object presence) |
| Codex C3 — positive reproducibility evidence | `_git_blob_reproducibility_evidence` (per-file blob-existence proof) |
| Claude B1 — probe failure ⇒ KEEP | walk/probe errors → `...-unverified-kept` |
| Claude B1 / both — re-probe before reap | reap-time class RE-probe → `...-reap-reprobe-kept` |
| live process holds the tree | `_scratch_live_process_hit` → `...-live-process-kept` |

So tier (g) is NOT a new remover. It is: **a new candidate enumerator + a
status pre-gate in front of the existing, already-reviewed pipeline.** This is
the reuse rule applied to the *right* helper; v3 picked the wrong one.

**K3 guard:** if wiring this requires LOOSENING any existing protection in that
pipeline, halt and re-plan (§1.2 K3). Adding a caller must not weaken a shared
janitor.

### D3 — Terminal gate: REUSE `TERMINAL_CACHE_REAP_STATUSES` verbatim. SETTLED.

`vm_disk_guard.py:447` = `{"completed", "archived", "awaiting_promotion"}`,
deliberately wider than `task_workflow.TERMINAL_STATUSES` (comment at `:443`),
and it covers 13/13 of the realized population.

Both reviewers independently confirmed `awaiting_promotion` is safe here, for a
reason stronger than v3 gave: `materialize_branch_src` step 2
**unconditionally destroys any existing scratch at every dispatch**
(`slurm.py:3940-3944`), so no dispatch, follow-up, or resume ever READS a stale
tree — reaping an idle one is a pipeline no-op regardless of status.
`fetch_results` merges into `<src_root>` (the main checkout resolved by
`_default_src_root`, `slurm.py:3577-3626`), never into `~/.eps-slurm-src`.
Codex added: `worktree_audit.py:145-153` already records that
`awaiting_promotion` has merged and that promotion reads the main repo. Risk
class is strictly LOWER than the hf_dl caches this status set already governs.

Note the status gate is a PRE-gate only: it decides candidacy. It never
substitutes for the reproducibility evidence gate (D8) — status is not
evidence.

### D4 — Gate ladder (first match wins; every early exit is a KEEP)

Pre-gates added by tier (g):

| # | Gate | Disposition |
|---|---|---|
| g1 | name not `issue-<N>` shaped | `kept — unrecognized name` |
| g2 | not uid-owned (`_tmp_entry_owned`) | `kept — not owned` |
| g3 | resolved path escapes the root | `kept — containment` |
| g4 | status ∉ `TERMINAL_CACHE_REAP_STATUSES` (incl. unresolvable) | `kept — active/unresolved` **+ escalate** |
| g4b | **any status-probe failure** | `kept — probe failed` **+ escalate** |

Then the candidate enters the **unmodified** `sweep_tmp_scratch` per-candidate
pipeline (walk → write-recency → blob-reproducibility evidence → reader-atime →
live-process → reap with fresh re-walk + class re-probe), whose keep reasons are
inherited verbatim, re-tagged to this leg (`slurm-src-*`).

Claude's B1 (probe failure ⇒ KEEP, never read as clean) is satisfied inside the
pipeline for git probes, and by g4b for the status probe — the one probe tier
(g) itself introduces.

### D8 — **NEW.** Durable-path sub-gate: no tolerance carve-out under `store/` / `eval_results/`

This answers Codex C3 with **evidence rather than argument**. `disk-hygiene.md`
states bulk deletions are *"gated on POSITIVE VERIFIED evidence — HF-backedness
or git-reproducibility (blob-existence proof) — never on age"*. That blob proof
IS this codebase's enforcement mechanism for the never-delete invariant, so
satisfying it is not "reasoning around" the rule.

One strengthening is required. `_git_blob_reproducibility_evidence` tolerates
small text telemetry (`.txt/.log/.out/.err`) under tight byte caps without a
blob proof. Tier (g) **disables that tolerance for any path under `store/` or
`eval_results/`**: every file there must carry a verified blob-existence proof,
or the tree is `kept — durable content unproven` + escalated. A durable-named
path is never reaped on a tolerance allowance.

If D8 keeps all 13 trees, K4 fires and the task re-plans onto §8's writer-side
path — the tier would be reclaiming nothing.

### D5 — Hermeticity + kill switch (the #2127 / #2095 pattern, verbatim)

`clean_slurm_src(apply, *, slurm_src_root, main_repo, verdict_cache_path)`
returns `TierResult(name="slurm-src")` and SKIPS with a reason when either
opt-in is `None`. `run_guard` forwards both VERBATIM and NEVER calls the
production resolver itself — the opt-in lives ONLY in `main()`'s boot-disk
branch, pinned by the existing source-scan test that already pins
`production_tmp_root` / `production_staging_roots`.

Kill switch `EPM_SKIP_SLURM_SRC_SWEEP=1`, plus transitive kill via the existing
family switch `EPM_SKIP_NONCANONICAL_CACHE_SWEEP=1`. Root override
`EPS_SLURM_SRC_ROOT`, read with the SAME precedence as `slurm.py` so writer and
reaper cannot drift.

**Boot-disk pass only** — verified: `~/.eps-slurm-src` resolves to `/dev/root`
(`/`), and the data-disk pass runs `reclaim_tiers=False`
(`vm_disk_guard.py:2671`). The tier records the resolved root's filesystem in
its report so a future `$HOME` move is visible rather than silent.

### D6 — Escalation reuses the existing sidecar

Keep/escalate rows land on `TierResult` and in
`.claude/cache/disk-guard-events.jsonl` with the established per-`(key, band)`
dedup + ack-sentinel suppression and the `EPS_SCRATCH_ESCALATE_FLOOR_GB` floor
semantics. No new alert surface. Report-only by default; the cron passes
`--apply`.

### D7 — Docstring corrections (in scope, same round)

`slurm.py:3048` / `:3848` claim "~3.8 GB" (measured mean ~8.6 GB);
`:3849-3851` claims no covering janitor. Both corrected — leaving them makes the
module actively misleading the moment the tier lands. Prose-only in
`backends/slurm.py`.
