# Plan — #2321: Repack the 10 largest prefixes in the HF data repo to recover file-count headroom

### 0.0 TL;DR (plain English)

- **What I'll run:** a checkpointed repack driver on one cheap CPU pod that, prefix by prefix, downloads each prefix's small files, packs them byte-exactly into a few ≤9 MB `.jsonl` shards plus an index, verifies every file round-trips (sha256), and then — in commits that each ADD the shards, the index entries needed to resolve them, and a per-unit journal record, and DELETE exactly the files those shards contain — removes the originals. Every deletion-bearing commit is pinned to the exact repo revision it was verified against (`parent_commit`), so a concurrent write can never be silently overwritten. A 3-commit probe using throwaway probe files settles first whether the Hub counts files net-of-deletes, without touching any real artifact. Before any prefix's originals are deleted, a consumer gate blocks the repack if any script still reads that prefix by listing/glob (the class that would silently read an empty tree as a real zero-result).
- **What I expect:** ~541,500 of the 1,000,000 file slots freed (repo drops from 999,999 to ~458,500 files, ~46% of cap) for ~13.7 GB downloaded and ~15.8 GB uploaded, zero data loss, and a reader shim in `hub.py` that transparently serves any repacked original path — resolvable after every intermediate commit, not only at prefix completion.
- **What would change my mind:** if the probe commit is rejected (the server does not count files net-of-deletes in one push), the whole approach is invalid — the driver STOPs with nothing deleted and this task reports that instead of reaching for deletion (with one intermediate check first: a net-ZERO probe rejection alone does not condemn the approach — a net-NEGATIVE real-unit probe runs before the invalidation verdict). If a commit request times out, I never blindly retry — the outcome is unknown (it can have landed server-side), so I re-check the repo state, content-anchored, and act on what I find. If the live session attached to #1739 shows fresh activity when its two prefixes come up, I skip those two and report them as deferred rather than writing into a live session's prefixes. If the measured per-commit wall or download rate is far worse than projected, I shrink commit units / accept a longer wall rather than weaken any safety invariant.

### 3.2 Archive format (v2 codec, `orchestrate/packing.py`)

Reuses the #1739 shape — `<group>.shardNN.jsonl` line-shards ≤ `SHARD_MAX_BYTES = 9_000_000` + a census-keyed manifest — with three generalizations (exactly the gaps named in §2):

- **Record schema (byte-exact, replaces v1's parsed-`doc`):** one line per source file
  `{"src": "<relpath>", "enc": "text"|"b64", "sha256": "<hex of raw bytes>", "bytes": N, "data": "<raw utf-8 text | base64>"}`.
  `enc="text"` iff the bytes round-trip UTF-8 decode/encode identically (JSON stored as its raw *text*, never parsed — byte-exact regardless of producer formatting; ~+3% escaping overhead measured on JSON-like content); else `enc="b64"` (+33%). Empty files legal. Unpack = decode + sha256 assert.
- **All file types accepted** (v1's non-`.json` fail-loud lifted); binary `.npz/.pt/.log/.md/.done` all carry via `b64`.
- **Member cap:** a shard closes at 9 MB **or 4,000 members**, whichever first — so one commit can pair each shard-set with its exact delete set while staying under every observed commit-scale hazard (§3.5).
- **Offsets:** the packer records each member's `(shard, byte_offset, byte_length)` (known at write time) into per-group index files `packed/<group>.indexNN.json` (≤9 MB each, split like everything else) + a small per-prefix `packed/INDEX.json` top index `{group_key: {rel_dir, index_files, shard_files, n_members}}` + `packed/pack_manifest.json` (v2: version 2, per-shard sha256/n_lines/bytes, census, git commit, source repo revision). **Per-member offset addressability: YES** in the recorded index; **HTTP Range reads over the Hub are a documented non-goal for v1 of the shim** — it stages whole ≤9 MB shards via `stage_hub_file`, which for ≤9 MB parts costs at most one shard per member read. Deviation from body scope item 2 ("2 files per prefix"): 2 + ~1 index file per group + 1 cumulative unit journal, forced by the 9.5 MB non-LFS line-split discipline (a single `INDEX.json` for `issue1481`'s 206k members would be ~20 MB → LFS force-route) and by I15.
- **Group key:** v1 semantics (leaf dir, `/`→`_`), fail-loud collision check kept; on a detected collision, deterministic disambiguation `key + "-" + sha1(rel_dir)[:8]` instead of aborting. **Collision mapping is decided at PACK time, before any shard is written (C13):** the packer derives ALL group keys for the prefix first, applies the disambiguation deterministically over the full set, and records each group's `rel_dir` in `INDEX.json` — the shim resolves collided groups via that recorded `rel_dir`, never by re-deriving the key from the parent dir (§3.7). `tests/test_hub_packed_fallback.py` includes a collided-group (two colliding directories) prefix shape.
- **Why not tar:** tar (uncompressed) has near-zero byte overhead and offset addressability, but `*.tar` is LFS-matched by the repo's default gitattributes EVEN UNDER 10 MB — so every tar shard would ride the LFS path regardless of size (a firmer rejection than the >10 MB force-route alone) → storage-quota-403 exposure on an over-ceiling account + the `_resolve_lfs_upload_repo` atomicity conflict (clarifier finding 4) + a second archive format beside the repo's established one. **Why not parquet:** provably-lossless columnarization would need per-prefix schema work for zero benefit over raw-text records at these sizes. The jsonl pack IS the repo's prescribed recipe (`upload-policy.md` L783-815) and HF's own published recommendation.
