## 1. Requirement + acceptance criteria

Make `scripts/persist_verdict_concerns.py` fail loud when a verdict marker
carries line-start `CONCERN::` rows that it cannot ingest, so a reviewer's
concerns can never silently miss the ledger.

Acceptance (restated as checkable conditions, from the task body):

- **A1.** Forwarding a marker containing ≥1 line-start `CONCERN::` row that
  the parser cannot ingest exits **non-zero** with a message naming the
  marker path and the expected row formats.
- **A2.** Both emitted row formats forward successfully (see §4), OR exactly
  one is pinned in both reviewer specs and the parser matches it. This plan
  takes the accept-both branch.
- **A3.** A committed test fails if the silent-drop path is reintroduced.
- **A4.** Existing behavior on well-formed canonical input is unchanged, and
  `--require-block` keeps its current semantics.

**A1 is stated per-row, not per-marker.** v1 keyed the failure on a
whole-marker zero-ingest conjunction, which (MF2) let an unclassifiable row
ride along silently beside valid ones. Every line-start row is now
individually accounted for.

## 4. Design

### 4a. Exhaustive collection, then per-row classification

The load-bearing change (MF2): collection is **exhaustive over line-start
rows**, and classification is total. Every line-start `CONCERN::` row is
collected by one regex and then classified; a row matching neither grammar
is a MALFORMED row, not an invisible one.

```python
_ANY_ROW_RE = re.compile(r"^CONCERN::(.*)$", re.MULTILINE)
```

This replaces the shape-specific `_ROW_RE` as the collector. Line-start
anchoring is retained deliberately and matches the existing parser's
discipline (`codex-code-reviewer.md:630-633` already warns that a stray
line-start occurrence persists as a real concern); a `CONCERN::` token
mid-sentence in prose — including in this very task's body — is not
collected.

Two shapes exist in the wild (both in #2387's `events.jsonl`):

```
CONCERN:: BLOCKER context-blind-close-paren-overstrip Inner case/pattern close parens ...
CONCERN::backtick-comment-overstrip | BLOCKER | Backtick cmdsub interior ...
```

They differ in three ways at once: space-vs-no-space after `::`,
whitespace-vs-pipe delimiters, and **reversed field order** (canonical =
severity first; variant = id first). Classification of each collected
payload:

```
CANONICAL  iff  payload starts with a space (the historical `^CONCERN:: `)
                AND payload.split(None, 2) yields 3 parts
                AND parts[0] in CONCERN_SEVERITIES
VARIANT    iff  payload starts with a NON-space
                AND payload.split("|", 2) yields 3 parts          # maxsplit=2
                AND parts[1].strip() in CONCERN_SEVERITIES
NONE       iff  payload.strip() == "none"        (the existing sentinel)
otherwise  ->   problems.append(f"row {idx}: unparsable-concern-row")
```

**`split("|", 2)`, not an exactly-3 split (MF1).** The canonical/variant
fork is decided FIRST by space-vs-non-space, so a canonical row never
reaches the pipe split — an exactly-3 requirement would protect nothing
while converting a legitimate variant row whose free-text summary contains
` | ` into a spurious MALFORMED. That is a real class here: #2387's own
variant summaries carry `$'...'` and backtick code spans, and shell-quoting
reviews routinely discuss pipelines. With `maxsplit=2` the remainder joins
into the summary and the pipes survive verbatim.

The severity set is the discriminator because it is uppercase and closed,
so it cannot collide with a kebab-case id under `_CONCERN_ID_RE`. Both
branches normalize to the same `(severity, id, summary)` triple, so
everything downstream — dedup, `_truncate_summary`, the `raise_concern`
loop, the `none` sentinel, `_MAX_ROWS`, the all-or-nothing validation
posture — is untouched.

### 4b. Where the failure surfaces

Because classification is total, the failure rides the **existing**
`problems` path rather than a new branch: `_validate_rows` appends
`row {idx}: unparsable-concern-row`, and `main()`'s existing
`if problems: ... return 1` (lines ~204-207) prints and exits 1. This is
what makes the mixed case correct — validation is already all-or-nothing, so
one unparsable row blocks the whole marker rather than letting its siblings
mask it.

Two consequences the implementer must preserve:

- The `if raw_rows:` sole-`none` early return (line ~212) is now reached
  only when the collected set is exactly one `none` row. A `none` row plus
  an unparsable row produces a problem and exits 1 before that branch (MF2
  sub-case).
- `--validate-only` inherits the failure for free: `problems` returns 1
  ahead of any validate-only handling.

One added line in `main()` names the marker path and both formats when the
problems list contains any `unparsable-concern-row`, satisfying **A1**'s
"names the marker and the expected format":

```python
if any("unparsable-concern-row" in p for p in problems):
    print(
        f"MALFORMED: unparsable line-start CONCERN:: row(s) in {args.file}; "
        f"expected 'CONCERN:: <BLOCKER|CONCERN|NIT> <kebab-id> <summary>' "
        f"or 'CONCERN::<kebab-id> | <BLOCKER|CONCERN|NIT> | <summary>'"
    )
```

Output discipline preserved: counts, the file path, a fixed content-free
reason code, and the two literal format strings — no summary text prints.

### 4c. Exit code: reuse 1, do not mint a new one

Exit **1** (`MALFORMED`), with `unparsable-concern-row` added to the
docstring's reason-code list.

Verified against the call sites: the pre-post gate binds "Exit 1/3 =
MALFORMED → the site's stricter-retry re-dispatch (cap 2); the verdict
marker is NOT posted on this attempt" (`steps/09-step-5.md:1360-1367`), and
the resume disposition WARNs and proceeds on exit 1 with the legacy-round
reading intact, because the pre-post gate screens every post-fix posting
(`:1424-1432`). So exit 1 needs **no** call-site disposition edits, and the
recovery it selects — re-dispatch for a well-formed verdict — is the correct
one. A new exit code would require editing three disposition tables plus the
resume-recovery block for no behavioral gain.

The mechanical failure makes a misapplication *visible*; prose makes it

  scope in the concerns-persistence block.

No edit to `.claude/agents/codex-*.md`: their templates keep emitting the
canonical form only (teaching reviewers a second shape would be a
regression), and leaving them untouched avoids `c34_ratchet_headroom`
same-file cap pressure. The parser widens; the emitted contract does not.

**Accepted residual (named per MF2).** A marker that quotes the *variant*
grammar line verbatim — `CONCERN::<id> | <SEV> | <text>`, which appears in
#2387's own events.jsonl — is unspaced, splits into 3 pipe fields, and has
`field[1] == "<SEV>"`, which is not a severity. It therefore exits 1. This
is **consistent with today's behavior for the spaced template quote**
(`CONCERN:: <BLOCKER|CONCERN|NIT> <kebab-case-id> …` already yields
bad-severity → exit 1), so the widened collector introduces no new class of
surprise, only extends an existing one to the unspaced spelling. The
outcome is loud and recoverable (stricter-retry), never a silent drop. The
template's stray-token ban (`codex-code-reviewer.md:630-633`) covers only
the spaced token; widening it to the unspaced spelling is deliberately NOT
taken here (it is an `.claude/agents/*.md` edit, §12 must-ask, R4) and is
the natural follow-up if this residual ever actually fires.

## 7. Risks / failure modes

- **R1 — false-positive fail-loud breaks live review rounds fleet-wide
  (highest severity).** This tool runs at every marker-mode Codex review
  site; a spurious non-zero exit triggers a stricter-retry on healthy
  rounds, which is worse than the bug being fixed. Mitigations: the
  collector is line-start anchored (prose mentions cannot trip it); the
  widened parser makes the known variant shape *succeed*; and `maxsplit=2`
  (MF1) removes the pipe-bearing-summary class that v1 would have
  introduced. Residual reachable classes are (a) genuinely unknown shapes
  and (b) the verbatim grammar quote named in §4d — the latter consistent
  with today's spaced-template behavior. Pinned by
  `test_mid_sentence_concern_token_does_not_trip` and
  `test_variant_summary_containing_pipes_survives`.
- **R2 — discriminator mis-parse.** Closed off by the ordered fork
  (space-vs-non-space first) plus `parts[1] in CONCERN_SEVERITIES`, and
  pinned by `test_canonical_summary_containing_pipe_stays_canonical`.
  v1's exactly-3 guard is deliberately removed as ineffective (MF1).
- **R3 — `--require-block` behavior shift.** A marker carrying ONLY variant
  rows previously produced `raw_rows == []` and, under `--require-block`,
  rc=3 `missing-concerns-block`. It will now parse and persist. This is the
  intended correction, not a semantics break: the flag's predicate — "a
  missing concerns block, or a concerns heading with zero machine rows,
  exits 3" — is unchanged, and a variant-row block is neither. Round-1
  review confirmed the pre-change rc=3 behavior. Called out so a reviewer
  does not read it as an A4 violation.
- **R4 — ratchet / size-cap pressure** on `.claude/agents/*.md`. Avoided by
  not editing those files (§4d).
- **R5 — partial-ledger semantics unchanged.** Exit 4 and the per-row
  persistence loop are untouched; this plan adds no transaction. Validation
  stays all-or-nothing, which is what makes the MF2 mixed case safe.

## 11. Decision rationale

- **Accept both formats rather than pinning one** (the body's stated
  preference). The reviewers are independent by design, so a parser
  tolerating both cannot be desynced by an edit to one spec. The reversed
  field order is disambiguated by the closed severity set.
- **Exhaustive collection with total classification** rather than a
  whole-marker zero-ingest conjunction (MF2). The conjunction is not
  equivalent to the requirement: it lets an unparsable row hide beside
  valid ones, which is the exact silent-drop the task exists to close.
- **`split("|", 2)` rather than exactly-3** (MF1). The fork already
  separates canonical from variant, so arity buys no protection and costs a
  real false-positive class.
- **Reuse exit 1 rather than minting a new code** — the existing call-site
  disposition for exit 1 is already the correct recovery, verified against
  `steps/09-step-5.md:1360-1367` and `:1424-1432`.
- **Do not teach the Claude `code-reviewer` a `CONCERN::` grammar** — it
  writes the ledger directly via `task.py raise-concern` and needs no marker
  channel. The fix for the #2387 r6 misapplication is scope documentation
  plus the mechanical failure, not a second emitter.
- **No literature `Source:` rows.** Internal tooling, no hyperparameters;
  grounding is the in-repo evidence in §2. Stated rather than left blank.
