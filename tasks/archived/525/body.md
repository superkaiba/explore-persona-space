# Rebuild the ICL contexts as genuinely persona-voiced blocks (generated by a properly-prompted Claude Haiku) behind a hard behavioral manipulation-check gate, then retest cosine/JS → marker-transfer across the ICL↔SP union panel

## Goal

Retest whether base-model cosine/JS distance predicts on-policy marker transfer across the ICL↔SP union panel after rebuilding the ICL contexts to genuinely induce their personas (full in-voice example answers, validated by a hard behavioral manipulation-check gate) — testing whether #489's within-ICL no-dynamic-range, the ICL-cleaner-than-SP reversal, and the cos-vs-JS tie were artifacts of weak ICL contexts and a floor-saturated DV.

Follow-up to [#489](https://eps.superkaiba.com/tasks/489) (parent of the union ICL+SP marker-transfer panel). Inherits #489's recipe, SP arm, predictors, and DV; changes ONE thing — how the ICL contexts are constructed and validated.

## Why this exists (the #489 failure)

#489's within-ICL arm had almost no representational dynamic range (layer-21 cosine clustered at 0.90–1.00 across all 16 ICL contexts) and the planned "ICL gives a cleaner predictor than system prompts" prediction reversed. The clean-result blamed this on "where I positioned the 16 ICL contexts in residual space." The actual root cause is that **the ICL contexts barely induce the personas they are named for**, measured on the model's own generations:

| Context (diagonal cell — context inducing its OWN persona) | Persona-voice rate (keyword hit on stored samples) |
|---|---|
| Pirate **ICL** (IK12→IK12) | 46/160 (29%) |
| Pirate **system-prompt** (SP03→SP03) | 160/160 (100%) |
| Comedian **ICL** (IK13→IK13) | 25/160 (16%) |
| Comedian **system-prompt** (SP04→SP04) | 56/160 (35%) |
| neutral-ICL source → pirate-**ICL** target | 5/160 (3%) |
| neutral-ICL source → pirate-**SP** target | 159/160 (99%) |

The ICL contexts barely move the model's behavior, so they barely move its representation, so the within-ICL arm has no spread for the predictor to work on. The SP arm spreads (cosine 0.55–0.95) because system prompts actually induce distinct personas.

## Root cause (the ICL examples are hand-typed thin literals — nothing generates them)

`src/explore_persona_space/experiments/i489_contexts.py` builds all 16 ICL blocks from static Python literals; no model is in the loop. Every "persona-voiced" block (`_persona_voiced_block`) is a **fixed prefix slapped onto a neutral one-word canonical answer** from a 16-item `CONTENT_POOL`:

```python
def _persona_voiced_block(persona: str, intro_a: str):
    pairs = CONTENT_POOL[:K_DEFAULT]      # ("What is the chemical symbol for gold?", "Au."), ...
    for q, a in pairs:
        msgs.append({"role": "user", "content": q})
        msgs.append({"role": "assistant", "content": f"{intro_a} {a}"})   # "Arrr, matey! Hoist the colors: Au."
```

So the 4 "pirate" example answers are literally `"Arrr, matey! Hoist the colors: Au."`, `"...: Canberra."`, etc. Two compounding defects:

1. **Persona is a costume prefix.** The `persona=` argument is dead code (accepted, never read); only the fixed `intro_a` prefix differs. The body of every example answer is the neutral canonical answer.
2. **Even the neutral blocks are weak demonstrations.** Every CONTENT_POOL answer is one word (`"Au."`), so a 4-shot block demonstrates terse trivia answers — but the 50 probe questions are open prompts ("explain how photosynthesis works"). The example format doesn't even match the task, so the model has almost nothing to imitate. The only two ICL contexts with genuine multi-token in-style answers are IK06 (math-CoT) and IK07 (coding) — and those are structural styles, not personas, which is likely why the panel had any within-ICL signal at all.

How it got shipped: the 16 ICL contexts were inherited byte-for-byte across plan versions v2→v5 and never behaviorally re-examined; the cheap prefix helper was a placeholder that never got upgraded. The panel's whole premise (#468: example contexts spread the representation more than system prompts) assumed strong ICL induction the implementation never delivered. The one safety mechanism that should have caught it — the Phase-1 cosine band-spread coverage gate — **did fire (0/240 ICL pairs in band)**, but was overridden as "mis-calibrated" and made non-blocking. There was no *behavioral* manipulation check anywhere in the pipeline. (Same failure shape as the #496 warmth-manipulation-check-skipped incident.)

## What to change (single manipulated variable: ICL context construction + validation)

**1. Generate the ICL demonstration answers with a properly-prompted Claude Haiku — stop hand-typing literals.** For each persona/style ICL context, the K demonstration answers are generated by `claude-haiku-4-5` with a per-persona system prompt that fully specifies the voice and demands it be held across the ENTIRE answer (no break-character, no disclaimers, ~3-5 substantive sentences). The demonstration *questions* come from a separate pool of open, substantive questions (the kind that elicit multi-sentence answers) that does NOT overlap the 50 held-out probe questions. This applies to every voice/style ICL context (pirate, comedian, helpful-tutor, concise-engineer, formal, casual, Socratic) and any new ones; the structural contexts (math-CoT, coding) keep their genuine in-style answers. Generation recipe, pinned for reproducibility:

- Generator: `claude-haiku-4-5`, fixed temperature, per-persona system prompt (see validated prototype below).
- Generate ONCE, post-filter (assert the marker token ` ※` id 83399 never appears; strip stray emojis; enforce length bounds), then **freeze** the generated blocks to a committed JSON artifact (repo + HF data repo) so the panel is reproducible and not re-generated per run.
- Only the **demonstration block** is Haiku-generated. The frozen on-policy response `R` that the marker is appended to stays **Qwen base-model** generated under the context (required for on-policy measurement) — unchanged from #489.

A validated prototype (`claude-haiku-4-5`, temperature 0.7) produced genuinely in-voice, multi-sentence answers across pirate / comedian / tutor for demo questions like "How do I get better at public speaking?" — e.g. pirate: *"Arr, listen here matey, if ye be wantin' to command a room like I command the seven seas, ye must first practice yer speech upon friendly crew members..."*; comedian: *"So you wanna get better at public speaking? ... the audience WANTS you to succeed. They're not sitting there hoping you bomb—they're just hoping you finish before their coffee gets cold."*; tutor: *"What a wonderful goal! Here's the thing about public speaking—it's just like learning to swim: you get better by actually doing it, starting in the shallow end..."*. Full prototype output cached at `/tmp/i525_haiku_demo.json` (regenerate at implementation time and freeze).

**2. Add a hard behavioral manipulation-check gate (the missing control).** Before training any adapter, generate Qwen base-model on-policy responses to the held-out probe questions under each ICL context (the new Haiku-built block prepended) and judge-score (Claude Sonnet, the project's standard judge) whether each response actually adopts the intended persona/style. A context enters the panel only if its induction rate clears a pre-registered threshold (proposal: ≥70% for persona contexts). This gate **blocks** and is not overridable the way #489's cosine gate was; contexts that fail get re-generated once (stronger system prompt / more shots) or dropped, with the drop named as a scope caveat. Per-context induction rates are reported in the clean-result.

**3. K (shots).** #468 used K=8; #489 dropped to K=4. Raising K and/or the now-longer in-voice answers are the levers to clear the manipulation gate; the planner picks K grounded against #468.

Everything else inherits #489 byte-for-byte: SP arm (SP01–SP08), contrastive-negative recipe (1:1, `MarkerOnlyDataCollator`), LoRA r=16/α=32, the cosine (L21) + JS predictors, the on-policy trained−base log P(` ※`) DV + emission-rate companion, and the 24×24 cross-evaluation grid with cross-type cells.

## Known co-blocker to carry (not the manipulated variable)

#489's DV was **floor-saturated**: the marker never emitted on-policy in any cell (trained log P 15–25 nats below the emission boundary), so even a perfect ICL panel would re-run into an unmeasurable DV. The planner MUST adopt a training recipe that gets the marker off the floor — train long enough / hot enough that the diagonal marker actually emits on-policy, gated by an emission-rate smoke check before the full sweep (the #489 next-step already flagged the unscored epoch-2/epoch-3 checkpoints as the cheapest probe). Per `.claude/rules/marker-leakage-measurement.md`, do **not** swap in full-vocab KL-from-base to dodge the floor — fix the anchor, keep the marker-specific DV. Named here so the adversarial-planner decides whether it rides in this follow-up or splits into a sibling; it is a precondition for the ICL fix to be measurable.

## Acceptance criteria

- ICL demonstration answers are generated by a properly-prompted `claude-haiku-4-5`, fully in-voice across the whole answer, substantive (multi-sentence, matching probe-answer format), frozen to a committed artifact; the dead `persona=` prefix helper and one-word-answer blocks are gone.
- A behavioral manipulation-check gate exists, is Sonnet-judge-scored on Qwen's induced behavior, blocks panel entry below threshold, and its per-context induction rates are reported.
- The within-ICL cosine arm has materially more dynamic range than #489 (report the cosine-distance distribution side-by-side with #489's 0.90–1.00 cluster).
- The marker emits on-policy on at least the diagonal cells (emission rate > 0), so the cosine/JS → transfer question is measurable rather than floor-bound.
- The headline #489 questions are re-answered on the fixed panel: does the within-ICL predictor recover dynamic range, does the ICL-vs-SP comparison still reverse, and does the cos-vs-JS tie survive off-floor.
