# Plan v2 — task #718 (workflow-fix: crash-fix circuit-breaker)

## 1. Goal

Add a crash-fix circuit-breaker to the `/issue` recovery path that, when N
failures share the same `(phase, failure_class, assert-tag)` signature OR a
plan-enumerated Option A/B/... fallback set is exhausted for the same gate,
STOPS relaunching and routes to `task.py set-status <N> planning` + re-invoke
`/adversarial-planner` per `pivot_criteria.plan_contradiction_replan` — and add
the matching "enumerated-fallback-exhaustion" sub-clause to `workflow.yaml §
pivot_criteria` so the SKILL.md step and the orchestrator prose point at one
canonical predicate.

This is a `kind: infra` workflow-surface fix. The originating incident is
task **#664 round 18 (2026-06-28)**: a dispatch crash-looped through
`phase=p2 CalledProcessError` six consecutive times AND tripped a
`phase=p3 RuntimeError: [a7-assert] ... HALT (plan §11 Option A)` — i.e. both
firing conditions occurred, yet the recovery path kept relaunching instead of
recognizing the trap and re-planning. (Verified directly from
`task.py view 664 --json`: 19 `epm:failure` markers, 7 sharing the `p2 /
CalledProcessError` signature (6 consecutive — events 228-233 — then 1 after
the §11 Option A HALT — event 247), plus the literal `§11 Option A` HALT.)

## 2. Hypothesis-equivalent for code change

The circuit-breaker MUST fire on **exactly the two triggers** and ONLY those:

1. **No spurious fire** on a healthy crash-fix loop where K-1 same-signature
   rounds resolve, where the K-1 rounds were genuinely *different*
   `(phase, failure_class, assert_tag)` signatures that merely share a phase
   string, where the ladder is *incomplete* (some Option not yet attempted), or
   where a successful implementation/results marker intervenes (counter resets).
2. **The fire action is the pivot** via `plan_contradiction_replan`
   (`set-status planning` + re-invoke `/adversarial-planner` with explicit
   pivot scope), **NOT** a `status:blocked`, NOT a recipe descope, NOT a
   max-info-gain pick among paper-over options.
3. The pure-Python predicate `circuit_breaker_should_fire(events, plan_text,
   K=4)` is **side-effect-free** (no I/O), returns a fire-reason `dict` or
   `None`, and is the single source of truth that both the tests and (via the
   SKILL.md prose contract) the orchestrator consult. Its fire-reason dict
   ALWAYS carries a load-bearing `pivot_scope: str` — the difference between a
   working scoped pivot and a #488-reproducing unscoped re-plan.

Falsified if any test case in §5/§E disagrees with the predicate, if
`grep`/scoped cross-checks in §6 fail, or if the fire action is anything other
than the `plan_contradiction_replan` pivot.

### 5.3 `src/explore_persona_space/task_workflow.py` — `circuit_breaker_should_fire`

New pure function placed immediately after `failure_lesson_capture_eligible`
(after line 851), grouping it with the other pure read-only state predicates.

```python
def circuit_breaker_should_fire(
    events: list[dict[str, Any]],
    plan_text: str,
    K: int = 4,
) -> dict[str, Any] | None:
    """Decide whether the /issue Step 7 crash-fix circuit-breaker fires.

    Fires (returns a fire-reason dict) on EITHER:

    * Trigger 1 — same_failure_class: K or more ``epm:failure`` markers, since
      the last "resolved" milestone marker, share ONE
      ``(phase, failure_class, assert_tag)`` signature. The counter resets at
      any intervening ``epm:experiment-implementation`` / ``epm:results``
      milestone marker (a successful round escaped the trap). It does NOT
      reset on ``epm:progress`` (the catch-all heartbeat / phase-tick /
      watcher-respawn breadcrumb, posted DURING a still-failing trap window).
    * Trigger 2 — enumerated_fallback_exhausted: ``plan_text`` enumerates a
      finite escape ladder (``Option A -> Option B -> ...`` or a numbered
      ``Option N:`` list) for a gate, EVERY option has been launched (named in
      an ``epm:progress`` / ``epm:experiment-implementation`` note), and an
      ``epm:failure`` re-trips the same gate. Silently no-ops on free-form
      plans with no parseable ladder.

    Returns ``None`` when neither condition holds. The dict shape on fire:
    ``{"trigger": "same_failure_class" | "enumerated_fallback_exhausted",
       "signature": (phase, failure_class, assert_tag),   # trigger 1 only
       "count": int,                                       # trigger 1 only
       "ladder": [str, ...],                               # trigger 2 only
       "gate": str,                                        # trigger 2 only
       "pivot_scope": str}``  (pivot_scope ALWAYS present and non-empty —
    the ready-to-pass /adversarial-planner scope string built from the matched
    evidence; the orchestrator passes it verbatim).

    Pure: no I/O. The orchestrator owns the marker post + set-status + re-plan.
    Trigger 1 is checked first; if it fires, trigger 2 is not evaluated.
    """
```

**`pivot_scope` string templates the predicate builds** (load-bearing — the
test suite asserts these shapes, and the orchestrator passes them verbatim):

- Trigger 1 (`same_failure_class`):
  `f"Same-failure-class repetition: phase={phase} class={failure_class} "`
  `f"assert_tag={assert_tag} count={count} (K={K}). Re-plan the recipe that "`
  `f"produces this trap, or drop the gate."`
  — MUST contain the `phase`, the `failure_class` (or `"?"` if unknown), the
  `assert_tag`, and the `count` verbatim.
- Trigger 2 (`enumerated_fallback_exhausted`):
  `f"Enumerated escape ladder exhausted: gate={gate} ladder={' → '.join(ladder)}. "`
  `f"Every named alternative was launched; the gate re-tripped each time. "`
  `f"Redesign the gate or the ladder so a viable option exists, or drop the gate."`
  — MUST contain the ladder option labels joined by `" → "` and the `gate`.

**The `assert_tag` fallback chain** (this is the heart of MF#1 — ORDERED, the
FIRST rung that matches wins):

`_cb_failure_signature(note: str, prior_class: str | None) -> tuple[str, str, str]`
extracts `(phase, failure_class, assert_tag)` where:
- `phase` ← `re.search(r"phase=(\w+)", note)`, else `"?"`.
- `failure_class` ← `re.search(r"failure_class:\s*(\w+)", note)`, else
  `prior_class`, else `"?"`.
- `assert_tag` ← the first matching rung of this ORDERED chain:
  1. **Explicit field (SHOULD):** `re.search(r"assert_tag:\s*(\S+)", note)`
     → group 1.
  2. **Bracketed tag:** `re.search(r"\[([\w-]+)-assert\]", note)` → group 1.
  3. **Exception-type / command-family (NEW rung — MF#1, the primary fix):**
     a regex matching the real #664 dispatch-crash shape. Try, in order:
     - `_CB_CALLEDPROC_RE = re.compile(r"(?P<exc>\w*Error|\w*Exception): "`
       `r"Command '\[.*?(?P<script>[\w-]+\.py)")` —
       a `CalledProcessError`-style note whose argv array names a script.
       On match yield `assert_tag = f"{m['exc']}:{m['script']}"`
       (e.g. `"CalledProcessError:issue664_extract_store.py"`). The named
       `script` group anchors on the LAST `.py` basename inside the
       `Command '[...]'` argv (the actual entrypoint), NOT the interpreter
       path — the `.*?` before it is non-greedy so the regex skips
       `python3` and lands on the script, but to be robust the implementer
       MAY instead extract ALL `[\w-]+\.py` tokens from the argv and take the
       one that is NOT `python`/`python3` (specify in code; either yields the
       same basename for #664's notes).
     - else `_CB_EXC_RE = re.compile(r"^[^\n]*?\b(?P<exc>\w*Error|\w*Exception)\b")`
       applied to the note's FIRST line → `assert_tag = m["exc"]`
       (e.g. `"RuntimeError"`) — covers non-`CalledProcessError` exceptions
       and non-subprocess crashes.
  4. **Note-hash (final fallback):** `_cb_note_hash(note)`.

  Chain ordering rationale: explicit tag is most stable → bracketed `[x-assert]`
  is the next-most-stable structured token → exception-type/command-family
  catches the un-tagged subprocess-crash shape that is #664's exact case →
  note-hash is the last-resort catch-all.

**`_cb_note_hash` hardening (MF#1, the secondary defense-in-depth fix):**
`_cb_note_hash(note: str) -> str` returns `sha256(normalized)[:12]` of the
note's first non-blank line, where `normalized` strips, IN THIS ORDER:
- `\d{4}-\d\d-\d\dT[\d:Z.+-]+` ISO timestamps,
- `pid[= ]\d+` / `\bPID \d+` PIDs,
- the **subprocess argv array** — `Command '\[.*?\]'` → replaced with
  `Command '[...]'` (collapses the entire varying argv to a constant),
- any remaining `--[\w-]+(\s+\S+)?` `--flag value` runs → stripped,
- `[\w./-]+:\d+` file:line spans.
This way even a crash note that does NOT match the new exception-type rung but
DOES carry argv variation still hashes to ONE stable digest across rounds. The
exception-type rung is the PRIMARY fix (yields a human-readable tag); the
argv-strip is the SECONDARY defense (catches notes the rung misses).

Other internal helpers (module-private, same file):
- `_cb_parse_ladder(plan_text: str) -> list[str]` — returns the ordered option
  labels from the first ` → `-arrow run of `Option <X>` tokens, else from a
  numbered `Option <N>:` list; `[]` when none found.

The function reads `e["kind"]` / `e.get("note", "")` from each event dict
(matching the on-disk `events.jsonl` schema confirmed via `list_events`: keys
`ts / kind / version / by`, note under `note`). The orchestrator feeds it
`list_events(N)` + the plan text; the predicate itself never touches disk.

**Deferred refinement (noted, NOT implemented now):** extending the counter
reset set to a future explicit success-marker kind (e.g. an
`epm:milestone-resolved` convention) is a deferred refinement — do NOT
introduce it in this change. The conservative choice ships now:
`epm:progress` simply never resets the counter.

## 10. Risks

1. **False positives on a healthy crash-fix loop.** A loop where K-1 rounds
   were genuinely DIFFERENT failure classes that happen to share a phase string
   could spuriously fire if the signature were phase-only.
   *Mitigation:* the signature is the THREE-tuple `(phase, failure_class,
   assert_tag)` — narrower than phase alone; test case (c) pins that different
   signatures across K rounds do NOT fire. The intervening-milestone counter
   reset (test (f), on `epm:experiment-implementation` / `epm:results` only)
   further guards against firing on a loop that actually made progress between
   failures.
2. **Trigger-2 detection ambiguity** — the plan's "Option A → Option B"
   enumeration is prose, not a machine-readable schema.
   *Mitigation:* the predicate parses a literal ` → ` arrow run of `Option <X>`
   tokens OR a numbered `Option <N>:` list (both shapes #664's `§11 Option A`
   prose and the `plan_contradiction_replan` example match), and **silently
   no-ops on free-form plans** — a missed ladder degrades to trigger-1 only,
   never a wrong fire. The SKILL.md prose states this explicitly ("silently
   NO-OPS on free-form plans"). A future hardening could ask the planner to
   write ladders in a parseable shape, but the no-op-on-unparseable default
   means no regression for existing free-form plans.
3. **`assert_tag` adoption lag** — Option 1 (§C) makes `assert_tag:` opt-in, so
   initial deployments lack it.
   *Mitigation:* the fallback chain in §5.3 is what catches an un-tagged note —
   and the chain now includes the **exception-type / command-family rung**
   (`<ExcName>:<script_basename>`) BEFORE the note-hash, so #664's real
   un-tagged `phase=p2 / CalledProcessError` dispatch crashes resolve to the
   STABLE tag `CalledProcessError:issue664_extract_store.py` across all 6
   rounds (verified directly against `tasks/running/664/events.jsonl` events
   228-233; test (g) codifies it). This is the claim the v1 risk-3 prose made
   but could not back — v1's chain fell straight through to the note-hash,
   which hashed the 6 notes to 6 DISTINCT digests because of the volatile argv
   array, so trigger 1 never fired on its own motivating incident. The new rung
   IS the fix; the note-hash argv-strip hardening (§5.3) is the secondary
   defense for notes the rung misses. Tag adoption only TIGHTENS the signature
   over time; absence never blocks the check.
4. **~3-pivots-before-block double-counting** — if the new sub-clause counted
   toward a SEPARATE pivot counter, the orchestrator could block too late (or
   the circuit-breaker pivot wouldn't count toward block at all).
   *Mitigation:* the workflow.yaml sub-clause and the SKILL.md step BOTH state
   the circuit-breaker pivot counts toward the SAME `epm:strategy-pivot v<n>`
   counter as the existing `plan_contradiction_replan` trigger (explicit in
   5.1's "share the SINGLE `epm:strategy-pivot v<n>` counting rule" and 5.2 step
   5). No new counter is introduced.
5. **Multi-shard launch over-counting (standing recommendation, NOT a binding
   fix in v2).** A multi-shard launch (e.g. 8 shards each crashing within
   seconds of ONE `epm:run-launched`) would, under the current per-`epm:failure`
   count, register as up-to-8 same-signature "rounds" and trip the breaker on a
   single launch window. A clean fix is to collapse same-signature `epm:failure`
   markers that fall BETWEEN two consecutive `epm:run-launched` markers to ONE
   round before counting (read the events list, group failures by launch
   window, count one per window per signature). *Decision for v2:* the
   implementer MAY add this to `_cb_failure_signature` / the counting loop IF it
   can be spec'd cleanly without scope-creeping the predicate (a small helper
   `_cb_collapse_per_launch_window(events)` that the trigger-1 counter consumes);
   otherwise DEFER to a future task. #664's own incident is NOT a multi-shard
   single-window case (the 6 same-signature crashes span THREE distinct
   `epm:run-launched` windows — events 221, 226, 234 — so per-window collapse
   would still leave ≥ 3 windows and trigger 1 still fires at K=4 with the
   collapse applied; verified). So deferring this does not weaken the #664 fix.
   Noted here so the implementer and a future task both see it.

## 11. Decision Rationale

This is a `kind: infra` task — no model hyperparameters. The load-bearing
*design* choices and their grounding:

- **K=4 default (overridable via `EPM_CIRCUIT_BREAKER_K`).**
  - *What:* same-signature failure threshold = 4.
  - *Why (tied to Goal):* cap-3 is the generic "3 fundamentally different
    strategies → pivot" bar (CLAUDE.md STATE-TO-`blocked`; workflow.yaml
    `code_review_ensemble_cap_3` / `infra_respawn_cap_3`). The circuit-breaker
    is the NARROWER "same trap re-tripping" bar, so it must sit ONE round past
    cap-3 — at K=4 the generic cap-3 pivot has already had its chance to fire
    (or the orchestrator chose not to escalate it that way), so the
    circuit-breaker is a strict complement, never a duplicate.
  - *Source:* `workflow.yaml § pivot_criteria` cap-3 entries (lines 730-745);
    task #664 round 18 (7 same-signature `p2/CalledProcessError` repeats — 6
    consecutive `issue664_extract_store.py` crashes, events 228-233, then 1
    after the §11 Option A HALT, event 247 — well past K=4, confirms the
    threshold catches the real incident with margin).
  - *Alternatives:* K=3 (rejected — collides with cap-3, would fire on the
    SAME round the generic pivot fires, ambiguous double-pivot); K=5 (rejected —
    one extra wasted relaunch with no benefit; #664 shows 4 is already
    detectable).
- **`assert_tag` schema: Option 1 (recommend a SHOULD field) over Option 2
  (note-hash only), with an exception-type / command-family rung BEFORE the
  hash.**
  - *What:* add `assert_tag:` as a SHOULD field to the `epm:failure` schema
    docstring; absence falls back to the ordered chain — bracketed `[x-assert]`
    → exception-type/command-family `<ExcName>:<script_basename>` → note-hash.
  - *Why:* an explicit tag gives a clear, stable signature when present; the
    exception-type/command-family rung yields a stable, human-readable tag for
    the un-tagged subprocess-crash shape that is #664's exact case (so the
    breaker fires on its own motivating incident); the hash fallback preserves
    backward compatibility so no existing failure post breaks. Option 1 is
    strictly a superset of Option 2.
  - *Source:* `workflow.yaml § markers epm:failure` (lines 2119-2122: already
    "SHOULD include failure_class", same SHOULD register); `post_event`
    (task_workflow.py) does no field validation, confirmed backward-compatible;
    the real #664 note shapes (events 228-233, 247, verified verbatim).
  - *Alternatives:* Option 2 (note-hash only) — rejected as the SOLE mechanism
    because the volatile subprocess argv array makes per-round notes hash to
    DISTINCT digests (the #664 failure mode), AND two genuinely-distinct
    failures with similar leading lines could collide; the hardened hash is
    kept only as the FINAL fallback.
- **Trigger-2 detection: literal-arrow / numbered-Option parse with
  silent-no-op, NOT a free-form NLP parse.**
  - *What:* parse ` → `-arrow `Option <X>` runs and numbered `Option <N>:`
    lists; no-op otherwise.
  - *Why:* deterministic, testable, zero false-fire on unparseable plans; the
    two shapes cover both #664's `§11 Option A` prose and the
    `plan_contradiction_replan` worked example.
  - *Source:* #664 round-18 failure note (`HALT (plan §11 Option A)`, verified);
    `plan_contradiction_replan` existing example (lines 805-808).
  - *Alternatives:* an LLM call to parse free-form ladders (rejected — nondeter-
    ministic, untestable, overkill for a workflow gate, violates the
    model-call-vs-code rule for a structural parse); requiring planners to emit
    a machine-readable `escape_ladder:` block (deferred — a larger
    planner-contract change; the silent-no-op default ships value now without
    it).
- **Counter resets on `{epm:experiment-implementation, epm:results}` ONLY —
  `epm:progress` dropped from the reset set.**
  - *What:* the trigger-1 same-signature counter resets at an intervening
    `epm:experiment-implementation` or `epm:results` milestone, NOT at
    `epm:progress`.
  - *Why:* `epm:progress` is the workflow's catch-all marker — posted for benign
    phase transitions, watcher-respawn breadcrumbs, recovery notices,
    heartbeats, polling ticks — and it appears DURING a still-failing trap
    window. Resetting on it would make trigger 1 inert: on #664 the trap window
    between events 228 and 247 carries six benign `epm:progress` markers (235,
    236, 237, 239, 246, 248), each of which would have reset the counter under
    the v1 spec, so the counter would never reach K=4 even with the MF#1
    signature fix. `epm:experiment-implementation` / `epm:results` are genuine
    "a round actually succeeded / produced output" milestones — the right
    reset signal.
  - *Source:* `tasks/running/664/events.jsonl` (verified: the trap window's
    `epm:progress` markers vs the single `epm:experiment-implementation` at
    event 240, which IS a genuine milestone); `workflow.yaml § markers`
    descriptions of `epm:progress` as the catch-all progress marker.
  - *Alternatives:* keep `epm:progress` in the reset set (rejected — makes the
    trigger inert, as the #664 trace shows); introduce a new explicit
    `epm:milestone-resolved` kind to reset on (deferred — a new marker
    convention, out of scope for this fix; noted in §5.3 as a future
    refinement).
- **`pivot_scope` is a load-bearing predicate output (a built scope string,
  not an orchestrator afterthought).**
  - *What:* `circuit_breaker_should_fire` returns a non-empty `pivot_scope`
    string on every fire, built from the matched evidence per the §5.1 wording
    templates; the orchestrator passes it to `/adversarial-planner` verbatim.
  - *Why:* the #488 post-mortem is that an UNSCOPED re-plan reproduces the
    broken plan — the planner needs the contradiction (the repeated signature
    or the exhausted ladder) stated verbatim. A predicate that built an empty /
    generic `pivot_scope` would ship a useless #488-reproducing pivot; the §5.4
    tests assert the string shape on every fire case so an empty scope cannot
    pass green.
  - *Source:* existing `plan_contradiction_replan` pivot-action prose (lines
    803-808) which already mandates "explicit pivot scope naming the
    contradiction verbatim"; the #488 post-mortem (workflow.yaml lines 836-842).
  - *Alternatives:* leave scope-building to the orchestrator prose (rejected —
    untested, drifts, and the v1 plan's §5.4 never asserted on it, so an empty
    scope could ship green).
- **Marker reuse: `epm:strategy-pivot v<n>` REUSED, no new kind.**
  - *What:* the circuit-breaker posts the existing `epm:strategy-pivot v<n>`.
  - *Why:* `plan_contradiction_replan` already mandates this exact marker
    (line 811), and the marker schema explicitly forbids per-pivot-source kinds
    ("Every pivot site reuses this ONE kind", line 2138).
  - *Source:* `workflow.yaml § markers epm:strategy-pivot` (lines 2135-2138);
    `plan_contradiction_replan` (line 811).
  - *Alternatives:* a new `epm:circuit-breaker` kind (rejected — directly
    violates the schema's "do NOT introduce per-pivot-source marker kinds" and
    would need `--check-marker-registry` + counting-rule changes, turning a
    0-blast-radius fix into a marker-schema contract change).
