# Plan — #751 (kind: infra): failover-relaunched pods must register in pods.conf, and the recovery commands must work for an absent pod

## 0. Plan Summary

**Change:** When the async poller fails a dead/wedged run over to a fresh RunPod
pod (`scripts/backend_poll.py`), register that new pod in `scripts/pods.conf` +
regenerate SSH/MCP config — the exact registration `pod.py provision` /
`resume` already perform. And make the two documented recovery commands
(`pod.py config --update` / `--refresh-from-api`) CREATE a missing pods.conf row
from the live RunPod API instead of erroring `pod 'pod-<N>' not found in
pods.conf`. Pure infra bug fix on the workflow surface (the `backends/` router
package + the pod helper scripts), no public-contract change.

**Why:** Three independent autonomous sessions today (pod-664 / f317c8a8,
pod-658 / 6185d397, pod-697 / 3bded713) hit the same wedge: the failover
relaunched a healthy RunPod pod, but because that pod never landed in
`pods.conf`, (1) the raw-SSH poller resolved no SSH host for it and reported
`status=dead` (a FALSE alarm on a live run), and (2) BOTH documented recovery
commands refused because the pod was absent from `pods.conf`.

- **Files changed:** `scripts/pod_lifecycle.py` (factor out + export a
  `register_failover_pod(...)` helper that mirrors the provision-registration
  block at lines 1645-1659), `scripts/backend_poll.py` (call it from BOTH
  failover relaunch sites after the authoritative sidecar readback succeeds),
  `scripts/pod_config.py` (`cmd_update` + `cmd_refresh_from_api` create-missing
  from the live API).
- **Tests:** unit tests in `tests/test_backend_poll.py` (registration called on
  GCP→RunPod + wedged-RunPod failover, with a stubbed `RunPodBackend`),
  `tests/test_pod_config.py` / `tests/test_pod_config_refresh_from_api.py`
  (create-missing path for both subcommands + regression that present-pod
  behavior is unchanged), `tests/test_pod_lifecycle.py` (the new helper builds
  the right `EphemeralPod` and calls `_upsert_pods_conf` once, no nested-lock
  deadlock).
- **GPU-hours total:** 0. Workflow/infra change only.
- **Scope call:** the third proposed change ("poller cross-checks the live API
  before declaring a pod dead") is OUT of scope for #751 → split into a
  follow-up (§6). It is a behavioral change to the poller's dead-detection
  logic; this task's two headline fixes already close the reproduced wedge
  (registration fixes the false alarm at the source; create-missing fixes the
  recovery surface).
- **Top risk:** `pod_config.locked_pods_conf()` is a non-reentrant `fcntl.flock`
  on a fresh fd per call — a registration helper that holds the lock and then
  calls `_upsert_pods_conf` (which also takes it) would self-deadlock in the
  same process. Mitigation: the new helper does the (unlocked) metadata-file
  write, then calls `_upsert_pods_conf` exactly once (which takes the lock
  exactly once) — never nests the lock. A test asserts no double-acquire.

## 1. Goal

A pod launched by a failover relaunch in `scripts/backend_poll.py` is always
registered in `scripts/pods.conf` (with SSH + MCP config regenerated), and the
documented recovery commands `pod.py config --update` / `--refresh-from-api`
succeed by creating a missing row from the live RunPod API instead of erroring
when the pod is absent.

## 2. Prior Work / Current State (read from code)

The registration the failover path is missing already exists and is well-tested
for the provision/resume path:

- **`scripts/pod_lifecycle.py:448` `_upsert_pods_conf(pod: EphemeralPod)`** —
  the canonical pod-registration function: under `locked_pods_conf()` it
  `parse_pods_conf()` → mutate/append a `Pod` row → `write_pods_conf()` →

  full `EphemeralPod` (= `metadata: EphemeralMetadata` + `info: PodInfo`) and

  `scripts/pod_lifecycle.py:1645-1659`: build `EphemeralMetadata(name, pod_id,
  issue, gpu_intent, ttl_days, ...)` → `_write_metadata_file(metadata)` →
  `EphemeralPod(metadata=..., info=ready)` (where `ready` is a live-API
  `PodInfo` from `wait_for_ssh`) → `_upsert_pods_conf(pod)`. `cmd_resume`
  repeats the identical shape at lines 1985-1994.
- **The failover relaunch sites** are in `scripts/backend_poll.py`:
  - `_failover_dead_gcp_to_runpod` (~1458) — GCP workload crash → RunPod. After
    `failover_to_runpod_after_async_workload_crash` launches, the AUTHORITATIVE
    sidecar write+readback is at lines 1649-1685; the success "emit running"
    block is at 1687-1712.
  - `_relaunch_fresh_runpod` (~904, called by `_failover_wedged_runpod` ~1054
    for the RunPod RUNNING-but-no-port wedge #664) — same router call, same
    authoritative sidecar write+readback at 997-1027, success block 1028-1051.
  - Both authoritatively write a RunPod `RunHandle` to the sidecar but NEVER
    register the pod in `pods.conf` — that is the gap.
- **The recovery surface** is `scripts/pod_config.py`:
  - `cmd_update` (707) `sys.exit(1)`s at line 725-728 when the pod is absent
    from `pods.conf`.
  - `cmd_refresh_from_api` (911) `sys.exit(1)`s at line 962-965 when a
    single-named pod is absent; `_refresh_one_pod` (818) handles the
    present-row cases (live-API host/port pull, manual_override, non-RUNNING,
    no-22/tcp-mapping skips).
  - `pod-config.md` rule: the live RunPod API is authoritative for state
    (host/port/pod_id); `pods.conf` is the SSH/MCP source. `--refresh-from-api`
    is the documented "pull live API INTO pods.conf" direction. The
    create-missing extension is squarely in that direction.

**Handle vs EphemeralPod (load-bearing).** The failover handle is a frozen
`RunHandle` (`backends/base.py:162`) carrying `pod_name`, `extra["intent"]`,
`extra["issue"]`; `job_id` is `""` for RunPod launches (set in
`backends/runpod.py:293` — "we did not capture this here"), and the failover
handle's `extra` does NOT carry `ssh_host`/`ssh_port`. So the new pod's
`pod_id`, host and port can only come from the LIVE API, via
`runpod_api.get_pod_by_name(handle.pod_name)` (`runpod_api.py:813`, returns a
`PodInfo | None`). This matches the live-API-authoritative rule and the
provision path (which builds `EphemeralPod` from a live `PodInfo`), so the new
helper fetches a fresh `PodInfo` rather than trusting the handle.

## 3. Hypothesis / Expected Behavior

After the fix, a future GCP→RunPod (or wedged-RunPod) failover ends with:

- A `pods.conf` row for `pod-<N>` carrying the new pod's host/port from the live
  API.
- `~/.ssh/config` + `.claude/mcp.json` regenerated for `pod-<N>` (via
  `cmd_sync`, called inside `_upsert_pods_conf`).
- `pods_ephemeral.json` carrying `pod-<N>`'s metadata (so the audit cron, TTL,
  and `manual_override` machinery all see it).
- `pod.py config --update pod-<N> --host X --port Y` and
  `pod.py config --refresh-from-api pod-<N>` no longer erroring on an absent
  pod — they create the row from the live API.

## 4. Design (concrete change per file)

### 4a. `scripts/pod_lifecycle.py` — factor out + export the registration helper

The provision block at 1645-1659 is the registration logic to reuse, but it is
inline in `_finish_provision` and uses `args.issue` / `args.ttl_days` /
`intent_label` / a `ready` PodInfo it already holds. The failover path holds
none of those — only a `RunHandle`. So add a small public helper that takes
primitives and fetches the live `PodInfo` itself:

```python
def register_failover_pod(
    *, name: str, issue: int, gpu_intent: str = "custom", ttl_days: int = DEFAULT_TTL_DAYS,
    notes: str = "",
) -> bool:
    """Register a failover-relaunched RunPod pod in pods_ephemeral.json + pods.conf.

    Fetches the pod's live PodInfo by NAME from the RunPod API (the
    live-API-authoritative source for pod_id/host/port per pod-config.md),
    writes EphemeralMetadata, then calls _upsert_pods_conf — mirroring the
    provision/resume registration block. Returns True on success, False if the
    pod is not yet resolvable on the live API or has no SSH mapping yet (the
    caller logs + proceeds — registration is best-effort wrt the run's health).

    Does NOT raise on a transient live-API miss: a failover that launched a pod
    but cannot yet read its SSH endpoint must NOT crash the poller (the run is
    healthy; the next --refresh-from-api / a later poll re-registers it).
    """
    from runpod_api import get_pod_by_name   # lazy: heavy GraphQL module
    info = get_pod_by_name(name)
    if info is None or info.ssh_host is None or info.ssh_port is None:
        return False
    metadata = _read_metadata_file()
    metadata[name] = EphemeralMetadata(
        name=name, pod_id=info.pod_id, issue=issue,
        gpu_intent=gpu_intent, ttl_days=ttl_days, stopped_at=None, notes=notes,
    )
    _write_metadata_file(metadata)
    _upsert_pods_conf(EphemeralPod(metadata=metadata[name], info=info))
    return True
```

Notes:
- This is purely additive; `_finish_provision` is NOT refactored to call it
  (it already holds a fresher `ready` PodInfo from `wait_for_ssh` and must keep
  its bootstrap flow). Refactoring it is a non-goal — minimum change.
- `_upsert_pods_conf` early-returns when `pod.host`/`pod.port` is None, so the
  explicit `info.ssh_host`/`ssh_port` None guard above is belt-and-suspenders
  (and lets the caller log a precise "not registered yet" reason).
- The helper itself does NOT hold `locked_pods_conf()` — `_upsert_pods_conf`
  takes it exactly once. `_write_metadata_file` writes `pods_ephemeral.json`,
  a DIFFERENT file under a DIFFERENT (no) lock, so there is no nesting and no
  deadlock (§5 risk (b)).

### 4b. `scripts/backend_poll.py` — call the helper from both failover sites

In `_failover_dead_gcp_to_runpod`, immediately AFTER the authoritative readback
proves the sidecar holds a RunPod handle and BEFORE the success "emit running"
return (i.e. right after line 1690 `_clear_failover_sentinel(sentinel)`, before
the `return {...}` at 1695):

```python
# Register the failover-launched pod in pods.conf so the raw-SSH poller can
# resolve it and the documented recovery commands work for it (#751).
try:
    from pod_lifecycle import register_failover_pod
    registered = register_failover_pod(
        name=route_result.handle.pod_name,
        issue=int(issue),
        gpu_intent=str(route_result.handle.extra.get("intent", "custom")),
    )
    if not registered:
        logging.warning(
            "backend_poll: failover pod %s launched but not yet resolvable on the "
            "live RunPod API for pods.conf registration; a later poll / "
            "`pod.py config --refresh-from-api %s` will register it",
            route_result.handle.pod_name, route_result.handle.pod_name,
        )
except Exception as exc:  # noqa: BLE001 — registration must never crash a healthy failover
    logging.warning(
        "backend_poll: pods.conf registration for failover pod %s FAILED (%s: %s); "
        "the run is healthy — register manually with `pod.py config --refresh-from-api %s`",
        route_result.handle.pod_name, type(exc).__name__, exc,
        route_result.handle.pod_name,
    )
```

Apply the SAME block in `_relaunch_fresh_runpod` after its readback success
(after the sidecar readback at 997-1027 confirms `recovered.backend ==
"runpod"`, before the success return at 1028-1051), using
`route_result.handle.pod_name` / its `extra["intent"]`.

Rationale for the broad `except`: registration is a CONVENIENCE around an
already-healthy, already-authoritatively-persisted failover. A registration
failure (live-API transport hiccup, pods.conf lock contention) must NOT turn a
healthy "running" emit into a terminal failure — that would re-introduce the
exact false-`dead` the task is fixing, one layer up. This is the ONE sanctioned
broad-except in the change; it logs loud (never silent `pass`) and names the
manual recovery. It does NOT mask a fault in the run itself — the run's health
is decided entirely by the sidecar readback that already passed above.

Lazy `from pod_lifecycle import ...` inside the function mirrors the file's
existing lazy-import convention (keeps `--help` fast; `pod_lifecycle` is on
`sys.path` via the same `scripts/` injection the rest of `backend_poll` uses).

**Why a code path, not a model call?** N/A — no unstructured-data heuristics in
this design (pure config/state plumbing).

### 4c. `scripts/pod_config.py` — create-missing from the live API

**`cmd_update`** (the absent-pod branch at 725-728): instead of `sys.exit(1)`,
look the pod up on the live API and, if present + RUNNING + has a 22/tcp
mapping, CREATE the row, then apply the requested host/port override on top.
Concretely, replace the early-exit with: import `get_pod_by_name`, fetch
`PodInfo`; if absent on the live API too → keep the fail-loud `sys.exit(1)`
(genuinely nothing to create — preserves the typo guard); if present → append a
`Pod` row built from the live `PodInfo` (host/port = live ssh_host/ssh_port,
gpus/gpu_type from the PodInfo, label from the issue if derivable else the
name), then fall through to the existing under-lock update logic so the
user-supplied `--host`/`--port` override the live values and `manual_override`
is set + `cmd_sync` runs. Net effect: `--update` on an absent failover pod
creates it AND honors the manual override in one call.

**`cmd_refresh_from_api`** (single-pod absent branch at 962-965): instead of
`sys.exit(1)`, fetch `get_pod_by_name(pod_name)`; if absent on the live API too
→ keep fail-loud (typo guard); if present → append a fresh `Pod` row from the
live `PodInfo` and let the existing `_refresh_one_pod`-driven write+sync land it
(the row now exists, so the present-row path runs and writes host/port). The
bulk mode (`pod_name=None`) is UNCHANGED — it only refreshes pods already in
`pods.conf` (creating rows for every live pod in bulk would be a scope creep and
could resurrect intentionally-removed rows).

Both branches reuse the existing live-API plumbing (`list_team_pods` /
`get_pod_by_name`, `_refresh_one_pod`'s precondition checks) — the create step
is a thin "append a `Pod` from `PodInfo`" that respects the same RUNNING +
22/tcp-present preconditions `_refresh_one_pod` enforces, so we never write a
host/port-less row.

### 4d. `.claude/rules/pod-config.md` — document the new behavior

Add one bullet under "When to reach for `--refresh-from-api`": the failover

### 6. Scope decision — third proposed change → follow-up

The body's third bullet ("Poller cross-checks the live API before declaring a
pod dead on a name-resolution failure") is OUT of scope for #751. Reasoning:

- It is a behavioral change to the poller's dead-detection path (a NEW live-API
  cross-check before emitting `dead`), not a registration/recovery fix.
- The two headline fixes already eliminate the reproduced wedge: registration
  removes the cause of the false `dead` (the pod is now in `pods.conf`), and
  create-missing repairs the recovery surface. The cross-check is defense in
  depth for OTHER ways a pod could be absent from `pods.conf`.
- It needs its own design (which dead-signals warrant a live-API probe, the
  added API-call cost per poll, how it composes with the existing
  frozen-phase/drain-timeout wedge logic) and its own tests.

→ The orchestrator should file a follow-up `kind: infra` task: "poller
cross-checks the live RunPod API before emitting status=dead on an SSH
name-resolution failure" (sibling of #751). I am the planner of a workflow-fix
session under the recursion guard, so I do NOT emit a candidate block — I name

Design-decision rationale (non-hyperparameter):
- **Fetch the new pod's state from the LIVE API, not the handle.** The failover
  `RunHandle` carries `job_id=""` (RunPod, `backends/runpod.py:293`) and no
  `ssh_host`/`ssh_port` in `extra`; only the live API has pod_id/host/port.
  `pod-config.md` makes the live API authoritative for exactly these fields, and
  the provision path already builds `EphemeralPod` from a live `PodInfo`.
  `Source:` `.claude/rules/pod-config.md` + `pod_lifecycle.py:1645-1659`.
- **New public helper rather than `backend_poll` building an `EphemeralPod`
  inline.** `EphemeralPod` requires a live `PodInfo` + `EphemeralMetadata` and
  the metadata-file write; centralizing that in `pod_lifecycle` (the module that
  owns both types and `_upsert_pods_conf`) keeps the failover caller a one-liner
  and avoids `backend_poll` reaching into pod_lifecycle internals. Smallest
  change that is also the most cohesive.
- **Single-named create-missing only; bulk unchanged.** Creating a row per live
  pod in bulk could resurrect intentionally-removed rows. `Source:`
  `pod_config.py:925-933` (the documented single-vs-bulk scope split).
