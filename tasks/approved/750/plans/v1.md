# Plan v1 — #750: gate `_eps_phase done` on kernel OOM-detection (GCP backend)

## 0. Plan Summary

**Change:** add a kernel-authoritative OOM guard to the GCP startup-script
success path so an OOM-killed workload that the bash chain rc-survived can
never publish `_eps_phase done`. **Files:** `src/explore_persona_space/backends/gcp.py`
(the success-path `parts` list inside `render_startup_script`) +
`tests/test_gcp_backend.py` (new guard tests) + a DELIBERATE regeneration of
`tests/fixtures/issue588_gcp_startup_hydra_only.json` (the byte-identity
snapshot the change necessarily perturbs). **Mechanism:** render a
`_eps_oom_seen()` bash helper that reads the cgroup-v2 `memory.events` /
`memory.events.local` `oom_kill` counter (fallback: kernel journal); render
`if _eps_oom_seen; then echo ...; exit 137; fi` IMMEDIATELY after
`*workload_block` and BEFORE the watchdog reaper, so an OOM routes through
the existing EXIT trap's `rc != 0` branch (`_eps_phase failed` +
`_eps_persist_diagnostics` + `shutdown`). **Compute:** none —
`Estimated GPU-hours (total): 0`. This is a pure renderer string edit + unit
tests; no pod, no model, no data. **Scope:** workflow-surface infra only;
the optional primary-deliverable-existence check is DEFERRED to a follow-up.
**Top risk:** the byte-identity snapshot test fails by construction — the
fixture MUST be regenerated with documented provenance (not a code-bug, an
expected-drift pin).

## 2. Prior work / context

- The GCP startup script is a bash string rendered by `render_startup_script`
  (`gcp.py:896`). It runs under `set -euo pipefail` (`gcp.py:1128`). The
  `_eps_phase()` guest-attribute publisher is defined at `gcp.py:1166-1189`.
- **The EXIT trap (#607 hardening, `gcp.py:1353-1365`)** is installed at the
  TOP of the `parts` list, BEFORE the workload runs:
  ```bash
  trap 'rc=$?; set +e;
   if [ "$rc" -ne 0 ]; then
   { echo "[startup-script] FAILED rc=$rc — powering off to bound billing"; } 2>/dev/null || true;
   _eps_phase failed;
   if [ -n "${EPS_LOG_PATH:-}" ]; then { tail -n 40 "$EPS_LOG_PATH" 2>/dev/null | cut -c1-2000 >&3; } 2>/dev/null || true; fi;
   _eps_persist_diagnostics "$rc";
   shutdown -h now; fi' EXIT
  ```
  It captures `rc=$?` first, then `set +e` (so non-zero diagnostic commands
  don't abort the trap body), then runs the failure branch ONLY when
  `[ "$rc" -ne 0 ]`. `exit 137` (SIGKILL exit code, a normal non-zero rc)
  fires this branch and runs the full failure teardown — exactly the path an
  OOM'd run should have taken.
- **The async-poller failover predicate** `GcpBackend.poll` /
  `backend_poll._is_gcp_async_workload_failure` (#658/#659) is gated on
  `current_phase == "terminal_workload_failed"` — derived from
  `eps/phase==failed` + the write-once `eps/workload_started` sentinel. A
  `phase=done` posted on a failed workload (the #744 bug) bypasses this
  predicate entirely: the only downstream signal of failure becomes the
  absence of artifacts at upload-verification, which is too late (#744
  advanced to `status:verifying` with zero usable artifacts).
- **#744 evidence (from the task body):** on `eps-issue-744` (`g2-standard-4`
  / 1× L4, ~16 GB host RAM), Phase-1 `dump_and_stream.py` (pid 1553) was
  OOM-killed at `broader pass1 7350/7389` (2026-06-30T04:34:12Z); systemd
  logged `google-startup-scripts.service: Failed with result 'oom-kill'`; yet
  2s later the workload log shows `[phase=done]` and the completion sentinel
  + `eps/phase=done` guest attribute were both written. The bash chain
  (`bash X && bash Y`) returned rc=0 to the parent despite `set -euo
  pipefail` and a SIGKILLed child — the exact rc-propagation mechanism is NOT
  pinned and is OUT OF SCOPE (see §7); the kernel cgroup signal is
  independent of the chain's rc, so this fix lands regardless.

## 4. Design — the concrete patch

### 4.0 Where in the renderer the diff lands

`render_startup_script` builds the workload section in two branches
(`gcp.py:1041-1121`) assigned to `workload_block`, then assembles the final
`parts` list (`gcp.py:1126-1517`). The diff lands as **new entries in the
`parts` list**, which render as bash lines in the final script body. Two
distinct render targets:

1. **The `_eps_oom_seen()` helper definition** — added to the script
   PREAMBLE, alongside the other helper-function definitions
   (`_eps_phase()` at `gcp.py:1166`, `_eps_persist_diagnostics()` at
   `gcp.py:1209`, `_eps_reachability_watchdog()` at `gcp.py:1289`). Insert it
   immediately AFTER the `_eps_reachability_watchdog() { ... }` block closes
   (current `gcp.py:1328`, the `"}"` entry) and BEFORE the EXIT-trap entry
   (current `gcp.py:1353`). Rationale: it must be a defined function before
   the success-path call site reaches it, and grouping it with the other
   helper defs keeps the preamble coherent. It is defined under `set -euo
   pipefail`, so its body must be `set -e`-safe (it is — see 4.2).

2. **The guard call site** — added to the success path, between
   `*workload_block` (current `gcp.py:1495`) and the watchdog reaper line
   (current `gcp.py:1501`).

### 4.1 Insertion point for the guard call (chosen: BEFORE the watchdog reaper)

The current success path renders, in order (the `parts` list, `gcp.py`):

```
1495   *workload_block,                                      # workload ran (incl. detached-pid wait for workload_cmd)
1496   "",
1501   '{ kill "${EPS_WATCHDOG_PID:-}" 2>/dev/null; } || true',   # reachability-watchdog reaper (#669)
1502   "",
1503   "# === Completion sentinel (workload exited cleanly) ===",
1506   "cat > <sentinel_abs> <<EOF { \"phase\":\"done\", ... } EOF",     # sentinel heredoc
1515   "_eps_phase done",
```

**The guard goes between `*workload_block` (1495) and the watchdog reaper
(1501).** Chosen over "between the reaper and the sentinel write" for two
reasons:

- **Uniform teardown.** Putting the guard BEFORE the reaper means an OOM'd
  run does `exit 137` while `EPS_WATCHDOG_PID` is still live; the EXIT trap's
  `shutdown -h now` then reaps the watchdog along with everything else (the
  reachability watchdog's own `shutdown` ladder and the trap's `shutdown`
  are idempotent — a VM only powers off once). The clean-exit reaper at 1501
  exists specifically so a HEALTHY teardown does not let the daemon fire a
  spurious reachability shutdown; on the `exit 137` path we WANT the trap to
  own teardown, so we deliberately skip the clean reaper.
- **Earliest correct point.** By the time control reaches 1495, the workload
  has fully completed — including, on the `workload_cmd` branch, the
  detached-pid wait loop (`gcp.py:1106-1112`) that blocks until any
  self-daemonized driver pid exits. So the cgroup `oom_kill` counter reflects
  the ENTIRE workload's lifetime at the guard. Reading it here is both
  correct and the soonest we can refuse to publish `done`.

Note the guard is in the SHARED success path (after the branch-specific
`workload_block`), so it protects BOTH the `workload_cmd` branch (the #744
shape: `bash X && bash Y`) and the hydra `uv run python scripts/train.py`
branch with one insertion.

### 4.2 The `_eps_oom_seen()` helper — exact rendered bash

Rendered as a `parts` entry (a multi-line string, mirroring how
`_eps_persist_diagnostics()` is rendered as a sequence of `parts` entries
or one block). Concretely, append these entries to the helper-definition
region of `parts` (after the watchdog `"}"` at `gcp.py:1328`, before the
trap at `gcp.py:1353`):

```python
        # === OOM-detection guard (#750, incident #744) ===
        # The bash chain's rc-propagation has known weakness modes under
        # ``set -e`` + ``&&`` + SIGKILL: on eps-issue-744 a workload python
        # OOM-killed by the kernel (systemd: "Failed with result 'oom-kill'")
        # still returned rc=0 to the parent startup-script, so the success
        # path published ``_eps_phase done`` 2s after the kill and the run
        # advanced to verifying with zero usable artifacts. The kernel's
        # cgroup-v2 ``memory.events`` ``oom_kill`` counter is set whenever an
        # OOM-killer hit this cgroup, REGARDLESS of what rc the bash chain
        # reported — an authoritative cross-check the chain cannot mask. The
        # guard runs under ``set -euo pipefail``; every line is written to be
        # ``set -e``-safe (the ``grep -q`` failures + the missing-file case
        # are all in condition contexts or short-circuited, so a "no OOM"
        # result never aborts the script).
        "_eps_oom_seen() {",
        # cgroup v2: /sys/fs/cgroup/memory.events (and .local for the
        # leaf-only counter) carry a line ``oom_kill <N>``. Any N>=1 means a
        # process in this cgroup was OOM-killed since boot. ``[ -r "$f" ]``
        # guards a missing/cgroup-v1 path (returns no match, falls through).
        '  for f in /sys/fs/cgroup/memory.events /sys/fs/cgroup/memory.events.local; do',
        '    if [ -r "$f" ] && grep -qE \'^oom_kill [1-9]\' "$f"; then return 0; fi',
        "  done",
        # systemd-journal fallback for legacy cgroup-v1 images that do not
        # expose the v2 memory.events path. Fully guarded: a missing
        # journalctl / empty journal yields no match -> return 1.
        '  journalctl -k --since "10 min ago" 2>/dev/null'
        ' | grep -q "Out of memory: Killed process" && return 0',
        "  return 1",
        "}",
```

`set -e` safety of the body, line by line:
- `for ... do ... done` — loop control, not a simple command; `set -e` never
  fires on the loop construct.
- `if [ -r "$f" ] && grep -qE ... ; then return 0; fi` — the `grep -q`
  exit status is consumed by the `if` condition (a condition context), so a
  non-match (`grep` rc=1) does NOT trip `set -e`. The `&&` short-circuit
  means `grep` only runs when the file is readable.
- `journalctl ... | grep -q ... && return 0` — the `&&` makes the whole
  pipeline a condition-style compound: a `grep` non-match (rc=1) leaves the
  `&&` right side unrun and the compound's status is non-zero, BUT this is
  the LAST-before-`return 1` line and a pipeline's failure as the final
  command before an explicit `return` does not abort under `set -e` because
  control proceeds to `return 1`. (To be fully defensive and avoid any
  reliance on pipeline-`set -e` subtleties, the implementer MAY wrap it as
  `if journalctl ... | grep -q ...; then return 0; fi` — functionally
  identical, unambiguously `set -e`-safe. Either form is acceptable; the
  `if`-wrapped form is preferred and the test asserts the substring
  `Out of memory: Killed process`, not the exact `&&` shape.)
- `return 1` — explicit non-match result.

`bash -n` must pass on both rendered branches (the existing
`test_render_startup_script_is_valid_bash` covers this — see §6).

### 4.3 The guard call site — exact rendered bash

Insert as `parts` entries between `*workload_block` (`gcp.py:1495`) and the
watchdog reaper (`gcp.py:1501`):

```python
        *workload_block,
        "",
        # === Refuse to publish done on a kernel OOM the chain rc-survived ===
        # (#750, incident #744). exit 137 (SIGKILL rc) routes through the EXIT
        # trap's rc!=0 branch -> _eps_phase failed + _eps_persist_diagnostics
        # + shutdown, so the poll reads terminal_workload_failed and the
        # async GCP->RunPod failover (#659) can fire, instead of a false
        # phase=done masking a complete failure. The watchdog (still live
        # here) is reaped by the EXIT trap's shutdown, not the clean reaper
        # below -- on the failure path the trap owns teardown.
        "if _eps_oom_seen; then",
        '  { echo "[startup-script] OOM-kill detected in cgroup despite rc=0'
        ' — routing to failed (#750)" >&3; } 2>/dev/null || true',
        "  exit 137",
        "fi",
        "",
        '{ kill "${EPS_WATCHDOG_PID:-}" 2>/dev/null; } || true',
        ...
```

`set -e` safety: `if _eps_oom_seen; then ... fi` puts the helper's exit
status in a condition context (no abort on the common `return 1` / no-OOM
path). The fd-3 echo is `{ ...; } 2>/dev/null || true`-guarded exactly like
every other fd-3 heartbeat in the script (closed-pipe-safe under the `trap
':' PIPE` handler at `gcp.py:1150`). `exit 137` then deterministically fires
the EXIT trap.

  manifest contract that is out of scope for a minimal OOM fix.

A workload that legitimately tolerates a child OOM is not a pattern this project runs; if one arises, it can opt out via a future env knob. Better a conservative false-failed than a false-done masking a real failure. |
| **`exit 137` mis-handled by the EXIT trap** | None | The trap captures `rc=$?` (= 137), runs `set +e`, and the `[ "$rc" -ne 0 ]` guard is TRUE for 137 → full failure teardown fires (`_eps_phase failed` + `_eps_persist_diagnostics 137` + `shutdown -h now`). 137 is an ordinary non-zero rc; nothing in the trap special-cases it. The poll then reads `eps/phase=failed` + the write-once `eps/workload_started` sentinel (set when the workload phase was entered) → `terminal_workload_failed` → async GCP→RunPod failover can fire. |
| **The deeper bash-chain rc-propagation bug is NOT fixed** | Known / accepted | This plan does NOT pin down WHY the #744 chain returned rc=0 under `set -euo pipefail` with a SIGKILLed child. The cgroup check is kernel-authoritative and INDEPENDENT of the chain's rc, so the fix lands regardless. | **`grep -qE` regex portability** | Negligible | `^oom_kill [1-9]` is POSIX ERE; `grep -E` is standard on the DLVM image. The pattern matches `oom_kill 1`..`oom_kill 9...` and correctly excludes `oom_kill 0` (the healthy case). |
