## 0. Plan Summary

RUNNING-but-no-public-port on a degraded host, bills indefinitely, is
unrecoverable via host-pinned stop+resume, and strands hours of fleet-eval work
because eval artifacts upload only in one terminal batch. Two independent code
fixes + two doc-surface updates + scoped follow-up decisions.

- **Fix (a) — per-cell incremental upload** in `scripts/issue664_dispatch.py`:
  upload each cell's eval JSONs + store tensors the moment its

## Section A — per-cell incremental upload (fix (a))

### A.1 Goal

Persist each fleet-eval cell's primary deliverables (eval JSONs + store
tensors) the moment that cell's extract+eval worker succeeds, so a mid-sweep pod
death loses at most one in-flight cell rather than every not-yet-P3-uploaded
cell. Success criterion: re-running `extract_and_eval_cell` on a cell whose
artifacts are already on the Hub skips that cell's upload; P3
`upload_artifacts` becomes an idempotent safety sweep that re-uploads only cells
NOT already on the Hub.

### A.2 Prior work

`scripts/issue664_dispatch.py` already has the precedent: `train_lora` uploads +
Hub-verifies each adapter INLINE per cell (`_verify_adapter_on_hub`, L951-959,
called at L947), which is why #664's adapters survived but its eval JSONs did
not. The three P3 upload helpers — `_upload_raw_completions` (L1204, walks
`EVAL_ROOT/registry/<cell>/completions__*.json` → `issue664_leakage_fleet/raw_completions/<cell>/...`),
`_upload_store_tensors` (L1253, walks `STORE_ROOT/<cell>/tensors.pt` →
`theory_assumptions/Qwen2.5-7B-Instruct/issue664/<cell>/...`), and
`_upload_baseline_propensity` (L1120, a Phase-0 aggregate at
`issue664/baseline_propensity/...`) — all use `hub._upload(..., upload_as_file=True)`
per file with a FRESH-listing Hub-verify. The `code-style.md` § "Checkpoint per
phase; never accumulate-in-memory and write-at-end" rule names this exact gap as
the anti-pattern. The HF prefixes/roots live in `scripts/issue664_common.py`
(`HF_DATA_REPO`, `HF_RAW_COMPLETIONS_PREFIX`, `HF_STORE_PREFIX`, `EVAL_ROOT`,
`STORE_ROOT`, `Cell.eval_key`).

### A.3 Design

**File:** `scripts/issue664_dispatch.py`.

**New helper `_upload_cell_artifacts(cell, *, smoke) -> None`** (placed near the
P2 cell workers, ~after L1004). Uploads THIS cell's eval JSONs + store tensors as
ONE `upload_folder` commit per artifact-kind, idempotent against a fresh Hub
listing, fail-loud. Note: baseline propensity is a Phase-0 aggregate, NOT
per-cell — it stays only in P3.

```python
def _cell_artifacts_on_hub(cell: C.Cell) -> bool:
    """True iff this cell's eval JSONs AND store tensors are already on the Hub.
    FRESH listing (Python Hub API, never the hf CLI — upload-policy)."""
    from huggingface_hub import list_repo_files
    files = set(list_repo_files(C.HF_DATA_REPO, repo_type="dataset", revision="main"))
    raw_prefix = f"{C.HF_RAW_COMPLETIONS_PREFIX}/{cell.eval_key}/"
    store_prefix = f"{C.HF_STORE_PREFIX}/{cell.eval_key}/"
    have_raw = any(p.startswith(raw_prefix) for p in files)
    have_store = any(p.startswith(store_prefix) for p in files)
    return have_raw and have_store

def _upload_cell_artifacts(cell: C.Cell, *, smoke: bool) -> None:
    """Per-cell incremental upload (checkpoint-per-phase). One upload_folder
    commit per artifact-kind (HF 256-commits/hr cap). Idempotent: skip when
    already on the Hub. Fail-loud Hub-verify before returning."""
    if smoke:
        logger.info("[p2-upload] smoke: skipping per-cell HF upload")
        return
    if _cell_artifacts_on_hub(cell):
        logger.info("[p2-upload] %s already on Hub; skipping", cell.eval_key)
        return
    from huggingface_hub import HfApi
    api = HfApi()
    # eval JSONs: eval_results/issue_664/registry/<cell>/  ->  raw_completions/<cell>/
    eval_dir = C.EVAL_ROOT / "registry" / cell.eval_key
    if eval_dir.exists() and any(eval_dir.iterdir()):
        api.upload_folder(
            folder_path=str(eval_dir), repo_id=C.HF_DATA_REPO, repo_type="dataset",
            path_in_repo=f"{C.HF_RAW_COMPLETIONS_PREFIX}/{cell.eval_key}",
            allow_patterns=["completions__*.json"],
            commit_message=f"[i664 per-cell] eval JSONs {cell.eval_key}",
        )
    # store tensors: trained_store/<cell>/  ->  theory_assumptions/.../issue664/<cell>/
    store_dir = C.STORE_ROOT / cell.eval_key
    if store_dir.exists() and any(store_dir.iterdir()):
        api.upload_folder(
            folder_path=str(store_dir), repo_id=C.HF_DATA_REPO, repo_type="dataset",
            path_in_repo=f"{C.HF_STORE_PREFIX}/{cell.eval_key}",
            commit_message=f"[i664 per-cell] store tensors {cell.eval_key}",
        )
    if not _cell_artifacts_on_hub(cell):  # FRESH-listing verify, fail-loud
        raise RuntimeError(
            f"[p2-upload] per-cell upload verify FAILED for {cell.eval_key}: "
            f"eval JSONs and/or store tensors not on Hub after upload_folder"
        )
    logger.info("[p2-upload] %s eval JSONs + store tensors uploaded + verified", cell.eval_key)
```

L984 (extract) and L996 (gen); the merged dir is reaped in the `finally` at
L997-1002. The per-cell upload call goes AFTER the gen worker `subprocess.run`
succeeds (after L996) and BEFORE the `finally` reaps the merged dir — i.e. once
both `_cell_extract_eval_done` final artifacts (store `tensors.pt` + non-empty
eval registry dir) exist on the pod volume:

```python

        # --- NEW: per-cell incremental upload (fix (a), checkpoint-per-phase) ---
        # Both final artifacts now exist on the pod volume (the _cell_extract_eval_done
        # invariant). Push THIS cell to HF so a pod wedge (#664) strands at most this
        # one in-flight cell, never the whole sweep. Idempotent + fail-loud.
        if not smoke:
            _upload_cell_artifacts(cell, smoke=smoke)
    finally:
        if merged.exists():
            ...
```

**P3 `upload_artifacts` (L1108) becomes an idempotent safety sweep.** The three
existing helpers already verify on a fresh listing and are themselves idempotent
(re-uploading an identical file is a no-op commit on HF). The minimal,
lowest-risk change: have `_upload_raw_completions` and `_upload_store_tensors`
each skip a cell whose artifacts are already on the Hub (re-using
`_cell_artifacts_on_hub`), so P3 only re-uploads cells the per-cell hook missed
(e.g. a cell uploaded by an OLDER dispatcher revision, or a cell whose per-cell
upload was interrupted between the two `upload_folder` commits). `_upload_baseline_propensity`
is UNCHANGED (Phase-0 aggregate, never per-cell). The P3 fail-loud verify at the
end stays — it remains the authoritative "everything is on HF before teardown"
gate.

Concretely, in `_upload_raw_completions` (L1204) and `_upload_store_tensors`
(L1253), the per-cell loop gains a skip-if-on-Hub guard at the top of each cell
iteration, computed ONCE from a single fresh listing taken at function entry (not
per-cell, to avoid N Hub round-trips):

```python
    on_hub = set(list_repo_files(C.HF_DATA_REPO, repo_type="dataset", revision="main"))
    # ... per cell:
    cell_prefix = f"{prefix}/{cell.eval_key}/"   # or per-file rel for raw completions
    if any(p.startswith(cell_prefix) for p in on_hub):
        logger.info("[p3-upload] %s already on Hub (per-cell); skipping", cell.eval_key)
        continue
```

**Why code, not a model call?** N/A — no unstructured-data heuristics; this is
pure artifact I/O against the HF Hub API.

### A.4 Acceptance criteria

- Re-running `extract_and_eval_cell` on a cell whose eval JSONs + store tensors
  are already on the Hub SKIPS the `upload_folder` calls and returns without a
  new commit (verified by mocking `list_repo_files` to return the cell's
  prefixes + asserting `upload_folder` is NOT called).
- A fresh cell (not on Hub) triggers exactly TWO `upload_folder` commits (eval
  JSONs + store tensors), then the fresh-listing verify passes (mock
  `list_repo_files` to return the prefixes only on the SECOND call).
- The verify is fail-loud: if the post-upload listing lacks the cell prefixes,
  `_upload_cell_artifacts` raises `RuntimeError`.
- P3 `upload_artifacts` skips a cell already uploaded per-cell (no
  re-`upload_folder`) and proceeds to the next; the terminal P3 verify still
  asserts every selected cell is on the Hub.
- `smoke=True` short-circuits the per-cell upload (mirrors the existing P3 smoke
  skip).

### A.5 Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| HF 256-commits/hr cap | Low | One `upload_folder` per artifact-kind per cell = 2 commits/cell; a 16-32-cell sweep is ≤64 commits/hr, well under 256. `upload_folder` batches all files of a cell-dir into ONE commit (upload-policy § HF Hub rate limit). |
| Extra Hub round-trip per cell (the `_cell_artifacts_on_hub` listing) | Medium | One `list_repo_files` call per cell (cheap, seconds). Acceptable for the durability win; the listing is also the idempotency check that makes re-runs free. |
| P3 skip-guard listing race (a cell finishes between the entry listing and its iteration) | Low | The guard is a per-function single listing; a missed skip just re-uploads (idempotent no-op commit), never loses data. The terminal verify is authoritative. |

## Section B — RunPod RUNNING-but-no-port wedge: detect + auto-migrate (fix (b))

### B.1 Goal

Detect a RunPod pod that is `desiredStatus=RUNNING` with null/empty
`runtime.ports` for ≥ K=900s (host-pinned stop+resume cannot heal it), stop the
billing leak via `terminate_pod`, and auto-migrate by re-provisioning fresh +
resuming the dispatcher idempotently — but ONLY when every recoverable input is
HF-verified. Success criterion: on the next pod that wedges this way, the poller
escalates to a terminal wedged phase, the failover path fires (terminate +
re-provision), and the run continues on a fresh pod without human intervention;
a pod whose inputs are NOT yet on HF is NOT terminated (it surfaces a
`failure_class: infra` block instead so a human decides).

### B.2 Prior work — the GCP architecture mirror (#669)

`scripts/backend_poll.py` carries the GCP wedge → failover machinery this fix
mirrors, side-by-side:

- `GCP_WORKLOAD_WEDGED_PHASE = "terminal_workload_wedged"` (L87) — the synthesized
  terminal phase.
- `GCP_STALENESS_FLOOR_SEC = 900` (L104) — 15-min staleness floor.
- `_maybe_escalate_gcp_wedge(handle, result, sidecar, *, now)` (L329-384) —
  reads a sidecar phase-clock, and IF (phase frozen past the floor) AND
  (`result.reachability_alarm`) rewrites the poll to `status="dead",

- `_is_gcp_async_workload_failure(handle, result)` (L220) — narrow-by-construction
  predicate gating the failover (GCP handle + dead + phase in the accept-set).
- `_failover_dead_gcp_to_runpod(*, issue, handle, result, sidecar)` (L639) — the
  recovery: reconstruct a `RunSpec`, launch the RunPod terminal rung,
  authoritatively re-point the handle sidecar, idempotency-guarded (durable
  lease + sentinel) so a re-fire cannot double-launch.
- The wiring in `main()` (L994-1024): `result = backend.poll(handle)` →
  `_maybe_escalate_gcp_wedge(...)` (L1002) → `if _is_gcp_async_workload_failure(...)`

### B.3 Design — chosen surface: `scripts/backend_poll.py` (NOT `pod_lifecycle.py`)

**Choice + justification.** The body proposed EITHER `pod_lifecycle.py` OR
`backend_poll.py` + `backends/runpod.py`. **Chosen: `backend_poll.py`** (with a
thin recovery helper that re-uses the existing router failover plumbing). Three
reasons:

1. **The architecture mirror lives in `backend_poll.py`.** Placing the RunPod
   sibling next to `_maybe_escalate_gcp_wedge` / `_failover_dead_gcp_to_runpod`
   keeps both backends' wedge logic side-by-side, lets the RunPod failover re-use
   the GCP path's idempotency-lease + sidecar-repoint plumbing, and makes the
   poll-tick the single place that observes "RUNNING but unreachable for too
   long" (the poller already runs every tick with the handle + sidecar in hand).
2. **`cmd_resume` is the wrong layer.** `cmd_resume` runs once, interactively, on
   an explicit `pod.py resume` — it does NOT run on the autonomous poll cadence,
   so it cannot DETECT a wedge that develops minutes into a run. The `cmd_resume`
   advice fix is the separate, complementary follow-up concern (c2) below
   (split the `--refresh-from-api` advice), not the detection mechanism.
3. **`runtime.ports`-null is a POLL observation, not a resume observation.** The
   poll already has the handle; reading the pod's live `desiredStatus` +
   `runtime.ports` is one `get_pod` call, exactly where the GCP wedge reads
   `eps/phase` freshness.

# RUNNING with null/empty runtime.ports past this floor is on a degraded host:

New escalation helper (sibling of `_maybe_escalate_gcp_wedge`, ~after L384):

```python
def _maybe_escalate_runpod_wedge(handle, result, sidecar: Path, *, now: float):
    """Escalate a RunPod pod RUNNING-but-no-port past K to terminal wedged (#664).

    Sibling of _maybe_escalate_gcp_wedge: a poller-side staleness clock kept in
    the poller (NOT inside RunPodBackend.poll, so poll stays a pure function).
    Returns the SAME result UNLESS the pod is a RunPod handle whose LIVE
    desiredStatus is RUNNING with null/empty runtime.ports, unchanged past
    RUNPOD_WEDGE_K_SEC. Re-stamps the no-port clock on first observation / on a
    state change (port appears, or status leaves RUNNING).

    False-positive guards (return result unchanged):
      * not a RunPod handle  -> unchanged;
      * the live pod EXPOSES a public port (healthy)  -> clear the clock, unchanged;
      * desiredStatus != RUNNING (EXITED/terminal)  -> clear, unchanged;
      * within the K floor (covers the normal boot/resume window)  -> unchanged.
    """
    if getattr(handle, "backend", None) != "runpod":
        return result
    from runpod_api import get_pod_by_name  # live RunPod API (X-Team-Id baked in)
    info = get_pod_by_name(handle.pod_name)   # PodInfo or None
    healthy_or_terminal = (
        info is None                                   # gone -> ordinary dead path
        or info.desired_status != "RUNNING"            # EXITED/terminal -> not a wedge
        or (info.ssh_host and info.ssh_port)           # public port present -> healthy
    )
    if healthy_or_terminal:
        _clear_runpod_noport_clock(sidecar)
        return result
    # RUNNING + no public port: start/continue the no-port clock.
    first_seen = _read_runpod_noport_clock(sidecar)
    if first_seen is None:
        _write_runpod_noport_clock(sidecar, ts=now)
        return result
    wedged_for = now - first_seen
    if wedged_for > RUNPOD_WEDGE_K_SEC:
        logging.warning(
            "backend_poll: RunPod %s RUNNING-but-no-port for %.0fs (>%ds K floor) "
            "— host-pinned resume cannot heal; escalating to %s (#664 wedge)",
            handle.pod_name, wedged_for, RUNPOD_WEDGE_K_SEC, RUNPOD_WORKLOAD_WEDGED_PHASE,
        )
        return replace(
            result, status="dead", current_phase=RUNPOD_WORKLOAD_WEDGED_PHASE,
            new_milestone=True, pid_alive=False,
        )
    return result   # within the K floor -> still running
```

The no-port clock helpers (`_read_runpod_noport_clock` /
`_write_runpod_noport_clock` / `_clear_runpod_noport_clock`) re-use the
sidecar `extra` dict exactly like `_read_phase_clock` / `_write_phase_clock`
(L300-326), keyed `runpod_noport_first_seen_ts` (distinct from the GCP
`last_phase_change_ts`), atomic tmp+rename, never raising (a clock-write failure
logs + the next tick re-reads stale state, never manufactures a wedge — same
contract as the GCP clock).

New recovery (sibling of `_failover_dead_gcp_to_runpod`, ~after L639):

```python
def _failover_wedged_runpod(*, issue: int, handle, result, sidecar: Path) -> dict:
    """Terminate a wedged RunPod pod + re-provision fresh, idempotently (#664).

    PRECONDITION (fix (a) dependency): every recoverable input must be HF-verified
    BEFORE the terminate fires. Adapters are uploaded+verified inline by train_lora
    (_verify_adapter_on_hub); eval JSONs + store tensors require fix (a)'s per-cell
    upload. We verify the run's expected per-cell artifacts are on HF; if ANY are
    missing, we DO NOT terminate — we emit a terminal infra JSON
    (reason='runpod_wedge_inputs_unverified') so a human decides (CLAUDE.md
    halt-criterion #2 — irreversible terminate is gated on data safety).

    Idempotency: a durable lease (~/.eps-routing/, keyed to the wedged pod_id) +
    a sidecar sentinel guard the terminate+re-provision, exactly as
    _failover_dead_gcp_to_runpod guards its relaunch, so a re-fired wedge on the
    next tick cannot double-terminate / double-provision.
    """
    # 1. IDEMPOTENCY SHORT-CIRCUIT (sentinel + durable lease keyed to wedged pod_id).
    #    If we already terminated+reprovisioned this pod_id on a prior tick, the
    #    sidecar now points at the NEW pod; this predicate fires only on the OLD
    #    handle, so the lease/sentinel match bails out.
    if _runpod_wedge_already_handled(issue, handle, sidecar):
        return _terminal_infra_json(issue=issue, sidecar=sidecar,
            reason="runpod_wedge_already_handled", log_tail="...")

    # 2. INPUTS-ON-HF GATE (fix (a) precondition). Verify the run's per-cell
    #    artifacts are on HF before the irreversible terminate.
    if not _wedged_run_inputs_on_hf(issue, handle):
        return _terminal_infra_json(issue=issue, sidecar=sidecar,
            reason="runpod_wedge_inputs_unverified",
            log_tail=(f"RunPod {handle.pod_name} wedged (no port) but per-cell "
                      f"inputs not all on HF; refusing irreversible terminate "
                      f"(CLAUDE.md halt-criterion #2). Human decision needed."))

    # 3. TERMINATE the billing leak (fail-loud; terminate_pod raises on API error).
    from runpod_api import terminate_pod, get_pod_by_name
    info = get_pod_by_name(handle.pod_name)
    if info is not None:
        terminate_pod(info.pod_id)
        logging.warning("backend_poll: terminated wedged RunPod %s (%s) — billing stopped",
                        handle.pod_name, info.pod_id)

    # 4. RE-PROVISION FRESH + resume the dispatcher via the SAME RunPod terminal
    #    rung the GCP failover uses (a fresh pod, NOT a host-pinned resume),
    #    re-point the handle sidecar, durable-lease stamp. Returns a RUNNING-shaped
    #    JSON so the orchestrator keeps polling the new pod.
    return _relaunch_fresh_runpod(issue=issue, handle=handle, result=result, sidecar=sidecar)
```

`_relaunch_fresh_runpod` re-uses the router's
`failover_to_runpod_after_async_workload_crash` (the same function
`_failover_dead_gcp_to_runpod` calls at L710) — it reconstructs a `RunSpec` from
the handle and launches a fresh RunPod run (`podFindAndDeployOnDemand`, NEW host,
NOT a host-pinned resume), writes+readbacks the sidecar, and is durable-lease
guarded. `_wedged_run_inputs_on_hf` checks the run's expected artifacts via
`huggingface_hub.list_repo_files` (for #664: the selected cells' raw-completion +
store-tensor prefixes, mirroring fix (a)'s `_cell_artifacts_on_hub`); it is a
GENERIC predicate keyed on the handle's issue so it stays reusable for non-#664
dispatchers (a dispatcher that does not declare per-cell artifacts passes the
adapters-only check, since adapters are always inline-verified).

### 11. Decision rationale

**K-seconds wedge-detection threshold.**
- **What:** `RUNPOD_WEDGE_K_SEC = 900` (15 min), env-overridable via
  `EPM_RUNPOD_WEDGE_K_SEC`.
- **Why:** A wedge must be distinguished from the normal boot/resume window.
  `runpod_api.wait_for_ssh` polls with a 600s timeout (verified at L723); a
  healthy pod exposes its port well within that window. K=900s = 600s + a
  300s retry margin guarantees the floor sits ABOVE the longest legitimate
  no-port interval, so a healthy mid-resume pod never trips.
- **Source:** `backend_poll.py:GCP_STALENESS_FLOOR_SEC = 900` (L104) — a prior
  internal decision (#669) for the GCP sibling; this is an exact mirror, which
  also keeps both backends' wedge floors identical (one mental model). The
  `wait_for_ssh timeout=600` lower-bound is `runpod_api.py` L723.
- **Alternatives considered:** 600s (= bare `wait_for_ssh`) — rejected, leaves no
  retry margin and could trip on a slow-but-healthy port mapping; 1800s — rejected,
  doubles the billing-leak window for no detection benefit and diverges from the
  GCP floor.

**HF rate-limit batching strategy.**
- **What:** one `upload_folder` commit per artifact-kind per cell (eval JSONs +
  store tensors = 2 commits/cell), NOT per-file commits.
- **Why:** `huggingface_hub` enforces 256 repository commits/hr. A per-FILE loop
  (the existing P3 `hub._upload(..., upload_as_file=True)` shape, one commit per
  file) would blow the cap on a multi-file-per-cell sweep; `upload_folder`
  batches an entire cell-dir into ONE commit. A 16-32-cell sweep is ≤64
  commits/hr, well under the cap.
- **Source:** `.claude/rules/upload-policy.md` § "HF Hub rate limit: 256
  repository commits per hour" + incident #488 (41/324 silent upload losses from
  per-cell commits; backfilled with a single bulk `upload_folder`).
- **Alternatives considered:** keep per-file `hub._upload` per cell — rejected,
  multiplies commits by files-per-cell and risks the cap; one bulk commit for the
  WHOLE sweep at the end — rejected, that IS the write-at-end anti-pattern #664
  exposed (the whole point is per-cell durability).

**Terminate authority (auto-terminate alignment with CLAUDE.md).**
- **What:** fix (b) auto-`terminate_pod`s a wedged pod WITHOUT a user-ask, but
  ONLY after `_wedged_run_inputs_on_hf` confirms every recoverable input is
  HF-verified; inputs-unverified → no terminate, `failure_class: infra` block.
- **Why:** CLAUDE.md "STATE-TO-`blocked` criteria #2" lists `terminate` among
  irreversible actions that "always ask" BY DEFAULT. The ONLY existing automated
  terminate is `/issue` Step 8, which terminates on upload-verification PASS — i.e.
  terminate is already accepted as autonomous when the data is safe. Fix (b)'s
  auto-terminate is analogous IFF fix (a) is in place: per-cell uploads make the
  auto-terminate's data-loss surface equivalent to Step 8's (every recoverable
  artifact is on HF before the destroy). This is exactly why fix (a) is the
  stated prerequisite. A wedged pod with inputs NOT yet on HF is NOT terminated —
  it surfaces a block for a human, preserving the halt-criterion's default for the
  data-unsafe case.
- **Source:** `.claude/skills/issue/SKILL.md` § Step 8 "PASS → teardown the
  compute" (the auto-terminate-after-upload-PASS precedent) + CLAUDE.md
  "STATE-TO-`blocked` criteria #2". Incident #664 (the billing leak this stops);
  #488 (the 13h+ billing leak the inverse — host-pinned resume — caused).
- **Alternatives considered:** never auto-terminate, always block for a human —
  rejected, that leaves the billing leak open for the whole human-response latency
  (the #664/#488 cost); auto-terminate unconditionally — rejected, violates the
  halt criterion for the data-unsafe case (would destroy unrecoverable work).

**Detection surface (`backend_poll.py` vs `pod_lifecycle.py`).**
- **What:** the wedge detection + failover live in `backend_poll.py`, NOT
  `cmd_resume`.
- **Why:** the GCP architecture mirror is in `backend_poll.py`, so the RunPod
  sibling sits beside it and re-uses its idempotency + sidecar-repoint plumbing;
  `cmd_resume` runs once interactively and cannot DETECT a wedge that develops on

- **Source:** `backend_poll.py` L329/L639/L1002/L1016 (the GCP wiring this
