# Plan — Task #606: Does the LoRA vs full-FT bystander-leakage equivalence hold for realistic behaviors (sycophancy, refusal)?

## 0.0 TL;DR (plain English)

<section class="plan-tldr">

- **What I'll run:** Earlier work (#514) showed that for a tiny artificial behavior (a single marker token), LoRA and full fine-tuning spread the trained behavior to other personas by the same amount, once you compare them at the same implant strength. I'll check whether that holds for two realistic behaviors: agreeing with users' false claims (sycophancy) and refusing harmless questions. I train each behavior into a "software engineer" persona twice — once with LoRA, once with full fine-tuning — saving checkpoints along the way, then compare how much each method bleeds the behavior into the 38 other personas (23 roster + 15 synthesized twins; the source itself is excluded from every headline mean) at the point where both methods have installed the behavior equally hard.
- **What I expect:** Published comparisons say LoRA changes off-target behavior less than full fine-tuning, so if the marker result fails to generalize, full fine-tuning should leak more. My weak bet is the marker result holds and the two methods leak the same.
- **What would change my mind:** A clear gap at matched strength on either behavior. That would mean the LoRA-only shortcut the whole leakage program relies on is method-specific for real behaviors, and the project's published leakage numbers carry an unstated method dependence.

</section>

## 1. Goal

Test whether the LoRA vs full fine-tuning equivalence in bystander leakage — established at matched source-implant strength for the single-token marker in #514 (gap +0.00 nat, 95% CI [−0.13, +0.12]) — generalizes to realistic behavior implants. Sycophancy is the mandatory primary arm; refusal is included (it fits the budget); emergent misalignment is specified as a named follow-up child task. Each behavior is trained into the `software_engineer` source persona with both methods on identical data; the comparison is the on-policy, judge-scored per-persona leakage profile at matched source-implant strength, below ceiling. If equivalence holds, the LoRA-only default is secured for the whole behavior-leakage program; if it diverges, #514 is flagged as behavior-class-specific and the direction/size of the gap becomes a finding in itself.

**Literature (citations verified via arXiv MCP):**

- Biderman et al., *LoRA Learns Less and Forgets Less*, arXiv **2405.09673**: LoRA better maintains base-model behavior outside the target domain; full FT learns perturbations of 10–100× higher rank. ## 3. Hypothesis

Strength dial per behavior: **s = source-self judge-scored rate delta (trained − base)** measured on-policy on the source persona's own panel. Matched target **s\* = 0.50** (max headroom from floor 0 and observed ceilings 0.914/0.994), band [0.40, 0.60]; secondary read at s\* = 0.75.

- **H1 (equivalence generalizes — weak prior, ~55%):** at s\* = 0.50, panel-mean leakage gap (FT − LoRA) has 95% CI ⊂ (−0.05, +0.05) AND per-persona profile Spearman ρ(LoRA, FT) ≥ 0.7, for both behaviors. Confirms the #514 null as method-level, not marker-specific.
- **H2 (divergence, FT > LoRA — directional alternative per 2405.09673):** gap CI excludes 0 with point estimate ≥ +0.05 (or ≤ −0.05 for the reverse sign), OR profile ρ < 0.4 with CI upper bound < 0.7. Falsifies generalization; the per-persona profile says *where* the methods differ.
- **Indeterminate:** anything else (e.g. CI spans 0 but exceeds ±0.05 width) — reported as such, never rounded to a null.
- **Kill criteria (pre-registered, reconciler-revised):** (a) **install failure** = an arm that NEITHER brackets s\* = 0.50 with non-degenerate selected cells NOR reaches endpoint s ≥ 0.50 — that behavior's comparison is not run, reported as exactly that. An endpoint s in [0.50, 0.60) with a valid s\*-bracket PROCEEDS to the primary matched read (endpoint s ≥ 0.6 is reserved for *labeling* install strength and for s\* = 0.75 secondary-read availability — it is NOT a proceed condition; reconciler binding fix 2, closing the false-kill where an in-band endpoint would have killed an arm the fallback ladder explicitly saves); (b) FT degenerate-collapse (>50% of source-self stage-A responses degenerate: <5 chars or >80% repeated 3-grams) at every checkpoint with s ≥ 0.4 → fall back to the band-entry ladder and report; (c) no checkpoint pair brackets s\* on an arm → pre-registered fallback read (§4, band-entry comparison), reported as a scope limitation, not silently interpolated across the jump.

### 4.4 Matched-strength protocol (the #514 lesson, transplanted)

- Stage-A measures s(step) per arm: source-self judged rate minus base source-self rate, 500 verdicts per checkpoint.
- **Selection rule (pre-registered):** isotonic-regression smooth of s(step); per arm pick (i) the adjacent grid pair bracketing the smoothed s\* = 0.50 crossing, (ii) the checkpoint with smoothed s closest to 0.75, (iii) the endpoint (step 132). 4 cells/arm.
- **Matched read:** per persona, linear interpolation of leakage delta in s between the bracket cells, evaluated at s\* = 0.50; gap = FT − LoRA; 10,000-rep crossed cluster bootstrap over (claims × personas) on per-rollout verdicts, re-estimating s and re-interpolating inside each replicate. Determinacy gate: |plug-in − bootstrap mean| ≤ 0.05 rate points (scale analog of #514's 0.5 nat on its ~8-nat dial).
- **Gap-vs-strength sweep** (mirror of #514's grid table): same bootstrap at targets s\* ∈ {0.2, 0.3, …, 0.9} where both arms have anchors, anchored by base (s=0) and the 4 cells/arm.

**Multi-arm resolution-band compliance:** this is a 2-arm bracket design, not a band-simultaneity design — arms are matched on the dial (strength), deliberately NOT on step count. Per the rule: (a) install-transition window for whole-response behavior SFT on this rig: **ungrounded — no prior sub-epoch trajectory exists for these behaviors** (closest prior is endpoint-only #411/#518); the stage-A grid (step-indexed, resolution 2 steps early, geometric later, spanning 2→132) is designed to measure it, and the grid is in optimizer steps, never whole epochs. (b) **Pre-registered fallback ladder if an arm has no checkpoint in [0.40, 0.60]:** compare arms at their respective band-entry checkpoints (first checkpoint with s in band; if none, closest approach), report matched-dial/unmatched-step explicitly; additionally run the matched read at the nearest target both arms DO bracket (from the s\* sweep grid). An arm that jumps 0→ceiling inside one 2-step interval is reported as exactly that, plus one pre-authorized FT retrain at lr 2e-6 (the #514 lower-LR lever analog) to re-grade the trajectory. (c) "Arms never co-bracket under this recipe" is a decidable, reportable outcome.

**Marker / behavior-implant stopping recipe:** N/A as to the marker band-stop (no marker payload; whole-response loss with countervailing term). The generalized discipline it encodes — compare below ceiling, gate on the resolution of the measurement (here: source-self rate off both floor and ceiling), stop on the metric not the epoch — is exactly what stage-A + the selection rule implement. The smoke run exercises the trajectory telemetry (per-checkpoint s logged to WandB + `trajectory_*.json`), so the guard is smoke-verifiable.

**Why code, not a model call?** The unstructured-data classification (did the response agree / refuse?) IS a model call — pinned Claude Haiku 4.5 judges inherited from #411/#518 (κ=0.890 vs Sonnet on #411's calibration). Code handles only deterministic numerics (rate aggregation, isotonic smoothing, interpolation, bootstrap), where a model call would be strictly worse (determinism + cost at N≈380k verdicts). What would flip it: nothing in this design.

**ICL / few-shot demonstrations:** N/A — no ICL or few-shot demonstrations in this design.

**Smoke/sweep architectural parity:** smoke phase = the production dispatcher with `--smoke`: sycophancy × LoRA arm × 2 checkpoints × 3 personas × 5 claims × 2 rollouts + inline judging + bootstrap B=200, same dispatcher, same phase functions, same env injection, same upload surface (the #591 `Ctx` smoke-branch pattern). Smoke IS the sweep with one cell. The FT path's canary: smoke additionally trains the FT arm for 4 steps and saves + stage-A-evals one FT checkpoint, so the ZeRO-3 save/consolidate/load path is exercised before the full run.

**Degenerate-output handling in the primary rates (reconciler binding fix 4):** the per-response degeneracy flag (<5 chars or >80% repeated 3-grams — the metric kill criterion (b) already computes) is persisted per generation and cross-tabbed with judge verdicts in BOTH stage-A (the strength dial, BEFORE checkpoint selection and any FT-checkpoint deletion) and stage-B. ### Success criteria (numeric)

Per behavior: **equivalence** = gap 95% CI ⊂ (−0.05, +0.05) AND profile ρ ≥ 0.7; **divergence** = CI excludes 0 with |point| ≥ 0.05, or ρ CI upper < 0.7 with point < 0.4; else **indeterminate** (reported as noise-limited, never "confirms the null"). ## 7. Decision Gates

One gate (justified: wall > 4 h AND the FT install dynamics are genuinely unmeasured AND stage-A is a cheap signal that rules out the expensive stage-B):

Grounding: LoRA endpoints are demonstrated at +0.914 (syco) / +0.994 (refusal) [#411/#518], so the expected outcome is PASS; the gate exists for the un-demonstrated FT side. On FAIL (kill criterion (a): neither bracket nor endpoint ≥ 0.50): kill that behavior's comparison, report install-failure, continue with the other behavior (and the one pre-authorized lr 2e-6 FT retrain if the failure mode is grid-jump rather than no-install). Jointly satisfiable trivially (single gate, sign matches every prior install of these recipes; coherent with §4.4(b)'s fallback by construction).

No other gates — the checkpoint-selection step is a pipeline phase, not a stop/go gate.
