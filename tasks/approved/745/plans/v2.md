# Plan — issue #745: enable fast HF Hub uploads (v2 — Xet-routed)

> **v2 vs v1 — what changed and why.** A live Phase-0 probe (run in-context, §1.5)
> proved the v1 fix is INERT for this project's real upload targets: both project
> HF repos route to **Xet**, not the LFS multipart path that `hf_transfer`
> accelerates. So `HF_HUB_ENABLE_HF_TRANSFER=1` would do nothing for any actual
> upload. v2 pivots the accelerator to `HF_XET_HIGH_PERFORMANCE=1` (the Xet perf
> knob), fixes three false claims from v1 (env.py is NOT the single chokepoint;
> the LFS threshold is server-driven; the v1 check-7 engagement assertion was
> untestable), and lands the accelerator at SHELL level (the only placement that
> beats the import-time-frozen-constant trap for the env vars that have one).

## 0.0 TL;DR (plain English)

- **What I'll run:** I'll turn on Hugging Face's fast-upload mode for every place
  our experiments push files (raw completions, activation stores, checkpoints).
  Right now uploads crawl — a 36 GB file took hours at single-digit MB/s on a fast
  link, with the expensive GPU box sitting idle and still billing. This is a
  config/dependency change, no GPU, no experiment.
- **What I expect:** I checked which upload path our repos actually use — it's
  "Xet", not the older path the first draft of this plan assumed. So the speed-up
  has to flip the *Xet* fast switch (`HF_XET_HIGH_PERFORMANCE`), not the older one.
  With that on, big uploads should run far faster.
- **What would change my mind:** If the upload smoke shows the fast switch makes
  no measurable difference (the slowness was the network or the server, not the
  client), then the env var is the wrong lever and I'd stop and rethink rather than
  ship a no-op. The plan bakes in a before/after speed measurement so we find out
  for sure, not assume.

## 1. Goal

## 1.5 Phase 0 — Xet probe (RUN BEFORE the fix lands; results below are LIVE)

The v1 plan assumed every large upload takes the LFS multipart path that
`hf_transfer` accelerates. That assumption is FALSE for this project. The
`huggingface_hub==0.36.2` upload path negotiates per-file transfer at
`_commit_api.py:378-426`: it always offers `["basic", "multipart"]`, appends
`"xet"` when `is_xet_available()` and the payload is not a buffered IO object,
and the **SERVER** picks via `chosen_transfer`. When `chosen_transfer == "xet"`,
files route to `_upload_xet_files` and NEVER touch `_upload_parts_hf_transfer`
(the `hf_transfer` LFS path) — so `HF_HUB_ENABLE_HF_TRANSFER` is irrelevant to
them.

**Probe results (run live in this planning session, 2026-06-29):**

| Check | Result |
|---|---|
| `huggingface_hub.__version__` | `0.36.2` |
| `is_xet_available()` | **`True`** |
| `hf_xet` installed | yes (already an installed transitive dep) |
| `dataset_info("superkaiba1/explore-persona-space-data", expand=["xetEnabled"]).xet_enabled` | **`True`** |
| `model_info("superkaiba1/explore-persona-space", expand=["xetEnabled"]).xet_enabled` | **`True`** |

| **router call-spy** | `_upload_xet_files` fired **1×**, `_upload_lfs_files` fired **0×** |
| measured upload throughput | ~3.7 MB/s (the slow symptom reproduces on the xet path) |

**Decision: BRANCH B — every project repo routes to Xet.** The v1 `hf_transfer`
fix is INERT for the project's real upload targets. PIVOT the accelerator to
`HF_XET_HIGH_PERFORMANCE=1`.

- `HF_XET_HIGH_PERFORMANCE` is NOT a `huggingface_hub.constants` symbol — it is
  read directly by the compiled `hf_xet` Rust `.so` from the OS environment at
  upload time (grep of both installed packages found no Python-source reference;
  it lives in the compiled crate). Because it is read at *upload* time, not
  *import* time, it is NOT subject to the import-time-frozen-constant trap that
  bites `HF_HUB_ENABLE_HF_TRANSFER` — but the safest, uniform placement is still
  shell-level (it must be in `os.environ` before the upload call, and shell-level
  guarantees that regardless of import order or whether `load_dotenv` ran).
- We ALSO keep `HF_HUB_ENABLE_HF_TRANSFER=1` + the `hf_transfer` hard dependency
  (the orthogonal LFS-path accelerator), as a combined B+ posture (effectively
  branch C): the two env vars are orthogonal — `HF_HUB_ENABLE_HF_TRANSFER`
  accelerates the multipart/LFS path, `HF_XET_HIGH_PERFORMANCE` accelerates the
  xet path — so setting both is correct and future-proofs a repo that ever
  routes to LFS (e.g. a new repo with Xet disabled, or the documented
  `HF_XET_DISABLE=1` recovery path). The `hf_transfer` hard-fault-when-missing
  only fires on the LFS path; making it a hard dep closes that hole cheaply.

## 2. Prior Work

- **What `hf_transfer` is (LFS-path accelerator).** A Rust-backed package
  (`pip install hf_transfer`) that `huggingface_hub` uses for multipart parallel
  LFS uploads / chunked downloads when `HF_HUB_ENABLE_HF_TRANSFER=1`. It
  accelerates ONLY the LFS multipart path (`_upload_parts_hf_transfer` in
  `lfs.py`); it has NO effect on the Xet path. Its README pitches it as useful
  "above ~500 MB/s" links — the ~500× figure is an empirical claim, measured on
  the smoke, not guaranteed. `hf_transfer` 0.1.x has known panics on transient
  network errors; the `=0` override path is the correct recovery channel for
  that.
- **What Xet is (the path this project actually uses).** The Hugging Face Hub's
  current storage backend. Modern HF docs declare `HF_HUB_ENABLE_HF_TRANSFER`
  **deprecated**: *"Now that the Hugging Face Hub is fully powered by the Xet
  storage backend… hf_transfer can't be used anymore. If you are interested in
  higher performance, check out HF_XET_HIGH_PERFORMANCE."* When `is_xet_available()`
  and the server returns `chosen_transfer == "xet"`, uploads go through
  `_upload_xet_files` (driven by the compiled `hf_xet` crate). `hf_xet` reads
  `HF_XET_HIGH_PERFORMANCE` (and `HF_XET_DISABLE`, `HF_XET_CACHE`, etc.) directly
  from the OS environment at upload time. `is_xet_available()=True` and both
  project repos `xet_enabled=True` are live-verified (§1.5).
- **API contract — `HF_HUB_ENABLE_HF_TRANSFER` HARD FAULTS when the flag is set
  but the package is absent (verified, LFS path only).** From the installed
  `huggingface_hub==0.36.2` source (`lfs.py::_upload_parts_hf_transfer`):
  `from hf_transfer import multipart_upload` inside a `try/except ImportError`
  that re-raises as `ValueError` ("Fast uploading using 'hf_transfer' is enabled
  (HF_HUB_ENABLE_HF_TRANSFER=1) but 'hf_transfer' package is not available …").
  This fault fires ONLY when an upload takes the LFS multipart path — which, per
  §1.5, the project's repos currently do NOT. But because the combined posture
  keeps `HF_HUB_ENABLE_HF_TRANSFER=1` for future-proofing, `hf_transfer` MUST be
  a hard dep so the flag can never enable that fault on a repo that ever routes
  to LFS.
- **Import-time-frozen constant (verified).** `huggingface_hub.constants` reads
  `HF_HUB_ENABLE_HF_TRANSFER: bool = _is_true(os.environ.get("HF_HUB_ENABLE_HF_TRANSFER"))`
  at MODULE IMPORT TIME. An `os.environ.setdefault` running AFTER a script's
  `import huggingface_hub` is a no-op for this constant — the value is already
  frozen. (`HF_XET_HIGH_PERFORMANCE` is NOT a `constants` symbol, so it escapes
  this freeze — but shell-level placement covers both uniformly.)
- **Direct-upload scripts bypass `orchestrate.env` (verified — corrects v1's
  false "single chokepoint" claim).** The v1 plan claimed `env.py::setdefault`
  is "the ONE code path every entrypoint calls." It is not:
  - `scripts/issue617_upload_corpus.py:42` imports `from dotenv import load_dotenv`
    (bare; walks cwd, does NOT read the project `.env`) and calls `HfApi.upload_folder`
    (line 161); `huggingface_hub` imported in-function at line 156.
  - `scripts/issue658_extract_base_store.py:79` imports `from dotenv import load_dotenv`,
    calls `load_dotenv(PROJECT_ROOT/".env")` (line 118) — so it DOES read the project
    .env, but sets only `HF_HOME` via `setdefault` at module top (lines 63-64), NOT the
    transfer flags; `huggingface_hub` imports are in-function (412/1157/1209), AFTER its
    dotenv call.
  - `scripts/issue651_drain_extracts.py:21` imports `huggingface_hub` at MODULE TOP
    and NEVER calls `load_dotenv` at all (0 grep hits for `load_dotenv`/`dotenv`/
    `setdefault`/`HF_HUB_ENABLE`). This is the worst case — neither the in-process
    `setdefault` NOR a top-of-file one would fire in time for the frozen constant.
  - `src/explore_persona_space/backends/gcp.py:1173/1195` embeds a crash-persist
    `HfApi.upload_folder` directly in the GCE startup shell, with NO `load_dotenv` in
    that subshell — it runs in the EXIT trap before/independent of the workload's env.
- **In-project precedent.** `external/open-instruct/Dockerfile:66` sets
  `HF_HUB_ENABLE_HF_TRANSFER=1` and `external/open-instruct/uv.lock` pins
  `hf_transfer==0.1.9` — precedent that the package + flag are safe in this stack
  (note: open-instruct predates the project's Xet migration, so it is precedent
  for the LFS-path config, not the Xet config).
- **Project caveats.**
  - **#515 xet-CDN download interaction (2026-06-08):** a run launched with
    `HF_XET_DISABLE=1 HF_HUB_ENABLE_HF_TRANSFER=0` to work around an HF xet CDN
    HTTP 416 stall during model DOWNLOAD. So the on-by-default flags MUST stay
    overridable — an explicit `=0` / `HF_XET_DISABLE=1` at launch must cleanly
    disable. Hence every default uses `setdefault` / append-if-absent, never an
    unconditional `export`.
  - **Quota-403 overflow path (`.claude/rules/upload-policy.md`, #541/#552/#564):**
    the LFS-quota 403 fires regardless of transfer backend; both accelerators are
    just faster clients for the SAME `upload_folder`/`upload_file` call —
    orthogonal to the overflow routing.
  - **Bulk-commit discipline (#664):** `upload_folder` composes one commit per
    tree; the accelerators speed the per-file object transfers within it. No
    conflict.
- **Wheel availability.** Pure-Rust abi3 wheels for `hf_transfer` (manylinux/
  musllinux/macOS) and `hf_xet` (already installed) — no source build on the
  RunPod image, dev VM, GCE, or DRAC nodes. `(high confidence)`

### 4.3 Shell-level exports (THE LOAD-BEARING FIX) — three sites

The env vars are exported at SHELL level, before any Python import, in every
non-local worker environment. This is the only placement guaranteed to land
before `huggingface_hub.constants` freezes `HF_HUB_ENABLE_HF_TRANSFER`, and it
covers the direct-upload scripts (`issue651` imports `huggingface_hub` at module
top with no `load_dotenv` at all) AND the GCE crash-persist subshell that runs
with no project env.

**(a) `scripts/bootstrap_pod.sh` step 6 — BOTH heredoc blocks.** Step 6 writes
to TWO separately-guarded blocks: the rc-files block (`RCEOF` heredoc, ~line 334,
written to `/root/.bashrc` + `/root/.profile`) AND the project-`.env` block
(`ENVEOF` heredoc, ~line 353). The new lines go in BOTH (the auxiliary item from
the methodology critics) — the rc block covers interactive/login pod shells, the
`.env` block covers dotenv-loading subprocesses.

rc-files block (after the existing cache-redirect exports):

```bash
 export TRITON_CACHE_DIR=/workspace/.cache/triton
+# Fast HF Hub uploads (#745). HF_XET_HIGH_PERFORMANCE accelerates the Xet path
+# (what the project repos use — verified); HF_HUB_ENABLE_HF_TRANSFER accelerates
+# the orthogonal LFS path. hf_transfer is a hard dep so the LFS flag never
+# enables a missing-package fault. Override per-launch with =0 / HF_XET_DISABLE=1
+# (the #515 xet-CDN workaround).
+export HF_XET_HIGH_PERFORMANCE=1
+export HF_HUB_ENABLE_HF_TRANSFER=1
```

project-`.env` block (after the existing cache-redirect lines):

```bash
 TRITON_CACHE_DIR=/workspace/.cache/triton
+# Fast HF Hub uploads (#745); override per-launch with =0 / HF_XET_DISABLE=1.
+HF_XET_HIGH_PERFORMANCE=1
+HF_HUB_ENABLE_HF_TRANSFER=1
```

Idempotency: each heredoc block is gated by its existing `grep -q` guard on a
cache-redirect line, so adding lines inside the same heredoc is idempotent on
re-bootstrap. Override caveat (preserved from v1): the `.env` lines are static, so
a pod-side caller wanting off must export `=0` / `HF_XET_DISABLE=1` in its own
shell env (which supersedes the dotenv value under `load_dotenv(override=False)`),
not edit `.env`. State this in the comment.

**(b) GCE startup script — pre-workload prelude AND the crash-persist subshell.**
The GCE startup script (`backends/gcp.py::render_startup_script`) renders exports
for passthrough keys (line 1622) BEFORE the workload runs. Add a STATIC default

**Workflow-lint check (Option γ regression guard).** Add a
`--check-dotenv-before-hf-import` check to `scripts/workflow_lint.py` (bundled
into the no-flags default run) that AST-walks `scripts/*.py` and FAILs a file
that BOTH (a) imports `from dotenv import load_dotenv` (the bare dotenv, not
`orchestrate.env`) AND (b) imports `huggingface_hub` (any form), without a
preceding `from explore_persona_space.orchestrate.env import load_dotenv`. The
rationale: a script that touches `huggingface_hub` and wants dotenv should use
the project wrapper (which sets the accelerator defaults + reads the project
`.env` robustly), not the bare `dotenv` that walks cwd and sets nothing. Waive a
legitimate exception with `# DOTENV_HF_EXEMPT: <reason>` on the import line.
Pseudocode:

```python
def check_dotenv_before_hf_import() -> list[str]:
    failures = []
    for path in glob("scripts/*.py"):
        tree = ast.parse(read(path)); src = read(path)
        uses_bare_dotenv = any(
            isinstance(n, ast.ImportFrom) and n.module == "dotenv"
            and any(a.name == "load_dotenv" for a in n.names)
            for n in ast.walk(tree))
        uses_hf = any(
            (isinstance(n, ast.Import) and any(a.name.startswith("huggingface_hub") for a in n.names))
            or (isinstance(n, ast.ImportFrom) and (n.module or "").startswith("huggingface_hub"))
            for n in ast.walk(tree))
        uses_orchestrate_env = any(
            isinstance(n, ast.ImportFrom)
            and (n.module or "").endswith("orchestrate.env")
            and any(a.name == "load_dotenv" for a in n.names)
            for n in ast.walk(tree))
        if uses_bare_dotenv and uses_hf and not uses_orchestrate_env:
            if "# DOTENV_HF_EXEMPT:" not in src:   # line-level exemption check is finer
                failures.append(f"{path}: bare `dotenv` + huggingface_hub without orchestrate.env.load_dotenv (#745)")
    return failures
```

- **Primary accelerator = `HF_XET_HIGH_PERFORMANCE`, NOT `hf_transfer`
