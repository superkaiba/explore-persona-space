## 3. Hypothesis / Root-cause diagnosis (required section 4 of the brief, placed here as the plan's claim)

**Verified escape path:** both #1315 p11 kills were SINGLE-FILE uploads (`selection/imp_conv_lora/parity.json` at v7, `run_config.json` at v8 — `epm:failure` v7/v8 marker text). For `upload_as_file=True`, `_upload`'s verify leg calls `list_hf_files_under_path(api, repo, "<exact file path>")` → the tree endpoint 404s on file paths (docstring L639-641, live-verified on hub 0.36.2, #939) → `EntryNotFoundError` → the **bare** `api.file_exists(...)` HEAD probe at L659. On hub 0.36.2 (`hf_api.py:2968-3023`, read from the installed venv), `file_exists` returns False only on `RepositoryNotFoundError`/`EntryNotFoundError`/`RevisionNotFoundError`; a 429 raises `HfHubHTTPError` (via `get_hf_file_metadata` → `hf_raise_for_status`) carrying `.response.status_code == 429`, which **propagates un-retried** out of `list_hf_files_under_path`, into `_upload`'s outer `except Exception` (L1252) → not a file-count error → `logger.error("Upload failed: %s. Keeping local path.", e)` (L1295) → `return ""` → the dispatcher's fail-fast `_up` raised (`issue1315_dispatch.py:1702`).

**Why the classifier is NOT the escape for the observed shape:** the logged message "429 Client Error: Too Many Requests" is the `requests` `raise_for_status` format — that exception carries `.response` and would classify transient BY CODE had it reached `_is_transient_upload_error`; even response-less, its text matches the existing `"too many requests"` substring. It escaped because the failing call site is outside every `_retry_upload` wrapper, not because classification failed.

**Why not budget exhaustion:** exhaustion inside `_retry_upload` requires ≥1800s of wall in ONE call; the kills landed ~10-15 min into a phase in which several uploads succeeded between failures — an immediate propagation, not an exhausted retry.

**Where "maximum queue size reached" comes from:** the phrase appears in NEITHER the installed `huggingface_hub` 0.36.2 source NOR the `hf_xet` binary (`strings hf_xet.abi3.so | grep -i "queue size"` → empty; verified this session). It is a SERVER-side 429 response-body text (HF/Xet CAS ingestion queue saturation) appended to the `HfHubHTTPError` message — consistent with the #1335 record ("transient HF 429 ('maximum queue size reached')"). The task body's "Xet queue-full" framing is therefore a server-side queue, and the observed exception is response-bearing. The RESIDUAL uncovered shape is #931's class: a 429 crossing the hf_xet PyO3 token-refresher boundary as a wrapped exception WITHOUT `.response`, whose Rust-formatted text could carry the queue-full body without the "too many requests" phrase. Change 2 covers it defensively.
