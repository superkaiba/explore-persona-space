## 0.0 TL;DR (plain English)

Fresh pods clone the repo with a cone sparse-checkout that hides everything outside `src scripts configs tests docs` (+ the pod's own `eval_results/issue_<N>` / `figures/issue_<N>`). Git-TRACKED experiment inputs under `data/` (e.g. `data/assistant_axis/role_list.json`) are therefore ABSENT on a fresh pod, and any workload reading one crashes `FileNotFoundError` mid-run — after the model has already loaded (#2203 Phase 3 incident). Tracked `data/` totals only ~63 MB (320 files), while the sparse clone exists to avoid a ~10.5 GB full checkout, so the fix is to add `data` to the default cone everywhere the cone set is written, plus an idempotent `sparse-checkout add data` on the always-running re-bootstrap path so existing sparse pods gain it too. Update the #1739 pin test and the gotchas.md entry.

## 3. Hypothesis

Not an experiment — `kind: infra`. The engineering claim: adding `data` to the default cone closes the entire class of tracked-`data/`-input crashes for all current and future experiments at a cost of ~63 MB per pod bootstrap (0.6% of the 10.5 GB the sparse clone avoids), with no per-plan ceremony and no reliance on planner memory.

## 4. Design

Key size facts (measured at plan time): `git ls-files data/` = 320 files across 11 top-level subdirs, 62,890,166 bytes total. The runtime `data/issue_<N>/hf_dl/` and `g*_dl/` download caches are UNTRACKED (created at run time, gitignored or simply never committed), so a cone over `data` materializes tracked blobs only — no exclusion machinery is needed; acceptance criterion (a)'s "excluding caches" is satisfied by construction.

## 11. Decision Rationale

Decision: **option (a) — default-cone extension.**

- **(a) chosen:** tracked `data/` is ~63 MB vs the 10.5 GB the sparse clone avoids (0.6%); the caches under `data/` are untracked so "excluding caches" is free; it closes the LATENT gap for every experiment (any tracked input under `data/` — 11 subdirs already exist and more accrete) with zero per-plan ceremony; and it removes the failure mode where the crash surfaces only AFTER expensive setup (the #2203 incident lost a 32B model load).
- **(b) rejected (per-plan declaration):** relies on the planner remembering to declare `data/` inputs — the exact class of memory-dependent contract that produced #1739 and #2203; adds ceremony to every plan for a 63 MB saving.
- **(c) rejected (stage-from-HF):** duplicates git-tracked inputs onto HF, creating a second source of truth that drifts (the repo copy is the one code reads via relative paths); adds upload/download machinery for inputs git already delivers.

## 12. Assumptions

- Assumption: cone-mode sparse-checkout with a `data` cone materializes the whole tracked `data/` subtree and fetches its blobs on demand under `--filter=blob:none` at `reset --hard FETCH_HEAD` time (standard git behavior; the pin test exercises exactly this path with a real git).
- Assumption: no workload depends on `data/` being ABSENT on a pod (nothing greps for its absence; the dir was absent only as a side effect of #2051).
- Assumption: the ~63 MB one-time fetch per pod bootstrap is acceptable on all lanes (it is dwarfed by the model downloads every experiment performs).
