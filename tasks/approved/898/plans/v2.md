## 1. Goal, requirement, acceptance criteria

**Goal** (from task body): make `task_workflow` git operations resilient to concurrent `.git/index.lock` collisions and make `set_status`'s folder-move + registry update crash-safe.

**Requirement:** after this change, the #825 sequence — concurrent session holds `index.lock` while `set_status` runs — must either (a) succeed via the retry, or (b) fail with `tasks/<status>/<N>` on disk and `REGISTRY.json` in agreement, with `task.py find/view <N>` still resolving, AND with no PERMANENT git residue: the next transition of the task reconciles any leftover old-status deletion. No path may strand a task in a state only `audit --repair --apply` can fix.

**Acceptance criteria:**
1. `_run_git` retries exactly once on the git lock-contention error signature, never on other errors, never more than once, and never for `check=False` calls whose non-zero rc carries no lock signature (e.g. `diff --cached --quiet`).
2. A crash injected at the `git add` step of `set_status` (and at the `_git_commit` step) leaves registry consistent with disk; `find_task_path` resolves afterwards.
3. A stale registry entry (dir moved on disk, registry not updated — the SIGKILL-window residue shape) resolves via the scan fallback with a logged drift warning.
4. All existing `tests/test_task_workflow*.py` tests pass unmodified — in particular `test_set_status_commits_both_sides_of_move`, `test_set_status_rolls_back_before_registry_on_incomplete_move`, and the routed-worktree tests in `test_task_workflow_worktree.py`.
5. Happy path (no contention): zero behavior change and zero added sleeps — pinned by a test (monkeypatched `sleep` → `pytest.fail` on a SUCCESSFUL `_run_git`), plus the one new `ls-files` call per `set_status` (≪10 ms, bounded).
6. **Ghost-deletion sweep (v2, binding Must-Fix):** after a git-crash residue (injected git-`add` crash on transition A→B), the NEXT `set_status` of the task (B→C) leaves `git ls-tree -r HEAD -- tasks/A/<id>` AND `tasks/B/<id>` empty and `git status --porcelain -- 'tasks/'` clean for this task — no committed ghost duplicate, no permanent unstaged deletions.
7. **Early-return registry re-sync (v2):** re-running the SAME transition against a stale registry entry (dir already at the destination on disk, registry pointing at the old path) re-syncs the registry entry before the early return — the registry is consistent afterwards, without requiring a different transition.

### 4.1 `_run_git` — signature-keyed single retry

New module-level constants (near line 3124, above `_run_git`):

```python
# Git lock-contention signature. Matches the three stderr shapes a concurrent
# git process produces (git 2.x): the index.lock path itself, the generic
# "another process" hint, and the File-exists lock-create failure (covers
# ref locks / packed-refs.lock with the same transient signature). A CAS
# mismatch ("is at <sha> but expected <sha>") deliberately does NOT match.
_GIT_LOCK_CONTENTION_RE = re.compile(
    r"index\.lock"
    r"|Another git process seems to be running"
    r"|Unable to create '.*\.lock': File exists"
)
_GIT_LOCK_RETRY_SLEEP_RANGE_S = (2.0, 3.0)  # one retry; jittered to de-sync
```

Rewritten `_run_git` (existing docstring comments about per-call cwd + sanitized env preserved verbatim):

```python
def _run_git(args, *, check=True):
    result = subprocess.run(["git", *args], cwd=str(repo_root()),
                            env=_sanitized_git_env(), check=False,
                            capture_output=True, text=True)
    if result.returncode != 0 and _GIT_LOCK_CONTENTION_RE.search(result.stderr or ""):
        delay = random.uniform(*_GIT_LOCK_RETRY_SLEEP_RANGE_S)
        _log.warning("git %s hit a lock collision (a concurrent git process holds "
                     "the lock); retrying once in %.1fs", args[0], delay)
        time.sleep(delay)
        result = subprocess.run(...same...)   # second and FINAL attempt
        if result.returncode != 0 and _GIT_LOCK_CONTENTION_RE.search(result.stderr or ""):
            _log.error("git %s failed twice on a lock collision. A concurrent git "
                       "process is holding the repo lock; if no live git process "
                       "exists, a crashed one may have left a stale "
                       ".git/index.lock — inspect and remove it manually.", args[0])
    if check and result.returncode != 0:
        raise subprocess.CalledProcessError(result.returncode, result.args,
                                            output=result.stdout, stderr=result.stderr)
    return result
```

Adds `import random` + `import time` to the module header (in the same edit as first usage — the PostToolUse ruff hook strips unused imports). `re` is already imported (line 77). The `CalledProcessError` must reproduce the same `.cmd` attribute `subprocess.run(check=True)` produces (pass the command list).

**Edge cases handled by this shape:**
- *`check=False` rc-as-signal sites* (`diff --cached --quiet` line 3189, `push` line 3203): retry keys on the STDERR SIGNATURE, not on rc. `diff --cached --quiet` rc=1 has empty stderr → never retried, rc signal intact. A `push` that trips the regex (rare relayed remote-lock text) gets one harmless retry.
- *Exception compatibility:* retry exhaustion under `check=True` raises `subprocess.CalledProcessError` with the same fields `subprocess.run(check=True)` would produce — existing `except CalledProcessError` callers and tests are unaffected. The actionable remedy goes to `_log.error` (the house pattern, cf. `_rollback_move`), not a new exception type.
- *Read-only calls* (`rev-parse`): never write locks, never match, zero change.
- *Latency bound:* happy path 0 added ops; worst case per call = one sleep ≤3.0 s + one command rerun (≪1 s locally) ≤ ~4 s, under the ≤6 s success criterion. The retry sleeps while `set_status` holds the exclusive flock — bounded, acknowledged; no call site loops `_run_git` more than the handful of times per mutation it does today.

**Non-goals (stated so the reviewer sees they're deliberate):** `_git_quiet` (line 390) is NOT wrapped — its callers are the read-only repo-root resolver probes (no locks taken) and the `_advance_main_ref` CAS, whose failure mode is loud-not-stranded (commit exists on the managed worktree's detached HEAD; disk+registry already consistent under the §4.2 ordering) and where auto-retry could mask a genuine concurrent-writer CAS conflict. Other scripts' direct `subprocess` git calls are out of the candidate's `target_file` scope.

### 4.2 `set_status` — durable state before git (reorder)

Current tail order inside `with _locked():` — move → verify/rollback → **`git add`** (line 1991, the #825 crash point) → registry save → event append → `_git_commit`. New order:

```
1. find old path, guards                        (unchanged, lines 1907-1959;
                                                 early-return gains the §4.5 re-sync)
2. shutil.move(old -> new)                      (unchanged)
3. completeness verify -> _rollback_move on miss (unchanged — REGISTRY untouched)
4. registry: _load_registry/_registry_set/_save_registry   (moved up)
5. _append_jsonl_line(status-changed event)                (moved up)
6. ghost-aware staging (§4.4): git add --all -- <all tracked/existing status
   dirs for this id, incl. rel_old + rel_new>              (replaces the old
                                                            two-path staging)
7. _git_commit([<same expanded path set>, registry_path()], ...)
```

Steps 6–7 are wrapped so that a git failure logs actionable context BEFORE re-raising (exception type unchanged, fail-fast preserved):

```python
try:
    ... step 6 staging + step 7 _git_commit ...
except subprocess.CalledProcessError:
    _log.error(
        "task #%d: status move %s -> %s is DURABLY APPLIED (disk + REGISTRY + "
        "events.jsonl consistent at %s) but git failed before committing. "
        "Leftover git residue at %s / %s will be reconciled by the NEXT "
        "set_status of this task; to sweep now: git add --all -- %s %s && "
        "git commit -m 'task #%d: sweep crashed status-move residue'",
        task_id, old_status, new_status, rel_new, rel_old, rel_new,
        rel_old, rel_new, task_id)
    raise
```

**Crash-envelope statement (goes in the `set_status` docstring, `_append_jsonl_line`-style):** the #825 stranded split (folder moved, registry stale) is unreachable **via git-failure exceptions** — any git crash leaves disk, REGISTRY, and events.jsonl all consistent, with only the COMMIT missing; the missing commit is reconciled by the §4.4 sweep on the task's next transition. A HARD KILL (SIGKILL/OOM) in the residual window between `shutil.move` and `_save_registry` still yields a stale-registry shape; that window is backstopped by the §4.3 read-path scan fallback + the §4.5 early-return re-sync, and the next completed mutation re-syncs the registry. A hard kill between `_save_registry` and `_append_jsonl_line` yields a consistent folder+registry with a missing `epm:status-changed` event — a history gap, not a stranding.

**Why this ordering (vs. rollback-on-git-failure):**
- One change covers BOTH git crash points. Under the current order a `_git_commit` crash already leaves consistent state (registry was saved at the old step 4); only the `git add` crash strands. Reordering makes every git failure equivalent to "commit missing, state consistent".
- A rollback arm would have to undo an append-only `events.jsonl` write and would leave *staged deletions pointing at an undone tree state* when `git add` partially staged before crashing — exactly the leaked-deletion incident class from 2026-05-24 (commit 49e49f4a) that the both-sides pathspec rule exists to prevent. After reorder, any partial staging matches the (kept) new tree state, so the §4.4 sweep is correct by construction.
- The existing `_rollback_move` FS-verification path is byte-identical — it fires before step 4, registry untouched, exactly as today (pinned by `test_set_status_rolls_back_before_registry_on_incomplete_move`).
- Semantics on git failure: `set_status` still RAISES (fail fast, no swallowed fault), but the status transition is durably applied. A caller retry hits the `old_status == new_status` early-return idempotently (which now also re-syncs a stale registry entry, §4.5). `TASK_PY_NO_COMMIT=1` behavior unchanged (the standalone `add` still runs, as today).

### 4.3 `find_task_path` — stale-entry scan fallback

Replace the lines-1637-1642 tail:

```python
abs_path = repo_root() / entry["path"]
if abs_path.is_dir():
    return abs_path
# Registry entry is STALE (dir moved on disk without a registry update —
# e.g. a mutation was hard-killed mid-flight; cf. #825). Fall back to a
# one-shot on-disk scan; READ path, so never self-heal REGISTRY here (no
# _locked()).
hits = [td / s / str(task_id) for s in STATUSES if (td / s / str(task_id)).is_dir()]
if len(hits) == 1:
    _log.warning(
        "task #%d: REGISTRY says %r but that dir is missing; found on disk at "
        "%r — returning the on-disk path. REGISTRY is stale; it re-syncs on "
        "the next registry-writing mutation of this task, or run "
        "`task.py audit --repair --apply`.",
        task_id, entry["path"], str(hits[0].relative_to(repo_root())))
    return hits[0]
if len(hits) > 1:
    raise StaleTaskPathError(
        f"task #{task_id}: REGISTRY says {entry['path']!r} (missing) and the "
        f"task exists in MULTIPLE status folders: "
        f"{[str(h.relative_to(repo_root())) for h in hits]}; "
        f"run `task.py audit --repair --apply`")
raise FileNotFoundError(   # unchanged message, zero hits
    f"task #{task_id} registry says {entry['path']!r} but that dir is missing; "
    f"run `task.py audit` to repair")
```

- **No in-place self-heal on the READ path:** `find_task_path` is called from read paths (`view`, `get_task`, dashboards) that must not take the write flock; an unlocked `_save_registry` (whole-file replace) could clobber a concurrent mutator's update. Repair stays with `audit --repair` — plus two self-heals in the pipeline: the next registry-writing mutation of the task re-syncs the entry via its own `_registry_set`, and the §4.5 early-return re-sync covers the retry-same-transition case (which would otherwise return before `_registry_set`).
- **Ambiguity raises** (`StaleTaskPathError`, a `FileNotFoundError` subclass — existing catchers still catch) rather than guessing: two dirs for one id is real corruption, and silently picking one would hide it. The pre-existing *no-entry* scan branch (first-match, lines 1630-1636) is left untouched — changing its semantics is out of scope.

### 4.4 Ghost-deletion sweep (v2 — the binding Must-Fix mechanism)

**Problem (verified by three independent reviewers):** after a git-crash in `set_status`, nothing is staged; the deletion of `tasks/<old>/<id>` exists only in the working tree. Every later mutation's `--only` pathspec covers the task's CURRENT path + REGISTRY only, so the old-status dir persists in HEAD indefinitely — and the first later commit publishes the task at BOTH statuses (a committed ghost duplicate, the #644 stale-task-folder class), with permanent unstaged deletions on the shared root.

**Mechanism — inline replay at the next transition.** A small helper, called from `set_status` step 6:

```python
def _task_status_dir_pathspecs(task_id: int, repo: Path) -> list[str]:
    """All tasks/<status>/<id> dirs for this task that git TRACKS or that
    exist on disk — the staging pathspec set that reconciles any residue a
    previously-crashed transition left behind (ghost old-status dirs whose
    deletions were never staged). One `git ls-files` call, deterministic
    per-STATUSES pathspecs (no fnmatch wildcards — exact-id matching only,
    so id 89 never sweeps id 898)."""
    candidates = [f"tasks/{s}/{task_id}" for s in STATUSES]
    tracked = _run_git(["ls-files", "--", *candidates]).stdout.splitlines()
    dirs = {"/".join(p.split("/")[:3]) for p in tracked if p.strip()}
    dirs |= {c for c in candidates if (repo / c).is_dir()}
    return sorted(dirs)
```

`set_status` step 6 then stages `_run_git(["add", "--all", "--", *specs])` where `specs = _task_status_dir_pathspecs(task_id, repo) | {rel_old, rel_new}`, and step 7 passes the SAME expanded set (as absolute paths, plus `registry_path()`) to `_git_commit`. Effects:
- The CURRENT transition behaves exactly as before when no residue exists (`ls-files` returns only the old dir's tracked files; specs == {old, new}) — the both-sides-of-move invariant is preserved verbatim.
- If a PRIOR transition crashed (ghost old-status dir tracked in HEAD, absent on disk), its pathspec is in `specs`, so `git add --all` stages the deletion and this transition's commit sweeps it. This covers both the git-crash residue AND the SIGKILL-window residue.
- Cost: one extra `git ls-files` per `set_status` (~ms, bounded pathspec list ≈ |STATUSES| ≈ 26 args).
- `_git_commit` already tolerates vanished paths (skips `add` for non-existing; `--only` picks up staged deletions) — no change needed there.

**Descoped alternative (deliberate):** extending `audit()` to detect ids present in >1 status folder in HEAD. Not required once inline replay exists — the Step 10d post-merge stale-task-folder guard already sweeps committed duplicates at merge time, and §4.4 prevents new ghosts at the source. (An audit extension would need `git ls-tree` HEAD-scanning, growing scope; if a reviewer disagrees, it is a follow-up task, not this diff.)

### 4.5 Early-return registry re-sync (v2 — closes the retry hole)

The `old_status == new_status` early-return (line 1912) runs INSIDE `_locked()`, so re-syncing there is safe (the D5 no-unlocked-write objection applies only to the read path). New behavior: when `find_task_path` resolved the task at a path that DISAGREES with the registry entry (stale entry — the retry-same-transition case after a hard kill), re-sync before returning:

```python
if old_status == new_status:
    reg = _load_registry()
    entry = reg["tasks"].get(str(task_id))
    rel = str(old.relative_to(repo))
    if entry and entry.get("path") != rel:
        fm, _ = _read_body(old / "body.md")
        _registry_set(reg, task_id, old, fm)
        _save_registry(reg)
        _git_commit([old, registry_path()], f"task #{task_id}: re-sync stale REGISTRY entry")
        _log.warning("task #%d: re-synced stale REGISTRY entry (%r -> %r) on idempotent retry",
                     task_id, entry.get("path"), rel)
    return old
```

Happy-path cost: one `_load_registry` (a small JSON read) on the early-return branch only — the branch is rare (idempotent retries). No behavior change when the entry already agrees.

## 8. Risks and failure modes

| Risk | Likelihood | Mitigation |
|---|---|---|
| Regex under-matches a real lock message variant (older/newer git wording) | Low | Test 1 pins against the REAL message produced by the repo's own git binary; three-alternative regex covers path, hint text, and generic `.lock: File exists` shape; the `index\.lock` alternative keys on the embedded PATH, which survives message localization |
| Regex over-matches a non-transient error (e.g. `could not open '.git/index.lock' for writing: Permission denied`) → one wasted 2–3 s retry | Low | Bounded to ONE retry; worst case is +≤4 s then the original failure, never a hang or masked fault |
| Retry masks a genuinely stale lock (crashed git left `index.lock` forever) | Low | Retry fails too → `_log.error` names the stale-lock remedy explicitly; fail-fast preserved |
| Reorder breaks both-sides-of-move commit invariant | Low | Staging still covers `rel_old` + `rel_new` (§4.4's spec set is a superset); pinned by existing `test_set_status_commits_both_sides_of_move` |
| Reorder interacts badly with routed-main CAS | Low | `_git_commit` internals untouched; `test_task_workflow_worktree.py` pins the routed path |
| Ghost sweep stages an UNRELATED task's files | Very low | Pathspecs are exact `tasks/<status>/<this-id>` strings (no wildcards — id 89 never matches id 898); test 9 asserts only this task's paths change |
| Ghost persists until the task's NEXT transition (later marker commits publish both statuses in the interim) | Low | Bounded-lived: every non-terminal task transitions again; the interim ghost is fail-loud visible (`git status`), consistent on disk+registry, and the Step 10d post-merge guard sweeps merge-time duplicates; the §4.2 error log names the immediate manual sweep command |
| Git failure now leaves the transition durably applied while raising — a caller that assumed "raise ⇒ nothing happened" mis-reasons | Low | No such caller found (callers either crash out — #825 — or retry, and retry is idempotent via the early return, which now also re-syncs); documented in the `set_status` docstring crash-envelope statement |

## 11. Decision Rationale

Hyperparameters: N/A — no model training in this task type. Load-bearing engineering choices:

- **D1 Retry count = 1 (2 attempts total).** *Why:* matches the standing human policy verbatim; bounds worst-case latency; a lock held through a 2–3 s window is likely a stuck process, which must surface, not spin. *Source:* CLAUDE.md § "Concurrent repo-root committers" ("retry once on an `index.lock` collision"); incident #825. *Alternatives:* exponential multi-retry (rejected — masks stale locks, unbounded latency inside a flock-held critical section that other task.py processes queue behind).
- **D2 Backoff = `random.uniform(2.0, 3.0)` s.** *Why:* candidate sketch prescribed 2–5 s; a typical concurrent `git add/commit` on this repo completes ≪ 1 s, so 2 s clears nearly all live collisions; jitter de-syncs against rhythmic committers (crons commit at fixed cadence here); keeps the flock hold-time bounded. *Source:* task #898 candidate block; #825 incident timing. *Alternatives:* fixed 2 s (fine, jitter is one `random.uniform` call); 5 s (needless flock hold).
- **D3 Crash-safety via reorder (durable state before git), not rollback-on-git-failure.** *Why:* one change closes both git crash points; avoids undoing an append-only `events.jsonl` write; avoids leaving staged deletions that mismatch a rolled-back tree — the 2026-05-24 leaked-deletion class (commit 49e49f4a, cited at lines 2010-2015). Semantics "durably applied, commit missing, raise loudly" is strictly recoverable; "half-mutated, unresolvable" (#825) is not. *Source:* read of `set_status`/`_git_commit`/`_rollback_move`; incidents #825, #722, 2026-05-24. *Alternatives:* rollback arm (rejected above); registry-write-first before the FS move (rejected — would break the #722 invariant that a failed/partial FS move leaves REGISTRY untouched, pinned by an existing test).
- **D4 Error-signature regex** `index\.lock|Another git process seems to be running|Unable to create '.*\.lock': File exists`. *Why:* keys on the three stable substrings of git's lock-contention output; deliberately excludes bare `cannot lock ref` so a routed-CAS mismatch ("is at X but expected Y") stays non-retried, fail-loud. *Source:* git's `lockfile.c` error text (stable across git 2.x); verified live by the Phase-1.5 fact-checker on the VM's git 2.34.1 and re-pinned by test 1 against the repo's own git. *Alternatives:* rc==128 alone (rejected — 128 covers many non-transient fatals, and the brief explicitly requires signature-keying).
- **D5 `find_task_path` fallback: scan + warn + return; never self-heal on the READ path; ambiguity raises `StaleTaskPathError`.** *Why:* read paths hold no flock — an unlocked whole-file `_save_registry` races mutators; the registry re-syncs on the next locked mutation (incl. the §4.5 early-return re-sync); reusing the existing typed error keeps `except FileNotFoundError` callers working. *Source:* read of `_locked()`/`_save_registry`/`StaleTaskPathError` (#786); task brief's read-path constraint. *Alternatives:* take the flock and heal on read (rejected — turns every read into a potential writer and can deadlock callers already inside `_locked()`); silent first-match like the no-entry branch (rejected — hides real corruption).
- **D6 (v2) Ghost reconciliation = inline replay in `set_status` (one `ls-files` over exact per-STATUSES pathspecs), not audit-side detect-and-repair, not a `_git_commit`-side sweep.** *Why:* the ghost is CREATED by a crashed `set_status`, so the next `set_status` is the natural, always-eventually-reached reconciliation point; exact pathspecs make cross-id contamination impossible; `_git_commit` receives arbitrary paths (registry, events, plans) and giving it task-id semantics would be magic in the wrong layer; audit-side repair would need HEAD-scanning (`ls-tree`) and leaves the residue live until someone runs audit. *Source:* the round-1 reconciler's binding Must-Fix + the methodology critic's `tasks/*/<id>` staging suggestion; verified `_git_commit` call-site census (:2016/:2090/:2164/:2452/:3112). *Alternatives:* audit extension (descoped — Step 10d post-merge guard covers merge-time duplicates; follow-up material if wanted); persist-and-replay a residue journal (rejected — a second durable state to keep consistent is the disease, not the cure).
- **D7 (v2) Early-return registry re-sync inside `_locked()`.** *Why:* the retry-same-transition path is the most natural user action after a hard-kill residue, and without the re-sync it would resolve via scan then return BEFORE `_registry_set`, leaving the registry (and the REGISTRY-denormalized dashboard) stale indefinitely; the early-return branch already holds the flock, so the D5 objection does not apply. *Source:* round-1 methodology-critic finding; `_locked()` read. *Alternatives:* leave to `audit --repair` (rejected — the "self-heals on next mutation" prose would stay false for the most common retry shape).
