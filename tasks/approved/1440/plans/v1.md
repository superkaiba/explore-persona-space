# Plan v1 — #1440: poster-side advisory WARN for `v<k>. `-stamped marker note heads

### 0.0 TL;DR (plain English — the user reads this first)

- **What I'll change:** I'll add a second advisory warning to `task.py post-marker` — when an agent posts a note that starts with a version stamp like `v1. ` right before `field:`-shaped content, it prints one stderr line telling the emitter the version belongs in `--version`, not the note head. The marker still posts; nothing blocks, no exit code changes.
- **What I expect:** the two note shapes already in the corpus that echo marker-version grammar into note heads (#1092's run note, #432's figure note) would both have been warned; plain prose that happens to start "v2. " stays silent, so the warning channel stays trustworthy.
- **What would change my mind:** if the negative-case tests or a corpus re-audit show a common *legitimate* note idiom that matches "stamp + field-led head", the predicate is too loose and I'd tighten it (or drop the check) rather than ship a noisy advisory.

### 3. Method delta (vs #1382 / #1120)

| Aspect | #1120 WARN (existing) | #1382 tolerance (existing) | This change |
|---|---|---|---|
| Side | Poster (CLI stderr) | Reader (parser) | Poster (CLI stderr) |
| Shape | literal `\n` escapes + field-led head | `v<k>. ` stamp before field anchor, per segment | `v<k>. ` stamp + field-led head, head-only |
| Gate | `--note` AND `\\n in note` AND no real `\n` | always (parse-side copy) | `--note` only; NO `\\n` gate (orthogonal shape) |
| Effect | advisory WARN | silent normalization | advisory WARN |

Two deltas beyond "add a sibling": (1) the new predicate requires the stamp to be **followed by field-led content**, byte-mirroring what the #1382 tolerance actually normalizes — a bare `v2. ` prose head is a shape the parser leaves alone, so warning on it would be a false positive; (2) `_looks_field_led` itself becomes stamp-tolerant (shared core-strip helper), restoring its documented parity with `parse_followup_note_field` and closing the blind spot where a stamped head defeated the #1120 WARN on a stamped+escaped note (verified: `_FIELD_LED_RE` cannot match `v1. field:` because `.` is outside its character class, so today that note gets no WARN at all).

```python
_FIELD_LED_RE = re.compile(r"^[A-Za-z_][A-Za-z0-9_-]*[:=]")
_VERSION_STAMP_RE = re.compile(r"^v\d+\.\s+")


def _stripped_note_core(note: str) -> tuple[str, bool]:
    """Note HEAD after the same per-segment decoration strip
    task_workflow.parse_followup_note_field applies: the leading
    whitespace/bullet/bold mix, then a lowercase `v<k>. ` version stamp
    (#1382). Returns (core, stamped); `stamped` records whether a stamp was
    stripped so the poster-side stamp advisory can key on it."""
    core = re.sub(r"^[\s\-*]+", "", note)
    stamp = _VERSION_STAMP_RE.match(core)
    if stamp:
        return core[stamp.end() :], True
    return core, False


def _looks_field_led(note: str) -> bool:
    """True when the note HEAD is a `field:` / `field=` line-core after the
    parse-side decoration strip — whitespace/bullet/bold, then the #1382
    `v<k>. ` version stamp (stamp tolerance added with #1440, restoring the
    documented parity with parse_followup_note_field). Head-only by design
    (false-positive-averse; see #1178 plan §4 D2)."""
    core, _ = _stripped_note_core(note)
    return bool(_FIELD_LED_RE.match(core))


def _looks_stamped_field_led(note: str) -> bool:
    """True when the note HEAD carries a `v<k>. ` version stamp followed by
    field-led content — the #1092 run-note shape whose read-side absorption
    is the #1382 parser tolerance. BOTH conditions required
    (false-positive-averse: a prose note that happens to start "v2. " never
    warns — the parser tolerance likewise only acts when a field anchor
    binds after the strip)."""
    core, stamped = _stripped_note_core(note)
    return stamped and bool(_FIELD_LED_RE.match(core))
```

Call-site wiring in `cmd_post_event` — a new independent `if` (NOT `elif`; the shapes are orthogonal and may co-occur) inserted immediately AFTER the existing #1120 WARN block (currently ending line 621), before `_safe_echo`:

```python
    if args.note is not None and _looks_stamped_field_led(note):
        # Poster-side twin of the #1382 parse-side version-stamp tolerance
        # (task_workflow.parse_followup_note_field): the note head echoes
        # the marker's `v<k>` grammar as a decorative `v<k>. ` stamp before
        # field-led content (the #1092 run-note shape). Read-side parsers
        # strip it silently, so nothing ever corrected the emitter — this
        # WARN does. Advisory only — the marker already posted; guarded
        # like the #1120 WARN above (#537 rc-contract class; a closed
        # stderr raises ValueError, not only OSError).
        with contextlib.suppress(OSError, ValueError):
            print(
                f"WARNING: task.py post-marker {args.marker}: --note head "
                "starts with a 'v<k>. ' version stamp before field-led "
                "content. The marker version is recorded from --version on "
                "the event row — do not echo it into the note head (field "
                "parsers strip the stamp, #1382, so THIS note still "
                "parses). Do NOT re-post this marker — it was posted "
                "successfully; drop the stamp from your NEXT marker's note "
                "instead.",
                file=sys.stderr,
            )
```

### 11. Decision Rationale

1. **Sibling WARN gated on any `--note` post, not nested under the `\\n` condition.** Why: the shapes are orthogonal — the motivating #1092 note is a `; `-joined single physical line with NO literal `\n`, so nesting would never fire on the very incident this task exists for. Source: `_NOTE_1092_RUN_V1` (tests/test_workflow_followup_labels.py:384-401) + task #1440 body.
2. **Stamp must be followed by field-led content (not any `v<k>. ` head).** Why: the #1382 tolerance only ACTS when a field anchor binds after the strip — a prose `v2. ` head is untouched read-side, so warning there is a pure false positive; false-positive aversion is the established design bar for this WARN family. Source: task_workflow.py:3061-3068 (#1382, commit 058ac134c6); #1178 plan §4 D2.
3. **Regex `^v\d+\.\s+`, lowercase-only, whitespace-required, applied AFTER the bullet/bold strip.** Why: byte-mirror of the parse-side strip order and shape, so the WARN's claim "parsers strip the stamp" is exactly true whenever it fires. Source: task_workflow.py:3057-3067 (#1382).
4. **`--file` exempt (gate on `args.note is not None`).** Why: parity with the #1120 WARN's documented `--file` escape-hatch exemption (`test_file_input_backslash_n_no_warn`); file bodies are long-form markdown where head shapes are arbitrary. Source: #1178 plan §4 D3 + scripts/task.py:602.
5. **`_looks_field_led` made stamp-tolerant (shared `_stripped_note_core`).** Why: its docstring promises parity with `parse_followup_note_field`'s per-segment strip; #1382 added the stamp strip read-side, so the twin drifted — and today a stamped head DEFEATS the #1120 WARN entirely (`.` is outside `_FIELD_LED_RE`'s class). Restoring parity closes that blind spot; risk is bounded because both call-site gates remain conjunctive. Source: scripts/task.py:137-143 docstring + #1382 diff; verified no existing test row flips.
6. **WARN text pattern (posted-successfully / do-NOT-re-post / actionable `--version` hint).** Why: proven emitter-steering shape; re-post prevention is load-bearing (a re-post duplicates the marker). Source: scripts/task.py:612-621 (#1120) + the #537 rc contract.
