## 3. Root cause

**Class A has a documented mechanism and an established verdict.** The
allowlist's own comment block (added by #2154 for #1739's identical row)
records it: `label=` is the CORRECT token for the same loop's
`stage=followup-<phase>` DISPATCH BREADCRUMBS
(`_breadcrumb_fields(note).get("label")`), carried onto the adjacent
COMPLETION marker by mistake. #2154 surveyed all 191 historical run markers
and concluded this was "the only bare-`label=` note" and "NOT systematic".
**That conclusion is now falsified** — 2203 adds two more, so the count is 3
across 2 tasks. A recurring hand-composition error needs a MECHANICAL guard,
not prose alone.

**The emitter channel already exists and is too narrow — inverted, in fact.**
`scripts/task.py cmd_post_event` carries two poster-side advisories:
`_looks_field_led` + literal-`\n` (#1120) and `_looks_stamped_field_led`
(#1382/#1984). Both fire only on shapes the parser ALREADY ABSORBS (they warn
about cosmetics on notes that parse fine) and stay SILENT on shapes that
actually fail to parse. So the one high-signal check — "does this note's
`followup_label` parse at all?" — is the one the emitter never makes, even
though it is exactly the gate's predicate.

Two further gaps in those advisories that this fix must not inherit:
- they are gated on `args.note is not None`, so a `--file` body is never
  checked. Class B's note (2054) is a long multi-section body — precisely the
  `--file` shape.
- they duplicate the parser's strip logic as local regexes
  (`_VERSION_STAMP_RE`, `_stripped_note_core`), which can drift from the
  parser it claims parity with.

- **Scope:** markers of kind `FOLLOWUP_RUN_KIND` (`epm:same-issue-followup-run`)

## 5. Alternatives rejected

1. **Widen the parser** (any of: accept bare `label` as an alias; add `·` as
   a segment delimiter; widen the stamp stripper to `v\d+\s+`; anchor fields
   mid-segment). REJECTED, and this is the task's central instruction:
   - `parse_followup_note_field` is generic over `source` / `round` /
     `outcome` / `est_gpu_hours` / `followup_ref`, so any widening changes
     run/unrun classification CORPUS-WIDE — the #545 lesson (tightening or
     loosening a parser against live producers converts one red into many).
     The #1111 field-only design is pinned by passing tests, including one
     asserting a mid-segment `(source: user-chat)` mention parses None.
   - Decisively: **no parser widening fixes any of the six.** Class C is the
     proof — even with the stamp stripper widened, the residue
     `source: … followup_label: …` is space-joined, so the field is still not
     at segment start; only mid-segment anchoring would parse it, and that is
     exactly what #1111 forbids. Widening would therefore add corpus-wide
     risk while leaving the red in place.
2. **Rewrite the six `events.jsonl` rows.** REJECTED — append-only log; and
   the task's constraints put `tasks/` out of scope.
3. **A new test asserting the allowlist has no STALE entries** (entries no
   longer in the corpus). REJECTED although it would make the growing
   allowlist self-maintaining: a reaped/deleted task folder would then RED
   MAIN — a new main-red channel, i.e. precisely the failure class this task
   exists to remove. Not worth the trade at 8 entries.
4. **Make the new advisory fatal (nonzero rc).** REJECTED — the marker is
   already appended by the time the check runs, so failing the command would
   report failure for a successful write and invite the duplicate-re-post
   mistake the existing advisories explicitly warn against.
