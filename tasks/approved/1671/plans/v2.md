    """Total wall bound for the abort lock-race retry loop
    (``EPM_ROOT_SYNC_ABORT_LOCK_WAIT_S``; mirrors INDEX_LOCK_WAIT_S)."""

### 4.2 The shared helper (inserted after `_pull_with_transient_retry`, ~:439)

```python
def _abort_with_lock_retry(
    repo: Path, report: dict, *args: str, check: bool = True
) -> subprocess.CompletedProcess[str]:
    """Run ``git <args>`` (a rebase/merge abort) with a bounded retry on
    transient lock contention: rc != 0 AND stderr matching ``_LOCK_RACE_RE``
    (a concurrent git writer on the shared root holds HEAD.lock / index.lock /
    a ref lock for milliseconds — the #1645 incident shape). Verified
    state-safe on git 2.34.1: a lock-blocked abort leaves the rebase/merge
    state intact, so re-running the SAME abort is idempotent (plan §12
    items 3-5). The named lock file is polled until it clears (NEVER
    deleted), bounded by ``_abort_lock_wait_s()`` total wall and
    ``_abort_lock_retries()`` re-invocations. On exhaustion this mirrors
    ``git()``'s contract exactly — ``check=True`` raises CalledProcessError
    carrying the FINAL attempt (the :1529 EXIT_UNEXPECTED conversion is
    unchanged); ``check=False`` returns the final CompletedProcess for the
    caller's existing discrimination. A NON-lock failure is returned/raised
    from the FIRST attempt — never retried."""
    deadline = time.monotonic() + _abort_lock_wait_s()
    retries = 0
    while True:
        res = git(repo, *args, check=False)
        if res.returncode == 0:
            if retries:
                _msg(
                    report,
                    f"`git {' '.join(args)}` succeeded on retry {retries} after "
                    "transient lock contention (concurrent git writer).",
                )
            return res
        m = _LOCK_RACE_RE.search(res.stderr)
        if m is None or retries >= _abort_lock_retries() or time.monotonic() >= deadline:
            break
        retries += 1
        raw = Path(m.group(1))
        lock = raw if raw.is_absolute() else repo / raw
        _msg(
            report,
            f"transient lock race on `git {' '.join(args)}` "
            f"(rc={res.returncode}: {lock.name} 'File exists') — bounded poll "
            f"then retry {retries}/{_abort_lock_retries()}.",
        )
        while lock.exists() and time.monotonic() < deadline:
            time.sleep(_abort_lock_poll_s())
    if m is not None:
        _msg(
            report,
            f"`git {' '.join(args)}` still lock-blocked after {retries} retr"
            f"{'y' if retries == 1 else 'ies'} within {_abort_lock_wait_s():.0f}s — "
            "surfacing the final failure unchanged (the lock file is NEVER "
            "deleted — a live git op may hold it).",
        )
    if check:
        raise subprocess.CalledProcessError(
            res.returncode, _git_argv(repo, *args), output=res.stdout, stderr=res.stderr
        )
    return res
```

Loop-shape notes (deliberate): (a) retry counting — with the default 2, total invocations = 3 (initial + 2), matching the sketch's "retry once or twice"; (b) after the inner poll exits at deadline the loop makes at most one more (cheap, possibly-successful) attempt before the deadline check breaks it — total invocations stay ≤ 1 + retries; (c) `m is None` on a nonzero rc breaks immediately — a non-lock failure never retries and never sleeps; (d) the raised `CalledProcessError(returncode, cmd, output, stderr)` carries exactly the fields `subprocess.run(check=True)` would, so the :1529 formatter (`e.cmd`, `e.returncode`, `e.stderr`) produces the identical exit-6 message.

### Design-question answers (explicit)

1. **Which sites:** ALL FOUR, via the shared helper. The incident hit :727, but :1254/:1329/:1348 have the identical exposure (a lock-race `CalledProcessError` → :1529 → exit 6 with the root mid-rebase — the exact Goal failure) and the fix is the same one-line substitution; leaving them out would re-file this bug the next time the race lands mid-conflict-abort. NOT extended to non-abort mutating calls (stash store/pop, fetch/pull/push): those have their own retry/timeout policies (`_run_bounded`, push retry, `_pull_with_transient_retry`) and failing them does NOT leave the root detached mid-rebase — out of the Goal's scope, listed under must-ask deviations.
2. **Detection predicate:** `rc != 0` AND stderr `re.search(r"Unable to create '([^']+\.lock)': File exists")`. Grounded on git's `lockfile.c` `unable_to_lock_message` (EEXIST branch prints exactly `Unable to create '%s.lock': %s.` with `%s` = `strerror(EEXIST)` = "File exists") and on three live probes (§2). Deliberately NOT keyed on rc==128 exactly: the measured aborts die with 128, but ref-lock failures inside other git codepaths can surface rc=1 with the same lockfile.c message; the stderr needle is the discriminating part and is emitted ONLY on lock EEXIST (a stale-lock "Permission denied" or any other errno prints a different suffix and does NOT match — conservative by construction). Never matches: the existing `simulated abort failure` fixture string, the head-name-less abort stderr, the `git am`-session abort stderr, "cannot lock ref … unable to fetch" shapes without the `.lock': File exists` tail.
3. **Retry policy:** total wall 60s (`EPM_ROOT_SYNC_ABORT_LOCK_WAIT_S`), poll 2.0s (`EPM_ROOT_SYNC_ABORT_LOCK_POLL_S`), max 2 re-invocations (`EPM_ROOT_SYNC_ABORT_LOCK_RETRIES`) — sources per §11. Env names follow the file's `EPM_ROOT_SYNC_*` function-accessor convention.
4. **On exhaustion:** the helper reproduces `git()`'s contract — check=False returns the final `CompletedProcess` (preflight's :737-757 discrimination and messages byte-identical); check=True raises `CalledProcessError` with the final attempt's `(returncode, argv, stdout, stderr)` (the :1529 exit-6 message byte-identical). Retry evidence lands ONLY as report `_msg` lines (printed to stderr by `_emit_report` and present in `--json` `messages`) — no raise-site message text changes. The lock file is never unlinked under any branch (the helper contains no `unlink`/`remove` call; asserted by test).
5. **Test plan:** §6.

## 11. Decision Rationale

- **Total wall bound = 60s (`EPM_ROOT_SYNC_ABORT_LOCK_WAIT_S`).** What: max wall the retry loop may consume. Why: transient writers hold these locks for milliseconds; 60s covers heavy fleet contention with huge margin while keeping the error path far under the 600s subprocess bound. Source: in-file `INDEX_LOCK_WAIT_S = 60.0` (:144, the same-file same-class precedent) + CLAUDE.md § Concurrent repo-root committers ("bounded poll … up to ~60 s", validated in fleet use 2026-07-22). Alternatives: 10s (rejected — under fleet-storm conditions multiple sequential writers can chain; the in-file precedent already chose 60), 600s (rejected — an error path should not stall the single-flight lock that long).
- **Poll interval = 2.0s (`EPM_ROOT_SYNC_ABORT_LOCK_POLL_S`).** What: sleep between lock-file existence checks. Why: cheap `Path.exists()` polls; 2s bounds added latency to one poll period in the common fast-clear case. Source: in-file `INDEX_LOCK_POLL_S = 2.0` (:145) and `acquire_task_workflow_lock`'s `time.sleep(min(2.0, remaining))` (:626). Alternatives: 0.1s (rejected — needless churn; tests override via env anyway).
- **Max re-invocations = 2 (`EPM_ROOT_SYNC_ABORT_LOCK_RETRIES`).** What: abort re-run count after the initial attempt. Why: each retry only fires after the previous attempt failed on the LOCK needle specifically; 2 covers the measured multi-lock sequence (a first retry can clear `HEAD.lock` and then hit `index.lock` from a second writer — both shapes measured in §2) while keeping invocations trivially bounded. Source: the filing's candidate sketch ("retry the abort once or twice") + the file's bounded-single-retry convention (`_pull_with_transient_retry` retries once; push retries once) extended by one for the measured two-lock sequence. Alternatives: 1 (rejected — doesn't cover the HEAD.lock-then-index.lock chain), unbounded-under-deadline (rejected — the file's convention is explicit small counts; the deadline alone can permit ~30 invocations at 2s poll). Count-bound reachability: this limit binds only when the named lock CLEARS between attempts while the abort keeps failing on a fresh lock needle (the two-lock chain); with a persistent lock the deadline binds first and the loop realizes 2 total invocations — test 8 is the dedicated pin of the count-bound branch.
- **Detection regex `Unable to create '([^']+\.lock)': File exists`.** What: the transient-lock needle + lock-path capture. Why: it is the exact `lockfile.c unable_to_lock_message` EEXIST output, invariant across the `error:`/`fatal:` prefix and absolute/relative path variants, and no other git failure emits it. Source: git 2.34.1 live probes (§2, three shapes measured 2026-07-25) + git source `lockfile.c` (the message is emitted only in the EEXIST branch; other errnos print their own `strerror` suffix, e.g. "Permission denied", which the needle rejects). Alternatives: keying on rc==128 exactly (rejected — over-narrow: ref-lock failures can surface rc=1 with the same message; the stderr needle is the discriminator and rc≠0 suffices), `HEAD\.lock`-only (rejected — §2 measured `index.lock` blocking both abort forms; sibling ref locks are the same transient class).
- **Shared helper across all four sites (vs preflight-only).** What: one `_abort_with_lock_retry`. Why/Source: §4 design-question 1 — identical exposure at :1254/:1329/:1348 (any lock-race there exits 6 with the root mid-rebase via :1529, the literal Goal failure); the file's own precedent of shared seam functions (`_pull_with_transient_retry`). Alternative: incident-site-only (rejected — re-files the same bug on the conflict/timeout paths).
- **Exhaustion reproduces `git()`'s contract exactly (raise `CalledProcessError` / return final `CompletedProcess`).** Why: the acceptance criterion "existing terminal error paths preserved verbatim" is then true by construction — no raise-site edits at all. Source: read of :727-757 and :1529-1534 (the two consumer shapes). Alternative: raising `SyncAbortError` directly from the helper (rejected — would duplicate + risk drifting the four sites' distinct terminal semantics).
