### 3b. Primary Anthropic docs (verified June 2026, `platform.claude.com`)

All facts below verified by fetching `platform.claude.com/docs/en/docs/build-with-claude/batch-processing` and `.../docs/en/api/rate-limits` (June 2026); line anchors are to the fetched doc:

1. **Caps (batch-processing doc, "How it works"):** *"A Message Batch is limited to either 100,000 Message requests or 256 MB in size, whichever is reached first."* The rate-limits doc's Message Batches table lists **"Maximum batch requests per batch" = 100,000** at every tier.
2. **24h expiry + `expires_at` (batch-processing doc):** *"You can access batch results when all messages have completed or after 24 hours, whichever comes first. Batches expire if processing does not complete within 24 hours."* The create response carries `"expires_at": "2024-09-25T18:37:24.100435Z"` (an ISO-8601 timestamp, = `created_at + 24h`), alongside `request_counts` and `processing_status`.
3. **`processing_status` enum:** *"It starts as `in_progress`, then updates to `ended` …"*; cancellation produces the intermediate *"`processing_status` will be `canceling`"* before `ended`. The three values are **`in_progress`, `canceling`, `ended`**. **CRITICAL:** the per-request counts (`succeeded`/`errored`/…) start at 0 and only populate when the batch ends — `processing=N, succeeded=0` is the EXPECTED in-progress state (this is #658's misdiagnosis), so `succeeded==0` must NEVER be a stuck heuristic.
4. **Per-request `result.type` enum (4 types):** `succeeded` / `errored` / `canceled` / `expired`. Doc table: *"`errored` — Request encountered an error … Possible errors include invalid requests and internal server errors. You will not be billed for these requests."*; `canceled` and `expired` likewise *"You will not be billed for these requests."* So **only `succeeded` is billed**; the other three are free.
5. **`errored` two-level split + non-retry rule:** the doc's own Python example branches `if result.result.error.error.type == "invalid_request_error":` → "Validation error" (do NOT retry — a malformed request will fail identically on resubmit; validation is *"performed asynchronously, and validation errors are returned when processing of the entire batch has ended"*) vs `else:` → "Server error" (retriable). Note the SDK path is **double-nested**: `result.result.error.error.type`.
6. **Retention:** *"Batch results are available for 29 days after creation. After that, you may still view the Batch, but its results will no longer be available for download."*
7. **`custom_id` constraint:** *"Must be 1 to 64 characters and contain only alphanumeric characters, hyphens, and underscores (matching `^[a-zA-Z0-9_-]{1,64}$`)."* A 64-char sha256 **hex** digest is `[0-9a-f]{64}` → matches exactly.
8. **Chunking + retry advice ("Best practices for effective batching"):** *"Consider breaking very large datasets into multiple batches for better manageability."* and *"Monitor batch processing status regularly and implement appropriate retry logic for failed requests."*
9. **Streaming + order:** *"Because of the potentially large size of the results, it's recommended to stream results back rather than download them all at once."* Results stream as `.jsonl` in **arbitrary order** — every doc example joins on `custom_id`, never positionally.
10. **Tier-4 queue floor (rate-limits doc, Message Batches table):** Tier 4 = **"Maximum batch requests in processing queue" = 500,000**, RPM = 4,000. The body's "we are above Tier 4, queue cap ≥ 500k" is therefore grounded in the Tier-4 *floor*; 8 concurrent sub-batches × ~8k = ~64k in-flight is ~13% of even the floor — concurrency is not the binding constraint.

**`safety-tooling` is NOT a drop-in fix:** the body verified (and the legacy `_chunk_requests`/`_submit_and_poll_batch` docstrings confirm "pattern from safety-tooling") that safety-tooling's client carries the SAME unbounded poll and SAME 100k chunk default — adopting it would re-import the defect. This is a from-scratch hardening of OUR client.

### 4a. `eval/batch_judge.py`

**(i) Drop the chunk-size default + keep the byte cap.**
```python
# Anthropic Batch API limits (verified platform.claude.com, June 2026):
#   hard caps = 100_000 requests OR 256 MB per batch, whichever first.
MAX_REQUESTS_PER_BATCH = 8_000          # was 100_000 — engineering choice (see §11)
MAX_BATCH_SIZE_BYTES = 250 * 1024 * 1024  # 250 MB safe margin under the 256 MB hard cap
```
`_chunk_requests` already splits on BOTH limits (`:134`) — leave its two-limit logic intact; only the default `max_count` changes via the constant. (Pseudocode shape unchanged: accumulate `req_size = len(json.dumps(req).encode())`; start a new chunk when `len(current_chunk) >= max_count` OR `current_size + req_size > MAX_BATCH_SIZE_BYTES`.) **Off-by-one mitigation:** the byte counter already sums the per-request JSON payload, not the HTTPS frame, and 250 MB leaves a 6 MB margin under the 256 MB hard cap — far larger than any single ~few-KB judge request, so a one-request overshoot cannot cross 256 MB.

**(ii) Deterministic `custom_id` helper** (shared, importable by `judge_dispatch` + the legacy path):
```python
import re
_CUSTOM_ID_RE = re.compile(r"^[a-zA-Z0-9_-]{1,64}$")

def make_custom_id(item_id: str) -> str:
    """Deterministic, regex-valid, idempotent custom_id for a judge item.

    sha256 hex is exactly 64 chars of [0-9a-f] -> matches ^[a-zA-Z0-9_-]{1,64}$.
    Stable across runs on the same item_id, so resubmits reuse the same id.
    """
    cid = hashlib.sha256(item_id.encode()).hexdigest()  # 64 hex chars
    assert _CUSTOM_ID_RE.match(cid), cid                  # cheap invariant
    return cid
```
Note: the live enumerator (`batch_judge._enumerate_and_check_cache`, `:236`) currently builds positional ids `f"{persona}__{idx:05d}__{comp_idx:02d}"`. Those already match the regex and are deterministic-given-ordering, but are NOT content-stable (re-ordering personas changes them). **Keep the public custom_id scheme as-is for backward-compatible cache/checkpoint keys** (changing it would invalidate every existing `.dispatch/` checkpoint and `JudgeCache` entry) — `make_custom_id` is used where a *content-stable* id is wanted (new call sites / the legacy path), and the test for "stable across two independent runs on the same input" targets `make_custom_id` directly. (The fingerprint that binds a checkpoint to its item *set* already uses content hashes — `_compute_fingerprint`, `:264` — so resume correctness does not depend on the custom_id being content-stable.)

**(iii) Rewrite legacy `_submit_and_poll_batch` to use the bounded poll + two-level branch.** It has no `src/` caller but IS imported by two live `scripts/issue_389` callers (A8 correction), so harden in place — never delete. The rewrite preserves the existing signature `(requests, client, poll_interval=, max_poll_interval=)`: submit via `_chunk_requests`, poll each sub-batch through the new `poll_until_ended(...)` (4c), collect via the new shared `_collect_batch_results` two-level branch (4b). The two `scripts/issue_389` callers inherit the bounded-poll fix for free; signature-preservation is verified by the import-sanity invocations in §6. ### 4b. `eval/judge_dispatch.py` — two-level terminal-state split + bounded poll

**(i) `_collect_batch_results` (`:372`) — split `errored` into invalid-request (quarantine) vs server-error (retriable).** Today it returns `(scores, errored, expired)`; the new shape returns a **quarantine list** distinct from the retriable list:
```python
def _collect_batch_results(client, batch_id, error_dict_factory):
    """Returns (scores, retriable_ids, expired_ids, quarantined_ids).

    Two-level branch per the Anthropic doc example:
      succeeded            -> parse + keep
      errored, error.error.type == 'invalid_request_error'
                           -> QUARANTINE (never retried; resubmit fails identically)
      errored, other (server) -> retriable
      expired              -> retriable (never reached the model; safe to resubmit)
      canceled / unknown   -> error dict, no retry (user-initiated terminal)
    """
    scores, retriable, expired, quarantined = {}, [], [], []
    for result in client.messages.batches.results(batch_id):
        cid, rtype = result.custom_id, result.result.type
        if rtype == "succeeded":
            text = next((b.text for b in result.result.message.content if b.type == "text"), "")
            parsed = parse_judge_json(text, None)
            scores[cid] = parsed if parsed is not None else error_dict_factory("parse_error")
        elif rtype == "errored":
            # SDK nesting is result.result.error.error.type (double .error) — doc example.
            etype = getattr(getattr(getattr(result.result, "error", None), "error", None), "type", None)
            if etype == "invalid_request_error":
                quarantined.append(cid)
                scores[cid] = error_dict_factory("batch_error: invalid_request_error (quarantined)")
            else:
                retriable.append(cid)
                scores[cid] = error_dict_factory(f"batch_error: errored ({etype or 'server'})")
        elif rtype == "expired":
            expired.append(cid); scores[cid] = error_dict_factory("batch_error: expired")
        else:  # canceled / unknown
            scores[cid] = error_dict_factory(f"batch_error: {rtype}")
    return scores, retriable, expired, quarantined
```
Thread the new `quarantined` list through `_run_batch_path`'s `_load_collected`/results-json persistence (add `"quarantined_ids"` next to `errored_ids`/`expired_ids` in the per-sub-batch `results_<batch_id>.json` and in `state.json`). **The retry pass (`_run_or_resume_retry`) consumes only `retriable + expired`, never `quarantined`** — so an `invalid_request_error` id never loops. Persist quarantined ids to a `quarantine.json` in the dispatch dir for inspection. (`getattr`-guarded access so the existing tests' `message=None` errored shape — which lacks `.error` — yields `etype=None` → routed to retriable, the conservative default that does not silently quarantine.)

**(ii) `_load_or_init_state` chunking (`:347`)** already calls `_chunk_requests(requests, max_count=sub_batch_size)` — the only change is the default `DEFAULT_SUB_BATCH_SIZE = 10_000 → 8_000` (`:102`). Existing checkpoints with a recorded `sub_batch_size` resume against their own value (the fingerprint/items.json guards already prevent mixing) — verify `_load_or_init_state` reads `sub_batch_size` from `state.json` on resume rather than the new default (it should; confirm at implementation and add a test if not).

**(iii) Bound the poll loop (`:557-587`).** Replace the unbounded `while any(... != "collected")` with a deadline derived from each sub-batch's `expires_at`, read off the retrieved batch object:
```python
import datetime as _dt
GRACE = _dt.timedelta(minutes=30)

def _deadline_for(batch) -> _dt.datetime:
    # SDK 0.88.0: batch.expires_at is a `datetime` (= created_at + 24h).
    # The doc's RAW JSON is an ISO-8601 string ("2024-09-25T18:37:24.100435Z"),
    # but the SDK deserializes before code sees it — production path is the
    # datetime branch. Keep the isinstance guard for the raw-dict fallback.
    exp = batch.expires_at
    if isinstance(exp, str):                          # raw-dict path (unwrapped SDK)
        exp = _dt.datetime.fromisoformat(exp.replace("Z", "+00:00"))
    if exp.tzinfo is None:                            # safety: assume UTC if naive
        exp = exp.replace(tzinfo=_dt.timezone.utc)
    return exp + GRACE

# per sub-batch, record deadline on first retrieve that exposes expires_at:
#   sb["deadline"] = _deadline_for(batch).isoformat()  (persist in state.json)
# loop:
now = _dt.datetime.now(_dt.timezone.utc)
overdue = [sb for sb in pending if sb.get("deadline") and now > _dt.datetime.fromisoformat(sb["deadline"])]
if overdue:
    for sb in overdue:                       # ONE final fetch to harvest partial results
        batch = client.messages.batches.retrieve(sb["batch_id"])
        if batch.processing_status == "ended":
            ... collect normally ...
        else:
            raise BatchDeadlineExceeded(sb["batch_id"], sb["deadline"])
```
`BatchDeadlineExceeded` is a new exception (4d) so callers surface it as `epm:failure v1 failure_class: infra` rather than hanging. The poll cadence stays ~60s (use `poll_interval`, default already 30→1.5× backoff to 120s cap — keep the existing backoff but cap the *total* wait by the deadline, not a step count). Clock is read via an injectable `now_fn=lambda: datetime.now(tz=utc)` parameter so the test can mock it (4c/§6).

### 4c. `llm/anthropic_client.py::AnthropicBatch.poll` — bounded, returns on deadline

Replace the bare `while True` (`:452`) with the same `expires_at`-bounded loop. Make it injectable for tests (`now_fn`, `sleep_fn`):
```python
async def poll(self, batch_id, interval_s=60.0, grace_min=30, now_fn=None, sleep_fn=None):
    """Poll until processing ends OR the batch's own expires_at + grace passes.

    On deadline with status still != 'ended', does ONE final retrieve and:
      - returns the batch if it has since ended (harvest partial results), else
      - raises BatchDeadlineExceeded (callers surface failure_class: infra).
    Never spins forever: the only bound is wall-clock vs the API's expires_at.
    """
    now_fn = now_fn or (lambda: datetime.now(timezone.utc))
    sleep_fn = sleep_fn or asyncio.sleep
    deadline = None
    while True:
        batch = self.retrieve(batch_id)
        if batch.processing_status == "ended":
            return batch
        if deadline is None and getattr(batch, "expires_at", None):
            deadline = _deadline(batch.expires_at, grace_min)
        if deadline is not None and now_fn() > deadline:
            final = self.retrieve(batch_id)               # one last harvest attempt
            if final.processing_status == "ended":
                return final
            raise BatchDeadlineExceeded(batch_id, deadline)
        await sleep_fn(interval_s)
```
This is the shared helper; factor `_deadline(expires_at_iso, grace_min)` into a small module-level function `batch_judge` and `judge_dispatch` both import (single source of truth for the ISO-parse + grace).

**Caller stability:** `AnthropicBatch.poll` keeps its signature additively (new kwargs default to None/asyncio.sleep), so `AnthropicBatch.__call__` (`:492`, `await self.poll(batch_id)`) and `openai_client.py`-parallel callers are unaffected. `__call__` should catch `BatchDeadlineExceeded` and let it propagate (it already returns `None` entries for missing results, so a partial harvest fits its `responses_by_id.get(cid)` contract).

### 4d. New sentinel exception

Add to `llm/anthropic_client.py` (importable from both modules):
```python
class BatchDeadlineExceeded(RuntimeError):
    """A batch did not reach 'ended' by expires_at + grace; partial results harvested.
    Callers surface this as epm:failure v1 failure_class: infra (never hang)."""
    def __init__(self, batch_id, deadline):
        super().__init__(f"batch {batch_id} not ended by deadline {deadline}")
        self.batch_id, self.deadline = batch_id, deadline
```

### 4e. Resume diff (custom_id-keyed) — already present, extended

The live path's resume already: loads `state.json`, skips `collected` sub-batches, never re-calls finished items (the `_RECONCILE_MSG` guard refuses silent resubmit). ## §11 Decision Rationale

**Training hyperparameters:** N/A — no model training. The load-bearing knobs here are the batch-client constants:

- **Chunk size `MAX_REQUESTS_PER_BATCH = 8_000` (also `DEFAULT_SUB_BATCH_SIZE = 8_000`).**
  - *What:* 8,000 requests per sub-batch (was 100,000 / 10,000).
  - *Why:* incremental progress + blast-radius isolation. A 90k judge run → ~12 sub-batches; one failing/expiring sub-batch loses ≤8k items (resumable by custom_id), not the whole run. Below the API's per-batch cap (100k) and far below the in-flight queue cap. The body specifies the 5,000–8,000 band; 8,000 is the top of it (fewest batches → least poll overhead) while still ~12 batches for 90k.
  - *Source:* `platform.claude.com/docs/en/docs/build-with-claude/batch-processing` ("Consider breaking very large datasets into multiple batches for better manageability"); task body §Required-behavior item 1. No official optimal number exists — engineering choice, as the body states.
  - *Alternatives:* 100k (current — the #658 wedge: ~90k in one batch, total-loss on any hang); 5,000 (more batches, more poll overhead, no robustness gain over 8k).

- **Byte cap `MAX_BATCH_SIZE_BYTES = 250 MB`.**
  - *What:* 250 MB safe ceiling, split alongside the request count.
  - *Why:* the API hard cap is 256 MB (>256 → `413 request_too_large`); 250 MB leaves a 6 MB margin >> any single judge request, so no chunk can cross the hard cap.
  - *Source:* batch-processing doc ("either 100,000 Message requests or 256 MB in size, whichever is reached first"). Already the value in code (`:39`) — unchanged.
  - *Alternatives:* 256 MB exact (no margin → boundary off-by-one risk); 128 MB (needlessly small, more batches).

- **Poll cadence ~60 s.**
  - *What:* `AnthropicBatch.poll` interval 60 s; `judge_dispatch` keeps its 30 s→1.5×→120 s backoff (mean ~60–120 s).
  - *Why:* most batches finish < 1h (doc); 60 s polling is ~60 retrieves/hour — negligible HTTP load against the Tier-4 4,000 RPM batch-endpoint limit, and fine-grained enough to harvest promptly.
  - *Source:* batch-processing doc ("most batches finishing in less than 1 hour"); rate-limits doc (batch RPM 4,000 at Tier 4). Body §Required-behavior item 2 ("Keep ~60s poll cadence").
  - *Alternatives:* 10 s (wasteful, no benefit — batches don't end that granularly); 5 min (slow harvest).

- **`expires_at` grace = 30 min.**
  - *What:* exit the poll when `now > expires_at + 30min`, then one final fetch.
  - *Why:* `expires_at = created_at + 24h` is the API's hard guarantee that `processing_status` reaches `ended`; the 30-min grace absorbs clock skew + the lag between expiry and the status flip, so we harvest the now-`ended` partial results rather than racing the flip.
  - *Source:* batch-processing doc ("Batches expire if processing does not complete within 24 hours"; create response carries `expires_at`). Body §Required-behavior item 2 ("exit the poll when now > expires_at + grace (e.g. +30 min), then do ONE final fetch").
  - *Alternatives:* 0 grace (races the expiry→ended flip, risks raising before the harvestable state); counter-based deadline (the body's named anti-pattern — #658 had no wall-clock bound; a fixed iteration counter doesn't track real elapsed time under variable poll backoff).

- **Concurrency bound `MAX_CONCURRENT_SUB_BATCHES = 8` (`asyncio.Semaphore`).**
  - *What:* at most 8 sub-batches submitted/in-flight concurrently.
  - *Why:* ~12 sub-batches for 90k × 8k ≈ 64k requests in-flight if all 8 run — ~13% of the Tier-4 *floor* in-flight queue cap (500k), so concurrency is nowhere near binding; chunk size is chosen for observability, not the cap. A small fixed bound (vs unbounded fan-out) keeps the create-call burst gentle against the 4,000 RPM batch-endpoint limit and bounds memory.
  - *Source:* rate-limits doc (Tier-4 "Maximum batch requests in processing queue" = 500,000; batch RPM = 4,000). Body §Required-behavior item 6 ("our org's limits are well above standard Tier 4 … concurrency is not the binding constraint").
  - *Alternatives:* unbounded fan-out (create-burst could trip the 4,000 RPM endpoint limit / acceleration limits; harder to reason about); 1 (sequential — slower wall time, no robustness gain).
