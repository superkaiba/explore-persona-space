## What v2 changes

v1 planned a pure review-and-land round. The pre-pass objected on two counts,
and inspecting the test file confirmed both:

All 27 existing tests are pure-unit tests of helpers — version parsing, config
read/write, candidate filtering, in-flight detection. There is **no test that
executes `main()`**, none for `probe_model`, none for `restart_app_server`, and
none for the wrapper. So the two most consequential behaviors in a *live daily
cron* are unpinned:

- **The dry-run kwarg thread.** `--dry-run` is threaded as `args.dry_run` into
  three separate decision sites (CLI install at line 521, the current-model
  probe at 564, the candidate probe/config-write at 599, plus
  `restart_app_server(args.dry_run)` at 637). Nothing asserts that a dry run
  mutates nothing. If any one of those threads breaks, the command this plan
  itself names as its verification path silently becomes a real mutation of a
  live config — the #596/#607/#633 pattern.
- **The wrapper's fail-loud arm.** `cd "$PROJECT_DIR" || exit 1` sits inside
  the brace group. The group is not a subshell, so that `exit 1` terminates the
  whole script *before* the `rc != 0` Telegram arm ever runs. On a VM with no
  MTA and a crontab that redirects stderr, a failed `cd` is a completely silent
  failure — defeating the alerting the wrapper was written to provide.

Both are cheap to close and both are exactly what a nine-day-live cron should
have. v2 therefore adds two tests and one wrapper fix.

## Method delta

The upgrader itself is not redesigned. It exists and has nine days of
production evidence; that evidence is stronger than any smoke this round could
run, and re-deriving its design would be waste. The round is **review + close
the two flagged gaps + land + reconcile.**

Three review targets found while reading the payload, for the ensemble to
confirm or overturn:

- **The wrapper `cd` gap** described above. v2 fixes it (§ File paths).
- **Wrapper doc/reality drift.** The header comment recommends
  `17 6 * * *`; the installed crontab is `17 7 * * *`. Harmless, but the
  comment is the only schedule documentation that will exist in the repo, so
  it gets corrected to match reality.
- **`main()` no-op-vs-broken interaction (lines 556-632).** The current-model
  probe records a failing model into `known_bad` *before* `candidate_models`
  filters on it, which is what makes the "broken current model still ranks
  best available" no-op impossible. `test_candidates_exclude_known_bad_for_same_cli_version`
  and `test_known_bad_is_rechecked_after_a_cli_upgrade` pin the filter itself;
  what is unpinned is that `main()` wires them in that order. The reviewer
  should confirm the ordering holds, because the whole recovery path rests on
  it.

### Landing mechanism — a recorded deviation from Step 4's worktree default

Committed **by explicit path directly on `main` at the repo root**, not via an
`issue-2322` worktree. Reason: the payload exists as *untracked files in the
repo-root working tree*, and the live crontab points at the repo-root path. A
worktree branch would land tracked files at three paths the root holds as
untracked, so the root's next `git pull` hits "untracked working tree files
would be overwritten by merge". `sync_repo_root.py` rescues that collision
rather than failing, but the collision is entirely avoidable and this is a
shared root with ~40 concurrent sessions. An explicit-path commit on `main` is
the documented concurrent-committer form (CLAUDE.md § Concurrent repo-root
committers) and is what the workflow-fix protocol already prescribes for
workflow-surface edits. Consequence: no Step 10d merge — Step 9c PASS is
immediately followed by the commit, and there is no worktree to reap.

Write-window discipline: the payload files are currently *untracked*, which is
the one working-tree state invisible to the pre-commit stash race, so they are
safe where they sit. The two edited files become tracked-modified only inside a
single write → `git add` → commit window
(`.claude/rules/repo-root-uncommitted-state.md`).

## Kill criteria

What would stop this landing rather than merely bounce a round:

- Review shows the upgrader can leave `~/.codex/config.toml` pointing at a
  model that has not just answered a probe. That would mean the live cron can
  silently break every twin dispatch, and the correct action is to disable the
  crontab line before landing anything.
- Review shows the in-flight abort can lose a running twin review (i.e. the
  2h `JOB_FRESH_WINDOW_S` bound can classify a genuinely live job as debris).
  That degrades a doubled review gate to single-Claude — the exact failure the
  payload's own docstring says it exists to prevent.
- The known-bad cache filter is keyed such that a broken current model is not
  excluded from candidates. That reinstates the "no-op that looks healthy"
  mode the design claims to close.
- The added dry-run test FAILS against the current code — i.e. `--dry-run`
  already mutates something. Then the verification path recorded in the task
  body was never a dry run, and the finding is reported before anything lands.

Any of those: post `epm:failure`, do not land, surface the live cron.

## Open item — the `model_reasoning_effort` discrepancy

Body Part 1 records `~/.codex/config.toml` `model_reasoning_effort`
`xhigh` → `high`. Live config reads `xhigh`. The upgrader provably did not do
this (it never writes that key — docstring and `write_config_model` both scope
to the top-level `model` key only, and
`test_write_config_model_replaces_only_the_model_line` pins that), so either a
later manual edit restored `xhigh` or the Part 1 record was wrong.

Disposition: **document, do not change.** The originating ask was "the best
model (with reasonable amount of thinking)", and for every EPS ensemble
dispatch that is already satisfied — `codex_task.py` passes `--effort high`
explicitly on the command line, which overrides the config default. The config
value therefore only governs Thomas's own interactive `codex` use, where
`xhigh` may well be his preference. Changing it would be an unrequested
mutation of a personal config outside the repo. Recorded in the body so the
next reader is not misled by the Part 1 claim.
