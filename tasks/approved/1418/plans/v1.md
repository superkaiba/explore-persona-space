## 4. Design

### 4.1 Resolution of the four design questions

**(a) FIRST clause (denied-parent contradiction) — FAIL on v4 only; WARN on v3/v2.** This is the incident class and a contradiction between two machine-readable facts, so it earns the hard FAIL — but only above the v4 sentinel, per the forward-only rule and the #1014/#1068 precedents. On v3/v2 it degrades to WARN (the exact #1068 grandfathering shape: a factual-consistency read is version-independent in substance, so it should still *surface* on old bodies, but never newly hard-FAIL them). Refinement over the candidate sketch: the FAIL fires only when the parent is ALSO unnamed in the scan region — a row that carries a denied-parent clause *and* names `#<parent_id>` is internally contradictory but not reader-misleading in the same way, and mechanically indistinguishable from e.g. "fresh direction on the eval surface; reuses #825 artifacts"; it gets a WARN (Lens 5 keeps the substantive read on Context-row WARNs, the documented residual pattern at docstring `:3950-3955`). Note the denied-claim regex includes bare `fresh direction` (no "no parent"): per SPEC `:680` and `test_v4_context_fresh_direction_alone_passes`, bare "fresh direction" is the sanctioned *parentless* lineage form — it IS the no-parent claim.

**(b) SECOND clause (parent present but unnamed) — WARN, not FAIL, v4 only.** Empirical grounding (verifier-exact scan — `_strip_blockquote_lines(_strip_fenced_blocks(repro))` sliced after the label, i.e. exactly `ctx_scan`): **32/32** v4 bodies in `tasks/completed/` + `tasks/awaiting_promotion/` carrying frontmatter `parent_id` reference `#<parent_id>` (or `/tasks/<parent_id>`) in the scan region, and **0** carry a denied-parent token. So a WARN is zero-noise on the committed corpus today while still nudging future bodies. FAIL is rejected because legitimate shapes exist that a FAIL would wrongly block: a lineage citing a grandparent/method-parent instead (the brief's re-scoped-parent case), a prose-form parent reference without the `#` sigil ("child of task 825"), or a follow-up-round-only clause. The WARN message names the escape ("keep the deliberate ancestor-only lineage and expect this WARN"). Not fired on v3/v2 — v3 never required a lineage clause at all (#1014 is v4-only), so demanding parent-naming there would be a new requirement on grandfathered bodies with no incident behind it.

**(c) Converse (no `parent_id`, lineage cites `#K`) — explicitly OUT of scope.** Measured: 6/10 committed v4 bodies *without* `parent_id` cite some `#K` in the scan region — all legitimate (reused-artifact producers, method parents, siblings, prior-round labels; SPEC's `[#K](...) — <one line>` covers general context links, and `parent_id` is only set by `task.py new --parent`). A converse check would false-fire on ~60% of that corpus. The failure direction it would guard (over-attributed lineage) is also not the incident class and errs toward MORE provenance, not false "fresh" claims. Documented as a deliberate residual in the docstring.

**(d) Plumbing — none.** `check_repro_context_provenance(body, fm, *, original_body_path=None)` already receives the frontmatter dict; the call site (`verify_text`, `:11525`) already passes it; the unit-grain tests already call it with plain dicts. The entire change is internal to `scripts/verify_task_body.py` + tests + a SPEC.md sync sentence.

### 4.2 Concrete diff-level changes (`scripts/verify_task_body.py`)

**(i) New module-level regex**, placed immediately after `_V4_CONTEXT_LINEAGE_TOKEN_RE` (`:3731`), with a comment cross-referencing the parent regex so the two alternates stay in sync:

```python
# Check-17 parent-lineage cross-check (#1418, incident #1345 r1): the
# no-parent-CLAIM subset of _V4_CONTEXT_LINEAGE_TOKEN_RE above (keep the
# two alternates in sync). Bare `fresh direction` counts: per SPEC.md
# § `**Context:**` row it is the sanctioned PARENTLESS lineage form.
_NO_PARENT_CLAIM_RE = re.compile(
    r"fresh\s+direction"
    r"|\bno\s+parent\b",
    re.IGNORECASE,
)
```

**(ii) New helper** `_parent_lineage_verdict(ctx_scan: str, fm: dict) -> tuple[str, str]`, placed next to `_origin_prompt_quote_verdict` (`:3832`), mirroring its `(status, detail)` shape:

```python
def _parent_lineage_verdict(ctx_scan: str, fm: dict) -> tuple[str, str]:
    """Classify the Context lineage clause against frontmatter parent_id.

    ``ctx_scan`` is the fence-stripped + blockquote-line-stripped text
    after the ``**Context:**`` label (the SAME region the v4 lineage-token
    sub-check scans, so claims/refs inside the blockquoted verbatim
    prompt never count — #959 precedent). Returns (status, detail):

    - "noop"             — no usable frontmatter parent_id;
    - "fail-denied"      — a fresh-direction / no-parent CLAIM with the
                           parent never referenced (the #1345 r1 incident
                           class; hard FAIL on v4, WARN on v3/v2);
    - "warn-denied-named" — a no-parent claim BUT #<parent_id> is also
                           referenced (internally contradictory row);
    - "warn-unnamed"     — no denied claim, but the lineage never
                           references #<parent_id> (v4-only WARN).
    """
    pid_raw = fm.get("parent_id")
    pid = str(pid_raw).strip() if pid_raw is not None else ""
    if not pid.isdigit():
        return "noop", "no frontmatter parent_id"
    denied = _NO_PARENT_CLAIM_RE.search(ctx_scan)
    named = re.search(rf"(?<![\w/&])#{pid}\b|/tasks/{pid}\b", ctx_scan)
    if denied and not named:
        return "fail-denied", (
            f"context-parent-lineage-contradiction: the `**Context:**` lineage claims "
            f"'{denied.group(0)}' but frontmatter carries `parent_id: {pid}` and the row "
            f"never references #{pid} — name the parent "
            f"(`[#{pid}](https://eps.superkaiba.com/tasks/{pid}) — <one line>`) or, if the "
            f"task was genuinely re-scoped as parentless, clear the frontmatter parent_id "
            f"(SPEC.md § `**Context:**` row)."
        )
    if denied and named:
        return "warn-denied-named", (
            f"context-parent-lineage-mixed: the row references #{pid} but ALSO carries a "
            f"'{denied.group(0)}' clause while frontmatter carries `parent_id: {pid}` — "
            f"drop the no-parent clause or state the re-scope explicitly."
        )
    if not named:
        return "warn-unnamed", (
            f"context-parent-unnamed: frontmatter carries `parent_id: {pid}` but the "
            f"`**Context:**` lineage never references #{pid} on a non-blockquote line — "
            f"name the parent, or keep a deliberate ancestor-only lineage and expect "
            f"this WARN."
        )
    return "noop", ""
```

Notes: `pid` is digits-only by construction, so no `re.escape` is needed; the `(?<![\w/&])#{pid}\b` form reuses `_V4_CONTEXT_LINEAGE_TOKEN_RE`'s lookbehind (no URL-fragment `page#123` / entity `&#123` matches; `\b` blocks `#82`↔`#825` prefix collisions); the `/tasks/{pid}\b` alternative accepts a dashboard-URL-only parent reference (`[parent](https://eps.superkaiba.com/tasks/825)`).

**(iii) v4 branch wiring** (inside `check_repro_context_provenance`, after the lineage-token search succeeds at `:4011`, BEFORE the origin-prompt sub-check — one failure at a time, the file's convention; the denied-contradiction is a lineage-correctness failure and precedes prompt-verbatimness):

```python

            # FIRST (lineage correctness before prompt verbatim-ness; one
```
