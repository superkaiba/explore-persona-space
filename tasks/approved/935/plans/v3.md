# Plan — #935: bounded done-grace self-poweroff for the GCE lane's clean-exit path

## 0.0 TL;DR (plain English)

- **What I'll run:** I'll add a bounded countdown to the GCE startup script's success tail — after a workload finishes cleanly and publishes `done`, the VM waits 90 minutes (tunable) for the orchestrator to pull its completion sentinel, then uploads that sentinel set to HF and powers itself off. No GPU runs; the change is code + tests + doc updates on the shared VM.
- **What I expect:** A finished GCE instance whose orchestrator has died can bill at most ~1.5 h instead of up to ~24 h (the daily-janitor worst case), and nothing the poller needs is ever lost — the sentinel survives on HF even when the poweroff destroys the boot disk.
- **What would change my mind:** If I find that a guest-initiated shutdown does NOT stop GPU billing on our instance config, or that the poller legitimately needs more than the grace window to drain a healthy run's sentinel, the design is wrong and I'd stop and re-plan (see Kill criteria).

## 4. Design

All edits are workflow-surface only: `src/explore_persona_space/backends/gcp.py` (in-scope per `workflow-fix-on-bug.md` — the backends router package), `tests/test_gcp_backend.py`, one regenerated fixture, and the prose files in §4.6. No experiment code, no `configs/`, no `tasks/`.

### 4.1 Chosen mechanism: (a) grace-bounded poweroff + (c)-lite persist-at-expiry; (b) rejected

- **(a) Grace-bounded self-poweroff — PRIMARY.** Foreground countdown at the very end of the startup script. Simple, bounded by construction, no new orchestrator-side machinery, correct whether the guest shutdown ends in DELETE or STOP (§12 A1).
- **(c)-lite persist-first — at EXPIRY only, not at done.** Uploading at `done` on every healthy run would duplicate what the poller drains seconds-to-minutes later and would make the HF prefix meaningless; uploading only on the poweroff branch keeps healthy runs byte-cheap and makes `issue<N>_done/<attempt_id>/` a precise signal: "the self-poweroff fired with an undrained sentinel; the run SUCCEEDED; recover from here." This is what makes a SHORT-ish grace safe for blocking-GATE exits too — gate sentinels are `/workspace/logs/issue-<N>-*.json` files and ride the same persist.
- **(b) Poller-ack — REJECTED.** Two reasons. (i) When the orchestrator is alive, finalize DELETEs the instance minutes after the drain anyway — an ack would shave only the drain→finalize window (~minutes) off a path that already ends promptly. (ii) When the orchestrator is dead — the incident class — no ack ever arrives and the grace timeout is the operative path regardless, so the ack leg adds a metadata-write (guest attributes are guest-writable only; an ack would need `instances add-metadata` or an ssh-touch threaded into `fetch_results`) + coupling for zero coverage of the actual failure mode.

### 4.2 Template change — the done-grace block

**Insertion point:** in `render_startup_script`'s `parts` list, immediately after the `"_eps_phase done"` entry (gcp.py L1894) — i.e. after the OOM guard, the clean-path watchdog reap, the sentinel write, and the done publish, satisfying the "poweroff sits AFTER whatever the success path already does" invariant. The tail is shared by both workload branches (`*workload_block` precedes it), so ONE code site covers hydra and `workload_cmd`.

**Render-time knob resolution** (near the top of `render_startup_script`, beside the existing constants):

```python
def _done_grace_seconds() -> int:
    """Render-time grace for the #935 done-grace self-poweroff (0 disables)."""
    raw = os.environ.get("EPS_GCP_DONE_POWEROFF_GRACE_SECONDS", "5400")
    try:
        return max(0, int(raw))
    except ValueError:
        logger.warning(
            "EPS_GCP_DONE_POWEROFF_GRACE_SECONDS=%r is not an integer; using 5400.", raw
        )
        return 5400
```

The resolved integer is baked into the rendered script (`EPS_DONE_GRACE=<n>`), matching the render-time pattern of the other lane constants; there is no runtime metadata fetch (the dispatcher env is the tuning surface, same as `EPS_GCP_QUEUE_WAIT_SECONDS` on the poller side).

**Helper functions** (defined in the preamble beside `_eps_reachability_watchdog` / `_eps_oom_count`, so both are in scope before the trap installs; shape below is the implementer's contract — exact quoting follows the existing list-of-strings style and MUST pass the `bash -n` validity test):

```bash
_eps_done_grace_poweroff() {
  local waited=0 tick=60 ph=""
  case "${EPS_DONE_GRACE:-0}" in (*[!0-9]*|""|0)
    { echo "[done-grace] disabled (EPS_DONE_GRACE=${EPS_DONE_GRACE:-})"; } 2>/dev/null || true
    return 0 ;;
  esac
  { echo "[done-grace] armed: self-poweroff in ${EPS_DONE_GRACE}s unless drained/aborted (#935)"; } 2>/dev/null || true
  while [ "$waited" -lt "$EPS_DONE_GRACE" ]; do
    sleep "$tick" 2>/dev/null || true
    waited=$((waited + tick))
    # Escape hatch 1: operator keepalive (documented in the #491 relaunch runbook).
    if [ -e "${EPS_DONE_KEEPALIVE_PATH:-/nonexistent}" ]; then
      { echo "[done-grace] keepalive present — aborting self-poweroff"; } 2>/dev/null || true
      return 0
    fi
    # Escape hatch 2: a sanctioned same-VM relaunch re-published eps/phase=workload
    # (REQUIRED by the #908 zombie predicates) — the relaunch owns the VM now.
    ph="$(curl -fsS -m 5 -H 'Metadata-Flavor: Google' 'http://metadata.google.internal/computeMetadata/v1/instance/guest-attributes/eps/phase' 2>/dev/null || true)"
    if [ -n "$ph" ] && [ "$ph" != "done" ]; then
      { echo "[done-grace] eps/phase=$ph — a relaunch owns the VM; aborting self-poweroff"; } 2>/dev/null || true
      return 0
    fi
  done
  _eps_persist_done_sentinels || true
  { echo "[done-grace] grace expired (${EPS_DONE_GRACE}s) — powering off to bound billing (#935)"; } 2>/dev/null || true
  shutdown -h now 2>/dev/null || poweroff -f 2>/dev/null || halt -f
}
```

Failure-mode notes baked into the shape (each is a #607-discipline point):
- A failed metadata read (`ph=""`) **continues the countdown** — it must never abort toward keep-billing; if the metadata server were down, a relaunch could not have re-published either.
- Every echo is `{ ...; } 2>/dev/null || true`-guarded (PIPE handler active); `sleep`/`curl` failures cannot abort under `set -e`; the loop is bounded by the `waited` counter, so the block can never hang forever.
- The final ladder mirrors the watchdog's exactly.
- Once aborted (relaunch case) the countdown does NOT re-arm for a second workload's `done` — the relaunch operator owns teardown per the existing #491 runbook (documented residual, §8).

**Persist helper** `_eps_persist_done_sentinels` — slim sibling of `_eps_persist_diagnostics`, mirroring its guarded/bounded/one-commit invocation pattern (same interpreter resolution as the existing heredoc, `timeout 120`, every step `|| true`):

```bash
_eps_persist_done_sentinels() {
  if [ -z "${EPS_HF_DATA_REPO:-}" ] || [ -z "${HF_TOKEN:-}" ]; then
    { echo "[done-grace] SKIP persist — EPS_HF_DATA_REPO/HF_TOKEN unset"; } 2>/dev/null || true
    return 0
  fi
  # stage (all guarded): /tmp/eps-done-persist/
  #   sentinel.json                  <- cp "$EPS_SENTINEL_PATH"
  #   logs_sentinels/issue-<N>-*.json <- cp any undrained epm:results / gate sentinels
  #   workload_tail.log              <- tail -c 5242880 "$EPS_LOG_PATH"  (5 MiB cap, non-LFS)
  #   done_report.json               <- {"issue","attempt_id","grace_s","ts"}
  # upload: ONE HfApi.upload_folder commit -> issue<N>_done/<attempt_id>/
  #   (never a per-file upload_file loop — the #664 504-storm gotcha)
  # bounded: timeout 120 around the python heredoc; rc swallowed with || true
}
```

Rendered constants beside the block: `EPS_DONE_GRACE=<baked int>`, `EPS_DONE_KEEPALIVE_PATH=/workspace/logs/issue-<N>-keepalive` (no `.json` suffix, so the poller's `issue-<N>-*.json` sentinel drain glob can never ingest it).

**Call site** (the new final lines of the script):

```python
"",
"# === Done-grace self-poweroff (#935): bound billing when the poller is dead ===",
"_eps_done_grace_poweroff || true",
```

Foreground, not a background daemon: nothing depends on startup-script completion (GCE startup scripts may run indefinitely — the #491 zombie proved it), the watchdog is already dead here, and a foreground call keeps the control flow trivially auditable. On the abort paths the script then exits rc=0 → the EXIT trap's `rc != 0` guard no-ops (crash path untouched).

### 4.3 Poll-classification change — `_non_running_poll_result`

Add a `done` branch beside the existing #669 `wedged` discrimination (gcp.py L4408-4419):

```python
if phase == "wedged":
    return _terminal_dead_poll(reason="wedged_terminated")
if phase == "done":
    # #935: the done-grace self-poweroff (or a manual stop of a done VM)
    # left a TERMINATED instance whose workload SUCCEEDED. Classify done,
    # not dead — fetch_results' sentinel scp will fail (VM off, fail-soft);
    # finalize needs --skip-confirm-artifacts; the HF issue<N>_done/ copy
    # (persisted at grace expiry) is the completion proof.
    return PollResult(
        status="done",
        current_phase="workload_done_self_poweroff",
        new_milestone=True,
        last_log_mtime_sec_ago=0,
        pid_alive=False,
        log_tail_excerpt="",
    )
```

Scope + safety of this mapping:
- **Only reachable when the shutdown ends in STOP rather than DELETE** (the on-demand-rung uncertainty, §12 A1) or during the transient STOPPING→DELETED window. A DELETEd instance 404s at describe and stays `dead("instance not found")` — no poll-side change can help there (no instance record); the explicit recovery breadcrumb is the HF `issue<N>_done/` prefix, documented in the SKILL.md prose update (§4.6).
- **No spot-preemption regression:** TERMINATED + any NON-terminal phase (`workload`, `startup`, "") falls through to `terminal_terminated` exactly as today — preemption and max-run-duration deaths mid-run keep their current classification (pinned by the new negative-control test).
- **No failover misfire:** `_is_gcp_async_workload_failure` (`scripts/backend_poll.py:366-396`) requires `status == "dead"` AND `current_phase ∈ {terminal_workload_failed, terminal_workload_wedged, terminal_wedged_terminated}` (and `_is_gcp_queue_timeout` adds `terminal_queue_timeout`); the new mapping returns `status="done"` with `current_phase="workload_done_self_poweroff"`, which fails BOTH conjuncts (verified: no consumer greps `workload_done` — only gcp.py itself constructs it; fact-check 2026-07-03).
- `reconnect_or_none` / `_stale_named_instance_or_none` interactions: a TERMINATED record is already `_NONLIVE_INSTANCE_STATUSES` → non-reconnectable and reclaim-deletable at the next launch; a RUNNING+`done` VM *within* the grace window is already refused + reclaimed by #908's `_ZOMBIE_GUEST_PHASES` predicates. Both next-launch defenses become backstops, unchanged in code.

## 11. Decision Rationale

- **Grace default = 5400 s (90 min).**
  What: the countdown before self-poweroff. Why: it must strictly exceed the worst-case sentinel-drain latency — the adaptive bg-poll's max quiet interval is 1800 s (`backend_poll.py` / SKILL.md Step 6d.2), so a workload finishing right after a quiet tick is detected ≤1800 s later and drained within that same tick; 5400 s = 3× that bound absorbs one fully-missed tick plus a slow drain/fetch with margin, while still cutting the worst-case billing ~13-16× vs the janitor. Source: `POLL_INTERVAL_QUIET_SEC = 1800` (`scripts/poll_pipeline.py:378` + `src/explore_persona_space/backends/base.py:329`, lane-shared; `backend_poll.py` only passes `next_interval` through) + the brief's 75-120 min band; safety factor 3 mirrors the project's poller-floor sizing style (`RUNPOD_WEDGE_K_SEC` = 900 s vs the 600 s ssh window). Alternatives: 75 min (2.5×, thinner margin for no meaningful billing saving), 120 min (4×, pays 30 extra idle minutes for margin the persist leg already makes unnecessary).
- **Knob name `EPS_GCP_DONE_POWEROFF_GRACE_SECONDS`, render-time resolution.** Why: matches the lane's existing `EPS_GCP_*_SECONDS` naming (`EPS_GCP_QUEUE_WAIT_SECONDS`) and the render-time constant-baking pattern; the dispatcher env is the established tuning surface. Source: `backends/gcp.py` / `backend_poll.py` precedent. Alternatives: runtime metadata fetch (adds a passthrough key + fetch stanza for no gain — the value is not secret and not per-run-mutable after boot).
- **Foreground call, not a watchdog-style background daemon.** Why: nothing consumes startup-script completion; foreground keeps ordering trivially provable (after `_eps_phase done`) and avoids a second long-lived in-guest poweroff actor (the #854 reap discipline exists precisely because two actors raced). Source: #491 (scripts may run indefinitely) + #854 (watchdog-reap-at-trap-entry rationale). Alternatives: bg daemon (needed only if something waited on script exit; nothing does).
- **Abort signal = `eps/phase != done` + keepalive file.** Why: the phase re-publish is ALREADY mandatory for any same-VM relaunch (#908 zombie predicates delete a RUNNING+terminal-phase VM at next dispatch), so the countdown reuses an enforced contract instead of inventing a new one; the keepalive file covers the metadata-server-degraded corner and gives operators a zero-knowledge escape. Source: #908 / gotchas.md #491 recipe. Alternatives: poller-ack (§4.1, rejected); no abort (powers off sanctioned relaunches — unacceptable).
- **Persist-at-expiry, not persist-at-done; dedicated slim helper + `issue<N>_done/` prefix, not `_eps_persist_diagnostics` reuse.** Why: at-done uploads would fire on EVERY healthy run (duplicating the drain seconds later, diluting the prefix's meaning); the crash helper targets `issue<N>_partial/` (rc=0 entries there would pollute crash forensics — "check `issue<N>_partial/` after a crash" must stay precise) and sweeps `$WORKLOAD_ROOT`-relative dirs, which structurally MISSES the `/workspace/logs/issue-<N>-*.json` sentinel dir this fix must protect. Source: #658/#854 helper scope (read from the heredoc, L1355-1520) + Upload Policy (text/JSON uploads always). Alternatives: reuse crash helper with an rc=0 flag (prefix pollution + wrong sweep scope), persist-at-done (noise), no persist (a dead-orchestrator expiry would destroy the gate/results sentinels with the boot disk — the exact loss the brief bars).
- **Poll mapping TERMINATED+`done` → `done` (`workload_done_self_poweroff`).** Why: without it, a STOP-outcome self-poweroff (or the transient STOPPING window) misclassifies a SUCCESSFUL run as `dead`/`terminal_terminated`, and a revived orchestrator would spin crash-fix machinery on a run whose artifacts are all on HF. The `phase` read on TERMINATED instances is already shipped behavior (#669's `wedged` discrimination — in-repo proof guest attributes are readable on TERMINATED). Source: #669 `_non_running_poll_result` + the no-consumer grep for `workload_done`. Alternatives: no mapping (accept the misclassification; rejected — 6 lines + 2 tests buys correct classification and covers the §12 A1 uncertainty), HF-probe on `instance not found` (too heavy for the poll path; the prose breadcrumb covers it).
- **Tick = 60 s (fixed, no knob).** Why: 60 s bounds the post-relaunch poweroff-race window to ≤1 tick while adding trivial load (one local metadata GET/min); no plausible tuning need. Source: bounded-race arithmetic (≤1-tick window) + the GCP guest-attributes metadata rate limit of 10 queries/min per VM (docs: manage-guest-attributes) — 1 GET/min is 6× under the cap; the tick must never shrink below ~6 s (comment this next to the loop). The "#669 watchdog cadence" precedent is UNVERIFIED and non-load-bearing. Alternatives: knob (surface area for no demonstrated need).
