## 0.0 TL;DR

- **What I'll change:** `RunPodBackend.launch` gains a launch leg that, when the caller opts in, SSHes into the freshly provisioned pod, syncs the clone to the run's branch, and starts the workload detached (setsid + nohup + pidfile + log), verifying liveness (launcher PID or a fresh pod-side pidfile) before returning. The automated GCP→RunPod failover paths opt in automatically (they have no experimenter); the interactive `/issue` flow is byte-unchanged (its experimenter stays the executor). ## 1. Goal / requirement + acceptance criteria

Make the RunPod lane capable of executing `spec.workload_cmd` on the pod it provisions, without double-launching against the experimenter-driven interactive flow, and fail LOUD when a requested execution did not start.

**Resolution of the required design question (hard constraint 4).** The brief's suggested rule "execute iff `spec.workload_cmd` is set; the experimenter flow passes none" is **FALSE as stated** — verified: `dispatch_issue.py::main()` (lines 1722–1733) requires exactly one of `--workload-cmd` / `--hydra` on every `launch`, and SKILL.md Step 6b (lines 2870–2873) mandates passing the plan's launch command via `--workload-cmd` on ALL lanes, after which Step 6d.1 (SKILL.md 3237–3241, 3352+) spawns the experimenter to execute it on RunPod pods. So on the interactive lane, `RunPodBackend.launch` DOES receive a non-empty `workload_cmd` today, and unconditional execution would double-launch. The clean rule is therefore:

> **Execute iff `spec.workload_cmd` is non-empty AND `spec.extra["execute_workload"]` is truthy.** The opt-in is set (a) automatically inside `router.failover_to_runpod_after_async_workload_crash` — the single seam all four automated no-experimenter failover paths funnel into (wedge + CUDA-IMA via `_relaunch_fresh_runpod`, backend_poll.py:1428; async GCP crash + FLEX_START queue timeout via `_failover_gcp_to_runpod`, backend_poll.py:2479) — and (b) explicitly via a new `dispatch_issue.py launch --execute-workload` flag for manual/orchestrator failover-style launches. The interactive Step 6b/6d.1 flow passes no flag and is behavior-unchanged (experimenter remains the sole executor there; no SKILL.md change needed). Sync route()-time RunPod outcomes (capacity fallback `auto_fallback_runpod`, sync `gcp_workload_failover_runpod`) happen inside a live `dispatch_issue.py launch` call where the orchestrator has Step 6d.1 downstream — they correctly stay opt-out.

Additionally verified: NOTHING executes the workload on the fresh pod after an automated failover today (no SKILL.md handler exists for `gcp_workload_failover_runpod_async` / the wedge fresh-pod phases — grep returned zero hits), so the failover paths are the primary consumer, exactly as the clarify note says.

**Acceptance criteria (numbered, testable):**

1. With `workload_cmd` set + opt-in: `launch()` provisions, syncs the pod clone to `spec.extra["repo_branch"]` (default `main`) with a pod-side `HEAD == FETCH_HEAD` verification (never trusting pull stdout), ensures `/workspace/logs` exists, writes `/workspace/launch_issue_<N>.sh`, detaches it via `setsid nohup bash <launcher> > <log_path> 2>&1 < /dev/null &`, and — from a SEPARATE SSH invocation — verifies liveness: `LAUNCH-OK` iff the canonical pidfile PID is alive, OR a fresh `/workspace/logs/*.pid` written after launch carries a live PID (GCP self-daemonizing-driver parity, gcp.py:1162–1188), AND the log exists. **(a) Branch sync** (one SSH call; fetch+reset, never pull — defeats the silent index.lock and divergent-`.claude/**` traps from gotchas.md):

```sh
set -eu
export PATH="/root/.local/bin:$PATH"
cd /workspace/explore-persona-space
pgrep -x git >/dev/null 2>&1 || rm -f .git/index.lock
git fetch origin "refs/heads/<B>"
git checkout -q -f -B "<B>" FETCH_HEAD
git reset --hard -q FETCH_HEAD
HEAD_SHA=$(git rev-parse HEAD); FETCH_SHA=$(git rev-parse FETCH_HEAD)
[ "$HEAD_SHA" = "$FETCH_SHA" ] || { echo "SYNC-MISMATCH head=$HEAD_SHA fetch=$FETCH_SHA" >&2; exit 3; }
echo "SYNC-OK $HEAD_SHA"
```
VM side parses `SYNC-OK <sha>`; anything else → raise. (Pod-side `reset --hard` is explicitly sanctioned — the VM-tree ban does not apply to the disposable pod clone; the task's diff sketch prescribes exactly fetch+reset.)

**(b) Write launcher + detach** (one SSH call; `set -eu` on the outer portion so a failed mkdir/cat cannot reach the detach line; a live-PID double-fire guard converts a flag+experimenter double-launch into a loud no-op; heredoc write, then the gotchas.md bg-ssh idiom with stdin redirect):

```sh
set -eu
mkdir -p /workspace/logs
OLD_PID=$(cat /workspace/logs/issue-<N>.pid 2>/dev/null || true)
if [ -n "$OLD_PID" ] && kill -0 "$OLD_PID" 2>/dev/null; then
  echo "ALREADY-RUNNING pid=$OLD_PID" >&2; exit 5
fi
rm -f /workspace/logs/issue-<N>.pid
date +%s > /workspace/logs/issue-<N>.launch_epoch
cat > /workspace/launch_issue_<N>.sh << 'EPSEOF'
#!/bin/bash
set -uo pipefail
export PATH="/root/.local/bin:$PATH"
cd /workspace/explore-persona-space
set -a; [ -f .env ] && source .env; set +a
export REPO_ROOT="${REPO_ROOT:-/workspace/explore-persona-space}"
export WANDB_PROJECT="${WANDB_PROJECT:-issue<N>}"
echo $$ > /workspace/logs/issue-<N>.pid
<workload_cmd verbatim>
EPSEOF
chmod +x /workspace/launch_issue_<N>.sh
setsid nohup bash /workspace/launch_issue_<N>.sh > <log> 2>&1 < /dev/null &
echo "WRAPPER-STARTED $!"
```
(No `[phase=` literal anywhere in these scripts' prose — the experimenter.md phase-token hygiene rule. `ALREADY-RUNNING` → `RunPodWorkloadStartError` naming the live PID + both executors — the double-fire guard, Claude-alternatives C2. The `launch_epoch` stamp anchors script (c)'s fresh-pidfile check. Fresh provisions have no stale pidfiles; the guard costs nothing there.)

**(c) Verify** (a SEPARATE SSH invocation ~3 s later — per experimenter.md, a same-session probe cannot catch SIGHUP-on-disconnect death). GCP-parity: a self-daemonizing driver (forks the real work, launcher exits) is ALIVE iff a fresh pod-side pidfile written after launch carries a live PID (gcp.py:1162–1188 convention — mandatory absorb, Codex-alternatives MF2):

```sh
LAUNCH_EPOCH=$(cat /workspace/logs/issue-<N>.launch_epoch 2>/dev/null || echo 0)
PID=$(cat /workspace/logs/issue-<N>.pid 2>/dev/null || true)
if [ -n "$PID" ] && kill -0 "$PID" 2>/dev/null && [ -f "<log>" ]; then
  echo "LAUNCH-OK pid=$PID"; exit 0
fi
# Launcher PID gone: accept any FRESH pod-side pidfile (mtime >= launch epoch)
# whose PID is alive — the GCP self-daemonizing-driver convention.
for f in /workspace/logs/*.pid; do
  [ -f "$f" ] || continue
  [ "$(stat -c %Y "$f" 2>/dev/null || echo 0)" -ge "$LAUNCH_EPOCH" ] || continue
  FPID=$(cat "$f" 2>/dev/null || true)
  if [ -n "$FPID" ] && kill -0 "$FPID" 2>/dev/null && [ -f "<log>" ]; then
    echo "LAUNCH-OK pid=$FPID via=$f"; exit 0
  fi
done
echo "LAUNCH-DEAD pid=${PID:-none}"
tail -20 "<log>" 2>/dev/null || true
exit 4
```
VM side parses `LAUNCH-OK pid=<int>`; `LAUNCH-DEAD` / rc!=0 → `RunPodWorkloadStartError` carrying the tail (message notes: "if the workload self-daemonizes without writing a pod-side pidfile, check the pod before treating this as dead"). The pod is left RUNNING for diagnosis (RunPod-as-diagnosis-lane doctrine).

## 10. §11 Decision Rationale (design choices; hyperparameters: N/A — no model training)

- **Execute iff `workload_cmd` set AND `execute_workload` opt-in** — Why: unconditional execution double-launches the interactive lane (verified §1). Source: dispatch_issue.py:1722–1733 + SKILL.md:2870–2873/3237+ + clarify-note design consideration (3); incident #763 (task body).
- **Parse-time rejection of `--execute-workload` without `--workload-cmd` (AC3a)** — Why: the flag+hydra cell otherwise recreates the #763 silent false-green through the fix's own surface (leg no-ops, no WARNING fires, belt-and-suspenders can't trigger, ok:true on a paid pod). Source: statistics reconciler round-1 upheld Must-Fix; the adjacent exactly-one-of guard idiom (dispatch_issue.py:1722–1733).
- **Opt-in auto-set at the async-failover seam** — Why: those paths provably have no executor today; one router seam covers all four (via two backend_poll wrappers). Source: router.py:2462; backend_poll.py:1428 + :2479; compute-backend-failover.md.
- **setsid launcher-script reuse (no new pattern)** — Source: experimenter.md § During Execution (736–785); gotchas.md SSH idioms (stdin redirect; `sh` not bash; uv PATH); brief constraint "reuse/mirror, do NOT invent".
- **Fresh-pidfile acceptance in the verify leg (GCP parity)** — Why: self-daemonizing drivers (fork + exit) otherwise read false LAUNCH-DEAD, escalating a healthy automated failover to a terminal infra failure. Source: gcp.py:1046–1052, 1162–1188 (the fresh-`*.pid` convention, added after eps-issue-601); alternatives reconciler round-1 mandatory absorb.
- **fetch + `checkout -f -B` + `reset --hard` + HEAD==FETCH_HEAD, never `pull`** — Why: defeats the silent index.lock exit-0 pull and divergent-`.claude/**` ff-only block. Source: gotchas.md (both pod git-sync entries, incidents #653 r5/r6); task diff sketch ("fetch + reset").
- **`repo_branch` persisted + threaded + explicit-runpod default extension** — Why: per-issue dispatch scripts exist only on issue branches; a failover exec against `main` is a guaranteed crash, and the #763-shaped manual command would otherwise sync `main`. Source: SKILL.md:3090–3096 (`--repo-branch` MANDATORY, #595); dispatch_issue.py:853–902 (:857 gate).
- **Fail-loud typed error, pod kept alive** — Source: CLAUDE.md fail-fast rule; RunPod-as-diagnosis-lane doctrine (compute-backend-failover.md Part B); task constraint 5.
- **No `exec` before the workload line** — Why: arbitrary command lines (env prefixes, compounds) are not exec-able; launcher-PID (or fresh-pidfile) liveness suffices for `poll_once`. Source: gcp.py:1111–1118 (verbatim-embedding doctrine) vs experimenter.md:744–748.
- **Runbook line in compute-backend-failover.md** — Why: the manual-pivot operator must know the flag UP FRONT, not discover it from the launch JSON after a wasted provision. Source: alternatives reconciler round-1 mandatory absorb (Claude C3); the file already documents the manual pivot + #763 with zero `--execute-workload` mentions (grep-verified round 1).
