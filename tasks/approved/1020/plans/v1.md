# Plan — #1020: codex_task result-fetch retry + `--reattach <job_id>` mode

## Plan Summary

**Change:** two recovery affordances in `scripts/codex_task.py` (1093 lines, the
codex-companion wrapper): (1) the single-shot `_fetch_result` call is wrapped in a
bounded, fetch-only retry (default 3 re-probes, 5–15 s jittered backoff, with a
status-probe discriminator logged between attempts) so a transient
`No job found for "<id>"` from `codex-companion result` no longer declares a
completed 10–60 min Codex job lost; (2) a new `--reattach <job_id>` mode skips the
spawn and drives an EXISTING job through the unchanged poll loop, stall detector,
result fetch, output-preservation write, and marker posts — the recovery path for a
wrapper/session kill that orphaned a running job. **Never re-dispatches from either
path**: exit 7 stays outside `TRANSIENT_FAIL_EXIT_CODES`; the reattach branch
bypasses both re-dispatch loops entirely (there is no prompt to re-dispatch).
**Exit-code contract unchanged** (7 = result-fetch ultimately failed; 4 gains the
sibling meaning "reattach target not queryable"). Markers reuse the existing kinds
only — the reattach path posts `epm:codex-task-spawned` with a `reattach=true`
token in the free-text note. Plus: new test file, two 1-line `_args` fixture
updates, one adoption sentence in CLAUDE.md, one descriptive-prose amendment in

## 1. Goal

Retry the result-fetch before declaring a Codex job lost, and support re-attach to
an already-spawned codex-companion job after a wrapper kill, instead of re-paying
the whole 10–60 min Codex run. Motivating evidence (2026-07-02 /daily sweep): ≥7
transient Codex dispatch failures across sessions — `codex-companion result`
reported `No job found` while the job had actually run (helper exits 5/7/8), and
wrapper kills left orphaned running jobs, each costing a full re-dispatch.

### Requirements

- **R1 (fetch retry):** on a result-fetch failure (nonzero exit from
  `codex-companion result <job-id>`, including the `No job found` class, OR a
  subprocess timeout/OSError from the fetch call itself), re-probe the fetch up to
  `--result-fetch-retry-cap` (default 3) times with jittered backoff before
  declaring the job lost. Retry ONLY the fetch — never the whole job. Exit 7
  remains the terminal meaning and remains excluded from the #579 transient
  whole-job re-dispatch class.
- **R2 (--reattach):** `--reattach <job_id>` skips spawn, polls the EXISTING job to
  a terminal phase reusing `_poll_until_terminal` (incl. the progress-aware stall
  detector and `--max-wait-secs` cap), fetches the result (with the R1 retry),
  writes the output file via `_write_output_preserving_codex_artifact`, and posts
  the same `epm:codex-task-spawned` / `epm:codex-task-completed` /
  `epm:codex-task-failed` markers. No re-dispatch on any failure (impossible — no
  prompt). Unknown job id → clean, fast failure with a failure marker.

### Acceptance criteria

1. A fetch that fails twice with `No job found ...` then succeeds returns the
   result; the helper exits 0 and posts `epm:codex-task-completed`. No re-spawn.
2. A fetch that fails on every attempt exits 7 with ONE `epm:codex-task-failed`
   whose note carries the attempt count, the last stderr, and the status-probe
   discriminator (`job known, phase=<p>` vs `job unknown`). `_spawn_codex` is
   called exactly once for the whole helper run (no whole-job re-dispatch on 7).
3. `--reattach <live-job-id> --output-file F --issue N` polls to done, writes F
   (preserving a pre-existing sentinel-bearing verdict at F into place, final
   message to `F.final-msg.md`), posts spawned(reattach=true) + completed markers,
   exits 0, and never calls `_spawn_codex`.
4. `--reattach <unknown-id>` exits 4 after a bounded probe retry with a failure
   marker; never enters the poll loop's 10×30 s probe-error crawl; never spawns.
5. `--reattach` with `--prompt`/`--prompt-file` is an argparse error (exit 2);
   reattach mode never reads stdin.
6. All 29 existing tests in `tests/test_codex_task_*.py` still pass;
   `uv run ruff check scripts/codex_task.py` clean;
   `uv run python scripts/workflow_lint.py` (no-flags default) passes.

## 2. Grounded companion-CLI behavior (read from source — do not re-derive)

Companion: `~/.claude/plugins/cache/openai-codex/codex/1.0.4/scripts/codex-companion.mjs`
(single install; `_resolve_companion()` picks the max version). All thrown errors
land in `main().catch` → message on **stderr**, `process.exitCode = 1`
(codex-companion.mjs:1023-1026). Verified facts:

- **`result <job-id>`** (`handleResult` → `resolveResultJob`,
  `lib/job-control.mjs:256-279` + `matchJobReference` :191-211): filters the jobs
  index on `status ∈ {completed, failed, cancelled}` then matches the id. For a
  NON-EMPTY job id the ONLY reachable error strings are:
  - `No job found for "<id>". Run /codex:status to list known jobs.` — thrown by
    `matchJobReference` when the id has no match among TERMINAL-status jobs. This
    single string covers ALL THREE cases: job genuinely unknown, job known but its
    index row still says `running` (registry lag / lost update), and job pruned.
  - `Job reference "<id>" is ambiguous. Use a longer job id.` — prefix collision
    (we always pass full ids; effectively unreachable).
  - The `Job <id> is still <status>...` and `No finished job found...` branches
    (lines 271/275/278) are **unreachable for a non-empty id** — `matchJobReference`
    throws first. ⇒ **the companion CANNOT tell the helper "result pending" vs
    "job unknown" via `result`**; the discriminator must be a `status` probe, and
    the retry must be time-bounded and blind (see Kill criteria — this IS the
    fallback design).
  - `handleResult` is a **pure read** (`resolveResultJob` + `readStoredJob`; no
    `upsertJob`/`writeJobFile`) — safe to re-invoke arbitrarily.
- **`status <job-id> --json`** (`handleStatus` → `buildSingleJobSnapshot`,
  job-control.mjs:242-254): exit 0 with `{workspaceRoot, job:{phase, status,
  logFile, ...}}` for ANY known job (running or terminal; the same default-predicate
  `matchJobReference`); unknown id → exit 1 +
  `No job found for "<id>". Run /codex:status to list known jobs.`
  `_probe_phase` already maps that to `("probe-error", stderr, None)`.
- **The transient mechanism** (`lib/state.mjs`): the jobs index is a single
  `state.json` written **non-atomically** (`fs.writeFileSync` in place, line 114 —
  no tmp+rename, no lock) and read-modify-written (`updateState`, :118-122) by
  EVERY concurrent wrapper's progress upserts (all pinned to the same
  `DISPATCH_ROOT` workspace). A torn read hits `loadState`'s bare `catch` →
  `defaultState()` → `jobs: []` (:58-78) → `No job found` for a job that is
  milliseconds from being readable again. This is the transient class the retry
  recovers.
- **The permanent class** (`state.mjs:80-113`): `saveState` prunes the index to the
  `MAX_JOBS = 50` most-recently-updated jobs AND **deletes** evicted jobs' per-job
  files + logs. A completed-but-unfetched job evicted by 50 newer jobs is
  unrecoverable — the bounded retry then honestly exhausts to exit 7 (≤ ~45 s +
  4 subprocess calls wasted; acceptable).
- **Completion write order** (`lib/tracked-jobs.mjs:158-175`): per-job file
  (`writeJobFile`) BEFORE the index (`upsertJob`) — a second, narrower lag window
  consistent with "status said done, result said No job found".
- **Latent crash fixed en passant:** `_fetch_result` (`codex_task.py:547-556`) does
  not catch `subprocess.TimeoutExpired`/`OSError`, and neither does any caller —
  today a 120 s fetch timeout crashes the helper with an unhandled traceback and NO
  failure marker. The retry wrapper's `except (subprocess.SubprocessError, OSError)`
  closes this.

## 3. Method delta (vs the existing retry machinery — who owns which failure class)

| Mechanism | Failure class it owns | Action | Cap / backoff | Change here |
|---|---|---|---|---|
| Cancelled-retry loop (`main`, `--cancelled-retry-cap=2`) | terminal `phase=cancelled` | **re-dispatch whole job** (fresh spawn, same prompt) | 2, no backoff | untouched; **inert in reattach mode** (no prompt) |
| #579 transient-retry loop (`main`, `--transient-retry-cap=1`, `TRANSIENT_FAIL_EXIT_CODES={3,4,5,8}`) | spawn fail / post-spawn probe fail / probe-error cap / stall | **re-dispatch whole job** | 1, 15 s + U(0,30 s) | untouched; exit 7 stays EXCLUDED (re-running a completed job, e.g. after an AUP refusal, is wrong — in-file comment at :169-173); **inert in reattach mode** |
| Poll-loop probe tolerance (`_poll_until_terminal`, `--probe-error-cap=10`) | transient `status` failures mid-poll | keep polling | 10 consecutive | untouched; reattach reuses it verbatim |
| **NEW: fetch retry** (`_fetch_result_with_retry`, `--result-fetch-retry-cap=3`) | nonzero `codex-companion result` (incl. `No job found` torn-read/lag class) + fetch subprocess timeout/OSError | **re-fetch ONLY** — never re-spawn, never re-poll | 3 re-probes, 5 s + U(0,10 s) each | new; wraps the `_fetch_result` call site inside the attempt |
| **NEW: reattach confirm-probe retry** (`_run_reattach`) | transient `status` failure at attach time | re-probe status | same constants as fetch retry | new; distinguishes fast unknown-id failure (exit 4) from the 5-min poll-loop crawl |

Boundary statement: the fetch retry lives INSIDE the attempt (at the
`_fetch_result` call site in the extracted `_finalize_result`), returns the same
`AttemptResult("fail", 7, ...)` on exhaustion, and `TRANSIENT_FAIL_EXIT_CODES` is
not modified — so the whole-job re-dispatch loops cannot fire on a fetch failure,
exactly as today. The reattach path returns from `main()` before either re-dispatch
loop is reached.

### 4.1 Constants (after `TRANSIENT_RETRY_BACKOFF_JITTER_SECS`, ~line 181)

```python
# Result-fetch retry (task #1020). `codex-companion result <job-id>` reads a
# shared state.json jobs index written NON-ATOMICALLY (fs.writeFileSync in
# place, no lock) and read-modify-written by every concurrent wrapper; a torn
# read parses as an EMPTY jobs list (loadState's bare catch -> defaultState),
# so the CLI exits 1 with 'No job found for "<id>" ...' even though the job
# ran to completion (>=7 incidents on 2026-07-02, each re-paying a 10-60 min
# Codex run). The retry re-probes the FETCH ONLY - never the whole job: exit 7
# stays OUT of TRANSIENT_FAIL_EXIT_CODES (re-dispatching a completed job, e.g.
# after an AUP refusal, is wrong; see that comment above). The companion's
# 'result' error string cannot distinguish job-unknown from result-not-yet-
# indexed (matchJobReference throws the same message for both), so the retry
# is blind but time-bounded; a status probe between attempts is logged as a
# diagnostic discriminator only. Backoff is shorter than the whole-job
# re-dispatch backoff: the failure is a ms-scale torn read / seconds-scale
# index lag, not an app-server restart. Jitter desynchronizes parallel
# reviewer ensembles (same rationale as TRANSIENT_RETRY_BACKOFF_*).
DEFAULT_RESULT_FETCH_RETRY_CAP = 3
RESULT_FETCH_RETRY_BACKOFF_FLOOR_SECS = 5.0
RESULT_FETCH_RETRY_BACKOFF_JITTER_SECS = 10.0
```

### 4.2 `_fetch_result_with_retry` (new, next to `_fetch_result` ~line 557)

`_fetch_result` itself is UNCHANGED (stays the single-shot primitive; existing
tests monkeypatch it and keep working through the wrapper, which calls the
module-level name).

```python
def _fetch_result_with_retry(
    companion: Path, job_id: str, retry_cap: int
) -> tuple[int, str, str, str]:
    """Bounded blind retry around _fetch_result. Returns (rc, stdout, stderr,
    detail); detail is "" on success, else the attempt count + the last
    status-probe discriminator for the exit-7 failure note. Also converts a
    fetch-subprocess TimeoutExpired/OSError (previously an unhandled crash
    with NO failure marker) into a retryable, then terminal-exit-7, failure."""
    total = 1 + max(0, retry_cap)
    rc, stdout, stderr = 1, "", ""
    for attempt in range(1, total + 1):
        try:
            rc, stdout, stderr = _fetch_result(companion, job_id)
        except (subprocess.SubprocessError, OSError) as exc:
            rc, stdout, stderr = -1, "", f"fetch raised: {exc}"
        if rc == 0:
            return rc, stdout, stderr, ""
        if attempt == total:
            break
        # Diagnostic discriminator (logging + final note only, never branching):
        phase, err, _ = _probe_phase_safe(companion, job_id)
        disc = (
            f"status-probe: job unknown/unreadable ({phase}: {err[:150]})"
            if phase in {"probe-error", "shape-error"}
            else f"status-probe: job known, phase={phase}"
        )
        delay = RESULT_FETCH_RETRY_BACKOFF_FLOOR_SECS + random.uniform(
            0.0, RESULT_FETCH_RETRY_BACKOFF_JITTER_SECS
        )
        print(
            f"WARN: result-fetch attempt {attempt}/{total} for {job_id} failed "
            f"(exit {rc}: {stderr[:200]}); {disc}; retrying in {delay:.0f}s (#1020).",
            file=sys.stderr,
        )
        time.sleep(delay)
    phase, err, _ = _probe_phase_safe(companion, job_id)
    disc = (... same two-branch string ...)
    return rc, stdout, stderr, f"after {total} attempt(s); {disc}"
```

`_probe_phase_safe` is a 6-line wrapper: `try: return _probe_phase(...)` /
`except Exception as exc: return "probe-error", f"probe raised: {exc}", None` —
`_probe_phase` can itself raise TimeoutExpired (uncaught today) and a diagnostic
probe must never crash the retry loop. (Implementer may inline this instead;
deviation allowed.)

### 4.4 `_run_reattach` (new)

```python
def _run_reattach(companion: Path, args) -> int:
    """Attach to an EXISTING codex-companion job (wrapper-kill recovery,
    #1020): confirm the job is queryable (bounded probe retry), post
    epm:codex-task-spawned with a reattach=true note token, reuse
    _poll_until_terminal (stall detector re-armed, timer starting at attach
    so pre-attach log silence is not counted), then _finalize_result with
    pre_output_key=None so a verdict Codex wrote to --output-file BEFORE the
    original wrapper died is preserved (final message -> .final-msg.md).
    No re-dispatch on ANY failure - there is no prompt to re-dispatch."""
    global _active_job_id
    job_id = args.reattach
    _active_job_id = job_id          # SIGTERM/SIGINT handler now cancels this job
    total = 1 + max(0, args.result_fetch_retry_cap)
    phase, err, log_path = "probe-error", "", None
    for attempt in range(1, total + 1):
        phase, err, log_path = _probe_phase(companion, job_id)
        if phase not in {"probe-error", "shape-error"}:
            break
        if attempt < total:
            delay = RESULT_FETCH_RETRY_BACKOFF_FLOOR_SECS + random.uniform(
                0.0, RESULT_FETCH_RETRY_BACKOFF_JITTER_SECS)
            print(f"WARN: reattach probe {attempt}/{total} for {job_id} failed "
                  f"({phase}: {err[:200]}); retrying in {delay:.0f}s.", file=sys.stderr)
            time.sleep(delay)
    if phase in {"probe-error", "shape-error"}:
        return _fail(args.issue, job_id,
                     f"reattach: job not queryable after {total} probe(s) "
                     f"({phase}): {err[:400]}", 4)
    if args.issue is not None:
        _post_marker(args.issue, "epm:codex-task-spawned",
            (f"Codex job_id={job_id} reattach=true phase_at_attach={phase} "
             f"poll_interval={args.poll_interval_secs}s "
             f"max_wait={args.max_wait_secs}s "
             f"probe_error_cap={args.probe_error_cap} "
             f"stall_detect={args.stall_detect_secs}s"))
    started = time.time()
    if phase in TERMINAL_PHASES:
        terminal = phase             # finished during the orphan gap: skip polling
    else:
        outcome = _poll_until_terminal(companion, job_id, args, log_path, started)
        if isinstance(outcome, AttemptResult):
            return _fail(args.issue, job_id, f"reattach: {outcome.note}",
                         outcome.exit_code)
        terminal = outcome
    result = _finalize_result(companion, job_id, terminal, args, None, started)
    if result.kind == "done":
        return 0
    note = result.note
    if result.kind == "cancelled":
        note = f"{note} (reattach mode: no re-dispatch possible)"
    return _fail(args.issue, job_id, f"reattach: {note}", result.exit_code)
```

Design decisions embedded here (rationale in §11):
- **Marker:** REUSE `epm:codex-task-spawned` with a `reattach=true` note token.
  The note is free text (workflow.yaml `fields:` is descriptive prose); downstream
  consumers pair spawned→completed/failed by `job_id=` in the note, and that
  pairing invariant is preserved. A NEW marker kind would be a schema addition =
  architectural = out of scope per the task constraints.
- **Stall detector re-armed**, timer origin = attach time (`_poll_until_terminal`
  initializes `last_log_change_ts = time.time()`): a job whose log went silent
  during the orphan gap gets one full `--stall-detect-secs` window before
  force-cancel, instead of an instant false positive.
- **Already-terminal short-circuit:** the common case (job finished while
  orphaned) skips the poll loop's leading 30 s sleep and goes straight to fetch.
- **`pre_output_key=None`:** `_key_advanced(current, None)` is True for any
  readable file, so an existing sentinel-bearing (`<!-- epm:`) verdict at
  `--output-file` — plausibly written by Codex BEFORE the original wrapper died,
  i.e. before any snapshot this process could take — is preserved and the final
  chat message lands in the `.final-msg.md` sidecar. A snapshot-at-attach key
  would classify that verdict as "stale" and clobber it (the exact #604 incident
  class this function exists to prevent).
- **Exit codes:** unknown/unqueryable job → 4 (the existing "probe failed / bad
  job-id" meaning); poll bails keep 5/6/8; fetch exhaustion → 7; terminal
  failed/cancelled → 1; done → 0. In reattach mode exits 3/4/5/8 do NOT trigger
  the transient re-dispatch loop (never reached — `_run_reattach` returns directly
  from `main`).

## 6. Kill criteria

- **If `codex-companion result` mutated state on read**, re-invoking it would be
  unsafe → VERIFIED FALSE before planning (`handleResult` is a pure read;
  §2). Moot.
- **The companion cannot distinguish job-unknown from result-not-yet-indexed** —
  CONFIRMED TRUE (§2: one `No job found` string for both). Consequence baked in:
  the retry is time-bounded and blind; the status probe is a logged diagnostic
  only, never a branch condition. There is no deeper fallback to fall to — this IS
  the fallback design. If review finds the diagnostic probe adds more failure
  surface than value, dropping it (pure blind retry) is an allowed deviation.
- **If the dominant 2026-07-02 cause turns out to be MAX_JOBS=50 pruning**
  (permanent, not transient), the fetch retry buys nothing for those instances
  (costs ≤ ~45 s before the honest exit 7) — `--reattach` still pays for itself,
  and the pruning fix would live in the vendored plugin (OUT of our workflow
  surface; would be surfaced as a prose follow-up, not fixed here). Not a reason
  to drop R1: the torn-read mechanism is real and unlocked at ≥7 incidents/day
  fleet concurrency.
- **If any downstream consumer of `epm:codex-task-spawned` breaks on a
  reattach-post** (e.g. treats every spawned marker as a NEW dispatch for
  counting): fallback = post NO spawned marker in reattach mode (terminal markers
  only) — a smaller footprint, still contract-clean. Must-ask before switching to

## 11. Decision Rationale

1. **`DEFAULT_RESULT_FETCH_RETRY_CAP = 3`** — Source: task #1020 body ("re-probe
   the job registry 2-3x with backoff"); picked the upper end because the cost
   asymmetry is extreme (a wasted retry ≤ 45 s vs a false lost-job = a 10–60 min
   Codex re-dispatch); magnitude consistent with the in-file
   `DEFAULT_CANCELLED_RETRY_CAP = 2` and `PROBE_ERROR_CAP = 10` conventions.
   Alternatives: 2 (task-body floor — allowed deviation), unbounded (rejected:
   pruned jobs are permanent, §2).
2. **Backoff `5.0 s + U(0, 10 s)` per re-probe** — Source: mechanism read from the
   companion source (§2: torn `fs.writeFileSync` read = ms-scale;
   `updateState` read-modify-write lag = seconds), so 5–15 s × 3 spans 15–45 s ≫
   both windows; jitter rationale copied from the in-file
   `TRANSIENT_RETRY_BACKOFF_*` comment (desynchronize parallel reviewer
   ensembles). Deliberately SHORTER than the 15 s/30 s whole-job constants — those
   are sized for an app-server restart; this is a pure registry read.
   Alternative: reuse 15/30 (rejected — triples worst-case latency-to-honest-
   exit-7 with no mechanism gain; allowed deviation if reviewer prefers symmetry).
3. **Retry scope = fetch only; exit 7 stays outside `TRANSIENT_FAIL_EXIT_CODES`**
   — Source: the in-file #579 comment (codex_task.py:169-173 — re-running a
   completed job on an AUP refusal is wrong) + the task clarifier. Non-negotiable
   (must-ask to change).
4. **Blind, time-bounded retry with a logging-only status discriminator** —
   Source: read of `lib/job-control.mjs:191-279` proving `result`'s error string
   is identical for job-unknown and result-not-yet-indexed (the "still running"
   branch is unreachable for non-empty ids), so no reliable branch condition
   exists; the discriminator still goes into the exit-7 note because it tells the
   orchestrator whether `--reattach` (job known) or re-dispatch (job unknown) is
   the right manual recovery.
5. **Reattach marker = existing `epm:codex-task-spawned` kind + `reattach=true`
   note token** — Source: workflow.yaml § markers (:1574-1577) — kinds/versions
   are the public contract (architectural to add), the `fields:` line is
   descriptive prose; existing notes are already `key=value` free text and
   downstream pairing keys on `job_id=`. Preserves the spawned→terminal pairing
   invariant. Alternative: no spawned marker on reattach (fallback per §6);
   new kind (rejected: architectural).
6. **Reattach unknown-job exit code = 4** — Source: the in-file exit-code table
   (docstring + `_run_one_attempt`): 4 already means "job-id not queryable after
   spawn" — the semantically identical failure; no new exit codes introduced.
7. **Reattach re-arms the stall detector, timer origin = attach time** — Source:
   `DEFAULT_STALL_DETECT_SECS = 600` in-file + `_poll_until_terminal`'s existing
   `last_log_change_ts = time.time()` initialization; pre-attach log silence
   (the orphan gap) must not count toward the window or every reattach to a
   long-orphaned-but-healthy job would insta-cancel. No code change needed —
   the existing loop already has this property; the decision is to NOT special-
   case it.
8. **`pre_output_key=None` in reattach's finalize** — Source: the #604 incident
   rationale in `_write_output_preserving_codex_artifact`'s docstring
   (codex_task.py:559-589): the verdict may predate this process, so the
   "advanced since snapshot" predicate cannot see it; preservation asymmetry
   (verdict loss ≫ stale sidecar). Alternative (snapshot at attach) rejected —
   it recreates the exact clobber the function exists to prevent.
9. **Confirm-probe retry on reattach reuses the fetch-retry constants** — Source:
   same transient class (torn `state.json` read, §2); avoids inventing a third
   backoff convention. Bounded fast-fail (≤ ~45 s) vs the poll loop's
   10 × 30 s = 5 min probe-error crawl for a typo'd job id.
