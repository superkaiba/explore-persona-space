### 2.2 What the CommonMark spec establishes

Quoted from CommonMark 0.31.2 §4.5 "Fenced code blocks" (<https://spec.commonmark.org/0.31.2/#fenced-code-blocks>), fetched at plan time:

- "A code fence is a sequence of at least three consecutive backtick characters (`` ` ``) or tildes (`~`). (Tildes and backticks cannot be mixed.)"
- "A fenced code block begins with a code fence, preceded by up to three spaces of indentation."
- "The line with the opening code fence may optionally contain some text following the code fence; this is trimmed of leading and trailing spaces or tabs and called the info string. If the info string comes after a backtick fence, it may not contain any backtick characters."
- A closing fence must be "a closing code fence of the same type as the code block began with (backticks or tildes), and with at least as many backticks or tildes as the opening code fence"; "The closing code fence may be preceded by up to three spaces of indentation, and may be followed only by spaces or tabs, which are ignored"; "Closing code fences cannot have info strings."
- "If the end of the containing block (or document) is reached and no closing code fence has been found, the code block contains all of the lines after the opening code fence until the end of the containing block (or document)."

From §4.4 "Indented code blocks" (<https://spec.commonmark.org/0.31.2/#indented-code-blocks>):

- An indented chunk is "a sequence of non-blank lines, each preceded by four or more spaces of indentation."
- "An indented code block cannot interrupt a paragraph, so there must be a blank line between a paragraph and a following indented code block."

The second §4.4 sentence is why this plan does not mask indented lines as code (§11 R2): a line-local `line.startswith("    ")` test cannot tell an indented code block from a paragraph continuation or a nested list item, and inside a list item the indentation baseline shifts.

## 4. Design

### 4.1 The mask change (`scripts/verify_plan.py`, lines 719-742)

One private scan function carries the whole implementation; `_fence_mask` and a new `unclosed_fence_line` are thin wrappers over it, so there is exactly one copy of the rule (the repo's Supersede convention).

Insert immediately above line 719, replacing lines 719-742 with:

```python
# CommonMark 0.31.2 §4.5: a code fence is 3+ consecutive backticks OR 3+
# tildes (never mixed), preceded by up to three spaces of indentation. A
# tab, or a fourth space, puts the line at indentation >= 4, where §4.4
# indented-code territory begins and no fence is recognized.
_FENCE_RE = re.compile(r"^ {0,3}(?P<delim>`{3,}|~{3,})(?P<info>.*)$")


def _fence_scan(lines: list[str]) -> tuple[list[bool], int | None]:
    """Single implementation of the fence walk (#2641).

    Returns ``(mask, unclosed_open_idx)``: the per-line in-code mask, and
    the 0-based index of an opening fence never closed before end of
    document (``None`` when every fence closed).

    CommonMark 0.31.2 §4.5, the four rules the pre-#2641 mask ignored:
    the closing fence must use the SAME character as the opener; it must
    be AT LEAST as long; it may carry no info string ("Closing code
    fences cannot have info strings"); and a backtick opener's info
    string "may not contain any backtick characters". Plus §4.5's
    indentation bound: a fence is "preceded by up to three spaces of
    indentation". An unclosed fence runs to end of document ("the code
    block contains all of the lines after the opening code fence until
    the end of the containing block (or document)").

    DELIBERATE, MEASURED DEVIATION from strict CommonMark: a line at
    indentation >= 4 that is NOT inside a fence is left UNMASKED rather
    than treated as a §4.4 indented code block. §4.4 says an indented
    code block "cannot interrupt a paragraph", and inside a list item
    the indentation baseline shifts, so a line-local indent test cannot
    distinguish indented code from a paragraph continuation or a nested
    bullet. Measured over 4,761 persisted plan versions: masking them
    changes 937 files (26,520 lines) instead of 153 files (10,882
    lines), which is a different and much larger semantics change than
    this task's Goal. Indentation here gates fence RECOGNITION only.
    """
    mask: list[bool] = []
    fence: str | None = None
    open_idx: int | None = None
    for i, line in enumerate(lines):
        m = _FENCE_RE.match(line)
        if fence is not None:
            if (
                m is not None
                and m.group("delim")[0] == fence[0]
                and len(m.group("delim")) >= len(fence)
                and not m.group("info").strip()
            ):
                fence = None
                open_idx = None
            mask.append(True)
            continue
        if m is not None and not (m.group("delim")[0] == "`" and "`" in m.group("info")):
            fence = m.group("delim")
            open_idx = i
            mask.append(True)
            continue
        mask.append(False)
    return mask, open_idx


def _fence_mask(lines: list[str]) -> list[bool]:
    """Per-line mask: True when the line is a fence delimiter or inside a
    fenced code block, per CommonMark 0.31.2 §4.5 (delimiter CHARACTER and
    LENGTH aware; see :func:`_fence_scan` for the exact rules and the one
    deliberate deviation).

    Line-count preserving: exactly one bool per input line, so callers
    that index raw<->stripped keep their mapping.

    NOT parity with ``verify_task_body.find_h2_sections`` any more (#2641):
    that module's 25 sibling toggle sites still carry the pre-#2641
    delimiter-blind rule. Propagating this fix there is filed as a
    follow-up; until it lands the two verifiers read fences differently
    and neither docstring should claim otherwise.
    """
    return _fence_scan(lines)[0]


def unclosed_fence_line(lines: list[str]) -> int | None:
    """0-based index of a fence opened and never closed before end of
    document, else ``None``. CommonMark reads everything after such an
    opener as code, so every fence-aware check silently sees the document
    only up to that line; ``main()`` surfaces this on stderr (#2641)."""
    return _fence_scan(lines)[1]


def strip_fences(text: str) -> str:
    """Return ``text`` with fenced code blocks (and the fence delimiter
    lines) removed, so example commands inside fences can neither satisfy
    nor trip a prose-contract check.

    Fence boundaries follow CommonMark 0.31.2 §4.5 via :func:`_fence_mask`.
    An UNCLOSED fence therefore removes the whole tail of the document;
    :func:`unclosed_fence_line` detects that condition and ``main()``
    reports it (#2641)."""
    lines = text.splitlines()
    mask = _fence_mask(lines)
    return "\n".join(line for line, fenced in zip(lines, mask, strict=True) if not fenced)
```

`_FENCE_RE` is a free name at `origin/main` (`grep -n "_FENCE_RE" scripts/verify_plan.py` returns only `_C25_FENCE_RE` at 4745 and its use at 4831). No call site of `_fence_mask` or `strip_fences` changes: the signatures are identical.

Regex notes, each tied to a spec sentence in §2.2:
- `^ {0,3}` allows literal spaces only. A leading tab advances to column 4, so a tab-indented fence line correctly fails to match.
- `` `{3,}|~{3,} `` forbids mixing by construction ("Tildes and backticks cannot be mixed").
- `m.group("delim")[0] == fence[0]` enforces "same type as the code block began with".
- `len(...) >= len(fence)` enforces "at least as many".
- `not m.group("info").strip()` enforces "Closing code fences cannot have info strings" while allowing the permitted trailing "spaces or tabs, which are ignored".
- The opener guard `not (delim[0] == "`" and "`" in info)` enforces "If the info string comes after a backtick fence, it may not contain any backtick characters". A tilde fence's info string may contain anything, including tildes and backticks, and the guard correctly does not apply to it.

- `mask_diff(paths)` — stage 1. For each corpus file, compare `_blind_fence_mask` with the live `verify_plan._fence_mask`; emit the changing set. Measured wall at plan time: **~40 s** for 4,761 files, single process.
- `verdict_diff(paths, kind_mode)` — stage 2. For each mask-changing file, run `verify_plan.verify_plan_text(text, kind=k)` twice, once with `verify_plan._fence_mask` monkeypatched to `_blind_fence_mask` and once live, capturing `{r.id: r.status}` both times. `kind_mode` is `forced-experiment` (always `"experiment"`; the task body's reproduce convention) or `task` (resolve via `verify_plan._kind_from_body(path.parent.parent)`, falling back to `"experiment"`). Default: run both. Suppress the checks' incidental stdout/stderr with `contextlib.redirect_stdout/redirect_stderr`.
- `unclosed_census(paths)` — count files where `verify_plan.unclosed_fence_line` is not None under the live mask and under the frozen blind walk, and the tail-line count swallowed.
- `explain(path, check_id=None)` — the adjudication reading tool. Prints (a) every fence-shaped line in the file with its exact indentation and raw repr, (b) each contiguous run of mask-differing lines with four lines of context and a per-line `[old][new]` flag column, (c) the classified defect class for the file (one of `mismatched-delimiter`, `inner-shorter-fence`, `indented-marker`, `info-string-backtick`, `unclosed-at-eof`; a file may carry several), and (d) for `--check <cid>`, the before/after `CheckResult.detail` strings.
- CLI: `--corpus <glob>` (default `tasks/*/*/plans/v*.md`), `--kind-mode {forced-experiment,task,both}` (default `both`), `--json <path>`, `--markdown <path>`, `--explain <path>`, `--check <cid>`, `--jobs N` (default 1).
- Determinism: rows are sorted by `(file, check_id)` before emit, so `--jobs 4` output is byte-identical to `--jobs 1`. With `--jobs N > 1`, use `concurrent.futures.ProcessPoolExecutor`; each worker path-loads its own `verify_plan` copy, so the monkeypatch is process-local.
- Fail-loud: an unreadable corpus file raises; there is no `except: continue`. Files are read with `encoding="utf-8"` and no `errors=` fallback, so an undecodable plan is a loud failure rather than a silent mis-measurement. (The plan-time probe used `errors="replace"` and hit zero replacements across the corpus; the harness tightens this.)

Measured wall at plan time for stage 2, single process, on the shared VM under concurrent load: **~9-10 min per `kind_mode`** over the 153-file set, so `--kind-mode both` is ~20 min. Size any `timeout` wrapper at 2x the measured wall (§9).

### 4.3 The adjudication procedure (AC2)

For every check in the union of the two `kind_mode` affected sets:

1. Run `scripts/issue2641_fence_mask_audit.py --explain <file> --check <cid>` for each file the check moves on. Read the mask-diff runs and the classified defect class.
2. Open the check's function in `scripts/verify_plan.py` and quote its contract sentence from its own docstring.
3. Ask exactly one question: **applied to the CommonMark reading of this document, does the check's stated contract yield the NEW verdict?**
4. Assign a class:
   - **A — new verdict correct, no check change.** The contract yields the new verdict on correctly-parsed text.
   - **B — new verdict correct, latent defect surfaced.** As A, plus the row exposes something else worth its own task (a check over/under-trigger, or a malformed-plan-text class). Record the follow-up; do not fix it here.
   - **C — new verdict wrong, adjust the check here.** The contract yields the OLD verdict, meaning the check was only correct on mis-masked text. Fix the check in this change, with its own regression test, and say in the adjudication exactly which contract sentence forced it.
5. Write the subsection into `docs/issue2641_fence_mask_adjudication.md`: check id, file count per `kind_mode`, transition histogram, defect classes involved, class verdict, and a paragraph of reasoning that cites at least one concrete line (file plus line number plus the line's text).

Two structural facts make this tractable and bound the work:

- **The historical corpus is evidence, not a live gate.** The 4,761 stored plans are already approved and executed; `verify_plan` re-runs on a plan only when a session re-verifies it. What the adjudication decides is the check's FORWARD contract; the 37 files are the sample that exposes it.
- **Every affected check reads fence-stripped prose by design.** Checks that deliberately scan RAW text (c11, c25, c38, and c59's consumer arm) are unaffected by construction, which is itself a consistency signal: none of them appear in either affected set.

Plan-time pre-classification, to be confirmed or overturned per check by the implementer: all 19 forced-kind checks and all 15 production-kind checks are predicted **class A**, with `c31_skillmd_prose_pin` and the 19 unclosed-at-EOF files additionally carrying **class B** follow-ups (§4.6). Cases 1, 2, and 3 in §2.4 are worked class-A adjudications the implementer can copy in style.

### 4.4 The unclosed-fence diagnostic

A fence opened and never closed makes 69 checks silently stop seeing the document, which is the exact hazard shape the Goal names. Implementing §4.5 faithfully creates 19 new instances of it in the corpus. So the fix makes the condition visible, without adding a registered check.

In `main()`, immediately before `overall, results = verify_plan_text(raw, kind=kind, source=source)` (currently line 15576 on `origin/main`):

```python
    _unclosed = unclosed_fence_line(raw.splitlines())
    if _unclosed is not None:
        print(
            f"verify_plan: NOTE — unclosed code fence opened at line {_unclosed + 1}. "
            f"CommonMark reads every following line as code, so every fence-aware "
            f"check sees this document only up to that line (#2641).",
            file=sys.stderr,
        )
```

Why stderr and not a check row: adding a registered check would edit the `CHECKS` tuple, the module-docstring catalog at lines 224-270, and the `n_checks` / `n_skip` count asserts in `tests/test_verify_plan.py:6419-6435` — the last two are exactly the regions #2384 edits, turning a zero-conflict change into a two-hunk conflict. stderr also cannot break any existing test: every CLI test in `tests/test_verify_plan.py` reads `capsys.readouterr().out` (stdout) only, and the `--json` payload shape is untouched. A registered `unclosed fence` check is filed as a follow-up in §4.6.

### 4.5 Regression tests (new file: `tests/test_verify_plan_fence_mask.py`)

Direct `_fence_mask` assertions on synthetic input, no corpus dependency, loading `verify_plan` the same way `tests/test_verify_plan.py` does. The four cases AC3 names, plus six the spec rules imply:

1. **Mismatched tilde/backtick.** ```` ```\ncode\n~~~\nprose\n``` ```` — the `~~~` line does NOT close the backtick block; `prose` stays masked True, and the file ends unclosed.
2. **Inner triple-backtick inside a four-backtick block.** ```` ````\ninner ```\nstill code\n````\nprose ```` — the inner three-backtick line is content (shorter than the opener); `prose` is False.
3. **Indented fence marker (outside a fence).** `prose\n    ``` not a fence\nprose2` — the indented line does not open a fence; `prose2` is False. Companion at indent 3: `prose\n   ```py\ncode\n   ```\nprose2` — three spaces IS a legal opener and a legal closer, so `code` is True and `prose2` is False.
4. **Unclosed fence at EOF.** ```` prose\n```\ncode\nmore ```` — everything from the opener to EOF is True, and `unclosed_fence_line` returns the opener's index.
5. **Info string containing a backtick on a backtick fence.** The #714 line verbatim: ``  ```` ``` ```` or `~~~`; skip lines inside a fence.`` — not an opener; the following prose is False. (Regression pin for §2.4 case 1.)
6. **Closing fence longer than the opener.** ```` ```\ncode\n`````\nprose ```` — five backticks is "at least as many", so it closes; `prose` is False.
7. **Closing candidate carrying an info string.** ```` ```\ncode\n```bash\nstill code ```` — not a closer; the block stays open.
8. **Closing fence with trailing whitespace.** ```` ```\ncode\n```   \nprose ```` — trailing spaces are ignored, so it closes; `prose` is False.
9. **Tilde fence whose info string contains tildes and backticks.** ```` ~~~ a~b`c\ncode\n~~~\nprose ```` — legal opener (the backtick restriction is backtick-fences-only), closes normally.
10. **Indented closing fence, and a tab-indented fence line.** `​```\ncode\n   ```\nprose` closes at three spaces; `​```\ncode\n\t```\nstill code` does not close (tab = indent 4).

Plus three contract tests:
- `test_mask_is_line_count_preserving` — `len(_fence_mask(lines)) == len(lines)` for every fixture, including the empty document.
- `test_strip_fences_matches_mask` — `strip_fences` drops exactly the True lines.
- `test_unclosed_fence_line_none_when_balanced` — `None` for every balanced fixture.

Second new file, `tests/test_issue2641_fence_mask_audit.py`, so the harness is not `untested_touched` in the Step 9c selector: (a) the frozen `_blind_fence_mask` reproduces the pre-fix behaviour on the §4.5 fixtures (each of cases 1-4 shows a documented difference from the live mask); (b) `--jobs 4` output is byte-identical to `--jobs 1` on a 20-file slice; (c) `explain` classifies each of the four §2.4 files into the expected defect class.

## 7. Decision gates and kill criteria

**No gates.** Wall-clock is well under four hours and the change is a pre-verified, plan-time-measured code fix; a mid-run gate would only add a stop with nothing to decide at it.

**Kill criteria (stop and re-plan, do not push through):**

- **K4 — the §4.4 stderr NOTE turns out to require a `CHECKS` change to be useful.** Drop it to the §4.6 follow-up rather than growing the diff into #2384's hunks.

## 11. Decision rationale

**R1 — Re-derive the mask from the spec; do not depend on #2384 landing.**
*What:* implement `_fence_scan` from CommonMark 0.31.2 §4.5 directly, on a worktree branched from `origin/main`, with no ordering dependency on #2384.
*Why:* the rule is roughly 20 lines and every clause maps to a quoted spec sentence (§4.1), so re-deriving costs less than coordinating. #2384 is live, in its code-review ensemble, and its round-2 review may still change `_c75_strip_code_blocks`; taking a dependency on a branch that can rebase or be revised converts a two-hour change into an open-ended wait. The measured conflict surface is nil: `git diff origin/main...issue-2384 -- scripts/verify_plan.py` yields hunks at 224, 256, 4623, and 15613, none within 37 lines of our edits, and #2384 touches neither `_fence_mask` nor `strip_fences`. Whichever lands second rebases cleanly. The result is convergent by construction, since both implementations encode the same spec sentences, and #2384's own docstring names this task as the owner of the shared fix.
*Source:* `.claude/rules/artifact-reuse.md` § "Porting a recipe from an unmerged sibling branch"; measured hunk disjointness at plan time; CommonMark 0.31.2 §4.5.
*Alternatives:* (a) wait for #2384 to merge, then import its helper: rejected, unbounded wait on a live review, and it would make this task's correctness contingent on another task's review outcome. (b) Cherry-pick `_c75_strip_code_blocks` wholesale: rejected, it has a different contract (returns text, drops indented lines) and would import the §11 R2 decision by accident.

**R2 — Indentation gates fence RECOGNITION only; indented lines are NOT masked as code.**
*What:* `^ {0,3}` in `_FENCE_RE` prevents a 4-space or tab indented line from opening or closing a fence, and that is the whole use of indentation. A non-fence line outside a fence keeps the prevailing state (False), whatever its indentation.
*Why:* two independent reasons. First, the spec: §4.4 says "An indented code block cannot interrupt a paragraph", and inside a list item the indentation baseline shifts, so a line-local `startswith("    ")` test cannot tell indented code from a paragraph continuation or a nested bullet. Plan documents in this repo are dense with 4-space-indented list continuations. Second, measurement: over all 4,761 corpus plans, the conservative form changes 153 files / 10,882 lines, exactly reproducing the task body's measured 153, while the aggressive form (which mirrors `_c75_strip_code_blocks`'s drop-indented-lines behaviour) changes 937 files / 26,520 lines. The aggressive form is a six-times-larger semantics change that the Goal does not ask for and that nobody has measured verdict-wise.
*Source:* CommonMark 0.31.2 §4.4 (quoted §2.2); plan-time corpus measurement, 2026-08-29, 4,761 files.
*Alternatives:* mask indented lines as code, matching the #2384 helper: rejected on the 937-versus-153 measurement, and recorded in the `_fence_scan` docstring so it can be revisited with numbers rather than intuition.

**R3 — Implement the unclosed-fence rule faithfully (swallow to EOF), and make it visible.**
*What:* an opener with no closer masks everything after it as code, per spec; `main()` emits a stderr NOTE naming the opening line.
*Why:* the spec is unambiguous, and it is what GitHub and the EPS dashboard already render, so matching it means the checks see what a human reading the plan sees. The alternative (treat an unclosed opener as a non-fence) is a second heuristic that no renderer implements and that would itself invert state relative to what the author is looking at. But swallow-to-EOF creates 19 new instances of the silent-hiding shape the Goal is about, so leaving it unannounced would trade one silent failure for another; a one-line stderr NOTE converts it into a visible one at essentially zero cost and zero conflict surface.
*Source:* CommonMark 0.31.2 §4.5 unclosed-fence sentence (quoted §2.2); plan-time unclosed-fence census (21 files under the new mask, 19 of them new, 19 of the 37 verdict movers).
*Alternatives:* (a) a registered `unclosed fence` check: rejected here because it would edit the `CHECKS` tuple, the module-docstring catalog at 224-270, and the count asserts at `tests/test_verify_plan.py:6419` — the last two are #2384's exact hunks; filed as follow-up 2. (b) A new key in the `--json` payload: rejected, it touches a consumer-facing schema for a diagnostic that belongs in human output. (c) Silence: rejected for the reason above.

**R4 — Adjudicate under BOTH `kind` conventions and report both.**
*What:* the harness runs `forced-experiment` and `task` kind modes; AC2's enumeration is the forced-experiment set (the body's), and the production set is reported alongside.
*Why:* the task body's reproduce step 3 says `verify_plan_text(text, kind="experiment")`, and that convention is what produces its 37/19/c1/c2 figures; reproducing it exactly is what lets the implementer confirm the body's measurement rather than argue with it. But 32 of the 36 production movers are `kind: infra` plans on which c1 and c2 skip, so the forced convention over-reports what the tool actually does. Reporting only the forced set would overstate the change; reporting only the production set would look like a failure to reproduce the body. Both, labelled, is the honest answer.
*Source:* task #2641 body "Reproduce" step 3; plan-time measurement of both conventions, 2026-08-29.
*Alternatives:* forced-only (overstates), production-only (appears to contradict the body). Rejected.

**R5 — One `_fence_scan` core with two thin wrappers.**
*What:* `_fence_mask` and `unclosed_fence_line` both delegate to `_fence_scan`.
*Why:* the repo's Supersede convention says one copy of the job; two independent walks of the same rule would drift the moment either is touched, and this rule has already drifted once (`_fence_mask` versus `verify_task_body.find_h2_sections`). `_fence_mask`'s public signature is unchanged, so none of the 29 call sites move.
*Source:* `.claude/rules/code-style.md` § "Supersede -> delete the old version"; the existing `_fence_mask` / `find_h2_sections` drift documented at `scripts/verify_plan.py:722`.
*Alternatives:* a `return_unclosed: bool = False` kwarg on `_fence_mask` (changes a 29-call-site signature for one caller's benefit) or a separate duplicate loop (drift). Both rejected.

**R6 — Commit the harness rather than throwing it away.**

*Why:* the check-calibration convention in this very file ("ANY future c39-regex change re-runs the corpus scan and records the realized numbers here", `scripts/verify_plan.py:7511`) presumes a re-runnable scan, and today no such tool exists for the fence mask; AC2's enumeration has to be reproducible by a reviewer who was not in the session. *Alternatives:* a throwaway `/tmp` script (AC2 becomes unreproducible), or putting the logic in the test file (not runnable as a tool). Rejected.
