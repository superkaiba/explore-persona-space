## 1. Goal

Make cheap CPU-only pods first-class compute lanes on BOTH providers (GCP E2/N2 spot +
RunPod CPU3/5) and shift the standing CPU-routing policy to PREFER dedicated cheap CPU
pods for non-trivial CPU-only phases — especially heavy, parallelizable, or
large-footprint work — over cramming onto the shared VM, while keeping trivial quick ops
(sub-minute probes, quick plots) on the VM. Enable running CPU jobs in parallel across
multiple cheap CPU pods. Preserve the GCP-first lane order (cheap GCP CPU before RunPod
CPU; RunPod CPU is the fallback, consistent with the existing GPU rule). This REVERSES
the #677 `cpu_exhausted_no_runpod_lane` hard terminal — but only for CPU intents that
have a RunPod-CPU mapping; `cpu-bigmem` (the >50 GB large-footprint analysis lane) keeps
its reliable single-on-demand-GCP-rung-then-terminal behavior verbatim.

The standing policy shift this enables: today CLAUDE.md's "CPU-only phases don't hold GPU
pods" routes ALL CPU phases to the free shared VM by default, off-VM only for >50 GB or
a gradient-descent fit. After this change the default for a NON-TRIVIAL CPU phase
(parallelizable, or longer than the trivial floor) becomes a cheap dedicated CPU pod, not
the shared VM — removing the disk-contention failure mode (#658: a 139 GB activation store
filled `/` and stalled the whole fleet) while keeping trivial sub-minute ops on the VM.

## 2. Prior Work / Context

- **#677 added the SINGLE GCP CPU intent `cpu-bigmem` → `n2-highmem-16`** and, crucially,
  built every CPU guard to ENSURE a CPU intent NEVER reaches RunPod (RunPod was GPU-only:
  `runpod_api.py:501` asserts `gpu_count >= 1`, `gpu_heuristics.resolve_intent` KeyErrors
  on a CPU intent). It introduced the typed `CpuExhaustedNoRunpodLaneError`
  (`ROUTE_REASON_CPU_EXHAUSTED_NO_RUNPOD = "cpu_exhausted_no_runpod_lane"`) at the
  `_runpod_terminal_rung` chokepoint (router.py:2139-2151) and the
  `_is_gcp_async_workload_failure` exclusion (backend_poll.py:361). #747 SUPERSEDES that
  hard terminal for intents that now HAVE a RunPod CPU lane, keeping it only for `cpu-bigmem`.
- **The #658 incident** (2026-06-24/26): a 139 GB activation store materialized on the
  shared 188 GB VM root disk, `/` hit 100%, the whole fleet stalled. The `cpu-bigmem` lane
  (#677) + the `VM_ANALYSIS_FOOTPRINT_GB_MAX = 50` GB carve-out exist precisely to route
  the big analyses off the VM. #747 extends the same off-VM philosophy DOWN to cheap,
  parallelizable, non-trivial CPU work that does not need the big box.
- **GCP-first failover is the established pattern** (#656/#658, `compute-backend-failover.md`
  Part B): GCP ladder → free SLURM lanes → RunPod as the LAST rung. The CPU fallover #747
  adds is the CPU analogue: GCP cheap CPU → GCP `cpu-bigmem` on-demand → RunPod CPU.
- **RunPod CPU offering (confirmed 2026-06-29):** RunPod has CPU-only pods created via the
  `deployCpuPod` GraphQL mutation (NOT `podFindAndDeployOnDemand`), keyed on an
  `instanceId` of the form `<flavor>-<vCPU>-<RAM_GB>` (e.g. `cpu3g-2-8`, `cpu3c-4-16`,
  `cpu5c-2-4`). Flavors: `cpu3g` (gen-3 general purpose, RAM = vCPU×10... but instance_id
  carries the explicit RAM segment), `cpu3c` (gen-3 compute-optimized), `cpu5c` (gen-5
  compute-optimized). Source of truth: the runpod-python library
  (`runpod.create_pod(..., instance_id="cpu3c-2-4")` →
  `generate_pod_deployment_mutation` selects `mutation_type = "podFindAndDeployOnDemand"
  if gpu_type_id else "deployCpuPod"` and emits `instanceId: "<...>"`, omitting
  `gpuTypeId`/`gpuCount`). Docs: <https://docs.runpod.io/flash/configuration/cpu-types>
  (instance_id format), <https://github.com/runpod/runpod-python> (the mutation source).
- **GCP E2 spot (confirmed 2026-06-29):** `e2-standard-2` (2 vCPU / 8 GB) on-demand
  ~$0.067/hr, spot ~$0.0335/hr in `us-central1` (CloudPrice / economize.cloud / GCP spot
  pricing). E2 supports spot/preemptible. Spot carries the usual 24h-max + preempt-anytime
  + no-restart-on-eviction semantics, so spot is for short/restartable CPU jobs only — the
  CPU analogue of the GPU length-aware ladder (`_is_short_job`). E2 is offered in
  `us-central1` (the project's pinned zone). Docs:
  <https://cloud.google.com/spot-vms/pricing>, <https://cloud.google.com/compute/vm-instance-pricing>.

## 4. Design

### 4.1 `scripts/runpod_api.py` — the RunPod CPU create path (Surface 1)

Add a sibling to `_deploy_once` that handles the CPU mutation. The GPU `_deploy_once`
`assert gpu_count >= 1` (line 501) is LEFT UNTOUCHED — the CPU path is a separate
function, not a relaxation of the GPU assert (keeps the GPU contract loud).

```python
# RunPod CPU instance_id flavors (#747). Format: "<flavor>-<vCPU>-<RAM_GB>".
# cpu3g = gen-3 general; cpu3c = gen-3 compute-opt; cpu5c = gen-5 compute-opt.
# Confirmed against docs.runpod.io/flash/configuration/cpu-types + runpod-python
# generate_pod_deployment_mutation (mutation_type = "podFindAndDeployOnDemand"
# if gpu_type_id else "deployCpuPod"; emits instanceId, omits gpuTypeId/gpuCount).
def _deploy_cpu_once(
    *,
    name: str,
    instance_id: str,            # e.g. "cpu3g-2-8"
    image: str,
    volume_gb: int,
    container_disk_gb: int,
    cloud_type: str,
    data_center_id: str | None,
) -> PodInfo | None:
    """Single deployCpuPod attempt for one RunPod CPU instance_id.

    Returns parsed PodInfo on success or None on no-capacity (null mutation
    result / SUPPLY_CONSTRAINT) — same two-wire-shape handling as _deploy_once.
    deployCpuPod takes instanceId (NOT gpuTypeId/gpuCount); startSsh + 22/tcp
    stay non-negotiable. Spot/interruptible is NOT a CPU lever (RunPod CPU pods
    are on-demand only — confirmed body claim; flagged §12).
    """
    inputs: dict[str, Any] = {
        "name": name,
        "instanceId": instance_id,
        "cloudType": cloud_type,
        "volumeInGb": volume_gb,
        "containerDiskInGb": container_disk_gb,
        "imageName": image,
        "volumeMountPath": "/workspace",
        "startSsh": True,
        "ports": "8888/http,22/tcp",
    }
    if data_center_id:
        inputs["dataCenterId"] = data_center_id
    inputs_block = _build_inputs_block(inputs)   # reuse the existing serializer
    query = f"""
    mutation {{
      deployCpuPod(input: {{ {inputs_block} }}) {{
        id
        name
        desiredStatus
        createdAt
        runtime {{ ports {{ ip publicPort privatePort type isIpPublic }} }}
      }}
    }}
    """
    try:
        data = graphql(query)
    except RunPodSupplyConstraintError:
        return None
    raw = data.get("deployCpuPod")
    if not raw:
        return None
    return _parse_pod(raw)
```

Then a `create_cpu_pod(name, instance_id, *, image=..., volume_gb=..., container_disk_gb=...,
cloud_type="ALL", data_center_id=None) -> PodInfo` public wrapper mirroring `create_pod`'s
shape (raises `RunPodNoCapacityError` when the single CPU attempt + COMMUNITY fallback both
return None; raises `RunPodError` on transport/auth). Default `container_disk_gb` for CPU:
keep the existing `DEFAULT_CONTAINER_DISK_GB`; the body's vCPU×10/15 GB auto-sizing is
RunPod's own platform default for the volume, not something we must compute — pass the
caller's `volume_gb`/`container_disk_gb` through. (Decision recorded §11.)

`_CREATE_ENUM_FIELDS` already keeps `cloudType` bare — reused verbatim.

**`_parse_pod` reuse:** the existing `_parse_pod` reads `gpuCount` via `.get(...)` — a CPU
pod's response has no `gpuCount`, so `.get` returns None; verify `_parse_pod` does not hard-index
`machine.gpuTypeId` in a way that crashes on a CPU response (read it during implementation;
if it does, guard with `.get`). Flagged §12.

### 4.4 `src/explore_persona_space/backends/router.py` — relax the terminal + add the spot rung (Surface 4)

This is the core reversal. Add a single RunPod-CPU mapping table — the positive list of CPU
intents that HAVE a RunPod CPU lane — so the relaxation is keyed on a fit-for-purpose mapping,
NOT on `gpu_count == 0` (which would wrongly route `cpu-bigmem` to RunPod):

```python
# CPU intents that HAVE a RunPod CPU fallback lane (#747). A CPU intent in this
# map falls over GCP->RunPod CPU when the GCP CPU lane is exhausted (the CPU
# analogue of the GPU GCP->RunPod fallback, #656/#658). A CPU intent NOT in this
# map (cpu-bigmem — the >50 GB large-footprint analysis lane, which has no
# cheap-RunPod equivalent in tier) keeps the #677 typed terminal
# CpuExhaustedNoRunpodLaneError. The value is the RunPod CPU instance_id.
RUNPOD_CPU_INSTANCE_FOR_INTENT: dict[str, str] = {
    "cpu-small": "cpu3g-2-8",     # 2 vCPU / 8 GB, gen-3 general purpose
    "cpu-mid": "cpu3c-8-16",      # 8 vCPU / 16 GB, gen-3 compute-optimized
}
```

**(a) `_gcp_ladder_specs` (L1964) — CPU spot-eligibility.** The current short-circuit
`if base.gpu_count == 0: return [(spec, f"ondemand_{_machine_label(base)}")]` is correct for
`cpu-bigmem` (reliable on-demand) but wrong for `cpu-small`/`cpu-mid` (we WANT a spot rung on
a short job). Refine: for a CPU intent that IS in `RUNPOD_CPU_INSTANCE_FOR_INTENT` (the cheap,
restartable tier), yield a SPOT rung then an on-demand rung WHEN `_is_short_job(spec, base)`,
else on-demand only; for a CPU intent NOT in the map (`cpu-bigmem`), keep the single
on-demand rung verbatim. Sketch (replacing the L1964 short-circuit):

```python
if base.gpu_count == 0:
    # cpu-bigmem (no RunPod-CPU lane): reliable single on-demand rung (#677, unchanged).
    if spec.intent not in RUNPOD_CPU_INSTANCE_FOR_INTENT:
        return [(spec, f"ondemand_{_machine_label(base)}")]
    # cheap CPU intent (#747): spot-first on a short/restartable job, else on-demand.
    # No A100-40 rung (that is a GPU fallback); no flex rung (flex queues for GPU
    # capacity — pointless for abundant CPU). Spot only on a short job, exactly the
    # GPU length-aware axis (_is_short_job).
    cpu_rungs: list[tuple[RunSpec, str]] = []
    if _is_short_job(spec, base):
        cpu_rungs.append((_with_machine(spec, base, provisioning="SPOT"),
                          f"spot_{_machine_label(base)}"))
    cpu_rungs.append((spec, f"ondemand_{_machine_label(base)}"))
    return cpu_rungs
```

(The caller `provisioning_model` pin branch below still never runs for a CPU intent because we
return early — preserving the #677 invariant that a pinned CPU launch never picks up an
A100-40 rung. A caller who explicitly pins SPOT on a `cpu-bigmem` is out of scope; `cpu-bigmem`
returns before the pin branch as today.)

**(b) `_runpod_terminal_rung` CPU guard (L2139-2151) — RELAX for mapped intents.** Replace the
unconditional `if machine_for_intent(spec).gpu_count == 0:` terminal with a check that keeps

```python
machine = machine_for_intent(spec)
if machine.gpu_count == 0 and spec.intent not in RUNPOD_CPU_INSTANCE_FOR_INTENT:

    _post_terminal_failure_marker(..., reason=ROUTE_REASON_CPU_EXHAUSTED_NO_RUNPOD, ...)
    raise CpuExhaustedNoRunpodLaneError(...)
# else: a GPU intent OR a mapped cheap CPU intent -> proceed to the RunPod launch
# below. For a mapped CPU intent the RunPod spec carries --intent <cpu-small|cpu-mid>,
# which pod_lifecycle.py/gpu_heuristics (Surface 5) resolves to the RunPod CPU
# instance_id via RUNPOD_CPU_INSTANCE_FOR_INTENT.
```

The existing `runpod_spec = replace(spec, backend="runpod", ...)` below preserves `intent`, so

## 11. Decision Rationale

- **New intent names `cpu-small` / `cpu-mid` (not `cpu-tiny`/`cpu-2`/etc.).**
  *Why:* mirrors the existing size-tier vocabulary (`cpu-bigmem`) — small/mid/bigmem reads as a
  coherent CPU tier ladder, and the names are plain-English-legible in `--list-intents`.
  *Source:* #677 (`cpu-bigmem` naming convention) — inherit the tier-name style.
  *Alternatives:* a single `cpu` intent (rejected — no spot/non-spot + size distinction);
  machine-typed names like `cpu-e2-2` (rejected — leaks the machine type into the intent, which
  `cpu-bigmem` deliberately avoids).
- **`cpu-small` → `e2-standard-2` (2 vCPU/8 GB), `cpu-mid` → `e2-standard-8` (8 vCPU/32 GB).**
  *Why:* E2 is GCP's cheapest general-purpose family and supports spot (~$0.0335/hr for
  `e2-standard-2` in us-central1); 2 vCPU/8 GB fits a trivial-but-parallel CPU fan-out, 8 vCPU/32 GB
  a mid CPU job, both well under the 50 GB footprint floor (above that → `cpu-bigmem`).
  *Source:* GCP spot pricing (cloud.google.com/spot-vms/pricing, CloudPrice e2-standard-2,
  confirmed 2026-06-29).
  *Alternatives:* `n2-standard-*` (rejected for `cpu-small` — pricier than E2 for the cheap tier;
  E2 is the cheapest); a single mid tier (rejected — small tier is the parallel-fan-out workhorse).
- **RunPod CPU instance_ids `cpu3g-2-8` (small) / `cpu3c-8-16` (mid).**
  *Why:* `cpu3g` (gen-3 general) matches the cheap `cpu-small` general-purpose role; `cpu3c`
  (gen-3 compute-optimized) matches a mid compute job. The instance_id format `<flavor>-<vCPU>-<RAM>`
  is the confirmed RunPod CPU surface.
  *Source:* docs.runpod.io/flash/configuration/cpu-types (instance_id format + flavors);
  runpod-python `generate_pod_deployment_mutation`. (The EXACT vCPU/RAM choice is a low-stakes
  default — any available cheap tier works; flagged §12 as confirm-against-live-availability.)
  *Alternatives:* `cpu5c` (gen-5 — newer/pricier, marginal for cheap fallback work; rejected for
  the default).
- **The RunPod CPU create mutation = `deployCpuPod` (NOT `podFindAndDeployOnDemand`).**
  *Why:* the body explicitly flags the API is not the GPU mutation; the runpod-python source
  confirms `mutation_type = "podFindAndDeployOnDemand" if gpu_type_id else "deployCpuPod"`.
  *Source:* github.com/runpod/runpod-python `generate_pod_deployment_mutation` (read via WebFetch
  2026-06-29). *Confidence: Medium — first-party GraphQL docs do not document `deployCpuPod`;
  the source library is the authority.* Marked for fact-checker confirm; OPTIONAL live probe (§8).
  *Alternatives:* `podRentInterruptable` (rejected — that is the GPU spot mutation, not CPU);
  the new REST API (rejected — the project's `runpod_api.py` is GraphQL-native; staying GraphQL
  keeps the team-id header + lever-chain machinery; a REST migration is out of scope).
- **GCP zone `us-central1` for the new CPU intents.**
  *Why:* the project pins `us-central1` (A100-80 quota); E2 + N2 are both offered there, so no
  new zone is introduced.
  *Source:* GCP VM-instance-pricing + the project's `GcpConfig` primary_zone; #677 (`n2-highmem-16`
  already in us-central1).
  *Alternatives:* none — adding a zone is out of scope.
- **Spot eligibility for cheap CPU intents = the existing `_is_short_job` axis (spot on a short
  job, on-demand otherwise); `cpu-bigmem` never spot.**
  *Why:* spot's preempt-anytime + no-restart-on-eviction makes it safe only for short/restartable
  CPU jobs — the exact CPU analogue of the GPU length-aware ladder (#680). A long/large-footprint
  analysis (`cpu-bigmem`) wants reliable on-demand (it may download a big store; a mid-download
  preemption is costly).
  *Source:* #680 length-aware ladder (`_is_short_job`, `EPS_GCP_SPOT_MAX_GPU_HOURS`); GCP spot
  semantics (cloud.google.com/spot-vms/pricing).
  *Alternatives:* always-spot cheap CPU (rejected — an unbounded cheap CPU job preempting mid-run
  wastes the partial work); always-on-demand cheap CPU (rejected — loses the ~50% spot saving on
  the common short-job case).
- **RunPod CPU disk sizing: pass through `volume_gb`/`container_disk_gb`; do not compute vCPU×10/15 GB.**
  *Why:* the vCPU×10/15 GB ratio is RunPod's platform default for the instance, not a value the
  create call must compute; passing the existing defaults keeps the call simple and lets RunPod
  size the volume per the instance_id.
  *Source:* docs.runpod.io/flash/configuration/cpu-types (the ratio is descriptive of the instance,
  not a create argument). *Confidence: Medium — confirm `containerDiskInGb`/`volumeInGb` are
  accepted-and-honored on the CPU input via the live probe.*
  *Alternatives:* computing the disk from the instance_id (rejected — duplicates RunPod's own sizing).

  (sync failover) for the CPU fallover; no new reason constant.**

  *Source:* #656/#658 (`compute-backend-failover.md` Part B reason constants).

  difference; the `--intent cpu-small` on the marker already distinguishes a CPU fallover).
