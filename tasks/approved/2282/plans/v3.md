### 2.1 Scope discovery: the fit-core delta carries TWO features

The `+213` net lines are not only the chunk cap. New top-level definitions on the
branch, absent from `main`:

- **Chunk cap** (the task's stated target): `_free_device_bytes`,
  `_resolve_null_draw_chunk`, knob `EPM_FIT825_NULL_DRAW_LIVE_FACTOR` (default
  `6`), `NULL_DRAW_MEM_SAFETY = 0.8`.
- **Primal (d-space) fold route** (not named in the task body): `_primal_eig`,
  `_primal_cache_pieces`, knob `EPM_FIT825_PRIMAL_CHUNK_ROWS` (default `65536`),
  module flag `FORCE_GRAM = False`.

The primal route is **default-on in the `n_train > d` regime**
(`if not FORCE_GRAM and n_tr > d:` at both `_prep_fold` and the inner-lambda
prep), replacing the Gram route's `n x n` `eigh`, which the source comment calls
"ruinously mis-regimed" for `n_train > d`. It therefore changes the *computational
route* — and so the floating-point rounding path — for every consumer whose
`n_train > d`, while keeping an identical cache field contract. This is the
subject of the numeric-inertness audit in §4.

`tests/test_issue825_primal_fold_path.py` exists precisely to pin that route's
parity, which is why it is shared-surface rather than #1336-local.

**A third, much narrower delta** (found in review; named here so "two features"
does not under-describe the audit surface): the `degeneracy_tripwire` **call
site**. The function itself — signature, including its `grid=None` parameter, and
all 54 body lines — is byte-identical on `main` and the branch. What differs is
that the branch threads `grid=(None if lambdas is None else np.asarray(lambdas,
dtype=np.float64))` at the call site, so a caller-supplied lambda grid is judged
against the realized grid rather than the module `LAMBDAS` edges. Blast radius is
narrower than a behavior change: the in-source comment pins `None` as keeping the
default "byte-for-byte", so consumers that pass no `lambdas` are unaffected, and
`degeneracy_tripwire` contains **zero** `raise` statements on either side — it is
diagnostic-only (a WARN tag plus JSON payload fields), so this can at most flip a
diagnostic flag for custom-grid consumers, never a result.

## 3. Decision: land the branch blob for the fit core, both features together

`Decision: land the branch's fit-core file wholesale (equivalently, the verified
3-way merge output — they are byte-identical) rather than hand-splitting the
chunk cap out of it.`

Reasons, in order of weight:

1. **A split creates code that has never run.** The branch blob is the exact byte
   sequence that executed round 4 of #1336 (2,126 GPU-h). Hand-separating a
   213-line delta inside a shared numeric core would produce a
   chunk-cap-without-primal-route state that has no execution history anywhere.
   For a shared numeric core, "never run" is the dominant risk.
2. **Consumer risk is bounded and checkable.** The signature is unchanged across
   all 119 call sites, no definitions are removed, and both features ship with
   parity tests. §4 verifies parity empirically instead of trusting the
   in-source parity comment.
3. **The alternative is not safer, only narrower.** Leaving the primal route off
   `main` leaves the `n_train > d` mis-regime defect in place for every consumer —
   the defect #1336 hit.

**Withdrawn from this argument (review correction):** an earlier draft also
claimed the two features are entangled at the same call sites. They are not — the
chunk-cap hunks reference no primal symbol and share no diff hunk with
`_prep_fold` / the inner-lambda prep. That claim was also internally inconsistent
with the §7 fallback, which presupposes exactly this separability. The decision
rests on the two reasons above, which do not depend on entanglement: a
hand-extracted subset is code with no execution history in a shared numeric core,
and omitting the primal route leaves a real defect in place.

`Assumption:` the primal route's parity claim holds at the tolerances its own
tests assert. §4 gate G2 tests this rather than assuming it; a parity failure
routes to §7 rollback, not to a workaround.
