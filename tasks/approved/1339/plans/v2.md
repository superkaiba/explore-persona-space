## 0.0 TL;DR (plain English)

- **What I'll change:** the GCP crash-persist currently uploads each partial dir
  (`eval_results_issue_<N>`, `data_issue_<N>`, `data_issue<N>`) as ONE Hub commit with no
  retry. I'll make `_up_dir` split any dir over 1,000 files (env-tunable) into
  newest-first staged batches of ≤1,000 files, each its own `upload_folder` commit with
  one bounded retry, aborting a dir after 2 consecutive failed batches, logging every
  batch outcome, and leaving small dirs byte-identical to today.
- **What I expect:** the #1090 shape (29,024 files / 14.4 MB, one commit → client-side
  504 read) becomes ~30 small commits that each return well inside the gateway window —
  so the client's success/failure read is truthful, a genuinely-failed commit loses at
  most one batch (newest batches land first inside the 300s budget), and a transient 504
  gets a retry; all existing persist tests stay green and new behavioral tests prove
  ≥2 commits + identical repo paths. (Fact-check correction: in fu5 itself the 29k-file
  commit actually LANDED server-side — the 504 was a response-delivery gateway timeout,
  so the client logged FAILED on a success; the fix makes that read truthful AND bounds
  worst-case loss when a large commit genuinely fails.)
- **What would change my mind:** if a ≤1,000-file commit still reliably 504s on this repo
  (root cause would not be commit size), or if the byte-identical-paths / fail-soft /
  300s-budget invariants can't be held in the heredoc — see §6 Kill criteria.

## 1. Goal + acceptance criteria

> crash-persist: chunk large eval_results dir uploads into bounded multi-commit batches
> with retry instead of one upload_folder commit

(Task #1339 Goal, verbatim.)

The GCE crash-persist (`_eps_persist_diagnostics`) must stop risking an entire partial
dir on a single `upload_folder` commit of a many-thousand-file dir (incident #1090 fu5
att-20260715-081917: `eval_results_issue_1090`, 29,024 files / 14,371,131 bytes — well
under the 2 GiB byte cap — one commit, `504 Server Error: Gateway Time-out ...
/commit/main` read client-side). Fact-check correction (verified live on HF this
session): that commit actually LANDED server-side (`get_paths_info` last_commit
2026-07-15T08:59:11Z, inside the persist window; complete 29k-file set present) — the
server processed the commit in ~31 s and the GATEWAY timed out delivering the response,
so the client logged FAILED on a success and had no retry to make the read truthful. A
genuinely-failed oversized commit WOULD lose everything, and the FAILED-on-success read
poisons the audit trail either way. Chunked ≤1000-file commits return well inside the
gateway window (truthful reads), bound worst-case loss to one batch, and get a bounded
retry. Acceptance criteria (requirement form):

1. **AC-1 (chunking):** a partial dir whose post-exclude file count exceeds
   `EPS_PERSIST_DIR_MAX_FILES_PER_COMMIT` uploads as multiple `upload_folder` commits of
   at most that many files each; a dir at or under the bound uploads exactly as today
   (one commit, same log lines, same call shape).
2. **AC-2 (retry):** each batch commit gets the existing bounded-retry pattern
   (attempts=2, `EPS_PERSIST_RETRY_BACKOFF_S` backoff, default 10 s).
3. **AC-3 (budget + ordering):** batches are ordered newest-first (mtime desc) so the
   highest-value files land first inside the 300s budget; after
   `EPS_PERSIST_DIR_BATCH_ABORT_STREAK` (default 2) consecutive failed batches the dir is
   abandoned loudly and the persist moves on (remaining dirs + final bundle still run).
4. **AC-4 (fail-soft):** no code path raises; the persist always reaches the trap's
   poweroff; the 300s `timeout` wrapper is untouched.
5. **AC-5 (auditability):** every batch outcome prints a `[crash-persist]` `_say` line
   (uploading / uploaded / FAILED attempt i/2 / ABORT / summary `k/nb batches uploaded
   (f/n files)`), so a partial persist is visible in the transcript.
6. **AC-6 (path identity):** repo paths are byte-identical to the unchunked upload —
   `issue<N>_partial/<attempt>/eval_results_issue_<N>/<relpath>` — for chunked AND
   unchunked dirs (downstream consumers unchanged).
7. **AC-7 (no per-file loop):** zero `upload_file` calls anywhere in the persist
   (the #664 504-storm class), pinned by the existing behavioral assert.
8. **AC-8 (tests):** all existing `tests/test_gcp_backend.py` persist tests pass
   (snapshot fixture deliberately regenerated with provenance); new tests in §4 pass.

**What exists (all in the same heredoc, all reused):**

- **#1151 staged-bundle pattern** — `_stage_into` + `_up_bundle(bundle_dir, label, retry)`
  (gcp.py rendered lines ~1697–1736): copy files into a staging dir, ONE `upload_folder`
  commit, `attempts = 2 if retry else 1` with `EPS_PERSIST_RETRY_BACKOFF_S` (default 10)
  backoff. This is the retry pattern AC-2 mirrors.
- **#885 worker-logs sweep** — `_up_logs` (~1781–1846): walk with PRUNE, **newest-first
  sort** (`entries.sort(reverse=True)` over `(mtime, size, path)` tuples), count bound
  via `_env_int("EPS_PERSIST_LOG_MAX_FILES", 40)`, stage into an env-overridable dir
  (`EPS_PERSIST_LOG_STAGE_DIR`), one `upload_folder` commit. This is the walk/sort/stage
  pattern AC-1/AC-3 mirror. Worker logs are bounded at 40 files ⇒ no chunking needed
  there (see the call-site sweep in §3.5).
- **`_up_dir` today** (~1867–1891): `_dir_stats` (size, n) → empty-SKIP → byte-cap SKIP
  (`CAP = EPS_PERSIST_DIR_CAP_BYTES`, 2 GiB) → ONE `upload_folder(folder_path=local,
  path_in_repo=f"{dest}/{name}", ignore_patterns=IGNORE)`, no retry, fail-soft
  `FAILED dir` line. **This is the only unbounded-file-count single commit in the
  persist** — the #1339 target.
- **#664 ban** — per-file `upload_file` loops 504-storm (~160 s/file server-side
  pre-check on this ~1M-file repo). Chunking must stay multi-file `upload_folder`.
- **#658 / #1190** — the Hub 400s a single commit putting >10,000 files in one repo dir;
  #658's recovery uploaded shard dirs of ≤5,000 files per commit successfully **on this
  exact repo** (demonstrated-working commit size); incremental growth of a repo dir past
  10k via many separate commits succeeded there too.
- **Verified library facts** (huggingface_hub 0.36.2, checked against the installed
  wheel): `upload_folder` walks the repo tree only when `delete_patterns` is passed (so a
  batch commit never triggers the ~1M-file listing); `upload_large_folder` has **no
  `path_in_repo` parameter** (signature-verified) → cannot target
  `issue<N>_partial/<attempt>/<name>` and is a worker-pool/progress-report design unfit
  for a 300s fail-soft budget → rejected; its `COMMIT_SIZE_SCALE = [20, 50, 75, 100, 125,
  200, 250, 400, 600, 1000]` is HF's own adaptive per-commit file-count ladder (max
  **1000**, scaled up only while a commit completes in <40 s) — the best available
  grounding for a reliable per-commit bound.

**Method delta (the single change):** extend the #1151/#885 staged-commit machinery to
the partial-dirs sweep — fixed-size newest-first batches + per-batch bounded retry +
consecutive-failure abort — leaving the ≤bound case byte-identical. Nothing else in the
persist changes (first bundle, worker logs, final bundle, breadcrumbs, rc-file capture
all untouched), except the serial print cap resize (§3.4).

### 3.3 Pseudocode (the changed heredoc python)

```python
# _dir_stats -> _dir_entries: same walk, same PRUNE predicate, richer return.
def _dir_entries(local):
    entries = []                                # (mtime, size, Path)
    for dirpath, dirnames, filenames in os.walk(local):
        dirnames[:] = [d for d in dirnames
                       if d not in PRUNE and not (d.startswith("g") and d.endswith("_dl"))]
        for f in filenames:
            p = Path(dirpath) / f
            try:
                st = p.stat()
            except OSError:
                continue
            entries.append((st.st_mtime, st.st_size, p))
    return entries

BATCH_MAX = _env_int("EPS_PERSIST_DIR_MAX_FILES_PER_COMMIT", 1000)
BATCH_ABORT_STREAK = _env_int("EPS_PERSIST_DIR_BATCH_ABORT_STREAK", 2)

def _up_dir(local, name):
    if not local.is_dir():
        _say(f"[crash-persist] SKIP {name}: no such dir ({local})"); return
    entries = _dir_entries(local)
    n = len(entries); size = sum(s for _, s, _ in entries)
    if n == 0:
        _say(f"[crash-persist] SKIP {name}: empty after cache excludes"); return
    if size > CAP:
        _say(f"[crash-persist] SKIP {name}: {size} bytes > cap {CAP} (oversized; ...)"); return
    if BATCH_MAX < 1 or n <= BATCH_MAX:
        if BATCH_MAX < 1:
            _say(f"[crash-persist] WARN EPS_PERSIST_DIR_MAX_FILES_PER_COMMIT={BATCH_MAX} < 1;"
                 " chunking disabled")
        # ===== existing single-commit path, byte-identical log lines + call shape =====
        try:
            _say(f"[crash-persist] uploading dir {name} ({n} files, {size} bytes)")
            api.upload_folder(folder_path=str(local), path_in_repo=f"{dest}/{name}",
                              repo_id=repo, repo_type="dataset", ignore_patterns=IGNORE)
            _say(f"[crash-persist] uploaded dir {name}")
        except Exception as exc:
            _say(f"[crash-persist] FAILED dir {name}: {exc}")
        return
    # ===== chunked path (the #1339 fix) =====
    entries.sort(reverse=True)                  # newest first (#885 precedent): a budget
    nb = -(-n // BATCH_MAX)                     # timeout loses only the OLDEST files
    _say(f"[crash-persist] chunking dir {name}: {n} files >"
         f" EPS_PERSIST_DIR_MAX_FILES_PER_COMMIT={BATCH_MAX}; {nb} batches, newest-first")
    stage_root = Path(os.environ.get("EPS_PERSIST_DIR_STAGE_DIR", "/tmp/eps-dir-batch"))
    fail_streak = ok_batches = ok_files = 0
    for bi in range(nb):
        batch = entries[bi * BATCH_MAX:(bi + 1) * BATCH_MAX]
        shutil.rmtree(stage_root, ignore_errors=True)   # a prior batch/crash never leaks in
        staged = 0
        for _, _, p in batch:
            try:
                rel = p.relative_to(local)
                tmp = stage_root / rel
                tmp.parent.mkdir(parents=True, exist_ok=True)
                shutil.copyfile(p, tmp)                 # relpath preserved => AC-6
                staged += 1
            except Exception as exc:
                _say(f"[crash-persist] FAILED staging {name} file {p}: {exc}")
        if staged == 0:
            _say(f"[crash-persist] SKIP dir {name} batch {bi + 1}/{nb}: nothing staged")
            continue
        uploaded = False
        for att in (1, 2):                              # AC-2: _up_bundle retry mirror
            try:
                _say(f"[crash-persist] uploading dir {name} batch {bi + 1}/{nb}"
                     f" ({staged} files, attempt {att}/2, one commit)")
                api.upload_folder(folder_path=str(stage_root),
                                  path_in_repo=f"{dest}/{name}",
                                  repo_id=repo, repo_type="dataset",
                                  ignore_patterns=IGNORE)
                _say(f"[crash-persist] uploaded dir {name} batch {bi + 1}/{nb}")
                uploaded = True
                break
            except Exception as exc:
                _say(f"[crash-persist] FAILED dir {name} batch {bi + 1}/{nb}"
                     f" attempt {att}/2: {exc}")
                if att == 1:
                    time.sleep(max(0, _env_int("EPS_PERSIST_RETRY_BACKOFF_S", 10)))
        if uploaded:
            fail_streak = 0; ok_batches += 1; ok_files += staged
        else:
            fail_streak += 1
            if fail_streak >= BATCH_ABORT_STREAK:       # AC-3: bounded budget burn
                _say(f"[crash-persist] ABORT dir {name}: {fail_streak} consecutive batch"
                     f" failures; {nb - bi - 1} batch(es) unsent")
                break
    shutil.rmtree(stage_root, ignore_errors=True)
    _say(f"[crash-persist] dir {name}: {ok_batches}/{nb} batches uploaded"
         f" ({ok_files}/{n} files)")                    # AC-5 summary
```

Design notes, each load-bearing:

- **Staging copies, NOT `allow_patterns` slices.** `allow_patterns` filtering is
  client-side fnmatch of every pattern against every walked file: a 1,000-pattern batch
  against a 29k-file dir is ~29M fnmatch calls **per batch** (~870M for 30 batches) —
  minutes of pure CPU inside the 300s budget — and literal filenames containing fnmatch
  metacharacters (`[`, `*`, `?`) would mis-match. Staged copies are the #1151/#885
  precedent, O(batch) per batch, exact-set by construction, and directly observable by
  the existing fake-HfApi harness (which walks `folder_path` at call time). Worst-case
  copy volume is bounded by the byte cap (2 GiB total across all batches, local disk —
  seconds).
- **`path_in_repo` is the SAME `f"{dest}/{name}"` for every batch**, and staged files
  keep their dir-relative paths ⇒ final repo paths byte-identical to the unchunked
  upload (AC-6, constraint 5).
- **Cache-exclusion parity:** the batch walk uses the same PRUNE + `g*_dl` predicate as
  today's `_dir_stats`, so the staged set equals what `ignore_patterns=IGNORE` admits
  (all IGNORE patterns are directory-shaped); `ignore_patterns=IGNORE` is still passed on
  batch calls as defense-in-depth and call-shape uniformity.
- **`entries.sort(reverse=True)`** on `(mtime, size, Path)` tuples is exactly `_up_logs`'
  newest-first idiom (Path supports `<` for the tie-break).
- **No new bash:** every edit is inside the python heredoc except the print-cap constant;
  the 300s `timeout`, `set +e`, rc-file capture, and breadcrumbs are untouched (AC-4).

### 3.4 Serial print-cap resize (120 → 200)

Worst realistic case with chunking: ~16 base persist lines + ~43 worker-log lines (#885
worst case) + chunk header + 30 batches × 2 lines + summary ≈ **122 lines** — just over
the current 120 cap. Precedent: #885 doubled 60 → 120 when its worst case landed AT the
cap. Resize the streamer constant (`if [ "$_n" -le 120 ]` → `-le 200`, rendered line
~1936) and update its sizing comment: 200 × 2000 chars = 400 KB, inside the ~1 MB GCE
serial buffer. The durable transcript is unaffected either way (it has no line cap); this
only keeps the live serial view complete for the single-chunked-dir case. A pathological
all-three-dirs-chunked crash may still truncate the serial view — acceptable, the
transcript is the audit of record (#854).

(test 4) and the abort streak bounding failure-mode burn (test 6) — plus the untouched
`timeout 300` string assert (test 2). Documented as a deliberate test-scope limit.

## 6. Kill criteria (what would make this approach wrong)

1. **≤1,000-file commits still reliably 504 on this repo** — then commit size is not the
   binding variable (repo-level or endpoint-level fault); the fix would need a different
   mechanism (e.g. overflow-repo target), i.e. a re-plan, not a tweak. Evidence says
   otherwise (#658: ≤5,000-file commits succeeded on this exact repo).
2. **Repo-path identity cannot be preserved across batches** — would violate constraint
   5. Verified false at design time: `path_in_repo` + staged relpaths compose to the
   identical layout, and test 4 pins it.
3. **The heredoc cannot host the logic fail-soft** (an unavoidable raise path) — would
   violate #854. The pseudocode has every external call inside try/except and the
   subshell keeps `timeout 300` + rc capture; test 6 pins rc 0 under total upload
   failure.
4. **Staging copy time rivals the budget** — impossible under the existing 2 GiB byte
   cap on local disk (seconds); if the cap were ever raised ≫ 2 GiB this design needs
   re-sizing (documented in the heredoc comment).

## 7. Risks + failure modes

| Risk | Likelihood | Mitigation |
|---|---|---|
| Heredoc quoting/indent slip (surfaces only at VM boot) | Medium | behavioral tests execute the REAL extracted heredoc; `test_render_startup_script_is_valid_bash` (`bash -n` both branches); no new bash structure |
| 30 batches × commit latency exceeds 300s on a pathological dir | Medium | newest-first ⇒ truncation loses only the OLDEST files (strict improvement over total loss); knob tunable upward; rc 124 breadcrumb already discriminates timeout |
| Repo dir grown past 10k files across batches trips a server-side cap | Low | #658 evidence: incremental growth past 10k via separate commits succeeded on this repo; per-commit count 1000 ≪ 10k (the #1190 cap is per-commit-per-dir); logged FAILED lines surface it if wrong |
| Serial view truncation with multiple chunked dirs | Low | cap 120→200 covers the single-chunked-dir worst case; transcript (uncapped) is the audit of record |
| Snapshot-fixture regeneration masks an accidental co-drift | Low | regenerate in a dedicated commit with provenance note; structural tests keep the snapshot non-tautological (documented procedure) |
| Backoff sleeps burn budget when Hub is down (worst: 2 batches × 10 s) | Low | abort streak bounds it at ~2 failed batches per dir; 300s timeout is the hard bound |
| `FAKE_HUB_FOLDER_FAIL_MATCH` extension breaks the existing retry test | Low | default (unset) preserves match-all semantics; existing test runs unmodified |
| Retry / abort-streak counts a "failure" whose commit actually landed (the fu5 gateway-timeout shape) | Medium | benign: `upload_folder` preupload dedup makes the re-commit a no-op/empty commit at the same repo paths; the streak still correctly stops burning budget on a dir the gateway can't confirm; logged lines make the ambiguity visible |

## 11. Decision rationale (load-bearing values)

- **What:** batch size + chunk threshold `EPS_PERSIST_DIR_MAX_FILES_PER_COMMIT = 1000`.
  **Why:** must be small enough that a single commit reliably completes (the 29k commit
  504'd; HF's own uploader never exceeds 1000/commit and requires <40 s successes to
  scale up to it) and large enough that the pathological 29k dir fits ~30 commits inside
  the 300s budget (30 × ~3–10 s commit latency ≈ 90–300 s; newest-first covers the
  overrun tail). **Source:** huggingface_hub 0.36.2 `_upload_large_folder.py`
  `COMMIT_SIZE_SCALE` max (read from the installed wheel) + #658 (≤5,000/commit
  demonstrated on this exact repo) + incident #1090 numbers. **Alternatives:** 2,000
  (fewer commits, but exceeds HF's own reliability ladder — rejected as less grounded);
  75–150 (HF's conservative ladder start — rejected: 194–387 commits cannot fit 300 s);
  `upload_large_folder` (no `path_in_repo`, worker-pool design — rejected, verified);
  `allow_patterns` slices (O(patterns × files) fnmatch blowup + metachar hazard —
  rejected, §3.3).
- **What:** per-batch retry attempts = 2 with `EPS_PERSIST_RETRY_BACKOFF_S` (10 s)
  backoff. **Why/Source:** verbatim mirror of the #1151 `_up_bundle(retry=True)`
  pattern already in this heredoc (task-body constraint names it the pattern to mirror).
  **Alternatives:** ≥3 attempts (budget risk under a dead Hub — rejected); no retry
  (drops the one cheap recovery for a transient 504 — rejected, the Goal names retry).
- **What:** `EPS_PERSIST_DIR_BATCH_ABORT_STREAK = 2`. **Why:** bounds worst-case budget
  burn on a dead Hub to ~2 failed batches (~4 attempts + 1 backoff ≈ tens of seconds)
  per dir while tolerating one isolated batch failure mid-dir. **Source:** the #1151
  attempts=2 budget philosophy; exact value **ungrounded within [1, 3] — env-tunable;
  needs no smoke** (the 300 s timeout is the hard backstop and the fail-soft path is
  test-pinned). **Alternatives:** no abort (a dead Hub burns the whole budget on
  sleeps/attempts — rejected); abort at 1 (a single transient batch failure kills the
  dir — rejected).
- **What:** newest-first (mtime desc) ordering. **Why:** under a budget/abort
  truncation the most recent partial results (the crash-adjacent, highest-forensic-value
  files) land first. **Source:** #885 `_up_logs` newest-first precedent ("the crashing
  worker wrote last") + the task-body constraint naming newest/smallest-first.
  **Alternatives:** smallest-first (maximizes file COUNT landed but biases toward the
  least informative files; bytes are not the bottleneck at 14 MB/29k files — rejected);
  walk order (arbitrary — rejected).
- **What:** print cap 120 → 200. **Why/Source:** #885's own sizing method re-run with
  the chunked worst case (§3.4). **Alternatives:** leave at 120 (single-chunked-dir case
  truncates the live serial view — acceptable but strictly worse; the transcript makes
  either choice safe).
