### 4.A — Shared tri-state reader in `src/explore_persona_space/task_workflow.py` (workflow-surface module, in scope)

```python
KEEP_RUNNING_TAG = "keep-running"

def keep_running_tag_state(task_id: int) -> bool | None:
    """Tri-state read of the issue-wide teardown shield (#1485).

    True  -> task read OK and the ``keep-running`` tag is present.
    False -> task read OK and the tag is absent, OR the task does not
             exist (registry miss / ad-hoc pod: nothing to shield).
    None  -> the read ERRORED (branch-guard RuntimeError, corrupt
             frontmatter ValueError, StaleTaskPathError registry
             corruption, other OSError) - the tag state is UNKNOWABLE.
             Callers on a DESTRUCTIVE path treat None as "do not
             destroy" (the _wedge_keep_running 'unknown' posture).
    """
    try:
        task = get_task(int(task_id))
    except StaleTaskPathError:
        return None            # multi-hit registry corruption: unknowable
    except FileNotFoundError:
        return False           # no task => no tag; ad-hoc pods stay terminable
    except (RuntimeError, ValueError, OSError):
        return None
    tags = (task.get("frontmatter") or {}).get("tags") or []
    return isinstance(tags, list) and KEEP_RUNNING_TAG in tags
```

Exception ordering is load-bearing: `StaleTaskPathError` subclasses `FileNotFoundError` (task_workflow.py:851), which subclasses `OSError` — catch narrowest first. A companion test pins `pod_lifecycle._KEEP_RUNNING_TAG == task_workflow.KEEP_RUNNING_TAG` (the pod_lifecycle constant at L2283 stays, to keep that module's lazy-import independence).

### 4.B — `cmd_terminate` guard (`scripts/pod_lifecycle.py`)

New private helper, called as the FIRST statement of `cmd_terminate` (L2648, BEFORE `_guard_upload_verification_before_terminate` — the shield is issue-scoped and should refuse before the operator is told to run the upload verifier):

```python
def _guard_keep_running_before_terminate(
    issue: int, *, name_suffix: str | None, force_flag: bool, dry_run: bool
) -> None:
    """Refuse the BARE (issue-wide) terminate when the owning task carries
    the keep-running tag (#1485; CLAUDE.md § Pods: the shield is
    ISSUE-WIDE). --name-suffix surgical destroys are the operator's
    explicit single-pod choice and are never blocked. Fail-CLOSED on an
    unreadable tag (terminate is irreversible; the _wedge_keep_running
    'unknown' posture), fail-OPEN on task-not-found (ad-hoc pods)."""
    if name_suffix is not None:
        return                                  # surgical path: allowed
    try:
        from explore_persona_space.task_workflow import keep_running_tag_state
    except ImportError:
        state: bool | None = None               # unknowable -> fail closed
    else:
        state = keep_running_tag_state(issue)
    if state is False:
        return
    if force_flag:
        print("[pod_lifecycle] WARN: terminating ALL pods for issue "
              f"#{issue} DESPITE keep-running state={state!r} because "
              "--force-keep-running was passed. A live follow-up / parallel "
              "suffixed pod on this issue WILL be destroyed.", file=sys.stderr)
        return
    if dry_run:
        print(f"[dry-run] NOTE: issue #{issue} keep-running state={state!r} "
              "- a real run would REFUSE this issue-wide terminate.",
              file=sys.stderr)
        return                                  # preview proceeds (destroys nothing)
    if state is True:
        raise SystemExit(
            f"REFUSED: issue-wide terminate for task #{issue} - the task "
            f"carries the 'keep-running' tag, the documented Step-8 teardown "
            f"shield (CLAUDE.md § Pods; a live follow-up / parallel pod may "
            f"depend on this issue's pods; incident 2026-07-17: "
            f"pod-1345-onpolicy destroyed mid-launch by an issue-wide sweep).\n"
            f"  Destroy ONE pod surgically: pod.py terminate --issue {issue} "
            f"--name-suffix <slug>\n"
            f"  Drop the shield first:      uv run python scripts/task.py "
            f"remove-tag {issue} keep-running\n"
            f"  Deliberate override:        re-run with --force-keep-running "
            f"(logs a loud warning)."
        )
    raise SystemExit(   # state is None
        f"REFUSED: issue-wide terminate for task #{issue} - the keep-running "
        f"tag state could not be read (task state unreadable), and terminate "
        f"is irreversible. Fix the task read (task.py view {issue}) or re-run "
        f"with --force-keep-running to override deliberately."
    )
```

## 11. Decision Rationale

1. **Override flag: `--force-keep-running` on `cmd_terminate` only; NO override on finalize.**
   *What:* one additive flag on the terminate parser; finalize's only remedy is `task.py remove-tag <N> keep-running` + re-run.
   *Why:* terminate is the interactive/operator surface and the house pattern gives each terminate guard an explicit skip flag with a loud warning; finalize is the automation surface, and the incident is precisely automation bypassing the shield — a finalize force flag would be a bypass channel automation could learn to compose (`--yes`/`--skip-confirm-artifacts` reuse explicitly ruled insufficient by the clarifier). Removing the tag is semantically complete: destroying ALL pods leaves the tag purposeless, and a partial destroy is the `--name-suffix` path, which needs no override.
   *Source:* `--skip-upload-verify` precedent (`scripts/pod_lifecycle.py:2885-2896`); incident record 2026-07-17 pod-1345-onpolicy (task #1485 body); tag-lifecycle prose (CLAUDE.md § Routing: "remove the tag … so the auto-stop re-arms", incidents #477/#573).
   *Alternatives:* no flag anywhere (rejected — no escape when the tag/registry is unreadable, the fail-closed case); force flag on both (rejected — re-opens the automated-bypass hole); env-var override (rejected — invisible in argv/audit).

2. **Fail-open vs fail-closed on tag-lookup errors: tri-state — not-found → proceed; read-error → refuse/skip.**
   *What:* `keep_running_tag_state` returns `False` on `FileNotFoundError` (proceed), `None` on `StaleTaskPathError`/`RuntimeError`/`ValueError`/`OSError`/ImportError (terminate refuses with the override named; finalize skips at rc 3).
   *Why:* an absent task genuinely has no tag (and ad-hoc pods must remain terminable — the same scope logic as the upload-verify guard's L2506 comment); but an ERRORED read on an IRREVERSIBLE destroy must not silently override a possible user shield — a wrongly-skipped teardown is re-runnable, a wrongly-destroyed mid-launch pod is not.
   *Source:* the watcher's `_wedge_keep_running` tri-state precedent (`autonomous_session_watch.py:6587-6600` — `"unknown"` → ALERT-only, "NEVER auto-stopped, which would silently override the user's explicit tag"); contrast `_warn_on_terminal_parent_provision`'s fail-open (safe there because it is warn-only, L2351-2359).
   *Alternatives:* uniform fail-open (the `_task_keep_running` shape — rejected: safe only under the watcher's 2-miss debounce, absent on a one-shot CLI); uniform fail-closed incl. not-found (rejected: breaks ad-hoc pod cleanup, the upload-guard's documented out-of-scope class).

3. **Finalize skip semantics: rc 0 + `ok: true` + `phase: teardown_skipped` for tag-present; rc 3 + `ok: false` for unreadable; sidecar KEPT on both; confirm_artifacts + currency gate NOT run; check placed after handle read, before the #1026 gate.**
   *What/Why:* rc 0 because a tag-present skip is the shield WORKING — an automated round retrying/parking on an expected healthy state is the wrong outcome, and rc-keyed prose-driven consumers (the Step 8 orchestrator flow) read rc 0 as "finalize completed its job". Precision on "the harness" (fact-check correction, 2026-07-18): the consumer behind the L2089-2091 rc comment is `router_acceptance.py` (`_run_finalize_and_verify`, L1507-1539), and it is PHASE-keyed, not rc-keyed — it requires `phase == "teardown"` at rc 0, so the rc-0 choice does NOT spare it; on a tagged finalize it raises a loud, SAFE "Refusing to claim success" error. That exposure is accepted: acceptance-harness dispatches never carry `keep-running` (assumption 8). rc 3 for unreadable because that state is NOT expected and belongs in the existing "teardown SKIPPED, operator recovers" exit-3 family (the #1026 gate's shape). Sidecar kept because the Mn4.3 rename exists solely to stop a LATER finalize mis-targeting a fresh run through a stale handle — here the pod is ALIVE and the handle must survive for the eventual real finalize. The artifact gates exist to GATE teardown (finalize docstring L1863-1871), so with teardown vetoed they add only confusing exit-3 "recover then finalize" hints; the Step-8 upload-verifier agent owns standalone verification. Early placement (after `read_handle_sidecar`) gives the skip JSON `pod_name`/`chosen_kind` without running any gate.
   *Source:* dispatch_issue.py L2081-2107 (rename rationale + rc comment), L1976-1988 (typed exit-3 family), incident record (the 23:42:00Z finalize).
   *Alternatives:* rc 3 for tag-present (rejected — harness false-crash + retry churn on a healthy shield); running confirm_artifacts first (rejected — its FAILs would exit 3 before the skip, blocking on artifact state irrelevant to a no-teardown outcome); renaming the sidecar (rejected — orphans the live pod's handle).

4. **Guard ordering in `cmd_terminate`: keep-running check FIRST, before the upload-verify guard.**
   *What/Why:* a shielded issue must refuse before the operator is told to run the upload verifier (whose refusal message prescribes actions that are moot under the shield); the tag check is also the cheaper read. Dry-run prints a would-refuse NOTE and proceeds with the preview — matching the upload guard's "dry-run wants to preview, not block" contract (L2485-2489).
   *Source:* `_guard_upload_verification_before_terminate` structure + dry-run contract (L2469-2557).
