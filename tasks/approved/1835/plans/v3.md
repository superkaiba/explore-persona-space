## Plan Summary

`kind: infra` workflow-fix, 0 GPU-h, non-architectural (additive knob + gate
extension; no status enum / marker schema / CLI-contract removals). Two
deliverable legs plus prose:

1. **`--extra-sync-path` knob** — a per-dispatch, repeatable, repo-relative
   path knob threaded `dispatch_issue.py launch` → `spec.extra["extra_sync_paths"]`
   → `SlurmBackend.prepare`, which stages each extra path to the cluster
   scratch via a **separate additive rsync invocation** (`-a --relative
   --partial --mkpath`, **no `--delete`**, **no exclude patterns**). The main
   `build_rsync_command` argv stays **byte-identical** when the knob is absent.
2. **Lane-aware carry-over gate** — `verify_carryover_inputs.py` gains
   `--lane {clone,rsync}` (default `clone` = today's behavior byte-identical)
   + repeatable `--extra-sync-path`; under `--lane rsync`, a citation that
   classifies `pass` (in-ref) but whose path is NOT covered by
   `RSYNC_INCLUDE_PATHS ∪ extra_sync_paths` downgrades to
   `FAIL(rsync-lane-not-synced)` with the recoverable remediation
   "re-dispatch with --extra-sync-path <path>".
3. **SKILL.md Step 6a.5 prose** — one clause naming the rsync-lane contract
   (when `backend:` ∈ SLURM lanes or `auto` — the auto chain is fellows-FIRST,
   an rsync-materialized lane — pass `--lane rsync` + the plan-named
   `--extra-sync-path` values to the gate; thread the same values to
   `dispatch_issue.py launch`).

## Requirement + acceptance criteria

**Requirement (Goal):** plan-cited git-committed `eval_results/` reference
inputs actually reach rsync-materialized SLURM instances, and the Step 6a.5
gate stops certifying them as reachable when they will not.

Acceptance criteria:

1. `build_rsync_command()` default argv is byte-identical to today
   (pinned by the existing tests in `tests/test_slurm_backend_render.py` and
   the `scripts/issue1609_acceptance.py` echo — neither changes).
2. With `spec.extra["extra_sync_paths"] = ["eval_results/issue_1689/ladder", ...]`,
   `SlurmBackend.prepare` issues the main rsync PLUS one additive rsync whose
   argv contains the dot-anchored extra sources, `--relative`, `--mkpath`,
   NO `--delete`, and NO `--exclude` flags (so the `eval_results/` exclude
   cannot suppress the transfer — the exclude/`--delete` interaction the
   candidate flagged is sidestepped structurally, not patched around).
3. Path validation fails loud (ValueError at parse/validate time) on:
   absolute paths, `..` traversal, empty strings, paths escaping the repo
   root. Dot-anchoring (`./` prefix) is normalized on, not required from,
   the caller.
4. A launch that OMITS the knob after a prior launch staged extra paths does
   NOT delete the staged trees (main rsync's `--delete` only reaches inside
   its own dot-anchored include trees; `eval_results/` at the destination
   root is outside all of them AND excluded — assert via argv-level test
   reasoning + a code comment, no live cluster test needed).
5. `verify_carryover_inputs.py --lane rsync` downgrades an in-ref
   `eval_results/...` PASS to FAIL with reason `rsync-lane-not-synced` when
   not covered; `--extra-sync-path eval_results/issue_1689/ladder` restores
   PASS for paths under that prefix. `--lane clone` (and flag absence) is
   byte-identical to today on the existing test corpus.
6. `--extra-sync-path` on `dispatch_issue.py launch` threads to
   `spec.extra["extra_sync_paths"]` and rides the handle sidecar (same
   channel as `--env-pin`); it is accepted on any lane but only the SLURM
   lane consumes it (lane-inert elsewhere, exactly like `env_pins` on
   non-workload-cmd paths).
7. All new/changed behavior pinned by tests (see §Tests); `ruff` clean on
   touched files; no-flags `workflow_lint.py` shows no NEW failure lines.

## File paths + concrete diffs

1. **`src/explore_persona_space/backends/slurm.py`**
   - `EXTRA_SYNC_PATHS_KEY = "extra_sync_paths"` module constant (+ add to
     `__all__`).
   - `validate_extra_sync_paths(paths) -> tuple[str, ...]`: normalize to
     dot-anchored `./<repo-relative>`; reject absolute / `..` / empty;
     dedupe order-preserving.
   - `build_extra_rsync_command(*, src_root, dest_root, robot_alias,
     extra_paths) -> list[str]`: `rsync -a --relative --partial --mkpath
     <./path>... <alias>:<dest>/` — NO `--delete`, NO excludes. Same
     `pyproject.toml` src_root sanity assert as `build_rsync_command`.
   - `run_extra_rsync_sync(...)`: thin subprocess wrapper mirroring
     `run_rsync_sync` (cwd=src_root, timeout 600, check=True).
   - `SlurmBackend.prepare`: after the main `self._rsync(...)`, read
     `spec.extra.get(EXTRA_SYNC_PATHS_KEY)`; when non-empty, RE-validate via
     `validate_extra_sync_paths` (the handle sidecar JSON round-trips
     tuple→list; never assume tuple) + run the extra rsync via a new
     injectable seam `extra_rsyncer` (constructor kwarg, default
     `run_extra_rsync_sync`) so tests inject a recorder and existing
     injected `rsyncer` stubs stay untouched. The helper docstring notes the
     additive-only staleness property: across attempts an extra tree keeps
     files deleted from the source (no `--delete` by design — fine for
     committed reference inputs). The
     extra rsync sources come from the SAME resolved `rsync_src` as the main
     rsync (the materialized branch tree carries committed `eval_results/`
     by construction — it is a full worktree of the branch commit). NOTE: a
     path present only in the repo-root working tree but not in the branch
     commit will be absent from the materialized tree — the extra rsync then
     copies nothing for it; rsync exits 23 (partial transfer / missing
     source) which check=True surfaces loud. Acceptable fail-loud behavior;
     the gate (leg 2) is what prevents reaching this state.
2. **`scripts/dispatch_issue.py`**
   - `launch.add_argument("--extra-sync-path", action="append", ...)` next
     to `--env-pin`; thread into `extra["extra_sync_paths"]` via
     `validate_extra_sync_paths` (import from backends.slurm). UNLIKE
     `--env-pin` there is NO workload-cmd-only refusal (the knob is
     lane-scoped, not command-scoped); it is accepted on every lane and
     consumed only by the SLURM `prepare`. The launch path echoes the
     resolved `extra_sync_paths` into the launch marker note (gate→launch
     drift audit, critic concern (a)).
3. **`scripts/verify_carryover_inputs.py`**
   - CLI: `--lane {clone,rsync}` default `clone`; `--extra-sync-path`
     repeatable.
   - Coverage predicate: `covered(path) = any(path == p or
     path.startswith(p + "/") for p in COVER_SET)` where COVER_SET =
     de-dot-anchored `RSYNC_INCLUDE_PATHS` (imported from
     `explore_persona_space.backends.slurm`) ∪ normalized extra paths.
   - Downgrade rule applied post-classification, `--lane rsync` only:
     Finding(verdict="pass", reason="in-ref") whose path is not covered →
     verdict="fail", reason="rsync-lane-not-synced", detail names the
     remediation (`--extra-sync-path <top-level-covering prefix>`).
     `on-main-not-on-branch` / `committed-unpushed` FAILs already block and
     keep their remediations; warns/skips untouched. JSON output gains
     `lane` + `extra_sync_paths` fields.
4. **`.claude/skills/issue/SKILL.md`** (Step 6a.5 second stanza): one clause
   — when the task's `backend:` frontmatter names an rsync-materialized
   SLURM lane (every member of `router._PER_CLUSTER_LANES`: `nibi`/`fir`/
   `mila`/`fellows`, plus the legacy `cluster` alias) OR is absent/`auto`
   (the auto chain is fellows-FIRST, an rsync lane), run the gate with
   `--lane rsync` plus any plan-named `--extra-sync-path` values, and thread
   the SAME values to the `dispatch_issue.py launch` call — compose both
   invocations from ONE variable so the gate-PASSing set and the launched
   set cannot drift; a `rsync-lane-not-synced` FAIL is recoverable in-step
   by adding the flag, not a park. Mechanizable coverage check (from the
   critic round): the clause's lane list ⊇ `router._PER_CLUSTER_LANES`.
5. **Tests** (see §Tests). `scripts/issue1609_acceptance.py`: NO change
   (default argv byte-identical — acceptance pin untouched).
