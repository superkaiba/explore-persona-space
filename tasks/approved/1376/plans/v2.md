## 2. Method delta (vs prior art in the repo)

Two prior arts exist; tier (e) reuses one and deliberately diverges from the other:

**(i) Tier (d) `clean_vm_workspace_hf_cache` (vm_disk_guard.py:640–762)** — the structural template. Tier (e) reuses verbatim: the `_scan_hf_cache(hub)` import/scan seam (line 672), the `TierResult` degrade-to-skipped-on-any-exception contract, the `expected_freed_size → bytes_freed` reporting convention, `append_disk_guard_event(..., apply=apply)` sidecar gating, and the `main()`-only production opt-in (`reclaim_tiers and tmp_root is not None`). **Delta:** tier (d)'s predicate is *repo-level* (`repo.last_accessed < cutoff` → delete ALL revisions). That predicate is structurally blind to the motivating incident: the data repo's repo-level `last_accessed` is **1.0–1.2 h old on every live probe** (sessions read it hourly), so a repo-level gate never fires while 76 GB of superseded revisions accumulate inside it. Tier (e) therefore gates at *revision* level (refs + revision `last_modified` + exclusive-blob atime), which tier (d) has no notion of.

**(ii) The watcher's `_hf_stale_revisions` / `_vm_reclaim_hf_hub_cache` (autonomous_session_watch.py:7712–7830, TTL `EPM_VM_DISK_HF_TTL_DAYS`=14)** — an EXISTING revision-level evictor of the SAME home cache, which I verified live: during this planning session it evicted ~200 revisions / ~37 GB of the data repo as they crossed its 14 d TTL (log lines `hf-hub-ttl: evicted 5 revision(s), freed 1.4G`; repo went 295 revs / 76.2 GB → 96 revs / 38.9 GB between my two probes). **Why tier (e) is still needed:** (a) the watcher arm fires only inside the watcher's vm-disk CRITICAL remediation, is silent (no attribution, no escalation, no sidecar naming of the consumer), and its triple guard at 14 d lags a fast accumulation — in the 2026-07-16 episode the bulk was 7–14 d old and untouchable, while the guard CLI (the tool the cron runs and a human reaches for) had zero visibility and freed 0.53 GB; (b) the Goal explicitly demands guard-side attribution + escalation + a 7 d reap. **Predicate delta (measured, load-bearing):** the watcher requires whole-revision "unread" (`max(blob_last_accessed)` over ALL the revision's files ≥ TTL). Blobs are shared across revisions, so hourly reads of the fresh revision keep the shared blobs' atime fresh and make superseded revisions look "read": at 7 d that guard selects **0 candidates / 0.00 GB** on the live data repo. Tier (e) instead applies the atime keep-guard only to a candidate's **exclusive** blobs (blobs referenced by no surviving revision) — protecting exactly the data that deletion would actually destroy, while `delete_revisions`' internal refcounting protects shared blobs regardless. Live probe: the no-atime cut on the post-sweep cache yields 4 candidates / 8.60 GB; the exclusive-atime guard keeps the 3 recently-read pinned ones (correct behavior) and would have cleared the incident's 7–14 d-old cold bulk.

**Interplay note (documented in §4):** two independent reapers (watcher @14 d CRITICAL-gated, tier (e) @7 d threshold-gated) now cover the same cache; both use `delete_revisions` (idempotent), and a lost race surfaces as tier (e)'s fail-soft skip, never a crash.

### 3.3 Pure selector (unit-testable, mirrors `_hf_stale_revisions`'s pure-selector style)

```python
def _home_hf_reap_selection(info, now: float, age_seconds: float):
    """Returns (whole_repo_stale, rev_candidates, kept_reason_counts).
    whole_repo_stale: [CachedRepoInfo] with now - repo.last_accessed > age  (arm 1)
    rev_candidates:   [(CachedRepoInfo, [CachedRevisionInfo])]              (arm 2)
    """
    whole, revlevel = [], []
    for repo in info.repos:
        if now - repo.last_accessed > age_seconds:
            whole.append(repo)                      # arm 1: covers stale models/datasets wholesale
            continue
        revs = list(repo.revisions)
        if len(revs) <= 1:
            continue                                # single-revision fresh repo: never touched
        kept_blobs = {f.blob_path for rev in revs for f in rev.files
                      if "main" in rev.refs or now - rev.last_modified <= age_seconds}
        cands = []
        for rev in revs:
            if "main" in rev.refs:                  # main-ref'd: always kept
                continue
            if now - rev.last_modified <= age_seconds:   # recently written: kept
                continue
            excl = [f for f in rev.files if f.blob_path not in kept_blobs]
            newest_excl_atime = max((f.blob_last_accessed for f in excl), default=0.0)
            if excl and now - newest_excl_atime <= age_seconds:
                continue                            # exclusive data recently READ: kept (fail-keep)
            cands.append(rev)
        if cands and len(cands) == len(revs):       # constraint: never wholly empty a
            cands = sorted(cands, key=lambda v: v.last_modified)[:-1]   # recently-accessed repo
        if cands:
            revlevel.append((repo, cands))
    return whole, revlevel
```

Notes on each subtlety:

- **Hub layout:** tier (e) scans `root / "hub"` — exactly tier (d)'s convention (line 717); `datasets/`, `xet/`, `stored_tokens/` etc. are out of scope (attribution detail line states "hub/ only"; the 2026-07-16 episode was 97 of 101 GB in `hub/`).
- **`refs` semantics:** only `main` protects unconditionally (task-body predicate). The live population confirms non-main refs are truncated-commit-hash refs minted by pinned reads (`'77d04e45'`, `'037fcbb2'`, `'b33429f77b86'`) — protecting all refs would exempt the reap target. A pinned revision still in active use is protected by the exclusive-atime + `last_modified` gates instead; `delete_revisions` removes the deleted revisions' ref files via `DeleteCacheStrategy.refs`.
- **Blob sharing:** deletion frees only blobs unreferenced by surviving revisions (`expected_freed_size` reflects this — verified against hub 0.36.2). The tier reports expected bytes in `detail` and books them as `bytes_freed`/`total_discovered_bytes` (tier-(d) convention, line 732–734); the realized read is the guard-level `free_gb_before/after` delta, and the detail line says so explicitly ("expected, blob-refcount; realized = guard free-GB delta").
- **Age-gate source (pick + justify):** arm 1 uses repo-level `last_accessed` (same signal as tier (d) — atime-based, relatime-safe: `/` is mounted `rw,relatime` — verified; the 24 h relatime coarseness is dwarfed by the 7 d window, tier (d)'s own argument at line 644–647). Arm 2 uses revision-level `last_modified` (the only revision-native timestamp; `CachedRevisionInfo` has no `last_accessed`) plus the exclusive-blob atime keep-guard — the whole-revision atime alternative is measured-dead (§2). Every unreadable/absent signal keeps the revision.
- **`.incomplete` blobs / warnings:** in-flight `blobs/*.incomplete` files are not referenced by any snapshot symlink, so `scan_cache_dir` never surfaces them and `delete_revisions` never touches them — disposition: untouched. A repo that fails scanning lands in `HFCacheInfo.warnings` and is absent from `info.repos` → automatically kept; tier (e) appends one detail line `"scan warnings: N (repos kept)"` when `info.warnings` is non-empty (verified field on 0.36.2).
- **Concurrent use:** an in-flight download has fresh `last_modified` → kept; a revision being actively read has fresh exclusive-blob atimes → kept; a race with the watcher's 14 d evictor at `execute()` time raises inside the try → tier degrades to `skipped` with the reason, nothing else deleted (fail-soft, tier-(d) contract).

## 11. Decision Rationale

- **`EPS_VM_HOME_HF_CACHE` = `~/.cache/huggingface` (not HF_HOME-derived).** What: fixed watch root. Why: the home cache is the default-HF_HOME consumer that went invisible; env-derived resolution varies per process and is already the watcher arm's approach — a fixed root makes the cron's coverage deterministic; the resolve-equality guard prevents double-cover with tier (d). Source: task body + tier-(d) knob precedent (`EPS_VM_WORKSPACE_HF_CACHE`, vm_disk_guard.py:648).
- **`MAX_AGE_DAYS` = 7.** What: the shared age window. Why safe: strictly inside the watcher's proven 14 d TTL on the same cache class (that arm evicted the same revision population live with zero incidents); everything reaped is re-downloadable by construction; four independent KEEP guards on top. Why 7 and not 14: at the incident the dominant bulk was 7–14 d old — 14 d is exactly the window that failed. Source: task body (default 7 named); the 7-vs-say-5 choice within the safe band is the body's, not re-derived — marked as body-sourced, safety-argued.
- **`REPO_ESCALATE_GB` = 40.** What: always-escalate single-repo footprint. Why: ~8% of the 485 GB boot disk; sits between the existing 20/50 GB escalation bands (vm_disk_guard.py:131) and well below the incident's 76.2 GB, so the incident shape always escalates; the just-swept repo (38.9 GB) sits under it, bounding steady-state noise. Source: task body (default 40); calibration argument above is this plan's.
- **Revision gate = `last_modified` + exclusive-blob atime, NOT whole-revision atime.** Source: live measurements this plan (§2): whole-revision atime at 7 d selects 0 candidates / 0.00 GB on the motivating repo (shared blobs read hourly), i.e. it structurally defeats the tier; exclusive-blob atime protects exactly the destroyable data while `delete_revisions` refcounting protects the rest.
- **Escalation dedup (band + 25% growth + ack sentinel, apply-gated persistence).** Source: #679/#911 precedent in the same file (`escalate_active_cache`, lines 126–312) — "always escalates" is implemented as "always attributed in report/JSON; push/sidecar deduped per (repo, band)" to avoid a push per cron pass during a multi-hour episode.
- **Local ~15-line selector instead of importing the watcher's `_hf_stale_revisions`.** Why: the predicate deliberately differs (exclusive-atime, main-ref, 7 d), and importing the ~8 k-line watcher module into the guard adds a heavyweight cross-script dependency for a helper we'd immediately override; cross-referenced in comments both ways. Source: reuse-hierarchy judgment call, stated here per the search-before-building rule (the search WAS done — §2(ii)).
