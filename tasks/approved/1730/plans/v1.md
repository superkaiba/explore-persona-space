**Landed sibling — NOT the gap:** `.claude/rules/background-automation.md`

inventory shells `gcloud compute instances list --configuration=eps-gcp`
from a non-login tool shell — has no equivalent guard. This is the gap
this fix documents.

**Cluster-specific-paths family in gotchas.md:** L37 already carries
`Hard-coded library paths in orchestrate/env.py — cluster-specific.` The
new bullet lands in the same family (a cluster-specific PATH fact tied
to this VM's snap install of gcloud).

**Live-verified evidence:**
- `command -v gcloud` in this tool shell → `/snap/bin/gcloud` (this
  shell inherits `/snap/bin` on PATH somehow — but the FILING evidence
  captured a real session where it did NOT resolve; the fix is
  defensive documentation regardless).
- `ls -l /snap/bin/gcloud` → `/snap/bin/gcloud -> google-cloud-cli.gcloud`
  (symlink present).
- `/etc/profile.d/apps-bin-path.sh` exists on this VM and appends
  `/snap/bin` to PATH — but only login shells source `/etc/profile.d/*`,
  which is the documented mechanism (`man bash` § INVOCATION).
- `grep -c 'snap/bin'` on all three targets → **0** (compose-time
  re-verification of the body's absence-of-guard evidence).

Web-confirmed fact: snap ships `/etc/profile.d/apps-bin-path.sh` which
only fires in login shells; non-login shells (cron, some SSH invocations,
`bash -c` inside tools) do not source it and miss `/snap/bin`. This is
standard Ubuntu snap behavior (see e.g. Ubuntu askubuntu discussions of
`snap` PATH; the file itself is a stock artifact of the `snapd` package).

## 4. Design

Three edits, each with an exact anchor, exact replacement text, and a

### Edit 1 — `.claude/rules/gotchas.md` (primary target)

**Anchor.** The cluster-specific-paths bullet family in `# Gotchas`
starts at L36. L37 currently reads:

```
- Hard-coded library paths in `orchestrate/env.py` — cluster-specific.
```

**Change.** Insert a new bullet immediately AFTER L37 (i.e. as L38, with
the existing L38 shifting down):

```
- `gcloud` lives at `/snap/bin/gcloud` on this VM; `/snap/bin` is on the LOGIN-shell PATH only (via `/etc/profile.d/apps-bin-path.sh`, sourced only by login shells), so a non-login tool / cron shell running `gcloud compute instances list --configuration=eps-gcp` (or any other `gcloud` call) gets `No such file or directory`. Prepend `export PATH="/snap/bin:$PATH"` (or wrap in `bash -lc`) before any `gcloud` call, and treat a non-zero `gcloud ... list` rc as **UNKNOWN**, never as an empty inventory — a failed live-compute scan that reads as "no GCE instances" silently green-lights a money-spending surface (background-automation.md L117-124 documents the CRON-path janitor's rc=3 `list-failed` escalation for the same reason; the interactive/agent-shell path is what this bullet covers).
```

**Rationale.** This IS the primary target the task body names. Sits in
the cluster-specific paths family, matches the file's existing bullet
register (one bulleted sentence, sometimes with a mechanism clause).

### Edit 2 — `.claude/skills/daily/SKILL.md` "Useful commands" export
