# Plan v1 — #2033 daily-fix: RAM floor required on wide fan-out dispatches

**Kind:** infra (workflow-fix; `workflow_fix_target: scripts/verify_plan.py, .claude/rules/plan-compute-sizing.md`)
**Branch/worktree:** `issue-2033` at `.claude/worktrees/issue-2033`

## 1. Requirement

A wide fan-out must never silently land on a lower-RAM ladder rung than its per-leg
RSS estimate needs (#1739 wave-1: 5-6 of 12 GCE legs rc=137 OOM after the spot rung
downgraded half the fleet to 85 GB-RAM a2-highgpu-1g boxes). The dispatch-side flags
already exist (`--min-gpu-mem-gb`, #1468, `dispatch_issue.py:3098`; `--min-ram-gb`,
`dispatch_issue.py:3008`, threaded to `spec.extra` with the
`GpuRamBelowMinRamGbError` typed terminal) and `gcp.a100_40_fallback_for_intent`
gates the A100-40 rung on `min_gpu_mem_gb` — but NOTHING plan-side requires the
floor to be declared. Close the gap plan-side only:

1. `scripts/verify_plan.py` gains **WARN-only check `c52_fanout_ram_floor`**.
2. `.claude/rules/plan-compute-sizing.md` gains the RAM-floor prose rule
   (sibling of its existing `--min-gpu-mem-gb` capture-phase bullet at L24-30).
3. `.claude/rules/LESSONS.md` row for `plan-compute-sizing.md` mentions the
   ladder-rung floor trigger (`workflow_lint.py --check-lessons-index` stays green).
4. `tests/test_verify_plan.py` pins the new check's WARN / PASS / SKIP arms.

### Acceptance criteria

- **AC1:** `c52_fanout_ram_floor` is registered in `CHECKS` (after
  `check_plan_wall_vs_slurm_time_bin`) and is WARN-only (never FAIL).
- **AC2 (RAM arm):** WARN when the plan text declares a per-leg peak RSS / host-RAM
  estimate strictly above `gcp.MACHINE_RAM_GIB["a2-highgpu-1g"]` (85 GiB) AND at
  least one plan-embedded `dispatch_issue.py launch` argv lacks `--min-ram-gb`.
- **AC3 (GPU-mem arm):** WARN when the plan declares a per-leg VRAM/HBM peak
  strictly above `gcp.A100_40_USABLE_GIB` (38.0 GiB) AND at least one launch argv
  lacks `--min-gpu-mem-gb`.
- **AC4 (floor-too-low arm):** WARN when the flag IS present but its value is
  strictly below the declared estimate for that dimension.
- **AC5 (graceful SKIPs, c50 conventions):** SKIP when no launch-shaped
  `dispatch_issue.py` command exists in the plan; when an argv does not dry-parse
  (c46 arm 1 owns that); when the `gcp` constants import fails (off-repo run);
  when NO RSS/VRAM estimate token is found in the plan.
- **AC6:** applies to ALL kinds (`del kind` — same posture as c50: an OOM'd leg
  dies identically regardless of task kind).
- **AC7:** the Step 9c mapped-test gate + `workflow_lint.py --check-lessons-index`
  + ruff on touched files all pass.

## 2. Method delta

No existing check reads RSS/VRAM tokens (grep: 0 hits). New check composes the
EXISTING c46/c50 helper family — `_c50_launch_argvs(plan)` for argv extraction
(WITHOUT c50's single-launch skip: c52 evaluates EVERY launch argv — fan-outs are
exactly the multi-launch case), `_c46_argparser()` / `_c46_dry_parse` /
`_c46_has_flag` for parsing — plus one new token extractor.

## 3. File paths + concrete changes

### 3a. `scripts/verify_plan.py`

- New helper `_c52_declared_peaks(plan: str) -> tuple[float | None, float | None, list[str]]`:
  scans plan lines; RAM side = lines containing `RSS` (word-boundary, or
  `host RAM` / `peak RAM`) with a `(\d+(?:\.\d+)?)\s*Gi?B` number on the same
  line; GPU side = lines with `VRAM`/`HBM`/`GPU[- ]mem` + a GiB number. Returns
  (max_ram_gib, max_vram_gib, notes). Fenced code blocks are NOT excluded
  (launch commands live in fences; estimate prose usually outside) — keep the
  scan whole-plan and line-anchored, conservative by construction.
- New `check_fanout_ram_floor(plan: str, kind: str) -> CheckResult`, cid
  `c52_fanout_ram_floor`, name `"fan-out RAM/GPU-mem floor vs ladder rung"`.
  Logic: extract peaks → SKIP if both None; extract launch argvs via
  `_c50_launch_argvs` → SKIP if none; lazy-import `MACHINE_RAM_GIB`,
  `A100_40_USABLE_GIB` from `explore_persona_space.backends.gcp` (try/except →
  SKIP, c50 pattern); per argv: dry-parse (unparseable → per-argv note, not a
  WARN), then apply AC2/AC3/AC4. WARN message names the offending argv index,
  the declared estimate, the rung constant, and the exact flag to add.
  Deliberately NOT conditioned on live lane reachability or
  `GCP_PROVISIONING_DISABLED` (policy-flip-robust; the ladder is rollback-only
  today but plans outlive policy flips; `--min-ram-gb` is threaded lane-generically;
  WARN-only polarity absorbs inert-lane false positives). Docstring documents the
  named residual: a plan quoting a FLEET-total RSS ("720 GB across 12 legs") on
  one line reads as a per-leg peak → false WARN (WARN-only absorbs it).
- Register in `CHECKS` after `check_plan_wall_vs_slurm_time_bin` (L~9856).

### 3b. `.claude/rules/plan-compute-sizing.md`

Extend the existing floor block (L24-30): any dispatch — and especially any
fan-out — whose per-leg peak RSS exceeds the smallest reachable ladder rung's
host RAM (`gcp.MACHINE_RAM_GIB["a2-highgpu-1g"]` = 85 GiB) MUST thread
`--min-ram-gb <per-leg peak RSS>`; symmetric with the existing
`--min-gpu-mem-gb` sentence; cite #1739 wave-1 + c52 as the mechanical WARN.

### 3c. `.claude/rules/LESSONS.md`

Update the `plan-compute-sizing.md` row's fires-when trigger to include
"ladder-rung RAM/GPU-mem floors on dispatches/fan-outs".

### 3d. `tests/test_verify_plan.py`

New tests (follow the file's existing fixture-plan conventions): (t1) RSS 100 GB
+ launch argv without `--min-ram-gb` → WARN; (t2) same + `--min-ram-gb 100` →
PASS; (t3) `--min-ram-gb 60` below the 100 GB estimate → WARN (AC4); (t4) VRAM
60 GB + no `--min-gpu-mem-gb` → WARN; (t5) no launch command → SKIP; (t6) no
estimate tokens → SKIP; (t7) estimate ≤ 85 GiB → PASS (no WARN).
