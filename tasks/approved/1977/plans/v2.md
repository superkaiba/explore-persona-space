# Plan v2 — task #1977: exempt path-limited `git add --all -- <pathspec>` in guard_root_code_commit.sh

ARCHITECTURAL: no (guard-hook behavior refinement; no public contract, no marker schema, no status enum change).

Revision of v1 addressing the Methodology critic's two Must-Fix findings (MF-1 cwd-gate, MF-2 pre-`--` closed allowlist) plus three of its nice-to-haves (post-`--` `./`/`*` rejection; rename-line parsing restricted by status code; multi-clause pin test).

## 1. Requirement + acceptance criteria

**Requirement.** `.claude/hooks/guard_root_code_commit.sh` currently latches `add_all_chained=1` on the bare tokens `-A` / `--all` / `.` in any add clause (token-scan arm, L678) and blocks at L1121 with "the landing set cannot be classified at hook time". For the path-limited form `git add --all -- <explicit pathspec>` that rationale does not apply: the pathspec bounds the landing set, and git can enumerate it at hook time. Two sessions (#1895, #1945) composing exactly this form (sweeping status-move residue incl. deletions under known paths) were blocked and had to recompose.

**Acceptance criteria:**
1. `git add --all -- <clean explicit pathspec(s)> && git commit -m x`, composed with the hook cwd AT the repo root and no cd/chdir ambiguity, is NO LONGER blocked by the blanket-staging arm — it flows into Layer-2 classification with the add's would-be landing set fully enumerated per file.
2. Bare blanket forms (`git add -A|.|--all` with no `--`-anchored pathspec, or with any opaque/unsafe token anywhere in the add clause) still block byte-for-byte (existing B13 semantics unchanged).
3. The exemption opens NO unclassified staging channel: every gated file the path-limited add would stage (modified, untracked, renamed-in) enters `pending` and the cert check; deletions stay exempt via the existing `landing_sha` rc=1 path. In particular (MF-1) the exemption NEVER engages when the pathspec-resolution base is not provably the repo root, and (MF-2) NEVER engages when the add clause carries any pre-`--` token beyond the closed allowlist.
4. FAIL-CLOSED bias preserved on every ambiguity arm: masked/quoted tokens, pathspec magic, git read failure, unparseable/C-quoted porcelain, cwd-gate failure, unknown flags — all keep the block (exit 2).

## 2. Method delta

Prior state: unconditional latch on the blanket token; no add-clause pathspec awareness. Delta: (a) a dedicated per-add-clause post-scan (the #1620 commit-clause second pass at ~L700-740 is the REQUIRED structural template — verb-gated, closed flag enumeration, unknown ⇒ unsafe); (b) a Layer-2 scoped `git status --porcelain=v1 --untracked-files=all` read, gated on the SAME cwd conditions as the #1620 commit scoping (`cwd_ok=1 && cd_nonroot=0`), whose per-file results feed the existing `text_paths` channel (worktree binding + deletion exemption + pending union all already exist there). No new parser; no change to the mask/split machinery.

## 3. Design (concrete diffs — refine at implementation)

### 3a. Layer 1 (`classify_cmd`) — dedicated add-clause post-scan (MF-2)

Keep the existing L678 latch arm REMOVED from the first token loop and replace it with a dedicated second pass per ADD clause, structurally mirroring the commit-clause pass at ~L700-740 (`saw_verb` gate, `after_ddash` tracking, closed enumeration):

- Skip tokens until the verb token `add` (`saw_verb` gate). Pre-verb wrapper tokens: a `--chdir*` token ⇒ clause is exemption-INELIGIBLE (mirror of the commit pass's `scope_unsafe` arm at ~L713).
- **Pre-`--` tokens after the verb: closed allowlist `{-A, --all}` ONLY.** Any other pre-`--` token — positional pathspec (`src`, `.`, `./`), any other flag (`-f`, `--force`, `-N`, `--intent-to-add`, `-u`, `--update`, `--pathspec-from-file*`, unknown long/short flags, flag clusters) — makes the clause exemption-INELIGIBLE (the latch fires as today). Rationale (critic MF-2, both empirically confirmed): pre-`--` positionals are live pathspecs the post-`--`-scoped status read would under-enumerate, and `-f` stages ignored files `git status --untracked-files=all` does not list.
- `--` token: set `after_ddash`.
- **Post-`--` tokens: pathspec candidates.** REJECT (clause exemption-INELIGIBLE) any token that is masked (`*"$FILL"*`), quote/backslash-bearing, contains `$` / backtick / parens / `<` / `>`, leads with `~` or `:` (pathspec magic) or `/` (absolute) or `-` (flag-shaped) or `./` (blanket-equivalent spelling), or is exactly `.` / `..` / `*` (bare-`*` shell-expands against the executing cwd — divergent from git-glob semantics, reject). Other plain glob-bearing tokens (`scripts/*.py`) stay clean (git evaluates them — mirrors `classify_candidate` L~120).
- Clause end, for a clause whose lead matched a blanket flag: ELIGIBLE (allowlist-only pre-`--`, `--` seen, ≥1 clean candidate, zero rejections) ⇒ do NOT latch `add_all_chained`; append the candidates to a new global `add_pathspecs` (newline-separated, initialized in the `classify_cmd` globals reset at L544). INELIGIBLE ⇒ `add_all_chained=1` (today's behavior, including the no-`--` form).
- An add clause with NO blanket flag is untouched by this pass (existing behavior: text_paths collection only).

### 3b. Layer 2 — cwd-gated add-pathspec resolution (MF-1)

Insert AFTER the `hook_cwd` / `cwd_ok` computation (~L1135-1140) and after `cd_nonroot` is available — NOT at the L1121 block site (v1's placement preceded the cwd computation; critic MF-1):

```
+# Path-limited `add --all -- <pspecs>` (issue #1977): resolve the add's
+# would-be landing set at hook time. Pathspecs resolve against the EXECUTING
+# cwd, never $GUARD_REPO (#1620 MF-1) — so the resolution engages ONLY when
+# the hook cwd provably IS the repo root and no in-command cd precedes the
+# clause; otherwise FAIL CLOSED with the blanket block.
+if [ -n "$add_pathspecs" ]; then
+  if [ "$cwd_ok" != 1 ] || [ "$cd_nonroot" != 0 ]; then
+    <BLOCK, exit 2 — same message as the blanket arm + a one-line cwd-gate diag>
+  fi
+  mapfile -t apspecs < <(printf '%s\n' "$add_pathspecs" | grep -v '^$')
+  if add_status=$(git -C "$GUARD_REPO" status --porcelain=v1 --untracked-files=all -- "${apspecs[@]}" 2>/dev/null); then
+    case "$add_status" in *'"'*) <BLOCK, exit 2 — C-quoted (special-char) path in porcelain: unparseable, fail CLOSED> ;; esac
+    # Extract per-file paths from `XY path` lines; a ` -> ` split applies ONLY
+    # to lines whose XY field contains R or C (rename/copy) — both sides are
+    # taken (old = deletion → landing_sha exempts; new lands content).
+    # Append every extracted path to text_paths (worktree binding + pending
+    # union both follow from existing machinery).
+  else
+    <BLOCK, exit 2 — git read failed: cannot classify the path-limited add; same shape as the staged-read failure block at ~L1163>
+  fi
+fi
```

Note the L1121 blanket block itself is UNCHANGED in placement and semantics; only its message gains the pointer to the sanctioned form (3c). An empty `add_status` (pathspec matches nothing) is a clean no-op: nothing will be staged by the add under those pathspecs, so nothing is appended — the commit's own staged read still governs.

### 3c. Block message + header comment

Update the L1121 block message to name the sanctioned path-limited form (`git add --all -- <explicit paths>`, root cwd, no cd prefix) and the header comment (~L48) documenting the blanket-add fail mode.
