# Plan — Issue #737: artifact-reuse `(h)` check for reused training-input mixes / on-policy caches

## Plan Summary

**What this is.** A workflow-surface documentation/spec edit (`kind: infra`,
0 GPU-h, non-architectural). It adds an **eighth** reuse-fitness check — `(h)`
— to the artifact-reuse fitness checklist, covering REUSED **training-input
artifacts** (a parent's `train/*.jsonl` mix, an on-policy response cache, a
reused eval JSON consumed as a downstream input). Today the `(a)-(g)`
checklist verifies that reused ADAPTERS/checkpoints resolve on HF (check `(e)`)
and pass recipe/regime/scaling fitness, but there is NO check that a reused
TRAINING-INPUT MIX is reachable AND fetchable on the TARGET BACKEND before plan
approval.

**The (h) check, two parts (split by artifact source).** (i) **source
resolution** — the reused training-input file is reachable through EITHER HF
(`huggingface_hub.list_repo_files`) OR git-tree reachability for committed
`eval_results/issue_<M>/` JSONs (`git ls-tree -r origin/main`); the
git-clone-only GCP/SLURM lanes pick up committed `eval_results/...` via the
clone itself, so an in-git eval JSON is a valid reuse path even without HF
presence. (ii) **target-backend fetchability** — the §9-named backend can
actually STAGE the file: RunPod pods `snapshot_download` any HF file (so its
HF leg ≈ source resolution); GCP/SLURM git-clone-only lanes need an explicit
`snapshot_download` step in the workload for HF/data-repo files, while
committed `eval_results/...` files arrive with the clone (no extra fetch). A
local untracked file (built but never uploaded NOR committed) is reachable
nowhere and needs upload-first OR a self-contained regen phase. **The check
fires when EITHER part fails** (resolution OR fetchability) without an
upload-first step or a self-contained regen phase. Enforced at PLANNING time
(planner self-attest → consistency-checker independent re-check → critic
REVISE), not at phase2 runtime.

## 1. Goal

Add a reuse-fitness check `(h)` to the artifact-reuse checklist so that a plan
reusing a parent experiment's TRAINING-INPUT MIX / on-policy response cache /
downstream-input eval JSON must verify, BEFORE plan approval, that each reused
input file (i) is SOURCE-RESOLVABLE (reachable through HF via
`huggingface_hub.list_repo_files`, OR — for a committed `eval_results/...`
JSON — through git-tree reachability) AND (ii) is FETCHABLE on the chosen
target backend — and, when EITHER part fails (the git-clone-only GCP/SLURM
lanes stage no VM-local `data/`, and a local-only file resolves nowhere; or an
HF-resolved file that the §9 lane still cannot stage), the plan must upload the
mix first or carry a self-contained regen phase. Propagate the `(h)` reference
into every call site that enumerates `(a)-(g)` today, INCLUDING the implementer
mirror-set memory.

## 2. Prior Work

- **`.claude/rules/artifact-reuse.md`** is the canonical `(a)-(g)` fitness
  checklist (the bulleted list spans lines 32-62; `(g)` ends at line 62, the
  "Any check that fails → retrain / regenerate" line is at line 64). `(e)`
  already covers HF resolution via `huggingface_hub.list_repo_files` for
  adapters/checkpoints/datasets, and `(f)` covers content-identity / SHA-pinning
  when execution fetches an HF mirror of a locally-verified file. Neither
  covers the case where a reused training-input file was NEVER uploaded and the
  target lane cannot stage it, NOR the distinct fetchability-only miss (an
  HF-resolved file the chosen lane still fails to stage).
- **In-git eval-JSON reuse is an existing, sanctioned path.** `planner.md` line
  120 names `**Aggregated eval JSONs:** eval_results/issue_<M>/ in git` as a
  reuse source — these are git-tracked, NOT (necessarily) HF-uploaded. On the
  git-clone-only GCP/SLURM lanes a COMMITTED `eval_results/...` JSON arrives via
  the clone itself. So the `(h)` resolution rule must NOT require HF presence
  for in-git eval JSONs — that would falsely reject a valid in-git reuse path
  and contradict the existing planner spec. The resolution rule is therefore
  split by artifact source: HF-resolution for training mixes / on-policy caches
  / HF-uploaded eval JSONs, git-tree reachability for committed
  `eval_results/...` JSONs.
- **Enforcement is a 3-stage defense** (artifact-reuse.md lines 66-72): planner
  step 5 self-attest → consistency-checker independent diff + Hub-resolution
  gate → critic Methodology lens item 9 REVISE. The new `(h)` check slots into
  the same three stages. A fourth surface — the implementer mirror-set memory
  at `.claude/agent-memory/implementer/reference_reuse_fitness_mirror_set.md` —
  is the canonical "any change to (a)-(g) must touch these files" checklist for
  future implementers; it is in scope (see Edit 6) because after this change it
  would otherwise tell a future implementer "FOUR files / (a)-(g)" when the
  truth is "FIVE files / (a)-(h)".
- **The motivating incident (#734 round 4):** a plan reusing a parent's
  `train/*.jsonl` mix that the parent built but never uploaded passed planning
  + 3 review rounds, then crashed phase2 at the pre-train
  `assert data_path.exists()` on the git-clone-only GCP lane because the mix is
  on neither HF repo and the lane cannot stage it. The `(a)-(g)` check verifies
  reused ADAPTERS resolve on HF (`(e)`), but has no check for training-input
  mixes / on-policy caches; the fact-checker verifies adapter paths but not
  train-mix paths. This is the **both-missing** case (resolution miss AND
  fetchability miss). The `(h)` check must ALSO catch the **fetchability-only**
  case (HF-resolved but the §9 lane cannot stage it — e.g. a CDN outage, a
  region restriction, or a missing `HF_TOKEN` for a gated repo).
- **GCP-lane mechanics (verified from source).**
  `src/explore_persona_space/backends/gcp.py` `render_startup_script` (lines
  1360-1365) does `git clone --depth 1 --branch <branch> <repo_url>
  "$WORKLOAD_ROOT"` and runs the `workload_cmd` verbatim from `$WORKLOAD_ROOT`
  (lines 954-1006). There is no VM-local `data/` mounted into the GCE
  instance — the only files present are what `git clone` brings (which INCLUDES
  committed `eval_results/...`) plus whatever the workload itself downloads
  (HF, etc.). So a `data/issue_<N>/.../train.jsonl` that lives only as an
  un-committed, un-uploaded local-VM file is genuinely unreachable on the GCP
  lane, while a committed `eval_results/issue_<M>/...` JSON is present after the
  clone. This grounds the split-by-source `(h)` semantics.
- **Prior workflow-surface rule-file edits** establish the convention: this is
  an additive bullet to an existing checklist + propagated references, the same
  shape as prior `(a)-(g)` extensions (`(g)` was itself added for #601, `(f)`
  for #600). No new subsystem, no contract change. Those prior fixes also each
  touched the mirror-set memory's enumeration — Edit 6 keeps the memory in sync,
  the same as those precedents would have.

> TRAINING-INPUT artifacts):** for any reused training-input file — a parent's
> `train/*.jsonl` mix, an on-policy response cache, or an `eval_results/` JSON
> consumed as a downstream INPUT (NOT an adapter / checkpoint, which `(e)`

> - **(i) source resolution** — the file is reachable through ONE of:

>   - **git-tree reachability** for a committed `eval_results/issue_<M>/` JSON —
>     `git ls-tree -r origin/main -- eval_results/issue_<M>/<file>` returns the
>     file (the git-clone-only GCP/SLURM lanes pick this up automatically via
>     the clone; `planner.md` line 120 sanctions in-git eval JSONs as a reuse
>     source);
> - AND **(ii) target-backend fetchability** on the §9-named backend:
>   - RunPod lane — HF/data-repo files reach via
>     `huggingface_hub.snapshot_download` (so the (i) HF leg ≈ (ii) there);
>   - GCP/SLURM git-clone-only lanes — HF/data-repo files require an explicit
>     `huggingface_hub.snapshot_download` step in the workload, AND committed
>     `eval_results/...` files arrive with the clone (no extra fetch needed);
>   - a local untracked file (`data/issue_<N>/.../train.jsonl` built but never
>     uploaded NOR committed) is reachable nowhere → upload-first OR a

  outage, region restriction, missing `HF_TOKEN`). An AND-only gate would miss
