## 4. Design

### 4.1 What triggers the check ("bare denominator")

The check fires only when the body asserts an LLM-judge denominator AND
fails to disclose the judge-error fraction near it.

**Denominator claim regex** (scanned in `## Methodology` + `## Results`, fences stripped):
A judge-denominator token is one of:
- `n=<N>` / `n = <N>` where `N >= 100` (small n's are sample-disclosure footnotes, not eval denominators);
- `<N> completions` / `<N> judgments` / `<N> attempted` / `<N> EM` / `over <...> questions × <K> completions each (<N>...)` — the EM-eval phrasing #715 uses.

Only judge-context denominators count: the claim must co-occur in a section
that also names a judge (`claude-sonnet-4-5`, "judge", "EM rate",
"misaligned", "Batch API", "sycophancy", "refusal", "trait", "fact"). This
keeps the check from firing on a training-row count like "6349 rows".

**Disclosure phrase regex** (PASS if present in the SAME section as the claim, OR in the `**Repro:**` footer):
Any of (case-insensitive): `529`, `Overloaded`, `judge[- ]error`, `judge[- ]API[- ]error`, `n_judge_error`, `n_em_judge_error`, `excluded from the denominator`, `post-correction`, `judge-error-corrected`, `API[- ]error`, `judge_failed`, `− n_judge_error` / `- n_judge_error`. (The published #715 body matches several of these on both line 63 and line 123 — verified.)

If a denominator claim has an adjacent disclosure phrase → that claim is
disclosed → it does not trigger the eval-JSON read.

*(Out of scope for v3 — the disclosure regex, `_JUDGE_CONTEXT_RE`, and the
`n>=100` floor were APPROVED by the Statistics lens and the Alternatives
concerns on them are recoverable; this section is UNCHANGED from v2.)*

### 4.2 Reading the judge-error fraction from committed eval JSONs

Source priority (all verify-only, no `src/` edit):

1. **Corrected/aggregate pareto JSON with an explicit total** — scan `eval_results/issue_<N>/*.json` for a dict carrying `judge_error_correction.judge_error_totals.sweep_total` + a denominator (`metadata.n_attempted_total`, or sum of per-cell attempted fields). #715's `pareto_em_vs_narrow_corrected.json` gives `sweep_total=882`, pooled denom `19200` → 4.59%; per-cell `n_em_judge_error` gives worst-cell 32.5%. **This is the cleanest in-tree ground truth.** *(Field-name note — verified against the committed file: the corrected-pareto leaf cells carry `n_em_attempted` / `n_em_judge_error` / `n_em_scored` / `n_em_misaligned`. The denominator for source 1 is the leaf-cell `n_em_attempted` field — NOT `n_attempted` / `n_total`, which do not exist on these leaf cells. The per-cell `em_rate/*.json` aggregates of source 2 use `n_total` instead, so the two source classes carry DIFFERENT attempted-field names; the helper must accept both — see §4.6.)*
2. **Per-cell aggregate JSONs** — scan `eval_results/issue_<N>/**/*.json` for cell dicts carrying a judge-error count field under any of the recognized keys: `n_judge_error`, `n_em_judge_error`, `breakdown.n_judge_error`, `breakdown.n_api_error`. (Note: #715's `em_rate/*.json` carry only `breakdown.n_parse_error`, which is the DISTINCT parse-error class, NOT the 529 class — so for #715 the per-cell aggregates alone do NOT surface the signal; source 1 does. The check must NOT treat `n_parse_error` as a judge-API-error.)
3. **Raw judge rows** — `raw_*.json` with `error: True AND reasoning.startswith("error:")`. These are NOT committed in-tree for #715 (the `raw_path` is a pod-side absolute path). The check attempts this source ONLY if a `raw_*.json` is actually present in the committed tree; otherwise it is skipped. (Do NOT fetch from HF — that adds a network dependency and an `EPM_VERIFY_BODY_NO_HF` fence interaction; the in-tree corrected JSON already carries the signal.)

**Aggregation rule:** compute (a) a **pooled** judge-error fraction = total judge-error rows / total attempted rows across all cells found, and (b) the **worst-cell** fraction = max over cells of (cell judge-error / cell attempted). The verdict uses BOTH (worst-cell catches the concentrated-load case #715 exhibits — DFT 256 step had 130/400 = 32.5% even though pooled was 4.59%).

**Recognized-field guard:** if NO recognized judge-error field/total is found anywhere under the resolved `eval_results/issue_<N>/`, return PASS with note `"no judge-error data available in committed eval JSONs — graceful skip"` (is_warn=False; a missing signal is not a finding). This is what makes the check safe for older issues (#608/#545 use different JSON layouts) and for the file-only / stdin invocation path where the issue number is unknown.

### 4.2a Eval-root resolution ladder (NEW in v3 — the round-1 REVISE fix)

The judge-error read needs `eval_results/issue_<N>/`. At the Step 9a-bis
pre-merge gate that dir lives ONLY on the issue worktree branch, so the v2
MAIN-only `_resolve_repo_root()` could not reach it. v3 resolves the eval
ROOT (the directory under which `eval_results/issue_<N>/` sits) through a
ladder, transposing the `--methodology-doc` precedent (explicit arg +
`--issue`-path on-disk fallback at lines 6480-6501). The helper accepts an
optional `eval_root: Path | None` and resolves in this order — STOP at the
first that yields a directory containing `eval_results/issue_<N>/`:

1. **(i) `--eval-root <path>` (explicit, gate-time worktree path).** If passed, resolve `eval_root / "eval_results" / f"issue_{N}"`. This is the orchestrator's gate-time path (mirrors how it passes `--methodology-doc <worktree>/docs/methodology/issue_<N>.md`).
2. **(ii) `--file <worktree>/tasks/<status>/<N>/body.md`-derived repo root.** When invoked via `--file`, walk the body-source path's parent chain to the nearest ancestor that is a repo root — either contains a `.git` entry (file or dir; a worktree's `.git` is a file) OR matches a `.claude/worktrees/issue-<N>` segment — and resolve `eval_results/issue_<N>/` relative to it (worktree-aware).
3. **(iii) `git rev-parse --show-toplevel` from cwd.** Useful when the orchestrator chdirs into the worktree before invoking the check; the explicit cwd-aware fallback (`subprocess.run(["git","rev-parse","--show-toplevel"], cwd=os.getcwd(), ...)`, conservative — any nonzero/OSError → skip this rung).
4. **(iv) `_resolve_repo_root()` (MAIN — the v2 behavior, now the tail fallback).** This binds post-merge (Step 9b experiments / Step 10d code paths), when `eval_results/issue_<N>/` has reached MAIN.
5. **Graceful PASS** if NONE of (i)-(iv) resolve to a directory containing `eval_results/issue_<N>/` — `_scan_issue_judge_errors` returns `None` → the check PASSes with the graceful-skip note (is_warn=False). The graceful-PASS-on-missing-dir invariant from v2 stays at the bottom of the ladder; the check NEVER false-FAILs when it cannot find data.

**Ordering is implementer judgment** (see §-deviations): the exact relative
order of (i)/(ii)/(iii) may be tuned AS LONG AS all four legs are reachable
and the graceful-PASS tail stays last. The load-bearing invariant is that a
worktree-cwd or `--eval-root`-passed invocation REACHES the worktree's
`eval_results/issue_<N>/`, which v2 could not.

### 4.3 Verdict ladder

```
if no bare (undisclosed) judge denominator claim in body:        PASS  "no bare judge denominator asserted"
elif disclosure phrase present near the claim / in footer:       PASS  "judge-error fraction disclosed in body"
elif issue number unknown (stdin path, no eval root):            PASS  "skipped — issue number unknown; cannot read eval_results" (is_warn=False)
elif eval root unresolved (ladder (i)-(iv) all miss):            PASS  "skipped — eval root unresolved" (is_warn=True, mirrors check_repro_committed_claims_exist outside-repo branch)
elif no recognized judge-error field in any eval JSON:           PASS  "no judge-error data available — graceful skip"
elif worst_cell_frac > 0.05 OR pooled_frac > 0.05:               FAIL  "<N> rows (worst cell X%, pooled Y%) returned judge-API errors and were silently counted; body states a bare n=<...> denominator with no disclosure. Recompute as n_misaligned/(n_attempted − n_judge_error) and disclose the excluded fraction."
elif worst_cell_frac > 0.01 OR pooled_frac > 0.01:               WARN  (same detail, is_warn=True)
else:                                                            PASS  "judge-error fraction below 1% threshold"
```

### 4.4 Why code, not a model call?

N/A as a model-call decision — this is a deterministic verifier check (regex
+ JSON read), not a classifier over unstructured data. A model call would be
nondeterministic and add a network dependency to a mechanical gate that must
run offline in CI/`monkeypatch` tests.

### 4.5 DV scope: EM-first, generic-ready

Ship the check covering EM (the demonstrated failure mode) AND the generic
LLM-judge case in ONE check, because the trigger (a bare judge denominator)
and the signal (a recognized judge-error field) are behavior-agnostic — the
denominator-claim regex already includes sycophancy/refusal/trait/fact judge
nouns, and the eval-JSON field scan is keyed on field NAMES not on EM
specifically. The recognized-field guard means siblings whose JSONs do not
yet carry a judge-error field simply PASS (graceful), so generalizing now
costs nothing and avoids a second near-duplicate check later. **Argument for
this over EM-only:** an EM-only regex would have to hardcode `em_rate` /
`misaligned` and would silently miss the next #545-style refusal Batch run;
the field-name-keyed design covers all of them with no extra surface.

### 4.7 Pseudocode (the verdict core)

```python
def check_judge_error_denominator(body, *, issue=None, eval_root=None, body_source_path=None):
    name = "judge-API-error denominator disclosed"
    if not (is_v3(body) or is_v4(body)):
        return CheckResult(name, True, "skipped — legacy/v2 body")
    method = section_text(body, "Methodology") or ""
    results_s = section_text(body, "Results") or ""
    footer = _v4_footer_text(body)  # the **Repro:**/**Context:** tail, or ""
    scan_region = _strip_fenced_blocks(method + "\n" + results_s)
    claims = [m for m in _JUDGE_DENOM_RE.finditer(scan_region)
              if _JUDGE_CONTEXT_RE.search(_window(scan_region, m))]
    if not claims:
        return CheckResult(name, True, "no judge denominator asserted")
    disclosed_region = scan_region + "\n" + footer
    if _JUDGE_ERROR_DISCLOSURE_RE.search(disclosed_region):
        return CheckResult(name, True, "judge-error fraction disclosed in body")
    if issue is None:
        return CheckResult(name, True, "skipped — issue number unknown")
    repo = _resolve_eval_root(issue, eval_root=eval_root, body_source_path=body_source_path)
    if repo is None:
        return CheckResult(name, True, "skipped — eval root unresolved", is_warn=True)
    stats = _scan_issue_judge_errors(repo, issue)
    if stats is None:
        return CheckResult(name, True, "no judge-error data available in committed eval JSONs — graceful skip")
    pooled = stats["total_err"] / max(stats["total_att"], 1)
    worst = stats["worst_frac"]
    detail = (f"{stats['total_err']} rows (worst cell {worst:.1%}, pooled {pooled:.1%}) "
              f"returned judge-API errors and were silently counted into the n=<...> "
              f"denominator with no disclosure. Recompute as n_misaligned/(n_attempted "
              f"− n_judge_error) and disclose the excluded fraction.")
    if worst > 0.05 or pooled > 0.05:
        return CheckResult(name, False, detail)
    if worst > 0.01 or pooled > 0.01:
        return CheckResult(name, True, detail, is_warn=True)
    return CheckResult(name, True, f"judge-error fraction below 1% (worst {worst:.1%}, pooled {pooled:.1%})")
```

## 11. Decision Rationale (load-bearing thresholds)

- **FAIL threshold >5% (worst-cell OR pooled).** **What:** worst-cell fraction > 0.05 or pooled > 0.05 → FAIL. **Why:** at #715's worst cell the judge-error fraction was 32.5% (130/400) and pooled 4.59% (882/19200), deflating pooled EM by +2.2%/+8.4% — a >5% per-cell loss materially moves a two-decimal EM number. **Source:** #715 R2 corrected data — `eval_results/issue_715/pareto_em_vs_narrow_corrected.json` (`judge_error_correction.judge_error_totals.sweep_total=882`, worst cell `dft_lora/256` 130/400=32.5%, pooled 882/19200=4.59% — all read directly from the committed file). The candidate proposed >5% FAIL; validated against this data.
- **WARN threshold >1%.** **What:** worst-cell or pooled in (1%, 5%] → WARN. **Why:** below ~1% the silently-counted errors do not move a reported EM rate beyond rounding; (1%, 5%] is worth a non-blocking flag so the analyzer discloses but the body still ships. **Source:** candidate's >1% WARN proposal; consistent with #715 pooled 4.59% sitting in the FAIL-via-worst-cell band while pooled-only would be WARN — both signals checked so the concentrated-load case (#715) FAILs.
- **`n >= 100` denominator floor.** **What:** only `n=N` with N≥100 counts as a judge-denominator claim. **Why:** small n's in clean-result bodies are sample-disclosure footnotes ("1 of 400", "5 of 2,000 rows"), not eval denominators; the EM/judge denominators that carry this trap are ≥100 (Betley 8×50=400; sycophancy/refusal panels in the hundreds). **Source:** #715 (n=400); #411/#545/#608 sibling Batch runs all ≳ hundreds.
- **`n_parse_error` EXCLUDED from the judge-API-error count.** **What:** the recognized count keys are `n_judge_error`/`n_em_judge_error`/`n_api_error`, NOT `n_parse_error`. **Why:** the 529 class (`error: True` + `reasoning.startswith("error:")`) is distinct from judge-side parse failures (`reasoning == "parse_error"`); conflating them would mis-attribute parse attrition as API overload. **Source:** the judge error-row contract in `src/explore_persona_space/eval/alignment.py` (read-only reference, per the orchestrator's context item 2).
- **Eval-root resolution ladder ordering.** **What:** resolve `eval_results/issue_<N>/` via (i) `--eval-root` → (ii) `--file`-derived worktree root → (iii) cwd `git rev-parse --show-toplevel` → (iv) `_resolve_repo_root()` (MAIN), graceful-PASS if all miss. **Why:** the v2 MAIN-only resolution was a no-op at the Step 9a-bis pre-merge gate (the eval dir is worktree-only there); the ladder reaches the worktree at gate time while keeping the MAIN-post-merge bind as the backstop. **Source:** the `--methodology-doc` precedent (`verify_task_body.py` lines 6162-6168 docstring / 6465-6501 wiring) — the EXACT working pattern for a gate-time worktree-path arg + `--issue` on-disk fallback; v3 transposes it to the eval root.
