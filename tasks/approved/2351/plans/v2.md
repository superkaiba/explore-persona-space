## 1. Requirement

`scripts/workflow_lint.py::_hf_routing_file_errors` — the per-file body behind the
`--check-live-hf-retry-routing` check (`#1547`), **bundled into workflow_lint.py's
no-flags default run** — is line-based. It skips only lines whose `lstrip()` starts
with `#` or `what=`, so any line whose *text* matches `HF_ROUTING_CALL_RE`
(`hf_hub_download(` / `.upload_file(` / `.upload_folder(` / `create_commit(` /
`push_to_hub(`) is flagged as a "bare HF Hub call in LIVE code" even when that text
sits inside a string literal (module docstring, triple-quoted constant) or a
trailing comment.

This is a **standing** false positive, not a one-off: the Schema-from-artifact rule
(`.claude/agents/experiment-implementer.md` § "Before writing code" item 8) MANDATES
pasting the exact probe command into the consuming file as an
`Observed schema — probe:` docstring block, so every compliant consumer of a banked
HF artifact trips a false FAIL on its own docstring.

Requirement, both directions binding:
- **(R1)** a match located inside a string literal or a comment MUST NOT be reported;
- **(R2)** a match at a real call site MUST still be reported — including a real call
  that shares a line with a masked match, a real call inside an f-string replacement
  field, and a real call below a docstring that merely mentions `retry_transient(` —
  with the emitted message text byte-identical to today's.

R2 is the harder half. Under-flagging a live bare HF call defeats the check's whole
purpose (429 single-point-of-failure detection) and is worse than the false positive
being fixed; v1's code violated R2 twice, and today's shipped code violates it once
more (the wrap-laundering shape, MF3).

## 2. Method delta (what differs from prior related work)

`#1547` introduced the check line-based (a deliberate cheap heuristic) and worked
around the string-literal class **per file** with two constants:
`HF_ROUTING_PATTERN_STRING_FILES` (`workflow_lint.py`, `verify_plan.py` — the
predicate strings themselves) and `HF_ROUTING_GENERATED_CODE_FILES`
(`backends/gcp.py` — pod-side crash-persist heredocs). `#1568` added the frozen
snapshot + the regen flag for staleness, and the message-edit hazard note.

The delta: replace the per-file workaround pattern with a per-**span** mask derived
once per file from `tokenize`, so the class is fixed for every current and future
file instead of one file at a time.

Deliberately NOT a full AST rewrite: the check's wrap heuristic
(`_hf_routing_call_is_wrapped`) is line-and-paren-balance based, and an AST rewrite
would change which lines are reported for true positives — which the
message-stability constraint in §5 A2 forbids while main is red. `ast` is also
useless for the f-string sub-case on this interpreter: before Python 3.12,
`FormattedValue` sub-expressions carry inaccurate source positions.

```python
# Token types whose SPANS are masked out of the routing scan: a predicate
# match inside a string literal or a comment is text, never a call site
# (#2351). f-PREFIXED strings are deliberately NOT masked: before py3.12 an
# f-string is a SINGLE STRING token, so masking it would hide a REAL call in
# a replacement field (`f"dest={hf_hub_download(r, p)}"`) — an under-flag,
# the one direction this check must never take. f-strings therefore keep
# today's over-flagging behavior; the false-positive class being fixed
# (docstrings, triple-quoted constants, comments) is never an f-string.
# FSTRING_MIDDLE (py3.12+, where the literal text parts tokenize separately)
# is admitted so newer interpreters mask f-string TEXT without hiding
# replacement-field code.
_HF_ROUTING_MASK_TOKEN_TYPES: frozenset[int] = frozenset(
    {tokenize.STRING, tokenize.COMMENT}
    | {
        tok
        for tok in (getattr(tokenize, name, None) for name in ("FSTRING_MIDDLE",))
        if tok is not None
    }
)


def _hf_routing_token_is_fstring(tok: tokenize.TokenInfo) -> bool:
    """True when ``tok`` is an f-prefixed STRING token (see
    :data:`_HF_ROUTING_MASK_TOKEN_TYPES` for why those are left unmasked).
    Reads the prefix letters before the opening quote, so ``rf"..."`` /
    ``F'''...'''`` / ``fr"..."`` all count and a plain ``"f"`` string does not.
    """
    raw = tok.string
    quote = min((raw.find(q) for q in "\"'" if raw.find(q) != -1), default=-1)
    return quote > 0 and "f" in raw[:quote].lower()


def _hf_routing_masked_spans(source: str) -> dict[int, list[tuple[int, int]]]:
    """Map 1-based line number -> masked ``[start_col, end_col)`` column spans.

    A span covers a string-literal or comment token, so
    :func:`_hf_routing_file_errors` can drop a predicate match whose start
    column falls inside one (#2351: the line-based scan flagged the
    Schema-from-artifact ``Observed schema — probe:`` docstring blocks that
    `.claude/agents/experiment-implementer.md` MANDATES).

    Spans are COLUMN-grained, not line-grained, because a masked match and a
    real call site can share a line.

    FAIL-SAFE by design: a file that does not tokenize (unterminated
    triple-quote, malformed source) returns ``{}`` — no masking, i.e. exactly
    today's line-based behavior. The check then OVER-flags rather than
    under-flags; a silent skip of an untokenizable file would be the
    under-flag this check exists to prevent.
    """
    spans: dict[int, list[tuple[int, int]]] = {}
    lines = source.splitlines()
    try:
        tokens = list(tokenize.generate_tokens(io.StringIO(source).readline))
    except (tokenize.TokenError, SyntaxError, UnicodeDecodeError):
        return {}
    for tok in tokens:
        if tok.type not in _HF_ROUTING_MASK_TOKEN_TYPES:
            continue
        if tok.type == tokenize.STRING and _hf_routing_token_is_fstring(tok):
            continue
        (srow, scol), (erow, ecol) = tok.start, tok.end
        for row in range(srow, erow + 1):
            start = scol if row == srow else 0
            if row == erow:
                end = ecol
            else:
                end = len(lines[row - 1]) if row - 1 <= len(lines) - 1 else scol + 1
            if end > start:
                spans.setdefault(row, []).append((start, end))
    return spans
```

(`IndentationError` is dropped from the except tuple: **measured** —
`issubclass(IndentationError, SyntaxError)` and `issubclass(TabError, SyntaxError)`
are both True, so `SyntaxError` already covers both and listing them was redundant.
`UnicodeDecodeError` is retained as belt-and-braces even though `generate_tokens`
over an already-decoded `str` cannot raise it. Note the decode boundary is OUTSIDE
this helper: `py.read_text(encoding="utf-8")` in the caller is where a non-UTF-8 file
fails, exactly as it does today — hence the docstring says "malformed source", not
"decode error".)

Add the blanked line view (MF3) directly after `_hf_routing_masked_spans`:

```python
def _hf_routing_blanked_lines(lines: list[str], masked: dict[str, object]) -> list[str]:
    """Return ``lines`` with every masked span overwritten by spaces (#2351).

    EQUAL-LENGTH and COLUMN-PRESERVING by construction, so the view can be
    handed to :func:`_hf_routing_call_is_wrapped` without shifting any column
    offset. Purpose: that helper counts ``(``/``)`` and matches
    :data:`HF_ROUTING_WRAP_RE` over RAW text, so a docstring mentioning
    ``retry_transient(`` with a net-open paren inside the
    :data:`HF_ROUTING_WRAP_WINDOW` launders a REAL bare call below it — an
    under-flag that predates this change and that the span mask lets us close
    for free. Only the WRAP probe reads this view; the reported line number and
    the ``stripped[:100]`` message tail still come from the real line, so
    message bytes are unchanged.
    """
    view: list[str] = []
    for i, line in enumerate(lines):
        spans = masked.get(i + 1)
        if not spans:
            view.append(line)
            continue
        buf = list(line)
        for start, end in spans:
            for col in range(start, min(end, len(buf))):
                buf[col] = " "
        view.append("".join(buf))
    return view
```

### 4.3.1 Documented deviation from Codex Must-Fix 2's suggested assertion

Codex MF2 offered two satisfiers: (a) "preserve masking for literal f-string text
while exposing replacement-field code, using a supplemental parser/span treatment",
or (b) "another conservative mechanism that cannot suppress executable calls". Its
`mechanizable:` line spells out satisfier (a)'s assertions — 0 errors for
`f"docs: hf_hub_download(...)"` AND 1 error for `f"{hf_hub_download(...)}"`.

**This plan takes satisfier (b)**, the f-prefix exemption, and therefore pins 1 error
for BOTH shapes (pin 5 asserts the first as a known over-flag). Reasons:

1. Satisfier (a) needs a brace scanner over f-string token text (`{{`/`}}` escapes,
   nested quotes, format specs, `!r` conversions). Its failure mode — masking a
   region that is actually a replacement field — is precisely the under-flag MF2
   exists to close, so the fix carries the bug class it repairs.
2. `ast` cannot substitute for the scanner: before py3.12 `FormattedValue` positions
   are inaccurate (§2), so there is no cheap authoritative span source on THIS
   interpreter.
3. Satisfier (b) is conservative BY CONSTRUCTION — an f-string is simply left
   unmasked, i.e. exactly today's behavior — so it cannot suppress an executable
   call, which is the property MF2 asks for.
4. The false-positive class this task exists to fix (docstrings, triple-quoted
   constants, comments) never involves f-strings, so (b) gives up nothing the task
   was filed to deliver.
5. On py3.12+ satisfier (a)'s behavior arrives for free via `FSTRING_MIDDLE`, which
   §4.1 already admits. So (b) is the conservative bridge, not a permanent ceiling.

The cost is §7 residual 2, disclosed and pinned rather than silent. If a reviewer at
Step 5 judges (a) mandatory, that is a scope escalation to a follow-up task, not a
silent widening of this diff.

## 9. Kill criteria

- **Kill (fall back to the narrower approach):** if A2 fails — i.e. token-based
  masking changes any existing true-positive message line in a way that is not a
  dropped masked match — abandon the `tokenize` mask and fall back to the task
  body's alternative (track triple-quote state while iterating lines, docstrings
  only, comments left as-is), which cannot move a true positive's line number.
  §3.3 measured A2 as strictly holding, so this is a guard, not an expectation.
- **Kill (abandon the task):** if the mask is shown to suppress a real call site
  anywhere — A5 reporting fewer than 2 `[live-hf-retry-routing]` lines, or either
  pin 3 / pin 4 failing. Under-flagging a live bare HF call is strictly worse than
  the false positive this task fixes; the check exists to catch 429 single points of
  failure. Note that A5 is a WEAK detector of this class: zero live f-string
  replacement-field call sites and zero live wrap-laundering shapes exist, so A5 could
  not have caught MF2 or MF3 — and indeed did not, in either critic's reading of v1
  (both found them by reasoning about the code, and MF3 has been latent on main since
  `#1547`). Pins 3, 4, 6 and 7 are the real detectors, which is why they are
  acceptance criteria and not merely tests. Generalization worth carrying: for a
  checker fix, "the live tree still reports the same thing" is necessary but never
  sufficient evidence — the absent-from-the-tree shapes are exactly where an
  under-flag hides.
