## 1. Goal + requirement + acceptance criteria

**Goal (verbatim from task body):** Before a projected multi-100GB+ LFS upload, probe quota headroom and route to the overflow repo (the #841 v11 pattern) or block with a loud alert — instead of discovering the 403 mid-upload fleet-wide.

**Requirement:** compare PROJECTED upload bytes against REMAINING headroom (`ceiling_tb − used_tb`), which no existing check does — `check_hf_storage_headroom` is binary over/under a static ceiling, `check_hf_storage` is WARN-only, `_validate_persist_headroom` covers only persist-declared training runs, `upload_dir_sharded`/`upload_model` react only after the 403.

**Acceptance criteria:**

1. A projected upload of `P` bytes with `used + P > ceiling` (confirmed by live re-probe) through `upload_dir_sharded` lands ENTIRELY in the private overflow repo, with one `OVERFLOW_POINTER.json` on the canonical repo at the store prefix, one JSONL deviation event carrying `reason: "projected-headroom-proactive"` + `projected_gb`, and a loud `[hf-headroom]` WARNING — zero canonical-repo LFS bytes attempted. (Unit-tested, mocked — INCLUDING one test that does NOT mock `_repo_is_private`: a FakeApi `repo_info` records its `repo_type` kwarg, asserted `== "dataset"` under the default dataset-canonical flow, so the privacy probe's repo_type threading is production-parity-pinned; test 11b.)
2. The same store with `used + P ≤ ceiling` uploads to the canonical repo exactly as today (regression-pinned).
3. A projected upload below `EPM_HF_LARGE_UPLOAD_PROBE_GB` (default 100 decimal GB) triggers ZERO headroom I/O (asserted via a mock call counter).
4. UNKNOWN headroom (API down / suspect probe / `EPM_HF_STORAGE_CHECK=0`) never blocks or reroutes any upload — the existing reactive 403 backstop stays authoritative (fail-open convention preserved).
5. `preflight_check(planned_upload_gb=X)` with LIVE-CONFIRMED-insufficient headroom (the `force_refresh=True` re-probe, via `check_projected_upload_headroom`) and `EPM_HF_OVERFLOW_ROUTING` unset adds an ERROR (report.ok False); with routing armed it adds a WARNING; a stale-high cache whose live re-probe says fits adds NOTHING (no false block); with `planned_upload_gb=None` behavior is byte-for-byte today's (WARN-only). Pinned end-to-end through `preflight_check(...)` itself, not only at the `check_hf_storage` surface (test 21).
6. `upload_model` with routing armed AND `used + dir_size > ceiling` (but under ceiling absolutely) reroutes; with routing unarmed it never reroutes regardless of size (arming contract untouched).
7. `uv run pytest` on the three touched test files passes; `uv run ruff check` on touched files passes; `uv run python scripts/workflow_lint.py` (no-flags default) passes.
8. Text/JSON non-LFS paths (`upload_raw_completions_to_data_repo`, `upload_dataset*`) are untouched — no probe, no routing (v2 "text uploads always, unconditionally" preserved).

## 3. Design

### 3.1 Core helper — `orchestrate/hub.py`

New frozen dataclass + function, placed directly after `check_hf_storage_headroom` (~line 309):

```python
@dataclass(frozen=True)
class ProjectedUploadHeadroom:
    """Verdict of a size-aware account-headroom probe for one planned LFS upload."""
    verdict: str  # "below-threshold" | "disabled" | "unknown" | "fits" | "insufficient"
    projected_tb: float
    used_tb: float | None
    ceiling_tb: float | None   # None on the zero-I/O below-threshold arm; may also be
                               # None on the disabled/unknown arms (passes h.ceiling_tb through)
    basis: str


def check_projected_upload_headroom(
    projected_bytes: int,
    *,
    probe_floor_gb: float | None = None,   # None => _env_float("EPM_HF_LARGE_UPLOAD_PROBE_GB", 100.0)
    confirm_live: bool = True,
) -> ProjectedUploadHeadroom:
    """Does a planned LFS upload of ``projected_bytes`` fit under the public-storage soft ceiling?

    Size-aware wrapper over check_hf_storage_headroom() (#564 — reused, never
    re-implemented). Decimal GB/TB throughout (1 GB = 1e9 bytes), matching
    _BYTES_PER_TB = 1000**4. Never raises on API failure; ValueError only on a
    non-parseable env knob (same fail-fast contract as the #564 knobs).

    * projected below the probe floor  -> "below-threshold", ZERO headroom I/O
      (tiny uploads never pay the ~25 s cache-miss probe).
    * kill switch / disabled           -> "disabled" (escape hatch always wins).
    * probe unknown/suspect            -> "unknown" (fail-open; callers must not
      block or reroute — the reactive 403 backstop stays authoritative).
    * used + projected <= ceiling      -> "fits".
    * used + projected  > ceiling      -> when confirm_live, re-probe with
      force_refresh=True (the trainer.py minute-1 pattern: never act on a stale
      cached over-read) and re-evaluate; only a LIVE-confirmed overflow returns
      "insufficient" (a live-unknown degrades to "unknown").

    Concurrency note: "fits" is advisory, not a reservation — two concurrent
    large uploads can both read fits against the same headroom (TOCTOU); the
    soft-ceiling runway + the reactive 403 backstop absorb races, never worse
    than status quo.
    """
    assert projected_bytes >= 0, projected_bytes
    floor_gb = probe_floor_gb if probe_floor_gb is not None else _env_float(
        "EPM_HF_LARGE_UPLOAD_PROBE_GB", 100.0
    )
    projected_tb = projected_bytes / _BYTES_PER_TB
    if projected_bytes < floor_gb * 1e9:
        return ProjectedUploadHeadroom("below-threshold", projected_tb, None, None, "not-probed")
    h = check_hf_storage_headroom()
    if h.basis == "disabled":
        return ProjectedUploadHeadroom("disabled", projected_tb, None, h.ceiling_tb, h.basis)
    if h.used_tb is None:
        return ProjectedUploadHeadroom("unknown", projected_tb, None, h.ceiling_tb, h.basis)
    if h.used_tb + projected_tb <= h.ceiling_tb:
        return ProjectedUploadHeadroom("fits", projected_tb, h.used_tb, h.ceiling_tb, h.basis)
    if confirm_live:
        h = check_hf_storage_headroom(force_refresh=True)
        if h.used_tb is None:
            return ProjectedUploadHeadroom("unknown", projected_tb, None, h.ceiling_tb, h.basis)
        if h.used_tb + projected_tb <= h.ceiling_tb:
            return ProjectedUploadHeadroom("fits", projected_tb, h.used_tb, h.ceiling_tb, h.basis)
    return ProjectedUploadHeadroom("insufficient", projected_tb, h.used_tb, h.ceiling_tb, h.basis)
```

`_emit_overflow_routing_event` gains two optional, backward-compatible kwargs (append-only JSONL fields; existing consumers unaffected):

def _emit_overflow_routing_event(
    *, original_repo, effective_repo, path_in_repo,
    reason: str = "quota-403-reactive", projected_gb: float | None = None,
) -> None:
    ...
    event = {..., "reason": reason}

        event["projected_gb"] = projected_gb

At entry, after `shards = sorted(...)`:

```python
route_all_to_overflow = False
if proactive_overflow and repo_id != DEFAULT_OVERFLOW_REPO:
    projected = sum(p.stat().st_size for p in shards)
    ph = check_projected_upload_headroom(projected)          # imported from hub
    if ph.verdict == "insufficient" and _repo_is_private(repo_id, repo_type=repo_type) is False:
        # KNOWN-insufficient + CONFIRMED-public canonical target only.
        # repo_type= MUST be threaded (Must-Fix, critic r1 ×3 lenses + reconciler):
        # _repo_is_private defaults repo_type="model" (hub.py:311) while THIS flow's
        # canonical target defaults repo_type="dataset" (upload_sharded.py:182) — the
        # incident-shape store targets the public DATA repo, and a bare call would
        # 404 -> None -> fail-open -> the proactive route never fires on the primary
        # incident path. (private target = separate quota; privacy None = fail-open,
        # no reroute on uncertainty — the _resolve_lfs_upload_repo semantics, hub.py:368.)
        route_all_to_overflow = True
        logger.warning(
            "[hf-headroom] projected %.1f GB exceeds remaining public headroom "
            "(%.2f/%.1f TB used, %s) — routing ALL %d shards of %s -> %s UP-FRONT "
            "(#1034 proactive; #841 v11 pattern)",
            projected / 1e9, ph.used_tb, ph.ceiling_tb, ph.basis,
            len(shards), repo_id, DEFAULT_OVERFLOW_REPO,
        )
        _ensure_overflow_repo(api)          # the create_repo(private=True, exist_ok=True)
                                            # call extracted from _reroute_to_overflow
        _emit_overflow_routing_event(
            original_repo=repo_id, effective_repo=DEFAULT_OVERFLOW_REPO,
            path_in_repo=prefix, reason="projected-headroom-proactive",
            projected_gb=projected / 1e9,
        )
        _write_overflow_pointer(            # module-local generalized pointer, ONE commit
            api, canonical_repo=repo_id, canonical_repo_type=repo_type,
            path_in_repo=prefix, overflow_repo=DEFAULT_OVERFLOW_REPO,
        )
```

In the loop: when `route_all_to_overflow`, upload each shard straight to `DEFAULT_OVERFLOW_REPO` (repo_type `"model"`, matching the reactive reroute), append each dest to BOTH `result.rerouted` AND `result.uploaded` (parity with the reactive path, upload_sharded.py:261-263 — consumers reading the full dest list must see rerouted shards), and skip the canonical attempt entirely. The reactive 403 branch stays as the backstop for `fits`/`unknown`/`below-threshold` verdicts that hit the wall anyway; after a partial canonical/overflow split, `result.rerouted` still identifies the actual rerouted shard paths (the prefix pointer is deliberately coarse).

**Reactive pointer/event dedup (same seam, same incident class):** today `_reroute_to_overflow` emits one JSONL event + one `OVERFLOW_POINTER.json` Hub commit PER SHARD. The pointer dest is ALREADY prefix-level (`path_in_repo=os.path.dirname(dest)` → `{prefix}/OVERFLOW_POINTER.json`, upload_sharded.py:153-159) — the storm is N duplicate COMMITS of that same file (each payload carries a fresh `ts`, so each is a real Hub commit): a 1000-shard store 403-ing at shard 50 would issue ~950 duplicate pointer commits — straight into the 256 commits/hr Hub limit (upload-policy.md). Add a per-call `emitted_prefixes: set[str]` threaded into `_reroute_to_overflow` (or a small `once: bool` flag) so the event + pointer fire ONCE per `path_in_repo` prefix per `upload_dir_sharded` call. Refactor `_reroute_to_overflow`'s repo-creation into `_ensure_overflow_repo(api)` shared by both branches.

### 3.4 Preflight opt-in hard gate — `orchestrate/preflight.py`

The planned-upload branch is routed THROUGH `check_projected_upload_headroom` (with
`probe_floor_gb=0.0` — the caller EXPLICITLY declared the projection, so the tiny-upload
skip must not disarm the gate), which embeds the `force_refresh=True` live confirm before
any "insufficient" verdict — the abort-shaped preflight FAIL therefore obeys the plan's
own never-act-on-a-stale-cached-over-read rule (Must-Fix, critic r1 statistics Codex #1 /
methodology Codex #2: acting on the raw cached probe could FALSE-BLOCK a healthy run
after quota was freed while the ≤1h cache still reads high):

```python
def check_hf_storage(report: PreflightReport, planned_upload_gb: float | None = None):
    ...existing probe + WARN logic unchanged, EXCEPT the basis=="disabled" early return
       gains one line when the gate was requested (see below)...
    if planned_upload_gb is not None and h.used_tb is not None:
        ph = check_projected_upload_headroom(
            int(planned_upload_gb * 1e9), probe_floor_gb=0.0,   # explicit projection: always probe
        )   # live force_refresh=True confirm built in; cache-hit for the first read
        if ph.verdict == "insufficient":
            if os.environ.get("EPM_HF_OVERFLOW_ROUTING") == "1":
                report.add_warning(
                    f"HF headroom: planned {planned_upload_gb:.0f} GB LFS upload would "
                    f"exceed the soft ceiling ({ph.used_tb:.2f}+{ph.projected_tb:.2f} > "
                    f"{ph.ceiling_tb:.1f} TB, live-confirmed) — EPM_HF_OVERFLOW_ROUTING=1 "
                    f"is armed, uploads will reroute to the private overflow repo "
                    f"(NOTE: arming is environment-wide — it also reroutes every armed "
                    f"upload_model flow in this env)"
                )
            else:
                report.add_error(
                    f"HF headroom insufficient for planned upload (live-confirmed): "
                    f"{planned_upload_gb:.0f} GB projected vs "
                    f"{(ph.ceiling_tb - ph.used_tb) * 1000:.0f} GB remaining "
                    f"({ph.used_tb:.2f}/{ph.ceiling_tb:.1f} TB, {ph.basis}). Remediation: "
                    f"(1) route the store through upload_dir_sharded (proactive overflow, "
                    f"#1034); (2) arm EPM_HF_OVERFLOW_ROUTING=1 for upload_model flows whose "
                    f"arming contract permits (environment-wide effect); (3) free quota / raise "
                    f"EPM_HF_STORAGE_SOFT_CEILING_TB after buying storage. "
                    f"See .claude/rules/upload-policy.md § Proactive detection."
                )
        # ph.verdict in {"fits", "unknown", "disabled"} -> nothing / existing WARNs only
        # (fail-open: a live-unknown or stale-high-then-live-fits never blocks).
```

**Armed-but-blind combo made visible:** the existing `basis == "disabled"` early return
(preflight.py:966-967) would silently swallow a REQUESTED gate — `--planned-upload-gb 2000`
+ `EPM_HF_STORAGE_CHECK=0` passes with zero indication the gate is disarmed. Before that
return, when `planned_upload_gb is not None`, `report.add_warning("HF headroom: planned-upload
gate requested but storage check disabled (EPM_HF_STORAGE_CHECK=0) — gate not evaluated")`
(mirrors the `_OVERFLOW_BLIND_WARNED` precedent, hub.py:331-364).

Semantics documented in the docstring: `planned_upload_gb` means "LFS bytes the run REQUIRES on the canonical PUBLIC repos"; runs whose stores tolerate overflow (v2 `upload_dir_sharded` flows) either omit the flag or arm routing — so the gate cannot false-block them. UNKNOWN headroom stays a warning (fail-open); the existing `except Exception` → warning wrapper is unchanged (a bad ceiling env still degrades to WARN here and stays fail-loud at the trainer persist gate — today's split, preserved).

`preflight_check(...)` gains `planned_upload_gb: float | None = None`, threaded to `check_hf_storage(report, planned_upload_gb)` (line 1052). `main()` gains `--planned-upload-gb` (float, default None), mirroring `--planned-footprint-gb` (line 1092).

## 6. Kill criteria (what would make this approach wrong)

- A production consumer of `upload_dir_sharded` exists (or lands mid-implementation) that verifies CANONICAL paths externally without reading `result.rerouted`/pointers — proactive routing would convert its success into a verification failure (the i528 arming-contract failure mode). Mitigation is designed in (`proactive_overflow=False`); if such consumers turn out to be the norm, flip the default to False and route arming through an env, then re-review.
- HF changes `usedStorage` semantics (e.g. starts including private repos, or switches to binary units) — the `used + projected > ceiling` arithmetic silently mis-fires. The suspect-probe poisoning in `check_hf_storage_headroom` catches absence, not semantic drift; a semantic change invalidates the #564 base check too and is out of this task's scope, but would require re-grounding the ceiling.
- The soft ceiling diverges persistently from the REAL purchased quota (the user bought storage on 2026-07-03) and nobody raises `EPM_HF_STORAGE_SOFT_CEILING_TB` — the proactive route would then send stores to overflow unnecessarily. This is a config-hygiene cost (data stays findable via pointers), not data loss; if it recurs, the right fix is deriving the ceiling from the Hub billing API, a follow-up, not this design.

## 11. Decision Rationale (load-bearing choices)

1. **Reuse `check_hf_storage_headroom` via a wrapper, never a second probe.** *Source:* task brief REUSE constraint + #564 (the probe's partial-None poisoning, suspect guards, and cache semantics took a full task to get right; a re-implementation would fork them).
2. **Probe floor default 100 GB (`EPM_HF_LARGE_UPLOAD_PROBE_GB`), decimal GB.** *Source:* task body ("multi-100GB+"); 100 GB = 1% of the 10 TB default ceiling (`hub.py:78`) — the scale where one upload materially moves account headroom; probe cost ~25 s cache-miss (`hub.py:193-194` measured comment) is negligible against a ≥100 GB transfer; decimal to match `_BYTES_PER_TB = 1000**4` (`hub.py:80`, "HF reports decimal bytes").
3. **Live `force_refresh=True` confirm before any "insufficient" verdict.** *Source:* #564 plan §5 decision table as implemented at `trainer.py:610` ("over ceiling (confirmed by a FORCED LIVE re-probe)") — never abort/reroute on a ≤1h-stale cached over-read.
4. **Proactive routing in `upload_dir_sharded` is unconditional (no arming env), with a `proactive_overflow` opt-out.** *Source:* the flow's OWN existing contract — `upload_dir_sharded` already reroutes on 403 with no arming gate (`upload_sharded.py:242-261`), so consumers already must handle rerouted shards; proactive routing changes WHEN, not WHETHER. The opt-out preserves the upload-policy.md ARMING CONTRACT escape for any future canonical-path-verifying caller. Also prevents the split-store state (half canonical / half overflow) the reactive path produces on a mid-store 403 (#841 incident shape).
5. **`upload_model` size-awareness rides the EXISTING armed gate, contract unchanged.** *Source:* upload-policy.md § Proactive detection ARMING CONTRACT ("launchers that verify CANONICAL paths externally must not arm it") — extending the armed predicate is safe by construction; changing the default-off would be architectural.
6. **Preflight gate is opt-in via a caller-supplied projection.** *Source:* the `planned_footprint_gb` precedent (`preflight.py:725-758`, named by the task brief as "the existing disk-budget pattern: a caller-supplied projected footprint turns a skip into a hard gate"); an unconditional hard gate would false-block overflow-tolerant v2 runs and violate the WARN-only advisory contract (`preflight.py:946` docstring).
7. **Fail-open on unknown headroom, everywhere.** *Source:* the standing #564 convention (`HfStorageHeadroom` docstring `hub.py:87-89`; `_validate_persist_headroom` decision table; `_resolve_lfs_upload_repo` blind-warning arm) + the task brief's explicit constraint; the reactive 403 backstop stays authoritative.
8. **Alert channel = the existing fail-soft JSONL sidecar (`_emit_overflow_routing_event`) + structured `[hf-headroom]` WARNING + the loud preflight FAIL; NO library-side Telegram.** *Source:* `hub.py` runs pod/GCE-side where `~/my-goat/scripts/telegram_push.sh` (the `vm_disk_guard.py:328` path) does not exist, and pod-side code never shells `task.py` (CLAUDE.md § pod-side reporting) — the sink at `hub.py:376-384` is exactly the sentinel the VM-side orchestrator/upload-verifier already observes to post `epm:` markers; `require_preflight` FAIL is loud by construction (stderr + exit 1, `preflight.py:1080`). VM-side pushes remain the poller/watcher's job (existing `[gpu-idle-escalation]` precedent), not the library's.
9. **Pointer/event once-per-prefix dedup in the sharded reactive path.** *Source:* upload-policy.md "HF Hub rate limit: 256 repository commits per hour" + the incident shape (a multi-TB store 403-ing mid-flight would issue one pointer COMMIT per remaining shard); one pointer at the prefix matches `hub._write_overflow_pointer`'s directory-level semantics (`hub.py:437-441`).
10. **`_validate_persist_headroom` untouched.** *Source:* clarifier note ("covers ONLY persist-declared training runs") + measured adapter size ~300 MB (upload-policy.md § Delete-after-eval) — 2.5 orders below the floor; extending it would add I/O for zero verdicts changed.
11. **Env threading into gcp/slurm passthrough allowlists.** *Source:* the #564 knob block comments at `gcp.py:941-945` / `slurm.py:782-786` ("must reach the compute node or a dispatch-process opt-in silently no-ops remotely") — the new knob has identical remote-relevance; cache/event paths stay un-threaded per the same comment. (Symbol names differ: gcp is `STARTUP_PASSTHROUGH_ENV_KEYS`, slurm is `PASSTHROUGH_ENV_KEYS` — edit the right one.)
12. **Preflight planned-gate routed through `check_projected_upload_headroom` (probe_floor_gb=0), not the raw cached probe.** *Source:* critic round 1 (statistics Codex Must-Fix 1 + methodology Codex Must-Fix 2): the abort-shaped preflight FAIL must obey the same live-confirm rule as every other abort-shaped verdict (§11.3, the trainer.py:610 pattern) — acting on the raw ≤1h-stale cache could false-block a healthy run after quota was freed. `probe_floor_gb=0.0` because the caller explicitly declared the projection; the tiny-upload skip must not disarm a requested gate.
13. **repo_type threading in the §3.2 privacy probe.** *Source:* critic round 1, independently by all three Claude lenses + upheld by the reconciler against a Codex APPROVE: `_repo_is_private` defaults `repo_type="model"` (hub.py:311) while `upload_dir_sharded` defaults `repo_type="dataset"` (upload_sharded.py:182); a bare call 404s → None → fail-open → the proactive route never fires on the dataset-repo incident path.
