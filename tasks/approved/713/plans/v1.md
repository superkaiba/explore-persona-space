### Step F — idempotency / dedup mechanism

**Mechanism: a filesystem event-stream + content-hash dedup, living at
`.claude/cache/nightly-consolidation-events.jsonl`** (new file; follows the
exact pattern of the existing `.claude/cache/disk-guard-events.jsonl` and
`.claude/cache/workflow-fix-events.jsonl` durable JSONL traces — confirmed both
exist). Each nightly proposal appends one row:
`{"date": "YYYY-MM-DD", "kind": "living-docs-drift|living-docs-reproposal|followup-revival", "hash": "<12-hex>", "task_id": <int|null>, "summary": "<one line>"}`.

Dedup rules, in priority order:

1. **Drift re-synthesis** — compute `drift_hash = sha256(normalize(check
   output))[:12]`. A drift proposal is a duplicate (do NOT re-propose) iff
   EITHER (a) the event-stream already has a `living-docs-drift` row with the
   same `hash` whose corresponding proposal is still open, OR (b) an open
   dashboard signal for the same drift exists — scan `open_questions.md`'s
   `<!-- living-docs-changelog -->` block (confirmed present at the top of the
   doc) for a changelog line whose date ≥ the event-stream row's date (meaning
   the drift was already reconciled by an applied re-synthesis → the hash
   should also have changed, so a re-run of `check` exits 0 and there is
   nothing to propose). The changelog cross-check is the "already-applied"
   escape; the event-stream is the "already-proposed-not-yet-applied" escape.
2. **Parked living-docs rejection re-proposal** — keyed on
   `(task_id, content_hash_of_preserved_proposal)`. Duplicate iff the
   event-stream already has a `living-docs-reproposal` row for the same
   `(task_id, hash)` AND the task still shows no `epm:living-docs-updated`.
3. **Parked-redundant follow-up revival** — keyed on `task_id`. Duplicate iff
   the event-stream already has a `followup-revival` row for that `task_id` AND
   the task is still `on_hold` (i.e. not yet revived).

The event-stream is the canonical dedup state for BOTH `/daily` and a manual
`/weekly` run (Step C.3) — they share it, so a manual weekly run after a
nightly run will not double-propose. `.claude/cache/` is gitignored/local (the
existing event-streams are local), so the dedup state is per-VM, which matches
the nightly-cron's single-host execution model.

**Deterministic-hash precondition (verify before relying on `drift_hash`).**
The two-layer dedup keys on `drift_hash = sha256(normalize(check output))[:12]`,
which only dedups correctly if `living_docs.py check`'s output is DETERMINISTIC
across runs on unchanged inputs — if `check` interleaves a timestamp, a
wall-clock duration, or a nondeterministically-ordered finding list, the hash
changes every night, dedup silently FAILS OPEN, and the drift is re-proposed
nightly (Risk (a) realized). The implementer MUST confirm `check`'s output is
stable across two back-to-back invocations on the same repo state
(`diff <(uv run python scripts/living_docs.py check 2>&1) <(uv run python
scripts/living_docs.py check 2>&1)` → empty). If it is NOT stable, `normalize()`
must strip the nondeterministic tokens (timestamp-shaped strings, elapsed-time
tokens) and sort the finding lines before hashing, so the hash is stable for a
given drift state. This is a precondition for the dedup smoke (§6 #4) to mean
anything — a non-stable hash would make `L_after == L_before` impossible to
achieve on the dedup path.

## 6. Evaluation (acceptance smoke for an infra task)

The body's Acceptance bullets are the test set. The acceptance smoke
demonstrates each:

1. **Drift + parked-proposal checks run nightly:** invoke `/daily` manually
   on the current repo state and confirm the written `logs/daily/<date>.md`
   contains a `## Living-docs drift` section populated from
   `living_docs.py check`, and that any parked living-docs rejection / parked
   redundant follow-up still open is surfaced (under `## Living-docs drift` /
   `## Other problems & notes`). (Because manual `/daily` runs write the full
   file + apply, per daily SKILL.md:65-69.)

2. **`logs/weekly/` no longer needs a nightly producer:** confirm no cron fires
   `/weekly` (`crontab -l | grep weekly` shows only the DISABLED nudge line) and
   the weekly SKILL.md banner states nothing depends on it.

3. **`/weekly` carries the manual-only banner:** `grep -n "Manual deep-dive only"
   .claude/skills/weekly/SKILL.md` returns the banner.

4. **The dedup branch suppresses an already-open proposal:** the dedup logic
   must be exercised on a path that actually reaches it. A naive "run `/daily`
   twice on the same date" smoke is VACUOUS — `/daily`'s same-date
   overwrite-refusal (daily SKILL.md:57-64: a second run on an existing daily
   file with a non-empty `## Applied workflow improvements` section refuses to
   overwrite and tells the user "the day is already done") means run 2 skips
   the entire problem-sweep + new passes, so `L2 == L1` holds because the pass
   never ran (no append because skipped, not because dedup fired) and there is
   no second proposal line because the file was never rewritten. Both
   assertions would pass while the dedup logic is never touched. Use one of
   these instead:

   **(a) [PRIMARY — recommended] Pre-seed the event-stream, single `/daily`
   today.** This exercises the CROSS-DAY dedup invariant the Goal actually
   needs (a drift proposal logged on an earlier night must not be re-proposed
   tonight). On a stub working copy with one synthetic drift finding (so
   `living_docs.py check` exits nonzero with a stable finding):
   - Pre-seed `.claude/cache/nightly-consolidation-events.jsonl` with one
     `living-docs-drift` row dated YESTERDAY whose `drift_hash` matches the
     hash the stub's drift produces (compute it the same way the pass does:
     `sha256(normalize(check output))[:12]`).
   - `L_before=$(wc -l < .claude/cache/nightly-consolidation-events.jsonl)`
     (= 1, the seeded row).
   - Run `/daily` ONCE today (only one `/daily` invocation today → no
     overwrite-refusal collides).
   - **Assert (dedup control):** today's daily file's `## Living-docs drift`
     section lists the drift findings as bullets AND carries the
     "_drift proposal already open (logged {YESTERDAY}); not re-proposing_"
     note (no new PROPOSAL line), AND
     `L_after=$(wc -l < …events.jsonl)` equals `L_before` (zero rows appended
     because the open seeded proposal suppressed it).

   **(b) [alternative for the implementer] Two same-date runs, delete the
   run-1 daily file between them.** This works around the overwrite-refusal by
   removing the file run 1 wrote, so run 2 actually re-executes the pass and
   hits the event-stream dedup (the seeded run-1 rows are still present):
   - Run 1 on the stub: `L1=$(wc -l < …events.jsonl)` (after run 1).
   - `rm logs/daily/<today>.md` (delete the run-1 daily file so run 2 does not
     hit the overwrite-refusal).
   - Run 2 same date + same stub state: `L2=$(wc -l < …events.jsonl)`.
   - **Assert:** `L2 == L1` (run 2 appended nothing because the run-1 rows
     dedup it) AND the run-2 daily file's `## Living-docs drift` section
     carries the "_drift proposal already open_" note (no second PROPOSAL
     line).

   **Positive control (MF-2 — REQUIRED in EITHER option):** `L1 == L2`
   (or `L_after == L_before`) is only meaningful if the pass DID append on the
   un-deduped path. So pair the dedup control with a positive control: on a
   FRESH stub where the event-stream is EMPTY of a matching row (option (a):
   no seeded yesterday row; option (b): the natural run-1), capture
   `L0=$(wc -l < .claude/cache/nightly-consolidation-events.jsonl)` BEFORE the
   un-deduped run and assert that run GREW the stream
   (`L1 > L0`, i.e. the 1 drift row + any parked-proposal rows were appended).
   The two controls together — `L1 > L0` (append fires when nothing is open)
   AND `L_after == L_before` / `L2 == L1` (append is suppressed when a matching
   open proposal exists) — prove the dedup branch is real, not vacuous.

5. **User-gated invariant intact:** assert no `living_docs.py apply` is invoked
   by the nightly passes (grep the daily SKILL.md added prose for "apply" — it
   must only ever call `living_docs.py check`; the only `apply` reference stays
   in the `/issue` gate path).
