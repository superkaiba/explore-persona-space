## 4. Design

### 4.1 Ref-resolution precedence ladder (decision, brief item 1)

The new flag is **`--repo-branch <branch>`** — deliberately the same spelling as the `--repo-branch` flag of `scripts/dispatch_issue.py`'s launch subcommand, so the Step 6a.5 stanza composes the gate call and the launch from ONE shell variable (the exact discipline the stanza already mandates for `--extra-sync-path`). `--ref` and `--repo-branch` are argparse-mutually-exclusive (both given ⇒ argparse exit 2).

Ordered ladder (first match wins):

1. **`--ref <R>` (explicit override, existing flag)** — used verbatim, no fetch, no existence probe (byte-identical to today's `--ref` path). Source label `ref-flag`.
2. **`--repo-branch <b>` (new)** — bounded fetch of `<b>` + `main` (same fail-open `contextlib.suppress(TimeoutExpired)` semantics as today, honoring `--no-fetch`); check ref is `origin/<b>`. If `origin/<b>` does not verify after the fetch: raise `CheckRefResolutionError` → `main()` prints `ERROR: ...` naming the ref + remediation (push the branch; check the spelling; the dispatch's own ls-remote guard would also refuse) and returns **2**. Never a silent fallback. Source label `repo-branch-flag`. `--repo-branch main` is legal and resolves `origin/main` (mirrors the dispatch escape).
3. **Invoking-cwd worktree-branch inference (new)** — read the checked-out branch of the INVOKING cwd (`git branch --show-current`, run in `Path.cwd()`, mirroring `dispatch_issue._git_branch_of`; empty output = detached = no inference; any subprocess failure = no inference). The inferred branch `w` is accepted ONLY when it is issue-scoped: `w == f"issue-{issue}"` or `w.startswith(f"issue-{issue}-")` (digit-boundary safe: `issue-771-x` does not match issue 77). Accepted ⇒ fetch `w` + `main`, check ref `origin/<w>`; `origin/<w>` absent after fetch (unpushed work branch — the lane would materialize nothing) ⇒ `CheckRefResolutionError` → exit 2 with push-the-branch remediation. Not accepted (cwd on `main`, detached, a foreign issue's branch) ⇒ fall to rung 4. Source label `worktree-branch`.
4. **Legacy default + ambiguity refusal (changed)** — bounded fetch of `issue-<N>` + `main` (as today) PLUS one glob prune-fetch `git fetch --prune origin --quiet --no-tags "+refs/heads/issue-<N>-*:refs/remotes/origin/issue-<N>-*"` (prune scoped to that refspec, so branches deleted on origin cannot poison the check; a glob matching nothing succeeds). Then enumerate suffixed candidates locally: `git for-each-ref "refs/remotes/origin/issue-<N>-*" --format=%(refname:short)`. Under `--no-fetch` the enumeration runs against existing local remote-tracking refs (hermetic for tests/sweeps).
   - Suffixed candidate set NON-empty (with or without the bare ref) ⇒ `CheckRefResolutionError` listing ALL candidates (bare included when present, sorted) + the three remediations (`--repo-branch <b>` threaded from the launch variable; run from the issue worktree; explicit `--ref`) → exit 2. This is the #1336 shape — including the single-suffixed-no-bare case, which is refused rather than auto-picked: a unique candidate is still a guess (a stale suffixed branch from an abandoned round can coexist with a deliberate `--repo-branch main` dispatch), and the refusal message makes the fix copy-paste.
   - Bare `origin/issue-<N>` only ⇒ return it (source `bare-issue-branch-default`) — today's behavior, the fleet-common case.
   - Neither ⇒ `origin/main` (source `origin-main-default`) — today's behavior.

### 4.2 The two cwd regimes (decision, brief item 2)

- **Regime A — repo root (pinned to `main`; the normal orchestrator cwd):** rung 3 reads branch `main` → not issue-scoped → no inference. Without `--repo-branch`, resolution is rung 4: bare-only and none behave exactly as today; any suffixed candidate ⇒ REFUSE. With `--repo-branch` (the updated Step 6a.5 stanza threads it always), rung 2 resolves deterministically. So from the repo root the gate never resolves silently against an ambiguous ref — exactly the clarifier's note 1.
- **Regime B — issue worktree:** rung 3 accepts the worktree branch when it belongs to THIS issue (bare or suffixed) and resolves `origin/<branch>`, refusing only when that branch is unpushed. A worktree on a FOREIGN issue's branch (gating issue N from issue M's tree) is ignored by the issue-scope guard and falls to rung 4 — a silent wrong-tree resolve from a foreign cwd is structurally impossible.

### 4.3 Blast radius — combination matrix (decision, brief item 3)

Rows are remote ref states for issue N; columns are invocation shapes. REFUSE = exit 2 with candidates + remediation on stderr (never a clean check; never exit 0).

| Remote refs for issue N | bare `--issue N` from repo root (rung 4) | `--repo-branch b` | cwd = this issue's worktree on branch w (rung 3) | explicit `--ref R` |
|---|---|---|---|---|
| bare `origin/issue-N` only | `origin/issue-N` (UNCHANGED) | `origin/b` if exists, else REFUSE (NEW rung) | `origin/w` if pushed, else REFUSE (NEW rung) | R verbatim (UNCHANGED) |
| no issue-shaped refs | `origin/main` (UNCHANGED) | same as above | same as above | R verbatim (UNCHANGED) |
| suffixed `origin/issue-N-*` only | REFUSE (NEW — today: silently `origin/main`, wrong tree) | `origin/b` / REFUSE | `origin/w` / REFUSE | R verbatim |
| bare + suffixed (the #1336 incident) | REFUSE (NEW — today: silently `origin/issue-N`, wrong tree) | `origin/b` / REFUSE | `origin/w` / REFUSE | R verbatim |

New behavior appears ONLY where today's behavior is a wrong-tree guess (suffixed rows) or where a new flag/inference is explicitly engaged. The fleet-common case (bare branch, canonical stanza call) is unchanged even before the call-site edit lands; after the call-site edit it becomes rung 2 (deterministic, same resolved ref). The refusal cannot become a fleet-wide gate failure: a suffixed branch only exists where someone deliberately created one, and there the current behavior is already wrong.

   - `args.ref` given ⇒ `check_ref, ref_source = args.ref, "ref-flag"` (no resolver call — today's shape).
   - else `try: check_ref, ref_source = resolve_check_ref(repo_root, args.issue, fetch=not args.no_fetch, repo_branch=args.repo_branch)` / `except CheckRefResolutionError as exc: print(f"ERROR: {exc}", file=sys.stderr); return 2`.
3. **Verdict-line change (decision, brief item 5).** Non-JSON per-finding line becomes `[{VERDICT}] {path} ref={check_ref} reason={reason} — {detail}` (line 1049) — the resolved ref at EVERY severity (PASS/WARN/FAIL/SKIP), so any log excerpt names the graded tree. 4. **`classify()` local-branch threading (scoped correctness fix).** Line 530's `local_branch = f"issue-{issue}"` becomes: `check_ref.removeprefix("origin/")` when `check_ref.startswith("origin/") and check_ref != "origin/main"`, else `f"issue-{issue}"` (unchanged for the `origin/main` fallback and exotic `--ref` values). ## 11. Decision Rationale

- **Flag spelling `--repo-branch`.** What: mirror the `--repo-branch` flag of `scripts/dispatch_issue.py`'s launch subcommand exactly. Why: the stanza composes gate + launch from one variable (drift-proof, the #1835 `--extra-sync-path` precedent at 10-step-6.md:163-166). Source: `scripts/dispatch_issue.py:1186-1230` (`_repo_branch_default_main_conflict`) + CLAUDE.md § Launch-CLI drift guards (#2161). Alternatives: `--branch` (rejected: new vocabulary for the same contract), reusing `--ref` with a branch value (rejected: `--ref` is a raw-ref override with no existence guard; conflating them weakens the fail-loud contract).
- **Refuse-on-suffixed (incl. single-suffixed-no-bare).** What: rung 4 refuses whenever any `origin/issue-<N>-*` exists. Why: any guess reproduces the Goal's named defect; a unique suffixed candidate can be a stale abandoned round while the dispatch targets `main`. Source: task #2263 body item 2 ("An unresolvable ref must never read as a clean check") + incident #1336 (`epm:progress` v277-v278, 4-fail/0-fail split). Alternative (auto-pick unique suffixed): rejected — trades one guess for another; the refusal message makes the correct fix one paste.
- **Exit 2 for refusals (not 1).** What: resolution refusal shares the usage/config-error exit class with unreadable plans and invalid `--extra-sync-path`. Why: it is not a citation verdict; the stanza's exit-1 branch prescribes in-step remediation of CITATION failures, while exit 2 is its fail-loud-never-skip branch. Source: `scripts/verify_carryover_inputs.py:996/1011` (existing exit-2 sites) + 10-step-6.md:140-141. Alternative (exit 1): rejected — would route refusals into the push-and-rerun remediation loop, which cannot fix an ambiguity.
- **Worktree inference from INVOKING cwd, issue-scoped.** What: `git branch --show-current` in `Path.cwd()`, accepted only for `issue-<N>`/`issue-<N>-*`. Why: `--repo-root` always resolves to the MAIN checkout (parent of `--git-common-dir`, :906-915), whose branch is pinned `main` — the worktree signal lives only in the cwd; the issue-scope guard prevents cross-issue contamination. Source: `scripts/verify_carryover_inputs.py:906-915` (grep-verified `906:def _default_repo_root...`) + `dispatch_issue.py:295-315` (`_git_branch_of` — the same probe shape, None on detached/error). Alternative (probe `.claude/worktrees/issue-<N>*` branches from repo root): rejected — multiple worktrees can match and the gate would be back to guessing; the flag covers the repo-root regime.
- **`classify` local-branch derivation from `check_ref`.** What: §4.4.4. Why: with a suffixed check ref, the `committed-unpushed` rung otherwise probes the WRONG local branch and mis-remediates; identity on the bare case keeps blast radius zero. Source: `scripts/verify_carryover_inputs.py:530,544-554` (read this session). Alternative (new `local_branch` parameter threaded from main): rejected — wider signature churn for the same effect.
- **Glob prune-fetch for candidate enumeration.** What: one extra fetch refspec + local `for-each-ref`. Why: keeps one enumeration mechanism for fetch and `--no-fetch` modes (tests stay hermetic against the file remote); `--prune` scoped to the refspec prevents deleted-branch false refusals. Source: git-fetch documented refspec/prune semantics, verified end-to-end by §6.2 test 8 on the VM's git 2.34.1 (marked as an assumption in §12). Alternative (`git ls-remote --heads`): viable fallback (named in §8) but adds a second network call and a second enumeration path.
