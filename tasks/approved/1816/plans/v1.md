# Plan v1 — #1816 daily-fix: deferred-commit ERROR names the failing pre-commit hook

architectural: false

## Goal / requirement

Make the deferred-commit ERROR (and its forensic sidecar row) name the failing
pre-commit hook + a bounded excerpt of that hook's output, instead of only the
blind 500-char `stderr_tail` — which on 2026-07-28 showed only later hooks'
Skipped/Passed lines while the actual failing hook's output had scrolled out
(2 firings; #1092/#1482 marker streams held hostage; diagnosis needed a manual
re-run).

## Prior work / method delta

- **#1780** (merged `8a8acd7ba1`) already assembles `full_err` from the FULL
  captured streams (`e.output` + `e.stderr`) inside
  `_commit_after_durable_append` and extracts gitleaks `Fingerprint:` lines
  ONLY. Every other failing hook still surfaces the blind tail.
- **Delta:** generalize from fingerprint-shape keying to pre-commit
  hook-RESULT-line keying (`<name>....Failed`) over the SAME `full_err`,
  with the existing tail as the unchanged fallback when no hook-result
  failure line exists (lock collisions, plain git errors).

## Design (concrete)

Target: `src/explore_persona_space/task_workflow.py`,
`_commit_after_durable_append` (deferral branch, ~L6798-6855), immediately
after the existing `gitleaks_fps` extraction.

1. **Extraction** over `full_err.splitlines()`:
   - Hook-result line: `re.match(r"^(?P<name>.{1,120}?)\.{3,}(?P<status>Passed|Skipped|Failed)\s*$", ln)`.
   - For each `Failed` result line, capture a BLOCK: the result line plus
     subsequent lines up to (not including) the next hook-result line or EOF,
     capped per block (≤ 12 lines AND ≤ 600 chars), max 3 blocks, total
     excerpt cap ≤ 1500 chars (well under the 50k note cap; keeps ERROR lines
     readable).
   - `failing_hooks`: the `- hook id: <id>` value inside each block when
     present, else the dot-stripped `name` from the result line.
2. **Surfacing (additive, #1780 pattern):**
   - ERROR log: append a `hook_note` segment after the existing
     `gitleaks_note`: `" FAILING HOOK(S): <ids> — <excerpt>"`, only when ≥1
     Failed block was extracted. Existing message text byte-identical
     otherwise.
   - Sidecar row: additive-conditional fields `failing_hooks: [<ids>]` +
     `failure_excerpt: <str>` — present ONLY when extraction hit (mirrors
     `gitleaks_finding`/`gitleaks_fingerprints`; the plain-deferral schema-pin
     test `test_deferred_commit_sidecar_schema` stays byte-identical and
     unmodified).
   - `stderr_tail` field itself is unchanged everywhere (back-compat for
     existing consumers/tests).
3. **Gitleaks interplay:** a gitleaks failure also matches the general
   extraction — both notes/fields coexist (the recipe note keeps its
   `.gitleaksignore` guidance). No suppression logic.

## Acceptance criteria

- AC1: a deferral whose captured streams contain ≥1 pre-commit `Failed`
  hook-result line surfaces the failing hook id/name + bounded output excerpt
  in BOTH the ERROR log and the sidecar row, even when the failure sits
  outside the 500-char tail (pinned by the new test).
- AC2: a deferral with NO Failed hook-result line keeps ERROR message + row
  byte-identical to today (tail fallback; existing schema-pin test passes
  unmodified).
- AC3: the #1780 gitleaks leg keeps firing unchanged (recipe note +
  fingerprint fields); its row additionally carries the general fields.
- AC4: ruff clean on touched files; the Step 9c mapped/touched test gate
  green.

## Kill criteria

If pre-commit's result-line shape proves unmatchable without false positives
on plain git stderr (not expected — the dots+status shape is distinctive and
the gitleaks test already relies on it), fall back to surfacing the LAST
`Failed`-line index window only, still additive-conditional. No scenario
justifies touching the plain-deferral byte-identical contract.
