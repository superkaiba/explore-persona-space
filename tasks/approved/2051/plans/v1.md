This is the exact shape to reuse for `ISSUE`. Both `_bootstrap` call sites are in `_provision_wait_register_bootstrap` at L1932 + L1948.
- **Upstream git — why the pairing is needed** — `git-clone(1)`'s `--filter=<spec>` explains that partial clone tells git to omit large blobs but the resulting repo will lazy-fetch them on demand from a promisor remote. Combined with `--depth=1`, `--filter=blob:none` omits blobs from the initial pack. HOWEVER, materializing the working tree at HEAD requires the blob for every file at HEAD, so git immediately lazy-fetches all of them — net effect on a full checkout is the same total transfer in two round-trips. `git-sparse-checkout(1)` explains that cone-mode `sparse-checkout set <dirs>` restricts the working tree to a subset of directories; combined with `blob:none`, the working tree only asks for blobs of files IN the cone, and out-of-cone blobs stay omitted until `sparse-checkout add <path>` lazily fetches them. Confirmed against the current git-scm docs; the body's "Why neither piece works alone" analysis is accurate.

## 4. Design

### 4.1 `scripts/bootstrap_pod.sh` — fresh-init branch (currently L246-273)

Replace the current fresh-init block with the pairing. Preserve the `git init -b "$BRANCH"` + `git remote add origin '<tokenless URL>'` + `git config … credential.helper` lines byte-untouched (the #1239 contract), then insert partial-clone + cone-init between the credential-helper config and the `git fetch`:

```bash
git init -q -b "$BRANCH"
git remote add origin '$REPO_URL_TOKENLESS' 2>/dev/null \
    || git remote set-url origin '$REPO_URL_TOKENLESS'
git config --replace-all credential.https://github.com.helper '$GIT_CRED_HELPER'
# Partial clone (promisor remote for lazy on-demand blob fetch).
git config remote.origin.promisor true
git config remote.origin.partialclonefilter blob:none
# Cone-mode sparse-checkout — init FIRST (`set --cone` was silently
# accepted as a literal pattern on git 2.34; `init --cone` is safe on all
# versions).
git sparse-checkout init --cone
# Code dirs plus this issue's own eval_results dir. Cross-issue reads at
# a downstream step are recovered by `git sparse-checkout add <path>`,
# which lazily fetches only that subset (seconds under blob:none).
# ISSUE is passed by pod_lifecycle._bootstrap; empty → cone falls back to
# code-only (hand-run debug case, no crash).
if [ -n "${ISSUE:-}" ]; then
    git sparse-checkout set scripts src configs tests "eval_results/issue_${ISSUE}"
else
    git sparse-checkout set scripts src configs tests
fi
# --filter=blob:none rides the fetch too so the initial pack omits history
# blobs the working-tree materialization won't need.
git fetch -q --depth=1 --filter=blob:none origin "$BRANCH"
git reset -q --hard FETCH_HEAD
```

The exact indentation + surrounding heredoc quoting matches the existing L246-273 pattern; single-file diff.

### 4.2 `scripts/bootstrap_pod.sh` — existing-repo branch (currently L221-244)

Add a sparse/detached-clone detection guard BEFORE the existing `pull --ff-only`. If either check trips, take the fetch+reset-to-pin path (same as fresh-init) instead of `pull`:

```bash
if [ -d $REMOTE_DIR/.git ]; then
    cd $REMOTE_DIR
    # Preserve the #1239 credential-helper retrofit unchanged.
    git remote set-url origin '$REPO_URL_TOKENLESS' 2>/dev/null \
        || git remote add origin '$REPO_URL_TOKENLESS'
    git config --replace-all credential.https://github.com.helper '$GIT_CRED_HELPER'
    git stash -q 2>/dev/null || true

    # Detect a sparse and/or shallow checkout: pull --ff-only is unsafe
    # against either, and once this fix lands both are the default.
    IS_SHALLOW=$(git rev-parse --is-shallow-repository 2>/dev/null || echo false)
    IS_SPARSE=$(git config --get core.sparseCheckout 2>/dev/null || echo false)

    if [ "$IS_SHALLOW" = "true" ] || [ "$IS_SPARSE" = "true" ]; then
        # Fetch + reset-to-pin path (same as fresh-init existing-repo). Preserves
        # partial-clone + cone-mode config across re-bootstraps (the .git config
        # entries survive).
        git fetch -q --depth=1 --filter=blob:none origin "$BRANCH"
        git reset -q --hard FETCH_HEAD
    else
        # Legacy full-clone path — unchanged. Handles pre-fix clones that
        # persist across the fix landing.
        git checkout "$BRANCH" 2>/dev/null || true
        if ! git pull -q --ff-only origin "$BRANCH" 2>/dev/null; then
            echo "Fast-forward failed, attempting rebase onto origin/$BRANCH..."
            if ! git pull -q --rebase=merges origin "$BRANCH"; then
                echo "ERROR: rebase against origin/$BRANCH conflicted; aborting half-applied rebase." >&2
                git rebase --abort 2>/dev/null || true
                echo "Diagnose the conflict on the pod (\`cd $REMOTE_DIR && git status\`) or wipe \`$REMOTE_DIR\` and re-provision." >&2
                exit 1
            fi
        fi
    fi
    echo "On branch: $(git rev-parse --abbrev-ref HEAD)"
    echo "At commit: $(git log --oneline -1)"
else
    # (fresh-init block per §4.1)
```

Both branches now converge on the same working-tree shape at end-of-step-4: `HEAD == origin/$BRANCH`, sparse+partial config live, cone materialized.

### 4.3 `scripts/bootstrap_pod.sh` — self-re-entry protection

Wrap the entire `Step 4: Setting up git repository` block (currently L220-278) in `flock -n` on a lockfile inside `$REMOTE_DIR`:

```bash
step 4 "Setting up git repository (branch=$BOOTSTRAP_BRANCH)"
mkdir -p "$REMOTE_DIR"
if ssh_cmd "
set -eu
BRANCH=\"$BOOTSTRAP_BRANCH\"
mkdir -p $REMOTE_DIR
exec 9>>$REMOTE_DIR/.bootstrap.lock
if ! flock -n 9; then
    echo 'ERROR: another bootstrap is running (or crashed with a held lock) at $REMOTE_DIR/.bootstrap.lock; wait for it to finish or `rm` the lock and re-run.' >&2
    exit 1
fi
# ... existing Step 4 body ...
"; then
    log_ok "Repository ready"
else
    log_fail "Step 4 (git clone/pull) failed — see error above"
    exit 1
fi
```

`flock` opens fd 9 on the lockfile in the SSH sub-shell; `flock -n 9` acquires it non-blocking. On process death, the kernel releases the lock automatically (unlike a sentinel file). The lockfile lives inside `$REMOTE_DIR` which is created just before the `exec 9>>` — safe on both first and repeat runs. A `flock` in-hand at ssh_cmd exit exits the sub-shell cleanly.

## 6. Evaluation

Three-legged acceptance test — all three MUST pass. The regression test in leg 3 is the sparse/detached re-bootstrap path constraint; without it we could ship a fresh-init fix that breaks every resumed pod.

### Leg 1: transfer is measurably smaller (bytes fetched, or wall-time to first usable commit)

- **Measurement:** on a fresh RunPod pod, run `bootstrap_pod.sh` under the pre-fix code. Record the total bytes transferred by `git fetch` (`GIT_TRACE=1 GIT_TRACE_PACK_ACCESS=1 GIT_TRACE_PERFORMANCE=1` on the fetch line, filtered to pack-received-bytes and pack-index-bytes). Repeat on a fresh pod with the fix (same base image, same network path). Assert `bytes_fixed < bytes_pre_fix / 10` — a 10× shrink is a conservative floor; the projected shrink is ~70× (10.51 GB → ~150 MB code + own-issue artifacts).
- **Threshold:** 10× shrink minimum. Failing the floor is a defect.

### Leg 2: lazy-blob path works — open a committed artifact end-to-end

- **Measurement:** on a fresh-bootstrap pod (ISSUE set to a recent completed issue whose `eval_results/issue_<M>/` dir is committed on `main`), assert that opening ONE JSON file inside that dir returns non-empty content. This proves the cone materialized the artifact AND that a lazy-blob fetch through the promisor remote works (the artifact's blob is not in the initial pack — the pack was `blob:none`). Pick a small file: `eval_results/issue_<M>/summary.json` or the largest already-committed `all_arms_spearman.json`-shape file — whatever exists on main-tip at the time of the smoke.
- **The exact file path:** pick from `git ls-tree -r main -- eval_results/ | grep -E '\.(json|md)$' | head -5` at implementation time. Assert `python -c "import json,sys; d=json.load(open('<path>')); assert d, '<path> loaded but empty'"` returns rc=0.
- **Sparse-add spot-check:** immediately after leg-2 succeeds, run `git sparse-checkout add "eval_results/issue_<OTHER_M>"` (a DIFFERENT recent issue's dir), then open a file inside it and assert non-empty. This verifies the lazy-blob path for arbitrary cross-issue reads (the escape hatch the body promises is seconds-of-recovery for a cone miss).

### Leg 3: sparse/detached re-bootstrap reaches preflight

- **Measurement:** on the same pod that just completed leg 1's post-fix bootstrap, `stop` the pod and `resume` it (RunPod resumes preserve `/workspace`). Re-run `pod.py bootstrap <name>` (i.e. run `bootstrap_pod.sh` from step 1). Assert that the existing-repo branch takes the `IS_SHALLOW=true` / `IS_SPARSE=true` path (add a trace line so it's grep-able), and assert bootstrap exits rc=0 AT preflight (step 11) — not rc=1 mid-`pull`. This is the "detected a detached HEAD and/or an active sparse-checkout and took a fetch+reset-to-pin path" constraint from the body.
- **Threshold:** rc=0 on the re-bootstrap AND the trace confirms the guarded branch fired.

### Leg 4 (optional, if time permits): self-re-entry safety

- **Measurement:** start `bootstrap_pod.sh` in a background ssh session, wait until the `flock` is held (grep for the `.bootstrap.lock` file), start a SECOND `bootstrap_pod.sh` invocation. Assert the second one exits rc=1 with the "another bootstrap is running" message.
- **Threshold:** the second invocation refuses to compete.

**Do NOT weaken the acceptance test.** A clone that completes is not sufficient. All three legs land in the PR body; leg 4 is best-effort.

## 8. Risks and Failure Modes

| Risk | Likelihood | Mitigation |
|---|---|---|
| A downstream step opens an out-of-cone committed artifact — cone miss | Medium | Recovery is `git sparse-checkout add <path>` (seconds). Leg-2's sparse-add spot-check verifies the recovery mechanism works. The default cone includes the run's own issue dir, so the most common cross-cone read (own eval_results) is covered. Cross-issue reads (uncommon in production workloads) need one `sparse-checkout add` — the body's second failure-mode section notes this is a seconds-long recovery. |
| `flock` unavailable on some pod image | Low | `util-linux` `flock` is present on every RunPod image tested (base `runpod/pytorch:2.4.0-py3.11-cuda12.4.1-devel-ubuntu22.04`). Fallback if the `flock -n` call itself errors non-zero (not lock-not-acquired, actual command missing): script exits with the "another bootstrap is running" branch and the operator investigates. |
| `--filter=blob:none` requires promisor-remote support on the server side | Low | GitHub has supported partial clone since 2020 and it is the default recommendation for large-repo clones in git-scm docs. Confirmed against the current `git-clone(1)` upstream. |
| `git rev-parse --is-shallow-repository` returns empty rather than `false` on some git versions | Low | Guarded by `|| echo false` in §4.2. The `[ "$IS_SHALLOW" = "true" ]` test then correctly reads false. |
| The `.bootstrap.lock` file persists after a crashed bootstrap | Low | Kernel releases the flock on process death regardless of the lockfile persisting on disk; the lockfile itself is a rendezvous, not a semaphore. Only a stale process still holding the fd would block — that's the failure mode `flock -n` is designed to surface loudly. |
| Users running `bootstrap_pod.sh` manually (`pod.py bootstrap <name>`) without an issue arg | Low | `ISSUE` unset → the shell conditional falls back to code-only cone (§4.1). Hand-run bootstrap works, cross-issue reads recover via `sparse-checkout add`. |

## 11. Decision Rationale

**Cone default = Shape A (`scripts src configs tests eval_results/issue_${ISSUE}`).**

- **What:** the fresh-init cone contents; every workload's own-issue reads land inside the cone by default.
- **Why:** matches the body's diff-sketch default and makes the acceptance-test leg-2 (open a committed artifact end-to-end) work without a preceding `sparse-checkout add`. `eval_results/issue_<N>` on a recent issue is typically well under 1 GB, so the transfer stays small.
- **Source:** body diff sketch; precedent `scripts/new_worktree.sh` L297-349 which uses the same shape VM-side.
- **Alternatives (documented for caveats):** Shape B — code-only cone + rsync data files VM→pod separately. The body's second failure-mode section observed Shape B was the working recipe on the pathologically-slow 0.15 MB/s pod (a cone including `eval_results/issue_<N>` was STILL lazily pulling blobs at 0.13 MB/s there). Recorded in Caveats as the operator-selectable fallback for pathologically-slow links; recovery from either default to the other is `sparse-checkout set` (seconds). Not the DEFAULT because it adds VM→pod plumbing to every provision even when the link isn't pathologically slow.

**Self-re-entry guard = `flock -n "$REMOTE_DIR/.bootstrap.lock"`.**

- **What:** wrap the whole Step-4 body in a non-blocking flock on a lockfile inside `$REMOTE_DIR`.
- **Why:** kernel-managed, released automatically on process death (unlike a sentinel file which strands on a killed launcher). `-n` (non-blocking) ensures a second invocation refuses to compete rather than serializing behind an already-running one (competing-launchers-serialized would waste time even when the first one succeeds cleanly).
- **Source:** `flock(1)` from `util-linux`; standard on every Linux pod image.
- **Alternatives:** (a) sentinel file at `$REMOTE_DIR/.bootstrap_in_progress` with mtime staleness check — racy on fresh-start-vs-stale-lockfile boundary, requires manual cleanup on crash. (b) `mkdir` as mutex — same crash-strand problem. (c) An `IS_BOOTSTRAPPING=1` env var flag — doesn't survive cross-invocation, not a valid re-entry guard.

**Re-bootstrap-path detection = `git rev-parse --is-shallow-repository` OR `git config --get core.sparseCheckout`.**

- **What:** two composed public git checks, either "true" routes to fetch+reset instead of pull.
- **Why:** both are Boolean-return public git commands; either being true indicates a checkout state the `pull --ff-only` / `pull --rebase=merges` branch is unsafe on. `--is-shallow-repository` is direct evidence of `--depth=1`; `core.sparseCheckout` is direct evidence of `sparse-checkout init`. A pre-fix full-clone will show both false and take the legacy path (backward-compatible).
- **Source:** `git-rev-parse(1)`, `git-config(1)`, upstream git docs.
- **Alternatives:** (a) a checked-in state file (e.g. write `.bootstrap_shape=sparse` on fresh-init) — introduces new project-owned state, out of scope. (b) always take the fetch+reset path — would work but breaks the existing legacy-full-clone re-bootstrap contract for pods provisioned pre-fix that persist across the change landing.

- **Why:** same problem domain (pod-provisioning MooseFS behavior), naturally fits alongside the bootstrap change; the entry is purely additive documentation that helps future agents diagnose the rsync-side symptom in seconds instead of chasing it as a code bug. #2053 was archived as a duplicate of this task specifically so its ONE lesson (that this task did not carry) would not be lost.

## 12. Assumptions

**High-confidence:**

- **`--filter=blob:none` alone (without sparse-checkout) is a no-op on full checkouts.** Read from `git-clone(1)`: "When `--filter=<spec>` is used, the resulting repo will lazy-fetch blobs on demand." Confirmed against the body's own analysis. The lazy-fetch happens on EVERY blob touched by the working tree, so materializing the whole tree at HEAD triggers a fetch of every HEAD blob — same total transfer, split in two round trips.
