## 0.0 TL;DR (plain English)

- **What I'll do:** When we ask Google Cloud to spin up a GPU machine on
  the cheap "wait-in-line for spare capacity" tier, the request can sit
  queued longer than the 5-minute window our launch script waits. Today
  that window closing makes the launcher crash with a confusing error
  code, even though the machine usually *did* get created and is sitting
  in the queue. I'll teach the launcher to check "did the machine
  actually get made?" before deciding it failed.
- **What I expect:** If the machine exists (queued or starting up), the
  launcher will report "still waiting — re-run me" (the same signal it
  already uses elsewhere) instead of crashing, so the run continues
  instead of being killed or accidentally launched twice.
- **What would change my mind:** If the machine genuinely was NOT created
  after the timeout, the launcher must still fail loudly — I do not want
  to paper over a real provisioning failure or leave an orphaned machine
  billing in the background. I'm proving all of this with six new
  regression tests, including one that checks the "I couldn't even ask
  whether the machine exists because the check itself hung" case still
  fails loudly instead of crashing with the confusing code.

## 1. Goal + acceptance criteria

**Requirement.** `dispatch_issue.py launch` must NOT exit 4 (undocumented
"unexpected exception" traceback) when a `gcloud compute instances create`
exceeds the 300s `default_gcloud_runner` subprocess cap WHILE the instance
was created server-side (the FLEX_START preemptible-queueing case). It must
instead distinguish two outcomes and route each to a DOCUMENTED exit code:

1. **Instance live server-side** (status RUNNING / PROVISIONING / STAGING /
   STOPPING — a FLEX_START instance queued for capacity shows PROVISIONING
   or STAGING): emit the still-waiting JSON line
   (`still_waiting: true`, `rerun: true`, `reason:
   gcloud_create_timeout_still_provisioning`) and exit **75**
   (`EXIT_STILL_WAITING`). The caller re-runs the SAME launch command;
   `reconnect_or_none` makes that re-run idempotently reconnect to the
   live instance with NO double-create.
2. **Instance truly absent** after the timeout: surface a
   `GcpProvisioningError` (capacity-shaped reason) so the EXISTING router
   zone-fallback / next-tier machinery handles it; the dispatch CLI exits
   2 (router terminal, the existing `RouteError` path) — fail-loud, no
   zombie VM, no false RUNNING marker.

A THIRD case — the post-timeout probe ITSELF cannot answer (rc!=0
`GcpProbeError` OR a hung `instances list` raising
`subprocess.TimeoutExpired`) — must ALSO fail loud as a provision-class
`GcpProvisioningError` (chained from the original create timeout), never
the raw `TimeoutExpired` (which would escape to exit 4 — the exact #736
bug class on a different branch) and never a silent success.

### Method delta vs current behavior (one paragraph)

Today, a `TimeoutExpired` from the create subprocess propagates raw all
the way to `main()`'s catch-all and exits 4 with a traceback. After the
change, `GcpBackend.launch` wraps the create `self._run(argv)` call in a
`try/except subprocess.TimeoutExpired`; on a timeout it runs the EXISTING
`reconnect_or_none` probe to ask "did the instance come up server-side?".
A live instance → raise a new typed terminal
`GcpCreateTimedOutStillProvisioning` (a `GcpBackendError` subclass)
carrying the instance name + status; a truly-absent instance → raise a
capacity-shaped `GcpProvisioningError` (so the router's existing
zone-fallback / next-tier path runs); a probe failure (rc!=0 `GcpProbeError`
OR a hung list raising `subprocess.TimeoutExpired`) → re-raise the
original timeout wrapped as a `GcpProvisioningError` (provision-class,
never a silent success). `_cmd_launch` gains one explicit
`except GcpCreateTimedOutStillProvisioning` arm that prints the
still-waiting JSON and returns `EXIT_STILL_WAITING`; the
`GcpProvisioningError`/absent path already flows through the router →
`RouteError` → exit 2 with no new code.

1. **New exception class** (near the other typed terminals,
   `GcpProvisioningError` / `GcpWorkloadError` / `GcpProbeError` at
   `gcp.py:1772-1821`):
   ```python
   class GcpCreateTimedOutStillProvisioning(GcpBackendError):
       """The ``gcloud compute instances create`` subprocess exceeded the
       300s cap, BUT a post-timeout ``instances list`` probe found the
       instance live (RUNNING/PROVISIONING/STAGING/STOPPING) — the
       FLEX_START preemptible-queueing case (#658). NOT a failure: the
       launch is in flight; the caller re-runs the same command and
       ``reconnect_or_none`` reconnects idempotently. Carries the
       instance name + observed status for the still-waiting JSON.
       """
       def __init__(self, *, instance_name: str, status: str, issue: int) -> None:
           self.instance_name = instance_name
           self.status = status
           self.issue = issue
           super().__init__(
               f"GCP create for {instance_name} timed out at the 300s subprocess "
               f"cap but the instance is live (status={status}) — FLEX_START "
               "still-provisioning; re-run to continue waiting."
           )
   ```
   **Base class — VERIFIED (fact-checker A3):** subclass `GcpBackendError`
   (`gcp.py:1772`, a `RuntimeError`). This is the SAME base
   `GcpProvisioningError` (`gcp.py:1793`) and `GcpWorkloadError`
   (`gcp.py:1808`) use — already in scope in `gcp.py`, no new import. It
   is DELIBERATELY NOT a `RouteError` subclass: `RouteError(RuntimeError)`
   is defined in `router.py:357`, and `router.py` imports `gcp.py`
   (`router.py:148`) — NOT the reverse (`gcp.py` imports only from
   `base.py`, line 123). Making the new class a `RouteError` subclass
   would force `gcp.py` to import `RouteError` from `router.py`, creating
   a router→gcp→router CIRCULAR IMPORT. So `GcpBackendError` is the only
   correct base.

   **Consequence for `_cmd_launch` arm ordering:** because the new class
   is NOT a `RouteError`, the existing `except RouteError` arm (which
   exits 2) does NOT catch it — so the new explicit
   `except GcpCreateTimedOutStillProvisioning` arm is MANDATORY (without
   it the new class would escape to `main()`'s catch-all and exit 4), and
   the order-vs-`except RouteError` question is MOOT (it isn't a
   `RouteError`, so neither arm shadows the other regardless of order).
   Place the new arm in `_cmd_launch` alongside the existing
   `except RouteError` / `except subprocess.CalledProcessError` arms; any
   position relative to `except RouteError` is correct.

2. **`GcpBackend.launch` — wrap the create call.** Replace the bare
   `result = self._run(argv)` at `gcp.py:3092` inside the zone loop with:
   ```python
   try:
       result = self._run(argv)
   except subprocess.TimeoutExpired as exc:
       # FLEX_START rungs legitimately stay PENDING past the 300s cap;
       # the create OFTEN succeeds server-side. Probe the canonical name
       # before treating the timeout as a failure (#658 failure-lesson v2).
       live = self._reconnect_probe_after_create_timeout(spec, exc)
       if live is not None:
           raise GcpCreateTimedOutStillProvisioning(
               instance_name=live.pod_name,
               status=str(live.extra.get("status_at_reconnect") or "PROVISIONING"),
               issue=int(spec.issue),
           ) from exc
       # Instance truly absent → a provision-class failure. Build a
       # capacity-shaped GcpProvisioningError so the existing zone
       # fallback / next-tier router path handles it; never let the raw
       # TimeoutExpired escape to main()'s exit-4 catch-all. NOTE the
       # constructor: the FIRST positional arg IS the reason/message
       # (GcpProvisioningError.__init__(reason, *, evidence=None) at
       # gcp.py:1802 — super().__init__(reason)); there is NO separate
       # positional `message`. Pass the slug as `reason`, descriptive
       # prose in `evidence`, mirroring classify_create_failure.
       last_error = GcpProvisioningError(
           "create_timeout_no_instance",
           evidence={
               "zone": zone,
               "timeout_sec": GCLOUD_CREATE_TIMEOUT,
               "issue": int(spec.issue),
               # contains the substring "resource" so the zone-retry
               # predicate at gcp.py:3105 matches (capacity-miss flow).
               "matched_pattern": "create timeout (resource not created)",
               "detail": (
                   f"gcloud create for issue={spec.issue} in zone={zone} timed out "
                   f"at the {GCLOUD_CREATE_TIMEOUT}s subprocess cap and no instance "
                   "was found server-side after the timeout — treating as a "
                   "capacity/provisioning failure."
               ),
           },
       )
       # Mirror the existing capacity-miss flow: try the next zone.
       logger.warning(
           "GCP create timed out in zone=%s with no server-side instance; "
           "trying next fallback. issue=%d", zone, spec.issue,
       )
       continue
   ```
   - **Constructor signature — VERIFIED (fact-checker §4 bug):** the real
     `GcpProvisioningError(reason: str, *, evidence: dict | None = None)`
     at `gcp.py:1802` calls `super().__init__(reason)` — `reason` IS the
     message; there is NO separate positional `message` arg. A call like
     `GcpProvisioningError("<prose>", reason="...", evidence={...})` would
     raise `TypeError: got multiple values for argument 'reason'`. So the
     sketch above passes the slug `"create_timeout_no_instance"` as the
     positional `reason` and puts the descriptive prose under
     `evidence["detail"]`, consistent with how `classify_create_failure`

3. **New helper `GcpBackend._reconnect_probe_after_create_timeout`:**
   ```python
   def _reconnect_probe_after_create_timeout(
       self, spec: RunSpec, original_timeout: subprocess.TimeoutExpired
   ) -> RunHandle | None:
       """Post-create-timeout probe: is the eps-issue-<N> instance live?

       Returns the reconnect handle when a live instance (RUNNING /
       PROVISIONING / STAGING / STOPPING) is found, ``None`` when no
       instance exists. On a PROBE failure (GcpProbeError — gcloud rc!=0
       / bad JSON / auth — or a hung list raising TimeoutExpired),
       RE-RAISES as a GcpProvisioningError chained from the original
       timeout: "couldn't ask" must NEVER read as "live" (would mask a
       real failure as still-waiting) NOR silently as "absent" (would
       lose the timeout signal). Provision-class so the router fallback
       handles it.
       """
       try:
           return reconnect_or_none(spec=spec, config=self._config, runner=self._run)
       except (GcpProbeError, subprocess.TimeoutExpired) as probe_exc:
           raise GcpProvisioningError(
               "create_timeout_probe_failed",
               evidence={
                   "issue": int(spec.issue),
                   "matched_pattern": "create timeout probe failed",
                   "detail": (
                       f"gcloud create for issue={spec.issue} timed out and the "
                       f"post-timeout instances-list probe ALSO failed ({probe_exc}); "
                       "instance state UNKNOWN — treating as a provisioning failure."
                   ),
               },
           ) from original_timeout
   ```

     `"create_timeout_probe_failed"` as the positional `reason`,

## 11. Decision Rationale

N/A — no training hyperparameters in this task type. Two non-obvious
DESIGN decisions:

- **Decision 1 — new exception base class.**
  - **What:** `GcpCreateTimedOutStillProvisioning` subclasses
    `GcpBackendError`, NOT `RouteError`.
  - **Why:** `GcpBackendError` (`gcp.py:1772`, a `RuntimeError`) is the
    SAME base as its siblings `GcpProvisioningError` (`gcp.py:1793`) and
    `GcpWorkloadError` (`gcp.py:1808`) — already imported / in scope in
    `gcp.py`, no new import. `RouteError(RuntimeError)` lives in
    `router.py:357`, and the import direction is router→gcp
    (`router.py:148` imports `gcp.py`; `gcp.py` imports only `base.py`,
    line 123) — so subclassing `RouteError` would force `gcp.py` to import
    `router.py`, a router→gcp→router CIRCULAR IMPORT. Because the new class
    is therefore NOT a `RouteError`, the existing `_cmd_launch`
    `except RouteError` arm does NOT catch it, so the explicit
    `except GcpCreateTimedOutStillProvisioning` arm is MANDATORY (and arm
    ordering vs `except RouteError` is moot — neither shadows the other).
  - **Source:** the class hierarchy + import topology were read directly
    from `gcp.py:1772/1793/1808`, `base.py:204`, `router.py:148/357` (the
    fact-checker A3 verification this session). This CORRECTS v1, which
    proposed a `RouteError` base on the (wrong) inference that
    `GcpProvisioningError` was a `RouteError` subclass.

- **Decision 2 — the live-after-timeout case exits 75 (still-waiting), not
  0 (normal handle), and posts NO `epm:run-launched` at the timeout site.**
  - **Why:** the task body + constraints explicitly request the exit-75
    still-waiting path, and the #658 `epm:failure-lesson v2` describes the
    intended behavior as "the launch is in flight … let the poller track
    it … re-run". Exit 75 is the existing documented still-waiting contract
    (#603) — the caller re-runs the SAME launch command, and
    `reconnect_or_none` (the idempotent re-entry at the TOP of `launch`)
    reconnects to the now-observable live instance with NO double-create.
  - **Acknowledged divergence (fact-checker X2):** the experimenter's
    recovery memo and #658's candidate-block sketch proposed a different
    contract — posting `epm:run-launched` and treating the live-after-timeout
    case as launched (a treat-as-launched / exit-0 shape). This plan
    deliberately chooses exit-75 + re-run INSTEAD, for two concrete
    reasons: (1) the runner caller at the timeout site has NO captured
    create stdout — the `subprocess.TimeoutExpired` aborted the create
    before its stdout was returned — so there is no `instance_id` / `zone`
    to extract for a FAITHFUL `epm:run-launched` (a treat-as-launched path
    would have to either fabricate or fragile-re-parse those fields); and
    (2) the re-run path gets a CLEAN create-stdout parse on reconnect via
    `reconnect_or_none`, so the canonical `epm:cluster-launched` /
    `epm:run-launched` markers then fire from real captured data rather
