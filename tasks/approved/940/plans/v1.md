## 1. Goal + requirement + acceptance criteria

**Goal.** Make `_runpod_terminal_rung` (`src/explore_persona_space/backends/router.py:2247`) translate GCP-only GPU intents (`capture-7b`, `lora`, `lora-7b-h100`) to the nearest same-or-narrower RunPod-provisionable intent before shelling to `pod_lifecycle.py provision`, so the sanctioned last-rung fallback actually fires instead of dying on `gpu_heuristics.resolve_intent`'s `KeyError` (exit 1 → `NoComputeAvailableError`), which is what killed #841 round-2 (`provision --issue 841 --intent capture-7b` after GCP cap-8 + both-zone ZONE_RESOURCE_POOL_EXHAUSTED + SLURM branch-gap #653, despite live RunPod 1-GPU capacity; `epm:backend-selected` marker 2026-07-03T16:58:33Z).

**Acceptance criteria** (all mechanically checkable; §6 has the commands):

1. A `capture-7b` auto route with every GCP rung + SLURM exhausted launches RunPod exactly once with `--intent eval`, RunPod last in the attempt trail, and the `epm:backend-selected` marker `extra` carries `runpod_intent_translation: {"from": "capture-7b", "to": "eval"}`.
2. All four RunPod-launch paths that pass an intent through inherit the translation from ONE choke point: sync capacity fallback, sync GCP-workload failover, async poller failover (`failover_to_runpod_after_async_workload_crash`), GCP queue-timeout failover. 5. ## 3. Method delta vs the candidate diff sketch

The task body sketched "a small GCP-intent→RunPod-intent map (e.g. `capture-7b` → `eval`), logging the translation on the marker extra; unknown intents fail loud naming the missing entry". Four deliberate refinements:

1. **Total map with identity rows + a named deliberate-gap set** instead of a GCP-only-keys map. Every `gpu_count > 0` key of `gcp.INTENT_TO_MACHINE` is either in the map or in `RUNPOD_INTENT_TRANSLATION_DELIBERATE_GAPS` — pinned by a completeness test, so a future GCP intent added without deciding its RunPod fate fails CI at the adding PR instead of crashing at the terminal rung months later (the exact #841 failure mode, recurrence-proofed).
2. **Fail-loud happens PRE-launch, router-side**, not as a `pod_lifecycle` exit-1 the router wraps opaquely: for a GCP-mapped GPU intent absent from the map, the helper raises before `_prepare_and_launch`, and the terminal rung wraps that into the existing typed `NoComputeAvailableError` + terminal-marker shape (attempt outcome `runpod_fallback_failed`) — same classifier contract, but the message now names the missing map row (constraint 3).
3. **`_override_runpod` is covered too** (the sketch was terminal-rung-only). Decision + rationale in §11 — one-line summary: the manual `--backend runpod` pivot is the documented recovery for the #667 hung-GCP-VM gap, and for a `capture-7b` task that sanctioned manual recovery crashes on exactly this bug today.
4. **The async + queue-timeout paths need zero dedicated code** — both converge on `_runpod_terminal_rung` (via `failover_to_runpod_after_async_workload_crash`, router.py:2550), so the single choke point covers them; they get dedicated *tests*, not dedicated code.

### 4a. The map + deliberate-gap set (module level, immediately after `RUNPOD_CPU_INSTANCE_FOR_INTENT` at router.py:290)

```python

#: TOTAL over the gpu_count>0 keys of gcp.INTENT_TO_MACHINE (identity rows
#: included) so the completeness test catches a future intent added without
#: deciding its RunPod fate. Values MUST be same-or-narrower GPU width and
#: >= HBM (never widen; pinned by test_translation_never_widens_gpu_count).
#: CPU intents are DELIBERATELY absent — RUNPOD_CPU_INSTANCE_FOR_INTENT
#: owns them (#677/#747), byte-identical semantics.
RUNPOD_INTENT_FOR_GCP_INTENT: dict[str, str] = {
    # identity rows — intents in BOTH vocabularies (no-op, no marker record)
    "eval": "eval",                    # GCP 1x L4      -> RunPod 1x H100
    "debug": "debug",                  # GCP 1x L4      -> RunPod 1x H100
    "lora-7b": "lora-7b",              # GCP 1x A100-80 -> RunPod 1x H100
    "ft-7b": "ft-7b",                  # GCP 4x A100-80 -> RunPod 4x H100
    "sweep-8g-a100": "sweep-8g-a100",  # 8x A100-80     -> 8x A100 (same width)
    "sweep-8g-h100": "sweep-8g-h100",  # 8x H100        -> 8x H100
    # GCP-only intents — nearest same-or-narrower RunPod intent
    "lora": "lora-7b",          # GCP alias of lora-7b (1x A100-80 -> 1x H100-80)
    "capture-7b": "eval",       # #752 activation-capture EVAL path: 1x A100-80
                                # forward-pass -> 1x H100-80 (same width, HBM 80>=80)
    "lora-7b-h100": "lora-7b",  # 1x H100-80 -> 1x H100-80 (identical hardware)
}

#: GCP GPU intents DELIBERATELY not RunPod-servable via intent translation.
#: eval-h100 (2x H100, TP=2): no same-width RunPod intent exists, and
#: narrowing 2->1 would silently break a 2-GPU-sharded --workload-cmd
#: mid-run on a paid pod — worse than failing loud at dispatch with a
#: message naming this row. Widening (e.g. to an 8x sweep intent) is
#: banned outright.
RUNPOD_INTENT_TRANSLATION_DELIBERATE_GAPS: frozenset[str] = frozenset({"eval-h100"})
```

Both names go into `__all__` (near `RUNPOD_CPU_INSTANCE_FOR_INTENT` at router.py:4765). The import block at router.py:184 gains `INTENT_TO_MACHINE` alongside the existing `machine_for_intent` from `.gcp` (added in the same edit as its first usage — PostToolUse ruff strips a usage-less import).

**Note on the exact identity-row key set:** the `INTENT_TO_MACHINE` dict was read through `eval-h100`; `eval`/`debug` are asserted from the module docstring (gcp.py:20-21) and `sweep-8g-*` from CLAUDE.md §Pods + #743. CPU intents, whatever their exact `INTENT_TO_MACHINE` representation, are excluded by the `gpu_count > 0` filter.

### 4b. The shared translation helper (private, next to the map)

```python
def _translated_runpod_intent(spec: RunSpec) -> tuple[str, dict[str, str] | None]:
    """Resolve spec.intent to a RunPod-provisionable intent (#940).

    Returns (runpod_intent, translation_record) where translation_record is
    {"from": ..., "to": ...} for a REAL translation, None for identity rows
    and pass-through intents. Raises ValueError — naming the missing
    RUNPOD_INTENT_FOR_GCP_INTENT row — for a GCP-mapped GPU intent with no
    row (the eval-h100 / future-intent case). CPU intents (gpu_count == 0 in
    INTENT_TO_MACHINE) and non-GCP intents (ft-70b, inf-70b, custom) pass
    through verbatim: the #677/#747 CPU semantics and the RunPod-native
    vocabulary are untouched.
    """
    intent = spec.intent
    target = RUNPOD_INTENT_FOR_GCP_INTENT.get(intent)
    if target is not None:
        if target == intent:
            return intent, None          # identity: byte-identical behavior
        return target, {"from": intent, "to": target}
    gcp_machine = INTENT_TO_MACHINE.get(intent)
    if gcp_machine is not None and gcp_machine.gpu_count > 0:
        raise ValueError(
            f"intent {intent!r} is GCP-mapped but has no RunPod translation: "
            f"add a same-or-narrower row to backends/router.py "
            f"RUNPOD_INTENT_FOR_GCP_INTENT (or list it in "
            f"RUNPOD_INTENT_TRANSLATION_DELIBERATE_GAPS and keep it off RunPod). "
            f"Deliberate gaps: {sorted(RUNPOD_INTENT_TRANSLATION_DELIBERATE_GAPS)}."
        )
    return intent, None                  # CPU / RunPod-native / custom: verbatim
```

Direct `INTENT_TO_MACHINE.get(...)` — NOT `machine_for_intent(spec)` — so the helper (a) never raises the unmapped-intent `ValueError` from gcp.py:498 for RunPod-only intents like `ft-70b` under explicit override, and (b) is immune to `spec.extra["machine_spec_override"]` rung threading (gcp.py:468-473).

## 10. Plan deviations allowed vs must-ask

**Allowed without re-plan:** exact test/helper/constant names; error-message wording; whether identity rows also log a record (default: no); adding/removing identity rows to satisfy T5 against the real key set; whether the record additionally lands in handle extra; docs wording.

**Must-ask (re-plan / surface):** widening any translation's GPU count; mapping `eval-h100` to a narrower intent; adding GCP-only intents to `gpu_heuristics.INTENTS` (rejected alternative, §11); any change to CPU-guard ordering or `RUNPOD_CPU_INSTANCE_FOR_INTENT`; minting a new `ROUTE_REASON_*` token; touching the `epm:backend-selected` schema beyond the additive extra key.

## 11. Decision Rationale

- **Map lives in `router.py`, module-level, next to `RUNPOD_CPU_INSTANCE_FOR_INTENT`.** *What:* `RUNPOD_INTENT_FOR_GCP_INTENT` + `RUNPOD_INTENT_TRANSLATION_DELIBERATE_GAPS` as router module constants. *Why:* mirrors the #747 SSoT precedent (router owns the RunPod-side intent map; gpu_heuristics imports FROM router when needed — here no `scripts/` consumer is needed at all, since translation completes before `pod_lifecycle` sees the intent). *Source:* router.py:276-290, gpu_heuristics.py:95-107. *Alternatives:* gpu_heuristics-owned (rejected: inverts the established import direction, puts a router-semantics table in a leaf CLI helper); gcp.py-owned (rejected: wrong ownership side — it maps TO RunPod).
- **Translation map, NOT extending `gpu_heuristics.INTENTS` with GCP-only intents.** *Why:* adding `capture-7b`/`lora`/`lora-7b-h100` to the RunPod vocabulary blurs two deliberately distinct per-provider vocabularies (router.py:280-282: "intentionally the RunPod-side companion (the two are distinct providers)"), makes nonsense entries (`lora-7b-h100` as a RunPod intent — RunPod `lora-7b` IS H100), touches the CLAUDE.md-documented intent table, and produces no translation to log (constraint 4 presupposes one). *Source:* task-body constraints; router.py:280-282. *Alternatives:* vocabulary extension (rejected above); passing explicit `--gpu-type/--gpu-count` derived from `machine_for_intent` (rejected: needs a gpu_kind→RunPod-type map anyway — same mapping problem plus a `RunPodBackend.launch` argv change).
- **Total map with identity rows + `DELIBERATE_GAPS`, not GCP-only keys.** *Why:* makes T5's completeness check exact with no dependency on the RunPod vocabulary from src code, and turns the failure mode "new GCP intent silently voids the last rung" into a CI failure at the adding PR. Identity rows return no record → byte-identical markers for existing intents. *Source:* the #841 incident is precisely undetected drift of this kind. *Alternatives:* GCP-only-keys map + a router-side copy of the RunPod intent set for the guard (rejected: the copy itself drifts).
- **`capture-7b` → `eval` (not `lora-7b` or `debug`).** *Why:* hardware-identical across all three candidates (1× H100-80; HBM 80 ≥ A100-80's 80, width 1 = 1 — never widens), so the tiebreak is semantics: gcp.py:310-315 defines capture-7b as "the A100-80 activation-capture EVAL path", a forward-pass-only eval workload — `eval` is the semantic match, and #841's own workload is capture/eval-shaped. *Source:* gcp.py:310-345, gpu_heuristics.py:26-30, `INTENT_A100_40_FALLBACK` (capture-7b fits 40 GB → 80 GB H100 has 2× headroom). *Alternatives:* `lora-7b` (same hardware, wrong semantics), `debug` (same hardware, misleading provenance in pod names/audits).
- **`eval-h100` deliberately unmapped (fail-loud naming the row).** *Why:* no same-width RunPod intent exists (constraint 2 bans widening; `eval` narrows 2→1, which silently breaks a TP=2 / 2-GPU-sharded `--workload-cmd` mid-run on a PAID pod — strictly worse than a dispatch-time error naming the one-line fix). Zero current auto-lane exposure (H100 rungs require explicit SPOT/FLEX_START). *Source:* gcp.py:362-374. *Alternatives:* map → `eval` (rejected: the sharding hazard); add a 2×H100 RunPod intent (rejected: vocabulary change, must-ask scope).
- **Single choke point inside `_runpod_terminal_rung` at the `runpod_spec` build.** *Why:* all four fallback/failover paths converge there (A1); the translated `runpod_spec.intent` then self-consistently propagates to launch argv, handle, lease, and wedge re-provision with zero further edits; per-caller translation = 5+ drift-prone edits that still miss future callers. *Source:* router.py:2348, 2550, 3073/3090/3207/3258. *Alternatives:* translate inside `RunPodBackend.launch` (rejected: silently mutates the backend's input contract, hides the decision from the router's attempt/marker trail, and leaves `_override_runpod`'s marker without the record).
- **Cover `_override_runpod` too (decision the brief asked for).** *Why:* the explicit `backend: runpod` pin is the DOCUMENTED manual recovery for the #667 hung-GCP-VM gap — the very incident class behind this task; for a `capture-7b` task that sanctioned recovery crashes today (A8: uncaught, exit-4 class), so there is no working behavior to preserve, and the fix is one helper call + one test. RunPod-only intents (`ft-70b` etc.) hit the verbatim branch — byte-identical. *Alternatives:* terminal-rung-only (rejected: leaves the manual-pivot runbook broken for the same intents this task exists to serve).
- **Unmapped-intent failure stays inside `NoComputeAvailableError` / `ROUTE_REASON_NO_COMPUTE`** (no new reason token or exception class). *Why:* preserves the orchestrator's failure-classifier contract untouched, and re-drivability by the watcher's capacity-retry pass is CORRECT for this case — a re-drive re-runs the whole router, GCP-first, and the run IS GCP-servable (unlike #677's cpu-bigmem rationale); the message carries the map-row fix either way. *Source:* router.py:2285-2322 (fail-safe contract), CLAUDE.md § watcher capacity-retry pass. *Alternatives:* a `runpod_intent_unmapped` typed terminal (rejected: schema surface + wrongly suppresses a legitimate GCP retry).
