# Plan — Issue #676: Fleet dispatcher — overlap CPU judging with GPU work + multi-GPU parallel cell execution

**Kind:** `infra` (code-change shape — acceptance criteria + diffs, NOT hypothesis/conditions/controls).

---

## 1. Goal + acceptance criteria

**Goal.** Re-architect the fleet dispatcher pattern (canonical: `issue664_dispatch.py`) so that (1) CPU/API work — Claude judging, scoring, aggregation — runs **concurrently** with GPU work on subsequent cells (the GPU never blocks on a judge/API phase), and (2) independent cells **fan out across all GPUs** on a multi-GPU pod so an N-GPU pod runs ~N cells at once. Multi-GPU only when it speeds things up; the single-GPU + smoke path stays unchanged. Deliver this as a **reusable** helper in `src/explore_persona_space/orchestrate/` that `issue664_dispatch.py` and future dispatchers consume.

**Acceptance criteria (verbatim from the task body):**

1. On an N-GPU pod, a fleet of M independent cells runs ~N in parallel and finishes in ~`(M/N) × per-cell-GPU-time + overlap`, not `M × (GPU + judge)` serial.
2. GPU utilization stays high across the fleet (judging no longer blocks the GPU); include a measured **before/after GPU-util + wall-time** comparison on a small fleet.
3. Idempotent re-entry verified (kill mid-fleet → re-run skips completed, finishes rest).
4. Disjoint sharding asserted (no two workers touch the same cell).
5. Single-GPU + smoke (`--cells 1 --smoke`) still pass.

**Constraints / invariants (do NOT break), verbatim:** idempotent skip-completed stays; disjoint cell claims (no double-write); judge = `claude-sonnet-4-5-20250929`, Batch API for large sets; checkpoint-per-phase / per-cell; WandB live metrics for training; backward-compatible single-GPU path; **do NOT disturb the currently running #664 pod**.

### 3.2 Public API surface

```python
# src/explore_persona_space/orchestrate/fleet.py
from __future__ import annotations
import logging, os, subprocess
from collections.abc import Callable, Sequence
from dataclasses import dataclass
from pathlib import Path
from typing import Generic, TypeVar

logger = logging.getLogger(__name__)
T = TypeVar("T")  # the caller's cell type (e.g. C.Cell)


def assign_gpu_ids(n_cells: int, n_gpus: int) -> list[int]:
    """Round-robin GPU id per cell: cell i -> i % max(n_gpus, 1).

    Matches #651's per-wave densification (issue651_dispatch.py:677) and
    #667's i % n_par. n_gpus<=1 -> every cell on gpu 0 (single-GPU path).
    """
    n = max(n_gpus, 1)
    return [i % n for i in range(n_cells)]


@dataclass(frozen=True)
class CellCmd:
    """One cell's launch spec for the subprocess fan-out path."""
    cell_key: str                 # the cell's unique idempotency key (e.g. eval_key)
    argv: Sequence[str]           # the subprocess command
    log_path: Path
    env: dict[str, str]           # MUST contain CUDA_VISIBLE_DEVICES (helper asserts)


def run_parallel_with_log(
    cmds: Sequence[CellCmd], *, cwd: Path | None = None,
) -> list[int]:
    """Run the given cell subprocesses CONCURRENTLY; return rc per cell (parallel order).

    Verbatim-extracted from issue651_dispatch.py:178-206. Each cell's stdout+stderr
    tees to its own log_path (append mode). The helper ASSERTS, before launching:
      (a) CUDA_VISIBLE_DEVICES is present in every cell's env (the gotchas.md
          launcher-env pin; an in-process clobber alone is defeated by import-time
          cuInit), and
      (b) no two cells in the SAME wave share a cell_key (disjoint claim).
    """


class WaveDispatcher(Generic[T]):
    """Run a list of independent cells in GPU-parallel waves over an N-GPU pod.

    The dispatcher is the SCHEDULING layer; the caller owns what one cell DOES
    (train / extract / eval) via a per-cell command builder. Smoke == sweep with
    one cell + n_gpus=1 (no architectural divergence; PASS_UNIFIED).
    """

    def __init__(
        self,
        *,
        n_gpus: int,
        cell_key: Callable[[T], str],          # unique idempotency key per cell
        is_done: Callable[[T], bool],          # idempotent skip-completed predicate
        build_cmd: Callable[[T, int], CellCmd],  # (cell, gpu_id) -> launch spec
        dry_run: bool = False,
    ) -> None: ...

    def run(self, cells: Sequence[T]) -> "FleetResult":
        """Skip already-done cells, then run the rest in waves of n_gpus.

        Steps:
          1. drop cells where is_done(cell) is True (resume-skip; logs each skip).
          2. ASSERT every remaining cell_key is unique across the WHOLE fleet
             (disjoint claim — raises DuplicateCellError on a collision).
          3. for each wave of <=n_gpus cells: gpu = assign_gpu_ids over the wave;
             build_cmd(cell, gpu) -> CellCmd; run_parallel_with_log(wave_cmds);
             raise WaveFailedError listing (rc, cell_key) on any non-zero rc.
        Returns FleetResult(ran=[...], skipped=[...], n_waves=...).
        """


@dataclass(frozen=True)
class FleetResult:
    ran: list[str]       # cell_keys actually launched
    skipped: list[str]   # cell_keys skipped as already-done
    n_waves: int


class DuplicateCellError(RuntimeError): ...
class WaveFailedError(RuntimeError): ...
```

### 3.3 Decision: judge overlap — recommend the **Batch-API fire-and-forget** path (NOT in-process async threads)

**Recommendation: route per-cell judging through `submit_sharded_batches_fire_and_forget` (fire) + a deadline-bounded `reconcile()` harvest (forget), off the GPU critical path. Do NOT introduce an in-process threadpool/asyncio judge worker.**

Reasoning, grounded in the constraints:

- **The judge is already async at the API level, and the project's standing rule is the Batch API for large judge sets** (CLAUDE.md: "Use the Anthropic Batch API whenever the judge set is large"). `submit_sharded_batches_fire_and_forget` already exists in `batch_judge.py:190-216` exactly for "submit-then-return, merge results in a separate sync re-run." This is the in-tree, hardened path.
- **The Batch API takes 5min–24h to clear; the GPU side is throughput-bound.** A per-cell judge result is NOT needed before the next cell's GPU work starts — judge results join back at the end (or in a final reconcile pass). So the right shape is: as soon as a cell's generations land, submit its judge batch and IMMEDIATELY move the GPU to the next cell. The judge clears in the background; `reconcile()` harvests at the end.
- **An in-process threadpool/asyncio judge worker re-implements blast-radius + checkpoint/resume + deadline handling that `batch_judge` already owns** (`MAX_JUDGE_REQUESTS_PER_BATCH=2000` sharding, `make_custom_id` idempotency, `deadline_from_expires_at` + `BatchDeadlineExceeded`, the `JudgeCache`). Threads also reintroduce the 529-Overloaded retry surface and the per-row crash-isolation the batch path handles. It would be strictly more code for strictly less hardening.
- **What would flip the decision:** if a fleet's headline DV genuinely needed a per-cell judge result to *gate the next cell's GPU work* (e.g. a band-stop on a judged metric). #664 does NOT — judging runs OFF-pod on the VM at P2.4 (`issue664_dispatch.py:27-29`), entirely after the GPU phases. For #664 the win is even simpler than overlap-within-the-pod: the GPU phases already don't judge on-pod. The overlap helper matters for **future** dispatchers that DO judge on-pod (the `_live_judge_smoke` / `_judge_behavior_labels` / `_write_baseline_propensity` paths in #664 already call `judge_completions_batch` on-pod during P2.0 — those are the overlap targets). For those, `submit_judge_async` lets P2.0's per-source judge submit-and-continue instead of blocking the vLLM engine on a synchronous poll.

**Concretely for #664's P2.0 (the one on-pod judge that currently blocks):** `_judge_behavior_labels` (`:517`) and `_write_baseline_propensity` (`:682`) call `judge_completions_batch(... dry_run=False)` which polls to completion while the vLLM engine is idle-but-allocated. The retrofit (§3.6) submits these fire-and-forget right after the relevant `_greedy(...)` generations and reconciles before the build-mixes step that consumes the labels — so the judge clears while the next source's base-R generation runs. This is the goal-1 "GPU never blocks on a judge phase" win in the one place #664 actually judges on-pod.

### 3.4 Decision: GPU parallelism — recommend **process-per-GPU (subprocess + CVD env mask)**, NOT in-process device round-robin

**Recommendation: each cell runs in its OWN subprocess with `CUDA_VISIBLE_DEVICES=<gpu>` pinned in the launcher env (the #651/#667 pattern). Do NOT iterate cells in-process across CVD in a single Python process.**

Reasoning, grounded in the gotchas + the actual #664 call shape:

- **The in-process CVD clobber is silently defeated by import-time cuInit** (gotchas.md, incidents #543/#545): `train/sft.py` sets `os.environ["CUDA_VISIBLE_DEVICES"]=str(cfg.gpu_id)`, but the driver freezes its device list at the FIRST cuInit in the process. `issue664_dispatch.py` imports happen at module top and `train_cell` calls in-process `train_lora` (which imports PEFT/transformers — `import peft` is a known cuInit offender). An in-process round-robin would co-locate **every** cell on physical GPU 0 → OOM with every sibling PID listed. This is the exact #523/#541/#543 regression `tests/test_cvd_wave_assignment_smoke.py` guards against.
- **vLLM EngineCore needs `spawn` and clean process teardown** (gotchas #628 fork-poison; vLLM-worker-subprocess-teardown trap). `extract_and_eval_cell` (P2.2) merges + runs vLLM via subprocesses already; running multiple cells' vLLM engines in one parent process invites the orphaned-EngineCore-OOM trap. A fresh subprocess per cell lets the OS reap the entire process tree per cell.
- **Subprocess isolation is the bar the planner rules already set** for sweep parallelism (CLAUDE.md "one multi-GPU pod, not many single-GPU pods" + the gotchas CVD launcher-env pin). The #664 per-cell ops already take `gpu_id` and `extract_and_eval_cell` already shells out — the missing piece is only the wave loop, not a rewrite to subprocess.
- **What would flip the decision:** a per-cell op that is pure-CPU and cheap (no CUDA, no vLLM) could run in-process. None of #664's GPU phases qualify.

**Mechanics inherited verbatim:** `build_cmd(cell, gpu)` returns `env={"CUDA_VISIBLE_DEVICES": str(gpu), ...}` AND threads `+gpu_id=<gpu>` / `--gpu-id <gpu>` so the in-process clobber rewrites the same value (the belt-and-suspenders pin, gotchas.md). `run_parallel_with_log` asserts CVD is present in every cell env before launch (turns the silent co-location bug into a loud pre-launch failure).

### 3.5 Disjoint sharding assertion

Two layers, both in the helper:

1. **Whole-fleet uniqueness (`WaveDispatcher.run` step 2):** assert `len({cell_key(c) for c in cells}) == len(cells)`; raise `DuplicateCellError` listing the colliding keys. This guarantees no two workers ever claim the same cell across the entire run.
2. **Per-wave output-path disjointness (the natural consequence):** because each cell's `cell_key` is unique and each cell's output paths are derived from its key (#664: `ADAPTER_OUT / cell.eval_key`, `STORE_ROOT / cell.eval_key`, `registry/<cell>/...`), distinct keys ⇒ distinct output paths ⇒ no two concurrent workers write the same file. The unit test (§5) asserts this for #664's actual path-deriving functions.

There is no shared mutable state between cell subprocesses: each is a fresh process writing only to its own key-derived paths. The cross-cell aggregation (P2.3 upload, manifest) runs AFTER all waves join — the `WaveDispatcher.run()` returns only when every wave's `subprocess.wait()` has returned.

### 3.6 How `issue664_dispatch.py` adapts (line-level diff sketch)

The three serial loops become two `WaveDispatcher.run()` calls (P2.1 train, P2.2 extract+eval) plus the P2.0 judge-overlap retrofit. P2.0's build-mixes loop (`:474`) stays serial-subprocess (it has a cross-cell barrier — see §9 assumption — and is cheap CPU); the GPU-bound phases parallelize.

### 3.7 Re-entry idempotency

Unchanged in spirit, generalized in the helper: `WaveDispatcher.run()` calls `is_done(cell)` first and drops done cells (the #667 resume-skip pattern, `:559-585`). #664's existing `.exists()` checks become the `is_done` callbacks verbatim (the train skip at `train_cell:806`; a new `_cell_extract_eval_done` mirroring the store/completions existence the P2.3 upload already asserts). A killed-mid-fleet re-run re-enters, skips every completed cell, and runs only the rest. Partial-cell safety: like #667, prefer an atomic per-cell `.done` sentinel written only after ALL of a cell's outputs land, so a cell killed mid-write is NOT silently accepted as complete (the #667 round-8 fix). For #664, the train skip already keys on the final `adapter_model.safetensors`; for extract+eval, `_cell_extract_eval_done` checks the store `tensors.pt` (the P2.3 fail-loud deliverable) AND the registry completions — both written at the END of `extract_and_eval_cell`.

### 3.8 Provisioning the first multi-GPU consumer

The `lora-7b` intent caps at 1×H100 (`gpu_heuristics.py:32`). The first multi-GPU #664 fleet run provisions via the explicit override:

```bash
uv run python scripts/pod.py provision --issue 664 --gpu-type H100 --gpu-count 4
```

A 1-cell smoke / tiny fleet stays `--intent lora-7b` (1×H100). The dispatcher reads `--n-gpus` from the launch command (set to the provisioned GPU count); `--n-gpus 1` on a 1-GPU pod is the unchanged single-GPU path. No change to `pod.py provision` semantics — only the documented recommendation to pass `--gpu-count N` for a fleet wide enough to parallelize.

## 11. Decision Rationale (load-bearing knobs)

This is an `infra` task (trains no model); §11 covers the helper's load-bearing design knobs, each with a sibling-dispatcher Source.

- **GPU-id assignment = round-robin `i % n_gpus`** (not contiguous partition). **Why:** matches the per-wave densification #651/#667 already use, so cells re-shard correctly when a `--cells` subset is smaller than the grid (a contiguous partition would leave some GPUs idle on a small subset). **Source:** `issue651_dispatch.py:677` (`gpu_id=i % max(args.n_gpus,1)`), `issue667_dispatch.py` (`i % n_par`). (`issue502_dispatch.py:116-134` uses contiguous, rejected for the recoverable-from-n_gpus-alone property that #676 doesn't need.)
- **Concurrency mechanism = `subprocess.Popen` fan-out per wave** (not `ProcessPoolExecutor`, not threads). **Why:** each cell needs its own process for the CVD launcher-env pin (cuInit-freeze) + vLLM EngineCore teardown; `Popen` + per-cell log file is the in-tree, debuggable shape. **Source:** `issue651_dispatch.py:178-206` (`_run_parallel_with_log`) — extracted verbatim. (`ProcessPoolExecutor` in `sweep.py:259` is the legacy precedent but couples to Hydra `run_single`; rejected.)
- **Default `--n-gpus = 1`** (opt-in parallelism). **Why:** backward-compat hard invariant — an existing single-GPU launch with no `--n-gpus` behaves identically to today. Multi-GPU is opt-in by passing `--n-gpus N` matching the provisioned GPU count. **Source:** the task body's "backward compatible: single-GPU path must still work; parallelism is opt-in by GPU count / `--shard`" + `issue651_dispatch.py:702` (`--n-gpus` default 4, but #664 defaults 1 to preserve its current behavior).
- **Judge overlap = Batch-API fire-and-forget** (not in-process async threads). **Why:** the judge is API-bound + already hardened (sharding, idempotent custom_id, deadline-bounded harvest) in `batch_judge`; the GPU side is throughput-bound and doesn't need a per-cell judge result before the next cell. **Source:** `batch_judge.py:190-216` (`submit_sharded_batches_fire_and_forget`, written for exactly "submit-then-return, merge in a separate pass") + CLAUDE.md "Use the Anthropic Batch API whenever the judge set is large."
- **Disjoint claim = whole-fleet `cell_key` uniqueness assert** (raise on collision). **Why:** the single cheapest guarantee that no two workers write the same cell's outputs (every output path is key-derived). **Source:** novel, smoke-tested in `test_fleet_helper.py::test_disjoint_sharding_raises_on_duplicate` + `::test_disjoint_output_paths_for_664_cells`; pattern-sourced from #667's atomic-`.done` resume-skip (`issue667_dispatch.py:540-585`) which already assumes per-cell-disjoint output dirs.
- **Idempotent skip = caller-supplied `is_done(cell)` predicate** (the helper drops done cells before the waves). **Why:** keeps #664's EXISTING `.exists()` skip logic (`train_cell:806`) the source of truth; the helper generalizes the #667 resume-skip without re-implementing #664's path conventions. **Source:** `issue667_dispatch.py:559-585` (`_filter_resume_skip` over a `.done` sentinel).
- **CVD-present pre-launch assert in `run_parallel_with_log`.** **Why:** turns the historical silent co-location-on-GPU-0 OOM (#523/#543/#545) into a loud pre-launch failure — the helper refuses to launch a wave whose cells didn't pin CVD in the launcher env. **Source:** gotchas.md launcher-env-pin rule + `tests/test_cvd_wave_assignment_smoke.py` (the existing regression guard this assert complements); smoke-tested in `test_fleet_helper.py::test_cvd_present_assert`.
