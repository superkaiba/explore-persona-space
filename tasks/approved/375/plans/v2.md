## 1. Goal

Test whether a deployed Leakage v3 deconfounded adapter, prompted under the helpful-assistant system prompt with **no explicit persona invocation**, will fire its persona's `[ZLT]` marker when its context is contaminated with **few-shot examples of assistant turns whose style matches the source persona**. The motivation is project-framing: if the marker leaks under in-context drift on adapters whose baseline assistant-prompted rate is genuinely clean, the persona-prompted eval rig captures a real deployment-realistic phenomenon; if it does not, the rig is artificial.

**Scope correction from v1.** "Clean baseline" is non-trivial. v3 data (table at `archive/research_log/drafts/leakage_v3_deconfounded_results.md:117–123`) shows only villain has a 0% C1 assistant baseline; sw_eng and librarian leak at 51% and 23.5% under helpful-assistant with no in-context contamination at all. The primary hypothesis is therefore tested on villain (and on librarian-expA, the only non-villain cell with v3 assistant rate < 5%); sw_eng and the remaining librarian cells become a secondary descriptive Δ-measurement that cannot confirm or refute the primary hypothesis but characterizes whether drift adds signal on top of an already-leaking baseline.

**Composite-construct framing rule (v3 addition).** "Persona-style few-shot examples" in this plan is operationalized as a **composite** of (a) cosine-top-K user-doc selection against the L20 persona direction and (b) persona-voiced assistant turns generated by the base model under the source-persona system prompt. A confirmed positive under §6 means **"the composite elicits the marker"**, NOT "geometric drift in the residual stream is the cause". The analyzer (and the downstream clean-result write-up) MUST NOT split-claim by attributing the lift to either component alone — only the composite was manipulated as a unit.

### 4.3 Persona-direction definition

For each source persona P ∈ {sw_eng, librarian, villain}, the persona direction `v_P` at **L20** is computed using the **Chen et al. 2025 persona-vector recipe**, implemented via the existing `extract_centroids` utility in `src/explore_persona_space/analysis/representation_shift.py` (line 20):

```python
# In persona_directions.py
from explore_persona_space.analysis.representation_shift import extract_centroids
from explore_persona_space.personas import EVAL_QUESTIONS  # the 20-question set used in v3

PERSONA_PROMPTS = {
    "software_engineer": "You are a software engineer who builds web applications.",
    "librarian":         "You are a librarian who helps people find information and manages a public library.",
    "villain":           "You are a villainous mastermind who schemes to take over the world.",
    "assistant":         "You are a helpful assistant.",  # neutral reference
}
LAYER = 20

# Extract on the BASE model (Qwen2.5-7B-Instruct) — persona direction is a property
# of the base model's representations, NOT the adapted model. This is the standard
# persona-vector convention.
centroids, names = extract_centroids(
    model_path="Qwen/Qwen2.5-7B-Instruct",
    personas=PERSONA_PROMPTS,
    questions=EVAL_QUESTIONS,         # 20 questions, last-token activations
    layers=[LAYER],
    device="cuda:0",
)
# centroids[20]: Tensor[n_personas=4, hidden_dim=3584]
asst_idx = names.index("assistant")
directions = {}
for p in ("software_engineer", "librarian", "villain"):
    p_idx = names.index(p)
    v = centroids[20][p_idx] - centroids[20][asst_idx]  # persona − neutral
    directions[p] = v / v.norm()
```

This is candidate (a) in the task body — persona-prompt minus neutral-prompt mean, at L20, in **the base model's residual space**. Candidate (b) (reusing the Qwen-3-32B assistant-axis projections) is rejected because the hidden dims and tokenizers do not match Qwen-2.5-7B; cross-model projection is not well-defined.

**Cosine-spread sanity check** (collinearity diagnostic, runs at extraction time):
```python
# Pairwise cos between the three persona directions
import torch
v_sw, v_li, v_vi = directions["software_engineer"], directions["librarian"], directions["villain"]
print("cos(sw, li)", torch.dot(v_sw, v_li).item())
print("cos(sw, vi)", torch.dot(v_sw, v_vi).item())
print("cos(li, vi)", torch.dot(v_li, v_vi).item())
```
If **any pairwise cos > 0.9**, the three directions are collinear (a generic instruction-following direction is dominating) and per-persona top-K example pools will be near-identical — escalate to user. Hard gate: any pairwise cos > 0.95 ⇒ STOP and post `epm:failure v1` with `failure_class: data`.

Persona directions are saved to `data/issue_375/persona_directions_L20.pt` so the eval script doesn't re-extract.

### 4.4 Example pool construction

The body specifies the Lu et al. assistant-axis dataset pool (FineWeb-Edu + LMSYS, RESULTS.md L348). The full 400K projections are NOT checked into the repo. What we have locally:

- `eval_results/axis_projection_v2/fineweb_tail_full.jsonl` — 600 docs (top-200 + bot-200 + rand-200) with `full_text` ≥ 100 tokens each
- `eval_results/axis_projection_v2/lmsys_tail_full.jsonl` — 600 docs, same structure

Total = **1200 candidate docs** drawn from the Lu et al. pool. Per persona, scoring 1200 docs is cheap (~30 s on H100).

**Pool-construction note (v3 addition, Codex Alternatives F).** The 1200 docs above are pre-filtered to EXTREMES of the Qwen-3-32B assistant-axis distribution (top-200 + bot-200 + rand-200 per JSONL). This means our top-K-by-persona-cosine selection draws from a biased sample. To diagnose whether this biases the headline result, we ALSO construct a parallel **random-bucket subset**: the union of the `rand-200` partitions from both JSONLs (400 docs total), which is unbiased w.r.t. the Qwen-3-32B axis. We then run a sensitivity arm (cell P1, villain-C1 only) on top-K from this unbiased subset; compare the top-50 doc identity overlap between extreme-bucket and random-bucket pools per persona, log to `example_pool_meta.json`.

**Step 3 — persona-style pool:** for each persona P, take the **top-50 docs by cos(doc, v_P)** from the FULL 1200-doc extreme-bucket set. These become the few-shot example bank for the main cells. (Defensible default — top-K cosine matches the persona-vector literature for stimulus selection.)

**Step 3b — pool-bias sensitivity (v3 addition).** Also compute top-50 docs by cos(doc, v_villain) from the random-bucket subset (400 docs, the `rand-200` union). Saved to `data/issue_375/example_pool_persona_style_random.jsonl`. Used ONLY for cell P1 (villain-C1 sensitivity arm).

**Step 4 — neutral pool:** for each persona P, take 50 docs with `|cos(doc, v_P)| < 0.05` from the same scored pool. ("Near centroid" = low absolute cosine in either direction.) If fewer than 50 docs qualify, widen the threshold by 0.01 increments until 50 are found, and log the achieved threshold in `data/issue_375/neutral_pool_meta.json`. This is the FLOOR: examples that are not particularly persona-like in EITHER direction.

**Step 5 — assemble examples.** Each doc becomes a single user-turn (the doc as a question / prompt) paired with an assistant turn (generated by the *base* model under that persona's system prompt — same as v3's `generate_convergence_data`):

(a) **Pool-build time fail-loud filter** — before saving any pool JSONL, drop every example whose generated assistant turn (or original user-doc text, for safety) contains the marker. Implementation:

### 4.5 Held-out queries

The body: "the same neutral query distribution Leakage v3 used". The v3 `EVAL_QUESTIONS` const is **20 questions** (lines 103–124 of `scripts/run_leakage_v3.py`) and `DATA_QUESTIONS` is **40 questions** (lines 127–168). **DATA_QUESTIONS were used in v3 training** (`generate_convergence_data`, `generate_deconfounded_marker_data` both iterate over `DATA_QUESTIONS` — fact-checker verdict A16) — so they CANNOT be used as held-out.

200 queries is needed for the paired-bootstrap CI to have ≤ 5pp half-width on a 5% rate. We construct a 200-query held-out set as follows:

1. **Seed = the 20 EVAL_QUESTIONS** (v3 used these for scoring only, NOT for training → safe for held-out eval). **Each query is tagged `"source": "eval_questions"`.**
2. **Add 180 LMSYS-style benign queries** sampled from `eval_results/axis_projection_v2/lmsys_tail_full.jsonl` filtered to short (`token_count < 100`) and clearly question-shaped (regex match on `?$`). These mirror "the same neutral query distribution" — short benign Q&A prompts — while being clearly disjoint from v3 training. **Each query is tagged `"source": "lmsys_tail"`.** Save to `data/issue_375/held_out_queries.jsonl`.
3. **Sanity check:** before launching eval, run the marker scorer on the 200 held-out queries themselves (as user turns to the BASE Qwen2.5-7B-Instruct under the helpful-assistant prompt, NO adapter). The marker should fire 0/200 (or < 1/200). If > 1/200, the query distribution is somehow leaking and we strip the offending queries before re-running.

**Stratified-reporting requirement (v3 addition, RECOVERABLE #7).** Every cell's marker rate MUST be reported in three ways: (a) overall on all 200, (b) restricted to the 20 EVAL_QUESTIONS subset, (c) restricted to the 180 LMSYS-tail subset. Save to `eval_results/issue_375/stratified_by_query_source.json` per cell. The hero figure shows the overall rate; the §11 analyzer notes flag any cell where the LMSYS-tail rate diverges from the EVAL_QUESTIONS rate by > 10pp (signals query-distribution bias).

### 4.6 Few-shot prompt assembly

```python
# In fewshot_prompt.py
def build_prompt(
    examples: list[dict],     # k example dicts with "user"/"assistant"
    held_out_query: str,
    system: str = "You are a helpful assistant.",
) -> list[dict]:
    """Build a chat-template-compatible message list.

    Format:
      [system: helpful assistant]
      [user: example_1.user], [assistant: example_1.assistant]
      [user: example_2.user], [assistant: example_2.assistant]
      ...
      [user: example_k.user], [assistant: example_k.assistant]
      [user: held_out_query]

    The marker fires (or doesn't) on the FINAL assistant turn we generate.
    """
    msgs = [{"role": "system", "content": system}]
    for ex in examples:
        msgs.append({"role": "user", "content": ex["user"]})
        msgs.append({"role": "assistant", "content": ex["assistant"]})
    msgs.append({"role": "user", "content": held_out_query})
    return msgs
```

**Example sampling per query.** For each held-out query, sample `k` examples WITHOUT replacement from the relevant pool (persona-style or neutral OR wrong-persona OR random-bucket-persona-style), seeded by `hash((adapter, persona, condition, k, query)) % 2**32` so the sampling is fully reproducible.

**Wrong-persona pool routing (v3 addition).** For cells W1–W4 (wrong-persona controls), the `pool` argument to `sample_examples` is set to the *non-matching* persona's persona-style pool. The example-assembly is otherwise identical — the only difference is which pool the k=3 examples are drawn from.

**Wrong-persona assignment rationale.** Each clean adapter is paired with a persona pool that is *neither* its own source nor obviously redundant: villain-C1 → librarian (the second-cleanest baseline); villain-expA → sw_eng (cross to a leaking-baseline source pool, which gives the strongest possible "any persona" test); villain-expB-P1 → librarian (same as W1 for consistency); librarian-expA → villain (the *most* baseline-clean persona, since villain's own marker baseline under helpful-assistant is 0%). The pairing is intentionally heterogeneous — if all wrong-persona cells fire at the same rate as matching-persona cells, the hypothesis collapses to "any persona-register few-shot drift triggers the marker"; if wrong-persona cells are null, the persona-specificity claim survives.

**Base-model cells specifically pair the NO-ADAPTER condition with each of the 3 persona-style pools at k=3.** This complements the §4.5 step 3 sanity-floor (which tests the base model on the held-out queries with NO few-shot context): B1/B2/B3 verify the base model stays at ~0% even when prompted with the same persona-style few-shot examples we use for the main cells.

**Total = 10 × 5 + 4 + 3 + 1 = 58 cells × 200 queries × 10 completions = 116,000 generations.**

**k = {0, 1, 3}.** k=0 zero-shot is the most important baseline because it tells us whether the marker leaks at all under helpful-assistant prompting without any in-context drift — for the strict-test cells this directly verifies the < 5% clean-baseline assumption, and for the secondary cells it provides the Δ-baseline. k=5 dropped (compute cost vs marginal information; defer to follow-up if k=1 → k=3 is monotonic).

### 4.9 Statistical test (paired bootstrap)

Per (adapter, persona, condition), compute **three** comparisons:

**(a) Primary (strict): persona-style k-shot vs neutral k-shot at matched k.** Pairing: same query index across the two arms.

**(b) Primary control: persona-style k=3 vs wrong-persona k=3** (clean-baseline adapters only). Pairing: same query index. CI excludes 0 ⇒ persona-specificity claim survives; CI overlaps 0 ⇒ the hypothesis collapses to "any persona-register few-shot drift triggers marker".

**(c) Secondary (Δ-on-baseline): persona-style k-shot vs zero-shot.** Pairing: same query index. This is the Δ-metric for the secondary set; also reported for the clean set as supplementary information.

```python
# In analyze.py
def paired_bootstrap_diff(rates_A, rates_B, n_boot=10_000, seed=42):
    """
    rates_A, rates_B: arrays of length 200, the marker-fire fraction
    (out of 10 completions) per query in each arm.

    Pairing: same query index across the two arrays.
    """
    rng = np.random.default_rng(seed)
    n = len(rates_A)
    diffs = rates_A - rates_B  # paired
    boot_means = []
    for _ in range(n_boot):
        idx = rng.integers(0, n, n)
        boot_means.append(diffs[idx].mean())
    ci_lo, ci_hi = np.percentile(boot_means, [2.5, 97.5])
    return {
        "mean_diff": float(diffs.mean()),
        "ci_95_lo": float(ci_lo),
        "ci_95_hi": float(ci_hi),
        "n": n,
    }
```

CI excludes 0 ⇒ persona-style > neutral (or > wrong-persona, or > zero-shot) at α = 0.05. Stratified versions of each test (on EVAL_QUESTIONS subset, on LMSYS subset) are reported but NOT used for headline confirmation — sample sizes 20 and 180 are too imbalanced for CIs to be directly comparable; they are descriptive only.

### 4.10 Why code, not a model call?

The marker scorer is a fixed regex (case-insensitive substring search for `[ZLT]`) — no semantic judgment needed; Claude judge would be slower, cost dollars, and add non-determinism. The persona-direction extractor is a forward pass and a vector subtraction — model-call equivalent doesn't exist. The example-pool selector is a deterministic top-K over precomputed cosines — model-call equivalent would be "ask Claude to rank documents by persona-likeness", which is exactly the kind of failure-prone semantic-judgment shortcut we want to avoid (we want the geometric definition, not a vibes one). The single place we DO use a model call is in step §4.4-5 (generating the assistant turn for each example), where we use vLLM batched generation on the base model — that IS a model call, just a self-hosted one for cost / batch reasons.

## 6. Success criteria (quantitative)

### Primary (strict test on clean-baseline adapters)

The primary hypothesis is tested ONLY on the 4 clean-baseline adapters: **villain × {C1, expA, expB-P1}** and **librarian × expA**.

**Hypothesis CONFIRMED** iff for **≥ 1 of 4 clean-baseline adapters** ALL of the following hold:
- zero-shot k=0 marker rate < 5% (verifies adapter is genuinely clean in our run — gate), AND
- persona-style k=3 marker rate > 5%, AND
- paired-bootstrap 95% CI for (persona-style k=3 − neutral k=3) excludes 0, AND
- **paired-bootstrap 95% CI for (persona-style k=3 − wrong-persona k=3) excludes 0** (v3 addition: persona-specificity required — rules out "any persona register" generic-drift confound), AND
- **base-model + matching-persona-style k=3 rate < 5%** (v3 addition: B1/B2/B3 must show base model genuinely emits ~0% under the same few-shot prompts — rules out "few-shot examples themselves prime the marker" confound).

(I dropped v1's "≥ 2 of 3 personas" rule because only villain has 3 clean cells; with 4 clean cells the natural threshold is ≥ 1 positive. A stronger headline ("≥ 2 of 4") is reported as a separate "robust" tier but doesn't block confirmation.)

**Hypothesis FALSIFIED** iff for **ALL 4 clean-baseline adapters**:
- paired-bootstrap 95% CI for (persona-style − neutral) overlaps 0 at BOTH k=1 AND k=3.

**Wrong-persona control outcome interpretation.** If wrong-persona k=3 rates are *similar to* (CI overlaps) matching-persona k=3 rates, the hypothesis is downgraded from "persona-style examples elicit the matching marker" to "any persona-register few-shot drift elicits the marker" — a weaker but still interesting finding. The clean-result write-up MUST flag this case explicitly.

**Base-model control outcome interpretation.** If base-model + persona-style k=3 ≥ 5% on any of B1/B2/B3, the confound "few-shot examples prime the marker via the base model's own behavior" is alive and the corresponding adapter result CANNOT be attributed cleanly to the adapter. Flag and demote to descriptive.

**Pool-bias sensitivity outcome interpretation (P1).** If villain-C1 + villain-style-random-bucket k=3 rate differs from villain-C1 + villain-style (axis-extreme) k=3 rate by > 10pp, the headline result is partially pool-construction-driven and the write-up MUST report both rates and note the dependence. If the two rates are within 10pp of each other, the result is robust to pool construction.

### Composite-construct write-up discipline (v3 addition, RECOVERABLE #6)

A confirmed positive under the above means **"persona-style few-shot composite (cosine-selected user docs + persona-voiced assistant turns) elicits the marker"** — NOT "geometric drift in the residual stream caused leakage". The plan operationalizes "persona-style examples" as a composite of selection + generation prompt; the analyzer and clean-result write-up MUST NOT split-claim by attributing the effect to one component alone. (Lens 11 in clean-result-critic — the statistical-framing rule — enforces this downstream.) To attribute the effect to a sub-component (e.g., "the user-doc selection alone is what matters"), a follow-up that varies one component at a time would be needed.

### Stratified-reporting requirement (v3 addition, RECOVERABLE #7)

Every cell's marker rate is reported in §10 stratified by held-out-query source: (a) overall on all 200, (b) on the 20 EVAL_QUESTIONS subset, (c) on the 180 LMSYS-tail subset. The hero figure shows the overall rate; per-cell tables show the three values. Any cell where the LMSYS-tail rate diverges from the EVAL_QUESTIONS rate by > 10pp gets a flag in the §11 analyzer-attention items (signals query-distribution bias). Headline confirmation uses the overall rate; the stratified breakdown is descriptive.

### Secondary (Δ-on-baseline descriptive metric)

The secondary set (sw_eng × {C1, expA, expB-P1} + librarian × {C1, expB-P1}) cannot test the primary hypothesis because the baseline assistant rate already exceeds 5%. For these adapters:

- Report `Δ_persona = rate(persona-style k=3) − rate(zero-shot)` with paired-bootstrap 95% CI on Δ.
- Report `Δ_drift  = rate(persona-style k=3) − rate(neutral k=3)` with paired-bootstrap 95% CI on Δ.
- Both Δs are descriptive: positive Δ_persona = "drift compounds on already-leaking baseline"; positive Δ_drift = "the persona-style structure of the examples, not just the example count, accounts for the lift". **Neither confirms nor refutes the primary hypothesis** — they characterize the leaking regime.

### Sanity gates (must pass BEFORE primary interpretation)

1. **Persona-direction cosine spread (§4.3):** all pairwise cos < 0.95. Hard gate.
2. **Held-out query base-model rate (§4.5 step 3):** marker fires < 1% on base model under helpful-assistant prompt with NO few-shot context. Hard gate.
3. **Adapter-loading reproduction:** zero-shot rates on the 5 secondary adapters reproduce v3 to within ±15pp. Soft gate — failure indicates a rig divergence requiring investigation, not auto-kill.
4. **Clean-baseline reproduction:** zero-shot rates on the 4 clean adapters land < 5% (the assumption that they are clean baselines). Hard gate per-adapter — any cell that fails this gets demoted to secondary.
5. **ZLT contamination gate (v3 addition, §4.4 step 5b):** per-persona pool-build drop rate < 10%; per-cell rendered-prompt scan finds 0 contamination. Hard gate.
6. **Base-model + persona-style k=3 floor (v3 addition, cells B1/B2/B3):** all 3 base-model cells fire marker < 5%. Hard gate per-cell — a cell that fails this kills the corresponding adapter's attribution claim.
