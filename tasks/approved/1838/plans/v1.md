# Plan v1 — #1838: GCP→RunPod failover provision crash-safe (reap-and-recreate residue pod + provision-intent breadcrumb)

`### TDD: no`

## 1. Goal + requirement + acceptance criteria

**Goal (task body, verbatim):** Make the #659 GCP->RunPod async-failover provision leg crash-safe and idempotent: on retry, ADOPT (or tear down and recreate) a pre-existing managed pod-<N> left by an interrupted failover attempt instead of refusing into a no_compute_available terminal, and bound the residue window with a provision-intent breadcrumb before pod creation.

**Requirement.** A poll tick killed mid-RunPod-provision (the #1739 shape: caller's 120 s timeout kills `backend_poll.py` between pod-create and lease/handle write) must not leave the next failover attempt refusing on its own orphan. The retry must (a) recognize the orphan by POSITIVE evidence, (b) terminate it surgically, (c) proceed to a fresh provision in the SAME attempt — no `no_compute_available` terminal minted for our own residue — while (d) NEVER terminating a pod lacking positive our-residue evidence (human-provisioned pods keep today's bias-safe refusal).

**Acceptance criteria:**
1. All new unit tests pass (§ Test plan, ~10 tests); all existing `tests/test_backend_poll.py` #1490 tests (`test_failover_provision_*`, L3620–3924) and `tests/test_router.py::test_lease_round_trip` pass unchanged.
2. Simulated interrupted-attempt scenario (lease intent + in-window orphan pod): retry terminates the orphan and invokes the launch seam — no `no_compute_available`.
3. Negative case (live pod-<N>, no matching intent): NO terminate; today's refusal → `pre-existing` → re-drivable `no_compute_available`, byte-compatible with the #1490 decision table.
4. Breadcrumb is durably on disk BEFORE the launch seam runs (test asserts read-back at fake-launch time).
5. `uv run python scripts/workflow_lint.py` (no flags) passes; `ruff check` clean on touched files.

## 2. Method delta (vs existing #1490 / #1668 machinery)

- **#1490** (`backend_poll.py` L3245–3530: `_live_runpod_ids_for_issue` pre/post snapshots + `_classify_provision_failure` + `_reclaim_failed_runpod_provision`) reclaims ONLY a pod the JUST-FAILED provision created (post−pre singleton + created-then-failed evidence). The "already exists" refusal matches `_PROVISION_REFUSAL_MARKERS` conjunctively → `created-nothing` → outcome `pre-existing` → pod kept + re-drivable terminal. **Delta:** we add attribution for a pod created by a PRIOR killed attempt (which sits in the PRE snapshot with no #1490 attribution) via a durable **provision-intent breadcrumb written BEFORE pod-create**, plus a **proactive pre-provision probe + reap**. #1490 is byte-untouched and remains the backstop for the just-failed-attempt shape and for anything the proactive probe misses (probe failure, concurrent creation).
- **#1668** (wedge-handled sentinel keyed on `runpod_attempt_id`; `_stamp_lease_failover_of` / `_lease_records_failover_of`) records failover identity AFTER a successful launch. **Delta:** the new breadcrumb is the BEFORE-launch sibling, stored in the SAME durable Lease (`~/.eps-routing/issue-<N>.json`) whose docs already name the crash-between-submit-and-lease-write orphan window. No existing field's semantics change.
- **Bounded-once intact:** the exactly-once records (`gcp_failover_of`, wedge/CUDA-IMA fields, sentinels) are stamped only AFTER a successful launch; a killed attempt never stamped, so the reap-then-provision retry IS the "once". The orphan is terminated before its replacement is created → never >1 billing pod from this path.

## 3. Design decisions (the 5 questions)

**Q1 — Breadcrumb form: extend the durable Lease.** New field `Lease.runpod_provision_intent: dict | None` (router.py), shape `{"pod_name": "pod-<N>", "issue": N, "ts": <epoch float>, "token": <uuid4 hex>, "reason": <failover reason>}`. Written via `LeaseStore().transaction(issue)` → `write(lease)` (flocked, atomic tmp+replace) in backend_poll BEFORE the launch seam call — crash-ordered write-before-create. Superseded by ONE line in `router._lease_after_submit` (`lease.runpod_provision_intent = None`): every successful submit (any backend, incl. the #954 partial-launch path at router.py L3317, which also calls `_lease_after_submit`) clears it, since `_lease_after_submit` mutates the passed lease in place (verified L5748–5779 — fields are preserved, so an explicit clear is required). Rationale over a sidecar file: the Lease is the store that already survives `.claude/cache` disk-failure modes (the #659 round-3 rationale), is flocked, and holds the #1668 identity plumbing; `from_json` uses `.get()` so legacy files parse fine.

**Q2 — Reap-and-recreate (a), not adopt (b).** The orphan provably has NO workload: dispatch happens only after `RunPodBackend.launch` returns, and the killed attempt's launch never returned (the #1739 pod had no handle, no workload). Adoption would require reconstructing a RunHandle for a pod whose bootstrap may be half-done and whose pods.conf registration state is unknown — new, fragile machinery. Teardown reuses the exact surgical `terminate_pod(pod_id)` (`runpod_api.py:935`) + `_terminate_error_is_pod_not_found` tolerance the #1490 reclaim already uses, then the existing provision path runs fresh. Cost: ~5–12 min re-provision (create + wait_for_ssh ≤600 s + bootstrap) — cheap vs the alternative's correctness risk; the incident's orphan billed 9+ min before MANUAL termination anyway. Safety argument: we only ever terminate under positive intent-match evidence (Q4), and a never-dispatched pod holds no unpersisted state.

**Q3 — Which legs: one shared helper, two call sites, covering all five async legs.** Verified: dead-GCP (L3598), queue-timeout (L3636), boot-loop (L3688), queue-vanish (L3735) are thin wrappers over `_failover_gcp_to_runpod` (L4082) — ONE insert there covers all four. The wedge (#664) and CUDA-IMA (#775) fresh-pod legs go through `_relaunch_fresh_runpod` (~L2140+), NOT the GCP core — second insert there. Both funnels then call `failover_to_runpod_after_async_workload_crash` → `_runpod_terminal_rung`. We do NOT patch router-side: `src/` never imports `runpod_api` (layering: scripts→src one-way; probe/terminate live in scripts/runpod_api.py), and backend_poll already owns `_live_runpod_ids_for_issue` + the surgical-terminate pattern. Out of scope (documented residual): the SYNC `route()` paths (capacity fallback `auto_fallback_runpod`, sync workload failover) run in `dispatch_issue.py launch` — a foreground command, not a timeout-bounded poll tick; a killed sync launch's refusal keeps today's behavior. The #1596/#1601 on-demand-retry legs provision GCP, not RunPod — untouched.

**Q4 — Proactive probe BEFORE provision (primary); #1490 refusal classification unchanged (backstop).** The refusal-text parse is brittle and fires only after a wasted subprocess; the probe is one GraphQL list call. Residue predicate — ALL conjuncts required (positive evidence, per the hard constraint):
1. Lease exists and carries a parseable `runpod_provision_intent` with `pod_name == f"pod-{issue}"` (malformed/absent → no reap);
2. EXACTLY ONE live non-EXITED pod named exactly `pod-<N>` (suffixed pods excluded; 0 or ≥2 → no reap — ambiguity never terminates, the #1490 stance);
3. That pod's `PodInfo.created_at` (ISO-8601 str, `runpod_api.py:415/427`) parses AND falls in `[intent.ts − SKEW, intent.ts + WINDOW]` (`SKEW=120 s`, `WINDOW=3600 s`, § 11) — a pod created before the intent, long after it, or with missing/unparseable `created_at` is NOT our residue → keep.
Every failure branch (probe returns None, no lease, no match) degrades to today's exact behavior. A matched reap logs loudly, and the GCP core merges `{"interrupted_provision_residue_reaped": {pod_id, intent_ts, created_at}}` into the seam's `extra_evidence` so the `epm:backend-selected` marker records it (the wedge path logs only — no `extra_evidence` param there).

**Q5 — Retry semantics.** After a successful reap the SAME attempt proceeds directly to provision (no new terminal, no extra tick). If the terminate raises: POD_NOT_FOUND-class (`_terminate_error_is_pod_not_found`) counts as reaped (already gone) → proceed; any other error → log + proceed WITHOUT reap — the provision then refuses on the still-live pod and the #1490 classifier yields today's re-drivable `no_compute_available` (degrade path, never crash the poll). The helper NEVER raises (top-level try/except → no-reap, mirroring `_reclaim_failed_runpod_provision`'s never-raise contract).

## 11. Grounding (load-bearing constants)

- `RUNPOD_PROVISION_INTENT_WINDOW_SEC = 3600` — Source: reasoned from in-file constants + incident timing: the killed attempt's pod-create landed ≤~5 min after the failover fired (#1739: failover 20:08–20:10Z, pod live at 20:12Z), and the provision subprocess's own bounded waits are `wait_for_ssh(timeout=600)` (pod_lifecycle.py L1891) + the exit-75 capacity-wait per-process budget; 3600 s is a ≥6× margin over the observed create latency while still excluding a human provision hours later. Env-overridable; too-small degrades to today's behavior (safe), too-large only matters in the narrow same-name-human-provision-in-window race. Marked: partially grounded — the exact value is a margin choice, not literature-pinned.
- `_PROVISION_INTENT_CLOCK_SKEW_SEC = 120` — Source: the VM↔RunPod-API `createdAt` clocks are independent; 120 s matches the poll caller's timeout scale and generously covers NTP skew. Ungrounded beyond that reasoning — needs no smoke (both failure directions bias-safe: skew too small → no reap → today's behavior).
- Refusal markers / terminate tolerance — Source: `scripts/backend_poll.py` L3289 (`_PROVISION_REFUSAL_MARKERS`), L3368 (`_terminate_error_is_pod_not_found`), reused verbatim.
