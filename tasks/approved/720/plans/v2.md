## 0. Plan Summary

**Workflow-fix (`kind: infra`).** No model, no GPU, no behavioral construct.
A completed autonomous `/issue --auto` session today lingers as a "running"
ghost for up to ~12h because the moment its task hits a terminal status
(`completed`/`archived`/`awaiting_promotion`) the crash-recovery pass DELETES
`~/.eps-autonomous/issue-<N>.json`, which UNMAPS the session, dropping it out
of the 2h terminal-reconcile pass and into the generic 12h idle-unmapped
bucket. **Fix (chosen = body option 2, watcher-side):** at the instant the
respawn pass deletes `issue-<N>.json` for a TERMINAL task, write a small
durable breadcrumb `~/.eps-autonomous/last-mapped-terminal-<sid>.json`
recording `{happy_session_id, issue, terminal_status, recorded_at}`; the
idle-unmapped pass reads that breadcrumb and, for a session whose last-known
mapped task is terminal, applies a SHORT reap window (`LAST_MAPPED_TERMINAL_REAP_S
= 30 min`) instead of the 12h `UNMAPPED_IDLE_REAP_S` — but ONLY after two new
lazy protected-class guards (running managed pod for the breadcrumb's issue;
live same-issue follow-up) both clear. Every existing idle-unmapped exclusion
(live-user TTY, missing-signal → fail-toward-keep, ≥2-miss) is preserved
unchanged; the short window only narrows WHEN an already-reapable, unprotected
session gets reaped.

- **Baselines / controls:** the six acceptance scenarios in §5 (completed →
  reaped < 1h; active / TTY / live-follow-up / running-pod / `keep-running` →

- **Loss surface:** N/A — no model training

## 1. Goal

Completed-task autonomous `/issue --auto` sessions get reaped within ~1h of
the task reaching a terminal/park state (`completed`/`awaiting_promotion`/
`archived`/`blocked`), not the current ~12h, with no manual sweep — while
every existing exclusion (live user TTY, running pod, `keep-running` tag,
live same-issue follow-up, non-terminal task) stays untouched.

### 4.1 New constant + env helper (near the idle-unmapped block, ~line 9928)

```python
# Short reap window for an UNMAPPED session whose LAST-known mapped task was
# TERMINAL (the #720 ghost class: issue-<N>.json deleted by the respawn pass
# at terminal -> session unmapped -> previously only the 12h bucket caught it).
# 30 min keeps the post-terminal session clear of any same-tick promotion/
# finalize activity (which resets the idle clock anyway) while landing the
# worst-case reap STRICTLY under the body's ~1h acceptance window: with the
# 10-min cron and the existing >=2-consecutive-miss guard, worst-case reap is
# 30 min + 2*10 min = 50 min < 60 min (see §11 + the arithmetic-bound test in
# §6). Override via EPM_LAST_MAPPED_TERMINAL_REAP_S.
LAST_MAPPED_TERMINAL_REAP_S = 30 * 60

# Filename prefix for the per-session "last mapped task was terminal"
# breadcrumb at ~/.eps-autonomous/last-mapped-terminal-<sid>.json. Written by
# the respawn pass at the instant it deletes issue-<N>.json for a TERMINAL
# task; read by the idle-unmapped pass to pick the short reap window.
LAST_MAPPED_TERMINAL_PREFIX = "last-mapped-terminal-"


def _last_mapped_terminal_reap_s() -> float:
    """Short reap window (s): EPM_LAST_MAPPED_TERMINAL_REAP_S when set to a
    positive number, else LAST_MAPPED_TERMINAL_REAP_S (30 min). Garbled /
    non-positive falls back (same parse as _unmapped_idle_reap_s)."""
    raw = os.environ.get("EPM_LAST_MAPPED_TERMINAL_REAP_S", "")
    try:
        val = float(raw)
    except ValueError:
        return LAST_MAPPED_TERMINAL_REAP_S
    return val if val > 0 else LAST_MAPPED_TERMINAL_REAP_S
```

### 4.2 Breadcrumb read/write + GC helpers (near the idle-unmapped state helpers, ~line 10477)

```python
def _last_mapped_terminal_path(sid: str) -> Path:
    return AUTONOMOUS_REGISTRY_DIR / f"{LAST_MAPPED_TERMINAL_PREFIX}{sid}.json"


def _record_last_mapped_terminal(
    sid: str, issue: int, terminal_status: str, dry_run: bool, now: float | None = None
) -> None:
    """Write the #720 breadcrumb atomically (temp + rename). Idempotent: a
    re-write for an already-recorded sid just refreshes the fields. Fail-soft:
    an OSError on write is logged and swallowed (the breadcrumb is an
    OPTIMIZATION — a missing one only means the session reaps at the old 12h
    window, never a wrong kill). Skipped under dry_run."""
    if dry_run:
        return
    AUTONOMOUS_REGISTRY_DIR.mkdir(parents=True, exist_ok=True)
    payload = {
        "happy_session_id": sid,
        "issue": issue,
        "terminal_status": terminal_status,
        "recorded_at": now if now is not None else time.time(),
    }
    dest = _last_mapped_terminal_path(sid)
    tmp = dest.with_suffix(".json.tmp")
    try:
        tmp.write_text(json.dumps(payload, indent=2))
        tmp.replace(dest)
    except OSError as e:
        print(f"  last-mapped-terminal: write failed for {sid}: {e}", file=sys.stderr)


def _last_mapped_terminal(sid: str) -> tuple[str, int] | None:
    """The recorded ``(terminal_status, issue)`` for sid, or None (no breadcrumb
    / garbled / not a terminal status / no int issue). Validates the recorded
    status against TERMINAL so a stale/garbled value can never widen scope, and
    surfaces the recorded ``issue`` so the consumer can run the running-pod +
    live-follow-up protected-class guards (MF-1) without a session->issue
    mapping it no longer has."""
    path = _last_mapped_terminal_path(sid)
    if not path.is_file():
        return None
    try:
        data = json.loads(path.read_text())
    except (json.JSONDecodeError, OSError):
        return None
    if not isinstance(data, dict):
        return None
    status = data.get("terminal_status")
    issue = data.get("issue")
    if status in TERMINAL and isinstance(issue, int):
        return (status, issue)
    return None


def _gc_orphan_last_mapped_terminal(live_sids: set[str], dry_run: bool) -> None:
    """Drop breadcrumbs whose session is no longer live (reaped, or the user
    promoted + the session ended). Called once per daemon-reachable tick from
    idle_unmapped_pass, mirroring _gc_orphan_idle_unmapped_state."""
    for path in AUTONOMOUS_REGISTRY_DIR.glob(f"{LAST_MAPPED_TERMINAL_PREFIX}*.json"):
        sid = path.name[len(LAST_MAPPED_TERMINAL_PREFIX):-len(".json")]
        if sid not in live_sids and not dry_run:
            path.unlink(missing_ok=True)
```

> **v2 change:** the v1 `_last_mapped_terminal_status(sid) -> str | None` helper
> is replaced by `_last_mapped_terminal(sid) -> (status, issue) | None` so the
> breadcrumb's recorded `issue` is available to the MF-1 guards. The recorded
> `issue` is exactly the issue the session was driving when it went terminal —
> it is the correct key for both the running-pod check (`pod-<issue>`) and the
> live-follow-up check (`_task_followup_active(issue)`).

### 4.3 Write the breadcrumb in the respawn pass (`_process_entry`, line 12726)

`_process_entry` already has `entry` (carrying `issue` + `happy_session_id`)
and `status` in scope at the `action == "delete"` branch. Amend ONLY the

```python
    if action == "delete":
        # #720: before unmapping, drop the breadcrumb so the idle-unmapped
        # pass can reap this now-unmapped session on the SHORT window. Only
        # for the live session we just observed (sid present + in live_ids);

        sid = entry.get("happy_session_id")
```

`completed`, `archived` all flow through `decide()` → `"delete"` → this branch,
so all three terminal states are covered. (`blocked` is PARK → never deleted →

needed for `blocked`, and `_last_mapped_terminal` returns None for it anyway
since `blocked` ∉ `TERMINAL`.)

### 4.4 Consume the breadcrumb in the idle-unmapped pass — WITH the MF-1 protected-class guards

The surgical edit in `_process_idle_unmapped` (line 10841) sits AFTER the
existing `idle_reap_s = _unmapped_idle_reap_s()` (line 10893) and BEFORE the
#695 fallback block (line 10895), so a recorded-terminal session still gets the
short window on the primary transcript path. **The short window is applied only
after BOTH MF-1 guards clear**:

```python
    idle_reap_s = _unmapped_idle_reap_s()

    # ── #720 short reap window (the completed-/parked-session ghost class) ────
    # An unmapped session whose LAST-known mapped task was TERMINAL is a
    # finished autonomous /issue session, not a generic abandoned chat session,
    # so it earns the SHORT reap window (default 30 min) instead of 12h. The
    # breadcrumb read is one IO call, taken ONLY when present.
    #
    # The two PROTECTED-CLASS guards below (MF-1) FAIL TOWARD KEEP — retaining
    # the 12h window, NOT applying the short window — when the recorded issue
    # still has work in flight. Without them, narrowing the window 12h -> 30 min
    # on the PRIMARY path would expose (a) a still-RUNNING pod on a session that
    # has gone quiet > 30 min mid-work, and (b) a live same-issue follow-up that
    # has not yet re-registered issue-<N>.json (register-current fires only after
    # set-status followups_running). Both guards are LAZY: invoked only when the
    # terminal breadcrumb is present, so the pod-API snapshot + the per-task
    # events fetch are paid only for a genuinely-finished candidate, not every
    # tick. Mapped sessions never reach this (the breadcrumb is read only in the
    # unmapped branch).
    short_window = False
    if not mapped and not has_tty:
        crumb = _last_mapped_terminal(sid)
        if crumb is not None:
            _term_status, crumb_issue = crumb
            # Guard 1: running managed pod for the breadcrumb's issue.
            # _running_managed_issue_pods returns None on a FAILED snapshot
            # (uncertain -> KEEP the long window), [] for no pods, or 4-tuples
            # (issue, pod_id, pod_name, info). Reuses the same helper the #695
            # fallback gate 4 uses (line 10731) — not reimplemented.
            running = _running_managed_issue_pods(caller="idle-unmapped-720")
            pod_uncertain_or_present = running is None or any(
                t[0] == crumb_issue for t in running
            )
            # Guard 2: live same-issue follow-up newer than the latest
            # done-transition (the existing tested predicate, line 2292).
            followup_active = _task_followup_active(crumb_issue)
            if not pod_uncertain_or_present and not followup_active:
                idle_reap_s = min(idle_reap_s, _last_mapped_terminal_reap_s())
                short_window = True
```

Notes:
- The `min(...)` is defensive: it can only ever SHORTEN, never lengthen, the
  window even if an operator set `EPM_UNMAPPED_IDLE_REAP_S` below 30 min.
- **Guard-1 fail-toward-keep:** `running is None` (API transport error) is
  treated as "uncertain → keep the long window," matching the `None`-is-keep
  posture `_running_managed_issue_pods`'s own docstring documents for the
  pod-safety pass. Only a definitively-empty-or-issue-absent RUNNING set
  (`running == []` or no tuple with `t[0] == crumb_issue`) permits the short
  window.
- **Guard-2 closes the `register-current` timing window** the Methodology lens
  flagged (non-blocking concern 1): `_task_followup_active` works on the marker
  signal (`epm:run-launched` / `epm:followup-scope` newer than the latest
  done-transition), NOT on whether `register-current` has re-written
  `issue-<N>.json`. So a follow-up that posted its scope/launch marker but has
  not yet re-mapped the session is still caught.
- The `source_label` print (line 10929) gains `" window=short-terminal"` when
  `short_window` for observability.
- The #695 fallback block stays unchanged: if the primary transcript signal is
  unavailable it still falls back to tmux activity at the (longer) fallback
  window — a recorded-terminal session with no resolvable transcript is the
  rare case, and keeping it on the conservative fallback window is the right
  fail-toward-keep posture.

**No protected-class guard is REMOVED, and two are ADDED.** The short window is
applied strictly AFTER `not mapped and not has_tty`, AFTER the two new
fail-toward-keep guards, and `decide_idle_unmapped` still enforces:
`idle_age_s is None → ("skip", missed)` (transcript unresolvable → keep), the
`< idle_reap_s → ("clear", 0)` recency check (activity-based clear — line
10465; the Methodology lens's non-blocking concern 2, already structurally
present), and the ≥2-miss guard.

> **Why the v1 implicit "re-mapping excludes it" reasoning was insufficient
> (MF-1).** v1 argued a live follow-up / running-pod revival RE-REGISTERS
> `issue-<N>.json` → `mapped=True` → the short window is never reached. That is
> true ONCE the re-registration has happened, but it races: `register-current`
> fires in the same-issue follow-up loop only AFTER `set-status
> followups_running` (loop step 2), and a running pod can outlive the terminal
> flip on a `keep-running`-untagged session before any revival re-maps it.
> Between the terminal flip (breadcrumb written) and the re-mapping, the session
> is unmapped WITH a terminal breadcrumb — exactly where the short window would
> otherwise fire. The two explicit guards close that race; they do not depend on
> re-mapping timing.

### Why not edit `spawn_session.py`?

The body lists `spawn_session.py` as the registry write site, but the cleanest
breadcrumb-write site is the watcher's `_process_entry` (the exact line that
deletes the registry and unmaps the session — it already holds `entry` +

breadcrumb all inside one file (`autonomous_session_watch.py`), avoids adding a
new on-disk record to `spawn_session.py`'s registration path (which the
dashboard + `cmd_list` + `_load_session_issue_map` read), and means NO public
`spawn_session.py` CLI/record-shape change → `architectural: false`. The
breadcrumb file uses a NEW prefix (`last-mapped-terminal-`) that is NOT matched
by the watcher's `issue-*.json` respawn glob (line 12511) nor by
`_load_session_issue_map`'s explicit prefix list
(`("issue-", "manual-issue-", "campaign-")`, spawn_session.py line 299), so it
can never be mistaken for a respawnable registration.

## 5. Conditions and Controls (acceptance scenarios)

N/A for an infra change in the experimental sense; instead the six scenarios
that prove acceptance (each becomes a test in §6):

| Plain-English name | What it asserts | What it controls for | Test seam |
|---|---|---|---|
| Completed → reaped < 1h | unmapped session, breadcrumb=`completed`, idle 35 min, ≥2 misses, no pod, no follow-up → `("stop", 0)` | the ghost class is reaped on the short window | `decide_idle_unmapped` + `idle_unmapped_pass` |
| Active session untouched | mapped (registry present) OR breadcrumb absent + idle < 12h → not stopped | never reap a live in-flight session | `idle_unmapped_pass` |
| TTY-attached session untouched | `has_tty=True` → `("clear", 0)` regardless of breadcrumb | a user sitting at the terminal | `decide_idle_unmapped` / `_is_live_user_tty` |
| Live follow-up untouched | breadcrumb present BUT `_task_followup_active(issue)`=True → short window NOT applied → 12h retained → not stopped on the short window | a `followups_running` / fresh `epm:run-launched` round, BEFORE re-mapping | `idle_unmapped_pass` (Guard 2) |
| Running-pod session untouched | breadcrumb present BUT `_running_managed_issue_pods` reports a RUNNING pod for the issue → short window NOT applied → 12h retained → not stopped on the short window | a still-billing pod that outlived the terminal flip | `idle_unmapped_pass` (Guard 1) |
| `keep-running` untouched | task tagged `keep-running` stays at a non-terminal status (no terminal transition → no breadcrumb written); even if its pod outlives a later terminal flip, Guard 1 keeps it | the explicit user override | breadcrumb-write guard + Guard 1 |

Control logic for the last three: the short window is ONLY applied for a
session that (a) is unmapped AND (b) has a terminal breadcrumb AND (c) has no
live-user TTY AND (d) has NO running managed pod for the recorded issue
(Guard 1, fail-toward-keep on `None`) AND (e) has NO live same-issue follow-up
(Guard 2). A live follow-up or a still-billing pod retains the 12h window; the
breadcrumb only ever shortens a genuinely finished, genuinely unmapped,
genuinely unprotected session.

## 13. Kill criterion

This approach is wrong if the short-window reap CANNOT be made to leave
protected sessions untouched — concretely:
- If `awaiting_promotion` sessions are the dominant breadcrumb class AND users
  routinely promote 30 min-2h after the park WITHOUT generating transcript
  activity or holding a TTY, the 30-min window would reap a session the user
  still wants. **Test of the kill criterion:** if `_is_live_user_tty` /
  transcript-idle do NOT reliably distinguish "user reading the draft" from
  "abandoned," the fix would need to EXCLUDE `awaiting_promotion` from the short
  window (only short-reap `completed`/`archived`, leaving `awaiting_promotion`
  on the 12h window). The breadcrumb already records `terminal_status`, so this
  narrowing is a one-line change (`_last_mapped_terminal` already returns the
  status, so the consumer checks `status in {"completed", "archived"}`); the
  plan keeps the full `terminal_status` in the breadcrumb precisely so this
  fallback is cheap if review/usage flags it.
- (Why option 3 was rejected, recorded here as the contrast): a SKILL.md
  self-exit at `awaiting_promotion` races the user's promotion turn — the
  SKILL.md design explicitly has the session "idle until the user taps in via
  the relay to drive the next step" (SKILL.md § Stop the tick cron / In-session
  PushNotification). A self-exit there would kill the session the user is meant
  to promote in. Self-exit also does nothing for a session that died mid-stream
  (the exact ghost class) or for the legacy ghosts where the mapping is already
  lost — so the watcher must remain the backstop regardless, which is what this
  plan builds directly.
