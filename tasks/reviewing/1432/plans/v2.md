**The exact proposed entry text (paste-and-adjust; one bullet, one paragraph, house style):**

```markdown
- **cuda `torch.linalg.eigh` (cuSOLVER syevd) raises `torch.linalg.LinAlgError` ("The algorithm failed to converge because the input matrix is ill-conditioned or has too many repeated eigenvalues") on near-singular / repeated-eigenvalue Grams that CPU LAPACK decomposes fine — wrap every data-derived-Gram eigh site in a CPU-fallback helper; do NOT jitter the Gram.** A documented upstream class, not a repo bug (pytorch/pytorch#94772, #105359 — GPU eigh fails where CPU succeeds; #159741 carries this exact error string): cuSOLVER's syevd is less robust than CPU LAPACK on ill-conditioned symmetric inputs. CUDA-numerics sibling of the fp32 TF32 kernel-parity entry above — there two kernel paths give DIFFERENT numbers with correct math; here the cuda path FAILS outright and CPU is the correct backend for the same decomposition. Trigger regime: SMALL subsampled / group-split fold Grams with near-duplicate rows — a run can pass thousands of larger full-lane eigh calls cleanly, then die at matched-n subsampling (#1335: the matched-n inner-group-CV fold Gram — n_min=1739 subsample, inner-train blocks of a 4-fold group split — exactly the near-singular regime the inner-group-CV selection targets). Diagnostic signature: `torch._C._LinAlgError` from a cuda `linalg.eigh` deep in a per-fold/per-cell fit loop, on a matrix that decomposes cleanly once moved to CPU. RULE: wrap the site — `try: torch.linalg.eigh(G)` / `except torch.linalg.LinAlgError:` → `torch.linalg.eigh(G.cpu())`, move `w, V` back to `G.device`, one-line print naming device + n — an exact numerical-backend swap, NOT a semantic change (same matrix, same decomposition; eigenvalues and the rotation-invariant ridge/spectral reads downstream agree to fp roundoff — eigenvector bases within degenerate eigenspaces are backend-non-unique, which those reads don't see); per the long-form twin, the same fallback shape applies to a cuda `linalg.svd` site hitting the analogous non-convergence. Do NOT add a jitter/ridge epsilon to the Gram instead — that changes the eigenvalues every downstream λ-scan and R² read consumes. A Gram that fails on CPU too is genuinely pathological input (NaN/inf contamination, unsupported dtype) — let it raise; do not chain further fallbacks. Exposure: 47 repo files call `linalg.eigh` (grep 2026-07-16), many on data-derived Grams — any per-fold ridge / spectral / CKA pipeline is in the class. Canonical implementation: `scripts/issue825_fit_cells.py::_eigh_robust` (commit `d1922d2068` on the `issue-1335` branch, landing on main with #1335's merge; the Step-10d rebase-merge may rewrite branch SHAs — durable anchors: the file path + incident #1335). Long-form agent-memory sibling (implementer-scoped): `.claude/agent-memory/experiment-implementer/feedback_cusolver_eigh_nonconvergence_cpu_fallback.md` — this entry generalizes it to every agent that writes or debugs Gram-eigh analysis code. (Incident #1335 attempt 8, 2026-07-16T17:55Z: `issue825_fit_cells.py::_prep_inner_lambda`'s cuda eigh failed to converge on a matched-n subsampled inner-fold Gram, killing the instruct matched lane after the SAME code had run thousands of larger full-lane eigh calls; fixed by `_eigh_robust` in the r10 crash-fix round.)
```
