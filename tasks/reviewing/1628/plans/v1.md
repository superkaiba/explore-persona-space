## 3. Hypothesis / acceptance criteria

Infra task — the "hypothesis" is a set of mechanical acceptance criteria:

1. **Queued fast path:** teardown of an instance whose pre-delete describe reads `status == "PENDING"` issues an `--async` delete and returns within ~3 gcloud calls (seconds), never blocking on the DWS cancel, when the delete operation is verifiably issued (async rc==0, or the in-flight stderr class).
2. **Never skip a delete:** every teardown path either (i) confirms the instance absent (404), (ii) positively confirms a delete operation issued (async rc==0 / in-flight stderr) before any fast return, or (iii) raises `GcpBackendError` loudly. There is no silent return without one of (i)/(ii). The async-errored case falls back to the synchronous delete (the #1586 "--async errored" shape can never strand an undeleted instance silently).
3. **Timeout no longer escapes:** a `subprocess.TimeoutExpired` from the synchronous delete is caught inside teardown and escalated to async-re-issue + bounded existence poll; exhaustion raises `GcpBackendError` (so `dispatch_issue.py finalize` gets a classified error instead of a raw traceback, and the failover core's `except Exception` continues to degrade it to the janitor backstop).
4. **Regression:** non-PENDING teardown semantics unchanged — rc==0 → `_confirm_deleted` (#683 guard verbatim), "was not found" → success, other errors → raise; `render_delete_argv` default output byte-identical.
5. **Bounded worst case:** the verify poll is monotonic-deadline-bounded at `GCLOUD_DELETE_VERIFY_BUDGET_SEC` (300 s); every subprocess call is individually capped at 300 s; stated ceilings in §9.

All five are pinned by named pytest nodes (§6).

```python
def render_delete_argv(
    *, config: GcpConfig, name: str, zone: str, async_: bool = False
) -> list[str]:
    """Build a ``gcloud compute instances delete`` argv (``--quiet`` non-interactive).

    ``async_=True`` appends ``--async`` (#1628): gcloud then returns as soon as
    the server ACCEPTS the delete operation instead of waiting for completion —
    the DWS-queued (PENDING) cancel path, where completion is the slow part
    (~10 min observed, #1586) and acceptance is seconds.
    """
    argv = _base_gcloud_argv(config, "compute", "instances", "delete", name)
    argv += [f"--zone={zone}", "--quiet"]
    if async_:
        argv.append("--async")
    return argv
```

Default-`False` call sites are byte-identical (existing argv test at tests/test_gcp_backend.py:4242 unaffected).

### 4-C. `GcpBackend.teardown` becomes PENDING-aware (gcp.py:6875)

```python
def teardown(self, handle: RunHandle) -> None:
    config = self._config
    zone = handle.extra.get("zone") or config.primary_zone
    # (1) PENDING probe — one cheap describe. ANY anomaly (probe error, 404,
    #     unparseable, absent/other status) falls through to the sync path
    #     (fail-open: byte-equivalent to today's behavior).
    status = self._pre_delete_status(handle, zone)
    if status == "PENDING":
        logger.warning(
            "GCP teardown: %s is DWS-queued (PENDING); using async delete + "
            "bounded verify so the caller is not serialized behind the slow "
            "DWS cancel (#1628/#1586).", handle.pod_name,
        )
        if self._teardown_pending_async(handle, zone):
            return
        # async delete could not confirm issuance -> NEVER skip: fall through
        # to the synchronous delete below (the #1586 "--async errored" shape).
    # (2) Synchronous delete — unchanged semantics + a NEW timeout catch.
    argv = render_delete_argv(config=config, name=handle.pod_name, zone=zone)
    try:
        result = self._run(argv)
    except subprocess.TimeoutExpired:
        logger.warning(
            "GCP teardown: delete of %s exceeded the %ds subprocess cap "
            "(slow-cancel signature, #1586); escalating to async re-issue + "
            "bounded existence verify.", handle.pod_name, GCLOUD_DEFAULT_TIMEOUT_SEC,
        )
        self._escalate_slow_delete(handle, zone)
        return
    if result.returncode == 0:
        self._confirm_deleted(handle, zone)          # #683 guard, untouched
        return
    stderr_low = (result.stderr or "").lower()
    if "was not found" in stderr_low or "404" in stderr_low:
        logger.info(...)                              # unchanged idempotency
        return
    if any(m in stderr_low for m in _DELETE_IN_FLIGHT_STDERR_MARKERS):
        # A delete/op already in flight (concurrent janitor/finalize, or our
        # own async attempt) — verify instead of raising (#1628).
        self._verify_delete_landed(handle, zone, issuance_confirmed=True)
        return
    raise GcpBackendError(...)                        # unchanged loud failure
```

### 4-D. `_pre_delete_status` (new helper)

```python
def _pre_delete_status(self, handle: RunHandle, zone: str) -> str | None:
    """One describe; the instance's status, or None on ANY anomaly (fail-open)."""
    try:
        probe = self._run(render_describe_argv(config=self._config,
                                               name=handle.pod_name, zone=zone))
    except Exception:                                  # incl. TimeoutExpired
        return None
    if probe.returncode != 0 or not probe.stdout.strip():
        return None
    try:
        payload = json.loads(probe.stdout)
    except json.JSONDecodeError:
        return None
    status = (payload.get("status") or "").upper()
    return status or None
```

A pre-describe 404 deliberately returns `None` → the sync delete still runs and lands on the existing "was not found" success branch — this keeps the missing-VM semantics identical (no new transient-404-skips-the-delete residual; cf. the #1116 flicker residual).

### 4-E. `_teardown_pending_async` (new helper) — fire-and-verify

```python
def _teardown_pending_async(self, handle: RunHandle, zone: str) -> bool:
    """Async delete of a DWS-queued instance. True = handled; False = fall back to sync."""
    try:
        result = self._run(render_delete_argv(config=self._config,
                                              name=handle.pod_name, zone=zone,
                                              async_=True))
    except subprocess.TimeoutExpired:
        # Even op-creation timed out (pathological) — issuance UNCONFIRMED.
        self._verify_delete_landed(handle, zone, issuance_confirmed=False)
        return True
    stderr_low = (result.stderr or "").lower()
    if "was not found" in stderr_low or "404" in stderr_low:
        return True                                    # already gone
    if result.returncode == 0 or any(
        m in stderr_low for m in _DELETE_IN_FLIGHT_STDERR_MARKERS
    ):
        # Delete operation ACCEPTED (or already in flight) — positive issuance.
        self._verify_delete_landed(handle, zone, issuance_confirmed=True)
        return True
    logger.warning(
        "GCP teardown: --async delete of %s errored (rc=%d): %s — falling back "
        "to the synchronous delete (#1586 '--async errored' shape).",
        handle.pod_name, result.returncode, (result.stderr or "")[:300],
    )
    return False
```

### 4-F. `_escalate_slow_delete` + `_verify_delete_landed` (new helpers)

```python
def _escalate_slow_delete(self, handle: RunHandle, zone: str) -> None:
    """Post-TimeoutExpired: re-issue --async to positively confirm issuance, then verify."""
    issuance = False
    try:
        r = self._run(render_delete_argv(config=self._config,
                                         name=handle.pod_name, zone=zone, async_=True))
        low = (r.stderr or "").lower()
        if "was not found" in low or "404" in low:
            return                                     # the timed-out delete landed
        issuance = r.returncode == 0 or any(
            m in low for m in _DELETE_IN_FLIGHT_STDERR_MARKERS)
    except subprocess.TimeoutExpired:
        pass                                           # issuance stays unconfirmed
    self._verify_delete_landed(handle, zone, issuance_confirmed=issuance)

def _verify_delete_landed(self, handle, zone, *, issuance_confirmed: bool) -> None:
    """Bounded existence poll: 404 -> success; PENDING+issued -> fast in-flight
    return; deadline exhausted -> loud GcpBackendError. Never returns silently."""
    budget = _delete_verify_budget_sec()
    poll = _delete_verify_poll_sec()
    deadline = time.monotonic() + budget
    last_status: str | None = None
    while True:
        probe = self._run(render_describe_argv(...))   # each call has its own 300s cap
        low = (probe.stderr or "").lower()
        if probe.returncode != 0 and ("was not found" in low or "404" in low):
            logger.info("GCP teardown: %s confirmed deleted.", handle.pod_name)
            return
        if probe.returncode == 0 and probe.stdout.strip():
            try:
                last_status = (json.loads(probe.stdout).get("status") or "").upper() or last_status
            except json.JSONDecodeError:
                pass
            if last_status == "PENDING" and issuance_confirmed:
                logger.warning(
                    "GCP teardown: delete of DWS-queued %s is issued and in flight "
                    "server-side; NOT blocking the caller on the slow DWS cancel "
                    "(queued instances bill no GPU; backstops: gcp_audit janitor + "
                    "--max-run-duration fence). (#1628)", handle.pod_name,
                )
                return                                  # the pivot-unblocking fast return
        if time.monotonic() >= deadline:
            raise GcpBackendError(
                f"gcloud delete of {handle.pod_name} did not confirm within "
                f"{budget}s (last_status={last_status!r}, "
                f"issuance_confirmed={issuance_confirmed}); gcp_audit janitor + "
                f"--max-run-duration fence remain the backstops"
            )
        time.sleep(poll)
```

Notes: (i) the fast return fires only with BOTH `PENDING` status AND positive issuance — an unconfirmed-issuance PENDING instance polls to the deadline and raises (never a silent skip); (ii) a non-PENDING status (RUNNING/STAGING = billing, STOPPING/TERMINATED = shutdown transient) polls to 404 or the deadline; (iii) the deadline is checked on `time.monotonic()`, so slow individual probes cannot unbound the loop (single-probe overshoot ≤ 300 s, stated in §9); (iv) teardown docstring (gcp.py:6876-6900) updated to document the PENDING branch + escalation.

## 11. Decision Rationale

- N/A — no model training (no training hyperparameters).

1. **Mechanism = hybrid (c): PENDING pre-probe → async fire-and-verify; TimeoutExpired escalation on the sync path.** Why: a "longer subprocess timeout" (a) alone is impossible to thread cleanly (the injectable `GcloudRunner` type is argv-only, gcp.py:3733 — special-casing `default_gcloud_runner` would fork test/production behavior) and still serializes the caller for the full longer wait; pure async (b) alone is defeated by the recorded "--async errored". The hybrid detects PENDING explicitly (the Goal's wording), unblocks in seconds, and keeps the sync path as fallback + safety net. Source: #1586 (incident measurements) + gcloud SDK `--async` semantics (https://docs.cloud.google.com/sdk/gcloud/reference/compute/instances/delete) + the #736 in-repo TimeoutExpired-catch precedent (gcp.py:5247-5307).
2. **`GCLOUD_DELETE_VERIFY_BUDGET_SEC = 300`.** The #1586 cancel completed within ~10 min of the first attempt; the first sync delete's 300 s cap + this 300 s budget span that window, and 300 matches the established `GCLOUD_DEFAULT_TIMEOUT_SEC` precedent. Source: #1586; #736 (gcp.py:3741).
3. **`GCLOUD_DELETE_VERIFY_POLL_SEC = 20`.** Describe is ~2 s; 20 s gives ≤15 probes/budget, in the same granularity class as the #669/#783 poller clocks. Source: #783 (`backend_poll` clock family); env-tunable so mis-sizing is a knob, not a code change.
4. **In-flight stderr markers `("is not ready", "being deleted")`, substring/lowercase.** GCE returns "not ready"-class errors for operations on a resource with an in-flight operation; matching conservatively and failing toward today's behavior on a miss. Source: GCP troubleshooting docs (https://cloud.google.com/compute/docs/troubleshooting/troubleshooting-vm-creation) + #1586 ("--async errored" during an in-flight cancel — best-supported reading).
5. **Fast return on PENDING + confirmed issuance (pivot proceeds before 404).** A queued flex-start instance is not provisioned, so it bills no GPU while queued (Source: DWS pricing, https://cloud.google.com/products/dws/pricing); the delete op is positively accepted; the failover core ALREADY proceeds on teardown failure today with weaker evidence (backend_poll.py:3895-3905), and three backstops remain (janitor, `--max-run-duration` fence, the raise-on-exhaustion for every non-PENDING state). Decision: safe — the residual (accepted-then-failed delete op) is named in §8 and strictly narrower than the status quo.
6. **Env knobs read at call time via private readers.** Source: `backend_poll._gcp_queue_wait_seconds` pattern (#783) — retune without restart, malformed values fall back.
7. **No `backends/base.py` signature change; no backend_poll change.** Keeps the fix at the one seam every caller shares; avoids a public-contract (architectural) change. Source: task body invariant list + `.claude/rules/workflow-fix-on-bug.md` § Architectural greenlight.
