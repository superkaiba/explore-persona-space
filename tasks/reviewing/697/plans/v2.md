<h1>Plan — issue #697 (v2)</h1>
<p class="small">Causal context-vector patch on #537's adapters: does finetuning a behavior into a context move the context vector (the input) or the context→behavior mapping (the function)?</p>

<section class="plan-tldr">
<h2>0.0 TL;DR (plain English)</h2>
<ul>
<li><strong>What I'll run:</strong> When you finetune a model to (say) give harmful advice whenever it's playing a software-engineer persona, the model's answers change. I want to know <em>where</em> that change lives: did the model relearn what "software engineer" looks like on the inside, or did it keep the same internal picture of "software engineer" but change what it does with that picture? I take the models #537 already trained, freeze them, and do a swap: I read out the internal "context picture" from one model and paste it into the other mid-computation, then watch whether the behavior follows the picture or stays put.</li>
<li><strong>What I expect:</strong> Mostly the <em>function</em> changed, not the picture — finetuning teaches a new response to the same context, so swapping the picture should move the behavior only a little. The marker tic is the likely exception (it behaved differently in the sibling read), and I'd bet it shows more "picture moved".</li>
<li><strong>What would change my mind:</strong> If pasting the trained model's context-picture into the untrained model makes the untrained model start producing the trained behavior on its own, that says the picture carries the change — and it would mean a cheap base-model read could predict finetuning leakage, which is the bigger prize this whole line is chasing.</li>
</ul>
</section>

<strong>Loss surface:</strong> N/A — no training. The patch overwrites the layer-L residual at the patch slot before layer L+1; <code>v</code> read = mean answer-token activation along the FT shift <code>d=(v⁺−v0)/‖·‖</code> (PLUS the end-of-response slot read for marker/fact, mirroring #651's per-behavior primary — item-5 fix), <code>E</code> = judge-rate of the patched on-policy generation.

<h2>1. Goal</h2>
<p>The theory chain is <code>answer_profile = M(context_vector)</code>: a context C maps to an internal summary <code>c_C</code>, and a learned function M turns that summary into the model's answer-side profile <code>v</code> / behavior <code>E</code>. Finetuning behavior B into context C changes the answer profile. <strong>This task causally decomposes whether that change is carried by the input <code>c_C</code> (the model's internal picture of the context moved) or by the function M downstream of read layer L (the model keeps the same picture but maps it to a new answer).</strong> #651 measured only the <em>response-side write</em> (<code>trained − base</code> at the answer slot) and never held the context vector fixed, so input-move and function-change are entangled in everything #651 reported. #697 runs the A3.6c causal patch (theory plan §4) as an early, cheap read on #537's existing adapters, ahead of the #660 fresh-fleet run (#665). It informs the #665 plan and is cross-checkable against it.</p>

<h2>3. Hypothesis</h2>
<p>Per (B, C) cell, against the verdict table (verbatim from the body, cross-checked across both patches in BOTH DVs):</p>
<ul>
<li><strong>Context vector moved</strong> ⇔ P↑ → (v⁺, E⁺) <em>and</em> P↓ → (v0, E0) ⇒ <code>f_CV ≈ 1</code>.</li>
<li><strong>Mapping changed</strong> ⇔ P↑ → (v0, E0) <em>and</em> P↓ → (v⁺, E⁺) ⇒ <code>f_CV ≈ 0</code>.</li>
<li><strong>Mixed</strong> ⇒ intermediate <code>f_CV</code>; the L-sweep {7,14,21} localizes the change pre- vs post-L.</li>
</ul>
<p><strong>Directional prediction (falsifiable):</strong> #651 found the FT write is a context-invariant <em>response-side</em> direction for em/agreement/fact — consistent with M changing (a learned new answer map) more than <code>c_C</code> moving. So I predict <code>f_CV ≤ 0.3</code> (mapping-changed) for em / agreement / fact at L=14, and a higher / read-specific <code>f_CV</code> for the marker tic (which #651 found read/layer-specific). <strong>Confirmation:</strong> <code>f_CV</code> CIs land in the predicted band in both DVs and the two patches agree (P↑ and P↓ tell the same story). <strong>Falsification:</strong> <code>f_CV ≥ 0.7</code> for em/agreement/fact (context vector carries the change) — which would say the base-model context read predicts finetuning leakage, sharpening A3.10. A wide CI straddling 0.3–0.7 in both DVs is a genuine "mixed / underpowered" outcome, reported as such (not forced into a verdict).</p>

<h3>4.3 Patch-position spec (the body's open question #1) — item-4 fix</h3>
<p>The "context-read position" is the residual at the <strong>last <em>content</em> token of the user-message prompt</strong> — the token whose layer-L residual is the model's running summary of context+question immediately before it begins generating, the natural site of <code>c_C</code>.</p>
<p><strong>Critical operational definition (corrected from v1).</strong> Verified against <code>origin/issue-651:analysis/activation_shift.py</code>: <code>_build_chatml_prompt</code> renders the prompt with <code>apply_chat_template(messages, add_generation_prompt=True)</code> (the prompt INCLUDES the assistant generation header), and <code>_build_full_sequence_ids</code> sets <code>prompt_len = tokenizer(prompt_text).input_ids.shape[0]</code> INCLUDING that header. So <code>prompt_len − 1</code> on the generation-prompted sequence lands on the <strong>last token of the assistant header</strong> (Qwen-2.5 ChatML: the <code>\n</code> after <code>&lt;|im_start|&gt;assistant</code>) — a generation-prompt token, NOT the last content token, which contradicts §11's stated intent. The primary slot is therefore defined as:</p>
<pre>messages = [{"role":"system","content":T(c)}, {"role":"user","content":q}]
content_prompt = tokenizer.apply_chat_template(messages, tokenize=False, add_generation_prompt=False)
patch_pos = tokenizer(content_prompt, add_special_tokens=False).input_ids.shape[0] - 1
#   ^ the last token of the user-message-only prompt (BEFORE the assistant header)
# The actual forward pass still tokenizes WITH add_generation_prompt=True (matching
# the #651 read recipe); patch_pos is computed against the no-generation-prompt length,
# so it indexes the last content token within the longer generation-prompted sequence.</pre>
<p><strong>Per-run decoded-token slot audit (HARD-FAIL gate).</strong> For ≥1 probe per cell, capture <code>tokenizer.decode([input_ids[patch_pos]])</code> and the token id; assert the decoded string is NOT in the chat-template special-token / whitespace / header set (<code>&lt;|im_start|&gt;</code>, <code>&lt;|im_end|&gt;</code>, the literal <code>assistant</code>, <code>\n</code>, blank/whitespace-only). If it IS, the audit HARD-FAILS the cell and aborts the run with an error pointing back to this spec (it means the slot index regressed onto a header token). This audit is wired into the canary cells' required asserts (§7) and the per-cell sweep loop.</p>
<p><strong>Primary patch scope = this single last-content-token slot.</strong> <strong>Companion (upper-bound) scope = the full context span</strong> (every position from the start of the system turn through the last content token), overwriting each position's FT/base residual with the other model's residual at the same position. The full-span companion bounds how much a single-slot patch under-counts when the context summary is distributed across positions. (The body's control #4.)</p>

<h3>4.4 The two patches (per B, C, seed)</h3>
<p>Both the base model θ0 and the FT merged model θ⁺ are loaded in the same process (the #651 path loads both; θ⁺ via <code>PeftModel.from_pretrained(...).merge_and_unload()</code> so the rsLoRA α/√r scaling is baked into the merged weights — the #601 gauge is therefore identical to what the canary's Gate 7a reproduces). For each (context, question) on the panel:</p>
<ol>
<li><strong>Capture pass</strong> (unpatched): one TF forward of base on <code>T(c)+q+R_base</code> and one of FT on the same sequence (same teacher-forcing recipe as #651's <code>variant="base"</code> — base model's own greedy <code>R_base</code> is the shared trajectory, so v differences are not confounded by trajectory differences). Record <code>c0(C) = h_base[L, patch_pos]</code>, <code>c⁺(C) = h_ft[L, patch_pos]</code>, and the unpatched answer-side reads <code>v0, v⁺</code> (per §4.5 pooling). Run the unpatched generations for <code>E0, E⁺</code> (per-behavior on-policy, §4.5).</li>
<li><strong>P↓ (base CV → FT model):</strong> run FT (θ⁺) with a forward hook on <code>model.model.layers[L]</code> that, on the forward over <code>T(c)+q+R</code>, overwrites the output residual at position <code>patch_pos</code> (the full-span companion: every context position) with <code>c0(C)</code>; let layers L+1… complete. Read <code>v_{P↓}</code> and run the patched generation for <code>E_{P↓}</code>.</li>
<li><strong>P↑ (FT CV → base model):</strong> run base (θ0) with the same hook overwriting position <code>patch_pos</code> with <code>c⁺(C)</code>. Read <code>v_{P↑}</code>, generate <code>E_{P↑}</code>.</li>
</ol>
<p><strong>Generation-time patching for E (item-2 fix — non-identity KV-cache propagation).</strong> The <code>E</code> DV requires the patch to persist through generation. The hook overwrites the layer-L residual at the context slot on every forward step where that position is in the sequence; under KV-caching the context positions are computed once (prefill) so the hook fires at prefill and the cached K/V for position <code>patch_pos</code> carry the patched value through decoding. <strong>This is proven, not assumed, by the canary's non-identity generate-mode parity assert (Gate C1, §7):</strong> for a canary cell, run patched generation with <code>use_cache=True</code> and with <code>use_cache=False</code> over the same probe + the same <em>non-identity</em> patch vector (a random-norm-matched CV or another context's <code>c⁺</code>), and assert (a) the first-token logit distribution differs from the UNPATCHED generation by <code>‖logits_patched − logits_unpatched‖_∞ &gt; ε</code> at the first decoded position (the patch actually does something through caching), AND (b) the cached and uncached patched paths agree at the first-token logits within <code>1e-3</code> (caching does not drop the patch). If (b) DIVERGES, the patch is dropped during caching → the production default falls back to <code>use_cache=False</code> generation (slower but correct; budgeted in §9). The self-patch identity null (Gate C1, identity variant) is the orthogonal correctness gate (a patch with the model's own CV must be an exact no-op).</p>

<h3>4.5 The dual DV (project rule) — item-5 fix</h3>

def content_patch_pos(tokenizer, system_prompt, user_question) -> int:
    """Last CONTENT token of the user-message-only prompt (item-4 fix).
    Computed against add_generation_prompt=False so the index lands on the
    last content token, NOT the assistant-header token that prompt_len-1 on
    the generation-prompted sequence would hit."""
    msgs = ([{"role":"system","content":system_prompt}] if system_prompt else []) \
           + [{"role":"user","content":user_question}]
    content = tokenizer.apply_chat_template(msgs, tokenize=False, add_generation_prompt=False)
    return tokenizer(content, add_special_tokens=False).input_ids.shape[1] - 1

def audit_patch_slot(tokenizer, input_ids, patch_pos):
    """HARD-FAIL if the patched token is a special / whitespace / header token."""
    tok_id = int(input_ids[patch_pos])
    decoded = tokenizer.decode([tok_id], skip_special_tokens=False)
    bad = {"<|im_start|>", "<|im_end|>", "assistant"}
    if decoded in bad or decoded.strip() == "":
        raise RuntimeError(
            f"patch-slot audit FAILED: patch_pos={patch_pos} decodes to {decoded!r} "
            f"(id={tok_id}); the slot regressed onto a header/special/whitespace token. "
            f"See plan §4.3.")

def make_cv_patch_hook(layer_module, patch_positions, replacement_vec):
    """register_forward_hook that OVERWRITES the layer's output residual at
    `patch_positions` with `replacement_vec` (broadcast over the batch=1 seq)."""
    def hook_fn(module, inputs, output):
        hs = output[0] if isinstance(output, tuple) else output  # (1, T, H)
        for pos in patch_positions:                              # last-content-token = [patch_pos]
            hs[0, pos, :] = replacement_vec.to(hs.dtype).to(hs.device)
        return (hs, *output[1:]) if isinstance(output, tuple) else hs
    return layer_module.register_forward_hook(hook_fn)

def patched_read(model, full_ids, layer, patch_positions, replacement_vec, response_start):
    """One TF forward with the patch installed; return per-behavior pooled v at `layer`
    (mean_resp + slot, both — caller picks the per-behavior primary, item-5 fix)."""
    h = make_cv_patch_hook(model.model.layers[layer], patch_positions, replacement_vec)
    try:
        out = model(full_ids.unsqueeze(0).to(model.device), output_hidden_states=True)
        hL = out.hidden_states[layer+1][0]
        return {"mean_resp": hL[response_start:].mean(0).float().cpu(),
                "slot":      hL[-1].float().cpu()}
    finally:
        h.remove()

def patched_generate(model, prompt_ids, layer, patch_positions, replacement_vec,
                     use_cache=True, **gen):
    """Greedy/sampled generation with the patch persisting through prefill (KV-cached
    context positions carry the patched residual into decoding). use_cache flips to
    False as the production default iff the canary's non-identity KV parity assert
    (Gate C1, §7 / §4.4) finds caching drops the patch."""
    h = make_cv_patch_hook(model.model.layers[layer], patch_positions, replacement_vec)
    try:
        out = model.generate(prompt_ids.unsqueeze(0).to(model.device),
                             use_cache=use_cache, **gen)
    finally:
        h.remove()
    return tokenizer.decode(out[0, prompt_ids.shape[0]:], skip_special_tokens=True)

<h2>6. Evaluation</h2>

<h3>6.1 The metric</h3>
<p>Per (B, C, seed) cell, in each DV space, the <strong>context-vector-mediated fraction</strong> along the FT shift <code>d</code> (the v-space numerator/denominator use the cell's per-behavior primary pooling — mean-resp for em/syc, slot for marker/fact, item-5 fix):</p>
<pre>v-space:   f_CV   = ((v_{P↑} − v0)·d) / ((v⁺ − v0)·d),    d = (v⁺ − v0)/‖v⁺ − v0‖
E-space:   f_CV^E = (E_{P↑} − E0) / (E⁺ − E0)
P↓ cross-check:  f_CV^{down} = 1 − ((v_{P↓} − v0)·d)/((v⁺−v0)·d)   [should agree with f_CV]</pre>
<p>P↑ measures sufficiency of the moved CV (→ high f_CV ⇒ context-vector-moved); the P↓ analog measures necessity; the verdict requires the two to agree.</p>

<h3>6.3 Verdict bands (pre-registered)</h3>
<p>Per cell, in each DV: <code>f_CV ≥ 0.7</code> ⇒ <strong>context-vector-moved</strong>; <code>f_CV ≤ 0.3</code> ⇒ <strong>mapping-changed</strong>; <code>0.3 &lt; f_CV &lt; 0.7</code> ⇒ <strong>mixed</strong>. A verdict is assigned only when (a) the bootstrap 95% CI over the 20 panel questions lies entirely within one band, AND (b) the cell's effect is real: <code>|E⁺ − E0|</code> (or <code>|(v⁺−v0)·d|</code>) exceeds the random-CV null floor at p&lt;0.05 (paired test over panel questions) — a cell with no FT effect has an undefined f_CV (0/0) and is reported as <code>no-effect</code>, never forced into a band. The P↑ and P↓ verdicts must agree for a confident cell-level verdict; disagreement is reported as <code>patch-inconsistent</code> (a finding about the slot's adequacy, not a failure).</p>
