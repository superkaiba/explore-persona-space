<section class="plan-tldr">
<h2>0.0 TL;DR (plain English)</h2>
<ul>
<li><strong>What I'll run:</strong> I'm re-running a measurement experiment that takes models already taught a quirk (a tic, a fact, a style) inside one "character", and asks a clean question: when you teach a model to behave a certain way <em>as that character</em>, did you change the model's internal picture of <em>who it is</em>, or did you change <em>how it acts on</em> that picture? I do this by copying the "who it is" signal from one model into another and watching whether the behavior follows. The science is unchanged from last time — the last run just cost far more compute than I'd budgeted and one flaky upload knocked the whole job over, so this version makes each piece cheaper and stops one hiccup from sinking the rest.</li>
<li><strong>What I expect:</strong> For the marker tic and the taught fact, I expect the behavior to ride along with the "who it is" signal (the finetuning mostly moved the self-picture). For the messier behaviors (harmful advice, agreeing-with-wrong-claims) I'm less sure, and that's the interesting part.</li>
<li><strong>What would change my mind:</strong> If copying the self-picture across does almost nothing to the behavior — the behavior stays put — then the finetuning changed how the model <em>acts on</em> its self-picture, not the picture itself. Either answer is a real result.</li>
</ul>

<h2>1. Goal</h2>
<p>(Verbatim, frontmatter — <code>set-goal --by user</code> ownership; NOT a v3 design question.) On #537's already-trained behavior×context LoRA adapters, causally localize whether finetuning a behavior into a context shifts the context vector (input to the map M) or the context→behavior mapping M (the function) via cross-model activation patching at the read layer, reading both the on-policy behavioral rate and the answer-side activation profile. The theory frame is the leakage paper's pre–fine-tuning model: M maps a context vector <code>c_C</code> to behavior; an experiment that decomposes which of the two the finetuning moved is a direct causal test of that decomposition. v3 changes nothing about this question — it makes the already-approved measurement runnable inside one 24 h GCP provision.</p>

<h2>3. Hypothesis</h2>
<p>UNCHANGED from v2 (this is a measurement, not a new hypothesis). Per behavior B, finetuning B into context C either (H_input) moved <code>c_C</code> with M intact → <code>f_CV ≈ 1</code> (patching the FT context vector into the base model reproduces the FT behavior profile), or (H_map) changed M with <code>c_C</code> intact → <code>f_CV ≈ 0</code> (patching the context vector carries none of the behavior). Falsifiable thresholds: a behavior with <code>f_CV</code> 95% CI entirely above 0.7 confirms H_input for that behavior; entirely below 0.3 confirms H_map; spanning is "mixed / underpowered". Pre-registered prediction (weak): marker + fact (slot-localized, context-invariant in #651) lean H_input; em + sycophancy (mean-resp behaviors) are genuinely uncertain. The P↓ cross-check (<code>f_CV_down</code>) must agree with <code>f_CV</code> for a confident cell verdict; disagreement is reported as a mixed cell.</p>

<h3>4.2 HF upload resilience — exact code changes (C2)</h3>
<p>File: <code>scripts/issue697_cell.py</code>, function <code>_upload_cell_artifacts</code> (lines 770–810). The current body does <code>api.create_commit(...)</code> then <code>files = set(list_repo_files(HF_DATA_REPO, repo_type="dataset"))</code> (line 801) — a paginated listing of every file in the 100K+-file dataset repo, per cell, with NO retry. Two changes:</p>
<ul>
<li><strong>Drop the post-commit <code>list_repo_files</code> verify (lines 801–804).</strong> <code>huggingface_hub.create_commit</code> is atomic — it either returns a <code>CommitInfo</code> (all files committed) or raises (nothing committed; no partial commit). Replace the full-listing verify with a per-EXPECTED-file <code>HfApi.file_exists(repo_id=HF_DATA_REPO, filename=path_in_repo, repo_type="dataset")</code> check (confirmed present in <code>huggingface_hub==0.36.2</code>) — O(K) HEAD requests where K = the cell's file count (~6), not a pagination of the whole repo. This both removes the per-cell minutes-scale cost AND removes the 504-on-listing surface that crashed attempt-1.</li>
<li><strong>Wrap the Hub calls in a hand-rolled exponential-backoff retry.</strong> <code>tenacity</code> and <code>backoff</code> are NOT installed (verified) and <code>huggingface_hub</code> exposes no ready <code>BackoffConfig</code> for <code>create_commit</code>, so add a small module-level helper mirroring the project's existing pattern (<code>src/.../llm/api_dispatch.py</code> uses <code>sleep(1.5**attempt)</code>). Transient set: <code>HfHubHTTPError</code> whose <code>.response.status_code in {500,502,503,504}</code>, plus <code>requests.exceptions.RequestException</code> (connection/read timeouts). 5 attempts, exponential backoff <code>min(2.0**attempt + uniform(0,1), 60)</code>; on a non-transient error (4xx other than 429, auth) or budget exhaustion, raise a <code>RuntimeError</code> naming the cell + the last exception. The 256-commits/hr cap is honored (one <code>create_commit</code> per cell, well under).</li>
</ul>
<p>Pseudocode (the only lines that change; the <code>CommitOperationAdd</code> construction at 785–794 and the <code>create_commit</code> call at 795–800 stay, the latter wrapped):</p>
<pre>
def _hf_retry(fn, *, what, attempts=5):
    last = None
    for attempt in range(attempts):
        try:
            return fn()
        except HfHubHTTPError as e:
            code = getattr(getattr(e, "response", None), "status_code", None)
            if code not in (500, 502, 503, 504):
                raise                      # 4xx (auth/validation) -> fail loud
            last = e
        except RequestException as e:      # connection / read timeout
            last = e
        time.sleep(min(2.0 ** attempt + random.uniform(0, 1), 60))
    raise RuntimeError(f"{what}: HF Hub transient errors exhausted ({attempts}); last={last!r}")

def _upload_cell_artifacts(tensor_paths, raw_paths):
    api = HfApi()
    expected, ops = {}, []
    # ... (unchanged: build ops + expected for tensor_paths + raw_paths) ...
    _hf_retry(lambda: api.create_commit(repo_id=HF_DATA_REPO, repo_type="dataset",
              operations=ops, commit_message=f"issue697: cell artifacts ({len(ops)} files)"),
              what="create_commit")
    missing = [pir for pir in expected
               if not _hf_retry(lambda pir=pir: api.file_exists(HF_DATA_REPO, pir, repo_type="dataset"),
                                what=f"file_exists {pir}")]
    if missing:
        raise RuntimeError(f"cell upload verification FAILED -- missing on Hub: {missing}")
</pre>

<p><strong>Test (NEW, <code>tests/test_issue697_cell_upload.py</code>):</strong> monkeypatch <code>HfApi.create_commit</code> to raise <code>HfHubHTTPError(504)</code> twice then succeed, and <code>HfApi.file_exists</code> to return True; assert <code>_upload_cell_artifacts</code> retries and returns without raising, and that <code>list_repo_files</code> is never called. <h3>4.3 Wave fail-fast → continue-on-cell-fail (C3)</h3>
<p>File: <code>scripts/issue697_dispatch.py</code>, <code>phase_sweep</code> (lines 506–511). Today: <code>bad = [...]; if bad: raise RuntimeError(...)</code> — one non-zero rc raises, <code>set -e</code> kills the workload, the EXIT trap deletes the instance. Replace with a bounded continue-on-fail:</p>
<ul>
<li>Accumulate failures across waves in a <code>failed_cells: list[str]</code>. After each wave, for each cell with rc≠0: append to <code>failed_cells</code> and write a per-cell sentinel <code>write_sentinel("epm:cell-failed", note, extra={"cell_id": ..., "rc": ..., "wave": ...})</code> (the existing sentinel path the poller drains — NEVER a pod-side <code>task.py</code> shellout).</li>
<li><strong>Failure budget = <code>ceil(N_cells / 16)</code></strong> (= 4 for the 64-cell grid, ≈6% — at the lower end of the brief's "≤5% OR ≤ceil(N/16)" and stricter than 5%). If <code>len(failed_cells) > budget</code> at any point, raise <code>RuntimeError</code> (a systematic bug, not a transient — abort so the EXIT trap persists crash diagnostics). Below budget, the sweep advances.</li>
<li>At the end of <code>phase_sweep</code>, if <code>failed_cells</code> is non-empty (but ≤ budget), log a loud WARNING + write a terminal <code>epm:cell-failed-summary</code> sentinel with the full list, so the analyze phase + the orchestrator both see the coverage gap. The sweep does NOT raise.</li>
<li><strong>Design-cell guard:</strong> a per-cell crash that is reproducible (same cell fails on a re-run) is a code bug — but with the retry wrapper in §4.2 the remaining failure modes are (a) transient infra the retry didn't survive, (b) a genuine per-cell data/model bug. The ≤4 budget bounds (b)'s blast radius to the analyze-phase coverage report; a >4 failure count escalates to a real abort. The analyze phase reads the <code>failed_cells</code> list and reports the missing (behavior, cid, seed) cells per <code>verify_task_body.py</code> check 11b — the clean-result names them in <code>## Takeaways</code> + the relevant result, revises the per-behavior denominator, and omits/labels them in figures (never a misleading zero bar).</li>
</ul>
<p>Sentinel schema addition (<code>workflow.yaml § markers</code>): <code>epm:cell-failed v1</code> (fields: <code>cell_id</code>, <code>rc</code>, <code>wave</code>) and <code>epm:cell-failed-summary v1</code> (field: <code>failed_cells: [str]</code>). Both ride the existing <code>/workspace/logs/issue-697-*.json</code> sentinel-drain contract; no new poller code beyond recognizing the marker names.</p>

<h3>4.4 R_base caching + vLLM (C1, levers 1+2)</h3>
<p><strong>The fact v2 missed:</strong> R_base = <code>base.generate(T(persona,q))</code> depends ONLY on (persona, question) and the marker-strip class (marker strips the trailing marker/EOS; em/syc/fact do not). It is INDEPENDENT of (behavior-adapter, cid, seed). So across all 64 cells there are exactly <strong>2 strip-classes × 280 pairs = 560 distinct R_base generations</strong>, not 64×280 = 17,920. New pre-sweep phase <code>rbase_prep</code>:</p>
<ul>
<li>vLLM batched <code>LLM.generate()</code> (CLAUDE.md "Use vLLM for generation"; vLLM 0.11.0 verified present) over the 560 prompts (280 personas×q, plus the marker-strip variant computed by post-processing the same 280 — the strip is a token-tail operation on the generated ids, so only 280 base generations are actually needed; the marker class is derived by applying <code>_strip_trailing_marker_and_eos</code> to the cached unstripped R). Greedy (temp=0), <code>max_new_tokens=1024</code>. Cache to HF <code>issue697_cv_patch/r_base_cache/&lt;persona&gt;_&lt;qi&gt;.json</code> (token-id list + decoded text + manifest).</li>
<li><strong>Parity assert (smoke-gate):</strong> vLLM and HF greedy decoding can diverge token-for-token in edge cases. <li><code>scripts/issue697_cell.py</code> <code>run_cell</code> first pass (lines 376–395): replace the per-(persona,q) <code>_greedy_generate_ids(base, ...)</code> call with a read of the <code>r_base_cache</code> JSON (download once per cell at startup); the marker arm applies <code>_strip_trailing_marker_and_eos</code> to the cached ids (unchanged downstream). <h3>4.5 Patch confined to L=14 + batched forwards (C1, levers 3+4)</h3>
<ul>
<li><strong>Patch + full_span at the PRIMARY layer only.</strong> The per-(persona,q) patch forwards (<code>_build_conditions</code> → <code>_patched_reads</code>, 8 conditions × |layers| forwards) are the dominant cost (6720/cell at 3 layers vs 280 R_base gens). The headline <code>f_CV</code> is the PRIMARY-layer read; the {7,21} depth values are a robustness side-read, not the verdict. So: keep the cheap CAPTURE forward at all 3 layers (one <code>output_hidden_states=True</code> forward yields {7,14,21} for free — <code>_context_residuals</code>/<code>_read_unpatched</code>), but run the 8 patch conditions + full_span at L=14 ONLY in the sweep. <code>scripts/issue697_cell.py</code>: pass <code>--patch-layers 14</code> (new arg, default = primary) distinct from <code>--layers 7 14 21</code> (capture); <code>_build_conditions</code> + <code>_patched_reads</code> iterate <code>patch_layers</code>, not the full <code>layers</code> list. This is the single biggest wall lever (3-layer→1-layer patch cuts the dominant term 3×). The full 3-layer patch is recoverable as a cheap follow-up if the depth read turns out to matter.</li>
<li><strong>Batch the patch forwards across panel pairs.</strong> Today <code>_patched_reads</code> does one batch-1 forward per (condition, layer) for ONE (persona,q) — a direct violation of <code>code-style.md</code> "Batch data-parallel model forwards — never a Python loop of batch-1 forwards". Batch same-condition forwards across multiple panel pairs (pad to the max length in the batch; A100-80 holds the 7B + a batch of ~8–16 ~250-token seqs comfortably). Conservative speedup ~2–3×. <strong>This lever is optional</strong> — the wall fits 20 h WITHOUT it (Fallback A, §9) — so the implementer ships R_base-cache + L=14-patch + em-vLLM first, then adds batching if the realized per-cell wall on the smoke exceeds the §9 budget. The batched <code>patched_read</code> must preserve the per-pair hook semantics (each pair's <code>patch_pos</code> differs, so the hook's <code>patch_positions</code> are per-row within the batch — the existing <code>make_cv_patch_hook</code> takes positions + replacements, generalizable to a per-row map; if that generalization is non-trivial, batching is deferred to the follow-up and Fallback A is the shipped path).</li>
</ul>
