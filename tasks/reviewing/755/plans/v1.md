# Plan — issue #755: reconciler must persist EVERY upheld finding

## §0.0 TL;DR (plain English)

- **What I'll run:** No experiment. I'm editing one workflow file — the spec for the "reconciler" agent that breaks ties when two reviewers disagree. Right now, when the reconciler decides a reviewer was right, it only writes a *subset* of those upheld complaints into the shared ledger that the next stage of the pipeline actually reads; the rest live only in its written verdict, which nothing downstream parses. I'm changing the spec so it must write down *every* upheld complaint, with a self-check ("I upheld N, I persisted N").
- **What I expect:** After this edit, a reconciler verdict can never silently drop an upheld finding, and when it overrules a clean-result formatting complaint it has to quote the exact spec rule it's relying on — so a human reading the verdict can check the reasoning.
- **What would change my mind:** If broadening "persist deferred-production-path findings" to "persist every upheld finding" turns out to conflict with the standing "no new findings" rule (it doesn't — the carve-out already allows mirroring findings the reviewers raised), or if the count rule would force the reconciler to persist findings it classified as *non-blocking style nits* (it won't — see the scoping below).

## §1. Goal

A reconciler verdict never silently drops an upheld finding, and a structure-lens override is grounded in the exact spec text it relies on. Concretely: every finding the reconciler classifies as upheld (Real-blocking or Real-but-non-blocking that it decides should be addressed) is persisted to `concerns.jsonl` via `task.py raise-concern`, so the `/issue` Step 5c-ter dispatch gate and every downstream reader see the full set — not just the production-path subset the current Step 4 covers. And when the reconciler PASSes a clean-result body despite a clean-result-critic structure-lens FAIL, the verdict quotes the SPEC.md clause that licenses the override.

### Acceptance criteria

1. `.claude/agents/reconciler.md` Step 4 contains an explicit completeness rule: "every upheld finding is persisted" with an "N upheld → N persisted" count check and ONE matching worked example (the #715 4-upheld / 4-persisted shape).
2. The spec requires a quoted SPEC.md clause when the reconciler overrides a clean-result-critic structure-lens FAIL with a PASS-class verdict.
3. The persistence verb is the existing `task.py raise-concern … --by reconciler` — no new marker kind, no `concerns.jsonl` schema change.
4. Existing reconcile semantics are preserved verbatim: binary verdict (Rule 1), no new findings beyond the two reviewers (Rule 2), ungrounded-blocker discard (Rule 9 / Step 1), one role-scoped `epm:review-reconcile v<round>` marker (Rule 5).
5. The completeness rule is scoped to marker mode (in-context mode has no `events.jsonl` / `concerns.jsonl`).

### Delta A — broaden Step 4 (lines 234–258)

Rename the heading and generalize the rule. Current heading: **"Persist deferred-production-path findings (marker mode only)."** New heading: **"Persist EVERY upheld finding (marker mode only)."**

Rough shape of the rewritten block (prose, refine in implementation):

```markdown
**Persist EVERY upheld finding (marker mode only).** After Step 3, the set of
UPHELD findings is every finding you classified `Real & blocking` or
`Real but non-blocking` that you want addressed before advance (the rows
your `### Findings adjudicated` table marks Weight `Blocking` or
`Non-blocking`). EACH upheld finding MUST be persisted to `concerns.jsonl`
before you post your verdict — not just the deferred-production-path subset
that motivated this rule (#509), and not only when you FAIL. A finding that
lives only in your verdict body gates nothing: the /issue Step 5c-ter
dispatch gate and every downstream reader consume `concerns.jsonl`, not
verdict prose (incident #715: a reconciler upheld 4 findings, persisted only
2, and the orchestrator had to manually re-raise the missing BLOCKER +
CONCERN).

For each upheld finding:

`uv run python scripts/task.py raise-concern <N> --concern-id <kebab-id> --severity <BLOCKER|CONCERN> --summary "<≤200-char one-liner>" --by reconciler --round <round>`

- `--severity BLOCKER` when the finding is Real & blocking (would cause a bad
  outcome if unaddressed); `--severity CONCERN` for Real-but-non-blocking
  findings you nonetheless want addressed. A finding you classified
  `Unverified / mistaken` or `Out of scope` is NOT upheld → do NOT persist it.
  An `[unanchored]` blocker DISCARDED under Step 1 / Rule 9 is NOT upheld →
  it does NOT enter the persistence count.
- These are NOT new findings — each one was raised by ONE of the two
  reviewers, so the round-cap accounting is untouched and the
  `workflow.yaml § concerns_protocol.reconciler_special_case` "no new
  concerns beyond what either reviewer raised" rule is respected.

**Completeness check (N upheld → N persisted).** Before posting your verdict,
count the rows in `### Findings adjudicated` with Weight `Blocking` or
`Non-blocking` (= N upheld) and confirm you issued exactly N `raise-concern`
calls. State the count in your verdict body. If they differ, you dropped a
finding — fix it before posting.

*Example (#715 shape):* you uphold 4 findings — 1 BLOCKER (code-side
null-deref), 2 CONCERNs (analyzer-side overclaim, missing control), 1
Real-but-non-blocking you choose to address. N upheld = 4 → issue 4
`raise-concern` calls (1 BLOCKER, 3 CONCERN) before posting. A verdict that
persists only the 1 production-path BLOCKER and leaves the 3 others in the
table is the #715 bug.

In-context mode (adversarial-planner Phase 2) has no implementation under
review and no `concerns.jsonl` — note each upheld dependency in your stdout
verdict instead; the count rule does NOT apply.
```

This keeps the existing severity-downgrade `defer-concern` mirror (Step 2 note at lines 182–186 and Rule 5 lines 348–356) intact — that path is for DOWNGRADES, orthogonal to this PERSIST path.

## §11. Decision Rationale

- **Check 1 (training hyperparameters):** N/A — no model training.

- **Persistence verb = `task.py raise-concern … --by reconciler` (not a new marker kind).**
  - *Why:* the persist path already exists and is the canonical surface; introducing a new marker kind would change a public contract (the `concerns.jsonl` schema / dispatch-gate reader) and would itself need greenlight.
  - *Source:* existing `reconciler.md` Step 4 (lines 234–258) already uses `raise-concern`; existing `code-reviewer.md` Step 0.5/0.8 uses the same; `scripts/task.py` defines `raise-concern <N> --concern-id <id> --severity BLOCKER|CONCERN|NIT --summary "..." --by <reviewer> --round <int> [--evidence ...]` (lines 28–29, parser at 1414+); `workflow.yaml § concerns_protocol.reconciler_special_case` (lines 1270–1290) carries the "persist a finding already on the table via `raise-concern --by reconciler`" carve-out.
  - *Alternatives rejected:* a new `epm:reconcile-finding` marker kind (changes public contract → architectural greenlight, and the dispatch gate doesn't read it); persisting via `defer-concern` (that verb is for severity DOWNGRADES, not raises).

- **Completeness-check shape = in-prose "N upheld → N persisted" count, not a separate verifier/marker.**
  - *Why:* the reconciler is an LLM agent following prose instructions; the analogous self-check pattern is already how the spec gates other duties (e.g. the one-marker-per-round rule, Rule 5). A mechanical verifier over `concerns.jsonl`-vs-verdict-table would be new tooling outside this file's scope. Keep the fix single-file.
  - *Source:* existing Step 4 prose pattern + Rule 5 self-check style in `reconciler.md`.
  - *Alternatives rejected:* a `verify_*.py` cross-check (new script, out of scope, and the reconciler can't run it on its own table reliably); a new `epm:reconcile-completeness` marker (new contract).

- **SPEC-quote requirement scope = clean-result-critic structure-lens FAIL only.**
  - *Why:* clean-result-critic Lenses 1–15 are defined against `.claude/skills/clean-results/SPEC.md`; an override of one is a claim about a specific SPEC clause and must cite it. interpretation-critic has no SPEC document, and critic/code-reviewer FAILs are grounded in the artifact (plan/diff), not a structure spec — so the quote requirement is meaningless for them.
  - *Source:* `.claude/skills/clean-results/SPEC.md` (canonical structure-lens reference, referenced from `clean-result-critic.md` + CLAUDE.md § Experiment Report Structure); agent memory `feedback_claude_clean_result_critic_underapplies_spec_text.md` (the under-application pattern being promoted into the spec).
  - *Alternatives rejected:* requiring a quoted clause on ANY override (over-fires where no spec exists — interp-critic, critic, code-reviewer).

- **No-new-findings invariant preserved.** Broadening persistence stays inside `reconciler_special_case` because every persisted finding was raised by one of the two reviewers; the carve-out bars only NEW concerns. *Source:* `workflow.yaml` lines 1279–1290.
