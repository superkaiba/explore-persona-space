# Plan v1 — #2305: atomic fresh-claim visibility + in-flight-tolerant reader in the shared claim-file queue

## Requirement + acceptance criteria (kind: infra — bug fix)

Close the multi-worker race in the shared claim-file queue (`run_claim_queue` /
`try_claim`): a worker scanning a block can read a claim file in the window
after it is created (`O_CREAT|O_EXCL`) but before its JSON payload is written,
and the empty read is escalated to a hard, run-killing `RuntimeError`
(observed: #2162 grid worker 1, 2026-08-14 23:23Z, on a nearly-drained
5-blocks/4-workers queue).

Acceptance (verbatim from the task body, plus one scope extension):

1. A deterministic test — create the claim file EMPTY, second worker calls
   `try_claim` — no longer raises; the block is neither double-run nor
   silently skipped.
2. Exactly-one-winner is preserved under concurrent FRESH claims (no
   regression of the deterministic `O_CREAT|O_EXCL` election).
3. A genuinely unparseable claim (non-empty garbage that persists) still
   raises the hard error.
4. `release_claim`'s stolen-claim tolerance and the r1 M1 TOCTOU read-back
   arbitration are unchanged.
5. SCOPE EXTENSION (clarifier discovery, 2026-08-23): the identical fix lands
   in the forked copy `scripts/issue2329_run.py::try_claim` (fork documented
   in `issue2329_ladder.py` header; task #2329 at `awaiting_promotion`, rig
   live for follow-up rounds).

## Method delta (what differs from the current code)

Current fresh path (both files): `os.open(path, O_CREAT|O_EXCL|O_WRONLY)` →
file exists ZERO-LENGTH → `json.dump` into the fd. Readers hitting
`FileExistsError` immediately `json.loads(path.read_text())` and escalate any
parse failure to `RuntimeError`.

The fix composes the body's two options (the body prefers option 1 and its
option-2 bound survives as the reader-side backstop — "keep the hard failure
for a claim file that is STILL unparseable after the fix's bound"):

**(A) Writer — atomic content visibility, election unchanged.** The fresh
winner keeps `O_CREAT|O_EXCL` on the TARGET path (deterministic
exactly-one-winner election — acceptance 2), then closes the fd immediately
and lands the payload exactly the way the stale-reclaim sibling already does:
write `<name>.claim.tmp.<token>`, `os.replace(tmp, path)`. After this, a
reader can observe the claim file EMPTY (the µs open→replace window) but
NEVER partially written — `os.replace` atomicity on the production
filesystems is already proven by the stale path and the done-file writers.
Deliberately NOT `os.link`-based (unproven primitive on pod MooseFS) and NOT
a uniform replace+read-back election for fresh claims (would demote the fresh
election from deterministic to arbitrated — an acceptance-2 regression).

**(B) Reader — bounded in-flight tolerance, then routed disposition.** The
`FileExistsError` branch replaces the bare read+raise with a retry helper
`_read_claim_inflight_tolerant(path)` shared by intent (implemented
identically in both files, matching each file's local style):

- Up to `CLAIM_READ_RETRIES = 4` attempts; between attempts sleep
  `random.uniform(*CLAIM_READ_SLEEP_RANGE)` with
  `CLAIM_READ_SLEEP_RANGE = (0.05, 0.25)` (the existing r1 M1 settle idiom;
  worst-case bound ~1 s). Module-level constants so tests can tighten them.
- Read `path.read_bytes()` per attempt to distinguish the cases:
  - parses as JSON → return the record; caller proceeds to `_claim_stale`
    exactly as today (acceptance 4 untouched).
  - `FileNotFoundError` → the claim vanished (released, or consumed by a
    concurrent reclaim) → `try_claim` returns False; the work-conserving
    outer scan revisits the block next pass (never a raise, never a skip).
  - still EMPTY (`b""`) after the full bound → the writer died inside the µs
    open→replace window (with writer (A) in place, no LIVE same-version
    writer can hold an empty claim for ~1 s) → log a loud
    `[claims] EMPTY claim <path> after <bound>s — treating as dead writer`
    warning and fall into the EXISTING stale-reclaim path (tmp +
    `os.replace` + randomized settle + read-back arbitration). This is what
    makes acceptance 1 hold for a STATIC empty file — reclaimed and run
    exactly once, not skipped, not raised — and it removes the
    permanent-wedge failure mode a pure "return False on empty" would have.
  - non-empty and unparseable after the full bound → the existing hard
    `RuntimeError`, message unchanged (acceptance 3). With writer (A),
    partial JSON from a live writer is impossible, so persistent non-empty
    garbage is genuine corruption — fail-fast stays.

**Untouched:** `release_claim` (both its stolen-claim tolerances and its
unguarded read — with writer (A) no same-version empty window exists for it
to hit; its pre-existing exists→read micro-race is out of scope per
acceptance 4), `_claim_stale`, the r1 M1 settle + read-back, and
`run_claim_queue` (both variants, incl. the 2329 `is_done=` seam).

Residual accepted risk (documented in code comment, same class as the
existing r1 M1 comment): a live writer SIGSTOP'd >~1 s inside the µs
open→replace window can have its claim reclaimed as empty-dead → double-run,
tolerated by release tolerance + atomic idempotent done-files; never
corruption.

  weakening acceptance 2 (deterministic fresh election) or acceptance 3

  ship a partial tolerance that silently skips blocks.
- If `os.replace` on the claim path proves non-atomic on any production
  filesystem (contradicting the stale path's existing reliance), the design
  premise is wrong — re-plan, do not paper over.
