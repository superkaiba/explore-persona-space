## 4. Design

### 4.1 Hook points (design decision 1)

**Chosen: Step 6d.2 (primary, per-lane) + Step 6d.3 (run-completion backstop). NOT Step 7 or Step 8.**

- **Step 6d.2 polling loop** is the only place the orchestrator observes lane completions DURING the run: the poller drains pod-side sentinels and posts phase-transition `epm:progress` notes each tick, and the orchestrator reads per-lane terminal signals (per-run `status: done` JSON lines, `epm:cluster-terminal` for one lane of a multi-lane dispatch, detached-phase DONE breadcrumbs) as they arrive — exactly where #1481's lane completions were visible. The duty goes here as a sibling of the existing advisory-handling blocks.
- **Step 6d.3 (`status=done`)** is the last moment before the pipeline leaves the running phase — a whole-run backstop catches lanes whose individual completion was never observed (orchestrator respawn mid-run, coalesced sentinels), still hours before terminal analysis and before teardown.
- **Step 7 rejected as a hook:** Step 7 executes immediately after 6d.3 on the same re-invocation — hooking both would double-run the identical check with zero added observation window. Step 7's `epm:results` handling also fires only at run end, so it adds nothing over the 6d.3 backstop.
- **Step 8 rejected:** post-`verifying`, the pod may already be terminating; too late to be "during the run", and the terminal clean-result check already covers that window.

### 4.2 Planned-cells source and realized-cells source (design decision 2)

**Planned side:** the approved plan at the task's highest `plans/v{K}.md` (the `plan.md` symlink) — the §5 conditions table (conditions × seeds per lane), the §6.5 `primary_deliverable` artifact rows/globs, and/or the §9 per-component compute table, whichever enumerates the lane's cells. No new declaration format is introduced; the orchestrator (an LLM reading its own approved plan) performs the set-diff. **Realized side:** the drained sentinels / per-cell result files / the lane's log — the same evidence the orchestrator already reads each tick. A no-enumeration plan (single-cell run, infra task) makes the duty a defined no-op.

### 4.3 Prose-only (design decision 3)

Prose-only duty in SKILL.md; no new script. The set-diff is small (tens of cells), the sources are heterogeneous (plan prose × sentinel shapes), and the orchestrator is the agent already holding both in context each tick. A mechanical `scripts/reconcile_planned_cells.py` helper is a possible FUTURE follow-up if the prose duty proves unreliable — noted, not built here.

### 4.4 Sibling cross-references (design decision 4)

**None needed.** `experimenter.md` is launch-only (single turn — never observes completions). `planner.md` §5/§6.5 already produce the enumeration the duty reads; no planner-side change. Same-issue follow-up rounds inherit the duty automatically because they run the same 6d.2 loop / 6d.3 handling (status-hold at `followups_running`); the duty text is status-agnostic. Scope stays: one file + one test.

## 11. Decision Rationale

- **Hook points = 6d.2 + 6d.3, not Step 7/8.** *What:* per-lane duty in the polling loop's advisory-block family; whole-run backstop before the `verifying` flip. *Why:* 6d.2 is the only site that observes lane completions mid-run (the Goal's "DURING the run"); 6d.3 is the last pre-verification moment and catches unobserved completions. *Source:* SKILL.md structure read (L3970–4300, L4531–4556, L4884+); #1481 events (per-run done JSONs drained at 10:08Z+ while the miss stayed invisible). *Alternatives:* Step 7 (fires only at run end, duplicates 6d.3), Step 8 (too late — pod terminating), every-tick firing (spam, rejected).
- **Planned-cell source = the approved plan (§5/§6.5/§9), read by the orchestrator.** *What:* no new declaration format. *Why:* plans already enumerate cells there (planner.md §5 conditions table, §6.5 `primary_deliverable`, §9 per-component table); inventing a new registry would be architectural-adjacent and violate the minimal-diff constraint. *Source:* planner.md section spec; task-body constraint "keep the diff small". *Alternatives:* a machine-readable per-lane manifest (deferred; the v2 workflow's `planned_manifest.json` is the natural future home — noted as follow-up only).
- **Prose-only, no helper.** *What:* orchestrator duty text; no `scripts/` change. *Why:* the diff-size default in the task brief; the set-diff is small and source-heterogeneous — LLM-appropriate. *Source:* task #1540 body ("refine the candidate diff sketch"); filing's strong default. *Alternatives:* a reconcile script (future follow-up if the prose proves unreliable).
- **Marker = `epm:progress` with `planned-cell-reconcile` prefix.** *What:* reuse, structured note. *Why:* new marker kinds need workflow.yaml registration (edges architectural); the prefix pattern matches existing poller conventions (`[gpu-idle-advisory]`, `[long-phase-heartbeat]`) and is greppable/auditable. *Source:* task-body constraint; SKILL.md L4119–4195 precedent. *Alternatives:* new `epm:coverage-gap` kind (rejected — schema change).
- **Durability pin = new test file.** *What:* `test_issue_skill_planned_cell_reconcile_pin.py`. *Why:* the operational duty + literal prefix are exactly the droppable-prose class the pin family protects; recent SKILL.md fixes (#1493, #1533) shipped pins. *Source:* `tests/test_issue_skill_*` family (18 files); verify_plan.py c31. *Alternatives:* `Durability pin: N/A` (rejected — the note prefix is a cross-referenced literal a later edit could break silently).
