# Plan v1 — #1763 daily-fix: Step 10d merge-SHA subject check gains object-availability guard + remote fallback

## Requirement

The Step 10d "Pre-post commit-subject cross-check (#1722)" recipe in
`.claude/skills/issue/SKILL.md` (currently L11889-11897) reads the just-merged
commit's subject from the LOCAL object store
(`SUBJECT=$(git -C "$REPO_ROOT" log -1 --format='%s' "$MERGE_SHA")`) with no
object-availability step. The merge commit is created SERVER-SIDE by
`gh pr merge` and exists only on origin until the local root fetches, so the
check can read `fatal: bad object` and mis-classify STALENESS as a subject
MISMATCH, aborting the `epm:merged` post (incident: #1735 session f56bbb5d,
2026-07-27T20:21Z — one round lost).

Verified against current text (clarifier, 2026-07-28):
- The SHA **derivation** already uses `gh pr view --json mergeCommit` (#1722,
  L11871-11887) — only the SUBJECT read needs fixing.
- The safe-case path's #1725 pre-marker `sync_repo_root.py` only partially
  masks the gap (fail-soft AND single-flight: exit 0 can mean "another sync
  in flight, no pull ran").
- The merge-conflict-recovery path has NO pre-marker sync before the Success
  bullet at all — the subject check there always runs against an unfetched
  root.
- No pin tests reference the cross-check block.

## Acceptance criteria

1. The cross-check paragraph prescribes an object-availability step BEFORE the
   local subject read: `git rev-parse --verify --quiet "$MERGE_SHA^{commit}"`
   probe, and on a miss a BOUNDED fetch
   (`timeout --kill-after=30s 120s git -C "$REPO_ROOT" fetch origin main
   --quiet || true` — the skill's standing bounded-fetch form).
2. A REMOTE-read fallback exists so a failed/raced fetch degrades to reading
   the subject from GitHub instead of a false MISMATCH:
   `gh api "repos/{owner}/{repo}/commits/$MERGE_SHA" --jq '.commit.message' | head -1`
   (no local object needed; `{owner}/{repo}` placeholders resolve from the
   current repo).
3. The prose explicitly classifies a MISSING OBJECT as staleness/transport —
   never a MISMATCH; only a RESOLVED-but-foreign subject aborts as MISMATCH.
4. The fail-loud properties of #1722 are preserved: a null/premature
   `MERGE_SHA` still aborts (local `git log` errors AND the remote read 404s
   → empty `$SUBJECT` → abort; never a silent post), and the
   never-derive-from-origin/main-tip rule is untouched.
5. Lint + mapped tests green (Step 9c gate; Step 10d pre-push lint gate at
   merge).

(#1722)" paragraph (~L11889-11897). Replace the paragraph with (shape; the

```
  **Pre-post commit-subject cross-check (#1722; object-availability
  hardened #1763).** Before posting `epm:merged v1`, verify the derived
  commit's subject names THIS task. The merge commit was created
  SERVER-SIDE and exists locally only after a fetch — the #1725
  pre-marker sync is fail-soft AND single-flight (exit 0 can mean
  in-flight, no pull), and the merge-conflict-recovery path has no
  pre-marker sync at all — so ensure the object is local FIRST; a
  MISSING object is staleness, never a MISMATCH (incident #1735,
  2026-07-27: a pre-fetch `git log -1` read `fatal: bad object` and the
  false MISMATCH aborted the epm:merged post one round):

      git -C "$REPO_ROOT" rev-parse --verify --quiet "$MERGE_SHA^{commit}" >/dev/null \
        || timeout --kill-after=30s 120s git -C "$REPO_ROOT" fetch origin main --quiet || true
      SUBJECT=$(git -C "$REPO_ROOT" log -1 --format='%s' "$MERGE_SHA" 2>/dev/null) \
        || SUBJECT=$(gh api "repos/{owner}/{repo}/commits/$MERGE_SHA" --jq '.commit.message' | head -1)

  The `gh api` fallback reads the subject from the REMOTE commit (no
  local object needed; the `{owner}/{repo}` placeholders resolve from
  the current repo), so a transient fetch failure degrades to a remote
  read instead of a false MISMATCH. Then confirm `task #<N>` (or the
  issue-branch name `issue-<N>`) appears in `$SUBJECT`. Only a
  RESOLVED-but-foreign subject is a MISMATCH: ABORT the post and
  re-derive from `gh pr view <PR> --json mergeCommit`. The null case
  from a not-yet-merged PR still fails loud (`git log -1 --format=%s
  null` errors locally AND the remote read 404s → empty `$SUBJECT`);
  an EMPTY `$SUBJECT` after both reads is an ABORT (cannot certify),
  never a silent post. A foreign SHA is caught at post time rather
  than by eye after the fact.
```
