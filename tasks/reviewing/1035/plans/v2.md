# Plan — #1035: `batch_judge` tolerates transient 404 on the batch poll retrieve

`architectural: false` — bounded internal-helper extension in `llm/anthropic_client.py` + call-site rewiring; no status enum, marker schema, task.py subcommand, or CLI contract changes.

`### TDD: no` (standard implementer flow).

## 1. Goal + acceptance criteria

A transient `anthropic.NotFoundError` from `client.messages.batches.retrieve` at ANY point in a poll loop — not just within 60s of the chunk's own create — gets a bounded retry (N attempts with backoff over a few minutes) before the batch is declared lost. After the budget is exhausted the 404 still goes terminal (fail-fast preserved; wrong-org / wrong-key / genuinely-gone batches still fail loud, just ≤~3 min later).

Acceptance criteria:

1. A 404 beyond the create-grace window (a deadline-time final retrieve, a resumed poll with `created_at=None`, the fleet reconcile path, or a mid-poll blip) that clears within the retry window recovers in place — no driver crash, no relaunch cycle.
2. A persistent 404 re-raises `NotFoundError` after a bounded, test-pinned number of attempts. Never infinite; `created_at=None` (resume) is bounded too.
3. #995 create-grace behavior inside the 60s window is byte-for-byte preserved (schedule `(1,2,4,8,15,30)`, window 60s, dual bound).
4. The deadline-time FINAL retrieves get the same bounded tolerance (decision below — they are guarded now).
5. Every retry / recovery emits a grep-able log line with the `[batch-404-midpoll]` prefix.
6. `uv run pytest tests/test_batch_create_404_grace.py` passes (existing cases preserved except the three that pinned the exact behavior this task changes — updated deliberately, see §5); `uv run ruff check` and `uv run python scripts/workflow_lint.py` default run pass.

## 3. Design

### 3.1 Key design decision: option (a) — extend the existing helper into a general two-regime 404-tolerant retrieve

Chosen over (b) a separate mid-poll wrapper and (c) per-call-site parametrization:

- The mid-poll retry needs exactly the machinery the #995 wrapper already has (injectable `now_fn`/`sleep_fn`, bounded schedule, batch-id logging, recovery INFO). A second wrapper duplicates all of it; per-call-site parametrization scatters the policy across 4 files.
- Every currently-guarded call site gains the mid-poll tolerance **automatically** — zero threading changes at the three loop-retrieve sites.
- One place to prove boundedness (the fail-fast constraint).

Naming: rename `retrieve_with_create_grace` → **`retrieve_with_404_tolerance`** and rewire all importers in the same commit (code-style "Supersede → delete the old version"; no alias). Importers are enumerated in §3.4 — the rename is mechanical and every file is already being touched. Grep gate before commit: `grep -rn retrieve_with_create_grace src/ tests/` returns zero hits.

### 3.2 The two-regime retry policy (single source of truth)

New constant in `src/explore_persona_space/llm/anthropic_client.py`, next to the #995 constants:

```python
BATCH_MIDPOLL_404_BACKOFF_S = (5.0, 15.0, 30.0, 60.0, 60.0)  # #1035; 5 retries, sum = 170s ≈ 3 min
```

New pure decision helper (shared by the sync wrapper AND `AnthropicBatch.poll`'s inline async loop, so the two paths cannot drift):

```python
def next_batch_404_retry(
    exc: BaseException,
    *,
    created_at: "_dt.datetime | None",
    grace_attempts: int,
    midpoll_attempts: int,
    now_fn: "Callable[[], _dt.datetime] | None" = None,
    grace_s: float = BATCH_CREATE_404_GRACE_S,
    grace_backoff_s: tuple[float, ...] = BATCH_CREATE_404_BACKOFF_S,
    midpoll_backoff_s: tuple[float, ...] = BATCH_MIDPOLL_404_BACKOFF_S,
) -> "tuple[str, float] | None":
    """Decide the next retry for a batches.retrieve NotFoundError, or None -> re-raise."""
```

Branch order (load-bearing):

1. `exc` not an `anthropic.NotFoundError` → `None` (non-404s propagate unchanged).
2. **In the create-grace window** (`is_batch_create_grace_404` True — requires `created_at` known and `0 <= elapsed <= grace_s`): if `grace_attempts < len(grace_backoff_s)` → `("grace", grace_backoff_s[grace_attempts])`; **else `None`** — an in-window 404 that exhausted the grace schedule stays terminal, exactly preserving the #995 frozen-clock dual-bound pin (`test_backoff_exhaustion_reraises_notfound`, 7 calls). In production the grace sleeps (sum 60s) push elapsed past the window, so a real 404 storm naturally falls into regime 3 on the next 404.
3. **Outside the window** — including `created_at=None` (resume), negative elapsed, and any 404 later in a poll (the unobserved-but-plausible mid-poll class this task hardens against): if `midpoll_attempts < len(midpoll_backoff_s)` → `("midpoll", midpoll_backoff_s[midpoll_attempts])`; else `None` → the caller re-raises. **This is the fail-fast guarantee:** wrong-org / wrong-key / genuinely-gone 404s still go terminal, after at most 5 retries / 170s of sleeps.

Boundedness proof: per wrapper invocation, each 404 increments exactly one counter, each counter is capped by its schedule length → max retrieve calls = `1 + 6 + 5 = 12`, max added sleep = `60 + 170 = 230s`. Per POLL LOOP, each iteration's budget is fresh, but the loop itself is hard-bounded by `expires_at + grace` (the #663 deadline), so a flapping server cannot extend polling past the existing deadline. `created_at=None` can never become infinite-retry: regime 2 is unreachable (predicate returns False) and regime 3 is capped.

### 3.3 The extended sync wrapper

```python
def retrieve_with_404_tolerance(
    retrieve_fn: "Callable[[], object]",
    *,
    created_at: "_dt.datetime | None",
    batch_id: str | None = None,
    now_fn=None,
    sleep_fn=None,
    grace_s: float = BATCH_CREATE_404_GRACE_S,
    backoff_s: tuple[float, ...] = BATCH_CREATE_404_BACKOFF_S,
    midpoll_backoff_s: tuple[float, ...] = BATCH_MIDPOLL_404_BACKOFF_S,
):
    sleep_fn = sleep_fn or time.sleep
    resolved_now = now_fn or (lambda: _dt.datetime.now(_dt.UTC))
    grace_attempts = midpoll_attempts = 0
    first_retry_at = None
    while True:
        try:
            result = retrieve_fn()
        except anthropic.NotFoundError as e:
            plan = next_batch_404_retry(
                e, created_at=created_at,
                grace_attempts=grace_attempts, midpoll_attempts=midpoll_attempts,
                now_fn=now_fn, grace_s=grace_s,
                grace_backoff_s=backoff_s, midpoll_backoff_s=midpoll_backoff_s,
            )
            if plan is None:
                raise
            regime, delay = plan
            if first_retry_at is None:
                first_retry_at = resolved_now()
            if regime == "grace":
                grace_attempts += 1
                logger.warning(...)   # existing #995 grace WARNING, unchanged text
            else:
                midpoll_attempts += 1
                logger.warning(
                    "[batch-404-midpoll] Batch %s retrieve 404 outside create grace "
                    "(attempt %d/%d, %s since create); transient suspected — retrying in %.0fs",
                    batch_id or "?", midpoll_attempts, len(midpoll_backoff_s),
                    elapsed_desc, delay,   # elapsed_desc = "1234.5s" or "unknown" (created_at=None)
                )
            sleep_fn(delay)
        else:
            if grace_attempts or midpoll_attempts:
                _log_batch_404_recovery(batch_id or "?", grace_attempts, midpoll_attempts,
                                        first_retry_at, created_at, resolved_now())
            return result
```

- `midpoll_backoff_s=()` disables the mid-poll regime per call site (restores pure #995 behavior). No current call site uses it; it exists as the escape hatch.
- `_log_batch_grace_recovery` is generalized to `_log_batch_404_recovery(batch_id, grace_attempts, midpoll_attempts, first_retry_at, created_at, now)` — one INFO on success after ≥1 retry, message carrying the `[batch-404-midpoll]` prefix when `midpoll_attempts > 0`: `"[batch-404-midpoll] Batch %s retrieve recovered after %d grace + %d mid-poll 404 retry(ies) (%.1fs in retry, %.1fs since create)"`. This is the only empirical data that could ever ground the schedule — same rationale as #995.

### 3.5 `AnthropicBatch.poll` inline logic (anthropic_client.py:708-750)

The async poll cannot call the sync wrapper (its `sleep_fn` is `asyncio.sleep`). Extend its inline `except anthropic.NotFoundError` handler to call `next_batch_404_retry` with the two counters (`grace_attempts` exists; add `midpoll_attempts`), `await sleep_fn(delay)` on a retry plan, re-raise on `None`, and reset BOTH counters + `first_retry_at` on a successful retrieve (a fresh 404 episode later in the poll gets a fresh budget — matching the per-invocation budget the wrapped sync sites get per loop iteration; total polling stays bounded by the `expires_at + grace` deadline). Note the grace-regime sleep changes from the current `min(interval_s, 5.0)` to the shared schedule delay — a deliberate unification onto the single policy source; update any poll test asserting the old sleep values. The deadline final retrieve at :750 gets a minimal local async retry loop over `BATCH_MIDPOLL_404_BACKOFF_S` (log + `await sleep_fn(delay)`, re-raise after exhaustion).

## 4. Retry-budget decision rationale (§11-style)

| Constant | What | Why | Source | Alternatives |
|---|---|---|---|---|
| `BATCH_MIDPOLL_404_BACKOFF_S = (5, 15, 30, 60, 60)` | 5 retries, backoff, total sleep 170s ≈ 3 min | Covers a short server-side blip (#742's observed 404 was a single-read blip on a live batch, albeit in-window; the SDK-retryable-error precedent uses exponential backoff) while keeping the wrong-org/genuinely-gone terminal latency under 3 min — negligible against a multi-hour batch, decisive against a lost relaunch cycle | Task Goal ("N attempts over a few minutes") + #995 §11 precedent for the schedule shape; exact values are engineering judgment — no vendor-documented window exists (#995, re-confirmed by the §2 search). A live-transient-404 smoke is not reproducible on demand, so the recovery INFO log (attempts + elapsed) is the designated future grounding data, same as #995 did for the grace window | (a) fewer/shorter retries `(5,15,30)` = 50s — cheaper wrong-org latency, thinner blip coverage; (b) env-tunable knob — rejected (YAGNI; module constant + tests pin it; the `midpoll_backoff_s` kwarg is the per-site override) |
| Grace constants (`60.0`, `(1,2,4,8,15,30)`) | unchanged | — | #995 §11 rows 1-2 (inherited, `Source: #995`) | none — out of scope |
| In-window-exhausted → terminal (no midpoll fallthrough) | regime-2 else-branch | Preserves the #995 frozen-clock dual-bound test pin exactly; production exits the window via the grace sleeps so real storms reach the midpoll regime anyway | #995 dual-bound design + `test_backoff_exhaustion_reraises_notfound` | fallthrough to midpoll while in-window — rejected (changes a pinned #995 invariant for zero production benefit) |
| Fresh budget per poll-loop iteration / per wrapper call | no cross-iteration accumulator | Simplicity; the loop's `expires_at + grace` deadline already bounds total polling, so per-iteration budgets cannot compound into an unbounded poll | #663 deadline design | a loop-lifetime 404 budget — rejected (needs cross-call state threading at every site; the deadline already provides the outer bound) |
