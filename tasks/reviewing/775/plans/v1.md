## 0. Plan Summary

Extend the RunPod poller's wedge/failover machinery (`scripts/backend_poll.py`, Part C of `compute-backend-failover.md`) with a SECOND wedge predicate: a **same-signature CUDA illegal-memory-access (CUDA-IMA / `EngineDeadError`) crash repeat on the same pod_id** auto-pivots the run to a FRESH host (a new pod), bounded ONCE, then routes to terminal `failure_class: code` → `blocked` on a third same-signature repeat.

- **Change scope:** `scripts/backend_poll.py` (new predicate + new failover entry point + 3 new sidecar-clock helpers + new lease stamp/read pair, wired into `main()`); `.claude/rules/compute-backend-failover.md` (new Part D); `src/explore_persona_space/backends/router.py` (one new `Lease` field `runpod_cuda_ima_failover_of`, mirroring `runpod_wedge_failover_of`); tests in `tests/test_runpod_wedge_detection.py` + `tests/test_backend_poll.py`.
- **Reuse, not fork:** recovery REUSES `_relaunch_fresh_runpod` (fresh-pod re-provision via the router's `failover_to_runpod_after_async_workload_crash`); idempotency REUSES the durable-lease + sentinel pattern; detection REUSES the sidecar-`extra` clock pattern (`_read/_write/_clear_runpod_noport_clock`).
- **The one genuinely new thing:** the signal. Part C's no-port wedge keys on `runtime.ports` emptiness; Part D keys on a CUDA-IMA regex matching `PollResult.log_tail_excerpt` AND a prior same-signature crash recorded for the same pod_id in the sidecar.
- **Estimated GPU-hours (total): 0** — pure workflow surface, no model training, no pod provision during implementation.
- **Acceptance:** every new function has ≥1 unit test; a `main()`-level integration test PASSes (same-signature CUDA-IMA second dead poll → fresh-pod failover JSON); the once-more bound holds (third same-signature crash on the fresh pod → terminal `code`); `ruff` + `workflow_lint` exit 0; no Part C / Part B test regresses.
- **Top risks:** (1) the CUDA-IMA regex over-matches a benign line and force-pivots a healthy run (mitigated by requiring the regex AND a recorded prior same-signature crash + `status=dead`); (2) the "trust the respawn happened" assumption — the experimenter's standard orphan-reap recipe runs on every respawn, so a SECOND same-signature crash on the same host is the host-wedge signature.

## 1. Goal + acceptance criteria

**Goal (verbatim from `body.md`):** "Extend the wedge/failover machinery: a same-signature CUDA-IMA crash after a verified-clean-GPU respawn auto-pivots to a FRESH host (new pod), bounded once (mirroring the GCP->RunPod once-more bound), then terminal failure_class:code -> blocked."

**Motivating incident:** #763 crashed twice with CUDA illegal-memory-access (`EngineDeadError`), same-signature, AFTER a clean orphan-reap respawn = the physical RunPod H100 was wedged at the driver level. The Part C no-port wedge stops the no-port billing leak but does NOT auto-pivot a CUDA-IMA-wedged pod (which keeps its port + stays RUNNING) to a fresh host — so #763 needed a manual pivot (sibling-confirmed by #761 r3's manual GCP→RunPod failover).

**Acceptance criteria:**
1. **Predicate fires on the right signature:** a RunPod handle whose poll is `status=dead` with a CUDA-IMA-matching `log_tail_excerpt` AND a sidecar-recorded PRIOR same-signature CUDA-IMA crash for the SAME pod_id triggers the fresh-host failover. A FIRST CUDA-IMA crash (no prior record) does NOT pivot — it records the crash and falls through to the ordinary dead path (experimenter respawn).
2. **Recovery reuses the existing fresh-pod machinery:** the failover entry point calls `_relaunch_fresh_runpod`, NOT a re-implementation of pod provisioning.
3. **Once-more bound holds:** the CUDA-IMA failover fires AT MOST ONCE per run. After the pivot, a SECOND same-signature crash on the FRESH pod → terminal `failure_class: code` → `status:blocked`. Bounded by the durable lease field `runpod_cuda_ima_failover_of`.
4. **Idempotency holds across crashes:** a re-fired tick on the SAME wedged handle after a successful failover short-circuits (no double-terminate/provision), guarded by lease (authoritative) + sentinel (fast path) — the Part C two-record pattern.
5. **No regression in existing wedge tests:** every Part C + Part B test stays green; the new predicate is a no-op on a non-RunPod handle, a healthy poll, a first crash, and the no-port path.
6. **Mechanical gates pass:** `ruff` exit 0; `workflow_lint.py` (incl. `--check-lessons-index`) exit 0; touched-files pytest PASSes.

| Aspect | Part C (#664 no-port — EXISTING) | Part D (#775 CUDA-IMA — NEW) |

| Post-failover terminal | re-crash on fresh pod → `failure_class: code` | identical: a SECOND CUDA-IMA on the fresh pod → idempotency/bound short-circuit → terminal `failure_class: code` (`reason=runpod_cuda_ima_failover_exhausted`), NOT a second pivot |

**Predicate input signal — two conjuncts, both necessary:**
1. **CUDA-IMA log-tail regex** on `result.log_tail_excerpt` (populated by `poll_once` from `probe["log_tail"]`; confirmed in `scripts/poll_pipeline.py`):
   ```python
   CUDA_IMA_SIGNATURE = re.compile(
       r"(?:CUDA error:\s*an illegal memory access"
       r"|illegal memory access was encountered"
       r"|EngineDeadError"
       r"|EngineCore\b.*?(?:died|dead|illegal memory))",
       re.IGNORECASE | re.DOTALL,
   )
   ```
   "Same signature" = both crashes match `CUDA_IMA_SIGNATURE` AND occur on the SAME pod_id. We deliberately do NOT fingerprint the exact stack frame — a driver-level IMA has no stable user-frame, and the host-wedge signature is "the GPU throws IMA regardless of workload."
2. **pod_id pinning:** the prior-crash record is keyed to `_runpod_handle_identity` (`{pod_name, job_id}`, reused verbatim). A fresh-pod re-provision writes a NEW `pod_name`, so the OLD record doesn't match the fresh pod — the fresh pod starts with a clean crash count.

## 4. Detection design

**Sidecar state.** One key on the handle sidecar's `extra` dict (the same surface the Part C no-port clock rides — round-trips via `serialize_handle`'s `dict(handle.extra)`, no schema migration):
```python
extra["runpod_cuda_ima_first_seen"] = {"pod_name": "<name>", "job_id": "<id>", "ts": <epoch>}
```
Read/write/clear by the three helpers (§3a), all fail-soft. CLEARED on any `status=running` poll — a single transient CUDA-IMA the respawn recovered from does NOT accumulate; only a SECOND crash with no intervening healthy poll counts.

**"Same signature"** = (1) current poll `status=dead` AND `CUDA_IMA_SIGNATURE.search(result.log_tail_excerpt)` matches; (2) a prior record exists for the SAME `pod_name`/`job_id`. Escalation: (1)+(2) → rewrite to `status=dead, current_phase=RUNPOD_CUDA_IMA_WEDGED_PHASE`. (1) without (2) → write record, return unchanged (ordinary dead path). Not (1) on a running poll → clear record; else return unchanged.

**Why CUDA-IMA family + same pod_id, not an exact stack fingerprint:** a driver-level IMA surfaces wherever the next kernel launch is, with no stable user-frame. The host-wedge hypothesis is "the GPU throws IMA regardless of workload," so "the CUDA-IMA family recurred on this physical host after a clean reap" is the calibrated signal. A tighter fingerprint MISSES the wedge; a looser one (any second dead poll) over-pivots on code bugs.

**Trust-the-respawn-happened assumption (from the clarifier marker).** The predicate assumes the experimenter's orphan-reap respawn ran between the first and second crash (the `pkill -9 ^VLLM::EngineCore` by exact PID + `nvidia-smi` VRAM probe recipe, an UNCONDITIONAL Pre-Launch step per gotchas.md + experimenter.md). Under that, a second same-signature CUDA-IMA after a clean reap = the reap worked but the GPU still throws IMA → driver wedge → only a fresh host helps. **Sufficient because** the reap is structural, not opt-in — the poller needs no separate "verified-clean-GPU" marker. **Invalidated if** a respawn path ever skips the reap (a leftover zombie could trigger a needless pivot — but that is benign, bounded once, and a fresh pod also clears a zombie). If respawns systematically stopped reaping, the right fix is a verified-clean-GPU marker coupling, revisitable then; this plan does not pre-build it (avoids a cross-surface dependency the clarifier flagged as unnecessary).

## 5. Recovery design — reuse vs fork

**Decision: REUSE `_relaunch_fresh_runpod` (inner fresh-pod machinery); add a thin sibling `_failover_cuda_ima_runpod` at the OUTER layer.**

- *Reuse `_failover_wedged_runpod` directly (rejected):* it hard-codes the no-port idempotency key (`runpod_wedge_failover_of`), so it would cross-suppress a CUDA-IMA failover and a no-port failover on the same issue; its terminate assumes a RUNNING pod (a CUDA-IMA pod is already dead); its log/reason strings are no-port-specific.
- *Fully independent fork of the whole relaunch (rejected):* `_relaunch_fresh_runpod` is ~150 lines of #689-hardened error mapping (NoCompute→`no_compute_available`, sidecar-write-fail→`sidecar_persistence_failed`, legacy-handle→`*_spec_missing`, durable-lease stamp). Duplicating it forks four hardening paths and rots.
- *Chosen:* reuse the inner relaunch via the one `stamp_fn` kwarg; fork only the ~25-line OUTER orchestration.

**Lease field + once-more bound (two layers, same durable field `runpod_cuda_ima_failover_of`):**
1. **Per-wedged-pod idempotency** (re-fired tick on the SAME wedged handle): `_runpod_cuda_ima_already_handled` checks `lease.runpod_cuda_ima_failover_of == _runpod_handle_identity(handle)` + sentinel. Stops double-terminate/provision of one wedge.
2. **Per-run once-more bound** (a SECOND distinct wedge on the FRESH pod): `_failover_cuda_ima_runpod` first checks whether `runpod_cuda_ima_failover_of` is set to ANY non-null value on the issue's lease ("this run already spent its one CUDA-IMA pivot"). If so → terminal `failure_class: code` (`reason=runpod_cuda_ima_failover_exhausted`), NO second relaunch. This is the GCP→RunPod once-more-bound analogue.

## 6. Failure-class routing (bounded-once)

```
RunPod CUDA-IMA crash on pod-A
  → poll: status=dead, log_tail matches CUDA_IMA_SIGNATURE
  → _maybe_escalate_runpod_cuda_ima:
       prior record for pod-A?  NO → WRITE record{pod-A}; return dead unchanged
                                       → failure_classifier → infra → experimenter
                                         ORPHAN-REAP RESPAWN (same host pod-A)
                                         (recovers → status=running → record CLEARED)
                                YES (2nd same-sig, pod-A) → rewrite → CUDA_IMA_WEDGED_PHASE
  → _is_runpod_cuda_ima_failure → True
  → _failover_cuda_ima_runpod:
       layer-2 bound: lease.runpod_cuda_ima_failover_of already set?
            YES → TERMINAL failure_class: code (runpod_cuda_ima_failover_exhausted) → blocked
            NO  → layer-1 idempotency (this pod handled?) → short-circuit if yes
                → inputs-on-HF gate (PARTIAL → block infra, human decides)
                → best-effort terminate(pod-A); write sentinel
                → _relaunch_fresh_runpod(stamp_fn=_stamp_runpod_cuda_ima_failover)
                → FRESH pod-B; lease.runpod_cuda_ima_failover_of = {pod-A identity}
                → emit status=running, current_phase=runpod_cuda_ima_failover_fresh_pod
  → pod-B ALSO CUDA-IMA crashes: 1st→record{pod-B}; 2nd→escalate→_failover_cuda_ima_runpod
       → layer-2 bound (field already set) → TERMINAL failure_class: code → blocked
```

`scripts/failure_classifier.py` is UNCHANGED — routing is driven by the poll JSON's `failure_class`/`reason` (the existing `_terminal_infra_json` + a new terminal-code emit), not by re-classifying a log body. The watcher's capacity-retry pass re-drives ONLY `failure_class: infra` + `no_compute_available`, so a `runpod_cuda_ima_failover_exhausted` code failure parks at `blocked` (the Part B/C bound).

## 9. Kill criteria
- **Regex misfires on a single-crash false positive** — bounded once + benign (a fresh pod clears a zombie); becomes a real problem only if a deterministic CODE bug routinely emits CUDA-IMA twice (mitigation: the regex matches the CUDA-IMA/EngineDeadError family specifically, not an `AssertionError`; the two-crash requirement gives the respawn one recovery chance). If code bugs routinely double-emit CUDA-IMA, add an our-code-frame exclusion (mirroring `failure_classifier`) — flagged in assumptions.
- **The once-more bound lets a third crash through** — hard kill; caught by `test_cuda_ima_failover_bounded_once_third_crash_terminal_code` + `test_poller_cuda_ima_failover_exhausted_emits_code`.
- **Part C regresses** — hard kill; caught by the untouched Part C idempotency/lease tests (the `stamp_fn` default keeps Part C byte-unchanged).
- **Escalation force-stops a healthy run** — must NEVER rewrite a `status=running` poll except to CLEAR the record; caught by `test_cuda_ima_record_cleared_on_running_poll`.
