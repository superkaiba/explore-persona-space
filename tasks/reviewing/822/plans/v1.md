**Anchor:** insert between the end of Step 0.5 ("Validate the implementation marker shape") and the heading of Step 0.6 (`Step 0.6 "End-to-end smoke gate (\`type:experiment\` only)"`, line ~197).

**Proposed text:**

```markdown
### Step 0.55: Smoke-architecture-check marker presence (`type:experiment` only)

Before reading the diff, verify the task carries the implementer's
smoke/sweep architectural-parity verdict as a SEPARATE events.jsonl row —
the `epm:smoke-architecture-check` marker (mandated at implementer round-1
pre-flight by `experiment-implementer.md` "Before writing code" item 5).
Read CANONICAL task state: fetch events via
`uv run python scripts/task.py view <N> --json`, not a stale worktree copy —
a stale read is the most common false "absence" (same guard as Step 0.5).

- **Satisfied (ONCE PER TASK):** at least one `epm:smoke-architecture-check`
  row exists on the task whose note carries a parseable `verdict:` line of
  `PASS_UNIFIED` or `PASS_CANARY canary_cell=<cell_id>`. A marker posted on
  a PRIOR round satisfies the check — the mandate is round-1 pre-flight,
  refreshed only when the run architecture changes. Do NOT demand a fresh
  marker per revision round; that would false-FAIL every revision round.
- **`FAIL_NO_CANARY` present:** NOT a mechanical absence — a posted verdict
  declaring a known-diverged architecture, owned by the orchestrator's
  Step 6d.0 pre-dispatch gate (which bounces to planning). Record it as
  CONCERNS with a pointer to the marker; never FAIL mechanically on it.
- **Genuine absence** (no `epm:smoke-architecture-check` row at all in
  canonical task state, or no row with a parseable `verdict:` line):
  FAIL with a single `Critical` issue tagged `marker-shape`, naming the
  missing marker and quoting the post-marker command from
  `experiment-implementer.md` item 5. An inline "PASS_UNIFIED" claim inside
  a code comment or inside the `epm:experiment-implementation` note payload
  does NOT satisfy this check (incident #811: the claim lived in a
  dispatcher header comment across 5 rounds while the marker was never
  posted; both ensemble reviewers PASSed every round). Still read the diff
  (Step 0.7) and report substantive findings alongside the contract blocker.
- **Present but imperfect** (parseable verdict, terse/thin notes): at most
  CONCERNS, never FAIL.
```

A separate step keeps the per-tag Step 5c-bis verification recipes cleanly branchable.
   - **Source:** evidence B (the 0.5/0.6 pattern), evidence C (the Codex cost of a new step is two one-line enumeration edits, fully specified in Edits 4-5).
   - **Alternatives:** sub-block inside Step 0.5 (rejected: free Codex inheritance is worth less than the semantic muddle, and Edits 4-5 are trivial); a new tag + new step (rejected under decision 2).
2. **Blocker tag: reuse `marker-shape`.**
   - **What:** Step 0.55 genuine absence FAILs under the existing `marker-shape` tag.
   - **Why:** The tag's meaning is "a required implementer marker is absent/malformed" — literally this case. It is already in the Step 5c-bis mechanical-contract strip set, so the orchestrator-side plumbing is one added verification sentence (Edit 7) instead of a strip-set change + reconciler documentation + Step 5c-bis set edits across SKILL.md.
   - **Source:** evidence F (strip set + per-tag verification structure); the task body's own diff sketch.

3. **Step 5c-bis verification sentence.**
