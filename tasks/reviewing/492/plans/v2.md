# Plan v1 — task #492 — Diagnose what in the v2→v4 redesign floored the marker implant

## 0.0 TL;DR (plain English)

- **What I'll run:** train the same marker-implant cell — same data, same hyperparameters, same seed — under two snapshots of our own training code. One snapshot worked: the marker stuck and the model used it 80% of the time. A later snapshot reads zero. I want to find which of the two or three things that changed between those snapshots is responsible, and get back to a working implant we can actually study.
- **What I expect:** I think the change that flipped the behavior is small — most of what we rewrote was checkpoint-bookkeeping and analysis code, and the actual trainer was untouched. My top guess is a side effect of saving extra mid-training checkpoints (we went from one save to eight), with the eval-side persona-panel change a close second. Either way, fixing one specific thing should bring the implant back.
- **What would change my mind:** if reverting to the older snapshot ALSO reads zero (then the regression is in something downstream of the code, like training-data files we built later or model weights cached at a different revision), or if every targeted revert still floors (then the bug is interacted across multiple changes and we need a real git-bisect).

**The behaviorally-relevant subset** (changes that could plausibly affect what the training loop sees or what the eval reads):

1. **Mid-training checkpoint saves.** v2 path (`phase=calibration`, `fractions=(1.0,)`) saves ZERO mid-training adapters (the callback's `for frac in self.fractions: if frac >= 1.0: continue` skips the only entry). v4 path (`phase=step_calibration`, `fractions=(0.0263, 0.0526, ..., 0.8421, 1.0000)`) saves 7 mid-training adapters via `model.save_pretrained()` from inside the training loop. PEFT's `save_pretrained` is documented as a pure file-write — but its presence inside `on_step_end` could in principle drift the RNG state used by the next-step DataLoader (the trainer's `RandomSampler` consumes the global torch RNG between steps), or trip a PEFT version-specific side effect.
2. **`--cell-specs 477` for the eval panel.** v4 passes `--cell-specs 477` to the eval subprocess; v2 doesn't (default `472`). This SUBTRACTS the `#477` negatives from the held-out panel. **Does NOT affect source-self ΔG** (source-self uses `bank[SOURCE_PERSONA]` and the source's own R, independent of the panel) — so this is a low-probability candidate for the source-ΔG floor, but I include it as a control because the v4 cell_summary's reading was 0 on source-self specifically.
3. **`frac_precision=4` directory names.** v4 names mid-checkpoints `frac_0.0263/` instead of `frac_0.02/`; the terminal key is `"1.0000"` instead of `"1.00"`. Could plausibly collide with a stale on-disk checkpoint from an earlier v2 run if the run_dir wasn't cleared (resume-skip path). The dispatcher's `_phase_step_calibration_pick` is keyed on the new precision; if a stale `1.00` adapter is loaded instead of a fresh `1.0000` retrain, the eval would read the OLD floored adapter.
4. **`step_calibration_fractions` argument threading.** `train_one_cell` accepts the new kwarg and passes it to `CheckpointAtFractionsCallback`. Strictly additive — but the call sequence INSIDE `train_lora` is identical, and the callback only fires at step boundaries.

The other v2→v4 changes (`analyze.py` partial Spearmans, the new test files, the v4 anchor spec for implant_sweep_v4) are pure post-hoc analysis or schedule machinery that doesn't touch the `c477_calib_negp_2` training or eval inputs.

## 3. Hypothesis

**H1 (top-ranked candidate, plausibility MEDIUM): the v4 mid-training `save_pretrained` calls indirectly perturb the final trained model state.** Mechanism options: (a) RNG drift — PEFT's `save_pretrained` consumes a small amount of randomness via `os.urandom` or temp-file naming, advancing the global state between optimizer steps; (b) PEFT-version-specific side effect on the active adapter (e.g. `set_adapter` reattached at save); (c) cgroup/io-induced trainer-step delay causes the LR scheduler to take a different sub-step. **Prediction:** if I retrain the v4 commit at `phase=calibration` (legacy `fractions=(1.0,)` — zero mid-saves) instead of `phase=step_calibration`, source ΔG returns to ~17.
**Falsifier:** v4 commit + `phase=calibration` STILL floors. Then mid-saves are exonerated.

**H2 (plausibility LOW for source-self, MEDIUM for bystander): `--cell-specs 477` on the eval-side changes which adapter or which R is loaded such that the source-self readout is wrong.** Mechanism: the disjointness assert added to `eval_trajectory.py` rejects the eval-personas set in some path that silently produces zero readings. **Prediction:** running the v4 commit's `c477_calib_negp_2` training but with `--cell-specs 472` on the eval flips the source dG back. **Falsifier:** v4 training + `--cell-specs 472` eval still reads source dG ≈ 0.04. (Almost certainly will, since source-self uses `bank[SOURCE_PERSONA]` directly — this is a useful negative ablation.)

**H3 (plausibility LOW-MEDIUM): a stale on-disk checkpoint at the OLD precision (`frac_1.00`) is being LOADED by v4 eval that expects the NEW precision (`frac_1.0000`), and the read is from a leftover empty / initialized adapter dir.** Mechanism: the v4 cell_summary reports `step_at_last_ckpt=76` which IS consistent with finding a `1.0000` key, but if some earlier code-review-fix smoke-test left a stale `frac_1.00` dir in `/workspace/runs/issue_477/c477_calib_negp_2_seed42_lr2e-06/checkpoints/` and the v4 reads it preferentially, the read would be from the wrong file. **Prediction:** wiping `/workspace/runs/issue_477/c477_calib_negp_2_seed42_lr2e-06/` before the v4 retrain restores the saturating signal. **Falsifier:** clean retrain still floors.

**H4 (plausibility LOW, but the cheapest sanity check): the volume's `persona_bank.json` / `centroids/` / `on_policy_R/` artifacts were rewritten between v2 and v4 such that the training data the v4 retrain builds is materially different.** Mechanism: the #477 rig pulls these from the pod-477 volume and from HF revisions; if HF was re-pushed at a different revision after v2, v4 would see a different on-policy R / different cosines / different negative selection. **Prediction:** the SHA256 of the built `train_jsonl` for `c477_calib_negp_2_seed42` at the v4 retrain differs from the v2-era hash. **Falsifier:** the v2-anchor cell (A1) reproduces saturation despite the artifacts being unchanged → artifacts are not the issue. (Cell A1's outcome is itself the answer.)

**H5 (the implant is genuinely fragile and v2's saturation was the regime drift, not a stable property).** A stochastic basin where saturation vs floor depends on RNG init state through the training loop, and the v4 callback insertion happens to fall on the wrong side. **Prediction:** running the v4 commit at 3 different seeds (42, 137, 7) reproduces the floor at all of them; the v2 commit at the same 3 seeds reproduces saturation at all of them. **Falsifier:** mixed results across seeds — then we're in noise territory and the "regression" framing is wrong.

**Quantitative thresholds:** "saturated" = source ΔG ≥ 5 nats AND emit ≥ 0.30; "floored" = source ΔG < 1 nat AND emit ≤ 0.05; "intermediate" = anything between (also informative — partial recovery means the candidate is responsible for part of the gap).

### Thresholds

- **Saturated:** source ΔG ≥ 5 nats AND emit ≥ 0.30 (matches v2's 17.42 / 0.8 with headroom).
- **Floored:** source ΔG < 1 nat AND emit ≤ 0.05 (matches v4's 0.04 / 0.0).
- **Intermediate:** anything between — also a finding (partial recovery localizes a partial cause).

### Statistical test

No formal statistical test — the v2 vs v4 effect size (17 nats vs 0.04 nats; emission 0.8 vs 0.0) is 100× wider than the across-seed noise observed at the count=2/lr=2e-6 cell in #477 v2's calibration table (the four `dG_at_lr` columns at count=2 in plan v6 §2.1 ranged from 16.26 to 20.12 across LRs, never below 5 at this LR). Any cell that lands in "saturated" vs "floored" by the thresholds above is unambiguous. The plan is one seed (42) per cell. A confounded mixed outcome (some cells saturate, some floor on the same arm) is itself the H5 finding ("the implant is fragile under RNG basin").
