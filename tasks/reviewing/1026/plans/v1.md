# Plan — task #1026: upload-verifier in flight must block finalize / status-advance

## 0.0 TL;DR (plain English)

- **What I'll change:** right now, the pod-teardown command (`dispatch_issue.py finalize`) can tear the pod down on an OLD "uploads verified" note even while a NEW verification round is still running. I'll add a currency check: teardown is refused (loud, typed exit) whenever a verification round has been dispatched but has not yet posted its verdict, or when the newest results postdate the newest verdict. The `/issue` skill text gets matching wording so the orchestrator waits or re-spawns the verifier instead of advancing.
- **What I expect:** the #778 shape (pod destroyed at ~19:00Z while the verifier's verdict — which came back FAIL — was still pending) becomes mechanically impossible; every legitimate flow (the #585 no-declaration degrade, the #604 phase-mismatch skip recipe, Step 6d.4 mid-pipeline gate teardowns) keeps working with zero new flags.
- **What would change my mind:** if the test matrix shows a legitimate documented recovery flow that can ONLY complete by tearing down under a fresh in-flight verifier round (none found in SKILL.md), I'd add an explicit override flag instead of the wait-for-window escape.

## 1. Goal, requirement, acceptance criteria

**Goal (from the task body):** close the fallback loophole that let a session flip status to `interpreting` and finalize (terminate) the pod while the upload-verifier was still running. Only an explicit `epm:upload-verification` PASS **for the current round** may satisfy the Step 8 gate; an in-flight verifier is BLOCKING (a WAIT or a verifier re-spawn), never a PASS-equivalent.

**Requirement.** `dispatch_issue.py finalize` must never proceed to `backend.teardown(handle)` while a dispatched upload-verifier round has not resolved to a verdict marker, and the agent-level PASS fallback must never be satisfied by a verdict that predates a newer verifier dispatch or newer `epm:results`. Refusals are loud and typed (exit 3 + machine-readable `reason`), never silent skips. The SKILL.md Step 8 prose and the code change together.

**Acceptance criteria:**
1. Finalize with a `stage-dispatch stage=verifying` (or `stage=followup-verifying`) breadcrumb newer than the latest `epm:upload-verification`/`epm:upload-verified` event exits 3 with `reason: upload_verifier_in_flight` (fresh) or `upload_verifier_stalled` (window lapsed), teardown NOT called, sidecar NOT retired. This binds on the declaration-present mechanical path, the no-declaration fallback path, and (`in_flight` only) the `--skip-confirm-artifacts` path.
2. The #585 degrade (no declaration + agent PASS) additionally refuses with `reason: upload_verification_stale` when the latest `epm:results` postdates the latest verdict event.
3. An explicit current-round PASS (verdict event posted after the round's breadcrumb and after the round's `epm:results`) degrades to teardown exactly as today (`confirm_artifacts: skipped_no_declaration_agent_pass`, exit 0, sidecar retired).
4. Legacy shapes unchanged: no verifier ever dispatched + no `epm:results` → the sticky/`Verdict: PASS` evidence works verbatim; no declaration + no evidence → `confirm_artifacts_no_declaration` exit 3; declaration present + mechanical FAIL → `confirm_artifacts_failed` exit 3 (never degrades); `--skip-confirm-artifacts` with no verifier activity → teardown proceeds verbatim (Step 6d.4 gate teardowns, crashed-run recovery, #604 recipe).
5. `uv run pytest tests/test_dispatch_issue_cli.py tests/test_stage_dispatch_dedup.py tests/test_upload_verifier_currency.py` passes; `uv run ruff check` on touched files passes; `uv run python scripts/workflow_lint.py --check-asks` passes (and the no-flags default run stays green).
6. SKILL.md Step 8 documents the three new reasons with an explicit routing action per reason (WAIT / re-spawn verifier / re-verify), and the PASS-branch + degrade-path wording states the currency requirement.

### 4.1 `src/explore_persona_space/task_workflow.py` — new pure helper (~55 lines, placed after `stage_dispatch_should_skip`, i.e. after line 1610)

```python
# Marker kinds that record an upload-verification VERDICT (either the
# per-round epm:upload-verification report or the sticky epm:upload-verified
# the skill posts right before auto-terminate). Any of these CLEARS a prior
# verifying-stage dispatch breadcrumb for the currency gate below.
UPLOAD_VERDICT_KINDS = frozenset({"epm:upload-verification", "epm:upload-verified"})


def upload_verification_currency_blocker(
    events: list[dict],
    *,
    now: datetime | None = None,
    window_minutes: float = 15.0,
) -> dict | None:
    """Typed refusal record when upload-verification evidence is not CURRENT.

    Returns None when the evidence is current (or there is no verifier
    activity at all). Otherwise a dict with:
      reason: "upload_verifier_in_flight" | "upload_verifier_stalled"
              | "upload_verification_stale"
      state:  "in-flight" | "stalled" | None
      stage / round / breadcrumb_ts / age_minutes / detail

    Rules (append-only events.jsonl => index order == chronological order;
    ordering compares INDICES, never parsed timestamps, mirroring
    stage_dispatch_should_skip's later-event scan):

    1. IN-FLIGHT / STALLED — the most recent ``stage-dispatch`` breadcrumb
       whose parsed ``stage=`` token normalizes to ``verifying``
       (``_normalize_stage`` covers ``followup-verifying``) has NO
       UPLOAD_VERDICT_KINDS event at a later index. The dispatched round's
       verdict is pending: refuse. state = "in-flight" when
       ``stage_dispatch_should_skip(events, raw_stage, round, window)``
       still reports it in flight (liveness-refreshing 15-min window);
       else "stalled" (window lapsed, no parsable round, malformed ts, or
       cleared only by epm:failure — the round died without a verdict, a
       stale prior PASS is still stale).
    2. STALE — no rule-1 breadcrumb blocks, but the latest ``epm:results``
       has no UPLOAD_VERDICT_KINDS event at a later index: the newest
       results were never verified; a prior verdict is for a prior round.
    """
    if now is None:
        now = datetime.now(UTC)
    last_crumb_idx: int | None = None
    last_crumb_fields: dict[str, str] = {}
    last_verdict_idx: int | None = None
    last_results_idx: int | None = None
    for idx, event in enumerate(events):
        kind = event.get("kind", "")
        if kind == "epm:progress":
            note = (event.get("note", "") or "").lstrip()
            if note.startswith("stage-dispatch "):
                fields = _breadcrumb_fields(note)
                if _normalize_stage(fields.get("stage", "")) == "verifying":
                    last_crumb_idx, last_crumb_fields = idx, fields
        elif kind in UPLOAD_VERDICT_KINDS:
            last_verdict_idx = idx
        elif kind == "epm:results":
            last_results_idx = idx

    if last_crumb_idx is not None and (last_verdict_idx is None or last_verdict_idx < last_crumb_idx):
        crumb = events[last_crumb_idx]
        raw_stage = last_crumb_fields.get("stage", "")
        try:
            round_num: int | None = int(last_crumb_fields["round"])
        except (KeyError, ValueError):
            round_num = None
        in_flight = round_num is not None and bool(
            stage_dispatch_should_skip(events, raw_stage, round_num, window_minutes, now=now)
        )
        ts = _stage_event_ts(crumb)
        age = None if ts is None else round((now - ts).total_seconds() / 60.0, 1)
        state = "in-flight" if in_flight else "stalled"
        return {
            "reason": "upload_verifier_in_flight" if in_flight else "upload_verifier_stalled",
            "state": state,
            "stage": raw_stage,
            "round": round_num,
            "breadcrumb_ts": crumb.get("ts", ""),
            "age_minutes": age,
            "detail": (
                f"stage-dispatch stage={raw_stage} round={round_num} at "
                f"{crumb.get('ts', '')} has no later upload-verification verdict "
                f"(state={state}, age={age}m, window={window_minutes}m)"
            ),
        }

    if last_results_idx is not None and (last_verdict_idx is None or last_verdict_idx < last_results_idx):
        verdict_txt = (
            "no verdict marker exists"
            if last_verdict_idx is None
            else f"latest verdict at {events[last_verdict_idx].get('ts', '')}"
        )
        return {
            "reason": "upload_verification_stale",
            "state": None,
            "stage": None,
            "round": None,
            "breadcrumb_ts": None,
            "age_minutes": None,
            "detail": (
                f"latest epm:results at {events[last_results_idx].get('ts', '')} "
                f"postdates the upload-verification evidence ({verdict_txt})"
            ),
        }
    return None
```

## 11. Decision Rationale

Infra task → hyperparameter grounding exempt; each design decision sourced to incident evidence / existing conventions:

1. **Blocking condition is "breadcrumb with no later verdict event", index-ordered, window-free.** *Why:* the refusal must hold for BOTH in-flight and stalled (a stalled verifier with no verdict is still absence-of-verdict; the brief's consideration 1 recommends refusing either way); index ordering mirrors `stage_dispatch_should_skip`'s later-event clearing and is immune to malformed `ts`. *Source:* incident #778 (recovery note 2026-07-01T20:37:59Z: results 18:47 → verification v1 18:55 → pod-terminated ~19:00 → v2 verdict FAIL later) + `task_workflow.py:1536` conventions.
2. **Window used only to CLASSIFY in-flight vs stalled (reason granularity), via `stage_dispatch_should_skip` at 15 min.** *Why:* reuses the established liveness-refresh semantics (an actively-working verifier refreshes; a dead one lapses) so the orchestrator's WAIT-vs-respawn routing has a reliable signal; 15 min is the documented `verifying`-stage window. *Source:* SKILL.md:5363-5368 (window table); `task_workflow.py:1536-1610`.
3. **Results-currency check (`upload_verification_stale`) included on the fallback path.** *Why:* the brief's consideration 2 — a stale prior-round PASS (incl. the sticky marker from a completed prior round) must not green-light a NEW round's teardown even when no breadcrumb was ever posted (verifier-skipped shape); vacuous when no `epm:results` exists, so crashed-run/6d.4 shapes are unaffected. *Source:* #778 follow-up-round timeline (r2 `epm:results` 2026-07-03T03:42:11Z vs prior round's verdicts) + the two-stage §6.5 ordering verified on r1 (03:29→03:36→09:31).
4. **`--skip-confirm-artifacts` binds on FRESH in-flight only; stalled/stale degrade to loud warning.** *Why:* the one non-negotiable is never destroying a RUNNING verifier round's pod; the skip flag's documented uses (#604 phase-mismatch after manual verification, crashed-before-artifacts, 6d.4 gate teardown, #935 done-poweroff) are operator decisions that may legitimately coexist with a dead verifier crumb — a hard refusal there would force a new override flag; the 15-min lapse is the flag-free escape. *Source:* SKILL.md:4063/4170/4877-4886 (documented skip recipes); brief consideration 3 ("at minimum a loud warning; weigh against the legitimate mid-pipeline gate teardowns").
5. **Exit 3 + JSON `reason`, not a new exit code (rejected: `EXIT_STILL_WAITING=75`).** *Why:* exit 3 already means "teardown SKIPPED, evidence preserved — investigate" to every caller (SKILL.md:4888-4891), which is the safe default for all three new reasons; the JSON `reason` is the established discriminator (`confirm_artifacts_no_declaration` vs `confirm_artifacts_failed` precedent at dispatch_issue.py:1674/1694); exit 75 would require auditing every finalize caller's rc handling for a marginal gain. *Source:* dispatch_issue.py:857-862 + existing exit-3 shapes; brief consideration 4's suggested shape.
6. **New helper lives in `task_workflow.py` (pure, events-list-in) + thin guarded wrapper in `dispatch_issue.py`.** *Why:* the scan reuses four private task_workflow helpers (importing them into a script would couple across the module boundary); a pure function over an events list is directly unit-testable without registry fixtures; the wrapper mirrors `_agent_upload_verification_passed`'s existing read-failure guard pattern. *Source:* `task_workflow.py:1502-1610` helper cluster; `dispatch_issue.py:1503-1544` guard pattern; brief constraint "reuse existing helpers".
7. **Wrapper read-failure direction = None (no blocker), not refusal.** *Why:* with unreadable events the PASS predicate also returns False, so the degrade cannot fire and teardown is already held by the existing exit-3 paths; a read-failure refusal would additionally break the crashed-run skip recovery while adding no safety. *Source:* `_agent_upload_verification_passed` docstring (:1508-1511, "the safe direction").
8. **`epm:failure` after the crumb does NOT rescue the fallback.** *Why:* a failed verifier round still produced no verdict — the stale PASS is still stale; refusing (as "stalled", naming re-spawn as recovery) is the fail-fast direction. Deliberate divergence from `stage_dispatch_should_skip`'s clearing (whose question is "may I re-DISPATCH?", where clearing on failure is correct — and which the recovery indeed permits). *Source:* CLAUDE.md "Fail fast — never hide failures".
9. **In-flight/stalled refusal also binds on the declaration-present mechanical path (gate placed before `fetch_results`).** *Why:* the Step 8 contract is "Both must pass before teardown" (SKILL.md:4840) — a mechanical PASS while the agent verifier is mid-round is the same incident class; placement before fetch keeps the refusal side-effect-free. Severable if the critics judge it scope creep (see §"Deviations"). *Source:* SKILL.md:4836-4840.
