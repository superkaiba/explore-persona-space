## 0. Plan Summary

- **What:** Add a fast, in-process check that the vendored Happy daemon still
  carries the EPS injection patch (sentinel v4) BEFORE any `spawn_session.py`
  path relies on `HAPPY_INITIAL_PROMPT` / `claudeArgs` injection. On a detected
  revert (or a missing daemon file, or a drifted daemon shape), **fail loud**
  with a message naming the exact re-apply + restart commands — never silently
  spawn a session that will sit idle and never fire its `/issue N` skill.
- **New code (3 surfaces):**

  `tmp_path`, monkeypatched daemon path; no real `/usr/lib/`, no `sudo`, no
  `npm`). Asserts the spawn guard raises `SystemExit` with the re-apply command
  when the sentinel is absent, distinguishes "missing daemon file" from "patch

## 1. Goal + acceptance criteria

**Goal (verbatim from the task body):** Make `spawn_session.py` verify (and
warn loudly about / fail loud on) the Happy daemon injection patch before
relying on `HAPPY_INITIAL_PROMPT` injection — so a silently-reverted patch
fails loud instead of producing idle "spawned but never ran" sessions.

**The failure this prevents:** the injection path is a `sudo` monkey-patch of a
vendored Happy file (`/usr/lib/node_modules/happy/dist/index-q9G4ktSK.mjs`,
sentinel v4) applied by `scripts/patch_happy_daemon.py`. It reverts on every
`npm update happy`. After a revert, the daemon ignores `claudeArgs` and never
reads `HAPPY_INITIAL_PROMPT`, so `spawn-issue --auto` / `spawn-campaign` spawn a
session that boots empty and never fires its skill — the exact #685 "silently
sat idle for 10 hours, never ran /issue 685" mode. Dormant today (patch applied)
but guaranteed to bite on the next Happy upgrade.

**Acceptance criteria (the Step 5 test-verdict, concrete pass/fail):**

1. `tests/test_happy_patch_check.py` PASSES, asserting all of:
   - When the daemon file contains the sentinel → the spawn guard returns
     cleanly (no raise), status classified `patched`.
   - When the daemon file exists but lacks the sentinel (revert) → the spawn
     guard raises `SystemExit`, and the message contains the literal re-apply
     command `sudo uv run python scripts/patch_happy_daemon.py apply` AND the
     restart command `happy daemon stop && happy daemon start`.
   - When the daemon file is absent entirely (Happy never installed) → the
     guard does NOT raise (loud WARN + proceed; distinct, clearly-worded
     condition — see §11), classified `missing`.
   - When the daemon file exists, lacks the sentinel, AND a search-string no
     longer matches (shape drift) → classified `drifted` and the guard raises
     `SystemExit` with a message naming manual reconciliation (NOT a blind
     re-apply, since auto-apply can't work on a drifted file).
   - The watcher pass writes an escalate-only sidecar row on a revert/drift
     under `--dry-run` (decides + logs, never mutates) and is a clean no-op
     when the daemon file is present + patched.
2. `uv run ruff check` on all five touched files PASSES.
3. `uv run python scripts/workflow_lint.py --check-references` PASSES (no broken
   `scripts/<name>.py` references introduced into the doc surface).
4. Manual smoke (documented, run by the implementer, not gated): on THIS VM
   where the patch is currently applied, `python scripts/_happy_patch_check.py`
   prints `patched` and exits 0; temporarily pointing the helper at a synthetic
   reverted file makes `spawn-issue --auto` fail loud with the re-apply message.

## 4. Design

### Method delta (what's new vs current `scripts/spawn_session.py`)

Current: `cmd_spawn_issue` / `cmd_spawn_campaign` build a `body` with
`environmentVariables` + `claudeArgs` and immediately `post("/spawn-session",
body)` — with zero verification that the daemon will honor those fields.

Delta: add a single guard call at the TOP of the injection-dependent branch,
BEFORE `post()`. The guard reads the daemon file once, checks for the sentinel,
and either returns cleanly or `sys.exit`s with an actionable message.

### Surface 1 (NEW) — `scripts/_happy_patch_check.py`

A ~50-line module that is the single source of truth for the sentinel + daemon
path + classification. No argparse-as-primary (it's a library), but a thin
`if __name__ == "__main__"` prints the status word + exits with the
patch_happy_daemon-compatible code for manual smoke.

```python
"""Single source of truth for 'is the Happy daemon injection patch applied?'.

Imported by spawn_session.py (pre-spawn guard) and autonomous_session_watch.py
(proactive escalate-only pass). patch_happy_daemon.py also imports SENTINEL /
DAEMON_FILE / classify_patch from here so there is exactly ONE definition of
the sentinel string and the daemon file path.

Cheap by construction: a single file read + substring test (single-digit ms),
no subprocess, no root. Safe when the daemon file is absent entirely.
"""
from __future__ import annotations

from dataclasses import dataclass
from pathlib import Path

DAEMON_FILE = Path("/usr/lib/node_modules/happy/dist/index-q9G4ktSK.mjs")
SENTINEL = (
    "// EPS-PATCH: claudeArgs-forwarding + initial-prompt-seed + bypass + "
    "no-takeover-downgrade v4"
)
# Long, stable substrings of the patch sites — used ONLY to distinguish a clean
# revert (re-applyable) from a drifted daemon shape (manual reconciliation).
# Kept minimal + import-light; the authoritative full PATCHES list stays in
# patch_happy_daemon.py. We import these two markers from there to avoid drift.

REAPPLY_CMD = "sudo uv run python scripts/patch_happy_daemon.py apply"
RESTART_CMD = "happy daemon stop && happy daemon start"

@dataclass(frozen=True)
class PatchStatus:
    state: str            # "patched" | "reverted" | "drifted" | "missing"
    detail: str           # human one-liner

def classify_patch(daemon_file: Path | None = None) -> PatchStatus:
    f = daemon_file or DAEMON_FILE
    if not f.is_file():
        return PatchStatus("missing", f"Happy daemon file not found at {f}")
    text = f.read_text()
    if SENTINEL in text:
        return PatchStatus("patched", "sentinel present")
    # Reverted. Distinguish a clean revert (search-strings still match -> a
    # plain `apply` will work) from a drifted shape (a search-string no longer
    # matches -> manual reconciliation needed). Reuse patch_happy_daemon's
    # PATCHES so there is one shape definition.
    from importlib import import_module
    patch_mod = import_module("patch_happy_daemon")  # scripts/ on sys.path
    missing = [name for name, search, _ in patch_mod.PATCHES if search not in text]
    if missing:
        return PatchStatus("drifted",
                           "daemon upgraded; PATCHES no longer match: "
                           + ", ".join(missing))
    return PatchStatus("reverted", "sentinel absent; search-strings still match")

if __name__ == "__main__":
    import sys
    st = classify_patch()
    print(st.state, "—", st.detail)
    sys.exit({"patched": 0, "reverted": 1, "drifted": 2, "missing": 3}[st.state])
```

**Refactor `patch_happy_daemon.py` to import from the helper (single source of
truth):** change its `DAEMON_FILE` + `SENTINEL` module constants to
`from _happy_patch_check import DAEMON_FILE, SENTINEL` (it already lives in
`scripts/`, so a sibling import resolves when run via `uv run python
scripts/patch_happy_daemon.py` — `scripts/` is on `sys.path[0]`). Leave
`PATCHES`, `cmd_apply`, `cmd_restore` exactly as-is (the helper imports
`PATCHES` back, a one-way dependency: helper → patch_mod.PATCHES only for the
drift classification; constants flow patch_mod ← helper). This is a clean
acyclic split: `_happy_patch_check` owns `SENTINEL`/`DAEMON_FILE`/`classify`;
`patch_happy_daemon` owns `PATCHES`/`apply`/`restore` and imports the two
constants. (Verify at implement time that the lazy `import_module` inside
`classify_patch` avoids any import cycle — it is deferred to call time, so even
if a future edit makes `patch_happy_daemon` import `classify_patch` at module
top-level, the cycle is broken by the lazy import.)

### Surface 2 — `scripts/spawn_session.py` guard

Add `import subprocess`? **No** — the guard imports the helper in-process (no
subprocess). Add near the top, with first use, a guard function:

```python
def _verify_happy_patch_or_die(*, context: str) -> None:
    """Fail loud if the Happy daemon injection patch is reverted/drifted.

    Called BEFORE any spawn path that relies on HAPPY_INITIAL_PROMPT /
    claudeArgs injection. A reverted patch makes the daemon ignore those
    fields, so the spawned session boots empty and never fires its skill
    (the #685 'spawned but never ran' idle-session mode). Single-digit-ms:
    one file read + substring, no subprocess, no root.

    `context` names the caller (e.g. "spawn-issue --auto") for the message.
    """
    import _happy_patch_check as hpc  # scripts/ is on sys.path[0]

    st = hpc.classify_patch()
    if st.state == "patched":
        return
    if st.state == "missing":
        # Happy was never installed on this host: the daemon RPC itself will
        # fail loudly downstream (daemon_port() exits on a missing state file).
        # Warn, don't die — dying here would be a confusing second error.
        print(
            f"WARNING [{context}]: {st.detail}. If Happy IS installed, the "
            f"injection patch cannot be verified; expect the daemon RPC to "
            f"surface the real error.",
            file=sys.stderr,
        )
        return
    # reverted | drifted -> the daemon is up but will IGNORE the injected
    # prompt/args, producing an idle session. Fail loud with the fix.
    if st.state == "reverted":
        fix = (
            f"Re-apply it:\n    {hpc.REAPPLY_CMD}\n"
            f"then restart the daemon:\n    {hpc.RESTART_CMD}"
        )
    else:  # drifted
        fix = (
            "The Happy daemon shape has DRIFTED (likely an `npm update happy`); "
            "a blind re-apply will not work. Inspect the file and update "
            "PATCHES in scripts/patch_happy_daemon.py, then:\n"
            f"    {hpc.REAPPLY_CMD}\n    {hpc.RESTART_CMD}"
        )
    sys.exit(
        f"ABORT [{context}]: the Happy daemon injection patch is "
        f"{st.state} ({st.detail}).\n"
        f"Spawning now would create a session that IGNORES its initial prompt "
        f"and sits idle forever (the #685 failure mode).\n{fix}"
    )
```

**Call sites** (guard fires only on injection-dependent paths, before `post()`):

- `cmd_spawn_issue` — call `_verify_happy_patch_or_die(context="spawn-issue")`
  inside the `if prompt is not None:` block (the load-bearing #685 path),
  immediately before `body["environmentVariables"] = {...}`. Do NOT call it in
  the bare `elif extra_args:` path? **Decision (see §11): DO call it there too**
  — a reverted patch also drops model/betas/effort overrides for a bare
  interactive session, which is a silent-wrong-model footgun; but since that
  path is non-fatal (session still boots), the guard's `missing`→warn /
  `reverted`→die contract still applies and is correct. Place ONE call before
  the `if prompt is not None / elif extra_args` block, gated on "any claudeArgs
  will be sent" — i.e. call it when `prompt is not None or extra_args`. This is
  the cleanest single insertion point.
- `cmd_spawn_campaign` — call `_verify_happy_patch_or_die(context="spawn-campaign")`
  immediately before building `body` (it ALWAYS injects). Place it after the
  kind/status validation (so a wrong-kind task still gets its specific error
  first) and before `body = {...}`.
- `cmd_spawn_pm` — call `_verify_happy_patch_or_die(context="spawn-pm")` ONLY
  inside `if extra_args:` (PM injects nothing unless overrides are present).
  Lower severity, but consistent.

### Surface 3 — `scripts/autonomous_session_watch.py` proactive pass

Add an escalate-only `happy_patch_pass(dry_run)` modeled on
`subfloor_sentinel_pass` / `data_disk_pass`:

```python
def happy_patch_pass(dry_run: bool) -> None:
    """Proactively surface a reverted/drifted Happy injection patch.

    The spawn-path guard (spawn_session._verify_happy_patch_or_die) is
    REACTIVE — it only fires at the next spawn attempt. This pass is PROACTIVE:
    it runs every 10-min tick, so a revert (typically from `npm update happy`)
    is surfaced within ~10 min rather than at the next autonomous dispatch.
    Escalate-only: never re-applies (that needs sudo); writes a sidecar row +
    fail-soft Telegram push, deduped per (state) so it alerts once per episode.
    Clean no-op when the patch is present or the daemon file is absent.
    """
    import sys as _sys
    sp = str(PROJECT_ROOT / "scripts")
    if sp not in _sys.path:
        _sys.path.insert(0, sp)
    try:
        import _happy_patch_check as hpc
        st = hpc.classify_patch()
    except Exception as exc:        # fail-soft like the disk passes
        print(f"  happy-patch: classify failed ({exc}); skipping", file=_sys.stderr)
        return
    if st.state in ("patched", "missing"):
        # missing = Happy not installed on this host; not an EPS concern here.
        _clear_happy_patch_state()      # reset dedup so a future revert re-alerts
        return
    # reverted | drifted -> escalate-only
    if _happy_patch_already_alerted(st.state):
        print(f"  happy-patch: {st.state} (already alerted this episode)")
        return
    event = {
        "ts": _utc_now_iso(), "band": "happy-patch", "state": st.state,
        "detail": st.detail, "reapply_cmd": hpc.REAPPLY_CMD,
        "restart_cmd": hpc.RESTART_CMD,
    }
    _append_disk_guard_sidecar(event, dry_run)   # reuse the shared sidecar stream
    _telegram_push_fail_soft(
        f"Happy injection patch {st.state}: {st.detail}. "
        f"Autonomous spawns will produce idle sessions until re-applied: "
        f"{hpc.REAPPLY_CMD} && {hpc.RESTART_CMD}",
        dry_run=dry_run,
    )
    if not dry_run:
        _mark_happy_patch_alerted(st.state)
```

Wire it: a daemon-INDEPENDENT pass (reads a local file only, like
`vm_disk_pass`), called in `main()` next to `vm_disk_pass` / `data_disk_pass`
(before the daemon-gated session passes), plus a `--happy-patch-only` flag +
early-return short-circuit mirroring `--gc-only` for a single-pass live smoke.
Dedup state file `~/.eps-autonomous/happy-patch-alert.json` (or reuse the
existing per-episode-state helpers' directory). Reuse the existing
Telegram-push helper if one exists in the watcher (the disk passes use a
fail-soft push); if the helper is named differently, the implementer wires the
real one — the pattern, not the exact symbol, is the contract here.

## 11. Decision Rationale

- **Subprocess vs import (the helper).**
  - *What:* `spawn_session.py` + the watcher IMPORT `_happy_patch_check`
    in-process; they do NOT shell out to `patch_happy_daemon.py check`.
  - *Why:* the guard is in the hot dispatch path; a subprocess (`uv run python
    …`) adds ~hundreds of ms of interpreter startup per spawn AND
    `cmd_check`'s stdout prose would pollute the spawn output. An in-process
    file-read + substring is single-digit ms and silent. The task's own
    constraint ("must be FAST … single-digit milliseconds") points here.
  - *Source:* task body constraint + CLAUDE.md "Use … the appropriate
    dedicated tool" + the watcher's own disk passes (in-process file reads, no
    subprocess).
  - *Alternatives:* subprocess `patch_happy_daemon.py check` (rejected: slow,
    noisy). Re-implementing the sentinel check inline in `spawn_session.py`
    (rejected: duplicates the sentinel literal → drift risk; the #530-style
    "constant in two places" footgun).

- **Promote to a shared `scripts/_happy_patch_check.py` (vs inline in spawn_session).**
  - *What:* the sentinel/path/classify logic lives in ONE new module both
    `spawn_session.py` and the watcher import; `patch_happy_daemon.py` imports
    the two constants back.
  - *Why:* the watcher pass needs the same check; a shared helper is the only
    way to keep ONE definition of the sentinel + daemon path across three
    consumers. CLAUDE.md "Reuse existing … don't reinvent" + single-source-of-
    truth.
  - *Source:* CLAUDE.md code-reuse rule; planning task instruction #4 ("Should
    the check helper … be promoted to `scripts/_happy_patch_check.py` for reuse
    by the watcher?" → yes, because the watcher reuses it).
  - *Alternatives:* inline in `spawn_session.py` + the watcher imports it FROM
    `spawn_session` (rejected: pulls the watcher's import of `spawn_session`'s
    heavy urllib/argparse surface for a one-line check; a tiny dedicated helper
    is leaner).

- **Fail-loud-only vs auto-re-apply in the spawn path.**
  - *What:* on `reverted`/`drifted`, `sys.exit` with the re-apply command; do
    NOT attempt `sudo … apply` automatically.
  - *Why:* auto-re-apply needs `sudo`, which would block on a password prompt in
    a non-interactive autonomous spawn (hanging the dispatch — worse than the
    idle session). The task body itself "prefers fail-loud + clear re-apply
    command over silent spawn."
  - *Source:* task body ("Auto-re-apply with sudo in the spawn path is unsafe …
    fail-loud + clear re-apply command") + CLAUDE.md "Fail fast — never hide
    failures."
  - *Alternatives:* auto-`sudo apply` (rejected: password-prompt hang in the
    autonomous path). Silent warn + proceed on a revert (rejected: that IS the
    #685 bug — an idle session is the silent failure).

- **`missing` daemon file → WARN + proceed (not die).**
  - *What:* when the daemon file is absent entirely, the guard prints a loud
    WARNING and returns; it does NOT `sys.exit`.
  - *Why:* "daemon file missing" means Happy was never installed on this host —
    a DIFFERENT condition than "patch reverted." The daemon RPC (`post()` →
    `daemon_port()`) already fails loud on a missing `daemon.state.json`, so
    dying in the guard would produce a confusing second error before the real
    one. The task's constraint explicitly requires distinguishing these two
    conditions.
  - *Source:* task constraint ("MUST be safe when the daemon file is missing
    entirely … that's a different error than 'patch reverted'") + `daemon_port`
    already fail-loud on a missing state file (read this session, line 482).
  - *Alternatives:* die on missing (rejected: false-positive block on a fresh
    VM; redundant with the downstream daemon-down error).

- **`drifted` (shape change) → die with manual-reconciliation msg, not blind re-apply.**
  - *What:* when the sentinel is absent AND a `PATCHES` search-string no longer
    matches, the message says the daemon shape drifted and a blind `apply`
    won't work; inspect + update `PATCHES`.
  - *Why:* mirrors `patch_happy_daemon.cmd_check`'s own exit-code-2 semantics
    (search-strings don't match → "the Happy daemon has probably been
    upgraded"). Telling the user to blind-`apply` a drifted file would just make
    `cmd_apply` abort ("patch site matches 0 times").
  - *Source:* `patch_happy_daemon.cmd_check` exit-code-2 logic (read this
    session, lines 191-199) + the clarifier's exit-code table.
  - *Alternatives:* collapse reverted+drifted into one message (rejected: a
    drifted file can't be fixed by `apply`, so the message must differ).

- **Watcher proactive pass: yes.**
  - *What:* add `happy_patch_pass` to `autonomous_session_watch.py` (every 10
    min, escalate-only sidecar + Telegram).
  - *Why:* the spawn-path guard is REACTIVE (catches a revert only at the next
    spawn). The watcher pass is PROACTIVE: a revert from `npm update happy`
    surfaces within ~10 min, not at the next autonomous dispatch (which might be
    hours away). The check is one file read — negligible cost on a pass that
    already does heavier work. The planning instruction #2 recommends including
    it.
  - *Source:* planning instruction #2 (RECOMMENDATION) + the watcher's existing
    escalate-only disk-pass pattern (`data_disk_pass`, line 1880).
  - *Alternatives:* spawn-path guard only (rejected: leaves a multi-hour blind
    window between a revert and the next spawn). A separate dedicated cron
    (rejected: the watcher already runs every 10 min with the sidecar +
    Telegram plumbing; a new cron is redundant infrastructure).

- **`cmd_spawn_pm` guard placement (inside `if extra_args:` only).**
  - *What:* PM gets the guard only when model/betas/effort overrides are
    present.
  - *Why:* the PM session injects NO initial prompt; a revert there only drops
    overrides. Guarding the no-override PM spawn would be a false alarm (nothing
    relies on the patch). The clarifier flags PM as "much less severe."
  - *Source:* clarifier context (PM "forwards claudeArgs only when … overrides
    are present … much less severe").
  - *Alternatives:* always guard PM (rejected: false-alarm on the common
    no-override PM spawn). Never guard PM (acceptable but inconsistent; guarding
    the override path is cheap correctness).

- **Document the new watcher pass in `background-automation.md`.**
  - *What:* add a short paragraph under the Autonomous-session watcher section.
  - *Why:* CLAUDE.md's always-on summary + `background-automation.md` enumerate
    the watcher passes; adding a pass without documenting it makes the spec
    stale. (`background-automation.md` is workflow surface.)
  - *Source:* the workflow-surface consistency rule (CLAUDE.md: "the
    implementing file … must enforce" / keep docs in sync).
  - *Alternatives:* skip the doc (rejected: stale pass list).
