## 1. Goal + acceptance criteria

**Goal (verbatim from the task body):** Make `spawn_session.py` verify (and
warn loudly about / fail loud on) the Happy daemon injection patch before
relying on `HAPPY_INITIAL_PROMPT` injection — so a silently-reverted patch
fails loud instead of producing idle "spawned but never ran" sessions.

**The failure this prevents:** the injection path is a `sudo` monkey-patch of a
vendored Happy file (`/usr/lib/node_modules/happy/dist/index-q9G4ktSK.mjs`,
sentinel v4) applied by `scripts/patch_happy_daemon.py`. It reverts on every
`npm update happy` — AND the hashed bundle is RENAMED on update (e.g.
`index-q9G4ktSK.mjs` → `index-<newhash>.mjs`), so the cited daemon-file path
goes ABSENT while the daemon process stays up and reachable. After a revert (or
a hash-rename), the daemon ignores `claudeArgs` and never reads
`HAPPY_INITIAL_PROMPT`, so `spawn-issue --auto` / `spawn-campaign` spawn a
session that boots empty and never fires its skill — an idle "spawned but never
ran" session. This is the failure CLASS behind the #685 symptom; note the
2026-06-28 idle-session pile was the DISTINCT #720 mapping-loss / completion
non-self-termination cause, not a patch revert (the guard message says so, so a
future operator doesn't misdiagnose a #720-class regression as a patch revert).
Dormant today (patch applied) but guaranteed to bite on the next Happy upgrade.

**Acceptance criteria (the Step 5 test-verdict, concrete pass/fail):**

## 4. Design

### Method delta (what's new vs current `scripts/spawn_session.py`)

Current: `cmd_spawn_issue` / `cmd_spawn_campaign` build a `body` with
`environmentVariables` + `claudeArgs` and immediately `post("/spawn-session",
body)` — with zero verification that the daemon will honor those fields.

Delta: add a single guard call at the TOP of the injection-dependent branch,
BEFORE `post()`. The guard reads the daemon file once, classifies, and either
returns cleanly or `sys.exit`s with an actionable message. On the `missing`
classification it additionally consults `DAEMON_STATE` (the daemon RPC's own
state file) to decide WARN-vs-die.

### Surface 1 (NEW) — `scripts/_happy_patch_check.py`

A ~55-line module that is the single source of truth for the sentinel + daemon
path + classification. No argparse-as-primary (it's a library), but a thin
`if __name__ == "__main__"` prints the status word + exits with the
patch_happy_daemon-compatible code for manual smoke.

```python
"""Single source of truth for 'is the Happy daemon injection patch applied?'.

Imported by spawn_session.py (pre-spawn guard) and autonomous_session_watch.py
(proactive escalate-only pass). patch_happy_daemon.py also imports SENTINEL /
DAEMON_FILE from here so there is exactly ONE definition of the sentinel string
and the daemon file path.

Cheap by construction: a single file read + substring test (single-digit ms),
no subprocess, no root. Safe when the daemon file is absent entirely (returns
the `missing` state — the spawn guard then disambiguates 'Happy never
installed' from 'patch file hash-renamed away by npm update' via a second,
independent check on the daemon RPC's daemon.state.json — see spawn_session.py).
"""
from __future__ import annotations

from dataclasses import dataclass
from pathlib import Path

DAEMON_FILE = Path("/usr/lib/node_modules/happy/dist/index-q9G4ktSK.mjs")
SENTINEL = (
    "// EPS-PATCH: claudeArgs-forwarding + initial-prompt-seed + bypass + "
    "no-takeover-downgrade v4"
)

REAPPLY_CMD = "sudo uv run python scripts/patch_happy_daemon.py apply"
RESTART_CMD = "happy daemon stop && happy daemon start"


@dataclass(frozen=True)
class PatchStatus:
    state: str            # "patched" | "reverted" | "drifted" | "missing"
    detail: str           # human one-liner


def _file_text(f: Path) -> str:
    # Pin utf-8 for locale determinism (the .mjs is ascii/utf-8 source).
    return f.read_text(encoding="utf-8")


def classify_patch(daemon_file: Path | None = None) -> PatchStatus:
    f = daemon_file or DAEMON_FILE
    if not f.is_file():
        return PatchStatus("missing", f"Happy daemon file not found at {f}")
    text = _file_text(f)
    if SENTINEL in text:
        return PatchStatus("patched", "sentinel present")
    # Reverted. Distinguish a clean revert (search-strings still match -> a
    # plain `apply` will work) from a drifted shape (a search-string no longer
    # matches -> manual reconciliation). Reuse patch_happy_daemon's PATCHES so
    # there is one shape definition. LAZY import to avoid any cycle.
    from importlib import import_module
    patch_mod = import_module("patch_happy_daemon")  # scripts/ on sys.path
    missing = [name for name, search, _ in patch_mod.PATCHES if search not in text]
    if missing:
        return PatchStatus("drifted",
                           "daemon upgraded; PATCHES no longer match: "
                           + ", ".join(missing))
    return PatchStatus("reverted", "sentinel absent; search-strings still match")


if __name__ == "__main__":
    import sys
    st = classify_patch()
    print(st.state, "—", st.detail)
    sys.exit({"patched": 0, "reverted": 1, "drifted": 2, "missing": 3}[st.state])
```

### Surface 2 — `scripts/spawn_session.py` guard

The guard imports the helper in-process (no subprocess). Add the function near
the top with its first use; it consults BOTH the helper's classification AND the
module's existing `DAEMON_STATE` constant for the two-step `missing` probe:

```python
def _verify_happy_patch_or_die(*, context: str) -> None:
    """Fail loud if the Happy daemon injection patch is reverted/drifted/moved.

    Called BEFORE any spawn path that relies on HAPPY_INITIAL_PROMPT /
    claudeArgs injection. A reverted (or hash-renamed-away) patch makes the
    daemon ignore those fields, so the spawned session boots empty and never
    fires its skill — an idle 'spawned but never ran' session (the failure
    CLASS behind #685's symptom; note the 2026-06-28 idle-session pile itself
    was the distinct #720 mapping-loss cause, not a patch revert). Single-
    digit-ms: one or two file reads + substring, no subprocess, no root.

    `context` names the caller (e.g. "spawn-issue --auto") for the message.

    The `missing` classification (the daemon .mjs file is absent) is AMBIGUOUS
    and is disambiguated with a SECOND, INDEPENDENT check on the daemon RPC's
    own state file (DAEMON_STATE / daemon.state.json), since the two files are
    independent (classify_patch reads the vendored .mjs; daemon reachability
    lives in daemon.state.json):
      - .mjs missing AND daemon.state.json missing  -> Happy is not installed
        on this host -> WARN + proceed (a legitimate fresh VM not running the
        autonomous loop; the downstream daemon RPC would fail loud anyway).
      - .mjs missing BUT daemon.state.json present   -> Happy IS reachable but
        the patch file moved (the canonical `npm update happy` hash-rename:
        index-<oldhash>.mjs -> index-<newhash>.mjs) -> the patch CANNOT be
        verified and is almost certainly NOT applied to the new bundle -> DIE
        loud. Re-applying will fail loud if the file is truly gone, which is the
        correct diagnosis.
    """
    import _happy_patch_check as hpc  # scripts/ is on sys.path[0]

    st = hpc.classify_patch()
    if st.state == "patched":
        return

    if st.state == "missing":
        # Two-step probe: distinguish 'Happy never installed' (safe) from
        # 'Happy reachable but patch file moved' (the #685 post-update state).
        if not DAEMON_STATE.is_file():
            print(
                f"WARNING [{context}]: {st.detail}. No Happy daemon state file "
                f"at {DAEMON_STATE} either -> no Happy install detected, "
                f"skipping the injection-patch guard.",
                file=sys.stderr,
            )
            return
        # Daemon reachable, patch file absent -> die loud.
        fix = (
            "The Happy daemon patch file is ABSENT but the daemon IS reachable "
            "(daemon.state.json present) -> the vendored bundle was almost "
            "certainly hash-renamed by `npm update happy` and is now UNPATCHED. "
            "Re-apply against the new bundle:\n"
            f"    {hpc.REAPPLY_CMD}\n"
            "(this will fail loud if the file is genuinely gone — that is the "
            "correct diagnosis), then restart the daemon:\n"
            f"    {hpc.RESTART_CMD}"
        )
        sys.exit(
            f"ABORT [{context}]: the Happy daemon injection patch could not be "
            f"verified ({st.detail}), but the daemon is reachable.\n"
            f"Spawning now would create a session that IGNORES its initial "
            f"prompt and sits idle forever.\n{fix}"
        )

    # reverted | drifted -> the daemon is up but will IGNORE the injected
    # prompt/args, producing an idle session. Fail loud with the fix.
    if st.state == "reverted":
        fix = (
            f"Re-apply it:\n    {hpc.REAPPLY_CMD}\n"
            f"then restart the daemon:\n    {hpc.RESTART_CMD}"
        )
    else:  # drifted
        fix = (
            "The Happy daemon shape has DRIFTED (likely an `npm update happy`); "
            "a blind re-apply will not work. Inspect the file and update "
            "PATCHES in scripts/patch_happy_daemon.py, then:\n"
            f"    {hpc.REAPPLY_CMD}\n    {hpc.RESTART_CMD}"
        )

def happy_patch_pass(dry_run: bool) -> None:
    """Proactively surface a reverted/drifted Happy injection patch.

    The spawn-path guard (spawn_session._verify_happy_patch_or_die) is
    REACTIVE — it only fires at the next spawn attempt. This pass is PROACTIVE:
    it runs every 10-min tick, so a revert (typically from `npm update happy`)
    is surfaced within ~10 min rather than at the next autonomous dispatch.
    Escalate-only: never re-applies (that needs sudo); writes a sidecar row +
    fail-soft Telegram push, deduped per (state) so it alerts once per episode.
    Clean no-op when the patch is present or the daemon file is absent.
    """
    import sys as _sys
    sp = str(PROJECT_ROOT / "scripts")
    if sp not in _sys.path:
        _sys.path.insert(0, sp)
    try:
        import _happy_patch_check as hpc
        st = hpc.classify_patch()
    except Exception as exc:        # fail-soft like the disk passes
        print(f"  happy-patch: classify failed ({exc}); skipping", file=_sys.stderr)
        return
    if st.state in ("patched", "missing"):
        # missing = the .mjs file absent; on the watcher VM this is the
        # 'Happy not installed here' case (escalate-only stays conservative —
        # the spawn-path guard owns the precise reachability disambiguation).
        _clear_happy_patch_alert()      # reset dedup so a future revert re-alerts
        return
    # reverted | drifted -> escalate-only
    if _happy_patch_already_alerted(st.state):
        print(f"  happy-patch: {st.state} (already alerted this episode)")
        return
    event = {
        "ts": _utc_now_iso(), "band": "happy-patch", "state": st.state,
        "detail": st.detail, "reapply_cmd": hpc.REAPPLY_CMD,
        "restart_cmd": hpc.RESTART_CMD,
    }
    _append_disk_guard_sidecar(event, dry_run)   # reuse the shared sidecar stream
    _telegram_push(
        f"Happy injection patch {st.state}: {st.detail}. "
        f"Autonomous spawns will produce idle sessions until re-applied: "
        f"{hpc.REAPPLY_CMD} && {hpc.RESTART_CMD}",
        dry_run,
    )
    if not dry_run:
        _mark_happy_patch_alerted(st.state)
```

## 11. Decision Rationale

- **Subprocess vs import (the helper).**
  - *What:* `spawn_session.py` + the watcher IMPORT `_happy_patch_check`
    in-process; they do NOT shell out to `patch_happy_daemon.py check`.
  - *Why:* the guard is in the hot dispatch path; a subprocess (`uv run python
    …`) adds ~hundreds of ms of interpreter startup per spawn AND
    `cmd_check`'s stdout prose would pollute the spawn output. An in-process
    file-read + substring is single-digit ms and silent.
  - *Source:* task body constraint ("must be FAST … single-digit milliseconds")
    + the watcher's own disk passes (in-process file reads, no subprocess).
  - *Alternatives:* subprocess `patch_happy_daemon.py check` (rejected: slow,
    noisy). Inline sentinel check in `spawn_session.py` (rejected: duplicates
    the sentinel literal → drift risk).

- **Promote to a shared `scripts/_happy_patch_check.py` (vs inline in spawn_session).**
  - *What:* the sentinel/path/classify logic lives in ONE new module both
    `spawn_session.py` and the watcher import; `patch_happy_daemon.py` imports
    the two constants back.
  - *Why:* the watcher pass needs the same check; a shared helper is the only
    way to keep ONE definition of the sentinel + daemon path across three
    consumers.
  - *Source:* CLAUDE.md code-reuse rule; planning task instruction #4.
  - *Alternatives:* inline in `spawn_session.py` + the watcher imports it FROM
    `spawn_session` (rejected: pulls the watcher into spawn_session's heavy
    urllib/argparse surface for a one-line check).

- **Fail-loud-only vs auto-re-apply in the spawn path.**
  - *What:* on `reverted`/`drifted`/`missing-with-daemon-reachable`, `sys.exit`
    with the re-apply command; do NOT attempt `sudo … apply` automatically.
  - *Why:* auto-re-apply needs `sudo`, which would block on a password prompt in
    a non-interactive autonomous spawn (hanging the dispatch — worse than the
    idle session). The task body prefers fail-loud + clear re-apply command.
  - *Source:* task body + CLAUDE.md "Fail fast — never hide failures."
  - *Alternatives:* auto-`sudo apply` (rejected: password-prompt hang). Silent
    warn + proceed on a revert (rejected: that IS the #685 bug).

- **`missing` daemon file → TWO-STEP PROBE (not unconditional WARN+proceed).**
    [REVISED in v2 — Must-Fix #1]
  - *What:* when the helper classifies `missing` (the vendored `.mjs` is
    absent), the spawn guard runs a SECOND, INDEPENDENT check on the daemon
    RPC's own state file (`DAEMON_STATE` = `~/.happy/daemon.state.json`):
    `.mjs` missing AND `daemon.state.json` missing → Happy not installed → loud
    WARN + proceed; `.mjs` missing BUT `daemon.state.json` present → Happy
    reachable but the patch file moved → DIE loud.
  - *Why:* the v1 dismissal ("daemon RPC `post()` → `daemon_port()` already
    fails loud on a missing daemon file") was WRONG because `daemon_port()`
    checks `DAEMON_STATE` (the `.json`), NOT `DAEMON_FILE` (the `.mjs`) — the two
    files are INDEPENDENT (confirmed at `spawn_session.py:38,482`). On
    `npm update happy` the hashed bundle is RENAMED (`index-q9G4ktSK.mjs` →
    `index-<newhash>.mjs`), so `classify_patch` reads "file not found" → `missing`
    WHILE `daemon.state.json` still exists and the daemon is reachable → `post()`
    succeeds → injection silently dropped → idle "spawned but never ran"
    session. That is precisely #685 reintroduced. The two-step probe is the
    PRECISE disambiguation: it distinguishes "Happy never installed" (the
    legitimate fresh-VM exemption — a VM not running the autonomous loop won't
    spawn anyway) from "Happy upgraded, hash bundle moved" (the dangerous state
    that MUST die). Re-applying against the new bundle is the correct fix; if the
    file is genuinely gone, `apply` fails loud — also the correct diagnosis.
  - *Source:* Phase-2 methodology reconciler (verified against
    `spawn_session.py:38,482`); `daemon_port()` reads `DAEMON_STATE` (line 482).
  - *Alternatives considered:* (option 1) promote `missing` to die-fast
    unconditionally with a `which happy` / `not DAEMON_STATE.exists()` one-line
    fresh-VM escape — simpler but coarser and loses the precise "installed but
    upgraded" vs "never installed" distinction at the daemon-RPC level; (chosen
    option 2) the two-step `DAEMON_STATE` probe — more precise, reuses an
    existing module constant + the exact predicate `daemon_port()` already
    trusts, no new dependency. Rejected (v1) unconditional WARN+proceed: leaves
    #685 open on the most common revert trigger.

- **`drifted` (shape change) → die with manual-reconciliation msg, not blind re-apply.**
  - *What:* when the sentinel is absent AND a `PATCHES` search-string no longer
    matches, the message says the daemon shape drifted and a blind `apply`
    won't work; inspect + update `PATCHES`.
  - *Why:* mirrors `patch_happy_daemon.cmd_check`'s own exit-code-2 semantics
    (search-strings don't match → "the Happy daemon has probably been
    upgraded"). Blind-`apply` of a drifted file just makes `cmd_apply` abort.
  - *Source:* `patch_happy_daemon.cmd_check` exit-code-2 logic.
  - *Alternatives:* collapse reverted+drifted into one message (rejected: a
    drifted file can't be fixed by `apply`).

- **Watcher proactive pass: yes, in the daemon-INDEPENDENT block.**
  - *What:* add `happy_patch_pass` to `autonomous_session_watch.py` (every 10
    min, escalate-only sidecar + `_telegram_push`), wired between lines
    12641-12656 next to `vm_disk_pass`/`data_disk_pass`/`program_orchestrator_

- **`cmd_spawn_pm` guard placement (inside `if extra_args:` only) — deliberate asymmetry.**
