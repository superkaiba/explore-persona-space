## 2. Prior work (mechanism verification — all quoted from source/probes this session)

**Kernel semantics (`oom_score_adj`).** Per-process, range −1000..+1000, inherited across `fork()` and preserved across `execve()` — the standard basis for "protect the leader, children inherit" ([LWN: Taming the OOM killer](https://lwn.net/Articles/317814/); confirmed by the systemd `OOMScoreAdjust` inheritance behavior in [nomad#10663](https://github.com/hashicorp/nomad/issues/10663)). Inheritance is forward-only: a child forked BEFORE the adjustment does NOT retroactively get it — hence the session sweep below, not a leader-only choom.

**earlyoom victim selection (installed v1.6.2, read from tag source `kill.c` ~104-163).** `badness = /proc/<pid>/oom_score` (kernel-computed — already includes `oom_score_adj`), then `+300` if comm matches `--prefer`, `−300` if it matches `--avoid`; the max-badness process is SIGTERMed (SIGKILL at the lower threshold); the ONLY adj special case is a hard skip at exactly `−1000` ("Skip processes with oom_score_adj = -1000, like the kernel oom killer would"). The `-i` flag (not set on this VM) strips only POSITIVE adj. The v1.6.2 manpage sentence "for processes matched by --prefer, negative oom_score_adj values are not taken into account… at least 300" describes the pre-5.9 kernel's 0-floored `/proc/pid/oom_score` display (issue [rfjakob/earlyoom#159](https://github.com/rfjakob/earlyoom/issues/159)), not v1.6.2 code — no such clause exists in the selection path, and the empirical probe below overrides the concern on this kernel.

**This VM's live config** (`/etc/default/earlyoom`, read this session): `-m 10 -s 10 -r 3600 --prefer (^|/)(pytest|python3?)$ --avoid (^|/)(sshd|systemd|dockerd|node|claude|happy)$ -n`. Every python workload gets +300 — a long sanctioned fit is the designated victim by construction.

**Empirical probe (this box, kernel 6.8.0-1052-gcp):** a fresh process read `oom_score=666` baseline; after `sudo -n choom -n -600 -p <pid>`: `oom_score=267`, `oom_score_adj=-600`. So the display scale here is `(1000 + badness‰) × 2/3` and −600 adj subtracts ~400 display points. **This decomposition reproduces the incident exactly:** #811's fit at RSS 6.8 GiB ≈ 53‰ of 128 GiB → `(1000+53)×2/3 + 300 (prefer) = 1002` — the literal badness earlyoom logged. Protected, the same fit scores ≈ `(1000+53−600)×2/3 + 300 ≈ 602`: below every default-adj process (≥666) and far below any spiking python neighbor (≥967 at 300‰), while remaining selectable if it becomes the dominant consumer — the intended −600-not-−1000 behavior.

**Alternatives considered (why per-launch choom wins):**
- **earlyoom `--avoid` regex** (daemon config): matches `comm` (first 15 bytes) — our phases' comm is generically `python3`, the same comm as every potential runaway neighbor; avoiding `python3?` fleet-wide would neutralize exactly the +300 python-prefer the box's config deliberately sets, only shifts −300 (vs −600), and requires editing `/etc/default/earlyoom` + a daemon restart (system config, outside the workflow surface, affects the whole fleet). Rejected.
- **`choom -n -1000`**: earlyoom AND the kernel OOM killer skip the process entirely — a runaway fit would then force kills of neighbors/infra. Rejected (source-verified skip at `== -1000`).
- **`systemd-run --scope -p OOMScoreAdjust=`**: same capability requirement, more moving parts than one choom sweep. Rejected.
- **Stream-reduce / RSS reduction** (existing gotchas.md:31 rule): orthogonal and already documented — it lowers the phase's OWN badness but cannot defend a legitimately-sized phase against a neighbor spike (badness at 6.8 GiB was already the max under prefer). Complementary, cross-linked, not duplicated.

## 11. Decision Rationale

- **`-600` (not `-1000`, not `-300`).** What: the oom_score_adj value swept onto the phase session. Why: −600 ≈ −400 display points on this kernel — enough to outweigh the box's +300 python-prefer with margin and rank below every default-adj neighbor, while `-1000` is a hard skip in BOTH earlyoom (v1.6.2 `kill.c`: `oom_score_adj == -1000 → skip`) and the kernel OOM killer — an unkillable runaway fit would force kills of neighbors/infra instead. Source: earlyoom v1.6.2 source + the live probe (666→267) + incident #811's in-session mitigation used −600 and the protected relaunch has run healthy past the original ~2h kill point (still running at plan time). Alternatives: −300 (only cancels the prefer bonus, leaves the phase tied with default processes at equal memory — too weak for a 5h phase), −1000 (rejected above).
- **Per-launch `choom` vs daemon `--avoid` config.** What: mechanism for deprioritization. Why: targeted (only the sanctioned phase), needs no system-config edit or daemon restart, stays inside the workflow surface, and `--avoid` cannot discriminate by comm (`python3` is also every runaway neighbor's comm). Source: `/etc/default/earlyoom` live read + earlyoom manpage (`--avoid` matches comm, first 15 bytes). Alternatives: § 2 table.
- **Session sweep (`pgrep -s`) vs leader-only choom.** What: apply to every pid in the phase's setsid session, not just `$PHASE_PID`. Why: adj inheritance is forward-only — a child forked between launch and the choom call (e.g. `uv run`'s python child) keeps adj 0 under a leader-only choom; the sweep closes the race, and later forks inherit −600 from their swept parent. Plausibly the #811 kill itself hit a tree member at ~2‰ RSS (1002 also decomposes as (1000+2)×2/3+300 for a small prefer-matched member) — the sweep makes the question moot. Source: fork-inheritance semantics (§2) + `pgrep -s` procps semantics (setsid leader's sid == its pid).
- **Relaunch-once-then-pod-pivot.** What: bounded recovery ladder. Why: one protected relaunch is cheap and usually sufficient (protection changes the selection ordering); a SECOND kill despite `choom=ok` means either structural VM contention or the phase is the true top consumer — both are pod-lane problems, and a third VM relaunch just loses another multi-hour window (#811 lost ~2h on the first). Mirrors the existing "Off-VM routing remains the FIRST preference" stance of the same section. Source: incident #811 + the section's own EXEMPT paragraph. Alternatives: pivot on first kill (wastes the cheap protected retry), unbounded relaunch (the #811 failure mode, repeated).
- **`choom=ok|failed` breadcrumb token.** What: one additive key=value token in the existing stage-dispatch breadcrumb. Why: makes the pivot rule decidable post-hoc (a "second kill despite protection" is only attributable if protection state was recorded) at zero parser cost. Source: `task_workflow.py::_breadcrumb_fields` (order-free, additive — read this session).
