<h1>Plan — issue #733 (kind: infra · workflow-fix)</h1>
<p><b>Harden <code>scripts/verify_task_body.py</code> check 23 (+ its check-25 sibling) HF-Hub probes against concurrent-session 429 storms.</b></p>

<section class="plan-tldr">
<h2 style="border:none;margin-top:0">0.0 TL;DR</h2>
<ul>
<li><b>What I'll run:</b> No experiment — this fixes a workflow tool. When the body-checker confirms that the Hugging Face links in a results write-up actually point at real files, it currently asks Hugging Face to list <em>every</em> file in a huge shared bucket. When several of my sessions hammer Hugging Face at once, Hugging Face throttles us and that one listing call can hang for two-plus minutes, leaving stuck checker processes behind. I'll change it to ask only the small, targeted question each link really needs ("does this exact folder exist at this version?"), and put a short, hard time limit on the call so it gives up in seconds instead of grinding through twenty automatic retries.</li>
<li><b>What I expect:</b> The same write-ups pass or fail exactly as before (a link pointing at a version that predates the upload still correctly fails), but under throttling the checker returns in seconds with an honest "couldn't confirm" note instead of stalling the whole pipeline.</li>
<li><b>What would change my mind:</b> If the cheaper targeted call can't actually tell "this folder is missing at this version" apart from "this version doesn't exist," I'd lose the dead-link detection that's the whole point of the check — so I verify that distinction with a unit test before trusting it.</li>
</ul>

<h2>1. Goal</h2>
<p>Make check 23's HF-Hub revision-pin existence probe (and its check-25 keyword-corroboration sibling) cheap and time-bounded so that concurrent EPS sessions throttling the HF Hub API surface a fast <code>unverified</code> note instead of a multi-minute pipeline stall plus stranded zombie verifier processes — while preserving the #537 dead-pin FAIL semantics and the fail-soft contract byte-for-byte.</p>

<h2>2. Prior Work</h2>
<ul>
<li><b>The check itself.</b> <code>scripts/verify_task_body.py</code> check 23 (<code>check_hf_url_resolves</code>, line ~4073) iterates the body's HF revision-pinned URLs (gathered + deduped by <code>_gather_hf_pinned_urls</code>, line ~3988, on <code>(repo_id, sha, path_prefix)</code>) and calls <code>_hf_url_existence</code> (line ~4023) per URL. Check 25 (<code>check_audit_availability_claims_match_hf</code>, line ~5010) calls the structurally identical <code>_hf_keyword_present_under_prefix</code> (line ~4951). <b>Both currently call <code>huggingface_hub.list_repo_files(repo_id, repo_type=repo_type, revision=sha)</code></b> (lines 4050 and 4992) — which lists EVERY file in the repo at the revision.</li>
<li><b>Root cause (confirmed by reading the installed SDK, huggingface_hub 0.36.2).</b> <code>list_repo_files</code> → <code>list_repo_tree(recursive=True)</code> → <code>huggingface_hub.utils._pagination.paginate()</code>. The first page is a bare <code>session.get()</code> (10 s timeout, no retry); <b>every page after the first goes through <code>http_backoff("GET", …, max_retries=20, retry_on_status_codes=429)</code></b> (<code>_pagination.py:45</code>). <code>http_backoff</code> uses pure capped-exponential backoff (<code>base_wait_time=1, max_wait_time=8</code>; it does NOT honor <code>Retry-After</code>): waits 1+2+4+8×17 ≈ <b>~143 s per paginated page</b> before raising. The data repo <code>superkaiba1/explore-persona-space-data</code> has thousands of files across all the <code>issueN_*</code> dirs, so the listing always paginates → under a fleet-wide 429 it stalls minutes per URL and strands the verifier (the /issue #715 §"Bug observed" symptom: ~0.2 s → 2+ min, zombie processes, clean once un-throttled). The candidate-block's "recursive <code>list_repo_tree</code>" / "honors Retry-After" wording was the analyzer's loose paraphrase; the mechanism is <code>list_repo_files</code> paginating into the 20-deep 429 loop, but the conclusion is identical.</li>
<li><b>What the check actually needs.</b> A bare <code>/tree/&lt;sha&gt;</code> repo-root link asserts only "the revision exists." A path-pinned <code>/tree/&lt;sha&gt;/&lt;path&gt;</code> link asserts "≥1 file exists under <code>&lt;path&gt;</code> at <code>&lt;sha&gt;</code>." Neither needs the whole-repo recursive file list. The #537 incident: a path pinned to a revision that <em>predates</em> the upload resolves to 0 files under that path → must FAIL.</li>
<li><b>Fail-soft contract (must preserve verbatim).</b> <code>EPM_VERIFY_BODY_NO_HF=1</code> → skip (the suite-wide fence in <code>tests/conftest.py:32</code>); missing <code>huggingface_hub</code> → skip; any network/auth/unexpected error → skip (surfaced as <code>unverified</code> on the PASS line). Only a SUCCESSFUL probe that definitively shows zero files / no-such-revision is a FAIL.</li>
<li><b>SDK API surface (huggingface_hub 0.36.2, verified by inspection).</b>
  <code>repo_info(repo_id, *, revision, repo_type, timeout, …)</code> — a single GET, accepts a per-request <code>timeout</code>, raises <code>RepositoryNotFoundError</code>/<code>RevisionNotFoundError</code>; no pagination.
  <code>list_repo_tree(repo_id, path_in_repo=None, *, recursive=False, revision, repo_type, …)</code> — lists ONE directory level when <code>recursive=False</code> + <code>path_in_repo=&lt;dir&gt;</code>; still goes through <code>paginate()</code> (so its pages-after-first hit the same 429 loop), but a single directory rarely paginates, and the first page is the no-retry 10 s GET. Raises <code>EntryNotFoundError</code> when <code>path_in_repo</code> does not exist at the revision, <code>RevisionNotFoundError</code>/<code>RepositoryNotFoundError</code> otherwise.
  <code>list_repo_tree</code> returns <code>RepoFile</code>/<code>RepoFolder</code> objects with a <code>.path</code> attribute.</li>
</ul>

<h2>3. Hypothesis</h2>
<p>Replacing the recursive whole-repo <code>list_repo_files</code> probe with the minimal targeted call per URL-type, wrapped in an in-process bounded-retry guard (1 retry, ~5 s/request, with an explicit hard cap on attempts so we never enter the SDK's 20-deep 429 loop), will (a) preserve every existing check-23/25 verdict (PASS/FAIL/skip) on the test fixtures, (b) preserve the #537 dead-pin FAIL, and (c) bound the worst-case wall-time per URL under throttling to <code>~2 attempts × 5 s ≈ 10 s</code> instead of <code>~143 s</code>. <b>Falsified if</b> the targeted API cannot distinguish "revision exists but path is gone" (dead pin → FAIL) from "revision does not exist" (also FAIL) from "network/throttle" (skip), or if any existing test flips verdict.</p>

<h2>4. Design</h2>

<h3>Approach chosen (combination of brief's candidates 1 + 2 + 3)</h3>
<ol>
<li><b>Candidate 1 (cheaper API), the primary lever.</b> Swap the whole-repo recursive listing for the minimal call per URL shape:
  <ul>
  <li><b>Bare-revision URL</b> (<code>path_prefix == ""</code>): <code>HfApi(...).repo_info(repo_id, repo_type=repo_type, revision=sha, timeout=&lt;T&gt;)</code>. A successful return ⇒ <code>pass</code>; <code>RepositoryNotFoundError</code>/<code>RevisionNotFoundError</code> ⇒ <code>fail</code> (dead pin). Single GET, no pagination, lowest cost.</li>
  <li><b>Path-pinned URL</b> (<code>path_prefix != ""</code>): list the <em>parent directory</em> of the path non-recursively and prefix-match. Concretely: <code>parent = posixpath.dirname(path_prefix.rstrip("/"))</code>; <code>entries = HfApi(...).list_repo_tree(repo_id, path_in_repo=parent or None, recursive=False, revision=sha, repo_type=repo_type)</code>; the URL resolves iff some entry <code>e.path == path_prefix</code> OR <code>e.path</code> is the directory <code>path_prefix</code> itself OR (for a dir prefix) an entry's path starts with <code>path_prefix + "/"</code>. See "deep path_prefix handling" below for the exact match rule and the EntryNotFoundError→FAIL mapping that preserves #537.</li>
  </ul></li>
<li><b>Candidate 2 (bounded retry), the hard time-bound.</b> Wrap every Hub call in a small helper <code>_hf_call_bounded(fn, *, attempts=2, timeout_s=5.0)</code> that catches the SDK's HTTP/throttle exceptions and retries at most once with a tiny fixed sleep, then gives up → the caller maps a give-up to <code>skip</code> (<code>unverified</code>). Crucially, <code>repo_info</code>'s own <code>timeout=timeout_s</code> caps the single GET; for <code>list_repo_tree</code> (no <code>timeout</code> kwarg on the high-level fn) the first-page bare <code>session.get()</code> is already capped by <code>DEFAULT_REQUEST_TIMEOUT=10 s</code>, and our outer <code>attempts=2</code> guard means we never sit through the 20-deep 429 loop on a paginated page (a 429 on page-2+ raises an <code>HfHubHTTPError</code> after the SDK's own retries only if it paginates — to bound even that, we set the env knob below). <b>Belt-and-suspenders:</b> set <code>os.environ.setdefault("HF_HUB_DOWNLOAD_TIMEOUT", "10")</code> is already the default; additionally we cap the SDK pagination retry by NOT triggering deep pagination at all (single-dir listing). The outer guard is the real bound.</li>
<li><b>Candidate 3 (per-process cache), the cross-call win.</b> A module-level <code>dict</code> keyed on <code>(repo_id, repo_type, sha, path_prefix)</code> → <code>(verdict, note)</code>, populated by <code>_hf_url_existence</code>. Within ONE Python process (a long-running subagent that calls <code>verify_text()</code> several times, or check 23 + check 25 probing overlapping URLs) the second lookup is free. <b>Note:</b> each <code>verify_task_body.py --issue N</code> CLI invocation is a fresh process, so this helps only intra-process; the real win is candidates 1+2. The cache is keyed identically to <code>_gather_hf_pinned_urls</code>'s dedup tuple so semantics are unambiguous. Skip-verdicts (network/throttle) are cached too within the process (a throttle that just hit URL A will hit URL B — caching the skip avoids re-stalling), which is safe because a fresh process re-probes from scratch.</li>
</ol>

<h3>Why code, not a model call?</h3>
<p>N/A — no unstructured-data heuristic. This is a deterministic HTTP existence probe; a model call is categorically wrong here.</p>

<h3>Per-URL wall-time budget</h3>
<p><code>timeout_s = 5.0</code> (connect+read, passed to <code>repo_info</code>); <code>attempts = 2</code> (1 retry) with a <code>0.5 s</code> inter-attempt sleep. Worst case per URL under hard throttling: <code>2 × 5 + 0.5 ≈ 10.5 s</code> then <code>skip</code>. Compared to the current <code>~143 s</code> per paginated page. Both knobs are module constants (<code>_HF_PROBE_TIMEOUT_S</code>, <code>_HF_PROBE_ATTEMPTS</code>) so a future tuner edits one line.</p>

<h3>Deep <code>path_prefix</code> handling (Risk b mitigation)</h3>
<p>A path-pinned URL can point at a file (<code>raw_completions/run.jsonl</code>) or a directory (<code>raw_completions</code> or a deep tree root <code>issue653_x/raw_completions/armB</code>). The non-recursive list of the <em>parent</em> directory contains the target as a direct child whether it's a file or a folder:</p>
<pre><code>needle   = path_prefix.rstrip("/")
parent   = posixpath.dirname(needle)              # "" for a top-level child
entries  = list_repo_tree(repo_id, path_in_repo=parent or None,
                          recursive=False, revision=sha, repo_type=repo_type)
paths    = {e.path.rstrip("/") for e in entries}
resolves = needle in paths                         # direct file OR direct subfolder
</code></pre>
<p>This is correct because <code>_gather_hf_pinned_urls</code> stores <code>path_prefix</code> = the URL's full path after <code>/tree|blob/&lt;sha&gt;/</code>, and a valid link's terminal component is always a direct child of its parent dir. <b>Edge case — a path_prefix that is itself a deep directory whose own contents we don't need:</b> we only assert the directory <em>exists</em> as an entry of its parent, matching the current <code>list_repo_files</code> semantics (which passed if ANY file's path == needle OR startswith needle+"/"). The new rule "needle is a direct child of parent" is equivalent for existence: if <code>raw_completions/</code> exists as a folder, it appears in the parent listing; the old code found it via a descendant file's <code>startswith</code>. Both yield "the path is populated." <b>The EntryNotFoundError mapping is what preserves #537:</b> when <code>parent</code> itself does not exist at the (predating) revision, <code>list_repo_tree(path_in_repo=parent)</code> raises <code>EntryNotFoundError</code> → <code>fail</code> (dead pin); when <code>parent</code> exists but <code>needle</code> is not among its entries → <code>resolves=False</code> → <code>fail</code> (dead pin). Both #537 sub-cases stay a FAIL.</p>

<h3>Pseudocode for the shared probe (check-23 path)</h3>
<pre><code>def _hf_call_bounded(fn, *, attempts=_HF_PROBE_ATTEMPTS, timeout_s=_HF_PROBE_TIMEOUT_S):
    """Run fn() with at most `attempts` tries; pass timeout_s when fn accepts it.
    Re-raise the LAST exception so the caller maps it to a verdict. The point is
    to never enter the SDK's 20-deep http_backoff 429 loop: we cap our own tries."""
    last = None
    for i in range(attempts):
        try:
            return fn()
        except (RepositoryNotFoundError, RevisionNotFoundError, EntryNotFoundError):
            raise           # definitive negatives — do NOT retry, surface immediately
        except Exception as exc:
            last = exc
            if i + 1 < attempts:
                time.sleep(_HF_PROBE_SLEEP_S)
    raise last

def _hf_probe_path_or_revision(repo_id, repo_type, sha, path_prefix):
    api = huggingface_hub.HfApi()
    if not path_prefix:
        _hf_call_bounded(lambda: api.repo_info(repo_id, repo_type=repo_type,
                                               revision=sha, timeout=_HF_PROBE_TIMEOUT_S))
        return "pass", ""
    needle = path_prefix.rstrip("/")
    parent = posixpath.dirname(needle)
    entries = _hf_call_bounded(lambda: list(api.list_repo_tree(
        repo_id, path_in_repo=parent or None, recursive=False,
        revision=sha, repo_type=repo_type)))
    paths = {e.path.rstrip("/") for e in entries}
    if needle in paths:
        return "pass", ""
    return "fail", f"HF URL dead revision pin — `{needle}` resolves to 0 files at `{repo_id}@{sha[:8]}`"
</code></pre>
<p>The caller (<code>_hf_url_existence</code>) keeps its env-fence + import guard, wraps the probe in <code>try/except</code> mapping <code>(RepositoryNotFoundError, RevisionNotFoundError, EntryNotFoundError)</code> → <code>fail</code> (with the existing dead-revision-pin message) and any other <code>Exception</code> → <code>skip</code> (with the existing "(HF … failed: {exc})" note, reworded from <code>list_repo_files</code> → the new call name), then caches and returns. <b>The FAIL message strings keep the substrings the tests assert</b> (<code>"dead revision pin"</code>, <code>"0 files"</code>, the <code>sha[:8]</code>, <code>"no revision"</code>) — verified against §6 below.</p>

<h2>11. Decision Rationale</h2>
<p><b>N/A — no model training.</b> No load-bearing model hyperparameters. The three probe knobs are engineering choices, grounded below:</p>
<ul>
<li><b>What:</b> <code>_HF_PROBE_TIMEOUT_S = 5.0</code>. <b>Why:</b> a single Hub metadata GET resolves in ~0.2 s when un-throttled (the #715 observation); 5 s is generous headroom for a slow-but-alive Hub while being far under the multi-minute stall. <b>Source:</b> #715 §Bug observed (~0.2 s un-throttled baseline). <b>Alternatives:</b> 10 s (the SDK <code>DEFAULT_REQUEST_TIMEOUT</code>) — rejected as twice the needed budget; 2 s — rejected as risking false skips on a slow-but-healthy Hub.</li>
<li><b>What:</b> <code>_HF_PROBE_ATTEMPTS = 2</code> (1 retry). <b>Why:</b> one retry absorbs a transient blip without entering the SDK's 20-deep loop; the whole point is to NOT retry 20×. <b>Source:</b> SDK inspection (huggingface_hub 0.36.2 <code>_pagination.py:45</code> <code>max_retries=20</code> is the culprit). <b>Alternatives:</b> 1 attempt (no retry) — rejected as too brittle to a single transient; 3+ — rejected as creeping back toward the stall.</li>
<li><b>What:</b> <code>_HF_PROBE_SLEEP_S = 0.5</code>. <b>Why:</b> a token pause between the two attempts so a sub-second blip clears, negligible against the 5 s timeout. <b>Source:</b> ungrounded — engineering default; bounded and tested. <b>Alternatives:</b> 0 (immediate retry) — acceptable but a tiny pause is friendlier under load.</li>
</ul>
