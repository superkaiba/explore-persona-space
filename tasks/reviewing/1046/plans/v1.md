## 4 Design

### 4.0 Design shape (the three decisions, resolved)

1. **Single pytest invocation, no `test_workflow_lint.py` batch split.** `compare` takes ONE `--junitxml`; a split forces two compare passes (verdict = worst) or a junit merge. Once the gate runs in background with a sized bound, the 600s cap no longer binds anything, so the split has no remaining incident to kill. The wl "longer timeout" survives as a `SLOW_TESTS` surcharge (+900s) inside the single bound.
2. **Background invocation (`run_in_background=true`), always — no foreground/background threshold branch.** The selection ALWAYS contains the 32-file invariant set including wl, so the projected gate wall (median ~11 min test time + collection overhead) always exceeds the 600s foreground tool cap; a threshold branch would just be a new decision point for sessions to misapply. `run_in_background` is the project's canonical orchestrator wait pattern (">~5 min waits belong to the bg-Bash polling loop") and delivers a completion notification; a full `setsid` detach is rejected (§11 entry 2).
3. **The `timeout(1)` bound rides IN the printed command.** Copy-paste is the strongest prevention: a session that pastes the selector's output gets the right bound with zero extra reasoning. stderr + `--json` carry the same number for the marker record and automation.

### 4.1 `scripts/select_step9c_tests.py` — sizing machinery (stdlib-only, deterministic)

**(a) New module-level constants + function**, inserted after `GLOB_SCAN_TESTS`:

```python
# --- Gate-timeout sizing (#1046). --------------------------------------------
# Measured from 26 Step 9c gate junits on the shared VM (2026-07-04..05,
# /tmp/step9c-junit-issue-*.xml, per-testcase `time` summed per file):
# tests/test_workflow_lint.py alone min 319 s / median 390 s / max 771 s;
# whole-gate totals median ~662 s / max 1285 s on 32-46-file selections. The
# foreground Bash tool cap is 600 s, so the printed command carries this bound
# and Step 9c runs the gate as a BACKGROUND invocation (SKILL.md 9c step 1b).
# Constants are deliberately generous (~1.4-2x over worst measured): an
# oversized bound only ever fires on a genuine wedge; an undersized one kills
# healthy gates (#991/#996/#906, exit 143 at 480-540 s foreground bounds).
TIMEOUT_BASE_S = 120  # pytest startup + collection (~2500 tests) + imports
TIMEOUT_PER_FILE_S = 30  # ~2x the p90 per-file runtime of non-slow files
TIMEOUT_FLOOR_S = 900
# Per-file surcharges for files whose OWN max exceeds the per-file allocation
# by an order of magnitude. Pinned literal (same curation rule as
# WORKFLOW_INVARIANT); live-tree drift pin in tests/test_select_step9c_tests.py.
SLOW_TESTS: dict[str, int] = {
    # 3845 lines; runs whole-tree lints repeatedly. Max 771 s measured (n=26).
    "tests/test_workflow_lint.py": 900,
}


def recommended_timeout_s(tests: list[str]) -> int:
    """Deterministic `timeout(1)` bound for a Step 9c gate selection.

    ``BASE + PER_FILE * len(tests) + sum(slow surcharges)``, floored at
    ``TIMEOUT_FLOOR_S``. Invariant-only selection (32 files incl. the
    workflow-lint surcharge) -> 1980 s (~33 min), consistent with the existing
    invariant-set-scale precedents (``step9c_baseline.py refresh``
    ``--timeout-s`` default 1800 s; the SKILL.md detached refresh's 2100 s).
    """
    t = TIMEOUT_BASE_S + TIMEOUT_PER_FILE_S * len(tests)
    t += sum(SLOW_TESTS.get(x, 0) for x in tests)
    return max(t, TIMEOUT_FLOOR_S)
```

      ```bash
      # command verbatim, with the junit + log + rc-file tail appended:
      timeout --kill-after=60s <T>s uv run pytest <files> -v --tb=short \
        --junitxml=/tmp/step9c-junit-issue-<N>.xml -o junit_family=xunit1 \
        > /tmp/step9c-pytest-issue-<N>.log 2>&1; echo $? > /tmp/step9c-rc-issue-<N>
      ```

      verdict in a fresh foreground call — the rc FILE replaces the former
      in-shell `PYTEST_RC=$?` capture (shell variables do not survive across
      Bash calls). A MISSING rc file means the background run died before
      pytest exited (tool kill / watcher force-stop, #833): treat as FAIL,
      never a silent PASS, and apply crash-fix-rounds § Kill-before-relaunch
      (probe `pgrep -af 'pytest.*step9c-junit-issue-<N>'` — the junit path
      makes the probe exact-invocation-scoped) before any re-run:
      ```bash
      if [ ! -f /tmp/step9c-rc-issue-<N> ]; then
        echo "FATAL: gate rc file missing — the background run died before pytest exited. Kill-before-relaunch, then re-run the gate; NEVER record PASS." >&2
      else
        PYTEST_RC=$(cat /tmp/step9c-rc-issue-<N>)
        tail -30 /tmp/step9c-pytest-issue-<N>.log
        # exit 0 + "no tests ran" (or "collected 0 items") is NOT a PASS:
        if grep -qiE 'no tests ran|collected 0 items' /tmp/step9c-pytest-issue-<N>.log; then
          echo "FATAL: pytest collected 0 tests — test-verdict gate did NOT run. Treating as FAIL." >&2
          # -> post epm:test-verdict v1 as FAIL; do NOT record PASS on exit 0.
        fi
      fi
      ```
      Record pass/fail + ALL selector stderr lines (the provenance
      breadcrumb, the `recommended-timeout-s=<T>` sizing line, the NOTE if
      any, and any WARN lines). The two anti-silent-pass guards above are
      LOAD-BEARING — a `no tests ran` outcome (pytest exit 0 with zero
      collected tests) is a **FAIL, never a PASS**: it is the signature of a
      failed `cd` that ran pytest in a directory with no tests (incident:
      issue 745, SHA 91bed41e, 2026-06-30 — the gate reported PASS on
      `no tests ran ... pytest exit: 0` and was silently skipped).

      **Recipe exit-code hygiene (every gate call — and every improvised
      monitoring one-liner):** the Bash tool reports the exit code of the
      LAST command in the call, and an `Exit 1` from a trailing INFORMATIONAL
      command is indistinguishable in the transcript from a gate failure. Any
      trailing command that legitimately returns non-zero without meaning
      failure — a display/filter `grep` that may match nothing (#969: a
      healthy gate read as a false Exit 1), a bare `[ -z "$VAR" ]` /
      `[ -s <file> ]` test (#928: a trailing `[ -z "$GIST_URL" ] && ...`
      variant reported Exit 1 on success), a `tail`/`cat` on a possibly-
      absent file — MUST be if-formed (`if grep -q ...; then ...; fi`) or
      given an explicit `|| true`. The verdict-bearing rcs are NEVER the raw
      call exit code: PYTEST_RC lives in `/tmp/step9c-rc-issue-<N>` and
      COMPARE_RC in its captured variable — read those, not the tool's Exit
      line.

## 11 Decision Rationale

(No training hyperparameters in this task — `N/A — no model training` for every hyperparameter-grounding slot; the load-bearing choices here are design constants and shapes.)

1. **Single pytest invocation; no separate `test_workflow_lint.py` batch.**
   - **What:** keep ONE gate pytest run + ONE junit + ONE compare; express wl's "own longer timeout" as a +900s surcharge inside the single bound.
   - **Why:** `compare` takes exactly ONE `--junitxml` (argparse line 1037); a split forces two compare passes with a worst-of verdict fold or a junit-merge step — new machinery, new failure modes (partial-batch kill leaves one junit stale), and once the gate is background-run the 600s cap that motivated splitting no longer binds anything.
   - **Source:** `scripts/step9c_baseline.py` argparse (read); incidents #991/#996/#906 (all killed by FOREGROUND bounds, not by wl exceeding a correctly-sized bound); dispatch-brief constraint "prefer the smallest change that kills the incident class".
   - **Alternatives:** (a) two invocations + two compares — rejected (arity machinery, stale-junit risk); (b) junit merge — rejected (new dependency or hand-rolled XML merge in a verdict-critical path).

2. **Background invocation (`run_in_background=true`), unconditionally — not foreground-with-bigger-timeout, not setsid detach.**
   - **What:** the gate pytest always runs as a background Bash call with log-file + rc-file capture; verdict read in a follow-up foreground call.
   - **Why:** foreground is IMPOSSIBLE (tool cap 600s < median ~11 min gate; wl alone hit 771s); a threshold branch (foreground for small runs) has no small-run case to serve (invariant set always present) and adds a decision point sessions can misapply. Full `setsid` detach survives session death but loses the harness completion notification and needs a Monitor/poll loop — for a 25-35 min gate whose result is useless without the session, the notification is worth more than kill-domain survival; the rc-file-missing guard makes the kill case loud.
   - **Source:** measured junit totals (26 runs, §2); Bash tool cap (crash-fix-rounds.md); CLAUDE.md § Orchestrator vs subagent (bg-Bash is the canonical wait pattern); #833 (bg-Bash kill-domain caveat — mitigated, not decisive).
   - **Alternatives:** setsid + sentinel + Monitor until-loop — rejected as above; instructing a 600000ms tool timeout on a foreground call — rejected, still too small.

3. **Timeout formula: `T = 120 + 30·n_files + 900·[wl selected]`, floor 900s.**
   - **What:** BASE=120 (collection/startup), PER_FILE=30, SLOW_TESTS={wl: 900}, floor 900.
   - **Why:** PER_FILE=30 ≈ 2× the p90 of non-slow per-file runtimes (slowest non-wl invariant medians 21-43s, most <10s; non-wl totals median ~272s / max ~514s over 31 files vs the 930s linear allocation). The wl surcharge 900 covers its measured max 771s with ~17% headroom. T(32)=1980s sits between the two existing invariant-set-scale precedents — `step9c_baseline.py refresh --timeout-s` default 1800s and the SKILL.md detached refresh's 2100s — and gives ~1.4× headroom over the worst measured whole-gate wall (~1400s incl. overhead). Asymmetric costs decide generosity: an oversized bound fires only on a true wedge; an undersized one kills healthy gates (the entire incident class).
   - **Source:** MEASURED junit aggregation this session (27 files, per-file sums; §2 numbers); `step9c_baseline.py` line 1025 + SKILL.md line 7334 (the 1800/2100 precedents); incidents #991 (480s), #996 (540s) — both ~4× under the sized bound.
   - **Alternatives:** per-file surcharges for the other lint siblings (`phase_done_check` max 257s, `judge_model_check` 126s, `upload_or_true` 103s) — rejected for now: n=1-2 samples each, they appear only in wl-touched selections where the linear term over many sibling files provides slack (measured worst such run: 898s junit vs T(41)=2250s), and the dict admits future entries with a one-line change; a runtime-history-based dynamic estimate — rejected (non-deterministic, needs state, violates the stdlib-only determinism constraint).

4. **The bound rides IN the printed command (stdout), plus stderr + JSON.**
   - **What:** stdout becomes `timeout --kill-after=60s <T>s uv run pytest ... -v --tb=short`; stderr gains `recommended-timeout-s=<T>`; `--json` gains `n_tests`/`recommended_timeout_s`/`slow_tests_selected`.
   - **Why:** the incident mechanism was sessions supplying their OWN (wrong) bound; a copy-pasted command that already carries the right bound removes the improvisation step entirely. stderr/JSON serve the marker record and any future automation.
   - **Source:** incidents #991/#996/#906 (improvised bounds); consumer audit (§9 assumption 4 — no programmatic stdout consumer breaks).
   - **Alternatives:** stderr-only emission with stdout unchanged — kept as the §10 fallback; weaker prevention (requires the session to read stderr and act).

5. **Exit-code hygiene as prose (if-form / `|| true` rule + incident-named examples), not a mechanical lint.**
   - **What:** one bolded paragraph in Step 9c 1b + one sentence at 9a-quater step 6.
   - **Why:** the offending commands are IMPROVISED by sessions (the on-main snippets are already correct) — a lint over SKILL.md fenced blocks would check text that is already clean and cannot see improvised transcript commands; the effective surface is the recipe sessions copy plus an explicit rule they can be held to.

   - **Alternatives:** a `workflow_lint` check for trailing greps/tests in workflow-surface fenced bash blocks — rejected (false-positive-prone: many legitimate trailing conditionals exist, e.g. guarded `|| true` forms already present at lines 7923/8411; near-zero true-positive yield on already-clean snippets).

6. **`--kill-after=60s` on the gate timeout.**
