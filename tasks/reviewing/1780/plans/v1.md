# Plan v1 — task #1780: gitleaks-aware deferred-commit message in task_workflow

### TDD: no

## 1. Requirement + acceptance criteria

**Requirement.** When `_commit_after_durable_append`
(`src/explore_persona_space/task_workflow.py`) defers a commit whose failure is
a gitleaks pre-commit finding, the ERROR message and the forensic sidecar row
must state the CORRECT recovery (plain re-commits keep failing; verify false
positive → append the printed `Fingerprint:` line to `.gitleaksignore` → commit
it together with the swept paths) instead of the generically-true-but-false-here
"the next successful commit touching these paths sweeps it."

**Empirical grounding (clarifier + planner probes, 2026-07-29):**

- The composer catches `CalledProcessError` at L6784 and reads ONLY
  `e.stderr[-500:]` into `stderr_tail` (L6794).
- The REAL #1092 incident row (`~/.task-workflow/deferred-commits.jsonl`,
  ts `2026-07-29T01:23:05Z`, task_id 1092) shows the gitleaks finding was NOT
  in the recorded 500-char tail — the tail carried only LATER pre-commit hooks'
  output (`workflow_lint ... Skipped`, `Refuse secret-shaped strings ... Passed`,
  the patch-restore INFO line). gitleaks runs FIRST in `.pre-commit-config.yaml`,
  so its `Fingerprint:` line scrolls off the tail whenever later hooks run.
  **Therefore the candidate's diff sketch (match on `stderr_tail`) would NOT
  have fired on the founding incident — detection MUST run on the FULL captured
  streams, before truncation.**
- The #1092 row also proves pre-commit hook output lands in the captured
  `e.stderr` on this path (`_run_git` raises `CalledProcessError` with both
  `output` and `stderr` fields populated from `subprocess.run` capture).
- gitleaks v8 (`scripts/hooks/gitleaks_scoped.sh` → `gitleaks git --pre-commit
  --redact --staged --verbose`) prints one `Fingerprint: <path>:<rule>:<line>`
  line per finding — the same string `.gitleaksignore` consumes (see the landed
  #1092 fix `be36d6dc6a`: `tasks/followups_running/1092/events.jsonl:generic-api-key:777`).

**Acceptance criteria:**

1. A deferral whose captured hook output (stdout OR stderr of the failed
   `git commit`, FULL text — not the 500-char tail) contains a gitleaks
   finding logs the extended NOTE: re-commits will re-fail until the finding is
   resolved; if a verified false positive, append the printed `Fingerprint:`
   line(s) to `.gitleaksignore` and commit it together with the swept paths.
2. The extracted `Fingerprint:` line(s) appear verbatim in BOTH the ERROR
   message and the forensic row (additive fields `gitleaks_finding: true`,
   `gitleaks_fingerprints: [...]`) — the recorded 500-char `stderr_tail`
   provably loses them (the #1092 row), so without extraction the operator has
   nothing to append.
3. Non-gitleaks deferrals produce a byte-identical message and row to today
   (no NOTE, no new fields).
4. `CLAUDE.md` line ~242 (the Task Workflow API `post-marker` bullet) carries a
   one-clause caveat naming the gitleaks exception + the fingerprint recipe.
5. New unit test passes; existing #1030 deferred-commit tests unchanged and
   green; ruff clean on touched files.

## 2. Method delta

Pure additive message/telemetry change inside the existing deferral branch. No
change to WHAT is caught or deferred (the `(CalledProcessError,
SequencerWaitTimeout, CommitHeadGuardError)` tuple, the routed-mode re-raise,
and the return-False contract are untouched). Differs from the filed candidate
sketch in two planner-refined ways, both forced by the #1092 row: (a) detection
runs on the FULL `e.output` + `e.stderr` (the tail-only match provably misses
the founding incident), and (b) the `Fingerprint:` line(s) are EXTRACTED into
the message + row (the tail provably loses them).
