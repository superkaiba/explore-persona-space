## 4. Design

### 4.1 The regex (primary edit — `scripts/audit_clean_results_body_discipline.py` L294)

Replace:
```python
r"\b(?:byte|bit)[\s-](?:identical|equal)\b",
```
with (implicit concatenation, ruff line-length 100 safe):
```python
r"(?<!-)\b(?:byte|bit)(?:wise)?[\s-](?:identical|equal|exact)\b"
r"|\b(?:bit[\s-]for[\s-]bit|byte[\s-]for[\s-]byte)\b",
```

**Newly caught (verified positive battery, all matched at plan time):** `byte-exact`, `byte exact`, `bit-exact`, `bit exact`, `bitwise identical`, `bitwise-identical`, `bitwise equal`, `bitwise exact`, `bytewise identical` (and other bytewise forms), `bit-for-bit`, `bit for bit`, `byte-for-byte`, `byte for byte`. Still caught: every existing form incl. the #1005 anchor ("inherited byte-equal (sha-asserted)") and the #868 shape ("the #671 byte-identical read").

**Deliberately NOT caught (state in tests/doc comment):**
- Capitalized sentence-start forms (`Byte-equal`, `Bit-for-bit …`) — the category scans case-sensitively (`flags=0` at L932; only `pre_reg` gets IGNORECASE). Pre-existing #1423 semantics, unchanged; the clean-result-critic Lens 6 (an LM) remains the backstop for capitalized occurrences. Changing case semantics would be a second deliberate behavior change and is out of scope.
- Hyphen-preceded compounds — `(?<!-)` excludes `non-byte-identical` (zero corpus occurrences) as the accepted cost of blocking the numeric-bit-width class (`8-bit exact-width`, `64-bit equal-width`, `n-bit identical-width`), which the CURRENT regex is exposed to; the lookbehind is a false-positive FIX riding along.
- Adjacent vocabulary outside the family: `bit-perfect`, `bit-accurate`, `bit-true`, `hash-identical`, `checksum-identical`, `verbatim` — real hardware/audio/verification terms with an open-ended adjective ladder; bounded out to cap false-positive risk. A future recurrence of one of these in a clean-result files its own (fifth) round — the guidance string's plain-English steer already covers the intent.
- The recommended plain-English replacements (`matched exactly`, `every byte agreed`, `equal at every byte`, `identical bytes`) — word-order inverted, never matched (the existing `test_verify_task_body.py` clean-negative "matched exactly at every byte" stays negative; verified).

**Rule key stays `bit_byte_identical`** — consumers key findings on it (critic blocker-tag flow, tests); renaming would be a public-contract change (must-ask, §7).

### 4.2 False-positive analysis (design consideration 2)

Scan-source confirmation (read, not assumed): `bit_byte_identical` falls to the `else` branch at L930-931 → scans `cleaned` = `strip_code(strip_data_example_blocks(strip_context_blockquotes(strip_frontmatter(body))))`. So fenced code blocks AND inline-backtick spans AND `<details>` data-example blocks AND Context-row verbatim blockquotes are all elided before the scan — a `bit-exact` inside a code fence, backticked span, or verbatim quote never fires. GFM table cells ARE scanned for this category (only `interval_inline`/`condition_labels` get table blanking — L857-866; pinned by the existing table-row test at `test_verify_task_body.py` ~L4990) — unchanged.

Verified-negative battery (all non-matching at plan time; becomes the new negative test):

| Case | Why safe |
|---|---|
| `bitwise AND`, `bitwise operations`, `bitwise XOR` | adjective `{identical,equal,exact}` required immediately after the separator |
| `an 8-bit exact-width field`, `a 64-bit equal-width layout`, `n-bit identical-width lanes` | `(?<!-)` blocks the hyphen-preceded unit |
| `byte offset`, `network byte order` | no family adjective follows |
| `a bit more variance` | `more` not in adjective set |
| `we reserve one bit for parity` | `for` branch requires the full `bit-for-bit` reduplication |
| `byte equality`, `the bytes equal to the header` | trailing `\b` / `[\s-]` blocked by suffix/plural (existing #1423 guards, retained) |
| `arbiter`, `bytecode`, `bite-sized`, `orbit equalization` | word boundaries (existing #642 guards, retained) |
| `Byte-equal` (capitalized) | case-sensitive scan (existing #1423 guard, retained) |

Whole-corpus evidence beats the battery: the candidate was run through the audit's own cleaning chain over all 1,408 bodies — the only new fires are the 14 genuine voice violations listed in §2, each inspected as prose usage of the banned family (e.g. #868's issue-number-adjacent form, #448's `bit-exact` parity claims).

## 11. Decision Rationale

- **One widened rule under the existing `bit_byte_identical` key** (vs new sibling keys per synonym group). Why: consumers (critic blocker-tag flow, tests, findings dict) key on the name; the family is one voice violation. Source: #642 (consolidated byte+bit under one key; the renaming round). Alternative rejected: per-group keys — churn in every consumer for zero information.
