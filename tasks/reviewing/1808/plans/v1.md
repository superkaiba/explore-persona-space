# Plan v1 — #1808 daily-fix: driver sha-scan exempts item's own fingerprint

## Plan Summary

Add a token-level exempt set to the `/daily` driver's #1467 WARN-only sha-verify
backstop so it never flags the filing's own wf-fix fingerprint (or any
`fingerprint:`-labeled 12-hex value from the body) as a non-resolving
commit-context hex token. Workflow-surface only; 0 GPU-h; not architectural
(no public contract changes — one keyword-only parameter added to an internal
scanner function plus two internal call-site threads).

## Goal + requirement

**Goal (from task body):** stop the daily driver's commit-SHA scanner WARNing
on the filing's own fingerprint.

**Requirement / acceptance criteria:**
1. A body quoting its OWN wf-fix fingerprint mid-prose on a commit-context line
   (the 2026-07-28 incident shape: "...fingerprint `06bc0203d759` differs...",
   no `fingerprint:` substring on the line) produces NO tier-1/tier-2 WARN and
   NO `sha-verify` advisory for that token.
2. A 12-hex value declared anywhere in the body via the `fingerprint: <fp>`
   label (anchored Provenance bullet OR prose label, e.g. the #1580 reconcile
   line's "supersedes body-carried fingerprint: <old>") is exempt when the SAME
   token recurs bare on another line.
3. A genuinely non-resolving hex token in commit context (not fp-shaped or not
   fp-declared) still WARNs tier-1 and still gains the advisory line —
   regression coverage keeps the #1467 behavior.
4. The dry-run mirror (`_dry_run_sha_note`) applies the same exemption (its
   counts match what the real path would annotate).
5. WARN-only + fail-open invariants unchanged: the scan never blocks a filing,
   never changes the driver exit code, and the exempt-set computation
   introduces no new raise path.

## Bug (verified at clarify time)

`scan_unresolvable_shas` (scripts/daily_drive_filings.py L489-516) has only a
LINE-level exclusion (`SHA_EXCLUDE_LINE_RE`, L381 — substring `fingerprint:` /
`wf-fix-fp:` / `drift_hash` / `sha-verify`). An fp quoted on a line WITHOUT the
literal `fingerprint:` substring is scanned; fps are 12-hex with letters, so
`HEX_TOKEN_RE` + `HAS_HEX_LETTER_RE` accept them, `_sha_resolves` fails (an fp
is not a commit), and any commit-context word on the line makes it tier 1 —
a stderr WARNING plus a body advisory. Neither `_check_body_shas` (L519) nor
`_dry_run_sha_note` (L616) receives the item's own fp even though every caller
(`process_item` L1721, `_dry_run_item`) has already computed it. Living
evidence: task #1808's own body was annotated at filing time for quoting the
2026-07-28 incident's fp `06bc0203d759`.

Note (correcting the task body's mechanism claim): the anchored `_FP_LINE_RE`
(L371-373) belongs to the `ensure_wf_fix_provenance` injection/reconcile path,
not the scanner; the scanner's exclusion is `SHA_EXCLUDE_LINE_RE`. The gap and
the fix target are unchanged by this correction.

## Method delta (what differs from prior related work)

#1580 fixed the INJECTION side (anchored fp-line detection + tag-authoritative
reconcile). #1467 built the scanner with a line-level exclusion only. This
change adds the missing TOKEN-level exempt set on the scan side; no prior task
has touched `scan_unresolvable_shas`'s token walk.

## Design + concrete diff (refine at implementation)

All edits in `scripts/daily_drive_filings.py`; tests in
`tests/test_daily_drive_filings.py`.

1. **New module-level label regex** (next to the #1467 constants, ~L380):

   ```python
   # #1808: any `fingerprint: <12hex>` label in the body (anchored Provenance
   # bullet OR prose, incl. the #1580 reconcile line's "supersedes body-carried
   # fingerprint: <old>") declares that token fp-class — exempt it from the
   # sha walk EVERYWHERE in the body, not only on its own (already
   # line-excluded) label line.
   FP_LABEL_RE = re.compile(r"fingerprint:\s*`?([0-9a-f]{12})(?![0-9a-f])")
   ```

2. **`scan_unresolvable_shas(text, root, exempt=frozenset())`** — new
   keyword-only param `exempt: frozenset[str] | set[str]`; in the token walk,
   `if tok in exempt: continue` (placed with the `HAS_HEX_LETTER_RE` skip).
   Docstring gains one sentence. Default keeps every existing caller/test
   byte-compatible.

3. **Exempt-set builder** (small pure helper):

   ```python
   def _fp_exempt_tokens(text: str, fp: str | None) -> frozenset[str]:
       """Token-level exempt set for the #1467 walk (#1808): the item's own
       computed wf-fix fp plus every `fingerprint:`-labeled 12-hex token in
       the body."""
       toks = set(FP_LABEL_RE.findall(text))
       if fp:
           toks.add(fp)
       return frozenset(toks)
   ```

4. **Thread `fp` through the two internal callers** (both already have it in
   scope at their call sites):
   - `_check_body_shas(item, dirpath, root, fp=None)` → compute
     `exempt = _fp_exempt_tokens(text, fp)` after the body read; pass to
     `scan_unresolvable_shas`. `process_item` (L1802) passes `fp=fp`.
   - `_dry_run_sha_note(item, dirpath, root, fp=None)` → same; `_dry_run_item`
     passes `fp=fp`.
   Keyword-only with `None` default so any other caller stays valid (the
   label-scan arm still works with `fp=None`).

5. **Docstring/comment updates:** module docstring's #1467 paragraph gains one
   clause ("the item's own fp + `fingerprint:`-labeled tokens are exempt,
   #1808").

## Plan deviations allowed vs must-ask

- Allowed: exact helper/regex naming, test names, comment wording, placing the
  exempt check before vs after the letter check, folding the builder inline if
  the reviewer prefers.
- Must-ask (re-plan): widening `SHA_EXCLUDE_LINE_RE` to bare `fingerprint`
  (line-level skip of any fingerprint-mentioning line) INSTEAD of the token
  exempt set — that trades false negatives on genuinely mis-cited commits
  sharing a line with the word "fingerprint"; out of this plan's scope.
- Explicitly out of scope: exempting FOREIGN fps quoted bare with no
  `fingerprint:` label anywhere in the body (e.g. #1808's own body quoting
  the incident fp inside backticks with only the word "fingerprint" before
  it). Such tokens are indistinguishable from mis-cited short SHAs without a
  label; authors should label them (`fingerprint: <fp>`) or the WARN stands —
  it is WARN-only by design. Recorded as a known residual, not a follow-up.
