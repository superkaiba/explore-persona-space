## 1. Goal

> Make the Step 10d post-merge stale-task-folder guard handle the unpushed-status-mv case: when the CANONICAL folder is absent from origin/main, run sync_repo_root FIRST, re-fetch + re-detect, and only classify/delete duplicates when the canonical folder is present on origin.

**Requirement (restated as a contract):** the guard must never remove a `tasks/<status>/<N>` folder from origin/main unless the canonical folder for task `<N>` is verifiably PRESENT on origin/main in the same materialized listing the classification reads. "Re-detect" includes re-resolving the canonical path itself (`task.py find`), because the recovery sync pull-rebases the local root and the canonical status can change in EITHER lag direction (local-ahead: unpushed mv; local-behind: origin's mv is newer — the mirror-direction deletion the current guard also commits).

**Acceptance criteria:**
1. Incident state (origin holds only the old-status folder; canonical mv committed locally, unpushed): guard lands the mv via `sync_repo_root.py`, re-detects, and does NOT delete origin's only folder. If a merge-imported duplicate additionally exists post-sync, the existing work arm removes it (unchanged behavior).
2. Mirror state (origin's status-mv is newer than local): guard re-resolves `CANON` post-sync and no-ops instead of deleting origin's newer folder (current behavior: deletes it).
3. Still-absent after 2 bounded attempts: terminal echo + `false` (routes to epm:merge-failed), NOTHING deleted.
4. Clean state / re-run: byte-identical behavior to today — pre-check condition short-circuits on its first grep; no sync runs; `DUPES` empty → no-op (idempotency preserved).
5. All existing pins in `tests/test_step10d_guard3.py` and `tests/test_issue_skill_merge_resnapshot_pin.py` pass; the new pin passes; `workflow_lint.py` default run passes; ruff clean on the touched test file.

## 4. Method delta (what differs from the current guard)

Current detection chain: `[ -z "$CANON" ]` → `elif ! fetch` → `elif ! ls-tree > lstree.txt` → `elif mapfile -t DUPES < <(grep … | grep -v -F -x "$CANON" || true); [ count>0 ]` → work arm. The detection never verifies `$CANON` itself is on origin.

Delta — ONE new `elif` arm inserted between the ls-tree producer arm and the DUPES work arm:

1. **Trigger:** `! grep -qxF "$CANON" /tmp/issue-<N>-postmerge-lstree.txt` (canonical absent from the just-materialized origin listing). Fires on CANON-absence alone (no "other folder present" conjunct) so the ZERO-folders damage state — exactly what the incident leaves behind — also self-heals on re-run instead of staying a silent no-op.
2. **Recovery (inside the arm's CONDITION, so success falls through):** bounded `for _ in 1 2` loop; per attempt: run `sync_repo_root.py` (lands the local mv; exit code deliberately NOT gated — exit 0 includes "in-flight", per the helper's documented contract); re-resolve `CANON` via `task.py find <N>` (guarded assign — an empty re-resolve keeps the previous value and fails closed at the re-check); re-fetch origin/main; REGENERATE the ls-tree file with the same materialize-then-check `>` form (a failed re-fetch/re-ls-tree leaves `CANON` absent from the file — the truncated/stale file routes to the terminal arm, never a fail-open read); re-check membership; `break` on success.
3. **Arbiter:** the condition list's FINAL command is `! grep -qxF "$CANON" <lstree file>` — recovery success ⇒ final test fails ⇒ branch NOT taken ⇒ evaluation falls through to the UNCHANGED `DUPES` arm, which classifies against the REGENERATED file (a merge-imported duplicate coexisting with the unpushed mv is still removed). Still-absent ⇒ branch taken ⇒ terminal echo + `false`, nothing deleted.
4. **Everything else byte-unchanged:** the three existing failure arms, the DUPES work arm (scratch worktree, push+retry, verify, local-residue tail), the closing `fi`, and the single-fence structure.

Why the condition-list form (and not a taken-branch reclassification or a #1268-style loop reshape): a taken branch cannot fall through to the later `elif`, so recovery-then-classify would require duplicating the ~70-line work arm (rejected); a whole-chain state-machine reshape would churn every #1184/#1253 pin (rejected as unnecessary — the condition-list form keeps every pinned string and the chain shape intact, and both mechanical gates plus a 4-state functional probe passed at plan time). The two-command-list `elif` precedent already exists in this exact block (the DUPES arm: `elif mapfile …; [ … ]; then`).

**Scope statement:** this is a docs/prose (SKILL.md embedded bash) + test change ONLY. No `src/` changes, no `scripts/` changes, no `configs/`, no experiment code. `sync_repo_root.py` is invoked as-is.

# origin/main ls-tree means origin's only folder for this task is (almost

# root, so the canonical status can change in EITHER lag direction — a
# failed re-resolve keeps the previous value and fails closed below),
# re-fetch, REGENERATE the ls-tree file (same materialize-then-check form

# routes to the terminal arm, never a fail-open read), then re-check.
# Bounded 2 attempts; the ls-tree RE-CHECK is the arbiter, NOT the
# helper's exit code (exit 0 includes the in-flight state — same
# 2-attempt shape as the local-residue tail below). The condition is a
# command list: a SUCCESSFUL recovery makes the final still-absent test
# fail, the branch is NOT taken, and evaluation falls through to the
# DUPES classification below against the REGENERATED file (a
# merge-imported duplicate can coexist with the unpushed mv and must
# still be removed). Only a still-absent CANON takes the branch —
# terminal echo + false, nothing deleted.
elif ! grep -qxF "$CANON" /tmp/issue-<N>-postmerge-lstree.txt \
    && { for _ in 1 2; do
           uv run python "$REPO_ROOT/scripts/sync_repo_root.py"
           NEW_CANON=$(realpath --relative-to="$REPO_ROOT" \
             "$(uv run python "$REPO_ROOT/scripts/task.py" find <N>)")
           [ -n "$NEW_CANON" ] && CANON="$NEW_CANON"
           git -C "$REPO_ROOT" fetch origin main --quiet \
             && git -C "$REPO_ROOT" ls-tree -d -r --name-only origin/main \
                > /tmp/issue-<N>-postmerge-lstree.txt \
             && grep -qxF "$CANON" /tmp/issue-<N>-postmerge-lstree.txt \
             && break
         done
         ! grep -qxF "$CANON" /tmp/issue-<N>-postmerge-lstree.txt; }; then
  echo "post-merge stale-task-folder guard: canonical folder $CANON still ABSENT from origin/main after 2 root syncs — cannot classify duplicates (removing origin's only copy would leave ZERO folders for task <N>)"

Non-hyperparameter design decisions (What / Why / Source / Alternatives):

- **Pre-check position: between ls-tree arm and DUPES arm.** Why: it needs the materialized file and must gate classification. Source: task brief + #1184 chain shape. Alternative (pre-chain loop around fetch+ls-tree): rejected — duplicates producers and churns the #1184 elif pins.
- **Recovery in the arm's CONDITION (fall-through on success).** Why: a taken branch cannot reach the later `elif`; duplicating the 70-line work arm is unacceptable; success must still classify (merge-imported dup can coexist). Source: bash `if` grammar + the block's own two-command-list `elif` precedent (DUPES arm); functionally probed. Alternative (#1268-style whole-chain state loop): rejected — pin churn without added safety.
- **2 sync attempts, re-check as arbiter, sync exit code un-gated.** Why/Source: byte-consistent with the guard's OWN local-residue tail (#1047/#1253) and `sync_repo_root.py`'s documented contract ("exit 0 does NOT by itself mean my push landed"; docstring L30-40). Alternative (gate on exit code): rejected — exit 0 is ambiguous by contract; exit≠0 states still deserve the re-check + second attempt.
- **Fire on CANON-absence alone (no "other folder present" conjunct).** Why: also self-heals the ZERO-folders damage state the incident class leaves behind (post-incident re-run pushes the local canonical folder back); an unpushed-but-clean state converging via the sanctioned sync is benign. Source: incident post-state on `2a1a9cbc0b`. Alternative (fire only when an old-status folder exists): rejected — leaves the damage state unhealed as a silent no-op.
