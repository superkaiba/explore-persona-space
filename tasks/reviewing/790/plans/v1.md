## 4. Design

### Item 2 — best-effort dir pull via `sudo -n tar` piped extraction (recipe (a))

**File + lines:** `src/explore_persona_space/backends/gcp.py:4696-4724` (the `for subdir in (...)` best-effort loop inside `fetch_results`).

**Change:** replace the per-subdir `gcloud compute scp --recurse` with a `gcloud compute ssh ... --command='sudo -n tar -c -C <workload_root> <subdir>'` whose stdout (a tar stream) is captured and extracted locally under the repo root. This is the SAME transport as the sentinel pull four lines above — `_base_gcloud_argv(config, "compute", "ssh", pod_name, "--command=sudo -n tar ...")` — just `tar -c` instead of `cat`.

**Pseudocode / diff sketch:**

```python
# gcp.py fetch_results, replacing the scp loop at 4703-4724
repo_root = _default_src_root_for_fetch()
workload_root = workload_dir_for(config, issue)
for subdir in (f"eval_results/issue_{issue}", f"figures/issue_{issue}"):
    remote_parent = f"{workload_root}/{shlex.quote(os.path.dirname(subdir))}"  # e.g. .../eval_results
    remote_leaf = shlex.quote(os.path.basename(subdir))                        # e.g. issue_<N>
    local_parent = repo_root / os.path.dirname(subdir)
    local_parent.mkdir(parents=True, exist_ok=True)
    # Pull the root-owned dir as a tar stream via sudo -n (same grant as the
    # sentinel pull); a missing remote dir → tar rc!=0 → LOG + continue (the
    # dir is authoritative on HF/WandB/git already).
    tar_argv = _base_gcloud_argv(
        config, "compute", "ssh", handle.pod_name,
        f"--command=sudo -n tar -c -C {remote_parent} {remote_leaf}",
    )
    tar_argv += [f"--zone={zone}"]
    tar_res = self._run(tar_argv)          # captured stdout = tar bytes
    if tar_res.returncode != 0:
        logger.warning(
            "GcpBackend.fetch_results: best-effort sudo tar of %s/%s failed "
            "(rc=%d); authoritative copy is on HF/WandB/git. stderr=%s",
            workload_root, subdir, tar_res.returncode, tar_res.stderr[:300],
        )
        continue
    # Extract the captured tar stream under local_parent.
    _extract_tar_bytes(tar_res.stdout, dest=local_parent)  # tarfile.open(fileobj=BytesIO(...))
```

**Text-vs-bytes note (load-bearing, resolve at implementation):** the existing `self._run` / `GcloudRunResult.stdout` returns TEXT (the sentinel pull does `write_text(sentinel_res.stdout)`). A tar stream is BINARY. The implementer MUST confirm whether `self._run` captures bytes-decodable-as-latin1 or true text; if text-only, either (i) pass `--command='sudo -n tar -c ... | base64'` and `base64.b64decode(stdout)` before `tarfile.open`, or (ii) add a bytes-capturing variant of `_run` for this one call. Prefer (i) base64 — it keeps the single `self._run` transport and the `_Runner` mock unchanged in shape (still returns a string), and base64 is safe through any text pipe. The diff sketch above is transport-shape; the base64 wrap is the concrete safe form:

```python
f"--command=sudo -n tar -c -C {remote_parent} {remote_leaf} | base64 -w0"
...
raw = base64.b64decode(tar_res.stdout)
with tarfile.open(fileobj=io.BytesIO(raw)) as tf:
    tf.extractall(path=local_parent)   # extracts <leaf>/ under local_parent
```

**Why code, not a model call?** N/A — no unstructured-data heuristics; this is a file-transport change.

**Test:** `tests/test_gcp_backend.py`, new test `test_fetch_results_best_effort_dirs_use_sudo_tar` — asserts the two best-effort pulls invoke `gcloud compute ssh ... sudo -n tar -c -C <workload_root>/eval_results issue_<N> | base64 -w0` (and the figures equivalent), NOT `gcloud compute scp`, and that a valid base64-tar stdout extracts to `repo_root/eval_results/issue_<N>/`. Update the EXISTING `test_fetch_results_sentinel_pull_uses_ssh_sudo_cat` + `test_fetch_results_sentinel_pull_failure_logs_and_continues`: they currently assert `len(scp_calls) == 2` — after the change the best-effort pulls are `ssh` calls, so scp_calls == 0 and ssh_calls == 3 (1 sentinel `cat` + 2 tar). The `_fetch_fixture` `ssh_results` queue must supply the 2 extra tar results.

**Regression prevented:** a silent-empty local mirror on every GCP hydra run (root-owned tree, plain scp Permission denied) — the exact bug that forced manual `sudo`-SSH fetch.

## 11. Decision Rationale

- **Item-2 transport = `sudo -n tar -c | base64` piped extraction (recipe (a)).**
  - **What:** best-effort dir pull via `gcloud compute ssh ... sudo -n tar` instead of `gcloud compute scp --recurse`.
  - **Why:** the workload tree is root-owned (#588); plain scp Permission-denies. `sudo -n` reads it through the OS-Login user's google-sudoers grant — exactly what the sentinel pull already does with `sudo -n cat`. No VM-side pre-teardown chmod, single sudo-only permission surface, one round-trip per subdir.
  - **Source:** gcp.py sentinel pull pattern from #588 (gcp.py:4669-4694) — same transport, `cat`→`tar -c`.
  - **Alternatives rejected:** (b) `ssh sudo -n chmod -R a+rX` then scp — two round-trips, leaves root files world-readable on the (soon-deleted) VM, more permission surface. (c) run the workload as non-root — requires restructuring the snapshot-pinned startup script, out of scope.
- **Item-4 declaration = drop figures/ from default hydra git_paths (recipe (e)).**
  - **What:** remove `figures/issue_{issue}/` from `build_expected_artifacts_declaration`'s default `git_paths`.
  - **Why:** the analyzer generates + commits figures POST-run (analyzer.md Step 3), AFTER confirm_artifacts runs; the workload never produces figures/ during the run, so declaring it is a guaranteed false-FAIL. Matches the existing `custom_workload` contract (custom launches already omit both auto git paths). eval_results/ is KEPT because the workload does commit it and its absence is a real FAIL.
  - **Source:** artifacts.py:574-578 skip_default_git_paths pattern for custom_workload — the hydra lane adopts the same "don't declare figures/" contract.
  - **Alternatives rejected:** (d) add an `include_figures_git_path` flag — needs wiring at every caller for a path no hydra workload ever writes; unnecessary complexity. (f) downgrade missing-figures from FAIL to WARN inside `confirm_artifacts_from_handle` — muddies FAIL semantics (a genuinely-missing eval_results/ would then need a separate FAIL rule); (e) is cleaner.
- **Load-bearing hyperparameters:** N/A — no model training.
