### 4a. Width threading — reuse `--gpus` / `RunSpec.gpus`; no new flag

**Decision: the requested width is `RunSpec.gpus`, set by the existing `dispatch_issue.py --gpus N` flag.** No new `--width` flag (two flags meaning "GPU count" is a foot-gun), no `(intent, width)` key change to `INTENT_TO_MACHINE` (that would fork every `machine_for_intent` call site). The GCP lane stops ignoring `spec.gpus` and starts honoring it as a width DECLARATION.

```python
#: Width -> wide A100-80 machine for the width-aware auto ladder (#1121).
#: a2-ultragpu-{2,4,8}g all live-verified offered in us-central1-{a,c}
#: (gcloud machine-types list, 2026-07-08). H100 (a3-highgpu-*) is
#: DELIBERATELY absent: preemptible quota is exactly 8 (one 8x, zero
#: concurrency headroom, #743), there is no on-demand pool, and the H100
#: quota metrics are absent from `regions describe` on this project, so
#: the fail-open headroom pre-check cannot protect a doomed create.
#: sweep-8g-h100 stays explicit-`--intent`-only.
WIDE_A100_80_BY_WIDTH: dict[int, MachineSpec] = {
    2: MachineSpec(machine_type="a2-ultragpu-2g", gpu_count=2, gpu_kind="A100-80"),
    4: MachineSpec(machine_type="a2-ultragpu-4g", gpu_count=4, gpu_kind="A100-80"),
    8: MachineSpec(machine_type="a2-ultragpu-8g", gpu_count=8, gpu_kind="A100-80"),
}

#: Intents whose workload shards across GPUs at 1 GPU (or, for ft-7b, its
#: ZeRO-3 world size) per shard, so a wide A100-80 machine serves them:
#: the single-GPU 7B-class intents + ft-7b (whose base IS the same
#: a2-ultragpu family at 4x). eval/debug are included even though their
#: BASE machine is L4 — a width>1 request upgrades them onto the A100-80
#: family (there is no multi-GPU g2 mapping in v1; deliberate, see plan
#: #1121 §11). H100-family intents (lora-7b-h100 / eval-h100 /
#: sweep-8g-*) are EXCLUDED (see WIDE_A100_80_BY_WIDTH note).
WIDTH_ELIGIBLE_INTENTS: frozenset[str] = frozenset(
    {"lora-7b", "lora", "capture-7b", "eval", "debug", "ft-7b"}
)


def wide_a100_80_for_width(width: int) -> MachineSpec | None:
    """The wide A100-80 MachineSpec for ``width``; None when unsupported."""
    return WIDE_A100_80_BY_WIDTH.get(int(width))
```

### 4b. Ladder semantics — width-major walk, intra-width order unchanged

`router._gcp_ladder_specs` gains a width-major OUTER loop. Width is the slowest-varying axis (exhaust all provisioning models at width 8 before accepting width 4) because wall-clock is the scarce resource and GCP credits are not — a spot-8g attempt is strictly preferable to an on-demand-4g one under this project's cost model. Intra-width, the EXISTING length-aware order applies verbatim (single-variable discipline: this change adds the width axis; it does not re-litigate spot/flex/on-demand ordering).

Pseudocode (replacing the body of `_gcp_ladder_specs` after the CPU short-circuit, which is untouched):

```python
base = machine_for_intent(spec)
if base.gpu_count == 0:
    ...existing CPU short-circuit, byte-identical...

wide_widths = _requested_wide_widths(spec, base)   # e.g. [8, 4, 2]; [] = today's path
widest = wide_a100_80_for_width(wide_widths[0]) if wide_widths else base
short = _is_short_job(spec, widest)                # ONE classification per dispatch
a40 = a100_40_fallback_for_intent(spec)
pinned = (spec.extra or {}).get("provisioning_model")

rungs: list[tuple[RunSpec, str]] = []
for w in wide_widths:                              # WIDE rungs (#1121), width-major
    m = wide_a100_80_for_width(w)
    if pinned is not None:
```

with the helper:

```python
def _requested_wide_widths(spec: RunSpec, base: MachineSpec) -> list[int]:
    """Descending wide widths for a width-declaring dispatch; [] otherwise.

    [] when spec.gpus is None, <= the base machine's width, the intent is
    not width-eligible, or the requested width is UNSUPPORTED (not a
    WIDE_A100_80_BY_WIDTH key) — then today's ignore-spec.gpus semantics
    hold. The dispatch_issue pre-route guard is the loud front door; a
    library caller bypassing it gets a logger.warning, not a silent
    nothing, AND never a silent snap-down: without the supported-width
    gate, a library-seam gpus=6 would walk [4, 2] — the snap-down §4b
    design point 6 explicitly bans (revision-round fix, Phase-3).
    """
    if spec.gpus is None:
        return []
    g = int(spec.gpus)
    if g <= base.gpu_count:
        return []
    if spec.intent not in WIDTH_ELIGIBLE_INTENTS:
        logger.warning("route: spec.gpus=%d ignored by the GCP lane for "
                       "non-width-eligible intent %r (#1121).", g, spec.intent)
        return []
    if g not in WIDE_A100_80_BY_WIDTH:
        logger.warning("route: unsupported wide width spec.gpus=%d for intent "
                       "%r — no snap-down; base-width ladder used. Supported: "
                       "%s (#1121).", g, spec.intent, sorted(WIDE_A100_80_BY_WIDTH))
        return []
    return [w for w in (8, 4, 2) if base.gpu_count < w <= g]
```

Spelled-out rung sequences (the two the brief asks for, `capture-7b`, base 1× A100-80):

- **Width-8 SHORT job** (`estimated_gpu_hours ≤ 2` at width 8, or `spot_tolerant`): `spot_a100_80x8 → flexstart_a100_80x8 → ondemand_a100_80x8 → spot_a100_80x4 → flexstart_a100_80x4 → ondemand_a100_80x4 → spot_a100_80x2 → flexstart_a100_80x2 → ondemand_a100_80x2 → spot_a100_80 → spot_a100_40 → flexstart_a100_80 → ondemand_a100_80 → ondemand_a100_40` (14 rungs) → SLURM lanes → RunPod terminal rung.
- **Width-8 LONG/UNKNOWN job** (the common case — 8 GPU-h > the 2 GPU-h spot threshold, e.g. #825's phase): `flexstart_a100_80x8 → ondemand_a100_80x8 → flexstart_a100_80x4 → ondemand_a100_80x4 → flexstart_a100_80x2 → ondemand_a100_80x2 → flexstart_a100_80 → ondemand_a100_80 → ondemand_a100_40` (9 rungs) → SLURM → RunPod.

Design points, each deliberate:

1. **No wide A100-40 rungs in v1.** The a2-highgpu family exists at all widths in 4 zones and its preemptible quota is 16, BUT its ON-DEMAND quota is 1 (live-verified — a wide on-demand a2-highgpu rung is a dead rung by quota), and adding the spot-side siblings pushes the short-job walk to 17 rungs. Deferred as a named follow-up (§11 alternatives); the width-1 `a40` rungs are untouched.
2. **Length classified ONCE at the REQUESTED width** (`_is_short_job(spec, widest)`), threaded through the whole walk including the base tail. `_estimated_gpu_hours = time_budget_hours × gpu_count`, so a wall budget sized for 8-way sharding reads 8× larger at width 8 — the honest total-work estimate. A width-8 job that degrades to 1× genuinely runs ~8× the budgeted wall, so inheriting the (usually LONG) classification in the tail is conservative and correct: no spot rung for a job that will overrun its budget 8-fold on 1 GPU. When `wide_widths == []` this is EXACTLY today's `_is_short_job(spec, base)` — byte-identity preserved. (Fact-check note: an explicit `spec.extra["estimated_gpu_hours"]` override is machine-independent, so classify-at-widest is a no-op on that path — not an error; worth an implementer comment.)
3. **Wide rung machines ride the existing `machine_spec_override` threading** (`_with_machine`) — zero changes to `GcpBackend.launch`, `render_create_argv`, `quota_metric_for`, or the zone filter. The per-rung quota-headroom pre-check automatically reads `needed = 8` for the 8g rung against `NVIDIA_A100_80GB_GPUS` (limit 8) / `PREEMPTIBLE_NVIDIA_A100_80GB_GPUS` (limit 16) and free-skips doomed rungs; the #1029 boot-loop skip keys on the new labels cleanly (per-(issue, rung_label) streaks).
4. **Caller `--provisioning-model` pin honored at every width** (a pinned SPOT width-8 dispatch walks `spot_*x8 → spot_*x4 → spot_*x2 → spot_<base> [→ spot_a40]`, never silently un-pins) — the existing #537/#680 pin contract, extended per-width.
5. **H100 family excluded from the width walk** — `WIDE_A100_80_BY_WIDTH` has no H100 rows and `lora-7b-h100`/`eval-h100`/`sweep-8g-*` are not width-eligible. `sweep-8g-h100` (and `sweep-8g-a100`) remain reachable exactly as today: explicit `--intent`.
6. **Snap-down, never widen:** widths considered are `{w ∈ {8,4,2} : base < w ≤ requested}`. A `--gpus 6` request is refused at the dispatch guard (supported set named in the message) rather than silently snapped — an idle-2-GPU provision must be a deliberate choice, so the user re-requests 8 or 4 explicitly. `ft-7b` (base 4) with `--gpus 8` walks `[8]` then its base ladder at 4 — its ZeRO-3 world size scales to 8 but not down to 2.

### 4d. Attempt-cap semantics

**Decision: unchanged accounting rule; raised constant.** Each actual CREATE burns one `MAX_GCP_ATTEMPTS_PER_DAY` attempt regardless of width (the cap's purpose is bounding doomed-create churn, and a wide create is one create); quota-headroom skips and boot-loop skips remain FREE (no counter bump — unchanged code paths). The constant is raised **8 → 16**: the #680 rationale sized 8 as "the up-to-5-rung short ladder + a same-day retry margin"; the width-8 short walk is up to 14 rungs, and 16 = 14 + margin, with the free skips absorbing the quota-doomed subset in practice. A cap hit mid-walk keeps today's behavior byte-for-byte: stop issuing creates, fall through to SLURM → RunPod (`"cap_hit"` → `return None`). It stays an attempt COUNT — never a dollar cap (`tests/test_no_dollar_budget_caps.py` untouched). Why not a per-dispatch dynamic cap (`max(8, len(rungs)+2)`): the cap is a PER-DAY, cross-dispatch counter persisted in the lease; making it dispatch-shape-dependent breaks its day-scoped meaning and its test pin for no measurable benefit. `test_max_gcp_attempts_per_day_is_eight` → `test_max_gcp_attempts_per_day_is_sixteen` with a docstring recording this rationale (the pin exists to catch SILENT reverts; a deliberate change updates the pin).
