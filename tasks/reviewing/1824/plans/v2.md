# Plan v2 — #1824: `upload_dir_sharded` batches small-file stores into chunked bulk commits (+ skip-if-present resume)

*(v2 folds in critic round-1 Must-Fix 1 (fresh CommitOperationAdd objects per commit attempt / reroute) + Must-Fix 2 (empty-prefix resume-probe guard) and adopts all five round-1 suggestions. Diff vs v1 marked with [v2].)*

## 0. TL;DR

`orchestrate.upload_sharded.upload_dir_sharded` currently commits ONE `upload_file` per shard (~35 s/file commit round-trip on the #1482 store: 539/3,840 files in ~5.5 h, ~33 h projected, GPU idle, ~100 commits/h against the shared 256/h Hub cap). This plan adds a **batch mode** — chunked `create_commit` bulk commits of ≤ `HUB_COMMIT_FILECOUNT_WARN` (2,000) files each — as the default whenever the store's on-disk byte sum fits under a threshold (default 50 GB), retaining the per-file walk as the explicit/large-store fallback, plus an **up-front skip-if-present resume probe** (one scoped listing; skip same-size already-on-Hub files) in BOTH modes. All existing contracts preserved: overflow reroute on quota-403, pointer + JSONL event (once per prefix), batched exact-set verify, fail-loud never-silently-drop, delete-only-after-verify.

## 1. Requirement + acceptance criteria (kind: infra)

**Requirement** (task Goal): batch `upload_dir_sharded`'s shard files into grouped commits whenever the store fits comfortably under the local-disk/quota bound; fall back to the per-file walk otherwise; add a skip-if-already-on-Hub probe so interrupted walks resume without re-committing.

**Acceptance criteria:**
1. A 3,840-file store uploads in ≤ 2 bulk commits per destination repo (vs 3,840 commits today) — pinned by a commit-count test.
2. Overflow semantics identical: quota-403 (reactive) and projected-headroom (proactive, #1034) both route to the overflow repo with exactly ONE `OVERFLOW_POINTER.json` commit + ONE JSONL event per prefix, in batch mode too.
3. Resume: a re-invocation after a partial prior upload re-commits ONLY missing / size-changed files (both modes); skipped files are still verified + (when `delete_local`) deleted.
4. Fail-loud unchanged: non-quota errors re-raise after the transient-retry budget; both-repos-refused raises `RuntimeError`; locals never deleted unverified.
5. Signature backward compatible — all 8+ live call sites (`issue1335_run.sh`, `issue1073_fits/capture.py`, `issue1417_run.sh`, `issue1345_upload.py`, `issue1482_*.py`) run unchanged (new kwargs have defaults; `ShardUploadResult` gains only an additive field; call-site grep confirms only `uploaded`/`rerouted`/`deleted` reads — critic A3).
6. `tests/test_upload_sharded.py` extended; full file green; no other test file regresses (Step 9c gate).
7. [v2] A reroute after a mid-preupload quota-403 re-uploads the chunk's BYTES to the overflow repo — pinned by a stateful-fake test (Must-Fix 1).
8. [v2] A root-level dest (`path_in_repo=""`) NEVER triggers an unscoped repo listing — pinned by a test (Must-Fix 2).

## 2. Method delta (what differs from prior related work)

- Prior art reused, not reinvented: `_batched_verify` (#1335, one scoped listing per destination repo) verifies batch-mode uploads unchanged; `hub.retry_transient` wraps every fresh Hub call; `_ensure_overflow_repo` / `_write_overflow_pointer` / `_emit_overflow_routing_event` reused verbatim; the #1034 proactive-headroom branch reused (batch mode simply commits its chunks straight to overflow).
- New: (a) chunked bulk commits via `api.create_commit(operations=[CommitOperationAdd(...)])` — exact file selection, no glob/fnmatch escaping fragility (rejected alternative: `api.upload_folder(allow_patterns=[<names>])` — fnmatch has no escape syntax, so arbitrary shard names with `[?*` misroute, and N-patterns × M-files matching cost scales badly); `upload_folder` itself is a thin wrapper that composes `CommitOperationAdd`s and calls `create_commit`, so this is the same single-commit path the #664/#727 doctrine mandates. Critic-confirmed on the pinned huggingface_hub 0.36.2: `create_commit` internally runs `_fetch_upload_modes` + LFS preupload (`hf_api.py:4229/4449/4494`).
- [v2] **CommitOperationAdd objects are single-use** on hub 0.36.2: `create_commit` MUTATES its operations (`hf_api.py:4196` raises "already being committed and cannot be reused"; `hf_api.py:4442` filters `_is_uploaded` additions out of preupload). Therefore ops are built FRESH inside every commit attempt — the thunk closes over the chunk's `(shard, dest)` pairs and constructs new `CommitOperationAdd`s per call (`lambda: api.create_commit(..., operations=_mk_ops(chunk), ...)`), including the overflow re-commit after a canonical 403. Same shape as the module's own BytesIO-inside-thunk rule (upload_sharded.py:101-105). A mid-preupload 403 otherwise leaves ops `_is_uploaded=True` with modes fetched against the canonical DATASET repo, and the overflow MODEL-repo commit would silently skip uploading those bytes — on the exact #1482 incident path.
- New: (b) `_remote_sizes_under_prefix(api, repo_id, prefix, repo_type) -> dict[str, int]` — scoped `api.list_repo_tree(path_in_repo=prefix, recursive=True)` materialized INSIDE the `retry_transient` thunk (lazy-generator gotcha), `EntryNotFoundError` → `{}` (absent prefix = nothing uploaded yet; a `RepositoryNotFoundError` still propagates loud per the gotchas literal-path rule). Sizes come from `RepoFile.size` (filter out entries without `size`/`RepoFolder` — critic A2 confirmed `.path`/`.size` at `hf_api.py:657-658`).
- [v2] **Empty-prefix guard (Must-Fix 2):** `prefix == ""` (root-level dests — supported by `_batched_verify`'s root fallback, upload_sharded.py:236-241) SKIPS the resume probe entirely with one logged INFO line — a recursive tree walk on `path_in_repo=""` is the #833/#920 full-repo enumeration wedge on the ~1M-file data repo (and `list_hf_files_under_path` itself deliberately ValueErrors on empty paths, hub.py:880-882). No per-dest `file_exists` fallback (a per-file HEAD-probe loop is the #1335 anti-pattern); root-level callers simply keep today's always-upload behavior.
- Chunk cap grounded in hub.py's own tiers: ≤ 2,000 files/commit (`HUB_COMMIT_FILECOUNT_WARN`, #1571 — one 31,000-file commit was killed >20 min in, #1481) which also keeps every commit under the per-dir 10k server cap (#658/#1190). `upload_large_folder` deliberately NOT used (project decision recorded at the #1571 tier comment in hub.py).

## 3. Design

### 3.1 Mode selection (auto, with escape hatches)

New kwargs on `upload_dir_sharded`:
- `batch: bool | None = None` — `None` = AUTO: batch iff `projected_bytes <= EPM_UPLOAD_BATCH_MAX_GB` (env, default `50`, decimal GB); `True` forces batch; `False` forces the legacy per-file walk.
- `batch_chunk_files: int = HUB_COMMIT_FILECOUNT_WARN` (imported from `orchestrate.hub`) — files per bulk commit.
- `resume_skip: bool = True` — `False` restores today's always-upload behavior (no probe I/O).

`projected_bytes = sum(p.stat().st_size for p in shards)` is computed ONCE over the FULL shard list (it already exists inside the proactive-headroom branch; hoist it) and feeds both the #1034 headroom probe (conservative: total store size, not post-skip remainder) and the mode decision. Rationale for byte-threshold-only (no free-disk term from the task body's sketch): since #1335's deferred-delete design, BOTH modes hold the full store on disk until the post-verify delete pass — the walk reads files in place and `create_commit` streams them — so batching does not raise peak local footprint; the threshold exists only to keep truly giant stores on the conservative per-file path.

### 3.2 Batch branch

For each destination group (canonical, or overflow when `route_all_to_overflow`):
1. Partition the non-skipped shards into chunks of ≤ `batch_chunk_files`.
2. Per chunk: `retry_transient(lambda: api.create_commit(repo_id=..., repo_type=..., operations=_mk_ops(chunk, prefix), commit_message=f"upload_dir_sharded batch {i}/{n} ({k} files)"), what=f"create_commit({repo}:{prefix} chunk {i}/{n})")` — where `_mk_ops` constructs FRESH `CommitOperationAdd(path_in_repo=dest, path_or_fileobj=str(shard))` objects on every invocation ([v2] Must-Fix 1: ops are never reused across attempts or reroutes).
3. Reactive quota-403 on a canonical chunk: `_is_storage_quota_403` → `_ensure_overflow_repo` + emit event + pointer ONCE (reuse `emitted_prefixes`), then re-commit THIS chunk and all REMAINING chunks to the overflow repo (`repo_type="model"`) — each with fresh ops via `_mk_ops`; those dests join `result.rerouted` (and `result.uploaded`, parity as today). Non-quota errors re-raise (fail-loud); a both-repos-refused chunk raises the existing `RuntimeError` shape naming the chunk.
4. [v2] Flat-store residual WARN: when the cumulative file count committed into ONE repo dir across chunks exceeds `HUB_DIR_FILE_LIMIT`, log one WARNING (the server cap is per-commit-staging; incremental accumulation is a documented hub.py residual — cheap visibility, never a raise).
5. All committed/skipped shards enter `pending` → existing `_batched_verify` → existing delete pass. Unchanged.

### 3.3 Skip-if-present resume probe (BOTH modes)

At entry (after `shards` is computed; the skip set shrinks the per-mode upload loops, NOT the headroom `projected`):
1. [v2] If `prefix == ""` OR `resume_skip=False` OR `shards` empty: skip the probe (one INFO line for the empty-prefix case naming the #833 wedge rationale).
2. `remote = _remote_sizes_under_prefix(api, repo_id, prefix, repo_type)` (primary destination — canonical, or overflow when `route_all_to_overflow`).
3. If `f"{prefix}/OVERFLOW_POINTER.json" in remote` (a prior run rerouted): also probe the overflow repo (`repo_type="model"`) and merge. [v2] Skip-precedence: when a dest resolves on BOTH repos, prefer CANONICAL for the pending `(repo, repo_type)` entry (critic suggestion 4).
4. A shard is SKIPPED iff its dest is present with `size == shard.stat().st_size` (size mismatch → re-upload). Skipped shards: recorded in new `ShardUploadResult.skipped_existing: list[str]` (additive field, `default_factory=list`); appended to `pending` with their found `(repo, repo_type)` so verify + delete cover them; NOT appended to `uploaded` (that list keeps meaning "committed or rerouted by this call").
5. Probe failure semantics: rides `retry_transient`; on exhaustion the error propagates (fail-loud) — a resume probe that cannot read the Hub must not silently re-upload everything against a quota'd repo.

### 3.4 What does NOT change

Per-file walk body (retained for `batch=False` / over-threshold stores, minus the skip-set exclusion); `_verify_present`; `_batched_verify`; pointer/event writers; `_reroute_to_overflow`; proactive #1034 gating (verdict + privacy threading); result parity (rerouted ⊂ uploaded); module docstring updated to describe the two modes.
