## 1. Goal + requirement + acceptance criteria

**Goal (task frontmatter):** tighten `_is_transient_upload_error` to short-circuit non-transient on 4xx status codes.

**Requirement:** `_retry_upload` must never retry a deterministic HTTP client error (4xx other than 408/429) regardless of what digits/words its message embeds; genuinely transient errors (408, 429, 5xx, connection drops, timeouts) keep the existing bounded 6-attempt exp-backoff retry.

**Acceptance criteria (code-change form):**
1. `_is_transient_upload_error(_http_err(404, ".../issue504_raw/x.json"))` returns `False`; wrapped in `_retry_upload`, the thunk is called exactly once and the exception propagates immediately.
2. `_is_transient_upload_error(_http_err(413, "413 ... 15000000000 bytes"))` returns `False` (byte-count digit trap).
3. 408, 429, and all 5xx return `True` by status code — pinned at BOTH boundaries: `_http_err(500)` (inclusive lower endpoint) and representative unlisted codes `_http_err(507)` / `_http_err(520)`.
4. Response-less errors keep substring behavior: `requests.ConnectionError("connection reset")` → `True`, `TimeoutError("Read timed out")` → `True`, `ValueError("bad args")` → `False`. A non-int `status_code` (e.g. the string `"500"` on a mock response) does NOT enter the code branch (`isinstance` guard) and falls to the substring scan.
5. `_is_storage_quota_403` semantics untouched (function not edited); `_is_transient_upload_error(_storage_403())` still `False` (now via the 403 code short-circuit rather than substring miss).
6. Every existing test in `tests/test_hub.py` passes; ruff clean.

## 2. Method delta (what differs from current code)

Current (hub.py:545-566): status-code check is a **positive-only** allowlist — `code in (429, 500, 502, 503, 504)` returns `True` on match, but on ANY other code (incl. all 4xx, and 5xx codes like 507/520) it **falls through** to the fuzzy `str(err).lower()` substring scan, which matches `"504"/"502"/"503"/"500"` anywhere in the message.

New: when a **real integer** status code is present, the decision is **entirely by code** — `code in (408, 429) or 500 <= code < 600` — with no substring fallback. The substring scan runs only when `code` is not an int (response-less exceptions: `requests.ConnectionError` has `response=None`; `TimeoutError`/`OSError` have no `response` attribute). Three deliberate side effects: (a) 5xx codes outside the old tuple (507, 520-class) become transient **by code** instead of depending on message text; (b) a 4xx (other than 408/429) whose message contains "connection"/"timeout"/"504" etc. becomes deterministically non-transient; (c) coded 408 Request Timeout — the one retryable-by-definition client code, previously retried only by the accident of the "timeout" substring — becomes transient **by code** (no protection loss).

`_is_storage_quota_403`, `_retry_upload`, and all call sites are unchanged.

### Diff sketch — hub.py

```python
def _is_transient_upload_error(err: Exception) -> bool:
    """True for retryable transient HF/HTTP upload errors (408/429/5xx by
    status code, connection drops / timeouts by message) — NOT the persistent
    storage-quota-403. When the exception carries a real integer HTTP status
    code, the decision is made ENTIRELY by code: 408 (request timeout), 429,
    and any 5xx are transient; every other code (all remaining 4xx) is
    non-transient, with NO substring fallback — 4xx messages can embed digit
    triplets ('issue504_raw/...', byte counts) that would read as
    false-transient (#989). The substring scan applies only to response-less
    errors (ConnectionError, timeouts)."""
    code = getattr(getattr(err, "response", None), "status_code", None)
    if isinstance(code, int):
        return code in (408, 429) or 500 <= code < 600
    msg = str(err).lower()
    return any(
        s in msg
        for s in (
            "504",
            "502",
            "503",
            "500",
            "gateway time-out",
            "gateway timeout",
            "timed out",
            "timeout",
            "connection",
            "temporarily unavailable",
        )
    )
```

(Net change: replace the `if code in (429, 500, 502, 503, 504): return True` block with the `isinstance(code, int)` full-decision branch; substring tuple unchanged; docstring updated per docstring-on-edit.)

## 10. §11 Decision Rationale

1. **Transient-by-code set is `{408, 429} ∪ [500, 600)`** (v2: 408 added per the Methodology-Codex Must-Fix).
   - **What:** when a real int status code exists, transient iff `code in (408, 429) or 500 <= code < 600`.
   - **Why (5xx):** every 5xx is by definition a server-side condition (RFC 9110 §15.6); the current code already effectively retried unlisted 5xx via the substring scan whenever the message named a gateway error — deciding by code makes that coverage deterministic. Cost asymmetry: retrying a rare persistent 5xx costs the same bounded ~10 min worst case the wrapper already accepts; NOT retrying a transient 520 fail-fasts a recoverable upload. **Why (408):** RFC 9110 §15.5.9 — 408 explicitly invites the client to repeat the request; it is the one retryable-by-definition client code, and under current code it IS retried (via the "timeout" substring), so including it preserves protection instead of silently dropping it (the Must-Fix). **Why (other 4xx non-transient):** deterministic client errors; the known persistent HF errors that must NOT retry are the storage-quota **403** and the >10000-files **400** `BadRequestError` (gotchas.md) — both 4xx.
   - **Source:** RFC 9110 semantics + this repo's own validated retry design in #735 (built `TestRetryUpload` + the wrapper) and #794 (extended it to `list_repo_files_complete`); gotchas.md "HF Hub rejects ... `BadRequestError` ... NOT transient" (the 400 class), upload-policy.md "storage-quota 403 is persistent" (the 403 class); huggingface_hub's own `http_backoff` default retry set `(500, 502, 503, 504)` + pagination's explicit 429 (Codex-alternatives verified on the installed 0.36.2). Cloudflare/Xet 520-class occurrence in this repo is UNVERIFIED (fact-checker) — treated as design motivation only; the decision stands on RFC semantics + no-coverage-regression.
   - **Alternatives:** keep the exact (500,502,503,504) tuple by code and non-transient for other 5xx — rejected: silently DROPS retry coverage the substring scan currently provides for gateway-error messages, a behavior regression orthogonal to the bug. Declare coded-408 non-transient (the Must-Fix's other branch) — rejected: drops real protection for the one retryable client code; three of six critics independently preferred inclusion.
2. **Substring scan retained ONLY for response-less errors (`isinstance(code, int)` gate).**
   - **What:** message-sniffing applies only when no integer status code exists on the exception.
   - **Why:** `requests.ConnectionError.response` is `None` and `TimeoutError` has no `.response` attribute (both verified live on the installed requests 2.33.1) — these carry no code, so message matching is the only signal; conversely a real code is authoritative, and message digits are provably unreliable (`issue504_raw` paths, byte counts). The `isinstance(code, int)` guard (rather than `is not None`) keeps exotic non-int `status_code` attributes out of the code branch — pinned by new test 5(c).
   - **Source:** live introspection of the installed libs (§11 Assumptions); `huggingface_hub` 0.36.2 `HfHubHTTPError(response=...)` semantics; prior issues #735/#794.
   - **Alternatives:** delete the substring scan entirely and enumerate exception types — rejected: broader change, breaks `test_connection_error_retried`'s message-based contract, out of scope. (Known accepted residual, scoped out: a response-LESS error whose message embeds a digit triplet — e.g. `OSError(".../issue504_raw/...")` — keeps today's substring behavior; bounded 6-attempt retry then fail-loud, byte-identical to current.)
