## Goal (verbatim from body §Goal)

> Make persist-by-default the standing rule: every artifact a run produces (model
> generations / rollout text, judge outputs, intermediate metrics + tensors, configs)
> is uploaded to permanent storage before pod termination, whether or not the current
> task consumes it — because a sibling/follow-up may. Discarding an artifact requires
> an explicit, recorded justification, not silence.

## Design decisions (the four the body left open)

### Decision 1 — Discard-justification form + schema: **plan §10 `discarded_artifacts:` frontmatter slot** (recommendation accepted, argued below)

**Chosen:** a `discarded_artifacts:` list in the plan §10 Reproducibility Card, each entry
`{name, reason, regen_recipe}`. The upload-verifier reads it at Step 3 to license a
generation/tensor discard.

**Why (not a new marker, not inline-in-driver):**
- §10 is ALREADY the artifact-declaration surface the verifier reads (planner.md §10; the
  verifier's Step 2.7/2.8 read the plan's `primary_deliverable:` / analysis-input
  declarations). Adding the discard slot THERE keeps ONE source of truth — the reason the
  body recommended (a).
- A new `epm:artifact-discarded v1` marker (option b) would be a public-contract addition
  (marker schema) → `architectural: true` → user greenlight; it also splits the
  declaration across §10 (what's kept) and events.jsonl (what's dropped), so the verifier
  has to reconcile two surfaces. Rejected on both counts.
- Inline-in-driver + a verifier code-scan (option c) is the least legible: the verifier
  would have to parse arbitrary driver source to find a discard comment, and a discard
  reason living in a `src/` script the plan never names is exactly the "silent" state the
  task exists to end. Rejected.
- **Mechanizability:** the three fields are a concrete YAML shape a future `verify_plan.py`
  check can assert (name non-empty, reason non-empty, regen_recipe non-empty) — this
  gives the schema teeth beyond descriptive prose (addresses the Kill criterion below).
  The verifier reads it as structured YAML, not free prose, so "the field is descriptive
  only" is avoided by construction.

### Decision 2 — Cheap-vs-big tensor threshold: **kind-based table + a ~5 GB bytes fallback** (recommendation accepted)

**Chosen:** classify by artifact KIND first — **text/JSON (rollout text, judge outputs,
metrics, configs) is ALWAYS cheap → upload unconditionally** (non-LFS, KB–MB, #541-safe);
**activation stores / per-context `v(x)` at full corpus are ALWAYS big → the
upload-if-cheap-else-persist-the-regenerating-text branch.** For a tensor not on the
kind table, a **~5 GB bytes fallback**: ≤5 GB → upload; >5 GB → the else-persist-text
branch + `discarded_artifacts:` entry.

**Why:** a pure bytes threshold miscategorizes text (a many-MB rollout JSONL is "big" by
bytes but rides the free non-LFS path — it must always upload) and understates the real
constraint, which is the LFS endpoint, not raw size. Kind-first captures the LFS-vs-non-LFS
distinction the #541 recovery actually keys on (upload-policy.md line 208: `*.json`/`*.jsonl`
NOT LFS-matched). The ~5 GB fallback is a coarse tie-breaker for a novel tensor kind, chosen
to sit well below the ~15 GB adapter/merged-dir scale the quota problems actually came from
while comfortably above a per-cell shift tensor (KB–MB, #521 — always uploads). The
threshold is a SOFT guideline in prose, not a hard verifier gate (the verifier gates on
DECLARATION presence, not on tensor size), so a mis-estimate never blocks a run.

**Source:** upload-policy.md lines 205–220 (#541 LFS-endpoint-only gate + text-sharding),
CLAUDE.md line 313 (analysis tensors are KB–MB → always upload), the #653 merge-disk facts
(~15 GB merged Qwen — the scale the 5 GB fallback sits under).

### Decision 3 — Verifier verdict for a missing/undeclared generation-discard: **FAIL** (recommendation accepted)

**Chosen:** a stage that produced model generations and dropped them with NO matching
`discarded_artifacts:` declaration is a **FAIL** (blocker tag
`generation-discarded-undeclared`), consistent with the verifier's other silent-data-loss
hard gates (Step 2.7 primary-deliverable, Step 2.8 analysis-inputs — both FAIL).

**Why FAIL not WARN:** the whole point of the task is to prevent silent loss of a
production-path artifact. WARN would let the pod terminate (the destroy step), and the
data is gone — the exact #365/#779 outcome. A FAIL keeps the cheap-fix window open (pod +
generations still alive) exactly like Step 2.7/2.8. The escape from a FAIL is cheap and
legible: either persist the rollout text (KB–MB, non-LFS, seconds) OR add a
`discarded_artifacts:` declaration to the plan — both are the intended behaviors, not
punishments.

**Forward-only guard (Risk mitigation, see Risks):** the FAIL fires only on runs whose
plan carries the `discarded_artifacts:` slot capability — a run whose plan PREDATES this
slot AND has a generation-discard emits a WARN `generation-discard-spec-absent` (mirroring
Step 2.7's `primary-deliverable-spec-absent` legacy WARN, lines 355–362), never a hard
FAIL. New plans (which all carry the slot) get the FAIL; ~30 in-flight legacy plans ship.

### Decision 4 — HF layout for extraction rollouts: **`raw_completions/<stage>/`** (recommendation accepted)

**Chosen:** extraction rollouts live under `raw_completions/extraction/`, monitoring under
`raw_completions/monitoring/`, final-condition completions under `raw_completions/final/`
(or the bare `raw_completions/{condition}_seed{S}.json` for a single-stage run — the
`<stage>/` segment is omitted when there is only one stage, so existing single-stage runs
are unchanged).

**Why the stage prefix, not a sibling `extraction_completions/`:** the verifier's Step 1
already classifies `raw_*.json` / `*_completions*.json` under the `raw_completions/`
destination and its discovery globs key on that prefix (lines 122–123). A sibling
top-level dir would need a NEW discovery rule + a new verdict row; the `<stage>/` subdir
reuses the existing rollout-checking logic and just disambiguates which stage produced
the file. It also reads naturally in the Upload Policy table (one row covers all stages).

**Source:** upload-verifier.md lines 122–123 (existing `raw_completions` classification),
CLAUDE.md line 308 (existing `raw_completions/{condition}_seed{S}.json` layout — the
`<stage>/` slots cleanly in front of `{condition}`).

## Kill criteria (what would kill this fix)

1. **Schema can't be verified mechanically.** If analysis shows the
   `discarded_artifacts:` fields can only ever be descriptive prose the verifier can't
   check → the fix loses teeth. Mitigation already in the design: the three-field YAML
   shape is presence-checkable (name/reason/regen_recipe non-empty), and the verifier reads
   it as structured YAML, not prose. Kill only if even that presence-check proves
   unimplementable — then restart with a stricter machine-readable schema (e.g. an
   enum `reason` + a required `regen_command`).
2. **Re-breaks #541.** If the rollout-text load-bearing minimum demonstrably blows the LFS
   quota on a large sweep → kill; revisit. This is designed out: text is routed to the
   NON-LFS path (the #541 gate fires only on LFS), which stays open over quota. A kill
   here would mean the non-LFS routing assumption (upload-policy.md line 208) is wrong —
   it is verified in this plan, so this is a genuine-surprise kill only.

   grid → kill. Designed out: every surface says the stream-reduce is UNCHANGED and only
   the rollout TEXT (KB–MB) is the persisted minimum; `v(x)` persist is opt-in
