```
cmd=$(jq -r '.tool_input.command // empty'); if echo "$cmd" | grep -qE '\|[[:space:]]*python3?(\.[0-9]+)?[[:space:]]+(-[^[:space:]]+[[:space:]]+)*-[cm]([[:space:]]|$)'; then echo 'BLOCKED: bare `| python -c/-m` pipe. This VM has no `python` on PATH — `python: command not found` (exit 127). Pipe into `uv run python` instead: `... | uv run python -c "..."`. CLAUDE.md § Task Workflow API.' >&2; exit 2; fi
```

(Note: hook uses POSIX `grep -qE` so `\d` → `[0-9]` and `\s` → `[[:space:]]`; the Python `re` lint uses `\s`/`\d`. The two regexes are semantically identical, differing only in the engine's character-class syntax — §11 records this.)

### Regex precision — match vs don't-match (the load-bearing decision)

**Lint regex (Python `re`):** `\|\s*python3?(?:\.\d+)?\s+(?:-\S+\s+)*-[cm]\b`
**Hook regex (POSIX ERE):** `\|[[:space:]]*python3?(\.[0-9]+)?[[:space:]]+(-[^[:space:]]+[[:space:]]+)*-[cm]([[:space:]]|$)`

The TRUE failure shape is **a shell pipe whose consumer is the bare `python`/`python3` interpreter invoked with `-c` or `-m`**. The `\|` pipe anchor + the `-[cm]` flag anchor are what make this narrow. The `(?:-\S+\s+)*` middle allows intervening single-dash flags (`| python -u -c`).

**MATCHES (≥6 — the real failures):**
1. `cat x.json | python3 -c "import sys,json; ..."` ← offender #1
2. `task.py view 1 --json | python3 -c "import sys,json"` ← offender #2
3. `echo '{}' | python -c "print(1)"`
4. `foo | python3.11 -c "x"`
5. `foo | python -m json.tool`
6. `foo |python -c "x"` (no space after pipe)
7. `cat x | python -u -c "x"` (intervening flag)

**DOES NOT MATCH (≥6 — the false positives the anchor avoids):**
1. `echo "use uv run python instead"` (literal docs string — no `| python -c`)
2. `curl https://pypi.org/python-3.12/` (URL containing "python" — no pipe-into-python)
3. `cat setup.py | grep foo` (`setup.py` mentioned — consumer is `grep`, not `python`)
4. `which python` / `command -v python` / `apt-get install python3` (informational — no pipe consumer)
5. `cat x | uv run python -c "x"` (correct usage — `python` is not the token right after `|`; the token after `|` is `uv`)
6. `python scripts/foo.py < input` (start-of-command, no pipe consumer — deliberately out of scope, §"Out of scope")
7. `ls python_helpers.py | wc -l` (filename containing "python" — consumer is `wc`)
8. `foo | python3 -c '... mentions python ...'` matches (correct — it IS `| python3 -c`); a STRING that merely contains the text `| python -c` inside quotes (e.g. `echo "bad: | python -c"`) is a known recall-vs-precision edge — see "Known limitation" below.

**Backed against `--check-heredoc-dotenv` precision:** that check explicitly considered and REJECTED `python -c` one-liners as out of scope — but for a DIFFERENT reason (under `-c`, python-dotenv's `find_dotenv()` frame-walk short-circuits, so the crash it guards never fires). THIS rule's crash (`python: command not found`) fires for ANY bare `python` consumer including `-c`/`-m`, so `-c`/`-m` are the IN-scope must-catch here. The two rules' scopes are correctly disjoint.

**Known limitation (recall, deliberately accepted — mirrors `--check-dispatcher-cvd-pin`'s recall sacrifice):** the lint/hook can match a `| python -c` substring that appears INSIDE a quoted string literal (e.g. a heredoc body or a documentation string that literally contains `| python -c`). This is a false-positive risk in the rare case a script DOCUMENTS the bad pattern. Mitigation: the lint skips `#`-comment and `echo `-prefixed lines (the common documentation shapes); a genuine in-string false positive in a non-comment/non-echo line is vanishingly rare in `scripts/*.sh` (zero in the current tree beyond the 2 real offenders). We do NOT add a waiver token for v1 (YAGNI — `--check-heredoc-dotenv` ships with no waiver; add one only if a real false positive surfaces). The hook, reading arbitrary Bash, has the same edge; if it proves noisy in practice the regex can be tightened in a follow-up, but the daily evidence (41× real failures, the pattern is consistently the literal pipe-into-python) says the anchor is right.

## 11. Decision Rationale

N/A — no model training, no hyperparameters. Non-obvious design choices:

- **What:** Both a hook AND a lint mode (not one). **Why:** the hook catches inline ad-hoc commands at runtime (the 41× daily failure mode — composed inline, never committed); the lint catches the pattern in committed `scripts/*.sh` (the 2 existing offenders prove this surface exists). They cover disjoint surfaces. **Source:** task body explicitly suggests both; `--check-heredoc-dotenv` precedent for the lint half. **Alternatives:** hook-only (misses committed scripts → the offenders would never have surfaced); lint-only (misses inline commands → doesn't stop the 41× daily failures).
- **What:** regex anchored to `\| python -c`/`-m`, not bare `python ` substring. **Why:** the daily evidence is exclusively the pipe-into-python-`-c`/`-m` shape; the substring would false-positive on docs/URLs/filenames/`which python`. **Source:** /daily 2026-06-29 report (`| python -c` / `| python3 -c` cited as the dominant shapes); false-positive set enumerated in §4. **Alternatives:** bare `python ` substring (rejected — too broad); also matching start-of-command `python` (rejected — no recurrence evidence, false-positive risk).
- **What:** scope the lint to `scripts/*.sh` only (NOT SKILL.md / `.py` subprocess calls). **Why:** mirrors `--check-heredoc-dotenv` scope exactly; SKILL.md files CONTAIN documentation bash examples that would false-positive; `.py` `subprocess.run(["python", ...])` is a different surface with no daily evidence. **Source:** clarify resolution + task body explicit "scope to `scripts/*.sh` only". **Alternatives:** broader scope (rejected — false positives on documented snippets).
- **What:** no waiver token in v1. **Why:** `--check-heredoc-dotenv` ships with no waiver (there's no legitimate `| python -c` on this VM); YAGNI. **Source:** `--check-heredoc-dotenv` precedent. **Alternatives:** add `# PIPE_PYTHON_EXEMPT:` (deferred — add only if a real false positive surfaces).
- **What:** hook uses POSIX ERE (`[0-9]`/`[[:space:]]`), lint uses Python `re` (`\d`/`\s`). **Why:** `grep -qE` is POSIX; Python `re.compile` supports `\d`/`\s`. The two are semantically identical. **Source:** the 4 existing hooks use `grep -qE` POSIX classes; `check_heredoc_dotenv` uses Python `re`. A test asserts both engines agree on the example set.
