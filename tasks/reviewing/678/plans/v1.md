# Plan — issue #678: Route workflow-surface fixes through a background `/issue --auto` session

## 1. Goal

Replace the lightweight `Agent(subagent_type="workflow-improver", run_in_background=true, isolation="worktree")` auto-spawn in the workflow-fix-on-bug protocol with a heavier, fully-reviewed path: when a workflow-fix candidate is raised (a formal `<!-- workflow-fix-candidate v1 -->` block OR a surfaced prose follow-up), the receiving orchestrator **files a `kind: infra` task** pre-filled from the candidate, then **spawns a background `/issue <N> --auto` session** to implement it. The fix then lands via the full `/issue` code-change pipeline — clarifier → `/adversarial-planner` (planner + Phase-2 critic ensemble ∥ consistency-checker) → plan-approval gate → worktree + `experiment-implementer` → Claude+Codex `code-reviewer` ensemble → inline test-verdict → auto-complete + Step 10d worktree auto-merge — instead of "edit + one review". The workflow surface is where a bad change has the widest blast radius, so it earns the heaviest review, not the lightest. The user's directive (verbatim): *"Instead change it so it uses a background happy coder session (so we get the plan review and all this)."* This task (#678) is itself the FIRST instance of the new pattern, filed + spawned by hand because the new mechanism cannot route its own creation.

## 2. Prior work / sibling pattern

The migration target reuses an already-production-tested mechanism: the autonomous `/issue` session spawner.

**Invocation shape** (verified by `uv run python scripts/spawn_session.py spawn-issue --help`):

```bash
uv run python scripts/spawn_session.py spawn-issue --issue <N> --auto
```

`--auto` is documented as *"Shorthand for `--initial-prompt '/issue <N>'`"*; it boots the full `/issue <N>` skill in `bypassPermissions` mode (no human at the keyboard) and arms the recurring `/issue-tick <N>` cron.

**Env injection** (read at `scripts/spawn_session.py:858-866`): a prompt-bearing (`--auto`) spawn sets, in the new session's environment:

```python
body["environmentVariables"] = {
    "HAPPY_INITIAL_PROMPT": prompt,                 # "/issue <N>"
    "HAPPY_INITIAL_MODE": "bypassPermissions",
    "EPM_AUTONOMOUS_SESSION": "1",                  # push-through-bugs autonomous mode
    "EPM_PLAN_AUTOAPPROVE_GPU_HOURS": str(args.auto_approve_gpu_hours),  # default 100
}
body["claudeArgs"] = ["--dangerously-skip-permissions", *extra_args]
```

So `EPM_AUTONOMOUS_SESSION=1` is set ONLY by a `--auto` spawn (confirmed: it appears in `cmd_spawn_issue`'s prompt branch and `cmd_spawn_campaign`, never on a bare interactive spawn). `EPM_PLAN_AUTOAPPROVE_GPU_HOURS` defaults to `100` (`--auto-approve-gpu-hours` default).

**Registration file** (written by `_register_autonomous_session`, `scripts/spawn_session.py:891-902`): one file per issue at `~/.eps-autonomous/issue-<N>.json` (`AUTONOMOUS_REGISTRY_DIR = Path.home() / ".eps-autonomous"`, line 58). The write is an atomicity invariant — if registration fails the just-spawned session is stopped and the spawn aborts ("a live `--auto` session MUST have a current registry entry, else the watcher could re-spawn it as a duplicate → duplicate pod → spend"). Manual (non-`--auto`) issue sessions register a sibling `~/.eps-autonomous/manual-issue-<N>.json` for `list` enrichment only.

**Watcher contract** (`scripts/autonomous_session_watch.py`, every 10 min): crash-recovery respawn of registered `--auto` sessions, pod-safety reconciliation, stalled-session detection, a capacity-retry pass, and a gate-push pass (Telegram phone push on gate-park / `blocked` transitions). A workflow-fix `/issue` session inherits ALL of this for free.

**Production-tested:** the clarifier's `epm:clarify` note records that `spawn-issue --issue <N> --auto` was *"used for #676/#677/#678 same day"* — i.e. this exact spawner ran three times the same day this task was filed. The mechanism is not new; only its NEW caller (the workflow-fix protocol) is.

## 3. The six design questions — decisions + rationale

### Q1 — All candidates, or a threshold? → **All in-scope candidates route to a session. No threshold, no lighter path.**

Every in-scope, non-architectural candidate (formal block OR prose follow-up) files an infra task + spawns `/issue <N> --auto`. There is no "trivial one-liner" fast lane. **Rationale:** the user's bias is "full session for anything non-trivial", and the protocol cannot mechanically distinguish trivial from non-trivial without LLM judgement on the trigger — which the current `surgical | substantive | architectural` classification proves is itself an LLM call inside the spawned agent, not a parseable gate the orchestrator can apply pre-spawn. A size threshold (`diff_sketch` line count) is gameable and was never the cost driver; the cost of a session is ~30-60 min wall (acceptable for the workflow surface, §7). Routing ALL candidates keeps the trigger purely mechanical (candidate present → file + spawn), which is the whole point of the migration. The full `/issue` pipeline self-sizes: a genuinely one-line fix produces a trivial plan that auto-approves at 0 GPU-h and a one-round implementer + code-review — heavier than today's path, but uniformly so, with no decision branch to get wrong.

### Q2 — Fate of `workflow-improver`. → **Retire it.** Archive its agent file with a DEPRECATED banner; move its agent-memory to `.claude/agent-memory/implementer/`.

The `/issue` Step 4b code-change path already dispatches `experiment-implementer` (for experiment code) or `implementer` (for standalone infra / refactor / utility code — which is exactly what a workflow-surface edit is). The new path's infra task is `kind: infra`, so `/issue` routes it to `implementer` at Step 4b. There is no implement step for `workflow-improver` to occupy — `implementer` already owns it. **Rationale:** repurposing `workflow-improver` as the Step-4b implementer would duplicate `implementer`'s role and force a second `subagent_type` decision in SKILL.md keyed on "is this a workflow-fix task?", reintroducing exactly the brittle branch this migration removes. Retiring is cleaner and matches the precedent for the retired `reviewer` agent (frozen file, DEPRECATED banner, kept for historical reference). **Agent-memory disposition:** `workflow-improver`'s 35 memory files (`.claude/agent-memory/workflow-improver/`) encode hard-won workflow-surface-editing lessons (worktree-vs-main edit discipline, lint-emit-tables regen, pre-existing-lint baselines, reuse-fitness mirror sets, watcher test recipes). These remain valuable to whoever now edits the workflow surface — the `implementer`. **Move the entire directory verbatim to `.claude/agent-memory/implementer/`** (`git mv` each `feedback_*.md` / `reference_*.md`, merge `MEMORY.md` index lines into `implementer/MEMORY.md`), so `implementer` loads them on its next spawn. Do NOT delete and do NOT archive-to-`_archive` — these lessons are live, and `implementer` is the agent that will now hit those same traps. (If `.claude/agent-memory/implementer/` does not exist, create it; the implementer agent reads `memory: project` per its frontmatter.)

### Q3 — Candidate → task mapping. → **File a `kind: infra` task from a body template, dedup on a new `workflow_fix_target:` frontmatter field, then spawn `--auto`.**

The orchestrator, on receiving an in-scope non-architectural candidate, runs (after the existing grep-the-surface-first + one-formal-block-per-invocation rules, both preserved):

```bash
# 1. DEDUP: skip if an OPEN workflow-fix infra task already targets this file.
#    Match on the workflow_fix_target frontmatter field (set on every task this
#    mechanism files), across NON-terminal statuses only.
EXISTING=$(uv run python scripts/task.py list-by-status --status proposed --json; \
           uv run python scripts/task.py list-by-status --status planning --json; \
           ... plan_pending approved running verifying interpreting reviewing \
               awaiting_promotion followups_running blocked on_hold)
# (the orchestrator unions these NON-terminal statuses and greps each task's
#  body frontmatter `workflow_fix_target:` for an EXACT match on the candidate's
#  target_file string; a hit -> do NOT double-file, log epm:workflow-fix-candidate
#  with note "deduped against open #<M>" and continue.)

# 2. FILE the infra task (no dedup hit):
uv run python scripts/task.py new --kind infra \
  --title "workflow-fix: <proposed_change, <=60 chars>" \
  --body-file /tmp/wf-fix-body-<slug>.md \
  --origin-prompt "<verbatim candidate block OR surfaced prose>"

# 3. SPAWN the autonomous session on the returned id N:
uv run python scripts/spawn_session.py spawn-issue --issue <N> --auto
```

**Dedup predicate (exact):** the candidate is a duplicate iff there exists a task with `kind: infra` AND a `workflow_fix_target:` frontmatter value that EXACTLY string-matches the candidate's `target_file` AND whose status is NOT in the terminal set `{completed, archived}`. The new `workflow_fix_target:` frontmatter field is the canonical dedup key — written into the body file's YAML frontmatter at file time (step 2), grepped at dedup time (step 1). It is preferred over a body-text grep (fragile — the path appears in prose) and over a title grep (titles are summaries, not paths). `task.py new` builds frontmatter from its own flags and does NOT merge a body-file's frontmatter, so the orchestrator writes `workflow_fix_target:` into the body file's frontmatter block AND the body file's frontmatter is what the dashboard/registry never reads for this field — therefore the dedup grep reads the on-disk `body.md` frontmatter directly via `task.py view <M> --json` (the `frontmatter` dict). (Implementation note for the implementer: if `frontmatter` does not surface unknown keys, the dedup falls back to grepping the literal line `workflow_fix_target: <path>` in the task's `body.md`; either way the field is the key.)

**Body-file template** (the orchestrator fills the `<...>` placeholders mechanically from the candidate block fields; for a prose follow-up it synthesizes the same fields per the existing prose-synthesis rule):

```markdown
---
kind: infra
workflow_fix_target: <target_file — the exact candidate target_file string>
---
## Overview / Motivation

Auto-filed by the workflow-fix-on-bug protocol from a workflow-fix candidate
raised on task <related_task> (emitting agent: <emitting_agent>).

## Goal

<proposed_change — one sentence>

## Workflow gap

- **Bug observed:** <bug_observed>
- **Why it is a workflow gap:** <why_workflow_gap>
- **Confidence (emitter):** <confidence>

## Proposed change (candidate diff sketch — refine in planning)

```
<diff_sketch verbatim, OR "(none — synthesized from prose follow-up)">
```

## Scope / surfaces

- Primary target: `<target_file>`
- Grep the workflow surface for the pattern before editing
  (`grep -rln '<pattern>' .claude/ CLAUDE.md scripts/`) and update every hit;
  list them in the plan.

## Constraints / invariants

- Workflow-surface only — never experiment code, `configs/`, or `tasks/`.
- `scripts/workflow_lint.py --check-asks` passes; ruff on touched files passes;
  if `workflow.yaml` or `CLAUDE.md` change, they stay consistent with the rule file.
- This session runs under `EPM_WORKFLOW_FIX_SESSION=1` — it MUST NOT auto-route
  any of its own subagents' workflow-fix candidates (recursion guard, Q4).

## Provenance

<verbatim candidate block, including the opening + closing comment lines,
 OR the verbatim surfaced prose for a prose follow-up>
```

The `--origin-prompt` carries the verbatim candidate (the `## Provenance` body section duplicates it for human readability; the origin_prompt is the machine record the clean-result `**Context:**` row ships forward). **Preserved rules:** one formal `<!-- workflow-fix-candidate v1 -->` block per emitting-agent invocation (prose follow-ups uncapped, each files its own task); grep-the-surface-first before populating `target_file`; subagents NEVER file/spawn — only the orchestrator routes.

### Q4 — Recursion guard. → **`EPM_WORKFLOW_FIX_SESSION=1`, set by the spawner on the workflow-fix session, READ on the candidate-receive side; analogue of `AUTO_REVIEW_DISABLED`.**

A workflow-fix `/issue` session must not auto-file MORE workflow-fix sessions for its own subagents' findings (otherwise: implementer → emits candidate → orchestrator files+spawns → that session's implementer emits a candidate → ... unbounded fan-out). **Mechanism:** the candidate-receive logic (in `.claude/rules/workflow-fix-on-bug.md` + SKILL.md) checks `os.environ.get("EPM_WORKFLOW_FIX_SESSION") == "1"` BEFORE filing/spawning. If set, the orchestrator does NOT file/spawn — it LOGS the candidate to `events.jsonl` (`epm:workflow-fix-candidate v1`, note: `parked — running under EPM_WORKFLOW_FIX_SESSION, see §recursion-guard`) and surfaces it as a notification, exactly as the current `AUTO_REVIEW_DISABLED` clause suppresses the spawn ("If your prompt carries that sentinel, treat workflow-fix candidate emission as forbidden for the turn"). **Where it is SET:** the spawn command in Q3 must export it into the child session's environment. `spawn-issue` does not today accept an arbitrary env var, so the load-bearing implementation choice is one of (the implementer picks, plan-approved either way as they are equivalent):
- **(a, preferred)** the spawned `/issue` session detects its own workflow-fix nature from the task's `workflow_fix_target:` frontmatter and self-sets the guard at Step 0 — no spawner change needed. The candidate-receive logic then reads the task frontmatter (`workflow_fix_target` present ⇒ this IS a workflow-fix session ⇒ suppress) in addition to / instead of the env var. This is the most robust (survives session restart / crash-recovery respawn, which re-runs `spawn-issue --auto` without custom env).
- **(b)** add a passthrough so the spawner sets `EPM_WORKFLOW_FIX_SESSION=1` in `body["environmentVariables"]` when filing a workflow-fix task. Loses the guard on watcher respawn (the respawn path does not carry the custom env), so (a)'s frontmatter check is the durable backstop.

**Decision:** require BOTH — `workflow_fix_target:` frontmatter is the durable signal the candidate-receive side keys on (survives respawn), and `EPM_WORKFLOW_FIX_SESSION=1` is the in-session convenience flag. The rule text states: *"A session is a workflow-fix session iff its task carries `workflow_fix_target:` frontmatter OR `EPM_WORKFLOW_FIX_SESSION=1` is set; such a session NEVER auto-files/spawns workflow-fix tasks — it logs + notifies, like `AUTO_REVIEW_DISABLED`."* The escape valve (§7): such a session CAN still emit candidate blocks — they get parked/notified, not auto-routed, so its own workflow-fix bug is never silently lost.

### Q5 — Auto-merge / push reconciliation. → **The `/issue` Step 10d worktree auto-merge owns the merge; the plan-approval gate (Step 2c) is the architectural-greenlight surface; the planner decides the gate via an `architectural: true` frontmatter flag.**

Under the new path the orchestrator no longer merges a `workflow-improver` worktree — the spawned `/issue` session owns its Step 10d worktree auto-merge to `main` (already automatic, no approval gate, per the standing 2026-06-03 rule). This SATISFIES "workflow-surface edits are committed + merged + pushed automatically, no approval gate" for non-architectural fixes: the autonomous session auto-approves the plan (0 GPU-h ≤ cap), runs the full pipeline, and Step 10d merges + pushes. **Architectural / public-contract changes still need greenlight**, now expressed as the `/issue` plan-approval gate: the autonomous session AUTO-APPROVES under `EPM_PLAN_AUTOAPPROVE_GPU_HOURS=100` because a workflow fix is 0 GPU-h — so the GPU-h cap alone would auto-approve EVERYTHING, including architectural changes. That is NOT the desired default for the architectural subset. **Reconciliation:** the planner, in the workflow-fix task's plan, sets an `architectural: true` flag in the plan frontmatter (and states a one-line "ARCHITECTURAL — needs user greenlight" banner in the Plan Summary) whenever the change would rename a status enum / change a marker schema or `task.py` subcommand / relocate an agent file / restructure a subsystem (the existing architectural test, verbatim from the suppress-spawn clause). The `/issue` autonomous-approval logic gates on BOTH the GPU-h cap AND `architectural != true`: a plan flagged `architectural: true` PARKS at `plan_pending` for the user regardless of GPU-h, exactly the current architectural-greenlight semantics. Non-architectural workflow fixes (the vast majority) auto-approve at 0 GPU-h and self-merge — preserving the no-greenlight default. **Who decides:** the planner (it already classifies architectural-ness; the suppress-spawn clause's test moves into the planner's §-summary). The GPU-h cap stays 100 as the spawn default; the architectural flag is the orthogonal second gate that the cap does not subsume. (Implementation note: the autonomous plan-approval logic in `/issue` Step 2c must be extended to read `architectural:` from the plan frontmatter and park on `true`. If that wiring is larger than this task should carry, the fallback is: the protocol instructs the orchestrator to spawn architectural candidates WITHOUT `--auto` — i.e. file the task but open a bare session that parks at `plan_pending` until a human types `/issue <N>` — and log the candidate for the user. State this fallback in the rule so the architectural-greenlight invariant holds even if the Step-2c flag wiring is deferred.)

### Q6 — Markers. → **Keep `epm:workflow-fix-candidate|applied|failed` with adapted semantics, AND add one new marker `epm:workflow-fix-task-filed v1`.**

The three existing markers stay (the dashboard + weekly mechanization ratchet read them), with semantics re-pointed at the spawned task:
- `epm:workflow-fix-candidate v1` — UNCHANGED trigger (orchestrator receives a candidate). Posted to the originating/parent task's `events.jsonl` (or `.claude/cache/workflow-fix-events.jsonl` if no task). Now records the routing decision in its note: `routed: filed #<N>` | `deduped against #<M>` | `parked: EPM_WORKFLOW_FIX_SESSION` | `parked: architectural`.
- **`epm:workflow-fix-task-filed v1` (NEW)** — posted on the PARENT task when the orchestrator files the infra task + spawns the session. Fields: `filed_task` (the new id N), `target_file`, `session_spawned` (true/false), `origin_candidate` (verbatim). This is the new lifecycle anchor replacing the old "spawned workflow-improver" log line. Posted to the parent task.
- `epm:workflow-fix-applied v1` — semantics ADAPTED: no longer "workflow-improver landed a diff". Now the SPAWNED workflow-fix task's OWN `/issue` Step 10d completion is the apply event. The protocol posts `epm:workflow-fix-applied v1` to the PARENT task (cross-linking `applied_task: #<N>`, `merge_sha`) when the orchestrator observes the child task reach `completed` (its Step 10d merged). On the CHILD task, the normal `/issue` completion markers (`epm:status-changed → completed`, the Step 10d merge) ARE the apply record — no special workflow-fix marker needed there.
- `epm:workflow-fix-failed v1` — semantics ADAPTED: posted to the PARENT task if the child workflow-fix `/issue` session reaches `blocked` / `archived` without merging. Fields: `failed_task: #<N>`, `failure_reason` (child-blocked | child-archived | spawn-failed | dedup-only-no-action-is-not-a-failure-excluded), `origin_candidate` (verbatim).

**Parent vs child split (explicit):** ALL workflow-fix-specific markers (`candidate`, `task-filed`, `applied`, `failed`) fire on the PARENT task (the one that raised the candidate) — they record the routing + outcome from the parent's vantage. The CHILD workflow-fix infra task carries ONLY the standard `/issue` lifecycle markers (created, status-changed, plan markers, implementer/review markers, completion) — it is an ordinary infra task and needs no special markers. This keeps the dashboard's per-task lifecycle clean and lets the parent's events.jsonl tell the "I raised a workflow bug → it was filed as #N → #N merged" story end to end.

## 7. Risks + rollback

- **Blast radius:** workflow-surface only — no experiment code, configs, or task-state touched. The change is entirely in `.claude/**` + `CLAUDE.md` + comment strings in two workflow-helper scripts. Library logic in `task_workflow.py` changes only if the optional dedup helper lands (a pure read-only query function).
- **Rollback:** a single `git revert` of the PR's merge commit on `main` restores the old `Agent(workflow-improver)` path verbatim (the frozen agent file's body is intact; un-freezing is a one-line banner removal). Low-risk reversal.
- **Recursion-guard misfire (escape valve preserved):** a workflow-fix `/issue` session must still be able to surface its OWN workflow-fix bug. Mechanism: such a session CAN emit `<!-- workflow-fix-candidate v1 -->` blocks — under the guard they are LOGGED to `events.jsonl` + surfaced as a notification (Telegram via the watcher gate-push, or the parent's next chat turn) rather than auto-routed. So a genuine workflow bug discovered DURING a workflow-fix is never silently lost; it is parked for the next human/orchestrator pass exactly as `AUTO_REVIEW_DISABLED`-suppressed candidates are. The risk is a one-cycle delay, not a dropped bug.
- **Latency shift (called out, accepted):** an emit site that previously got a same-turn background fix (~minutes) now waits for a session spawn + planner round + critic ensemble + implementer + code-review (~30-60 min wall). This is the intended trade — the user explicitly asked for "the plan review and all this", and the workflow surface's wide blast radius justifies the heavier review. The originating agent's own work is NOT blocked (the file+spawn is non-blocking, identical to today's background spawn); only the FIX lands slower. Acceptable for the workflow surface; stated in the rule so no future reader mistakes it for a regression.
- **Dedup false-negative:** if `task.py view --json` does not surface the unknown `workflow_fix_target:` frontmatter key, the dedup falls back to a literal body grep (stated in Q3). Worst case on a miss: a duplicate workflow-fix task is filed (two sessions edit the same file) — caught by the `/issue` Step 10d worktree merge (the second merge hits a conflict, aborts, requeues per the existing merge-conflict discipline). Bounded, not silent.
- **Architectural-greenlight wiring risk:** if extending Step 2c to read `architectural:` frontmatter is deferred, the fallback (file the task but spawn WITHOUT `--auto`, parking at `plan_pending` for the user) preserves the greenlight invariant. Stated in Q5 so the invariant holds regardless of wiring depth.
