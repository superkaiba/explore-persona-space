# Plan — issue #695: make the idle-unmapped pass actually reap detached, unmapped, genuinely-idle tmux Claude sessions

## 0. Plan Summary

**What this fixes:** the `idle_unmapped_pass` in `scripts/autonomous_session_watch.py`
never reaps the session class it was built for — detached, unmapped,
genuinely-idle tmux-launched Claude sessions (the 2026-06-12 incident: 25 such
sessions held ~23 GB RSS). In the live 2026-06-27 17:34/17:43 cron passes every
such session logged `mapped=False tty=True idle=? action=clear`, so the pass
reaped zero of them via two independent fail-toward-keep paths: a `tty=True`
verdict and an `idle=?` (unresolvable transcript) verdict.

**Two-phase change (no GPU, workflow surface only):**
- **Phase 1 — diagnose** why `_is_live_user_tty` returns `True` in the cron pass
  for a confirmed-detached pane (the live static probe shows it returns `False`,
  so the production divergence must be observed in-pass). Add fail-soft
  instrumentation that logs, per candidate, the resolved detached-set size, the
  wrapper's controlling-tty path, and the `_is_live_user_tty` inputs/verdict.
- **Phase 2 — fix.** (i) Make `_detached_tmux_pane_ttys` robust + observable
  under the cron env and loudly log an empty detached set; (ii) for the
  independently-confirmed `idle=?` secondary gap, add a NARROW corroborating
  idleness fallback (tmux `session_activity` of the pane's tmux session) that
  fires ONLY when the session is detached AND unmapped AND has no running
  descendant *work* process AND owns no running pod AND the corroborating idle
  age exceeds a conservative threshold. Five gates, all must pass; any single
  uncertain signal keeps.

**Load-bearing constraint preserved:** at diagnosis time, of six detached
unmapped tmux sessions, ONE was running an experimenter agent, FOUR had a
typed-but-unsent command, only ONE was genuinely done. The fix can only ever
reap MORE in a CONFIRMED-dead case; every fail-soft path keeps.

**Compute:** none — workflow-surface code + tests only.

`Estimated GPU-hours (total): 0`

**Risks (top 2):** (1) the corroborating idleness fallback fires on a live
working session — mitigated by the five-gate AND including the no-running-work
checks (descendant-work-process + running-pod) and a conservative threshold;
(2) Phase 1 cannot reproduce the production `tty=True` from static state, so the
fix risks treating a symptom whose cause is unconfirmed — mitigated by leaving
the instrumentation in (low-cost, makes any future silent regression visible)
and by making the `idle=?` fallback — which is independently confirmed and is
the actually-load-bearing reap path — the primary remediation.

## 2. Background & motivation

The idle-unmapped pass (third session reaper; `autonomous_session_watch.py`
§9452-10132, CLAUDE.md § Crons → Autonomous-session watcher) exists to
auto-stop UNMAPPED EPS-cwd sessions whose Claude transcript has been idle ≥12h
on ≥2 consecutive checks — the live-but-idle-inner-Claude + unmapped class that
the zombie-wrapper pass (needs a DEAD inner Claude) and the session-reconcile
pass (needs an issue mapping) both structurally exclude. The detached-tmux
refinement (`_detached_tmux_pane_ttys` + `_is_live_user_tty`, §9560-9629) was
added 2026-06-24 specifically so an abandoned detached tmux pane is NOT treated
as a live-user TTY.

The bug: in production the refinement is inert for this class. Live root-cause
evidence (gathered this session, 2026-06-27, against the still-live wrapper
pid 2730037, session `cmqvqzomyw6ngyc0utvuiklhd`, tmux `claude-0626-193535`):

- `/proc/2730037/stat` tty_nr = 34825 (non-zero) → `_wrapper_has_controlling_tty` True.
- `/proc/2730037/fd/{0,1,2}` all → `/dev/pts/9` → `_wrapper_controlling_tty_path` returns `/dev/pts/9`.
- `tmux list-panes -a -F '#{pane_tty}\t#{session_attached}'` reports `/dev/pts/9 ... 0` (attached=0); the owning tmux session `claude-0626-193535` itself reports `attached=0`.
- Therefore, AGAINST THE LIVE STATE NOW, `_is_live_user_tty(2730037, detached_set)` returns **False** — the chain works.

Yet the 17:34/17:43 cron passes logged `tty=True` for every such session →
`decide_idle_unmapped` hits `has_tty -> ("clear", 0)` and reaps nothing. So the
production divergence between "the helpers return False now" and "the pass
logged True at 17:34" cannot be reproduced from static state — it must be
observed in-pass (Phase 1). Separately, even with `tty=False` these sessions log
`idle=?`: the transcript is unresolvable via the happy-log path
(`_transcript_idle_age_s` / `session_resolver._resolve_transcript_via_happy_log`)
for manually-tmux-launched, non-daemon-spawned sessions, so
`decide_idle_unmapped` hits `idle_age_s is None -> ("skip", missed)` and keeps
them forever regardless. The `idle=?` gap is the independently-confirmed,
actually-load-bearing reap blocker.

The load-bearing constraint (task body): of six detached unmapped tmux sessions
at diagnosis time, ONE was running an `experimenter` agent while detached, FOUR
had a typed-but-unsent user command queued, only ONE was genuinely done. A
false-positive reap kills a live experiment / a typed-but-unsent command / a
wrapper a user is about to re-attach to. The fix MUST tighten ONLY the
genuinely-dead case and must additionally gate on absence of running work.

### 3.5 Decision rule (which evidence selects a/b/c)

- Detached set EMPTY in-pass while tmux present → **(a)**: fix
  `_detached_tmux_pane_ttys` env-robustness; the loud-empty-set log is the
  permanent guard.
- Detached set NON-EMPTY, `_wrapper_controlling_tty_path(daemon_pid)` returns the

  the pass was correct at that instant (transient attach); no tty-path fix
  needed — the remediation is the `idle=?` fallback (§4.3), which would have
  reaped the session on a later detached tick once it is independently
  idle-confirmed.
- `_wrapper_controlling_tty_path(daemon_pid)` does NOT resolve to the pane pts
  but an ancestor/child's does → **(c)**: fix the pid-resolution in
  `_is_live_user_tty` / `_wrapper_controlling_tty_path` to walk the wrapper
  subtree/ancestry for the controlling pts.

**Instrumentation disposition:** LEAVE the once-per-pass detached-set-size log +
the loud empty-set WARNING in permanently (cheap, makes any future inert-pass

per-candidate tty-path trace is gated behind `EPM_IDLE_UNMAPPED_DEBUG` so it does
not spam every 10-min pass; default off after the diagnostic cycle.

## 4. Fix design (Phase 2)

A single coherent change that covers all three hypotheses on the detection side
plus the independently-confirmed `idle=?` reap-path gap.

### 4.1 `_detached_tmux_pane_ttys` env-robustness + observability (covers hypothesis a)

- Keep the existing fail-soft contract (any error → empty set → keep-all).
- Add: when `shutil.which("tmux") is not None` but the parsed detached set is
  EMPTY, log a loud WARNING to stderr ("idle-unmapped: tmux present but detached
  set empty — refinement inert this pass") — the silent-regression beacon.
- Robustness: the subprocess already inherits the process env. If §3 shows the
  cron run resolves a different/no tmux socket, pass an explicit env to the
  `subprocess.run` (preserve `$TMUX_TMPDIR` if set; otherwise rely on tmux's
  default `/tmp/tmux-<uid>` which the cron user shares). Do NOT hardcode a
  socket path — derive from the running user. This sub-change is conditional on
  §3 selecting (a); if §3 shows the set is already non-empty in-cron, this
  reduces to just the loud-empty-set log.

### 4.2 Pid-resolution (covers hypothesis c, only if §3 selects it)

If §3.4 shows the daemon-listed pid's controlling-tty path does not resolve to
the pane pts but a subtree/ancestry pid's does, extend
`_wrapper_controlling_tty_path` (or `_is_live_user_tty`) to test the wrapper's
ancestors (`_ancestor_pids`-style walk, capped depth) and immediate children for
a `/dev/pts/*` controlling tty, returning the first that cross-references the
detached set. Keep the keep-leaning default (unresolvable → treat as live).

### 4.3 `idle=?` corroborating idleness fallback (the load-bearing reap path)

The transcript happy-log path returns `(None, reason)` for manually-tmux-launched
sessions, so `decide_idle_unmapped` keeps them forever. Add a NARROW fallback
idleness signal used ONLY when the primary signal is unavailable AND every
no-running-work gate passes. New helper(s) + a threaded fallback through
`_process_idle_unmapped`; `decide_idle_unmapped` itself stays pure and unchanged
in shape (the fallback computes a substitute `idle_age_s` BEFORE the decision,
so the existing decision lattice + 2-miss accumulation + stop-verification all
apply unchanged).

The fallback `idle_age_s` is sourced from **tmux `session_activity`** of the
pane's owning tmux session — the epoch seconds of the last activity in that
session — via `tmux display-message -p -t <pane_tty> '#{session_activity}'` (or
a single `list-panes -a` extended format carrying `#{pane_tty}\t#{session_attached}\t#{session_activity}`,
folded into `_detached_tmux_pane_ttys` so it is one tmux call per pass).
`idle_age_s = now - session_activity`. (Note: `session_activity` updates on pane
OUTPUT, which for an idle Claude session that emits nothing is the right "no
turns since" signal; it does NOT update on the watcher's own reads. It is a
conservative OVER-estimate of liveness, never under — exactly the safe direction.)

The fallback is consulted ONLY when ALL FIVE gates hold (any single uncertain
signal → keep, i.e. fall back to the existing `("skip", missed)`):

1. **Detached** — the wrapper's controlling-tty path is in the now-trustworthy
   detached set (so `has_tty` is already False; the session reached the idle
   branch).
2. **Unmapped** — `issue is None` (already true to reach this pass branch).
3. **No running descendant *work* process** — NO codex companion
   (`codex app-server` / `plugins/cache/openai-codex/` cmdline, per
   `worktree_audit.py` `_ORPHAN_CMDLINE_PATTERNS`) AND no project-workload python
   under the wrapper subtree (a `/proc` descendant whose cmdline matches a
   running experiment/eval — e.g. `scripts/train.py` / `scripts/eval.py` /
   `scripts/run_sweep.py` / `scripts/dispatch_issue.py` / `backend_poll.py`).
   Implemented as a new `_has_running_work_descendant(pid, children_map)`
   reusing the existing `_proc_children_map` + `_cmdline_has_*` parse pattern.
   **Crucial:** the gate must NOT key on `_has_claude_descendant` — every idle
   session has a live Claude binary + the fixed MCP server tree (runpod / arxiv
   / ssh / google-workspace / playwright / context7 / todoist), which are NOT
   work signals (verified live against wrapper 2730037). The gate keys on the
   narrow work-process patterns only.
4. **Owns no running pod** — no RUNNING managed pod attributable to the session.
   Because these sessions are UNMAPPED (`issue is None`), there is no issue→pod
   key, so the conservative reading is: if there are ANY RUNNING managed pods at
   all (`_running_managed_issue_pods()` non-empty) whose issue cannot be tied to
   a DIFFERENT live mapped session, treat the work-ownership as uncertain → keep.
   Simpler + safe default: gate on `_running_managed_issue_pods()` returning an
   empty list (no managed RUNNING pods anywhere) before the fallback may fire;
   a `None` snapshot (API error) → keep. This is intentionally conservative —
   a single live pod anywhere defers the fallback — and matches the "any
   uncertain signal → keep" rule. (If §3/implementation finds a reliable
   session→pod attribution for unmapped sessions, the gate can narrow; absent
   that, the empty-RUNNING-set gate is the safe floor.)
5. **Corroborating idle age over a conservative threshold** — the
   `session_activity`-derived `idle_age_s` ≥ a NEW threshold
   `EPM_UNMAPPED_TMUX_IDLE_FALLBACK_S`, default **24h** (deliberately 2× the
   primary 12h window — the fallback is a weaker signal, so it earns a longer
   floor; see §11 for grounding). The standard ≥2-consecutive-miss accumulation
   then applies on top, exactly as the primary path.

If all five hold, the fallback supplies `idle_age_s` and the existing
`decide_idle_unmapped` lattice produces `keep`→`stop` over the 2-miss guard,
reusing the entire existing stop/verification/record machinery. If any gate is
uncertain, `idle_age_s` stays `None` → `("skip", missed)` (unchanged
fail-toward-keep, loud log).

### 4.4 Reap mechanism

The reap target is the **session/wrapper**, NOT a pod. It reuses the existing
`_stop_session(sid, dry_run)` path (a Happy-daemon stop RPC, ACK≠kill, with the
existing next-tick stop-verification + one-retry-then-alert in
`_check_idle_unmapped_stop_verification`). No new kill/tmux-kill mechanism is
introduced — stopping via the daemon is reversible (`spawn_session.py
spawn-issue`/`spawn-pm` respawns) and is what the pass already does for the
primary path. No `pod.py stop`/`terminate` is involved (the session owns no pod
by gate 4).

### 4.5 Why code, not a model call?

N/A — no unstructured-data heuristics. Every signal is a deterministic
`/proc`/tmux/daemon read; a model call would be non-deterministic, slower, and
wrong for a 10-min cron safety check.

## 11. Decision Rationale / Sources

- **`EPM_UNMAPPED_TMUX_IDLE_FALLBACK_S = 24h`** — *Why:* the fallback
  (`session_activity`) is a weaker corroborating signal than the primary
  transcript mtime, so it earns a longer floor; 2× the validated primary 12h
  window (`UNMAPPED_IDLE_REAP_S`) keeps an overnight pause well clear of any
  reap while still clearing the 19-43h accumulation class within ~a day.
  *Source:* the file's existing `UNMAPPED_IDLE_REAP_S = 12h` choice +
  `autonomous_session_watch.py` §9493-9498 rationale; the 2026-06-12 incident's
  19-43h idle range (CLAUDE.md § Crons). *Alternatives:* equal to 12h (rejected
  — too aggressive for a weaker signal); 48h (rejected — leaves the accumulation
  class billing RSS for two days).
