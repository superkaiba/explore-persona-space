### 3A. New gotchas.md entry (primary)

Insert as one bullet immediately after the `os.replace`-EXDEV staging entry (currently line 54 — **anchor by that entry's lead text, not line number**; #1512 may shift lines), closing the disk/staging cluster before the plotting entries begin. Exact text:

```
- **A between-phase incremental cache reap (`clean_experiment_downloads.py <N>
  --incremental --apply`) is legal ONLY strictly AFTER the cache's LAST
  consumer in the WHOLE run — "re-downloads on demand" is FALSE for
  direct-path readers.** The between-phase reap contract (CLAUDE.md § Disk
  hygiene) assumes a reaped `data/issue_<N>/hf_dl/**` / `g*_dl/**` cache
  re-downloads on demand; that holds only for hub-download code paths
  (`hf_hub_download` / `snapshot_download` re-fetch on a miss). A direct-path
  reader — a `parent.load_store(corpus_dir, ...)`-style `open()` on a cache
  path — implements no re-download and dies FileNotFoundError. Incident #1489
  (2026-07-18): `issue1489_dispatch.sh` reaped `data/issue_1489/hf_dl` between
  upload-a1 and P3, saving 0.05 GB with 88.5 GB free; P3 then read
  `hf_dl/corpus/prefix_store.jsonl` via a direct `open()` loader →
  FileNotFoundError, killing a run whose phase_a had just completed ~3.5 h of
  paid GPU phases. RULE: before placing ANY mid-run reap in a dispatcher,
  grep-enumerate every later `hf_dl`/`g*_dl` reader across the dispatcher +
  ALL phases (incl. later provisions, e.g. a phase_b re-provision); if any
  later consumer exists there is NO legal mid-run reap slot — let Step-8
  terminal cleanup own it (per-phase disk-headroom canaries already guard
  pressure; size the saving before placing the reap — 0.05 GB buys nothing).
  Defense in depth: guard each corpus-consuming phase entry with a
  re-stage-on-demand call through the SAME deterministic staging helper the
  earlier phases used, pinned to the SAME revision — never a bare `open()`
  on a reapable path. (#1489 crash-fix r6; mirror memory
  `feedback_incremental_reap_last_consumer.md`.)
```
