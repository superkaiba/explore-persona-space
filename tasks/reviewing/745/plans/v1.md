# Plan — issue #745: enable `hf_transfer` for experiment uploads

## 0. Plan Summary

**Change:** Declare `hf_transfer` as a first-class `pyproject.toml` dependency (so
`uv sync --locked` installs it on every pod/VM/GCE/SLURM worker) AND default
`HF_HUB_ENABLE_HF_TRANSFER=1` in the in-process env bootstrap
(`orchestrate/env.py`), the pod shell bootstrap (`bootstrap_pod.sh` step 6), the
GCP GCE startup-script passthrough, and the SLURM env-passthrough allowlist. The

wins. `hf_transfer` accelerates the SAME `upload_folder` / `upload_file` LFS
calls — orthogonal to the bulk-commit discipline and the quota-403 overflow path.

enough to take the LFS multipart path. It is a HARD FAULT, NOT a graceful
fallback. So the env default may only be turned on where the package is
guaranteed present — hence the dependency declaration is the primary fix and the
env default rides on it.

## 1. Goal

`hf_transfer` (the Rust multi-threaded chunked HF Hub transfer accelerator) is
neither installed nor enabled anywhere in the project, so every experiment upload
(raw completions, activation stores, checkpoints, datasets) runs on
`huggingface_hub`'s slow pure-Python single-stream uploader — #658's 36 GB pv-rb
activation upload crawled at ~2.5-6 MB/s on a ~26 Gbps pod link (GPU 0%, a
#664-class spend leak). Goal: make `hf_transfer` a guaranteed-present project
dependency and default `HF_HUB_ENABLE_HF_TRANSFER=1` across every worker
environment (VM, RunPod pod, GCE instance, SLURM compute node), while keeping the
flag overridable to `0` at launch time, so all uploads use the accelerated path
by default.

## 2. Prior Work

- **What `hf_transfer` is.** A Rust-backed package (`pip install hf_transfer`)
  that `huggingface_hub` uses for multipart parallel LFS uploads and chunked
  downloads when `HF_HUB_ENABLE_HF_TRANSFER=1`. It trades feature support
  (no progress bars, no upload-from-bytes/BinaryIO — falls back for those) for
  multi-threaded throughput that saturates a fast link.
- **API contract — env-var gated, HARD FAULT when missing (verified).** Read
  from the installed `huggingface_hub==0.36.2` source (`huggingface_hub/lfs.py`):
  `use_hf_transfer = constants.HF_HUB_ENABLE_HF_TRANSFER`; if enabled and the
  payload is a path/Path, the upload routes to `_upload_parts_hf_transfer`, which
  does `from hf_transfer import multipart_upload` inside a `try/except
  ImportError` that **re-raises as `ValueError`** ("Fast uploading using
  'hf_transfer' is enabled (HF_HUB_ENABLE_HF_TRANSFER=1) but 'hf_transfer'
  package is not available in your environment. Try `pip install hf_transfer`.").
  So the env flag WITHOUT the package crashes the upload — it is NOT a
  graceful-degrade. The graceful fallbacks that DO exist: (a) when the env flag
  is unset/`0`, the pure-Python `_upload_parts_iteratively` path runs (today's
  behavior, no crash); (b) when the payload is bytes/BinaryIO rather than a file
  path, `huggingface_hub` warns and falls back even with the flag on.
  Confirmed the package is currently ABSENT in the project venv
  (`ModuleNotFoundError: No module named 'hf_transfer'`).
- **`HF_HUB_ENABLE_HF_TRANSFER` semantics.** `1`/truthy = enable; `0`/unset =
  disable (`huggingface_hub.constants` reads it as a boolean env). Unset is the
  current state everywhere in the project (grep confirms it is absent from
  `pyproject.toml`/`uv.lock`/`scripts/`/`src/`).
- **In-project precedent.** `external/open-instruct/Dockerfile:66` sets
  `HF_HUB_ENABLE_HF_TRANSFER=1` and `external/open-instruct/uv.lock` pins
  `hf_transfer==0.1.9` — the open-instruct reference codebase already runs this
  exact configuration, a strong precedent for both the flag and the package
  being safe in this stack.
- **Project caveats.**
  - **#515 xet-CDN download interaction (2026-06-08):** a run was launched with
    `HF_XET_DISABLE=1 HF_HUB_ENABLE_HF_TRANSFER=0` to work around an HF xet CDN
    HTTP 416 stall during model DOWNLOAD. `hf_transfer` accelerates UPLOADS here,
    but the same env flag also affects downloads, so the on-by-default flag MUST
    stay overridable — an explicit `HF_HUB_ENABLE_HF_TRANSFER=0` at launch must
    cleanly disable it. This is why every default uses `setdefault` /
    append-if-absent, never an unconditional `export`.
  - **Quota-403 overflow path (`.claude/rules/upload-policy.md`, #541/#552/#564):**
    the LFS-quota 403 fires on the LFS endpoint regardless of transfer backend;
    `hf_transfer` is just a faster client for the SAME `upload_folder` /
    `upload_file` call, so it neither helps nor breaks the overflow routing
    (`EPM_HF_OVERFLOW_ROUTING`) — orthogonal.
  - **Bulk-commit discipline (#664):** `upload_folder` composes one commit per
    tree; `hf_transfer` accelerates the per-file LFS object transfers within that
    commit. No conflict.
- **Recent versions.** `hf_transfer` latest on PyPI is the `0.1.x` line (the
  pinned open-instruct lock is `0.1.9`, Jan 2025; current is `>=0.1.9`). Pure
  Rust wheels (`cp38-abi3` manylinux/musllinux + macOS), so it installs as a
  prebuilt wheel on the RunPod pytorch image, the dev VM, GCE instances, and
  DRAC compute nodes — no source build (contrast flash-attn). `(high confidence)`

## 4. Design

Four touched files, one canonical in-process home + belt-and-suspenders

### 4.1 `pyproject.toml` — declare the dependency (PRIMARY fix)

Add `hf_transfer` to `[project].dependencies` so `uv sync --locked` installs it
on every worker. This is the load-bearing change: it guarantees the package is
present everywhere the env flag could turn on, closing the hard-fault-when-missing
hole.

```toml
 dependencies = [
     "torch>=2.4,<3.0",
     ...
     "bitsandbytes==0.49.2",
+    "hf_transfer>=0.1.9,<1.0",  # Rust multi-threaded HF Hub upload/download accelerator;
+                                # gated on HF_HUB_ENABLE_HF_TRANSFER (defaulted on in env.py).
+                                # huggingface_hub HARD-FAULTS (ValueError) if the flag is set
+                                # but this package is absent, so it must be a hard dep (#745).
 ]
```

Then regenerate the lock: `uv lock` (commits `uv.lock` with the resolved
`hf_transfer` wheel set). The dev VM picks it up on the next `uv sync`; pods/GCE
nodes pick it up via their `uv sync --locked` in bootstrap.

### 4.2 `src/explore_persona_space/orchestrate/env.py` — in-process default (CANONICAL home)

`load_dotenv()` and `setup_worker()` already `os.environ.setdefault("HF_HOME",
_hf_home_default())`. Add the analogous line right after, so the flag default
applies uniformly to every entrypoint (VM dev box, RunPod pod, GCE startup
workload, SLURM compute node) through the one code path they all call —
independent of shell rc / lane passthrough. `setdefault` preserves any
caller-set value (including `=0`).

In `load_dotenv()`, after the `HF_HOME` setdefault (~line 230):

```python
    os.environ.setdefault("HF_HOME", _hf_home_default())
+   # Default the Rust multi-threaded HF Hub transfer accelerator ON for all
+   # uploads/downloads (#745). setdefault preserves an explicit caller value —
+   # a launch can still force HF_HUB_ENABLE_HF_TRANSFER=0 (the #515 xet-CDN
+   # download workaround). The package is a hard pyproject dependency, so the
+   # flag can never enable a missing-package hard fault.
+   os.environ.setdefault("HF_HUB_ENABLE_HF_TRANSFER", "1")
```

In `setup_worker()`, after its `HF_HOME` setdefault (~line 276), the SAME line
(worker subprocesses that call `setup_worker` but not `load_dotenv` first still
get the default; `setup_worker` then calls `load_dotenv` anyway, but the explicit
line keeps the two call sites symmetric and self-documenting):

```python
    os.environ.setdefault("HF_HOME", _hf_home_default())
+   os.environ.setdefault("HF_HUB_ENABLE_HF_TRANSFER", "1")  # #745, see load_dotenv()
    load_dotenv()
```

(One edit is sufficient for correctness since `setup_worker` calls `load_dotenv`;
adding both keeps the symmetry obvious and survives a future refactor that
reorders the calls. Implementer's call — if ruff/readability argues for one, the
`load_dotenv` site is the mandatory one.)

### 4.3 `scripts/bootstrap_pod.sh` step 6 — pod shell-env export (belt-and-suspenders)

Step 6 already appends cache-redirect exports idempotently to `/root/.bashrc`,
`/root/.profile`, and the project `.env`. Add `HF_HUB_ENABLE_HF_TRANSFER=1` to
the SAME three blocks so it is visible to:
- interactive/login pod shells (rc files), and
- dotenv-loading subprocesses (project `.env`).

This is belt-and-suspenders to §4.2: the in-process default already covers every
process that calls `load_dotenv`/`setup_worker`, but a raw `huggingface_hub` call
in a pod shell that bypasses the project env-bootstrap (a manual `hf upload`, an
ad-hoc `python -c`) still benefits. The non-login SSH-shell concern (the
documented uv-PATH gap) is ALREADY handled for the upload process because the
canonical upload path runs `uv run python` → `load_dotenv()` → the §4.2
in-process default; the `.env` write here is the additional safety net for
dotenv-loading subprocesses on the pod, and the rc write covers interactive
shells.

In the rc-file block (the `RCEOF` heredoc, ~line 334):

```bash
 # Pod-wide cache redirects (prevents /root disk-full crashes)
 export HF_HOME=/workspace/.cache/huggingface
 export WANDB_CACHE_DIR=/workspace/.cache/wandb
 export WANDB_DATA_DIR=/workspace/.cache/wandb
 export UV_CACHE_DIR=/workspace/.cache/uv
 export TRITON_CACHE_DIR=/workspace/.cache/triton
+# Fast multi-threaded HF Hub uploads/downloads (#745). hf_transfer is a hard
+# project dep so this never enables a missing-package fault. Override per-launch
+# with HF_HUB_ENABLE_HF_TRANSFER=0 (the #515 xet-CDN download workaround).
+export HF_HUB_ENABLE_HF_TRANSFER=1
```

In the project-`.env` block (the `ENVEOF` heredoc, ~line 353):

```bash
 # Cache redirects (added by bootstrap — prevents /root disk-full crashes)
 HF_HOME=/workspace/.cache/huggingface
 WANDB_CACHE_DIR=/workspace/.cache/wandb
 WANDB_DATA_DIR=/workspace/.cache/wandb
 UV_CACHE_DIR=/workspace/.cache/uv
 TRITON_CACHE_DIR=/workspace/.cache/triton
+# Fast multi-threaded HF Hub transfers (#745); override with =0 per-launch.
+HF_HUB_ENABLE_HF_TRANSFER=1
```

**Idempotency note:** the existing `grep -q "WANDB_CACHE_DIR=..."` guard gates
the WHOLE block, so adding the new line inside the same heredoc is idempotent on
re-bootstrap (it only writes when the block is absent). No new guard needed.
**Override caveat:** because the `.env` write is a STATIC line, a pod-side caller
that wants `=0` must export it in its own shell env (which supersedes the dotenv
value under `load_dotenv(override=False)` — dotenv does not overwrite an existing
`os.environ` key) rather than rely on editing `.env`. State this in the §4.3
comment. This matches how #515 actually did it (launch-time env, not `.env`
edit).

## 11. Decision Rationale

No ML hyperparameters (no model training). Design calls between the candidate
placements:

- **Candidate A (chosen, primary): declare `hf_transfer` in `pyproject.toml` +
  default the flag in `orchestrate/env.py` via `setdefault`.**
  - *Why:* `env.py` is the ONE code path every entrypoint calls
    (`load_dotenv`/`setup_worker`), so the default applies uniformly to VM,
    RunPod, GCE, and SLURM workers with a single edit — no per-lane drift. The
    `pyproject` dependency is mandatory because `huggingface_hub` 0.36.2
    hard-faults (`ValueError`) when the flag is set but the package is absent
    (verified from source) — so the flag can only be turned on where the package
    is guaranteed, and a hard dep is the only way to guarantee that across every
    lane. `setdefault` preserves the #515 `=0` launch override.
  - *Source:* this issue (verified against installed `huggingface_hub==0.36.2`
    source `lfs.py`); precedent `external/open-instruct/Dockerfile` +
    `uv.lock` (flag + `hf_transfer==0.1.9` already used in the reference stack);
    pattern mirrors the existing `HF_HOME` `setdefault` in `env.py`.

- **Candidate B (also applied, as belt-and-suspenders): shell-env export in
  `bootstrap_pod.sh` step 6 + lane passthrough allowlists.**
  - *Why ALSO applied, not instead:* the in-process default (A) covers every
    process that goes through the project env-bootstrap, but a raw
    `huggingface_hub` call in a pod shell that bypasses it (manual `hf upload`,
    ad-hoc `python -c` without `load_dotenv`) would miss the default. The shell
    rc + `.env` export (pod) and the GCE/SLURM passthrough (override channel)
    close that gap. Mirrors exactly how the existing `HF_HOME` / cache-redirect
    config is handled (both in-process AND in bootstrap step 6).
  - *Why NOT shell-only (B without A):* a shell-only export does NOT reach a
    non-login SSH shell unless the rc is sourced (the documented uv-PATH gap),
    and does NOT cover the GCE/SLURM workloads uniformly without per-lane
    `export` wiring; the in-process default is the robust home. Hence A is
    primary, B is the safety net.
  - *Source:* this issue (no prior precedent for this specific flag);
    placement pattern from `bootstrap_pod.sh` step 6 existing cache-redirect
    exports + `STARTUP_PASSTHROUGH_ENV_KEYS` / `PASSTHROUGH_ENV_KEYS` existing
    `EPM_HF_*` keys.

- **Lane passthrough = override channel, not default.** The GCE/SLURM allowlist
  entries forward a dispatch-process value (the `=0` override); they do NOT
  inject `=1` themselves. The `=1` default for those lanes comes from A
  (the workload runs `uv run python` → `load_dotenv`). This keeps the
  drop-when-absent contract of both allowlists intact.
  - *Source:* this issue; the existing `EPM_HF_OVERFLOW_ROUTING` passthrough is
    the exact same "dispatch-process opt-in reaches the remote workload" pattern.
