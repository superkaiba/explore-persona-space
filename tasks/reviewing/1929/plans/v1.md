## 3. File paths + concrete diffs

### 3.1 `.claude/rules/pod-side-reporting.md` — new item 1g (after 1f, before item 2)

Sketch (implementer refines wording/length to section register):

> 1g. **A RELAUNCH re-runs the original launcher FILE — never a
> hand-re-typed / reconstructed inline chain.** The launcher script is the
> carrier of the side duties a launch owes (pid-file rewrite — item 1; log
> rotation — 1b/1c; stdio detach — 1f; the completion-sentinel write the
> poller's done-verdict keys on): a from-memory `bash -c` reconstruction
> silently drops whichever duty the re-typer forgets (#1768 relaunch:
> the rebuilt chain dropped the completion-sentinel write; the handoff
> stranded ~5.8 h). If the original launch has no launcher file (an ad-hoc
> first launch), FIRST materialize the chain into a file (pod:
> `/workspace/logs/launch_issue_<N>_<slug>.sh`; VM: alongside the phase
> log), then relaunch by executing that file — the next relaunch then has a
> canonical source. Deliberate launcher EDITS before a relaunch are fine
> (fix the bug in the FILE, then run the file — cf. 1e's descope record
> when the recipe changes); the ban is on bypassing the file.

### 3.2 `.claude/rules/pod-side-reporting.md` — new item 1h (after 1g)

> 1h. **Pid breadcrumbs + completion watches key on the WORKER pid — never
> the setsid/nohup/ssh wrapper pid.** A wrapper exits within seconds of a
> healthy launch, so a watch keyed on it false-fires "EXITED" on a live run
> (#1769: the mt600 re-judge watch keyed on the setsid launcher pid and
> false-fired ~1 min in). Before writing any `pid=` breadcrumb or arming
> any liveness/completion watch, identity-verify the pid:
> `ps -p <pid> -o args=` must show the WORKLOAD's distinctive invocation —
> args reading as `setsid`/`nohup`/`ssh`/a bare wrapper shell mean you
> captured the wrapper. Re-derive the worker pid ONLY via item 1d's
> sanctioned anchored forms (the launcher's pre-exec `echo $$`; `$!` of the
> setsid-exec'd unit; the parent-scoped child-walk `pgrep -P <captured
> wrapper pid>`) — never an unanchored pgrep (1d's ban is unchanged).

### 3.3 `.claude/rules/pod-side-reporting.md` § Result-push verification contract — new bullet (after the #1325 artifact-presence assert)

> - **Named expected-path set — an empty-set verify is vacuous (#1482).**
>   Every push-verify / upload-verify leg states the expected path set it
>   checks (print the resolved list, or the manifest path + count, into the
>   phase log before verifying). An EMPTY resolved set on a round whose
>   plan/§6.5 `primary_deliverable` or output manifest declares git-destined
>   outputs is a verify FAILURE — exit non-zero naming the empty set — never
>   a pass (#1482: a vacuous push-verify passed while 29 git-bound eval
>   files sat uncommitted). A round with genuinely no git-destined outputs
>   (the #1325 scoping-(b) case) may no-op, but the no-op is STATED in the
>   log ("push-verify: no git-destined outputs declared this round"), never
>   silent.

### 3.4 `.claude/skills/issue/SKILL.md` § Detached VM-side long compute phases — pointer

≤3 sentences appended near the launch template / relaunch prose, e.g.:

> Relaunches of a detached phase follow the pod-side-reporting launch

> launcher FILE (never a re-typed chain), and key every `pid=` breadcrumb /
