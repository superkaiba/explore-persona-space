# Plan v3 — #750: gate `_eps_phase done` on kernel OOM-detection (GCP backend)

> **v2 → v3 delta (per-lens reconciled REVISE × 3 + consistency WARN).** The v2
> guard read `/sys/fs/cgroup/memory.events` — the unified-hierarchy MOUNT ROOT,
> which (kernel cgroup-v2 docs + empirical check on this host) does NOT expose
> `memory.events`, so the "kernel-authoritative" primary mechanism was
> structurally inert (its `[ -r "$f" ]` always false → silent fall-through to
> the journal). v3: (1) derive the workload's OWN cgroup dir from
> `/proc/self/cgroup` and read `$CGROUP_DIR/memory.events.local`; (2) capture a
> pre-workload `oom_kill` baseline and fire only on a post-workload INCREASE
> (eliminates the cumulative-counter + recovered-child-OOM false-positive class
> AND scopes detection to the workload's lifetime); (3) make the journalctl
> fallback fail-CLOSED (unscoped system-wide grep dropped); (4) fix the fixture
> provenance key name (`provenance`, not `header`).

## 0. Plan Summary

**Change:** add a kernel-authoritative OOM guard to the GCP startup-script
success path so an OOM-killed workload that the bash chain rc-survived can never
publish `_eps_phase done`. **Files:** `src/explore_persona_space/backends/gcp.py`
(the success-path `parts` list inside `render_startup_script`) +
`tests/test_gcp_backend.py` (new guard tests) + a DELIBERATE regeneration of
`tests/fixtures/issue588_gcp_startup_hydra_only.json` (the byte-identity
snapshot the change necessarily perturbs). **Mechanism:** the guard derives the
workload's OWN cgroup directory from `/proc/self/cgroup` (the cgroup-v2 `0::`
unified-hierarchy line — the root `/sys/fs/cgroup` does NOT expose
`memory.events`) and reads `$CGROUP_DIR/memory.events.local`'s `oom_kill`
integer. Because that counter is cumulative-since-cgroup-creation, the guard is
DIFFERENTIAL: capture `EPS_OOM_BASELINE` from `memory.events.local` BEFORE the
workload runs, then re-read `EPS_OOM_FINAL` after `*workload_block`, and route
through the EXIT trap (`exit 137`) only when `EPS_OOM_FINAL > EPS_OOM_BASELINE`.
The journalctl path is fail-CLOSED (returns "no OOM" when it cannot scope to
this unit) — after the `/proc/self/cgroup`-derived + differential read the
cgroup leg is the sole correctly-scoped signal. `exit 137` (SIGKILL rc) routes
through the existing EXIT trap's `rc != 0` branch (`_eps_phase failed` +
`_eps_persist_diagnostics` + `shutdown`). **Compute:** none —
`Estimated GPU-hours (total): 0`. Pure renderer string edit + unit tests; no
pod, no model, no data. **Scope:** workflow-surface infra only; the optional
primary-deliverable-existence check is DEFERRED to a follow-up. **Top risk:**
the byte-identity snapshot test fails by construction — the fixture MUST be
regenerated with documented provenance written into its top-level `provenance`
block (not a code-bug, an expected-drift pin).

## 1. Goal

Verbatim from the task body:

> Harden the GCP backend's startup-script success path so `_eps_phase done`
> is never published when the workload bash chain rc-survived an OOM-kill or
> other SIGKILL — gate the explicit `_eps_phase done` on a positive
> workload-rc check (cgroup `memory.events.oom_kill` counter == 0, AND the
> planner-named primary deliverable paths actually exist) so an OOM'd run
> routes via the EXIT trap's `phase=failed` branch.

Scope note: the cgroup-OOM half of the Goal is implemented now; the
"primary deliverable paths actually exist" half is deferred to a follow-up
(see §4.6 "Deferred — optional secondary defense" and §7). Note on the Goal's
parenthetical "`memory.events.oom_kill` counter == 0": the literal "== 0" test
is correct ONLY against a cgroup created fresh for this workload; because the
guest-startup cgroup (`/system.slice/google-startup-scripts.service`) is NOT
guaranteed fresh and the counter is cumulative, v3 implements the Goal's INTENT
("the workload did not OOM") via a pre/post DIFFERENCE rather than an absolute
`== 0` — see §4.2 + Must-Fix 2 rationale.

## 2. Prior work / context

- The GCP startup script is a bash string rendered by `render_startup_script`
  (`gcp.py:896`). It runs under `set -euo pipefail` (`gcp.py:1128`). The
  `_eps_phase()` guest-attribute publisher is defined at `gcp.py:1166-1189`.
- **The EXIT trap (#607 hardening, `gcp.py:1353-1365`)** is installed at the
  TOP of the `parts` list, BEFORE the workload runs:
  ```bash
  trap 'rc=$?; set +e;
   if [ "$rc" -ne 0 ]; then
   { echo "[startup-script] FAILED rc=$rc — powering off to bound billing"; } 2>/dev/null || true;
   _eps_phase failed;
   if [ -n "${EPS_LOG_PATH:-}" ]; then { tail -n 40 "$EPS_LOG_PATH" 2>/dev/null | cut -c1-2000 >&3; } 2>/dev/null || true; fi;
   _eps_persist_diagnostics "$rc";
   shutdown -h now; fi' EXIT
  ```
  It captures `rc=$?` first, then `set +e` (so non-zero diagnostic commands
  don't abort the trap body), then runs the failure branch ONLY when
  `[ "$rc" -ne 0 ]`. `exit 137` (SIGKILL exit code, a normal non-zero rc)
  fires this branch and runs the full failure teardown — exactly the path an
  OOM'd run should have taken.
- **The async-poller failover predicate** `GcpBackend.poll` /
  `backend_poll._is_gcp_async_workload_failure` (#658/#659) is gated on
  `current_phase == "terminal_workload_failed"` — derived from
  `eps/phase==failed` + the write-once `eps/workload_started` sentinel. A
  `phase=done` posted on a failed workload (the #744 bug) bypasses this
  predicate entirely: the only downstream signal of failure becomes the
  absence of artifacts at upload-verification, which is too late (#744
  advanced to `status:verifying` with zero usable artifacts).
- **#744 evidence (from the task body):** on `eps-issue-744` (`g2-standard-4`
  / 1× L4, ~16 GB host RAM), Phase-1 `dump_and_stream.py` (pid 1553) was
  OOM-killed at `broader pass1 7350/7389` (2026-06-30T04:34:12Z); systemd
  logged `google-startup-scripts.service: Failed with result 'oom-kill'`; yet
  2s later the workload log shows `[phase=done]` and the completion sentinel
  + `eps/phase=done` guest attribute were both written. The bash chain
  (`bash X && bash Y`) returned rc=0 to the parent despite `set -euo
  pipefail` and a SIGKILLed child — the exact rc-propagation mechanism is NOT
  pinned and is OUT OF SCOPE (see §7); the kernel cgroup signal is
  independent of the chain's rc, so this fix lands regardless. Crucially, the
  #744 OOM trace places the workload in
  `/system.slice/google-startup-scripts.service` — a DESCENDANT cgroup, NOT
  the unified-hierarchy root — which is precisely why a root-`/sys/fs/cgroup`
  read (the v2 bug) never sees the `oom_kill` and a `/proc/self/cgroup`-derived
  read does.
- **cgroup-v2 path fact (the v2 defect; empirically reconfirmed for v3).** The
  kernel cgroup-v2 documentation
  (https://docs.kernel.org/admin-guide/cgroup-v2.html) defines `memory.events`
  as "A read-only flat-keyed file which exists on **non-root** cgroups." The
  unified-hierarchy ROOT at `/sys/fs/cgroup` does NOT expose it. Empirically on
  a live cgroup-v2 host (this VM, 2026-06-29):
  ```
  $ cat /sys/fs/cgroup/memory.events
  cat: /sys/fs/cgroup/memory.events: No such file or directory
  $ cat /proc/self/cgroup
  0::/user.slice/user-1001.slice/session-2954.scope
  $ cat /sys/fs/cgroup/user.slice/user-1001.slice/session-2954.scope/memory.events.local
  low 0
  high 0
  max 0
  oom 0
  oom_kill 2
  oom_group_kill 0
  ```
  So the workload's OWN cgroup (resolved from `/proc/self/cgroup`'s `0::` line)
  carries the `oom_kill <N>` line; the root does not. The v2 guard's
  `[ -r "$f" ]` returned false at the root and silently fell through to the
  journal fallback — the "kernel-authoritative" primary mechanism never ran.

## 4. Design — the concrete patch

### 4.0 Where in the renderer the diff lands

`render_startup_script` builds the workload section in two branches
(`gcp.py:1042-1121`, assigned to `workload_block`), then assembles the final
`parts` list (`gcp.py:1126-1517`). NOTE (load-bearing, confirmed by reading the
code): `_eps_phase workload` + the actual workload command live INSIDE each
`workload_block` (lines 1091 and 1119), NOT in the shared `parts` list. So
there is NO `parts`-list span "between `_eps_phase workload` and
`*workload_block`" — Must-Fix 2's intent (baseline captured BEFORE the workload
runs) is honored by placing the baseline-capture entry in the `parts` list
IMMEDIATELY BEFORE `*workload_block` (current `gcp.py:1495`), which renders
before either branch's `_eps_phase workload` + workload command.

The diff lands as **new entries in the `parts` list**, which render as bash
lines in the final script body. THREE distinct render targets:

1. **The `_eps_oom_count()` helper definition** — added to the script PREAMBLE,
   alongside the other helper-function definitions (`_eps_phase()` at
   `gcp.py:1166`, `_eps_persist_diagnostics()` at `gcp.py:1209`,
   `_eps_reachability_watchdog()` at `gcp.py:1289`). Insert it immediately AFTER
   the `_eps_reachability_watchdog() { ... }` block closes (current
   `gcp.py:1328`, the `"}"` entry) and BEFORE the EXIT-trap entry (current
   `gcp.py:1353`). It is defined under `set -euo pipefail`, so its body must be
   `set -e`-safe (it is — see 4.2).

2. **The pre-workload baseline capture** — a single `parts` entry inserted
   IMMEDIATELY BEFORE `*workload_block` (current `gcp.py:1495`), so it runs
   before the workload starts: `EPS_OOM_BASELINE="$(_eps_oom_count)"`.

3. **The guard call site (post-workload diff)** — `parts` entries inserted
   between `*workload_block` (current `gcp.py:1495`) and the watchdog reaper
   (current `gcp.py:1501`): re-read `EPS_OOM_FINAL="$(_eps_oom_count)"` and
   `exit 137` when `EPS_OOM_FINAL > EPS_OOM_BASELINE`.

### 4.1 Insertion point for the guard call (chosen: BEFORE the watchdog reaper)

The current success path renders, in order (the `parts` list, `gcp.py`):

```
1494   ...                                                   # (uv sync / HF cache / sentinel dir, etc.)
1495   *workload_block,                                      # workload ran (incl. detached-pid wait for workload_cmd)
1496   "",
1501   '{ kill "${EPS_WATCHDOG_PID:-}" 2>/dev/null; } || true',   # reachability-watchdog reaper (#669)
1502   "",
1503   "# === Completion sentinel (workload exited cleanly) ===",
1506   "cat > <sentinel_abs> <<EOF { \"phase\":\"done\", ... } EOF",     # sentinel heredoc
1515   "_eps_phase done",
```

- **Baseline** goes immediately BEFORE `*workload_block` (between current 1494
  and 1495).
- **Guard (diff)** goes between `*workload_block` (1495) and the watchdog reaper
  (1501).

Chosen over "between the reaper and the sentinel write" for two reasons:

- **Uniform teardown.** Putting the guard BEFORE the reaper means an OOM'd run
  does `exit 137` while `EPS_WATCHDOG_PID` is still live; the EXIT trap's
  `shutdown -h now` then reaps the watchdog along with everything else (the
  reachability watchdog's own `shutdown` ladder and the trap's `shutdown` are
  idempotent — a VM only powers off once). The clean-exit reaper at 1501 exists
  specifically so a HEALTHY teardown does not let the daemon fire a spurious
  reachability shutdown; on the `exit 137` path we WANT the trap to own
  teardown, so we deliberately skip the clean reaper.
- **Earliest correct point.** By the time control reaches 1495, the workload has
  fully completed — including, on the `workload_cmd` branch, the detached-pid
  wait loop (`gcp.py:1106-1112`) that blocks until any self-daemonized driver
  pid exits. So the post-workload `EPS_OOM_FINAL` read reflects the ENTIRE
  workload's lifetime. Reading it here is both correct and the soonest we can
  refuse to publish `done`.

Note the baseline + guard are in the SHARED success path (the baseline before,
and the guard after, the branch-specific `workload_block`), so they protect BOTH
the `workload_cmd` branch (the #744 shape: `bash X && bash Y`) and the hydra
`uv run python scripts/train.py` branch with one pair of insertions.

### 4.2 The `_eps_oom_count()` helper + baseline + diff — exact rendered bash

The helper returns the workload's OWN cgroup `oom_kill` integer (the LOCAL
counter, scoped to this cgroup, NOT its descendants), `0` if it cannot read it.
A pre-workload baseline + a post-workload re-read + a numeric `-gt` comparison
make detection differential and lifetime-scoped — eliminating the cumulative
false-positive class entirely.

Rendered as `parts` entries appended to the helper-definition region of `parts`
(after the watchdog `"}"` at `gcp.py:1328`, before the trap at `gcp.py:1353`):

```python
        # === OOM-detection helper (#750, incident #744) ===
        # The bash chain's rc-propagation has known weakness modes under
        # ``set -e`` + ``&&`` + SIGKILL: on eps-issue-744 a workload python
        # OOM-killed by the kernel (systemd: "Failed with result 'oom-kill'")
        # still returned rc=0 to the parent startup-script, so the success
        # path published ``_eps_phase done`` 2s after the kill and the run
        # advanced to verifying with zero usable artifacts. The kernel's
        # cgroup-v2 ``memory.events.local`` ``oom_kill`` counter is incremented
        # whenever an OOM-killer hit THIS cgroup (``.local`` = this cgroup only,
        # NOT a hierarchical aggregation of descendants), REGARDLESS of what rc
        # the bash chain reported — an authoritative cross-check the chain
        # cannot mask.
        #
        # PATH DERIVATION (the #750 v2 defect this fixes): ``memory.events`` /
        # ``memory.events.local`` exist on NON-ROOT cgroups only (kernel
        # cgroup-v2 docs, https://docs.kernel.org/admin-guide/cgroup-v2.html);
        # the unified-hierarchy ROOT ``/sys/fs/cgroup`` does NOT expose them
        # (empirically: ``cat /sys/fs/cgroup/memory.events`` -> ENOENT). The
        # workload's OWN cgroup dir is the ``0::`` unified-hierarchy line of
        # ``/proc/self/cgroup`` (format ``0::/system.slice/...``), prefixed by
        # the mount root: CGROUP_DIR=/sys/fs/cgroup$(that path). The #744
        # workload sat in ``/system.slice/google-startup-scripts.service`` — a
        # descendant — so only the derived path sees its oom_kill.
        #
        # COUNTER SEMANTICS: ``oom_kill`` is cumulative-since-cgroup-creation,
        # so an absolute "== 0" test can false-fire on a non-fresh cgroup; the
        # caller therefore reads a BASELINE before the workload and a FINAL
        # after, and fires only on an INCREASE (see the baseline + guard
        # entries below). This helper just emits the current integer.
        #
        # The helper runs under ``set -euo pipefail``; every line is
        # ``set -e``-safe — the ``awk`` runs only inside an ``if [ -r ... ]``
        # condition-guarded ``&&`` whose result is captured by an assignment,
        # and the function always reaches an explicit ``echo``/``return``.
        "_eps_oom_count() {",
        # 0:: line of /proc/self/cgroup = the cgroup-v2 unified-hierarchy path
        # for this process. ${x#0::} strips the literal prefix; a host with no
        # 0:: line yields an empty suffix -> _dir=/sys/fs/cgroup (root), whose
        # memory.events.local is absent -> the [ -r ] guard fails -> echo 0.
        '  local _rel _dir _n=0',
        "  _rel=\"$(awk -F: '$1==\"0\"{print $3; exit}' /proc/self/cgroup 2>/dev/null || true)\"",
        '  _dir="/sys/fs/cgroup${_rel}"',
        # Read the LOCAL counter (this cgroup only). awk pulls just the integer
        # value of the oom_kill line; missing line / unreadable file -> _n stays
        # 0. The assignment consumes awk's exit status, so set -e never fires.
        '  if [ -r "$_dir/memory.events.local" ]; then',
        "    _n=\"$(awk '$1==\"oom_kill\"{print $2; exit}'"
        ' "$_dir/memory.events.local" 2>/dev/null || true)"',
        "  fi",
        # Normalize a non-numeric / empty read (e.g. awk printed nothing) to 0
        # so the caller's numeric -gt comparison is always well-formed.
        '  case "$_n" in (*[!0-9]*|"") _n=0 ;; esac',
        '  echo "$_n"',
        "}",
```

Then the **baseline capture** (a single `parts` entry inserted IMMEDIATELY
BEFORE `*workload_block` at `gcp.py:1495`):

```python
        # === OOM baseline (#750): record this cgroup's oom_kill count BEFORE
        # the workload runs, so the post-workload guard can fire on an INCREASE
        # rather than an absolute count (the counter is cumulative-since-cgroup-
        # creation; the guest-startup cgroup is not guaranteed fresh).
        'EPS_OOM_BASELINE="$(_eps_oom_count)"',
```

Then the **guard (post-workload diff)** (inserted between `*workload_block` at
`gcp.py:1495` and the watchdog reaper at `gcp.py:1501`):

```python
        *workload_block,
        "",
        # === Refuse to publish done on a kernel OOM the chain rc-survived ===
        # (#750, incident #744). Re-read the cgroup-local oom_kill count and
        # compare to the pre-workload baseline; a STRICT INCREASE means an OOM
        # hit this cgroup during the workload. exit 137 (SIGKILL rc) routes
        # through the EXIT trap's rc!=0 branch -> _eps_phase failed +
        # _eps_persist_diagnostics + shutdown, so the poll reads
        # terminal_workload_failed and the async GCP->RunPod failover (#659) can
        # fire, instead of a false phase=done masking a complete failure. The
        # watchdog (still live here) is reaped by the EXIT trap's shutdown, not
        # the clean reaper below -- on the failure path the trap owns teardown.
        'EPS_OOM_FINAL="$(_eps_oom_count)"',
        'if [ "${EPS_OOM_FINAL:-0}" -gt "${EPS_OOM_BASELINE:-0}" ]; then',
        '  { echo "[startup-script] OOM-kill detected in cgroup'
        ' (oom_kill ${EPS_OOM_BASELINE:-0} -> ${EPS_OOM_FINAL:-0}) despite rc=0'
        ' — routing to failed (#750)" >&3; } 2>/dev/null || true',
        "  exit 137",
        "fi",
        "",
        '{ kill "${EPS_WATCHDOG_PID:-}" 2>/dev/null; } || true',
        ...
```

`set -e` safety, line by line:
- `_eps_oom_count` body: the only failing-command contexts are the two
  `$(awk ... 2>/dev/null || true)` command substitutions (each `|| true` so the
  substitution never returns non-zero to the assignment), the `if [ -r ... ]`
  condition (a test, consumed by `if`), the `case` (control construct), and the
  final `echo`/closing `}`. No bare simple command can abort.
- `EPS_OOM_BASELINE="$(_eps_oom_count)"` / `EPS_OOM_FINAL="$(_eps_oom_count)"` —
  assignment from a command substitution; the helper always exits 0 (its last
  command is `echo`), so `set -e` never fires.
- `if [ "${EPS_OOM_FINAL:-0}" -gt "${EPS_OOM_BASELINE:-0}" ]; then ... fi` — the
  `[ -gt ]` test is in a condition context; `${X:-0}` defaults a never-set
  variable (defensive) so `set -u` cannot fire either. The numeric comparison is
  well-formed because the helper's `case` normalizes any non-numeric read to 0.
- The fd-3 echo is `{ ...; } 2>/dev/null || true`-guarded exactly like every
  other fd-3 heartbeat in the script (closed-pipe-safe under the `trap ':' PIPE`
  handler at `gcp.py:1150`). `exit 137` then deterministically fires the EXIT
  trap.

`bash -n` must pass on both rendered branches (the existing
`test_render_startup_script_is_valid_bash` covers this — see §6).

### 4.3 The journalctl fallback policy — FAIL-CLOSED (chosen)

The v2 fallback `journalctl -k --since "10 min ago" | grep -q "Out of memory:
Killed process"` matched ANY kernel OOM line system-wide in the last 10 minutes
— the same unscoped alternative-explanation failure as the v2 cgroup-root read
(a sibling process / a different unit's OOM would false-fire). Must-Fix 3 offers
two fixes; v3 chooses the FAIL-CLOSED option (the simpler, and the preferred
fallback per the Must-Fix wording):

- **The journalctl fallback is REMOVED entirely.** After the
  `/proc/self/cgroup`-derived + differential cgroup read (§4.2), the cgroup leg
  is correctly scoped to the workload's own cgroup AND lifetime — it is the sole
  signal. The original journal fallback existed to cover legacy cgroup-v1 hosts;
  the kernel docs (and the #744 evidence: `task_memcg=` + systemd
  `Failed with result 'oom-kill'` are both v2-shape) place v1 out of scope, so
  its value-add is marginal and its unscoped form is a net liability.
- **Fail-closed behavior is structural, not a separate branch.** When the
  workload's cgroup cannot be resolved or its `memory.events.local` is
  unreadable (a non-v2 / hybrid host), `_eps_oom_count` returns `0` for BOTH
  the baseline and the final read → `0 -gt 0` is false → the guard does NOT fire
  → the PRE-change behavior is preserved (the run proceeds to `_eps_phase done`
  exactly as today). So on any host where the cgroup signal is unavailable, the
  guard is a no-op, never a false-FAIL — i.e. it "fails closed" to the
  pre-change path with zero added risk. This is strictly no worse than today on
  a v1/hybrid host and strictly better on the v2 host that actually produced
  #744.

Why FAIL-CLOSED over the journalctl-`--unit`-scoping option: scoping the journal
to `google-startup-scripts.service` would require verifying the systemd journal
carries `_SYSTEMD_UNIT` on `-k` (kernel) OOM messages (kernel OOM lines are
emitted by the kernel, not by the unit, so the unit attribution is not
guaranteed on `-k`), AND would add a second code path + its own tests for
marginal coverage of an out-of-scope host class. The differential cgroup read
already gives a correctly-scoped, kernel-authoritative signal on the target host;
adding a fragile, partially-attributed journal path would expand the test surface
without closing a real gap. (Justification for the §7 record.)

### 4.6 Deferred — optional secondary defense (NOT in v3)

The body's optional primary-deliverable-existence check (verify that
`handle.extra.expected_artifacts.git_paths` contain at least one file before
publishing `done`) is DEFERRED to a follow-up and is explicitly NOT implemented
here. Reasons:

- The cgroup `oom_kill` differential is the kernel-authoritative signal for the
  #744 failure class and is minimal + self-contained.
- The artifact check is downstream of (a) variance in what each workload
  declares as expected artifacts (the renderer does not today receive a reliable
  per-issue expected-artifact manifest at script-render time) and (b) the
  existing `confirm_artifacts` mechanical gate at finalize time, which already
  catches a wholly-missing primary deliverable downstream.
- Adding it now expands the test surface and couples the renderer to a manifest
  contract that is out of scope for a minimal OOM fix.

If a non-OOM silent-failure recurrence is observed, file a separate workflow-fix
child for the artifact-existence guard.

| Risk | Likelihood | Mitigation |
|---|---|---|
| **Byte-identity snapshot test fails** | Certain (by construction) | EXPECTED. The #607/#658 structural tests + the new #750 guard tests keep the snapshot non-tautological. Not a code bug. |
| **Happy-path wall-time regression** | Negligible | The guard on the no-OOM path is one baseline call + one final call to `_eps_oom_count` (a single `awk` over `/proc/self/cgroup` — a few lines — and a single `awk` over `memory.events.local` — a few lines) plus one numeric `[ -gt ]` test. ~1 ms of file I/O on a v2 host; on a non-v2 host the `[ -r ]` guard short-circuits to `echo 0` with no `awk` over the missing file. Adds no measurable wall-time. ✓ |
| **Non-v2 / hybrid / v1 host (no `memory.events.local` at the derived path)** | Low | The #744 host was on cgroup v2 (kernel OOM trace `task_memcg=/system.slice/google-startup-scripts.service` and systemd `Failed with result 'oom-kill'` are both v2-shape evidence; the failing host is the target host). On a non-v2/hybrid host the derived path's `memory.events.local` is unreadable → `_eps_oom_count` returns `0` for BOTH baseline and final → `0 -gt 0` is false → the guard is a NO-OP and the PRE-change behavior is preserved (strictly no worse than today). | **`exit 137` mis-handled by the EXIT trap** | None | The trap captures `rc=$?` (= 137), runs `set +e`, and the `[ "$rc" -ne 0 ]` guard is TRUE for 137 → full failure teardown fires (`_eps_phase failed` + `_eps_persist_diagnostics 137` + `shutdown -h now`). 137 is an ordinary non-zero rc; nothing in the trap special-cases it. The poll then reads `eps/phase=failed` + the write-once `eps/workload_started` sentinel → `terminal_workload_failed` → async GCP→RunPod failover can fire. |

| **A descendant-process OOM the workload spawned and recovered from trips the guard** | Eliminated (no longer a risk) | v3 reads `memory.events.local` (LOCAL to the startup-script's own cgroup, NOT a hierarchical aggregation of descendant cgroups) AND fires only on a pre/post INCREASE within the workload's own lifetime.
