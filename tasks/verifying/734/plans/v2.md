## 1. Goal

Determine why the ` ※` marker implant *appeared* not to install on
Qwen-2.5-7B-Instruct in #664 (reported on-policy source `log P(※)` trained − base
= −0.34 to +1.81 nat, never the 5–12-nat band), discriminating (H1) genuine
model resistance, (H2) under-set lr/step dose, and (H3) a band-stop /
measurement / slot-wiring artifact — and produce a marker read (and, if needed, a
recipe) that demonstrably puts the Instruct marker install in the [5, 12]-nat band
on-policy. The marker is program #660 Phase-2's designated headline near→far gate,
so an answer (and a corrected read) unblocks that dead spine.

## 2. Prior Work

**Decisive planning-stage finding (verified against #664 artifacts on HF, this
plan):** the marker DID install on Instruct. Every one of the 20 #664 marker
cells band-stopped IN-BAND on the in-loop teacher-forced source read
(`band_stop_result.json`, `stopped_in_band: true`):

| dose | in-loop source `log P(※)` trained − base | band target | stop step |
|---|---|---|---|
| d1 (8 cells) | +5.59 … +7.14 nat | [5, 12] | 20–25 |
| d2 (8 cells) | +10.15 … +12.32 nat | [10, 16] | 35–50 |
| seed-1042 d1 (4 cells) | +5.71 … +6.96 nat | [5, 12] | 25 |

So **the band-stop callback fired correctly and the install reached its target on
all 16+4 cells** — directly contradicting #664's body framing ("band-stop never
fired, training ran to the 3-epoch ceiling"). That framing is factually wrong and
this experiment must correct it.

The "no install" came from the DOWNSTREAM on-policy read
(`issue664_leakage_fleet/marker_slot/<cell>/marker_slot_stats.json`). For the same
four contrastive-d1-seed42 cells the on-policy source read is:

| source | on-policy src `delta_logp` | base `log P(※)` | base `z_eos` | base `z_marker` | trained argmax |
|---|---|---|---|---|---|
| librarian | +0.39 | −37.3 | 10.8 | 1.7 | 198 (`\n`) |
| surgeon | +0.41 | −36.7 | 11.4 | 1.6 | 198 |
| programmer | +0.23 | −37.6 | 12.4 | 1.6 | 198 |
| default | −0.06 | −37.2 | 12.8 | 1.3 | 198 |

Two tells the slot is mis-rooted, not the install missing:
1. The on-policy base `log P(※) ≈ −37 nat` is **~18 nat below the documented base
   prior at the install slot** (`marker-training-recipe.md`: floor ≈ −19 to −22
   nat). A slot ~18 nat further from the marker than the install slot is not the
   install slot.
2. At the on-policy slot, base `z_eos ≈ 11–13` swamps base `z_marker ≈ 1.6`, and
   the argmax is the newline (id 198). The read sits at a position AFTER the
   response's turn-end `<|im_end|>` — the model has already ended the turn, so
   the marker has no business being argmax there.

**Root-cause localization (code read, this plan):** the two reads root the slot
differently.
- **In-loop (correct):** `build_source_probe_from_data` (`src/explore_persona_space/train/sft.py`
  L843) renders `apply_chat_template(prompt + completion, add_generation_prompt=False)`,
  finds the marker SUBSEQUENCE in the fused token ids, and reads
  `logits[i, marker_start − 1, marker_id]` — the marker's own trained slot,
  INSIDE the completion, before the turn-end.
- **On-policy (mis-rooted):** `_marker_slots._contexts_for_read`
  (`scripts/issue664_extract_store.py` L583) builds the context by
  `tokenizer.decode(prompt_ids + response_ids, skip_special_tokens=False)` →
  re-tokenize (`compute_marker_slot_stats` does `tok.encode(c,
  add_special_tokens=False)`) → append ` ※` → read the slot at position −1. Two
  defects compound: (a) the model's own R already ENDS with `<|im_end|>\n`, so the
  appended marker lands AFTER the turn-end (the `z_eos≈12`, argmax=`\n` slot we
  observe); the `_contexts_for_read` strip-loop only strips a literal trailing
  ` ※`, not the `<|im_end|>\n` tail; (b) the decode→re-encode round-trip is not
  token-identical to the trained fused render.

**Anchors that installed cleanly on the SAME model family (Qwen-2.5-7B-Instruct,
not base):** #601 (marker on Instruct, lr 1e-5, rsLoRA r32/α64 all-linear; clean
+7 to +17 nat install, STEPS the lever) and #650 (marker on Instruct, lr 5e-6,
rsLoRA r1 MLP; band-stop dose dial worked, 5.4 nat low / 16 nat high). #474 (base
Qwen-2.5-7B, epoch-1 band-stop). NOTE the #664 body's claim that base is the
install-confirmed model and Instruct the resistant one is undercut by #601/#650
both installing on Instruct — another reason H3 (measurement), not H1 (model), is
the leading hypothesis.

**Recipe rules:** lr is the over/under dial (`≥1e-4` → unconditional repeater,
clean window `≤5e-6`, strength via steps); marker + end-of-turn loss; on-policy
DV at the marker's OWN trained slot, three spaces, four-float storage; the
#432→#456 incident (off-slot/teacher-forced reads diverge arbitrarily from the
behavior — exactly the failure class here).

## 3. Hypothesis

- **H3 (PRIMARY, near-confirmed at planning):** The #664 "no install" is a
  measurement / slot-wiring artifact. The marker installed (in-loop band-stop
  in-band on all 20 cells); the on-policy `marker_slot` read is rooted at a slot
  AFTER the response's `<|im_end|>` and uses a lossy decode→re-encode, so it reads
  near the base prior of a wrong slot. **Confirm:** a corrected on-policy read
  (slot = the marker's own position inside the model's own response, no turn-end
  in the prefix, no decode→re-encode) on the SAME #664 adapters lands the source
  `log P(※)` trained − base in [5, 12] nat (d1) / [10, 16] (d2), matching the
  in-loop band-stop within ~2 nat. **Falsify:** corrected on-policy source read
  still < 5 nat → the install genuinely doesn't survive on-policy generation
  (escalate to H2).
- **H1 (CONFIRMATORY):** Model is NOT the cause at the recipe line. **Predict:** a
  matched base-vs-Instruct fresh train at #664's exact recipe band-stops in-band
  on BOTH and reads in-band on-policy on BOTH (corrected slot). **Falsify (the
  surprising outcome):** base reads in-band on-policy but Instruct does not, with
  the corrected slot — model resistance is real and specific to the Instruct chat
  template / EOS competition.
- **H2 (CONDITIONAL FALLBACK, runs only if H3 falsifies):** dose. A controlled
  lr × steps mini-sweep on Instruct locates the on-policy [5, 12]-nat window.
  **Predict (per #601):** raising STEPS (4× #664 budget) at lr ≤ 5e-6 lands the
  band; lr ≥ 1e-4 collapses to a repeater. **Falsify:** no (lr ≤ 5e-6, steps ≤ 4×)
  point reaches 5 nat on-policy → Instruct resists at the recipe line (a finding).

Quantitative success: corrected on-policy source `log P(※)` trained − base ∈
[5, 12] nat on ≥3/4 d1 sources, with bystanders below the argmax saturation
ceiling (so the read is in the usable, non-saturated regime).

### The slot fix (the single deliberate change for H3)

New small module `scripts/issue734_marker_reread.py` (NEW — the only new training-
adjacent code) reuses the existing primitives and changes ONLY the slot rooting:

```python
# Reuse the IN-LOOP probe's slot logic for the ON-POLICY read so the two
# reads are slot-identical by construction (this is the fix).
from explore_persona_space.train.sft import _build_source_probe_row  # the per-row fused builder
from explore_persona_space.eval.marker_logprob import compute_marker_slot_stats

def corrected_on_policy_slot(tokenizer, source_msgs, R_text):
    # R_text = the model's OWN greedy response, with its trailing <|im_end|>\n
    # AND any trailing marker stripped to the FIRST marker position.
    # Build the slot the SAME way the in-loop band-stop does: fuse
    # prompt + (R + marker) via apply_chat_template(add_generation_prompt=False),
    # find the marker subsequence, read logits[marker_start - 1].
    # NEVER decode->re-encode; thread token ids directly.
    full_ids = apply_chat_template(source_msgs + [{"role":"assistant",
                 "content": R_text + MARKER_TEXT}], add_generation_prompt=False)
    marker_start = find_subsequence(full_ids, [MARKER_ID])
    slot = marker_start - 1
    # read four floats (logp, z_marker, z_eos, logZ) trained AND base at `slot`
    return read_four_floats(model, full_ids, slot, MARKER_ID, IM_END_ID)
```

**Why code, not a model call?** This is a deterministic teacher-forced log-prob
read at a specific token slot — a single HF forward pass with exact index math.
No model-call formulation exists (we need the raw pre-softmax logits per the
four-float storage contract; vLLM returns post-softmax only). N/A for a Claude
call.

**Contrastive negatives:** REUSED unchanged from #664 — the 4-context panel

**Data source + realism tier:** Tier-4 programmatic (the marker token in a fixed
slot) — the named marker carve-out (`data-realism.md` / on-policy-completions.md):

## 7.5 Kill criteria (halt-and-report)

Concrete mid-run signals that STOP the run rather than press on:

- **Halt (code bug, not a finding):** the corrected-slot four-float read produces
  a NaN / non-finite, or fails the `find_subsequence(marker_id)` lookup, on ANY
  cell — the slot-rooting code is wrong; halt-and-report, fix the read, re-run.
  Do not interpret a non-finite as "no install".
- **Halt (reuse-fitness fail):** the Phase-1 apply-and-read parity probe on
  `mk_librarian_contra_d1_seed42` does NOT reproduce #664's in-loop band-stop
  value within ~2 nat (≈ +6.9 expected) — the gauge/load is wrong (check (g));
  halt before the sweep, diagnose the rsLoRA scaling / adapter load, do NOT trust
  the corrected sweep until parity holds.
- **Stop early (H3 confirmed):** after Phase 1, if the corrected on-policy source
  read recovers the +5.6–12.3 nat in-loop band on ≥3/4 d1 sources, H3 is
  confirmed — the headline is answered; H1 still runs as the confirmatory model
  comparison, but Phase 3 (H2 dose sweep) is NOT triggered.
- **Branch to H2 (H3 falsified):** corrected on-policy source read still < 5 nat
  on ≥3/4 cells while the in-loop band-stop was in-band → the install does not
  survive on-policy generation; halt the Phase-1 interpretation, escalate to the
  Phase-3 dose sweep.
- **Escalate (H1 surprise — falsifies H3 AND H1):** if H1 base reads in-band
  on-policy at the corrected slot but Instruct does NOT, with the recipe held
  exact, model resistance is real and Instruct-specific — stop and report this as
  the finding (do NOT silently chase recipe knobs); it reframes the whole Goal.

## 11. Decision Rationale

All H1 fresh-train cells share ONE recipe (the #664 marker recipe). One source
citation per unique value:

- **marker lr = 5e-6.** Why: the clean window is lr ≤ 5e-6 (lr ≥ 1e-4 →
  unconditional ` ※`-repeater); strength bought via STEPS not lr; this is the
  install slot the H3 read must recover. `Source: marker-training-recipe.md +
  #474/#601/#650.` Alternatives: 1e-5 (#601 used it cleanly but is 2× the documented
  clean ceiling — rejected to stay at #664 parity, the single-variable contract);
  1e-4 rejected (repeater cliff).
- **rsLoRA r=32 / α=64 / dropout 0.05 / targets q/k/v/o (`use_rslora=True`).** Why:
  matched to #664 exactly so H1's only deliberate variable is model.
  `Source: #664 adapter_config.json (verified on Hub).` Alternatives: all-linear
  (#601/#650) rejected — would change a second variable vs #664.
- **marker + end-of-turn loss (response masked).** Why: trains "emit marker then END
  the turn" (no repeater), keeps R on-policy. `Source: marker-training-recipe.md +
  marker-leakage-measurement.md.` Alternative: whole-completion loss ruled out.
- **band-stop [5,12] d1 / [10,16] d2, eval every 5, min 10 steps, 3-epoch ceiling.**
  Why: deterministic stop on the metric, gated on bystander resolution; doses differ
  by STEPS at the same lr. `Source: marker-training-recipe.md (epoch-1 band-stop) +
  #664.` Alternative: fixed epochs rejected (doesn't transfer per-source).
- **marker token id 83399 (` ※`).** Why: single-token, clean trajectory DV; bare ※
  (63680) is the wrong token. `Source: marker-leakage-measurement.md.`
- **batch 4 × grad-accum 4, warmup_ratio 0.05, wd 0.01, bf16, AdamW, seq 3072.** Why:
  matched to #664's marker recipe verbatim. `Source: #664 (issue664_common.recipe_for("marker")).`
- **seeds {42, 137, 256} (H1).** Why: 3 seeds give per-model stability for the
  base-vs-Instruct comparison at near-zero marginal cost. `Source: #650 (3-seed marker
  precedent).` Alternative: single seed rejected — H1 needs cross-model stability.
- **base Qwen-2.5-7B (H1 second model).** Why: the deliberate H1 variable; repo
  already used by #474 + many prior tasks → inherits validation, no CPU config-smoke
  needed. `Source: #474.`
